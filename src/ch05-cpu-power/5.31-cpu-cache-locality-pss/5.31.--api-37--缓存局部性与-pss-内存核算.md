## 这两个指标属于不同层级

Android 17 / API 37 没有引入一套把 CPU cache locality 与 PSS 合并计算的新机制。二者可能在同一次性能调查中出现，但数据来源与解释范围不同：

| 观察对象 | 粒度 | 回答的问题 | 常用证据 |
| --- | --- | --- | --- |
| CPU cache | cache line 与硬件 cache 层级 | 处理器访问热数据要付出多少代价 | Simpleperf PMU、Arm SPE、目标 SoC 拓扑 |
| PSS | resident page 及其映射关系 | 某进程应分摊多少驻留物理内存 | `smaps`、`smaps_rollup`、`dumpsys meminfo` |

一页内存已经计入 RSS/PSS，并不表示它的 cache line 正位于当前 CPU 的 L1 或 L2。一次 L1D miss 也不会改写这页的 PSS。数据布局优化有时会同时影响两者，例如减少装箱对象后，工作集和被触碰的页都可能缩小；报告仍需分别展示 cache event、CPU time、page fault、RSS 和 PSS，不能从一条曲线推导另一条曲线。

CPU cache 还要与 Linux page cache 分开。文件映射页只有在映射到进程且驻留后，才进入该进程的 file-backed RSS/PSS 核算。未映射到该进程的 page-cache 页面不会计入它的 PSS。

## PSS 的核算边界

PSS（Proportional Set Size）把私有 resident page 全额计给进程，并把共享 resident page 按映射数分摊。Android common kernel `android17-6.18-2026-06_r6` 的 `fs/proc/task_mmu.c` 遍历 VMA 与页表，依据 page/folio mapcount 累计相应份额。

这个数值具有以下边界：

- 同一共享页会按映射数分摊，多个进程的 RSS 因此不能直接相加；
- mapcount 和页表可能在读取期间变化，采样是一个时间窗口内的近似快照；
- USS 由私有 clean/dirty resident pages 合成，不等于 Java heap；
- SwapPss 描述共享换出页的分摊量，与 resident PSS 要分列理解；
- GPU 和其他设备内存可能需要 memtrack 补充，不能只依赖 `/proc/<pid>/smaps`。

Android 17 的 `libmeminfo` 会在完整 `smaps`、`smaps_rollup` 和较低成本的状态字段之间选择采集路径。`Debug.getMemoryInfo()`、`Debug.getPss()`、`Debug.getRss()`、`ActivityManager.getProcessMemoryInfo()` 和 `AppProfiler` 的调用权限、返回字段、缓存或采样策略不同，不能只因单位都是 KiB 就互换。

## 可复核的联合实验

若优化目标同时涉及 CPU 时间和内存占用，可采用固定构建、固定设备状态和相同 workload：

1. 记录 CPU 型号、cache topology、页大小、进程集合和采集工具版本；
2. 用 Simpleperf 采集 cycles、instructions、L1D refill 等目标设备支持的 PMU 事件；
3. 在稳定时间点采集 `dumpsys meminfo`，必要时读取 `smaps_rollup`；
4. 检查 major/minor fault、线程迁移、GC、温度和频率变化；
5. 分别报告 PMU 事件率、CPU time、RSS/PSS/USS 和业务耗时；
6. 用多轮样本与置信区间判断变化，避免把一次采样噪声写成机制结论。

cache miss 降低而 PSS 不变，说明热路径访问更局部，但驻留页集合大致相同。PSS 降低而 PMU 指标不变，常见原因是对象数量、映射页、共享关系或释放时机发生变化。两组指标都改善时，还要通过 allocation、映射和调用栈证据确认中间原因。
