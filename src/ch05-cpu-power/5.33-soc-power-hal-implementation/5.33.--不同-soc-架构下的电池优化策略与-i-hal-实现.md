# Android 17 不同 SoC 架构下的电池优化策略与 IPower HAL 实现

<!-- outline-start -->
## 要点

### 🔹 GPU功耗管理基础
Android 17 引入了全新的 GPU 功耗管理策略，基于 DVFS（动态电压频率调节）机制的深度优化。

### 🔹 DVFS 调优算法
新算法结合了应用负载预测和系统资源监控，实现了更智能的频率和电压调节。

### 🔹 多核心协调机制
跨 GPU 核心的功耗分配协调，根据不同应用场景动态调整核心工作状态。

### 🔹 热量控制与性能平衡
在控制 GPU 发热的同时保持最佳的性能表现，引入了热量感知的调度策略。

### 🔹 SoC 厂商定制化
支持不同 SoC 厂商的定制化 DVFS 策略，充分发挥硬件性能潜力。

## 扩展

### 🔸 游戏场景优化
针对游戏场景的特殊功耗优化策略，平衡帧率和功耗的关系。

### 🔸 AI 推理任务
AI 推理任务在 GPU 上的功耗管理，考虑模型大小和推理频率的影响。

### 🔸 后台任务处理
后台 GPU 任务的功耗管理策略，避免不必要的资源占用。

## 1. IPower 是跨设备契约

本文的平台锚点为 Android 17 / API 37 / `android-17.0.0_r1`，内核锚点为 `android17-6.18-2026-06_r6`。Android 17 冻结的 `android.hardware.power` AIDL 是 v7，默认服务身份为 `android.hardware.power.IPower/default`。

AIDL 统一了请求语义，没有统一厂商内部执行方式。v7 的 19 个 `Mode`、6 个 `Boost`、Hint Session 和 headroom 查询可以由设备按能力实现。调用方需要检查 `isModeSupported()`、`isBoostSupported()` 或 `getSupportInfo()`；枚举存在只说明协议允许该请求。

一个可维护的 vendor service 通常拆成以下职责：

| 模块 | 职责 | 评审重点 |
| --- | --- | --- |
| Binder 接口层 | 校验 AIDL 参数，处理版本与错误 | 不让非法值或死亡客户端破坏服务 |
| 状态层 | 跟踪 mode、boost、session 与过期时间 | enable/disable 幂等，临时请求可撤销 |
| 仲裁层 | 合并性能、thermal、battery saver 等约束 | 安全上限能够压过性能请求 |
| 执行层 | 调用内核、daemon 或固件接口 | 写入失败可见，节点缺失可降级 |
| 观测层 | 输出 dump、trace、计数和当前 vote | 能从请求追到生效资源与撤销结果 |

这种拆分是工程建议，不属于 AIDL 强制架构。产品可以采用其他实现，只要服务合同、生命周期、安全边界和测试结果满足平台要求。

## 2. 服务集成检查

Power HAL 能启动还不代表系统可以稳定使用。设备实现至少要使以下配置一致：

- VINTF manifest 声明 AIDL v7 与 `IPower/default`；
- init service 的可执行文件、用户组、class 和重启策略正确；
- SELinux domain、service context、binder call 与资源访问权限匹配；
- 稳定 AIDL 生成库和 vendor 分区依赖满足 VNDK/VINTF 约束；
- `PowerHalController` 能连接服务，服务重启后客户端可恢复；
- 不支持的 Mode、Boost、session 或 headroom 能力按合同返回；
- VTS 覆盖支持查询、调用、重复启停和异常参数。

AOSP reference Power HAL 用于展示接口形状。它对许多请求只保存状态或返回不支持，不能当作商品设备的省电算法，也不能据此推导频率、功率或响应时延。

## 3. 请求要有清晰的生命周期

`Mode`、`Boost` 与 Hint Session 不能共用一套无过期状态：

- `Mode` 从 enable 持续到对应 disable；重复调用应保持幂等；
- `Boost` 带持续时间，新请求是覆盖、延长还是并存，需要由实现定义并测试；
- Hint Session 持有线程集合与周期预算，close、进程死亡和线程退出都要释放资源；
- thermal、充电安全和硬件保护属于独立上限，不能被性能请求绕过。

资源仲裁时应记录 vote 的来源、创建时间、过期时间、目标资源和撤销原因。若多个客户端同时提出最小频率与最大频率约束，实现还要定义冲突优先级，并保证请求结束后恢复到剩余 vote 的合成结果，而非无条件清零。

把 mode 映射为 sysfs 写入时，要验证节点所有者、单位、值域和失败路径。节点名称可能随 kernel、driver 或产品配置变化。配置驱动可以减少硬编码，却不能代替权限检查、原子更新、回滚和升级兼容测试。

## 4. 不同 SoC 能从公开源码确认什么

Android common kernel 包含多家厂商的公开驱动，可用于理解硬件控制类型：

- Qualcomm `qcom-cpufreq-hw` 展示硬件 LUT 和性能状态控制，RPMh 驱动展示资源请求通道；
- MediaTek 同时有软件调压路径和硬件 LUT 路径，不同 compatible data 的能力不同；
- Samsung 公开的 Exynos TMU 展示一类热传感与 cooling 设备集成。

这些驱动只能证明相应 Linux 实现存在。它们不能证明某台量产设备启用了该驱动，也不能证明用户空间 Power HAL 会按固定顺序调用它。商品设备还可能使用专有 daemon、固件、vendor module、设备树参数或完全不同的内核分支。

跨 SoC 文档应把证据分成四类：

1. AOSP/AIDL 能确认的接口合同；
2. Android common kernel 能确认的通用或公开厂商驱动；
3. 目标产品源码、配置和 VINTF 能确认的实现；
4. trace、功率计和实验能够确认的运行行为。

缺少第 3 类证据时，不能写出厂商私有调用关系。缺少第 4 类证据时，也不能把代码路径直接写成省电收益。

## 5. 从请求验证到能耗验证

一轮 OEM 验证应覆盖完整生命周期：

1. 确认服务版本、instance、能力列表和 active cpufreq/cpuidle 配置；
2. 触发单一 mode、boost 或 session，记录 Binder 请求与 HAL trace；
3. 检查仲裁状态、内核约束、频率、idle、thermal 和资源写入错误；
4. 结束请求并确认 vote、QoS 与临时限制按时撤销；
5. 模拟 HAL 重启、客户端死亡、超时和节点写入失败；
6. 在固定 workload 下采集业务耗时、能量、温度与稳定性；
7. 用多轮对照样本判断收益，并保留 build、配置和测量工具版本。

频率上升只是一项中间观测。电池优化需要比较完成同一工作量所消耗的能量，同时确认响应、温度、持续性能与待机没有退化。
