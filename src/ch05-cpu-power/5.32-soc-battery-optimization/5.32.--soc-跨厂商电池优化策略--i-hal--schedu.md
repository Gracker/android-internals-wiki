# Android 17 SoC 跨厂商电池优化策略、IPower HAL 与 schedutil

<!-- outline-start -->
## 要点

### 🔹 GPU功耗管理基础
Android 17 引入了全新的 GPU 功耗管理策略，基于 DVFS（动态电压频率调节）机制的深度优化。

### 🔹 DVFS 调优算法
新算法结合了应用负载预测和系统资源监控，实现了更智能的频率和电压调节。

### 🔹 多核心协调机制
跨 GPU 核心的功耗分配协调，根据不同应用场景动态调整核心工作状态。

### 🔹 热量控制与性能平衡
在控制 GPU 发热的同时保持最佳的性能表现，引入了热量感知的调度策略。

### 🔹 SoC 厂商定制化
支持不同 SoC 厂商的定制化 DVFS 策略，充分发挥硬件性能潜力。

## 扩展

### 🔸 游戏场景优化
针对游戏场景的特殊功耗优化策略，平衡帧率和功耗的关系。

### 🔸 AI 推理任务
AI 推理任务在 GPU 上的功耗管理，考虑模型大小和推理频率的影响。

### 🔸 后台任务处理
后台 GPU 任务的功耗管理策略，避免不必要的资源占用。

## AOSP 规定接口，不规定厂商策略图

本文的平台锚点为 Android 17 / API 37 / `android-17.0.0_r1`，内核锚点为 `android17-6.18-2026-06_r6`。这两份源码能确认公共接口、调度算法和频率请求路径，却不能证明某款商品 SoC 使用了哪个固件消息、sysfs 节点、boost 时长或电压表。

Android 17 冻结的 `android.hardware.power` AIDL 是 v7。接口包含 19 个 `Mode` 和 6 个 `Boost`，还支持 ADPF Hint Session 与 CPU/GPU headroom 查询。独立的 `android.hardware.power.stats` AIDL 负责电源实体与能耗统计。每项能力都要通过接口查询或目标机枚举确认；接口出现于 AIDL 不代表设备必须支持，也不代表 AOSP reference HAL 已实现对应算法。

Framework、HAL 与 kernel 可按职责拆开：

| 组件 | 输入 | 输出或作用 |
| --- | --- | --- |
| `PowerManagerService` | 亮灭屏、交互、启动等系统场景 | 调用 mode 或 boost 路径 |
| `HintManagerService` / ADPF | 线程集合、目标工作时长、已完成工作时长 | 建立并更新 hint session |
| `IPower` AIDL | mode、boost、session、headroom 查询 | 把标准请求交给 vendor service |
| vendor Power HAL | 标准请求与设备私有状态 | 按产品策略调整可用资源约束 |
| scheduler / `schedutil` | 任务利用率、capacity、uclamp、频率限制 | 计算并提交 CPUFreq 目标 |
| cpuidle governor | 预计空闲时长、idle state 属性 | 选择本次 CPU idle state |

Power HAL 厂商实现可能更新 uclamp、cpufreq/devfreq、内存带宽或 idle 约束，也可能忽略不支持的 hint。AOSP 没有规定一条固定的 `IPower → schedutil` 直连路径。若设备建立了这种映射，文档必须引用该产品的 HAL、内核配置、vendor module 或 trace 证据。

## Mode、Boost 与 Hint Session 不可混写

三种输入的生命周期不同：

- `Mode` 表示可启用和取消的较长状态，调用方要成对管理 enable/disable；
- `Boost` 表示有时限的临时请求，duration 和取消规则由 AIDL 合同与实现共同约束；
- Hint Session 面向一组长寿命线程的周期工作，持续报告目标和完成时长。

`IPower.setMode()` 与 `setBoost()` 是 `oneway` 调用。Binder 事务排队成功只表明请求已经交给服务端，不能证明频点或硬件状态已经变化。普通应用也不能直接调用 `PowerManagerService` 的受限 mode/boost Binder API；应用侧公开入口主要是 ADPF 的 `PerformanceHintManager` 等接口。

Framework 的 mode/boost 路径不会统一经过一个固定 200 ms 聚合器。`PowerManagerService` 对 `LAUNCH` mode 存在省电策略过滤，随后通过 JNI 和 `PowerHalController` 连接 HAL。代码中的 `DIRTY_*` 位用于电源状态重计算，不宜概括所有 power hint 的传递方式。

## schedutil 只负责 CPUFreq 决策

`schedutil` 从调度器读取 utilization、CPU capacity、uclamp 与当前限制，换算 CPUFreq 请求。它不解析 AIDL `Mode`，也不直接管理 GPU、内存带宽、充电或电池健康。

`sugov_should_update_freq()` 会考虑 cpufreq driver 的限制变化、频率更新间隔和 policy 状态。`rate_limit_us` 控制更新节奏，但驱动是否支持 fast switch、policy 是否共享、频点表粒度和热限制都会影响可观察延迟。不能把某个设备的毫秒数写成 Android 17 通用常量。

EAS、Energy Model 与 cpuidle 也有各自职责：

- EAS 在候选 CPU 之间估算任务放置的能耗；
- Energy Model 提供性能域的 performance、frequency、power 和 cost 数据；
- cpuidle governor 从驱动注册的 idle states 中选择状态；
- 热框架和固件可继续压低频率或功率，即使 Power HAL 请求更高性能。

一次“请求后频率升高”的时间相关性不足以确认控制来源。调试时还要检查 utilization、uclamp、thermal pressure、cpufreq policy、active governor、driver trace 和其他并发 vote。

## 跨 SoC 比较方法

跨厂商实验应比较公共行为，不要假定内部节点同名：

1. 记录 build fingerprint、kernel tag/config、Power HAL AIDL 版本与支持能力；
2. 枚举 `Mode`、`Boost`、Hint Session、headroom 和 power stats 支持情况；
3. 固定 workload、屏幕、网络、温度、充电状态与后台进程；
4. 同时采集 Power HAL 调用、scheduler、uclamp、CPUFreq、CPU idle、thermal 和电源计量数据；
5. 区分请求时间、约束更新时间、频率变化和任务完成时间；
6. 采用启用/禁用对照与多轮样本，报告性能、能量和温度分布；
7. 把厂商专有推断标为产品结论，不上升为 Android 17 平台规则。

优化是否有效，要由业务工作量相同条件下的能量、耗时、温度与稳定性共同验证。只看瞬时频率，无法判断 race-to-idle 是否缩短总运行时间，也无法判断高频请求是否被热约束抵消。
