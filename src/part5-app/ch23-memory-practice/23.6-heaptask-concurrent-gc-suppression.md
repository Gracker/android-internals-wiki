# 23.6 Android 17 ART HeapTask 并发与 GC 抑制源码级机制

> 本节从**内存优化实战**角度剖析 ART HeapTask 并发机制与 GC 抑制技术。HeapTask 调度管线的架构与 7 种子类详见 [4.21](../part1-fundamentals/ch04-memory/4.21-art-heaptask-scheduling-pipeline.md)；启动场景下的 GC 抑制策略详见 [21.13](../part5-app/ch21-startup/13-art-gc-suppression-startup-performance.md)。本节聚焦：GC 抑制如何服务于**内存容量管理**而非启动速度。

[结构参考: Clippings/Android 性能优化 - 如何通过 GC 抑制来提升启动速度？.md + Clippings/Android 性能优化 - 物理内存优化实战：Java Heap 内存优化.md]

## ConcurrentGCTask 触发链路源码分析

[已验证: AOSP android-17.0.0_r1, art/runtime/gc/heap-inl.h + heap.cc]

### 分配路径上的 GC 触发判断

ART 虚拟机中所有 Java 对象分配都经过 `Heap::AllocObjectWithAllocator()`，该方法在完成分配后立即检查是否需要触发并发 GC：

```cpp
// art/runtime/gc/heap-inl.h
template<bool kInstrumented, bool kCheckLargeObject, bool PreFenceVisitor>
inline ObjPtr<mirror::Object> Heap::AllocObjectWithAllocator(
    Thread* self, ObjPtr<mirror::Class> klass, size_t byte_count,
    AllocatorType allocator, const PreFenceVisitor& pre_fence_visitor) {

  // 1. 大对象判断：>= large_object_threshold_（默认 3 页 = 12KB）
  if (kCheckLargeObject && UNLIKELY(ShouldAllocLargeObject(klass, byte_count))) {
    obj = AllocLargeObject<kInstrumented, PreFenceVisitor>(self, &klass, byte_count, ...);
    // 大对象分配后同样检查 GC 触发条件
  }

  // 2. 主空间分配
  obj = TryToAllocate<kInstrumented, false>(self, allocator, byte_count, ...);

  // 3. 分配后检查并发 GC 触发条件
  if (allocator != kAllocatorTypeLOS) {
    size_t new_target = num_bytes_allocated_.load(std::memory_order_relaxed) + byte_count;
    if (new_target >= concurrent_start_bytes_) {
      // 触发并发 GC
      RequestConcurrentGCAndSaveObject(self, ...);
    }
  }
}
```

**触发判断的核心变量**：

| 变量 | 类型 | 作用 |
|------|------|------|
| `num_bytes_allocated_` | `Atomic<size_t>` | 全局已分配字节数（所有 Space 共享） |
| `concurrent_start_bytes_` | `Atomic<size_t>` | 并发 GC 触发水位线 |
| `growth_limit_` | `size_t` | Java 堆上限（通常 256M/512M） |
| `target_footprint_` | `Atomic<size_t>` | 目标内存足迹（动态调整） |

### RequestConcurrentGCAndSaveObject 调用链

当 `num_bytes_allocated_` 超过 `concurrent_start_bytes_` 时，触发以下链路：

```
AllocObjectWithAllocator
  → RequestConcurrentGCAndSaveObject(self, origin, forceFG)
    → RequestConcurrentGC(self, forceFG)
      → CanAddHeapTask(self)          // 守门检查
      → AddTask(self, new ConcurrentGCTask(...))  // 加入任务队列
```

[已验证: AOSP android-17.0.0_r1, art/runtime/gc/heap.cc]

```cpp
// art/runtime/gc/heap.cc
void Heap::RequestConcurrentGCAndSaveObject(Thread* self, GcCause cause,
                                            bool forceFG, size_t bytes_allocated) {
  if (IsGcConcurrentAndMoving()) {
    RequestConcurrentGC(self, forceFG);
  }
  // 保存对象引用，防止 GC 过程中对象被移动
  if (bytes_allocated != 0) {
    Runtime::Current()->GetConcurrentGc()->SaveObject(...);
  }
}

void Heap::RequestConcurrentGC(Thread* self, bool force_full) {
  // 守门：检查是否可以添加 HeapTask
  if (!CanAddHeapTask(self)) {
    return;
  }
  // 创建 ConcurrentGCTask 并加入 TaskProcessor 队列
  GetTaskProcessor()->AddTask(self,
      new ConcurrentGCTask(NanoTime(), force_full, ...));
}
```

**关键结论**：ConcurrentGCTask 的触发完全由 `num_bytes_allocated_` 与 `concurrent_start_bytes_` 的比较决定。这两个变量都存储在 Java 堆的 Heap 对象中，是后续 GC 抑制和 mSponge 技术的作用靶点。

### CanAddHeapTask 守门条件

[已验证: AOSP android-17.0.0_r1, art/runtime/gc/task_processor.cc]

```cpp
bool TaskProcessor::CanAddHeapTask(Thread* self) {
  // 1. 检查是否正在运行 GC
  if (is_running_.load(std::memory_order_relaxed)) {
    return false;
  }
  // 2. 检查是否有正在排队的 GC 任务
  MutexLock mu(self, tasks_lock_);
  for (auto& task : tasks_) {
    if (task->GetTargetRunTime() <= NanoTime()) {
      return false;  // 有到期任务待执行，不重复添加
    }
  }
  return true;
}
```

这个守门条件是 GC 抑制方案的**关键约束**：它不会阻止 Hook 方案（因为 Hook 直接修改虚函数表，绕过 `Run()` 的执行），但会阻止"添加自定义阻塞任务"方案在已有到期任务时生效。

## GC 抑制技术体系

GC 抑制有三种主要技术路线，各有不同的适用场景和风险等级：

| 技术路线 | 原理 | 影响范围 | 风险等级 | 适用版本 |
|----------|------|----------|----------|----------|
| 虚函数 Hook | 替换 `ConcurrentGCTask::Run()` 虚函数指针 | 阻断并发 GC 执行 | 中高 | Android 8-17 |
| num_bytes_allocated_ Hook (mSponge) | 修改已分配字节数统计 | 突破堆容量限制 | 高 | Android 8-17 |
| TaskProcessor 阻塞 | 注入自定义长时间任务 | 阻塞整个 HeapTaskDaemon | 中 | Android 8-17 |

### 路线一：虚函数 Hook ConcurrentGCTask::Run()

[已验证: AOSP android-17.0.0_r1, art/runtime/gc/task_processor.h]

此方案在 [21.13](../part5-app/ch21-startup/13-art-gc-suppression-startup-performance.md) 中已有启动场景的完整实现。本节补充**内存管理场景**下的差异化应用。

**继承体系与虚函数表结构**：

```
Closure
  └─ virtual void Run(Thread* self) = 0
Task : Closure
  └─ virtual void Finalize() {}
SelfDeletingTask : Task
  └─ void Finalize() override { delete this; }
HeapTask : SelfDeletingTask
  └─ uint64_t target_run_time_
  └─ friend class TaskProcessor
```

所有 HeapTask 子类通过虚函数表实现多态。`TaskProcessor::RunAllTasks()` 调用 `task->Run(self)` 时，实际执行的是虚函数表中 `Run` 槽位指向的函数。

**Hook 实现核心步骤**：

```cpp
// 1. 定位 ConcurrentGCTask 的虚函数表
void *handle = dlopen("libart.so", RTLD_NOW);
void **vtable = (void **)dlsym(handle,
    "_ZTVN3art2gc4Heap16ConcurrentGCTaskE");

// 2. 找到原始 Run 函数地址（vtable 中 Run 的槽位）
//    Run 通常在 vtable 的第 N 个槽位（版本相关，需运行时搜索）
typedef void (*RunFunc)(void *, void *);
RunFunc originalRun = nullptr;

for (size_t i = 0; i < 64; i++) {
    // 通过 dladdr 验证槽位是否为 Run 方法
    Dl_info info;
    if (dladdr(vtable[i], &info) && 
        strstr(info.dli_sname, "ConcurrentGCTask") &&
        strstr(info.dli_sname, "Run")) {
        originalRun = (RunFunc)vtable[i];
        break;
    }
}

// 3. mprotect 修改内存页权限并替换
long pageSize = sysconf(_SC_PAGESIZE);
void *page = (void *)((uintptr_t)&vtable[slotIdx] & ~(pageSize - 1));
mprotect(page, pageSize, PROT_READ | PROT_WRITE);
vtable[slotIdx] = (void *)hookedRun;
mprotect(page, pageSize, PROT_READ);
```

**内存场景与启动场景的差异**：

| 维度 | 启动场景（21.13） | 内存场景（本节） |
|------|-------------------|-----------------|
| 目标 | 减少 CPU 争抢，加速启动 | 允许更多内存分配，突破临时容量瓶颈 |
| 抑制时长 | 3-5 秒 | 视场景而定，可达 10-30 秒 |
| 风险焦点 | 启动后 GC 风暴 | OOM 风险更高 |
| 监控重点 | CPU 占比、帧率 | Java 堆使用率、分配速率 |
| 结束策略 | P90 启动耗时 + 安全余量 | 内存水位达 80% 立即恢复 |

### 路线二：mSponge 黑科技 — Hook num_bytes_allocated_

[结构参考: Clippings/Android 性能优化 - 物理内存优化实战：Java Heap 内存优化.md]

**原理**：`num_bytes_allocated_` 是 ART Heap 对象中记录全局已分配字节数的原子变量。它作为 OOM 判断和 GC 触发的水位线。如果 Hook 这个变量使其返回一个小于实际值的数字，就能同时达到两个效果：

1. **推迟 GC 触发**：`num_bytes_allocated_` 不超过 `concurrent_start_bytes_`，ConcurrentGCTask 不会被创建
2. **突破堆容量限制**：`IsOutOfMemoryOnAllocation()` 判断中 `new_footprint > growth_limit_` 不成立，不会抛出 OOM

**LargeObjectSpace 特殊性**：

[已验证: AOSP android-17.0.0_r1, art/runtime/gc/heap-inl.h]

```cpp
inline bool Heap::IsOutOfMemoryOnAllocation(AllocatorType allocator_type,
                                            size_t alloc_size, bool grow) {
  size_t old_target = target_footprint_.load(std::memory_order_relaxed);
  while (true) {
    size_t old_allocated = num_bytes_allocated_.load(std::memory_order_relaxed);
    size_t new_footprint = old_allocated + alloc_size;
    if (new_footprint <= old_target) {
      return false;  // 未超目标，分配通过
    } else if (new_footprint > growth_limit_) {
      return true;   // 超过堆上限，OOM
    }
    // CAS 尝试更新 target_footprint_
    // ...
  }
}
```

LargeObjectSpace 分配的大对象（≥ 12KB 的基本类型数组和 String）**同样累加到 `num_bytes_allocated_`**。通过 Hook 使 LargeObjectSpace 的分配不计入统计，就能在 Java 堆名义使用率不变的情况下，实际使用更多内存。

**Hook 实现思路**：

```cpp
// 1. 通过 ELF 符号表定位 num_bytes_allocated_ 在 Heap 对象中的偏移
//    Heap 对象可通过 Runtime::Current()->GetHeap() 获取
void *handle = dlopen("libart.so", RTLD_NOW);

// 2. 定位 Heap 实例
//    Runtime 对象可通过 JavaVM->reserved0 获取
//    Heap 在 Runtime 中的偏移需根据版本确定
typedef void* (*GetHeapFunc)(void *);
GetHeapFunc getHeap = (GetHeapFunc)dlsym(handle, "...");

// 3. 获取 num_bytes_allocated_ 成员偏移
//    方法 A：从 .symtab 直接读取符号偏移
//    方法 B：通过已知的分配行为推断（分配 N 字节后观察变量增量）

// 4. Hook 策略：对 LargeObjectSpace 的分配减去对应大小
//    在自定义的 AllocLargeObject wrapper 中，分配后立即递减 num_bytes_allocated_
//
//    伪代码：
//    size_t before = num_bytes_allocated_.load();
//    obj = originalAllocLargeObject(...);
//    size_t delta = bytes_allocated;
//    num_bytes_allocated_.fetch_sub(delta);  // 抵消 LargeObjectSpace 的计数
```

**效果与风险**：

| 效果 | 风险 |
|------|------|
| LargeObjectSpace 分配不触发 GC | 实际内存使用远超虚拟机预期 |
| 突破 growth_limit_ 限制 | RSS 持续增长，可能触发 LMK |
| 可用于图片密集型场景 | GC 扫描时发现的存活对象数量与统计不符，可能导致 GC 内部状态不一致 |

⚠️ **重要风险提示**：mSponge 技术直接干预了 ART 内存统计的核心机制。在 Android 17 的分代 CC GC 环境下，年轻代（RegionSpace）的 `concurrent_start_bytes_` 阈值更低，如果 Hook 后实际分配速率过高，年轻代会快速填满，触发**同步 GC**（`kGcCauseForAlloc`），这种 GC 直接阻塞分配线程且**无法被虚函数 Hook 抑制**。

### 路线三：TaskProcessor 注入阻塞任务

**原理**：在 TaskProcessor 的任务队列中注入一个 `target_run_time_` 为当前时间的自定义任务，该任务的 `Run()` 方法执行长时间休眠。由于 `GetTask()` 在取出任务后会同步执行 `task->Run(self)`，这将阻塞整个 HeapTaskDaemon 线程。

```cpp
// 自定义阻塞任务
class BlockTask : public HeapTask {
public:
    BlockTask(uint64_t duration_ms) : HeapTask(NanoTime()), duration_ms_(duration_ms) {}

    void Run(Thread* self) override {
        usleep(duration_ms_ * 1000);  // 阻塞指定时长
    }

    void Finalize() override {
        delete this;
    }

private:
    uint64_t duration_ms_;
};

// 注入方式（需要获取 TaskProcessor 指针）
// TaskProcessor 的获取路径：
// Runtime::Current()->GetHeap()->GetTaskProcessor()
// 但 TaskProcessor::AddTask 不是公开 API，需要通过 JNI 或符号查找调用
```

**优势**：不需要修改虚函数表，仅利用公开的任务队列机制。

**劣势**：
1. `CanAddHeapTask()` 守门条件可能阻止添加（如果已有到期任务）
2. 需要获取 TaskProcessor 指针，在 Android 14+ 的 namespace 隔离下更困难
3. 阻塞期间**所有** HeapTask 都无法执行（包括 HeapTrimTask、ClearedReferenceTask），影响范围过大

## Android 17 新增 HeapTask 对抑制策略的影响

[已验证: AOSP android-17.0.0_r1, art/runtime/gc/heap.cc]

Android 17 引入的两个新 HeapTask 对 GC 抑制策略产生了重大影响。详细机制分析详见 [4.21](../part1-fundamentals/ch04-memory/4.21-art-heaptask-scheduling-pipeline.md)，此处仅列出对抑制策略的直接影响。

### TriggerPostForkCCGcTask 的强制 GC 窗口

```cpp
// art/runtime/gc/heap.cc:5113-5161
uint64_t post_fork_gc_time = last_adj_time
    + MsToNs(4 * kPostForkMaxHeapDurationMS + GetPseudoRandomFromUid());
GetTaskProcessor()->AddTask(self,
    new TriggerPostForkCCGcTask(post_fork_gc_time, starting_gc_num));
```

- fork 后约 **10-30 秒**（4×2s 基础 + 0-20s 随机偏移）强制触发一次后台 GC
- 这个 GC 任务**不受虚函数 Hook 影响**（因为 Hook 针对的是 ConcurrentGCTask 的虚函数表，而 TriggerPostForkCCGcTask 是不同子类）
- **应对策略**：如果需要同时抑制此任务，必须额外 Hook `TriggerPostForkCCGcTask::Run()` 的虚函数表槽位

### ReduceTargetFootprintTask 的双收缩机制

```cpp
// art/runtime/gc/heap.cc:5132-5151
size_t first_shrink_size = std::max(growth_limit_ / 4, initial_heap_size_);
last_adj_time += MsToNs(kPostForkMaxHeapDurationMS);  // +2s
GetTaskProcessor()->AddTask(self,
    new ReduceTargetFootprintTask(last_adj_time, first_shrink_size, ...));

if (initial_heap_size_ < first_shrink_size) {
    last_adj_time += MsToNs(4 * kPostForkMaxHeapDurationMS);  // +8s
    GetTaskProcessor()->AddTask(self,
        new ReduceTargetFootprintTask(last_adj_time, initial_heap_size_, ...));
}
```

- 在 fork 后 2 秒和 10 秒分别执行两次 `target_footprint_` 收缩
- 收缩后 `target_footprint_` 降低 → `concurrent_start_bytes_` 随之降低 → **GC 触发更频繁**
- **对 mSponge 的影响**：即使 Hook 了 `num_bytes_allocated_`，`target_footprint_` 的收缩仍会执行，但因为 `IsOutOfMemoryOnAllocation` 使用的 `old_allocated` 来自 Hook 后的值，所以 OOM 判断不受影响
- **对虚函数 Hook 的影响**：`ReduceTargetFootprintTask::Run()` 会调用 `SetIdealFootprint()`，这个操作直接修改内存管理参数，不会被 ConcurrentGCTask 的 Hook 拦截

### GetPseudoRandomFromUid 防风暴机制

```cpp
uint64_t GetPseudoRandomFromUid() {
    // 基于 UID 生成 [0, 20000) ms 的随机偏移
    return MsToNs(getuid() % 20000);
}
```

- 确保不同应用的 PostFork GC 不会在同一时刻集中触发
- **对抑制策略的影响**：增加了 GC 触发时间的不确定性，使得抑制方案的有效窗口在不同应用间存在差异

### Android 17 抑制策略适配矩阵

| 目标 Task | Hook 目标 | 兼容性 | 必要性 |
|-----------|-----------|--------|--------|
| `ConcurrentGCTask` | vtable Run 槽位 | ✅ 所有版本 | 高（最频繁触发的 GC 任务） |
| `TriggerPostForkCCGcTask` | vtable Run 槽位 | ✅ Android 17+ | 中（fork 后强制 GC） |
| `ReduceTargetFootprintTask` | vtable Run 槽位 | ✅ Android 17+ | 低（仅影响 target_footprint_，不直接触发 GC） |
| `num_bytes_allocated_` | 原子变量 Hook | ✅ 所有版本 | 高（同时抑制 GC 触发和 OOM 判断） |

## 生产环境部署与风险管控

### Android 14-17 兼容性约束

[已验证: AOSP android-17.0.0_r1, bionic linker namespace 限制]

Android 14 引入的 Native DCL（Dynamic Code Loading）安全限制对符号访问产生了显著影响：

| 版本 | dlopen("libart.so") | .symtab 可见性 | dlsym 符号查找 | 推荐方案 |
|------|---------------------|----------------|---------------|---------|
| Android 14 | ⚠️ 受限 | 部分符号不可见 | 可用但范围缩小 | dladdr 反查 |
| Android 15 | ⚠️ 受限 | 同上 | 同上 | dladdr + android_dlopen_ext |
| Android 16 | ❌ 困难 | 大部分不可见 | 严重受限 | 运行时地址推断 |
| Android 17 | ❌ 困难 | 大部分不可见 | 严重受限 | 运行时地址推断 + 降级方案 |

**推荐兼容策略**：

1. **符号定位优先级**：
   - 首选 `dladdr()` 对已知函数地址反查符号（绕过 .symtab 限制）
   - 次选 `android_dlopen_ext()` 配合正确的 linker namespace
   - 最后选运行时行为推断（分配已知大小对象，观察变量增量）

2. **降级策略**：
   - 符号不可用时自动降级为非 Hook 方案
   - 记录降级事件到监控平台

3. **OEM 差异**：
   - Pixel/Nexus 设备：符号可见性最好，可作为基准验证设备
   - MIUI/ColorOS：可能额外加固 libart.so，需逐设备验证
   - 游戏模式设备：PostFork 窗口可能被 OEM 延长

### OOM 风险评估与内存安全线

GC 抑制期间，内存只分配不回收，Java 堆持续增长。必须建立多层安全线：

| 安全线 | 触发条件 | 动作 | 优先级 |
|--------|---------|------|--------|
| 黄色预警 | Java 堆使用率 > 70% | 日志记录，准备恢复 | 低 |
| 橙色预警 | Java 堆使用率 > 80% | 立即恢复 GC（取消 Hook） | 高 |
| 红色警报 | Java 堆使用率 > 90% | 强制触发 `System.gc()` + 告警 | 紧急 |
| 终极保护 | `onLowMemory()` 回调 | 释放缓存 + GC + 拒绝新分配 | 系统级 |

**安全线实现**：

```java
public class GCSuppressionGuard {
    private static final long MAX_SUPPRESSION_MS = 10_000;  // 最长 10 秒
    private volatile long suppressionStartTime;
    private volatile boolean isActive = false;

    // 内存监控线程（每 200ms 检查一次）
    private final Thread monitor = new Thread(() -> {
        while (isActive) {
            Runtime rt = Runtime.getRuntime();
            long used = rt.totalMemory() - rt.freeMemory();
            double ratio = (double) used / rt.maxMemory();

            if (ratio > 0.90) {
                emergencyRelease();
            } else if (ratio > 0.80) {
                releaseSuppression();
            }

            if (System.currentTimeMillis() - suppressionStartTime > MAX_SUPPRESSION_MS) {
                releaseSuppression();  // 超时强制恢复
            }

            try { Thread.sleep(200); } catch (InterruptedException ignored) {}
        }
    });

    public void startSuppression() {
        isActive = true;
        suppressionStartTime = System.currentTimeMillis();
        monitor.start();
        // 执行 Native Hook
    }

    public void releaseSuppression() {
        if (!isActive) return;
        isActive = false;
        // 恢复虚函数表
        // 触发一次主动 GC 释放积压
        System.gc();
    }

    private void emergencyRelease() {
        releaseSuppression();
        // 额外清理：释放图片缓存等
    }
}
```

### 线上监控指标体系

| 指标 | 采集方式 | 正常范围 | 告警阈值 |
|------|---------|---------|---------|
| 抑制期间 Java 堆使用率 | `Runtime.getRuntime()` | < 70% | > 85% |
| 抑制结束后首次 GC 耗时 | Perfetto / Trace | < 50ms | > 100ms |
| 抑制期间 OOM 发生率 | ApplicationExitInfo | 0 | > 0 |
| RSS 峰值 | `/proc/self/status` VmRSS | < maxMemory()×1.2 | > maxMemory()×1.5 |
| 抑制期间分配速率 | 自定义分配计数器 | < 10MB/s | > 50MB/s |
| Hook 成功率 | Native 端上报 | > 95% | < 80% |

### 不适用场景

以下场景**不建议使用 GC 抑制**：

1. **低内存设备（< 3GB RAM）**：可用堆空间小，抑制期间 OOM 风险极高
2. **图片/视频编辑应用**：启动阶段即需大量内存分配，与 GC 抑制冲突
3. **长时间运行的服务**：GC 抑制收益场景短，风险随时间线性增长
4. **Android 14+ 未验证设备**：符号可见性不确定，Hook 失败率不可控
5. **已启用分代 GC 的应用**：年轻代 GC 频率更高，同步 GC 无法被抑制

## 扩展

### 🔸 替代方案：非 Hook 路径的内存优化

当 Hook 方案不可用或风险过高时，以下非侵入式方案可在一定程度上替代 GC 抑制：

**VMRuntime 接口方案**：

```java
// 注册敏感线程，减少 GC 对分配操作的阻塞
VMRuntime.getRuntime().registerSensitiveThread();

// 请求推迟后台 GC（效果有限，仅对某些 OEM 生效）
// 注意：非公开 API，需反射调用
Method method = VMRuntime.class.getDeclaredMethod("requestConcurrentGC");
```

**分配控制方案**：

- **对象池复用**：对高频创建的临时对象使用对象池，减少分配压力
- **延迟初始化**：将非关键路径的对象初始化推迟到空闲时段
- **预分配策略**：在应用启动早期预分配所需内存，避免在关键路径触发 GC
- **LargeObjectSpace 感知**：对于 > 12KB 的数组/String，注意其会触发独立的 GC 路径

**Android 17 特性利用**：

- `StartupCompletedTask`：通过 `VMRuntime.notifyStartupCompleted()` 及时通知启动完成，触发 dex cache 清理和 runtime image 生成，有助于后续内存优化
- `ReduceTargetFootprintTask` 的收缩行为：虽然降低了 `target_footprint_`，但也意味着系统认为应用需要更少内存，可通过合理的初始堆配置降低 GC 频率

### 🔸 GC 抑制在非启动内存密集场景的应用

GC 抑制思路可推广到启动以外的内存密集型场景：

**列表/图片密集滑动**：
- 在 `RecyclerView.onScrollStateChanged(SCROLL_STATE_DRAGGING)` 时启动短期抑制（500ms-1s）
- 在 `SCROLL_STATE_IDLE` 时立即恢复并触发 GC
- 滑动期间的对象分配速率通常远低于启动，OOM 风险可控

**Compose 重组密集期**：
- Compose 重组会产生大量短期 Lambda 对象和 State 对象
- 在已知的高频重组窗口（如动画过程中）短暂抑制 GC
- 需配合 Compose 性能监控（详见 [22.x] Compose 性能章节）确定抑制时机

**⚠️ 通用原则**：非启动场景的抑制窗口应严格控制在 1 秒以内，且必须有内存水位监控兜底。
