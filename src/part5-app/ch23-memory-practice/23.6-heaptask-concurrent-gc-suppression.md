# 23.6 Android 17 ART HeapTask 与“GC 抑制”的边界

以下分析以 AOSP `android-17.0.0_r1` 为准，回答三个容易混在一起的问题：

- Java 对象分配怎样请求一次并发 GC；
- `ConcurrentGCTask` 怎样排队、合并和执行；
- 应用能否通过修改 ART 内部状态来延后 GC。

普通应用没有受支持的 GC 抑制接口。Android 17 确有一段由 ART 管理的 post-fork 启动期策略，但它只是暂时放宽堆目标，并带有恢复条件，不等于禁止 GC。修改 `libart.so` 虚函数表、伪造 `num_bytes_allocated_` 或占用 `HeapTaskDaemon` 都不适合作为发布方案。

HeapTask 的完整类型、队列和生命周期见 [4.9 ART HeapTask 调度、启动维护与冻结边界](../../part1-fundamentals/ch04-memory/09-art-heaptask-scheduling-pipeline.md)；启动耗时分析见 [21.13 ART GC 抑制与启动性能优化](../ch21-startup/13-art-gc-suppression-startup-performance.md)。这里聚焦并发 GC 请求和应用内存治理的边界。

## 1. “并发”不是多个 HeapTask 并行执行

`HeapTaskDaemon` 是 `java.lang.Daemons` 创建的 Java 守护线程。它进入 `VMRuntime.runHeapTasks()` 后，由 native `TaskProcessor::RunAllTasks()` 反复取出到期任务。

`TaskProcessor` 使用按 `target_run_time_` 排序的 `std::multiset` 保存任务。一次循环只执行一个任务：

1. `GetTask()` 取出最早到期的 `HeapTask`；
2. 调用 `task->Run(self)`；
3. 调用 `task->Finalize()`；
4. 再取下一项。

所以，队列中的 HeapTask 是串行执行的。`ConcurrentGCTask` 名称里的 concurrent 描述的是收集器可与应用线程并发完成部分阶段，不表示多个 HeapTask 会在 `HeapTaskDaemon` 上并行运行。并发收集仍可能包含暂停应用线程的阶段，也会与应用争用 CPU 和内存带宽。

停止任务处理器也不是清空队列。`TaskProcessor::Stop()` 把 `is_running_` 设为 false 后，`GetTask()` 会忽略尚未到达的目标时间，依次返回剩余任务，直到队列排空。向该线程塞入长时间阻塞任务，会影响 GC 以外的堆裁剪、收集器切换、启动清理和定时检查。

[源码锚点：[`task_processor.h`](https://android.googlesource.com/platform/art/+/refs/tags/android-17.0.0_r1/runtime/gc/task_processor.h)、[`task_processor.cc`](https://android.googlesource.com/platform/art/+/refs/tags/android-17.0.0_r1/runtime/gc/task_processor.cc)、[`Daemons.java`](https://android.googlesource.com/platform/libcore/+/refs/tags/android-17.0.0_r1/libart/src/main/java/java/lang/Daemons.java)]

## 2. Java 分配怎样请求 ConcurrentGCTask

### 2.1 分配成功后更新堆记账

`Heap::AllocObjectWithAllocator()` 分配对象并完成必要的初始化后，会在取得一批新 TLAB 空间或发生其他需记账的分配时调用 `UpdateAndReportBytesAllocated()`。返回值是更新后的 Java 已分配字节数。

这里有两个阅读源码时必须保留的边界：

- `num_bytes_allocated_` 表示已分配且尚未回收的近似字节数；
- 活跃 TLAB 会整块计入，即使其中一部分尚未分给对象。

因此，这个字段不是逐对象精确求和，也不是进程 RSS。native 堆、图形内存、文件映射和交换页更不能用它代替。

### 2.2 Android 17 有阈值与基于时间的两种判定

并发收集器启用时，分配路径调用 `ShouldConcurrentGCForJava(new_num_bytes_allocated)`。它返回三种结果：

| 返回值 | 分配路径的动作 |
| --- | --- |
| `kNoNeedGc` | 不新增任务 |
| `kNeedGc` | 请求 `ConcurrentGCTask` |
| `kNeedGcThresholdCheck` | 安排 `TimeBasedGcThresholdCheckTask` |

未启用 time-based GC triggering，或该策略的阈值尚未建立时，判断是 `new_num_bytes_allocated >= concurrent_start_bytes_`。

启用 Android 17 的 time-based 分支且 `time_based_gc_threshold_` 非零时，ART 会综合 GC 后新增字节与经过时间计算进度。进度达到阈值便请求 GC；若应用停止分配后仅靠时间推移也会达到阈值，则安排一次定时复查。`concurrent_start_bytes_` 在这条分支中仍是接近堆限制前的保护条件。

这说明“只要伪造一个已分配字节字段，就能稳定控制 GC 时机”的前提已经不成立。即使忽略 time-based 分支，native allocation、显式请求、进程状态变化和分配失败也有各自的 GC 路径。

[源码锚点：[`Heap::AllocObjectWithAllocator()` 与 `ShouldConcurrentGCForJava()`](https://android.googlesource.com/platform/art/+/refs/tags/android-17.0.0_r1/runtime/gc/heap-inl.h)]

### 2.3 新对象为何需要临时保存在 Handle 中

下面的调用顺序用于理解分配成功到任务入队之间的对象安全，不是应用可调用的接口：

```text
AllocObjectWithAllocator()
  -> ShouldConcurrentGCForJava()
  -> RequestConcurrentGCAndSaveObject()
  -> RequestConcurrentGC()
  -> TaskProcessor::AddTask(ConcurrentGCTask)
```

`RequestConcurrentGCAndSaveObject()` 通过 `StackHandleScope` 和 `HandleWrapperObjPtr` 保护刚分配的对象。原因是 `TaskProcessor::AddTask()` 允许线程挂起；若移动式 GC 在此期间运行，Handle 能让局部对象引用随移动结果更新。它并不存在“把对象保存到某个全局并发 GC 对象池”的语义。

### 2.4 请求怎样去重

`RequestConcurrentGC()` 读取调用方观察到的 GC 序号，并围绕 `max_gc_requested_` 做原子比较交换。只有成功把最大请求序号推进到下一号的线程才创建 `ConcurrentGCTask`。别的线程若发现相同或更新的请求已经存在，会直接返回成功，不再重复入队。

任务运行时，`ConcurrentGC()` 又检查目标 GC 序号。若其他路径已经完成了足够新的 GC，这个请求不再重复收集。这个序号协议才是并发请求合并机制。

`CanAddHeapTask()` 也在这条路径上，但它不是“是否已有 GC 任务”的队列检查。Android 17 中它只验证：

- Runtime 已存在并完成启动；
- Runtime 没有关闭；
- 当前线程没有处理 native 栈溢出。

原先把 `CanAddHeapTask()` 描述成“检查 GC 是否正在运行并扫描到期任务”的说法，与 `android-17.0.0_r1` 源码不符。

[源码锚点：[`Heap::RequestConcurrentGC()`、`ConcurrentGCTask` 与 `CanAddHeapTask()`](https://android.googlesource.com/platform/art/+/refs/tags/android-17.0.0_r1/runtime/gc/heap.cc)]

## 3. 四个堆字段各自代表什么

| 字段 | Android 17 中的用途 | 不应怎样理解 |
| --- | --- | --- |
| `num_bytes_allocated_` | Java 堆已分配且未回收字节的近似值，包含完整活跃 TLAB | 不是 PSS，也不是逐对象精确值 |
| `concurrent_start_bytes_` | 并发 GC 的启动参考；time-based 策略下兼作临近堆限制的保护条件 | 不是 Java 堆上限 |
| `target_footprint_` | 非并发收集时的弱限制；并发收集时用于推导 GC 启动点 | 不是固定不变的容量 |
| `growth_limit_` | 当前 Java 堆增长限制，`largeHeap` 进程可能扩到 `capacity_` | 不是进程总内存限制 |

`IsOutOfMemoryOnAllocation()` 会用 `num_bytes_allocated_ + alloc_size` 与这些限制比较。源码还注明，多线程同时分配使这种检查只能近似执行。超过 `growth_limit_` 只是 Java 分配失败判断中的一环；进程也可能因 native、图形或文件页占用受到系统内存回收与进程终止策略影响。

大对象路径也不能简化为“所有超过 12 KB 的对象都进 LOS”。`ShouldAllocLargeObject()` 要同时满足运行时配置的 `large_object_threshold_`，并且对象是基本类型数组或 `String`。阈值来自当前 Runtime 配置，不应在跨设备文章里写成固定常量。

[源码锚点：[`heap.h` 字段定义](https://android.googlesource.com/platform/art/+/refs/tags/android-17.0.0_r1/runtime/gc/heap.h)、[`IsOutOfMemoryOnAllocation()` 与 `ShouldAllocLargeObject()`](https://android.googlesource.com/platform/art/+/refs/tags/android-17.0.0_r1/runtime/gc/heap-inl.h)]

## 4. ART 自己怎样减少启动期 GC 干扰

Android 17 的 `Heap::PostForkChildAction()` 为刚从 zygote fork 出来的应用进程设置一段临时策略：

1. 增加 GC 完成序号，使 fork 前后过早排入的旧请求失效；
2. 把 `target_footprint_` 临时提高到 `growth_limit_`；
3. 重新计算 `concurrent_start_bytes_`；
4. 清除尚未适用的 time-based 初始阈值；
5. 按堆配置安排零到两次 `ReduceTargetFootprintTask`；
6. 安排一个带 UID 确定性偏移的 `TriggerPostForkCCGcTask`。

`kPostForkMaxHeapDurationMS` 在该 tag 中为 2000 ms。由源码可得出下面的目标时间范围：

| footprint 调整次数 | 调整时间 | post-fork GC 任务目标时间 |
| ---: | --- | --- |
| 0 | 无 | fork 后 8～27.999 秒 |
| 1 | 2 秒 | fork 后 10～29.999 秒 |
| 2 | 2 秒、10 秒 | fork 后 18～37.999 秒 |

范围里的 0～19.999 秒偏移由 `std::default_random_engine(getuid())` 和 `std::uniform_int_distribution<int>(0, 19999)` 生成。它对同一 UID 可重复，在不同 UID 间变化；不是简单的 `getuid() % 20000`。

这些定时任务都带 GC 序号条件：

- `ReduceTargetFootprintTask` 仅在计划以来没有发生 GC、当前也没有收集器运行时调整目标；
- `TriggerPostForkCCGcTask` 仅在 GC 序号仍等于初始值时请求一次后台 GC。

所以，表中时间是任务的计划时间，不是“系统必定在该时刻强制 GC”。启动期若已经发生别的 GC，这些任务会成为空操作。温启动和热启动复用原进程，也不会再次进入 `PostForkChildAction()`。

[源码锚点：[`Heap::PostForkChildAction()`、`ReduceTargetFootprintTask` 与 `TriggerPostForkCCGcTask`](https://android.googlesource.com/platform/art/+/refs/tags/android-17.0.0_r1/runtime/gc/heap.cc)]

## 5. 三类“GC 抑制”方案为何不能发布

### 5.1 修改 `ConcurrentGCTask::Run()` 的 vtable

ART 的 C++ 类布局、符号可见性和调用约定不是 Android SDK 契约。`libart.so` 还可能通过 ART Mainline 模块更新，同一 API 级别不能保证内部地址与布局相同。只读映射、RELRO、CFI 和其他平台加固也会让写 vtable 的方案直接失败或以不可预测的方式退出。

即使 Hook 恰好生效，也只拦住这一类后台请求。达到分配限制时，应用线程仍可能等待正在运行的 GC、触发分配型 GC，或在回收后继续分配失败。把后台回收延后，通常会把工作移到更接近容量边界、代价更难控制的时刻。

### 5.2 伪造 `num_bytes_allocated_`，包括所谓 mSponge

修改记账值不会增加 allocator 的空间，也不会增加进程可用物理内存。该字段参与分配限制、GC 起点、trace 上报和 GC 后统计，TLAB 撤销与回收还会对它做配套修正。只改其中一个地址会使这些计算彼此矛盾。

常见后果包括：

- 并发 GC 请求被延后；
- 分配失败更靠近调用方；
- heap trace 与对象存活量失去对应关系；
- ART 版本或设备配置变化后写错内存；
- Java 堆增长挤压 native、图形和系统可回收内存。

这种做法不能把 `growth_limit_` 变成安全的额外容量，更不能防止 OOM 或系统因整体内存压力结束进程。

### 5.3 向 TaskProcessor 注入阻塞任务

`HeapTask` 和 `TaskProcessor::AddTask()` 都是 ART 内部接口。普通应用没有 SDK 入口可添加自定义任务。通过符号查找强行注入对象，还要匹配 C++ ABI、对象所有权、析构方式和 `SelfDeletingTask::Finalize()`。

阻塞 `HeapTaskDaemon` 会延迟整个队列，不只影响 `ConcurrentGCTask`。`HeapTrimTask`、收集器切换、time-based 复查、启动缓存清理、追踪停止和部分 JIT 工作都可能受影响。任务结束时的排空语义还会让多个逾期任务连续执行。

对系统镜像研发而言，改变 ART 策略应在固定 AOSP tag 的平台源码中完成，并覆盖 ART 单元测试、GC 压力、启动、低内存、进程冻结/解冻和运行时关闭场景。对三方应用而言，这三类方案都应排除。

## 6. `onTrimMemory()` 与 HeapTrimTask 是两条不同路径

Android 17 中，`ActivityThread.ApplicationThread.scheduleTrimMemory()` 把工作安排到主线程的 Choreographer commit 回调；没有 Choreographer 时才投递到主线程 Handler。`handleTrimMemory()` 收集进程内的 `ComponentCallbacks2`，逐个调用 `onTrimMemory(level)`，之后通知 `WindowManagerGlobal`。

这段实现没有调用 `VMRuntime.requestConcurrentGC()`、`requestHeapTrim()` 或 `trimHeap()`。应用在回调里释放强引用，只是让对象具备被回收的条件，GC 仍由 ART 自己决定。

从 API 34 开始，应用不再收到 `TRIM_MEMORY_RUNNING_MODERATE`、`RUNNING_LOW`、`RUNNING_CRITICAL`、`MODERATE` 和 `COMPLETE`。Android 17 应围绕两个仍有意义的级别设计：

| 级别 | 含义 | 合适动作 |
| --- | --- | --- |
| `TRIM_MEMORY_UI_HIDDEN` | 应用界面不再可见 | 释放只服务于可见界面的 Bitmap、播放与动画资源 |
| `TRIM_MEMORY_BACKGROUND` | 进程进入后台并可被结束 | 进一步释放能低成本重建的缓存和资源 |

`UI_HIDDEN` 描述可见性，不证明设备正在发生严重内存压力。回调实现也不应主动调用 `System.gc()`；Android 17 的接口注释明确说明，运行时可根据应用状态自行 GC，应用无须显式请求。

ART 自身的 heap trim 通常在 GC 完成后通过 `Heap::RequestTrim()`安排。重复请求由 `pending_heap_trim_` 合并，`HeapTrimTask` 延迟执行 `Heap::Trim()`。它处理的是 ART 空间和相关 native 结构向内核归还页面的工作，不是 `onTrimMemory()` 的自动下游。

[源码锚点：[`ActivityThread.scheduleTrimMemory()` 与 `handleTrimMemory()`](https://android.googlesource.com/platform/frameworks/base/+/refs/tags/android-17.0.0_r1/core/java/android/app/ActivityThread.java)、[`ComponentCallbacks2`](https://android.googlesource.com/platform/frameworks/base/+/refs/tags/android-17.0.0_r1/core/java/android/content/ComponentCallbacks2.java)、[`Heap::RequestTrim()` 与 `HeapTrimTask`](https://android.googlesource.com/platform/art/+/refs/tags/android-17.0.0_r1/runtime/gc/heap.cc)]

## 7. 应用侧应治理分配和存活对象

看到 GC 与卡顿重叠时，应找出为何在该时间窗达到回收条件；关闭 collector 不是治理目标。

### 7.1 启动阶段

- 把首屏无关的对象图、SDK 初始化和预加载移出 TTID/TTFD 路径；
- 控制并行初始化，避免多个线程同时制造分配峰值；
- 固定 APK、编译状态、启动类型、账号数据和设备温度后再做对照；
- 区分 post-fork 后台 GC 与业务分配引起的 GC。

### 7.2 列表滚动、动画和 Compose

- 用 allocation sampling 找到每帧重复创建的集合、字符串、lambda、绘制对象和中间数据；
- 把可复用对象移出高频回调，但不要为了零分配引入无边界对象池；
- 检查 Compose 状态读取范围、重组范围和列表 key，避免把重组次数直接当作 GC 原因；
- 同时观察帧时间、分配速率、存活字节和 GC pause。

### 7.3 大对象和缓存

- 大图按展示尺寸解码，明确 Bitmap、纹理和解码器的所有者；
- 缓存以可重建成本和设备档位定容量，不用固定 Java heap 百分比套所有机型；
- heap dump 用于确认存活对象与引用路径，allocation sampling 用于确认产生速率，两者不能互相代替；
- Java 堆不大时继续检查 native 堆、图形内存、文件映射、数据库页缓存和交换页。

`System.gc()` 只是一项请求，ART 可以调整或忽略。除非受控实验已经证明某个非交互时间窗的主动请求改善后续用户路径，而且没有增加长尾、CPU 与内存带宽竞争，否则不要在启动完成、页面切换或滑动前后调用它。

## 8. 用 Perfetto 建立因果证据

`TaskProcessor::RunAllTasks()` 没有为每种 `HeapTask` 自动生成同名 slice。排查时应组合多类证据：

1. 在线程轨道找到 `HeapTaskDaemon`，确认任务在哪个时间窗运行；
2. 查看 GC slice 的 cause、collector、暂停和释放字节；
3. 用 Java/Kotlin allocation sampling 定位分配调用栈；
4. 用 heap dump 确认关键时间点的存活对象与引用关系；
5. 用 `dumpsys meminfo`、Perfetto 内存计数器或对应分析工具区分 Java、native、图形内存与总 PSS；
6. 对照进程 fork、首帧、前后台切换和冻结/解冻时间。

看到 GC 原因为 `Background` 也不能单凭名称断定来自 post-fork 任务。普通并发 GC 请求同样使用该原因；还要检查进程启动时间、此前 GC 序号和分配活动。看到 `HeapTaskDaemon` 运行也不能直接算作 GC CPU，因为该线程还会执行 trim、定时检查与其他运行时工作。

线上不存在适用于所有应用的“Java 堆 80%”“GC 超过三次”或固定暂停时长告警线。阈值应来自应用自己的设备分档和版本基线，并联合观察：

- 分配速率与存活集增长；
- GC cause、collector、暂停与释放量；
- 主线程帧、启动或交互时间；
- Java、native、图形内存、PSS 与交换页；
- OOM、进程退出和低内存设备长尾。

只有当这些数据在同一时间轴上形成可重复的因果关系，修改分配点或缓存策略才有可靠验收依据。

## 10. 小结

- `HeapTaskDaemon` 串行执行 HeapTask；`ConcurrentGCTask` 的名称不代表任务并行。
- Android 17 的 Java 分配路径同时支持字节阈值和 time-based GC triggering。
- `max_gc_requested_` 与 GC 序号负责合并并发请求；`CanAddHeapTask()` 只守 Runtime 生命周期和 native 栈溢出边界。
- `num_bytes_allocated_`、`concurrent_start_bytes_`、`target_footprint_` 和 `growth_limit_` 含义不同，也都不是进程总内存。
- post-fork 策略会暂时放宽堆目标，再按条件恢复；它不保证一段时间内绝对没有 GC。
- vtable Hook、伪造堆记账和阻塞 TaskProcessor 会破坏 ART 的内存安全或任务时序，不应进入发布应用。
- `onTrimMemory()` 负责通知应用释放资源，与 ART 的 `HeapTrimTask` 没有自动调用关系。
- 可发布的优化应减少高频分配、控制存活对象和缓存，并用 Perfetto、分配采样、heap dump 与进程内存数据共同验证。
