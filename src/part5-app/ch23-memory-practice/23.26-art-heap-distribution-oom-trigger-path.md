# 23.26 ART 堆内存分布与 OOM 触发路径实战

> “M-Sponge 512MB 内存池”、`DAVSS` 固定字段和 `dumpsys meminfo --package <pkg>` 均不作为 AOSP 固定能力；以下结论只基于 `android-17.0.0_r1` ART 源码与 `android17-6.18` 内核锚点。

## 1. 调查目标

平台锚点为 Android 17 / API 37 / `android-17.0.0_r1`；涉及线程、地址空间与内核资源时，以 `android17-6.18-2026-06_r6` 为内核锚点。

ART heap OOM 的调查目标可以归纳为四个问题：

1. 失败对象会进入哪个 allocator 或 Space？
2. 快路径失败后，ART 做过哪些等待、GC 和重试？
3. 失败受 growth limit、最小空闲比例、连续空间还是地址映射影响？
4. 这条 `OutOfMemoryError` 是否来自 Java heap 分配？

同样叫 `OutOfMemoryError`，也可能由 `pthread_create()`、`Unsafe.allocateMemory()` 或 Bitmap native 分配入口抛出。FD 耗尽通常返回 `EMFILE` 或触发库自身错误，不应归入 Java heap OOM。

## 2. Android 17 的 ART Space

ART `Heap` 同时管理多类 Space。它们的地址、容量和是否存在取决于 collector、进程类型、运行时参数和厂商配置，不能画成每台设备都相同的固定地址布局。

| Space | 主要内容 | 可回收 | 可移动 | 诊断意义 |
|---|---|---:|---:|---|
| Boot Image Space | boot image 中预生成的类、对象和元数据 | 否 | 否 | 多为文件映射和跨进程共享页 |
| Zygote Space | fork 前形成的对象 | 应用进程中否 | 否 | 写入会产生 Copy-on-Write private dirty |
| Main Moving Space | 应用的大多数普通对象 | 是 | 是 | CC 常用 `RegionSpace`，CMC 使用 `BumpPointerSpace` |
| Non-moving Space | ART 要求地址稳定的托管对象 | 是 | 否 | 不能用 DirectByteBuffer/Bitmap 作通用类比 |
| Large Object Space | 符合类型和大小条件的大对象 | 是 | 否 | 关注 primitive array、String、连续区间与映射 |
| JIT code/data cache | 编译代码与相关数据 | 由 JIT 管理 | 不适用 | 属于进程内存，未计入 Java 对象 retained size |

`dumpsys meminfo`、maps 和 heap dump 分别看到不同侧面：

- `dumpsys meminfo <package>` 侧重 PSS/RSS 与系统分类；
- `/proc/<pid>/maps` / `smaps` 侧重虚拟映射和驻留页；
- HPROF 侧重托管对象、类和 GC Root；
- Perfetto GC trace 侧重 collector、cause、暂停和分配线程等待。

HPROF 无法可靠给出 RegionSpace、LOS 和 image mapping 的 PSS 占比。maps 也看不到对象的 GC Root。两种证据需要联合使用。

## 3. 对象怎样选择 allocator

### 3.1 普通对象与 TLAB

普通对象通常先走当前 allocator 的快路径。启用 TLAB 时，线程在自己的 buffer 中推进指针，避免每次分配都竞争全局锁。TLAB 用完后，线程再向 `RegionSpace` 或 `BumpPointerSpace` 请求新的可用区间。

Android 17 源码中的常量分属不同层级：

- `Heap::kDefaultTLABSize = 32 KiB`；
- `Heap::kPartialTlabSize = 16 KiB`；
- `RegionSpace::kRegionSize = 256 KiB`。

默认 TLAB 不是一个 region。TLAB 也不专属于 Concurrent Copying；Bump Pointer 路径同样可以使用。

### 3.2 Large Object Space 的进入条件

[`Heap::ShouldAllocLargeObject()`](https://android.googlesource.com/platform/art/+/refs/tags/android-17.0.0_r1/runtime/gc/heap-inl.h) 用两项条件选择 LOS。下面的源码节选用于确认判断范围：

```cpp
return byte_count >= large_object_threshold_ &&
        (c->IsPrimitiveArray() || c->IsStringClass());
```

Android 17 的默认大对象阈值为 12 KiB，运行参数可以调高，但不能低于 `kMinLargeObjectThreshold`。超过阈值的普通业务对象、对象数组或 Bitmap wrapper 不会只凭大小进入 LOS；类型仍要是 primitive array 或 `String`。

LOS 有两种实现：

- `FreeListSpace`：预留连续地址范围，以 free block 复用和合并；
- `LargeObjectMapSpace`：每个对象使用独立映射。

构建配置决定使用哪种实现。LOS 分配失败后，`AllocObjectWithAllocator()` 会清除这次 LOS OOM 异常，再尝试 main/non-moving allocator。因此“对象大于 12 KiB”不能证明最终失败发生在 LOS。

## 4. 快路径失败后的 GC 重试

普通分配返回空指针后，`Heap::AllocateInternalWithGc()` 接管。Android 17 的处理包含以下阶段：

1. 等待正在运行的 GC 完成；
2. 若等待期间完成过 GC，重试本次分配；
3. 没有可复用结果时，按 `next_gc_type_` 执行 blocking GC；
4. 重试仍失败后，使用 `gc_plan_.back()` 做覆盖范围更大的回收并清除 SoftReference；
5. 对支持的 allocator，满足配置和时间间隔时尝试 homogeneous space compaction；
6. 受回收收益和重试次数约束，仍无法分配时进入 OOME。

这里没有固定的“Young GC → Full GC”两步顺序。`next_gc_type_` 受 collector、代际状态、上次 GC 和 heap 目标影响。分配线程还可能长时间等待另一线程正在执行的 GC；Perfetto 中用户可见空洞会大于单个 pause。

### 4.1 growth limit、target footprint 与最小空闲

三个值容易混淆：

| 值 | 含义 |
|---|---|
| `growth_limit_` | 应用 Java heap 可增长到的限制 |
| `target_footprint_` | ART 为下一阶段分配/GC 调整的目标值 |
| `GetFreeMemoryUntilOOME()` | 当前 footprint 到 growth limit 之间可用于继续增长的估算 |

`target_footprint_` 会变化，不等同于硬上限。`android:largeHeap="true"` 可以清除普通 growth limit，让应用使用 large heap class 对应上限；它不会增加设备 RAM，也不会解决 native、graphics、线程栈和其他进程的压力。

ART 还要求 GC 后保留最小空闲比例。空闲总字节略大于请求值时，若分配后无法满足该比例，依然可能 OOM。目标 Space 没有足够连续块时也会失败。

## 5. 读懂 ART heap OOME

下面的示例用于标注 Android 17 错误文本中的字段：

```text
java.lang.OutOfMemoryError: Failed to allocate a 48 byte allocation with
3610680 free bytes and 3526KB until OOM, target footprint 536870912,
growth limit 536870912; giving up on allocation because <1% of heap free after GC.
```

字段解释如下：

- `allocation size`：本次对象请求。小请求失败常见于堆已贴近限制，大请求要检查输入尺寸、数组长度和整数溢出；
- `free bytes`：ART 统计的 heap 空闲总量，不保证目标 allocator 有合适连续块；
- `until OOM`：距离 growth limit 的估算增长空间；
- `target footprint`：当前调节目标；
- `growth limit`：Java heap 增长限制；
- `<1% ... after GC`：分配后无法保留 ART 要求的最小空闲比例。

[`Heap::ThrowOutOfMemoryError()`](https://android.googlesource.com/platform/art/+/refs/tags/android-17.0.0_r1/runtime/gc/heap.cc) 只有在“空闲总量不小于请求值”并且 allocator 不是 LOS 时，才调用目标 Space 的 `LogFragmentationAllocFailure()`。LOS OOME 缺少这段碎片详情，不能据此排除 LOS 碎片或地址空间问题。

### 5.1 OOME 对象也可能分配失败

ART 的 [`Thread::ThrowOutOfMemoryError()`](https://android.googlesource.com/platform/art/+/refs/tags/android-17.0.0_r1/runtime/thread.cc) 先尝试构造带错误文本的 `java.lang.OutOfMemoryError`。若构造异常时再次 OOM，就改用 Runtime 启动阶段准备的 OOME 对象；递归分支还会 dump 当前线程。

预分配对象保证线程能进入异常状态，不保证完整错误文本和 Java 栈。线上处理器不要在 OOME 后分配大集合、遍历全部线程或立即抓完整 heap dump。

## 6. 四种常见“内存不足”

### 6.1 Java heap OOM

证据通常包含 ART `Failed to allocate ...` 文本，Java heap 已接近 growth limit，或目标 Space 无法满足请求。常见原因分为：

| 类型 | 证据 | 修复方向 |
|---|---|---|
| 引用泄漏 | 同类对象和 GC Root 路径跨场景持续增长 | 修生命周期、listener、ThreadLocal、静态集合 |
| 合法存活集过大 | 对象都有 owner，但稳定态 retained size 接近预算 | 分页、按需加载、限制缓存、减少重复表示 |
| 分配抖动 | 存活集不高，分配速率和 GC 频率很高 | 流式处理、复用 buffer、减少热路径临时对象 |
| 单次大对象 | 栈集中在数组、Bitmap、解压或反序列化 | 输入上限、分块、目标尺寸解码、乘法溢出检查 |

### 6.2 Native allocation 失败

Native 没有统一的“native heap 上限”。`malloc()`、`mmap()`、GraphicBuffer 和线程栈经过不同路径。调用方忽略空指针可能转为 SIGSEGV；只有部分 Android JNI/Framework 入口会把 native 失败转换成 Java OOME。

`Unsafe.allocateMemory()`、部分 Bitmap 像素分配和 JNI 字符串入口都有显式 OOME 转换。应用自己的 C/C++ 分配器需要保存 errno、请求大小和调用栈。

### 6.3 Thread OOM

`Thread::CreateNativeThread()` 创建 ART `Thread`、JNI 环境和 pthread。失败信息可分为：

- `Could not allocate JNI Env: ...`；
- `pthread_create (<size> stack) failed: <errno text>`。

这类 OOME 与 Java heap Space 选择无关。调查线程数、每线程栈、VMA、native memory、task limit 和原始 errno。完整方法见 [23.13 应用虚拟内存优化实战](13-virtual-memory-optimization.md)。

### 6.4 FD 与地址空间耗尽

FD 到达 `RLIMIT_NOFILE` 后，`open()`、`socket()`、`pipe()` 等通常返回 `EMFILE`；它不必经过 OOME。32 位地址空间碎片、大量线程栈或 VMA 上限则可能让 `mmap()` 返回 `ENOMEM`，随后由上层选择抛 OOME、native crash 或业务错误。

综合分类与退出归因见 [20.5 Android OOM 治理](../ch20-stability/05-oom-governance.md)。

## 7. 观测工具怎样组合

### 7.1 同点快照

下面的命令用于保存 PSS/RSS、映射、线程和 managed heap：

```bash
package=com.example.app
pid=$(adb shell pidof -s "$package" | tr -d '\r')

adb shell dumpsys meminfo "$package" > meminfo.txt
adb shell cat "/proc/$pid/status" > status.txt
adb shell cat "/proc/$pid/maps" > maps.txt
adb shell "ls /proc/$pid/task | wc -l" > thread-count.txt
adb shell am dumpheap "$package" "/data/local/tmp/$package.hprof"
adb pull "/data/local/tmp/$package.hprof"
```

`am dumpheap` 的可用性取决于 build、profileable/debuggable、权限和进程状态；接近 OOM 时完整 HPROF 可能失败或加重停顿。更合适的做法是在风险水位出现但进程仍健康时，于灰度或实验设备抓取。

现代 Android heap dump 通常可直接被 Android Studio 或兼容分析器读取。`hprof-conv` 主要服务于旧格式兼容，不应成为 Android 17 固定步骤。

### 7.2 证据与用途

| 工具 | 适合回答 | 盲区 |
|---|---|---|
| `dumpsys meminfo` | 进程 PSS/RSS、Java/native/graphics 分类趋势 | 单个对象的 owner 和调用栈 |
| maps/smaps | VMA、权限、文件/匿名映射、驻留页 | Java GC Root |
| HPROF | 类、实例、retained size、GC Root | native malloc 栈、Space PSS |
| Perfetto ART trace | GC collector/cause、pause、分配线程等待 | 完整对象引用图 |
| heapprofd | 采样的 native malloc/free 栈 | Java 对象和所有直接 mmap |
| `ApplicationExitInfo` | 上次退出原因、trace/input stream | 设备不支持低内存归因时的信息缺口 |

`showmap` 在可用设备上可以补充 mapping 分类；量产 user build 可能限制访问。正确命令是 `dumpsys meminfo <pkg>`，而不是 `dumpsys meminfo --package <pkg>`；`DAVSS` 也不是 Android 17 固定输出字段。

## 8. “扩堆”与隐藏接口评估

### 8.1 `largeHeap`

`largeHeap` 只适合工作集客观较大的少数产品。采用前必须覆盖低内存设备、前后台切换、进程重建、GC 时延和系统压力测试。泄漏、无界缓存、错误尺寸和 native 增长都不会被它修复。

### 8.2 ART 内部字段与 hook

这些做法不进入生产方案：

- 修改 `num_bytes_allocated_`、`NonFreeableSize` 或 GC 水位；
- 调用未公开的 `setNativeAllocThreshold`；
- 改写 `large_object_threshold_`；
- hook allocator 让对象绕过 GC；
- 伪造 freed bytes 或 growth limit；
- 解除 ART heap mapping。

ART 的 allocation counter、bitmap、card table、Space membership 和 GC root 必须保持一致。只改一个计数会让 GC 触发时机、统计和对象生命周期失去一致性。

### 8.3 `mSponge 512MB` 的结论

`android-17.0.0_r1` 的 LOS 实现在 `art/runtime/gc/space/large_object_space.cc`，包含 `FreeListSpace` 和 `LargeObjectMapSpace`。源码没有 `mSponge` 类型、512 MiB 固定池或“绕过 GC”平台能力。

仓库中的 [4.38 LargeObjectSpace mSponge](../../part1-fundamentals/ch04-memory/4.38-android17-largeobjectspace-msponge.md) 已标记为 deprecated。任何同名实现都应视为应用/OEM 私有 hook，并单独审计崩溃、GC 一致性和版本兼容。

## 9. Android 17 边界

### MTE

MTE 主要帮助发现 native use-after-free、buffer overflow 等内存安全问题。它可能改变 native allocator 元数据、tag fault 和性能表现，不会直接提高 ART Java heap growth limit，也不会把 Java 对象转入另一种 Space。

### 16 KiB page size

16 KiB 页会改变 `mmap`、guard page、Space reservation 和 `madvise` 的对齐粒度。ART 的对象对齐仍有自己的规则；不能把页大小直接换算成“每个 Java 对象至少 16 KiB”。

### GC 策略

Android 17 可使用 CC、CMC 和分代路径，选择受内核能力、构建、属性与 flags 影响。collector 改变 Space 实现、搬迁方式、CPU 与 pause 分布；最终 OOM 判断仍要回到 allocator、growth limit、最小空闲、连续空间与重试结果。

## 10. 调查清单

处理一条 ART 相关 OOM 时，按以下顺序保留证据：

1. 保存完整异常消息、线程栈、进程 ABI、Android build 和页大小；
2. 根据消息区分 heap allocation、pthread、JNI Env 或 native entry；
3. 同点记录 Java heap、native heap、PSS/RSS、线程、FD、VmSize 和 VMA；
4. 从对象类型判断可能 allocator，避免只按请求字节数认定 LOS；
5. 在健康高水位抓 HPROF，比较 GC Root 与 retained size；
6. 用 Perfetto 确认 GC cause、collector、pause 和分配线程等待；
7. native 增长用 heapprofd/maps/graphics 工具补证；
8. 修复 owner、生命周期、并发和输入尺寸，再做同场景复测。

ART Space 的完整模型见 [4.3 ART 虚拟机内存管理](../../part1-fundamentals/ch04-memory/03-art-memory.md)。
