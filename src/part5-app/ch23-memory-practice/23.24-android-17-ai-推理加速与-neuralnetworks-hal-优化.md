# 23.24 Android 17 AI 推理加速与 NeuralNetworks HAL 优化

<!-- outline-start -->
## 要点

### 🔹 Android 17 NeuralNetworks HAL 架构与 AI 推理加速机制
Android 17 中 NeuralNetworks HAL 作为 AI 推理硬件抽象层，支持 NPU/GPU/CPU 多异构计算设备调度，通过 ANeuralNetworksDevice 列举可用硬件，ANeuralNetworksModel 加载后经过 ANeuralNetworksExecution 执行，提供内存优化的 Model/Memory/Buffer 三级管理。

### 🔹 16KB Page Size 与 NeuralNetworks 内存分配边界
Android 17 的 16KB Page Size 影响 NeuralNetworks 内存分配策略，内存对齐要求从 4KB 提升至 16KB，大模型加载时需处理 page alignment 问题，通过 ANeuralNetworksMemory_createWithAlignment API 指定 16KB 对齐。

### 🔹 NeuralNetworks 与 Binder IPC 性能协同
NeuralNetworks 大模型推理通过 Binder IPC 与 system_server 通信，ANeuralNetworksService 使用 Binder 调用底层 HAL，需注意 Binder 线程池饱和和 Binder transaction 过载问题。

### 🔹 NPU 驱动加载与 DVFS 调度协同
Android 17 NPU 驱动通过 libneuralnetworks 加载，DVFS 策略根据 NPU 负载动态调整频率，通过 ANeuralNetworksDevice_getCapabilities 获取硬件能力，根据模型复杂度选择计算单元。

### 🔹 TFLite 管线与 Android Runtime 优化集成
TFLite 在 Android 17 中与 ART GC 集成，大模型推理期间抑制 GC 暂停，通过 ANeuralNetworksCompilation 优化编译，支持 XNNPACK CPU 后端和 NNAPI delegate。

## 扩展

### 🔸 AI 推理性能瓶颈分析路径
从 CPU 占用率、GPU 频率、NPU 利用率、内存带宽四个维度定位 AI 推理性能瓶颈，使用 Perfetto 跟踪 ANeuralNetworks 调用链路。

### 🔸 大模型推理内存压力治理
大模型推理过程中的内存碎片化与峰值内存管理，通过 MemoryAdvice API 获取系统内存压力，实现模型分片加载。

**16KB 对齐加载**：
```java
public class ModelLoader {
    private static final int ALIGNMENT_16KB = 16 * 1024;
    
    public void loadWithAlignment(String modelPath) {
        try (RandomAccessFile file = new RandomAccessFile(modelPath, "r")) {
            long fileSize = file.length();
            // 分配 16KB 对齐的内存
            ByteBuffer alignedBuffer = ByteBuffer.allocateDirect(
                (int) ((fileSize + ALIGNMENT_16KB - 1) & ~(ALIGNMENT_16KB - 1))
            );
            // 加载并验证对齐
            verifyAlignment(alignedBuffer);
        }
    }
    
    private void verifyAlignment(ByteBuffer buffer) {
        // 确保缓冲区按 16KB 对齐
        int address = buffer.arrayOffset();
        if ((address & (ALIGNMENT_16KB - 1)) != 0) {
            throw new IllegalStateException("Memory not 16KB aligned");
        }
    }
}
```

```java
// 使用 MemoryAdvice API 监控系统内存压力
public class MemoryAwareInference {
    public void executeWithMemoryAwareness(Runnable inferenceTask) {
        MemoryAdvice.MemoryInfo memInfo = MemoryAdvice.getMemoryInfo();
        
        switch (memInfo.pressureLevel) {
            case MemoryAdvice.PRESSURE_NORMAL:
                inferenceTask.run(); // 正常执行
```

### 1. 模型生命周期管理

#### 模型热更新机制
```java
public class ModelManager {
    private Map<String, Model> activeModels = new ConcurrentHashMap<>();
    private ScheduledExecutorService updateExecutor = Executors.newScheduledThreadPool(1);
    
    public void scheduleModelUpdate(String modelName, String newModelPath) {
        updateExecutor.schedule(() -> {
            // 原子化模型更新，避免推理中断
            Model oldModel = activeModels.get(modelName);
            Model newModel = loadModel(newModelPath);
            
            // 双阶段切换：预加载 → 切换 → 释放旧模型
            activeModels.put(modelName, newModel);
            
            if (oldModel != null) {
                // 延迟释放，确保当前推理完成
                scheduleOldModelRelease(oldModel, 5000);
            }
        }, 0, TimeUnit.SECONDS);
    }
    
    private void scheduleOldModelRelease(Model oldModel, long delayMs) {
        Executors.newSingleThreadScheduledExecutor().schedule(
            oldModel::cleanup, 
            delayMs, 
            TimeUnit.MILLISECONDS
        );
    }
}
```

```java
        }
    }
}
```

### 2. LiteRT V2 `CompiledModel` —— GenAI 时代的统一 API

LiteRT V2 引入的 `CompiledModel` 抽象替换了传统「`Interpreter` + 显式 `Delegate`」二分模型，源码证据：

```cpp
// google-ai-edge/LiteRT litert/cc/litert_compiled_model.h
namespace lm {
  class LlmLiteRtCompiledModelExecutorDynamic;   // LLM decode 场景
  class LlmLiteRtCompiledModelExecutorStatic;    // LLM prefill 场景
  class LlmLiteRtNpuCompiledModelExecutor;       // NPU 分发

```

`LlmLiteRtCompiledModelExecutorDynamic` 与 `LlmLiteRtCompiledModelExecutorStatic` 的命名直接揭示了 LiteRT V2 对 LLM「动态/静态」切分——这是 GenAI 工作负载的特征（KV cache 每步扩张）。`litert/core/environment.cc:25 LiteRtEnvironmentT::CreateWithOptions` + `SetGpuEnvironment` 构成「环境—编译模型—执行」三层 API。

**对本章的含义**：当 §23.24 描述「TFLite 管线与 Android Runtime 优化集成」时，应补充 LiteRT V2 的 `CompiledModel` 已支持 GPU/NPU 透明分发，开发者不再需要手动 `ModifyGraphWithDelegate` 注入 NNAPI Delegate。

### 3. `ArenaPlanner` 与符号-神经混合的张力

源码证据（`tensorflow/lite/arena_planner.cc:67-82`）：

```cpp
TfLiteStatus ArenaPlanner::ResetAllocationsAfter(int node) {
  ...
  if (last_active_node_ > node) {
    arena_.CalculateActiveAllocs(allocs_, node);   // 快速路径
  } else {
    arena_.PurgeAfter(node);                       // O(N) 全表扫描
  }
  last_active_node_ = node;
  return kTfLiteOk;
}
```

`ArenaPlanner` 基于「节点级活跃区间」的静态内存复用策略，对动态控制流不友好——每次跳转都要做线性扫描或全表清理。在 LLM decode 这种每步都改变 KV cache 节点激活状态的场景下，频繁 `PurgeAfter` 是隐藏瓶颈。这正是 LiteRT V2 引入 `LlmLiteRtCompiledModelExecutorDynamic` 的工程动因。

**对本章的含义**：如果未来要支撑「符号-神经混合」（控制流触发 + 神经子图），需要走 `kTfLiteDynamic` 路径或在 `CompiledModel` 外层做符号调度。详见调研报告 §未验证/待深入 第 3 条。

### 4. NNAPI Delegate 的按 Node 委托粒度

源码证据（`tensorflow/lite/delegates/nnapi/nnapi_delegate.cc`）：

- 第 91 行 `static const char kNnapiId[] = "nnapi_"` + `accelerator_name` 组成 delegate_id，作为节点级 cache key。
- 第 110-130 行错误码表显示 Android 11+ 已稳定 `ANEURALNETWORKS_MISSED_DEADLINE_PERSISTENT`、`ANEURALNETWORKS_RESOURCE_EXHAUSTED_PERSISTENT`、`ANEURALNETWORKS_DEAD_OBJECT` 三类语义化错误，可驱动应用层降级策略。

NNAPI Delegate 的核心机制是**按 Node 粒度**把 TFLite 子图拆分为「可委托子图」与「保留子图」，委托部分下推到 NPU，未委托的留在 CPU XNNPack。这种 split-by-node 模型天然支持「神经子图交给 NPU + 符号控制流留在 CPU」的混合架构。

### 5. 16KB Page Size 与 NNAPI 内存对齐（与本章第 2 要点互证）

LiteRT V2 `litert_compiled_model.h:80-110` 的 `ToTensorBufferRequirements` 工具函数通过 `runtime->GetTensorBufferRequirementsSupportedBufferTypes` 拿到模型对硬件 buffer 类型的偏好（含 `kLiteRtTensorBufferTypeAhwb` 等 AHWB 类型）。AHWB（Android Hardware Buffer）在 Android 17 的 16KB page size 下需要 `ANeuralNetworksMemory_createWithAlignment(alignment=16384)` 显式声明，这是本章「16KB Page Size 与 NeuralNetworks 内存分配边界」要点的底层支撑。
