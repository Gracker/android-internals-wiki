# 23.24 Android 17 AI 推理加速与 NeuralNetworks HAL 优化

## 🔸 NNAPI 公共 API 与运行时边界

先明确生命周期边界：NNAPI 自 Android 15 起已被弃用。Android 17 上现有应用仍可调用这些 API，但官方预计未来多数设备可能只提供 CPU backend，因此不能仅凭 NNAPI 调用成功推断 NPU/GPU 加速已发生。新接入应优先评估 TensorFlow Lite in Google Play services、LiteRT 及适合模型的 GPU runtime；保留 NNAPI 的项目则需要记录实际 device、delegate 分割结果与回退路径。

### 1. 设备发现与能力查询

NNAPI 的公共入口以 NDK C API 为准。设备枚举的基本形态是：

```cpp
uint32_t num_devices = 0;
int result = ANeuralNetworks_getDeviceCount(&num_devices);
for (uint32_t i = 0; i < num_devices; ++i) {
    ANeuralNetworksDevice* device = nullptr;
    if (ANeuralNetworks_getDevice(i, &device) != ANEURALNETWORKS_NO_ERROR) {
        continue;
    }

    const char* name = nullptr;
    ANeuralNetworksDevice_getName(device, &name);

    const char* version = nullptr;
    ANeuralNetworksDevice_getVersion(device, &version);

    int64_t feature_level = 0;
    ANeuralNetworksDevice_getFeatureLevel(device, &feature_level);
}
```

可迁移的调优结论只应建立在这些公共能力、模型编译结果和实测 trace 上。诸如“设备热插拔自动更新”“NPU 特性位掩码”“设备能力查询提升固定百分比”若没有 Android 17 源码或实测证据，不应写成平台结论。

### 2. 模型、编译与执行

NNAPI 的典型生命周期是：创建 `ANeuralNetworksModel`、添加 operands/operations、`ANeuralNetworksModel_finish()` 固化图；再创建 `ANeuralNetworksCompilation`，设置偏好或缓存；随后创建 `ANeuralNetworksExecution`，设置输入输出并执行。

```cpp
ANeuralNetworksModel* model = nullptr;
ANeuralNetworksModel_create(&model);
// addOperand / setOperandValue / addOperation / identifyInputsAndOutputs ...
ANeuralNetworksModel_finish(model);

ANeuralNetworksCompilation* compilation = nullptr;
ANeuralNetworksCompilation_create(model, &compilation);
ANeuralNetworksCompilation_setPreference(
    compilation, ANEURALNETWORKS_PREFER_SUSTAINED_SPEED);
ANeuralNetworksCompilation_finish(compilation);

ANeuralNetworksExecution* execution = nullptr;
ANeuralNetworksExecution_create(compilation, &execution);
// ANeuralNetworksExecution_setInput / setOutput ...
ANeuralNetworksExecution_compute(execution);
```

异步执行、超时、deadline、reusable execution 等能力需要按对应 API level 和返回码逐项确认。分析 Android 17 差异时，应回到 `android-17.0.0_r1` 的 NNAPI headers/runtime 源码，而不是从上游 LiteRT main 分支反推平台行为。

## 🔸 16KB Page Size 下的内存实践

16KB page size 对推理的影响可以拆为三类：

1. **模型文件映射**：大权重文件通常通过 mmap 或 asset/file descriptor 映射。需要保证 offset 满足 mmap/page 约束，并留意 4KB 假设写死在自研 loader 中造成的失败或额外拷贝。
2. **共享 buffer**：跨进程或跨硬件 backend 传递大张量时，优先使用共享内存、`AHardwareBuffer` 或运行时提供的 tensor buffer；不要用 Java `ByteBuffer.arrayOffset()` 判断 direct buffer 的真实 native 地址，direct buffer 通常没有可访问 Java array。
3. **峰值与碎片**：16KB page 会改变小块 native 分配的内部碎片形态。对大模型，KV cache、临时 tensor arena、delegate 私有缓存的峰值叠加比单个 buffer 对齐更常见。

排查建议：

```bash
adb shell getconf PAGE_SIZE
adb shell dumpsys meminfo <package>
adb shell cat /proc/<pid>/smaps_rollup
```

如果使用 TFLite/LiteRT，应额外记录 delegate 是否启用、delegate 初始化耗时、compilation/cache 是否命中、输入输出是否发生 CPU staging copy。

## 🔸 Binder、线程与数据搬运

AI 推理性能问题经常被误判为“计算慢”，实际瓶颈可能在数据搬运：

- Binder 只适合传递控制消息、句柄和小型元数据；大 tensor 应经共享内存或硬件 buffer 传递。
- 不要在主线程做模型加载、delegate 初始化或首次 compilation；首次执行可能包含缓存构建和驱动初始化。
- Binder 线程池大小、vendor service 线程模型和驱动队列深度不是 Android 17 对应用公开的统一调参项，必须以目标设备 trace 为准。

观测入口：Perfetto 中查看应用线程是否阻塞在 Binder wait、是否出现 runnable 排队、是否有频繁 page fault 或大块 memcpy；同时结合 logcat/框架返回码区分 `OUT_OF_MEMORY`、`RESOURCE_EXHAUSTED_*`、`MISSED_DEADLINE_*` 等错误类别。

## 🔸 DVFS 与 NPU/GPU 调度的可控边界

应用层通常不能直接设置 NPU 频率。更可靠的策略是控制负载形态：

| 策略 | 作用 | 风险 |
| --- | --- | --- |
| 量化/小模型降级 | 降低带宽与计算量 | 精度下降，需要业务阈值 |
| 限制并发推理 | 避免 tensor arena 与 driver queue 峰值叠加 | 吞吐下降 |
| warmup 与缓存 | 减少首次 compilation/driver 初始化抖动 | 占用常驻内存 |
| batch/分片调节 | 平衡吞吐、延迟与峰值内存 | 过大 batch 可能触发热限制 |
| delegate fallback | 避免不支持 op 拖垮端到端路径 | CPU fallback 可能增加拷贝 |

固定“15ms/25ms/功耗 125%”这类数字只能来自明确设备、模型、温控状态、版本和测试脚本；没有这些条件时不应作为通用结论。

## 🔸 TFLite / LiteRT 与 NNAPI Delegate

端侧 AI 栈可分为三层：MediaPipe Tasks / LiteRT-LM 等应用层封装，TFLite/LiteRT 运行时层，以及 NNAPI delegate 到厂商 HAL 的硬件抽象层。对 Android 17 有效的结论是：

- TFLite NNAPI delegate 的常见工作方式是按节点/子图分割：支持的部分交给 NNAPI，不支持的部分保留在 CPU backend。
- tensor arena 复用能降低临时张量峰值，但动态 shape、LLM decode/KV cache 和控制流会削弱静态内存规划收益。
- LiteRT main 分支的 `CompiledModel`、`TensorBuffer`、LLM executor 命名可作为运行时演进参考，但不能直接等同于 AOSP `android-17.0.0_r1` 平台 API。

涉及 Android 17 平台能力的结论必须直接锚定 `android-17.0.0_r1` 中的 NNAPI NDK header、runtime service/driver 交互、HAL AIDL/HIDL 定义，以及 Android 构建采用的 TFLite/NNAPI delegate 版本。来自 LiteRT main 或厂商实现的行为只能作为独立参考，不能上升为 Android 17 平台保证。

## 🔸 Android 17 源码与构建锚点

`android-17.0.0_r1` 中可以把上述三层边界落到具体文件：`runtime/include/NeuralNetworks.h` 定义公共 NDK C API，`runtime/ExecutionPlan.cpp` 负责运行时分区与执行计划，Neural Networks AIDL `IDevice.aidl` 定义 runtime 与 vendor driver 的设备能力、支持算子、prepare/execute 和缓存合同。它们共同说明“公共 API 可调用”“runtime 怎样分区”和“HAL 能力合同”是三个不同层次，不能互相替代。

AOSP 的 `external/tensorflow` 快照还提供三个构建锚点：`METADATA` 固定上游 TensorFlow Git revision，根目录 `Android.bp` 定义 Android 构建目标，`tensorflow/lite/delegates/nnapi/nnapi_delegate.cc` 是该快照内的 NNAPI delegate 实现。只有这个 tag 中存在的 delegate 才能作为 Android 17 构建输入证据，不能用上游 LiteRT/TensorFlow 的产品版本号反推 AOSP 中的实现版本。
