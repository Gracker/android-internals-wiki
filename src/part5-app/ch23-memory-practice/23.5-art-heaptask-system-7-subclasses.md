# 23.5 Android 17 ART HeapTask 体系：“7 种”统计纠错

<!-- outline-start -->
## 要点

### 🔹 GPU调试工具链架构
Android 17通过Perfetto集成的FrameTracer提供跨进程帧追踪，FPSReporter实现分层FPS监控，JankTracker进行卡顿分类检测，TimeStats提供详细的帧时间统计。硬件层的直接集成（如grallocusage用法转换）和用户态SurfaceFlinger中的GPU调试开关系统支持实时性能数据收集和分析。

### 🔹 SurfaceFlinger GPU调试系统
SurfaceFlinger初始化阶段加载大量GPU调试开关，包括回压控制、采样策略、预测策略等核心属性。系统通过debug.sf.enable_gl_backpressure等属性控制GPU合成行为，支持实时的性能调试与优化。

### 🔹 FPS监控架构
FPSReporter作为跨进程FPS监控的核心组件，通过LayerHierarchy分发层级FPS信息，支持多监听器注册与移除机制。系统设计考虑了进程间通信的稳定性与性能开销。

### 🔹 GPU回压控制机制
Android 17引入了基于时间戳的GPU回压控制策略，通过CompareByTargetRunTime排序算法和精确的时间等待机制，实现GPU合成任务的智能调度，避免了传统FIFO调度的性能瓶颈。

### 🔸 扩展：GPU调试工具的生产环境部署
探讨如何在生产环境中部署GPU调试工具，包括性能开销控制、数据采样策略、以及与现有监控系统的集成方案。

## 1. 统计范围决定数量

在 Android 17 ART runtime 的生产 C++ 源码中搜索 `HeapTask` 派生关系，可以找到 10 个类型；只统计 `art/runtime/gc/heap.cc` 时是 6 个：

| 定义位置 | 派生类 | 主要工作 |
|---|---|---|
| `gc/heap.cc` | `ConcurrentGCTask` | 请求并发 GC |
| `gc/heap.cc` | `CollectorTransitionTask` | 执行收集器切换或后台压缩 |
| `gc/heap.cc` | `HeapTrimTask` | 裁剪 ART space、JNI 引用表和 arena |
| `gc/heap.cc` | `TimeBasedGcThresholdCheckTask` | 检查按时间与堆增长计算的 GC 阈值 |
| `gc/heap.cc` | `ReduceTargetFootprintTask` | fork 后分阶段降低目标堆大小 |
| `gc/heap.cc` | `TriggerPostForkCCGcTask` | 长时间没有 GC 时请求一次后台 GC |
| `gc/reference_processor.cc` | `ClearedReferenceTask` | 把已清理引用加入 Java `ReferenceQueue` |
| `startup_completed_task.h` | `StartupCompletedTask` | 完成启动通知并释放启动期资源 |
| `trace_profile.cc` | `TraceStopTask` | 到期停止低开销方法追踪 |
| `jit/jit.cc` | `MapBootImageMethodsTask` | 延时检查并映射 boot image 方法 |

“10 个派生类”也不能直接写成“10 种正常入队任务”。[`reference_processor.cc`](https://android.googlesource.com/platform/art/+/refs/tags/android-17.0.0_r1/runtime/gc/reference_processor.cc) 把 `kAsyncReferenceQueueAdd` 设为 `false`。`ClearedReferenceTask` 仍继承 `HeapTask`，但默认由 GC 调用方执行，不进入 `TaskProcessor` 队列。类型数量、定义目录和当前配置下的入队路径必须分别说明。

## 2. `TaskProcessor` 是按时间排序的单线程队列

[`task_processor.h`](https://android.googlesource.com/platform/art/+/refs/tags/android-17.0.0_r1/runtime/gc/task_processor.h) 使用 `std::multiset<HeapTask*, CompareByTargetRunTime>` 保存任务。比较器读取 `target_run_time_`，没有业务优先级字段。Java `HeapTaskDaemon` 进入 [`TaskProcessor::RunAllTasks()`](https://android.googlesource.com/platform/art/+/refs/tags/android-17.0.0_r1/runtime/gc/task_processor.cc) 后，每次取出最早到期的一项，依次调用 `Run()` 和 `Finalize()`。

这条执行路径给出三个边界：

- `ConcurrentGCTask` 中的 concurrent 描述 collector 与 mutator 的关系，不表示队列同时执行多个 `HeapTask`。
- `HeapTask` 继承 `SelfDeletingTask`，默认 `Finalize()` 释放任务；提交方交出所有权后不能再次释放。
- `TaskProcessor::Stop()` 会让未到期任务提前被取出，直到队列排空；它不是取消 GC 或清空队列的接口。

上方 outline 提到的 `CompareByTargetRunTime` 若出现在原始素材中，来源也是 ART 的这条时间队列。SurfaceFlinger 的 GPU backpressure、FPSReporter 和 LayerHierarchy 不通过 `HeapTask` 调度。

## 3. 普通应用能观察，不能控制

`VMRuntime.startHeapTaskProcessor()`、`stopHeapTaskProcessor()` 和 `runHeapTasks()` 都是隐藏运行时接口。普通应用没有受支持的 API 可以插入任务、修改 `target_run_time_`、暂停特定 GC 或调整 `target_footprint_`。

应用排查内存或卡顿时，可以：

- 在 Perfetto 线程列表定位 `HeapTaskDaemon`；
- 结合 GC cause、collector、暂停时间和 allocation 记录确认是否发生 GC；
- 查看 `Heap::TrimSpaces()`、启动清理或 time-based GC 的具体 slice；
- 把 Java heap、native heap、图形内存和文件页分开核算。

只有 `HeapTaskDaemon` 处于 Running 状态，无法判断它执行的是 GC、heap trim、启动清理、trace 停止还是 JIT 任务。通过 native hook 阻塞 daemon 或改写 vtable，还会延迟 GC 之外的运行时工作，并引入任务所有权和内部 ABI 风险。

应用侧的 GC 行为与风险边界会在 [23.6 HeapTask 与 GC 抑制纠错](23.6-heaptask-concurrent-gc-suppression.md) 继续说明。本页不再复制 post-fork 时序、任务去重和 Perfetto 细节，避免同一机制在多个入口产生不同版本。
