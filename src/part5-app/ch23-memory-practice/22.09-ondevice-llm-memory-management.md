# 22.9 端侧大模型推理的内存管理

端侧大模型推理将数十亿参数的模型加载到移动设备内存中运行。内存管理是大模型能否在目标设备上跑起来的前置条件——计算速度可以靠量化牺牲精度来换，内存放不下就是放不下。

本节聚焦 LLM 推理场景特有的内存管理问题。推理管线的硬件加速机制详见 5.11 节，Memory Advice API 的接口细节详见 23.10 节，Android 系统内存管理底层机制详见 4.1-4.3 节。

## 要点

### 大模型内存需求分析与优化

端侧大模型推理的内存消耗由三部分构成：模型权重、推理激活值（主要是 KV Cache）和框架运行时开销。

**模型权重**是基础占用。参数量直接决定内存下限：

| 模型规模 | FP16 权重 | INT8 权重 | INT4 权重 |
|----------|-----------|-----------|-----------|
| 2B | ~4 GB | ~2 GB | ~1 GB |
| 7B | ~13 GB | ~7 GB | ~3.5 GB |
| 13B | ~25 GB | ~13 GB | ~6.5 GB |

移动设备的实际可用内存远低于标称值。12 GB 内存的旗舰机，系统服务、后台进程和 GPU 共占据 4-6 GB，前台应用能拿到 2-4 GB（详见 4.1 节和 23.9 节 Android 17 App Memory Limits）。7B 模型在 FP16 下无法在端侧运行，量化到 INT4 才能挤进预算。

**量化方案**决定压缩后的精度损失：

- 对称量化（symmetric）：实现简单，零点附近精度损失大
- 非对称量化（asymmetric）：增加 scale 和 zero-point，精度更好
- 分组量化（group-wise）：按 group_size=64 或 128 分组，每组独立 scale，精度最好但增加元数据

Gemma-2 2B 在 INT4 对称量化后 MMLU 得分下降约 3-5 个百分点 `[来源: Google AI Edge 技术文档]`。实际应用中需要在目标设备上跑 benchmark，不能只看量化前后的精度指标。

**KV Cache** 是激活内存的主要来源。自回归生成时，每个 token 的 attention 计算需要前面所有 token 的 Key 和 Value 向量。KV Cache 大小计算公式：

```
KV Cache = 2 × num_layers × num_kv_heads × head_dim × seq_len × dtype_size
```

以 Llama-2 7B 为例（32 层、32 KV 头、128 维）：
- FP16、序列长度 2048：KV Cache ≈ 2 × 32 × 32 × 128 × 2048 × 2 ≈ 1 GB
- INT8 量化后：约 512 MB

控制 KV Cache 的三种方式：

1. **滑动窗口注意力**（Sliding Window Attention）：限制 attention 只计算最近 W 个 token，KV Cache 从 O(n×d) 降到 O(W×d)。Gemma-2 采用窗口大小 4096，丢弃窗口外的 KV 对，节省内存但损失长距离依赖。

2. **KV Cache 量化**：将 FP16 的 K 和 V 压缩到 INT8。Mistral 的测试数据显示 INT8 KV Cache 在大部分推理任务上精度损失可控（<1% MMLU 下降），代价是反量化计算开销。

3. **PagedAttention**：借鉴 OS 虚拟内存分页机制，KV Cache 按页分配而非预分配最大序列长度。vLLM 服务端推理框架率先实现。端侧推理框架截至 2026-05 尚未公开实现 PagedAttention `[待验证: MediaPipe LLM Inference API]`。

**框架运行时开销**通常在 100-300 MB 范围。包括推理引擎的中间表示（IR）、编译后的计算图、推理执行时的临时缓冲区。控制方式：

- 限制计算图编译时的中间缓冲区大小
- 内存复用（memory reuse）策略：不同推理步骤共享缓冲区
- 避免同时加载多个模型变体（如 FP16 和 INT4 版本同时驻留内存）

[结构参考: Clippings/Android 性能优化 - 原理：掌握 App 运行时的内存模型.md]

### Android 17 的 Memory Advice 集成

Memory Advice API 提供运行时内存压力感知，原本面向游戏场景（接口细节详见 23.10 节），对大模型推理同样适用。

**核心接口**：

```c
// 初始化
MemoryAdvice_init();

// 查询当前内存状态
MemoryState state = MemoryAdvice_getMemoryState();
// GREEN: 内存充足
// YELLOW: 接近压力阈值
// RED: 内存严重不足，应立即释放

// 注册 watcher 回调
MemoryAdvice_registerWatcher(&onMemoryPressure, nullptr);
```

`GetAvailableMemory()` 返回当前可用内存估算值（bytes），采样精度取决于设备的 meminfo 和 lowmemdetector 实现（详见 4.15 节）。

**大模型推理场景的集成策略**：

1. **加载前检查**：模型加载前查询 `GetMemoryState()`。YELLOW 降级到更小的量化版本（如 INT4 替代 INT8），RED 拒绝加载并提示用户。

2. **推理中监听**：注册 watcher 回调。收到 RED 通知时，停止当前推理、释放 KV Cache、通知上层模块降级。watcher 回调在独立线程触发，不能在里面做阻塞操作。

3. **降级链设计**：预设 INT8 → INT4 → 拒绝推理。降级过程需要释放当前模型、加载更小版本。7B INT4 模型约 3.5 GB，从 flash 加载约 2-5 秒。

Memory Advice API 在 2026-02 起被官方标记为 beta deprecated `[已验证: developer.android.com/games/sdk/memory-advice/overview, 2026-02-26]`。替代方案是 `ActivityManager.MemoryInfo` + `ComponentCallbacks2.onTrimMemory()` 的组合，精度不如 Memory Advice API。Android 17 没有提供新的替代框架 API。

### 多模型并发推理的资源调度

多模态应用需要多个模型同时驻留内存：文本模型 + 图像模型 + 语音模型。总内存预算固定，如何分配给多个模型是核心问题。

**优先级调度策略**：

为每个模型实例分配优先级：

- **P0**：当前正在交互的模型（如用户正在对话的文本 LLM）
- **P1**：后台准备的模型（如预加载的图像生成模型）
- **P2**：可选模型（如推荐的下一个对话模型）

内存压力触发时，从 P2 开始逐级驱逐。驱逐方式：

| 方式 | 动作 | 恢复时间 |
|------|------|----------|
| 直接卸载（unload） | 释放权重和 KV Cache，保留配置 | 重新加载完整时间 |
| 挂起（suspend） | 保存 KV Cache 到存储，卸载权重 | 权重加载时间 |
| 缓存保留（cache retain） | 卸载权重，保留热数据缓存 | 权重加载时间（无 KV 重建） |

**GPU 与 NPU 的任务分配**：

Android 设备上 NPU 和 GPU 是独立的硬件单元，可以并行执行。

- NPU 适合大矩阵运算（attention、FFN），能效比 GPU 高 3-5 倍 `[来源: Google AI Edge 文档]`
- GPU 适合中等规模并行计算（图像编码器、多模态投影层）
- CPU 作为 fallback，处理预处理和后处理

通过 NNAPI（API 27+）或 Delegate 机制指定目标硬件（详见 5.11 节 NNAPI 版本边界）。同一时刻 NPU 只能执行一个推理任务，第二个任务需要排队。多模型场景下，将计算密集型任务分配给 NPU，轻量任务分配给 GPU，避免 NPU 成为瓶颈。

### 推理过程的内存监控与治理

大模型推理的内存监控需要关注三个指标：

**1. 峰值内存（Peak RSS）**

推理过程中的最大 RSS 值。通过 `/proc/self/status` 的 VmHWM 字段读取，或使用 `Debug.getRss()` API（API 23+，详见 10.3 节）。

```kotlin
// 推理前记录基线
val baselineRss = Debug.getRss()

// 执行推理
runInference(model, input)

// 推理后读取峰值
val peakRss = Debug.getRss()
val inferenceMemoryDelta = peakRss - baselineRss
```

**2. GPU 内存占用**

通过 `dumpsys gfxinfo` 或 GPU 厂商扩展查询。不同 SoC 的查询路径不同——Qualcomm 通过 `/sys/kernel/kgsl/` 设备节点，ARM Mali 通过 `/sys/devices/mali0/` 设备节点。

**3. Native 堆碎片化**

Native 堆碎片化会导致推理时 malloc 失败，即使 RSS 没有超限。Android 默认使用 Scudo 分配器（详见 23.11 节），碎片化问题相对可控。

**OOM 预警和安全边际**：

推理前检查可用内存时，安全边际系数（safety margin）设为 1.5x——模型加载后，推理过程还会分配激活内存和临时缓冲区，峰值内存通常是模型大小的 1.2-1.5 倍。

```kotlin
val info = ActivityManager.MemoryInfo()
activityManager.getMemoryInfo(info)

// 可用内存不足模型大小的 1.5 倍 → 有 OOM 风险
if (info.availMem < modelSizeBytes * 1.5) {
    fallbackToSmallerModel()
}
```

不同推理框架的临时内存策略不同——TFLite 使用内存复用策略，临时开销较小；MediaPipe LLM Inference API 的临时开销较高。

**内存泄漏检测**：

大模型推理场景的内存泄漏来源：

- 模型加载/卸载循环中未释放的 Native 内存（推理引擎的 C++ 对象）
- KV Cache 未在推理结束后清理
- Delegate 资源（GPU buffer、NPU 编译结果）未释放

检测方法：

| 方法 | API 版本 | 适用场景 |
|------|----------|----------|
| `mallinfo2()` | API 31+ | Native 堆统计，对比推理前后的 `uordblks` 值 |
| Perfetto `java_hprof` | 全版本 | Java 堆快照（详见 14.22 节） |
| ASan（Address Sanitizer） | 开发期 | Native 内存泄漏检测 |

### 大模型推理的硬件加速适配

端侧大模型推理涉及 NPU、GPU 和 CPU 三条路径。硬件调度策略详见 5.11 节和 5.14 节，本节聚焦内存层面的适配差异。

**NPU 加速的内存布局约束**：

NPU 对输入数据的内存布局有严格要求。常见约束：

- 权重矩阵按 NCHW 或 NHWC 排列（不同 NPU 实现不同）
- 输入 tensor 需要连续内存（contiguous memory）
- batch size 通常固定为 1

权重重排发生在模型加载阶段。如果原始模型权重的排列方式与目标 NPU 不匹配，推理引擎需要在加载时做一次内存重排，额外消耗约 10-20% 模型大小的内存用于临时缓冲区。AOT 编译（提前编译）可以消除这个开销，但需要提前知道目标设备。

**GPU 推理的显存管理**：

GPU 推理通过 OpenCL 或 Vulkan Compute 执行。Android 设备采用 UMA 架构——GPU 显存和系统内存在同一物理 DRAM 上，但使用不同的虚拟地址映射。

跨硬件共享内存的关键接口：

- `AHardwareBuffer`（NDK API 26+）：跨模块共享内存，GPU 和 NPU 都可访问
- `CL_MEM_ALLOC_HOST_PTR`（OpenCL）：GPU 可访问区域分配，CPU 可映射
- Vulkan external memory（API 30+）：通过 `VK_ANDROID_external_memory_android_hardware_buffer` 扩展

推理引擎需要确保模型权重、KV Cache 和中间激活值都在 GPU 可访问的内存区域。TFLite GPU Delegate 通过 `CL_MEM_ALLOC_HOST_PTR` 处理；MediaPipe LLM Inference API 的 GPU 路径使用 Vulkan。

`[已验证: developer.android.com/ndk/reference/group/a-hardware-buffer; AOSP frameworks/ml/nn/]`

**CPU 推理的内存特征**：

当 NPU 和 GPU 不可用或不支持模型算子时，推理 fallback 到 CPU。CPU 推理的内存优势在于直接使用进程虚拟地址空间，不需要额外内存映射。劣势是计算速度慢、功耗高。

CPU 路径的内存优化方式：

- NEON SIMD 指令并行计算，缩短活跃内存窗口
- 按 layer 逐层计算，中间结果立即消费和释放
- 控制线程池并行度，避免过多线程同时分配临时内存

## 扩展

### 大模型推理的内存压力测试

验证端侧推理内存策略的测试方案：

**峰值内存测试**：在目标设备上运行最长允许的输入序列（如 4096 tokens），记录峰值 RSS 和 GPU 内存。连续运行 10 轮取最大值。

**长期碎片测试**：运行 1000 轮短序列推理（64 tokens 输入、32 tokens 输出），每轮结束后检查 Native 堆碎片化程度。对比第 1 轮和第 1000 轮的 `mallinfo2()` 统计。

**系统压力测试**：推理过程中启动其他内存密集型应用（相机、浏览器），观察 lmkd 是否杀掉推理进程。这个测试验证 Memory Advice API 的 watcher 是否及时触发降级。

**边界场景**：

- 后台已有 3-4 个应用时启动推理
- 推理过程中收到来电（通话应用优先级提升）
- 设备温度过高触发 thermal throttling（CPU/GPU 频率下降影响推理速度，不直接影响内存）

### 大模型推理的内存策略演进

**云端协同推理**：将大模型推理分布到端侧和云端。轻量部分（tokenization、early layers）在端侧执行，计算密集部分在云端。内存节省量取决于云端承担的比例，代价是网络延迟和隐私问题。

**推测解码（Speculative Decoding）**：用小模型（draft model）快速生成候选 token，大模型验证。内存开销增加一个小模型（通常 0.5-1B 参数），总内存增加约 15-25%，推理延迟减少 30-50%。端侧 speculative decoding 的实际效果数据 `[待验证: 截至 2026-05 缺乏公开 Android 端侧 benchmark]`。

### 行业案例分析

主流端侧 LLM 方案的内存策略对比：

| 方案 | 模型 | 量化 | 峰值内存（估算） | 目标设备 |
|------|------|------|-----------------|----------|
| Gemini Nano | ~3.25B | 自定义 | ~2.5 GB | Pixel 8+ |
| MediaPipe LLM Inference | Gemma-2 2B | INT4 | ~1.8 GB | 6GB+ |
| llama.cpp Android | Llama 7B | Q4_K_M | ~4.5 GB | 8GB+ |
| MLC-LLM | Phi-3 3.8B | Q4F16 | ~2.8 GB | 6GB+ |

`[来源: 各方案官方文档 / GitHub README，2026-05 数据]`

**多模态模型的额外内存**：

多模态模型（文本 + 图像）在传统 LLM 基础上增加视觉编码器。视觉编码器的内存开销集中在图像预处理阶段——一张 1024×1024 的图像在 FP16 下需要约 6 MB，经过 vision transformer 多层 attention 后，中间激活内存达到 100-300 MB。这部分内存可以和文本推理共享 GPU/NPU 路径，需要调度器协调分配。

## Android 17 源码级内存管理机制

本节基于 Android 17 (API 37) AOSP 源码深度分析，揭示端侧 AI Agent 内存管理的底层实现机制。

### LMKD 进程优先级批量管理机制

Android 17 引入了 LMKD (Low Memory Killer Daemon) 的 `LMK_PROCS_PRIO` 命令，支持批量进程优先级调整：

**核心源码位置**：`system/memory/lmkd/lmkd.cpp`

```cpp
static void cmd_procs_prio(LMKD_CTRL_PACKET packet, const int field_count, struct ucred* cred) {
    struct lmk_procs_prio params;
    const int procs_count = lmkd_pack_get_procs_prio(packet, &params, field_count);
    if (procs_count < 0) {
        ALOGE("LMK_PROCS_PRIO received invalid packet format");
        return;
    }
    
    for (int i = 0; i < procs_count; i++) {
        apply_proc_prio(params.procs[i], cred);
    }
}
```

**进程类型支持**：
- `PROC_TYPE_APP` - 应用进程（适用于 AI Agent）
- `PROC_TYPE_SERVICE` - 服务进程
- `PROC_TYPE_COUNT` - 进程类型总数

### ProcessList 批量处理优化

**位置**：`frameworks/base/services/core/java/com/android/server/am/ProcessList.java`

系统通过 `batchSetOomAdj()` 实现批量进程优先级调整，支持每批最多 3 个进程：

```java
public static void batchSetOomAdj(ArrayList<ProcessRecordInternal> apps) {
    final int totalApps = apps.size();
    if (totalApps == 0) return;
    
    ByteBuffer buf = ByteBuffer.allocate(MAX_OOM_ADJ_BATCH_LENGTH);
    int total_procs_in_buf = 0;
    buf.putInt(LMK_PROCS_PRIO);  // 命令类型：11
    
    for (int i = 0; i < totalApps; i++) {
        final int pid = apps.get(i).getPid();
        final int amt = apps.get(i).getCurAdj();
        final int uid = apps.get(i).uid;
        
        if (pid <= 0 || amt == UNKNOWN_ADJ) continue;
        if (total_procs_in_buf >= MAX_PROCS_PRIO_PACKET_SIZE) {
            writeLmkd(buf, null);
            buf.clear();
            total_procs_in_buf = 0;
            buf.allocate(MAX_OOM_ADJ_BATCH_LENGTH);
            buf.putInt(LMK_PROCS_PRIO);
        }
        
        buf.putInt(pid);
        buf.putInt(uid);
        buf.putInt(amt);
        buf.putInt(0);  // 默认进程类型：PROC_TYPE_APP
        buf.putInt(0);  // for_lmkd_only：批处理中不支持
        total_procs_in_buf++;
    }
    writeLmkd(buf, null);
}
```

**批处理限制**：
- `MAX_PROCS_PRIO_PACKET_SIZE = 3` - 每批最多 3 个进程
- `MAX_OOM_ADJ_BATCH_LENGTH = 64` - 批处理缓冲区大小

### OomAdjuster 智能调度策略

**位置**：`frameworks/base/services/core/java/com/android/server/am/psc/OomAdjuster.java`

OomAdjuster 管理待批量处理的进程列表：

```java
@GuardedBy("mServiceLock")
protected final ArrayList<ProcessRecordInternal> mProcsToOomAdj = new ArrayList<>();

public void batchSetOomAdj(ArrayList<ProcessRecordInternal> procsToOomAdj) {
    ProcessList.batchSetOomAdj(procsToOomAdj);
}
```

### GPU 内存监控机制

**位置**：`frameworks/base/services/core/java/com/android/server/am/ActivityManagerService.java`

系统提供精细的 GPU 内存监控：

```java
final long gpuUsage = Debug.getGpuTotalUsageKb();
if (gpuUsage >= 0) {
    final long gpuPrivateUsage = Debug.getGpuPrivateMemoryKb();
    if (gpuPrivateUsage >= 0) {
        final long gpuDmaBufUsage = gpuUsage - gpuPrivateUsage;
        // 输出 GPU 内存使用情况
        pw.print("      GPU: ");
        pw.print(stringifyKBSize(gpuUsage));
        pw.print(" (DMA: ");
        pw.print(stringifyKBSize(gpuDmaBufUsage));
        pw.print(", Private: ");
        pw.print(stringifyKBSize(gpuPrivateUsage));
        pw.println(")");
    }
}
```
