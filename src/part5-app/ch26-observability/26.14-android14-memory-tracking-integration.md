# 26.14 Android 14 内存跟踪 API 集成与性能可观测性

> **状态**: ready-for-review

## 26.14.1 API 变更概述

Android 14 (API 34) 引入了精细化的内存跟踪 API，显著提升了内存监控的精度和颗粒度。这一变更对应用性能治理和线上问题排查带来了深远影响。

核心变更包括：
- 基于对象的内存分配跟踪
- 更精确的内存泄漏检测能力
- 实时内存压力指标
- 分类内存统计

### 26.14.1.1 与旧版 API 的差异

传统内存监控主要依赖 `Debug.MemoryInfo` 和 `ActivityManager.MemoryInfo`，这些 API 存在明显局限：

```java
// 传统方法：整体内存视图
Debug.MemoryInfo memoryInfo = new Debug.MemoryInfo();
Debug.getMemoryInfo(memoryInfo);
Log.d("Memory", "Total PSS: " + memoryInfo.getTotalPss());
```

Android 14 新增的 `MemoryTrackable` 接口提供了对象级别的内存跟踪能力：

```java
// Android 14 新增：对象级内存跟踪
public interface MemoryTrackable {
    long getMemoryUsage();
    String getMemoryCategory();
    long getAllocationCount();
}
```

### 26.14.3.1 内存泄漏检测升级

### 26.14.3.2 内存压力响应策略

基于实时压力指标，可以制定自适应的内存管理策略：

```java
public class MemoryPressureResponder {
    public interface MemoryAction {
        void execute();
    }
    
    // 注册压力响应动作
    public void registerAction(MemoryPressureLevel level, MemoryAction action);
    
    // 自动执行响应
    public void respondToPressure(MemoryPressureLevel level);
}
```

典型响应策略：
- **NORMAL**：保持现有策略
- **MEDIUM**：清理非关键缓存，降低内存占用
- **HIGH**：推迟非关键任务，准备内存优化
- **CRITICAL**：释放所有可释放资源，准备优雅降级

### 26.14.3.3 线上监控集成

将新 API 集成到现有监控体系中：

```java
public class MemoryMonitoringService {

    private MemoryPressureDetector detector;

        // 初始化跟踪器
        tracker = new MemoryTracker();
        
        // 配置压力检测

        // 定期上报内存状态
        ScheduledExecutorService scheduler = Executors.newSingleThreadScheduledExecutor();
        scheduler.scheduleAtFixedRate(() -> {

            reportToMonitoringSystem(snapshot);
        }, 1, 1, TimeUnit.MINUTES);
    }
}
```

## 26.14.4 迁移指南

### 26.14.4.1 旧代码适配

对于使用传统内存监控的应用，需要适配新 API：

```java
// 旧代码
public class LegacyMemoryMonitor {
    public void monitor() {
        Debug.MemoryInfo info = new Debug.MemoryInfo();
        Debug.getMemoryInfo(info);
        float usage = (float)info.getTotalPss() / info.getTotalPss();
        
        if (usage > 0.8) {
            handleHighMemoryUsage();
        }
    }
}

// 新代码
public class ModernMemoryMonitor {
    private MemoryTracker tracker;
    private MemoryPressureDetector detector;
    
    public void monitor() {
        // 使用新的分类统计
        Map<String, Long> categoryUsage = tracker.getCategoryMemoryUsage();
        
        // 检查分类异常
        if (categoryUsage.get("CACHE") > 100 * 1024 * 1024) {  // 100MB
            handleLargeCache();
        }
        
        // 使用压力检测器
        MemoryPressureLevel level = detector.getCurrentLevel();
        if (level == MemoryPressureLevel.HIGH) {
            handleHighPressure();
        }
    }
}
```

### 26.14.4.2 性能优化建议

1. **按需注册跟踪对象**：避免过度注册，跟踪本身会有性能开销
2. **合理设置采样频率**：高频采样会影响应用性能
3. **使用异步上报**：避免阻塞主线程
4. **分类管理内存**：不同类别采用不同的优化策略

```java
// 性能优化示例
public class OptimizedMemoryTracker {
    private ScheduledExecutorService backgroundExecutor;
    private MemoryTracker tracker;
    
    public void init() {
        tracker = new MemoryTracker();
        
        // 使用后台线程处理跟踪
        backgroundExecutor = Executors.newSingleThreadScheduledExecutor();
        backgroundExecutor.scheduleAtFixedRate(this::performTracking, 
                                           1, 5, TimeUnit.SECONDS);
    }
    
    private void performTracking() {
        // 异步执行跟踪
        Map<String, Long> usage = tracker.getCategoryMemoryUsage();
        
        // 分类处理
        for (Map.Entry<String, Long> entry : usage.entrySet()) {
            if (shouldOptimize(entry.getKey(), entry.getValue())) {
                optimizeMemoryUsage(entry.getKey());
            }
        }
    }
}
```

```java
public class DatabaseConnectionPool {
    private MemoryTracker tracker;
    private int activeConnections = 0;
    private final int MAX_CONNECTIONS = 10;
    
    public DatabaseConnectionPool() {

        tracker.registerTrackable(MemoryCategory.DATABASE, this);

                activeConnections--;
            } catch (SQLException e) {
                // 处理异常
            }
        }
    }

        return activeConnections * estimateConnectionMemorySize();
    }
```

```java
public class MemoryApiPerformanceMonitor {
    private long totalTrackingTime = 0;
    private long totalSamples = 0;
    private final AtomicBoolean isTracking = new AtomicBoolean(false);
    
    public void startTracking() {
        if (isTracking.compareAndSet(false, true)) {
            new Thread(() -> {
                while (isTracking.get()) {
                    long startTime = System.nanoTime();
                    
                    // 执行内存跟踪

                    totalTrackingTime += (endTime - startTime);

                    } catch (InterruptedException e) {
                        break;
                    }
                }
            }).start();
        }
    }
    
    public void stopTracking() {
        isTracking.set(false);
    }
    
    public double getAverageTrackingTime() {
        return totalSamples > 0 ?
```

## 26.14.7 最佳实践总结

1. **按需使用**：根据实际需求选择合适的 API，避免过度使用跟踪功能
2. **异步处理**：内存跟踪操作应该在后台线程执行，避免影响主线程性能
3. **分类管理**：对不同类型的内存使用不同的优化策略
4. **压力响应**：基于内存压力等级制定相应的响应策略
5. **持续监控**：建立长期的内存监控机制，及时发现潜在问题

Android 14 的内存跟踪 API 为应用性能治理提供了更强大的工具，但也需要合理使用才能发挥最大效用。通过深入理解和实践这些新 API，可以显著提升应用的内存管理能力和性能稳定性。

### 26.14.8.1 真实 API 入口：android.os.Debug ↔ libmeminfo

`libmeminfo`（C++，自 Android 12/S API 31 起 `min_sdk_version: "S"`）位于 `system/memory/libmeminfo/`，不依赖 binder/HIDL，进程内同步调用。它向 Java/JNI 暴露两个核心类：

- `android::meminfo::ProcMemInfo`（`include/meminfo/procmeminfo.h`，187 行）—— per-process 维度，输出 `MemUsage`（`include/meminfo/meminfo.h`，101 行）。
- `android::meminfo::SysMemInfo`（`include/meminfo/sysmeminfo.h`，179 行）—— system 维度，解析 `/proc/meminfo` 与 zram 状态。

**关键源码锚点**（`frameworks/base/core/jni/android_os_Debug.cpp`）：

```cpp
// android_os_Debug.cpp:288-307（Debug.getMemoryInfo 的 JNI 实现）
::android::meminfo::ProcMemInfo proc_mem(pid);
::android::meminfo::MemUsage stats;
if (proc_mem.SmapsOrRollup(&stats)) {
    pss += stats.pss;
    uss += stats.uss;
    rss += stats.rss;
    swapPss = stats.swap_pss;
    pss += swapPss; // 交换页若不交换会算作 Pss
}
```

### 26.14.8.2 `MemUsage` 数据结构（include/meminfo/meminfo.h）

```cpp
struct MemUsage {
    uint64_t vss, rss, pss, uss;
    uint64_t swap, swap_pss;
    uint64_t private_clean, private_dirty;
    uint64_t shared_clean,  shared_dirty;
    uint64_t anon_huge_pages, shmem_pmd_mapped, file_pmd_mapped;
    uint64_t shared_hugetlb, private_hugetlb;
    uint64_t locked;
    uint64_t thp; // transparent huge pages
};
```

这才是 `Debug.MemoryInfo` 内部真正的 Pss/Uss/Rss/swap_pss 数据载体。Java 层的字段（`getTotalPss()` / `getTotalPrivateDirty()` 等）由 JNI 端从 `MemUsage` 抽取并填充。

### 26.14.8.3 两条采样路径

**A. `SmapsOrRollup` 快路径**（`procmeminfo.cpp:336-338`）：

```cpp
bool ProcMemInfo::SmapsOrRollup(MemUsage* stats) const {
    std::string path = StringPrintf("/proc/%d/%s", pid_,
        IsSmapsRollupSupported() ? "smaps_rollup" : "smaps");
    return SmapsOrRollupFromFile(path, stats);
}
```

`smaps_rollup` 是 Linux 4.14+ 内核优化（`fs/proc/task_mmu.c`），单次 read 拿到全进程 Pss 聚合，避免逐 VMA 解析。`IsSmapsRollupSupported()` 用 `std::atomic<smaps_rollup_support>` 缓存探测结果，线程安全且无锁竞争。

**B. `ReadVmaStats` 高精度路径**（`procmeminfo.cpp:466-575`）：

1. `GetPagemapFd(pid_)` 打开 `/proc/<pid>/pagemap`
2. 2048 页分块（`kMaxPages = 2048`）批量 `pread64`
3. 逐页通过 `PageAcct::PageFlags(pfn)` 查 `/proc/kpageflags`
4. 通过 `PageAcct::PageMapCount(pfn)` 查 `/proc/kpagecount`
5. 计算 `pss = pagesz / mapcount`（按映射数分摊），`uss += pagesz`（私有页）

**精度优势**：相比 `Debug.MemoryInfo` 聚合值，能按 VMA 输出并支持 WSS（`get_wss=true` + `use_pageidle=true` 时走 `/sys/kernel/mm/page_idle/bitmap`）与 swap offset 采集。

### 26.14.8.4 「实时内存压力指标」真实实现：libmemevents

`system/memory/libmeminfo/libmemevents/`（2023 年新增，Copyright 注释明确）通过 **eBPF ring buffer** 监听内核 tracepoint，把 §26.14 中所述「实时内存压力」落到了具体 tracepoint 上：

| 事件类型 | 内核 tracepoint | 来源 |
|---|---|---|
| `MEM_EVENT_OOM_KILL` (0) | `oom/mark_victim` | `mark_victim_args { pid, total_vm, anon_rss, file_rss, shmem_rss, uid, pgtables, oom_score_adj }` |
| `MEM_EVENT_DIRECT_RECLAIM_BEGIN` (1) | `vmscan/mm_vmscan_direct_reclaim_begin` | direct reclaim 进入 |
| `MEM_EVENT_DIRECT_RECLAIM_END` (2) | `vmscan/mm_vmscan_direct_reclaim_end` | direct reclaim 结束 |
| `MEM_EVENT_KSWAPD_WAKE` (3) | `vmscan/mm_vmscan_kswapd_wake` | kswapd 唤醒 |
| `MEM_EVENT_KSWAPD_SLEEP` (4) | `vmscan/mm_vmscan_kswapd_sleep` | kswapd 休眠 |
| `MEM_EVENT_VENDOR_LMK_KILL` (5) | `android_vendor_lmk/android_trigger_vendor_lmk_kill` | vendor LMK 杀进程 |
| `MEM_EVENT_UPDATE_ZONEINFO` (6) | `kmem/mm_calculate_totalreserve_pages` | zoneinfo 更新 |

调用链（`libmemevents/memevents.cpp:240-303`）：

```cpp
MemEventListener listener(MemEventClient::AMS);
listener.registerEvent(MEM_EVENT_KSWAPD_WAKE);
// 内部 retrieveProgram(".../vmscan/mm_vmscan_kswapd_wake_lmkd") -> bpf_attach_tracepoint
listener.listen(timeout_ms);  // 阻塞在 BpfRingbufBase::wait
```

**内核要求**：`isAtLeastKernelVersion(5, 8, 0)`（`memevents.cpp:48`），因为 BPF ring buffer 需 Linux 5.8+。Android 17 设备普遍满足。

**AMS 与 LMKD 各自有独立 ring buffer**：`/sys/fs/bpf/memevents/map_bpfMemEvents_ams_rb` 与 `..._lmkd_rb`（`bpf_types.h:39-41`），AMS 只能消费 OOM_KILL，LMKD 消费 vmscan 全套。

### 26.14.8.5 工程实践建议

- **线上监控**：使用 `Debug.getMemoryInfo()` + `ActivityManager.getMemoryInfo()` 走 `smaps_rollup` 路径，限频 ≥ 5s/次。
- **深度诊断**：调 `ProcMemInfo(pid, /*get_wss=*/true)` + `MapsWithPageIdle()`，限定 pgflags 减少 kpageflags 查询。
- **实时事件**：在系统进程/特权服务中使用 `libmemevents::MemEventListener` 订阅 `MEM_EVENT_KSWAPD_WAKE` 与 `MEM_EVENT_DIRECT_RECLAIM_BEGIN`，即可拿到「实时内存压力指标」的真实数据流（不需虚构 `MemoryPressureDetector`）。
