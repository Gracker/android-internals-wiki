# 22.29 Jetpack Compose 并发安全机制

Compose 允许工作线程参与状态计算，也允许 Snapshot 状态在不同线程上读写。这句话很容易被压缩成“Compose State 是线程安全的”，继而掩盖三个仍由应用负责的问题：

- 多个字段能否作为一份一致数据被观察；
- `value++` 这类读—改—写操作会不会丢更新；
- Android View、窗口 Owner 和线程受限资源是否仍在 UI 线程使用。

分析并发问题时，需要把 Snapshot 一致性、状态生产者的并发控制、Recomposer 调度、Android 出图线程分成四层。Snapshot 解决版本可见性和事务提交；它不会替业务代码决定谁可以写状态，也不会把任意复合操作变成原子操作。

## 1. 版本基线与四层边界

分析基线如下：

- Android 平台：Android 17 / API 37 / `android-17.0.0_r1`；
- kernel：`android17-6.18-2026-06_r6`；
- Jetpack Compose：稳定版 Compose BOM `2026.06.00`，Runtime 与 UI `1.11.4`。

Compose 独立于 Android platform 发布。`android-17.0.0_r1` 能固定 `Choreographer`、HWUI、BLASTBufferQueue 和 SurfaceFlinger 的实现，无法固定 Runtime、UI 或 Compose Compiler 的行为。工程复盘时要同时记录 platform、Compose BOM、Runtime/UI、Kotlin 与 compiler plugin 版本。

| 层次 | 负责的内容 | 不提供的保证 |
|---|---|---|
| Snapshot | 状态版本、读写可见性、可应用的隔离修改 | 业务级写者唯一性、复合读—改—写原子性 |
| 状态持有者 / 协程 | 请求排序、取消、并发生产者协调 | Compose 帧调度 |
| Recomposer | 收集失效、执行重组、应用 Composition 变更 | 替应用合并业务事件、固定每帧重组次数 |
| Android Owner / HWUI | UI 树、布局、绘制与窗口 buffer 提交 | 允许任意线程调用 View 或线程受限图形对象 |

传统 View 的 UI 线程规则仍然有效。某些越线程调用会被 `ViewRootImpl.checkThread()` 拒绝，另一些属性写入未必当场抛异常；“没有崩溃”不能证明调用合法。Compose 的 Snapshot 状态可以跨线程使用，`ComposeView`、`AndroidView`、Canvas 相关对象和窗口资源仍要遵守各自的线程约束。

## 2. StateObject、StateRecord 与读写路径

`mutableStateOf()` 返回的实现属于 `StateObject`。状态值保存在 `StateRecord` 链上，不同 Snapshot 按自己的 snapshot id 选择可见 record。这种设计接近 MVCC：读取者获得一致版本，MutableSnapshot 中的修改先留在自己的版本里，应用成功后才对全局状态可见。

下面的结构示意只保留 `SnapshotMutableStateImpl.value` 与 record 选择关系，便于区分 Snapshot 语义和业务原子操作。

```text
MutableState.value getter
    current StateRecord
        -> readable(this)
        -> return record.value

MutableState.value setter
    current StateRecord
        -> policy.equivalent(old, new)?
        -> overwritable(this, currentSnapshot)
        -> record.value = new
```

getter 会沿 record 链寻找当前 Snapshot 可见的版本。正常快路径不持有全局 `sync`；若并发推进全局 Snapshot 使快路径暂时找不到合法 record，Runtime 会在 `sync` 内重试。因而，“读取通常走无锁快路径”比“读取完全无锁”更准确。

setter 也不能描述成“单字段 CAS”。Runtime 1.11.4 的 `writable` / `overwritable` 在 `sync` 内选择或复用可写 record，再修改 record 内容。锁保护的是 Snapshot 内部版本结构；它不会把下面的 `counter.value++` 合成一个不可分割操作：

```kotlin
counter.value = counter.value + 1
```

这行代码包含一次读和一次写。两个生产者可以读到相同旧值，再分别写入同一个新值，造成一次更新被覆盖。单次 getter/setter 可安全执行，与一组业务操作具备原子性，是两件不同的事。

### 2.1 MutationPolicy 决定“值有没有变化”

`mutableStateOf` 默认使用 `structuralEqualityPolicy()`。新旧值按 `==` 相等时，setter 不产生可观察变化。`referentialEqualityPolicy()` 使用引用相等，`neverEqualPolicy()` 则把每次写入都视为变化。

MutationPolicy 还参与并行 MutableSnapshot 的冲突合并。默认策略的 `merge` 通常返回 `null`，表示无法自动合并两个分支的不同写入。它不负责整数累加、列表合并或请求去重；这些规则应放在状态持有者中。

### 2.2 状态对象的创建也有可见性边界

在 MutableSnapshot 内创建的状态对象，不宜在该 Snapshot 应用前泄露给别的线程或更早创建的 Snapshot。否则读取者可能遇到“状态创建时间晚于当前 Snapshot”的可见性错误。稳妥的做法是：

- 在全局上下文创建长期状态容器；
- 在一个 MutableSnapshot 内完成初始化，并在 apply 成功后发布引用；
- 不把尚未提交的 Snapshot 对象交给异步回调。

## 3. 全局写入与 MutableSnapshot 事务

直接写全局 Snapshot 状态时，修改会登记为全局待通知变化。它不等于“每次 setter 都创建一个 MutableSnapshot 并立即调用 `apply()`”。Runtime 会在推进全局 Snapshot 时通知 apply observers；`Snapshot.sendApplyNotifications()` 可主动发送待处理通知，Recomposer 的帧循环也会调用它。

连续写三个独立状态可能出现两种现象：

- 其他 Snapshot 有机会观察到字段组合的中间版本；
- 多次失效可能在帧前被合并，也可能跨越调度边界。

由此不能推导“三次 setter 必有三次重组”，也不能推导“同一帧一定只有一次重组”。正确性应依赖状态提交边界，性能结论应由 trace 证明。

### 3.1 用一份不可变 UiState 缩小一致性问题

有多个业务生产者时，推荐由 ViewModel 持有一份不可变状态，并用原子更新函数发布。下面的示例用于保证一次加载结果只发布一个 `SearchUiState`。

```kotlin
data class SearchUiState(
    val loading: Boolean = false,
    val items: List<SearchItem> = emptyList(),
    val errorMessage: String? = null,
)

class SearchViewModel : ViewModel() {
    private val _uiState = MutableStateFlow(SearchUiState())
    val uiState: StateFlow<SearchUiState> = _uiState.asStateFlow()

    fun publish(items: List<SearchItem>) {
        _uiState.update { old ->
            old.copy(
                loading = false,
                items = items,
                errorMessage = null,
            )
        }
    }
}

@Composable
fun SearchRoute(viewModel: SearchViewModel) {
    val uiState by viewModel.uiState.collectAsStateWithLifecycle()
    SearchScreen(uiState)
}
```

`MutableStateFlow.update` 对并发生产者执行原子更新。发生竞争时，更新 lambda 可能重跑，所以 lambda 内不能发送埋点、写数据库或执行网络请求。Android UI 侧用 `collectAsStateWithLifecycle()` 收集，生命周期停止时可避免无意义的 UI 收集工作。

这套写法把业务并发控制留在 ViewModel，把 Compose Snapshot 用于 UI 订阅。若状态只属于局部 UI，也可以直接使用 `MutableState`，但仍应明确唯一写者或事务边界。

### 3.2 `withMutableSnapshot` 提供多状态原子提交

多个既有 Snapshot 状态必须共同更新时，可以用 `Snapshot.withMutableSnapshot`。下面的代码用于避免读取者看到 `loading=false` 而 `data` 尚未更新的组合。

```kotlin
fun publish(result: LoadResult) {
    Snapshot.withMutableSnapshot {
        loading.value = false
        data.value = result.data
        error.value = result.error
    }
}
```

lambda 内的修改在 MutableSnapshot 中保持隔离。apply 成功后，其他 Snapshot 看到整组变化；apply 前看不到其中任何一项。这个保证描述的是可见性事务，不承诺一次 Composition、一次帧或一次绘制。

Runtime 1.11.4 的实现顺序可以压缩成下面的源码骨架。它用于说明异常、apply 与 dispose 的关系。

```kotlin
takeMutableSnapshot().run {
    var hasError = false
    try {
        enter(block)
    } catch (e: Throwable) {
        hasError = true
        throw e
    } finally {
        if (!hasError) apply().check()
        dispose()
    }
}
```

`block` 抛异常时不会 apply，Snapshot 仍会 dispose；apply 冲突时，`check()` 抛出 `SnapshotApplyConflictException`。`block` 的类型不是 `suspend`，不要在里面等待 I/O。重试冲突时还要确保 block 没有外部副作用，否则一次业务动作可能执行多次。

### 3.3 事务无法替代生产者协议

`withMutableSnapshot` 能把多项修改作为一次提交，却无法处理以下问题：

- 两个请求谁的新结果应覆盖旧结果；
- 搜索词改变后，旧请求是否取消；
- `counter.value++` 是否允许多个写者竞争；
- 一次支付、持久化或埋点能否重试。

请求代次、`flatMapLatest`、Actor、`Mutex`、数据库事务或 `MutableStateFlow.update` 才是相应层次的工具。选择哪一种取决于业务语义；Snapshot 只管理 Snapshot 状态。

## 4. Recomposer 如何处理状态变化

`Recomposer` 注册 Snapshot apply observer。变化集合与已知 Composition 的读取依赖相交后，相应 Composition 进入待处理集合。Runtime 1.11.4 的公开状态枚举如下：

| 状态 | 含义 |
|---|---|
| `ShutDown` | Recomposer 已关闭，无法继续运行 |
| `ShuttingDown` | 关闭流程进行中 |
| `Inactive` | 没有运行中的 recomposition runner，也没有待处理工作 |
| `InactivePendingWork` | runner 未运行，但已有待处理工作 |
| `Idle` | runner 正在等待，当前没有工作 |
| `PendingWork` | runner 有工作可处理 |

枚举中没有 `Working`。`PendingWork` 也不表示代码正在重组，它只说明调度器有工作可取。

### 4.1 `stateLock` 保护调度状态

`stateLock` 保护已知 Composition、Snapshot invalidation、待插入 movable content、待完成 continuation 等调度集合。`recordComposerModifications()` 会在锁内取出一批 invalidation 与目标 Composition，然后在锁外调用 `composition.recordModificationsOf()`。

重组、`applyChanges()`、`applyLateChanges()` 与 Composition 回调不会被一把长时间持有的 `stateLock` 整段包围。这个设计减少调度锁覆盖的工作量，也意味着应用不能把 `stateLock` 想象成“所有 Compose 写入的全局互斥锁”。

### 4.2 帧时钟提供节奏，不提供“一帧一次”契约

`runRecomposeAndApplyChanges()` 大致按以下顺序工作：

1. 等待待处理任务；
2. 需要帧作用域时，进入父级 `MonotonicFrameClock.withFrameNanos`；
3. 广播帧时间，并调用 `Snapshot.sendApplyNotifications()`；
4. 取出受影响的 Composition，在锁外执行重组；
5. 应用变更，并处理这轮重组产生的后续失效。

Runtime 可以在同一个 frame callback 中执行尾随重组。帧到来前的多次变化也常被合并。因此，下面两句话都不能作为契约：

- 每次状态写入都会单独重组；
- 每个显示帧只会重组一次。

若某项优化依赖重组次数，要用 Compose tracing、Layout Inspector 或测试计数器验证目标版本与目标场景。

### 4.3 Recomposer 的线程取决于 runner 上下文

Recomposer 使用启动 runner 的 coroutine context 与父级 frame clock。标准 Android 窗口的 `WindowRecomposer` 由窗口策略创建，使用该窗口 UI 线程的 `AndroidUiDispatcher.CurrentThread`；生命周期感知策略在窗口生命周期达到 `STARTED` 后恢复 frame clock 与 recomposition。

这个结论适用于标准 Android 窗口宿主。测试、Compose Multiplatform、自建 Recomposer 或显式提供 CompositionContext 时，上下文可以不同。不能把 Runtime API 概括成“所有 Recomposer 永远在 Android 主线程”。

## 5. apply observer 与 SnapshotStateObserver

`Snapshot.registerApplyObserver` 接收已经应用的变化集合。Runtime 1.11.4 在 `advanceGlobalSnapshot()` 中先于 `sync` 内完成全局 Snapshot 推进和状态交换，退出 `sync` 后再调用 apply observers，之后按需回到 `sync` 清理无用 record。

这条顺序有两个影响：

- observer 不应被描述成“在全局 Snapshot 锁内执行”；
- observer 仍可能来自不同线程，回调本身必须足够短，并遵守自身并发协议。

### 5.1 SnapshotStateObserver 不是可任意共享的线程安全对象

`SnapshotStateObserver` 的类注释明确说明实例不具备通用线程安全性。它内部做了定向并发防护：

- apply callback 可能来自别的线程，pending changes 通过 `AtomicReference` 汇集；
- observed-scope 映射在内部锁下检查和修改；
- `onChangedExecutor` 决定失效回调在哪个执行环境运行；
- `observeReads` 对当前嵌套观察线程做一致性检查。

这些实现细节用于让 apply 通知与观察线程协作，不等于一个 observer 可以同时在多个布局或绘制线程上调用 `observeReads`。Android Compose Owner 会按自己的线程模型使用它；自定义框架接入时，每个观察域应有清楚的线程归属。

性能分析也不应预设“CAS 只有纳秒级，所以 60 Hz/120 Hz 写入没有竞争”。变化集合大小、scope 数量、executor 排队、重组和绘制成本都会影响一帧。应在目标设备上测量。

## 6. 多个 ComposeView 通常共享窗口 Recomposer

每个 `ComposeView` 会创建自己的 `Composition`，却不必创建自己的 Recomposer。`AbstractComposeView.resolveParentCompositionContext()` 的查找顺序是：

1. 显式设置的 parent composition context；
2. View tree 上已有的 composition context；
3. 可复用的缓存 context；
4. 当前窗口的 `windowRecomposer`。

`windowRecomposer` 安装在内容根 View，并可被同一 View tree 中的多个 ComposeView 复用。因此，一个 Activity 中放置多个 ComposeView，常见形态是“多个 Composition，共享一个窗口 Recomposer、UI dispatcher 与 frame clock”。

以下情况才需要重点检查多个 Recomposer：

- 不同 Window 或不同 View root；
- 调用了 `setParentCompositionContext()`；
- 测试或基础设施自行创建 Recomposer；
- 缓存 context 的宿主迁移或窗口重挂载。

多 Recomposer 仍共享进程中的 Snapshot 状态系统，但各自维护待处理 Composition 和 coroutine context。它们是否落在同一线程、同一 frame clock，必须从创建路径确认，不能只数 ComposeView。

## 7. Flow、produceState 与 snapshotFlow

Flow 与 Snapshot 的方向不同：

- `collectAsStateWithLifecycle()` / `collectAsState()`：把外部数据流写入 Compose State；
- `produceState()`：在 Composition 生命周期中运行 producer，并把结果写入 Compose State；
- `snapshotFlow()`：观察 Snapshot State 读取，把结果转换成冷 Flow。

### 7.1 `produceState` 没有额外的批量提交机制

Runtime 1.11.4 中，`produceState` 的主体是 `remember { mutableStateOf(initialValue) }` 加 `LaunchedEffect(keys...)`。下面的示例用于让用户 id 变化时取消旧 producer，并启动新请求。

```kotlin
@Composable
fun rememberProfileState(
    repository: ProfileRepository,
    userId: String,
): State<ProfileUiState> = produceState(
    initialValue = ProfileUiState.Loading,
    repository,
    userId,
) {
    value = repository.load(userId)
        .fold(
            onSuccess = { ProfileUiState.Content(it) },
            onFailure = { ProfileUiState.Error(it.message) },
        )
}
```

key 变化或调用点离开 Composition 时，旧 producer 被取消。相等值由 `MutableState` 的策略合并，短时间连续赋值也可能只让观察者看到较新的值。`produceState` 不会为每个 `value = ...` 自动包一层 `withMutableSnapshot`，也不会替高频源采样。

回调式数据源可以在 producer 中注册监听，并用 `awaitDispose` 解除注册。阻塞 I/O 仍应由 repository 切换到合适 dispatcher，不能占用 composition effect context。

### 7.2 `snapshotFlow` 观察状态，不能修复写者竞争

下面的示例用于把“是否滚过首项”送给副作用收集器。副作用放在 `collect` 中，读取 block 保持纯函数。

```kotlin
LaunchedEffect(listState) {
    snapshotFlow {
        listState.firstVisibleItemIndex > 0
    }.collect { pastFirstItem ->
        analytics.updatePastFirstItem(pastFirstItem)
    }
}
```

`snapshotFlow` 在只读 Snapshot 中运行 block，记录 block 读取的状态。相关状态应用后，它会重跑 block；新结果与旧结果按 `equals` 不同时才 emit。block 若写 Snapshot 状态会抛 `IllegalStateException`。

快速变化可能被合并，block 也可能在输入集合相同的情况下重跑，所以它必须幂等且无副作用。它适合观察“当前状态”，不适合统计每一次点击、每个传感器样本或每笔业务事件。需要保留所有事件时，应从事件源直接建 Flow/Channel；需要采样时，可显式使用 `sample` 或 `debounce`，并承认它们改变了时间语义。

`snapshotFlow` 只处理观察端。两个生产者同时执行 `state.value++` 时，它不会补回丢失的更新。

## 8. Effect 的取消与线程受限资源

`LaunchedEffect` 在 Composition 的 effect coroutine context 中启动。key 变化或调用点离开 Composition 时，旧协程会被取消。`rememberCoroutineScope()` 返回的 scope 也随该 Composition 位置离开而取消。

要区分三类工作：

| 工作 | 建议位置 |
|---|---|
| 与某个 Composable 生命周期绑定的挂起工作 | `LaunchedEffect(key)` |
| 用户事件触发、仍受当前 Composition 生命周期约束的工作 | `rememberCoroutineScope()` |
| 应跨页面存活的业务请求与状态 | ViewModel 或更长生命周期的状态持有者 |

即使 Snapshot 写入允许从工作线程发起，下面这些对象也不能随意越线程使用：

- `View`、`ComposeView` 与窗口回调；
- 线程受限的 Canvas、图形上下文或资源；
- 要求特定 dispatcher 的数据库、IPC 或 SDK 对象；
- 依赖调用线程 Looper 的监听器。

状态值最好保持不可变，并避免把可变集合或线程受限对象装进 `MutableState` 后跨线程共享。Snapshot 能观察 state 引用变化，无法替普通 `ArrayList` 的内部修改提供并发保护。

## 9. 从状态变化到 Android 17 出图

纯 Compose 或普通 `ComposeView` 页面仍属于标准 HWUI App Window 路径。Snapshot 与 Recomposer 位于应用侧 UI 内容生成阶段；它们没有创建一条绕过 ViewRoot、HWUI 或 SurfaceFlinger 的显示通道。

在 Android 17 的标准窗口中，可以按下面的边界定位：

`Snapshot change → Recomposer → Composition / Layout / Drawing → AndroidComposeView → ViewRootImpl / HWUI → RenderThread → App Window BLASTBufferQueue → SurfaceFlinger → HWC → present`

只在 Drawing 阶段读取的状态，可以使失效停留在绘制阶段；若同一状态也在 Composition 或 Layout 读取，依赖范围会扩大。Drawing 仍由 Android Owner 进入宿主 HWUI，主体像素写入当前 App Window buffer。详细阶段与证据见 [§18.25 Jetpack Compose 渲染管线架构](../../part2-performance/ch18-rendering-pipelines/25-compose-rendering-pipeline.md) 和 [§22.20 Compose 性能盲区](20-compose-performance-blind-spots.md)。

kernel `android17-6.18-2026-06_r6` 负责调度应用主线程、RenderThread、Binder 与系统服务线程，并通过调度类、uclamp、cpuset 和 cpufreq 策略影响运行时机。kernel 不理解 Snapshot record、Composition scope 或 Recomposer 状态；不能用一次线程迁核解释状态一致性，也不能用 Snapshot 锁解释 GPU fence 等待。

## 10. 诊断顺序

并发问题与卡顿经常同时出现，但证据入口不同。

### 10.1 查一致性

1. 列出状态的所有写者及 dispatcher。
2. 标出必须一起变化的字段。
3. 检查复合读—改—写、请求代次与取消规则。
4. 检查可变集合、线程受限对象和未提交 Snapshot 引用是否跨线程泄露。
5. 对 `withMutableSnapshot` 冲突与 block 异常补测试。

单元测试可以让两个生产者在 barrier 后同时更新，重复运行以暴露丢更新；多字段状态则在 observer 端断言不变量。测试要验证状态组合，不能只断言“没有崩溃”。

### 10.2 查重组与帧

- Layout Inspector 的重组计数适合定位热点，调试开销会改变时序；
- Compose Compiler reports 用于检查 stability、restartability 和 skipping 条件；
- `androidx.compose.runtime:runtime-tracing` 可在 Perfetto 中补充 Composition 级切片；
- Macrobenchmark 的 `FrameTimingMetric` 用于比较用户路径的帧分布；
- Perfetto 继续检查 `Choreographer#doFrame`、Composition、Layout、Drawing、`syncAndDrawFrame`、RenderThread、BufferTX、SurfaceFlinger 与 present timing。

trace slice 名与可见粒度会随 Runtime、构建类型和 trace 配置变化。先记录版本与录制配置，再按时间轴解释；不要预设 `compose:snapshot-apply`、固定阈值或固定单帧重组次数一定存在。

## 11. 工程审查清单

- [ ] 状态容器使用不可变值，普通可变集合没有从多个线程直接修改。
- [ ] 每份业务状态有明确写者；多个写者使用 StateFlow 原子更新、Actor、Mutex 或相应事务。
- [ ] 必须共同可见的多个 Snapshot 状态放在同一个 MutableSnapshot 提交中。
- [ ] `withMutableSnapshot` block 不挂起、没有不可重放副作用，并处理 apply 冲突。
- [ ] 没有把 `state.value++` 当成并发原子操作。
- [ ] `snapshotFlow` block 只读、幂等，业务事件从原事件源收集。
- [ ] `produceState` 的 key 对应数据源身份，注册式数据源在 `awaitDispose` 中解除监听。
- [ ] ComposeView 的 CompositionContext 从创建路径确认，没有按 View 数量猜 Recomposer 数量。
- [ ] View、窗口、Canvas 和线程受限 SDK 仍在指定线程调用。
- [ ] 卡顿定位沿 Compose 阶段、HWUI、BLAST、SurfaceFlinger 与 present timing 继续向后检查。
