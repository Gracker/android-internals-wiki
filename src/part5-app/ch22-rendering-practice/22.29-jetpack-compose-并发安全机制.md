# 22.29 Jetpack Compose 并发安全机制

Compose 的渲染管线原理与重组控制机制已分别在 §7.7 和 §22.3 详细展开。本节聚焦一个在工程实战中经常被忽略、但直接影响线上稳定性的维度：**Compose 运行时的并发安全模型**。

传统 View 系统的线程规则极其简单——"只在主线程操作 UI"，违反即 crash。Compose 打破了这一约束：它的 Snapshot 状态系统在设计上允许任意线程安全地读写状态，而 Recomposer 负责将这些跨线程的状态变更安全地汇聚到主线程执行重组。这套机制带来了灵活性，也带来了新的性能陷阱。

> **版本基线**：本节基于 Compose BOM 2025.12.00（Compose 1.10）、Kotlin 2.2 分析。Snapshot 和 Recomposer 的核心并发模型自 Compose 1.0 起保持稳定，但具体实现细节（如 Pausable Composition、Strong Skipping）在后续版本有增量变化。

## 要点

### 🔹 Snapshot 状态系统：无锁读取 + 串行化合并

[已验证: Compose runtime source, Snapshot.kt — 基于公开 AndroidX 源码]

Compose 状态管理的核心是 **Snapshot 系统**。它借鉴了 MVCC（Multi-Version Concurrency Control）的思想，为每个状态对象维护一条 record chain，实现读不加锁、写时复制。

**状态对象的多版本结构**

以 `mutableStateOf(0)` 为例，底层创建的是 `SnapshotMutableStateImpl`，其 `value` 属性的 getter/setter 通过 `next.withCurrent { ... }` 在 state record chain 上操作：

```kotlin
// SnapshotMutableStateImpl.kt（简化示意）
override var value: T
    get() = next.ranks(next.readable.getRoot()).value
    set(value) {
        next.withCurrent { state ->
            // 写入时创建新的 record（copy-on-write）
            next.overwritable(state) { it.value = value }
        }
    }
```

**读路径（getter）完全无锁**。`next.readable` 通过原子操作在 record chain 上找到对当前快照可见的版本。这意味着任意线程可以安全地读取 `someState.value`——每个线程看到的是该线程当前 Snapshot 上下文中的版本。

**写路径（setter）创建新版本**。`overwritable` 在 record chain 上追加一条新 record。单次写入是原子的（单个字段的 CAS），但**跨多个状态的批量写入**需要用 `Snapshot.withMutableSnapshot { }` 保证原子性。

**全局 Snapshot 的 apply 串行化**

状态写入后，变更需要合并回全局 Snapshot 才能被其他 Snapshot 的观察者感知。这个合并（apply）过程通过一个 **全局锁** 串行化：

```kotlin
// Snapshot.kt（简化示意）
fun apply(snapshot: Snapshot, changed: Set<Any>): ApplyResult {
    synchronized(globalSnapshotLock) {
        val currentGlobal = currentGlobalSnapshot.get()
        // 1. 将 snapshot 的 changes 合并到全局 record chain
        val conflicts = snapshot.applyChanges(changed, currentGlobal)
        // 2. 通知所有 apply observers
        applyObservers?.forEach { observer ->
            observer(changed, snapshot)
        }
        return if (conflicts.isNotEmpty()) ApplyResult.Failure(conflicts)
        else ApplyResult.Success
    }
}
```

**关键性能特征**：
- apply 的锁粒度是**全局**的——所有 mutable snapshot 的合并都走同一把锁
- 但持有时间极短：仅做 record chain 指针交换 + observer 通知，不涉及 I/O 或重组计算
- 重组（composition）在 apply 之外的后续阶段发生，不持有全局锁

> ⚠️ **常见误解**：以为 Compose 的"无锁"意味着完全不需要关心线程安全。实际上，**单字段读写是无锁的，多字段原子写入仍然需要 `withMutableSnapshot`**。如果不使用它，跨多个状态的写入可能被其他线程的 apply 打断，观察到中间状态。

### 🔹 Recomposer 状态机与 stateLock

[已验证: Compose runtime source, Recomposer.kt — 基于公开 AndroidX 源码]

`Recomposer` 是 Compose 运行时的核心调度器。它维护一个状态机，决定何时执行重组。状态机由 **`stateLock`**（Recomposer 内部的 `Any` 对象）保护。

**Recomposer 的核心状态**

| 状态 | 含义 | 进入条件 |
|------|------|----------|
| `Idle` | 无待处理工作 | 所有 composition 已 apply，无 pending state changes |
| `PendingWork` | 有未完成的重组或 effect | Snapshot apply 通知了变更，或 `invalidate()` 被调用 |
| `Working` | 正在执行重组 | 从 `PendingWork` 进入，在帧回调中执行 |

**`runRecomposeAndApplyChanges()` 主循环**（简化）：

```kotlin
// Recomposer.kt（核心结构简化）
suspend fun runRecomposeAndApplyChanges() = coroutineScope {
    val companion = RecomposerState.companion
    while (shouldKeepRecomposing) {
        awaitWorkAvailable() // 挂起，等待 state 变更或帧回调
        choreographerFrameCallback.doFrame()
        synchronized(stateLock) {
            // 在锁内收集所有失效的 composition
            val snapshot = takeMutableSnapshot()
            snapshot.applyOnChange()
        }
        // 重组在锁外执行——不持有 stateLock
        performRecompose(compositions)
    }
}
```

**锁分离设计**：
1. **`stateLock` 保护的是状态机转换**（Idle → PendingWork → Working），不保护 Composition 执行
2. **Snapshot 全局锁保护的是状态合并**（apply），不保护状态机
3. **重组执行（`performRecompose`）在两把锁之外**——这是 Compose 并发设计的核心优势

这种锁分离确保了：重组耗时操作（遍历 Composable 树、计算 diff）不会阻塞其他线程的状态写入，也不会阻塞全局 Snapshot 的 apply。

**帧驱动的 recomposition 调度**

Recomposer 订阅 `monotonicFrameMilliseconds`（`Choreographer.FrameCallback` 在 Android 上的封装）。状态变更只是将 Recomposer 标记为 `PendingWork`，真正的重组发生在下一帧的 `doFrame` 回调中。

这意味着：
- 1 帧内的多次状态写入只会触发 1 次重组（帧级去重）
- 重组始终在主线程的帧回调中执行（单线程化）
- 跨线程写入的状态变更通过 Snapshot 的 apply 安全地传递到主线程

### 🔹 跨线程状态操作与 withMutableSnapshot

理解了双锁模型后，实际工程中最常遇到的并发场景是：**后台线程写状态 → UI 线程读到新值并触发重组**。

**正确的跨线程写入模式**

```kotlin
// ✅ 模式 1：批量原子写入（推荐）
Snapshot.withMutableSnapshot {
    viewModel.loadingState.value = false
    viewModel.dataState.value = newData
    viewModel.errorState.value = null
}
// 三次写入在一个 atomic snapshot 中，只触发一次 apply → 一次重组
```

```kotlin
// ❌ 反模式：分散写入导致中间状态泄漏
viewModel.loadingState.value = false  // apply → 可能触发部分重组
//                                        ↑ 其他线程可能读到 loading=false 但 data=null
viewModel.dataState.value = newData    // apply → 再次触发
viewModel.errorState.value = null      // apply → 第三次触发
```

分散写入有三个问题：
1. **部分重组**：第一次 apply 后 Recomposer 可能读到 `loading=false, data=null` 的中间状态
2. **性能浪费**：一次逻辑变更触发三次 apply + 三次重组调度
3. **竞态窗口**：后台线程的 apply 与主线程的帧回调之间存在时序不确定

**withMutableSnapshot 的实现**

```kotlin
// Snapshot.kt
inline fun <T> withMutableSnapshot(block: () -> T): T {
    val snapshot = takeMutableSnapshot()
    return try {
        snapshot.enter(block)
    } finally {
        applyMutableSnapshot(snapshot)  // 走全局锁 apply
    }
}
```

`takeMutableSnapshot()` 创建一个隔离的写上下文，`enter(block)` 在该上下文中执行 lambda，`applyMutableSnapshot` 将变更原子地合并到全局 Snapshot。

**从后台线程安全更新 UI 状态**

```kotlin
// ✅ 后台线程通过 withMutableSnapshot 安全写状态
suspend fun fetchData() {
    val result = withContext(Dispatchers.IO) {
        api.fetchData()
    }
    // 回到主线程后写入（最安全）
    Snapshot.withMutableSnapshot {
        state.data = result
        state.isLoading = false
    }
}

// ✅ 或者在后台线程直接用 withMutableSnapshot（Compose 允许跨线程写）
suspend fun fetchDataBackground() {
    val result = withContext(Dispatchers.IO) {
        api.fetchData()
    }
    Snapshot.withMutableSnapshot {
        state.data = result        // 后台线程写 Compose state，安全
        state.isLoading = false
    }
    // apply 在后台线程执行，但重组仍由主线程 Recomposer 调度
}
```

[适用版本: Compose 1.0+（Snapshot 系统的并发语义自始至终稳定）]

### 🔹 多 Recomposer 实例：隔离与共享

**全局 Snapshot 是单例**——无论一个进程中有多少个 Recomposer，它们共享同一个全局 Snapshot。这意味着跨 Recomposer 的状态变更也能被正确传播。

**但每个 Recomposer 拥有独立的：**
- `effectCoroutineContext`：Controlled by `produceComposer` / `runRecomposeAndApplyChanges`
- Composition tree（独立的 `Composition` 对象列表）
- 状态机（独立的 `stateLock` 和 `Idle/PendingWork/Working` 状态）

**典型场景：ComposeView 嵌套**

当一个 Activity 同时使用 `setContent { }` 和多个 `ComposeView` 时，每个 `ComposeView` 创建独立的 `WindowRecomposerPolicy`，但它们共享全局 Snapshot。状态变更在一个 ComposeView 中的修改可以通过 Snapshot apply 传播到另一个 ComposeView 的 Recomposer。

**潜在陷阱：多 Recomposer 的帧同步**

不同 Recomposer 各自订阅帧回调。如果两个 Recomposer 在同一帧中被调度，它们的重组按注册顺序串行执行（都在主线程）。这通常没问题，但如果某个 Composition 特别重（>8ms），会挤压后续 Recomposer 的帧时间。

建议在复杂页面（多个 ComposeView 共存）中用 Perfetto 观察：
- 每个 `androidx.compose.runtime.Recomposer` 的 trace section
- 帧内的 composition count 和单次耗时

### 🔹 SnapshotStateObserver 的无锁并发通知

§7.7 已详细介绍了 `SnapshotStateObserver`（SSO）的三阶段失效机制。这里补充其并发设计的关键细节。

**applyObserver 的注册与回调**

SSO 通过 `Snapshot.registerApplyObserver { changed, snapshot -> ... }` 注册到全局 Snapshot。每次 apply（合并变更到全局）后，所有 apply observers 被调用。这个过程在 `globalSnapshotLock` 内执行，因此：

```kotlin
// SnapshotStateObserver.kt（核心结构）
private val applyObserver: (Set<Any>, Snapshot) -> Unit = { applied, _ ->
    // ⚠️ 此回调在 globalSnapshotLock 内执行
    addChanges(applied)           // AtomicReference 无锁添加
    if (drainChanges()) {
        sendNotifications()        // 通过 onChangedExecutor 异步派发
    }
}
```

**`pendingChanges` 使用 `AtomicReference`** 实现无锁队列，避免在 observer 回调中竞争锁。`onChangedExecutor` 将通知派发延迟到自身线程（通常是主线程的 Handler），避免在 apply 锁内执行耗时回调。

**对性能的影响**：
- apply 锁内只做 `AtomicReference CAS` + 判断，纳秒级
- 真正的通知回调（标记 Composable 失效）异步执行，不阻塞 apply
- 这就是为什么高频状态变更（如动画 60fps 写 state）不会导致 apply 锁竞争

## 扩展

### 🔸 Compose 并发性能测试方法论

在评估 Compose 应用的并发性能时，以下指标值得持续监控：

| 指标 | 测量方式 | 告警阈值 |
|------|---------|----------|
| **重组频率** | `Recomposer.trackSourceInformation` + Perfetto trace section | 单帧 >3 次重组 |
| **Snapshot apply 耗时** | Perfetto `compose:snapshot-apply` track（如可用） | 单次 >1ms |
| **withMutableSnapshot 粒度** | 代码审查 + Compose Compiler Metrics | 单个函数内 >5 次 state 写入而未 batch |
| **跨线程写入频率** | `StrictMode` detectCustomSlowCalls + Thread.dumpStack | 非预期线程写入 |

**测试策略**：
1. **Macrobenchmark**：用 `androidx.benchmark:macro-junit4` 测量 `frameDurationCpuMs` 在高并发状态写入下的表现
2. **Compose Layout Inspector**：开启 "Show Recomposition Counts"，对比优化前后
3. **Perfetto trace**：搜索 `compose:recompose` track，观察单帧内的 composition 次数和耗时

[结构参考: Clippings/Android 性能优化 - CPU 优化（上）：合理使用线程池，提升 CPU 利用率.md — 线程池性能评估方法论]

### 🔸 与传统 View 系统的并发模型对比

| 维度 | 传统 View | Compose |
|------|----------|---------|
| UI 线程约束 | 只能主线程操作 View 树（违反即 crash） | 任意线程可写 Snapshot state |
| 线程安全保证 | 开发者自行保证（Handler/post） | 运行时 Snapshot 系统保证 |
| 批量更新 | `view.post { }` 手动串行 | `withMutableSnapshot { }` 声明式原子 |
| 失效通知 | `invalidate()` / `requestLayout()` | Snapshot apply observer 自动传播 |
| 测量/Layout | 主线程同步 | 主线程同步（相同），但可被 Pausable Composition 挂起 |
| 背景线程更新数据 | 必须 post 到主线程 | 直接写 state，运行时自动处理 |

**迁移建议**：从 View 迁移到 Compose 时，最大的并发模型变化是——不需要再写 `runOnUiThread { state.value = newValue }`。直接写 `state.value = newValue` 在任何线程都是安全的。但要注意 **批量写入用 `withMutableSnapshot`**，否则可能触发多次重组。

### 🔸 常见并发陷阱与诊断

**陷阱 1：LaunchedEffect 中的高频写入**

```kotlin
// ❌ 每秒 60 次写入，每次都触发独立 apply
LaunchedEffect(sensorFlow) {
    sensorFlow.collect { value ->
        sensorState.value = value  // 60fps apply，每次都进全局锁
    }
}

// ✅ 使用 produceState 或 batch collect
LaunchedEffect(sensorFlow) {
    sensorFlow.collect { value ->
        Snapshot.withMutableSnapshot {
            sensorState.value = value
            derivedValueState.value = computeDerived(value)
        }
    }
}
```

更优方案——将高频状态读取推迟到 Drawing 阶段：

```kotlin
// ✅ 在 drawWithContent 中读取，完全跳过 Composition/Layout
Modifier.drawWithContent {
    val currentValue = sensorState.value  // 读取不触发重组
    drawCircle(color = Color.red, radius = currentValue.toFloat())
}
```

这种方式利用了 §7.7 介绍的三阶段失效机制——Drawing 阶段的失效粒度最细，不会触发 Composition 重组。详见 §22.20（Compose 性能盲区）。

**陷阱 2：在 Composition 中创建 State**

```kotlin
// ❌ 每次重组都创建新的 State 对象
@Composable
fun BadPattern() {
    val state = remember { mutableStateOf(0) }
    // 如果 remember key 不稳定，会导致 State 频繁创建+销毁
    Button(onClick = { state.value++ }) { }
}
```

`remember { mutableStateOf(0) }` 的 State 对象生命周期与 Composable 的 `joinKey` 绑定。如果 joinKey 不稳定（例如 lambda 捕获导致每次不同），remember 会反复创建新的 State，旧的 State 被 GC 回收。这虽然不是并发问题，但在高重组频率下会放大内存抖动。详见 §22.3 重组控制章节。

**陷阱 3：忘记 produceState 的 Snapshot 语义**

`produceState` 内部的 `value = newValue` 每次都走 `Snapshot.withMutableSnapshot` 或直接 apply。对于高频更新场景（如传感器数据 60-100Hz），应优先使用：
- `snapshotFlow { state.value }` 将 State 转为 Flow，利用 Flow 的 conflate/distinctUntilChanged 做去重
- `derivedStateOf` 做低频派生（如连续 offset → 离散 page index）

详见 §22.3（Compose 性能优化实战）中 produceState 和 derivedStateOf 章节。
