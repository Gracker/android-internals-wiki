# 22.23 Navigation Compose 性能优化

<!-- outline-start -->
## 要点

### 🔹 Navigation Compose 架构与性能模型
- Navigation Compose 的性能问题通常不来自 `NavController.navigate()` 本身，而来自**路由参数建模、目标页组合范围、状态读取位置、返回栈状态保存**共同造成的重组与对象分配。[来源: developer.android.com/develop/ui/compose/navigation]
- `NavHost` 负责把当前 `NavBackStackEntry` 映射为目标 `composable` 内容；路由变化会让目标内容进入组合，但不等于整棵 App UI 都必须重组。应把 `NavHost` 放在稳定的 App Shell 内，让顶层栏、底部栏和内容区的状态读取边界清晰。[结构参考: 官方 Navigation Compose 文档]
- `NavBackStackEntry` 同时携带生命周期、`ViewModelStoreOwner` 和 `SavedStateRegistryOwner` 语义；性能审计时要看 ViewModel 作用域是否过大、是否把一次性大对象塞进路由或 saved state。[来源: developer.android.com/develop/ui/compose/libraries#hilt-navigation]

### 🔹 页面切换性能瓶颈
- 常见瓶颈一：把 `NavController.currentBackStackEntryAsState()` 读取放在过高层级，导致每次目的地变化都重组整套 Scaffold、导航栏或列表外壳。只在需要派生选中态的位置读取它，并用 `derivedStateOf` 或稳定映射控制重组范围。[来源: developer.android.com/develop/ui/compose/performance]
- 常见瓶颈二：路由参数传递过重。官方推荐只传递最小标识符，再由目标页从单一数据源加载详情；不要把完整对象序列化进路由字符串或 `Bundle`。[来源: developer.android.com/develop/ui/compose/navigation]
- 常见瓶颈三：导航回调在列表项中反复分配。Compose Compiler 的强跳过能力能缓解部分 lambda 分配问题，但工程上仍应保证 item key、路由字符串构造和 click handler 都以稳定输入为边界，避免点击前滚动阶段就制造额外重组。[关联: 22.3]

### 🔹 深度链接与动画性能
- 深链入口应被视为“冷启动/半热启动 + 导航恢复”的组合场景：先校验 URI、再转换为最小 route 参数，目标页延迟加载重数据。不要在 deep link 解析阶段同步做网络、数据库大查询或图片解码。[来源: developer.android.com/develop/ui/compose/navigation]
- 转场动画会增加页面切换期间的组合、布局与绘制压力。动画本身不是问题，但如果进入页首帧还伴随大列表初始化、同步 JSON 解析或图片解码，就容易把 jank 归因误判为 Navigation Compose。
- 对共享元素、复杂 enter/exit transition 或大屏多 Pane 导航，结论必须以 Macrobenchmark、Perfetto 或 FrameMetrics 数据为准；本章不写无测试条件的“提升 xx%”结论。[待验证: 项目实测]

### 🔹 复杂导航栈性能优化
- 嵌套图可以表达业务边界，但不要把每个小组件都建成独立目的地。目的地粒度越细，返回栈、状态保存和动画组合越复杂；适合独立返回、深链、权限边界或 ViewModel 作用域不同的页面才应成为 destination。
- 多 Tab 导航建议使用 `popUpTo(...){ saveState = true }`、`launchSingleTop = true`、`restoreState = true` 一类状态恢复策略，避免 Tab 重复入栈或每次切换都丢失滚动位置。[来源: developer.android.com/develop/ui/compose/navigation]
- `ViewModel` 不应被记忆在 Composable 局部变量里绕过作用域；如果使用 Hilt，应通过与当前 `NavBackStackEntry` 匹配的 `hiltViewModel()` 获取，必要时显式选择父图 entry 来共享流程级状态。[来源: developer.android.com/develop/ui/compose/libraries#hilt-navigation]

### 🔹 LazyList 导航集成
- LazyList 中的导航性能优先级是：稳定 `key`、轻量 item、点击时再构造必要 route、详情页按 id 加载数据。不要在每个 item 组合期间预先序列化复杂 route 或创建大型参数对象。
- 列表滚动与导航点击是两个不同场景：滚动阶段关注跳过重组和 item 复用；点击阶段关注去重点击、避免重复 navigate 和目标页首帧工作量。性能报告应分别采样，不能只用一次手感判断。
- 对快速连点，可在 UI 层做短窗口防抖或基于当前 destination 判重，避免重复压栈；这属于产品交互与导航状态保护，不应依赖 Navigation 组件自动吞掉所有重复事件。

### 🔹 实战：Tab 导航性能优化
- 底部 Tab 的推荐目标是“切换时恢复状态，而不是重新创建页面”。每个顶层 Tab 应有稳定 route；切换时使用 singleTop、restoreState 和保存起始 destination 状态，避免返回栈无限增长。[来源: developer.android.com/develop/ui/compose/navigation]
- Tab 预加载要谨慎：预组合多个重页面会改善首次切换手感，但会提高启动内存和首帧负担。除非有实测证明收益大于成本，否则优先保留按需组合 + 状态恢复。
- 顶栏标题、底栏选中态和内容页数据应分层读取状态；如果顶层 Scaffold 因每个详情页参数变化而整体重组，优先拆出只依赖 destination 层级的稳定 UI model。

### 🔹 实战：分步导航流程
- 登录、下单、开户注册等分步流程适合用嵌套 navigation graph 表达流程作用域；流程级 ViewModel 放在父图作用域，步骤页只读写必要字段，完成后整体弹出流程图。
- 步骤间不要通过 route 串传递大对象；传递 id、step 或 mode 即可。需要跨进程恢复的数据应进入 Repository/DataStore/Room 或 `SavedStateHandle` 中的轻量字段。
- 分支导航的性能风险主要在“回退路径不一致”和“重复创建流程状态”。审计时检查 `popUpTo` 目标、inclusive 语义和异常路径是否会留下不可见但仍持有资源的 back stack entry。

### 🔹 性能监控与调试
- Debug 阶段：使用 Layout Inspector 的重组计数/高亮、Compose Compiler metrics、系统 Trace/Perfetto 和 Macrobenchmark 分别回答“哪里重组”“为什么不可跳过”“是否造成慢帧”。[来源: developer.android.com/develop/ui/compose/performance]
- Release 阶段：不建议全量采集重型 Trace；更稳妥的是记录页面 route、导航耗时分段、慢帧窗口和关键业务事件，再对问题页面进行灰度采样 Trace。[关联: 22.37]
- 审计结论必须区分 Navigation、Compose Runtime、业务 IO、图片解码和动画绘制。Navigation 只是触发页面切换的入口，不应承担所有首帧慢的归因。

## 扩展

### 🔸 大型应用导航架构
- 大型应用可把 route 常量、参数编码和 graph 注册拆到 feature 模块，但应避免每个模块各自持有全局 `NavController`。跨模块只暴露导航意图或 route builder，实际 navigate 由宿主层统一执行。
- 动态功能模块、权限页和登录拦截会改变导航路径；性能测试应覆盖“首次安装模块/首次授权/已缓存”不同路径，避免只测最短路径。

### 🔸 可访问性性能权衡
- 可访问性语义树、焦点恢复和 TalkBack 朗读会改变页面切换后的首帧体验。优化时不能为了减少语义节点而破坏可访问性；应优先减少无意义嵌套、重复语义和同步主线程工作。
- 对复杂 Tab 或分步流程，焦点恢复策略应与返回栈状态恢复一起测试，确保 restoreState 后不会把焦点落到已不可见或语义重复的节点上。

### 🔸 跨平台导航性能
- 本章只覆盖 Android 应用中的 AndroidX Navigation Compose。Compose Multiplatform、Wear、TV 或 Automotive 的导航栈和输入模型不同，不能直接套用本章性能结论。[边界: 本章版本范围]
- 如果项目同时维护 Fragment Navigation 和 Navigation Compose，迁移期应用同一套 Macrobenchmark 场景对比首帧、返回、深链和 Tab 切换，不应只用 API 形态判断性能优劣。

## 1. 审计基线与边界

本章面向 **Android 14（API 34）到 Android 17（API 37）** 上运行的 AndroidX Navigation Compose 应用。Navigation Compose 属于 Jetpack/AndroidX 能力，实际行为随 `androidx.navigation:navigation-compose`、Compose Runtime、Compose Compiler 和 Kotlin 版本变化；它不是 Android 17 平台框架新增的系统导航机制。[来源: developer.android.com/jetpack/androidx/releases/navigation]

因此，本章采用两个边界：

1. **平台边界**：不引入 Android 18/API 38+ 的主线结论，也不把 Android 17 系统源码当作 Navigation Compose 行为的唯一依据。
2. **证据边界**：没有 Macrobenchmark、Perfetto、FrameMetrics 或项目埋点支撑时，不写固定百分比收益；只能给出可复核的结构性优化建议。

## 2. 性能模型：导航不是孤立耗时点

一次 Compose 导航通常包含以下链路：用户事件触发 `navigate()`，`NavController` 更新返回栈，当前 `NavBackStackEntry` 变化，`NavHost` 选择目标 destination，目标页进入组合并读取 ViewModel/Repository 状态，随后进入布局、绘制和可能的转场动画。慢帧可能发生在任一阶段。

工程审计时不要只问“Navigation Compose 快不快”，而要拆成四个问题：

- **状态读取是否过宽**：当前 destination 变化是否让整个 App Shell 重组？
- **目标页首帧是否过重**：是否在组合阶段同步做排序、过滤、JSON 解析、数据库阻塞或图片解码？
- **返回栈是否重复膨胀**：Tab、详情页或连点是否不断压入等价 destination？
- **状态恢复是否正确**：返回和 Tab 切换是否反复重建列表状态、ViewModel 或网络请求？

这四类问题中，只有第二类的一部分能从 Navigation API 表面看出来；其余都需要结合 Compose 性能工具和业务状态流向排查。[来源: developer.android.com/develop/ui/compose/performance]

## 3. 路由参数：只传最小标识符

官方 Navigation Compose 文档强调，导航时应传递必要的最小信息，例如对象 id，而不是把完整对象作为参数传递；目标页再根据 id 从单一数据源加载数据。[来源: developer.android.com/develop/ui/compose/navigation]

推荐模式：

```kotlin
@Serializable
data class ProfileRoute(val userId: String)

navController.navigate(ProfileRoute(userId = user.id))
```

目标页只把 `userId` 作为加载键：

```kotlin
@Composable
fun ProfileScreen(
    userId: String,
    viewModel: ProfileViewModel = hiltViewModel()
) {
    val uiState by viewModel.state(userId).collectAsStateWithLifecycle()
    ProfileContent(uiState)
}
```

反模式包括：

- 在 route 中拼接大段 JSON，导致编码、解码和字符串分配进入点击路径。
- 把可变业务对象直接塞进参数，造成恢复后状态与数据源不一致。
- 为了“少查一次库”把列表页的完整 item 传给详情页，最终破坏单一数据源和进程恢复能力。

如果确实需要临时共享复杂数据，优先考虑流程级 ViewModel、Repository 缓存或持久化数据源，而不是扩大路由参数。

## 4. 控制重组范围：让 destination 变化只影响必要 UI

`currentBackStackEntryAsState()` 很方便，但读取位置决定重组范围。如果在最顶层读取它并派生多个不稳定对象，页面切换会让顶层 Scaffold、底栏、顶栏和内容外壳一起重组。更稳妥的做法是把导航状态转换成稳定、粒度小的 UI model。

```kotlin
@Composable
fun AppScaffold(navController: NavHostController) {
    val backStackEntry by navController.currentBackStackEntryAsState()
    val currentRoute = backStackEntry?.destination?.route

    val selectedTab by remember(currentRoute) {
        derivedStateOf { currentRoute.toTopLevelTab() }
    }

    Scaffold(
        bottomBar = {
            AppBottomBar(
                selectedTab = selectedTab,
                onTabClick = { tab -> navController.navigateTopLevel(tab) }
            )
        }
    ) { padding ->
        AppNavHost(navController, Modifier.padding(padding))
    }
}
```

检查重点不是“有没有重组”，而是重组是否限制在真正依赖 route 的节点上。底栏选中态需要随 route 变化；列表 item、图片、详情页业务内容不应因为顶层派生对象不稳定而无意义重组。

## 5. Tab 导航：保存状态，避免重复入栈

底部 Tab 的常见目标是：切换到新 Tab 时打开该 Tab 起始页；再次切回旧 Tab 时恢复其滚动位置和子返回栈；重复点击当前 Tab 不重复压栈。Navigation Compose 的典型配置是 singleTop、保存起始 destination 状态并恢复状态：[来源: developer.android.com/develop/ui/compose/navigation]

```kotlin
fun NavHostController.navigateTopLevel(tab: TopLevelTab) {
    navigate(tab.route) {
        popUpTo(graph.findStartDestination().id) {
            saveState = true
        }
        launchSingleTop = true
        restoreState = true
    }
}
```

审计时需要验证三件事：

1. 连续点击同一 Tab，back stack 不应增加等价 destination。
2. 从 Tab A 的二级页切到 Tab B 再回来，产品期望是恢复二级页还是回到 A 的起始页；代码要和期望一致。
3. 列表滚动位置是否由 `LazyListState`、ViewModel 状态或 Navigation state 正确保存，不能靠“页面没被销毁”的偶然行为。

## 6. ViewModel 作用域：共享要显式，释放要及时

Navigation Compose 让每个 back stack entry 都可作为 ViewModel owner。Hilt 集成下，`hiltViewModel()` 默认从当前 destination 的 owner 获取 ViewModel；如果多个步骤需要共享同一个流程状态，应显式使用父 navigation graph 的 back stack entry。[来源: developer.android.com/develop/ui/compose/libraries#hilt-navigation]

```kotlin
@Composable
fun CheckoutStep(navController: NavHostController) {
    val parentEntry = remember(navController) {
        navController.getBackStackEntry("checkout")
    }
    val viewModel: CheckoutViewModel = hiltViewModel(parentEntry)
    CheckoutStepContent(viewModel)
}
```

这样做的收益是作用域清晰：流程未结束时状态共享；流程完成并从 back stack 弹出后，ViewModel 可以随父 entry 释放。反过来，如果把流程状态放到 Activity 级 ViewModel，只为了跨步骤方便，可能让一次性图片、表单草稿或上传任务在流程退出后仍被持有。

## 7. LazyList 到详情页：把滚动性能和点击性能分开测

列表页常见误区是把导航优化写在 item 组合路径上。例如每个 item 都提前构造复杂 route、格式化大对象或创建不稳定回调。更好的结构是：

```kotlin
items(
    items = users,
    key = { it.id }
) { user ->
    UserRow(
        user = user,
        onClick = { navController.navigate(ProfileRoute(user.id)) }
    )
}
```

如果 `UserRow` 仍频繁重组，优先检查 `users` 列表实例是否稳定、item key 是否正确、`user` 是否包含每帧变化字段，以及父级是否读取了过宽状态。点击导航本身应在用户事件发生时才执行；滚动阶段不应为尚未点击的 item 支付详情页参数构造成本。[关联: 22.3]

## 8. 深链和动画：用慢帧证据拆分责任

深链进入页面时，可能同时发生 Activity 启动、URI 解析、认证跳转、目标页数据加载、图片请求和转场动画。要定位 Navigation Compose 性能，建议记录以下时间点：

- 收到 deep link intent 的时间。
- 完成 URI 校验和 route 转换的时间。
- 调用 navigate 或设置 start destination 的时间。
- 目标页首个稳定 UI state 到达的时间。
- 首帧绘制和后续慢帧窗口。

转场动画审计也要使用类似分段：如果动画 Slice 正常，但目标页组合阶段同步加载 200 个 item，瓶颈不在动画；如果目标页轻量但动画期间 GPU/RenderThread 压力升高，才应优化动画复杂度、图层和绘制内容。

## 9. 监控清单

上线前至少建立以下检查项：

- **路由唯一性**：同一业务页面是否有稳定 route，重复点击是否被 singleTop 或业务判重保护。
- **参数轻量化**：route 只包含 id、枚举、分页键等轻量参数；大对象从数据源读取。
- **状态恢复**：Tab、返回、进程重建后是否恢复到符合产品预期的状态。
- **重组范围**：destination 变化是否只影响顶栏/底栏选中态和目标内容，不拖动无关列表或图片重组。
- **首帧负担**：目标页组合阶段没有同步重计算、阻塞 IO 或大对象解码。
- **证据闭环**：Debug 用 Layout Inspector/Perfetto/Macrobenchmark 定位；Release 用轻量埋点发现问题页面，再灰度采集重型证据。

## 10. 待验证项

本轮 deep-review 已把原占位内容改写为可审计正文，但以下内容仍需要项目级实测后才能定稿：

- 目标 App 的 Tab 切换、详情页进入、深链进入和返回路径的 Macrobenchmark 数据。
- `navigation-compose` 具体版本下 typed route、动画和状态恢复 API 的项目兼容性。
- 多模块导航中 route builder 的稳定性、混淆/序列化配置和动态功能模块加载耗时。
- TalkBack、键盘焦点、大屏多 Pane 场景下的状态恢复与首帧体验。

在这些证据补齐前，本章保持 `ready-for-review` 与 `confidence: medium`，不推进 `finalized`。
