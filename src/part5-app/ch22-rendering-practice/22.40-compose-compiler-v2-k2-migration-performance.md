# 22.40 Compose Compiler v2 / K2 编译器迁移与 @Composable 编译优化

Compose 编译器处在 Kotlin 源码与 Compose Runtime 之间。它既能影响构建时间，也会改变 `@Composable` 函数的调用约定、跳过判断和 lambda 记忆方式。讨论迁移时必须把这几层分开：

1. **K2 frontend** 负责语义分析、调用解析和类型推断；
2. **Compose compiler plugin** 在编译期间检查 Compose 语义并改写 IR；
3. **Kotlin/JVM backend、D8 与 R8** 继续生成、转换和优化字节码；
4. **Compose Runtime** 在设备上执行生成的 group、状态读取和跳过逻辑；
5. **Android framework、HWUI、SurfaceFlinger 与 kernel** 负责后续帧调度和显示。

K2 编译更快，不等同于某个页面会少重组；报告中的 `skippable` 增加，也不等同于帧耗时会下降。迁移、验证和性能测量都要遵守这条边界。

## 版本基线与名词校正

版本基线固定为 2026 年 7 月可复现的稳定版本：

| 层级 | 版本基线 | 约束 |
| --- | --- | --- |
| Android platform | Android 17 / API 37 / `android-17.0.0_r1` | `compileSdk = 37` 至少需要 AGP 9.1.1 |
| Android 构建工具 | AGP 9.1.1、Gradle 9.3.1、JDK 17 | AGP 9 默认启用 built-in Kotlin |
| Kotlin / Compose compiler | KGP 2.4.10 / `org.jetbrains.kotlin.plugin.compose` 2.4.10 | Compose plugin 引入同版本 KGP，须检查构建脚本的解析结果 |
| Jetpack Compose | Compose BOM 2026.06.01；Runtime、UI 1.11.4 | BOM 不管理 Compose compiler |
| Android kernel | `android17-6.18-2026-06_r6` | 不参与 Kotlin 或 Compose 编译器语义 |

AGP 9.1.1 的发布依赖以 KGP 2.2.10 为基线；Compose compiler plugin 2.4.10 又声明了对 KGP 2.4.10 的依赖。当前配置中，Gradle 的版本冲突解析会选择 2.4.10，但这不是“AGP 自带 Kotlin 2.4.10”。迁移时应检查根工程的 `buildEnvironment` 输出，确认没有 convention plugin、`pluginManagement` 或 resolution rule 把 KGP 固定到其他版本。Google Maven 上的 Compose BOM 2026.06.01 则把 Runtime 与 UI 都约束为 1.11.4。

“Compose Compiler v2”常用于泛指 Kotlin 2.x 时代的 Compose compiler。它不是一条独立于 Kotlin 的 `2.x` 版本线。Compose compiler 从 Kotlin 2.0.0 起并入 Kotlin 仓库，随 Kotlin 同步发布；Kotlin 2.4.10 对应的插件版本也是 2.4.10。

下列常见术语需要按当前实现收窄：

| 常见表述 | 当前实现中的准确含义 |
| --- | --- |
| Frontend IR | K2 frontend 使用 FIR（Frontend Intermediate Representation）；语义分析结果随后进入 Kotlin IR，Compose 的主要代码改写发生在 IR lowering |
| K1 → K2 适配层 | 迁移结果是一套面向 K2 与现行 compiler plugin API 的实现，不能按运行时“适配层”理解 |
| K2 优化 `@Composable` 解析路径 | K2 改写了 Kotlin frontend；Compose 插件仍负责 Compose 诊断和 IR 变换，官方没有承诺每个 composable 都走一条独立的快速解析路径 |
| Compose Compiler v2 | Kotlin 2.x 时代的简称；版本号跟随 Kotlin |
| `$composable` 后缀调用链 | 生成名称属于实现细节，没有一个可供业务代码依赖的通用 `$composable` ABI |
| K2 native codegen | Android 目标仍生成 JVM 字节码并转换为 DEX；Kotlin/Native、JS、Wasm 是其他 target |

这些区别会直接影响故障归因。编译前端报错、Compose lowering 报错、D8/R8 报错和设备上的重组异常，分别对应不同阶段。

## K2、FIR 与 Compose compiler 的关系

K1 和 K2 的主要分界位于 Kotlin frontend。frontend 读取源码和依赖信息，完成名字解析、重载选择、类型推断、控制流分析与诊断。K2 用 FIR 统一承载更多语义信息，再把合法程序交给公共 IR 与各平台 backend。

Compose compiler 是 Kotlin compiler plugin。它有两类工作：

- 在 frontend 阶段注册 Compose 相关检查和解析扩展，例如 `@Composable` 调用位置、target 与函数类型约束；
- 在 IR 阶段改写 composable 函数、调用、lambda、默认参数和稳定性信息。

Kotlin 2.4.10 的 [`ComposeIrGenerationExtension`](https://github.com/JetBrains/kotlin/blob/v2.4.10/plugins/compose/compiler-hosted/src/main/java/androidx/compose/compiler/plugins/kotlin/ComposeIrGenerationExtension.kt) 能看到当前 lowering 顺序。其中包括 `ComposableDefaultParamLowering`、`ComposerLambdaMemoization`、`ComposerParamTransformer` 和 `ComposableFunctionBodyTransformer`。这条源码证据比反编译后猜测某个方法名可靠，因为 R8、backend 与编译选项都可能继续改写产物。

K2 的构建收益也应限定到被测项目。JetBrains 的迁移文档给出了 Anki-Android 和 Exposed 的基准结果，但这些数字不能直接移植到另一套模块图、注解处理器、Gradle 插件和 CI 机器。项目内应分别测 clean build、无改动 build、ABI 变化和非 ABI 变化。

Kotlin 2.4.0 已移除 `-language-version=1.9`，K1 无法在 2.4 工具链内恢复。迁移失败时，可行的回退方式是把 Kotlin、Compose plugin、相关源码修改和构建配置一起退回已验证分支；只加一条 K1 flag 会在当前编译器中失败。

## `@Composable` 函数经过了什么改写

下面的源码只用于建立概念模型，参数数量、bit 排布和生成名称不能当成稳定 ABI：

```kotlin
@Composable
fun Greeting(name: String, emphasized: Boolean = false) {
    Text(if (emphasized) name.uppercase() else name)
}
```

业务源码只声明两个参数。编译后，Compose lowering 会引入 `Composer`、changed mask 和默认参数 mask，并围绕函数体生成 group、参数变化检查、跳过与 restart 更新逻辑。

下面的伪代码用于展示这类生成结构，不对应可直接编译的 Kotlin：

```text
Greeting(
    name,
    emphasized,
    composer,
    changedMask,
    defaultMask
) {
    dirty = changedMask + parameter-change checks
    if (parametersAllowExecution || !composer.skipping) {
        // original function body
    } else {
        composer.skipToGroupEnd()
    }
    endRestartGroup()?.updateScope { ... }
}
```

`Composer` 连接生成代码与 Compose Runtime；changed/default mask 传递调用点已知信息，减少重复比较；restart scope 让失效的 group 可以单独重新执行。固定 tag 的 [`ComposableFunctionBodyTransformer`](https://github.com/JetBrains/kotlin/blob/v2.4.10/plugins/compose/compiler-hosted/src/main/java/androidx/compose/compiler/plugins/kotlin/lower/ComposableFunctionBodyTransformer.kt) 对 changed bits、default bits、skip preamble 和 restart group 都有对应实现。

### composable lambda

源码中的 composable lambda 可能被包装为 Runtime 能跟踪和更新的对象，普通 lambda 还可能由编译器插入记忆逻辑。产物是否出现 `ComposableLambdaImpl`、独立类、`invokedynamic` 或内联结果，受 target、lambda 形态、Kotlin backend、Compose compiler 与 R8 共同影响。

因此，反编译产物适合回答“这个构建变体生成了什么”，不适合定义跨版本契约。业务代码和测试都不应反射生成类、依赖 synthetic 参数位置，或按生成方法后缀做 keep rule。

### 默认参数

Composable 的默认表达式需要在正确的 composition group 内执行。Compose compiler 使用默认参数 mask 处理这项工作，并为虚函数场景运行专门的 lowering。Kotlin 2.4.10 源码入口是 [`ComposableDefaultParamLowering`](https://github.com/JetBrains/kotlin/blob/v2.4.10/plugins/compose/compiler-hosted/src/main/java/androidx/compose/compiler/plugins/kotlin/lower/ComposableDefaultParamLowering.kt)。

迁移后出现默认参数或 override 相关诊断时，应先检查以下条件：

- interface、abstract/open 声明与 override 的 `@Composable` 契约是否一致；
- 函数类型两侧是否都带有正确的 `@Composable`；
- expect/actual 声明的参数、默认值和可见性是否满足 K2 规则；
- 依赖模块是否用兼容的 Kotlin 与 Compose compiler 重新发布；
- 是否仍存在旧插件注入的 compiler argument。

在公共 API 边界显式写出 `@Composable` 函数类型，比依赖旧 frontend 的宽松推断更容易维护。诊断变化并不表示 Runtime 改了 Composition 规则，它通常表示 K2 更早拒绝了一组含糊或不一致的声明。

## Android 17 工具链配置

API 37 的主基线采用 AGP 9.1.1。AGP 9 已为 Android module 提供 built-in Kotlin，因此 Android application/library module 不再应用 `org.jetbrains.kotlin.android`。Compose module 仍要应用 `org.jetbrains.kotlin.plugin.compose`。

下面的 version catalog 用于把 AGP 与 Kotlin/Compose plugin 版本放在一个可审计位置：

```toml
[versions]
agp = "9.1.1"
kotlin = "2.4.10"

[plugins]
android-application = { id = "com.android.application", version.ref = "agp" }
android-library = { id = "com.android.library", version.ref = "agp" }
compose-compiler = { id = "org.jetbrains.kotlin.plugin.compose", version.ref = "kotlin" }
```

`kotlin` 版本仍有用途：它给 Compose compiler plugin 定版，而该插件会引入同版本的 KGP。这里没有 `org.jetbrains.kotlin.android`，因为 Android module 的 Kotlin 编译已由 AGP 9 接管；Kotlin Multiplatform module 仍按 KMP 插件规则配置。插件依赖仍可能被工程级解析规则改写，因此升级后要用 `./gradlew buildEnvironment` 核对最终构建 classpath。

根工程只声明插件版本，供各 module 按需应用：

```kotlin
plugins {
    alias(libs.plugins.android.application) apply false
    alias(libs.plugins.android.library) apply false
    alias(libs.plugins.compose.compiler) apply false
}
```

`apply false` 不会在根工程执行 Android 或 Compose plugin。每个含 Compose 源码的 module 仍需单独应用 Compose compiler plugin。

应用 module 的最小配置可以写成下面这样：

```kotlin
plugins {
    alias(libs.plugins.android.application)
    alias(libs.plugins.compose.compiler)
}

android {
    namespace = "com.example.app"
    compileSdk = 37

    defaultConfig {
        targetSdk = 37
    }

    buildFeatures {
        compose = true
    }

    compileOptions {
        sourceCompatibility = JavaVersion.VERSION_17
        targetCompatibility = JavaVersion.VERSION_17
    }
}

dependencies {
    implementation(platform("androidx.compose:compose-bom:2026.06.01"))
    implementation("androidx.compose.runtime:runtime")
    implementation("androidx.compose.ui:ui")
}
```

Compose BOM 只约束列入 BOM 的 AndroidX Compose libraries。`org.jetbrains.kotlin.plugin.compose` 仍由 Kotlin 版本控制。AGP built-in Kotlin 默认让 JVM target 跟随 Android `targetCompatibility`，没有特殊需求时无需再复制一份 `jvmTarget`。

### 旧配置应当移除

Kotlin 1.9 时代常见的配置不能与新插件重复保留。下面这个片段只用于识别需要删除的旧项：

```kotlin
android {
    composeOptions {
        kotlinCompilerExtensionVersion = "1.5.x"
    }
}

tasks.withType<org.jetbrains.kotlin.gradle.tasks.KotlinCompile>().configureEach {
    kotlinOptions {
        freeCompilerArgs += listOf(
            "-P",
            "plugin:androidx.compose.compiler.plugins.kotlin:..."
        )
    }
}
```

使用 Kotlin 2.4 与 Compose Compiler Gradle Plugin 后，版本和选项由新插件传给编译器。旧 `kotlinCompilerExtensionVersion`、旧 Maven 坐标与手写 `-P plugin:` 参数可能造成重复选项、加载两份插件或使用不兼容 artifact。

直接引用 compiler artifact 的少数构建系统也要使用 Kotlin 仓库中的新坐标。Gradle Android 工程优先使用 plugin；手工拼装 `kotlin-compose-compiler-plugin-embeddable` 会把兼容性责任转移给工程维护者。

### built-in Kotlin 与 kapt

AGP 9 built-in Kotlin 不兼容 `org.jetbrains.kotlin.kapt`。迁移顺序应优先把 processor 切到 KSP；仍无法迁移的 module 可按 AGP 文档改用与 AGP 同版本的 `com.android.legacy-kapt`。这项变化属于 AGP 9 迁移，不能归因给 Compose Runtime。

`android.kotlinOptions {}` 也应改为 `kotlin.compilerOptions {}`。若只是设置 JVM target，并且已经设置 Android `targetCompatibility`，built-in Kotlin 的默认值通常已经满足要求。

## Strong Skipping 在 Kotlin 2.4 中的含义

Strong Skipping 从 Kotlin 2.0.20 起默认启用。到了 Kotlin 2.4，`enableStrongSkippingMode`、`ComposeFeatureFlag.StrongSkipping`、`enableIntrinsicRemember` 等旧开关已经提升为 error 级废弃项。迁移脚本不应继续“显式开启”这些基线行为。

Strong Skipping 改变两类生成结果：

1. restartable composable 即使含有不稳定参数，也可以被标记为 skippable；
2. composable 内的 lambda 会自动 memoize，包括捕获不稳定对象的 lambda。

能否在一次重组中跳过，仍取决于参数比较：

| 参数的编译器稳定性 | 运行时比较 |
| --- | --- |
| stable | 对象相等性，即 `equals()` |
| unstable | 实例相等性，即 `===` |

这一点容易被写反。`List<Item>` 默认被视为不稳定参数时，每次创建新 list 实例都会让实例比较失败；Strong Skipping 不会自动对它做逐元素 `equals()`。只有类型被编译器视为 stable 后才使用对象相等性，而错误的 stability 声明可能让 UI 漏掉更新。

下面的例子用于观察 unstable 参数和 lambda capture 的处理：

```kotlin
@Composable
fun ResultRow(
    result: SearchResult,
    onOpen: (SearchResult) -> Unit
) {
    Button(onClick = { onOpen(result) }) {
        Text(result.title)
    }
}
```

如果 `SearchResult` 被推断为 unstable，父级下次传入同一个实例时，`ResultRow` 有机会跳过；传入新实例时不会跳过。`onClick` lambda 会按捕获值生成记忆逻辑，unstable capture `result` 使用实例相等性作为 key 比较。

有明确语义需求时，可以使用 `@NonSkippableComposable` 退出函数跳过，或用 `@DontMemoize` 退出某个 lambda 的自动记忆。这两个注解适合解决已确认的语义或性能问题，不宜作为批量迁移模板。

Strong Skipping 也会增加少量生成代码。是否获得净收益取决于参数变化模式、比较成本、函数体成本和 APK 优化结果，应由 release 构建与设备测量决定。

## Kotlin 2.4 的增量编译变化

Kotlin 2.4 调整了跨文件 `internal` 类型的 Compose stability 处理。一个 composable 的参数若引用同 module、另一个文件中的 `internal` 类型，编译器会把相关 stability 判断延后到运行时，使该类型的推断变化不必强制重编译所有使用文件。

这一实现带来两个结果：

- 增量编译的一致性提高，stability 变化不再依赖使用文件是否恰好重编译；
- 未压缩产物可能同时编码 stable 与 unstable 两条执行路径，体积略有增加。

Kotlin 官方说明指出，全应用优化器可以识别并删除不可能使用的分支。Android release 构建中的 R8 属于这类优化器。该变化不会修改类型最终得到的 stability 值，也没有改变 composable 的预期行为。

这项改动不能概括为“K2 增量前端只分析改动文件”。Kotlin incremental compilation 还要追踪 ABI、inline、常量、lookup、compiler option、plugin input 和 annotation/symbol processor 的影响范围。任一环节扩大失效集，整次 build 都可能重编译更多文件。

## 编译性能怎样测

迁移报告至少拆成四个场景：

| 场景 | 要回答的问题 | 示例改动 |
| --- | --- | --- |
| clean release | 无缓存全量成本是否变化 | 删除工程 build 输出后 `assembleRelease` |
| no-change | 配置和 up-to-date 检查是否变慢 | 不改文件重复执行相同 task |
| non-ABI incremental | 函数体小改动影响多大 | 修改 private 函数体或字符串 |
| ABI incremental | 公共签名变更传播多远 | 修改 public 参数或返回类型 |

每个场景都要固定机器、JDK、Gradle、worker 数、daemon 状态、网络依赖缓存和构建 task。预热后多次运行，报告 median、p90 与离散程度；只报一次耗时无法区分迁移收益和后台负载。

下面的命令用于获取 Gradle 自带的构建 profile，适合建立初步阶段分布：

```bash
./gradlew :app:assembleRelease --profile
```

HTML profile 能显示 task 时间和配置阶段，但它不能替代严格的多轮 benchmark。需要自动应用源码变更时，可使用 Gradle Profiler 定义场景并保留原始结果。

Compose compiler reports 和 metrics 会增加分析结果序列化与磁盘写入。做常规编译耗时对比时应关闭它们；评估“生成报告的构建”时再作为单独场景开启。官方没有给出一条适用于所有工程的“报告生成速度提升比例”。

建议保存下面这些上下文，便于复现：

- commit SHA、Gradle task 和 variant；
- Kotlin、Compose plugin、AGP、Gradle、JDK 版本；
- configuration cache、build cache、KSP/kapt 状态；
- 本地或远端缓存命中率；
- Compose reports 是否开启；
- clean、warm 与 incremental 的准确操作；
- 每轮的原始耗时，而非只留平均值。

## 运行时对比不能从编译报告推断

Compose compiler 生成的代码会影响 Runtime 的跳过和 restart 逻辑，但“K1 产物”和“K2 产物”通常还伴随 Kotlin 版本、Compose compiler 版本、Strong Skipping 默认值和依赖版本变化。直接比较两份 APK，得到的是一组工具链变化的合成结果。

若要隔离运行时差异，可按以下方式组织实验：

1. 固定业务源码、Compose Runtime、设备、系统镜像和 benchmark 脚本；
2. 两个构建都使用 release、相同 R8 状态和相同 Baseline Profile 状态；
3. 清除或固定 app 数据与后台条件；
4. 以 Macrobenchmark 测 TTID、TTFD、frame timing 或特定交互；
5. 用 Layout Inspector 的重组/跳过计数定位范围，不拿 Inspector 开启时的耗时做结论；
6. 用 Perfetto 对齐 recomposition、UI thread、RenderThread 与 FrameTimeline；
7. 同时检查 DEX 体积、方法数和生成代码差异。

Kotlin 2.4 已没有同版本 K1 开关，无法构造“除 frontend 外完全相同”的当前版本 A/B。历史 K1/K2 比较可以记录迁移前后的产品表现，但结论应标注 compiler、Runtime、R8 和 profile 版本，不能只写“K2 快了多少”。

### value class 的边界

JVM value class 在部分调用点可以避免 wrapper 分配，但 nullable、泛型、接口、反射和 ABI 边界都可能触发装箱。Composable 的 synthetic 参数不会自动保证业务参数始终 unbox，Compose stability 与参数比较也仍然生效。

评估 value class 时要同时看：

- 编译器报告中的 stability；
- 反编译或 bytecode viewer 中该调用点是否装箱；
- R8 后 DEX 是否保留 wrapper；
- allocation profiler 与 Macrobenchmark 是否出现可重复变化；
- `equals()` 或实例比较是否符合状态更新语义。

把 data class 换成 value class 不是通用的重组优化。它可能改善某些数据路径，也可能在泛型和 nullable 边界反复装箱。

### Kotlin metadata

Kotlin metadata 记录 Kotlin 声明信息，供 Kotlin 编译器、反射、R8 和其他工具读取。Compose Runtime 不会在每次重组时读取 metadata 决定参数稳定性；Compose compiler 已把 stability 与 skip 检查编码进生成代码和相关标记。

R8 会读取并维护 Kotlin metadata，因此 Kotlin 升级也要满足 D8/R8 兼容表。Kotlin 2.4 要求 R8 9.1.29；使用 AGP 时应优先使用其内置的兼容版本，只有工具链维护者有明确验证依据时才覆盖 R8。

## Compose compiler reports 与 metrics

报告适合回答编译期问题：

- 哪些 class 被推断为 stable、unstable 或 runtime/uncertain；
- 哪些 composable 是 restartable、skippable；
- 参数和默认值得到什么稳定性标记；
- 一个 module 的函数、参数、class 统计如何变化。

报告不能回答这些运行期问题：

- 某函数在一次交互中重组了几次；
- 哪个 State 写入触发了失效；
- 参数比较花了多少时间；
- 跳过后整帧是否按时 present；
- R8 后设备上执行了哪条优化路径。

### Kotlin 2.4 DSL

下面的 module 配置用于按需生成 release 报告，并采用 Kotlin 2.4 的复数 stability 文件属性：

```kotlin
val composeReportsEnabled = providers
    .gradleProperty("composeReports")
    .map(String::toBoolean)
    .orElse(false)

composeCompiler {
    if (composeReportsEnabled.get()) {
        reportsDestination =
            layout.buildDirectory.dir("compose_compiler/reports")
        metricsDestination =
            layout.buildDirectory.dir("compose_compiler/metrics")
    }

    stabilityConfigurationFiles.add(
        rootProject.layout.projectDirectory.file("stability_config.conf")
    )
}
```

`reportsDestination` 生成 class 与 composable 明细，`metricsDestination` 生成 module 统计。Kotlin Multiplatform 会按 target 与 compilation 建子目录。旧的单数 `stabilityConfigurationFile` 在 Kotlin 2.4 已是 error 级废弃项，应改用 `stabilityConfigurationFiles`。

下面的命令用于在需要审计时打开报告：

```bash
./gradlew :app:assembleRelease -PcomposeReports=true
```

日常 build 不传该 property，便不会产生报告 I/O。若工程通过 convention plugin 统一配置，应确认 property 在每个 Compose module 的配置阶段得到同样解释。

### 三类报告怎样读

| 文件 | 主要内容 | 合理用途 |
| --- | --- | --- |
| `*-classes.txt` | class 字段和整体 stability | 找出不稳定类型的来源 |
| `*-composables.txt` | 函数的 restartable/skippable、参数和默认值 | 审计调用边界与比较规则 |
| `*-composables.csv` | composable 明细的机器可读版本 | 做跨 commit diff |
| `module.json` 等 metrics | module 级计数 | 观察大范围趋势 |

`restartable` 表示 Runtime 可以从对应 group 重新执行；`skippable` 表示运行时具备跳过函数体的生成路径；`readonly` 等标记描述编译器对函数行为的判断。标签本身不提供现场调用次数。

Strong Skipping 成为基线后，大量 restartable 函数都会显示 skippable。审计重心应转向参数比较是否命中、State 读取位置、lambda capture 和函数体成本。追求所有函数都带某个标签，可能引入错误 stability 契约。

### 报告 diff 的正确单位

跨 commit 比较报告时，应保持 Kotlin、Compose plugin、Runtime 和 compiler option 不变。Kotlin 2.4 对非 final class 的默认 stability 与跨文件 `internal` 类型处理都可能改变报告文本；工具升级产生的全量 diff，不应直接记为业务性能退化。

一个可执行的审计规则可以是：

- 只对同工具链构建的 CSV 做阈值检查；
- 新增 unstable/runtime 参数时输出函数名单；
- `@Stable`、`@Immutable` 或 stability config 的新增必须人工审阅；
- compiler 升级单独建立基线 commit；
- 报告异常再结合 Layout Inspector、Perfetto 和 Macrobenchmark。

## 常见迁移故障

### “Compose Compiler requires Kotlin …”

新插件版本必须与 Kotlin 版本一致。version catalog 中若 Compose plugin 引用另一条版本 key，先统一到 2.4.10；随后检查 convention plugin 和 `pluginManagement` 是否又声明了一次。

### duplicate plugin option

搜索 `kotlinCompilerExtensionVersion`、`androidx.compose.compiler`、`plugin:androidx.compose.compiler.plugins.kotlin`、`enableStrongSkippingMode` 和旧 `freeCompilerArgs`。Compose Gradle plugin 已提供同一选项时，手写参数会造成重复。

### Strong Skipping 或 stability 配置属性报错

Kotlin 2.4 已禁止旧 Strong Skipping/Intrinsic Remember 开关，也禁止单数 `stabilityConfigurationFile`。删除已成为 baseline 的开关，把 stability 文件改为复数属性。

### K2 新诊断阻止编译

按报错所在层处理：

- Kotlin 语言诊断：修复初始化、可见性、重载或 expect/actual 规则；
- Compose 诊断：检查 `@Composable` 调用上下文、函数类型、target 和默认参数；
- plugin crash：制作最小复现，记录 Kotlin、Compose plugin 与依赖版本；
- D8/R8 报错：核对 AGP/R8 对 Kotlin 2.4 class file 与 metadata 的支持。

用 suppression 或显式 cast 遮住 K2 诊断，可能把类型错误推迟到运行期。若旧代码依赖 K1 的解析差异，应把意图写进类型和声明中。

### kapt 在 AGP 9 下失败

这通常来自 built-in Kotlin 与旧 kapt plugin 冲突。优先迁移 KSP；短期无法迁移时使用 `com.android.legacy-kapt`，版本与 AGP 对齐。

### 无法回退到 K1

Kotlin 2.4 不接受 `languageVersion = 1.9`。保留迁移前可构建分支和 dependency lock，回退时一起恢复 Kotlin、Compose compiler、AGP 兼容配置及为 K2 修改的源码。分散回退单个 artifact 会产生未验证的组合。

## R8、Baseline Profile 与 Live Edit

### R8

R8 位于 Kotlin/JVM 和 Compose compiler 之后。它可以 inline、删除不可达分支、重命名和重排 class，并将 JVM bytecode 转为最终 DEX 优化结果。R8 不参与 K2 frontend 的类型推断，也不会改写 Compose 的状态语义。

Kotlin 2.4 跨文件 `internal` stability 生成的双路径，可以由 full-app optimization 删除无用分支。这是 Kotlin 2.4 文档明确说明的协作点。除此以外，不宜把一般的 shrinking 收益称作“K2 与 R8 专用协同”。

Kotlin 2.4 的 Compose Gradle Plugin 还提供 `includeComposeMappingFile`，用于让优化器产出的 mapping 包含 Compose group key 相关信息，帮助反混淆 minified Compose stack trace。它是诊断映射能力，不会减少重组。

### Baseline Profile

Baseline Profile 告诉 ART 哪些 class 和 method 路径应在安装期或运行前优先编译。Compose compiler 升级可能改变 synthetic 方法、描述符、inline 结果和代码布局，旧 profile 的覆盖率可能变化。

工具链升级后应重新运行关键用户旅程生成 profile，再用 release APK 在物理设备上做 Macrobenchmark。比较时保留 `CompilationMode.None`、`Partial` 等对照，确认收益来自 profile 覆盖，不能按“K2 产物天然更适合 Baseline Profile”下结论。

### Live Edit

Live Edit 面向开发迭代，只支持一部分函数体修改。它要求 debuggable process，修改后的 class 可能带性能开销，也不会执行 build 文件定义的所有 bytecode manipulation。方法签名、增删方法和 class hierarchy 变化仍需重新 Run。

因此，Live Edit 能否工作属于 IDE、AGP、Compose Runtime、设备 API 和变更形态的兼容问题。评估 K2 或 Compose compiler 的运行时性能时，应关闭 Live Edit，重新安装干净的 release 构建。

## Android 17 运行路径中的位置

Compose compiler、Compose Runtime 和 Android platform 属于三条发布线。`android-17.0.0_r1` 不包含 Kotlin 2.4.10 Compose compiler 的实现，platform tag 也不能证明某个 Strong Skipping 行为。

普通 Compose 页面仍属于标准 HWUI App Window 路径。一次状态变化大致经过：

1. Compose Runtime 记录 Snapshot 变化并安排 composition；
2. 主线程在帧节奏内执行需要的 recomposition、measure、layout 或 draw；
3. Compose UI 更新底层绘制结构，进入 ViewRootImpl/HWUI；
4. UI 线程经 `ThreadedRenderer` / `HardwareRenderer` 同步到 RenderThread；
5. RenderThread 生成 App Window buffer；
6. BLASTBufferQueue、SurfaceFlinger、HWC 和显示设备完成合成与 present。

Compiler 的 skip/restart 结果主要影响前两步需要执行多少应用代码。它不会绕过 RenderThread、BufferQueue、SurfaceFlinger 或 HWC，也不能修复 GPU、buffer backpressure 和 display 侧超时。分析帧问题时，仍应按 FrameTimeline、UI thread、RenderThread、buffer transaction 和 present fence 建立证据。

`android17-6.18-2026-06_r6` 负责设备上的线程调度、futex、频率和驱动等待等机制。它会影响生成代码在设备上的调度结果，但不决定 composable stability、FIR 解析或 compiler report。构建机运行 Linux 时也不能把 host 调度波动解释成 Compose compiler 语义变化。

## Compose Multiplatform、Wasm 与 Android Native 的边界

Compose compiler 位于 Kotlin 仓库后，可以面向 JVM、Native、JS 和 Wasm target 复用部分分析与 lowering。Kotlin 2.4.10 源码中也能看到 JS/Wasm 的专用 composable lambda lowering。

这些 target 的存在不会让 Android Jetpack Compose 自动改用 NDK 或 native rendering。Android application module 仍走 Kotlin/JVM → bytecode → D8/R8 → DEX → ART，界面仍由 Compose UI、Android framework 与 HWUI 接到系统显示链。

评估 Kotlin/Wasm 或 Compose Multiplatform 时，应为对应 target 单独建立编译、体积和运行时指标。把 Wasm 的增量编译改进外推到 Android JVM module，或把 Kotlin/Native codegen 外推到 Android HWUI，都缺少相同执行路径。

## 迁移检查表

### 配置

- [ ] API 37 使用 AGP 9.1.1 或更高的兼容版本，当前基线固定为 9.1.1；
- [ ] Gradle 9.3.1、JDK 17 与 AGP 9.1.1 对齐；
- [ ] Kotlin 与 `org.jetbrains.kotlin.plugin.compose` 同为 2.4.10；
- [ ] 每个 Compose module 都应用 Compose compiler plugin；
- [ ] AGP 9 Android module 已删除 `org.jetbrains.kotlin.android`；
- [ ] 旧 `kotlinCompilerExtensionVersion`、compiler artifact 和 `-P plugin:` 参数已移除；
- [ ] kapt 已迁往 KSP，或临时改为同 AGP 版本的 legacy kapt；
- [ ] `stabilityConfigurationFiles` 使用复数属性；
- [ ] 已删除 Kotlin 2.4 中报错的 Strong Skipping/Intrinsic Remember 开关。

### 编译验证

- [ ] clean release、no-change、non-ABI 与 ABI incremental 分开测；
- [ ] benchmark 记录 daemon、cache、worker、JDK 和机器状态；
- [ ] compiler reports 在单独场景开启；
- [ ] K2 新诊断按语言、Compose plugin、D8/R8 分层处理；
- [ ] migration branch 保留完整可构建的回退点。

### 运行时验证

- [ ] 使用 minified release APK；
- [ ] 重新生成并验证 Baseline Profile；
- [ ] Macrobenchmark 固定设备、系统版本和测试旅程；
- [ ] Layout Inspector 只用于定位重组与跳过；
- [ ] Perfetto 对齐 Compose、主线程、RenderThread 与 FrameTimeline；
- [ ] Strong Skipping 的 unstable 参数按实例相等性检查；
- [ ] value class 结论包含装箱、DEX、allocation 和 benchmark 证据；
- [ ] Live Edit 不参与性能样本。

## 结论

K2 是 Kotlin frontend 架构更新，Compose compiler 是建立在现行 Kotlin compiler plugin API 上的 Compose 语义检查与 IR 变换，Compose Runtime 再执行生成的 group、remember、restart 和 skip 逻辑。三者相互关联，却不能互相替代。

Android 17 基线下，可靠的迁移组合是 AGP 9.1.1、Gradle 9.3.1、JDK 17、Kotlin/Compose plugin 2.4.10 和 `compileSdk = 37`。Compose BOM 继续管理 Runtime/UI libraries，不能拿它给 compiler 定版。

性能结论需要拆开验证：构建速度看 Gradle 场景基准，stability 和 skippability 看 compiler reports，现场重组看 Layout Inspector/trace，用户可感知性能看 release Macrobenchmark 与 Perfetto。K2 或 Strong Skipping 的版本说明只能提供候选原因，工程自己的可复现实验才决定是否保留某项改动。
