# Android 17 内存泄漏监控框架实战

> **Draft-polish 边界（2026-07-26）**：本章当前只有一段已标注的 AOSP 源码调研材料，覆盖 Android 17（`android-17.0.0_r1`）中的 HPROF dump 管线；其余应用侧监控框架、报告格式与集成 API 仍缺少可路由材料。本文先收紧版本边界、移除“Android 17 内置应用侧泄漏监控框架”的未证实表述，并把示例定位为应用自建/第三方工具设计思路，暂不晋升 ready-for-review。

## 内存泄漏监控原理

Android 应用运行时常见的问题之一是内存泄漏，尤其是长期运行的应用中，生命周期对象、消息队列、静态缓存或未关闭资源都可能导致对象在业务语义上已经无用，却仍被 GC Root 引用，从而造成内存持续增长、频繁 GC，最终触发性能下降或 OOM。

### 什么是内存泄漏

在 Android 应用语境中，内存泄漏通常不是“虚拟机无法识别对象”，而是“对象虽然仍可达，但业务生命周期已经结束”。因此，泄漏判定需要结合对象生命周期状态与引用链：

- Activity/Fragment 被销毁后仍有强引用存在；
- 静态变量、单例或全局缓存持有 Activity/Fragment；
- Handler、Runnable、Timer、协程或线程任务间接持有页面对象；
- 非静态内部类隐式持有外部类引用；
- Cursor、FileDescriptor、Bitmap、注册监听器等资源未及时释放或反注册。

### 泄漏判定边界

判断对象是否泄漏需要基于开发者视角，而不能只看虚拟机层面。只要对象与 GC Root 有引用路径，运行时就会认为它仍然可达；但如果该对象对应的 Activity、Fragment 或业务资源已经退出生命周期，仍可达就可能是泄漏信号。

本章后续评审需要补充并验证以下边界：

- Activity 可用公开生命周期信号（如 `isFinishing()`、`isDestroyed()`）辅助判断；直接依赖私有字段（如 `mFinished`、`mDestroyed`）只能作为源码/调试分析依据，不应作为生产 API。
- Fragment 的内部状态字段属于实现细节；应用侧工具应优先使用 AndroidX Fragment 生命周期回调或工具库提供的对象观察机制，而不是直接访问私有字段。
- “发现引用链”通常依赖 HPROF dump 后离线/异步解析，不能等同于在主线程上即时遍历对象图。

## Android 17 HPROF dump 管线

### 引用链检测技术

要定位疑似泄漏对象，常见流程是：

1. **定义可能泄漏的对象集合**：以已结束生命周期的 Activity/Fragment、View、Context 包装对象或资源句柄为观察对象；
2. **触发 GC 与堆转储**：在合适时机采集 `.hprof`，避免频繁 dump 影响线上性能；
3. **解析引用链**：通过 HPROF 解析器确认对象是否仍可从 GC Root 到达，并输出最短/关键引用路径；
4. **结合业务语义判断**：引用链可达只是必要线索，最终仍需结合生命周期和保留原因判断是否为真实泄漏。

Android 平台公开入口仍可通过应用显式调用触发 HPROF dump：

```java
// 获取内存快照。注意：dump 成本较高，应在调试、灰度或受控诊断场景中使用。
Debug.dumpHprofData(path);
```

### HPROF dump 管线源码级注解（android-17.0.0_r1）

> 以下结论来自对 `external/perfetto/src/profiling/memory/java_hprof_producer.{h,cc}`、`art/runtime/hprof/hprof.cc`、`art/runtime/signal_catcher.cc` 的源码阅读。

**1. Android 17 已移除 `kill -10 <pid>` 触发 hprof 的旧路径。**
`art/runtime/signal_catcher.cc::HandleSigUsr1()` 现行实现：

```cpp
void SignalCatcher::HandleSigUsr1() {
  LOG(INFO) << "SIGUSR1 forcing GC (no HPROF) and profile save";
  Runtime::Current()->GetHeap()->CollectGarbage(false);
  ProfileSaver::ForceProcessProfiles();
}
```

源码注释 "no HPROF" 是显式语义变更。Android 17 上 hprof dump 入口只保留以下已知路径：

- **应用显式触发**：`android.os.Debug.dumpHprofData(String path)` → `art/runtime/hprof/hprof.cc::Hprof::Dump()`；
- **Perfetto 触发**：trace 配置 `data_sources.name = "android.java_hprof"`，由 `java_hprof_producer.cc` 经 `__SIGRTMIN + 6` 实时信号投递目标进程。

**2. Perfetto 数据源信号与 native heapprofd 隔离。**

```cpp
// java_hprof_producer.cc
constexpr int kJavaHeapprofdSignal = __SIGRTMIN + 6;
constexpr const char* kJavaHprofDataSource = "android.java_hprof";
```

与 `heapprofd_producer.cc` 使用的 `__SIGRTMIN + 4` 物理通道分离，避免与 native 采样事件竞争 `SignalCatcher` 的 `SignalSet`。

**3. hprof 文件采用「两遍式写入」+「128 对象 / 4KB 分段」。**

```cpp
// art/runtime/hprof/hprof.cc
static constexpr size_t kMaxObjectsPerSegment = 128;
static constexpr size_t kMaxBytesPerSegment   = 4096;

void Hprof::Dump() {
  // 第一遍：仅累加 length，用于 max_length 预算
  ProcessHeap(false);
  overall_size = count_output.SumLength();
  max_length   = count_output.MaxLength();
  // 第二遍：真正写入 / ddms 流
  ProcessHeap(true);
}

void CheckHeapSegmentConstraints() {
  if (objects_in_segment_ >= kMaxObjectsPerSegment ||
      output_->Length()    >= kMaxBytesPerSegment) {
    StartNewHeapDumpSegment();
  }
}
```

第二遍输出 `DCHECK_LE(file_output.SumLength(), overall_size)`，约束见 b/23521263——并发分配可能让第二遍略少，但绝不能多。

**4. 关键 HPROF tag（与 `HprofRecordTag` 一一对应）。**

| 解析器枚举 | 源码十六进制 | 含义 |
|---|---|---|
| `ROOT_JNI_GLOBAL` | `0x01` | JNI Global 引用根 |
| `ROOT_JNI_LOCAL` | `0x02` | JNI Local 引用根 |
| `ROOT_JAVA_FRAME` | `0x03` | Java 栈帧根 |
| `ROOT_NATIVE_STACK` | `0x04` | Native 栈根 |
| `ROOT_STICKY_CLASS` | `0x05` | Sticky Class 根 |
| `ROOT_THREAD_BLOCK` | `0x06` | Thread Block 根 |
| `HEAP_DUMP_END` | `0x2C` | dump 边界（Android 私有，段流式解析必备） |
| `ART_CLOCK_MONOTONIC` | `0xA0` | 基于 CLOCK_MONOTONIC 的时间锚点 |

**5. 大内存设备性能与风险提示。**

- `DumpToDdmsDirect` 模式下每段立刻 flush（依赖 `kDirectStream=true`）；如果厂商误配为 buffered（`kDirectStream=false`），单次 dump 会持有 `overall_size` 完整 buffer，超大内存设备（≥ 12GB）OOM 风险显著。
- Perfetto `connection_backoff_ms_` 封顶 30s，traced 重启期间 producer 最长静默 30s——对 `dump_interval_ms` 高频配置尤其敏感。
- 开启 `IsAllocTrackingEnabled()` 时，`PopulateAllocationTrackingTraces()` 会显著放大第一遍成本。

## 应用侧监控框架设计（待补材料）

本节只保留应用侧设计原则，不再声称 Android 17 提供名为 `MemoryMonitor`、`HeapAnalyzer`、`LeakDetector` 或 `MemoryProtoLogger` 的统一应用 API。若后续要写成实战章节，需要补充 LeakCanary/Shark、AndroidX lifecycle、Perfetto java_hprof 配置或项目内工具源码等可验证材料。

### 基础监控思路

一个保守的应用侧泄漏监控模块通常包含：

1. **对象观察**：在 Activity/Fragment/View 生命周期结束时，把对象注册到观察集合；
2. **延迟确认**：等待一段时间并触发/等待 GC，减少误报；
3. **弱引用校验**：若弱引用仍未清空，则标记为 retained object；
4. **受控 dump**：仅在调试、灰度或采样策略允许时转储 HPROF；
5. **离线分析**：解析最短引用链，过滤系统/已知库保留路径，再输出报告。

### Activity 泄漏观察示例（概念代码）

```java
public final class ActivityRetainedWatcher implements Application.ActivityLifecycleCallbacks {
    private final ReferenceQueue<Activity> queue = new ReferenceQueue<>();
    private final List<WeakReference<Activity>> destroyedActivities = new ArrayList<>();

    @Override
    public void onActivityDestroyed(Activity activity) {
        destroyedActivities.add(new WeakReference<>(activity, queue));
        // 实际实现应延迟检查，并避免在主线程执行昂贵分析。
    }

    public int retainedAfterGc() {
        System.gc();
        destroyedActivities.removeIf(ref -> ref.get() == null);
        return destroyedActivities.size();
    }

    // 其他 ActivityLifecycleCallbacks 方法省略。
}
```

> 说明：以上为概念代码，只表达“生命周期结束后以弱引用观察对象是否仍被保留”的模式；它不能替代成熟工具的引用链分析，也不能证明 retained object 一定是业务泄漏。

### Fragment 观察边界

Fragment 泄漏监控应避免直接读取内部字段。更安全的方向是结合 Fragment 生命周期回调、ViewLifecycleOwner、`onDestroyView()` / `onDestroy()` 边界与工具库的对象观察能力：

- Fragment 的 View 比 Fragment 本体更容易因 Adapter、Binding、监听器未释放而泄漏；
- `onDestroyView()` 后仍持有 ViewBinding 或 View 树通常是重点排查对象；
- 如果需要引用链，应把 HPROF 解析放到后台或离线流程，避免阻塞交互线程。

## 监控结果分析

### 报告字段建议（非平台固定格式）

内存泄漏报告格式应明确标注为工具输出，而不是 Android 17 平台固定格式。一个最小可用报告通常包含：

```json
{
  "timestamp": "2026-06-25T11:04:00Z",
  "process": "com.example.app",
  "retainedObjects": [
    {
      "type": "Activity",
      "className": "com.example.MainActivity",
      "state": "destroyed",
      "referenceChainAvailable": true
    }
  ],
  "heapDump": {
    "trigger": "manual-or-sampled",
    "androidBaseline": "android-17.0.0_r1"
  }
}
```

### 性能优化建议

基于泄漏报告，可以优先检查：

1. **静态引用与单例**：避免全局对象持有 Activity/Fragment/View；
2. **消息与异步任务**：在生命周期结束时取消 Handler、Runnable、Timer、Coroutine、Rx 订阅或回调；
3. **资源管理**：确保 Cursor、FileDescriptor、Closeable、传感器/广播/监听器及时关闭或反注册；
4. **大对象保留**：Bitmap、缓存和 native 分配需要有明确所有权与释放策略；
5. **采集成本**：HPROF dump 成本高，应避免在线上高频触发。

## 实际案例分析（需源码/工具材料补强）

### 案例一：静态变量持有 Activity

```java
// 问题模式：全局静态字段持有页面对象。
public final class ActivityRegistry {
    public static Activity currentActivity;
}

// 改进方向：只保存 Application Context，或保存弱引用并允许为空。
public final class ActivityRegistry {
    private WeakReference<Activity> currentActivity = new WeakReference<>(null);

    public void update(Activity activity) {
        currentActivity = new WeakReference<>(activity);
    }
}
```

### 案例二：Handler/Runnable 间接保留页面

```java
public class MainActivity extends AppCompatActivity {
    private final Handler handler = new Handler(Looper.getMainLooper());
    private final Runnable refreshTask = new Runnable() {
        @Override
        public void run() {
            // 处理 UI 刷新。
        }
    };

    @Override
    protected void onDestroy() {
        handler.removeCallbacksAndMessages(null);
        super.onDestroy();
    }
}
```

> 说明：上例只展示生命周期清理方向。是否需要静态内部类、弱引用或更彻底的任务取消，取决于实际 Runnable/Message 是否捕获 Activity、是否跨生命周期执行以及业务所有权。

## 总结

Android 17 相关的可靠增量在于 HPROF dump 管线与 Perfetto `android.java_hprof` 触发路径的源码边界，而不是一个可直接调用的系统级“内存泄漏监控框架”。应用侧泄漏监控仍应围绕生命周期对象观察、弱引用确认、受控 HPROF dump 与引用链分析来设计。

主要要点：

- 泄漏判断必须结合业务生命周期，不能只看对象是否可达；
- Activity、Fragment/View、异步任务和未释放资源是重点观察对象；
- Android 17 上旧的 `kill -10 <pid>` HPROF 路径不再成立，应使用 `Debug.dumpHprofData()` 或 Perfetto `android.java_hprof`；
- HPROF dump 成本高，线上使用必须采样、限频并保护隐私；
- 本章仍需补充应用侧工具材料后才能进入 ready-for-review。
