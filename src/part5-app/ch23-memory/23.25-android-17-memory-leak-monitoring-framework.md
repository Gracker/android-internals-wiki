# Android 17 内存泄漏监控框架实战

## 内存泄漏监控原理

Android 应用运行时最常见的问题之一就是内存泄漏，尤其是长期运行的应用中，内存泄漏会导致性能下降甚至应用崩溃。在 Android 17 中，内存监控机制进一步优化，让我们来深入了解其实现原理。

### 什么是内存泄漏

内存泄漏是指程序在不再使用某块内存时，没有将其释放，导致内存资源仍然被占用。随着时间推移，这些未释放的内存会累积，最终可能导致内存耗尽。

在 Android 中，常见的内存泄漏场景包括：

- Activity/Fragment 被销毁但仍有引用存在
- 静态变量持有 Activity/Fragment 的引用
- Handler 中的消息持有 Activity/Fragment 的引用
- 非静态内部类持有外部类的引用
- 资源未及时关闭（Cursor、FileDescriptor 等）

### 内存泄漏的判定依据

判断对象是否泄漏需要基于开发者视角，而不能只看虚拟机层面。虽然从虚拟机角度看，只要对象跟 GC Root 有联系就被认为是"有用的"，但实际上这些对象在业务逻辑中已经不再需要使用。

在 Android 17 中，内存泄漏的判定规则更加明确：

- **Activity 判定规则**：Activity 对象的 `mFinished` 或 `mDestroyed` 值为 true，但还能在 GC Root 引用链中被找到
- **Fragment 判定规则**：`mFragmentManager` 为空且 `mCalled` 为 true，同时能在 GC Root 引用链中被找到

## Android 17 内存监控架构

### 监控机制的核心组件

Android 17 的内存监控主要基于以下组件：

1. **MemoryProtoLogger**：负责内存事件的记录和转发
2. **HeapAnalyzer**：负责内存快照分析和引用链查找
3. **MemoryMonitor**：负责监控内存使用情况和阈值判断
4. **LeakDetector**：专门负责检测内存泄漏

### 引用链检测技术

要找到内存泄漏对象，需要两个关键步骤：

1. **定义可能泄漏的对象**：以 Activity/Fragment 作为切入点
2. **查找引用链**：通过 `.hprof` 文件解析，确认对象是否与 GC Root 存在引用路径

在 Android 17 中，`.hprof` 文件解析效率显著提升：

```java
// 获取内存快照
Debug.dumpHprofData(path);

// 分析堆转储文件

    setOf(

        HprofRecordTag.ROOT_STICKY_CLASS,
        HprofRecordTag.ROOT_THREAD_BLOCK,
        HprofRecordTag.ROOT_THREAD_OBJECT
    )
);
```

### HPROF dump 管线源码级注解（android-17.0.0_r1）

> 以下结论来自对 `external/perfetto/src/profiling/memory/java_hprof_producer.{h,cc}`、`art/runtime/hprof/hprof.cc`、`art/runtime/signal_catcher.cc` 的源码阅读。

**1. Android 17 已移除 `kill -10 <pid>` 触发 hprof 的旧路径。**
`art/runtime/signal_catcher.cc::HandleSigUsr1()` 现行实现：

```cpp
void SignalCatcher::HandleSigUsr1() {
  LOG(INFO) << "SIGUSR1 forcing GC (no HPROF) and profile save";
  Runtime::Current()->GetHeap()->CollectGarbage(false);
  ProfileSaver::ForceProcessProfiles();
}
```

源码注释 "no HPROF" 是显式语义变更。Android 17 上 hprof dump 入口只剩两条：
- **应用显式触发**：`android.os.Debug.dumpHprofData(String path)` → `art/runtime/hprof/hprof.cc::Hprof::Dump()`；
- **Perfetto 触发**：trace 配置 `data_sources.name = "android.java_hprof"`，由 `java_hprof_producer.cc` 经 `__SIGRTMIN + 6` 实时信号投递目标进程。

**2. Perfetto 数据源信号与 native heapprofd 隔离。**
```cpp
// java_hprof_producer.cc
constexpr int kJavaHeapprofdSignal = __SIGRTMIN + 6;
constexpr const char* kJavaHprofDataSource = "android.java_hprof";
```
与 `heapprofd_producer.cc` 使用的 `__SIGRTMIN + 4` 物理通道分离，避免与 native 采样事件竞争 `SignalCatcher` 的 `SignalSet`。

**3. hprof 文件采用「两遍式写入」+「128 对象 / 4KB 分段」。**
```cpp
// art/runtime/hprof/hprof.cc
static constexpr size_t kMaxObjectsPerSegment = 128;
static constexpr size_t kMaxBytesPerSegment   = 4096;

void Hprof::Dump() {
  // 第一遍：仅累加 length，用于 max_length 预算
  ProcessHeap(false);
  overall_size = count_output.SumLength();
  max_length   = count_output.MaxLength();
  // 第二遍：真正写入 / ddms 流
  ProcessHeap(true);
}

void CheckHeapSegmentConstraints() {
  if (objects_in_segment_ >= kMaxObjectsPerSegment ||
      output_->Length()    >= kMaxBytesPerSegment) {
    StartNewHeapDumpSegment();
  }
}
```

第二遍输出 `DCHECK_LE(file_output.SumLength(), overall_size)`，约束见 b/23521263——并发分配可能让第二遍略少，但绝不能多。

**4. 关键 HPROF tag（与 `HprofRecordTag` 一一对应）。**
| 解析器枚举 | 源码十六进制 | 含义 |
|---|---|---|
| `ROOT_JNI_GLOBAL`   | `0x01` | JNI Global 引用根 |
| `ROOT_JNI_LOCAL`    | `0x02` | JNI Local 引用根 |
| `ROOT_JAVA_FRAME`   | `0x03` | Java 栈帧根 |
| `ROOT_NATIVE_STACK` | `0x04` | Native 栈根 |
| `ROOT_STICKY_CLASS` | `0x05` | Sticky Class 根 |
| `ROOT_THREAD_BLOCK` | `0x06` | Thread Block 根 |
| `HEAP_DUMP_END`     | `0x2C` | dump 边界（Android 私有，段流式解析必备） |
| `ART_CLOCK_MONOTONIC`| `0xA0` | 基于 CLOCK_MONOTONIC 的时间锚点 |

**5. 大内存设备性能与风险提示。**
- `DumpToDdmsDirect` 模式下每段立刻 flush（依赖 `kDirectStream=true`）；如果厂商误配为 buffered（`kDirectStream=false`），单次 dump 会持有 `overall_size` 完整 buffer，超大内存设备（≥ 12GB）OOM 风险显著。
- Perfetto `connection_backoff_ms_` 封顶 30s，traced 重启期间 producer 最长静默 30s——对 `dump_interval_ms` 高频配置尤其敏感。
- 开启 `IsAllocTrackingEnabled()` 时，`PopulateAllocationTrackingTraces()` 会显著放大第一遍成本。

## 监控框架实战

### 基础监控设置

在 Android 17 中，内存监控可以通过以下方式设置：

```java
// 启用内存监控
MemoryMonitor memoryMonitor = new MemoryMonitor.Builder()
    .setContext(getApplicationContext())
    .setThreshold(1024 * 1024 * 10) // 10MB 阈值
    .setCheckInterval(1000) // 1秒检查一次
    .build();

memoryMonitor.start();
```

### Activity 内存泄漏监控

Activity 是内存泄漏检测的重点对象：

```java
public class MemoryLeakActivityMonitor {
    private final WeakReference<Activity> activityRef;
    
    public MemoryLeakActivityMonitor(Activity activity) {
        this.activityRef = new WeakReference<>(activity);
    }
    
    public boolean checkLeak() {
        Activity activity = activityRef.get();
        if (activity == null) {
            return false;
        }
        
        // 检查 Activity 是否已销毁
        boolean isDestroyed = activity.isDestroyed();
        boolean isFinished = activity.isFinishing();
        
        // 如果已销毁但仍能找到引用链，则判定为泄漏
        if (isDestroyed || isFinished) {
            return findReferenceChain(activity);
        }
        
        return false;
    }
    
    private boolean findReferenceChain(Activity activity) {
        // 使用 HeapAnalyzer 查找引用链
        HeapAnalyzer heapAnalyzer = new HeapAnalyzer();
        List<GcRoot> gcRoots = heapAnalyzer.findGcRoots(activity);
        
        return gcRoots != null && !gcRoots.isEmpty();
    }
}
```

### Fragment 内存泄漏监控

Fragment 的监控需要特别注意其生命周期状态：

```java
public class MemoryLeakFragmentMonitor {
    private final WeakReference<Fragment> fragmentRef;
    
    public MemoryLeakFragmentMonitor(Fragment fragment) {
        this.fragmentRef = new WeakReference<>(fragment);
    }
    
    public boolean checkLeak() {
        Fragment fragment = fragmentRef.get();
        if (fragment == null) {
            return false;
        }
        
        // Fragment 泄漏判定：FragmentManager 为空且 Called 为 true
        boolean isLeaked = (fragment.getActivity() == null) && 
                          (fragment.mCalled == true);
        
        return isLeaked && findReferenceChain(fragment);
    }
}
```

### 性能优化建议

基于监控结果，可以提出针对性的优化建议：

1. **静态引用优化**：避免静态变量持有 Activity/Fragment 的引用
2. **Handler 优化**：使用 WeakReference 包装 Handler 中的消息
3. **资源管理**：确保 Cursor、FileDescriptor 等资源及时关闭
4. **内存分配**：大对象分配考虑使用 Native 内存

## 实际案例分析

### 案例一：静态变量导致泄漏

```java
// 问题代码
public class MyApp extends Application {
    public static MainActivity currentActivity;
    
    @Override
    public void onCreate() {
        super.onCreate();
        currentActivity = new MainActivity();
    }
}

// 解决方案
public class MyApp extends Application {
    public WeakReference<MainActivity> currentActivity;
    
    @Override
    public void onCreate() {
        super.onCreate();
        currentActivity = new WeakReference<>(null);
    }
}
```

### 案例二：Handler 消息泄漏

```java
// 问题代码
public class MainActivity extends AppCompatActivity {
    private final Handler handler = new Handler() {
        @Override
        public void handleMessage(Message msg) {
            // 处理消息
        }
    };
}

// 解决方案
public class MainActivity extends AppCompatActivity {
    private final Handler handler = new Handler(Looper.getMainLooper()) {
        @Override
        public void handleMessage(Message msg) {
            // 处理消息
        }
    };
    
    @Override
    protected void onDestroy() {
        super.onDestroy();
        handler.removeCallbacksAndMessages(null);
    }
}
```

## 监控工具集成

### 集成到现有项目

```gradle
// build.gradle 添加依赖
dependencies {
    implementation 'androidx.memory:memory:1.0.0'
    implementation 'com.squareup.leakcanary:leakcanary-android:2.7'
}
```

### 自定义监控模块

```java
public class CustomMemoryMonitor {
    private static final String TAG = "MemoryMonitor";
    private MemoryMonitor memoryMonitor;
    
    public void init(Context context) {
        memoryMonitor = new MemoryMonitor.Builder()
            .setContext(context)
            .setThreshold(10 * 1024 * 1024) // 10MB
            .setCheckInterval(2000) // 2秒
            .setLeakDetector(new CustomLeakDetector())
            .build();
            
        memoryMonitor.start();
    }
    
    public void stop() {
        if (memoryMonitor != null) {
            memoryMonitor.stop();
        }
    }
}
```

## 总结

Android 17 的内存监控框架提供了更强大的功能和更精准的检测能力。通过合理的监控配置和优化实践，可以有效减少内存泄漏问题，提升应用的稳定性和性能。

主要要点：
- 基于开发者视角判断内存泄漏，不能只看虚拟机层面
- Activity 和 Fragment 是监控的重点对象
- 使用 .hprof 文件解析技术查找引用链
- 及时发现并修复内存泄漏问题
