# 23.1 内存泄漏检测与治理

## 内存泄漏本质与危害

作为应用层开发者，我们日常最能接触到的，其实就是堆内存分配时发生的 OOM。比如当前堆内存不足时，我们再去分配一个较大的内存，就很有可能超过虚拟机设立的限制（256M/512M），此时就会走到 Heap 里面的 ThrowOutOfMemoryError。

在 Android 程序中，**内存泄漏**是指程序在不再使用某块内存时，没有将其释放，导致内存资源仍然被占用；随着时间的推移，这些未释放的内存可以累积起来，最终导致内存耗尽。

### 内存泄漏判定标准

这里引出了一个概念，**GC Root**（GC 根），它是指那些被虚拟机直接引用的对象，是垃圾回收的起点。判断一个对象是否泄漏，关键在于：

1. **对象已不再使用**：从业务逻辑角度，该对象已完成其生命周期
2. **存在 GC Root 引用链**：从虚拟机角度，仍有可达路径

对于 Activity 和 Fragment，通用判定规则如下：

- **Activity 销毁判定**：当 `mFinished` 或 `mDestroyed` 值为 true，却还能够在 GC Root 引用链中被找到
- **Fragment 销毁判定**：`mFragmentManager` 为空且 `mCalled` 为 true，且仍能在 GC Root 引用链中被找到

### 常见内存泄漏场景

#### 1. 静态变量持有引用
```java
// 错误示例：静态变量持有 Context 引用
public class Singleton {
    private static Context mContext;
    
    public static void init(Context context) {
        mContext = context; // 可能导致泄漏
    }
}
```

#### 2. 非静态内部类持有外部类引用
```java
// 错误示例：非静态内部类隐式持有外部类引用
public class MainActivity extends Activity {
    private class MyHandler extends Handler {
        @Override
        public void handleMessage(Message msg) {
            // 隐式持有 MainActivity 引用
        }
    }
    
    private MyHandler mHandler = new MyHandler();
}
```

#### 3. 匿名 Runnable/TimerTask
```java
// 错误示例：匿名 Runnable 持有 Activity 引用
new Handler().postDelayed(new Runnable() {
    @Override
    public void run() {
        // 隐式持有 Activity 引用
    }
}, 10000);
```

#### 4. 未关闭的资源
```java
// 错误示例：未关闭 Cursor
public Cursor getData() {
    SQLiteDatabase db = dbHelper.getReadableDatabase();
    Cursor cursor = db.query("table", null, null, null, null, null, null);
    return cursor; // 调用者不关闭会导致泄漏
}
```

## 内存泄漏检测技术栈

### 1. LeakCanary 原理与实践

LeakCanary 是 Square 公司开源的内存泄漏检测库，其核心原理是：

#### 监控对象生命周期
```java
public class RefWatcher {
    public void watch(Object watchedReference, String referenceName) {
        // 1. 创建弱引用
        final WeakReference<Object> weakReference = new WeakReference<>(watchedReference);
        
        // 2. 延迟检查
        backgroundHandler.postDelayed(new Runnable() {
            @Override
            public void run() {
                checkRetainedObjects(weakReference, referenceName);
            }
        }, delayMillis);
    }
}
```

#### GC 前后对比检测
```java
private void checkRetainedObjects(WeakReference<Object> weakReference, String referenceName) {
    // 1. 执行 GC
    GCUtil.runGc();
    
    // 2. 检查是否仍被引用
    if (weakReference.get() != null) {
        // 3. dump heap 分析
        File heapDumpFile = dumpHeap();
        
        // 4. 分析泄漏路径
        AnalysisResult result = analyzeHeap(heapDumpFile);
        
        // 5. 发送通知
        if (result.retainedObjectCount > 0) {
            onHeapDumpAnalysis(heapDumpFile, result);
        }
    }
}
```

### 2. KOOM 框架对比

KOOM（Keep Object Orthogonal）是滴滴开源的内存监控框架，相比 LeakCanary 有以下优势：

#### 特点对比
| 特性 | LeakCanary | KOOM |
|------|------------|------|
| 检测方式 | 主动触发 dump | 自动监控 + 阈值触发 |
| 性能影响 | 高（heap dump） | 低（基于计数器） |
| 适用场景 | 开发调试 | 线上监控 |
| 检测精度 | 高（路径分析） | 中（统计推断） |

#### KOOM 核心机制
```java
// 基于计数器的监控
public class MemoryClassMonitor {
    private final AtomicInteger mMemoryClassCounter = new AtomicInteger(0);
    
    public void onMemoryClassChanged(int oldMemoryClass, int newMemoryClass) {
        if (newMemoryClass < oldMemoryClass) {
            // 内存减少，可能发生泄漏
            mMemoryClassCounter.incrementAndGet();
        }
    }
}
```

## Android 17 内存泄漏检测新特性

### 1. ApplicationExitInfo 增强

Android 17 中 `ApplicationExitInfo` 提供了更详细的内存退出信息：

```java
public class MemoryLeakDetector {
    public void analyzeExitInfo(ApplicationExitInfo exitInfo) {
        if (exitInfo.getReason() == ApplicationExitInfo.REASON_LOW_MEMORY) {
            // 获取详细的内存使用信息
            long privateMemory = exitInfo.getPrivateDirty();
            long sharedMemory = exitInfo.getSharedDirty();
            
            // 分析是否为泄漏导致
            if (isMemoryLeakPattern(privateMemory, sharedMemory)) {
                reportMemoryLeak(exitInfo);
            }
        }
    }
}
```

## 实战：自定义内存泄漏监控框架

### 1. 检测框架设计

```java
public class LeakMonitor {
    private final Map<String, WeakReference<Object>> mWatchedObjects = new ConcurrentHashMap<>();
    private final ScheduledExecutorService mExecutor = Executors.newScheduledThreadPool(1);
    
    public void watch(Object object, String tag) {
        mWatchedObjects.put(tag, new WeakReference<>(object));
        
        // 定期检查
        mExecutor.scheduleAtFixedRate(() -> checkLeaks(), 1, 1, TimeUnit.MINUTES);
    }
    
    private void checkLeaks() {
        for (Map.Entry<String, WeakReference<Object>> entry : mWatchedObjects.entrySet()) {
            String tag = entry.getKey();
            WeakReference<Object> ref = entry.getValue();
            
            if (ref.get() == null) {
                // 对象已被 GC，移除监控
                mWatchedObjects.remove(tag);
            } else {
                // 检查是否为泄漏
                if (isLeak(ref.get(), tag)) {
                    onLeakDetected(tag, ref.get());
                }
            }
        }
    }
}
```

### 2. 智能泄漏检测算法

```java
private boolean isLeak(Object object, String tag) {
    // 1. 检查对象状态
    if (isActivityDestroyed(object)) {
        // Activity 已销毁但仍被引用
        return true;
    }
    
    // 2. 检查引用链
    if (hasStrongReferenceToActivity(object)) {
        return true;
    }
    
    // 3. 检查内存使用模式
    if (isUnusualMemoryPattern(object)) {
        return true;
    }
    
    return false;
}
```

## 治理策略与实践

### 1. 预防性措施

#### 使用弱引用和软引用
```java
// 1. 弱引用：GC 时直接回收
private WeakReference<Context> mContextRef;

// 2. 软引用：内存不足时回收
private SoftReference<Bitmap> mBitmapRef;
```

#### 及时清理资源
```java
@Override
protected void onDestroy() {
    super.onDestroy();
    
    // 1. 清理 Handler 回调
    if (mHandler != null) {
        mHandler.removeCallbacksAndMessages(null);
    }
    
    // 2. 清理监听器
    if (mSensorManager != null) {
        mSensorManager.unregisterListener(mListener);
    }
    
    // 3. 清理数据库连接
    if (mDatabase != null) {
        mDatabase.close();
    }
}
```

### 2. 架构优化策略

#### 使用单例模式
```java
public class MemorySafeSingleton {
    private static volatile MemorySafeSingleton sInstance;
    private WeakReference<Context> mContextRef;
    
    private MemorySafeSingleton(Context context) {
        mContextRef = new WeakReference<>(context.getApplicationContext());
    }
    
    public static MemorySafeSingleton getInstance(Context context) {
        if (sInstance == null) {
            synchronized (MemorySafeSingleton.class) {
                if (sInstance == null) {
                    sInstance = new MemorySafeSingleton(context);
                }
            }
        }
        return sInstance;
    }
}
```

#### 使用 ViewModel + Lifecycle
```java
public class UserProfileViewModel extends ViewModel {
    private MutableLiveData<UserData> mUserData = new MutableLiveData<>();
    
    public void loadUserData(String userId) {
        // 自动感知生命周期，避免泄漏
        repository.getUserData(userId).observeForever(mUserData::setValue);
    }
}
```

## 线上治理方案

### 1. 分级告警机制

```java
public class MemoryLeakManager {
    public enum AlertLevel {
        INFO,    // 信息级别：内存使用正常
        WARNING, // 警告级别：内存使用偏高
        CRITICAL // 严重级别：内存泄漏风险
    }
    
    public void reportLeak(String processName, String component, AlertLevel level) {
        switch (level) {
            case INFO:
                Analytics.log("memory_leak_info", processName, component);
                break;
            case WARNING:
                AlertCenter.sendWarning("Memory leak detected in " + processName, component);
                break;
            case CRITICAL:
                AlertCenter.sendCritical("Critical memory leak in " + processName);
                // 自动触发OOM dump
                HeapDumpHelper.dump(processName);
                break;
        }
    }
}
```

### 2. 自动化治理流程

```java
public class AutomatedMemoryGovernance {
    public void processMemoryEvent(MemoryEvent event) {
        // 1. 分析事件
        LeakAnalysisResult result = analyzeLeak(event);
        
        // 2. 根据结果采取行动
        if (result.severity == Severity.CRITICAL) {
            // 强制清理
            forceCleanup(result.processName, result.component);
        } else if (result.severity == Severity.WARNING) {
            // 提醒开发者
            notifyDevelopers(result);
        }
        
        // 3. 记录到监控系统
        MonitorSystem.recordMemoryLeak(result);
    }
}
```

## 性能优化建议

### 1. 监控性能优化

- **控制检测频率**：避免过于频繁的内存检查
- **选择性监控**：只监控关键对象和页面
- **异步处理**：将检测逻辑放在后台线程

### 2. 减少内存开销

- **复用对象**：使用对象池减少频繁创建销毁
- **优化数据结构**：选择内存效率更高的数据结构
- **及时清理**：在不需要时及时释放资源

## 总结

内存泄漏检测与治理是 Android 开发中的重要环节。通过理解 GC 原理、掌握检测工具、实施预防措施，可以有效地减少内存泄漏的发生。在 Android 17 中，新的内存管理机制和监控工具为开发者提供了更强大的治理能力。

关键要点：
1. 理解内存泄漏的本质和判定标准
2. 熟练使用 LeakCanary、KOOM 等检测工具
3. 实施预防性措施和架构优化
4. 建立线上监控和自动化治理流程
5. 持续优化检测性能和治理效果
