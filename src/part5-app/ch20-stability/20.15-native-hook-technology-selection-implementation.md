## 三大流派概览

Native Hook 在 AIW 范围内系统化为三个流派，下文以源码为锚点说明：

### 一、GOT/PLT Hook（外部函数调用表重写）

- **bionic 行为**：android-17.0.0_r1 的 `bionic/linker/linker.cpp::soinfo::prelink_image()` 中 `DT_PLTGOT` 被显式标注为 "Ignored (because RTLD_LAZY is not supported)"（line 3017-3018）。所有 `R_GENERIC_JUMP_SLOT` 重定位在 `link_image()` 调用 `relocate()` 时通过 `process_relocation_impl<RelocMode::General>()` 的 fast path 立即将实地址写入 GOT slot。
- **关键含义**：GOT 写入时机 = `dlopen()` 同步期间；之后 GOT 永久保存绝对地址，除非通过 IFUNC 重新解析。
- **弱点**：`soinfo::link_image()` 末尾调用 `protect_relro()`（line 3480+）把 GNU_RELRO 段写回只读；GOT 大多落在 RELRO 段中，因此 inline mprotect 回 RW 的窗口期非常短；Android 14+ 引入 MEMTAG globals 后，部分 RELATIVE relocation 复用 place bits 存 tag metadata，RELRO 段内字节含义被改写。
- **适用范围**：xHook / ELF-Hook 类工具，主要用于 IO/Hook 拦截；要谨慎用于 ART 内部函数（JVM 已自行管理）。
- **关联引用**：ch14.13-hook-infrastructure.md 第 7 节（PLT/GOT 链路）已经描述完整，本节是其在 ARM64 + Android 17 实际状态下的精度补充。

### 二、Trap Hook（SIGTRAP 信号 + ptrace 拦截）

- **bionic 行为**：`system/core/debuggerd/handler/debuggerd_handler.cpp::debuggerd_signal_handler()`（line 663+）通过 `sigaction` 注册 `SA_RESTART | SA_SIGINFO | SA_ONSTACK | SA_EXPOSE_TAGBITS`（SA_EXPOSE_TAGBITS 为 Android 17 新增），对 SIGTRAP / SIGSEGV / SIGBUS / SIGFPE / SIGILL / SIGABRT 统一处理。
- **关键流程**：handler 内部 `prctl(PR_SET_DUMPABLE, 1)` → `clone()` 派生 pseudothread（`CLONE_THREAD | CLONE_SIGHAND | CLONE_VM | CLONE_CHILD_SETTID`，关键：**不依赖 ptrace 做读取**）→ fork 出 crash_dump 进程通过 ptrace 双端抓栈。
- **含义**：Trap Hook 一旦打 BRK 软断点，进程即被 debuggerd 接管 → tombstone 落盘；除非用户态 sigaction 抢先截获并伪造恢复，否则进程会在 tombstone 写完后被 resend_signal 终结。
- **陷阱**：与 libart 的 sigchain 优先级斗争；ART 进程必须走 `debuggerd_handle_signal()` 这个 user-facing 接口，不直接调用 `debuggerd_signal_handler`。

### 三、Inline Hook（指令级复写）

- **bionic 64-bit 行为**：`linker.cpp` line 3183：

  ```cpp
  case DT_TEXTREL:
  #if defined(__LP64__)
    DL_ERR(""%s" has text relocations", get_realpath());
    return false;  // 64-bit 直接拒绝
  #else
    has_text_relocations = true;
    break;
  #endif
  ```

  说明 64-bit SO 一旦声明 DT_TEXTREL，加载直接失败，Inline Hook **不能借助 text relocations 机制**完成。

- **ARM64 指令修复要点**（与 ARM32 本质差异）：

  | 维度 | ARM32 | ARM64 |
  |---|---|---|
  | Thumb | 支持（IT/T16/T32）| 不支持，固定 32-bit 指令 |
  | PC | R15，三级流水线 PC+8 | 没有"PC 寄存器"概念；PC-relative 走 ADRP/ADR |
  | 受影响指令 | LDR PC, [PC, #offset] / ADR / B / BL | ADRP/ADR / LDR (literal) / B (B.cond / CBZ / TBZ) |
  | Veneer | LDR PC, [PC, #offset] trampoline | B ±128MB 外的目标需 `BR Xn` 寄存器间接跳 + trampoline |

- **Inline Hook 关键动作**：
  1. mprotect `.text` 为 RWX（被 SELinux `execmem`/`execmod` 限制；参见 ch14.13 第 5 节）。
  2. 读取目标函数开头 K 条指令 → 拷贝到 hook 框架分配的 trampoline 区域。
  3. PC-relative 修复：ADRP/ADR/LDR 指令在新地址上重新计算页面/偏移。
  4. 目标函数头写入 B hook_func（±128MB 内）或通过 veneer 中转。
  5. `__builtin___clear_cache()` / `cacheflush()` 刷新 icache（ARM64 Harvard 变体）。

- **2026 现状**：Android 14 强制要求 64-bit app，因此 Hook 框架必须支持 ARM64；ShadowHook、xHook（bytedance/android-inline-hook）都已稳定支持 ARM64/ARM32 dual-arch，但 ARM64 性能优于 ARM32（无 Thumb 状态切换，指令修复更简单）。

## 选型矩阵

| 场景 | 推荐流派 | 理由 |
|------|----------|------|
| IO/系统调用诊断 | GOT/PLT | 透明；低开销；不影响 .text |
| ART 内部函数调试 | Trap Hook + debuggerd | 命中 .text 段（RELRO + JIT code）需绕开 SELinux |
| Native 加密/网络算法性能切换 | Inline Hook | GOT 钩不住（被 dlsym 提前解析或为 IFUNC）|
| 第三方 SDK 监控 | xHook 类 GOT 实现 | 稳定 + 不影响 ART 内部状态 |
| 大型 native 拦截 + dlsym 后调用 | Inline Hook | GOT/PLT 走不到 |
