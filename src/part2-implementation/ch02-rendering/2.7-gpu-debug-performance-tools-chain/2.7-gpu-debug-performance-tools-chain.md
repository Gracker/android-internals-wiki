# 2.7 Android 17 GPU 图形调试与性能优化工具链

Android 17 没有一条从 SDK 到 SurfaceFlinger、再到 GPU counter 的固定调试调用链。可用能力分布在应用帧统计、SurfaceFlinger 帧观测、Perfetto GPU producer、`GpuService`、桌面分析器和厂商工具中。每种能力观察的对象不同：

- FrameTimeline 观察帧预算与呈现结果；
- FrameTracer 观察 layer buffer 的若干生命周期节点；
- GPU render stage 观察驱动 producer 上报的 GPU 队列活动；
- GPU counter 观察设备定义的硬件计数器；
- AGI Frame Profiler 进入 draw、shader、pipeline state 和资源；
- HWC、fence 与显示驱动证据解释合成和 present。

本文固定平台源码为 Android 17 / API 37 的 `android-17.0.0_r1`，涉及 dma-buf、dma-fence 和调度时固定内核为 `android17-6.18-2026-06_r6`。

## 1. 先确定主体内容怎样出图

“GPU 卡”只描述现象，不能确定工作发生在哪个 GPU client。主体像素可能来自：

- View/Compose 经 HWUI 与 RenderThread 写入 App Window；
- `SurfaceView`、游戏或 native renderer 直接向独立 Surface 提交；
- `TextureView` 的外部 buffer 被 HWUI 采样进宿主窗口；
- Camera HAL、MediaCodec 或 WebView renderer 生产 buffer；
- SurfaceFlinger RenderEngine 为 CLIENT composition 生成 client target；
- HWC 选择 DEVICE composition，将 layer 交给显示硬件路径。

标准 App Window 通常能获得较完整的 App FrameTimeline。SurfaceView、Camera、视频和 native game 常需要另行追踪独立 layer、buffer frame number、acquire fence 与 display frame。TextureView 还要同时观察外部 Producer 和宿主 HWUI。

工具选择从以下对象表开始：

| 对象 | 识别方式 | 主要工具 |
|---|---|---|
| App 主线程与 RenderThread | tid、slice、调用栈 | Perfetto、simpleperf、应用 trace |
| 独立内容 Producer | Surface、BufferQueue、engine/camera/codec 线程 | Perfetto、Producer 日志、厂商 trace |
| layer 与 buffer | layer id/name、buffer id、frame number | FrameTracer、SurfaceFlinger trace、Winscope |
| GPU submission | context、queue、render stage | Perfetto GPU producer、AGI、厂商 profiler |
| 合成策略 | CLIENT/DEVICE、client target | SurfaceFlinger/HWC trace、dump |
| 显示完成 | present fence、release fence、DisplayFrame | FrameTimeline、FrameTracer、HWC/driver trace |

### 应用侧只能观察自身可见的边界

`Choreographer.FrameData` / `FrameTimeline` 向应用提供候选 VSync timeline，帮助应用选择 presentation deadline；它和 SurfaceFlinger Perfetto 中的 expected/actual FrameTimeline 不是同一个 API 对象。

[`FrameMetrics`](https://developer.android.com/reference/android/view/FrameMetrics) 按 Window 给出 UI、draw、sync、command issue、swap buffer 和 total 等时间项。字段可能受硬件加速、平台版本和统计实现影响，也不会给出 shader、GPU queue 或 HWC composition 的完整解释。

JankStats 是 Jetpack library，用于把应用 frame timing 与开发者提供的 UI state 关联。它不属于 Android 17 framework 的 `JankTracker`，也不接收 SurfaceFlinger 的 `gui::JankData`。

下面的命令用于快速查看指定应用的 HWUI 帧统计：

```bash
adb shell dumpsys gfxinfo com.example.app reset
# 执行固定操作路径
adb shell dumpsys gfxinfo com.example.app framestats
```

`framestats` 适合发现应用窗口帧时间是否异常，不能提供 GPU utilization、memory bandwidth 或独立 SurfaceView 主体内容的完整时序。

## 2. SurfaceFlinger 的五套观测机制

这些组件会共享 layer、fence 和 present 信息，但职责平行，不构成逐级处理管线。

| 组件 | Android 17 源码 | 输出与用途 |
|---|---|---|
| FrameTimeline | [`Scheduler/FrameTimeline.cpp`](https://android.googlesource.com/platform/frameworks/native/+/refs/tags/android-17.0.0_r1/services/surfaceflinger/Scheduler/FrameTimeline.cpp) | expected/actual SurfaceFrame、DisplayFrame、present 与 jank 分类 |
| FrameTracer | [`FrameTracer.cpp`](https://android.googlesource.com/platform/frameworks/native/+/refs/tags/android-17.0.0_r1/services/surfaceflinger/FrameTracer/FrameTracer.cpp) | layer/buffer/frame number、queue、fence、latch、composition、present 事件 |
| TimeStats | [`TimeStats.cpp`](https://android.googlesource.com/platform/frameworks/native/+/refs/tags/android-17.0.0_r1/services/surfaceflinger/TimeStats/TimeStats.cpp) | 按 layer、刷新率和渲染率聚合计数与直方图 |
| JankTracker | [`JankTracker.cpp`](https://android.googlesource.com/platform/frameworks/native/+/refs/tags/android-17.0.0_r1/services/surfaceflinger/Jank/JankTracker.cpp) | 缓存已生成的 `JankData`，批量通知 listener |
| FpsReporter | [`FpsReporter.cpp`](https://android.googlesource.com/platform/frameworks/native/+/refs/tags/android-17.0.0_r1/services/surfaceflinger/FpsReporter.cpp) | 按 task 的 layer hierarchy，从已呈现 DisplayFrame 计算 FPS 并通知 listener |

### FrameTimeline 回答“哪一侧错过了预算”

FrameTimeline 为 App SurfaceFrame 和 SurfaceFlinger DisplayFrame 保存 predicted 与 actual 时间线。它可以给出 `AppDeadlineMissed`、`SurfaceFlingerCpuDeadlineMissed`、`SurfaceFlingerGpuDeadlineMissed`、`DisplayHAL`、`BufferStuffing`、`PredictionError`、`Dropped` 等分类。

分类是排查方向，不是函数级根因。`SurfaceFlingerGpuDeadlineMissed` 指向 SurfaceFlinger 的 GPU composition 完成偏晚；它没有证明应用 shader 很慢。`AppDeadlineMissed` 也可能包含主线程、RenderThread、buffer 背压或应用 GPU 完成偏晚。

### FrameTracer 回答“buffer 停在哪一段”

FrameTracer 注册的数据源名是 `android.surfaceflinger.frame`。Android 17 的 `Layer.cpp` 在 transaction、latch 和 composition presented 等位置记录事件。当前调用点可产生 `DEQUEUE`、`QUEUE`、`ACQUIRE_FENCE`、`LATCH`、`FALLBACK_COMPOSITION` 和 `PRESENT_FENCE` 等信息。

它不会跟踪 gralloc 分配、每次像素写入、全部 GPU 命令或 buffer 的每一次引用变化。proto 中存在一个枚举值，也不能证明固定 tag 的 `Layer.cpp` 会在每帧写出该事件。

### JankTracker 批量发送已经分类的数据

Jank 分类在 FrameTimeline 中完成。JankTracker 按 layer 保存 `JankData`，单 layer backlog 达到 50 条时可触发 flush，并通过低优先级 executor 通知 listener。批量大小影响回调时机，不改变一帧的分类结果。

### TimeStats 与 FpsReporter 用于统计

TimeStats 适合比较固定场景中 janky frame 比例、present interval 和时间差分布。FpsReporter 的值来自目标 task 对应 layer 参与的已呈现 DisplayFrame。它们都不能替代单帧线程、GPU submission 和 fence 证据。

## 3. `GpuService` 提供系统级汇总

Android 17 的 Binder 服务名是 `gpu`，实现位于 [`GpuService.cpp`](https://android.googlesource.com/platform/frameworks/native/+/refs/tags/android-17.0.0_r1/services/gpuservice/GpuService.cpp)。常用 dump 分支如下：

| 命令 | 主要内容 | 不包含 |
|---|---|---|
| `dumpsys gpu --gpustats` | graphics driver、ANGLE 等加载与失败统计 | 连续 GPU 利用率和 shader 耗时 |
| `dumpsys gpu --gpumem` | `gpu_mem_total` 数据可用时的 GPU memory 汇总 | 所有 dma-buf、纹理对象和带宽 |
| `dumpsys gpu --gpuwork` | `gpu_work_period` 数据可用时的 GPU/UID active、inactive 汇总 | 指令效率和焦耳 |
| `cmd gpu vkjson` | Vulkan properties JSON | GLES 状态和运行时负载 |
| `cmd gpu featureOverrides` | 当前缓存的 ANGLE feature override | 修改系统 driver 的通用 shell 能力 |

下面的命令用于核对目标设备公开了哪些系统汇总：

```bash
adb shell dumpsys gpu --gpustats
adb shell dumpsys gpu --gpumem
adb shell dumpsys gpu --gpuwork
adb shell cmd gpu help
adb shell cmd gpu vkjson
adb shell cmd gpu featureOverrides
```

某项为空或报不可用时，应检查 driver tracepoint、BPF 程序、产品配置与权限。空输出不能按数值 0 参与比较。

`GpuService::toggleAngleAsSystemDriver()` 是受 `ACCESS_GPU_SERVICE` 保护的 Binder 方法，源码只允许 `system_server` 调用。它没有作为 `cmd gpu` 子命令公开。

## 4. Perfetto 的 GPU 数据源

[Perfetto GPU 文档](https://perfetto.dev/docs/data-sources/gpu)列出 Android 常见数据源：

| 数据源 | 可以观察 | 设备依赖 |
|---|---|---|
| `power/gpu_frequency` | GPU frequency 事件 | 内核/驱动是否提供 tracepoint |
| `gpu_mem/gpu_mem_total` | 全局或进程 GPU memory total | 驱动 tracepoint 与采集配置 |
| `gpu.counters` | 周期采样的硬件 counter | GPU producer、counter id/name、可并采数量 |
| `gpu.renderstages` | graphics/compute submission 的 GPU 时间线 | GPU producer 与驱动支持 |
| `vulkan.memory_tracker` | Vulkan allocation 和 bind | Vulkan layer/driver 与应用路径 |
| `gpu.log` | producer 上报的 GPU 调试消息 | producer 覆盖范围 |

设备 producer 可能使用带后缀的名称，如 `gpu.counters.adreno` 或 `gpu.renderstages.mali`。Tracing service 按名字精确匹配，采集前应查询 descriptor。

下面的命令用于枚举当前设备注册的数据源：

```bash
adb shell perfetto --query --long
```

查询结果应与 trace config 一起归档。GPU 轨道缺失只说明当前采集没有该类数据，原因可能是 producer 未注册、名字不匹配、counter 未选择、权限不足或驱动缺少支持。

### Counter descriptor 没有跨厂商归一化

Android GPU producer 使用 `GpuCounterDescriptor` 声明 counter id、name、description、unit、group 和采样能力。Android 模式要求 session 内的 counter id 全局协调。

[`InternedGpuCounterDescriptor`](https://android.googlesource.com/platform/external/perfetto/+/refs/tags/android-17.0.0_r1/protos/perfetto/trace/gpu/gpu_counter_event.proto) 让 descriptor 在 trusted packet sequence 内以 IID 引用，适合多 producer、多 GPU 场景。它减少重复描述并避免全局 id 协调，没有把 Adreno、Mali、PowerVR 或 Xclipse 的 counter 转换成同一种硬件语义。

跨设备比较前至少要记录：

- GPU 型号、架构和 driver build；
- counter 的完整 descriptor、单位和采样周期；
- counter multiplexing 与可同时启用数量；
- Graphics API、分辨率、目标帧率和 workload；
- 温度、频率、功耗模式和持续运行时间。

名称相近的 utilization 可能分别表示队列非空、时钟开启、shader core active 或其他厂商口径。没有相同物理定义时，只适合在各自设备内做前后对照。

## 5. APA、AGI 与厂商工具怎样分工

截至 2026 年 7 月，[Android Performance Analyzer](https://developer.android.com/blog/posts/introducing-android-performance-analyzer-the-next-evolution-in-profiling-for-android) 的 System Profiler 处于公开 beta。它面向 CPU、GPU、memory、power 和系统行为的时间线分析，并可使用 Perfetto 配置。

[Android GPU Inspector](https://developer.android.com/agi/start) 仍提供 System Profiler 和 Frame Profiler；官方 quickstart 已建议系统 profiling 优先评估 APA。AGI Frame Profiler 继续用于单帧的 Vulkan 或 OpenGL on ANGLE 捕获，可检查：

- API command；
- render pass 与 framebuffer；
- mesh、texture 和 shader；
- pipeline state；
- command 级 memory 与 GPU performance 数据。

两类工作应分开安排：

1. 用 Perfetto、APA 或 AGI System Profiler 找到稳定复现窗口，判断问题落在 CPU 准备、应用 GPU、buffer 背压、SurfaceFlinger、HWC 或显示侧；
2. 确认进入应用 GPU 执行层后，对同一 workload 做短窗口 AGI Frame Profile 或厂商 profiler；
3. 修改 shader、pass、纹理或资源后，回到未注入的系统 trace 复测。

Frame capture 会改变加载、同步、内存和时序，不能拿捕获帧的 wall time 直接替代未注入基线。不同 GPU 对 AGI、counter 和厂商工具的支持范围也不同。

## 6. 频率、利用率和带宽怎样解释

任何单项 GPU 指标都需要与工作窗口配对。

| 现象 | 可提出的假设 | 需要补的证据 |
|---|---|---|
| GPU stage 长、频率高 | GPU 工作量大或接近性能上限 | counter、帧捕获、分辨率对照、thermal |
| GPU stage 长、频率低 | 负载较小、策略限制或热/功耗限制 | workload、thermal severity、governor/driver 事件 |
| utilization 低、帧仍晚 | CPU、queue、fence、HWC 或利用率口径问题 | sched、FrameTimeline、BufferQueue、composition |
| bandwidth counter 高 | GPU 可能受共享内存流量影响 | 同设备基线、cache/stall counter、CPU/codec/camera 并发 |
| CLIENT composition 增多 | SurfaceFlinger RenderEngine 工作增加 | composition change、client target、整组 layer 条件 |

“带宽超过 80% 就是瓶颈”“低利用率代表还有固定优化空间”都缺少通用依据。阈值要来自目标 GPU 文档、同设备基线和可控实验。

功耗也不能用一个经验公式代替测量。GPU frequency、active time 和 counter 可解释工作状态；能量需要 Power Stats rail、battery counter、厂商 telemetry 或外置仪器，并写清 rail 是否包含内存和互连。

## 7. 调试属性只用于受控实验

`debug.sf.*` 属性通常改变 SurfaceFlinger 的策略或实现分支。它们不是观测指标，部分属性在进程启动时读取，部分受 build flag、设备能力和 vendor 配置影响。

使用任何属性前要完成三项核对：

1. 在 `android-17.0.0_r1` 中找到读取位置、默认值和生效时机；
2. 在目标设备上保存原值，确认是否需要重启 SurfaceFlinger 或设备；
3. 只改变一个变量，实验后恢复原值并重采基线。

原稿列出的 `debug.gpu.profiling_level`、`debug.sf.treat_170m_as_120m` 没有在本轮固定 tag 中形成可复用的 AOSP GPU 调试契约，因此不保留为通用速查项。厂商属性应按目标 build 的源码或属性清单验证。

## 8. 一次可复用的 GPU 排查顺序

### 步骤一：固定实验条件

记录设备 build、GPU/driver、Graphics API、分辨率、刷新率、目标帧率、画质、温度、充电状态和运行时长。冷启动、热启动与稳定态分开测。

### 步骤二：锁定 Surface、layer 和帧

标准 App Window 使用 surface/display token。独立 Surface 使用 layer、buffer frame number、engine frame id、Vulkan present id 和时间邻近关系。不要用宿主 Activity 的帧替代 SurfaceView 或 Camera 主体内容。

### 步骤三：沿显示路径找第一个逾期边界

按以下顺序检查：

1. VSync 和应用 CPU 工作是否按时开始；
2. GPU submission 与 producer completion fence 是否按时；
3. `queueBuffer`、BLAST transaction 与 acquire fence 是否积压；
4. SurfaceFlinger 是否及时 latch；
5. HWC 选择 CLIENT 还是 DEVICE；
6. RenderEngine、validate、present 与 present fence 是否按时；
7. release fence 是否造成后续 buffer 复用等待。

### 步骤四：再进入 GPU 微架构

只有 GPU stage、fence 或可控对照把延迟指向 GPU 执行后，才进一步检查 shader、纹理、overdraw、render pass、tile、bandwidth、cache 和 occupancy。降低分辨率、关闭单个 pass、替换单个 shader 都应保持其他条件一致。

### 步骤五：验证修复

保留 trace on/off 两组样本估计采集扰动。用相同 workload 重复多轮，报告帧时间分布、jank 分类、功耗/温度和画质变化，避免只比较一张 FPS 截图。

## 9. 常见误判

| 说法 | Android 17 的边界 |
|---|---|
| FrameTracer 覆盖 buffer 从分配到释放的全部六阶段 | 它只记录固定调用点写出的 layer/buffer 事件 |
| JankTracker 决定 App/SF jank | FrameTimeline 先分类，JankTracker 再投递 |
| GPU counter 已跨厂商标准化 | descriptor 公开 producer 语义，不转换硬件口径 |
| `dumpsys gpu --gpustats` 是 GPU 利用率轨道 | 它偏向 driver/ANGLE 加载统计 |
| FrameTimeline 的 GPU composition 表示应用 GPU 很慢 | 该字段描述显示帧是否涉及 SurfaceFlinger client composition |
| 低 GPU utilization 排除 GPU 问题 | 还受采样口径、空洞、同步、频率和 producer 覆盖影响 |
| `DEVICE` composition 表示该帧没用 GPU | 应用可能已用 GPU 生成 layer buffer |
| `CLIENT` composition 表示应用 shader 是根因 | 这里的额外 GPU 工作由 SurfaceFlinger RenderEngine 发起 |
