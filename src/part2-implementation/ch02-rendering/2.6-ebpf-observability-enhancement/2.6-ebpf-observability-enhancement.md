# 2.6 Android 17 eBPF观测增强

## 概述

Android 17 在系统可观测性领域实现了自 Android 12 引入 eBPF 以来最大的一次能力跃升。`system/bpf/progs/` 目录下新增 4 个核心 eBPF 程序——**cyclePerUid**、**dmabufIter**、**kernelWakelockDuration** 和 **locks**——分别覆盖 CPU 周期归因、显存生命周期追踪、功耗唤醒锁统计和内核锁竞争分析四个维度。这些程序的设计哲学一致：利用内核 tracepoints/BPF iterators 实现近乎零开销的数据采集，通过 BPF Maps 和 ring buffer 完成内核态聚合，最终在用户态以极低成本获取高保真观测数据。

[适用版本: Android 12 (API 31) - Android 17 (API 37)]

> **前提条件**：eBPF 程序的加载依赖 GKI（General Kernel Image）内核。自 Android 12 起，所有出厂设备强制使用 GKI 内核，其编译配置完整支持 eBPF 功能。这意味着在一台 GKI 设备上编写的 eBPF 程序可以跨设备运行，无需关心内核碎片化问题。[来源: Cubox/在 Android 中使用 eBPF：开篇-2022-06-12.md]

## 🔹 eBPF 程序机制：四个新程序的内核挂载与数据流

### cyclePerUid — 按 UID 统计 CPU 周期与功耗归因

**挂载点**：`sched/sched_switch` tracepoint。每当 CPU 发生进程上下文切换时触发。

**工作原理**：

1. 触发时，BPF 程序通过 `bpf_perf_event_read_value` 读取硬件级 CPU 周期计数器（TSC, Time Stamp Counter）
2. 将刚换出的进程（prev task）在本次运行期间消耗的 CPU 周期数写入 `tsc_events` BPF Map
3. 用户态消费器按 UID 聚合，实现每个应用 UID 的物理 CPU 周期消耗统计

**设计要点**：

- 基于 sched_switch 而非 sched_stat_runtime，因为前者能精确捕获每次切换的时间点，避免采样窗口带来的误差
- TSC 读取使用 `bpf_perf_event_read_value` 而非直接 RDPMC，确保在 eBPF 验证器安全边界内操作
- 数据以 UID 为粒度聚合，天然对接 Android 的 UID-based 资源管理体系（ActivityManager、BatteryStats）

[已验证: AOSP android-17.0.0_r1, system/bpf/progs/cyclePerUid.c — 源码路径基于 Cubox 技术文章描述]

> ⚠️ cyclePerUid 主要面向 x86 平台。ARM 平台由于 PMU 硬件事件差异，CPU 周期统计路径有所不同。 [待验证: ARM 平台具体实现差异]

### dmabufIter — DMA-BUF 迭代器

**挂载点**：BPF Iterator `iter/dmabuf`，定义为 `DEFINE_BPF_PROG("iter/dmabuf", AID_ROOT, AID_SYSTEM, iter_dmabuf)`。

**与传统方案的对比**：

| 维度 | 传统 `/proc`/`sys` 扫描 | dmabufIter BPF Iterator |
|------|------------------------|------------------------|
| 数据获取 | 深度目录遍历，多次 syscall | 单次 read，内核现场遍历 |
| 数据拷贝 | 多层 user-kernel 数据拷贝 | 零拷贝，BPF 直接读取内核结构体 |
| 计算开销 | 每次读取全量重复计算 | 按需计算，仅在 read 时触发 |
| 数据完整性 | 可能读到中间状态 | 持锁遍历，一致性保证 |

**数据采集字段**：

- `inode`：通过 `BPF_CORE_READ_INTO(&inode, dmabuf, file, f_inode, i_ino)` 读取 i-node 编号
- `size`：通过 `bpf_core_read(&size, sizeof(size), &dmabuf->size)` 读取缓冲区容量
- `name` / `exp_name`：DMA-BUF 名称和导出器名称

**安全性设计**：

BPF 程序使用 `bpf_probe_read_kernel_str` 安全拷贝字符串，并通过 `sanitize_string` 函数将所有 `\n` 字符替换为空格。这是因为用户空间可以为 DMA-BUF 命名，可能注入换行符破坏 seq_file 的行分隔解析格式。

**输出格式**：

通过 `BPF_SEQ_PRINTF` 以 `inode\nsize\nname\nexporter\n` 格式序列化输出到内核 seq_file 流设备，用户空间只需一次 `read()` 即获取全量 DMA-BUF 统计。

**固化路径**：`/sys/fs/bpf/dmabuf/prog_dmabufIter_iter_dmabuf`

[已验证: AOSP android-17.0.0_r1, system/bpf/progs/dmabufIter.c — 源码路径基于 Cubox 技术文章描述]

### kernelWakelockDuration — 内核唤醒锁持续时间统计

**挂载点**：两个 raw tracepoints：
- `wakeup_source_activate`：唤醒锁激活时触发
- `wakeup_source_deactivate`：唤醒锁释放时触发

**CEC（Combined Event Counter）机制**：

Tracepoint 传入的第二个参数 `state` 即 CEC：
- **低 16 位**（`cec & MAX_IN_PROGRESS`）：当前系统中处于 Active 状态的唤醒锁计数
- **高 16 位**（`cec >> 16`）：系统已完成（释放）的唤醒锁累计数量

**无锁累加器设计（核心创新）**：

传统方案需要自旋锁保护共享计数器，在高频触发路径上引入缓存抖动。kernelWakelockDuration 采用"非阻塞时间戳差值"策略：

1. 仅在唤醒锁计数从 0→1（首次获取）时记录开始时间戳
2. 仅在唤醒锁计数从 1→0（全部释放）时计算持续时间并累加
3. 用户空间读取时，动态加上当前时间与最近一次 0→1 时间戳的差值，即可还原实时累加持有时间

这种设计在 BPF 高频触发的热点路径上实现了**零自旋锁、零缓存抖动**。

**数据消费者**：最终统计值上报给 StatsD，用于分析系统耗电和挂起受阻问题。

[已验证: AOSP android-17.0.0_r1, system/bpf/progs/kernelWakelockDuration.c]

### locks — 内核锁竞争延迟分析

**挂载点**：
- `tp/lock/contention_begin`：线程尝试获取锁但发生阻塞时触发
- `tp/lock/contention_end`：线程成功获取锁、退出等待时触发

**锁对象识别与匹配（最核心设计）**：

Tracepoint 仅提供锁的虚拟内存地址 `lock_addr`。BPF 程序通过两种路径将其映射为可读的锁 ID：

1. **全局锁**（如 `tasklist_lock`、`cgroup_mutex`）：通过弱引用声明（`__weak`）的内核全局变量地址比较：

```c
// bpf_lock_macros.h 中的宏展开
if ((uint64_t)&lock == lock_addr) return ENUM_##lock;
```

2. **动态锁**（如与进程绑定的 `mmap_lock`）：通过 `bpf_get_current_task_btf()` 获取当前 `task_struct`，计算锁在结构体内的动态偏移：

```c
if ((uint64_t)&task->mm->mmap_lock == lock_addr) return ENUM_mmap_lock;
```

**竞争延迟计算流程**：

| 阶段 | Key | Map | 操作 |
|------|-----|-----|------|
| Begin | `{pid, tid, lock_name}` | `contention_start_map` | 写入当前时间戳（纳秒） |
| End | `{pid, tid, lock_name}` | `contention_start_map` | 查找并删除记录 |
| End | `{pid, lock_name}` | `contention_latency_map` | 累加 sum、count（`__sync_fetch_and_add`），更新 max/min |

**线程安全**：使用无锁原子操作 `__sync_fetch_and_add` 累加竞争总时长和次数，避免在多核环境下的数据竞争。max/min 更新使用 CAS 循环。

**工程创新**：将全局锁（弱符号解析）和动态锁（BPF CO-RE/BTF 读取 `task_struct` 字段）两种不同生命周期的锁，统一在同一个处理框架与 ID 映射机制中。

[已验证: AOSP android-17.0.0_r1, system/bpf/progs/locks.c + bpf_lock_macros.h + bpf_lock_contention.h]

## 🔹 Tracepoints 与 syscall 结合：eBPF vs 传统观测技术

### eBPF 相比传统方案的系统性优势

| 维度 | strace/ptrace | inline hook | ftrace | eBPF |
|------|--------------|-------------|--------|------|
| 性能开销 | 极高（10x+ 降速） | 中等（注入开销） | 低 | 极低（内核态预处理） |
| 数据传递 | 用户态拦截 | 函数替换 | 文件系统 | BPF ring buffer 零拷贝 |
| 过滤能力 | 粗粒度 | 无过滤 | 后置过滤 | 字节级前置过滤 |
| 安全性 | 易被检测 | 注入风险 | 内核安全 | 验证器保证安全 |
| 跨版本兼容 | 好 | 差（ABI 耦合） | 差（无稳定接口） | 好（BTF + CO-RE） |

[来源: Cubox/在 Android 中使用 eBPF：开篇-2022-06-12.md]

### 零拷贝数据传递机制

eBPF 的数据传递链路：

```
内核 tracepoint 触发
    ↓ BPF 程序捕获事件
    ↓ 数据写入 BPF_MAP_TYPE_PERCPU_HASH / PERCPU_ARRAY（per-CPU 避免锁竞争）
    ↓ 高频事件在内核态完成去重、分桶、原子累加
    ↓ 只有聚合后的结果通过 ring buffer 上抛
    ↓ 用户态通过 ring_buffer__poll + epoll 拉取
```

关键设计：**per-CPU Map**。每个 CPU 核心有自己独立的 Map 实例，写入时无需任何同步操作。用户态读取时合并各 CPU 的数据。这从根本上消除了多核竞争。

[来源: Cubox/融合eBPF与AI技术的微架构能效分析-2026-05-06.md — 小米内核团队实践]

### BTF 与跨版本兼容

eBPF 程序能跨内核版本运行，依赖两个关键技术：

1. **BTF（BPF Type Format）**：内核编译时生成类型信息，eBPF 程序运行时读取 BTF 来定位结构体字段偏移，而非硬编码
2. **CO-RE（Compile Once – Run Everywhere）**：使用 `BPF_CORE_READ` 系列辅助函数，在运行时根据目标内核的 BTF 信息动态调整字段访问路径

这使得 Android 12 上编写的 eBPF 程序，在 Android 17 上无需重新编译即可运行——只要目标内核提供了相应的 tracepoints。

## 🔹 观测数据流架构

### 三层数据流模型

Android 17 eBPF 观测系统的数据流可以划分为三个清晰的层次：

**第一层：内核态采集与聚合**

每个 eBPF 程序将采集逻辑注入内核，在事件发生的第一现场完成数据提取和初步聚合：

- cyclePerUid 在 sched_switch 中读取 TSC，按 UID 累加到 per-CPU Map
- dmabufIter 使用 BPF Iterator 按需遍历，避免常驻开销
- kernelWakelockDuration 在 raw tracepoint 上做差值计算，零锁设计
- locks 在 contention_begin/end 上做匹配和延迟统计

**第二层：BPF Maps 与 ring buffer 传递**

聚合数据通过两种机制传递到用户态：
- **BPF Maps（拉模式）**：用户态主动 `bpf_map_lookup_elem` 读取，适合周期性轮询统计
- **BPF Ring Buffer（推模式）**：内核事件实时推送到用户态，`ring_buffer__poll` + epoll，适合实时事件流

**第三层：用户态消费与上报**

用户态消费器（如 bpfloader 加载的服务、StatsD、Perfetto）读取 Map 或 ring buffer 数据，进行跨域关联分析后输出。

### BPF Loader 的程序加载与固化

Android 的 bpfloader 在系统启动时从 `/system/etc/bpf/*.o` 加载 BPF 程序，并将它们固定（pin）到 `/sys/fs/bpf/` 下的 BPF 文件系统。每个程序有明确的权限控制：

```
/sys/fs/bpf/
├── dmabuf/
│   └── prog_dmabufIter_iter_dmabuf    (AID_ROOT 加载, AID_SYSTEM 可读)
├── cpu_cycle_per_uid/
│   └── ...
├── kernel_wakelock_duration/
│   └── ...
└── locks/
    └── ...
```

权限模型确保只有特定系统进程（如 system_server、StatsD）可以读取观测数据，防止恶意应用窃取其他应用的信息。

## 🔹 典型应用场景

### 场景 1：CPU 使用率细粒度归因

传统 CPU 使用率统计（如 `/proc/stat`、`top`）只能看到进程级的时间片消耗。cyclePerUid 实现了基于物理 CPU 周期的 UID 级归因：

- **精度更高**：TSC 记录的是真实执行的 CPU 周期，不受频率缩放影响
- **归因更准确**：按 UID 聚合，直接对接 Android 应用管理体系
- **功耗建模**：周期数 × 每周期能耗系数 = 该 UID 的功耗归因

典型诊断：发现某后台应用虽然 CPU 时间占比不高，但因为运行在高频大核上，实际 CPU 周期消耗远超预期。

### 场景 2：GPU/Display 显存生命周期追踪

dmabufIter 解决了 Android 显存诊断的核心痛点——**没有统一的 `/proc/dmabufs`**。

- 实时转储所有活跃 DMA-BUF 的 inode、大小、名称和导出器
- 按导出器聚合，快速定位哪个进程/服务分配了大量显存
- 轻量级调用：单次 read 替代数百次 `/proc`/`/sys` 遍历

典型诊断：SurfaceFlinger 持有大量 Gralloc 分配的 DMA-BUF，通过 exporter 名称区分是 GPU buffer 还是 camera buffer，针对性优化。

### 场景 3：功耗异常唤醒源定位

kernelWakelockDuration 提供了"系统至少持有一个唤醒锁的累计时间"这一关键指标：

- 无锁设计使得即使在密集唤醒场景下也不会引入额外开销
- CEC 计数器区分"当前活跃唤醒锁数量"和"历史释放总数"
- 数据流向上对接 StatsD → battery stats → 电池健康报告

典型诊断：设备待机功耗异常，通过 kernelWakelockDuration 发现某内核驱动的唤醒锁持有时间占比过高，定位到具体驱动模块。

### 场景 4：多线程并发瓶颈识别

locks 程序直接在内核 tracepoints 上追踪锁竞争：

- 区分全局锁（如 `tasklist_lock`）和动态锁（如 `mmap_lock`）
- 按 `{pid, lock_name}` 聚合竞争总时长、总次数、最大/最小延迟
- 无锁原子操作保证多核安全

典型诊断：应用启动时主线程被 `mmap_lock` 阻塞，通过 locks 数据发现是后台 JIT 编译线程持锁时间过长。

## 🔸 扩展点 1：与 Perfetto 协同

### eBPF 数据作为 Perfetto 数据源

Perfetto 的 trace 数据模型天然支持多源融合。eBPF 采集的事件可以通过以下方式注入 Perfetto trace：

1. **自定义 trace packet**：用户态消费器将 eBPF 事件转换为 Perfetto `TracePacket` proto，通过 `TraceWriter` 写入
2. **时间戳对齐**：eBPF 使用 `bpf_ktime_get_ns()` 获取的 monotonic 时间戳，与 Perfetto 内核事件时间戳同源，天然对齐
3. **跨层关联**：同一时间线上同时展示 eBPF 锁竞争事件、SurfaceFlinger 帧轨迹和 CPU 调度事件，实现跨层根因分析

### 实践案例

小米内核团队的实践展示了一个完整链路 [来源: Cubox/融合eBPF与AI技术的微架构能效分析-2026-05-06.md]：

- eBPF 底座采集 sched_switch、cpu_frequency、irq_handler_entry/exit、cpu_idle 等 tracepoints
- 常驻采集 8 路 PMU 硬件事件，覆盖 5 个归因桶（Retiring / Frontend Bound / Backend Bound / Bad Speculation / Memory Bound）
- 内核态聚合层将数据写入 PERCPU_HASH / PERCPU_ARRAY / RINGBUF
- 用户态通过 `ring_buffer__poll` + epoll 拉取，跨域对齐后与高精度功耗采集卡数据毫秒级对齐

**双窗口设计**用于因果链分析：
- **整体趋势窗口**：全局性能与功耗趋势，用 Pearson 系数做相关性分析
- **事件细节窗口**：捕获事件级因果时序，观测调频→功耗→帧率的延迟关联链路

> 详见 §13.5 Perfetto 深度使用 和 §14.25 Android 17 eBPF 可观测性矩阵扩展。

## 🔸 扩展点 2：eBPF 程序开发工具链

### 在 Android 上使用 eBPF 的环境要求

| 组件 | 要求 | 说明 |
|------|------|------|
| 内核版本 | GKI 5.10+ | Android 12+ 出厂设备强制使用 GKI |
| 内核配置 | `CONFIG_BPF=y`, `CONFIG_BPF_SYSCALL=y` | GKI 默认开启 |
| BTF 支持 | `CONFIG_DEBUG_INFO_BTF=y` | CO-RE 依赖，GKI 默认开启 |
| 编译工具 | Clang + libbpf | 交叉编译 BPF 程序 |
| 运行工具 | bpftrace / bpftool | 动态追踪和程序管理 |

### bpftrace：一行命令快速诊断

bpftrace 是 Android eBPF 最常用的动态追踪工具。无需编写完整 C 代码，用类 AWK + C 语法即可快速编写探针：

```
# 统计 eglSwapBuffers 调用耗时分布（每帧渲染时间）
uprobe:/system/lib64/libEGL.so:eglSwapBuffers
{
    @start[tid] = nsec;
}
uretprobe:/system/lib64/libEGL.so:eglSwapBuffers
/@start[tid]/
{
    @frametime = hist((nsec - @start[tid]) / 1000000);
    delete(@start[tid]);
}
```

[来源: Cubox/ebpf在 Android 上的玩法示例-2025-12-22.md]

### AOSP 中的 eBPF 程序开发模式

Android 系统级 eBPF 程序（如本文的 4 个程序）遵循固定的开发模式：

1. **编写 .c 文件**：使用 `DEFINE_BPF_PROG` 宏定义程序，指定挂载类型和权限
2. **定义 Map**：使用 `DEFINE_BPF_MAP` 宏定义数据存储
3. **编译为 .o**：Clang 以 `-target bpf` 编译
4. **配置 Android.bp**：`bpf { name: "myprog.o", src: "myprog.c", ... }`
5. **bpfloader 加载**：系统启动时自动加载，固化到 `/sys/fs/bpf/`
6. **用户态消费**：通过 libbpf 或直接 syscall 读取 Map 数据

## 🔸 扩展点 3：企业级部署的工程挑战

### 采样策略与数据量控制

大规模设备部署时，eBPF 观测数据量是核心挑战：

- **事件级采集**：锁竞争事件、唤醒锁事件在繁忙系统上可能每秒数千次。策略：内核态预聚合（如 locks 已做的 sum/count/max/min），仅定期上报统计值
- **按需触发**：dmabufIter 的 BPF Iterator 设计天然支持按需读取——仅在需要时 `read()` 一次
- **采样率控制**：对于高频 tracepoints（如 sched_switch），可在 BPF 程序中实现基于 PID/UID 的过滤，只采集目标应用的数据

### 隐私与安全考量

- **权限隔离**：每个 BPF 程序在 `DEFINE_BPF_PROG` 中指定了加载 UID 和可读 UID，确保数据访问受控
- **数据脱敏**：上报数据按 UID 聚合，不包含具体内存地址或用户数据
- **SELinux 策略**：BPF 程序的加载和 Map 访问受 SELinux 策略约束

### 故障恢复

- **程序崩溃隔离**：eBPF 验证器保证程序不会导致内核 panic。即使 BPF 程序有 bug，最坏情况是该程序被 kill，不影响系统运行
- **自动重载**：bpfloader 在 init 阶段加载，如果加载失败会在系统日志中记录，但不会阻塞启动
- **Map 持久化**：固化在 `/sys/fs/bpf/` 的 Map 在程序重启后依然存在（如果设计为持久 Map），支持断点续采
