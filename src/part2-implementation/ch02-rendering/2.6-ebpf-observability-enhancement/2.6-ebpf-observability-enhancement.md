# 2.6 Android 17 eBPF 观测增强

Android 17 的 `platform/system/bpfprogs` 新增了四组值得关注的程序：

- `cyclePerUid.c`：按 UID 累计 CPU cycle；
- `dmabufIter.c`：按需枚举系统中的 DMA-BUF；
- `kernelwakelockduration/kernelWakelockDuration.c`：累计“至少存在一个 active kernel wakeup source”的时间；
- `locks/bpfLockContention.c`：统计一组指定内核锁的竞争时长。

四组程序覆盖 CPU、共享图形缓冲区、休眠阻塞和内核锁竞争，但它们没有组成一个统一的“Android 17 eBPF 监控系统”。挂载方式、输出载体、适用架构和消费方各不相同。理解这些差异，才能判断某个数据能回答什么问题。

本文的平台源码固定为 `android-17.0.0_r1`，内核源码固定为 `android17-6.18-2026-06_r6`。

## 1. 源码位置与能力边界

四组程序都在 Android 17 tag 的 [`platform/system/bpfprogs`](https://android.googlesource.com/platform/system/bpfprogs/+/refs/tags/android-17.0.0_r1) 仓库中。旧资料常写成 `system/bpf/progs`，该路径不能作为本版本的源码锚点。

| 程序 | attach 类型 | 输出 | Android 17 构建边界 |
|---|---|---|---|
| `cyclePerUid` | `tp_btf/sched_switch` | `LRU_PERCPU_HASH` 等 maps | `Android.bp` 仅为 x86_64 启用 |
| `dmabufIter` | `iter/dmabuf` | iterator 的 seq stream | RISC-V 禁用，加载另受 feature flag 控制 |
| `kernelWakelockDuration` | 两个 power raw tracepoint | 单元素 ARRAY map | 加载受 feature flag 控制 |
| `bpfLockContention` | 两个 lock tracepoint | 两个 HASH maps | RISC-V 禁用，加载另受 feature flag 控制 |

[`Android.bp`](https://android.googlesource.com/platform/system/bpfprogs/+/refs/tags/android-17.0.0_r1/Android.bp) 明确把 `cyclePerUid.bpf` 设为默认关闭，只在 `x86_64` 架构打开。其他三组程序是否出现在某个产品、是否已 attach，还要结合 [`progs.aconfig`](https://android.googlesource.com/platform/system/bpfprogs/+/refs/tags/android-17.0.0_r1/progs.aconfig)、产品配置和启动日志确认。AOSP tag 中存在源码，不等于每台 Android 17 设备都在运行它。

## 2. Android 的 BPF 程序怎样进入内核

Android 构建系统把 `libbpf_prog` 模块编译成 BPF object。[BPF loader](https://source.android.com/docs/core/architecture/kernel/bpf) 在启动阶段加载对象、创建 map，并将对象 pin 到 bpffs。`relative_install_path` 会让相关对象位于 `/sys/fs/bpf/` 的子目录，例如 `dmabuf`、`cpucycleperuid` 和 `lock_contention`。

从源码到可读数据要经过五个条件：

1. 产品构建包含对应 BPF object；
2. feature flag 允许加载；
3. 目标内核提供所需 program type、helper、BTF、tracepoint 或 iterator；
4. verifier 接受程序，attach 成功；
5. 用户态进程拥有 bpffs、map 或 iterator 的访问权限，并按正确格式消费。

[GKI](https://source.android.com/docs/core/architecture/kernel/generic-kernel-image) 缩小了内核差异，但没有消除这些条件。Android 12 起，使用 5.10 及以上内核出厂的设备需要采用 GKI；这不等于所有 Android 12 升级设备都使用同一内核，也不保证任意 BPF object 可以跨设备直接运行。BTF 类型、内核配置、可用 hook、vendor 模块和 SELinux 策略仍需核对。

## 3. `cyclePerUid`：x86_64 的 UID cycle 归因

[`cyclePerUid.c`](https://android.googlesource.com/platform/system/bpfprogs/+/refs/tags/android-17.0.0_r1/cyclePerUid.c) 在 `tp_btf/sched_switch` 上运行。每次上下文切换时，它读取当前 CPU 对应 perf event 的 counter，与该 CPU 上一次记录相减，再把差值计入换出任务所属 UID。

它使用的主要 map 如下：

| map | 类型 | 用途 |
|---|---|---|
| `last_recorded_cycle_map` | `PERCPU_ARRAY` | 保存每个 CPU 上一次 counter |
| `last_running_pid_map` | `PERCPU_ARRAY` | 检查换出 PID 是否与上次换入 PID 对应 |
| `uid_cpu_cycle_map` | `LRU_PERCPU_HASH` | 按 UID、按 CPU 累计 cycle |
| `tsc_events` | `PERF_EVENT_ARRAY` | 保存各 CPU 的 perf event fd |
| `desync_counter` | `PERCPU_ARRAY` | 记录 suspend/resume 等场景下的归因失配 |

程序跳过 idle task、首次样本和 PID 不连续的样本。`desync_counter` 因此是解释数据质量的一部分，不能只读取 UID 累计值。

用户态 [`libcycleperuid`](https://android.googlesource.com/platform/frameworks/native/+/refs/tags/android-17.0.0_r1/libs/cpucycleperuid/lib.rs) 负责：

- 为每颗 CPU 创建 TSC perf event；
- 填充 `tsc_events` map；
- attach `sched_switch` 程序；
- 汇总 per-CPU map；
- 读取 Intel RAPL package energy；
- 按各 UID 的 cycle 增量占比，分摊同一窗口的 package energy 增量。

因此，BPF 程序提供的是 cycle 计数。每 UID 能量值来自用户态按比例归因，不是硬件直接给出的“某 UID 耗电”。RAPL 路径和构建开关也说明这套实现面向 x86_64；不能把它套到 ARM big.LITTLE 设备。

这项数据适合回答“观测窗口内哪些 UID 消耗了更多 CPU cycle”。它不能区分同一 UID 内的主线程、RenderThread 和 worker，也不包含 GPU、内存控制器或显示硬件能量。

## 4. `dmabufIter`：全局 DMA-BUF 对象快照

[`dmabufIter.c`](https://android.googlesource.com/platform/system/bpfprogs/+/refs/tags/android-17.0.0_r1/dmabufIter.c) 定义 `iter/dmabuf` 程序。指定内核 tag 的 [`kernel/bpf/dmabuf_iter.c`](https://android.googlesource.com/kernel/common/+/refs/tags/android17-6.18-2026-06_r6/kernel/bpf/dmabuf_iter.c) 提供 iterator target，底层通过 [`dma_buf_iter_begin()` / `dma_buf_iter_next()`](https://android.googlesource.com/kernel/common/+/refs/tags/android17-6.18-2026-06_r6/drivers/dma-buf/dma-buf.c) 遍历全局 DMA-BUF 列表。

每个对象输出四个换行分隔字段：

1. inode；
2. `dma_buf::size`；
3. buffer name；
4. exporter name。

name 可以由用户空间提供，程序会把其中的换行替换为空格，避免破坏记录边界。无名称的 buffer 会输出空字符串。

这是一份读取时生成的对象快照。它没有长期保留 alloc/free 事件，也没有输出：

- 哪个进程当前持有 fd；
- importer 或 device attachment；
- SurfaceFlinger layer id；
- BufferQueue slot 和 frame number；
- acquire、release 或 present fence；
- GPU residency、压缩率和 IOMMU 映射；
- buffer 中的像素内容。

`size` 表示 DMA-BUF 对象声明的容量。把所有 `size` 相加可形成全局容量快照，但不能直接当作某应用的 PSS、GPU 驻留内存或某一帧的显存成本。

### 放回 Android 渲染链路理解

标准 HWUI、SurfaceView、TextureView、Camera、视频和 native graphics 都可能借助 DMA-BUF 在 producer、GPU、codec、SurfaceFlinger、HWC 与驱动之间共享 GraphicBuffer。`dmabufIter` 能告诉我们某时刻存在哪些共享对象，不能恢复对象在渲染管线里的角色。

渲染问题仍要按对象跟踪：

| 要回答的问题 | 主要证据 |
|---|---|
| 谁生产了本帧 | App/HWUI、Camera HAL、codec 或 native renderer 的 slice 与日志 |
| buffer 何时提交 | BufferQueue、BLAST transaction、frame number |
| Consumer 何时可读 | acquire fence |
| SurfaceFlinger 本轮用了哪块 buffer | layer trace、FrameTimeline、SurfaceFlinger trace |
| HWC 怎样合成 | composition type、validate/present、client target |
| buffer 何时可复用 | per-layer release fence |
| 共享对象总量是否异常 | `dmabufIter` 快照、进程 fd、exporter 与设备内存工具 |

例如，Camera 预览同时包含 HAL output、宿主 UI 和显示消费。DMA-BUF 数量增长只能说明共享对象积累；还需检查 `Image.close()`、BufferQueue 占用、HAL result、fence 与最终 layer，才能区分慢 Consumer、泄漏、GPU 等待和显示队列回压。

## 5. `kernelWakelockDuration`：active wakeup source 的并集时长

[`kernelWakelockDuration.c`](https://android.googlesource.com/platform/system/bpfprogs/+/refs/tags/android-17.0.0_r1/kernelwakelockduration/kernelWakelockDuration.c) attach 到：

- `raw_tp/wakeup_source_activate`；
- `raw_tp/wakeup_source_deactivate`。

指定内核 tag 的 [`power.h`](https://android.googlesource.com/kernel/common/+/refs/tags/android17-6.18-2026-06_r6/include/trace/events/power.h) 为两个事件提供 `name` 和 `state`。程序读取的是 `state` 中的 combined event counter：低位表示当前 active 数量，高位用于标记完成事件序列。

当 active 数量从 0 变为 1，程序从 `timer_state_ns` 减去当前 `bpf_ktime_get_boot_ns()`；当数量回到 0，再加回当前时间。结果是“系统至少有一个 kernel wakeup source active”的累计时间。

这个单值指标有明确限制：

- 不按 wakeup source name 分组；
- 多个 source 重叠时只计算一次；
- 不说明哪一个 source 阻止了 suspend；
- 不等同于应用持有 `PowerManager.WakeLock` 的时长；
- 不直接给出能量，active 期间的 CPU、外设和无线电状态仍需另查。

初始化逻辑还要处理 attach 前已存在 active source、跨 CPU 事件乱序和有限位宽 counter 回绕。阅读 map 时应使用对应用户态实现的语义，不能自行把内部字段当成绝对时间戳。

## 6. `bpfLockContention`：指定内核锁的进程级聚合

[`bpfLockContention.c`](https://android.googlesource.com/platform/system/bpfprogs/+/refs/tags/android-17.0.0_r1/locks/bpfLockContention.c) 使用指定内核 tag 中的 [`lock/contention_begin` 和 `lock/contention_end`](https://android.googlesource.com/kernel/common/+/refs/tags/android17-6.18-2026-06_r6/include/trace/events/lock.h)。

begin 事件把 `{tgid, tid, lock_name}` 到开始时间的映射写入 `contention_start_map`。end 事件找到并删除对应记录，再按 `{tgid, lock_name}` 更新：

- `sum`；
- `count`；
- `max`；
- `min`；
- 首次创建记录时的 `comm`。

程序只识别 [`bpf_lock_list.h`](https://android.googlesource.com/platform/system/bpfprogs/+/refs/tags/android-17.0.0_r1/locks/include/locks/bpf_lock_list.h) 列出的锁。范围包括 `tasklist_lock`、`cgroup_mutex`、`rtnl_mutex` 等全局符号，以及从当前 `task_struct` 可定位的 `mmap_lock`、`page_table_lock`、`pi_lock` 等动态锁。

以下对象不在这项统计中：

- Java monitor 和 Kotlin 协程等待；
- 普通 pthread mutex 的用户态快路径；
- 未进入 lock tracepoint 的 futex 等待；
- GPU driver 私有且未列出的锁；
- SurfaceFlinger、HWUI 或应用进程中的 C++ mutex。

`sum` 和 `count` 使用原子加法。源码对 `min`、`max` 的注释是“racy but simpler updates”，所以它们在并发更新下不具备严格统计保证。原稿所写的 CAS 循环与 Android 17 源码不符。

## 7. 与 Perfetto 联合分析

这四组程序都没有 ring-buffer map。`cyclePerUid`、`kernelWakelockDuration` 和 `bpfLockContention` 主要保留聚合值，`dmabufIter` 返回读取时的 seq stream。它们也没有自动注册成 Perfetto data source。

联合分析可以采用“时间线 + 前后快照”：

1. 记录复现开始时的 BPF map 或 iterator 快照；
2. 采集 Perfetto 的 sched、CPU frequency/idle、power、Binder、FrameTimeline、SurfaceFlinger、应用 slice 和目标设备可用的 GPU/thermal 数据；
3. 记录复现结束时的 BPF 快照；
4. 对累计值做差，并保留开始、结束时刻；
5. 用 Perfetto 定位窗口内的线程、帧和系统状态，再用 BPF 差值补充 UID、DMA-BUF、kernel wakeup source 并集或指定内核锁证据。

下面的命令用于确认设备是否包含相应 bpffs 子目录和加载日志：

```bash
adb shell su 0 ls -l /sys/fs/bpf/dmabuf
adb shell su 0 ls -l /sys/fs/bpf/cpucycleperuid
adb shell su 0 ls -l /sys/fs/bpf/lock_contention
adb shell su 0 logcat -d -b all | grep -i bpf
```

这些命令需要 root 或测试镜像权限；量产 user build 通常不允许 shell 直接读取系统 BPF 对象。目录不存在时，应继续检查产品构建、feature flag、BPF loader 日志与内核能力，不能只归因于 SELinux。

聚合数据无法恢复单次事件的顺序。若目标是分析某次 `mmap_lock` 等待与某个掉帧的先后关系，还需要 ftrace/Perfetto lock 事件、调度事件或专门的事件流采集。

## 8. 开销与数据质量

eBPF 把过滤和聚合放在内核事件路径，常能减少用户态采集与传输，但没有“零开销”保证。

- `cyclePerUid` 在每次 context switch 上读取 perf counter 并更新 map，频率很高；
- `bpfLockContention` 只处理发生竞争且命中白名单的锁，map 容量是 4096；
- `kernelWakelockDuration` 每次 wakeup source activate/deactivate 都执行初始化或累计逻辑；
- `dmabufIter` 平时不遍历，读取时要扫描当时的全局对象。

上线前应分别测量关闭与开启状态下的 CPU time、context-switch 成本、map 内存、丢失/失配计数和业务指标。map 满、LRU 淘汰、attach 失败、字段竞态和采集窗口不完整都可能让结果偏小或失真。

## 9. 开发与部署边界

AOSP 的系统 BPF 程序由平台构建、BPF loader、SELinux 和专用用户态库共同管理。普通三方应用不能把桌面 Linux 上的 `bpftrace` 工作流直接搬到量产 Android 设备。

开发新的平台程序时需要同步处理：

- `libbpf_prog` 构建项与 install path；
- program/map 的 owner、group 和访问模式；
- feature flag 与产品打包；
- kernel config、BTF、tracepoint/iterator/helper 版本；
- verifier 约束和失败日志；
- SELinux policy；
- map 生命周期、版本迁移和用户态解析；
- 采集开销、容量与数据清理；
- CTS/VTS、设备测试和 kernel 兼容性。

pin 到 bpffs 的 map 可以跨用户态 consumer 重启继续存在，但不会跨设备重启自动保留数据。对象是否复用、是否由 loader 重新创建，取决于启动加载与 map 定义兼容性。

## 10. 版本演进

| 版本 | 可核对结论 |
|---|---|
| Android 12 / API 31 | 平台已有 BPF loader、网络与 CPU time-in-state 等用途；[官方 BPF 文档](https://source.android.com/docs/core/architecture/kernel/bpf)中还记录了 `gpu_mem` 的进程/GPU 内存统计 |
| Android 13—16 | BPF 基础设施持续使用；本节四组文件在各版本 `r1` tag 中尚未出现 |
| Android 17 / API 37 | `system/bpfprogs` 的 `r1` tag 同时包含本节四组实现及相关构建项 |

版本表只描述可从 tag 验证的源码差异。某项程序进入 AOSP、被产品打包、默认启用和被用户态消费，可能处在不同时间点。

## 11. 排障结论应落在哪一层

| 观测结果 | 可以支持 | 仍需补充 |
|---|---|---|
| 某 UID cycle 增量高 | x86_64 上该 UID 的 CPU cycle 占比较高 | 线程、调用栈、频率、GPU 与能量模型 |
| DMA-BUF 总容量增长 | 全局共享 buffer 对象在积累 | fd 持有者、producer/consumer、fence、layer 和 exporter 语义 |
| kernel wakelock duration 增长 | 窗口内长期存在 active kernel wakeup source | source 名称、suspend 轨迹、CPU/外设活动 |
| `mmap_lock` 聚合时长高 | 某进程命中了所监控内核锁的竞争 | 单次事件、持锁方、调用栈与帧时间线 |

对渲染问题，BPF 指标是旁证。单帧结论仍需沿 producer → buffer queue → acquire fence → SurfaceFlinger layer → composition → present/release fence 检查，避免用全局内核统计替代帧级因果证据。
