# 2.30 Android 17 FrameTimeline GPU/CPU 合成边界判定机制

## 概述

FrameTimeline 是 Android 12 引入的系统级帧时间线追踪框架，在 SurfaceFlinger 和 App 进程之间建立了一套精确的帧耗时度量体系。到 Android 17，FrameTimeline 已经成为诊断渲染性能问题的核心工具——它能定位帧卡在 App 侧还是 SurfaceFlinger 侧。

下面聚焦 FrameTimeline 的数据模型（proto 定义与 trace_processor 表结构）、GPU/CPU 合成边界判定机制，以及如何利用这些信息进行渲染性能分析。与 2.4 节（Choreographer 与渲染流水线）关注 App 侧帧调度不同，本章从 **SurfaceFlinger 合成视角** 分析帧的完整生命周期。

## FrameTimeline 数据模型

### Perfetto proto 定义：两层数据源

Android 17 的 FrameTimeline 数据通过两个独立的 Perfetto proto 定义，分别对应 buffer/fence 事件和帧时间线 slice：

**GraphicsFrameEvent（buffer/fence 事件层）**

定义于 `external/perfetto/protos/perfetto/trace/android/graphics_frame_event.proto`。核心枚举 `BufferEventType` 定义了 buffer 在管线中的每一次状态迁移：

| BufferEventType | 含义 | 发射时机 |
|-----------------|------|---------|
| `DEQUEUE` | App 从 BufferQueue 取出空 buffer | `dequeueBuffer()` 调用 |
| `QUEUE` | App 填完内容后 buffer 入队 | `queueBuffer()` 调用 |
| `POST` | Buffer 从 BufferQueue 移交 SurfaceFlinger | BLASTBufferQueue 提交时 |
| `ACQUIRE_FENCE` | 等待 GPU 渲染完成的 fence 信号 | RenderThread 完成绘制后 fence signal |
| `LATCH` | SurfaceFlinger 选中该 buffer 作为本帧内容 | `Layer::latchBuffer()` |
| `HWC_COMPOSITION_QUEUED` | HWC 将合成该 buffer（proto 枚举保留） | Android 17 源码中未找到活跃发射点，判读时不要假设一定出现 |
| `FALLBACK_COMPOSITION` | 该 layer 进入 RenderEngine/客户端合成 | `Layer::onCompositionPresented()` 检测到 `requiresClientComposition()` |
| `PRESENT_FENCE` | Display present fence signal | 硬件 vsync + present 完成 |
| `RELEASE_FENCE` | Buffer 释放回 BufferQueue，App 可复用 | release fence signal |
| `MODIFY` | Buffer 元数据或状态修改 | BufferQueue 状态更新 |
| `DETACH` | Buffer slot 脱离队列 | detach buffer |
| `ATTACH` | Buffer slot 重新挂接队列 | attach buffer |
| `CANCEL` | 已 dequeue 的 buffer 被取消 | cancel buffer |

`GraphicsFrameEvent` 由 SurfaceFlinger 的 `FrameTracer`（`frameworks/native/services/surfaceflinger/FrameTracer/FrameTracer.cpp`）发射，按 buffer 粒度追踪。

以上枚举为 android-17.0.0_r1 proto 完整定义。Perfetto UI 可能在 track 上使用简化的显示名（如"App BufferDropped""SF Composing"），但这些是 UI 层的标注名，不是 proto 的事件名称。

**FrameTimelineEvent（帧时间线 slice 层）**

定义于 `external/perfetto/protos/perfetto/trace/android/frame_timeline_event.proto`。该 proto 提供两类帧级 slice：

| Slice 类型 | 子类型 | 含义 |
|-----------|--------|------|
| `DisplayFrame` | `ExpectedDisplayFrameStart` / `ExpectedDisplayFrameEnd` | SurfaceFlinger 预期的显示帧起止（由 VSync 周期、offset 和合成预算决定） |
| `DisplayFrame` | `ActualDisplayFrameStart` / `ActualDisplayFrameEnd` | 实际帧完成合成的起止时刻 |
| `SurfaceFrame` | `ExpectedSurfaceFrameStart` / `ExpectedSurfaceFrameEnd` | App 侧预期帧起止（由 VSync-app + offset 决定） |
| `SurfaceFrame` | `ActualSurfaceFrameStart` / `ActualSurfaceFrameEnd` | App 实际完成渲染并提交的起止时刻 |

在 Perfetto UI 中，Expected/Actual DisplayFrame 和 SurfaceFrame 分别展示为 **Expected Timeline** 和 **Actual Timeline** 两条 track。UI 层可能进一步将 DisplayFrame slice 标注为"SF Composing""SF Presenting"、将 SurfaceFrame slice 标注为"App → SF""VSYNC-app"等，但这些属于 Perfetto UI 的渲染层标注，不是 proto 中的一级事件类型。

### SurfaceFrame 与 DisplayFrame 的 token 关联

App 到 SurfaceFlinger 的帧关联通过帧 token 完成：

1. App 侧 `Choreographer` 在 VSync 回调中接收 `DisplayEventReceiver.VsyncEventData`，并选择 preferred `FrameTimeline` / `vsyncId`
2. `Choreographer.FrameTimeline`（`Choreographer.java` 内部类）通过 `getVsyncId()` 暴露当前帧的 vsyncId
3. SurfaceFlinger 的 `FrameTimeline::createSurfaceFrameForToken(FrameTimelineInfo, ...)` 根据该 vsyncId 创建 `SurfaceFrame`
4. `SurfaceFrame.display_frame_token` 字段指向对应的 `DisplayFrame`
5. `DisplayFrame` 后续由 `setSfWakeUp()`、`setSfPresent()` 等方法标记 SF 侧的关键时间点

这条链使得 Perfetto UI 能把 App 侧 `Choreographer#doFrame` 的 slice 和 SF 侧的合成/上屏 slice 精确关联到同一帧。

### 双数据源协同工作机制

FrameTimeline 相关 trace 由三路信号组成：

- **`android.surfaceflinger.frametimeline`** 数据源：由 SurfaceFlinger 注册，报告 `FrameTimelineEvent`（DisplayFrame / SurfaceFrame 的 Expected/Actual slice）
- **`android.surfaceflinger.frame`** 数据源：由 SurfaceFlinger 的 `FrameTracer` 注册，报告 `GraphicsFrameEvent`（buffer/fence 事件）
- **`view` / `gfx` atrace category**：由 App 进程中的 `ViewRootImpl` / `Choreographer` 等代码写入，报告 `Choreographer#doFrame`、`measure`、`layout`、`draw` 等 slice；它们不是独立的 Perfetto data source

`FrameTimelineEvent` 通过 `DisplayFrame.token = SurfaceFrame.display_frame_token` 关联 SF 与 App 的帧时间线。在 Perfetto UI 中，这种关联使得开发者可以在同一条时间线上看到：
- App 侧 `Choreographer#doFrame` 的开始和结束
- 对应 buffer 在 SurfaceFlinger 侧的合成 slice
- 最终的 display present 时刻

### 版本演进时间线

| 版本 | 主要变化 |
|------|---------|
| **Android 12 (API 31)** | FrameTimeline 首次引入，SurfaceFlinger 开始报告 Expected/Actual Timeline |
| **Android 13 (API 33)** | `Choreographer.FrameData` API 公开，App 可查询帧调度计划；SurfaceFlinger 主循环重构为 `commit`/`composite` |
| **Android 14 (API 34)** | FrameTargeter / Pacesetter 引入，重构了 VSync 调度和帧目标管理 |
| **Android 15 (API 35)** | FrameTimeline SQL 标准库增强，Perfetto 中新增 Jank CUJ 分析模块 |
| **Android 16 (API 36)** | 多显示器场景下 FrameTimeline 的 per-display 追踪完善 |
| **Android 17 (API 37)** | FrameTimeline 代码迁入 `Scheduler/FrameTimeline.{h,cpp}`，与 FrameRateOverrides 整合，支持自适应刷新率场景的帧时间线追踪 |

## GPU/CPU 合成边界判定机制

### 合成方式的本质区别

SurfaceFlinger 在合成每一帧时，需要决定使用哪种合成路径：

- **设备合成（Device Composition / HWC）**：将 layer 的 buffer 直接传递给硬件合成器（HWC），由显示控制器硬件完成图层叠加。不消耗 GPU 算力，功耗更低。
- **客户端合成（Client Composition / GPU）**：SurfaceFlinger 调用 RenderEngine（GLES/Vulkan）将所有 layer 渲染合成到一个 framebuffer 中，再将合成结果传递给 HWC。消耗 GPU 算力。

> 详见 2.6 节 SurfaceFlinger 与合成中关于 Client/Device 合成的原理阐述。

### HWC 合成决策算法

SurfaceFlinger 在每次 `composite()` 时执行以下决策流程：

```
1. 遍历所有可见 Layer，收集合成需求
2. 调用 HWC::validateDisplay() 将 layer 列表提交给 HWC
3. HWC 返回每个 layer 的合成类型建议（DEVICE / CLIENT / SOLID_COLOR...）
4. 如果 HWC 建议的 CLIENT 合成 layer 过多（超过 HWC 的 overlay 数量上限），
   SurfaceFlinger 将部分 layer 改为 GPU 合成
5. SurfaceFlinger 根据 HWC 的反馈执行：
   - 全部 DEVICE → 直通模式（HWC 直接合成，SF 无需 GPU 参与）
   - 混合模式 → GPU 先合成 CLIENT layers，结果作为一个 layer 给 HWC
   - 全部 CLIENT → GPU 全量合成
```

### gpu_composition 标志位的判定逻辑：SurfaceFrame 与 DisplayFrame 两条路径

在 Perfetto trace 中，FrameTimeline 的 `gpu_composition` 标志按 SurfaceFrame 和 DisplayFrame 两个层级分别写入，判定逻辑不同。

**SurfaceFrame 的 gpu_composition（layer 粒度）**

```cpp
// Layer::onCompositionPresented(const CompositionRefreshArgs&, const DisplayDevice&)
// frameworks/native/services/surfaceflinger/Layer.cpp
if (outputLayer->requiresClientComposition()) {
    // 该 layer 走了 GPU 合成路径，向 FrameTimeline 报告
    mSurfaceFrame->setGpuComposition();
    // 同时写入 FALLBACK_COMPOSITION 事件（本应 HWC 合成但退回了 GPU）
    mFrameTracker->setFallbackCompositionFrame(outputLayer);
}
```

判定条件：`requiresClientComposition()` 为 true → SurfaceFrame 标记 `gpu_composition = true` → 写入 `FALLBACK_COMPOSITION`。一条 layer 走了 GPU 合成，它在整个帧中对应的 `SurfaceFrame` 就被标注 gpu_composition。

**DisplayFrame 的 gpu_composition（帧粒度）**

```cpp
// SurfaceFlinger::onCompositionPresented()
// frameworks/native/services/surfaceflinger/SurfaceFlinger.cpp
if (display && display->getState().usesClientComposition) {
    gpuCompositionDoneFences.try_emplace(
        id, display->getRenderSurface()->getClientTargetAcquireFence());
}
mFrameTimeline->setSfPresent(
    presentTime.ns(), pacesetterPresentFenceTime,
    pacesetterGpuCompositionDoneFenceTime);

// FrameTimeline::DisplayFrame::traceActuals()
// Scheduler/FrameTimeline.cpp
actualDisplayFrameStartEvent->set_gpu_composition(
    mGpuFence != FenceTime::NO_FENCE);
```

DisplayFrame 的判定不看单个 layer，而是检查本帧合成过程中是否产生了 GPU composition done fence。只要任意一个 layer 走了 GPU 合成，该 fence 就存在，DisplayFrame 的 `gpu_composition` 就为 `true`。

**判据总结**：
- `gpu_composition = false`：本帧所有 layer 均由 HWC 硬件合成，SurfaceFlinger 不需要走 RenderEngine 合成
- `gpu_composition = true`：本帧至少有一个 layer 走了 GPU 合成路径，需要关注 GPU 负载

### HWC_COMPOSITION_QUEUED 事件的边界

`HWC_COMPOSITION_QUEUED` 是 `GraphicsFrameEvent.BufferEventType` 的枚举值之一，但在 android-17.0.0_r1 的 `FrameTracer.cpp`、`Layer.cpp` 与 `CompositionEngine/` 路径中，本轮未找到对该枚举的活跃发射点。它不是 FrameTimelineEvent 的子类型，也不应作为判断 HWC 合成路径时必然存在的 trace 事件。

在 Android 17 上判断 HWC / GPU 合成路径，应优先结合三类证据：

- `Layer::onCompositionPresented()` 是否因 `requiresClientComposition()` 发射 `FALLBACK_COMPOSITION`
- `DisplayFrame::traceActuals()` 中的 `gpu_composition` 是否为 true
- Layer trace / HWC dump 中的 output layer composition type

### RELEASE_FENCE 发射点分析

Release fence 是 SurfaceFlinger 在合成完成后释放 buffer 给 App 的同步信号。在 Android 17 中，release fence 的主要发射点：

1. **HWC 合成路径**：`Display::presentFrame()` 调用 `HWComposer::presentAndGetReleaseFences()`，随后通过 `getLayerReleaseFence()` 读取每个 HWC layer 的 release fence；present fence 与 release fence 是两类信号
2. **GPU 合成路径**：当 output 使用 client composition 时，`Output::presentFrameAndReleaseLayers()` 会把 HWC layer release fence 与 RenderSurface 的 client target acquire fence 合并为 layer release fence
3. **BLASTBufferQueue 回收**：App 侧的 BLASTBufferQueue 在收到 release fence signal 后，才回收该 buffer slot 供下次绘制使用

release fence 的时序直接影响 App 的 buffer 可用性：
- 如果 release fence 延迟到达，App 的 BufferQueue 可能耗尽（buffer starvation），导致丢帧
- FrameTimeline 中可以通过对比 Actual Timeline 的结束时间和下一帧 Expected Timeline 的开始时间来检测 buffer starvation

> 具体的 fence 超时阈值在不同 OEM 设备上可能有所不同。

## 渲染管线性能分析

### Frame Pacing 的量化分析

FrameTimeline 提供了帧节奏（frame pacing）的精确量化：

- **Expected Display Time**：帧预期上屏的时刻。由 VSync 周期、VSync offset 和 SurfaceFlinger 合成预算共同决定。
- **Actual Display Time**：帧实际被上屏的时刻（由 display present fence 标记）。
- **帧延迟（Frame Latency）** = Actual Display Time - Expected Display Time

当帧延迟 > 0 时，表示该帧"迟到"了，用户可能感知到卡顿。

### Jank 归因：App 侧 vs SF 侧

FrameTimeline 可以精确归因 jank 责任方：

| Perfetto 颜色编码 | 含义 | 卡顿来源 | 判定条件 |
|------------------|------|--------|---------|
| 🟢 绿色 | 帧准时完成 | — | Actual ≤ Expected |
| 🔴 红色 | App 侧导致卡顿 | App | App 侧帧渲染超时（`Choreographer#doFrame` 耗时过长或 RenderThread 延迟） |
| 🟡 黄色 | SF 侧导致卡顿 | SurfaceFlinger | SF 合成延迟（`composite()` 耗时过长、GPU 合成排队、HWC 响应慢） |

**App 侧卡顿的典型原因**：
- 主线程耗时操作（I/O、反序列化、复杂计算）阻塞了 `Choreographer#doFrame`
- View 层级过深导致 `measure`/`layout`/`draw` 超时
- RenderThread 的 GPU 指令提交延迟

**SF 侧卡顿的典型原因**：
- GPU 合成负载过高（大量半透明 layer 叠加、复杂 shader 效果）
- HWC HAL 响应延迟（低质量 HWC 实现）
- SurfaceFlinger 主线程被其他事务（Transaction）阻塞

### GPU 合成与 HWC 合成的性能差异

在分析渲染性能时，两种合成路径的性能特征差异显著：

```
场景 A：全部 HWC 合成（最优路径）
App 渲染 → HWC 直接合成（延迟极低，通常 < 1ms）→ Display

场景 B：GPU 合成参与（常见路径）
App 渲染 → RenderEngine GPU 合成（延迟因合成复杂度和 GPU 负载而异）→ HWC 最终合成 → Display
```

**触发 GPU 合成的常见因素**：
- Layer 带有圆角、阴影、模糊等效果（需要 shader 处理）
- Layer 的 pixel format 不被 HWC 支持
- Layer 数量超过 HWC 的 overlay 数量上限（通常 4-8 个，取决于硬件）
- Layer 缩放比例超出 HWC 的缩放能力范围

> 上述耗时取决于设备和刷新率，具体数值需要在目标设备上实测。

## 实际应用案例分析

### 案例一：列表滑动卡顿的 FrameTimeline 诊断

**场景**：RecyclerView 列表滑动，偶发性掉帧。

**FrameTimeline 分析步骤**：

1. **抓取 Perfetto trace**：正式分析必须用 pbtxt 显式包含 `android.surfaceflinger.frametimeline`、`android.surfaceflinger.frame` 以及 `view/gfx` atrace category。下面的短命令只适合作为 App 与调度辅助轨的快速入口，不能单独证明 FrameTimeline 数据完整。
```bash
adb shell perfetto -o /data/misc/perfetto-traces/trace.perfetto-trace -t 10s \
  sched freq idle am wm gfx view binder_driver hal
```

2. **打开 Perfetto UI**（ui.perfetto.dev），加载 trace 文件

3. **定位红色 slice**：在 Actual Timeline track 中找到红色（App jank）帧

4. **查看该帧的 App 侧详情**：
   - 展开 `Choreographer#doFrame` slice
   - 检查 `measure`、`layout`、`draw` 各子 slice 耗时
   - 如果 `measure` 耗时异常，可能是 View 层级过深
   - 如果 `draw` 耗时异常，可能是 RenderThread 的 GPU 指令过多

5. **检查 buffer 状态**：查看该帧前后的 BufferQueue 是否出现 buffer starvation（所有 buffer 都处于 DEQUEUED/QUEUED 状态，无可用 buffer）

**典型诊断结论**：如果 `measure` 耗时导致 jank，优化方向是扁平化 View 层级（使用 ConstraintLayout 或 Compose）。

### 案例二：游戏画面撕裂与帧节奏不一致

**场景**：游戏使用 SurfaceView 渲染，在高刷新率设备上出现画面撕裂。

**FrameTimeline 分析**：

游戏通常使用 `Choreographer.FrameData`（API 33+）来获取帧调度信息：

- `Choreographer.FrameData.getFrameTimeNanos()`：当前帧的 VSync 时间
- `Choreographer.FrameData.getFrameTimelines()`：返回 `FrameTimeline[]`，每个 `FrameTimeline` 提供 `getVsyncId()`、`getExpectedPresentationTimeNanos()`、`getDeadlineNanos()`
- `Choreographer.FrameData.getPreferredFrameTimeline()`：返回首选的 `FrameTimeline`

帧间隔信息通过相邻两帧的 `getFrameTimeNanos()` 差值计算，或从 `DisplayMode` 的刷新周期推导。

通过对比 FrameTimeline 中 Expected Timeline 的 `ExpectedSurfaceFrameStart` 和 Actual Timeline 的 buffer 提交时间，可以判断：
- 如果 Actual 明显早于 Expected：游戏在 VSync 之前就提交了 buffer（pacing 策略错误）
- 如果 Actual 延迟多个 VSync 周期：渲染管线耗时过长，需要降低画质或使用 Frame Pacing Library

**主要指标**：
- `FrameRate` / `RefreshRate` 匹配度
- `PresentLatency`（从渲染到上屏的延迟）
- `Jank percentage`（红色帧占比）

### 案例三：复杂半透明 UI 的 GPU 合成瓶颈

**场景**：应用使用多层半透明 overlay + 模糊效果，导致 GPU 合成成为瓶颈。

**FrameTimeline 诊断**：

1. 在 Perfetto trace 中检查 Actual Timeline slice 的 `gpu_composition` 标志
2. 如果大量帧的 `gpu_composition = true`，说明 HWC 无法处理这些 layer，退化为 GPU 合成
3. 检查 SurfaceFlinger track 中的合成 slice 耗时，如果超过该刷新率下的帧预算，GPU 合成就是瓶颈

**优化方向**：
- 减少同时可见的半透明 layer 数量
- 使用 `ColorMatrix` 替代 shader 效果（部分 HWC 支持）
- 评估是否可以使用 `SurfaceView` 的 hardware overlay 来绕过 GPU 合成

## 调试与监控工具

### Perfetto FrameTimeline 可视化分析方法

**基本流程**：

1. **抓取 trace**：确保包含 `android.surfaceflinger.frametimeline`、`android.surfaceflinger.frame` 与 `view/gfx` atrace category
2. **在 Perfetto UI 中定位 FrameTimeline tracks**：
   - Expected Timeline track：绿色/红色/黄色的帧 slice
   - Actual Timeline track：对应 App 侧和 SF 侧的实际帧数据
3. **颜色编码**：
   - 🟢 绿色 = 帧准时（无 jank）
   - 🔴 红色 = App 导致的 jank
   - 🟡 黄色 = SurfaceFlinger 导致的 jank
4. **深度分析**：点击某个红色/黄色 slice，查看其 annotated metadata（frame token、gpu_composition 标志、layer 列表等）

### Perfetto SQL 查询：批量分析帧数据

Perfetto v54+ 提供了 FrameTimeline 相关的 SQL 表，支持批量分析。主要表结构：

**基础查询：统计 jank 类型分布**

```sql
-- 统计 FrameTimeline 已解析的 jank 类型分布
-- jank_type 在 proto 中是 bitmask；trace_processor 表中已经展开成可读标签
SELECT
  actual.jank_type,
  actual.present_type,
  COUNT(*) AS frame_count,
  AVG(actual.dur) AS avg_duration_ns
FROM actual_frame_timeline_slice actual
GROUP BY actual.jank_type, actual.present_type
ORDER BY frame_count DESC;
```

**Perfetto Android stdlib 示例**：

```sql
-- 每帧 overrun / jank 统计
INCLUDE PERFETTO MODULE android.frames.per_frame_metrics;

SELECT
  was_jank,
  COUNT(*) AS frame_count,
  AVG(overrun) AS avg_overrun_ns
FROM android_frame_stats
GROUP BY was_jank;
```

```sql
-- SystemUI / 应用 CUJ 边界与帧数量
INCLUDE PERFETTO MODULE android.cujs.base;

SELECT
  cuj_name,
  state,
  dur,
  begin_vsync,
  end_vsync
FROM android_jank_cuj
ORDER BY dur DESC;
```

以上表名以 Perfetto 官方 stdlib 文档和 android-17.0.0_r1 `external/perfetto` 为准；不要把未进入 stdlib 的实验表名写成可直接执行 SQL。

### Perfetto Data Explorer（v54+）

Perfetto v54 引入的 Data Explorer 提供了无代码可视化分析界面，通过连接节点构建分析管线：

1. 选择数据源（如 `actual_frame_timeline_slice` 表）
2. 添加变换节点（如 filter、aggregate、join）
3. 实时查看交互式表格结果

这对不熟悉 SQL 的开发者特别有用，可以快速进行帧数据分析。

## 兼容性与迁移

### Android 12 前后的差异

| 方面 | Android 11 及以下 | Android 12+ |
|------|------------------|-------------|
| 帧追踪 | FrameMetrics API（仅 App 侧数据） | FrameTimeline（App + SF 完整流程） |
| Jank 检测 | Systrace 中的 Frame segment | Perfetto Expected/Actual Timeline |
| SF 主循环 | `onMessageReceived` (INVALIDATE/REFRESH) | `commit` / `composite`（Android 13+） |
| VSync 模型 | 固定 VSync offset | 可配置 VSync offset + FrameTargeter（Android 14+） |

### 应用层适配建议

1. **Android 13 (API 33) 适配**：使用 `Choreographer.FrameData` API 获取帧调度计划，替代手动 VSync 时间估算
2. **Android 14 (API 34) 适配**：FrameTargeter 引入后，`getPreferredFrameTimeline()` 返回的时间线可能动态变化，App 应响应 deadline 变化
3. **Perfetto trace 抓取**：确保 trace 配置包含 `android.surfaceflinger.frametimeline`、`android.surfaceflinger.frame` 与 `gfx/view` atrace category，否则 FrameTimeline 数据不完整
4. **线上监控**：使用 Jetpack JankStats 库进行运行时 jank 检测，不依赖 Perfetto trace 抓取

### 性能回归检测方案

建议在 CI/CD 流水线中集成 Perfetto trace 分析：

1. **自动化 trace 抓取**：在 UI 自动化测试期间持续抓取 Perfetto trace
2. **SQL 批量分析**：使用 Perfetto SQL 标准库的 weighted jank metrics 计算帧节奏质量评分
3. **基线对比**：将当前版本的 jank 指标与基线版本对比，超过阈值则报警
4. **Per-CUJ 分析**：使用 Perfetto v54 的 Jank CUJ 模块按用户交互场景（滚动、动画、过渡）分别评估

## 扩展

### 源码深度解析：FrameTimeline.cpp 核心方法

FrameTimeline 的核心实现位于 `frameworks/native/services/surfaceflinger/Scheduler/FrameTimeline.{h,cpp}`（Android 17 主线）。关键方法：

- `createSurfaceFrameForToken(FrameTimelineInfo, ownerPid, ownerUid, layerId, ...)`：为 App 侧的 vsyncId 创建 `SurfaceFrame`，建立 App→SF 的帧关联
- `setSfWakeUp(token, wakeUpTime, refreshRate, renderRate, displayState)`：记录 SurfaceFlinger 被 VSync 唤醒的时刻
- `setSfPresent(sfPresentTime, presentFence, gpuFence)`：记录 SurfaceFlinger 完成合成并提交给 HWC present 的时刻
- `onCommitNotComposited()`：记录某帧的 commit 被放弃（未进入合成）
- `finalizeCurrentDisplayFrame()`：关闭当前 DisplayFrame，将所有统计信息写入 Perfetto trace buffer

`FrameTracer`（`frameworks/native/services/surfaceflinger/FrameTracer/FrameTracer.cpp`）是向 Perfetto 发射 `GraphicsFrameEvent`（buffer/fence 事件）的桥接层，通过 `perfetto::Trace` API 将 buffer 级的 DEQUEUE/QUEUE/POST/LATCH/RELEASE_FENCE 等事件写入 trace buffer。

### Choreographer 与 FrameTimeline 协同机制

Choreographer 在 App 侧通过以下机制与 FrameTimeline 协同：

1. **帧调度请求**：`FrameDisplayEventReceiver` 收到 `VsyncEventData` 后更新 `FrameData`，再通过 `getPreferredFrameTimeline()` 选择当前帧的预期时间线
2. **帧完成报告**：`Choreographer.doFrame()` 结束后，`ViewRootImpl` 将帧完成信息通过 `FrameCallback` 和 `FrameMetrics` 回调上报
3. **Deadline 感知**：Android 14+ 的 FrameTargeter 会动态调整帧 deadline，`Choreographer.FrameTimeline` 内部类通过 `getDeadlineNanos()` 暴露当前帧的截止时间

`Choreographer.FrameTimeline` 是 `Choreographer.java` 的内部类（定义于 `frameworks/base/core/java/android/view/Choreographer.java`，Android 12+ 引入），App 侧不存在独立的 `android.view.FrameTimeline` 顶层类。

详见 2.4 节 Choreographer 与渲染流水线。

### 不同 GPU 架构下的 FrameTimeline 表现差异

不同 GPU / HWC / OEM 组合会影响 FrameTimeline 数据完整性，但不能只按 GPU 品牌下结论：

- GPU 合成完成信号在 Android 17 中以 RenderSurface 的 client target acquire fence 进入 `SurfaceFlinger::onCompositionPresented()`
- HWC layer release fence 通过 `HWComposer::presentAndGetReleaseFences()` / `getLayerReleaseFence()` 进入 CompositionEngine
- 如果某类 fence 或 composition type 缺失，需要先检查 OEM 的 SurfaceFlinger / HWC 集成，而不是直接归因到 GPU 架构

### OEM 定制 ROM 兼容性处理

OEM 对 SurfaceFlinger 的定制可能影响 FrameTimeline 数据质量：

1. **HWC 实现差异**：部分 OEM 的 HWC 实现可能不完整报告合成类型，导致 `gpu_composition` 标志不准
2. **VSync offset 定制**：OEM 可能调整 VSync offset 参数，Expected Timeline 的绝对时间在不同设备上不可直接对比
3. **自定义合成路径**：部分 OEM 引入了自定义的合成加速路径，可能不通过标准 FrameTimeline 报告

建议在性能基准测试中标注设备型号和 Android 版本。
