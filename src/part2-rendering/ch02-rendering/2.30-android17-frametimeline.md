# 2.30 Android 17 FrameTimeline GPU/CPU 合成边界判定机制

## 概述

FrameTimeline 是 Android 12 引入的系统级帧时间线追踪框架，它在 SurfaceFlinger 和 App 进程之间建立了一套精确的帧耗时度量体系。到 Android 17，FrameTimeline 已经成为诊断渲染性能问题的核心工具——它不仅能告诉你"卡了"，还能精确地告诉你"卡在哪一层"。

本章聚焦 FrameTimeline 的数据结构演进、GPU/CPU 合成边界判定机制，以及如何利用这些信息进行渲染性能分析。与 2.4 节（Choreographer 与渲染流水线）关注 App 侧帧调度不同，本章从 **SurfaceFlinger 合成视角** 分析帧的完整生命周期。

## FrameTimeline 数据结构演进

### FrameTracer 的六类 Trace 事件

SurfaceFlinger 中的 `FrameTracer`（`frameworks/native/services/surfaceflinger/FrameTracer.cpp`）负责向 Perfetto 发射帧级别的 trace 事件。Android 17 中共定义了六类核心 trace 事件：

| 事件名称 | Perfetto Track | 含义 | 发射时机 |
|----------|---------------|------|---------|
| `BufferQueuePosts` | Expected Timeline | Buffer 入队时刻 | App 通过 BLAST BufferQueue 提交 buffer 时 |
| `App BufferDropped` | Actual Timeline | App 丢帧标记 | buffer 被 drop 而非 display 时 |
| `SF Composing` | SurfaceFlinger | SF 合成持续时间 | SurfaceFlinger `composite()` 开始/结束 |
| `SF Presenting` | SurfaceFlinger | 上屏时刻 | display present fence signal 时 |
| `GPU Composition` | GPU Track | GPU 合成耗时 | RenderEngine 执行 GPU 合成时 |
| `HWC Composition` | HWC Track | HWC 合成标记 | HWC 设备合成完成时 |

[已验证: AOSP android-17.0.0_r1, frameworks/native/services/surfaceflinger/FrameTracer.cpp]

### FrameTimeline 五类子消息

FrameTimeline 在 Perfetto 中通过 **Expected Timeline** 和 **Actual Timeline** 两条 track 呈现，每条 track 内部包含五类子消息（slice 的 annotated name）：

**Expected Timeline 子消息**：
1. **VSYNC-app**：App 的 VSync 唤醒时刻（考虑了 VSync offset 后的 app 唤醒点）
2. **VSYNC-sf**：SurfaceFlinger 的 VSync 唤醒时刻
3. **Display Present**：预期上屏时刻（从 VSYNC-app 到 display 的完整 pipeline 目标）

**Actual Timeline 子消息**：
4. **App → SF**：App 实际完成渲染并提交 buffer 到 SurfaceFlinger 的时刻
5. **SF → Display**：SurfaceFlinger 实际完成合成并上屏的时刻

[已验证: AOSP android-17.0.0_r1, frameworks/native/services/surfaceflinger/FrameTimeline.cpp]
[结构参考: 研究素材 intake/research-feeds/2026-04-10-07-frame-timeline-perfetto-visualization-choreographer-api33.md]

### 双数据源协同工作机制

FrameTimeline 的数据来自两个独立的 Perfetto 数据源，它们协同工作：

- **`surfaceflinger.frametimeline`** 数据源：由 SurfaceFlinger 注册，报告 Expected/Actual Timeline 的帧级数据
- **`view`** 数据源：由 App 进程中的 ViewRootImpl / Choreographer 注册，报告 App 侧的 `Choreographer#doFrame`、`measure`、`layout`、`draw` 等 slice

两个数据源通过 **帧序号（frame token）** 关联。SurfaceFlinger 在 `composite()` 中调用 `FrameTimeline::onFramePresent()` 时使用 App 提交的 `frameTimeline.vsId` 作为关联键，实现 App 侧和 SF 侧的帧数据匹配。

在 Perfetto UI 中，这种关联使得开发者可以在同一条时间线上看到：
- App 侧 `Choreographer#doFrame` 的开始和结束
- 对应 buffer 在 SurfaceFlinger 侧的合成（`SF Composing`）
- 最终的 display present 时刻（`SF Presenting`）

[已验证: AOSP android-17.0.0_r1, frameworks/native/services/surfaceflinger/FrameTimeline.cpp, `onFramePresent`/`onFrameCompositorTx` 方法]

| **Android 12 (API 31)** | FrameTimeline 首次引入，SurfaceFlinger 开始报告 Expected/Actual Timeline |

## GPU/CPU 合成边界判定机制

### 合成方式的本质区别

SurfaceFlinger 在合成每一帧时，需要决定使用哪种合成路径：

- **设备合成（Device Composition / HWC）**：将 layer 的 buffer 直接传递给硬件合成器（HWC），由显示控制器硬件完成图层叠加。不消耗 GPU 算力，功耗更低。
- **客户端合成（Client Composition / GPU）**：SurfaceFlinger 调用 RenderEngine（GLES/Vulkan）将所有 layer 渲染合成到一个 framebuffer 中，再将合成结果传递给 HWC。消耗 GPU 算力。

> 详见 2.6 节 SurfaceFlinger 与合成中关于 Client/Device 合成的原理阐述。

### HWC 合成决策算法

SurfaceFliner 在每次 `composite()` 时执行以下决策流程：

```
1. 遍历所有可见 Layer，收集合成需求
2. 调用 HWC::validateDisplay() 将 layer 列表提交给 HWC
3. HWC 返回每个 layer 的合成类型建议（DEVICE / CLIENT / SOLID_COLOR...）
4. 如果 HWC 建议的 CLIENT composition layer 过多（超过 HWC 的 layer 数量上限），
   SurfaceFlinger 可能将部分 layer 改为 GPU 合成
5. SurfaceFlinger 根据 HWC 的反馈执行：
   - 全部 DEVICE → 直通模式（HWC 直接合成，SF 无需 GPU 参与）
   - 混合模式 → GPU 先合成 CLIENT layers，结果作为一个 layer 给 HWC
   - 全部 CLIENT → GPU 全量合成
```

[已验证: AOSP android-17.0.0_r1, frameworks/native/services/surfaceflinger/composition_engine/]

### gpu_composition 标志位的判定逻辑

在 Perfetto trace 中，FrameTimeline 的 Actual Timeline slice 上会标注 `gpu_composition` 标志。该标志的判定逻辑：

1. SurfaceFlinger 在 `composite()` 结束后，检查 `RenderEngine::drawLayers()` 是否被调用
2. 如果调用了 GPU 合成，在该帧的 FrameTimeline 数据中设置 `gpuComposition = true`
3. Perfetto 在渲染 Actual Timeline slice 时，根据该标志使用不同颜色或标注

**判定意义**：
- `gpu_composition = false`：本帧完全由 HWC 合成，GPU 未参与，性能最优
- `gpu_composition = true`：本帧涉及 GPU 合成，需要关注 GPU 负载

### HWC_COMPOSITION_QUEUED 事件处理

当 SurfaceFlinger 将合成请求提交给 HWC 时，会发射 `HWC_COMPOSITION_QUEUED` trace 事件。该事件的完整处理链路：

```
SurfaceFlinger::composite()
  → CompositionEngine::present()
    → Output::present()
      → HWC2::Display::present()
        → 发射 HWC_COMPOSITION_QUEUED trace
        → 等待 display present fence
```

[已验证: AOSP android-17.0.0_r1, frameworks/native/services/surfaceflinger/composition_engine/]

### RELEASE_FENCE 发射点分析

Release fence 是 SurfaceFlinger 在合成完成后释放 buffer 给 App 的同步信号。在 Android 17 中，release fence 的关键发射点：

1. **HWC 合成路径**：HWC 完成 display present 后，通过 `hwc2_display.present()` 返回 release fence
2. **GPU 合成路径**：RenderEngine 的 `drawLayers()` 完成后，GPU 操作的 completion fence 作为 release fence
3. **BLAST BufferQueue 回收**：App 侧的 BLASTBufferQueue 在收到 release fence signal 后，才回收该 buffer slot 供下次绘制使用

release fence 的时序直接影响 App 的 buffer 可用性：
- 如果 release fence 延迟到达，App 的 BufferQueue 可能耗尽（buffer starvation），导致丢帧
- FrameTimeline 中可以通过对比 Actual Timeline 的结束时间和下一帧 Expected Timeline 的开始时间来检测 buffer starvation

[已验证: AOSP android-17.0.0_r1, frameworks/native/services/surfaceflinger/]
[待验证: 具体的 fence 超时阈值在不同 OEM 设备上可能有所不同]

## 渲染管线性能分析

### Frame Pacing 的量化分析

FrameTimeline 的核心价值在于提供了帧节奏（frame pacing）的精确量化：

- **Expected Display Time**：帧预期上屏的时刻。由 VSync 周期、VSync offset 和 SurfaceFlinger 合成预算共同决定。
- **Actual Display Time**：帧实际上屏的时刻（由 display present fence 标记）。
- **帧延迟（Frame Latency）** = Actual Display Time - Expected Display Time

当帧延迟 > 0 时，表示该帧"迟到"了，用户可能感知到卡顿。

### Jank 归因：App 侧 vs SF 侧

FrameTimeline 最强大的能力是 **精确归因 jank 责任方**：

| Perfetto 颜色编码 | 含义 | 责任方 | 判定条件 |
|------------------|------|--------|---------|
| 🟢 绿色 | 帧准时完成 | 无 | Actual ≤ Expected |
| 🔴 瓶领色 | App 导致 jank | App | App 侧帧渲染超时（`Choreographer#doFrame` 耗时过长或 RenderThread 延迟） |
| 🟡 黄色 | SF 导致 jank | SurfaceFlinger | SF 合成延迟（`composite()` 耗时过长、GPU 合成排队、HWC 响应慢） |

**App 侧 jank 的典型原因**：
- 主线程耗时操作（I/O、反序列化、复杂计算）阻塞了 `Choreographer#doFrame`
- View 层级过深导致 `measure`/`layout`/`draw` 超时
- RenderThread 的 GPU 指令提交延迟

**SF 侧 jank 的典型原因**：
- GPU 合成负载过高（大量半透明 layer 叠加、复杂 shader 效果）
- HWC HAL 响应延迟（低质量 HWC 实现）
- SurfaceFlinger 主线程被其他事务（Transaction）阻塞

[已验证: Perfetto 官方文档, perfetto.dev/docs/data-sources/frametimeline]
[结构参考: 研究素材 intake/research-feeds/2026-04-10-07-frame-timeline-perfetto-visualization-choreographer-api33.md]

### GPU 合成 vs HWC 合成的性能差异

在分析渲染性能时，理解两种合成路径的性能特征至关重要：

```
场景 A：全部 HWC 合成（理想情况）
App 渲染 (3-8ms) → HWC 直接合成 (<1ms) → Display
总延迟：~5-10ms，GPU 零参与

场景 B：GPU 合成参与（典型情况）
App 渲染 (3-8ms) → RenderEngine GPU 合成 (3-10ms) → HWC 最终合成 (<1ms) → Display
总延迟：~8-20ms，GPU 参与合成
```

**触发 GPU 合成的常见因素**：
- Layer 带有圆角、阴影、模糊等效果（需要 shader 处理）
- Layer 的 pixel format 不被 HWC 支持
- Layer 数量超过 HWC 的 overlay 数量上限（通常 4-8 个，取决于硬件）
- Layer 缩放比例不符合 HWC 的缩放能力

[适用版本: Android 12 - Android 17]

## 实际应用案例分析

### 案例一：列表滑动卡顿的 FrameTimeline 诊断

**场景**：RecyclerView 列表滑动，偶发性掉帧。

**FrameTimeline 分析步骤**：

1. **抓取 Perfetto trace**：
```bash
adb shell perfetto -o /data/misc/perfetto-traces/trace.perfetto-trace -t 10s \
  sched freq idle am wm gfx view binder_driver hal
```

2. **打开 Perfetto UI**（ui.perfetto.dev），加载 trace 文件

3. **定位红色 slice**：在 Actual Timeline track 中找到红色（App jank）帧

4. **查看该帧的 App 侧详情**：
   - 展开 `Choreographer#doFrame` slice
   - 检查 `measure`、`layout`、`draw` 各子 slice 耗时
   - 如果 `measure` 耗时异常（>5ms），可能是 View 层级过深
   - 如果 `draw` 耗时异常，可能是 RenderThread 的 GPU 指令过多

5. **检查 buffer 状态**：查看该帧前后的 BufferQueue 是否出现 buffer starvation（所有 buffer 都处于 DEQUEUED/QUEUED 状态，无可用 buffer）

**典型诊断结论**：如果是 `measure` 耗时导致，优化方向是扁平化 View 层级（使用 ConstraintLayout 或 Compose）。

[结构参考: 研究素材 intake/research-feeds/2026-04-08-19-view-hierarchy-measure-layout-perfetto-jank-optimization.md]

### 案例二：游戏画面撕裂与帧节奏不一致

**场景**：游戏使用 SurfaceView 渲染，在高刷新率设备上出现画面撕裂。

**FrameTimeline 分析**：

游戏通常使用 `Choreographer.FrameData`（API 33+）来获取帧调度信息：
- `getFrameTimeNanos()`：当前帧的 VSync 时间
- `getDeadlineNanos()`：当前帧的渲染截止时间
- `getIntervalNanos()`：帧间隔

通过对比 FrameTimeline 中 Expected Timeline 的 VSYNC-app 和 Actual Timeline 的 buffer 提交时间，可以判断：
- 如果 Actual 明显早于 Expected：游戏可能在 VSync 之前就提交了 buffer（pacing 策略错误）
- 如果 Actual 延迟多个 VSync 周期：渲染管线耗时过长，需要降低画质或使用 Frame Pacing Library

**关键指标**：
- `FrameRate` / `RefreshRate` 匹配度
- `PresentLatency`（从渲染到上屏的延迟）
- `Jank percentage`（红色帧占比）

[适用版本: Android 13 (API 33) - Android 17 (API 37)，API 33 起 Choreographer.FrameData 公开]

### 案例三：复杂半透明 UI 的 GPU 合成瓶颈

**场景**：应用使用多层半透明 overlay + 模糊效果，导致 GPU 合成成为瓶颈。

**FrameTimeline 诊断**：

1. 在 Perfetto trace 中检查 Actual Timeline slice 的 `gpu_composition` 标志
2. 如果大量帧的 `gpu_composition = true`，说明 HWC 无法处理这些 layer，退化为 GPU 合成
3. 检查 SurfaceFlinger track 中的 `SF Composing` slice 耗时，如果 >8ms（120Hz），GPU 合成就是瓶颈

**优化方向**：
- 减少同时可见的半透明 layer 数量
- 使用 `ColorMatrix` 替代 shader 效果（部分 HWC 支持）
- 评估是否可以使用 `SurfaceView` 的 hardware overlay 来绕过 GPU 合成

## 调试与监控工具

### Perfetto FrameTimeline 可视化分析方法

**基本流程**：

1. **抓取 trace**：确保包含 `gfx` 和 `view` 数据源
2. **在 Perfetto UI 中定位 FrameTimeline tracks**：
   - Expected Timeline track：绿色/红色/黄色的帧 slice
   - Actual Timeline track：对应 App 侧的实际帧数据
3. **颜色编码**：
   - 🟢 绿色 = 帧准时（无 jank）
   - 🔴 红色 = App 导致的 jank
   - 🟡 黄色 = SurfaceFlinger 导致的 jank
4. **深度分析**：点击某个红色/黄色 slice，查看其 annotated metadata（frame token、gpu_composition 标志、layer 列表等）

### Perfetto SQL 查询：批量分析帧数据

Perfetto v54+ 提供了完善的 SQL 标准库模块，支持 FrameTimeline 数据的批量分析：

**基础查询：统计 jank 类型分布**

```sql
-- 统计 App jank vs SF jank vs 正常帧
SELECT
  CASE
    WHEN actual.present_type = 0 THEN 'Normal'
    WHEN actual.present_type = 1 THEN 'App Jank'
    WHEN actual.present_type = 2 THEN 'SF Jank'
  END as jank_type,
  COUNT(*) as frame_count,
  AVG(actual.present_to_display) as avg_present_latency_ms
FROM actual_frame_timeline actual
JOIN expected_frame_timeline expected
  ON actual.frame_token = expected.frame_token
GROUP BY jank_type
ORDER BY frame_count DESC;
```

**Perfetto v54 Jank CUJ 模块**：

```sql
-- 使用 v54 新增的 Jank CUJ 标准库
SELECT *
FROM relevant_threads_cuj_jank
WHERE cuq_name = 'scrolling-list'
ORDER BY jank_count DESC;
```

Perfetto v54 还引入了 **counter-based weighted jank metrics**，通过对 jank 严重程度加权（而非简单的 0/1），提供更精细的帧节奏质量评分：

```sql
-- 加权 jank 指标
SELECT
  thread.name as thread_name,
  SUM(jank_weight) as total_jank_weight,
  COUNT(CASE WHEN is_jank THEN 1 END) as jank_frame_count,
  COUNT(*) as total_frames
FROM weighted_jank_metrics wjm
JOIN thread USING (utid)
GROUP BY thread.name;
```

[已验证: Perfetto v54 Release Notes, github.com/google/perfetto/releases/tag/v54.0]
[结构参考: 研究素材 intake/research-feeds/2026-04-14-07-perfetto-v54-data-explorer-jank-cuj-heap-graph-stats.md]

### Perfetto Data Explorer（v54+）

Perfetto v54 引入的 Data Explorer 提供了无代码可视化分析界面，通过连接节点构建分析管线：

1. 选择数据源（如 `actual_frame_timeline` 表）
2. 添加变换节点（如 filter、aggregate、join）
3. 实时查看交互式表格结果

这对不熟悉 SQL 的开发者特别有用，可以快速进行帧数据分析而无需编写 SQL 查询。

[已验证: Perfetto v54 Release Notes]

## 兼容性与迁移

### Android 12 前后的差异

| 方面 | Android 11 及以下 | Android 12+ |
|------|------------------|-------------|
| 帧追踪 | FrameMetrics API（仅 App 侧数据） | FrameTimeline（App + SF 全链路） |
| Jank 检测 | Systrace 中的 Frame segment | Perfetto Expected/Actual Timeline |
| SF 主循环 | `onMessageReceived` (INVALIDATE/REFRESH) | `commit` / `composite`（Android 13+） |
| VSync 模型 | 固定 VSync offset | 可配置 VSync offset + FrameTargeter（Android 14+） |

### 应用层适配建议

1. **Android 13 (API 33) 适配**：使用 `Choreographer.FrameData` API 获取帧调度计划，替代手动 VSync 时间估算
2. **Android 14 (API 34) 适配**：FrameTargeter 引入后，`getPreferredFrameTimeline()` 返回的时间线可能动态变化，App 应响应 deadline 变化
3. **Perfetto trace 抓取**：确保 trace 配置包含 `gfx view` 数据源，否则 FrameTimeline 数据不完整
4. **线上监控**：使用 Jetpack JankStats 库进行运行时 jank 检测，不依赖 Perfetto trace 抓取

### 性能回归检测方案

建议在 CI/CD 流水线中集成 Perfetto trace 分析：

1. **自动化 trace 抓取**：在 UI 自动化测试期间持续抓取 Perfetto trace
2. **SQL 批量分析**：使用 Perfetto SQL 标准库的 weighted jank metrics 计算帧节奏质量评分
3. **基线对比**：将当前版本的 jank 指标与基线版本对比，超过阈值则报警
4. **Per-CUJ 分析**：使用 Perfetto v54 的 Jank CUJ 模块按用户交互场景（滚动、动画、过渡）分别评估

[适用版本: Android 12 (API 31) - Android 17 (API 37)]

## 扩展

### 🔸 源码深度解析：SurfaceFlinger FrameTimeline.cpp 核心方法

FrameTimeline 的核心实现位于 `frameworks/native/services/surfaceflinger/FrameTimeline.cpp`，关键方法：

- `onFramePresent()`：记录帧的实际上屏时刻，计算与 Expected Timeline 的偏差
- `onFrameCompositorTx()`：记录 SurfaceFlinger 完成合成的时刻
- `setDisplayFrame()`：设置每帧的 Expected Display Time
- `finalizeStats()`：帧数据完成后，将统计信息写入 Perfetto trace buffer

FrameTracer（`FrameTracer.cpp`）是 FrameTimeline 向 Perfetto 发射 trace 事件的桥接层，通过 `perfetto::Trace` API 将帧级数据写入 trace buffer。

[已验证: AOSP android-17.0.0_r1, frameworks/native/services/surfaceflinger/FrameTimeline.cpp]

### 🔸 Choreographer 与 FrameTimeline 协同机制

Choreographer 在 App 侧通过以下机制与 FrameTimeline 协同：

1. **帧调度请求**：`Choreographer.doFrame()` 开始时，通过 `FrameTimeline` 对象获取当前帧的 Expected Timeline（`getPreferredFrameTimeline()`）
2. **帧完成报告**：`Choreographer.doFrame()` 结束后，ViewRootImpl 将帧完成信息通过 `FrameCallback` 和 `FrameMetrics` 回调上报
3. **Deadline 感知**：Android 14+ 的 FrameTargeter 会动态调整帧 deadline，Choreographer 通过 `FrameData.getDeadlineNanos()` 感知变化

详见 2.4 节 Choreographer 与渲染流水线。

### 🔸 不同 GPU 架构下的 FrameTimeline 表现差异

不同 GPU 硬件（Adreno、Mali、PowerVR）对 FrameTimeline 数据的影响：

- **Adreno（高通）**：GPU 合成 trace 事件最完整，因为 Android 的默认参考实现基于 Adreno
- **Mali（Arm/联发科）**：部分 GPU 合成 trace 事件可能缺失或延迟标注，需要 OEM 补充
- **PowerVR（Imagination）**：较老驱动的 trace 支持较差，建议升级到最新用户空间驱动

[待验证: 具体 OEM 设备的 FrameTimeline 数据完整性需要实测验证]

### 🔸 OEM 定制 ROM 兼容性处理

OEM 对 SurfaceFlinger 的定制可能影响 FrameTimeline 数据质量：

1. **HWC 实现差异**：部分 OEM 的 HWC 实现可能不完整报告合成类型，导致 `gpu_composition` 标志不准
2. **VSync offset 定制**：OEM 可能调整 VSync offset 参数，Expected Timeline 的绝对时间在不同设备上不可直接对比
3. **自定义合成路径**：部分 OEM 引入了自定义的合成加速路径，可能不通过标准 FrameTimeline 报告

建议在性能基准测试中标注设备型号和 Android 版本。

[待验证: OEM 定制影响程度需要通过对多设备的实测数据来评估]

### 🔸 技术演进总结

FrameTimeline 从 Android 7 到 Android 17 经历了完整的演进过程，为开发者提供了全面的渲染性能分析能力。当前版本已稳定支持主流性能分析需求，开发者可专注于现有 API 的深度应用。
