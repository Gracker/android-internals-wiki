## 🔹 Pager 基础概念

Jetpack Compose Foundation 的 Pager 组件为构建分页界面提供了声明式 API。与传统 `ViewPager` / `ViewPager2` 相比，Compose Pager 更强调：状态由 `PagerState` 暴露，页面内容由 Composable 按需组合，动画和视觉变换通过 Modifier 或 Compose 动画 API 叠加。

> 版本边界：本文面向 Android 14+ 到 Android 17 设备上的 Compose 应用实践；Pager 本身属于 Jetpack Compose Foundation 库能力，不应把库版本特性直接等同为 Android 平台版本特性。

### 基础架构

在较新的 Compose Foundation Pager API 中，页数通常交给 `rememberPagerState(pageCount = { ... })`，`HorizontalPager` / `VerticalPager` 接收 `state` 并通过尾随 lambda 构建页面：

```kotlin
@Composable
fun BasicPager(items: List<PageItem>) {
    val pagerState = rememberPagerState(pageCount = { items.size })

    HorizontalPager(
        state = pagerState,
        key = { page -> items[page].id }
    ) { page ->
        PageContent(items[page])
    }
}
```

关键点：

- **pageCount**：总页数由 `PagerState` 持有，影响布局、滚动目标和边界计算。
- **state**：管理当前页、目标页、滚动偏移和布局信息。
- **key**：为页面提供稳定标识，减少列表变化时的状态错配。
- **pageContent**：每个页面的 Composable 内容；应避免在其中执行重型同步计算。

### 状态管理

`PagerState` 是 Pager 的状态中心，常用字段包括：

- **currentPage**：当前最接近吸附位置（snap position）的页面。
- **settledPage**：滚动或动画完成后稳定停留的页面。
- **targetPage**：正在滚动或动画过程中预计到达的页面。
- **currentPageOffsetFraction**：当前页相对吸附位置的偏移比例，可用于视觉变换。
- **isScrollInProgress**：当前是否处于滚动状态。
- **layoutInfo**：当前可见页面与布局信息，适合做调试和轻量策略判断。

这些字段足以覆盖大多数「页码显示、Tab 同步、滚动状态反馈、页面变换」场景。

## 🔹 页面切换动画

ViewPager 到 Compose Pager 的迁移不仅是组件替换，也会改变动画实现位置：传统 ViewPager 常通过 PageTransformer 或 View 属性动画实现；Compose Pager 更常通过页面内容的 `Modifier.graphicsLayer`、`Modifier.alpha`、`Modifier.scale` 和 Compose Animation API 实现。

### 基于偏移量的页面变换

官方文档推荐使用 `currentPageOffsetFraction` 计算当前页面与目标页面的相对偏移，再映射到透明度、缩放、位移等视觉属性：

```kotlin
@Composable
fun AnimatedPager(items: List<PageItem>) {
    val pagerState = rememberPagerState(pageCount = { items.size })

    HorizontalPager(state = pagerState) { page ->
        val pageOffset = (
            (pagerState.currentPage - page) + pagerState.currentPageOffsetFraction
        ).absoluteValue

        Card(
            modifier = Modifier
                .fillMaxWidth()
                .graphicsLayer {
                    val scale = lerp(
                        start = 0.85f,
                        stop = 1f,
                        fraction = 1f - pageOffset.coerceIn(0f, 1f)
                    )
                    scaleX = scale
                    scaleY = scale
                    alpha = lerp(
                        start = 0.5f,
                        stop = 1f,
                        fraction = 1f - pageOffset.coerceIn(0f, 1f)
                    )
                }
        ) {
            PageContent(items[page])
        }
    }
}
```

使用这类动画时应注意两点：

1. 变换计算应保持轻量，避免在滚动帧中做 I/O、复杂分配或大对象创建。
2. 视觉变换适合放在 Modifier 层；业务状态变更应尽量由 `settledPage` 或显式事件驱动，避免在每帧滚动偏移变化时触发昂贵副作用。

### 与 TabRow 同步

典型做法是用 `pagerState.currentPage` 或 `settledPage` 驱动 Tab 选中态，点击 Tab 时调用 `animateScrollToPage`：

```kotlin
@Composable
fun PagerWithTabs(tabs: List<String>) {
    val pagerState = rememberPagerState(pageCount = { tabs.size })
    val scope = rememberCoroutineScope()

    TabRow(selectedTabIndex = pagerState.currentPage) {
        tabs.forEachIndexed { index, title ->
            Tab(
                selected = pagerState.currentPage == index,
                onClick = {
                    scope.launch { pagerState.animateScrollToPage(index) }
                },
                text = { Text(title) }
            )
        }
    }

    HorizontalPager(state = pagerState) { page ->
        Text(text = tabs[page])
    }
}
```

## 🔹 性能优化策略

页面切换中的性能优化核心不是「手写调度器」，而是控制组合范围、避免每帧昂贵计算，并为 Pager 提供稳定状态和可预测页面内容。

### 使用 derivedStateOf 过滤高频状态

如果 UI 只关心从滚动状态派生出的低频布尔值或简单枚举，应使用 `derivedStateOf` 降低无意义重组：

```kotlin
@Composable
fun PagerChrome(pagerState: PagerState) {
    val showPrevious by remember {
        derivedStateOf { pagerState.currentPage > 0 }
    }
    val showNext by remember {
        derivedStateOf { pagerState.currentPage < pagerState.pageCount - 1 }
    }

    NavigationButtons(
        showPrevious = showPrevious,
        showNext = showNext
    )
}
```

### 隔离页面内部状态

避免把会高频变化的顶层状态一路传递到每个页面。每个页面只接收自己需要的数据，并在页面内部缓存可复用计算：

```kotlin
@Composable
fun IsolatedPagerItem(item: Item) {
    val title = remember(item.id, item.title) { item.title.trim() }

    Box(
        modifier = Modifier
            .fillMaxSize()
            .background(item.backgroundColor)
    ) {
        ItemContent(
            title = title,
            content = item.content
        )
    }
}
```

### 控制预加载和重型内容

Pager 可以通过 beyond-bounds/page spacing 等参数影响相邻页面的布局和预组合行为，但「更大的预加载」不总是更快。实践上应：

- 当前页和相邻页优先保障流畅；远离当前页的内容延后加载。
- 图片、视频、WebView 等重型资源跟随可见性启停，不要只依赖 Composable 是否存在。
- 用 Macrobenchmark、Perfetto/JankStats 等工具验证实际掉帧，而不是凭主观动画观感下结论。

> 本轮复查删除了“Android 17 新增智能页面预加载策略和基于用户行为的动态页面缓存机制”的断言；当前缺少足够来源证明这是 Android 17 平台或 Pager 公开 API 的稳定能力。

## 🔸 待验证的高级方向

以下内容适合作为后续源码级扩展方向，但在没有 Compose Runtime / Foundation 源码版本和官方文档证据前，不应写成已验证结论。

### Pausable Composition

Pausable Composition 可作为 Compose Runtime 内部机制或实验性方向讨论，但不能简单等同为「Android 17 中 Pager 自动支持的公开能力」。在业务代码中，更稳妥的做法是基于页面可见性显式降级重型内容：

```kotlin
@Composable
fun PausablePagerItem(
    item: Item,
    isVisible: Boolean,
    content: @Composable () -> Unit
) {
    if (isVisible) {
        content()
    } else {
        PlaceholderContent(title = item.title)
    }
}
```

后续若要 finalized，需要补充 Compose Runtime 对 Pausable Composition 的具体版本、API 可见性和 Pager 关联证据。

### Choreographer 与帧时间

`Choreographer` 是 Android 平台的帧调度入口，应用可通过 `Choreographer.getInstance().postFrameCallback { frameTimeNanos -> ... }` 获取帧回调；但 Compose 动画一般不需要直接操作它，优先使用 Compose 的动画 API 或协程帧时钟，例如 `withFrameNanos`。

```kotlin
LaunchedEffect(Unit) {
    withFrameNanos { frameTimeNanos ->
        // 读取帧时间戳，执行轻量级计算或记录
        recordFrame(frameTimeNanos)
    }
}
```

如果确实需要直接接入平台 Choreographer，应至少保证：

- 使用正确 API：`Choreographer.getInstance()`，不是 `Choreger`。
- 识别 VSYNC（不是 “VSENS”）与帧时间戳的含义。
- 回调中只做轻量工作；重型计算应提前完成或移到后台线程。
- 不把未验证的 deadline/帧预算能力写成 Pager 公开行为。

### 自定义动画控制器

高级动画控制器适合封装业务层动画状态，而不是替代 Compose 内置滚动和动画系统：

```kotlin
class PagerAnimationController {
    private val activePages = mutableSetOf<Int>()

    fun onVisiblePagesChanged(pages: List<Int>) {
        activePages.clear()
        activePages.addAll(pages)
    }

    fun shouldRunHeavyAnimation(page: Int): Boolean {
        return page in activePages
    }
}
```

性能考量：

1. **内存管理**：不要为每帧滚动创建大量临时对象。
2. **计算复杂度**：滚动路径上只保留 O(1) 或很小 O(n) 的轻量计算。
3. **帧率稳定**：动画复杂度必须用实际 trace/benchmark 验证。
