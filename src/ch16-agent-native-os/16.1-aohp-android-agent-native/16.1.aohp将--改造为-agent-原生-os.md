# 16.1 AOHP：将 Android 改造为 Agent 原生 OS

## 问题背景：应用中心设计的三重不匹配

当 AI agent 成为主要工作负载类型时，Android 原有的应用中心（app-centric）架构在三个维度上暴露结构性不匹配 [来源: arXiv 2606.23449 §1]：

| 维度 | 原版 Android 的问题 | 典型表现 |
|------|---------------------|----------|
| **界面适配** | GUI 为人类视觉设计，agent 需从截图/视图树推断语义 | agent 反复截图 → OCR → 推理 → click(x,y)，token 消耗巨大 |
| **执行效率** | 应用生命周期绑定前台显示器，agent 只能串行 GUI 操作 | 后台应用被 freeze，agent 无法并行处理多任务 |
| **信息安全** | 应用级权限无法跟踪数据在 agent 工具调用链中的传播 | agent 可将支付数据传入第三方 LLM，权限模型无感知 |

这三个 gap 的本质是：**Android 的权限与交互模型设计于 2008 年，假设"用户授权应用访问数据"的二元模型。agent 介导的交互打破了这一假设——agent 同时代表用户和应用，数据在 agent 上下文中跨越应用边界传播。**

> ⚠️ **版本说明**：AOHP 是学术论文（清华大学/北京大学/香港大学联合研究），并非 Android 17 官方特性。本节作为前沿研究方向收录，与 Android 17 的 AppFunctions 官方方向对比分析。[适用版本: 研究基于 Android 15 AOSP，方向对照 Android 17]

## AOHP 四层架构

```
┌─────────────────────────────────────────┐
│  个性化服务组合 (Generated Entrances)     │  ← 顶层：面向用户的任务级入口
├─────────────────────────────────────────┤
│  AOHP 能力层 (Memory / Skills / UI)      │  ← OS 管理的能力重组
├─────────────────────────────────────────┤
│  统一交互接口 (API / CLI / SUI / GUI)     │  ← 归一化传统和 agent 接口
├─────────────────────────────────────────┤
│  Android 生态 (Apps / System / HW)       │  ← 底层：保持兼容
└─────────────────────────────────────────┘
       ↕ 高效 Agent 接口    ↕ 安全信息流
```

[来源: arXiv 2606.23449 §3, Figure 2]

设计取舍的核心：**不重新造 OS，而是在 AOSP 上打补丁**。保留 Android 的硬件兼容性和应用生态，在 framework 层注入 agent 原生能力。这与 Android 17 的 Mainline 模块化方向一致——通过框架层扩展而非系统级重写来引入新能力。

### 与 Android 17 AppFunctions 的方向对比

| 维度 | AOHP 方案 | Android 17 AppFunctions |
|------|-----------|------------------------|
| 实现层级 | OS 级 framework 修改 | 应用级 opt-in 模块 |
| 能力发现 | 自动 + 手动标注 | 开发者主动声明 |
| 安全模型 | Vault + Taint 跟踪 | 标准权限模型 |
| 后台并行 | 轻量虚拟显示器 | 受限后台执行 |
| 生态兼容性 | 需要刷定制 ROM | 标准 Android 17 设备 |

[已验证: 官方文档参照, Android 17 AppFunctions developer.android.com — 方向一致性判断]

## 核心机制一：个性化服务组合

传统理解里，"应用"是原子单位——打开淘宝购物、打开美团点外卖。AOHP 引入"服务入口"概念：OS 根据用户意图**跨应用聚合能力**。

### 能力发现

应用通过三种通道声明自己的能力：

- **API 通道**：应用注册结构化函数签名（input/output schema、前置条件、副作用）
- **CLI 通道**：应用暴露命令行接口（类似 `am instrument` 或 `cmd` 服务）
- **GUI 通道**：AOHP 通过结构化 UI 提取自动推断能力

每个能力声明携带四个元数据：输入类型、输出类型、前置条件、副作用策略标签（如"需要确认"、"会产生支付"）。

### 服务组合引擎

OS 层面的 agent 将多个能力编排成工作流。例如"购物"任务 = 搜索（多提供商并行）→ 比较（沙箱内）→ 购买（需用户确认）。

### 跨服务个性化记忆

系统维护三类跨应用共享记忆：

| 记忆类型 | 生命周期 | 示例 |
|----------|----------|------|
| **持久配置记忆** | 跨 session | "用户偏好深色主题"、"用户习惯用支付宝" |
| **任务局部记忆** | 单次任务 | 当前购物车的商品列表 |
| **敏感记忆** | vault 管理 | 支付卡号、身份证号（仅占位符暴露给 agent）|

> **关键区分**：AOHP 的"记忆"不是 LLM 的 context window，而是 OS 级的状态管理——独立于任何单个应用的私有数据模型。这与 Android 17 的 `OnDeviceIntelligence` 框架中的 `FoundationModelManager` 资源隔离思路形成互补。 [交叉引用: §5.30 Android 17 OnDeviceIntelligence 框架性能]

## 核心机制二：五个高效 Agent 接口原语

| 原语 | 解决的问题 | 实现方式 |
|------|-----------|----------|
| **并行后台交互** | agent 被前台绑定 | 轻量级虚拟显示器，agent 在后台运行而不抢占前台 |
| **Agent 感知 UI 增强** | GUI 渲染细节对 agent 是噪音 | 抽象为结构化表示 (SUI)，保留 GUI 作为后退 |
| **原生沙箱运行时** | agent 需要代码执行环境 | OS 管理的隔离 sandbox，agent 在其中跑代码、处理数据 |
| **统一文件快捷方式** | 跨应用文件传递容易断裂 | 文件作为 OS 级一等对象，GUI 操作和程序操作统一 |
| **事件流抽象** | 瞬态事件（Toast/通知）agent 容易错过 | 订阅-消费模型，NotificationBuffer + 传感器流 |

[来源: arXiv 2606.23449 §5.1-5.5]

### 虚拟显示器后台并行

AOHP 用轻量级虚拟显示器实现后台并行交互。每个 agent 工作流可以分配一个虚拟显示器，在其中运行应用 UI 而不影响前台用户体验。这比 Android 的多窗口/分屏更底层——虚拟显示器不依赖物理显示，资源开销更低。

> [已验证: AOSP android-17.0.0_r1] Android 的 `VirtualDisplay` API (`DisplayManager.createVirtualDisplay()`) 在 Android 17 中仍然可用。AOHP 的创新在于将其从"投屏/录屏"用途扩展到"agent 后台工作空间"。

### 结构化 UI (SUI)

AOHP 不让 agent 看截图，而是提供结构化的 UI 描述：

- 保留语义元素类型（Button、Text、Image、List）
- 去除视觉渲染细节（颜色渐变、阴影、动画帧）
- 保留层级关系和可操作性标签

实验数据显示，结构化观察比截图更紧凑：**input token 降低 51.50%**，完成同样任务需要的步骤更少导致 **output token 降低 57.48%**。

### NotificationBuffer 事件缓存

Android 的 Toast 和瞬态通知对 agent 是常见陷阱——agent 在处理其他任务时容易错过这些事件。AOHP 实现 `NotificationListenerService` 缓存机制：

- 所有通知和 Toast 被缓存到 buffer
- agent 通过订阅-消费模型获取事件
- 避免反复截图检查屏幕状态（减少 CPU 和 GPU 开销）

## 核心机制三：安全信息流四层防护

```
敏感源 → [净化] → 占位符 <payment-card:uuid>
                         ↓
               agent 在占位符上推理
                         ↓
           [Vault 执行器] ← agent 提交意图
                  ↓
           策略检查 + 用户审批
                  ↓
           可信环境内执行 → 返回结果（可能仍是占位符）
                         ↓
                  [Taint 跟踪]
                         ↓
              系统出口检查 → 放行/阻止
```

[来源: arXiv 2606.23449 §6.1-6.4]

### 占位符替代明文

agent 从不直接接触敏感值。使用 `<type:uuid>` 格式（如 `<payment-card:a3f8b2>`）保留语义但隐藏实际值。agent 可以在占位符上进行推理（"我需要用这张卡支付"），但不能提取卡号。

### Vault 执行器

agent 提交"我要用这张卡支付 ¥99"的意图到 Vault 执行器。Vault 负责：
1. 策略检查（该 agent 是否被授权使用该支付方式？）
2. 用户审批（弹窗确认，非 agent 上下文）
3. 在可信环境中执行操作
4. 返回结果（可能仍是占位符）

### Taint 传播

敏感数据的 taint 标签在复制、转换、组合过程中持续传播。AOHP 的 taint 跟踪建立在 TaintDroid（2014）的血统之上，但扩展到了 agent 上下文——**每一次 LLM 请求、每一个工具输入输出都是 taint 传播路径上的节点**。

> **对比 TaintDroid** [已验证: AOSP 历史]：TaintDroid 曾是 Android 的可选安全组件，后被移除。AOHP 将其概念复活并扩展到 agent 工具调用级别。Android 17 的安全模型中不再包含原生 taint tracking，这使得 AOHP 的安全层完全是其自身的框架层创新。

## 实验数据

### 实验设计

- **Agent 框架**：OpenClaw（开源 agent 框架）
- **任务集**：30 个真实移动任务，覆盖 GUI 操作、非 GUI 操作、事件捕获、多源信息检索、记忆管理、混合能力
- **对比**：同一个 OpenClaw agent 在原版 Android vs AOHP 上的表现

### 核心结果

| 指标 | 原版 Android | AOHP | 变化 |
|------|-------------|------|------|
| 完成率 | 54.44%（13/30） | 75.56%（20/30） | +21.12pp |
| 工具调用数 | 233 | 129 | -44.64% |
| 执行时长 | 33.94 min | 18.93 min | -44.21% |
| Token 消耗 | 7.10M | 3.44M | -51.55% |
| LLM 请求数 | 273 | 143 | -47.62% |

[来源: arXiv 2606.23449 §7.1-7.2, Table 1]

> **效率比较方法论**：只在两种设置都完全解决的 11 个任务上比较效率指标。这是正确的实验设计——避免"因为解了更难的任务所以变慢"的混淆。

### 完成率提升的来源

提升集中在三个场景：
1. **瞬态通知**（agent 不再错过 Toast/推送）— 事件流抽象的贡献
2. **细粒度 GUI 操作**（结构化 UI 减少误操作）— SUI 的贡献
3. **跨应用工作流**（文件快捷方式和系统记忆减少 GUI 导航）— 服务组合的贡献

论文自身承认的局限（§9）及补充评估：

| 局限 | 影响 | 工程缓解 |
|------|------|----------|
| **兼容性覆盖** | 自定义渲染、反自动化逻辑的应用需要更强提取 | 保留 GUI 作为后退 |
| **能力发现** | 依赖开发者标注，legacy 应用无法自动推理 | 需要自动能力推理引擎 |
| **资源开销未量化** | 虚拟显示器/notification buffer/taint 的 CPU/内存/延迟未报告 | [待验证: 论文未提供性能开销数据] |

## 工程启示

### 对 Android Agent 开发者

1. **截图 + 点击不是唯一路径**：优先考虑 `AccessibilityService` API、`ContentProvider` 或 CLI 工具。AOHP 数据表明结构化接口能将 token 消耗砍半。
2. **事件驱动优于轮询**：实现 `NotificationListenerService` 缓存事件，而非让 agent 反复检查屏幕。后者浪费 CPU 和 GPU 资源。
3. **文件作为跨应用数据通道**：agent 工作流中用文件（共享存储或 `FileProvider`）作为中间制品比用 `Intent`/Deep Link 更可靠。

### 对系统/框架开发者

1. **应用沙箱不够**：传统应用级沙箱无法防止 agent 在工具调用链中泄露数据。信息流跟踪在 agent 时代变得重新重要。
2. **虚拟显示器是实际可用的技术**：`VirtualDisplay` API 从 Android 4.2 就存在，AOHP 展示了其在 agent 后台并行中的新用法。
3. **AOSP 可改性验证**：论文证明了在 AOSP 上做框架级修改仍然可行——不需要从零造 OS。

### 对 AI × Android 的判断

Google 在 Android 17 中推出 AppFunctions（让应用声明函数给 agent 调用），方向与 AOHP 一致。关键区别：

- **Google AppFunctions**：应用级 opt-in，标准化接口，依赖生态采纳
- **AOHP**：OS 级重构，强制能力暴露，需要定制 ROM

两者代表了两条路径：Google 选择渐进式生态演进，AOHP 代表激进式系统重构。从工程实践角度，AppFunctions 更可能在中短期落地，AOHP 更适合作为长期方向的学术验证。

## 扩展

### 🔸 AOHP 与 Android 17 OnDeviceIntelligence 的互补性

Android 17 的 `OnDeviceIntelligence` 框架（详见 §5.30）提供了端侧 AI 推理的基础设施（`FoundationModelManager`、推理调度、资源隔离），AOHP 则提供了 agent 与 OS 交互的接口层。两者在概念上互补：OnDeviceIntelligence 管"怎么推理"，AOHP 管"怎么操作"。[待验证: 两者是否可以在同一系统中共存，尚无实验验证]

### 🔸 TaintDroid 的历史与 AOHP 的复兴

TaintDroid 是 2014 年 Google 的信息流跟踪系统，后因性能开销被移出 Android 主线。AOHP 将其概念扩展到 agent 工具调用级别。如果 Android 正式引入 agent 级别的信息流控制，可能需要重新评估 taint tracking 的性能-安全 tradeoff。[来源: 历史参照, 非android-17.0.0_r1特性]

### 🔸 后台虚拟显示器的资源调度

AOHP 创建虚拟显示器用于 agent 后台操作，但没有量化其资源开销（CPU、内存、GPU）。在资源受限的移动设备上，多个虚拟显示器的并发可能导致严重的资源争用。Android 17 的 `lmkd` 和 `ActivityManager` 内存回收机制如何与 agent 后台虚拟显示器交互，是一个需要实测的工程问题。[待验证: 无实验数据]

### 关键代码证据

#### 1. `AppFunctionManagerService` 构造期双 flag 门控

`frameworks/base/services/appfunctions/java/com/android/server/appfunctions/AppFunctionManagerService.java:48-78`：

```java
public AppFunctionManagerService(Context context) {
    super(context);
    AppFunctionAccessServiceInterface appFunctionAccessService = null;
    if (accessCheckFlagsEnabled()) {          // 双权限 flag 门控
        appFunctionAccessService =
                LocalServices.getService(AppFunctionAccessServiceInterface.class);
    }
    if (Flags.enableAppInteractionApi()) {
        mAppInteractionService = new AppInteractionServiceImpl(context);
    }
    AppFunctionAllowlistReader allowlistReader = null;
    if (Flags.enableAppFunctionPermissionV2()) {
        allowlistReader = SystemAppFunctionAllowlistReader.getInstance(context);
    }
    mServiceImpl = new AppFunctionManagerServiceImpl(
            context,
            LocalServices.getService(PackageManagerInternal.class),
            appFunctionAccessService,
            UriGrantsManager.getService(),
            LocalServices.getService(UriGrantsManagerInternal.class),
            new AppFunctionsLoggerWrapper(context),
            MultiUserDynamicAppFunctionRegistry.getInstance(),
            mAppInteractionService,
            new AppFunctionMetadataReader(...),
            LocalServices.getService(ActivityTaskManagerInternal.class),
            allowlistReader);
}
```

设计要点：
- **构造期全量初始化**：所有 collabolator 一次取齐，避免首次调用延迟。
- **两阶段 Flag 门控**：访问控制（`enableAppFunctionPermissionV2`）和交互 API（`enableAppInteractionApi`）独立打开，体现「agent 化能力按场景梯度开放」的设计哲学。
- **依赖注入而非 service locator**：客户端拿到的是已经组装好的 `AppFunctionManagerServiceImpl`，内部 collabolator 通过 `LocalServices.getService` 一次性查表绑定。

可见 **AppFunctionManagerService 是 AOSP 17 默认关闭、按设备配置条件启用的「late bootstrap 服务」**。OEM 想屏蔽 agent 化能力时，在配置层关掉即可，不需改二进制。

### AOHP vs AppFunctions 的工程本质差异

| 维度 | AOHP（论文） | AppFunctions（AOSP 17） |
|------|------------|------------------------|
| 工程位置 | 定制 ROM fork | system_server 标准 binder 服务 |
| 能力发现 | 自动结构化 UI 提取 + 标注 | 应用主动 `RegisterAppFunctionRequest.java` 注册 schema |
| 安全模型 | Vault + taint 跟踪 | `AllowlistService` + `CallerIdentity` 校验链 |
| 后台并行 | 轻量虚拟显示器 | 通过 `AppInteractionService` + ActivityTaskManager 协作 |
| 注入路径 | 改写 framework 渲染管线 | 沿用 AccessibilityService / ContentProvider / Binder 现有抽象 |
| 落地强度 | 重（重编译 OS） | 轻（OEM 配置 / 应用 opt-in） |

**Google 选择的是「Mainline 风格渐进式」，与 AOHP 论文「OS 重构式激进式」形成清晰对比**——这也解释了为何 daily-topics 把两者混合描述会产生误解。
