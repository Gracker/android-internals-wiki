# 8.1 Android 17 任务调度器优化

<!-- outline-start -->
## 要点

### 🔹 本节当前结论
Android 17 AOSP 中可以复核到的是一组分层任务执行与资源约束机制：JobScheduler、DeviceIdleController、ActivityManager/ProcessList、TaskProfiles/cgroup、内核调度器以及 Perfetto/statsd/dumpsys 观测面。没有证据表明 `android-17.0.0_r1` 主线新增了独立的“ML TaskScheduler”平台框架。

### 🔹 应用层：JobScheduler 是后台任务入口
Android 17 的 JobScheduler 服务源码位于 `frameworks/base/apex/jobscheduler/service/java/com/android/server/job/`。它负责把应用提交的 job 与网络、电量、idle、充电、deadline 等约束关联起来；调优重点不是“预测一个固定延迟”，而是减少不必要 job、合并可延迟任务、给出正确约束，并用 `dumpsys jobscheduler` 与 statsd 观察实际调度状态。

### 🔹 系统与电源层：状态约束影响任务何时能跑
Device idle、进程优先级、后台执行限制与低内存策略会共同影响任务执行窗口。`DeviceIdleController.java`、`ProcessList.java`、`task_profiles.json` 等路径可以作为 Android 17 口径的边界锚点；它们不能直接推出“后台固定 5–20% CPU”或“夜间自动延迟 5–15 秒”这类全局数值。

### 🔹 内核与观测层：用 trace 解释调度延迟
Kernel 固定到 android17-6.18-2026-06_r6 时，任务最终仍进入 Linux 调度、cpuset、uclamp/schedutil 等路径。Perfetto 中的 `sched_switch`、`sched_wakeup`、CPU frequency、power/thermal 与 JobScheduler/statsd 事件可以把“job 何时满足约束”和“线程何时真正获得 CPU”拆开分析。

## 扩展

### 🔸 推荐调优顺序
先确认任务是否应该存在，再确认约束是否正确，最后用 trace 区分等待约束、等待唤醒、等待 CPU、等待锁/I/O 或被热/电源策略压制。

### 🔸 版本边界
本文只讨论 Android 17 / API 37 的 `android-17.0.0_r1` 与 android17-6.18 kernel；不把 Android 18/API 38+、厂商预测调度或研究型 ML scheduler 当成 Android 17 AOSP 主线事实。

## 🔹 本节当前结论

本节已从“ML 驱动任务调度器”重写为 **Android 17 任务执行与资源约束的多层边界**。在 `android-17.0.0_r1` 可复核源码中，安全结论是：

- 应用提交的后台任务主要通过 **JobScheduler / WorkManager** 等公共入口进入系统调度；WorkManager 是 Jetpack 库，最终会按条件选择 JobScheduler、AlarmManager 等系统能力。
- 平台侧会结合 job 约束、idle 状态、充电/电量、网络、进程状态、后台限制和系统资源状态决定任务何时可运行。
- 进程和线程最终仍受 Android common kernel 的调度、cpuset、uclamp/schedutil、cgroup/TaskProfiles、热管理和电源策略影响。
- 性能分析必须把“任务约束尚未满足”和“线程已经 runnable 但拿不到 CPU”分开，不应用一个笼统的“调度器优化百分比”解释所有延迟。

本节不再沿用原稿中的平台级 ML TaskScheduler、LSTM/CNN/GNN 参数、固定 CPU/内存配额、启动/续航/温度收益百分比。这些说法在本轮没有 `android-17.0.0_r1` 源码或官方材料支撑。

## 🔹 应用层：JobScheduler 是后台任务的系统入口

Android 17 的 JobScheduler 服务源码锚点是：

```text
frameworks/base/apex/jobscheduler/service/java/com/android/server/job/JobSchedulerService.java
frameworks/base/apex/jobscheduler/service/java/com/android/server/job/controllers/JobStatus.java
frameworks/base/apex/jobscheduler/service/java/com/android/server/job/controllers/*Controller.java
```

需要注意路径边界：较旧资料常把 JobScheduler 放在 `frameworks/base/services/core/java/com/android/server/job/`，但在 `android-17.0.0_r1` 中，本轮 Gitiles 探测到的服务实现位于 `frameworks/base/apex/jobscheduler/service/java/com/android/server/job/`。因此，重写或复核 Android 17 章节时，应以 jobscheduler APEX 路径为准。

JobScheduler 的工程意义不是“让每个后台任务尽快执行”，而是把后台工作约束化：

- 是否必须联网，网络类型或能力是否有限制；
- 是否需要充电、设备空闲或电量不低；
- 是否有 deadline，是否允许延迟和批量执行；
- 任务失败后是否需要退避重试；
- 同一应用是否提交了过多可合并 job。

对 App 来说，常见优化不是绕过 JobScheduler，而是减少低价值周期任务、合并批量同步、给出准确约束，并避免把用户不可见的 I/O 或网络轮询伪装成高优先级前台工作。

## 🔹 电源与 idle：任务可运行不等于马上运行

后台任务是否可运行，还会受 idle 和电源状态影响。Android 17 的可复核锚点包括：

```text
frameworks/base/apex/jobscheduler/service/java/com/android/server/DeviceIdleController.java
frameworks/base/apex/jobscheduler/service/java/com/android/server/alarm/AlarmManagerService.java
frameworks/base/services/core/java/com/android/server/power/PowerManagerService.java
```

这些组件共同决定设备进入或退出 idle、alarm 与 wakelock 对唤醒的影响、系统是否允许某类后台工作继续推进。排障时应先判断 job 是否仍在等待约束，而不是直接归因于 CPU 调度。

可操作的检查顺序：

1. `dumpsys jobscheduler`：看 job 是否 pending、active、约束是否满足、最近失败/停止原因是什么。
2. `dumpsys deviceidle`：确认设备 idle 状态、白名单、临时豁免和约束状态。
3. `dumpsys alarm` 与 `dumpsys batterystats`：确认是否存在过密唤醒、重复 alarm 或异常 wakelock。
4. statsd / Perfetto：把 JobScheduler 状态变化与 CPU、线程、功耗事件放到同一条时间线上。

如果 job 还没有满足约束，优化方向通常是调整业务触发和约束声明；如果 job 已经 active 但 worker 长时间 runnable，则需要进入线程、锁、I/O、CPU 频率和热状态分析。

## 🔹 进程状态：AMS/ProcessList 影响后台执行优先级

任务执行还受应用进程状态影响。Android 17 可复核源码锚点包括：

```text
frameworks/base/services/core/java/com/android/server/am/ActivityManagerService.java
frameworks/base/services/core/java/com/android/server/am/ProcessList.java
frameworks/base/services/core/java/com/android/server/am/OomAdjuster.md
```

`ProcessList`、`OomAdjuster` 与 AMS 的职责是维护进程优先级、adj、前后台状态、服务和进程生命周期。它们会影响系统如何看待某个进程的重要性，也会间接影响后台任务在内存压力、服务限制和进程回收下的稳定性。

这里要避免两个误读：

- `oom_score_adj` 是内存回收优先级输入，不是“CPU 配额百分比”。
- 前台、可见、perceptible、cached 等进程状态会影响保活和限制策略，但不能直接推导出固定 CPU/内存占比。

因此，分析“后台任务慢”时应同时查看 `dumpsys activity processes`、`dumpsys meminfo`、LMK/PSI 信号和任务自身日志，确认是进程被限制、被杀、重启，还是任务线程本身执行慢。

## 🔹 TaskProfiles / cgroup：资源分组不是固定收益承诺

Android 17 的进程/线程资源分组配置可从 system/core 的 libprocessgroup 路径复核：

```text
system/core/libprocessgroup/profiles/task_profiles.json
system/core/libprocessgroup/profiles/cgroups.json
system/core/libprocessgroup/task_profiles.cpp
system/core/libprocessgroup/sched_policy.cpp
```

TaskProfiles/cgroup 的作用是把线程放入不同资源组、应用调度属性或配置系统已定义的资源控制动作。它能解释“某类线程被放到哪个组”“是否应用了某类调度属性”，但不能在没有设备配置、内核状态和实测 trace 的情况下推出如下结论：

- 前台应用固定拥有 80% CPU；
- 后台任务固定只有 5–20% CPU；
- 系统服务固定预留 15% CPU；
- Android 17 平台保证启动时间减少 40–50%。

厂商设备还可能通过 Power HAL、thermal HAL、SoC governor、cpuset/uclamp 配置和私有策略改变实际表现。AIW 正文应把 AOSP 能证明的接口和配置边界，与目标设备上的实测行为分开描述。

## 🔹 内核层：android17-6.18 的调度边界

当任务线程已经 runnable，真正决定它何时获得 CPU 的路径在 kernel scheduler、cpuset、uclamp/schedutil、cpufreq 和热/电源策略之间。Android 17 本节固定 kernel 口径为 `android17-6.18-2026-06_r6`，可复核锚点包括：

```text
kernel/sched/core.c
kernel/sched/fair.c
kernel/cgroup/cpuset.c
kernel/sched/cpufreq_schedutil.c
```

这些文件可以作为说明 Linux/Android 调度基础的锚点：线程入队、唤醒、上下文切换、CFS/EEVDF 公平调度、cpuset 约束、util 到频率选择的传递。它们不能替代设备实测，因为目标设备的 CPU 拓扑、thermal 状态、vendor hook 和 HAL 策略会改变实际可用算力。

工程上应把任务延迟拆成几类：

| 现象 | 可能原因 | 推荐证据 |
| --- | --- | --- |
| job 长时间 pending | 网络/idle/充电/电量约束未满足 | `dumpsys jobscheduler`、statsd JobScheduler atom |
| job active 但 worker 未开始 | 进程启动、服务绑定、线程池排队 | app log、`dumpsys activity services`、Perfetto app slices |
| worker runnable 但 CPU 少 | CPU 竞争、cpuset/uclamp、热降频 | Perfetto `sched_switch` / `sched_wakeup` / cpufreq / thermal |
| worker running 但耗时长 | 锁、I/O、数据库、网络、算法热点 | trace slice、simpleperf、应用埋点 |
| 周期任务频繁唤醒 | 业务轮询、alarm/job 过密 | Battery Historian、`dumpsys batterystats`、job/alarm dump |

## 🔹 观测层：用 Perfetto、statsd 和 dumpsys 闭环

任务调度优化应以观测闭环结束，而不是以单一结论结束。推荐最小闭环如下：

1. **系统 dump**：采集 `dumpsys jobscheduler`、`dumpsys deviceidle`、`dumpsys activity processes`、`dumpsys batterystats`，判断任务约束、进程状态和唤醒行为。
2. **Perfetto trace**：打开 sched、freq、idle、power、thermal、binder、am/wm、应用自定义 trace 等数据源，把 job 触发点、worker 执行和 CPU 实际运行放到同一时间线。
3. **statsd 事件**：关注 JobScheduler 状态变化、设备约束变化、ANR/LMK、功耗相关 atom，用于线上聚合和趋势判断。
4. **业务指标**：记录任务名、触发来源、约束、耗时、成功率、失败原因、重试次数和用户可见影响。

只有当这些证据能指向同一个瓶颈时，才适合给出明确优化结论。例如：若 trace 显示 job 在 device idle 中等待约束，则优化点是减少后台唤醒或调整约束；若 worker runnable 后频繁被抢占且同时降频，则需要看 CPU 竞争、热状态和任务优先级；若 worker 长时间 running，则应回到代码热点、锁和 I/O。
