# Android 17 后台任务内存配额机制 — MemoryLimiter 与 cgroup memory.high

📅 2026-06-26 | Android-Internal-Wiki · 新建章节

## 概述

Android 17（API 37）引入了一个全新的后台任务内存配额系统 `MemoryLimiter`，它通过 cgroup v2 的 `memory.high` 和 `memory.swap.high` 实现进程级内存配额管理。这套系统与传统的 `onTrimMemory` 回调路径并行运行，形成 Android 内存管理的双重防线。

本文将深入分析 MemoryLimiter 的架构设计、源码实现和运行机制，重点解析其与既有的 `CachedAppOptimizer` 和 `lmkd` 系统的协作关系。

## 1. 内存管理架构演进

### 1.1 ComponentCallbacks2 trim 等级变化

Android 14（API 34）开始对传统的 trim 等级体系进行了重大调整：

| 常量 | 数值 | API 34 状态 |
|------|------|-------------|
| `TRIM_MEMORY_COMPLETE` | 80 | `@Deprecated` |
| `TRIM_MEMORY_MODERATE` | 60 | `@Deprecated` |
| `TRIM_MEMORY_BACKGROUND` | 40 | 仍派发 |
| `TRIM_MEMORY_UI_HIDDEN` | 20 | 仍派发 |
| `TRIM_MEMORY_RUNNING_CRITICAL` | 15 | `@Deprecated` |
| `TRIM_MEMORY_RUNNING_LOW` | 10 | `@Deprecated` |
| `TRIM_MEMORY_RUNNING_MODERATE` | 5 | `@Deprecated` |

**关键变化**：
- 五个等级被标记为 `@Deprecated`，官方建议开发者改用 `≥ 20` 或 `≥ 40` 的判等逻辑
- 这意味着传统的多档位 trim 策略在 Android 14+ 已经失效
- 系统简化为只有 `BACKGROUND(40)` 和 `UI_HIDDEN(20)` 两个有效档位

### 1.2 CachedAppOptimizer 的工作机制

`CachedAppOptimizer` 在进程被冻结前下发 `TRIM_MEMORY_BACKGROUND(40)`：

```java
// frameworks/base/services/core/java/com/android/server/am/CachedAppOptimizer.java
if (app.getSetAdj() >= CACHED_APP_MIN_ADJ) {
    final IApplicationThread thread = app.getThread();
    if (thread != null) {
        try {
            thread.scheduleTrimMemory(TRIM_MEMORY_BACKGROUND);
        } catch (RemoteException e) {
            // do nothing
        }
    }
}
```

**调用链**：
```
lmkd (kernel PSI/lowmem) → ActivityManager 收到 kill 决策 → 
CachedAppOptimizer 决定 freeze → IApplicationThread.scheduleTrimMemory(40) → 
ActivityThread.handleTrimMemory → Application#onTrimMemory(40) → 
mFreezeHandler 延迟若干秒后 cgroup-freeze
```

**重要限制**：
- 这是一次性 trim 回调，不是持续配额管理
- 仅对即将被 freeze 的 cached 进程生效
- 不影响正在运行的后台任务

## 2. MemoryLimiter 架构设计

### 2.1 系统定位

`MemoryLimiter` 是 Android 17 引入的**独立内存配额系统**，具有以下特点：

- **并行运行**：与 `onTrimMemory` 回调路径完全独立
- **进程配额**：基于 cgroup v2 实现进程级内存配额
- **多级配额**：根据进程状态（visible/notVisible/cached）应用不同配额
- **第二道防线**：在 lmkd 和 CachedAppOptimizer 之外增加内存管理层次

### 2.2 三种 LimitType

```java
static final int LIMIT_TYPE_UNKNOWN = 0;
static final int LIMIT_TYPE_MEMORY = 1;        // memory.high 触发
static final int LIMIT_TYPE_SWAP = 2;          // memory.swap.high 触发
static final int LIMIT_TYPE_ANON_SWAP = 3;     // anon + swap 之和超阈值
```

**机制解析**：
- `memory.high` 和 `memory.swap.high` 是 cgroup v2 的**软限制**
- 进程超限时会被 throttle 但不会立即 OOM kill
- MemoryLimiter 通过监听 `memory.events` 文件，将软限制转化为**30秒宽限后强制kill**的硬约束

### 2.3 基于 Process State 的配额矩阵

MemoryLimiter 根据进程状态应用不同的配额策略：

| Process State | 内存配额 | 交换配额 | 说明 |
|---------------|----------|----------|------|
| Top/BoundTop/ImportantForeground/TopSleeping | memVisible | swapVisible | 前台应用配额 |
| ForegroundService/ImportantBackground/Service/Receiver/Backup | memNotVisible | swapNotVisible | 后台任务配额 |
| CachedActivity/CachedRecent/CachedEmpty | LIMIT_IS_IGNORED | LIMIT_IS_DISABLED | 由 lmkd 接管 |
| Persistent/PersistentUI | LIMIT_IS_DISABLED | LIMIT_IS_DISABLED | 系统进程无限制 |

**设计要点**：
- **visible 进程**应用较宽松的配额，保证前台性能
- **notVisible 进程**应用较严格的配额，限制后台资源占用
- **cached 进程**不受 MemoryLimiter 控制，由传统 lmkd 机制处理
- **system_server 等系统进程**无配额限制

## 3. 源码实现细节

### 3.1 配额应用路径

**Java 控制器**：
```java
case MESSAGE_CONFIG -> {
    if (msg.obj != null && !shouldIgnore(uid)) {
        Limits limit = (Limits) msg.obj;
        configureLimit(service, pid, uid, limit.memHigh, limit.swapHigh);
    }
}
```

**JNI cgroup 写入**：
```cpp
writeLimit(cgroupPath(CgroupFile::kMemoryHigh), limit);   // 写到 memory.high
writeLimit(cgroupPath(CgroupFile::kSwapMax), limit);      // 写到 memory.swap.high
```

**关键文件**：
- `kMemoryEvent`：监听 high/swap.high 触发
- `kMemoryHigh`：写入 memory.high 限制
- `kSwapMax`：写入 memory.swap.high 限制

### 3.2 触发与 kill 机制

**触发入口**：
```java
public void onLimitExceeded(int pid, int uid, int type, long memHigh, long swapHigh,
        String pkg) {
    
    if (type == LIMIT_TYPE_ANON_SWAP) {
        // 触发 profiling
        ProfilingServiceHelper helper = ProfilingServiceHelper.getInstance();
        helper.onProfilingTriggerOccurred(uid, pkg, ProfilingTrigger.TRIGGER_TYPE_ANOMALY);
        
        // 30秒后 kill
        Message msg = mQueue.obtainMessage(MESSAGE_KILL, pid, uid,
                "MemoryLimiter:AnonSwap");
        mQueue.sendMessageDelayed(msg, KILL_DELAY_MS);   // 30秒
    }
}
```

**完整调用链**：
```
cgroup memory.events:high 或 memory.events:swap.high 触发
  → JNI 回调 Java onLimitExceeded(pid, uid, LIMIT_TYPE_ANON_SWAP, memHigh, swapHigh)
  → ProfilingServiceHelper.onProfilingTriggerOccurred(TRIGGER_TYPE_ANOMALY)
  → mQueue.sendMessageDelayed(MESSAGE_KILL, 30s)
  → killProcess(pid, uid, "MemoryLimiter:AnonSwap")
  → ApplicationExitInfo.REASON_OTHER + description="MemoryLimiter:AnonSwap"
```

**30秒宽限期的作用**：
- 让 ProfilingServiceHelper 完成 heap dump 抓取
- 为异常诊断提供现场数据
- 避免频繁 kill 影响系统稳定性

### 3.3 inotify 监听机制

JNI 使用 `inotify_add_watch` 监听 `memory.events` 文件变化：

```cpp
void watch(int inotify_fd, wdmap_t& wdmap, Statistics& stats) {
    if (mMemWatcher.mWd == UNSET) {
        std::string cpath = cgroupPath(CgroupFile::kMemoryEvent);
        char const* path = cpath.c_str();
        int memWd = inotify_add_watch(inotify_fd, path, IN_MODIFY);
        // ... 监听逻辑
    }
}
```

**双模式监听**：
- **inotify 监听**：实时响应 memory.events 变化
- **轮询备份**：inotify 失败时使用轮询机制

## 4. 与现有系统的协作

### 4.1 与 lmkd 的关系

| 系统 | 作用范围 | 触发条件 | 处理方式 |
|------|----------|----------|----------|
| MemoryLimiter | 运行中的后台任务 | 内存/交换配额超限 | 30秒后强制kill |
| lmkd | 所有进程（包括cached） | 系统内存压力 | 立即或延迟kill |

**分工原则**：
- MemoryLimiter 专注于**运行中的后台任务**
- lmkd 专注于**系统内存压力下的进程清理**
- 两者形成互补，覆盖不同场景

### 4.2 与 CachedAppOptimizer 的关系

| 系统 | 工作时机 | 作用对象 | 处理方式 |
|------|----------|----------|----------|
| CachedAppOptimizer | 进程冻结前 | cached 进程 | 下发 trim 回调 |
| MemoryLimiter | 运行时 | 后台任务 | 配额限制 + 30秒后kill |

**协作流程**：
1. CachedAppOptimizer 对即将冻结的 cached 进程下发 `TRIM_MEMORY_BACKGROUND(40)`
2. MemoryLimiter 对正在运行的后台任务进行配额管理
3. 两者互不干扰，覆盖不同生命周期的进程

### 4.3 配置来源

MemoryLimiter 的配额阈值来自 `/vendor/etc/memory-limiter-config.xml`：

```xml
<!-- 内存配额配置 -->
<memVisible>256MB</memVisible>
<memNotVisible>128MB</memNotVisible>
<swapVisible>512MB</swapVisible>
<swapNotVisible>256MB</swapNotVisible>
```

**与传统内存管理的区别**：
- **不依赖 minfree 缩放**：配额阈值固定，不受系统可用内存影响
- **vendor 配置**：由设备厂商根据硬件特性定制
- **进程状态感知**：根据进程重要性应用不同配额

## 5. 实战应用

### 5.1 应用适配建议

**内存使用优化**：
- 后台服务控制内存使用在 `memNotVisible` 配额以下
- 前台活动确保内存使用在 `memVisible` 配额以下
- 避免在后台任务中进行大量内存分配

**oom_score_adj 调优**：
- 关键后台任务适当提高 oom_score_adj
- 非关键任务降低优先级，让 lmkd 优先处理
- 避免 cached 进程中保留大量内存

**监控与调试**：
- 使用 `adb shell dumpsys meminfo` 检查进程状态
- 监控 `ApplicationExitInfo` 中的 kill 原因
- 分析 cgroup memory.events 文件查看配额触发情况

### 5.2 Profiling 集成

MemoryLimiter 与 ProfilingServiceHelper 深度集成：

```java
// 触发异常检测
helper.onProfilingTriggerOccurred(uid, pkg, ProfilingTrigger.TRIGGER_TYPE_ANOMALY);

// 获取 heap dump
HeapDumpResult result = helper.dumpHeapForProcess(uid, pkg);
```

**应用场景**：
- 内存异常时的自动 heap dump
- 内存泄漏的自动检测
- 内存使用模式的性能分析

### 5.3 性能影响分析

**正面影响**：
- 更精准的内存配额管理
- 减少意外 OOM 发生
- 提高系统整体稳定性

**潜在问题**：
- 30秒延迟可能影响用户体验
- 配额设置不当可能导致频繁 kill
- 与其他内存管理机制的冲突

## 6. 未来发展趋势

### 6.1 可能的改进方向

1. **更灵活的配额策略**
   - 支持动态调整配额阈值
   - 基于应用类型定制配额策略
   - 引入机器学习优化配额分配

2. **更精确的监控机制**
   - 实时内存使用监控
   - 更细粒度的内存分类统计
   - 内存使用模式识别

3. **与其他系统组件的协同**
   - 与 PowerManager 协同优化
   - 与 ThermalManager 协同散热
   - 与 PerformanceManager 协同调优

### 6.2 兼容性考虑

**向后兼容**：
- 传统 trim 回调继续有效
- 现有应用无需修改即可工作
- 配置可向后兼容

**升级建议**：
- 新应用应考虑 MemoryLimiter 配额
- 后台服务实现内存使用监控
- 准备应对可能的内存限制

## 7. 总结

Android 17 的 MemoryLimiter 代表了内存管理的一个重要演进：

1. **双重防线**：与传统 lmkd 形成互补，提供更全面的内存保护
2. **精准配额**：基于进程状态的多级配额策略，平衡性能和资源利用
3. **智能触发**：30秒宽限期 + profiling 集成，提供更好的诊断能力
4. **vendor 定制**：设备厂商可根据硬件特性优化配额策略

这套系统为 Android 平台带来了更精细的内存管理能力，但也需要开发者更好地理解和适配新的内存使用模式。随着 Android 17 的普及，理解和优化 MemoryLimiter 将成为应用性能优化的重要课题。
