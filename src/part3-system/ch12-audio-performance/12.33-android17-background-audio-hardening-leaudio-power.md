# 12.33 Android 17 后台音频硬化与 LE Audio 功耗边界

<!-- outline-start -->
## 要点

### 🔹 后台音频硬化机制
- Android 17 的后台音频硬化不能只看一个 Java 层入口：焦点、音量等 AudioManager API 先经过 `HardeningEnforcer`，播放 Track 创建/运行侧还要经过 AudioFlinger C++ 路径的 `Tracks::getHardeningDecision()`。
- 两侧都读取 `IAudioPolicyService.HardeningOverride` 的 `DEFAULT` / `ENABLE` / `DISABLE` / `THROW` 四态覆盖，但判定粒度不同：Java 侧偏 AppOps 与 API 方法，C++ 侧按 usage、权限、targetSdk 与 hardening flag 对每条 Track 判定。
- 因此排障时应把“焦点申请失败”“音量 API 无效”和“Track 静音/被拦截”分开看：任一侧拒绝都可能形成用户可见的后台音频异常。

### 🔹 版本边界与启动期边界
- 本节只讨论 Android 17 / API 37、`android-17.0.0_r1` 基线；不外推 Android 18/API38+ 主线行为。
- ART Mainline / Cloud Profile 不是音频策略输入，也不会改写 AudioService、AudioPolicyService 或 Bluetooth 音频服务启动顺序；它只可能在首启、OTA 后首次开机、BCP APEX 变化后通过 boot dexopt 阻塞 SystemServer 后续阶段。
- 运行期后台音频失败优先回到 HardeningEnforcer、AppOps、usage/permission/targetSdk 与 `Tracks::getHardeningDecision()`；只有问题集中在首启或升级后窗口时，才把 ART/PackageManager boot dexopt 纳入同一张排障表。

### 🔹 LE Audio 功耗边界的当前证据状态
- 本章只把 LE Audio、LC3 offload、ADSP/Spatial Audio 传输等功耗治理主题作为边界说明；当前可审材料主要支撑“后台音频硬化”和“ART 启动期边界”。
- 现阶段不能把 ART Profile、boot dexopt 或 Cloud Dexopt Artifacts 解释为 LE Audio codec offload、ADSP 分工、Bluetooth ISO/ACL 传输选择的策略输入。
- 若后续要写成 LE Audio 功耗治理专题，仍需要补充 android-17.0.0_r1 下 Bluetooth/audio HAL/AudioPolicy 相关源码材料。

## 扩展

### 🔸 实际应用场景
- 后台媒体播放：确认应用可见性、前台服务形态、AppOps、targetSdk 与 Track usage 是否满足硬化路径。
- 闹钟/提醒：重点核对 `AUDIO_USAGE_ALARM`、`SCHEDULE_EXACT_ALARM` / `USE_EXACT_ALARM` 权限与 partial exemption。
- OTA 后首次开机音频异常：同时查看 boot dexopt 日志和 AudioHardening 日志，避免把启动期编译阻塞误判为运行期音频策略拒绝。

### 🔸 调试实践
- 音频硬化覆盖：使用 Android 17 源码材料确认的 `cmd audio set-hardening <enable|disable|throw>` 与 `cmd audio clear-hardening`，不要继续使用未在材料中确认的 `set-enable-hardening` 形式。
- 拒绝日志：运行期问题优先采集 `AudioHardening`、AudioFocus、AudioFlinger Track 相关日志。
- 启动期问题：只在首启、OTA 后首次开机、ART/BCP APEX 更新后补查 `Starting boot dexopt for reason ...` 与 `ArtManagerLocal.onBoot` 进度。

> [!NOTE]
> 上面的 outline 是流水线保留区，其中“Java + C++ 双源链路”容易被理解成两层对同一个事件重复判定。固定标签源码显示，两层处理的对象不同：Java 层检查音量、铃声和 audio focus 控制调用，AudioFlinger 检查 playback track。以下正文按这个边界展开。

## 1. 本章的固定锚点

本文只采用 Android 17 / API 37 / `android-17.0.0_r1`。LE Audio 的 controller、DSP 和耳机固件并不由 common kernel tag 完整描述；涉及主机内核调度或驱动时，统一以 `android17-6.18-2026-06_r6` 为基线。

“后台没声音”至少可能落在四个不同位置：

| 位置 | 处理对象 | 受限后的常见表现 | 主要证据 |
|---|---|---|---|
| `system_server` / `HardeningEnforcer` | 音量、铃声、audio focus 控制调用 | 调用成为 no-op、focus 返回失败，测试模式下也可能抛异常 | `AudioHardening`、调用返回值、`dumpsys audio` |
| `audioserver` / AudioFlinger | playback track | Track 因 control AppOp 被静音 | Track 创建日志、hardening event、AudioFlinger dump |
| AudioPolicy 与 Bluetooth Audio HAL | route 与音频会话 | Track 正常运行但未送往目标 BLE 设备 | audio policy、HAL session、当前 routed device |
| Bluetooth LE Audio stack | group、ASE、CIS/BIS、codec 与 data path | 已连接但未进入 streaming，或继续走 host codec | Bluetooth dump、HCI/OEM trace、codec location |

前两行共享 hardening override 和部分兼容规则，执行对象与失败方式仍需分开分析。后两行处理路由和无线音频会话，不读取 `HardeningEnforcer` 的 Java 决策结果。

## 2. Java 路径：控制调用在进入业务逻辑前被检查

### 2.1 音量与铃声入口

Android 17 的 [`AudioService.java`](https://android.googlesource.com/platform/frameworks/base/+/refs/tags/android-17.0.0_r1/services/core/java/com/android/server/audio/AudioService.java) 在以下入口调用 `blockVolumeMethod()`：

- `adjustStreamVolume()`；
- `setStreamVolumeWithAttribution()`；
- `setRingerModeExternal()`；
- `adjustVolume()`；
- `adjustSuggestedStreamVolume()`。

[`HardeningEnforcer.blockVolumeMethod()`](https://android.googlesource.com/platform/frameworks/base/+/refs/tags/android-17.0.0_r1/services/core/java/com/android/server/audio/HardeningEnforcer.java) 依次 note `OP_CONTROL_AUDIO_PARTIAL` 和 `OP_CONTROL_AUDIO`。两级 AppOp 均允许时，该方法直接返回 `false`，后面的 override、target SDK 和 exact-alarm 兼容规则不会参与这次调用。

AppOp 已受限时，默认模式再选择允许、PARTIAL 或 FULL enforcement：

| 条件 | 默认模式下的结果 |
|---|---|
| 特权音频调用者 | 允许 |
| 持有 `USE_EXACT_ALARM`，或具备 schedule-exact-alarm 能力 | PARTIAL |
| `hardeningPartialVolume()` 关闭 | 允许 |
| `targetSdk < 37` | PARTIAL |
| 其余调用者 | FULL |

音量 API 没有 `AudioAttributes` 参数，因此 exact-alarm 分支不会检查 `USAGE_ALARM`。Automotive 设备走 `autoPublicVolumeApiHardening()` 的单独分支，不能套用上表。

PARTIAL 和 FULL 表示采用哪一级 control AppOp 作为限制门槛，并不表示固定的音量比例。`blockVolumeMethod()` 返回 `true` 后，`AudioService` 的这些入口直接返回，应用看到的是调用没有改变系统音量。

### 2.2 Audio focus 入口

Focus 使用另一组 AppOp：先 note `OP_TAKE_AUDIO_FOCUS`，再 note `OP_CONTROL_AUDIO`。`OP_TAKE_AUDIO_FOCUS` 已拒绝时记为 partial restriction；前者允许而 `OP_CONTROL_AUDIO` 拒绝时记为 full restriction。

下面的固定标签代码用于确认 hardening 与焦点仲裁的先后关系：

```java
if (mHardeningEnforcer.blockFocusMethod(uid,
        HardeningEnforcer.METHOD_AUDIO_MANAGER_REQUEST_AUDIO_FOCUS,
        clientId, focusReqType, callingPackageName, attributionTag, sdk, aa)) {
    return AudioManager.AUDIOFOCUS_REQUEST_FAILED;
}
return mMediaFocusControl.requestAudioFocus(...);
```

Hardening 命中后，请求在 `AudioService` 内提前结束，不会进入 `MediaFocusControl`。因此 `mFocusStack`、external focus policy、delayed focus 等状态都无法解释这一次拒绝。

默认模式的 focus 兼容顺序还包含 usage：

1. 特权音频调用者放行；
2. `USAGE_ALARM` 同时具备精确闹钟能力时采用 PARTIAL；
3. 特定兼容 flag 与旧 target SDK 组合可放行；
4. 持有 `BLUETOOTH_CONNECT` 时采用 PARTIAL；
5. `targetSdk < 37` 时采用 PARTIAL；
6. strict flag 关闭时采用 PARTIAL；
7. 其余调用者采用 FULL。

`BLUETOOTH_CONNECT` 只降低 enforcement level。它不会维持 LE Audio 连接，也不会跳过 AppOps、前台服务或 AudioPolicy 路由检查。

## 3. AudioFlinger 路径：为 playback track 选择限制等级

[`Tracks.cpp::getHardeningDecision()`](https://android.googlesource.com/platform/frameworks/av/+/refs/tags/android-17.0.0_r1/services/audioflinger/Tracks.cpp) 在 `AfPlaybackCommon` 构造期间读取 track usage、调用 UID、权限、flags 和 override，返回 `NONE`、`PARTIAL` 或 `FULL`。

固定标签中的 DEFAULT 决策顺序如下：

1. `AUDIO_USAGE_VIRTUAL_SOURCE` 和 system usage 返回 `NONE`；
2. 持有 `MODIFY_AUDIO_ROUTING` 或 `MODIFY_PHONE_STATE` 返回 `NONE`；
3. strict 模式下，满足闹钟条件、持有 `BLUETOOTH_CONNECT` 或 `targetSdk < 37` 返回 `PARTIAL`；
4. strict 模式下其余情况返回 `FULL`；
5. strict 关闭后，根据 partial flag 返回 `PARTIAL` 或 `NONE`。

Enforcement level 还要与 AppOp 状态结合。下面的函数节选用于说明映射关系：

```cpp
bool isPlaybackRestrictedControl() const {
    switch (mEnforcementLevel) {
        case EnforcementLevel::NONE:
            return false;
        case EnforcementLevel::PARTIAL:
            return !hasOpControlPartial();
        case EnforcementLevel::FULL:
            return !hasOpControlFull();
    }
}
```

`FULL` 自身不会立即把 track 音量设为零；full control AppOp 不允许时，该函数才报告 control restriction。`PlaybackTrack::isPlaybackRestricted()` 还会合并 `OP_PLAY_AUDIO` 等条件，排查静音不能只读 enforcement level。

对于需要 hardening 的非可信 UID，`AfPlaybackCommon` 创建 partial 与 full 两个 `AppOpsSession`。Offload/MMAP track 收到权限回调后，会用 `asyncBroadcast(40ms)` 唤醒线程，让两路回调有时间汇合。这个 40 ms 是权限回调的延迟广播参数，不能当作 `AudioTrack` 创建固定耗时。

`maybeLogPlaybackHardening()` 使用 `mPlaybackHardeningLogged.exchange(true, std::memory_order_acq_rel)`，使每条 track 最多上报一次 hardening event。事件经 `IAudioManagerNative` 回到 `AudioService`，Java 侧校验调用 UID 为 `AUDIOSERVER_UID` 后再写 counter、EventLogger 和 stats atom。

## 4. Override：共享状态，不共享执行结果

`AudioService.setHardeningOverride()` 更新 Java 侧缓存，再通过 AudioPolicy 把同一状态送到 audioserver。四种状态的边界如下：

| Override | Java 控制调用 | AudioFlinger playback |
|---|---|---|
| `DEFAULT` | 按 AppOps、权限、usage、target SDK 与 flags 判断 | 按 usage、权限、target SDK、flags 与 AppOps 判断 |
| `DISABLE` | AppOp 已受限时也按允许处理 | enforcement level 为 `NONE` |
| `ENABLE` | AppOp 已受限时采用 FULL | enforcement level 为 `FULL` |
| `THROW` | 受限的音量/focus 调用抛 `IllegalStateException` | 与 `ENABLE` 一样映射为 `FULL`，不会让 `AudioTrack.write()` 自动抛同类异常 |

`ENABLE` 不是给 AppOps 注入拒绝状态。两级 AppOp 均允许的 Java 调用会在读取 override 前放行；native 路径也要结合 AppOp 才能确定 track 是否受限。

Android 17 固定标签的 [`AudioManagerShellCommand.java`](https://android.googlesource.com/platform/frameworks/base/+/refs/tags/android-17.0.0_r1/services/core/java/com/android/server/audio/AudioManagerShellCommand.java) 注册了 `set-hardening` 和 `clear-hardening`。下面的命令用于隔离测试设备上的 A/B 与取证：

```bash
adb shell cmd audio help | grep -A 3 hardening
adb shell cmd audio set-hardening enable
adb shell cmd audio set-hardening disable
adb shell cmd audio set-hardening throw
adb shell cmd audio clear-hardening

adb shell dumpsys audio | grep -A 30 -i hardening
adb logcat -d -b all | grep AudioHardening
```

`set-hardening default` 也能被 parser 接受；`clear-hardening` 更直观地表达“恢复默认政策”。`disable` 是强制关闭 override，不能用它表示恢复默认。测试结束要执行 `clear-hardening`，并记录设备 `cmd audio help` 输出，避免把预览镜像或厂商分支的命令差异混入结论。

## 5. LE Audio 的功耗边界

后台 hardening、LE Audio background scan 和 LC3 codec location 属于三套独立状态。它们可能同时影响一个播放用例，但没有固定的串行调用关系。

### 5.1 Suspend 与 background scan

[`LeAudioService.setSystemSuspended()`](https://android.googlesource.com/platform/packages/modules/Bluetooth/+/refs/tags/android-17.0.0_r1/android/app/src/com/android/bluetooth/le_audio/LeAudioService.java) 给出了 suspend/resume 对 scanner 的直接动作。以下代码用于确认服务层行为：

```java
public void setSystemSuspended(boolean suspended) {
    mSystemSuspended = suspended;
    if (suspended) {
        mScanCallback.stopBackgroundScan();
    } else if (isScannerNeeded()) {
        mScanCallback.startBackgroundScan();
    }
}
```

Suspend 入口提交停止 background scan；resume 后只在 `isScannerNeeded()` 返回 `true` 时恢复。扫描工作由 scan thread 异步处理，方法返回不代表 controller 已同步停止扫描。节能幅度还受 controller offload、广告密度、固件和 suspend residency 影响，AOSP Java 代码给不出统一百分比。

### 5.2 Host 与 ADSP codec location

[`codec_manager.cc`](https://android.googlesource.com/platform/packages/modules/Bluetooth/+/refs/tags/android-17.0.0_r1/system/bta/le_audio/codec_manager.cc) 默认使用 `CodecLocation::HOST`。构造阶段满足以下两个 gate 后才切到 `ADSP`：

- `ro.bluetooth.leaudio_offload.supported=true`，并且 `persist.bluetooth.leaudio_offload.disabled=false`；
- `LeAudioHalVerifier::SupportsLeAudioHardwareOffload()` 返回支持。

后续还要由 HAL offload capability、codec preference 和目标 audio set configuration 共同完成配置匹配。LC3 的采样率、frame duration、每条 ISO stream 的通道数、每帧字节数都属于匹配维度。

HOST 表示 Bluetooth/audio 的主机侧 codec 路径，不等于应用进程负责 LC3 编解码。ADSP 路径也不能只靠系统属性确认；属性为 true 只能证明产品声明允许尝试 offload。

### 5.3 功耗结论怎样取证

以下命令用于收集 route、服务与 offload gate 的基础快照：

```bash
adb shell getprop ro.bluetooth.leaudio_offload.supported
adb shell getprop persist.bluetooth.leaudio_offload.disabled
adb shell dumpsys media.audio_policy > audio-policy.txt
adb shell dumpsys media.audio_flinger > audio-flinger.txt
adb shell dumpsys bluetooth_manager > bluetooth.txt
```

这些输出能够缩小调查范围，不能单独证明 ADSP 正在工作或给出节能比例。功耗实验至少要固定手机 build、耳机固件、音量、音频内容、空间音频、射频环境、温度和屏幕状态，并同时记录：

- 当前 routed device、AudioFocus 和 Track 状态；
- LE Audio group、ASE、CIS/BIS 与 codec configuration；
- Bluetooth Audio HAL session 与 codec location；
- AP CPU time、suspend residency、DSP/controller 指标和 power rail；
- 耳机侧电流或 telemetry。

同机多轮 A/B 才能区分收益来自 background scan、host/ADSP codec、无线条件或耳机固件。

## 6. ART boot dexopt 只作为时序旁证

ART Mainline profile 和 boot dexopt 不参与 audio hardening、AudioPolicy route、LC3 配置或 Bluetooth ISO transport。`ArtManagerLocal.onBoot()` 在首启、OTA 后首次开机或 Mainline 更新场景可能长时间阻塞 package dexopt 路径；这项信息只能帮助解释“升级后开机阶段整体服务就绪较慢”。

运行数分钟后仍可稳定复现的 focus 拒绝、Track 静音或 LE Audio 功耗偏高，应回到前五节的证据。只有异常严格集中在首启或升级后的启动窗口，才补查 `ArtManagerLocal.onBoot()` 和 boot dexopt reason。ART 日志无法证明音频政策发生变化。

## 7. 排障顺序

遇到“后台播放在蓝牙耳机上无声”，按以下顺序缩小范围：

1. 记录 `requestAudioFocus()` 返回值；失败时检查 Java hardening 与 focus AppOps；
2. 确认音量/铃声调用是否被 `blockVolumeMethod()` 处理；
3. 检查 playback track 的 enforcement level、control AppOp 与 mute state；
4. 确认 AudioPolicy 当前 route 指向目标 BLE device；
5. 检查 LE Audio group、ASE、CIS 和 HAL session 是否进入 streaming；
6. 读取 codec location 与 offload capability，避免用 CPU 下降反推 ADSP；
7. 若现象只出现在升级后开机窗口，再补查 boot dexopt。

更完整的 hardening 决策可参阅 [5.23 Android 17 后台音频 Hardening 与 LE Audio 功耗边界](../../part1-fundamentals/ch05-cpu-power/5.23-android17-background-audio-hardening-leaudio-power-source.md)，LE Audio 端到端路径与功耗实验可参阅 [18.1 Android 17 蓝牙低功耗音频与功耗优化](../../part4-system/ch18-connectivity/18-android17-bluetooth-le-audio-power-optimization.md)。
