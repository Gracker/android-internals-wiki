# 12.33 Android 17 后台音频硬化与 LE Audio 功耗治理

<!-- outline-start -->
## 要点

### 🔹 后台音频硬化机制
- Android 17 的后台音频硬化不能只看一个 Java 层入口：焦点、音量等 AudioManager API 先经过 `HardeningEnforcer`，播放 Track 创建/运行侧还要经过 AudioFlinger C++ 路径的 `Tracks::getHardeningDecision()`。
- 两侧都读取 `IAudioPolicyService.HardeningOverride` 的 `DEFAULT` / `ENABLE` / `DISABLE` / `THROW` 四态覆盖，但判定粒度不同：Java 侧偏 AppOps 与 API 方法，C++ 侧按 usage、权限、targetSdk 与 hardening flag 对每条 Track 判定。
- 因此排障时应把“焦点申请失败”“音量 API 无效”和“Track 静音/被拦截”分开看：任一侧拒绝都可能形成用户可见的后台音频异常。

### 🔹 版本边界与启动期边界
- 本节只讨论 Android 17 / API 37、`android-17.0.0_r1` 基线；不外推 Android 18/API38+ 主线行为。
- ART Mainline / Cloud Profile 不是音频策略输入，也不会改写 AudioService、AudioPolicyService 或 Bluetooth 音频服务启动顺序；它只可能在首启、OTA 后首次开机、BCP APEX 变化后通过 boot dexopt 阻塞 SystemServer 后续阶段。
- 运行期后台音频失败优先回到 HardeningEnforcer、AppOps、usage/permission/targetSdk 与 `Tracks::getHardeningDecision()`；只有问题集中在首启或升级后窗口时，才把 ART/PackageManager boot dexopt 纳入同一张排障表。

### 🔹 LE Audio 功耗治理的当前证据状态
- 本章标题包含 LE Audio、LC3 offload、ADSP/Spatial Audio 传输等功耗治理主题，但当前可审材料主要支撑“后台音频硬化”和“ART 启动期边界”。
- 现阶段不能把 ART Profile、boot dexopt 或 Cloud Dexopt Artifacts 解释为 LE Audio codec offload、ADSP 分工、Bluetooth ISO/ACL 传输选择的策略输入。
- LE Audio 功耗段落仍需要补充 android-17.0.0_r1 下 Bluetooth/audio HAL/AudioPolicy 相关源码材料后再定稿。

## 扩展

### 🔸 实际应用场景
- 后台媒体播放：确认应用可见性、前台服务形态、AppOps、targetSdk 与 Track usage 是否满足硬化路径。
- 闹钟/提醒：重点核对 `AUDIO_USAGE_ALARM`、`SCHEDULE_EXACT_ALARM` / `USE_EXACT_ALARM` 权限与 partial exemption。
- OTA 后首次开机音频异常：同时查看 boot dexopt 日志和 AudioHardening 日志，避免把启动期编译阻塞误判为运行期音频策略拒绝。

### 🔸 调试实践
- 音频硬化覆盖：使用 Android 17 源码材料确认的 `cmd audio set-hardening <enable|disable|throw>` 与 `cmd audio clear-hardening`，不要继续使用未在材料中确认的 `set-enable-hardening` 形式。
- 拒绝日志：运行期问题优先采集 `AudioHardening`、AudioFocus、AudioFlinger Track 相关日志。
- 启动期问题：只在首启、OTA 后首次开机、ART/BCP APEX 更新后补查 `Starting boot dexopt for reason ...` 与 `ArtManagerLocal.onBoot` 进度。

## 1. Java + C++ 双源硬化链路

Android 17 的后台音频硬化是双源决策，而不是单点开关。2026-07-10 的源码调研指出，Java 层 `HardeningEnforcer` 覆盖 AudioManager 侧的焦点与音量入口，C++ 层 `Tracks::getHardeningDecision()` 则在 AudioFlinger Track 侧按每条播放流重新判定；两侧都从 `IAudioPolicyService.HardeningOverride` 读取 `DEFAULT`、`ENABLE`、`DISABLE`、`THROW` 四态覆盖。[来源: DeepResearch/2026-07-10-android17-background-audio-hardening-enforcer-decision-matrix.md]

Java 侧的关键特征是以 AppOps 三档守门：`OP_TAKE_AUDIO_FOCUS`、`OP_CONTROL_AUDIO_PARTIAL`、`OP_CONTROL_AUDIO` 分别影响焦点和音量相关 API。材料核对的调用点包括 `adjustStreamVolume`、`setStreamVolume`、`setRingerMode`、`adjustVolume`、`adjustSuggestedStreamVolume` 与 `requestAudioFocus`；其中焦点入口会先经过 hardening gate，再进入 `MediaFocusControl.requestAudioFocus()` 的焦点栈操作。[来源: DeepResearch/2026-07-10-android17-background-audio-hardening-enforcer-decision-matrix.md]

C++ 侧的关键特征是逐 Track 判定。`Tracks::getHardeningDecision()` 的决策顺序是：先处理 hardening override；再放行系统 usage；再检查 `MODIFY_AUDIO_ROUTING`、`MODIFY_PHONE_STATE` 等系统权限；随后结合 strict/partial hardening flag、usage、精确闹钟权限、targetSdk 等条件输出 enforcement level 与 exemption reason。[来源: DeepResearch/2026-07-10-android17-background-audio-hardening-enforcer-decision-matrix.md]

这解释了为什么同一类“后台音频异常”可能表现为不同失败模式：`requestAudioFocus()` 可返回 `AUDIOFOCUS_REQUEST_FAILED`，音量 API 可能被拦截或无效，而播放流可能在 Track 层被强制处理。排障时不能只看 AudioManager 返回值，也不能只看 AudioFlinger Track 日志；应把 Java API gate 与 C++ Track gate 同时纳入证据链。[来源: DeepResearch/2026-07-10-android17-background-audio-hardening-enforcer-decision-matrix.md]

## 2. Hardening override 与 adb 调试命令

调研材料明确修正了早期“shell 命令缺失”的判断：`AudioManagerShellCommand` 在 `android-17.0.0_r1` 已支持 `set-hardening <enable|disable|throw>` 与 `clear-hardening`，用于临时覆盖 hardening 状态。[来源: DeepResearch/2026-07-10-android17-background-audio-hardening-enforcer-decision-matrix.md]

```bash
# 强制启用/禁用/抛错模式（以设备实际 help 输出为准）
adb shell cmd audio set-hardening enable
adb shell cmd audio set-hardening disable
adb shell cmd audio set-hardening throw

# 清除覆盖，回到 DEFAULT
adb shell cmd audio clear-hardening

# 采集硬化拒绝线索
adb logcat | grep AudioHardening
```

调试时建议先确认 override 是否被人为设置。如果 override 为 `DISABLE`，某些本该被拦截的后台行为会被放行；如果 override 为 `ENABLE` 或 `THROW`，则会更接近强制执行或异常暴露模式。只有清除 override 后，AppOps、usage、permission、targetSdk 与 hardening flag 的默认矩阵才具有排障代表性。[来源: DeepResearch/2026-07-10-android17-background-audio-hardening-enforcer-decision-matrix.md]

## 3. SystemServer / ART Profile：只影响启动期边界，不是音频策略

2026-07-17 的 SystemServer / ART Mainline 调研补充了一个容易误判的边界：Android 17 中所谓 Cloud Profile 更接近 ART Profile / Cloud Dexopt Artifacts，由 ART Mainline APEX (`com.android.art`) 驱动，在 SystemServer 启动期间通过 profile 合并与 dexopt 影响系统服务代码的装载/编译状态；它不是 AudioService、AudioPolicyService、Bluetooth 音频服务或 LE Audio 功耗策略的输入。[来源: DeepResearch/2026-07-17-android17-cloud-profiles-systemserver-onboot.md]

`ArtModuleServiceInitializer.setArtModuleServiceManager(new ArtModuleServiceManager())` 位于 `SystemServer.startBootstrapServices()` 的最早阶段，用于提前触发 `service-art.jar` 的 class linker，避免后续 PackageManagerService 分配大量对象触发 GC 时与 class linker 互斥造成 b/263486535 死锁。该入口不是音频服务初始化入口，也不会插入新的音频服务启动顺序。[来源: DeepResearch/2026-07-17-android17-cloud-profiles-systemserver-onboot.md]

真正可能影响“音频何时可被上层稳定使用”的，是 `SystemServer.startOtherServices()` 后续调用 `DexOptHelper.initializeArtManagerLocal(...)` 与 `mPackageManagerService.updatePackagesIfNeeded()`，再进入 `DexOptHelper.performPackageDexOptUpgradeIfNeeded()`。在首次开机、OTA 后首次开机、或 BCP APEX 变化后，它会调用 `ArtManagerLocal.onBoot(reason, ...)`；材料引用的源码注释说明该方法是 blocking，耗时约 30 秒到数分钟。[来源: DeepResearch/2026-07-17-android17-cloud-profiles-systemserver-onboot.md]

因此，若 AudioTrack / AudioFocus 的失败只在普通运行期出现，应优先回到 HardeningEnforcer、AppOps、usage/permission/targetSdk 与 `Tracks::getHardeningDecision()`；若问题集中在 OTA 后或 ART Mainline APEX 更新后的首次开机窗口，则应额外核对 boot dexopt 是否正在阻塞 SystemServer 后续阶段，而不能直接归因于 LE Audio codec offload 或后台音频硬化。[来源: DeepResearch/2026-07-17-android17-cloud-profiles-systemserver-onboot.md][来源: DeepResearch/2026-07-10-android17-background-audio-hardening-enforcer-decision-matrix.md]

| 场景 | ART/Profile 行为 | 对音频排障的意义 |
|------|------------------|------------------|
| 首次开机 / factory reset | `REASON_FIRST_BOOT` 触发整包 dexopt；材料说明首次开机时 ART Mainline Profile 同步通常尚未完成 | 首启音频服务延迟更可能来自系统整体 dexopt/初始化窗口，不宜直接判定为后台硬化拒绝 |
| OTA 后首次开机 | `REASON_BOOT_AFTER_OTA` 触发 `ArtManagerLocal.onBoot(...)`，可处理 pre-reboot staged files | OTA 后短时音频不可用或焦点恢复延迟，需要同时查看 boot dexopt 日志与 AudioHardening 日志 |
| BCP APEX 变化 / ART Mainline 更新 | `hasBcpApexesChanged()` 通过 `ApexManager.getActiveApexInfos()` 判断 active APEX 变化，命中后使用 `REASON_BOOT_AFTER_MAINLINE_UPDATE` | ART APEX 更新后的启动期抖动属于编译/提交产物路径；普通启动无该 reason 时，不应把运行期 LE Audio 功耗异常归因于 Cloud Profile |

## 4. LE Audio 功耗治理：本轮不能 finalized 的缺口

本章标题中的 LE Audio、LC3 codec offload、ADSP 协同、Spatial Audio 传输选择属于音频功耗治理的重要方向，但本轮可审材料没有提供足够的 android-17.0.0_r1 源码链路来支撑这些结论。尤其不能仅凭 ART Profile / Cloud Dexopt 材料推出 Bluetooth LE Audio codec offload、ADSP 分工或 ISO/ACL 传输策略变化。

为避免把不同子系统混写，本轮保留 LE Audio 作为待补证据范围：后续应补齐 Bluetooth/audio HAL、AudioPolicy、LE Audio codec/offload、Spatial Audio latency mode 相关的 Android 17 源码材料，再决定是否将本章推进到 `finalized`。在补证前，本章可作为后台音频硬化与启动期边界的复查稿，但不应作为 LE Audio 功耗治理的最终定稿。
