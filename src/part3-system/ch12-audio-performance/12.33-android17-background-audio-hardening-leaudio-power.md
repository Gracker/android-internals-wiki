### Android 17 源码级硬化机制补充（基于源码调研）

基于 Android 17 官方文档源码调研，我们对后台音频硬化机制有以下深度发现：

#### 两层硬化架构（API 37）

**基础层（所有 Android 17 应用）：**
- 必须有可见 activity 或非 SHORT_SERVICE 类型 foreground service
- 影响所有音频交互（播放、焦点、音量）

**API 37 附加层（应用 targetSdkVersion=37）：**
- 后台运行时，foreground service 必须具有 while-in-use (WIU) 能力
- WIU 获得条件：用户主动操作启动或应用可见时启动
- 豁免条件：exact alarm 权限 + USAGE_ALARM 属性的音频流

#### 失败模式细分

**静默失败（无异常）：**
- AudioTrack.write() - 播放静音
- setStreamVolume(), adjustVolume() - 音量调节无效
- setStreamMute(), setRingerMode() - 静音模式失效

**API失败（明确错误）：**
- requestAudioFocus() - 返回 AUDIOFOCUS_REQUEST_FAILED

#### Audio Managed SCO 重构实现

Android 17 将 SCO 连接管理从蓝牙框架迁移到音频框架：

```c++
// 伪代码：AudioFlinger 中硬化检查逻辑
bool AudioFlinger::checkAudioHardening(const sp<AudioPlaybackClient>& client) {
    // 基础层检查
    if (!client->hasVisibleActivity() && !client->hasValidFGS()) {
        return false;
    }
    
    // API 37 附加层检查
    if (client->isTargetApi37() && client->isInBackground()) {
        return client->getForegroundService()->hasWhileInUseCapability();
    }
    
    return true;
}
```

#### LE Audio 头部跟踪传输选择

Android 15 引入，Android 17 优化传输选择：

**传输机制优先级：**
1. le-acl：IMU 数据通过传感器栈
2. iso-hw：HT 数据直接蓝牙控制器 → 音频 DSP
3. iso-sw：IMU 数据通过传感器栈，无隧道化

**HAL 延迟模式对应：**
- FREE：无延迟约束
- LOW：<100ms，HT over ACL
- DYNAMIC_SPATIAL_AUDIO_SOFTWARE：ISO，框架处理 HT
- DYNAMIC_SPATIAL_AUDIO_HARDWARE：ISO，硬件加速 HT

#### FGS WIU 能力矩阵

| FGS 类型 | WIU 能力 | 获得条件 |
|---------|---------|----------|
| 标准 FGS | ✓ | 应用可见或后台启动能力 |
| 后台启动 FGS (BFSL) | ✓ | 用户主动意图（通知点击、小部件、媒体键） |
| 系统 FGS | ✓ | Telecom 库、VoiceInteractionService |


这些发现表明 Android 17 的音频硬化机制不仅提升了系统安全性，还通过统一架构改善了多设备场景下的音频一致性。

### SystemServer 启动期 ART Profile 对音频服务可用性的边界影响

本节原本聚焦后台音频与 LE Audio 的运行期治理；2026-07-17 的 SystemServer / ART Mainline 调研补充了一个需要在音频章节里明确的启动期边界：Android 17 的所谓 Cloud Profile 不是音频策略本身，也不会改写 AudioService、AudioPolicyService 或 Bluetooth 音频服务的启动顺序；它在源码中更接近 ART Profile / Cloud Dexopt Artifacts，由 ART Mainline APEX (`com.android.art`) 驱动，在 SystemServer 启动期通过 dexopt 与 profile 合并影响系统服务代码的装载/编译状态。[来源: DeepResearch/2026-07-17-android17-cloud-profiles-systemserver-onboot.md]

#### 启动顺序：不插入音频服务，只增加 dexopt 阻塞段

调研材料核对 `android-17.0.0_r1` 后指出，`ArtModuleServiceInitializer.setArtModuleServiceManager(new ArtModuleServiceManager())` 位于 `SystemServer.startBootstrapServices()` 的最早阶段，用于提前触发 `service-art.jar` 的 class linker，避免后续 PackageManagerService 分配大量对象触发 GC 时与 class linker 互斥造成 b/263486535 死锁；这不是音频服务初始化入口。[来源: DeepResearch/2026-07-17-android17-cloud-profiles-systemserver-onboot.md]

真正可能影响“音频何时可被上层稳定使用”的，是 `SystemServer.startOtherServices()` 后续调用 `DexOptHelper.initializeArtManagerLocal(...)` 与 `mPackageManagerService.updatePackagesIfNeeded()`，再进入 `DexOptHelper.performPackageDexOptUpgradeIfNeeded()`；在首启、OTA 后首次开机、或 BCP APEX 变化后，它会调用 `ArtManagerLocal.onBoot(reason, ...)`，而材料引用的源码注释说明该方法是 blocking，耗时约 30 秒到数分钟。[来源: DeepResearch/2026-07-17-android17-cloud-profiles-systemserver-onboot.md]

这意味着音频排障时应区分两类现象：若 AudioTrack / AudioFocus 的后台失败只在普通运行期出现，应优先回到 HardeningEnforcer、AppOps、usage/permission/targetSdk 以及 Tracks::getHardeningDecision() 的硬化路径；若问题集中在 OTA 后或 ART Mainline APEX 更新后的首次开机窗口，则需要额外核对 boot dexopt 是否正在阻塞 SystemServer 后续阶段，而不能直接归因于 LE Audio codec offload 或后台音频硬化。[来源: DeepResearch/2026-07-17-android17-cloud-profiles-systemserver-onboot.md][来源: DeepResearch/2026-07-10-android17-background-audio-hardening-enforcer-decision-matrix.md]

#### Cloud Profile 的源码身份：profile 输入，而非音频功耗策略

材料将 Cloud Profile 定位为 `com.android.server.art` 体系中的 `ProfilePath` 输入，包括 ref / cur / prebuilt / dm profile，并通过 `MergeProfileOptions.forBootImage` 与三类 classpath（`BOOTCLASSPATH`、`SYSTEMSERVERCLASSPATH`、`STANDALONE_SYSTEMSERVER_JARS`）合并到 boot image profile；这一路径的目标是让 SystemServer 及相关 classpath 的 hot/startup 方法获得更合适的 AOT/JIT 编译选择。[来源: DeepResearch/2026-07-17-android17-cloud-profiles-systemserver-onboot.md]

对于本章的音频主题，正确的结论是：ART Profile 可以改变 SystemServer 服务代码的编译产物与启动期耗时，但它不是 Bluetooth LE Audio 的 LC3 offload 协商、ADSP 分工、Spatial Audio 传输选择或后台音频硬化的策略输入；音频硬化仍应按 Java HardeningEnforcer 与 C++ Tracks::getHardeningDecision 的双源覆盖开关和逐 Track 判定来分析。[来源: DeepResearch/2026-07-17-android17-cloud-profiles-systemserver-onboot.md][来源: DeepResearch/2026-07-10-android17-background-audio-hardening-enforcer-decision-matrix.md]

#### 首启 / OTA / Mainline 更新的排障清单

| 场景 | ART/Profile 行为 | 对音频排障的意义 |
|------|------------------|------------------|
| 首次开机 / factory reset | `REASON_FIRST_BOOT` 触发整包 dexopt；材料说明首次开机时 ART Mainline Profile 同步通常尚未完成 | 首启音频服务延迟更可能来自系统整体 dexopt/初始化窗口，不宜直接判定为后台硬化拒绝 [来源: DeepResearch/2026-07-17-android17-cloud-profiles-systemserver-onboot.md] |
| OTA 后首次开机 | `REASON_BOOT_AFTER_OTA` 触发 `ArtManagerLocal.onBoot(...)`，可处理 pre-reboot staged files | OTA 后短时音频不可用或焦点恢复延迟，需要同时查看 boot dexopt 日志与 AudioHardening 日志 [来源: DeepResearch/2026-07-17-android17-cloud-profiles-systemserver-onboot.md] |
| BCP APEX 变化 / ART Mainline 更新 | `hasBcpApexesChanged()` 通过 `ApexManager.getActiveApexInfos()` 判断 active APEX 变化，命中后使用 `REASON_BOOT_AFTER_MAINLINE_UPDATE` | ART APEX 更新后的启动期抖动属于编译/提交产物路径；普通启动无该 reason 时，不应把运行期 LE Audio 功耗异常归因于 Cloud Profile [来源: DeepResearch/2026-07-17-android17-cloud-profiles-systemserver-onboot.md] |

#### 与既有调试命令的组合

在 Android 17 音频问题复盘中，可以将两组证据分层采集：第一层看音频硬化开关与拒绝日志，例如本章前文列出的 `adb shell cmd audio set-enable-hardening enable|disable|throw` 和 `adb logcat | grep AudioHardening`；第二层只在首启、OTA 后、APEX 更新后补查 ART/PackageManager 启动期日志，例如 `Starting boot dexopt for reason ...` 与 `ArtManagerLocal.onBoot` 进度。这样可以避免把 ART Mainline profile 带来的 boot-time dexopt 阻塞误判成后台音频策略变化。[来源: DeepResearch/2026-07-17-android17-cloud-profiles-systemserver-onboot.md]
