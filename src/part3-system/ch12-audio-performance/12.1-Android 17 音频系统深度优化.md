## 要点

### 🔹 音频性能度量体系与延迟分解

音频性能优化的前提是建立可重复、可量化的度量体系。Android 音频子系统的延迟由多个连续环节共同构成，每个环节都需独立测量才能定位瓶颈。

**延迟类型定义**：

| 延迟类型 | 定义 | 典型范围 |
|----------|------|----------|
| **输出延迟 (Output Latency)** | 应用调用 `write()` 到声音从扬声器发出的时间 | 20-50ms |
| **往返延迟 (Round-Trip Latency)** | 音频信号从麦克风输入到扬声器输出的完整环路 | 40-100ms |
| **应用延迟 (App Latency)** | 应用产生音频数据到送入 AudioFlinger 缓冲区的时间 | 5-20ms |
| **HAL 延迟** | AudioFlinger 将数据送入 HAL 到实际播出的时间 | 10-40ms |

[已验证: 官方文档, source.android.com/docs/core/audio/latency]

**延迟分解方法**：

输出延迟 = 应用缓冲帧数 / 采样率 + AudioFlinger 混音延迟 + HAL 传输延迟 + DAC 转换延迟

其中 AudioFlinger 混音延迟取决于数据路径：
- **Normal Mixer 路径**：多级缓冲，每级约一个 buffer 周期（通常 10-20ms），总混音延迟可达 40-80ms
- **FAST Mixer 路径**：单级缓冲，目标 < 20ms，要求应用使用 `PERFORMANCE_MODE_LOW_LATENCY`
- **MMAP Direct 路径**：绕过 AudioFlinger 混音器，理论延迟仅取决于 HAL 缓冲（可达 < 10ms）

[已验证: 官方文档, source.android.com/docs/core/audio/architecture]

**度量工具链**：

1. **`adb shell dumpsys audio`**：查看当前音频路由、设备、缓冲区配置、活跃 stream 信息
2. **Perfetto `audio` atrace 类别**：捕获 AudioFlinger/AudioPolicyService/AudioTrack 关键路径
3. **`aaudio_latency_benchmark`**（AOSP 可构建）：直接测量 AAudio 不同路径的端到端延迟
4. **Audio Loopback 测量**：使用外部设备或 `adb shell tinycap` 录制已知测试信号，计算往返延迟

**基线建立建议**：

```
# 采集 10 秒音频性能 trace
adb shell perfetto -t 10s \
  --atrace-categories audio,sched,freq,idle \
  --buffer 64mb \
  -o /data/misc/perfetto-traces/audio_baseline.perfetto-trace
```

### 🔹 AAudio MMAP 低延迟路径的工程化接入

AAudio 是 Android 8.0 引入的 native 音频 API，其 MMAP 模式（Android 8.1+）是实现超低延迟的关键。但 MMAP 不是自动启用的，需要应用主动配置且设备 HAL 支持。

**能力探测流程**：

```cpp
// 1. 创建 AAudioStreamBuilder
AAudioStreamBuilder *builder;
AAudio_createStreamBuilder(&builder);

// 2. 请求低延迟模式
builder->setPerformanceMode(AAUDIO_PERFORMANCE_MODE_LOW_LATENCY);

// 3. 请求 MMAP（底层自动选择，无法直接指定）
//    LOW_LATENCY + SHARED 方向会优先尝试 MMAP SHARED
//    要获得 EXCLUSIVE 模式，需要 setSharingMode(AAUDIO_SHARING_MODE_EXCLUSIVE)
builder->setSharingMode(AAUDIO_SHARING_MODE_EXCLUSIVE);

// 4. 打开 stream 后验证实际路径
AAudioStream *stream;
builder->openStream(&stream);

aaudio_performance_mode_t actualMode = 
    AAudioStream_getPerformanceMode(stream);
aaudio_sharing_mode_t actualSharing = 
    AAudioStream_getSharingMode(stream);

// 5. 计算实际延迟
int32_t framesPerBurst = AAudioStream_getFramesPerBurst(stream);
int32_t sampleRate = AAudioStream_getSampleRate(stream);
double latencyMs = (double)framesPerBurst * 1000.0 / sampleRate;
```

[已验证: 官方文档, developer.android.com/ndk/guides/audio/aaudio]

**MMAP 模式判定matrix**：

| 请求 PerformanceMode | 请求 SharingMode | 实际路径（HAL 支持 MMAP） | 实际路径（HAL 不支持） |
|---------------------|------------------|-------------------------|----------------------|
| LOW_LATENCY | EXCLUSIVE | MMAP EXCLUSIVE（最低延迟） | FAST Mixer |
| LOW_LATENCY | SHARED | MMAP SHARED | FAST Mixer |
| NONE / POWER_SAVING | 任意 | Normal Mixer | Normal Mixer |

**关键工程注意事项**：

1. **EXCLUSIVE 模式独占性**：同一时刻只有一个应用能获得 MMAP EXCLUSIVE。其他应用请求时会回退到 SHARED 或 FAST Mixer。需要在 `onErrorCallback` 中处理 `AAUDIO_ERROR_DISCONNECTED` 并重新协商路径。

2. **缓冲区对齐**：`framesPerBurst` 必须是 HAL 支持的 burst 大小的整数倍。使用 `AAudioStream_getFramesPerBurst()` 获取实际值，以此为基础设置 `setBufferSizeInFrames()`。

3. **自适应缓冲**：建议初始设置为 2× framesPerBurst，然后逐步减小：

```cpp
// 自适应缓冲策略：从保守开始，逐步降低延迟
int32_t burst = AAudioStream_getFramesPerBurst(stream);
AAudioStream_setBufferSizeInFrames(stream, burst * 2);

// 在运行时根据 underrun 情况动态调整
int32_t underruns = AAudioStream_getXRunCount(stream);
if (underruns == 0) {
    // 无 underrun，尝试减小缓冲
    int32_t currentSize = AAudioStream_getBufferSizeInFrames(stream);
    AAudioStream_setBufferSizeInFrames(stream, 
        max(currentSize - burst / 2, burst));
}
```

4. **Oboe 库的抽象**：Google 推荐使用 Oboe（C++ 封装库），它自动处理 MMAP 协商、设备路由变更、format 转换等。`oboe::AudioStreamBuilder` 的 `setPerformanceMode(oboe::PerformanceMode::LowLatency)` 会自动请求 MMAP EXCLUSIVE 并处理回退。

[已验证: 官方文档, developer.android.com/ndk/guides/audio]

### 🔹 音频线程实时调度与 underrun 防护

音频 underrun（缓冲区欠载）是最常见的音频性能问题。当音频线程无法及时填充缓冲区时，输出会出现可闻的卡顿、爆音或间断。

**underrun 根因分析**：

1. **CPU 调度延迟**：音频线程被抢占或未及时唤醒
2. **锁竞争**：音频回调中持锁阻塞
3. **GC 停顿**（Java 层）：如果使用 Java AudioTrack
4. **内存访问延迟**：大量数据拷贝或 cache miss
5. **系统级干扰**：thermal throttling、CPU freq 降频、IRQ 风暴

**SCHED_FIFO 实时调度**：

AAudio 的 FAST Mixer 和 MMAP 路径使用 `SCHED_FIFO` 实时调度策略（优先级 2-3）。应用侧音频回调线程也应提升优先级：

```cpp
// 在音频回调线程中设置 SCHED_FIFO
#include <sched.h>
#include <pthread.h>

void setAudioThreadPriority() {
    struct sched_param param;
    param.sched_priority = 2; // 与 AudioFlinger FastMixer 对齐
    
    if (sched_setscheduler(0, SCHED_FIFO, &param) != 0) {
        // 回退到 SCHED_FIFO 通过 pthread_setschedparam
        pthread_t currentThread = pthread_self();
        pthread_setschedparam(currentThread, SCHED_FIFO, &param);
    }
}
```

**关键约束**：SCHED_FIFO 线程必须在严格的时间预算内完成工作，否则会饿死其他线程导致系统卡死。音频回调中禁止的操作：
- ❌ 分配内存（malloc/new）
- ❌ 持锁等待（mutex_lock 可能阻塞）
- ❌ I/O 操作（文件、网络、日志）
- ❌ 调用 JNI（可能触发 GC）
- ✅ 从预分配环形缓冲区读写
- ✅ 使用 lock-free 队列传递数据
- ✅ 原子操作设置 flag

[已验证: AOSP android-17.0.0_r1, frameworks/av/services/audioflinger/FastMixer.cpp — FastMixer 线程使用 SCHED_FIFO 优先级 2]

**缓冲区大小与 underrun 概率的关系**：

underrun 概率与缓冲区大小的关系并非线性。经验法则：

| 缓冲区大小（帧） | 延迟（48kHz） | underrun 风险 | 适用场景 |
|-----------------|-------------|-------------|---------|
| 48 (1ms) | ~1ms | 极高 | 仅 MMAP EXCLUSIVE + 专业音频 |
| 96 (2ms) | ~2ms | 高 | 低延迟互动、乐器模拟 |
| 192 (4ms) | ~4ms | 中 | 实时通信（VoIP/游戏语音） |
| 480 (10ms) | ~10ms | 低 | 媒体播放（FAST Mixer 标准） |
| 960 (20ms) | ~20ms | 极低 | 后台播放（Normal Mixer） |

**thermal throttling 对音频的影响**：

当设备发热降频时，CPU 频率下降可能导致音频回调无法在预算时间内完成。Perfetto 可以观察到这一关联：

```sql
-- 查找音频 underrun 与 CPU 降频的关联
SELECT
    t1.ts AS underrun_ts,
    t1.name AS underrun_event,
    cpu_freq.value AS cpu_freq_at_underrun
FROM slice t1
JOIN thread_track tt ON t1.track_id = tt.id
JOIN thread t ON tt.utid = t.id
LEFT JOIN (
    SELECT ts, value FROM counter c
    JOIN counter_track ct ON c.track_id = ct.id
    WHERE ct.name = 'cpufreq'
) cpu_freq ON cpu_freq.ts <= t1.ts
    AND cpu_freq.ts > t1.ts - 1000000  -- 1ms 窗口
WHERE t.name LIKE '%FastMixer%' 
    AND t1.name LIKE '%underrun%'
ORDER BY t1.ts DESC
LIMIT 20;
```

### 🔹 Android 17 AudioTrack 新 API 的性能优化价值

Android 17（API 37）为 AudioTrack 引入了三个对性能优化有直接影响的新 API。本节聚焦其性能侧价值，不重复 25.18 节已覆盖的功耗优化角度。

[已验证: 官方文档, developer.android.com/about/versions/17/features]

**1. flushWrittenFramesFromPosition — 精确 flush 对延迟的影响**：

传统 `AudioTrack.flush()` 会丢弃整个未播放缓冲区，导致：
- 切歌时产生可闻 gap（等于缓冲区长度的静音）
- 有声书断点续播时丢失上下文
- 广告插入时的位置跳跃

新 API `flushWrittenFramesFromPosition(long positionFrames, int accuracy)` 允许从指定位置精确 flush，减少不必要的缓冲区清空。对延迟的影响：

- **FLUSH_FROM_ACCURACY_EXACT**：仅 flush 指定位置之后的数据，保留已排队的头部数据，gap 从整个缓冲区（~20ms）降至 < 1ms
- **FLUSH_FROM_ACCURACY_BEST_EFFORT**：尽量精确但允许 HAL 层面的微调，适用于对延迟不敏感但需要可靠性的场景

```java
// 精确切歌：从当前位置 flush，保留已缓冲数据
if (audioTrack.getFlushWrittenFramesFromPositionSupport()) {
    long currentPosition = audioTrack.getPlaybackHeadPosition();
    audioTrack.flushWrittenFramesFromPosition(
        currentPosition, 
        AudioTrack.FLUSH_FROM_ACCURACY_EXACT
    );
} else {
    // 回退到传统 flush（Android 16 及以下）
    audioTrack.flush();
}
```

[已验证: 官方文档, developer.android.com/reference/android/media/AudioTrack]

**2. getCodecProvenance — 编解码器来源对性能决策的影响**：

`getCodecProvenance()` 返回音频数据实际使用的编解码器类型（hardware/software/offload）。这对性能优化的价值：

- **硬件编解码**：CPU 负载低，功耗低，但可能存在格式限制
- **软件编解码**：兼容性好，但占用 CPU 和内存带宽
- **Offload 模式**：压缩数据直通 DSP，CPU 负载最低

在性能诊断中，如果发现播放期间 CPU 占用异常，可以用此 API 确认是否意外回退到软件解码：

```java
// 监控编解码器路径变化
audioTrack.addOnCodecProvenanceChangedListener(
    executor,
    (track, provenance) -> {
        if (provenance == AudioTrack.CODEC_PROVENANCE_SOFTWARE) {
            // 记录：预期硬件解码但回退到软件
            performanceMonitor.recordCodecFallback(
                "software_fallback", 
                track.getCodecProvenance()
            );
        }
    }
);
```

**3. USAGE_ASSISTANT — 独立音量流对资源竞争的影响**：

Android 17 引入 `USAGE_ASSISTANT` 专用音量流，将语音助手音频与标准媒体流解耦。从性能角度看：

- **独立 stream 意味着独立 AudioFlinger track**：不再与媒体播放共享混音通道
- **减少 Audio Focus 冲突**：Assistant 请求 Audio Focus 时不再阻塞媒体播放的音量控制
- **`MODE_ASSISTANT_CONVERSATION`**：优化了音频路由策略，减少 Assistant 会话期间的设备切换延迟

### 🔹 Android 17 后台音频硬化与性能侧影响

Android 17 对后台音频的严格管控（详见 25.17 节）不仅影响功能行为，还带来了性能侧的连锁影响。本节聚焦其对性能分析和优化的影响。

[已验证: 研究素材, intake/research-feeds/2026-04-08-15-android17-background-audio-hardening-audio-focus.md]

**不合规播放的性能症状**：

当应用未持有合规前台服务（WIU capability）就在后台调用音频 API 时：
- `AudioTrack.play()` 静默失败 — 写入的数据在 buffer 中堆积但不会播放
- 数据在 AudioFlinger track buffer 中积累，最终导致 buffer overflow
- 从 buffer overflow 状态恢复时可能出现突发性的大量 CPU 消耗（一次性 flush 全部积压数据）

**诊断方法**：

```bash
# 检查音频硬化状态
adb shell dumpsys audio | grep -A5 "Hardening"

# logcat 中的硬化违规日志
adb logcat -s AudioHardening:V
```

**合规迁移对性能的正面影响**：

正确使用 WIU 前台服务后，音频播放获得稳定的调度优先级。相比在 lifecycle 边缘反复触发限制，合规的前台服务路径：
- 音频线程获得 FOREGROUND 优先级组调度权重
- AudioFlinger 将该 track 提升为 active 状态，参与 FAST Mixer 评估
- 减少 Audio Focus 状态机抖动导致的路由切换

[交叉引用: 25.17 节详述后台音频硬化的合规要求与前台服务配置]

### 🔹 Perfetto 音频性能诊断工作流

本节提供可直接使用的 Perfetto 音频性能诊断流程，从数据采集到问题定位的完整链路。

**数据采集模板**：

```bash
# 模板 1：音频延迟与 underrun 诊断
adb shell perfetto -t 30s \
  --atrace-categories audio,sched,freq,idle,wm \
  --buffer 128mb \
  -o /data/misc/perfetto-traces/audio_underrun.perfetto-trace

# 模板 2：音频启动延迟分析
adb shell perfetto -t 10s \
  --atrace-categories audio,am,wm,sched,freq \
  --buffer 64mb \
  -o /data/misc/perfetto-traces/audio_startup.perfetto-trace

# 模板 3：音频功耗与 CPU 分析
adb shell perfetto -t 60s \
  --atrace-categories audio,sched,freq,idle,power \
  --buffer 256mb \
  -o /data/misc/perfetto-traces/audio_power.perfetto-trace
```

**关键 SQL 查询**：

```sql
-- 1. 音频 underrun 事件时间线
SELECT
    ts,
    dur,
    name,
    EXTRACT_ARG(arg_set_id, 'frames') AS frames_lost
FROM slice
WHERE name LIKE '%underrun%' OR name LIKE '%xrun%'
ORDER BY ts;

-- 2. AudioFlinger FastMixer 唤醒周期分析
SELECT
    AVG(dur) AS avg_wake_period_us,
    MIN(dur) AS min_period,
    MAX(dur) AS max_period,
    COUNT(*) AS wake_count
FROM slice
WHERE name = 'FastMixer: mix'
    AND ts > {{start_ts}} AND ts < {{end_ts}};

-- 3. 音频回调线程的 CPU 占用
SELECT
    t.name AS thread_name,
    SUM(s.dur) / 1000000.0 AS cpu_time_ms,
    COUNT(*) AS sched_count
FROM sched s
JOIN thread t ON s.utid = t.id
WHERE t.name LIKE '%Audio%' OR t.name LIKE '%aaudio%' OR t.name LIKE '%FastMixer%'
GROUP BY t.id
ORDER BY cpu_time_ms DESC;

-- 4. 音频线程调度延迟（wakeup 到实际运行）
SELECT
    AVG(s.dur) AS avg_run_delay_us,
    MAX(s.dur) AS max_delay_us,
    COUNT(*) AS wakeups
FROM sched s
JOIN thread t ON s.utid = t.id
WHERE t.name LIKE '%FastMixer%'
    AND s.prev_state = 'S';  -- 从 Sleep 唤醒

-- 5. 音频路由变更事件
SELECT
    ts,
    name,
    EXTRACT_ARG(arg_set_id, 'device') AS device,
    EXTRACT_ARG(arg_set_id, 'source') AS source
FROM slice
WHERE name LIKE '%setOutputDevice%' 
    OR name LIKE '%openStream%'
    OR name LIKE '%createTrack%'
ORDER BY ts;
```

**诊断决策树**：

```
症状：音频卡顿/爆音
├── 第一步：dumpsys audio → 确认当前数据路径
│   ├── Normal Mixer → 检查是否可升级到 FAST/MMAP
│   ├── FAST Mixer → 进入第二步
│   └── MMAP → 进入第三步
├── 第二步：Perfetto trace → 检查 FastMixer 唤醒周期
│   ├── 周期稳定（~burst size / sample_rate） → 检查 underrun 事件
│   └── 周期不稳定 → 检查 CPU freq / thermal throttling
├── 第三步：检查 underrun 与系统事件关联
│   ├── underrun 集中在 GC 时间窗口 → 迁移到 Native/AAudio
│   ├── underrun 集中在 CPU 降频窗口 → 调整调度策略或增大缓冲
│   └── underrun 随机分布 → 检查锁竞争或 I/O 阻塞
└── 第四步：检查设备路由变更
    └── 频繁 openStream/setOutputDevice → 音频策略抖动
```

### 🔹 跨场景音频性能策略matrix

不同使用场景对音频性能的要求截然不同。下表汇总了主要场景的优化策略，帮助工程师快速选择正确路径。

| 场景 | 延迟目标 | 推荐路径 | 缓冲策略 | 调度策略 | 关键风险 |
|------|---------|---------|---------|---------|---------|
| **实时通信 (VoIP)** | < 20ms 往返 | AAudio MMAP EXCLUSIVE | 1-2 burst | SCHED_FIFO + CPU pinning | 网络抖动叠加音频抖动 |
| **乐器模拟/DJ** | < 10ms 输出 | AAudio MMAP EXCLUSIVE | 1 burst | SCHED_FIFO 优先级 3 | underrun 可闻、HAL 不支持 |
| **游戏音效** | < 50ms 触觉-音频对齐 | FAST Mixer (AAudio LOW_LATENCY) | 2-3 burst | SCHED_FIFO 优先级 2 | 主线程阻塞影响音频回调 |
| **媒体播放** | 无严格要求 | Normal Mixer 或 Offload | 4+ burst | 普通调度 | 功耗优先于延迟 |
| **语音助手** | < 100ms 响应 | USAGE_ASSISTANT + FAST Mixer | 2 burst | SCHED_FIFO 优先级 2 | Assistant 会话生命周期与 Audio Focus |
| **后台播放** | 无严格要求 | Normal Mixer | 最大缓冲 | 普通调度 | Android 17 硬化合规 |
| **通知/铃声** | < 100ms 启动 | FAST Mixer (系统预加载) | 1-2 burst | SCHED_FIFO 优先级 2 | 低内存设备首次加载延迟 |

**场景迁移策略**：

当设备状态变化（如从 MMAP EXCLUSIVE 被抢占、或从前台进入后台）时，音频路径需要降级。推荐分级降级策略：

1. **MMAP EXCLUSIVE → MMAP SHARED**：延迟增加约 1 个 burst，无用户可感知差异
2. **MMAP SHARED → FAST Mixer**：延迟增加约 2-3 burst，对互动场景有轻微影响
3. **FAST Mixer → Normal Mixer**：延迟显著增加（40ms+），互动场景不可接受，应提示用户

每次降级应在 Perfetto 中产生可观测事件，用于线上监控降级频率和影响范围。

## 扩展

### 🔸 Audio HAL 性能基线与设备差异化

不同 OEM 的 Audio HAL 实现质量差异巨大。同一款应用在 Pixel 设备上延迟 8ms，在低端设备上可能超过 50ms。建议：
- 在 `AudioManager.getProperty(PROPERTY_OUTPUT_OUTPUT_LATENCY)` 获取设备报告的输出延迟（Android 9+）
- 建立「设备音频延迟数据库」覆盖目标用户设备分布
- 对延迟 > 40ms 的设备默认禁用实时音频功能

`PROPERTY_OUTPUT_LATENCY` 返回的是 HAL 报告值，可能与实际测量值有偏差。建议以 loopback 实测值为准，HAL 值仅作参考。

### 🔸 音频性能的持续监控与 CI 集成

音频性能问题往往在特定设备 + 特定负载组合下才暴露。建议建立持续监控体系：

```bash
# CI 中的音频延迟自动化测试
# 1. 启动延迟测试 App
adb shell am start -n com.test.audiolatency/.MainActivity
# 2. 触发延迟测量
adb shell input tap 500 500  
# 3. 采集 Perfetto trace
adb shell perfetto -t 10s --atrace-categories audio,sched \
  -o /data/misc/perfetto-traces/ci_audio.perfetto-trace
# 4. 使用 trace_processor 计算 P50/P90/P99 延迟
# 5. 与基线对比，超过阈值则告警
```

监控指标建议：
- 输出延迟 P50 / P90 / P99（每设备型号独立基线）
- underrun 率（underrun 次数 / 总 burst 数）
- MMAP EXCLUSIVE 获取率
- 音频路由切换次数 / 会话时长

### 🔸 MGLRU 与音频内存回收竞争

[待补充] Android 的 MGLRU 内存回收机制在回收冷页面时可能引发短暂的延迟尖峰。对音频线程的影响取决于音频缓冲区是否被 kernel 归类为 cold。需要进一步验证 `mlock()` 或 `PR_SET_TIMERSLACK` 对音频页面的保护效果。
