# 19.1 Android 17 游戏性能与温控优化

> **版本边界**：本节基于 `android-17.0.0_r1` 源码与官方文档验证。ADPF Thermal API 自 Android 12 (API 31) 引入，Performance Hint Session 自 Android 11 (API 30) 引入，Power Efficiency Mode 与 GPU 工作时长上报自 Android 15 (API 35) 引入，Thermal Headroom Listener 自 Android 16 (API 36) 引入。所有 API 在 Android 17 (API 37) 中均可用且无破坏性变更。[已验证: AOSP android-17.0.0_r1 + 官方文档]
>
> **本章定位**：本章是 Part 3 系统篇的「游戏综合性能」章节，从游戏开发者视角整合 ADPF、Game Mode、Thermal Management、Frame Pacing 和 Perfetto 分析流程，形成完整的游戏性能工程实践指南。机制原理详见交叉引用章节，本章聚焦「怎么用」和「怎么调」。

## 1. 游戏负载模型与系统调度的根本冲突

游戏应用的性能模型与普通 App 截然不同：普通 App 的 CPU 负载是脉冲式的（用户操作触发短暂峰值），而游戏需要**持续满帧运行**——每帧 16.6ms（60fps）或 8.3ms（120fps），整局游戏期间几乎不存在空闲窗口。

这种持续高负载与 Android 默认的动态电压频率调整（DVFS）机制存在根本矛盾：

### 1.1 DVFS 响应延迟

Android 的 CPU 调频依赖负载跟踪算法（PELT 或 WALT），通过统计过去一段时间的线程运行情况来预测未来需求。这种**反应式调度**存在固有延迟：

- 调频器需要约 **20-200ms** 才能识别负载上升并完成频率切换
- 一帧仅 16.6ms（60fps），意味着调频器识别到负载时，当前帧可能已经丢弃
- 典型现象：场景切换或特效爆发时，前 3-5 帧因 CPU 频率不足而丢帧，频率爬升后恢复

[已验证: 官方文档, developer.android.com/games/optimize/performance#adpf]

### 1.2 Thermal Throttling 的被动性

传统温控是**事件驱动的被动降频**：当芯片温度到达阈值时，内核 thermal zone 触发 cooling device 降频。这种方式有两个问题：

1. **响应滞后**：温度传感器到降频执行有数百毫秒延迟，期间已经产生大量丢帧
2. **缺乏预判**：系统不知道当前负载将持续多久，只能在过热后粗暴降频

ADPF 的核心设计理念是将被动温控转变为**主动式热管理**：游戏提前告知系统目标帧率和热预算，系统据此进行预判式调度。

> 详见 5.12 节 for Linux 内核 Thermal 子系统和 ADPF 的架构原理。

## 2. ADPF Performance Hint Session 集成实战

Performance Hint Session 是 ADPF 最核心的 API，让游戏向系统调度器发送前瞻性性能信号。

### 2.1 核心 API 架构

`PerformanceHintManager.Session` 在 AOSP `frameworks/base/core/java/android/os/PerformanceHintManager.java` 中定义：

```java
// android-17.0.0_r1 PerformanceHintManager.java 关键方法

// 创建 Hint Session
public Session createHintSession(int[] threadIds, long targetWorkDurationNanos)

// 更新目标帧时间（vsync 变化或场景切换时调用）
public void updateTargetWorkDuration(long targetDurationNanos)

// 报告实际帧工作时间
public void reportActualWorkDuration(long actualDurationNanos)

// Android 15+ 设置 Power Efficiency Mode
public void setPreferPowerEfficiency(boolean enabled)

// Android 15+ 通过 WorkDuration 同时报告 CPU/GPU 工作时长
public void reportActualWorkDuration(@NonNull WorkDuration workDuration)
```

[已验证: AOSP android-17.0.0_r1, frameworks/base/core/java/android/os/PerformanceHintManager.java + WorkDuration.java]

### 2.2 游戏循环集成模式

典型游戏循环中的 Hint Session 集成：

```kotlin
class GameLoop {
    private var hintSession: PerformanceHintManager.Session? = null
    private val targetFrameTimeNanos = 16_666_666L // 60fps

    fun onStart() {
        val phm = getSystemService(PerformanceHintManager::class.java)
        // 将渲染线程和逻辑线程纳入 hint session
        val threadIds = intArrayOf(
            renderThreadId,
            logicThreadId
        )
        hintSession = phm?.createHintSession(threadIds, targetFrameTimeNanos)
    }

    fun onFrameStart() {
        frameStartTime = System.nanoTime()
    }

    fun onFrameEnd() {
        val actualDuration = System.nanoTime() - frameStartTime
        hintSession?.reportActualWorkDuration(actualDuration)

        // 如果帧耗时接近或超过目标，系统会主动提升 CPU 频率
        // 如果帧耗时远低于目标，系统可以降低频率以省电
    }

    fun onSceneChange(newFps: Int) {
        val newTarget = 1_000_000_000L / newFps
        hintSession?.updateTargetWorkDuration(newTarget)
    }

    fun onStop() {
        hintSession?.close()
        hintSession = null
    }
}
```

**关键设计决策**：

| 决策点 | 推荐做法 | 常见错误 |
|--------|----------|----------|
| 线程选择 | 仅纳入渲染线程 + 主逻辑线程 | 纳入所有线程（稀释信号） |
| 目标时长 | 匹配 vsync 周期（16.6ms/8.3ms） | 设置过松（系统不提频） |
| 上报频率 | 每帧一次 | 间隔上报（调度器失去连续性） |
| Session 生命周期 | 游戏前台时存活，退后台时 close | 全局共用一个 session（后台仍占资源） |

### 2.3 Android 15+ Power Efficiency Mode

Android 15 (API 35) 引入的 `setPreferPowerEfficiency(true)` 让系统将线程调度到能效核心（E-core），适用于：

- **加载场景**：资源解压、shader 编译不需要极限性能
- **后台渲染**：截图、视频录制编码
- **低画质模式**：用户主动选择的省电模式

```kotlin
fun onLoadingScene() {
    // 加载场景：优先能效，降低功耗和发热
    hintSession?.setPreferPowerEfficiency(true)
}

fun onGameplayScene() {
    // 战斗场景：切回性能优先
    hintSession?.setPreferPowerEfficiency(false)
}
```

⚠️ Power Efficiency Mode 是**建议而非命令**——系统会根据整体热状态和功耗预算决定是否采纳。如果设备已接近热阈值，即使请求性能模式也可能被限制。

[已验证: 官方文档, developer.android.com/about/versions/15/features#adpf]

### 2.4 Android 15+ GPU + CPU 联合上报

Android 15 引入 GPU 工作时长上报能力，但不是单独的 `reportActualGpuWorkDuration(...)` 方法；android-17.0.0_r1 中的公共入口是 `PerformanceHintManager.Session.reportActualWorkDuration(WorkDuration)`，由 `WorkDuration` 同时携带 work period 起点、总耗时、CPU 耗时与 GPU 耗时：

```kotlin
fun onFrameEnd(
    workStartUptimeNanos: Long,
    totalDurationNanos: Long,
    cpuDurationNanos: Long,
    gpuDurationNanos: Long
) {
    if (Build.VERSION.SDK_INT >= 35) {
        val duration = WorkDuration().apply {
            setWorkPeriodStartTimestampNanos(workStartUptimeNanos)
            setActualTotalDurationNanos(totalDurationNanos)
            setActualCpuDurationNanos(cpuDurationNanos)
            setActualGpuDurationNanos(gpuDurationNanos)
        }
        hintSession?.reportActualWorkDuration(duration)
    } else {
        hintSession?.reportActualWorkDuration(totalDurationNanos)
    }
}
```

GPU 时长可通过以下方式获取：
- **Vulkan**：`vkGetCalibratedTimestampsEXT` 或 frame boundary extension
- **GLES**：`EGL_ANDROID_gpu_performance` 扩展（设备支持时）
- **AGDK Frame Pacing Library (Swappy)**：自动收集并暴露 GPU 帧时间

[已验证: AOSP android-17.0.0_r1, PerformanceHintManager.java + WorkDuration.java；官方文档 developer.android.com/about/versions/15/features#adpf]
[适用版本: GPU 工作时长上报 Android 15+，基础 Hint Session API Android 11+/12+ 文档边界]

## 3. Thermal Headroom 自适应画质策略

### 3.1 Thermal Headroom 监控方式

Android 提供两种 Thermal 监控路径：

**方式一：轮询（Android 12+）**

```kotlin
val powerManager = getSystemService(PowerManager::class.java)

// 获取当前热裕度（0.0 ~ 1.0+，1.0 表示到达热阈值）
val headroom = powerManager.getThermalHeadroom(0) // 0 = 当前

// 获取预测值（预测未来 N 秒的裕度）
val forecastHeadroom = powerManager.getThermalHeadroom(30) // 30秒后

// 获取各热状态阈值
val thresholds = powerManager.getThermalHeadroomThresholds()
// thresholds: Map<ThermalStatus, Float>
// THERMAL_STATUS_NONE(0) → THERMAL_STATUS_EMERGENCY(6)
```

**方式二：事件驱动 Listener（Android 16+）**

Android 16 (API 36) 引入 `addThermalHeadroomListener`，将轮询改为事件驱动：

```kotlin
if (Build.VERSION.SDK_INT >= 36) {
    powerManager.addThermalHeadroomListener(executor) {
        headroom, forecastHeadroom, forecastSeconds, thresholds ->
        // headroom: 当前热裕度
        // forecastHeadroom: 预测裕度
        // thresholds: Map<ThermalStatus, Float> 各级阈值

        when {
            headroom > 0.85f -> setQualityLevel(QUALITY_LOW)
            headroom > 0.65f -> setQualityLevel(QUALITY_MEDIUM)
            headroom < 0.40f -> setQualityLevel(QUALITY_HIGH)
        }
    }
}
```

源码层面，`ThermalManagerService` 使用 `HEADROOM_CALLBACK_MIN_INTERVAL_MILLIS = 5000ms` 做去抖，`HEADROOM_CALLBACK_MIN_DIFFERENCE = 0.03`（headroom 维度）做显著变化过滤，避免频繁回调影响游戏性能。

[已验证: AOSP android-16-release, frameworks/base/services/core/java/com/android/server/power/ThermalManagerService.java]
[引用: DeepResearch/2026-06-06-thermal-headroom-listener-android16-verify.md]
[适用版本: Thermal Headroom Listener Android 16+，轮询 API Android 12+]

### 3.2 自适应画质阶梯设计

推荐的热感知画质阶梯（Quality Ladder）：

```
QUALITY_ULTRA  → headroom < 0.30
  - 原始分辨率（1080p/1440p）
  - 最高阴影质量、开启光线追踪
  - 粒子效果全开

QUALITY_HIGH   → 0.30 ≤ headroom < 0.55
  - 分辨率不变，降阴影质量
  - 粒子数量 ×0.7
  - 关闭光线追踪

QUALITY_MEDIUM → 0.55 ≤ headroom < 0.75
  - 渲染分辨率 ×0.75（动态分辨率缩放）
  - 阴影质量降至 Low
  - 粒子数量 ×0.5

QUALITY_LOW    → headroom ≥ 0.75
  - 渲染分辨率 ×0.6
  - 关闭动态阴影
  - 粒子数量 ×0.3
  - 帧率目标降至 45fps 或 30fps
```

### 3.3 滞回设计（Hysteresis）

避免画质在阈值附近反复振荡（"画质闪烁"），必须引入滞回区间：

```kotlin
class ThermalQualityManager {
    private var currentLevel = QUALITY_ULTRA

    // 升级阈值（热裕度下降时）与降级阈值（热裕度上升时）之间留 0.10 的滞回
    private val upgradeThresholds = mapOf(
        QUALITY_LOW    to 0.55f,   // 从 LOW 升到 MEDIUM 需要 headroom < 0.55
        QUALITY_MEDIUM to 0.35f,   // 从 MEDIUM 升到 HIGH 需要 headroom < 0.35
        QUALITY_HIGH   to 0.20f,   // 从 HIGH 升到 ULTRA 需要 headroom < 0.20
    )
    private val downgradeThresholds = mapOf(
        QUALITY_ULTRA  to 0.55f,   // 从 ULTRA 降到 HIGH 需要 headroom > 0.55
        QUALITY_HIGH   to 0.75f,   // 从 HIGH 降到 MEDIUM 需要 headroom > 0.75
        QUALITY_MEDIUM to 0.85f,   // 从 MEDIUM 降到 LOW 需要 headroom > 0.85

    fun onHeadroomChange(headroom: Float) {
        val upgradeThreshold = upgradeThresholds[currentLevel]
        val downgradeThreshold = downgradeThresholds[currentLevel]

            upgradeThreshold != null && headroom < upgradeThreshold ->
                currentLevel = upgradeFrom(currentLevel)
            downgradeThreshold != null && headroom > downgradeThreshold ->
                currentLevel = downgradeFrom(currentLevel)
        }
        applyQualityLevel(currentLevel)
    }
```

## 4. Game Mode API 与系统协同调度

### 4.1 Game Mode 声明与查询

游戏通过 `<application>` 的 `<meta-data>` 声明支持的 Game Mode：

```xml
<application>
    <meta-data
        android:name="android.game_mode_intervention"
        android:value="true" />
    <meta-data
        android:name="android.game_mode_performance"
        android:value="true" />
    <meta-data
        android:name="android.game_mode_battery"
        android:value="true" />
</application>
```

运行时查询当前 Game Mode：

```kotlin
val gameManager = context.getSystemService(GameManager::class.java)
when (gameManager.gameMode) {
    GameManager.GAME_MODE_STANDARD -> {
        // 标准模式：系统默认行为
    }
    GameManager.GAME_MODE_PERFORMANCE -> {
        // 性能模式：系统提升 CPU/GPU 频率，降低后台限制
        // 游戏侧可：提升渲染分辨率、开启高级特效
    }
    GameManager.GAME_MODE_BATTERY -> {
        // 省电模式：系统限制频率，降低刷新率
        // 游戏侧可：降低渲染分辨率、限制帧率到 30fps
    }
}
```

`GameManagerService`（`frameworks/base/services/core/java/com/android/server/app/GameManagerService.java`）管理 Game Mode 状态，OEM 可通过 `GameModeConfiguration` overlay 自定义每个 Mode 的具体系统行为（CPU 频率范围、GPU 频率上限、刷新率等）。

[已验证: AOSP android-17.0.0_r1, frameworks/base/services/core/java/com/android/server/app/GameManagerService.java]

### 4.2 Game State API：场景级通信

Android 14+ 的 Game State API 让游戏向系统报告当前场景，系统据此做更精细的资源分配：

```kotlin
// None: 无活跃游戏内容（菜单/暂停）

```

### 4.3 Game Mode Interventions：OEM 对老游戏的兜底优化

对于未集成 Game Mode API 的旧游戏，OEM 可通过 **Game Mode Interventions** 施加优化：

- **Backbuffer 缩放**：降低 swapchain 分辨率以减少 GPU 负载
- **CPU 频率锁定**：维持稳定的中高频率，避免 DVFS 波动
- **帧率平滑**：通过 SurfaceFlinger 插帧或丢帧策略稳定输出

开发者可通过 `GameManager.isGameModeInterventionActive()` 检查是否被施加干预，并通过声明 `<meta-data android:name="android.game_mode_intervention" android:value="false"/>` 选择退出（如果游戏自行管理性能）。

> 详见 17.5 节 for OEM 游戏模式的触控调度与输入优先级机制。

## 5. 帧率稳定性与 Frame Pacing 联合调优

### 5.1 温控降频对帧率的影响链

当设备进入热降频状态时，影响帧率的路径：

```
温度上升
  → CPU/GPU 频率下降
    → 单帧计算时间 > vsync 间隔
      → SurfaceFlinger 检测到迟到的 frame
        → 丢帧（presentation Missed）
          → 用户感知卡顿
```

关键问题：DVFS 降频是**阶梯式**的，不是平滑过渡。一次降频可能从 2.8GHz 直接跳到 2.1GHz，导致帧时间从 14ms 突变到 22ms，产生明显卡顿。

### 5.2 主动降质 vs 被动丢帧

| 策略 | 原理 | 用户感知 |
|------|------|----------|
| 被动丢帧 | 不改变负载，让系统降频后自然丢帧 | 明显卡顿、不跟手 |
| 主动降分辨率 | 检测到热压力时，降低渲染分辨率 | 画面变模糊但帧率稳定 |
| 主动降帧率 | 将目标从 60fps 切到 45/30fps | 流畅度下降但无卡顿 |
| 主动降特效 | 降低阴影/粒子/后处理 | 画质下降但帧率稳定 |

**推荐优先级**：主动降分辨率 > 主动降特效 > 主动降帧率 > 被动丢帧

原因：分辨率缩放对 GPU 负载影响最大且最容易平滑过渡（逐帧调整 scaling factor），特效切换通常有视觉突变，帧率切换最明显。

### 5.3 Swappy Frame Pacing Library 的角色

AGDK 的 Swappy 库（Frame Pacing Library）负责：

1. **Vsync 对齐**：确保 buffer 提交对齐到 vsync，避免撕裂和 jank
2. **Pipeline 深度管理**：根据当前帧时间动态调整 rendering pipeline 深度
3. **统计上报**：自动收集帧时间数据

在热压力下，Swappy 的 pipeline depth 自动调整机制至关重要：

- 帧时间 < vsync 间隔 → pipeline depth = 1（最低延迟）
- 帧时间 ≈ vsync 间隔 × 2 → pipeline depth = 2（增加 1 帧延迟但避免丢帧）
- 配合 ADPF Hint Session，系统知道帧时间变化是故意的，不会误判为负载下降而降频

> 详见 18.16 节 for Swappy Frame Pacing 与游戏引擎渲染链路的完整分析。

## 6. Perfetto 游戏性能全链路分析工作流

### 6.1 游戏专用 Perfetto 采集配置

```protobuf
# game_perfetto_config.pbtxt
duration_ms: 10000  # 10秒采集，覆盖至少一个完整场景循环

# CPU 调度
data_sources {
    config { name: "linux.sched" }
}
data_sources {
    config { name: "linux.cpu_frequency" }
}

# GPU 渲染阶段
data_sources {
    config {
        name: "android.gpu.renderstages"
        gpu_counter_period_ms: 1
    }
}

# Thermal
data_sources {
    config { name: "android.power.thermal" }
```

### 6.2 关键分析步骤

**Step 1: 帧时间基线**

在 Perfetto 中找到 `SurfaceFlinger.frame_timeline` track，观察 `ExpectedDisplayTime` 与 `ActualDisplayTime` 的偏差。偏差 > 1 vsync 即为 jank。

**Step 2: CPU 频率 vs 帧时间关联**

在同一时间轴上对比 `cpu_frequency` track 和帧时间。如果帧时间突增伴随 CPU 频率下降，说明是 DVFS 降频导致。如果 CPU 频率稳定但帧时间突增，说明是 GPU 或锁竞争问题。

**Step 3: ADPF 信号验证**

搜索 `ADPF` track（如果设备支持），检查：
- Hint Session 的 target work duration 是否正确设置
- reportActualWorkDuration 是否每帧调用
- 系统是否响应了 hint（CPU 频率是否在 hint 后提升）

**Step 4: Thermal 事件关联**

查找 `thermal` track 中的 `THERMAL_STATUS_*` 变化事件，将其与帧时间异常关联。如果热状态变化前 200-500ms 出现帧率下降，说明可能是 thermal throttling 的前兆。

**Step 5: GPU 渲染阶段分析**

`gpu.renderstages` track 展示 GPU 管线的各阶段耗时：
- `RENDERING_STAGE_DRAW` → draw call 执行
- `RENDERING_STAGE_COMPOSITE` → GPU 合成
- `RENDERING_STAGE_SWAP` → buffer swap

如果 `DRAW` 阶段耗时在热压力下增长 50%+，说明 shader 复杂度过高，应优先降级。

### 6.3 常见 jank 模式快速诊断表

| Trace 特征 | 根因 | 解决方案 |
|------------|------|----------|
| CPU 频率突降 + 帧时间突增 | DVFS 降频 | 集成 ADPF Hint Session |
| GPU DRAW 阶段 >10ms | Shader 过重 | LOD shader 或降低 shader 复杂度 |
| `schedule` 中大量 `D` 状态 | I/O 阻塞 | 异步加载，资源预加载 |
| `binder_transaction` 频繁 | IPC 开销 | 批量化 IPC 调用 |
| Thermal status 变化 | 热降频 | 主动降质 + Adaptive Quality |
| SurfaceFlinger `MissedFrame` | buffer 未及时提交 | Pipeline 深度 + Swappy 调优 |

### 7.2 集成优先级建议

对于尚未集成任何性能 API 的游戏，推荐分三步走：

1. **第一步（投入 < 1天，收益最大）**：集成 `PerformanceHintManager.createHintSession`，将渲染线程纳入 hint session，每帧上报帧时间。这一步能解决最常见的前几帧降频丢帧问题。

2. **第二步（投入 2-3天，收益显著）**：集成 Thermal Headroom 监控 + 自适应分辨率缩放。在热压力下主动降低渲染分辨率，保持帧率稳定。

3. **第三步（投入 1-2周，完整体系）**：集成 Game Mode + Game State API，让系统全面理解游戏场景；加入 Perfetto 自定义 trace point 用于线上性能分析。

## 扩展

### 🔸 Unity/Unreal 引擎 ADPF 集成路径

**Unity**:
- 使用 `AndroidJavaClass` 调用 `PerformanceHintManager` API
- 在 `Update()` 末尾上报帧时间
- 通过 `Application.targetFrameRate` 联动设置 hint session target
- Unity 2023.x+ 的 Adaptive Performance 模块已内置 Samsung ADPF 适配

**Unreal Engine**:
- 使用 `FAndroidApplicationMisc` 或直接 JNI 调用
- 在 `FAndroidApplicationViewportClient::Draw` 中采集帧时间
- Unreal 5.4+ 的 Android Device Profile 支持 Game Mode 联动

[待验证: 具体引擎版本与 ADPF 集成细节需对照各引擎最新文档]

### 🔸 MediaTek MAGT 与 Qualcomm GEP 差异化适配

**MediaTek MAGT (MediaTek Adaptive Gaming Technology)**:
- 与 ADPF 集成，提供芯片级温度数据（vs 系统级）
- 实测帧率提升最高 57%，功耗显著降低
- 通过 `IThermal` hidden API 暴露，需要 OEM 配合

**Qualcomm Game Extension Pack (GEP)**:
- Snapdragon Game Performance Extension
- 提供 CPU 核心亲和性、GPU 频率锁定等精细控制
- 通过 `Adreno SDK` 暴露，需要高通 SDK 授权

两者均需要芯片厂商 SDK 或 OEM 配合，普通开发者建议优先使用标准 ADPF API，只有在特定 OEM 平台上才考虑差异化适配。
