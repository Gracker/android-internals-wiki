# 17.23 Android 17 Power Stats HAL OEM厂商功耗统计实现差异

Android 17 的 Power Stats 链路把设备功耗统计拆成三类对象：`PowerEntity` 负责状态驻留时间，`EnergyConsumer` 负责按组件/UID 的能耗归因，`Channel` 负责底层 rail energy meter。AOSP 只定义稳定 HAL 边界、framework 采集与持久化路径；真实设备上能看到多少 rail、能否做 per-UID attribution、时间戳是否稳定，主要取决于 vendor 的 PowerStats HAL 实现质量。

源码锚点为 `android-17.0.0_r1`。Pixel、高通、MTK、三星等闭源或受限仓库的实现细节无法从 AOSP 主线直接验证，因此只按典型差异维度讨论，不把未验证的厂商私有实现写成确定结论。

## 标准架构与厂商差异

### PowerStats HAL 标准架构

Android 17 的 HAL 边界位于 `hardware/interfaces/power/stats/aidl/android/hardware/power/stats/IPowerStats.aidl`。接口围绕 5 个 RPC 展开：

```aidl
PowerEntity[]              getPowerEntityInfo();
StateResidencyResult[]     getStateResidency(in int[] powerEntityIds);
EnergyConsumer[]           getEnergyConsumerInfo();
EnergyConsumerResult[]     getEnergyConsumed(in int[] energyConsumerIds);
Channel[]                  getEnergyMeterInfo();
EnergyMeasurement[]        readEnergyMeter(in int[] channelIds);
```

这组接口把功耗数据分成三层：

1. **状态驻留层**：`PowerEntity` / `StateResidencyResult` 描述 CPU、Display、Modem 等实体在不同状态停留多久。
2. **能耗归因层**：`EnergyConsumer` / `EnergyConsumerResult` 描述某类组件累计消耗，并可附带 `EnergyConsumerAttribution[]` 做 UID 归因。
3. **rail 计量层**：`Channel` / `EnergyMeasurement` 描述底层电源 rail 的累计能量，单位为 microwatt-seconds（μWs）。

HAL 只承诺对象模型与数据格式，不承诺具体设备一定有完整 rail 或完整 attribution。因此，应用和工具读取 PowerStats 时必须先检查对象列表，再判断该设备是否具备足够粒度。

### AOSP 默认实现不是真实设备基线

AOSP 默认实现位于 `hardware/interfaces/power/stats/aidl/default/`，作用更接近 reference/fake service：它提供少量 fake rail、fake state provider 和 fake energy consumer，方便接口联调和 VINTF 绑定验证。它不能代表真实手机的功耗统计能力。

这也是 OEM 差异的根源：

- 如果 vendor 只接入少量 rail，`dumpsys powerstats` 会看到对象列表存在，但组件覆盖不完整。
- 如果 vendor 没有实现可靠 attribution，Battery Historian 或系统侧模型只能得到粗粒度组件能耗，无法精确分摊到应用 UID。
- 如果 vendor 的时间戳、采样周期或单位换算不稳定，上层工具即使能读到数据，也不能直接用于跨机型横向比较。

### Framework 侧采用 BatteryTrigger + TimerTrigger 双路径

Android framework 侧的核心链路是：

```text
vendor PowerStats HAL
  → PowerStatsHALWrapper
  → PowerStatsService
  → PowerStatsLogger
  → PowerStatsDataStorage / PowerMonitor / dumpsys
```

`PowerStatsService` 通过两类触发器收集数据：

1. **BatteryTrigger**：电量下降时触发日志写入，适合捕捉跨电量段的 residency/model 数据。
2. **TimerTrigger**：周期触发，分别服务较高频的 meter/model 采集与较低频的带 attribution 采集。

持久化文件位于 `/data/system/powerstats/`，常见文件包括：

- `log.powerstats.meter.0`
- `log.powerstats.model.0`
- `log.powerstats.residency.0`

这些文件由 system_server 侧写入，上层可通过 `dumpsys powerstats` 或 PowerMonitor 相关 API 读取摘要/导出数据。

### 厂商差异主要看四个维度

评估一台 Android 17 设备的 PowerStats 质量时，不应只看「是否有 HAL」，而应看四个维度：

| 维度 | 需要确认的问题 | 对工具结果的影响 |
|---|---|---|
| 数据源覆盖 | rail、EnergyConsumer、PowerEntity 是否覆盖 CPU、Display、Modem、Wi-Fi、GNSS 等关键组件 | 决定功耗拆分是否完整 |
| 数据源真实性 | 数据来自 PMIC/rail 计量、kernel 计数器，还是模型估算 | 决定能否做实验级对比 |
| attribution 粒度 | 是否提供 `EnergyConsumerAttribution[]`，以及是否稳定映射到 UID | 决定 Battery Historian/App 排名可信度 |
| 时间与采样稳定性 | timestamp、duration、采样周期是否与 CLOCK_BOOTTIME/μWs 语义一致 | 决定跨窗口、跨设备对比是否可靠 |

这四个维度比「厂商品牌」本身更重要。同一厂商不同平台、不同内核、不同 PMIC 组合也可能表现不同。

### 权限与新旧 API 老化阈值

framework 中对 fine-grained power monitor 访问有权限校验，涉及 `ACCESS_FINE_POWER_MONITORS`。普通应用只能走更保守的 legacy 访问路径；具备 fine 权限的调用方可以读取更新鲜的数据。`android-17.0.0_r1` 的 `PowerStatsService.java` 中，普通路径最大数据年龄为 `MAX_POWER_MONITOR_AGE_MILLIS = 20_000`，fine-grained 路径为 `MAX_FINE_POWER_MONITOR_AGE_MILLIS = 250`；也就是说 legacy 路径允许更老的数据，fine-grained 路径要求更短的数据年龄。

实际排查时，如果看到 API 返回数据陈旧或告警，应同时检查：

- HAL 是否持续更新 meter/model/residency；
- TimerTrigger 周期是否被平台配置拉长；
- 调用方是否具备 fine-grained 权限；
- vendor 是否在低电量、灭屏、suspend 场景下暂停了某些采样。

## 能力分级与部署

### OEM 实现差异应写成能力分级，而不是品牌排名

Pixel、Samsung、小米/MTK 等实现的很多细节不在 AOSP 主线公开，因此应按能力给设备分级，不能直接按品牌排名：

| 能力等级 | 典型表现 | 适合的分析场景 |
|---|---|---|
| L0：接口占位 | 仅有 fake/default 或极少对象 | 只能验证接口可用，不适合做功耗结论 |
| L1：rail meter 可用 | 能读取部分 `Channel` / `EnergyMeasurement` | 可做系统级趋势分析，组件拆分有限 |
| L2：组件模型可用 | 多个 `EnergyConsumer` 覆盖关键硬件 | 可做 CPU/Display/Modem/Wi-Fi 等组件级分析 |
| L3：UID attribution 可用 | `EnergyConsumerAttribution[]` 稳定且覆盖主要组件 | 可支撑 Battery Historian 中应用级耗电排名 |
| L4：实验级校准 | rail、时间戳、duration、单位换算经过校准 | 可用于跨版本/跨设备性能实验，但仍需标注机型边界 |

这样既保留「OEM 差异」主题，又避免把未验证的闭源实现写成确定事实。

### 跨厂商数据标准化

跨厂商比较 PowerStats 数据时，需要先做归一化与可信度标注：

1. **对象列表归一化**：先记录 `getPowerEntityInfo()`、`getEnergyConsumerInfo()`、`getEnergyMeterInfo()` 返回对象，明确哪些组件缺失。
2. **单位与时钟检查**：确认 `EnergyMeasurement.energyUWs`、`timestampMs`、`durationMs` 是否符合 AIDL 语义。
3. **采样窗口对齐**：同一实验只比较相同负载、相同屏幕状态、相近电量区间、相近温度窗口下的数据。
4. **attribution 单独标注**：组件总能耗和 UID 分摊不是同一可信度；`EnergyConsumerAttribution[]` 缺失时不能推出「某 App 不耗电」。
5. **写入来源标记**：报告中标注机型、build、kernel、HAL 对象列表、采样时长和是否具有 fine 权限。

跨设备功耗分析应保证每组数据的来源、口径和缺口可复现，不必追求统一的绝对数。

### 企业设备与实验室设备池的部署

如果要在企业设备或实验室设备池中使用 PowerStats，应采用「先验收、再监控」的流程：

```bash
adb shell dumpsys powerstats
adb shell dumpsys powerstats --proto meter
adb shell dumpsys powerstats --proto model
adb shell dumpsys powerstats --proto residency
```

验收清单：

- `dumpsys powerstats` 中是否能列出 PowerEntity、Channel、EnergyConsumer；
- 关键场景（亮屏、灭屏、视频、网络、定位）下 meter/model 数据是否持续增长；
- `EnergyConsumerResult` 是否带 attribution，以及 attribution 总和是否不超过 total energy；
- 设备重启、OTA、低电量模式后对象 ID 与名称是否稳定；
- 导出的 protobuf 是否能被内部工具或 Battery Historian 流程解析。

部署时建议把「设备能力等级」作为元数据写入监控平台。否则同一张 App 耗电榜可能混合了 L1 与 L3 设备，导致运营或优化结论失真。

## 实战排查：为什么不同手机的功耗榜差异很大？

当同一个 APK 在两台 Android 17 设备上显示出明显不同的耗电归因时，可以按以下顺序排查：

1. **先看 HAL 对象列表**：对象数量不同，说明统计口径已经不同。
2. **再看 attribution 是否存在**：没有 UID attribution 的设备无法给出实际的应用级分摊。
3. **检查采样窗口**：低频 model 采集可能导致短时间实验结果仍是旧数据。
4. **确认权限路径**：没有 fine 权限时，调用方可能只能读到更旧的 legacy 数据。
5. **最终再比较业务代码**：不要在 HAL 能力差异未排除前，把所有差异归因到 App 代码。

一个更可靠的报告模板是：

```text
设备：<model/build/kernel>
PowerStats 能力：L1/L2/L3/L4
对象数量：PowerEntity=<n>, Channel=<n>, EnergyConsumer=<n>
采样窗口：<start/end/duration>
权限路径：legacy / ACCESS_FINE_POWER_MONITORS
结论：仅在上述口径内成立
```

## 版本边界与待验证项

- 版本边界固定为 `android-17.0.0_r1` / Android 17 (API 37)，不引入 Android 18/API 38+ mainline 结论。
- Pixel 真实 PowerStats 实现、高通/MTK/三星 vendor HAL 细节未在 AOSP 主线公开验证；它们只作为能力差异的可能来源，不给出闭源实现的源码级断言。
- Battery Historian 对 `model/meter/residency` protobuf 的具体消费逻辑仍需后续章节或源码调研补充。
- `StatsPullAtomCallbackImpl` 与 StatsD 的协同机制缺少当前材料支撑，这里不作扩展。
