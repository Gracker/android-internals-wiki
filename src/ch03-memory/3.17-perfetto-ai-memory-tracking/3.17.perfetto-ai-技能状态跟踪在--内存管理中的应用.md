## 1. 三条版本线要分别记录

“Android 17 上使用 Perfetto v57”包含三个彼此独立的版本对象：

| 对象 | 本文锚点 | 能力范围 |
| --- | --- | --- |
| Android 平台源码 | Android 17 / API 37 / `android-17.0.0_r1` | `external/perfetto` 属于 v54.0 系列，平台头文件没有 `TRACE_STATE` |
| 主机分析工具 | Perfetto v57.1 | 可以读取 Android 17 trace，能够解析 State Track，并提供 `state` SQL view |
| Perfetto AI skill | v57.1 skill bundle | 向 coding agent 提供工作流、PerfettoSQL、Python 脚本和 Trace Processor wrapper |

主机 Trace Processor 可以比设备端组件更新。它能解析已有 packet，却不会为旧 trace 补出设备从未上报的数据。Android 17 平台 SDK 因而不能直接调用 v57 的 `StateTrack` 或 `TRACE_STATE`。

如果应用需要产生 State Track，可以显式集成 v57.1 或更新的 Perfetto C++ SDK。工程还要验证 system backend 兼容性、category 配置、初始化和 flush 时机、二进制体积以及 release 构建策略。这属于应用依赖升级，不属于 API 37 framework 能力。

## 2. AI skill 在分析链中的位置

Perfetto AI skill 是主机侧的工作流包。它不包含设备端诊断模型，也不会让 Trace Processor 自动判断泄漏。agent 会按照 Markdown 指令运行 SQL 或辅助脚本，再把查询结果与代码联系起来。

v57.1 提供五组 Android 内存工作流：

1. `heap_dump.md`：按进程和 heap dump 时间点排查 dominator class path；
2. `heap_dump_caching_optimizer.md`：寻找重复对象和缓存候选；
3. `heap_dump_cluster.md`：对多份 heap dump 的路径做聚类；
4. `java_allocation_profile.md`：分析 Java 分配时间序列；
5. `native_heap.md`：分析 heapprofd 记录的 native allocation。

这些工作流减少了重复 SQL 编写，但输出仍是候选证据。报告中应保存 skill bundle 版本、`trace_processor --version`、查询文本、trace 哈希、构建版本和采集场景。缺少其中任一项，后续人员都很难复现实验。

### 2.1 Heap dump 能回答什么

`heap_dump.md` 的固定 triage SQL 会按每个 `(process_name, graph_sample_ts)` 找出 `self_size` 最大的 dominator class node，并恢复祖先路径。这里的 `self_size` 来自 dominator class tree 聚合，不能解释成某个对象的 shallow size，也不能解释成整条路径都可回收。

一条“大路径”只适合生成需复核的假设。判断对象是否泄漏，还需检查：

- 多次 dump 中对象数量和大小是否持续增长；
- GC root、reference path 与 dominator 关系；
- 场景结束后对象是否越过预期生命周期；
- 注册、缓存、任务和 listener 是否存在匹配的释放点；
- 正常样本、异常样本及修复后样本是否采用相同采集条件。

体积较大的稳定缓存可能符合设计；单次占用较小、每次重复操作都增长的对象链反而更可疑。OOM 归因还要结合进程上限、RSS/PSS、native heap、graphics memory 和采集完整性，不能只看 Java heap dump 的一条路径。

### 2.2 Fleet 聚类的边界

v57.1 的 `cluster_paths.py` 会删除实例计数和 GC root 标签，把路径文本转为 TF-IDF 向量，再用 K-Means 聚类。这个处理适合归并相似线索，却会弱化 class 顺序、引用字段和 root 类型。

聚类前应按进程、构建版本、场景和采集配置分组，并保留 `trace_uuid` 与 `graph_sample_ts`。脚本接收 `--process_name` 参数，但 v57.1 实现没有用它过滤 DataFrame，调用方必须先过滤输入。簇 ID 只表示文本相似度；代表样本仍要回到对象图和源码复核。

## 3. State Track 的数据语义

State Track 记录某个对象或子系统在一段时间内所处的互斥字符串状态。它与另外两类轨道回答不同问题：

| 轨道 | 适合表达 |
| --- | --- |
| slice | 有开始和结束边界的一次工作 |
| counter | 随时间变化的数值 |
| state | 持续到下一次变化或显式清空的离散状态 |

Perfetto v57.1 在 `TrackEvent.Type` 中加入 `TYPE_STATE = 5`，在 `TrackDescriptor` 中加入 `StateDescriptor`。Trace Processor 把解析结果写入公开 `state` view，其中常用列为 `ts`、`dur`、`track_id`、`category`、`value` 和 `arg_set_id`。

`StateTracker` 按以下规则更新时间区间：

- 新值不同：关闭旧行，并从新时间戳创建一行；
- 新值相同：不创建新行，只把参数合入当前行；
- 空值：关闭当前行，不创建空状态行；
- trace 结束前未关闭：该行保留 `dur = -1`。

重复写入相同状态无法统计心跳次数。次数应由 instant event 或 counter 表达。`state` 也不同于内核调度产生的 `thread_state`；只有 producer 发送 `TYPE_STATE`，或 parser 明确映射某类事件时，查询中才会出现对应状态。

## 4. 用状态区间辅助内存定位

应用可以用稳定、低基数的状态值标记业务阶段，例如 `Loading`、`Inference`、`Displaying` 和 `Idle`。状态值不要包含 URL、账号、提示词或用户输入，以免扩大 trace 中的敏感信息范围。

一轮可复核的排查可按以下顺序执行：

1. 用 State Track 标记请求或生命周期阶段，同时记录请求 ID 等必要参数；
2. 按问题类型采集 heapprofd、Java heap dump、Java allocation profile、RSS/PSS counter 和 GC 事件；
3. 通过 `state.ts` 与 `state.dur` 划出时间窗口，再关联对应进程的分配记录；
4. 分别计算分配流量、净变化、存活对象和 retained size，避免混用指标；
5. 对比多个相同场景，并检查 trace 丢包、flush 和未关闭状态；
6. 从异常调用栈回到当前构建的源码，验证所有权和生命周期；
7. 修复后用相同配置重新采集，比较趋势和业务行为。

“某状态期间分配很多”只说明时间重叠。分配可能来自同进程的其他线程、前一阶段提交的异步任务或采样误差。State Track 提供业务时间边界，因果判断还依赖调用栈、线程上下文、对象图和对照实验。

`dur = -1` 的状态常被查询脚本视为延续到 trace 末尾。若它由丢包、进程退出或遗漏 flush 引起，区间会被放大。运行关联 SQL 前，应同时检查 `stats` 表和状态是否按设计显式清空。

## 5. 审阅 agent 输出

采用 AI skill 后，人工审阅至少覆盖这些项目：

- 是否固定并记录 Trace Processor 与 skill bundle 版本；
- 是否逐个处理所有 `(upid, graph_sample_ts)`；
- 是否区分 shallow size、retained size、累计分配和净变化；
- 空结果是否被误写为“没有泄漏”；
- 进程、构建、场景和采集配置是否一致；
- 聚类比例的统计单位与分母是否匹配；
- 引用的源码是否对应 trace 所在构建；
- trace 和代码是否进入未经授权的服务或目录；
- 修改是否经过人工确认与修复后 trace 验证。

AI skill 适合执行固定查询和整理候选假设。数据完整性、指标含义、源码所有权与实验设计仍由工程师负责。
