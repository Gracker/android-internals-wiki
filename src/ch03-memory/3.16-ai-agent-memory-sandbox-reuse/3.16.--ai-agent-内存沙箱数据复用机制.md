# Android 17 AI Agent 内存沙箱数据复用机制

<!-- outline-start -->
## 要点

### 🔹 GPU功耗管理基础
Android 17 引入了全新的 GPU 功耗管理策略，基于 DVFS（动态电压频率调节）机制的深度优化。

### 🔹 DVFS 调优算法
新算法结合了应用负载预测和系统资源监控，实现了更智能的频率和电压调节。

### 🔹 多核心协调机制
跨 GPU 核心的功耗分配协调，根据不同应用场景动态调整核心工作状态。

### 🔹 热量控制与性能平衡
在控制 GPU 发热的同时保持最佳的性能表现，引入了热量感知的调度策略。

### 🔹 SoC 厂商定制化
支持不同 SoC 厂商的定制化 DVFS 策略，充分发挥硬件性能潜力。

## 扩展

### 🔸 游戏场景优化
针对游戏场景的特殊功耗优化策略，平衡帧率和功耗的关系。

### 🔸 AI 推理任务
AI 推理任务在 GPU 上的功耗管理，考虑模型大小和推理频率的影响。

### 🔸 后台任务处理
后台 GPU 任务的功耗管理策略，避免不必要的资源占用。

## 平台没有 Agent 专用内存对象

Android 17 / API 37 / `android-17.0.0_r1` 没有名为“AI Agent 进程”的内核对象，也没有 Agent 专用内存 namespace、跨应用模型共享池或统一 NPU buffer API。

模型推理与工具调用仍受已有边界约束：

- Linux UID、进程地址空间与文件描述符；
- Binder、SELinux 和组件权限；
- cgroup v2、AMS 进程状态、MemoryLimiter 与 lmkd；
- SharedMemory、HardwareBuffer、文件映射和 ContentProvider URI；
- 厂商推理 service、HAL、GPU/NPU driver 的产品协议。

`com.google.android.aicore`、厂商 NPU service 或某款设备的缓存策略不属于 AOSP tag。引用它们时，要同时给出设备、包/服务版本、SELinux、HAL 和驱动证据。

## 四种部署方式

| 部署 | 身份与进程 | 内存记账 | 隔离边界 |
|---|---|---|---|
| App 进程内 | 应用 UID / 主进程 | 主进程 Java、native、file mapping 与 driver buffer | 没有额外故障隔离 |
| `android:process=":inference"` | 通常同一应用 UID / 独立 PID | 独立 PID，可分别观察 RSS/PSS | 隔离地址空间和 crash；不构成跨 UID 安全沙箱 |
| isolated service | isolated UID / 独立 PID | isolated 进程及其映射 | 权限和文件访问收窄，能力要经 IPC/fd 显式传入 |
| 系统或厂商推理服务 | 服务自身 UID / 进程 | 服务进程、cgroup 与驱动侧内存 | 由系统映像、SELinux 和服务协议决定 |

`android:process` 适合隔离 native crash，并允许结束整个推理进程来回收地址空间。它仍使用应用身份，不能承载不可信代码的保密要求。

isolated service 不会自动继承宿主权限和私有文件访问。需要模型、输入图像或硬件服务时，宿主应传入最少的只读 fd、buffer 和元数据，并确认目标设备为 isolated domain 开放了哪些服务。

## 内存属于谁

跨进程共享页时，RSS 会在每个映射进程中完整计算驻留页，直接相加会重复。PSS 按映射者数量分摊当时驻留的共享页。

| 内存来源 | 常见记账 | 复用条件与遗漏 |
|---|---|---|
| Java/native heap | 主要归分配进程 | allocator free 后可能保留 span，RSS 不会立刻下降 |
| 只读文件 `mmap` | 各进程 RSS，PSS 分摊同一 page-cache 页 | 解压、重排或写时复制会生成私有页 |
| `SharedMemory` | 各映射进程 RSS，PSS 分摊 | fd 与 mapping 生命周期独立 |
| `HardwareBuffer` / dma-buf | 由导入者、gralloc 与驱动统计 | CPU、GPU、display、NPU 可能同时持有引用 |
| 加速器私有内存 | 取决于 driver | 可能不完整进入普通进程 PSS |

分析模型内存时，应分别记录权重映射、KV/state、计算工作区、输入输出、runtime/allocator 与驱动保留。一个 PSS 总数无法解释各项生命周期。

## 控制消息与大块数据分开

Binder 适合命令、token、小型结构体和 fd。大块数据塞进 Parcel 会与同进程其他 transaction 竞争接收缓冲区，并可能触发 `TransactionTooLargeException`。

| 内容 | 建议通道 | 需要验证的边界 |
|---|---|---|
| 命令、状态、小型参数 | AIDL/Parcelable | 调用者、版本、幂等与取消 |
| 一次性大块字节 | `SharedMemory` + Binder fd | 长度、保护、mapping 与 fd 释放 |
| 图像/视频/硬件 tensor | `HardwareBuffer` | 格式、usage、导入、cache 与 fence |
| 持久内容 | ContentProvider URI / fd | URI grant、用户、过期与审计 |
| 跨应用动作 | App Functions | system_server 资格校验、目标函数和结果权限 |

Binder 传 fd 仍会发送一个小 Parcel。共享的是 fd 指向的对象，不代表端到端没有复制：发送方写共享区、接收方读到数组、runtime 重排、driver staging 都可能创建副本。

## `SharedMemory` 是页与能力句柄

`SharedMemory` 可 Parcelable，并通过共享 mapping 让多个进程访问同一组页。发送只读数据时，应：

1. 创建区域并完成写入；
2. 解除发送方可写 mapping；
3. 用 `setProtect(PROT_READ)` 移除后续 mapping 的写权限；
4. 通过受约束 AIDL 传 fd 与有效长度；
5. 双方分别解除 mapping 并关闭 fd。

`setProtect()` 只影响后续 mapping，不会撤销已经存在的可写 mapping。发送方仍保留可写视图时，接收方拿到的内容不能称为不可变快照。

fd 是一种能力。拿到 fd 的进程可以在保护范围内访问数据，因此还要校验 Binder 调用者、offset、length、格式、世代号和会话归属。

## `HardwareBuffer` 不是通用 NPU 内存

`HardwareBuffer` 描述格式、尺寸、层数和 usage。GPU、codec、camera 或加速器能否直接导入，取决于 producer/consumer 契约与驱动。

使用前要确认：

- 双方支持相同格式、布局和 usage；
- HAL/driver 能导入，不需要私有 staging buffer；
- cache 一致性与 acquire/release fence 正确传递；
- CPU lock 是否允许；
- 量化、对齐或动态 shape 是否触发重新分配。

统一物理内存设备上的 HardwareBuffer 也不能简单称为“GPU 显存”。分配 heap、硬件可见性和统计方式由 gralloc/driver 决定。

## ContentProvider 与 App Functions

ContentProvider 让数据留在所有者应用中，调用方按 URI、权限和查询协议访问。大对象应返回 metadata 与 content URI，再用 `ParcelFileDescriptor` 流式读取；不要把大型 blob 塞进 Cursor/Bundle。

App Functions 解决“谁能调用目标 App 的哪个函数”。system_server 校验 calling UID/package、用户边界、权限、allowlist 与目标 service 声明。请求与响应仍走 Parcelable，图像、文档或音频继续使用受控 URI/fd。

两种机制都不会允许一个 App 读取另一个 App 的任意地址空间。

## MemoryLimiter、lmkd 与进程状态

Android 17 没有通用的“正在执行 AI”进程标签。AMS 按组件状态、绑定、前台可感知性等计算进程状态和 `oom_score_adj`；lmkd 结合压力与可杀进程选择目标；MemoryLimiter 的行为还受设备配置影响。

进程内存变大不会直接重写 `oom_score_adj`。同一 adj 档位的候选比较、释放收益和厂商策略可能受内存量影响，但进程重要性仍来自 AMS 状态模型。

测试应覆盖前台、退后台、解绑、冻结、解冻、服务死亡和重新绑定，并记录：

- `dumpsys activity processes` 与 `/proc/<pid>/oom_score_adj`；
- Java/native/file/shared/dma-buf/swap 分类；
- 服务与客户端的 Binder 依赖；
- lmkd kill reason、重启与用户状态恢复；
- GPU/NPU driver 的 buffer 和 session 生命周期。
