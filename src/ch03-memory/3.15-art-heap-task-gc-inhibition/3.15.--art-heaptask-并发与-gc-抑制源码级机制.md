## `HeapTask` 在 ART 中的位置

Android 17 / API 37 / `android-17.0.0_r1` 中，`HeapTask` 是 ART runtime 的内部延时任务抽象。Java `HeapTaskDaemon` 进入 native `TaskProcessor::RunAllTasks()`，`TaskProcessor` 按 `target_run_time_` 排列任务，并由同一个 daemon 串行执行到期项。

主路径是：

`Daemons$HeapTaskDaemon` → `VMRuntime.runHeapTasks()` → JNI → `TaskProcessor::RunAllTasks()` → `HeapTask::Run()` → `Finalize()`。

`HeapTask` 继承 `SelfDeletingTask`。任务执行后，默认 `Finalize()` 会释放对象；提交方把所有权交给处理器后不能再次释放。

## Android 17 的任务范围

统计类型时要说明搜索目录。只看 `art/runtime/gc/heap.cc` 有 6 个派生类；搜索 Android 17 ART runtime 的生产 C++ 源码，共能定位 10 个：

| 定义位置 | 任务 | 用途 |
|---|---|---|
| `gc/heap.cc` | `ConcurrentGCTask` | 申请并发 GC，并用 GC 序号合并重复请求 |
| `gc/heap.cc` | `CollectorTransitionTask` | 执行收集器切换或后台压缩 |
| `gc/heap.cc` | `HeapTrimTask` | 裁剪 ART space、JNI 引用表和 arena |
| `gc/heap.cc` | `TimeBasedGcThresholdCheckTask` | 检查按时间和存活堆大小计算的 GC 阈值 |
| `gc/heap.cc` | `ReduceTargetFootprintTask` | fork 后分阶段收紧目标堆大小 |
| `gc/heap.cc` | `TriggerPostForkCCGcTask` | 启动后长时间无 GC 时补发后台 GC |
| `gc/reference_processor.cc` | `ClearedReferenceTask` | 把清理后的引用交给 Java `ReferenceQueue` |
| `startup_completed_task.*` | `StartupCompletedTask` | 结束启动期并释放启动缓存/线程池 |
| `trace_profile.cc` | `TraceStopTask` | 到期停止低开销方法追踪 |
| `jit/jit.cc` | `MapBootImageMethodsTask` | 延迟重映射 boot image 方法 |

继承关系不能证明任务一定进入 `TaskProcessor`。例如 Android 17 把 `kAsyncReferenceQueueAdd` 设为 false，`ClearedReferenceTask` 由 GC 调用方执行，没有走常规异步队列。

## 队列与“并发”的含义

`ConcurrentGCTask` 名称中的 concurrent 描述 GC collector 与 mutator 的执行关系，不表示 `TaskProcessor` 同时执行多项 HeapTask。daemon 从有序集合取出一项，调用 `Run()` 与 `Finalize()`，再处理下一项。

`TaskProcessor::Stop()` 也不是取消：

- 它把处理器标成停止并唤醒等待线程；
- 队列中未来才到期的任务会被提前取出；
- 所有剩余任务完成或 finalize 后，主循环才退出。

因此，冻结/解冻或 runtime 停止附近看到多个 ART 工作连续出现时，要按具体任务、GC 序号和 pending 条件逐项核对。

## 普通应用没有 GC 抑制开关

应用不能通过受支持 API 停止 `HeapTaskDaemon`、替换 `ConcurrentGCTask::Run()`、改写 `target_footprint_` 或向 `TaskProcessor` 插入阻塞任务。

这些方案依赖 ART 私有 ABI、C++ vtable、对象布局和符号可见性，版本或编译选项改变后即可失效。风险不限于少做一次 GC：

- 修改 vtable 可能影响对象所有权，造成 use-after-free 或重复释放；
- 阻塞 `TaskProcessor` 会连带延迟 heap trim、启动缓存释放、time-based 检查、追踪停止和 JIT 映射；
- 篡改分配统计或 target footprint 会破坏 GC/增长决策，并可能把进程推向分配失败、内核 reclaim 或 lmkd；
- GC 暂停被推迟后，后续回收可能更重，启动耗时转移到首次交互。

面向普通应用的优化应处理分配模式和对象生命周期：

1. 用 allocation sampling、heap dump 与 GC slice 找出集中分配和高存活对象；
2. 推迟首屏前不需要的构造，限制并发初始化产生的峰值；
3. 分开 Java heap、native heap、graphics、文件页和 swap；
4. 比较 GC cause、暂停时间、释放字节、首帧与 RSS/PSS；
5. 需要调整 ART 策略的系统产品在固定 tag 修改源码，并运行 ART、启动、GC 压力和冻结/解冻测试。

## Perfetto 中怎样验证

`TaskProcessor::RunAllTasks()` 没有自动为每个 C++ 派生类生成同名 slice。可观察的证据包括：

- 线程列表中的 `HeapTaskDaemon`；
- 由 cause 与 collector 组成的 GC slice；
- `TimeBasedGcThresholdCheck` 与 `PureTimeGcTrigger`；
- `Heap::TrimSpaces()`、JNI table trim 与 monitor deflation；
- 启动缓存、linear alloc 和线程池清理；
- 低开销方法追踪的启动/停止事件。

先确认 Perfetto 配置启用了 ART 事件，再把 daemon 线程、GC 日志、分配速率、RSS/PSS 与暂停时间对齐。看到 daemon 忙碌只能证明它在执行 ART 延时工作，不能直接判定发生 GC。
