# 14.8 Android 17 GPU 调试与性能优化工具链

<!-- outline-start -->
## 要点

### 🔹 GPU调试工具链架构
Android 17通过Perfetto集成的FrameTracer提供跨进程帧追踪，FPSReporter实现分层FPS监控，JankTracker进行卡顿分类检测，TimeStats提供详细的帧时间统计。硬件层的直接集成（如grallocusage用法转换）和用户态SurfaceFlinger中的GPU调试开关系统支持实时性能数据收集和分析。

### 🔹 SurfaceFlinger GPU调试系统
SurfaceFlinger初始化阶段加载大量GPU调试开关，包括回压控制、采样策略、预测策略等核心属性。系统通过debug.sf.enable_gl_backpressure等属性控制GPU合成行为，支持实时的性能调试与优化。



### 🔹 AGI System Profiler 与 ANGLE denylist 机制

Android 17 在 GPU 调试工具链中引入了 AGI System Profiler，通过 FeatureOverrideParser 机制实现了对 ANGLE 的精细化管理。

#### APA vs AGI System Profiler 架构差异

APA System Profiler（Android Performance Profiler）专注于应用性能分析，而 AGI System Profiler（Android Graphics Inspector）更侧重于系统级别的图形性能监控。在 Android 17 中，AGI 通过以下机制增强了 ANGLE 的处理能力：

```cpp
// frameworks/native/services/gpuservice/gpuservice.cpp (android-17.0.0_r1)
const char* const kConfigFilePath = "/system/etc/angle/feature_config_vk.binarypb";
mFeatureOverrideParser(kConfigFilePath)  // Android 17 新增 FeatureOverrideParser
```

#### ANGLE denylist 处理机制

1. **配置文件管理**：
   - 配置文件路径：`/system/etc/angle/feature_config_vk.binarypb`
   - 格式：Protocol Buffers 二进制格式
   - 支持运行时 feature override 和应用级别的 denylist 规则

2. **API 接口**：
   ```cpp
   // 切换 ANGLE 作为系统驱动
   void GpuService::toggleAngleAsSystemDriver(bool enabled);
   
   // 获取 feature override 配置
   void GpuService::getFeatureOverrides(FeatureOverrides& featureOverrides);
   ```

3. **权限控制**：
   - 仅限 system 用户拥有 `android.permission.ACCESS_GPU_SERVICE` 权限
   - 支持多用户权限隔离：`multiuser_get_app_id(uid)`

4. **统计增强**：
   ```cpp
   // GpuStats 中新增 ANGLE 统计
   int32_t angleLoadingCount = 0;     // ANGLE 加载次数统计
   int32_t angleLoadingFailureCount = 0; // ANGLE 加载失败次数统计
   std::vector<int64_t> angleDriverLoadingTime; // 加载时间统计
   ```

#### dumpsys 调试接口

```bash
# 查看 ANGLE feature override 配置
adb shell dumpsys gpu featureOverrides

# 切换 ANGLE 为系统驱动
adb shell dumpsys gpu toggleAngleAsSystemDriver 1

# 查看统计信息
adb shell dumpsys gpu --gpustats
```

这些改进使得 AGI System Profiler 能够更精确地识别和解决应用与 ANGLE 的兼容性问题，同时为开发者提供详细的性能数据支撑。


### 🔹 FPS监控架构
FPSReporter作为跨进程FPS监控的核心组件，通过LayerHierarchy分发层级FPS信息，支持多监听器注册与移除机制。系统设计考虑了进程间通信的稳定性与性能开销。

### 🔹 GPU回压控制机制
Android 17引入了基于时间戳的GPU回压控制策略，通过CompareByTargetRunTime排序算法和精确的时间等待机制，实现GPU合成任务的智能调度，避免了传统FIFO调度的性能瓶颈。

### 🔸 扩展：GPU调试工具的生产环境部署
探讨如何在生产环境中部署GPU调试工具，包括性能开销控制、数据采样策略、以及与现有监控系统的集成方案。

### 🔸 补丁（2026-07-08）：AGI gapii Spy 架构与单帧捕获机制

2026-07-07 报告覆盖了 SurfaceFlinger 端 FrameTracer / TimeStats / JankTracker 三段式调用链与 Perfetto GPU counter proto 双模式。本节作为第二幕补丁，聚焦 **AGI（Android GPU Inspector）端** 的 gapii Spy 真实捕获机制，填补 §14.8 关于"AGI Frame Profiler 单帧 GPU 分析工具"的源码空白。

#### AGI 版本边界与符号注入

- **AGI 3.3.3**（2026 Q2，`github.com/google/agi/version.bzl`）：`AGI_VERSION_MAJOR="3" / MINOR="3" / POINT="3"`
- gapii 通过 `gapii/cc/gapii_android.exports` 显式声明对外符号（`Spy_Entry`、`Spy_Exit`、`Spy_CreateInstance`），在 Android 上以 Vulkan layer（`libVkLayer_agi.so`，layer 名 `VK_LAYER_ANDROID_agi`）或 GL interceptor 形式注入目标进程
- **零侵入挂载**：通过 `debug.agi.procname` 系统属性（`gapii/cc/spy.cpp` 中的 `kCaptureProcessNameSystemProperty`）选择目标进程，属性不匹配时 `shouldCapture()` 一次字符串比较返回 false，**近乎零开销**

#### 单帧捕获路径（observeFramebuffer）

`gapii/cc/vulkan_extras.cpp` 中的 `VulkanSpy::observeFramebuffer` 揭示 AGI 单帧捕获的核心路径：

1. **帧边界定义**：`LastSubmission == SUBMIT` 且 `LastBoundQueue` 存在 → 取 `LastDrawInfos[queue]` → 找到当前 `mRenderPass` / `mFramebuffer` / `mLastSubpass`
2. **关键差异**：AGI 的"帧" = `vkQueueSubmit` 边界，**与 Perfetto 的 VSync / Choreographer 边界根本不同**
3. **framebuffer 限制**：`kMaxFramebufferObservationWidth = 3840 / Height = 2560`（`spy.cpp`），4K 以内；8K DisplayPort 外接会触发截断——这是 AGI 在大屏设备上的已知限制

#### chunk 切片与 OOM 防护

```cpp
// gapii/cc/vulkan_mid_execution.cpp
const uint64_t kChunkSizeLimit = 16 * 1024 * 1024;  // 16 MiB chunk
```

每次 Vulkan mid-execution capture 切片为 16 MiB，避免长 session（>10 分钟）OOM。回放端 `chunk_writer.cpp` 顺序读取。

#### AGI 与 APA System Profiler 功能边界（重要修正）

§14.8 既有章节将 APA 与 AGI 混为"GPU 调试工具链"是误导，需要分层：

| 维度 | AGI | APA（Android Studio Profiler）|
|------|-----|------------------------------|
| 捕获端 | gapii Vulkan layer / GL interceptor | JVMTI + Perfetto ftrace |
| 输出格式 | `.gfxtrace` protobuf | `.pftrace` + HPROF |
| 单帧 draw call 步进 | ✅（`gapis/replay` 主机 GPU 重放）| ❌ |
| 生产部署可用 | ❌（30-50% 开销）| ✅（SamplingProfiler low-overhead）|
| 集成方式 | 独立 CLI / Bazel | Android Studio 集成 |

**结论**：AGI = 开发期 GPU 调试工具（替代 RenderDoc 在 Android 端的地位）；APA = 生产期性能监控工具。**不重叠**，通过 Perfetto trace 在用户视角互补。

#### gapidapk 部署与 DeviceInfoService

- `gapidapk/gapidapk.go`：`installAttempts = 5`、`checkFrequency = 5s`、`launcherPath = /data/local/tmp/agi_launch_producer`
- `gapidapk/deviceinfo.go`：`sendDevInfoPort = "gapid-devinfo"`（abstract unix socket），`DeviceInfoService` 仅在 AGI CLI 连接时启动，**空闲无后台运行**
- **5s 缓存机制**（`bind.GetRegistry` + `lastInstallCheckKey`）：避免每次命令都重新检查 APK

当设备使用 ANGLE（§14.8 既有章节提及的 denylist 路径），gapii 截获的是 Vulkan 调用（ANGLE 把 GL 转 Vulkan），**性能开销理论上翻倍**——本调研未做实测，标注"未经一手验证"。

### 🔸 补丁（2026-07-08）：Android 17 GPU功耗监控与DVFS调优策略

本节基于 Android 17.0.0_r1 源码，深入分析 GPU 功耗监控与 DVFS（动态电压频率缩放）调优策略的实现机制，填补 §14.8 关于现代 GPU 分析工具和方法的研究空白。

#### 性能模式阈值机制

Android 17 实现了基于刷新率的智能性能模式切换，核心阈值定义：

```cpp
// frameworks/native/services/surfaceflinger/Scheduler.cpp:1205
constexpr Fps FPS_THRESHOLD_FOR_KERNEL_TIMER = 65_Hz;
```

**技术实现**：
- **性能模式激活**：当刷新率 > 65Hz 时自动激活性能模式
- **内核定时器同步**：性能模式下，内核定时器同步到硬件 VSYNC，提升响应速度
- **节能模式**：刷新率 ≤ 65Hz 时，DPU 功耗折叠节省能源

**调用链**：
```
Scheduler::idleTimerCallback() -> refreshRate > FPS_THRESHOLD_FOR_KERNEL_TIMER -> 
性能模式切换 -> resyncAllToHardwareVsync(true)
```

#### 场景感知性能提升系统

Android 17 实现了双场景触发机制：

1. **显示电源事件**：
```cpp
// frameworks/native/services/surfaceflinger/Scheduler.cpp:1157
// Display Power event will boost the refresh rate to performance.
// Clear Layer History to get fresh FPS detection
mLayerHistory.clear();
```

2. **触摸事件**：
```cpp
// frameworks/native/services/surfaceflinger/Scheduler.cpp:1235
// Touch event will boost the refresh rate to performance.
```

**实现逻辑**：
- 显示电源事件：重置电源定时器，清除图层历史记录，提升到性能模式
- 触摸事件：设置 TouchState 为 Active，立即触发性能提升
- 自动降级：定时器超时后根据刷新率阈值自动回退到节能模式

#### 显示电源管理模式

**电源状态机**：
```cpp
// frameworks/native/services/surfaceflinger/Scheduler.h:584
hal::PowerMode powerMode = hal::PowerMode::OFF;
```

**关键函数**：
- `setDisplayPowerMode()` - 设置显示电源模式
- `startPowerTimer()` - 启动电源状态管理定时器
- `displayPowerTimerCallback()` - 处理电源状态切换回调

**状态转换**：
```
hal::PowerMode::OFF -> hal::PowerMode::ON (性能模式)
hal::PowerMode::ON -> hal::PowerMode::OFF (节能模式)
```

#### DVFS定时器系统架构

**显存池配置**：

```cpp
maxFrameBufferAcquiredBuffers = max_frame_buffer_acquired_buffers(2);
```

#### 功耗优化效果与用户体验影响

**功耗优化效果**：
- **高负载场景**：性能模式激活，GPU 全频运行，提供最佳帧率

### 🔸 补丁（2026-07-11 daily-topics#6）：Android 17 Power HAL V6 GPU Headroom 与 DVFS 调优机制

本节接续 2026-07-08 已落地的 [SurfaceFlinger Scheduler 侧 DVFS 阈值与 Power Timer](#)，把视角切到 Power HAL V6 的 GPU 设备侧——即 `getGpuHeadroom()` 让上层应用在渲染前能拿到 GPU 余量估值，`EXPENSIVE_RENDERING` / `DISPLAY_UPDATE_IMMINENT` 让 SurfaceFlinger 主动告知 HAL 当前是"重负载还是空闲"。整套机制把 Android 17 的 GPU 功耗管理从"单点能量度量"升级到"三维：余量 + 趋势 + 反向信号"。

#### Power HAL V6 的 GPU 头空间接口

**源码位置**：`hardware/interfaces/power/aidl/android/hardware/power/IPower.aidl` (android-17.0.0_r1)

```aidl
GpuHeadroomResult getGpuHeadroom(in GpuHeadroomParams params);
```

* `setBoost()` 注释明确写"may be appropriate to raise the frequencies of CPU, GPU, memory subsystem, or stop CPU from going into deep sleep state"——**GPU 频率是 boost 的一等公民**。
* 引入 `sendCompositionData()` / `sendCompositionUpdate()`：让 SurfaceFlinger 把合成层的帧时序回灌到 HAL，让 HAL 自校准 DVFS 决策（不是被动等 `reportActual`）。

**GPU 相关 Boost（Boost.aidl）**：
* `INTERACTION`：触控事件，让 CPU/GPU 频率同时抬升；
* `DISPLAY_UPDATE_IMMINENT`：即将产生新帧，保证显示通路处于高性能态。

**GPU 相关 Mode（Mode.aidl）**：
* `EXPENSIVE_RENDERING`：即将进入重渲染窗口，让 HAL 抬 GPU 上限；
* `SUSTAINED_PERFORMANCE`、`FIXED_PERFORMANCE`、`GAME`、`GAME_LOADING`：长期功耗曲线约束。

#### GPU Headroom 计算参数与能力矩阵

**源码位置**：`hardware/interfaces/power/aidl/android/hardware/power/GpuHeadroomParams.aidl`

```aidl
parcelable GpuHeadroomParams {
    enum CalculationType { MIN, AVERAGE }
    CalculationType calculationType = CalculationType.MIN;
    int calculationWindowMillis = 1000;
}
```

* 两种计算语义：`MIN` 取窗口最小值（适合"是否还能再加负载"判断），`AVERAGE` 取均值（适合趋势分析）。
* 默认 1000ms 窗口与 kernel governor 周期对齐。

**源码位置**：`hardware/interfaces/power/aidl/android/hardware/power/SupportInfo.aidl`

`HeadroomSupportInfo` 强制约束 HAL 实现：
```aidl
parcelable HeadroomSupportInfo {
    boolean isGpuSupported;             // 能力开关
    int     gpuMinIntervalMillis;       // 轮询节流窗口（最小间隔）
    int     gpuMinCalculationWindowMillis = 50;
    int     gpuMaxCalculationWindowMillis = 10000;
}
```

* `isGpuSupported` 未实现时 framework 抛 `UnsupportedOperationException`；
* `gpuMinIntervalMillis` 控制**轮询频率**（call 太快返回缓存），不同于 `gpuMinCalculationWindowMillis`（估算时间宽度）。

#### Framework 端节流：`HintManagerService.getGpuHeadroom()`

**源码位置**：`frameworks/base/services/core/java/com/android/server/power/hint/HintManagerService.java` (android-17.0.0_r1)

缓存初始化（约 line 358）：
```java
mGpuHeadroomCache = new HeadroomCache<>(2, mSupportInfo.headroom.gpuMinIntervalMillis);
```

容量固定为 2 的 LRU 缓存，过期时间就是 HAL 上报的 `gpuMinIntervalMillis`。

`getGpuHeadroom()` 主体（约 line 1799–1847）：
```java
public GpuHeadroomResult getGpuHeadroom(@NonNull GpuHeadroomParamsInternal params) {
    if (!mSupportInfo.headroom.isGpuSupported) {
        throw new UnsupportedOperationException();
    }
    synchronized (mGpuHeadroomLock) {
        final GpuHeadroomResult res = mGpuHeadroomCache.get(halParams);
        if (res != null) {
            return res;  // 节流：不重发 binder call
        }
    }
    try {
        final GpuHeadroomResult res = mPowerHal.getGpuHeadroom(halParams);
        synchronized (mGpuHeadroomLock) {
            mGpuHeadroomCache.add(halParams, res);
        }
        return res;
    } catch (RemoteException e) { /* log + null */ }
}
```

* **节流策略**：参数组合（calculationType, calculationWindowMillis）命中缓存时直接复用，**绝不重发 binder call**；HAL 端即便支持更高频，也无法绕过 framework 这层缓存。
* **可观测性**：每次调用都写 `FrameworkStatsLog.GPU_HEADROOM_REPORTED`，包含 status / isFromCache / 归一化后的 headroom 值（写到 [0,1]）。
* **参数校验**：通过反射比对 `CalculationType` enum 字段，确保 `calculationWindowMillis` 落在 HAL 报告的 [min, max] 区间。

#### 应用层入口：`SystemHealthManager.getGpuHeadroom()`

**源码位置**：`frameworks/base/core/java/android/os/health/SystemHealthManager.java` (android-17.0.0_r1)


#### 14.8.10.1 `cmds/flatland/`：长期维护的 GPU 2D 合成基准

`flatland` 是 **2012 年起源、长期维护至今**的 cc_benchmark，用于 SoC 选型阶段早期评估 GPU 硬件性能（README 自陈）。**它不是调试工具，是基准工具**——与 §14.8 既有 GpuService / AGI / APA 服务端机制属于完全不同的层。

**构建系统**（`frameworks/native/cmds/flatland/Android.bp`，锚定 main）：

```python
cc_benchmark {
    name: "flatland",
    srcs: ["Composers.cpp", "GLHelper.cpp", "Renderers.cpp", "Main.cpp"],
    shared_libs: ["libEGL", "libGLESv2", "libcutils", "libgui", "libui", "libutils"],
    cflags: ["-Wall", "-Werror"],
    compile_multilib: "both",  // 同时产出 32/64 位（stem: flatland / flatland64）
}
```

**关键观察**：
- `cc_benchmark` 类型：**不是** `cc_binary`——标记这是 NDK benchmark，编译进 system 但不出 Play Store。
- `auto_gen_config: false`——不需要 host 自动测试配置。
- 依赖精简：`libgui`（SurfaceControl + BufferQueue）+ `libui`（Fence）+ `libEGL/libGLESv2`，**不依赖 libGLESv3**。

**核心抽象**（`frameworks/native/cmds/flatland/Flatland.h`）：

```cpp
enum { MAX_NUM_LAYERS = 16 };
enum { MAX_TEST_RUNS = 16 };

struct LayerDesc {
    uint32_t flags;
    Renderer* (*rendererFactory)();
    Composer* (*composerFactory)();
    int32_t x; int32_t y;
    uint32_t width; uint32_t height;
};

class Composer {
public:
    virtual bool setUp(const LayerDesc& desc, GLHelper* helper) = 0;
    virtual void tearDown() = 0;
    virtual bool compose(GLuint texName, const sp<GLConsumer>& glc) = 0;
};

class Renderer {
public:
    virtual bool setUp(GLHelper* helper) = 0;
    virtual void tearDown() = 0;
    virtual bool render(EGLSurface surface) = 0;
};
```

- `Renderer` 负责层内容生成，**唯一实现** `staticGradient()`。
- `Composer` 负责层叠加，**5 个实现**：`nocomp / opaque / opaqueShrink / blend / blendShrink`。
- 数据驱动：测试场景即一组 `LayerDesc` 数组，`BenchmarDesc` 持场景名 + 几何 + 测试高度数组 + 层列表。
- 单场景最多 16 层（`MAX_NUM_LAYERS`）、单次跑最多 16 个高度测试（`MAX_TEST_RUNS`）。

**5 个预定义基准场景**（`Main.cpp` 中 `benchmarks[]`）：

| 场景 | 几何 | 用途 |
|---|---|---|
| `16:10 Single Static Window` | 2560×1600 | 单层静态窗口 baseline |
| `4:3 Single Static Window` | 2048×1536 | 平板尺寸 |
| `16:10 App → Home Transition` | 2560×1600 | Launch 转场 + blend |
| `4:3 App → Home Transition` | 2048×1536 | 平板 Launch 转场 |
| `16:10 SurfaceView → Home Transition` | 2560×1600 | 硬件加速 surface 转场 |

每个场景在 4 个不同高度（800/1200/1600/2400）跑多次采样。**与 SF 服务端的差异**：flatland 用独立 GLContext 跑基准，**不经过生产 SurfaceFlinger 路径**。

**GradientRenderer 实现细节**（`Renderers.cpp`）：
- Shader 名 `"Gradient"`，通过 `helper->getShaderProgram` 检索。
- Uniform 列表：`uvToInterp / objToNdc / ditherKernel / invDitherKernelSize / color0 / color1`。
- Vertex attribute：`position / uv`。
- Dither 纹理：`GL_TEXTURE_2D`，kernel 大小由 `GLHelper::DITHER_KERNEL_SIZE` 决定。
- 颜色生成：`genColor()` 从 5 色轮盘（紫黄绿粉蓝）取色，保证多层视觉差异。

**Blitter 实现**（`Composers.cpp`）：
- `blit(texName, texMatrix, x, y, w, h)` 与 `modBlit(texName, texMatrix, modColor, ...)` 两种 API。
- Shader 名 `"Blit"`，uniform：`uvToTex / objToNdc / blitSrc / modColor`。

**⚠️ 运行要求**（`README.txt` 关键警告）：
- 运行前应**关闭显示 / 停止后台服务**（`adb shell stop`），**锁定 CPU/GPU/Memory 总线时钟**（README 明文："Running flatland with dynamic clocking essentially measures the behavior of the dynamic clocking algorithm under a fairly unrealistic workload"）
- frame time 输出三档：`fast (<3ms)` / 数值 / `slow (>50ms)` / `varies`
- `-s <ms>` 命令行选项防热降频，单样本 50~200 ms，推荐 sleep 10~50 ms

#### 14.8.10.2 `cmds/sfdo/`：2024 年新增的 Rust SF 调试 CLI

**这是 Android 17 in-development 阶段命令行调试的真正新增点**——SF 调试工具从 C++ 重写为 Rust。

**构建系统**（`frameworks/native/cmds/sfdo/Android.bp`，锚定 main）：

```python
rust_binary {
    name: "sfdo",
    srcs: ["sfdo.rs"],
    rustlibs: ["android.gui-rust", "libclap"],
    edition: "2021",
}
```

- `rust_binary` 类型——SF 调试 CLI 现代化重写的标志。
- 仅依赖 `libclap`（参数解析） + `android.gui-rust`（`gui/` Rust bindgen 自动生成的 AIDL 绑定）。
- **`android.gui-rust` 是 Android 平台统一模式**：与 `trusty/*`、`microdroid/*` Rust 二进制风格一致。

**核心 5 个子命令**（`frameworks/native/cmds/sfdo/sfdo.rs`）：

```rust
//! sfdo: Make surface flinger do things
use android_gui::{aidl::android::gui::ISurfaceComposer::ISurfaceComposer, binder};
use clap::{Parser, Subcommand};

const SERVICE_IDENTIFIER: &str = "SurfaceFlingerAIDL";

#[derive(Parser)]
struct Cli { #[command(subcommand)] command: Option<Commands> }

#[derive(Subcommand, Debug)]
enum Commands {
    DebugFlash { #[arg(short, long, default_value_t = 0)] delay: i32 },
    ForceClientComposition { state: Option<String> },
    FrameRateIndicator { state: Option<String> },
    ScheduleComposite,
    ScheduleCommit,
}
```

**子命令对照表**：

| 命令 | AIDL 调用 | 用途 | 与 §14.8 既有章节的关系 |
|---|---|---|---|
| `sfdo debug-flash -d N` | `setDebugFlash(N)` | 闪屏调试（整屏色块翻转） | 对应 §14.8「SF GPU 调试开关系统」的 setDebugFlash 入口 |
| `sfdo force-client-composition enabled` | `forceClientComposition(true)` | **强制关闭 HWC Overlay、走 GPU 合成** | **HWC bug 排查核心命令**（AIDL 注释："check if there is a bug in HW Composer"） |
| `sfdo frame-rate-indicator show` | `enableRefreshRateOverlay(true)` | 左上角绘制实时 fps 文本 | 补充 §14.8「FPS 监控架构」的交互入口 |
| `sfdo schedule-composite` | `scheduleComposite()` | 强制下一 VSYNC 前合成 | — |
| `sfdo schedule-commit` | `scheduleCommit()` | 强制下一 VSYNC 前提交 | — |

**toggle 解析**（`sfdo.rs::parse_toggle`）：
- 接受 `1/true/y/yes/on/enabled/show` 与 `0/false/n/no/off/disabled/hide`。
- `to_lowercase` 后字符串包含检查，**与 `dumpsys gpu` 的开关语义对齐**。
- **这是 `dumpsys gpu` 的 CLI 现代化替代**——同样功能，Rust 重写 + AIDL 化 + 有类型校验。

**进程模型**：`binder::ProcessState::start_thread_pool()` 启动线程池 → `binder::get_interface::<dyn ISurfaceComposer>(SERVICE_IDENTIFIER)` 拿到 `SurfaceFlingerAIDL` 代理 → 单调用 → 进程退出。**不常驻**，**不与 GpuStats sampling 冲突**。

#### 14.8.10.5 性能影响

- `flatland`：单样本 50~200 ms，**强制锁定 GPU/CPU/内存时钟**。5 场景 × 4 高度 ≈ 20 次采样 = 单设备 4~8 分钟。**对功耗与温度有显著影响**。
- `sfdo`：单调用 ≈ 1 AIDL binder transaction ≈ **< 5ms**。5 个子命令全部为诊断触发类，**对性能无影响**。

### 🔸 补丁（2026-07-10 daily-topics#5）：Flutter Impeller 运行时 Pipeline 创建反馈 + 异步编译线程模型 + PSO 缓存落盘策略

> ⚠️ **重要边界披露**：daily-topics#5（2026-07-10）原 source_refs `cmds/gpu/` 路径**实地核查不存在**（与 daily-topics#1 同源笔误）。该题面实为"Flutter Impeller shader 编译性能对渲染管线的影响机制"，是 Flutter engine 内部机制，**不在 AOSP 中**。本节源码全部锚定 `github.com/flutter/engine@main`。**Impeller 是 Flutter 独立项目，未进入 android-17.0.0_r1**（该 tag 截至 2026-07-10 公开 AOSP 尚未推送）。

#### 14.8.11.1 三后端 Pipeline 创建线程模型差异

| 后端 | 编译线程 | 与 Raster 线程关系 | async 参数生效 | 磁盘缓存 |
|---|---|---|---|---|
| **Vulkan** | `worker_task_runner_`（`fml::ConcurrentTaskRunner` 线程池） | 并行 | ✅ 是 | ✅ `flutter.impeller.vkcache` |
| **Metal** | Metal 内部线程（`completionHandler`） | 并行 | ✅ 是（间接） | ❌ 无（依赖驱动 MTLPipelineCache） |
| **GLES** | `ReactorGLES` 串行队列（保证 OpenGL ctx 单一线程） | 可能并行 / 串行 | ❌ **否**（参数忽略） | ❌ 无（仅内存 `programs_` 表） |

**关键源码**：
- `impeller/renderer/backend/vulkan/pipeline_library_vk.cc:144-220`：Vulkan `GetPipeline` 根据 `async` 决定 `worker_task_runner_->PostTask(generation_task)` 还是同步执行。
- `impeller/renderer/backend/metal/pipeline_library_mtl.mm:120-180`：Metal 走 `[device newRenderPipelineStateWithDescriptor:completionHandler:]`，**x86_64 模拟器**走 `retry_handler` 二次尝试。
- `impeller/renderer/backend/gles/pipeline_library_gles.cc:240-280`：GLES **完全忽略 `async` 参数**，统一走 `reactor_->AddOperation` 进入串行队列。

**性能影响**：GLES 路径的"async"参数是 API 对称性的 no-op，开发期用 Perfetto `impeller` category 抓 trace 时，所有 `impeller::LinkProgram` 事件都集中在 ReactorGLES 线程。

#### 14.8.11.2 Vulkan Pipeline 创建反馈埋点（kImpellerPipelineTraceID=1988）

```cpp
// impeller/renderer/backend/vulkan/pipeline_vk.cc:65-90
static void ReportPipelineCreationFeedbackToTrace(
    const PipelineDescriptor& desc,
    const vk::PipelineCreationFeedbackCreateInfoEXT& feedback) {
  static int64_t gPipelineCacheHits = 0;
  static int64_t gPipelineCacheMisses = 0;
  static int64_t gPipelines = 0;
  if (feedback.pPipelineCreationFeedback->flags &
      vk::PipelineCreationFeedbackFlagBits::eApplicationPipelineCacheHit) {
    gPipelineCacheHits++;
  } else {
    gPipelineCacheMisses++;
  }
  gPipelines++;
  static constexpr int64_t kImpellerPipelineTraceID = 1988;
  FML_TRACE_COUNTER("impeller", "PipelineCache", kImpellerPipelineTraceID,
                    "PipelineCacheHits", gPipelineCacheHits,
                    "PipelineCacheMisses", gPipelineCacheMisses,
                    "TotalPipelines", gPipelines);
}
```

**关键观察**：
- 三个 counter：`PipelineCacheHits` / `PipelineCacheMisses` / `TotalPipelines`，ID 固定为 `1988`（Impeller 团队约定的"PSO 缓存观测系列"）。
- **判断条件是 `eApplicationPipelineCacheHit` flag**——这是 Vulkan 1.3 驱动返回的 PSO cache 命中标志，Impeller 不自己算命中率，直接读驱动反馈。
- 日志输出由 `kReportPipelineCreationFeedbackToLogs = false` 默认关闭，但 trace 通道**总是开启**——开发期打开 `impeller` category 即可看到。
- **应用价值**：排查 Flutter 应用首屏 jank 时，可同时观察 `impeller` category 的 `PipelineCache` counter + `gfx` category 的 GPU 时间——若 `PipelineCacheMisses` 在某帧陡增且同步阻塞 Raster 线程，可判定为驱动 PSO 编译开销。

#### 14.8.11.3 50 帧 PSO 缓存落盘策略

```cpp
// impeller/renderer/backend/vulkan/pipeline_library_vk.cc:285-310
void PipelineLibraryVK::DidAcquireSurfaceFrame() {
  if (++frames_acquired_ == 50u) {
    if (cache_dirty_) {
      cache_dirty_ = false;
      PersistPipelineCacheToDisk();
    }
    frames_acquired_ = 0;
  }
}

void PipelineLibraryVK::PersistPipelineCacheToDisk() {
  worker_task_runner_->PostTask(
      [weak_cache = decltype(pso_cache_)::weak_type(pso_cache_)]() {
        auto cache = weak_cache.lock();
        if (!cache) { return; }
        cache->PersistCacheToDisk();
      });
}
```

**关键观察**：
- **`frames_acquired_ == 50u` 是严格等于 50 触发**（不是 `>=`），第 50 帧之后清零——每 50 帧重新计数。
- `cache_dirty_` 在每次新 pipeline 请求时即置位（`pipeline_library_vk.cc:158`），**但只有当帧数到 50 才检查**——**首 50 帧内新增的 PSO 不会落盘**，应用在第 30 帧被强杀就丢失。
- 50 帧 ≈ 1 秒（60Hz）/ 0.83 秒（120Hz）——大多数用户场景在第 50 帧时还在首屏 loading，**实际"安全窗口"比想象中小**。
- 落盘本身走 `worker_task_runner_->PostTask`——**不在 Raster 线程上**，避免 IO 阻塞。
- `DidAcquireSurfaceFrame` 从 `Rasterizer::DrawToSurfaces` 流程回调进入（具体路径在 `shell/common/rasterizer.cc`），不是每个 vsync 都触发。

#### 14.8.11.4 运行时 Shader 路径（JIT 编译 / RuntimeStage）

**关键源码**：`impeller/runtime_stage/runtime_stage.cc`

```cpp
// impeller/runtime_stage/runtime_stage.cc:55-72
RuntimeStage::Map RuntimeStage::DecodeRuntimeStages(
    const std::shared_ptr<fml::Mapping>& payload) {
  if (payload == nullptr || !payload->GetMapping()) { return {}; }
  if (!fb::RuntimeStagesBufferHasIdentifier(payload->GetMapping())) { return {}; }
  auto raw_stages = fb::GetRuntimeStages(payload->GetMapping());
  return {
      {RuntimeStageBackend::kSkSL,      RuntimeStageIfPresent(raw_stages->sksl(), payload)},
      {RuntimeStageBackend::kMetal,     RuntimeStageIfPresent(raw_stages->metal(), payload)},
      {RuntimeStageBackend::kOpenGLES,  RuntimeStageIfPresent(raw_stages->opengles(), payload)},
      {RuntimeStageBackend::kOpenGLES3, RuntimeStageIfPresent(raw_stages->opengles3(), payload)},
      {RuntimeStageBackend::kVulkan,    RuntimeStageIfPresent(raw_stages->vulkan(), payload)},
  };
}
```

**关键观察**：
- 一次 flatbuffer 解码产出 **5 个后端变体**（kSkSL/kMetal/kOpenGLES/kOpenGLES3/kVulkan）——RuntimeStage 离线打包时所有后端代码都打到 payload 中，运行期按 `impeller_context->GetRuntimeStageBackend()` 选择。
- **kSkSL 是兜底后端**：当 Impeller context 为空时（`shell/common/shell.cc:198-203` `DetermineRuntimeStageBackend` 函数），强制走 kSkSL——**关闭 Impeller 时 RuntimeStage 仍能用**（Skia 渲染路径）。
- Vulkan UBO 强制约定：`kVulkanUBOName = "_RESERVED_IDENTIFIER_FIXUP_gl_DefaultUniformBlock"`——用户 shader 不能用这个 UBO 名，否则 binding slot 冲突。
- **这是真正的运行时编译路径**（与 AOT 离线编译对照），主要服务于 Flutter `FragmentProgram` / `CustomFragmentShader` 引入的用户自定义 shader——是 Dart 端自定义 shader 引入 jank 的根因。

| 维度 | §14.8 主线（AOSP） | 本节（Impeller） |
