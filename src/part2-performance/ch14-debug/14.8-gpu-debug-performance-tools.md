# 14.8 Android 17 GPU 调试与性能优化工具链

<!-- outline-start -->
## 要点

### 🔹 GPU调试工具链架构
Android 17通过Perfetto集成的FrameTracer提供跨进程帧追踪，FPSReporter实现分层FPS监控，JankTracker进行卡顿分类检测，TimeStats提供详细的帧时间统计。硬件层的直接集成（如grallocusage用法转换）和用户态SurfaceFlinger中的GPU调试开关系统支持实时性能数据收集和分析。

### 🔹 SurfaceFlinger GPU调试系统
SurfaceFlinger初始化阶段加载大量GPU调试开关，包括回压控制、采样策略、预测策略等核心属性。系统通过debug.sf.enable_gl_backpressure等属性控制GPU合成行为，支持实时的性能调试与优化。



### 🔹 AGI System Profiler 与 ANGLE denylist 机制

Android 17 在 GPU 调试工具链中引入了 AGI System Profiler，通过 FeatureOverrideParser 机制实现了对 ANGLE 的精细化管理。

#### APA vs AGI System Profiler 架构差异

APA System Profiler（Android Performance Profiler）专注于应用性能分析，而 AGI System Profiler（Android Graphics Inspector）更侧重于系统级别的图形性能监控。在 Android 17 中，AGI 通过以下机制增强了 ANGLE 的处理能力：

```cpp
// frameworks/native/services/gpuservice/gpuservice.cpp (android-17.0.0_r1)
const char* const kConfigFilePath = "/system/etc/angle/feature_config_vk.binarypb";
mFeatureOverrideParser(kConfigFilePath)  // Android 17 新增 FeatureOverrideParser
```

#### ANGLE denylist 处理机制

1. **配置文件管理**：
   - 配置文件路径：`/system/etc/angle/feature_config_vk.binarypb`
   - 格式：Protocol Buffers 二进制格式
   - 支持运行时 feature override 和应用级别的 denylist 规则

2. **API 接口**：

   ```cpp
   // 获取 feature override 配置
   ```

3. **权限控制**：
   - 仅限 system 用户拥有 `android.permission.ACCESS_GPU_SERVICE` 权限
   - 支持多用户权限隔离：`multiuser_get_app_id(uid)`

4. **统计增强**：
   ```cpp

   ```

### 🔹 FPS监控架构
FPSReporter作为跨进程FPS监控的核心组件，通过LayerHierarchy分发层级FPS信息，支持多监听器注册与移除机制。系统设计考虑了进程间通信的稳定性与性能开销。

### 🔹 GPU回压控制机制
Android 17引入了基于时间戳的GPU回压控制策略，通过CompareByTargetRunTime排序算法和精确的时间等待机制，实现GPU合成任务的智能调度，避免了传统FIFO调度的性能瓶颈。

### 🔸 补丁（2026-07-11 daily-topics#7）：CPU-GPU同步瓶颈分析与线程调度优化策略

Android 17 RenderEngine 采用**「调用线程发任务 + worker 线程消费 + promise/future 异步回值」**的纯异步模型。`RenderEngineThreaded::threadMain` 在创建时把自己提到 `SCHED_FIFO priority=2` 并设置 cgroup task profile `"SFRenderEnginePolicy"`，并在 GPU 命令入队时通过 `panopticon::share()` 注册到 frame timeline；当 GPU 端不可用 native fence（`!GLExtensions::getInstance().hasNativeFenceSync()`）时，CPU 退路是 `sync_wait(fd, -1)` 的**阻塞等**，这是 Android 17 CPU-GPU 同步最大瓶颈的源码定位点。`FrameTimeline.cpp` 把 jank 拆成 `JankType::SurfaceFlingerCpuDeadlineMissed`（HWC 路径 CPU 错过 deadline）与 `JankType::SurfaceFlingerGpuDeadlineMissed`（GPU 合成路径 GPU 错过 deadline）两个独立位，让 dumpsys / Perfetto 能直接区分"卡在 CPU 还是卡在 GPU"。SFDO（Rust 重写后的 `cmds/sfdo/sfdo.rs`）新增的 `ScheduleComposite` / `ScheduleCommit` 让测试时绕过预测逻辑强制提交一帧，为同步延迟复现/测量提供工具。

#### 14.8.11.6 RenderEngine 线程模型与同步机制

**源码位置**：`frameworks/native/libs/renderengine/threaded/RenderEngineThreaded.cpp`（android-17.0.0_r1）

`RenderEngineThreaded` 继承 `RenderEngine`，构造时立即 `std::thread(&RenderEngineThreaded::threadMain, ...)` 起一条 worker 线程，并把 `mRenderEngine`（真正 Skia 后端）的所有权交给 worker（`mRenderEngine.reset()` 也在 worker 线程做）。调用线程发任务的方式是 `mFunctionCalls.push(...)` + `mCondition.notify_one()`：

```cpp
// RenderEngineThreaded.cpp:91-99  worker 主循环
void RenderEngineThreaded::threadMain(CreateInstanceFactory factory) {
    if (!SetTaskProfiles(0, {"SFRenderEnginePolicy"})) {
        ALOGW("Failed to set render-engine task profile!");
    }
    if (setSchedFifo(true) != NO_ERROR) {
        ALOGW("Couldn't set SCHED_FIFO");
    }
    ...
    while (mRunning) {
        if (const auto task = getNextTask(); task) { (*task)(*mRenderEngine); }
        std::unique_lock<std::mutex> lock(mThreadMutex);
        mCondition.wait(lock, [this] { return !mRunning || !mFunctionCalls.empty(); });
    }
}
```

**关键观察**：
- **优先级提升到 SCHED_FIFO 2**：worker 线程直接抢占 RT 调度权，绕开 CFS 公平调度。这是 GPU 同步延迟可控的关键设计——worker 拿到任务立即跑，不被 binder 线程或其他 SurfaceFlinger 工作项"插队"。
- **`SetTaskProfiles(0, {"SFRenderEnginePolicy"})`**：cgroup task profile 进一步限制 CPU 亲和性和大核调度。flag `disable_sched_fifo_re` 可关掉，用于功耗受限的低端机。
- **`mRenderEngine.reset()` 在 worker 线程**：这是"GL context 与创建线程同生死"的硬约束——worker 线程销毁 GL context，避免跨线程 EGL 资源释放导致的 GPU 端 crash。

#### 14.8.11.7 drawLayers 的异步 fence 返回：promise/future 通道

**源码位置**：`RenderEngineThreaded.cpp:289-307` + `RenderEngineThreaded.h`

调用线程提交 drawLayers 任务时，立刻把 `bufferFence.release()` 把 fd 所有权转交给 worker。worker 把 GPU 完成时返回的 `FenceResult` 通过 `resultPromise->set_value(...)` 推回。调用线程通过 `ftl::Future<FenceResult>` 等待 fence：

```cpp
// RenderEngineThreaded.cpp:289-307  drawLayers 入队
ftl::Future<FenceResult> RenderEngineThreaded::drawLayers(
        const DisplaySettings& display, const std::vector<LayerSettings>& layers,
        const std::shared_ptr<ExternalTexture>& buffer, base::unique_fd&& bufferFence) {
    SFTRACE_CALL();
    const auto resultPromise = std::make_shared<std::promise<FenceResult>>();
    std::future<FenceResult> resultFuture = resultPromise->get_future();
    int fd = bufferFence.release();
    {
        std::lock_guard lock(mThreadMutex);
        mNeedsPostRenderCleanup = true;
        mFunctionCalls.push(
                [resultPromise, display, layers, buffer, fd,
                 registration = panopticon::share()](renderengine::RenderEngine& instance) {
                    SFTRACE_NAME("REThreaded::drawLayers");
                    registration->start();  // 关键：注册到 frame timeline
                    instance.updateProtectedContext(layers, {buffer.get()});
                    instance.drawLayersInternal(std::move(resultPromise), display, layers, buffer,
                                                base::unique_fd(fd));
                });
    }
    mCondition.notify_one();
    return resultFuture;
}
```

**关键观察**：
- **`panopticon::share()`**：注册当前 frame 到 `FrameTimeline` 的共享注册对象。worker 线程完成 GPU 提交后，由 `FrameTimeline` 计算 deadline miss 并写入 jank 类型。`registration->start()` 在 worker 端打点，明确标记「GPU 工作从这一刻开始」。
- **`drawLayersInternal` 默认返回 `Fence::NO_FENCE`**（`RenderEngineThreaded.cpp:265-273`）——子类的 `SkiaGLRenderEngine` 在 `flushAndSubmit` 里覆盖该行为，生成真正的 native fence fd。

#### 14.8.11.8 GPU 端 fence 生成与 CPU 端等待：核心同步原语

**源码位置**：`frameworks/native/libs/renderengine/skia/SkiaGLRenderEngine.cpp:346-439`（android-17.0.0_r1）

```cpp
// SkiaGLRenderEngine.cpp:382-411  GPU fence → CPU 等
bool SkiaGLRenderEngine::waitGpuFence(base::borrowed_fd fenceFd) {
    if (!GLExtensions::getInstance().hasNativeFenceSync() ||
        !GLExtensions::getInstance().hasWaitSync()) {
        return false;   // 关键降级路径
    }
    base::unique_fd fenceDup(dup(fenceFd.get()));
    EGLint attribs[] = {EGL_SYNC_NATIVE_FENCE_FD_ANDROID, fenceDup.release(), EGL_NONE};
    EGLSyncKHR sync = eglCreateSyncKHR(mEGLDisplay, EGL_SYNC_NATIVE_FENCE_ANDROID, attribs);
    ...
    eglWaitSyncKHR(mEGLDisplay, sync, 0);   // CPU 端阻塞等
    EGLint error = eglGetError();
    eglDestroySyncKHR(mEGLDisplay, sync);
    return true;
}

// SkiaGLRenderEngine.cpp:413-441  CPU → GPU fence
base::unique_fd SkiaGLRenderEngine::flushGL() {
    if (!GLExtensions::getInstance().hasNativeFenceSync()) {
        return base::unique_fd();   // 关键：返回 -1 表示「无法生成 native fence」
    }
    EGLSyncKHR sync = eglCreateSyncKHR(mEGLDisplay, EGL_SYNC_NATIVE_FENCE_ANDROID, nullptr);
    if (sync == EGL_NO_SYNC_KHR) return base::unique_fd();
    glFlush();
    base::unique_fd fenceFd(eglDupNativeFenceFDANDROID(mEGLDisplay, sync));
    eglDestroySyncKHR(mEGLDisplay, sync);
    return fenceFd;
}
```

**关键观察**：
- **`hasNativeFenceSync` 是同步机制的硬门槛**：`SkiaGLRenderEngine::flushGL` 直接 return `unique_fd()`（即 fd=-1），`flushAndSubmit` 据此判断 `requireSync = true`，调用 `GrSyncCpu::kYes` 让 Skia 在 submit 时插入同步点——**这一条降级路径是 Android 17 同步瓶颈的源头**。
- **CPU 等 GPU 用 `eglWaitSyncKHR`**：这是 EGL 同步原语，理论上不阻塞 CPU 线程但需要 GPU 端 poll；但实际在某些驱动上仍会让 CPU 短暂 spin（`sync_wait(fd, -1)` 退路在 `waitFenceImpl` 里：`SkiaGLRenderEngine.cpp:347`）。

**源码位置**：`frameworks/native/cmds/sfdo/sfdo.rs`（android-17.0.0_r1，**已重写为 Rust**）

```rust
// sfdo.rs:140-160  ScheduleComposite / ScheduleCommit 实现
```

**关键观察**：
- **`sfdo` 已从 C++ 迁到 Rust**（文件 177 行，`copyright 2024`），这是 Android 17 的重大变化——`tools` 一类轻量调试工具统一用 Rust 重写以减少 C++ 编译依赖。
- **`ScheduleComposite` / `ScheduleCommit`** 是新增命令，绕过正常的预测调度逻辑，立即触发一次合成/提交——**这正是验证 CPU-GPU 同步延迟的工具入口**。运行 `adb shell sfdo schedule-commit` 后用 `dumpsys SurfaceFlinger --latency` 观察下次 vsync 的 `postComposition` 时间差，即可测出同步延迟上界。

#### 14.8.11.10 调试与诊断方法

**源码位置**：`frameworks/native/services/surfaceflinger/Scheduler/FrameTimeline.cpp`（android-17.0.0_r1）

```cpp
// FrameTimeline.cpp:109-130
std::vector<std::string> janks;
if (jankType & JankType::DisplayHAL) { janks.emplace_back("Display HAL"); jankType &= ~JankType::DisplayHAL; }
if (jankType & JankType::SurfaceFlingerCpuDeadlineMissed) {
    janks.emplace_back("SurfaceFlinger deadline missed (while in HWC)");
    jankType &= ~JankType::SurfaceFlingerCpuDeadlineMissed;
}
if (jankType & JankType::SurfaceFlingerGpuDeadlineMissed) {
    janks.emplace_back("SurfaceFlinger deadline missed (while in GPU comp)");
    jankType &= ~JankType::SurfaceFlingerGpuDeadlineMissed;
}
```

**关键调试命令**：
1. **`adb shell dumpsys SurfaceFlinger --latency`**：观察每个 VSYNC 周期内，从信号量触发到 `postComposition` 的时间差。若 `postComposition` 时间远超 previous vsync timestamp，说明 GPU 合成卡住。
2. **`adb shell sfdo schedule-commit`**：强制提交一帧，绕过正常预测调度。配合 `dumpsys SurfaceFlinger --latency` 可以直接观察 CPU-GPU 同步延迟。
3. **`adb shell dumpsys SurfaceFlinger --display-id`**：结合 `JankType` 枚举值，定位是 CPU 端（HWC 合成路径）还是 GPU 端（GPU 合成路径）瓶颈。

### 🔸 补丁（2026-07-08）：AGI gapii Spy 架构与单帧捕获机制

2026-07-07 报告覆盖了 SurfaceFlinger 端 FrameTracer / TimeStats / JankTracker 三段式调用链与 Perfetto GPU counter proto 双模式。本节作为第二幕补丁，聚焦 **AGI（Android GPU Inspector）端** 的 gapii Spy 真实捕获机制，填补 §14.8 关于"AGI Frame Profiler 单帧 GPU 分析工具"的源码空白。

#### AGI 版本边界与符号注入

- **AGI 3.3.3**（2026 Q2，`github.com/google/agi/version.bzl`）：`AGI_VERSION_MAJOR="3" / MINOR="3" / POINT="3"`
- gapii 通过 `gapii/cc/gapii_android.exports` 显式声明对外符号（`Spy_Entry`、`Spy_Exit`、`Spy_CreateInstance`），在 Android 上以 Vulkan layer（`libVkLayer_agi.so`，layer 名 `VK_LAYER_ANDROID_agi`）或 GL interceptor 形式注入目标进程
- **零侵入挂载**：通过 `debug.agi.procname` 系统属性（`gapii/cc/spy.cpp` 中的 `kCaptureProcessNameSystemProperty`）选择目标进程，属性不匹配时 `shouldCapture()` 一次字符串比较返回 false，**近乎零开销**

#### 单帧捕获路径（observeFramebuffer）

`gapii/cc/vulkan_extras.cpp` 中的 `VulkanSpy::observeFramebuffer` 揭示 AGI 单帧捕获的核心路径：

1. **帧边界定义**：`LastSubmission == SUBMIT` 且 `LastBoundQueue` 存在 → 取 `LastDrawInfos[queue]` → 找到当前 `mRenderPass` / `mFramebuffer` / `mLastSubpass`
2. **关键差异**：AGI 的"帧" = `vkQueueSubmit` 边界，**与 Perfetto 的 VSync / Choreographer 边界根本不同**
3. **framebuffer 限制**：`kMaxFramebufferObservationWidth = 3840 / Height = 2560`（`spy.cpp`），4K 以内；8K DisplayPort 外接会触发截断——这是 AGI 在大屏设备上的已知限制

#### chunk 切片与 OOM 防护

```cpp
// gapii/cc/vulkan_mid_execution.cpp
const uint64_t kChunkSizeLimit = 16 * 1024 * 1024;  // 16 MiB chunk
```

每次 Vulkan mid-execution capture 切片为 16 MiB，避免长 session（>10 分钟）OOM。回放端 `chunk_writer.cpp` 顺序读取。

#### AGI 与 APA System Profiler 功能边界（重要修正）

§14.8 既有章节将 APA 与 AGI 混为"GPU 调试工具链"是误导，需要分层：

| 维度 | AGI | APA（Android Studio Profiler）|
|------|-----|------------------------------|
| 捕获端 | gapii Vulkan layer / GL interceptor | JVMTI + Perfetto ftrace |
| 输出格式 | `.gfxtrace` protobuf | `.pftrace` + HPROF |
| 单帧 draw call 步进 | ✅（`gapis/replay` 主机 GPU 重放）| ❌ |
| 生产部署可用 | ❌（30-50% 开销）| ✅（SamplingProfiler low-overhead）|
| 集成方式 | 独立 CLI / Bazel | Android Studio 集成 |

**结论**：AGI = 开发期 GPU 调试工具（替代 RenderDoc 在 Android 端的地位）；APA = 生产期性能监控工具。**不重叠**，通过 Perfetto trace 在用户视角互补。

#### gapidapk 部署与 DeviceInfoService

- `gapidapk/gapidapk.go`：`installAttempts = 5`、`checkFrequency = 5s`、`launcherPath = /data/local/tmp/agi_launch_producer`
- `gapidapk/deviceinfo.go`：`sendDevInfoPort = "gapid-devinfo"`（abstract unix socket），`DeviceInfoService` 仅在 AGI CLI 连接时启动，**空闲无后台运行**
- **5s 缓存机制**（`bind.GetRegistry` + `lastInstallCheckKey`）：避免每次命令都重新检查 APK

#### ANGLE 路径下的性能开销（未经一手实测）

当设备使用 ANGLE（§14.8 既有章节提及的 denylist 路径），gapii 截获的是 Vulkan 调用（ANGLE 把 GL 转 Vulkan），**性能开销理论上翻倍**——本调研未做实测，标注"未经一手验证"。

`getGpuHeadroom()` 主体（约 line 1799–1847）：
```java
public GpuHeadroomResult getGpuHeadroom(@NonNull GpuHeadroomParamsInternal params) {
    if (!mSupportInfo.headroom.isGpuSupported) {
        throw new UnsupportedOperationException();
    }
    synchronized (mGpuHeadroomLock) {
        final GpuHeadroomResult res = mGpuHeadroomCache.get(halParams);
        if (res != null) {
            return res;  // 节流：不重发 binder call
        }
    }
    try {
        final GpuHeadroomResult res = mPowerHal.getGpuHeadroom(halParams);
        synchronized (mGpuHeadroomLock) {
            mGpuHeadroomCache.add(halParams, res);
        }
        return res;
    } catch (RemoteException e) { /* log + null */ }
}
```

* **节流策略**：参数组合（calculationType, calculationWindowMillis）命中缓存时直接复用，**绝不重发 binder call**；HAL 端即便支持更高频，也无法绕过 framework 这层缓存。
* **可观测性**：每次调用都写 `FrameworkStatsLog.GPU_HEADROOM_REPORTED`，包含 status / isFromCache / 归一化后的 headroom 值（写到 [0,1]）。
* **参数校验**：通过反射比对 `CalculationType` enum 字段，确保 `calculationWindowMillis` 落在 HAL 报告的 [min, max] 区间。

```cpp
        stats.min_value = *std::min_element(pair.second.begin(), pair.second.end());
        stats.max_value = *std::max_element(pair.second.begin(), pair.second.end());

    }
```

```cpp
    const GpuCounterData& counters,

    float basePower = getBasePowerForState(state);
```

#### 14.8.10.1 `cmds/flatland/`：长期维护的 GPU 2D 合成基准

`flatland` 是 **2012 年起源、长期维护至今**的 cc_benchmark，用于 SoC 选型阶段早期评估 GPU 硬件性能（README 自陈）。**它不是调试工具，是基准工具**——与 §14.8 既有 GpuService / AGI / APA 服务端机制属于完全不同的层。

**构建系统**（`frameworks/native/cmds/flatland/Android.bp`，锚定 main）：

```python
cc_benchmark {
    name: "flatland",
    srcs: ["Composers.cpp", "GLHelper.cpp", "Renderers.cpp", "Main.cpp"],
    shared_libs: ["libEGL", "libGLESv2", "libcutils", "libgui", "libui", "libutils"],
    cflags: ["-Wall", "-Werror"],
    compile_multilib: "both",  // 同时产出 32/64 位（stem: flatland / flatland64）
}
```

**关键观察**：
- `cc_benchmark` 类型：**不是** `cc_binary`——标记这是 NDK benchmark，编译进 system 但不出 Play Store。
- `auto_gen_config: false`——不需要 host 自动测试配置。
- 依赖精简：`libgui`（SurfaceControl + BufferQueue）+ `libui`（Fence）+ `libEGL/libGLESv2`，**不依赖 libGLESv3**。

**核心抽象**（`frameworks/native/cmds/flatland/Flatland.h`）：

```cpp
enum { MAX_NUM_LAYERS = 16 };
enum { MAX_TEST_RUNS = 16 };

struct LayerDesc {
    uint32_t flags;

    Composer* (*composerFactory)();
```

- `Renderer` 负责层内容生成，**唯一实现** `staticGradient()`。
- `Composer` 负责层叠加，**5 个实现**：`nocomp / opaque / opaqueShrink / blend / blendShrink`。
- 数据驱动：测试场景即一组 `LayerDesc` 数组，`BenchmarDesc` 持场景名 + 几何 + 测试高度数组 + 层列表。
- 单场景最多 16 层（`MAX_NUM_LAYERS`）、单次跑最多 16 个高度测试（`MAX_TEST_RUNS`）。

**5 个预定义基准场景**（`Main.cpp` 中 `benchmarks[]`）：

| 场景 | 几何 | 用途 |
|---|---|---|
| `16:10 Single Static Window` | 2560×1600 | 单层静态窗口 baseline |
| `4:3 Single Static Window` | 2048×1536 | 平板尺寸 |
| `16:10 App → Home Transition` | 2560×1600 | Launch 转场 + blend |
| `4:3 App → Home Transition` | 2048×1536 | 平板 Launch 转场 |
| `16:10 SurfaceView → Home Transition` | 2560×1600 | 硬件加速 surface 转场 |

**GradientRenderer 实现细节**（`Renderers.cpp`）：
- Shader 名 `"Gradient"`，通过 `helper->getShaderProgram` 检索。
- Uniform 列表：`uvToInterp / objToNdc / ditherKernel / invDitherKernelSize / color0 / color1`。
- Vertex attribute：`position / uv`。
- Dither 纹理：`GL_TEXTURE_2D`，kernel 大小由 `GLHelper::DITHER_KERNEL_SIZE` 决定。
- 颜色生成：`genColor()` 从 5 色轮盘（紫黄绿粉蓝）取色，保证多层视觉差异。

**Blitter 实现**（`Composers.cpp`）：
- `blit(texName, texMatrix, x, y, w, h)` 与 `modBlit(texName, texMatrix, modColor, ...)` 两种 API。
- Shader 名 `"Blit"`，uniform：`uvToTex / objToNdc / blitSrc / modColor`。

- 运行前应**关闭显示 / 停止后台服务**（`adb shell stop`），**锁定 CPU/GPU/Memory 总线时钟**（README 明文："Running flatland with dynamic clocking essentially measures the behavior of the dynamic clocking algorithm under a fairly unrealistic workload"）

#### 14.8.11.2 Vulkan Pipeline 创建反馈埋点（kImpellerPipelineTraceID=1988）

```cpp
// impeller/renderer/backend/vulkan/pipeline_vk.cc:65-90
static void ReportPipelineCreationFeedbackToTrace(
    const PipelineDescriptor& desc,
    const vk::PipelineCreationFeedbackCreateInfoEXT& feedback) {
  static int64_t gPipelineCacheHits = 0;
  static int64_t gPipelineCacheMisses = 0;
  static int64_t gPipelines = 0;
  if (feedback.pPipelineCreationFeedback->flags &
      vk::PipelineCreationFeedbackFlagBits::eApplicationPipelineCacheHit) {
    gPipelineCacheHits++;
  } else {
    gPipelineCacheMisses++;
  }
  gPipelines++;
  static constexpr int64_t kImpellerPipelineTraceID = 1988;
  FML_TRACE_COUNTER("impeller", "PipelineCache", kImpellerPipelineTraceID,
                    "PipelineCacheHits", gPipelineCacheHits,
                    "PipelineCacheMisses", gPipelineCacheMisses,
                    "TotalPipelines", gPipelines);
}
```

**关键观察**：
- 三个 counter：`PipelineCacheHits` / `PipelineCacheMisses` / `TotalPipelines`，ID 固定为 `1988`（Impeller 团队约定的"PSO 缓存观测系列"）。
- **判断条件是 `eApplicationPipelineCacheHit` flag**——这是 Vulkan 1.3 驱动返回的 PSO cache 命中标志，Impeller 不自己算命中率，直接读驱动反馈。
- 日志输出由 `kReportPipelineCreationFeedbackToLogs = false` 默认关闭，但 trace 通道**总是开启**——开发期打开 `impeller` category 即可看到。
- **应用价值**：排查 Flutter 应用首屏 jank 时，可同时观察 `impeller` category 的 `PipelineCache` counter + `gfx` category 的 GPU 时间——若 `PipelineCacheMisses` 在某帧陡增且同步阻塞 Raster 线程，可判定为驱动 PSO 编译开销。

#### 14.8.11.3 50 帧 PSO 缓存落盘策略

```cpp
// impeller/renderer/backend/vulkan/pipeline_library_vk.cc:285-310
void PipelineLibraryVK::DidAcquireSurfaceFrame() {
  if (++frames_acquired_ == 50u) {
    if (cache_dirty_) {
      cache_dirty_ = false;
      PersistPipelineCacheToDisk();
    }
    frames_acquired_ = 0;
  }
}

void PipelineLibraryVK::PersistPipelineCacheToDisk() {
  worker_task_runner_->PostTask(
      [weak_cache = decltype(pso_cache_)::weak_type(pso_cache_)]() {
        auto cache = weak_cache.lock();
        if (!cache) { return; }
        cache->PersistCacheToDisk();
      });
}
```

**关键观察**：
- **`frames_acquired_ == 50u` 是严格等于 50 触发**（不是 `>=`），第 50 帧之后清零——每 50 帧重新计数。
- `cache_dirty_` 在每次新 pipeline 请求时即置位（`pipeline_library_vk.cc:158`），**但只有当帧数到 50 才检查**——**首 50 帧内新增的 PSO 不会落盘**，应用在第 30 帧被强杀就丢失。
- 50 帧 ≈ 1 秒（60Hz）/ 0.83 秒（120Hz）——大多数用户场景在第 50 帧时还在首屏 loading，**实际"安全窗口"比想象中小**。
- 落盘本身走 `worker_task_runner_->PostTask`——**不在 Raster 线程上**，避免 IO 阻塞。
- `DidAcquireSurfaceFrame` 从 `Rasterizer::DrawToSurfaces` 流程回调进入（具体路径在 `shell/common/rasterizer.cc`），不是每个 vsync 都触发。

```cpp
RuntimeStage::Map RuntimeStage::DecodeRuntimeStages(
    const std::shared_ptr<fml::Mapping>& payload) {
  if (payload == nullptr || !payload->GetMapping()) { return {}; }
  if (!fb::RuntimeStagesBufferHasIdentifier(payload->GetMapping())) { return {}; }
  auto raw_stages = fb::GetRuntimeStages(payload->GetMapping());

      {RuntimeStageBackend::kMetal,     RuntimeStageIfPresent(raw_stages->metal(), payload)},
```

**关键源码——GpuMem 的 eBPF attach 流程**：

```cpp
// frameworks/native/services/gpuservice/gpumem/GpuMem.cpp (android-17.0.0_r1)
static constexpr char kGpuMemTraceGroup[] = "gpu_mem";
static constexpr char kGpuMemTotalTracepoint[] = "gpu_mem_total";
static constexpr char kGpuMemTotalProgPath[] =
        "/sys/fs/bpf/prog_gpuMem_tracepoint_gpu_mem_gpu_mem_total";
static constexpr char kGpuMemTotalMapPath[] = "/sys/fs/bpf/map_gpuMem_gpu_mem_total_map";
static constexpr int kGpuWaitTimeout = 30;  // 30 秒 attach 重试窗口

void GpuMem::initialize() {
    bpf::waitForProgsLoaded();
    int fd = bpf::retrieveProgram(kGpuMemTotalProgPath);
    int count = 0;
    while (bpf_attach_tracepoint(fd, kGpuMemTraceGroup, kGpuMemTotalTracepoint) < 0) {
        if (++count > kGpuWaitTimeout) {
            ALOGE("Failed to attach bpf program to %s/%s", kGpuMemTraceGroup,
                  kGpuMemTotalTracepoint, errno, strerror(errno));
            return;
        }
    }
    mGpuMemTotalMap = bpf::BpfMapRO<uint64_t, uint64_t>(kGpuMemTotalMapPath);
    mInitialized.store(true);
}
```

**技术要点**：
- **BPF map key = `uint64_t`**——`(gpu_id << 32) | pid` 打包成单 key，适配 eBPF 内核 map 接口；
- **30 秒轮询 attach**——`kGpuWaitTimeout=30` 容忍 BPF FS 在 early-boot 阶段未就绪；
- **RO 权限**——`BpfMapRO<uint64_t, uint64_t>` 用户态只读，防止应用进程污染追踪数据；
- **路径标准化**——`/sys/fs/bpf/prog_gpuMem_tracepoint_gpu_mem_gpu_mem_total` 反映 BPF FS 的 `prog_<program>_<group>_<event>` 命名约定。

#### Perfetto 数据源：启动期快照模型

**源码位置**：`tracing/GpuMemTracer.cpp`（android-17.0.0_r1）

```cpp
void GpuMemTracer::threadLoop(bool infiniteLoop) {
    do {
        std::unique_lock<std::mutex> lock(sTraceMutex);
        while (!sTraceStarted) sCondition.wait(lock);  // 等 Perfetto Start 通知
        traceInitialCounters();                         // 启动瞬间拍快照
        sTraceStarted = false;
    } while (infiniteLoop);
}

void GpuMemTracer::traceInitialCounters() {
    mGpuMem->traverseGpuMemTotals([](int64_t ts, uint32_t gpuId, uint32_t pid, uint64_t size) {
        GpuMemDataSource::Trace([&](GpuMemDataSource::TraceContext ctx) {
            auto packet = ctx.NewTracePacket();
            packet->set_timestamp_clock_id(perfetto::protos::pbzero::BUILTIN_CLOCK_MONOTONIC);
            packet->set_timestamp(ts);
            auto* event = packet->set_gpu_mem_total_event();
            event->set_gpu_id(gpuId);
            event->set_pid(pid);
            event->set_size(size);
        });
    });
    GpuMemDataSource::Trace([](GpuMemDataSource::TraceContext ctx) { ctx.Flush(); });
}
```

**技术要点**：
- **数据源名** `kGpuMemDataSource = "android.gpu_mem"`——Perfetto UI 可直接识别渲染；
- **守护线程** `pthread_setname_np(handle, "GpuMemTracerThread")`——独立命名便于 `ps -A` 排查；
- **系统后端** `kSystemBackend`——数据通过 `traced` 守护进程转发，非 in-process。

#### 显存池碎片整理：真实职责边界

**关键判断**：Android 17 的「显存池碎片整理」**不存在于 AOSP 用户态代码**。证据如下：

1. **AOSP 不持有显存**——`gpuservice/` 仅做观测，所有分配由 gralloc HAL 与厂商驱动（KGSL/ARM/Mali/PVRCore）完成；
2. **SurfaceFlinger 层的「显存池」是 buffer 缓存策略**——`maxFrameBufferAcquiredBuffers = max_frame_buffer_acquired_buffers(2)`（默认 2 帧三缓冲）、`imageCacheSize` 与 `BUFFER_CACHE_MAX_SIZE = 4096`（64 buffers × 64 layers），属于**应用层 buffer 缓存上限**，不是驱动级碎片整理；
3. **真正的碎片整理在驱动内**——AOSP 公开代码不含厂商私有实现（Adreno KGSL 的 `kgsl_sharedmem`、Mali 的 `kbase_mem_alloc`），本调研无法深入；
4. **应用层接口缺失**——当前 AOSP 未提供 NDK API 让应用主动声明显存预算或触发整理。

**可观测 vs 可干预的边界**：

| 层级 | 可观测 | 可干预 |
|------|--------|--------|
| AOSP gpuservice/ | ✅ BPF map + Perfetto + statsd | ❌（无分配 API） |
| SurfaceFlinger 策略层 | ✅ dumpsys / proto dump | ✅ `maxFrameBufferAcquiredBuffers` / `imageCacheSize` 等 sysprop |
| gralloc HAL | ❌（黑盒） | ✅（厂商私有） |
| 内核驱动 | ❌（黑盒） | ✅（厂商私有） |

#### 与 §14.8 主线（GPU 调试工具链）的集成

`gpuservice/` 三套观测机制直接增强 §14.8 主线工具链：

1. **AGI System Profiler**——可通过 Perfetto trace 拉取 `gpu_mem_total_event`，在 UI 中按 pid 展示显存占用瀑布图；
2. **dumpsys gpu**——`dumpGpuMemoryUsage()` 走 `traverseGpuMemTotals()`，输出每个 pid 的总占用字节数；
3. **sfdo/flatland**——可结合 statsd 历史数据做 GPU 内存与帧时延的联合分析；
4. **APA**——Android Performance Profiler 通过 statsd pull atom 拿到 `GPU_STATS_GLOBAL_INFO`/`GPU_STATS_APP_INFO`，补充驱动加载耗时数据。
