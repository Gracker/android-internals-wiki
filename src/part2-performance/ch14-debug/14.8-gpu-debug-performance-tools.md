# 14.8 Android 17 GPU 调试与性能优化工具链

<!-- outline-start -->
## 要点

Android 17（`android-17.0.0_r1`）的 GPU 调试与性能优化工具链不是一个单一 Profiler，而是由 **SurfaceFlinger 帧时序、GpuService 驱动与内存统计、Perfetto/StatsD 数据通道、AGI 开发期捕获工具、以及 `sfdo`/`flatland` 命令行工具**共同组成。阅读本节时需要先区分三类边界：

1. **系统侧观测**：FrameTracer、TimeStats、JankTracker、GpuMem/GpuStats 等常驻于 SurfaceFlinger 或 GpuService，面向 Perfetto、statsd、`dumpsys` 输出。
2. **开发期 GPU 捕获**：AGI（Android GPU Inspector）通过 gapii Vulkan layer / GL interceptor 注入目标进程，适合单帧 draw call 和 GPU state 分析，不适合生产常驻。
3. **诊断触发工具**：`sfdo`、`dumpsys SurfaceFlinger`、`dumpsys gpu`、`flatland` 用于强制合成、查看统计、跑基准或复现场景；它们不能替代系统侧持续观测。

> 版本边界：本节只讨论 Android 17 / API 37 / `android-17.0.0_r1` 已有机制。凡是来自独立项目（如 Flutter engine）或 AOSP main 分支而未锚定 r1 的内容，不作为本节结论。

## 14.8.1 SurfaceFlinger 帧时序：FrameTracer、TimeStats 与 JankTracker

Android 17 的图形性能观测主线可以拆成三条互补通道：

| 通道 | 运行位置 | 输出 | 适合回答的问题 |
|---|---|---|---|
| FrameTracer | SurfaceFlinger / Layer 生命周期 | Perfetto DataSource：`android.graphics.FrameLatency` | 单个 Layer 的 buffer 何时 dequeue、queue、latch、present？ |
| TimeStats | SurfaceFlinger 聚合统计 | statsd pull atom / dumpsys | 一段时间内帧耗时、jank payload、帧率投票分布如何？ |
| JankTracker | SurfaceFlinger jank 通知 | 监听器批量分发 | 运行时卡顿分类和监听回调是否触发？ |

### FrameTracer 的真实入口

FrameTracer 不是在 Perfetto 里凭空生成事件，而是在 `frameworks/native/services/surfaceflinger/Layer.cpp` 的 buffer 生命周期关键点被调用。已验证的事件包括：

```cpp
// AOSP android-17.0.0_r1, frameworks/native/services/surfaceflinger/Layer.cpp
mFlinger->mFrameTracer->traceTimestamp(layerId, bufferId, frameNumber,
                                       dequeueTime,
                                       FrameTracer::FrameEvent::DEQUEUE);
mFlinger->mFrameTracer->traceTimestamp(layerId, bufferId, frameNumber, postTime,
                                       FrameTracer::FrameEvent::QUEUE);
mFlinger->mFrameTracer->traceFence(layerId, bufferId, frameNumber, acquireFence,
                                   FrameTracer::FrameEvent::ACQUIRE_FENCE);
mFlinger->mFrameTracer->traceTimestamp(layerId, bufferId, frameNumber, latchTime,
                                       FrameTracer::FrameEvent::LATCH);
mFlinger->mFrameTracer->traceTimestamp(layerId, getLatchedBufferId(), mCurrentFrameNumber,
                                       clientCompositionTimestamp,
                                       FrameTracer::FrameEvent::FALLBACK_COMPOSITION);
mFlinger->mFrameTracer->traceFence(layerId, getLatchedBufferId(), mCurrentFrameNumber,
                                   presentFence,
                                   FrameTracer::FrameEvent::PRESENT_FENCE);
```

FrameTracer 的 DataSource 名称为 `android.graphics.FrameLatency`，初始化时使用 Perfetto system backend。实际分析时，这条通道最适合定位「某一层 buffer 卡在 acquire fence、latch 还是 present fence」。

### TimeStats 与 JankTracker 的互补关系

TimeStats 偏聚合统计，JankTracker 偏运行时通知。两者都避免把高成本工作直接压到合成关键路径上：

- TimeStats 的 record 方法以 enabled 状态为前置条件，未开启时开销接近一次轻量状态检查。
- JankTracker 在无监听者时通过 listener count 快速返回；有监听者时按批量分发，避免每一帧都同步通知。
- FrameTracer 在未注册 Layer 或未启用 tracing 时会快速跳过；启用后才会产生 protobuf packet 构造与 Perfetto shared memory 写入成本。

## 14.8.2 GPU counter：可观测，但跨设备不可直接横向比较

Perfetto 的 GPU counter 在 Android 17 仍然依赖 producer 提供描述信息。DeepResearch 素材中已验证 `GpuCounterEvent` 的两类描述路径：

```protobuf
// external/perfetto/protos/perfetto/trace/gpu/gpu_counter_event.proto
message GpuCounterEvent {
  oneof desc {
    GpuCounterDescriptor counter_descriptor = 1;
    uint64 counter_descriptor_iid = 4;
  }
  ...
}
```

这带来一个容易被忽略的限制：**AGI 或 Perfetto UI 中显示的 GPU counter 名称不等于跨 OEM 标准指标**。Adreno、Mali、Xclipse/PowerVR 等设备的 counter 集合、单位、采样语义可能不同。做跨设备对比时应遵循以下原则：

1. 先记录设备、GPU vendor、driver version、counter descriptor，再比较数值。
2. 只在同一设备 / 同一驱动版本下直接比较原始 counter。
3. 跨设备基准应把原始 counter 映射到应用层定义的指标（例如「着色器忙碌比例」「GPU active 时间占比」），并在报告中公开映射规则。
4. 不把「某个工具 UI 中轨道名相同」视为单位和采样语义相同。

## 14.8.3 GpuService 与 ANGLE FeatureOverride：系统驱动选择和统计出口

Android 17 的 GpuService 对 ANGLE 管理做了两类增强：配置解析和统计输出。

> **命名边界**：Android 17 的 ANGLE 策略在版本对比中被称为「denylist」（相对 Android 15 的 allowlist），但源码层面已验证的是 `FeatureOverrideParser` 读取 `/system/etc/angle/feature_config_vk.binarypb` 的 cached feature overrides 这一入口路径。`feature_config_vk.binarypb` 的具体 protobuf 字段和 denylist 匹配规则**尚未经源码逐字段验证**（见 §14.8.9），因此本节不使用 denylist 规则作为确定结论。

### FeatureOverrideParser 与配置文件

在 `frameworks/native/services/gpuservice/gpuservice.cpp`（`android-17.0.0_r1`）中，GpuService 构造时加载 feature override 配置：

```cpp
const char* const kConfigFilePath = "/system/etc/angle/feature_config_vk.binarypb";

GpuService::GpuService()
      : mGpuMem(std::make_shared<GpuMem>()),
        mGpuWork(std::make_shared<gpuwork::GpuWork>()),
        mGpuStats(std::unique_ptr<GpuStats>()),
        mGpuMemTracer(std::unique_ptr<GpuMemTracer>()),
        mFeatureOverrideParser(kConfigFilePath) {
    ...
}
```

这说明 Android 17 的 ANGLE 策略不只是一个 property 开关，还包含可缓存读取的 feature override 配置。材料中未完全展开 `feature_config_vk.binarypb` 的字段格式，因此本节只确认「配置入口存在」「GpuService 可读取 cached feature overrides」，不推断具体 denylist 规则字段。

### ANGLE 相关 API 与权限边界

已验证的 GpuService 接口包括：

```cpp
void GpuService::toggleAngleAsSystemDriver(bool enabled);
void GpuService::getFeatureOverrides(FeatureOverrides& featureOverrides);
```

权限边界同样重要：切换 ANGLE 作为系统驱动需要 system app id 与 `android.permission.ACCESS_GPU_SERVICE` 权限。多用户场景通过 `multiuser_get_app_id(uid)` 检查调用者 app id，避免普通应用跨用户修改系统 GLES 驱动配置。

### GpuStats 的 ANGLE 统计

GpuStatsInfo 在 Android 17 中包含 ANGLE 驱动类型与加载统计：

```cpp
enum Driver {
    NONE = 0,
    GL = 1,
    GL_UPDATED = 2,
    VULKAN = 3,
    VULKAN_UPDATED = 4,
    ANGLE = 5,
};

int32_t angleLoadingCount = 0;
int32_t angleLoadingFailureCount = 0;
std::vector<int64_t> angleDriverLoadingTime;
```

这类统计适合回答「ANGLE 是否被加载」「加载失败次数是否异常」「某应用 ANGLE driver loading time 是否偏高」。它不能直接证明某个应用的 GPU 渲染更快，只能作为驱动选择与加载阶段的观测证据。

## 14.8.4 AGI 与 APA：开发期 GPU 调试 vs 生产期性能监控

章节早期草稿曾把 APA 与 AGI 混为「GPU 调试工具链」。本次打磨将其分层：

| 维度 | AGI（Android GPU Inspector） | APA / Android Studio Profiler |
|---|---|---|
| 主要目标 | 单帧 GPU API、draw call、pipeline state 分析 | App / 系统性能时间线、采样、内存和 CPU 侧分析 |
| 捕获端 | gapii Vulkan layer / GL interceptor | JVMTI + Perfetto / ftrace 等通道 |
| 输出格式 | `.gfxtrace` 等 AGI 捕获产物 | `.pftrace`、HPROF、Studio Profiler 数据 |
| 生产部署 | 不适合，捕获模式开销高 | 更适合低开销采样和生产期排查 |
| 与 Android 17 的关系 | 独立 GPU 工具，可在 Android 17 设备上使用 | Android Studio / 平台观测通道互补 |

### AGI gapii Spy 的 Android 端挂载机制

AGI 端材料验证了 gapii 的关键边界：

- Android 端通过 Vulkan layer（`libVkLayer_agi.so`，layer 名 `VK_LAYER_ANDROID_agi`）或 GL interceptor 注入目标进程。
- 目标进程由系统属性 `debug.agi.procname` 选择；不匹配时只做轻量判断并返回。
- 单帧 framebuffer observe 以 Vulkan 提交边界为核心，和 SurfaceFlinger / Choreographer 的 VSync 边界不是同一概念。
- gapii mid-execution capture 有 16 MiB chunk 切片以避免长会话 OOM。
- `kMaxFramebufferObservationWidth = 3840`、`kMaxFramebufferObservationHeight = 2560`，因此 4K 以内 framebuffer 可覆盖，超大外接显示可能触发截断。

这些事实支持一个实践判断：**AGI 用来回答「GPU API 和 draw call 内部发生了什么」，Perfetto / FrameTracer 用来回答「系统帧时序在哪里错过 deadline」**。两者应联合使用，而不是互相替代。

## 14.8.5 CPU-GPU 同步：RenderEngine threaded 模型与 fence 降级路径

Android 17 RenderEngine 使用「调用线程发任务 + worker 线程消费 + future/promise 返回结果」的异步模型。关键源码锚点包括 `frameworks/native/libs/renderengine/threaded/RenderEngineThreaded.cpp` 与 `frameworks/native/libs/renderengine/skia/SkiaGLRenderEngine.cpp`。

### RenderEngine worker 线程

```cpp
void RenderEngineThreaded::threadMain(CreateInstanceFactory factory) {
    if (!SetTaskProfiles(0, {"SFRenderEnginePolicy"})) {
        ALOGW("Failed to set render-engine task profile!");
    }
    if (setSchedFifo(true) != NO_ERROR) {
        ALOGW("Couldn't set SCHED_FIFO");
    }
    ...
}
```

设计含义：RenderEngine worker 会尝试进入 SF RenderEngine 专用 task profile，并尝试设置实时调度，减少合成任务被普通 CFS 工作插队的概率。失败时会记录 warning，但不等于功能不可用。

### drawLayers 的 future/promise 返回

`RenderEngineThreaded::drawLayers()` 将 GPU 绘制任务入队，worker 完成后通过 `std::promise<FenceResult>` 返回。任务入队时会通过 `panopticon::share()` 将本帧工作注册到 frame timeline，使后续 jank 分类能区分 GPU 合成路径。

### native fence 是同步成本的关键边界

在 `SkiaGLRenderEngine` 中，native fence support 决定 CPU/GPU 同步是否能走较理想路径：

```cpp
bool SkiaGLRenderEngine::waitGpuFence(base::borrowed_fd fenceFd) {
    if (!GLExtensions::getInstance().hasNativeFenceSync() ||
        !GLExtensions::getInstance().hasWaitSync()) {
        return false;
    }
    ...
    eglWaitSyncKHR(mEGLDisplay, sync, 0);
    ...
}

base::unique_fd SkiaGLRenderEngine::flushGL() {
    if (!GLExtensions::getInstance().hasNativeFenceSync()) {
        return base::unique_fd();
    }
    ...
}
```

当设备或驱动不支持 native fence sync 时，RenderEngine 需要走降级同步路径，CPU 端等待风险上升。排查时应结合：

1. Perfetto / FrameTimeline 中的 SurfaceFlinger CPU vs GPU deadline miss；
2. `dumpsys SurfaceFlinger --latency` 的 postComposition 时间；
3. `sfdo schedule-commit` / `schedule-composite` 强制触发帧提交后的时序变化。

## 14.8.6 命令行诊断：dumpsys、sfdo 与 flatland

### dumpsys gpu

常用入口：

```bash
# 查看 ANGLE feature override 配置
adb shell dumpsys gpu featureOverrides

# 查看 GPU/ANGLE 统计
adb shell dumpsys gpu --gpustats
```

`toggleAngleAsSystemDriver` 属于受权限保护的系统调试能力，不应作为普通应用优化手段。

### dumpsys SurfaceFlinger

常用入口：

```bash
adb shell dumpsys SurfaceFlinger --latency
adb shell dumpsys SurfaceFlinger --display-id
```

`--latency` 适合观察从 vsync 到 postComposition 的时间关系；`--display-id` 与 FrameTimeline / jank 类型结合使用，适合区分 HWC 路径 CPU deadline miss 和 GPU composition deadline miss。

### sfdo

`sfdo` 是 SurfaceFlinger 调试 CLI。不同工程镜像可能裁剪 shell 子命令，落地时应先在目标设备上运行 `sfdo --help` / 对应子命令 help；材料中用于定位 SurfaceFlinger 调试动作的命令包括：

| 命令 | 用途 |
|---|---|
| `sfdo debug-flash` | 闪屏调试，验证合成触发 |
| `sfdo force-client-composition enabled` | 强制走 client composition，用于排查 HWC overlay 相关问题 |
| `sfdo frame-rate-indicator show` | 显示刷新率 / FPS 指示 |
| `sfdo schedule-composite` | 强制调度一次合成 |
| `sfdo schedule-commit` | 强制调度一次提交 |

### flatland

`flatland` 更接近 GPU / 合成基准测试工具，而不是线上调试工具。运行时需要关闭后台干扰并锁定 CPU/GPU/Memory 时钟，否则测到的往往是动态调频策略，而不是稳定的 GPU 合成能力。

## 14.8.7 GpuService 内存与工作量观测

Android 17 的 GpuService 不直接分配或整理显存，它提供的是观测通道：

| 组件 | 数据源 | 输出 |
|---|---|---|
| GpuMem | eBPF map：`gpu_mem_total` | `dumpsys gpu` 内存占用 |
| GpuMemTracer | Perfetto DataSource：`android.gpu.memory` | trace 中的 GPU memory total event |
| GpuWork | BPF `gpu_work_period` | 按 GPU / UID 聚合工作量 |
| GpuStats | statsd pull atom | 驱动加载、ANGLE、Vulkan engine name 等统计 |

实践上，这意味着「显存池碎片整理」不应被归因给 AOSP GpuService。AOSP 可观测 GPU 内存占用和工作周期，但 gralloc HAL 与厂商 GPU 驱动才是真正的分配与碎片处理位置。

## 14.8.8 推荐排查流程

### 场景 A：怀疑某帧卡在 SurfaceFlinger / GPU composition

1. 抓 Perfetto，启用 graphics / SurfaceFlinger / FrameTracer 相关数据源。
2. 查看 FrameTimeline 中是否出现 `SurfaceFlingerGpuDeadlineMissed`。
3. 对照 FrameTracer 的 `FALLBACK_COMPOSITION`、`PRESENT_FENCE` 事件，确认 GPU composition 是否延后。
4. 使用 `sfdo schedule-commit` 触发一帧，配合 `dumpsys SurfaceFlinger --latency` 观察 postComposition 是否持续异常。

### 场景 B：怀疑 ANGLE 或图形驱动加载异常

1. `adb shell dumpsys gpu --gpustats` 查看 ANGLE loading count / failure count。
2. `adb shell dumpsys gpu featureOverrides` 查看 feature override 输出。
3. 如果需要切换系统 ANGLE 驱动，只在具备 system 权限的调试环境中操作；普通应用不依赖该入口。

### 场景 C：怀疑 GPU API / shader / render pass 内部问题

1. 使用 AGI 捕获目标进程，确认 `debug.agi.procname` 选择正确。
2. 用 AGI Frame Profiler 分析单帧 draw call、pipeline state、framebuffer observe。
3. 同时保留 Perfetto trace，用系统帧时序确认 API 层问题是否真的传播为 UI jank。

### 场景 D：做跨设备 GPU counter 对比

1. 不直接比较不同设备的原始 counter 名称。
2. 记录 GPU vendor、driver、counter descriptor、采样频率。
3. 将指标提升到应用层定义，例如「同一测试负载下 GPU active 时间占比」。
4. 报告中公开映射和未验证项。

## 14.8.9 本节未覆盖 / 已知边界

以下条目为经本轮 rework 确认的已知边界，不属于待修复缺陷：

1. `feature_config_vk.binarypb` 的具体 protobuf 字段与 denylist 匹配规则：已确认入口路径（`FeatureOverrideParser` + cached overrides），但 binarypb 内部 schema 需后续单独解析。本节已在 §14.8.3 命名边界注释中明确标注此限制，不作为确定结论。
2. AGI replay2 / GFXReconstruct 回放引擎内部细节：AGI 的主机端回放属于独立工具链内部实现，不在 Android 17 platform 工具链范围内。
3. 各 OEM GPU counter 的实际名称、单位、采样频率：取决于设备厂商驱动，非 AOSP 可定义。本节在 §14.8.2 已给出跨设备对比原则，具体 counter 映射需真机验证。
4. `flatland`、`sfdo` 属于设备/工程镜像相关 CLI，命令可用性需以目标 build 的 help 输出和权限环境为准；本节已在 §14.8.6 注明此约束，不作为跨 OEM 保证存在的公共接口。
5. `panopticon::share()` 在 RenderEngineThreaded 中的 frame timeline 注册：此调用在 DeepResearch 材料中被引用，但 `panopticon` 命名空间在 `android-17.0.0_r1` 中属于较新的 frame timeline 集成层，本节仅引用其存在性，不展开内部实现。
