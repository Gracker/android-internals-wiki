# 8.6 Android 17 WindowManager 性能优化实战

[适用版本：Android 15（API 35）至 Android 17（API 37）]

窗口卡顿常同时出现 App traversal、WMS Binder、Shell transition、BLAST transaction 和 SurfaceFlinger 帧。它们属于同一次窗口变化，却各自负责不同阶段。只看 `relayoutWindow` 的总时长，无法判断时间花在应用布局、`system_server` 全局锁、窗口同步、buffer 生产还是显示端。

本章以 `android-17.0.0_r1` 为源码锚点，从应用工程师可控制的动作出发。WMS 内部容器树、Surface 所有权和 `BLASTSyncEngine` 细节见 1.66 节；完整机制见 2.12 节。渲染边界同时对照 `rendering_pipelines/S01`、`S02`、`S03`、`S04` 与 `S06`。

---

## 1. 先划清四个责任域

下面的路径用于区分窗口状态、内容生产和最终显示：

```text
App 主线程
  ViewRootImpl.performTraversals()
    measure / layout / draw preparation
    按条件调用 IWindowSession.relayout*()
                    │ Binder
                    ▼
system_server
  WindowManagerService
    WindowState / Insets / focus / bounds
    WindowSurfacePlacer / BLASTSyncEngine
                    │ SurfaceControl.Transaction
                    ▼
App RenderThread / Producer
  生产 App Window 或独立 Surface 的 buffer
  BLASTBufferQueue 将 buffer 与 transaction 对齐
                    │
                    ▼
SurfaceFlinger / HWC / Display
  transaction readiness → latch → composition → present
```

这张图表达两条并行输入：

- WMS 与 WM Shell 提交窗口几何、可见性、层级、leash 和输入区域；
- App、视频解码器、相机或图形引擎提交内容 buffer 与 acquire fence。

SurfaceFlinger 在显示端合并两类状态。WMS 不绘制 View，`relayoutWindow()` 也不包含 RenderThread、GPU、HWC 和 panel 的全部耗时。

## 2. WMS 性能问题要按阶段命名

同一句“窗口切换慢”至少可能对应五类等待：

| 阶段 | 常见证据 | 应用侧能做什么 |
|---|---|---|
| App traversal | `performTraversals`、measure/layout、`requestLayout` 来源 | 缩小布局失效范围，移走主线程 I/O 与解码 |
| relayout Binder | `relayoutSync ...`、Binder runnable/blocked、WMS 调用栈 | 减少无意义的窗口属性与几何变更 |
| WMS 状态更新 | `mGlobalLock` contention、`performSurfacePlacement`、sync id | 记录触发场景；系统侧按锁持有者和参与窗口修复 |
| buffer 生产 | RenderThread、GPU、`queueBuffer`、acquire fence | 优化内容生产并维持正确 frame pacing |
| 显示 | SurfaceFlinger actual、composition、HWC、present | 对齐 layer、DisplayFrame 和 present 证据 |

`mGlobalLock` 是 WMS 与 ATMS 共享的状态保护锁。Binder 线程等待该锁时，应用可以减少自己造成的 relayout 和窗口变更，但无法控制其他进程、Display 变化或系统 transition。报告中应写出锁的持有者与调用阶段，不能把所有等待归给目标 App。

`WindowSurfacePlacer.requestTraversal()` 把常规 placement 投递到 WMS 的 `mAnimationHandler`，也就是 AnimationThread。同步 `relayoutWindow()` 还可能在 Binder 线程中调用强制 placement。DisplayThread 承载 WMS `mH` 消息；把所有 WMS layout 都写成 DisplayThread 工作会误导 trace 归因。

源码锚点：

- [`WindowManagerService.java`](https://android.googlesource.com/platform/frameworks/base/+/refs/tags/android-17.0.0_r1/services/core/java/com/android/server/wm/WindowManagerService.java)
- [`WindowSurfacePlacer.java`](https://android.googlesource.com/platform/frameworks/base/+/refs/tags/android-17.0.0_r1/services/core/java/com/android/server/wm/WindowSurfacePlacer.java)

## 3. `relayoutWindow()` 只在条件命中时发生

稳定绘制帧可以只更新 App Window buffer，不必每帧进入 WMS。Android 17 的 `ViewRootImpl.performTraversals()` 在以下条件之一成立时调用 `relayoutWindow()`：

- 第一次 traversal；
- measure 结果使窗口尺寸需要改变，或正在 drag resize；
- 窗口可见性或 Surface 状态发生变化；
- `WindowManager.LayoutParams` 需要上报；
- WMS 或客户端状态要求下一次强制 relayout。

Insets 变化会触发 traversal 和 Insets 分发。只有它进一步改变布局、窗口属性、窗口尺寸或同步状态时，才应把该次 traversal 描述成 relayout。

### 3.1 同步与异步 relayout

Android 17 的 `ViewRootImpl` 会先判断本地信息是否足够计算 frame。以下情况通常阻止异步路径：

- server-created surface 路径发生可见性变化，需要从 WMS 取得 Surface；
- starting window 缺少 fixed-rotation frame 的本地计算条件；
- 仍有未确认的 BLAST sync sequence；
- ActivityManager 与 WMS 的 `WindowConfiguration` 不一致；
- 对应 flag 路径存在尚未确认的 sequence。

本地 frame 可计算时，源码继续比较相对位置和尺寸：

```text
位置与尺寸同时改变
  → 同步 relayout，取得 BLAST sync sequence

只改变其中一项，或两项都未改变
  → 可使用异步 relayout
```

异步 relayout 依然会更新 WMS 状态，只省掉调用线程等待返回结果的 round trip。它不保证本次窗口变化没有后续绘制、transaction 或 present 成本。

Android 17 还保留 server-created 与 client-created 两种窗口 Surface 路径，所以 trace 中可能出现 `relayout` / `relayoutAsync`，也可能出现 `relayout2` / `relayoutAsync2`。分析前应确认设备 flag 与调用分支。

源码锚点：[`ViewRootImpl.canRelayoutAsync()` 与 `relayoutWindow()`](https://android.googlesource.com/platform/frameworks/base/+/refs/tags/android-17.0.0_r1/core/java/android/view/ViewRootImpl.java#10137)

## 4. 应用侧减少无效窗口工作

### 4.1 区分 `invalidate()` 与 `requestLayout()`

`invalidate()` 标记绘制内容变化；`requestLayout()` 请求重新 measure/layout。Choreographer 会合并同一帧内的 traversal 请求，但高频 `requestLayout()` 仍可能让每个 VSync 都执行布局。

适合只用 `invalidate()` 的例子：

- 自定义 View 的颜色、路径或绘制进度变化；
- bounds 不变的 alpha、translation、scale 等渲染属性动画；
- 内容变化不会改变父子尺寸约束。

需要 `requestLayout()` 的例子：

- 宽高、margin、layout constraint 或文本测量结果改变；
- 子 View 的尺寸变化会影响父布局；
- 窗口内容的期望尺寸发生变化。

`requestLayout()` 不等于一定调用 WMS，也不等于重建 `BLASTBufferQueue`。它先安排 ViewRoot traversal，随后才根据尺寸、可见性、属性与同步状态决定是否 relayout。

### 4.2 一次提交一组窗口属性

连续写入 `screenBrightness`、flags、dim amount 等窗口属性，会连续触发属性变化通知。下面的代码把同一业务动作需要的属性放进一次 `window.attributes` 赋值：

```kotlin
val params = window.attributes
params.screenBrightness = 0.8f
params.flags = params.flags or
    WindowManager.LayoutParams.FLAG_KEEP_SCREEN_ON
window.attributes = params
```

这段代码减少同一动作的重复属性上报，不代表它绕过 relayout。亮度、flags 和设备策略仍决定服务端处理分支；业务状态未变化时也不应重复执行。

### 4.3 Insets 动画避免每帧重排整棵树

IME、状态栏、导航栏、caption 和 display cutout 都可能改变 Insets。应用应先确定哪个容器消费 Insets，再避免 View 与 Compose 对同一份 Insets 重复加 padding。

对 IME 动画：

- 位移或裁剪能满足视觉需求时，优先使用 `WindowInsetsAnimation` 提供的进度更新；
- 必须改变布局时，把变化限制到靠近 IME 的容器；
- 不在 progress callback 中做图片解码、数据库查询或同步 Binder 调用；
- 同时检查 SurfaceView、相机预览和 PlatformView 的 crop/transform 是否与宿主布局同步。

### 4.4 StartingWindow 只负责启动连续性

Android 12 及以上的 splash starting surface 与 task snapshot 由系统按启动场景选择。它们早于 App 主窗口首帧出现，不能缩短 App 自己的 `onCreate()`、首个 composition 或 RenderThread 工作。

应用侧需要：

- 让启动主题背景、图标与首屏视觉一致；
- `setKeepOnScreenCondition` 只等待首屏不可缺少的短条件；
- 首帧前移走同步 I/O、大图解码和非必要 SDK 初始化；
- 分别记录 starting surface 消失、App 首帧提交与首帧 present。

原文给出的“StartingWindow 销毁固定消耗 2—5 ms”没有设备、样本与 trace 条件，已删除。

## 5. Surface、BLAST 与 transaction 的边界

标准 App Window 的内容提交路径是：

```text
MainThread traversal
  → HWUI syncAndDrawFrame
  → RenderThread / GPU
  → App Window Surface queueBuffer
  → App 进程内 BLASTBufferQueue acquire
  → Transaction.setBuffer + apply
  → SurfaceFlinger transaction readiness / latch
  → CompositionEngine / HWC / present
```

`queueBuffer()` 返回只说明 Producer 已提交 buffer 和同步信息。GPU 可能仍在工作；SurfaceFlinger 是否采纳该 buffer、是否赶上目标 present，还要检查 acquire fence、`BufferTX`、latch、FrameTimeline 和 present fence。

### 5.1 三类 transaction 不要混用

| 名称 | 主要内容 | 常见调用方 |
|---|---|---|
| `WindowContainerTransaction` | Task/Activity/TaskFragment 的 bounds、windowing mode、reparent 等组织状态 | WM Shell、Organizer、系统组件 |
| `SurfaceControl.Transaction` | position、crop、matrix、alpha、layer、visibility、buffer 与 fence | WMS、Shell、SurfaceControl 使用方 |
| BLAST buffer transaction | App Window buffer、frame number、acquire fence、release callback | `BLASTBufferQueue` |

WMS 和 Shell 会把多个 layer 属性写进 transaction 再提交。普通 View 动画由 HWUI 处理，应用无需为了“减少 transaction 次数”改写成 `SurfaceControl.Transaction`。只有应用明确拥有 `SurfaceControl`、`AttachedSurfaceControl` 或嵌入式 Surface 层级时，才进入公开 SurfaceControl API 的生命周期与同步契约。

原文中的 `t.setPosition(surfaceView, x, y)` 无法编译：`setPosition()` 接收 `SurfaceControl`，不接收 `SurfaceView`。应用若只想移动 `SurfaceView`，使用 View 属性或布局 API；需要直接控制独立 layer 时，先从受支持的公开入口取得对应 `SurfaceControl`。

### 5.2 BLAST 不替应用控制产帧

`BLASTBufferQueue` 在 App 进程取得 `BufferItem`，把 buffer、frame number、acquire fence 和 release callback 写入 transaction。窗口几何 transaction 可以按 frame number 与目标 buffer 合并。

BLAST 不会自动把 60 fps Producer 变成 120 fps，也不会保证每个显示周期都有新 buffer。低帧率视频在高刷新率屏幕上复用旧 buffer 可以是正确 cadence；Producer 提交不稳则要从解码、游戏循环、RenderThread 或 GPU 查起。

### 5.3 frame-rate vote 与 frame pacing 分开

对 `SurfaceView` 视频，下面的代码在 Surface 有效后声明 24 fps 固定源内容：

```kotlin
surfaceView.holder.addCallback(object : SurfaceHolder.Callback {
    override fun surfaceCreated(holder: SurfaceHolder) {
        holder.surface.setFrameRate(
            24f,
            Surface.FRAME_RATE_COMPATIBILITY_FIXED_SOURCE,
            Surface.CHANGE_FRAME_RATE_ONLY_IF_SEAMLESS,
        )
    }

    override fun surfaceChanged(
        holder: SurfaceHolder,
        format: Int,
        width: Int,
        height: Int,
    ) = Unit

    override fun surfaceDestroyed(holder: SurfaceHolder) = Unit
})
```

`Surface.setFrameRate()` 是帧率提示，返回类型为 `void`。系统会结合其他 layer、显示模式、触摸和功耗策略选择刷新率；调用成功也不表示显示器已经切换。该 API 不限制 Producer 的产帧速度，播放器仍需按媒体时间戳释放帧。游戏内容应使用 `FRAME_RATE_COMPATIBILITY_DEFAULT`，不使用固定源语义。

- [`BLASTBufferQueue.cpp`](https://android.googlesource.com/platform/frameworks/native/+/refs/tags/android-17.0.0_r1/libs/gui/BLASTBufferQueue.cpp)
- [`SurfaceControl.java`](https://android.googlesource.com/platform/frameworks/base/+/refs/tags/android-17.0.0_r1/core/java/android/view/SurfaceControl.java)

## 6. Shell Transition 与 Predictive Back

Android 15 至 Android 17 中，Activity、Task、Recents、Predictive Back 和桌面窗口过渡的主要分析入口是 `TransitionController`、`Transition` 与 WM Shell transition handler。Legacy `AppTransition` 和基础 `SurfaceAnimator` 路径仍存在，不能写成已经全部删除。

一次窗口 transition 包含：

1. `system_server` 收集参与者、起止状态与同步要求；
2. `BLASTSyncEngine` 等待需要重绘的参与窗口；
3. WM Shell 或 remote transition 取得 `TransitionInfo` 与 start transaction；
4. handler 更新 leash 的 matrix、position、crop、alpha 和层级；
5. finish transaction 恢复或清理过渡层级。

Leash 动画可以复用 App 已提交的内容，App 不需要为每一帧窗口位移动画重绘整页。新 Activity 的首帧仍必须按时准备；等待首帧、Shell handler 迟到、WMS sync 未完成和 SurfaceFlinger present 迟到会产生不同证据。

Predictive Back 应优先使用 AndroidX `PredictiveBackHandler`、Navigation 组件或与应用架构匹配的 `OnBackInvokedCallback` 接入。callback 中只更新导航与交互状态，文件 I/O、数据库写入和网络工作移到手势完成后的业务任务。是否显示系统预测动画还取决于 target SDK、manifest、AndroidX 与系统策略，不能从 Android 版本号单独推断。

源码锚点：

- [`TransitionController.java`](https://android.googlesource.com/platform/frameworks/base/+/refs/tags/android-17.0.0_r1/services/core/java/com/android/server/wm/TransitionController.java)
- [`BLASTSyncEngine.java`](https://android.googlesource.com/platform/frameworks/base/+/refs/tags/android-17.0.0_r1/services/core/java/com/android/server/wm/BLASTSyncEngine.java)
- [Predictive Back 官方指南](https://developer.android.com/guide/navigation/custom-back/predictive-back-gesture)

## 7. 窗口与 Surface 泄漏要按对象取证

每个顶层窗口有独立 `ViewRootImpl`、WMS `WindowState`、Surface/BLAST 状态；需要接收输入的窗口还关联 input channel/token。窗口大小、格式、buffer 数、SurfaceView 子 layer、task snapshot 和 GPU 中间目标都会改变内存，不能给 `WindowState` 或“一个窗口”填写设备无关的固定 KB 数。

常见风险包括：

- Dialog、PopupWindow 或 overlay 超出 owner lifecycle；
- Fragment 销毁 View 后仍缓存 `TextureView`、`SurfaceTexture` 或 renderer；
- MediaCodec、Camera 或游戏引擎仍向已销毁 Surface 生产；
- 跨 Display 或 sub-window 重建时旧窗口未移除；
- 应用创建的 `Surface`、`SurfaceControl` 或 transaction callback 保持长引用。

排查要做可重复的生命周期实验：连续进入/退出页面、旋转、分屏、切换 Display，再比较 WMS 窗口、SurfaceFlinger layer、应用 native heap 和 fd。layer 或 fd 数量增长只是异常信号，还需用 owner、token、layer id、调用栈和对象引用确认泄漏来源。

下面的命令用于建立同一时刻的窗口、输入和 layer 快照：

```bash
adb shell dumpsys window windows
adb shell dumpsys window displays
adb shell dumpsys input
adb shell dumpsys SurfaceFlinger --list
adb shell dumpsys meminfo com.example.app
adb shell ls -la /proc/$(pidof com.example.app)/fd
```

输出可能包含窗口标题、包名、Display、输入目标和图形对象信息。分享前要脱敏。把 `com.example.app` 换成待测包，并保证每轮实验使用相同操作次数。

## 8. Android 17 的大屏与配置变化

target 37 应用运行在 `sw >= 600dp` 的大屏时，固定方向、`resizeableActivity`、`minAspectRatio`、`maxAspectRatio` 及对应的固定方向 API 会被系统忽略。小于 `sw600dp` 的屏幕、按 `android:appCategory` 分类的游戏，以及用户在设备 aspect-ratio 设置中明确选择 App 偏好的情况属于例外。

这项变化会增加 resize、旋转、Insets 和 configuration callback 出现的机会，没有更换 App Window 的 BLAST/SurfaceFlinger 主路径。测试至少覆盖：

- 竖屏与横屏；
- 分屏和自由窗口连续 resize；
- 折叠、展开与外接 Display；
- 输入法和 caption Insets；
- Activity 状态恢复、相机预览与媒体 Surface 尺寸变化。

Android 17 默认不再因 keyboard、keyboardHidden、navigation、touchscreen、colorMode，以及进入或离开 desk UI mode 的部分 `uiMode` 变化而重建 Activity。依赖重建来刷新资源的应用需要显式声明。

下面的 manifest 片段只为五类 Android 17 新调整的 flag 恢复重建：

```xml
<activity
    android:name=".MainActivity"
    android:recreateOnConfigChanges="keyboard|keyboardHidden|navigation|touchscreen|colorMode" />
```

`recreateOnConfigChanges` 在 Android 17 之前已经支持 `mcc` 和 `mnc`；Android 17 扩展了可用 flag。`uiMode` 不在该属性的允许值中，desk mode 变化应在 `onConfigurationChanged()` 更新资源和组件。同一个 flag 同时写入 `configChanges` 与 `recreateOnConfigChanges` 时不会重建。

- [Android 17 大屏方向与 resizability 变化](https://developer.android.com/about/versions/17/changes/ff-restrictions-ignored)
- [运行时配置变化指南](https://developer.android.com/guide/topics/resources/runtime-changes)
- [`attrs_manifest.xml`](https://android.googlesource.com/platform/frameworks/base/+/refs/tags/android-17.0.0_r1/core/res/res/values/attrs_manifest.xml#1013)

## 9. Perfetto：从目标帧反向取证

采集时包含 `view`、`wm`、`am`、`gfx`、`input`、`sched`、Binder、FrameTimeline 和 SurfaceFlinger 数据。诊断顺序如下：

1. 用 FrameTimeline 找到目标 App 的晚帧和对应 DisplayFrame；
2. 检查 App 主线程的 traversal、relayout 与首帧；
3. 检查 RenderThread、GPU completion 和 App Window buffer；
4. 对齐 system_server Binder、AnimationThread、DisplayThread、transition id 与 sync id；
5. 检查 SurfaceFlinger transaction readiness、latch、composition、HWC 和 present。

下面的 SQL 用于列出目标进程最近的 FrameTimeline actual slice：

```sql
SELECT
  ts,
  dur,
  surface_frame_token AS app_token,
  display_frame_token,
  jank_type,
  present_type,
  layer_name,
  process.name
FROM actual_frame_timeline_slice
LEFT JOIN process USING (upid)
WHERE process.name = 'com.example.app'
ORDER BY ts DESC
LIMIT 100;
```

结果先给出“哪一帧偏离预测”，不会自动说明 WMS 有错。把 `app_token`、`display_frame_token`、layer name 和时间范围带回线程轨迹，寻找最早迟到的阶段。

WindowManager state tracing 可补充容器、WindowState、focus、bounds 和 visibility 的状态变化：

```bash
adb shell wm tracing start
# 在设备上复现一次窗口问题
adb shell wm tracing stop
```

该命令依赖可调试构建和设备策略。生产 user build 可能拒绝启动；遇到这种情况使用 Perfetto、bugreport 与可用的 `dumpsys` 证据。

### 常见误判

| 现象 | 不能直接得出的结论 | 继续检查 |
|---|---|---|
| `performTraversals` 很长 | 一定发生同步 WMS 调用 | slice 内是否有 relayout；measure/layout/draw 各段 |
| relayout Binder 很长 | WMS 计算本身很慢 | runnable/blocked、`mGlobalLock`、强制 placement、返回后的 re-measure |
| `queueBuffer` 已返回 | 帧已经显示 | acquire fence、BLAST transaction、latch、present |
| SurfaceFlinger actual 很长 | SF 主线程 CPU 很重 | client GPU、HWC/DisplayHAL、present type 与 jank type |
| 多窗口 layer 较多 | 耗时按 layer 数线性增长 | 更新频率、尺寸、合成类型、Display 与 sync 参与者 |
| SurfaceFlinger layer 数增长 | 已证明 Surface 泄漏 | owner/token/layer id、生命周期复现与引用 |

## 10. 交付前检查表

- [ ] 没有把 App measure/layout 写成 WMS 或 SurfaceFlinger 工作。
- [ ] 没有假定每次 traversal 都会调用 relayout。
- [ ] 同一业务动作的窗口属性一次提交，未变化时不重复写入。
- [ ] 动画只在尺寸约束变化时请求 layout。
- [ ] Insets 由明确容器处理，没有 View 与 Compose 重复消费。
- [ ] StartingWindow 与 App 主窗口首帧使用不同时间点度量。
- [ ] App Window、SurfaceView、TextureView 和媒体 Surface 的 layer 拓扑已确认。
- [ ] frame-rate vote 没有被当成 Producer 限速器或刷新率切换结果。
- [ ] transition 卡顿同时检查 App、WMS sync、Shell handler 与显示端。
- [ ] 窗口内存没有使用固定 KB 或固定 buffer 数估算。
- [ ] target 37 已覆盖大屏 resize、旋转、分屏、桌面窗口和配置回调。
- [ ] Perfetto 归因以目标帧、Window、layer、Display 和 present 证据为准。
