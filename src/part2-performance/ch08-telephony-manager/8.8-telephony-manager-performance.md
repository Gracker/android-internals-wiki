# 8.8 Android 17 TelephonyManager 性能优化实战

TelephonyManager 是应用访问蜂窝网络能力的入口：信号强度、网络注册状态、通话状态、SIM 信息、数据连接类型等全部经由此 API 暴露。与 ConnectivityService（§11.1、§12.5）关注的数据网络连通性不同，本章聚焦 **Telephony 架构本身的 IPC 开销、回调分发性能和 RIL 阻塞风险**——这些是导致主线程 ANR 和后台功耗泄漏的常见根源。

## 要点

### 🔹 Telephony 架构与 IPC 性能模型

Telephony 子系统的进程架构在 Android 17 中保持三层分离：

```
App Process
  └─ TelephonyManager (SDK API)
       └─ Binder IPC → com.android.phone (PhoneApp 进程)
            └─ RILJ (frameworks/opt/telephony)
                 └─ Socket → RILD (/vendor/bin/rild)
                      └─ Vendor RIL → Modem
```

关键 IPC 边界有三处：

1. **App → TelephonyRegistry**（system_server 进程）：`listen()` / `registerTelephonyCallback()` 注册的状态回调由 TelephonyRegistry 在 system_server 中分发。TelephonyRegistry 维护全部注册者的列表，每次信号变化都会遍历所有注册者并跨进程调用。

2. **App → PhoneApp 进程**：`getDeviceId()`、`getCellLocation()`、`getNetworkType()` 等查询类 API 通过 Binder 进入 PhoneApp 进程（`com.android.phone`），再经 RILJ 同步等待 RILD/Modem 响应。**这是关键的阻塞路径**——如果 Modem 响应延迟，调用方主线程会被阻塞。

3. **RILJ → RILD**：RILJ 与 RILD 之间通过 Unix Socket 通信，使用 RIL 协议序列化/反序列化。Android 17 的 RILJ 维护了请求队列和 token 机制，但单个 RIL 请求的超时默认值通常为 5-10 秒（取决于请求类型），超时后返回错误但**不会自动解除调用方的阻塞**。

[已验证: AOSP android-17.0.0_r1, frameworks/opt/telephony/src/java/com/android/internal/telephony/RIL.java — RIL 请求/响应架构]
[待验证: 具体超时值需确认 Android 17 是否有变更]

**性能影响量化**：

| 操作 | 典型延迟 | 阻塞风险 |
|------|----------|----------|
| `getNetworkType()` | 5-50ms（缓存命中）/ 100-500ms（RIL 查询） | 中 — 主线程调用可能 ANR |
| `getCellLocation()` | 200-2000ms | 高 — 强烈建议异步 |
| `listen()` 注册回调 | 5-20ms | 低 — 一次性开销 |
| 回调分发（每次信号变化） | 0.5-5ms/注册者 | 中 — 频繁变化时累积 |
| `getServiceState()` | 10-100ms | 中 |

> 详见 §9.10 ANR 预警回调与 §9.11 企业级 ANR 监控平台

### 🔹 PhoneStateListener / TelephonyCallback 回调性能

**API 演进**：Android 12（API 31）引入 `TelephonyCallback` 替代已废弃的 `PhoneStateListener`。Android 17 中两者并存，但 `PhoneStateListener` 内部已桥接到 `TelephonyCallback` 实现。

```kotlin
// Android 12+ 推荐写法
val telephonyCallback = object : TelephonyCallback(),
    TelephonyCallback.SignalStrengthsListener {
    override fun onSignalStrengthsChanged(signalStrength: SignalStrength) {
        // 处理信号强度变化
    }
}
tm.registerTelephonyCallback(
    mainExecutor,  // 指定回调线程
    telephonyCallback
)
```

**回调分发路径与性能陷阱**：

TelephonyRegistry 收到 Modem 上报的信号变化后，会遍历所有注册者并通过 Binder `onTransact` 分发回调。性能陷阱包括：

1. **注册者过多导致分发风暴**：每个信号变化事件（SignalStrength、ServiceState、CallState、DataConnectionState）都会触发全量注册者遍历。如果 App 注册了多个 listener 实例（例如每个 Activity 各注册一个），每次信号变化都会产生 N×M 次 Binder 调用。

2. **回调 Executor 选择不当**：`registerTelephonyCallback(executor, callback)` 的 Executor 决定回调在哪个线程执行。传入 `mainExecutor` 意味着回调排队进入主线程 MessageQueue。如果主线程繁忙（如正在渲染帧），回调会被延迟处理，导致信号信息滞后。对于非 UI 场景，应使用后台线程池。

3. **回调中执行重操作**：在 `onSignalStrengthsChanged` 中执行 JSON 解析、数据库写入等操作会阻塞 Binder 调用线程（对于 mainExecutor 即主线程），直接引发卡顿或 ANR。

**优化建议**：

```kotlin
// ❌ 错误：每个 Activity 各注册一份 listener
class ActivityA : AppCompatActivity() {
    private val listener = object : TelephonyCallback(), ... { ... }
    override fun onStart() {
        super.onStart()
        tm.registerTelephonyCallback(mainExecutor, listener)
    }
}

// ✅ 正确：Application 级单例注册，按 lifecycle 过滤事件
class AppTelephonyMonitor(private val context: Context) {
    private val callback = object : TelephonyCallback(),
        TelephonyCallback.SignalStrengthsListener { ... }

    init {
        val tm = context.getSystemService(TelephonyManager::class.java)
        tm.registerTelephonyCallback(
            backgroundExecutor,  // 非主线程
            callback
        )
    }
}
```

[已验证: AOSP android-17.0.0_r1, frameworks/base/services/core/java/com/android/server/TelephonyRegistry.java — 注册者列表管理与回调分发]

### 🔹 信号强度传播路径与更新节流

信号强度从 Modem 到应用的传播路径：

```
Modem → RILD → RILJ (RIL_UNSOL_SIGNAL_STRENGTH)
  → TelephonyRegistry.notifySignalStrength()
    → 遍历所有注册者 → Binder onTransact → App 回调
```

**TelephonyRegistry 的内置节流机制**：

TelephonyRegistry 对信号强度回调有内置的去重和节流逻辑——只有当信号等级（level）发生变化时才会通知注册者，单纯地 dBm 值小幅波动不会触发回调。但对于 `SignalStrength` 的完整对象（包含各制式 RSRP/RSRQ/SNR 等），如果注册者通过 `SignalStrengthsListener` 监听，每次 Modem 上报都会分发。

[待验证: Android 17 TelephonyRegistry 中 notifySignalStrength 是否有额外的时间窗口节流]

**性能优化建议**：

- 只在需要信号等级（Level 0-4）时使用 `SignalStrengthsListener`，避免在每次 dBm 微小变化时触发 UI 重绘
- 如需精确信号值（如网络诊断场景），将采样间隔控制在 ≥ 5 秒，避免高频调用 `getSignalStrength()`
- 使用 `TelephonyManager.getSignalStrength()` 主动拉取（pull）代替注册回调（push），适用于低频需求场景——但注意这是 IPC 调用，不可在主线程频繁调用

### 🔹 TelephonyManager 阻塞式 API 与 ANR 风险

TelephonyManager 中多个查询类 API 实质上是通过 Binder IPC 进入 PhoneApp 进程，再经 RILJ 同步等待 RILD/Modem 响应。这类调用有明确的 ANR 风险。

**高风险 API**（禁止主线程调用）：

| API | 阻塞原因 | 建议方式 |
|-----|---------|---------|
| `getCellLocation()` | 等待 Modem 定位 | `AsyncTask`/协程后台调用 |
| `getAllCellInfo()` | 触发 Modem 扫描，可能需数秒 | `requestCellInfoUpdate()` 异步回调 |
| `getNetworkSpecifier()` | 查询活动数据网络 | 后台线程 |
| `getDataNetworkType()` | RIL 查询当前数据网络类型 | 后台线程 |

**低风险 API**（可主线程调用，但有缓存依赖）：

| API | 缓存机制 | 注意事项 |
|-----|---------|---------|
| `getNetworkType()` | TelephonyRegistry 缓存 | 缓存值可能滞后数秒 |
| `getSimState()` | 直接读 SIM 状态文件 | 微秒级 |
| `getSimOperator()` | 从 SIM 读取并缓存 | 首次调用可能 10-50ms |
| `getServiceState()` | TelephonyRegistry 缓存 | 信号切换期间可能不一致 |

**Android 17 StrictMode 增强**：

Android 17 在 `StrictMode` 中强化了对主线程磁盘读写和网络请求的检测，但 TelephonyManager 的 IPC 调用本身不被 `StrictMode` 的 `detectNetwork()` 捕获（因为它不是 socket I/O，而是 Binder IPC）。这意味着 TelephonyManager 的主线程阻塞不会被标准 StrictMode 检测发现，需要自定义监控。

> 详见 §9.10 ANR 预警系统、§9.11 企业级 ANR 监控平台架构设计

### 🔹 Radio 状态机与功耗性能平衡

蜂窝 Radio 的功耗状态直接影响应用的网络请求延迟和设备续航：

```
                     ┌─────────────────────┐
                     │   HIGH_POWER (DCH)  │ ← 数据传输中
                     │   电流 ~200-400mA    │
                     └─────────┬───────────┘
                               │ inactivity timer (5-10s)
                               ▼
                     ┌─────────────────────┐
                     │  MEDIUM_POWER (FACH)│ ← 控制信道保持
                     │   电流 ~50-100mA    │
                     └─────────┬───────────┘
                               │ inactivity timer (10-30s)
                               ▼
                     ┌─────────────────────┐
                     │  LOW_POWER (IDLE)   │ ← 仅监听寻呼
                     │   电流 ~5-20mA      │
                     └─────────────────────┘
```

**应用层面的功耗优化策略**：

1. **批量网络请求**：将分散的网络请求聚合到同一时间窗口发送，减少 Radio 从 IDLE 到 HIGH 的切换次数。`JobScheduler` 和 `WorkManager` 已内置此能力——Android 17 的 JobScheduler 会参考 Radio 状态进行批处理调度。

2. **避免短连接保活**：频繁的心跳包（每 30 秒一次 HTTP 请求）会持续将 Radio 拖入 HIGH_POWER 状态。建议使用 FCM（Firebase Cloud Messaging）做推送唤醒，或使用 WebSocket 长连接代替轮询。

3. **预取（Prefetch）策略**：预测用户即将消费的内容（如信息流下一页），在 Radio 已激活时一次性拉取多页数据，然后让 Radio 回到 IDLE。Android 17 的 `NetworkRequest.Builder.setIncludeRadios()` 不存在，但可通过 JobScheduler 的 `setRequiredNetwork()` 约束确保批量请求在网络可用时统一执行。

[已验证: AOSP android-17.0.0_r1, frameworks/base/services/core/java/com/android/server/connectivity/ — Radio 活动状态由 ConnectivityService 与 Telephony 协同管理]
[待验证: 具体定时器值（inactivity timer）因运营商和设备配置而异，需查 PowerProfile.java 和 carrier config]

## 扩展

### 🔸 5G NR 性能特性与 Android 17

Android 17 对 5G NR（New Radio）的支持包括：

- **网络切片（Network Slicing）**：`TelephonyManager.getNetworkSlicingConfiguration()` 可查询当前切片配置（Android 14+ 引入，Android 17 增强）。企业应用可利用切片获得 guaranteed Bit Rate 保证。但切片查询本身是 IPC + RIL 调用，延迟可达 500ms+。

- **NR 独立组网（SA）检测**：`overrideNetworkType` 返回 `NR_NSA` 或 `NR_SA`。NR SA 模式下，语音通话使用 VoNR 而非 VoLTE，延迟模型不同。

- **上行载波聚合（UL CA）**：影响上行吞吐量，但不直接影响应用层 API 调用性能。

[已验证: 官方文档, developer.android.com/reference/android/telephony/TelephonyManager — 5G 相关 API 从 Android 11 起逐步扩展]
[自动发现: Android 17 是否新增 NR 的性能相关 API 需进一步确认]

### 🔸 双卡/多卡性能模型

多 SIM 场景下的性能影响：

1. **DSDS（Dual SIM Dual Standby）**：两张 SIM 共享一个 Radio 收发器。当 SIM 1 进行数据传输时，SIM 2 的信号监听会被中断（gap）。这导致在 SIM 2 上注册的 listener 会经历周期性的信号丢失上报。

2. **DSDA（Dual SIM Dual Active）**：两张 SIM 各有独立收发器。无 Radio 竞争问题，但功耗更高。

3. **SubscriptionManager 性能**：`SubscriptionManager.getActiveSubscriptionInfoList()` 是 IPC 调用，应避免在主线程频繁调用。Android 17 中 SIM 信息有内容观察者（ContentObserver）机制，建议使用监听代替轮询。

[已验证: AOSP android-17.0.0_r1, frameworks/base/telephony/java/android/telephony/SubscriptionManager.java]
