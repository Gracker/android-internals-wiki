# 8.8 Android 17 TelephonyManager 性能优化实战

[适用版本：Android 14（API 34）至 Android 17（API 37）]

`TelephonyManager` 让应用读取蜂窝注册、信号、数据网络、通话和 SIM 相关状态。一次调用可能只读 Phone 进程缓存，也可能请求 Radio HAL 和 Modem；状态 callback 则经 `TelephonyRegistry` 分发。把它们都解释成“同步等待 Modem”，会得到错误的线程与超时结论。

本章以 `android-17.0.0_r1` 为平台锚点，重点讨论应用能控制的查询频率、callback 数量、Executor、CellInfo 刷新、多卡缓存和现场诊断。Telephony 完整进程模型见 1.61 节。

---

## 1. Android 17 的进程与传输边界

Android 17 常见路径如下：

```text
应用进程
  TelephonyManager
    ├─ ITelephony Binder
    │      ↓
    │  com.android.phone
    │    PhoneInterfaceManager
    │    Phone / ServiceStateTracker / RIL
    │      ├─ 分域 AIDL Radio HAL Binder
    │      └─ HIDL IRadio HwBinder 兼容路径
    │              ↓
    │          Vendor Radio HAL → Modem
    │
    └─ ITelephonyRegistry Binder
           ↓
       system_server
         TelephonyRegistry
           └─ oneway IPhoneStateListener → 应用 Binder Stub → Executor
```

早期 Android 常见的 `RILJ → Unix Socket → /vendor/bin/rild` 图，不能作为 Android 17 的通用模型。AOSP 的主路径是按 data、messaging、modem、network、sim、voice、ims 等域划分的 AIDL Radio HAL，仍保留 HIDL 1.4 至 1.6 回退。Vendor HAL 到 Modem 的传输由厂商决定，设备上也不一定存在名为 `rild` 的独立进程。

三个进程有不同职责：

- `TelephonyManager` 在应用进程完成参数、subscription 和兼容处理；
- `PhoneInterfaceManager` 在 `com.android.phone` 实现大量 `ITelephony` 查询与控制；
- `TelephonyRegistry` 在 `system_server` 保存部分状态，并把事件发送给已注册 callback。

回调路径和查询路径分开后，才能判断慢在 App Executor、Registry 扇出、Phone 主 Looper、Radio HAL 或 Modem。

源码锚点：

- [`TelephonyManager.java`](https://android.googlesource.com/platform/frameworks/base/+/refs/tags/android-17.0.0_r1/telephony/java/android/telephony/TelephonyManager.java)
- [`PhoneInterfaceManager.java`](https://android.googlesource.com/platform/packages/services/Telephony/+/refs/tags/android-17.0.0_r1/src/com/android/phone/PhoneInterfaceManager.java)
- [`RIL.java`](https://android.googlesource.com/platform/frameworks/opt/telephony/+/refs/tags/android-17.0.0_r1/src/java/com/android/internal/telephony/RIL.java)

## 2. 把 API 分成三类

### 2.1 Phone 进程缓存查询

`getDataNetworkType()`、`getServiceState()`、`getSignalStrength()` 等常见 getter 会跨 Binder，但服务端通常读取 `Phone`、`ServiceStateTracker` 或 signal controller 已维护的状态。正常路径不要求为每次调用向 Modem 发起新请求。

缓存查询仍有这些成本和边界：

- 获取 Binder 服务句柄、Binder 排队、权限与 AppOps 检查；
- `com.android.phone` 线程执行和 Parcelable 复制；
- Phone 进程重启时的 null、unknown 或 RemoteException 兼容返回；
- 状态可能比当前 radio 变化晚一步。

因此，不要给 getter 写通用的“缓存命中 5 ms、RIL 查询 500 ms”表。轻量缓存查询也不应放进每帧、紧循环或列表 bind。

### 2.2 异步 Radio/Modem 请求

需要 Radio 刷新的 API 通常提供 callback、`OutcomeReceiver` 或 Executor。RIL 为请求分配 serial，放入 request list，再经 AIDL/HIDL Radio HAL 异步发送；response 带 serial 返回后完成对应请求。

RIL 的 WakeLock timeout 用于防止 RIL WakeLock 长期持有，不会自动取消 request list 中的请求，也不是所有 Telephony API 共用的调用超时。Binder 本身同样没有可让应用依赖的“5—10 秒 Telephony 超时”。

### 2.3 Registry callback

`registerTelephonyCallback()` 通过 `ITelephonyRegistry` 在 `system_server` 创建记录。注册时可立即收到当前缓存状态，后续事件经 oneway `IPhoneStateListener` 到应用 Binder Stub，再由注册时传入的 Executor 执行。

callback 业务代码不会直接在 `TelephonyRegistry` 线程执行。慢 callback 会堵住应用自己的 Executor；若使用 direct executor，还可能占住应用 Binder 线程。事件持续到达时，应用侧会出现过期状态积压。

## 3. TelephonyCallback 的线程与生命周期

Android 12 / API 31 引入 `TelephonyCallback`，用来替代已废弃的 `PhoneStateListener` 注册方式。一个 callback 通过实现不同 listener interface 选择事件。

下面的 tracker 用单线程 Executor 保留回调顺序，并只发布界面需要的 data registration state 与信号等级：

```kotlin
class TelephonyStateTracker(
    context: Context,
    subscriptionId: Int,
) : Closeable {
    private val tm = context
        .getSystemService(TelephonyManager::class.java)
        .createForSubscriptionId(subscriptionId)

    private val executor = Executors.newSingleThreadExecutor()

    data class State(
        val dataRegistrationState: Int =
            ServiceState.STATE_OUT_OF_SERVICE,
        val signalLevel: Int? = null,
    )

    private val _state = MutableStateFlow(State())
    val state: StateFlow<State> = _state.asStateFlow()

    private val callback = object : TelephonyCallback(),
        TelephonyCallback.ServiceStateListener,
        TelephonyCallback.SignalStrengthsListener {

        override fun onServiceStateChanged(serviceState: ServiceState) {
            _state.value = _state.value.copy(
                dataRegistrationState =
                    serviceState.dataRegistrationState
            )
        }

        override fun onSignalStrengthsChanged(
            signalStrength: SignalStrength,
        ) {
            _state.value = _state.value.copy(
                signalLevel = signalStrength.level
            )
        }
    }

    init {
        tm.registerTelephonyCallback(executor, callback)
    }

    override fun close() {
        tm.unregisterTelephonyCallback(callback)
        executor.shutdown()
    }
}
```

这段代码有三个设计约束：

- callback 是成员字段；framework stub 只弱引用 `TelephonyCallback`，注册期间应用必须持有强引用；
- 注册与注销使用同一个实例；
- callback 只复制小状态，数据库、网络和复杂计算进入业务队列。

只有 UI 生命周期需要监听时，可在 `onStart()` 创建、在 `onStop()` 关闭。多个页面使用同一份状态时，放到进程级容器更省 callback；涉及不同 subId 或不同权限域时，应按 subscription 和数据访问边界分开。

源码锚点：

- [`TelephonyCallback.java`](https://android.googlesource.com/platform/frameworks/base/+/refs/tags/android-17.0.0_r1/core/java/android/telephony/TelephonyCallback.java)
- [`TelephonyRegistry.java`](https://android.googlesource.com/platform/frameworks/base/+/refs/tags/android-17.0.0_r1/services/core/java/com/android/server/TelephonyRegistry.java)

## 4. callback 数量上限用于发现泄漏

Android 17 的 `TelephonyCallback.DEFAULT_PER_PID_REGISTRATION_LIMIT` 是 50。该值可由 DeviceConfig 调整，Phone、system 和 Registry 所在 UID 有豁免。普通进程超过当前上限时，注册会抛出 `IllegalStateException`。

这个数字不是应用的可用容量。`TelephonyRegistry` 的 notify 方法在 `mRecords` 锁内遍历记录，再按 event、subId、phoneId 和权限筛选。记录越多，筛选、对象复制和 oneway Binder 投递越多。

常见泄漏来源：

- Activity 重建时注册新对象，旧对象未注销；
- 同一个 callback 未注销就再次注册；
- 切换 subId 后创建新 tracker，旧 subscription 的 tracker 仍存活；
- Executor shutdown 了，但 callback 还在 Registry 中；
- 只依赖 callback 被 GC，不调用 unregister。

测试可以连续执行旋转、分屏、导航返回、SIM 切换和进程前后台，再检查 `dumpsys telephony.registry` 中调用包的记录数是否回到预期。

## 5. 信号强度：平台比较完整对象

Android 17 的 `SignalStrengthController.notifySignalStrength()` 比较完整 `SignalStrength` 与上一次对象，同时比较 subId。对象或 subId 变化时才继续通知。它不是只在 `level` 的 0—4 档发生变化时才分发，也没有可供普通应用依赖的固定五秒节流窗口。

应用可按用途做第二层归并：

- UI 只显示信号格时，提取 `signalStrength.level`，相同等级不重绘；
- 网络诊断需要 RSRP、RSRQ、SINR 等细节时，保存技术类型、时间和权限条件；
- 事件上报按时间窗口合并，但保留状态切换边界；
- 不用高频 `getSignalStrength()` 轮询替代 callback。

信号好不等于互联网可用。蜂窝已注册、data call 已连接、Connectivity 已验证、该网络成为应用默认网络、业务服务可达，属于不同状态。

源码锚点：[`SignalStrengthController.java`](https://android.googlesource.com/platform/frameworks/opt/telephony/+/refs/tags/android-17.0.0_r1/src/java/com/android/internal/telephony/SignalStrengthController.java#784)

## 6. CellInfo：缓存读取与主动刷新

面向 Android 10 / API 29 及以上的应用，`getAllCellInfo()` 返回 Phone 进程的最新缓存，不再因调用而刷新 Radio。数据是否新鲜要检查每个 `CellInfo` 的 timestamp。

需要更新时使用 `requestCellInfoUpdate()`。请求会被系统限频，也不保证成功；应用要处理 timeout、modem error、空列表和仍然较旧的数据。

下面的调用用于执行一次异步刷新，并把失败原因留给业务层：

```kotlin
telephonyManager.requestCellInfoUpdate(
    executor,
    object : TelephonyManager.CellInfoCallback() {
        override fun onCellInfo(cellInfo: List<CellInfo>) {
            cellRepository.update(cellInfo)
        }

        override fun onError(
            errorCode: Int,
            detail: Throwable?,
        ) {
            cellRepository.recordRefreshFailure(errorCode, detail)
        }
    },
)
```

这不是周期采样器。持续监控应使用 `TelephonyCallback.CellInfoListener`，并根据产品所需分辨率去重。CellInfo 需要位置权限；回调与返回字段还会受 `READ_PHONE_STATE`、`ACCESS_FINE_LOCATION`、目标版本和位置开关影响。

原文把 `getCellLocation()` 写成“等待 Modem 定位”，又把 `getAllCellInfo()` 写成每次触发扫描，都与 Android 17 的缓存和异步刷新实现不符。`getCellLocation()` 本身也早已废弃。

源码锚点：

- [`TelephonyManager.getAllCellInfo()`](https://android.googlesource.com/platform/frameworks/base/+/refs/tags/android-17.0.0_r1/telephony/java/android/telephony/TelephonyManager.java#6880)
- [`PhoneInterfaceManager.getAllCellInfo()`](https://android.googlesource.com/platform/packages/services/Telephony/+/refs/tags/android-17.0.0_r1/src/com/android/phone/PhoneInterfaceManager.java#3472)

## 7. 主线程调用的判断方式

Telephony getter 是 Binder 调用。即使服务端当前只读缓存，也可能遇到 Phone 进程启动、Binder 排队、Phone 主 Looper 排队、权限服务等待或厂商实现差异。StrictMode 的 network 与 disk 检测不会自动把普通 Binder 等待标成 Telephony 风险。

可以按以下规则处理：

- 启动和首帧不依赖的 Telephony 查询放到后台；
- 提供异步 API 的操作使用异步 API；
- 同一状态靠 callback 更新业务缓存，页面只读本地快照；
- 轻量 getter 不进入 `onDraw()`、RecyclerView bind、动画 callback 或高频 timer；
- 每个产品关心的调用加自定义 trace，记录 subId、结果类别和耗时，不记录电话号码、IMSI、CellIdentity 等敏感数据。

不要维护“高风险 API 2 秒、低风险 API 50 ms”静态表。服务端路径、设备 feature、权限、Radio HAL、运营商配置和 Phone 进程状态都会改变耗时。

## 8. Telephony 数据连接与 Connectivity 默认网络

`TelephonyCallback.DataConnectionStateListener` 提供蜂窝数据连接的粗粒度状态。它不能回答以下问题：

- 网络是否包含 `NET_CAPABILITY_VALIDATED`；
- VPN 是否成为该 UID 的默认网络；
- Data Saver 或其他策略是否阻断当前 UID；
- DNS、路由和 Private DNS 是否完成；
- 业务端点是否可访问。

“蜂窝有信号但应用无网”可按这组顺序排查：

1. `ServiceState` 是否注册到蜂窝；
2. data state 是否 connected；
3. Telephony network agent 是否已注册到 Connectivity；
4. `NetworkCapabilities` 是否匹配应用需求；
5. validation、默认网络、blocked status、DNS 与路由；
6. TLS、HTTP、CDN 和业务服务。

普通应用的联网状态使用 `ConnectivityManager.registerDefaultNetworkCallback()`。Telephony callback 适合展示运营商、制式、信号或通话相关状态，不能替代 Connectivity。

## 9. 多 SIM：缓存必须带 subscription 维度

`slotIndex`、`phoneId`、eSIM port 和 `subscriptionId` 表示不同对象，SIM 热插拔、eSIM profile 切换和 modem 数量变化都可能改变映射。

应用应：

- 用 `createForSubscriptionId(subId)` 构造明确 subscription 的 `TelephonyManager`；
- 用 `SubscriptionManager.addOnSubscriptionsChangedListener()` 观察 active subscription 变化；
- subscription 变化后关闭旧 callback，使旧缓存失效；
- 异步任务执行前重新确认 subId 仍 active；
- 不把 subId 当作永久 SIM 身份写入长期业务主键。

DSDS 只说明多卡待机能力，不保证“另一张卡周期性丢信号”；DSDA 也不等于每台设备都有两套完全独立的射频。并发通话与数据能力应读取设备提供的 capability，并在目标设备测试。

## 10. Radio 功耗不要沿用 3G DCH/FACH 图

原文给出的 `DCH → FACH → IDLE`、固定 inactivity timer 和固定电流值来自特定 3G 网络模型，无法解释 Android 17 的 LTE、NR NSA/SA、双连接、运营商配置和厂商基带策略。

应用仍能做三件稳定有效的事：

- 合并可延期请求，减少设备、网络和应用反复唤醒；
- 后台同步使用 WorkManager 或 JobScheduler 的网络与充电约束；
- 下行即时消息优先使用适合业务的共享推送通道，避免每个应用各自短周期轮询。

WebSocket 不会天然比轮询省电。心跳周期、NAT、网络切换、服务端策略和 radio tail 都会影响结果。预取也要比较命中率、额外流量、内存和内容过期，不能只看请求次数。

测量时记录传输字节、请求批次、radio active 相关轨迹、CPU、WakeLock、网络类型、信号和任务完成量。不同方案必须完成同样的业务工作。

## 11. Android 17 与 5G 能力的边界

Android 17 的 Telephony API 包含 network slicing、NR、IMS、NTN/satellite 等能力，但方法出现在 SDK 或源码中，不代表每台 Android 17 设备都支持：

- 先检查对应 `PackageManager` telephony feature；
- 再检查 API flag、carrier config、subscription、区域和 provisioning；
- 按方法文档满足普通权限、privileged permission 或 carrier privilege；
- 异步 API 处理 unsupported、timeout、radio unavailable 和 modem error；
- 不把网络切片描述成第三方应用必然获得 guaranteed bitrate。

`TelephonyDisplayInfo` 的 override network type 用于显示和策略摘要，不能据此推断完整 NR 架构、吞吐量、延迟或 VoNR 会话状态。

## 12. 诊断：从 Binder 到 Radio response

### 12.1 只读状态

下面的命令用于查看 Phone、Registry、subscription 和 Radio HAL：

```bash
adb shell 'service list | grep -E "phone|telephony.registry|isub|isms"'
adb shell dumpsys phone
adb shell dumpsys telephony.registry
adb shell dumpsys isub
adb shell lshal | grep -i radio
adb shell 'service list | grep android.hardware.radio'
adb shell ps -A | grep -i -E 'radio|ril'
```

输出可能包含 subscription、CellIdentity、运营商和通话信息。保存或分享前必须脱敏。AIDL 服务从 Binder service manager 查看，HIDL 服务通常由 `lshal` 展示；不能只搜索 `rild`。

### 12.2 Perfetto 时间线

抓取 Binder、sched、CPU frequency/idle、power 和应用自定义 trace，把慢操作分段：

```text
App 发起 ITelephony
  → Phone Binder thread
  → Phone main Looper（若该 API 需要）
  → RIL request serial
  → Radio HAL
  → RIL response serial
  → Phone 完成查询或通知 TelephonyRegistry
  → App callback Binder
  → App Executor 开始
  → 业务状态发布
```

RIL 使用 `TRACE_TAG_NETWORK` 记录名为 `RIL` 的异步轨道，并用 request serial 作为 cookie。它可以帮助对齐 request 与 response。没有 radio request 时，不能把整个 Binder 时长写成 Modem 延迟。

Telephony callback 没有固定的毫秒到达保证。性能回归应比较同设备、同 SIM、同 radio 环境、同系统 build 和同脚本下的分位数。

## 13. 交付前检查表

- [ ] 新代码使用 `TelephonyCallback`，没有新增 `PhoneStateListener`。
- [ ] callback 是强引用字段，注册和注销使用同一个实例。
- [ ] Executor 有明确线程与关闭时机，callback 内不做数据库、网络或复杂计算。
- [ ] 同一 lifecycle 和 subId 复用少量 callback，旋转和导航后记录数不会增长。
- [ ] getter 不在帧循环、列表 bind 或紧密轮询中调用。
- [ ] `getAllCellInfo()` 被视为缓存；主动刷新使用 `requestCellInfoUpdate()` 并处理错误。
- [ ] 信号 UI 按业务字段去重，没有假定平台只按 level 分发。
- [ ] Telephony data connected 没有被当作互联网已验证。
- [ ] 所有缓存包含 subId，subscription 变化后会失效。
- [ ] 权限拒绝、feature 缺失、Phone 进程异常、radio unavailable 和 timeout 分开处理。
- [ ] 日志与 trace 不记录电话号码、IMSI、CellIdentity 等敏感数据。
