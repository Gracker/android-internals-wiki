# 8.9 Android 17 ConnectivityManager 性能优化实战

ConnectivityManager 是应用感知和调度网络连接的核心入口：NetworkCallback 注册/注销、默认网络变化监听、NetworkRequest 请求生命周期、TrafficStats 流量统计——全部经由此 API 暴露。与 §8.8 聚焦的 Telephony IPC 阻塞不同，本章关注 **ConnectivityManager 自身的回调分发性能、NetworkRequest 限流机制、网络切换平滑性，以及 Android 17 引入的网络性能新特性**。

> 详见 §11.1（网络性能优化策略）和 §11.2（网络性能深入分析）了解上层网络优化方法论。

## 要点

### 🔹 ConnectivityManager 架构与 IPC 性能模型

Android 17 中 ConnectivityManager 的代码已从 `frameworks/base` 迁移到 Mainline 模块 `packages/modules/Connectivity/`，但其对应用暴露的 API 接口不变。进程架构如下：

```
App Process                              System Server (system_server)
  └─ ConnectivityManager (SDK API)       └─ ConnectivityService
       └─ Binder IPC → IConnectivityManager
            └─ ConnectivityThread (共享单例 HandlerThread)
                 └─ CallbackHandler (网络状态回调分发)
                                         └─ NetworkAgentInfo (每个网络连接的抽象)
                                              └─ NetworkMonitor (网络探测/验证)
```

**关键 IPC 边界**：

1. **App → ConnectivityService**：所有 `registerNetworkCallback`、`requestNetwork`、`getActiveNetwork` 等调用通过 Binder 进入 system_server 的 ConnectivityService。同步查询类 API（`getActiveNetwork`、`getNetworkCapabilities`）直接返回缓存值，延迟 < 1ms；异步操作（`requestNetwork`）触发 ConnectivityService 内部的 NetworkAgent 状态机，回调通过 `Messenger` → `CallbackHandler` 投递回应用进程。

2. **ConnectivityThread 共享单例**：ConnectivityManager 的所有 NetworkCallback 默认在同一个 `ConnectivityThread` 上分发——这是一个进程级单例 `HandlerThread`（懒加载，首次调用 `getDefaultHandler()` 时创建）。**这意味着所有未指定 Handler 的 NetworkCallback 回调都在同一个线程上串行执行**。如果一个回调的 `onCapabilitiesChanged` 耗时 50ms，后续所有其他回调的投递都会被延迟 50ms。

[已验证: AOSP android-17.0.0_r1, packages/modules/Connectivity/framework/src/android/net/ConnectivityThread.java — 全文仅 56 行，纯单例 HandlerThread]
[已验证: AOSP android-17.0.0_r1, packages/modules/Connectivity/framework/src/android/net/ConnectivityManager.java:4729-4734 — getDefaultHandler() 懒加载 sCallbackHandler]

**性能影响量化**：

| 操作 | 典型延迟 | 阻塞风险 |
|------|----------|----------|
| `getActiveNetwork()` | 0.1-1ms（缓存读取） | 极低 |
| `getNetworkCapabilities()` | 0.1-1ms | 极低 |
| `registerNetworkCallback()` | 2-10ms | 低 — 一次性 |
| `onCapabilitiesChanged` 回调 | 0.5-5ms/次 | 中 — 频繁变化时累积 |
| `requestNetwork()` 触发新连接 | 500-5000ms | 高 — 异步但不保证成功 |
| WiFi↔Cellular 切换全流程 | 2-15s | 高 — UI 感知明显 |

### 🔹 NetworkCallback 回调分发性能与线程模型

#### 默认线程：ConnectivityThread 单例

```java
// ConnectivityManager.java:4729-4734 (android-17.0.0_r1)
private CallbackHandler getDefaultHandler() {
    synchronized (sCallbacks) {
        if (sCallbackHandler == null) {
            sCallbackHandler = new CallbackHandler(ConnectivityThread.getInstanceLooper());
        }
        return sCallbackHandler;
    }
}
```

ConnectivityThread 的实现极其简洁——一个标准的 HandlerThread 单例：

```java
// ConnectivityThread.java (android-17.0.0_r1) — 全文
public final class ConnectivityThread extends HandlerThread {
    private static class Singleton {
        private static final ConnectivityThread INSTANCE = createInstance();
    }
    private ConnectivityThread() { super("ConnectivityThread"); }
    // ...
    public static Looper getInstanceLooper() { return Singleton.INSTANCE.getLooper(); }
}
```

[已验证: AOSP android-17.0.0_r1, packages/modules/Connectivity/framework/src/android/net/ConnectivityThread.java]

**性能陷阱**：由于所有未指定 Handler 的 NetworkCallback 共享这一个线程，任何回调中的阻塞操作（如同步网络请求、数据库写入）会卡住所有其他网络状态回调的分发。一个典型的踩坑场景：

```kotlin
// ❌ 危险：在 NetworkCallback 中做同步 IO
connectivityManager.registerDefaultNetworkCallback(object : NetworkCallback() {
    override fun onCapabilitiesChanged(network: Network, caps: NetworkCapabilities) {
        // 这段代码运行在 ConnectivityThread 上
        // 如果数据库写入耗时 200ms，期间所有其他 NetworkCallback 都被阻塞
        db.saveNetworkState(network, caps) // 同步数据库写入！
    }
})
```

```kotlin
// ✅ 正确：回调中只做轻量操作，耗时任务转移
connectivityManager.registerDefaultNetworkCallback(object : NetworkCallback() {
    override fun onCapabilitiesChanged(network: Network, caps: NetworkCapabilities) {
        // 只做必要的状态记录（< 1ms）
        lastNetworkState = NetworkState(network, caps)
        // 耗时任务转移到 IO 线程
        scope.launch(Dispatchers.IO) {
            db.saveNetworkState(network, caps)
        }
    }
})
```

#### Android 12+ Callback 方法过滤优化

Android 12（API 31）引入了基于 `FLAG_USE_DECLARED_METHODS_FOR_CALLBACKS` 的方法过滤机制。ConnectivityManager 在注册回调时，通过反射检查 NetworkCallback 子类覆写了哪些方法，只发送对应的消息：

```java
// ConnectivityManager.java:1233-1244 (android-17.0.0_r1)
private static final LruCache<Class<? extends NetworkCallback>, Integer> sMethodFlagsCache =
        new LruCache<>(100);

// 注册时计算 method flags
int declaredMethodsFlag = useDeclaredMethods
        ? tryGetDeclaredMethodsFlag(callback)
        : NetworkCallback.DECLARED_METHODS_ALL;
```

**性能意义**：只覆写 `onAvailable` 和 `onLost` 的回调，不会收到 `onCapabilitiesChanged` 消息，减少了不必要的 IPC 和 Handler 投递开销。这与 Android 12 之前的全量回调形成对比。

[已验证: AOSP android-17.0.0_r1, ConnectivityManager.java:1233-1244 — LruCache(100) 缓存方法标志位]

#### 回调消息分发流程

CallbackHandler.handleMessage 处理的消息类型（android-17.0.0_r1）：

| 消息常量 | 对应回调 | 触发频率 |
|----------|---------|---------|
| `CALLBACK_AVAILABLE` | `onAvailable()` | 每次网络连接 |
| `CALLBACK_LOSING` | `onLosing()` | 网络即将丢失 |
| `CALLBACK_LOST` | `onLost()` | 每次网络断开 |
| `CALLBACK_UNAVAIL` | `onUnavailable()` | requestNetwork 超时 |
| `CALLBACK_CAP_CHANGED` | `onCapabilitiesChanged()` | **高频** — 信号/带宽变化 |
| `CALLBACK_IP_CHANGED` | `onLinkPropertiesChanged()` | 中频 — IP/DNS 变化 |
| `CALLBACK_BLK_CHANGED` | `onBlockedStatusChanged()` | 低频 — 后台限制变化 |
| `CALLBACK_SUSPENDED` / `CALLBACK_RESUMED` | `onNetworkSuspended/Resumed` | 极低频 |

其中 `onCapabilitiesChanged` 是最高频的回调——WiFi 信号强度变化、Cellular 信号波动、带宽估计更新都会触发。在弱网环境或网络切换期间，该回调可能每秒触发多次。

### 🔹 NetworkRequest 限流机制

ConnectivityService 对每个 UID 的 NetworkRequest 数量有硬限制：

```java
// ConnectivityService.java:566-575 (android-17.0.0_r1)
static final int MAX_NETWORK_REQUESTS_PER_UID = 100;
static final int MAX_NETWORK_REQUESTS_PER_SYSTEM_UID = 375;
```

[已验证: AOSP android-17.0.0_r1, packages/modules/Connectivity/service/src/com/android/server/ConnectivityService.java:566-575]

**实际限制**：普通应用最多 99 个并发 NetworkRequest（`MAX_NETWORK_REQUESTS_PER_UID - 1 = 99`），system UID 最多 374 个。超出会抛出 `ServiceSpecificException`。

**性能影响**：
- 每个 `requestNetwork()` 调用在 ConnectivityService 中创建一个 `NetworkRequestInfo` 对象，维护在 `mNetworkRequests` HashMap 中
- 每次 NetworkAgent 状态变化，ConnectivityService 遍历匹配的 NetworkRequest 列表并触发回调
- 大量未注销的 NetworkRequest 会导致 rematch 开销线性增长

**最佳实践**：

```kotlin
// 始终在组件销毁时注销回调
class NetworkAwareActivity : AppCompatActivity() {
    private val callback = object : NetworkCallback() {
        override fun onAvailable(network: Network) { /* ... */ }
    }

    override fun onStart() {
        super.onStart()
        connectivityManager.registerNetworkCallback(
            NetworkRequest.Builder()
                .addCapability(NET_CAPABILITY_INTERNET)
                .build(),
            callback
        )
    }

    override fun onStop() {
        super.onStop()
        connectivityManager.unregisterNetworkCallback(callback)
    }
}
```

> ⚠️ 未注销 NetworkCallback 是最常见的 ConnectivityService 泄漏来源。Android 17 不会自动清理未注销的回调（除非进程死亡），每次 Activity 重建时重复注册会快速逼近 100 个上限。

### 🔹 网络状态切换的性能剖析

WiFi ↔ Cellular 切换是影响用户体感最大的网络性能事件。Android 17 的切换流程：

```
1. WiFi 信号衰减 → WifiTracker 检测到 RSSI < 阈值
2. ConnectivityService 收到 NetworkAgent 劣化通知 → onLosing(callback, maxMsToLive)
3. WifiNetworkAgent 进入 lingering 状态（默认 30s grace period）
4. Cellular NetworkAgent 注册 → ConnectivityService rematch
5. 新默认网络确定 → makeDefault() → onAvailable(newNetwork) 投递
6. 旧 WiFi 网络 linger 超时 → onLost(wifiNetwork)
```

**关键性能指标**：

| 阶段 | 典型耗时 | 可优化方向 |
|------|---------|-----------|
| WiFi→Cellular 检测延迟 | 1-5s | 预注册 Cellular NetworkRequest |
| onLosing → onAvailable 间隔 | 200ms-3s | 应用层缓存 + 请求重试策略 |
| TCP 连接迁移 | 0ms（同 socket）- 5s（新建连接） | 使用 `bindSocketToNetwork()` 绑定 |
| DNS 重新解析 | 50-500ms | 使用 `Network.getAllByName()` 指定网络 |

**`bindProcessToNetwork()` 的性能影响**：调用 `ConnectivityManager.bindProcessToNetwork()` 会改变所有后续 socket 的默认网络。如果应用在切换期间有大量 pending HTTP 请求，bindProcessToNetwork 后这些请求会尝试在新网络上发送，但旧 socket 上已建立的连接不会自动迁移。

### 🔹 后台网络优化策略

#### NetworkCallback vs 广播：性能对比

Android 7.0（API 24）废弃了 `CONNECTIVITY_ACTION` 广播，推荐使用 `registerDefaultNetworkCallback()`。Android 17 中广播已完全移除。性能对比：

| 特性 | 广播（已废弃） | NetworkCallback |
|------|-------------|----------------|
| 唤醒频率 | 所有网络变化 | 可过滤的 |
| IPC 次数 | 每次变化对所有接收者各一次 | 每次变化只通知注册者一次 |
| 主线程影响 | BroadcastReceiver.onReceive 在主线程 | 可指定 Handler 线程 |
| 延迟 | 100-500ms（广播队列） | 5-50ms（直接 Binder 回调） |

#### JobScheduler 网络约束的内部实现

`JobScheduler` 的网络约束（`setRequiredNetwork()`）最终通过 ConnectivityService 的 NetworkRequest 机制实现。每个带网络约束的 Job 会在 ConnectivityService 中注册一个系统级 NetworkRequest。当网络满足约束时，JobScheduler 收到回调并调度 Job。

**这意味着**：大量使用网络约束的 Job 会在 ConnectivityService 中累积 NetworkRequest，进一步消耗该 UID 的 100 个配额（但 JobScheduler 内部的请求使用 system UID，不计入应用配额）。

### 🔹 Android 17 网络性能 API 变更

#### Data Plan Streaming API

Android 17（API 37）新增 `NetworkStatsManager.getStreamingAppMaxDownlinkKbps()` 和 `getStreamingAppMaxUplinkKbps()`，允许应用查询运营商分配的流媒体速率上限：

```kotlin
val maxDownlink = networkStatsManager.getStreamingAppMaxDownlinkKbps(subscriberId)
val maxUplink = networkStatsManager.getStreamingAppMaxUplinkKbps(subscriberId)

// 根据运营商限制自适应调整流媒体质量
if (maxDownlink > 0 && maxDownlink < 2_000_000) {
    // 运营商限速 < 2 Mbps，降低视频质量
    videoPlayer.setQuality(VideoQuality.LOW)
}
```

[结构参考: research-feeds/2026-04-08-11-android17-network-data-plan-streaming-access-local-network-tls.md]

**性能意义**：此前应用只能通过实测吞吐量推测网络瓶颈，现在可以直接从系统获取运营商限速信息，避免「请求高码率 → 等待超时 → 降级重试」的恶性循环。

#### ACCESS_LOCAL_NETWORK 权限

Android 17 新增普通权限 `android.permission.ACCESS_LOCAL_NETWORK`，要求应用显式声明才能访问本地网络（mDNS 发现、局域网设备通信等）。此前无需任何权限即可访问本地网络。

**影响**：投屏、IoT 控制、本地服务器类应用需要在 manifest 中声明权限，并处理权限拒绝场景。未声明权限的应用在 targetSdk=37 时会收到 `SecurityException`。

#### DeliQueue 对网络回调的间接优化

Android 17 的无锁 MessageQueue 实现（DeliQueue，target API 37 时生效）直接影响网络回调在主线程的投递效率。网络请求的 `onResponse`/`onFailure` 回调通过 MessageQueue 投递到主线程时，减少锁等待意味着网络结果能更快驱动 UI 更新。

> 详见 §1.26 DeliQueue 无锁 MessageQueue 章节

## 扩展

### 🔸 WiFi 扫描与连接性能

WiFi 扫描（`WifiManager.startScan()`）在 Android 9+ 已被限流：每个前台应用每 30 秒最多 4 次扫描，后台应用每 30 分钟最多 1 次。Android 17 维持这一限制。建议使用 `WifiManager.getScanResults()` 获取缓存的扫描结果（由系统定期更新），而非主动触发扫描。

[待验证: Android 17 是否调整了扫描限流参数]

### 🔸 TrafficStats 性能监控

`TrafficStats.getUidRxBytes()` / `getUidTxBytes()` 从 `/proc/uid_stat/<uid>/tcp_rcv` 读取，单次调用约 50-100μs。适合低频采样（每分钟级别），不适合高频率轮询。推荐使用 `NetworkStatsManager.queryDetailsForUid()` 获取时间范围内的流量统计，性能更优且支持分网络类型查询。

### 🔸 SocketKeepalive 机制

Android 17 支持 `ConnectivityManager.createSocketKeepalive()`，允许应用维持 NAT 穿透保活连接而无需定期发送应用层心跳。这显著降低了后台保活的功耗和流量开销。但每个 UID 的 keepalive slot 数量有限（通常 3-6 个，取决于硬件支持）。
