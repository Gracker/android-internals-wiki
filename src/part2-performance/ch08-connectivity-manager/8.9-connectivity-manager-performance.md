# 8.9 Android 17 ConnectivityManager 性能优化实战

[适用版本：Android 14（API 34）至 Android 17（API 37）]

应用通过 `ConnectivityManager` 观察默认网络、监听匹配网络、主动请求额外网络，并把 socket 或 DNS 查询限定到指定 `Network`。优化这条路径时，常见误区是把网络建链、互联网验证、默认网络选择、应用回调和业务请求耗时混成一个“网络切换时间”。

本章以 `android-17.0.0_r1` 为平台锚点，讨论应用能够测量和修改的部分。网络评分、NetworkMonitor、BPF 统计和 VPN 的完整架构见 1.62 节。

---

## 1. 一次状态变化经过哪些进程

Android 17 的 Connectivity 代码由 Mainline 模块交付。模块位置变了，服务的进程边界没有因此合并：

```text
应用进程
  ConnectivityManager
    └─ IConnectivityManager Binder
          ↓
system_server
  ConnectivityService
    ├─ NetworkRequest 匹配与每 UID 默认网络
    ├─ NetworkAgentInfo / NetworkRanker
    └─ 与 netd、NetworkStack 协调
          ↓
com.android.networkstack.process
  NetworkMonitor：互联网、门户网络、Private DNS 验证

Wi-Fi / Telephony / Ethernet / VPN 所在进程
  NetworkAgent：向 ConnectivityService 上报网络及属性
```

这里有四段不同的等待：

1. Wi-Fi、蜂窝或 VPN 提供者完成建链和 IP 配置；
2. `ConnectivityService` 注册网络、匹配请求并选择每个 UID 的默认网络；
3. NetworkStack 进程验证互联网或 Private DNS；
4. 回调进入应用进程后，等待目标 Looper 并执行应用代码。

回调晚到只能证明第 1 至第 4 段中的某处有等待。要定位到 `ConnectivityManager`，还需结合 Binder、线程调度、Connectivity dumpsys 和应用自己的时间戳。

源码锚点：

- [`ConnectivityManager.java`](https://android.googlesource.com/platform/packages/modules/Connectivity/+/refs/tags/android-17.0.0_r1/framework/src/android/net/ConnectivityManager.java)
- [`ConnectivityService.java`](https://android.googlesource.com/platform/packages/modules/Connectivity/+/refs/tags/android-17.0.0_r1/service/src/com/android/server/ConnectivityService.java)

## 2. 同步查询会跨 Binder，不要在回调里补查

`getActiveNetwork()` 和 `getNetworkCapabilities()` 在 Android 17 的 `ConnectivityManager` 中都会调用 `IConnectivityManager`。它们不是应用进程内的零成本缓存读取，也没有通用的“小于 1 ms”保证。

在 `onAvailable(network)` 中立刻同步调用 `getNetworkCapabilities(network)` 还有竞态：网络属性可能在 Binder 查询前再次变化，查询结果与正在分发的回调序列不再对应。Android 8.0 及以上对新可用网络按顺序分发：

1. `onAvailable()`；
2. `onCapabilitiesChanged()`；
3. `onLinkPropertiesChanged()`；
4. `onBlockedStatusChanged()`。

应用应使用回调携带的 `NetworkCapabilities` 与 `LinkProperties` 更新快照。同步查询适合一次性诊断或没有回调上下文的低频检查，不能替代持续监听。

文档：[Read network state](https://developer.android.com/develop/connectivity/network-ops/reading-network-state)

## 3. 默认回调共享 ConnectivityThread

无 `Handler` 参数的 `registerDefaultNetworkCallback()`、`registerNetworkCallback()` 和 `requestNetwork()` 使用进程内静态 `CallbackHandler`。该 Handler 绑定到 `ConnectivityThread` 的单例 Looper，因此同一应用进程内使用默认 Handler 的网络回调会串行执行。

这条线程模型会产生两类问题：

- 某个回调做同步数据库、网络访问或长时间持锁，会延迟同进程其他默认网络回调；
- 回调线程与 UI 线程不同，直接修改非线程安全 UI 状态会引入竞态。

可以传入专用 Handler，让线程所有权和生命周期更清楚。下面的 tracker 用于维护应用默认网络快照；它只解析回调数据，不在 Connectivity 回调线程执行探测或 I/O：

```kotlin
class DefaultNetworkTracker(
    context: Context,
) : Closeable {
    private val cm =
        context.getSystemService(ConnectivityManager::class.java)
    private val thread = HandlerThread("default-network-tracker").apply {
        start()
    }
    private val handler = Handler(thread.looper)

    data class State(
        val network: Network? = null,
        val validated: Boolean = false,
        val captivePortal: Boolean = false,
        val metered: Boolean = true,
        val blocked: Boolean = false,
    )

    private val _state = MutableStateFlow(State())
    val state: StateFlow<State> = _state.asStateFlow()

    private val callback = object : ConnectivityManager.NetworkCallback() {
        override fun onAvailable(network: Network) {
            _state.value = State(network = network)
        }

        override fun onCapabilitiesChanged(
            network: Network,
            caps: NetworkCapabilities,
        ) {
            if (_state.value.network != network) return
            _state.value = _state.value.copy(
                validated = caps.hasCapability(
                    NetworkCapabilities.NET_CAPABILITY_VALIDATED
                ),
                captivePortal = caps.hasCapability(
                    NetworkCapabilities.NET_CAPABILITY_CAPTIVE_PORTAL
                ),
                metered = !caps.hasCapability(
                    NetworkCapabilities.NET_CAPABILITY_NOT_METERED
                ),
            )
        }

        override fun onBlockedStatusChanged(
            network: Network,
            blocked: Boolean,
        ) {
            if (_state.value.network == network) {
                _state.value = _state.value.copy(blocked = blocked)
            }
        }

        override fun onLost(network: Network) {
            if (_state.value.network == network) {
                _state.value = State()
            }
        }
    }

    init {
        cm.registerDefaultNetworkCallback(callback, handler)
    }

    override fun close() {
        cm.unregisterNetworkCallback(callback)
        thread.quitSafely()
    }
}
```

`close()` 必须由 tracker 的所有者调用。更常见的产品实现会把 tracker 放在进程级容器中，由多个页面共享一份状态，避免每个 Activity 各注册一份。

源码锚点：

- [`ConnectivityThread.java`](https://android.googlesource.com/platform/packages/modules/Connectivity/+/refs/tags/android-17.0.0_r1/framework/src/android/net/ConnectivityThread.java)
- [`ConnectivityManager.CallbackHandler`](https://android.googlesource.com/platform/packages/modules/Connectivity/+/refs/tags/android-17.0.0_r1/framework/src/android/net/ConnectivityManager.java#4569)

## 4. 三类 NetworkRequest 用途

| API | 系统语义 | 适用场景 |
|---|---|---|
| `registerDefaultNetworkCallback()` | 观察当前应用的默认网络 | 大多数应用的联网状态 |
| `registerNetworkCallback(request, ...)` | 被动观察所有满足条件的网络 | 观察特定 transport、capability 或候选网络 |
| `requestNetwork(request, ...)` | 请求系统尝试提供并维持最佳匹配网络 | 明确需要额外网络的短期任务 |

`requestNetwork()` 可能促使提供者扫描、拨号或维持 radio。它不适合轮询网络状态，任务完成后必须注销。若某个网络只为该请求建立，注销时系统可能释放它。

构建 `NetworkRequest` 时只声明业务所需条件：

- 通用互联网状态通常使用默认网络回调；
- 需要已验证互联网时检查 `NET_CAPABILITY_VALIDATED`，不要把 `TRANSPORT_WIFI` 当作“免费且更快”；
- DNS、路由、MTU 和代理变化从 `LinkProperties` 读取；
- Data Saver、Doze 或策略阻断由 `onBlockedStatusChanged()` 表达，`onAvailable()` 不代表当前 UID 一定能发送流量。

`NetworkRequest.Builder` 带有默认 capability。清除或增加条件前要阅读当前 API 文档，避免监听到业务不会使用的网络。

## 5. 每 UID 上限是泄漏保护，不是容量预算

公开 API 文档说明：`registerNetworkCallback()`、`requestNetwork()` 及 `ConnectivityDiagnosticsManager` 的相关注册共享每 UID 100 个 outstanding request 上限，超限会抛出运行时异常。

`android-17.0.0_r1` 的 `ConnectivityService` 定义 `MAX_NETWORK_REQUESTS_PER_UID = 100`，创建计数器时传入 `MAX_NETWORK_REQUESTS_PER_UID - 1`，源码注释说明这是兼容旧计数器在边界抛异常的处理。应用不应依赖 99 与 100 的边界差异；正常设计应远低于该数量。

减少请求数量比捕获超限异常更有效：

- 进程内复用默认网络 tracker；
- 页面只订阅 tracker 状态，不直接注册系统回调；
- 对同一 `NetworkRequest` 合并观察者；
- 注册成功后记录所有者，按相同 callback 实例注销；
- 测试 Activity 重建、导航返回和配置变化后，请求数是否持续增长。

进程死亡会清理该进程的 Binder 注册，但不能修复进程存活期间的重复注册、重复回调和无谓匹配。

源码与文档：

- [`ConnectivityService.java`](https://android.googlesource.com/platform/packages/modules/Connectivity/+/refs/tags/android-17.0.0_r1/service/src/com/android/server/ConnectivityService.java#566)
- [`ConnectivityManager` API](https://developer.android.com/reference/android/net/ConnectivityManager)

## 6. 网络切换不会迁移现有 TCP 连接

默认网络从 Wi-Fi 改为蜂窝后：

- 未显式绑定的新 socket 使用新的 UID 默认网络；
- 新的主机名解析也使用新的默认网络；
- 旧 socket 仍与创建时的网络关联，不会被 `ConnectivityService` 搬到新网络；
- 旧网络稍后断开或系统关闭相关 socket 时，应用需要按协议语义恢复。

默认网络回调中的 `onLost(oldNetwork)` 表示该网络不再是该应用的默认网络；旧网络可能仍保持连接。`onLosing()` 也不是每次失去网络前都保证出现，恢复逻辑不能依赖它。

### 6.1 优先绑定单次操作

确有多网络需求时，可以从 `Network` 获取 socket factory、执行指定网络的 DNS，或在 socket 连接前调用 `Network.bindSocket()`。这比进程级绑定更容易控制作用范围。

下面的片段用于在指定网络上解析并创建新的 HTTP 连接：

```kotlin
val addresses = network.getAllByName("example.com")
val socketFactory = network.socketFactory
val socket = socketFactory.createSocket(addresses.first(), 443)
```

这段代码没有处理 TLS、连接超时和地址轮换，只用于说明 socket 与 DNS 可同时限定到同一个 `Network`。生产代码应交由支持 `Network` 绑定的网络栈完成完整协议处理。

`bindProcessToNetwork()` 会改变进程后续 socket 和 DNS 的默认网络，影响范围很大。调用前已连接的 socket不会迁移。除专用多网络组件外，不要用它修复普通网络切换。

### 6.2 按请求语义恢复

网络变化后，重试策略要区分：

- GET 等幂等请求可在退避和总超时范围内重试；
- 写请求需要业务 request ID、幂等键或服务端去重；
- WebSocket、HTTP/2 和 QUIC 的连接迁移能力取决于所用库与服务端；
- 上传、下载要保存校验信息和断点，不能只从 UI 进度推断服务端状态。

不要在 `onAvailable()` 中立即并发重放全部请求。可先等待目标业务需要的 capability，并由连接管理器控制重连速率。

## 7. `CONNECTIVITY_ACTION` 的准确边界

`CONNECTIVITY_ACTION` 在 API 中仍然存在，Android 17 源码也保留兼容路径。它已废弃，且面向 Android 7.0 及以上的应用不能依靠 manifest receiver 接收连接变化；运行时注册仍属于旧兼容方式。

新代码使用 `NetworkCallback`。默认网络回调能够表达当前应用在 VPN、企业策略或每 UID 路由下看到的网络，也避免把系统物理默认网络误当成应用默认网络。

把广播替换成回调后，仍要处理：

- 进程启动时已有默认网络，注册后会收到当前状态；
- capability 和 link properties 可在同一个 `Network` 对象存活期间多次变化；
- 回调没有固定到达毫秒数；
- 网络可用不等于业务服务健康，HTTP、TLS 和服务端错误需要独立处理。

## 8. Android 17 / API 37 变化

### 8.1 本地网络权限

面向 Android 17（target SDK 37）及以上的应用，直接访问本地网络默认受限。`android.permission.ACCESS_LOCAL_NETWORK` 是 `NEARBY_DEVICES` 权限组中的 dangerous runtime permission，不是安装时自动授予的普通权限。

直接 TCP/UDP、组播、广播、入站连接、mDNS 以及 `.local` 解析都可能受影响。产品有两种路径：

- 使用系统提供的设备或服务 picker，只访问用户选择的设备；
- 业务需要广泛 LAN 访问时，声明并在运行时请求权限，同时处理拒绝和撤销。

下面的 manifest 片段用于声明广泛本地网络访问：

```xml
<uses-permission android:name="android.permission.ACCESS_LOCAL_NETWORK" />
```

声明之后仍要执行运行时权限流程。target SDK 36 及以下的应用暂时通过 `INTERNET` 获得兼容访问，官方文档要求这类应用不要提前请求新权限。

文档：

- [Local network permission](https://developer.android.com/privacy-and-security/local-network-permission)
- [Android 17 behavior changes](https://developer.android.com/about/versions/17/behavior-changes-17)

### 8.2 流媒体套餐速率

Android 17 新增的公共 API 位于 `android.telephony.SubscriptionInfo`：

```kotlin
val maxDownKbps = subscriptionInfo.streamingAppMaxDownlinkKbps
val maxUpKbps = subscriptionInfo.streamingAppMaxUplinkKbps

if (maxDownKbps != SubscriptionPlan.BITRATE_UNKNOWN) {
    playerPolicy.updateCarrierStreamingLimitKbps(maxDownKbps)
}
```

返回值单位是 Kbps；`2000` 表示 2000 Kbps，约 2 Mbps。它表示运营商依据套餐为流媒体应用分配的上、下行上限，不是当前链路吞吐量。码率控制还要结合 buffer、传输采样、RTT、丢包和服务端策略。

原文把这两个方法放在 `NetworkStatsManager`，并用 `2_000_000` 判断 2 Mbps，类名与数量级都不正确。

源码与文档：

- [`SubscriptionInfo.java`](https://android.googlesource.com/platform/frameworks/base/+/refs/tags/android-17.0.0_r1/telephony/java/android/telephony/SubscriptionInfo.java)
- [`SubscriptionInfo` API](https://developer.android.com/reference/android/telephony/SubscriptionInfo)

### 8.3 DeliQueue 与网络回调

运行在 Android 17 且 target SDK 37 的应用默认使用 DeliQueue。Connectivity 默认回调所在的 `ConnectivityThread` 也有 Looper，因此会经过对应的 MessageQueue 实现。

DeliQueue 只改变消息队列的并发结构。它不会缩短 Wi-Fi 建链、蜂窝拨号、NetworkMonitor 验证、Binder 传输、DNS、TLS 或服务端响应时间，也不会让耗时 callback 变快。对网络切换的分析仍要按第 1 节的四段分别测量。实现与兼容开关见 1.13 和 1.26 节。

## 9. 流量统计不要依赖旧 `/proc/uid_stat`

Android 17 的流量统计以 netd/BPF 计数和 NetworkStats 的历史集合为主，不能继续描述成 `TrafficStats.getUidRxBytes()` 每次读取 `/proc/uid_stat/<uid>/tcp_rcv`。

两类 API 的用途不同：

| API | 适合用途 | 使用限制 |
|---|---|---|
| `TrafficStats` | 观察 UID 或线程 tag 的累计量和短区间差值 | 不是逐请求延迟工具，重启和不支持值要单独处理 |
| `NetworkStatsManager` | 按时间、订阅、网络模板查询历史用量 | 查询可能涉及 Binder、历史 bucket 与 I/O，应放在工作线程 |

高频轮询会增加唤醒和处理成本。采样周期从产品需要的时间分辨率倒推，并记录屏幕、前后台和网络类型，避免采集本身干扰功耗实验。

## 10. 可复现的排查方法

### 10.1 为业务路径加时间戳

至少记录以下事件：

1. 系统回调进入应用；
2. 快照发布给业务；
3. 重连或请求开始；
4. DNS 完成、连接完成、TLS 完成；
5. 首字节和业务成功；
6. 失败类型、当前 `Network`、capability 和 blocked 状态。

这些时间戳能区分“系统回调慢”和“回调后业务恢复慢”。不要只记录 `onAvailable()` 与最终成功两个点。

### 10.2 查看系统状态

下面的命令用于核对网络、验证、DNS、策略和路由：

```bash
adb shell dumpsys connectivity
adb shell dumpsys network_stack
adb shell dumpsys dnsresolver
adb shell dumpsys netd
adb shell dumpsys netpolicy
adb shell dumpsys netstats
adb shell ip rule
adb shell ip route show table all
```

不同 build 会隐藏敏感字段。保存诊断输出时要同时记录设备 build、UID、复现时刻和操作步骤。

### 10.3 用 Perfetto 判断队列归属

抓取 Binder、sched、应用自定义 trace 和网络相关数据：

- Binder 事务排队：查询或回调是否卡在跨进程边界；
- ConnectivityThread 的 runnable、sleeping 与执行区间：回调是否在应用进程积压；
- 主线程：状态发布后 UI 是否又被其他消息阻塞；
- NetworkStack 与系统线程：验证和系统调度是否有长等待；
- radio 与业务请求：网络激活成本和请求恢复是否重叠。

比较网络切换前后时，固定设备、SIM、Wi-Fi AP、信号控制方式、VPN、Data Saver、屏幕状态和应用版本。用多次样本的分位数描述结果，不写通用的“Wi-Fi 切蜂窝需要几秒”。

## 11. 交付前检查表

- [ ] 大多数页面共享一份默认网络 tracker，没有重复注册系统回调。
- [ ] callback 使用明确的 Handler，回调中没有磁盘 I/O、同步网络请求或长时间锁等待。
- [ ] `onAvailable()` 后使用后续 capability 与 link properties 回调，没有同步补查。
- [ ] 注册和注销使用同一个 callback 实例，Activity 重建后 request 数量不会增长。
- [ ] 观察网络使用 `registerNetworkCallback()`，主动拉起额外网络才使用 `requestNetwork()`。
- [ ] `onLost()` 与 `onLosing()` 没有被当成固定配对事件。
- [ ] 重试区分读请求、写请求和长连接，并有总超时与退避。
- [ ] `bindProcessToNetwork()` 只用于明确的进程级多网络需求。
- [ ] target SDK 37 的 LAN 功能已选择系统 picker 或运行时权限流程。
- [ ] 流媒体速率读取自 `SubscriptionInfo`，按 Kbps 和 unknown 值处理。
- [ ] TrafficStats 与 NetworkStatsManager 按各自口径使用，没有依赖 `/proc/uid_stat`。
