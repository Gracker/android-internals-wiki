# 2.52 Compose Pager 从基础到高级动画

`HorizontalPager` 与 `VerticalPager` 是 Compose Foundation 的懒布局组件。它们负责等尺寸 page 的组合、测量、滚动和吸附；页面内容仍由调用方提供。Pager 的状态模型比 `ViewPager2` 简洁，但“当前页”“停止页”“目标页”、可见 page、额外保留 page 和预取 page 各有不同语义。

本文以 **Compose Foundation 1.11.4 稳定版**为 API 与源码参考，以 **Paging Compose 3.5.0**说明分页数据示例。Android 12—17 是本知识库的验证范围，不是 Pager 的最低 API 声明。运行在 Android 17 / API 37 时，平台渲染部分仍以 `android-17.0.0_r1` 为准；Jetpack Compose 独立发布，不属于 AOSP platform tag。

## Pager 在 Android 17 出图链中的位置

普通 Compose Pager 仍属于标准 App Window 的 HWUI 出图类型。状态变化在 UI 线程触发 composition、layout 与 draw；Compose 生成的绘制内容交给 Android HWUI / RenderThread，窗口 buffer 经 BLASTBufferQueue 提交给 SurfaceFlinger，再由 HWC 与显示设备完成 present。

这条边界会影响工具选择：

- `graphicsLayer` 通常是 App Window 内部的绘制图层，不等于 SurfaceFlinger layer；
- `currentPage` 更新、composition 完成或 `queueBuffer()` 返回，都不等于画面已经 present；
- 页面中嵌入 SurfaceView、Camera preview、视频或 native engine 时，会出现独立 Producer 与 layer，不能只看 Pager 所在宿主窗口；
- Pager 卡顿应先区分 UI composition / layout、RenderThread / GPU、BufferQueue backpressure 与 SF / display 超时，再选择 Compose tracing、Perfetto 或 GPU 工具。

因此，Compose 的 recomposition count 只能解释应用生产阶段。用户可见帧是否按时，仍要与 FrameTimeline、窗口 buffer 和 display present 对齐。

## 1. 先固定依赖版本

“使用 Compose BOM”不能代替记录 artifact 版本。BOM 只为一组 Compose 依赖选择兼容版本，Pager 的公开 API 和内部预取行为仍由最终解析出的 `androidx.compose.foundation:foundation` 决定。

| 版本轴 | 本文使用值 | 负责的内容 |
|---|---|---|
| Android platform | Android 17 / API 37 / `android-17.0.0_r1` | Choreographer、HWUI、Surface、SurfaceFlinger 等平台实现 |
| Compose Foundation | `1.11.4` stable | Pager API、测量、预取、滚动和吸附 |
| Paging Compose | `3.5.0` | `LazyPagingItems`、`itemKey` 与加载状态 |
| Compose BOM | 由项目声明 | Maven 版本对齐，不定义单独的运行时机制 |

下面的 Gradle 命令用于确认应用最终解析到的 Foundation 版本：

```bash
./gradlew :app:dependencyInsight \
  --dependency androidx.compose.foundation \
  --configuration debugRuntimeClasspath
```

结果应记录到性能报告中。只记录 BOM 名称会遗漏依赖约束、版本覆盖和多模块解析差异。

## 2. `PagerState` 的四组状态

### 2.1 创建状态

下面的签名摘自 Foundation 1.11.4，用于说明三个初始化参数的约束：

```kotlin
@Composable
fun rememberPagerState(
    initialPage: Int = 0,
    initialPageOffsetFraction: Float = 0f, // [-0.5, 0.5]
    pageCount: () -> Int,
): PagerState
```

`pageCount` 是 lambda，`DefaultPagerState` 会持有最新 lambda 并在读取 `pageCount` 时调用它。数据数量变化后，Pager 会在后续测量中更新可滚动范围。调用方仍要处理空数据、当前对象被删除和业务选择状态迁移，不能把这些问题交给 `pageCount` 自动解决。

`initialPageOffsetFraction`、`scrollToPage()` 和 `animateScrollToPage()` 的 offset 参数都要求位于 `-0.5..0.5`。这个值描述目标 page 相对吸附位置的偏移，不是任意页面相对当前 page 的距离。

### 2.2 `currentPage`、`settledPage` 与 `targetPage`

| 属性 | 何时变化 | 适合用途 |
|---|---|---|
| `currentPage` | 最靠近 snap position 的 page 发生变化时 | 指示器、与滚动位置同步的视觉状态 |
| `settledPage` | 手势或动画结束后 | 页面曝光、选中项提交、一次性业务动作 |
| `targetPage` | fling 或编程滚动期间根据目标更新 | 预判将停靠的 page、轻量预热 |
| `currentPageOffsetFraction` | 滚动过程中高频变化，范围 `-0.5..0.5` | 绘制或图层变换，不宜直接驱动大范围组合 |

滚动一半附近时，`currentPage` 可能先切到新 page，而 `settledPage` 仍保留滚动开始前的 page。把曝光统计绑在 `currentPage` 上，往返拖动会产生多次事件。

下面的代码用于在一次滚动稳定后记录 page：

```kotlin
LaunchedEffect(pagerState) {
    snapshotFlow { pagerState.settledPage }
        .distinctUntilChanged()
        .collect { page ->
            analytics.recordPagerSettled(page)
        }
}
```

`snapshotFlow` 把 Compose state 读取转换为 Flow；`distinctUntilChanged()` 让业务语义在代码中可见。不要在 page Composable 每次重组时直接发送曝光。

## 3. 懒布局、额外 page 与预取

Pager 只为可见范围和当前策略需要的 page 建立内容。这里要区分三类对象：

1. **visible pages**：当前 viewport 内参与布局的 page；自定义 `PageSize` 时可能同时有多个。
2. **beyond-viewport pages**：由 `beyondViewportPageCount` 明确要求在可见范围前后额外组合、测量和放置的 page。
3. **prefetched pages**：滚动方向上的预取对象，不计入 `beyondViewportPageCount`。

Foundation 1.11.4 中 `PagerDefaults.BeyondViewportPageCount` 仍是 `0`，但 Pager 另有 prefetch / cache-window 逻辑。因此，`beyondViewportPageCount = 0` 不表示运行时永远只有当前 page 的 composition，也不能据此推断离屏资源已经立即释放。

### 3.1 不要给出固定“最佳值”

`beyondViewportPageCount` 增加一页，就会增加相应 page 的 composition、measure、placement 以及页面自身资源。纯文本、图片、地图、视频和嵌套列表的代价差别很大，不存在通用的“文本设 3、图片设 1”规则。

选择方法应以测量为准：

- 保持默认值，记录快速滑动时是否出现 composition / measure 长帧；
- 只增加一页，比较帧时间、内存、图片解码、网络和页面副作用；
- 若收益不足，回到默认值并优化 page 自身；
- 视频、地图、相机等重资源应以可见性和业务生命周期控制启停，不能依赖 composition 是否还存在。

### 3.2 `key` 负责对象身份

数据可能插入、删除或重排时，应使用稳定、唯一且可保存的业务 key。下面的示例让 Pager 在索引变化后继续识别同一个条目：

```kotlin
val pagerState = rememberPagerState(pageCount = { pages.size })

HorizontalPager(
    state = pagerState,
    key = { index -> pages[index].id },
) { index ->
    PageContent(pages[index])
}
```

Foundation 会按 key 尝试维持滚动对象。key 不能重复，也不要使用会随刷新变化的临时值。固定数据可以省略 key；显式写 `key = { it }` 仍然只是索引身份。

`rememberSaveable` 能否恢复还取决于 key 是否可由 Android `Bundle` 保存、状态内容是否有 Saver，以及页面是否仍属于同一个业务对象。不能把稳定 key 写成“所有页面状态永久保留”的保证。

## 4. 滚动动画：用页面距离，不要误读 offset fraction

### 4.1 两个 offset 不是一回事

`currentPageOffsetFraction` 只描述当前 page 到 snap position 的偏移，范围为 `-0.5..0.5`，切换 `currentPage` 时符号和基准都会改变。

Foundation 1.11.4 提供 `PagerState.getOffsetDistanceInPages(page)`，它返回指定 page 相对当前吸附状态的距离，可以大于一页。例如当前 page 为 1、fraction 为 0.2 时，page 2 的距离是 `0.8`。

旧文章常见的手算公式：

```text
(pagerState.currentPage - page) + pagerState.currentPageOffsetFraction
```

这个公式的符号方向与 `getOffsetDistanceInPages(page)` 相反。两者都能生成对称动画，但不要在同一组 rotation、translation 公式中混用。

### 4.2 把高频 state 读取留在图层阶段

下面的示例用 page 距离驱动透明度、缩放和 Y 轴旋转：

```kotlin
HorizontalPager(state = pagerState) { page ->
    Card(
        modifier = Modifier
            .fillMaxSize()
            .graphicsLayer {
                val offset = pagerState
                    .getOffsetDistanceInPages(page)
                    .coerceIn(-1f, 1f)
                val distance = offset.absoluteValue

                alpha = lerp(0.55f, 1f, 1f - distance)
                scaleX = lerp(0.90f, 1f, 1f - distance)
                scaleY = lerp(0.90f, 1f, 1f - distance)
                rotationY = -24f * offset
                cameraDistance = 12f * density
            },
    ) {
        PageContent(page)
    }
}
```

`graphicsLayer { ... }` 的 lambda 版本可以在图层属性更新时避开页面内容重组。若先在 Composable 正文读取 `currentPageOffsetFraction`，再把计算结果作为普通参数传给 modifier，所有依赖该读取的可见 page 都可能随每个滚动帧重组。

`alpha < 1`、旋转、阴影、clip 或 render effect 可能引入独立 graphics layer，某些组合还会使用离屏缓冲。动画是否流畅要同时检查 UI / RenderThread、GPU、内存带宽和 layer 数量，不能只看 recomposition count。

### 4.3 动画边界

- 对称淡入淡出通常使用 `absoluteValue`；
- 方向性翻页保留 offset 正负号；
- 对 alpha、scale 等参数做 `coerceIn()`，避免远处预取 page 得到负值或过度缩放；
- 3D rotation 会改变视觉形状，不会自动改变 hit test 区域和语义顺序；
- `cameraDistance` 使用像素语义，示例乘以 `density` 是为了让不同密度设备上的透视强度更接近。

## 5. Page size、padding、spacing 与 snap position

### 5.1 多 page viewport

下面的 `PageSize` 在可用空间中放三页，并把两段 page spacing 从尺寸预算中扣除：

```kotlin
val threePagesPerViewport = object : PageSize {
    override fun Density.calculateMainAxisPageSize(
        availableSpace: Int,
        pageSpacing: Int,
    ): Int = (availableSpace - 2 * pageSpacing) / 3
}

HorizontalPager(
    state = pagerState,
    pageSize = threePagesPerViewport,
    pageSpacing = 12.dp,
    snapPosition = SnapPosition.Center,
) { page ->
    PageCard(page)
}
```

此时 visible page 不再等于一个。`currentPage` 由最靠近 `SnapPosition.Center` 的 page 决定，测试和曝光逻辑也要按新的 snap position 解释。

### 5.2 `contentPadding` 与外部 padding

`contentPadding` 进入 Pager 的布局计算，可在首尾留出空间，也会影响 viewport、page position 与吸附计算。`Modifier.padding()` 改变 Pager 容器本身可用的约束。两者都能制造边缘留白，但测量语义不同。

边缘露出相邻 page 时，应一起设置 `contentPadding`、`pageSize` 和 `pageSpacing`，并在 LTR、RTL、横竖屏和 font scale 条件下检查。不要把某个固定 dp 数值称为 Material 的通用要求。

### 5.3 负 `pageSpacing`

当前 API 没有限制 `pageSpacing` 必须为非负数，负值可让 page 几何范围重叠。重叠后要验证绘制顺序、`zIndex`、手势命中、可访问性焦点和 clip。若设计只是卡片缩放或露边，优先使用 page size 与 padding；负 spacing 更适合经过专项测试的视觉效果。

## 6. Fling 与编程滚动

### 6.1 Fling 距离

默认 `PagerDefaults.flingBehavior()` 使用 `PagerSnapDistance.atMost(1)`。下面的配置允许一次 fling 的目标 page 最多离起始 page 三页：

```kotlin
val flingBehavior = PagerDefaults.flingBehavior(
    state = pagerState,
    pagerSnapDistance = PagerSnapDistance.atMost(3),
)

HorizontalPager(
    state = pagerState,
    flingBehavior = flingBehavior,
) { page ->
    PageContent(page)
}
```

`atMost(3)` 约束目标范围，不承诺中间 page 都会完整显示，也不会自动把 `beyondViewportPageCount` 改成 3。多页 fling 是否适合产品，要用触控距离、可预测性、内容加载和无障碍操作共同判断。

### 6.2 三种滚动入口

| API | 时机与语义 | 注意点 |
|---|---|---|
| `scrollToPage()` | suspend，立即跳到目标 page | 仍需等待 Pager 完成首次 layout |
| `animateScrollToPage()` | suspend，按 animation spec 滚动 | 远距离目标会先跳到较近 page，再完成剩余动画，避免组合所有中间 page |
| `requestScrollToPage()` | 请求下一次 remeasure 使用指定位置 | 会取消进行中的滚动，适合与数据集变化协调，不是普通点击导航的默认选择 |

Pager 的滚动基于 `ScrollableState` 的互斥变更。新的手势或滚动任务可能取消正在执行的 `animateScrollToPage()`；调用方应按协程取消语义清理业务状态，不要把 `CancellationException` 当成需要吞掉的普通错误。

## 7. 与 Paging 3 集成

Pager 可以消费 `LazyPagingItems`，但 Pager 的 page 与 Paging 的 loaded page 不是同一概念。前者是 UI 索引，后者是 PagingSource 的数据批次。

下面的示例使用 Paging 提供的 `itemKey()`，同时为 placeholder 保留稳定 key：

```kotlin
val lazyItems = viewModel.items.collectAsLazyPagingItems()
val pagerState = rememberPagerState(pageCount = { lazyItems.itemCount })

HorizontalPager(
    state = pagerState,
    key = lazyItems.itemKey { item -> item.id },
) { index ->
    when (val item = lazyItems[index]) {
        null -> PagePlaceholder(index)
        else -> PageContent(item)
    }
}
```

`lazyItems[index]` 会通知 Paging 本次访问，并可能按 `prefetchDistance` 触发加载；`peek(index)` 只读取当前已呈现值，不触发这类访问通知。`itemCount` 在 placeholder 开启时可包含尚未加载的索引，所以 page 内容必须处理 `null` 与 `loadState`。

Pager 的预取与 Paging 的预取会叠加。增加 `beyondViewportPageCount` 可能更早访问 `LazyPagingItems`，继而增加数据加载、图片请求和内存。调参时要把 composition、Paging load、网络、解码与缓存命中放在同一条时间线上。

## 8. 嵌套 Pager 与页面副作用

### 8.1 嵌套滚动

水平 Pager 内嵌垂直 Pager 时，两个方向通常可以由手势方向判定各自处理。相同方向的 Pager、Pager 中的同向 LazyRow，或可缩放内容，会出现更复杂的手势竞争。

`pageNestedScrollConnection` 控制 Pager 如何消费子组件传来的 nested scroll delta；默认实现会消费对应方向的 nested delta。是否需要自定义 connection 取决于产品对边界继续滚动、fling 传递和父子吸附的要求。仅添加一个空泛的 `Modifier.nestedScroll()` 不能自动解决同向手势归属。

嵌套页面数量也不能用“外层 2 × 内层 2 = 9”推算。可见页数、beyond-viewport 数量、预取方向、子 Pager 是否已组合和每页内容状态都会改变存活对象。

### 8.2 页面可见性与资源启停

Composable 进入 composition 不等于用户正在观看该页，离开 viewport 也不保证对象立刻销毁。视频、地图、相机和传感器应依据清晰的产品状态启停，例如：

- 使用 `settledPage` 决定唯一主播放页；
- 使用 `layoutInfo.visiblePagesInfo` 判断可见集合，但避免在 composition 中直接高频读取；
- 用 `snapshotFlow` 收集可见集合变化；
- 用 `DisposableEffect(itemId)` 绑定确需跟随对象身份的资源；
- Activity / Lifecycle 停止时仍要释放或暂停外部资源。

## 9. 性能诊断

### 9.1 常见现象与证据

| 现象 | 可能原因 | 应查看的证据 |
|---|---|---|
| 拖动时所有 page 高频重组 | 在 Composable 正文读取 offset、参数不稳定、父层 state 范围过大 | Layout Inspector、Compose tracing、compiler stability report |
| 新 page 进入时长帧 | 首次 composition / measure、图片解码、同步 I/O、复杂初始化 | Perfetto UI thread、RenderThread、I/O、应用 trace section |
| fling 周期性停顿 | page 生产慢、Paging 加载、buffer / GPU 压力、nested scroll | FrameTimeline、sched、Compose trace、网络 / Paging marker |
| 动画 CPU 正常但 GPU 完成晚 | 多 graphics layer、overdraw、离屏缓冲、图片面积过大 | Perfetto GPU completion、HWUI、AGI / 厂商工具 |
| 内存随滑动持续增长 | 图片缓存、播放器 / 地图资源、页面副作用未释放、预取过多 | heap dump、heapprofd、资源实例计数 |
| page 插入后位置跳动 | 缺少稳定 key、业务选择仍按索引保存 | Pager key、数据 diff、当前业务 ID |

### 9.2 测量顺序

1. 使用 release 或接近 release 的 profileable 构建，避免用 debug 性能代表用户版本。
2. 用 Macrobenchmark 固定启动状态、手势脚本和测试设备，收集 `FrameTimingMetric`。
3. 用 Perfetto 对齐 MainThread、RenderThread、FrameTimeline、I/O 与应用 trace section。
4. 若指向 Compose composition / layout，再看 Compose tracing 与 Layout Inspector。
5. 若 producer 及时而 GPU completion 晚，再使用 GPU 工具分析图层、overdraw、纹理与 shader。
6. 每次只调整一项：page 内容、key、offset 读取位置、beyond count、Paging prefetch 或图层效果。

Layout Inspector 的 recomposition count 适合定位候选范围，不是发布构建的性能分数。帧是否按时交付仍要由 frame timing 与系统 trace 判断。

## 11. 版本演进与资料

- Compose Foundation 1.7 是旧稿的最低写作基线，但不能代表 2026 年 Pager 的全部行为。
- Foundation 1.9 引入 `PagerScope` 和页面距离工具；当前 API 使用 `getOffsetDistanceInPages()`。
- Foundation 1.10 系列将 `currentPageOffsetFraction` 标注为高频变化值，并试验 cache-window prefetch；该系列后续又调整过 rollout flag，不能只凭主版本号推断设备上的预取行为。
