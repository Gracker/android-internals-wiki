# 8.10 Android 17 PowerManager 性能优化实战

PowerManager 是 Android 电源管理的核心入口：WakeLock 申请/释放、屏幕亮度控制、Doze/Standby 模式管理、热状态监听——全部经由此 API 暴露。与 §5.22（内核 wakelock 机制）聚焦内核层不同，本章关注 **应用层 WakeLock 的性能开销、LowPowerStandby 新机制，以及热管理 API 对应用性能的影响**。

> 详见 §5.22 内核 wakelock 与 suspend 流程，§5.1 CPU 调度与功耗

## 要点

### 🔹 WakeLock 类型与性能影响

Android 17 中 PowerManager 定义了 5 种 WakeLock 级别：

| WakeLock 类型 | 值 | CPU | 屏幕 | 键盘灯 | 典型用途 | 功耗影响 |
|--------------|-----|-----|------|--------|---------|---------|
| `PARTIAL_WAKE_LOCK` | 0x1 | ✅ 保持运行 | ❌ | ❌ | 后台音乐、下载 | 中 — CPU 可运行但屏幕关闭 |
| `SCREEN_DIM_WAKE_LOCK` | 0x6 | ✅ | 💡 暗光 | ❌ | 已废弃 | 高 |
| `SCREEN_BRIGHT_WAKE_LOCK` | 0xa | ✅ | 💡 亮光 | ❌ | 已废弃 | 很高 |
| `FULL_WAKE_LOCK` | 0x1a | ✅ | 💡 亮光 | ✅ | 已废弃 | 很高 |
| `DRAW_WAKE_LOCK` | 0x80 | ✅ | 💡 亮光 | ❌ | DOZE 模式下绘制 | 高 |

[已验证: AOSP android-17.0.0_r1, frameworks/base/core/java/android/os/PowerManager.java:91-193]

**关键变化**：`SCREEN_DIM_WAKE_LOCK`、`SCREEN_BRIGHT_WAKE_LOCK`、`FULL_WAKE_LOCK` 在 Android 13+ 已标记废弃。Google 推荐使用 `WindowManager.LayoutParams.FLAG_KEEP_SCREEN_ON` 替代屏幕相关 WakeLock，该方案不需要权限且自动随 Activity 生命周期释放。

```kotlin
// ❌ 废弃做法：使用屏幕 WakeLock
val wakeLock = powerManager.newWakeLock(
    PowerManager.SCREEN_BRIGHT_WAKE_LOCK or PowerManager.ACQUIRE_CAUSES_WAKEUP,
    "MyApp::ScreenOn"
)
wakeLock.acquire()

// ✅ 推荐做法：使用 FLAG_KEEP_SCREEN_ON
window.addFlags(WindowManager.LayoutParams.FLAG_KEEP_SCREEN_ON)
// 或在 XML 中
// android:keepScreenOn="true"
```

**`PARTIAL_WAKE_LOCK` 是唯一推荐应用使用的 WakeLock 类型**——它保持 CPU 运行但允许屏幕关闭，适用于后台任务。但 PARTIAL_WAKE_LOCK 也是后台功耗泄漏的最大来源。

### 🔹 WakeLock 引用计数与泄漏检测

Android 17 的 WakeLock 默认使用引用计数（`mRefCounted = true`）。多次 `acquire()` 需要等量 `release()` 才能真正释放：

```java
// PowerManager.WakeLock 内部实现 (android-17.0.0_r1)
private void acquireLocked() {
    mInternalCount++;
    mExternalCount++;
    if (!mRefCounted || mInternalCount == 1) {
        // 实际向 PowerManagerService 注册 wakelock
        mService.acquireWakeLock(mToken, mFlags, mTag, mPackageName, ...);
        mHeld = true;
    }
}

public void release(int flags) {
    synchronized (mToken) {
        if (mInternalCount > 0) { mInternalCount--; }
        if ((flags & RELEASE_FLAG_TIMEOUT) == 0) { mExternalCount--; }
        if (!mRefCounted || mInternalCount == 0) {
            // 实际向 PowerManagerService 释放 wakelock
            mService.releaseWakeLock(mToken, flags);
            mHeld = false;
        }
        if (mRefCounted && mExternalCount < 0) {
            throw new RuntimeException("WakeLock under-locked " + mTag);
        }
    }
}
```

[已验证: AOSP android-17.0.0_r1, frameworks/base/core/java/android/os/PowerManager.java:4354-4434]

**性能陷阱**：

1. **`finalize()` 兜底释放**：WakeLock 的 finalize 方法会检测 `mHeld == true` 并调用 `mService.releaseWakeLock()`，同时输出 `Log.wtf(TAG, "WakeLock finalized while still held: " + mTag)`。这意味着未释放的 WakeLock 在 GC 时才会被回收，期间 CPU 保持唤醒状态。从 ART GC 的延迟来看，这可能持续数秒到数分钟。

2. **`under-locked` 异常**：如果 `release()` 调用次数超过 `acquire()`，会抛出 `RuntimeException("WakeLock under-locked")`。这通常发生在异步任务中 acquire 后、任务取消但 release 仍被执行的场景。

3. **超时 WakeLock 的内部机制**：`acquire(long timeout)` 通过 `mHandler.postDelayed(mReleaser, timeout)` 实现自动释放。`mReleaser` 调用 `release(RELEASE_FLAG_TIMEOUT)`，其中 `RELEASE_FLAG_TIMEOUT` 标志确保超时释放不会递减 `mExternalCount`（只有显式 release 才递减外部计数）。

**最佳实践**：

```kotlin
class SafeWakeLock(
    private val wakeLock: PowerManager.WakeLock,
    private val tag: String
) : AutoCloseable {

    fun acquire(timeoutMs: Long? = null) {
        synchronized(wakeLock) {
            if (!wakeLock.isHeld) {
                if (timeoutMs != null) {
                    wakeLock.acquire(timeoutMs)
                } else {
                    // 默认 10 分钟超时，防止永久泄漏
                    wakeLock.acquire(10 * 60 * 1000L)
                }
            }
        }
    }

    fun release() {
        synchronized(wakeLock) {
            if (wakeLock.isHeld) {
                try {
                    wakeLock.release()
                } catch (e: RuntimeException) {
                    if (e.message?.contains("under-locked") == true) {
                        Log.w(TAG, "WakeLock under-locked: $tag")
                    } else throw e
                }
            }
        }
    }

    override fun close() = release()
}
```

### 🔹 Binder IPC 开销分析

每次 `acquire()` / `release()` 都是一次 Binder 调用到 system_server 的 PowerManagerService：

```java
// acquire 路径
mService.acquireWakeLock(mToken, mFlags, mTag, mPackageName, mWorkSource, mHistoryTag, mDisplayId, mCallback);
// release 路径
mService.releaseWakeLock(mToken, flags);
```

**单次 Binder 开销**：5-50μs（取决于是同步还是 oneway）。WakeLock 的 acquire/release 是同步调用（非 oneway），因为调用方需要确认状态变更已生效。

**性能影响**：高频 acquire/release（如每秒多次）会产生显著的 Binder 开销。典型场景：传感器数据采集中每次采样都 acquire/release WakeLock。

```kotlin
// ❌ 高频 acquire/release
sensorManager.registerListener(object : SensorEventListener {
    override fun onSensorChanged(event: SensorEvent) {
        val wakeLock = powerManager.newWakeLock(PARTIAL_WAKE_LOCK, "Sensor::Poll")
        wakeLock.acquire()  // 每次采样都创建 + acquire
        try {
            processData(event)
        } finally {
            wakeLock.release()  // 立即 release
        }
    }
}, sensor, SensorManager.SENSOR_DELAY_FASTEST)

// ✅ 批量处理，单次 WakeLock
val wakeLock = powerManager.newWakeLock(PARTIAL_WAKE_LOCK, "Sensor::Batch")
wakeLock.acquire(30 * 1000L) // 30 秒超时
sensorManager.registerListener(object : SensorEventListener {
    override fun onSensorChanged(event: SensorEvent) {
        processData(event) // 在同一个 WakeLock 保护下批量处理
    }
}, sensor, SensorManager.SENSOR_DELAY_FASTEST)
// 在批量处理完成或超时后释放
```

### 🔹 LowPowerStandby：Android 15+ 的新功耗模式

Android 15 引入 LowPowerStandby 模式，Android 17 进一步增强了 API。LowPowerStandby 是介于 Doze 和屏幕关闭之间的中间状态——屏幕关闭且设备空闲时，系统限制后台网络和计算活动，但允许已声明的应用继续运行。

**关键 API（android-17.0.0_r1）**：

```java
// 检查设备是否支持 LowPowerStandby
public boolean isLowPowerStandbySupported();

// 检查/设置 LowPowerStandby 启用状态
public boolean isLowPowerStandbyEnabled();
public void setLowPowerStandbyEnabled(boolean enabled);

// 检查当前应用是否被豁免
public boolean isExemptFromLowPowerStandby();

// 设置 LowPowerStandby 策略
public void setLowPowerStandbyPolicy(@Nullable LowPowerStandbyPolicy policy);

// 维护端口在 LowPowerStandby 期间保持打开
public LowPowerStandbyPortsLock newLowPowerStandbyPortsLock(
        @NonNull List<LowPowerStandbyPortDescription> ports);
```

[已验证: AOSP android-17.0.0_r1, frameworks/base/core/java/android/os/PowerManager.java:2698-2911]

**性能意义**：需要持续网络连接的应用（如 VoIP、即时通讯）可以使用 `LowPowerStandbyPortsLock` 在待机期间保持特定端口打开，无需申请 PARTIAL_WAKE_LOCK 维持整个 CPU。这显著降低了待机功耗。

[待验证: LowPowerStandbyPortsLock 在实际设备上的功耗节省数据]

### 🔹 热管理 API 与性能降级

PowerManager 暴露了热状态监听 API，应用可以感知设备温度并主动降级：

```java
// 获取当前热状态
public int getCurrentThermalStatus();
// 热状态值：THERMAL_STATUS_NONE(0) → LIGHT(1) → MODERATE(2) → SEVERE(3)
//         → CRITICAL(4) → EMERGENCY(5) → SHUTDOWN(6)

// 注册热状态监听器
public void addThermalStatusListener(@NonNull OnThermalStatusChangedListener listener);
```

**性能降级策略**：

| 热状态 | 推荐策略 | 帧率影响 |
|--------|---------|---------|
| NONE | 正常运行 | 60fps |
| LIGHT | 降低后台任务频率 | 60fps |
| MODERATE | 降低视频质量、减少线程池大小 | 60fps |
| SEVERE | 停止非必要后台任务 | 30-45fps |
| CRITICAL | 仅保留核心功能 | 30fps |
| EMERGENCY | 最小化 CPU 使用 | 15-24fps |

```kotlin
powerManager.addThermalStatusListener { status ->
    when (status) {
        PowerManager.THERMAL_STATUS_NONE,
        PowerManager.THERMAL_STATUS_LIGHT -> {
            videoPlayer.setQuality(VideoQuality.AUTO)
            threadPoolSize = Runtime.getRuntime().availableProcessors()
        }
        PowerManager.THERMAL_STATUS_MODERATE -> {
            videoPlayer.setQuality(VideoQuality.MEDIUM)
            threadPoolSize = (Runtime.getRuntime().availableProcessors() * 0.5).toInt()
        }
        PowerManager.THERMAL_STATUS_SEVERE,
        PowerManager.THERMAL_STATUS_CRITICAL -> {
            videoPlayer.setQuality(VideoQuality.LOW)
            threadPoolSize = 2
            // 暂停非关键的后台同步
            backgroundSyncManager.pause()
        }
    }
}
```

### 🔹 Doze 模式与应用适配

Android 6+ 引入 Doze 模式，Android 17 维持其核心机制。Doze 限制所有后台活动（网络、Wakelock、Alarm、JobScheduler），仅在维护窗口期放行。

**Doze 的三级状态机**：

```
屏幕关闭 + 静止 → Doze_IDLE（深度休眠）
                    ↓ 维护窗口（定期开放）
                Doze_IDLE_MAINTENANCE（短暂唤醒）
                    ↓ 长时间静止
                Doze_LIGHT_IDLE（轻度休眠，限制更少但仍有约束）
```

**应用层的 Doze 适配策略**：
1. 使用 `JobScheduler` 替代 AlarmManager — 系统会在维护窗口批量执行
2. 使用 FCM（Firebase Cloud Messaging）替代轮询 — 高优先级 FCM 可穿透 Doze
3. `setExactAndAllowWhileIdle()` 用于必须精确触发的闹钟（每个应用每天 2 次限制）

## 扩展

### 🔸 PowerHint 系统级性能提示

`PowerManager.powerHint()` 允许系统向底层发送性能提示（如游戏启动、视频播放开始），触发 CPU/GPU 频率提升。此 API 为 SystemAPI，普通应用无法直接调用，但可以通过 `Window.setSustainedPerformanceMode()` 或 `GameMode` 间接影响。

### 🔸 LocationTracking WakeLock

Android 17 中 `PARTIAL_WAKE_LOCK` 配合位置服务使用时，系统会额外跟踪 wakelock 的持有者。通过 `WakeLock.setWorkSource(WorkSource)` 可以将 wakelock 归因到具体的发起应用（适用于系统应用或代理场景），便于 BatteryStats 精确统计。

[待验证: WorkSource 在 Android 17 中是否有新增字段]

### 🔸 WakeLockStateListener 新接口

Android 17 新增了 `WakeLockStateListener` 接口，允许监听 WakeLock 被系统强制启用/禁用的状态变化：

```java
public interface WakeLockStateListener {
    void onWakeLockStateEnabled();
    void onWakeLockStateDisabled();
}
```

这为系统级的电源管理干预提供了感知机制——当 PowerManagerService 因全局策略（如过热、电量不足）强制禁用某个 WakeLock 时，应用可以收到通知并做出适配。
