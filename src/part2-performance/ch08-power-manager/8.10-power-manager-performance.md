# 8.10 Android 17 PowerManager 性能优化实战

[适用版本：Android 14（API 34）至 Android 17（API 37）]

`PowerManager` 让应用查询电源、空闲和热状态，也提供 WakeLock。它不负责 JobScheduler、AlarmManager、Doze、App Standby 和 Low Power Standby 的全部策略；这些机制会在 `PowerManagerService`、DeviceIdle、NetworkPolicy、AlarmManager 和任务调度器之间协作。

本章以 `android-17.0.0_r1` 为平台锚点，重点回答三个应用问题：什么时候需要手工 WakeLock、为什么持有 WakeLock 仍可能不执行、怎样把热降级和功耗结论做成可验证结果。

---

## 1. 先选择替代 API

手工 partial WakeLock 直接延长设备不能 suspend 的时间。多数任务已有系统托管的唤醒方式：

| 需求 | 优先选择 | 是否还要手工 WakeLock |
|---|---|---|
| 页面阅读、视频画面保持亮屏 | `View.setKeepScreenOn()`、`android:keepScreenOn` 或 `FLAG_KEEP_SCREEN_ON` | 不需要 |
| 可延期且要求完成的后台任务 | WorkManager 或 JobScheduler | 调度器执行任务时管理并归因 WakeLock |
| 用户发起的长时间上传、下载 | 对应的用户发起数据传输 API | 由专用机制管理 |
| 音频播放 | Audio/Media3 的 wake mode | 由媒体栈管理 |
| 定时触发 | 合适类型的 AlarmManager alarm | Alarm 投递期间由系统管理 |
| 传感器唤醒 | wake-up sensor 与 batching | 通常不需要按每条事件加锁 |
| 前台服务中的短暂、不可中断 CPU 工作 | 先确认没有专用 API | 可能需要短时 partial WakeLock |

前台服务不会自动让 CPU 始终保持运行。反过来，显示 FGS 通知也不能把不合规的后台工作变成合理 WakeLock 用例。任务既不要求用户即时感知，也允许系统稍后完成时，应交给系统调度。

文档：[Choose the right API to keep the device awake](https://developer.android.com/develop/background-work/background-tasks/awake)

## 2. 应用能够使用哪些 WakeLock

Android 17 源码中有多种 wake lock level，但可见常量不等于普通应用都适合使用：

| Level | 平台语义 | 应用侧边界 |
|---|---|---|
| `PARTIAL_WAKE_LOCK` | 允许屏幕关闭，阻止 CPU suspend | 手工 WakeLock 的主要应用级用途，需要 `WAKE_LOCK` 权限 |
| `SCREEN_DIM_WAKE_LOCK` | 保持屏幕点亮，可变暗 | API 17 起废弃，使用 window/view 的 keep-screen-on |
| `SCREEN_BRIGHT_WAKE_LOCK` | 保持屏幕高亮 | API 17 起废弃 |
| `FULL_WAKE_LOCK` | 保持屏幕和键盘背光 | API 17 起废弃 |
| `PROXIMITY_SCREEN_OFF_WAKE_LOCK` | 近距离传感器触发时关闭屏幕 | 设备不一定支持，先调用 `isWakeLockLevelSupported()` |
| `DOZE_WAKE_LOCK`、`DRAW_WAKE_LOCK` | Dream、WindowManager 等系统 doze 路径 | hidden 且需要 `DEVICE_POWER`，普通 SDK 应用不能使用 |

原文把 `DRAW_WAKE_LOCK` 当作普通应用的第五种 WakeLock，并称屏幕 WakeLock 从 Android 13 才废弃，这两处都与 API 注解不符。

保持 Activity 屏幕点亮时，下面的写法不需要 `WAKE_LOCK` 权限：

```kotlin
override fun onCreate(savedInstanceState: Bundle?) {
    super.onCreate(savedInstanceState)
    window.addFlags(WindowManager.LayoutParams.FLAG_KEEP_SCREEN_ON)
}
```

Activity 不再可见时，WindowManager 会按窗口状态处理该 flag。后台 Service 不能用它维持屏幕；这类需求通常需要重新检查产品交互。

源码锚点：[`PowerManager.java`](https://android.googlesource.com/platform/frameworks/base/+/refs/tags/android-17.0.0_r1/core/java/android/os/PowerManager.java#91)

## 3. 手工 partial WakeLock 的安全边界

### 3.1 引用计数和超时是两套状态

`PowerManager.WakeLock` 默认引用计数：

- 第一次 `acquire()` 才向 `PowerManagerService` 注册；
- 后续 `acquire()` 增加内部计数；
- 相同次数的 `release()` 完成后，服务端 WakeLock 才释放；
- 多释放一次会抛出 `WakeLock under-locked`。

`acquire(timeout)` 会在当前进程的 Handler 上安排 `mReleaser`，超时后使用 `RELEASE_FLAG_TIMEOUT` 释放。超时属于故障上限，不能替代 `finally`。进程线程严重阻塞时，定时 Runnable 自身也可能晚于请求时间执行。

对象被终结时，源码会记录 `WakeLock finalized while still held` 并尝试释放。GC 和 finalization 没有及时性保证，不能作为资源管理方案。

### 3.2 一个简单、可审计的持有区间

下面的辅助函数只适合单个同步工作区间。它为每次操作创建独立、非引用计数的 WakeLock，设置故障超时，并在 `finally` 释放：

```kotlin
inline fun <T> PowerManager.withPartialWakeLock(
    tag: String,
    timeoutMs: Long,
    block: () -> T,
): T {
    val wakeLock = newWakeLock(PowerManager.PARTIAL_WAKE_LOCK, tag).apply {
        setReferenceCounted(false)
    }

    wakeLock.acquire(timeoutMs)
    return try {
        block()
    } finally {
        if (wakeLock.isHeld) {
            wakeLock.release()
        }
    }
}
```

调用方还要满足四个条件：

- tag 使用稳定的包名、类名或用途，不放用户标识和动态 ID；
- `timeoutMs` 来自该操作的故障预算，不能随意写成十分钟；
- `block` 不等待无界网络、用户输入或永不完成的 callback；
- 任务取消、异常和提前返回都经过 `finally`。

不要捕获并吞掉 under-lock 异常。它表示 acquire/release 所有权已经出错，隐藏异常会让后续持有状态更难判断。

### 3.3 高频 acquire/release 也要看持有语义

WakeLock 的服务端状态变化经过 Binder。引用计数模式下，重复 acquire 不一定每次发 Binder；非引用计数模式会在 acquire 路径重新向服务端申请。无论哪种模式，都没有适用于所有设备的固定微秒开销。

优化重点不应停在 Binder 次数。需要同时问：

- 这批事件能否由 wake-up sensor、batching、JobScheduler 或媒体 API托管？
- 工作是否可以合并，让设备少经历几次唤醒和 suspend/resume？
- WakeLock 持有期间是否在等待网络、锁或空队列？
- 相同 tag 的持有时长分布是否随版本增长？

按每条传感器事件创建 WakeLock，会增加对象、Binder 和电源状态管理成本，也容易延长设备活跃时间。对传感器采集，先使用 `maxReportLatencyUs` 进行 batching，再把上传和处理交给合适的调度器。

## 4. `isHeld()` 不等于当前仍能阻止 suspend

`WakeLock.isHeld()` 描述客户端对象是否处于 acquired 且尚未 release 的状态。系统可能因为 Low Power Standby、allowlist 变化、配额或 cached 进程策略把 WakeLock 的有效状态禁用，此时客户端仍可能认为对象处于 held。

`WakeLockStateListener` 用于观察有效状态变化。它从 API 33 已存在，不是 Android 17 新接口；方法签名是 `onStateChanged(boolean enabled)`，原文中的 `onWakeLockStateEnabled()` 与 `onWakeLockStateDisabled()` 不存在。

下面的代码用于把“已申请”和“当前有效”分别记录：

```kotlin
val wakeLock = powerManager.newWakeLock(
    PowerManager.PARTIAL_WAKE_LOCK,
    "com.example.sync:commit",
)

wakeLock.setStateListener(backgroundExecutor) { enabled ->
    powerDiagnostics.recordWakeLockEffectiveState(enabled)
}
```

listener 只提供状态通知，不能让被系统禁用的 WakeLock重新生效。业务正确性仍要允许暂停、取消或稍后恢复。

源码锚点：[`WakeLockStateListener`](https://android.googlesource.com/platform/frameworks/base/+/refs/tags/android-17.0.0_r1/core/java/android/os/PowerManager.java#4215)

## 5. Low Power Standby 的公开能力与系统能力

Low Power Standby（LPS）从 Android 13 / API 33 提供公开查询。启用时，设备非交互且位于 device-idle 维护窗口之外，受限应用的网络访问会被禁用，WakeLock 会被忽略；普通 FGS 也不自动豁免。

Android 17 中要区分以下 API：

| API | 普通应用是否可用 | 说明 |
|---|---|---|
| `isLowPowerStandbyEnabled()` | 可用 | 只返回全局 enabled，不表示 LPS 此刻 active |
| `isExemptFromLowPowerStandby()` | 可用，API 34+ | LPS 关闭时也返回 true |
| `isAllowedInLowPowerStandby(reason/feature)` | 可用，API 34+ | 查询 policy 是否允许某个 reason 或 feature |
| `isLowPowerStandbySupported()` | System API + 特权权限 | 普通 SDK 应用不能用来判断设备能力 |
| `setLowPowerStandbyEnabled()`、`setLowPowerStandbyPolicy()` | System API + 特权权限 | 供系统管理组件使用 |
| `newLowPowerStandbyPortsLock()` | System API + `SET_LOW_POWER_STANDBY_PORTS` | 只有调用包已获 LPS 豁免等条件满足时才生效 |

普通 VoIP 或即时通讯应用不能申请 ports lock 保持端口开放。它既是受权限保护的 System API，也要求调用包已被 policy 豁免。产品代码应通过公开查询理解当前策略，并用系统认可的通话、消息或调度机制工作。

源码锚点：

- [`PowerManager.java`](https://android.googlesource.com/platform/frameworks/base/+/refs/tags/android-17.0.0_r1/core/java/android/os/PowerManager.java#2698)
- [`LowPowerStandbyController.java`](https://android.googlesource.com/platform/frameworks/base/+/refs/tags/android-17.0.0_r1/services/core/java/com/android/server/power/LowPowerStandbyController.java)

## 6. Doze、App Standby 与 LPS 要分别归因

三种机制名称接近，触发范围不同：

| 机制 | 主要对象 | 典型限制 |
|---|---|---|
| Doze / device idle | 设备级 | 网络暂停、WakeLock 被忽略、Job/Sync/普通 Alarm 延后 |
| App Standby | 长期未使用的应用 | 主要延后后台网络和任务机会 |
| Low Power Standby | 设备级，按 UID 豁免 | 非交互阶段进一步限制网络和 WakeLock |

Doze 有 light idle 与 deep idle 两套状态推进。原文画出的 `Doze_IDLE → maintenance → Doze_LIGHT_IDLE` 不是 Android 17 的正确状态顺序。应用无需依赖内部状态名，只需验证公开行为：

- 普通 Job、WorkManager、sync 和 Alarm 会延后到允许的执行窗口；
- `setAndAllowWhileIdle()` 与 `setExactAndAllowWhileIdle()` 只用于确有用户价值的时刻；官方 Doze 文档说明每应用不能频于约九分钟一次，系统还可能应用其他约束；
- FCM 高优先级只用于会产生及时、用户可见通知的消息，不能用于后台轮询；
- 退出 idle 后，任务必须能从持久状态恢复。

Doze 期间持有 partial WakeLock 也可能被系统忽略。用“WakeLock 已 acquire”解释任务必定持续运行，会在真实待机场景下失效。

文档：[Optimize for Doze and App Standby](https://developer.android.com/training/monitoring-device-state/doze-standby)

## 7. 热状态用于策略输入，不用于硬编码帧率

`getCurrentThermalStatus()` 和 `OnThermalStatusChangedListener` 提供从 `NONE` 到 `SHUTDOWN` 的离散严重程度。状态来自设备 Thermal HAL 和厂商热策略，同一个状态在不同 SoC、散热结构与室温下可能对应不同 CPU、GPU、显示或充电限制。

不能从 `SEVERE` 推导出固定 30—45 fps，也不该在 `CRITICAL` 时对所有应用统一设置两个线程。降级动作需要按功能和设备实验设计：

| 工作负载 | 可调旋钮 | 用户可观察指标 |
|---|---|---|
| 游戏或实时渲染 | 目标帧率、分辨率、特效、后台资源加载 | 帧时间、卡顿、输入延迟 |
| 视频播放或转码 | 码率、分辨率、编码并发 | buffer、掉帧、完成时间 |
| 相机和视觉算法 | 分析帧率、模型、分辨率 | 预览流畅度、识别延迟 |
| 本地生成式模型 | 上下文、输出上限、并发、模型档位 | 首 token、token 速率、取消率 |
| 后台同步 | 批量、并发、重试节奏 | 完成时间、网络与能耗 |

下面的 listener 只把热状态交给产品自己的策略对象，callback 不执行昂贵切换：

```kotlin
powerManager.addThermalStatusListener(backgroundExecutor) { status ->
    thermalPolicy.onStatusChanged(status)
}
```

策略对象应做去抖和恢复滞后，避免温度在阈值附近变化时频繁切换质量。降级阈值由同一设备上的温度、帧时间、功耗和用户体验实验共同确定。

`getThermalHeadroom(forecastSeconds)` 可提供 0 至 60 秒预测；返回 `NaN` 表示设备不支持或暂时无法提供。调用频率明显高于每秒一次可能得到 `NaN`，它不适合每帧轮询。

源码锚点：[`PowerManager thermal APIs`](https://android.googlesource.com/platform/frameworks/base/+/refs/tags/android-17.0.0_r1/core/java/android/os/PowerManager.java#2989)

## 8. PowerManager 不是普通应用的提频开关

`PowerManager.powerHint()` 属于隐藏或系统侧接口，普通应用不能用它请求 CPU/GPU 提频。`Window.setSustainedPerformanceMode()` 只在声明支持的设备上提供持续性能模式，也不是任意 boost。

需要向系统表达工作负载时，使用对应公开 API：

- 实时线程和工作周期：ADPF `PerformanceHintManager`；
- 游戏：Game Mode 与游戏适配 API；
- Surface 帧率：frame rate / refresh rate API；
- 媒体：MediaCodec、Audio 和 Media3 的专用能力；
- 后台工作：JobScheduler、WorkManager 或用户发起数据传输。

这些 API 能表达用途和生命周期，系统仍会受 thermal、battery saver 和硬件能力约束。

## 9. 从“耗电高”定位到具体 WakeLock

### 9.1 建立测试条件

功耗结果至少记录：

- 设备型号、Android build、目标 API 和电池状态；
- 屏幕、亮度、网络、信号、温度和充电状态；
- 测试时长、操作脚本、账号和数据规模；
- 进程是否被杀、任务是否成功完成；
- WakeLock tag、获取次数、总持有时长和最长单次持有。

“Binder 单次多少微秒”或“持锁必然增加多少毫安”不能跨设备复用。对照实验应保持业务完成量一致，避免省电版本只是少做了工作。

### 9.2 系统工具

下面的命令用于查看当前电源状态、WakeLock 和历史归因：

```bash
adb shell dumpsys power
adb shell dumpsys batterystats
adb shell dumpsys batterystats --enable full-wake-history
adb shell dumpsys deviceidle
adb shell dumpsys jobscheduler
adb shell dumpsys alarm
```

长时间实验可结合 bugreport、Power Profiler、Macrobenchmark power metric 和 Perfetto。Battery Historian 仍能读取 batterystats，但官方已不再积极维护，新的工作流优先使用 system tracing、Power Profiler 或 Macrobenchmark。

Perfetto 中把以下事件对齐：

- 用户空间 WakeLock acquire/release 与有效状态；
- suspend/resume 和 wakeup reason；
- 目标进程的 sched、CPU 时间和线程状态；
- thermal severity、频率限制和可用 power rail 数据；
- Job、Alarm、网络与业务自定义 trace。

WakeLock 持有时间长但线程持续 sleeping，通常表示代码在锁、网络或队列上空等。CPU 时间高而持锁很短，则要继续定位算法、渲染或编解码。

### 9.3 强制 Doze 测试

下面的命令用于让测试设备进入和退出 device idle：

```bash
adb shell dumpsys battery unplug
adb shell dumpsys deviceidle force-idle

# 执行业务观察后退出
adb shell dumpsys deviceidle unforce
adb shell dumpsys battery reset
```

测试应覆盖 idle 前提交、idle 中触发、维护窗口和退出 idle 后恢复。不要只检查 callback 是否到达，还要检查任务有没有重复、丢失或破坏幂等性。

文档：[Debug wake locks locally](https://developer.android.com/develop/background-work/background-tasks/awake/wakelock/debug-locally)

## 10. 交付前检查表

- [ ] 已确认专用 API、JobScheduler、WorkManager、媒体或传感器机制不能满足需求后才使用手工 WakeLock。
- [ ] 屏幕常亮使用 view/window API，没有使用废弃的 screen/full WakeLock。
- [ ] partial WakeLock tag 稳定且不含用户数据、时间戳或随机 ID。
- [ ] 每次 acquire 都有明确所有者、故障超时和 `finally` release。
- [ ] 没有捕获并忽略 under-lock 异常。
- [ ] callback、网络、用户输入和无界队列不会在持锁区间内无限等待。
- [ ] 进程能够在 WakeLock 被 LPS 或 Doze 忽略后暂停并恢复。
- [ ] 没有把 LPS System API 或 ports lock 当作普通应用能力。
- [ ] 热降级策略来自目标设备实验，没有按状态硬编码通用帧率。
- [ ] 功耗对照保证业务完成量相同，并同时记录 WakeLock、CPU、网络和 thermal。
