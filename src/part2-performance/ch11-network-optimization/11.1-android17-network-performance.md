# 11.1 Android 17 网络性能优化实战

网络性能不是一个“请求总耗时”数字。一次请求可能消耗在 DNS、连接建立、TLS、请求发送、服务端处理、响应传输、解码和 UI 提交中的任一阶段。只有把阶段、网络和请求语义同时记录下来，优化动作才有明确依据。

本章以 Android 17 / API 37 / `android-17.0.0_r1` 为平台锚点，内核侧以 `android17-6.18-2026-06_r6` 为锚点。OkHttp、Cronet 及其他第三方网络库由应用依赖决定；AOSP 中存在同名组件，不代表应用使用了该版本。

## 1. 先把请求时间分对

HTTP 请求的可观测时间可以按下面的关系理解：

`请求总时间 = 排队 + DNS + 建连 + TLS + 请求发送 + 服务端等待 + 响应读取 + 客户端处理`

各阶段的边界如下。

| 阶段 | 常见起止点 | 主要影响因素 | 容易误判的地方 |
|---|---|---|---|
| 排队 | 创建 Call 到获得执行线程 | 客户端并发限制、线程池、业务互斥 | 常被算进“网络慢” |
| DNS | 查询开始到获得地址集合 | 缓存、Private DNS、VPN、解析器、IPv4/IPv6 | 连接复用时不会发生 |
| 建连 | `connect()` 到连接成功 | RTT、丢包、地址竞速、代理 | 一次 Call 可能尝试多个地址 |
| TLS | 握手开始到会话可用 | RTT、证书链、算法、会话恢复 | 复用连接时不会发生 |
| 请求发送 | 请求头开始到请求体结束 | 上行、请求体大小、流控 | 小请求也可能被连接流控阻塞 |
| 服务端等待 | 请求发送后到响应头到达 | 服务端、网关、CDN、排队 | 客户端无法单独分离所有服务端阶段 |
| 响应读取 | 响应头到响应体读取结束 | 下行、压缩、流控、消费速度 | 未读取完整响应体时计时会提前结束 |
| 客户端处理 | 字节到业务对象和界面 | 解压、反序列化、数据库、主线程 | 与 TCP/TLS 无直接关系 |

DNS、TCP 和 TLS 没有跨业务通用的固定毫秒阈值。移动网络 RTT、服务器区域、代理、连接复用率与请求体量都会改变分布。合理的基线来自同一端点、同一网络类别、同一设备层级和同一版本的历史分位数。

## 2. Android 网络栈：数据面和控制面

普通应用发起 HTTP 请求时，数据通常不会逐包经过 `ConnectivityService` 和 `netd`。需要分开看两条路径。

### 2.1 数据面

请求数据的常见路径是：

`HTTP 库 → libcore / bionic → socket 系统调用 → Linux TCP/IP 栈 → 网络设备驱动 → Wi-Fi 或蜂窝硬件`

`send()`、`recv()`、拥塞控制、重传、队列和路由查找位于进程与内核的数据通路中。`wpa_supplicant` 负责 Wi-Fi 连接管理，蜂窝调制解调器由 telephony/RIL 体系控制；它们不是 TCP 报文离开内核后的逐包转发节点。

### 2.2 控制面

控制面决定应用当前能用哪张网络、网络具有什么能力，以及 UID 和 socket 应采用哪些规则。

| 组件 | 职责 | 与性能诊断的关系 |
|---|---|---|
| `ConnectivityService` | 维护 Network、默认网络、能力、请求和切换 | 解释网络选择、验证和默认网络变化 |
| NetworkAgent / NetworkMonitor | 上报链路状态并执行网络验证 | 解释 `VALIDATED`、门户网络和能力变化 |
| `netd` | 网络配置、路由、权限、流量控制等系统服务 | 解释 UID 规则、网络绑定和系统配置 |
| `DnsResolver` | 面向网络执行 DNS 解析并管理解析状态 | 解释 Private DNS、网络作用域和解析失败 |
| Linux 内核 | socket、TCP/IP、路由、队列、BPF 和驱动 | 解释重传、RTT、拥塞和收发队列 |

`ConnectivityManager` 的应用 API 通过 Binder 与系统网络服务交互，适用于查询、监听和申请网络。HTTP 请求建立完 socket 后，正文数据不会为每个字节再走一遍这条 Binder 控制链。

[已验证: AOSP `android-17.0.0_r1`, `packages/modules/Connectivity/service/src/com/android/server/ConnectivityService.java`, `packages/modules/DnsResolver/DnsResolverService.cpp`, `system/netd/server/NetdNativeService.cpp`]

## 3. 建立分层测量

单一工具无法同时回答 HTTP 语义、socket 行为、系统网络切换和内核丢包。工程上应按问题选择证据。

### 3.1 HTTP 库事件：定位请求阶段

OkHttp 的阶段回调接口名为 `EventListener`。每个 Call 使用独立 listener，才能避免并发请求互相覆盖时间戳。下面的示例只演示计时结构，事件最终应写入有界、采样的指标管道。

```kotlin
class TimingEventListener(
    private val report: (name: String, durationNs: Long) -> Unit
) : EventListener() {
    private val starts = mutableMapOf<String, Long>()
    private var callStartNs: Long? = null

    private fun start(name: String) {
        starts[name] = SystemClock.elapsedRealtimeNanos()
    }

    private fun end(name: String) {
        val begin = starts.remove(name) ?: return
        report(name, SystemClock.elapsedRealtimeNanos() - begin)
    }

    override fun callStart(call: Call) {
        val now = SystemClock.elapsedRealtimeNanos()
        callStartNs = now
        starts["call"] = now
    }

    override fun dnsStart(call: Call, domainName: String) = start("dns")

    override fun dnsEnd(
        call: Call,
        domainName: String,
        inetAddressList: List<InetAddress>
    ) = end("dns")

    override fun connectStart(
        call: Call,
        inetSocketAddress: InetSocketAddress,
        proxy: Proxy
    ) = start("connect")

    override fun secureConnectStart(call: Call) = start("tls")

    override fun secureConnectEnd(call: Call, handshake: Handshake?) = end("tls")

    override fun connectEnd(
        call: Call,
        inetSocketAddress: InetSocketAddress,
        proxy: Proxy,
        protocol: Protocol?
    ) = end("connect")

    override fun responseHeadersStart(call: Call) {
        val now = SystemClock.elapsedRealtimeNanos()
        callStartNs?.let { report("call_to_response_headers", now - it) }
        starts["response_headers"] = now
    }

    override fun responseHeadersEnd(call: Call, response: Response) =
        end("response_headers")

    override fun callEnd(call: Call) = end("call")

    override fun callFailed(call: Call, ioe: IOException) = end("call")
}

fun createHttpClient(
    metricSink: (name: String, durationNs: Long) -> Unit
): OkHttpClient = OkHttpClient.Builder()
    .eventListenerFactory { TimingEventListener(metricSink) }
    .build()
```

连接复用时，DNS、connect 和 TLS 事件缺失属于正常现象。一次 Call 还可能经历代理选择、多个地址尝试、重定向或认证重试；生产指标需要记录“事件是否出现”和“尝试次数”，不能把缺失阶段写成 0 ms。`responseHeadersStart` 是响应头开始读取的近似观测点，不等同于服务端独立记录的 TTFB。

Interceptor 适合记录完整 Call 的业务标签、状态码和总时间。它看不到可靠的 DNS、TCP、TLS 分段，`HttpLoggingInterceptor` 也不该用于生产 APM 采集。

### 3.2 Perfetto 网络包数据源：观察 UID 与方向

Android 14 起，Perfetto 提供 `android.network_packets` 数据源。下面的 pbtxt 配置降低了轮询间隔，并在 trace 中丢弃两端端口，适合受控实验。

```protobuf
buffers {
  size_kb: 32768
  fill_policy: RING_BUFFER
}

data_sources {
  config {
    name: "android.network_packets"
    network_packet_trace_config {
      poll_ms: 250
      aggregation_threshold: 32
      intern_limit: 1024
      drop_local_port: true
      drop_remote_port: true
    }
  }
}
```

该数据源是否可用还受设备版本、构建类型和 tracing 权限影响。端口字段可能具有隐私敏感性；只有诊断确有需要时才保留，并限制 trace 的访问范围。

导入标准库模块后，可以按包名和方向聚合 trace 中记录的包字节数。

```sql
INCLUDE PERFETTO MODULE android.network_packets;

SELECT
  package_name,
  direction,
  SUM(packet_length) AS bytes,
  SUM(packet_count) AS packets
FROM android_network_packets
GROUP BY package_name, direction
ORDER BY bytes DESC;
```

这里的 `packet_length` 来自抓取到的网络包信息，不能当作 HTTP 有效载荷，也不能推导单个请求的 DNS 或建连耗时。HTTP/2、HTTP/3 多路复用时，包和业务请求之间也没有简单的一对一关系。

[已验证: Perfetto TraceConfig `network_packet_trace_config`, 数据源 `android.network_packets`; AOSP `external/perfetto/src/trace_processor/perfetto_sql/stdlib/android/network_packets.sql`]

### 3.3 系统计数器：回答流量问题

| 接口 | 能回答什么 | 不能回答什么 |
|---|---|---|
| `TrafficStats.getUidRxBytes/TxBytes()` | UID 累计收发字节的前后差值 | DNS、TLS、单请求耗时和 HTTP 有效载荷 |
| `TrafficStats` thread tag | 将 socket 流量与应用自定义 tag 关联 | 自动生成完整请求链路 |
| `NetworkStatsManager` | 按时间、UID 和网络模板查询历史 bucket | 不具备权限时读取任意 UID；逐包时序 |
| HTTP `EventListener` | Call 的库内阶段与失败位置 | 内核重传、驱动队列和真实服务端耗时 |
| Perfetto / ftrace | 包、调度、内核事件和应用 trace 的时间关联 | 无应用标记时还原完整业务语义 |

`TrafficStats` 返回平台维护的累计值，底层实现可使用 eBPF 等设施。代码不应依赖旧版 `/proc/uid_stat` 路径。返回 `TrafficStats.UNSUPPORTED` 时还要停止计算差值。

## 4. Android 17 对网络应用的直接影响

### 4.1 流媒体带宽提示属于 `SubscriptionInfo`

API 37 新增的方法是：

- `SubscriptionInfo.getStreamingAppMaxDownlinkKbps()`
- `SubscriptionInfo.getStreamingAppMaxUplinkKbps()`

返回类型为 `long`，单位为 Kbps；未知或不适用时返回 `SubscriptionPlan.BITRATE_UNKNOWN`。这个值表示运营商给流媒体应用分配的速率上限提示，不是当前链路测速结果。

下面的读取示例以默认数据订阅为目标，并显式处理设备能力、权限和未知值。

```kotlin
data class StreamingRateLimit(
    val subscriptionId: Int,
    val downlinkKbps: Long?,
    val uplinkKbps: Long?
)

@RequiresApi(37)
@RequiresPermission(Manifest.permission.READ_PHONE_STATE)
fun readDefaultDataStreamingLimit(context: Context): StreamingRateLimit? {
    val pm = context.packageManager
    if (!pm.hasSystemFeature(PackageManager.FEATURE_TELEPHONY_SUBSCRIPTION)) {
        return null
    }

    val subId = SubscriptionManager.getDefaultDataSubscriptionId()
    if (!SubscriptionManager.isValidSubscriptionId(subId)) return null

    val manager =
        context.getSystemService(SubscriptionManager::class.java) ?: return null
    val info = manager.getActiveSubscriptionInfo(subId) ?: return null
    val unknown = SubscriptionPlan.BITRATE_UNKNOWN

    return StreamingRateLimit(
        subscriptionId = subId,
        downlinkKbps = info.streamingAppMaxDownlinkKbps
            .takeUnless { it == unknown },
        uplinkKbps = info.streamingAppMaxUplinkKbps
            .takeUnless { it == unknown }
    )
}
```

`getActiveSubscriptionInfo()` 要求 `READ_PHONE_STATE` 或运营商权限，并可能因设备不支持 telephony subscription 而失败。双卡设备的默认数据订阅会变化，媒体会话应把读取结果与 `subscriptionId` 绑定，并在订阅变化后刷新。`2000` 表示 2000 Kbps，不能写成 2,000,000。

码率决策还要结合播放器吞吐估计、缓冲区、清晰度切换成本和服务端阶梯。运营商提示适合作为上界输入，不能替代播放会话的持续测量。

[已验证: AOSP `android-17.0.0_r1`, `frameworks/base/telephony/java/android/telephony/SubscriptionInfo.java`; Android API 37 `SubscriptionInfo` 文档]

### 4.2 `ACCESS_LOCAL_NETWORK` 是运行时权限

target SDK 37 及以上的应用在 Android 17 上直接访问局域网时，默认会受到 Local Network Protection 限制。`android.permission.ACCESS_LOCAL_NETWORK` 属于 `NEARBY_DEVICES` 权限组，是 dangerous runtime permission。

需要宽泛、持续访问局域网的应用应在 target SDK 37 后声明该权限。

```xml
<uses-permission android:name="android.permission.INTERNET" />
<uses-permission android:name="android.permission.ACCESS_LOCAL_NETWORK" />
```

声明本身不会授予访问能力，应用仍需在用户触发局域网功能时检查并申请运行时权限。target SDK 36 及以下沿用兼容授予路径，官方迁移指导要求这些旧 target 应用不要提前申请该 API 37 权限。

受保护的操作包括：

- 出站和入站 TCP；
- UDP 单播、组播与广播；
- mDNS、SSDP 和 `.local` 解析；
- Java、NDK、OkHttp、Cronet、WebView 及其上层库发起的局域网访问。

媒体投放可优先采用系统 Output Switcher。mDNS 设备选择可评估 `DiscoveryRequest.FLAG_SHOW_PICKER`，让系统向用户展示设备并授予选中设备的访问范围。确需扫描和管理多个设备的 IoT 场景，再申请宽泛权限。

拒绝或撤销权限后，局域网流量会被阻止。UDP 调用可能得到 `EPERM`；浏览器类 NDK 客户端可通过 `android_getnetworkblockedreason(fd)` 区分 `ANDROID_NETWORK_BLOCKED_REASON_LNP`。普通应用不应只等待 `SecurityException`，还要把 socket 错误、超时和取消纳入状态机，且不得在拒绝后循环重试。

[已验证: Android 17 Local Network Permission 官方迁移文档；AOSP `frameworks/base/core/res/AndroidManifest.xml`]

### 4.3 ECH 改变 TLS 隐私边界

对 target SDK 37 及以上应用，Android 17 的 Network Security Configuration 默认采用 ECH `enabled` 模式。生效还要求应用的网络库已接入 ECH，服务端也提供 ECH 配置。没有可用 ECH 配置时，启用模式会使用 ECH GREASE。

下面的配置保留全局启用，同时为一个兼容性尚未完成的域名禁用 ECH。

```xml
<?xml version="1.0" encoding="utf-8"?>
<network-security-config>
    <base-config>
        <domainEncryption mode="enabled" />
    </base-config>
    <domain-config>
        <domain includeSubdomains="true">legacy.example.com</domain>
        <domainEncryption mode="disabled" />
    </domain-config>
</network-security-config>
```

`<domainEncryption>` 只在采用该 Network Security Configuration 的网络库已经支持 ECH 时发挥作用。ECH 保护 ClientHello 中的 SNI 隐私，不提供固定的握手提速承诺。禁用某个域名前，应保留服务端、DNS HTTPS 记录和客户端握手证据，避免把普通证书或网络故障归因给 ECH。

Android 17 还对 target SDK 37 应用默认启用 Certificate Transparency。CT、证书信任、证书固定和 ECH 属于不同检查面，诊断时要分别记录失败类型。

[已验证: Android 17 target behavior changes；Android Network Security Configuration `domainEncryption` 文档]

### 4.4 无锁 `MessageQueue` 不等于网络栈提速

Android 17 为 target SDK 37 及以上应用启用新的无锁 `android.os.MessageQueue` 实现。它影响 Looper 消息入队与处理的并发开销，不会缩短 DNS、TCP、TLS 或服务端处理时间。

网络回调也不一定经过主线程：

- `ConnectivityManager.NetworkCallback` 默认运行在应用的 connectivity thread；
- OkHttp 异步回调由其 dispatcher 执行；
- 应用将结果提交给主线程时，才会经过主 Looper。

因此，不能给无锁队列附加“网络 UI 固定减少若干毫秒”的结论。应在应用 trace 中分别标出 Call 完成、解析、状态更新和帧提交，再判断延迟位于哪一段。

## 5. 根据网络能力调整策略

### 5.1 使用回调携带的快照

在 `onAvailable()` 中立刻调用 `getNetworkCapabilities(network)` 存在竞态。Android 8.0 及以上会在 `onAvailable()` 后有序发送能力与链路属性回调，应用应使用回调参数。

下面的对象把默认网络能力转成业务可消费的快照，并把回调放到独立 HandlerThread。

```kotlin
data class NetworkPolicySnapshot(
    val network: Network,
    val validated: Boolean,
    val metered: Boolean,
    val roaming: Boolean,
    val congested: Boolean,
    val suspended: Boolean,
    val downstreamKbps: Int
)

class DefaultNetworkObserver(
    context: Context,
    private val onUpdate: (NetworkPolicySnapshot?) -> Unit
) : Closeable {
    private val connectivityManager =
        context.getSystemService(ConnectivityManager::class.java)
    private val callbackThread =
        HandlerThread("default-network-observer").apply { start() }
    private val callbackHandler = Handler(callbackThread.looper)
    private var currentNetwork: Network? = null

    private val callback = object : ConnectivityManager.NetworkCallback() {
        override fun onAvailable(network: Network) {
            currentNetwork = network
            // 等待紧随其后的 onCapabilitiesChanged()。
        }

        override fun onCapabilitiesChanged(
            network: Network,
            caps: NetworkCapabilities
        ) {
            currentNetwork = network
            onUpdate(
                NetworkPolicySnapshot(
                    network = network,
                    validated = caps.hasCapability(
                        NetworkCapabilities.NET_CAPABILITY_VALIDATED
                    ),
                    metered = !caps.hasCapability(
                        NetworkCapabilities.NET_CAPABILITY_NOT_METERED
                    ),
                    roaming = !caps.hasCapability(
                        NetworkCapabilities.NET_CAPABILITY_NOT_ROAMING
                    ),
                    congested = !caps.hasCapability(
                        NetworkCapabilities.NET_CAPABILITY_NOT_CONGESTED
                    ),
                    suspended = !caps.hasCapability(
                        NetworkCapabilities.NET_CAPABILITY_NOT_SUSPENDED
                    ),
                    downstreamKbps = caps.linkDownstreamBandwidthKbps
                )
            )
        }

        override fun onLost(network: Network) {
            if (currentNetwork == network) {
                currentNetwork = null
                onUpdate(null)
            }
        }
    }

    init {
        connectivityManager.registerDefaultNetworkCallback(
            callback,
            callbackHandler
        )
    }

    override fun close() {
        connectivityManager.unregisterNetworkCallback(callback)
        callbackThread.quitSafely()
    }
}
```

这个快照适合控制延后上传、预取规模、媒体初始码率和离线提示。回调线程中仍不应执行数据库迁移、大对象解析或同步 I/O；可以将不可变快照交给业务协程。

能力的解释边界要写进策略：

- `NET_CAPABILITY_INTERNET` 表示网络配置为可访问互联网；
- `NET_CAPABILITY_VALIDATED` 是平台验证通过的信号，仍不保证业务域名可达；
- `linkDownstreamBandwidthKbps` 是第一跳带宽估计，不是端到端即时吞吐；
- Wi-Fi 可能计费、拥塞或带宽较低，蜂窝也可能不计费；
- 缺少 `NOT_CONGESTED` 时，可延后日志和分析数据等非交互流量；
- 缺少 `NOT_SUSPENDED` 时，不宜启动新的大传输。

`NET_CAPABILITY_PRIORITIZE_LATENCY` 与 `NET_CAPABILITY_PRIORITIZE_BANDWIDTH` 从 Android 14 起用于具备相应运营商和设备支持的 premium network 请求。面向 Android 14 及以上 target 的请求还涉及 self-certified network capabilities 配置。它们不是通用路由加速开关，也不应加入默认网络监听来替代端到端测量。

[已验证: AOSP `android-17.0.0_r1`, `ConnectivityManager.java`, `NetworkCapabilities.java`; Android “Read network state” 官方文档]

### 5.2 正确理解默认网络切换

默认网络从蜂窝切到 Wi-Fi 时：

1. 新建连接使用新的默认网络；
2. 旧网络上的既有连接可能暂时继续工作；
3. 系统会在之后终止旧默认网络上剩余的连接。

`registerDefaultNetworkCallback()` 的 `onLost(network)` 表示该 Network 不再是应用默认网络，它可能仍处于连接状态。普通 `registerNetworkCallback()` 观察额外网络时，`onLost()` 才表示那张 Network 已断开。

HTTP/1.1 和 HTTP/2 的既有 TCP 连接不能迁移到新网络。基于 QUIC 的 HTTP/3 客户端可能支持连接迁移，能否迁移取决于 HttpEngine、Cronet 或其他实现、服务端配置及当前路径。不要假设 OkHttp dispatcher 会在网络切换时自动取消排队请求。

重试策略必须考虑请求语义：

- GET、HEAD 等幂等请求可在满足业务条件时有限重试；
- 创建订单、支付和上传提交应使用服务端幂等键或可查询的事务状态；
- 已发送部分请求体、已收到部分响应或连接切换时，不应仅凭异常类型判定服务端未执行；
- 重试需要指数退避、抖动、总时限和取消传播。

## 6. HTTP 客户端优化的边界

### 6.1 复用一个配置稳定的客户端

OkHttp、HttpEngine 和 Cronet 都能复用连接。应用若为每个请求新建客户端，会丢失连接池、DNS 状态、HTTP/2 会话和 TLS 会话恢复机会。

配置连接池前要确认库版本和实际问题。`ConnectionPool` 的 max idle 参数限制空闲连接数，不是总并发数；扩大它不会自动提高 HTTP/2 并发。应用进入后台时普遍调用 `evictAll()` 也可能把可复用连接全部关闭，增加下一次前台请求的握手成本。

依赖边界同样明确：应用 Gradle 解析出的 OkHttp 版本才决定 API、默认值和协议行为，不能拿 `android-17.0.0_r1/external/okhttp` 作为所有应用的实现依据。

### 6.2 分开设置超时

| 超时 | 保护的阶段 | 设计依据 |
|---|---|---|
| connect timeout | 单次连接尝试 | 网络类别、地址竞速、代理和用户等待预算 |
| read timeout | 两次读取之间的等待 | 流式响应、服务端心跳和单块大小 |
| write timeout | 两次写入之间的等待 | 上传大小、上行和服务端接收速度 |
| call timeout | 整个 Call | 业务操作总预算，包含重试和重定向 |

固定使用同一组超时会同时伤害交互小请求和大文件传输。配置应按请求类别制定，并保证协程取消或生命周期结束能传到 Call。

### 6.3 DNS 优化要尊重系统网络语义

`InetAddress.getAllByName()` 的一次预解析不保证能预热某个 HTTP 库内部的解析路径。库、Android 版本、当前 Network 和缓存策略都会影响结果。

自建 HTTP DNS 还可能改变：

- Private DNS 与企业 VPN 的解析策略；
- split DNS 和按 Network 作用域的答案；
- DNS64/NAT64 的地址合成；
- 代理和受限网络行为；
- TLS 主机名验证与证书选择。

缺少充分证据时应保留系统解析器。采用自定义解析后，要按 Network 隔离缓存，保留 IPv6/IPv4 地址集合与失败信息，网络切换时失效旧答案，并保持 TLS 使用原始主机名校验。

### 6.4 减少传输量，保留流式消费

- 对静态响应启用正确的 HTTP 缓存头，避免业务层缓存和协议缓存互相冲突；
- 让服务端按 `Accept-Encoding` 协商压缩，不要给已经压缩的图片、视频和归档重复压缩；
- 大响应采用流式解析，避免先复制完整字节数组再反序列化；
- 上传采用可恢复分片时，要设计分片校验、服务端去重和过期清理；
- 图片格式选择应基于目标设备解码支持、画质、透明度和实测体积，不能预设固定节省比例；
- GraphQL 或 batch API 能减少往返，也会扩大失败范围和响应体，需设置批次上限。

预取要由命中率、流量、内存和首屏竞争共同约束。网络更快时无限扩大预取会占用连接流控窗口，并可能推迟用户正在等待的请求。

## 7. 后台网络与蜂窝功耗

蜂窝 radio 的状态、驻留时间和功耗由制式、运营商、基带与设备策略共同决定。通用的 `HIGH → MEDIUM → DORMANT` 固定时长图只能描述某些旧网络示例，不能作为 Android 17 设备的实现模型。

可靠的工程原则是区分交互请求和可延后工作：

- 用户正在等待的请求优先响应，不为了批处理额外等待；
- 日志、分析、备份和内容同步使用 WorkManager 或 JobScheduler；
- 大型可延后传输可约束为 `UNMETERED`、充电中或设备空闲；
- 合并后台小请求可能减少 radio 唤醒次数，也可能增大瞬时队列和尾延迟，应同时看功耗与成功率；
- FCM 高优先级只用于时间敏感、对用户可见的事件，并遵守后台执行限制。

`NetworkType.UNMETERED` 表示系统判断为不计费网络，不等同于“只允许 Wi-Fi”。若产品需求限定某种 transport，还要单独评估网络请求、前台生命周期和设备差异。

## 8. 从症状回到证据

### 8.1 诊断表

| 症状 | 先收集的证据 | 后续判断 |
|---|---|---|
| `UnknownHostException` 增多 | Network、Private DNS/VPN、DNS 事件、地址族、解析错误 | 解析器、网络切换、域名配置、IPv6/IPv4 |
| connect 变慢 | 每次地址尝试、代理、Network、内核重传、RTT | 路径丢包、地址竞速、服务端监听、代理 |
| TLS 失败 | TLS 版本、证书链、主机名、ECH/CT 结果、系统时间 | 证书、信任、CT、ECH、协议兼容 |
| 响应头等待变长 | 请求发送完成点、CDN、服务端 trace、重试次数 | 服务端排队、缓存未命中、跨区、客户端重试 |
| 下载吞吐低 | 响应字节、读取节奏、协议、包统计、CPU | 网络拥塞、HTTP 流控、消费端阻塞、解压 |
| Wi-Fi/蜂窝切换失败 | 默认网络回调、Call 事件、幂等信息 | 旧连接终止、DNS 作用域、重试策略 |
| 局域网功能超时 | target SDK、授权状态、目标地址、errno | LNP 阻止、设备离线、路由或服务发现 |

异常类只说明客户端观察到的结果。例如 `SocketTimeoutException` 既可能来自链路，也可能来自服务端迟迟不发送数据；`SSLHandshakeException` 还需要结合证书和握手告警才能定位。

### 8.2 内核证据

`android17-6.18-2026-06_r6` 的 TCP tracepoint 定义以 `include/trace/events/tcp.h` 为锚点，TCP 实现位于 `net/ipv4/` 等目录。可用事件受设备内核配置、厂商补丁和 tracing 权限影响；文章列出的源码事件不保证所有量产机都开放。

出现重传和吞吐问题时，可以关注：

- `tcp_retransmit_skb` 等 TCP tracepoint 是否启用；
- socket 的地址族、状态和重传统计；
- 网络设备收发队列与丢包；
- 应用线程是否及时消费 response body；
- Network 切换时间是否与连接失败重合。

内核重传能证明传输路径出现未确认数据，不能单独判定是 Wi-Fi、运营商、远端主机还是中间设备丢包。需要结合接口、路由、端点和服务端观测。

### 8.3 受控采集流程

下面是一组面向测试机的最小命令骨架，具体输出权限随构建而变。

```bash
adb shell dumpsys connectivity > connectivity.txt
adb shell dumpsys netd > netd.txt

adb push network.pbtxt /data/local/tmp/network.pbtxt
adb shell perfetto --txt \
  -c /data/local/tmp/network.pbtxt \
  -o /data/misc/perfetto-traces/network.pftrace
adb pull /data/misc/perfetto-traces/network.pftrace
```

`dumpsys` 适合核对 Network、能力、路由和系统服务状态；Perfetto 用于时间关联。采集前应缩短窗口、去除端口等敏感字段，并记录设备构建、网络环境和复现步骤。

## 9. 生产指标与隐私

生产网络遥测建议保留以下低基数字段：

- 经过白名单映射的 endpoint 模板，不记录完整 URL；
- HTTP 方法、状态码类别和错误家族；
- 总时间及出现过的 DNS、connect、TLS、响应头和响应体阶段；
- 协议、连接是否复用、缓存命中状态；
- 请求体与响应体字节区间；
- `VALIDATED`、计费、漫游、拥塞、暂停等能力；
- 应用版本、设备层级和匿名网络类别；
- 采样率与指标 schema 版本。

查询参数、Authorization、Cookie、请求体、响应体、原始 IP 和用户输入不应进入性能日志。主机名也可能暴露用户行为，可使用受控映射或带轮换密钥的散列。异常消息要按类型归一化，避免把 URL 和令牌随 `IOException.message` 上传。

比较优化前后结果时，至少按 endpoint、应用版本、协议、是否复用连接和网络能力分层。全局 P90 可能因请求构成变化而改善，即使每类请求都变慢；分层分位数和请求量必须一起观察。

## 10. 测试与发布验证

### 10.1 客户端确定性测试

MockWebServer 或受控测试服务适合验证：

- 缓存头、重定向、认证和协议错误；
- 慢响应头、分块响应、断流和取消；
- 幂等键、重试次数与退避；
- response body 是否总能关闭；
- EventListener 在复用与新建连接下的事件完整性。

这类测试能稳定复现客户端行为，不能代替公网 RTT、运营商切换或真实拥塞测试。

### 10.2 网络实验室测试

在可控代理、路由器或仿真环境中组合延迟、丢包、限速、乱序、IPv6-only、DNS64/NAT64、代理和网络切换。测试服务端应同步记录请求 ID、到达时间、处理时间和响应字节，便于区分客户端、链路与服务端。

Android 17 升级还要覆盖：

- target SDK 36 与 37 的局域网行为差异；
- 用户允许、拒绝、撤销 `ACCESS_LOCAL_NETWORK`；
- ECH 支持与不支持的服务端；
- 双卡默认数据订阅变化和未知流媒体速率；
- Wi-Fi、蜂窝、VPN、Private DNS、门户网络及网络切换；
- MessageQueue 行为变化下的应用私有反射兼容性。

Macrobenchmark 可测启动、帧和自定义 trace 区间，但它不会自动生成可信的 `networkRequestMs` 指标。网络实验应使用应用自定义 trace、HTTP 事件、服务端记录和受控网络条件共同构成结果。

### 10.3 发布判定

网络优化的发布指标至少包括：

- 用户等待时间分位数；
- 成功率、取消率和重复提交率；
- 每次成功操作的传输字节；
- 缓存命中率与连接复用率；
- 后台任务完成率、延迟和耗电变化；
- 按网络能力和应用版本分层的回归；
- 隐私字段扫描和采样成本。

没有统一的“优秀网络耗时”表。团队应从业务等待预算和历史分布制定 SLO，并在端点或请求构成变化时重新建立基线。

## 12. 工程检查表

- [ ] 用 HTTP 事件区分排队、DNS、连接、TLS、响应头和响应体。
- [ ] 把连接复用导致的阶段缺失记录为“未发生”，不写成 0 ms。
- [ ] 默认网络回调使用回调参数，不在回调里同步查询同一 Network。
- [ ] 业务策略依据 capability，未用 transport 猜测计费和带宽。
- [ ] `SubscriptionInfo` 速率使用 Kbps 和 `long`，处理未知值与订阅变化。
- [ ] target SDK 37 的局域网路径覆盖系统 picker、授权、拒绝和撤销。
- [ ] ECH 配置与网络库、服务端支持情况一起验证。
- [ ] 重试受到幂等语义、总时限、退避和取消约束。
- [ ] 自定义 DNS 保留 Network、VPN、Private DNS、IPv6 和 TLS 主机名语义。
- [ ] Perfetto 包数据没有被解释成 HTTP 有效载荷或阶段耗时。
- [ ] 生产日志不包含完整 URL、查询参数、令牌、正文和原始 IP。
- [ ] 后台批处理同时检查耗电、尾延迟、峰值流量和成功率。
- [ ] 测试覆盖网络切换、IPv6-only、代理、Private DNS 和受限局域网。
