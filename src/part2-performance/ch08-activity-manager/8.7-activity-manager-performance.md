# 8.7 Android 17 ActivityManager 性能优化实战

[适用版本：Android 15（API 35）至 Android 17（API 37）]

这一章处理四类应用能够观察和干预的问题：组件启动等待、进程创建与初始化、进程重要性变化，以及 Service、Broadcast 和缓存进程带来的后台行为。分析时要把 `system_server` 的调度时间、应用主线程工作和内存压力分开，否则很容易把应用初始化慢写成 AMS 慢。

Android 17 的平台源码锚点统一为 `android-17.0.0_r1`。AppFlow 是研究方案，不是该版本 AOSP 的 AMS 或 LMKD 能力；4.5 节保留它，只用于讨论假设性的产品集成边界。

---

## 1. 先划清 AMS、ATMS 与应用进程的职责

Activity 启动、Service 调度、Broadcast 分发都经过 ActivityManager 体系，但耗时可能发生在不同进程和线程：

| 观察到的现象 | 平台侧入口 | 常见等待位置 | 应用侧检查对象 |
|---|---|---|---|
| 冷启动慢 | ATMS、AMS、`ProcessList` | 进程创建、`bindApplication`、首个 Activity 调度 | Provider、`Application.onCreate()`、Activity 初始化、首帧 |
| `bindService()` 返回或回调慢 | `ActiveServices` | 目标进程启动、Service 创建、Binder 线程排队 | `onCreate()`、`onBind()`、同步 Binder 调用 |
| 广播迟到或接收超时 | `BroadcastQueueImpl` | 每进程队列、冷进程启动、前序 Receiver | `onReceive()` 与 `goAsync()` 后的工作 |
| 后台进程被杀 | `OomAdjusterImpl`、`ProcessList`、lmkd | 进程状态计算、内存压力下的 victim 选择 | 组件是否仍活跃、内存占用、后台工作模型 |
| 缓存进程恢复后消息集中出现 | `CachedAppOptimizer` | 冻结期间线程不运行，解冻后继续处理 | 对后台即时性的错误依赖 |

ATMS 管 Activity、Task 和窗口侧状态，AMS 管进程及 Service、Broadcast、Provider 等组件。`system_server` 发出生命周期事务后，应用进程仍要在主线程执行回调、布局和绘制。Perfetto 中出现长启动区间，只能说明这段用户旅程慢，不能直接证明 AMS 的某个方法耗时过长。

源码锚点：

- [`ActivityTaskManagerService.java`](https://android.googlesource.com/platform/frameworks/base/+/refs/tags/android-17.0.0_r1/services/core/java/com/android/server/wm/ActivityTaskManagerService.java)
- [`ActivityManagerService.java`](https://android.googlesource.com/platform/frameworks/base/+/refs/tags/android-17.0.0_r1/services/core/java/com/android/server/am/ActivityManagerService.java)

## 2. Activity 冷启动：沿因果顺序找等待

一次典型冷启动包含以下阶段：

1. ATMS 接收启动请求，`ActivityStarter` 完成解析、权限检查和 Task 放置。
2. 目标进程不存在时，`ActivityTaskSupervisor` 调到 `ActivityTaskManagerService.startProcessAsync()`。
3. ATMS 经 `ActivityManagerInternal` 请求 AMS 创建进程，`ProcessList` 再与 Zygote 交互。
4. 应用进程的 `ActivityThread` attach 到 AMS，`system_server` 执行 `attachApplication`。
5. `ActivityThread.handleBindApplication()` 创建 Application，并安装随启动发布的 ContentProvider。
6. Provider 安装完成后，`Application.onCreate()` 才会被调用。
7. Activity 生命周期事务到达应用主线程，随后发生布局、绘制和 Surface 提交。

第 5、6 步的顺序很实用。许多“`Application.onCreate()` 还没开始就卡住”的案例，耗时来自自动初始化 Provider 或 Provider 自身的 `onCreate()`。AndroidX Startup 能合并初始化入口，但它不会让初始化工作自动变快，仍需按首帧依赖关系决定哪些工作同步执行。

源码锚点：

- [`ActivityTaskSupervisor.java`](https://android.googlesource.com/platform/frameworks/base/+/refs/tags/android-17.0.0_r1/services/core/java/com/android/server/wm/ActivityTaskSupervisor.java)
- [`ProcessList.java`](https://android.googlesource.com/platform/frameworks/base/+/refs/tags/android-17.0.0_r1/services/core/java/com/android/server/am/ProcessList.java)
- [`ActivityThread.java`](https://android.googlesource.com/platform/frameworks/base/+/refs/tags/android-17.0.0_r1/core/java/android/app/ActivityThread.java)

### 2.1 应用侧怎么减工作

给启动任务做分类时，可以问三个问题：

- 首帧缺少它，用户是否无法理解当前页面？
- 它是否要求主线程、当前进程或已创建的 Activity？
- 延后执行会不会改变数据一致性、权限或安全语义？

首帧依赖的数据读取、路由和最小 UI 状态需要保留。分析 SDK、远端配置刷新、缓存整理和非首屏数据库预热，通常可以改成懒加载或在页面稳定后调度。延后不等于随意开一个后台线程；进程进入 cached 状态后可能被冻结或回收，需要持久完成保证的任务应交给 WorkManager 或 JobScheduler。

下面的示例演示“按使用点初始化”，用途是避免 `Application.onCreate()` 无条件创建昂贵对象：

```kotlin
class AppContainer(context: Context) {
    private val appContext = context.applicationContext

    val searchIndex: SearchIndex by lazy(LazyThreadSafetyMode.SYNCHRONIZED) {
        SearchIndex.open(appContext)
    }
}

class WikiApp : Application() {
    lateinit var container: AppContainer
        private set

    override fun onCreate() {
        super.onCreate()
        container = AppContainer(this)
    }
}
```

这段代码只推迟 `SearchIndex.open()`，不会保证调用发生在后台线程。若初始化包含磁盘 I/O，调用方还要选择合适的 dispatcher，并处理初始化期间的 UI 状态。

### 2.2 不要给所有设备套固定毫秒线

`Application.onCreate() < 50 ms` 或“中端机冷启动必须小于 800 ms”只能是某个产品、某组设备和某种测试条件下的预算，不能当作 Android 17 平台约束。官方 Android vitals 给出的是用于发现过慢启动的统计口径，不等同于产品体验目标。

团队应固定启动场景、设备档位、系统镜像、温度、编译类型、网络和账号状态，分别记录 cold、warm、hot 的 TTID 与 TTFD。产品预算从连续采样的 P50、P90、P95 或 P99 建立，并注明版本和样本条件。

参考：[App startup time](https://developer.android.com/topic/performance/vitals/launch-time)

## 3. `procstate`、`oom_adj` 与 lmkd：应用不能手工设分

Android 17 中，`ProcessStateController` 维护进程状态写入入口，`OomAdjusterImpl` 根据 Activity、Service、Provider、Broadcast、Binder 依赖和其他可达关系计算 `procstate`、`oom_adj`、调度组与 capability。计算结果经 `ProcessList` 发送给 lmkd；lmkd 在内存压力下结合这些优先级选择回收对象。

`procstate` 与 `oom_adj` 服务于不同判断，二者不存在适用于所有时刻的一对一固定表。进程也不能通过公开 API 指定自己的 adj。应用能改变的是组件关系和正在进行的用户可感知工作：

- 页面可见时只保留页面所需资源，不用隐藏 Activity 或无意义 Service 延长进程寿命。
- 后台播放、导航等符合 FGS 语义的工作使用相应 FGS 类型，并显示通知。
- 可延期且要求完成的工作交给系统调度器，同时保存可恢复的进度。
- `bindService()` 的绑定关系会参与重要性传播；避免长期保留已无用途的绑定。
- 多进程会增加运行时、堆、线程池和共享库页表等基线成本，拆进程前要测总 PSS、启动次数和 IPC 等待。
- Provider 的 `exported` 属性决定外部访问边界。单凭导出状态不会提高进程优先级，正在发生的 Provider 访问及其依赖关系才会参与状态计算。

`PROCESS_STATE_TOP_SLEEPING` 描述设备进入睡眠时的 top 进程状态。ATMS 在 `sleepIfNeededLocked()` 中把 top state 改为该值，在唤醒路径恢复为 `PROCESS_STATE_TOP`。它不是“Activity 执行了 `onPause()`、尚未执行 `onStop()`”的通用标签。

源码锚点：

- [`ProcessStateController.java`](https://android.googlesource.com/platform/frameworks/base/+/refs/tags/android-17.0.0_r1/services/core/java/com/android/server/am/psc/ProcessStateController.java)
- [`OomAdjusterImpl.java`](https://android.googlesource.com/platform/frameworks/base/+/refs/tags/android-17.0.0_r1/services/core/java/com/android/server/am/psc/OomAdjusterImpl.java)

## 4. Service 与前台服务：区分三组限制

前台服务相关问题常被混成一个“5 秒规则”。Android 17 源码中至少要区分以下机制：

| 机制 | Android 17 行为 | 排查入口 |
|---|---|---|
| 从 `startForegroundService()` 启动后晋升 | Service 必须在平台配置的期限内调用 `startForeground()`；`android-17.0.0_r1` 的 `DEFAULT_FGS_START_FOREGROUND_TIMEOUT_MS` 为 10 秒，DeviceConfig 可覆盖 | `ActivityManagerConstants`、`ActiveServices`、异常日志 |
| Service 生命周期回调超时 | 前台进程中的 Service 默认 20 秒乘硬件超时系数，后台为该值的 10 倍；这是 Service 执行超时，不是晋升期限 | `serviceTimeout()`、ANR trace |
| 有时限的 FGS 类型 | `shortService`、`dataSync` 等类型有各自的时限和超时回调规则 | FGS 类型文档、`ActiveServices` |

默认值可以被平台配置覆盖，因此应用代码不要把 10 秒当作可用预算。调用 `startForegroundService()` 后应尽快创建通知并调用 `startForeground()`，耗时资源准备放到晋升之后。

面向 target SDK 34 及以上的应用，需要在 manifest 声明符合用途的 FGS 类型和对应权限。缺少类型时，调用 `startForeground()` 会抛出 `MissingForegroundServiceTypeException`，系统不会静默降级成普通 Service。

下面的 manifest 片段用于声明媒体播放前台服务：

```xml
<uses-permission android:name="android.permission.FOREGROUND_SERVICE" />
<uses-permission android:name="android.permission.FOREGROUND_SERVICE_MEDIA_PLAYBACK" />

<application ...>
    <service
        android:name=".playback.PlaybackService"
        android:exported="false"
        android:foregroundServiceType="mediaPlayback" />
</application>
```

类型声明还要与运行时用途、权限和调用时传入的类型一致。声明类型只满足校验条件，不会绕过后台启动限制，也不保证进程永远存活。

源码与文档：

- [`ActivityManagerConstants.java`](https://android.googlesource.com/platform/frameworks/base/+/refs/tags/android-17.0.0_r1/services/core/java/com/android/server/am/ActivityManagerConstants.java)
- [`ActiveServices.java`](https://android.googlesource.com/platform/frameworks/base/+/refs/tags/android-17.0.0_r1/services/core/java/com/android/server/am/ActiveServices.java)
- [Declare foreground services and request permissions](https://developer.android.com/develop/background-work/services/fgs/declare)

## 5. Broadcast：等待可能来自目标进程队列

Android 17 使用 `BroadcastQueueImpl` 和按进程组织的 `BroadcastProcessQueue`。可运行队列晋升为 running 后才会分发；对于尚未运行的目标进程，队列需要等待冷启动。源码限制同一时刻只请求一个广播目标冷启动，用来控制系统健康风险。

这带来两个诊断结论：

- 广播从发送到 `onReceive()` 的等待时间，可能包含前序广播、目标进程队列以及进程冷启动。
- `onReceive()` 自身很短，仍不能证明广播系统没有排队；要同时看 enqueue、dispatch、receiver 执行和 finish。

`BroadcastConstants` 的默认 delivery timeout 是 10 秒乘硬件超时系数，前台、后台队列还能使用各自配置。`BroadcastQueueImpl` 先设置 soft timeout，并在超时时考虑进程获得的 CPU 时间。原文所写“Android 17 前台 8 秒、后台 60 秒”在 `android-17.0.0_r1` 中没有源码依据。

Receiver 只在 `onReceive()` 调用期间被视为活跃。短异步工作可以调用 `goAsync()`，并保证所有路径都执行 `PendingResult.finish()`；需要可靠完成或可能持续较久的工作，应转交 JobScheduler 或 WorkManager。

下面的示例用于把短数据库写入移出主线程，同时确保广播完成信号一定发回系统：

```kotlin
class BookmarkChangedReceiver(
    private val appScope: CoroutineScope,
    private val repository: BookmarkRepository,
) : BroadcastReceiver() {

    override fun onReceive(context: Context, intent: Intent) {
        val pendingResult = goAsync()
        appScope.launch(Dispatchers.IO) {
            try {
                repository.refreshFrom(intent)
            } finally {
                pendingResult.finish()
            }
        }
    }
}
```

这个模式适合有明确上界的短任务。若进程退出后仍要求完成，协程本身不提供持久保证，Receiver 应只解析参数并提交可持久调度的任务。

广播注册限制也要说准确：Android 8.0 起，面向相应版本的应用不能在 manifest 中声明大多数隐式广播；豁免广播仍可静态注册。运行时注册适用于 Context 有效期间，注册和注销时机应匹配界面或进程需要的可见范围。

- [`BroadcastConstants.java`](https://android.googlesource.com/platform/frameworks/base/+/refs/tags/android-17.0.0_r1/services/core/java/com/android/server/am/BroadcastConstants.java)

## 6. Cached App Freezer：冻结的对象是缓存进程

`CachedAppOptimizer` 会让符合条件的 cached 进程进入冻结候选。Android 17 的实现先冻结 Binder 接口，再冻结进程；解冻时则先恢复 Binder 接口，避免随进程恢复触发的定时器立刻遇到 Binder 失败。

同步 Binder 事务到达冻结进程不是普通的“EAGAIN 后等 50 ms 重试”流程。`CachedAppOptimizer` 查询到 `SYNC_RECEIVED_WHILE_FROZEN` 时，会把目标进程按 freezer 原因终止。异步事务有独立的冻结信息和待处理检查，平台还会处理事务积压导致的冻结失败。

应用侧应遵守这些边界：

- cached 状态不具备实时执行保证，Handler、定时器和普通线程都可能长时间没有运行机会。
- 不要轮询 `getRunningAppProcesses()` 决定业务正确性。状态可能在检查后立刻变化，该 API 也不能替代系统调度。
- 后台 IPC 调用方要有取消、超时和重连设计，不能假设缓存进程一直响应。
- 对冻结和回收都敏感的状态要持久化，并让恢复流程具备幂等性。

源码锚点：[`CachedAppOptimizer.java`](https://android.googlesource.com/platform/frameworks/base/+/refs/tags/android-17.0.0_r1/services/core/java/com/android/server/am/CachedAppOptimizer.java)

## 7. 生命周期资源管理：按所有权释放

“所有资源都在 `onStop()` 释放”会制造新的问题。数据库连接通常由进程级仓库管理；每次页面停止都关闭数据库，可能增加下次显示的打开成本，还会影响其他页面。Receiver、传感器监听和回调则应按订阅所需的生命周期成对注册和注销。

| 资源 | 推荐所有者 | 常见释放或暂停位置 |
|---|---|---|
| 页面动画、相机预览 | Activity、Fragment 或其视图 | 不再可见时暂停；视图销毁时释放视图引用 |
| 仅前台页面需要的 Receiver | Activity 或 Fragment | `onStart()` 注册、`onStop()` 注销，或按更窄的 resume 区间配对 |
| 数据库、网络客户端 | Application 级容器或 Repository | 由容器管理，不随单页 `onStop()` 反复关闭 |
| 页面异步任务 | lifecycleScope、viewLifecycleOwner | 生命周期取消时自动取消，或显式取消不可继续的任务 |
| ViewModel 中的流和缓存 | ViewModel | `onCleared()` 清理 ViewModel 所拥有的资源 |

系统在杀进程前不保证调用 `Activity.onDestroy()`，所以持久状态不能只在 `onDestroy()` 保存。ViewModel 也不应持有 Activity、Fragment 或 View；需要 Context 时优先传入 Application context，或把依赖放到生命周期更合适的对象中。

## 8. 一套可复现的诊断顺序

### 8.1 记录启动分类和时间戳

Android 15 至 Android 17 可通过 `ActivityManager.getHistoricalProcessStartReasons()` 读取本应用的 `ApplicationStartInfo`。Android 17 的源码提供 launch、fork、`bindApplication`、`Application.onCreate`、first frame、fully drawn 等时间戳，其中部分时间戳只在对应启动状态完成后存在。

这组数据适合回答“进程何时 fork”“应用绑定到首帧用了多久”。TTFD 还需要应用在可交互时调用 `reportFullyDrawn()`；没有上报就不能凭 TTID 推断 TTFD。

源码锚点：

- [`ApplicationStartInfo.java`](https://android.googlesource.com/platform/frameworks/base/+/refs/tags/android-17.0.0_r1/core/java/android/app/ApplicationStartInfo.java)
- [`ActivityManager.java`](https://android.googlesource.com/platform/frameworks/base/+/refs/tags/android-17.0.0_r1/core/java/android/app/ActivityManager.java)

### 8.2 用 Perfetto定位等待归属

抓取包含 app、`system_server`、Binder、sched、am、wm 和内存事件的 trace，在 Perfetto 中找到 **Android App Startups** 派生轨道，并沿时间线检查：

1. 启动请求到进程 fork：关注 `system_server`、Zygote 和调度等待。
2. fork 到 `bindApplication`：关注新进程启动、主线程调度和运行时初始化。
3. `bindApplication` 到 `Application.onCreate()`：关注 Provider 和框架绑定工作。
4. Application 到首帧：关注主线程回调、Binder、磁盘 I/O、布局和绘制。
5. TTID 到 TTFD：关注首屏数据、图片和业务定义的可交互条件。

这里不提供依赖猜测 slice 名称的 SQL。Perfetto 表结构和 trace 数据源会随版本变化，`slices` 也不是标准表名；应基于当前 trace 的派生指标和可见轨道确认事件，再保存项目自己的查询。

参考：[How to identify app startup in Perfetto](https://developer.android.com/topic/performance/vitals/launch-time#perfetto)

### 8.3 用 dumpsys 与 procfs 核对运行状态

下面这组命令用于观察进程、组件队列和内存压力，执行前后要记录设备 build、时刻和复现场景：

```bash
adb shell dumpsys activity processes
adb shell dumpsys activity oom
adb shell dumpsys activity services com.example.app
adb shell dumpsys activity broadcasts
adb shell dumpsys activity providers
adb shell dumpsys activity activities
adb shell dumpsys meminfo com.example.app
adb shell cat /proc/pressure/memory
adb shell cat /proc/<pid>/oom_score_adj
```

`dumpsys activity` 的文本字段属于诊断输出，不是稳定 API。自动化解析前要在目标镜像上保存样例并做版本兼容。`android-17.0.0_r1` 没有原文所说的 `dumpsys activity processes --verbose` AppFlow 状态。

## 9. 从症状到证据

| 症状 | 证据组合 | 满足什么条件才改代码 |
|---|---|---|
| 冷启动 P95 回退 | Macrobenchmark/线上 TTID + `ApplicationStartInfo` + Perfetto | 回退稳定复现，并定位到具体阶段或初始化任务 |
| `bindService()` 偶发长等待 | 调用方 Binder slice + 目标进程状态 + Service 生命周期 trace | 目标冷启动、主线程回调或 Binder 排队有明确时间占比 |
| 广播偶发迟到 | `dumpsys activity broadcasts` + Perfetto + Receiver 自定义 trace | 等待位于目标队列、冷启动或 Receiver 工作中的某一段 |
| 后台进程频繁重建 | `ApplicationExitInfo` + `oom_score_adj` + PSI + PSS | 能区分 LMK、crash、ANR、freezer 和用户操作等退出原因 |
| 从后台回来数据陈旧 | 冻结/解冻事件 + 生命周期日志 + 数据版本 | 代码依赖 cached 进程持续运行，恢复逻辑缺少重新校验 |

每次修改只改变一个可解释因素，再用相同场景比较分位数和 trace。单次启动、单个设备或一条 `dumpsys` 不能支撑普遍结论。
