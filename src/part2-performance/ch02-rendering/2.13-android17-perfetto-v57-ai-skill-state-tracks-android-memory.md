## 三个版本对象必须分开

| 对象 | 本轮固定锚点 | 能力边界 |
|---|---|---|
| Android 平台源码 | `android-17.0.0_r1` | `external/perfetto` 位于 v54.0 系列，平台头文件没有 `TRACE_STATE`、`StateTrack`，Trace Processor 也没有公开 `state` 表 |
| 主机分析工具 | Perfetto v57.1，commit `c59f57dd4d9c4ad37c44f0fee9dde060707534fa` | 可以解析 State Track，并可分析 Android 17 设备采集的 trace |
| AI skill | v57.1 标签中的 `ai/skills/perfetto` 与对应安装包 | 为 coding agent 提供工作流、SQL、Python 脚本和 `trace_processor` wrapper；设备上没有随之运行的 AI 模型 |

Android 平台版本与上游 Perfetto 版本没有一一对应关系。使用 v57.1 的主机 Trace Processor 打开 Android 17 trace，不表示 v57.1 已进入 Android 17 平台源码。

如果 Android 17 应用要产生 State Track，需要自行集成 v57.1 或更新版本的 Perfetto C++ SDK，并验证 producer、设备 tracing service 和主机 parser 的组合。只使用 `android-17.0.0_r1` 自带 SDK，无法调用 `TRACE_STATE`。

## AI skill 与 State Track 是两项独立能力

Perfetto v57.0 的发布记录同时加入了 AI skill 和 State Track，v57.1 修复 skill 安装包遗漏 `trace_processor` wrapper 的问题。发布时间相近不代表两者存在自动调用关系：

- AI skill 驱动 agent 查询已有 trace，内存工作流使用 heap graph、heap profile 和 PerfettoSQL。
- State Track 由 producer 主动写入符号状态，Trace Processor 把它解析为 `state` 表。
- v57.1 的五个 Android 内存工作流没有查询 `state` 表，也没有调用 `TRACE_STATE`。
- State Track 不会把 heap dump 自动改写成对象生命周期状态，也不会自动建立“某状态导致某次分配”的因果关系。

当应用主动记录了 `Loading`、`Playing`、`Idle` 等业务状态时，分析者可以按状态窗口关联 `heap_profile_allocation`。这种关联只能说明时间重叠；异步任务、其他线程和采样误差仍需结合 callsite、源码与对照样本核验。

## v57.1 内存工作流的准确清单

v57.1 标签下有五个顶层 Android 内存工作流，不是六个：

1. `heap_dump.md`：Java heap dump 的 dominator 路径初筛与深入查询。
2. `heap_dump_caching_optimizer.md`：重复对象与缓存候选。
3. `heap_dump_cluster.md`：多份 heap dump 的路径聚类。
4. `java_allocation_profile.md`：Java/Kotlin 分配 profile。
5. `native_heap.md`：heapprofd 采集的 native heap 分析。

其中 `heap_dump.md` 要求先运行 `triage_dominator_path.sql`。脚本按每个 `(upid, graph_sample_ts)` 选择 `self_size` 最大的 dominator class-tree 节点，再恢复祖先路径。这个结果是候选线索，不能单独证明内存泄漏：

- `self_size` 不能替代 retained/dominated size。
- 单个 heap dump 不能证明对象数量持续增长。
- 大缓存或资源池可能符合产品设计。
- GC root 路径仍要对应到源码中的注册、持有和释放点。
- 修复后需要用相同场景、相同采集配置重新验证。

`cluster_paths.py` 使用 TF-IDF、K-Means 和 silhouette score 归并相似路径。它会去掉实例计数和 root 标签，因而不保留完整引用顺序与字段语义。聚类结果适合缩小样本范围，不能直接指定泄漏责任类。

## State Track 的源码链路已经实现

研究素材曾因在 `track_event_parser.cc` 中搜索不到 `TYPE_STATE`，把解析链标成待验证。v57.1 的代码拆在其他文件中，链路可以完整核对：

1. `track_event.proto` 定义 `TYPE_STATE = 5`，`TrackDescriptor` 通过空的 `StateDescriptor` 标记 State Track。
2. `track_event_tokenizer.cc` 要求事件提供 `track_uuid`，并检查目标 descriptor 确为 state track。
3. `track_event_event_importer.h` 把 `TYPE_STATE` 分派到 `ParseStateEvent()`。
4. `StateTracker::UpdateState()` 在状态变化时关闭旧行并写入新行。
5. `after_eof/views.sql` 把内部 `__intrinsic_state` 暴露为公开 `state` view。

同一轨道的新值与当前值相同时，Trace Processor 不新增状态行，只合并参数；不同值会把旧行的 `dur` 写成两个时间戳之差；空值会关闭当前状态而不创建空状态行。末尾未关闭的状态保留 `dur = -1`。需要事件次数时，应使用 instant event 或 counter，不能把重复状态上报当成心跳。

`state` 表也不能和 `thread_state` 混用。前者来自 v57 State Track producer，表示业务或子系统的符号状态；后者主要来自调度事件，表示线程 Running、Runnable、Sleeping 等内核调度状态。

## Android 17 上的可行用法

| 目标 | 推荐组合 | 说明 |
|---|---|---|
| 分析 Android 17 Java heap dump | Android 17 设备采集 + v57.1 主机 Trace Processor/AI skill | 不需要设备端支持 State Track |
| 分析 native 内存增长 | Android 17 heapprofd trace + v57.1 `native_heap.md` | 区分累计分配、尚未释放和净变化 |
| 用业务状态切分分配 | 应用集成 v57.1 C++ SDK + v57.1 主机工具 | 需要自行发出 State Track，并验证发布构建开销 |
| 只使用 Android 17 平台 Perfetto | 平台 v54.0 采集与分析能力 | 不应引用 v57 的 `TRACE_STATE` 或 `state` 表 |

AI skill 能降低第一次编写 PerfettoSQL 的门槛。每次报告仍要保留 `trace_processor --version`、实际 SQL、进程与采样时间、空结果处理、数据完整性检查和源码证据。agent 给出的“疑似泄漏”必须作为待验证假设。

## 本章小结

本章是 ch02-rendering 目录下的兼容入口，不重复维护安装命令和完整 SQL，完整正文在 [13.23](../../part1-fundamentals/ch13-profiling/13.23-perfetto-v57-ai-skill-state-tracks-memory-debug.md)。本章确认了三个关键事实：

1. **版本边界**：Android 17（`android-17.0.0_r1`）平台自带 Perfetto 是 v54.0 系列，不包含 `TRACE_STATE` / `state` 表。主机分析工具 v57.1 是独立的上游版本，不等于平台已集成 v57。
2. **AI skill ≠ State Track**：v57.1 的五个 Android 内存工作流只使用 heap graph、heap profile 和 PerfettoSQL，不查询 `state` 表，不调用 `TRACE_STATE`。两者是独立能力。
3. **State Track 源码链路**：v57.1 的 State Track 解析链路已在上游源码中完整实现（`track_event.proto` → `track_event_tokenizer.cc` → `track_event_event_importer.h` → `StateTracker::UpdateState()` → `state` view），此前的"待验证"标记可以解除。
