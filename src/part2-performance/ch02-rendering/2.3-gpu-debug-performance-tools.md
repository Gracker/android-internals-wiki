# 2.3 Android 17 GPU 调试性能工具链源码调研

图形问题不能只看一条“GPU 耗时”。应用何时开始生产、buffer 何时提交、SurfaceFlinger 是否及时采纳、HWC 选择哪种合成方式、GPU job 何时执行，是五组不同的证据。本章以 Android 17 / API 37 / `android-17.0.0_r1` 为平台锚点，以 `android17-6.18-2026-06_r6` 为 kernel 锚点，说明各类工具能回答什么，以及哪些结论仍需要设备和 vendor 驱动支持。


## 1. 先确定问题属于哪一层

“掉帧”描述的是用户看到的结果，不等于“GPU 很慢”。Android 显示路径至少要拆成下面四层：

| 层次 | 主要问题 | 适合的证据 |
|---|---|---|
| 应用帧生产 | VSync 回调晚、主线程或 RenderThread 超期、引擎提交晚 | FrameTimeline、线程 slice、`dumpsys gfxinfo ... framestats`、应用自定义 marker |
| buffer 与 layer | 无可用 buffer、release fence 晚、BufferTX 积压、acquire fence 未就绪 | Perfetto BufferQueue/BufferTX、layer trace、fence、SurfaceFlinger dump |
| 系统合成与显示 | SurfaceFlinger 调度晚、CLIENT composition、HWC validate/present 慢 | SurfaceFlinger FrameTimeline、CompositionEngine、HWC/DisplayHAL、present fence |
| GPU 执行 | shader、带宽、overdraw、driver queue、频率或热限制 | AGI、Perfetto GPU render stages/counters、vendor profiler、GPU fence |

排查应沿 producer 到 display 的方向推进。只看到 RenderThread 很长，不能据此宣布 GPU 很慢；只看到 `queueBuffer()` 返回，也不能说明画面已经被显示。

## 2. 渲染类型决定证据是否完整

工具选择要从画面由谁生产开始。

### 2.1 标准 View / Compose 窗口

普通 View 和没有独立 `Surface` 的 Compose 页面，主体内容通常沿 `ViewRootImpl → HWUI RenderThread → App Window BLAST → SurfaceFlinger` 提交。此类页面的 FrameTimeline 覆盖较完整，可以从 expected/actual app frame 继续跟到 SurfaceFlinger display frame。

### 2.2 SurfaceView、Native Graphics 与游戏

`SurfaceView`、EGL/Vulkan 游戏或自有 render loop 会形成独立 producer 和 layer。宿主窗口的 `Choreographer#doFrame` 可能只代表外壳 UI，主体画面的提交点在引擎线程、`eglSwapBuffers()` 或 `vkQueuePresentKHR()`。

此时需要用 layer name、buffer frame number、present id、fence 和引擎 marker 对齐帧。标准 App Window 的 FrameTimeline slice 缺失，不能解释为“这一帧没有显示”；它只说明当前 Surface 没有提供同等完整的 token 证据。

### 2.3 TextureView

`TextureView` 先让外部 producer 写入 `SurfaceTexture`，再由宿主 HWUI 把该纹理采样进 App Window。SurfaceFlinger 通常只看到宿主窗口的结果。预览卡顿可能来自外部 producer，也可能来自宿主采样和重绘，单看 App Window 帧无法区分两者。

### 2.4 视频 overlay 与受保护内容

视频输出到 `SurfaceView` 时，可以成为独立 layer，并由 HWC 尝试 DEVICE composition。输出到 `TextureView` 时，视频 buffer 会先被宿主 GPU 采样，通常失去直接 overlay 的路径。

受保护内容不能依靠截图或 frame capture 验证像素，但 Perfetto 仍可观察线程、transaction、fence、layer 和 composition metadata。工具拿不到画面不等于显示链没有证据。

### 2.5 多窗口

多窗口会增加可见 layer、刷新率诉求、透明混合、缩放和 HWC plane 竞争。AOSP 没有“按窗口面积分配 GPU 调度权重”的通用策略，也没有为桌面窗口固定 60 FPS、后台窗口固定 30 FPS、画中画固定 50 MB 的规则。每个 producer 的 pacing、各 layer 的 composition type 和最终 display frame 才是可验证对象。

## 3. FrameTimeline：判断谁错过了显示计划

Android 17 的系统实现位于 SurfaceFlinger 的 `Scheduler/FrameTimeline.cpp`。Java API 不是独立的 `android.view.FrameTimeline` 文件，而是 `Choreographer.FrameData` 与 `Choreographer.FrameTimeline` 两个嵌套类。每个候选 timeline 提供 `vsyncId`、expected presentation time 和 deadline，而且这些对象只在 VSync callback 期间有效。

Perfetto 数据源名是 `android.surfaceflinger.frametimeline`。它生成应用和 SurfaceFlinger 两侧的 expected/actual timeline：

- `expected_frame_timeline_slice` 表示调度器给出的目标时间窗；
- `actual_frame_timeline_slice` 表示观测到的完成区间；
- app `surface_frame_token` 与 display `display_frame_token` 语义不同；
- 一个 DisplayFrame 可以包含多个进程、多个 layer 的 SurfaceFrame；
- `jank_type` 是分类线索，仍需结合线程、buffer、fence 和 composition 证据定位原因。

FrameTimeline 的 app actual end 包含应用 GPU 完成或 post 完成的较晚者，但它不是一条独立 GPU job 的执行时长。`SurfaceFlingerGpuDeadlineMissed` 也指向 SurfaceFlinger 合成侧错过 deadline，不等于目标应用的 shader 一定是根因。

下面的查询用于列出目标进程的 actual frame，并保留 layer 与两类 token，便于继续向显示侧核对：

```sql
SELECT
  process.name,
  actual_frame_timeline_slice.layer_name,
  actual_frame_timeline_slice.surface_frame_token,
  actual_frame_timeline_slice.display_frame_token,
  actual_frame_timeline_slice.ts,
  actual_frame_timeline_slice.dur,
  actual_frame_timeline_slice.present_type,
  actual_frame_timeline_slice.jank_type,
  actual_frame_timeline_slice.on_time_finish
FROM actual_frame_timeline_slice
LEFT JOIN process USING (upid)
WHERE process.name = 'com.example.app'
ORDER BY actual_frame_timeline_slice.ts;
```

查询结果中的 `ts` 和 `dur` 单位是纳秒。同一个 app token 可能对应多个 layer slice，分析时还要用 `layer_name` 过滤，不能把它们相加成“GPU 总耗时”。

## 4. Android 17 中的 FpsReporter 与 JankTracker

这两个类都存在，但职责和 outline 的伪代码不同。

### 4.1 FpsReporter

`FpsReporter::dispatchLayerFps()` 以 task id 找到对应的 layer hierarchy，收集该层级的 layer id，再调用 `FrameTimeline::computeFps()`。回调派发间隔至少 500 ms。

`computeFps()` 遍历 FrameTimeline 保存的 DisplayFrame，选出至少显示过一个目标 layer 的 present time，再按相邻 present 间隔计算历史 FPS。源码里没有 outline 所写的 `mFrameIntervalHistory` 60 帧 `vector`，也没有 `gpu.timestamp` 事件。

该能力通过 SurfaceComposer 内部接口注册 `IFpsListener`，面向系统组件，不等同于普通应用可随意使用的公开 FPS SDK。应用侧要记录业务场景和页面状态，可使用 JankStats、Macrobenchmark 或自有 frame marker；系统侧则优先使用 FrameTimeline。

### 4.2 JankTracker

Android 17 的 `JankTracker` 负责管理按 layer 注册的 listener，把已经生成的 `JankData` 放入后台队列，并在单 layer 累积到 50 条或显式 flush 时批量发送。它没有 `onFrameStarted/onFramePresented/onFrameFinished` 三个插桩点，也没有 1 ms、2 ms、5 ms 的轻中重三级阈值，更不会因 5 ms 超时触发 ANR。

帧分类发生在 FrameTimeline。Android 17 可见的类型包括 `AppDeadlineMissed`、`SurfaceFlingerCpuDeadlineMissed`、`SurfaceFlingerGpuDeadlineMissed`、`DisplayHAL`、`BufferStuffing`、`SurfaceFlingerStuffing`、`PredictionError`、`Dropped` 等。ANR 是进程响应性机制，不能由一条图形帧的固定毫秒阈值推导。

## 5. `dumpsys gfxinfo`：HWUI 帧统计，不是 GPU 遥测

`dumpsys gfxinfo` 通过目标进程的 `ActivityThread.dumpGfxInfo()` 进入 `ThreadedRenderer.handleDumpGfxInfo()`。Android 17 识别的核心参数包括 `framestats`、`reset` 和 bugreport 使用的 `-a`。源码没有 `gpu` 子命令，也没有下面这些属性：

- `gfxinfo.gpu_utilization`
- `gfxinfo.gpu_memory_used`
- `gfxinfo.gpu_power_state`
- `gfxinfo.memory_bandwidth_*`

采样用户路径前，可以先清空目标进程累积的 HWUI 数据：

```bash
adb shell dumpsys gfxinfo com.example.app reset
```

`reset` 只影响这组 profile 统计，不会重启应用，也不会清空 SurfaceFlinger、GPU driver 或 Perfetto 的状态。

执行完一段可复现操作后，用 `framestats` 导出逐帧时间戳：

```bash
adb shell dumpsys gfxinfo com.example.app framestats
```

输出适合观察该进程的 HWUI 帧分布和阶段时间。它不覆盖独立游戏 Surface、视频 decoder 到 overlay 的耗时，也不提供通用 GPU 利用率、显存带宽或整机功耗。Macrobenchmark 也会用 `gfxinfo` 在用户旅程前后圈定帧统计，因此测试前应固定包名、刷新率、设备温度和操作脚本。

开发者选项中的 Profile HWUI rendering 条形图同样偏向 UI/HWUI 阶段。`Process/Swap Buffers` 很长可能来自 driver flush、队列回压、等待 free slot 或 release fence，不能只凭条形图分辨 shader 与显示消费端。

## 6. SurfaceFlinger 与 HWC：确认第二次合成发生在哪里

应用 GPU 画完自己的 buffer 后，SurfaceFlinger 仍可能使用 RenderEngine 做 CLIENT composition。HWC 会按当前 layer stack 和硬件能力返回 composition type：

- `DEVICE`：该 layer 由显示硬件路径处理，常见于满足限制的 overlay；
- `CLIENT`：SurfaceFlinger 使用 RenderEngine 生成 client target，再交给 HWC；
- `SOLID_COLOR`、`CURSOR`、`SIDEBAND` 等类型还有各自约束。

`DEVICE` 不表示应用没有使用 GPU；游戏可能已经用 GPU 画完 layer，只是系统合成阶段不再采样它。`CLIENT` 也不表示卡顿一定来自应用 GPU，因为这次额外 GPU 工作属于 SurfaceFlinger/RenderEngine。

下面的命令用于获取当前 SurfaceFlinger 状态，确认 display、layer 和合成相关信息：

```bash
adb shell dumpsys SurfaceFlinger
```

dump 是时点快照，适合确认配置和当前状态；逐帧问题仍要回到 Perfetto、layer trace 与 fence。不同厂商可在 HWC/ComposerHAL 中加入扩展，AOSP dump 不保证暴露每个 DPU plane 的内部决策。

需要特别区分三种 fence：

- acquire fence：producer 写完当前 buffer 后，consumer 才能读取；
- release fence：显示端不再使用旧 buffer 后，producer 才能安全复用；
- present fence：本轮 display present 的完成反馈。

`queueBuffer()` 返回不代表 acquire fence 已 signal；SurfaceFlinger 已采纳 transaction 也不代表面板已完成扫描。Android 17 kernel 锚点下，这些异步关系以 dma-fence/sync_file 为基础，vendor GPU 与 display driver 的 tracepoint 仍会有差异。

## 7. Perfetto 的 GPU 数据：能力由设备声明

Perfetto 定义了多组 GPU 数据源：

| 数据源 | 能回答的问题 | 关键限制 |
|---|---|---|
| `gpu.counters` | 频率、忙碌度、cache、带宽等设备提供的计数器 | counter id 和含义由 producer 描述；不同 GPU 不可硬套同一组 id |
| `gpu.renderstages` | GPU graphics/compute submission 的阶段与硬件队列 | 需要 driver 或 profiler producer 支持；没有数据不代表 GPU 空闲 |
| `vulkan.memory_tracker` | Vulkan allocation 与 bind | 只覆盖 Vulkan 可观察范围，不等于系统总显存 |
| `gpu.log` | GPU debug 消息 | 取决于 producer 和配置 |
| `linux.ftrace` | GPU 频率、`gpu_mem_total`、DRM scheduler/fence 等 kernel 事件 | tracepoint 名与可用性受 kernel 和 vendor 驱动影响 |

Android 17 tag 中的 `GpuCounterConfig` 支持采样周期、counter id、instrumented sampling 和 trace 期间固定 GPU clock 的请求；`GpuRenderStagesConfig` 支持 low-overhead 模式与 stage metrics。配置字段存在，不代表每台 API 37 设备都实现相同 producer。采集前应查询设备上注册的数据源及其 descriptor，再选择 counter。

如果 trace 中只有 FrameTimeline，没有 `gpu.renderstages`，可以证明帧是否超期，却不能把 app actual slice 直接当成 shader duration。反过来，GPU job 很长也要继续确认它属于目标进程、哪次 submission，以及是否影响目标 display frame。

## 8. AGI：GPU 深挖工具，不替代显示时间线

Android GPU Inspector 提供两类分析：

- System Profiler：把 CPU、系统服务、GPU、内存、功耗和 GPU counter 放在同一时间轴；
- Frame Profiler：捕获单帧的 Vulkan/OpenGL ES 调用和 GPU 工作，适合分析 pass、draw call、shader 与资源。

AGI 更适合回答“GPU 在做哪类工作、哪一段贵”。FrameTimeline、SurfaceFlinger 和 HWC 更适合回答“这张 buffer 是否赶上目标显示周期”。两者需要用 submission、buffer、frame/present id 和时间戳对齐。

设备、GPU、驱动和图形 API 必须满足 AGI 支持条件。受保护内容、系统 surface、不可调试进程或 vendor 限制可能阻止 frame capture。系统分析工具自身也可能改变调度、频率和温度，长时间 profile 的结果应与低开销 trace、无采集基线互相验证。

截至本章复核时，Android Developers 的 AGI quickstart 已把 Android Performance Analyzer 标为新的 system profiling 推荐工具；AGI 的 frame profiling 仍用于 Vulkan/OpenGL ES 单帧深挖。工具名称会继续变化，证据层次与显示路径边界不会因此改变。

## 9. `gpu` 服务：有真实服务，没有 `gpu-debugd`

Android 17 启动的是独立 `gpuservice` 进程，并向 ServiceManager 注册名为 `gpu` 的 Binder 服务。源码没有 `gpu-debugd` 服务，也没有 outline 中的 TCP 远程调试协议。

`GpuService::doDump()` 支持 driver info、GPU stats、GPU memory 和 GPU work 等分支。下面的命令用于查看设备是否提供相应数据：

```bash
adb shell dumpsys gpu
adb shell dumpsys gpu --gpumem
adb shell dumpsys gpu --gpuwork
adb shell cmd gpu help
```

`--gpumem` 依赖 `gpu_mem/gpu_mem_total` tracepoint 与 eBPF map，输出全局及按进程的 GPU memory snapshot；`--gpuwork` 依赖 `power/gpu_work_period`，按 GPU id 和 UID 汇总 active/inactive duration。驱动未提供 tracepoint、BPF 程序未加载或设备策略不支持时，命令会报告不可用。它们不是通用的逐帧 shader profiler。

## 10. 一套可复现的排查顺序

### 10.1 固定复现条件

记录设备 build fingerprint、刷新率、分辨率、温度、充电状态、应用版本和页面操作。GPU 降频常在持续负载后出现，冷机的几秒结果不能代表稳定性能。

### 10.2 锁定 producer 与目标 layer

确认主体画面属于 App Window、SurfaceView、TextureView、视频 layer 还是引擎 swapchain。用进程、线程、layer name 和 surface 关系排除 SystemUI、输入法、壁纸及其他窗口。

### 10.3 从 FrameTimeline 选一帧

比较 expected 与 actual，记录 app token、display token、present type、jank type 和 layer name。若目标 Surface 没有完整 FrameTimeline，改用 buffer frame number、present id 与 fence。

### 10.4 沿 producer 查到 `queueBuffer`

标准页面看主线程、RenderThread、`dequeueBuffer`、`queueBuffer`；native/game 看 logic、RHI/render thread、acquire、submit、swap/present。函数调用很长时，结合线程状态和 fence 判断它在执行还是等待。

### 10.5 沿 buffer 查到 display

核对 BufferTX、transaction readiness、latch、acquire fence、composition type、RenderEngine、HWC validate/present 与 present fence。buffer 已提交但显示晚，问题常在这一段。

### 10.6 有 GPU 证据再下 GPU 结论

用 AGI、`gpu.renderstages`、GPU counter 或 vendor profiler 确认 GPU job、硬件队列、频率与瓶颈类型。只有 CPU slice 或 FrameTimeline 分类时，应写“怀疑 GPU/合成侧，待 GPU 证据确认”，不要写成已证实的 shader 问题。

## 11. 调试开销怎样评估

不存在跨设备通用的 “Perfetto 每帧增加 0.3 ms” 或 “FrameTracer 固定增加 2–3 ms”。开销取决于：

- 数据源数量、buffer 大小与采样频率；
- GPU counter 是否使用 instrumented sampling；
- 是否记录调用栈、binder、sched、ftrace 和 layer trace；
- frame capture 是否重放或插装命令；
- 设备存储、USB、温度和 vendor driver。

安全的做法是保存无采集基线，再依次启用 FrameTimeline、sched/graphics、GPU counter、render stages 或 frame capture；每加一组数据都比较帧率、温度和频率。线上版本只保留经过成本评估的轻量业务 marker 与聚合指标，深度 GPU capture 放在可控测试设备上。

## 12. Android 12—17 的版本边界

| 版本 | 与本章相关的边界 |
|---|---|
| Android 12 / API 31 | FrameTimeline 与现代 BLAST App Window 诊断成为可用基线 |
| Android 13 / API 33 | `AChoreographer` 的多 FrameTimeline 查询接口进入 API；unsignaled buffer latch 改变部分 transaction 与 fence 的观察顺序 |
| Android 14 / API 34 | SurfaceView 的 alpha/lifecycle 能力扩展，但不会把标准 App Window 自动变成独立 Surface |
| Android 15 / API 35 | HDR、edge-to-edge 等策略可能改变 layer 与合成成本，producer/consumer 基本边界不变 |
| Android 16 / API 36 | 主显示路径继续沿用 FrameTimeline、BLAST、SurfaceFlinger 与 HWC；工具结果仍受 vendor 实现影响 |
| Android 17 / API 37 | 本章固定源码锚点；`FpsReporter`、`JankTracker`、`GpuService` 和 Perfetto 配置均按该 tag 的当前实现描述 |

“在 Android 17 源码中存在”不等于“Android 17 新增”。`android-12.0.0_r1` 已包含 `FpsReporter.cpp`，`android-16.0.0_r1` 已包含当前这条 `JankTracker` 分支；因此不能把它们写成 Android 17 新能力。其他版本演进结论也需要旧 tag 或公开 API level 记录支持。

## 13. Review 检查表

- 是否先识别 producer、Surface 和 layer，而非从 UI 框架名称猜测？
- 是否区分 app GPU rendering 与 SurfaceFlinger CLIENT composition？
- 是否区分 `surface_frame_token`、`display_frame_token`、buffer frame number 和 Vulkan present id？
- 是否把 acquire、release、present fence 分开解释？
- 是否把 `gfxinfo` 限定在 HWUI 帧统计，没有虚构 GPU 利用率和带宽字段？
- 是否确认设备注册了所用 Perfetto GPU data source 与 counter descriptor？
- 是否用 GPU job/counter/driver 证据支撑“GPU 瓶颈”结论？
- 是否记录采集开销、温度、刷新率和无采集基线？
