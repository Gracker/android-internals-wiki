## 复核定位：先区分五种状态

看到 AOSP 中存在一个 `.c` 文件，不能直接写成“所有 Android 17 设备都在采集”。
一项 Android BPF 能力至少要经过五个状态：

1. 源文件由 `libbpf_prog` 编译成 `.bpf` 对象；
2. 对象被列入产品镜像的 `required`；
3. `bpfloader` 根据架构、内核版本和 aconfig flag 决定是否加载；
4. 程序被 attach，map、program 或 link 被 pin 到 `/sys/fs/bpf/`；
5. system 组件读取 map 或 iterator，并把结果用于统计、诊断或上报。

Android 17 的 `bpfloader` 已经是 Rust 入口，`Loader.cpp` 提供
`libbpf_android` 兼容层。本文讨论的四项程序都由
`platform/system/bpfprogs` 构建，再由 `platform/system/bpf/loader/bpfloader.rs`
描述加载、权限和 pin 路径。

## Android 17 的四项程序

下面的表按源码名称列出能力边界：

| 对象 | 构建与开关 | attach 点 | 能回答的问题 |
| --- | --- | --- | --- |
| `cyclePerUid.bpf` | 仅 x86_64；还要求 `x86_cpu_energy_attribution` | `tp_btf/sched_switch`，由消费者按需 attach | 各 UID 在统计窗口内消耗了多少 CPU cycle |
| `dmabufIter.bpf` | 除 riscv64；`load_dmabuf_iterator` | `iter/dmabuf`，loader 自动 attach | 当前 DMA-BUF 的 inode、size、name、exporter |
| `kernelWakelockDuration.bpf` | `kernel_wakelock_duration` | `raw_tp/wakeup_source_activate` 与 `deactivate` | 系统至少持有一个 kernel wakeup source 的累计时长 |
| `bpfLockContention.bpf` | 除 riscv64；`load_bpf_lock_contention`；内核至少 6.1 | `tp/lock/contention_begin` 与 `contention_end` | 白名单内核锁按进程聚合的竞争时长 |

三个 aconfig flag 出现在
`system/bpfprogs/progs.aconfig`。`.bpf` 文件被打进 system image 只表示具备加载
条件；flag 未开启时，`get_file_vec()` 不会把对应描述加入本次加载列表。

### 1. `cyclePerUid`：这是 x86 能耗归因组件

`cyclePerUid.c` 定义了五个 map：

- `last_recorded_cycle_map`：每 CPU 保存上一次 cycle 读数；
- `last_running_pid_map`：每 CPU 保存上一次调度进入的 PID；
- `uid_cpu_cycle_map`：以 UID 为 key 的 `LRU_PERCPU_HASH`；
- `tsc_events`：每 CPU 一个 perf event，用来读取 TSC cycle；
- `desync_counter`：统计 suspend/resume 等情况下前后 PID 对不上的次数。

在 `sched_switch` 上，当前 task 是即将换出的 `prev`。程序读取该 CPU 的 perf event
counter，与上一次读数相减，再用 `bpf_get_current_uid_gid()` 得到 `prev` 的 UID，
把 cycle 差值累加到 `uid_cpu_cycle_map`。

两个构建文件把它限制在 x86_64：

- `system/bpfprogs/Android.bp` 默认 `enabled: false`，只在 x86_64 打开；
- `system/bpf/loader/bpfloader.rs` 用 `#[cfg(target_arch = "x86_64")]` 包住加载描述。

`frameworks/native/libs/cpucycleperuid/lib.rs` 还读取
`/sys/class/powercap/intel-rapl:0/energy_uj`。用户态库计算统计窗口内的 package energy
变化，再按各 UID 的 cycle 增量分摊。这是基于 cycle 比例的归因结果，不是硬件为
每个 UID 提供的独立电能计数。

因此，这条能力不能写成 arm64 手机的 Android 17 通用特性。在 arm64 SoC 上，应根据
目标产品已有的 time-in-state、PMU、PowerStats HAL 和厂商能耗模型选择数据源。

### 2. `dmabufIter`：给出系统快照，不给完整生命周期

`dmabufIter.c` 的 section 是 `iter/dmabuf`。每个 `dma_buf` 只输出四个字段，并用换行
分隔：

1. inode；
2. size；
3. 可选的 buffer name；
4. exporter name。

name 可以由用户空间设置，程序会把其中的换行替换为空格，避免破坏四行一组的格式。
Android 17 的 `libdmabufinfo` 通过
`/sys/fs/bpf/dmabuf/prog_dmabufIter_iter_dmabuf` 打开 iterator，把 size 与 buffer
数量按 exporter 聚合。

这份快照适合回答“当前总共有多少 DMA-BUF”“哪个 exporter 占用较大”“重复采样时
数量是否持续增长”。它没有输出 PID、fd、attachment count 或引用计数，也不记录
分配、释放事件。看到某个 exporter 的总量增长，只能得到调查方向；还需要结合
`/proc/<pid>/fdinfo`、gralloc、GPU、camera、codec 和 SurfaceFlinger 证据定位持有者。

对于渲染问题，`dmabufIter` 可以补充前后两个时点的内存快照。帧为何迟到仍要看
Perfetto 中的 producer、consumer、fence、调度与合成事件，iterator 不能替代帧时间
分析。

### 3. `kernelWakelockDuration`：统计“至少一个”，不区分名称

内核 `wakeup_source_activate` 和 `wakeup_source_deactivate` tracepoint 都携带
`name` 与 `state`。Android 17 的 BPF 程序只读取第二个参数 `state`，没有读取或保存
name。

`state` 是 combined event counter：低半部分表示正在进行的 kernel wakeup events
数量，高半部分表示已完成数量。程序在低半部分从 0 变 1 时减去
`bpf_ktime_get_boot_ns()`，从 1 变 0 时加回当前 boot time。`timer_state_ns` 因而表示
“系统至少存在一个活跃 kernel wakeup source”的累计时间。

`initialize()` 还要处理 loader attach 附近乱序到达的事件，以及高半部分 16 位计数
回绕。它会观察足够多的新事件后才把 `program_init` 标成完成，避免用旧事件破坏
累计值。

该 map 不能告诉你哪个 wakeup source 持有最久，也不能按 UID 归因。要定位具体名称，
仍需 Perfetto/ftrace 的 wakeup source 事件、`/sys/kernel/debug/wakeup_sources` 或
产品已有的功耗统计。

### 4. `bpfLockContention`：只观察白名单内核锁

Android 17 的程序监听内核 `contention_begin` / `contention_end` tracepoint。begin
时以 `{tgid, tid, lock_name}` 记录开始时间；end 时删除这条临时记录，并以
`{tgid, lock_name}` 聚合：

- `sum`：等待总时长；
- `count`：竞争次数；
- `max` / `min`：单次等待的极值；
- `comm`：创建聚合项时记录的进程名。

程序不会追踪任意锁地址。`bpf_lock_list.h` 在 Android 17 中列出 11 个全局锁和 6 个
可从当前 `task_struct` 找到的动态锁，例如 `tasklist_lock`、`cgroup_mutex`、
`rtnl_mutex`、`mmap_lock`、`page_table_lock` 与 `pi_lock`。其他地址会被
`LOCK_ID_UNKNOWN` 分支丢弃。

`sum` 和 `count` 使用原子加法；源码明确把 `min` / `max` 更新标为“racy but
simpler”。高并发时，极值可能发生覆盖，不能把它们当作无误差的审计数据。这项程序
观察的是内核锁竞争，也不能直接解释 Java monitor、Kotlin mutex 或应用 C++ mutex。

## 加载、权限与 pin 路径

`bpfloader` 为每个对象声明 map/program 的 group、权限、最低内核版本和是否自动
attach。自动 attach 的对象会把 BPF link pin 到原本用于 program 的路径；非自动
attach 的 `cyclePerUid` 则 pin program，等待 `libcycleperuid` 建立 perf events 并
attach `sched_switch`。

典型 pin 前缀如下：

| 对象 | bpffs 前缀 |
| --- | --- |
| cycle per UID | `/sys/fs/bpf/cpucycleperuid/` |
| DMA-BUF iterator | `/sys/fs/bpf/dmabuf/` |
| kernel wakelock duration | `/sys/fs/bpf/kernelwakelockduration/` |
| lock contention | `/sys/fs/bpf/lock_contention/` |

这些路径面向 root/system 组件，并不构成第三方应用 API。普通应用受 UID、SELinux、
bpffs 权限和 BPF syscall 限制，不能依赖直接读取系统 map。产品若要对应用开放指标，
应由受信任的系统服务读取并做权限、隐私和采样频率控制。

## 设备上怎样核对

下面的命令用于 userdebug/eng 设备确认镜像、flag 与 pin 状态；量产 user build 可能
只允许其中一部分读取。

```bash
adb shell getprop ro.build.version.release
adb shell uname -r
adb shell ls -l /system/etc/bpf/
adb shell ls -l /sys/fs/bpf/cpucycleperuid/ \
  /sys/fs/bpf/dmabuf/ \
  /sys/fs/bpf/kernelwakelockduration/ \
  /sys/fs/bpf/lock_contention/
adb shell logcat -b all -d | grep -i bpfloader
```

镜像中有对象、bpffs 中有 pin、日志显示成功 attach 是三种不同证据。某个目录缺失时，
按“架构 → 内核版本 → aconfig flag → loader 错误 → SELinux/权限”顺序排查。

`bpftool` 在 Android 17 的 `bpfloader` 构建中只作为 debuggable 产品依赖。设备提供
它时，可以继续查看 program、map 和 link：

```bash
adb shell su root bpftool prog show
adb shell su root bpftool map show
adb shell su root bpftool link show
```

这些列表可以证明对象是否加载和 attach，但还不能证明用户态消费者正在读取。需要
再检查对应 system service、测试负载和指标变化。

下面的命令用于读取 DMA-BUF iterator 的文本快照，前提是设备已打开 flag 且调用者有
权限：

```bash
adb shell su root cat \
  /sys/fs/bpf/dmabuf/prog_dmabufIter_iter_dmabuf
```

输出每四行为一块 buffer。计算总量时要按 exporter 聚合并去重 inode；不要把 name
当作可信的进程标识。

## 与 Perfetto 的关系

这四个 BPF 对象没有自动变成 Perfetto track 的共同机制。map/iterator 中的数据需要
用户态 consumer 读取，再由 statsd、PowerStats、诊断工具或自定义 Perfetto producer
输出。文章若声称“启用 BPF 后 Perfetto 自动出现某条轨道”，必须给出对应 producer
与 trace packet 源码。

选择工具时按问题来：

| 问题 | 主证据 | BPF 补充 |
| --- | --- | --- |
| UI 卡顿、掉帧 | Perfetto frame timeline、sched、binder、freq、fence | lock contention 可提示白名单内核锁等待 |
| 图形/相机 buffer 增长 | gralloc、dma-buf、SurfaceFlinger/camera dump | dmabuf iterator 做系统快照与 exporter 聚合 |
| suspend 被阻止 | suspend/resume、wakeup source、PowerStats | kernel wakelock duration 给出系统被阻止的累计时间 |
| x86 产品 UID 能耗 | RAPL、任务负载、频率和温度 | cycle per UID 用 cycle 比例分摊 package energy |

eBPF 的采集开销取决于 attach 频率、map 类型、key 数、用户态读取周期和 workload。
“近乎零开销”不适合作为统一结论。上线前应做 flag 开关对照测试，至少比较 CPU time、
调度长尾、内存、功耗和事件丢失。
