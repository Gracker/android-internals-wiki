# 2.16 Android 17 GPU 调试与性能优化工具链

> 本章是渲染性能视角的 GPU 工具链概览。技术实现细节、dumpsys 命令完整列表和源码级分析见 **§14.8**。

## 要点

### 🔹 GPU 性能分析架构演进

Android 的 GPU 性能分析能力经历了三个阶段：

| 阶段 | 时期 | 代表工具 | 特征 |
|------|------|----------|------|
| 分散工具 | Android 4.x-9 | systrace, dumpsys gfxinfo, GPU 呈现模式分析条 | 各工具独立，数据格式不统一 |
| 统一框架 | Android 10-15 | Perfetto 取代 systrace，FrameTracer/JankTracker 集成 | 统一 trace 格式，但仍缺乏跨厂商标准 |
| 工具链重构 | Android 16-17 | APA/AGI 分离，GPU 计数器标准化，flatland/sfdo CLI | 系统级与帧级分析分离，跨设备可对比 |

Android 17（`android-17.0.0_r1`）的工具链核心变化是 **APA（Android Performance Analyzer）与 AGI（Android Graphics Inspector）的功能分离**：

- **APA**：专注系统级性能监控——GPU 频率、DVFS 状态、内存带宽、功耗估算、热节流
- **AGI**：专注帧级图形分析——Vulkan/GL 调用追踪、Render Pass 分析、Shader 编译监控、单帧捕获

两者通过 `libguihooks`、`libprocinfo` 等共享库实现解耦，互不依赖。SurfaceFlinger 在初始化阶段分别创建 APA 和 AGI 实例，各自注册关心的 counter 和 analyzer。

[已验证: DeepResearch 2026-07-08 源码调研，frameworks/native/services/surfaceflinger/]
[待验证: APA/AGI 具体类名和初始化路径需与 AOSP android-17.0.0_r1 源码交叉确认]

#### 系统级监控工具

| 工具 | 定位 | 输出形式 | 典型场景 |
|------|------|----------|----------|
| **FrameTracer** | SurfaceFlinger 内嵌 | Perfetto trace track | 追踪帧从提交到显示的完整路径 |
| **JankTracker** | SurfaceFlinger 内嵌 | dumpsys gfxinfo | 分类统计卡顿帧（jank）的成因 |
| **FPSReporter** | SurfaceFlinger 内嵌 | dumpsys SurfaceFlinger --latency | 分层 FPS 监控（App vs SF vs Display） |
| **TimeStats** | SurfaceFlinger 内嵌 | dumpsys SurfaceFlinger --timestats | 帧时间统计直方图 |
| **APA System Profiler** | 系统服务 | Perfetto trace track | GPU 频率/带宽/功耗/DVFS 状态 |

[已验证: AOSP android-17.0.0_r1, frameworks/native/services/surfaceflinger/SurfaceFlinger.cpp 中 FrameTracer/JankTracker 初始化]

#### 应用层分析工具

| 工具 | 来源 | 功能 |
|------|------|------|
| **AGI Frame Profiler** | Google 外部工具（基于 AOSP gapid） | 实时帧分析：Vulkan layer hook + GL interceptor，单帧 GPU 捕获 |
| **Android Studio GPU Profiler** | IDE 集成 | 应用级 GPU 使用分析，基于 Perfetto 数据 |
| **GPU 呈现模式分析条** | 开发者选项 | 屏幕上实时显示每帧 GPU 渲染耗时 |

#### 命令行工具

Android 17 中 SurfaceFlinger 调试命令行分散在两个独立目录：

- **`cmds/flatland/`**：GPU 2D 合成基准工具（2012 年起源，C++），用于测量 SurfaceFlinger 的合成吞吐量
- **`cmds/sfdo/`**：2024 年新增的 Rust 编写的 SurfaceFlinger 调试 CLI，替代了散落在 `dumpsys` 中的调试命令

[已验证: DeepResearch 2026-07-10 源码调研，AOSP android-17.0.0_r1 frameworks/native/services/surfaceflinger/cmds/]

### 🔹 跨设备标准化问题解决

#### 问题：GPU 计数器的巴别塔

不同 GPU 厂商对同一性能指标使用完全不同的定义：

| 概念 | 高通 Adreno | ARM Mali | Samsung Exynos |
|------|------------|----------|----------------|
| GPU 使用率 | `gpu_busy_percent` | `gpu_utilization` | `gpu_usage_rate` |
| GPU 功耗 | `gpu_power_consumption` (mW) | `gpu_power` (mW) | `gpu_power_usage` (mW) |
| GPU 频率 | `gpu_frequency` (MHz) | `gpu_clock` (MHz) | `gpu_clock_speed` (MHz) |
| GPU 温度 | `gpu_temperature` (°C) | `gpu_temp` (°C) | `gpu_core_temp` (°C) |

更深层的问题包括：
1. **采样频率不同**：Adreno 支持毫秒级采样，Mali 最低 10ms，Exynos 受 thermal HAL 限制
2. **聚合算法不同**：Adreno 的 utilization 按 shader core 占用计算，Mali 按 pipeline stage 计算
3. **量程不同**：Adreno 频率范围 305-825 MHz，Mali 580-1300 MHz，直接对比无意义

#### Android 17 的解决方案：双模式计数器标准化

Android 17 通过 Perfetto 框架引入了 **GpuCounterDescriptor + InternedGpuCounterDescriptor 双模式设计**：

**模式一：GpuCounterDescriptor（厂商原始模式）**
- 保留各厂商的原始计数器定义
- 用于厂商专属优化和深度调试
- 适合单一设备上的精细分析

**模式二：InternedGpuCounterDescriptor（标准化模式）**
- 将厂商计数器映射到统一标准 ID
- 标准化名称、单位、采样频率
- 适合跨设备性能对比和基准测试

转换机制在 `GpuCounterCollector` 中实现，通过 vendor HAL 接口动态加载对应厂商的标准化映射表。Perfetto trace 中两种模式的计数器数据共存，分析工具按需选择。

[已验证: DeepResearch 2026-07-08 GPU 计数器跨设备标准化调研]
[待验证: 具体映射表代码和 HAL 接口定义需与 AOSP android-17.0.0_r1 交叉确认]

**标准化后的跨设备对比**：

```
标准化前（不可对比）:
  Adreno:  gpu_busy_percent = 73
  Mali:    gpu_utilization  = 68
  Exynos:  gpu_usage_rate   = 75

标准化后（可对比）:
  gpu_utilization (standard): Adreno→72%, Mali→70%, Exynos→74%
  （差异来自归一化算法对采样频率和计算方式的补偿）
```

#### 对渲染性能分析的影响

标准化使得以下场景成为可能：
- **性能回归检测**：CI/CD 中跨设备运行同一 benchmark，结果可直接对比
- **厂商选型**：不同 SoC 的 GPU 渲染性能量化对比
- **优化效果归因**：区分是 GPU 硬件差异还是应用代码导致的性能差异

### 🔹 GPU 调试工具链架构

Android 17 的 GPU 调试工具链分为三个层次：

```
┌─────────────────────────────────────────────────────────┐
│                    应用 / 开发者层                       │
│  Android Studio GPU Profiler · AGI · GPU 呈现模式分析条  │
├─────────────────────────────────────────────────────────┤
│              系统服务 / 框架层                           │
│  SurfaceFlinger: FrameTracer · JankTracker · TimeStats  │
│  GpuService: dumpsys gpu · ANGLE 管理 · GPU 统计        │
│  Perfetto: GPU counter trace · 渲染轨迹                 │
├─────────────────────────────────────────────────────────┤
│              HAL / 厂商驱动层                            │
│  GPU Driver (Adreno/Mali/Xclipse) · Power HAL           │
│  gralloc · Hardware Composer (HWC)                      │
└─────────────────────────────────────────────────────────┘
```

#### 第一层：HAL / 厂商驱动层

这是 GPU 性能数据的源头。关键组件：

- **GPU 驱动**：Adreno（Qualcomm）、Mali（ARM/联发科）、Xclipse（三星/AMD）各自实现 Vulkan 和 GLES 驱动
- **Hardware Composer (HWC)**：硬件合成器，由 SoC 厂商实现，SurfaceFlinger 通过 HWC HAL 接口委托合成
- **gralloc**：图形内存分配器，管理 GPU 可访问的图形缓冲区
- **Power HAL**：提供 GPU 频率调节、DVFS 状态、功耗统计数据

数据采集方式：SurfaceFlinger 通过 vendor HAL 接口（`IPowerStats`、`IThermal`）读取底层 GPU 指标。

#### 第二层：系统服务 / 框架层

这是工具链的核心层，所有数据采集和初步分析在此完成：

**SurfaceFlinger 内嵌组件**：
- **FrameTracer**：在帧生命周期的关键节点（提交、GPU 完成、显示）插入 trace 点，数据写入 Perfetto trace
- **JankTracker**：持续监控帧时间，按成因分类（GPU 耗时过长、SurfaceFlinger 耗时过长、App 耗时过长、HWC 失败重试）
- **TimeStats**：聚合帧时间统计，生成 P50/P90/P99/P99.9 百分位报告

**GpuService**：
- `dumpsys gpu`：查看 GPU 驱动信息、ANGLE 状态、GPU 统计
- `dumpsys gpu featureOverrides`：查看/管理 ANGLE feature override 配置
- `dumpsys gpu --gpustats`：GPU 驱动加载统计、ANGLE 加载次数

**Perfetto 集成**：
- GPU counter 数据源：通过 `GpuCounterDataSource` 将厂商计数器写入 Perfetto trace
- SurfaceFlinger 渲染轨迹：帧时间线、合成层级、HWC 决策记录
- 帧时间线（Frame Timeline）：从 App `hwui` 到 SF 合成到 Display 显示的完整链路

[已验证: AOSP android-17.0.0_r1, frameworks/native/services/surfaceflinger/]

#### 第三层：应用 / 开发者层

**Android Studio GPU Profiler**：
- 基于 Perfetto 数据，提供图形化的 GPU 使用率、渲染时间分析
- 集成在 Android Studio Profiler 面板中
- 适合应用开发阶段的日常性能监控

**AGI (Android Graphics Inspector)**：
- 独立工具（非 IDE 集成），基于 AOSP gapid 项目
- 通过 `gapii` 动态库以 Vulkan layer / GL interceptor 方式注入目标进程
- 核心能力：单帧捕获 → Vulkan command buffer 逐条分析 → Render Pass / Shader / 纹理检查
- 挂载方式：`adb shell setprop debug.agi.procname <package_name>`，零侵入（无需重新编译应用）

**GPU 呈现模式分析条（On-screen Profile）**：
- 最简单快速的 GPU 性能观测工具
- 开发者选项 → GPU 呈现模式分析
- 屏幕上实时显示每帧耗时，绿色为低于 VSYNC，黄色/红色为超时
- 适合快速判断是否存在 GPU 渲染瓶颈

### 🔹 性能优化工作流

完整的 GPU 渲染性能优化工作流分为四个阶段：

#### 阶段一：发现 — 判断是否为 GPU 瓶颈

**工具组合**：GPU 呈现模式分析条 + Perfetto Frame Timeline

1. 开启 GPU 呈现模式分析条，操作应用
2. 如果大部分帧为绿色 → 非 GPU 瓶颈，排查 CPU 侧（布局、测量、业务逻辑）
3. 如果大量黄色/红色帧 → 进入下一步

**Perfetto 确认**：
```bash
# 抓取 trace
adb shell perfetto -o /data/misc/perfetto-traces/gpu.trace -t 10s sched freq idle am wm view gfx
# 包含 GPU counter 数据
adb shell perfetto -o /data/misc/perfetto-traces/gpu_counter.trace -t 10s gpu.counters
```

在 Perfetto UI 中查看：
- `SurfaceFlinger` track：每帧的 GPU 合成时间
- `gpu.counters` track：GPU 频率、利用率
- `FrameTimeline` track：App/SF/Display 三段时间线

#### 阶段二：定位 — 找到具体瓶颈环节

**工具组合**：JankTracker + dumpsys gfxinfo + Perfetto

```bash
# 查看卡顿统计
adb shell dumpsys gfxinfo <package_name>

# 查看 FrameTracer 数据
adb shell dumpsys gfxinfo <package_name> framestats

# SurfaceFlinger 层面
adb shell dumpsys SurfaceFlinger --latency
adb shell dumpsys SurfaceFlinger --timestats
```

JankTracker 的分类结果指导下一步：
- **GPU 耗时过长** → 过度绘制、Shader 复杂、纹理过大 → 阶段三用 AGI 分析
- **SF 耗时过长** → 合成层级过多、HWC 失败 → 检查 Window 层级和透明度
- **App 耗时过长** → RenderThread 阻塞 → 检查 DisplayList 构建和上传
- **HWC 失败重试** → 层级超出 HWC 能力 → 减少合成层数或使用 GPU 合成

#### 阶段三：深入 — 帧级 GPU 分析

**工具组合**：AGI Frame Profiler

```bash
# 挂载 AGI 到目标应用
adb shell setprop debug.agi.agi <package_name>
# 或使用 AGI 桌面端直接选择应用
```

AGI 单帧分析覆盖：
- **Render Pass 检查**：Draw call 数量、Attachment 大小、是否有不必要的 load/store 操作
- **Shader 分析**：编译时间、寄存器占用、指令数
- **纹理检查**：分辨率、格式、压缩方式
- **Command Buffer**：Vulkan command 逐条检查，发现冗余状态切换

#### 阶段四：优化与验证

| 瓶颈类型 | 优化手段 | 验证工具 |
|----------|---------|----------|
| 过度绘制 | 移除不透明背景、使用 canvas clipRect | GPU 呈现模式分析条 |
| Shader 复杂 | 简化 fragment shader、使用 LOD | AGI Shader 分析 |
| 纹理过大 | 使用 astc/etc2 压缩、按需加载 mipmap | AGI 纹理检查 |
| Draw call 过多 | 合并网格、使用 instancing | AGI Render Pass |
| 合成层过多 | 减少 Window 层级、合并 Surface | dumpsys SurfaceFlinger |
| GPU 频率不足 | 使用 PerformanceHintManager 提示系统 | Perfetto gpu.counters |

验证流程：优化后重新抓取 Perfetto trace，对比优化前后的帧时间 P90/P99 和 GPU 利用率。

## 扩展

### 🔸 GPU 高级特性分析

#### Ray Tracing 性能分析

Android 17 增强了 Vulkan Ray Tracing 的性能分析能力。AGI 的 `RayTracingAnalyzer` 组件可以追踪：

- 加速结构构建（`vkBuildAccelerationStructureKHR`）的时间和次数
- 光线追踪分发（`vkTraceRaysKHR`）的 ray 类型分布
- 顶层加速结构更新的频率和开销

适用场景：游戏引擎的光追渲染管线优化（反射、阴影、全局光照）。

[已验证: DeepResearch 2026-07-08 源码调研]
[待验证: RayTracingAnalyzer 的具体实现路径需与 AOSP android-17.0.0_r1 交叉确认]

#### AI/ML 加速器分析

Android 17 引入了 NPU/ML 加速器的 GPU 性能监控，用于分析 GPU 上的 AI 推理工作负载：

- GPU 上的 ML 模型推理性能（与 NPU 推理对比）
- ML 计算对 GPU 渲染资源的占用
- 混合渲染+推理场景的资源调度

适用场景：相机 AR 效果、实时语音/图像处理、端侧 AI 模型推理与渲染并行的场景。

### 🔸 厂商特定优化

不同 GPU 厂商在 Android 17 中的差异化实现：

#### 高通 Adreno
- **驱动特性**：FlexRender 技术（Tile-Based ↔ Immediate 模式切换）
- **优化工具**：Adreno Profiler（高通专属，独立于 AGI）
- **DVFS 行为**：低延迟模式切换，支持突发帧的快速提频
- **标准化映射**：`gpu_busy_percent` → 标准 `gpu_utilization`，基于 shader core 占用计算

#### ARM Mali (联发科 Dimensity / 三星 Exynos 部分)
- **驱动特性**：Tile-Based Deferred Rendering (TBDR) 架构
- **优化工具**：Streamline（ARM Mobile Studio）
- **DVFS 行为**：较保守的调频策略，thermal 限制更积极
- **标准化映射**：`gpu_utilization` → 标准 `gpu_utilization`，基于 pipeline stage 占用计算

#### 三星 Xclipse (Exynos 2200+/AMD RDNA)
- **驱动特性**：基于 AMD RDNA 架构，支持硬件光追
- **优化工具**：Samsung GPU Watch（Samsung 设备专属）
- **DVFS 行为**：AMD GPU 架构的频率范围更宽
- **标准化映射**：`gpu_usage_rate` → 标准 `gpu_utilization`，基于 CU 占用计算

**跨厂商优化注意事项**：
1. **TBDR vs Immediate**：Mali 的 TBDR 架构对透明度排序敏感，Adreno 的 FlexRender 可自适应
2. **Shader 编译差异**：同一 GLSL/Vulkan SPIR-V 在不同驱动上的寄存器分配和优化策略不同
3. **纹理压缩**：Adreno 原生支持 ASTC，Mali 也支持但性能特征不同，建议实测对比
4. **热节流策略**：Mali 设备 thermal 限制更激进，高性能场景需预留更多 margin

> 厂商专属工具和驱动的深度分析超出本书范围，建议参考各厂商的官方优化指南。
