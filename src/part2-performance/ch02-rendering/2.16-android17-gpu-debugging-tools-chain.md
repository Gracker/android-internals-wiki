# 2.16 Android 17 GPU 调试与性能优化工具链

> 本章从渲染问题出发，说明 Android 17 上各类 GPU 与显示工具分别能证明什么。工具实现与命令清单可继续阅读 [§2.3 GPU 调试和性能工具](2.3-gpu-debug-performance-tools.md)、[§2.9 Android 17 GPU 工具源码地图](2.9-android17-gpu-debug-performance-tools-source.md) 与 [§14.8 GPU 调试和性能工具](../ch14-debug/14.8-gpu-debug-performance-tools.md)。

## 结论

“画面卡了”不等于“GPU 慢了”。一帧从内容生产到送屏，至少要经过应用或引擎生产、buffer 提交、fence 同步、SurfaceFlinger 采纳、HWC 合成策略和 display present。GPU 可能参与应用绘制，也可能参与 SurfaceFlinger 的 CLIENT composition；HWC 走 DEVICE composition 时，某个独立 layer 甚至不需要由 SurfaceFlinger 再绘制一次。

排查时要守住三条边界：

1. 先确认谁在生产主体内容，以及内容进入哪个 Surface / layer。普通 HWUI、SurfaceView、TextureView、Camera、Video、游戏和多窗口需要不同的应用侧证据。
2. `queueBuffer()` 返回只表示 buffer 已交给队列，producer completion fence 可能尚未 signal；SurfaceFlinger latch、HWC present 与 panel 显示也都发生在后面。
3. 一项指标只能解释它覆盖的阶段。HWUI 柱状图不是 GPU 利用率，GPU 利用率不是单帧 render pass 成本，`dumpsys SurfaceFlinger` 的瞬时状态也不是历史时间线。

本文沿用《App 出图类型》S01—S14 的分类方式：先找 Producer、Surface、layer 和 Display，再选择工具。这样可以避免在错误的对象上收集一组看似完整的数据。

## 1. 先识别出图类型

同一个页面可以同时存在多路生产者。例如，相机页可能有宿主 HWUI 控件、Camera HAL 预览、ImageReader 分析流和编码流。宿主 `doFrame` 正常，只能说明控件窗口没有明显超时，不能证明预览 buffer 按时到达。

| 主体出图类型 | 生产者与承载方式 | 应用侧优先证据 | 容易误用的工具 |
|---|---|---|---|
| 普通 View / Compose | MainThread 整理状态，RenderThread 生成 App Window buffer | `Choreographer#doFrame`、Traversal、RenderThread、HWUI frame stats | 把 HWUI 柱状图中的整根柱子称为“GPU 时间” |
| SurfaceView / Native Graphics / 游戏 | 解码器、引擎或 native render loop 生产独立 Surface buffer | 引擎 marker、EGL/Vulkan submit、swap/present、独立 BufferQueue | 只看宿主 `dumpsys gfxinfo` |
| TextureView / WebView / Flutter / React Native 混合页 | 外部内容可能回流到宿主纹理，也可能另有独立 layer | 同时建立宿主窗口与引擎 producer 的对象表 | 根据线程名或控件类型猜最终 layer 拓扑 |
| Camera / Video | Camera HAL、codec 或 sideband producer | request/result、PTS、output buffer、consumer release、预览或视频 layer | 把 `releaseOutputBuffer()` 或 HAL result 当成已显示 |
| 多窗口 / 多 Display | 多个 Window、layer 集合与 Display composition 并存 | 按 Window、layer、Display 分组，再对齐 transaction 与 present | 用单个进程 FPS 解释整个 Display |

类型判定不是文档分类工作。它决定后续“帧号属于谁”“哪个 fence 在保护哪块 buffer”“哪个 Display 的 present 才是验收点”。

## 2. 把一帧拆成六个证据区间

下面这张表把常见工具放回它们能够观察的区间。实际设备可能缺少 vendor GPU 数据源，但 BufferQueue、SurfaceFlinger 和 display 的职责边界不因此改变。

| 区间 | 关键事件 | 可以回答的问题 | 常用证据 |
|---|---|---|---|
| 内容生产 | input、animation、layout、engine logic、render preparation | CPU 是否按时准备本帧 | sched、应用 marker、`doFrame`、RenderThread / RHI thread |
| GPU 提交与执行 | GLES/Vulkan command submission、GPU job、producer fence | 命令是否提交晚，GPU 是否完成晚 | Perfetto GPU render stages / counters、driver trace、AGI |
| BufferQueue | dequeue、queue、acquire / release fence、pending buffer | 是否无可用 slot、buffer 是否排队、fence 是否阻塞复用 | BufferQueue track、FrameTracer、fence / dma-fence |
| SurfaceFlinger | transaction flush、layer snapshot、latch、SF CPU / GPU | 新 buffer 是否被采纳，SF 是否错过 deadline | FrameTimeline、SurfaceFlinger slices、layer trace、TimeStats |
| HWC composition | validate、CLIENT / DEVICE、client target、present | 是否发生 CLIENT composition，HWC 是否拒绝或改写策略 | composition type、RenderEngine、Composer HAL / vendor trace |
| Display present | present fence、mode / refresh rate、scanout | 本帧何时交付显示，是否存在刷新率或显示端延迟 | DisplayFrame、present fence、display driver trace |

这里有三个时间点不能互换：

- **producer fence signal**：生产者对 buffer 的写入已经完成，Consumer 可以安全读取；
- **present fence signal**：本轮 display frame 已完成平台定义的 present；
- **release fence signal**：旧 buffer 可以由 Producer 再次使用。

它们共同描述异步流水，但没有一个单独代表“用户眼睛已经看到像素变化”。面板扫描与像素响应需要 display driver 或外部测量补证。

## 3. 工具地图：每件工具只回答一类问题

### 3.1 Perfetto：跨进程时间轴

Perfetto 适合建立低侵入的系统时间轴。Android 17 的关键数据源包括：

| 数据源或轨迹 | Android 17 中的职责 | 使用限制 |
|---|---|---|
| `android.surfaceflinger.frametimeline` | 记录 expected / actual SurfaceFrame 与 DisplayFrame、present type 和 jank type | 需要有效 VSync token；自有引擎、sideband 或设备私有路径未必具有完整 App timeline |
| `android.surfaceflinger.frame` | `FrameTracer` 记录 layer buffer 的 acquire、latch、present 等事件 | 它追踪 layer frame，不解释 shader 为什么慢 |
| `gpu.renderstages` | 记录驱动或 GPU producer 暴露的 render stage | 是否存在、粒度和名称由驱动实现决定 |
| `gpu.counters` | 按 descriptor 记录 GPU counter | counter ID、单位、采样代价和语义必须从设备 descriptor 读取 |
| `linux.ftrace` | 调度、频率、idle、binder、可用的 GPU / display tracepoint | vendor kernel 可能使用私有事件；不能假设每台设备都有 `power/gpu_frequency` |

FrameTimeline 的 jank type 是分类结果，不是根因报告。Android 17 的 `FrameTimeline.cpp` 会区分 App deadline、SF CPU、SF GPU、Display HAL、buffer stuffing、prediction error、display mode change 等情况。看到 `JANK_SF_GPU_DEADLINE_MISSED` 后，还要检查 CLIENT composition、RenderEngine 工作、GPU 队列和 fence，不能直接改应用 shader。

录制前应查询目标设备实际注册的数据源，并只启用问题需要的轨迹。把设备不支持的数据源写进配置，不会凭空产生 GPU counter；把所有高频 counter 一次打开，还可能改变被测负载。

### 3.2 Android Studio System Trace：应用与系统的入口视图

Android Studio 的 UI jank 视图建立在 system trace 上。Android 12 及以上设备会展示 janky frames，并把相关主线程、RenderThread 和 GPU completion 事件放到附近。它适合从一个超时帧跳到线程与系统轨迹。

这个视图仍受出图类型约束。普通 App Window 的 frame lifecycle 较完整；SurfaceView 游戏、Camera 预览或 codec 视频拥有独立 producer，宿主窗口的 frame 不能代替它们。

### 3.3 Profile HWUI rendering 与 `dumpsys gfxinfo`

开发者选项中的 **Profile HWUI rendering**（旧名称 Profile GPU Rendering）显示 UI Window 每帧的分阶段耗时。柱状图包含 input、animation、measure/layout、draw、sync/upload、issue commands、swap buffers 等 CPU 或等待阶段。某些阶段变长可以提示 GPU 队列压力，但整根柱子不是 GPU 执行时间。

`dumpsys gfxinfo <package> framestats` 适合查看由 HWUI 记录的窗口帧历史。它不能覆盖独立 SurfaceView 中的游戏 swapchain、Camera HAL producer 或 tunneled video。若页面主体不在 App Window buffer 里，`gfxinfo` 只能解释宿主 UI。

### 3.4 SurfaceFlinger 内部组件

Android 17 的 SurfaceFlinger 有多套互补组件，职责需要分开：

| 组件 | 源码职责 | 不负责的事情 |
|---|---|---|
| `FrameTimeline` | 建立 SurfaceFrame / DisplayFrame，比较预测与实际时间并分类 jank | 不分析 shader、纹理或 draw call |
| `JankTracker` | 缓存已经生成的 `JankData`，管理并通知按 layer 注册的 listener | 不自行计算 jank，也不向 `dumpsys gfxinfo` 提供分类引擎 |
| `FpsReporter` | 根据 LayerHierarchy 找到 task 关联的 layer，并用 FrameTimeline 计算 FPS 后通知 listener | 不是 `dumpsys SurfaceFlinger --latency` 的固定 60 帧缓存 |
| `FrameTracer` | 通过 `android.surfaceflinger.frame` 输出 layer frame 事件 | 不覆盖应用内部业务阶段 |
| `TimeStats` | 聚合 layer 与 display 的时间统计和 jank metadata | 百分位不能替代单帧依赖分析 |

`dumpsys SurfaceFlinger` 适合查看 layer、Display、composition 和调度状态，也提供 `--frametimeline`、`--timestats` 等受版本约束的 dump 入口。一次 dump 是观测时刻的状态快照；复现期的状态变化仍应使用 trace。

### 3.5 `GpuService`：驱动、内存、工作与加载统计

Android 17 的 `GpuService::doDump()` 只识别四类筛选参数。下面的命令用于按类别缩小 dump 输出：

```bash
adb shell dumpsys gpu --gpudriverinfo
adb shell dumpsys gpu --gpumem
adb shell dumpsys gpu --gpustats
adb shell dumpsys gpu --gpuwork
```

不带这四个参数时，服务会输出全部类别。`--gpustats` 主要是应用加载 GPU driver / ANGLE 等统计，`--gpumem` 与 `--gpuwork` 依赖对应服务和驱动提供的数据；这些输出不是通用 GPU 利用率时间线。

`GpuService::shellCommand()` 另有 `featureOverrides`、`vkjson`、`vkprofiles` 和 `help`。这些命令用于驱动与 Vulkan 配置检查，不应被描述为帧级性能分析器。

### 3.6 AGI：System Profiler 与 Frame Profiler

Android GPU Inspector（AGI）本身同时提供两类能力：

- **System Profiler** 观察一段时间内的 CPU、GPU、内存、系统服务和设备 counter；
- **Frame Profiler** 捕获一个应用帧，检查 Vulkan / OpenGL ES 调用、render pass、pipeline、shader、纹理、mesh、framebuffer 和命令级 GPU 性能数据。

AOSP `android-17.0.0_r1` 中不存在名为 “APA（Android Performance Analyzer）” 的配套系统服务，也不存在 SurfaceFlinger 创建 APA / AGI 实例、再经 `libguihooks` 协调的架构。AGI 是独立桌面工具，能否捕获取决于设备、GPU、graphics API、应用可调试或 profileable 条件以及 AGI 版本。安装、启动和注入应由 AGI UI 按该版本文档完成，不要依赖未经源码或官方文档确认的 `debug.agi.*` 属性。

System profile 用来选中“哪一帧、哪段 GPU 工作值得深挖”；frame profile 用来解释这一帧的 API 与资源成本。高侵入捕获不适合直接充当性能基线，优化前后的验收仍应回到相同设备状态下的低侵入 trace 与 frame-time 分布。

### 3.7 厂商工具：硬件 counter 的解释器

AGI 与 Perfetto 能承载 GPU 数据，但硬件 counter 的可用性仍取决于厂商驱动。Adreno、Mali、PowerVR、Xclipse 等架构在 shader core、tiler、texture、cache、带宽和 DVFS 上的计数方式不同。分析复杂 GPU bound 时，应优先使用目标 GPU 厂商支持的 profiler 和 counter 说明。

不能依据 GPU 品牌写死频率范围、最低采样周期、温控策略或统一 utilization 公式。同一品牌的不同 SoC、driver 和固件也可能改变这些条件。

## 4. 一套可复用的排查顺序

### 第一步：固定测试条件

记录设备型号、build fingerprint、Android 17 构建、GPU driver、刷新率、分辨率、亮度、充电状态、温度、应用版本、页面状态和 graphics API。游戏还要记录目标 FPS、render scale、frame pacing 与最大 in-flight frame；视频要记录 codec、PTS、HDR、secure / tunneled 状态。

冷机短测和十分钟后的持续负载可能得出相反结论。回归比较必须采用相同预热、操作脚本和环境条件。

### 第二步：建立对象表

对每路可见内容记录以下对象：

| 字段 | 示例 |
|---|---|
| Producer | HWUI RenderThread、Camera HAL、MediaCodec、Unity RHI thread |
| Surface / BufferQueue | App Window、SurfaceView child、codec output Surface |
| SurfaceFlinger layer | layer name、owner、parent、layer ID |
| Display | physical display ID、active mode、refresh rate |
| 帧标识 | VSync ID、frame number、PTS、engine frame ID |

不要只凭 layer name 认对象。owner、parent、buffer format、transaction、frame number 和时间关系能提供更可靠的映射。

### 第三步：用低侵入 trace 找到超时区间

从 FrameTimeline 的 expected / actual frame 开始，判断是 App deadline、SF CPU / GPU、Display HAL、buffer stuffing，还是模式切换期间的受控波动。再回到对应线程、buffer 与 fence。

如果 trace 中没有完整 FrameTimeline，也不应停在“无数据”。Native game 可以对齐 engine frame ID、submit、producer fence、queue、latch 和 present；Camera / Video 可以用 request / PTS、output buffer、queue、layer 与 present 建立同等强度的证据。

### 第四步：区分等待与执行

长 slice 或长墙钟时间可能包含等待：

- `dequeueBuffer` 长：检查 free slot、release fence 和 Consumer 节奏；
- swap / present 长：检查 frame pacing、queue-stuffing、driver backpressure；
- producer fence 晚：检查 GPU job 以及更早提交是否已经堆积；
- SurfaceFlinger latch 晚：检查 acquire fence、transaction readiness 和目标 present time；
- RenderEngine 长：检查 CLIENT composition 与输入 layer fence；
- present 晚：检查 HWC、display mode、driver 和 present fence。

只有在 GPU job 持续占满、完成 fence 变晚，并且 counter / stage 与工作负载相互印证时，才能把问题收敛到 GPU 执行。

### 第五步：选择深挖工具

| 已有证据 | 深挖方向 |
|---|---|
| MainThread / RenderThread CPU 晚 | CPU sample、方法 trace、Compose / View 专项、锁与调度 |
| GPU job 晚，应用自绘 | AGI frame profile、厂商 profiler、shader / render pass / bandwidth counter |
| SF GPU deadline missed | layer composition、CLIENT target、RenderEngine、GPU 队列竞争 |
| 独立 layer 排队 | engine / codec / HAL producer、BufferQueue、frame pacing |
| DEVICE 与 CLIENT 频繁切换 | layer 属性、plane 能力、transform、alpha、dataspace、HDR 与系统 overlay |
| 长时间后频率下降 | thermal、power、GPU / memory frequency、温度与持续帧时间 |

### 第六步：回到用户可见指标验收

修复后重复同一场景，比较 frame-time 分布、jank type、present-to-present 间隔、输入到显示延迟和功耗 / 温度。平均 FPS 不能反映长帧簇、1% low 或排队造成的输入延迟。

## 5. 四类常见场景怎么选证据

### 5.1 普通 HWUI 页面

观察顺序是 MainThread → RenderThread → App Window BufferQueue → SurfaceFlinger → HWC / present。

- MainThread 晚：检查 input、animation、measure/layout、draw 与业务回调；
- RenderThread CPU 晚：检查 DisplayList 同步、资源上传、命令提交；
- sync / swap 长：检查 GPU 队列和 buffer backpressure；
- App buffer 按时而 SF 晚：检查 SF deadline、composition 与 display。

Profile HWUI rendering 适合快速提示哪个窗口阶段变长，Perfetto 用于证明跨进程依赖。两者不能由柱状图颜色直接推导“GPU bound”。

### 5.2 SurfaceView、Native Graphics 与游戏

独立 Surface 的主体帧不写入宿主 App Window buffer。需要找到 render / RHI thread、EGL 或 Vulkan submit、swapchain image、producer fence、独立 layer 和 present。

CPU submit 很早但 producer fence 持续变晚，才有必要进入 GPU stage、counter 或 AGI。swap / acquire 周期性等待也可能是主动 frame pacing 或 queue-stuffing，缩短等待未必降低触控到显示延迟。

### 5.3 Camera 与 Video

Camera 从 capture request、sensor timestamp、HAL result 与每个 output stream 开始；Video 从 input / output PTS、codec output、release timestamp 和输出 Surface 开始。SurfaceView 只说明承载方式，不能证明一定获得 DEVICE composition。

TextureView 会把外部内容采样进宿主窗口，HWC 看到的是合成后的 App Window buffer。tunneled video 可能使用 sideband，不能强行寻找普通逐帧 BufferQueue 事件。

### 5.4 多窗口与复杂合成

SurfaceFlinger 和 HWC 按 Display 处理可见 layer 集合。某个窗口本身按时，仍可能因另一 layer、系统 overlay、HDR / dataspace、旋转、缩放或 plane 资源变化而触发 CLIENT composition。

诊断时按 Display 建 layer 表，再比较每轮 composition type、RenderEngine client target 与 present。不能把“层数多”直接等同于“HWC 失败”；硬件能力、layer 属性和整组约束才决定策略。

## 6. GPU counter：描述格式不等于跨设备统一

Perfetto 的 `GpuCounterEvent` 提供两种 descriptor 用法：

1. `GpuCounterDescriptor` 使用全局 counter ID，适合单 producer；Android OEM 为满足 CDD / CTS 约束时必须使用这种机制。
2. `InternedGpuCounterDescriptor` 把 descriptor 放进 trusted sequence 的 interned data，并可标识 `gpu_id`，适合多 producer 或多 GPU。

第二种模式减少 descriptor 重复与全局 ID 协调，不会把 Adreno、Mali、PowerVR 或 Xclipse 的计数器映射成统一语义。AOSP 中没有通用 `GpuCounterCollector` 归一化表，也没有对采样频率、量程和 utilization 算法做补偿的标准值。

跨设备比较至少要满足这些条件：

- counter 来自可核对的 descriptor，名称、单位、峰值含义和采样周期一致；
- workload、分辨率、刷新率、driver、功耗模式和温度条件可比；
- 原始 counter 与厂商公式可追溯；
- 不把频率、busy ratio、ALU occupancy、tiler utilization 或 bandwidth 当成同一个指标。

对业务回归而言，比较同一设备与同一 driver 上的 frame time、jank、GPU stage 和少量稳定 counter，通常比制造一个跨厂商“统一 GPU 利用率”更可靠。

## 7. `sfdo` 与 `flatland` 的边界

Android 17 的 `sfdo` 是 Rust 编写的 SurfaceFlinger 内部命令客户端，通过 `SurfaceFlingerAIDL` 调用有限接口。源码中只有以下命令：

- `debug-flash`
- `force-client-composition`
- `frame-rate-indicator`
- `schedule-composite`
- `schedule-commit`
- `force-pacesetter`
- `reset-forced-pacesetter`

它没有替代 `dumpsys SurfaceFlinger`，也不是 GPU profiler。`force-client-composition` 可以用于 A/B 判断 HWC 路径是否参与异常，但它主动改变 composition 策略，不能用开启后的数据代表正常性能。

`flatland` 是早期设备开发阶段使用的 2D UI 与窗口合成 GPU benchmark。其 README 要求静态环境，并建议固定 CPU、GPU 和内存总线时钟；动态频率下的结果会混入调频策略。它不分析某个应用的 jank，也不适合在量产用户态环境中直接作为体验指标。

## 8. 从证据到优化动作

| 证据指向 | 合理动作 | 不应直接做的事 |
|---|---|---|
| UI / RenderThread CPU 超时 | 减少无效 layout / draw、资源上传、锁竞争，调整任务时机 | 因为柱子超线就降低 shader 复杂度 |
| 应用 GPU 执行超时 | 用 AGI / 厂商工具查 render pass、overdraw、shader、纹理、带宽与同步 | 只看利用率百分比就修改渲染架构 |
| BufferQueue stuffing | 修正 frame pacing、限制 in-flight frame、检查 Consumer 与 release fence | 把所有 swap 等待当作 GPU 运算 |
| SF CLIENT composition 昂贵 | 检查 layer 属性、RenderEngine 输入、overlay 条件与 GPU 竞争 | 一味减少 Window 数量而不看 composition type |
| HWC / display 晚 | 检查 Composer HAL、display mode、present fence 与 vendor driver | 用应用 CPU profiler解释显示端延迟 |
| 持续负载后退化 | 建立温度、频率、功耗与帧时间的时间关系 | 用冷机单帧数据宣称稳定性能 |

`PerformanceHintManager` / ADPF 向系统报告线程组、目标周期和实际工作时长，资源决策仍由 Power HAL 与设备策略完成。它不是设置 GPU 频率的公开 API，也不能代替减少 GPU 工作量或修正 frame pacing。

## 版本边界

平台实现统一以 Android 17 / API 37 的 `android-17.0.0_r1` 为准，kernel 公共同步机制以 `android17-6.18-2026-06_r6` 为准。AGI、Android Studio 和厂商 profiler 独立发布，使用时要另记工具版本、支持范围与目标设备 driver。

Android 17 没有名为 APA 的 AOSP GPU 分析服务，没有跨厂商 counter 自动归一化，也没有 `RayTracingAnalyzer` 或 `NpuAnalyzer` 这类已由平台源码确认的通用分析组件。光线追踪、GPU compute 与端侧 ML 并行负载仍可使用 Vulkan marker、AGI、Perfetto 和厂商工具分析，但结论要回到目标 API、driver 与硬件 counter。
