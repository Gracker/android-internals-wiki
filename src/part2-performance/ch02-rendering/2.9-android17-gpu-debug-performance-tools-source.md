## 1. 源码地图：每个组件负责什么

Android 17 / API 37 的平台锚点是 `android-17.0.0_r1`。与 GPU 和显示诊断直接相关的源码分布在多个仓库，不能只搜索 `SurfaceFlinger.cpp`。

| 关注点 | Android 17 源码入口 | 能确认的事实 |
|---|---|---|
| 应用 VSync 候选时间 | `frameworks/base/core/java/android/view/Choreographer.java` | `Choreographer.FrameData`、`Choreographer.FrameTimeline`、vsync id、deadline、expected presentation time |
| 显示帧预测与 jank 分类 | `frameworks/native/services/surfaceflinger/Scheduler/FrameTimeline.cpp` | expected/actual SurfaceFrame 与 DisplayFrame、present type、jank type、Perfetto data source |
| task 级历史 FPS 回调 | `frameworks/native/services/surfaceflinger/FpsReporter.cpp` / `.h` | 按 task layer hierarchy 取 present time，`kMinDispatchDuration` 为 500 ms |
| jank 数据回调 | `frameworks/native/services/surfaceflinger/Jank/JankTracker.cpp` | listener、后台缓存、50 条批量 flush；不负责发明固定毫秒阈值 |
| 聚合显示统计 | `frameworks/native/services/surfaceflinger/TimeStats/TimeStats.cpp` | layer 与 display 的时间统计、直方图、dump |
| HWC 合成协商 | `frameworks/native/services/surfaceflinger/CompositionEngine/`、`DisplayHardware/` | CLIENT/DEVICE 等 composition type、client target、validate/present 与 fence |
| GPU Binder 服务 | `frameworks/native/services/gpuservice/GpuService.cpp` | 服务名 `gpu`，driver info、gpustats、gpumem、gpuwork dump 分支 |
| GPU memory 快照 | `frameworks/native/services/gpuservice/gpumem/GpuMem.cpp` | `gpu_mem_total` tracepoint、eBPF map、按 GPU id/PID 汇总 |
| GPU work 汇总 | `frameworks/native/services/gpuservice/gpuwork/GpuWork.cpp` | `gpu_work_period` tracepoint、按 GPU id/UID 汇总 active/inactive duration |
| Perfetto GPU 配置 | `external/perfetto/protos/perfetto/config/gpu/` | `gpu.counters` 与 `gpu.renderstages` 的配置结构 |
| Perfetto GPU 事件 | `external/perfetto/protos/perfetto/trace/gpu/` | counter descriptor、render stage、Vulkan memory 与日志事件 |

这张表也给出一个阅读规则：源码里有 proto 或 Binder 方法，只能证明平台定义了数据格式或调用入口；设备能否输出数据，还取决于 vendor producer、GPU driver、kernel tracepoint 和权限。

## 2. FrameTimeline、FpsReporter 与 JankTracker 的关系

三者会在文章中一起出现，但职责不同。

### 2.1 FrameTimeline 是分类与关联中心

SurfaceFlinger 的 FrameTimeline 保存 DisplayFrame 及其 SurfaceFrame，结合预测时间、app 提交、GPU fence、present fence 和显示结果产生分类。Perfetto 数据源名为 `android.surfaceflinger.frametimeline`，Trace Processor 把事件展开到：

- `expected_frame_timeline_slice`
- `actual_frame_timeline_slice`

App SurfaceFrame 使用 `surface_frame_token`，SurfaceFlinger DisplayFrame 使用 `display_frame_token`。一个 DisplayFrame 可以包含多个进程的 SurfaceFrame，所以两类 token 不能合成一个“端到端帧号”。

### 2.2 FpsReporter 读取历史 present time

`FpsReporter` 不维护素材所写的 60 帧 `vector`。它按 task id 找到 layer hierarchy，把 layer id 集合传给 `FrameTimeline::computeFps()`；后者从已 presented 的 DisplayFrame 提取 present time，以相邻显示间隔计算 FPS。

因此这项 FPS 更接近“目标 task 的 layer 有多少次进入显示帧”，不等于应用 render loop 提交率，也不等于面板刷新率。重复显示旧 buffer、producer 丢帧和显示模式切换需要结合 FrameTimeline 明细判断。

### 2.3 JankTracker 分发分类结果

Android 17 的 `JankTracker` 接收已经形成的 `JankData`，按 layer 缓存并异步通知 listener。没有 listener 时，主线程路径会快速返回。单 layer 缓存达到 50 条时触发批量 flush。

`JankTracker` 没有 1–2 ms、2–5 ms、5 ms 以上的轻中重分类，也不负责触发 ANR。Android 17 的 FrameTimeline 分类包括 `AppDeadlineMissed`、`SurfaceFlingerCpuDeadlineMissed`、`SurfaceFlingerGpuDeadlineMissed`、`DisplayHAL`、`BufferStuffing`、`PredictionError` 和 `Dropped` 等。

## 3. 指标分层：数值属于哪个时钟和边界

GPU 分析最常见的误判，是把名字相似的指标放进同一张图直接比较。

| 指标 | 起止边界 | 可以说明 | 不能单独说明 |
|---|---|---|---|
| App actual frame duration | VSync callback 到 app post/GPU ready 的较晚者 | 应用是否按时交付此 SurfaceFrame | 独立 shader 或 GPU job 的纯执行时长 |
| Display actual frame duration | SF wake-up 到显示 present 反馈 | 系统合成和显示是否按时 | 哪个应用或哪个 GPU pass 是根因 |
| `queueBuffer()` duration | producer 线程调用区间 | driver flush、队列回压、slot/fence 等混合等待 | buffer 已经显示 |
| acquire fence signal | producer 完成当前 buffer 写入 | consumer 何时可以读取 | 面板何时扫描 |
| release fence signal | consumer 不再使用旧 buffer | producer 何时可复用旧 buffer | 当前新 buffer 的显示时刻 |
| present fence signal | display present 完成反馈 | 当前 display frame 的显示端进度 | 应用 GPU job 内部分段 |
| GPU counter | producer 定义的采样值 | 某项硬件状态随时间变化 | 跨 GPU 架构直接可比 |
| `gpu_work_period` | driver 上报的 active/inactive period | GPU/UID 活跃时间汇总 | shader 效率、显存带宽或能耗 |
| thermal severity/headroom | Thermal HAL 与 framework 预测 | 设备接近热限制的程度 | GPU 单元独占的温度或功耗 |

同名的“GPU busy”也可能采用不同口径：时钟开启、硬件队列非空、某组 shader core 活跃，得到的百分比不会相同。分析报告应保留 descriptor 的名称、描述、单位、GPU id、采样周期和设备 build。

## 4. Perfetto 没有替厂商归一化 counter

`GpuCounterDescriptor` 由 GPU counter producer 声明硬件提供的 counter，字段包括 id、name、description、单位、分组、峰值和采样周期。Android OEM 使用的模式要求 counter id 在 session 内全局协调。

`InternedGpuCounterDescriptor` 解决的是 descriptor 的 sequence scope，以及多 producer、多 GPU 场景中的引用问题。它没有把 Adreno、Mali、PowerVR 或 Xclipse 的利用率映射成统一语义，也没有 `GpuCounterCollector` vendor HAL 标准化表。

跨设备比较至少要满足以下条件：

1. descriptor 的指标定义与单位一致；
2. 工作负载、分辨率、帧率和图形 API 一致；
3. 采样周期及 counter multiplexing 条件一致；
4. GPU 架构、驱动、频率策略和温度被记录；
5. 结果按帧、像素、时间或工作量归一化后仍有明确物理意义。

如果第 1 条不成立，两个百分比只能作为各自设备的时间序列，不能做横向排名。

## 5. SurfaceFlinger 指标不等于应用 GPU 指标

应用用 GLES/Vulkan 画出 layer 后，HWC 仍要为本轮 display 决定 composition type：

- `DEVICE` 表示该 layer 交给显示硬件路径处理；
- `CLIENT` 表示 SurfaceFlinger 用 RenderEngine 生成 client target；
- HWC 随后对 layer 与 client target 执行 validate/present。

`DEVICE` 不等于“没有 GPU”：应用可能已经用 GPU 生成 buffer。`CLIENT` 也不等于“应用 GPU 慢”：额外采样和混合由 SurfaceFlinger/RenderEngine 发起。

渲染类型还会改变证据覆盖：

- 标准 View/Compose App Window 通常有较完整的 FrameTimeline；
- `SurfaceView`、native game、camera 和 video layer 要补 layer/buffer/fence/HWC；
- `TextureView` 把外部 buffer 采样进宿主窗口，需要同时看外部 producer 与 HWUI；
- 受保护内容可能无法截图或 frame capture，但 transaction、fence 和 composition metadata 仍可观察。

## 6. `gpuservice` 能提供哪些系统数据

Android 17 注册的是 Binder 服务 `gpu`，不是 `gpu-debugd`。下面的命令用于枚举常用 dump 分支：

```bash
adb shell dumpsys gpu
adb shell dumpsys gpu --gpustats
adb shell dumpsys gpu --gpumem
adb shell dumpsys gpu --gpuwork
adb shell cmd gpu help
```

`--gpustats` 偏向 driver/ANGLE 加载统计；`--gpumem` 读取 `gpu_mem_total` eBPF map；`--gpuwork` 读取 `gpu_work_period` 汇总。命令返回“不可用”时，应检查 driver tracepoint、BPF 程序、权限和 product 配置，不能用 0 代替缺失数据。

需要观察 HWUI 帧时间时，应使用另一组入口：

```bash
adb shell dumpsys gfxinfo com.example.app reset
# 执行固定用户路径
adb shell dumpsys gfxinfo com.example.app framestats
```

`gfxinfo` 的 `framestats` 用于应用/HWUI 帧统计，不存在通用的 `gfxinfo ... gpu` 子命令，也不会返回 GPU 利用率、显存带宽或 GPU 功耗。

## 7. GPU 热限制怎样验证

Android 17 Thermal HAL 的 `TemperatureType` 包含 `GPU`，但设备是否提供独立 GPU 传感器、传感器位置和阈值由实现决定。系统级 thermal status 或 headroom 可能由 skin、battery、CPU、GPU 等多种传感器共同影响，不能反推某个 GPU 核心的摄氏温度。

Power Stats HAL 的标准 `EnergyConsumerType` 没有独立 GPU 枚举。厂商可以用 `OTHER` 和 vendor-specific name 暴露相关 rail，也可能把 GPU 与内存、总线或 SoC 域放在同一电源轨。功耗报告要写清：

- 数据来自 battery counter、power rail、Power Stats HAL 还是外置仪器；
- rail 是否只覆盖 GPU；
- 采样周期与时间对齐方式；
- 是否同时记录频率、工作量和 thermal severity。

`gpu_work_period` 是活跃时间，不是焦耳；GPU frequency 也不是功率。要确认热限制，应寻找“负载相近但频率下降、帧时间变长，并伴随 thermal severity/headroom 变化”的共同证据。

## 8. 源码驱动的诊断顺序

### 8.1 识别 producer

从 layer tree 和线程确定主体像素由 HWUI、SurfaceView、TextureView、codec、camera 还是 native engine 生产。UI 框架名称只能提供线索，Surface 与 BufferQueue 才定义显示边界。

### 8.2 选中一帧

标准窗口按 FrameTimeline 的 app/display token 选帧；独立 Surface 使用 buffer frame number、Vulkan present id、引擎 frame id 和时间邻近关系。先记录 present type 与 jank type，不急着给根因命名。

### 8.3 沿 buffer 前进

核对 producer CPU work、GPU submission、`queueBuffer`、BufferTX、transaction readiness、latch、acquire fence、composition type、HWC present 和 present fence。在哪个边界首次错过时间窗，后续证据才有明确方向。

### 8.4 用 GPU 工具细分

确认问题进入 GPU 执行层后，再启用 AGI frame profiling、Perfetto `gpu.renderstages`/`gpu.counters` 或 vendor profiler。没有 producer 支持时，Perfetto 里缺少 GPU track 只代表数据不可见。

### 8.5 验证修改

复测要保持设备、build、分辨率、刷新率、温度区间和用户路径一致。短期峰值与持续性能分开报告，trace on/off 各保留一组结果，用来估计采集开销。

## 9. 版本边界

- Android 12 / API 31 已具备 FrameTimeline 诊断基线，也已包含 `FpsReporter.cpp`；
- Android 13 / API 33 为 native Choreographer 提供多 timeline 查询接口；
- Android 16 / API 36 已包含当前 `JankTracker` 分支；
- Android 17 / API 37 是本章读取方法名、flag 与 proto 的固定平台锚点；
- kernel 侧固定为 `android17-6.18-2026-06_r6`，但 GPU/display driver tracepoint 仍由设备实现决定。

因此，源码中存在 `FpsReporter`、`JankTracker` 或 GPU proto，不足以证明它们由 Android 17 引入。版本演进必须用旧 tag、API level 或工具 release note 验证。

## 10. Review 结论与使用边界

本轮复查按 `android-17.0.0_r1` 抽样核对了 FrameTimeline、FpsReporter、JankTracker、gpuservice、Perfetto GPU descriptor、Thermal HAL 与 Power Stats HAL 的关键边界。正文已经把原素材中“Android 17 新增统一 GPU 调试框架”“通用 GPU 利用率/功耗归一化”和“固定 jank 毫秒阈值”等无源码支撑说法降级为源码导航与证据约束，因此可以作为 Android 17 GPU/显示诊断入口 finalized。

使用本章时仍要保留两条限制：

- 设备是否输出 `gpu_work_period`、`gpu_mem_total`、GPU counter、render stages、独立 GPU thermal sensor 或 power rail，取决于 vendor producer、driver、kernel tracepoint、HAL 与权限；
- 本章只锁定 Android 17 / API 37 / `android-17.0.0_r1` 与 android17-6.18 内核边界，不外推 Android 18/API 38+ 或未验证主线变更。
