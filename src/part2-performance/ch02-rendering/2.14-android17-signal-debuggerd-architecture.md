## 源码核查结论

研究素材把一段早期初始化接线描述成了“debuggerd 整体迁入 linker”，并由此推导出同核信号分发、动态 altstack 和一组性能数据。Android 17 源码不支持这些结论。

| 素材说法 | Android 17 源码结论 |
|---|---|
| debuggerd 从 `system/core/debuggerd` 迁到 `bionic/linker` | dump、unwind、tombstone 生成与 `tombstoned` 仍在 `system/core/debuggerd`；linker 只提供早期注册点和回调 |
| 新文件是 `linker_debuggerd.cpp` | Android 实现位于 `bionic/linker/linker_debuggerd_android.cpp` |
| fatal signal handler 固定到故障发生的 CPU | 源码没有 `sched_setaffinity()` 或 `pthread_setaffinity_np()` 路径 |
| altstack 按设备内存动态取 8～16 MiB | debuggerd 自己分配的是固定 8 个可读写页的 pseudothread stack，外加两页 guard；它不是每线程 `sigaltstack` |
| 新链路取消 IPC，直接在 linker 内 dump | 仍会创建 `crash_dump32/64`，连接 `tombstoned`，并把应用级 native crash 报给 system_server |
| `ro.debuggerd.enable` 控制新旧实现 | 源码没有该兼容开关；debuggable 构建可用 `debug.debuggerd.disable=1` 禁用 fatal handlers |
| 延迟下降 30%～70%、CPU/内存降低若干比例 | AOSP 没有这些基准测试和可复现实验数据 |

因此，本章标题中的“架构迁移”应理解为 linker 与 debuggerd 的早期接线和状态交接，不是目录、进程职责或 tombstone 管线的整体迁移。

## linker 负责尽早注册

`linker_main()` 初始化系统属性和平台属性后调用 `linker_debuggerd_init()`。Android 版本的 `linker_debuggerd_android.cpp` 组装 `debuggerd_callbacks_t`，把这些信息交给 `debuggerd_init()`：

- linker/libc shared globals 中的 abort message；
- fdsan、GWP-ASan、Scudo 和 crash detail 回调；
- dump 完成后通知 gdb 更新库列表的 `post_dump`；
- APEX 构建条件下的进程信息回调。

这样做的价值是进程在普通共享库和应用入口运行前就具备 fatal signal handler，并能把 allocator/linker 已知的诊断信息带进 tombstone。复杂的 ptrace、unwind 和文件输出没有搬进 dynamic linker。

## fatal native crash 的职责链

Android 17 的 native fatal crash 可以按五个角色理解：

1. 内核把 `SIGSEGV`、`SIGABRT`、`SIGBUS` 等信号交给目标线程。
2. 进程内 `debuggerd_signal_handler` 保存 `siginfo_t`、`ucontext_t` 和线程信息。
3. handler 创建共享地址空间但不共享 fd 表的 dispatch pseudothread；该辅助执行单元再 fork/exec `crash_dump32` 或 `crash_dump64`。
4. `crash_dump` ptrace 目标线程、读取寄存器和 maps、执行 unwind，并向 `tombstoned` 申请输出 fd。
5. `tombstoned` 管理文本/protobuf tombstone；应用 fatal crash 还会经 `/data/system/ndebugsocket` 进入 system_server 的 `NativeCrashListener` 和 ActivityManager。

这条链路保留了进程内现场，同时把需要分配内存、访问文件和符号化的复杂工作移出 signal handler。它也解释了为什么自定义 crash SDK 不能在 handler 中执行 Java/JNI、`malloc()`、`dlopen()`、全线程 unwind 或网络上传。

## 信号在哪个线程处理

同步硬件故障通常交给产生 fault 的线程，例如非法内存访问或非法指令。handler 先在该线程的上下文中运行。进程定向的异步信号可以由任一没有屏蔽该信号的合格线程接收。

这里的“线程相关”来自 POSIX/Linux 信号语义：

- signal disposition 是进程级状态；
- signal mask 是线程级状态；
- alternate signal stack 也是线程级状态；
- `ucontext_t` 描述收到信号时的线程寄存器现场。

它不等于 CPU affinity。把 handler 绑回“信号发生的 CPU”也不会提高寄存器现场精度，因为寄存器已经由内核写入 signal frame；Android 17 debuggerd 没有实施这种调度策略。

## pseudothread stack 不是 altstack

`debuggerd_init()` 映射 10 页：中间 8 页改为可读写，两侧各保留一页 `PROT_NONE` guard。这个区域存入 `pseudothread_stack`，供后续 `clone()` 出来的 dispatch pseudothread 使用。

它的有效字节数随页大小变化：

- 4 KiB 页设备：8 页为 32 KiB；
- 16 KiB 页设备：8 页为 128 KiB。

页数仍是源码中的固定值，不会根据设备总内存、进程 RSS 或崩溃栈深度计算。fatal signal action 带有 `SA_ONSTACK`，含义是目标线程已经配置 alternate signal stack 时可以使用；debuggerd 的 8 页 pseudothread stack 没有通过 `sigaltstack()` 安装到每个线程。

## handler 注册与恢复

Android 17 为以下信号注册统一 fatal action：

- `SIGABRT`
- `SIGBUS`
- `SIGFPE`
- `SIGILL`
- `SIGSEGV`
- `SIGSTKFLT`
- `SIGSYS`
- `SIGTRAP`

action 使用 `SA_RESTART | SA_SIGINFO | SA_ONSTACK | SA_EXPOSE_TAGBITS`。`SA_EXPOSE_TAGBITS` 保留 fault address 的 tag bits，便于 MTE 诊断。`BIONIC_SIGNAL_DEBUGGER` 另作主动 native backtrace/tombstone 的控制通道，不能把它当成公开、跨版本固定的 signal number。

自定义 native crash handler 必须保存旧 `sigaction` 并按 `SA_SIGINFO`、`SIG_DFL`、`SIG_IGN` 和 mask 语义转交。采集完成后直接 `_exit()`，或者把原来的 `SIGSEGV` 改成 `SIGABRT`，都会破坏 fault address、系统 tombstone 或 ActivityManager 报告。

## 与 ART 信号路径的边界

ART 还通过 sigchain 处理具有运行时语义的 fault。generated code 的隐式检查、suspend check 等信号若被 ART special handler 消费，就不会进入 fatal tombstone 路径；没有被消费的信号才继续转交。

`SIGQUIT` 也不表示 native crash。ART 的 `SignalCatcher` 线程通过 `sigwait` 等待它并生成 Java/ART thread dump。调试时要区分：

| 操作或事件 | 产物 | 是否杀死目标进程 |
|---|---|---|
| native fatal signal | tombstone、crash log、AMS crash 处理 | 按 fatal 语义退出 |
| `debuggerd -b PID` | 主动 native backtrace | 请求本身不要求退出 |
| `debuggerd -j PID` | ART Java traces | 请求本身不要求退出 |
| Java 未捕获异常 | framework crash report | 由 RuntimeInit/AMS 处理，不等同 native tombstone |

ANR、Java crash 和 native fatal crash 的采集入口、证据格式与治理指标都应分开。

## MTE 与 GWP-ASan 的受控恢复

`debuggerd_handle_signal()` 对 SIGSEGV 检查 permissive MTE 和 recoverable GWP-ASan 等系统定义场景。它们依赖 bionic、allocator、sigchain 与 debuggerd 共享的回调协议。

这不授权应用对任意 SIGSEGV “修复后继续”。越界、use-after-free 或堆损坏发生后，寄存器、锁和 allocator 状态可能已经不一致。三方 SDK 应优先保住系统报告，在下次启动或独立进程中完成聚合和上传。

## 调试时如何定位证据丢失

排查 native crash 时按职责链检查：

1. `logcat -b crash` 是否有 signal、`si_code`、fault address 和 abort message。
2. `/data/tombstones/` 是否生成文本/protobuf 文件。
3. build ID、ABI、APEX/APK 版本与 unstripped symbols 是否完全匹配。
4. 出事线程的首个可靠业务 frame 是否能符号化。
5. GWP-ASan、Scudo、fdsan 或 MTE 是否提供 allocator 证据。
6. tombstone 缺失时，检查 ptrace、fd exhaustion、`tombstoned` 连接、SELinux 和 system_server 通知阶段。

量产应用没有读取其他进程 tombstone 或调用私有 debuggerd client API 的稳定权限。应使用 Play Console、受控 bugreport、OEM 系统能力或应用自己的最小 signal-safe 记录补充系统证据。
