# 2.12 Android 17 ApplicationStartInfo：启动记录的边界与用法

<!-- outline-start -->
## 要点

### 🔹 ApplicationStartInfo 的 API 边界
`ApplicationStartInfo` 是 Android 15 / API 35 起的公开启动记录 API；Android 17 继续沿用这套字段与查询/回调入口。

### 🔹 启动原因、类型与组件维度
按 `reason`、`startType`、`startComponent` 和进程身份拆分样本，避免把不同拉起路径混进同一启动性能分位值。

### 🔹 时间戳与时钟域
八个系统时间戳使用单调纳秒值；只在键存在且顺序合理时计算 TTID/TTFD，不能用 wall clock 或缺省 0 直接相减。

### 🔹 查询与 completion listener
历史查询返回有限的最近记录；completion listener 在首帧绘制后触发一次，不等待 `reportFullyDrawn()`。

### 🔹 system_server 实现边界
`AppStartInfoTracker` 的容量、持久化延迟、保留窗口和临时 fully drawn 记录是 AOSP Android 17 实现细节，不是 SDK 稳定承诺。

## 扩展

### 🔸 与 Perfetto / ProfilingManager 协作
`ApplicationStartInfo` 适合筛选慢启动样本和拆分阶段，线程调度、I/O、Binder、帧流水线仍需 Perfetto、Macrobenchmark 或触发式 profiling 补证。

### 🔸 开发者时间戳治理
21～30 号开发者键需要团队内固定字典，并在首帧前按同一单调时钟域单次写入。

## 先把名称分开

`ApplicationStartInfo` 是 Android 15（API 35）加入的公开平台 API。它记录一次应用进程启动的触发原因、启动类型、进程身份和若干单调时钟时间戳，应用通过 `ActivityManager` 查询或接收首帧完成回调。

“Startup Insights”不是 Android 17 中负责采集这些记录的系统服务名。AndroidX Benchmark 等工具也会使用 Startup Insights 这个名称描述基准测试诊断信息，那套离线分析能力与 `ApplicationStartInfo` 的运行时记录应分别讨论。源码中不存在 `StartupInsightsService`、`StartupEvent` 历史队列或 `SystemHealthManager.getHistoricalStats()` 这一组平台接口。

本章聚焦 `ApplicationStartInfo` 的字段和服务端实现边界。完整的线上上报协议见 [26.13 ApplicationStartInfo 与启动归因上报](../../part5-app/ch26-observability/13-application-start-info.md)，启动优化实践见 [21.17 Startup Insights API 与启动性能可观测性](../../part5-app/ch21-startup/17-startup-insights-api-observability.md)。

## Android 17 源码核查结论

研究素材中的数字和版本说明有几处偏差，直接照搬会让版本门控和数据解析出错。

| 项目 | Android 17 / `android-17.0.0_r1` 结论 | 容易写错的说法 |
|---|---|---|
| `ApplicationStartInfo` 基础 API | API 35 加入 | Android 17 新增 |
| 启动原因 | `START_REASON_*` 共 12 种，取值 0～11 | 13 种 |
| 启动类型 | `UNSET`、`COLD`、`WARM`、`HOT` 共 4 种 | 只有冷、温、热三种状态 |
| 启动组件 | API 36 加入，共 5 种：Activity、Broadcast、ContentProvider、Service、Other | Android 17 新增、只有 4 种 |
| 系统时间戳 | 8 个，键 0～7，均从 API 35 可用 | Android 17 才补齐 |
| 开发者时间戳 | 键 21～30；通过 `ActivityManager.addStartInfoTimestamp()` 写入，从 API 35 可用 | 调用 `ApplicationStartInfo.addStartupTimestamp()`，或认为 API 37 才支持 |
| completion listener | 首帧绘制时触发，最多一次，触发后自动移除 | 等待 `reportFullyDrawn()` |

`ApplicationStartInfo.addStartupTimestamp()` 在源码中带有 `@hide`，应用不能把查询到的对象当成可写记录。公开入口是 `ActivityManager.addStartInfoTimestamp()`；AMS 再把调用方 UID 对应的时间戳写入最近一条记录。

## 一条记录能回答什么

### 状态、原因、类型和组件分工

`getStartupState()` 描述记录的采集进度：

- `STARTUP_STATE_STARTED`：启动已经开始，后续字段仍可能补入。
- `STARTUP_STATE_ERROR`：启动失败，已有字段可能不完整，系统不会再承诺增加字段。
- `STARTUP_STATE_FIRST_FRAME_DRAWN`：首帧已经绘制，核心启动节点已经可用于回调与 TTID 计算；`FULLY_DRAWN` 以及部分显示管线可选键仍可能缺失或后续才补入。

`getReason()` 回答“什么事件拉起了进程”。Android 17 的 12 个原因是 Alarm、Backup、Boot Complete、Broadcast、ContentProvider、Job、Launcher、Launcher Recents、Other、Push、Service 和 Start Activity。

`getStartType()` 回答本次 Activity 启动采用冷、温还是热路径。记录处于 `STARTED` 或 `ERROR` 时，该字段不保证有效，因此统计代码要保留 `START_TYPE_UNSET`，不能把它归入冷启动。

`getStartComponent()` 回答“为了哪类 Android 组件启动进程”。它在 API 36 加入，包含 4 类标准组件和 `OTHER`。`reason` 与 `component` 不能互相推导：例如 Job 通常通过 Service 组件执行，原因是 `JOB`，组件仍是 `SERVICE`。

### 进程身份字段

`pid`、`realUid`、`packageUid`、`definingUid` 和 `processName` 用于区分普通进程、隔离进程以及 external service：

- `realUid` 是进程运行时使用的内核 UID。
- `packageUid` 是软件包安装时分配的 UID。
- `definingUid` 在 `useAppZygote` 配合 external service 时可能属于服务提供方。
- `processName` 是进程名，不能用包名替代；多进程应用必须把它纳入聚合维度。

普通应用调用 `getHistoricalProcessStartReasons()` 时，AMS 按调用方 UID 过滤，不能借此读取其他应用的记录。系统 API 的跨包查询还要求 `DUMP` 权限。

`getIntent()` 返回的是经过裁剪的 Intent。公开 API 明确说明 extras 不在结果中；源码还会按 Intent 内容选择 `maybeStripForHistory()`、`cloneFilter()` 或普通克隆，并清除 original intent。它适合判断 action、component、categories 等路由信息，不适合作为业务参数存档。

## 八个系统时间戳

`getStartupTimestamps()` 返回 `Map<Integer, Long>`，单位是纳秒，语义是 monotonic clock。键存在才表示该里程碑被采集，不能用 `0` 补缺后参与耗时计算。

| 键 | 语义 | Android 17 可用性边界 |
|---|---|---|
| `START_TIMESTAMP_LAUNCH` | 启动序列开始 | `STARTED` 状态保证存在；Android 16（Baklava）及更早版本的 Service 启动值可能不准 |
| `START_TIMESTAMP_FORK` | 发起 Zygote fork | 冷启动时有价值，但公开 API 没有把它列为所有完成记录的必有项 |
| `START_TIMESTAMP_APPLICATION_ONCREATE` | 调用 `Application.onCreate()` 前 | `FIRST_FRAME_DRAWN` 状态保证存在 |
| `START_TIMESTAMP_BIND_APPLICATION` | system_server 发起 `bindApplication` | `FIRST_FRAME_DRAWN` 状态保证存在 |
| `START_TIMESTAMP_FIRST_FRAME` | WindowManager 观察到窗口首帧 | `FIRST_FRAME_DRAWN` 状态保证存在，并触发 completion listener |
| `START_TIMESTAMP_FULLY_DRAWN` | 应用调用 `reportFullyDrawn()` | 从不保证存在 |
| `START_TIMESTAMP_INITIAL_RENDERTHREAD_FRAME` | RenderThread 初始帧开始 | 设备和启动路径相关，不应视为必有项 |
| `START_TIMESTAMP_SURFACEFLINGER_COMPOSITION_COMPLETE` | 初始画面由 SurfaceFlinger 完成呈现 | 设备和启动路径相关，不应视为必有项 |

这里有三个容易混淆的时刻：

1. `FIRST_FRAME` 表示 WindowManager 侧观察到启动窗口完成首帧绘制，也是 completion listener 的完成条件。
2. `SURFACEFLINGER_COMPOSITION_COMPLETE` 更接近显示系统完成初始画面呈现，但它不在公开 API 承诺的必有集合里。
3. `FULLY_DRAWN` 来自应用主动调用 `reportFullyDrawn()`，它可以比首帧晚很多，也可能永远缺失。

因此，TTID 可以在 `FIRST_FRAME - LAUNCH` 两个键都存在时计算；TTFD 只能在 `FULLY_DRAWN` 存在时计算。缺失值要上报为 unavailable，不能退化成首帧值。

### 时钟域不能靠名字猜

公开文档只把这些值定义为 monotonic nanoseconds。Android 17 的 Activity 启动链中，`ActivityMetricsLogger` 的启动点和首帧、`ProcessList` 的 fork 点、`ActivityThread` 的 `Application.onCreate()` 点都使用 `SystemClock.uptimeNanos()`。这组时间不包含深度睡眠时间。

同一条 Activity 启动记录内做差是最稳妥的用法。把原始数值叠到 Perfetto 时，需要依据 trace 的 `ClockSnapshot` 或采集环境确认时钟转换；不能默认 trace SQL 的 `ts` 与记录值属于同一时钟，也不能用 wall clock 直接相减。

应用写入自定义启动时间戳时，应使用相同的单调时钟。下面的写法把“首屏数据进入可渲染状态”记录到开发者预留的 21 号键：

```kotlin
if (Build.VERSION.SDK_INT >= Build.VERSION_CODES.VANILLA_ICE_CREAM) {
    val activityManager = getSystemService(ActivityManager::class.java)
    activityManager.addStartInfoTimestamp(
        ApplicationStartInfo.START_TIMESTAMP_RESERVED_RANGE_DEVELOPER_START,
        SystemClock.uptimeNanos(),
    )
}
```

这段调用只更新调用方最近的启动记录。SDK 文档写明相同键会覆盖旧值，并明确 `reportFullyDrawn()` 之后的写入会被丢弃；`android-17.0.0_r1` 的 `AppStartInfoTracker` 实现更严格：已有键不会重写，记录进入 `FIRST_FRAME_DRAWN` 后也不再接受开发者键。工程代码应把每个键当成单次写入，并在首帧前完成记录，避免依赖文档与该版本实现之间的差异。键 21～30 还需要在团队内建立固定字典，否则不同版本会把同一数字解释成不同业务里程碑。

## 查询与回调是两种不同的观察窗口

### 主动查询

`ActivityManager.getHistoricalProcessStartReasons(maxNum)` 按时间从新到旧返回记录。查询可能拿到仍处于 `STARTED` 的对象，这允许应用较早观察启动来源，但此时不能读取尚未承诺的字段。

`maxNum == 0` 表示返回可用的匹配记录，并不代表历史无限。Android 17 AOSP 的服务端实现使用环形容量：基础资源 `config_app_start_info_history_list_size` 的默认值为每包 16 条，OEM 可以用资源覆盖改变它。调用方应按“有限、可能变化的最近记录”设计去重和上报。

### 首帧完成回调

以下代码只在字段存在时计算从启动到首帧的耗时，并把回调安排到应用自有的后台执行器：

```kotlin
@RequiresApi(35)
fun observeCurrentStart(
    context: Context,
    executor: Executor,
    enqueue: (ApplicationStartInfo, Long?) -> Unit,
) {
    val activityManager = context.getSystemService(ActivityManager::class.java)
    activityManager.addApplicationStartInfoCompletionListener(executor) { info ->
        val timestamps = info.startupTimestamps
        val launchNs = timestamps[ApplicationStartInfo.START_TIMESTAMP_LAUNCH]
        val firstFrameNs = timestamps[ApplicationStartInfo.START_TIMESTAMP_FIRST_FRAME]
        val ttidMs = if (launchNs != null && firstFrameNs != null && firstFrameNs >= launchNs) {
            TimeUnit.NANOSECONDS.toMillis(firstFrameNs - launchNs)
        } else {
            null
        }
        enqueue(info, ttidMs)
    }
}
```

listener 最多回调一次，并由框架自动移除。回调发生在首帧，因此此处得到的对象通常还没有 `FULLY_DRAWN`。如果应用随后调用了 `reportFullyDrawn()`，需要再次调用 `getHistoricalProcessStartReasons()` 取得更新后的记录。

Service、Broadcast、ContentProvider 等后台拉起没有 Activity 首帧时，不应依赖这个 listener 收尾；主动查询更适合这些场景。

## system_server 如何保存记录

Android 17 的实现由 `AppStartInfoTracker` 管理。下面这些值是 `android-17.0.0_r1` 的实现细节，不属于 SDK 稳定契约：

| 实现项 | AOSP Android 17 值 | 工程含义 |
|---|---:|---|
| 每包历史容量 | 资源默认 16 条 | OEM 可覆盖，业务侧不能假定固定值 |
| 持久化延迟 | 30 分钟 | 刚产生的记录可能在 system_server 重启前尚未落盘 |
| 持久化保留窗口 | 14 天 | 清理发生在序列化路径；不是服务端长期审计日志 |
| Activity 待补 `FULLY_DRAWN` 的临时记录 | 最多 5 条 | 未调用 `reportFullyDrawn()` 是正常路径，旧条目会被裁剪 |
| 存储目录和文件 | `procstartstore/procstartinfo` | 属于系统内部格式，应用不应直接读取 |

记录加入历史容器时会安排持久化任务。`reportFullyDrawn()` 主要负责给仍在临时表中的 Activity 启动补时间戳并移除临时项；它不负责触发首帧 completion listener。把 30 分钟、14 天或 16 条写成兼容性承诺，会在 OEM 定制或后续版本调整时产生错误假设。

源码也没有给出“内存低于 100 KB”“文件低于 10 KB”“零性能开销”这类可移植结论。查询涉及 Binder、Parcel 和对象分配；应用侧仍应在后台线程处理、抽样上报并避免复制完整 Intent 字符串。

## 从记录走到问题定位

一条 `ApplicationStartInfo` 适合做分流和阶段定位，不能替代 Perfetto：

1. 先按 `processName`、`startComponent`、`reason` 和 `startType` 分组。后台组件拉起不要混入用户点击桌面图标的冷启动分位值。
2. 检查 `startupState` 和键集合，再计算存在且顺序合理的时间差。
3. `LAUNCH → FORK` 偏大时，关注 system_server 调度、Zygote、进程创建和系统负载。
4. `APPLICATION_ONCREATE → FIRST_FRAME` 偏大时，关注主线程初始化、ContentProvider、类加载、I/O 和首屏布局。
5. `FIRST_FRAME → FULLY_DRAWN` 偏大时，结合应用为 `reportFullyDrawn()` 定义的业务完成条件分析；若该键缺失，先检查调用覆盖率。
6. 线上分位值发现异常后，再用 Perfetto、Macrobenchmark 或条件触发 profiling 获取线程调度、Binder、I/O 和帧流水线证据。

`ApplicationStartInfo` 没有函数调用栈、CPU 频率因果关系、I/O 调用点或每帧 jank 分类。仅凭某个阶段变长，不能断言是 CPU、GPU、锁竞争或存储造成的。

## Android 15 到 Android 17 的版本边界

| 平台 | 可以依赖的能力 |
|---|---|
| Android 15 / API 35 | `ApplicationStartInfo`、历史查询、首帧 completion listener、8 个系统时间戳、21～30 号开发者时间戳、`addStartInfoTimestamp()` |
| Android 16 / API 36 | 增加 `getStartComponent()` 和 5 个 `START_COMPONENT_*` 常量 |
| Android 17 / API 37 | 延续上述 API；本章按 `android-17.0.0_r1` 重新核准服务端持久化、首帧回调和组件分类实现 |

Android 17 的新 profiling trigger 可以用冷启动类型触发采集，但 `ApplicationStartInfo` 本身没有在 API 37 改名为 Startup Insights，也没有变成持续 trace 服务。结构化启动记录负责筛选样本，Perfetto 或 ProfilingManager 负责提供重型诊断数据，两者的成本和采集周期应分开控制。
