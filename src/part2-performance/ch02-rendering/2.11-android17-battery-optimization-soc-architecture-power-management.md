素材 `DeepResearch/2026-07-05-android17-battery-optimization-soc-architecture-power-management.md` 找到了几组真实的 Perfetto power 数据结构，却把“数据采集”“Framework 策略”“Power HAL 提示”“kernel 调度”和“厂商硬件控制”写成了一套 Android 17 统一优化架构。这个因果关系不成立。

## 素材中可以保留的事实

### Perfetto 可以采集电池 counter

`LinuxPowerSysfsDataSource` 可以从 `/sys/class/power_supply` 读取设备提供的 charge counter、capacity、current、energy counter 和 voltage。`AndroidPowerDataSource` 还可以采集 power rails、energy estimation breakdown 与 entity state residency。

`BatteryCounters` proto 中的这些字段也存在：

- `charge_counter_uah`
- `capacity_percent`
- `current_ua`
- `current_avg_ua`
- `energy_counter_uwh`
- `voltage_uv`

这些字段证明 Perfetto 能记录设备暴露的测量值，不证明 Perfetto 会据此调节 CPU/GPU，也不保证每台 Android 17 设备都提供所有字段。

### Power Stats HAL 可以报告能量与状态驻留

`android.hardware.power.stats.IPowerStats` 定义了：

- `getStateResidency()`：报告 PowerEntity 各状态的累计驻留时间；
- `getEnergyConsumed()`：报告 EnergyConsumer 自开机以来的累计能量；
- `readEnergyMeter()`：报告 channel 的累计能量测量。

这是观测接口。控制提示属于 `android.hardware.power.IPower`，两者没有“PowerStats 自动反馈到 schedutil”的标准调用关系。

### Power HAL 可以接收场景与周期负载提示

Android 17 的 AIDL `IPower` 提供 `Mode`、`Boost`、HintSession、CPU/GPU headroom 和 composition data 等接口。接口允许设备忽略 mode/boost，且没有规定提示必须映射到哪个 CPUFreq、devfreq、uclamp 或 vendor 节点。

## 必须撤销的结论

| 素材说法 | Android 17 核查结果 |
|---|---|
| Perfetto 是四层电池优化架构的“硬件层” | Perfetto 是采集与分析工具，不是硬件控制层 |
| ARM 有 8–12 个电源域、高通有 15–20 个 | 没有设备型号、PowerStats descriptor 或厂商一手资料支持 |
| 高通精度 ±2%/5 Hz，MediaTek ±3%，ARM ±5%/1 Hz | 没有测量对象、仪器、样本或公开接口契约支持 |
| Android 17 使用 Perfetto v23.0 并新增智能电池估算 | 平台锚点是 `android-17.0.0_r1`；该版本表与 AOSP tag、Perfetto release 不对应 |
| LMK priority 批处理属于 Big.LITTLE 功耗调度 | LMKD 进程优先级更新与 CPU 异构选频不是同一机制 |
| 电池监控可延长续航 5–8%、调度降功耗 15–20% | 没有基线、工作负载、设备、统计方法和原始数据 |
| Perfetto 采集固定增加 0.5–1% CPU、2–4 MB 内存 | 开销随数据源、采样周期、buffer、设备和 trace 配置变化 |
| 电池状态会增加 10–50 ms 调度决策延迟 | AOSP 没有这条固定控制路径或测量结果 |

素材明确承认拿不到 Qualcomm、MediaTek 等私有实现，却继续给出厂商粒度、精度和收益数字。这些数字不能进入知识库正文。

## 正确的职责划分

| 层次 | AOSP 能证明的内容 | 仍需设备证据的内容 |
|---|---|---|
| Framework | Battery Saver、Device Idle、JobScheduler/AlarmManager 约束、PowerManagerService 状态 | OEM 后台策略与白名单行为 |
| AIDL `IPower` | Mode、Boost、HintSession、headroom 等接口契约 | 提示如何变成 CPU/GPU/DDR/idle 控制 |
| AIDL `IPowerStats` | energy consumer、meter channel、state residency 数据格式 | rail 数量、命名、精度、采样率和覆盖范围 |
| Perfetto | 记录 battery counter、power rail、residency、调度与频率 | 数据是否在目标设备可用、采集开销 |
| Android common kernel | scheduler、schedutil、cpufreq、cpuidle、thermal/cooling 的通用机制 | vendor hook、firmware、具体 OPP 与产品策略 |

平台源码固定为 Android 17 / API 37 / `android-17.0.0_r1`，kernel 固定为 `android17-6.18-2026-06_r6`。在该 kernel 中，schedutil 根据 scheduler utilization 与 policy 约束选频；`rate_limit_us` 初始值来自 cpufreq policy transition delay，不是 Android 17 固定常量。

Android 17 kernel 的 schedutil 还会优先读取 `scx_cpuperf_target()`。只有启用 `sched_ext` 且 BPF scheduler 写入 cpuperf target 时，这条输入才改变选频；未启用时仍回到常规 utilization 路径。它不是 Power HAL mode 到频率的固定函数调用。

## 如何验证一台真实设备

一次可复现的 SoC 功耗实验至少要记录：

1. build fingerprint、kernel、Power HAL AIDL 版本和 VINTF 服务；
2. battery saver、充电、亮度、网络、thermal status 与环境温度；
3. 目标 workload、持续时间、刷新率和编译状态；
4. CPU/GPU frequency、idle、sched、thermal、power rail 与业务 marker；
5. 延迟、掉帧、吞吐、累计能量差和稳定温度；
6. trace 开启与关闭两组基线。

跨设备比较不能只看一个 “GPU busy” 或一条 rail。设备的 rail 分组、传感器、固件和电源域不同；内部 rail 更适合单设备归因，整机能耗比较通常需要统一的外部仪器和供电条件。
