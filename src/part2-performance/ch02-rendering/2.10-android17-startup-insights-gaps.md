## 审阅结论

素材 `DeepResearch/2026-07-06-android17-startup-insights-gaps.md` 的核心架构不成立。它把 `SystemHealthManager`、`ApplicationStartInfo`、AndroidX Benchmark 和 Perfetto 拼成一个不存在的 Android 17 `StartupInsightsService`，随后又据此生成接口、proto、版本演进和开销数据。

下面是 Android 17 / API 37 / `android-17.0.0_r1` 的源码核查结果：

| 素材说法 | 核查结果 |
|---|---|
| `SystemHealthManager.getHistoricalStats(...)` 收集启动历史 | Android 17 没有该方法；该类提供 HealthStats snapshot、power monitor、CPU/GPU headroom 等能力 |
| `STARTUP_INFO_COLLECTOR`、`APPLICATION_START`、`STATS_APPLICATION_START_INFO` | AOSP 中没有这些常量 |
| `StartupInsightsService` | AOSP 中没有该服务或类 |
| `ApplicationStartInfo.startupPhase/metrics`、`setStartupPhase()`、`addStartupMetric()` | 公开类没有这组字段和方法 |
| `ActivityManager.startupTiming()`、`registerStartupMonitor()` | Android 17 没有这组公开 API |
| Perfetto `StartupEvent` proto | `external/perfetto` 与平台源码中没有素材给出的 message |
| SystemHealthManager 8 KB、1000 条环形记录、监控开销小于 1 ms | 没有源码、实验设计或设备数据支持 |
| Android 15/16/17 的 CPU→网络→多维启动监控演进 | 没有对应 tag、API level 或 release note 支持 |

这不是“源码暂时没找到”的灰区。素材给出的类成员、常量和数据格式与固定 tag 直接冲突，应从知识库结论中撤销。

## 三套名称相近但职责不同的能力

| 能力 | 所在层次 | 数据来源 | 适合回答的问题 |
|---|---|---|---|
| AndroidX Benchmark Startup Insights | AndroidX 测试工具 | Macrobenchmark 捕获的 Perfetto trace 与 `android_startup` metric | 可重复启动实验命中了哪些慢启动候选信号 |
| `ApplicationStartInfo` | Android 平台公开 API，API 35 起 | ActivityManager 保存的进程启动记录 | 进程为何启动、属于冷/温/热哪类、有哪些平台时间戳 |
| `ProfilingTrigger.TRIGGER_TYPE_COLD_START` | Android 17 / API 37 平台 API | 系统在真实冷启动时触发的 system trace 与 stack sampling | 如何采集难以在本地复现的冷启动样本 |

三者可以互补，但没有共同的 `StartupInsightsService`。AndroidX 工具独立发布，不能按 Android 平台版本推断其行为；`ApplicationStartInfo` 是结构化启动记录，不是 CPU、内存、网络连续 profiler；冷启动 trigger 负责采集，不会替开发者生成修复方案。

## `ApplicationStartInfo` 的有效边界

Android 17 的 `ApplicationStartInfo` 包含：

- `STARTUP_STATE_STARTED`、`ERROR`、`FIRST_FRAME_DRAWN`；
- launcher、broadcast、service、job、content provider 等 start reason；
- cold、warm、hot start type；
- standard、singleTop、singleTask 等 launch mode；
- launch、fork、bindApplication、`Application.onCreate()`、first frame、fully drawn、initial RenderThread frame、SurfaceFlinger composition complete 等 timestamp key；
- start component、start Intent、PID/UID/package 等归因字段。

这些字段不是每次都齐全。`STARTUP_STATE_STARTED` 只保证 launch timestamp；`FIRST_FRAME_DRAWN` 才额外保证 `APPLICATION_ONCREATE`、`BIND_APPLICATION` 和 `FIRST_FRAME`。`FULLY_DRAWN` 依赖应用调用 `reportFullyDrawn()`，文档明确说明它从不保证存在。

`getHistoricalProcessStartReasons()` 返回的是有限历史记录，不是函数级 trace。线程为何 runnable、锁在哪里阻塞、Binder 对端做了什么、I/O 是否命中 page cache，仍要查看 Perfetto 和应用代码。

## AndroidX Startup Insights 的有效边界

项目固定的工具锚点为 AndroidX Benchmark 1.4.1。该版本的 `StartupInsights.queryInsights()` 读取 Perfetto `android_startup` metric 的 `slow_start_reason_with_details`，按目标包与迭代汇总为 `Insight`。

它能提示缺少 Baseline Profile、JIT/GC、主线程 blocking I/O、Binder、锁竞争、View inflation、类校验或 CPU 竞争等候选信号。Insight 是进入对应 trace 的导航，不是自动根因判决，也不修改应用调度、依赖关系或初始化顺序。

工具版本与平台版本要分开记录：

- 测试设备可以运行 Android 17；
- Startup Insights 的逻辑来自测试工程依赖的 AndroidX Benchmark；
- slow-start reason 与阈值来自相应 Perfetto metric；
- 任一工具升级后，都要复核 API、输出字段和阈值。

## Android 17 冷启动触发式 profiling

API 37 的 `ProfilingTrigger.TRIGGER_TYPE_COLD_START` 是素材没有覆盖的真实 Android 17 能力。它以 `ApplicationStartInfo.getStartType() == START_TYPE_COLD` 为触发前提，在应用冷启动早期开始 system trace 与 stack sampling，并在 `reportFullyDrawn()` 或默认超时后停止。

这项能力解决的是“异常只在线上真实启动中出现，如何拿到诊断资料”。它不等同于 AndroidX Startup Insights，也不会把 trace 自动变成 `ApplicationStartInfo` 的扩展字段。应用仍需设置 profiling listener、处理结果文件、遵守频率与权限限制，并把样本和版本、设备、启动入口关联。

## 正确的启动诊断组合

1. 用 Macrobenchmark 固定构建、编译模式、启动入口和设备条件，测量 TTID/TTFD；
2. 开启 AndroidX Startup Insights，找到跨迭代重复出现的候选信号；
3. 从 Insight 链接进入 Perfetto，核对主线程、RenderThread、Binder、I/O、锁和调度；
4. 用 `ApplicationStartInfo` 对线上启动按 reason、start type、component 和 timestamp 分流；
5. 对难复现的 Android 17 冷启动问题使用系统触发式 profiling；
6. 修改一个假设后，以相同实验重测，并检查首次交互和业务正确性。

本地 benchmark、平台历史记录和线上触发 trace 的时间窗与样本人群不同。不能把本地十次冷启动的命中比例当成线上用户分布，也不能把一个 timestamp 差值解释成其中所有函数的 CPU 时间。
