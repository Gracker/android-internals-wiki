# 10.01 Android 内存性能优化

内存优化要在明确的设备、进程状态和业务负载下，减少泄漏、无效分配、资源峰值、换页和进程重启，同时保住响应速度与缓存命中率。单独压低某一条曲线不能代表优化完成。

第 10 章按内存域和故障类型组织。平台行为以 Android 17 / API 37 / `android-17.0.0_r1` 为当前锚点；PSI、cgroup v2 与内核回收语义以 `android17-6.18-2026-06_r6` 为锚点。每一类问题的源码和实战细节由后续小节展开。

## 一、先给问题命名

“内存占用高”不是完整的问题陈述。至少要区分下面几类现象：

| 类型 | 可观察特征 | 主要风险 | 优先工具 |
| --- | --- | --- | --- |
| 泄漏 | 业务退出后对象仍被 GC root 或资源 owner 持有 | live set 持续增加、OOM | heap dump、引用链、资源表 |
| 持续增长 | 多轮操作后 PSS、RSS 或某个内存域单调上升 | 超限、后台被杀、恢复变慢 | 时间序列、heap/native profile、DMA-BUF |
| 分配抖动 | live set 稳定，单位时间分配量很高 | GC CPU、暂停、帧丢失 | ART allocation profile、Perfetto |
| 瞬时峰值 | 某个阶段同时保留输入、中间结果和输出 | 分配失败、系统压力 | 业务 trace、峰值快照、并发数 |
| 系统低内存 | PSI、换页、working-set refault 或 lmkd 活跃 | 全机卡顿、cached process 重启 | Perfetto、PSI、lmkd 日志 |
| ART 碎片 | moving/non-moving 空间的空闲分布影响搬迁或分配 | GC 成本、连续分配失败 | GC timing、collector/space 源码、profile |
| Native/图形资源未释放 | Java wrapper 很少，Native、Graphics 或 DMA-BUF 增长 | RSS/PSS 上升、驱动分配失败 | heapprofd、memtrack、GPU/DMA-BUF |
| 资源句柄耗尽 | FD、线程、Binder 或映射数量增长 | `EMFILE`、线程创建失败、间接内存增长 | `/proc/<pid>/fd`、线程和映射统计 |

不同类型可能同时出现。例如，图片列表既可能泄漏页面对象，又可能因预取并发造成短时峰值，还可能把像素资源记到 Graphics 或 DMA-BUF。一次 heap dump 只能覆盖其中一部分。

## 二、Android 进程没有一个“总内存”数字

### 2.1 主要内存域

| 内存域 | 常见内容 | owner 或记账来源 |
| --- | --- | --- |
| ART managed heap | Java/Kotlin 对象、数组、字符串 | ART collector 与 heap space |
| Native heap | C/C++/Rust 对象、JNI buffer、库内部状态 | bionic allocator、库或引擎 |
| 匿名映射 | arena、JIT、共享内存映射、runtime 区域 | VMA、页表、memcg |
| 文件映射 | APK、DEX/OAT、so、模型权重、数据库 mmap | page cache 与进程页表 |
| Graphics/GPU | GraphicBuffer、硬件 Bitmap、GL/Vulkan 私有资源 | memtrack、DMA-BUF、GPU 驱动 |
| Stack/Code | 线程栈、JIT/AOT code、共享库 | ART、linker、kernel |
| Swap/ZRAM | 被换出的匿名页 | kernel、memcg、ZRAM |

GC 只管理 managed heap 中可回收的对象。它不会关闭文件描述符，不会释放仍被 Native owner 持有的 buffer，也不会回收仍在 Surface、codec 或 GPU 队列中的图形资源。

### 2.2 常用指标回答不同问题

| 指标 | 含义 | 适合的用途 | 不能推出的结论 |
| --- | --- | --- | --- |
| Java heap used | ART 当前计入的已分配 managed bytes | 对象存量与 GC 趋势 | 整个进程占用 |
| Native allocated | allocator 仍视为已分配的字节 | Native 分配趋势 | Native RSS 或全部映射 |
| RSS | 当前驻留的共享与私有页总和 | 低成本观察驻留变化 | 多进程相加后的物理总量 |
| PSS | 私有页加按映射者分摊的共享页 | 进程 footprint 对比 | 应用硬上限或唯一 kill 条件 |
| USS | 进程独占的 clean/dirty 页 | 私有驻留规模 | swap、GPU private 或未映射 buffer |
| SwapPss | 按共享比例分摊的换出页 | 换页归属分析 | 当前驻留内存 |
| `memory.current` | memcg 当前内存 charge | cgroup 内存使用 | 已包含 `memory.swap.current` |
| PSI | 任务因资源短缺发生 stall 的时间比例 | 系统压力与用户可感知延迟 | 某个 App 泄漏的直接证据 |

Android 17 的 `Debug.MemoryInfo.getTotalPss()` 已包含可用的 swapped-out PSS。不要再无条件追加 `VmSwap`，否则会混合比例口径与非比例口径，还可能重复计算。

PSS 计算需要遍历和分摊共享映射，采样成本和更新频率都高于 RSS。性能监控系统应保存指标来源、单位、采样时钟和进程状态，不能把不同时间取得的数值拼成一个“精确总内存”。

## 三、Android 17 的相关变化

### 3.1 Generational CMC

Android 17 的官方发布说明把年轻代回收加入 Concurrent Mark-Compact（CMC）路线。`android-17.0.0_r1` 中：

- `Heap` 在 CMC 可用且分代开启时创建一个主 `MarkCompact` 和一个轻量 `YoungMarkCompact`；
- sticky GC 选择 `YoungMarkCompact`；
- young、mid、old 三段边界由主 `MarkCompact` 管理；
- young collection 复用主 collector 的标记和压缩实现。

这项变化可以减少对稳定长生命周期对象的重复处理，但应用仍可能因高分配速率、过大 live set 或系统压力出现卡顿。设备是否运行 CMC、是否启用分代，还受 ART flags、系统属性、内核 UFFD 能力和 Mainline 模块版本影响。

详细源码见 [§10.10 ART GC 碎片化、Compaction 与性能诊断](10-art-gc-fragmentation-regions-optimization.md)。

### 3.2 MemoryLimiter

Android 17 的 `system_server` 加入 `MemoryLimiter`。官方开发者说明把它描述为按设备 RAM 实施应用内存限制；AOSP 源码给出了更细的产品边界：

- 功能受 aconfig flag 控制；
- 设备需要有效的 `/vendor/etc/memory-limiter-config.xml`；
- vendor 配置为不同总内存设备提供 visible/not-visible 的 memory 与 swap 配额；
- Java/JNI 链路写入每进程 cgroup v2 `memory.high` 和 `memory.swap.max`；
- 匿名页、shmem 与 swap 的联合用量持续越界时，系统可采集诊断并延迟终止进程；
- 退出描述使用 `MemoryLimiter:AnonSwap`，退出 reason 为 `ApplicationExitInfo.REASON_OTHER`。

“Android 17 设备一定采用同一固定上限”不符合源码。启用状态、限额和 kill 开关都可能因产品配置而异。应用应控制 live set、缓存和峰值，并在下次启动查询 `ApplicationExitInfo`；系统或 OEM 调试还要核对实际 cgroup 配置。

详细机制见 [§4.13 Android 17 MemoryLimiter：memcg 限制与超限诊断](../../part1-fundamentals/ch04-memory/13-android17-memorylimiter.md)。

### 3.3 `ProfilingTrigger.TRIGGER_TYPE_ANOMALY`

API 37 增加 `ProfilingTrigger.TRIGGER_TYPE_ANOMALY`。应用可通过 `ProfilingManager` 注册系统触发的诊断；产物类型取决于 anomaly。Android 17 的内存限制链路可以在终止前触发 heap profiling，但能否获得产物还受平台 flags、UID 下包数量、系统资源和诊断配置影响。

这是一种现场取证能力，不是实时自救回调。应用不能假设收到 trigger 后还有固定时长完成资源释放。

### 3.4 lmkd 仍以压力和进程重要性为基础

`android-17.0.0_r1` 没有一套公开的“机器学习内存调度器”替代 lmkd。lmkd 读取 PSI、swap、working-set refault、进程 `oom_score_adj` 和设备配置，在全机压力下选择符合条件的进程。

MemoryLimiter 与 lmkd 的输入和作用范围不同：

| 组件 | 主要范围 | 主要信号 | 动作 |
| --- | --- | --- | --- |
| ART GC | 单进程 managed heap | 分配、heap footprint、GC plan | 标记、回收、移动对象 |
| MemoryLimiter | 单应用进程 cgroup | proc state、vendor 限额、memcg 事件 | 节流/回收压力、诊断、可选 kill |
| lmkd | 全系统 | PSI、thrashing、swap、进程优先级 | 选择并终止进程 |
| Kernel reclaim | zone、node、memcg | 水位、页访问、分配需求 | 回收文件页、换出匿名页、compaction |

把这些组件统一写成“智能回收”会丢失触发条件和证据边界。

## 四、工具应该按问题选择

| 工具 | 最擅长回答的问题 | 常见误用 |
| --- | --- | --- |
| `dumpsys meminfo` | 某一时刻各内存大类、PSS/RSS/SwapPss 怎样分布 | 直接列出泄漏对象或 owner |
| Android Studio heap dump | 哪些 Java/Kotlin 对象仍可达、谁在持有 | 解释 Native/GPU 增长 |
| ART allocation profile | 哪些调用栈持续创建 managed object | 判断对象当前是否仍存活 |
| Perfetto system trace | GC、调度、frame、fault、PSI 与业务区间的时间关系 | 只看一条 slice 就下结论 |
| Native heap profile | `malloc`/`free` 的调用栈与存量 | 覆盖 mmap、GPU private 或所有 allocator |
| `/proc/<pid>/smaps` | 映射级 RSS/PSS、匿名/文件页、swap | 识别 Java 对象引用链 |
| DMA-BUF / memtrack / `dumpsys gpu` | 图形 buffer 与 GPU 私有内存 | 代替 Java/Native heap 分析 |
| `ApplicationExitInfo` | 上次进程退出原因、时间和重要性 | 依赖 description 字符串作为永久协议 |

“Memory Profiler”是 Android Studio Profiler 的内存任务集合，不存在一个跨所有内存域、可直接输出 ART 碎片率的公开工具。碎片判断必须绑定到 allocator、space 和分配失败路径。

## 五、建立第一份可复现快照

下面的命令用于保存包级内存摘要、页大小、进程状态和映射汇总：

```bash
package_name=com.example.app
adb shell dumpsys meminfo -d "$package_name"
adb shell getconf PAGE_SIZE
adb shell "pid=\$(pidof $package_name); \
  grep -E 'State|VmRSS|RssAnon|RssFile|RssShmem|VmSwap|Threads' /proc/\$pid/status; \
  cat /proc/\$pid/smaps_rollup"
```

这组输出是一张快照。采集时还要记录业务步骤、前后台状态、时间戳、应用版本、build fingerprint 和 ART 模块版本；否则很难与下一次样本比较。

有系统调试权限时，再补充下面的全机压力证据：

```bash
adb shell cat /proc/pressure/memory
adb shell dumpsys activity processes
adb shell am memory-limiter status
adb shell logcat -d -b all | grep -E 'lmkd|lowmemorykiller|MemoryLimiter'
```

普通量产应用通常无权读取其他进程或系统 cgroup 的完整信息。命令失败时应记录权限和构建类型，不能把缺少输出解释成组件未运行。

## 六、通用诊断流程

### 6.1 定义业务窗口

先写清操作序列，例如“冷启动后进入图片列表，滚动 60 秒，打开详情并返回 20 轮，再空闲 30 秒”。同一轮实验固定：

- 设备与 Android build；
- ART Mainline 模块；
- 应用版本、ABI 和构建类型；
- 账号、数据集和网络响应；
- 屏幕刷新率、温度和供电；
- 预热方式、循环次数与采样周期。

内存曲线缺少业务时间线时，很难区分合理缓存、延迟释放、周期性 GC 和持续泄漏。

### 6.2 先找增长的内存域

按同一采样时钟比较：

1. Java heap 是否增长；
2. Native heap 是否增长；
3. 文件映射或匿名映射是否增长；
4. Graphics、DMA-BUF 或 GPU private 是否增长；
5. SwapPss、major fault 和 PSI 是否同时上升；
6. FD、线程或 Surface 数量是否增长。

Java heap 稳定时，不要继续只抓 HPROF。Graphics 增长时转到 GPU/DMA-BUF；Native 增长时抓 heapprofd；文件映射增长时检查 VMA owner 与生命周期。

### 6.3 再区分 live set、churn 和峰值

- heap dump 在业务退出后仍显示对象引用链，说明 live set 没有释放；
- live set 稳定而 allocation profile 很高，说明短命分配较多；
- 平稳阶段正常、某个业务区间突然冲高，说明并发存量或中间结果形成峰值；
- Java/Native 都稳定而 RSS 与 SwapPss 上升，要继续检查映射、回收和系统压力。

同一种优化不能覆盖三类问题。泄漏要修 owner，churn 要修高频分配，峰值要修流水阶段与并发。

### 6.4 把内存与用户体验对齐

Perfetto 中至少同时观察：

- GC 总 slice 和 pause；
- 主线程 runnable/running 状态；
- frame timeline；
- page fault 与 swap；
- PSI memory stall；
- lmkd 或进程退出事件；
- 自定义业务 trace。

并发 GC 即使 pause 很短，也可能与应用线程竞争 CPU、缓存和内存带宽。只看 STW 时间会漏掉这部分干扰。

### 6.5 用对照实验验证

一次实验只改变一个可解释变量，例如缓存容量、图片目标尺寸、解析批次、并发任务数或某个临时 buffer。至少比较：

- live bytes 与对象数；
- 分配字节/秒和分配次数；
- young/full GC 次数、pause 和总时长；
- RSS、PSS、SwapPss；
- frame deadline miss 或业务尾延迟；
- 缓存命中、I/O、解码和 CPU 代价。

如果内存下降却显著增加 I/O、CPU 或重建延迟，方案仍需调整。内存优化是资源权衡，不是一项独立分数。

## 七、应用侧优化原则

### 7.1 修复 owner 和生命周期

常见 owner 包括：

- 静态集合持有 Activity、View 或 adapter；
- listener、callback、observer 没有按生命周期注销；
- coroutine、Flow 或 RxJava 链的 scope 超过页面；
- Handler、队列或 executor 持有长时间等待的任务；
- 图片、媒体、相机或数据库 wrapper 没有关闭；
- 缓存没有容量、TTL 或逐出策略；
- JNI 全局引用与 Native handle 没有配对释放。

`WeakReference` 不是通用生命周期修复。它可能让对象过早消失，也不能替代 unregister、`close()`、scope cancel 和缓存预算。

### 7.2 降低无效分配

先通过 allocation profile 找出热调用栈，再考虑：

- 移除循环中的临时集合与重复转换；
- 避免同一数据在 JSON、String、`byte[]` 间反复复制；
- 对固定格式数据采用流式或分块处理；
- 避免每帧创建路径、绘制参数和事件 wrapper；
- 调整分页、预取和批处理，限制同一时间的中间结果；
- 对创建成本高且状态可安全重置的对象评估有界复用。

普通小对象的 ART 分配成本较低。盲目对象池会延长对象寿命、扩大 old generation、增加锁和脏状态风险。

### 7.3 给缓存写出预算

缓存策略至少定义：

- 最大字节数或条目数；
- 单条目上限；
- 前台、后台和不可见状态的容量；
- 淘汰规则与命中率；
- 重建成本；
- 低内存或业务退出时的处理；
- 多进程是否重复缓存。

LRU 只是一种淘汰顺序，不会自动给出合适容量。磁盘缓存也可能增加 page cache、文件映射和 I/O，不能当作“零内存”方案。

### 7.4 图片以内存中尺寸为准

PNG、JPEG、WebP 和 AVIF 的文件体积不等于解码后的像素内存。解码后的占用主要受宽高、像素格式、row stride、是否硬件 Bitmap 和并发副本影响。

优先措施包括：

- 按实际展示尺寸请求和解码；
- 避免原图、变换输入、变换输出同时长期存活；
- 控制列表预取与并发解码；
- 理解图片库的内存缓存、bitmap pool 与硬件 Bitmap 策略；
- 把 Java、Native、Graphics 和 DMA-BUF 一起观察。

仅把 PNG 改成 WebP 可能减少网络和磁盘字节，却不保证解码后的 RAM 同比例下降。

### 7.5 数据结构要按访问模式比较

`SparseArray` 对 `int` key 可以避免部分装箱，但它的查找、删除和维护成本与 `HashMap` 不同。`ArrayList`、`ArrayMap`、primitive collection、紧凑数组和数据库查询也各有适用负载。

判断依据应是：

- 条目数量与 key/value 类型；
- 查询、遍历、插入和删除比例；
- 是否位于热路径；
- 对象和 backing array 的实际占用；
- CPU、GC 与可读性代价。

“所有 HashMap 都换成 SparseArray”或“数据类天然更省内存”都不是可靠规则。

### 7.6 异步不能自动降低峰值

把工作移到协程或后台线程只改变执行线程。若多个任务并发持有输入、中间结果和输出，峰值反而可能升高。

需要显式控制：

- 并发度；
- 队列长度；
- backpressure；
- 取消后的资源释放；
- 超时与失败重试；
- 结果交付前的最大积压。

对内存密集型任务，串行或小并发有时能换取更稳定的峰值；是否值得要结合吞吐和尾延迟测量。

### 7.7 正确处理后台状态

应用应在 UI 不可见或进入后台时释放可低成本重建的缓存和资源。Android 14 / API 34 起，多项历史 `onTrimMemory()` level 不再发送；`TRIM_MEMORY_UI_HIDDEN` 与 `TRIM_MEMORY_BACKGROUND` 仍有实际用途，具体边界见 [§10.4 低内存对系统性能的影响](04-low-memory-impact.md)。

回调不是 MemoryLimiter 的专用通知，也不能保证每次进程终止前都到达。重要状态要及时持久化，资源治理不能等待临终信号。

## 八、容易产生反效果的做法

### 8.1 频繁调用 `System.gc()`

显式 GC 不能释放仍可达对象、Native 泄漏、GPU 资源或未关闭的映射。放在交互路径还可能增加暂停和 CPU。只有可复现实验能证明某个离线阶段受益时，才值得保留，并记录设备与版本边界。

### 8.2 只看峰值数字

合理的图片解码、Dex 加载或模型初始化都可能形成短时峰值。应结合持续时间、回落情况、同时段业务和是否接近设备限制判断。把所有峰值压低可能导致重复 I/O、重复解码或频繁重建。

### 8.3 在生产环境高频采集重型数据

高频 PSS、完整 smaps、heap dump 和 allocation profile 都有成本。线上监控应采用轻量趋势、抽样和触发式诊断；重型采集放在异常窗口，并设置频率、存储、隐私与电量预算。

### 8.4 把工具标签当成因果

`dumpsys meminfo` 的 `Java Heap`、`Native Heap`、`Graphics` 是统计分类。分类增长只负责缩小调查范围，不能自动指出业务 owner。修复仍需调用栈、引用链、资源表或源码证据。

## 十、版本与证据边界

- 当前平台结论止于 Android 17 / API 37 / `android-17.0.0_r1`。
- 内核 PSI、cgroup v2 和回收语义止于 `android17-6.18-2026-06_r6`。
- Android 10～16 的版本差异可以保留，但应回到对应 release tag 核对。
- ART Mainline、OEM runtime、allocator 和 GPU 驱动可能独立于 API level 更新，实验记录必须包含设备实际版本。
- 任何收益数字都应来自可复现的目标设备实验，不使用脱离负载与硬件的固定百分比。
