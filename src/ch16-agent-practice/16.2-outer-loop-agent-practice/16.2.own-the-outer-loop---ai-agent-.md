# Own the Outer Loop - AI Agent 工程实践

## 要点

### 🔹 GPU功耗管理基础
Android 17 引入了全新的 GPU 功耗管理策略，基于 DVFS（动态电压频率调节）机制的深度优化。

### 🔹 DVFS 调优算法
新算法结合了应用负载预测和系统资源监控，实现了更智能的频率和电压调节。

### 🔹 多核心协调机制
跨 GPU 核心的功耗分配协调，根据不同应用场景动态调整核心工作状态。

### 🔹 热量控制与性能平衡
在控制 GPU 发热的同时保持最佳的性能表现，引入了热量感知的调度策略。

### 🔹 SoC 厂商定制化
支持不同 SoC 厂商的定制化 DVFS 策略，充分发挥硬件性能潜力。

## 扩展

### 🔸 游戏场景优化
针对游戏场景的特殊功耗优化策略，平衡帧率和功耗的关系。

### 🔸 AI 推理任务
AI 推理任务在 GPU 上的功耗管理，考虑模型大小和推理频率的影响。

### 🔸 后台任务处理
后台 GPU 任务的功耗管理策略，避免不必要的资源占用。

## 1. Outer Loop 解决的是责任边界

“Own the Outer Loop”来自 Addy Osmani 在 2026 年提出的 agentic engineering 工作模型。agent 可以在 inner loop 中调查、实现、验证并迭代；工程师在 outer loop 中决定任务是否值得做、证据是否足以支持发布，以及失败后由谁处理。

两个循环的分工可以写成一张表：

| 循环 | 主要动作 | 输出 |
| --- | --- | --- |
| Inner loop | 调查、计划、修改、运行检查、修复失败、汇报 | diff、测试、日志、假设和未解决项 |
| Outer loop | 定义目标与约束、选择 verifier、审查证据、批准或阻断、对后果负责 | task contract、quality policy、verdict、owner、回退决定 |

这里的“own”包含三个责任：

- **Quality**：提前定义哪些检查能够证明结果满足要求；
- **Verdict**：根据证据作出 accept、revise、block 或 rollback；
- **Answerability**：事后能够解释做了什么、依据是什么、风险由谁接管。

工程师无需介入 agent 的每一步工具调用。人应把注意力放在目标、不可变约束、高风险操作和发布边界。低风险且可自动验证的内循环可以长时间自主运行；证据不足或将要越过权限边界时，循环必须停下。

## 2. 证据是两个循环的接口

自然语言汇报只能帮助阅读，不能独立证明代码正确。inner loop 交给 outer loop 的 evidence packet 至少包含：

- 基线 commit、目标版本与环境；
- 改动文件和 diff；
- 运行过的命令、退出码与原始结果位置；
- 被验证的需求和未覆盖的需求；
- 源码、API 或设计依据；
- 已知风险、失败模式和回退步骤；
- 需要人工判断的具体问题。

“测试都通过”仍然缺少测试范围。Android 平台修改要说明跑的是单元测试、`TEST_MAPPING`、CTS 模块、CTS-V、VTS、GTS、自定义设备测试中的哪些部分。文档修改则要说明元数据、内部链接、版本边界、引用可达性和构建检查。

证据还要能由另一个执行者复现：

1. 命令不依赖未记录的本机状态；
2. 输入、设备和 build fingerprint 可定位；
3. 原始输出不会被 agent 摘要覆盖；
4. 失败结果与成功结果同样保留；
5. verifier 与实现使用独立判断标准。

## 3. 用 Task Contract 约束 inner loop

一个可执行的 task contract 要把“完成”从感觉改成可判定状态。下面的 YAML 用于描述 Android 17 framework 修复任务：

```yaml
goal: 修复指定 Binder 调度问题
baseline:
  platform: android-17.0.0_r1
  kernel: android17-6.18-2026-06_r6
scope:
  allowed_projects:
    - frameworks/base
    - system/core
  forbidden:
    - public_api_change
    - new_privileged_permission
invariants:
  - 不改变跨用户隔离
  - 不扩大调用方权限
evidence:
  - source_path_and_line
  - focused_atest_result
  - TEST_MAPPING_result
  - git_diff
stop:
  - 需要修改 scope 外项目
  - 测试连续三次出现无法解释的不稳定
  - 发现安全或兼容性影响
```

这份 contract 把平台与 kernel 锚点、允许范围、不变量、证据和停止条件放在同一处。agent 可以自由选择调查顺序，但不能自行扩大工程范围或降低验证标准。

不同任务需要不同 contract：

| 任务 | 必要约束 | 典型 verifier |
| --- | --- | --- |
| framework bug | tag、目标模块、API/权限不变量 | 单测、`TEST_MAPPING`、CTS、源码 review |
| kernel bug | kernel tag、config、ABI/KMI、设备 | KUnit、kselftest、VTS、设备压力测试 |
| 性能优化 | 场景、设备、thermal、metric schema | Perfetto、benchmark、置信区间、守护指标 |
| 文档 review | frontmatter、outline、版本上限、章节范围 | metadata、链接、引用、构建、文字扫描 |
| 定时维护 | allowlist、幂等键、锁、预算、冲突策略 | dry-run、状态机、审计日志、差异上限 |

## 4. Inner Loop 要怎样设计

### 4.1 调查与修改分开

调查阶段先建立最小事实集：

- 当前分支、commit 与 dirty files；
- 目标文件 owner 和并发修改；
- 相关源码调用链；
- 现有测试与失败复现；
- 历史变更和已知约束。

修改阶段只处理 contract 内的机制。调查中发现相邻问题时，记录为 follow-up，不把它悄悄塞进当前提交。这样可以保持因果关系清晰，也便于回滚。

### 4.2 Verifier 由问题决定

模型的自我评价不属于独立验证。verifier 应尽量使用外部、确定且可重复的信号：

- compiler、lint、Metalava 和静态分析；
- 单元、集成、设备和兼容性测试；
- Perfetto、trace processor SQL 与 benchmark；
- schema、metadata、link、format 和 build checker；
- 权限组合表、SELinux denial 与 negative test；
- 人工交互测试和视觉检查。

对于 Android 平台代码，下面的命令演示从目标测试到当前目录 `TEST_MAPPING` 的两级验证：

```bash
atest FrameworksServicesTests:TargetTest
atest --test-mapping frameworks/base/services
```

第一条命令适合快速验证直接相关测试，第二条命令扩大到声明的 presubmit 集合。两者都不能替代受影响 CTS/VTS、设备测试或人工场景；evidence packet 要记录未运行部分。

### 4.3 失败必须改变下一轮动作

有效循环会根据失败类型选择不同路径：

| 失败类型 | 下一步 |
| --- | --- |
| compile error | 修复语法、类型或依赖，不讨论业务结论 |
| deterministic test failure | 定位第一个失败，检查基线与改动 |
| flaky failure | 保存多轮分布，隔离设备/时序/环境变量 |
| verifier 缺失 | 暂停发布，补测试或请求人工验证 |
| scope 冲突 | 停止修改，向 outer loop 请求扩大授权 |
| 同一假设反复失败 | 放弃该假设，回到调查阶段 |

无进展重试会消耗预算并制造噪声。循环应记录“本轮新增了什么证据”，连续多轮没有新证据时自动停下。

## 5. Outer Loop 的四个控制面

### 5.1 Constraints

constraints 定义 agent 可以接触什么、不能改变什么：

- 仓库、目录、分支和文件 allowlist；
- Android/platform/kernel tag；
- 可用凭据和外部服务权限；
- 禁止发送、删除、发布或推送的对象；
- API、ABI、权限、用户数据和兼容性不变量；
- 时间、token、设备和并发预算。

约束要由 harness 强制执行。只把“请勿修改其他文件”写进 prompt，仍然缺少文件级 diff 检查和提交 allowlist。

### 5.2 Sampling

agent 产出速度可能高于人工 review 速度。sampling policy 决定哪些结果必须逐项看，哪些可以抽样：

- 安全、隐私、支付、权限和数据迁移逐项 review；
- public API、kernel ABI、SELinux 和跨用户行为逐项 review；
- 机械格式化或已由强 verifier 覆盖的低风险改动可抽样；
- 新类型任务在获得稳定历史前提高抽样率；
- 发现一例系统性缺陷后扩大到同批次或同模板。

抽样率应随风险和 verifier 可信度变化，不按固定百分比长期运行。

### 5.3 Audit

审计记录关注决策与边界，不需要保存全部模型思考。建议保留：

- task contract 与版本；
- 输入材料的来源和哈希；
- agent/harness/tool 版本；
- 状态转移、重试、超时和人工接管；
- diff、测试和发布证据；
- verdict、批准者、时间和理由；
- 回滚或事故关联。

敏感 prompt、用户数据、凭据和完整 trace 不应无条件写入日志。审计可解释性与数据最小化要一起设计。

### 5.4 Ownership

每个自动化都要有清楚的 owner：

- 谁维护 prompt、skill 和 verifier；
- 谁处理定时任务连续失败；
- 谁批准新的写权限；
- 谁响应错误提交、错误发布或数据损坏；
- 谁决定停用、降级和回滚；
- owner 不在线时由谁接管。

自动化名称、告警目标和仓库 CODEOWNERS 不能代替值班责任。owner 需要有权限执行回退，也要能读取足够证据。

## 6. Back-pressure：按验证能力限制产出

并行 agent 增加的是候选变更数量，review、设备和发布容量不会同比增长。没有 back-pressure 时，未审证据会堆积，工程师只能依赖摘要作决定。

常用的 back-pressure 机制包括：

- 限制同时处于 review 的任务数；
- 每个模块同一时间只允许一个写任务；
- 前一批 verdict 未完成前不启动下一批；
- 设备实验室按风险分配队列；
- diff 超过文件数或行数阈值时拆分任务；
- flaky rate、回滚率或人工拒绝率升高时自动降并发；
- 缺少 owner、baseline 或 verifier 的任务不进入执行队列。

吞吐量应以“被验证并可负责的变更”计数。生成了多少 patch、运行了多少 agent 或消耗了多少 token，都不能单独表示工程产出。

## 7. 定时 Agent 的状态机

定时任务需要显式状态，避免每次唤醒都从 prompt 猜测进度：

| 状态 | 进入条件 | 允许动作 |
| --- | --- | --- |
| queued | contract 完整、资源可用 | 只读检查、获取锁 |
| investigating | 锁与 baseline 已确认 | 搜索、读取、复现 |
| editing | 假设和 scope 已确定 | 修改 allowlist 文件 |
| verifying | diff 固定 | 运行 verifier、保存证据 |
| needs-review | 自动检查通过 | 等待 outer-loop verdict |
| needs-rework | reviewer 给出可执行反馈 | 修改当前 scope |
| blocked | 缺权限、冲突或无新证据 | 停止写入并报告 |
| finalized | verdict 接受 | 提交、发布或归档 |

状态转移要带幂等键。任务重启后读取已有 commit、日志和 verifier 结果，不能重复发送消息、重复创建文件或重复提交同一改动。

并发写入还需要锁与冲突策略：

- 锁定文件或章节，不锁整个仓库；
- 获取锁后再次确认 HEAD 和 dirty state；
- 发现其他 agent 已改同一文件时退出或请求协调；
- 提交只包含 allowlist 文件；
- 不清理、不回退、不重排其他任务的改动；
- 锁超时后检查 owner 是否仍存活，再决定回收。

## 8. Android 17 平台工作的证据梯度

Android 平台变更可以按证据强度逐层提高：

1. **Source evidence**：在 `android-17.0.0_r1` 找到调用链和版本边界；
2. **Local build**：目标模块编译，API/ABI 检查通过；
3. **Focused test**：直接相关单元或集成测试通过；
4. **Mapping test**：运行 `TEST_MAPPING` 中的 presubmit/postsubmit；
5. **Compatibility test**：运行受影响 CTS/VTS/CTS-V 模块；
6. **Device evidence**：在目标 build、设备和场景复现；
7. **Release evidence**：灰度、守护指标、停止和回退条件生效。

CTS 覆盖公共 API、权限、资源、Intent 等兼容性要求，但 Android 17 CDD 明确要求实现者对测试未覆盖的行为兼容性负责。outer loop 要保留源码 review、设备行为和产品约束，不能把“CTS 通过”解释成所有风险已消失。

kernel 修改另加 `android17-6.18-2026-06_r6`、defconfig、KMI/ABI、KUnit/kselftest、VTS 和目标 SoC 设备证据。vendor driver、firmware 与 AOSP common kernel 的差异要单列。

## 9. 知识库 Review 的 Outer Loop

知识库流水线同样适用这套模型。inner loop 可以逐篇读取、查证、修改和运行检查；outer loop 要预先定义：

- 平台锚点 Android 17 / API 37 / `android-17.0.0_r1`；
- kernel 锚点 `android17-6.18-2026-06_r6`；
- frontmatter 和受保护 outline 的字节不变量；
- 一篇一提交，不混入并发任务文件；
- 历史版本可以保留，最高版本不超过 Android 17；
- 源码、官方文档和实验结果的证据等级；
- metadata、SUMMARY、内部链接、外链、代码块和文字检查；
- 全库完成后的统一文风与交叉引用 review。

每章提交就是一个小 verdict：该章在当前证据范围内可以进入下一阶段。它不代表文章永久正确；tag、工具和研究原型更新后，应由 freshness task 重新打开 review。

如果自动任务发现 frontmatter 格式损坏，应只修复阻断解析的最小部分，保留 task6/task9 字段和值。若另一个任务正在改正文，当前任务应避让，不能用回退命令恢复自己预期的文件版本。

## 10. 常见失控模式

### 10.1 把 agent 汇报当作 verifier

“已完成并测试”属于声明。outer loop 应读取命令、退出码、原始结果和覆盖范围，并对高风险 diff 做独立 review。

### 10.2 verifier 与需求错位

lint 通过只能证明规则覆盖的格式或静态性质；它不证明 Binder 身份校验、跨用户隔离或启动性能。每条需求都要能映射到一个 verifier 或人工判断。

### 10.3 让 agent 自行扩大权限

循环遇到访问拒绝时，不能自行安装凭据、关闭 SELinux、修改 CI policy 或扩大仓库写权限。权限变化属于 outer-loop verdict。

### 10.4 用重试掩盖不稳定

测试失败后反复运行到通过，会丢失 flaky 信号。保存每轮结果，报告失败比例和环境，单独处理确定失败与环境失败。

### 10.5 只保留成功证据

被否决的假设、失败实验和回滚同样有价值。删除它们会让后续 agent 重走同一路径，也会削弱事故复盘。

### 10.6 产出超过 review 容量

agent fleet 可以在短时间产生大量 diff。review queue 持续增长时应降低并发、缩小 scope 或加强 verifier，不能继续用摘要压缩人的判断。

## 11. 一份可直接使用的 Verdict 模板

下面的模板用于 outer loop 对一次 agent 任务作出裁决：

```text
Verdict: ACCEPT | REVISE | BLOCK | ROLLBACK

目标:
基线:
影响范围:

已核验证据:
- diff:
- tests:
- source/API:
- device or document checks:

未覆盖:
- （填写）

风险与回退:
- （填写）

责任人:
裁决理由:
```

模板要求 reviewer 明示未覆盖范围，避免把局部测试写成全面保证。`ACCEPT` 表示在记录的约束与证据内接受；环境或目标变化后需要重新评估。
