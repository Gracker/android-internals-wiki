# Android 17 AGI Frame Profiler 与 gapii Spy 架构解析

<!-- outline-start -->
## 要点

### 🔹 GPU功耗管理基础
Android 17 引入了全新的 GPU 功耗管理策略，基于 DVFS（动态电压频率调节）机制的深度优化。

### 🔹 DVFS 调优算法
新算法结合了应用负载预测和系统资源监控，实现了更智能的频率和电压调节。

### 🔹 多核心协调机制
跨 GPU 核心的功耗分配协调，根据不同应用场景动态调整核心工作状态。

### 🔹 热量控制与性能平衡
在控制 GPU 发热的同时保持最佳的性能表现，引入了热量感知的调度策略。

### 🔹 SoC 厂商定制化
支持不同 SoC 厂商的定制化 DVFS 策略，充分发挥硬件性能潜力。

## 扩展

### 🔸 游戏场景优化
针对游戏场景的特殊功耗优化策略，平衡帧率和功耗的关系。

### 🔸 AI 推理任务
AI 推理任务在 GPU 上的功耗管理，考虑模型大小和推理频率的影响。

### 🔸 后台任务处理
后台 GPU 任务的功耗管理策略，避免不必要的资源占用。

## 这个工具解决什么问题

Android GPU Inspector（AGI）提供两种尺度不同的分析：

| 模式 | 主要数据路径 | 适合回答的问题 |
|---|---|---|
| System Profile | Perfetto 与设备/厂商 producer | CPU 调度、GPU queue、frequency、counter、功耗与 thermal 在一段时间内怎样变化 |
| Frame Profile | GraphicsSpy Vulkan layer、gapii、GAPIS、GAPIR | 一帧附近的 API command、pipeline、shader、texture、render pass 与 framebuffer 状态 |

System Profile 用于确认问题窗口和责任阶段。帧已被证据指向 GPU command、shader、纹理或 render pass 后，再使用 Frame Profile 做单帧检查。gapii 会进入目标进程并记录 API 参数、资源和内存观察，采集开销远高于常规系统 trace，不适合作为生产监控器。

## 两套版本坐标

AGI 不属于 `android-17.0.0_r1` 平台源码。复现实验需要同时记录：

- Android 17 / API 37 / `android-17.0.0_r1`：负责 Vulkan loader、调试 layer 注入条件、应用与系统安全边界；
- AGI release 或 commit：负责 gapii、GAPIS、GAPIR、gapid APK 和 `.gfxtrace` 格式。

正式章节把工具源码固定到 AGI `v3.3.3`，Android 设备侧固定到 `android-17.0.0_r1`。Android 版本相同、AGI 或 GPU driver 不同，抓帧与 replay 结果仍可能变化。

## 组件放在哪里

| 组件 | 位置 | 职责 |
|---|---|---|
| AGI UI / GAPIC | 开发机 | 发起采集并展示 Commands、Pipeline、Shader、Texture 等视图 |
| GAPIS | 开发机 | 解析 `.gfxtrace`、演算 API state、生成 replay payload |
| GraphicsSpy + `libgapii.so` | 目标 App 进程 | 作为 Vulkan layer 拦截调用，记录参数、状态和资源 |
| gapid APK | Android 设备 | 提供按 ABI 打包的 layer、设备信息服务和 replay Activity |
| GAPIR | Android 设备 | 在目标 GPU driver 上执行 replay opcode |

主机端不会用开发机 GPU 代替目标设备完成 replay。图像和性能结果依赖目标设备的 OS、GPU、driver、extension 与捕获状态。

## Android 17 的 layer 注入边界

Android 设备通过 global settings 选择调试 layer，主线键包括：

- `enable_gpu_debug_layers`：开启 GPU 调试 layer；
- `gpu_debug_app`：限定目标 package；
- `gpu_debug_layer_app`：指定提供 layer 的 gapid APK；
- `gpu_debug_layers`：选择 `GraphicsSpy`。

`debug.agi.procname` 进一步选择包内进程名，不能替代 package 选择。多进程游戏没有选中负责 Vulkan 渲染的进程时，应用可以正常启动，却没有 capture 数据。

Android 17 Vulkan loader 允许调试 layer 的条件包括目标 App 可调试、可 root 的 userdebug 环境，或满足平台声明与 target SDK 条件的应用。AGI 官方支持流程仍要求目标 App 为 debuggable。平台存在其他允许路径，不表示 AGI 支持抓取任意量产应用。

layer APK 的 ABI 必须与目标进程匹配。排查无数据时，要分开检查：

1. gapid APK 是否安装且 ABI 正确；
2. global settings 是否指向目标 package 和 `GraphicsSpy`；
3. Vulkan loader 是否找到 `libVkLayer_GraphicsSpy.so`；
4. wrapper 是否加载 `libgapii.so`；
5. gapii local abstract socket 与 adb forward 是否建立；
6. 触发窗口内是否出现 frame boundary。

## 捕获与 replay 的证据边界

一份 `.gfxtrace` 可包含捕获头、初始 Vulkan state、API command、memory observation 和资源数据。它使用 ProtoPack v2 容器，不能概括成单个普通 protobuf 文件。

GAPIS 可以在主机 CPU 上演算绑定状态；draw call 对 framebuffer 的像素结果仍需 GAPIR 在目标设备 driver 上 replay。未显式同步的竞态、外部资源、driver 差异和不支持 extension 都可能让 replay 与原画面不同。

CPU submit 返回只说明 command 已交给 driver。判断 GPU 工作何时完成，仍要对齐 GPU job 与 producer completion fence；判断显示何时完成，还要继续追 BufferQueue、SurfaceFlinger、HWC 和 present fence。Frame Profile 的 command 视图不能替代整条显示时间线。

## 使用顺序

1. 用 System Profile 找到慢帧或 GPU-bound 时间窗。
2. 检查 CPU submit、GPU fence、FrameTimeline、频率、thermal 与 HWC composition。
3. 选取可稳定复现的一帧做 Frame Profile。
4. 在 Commands 中定位昂贵 render pass/draw，再检查 pipeline、shader、纹理与 attachment。
5. 修改一个变量，回到 System Profile 验证帧时间、功耗与温度。

单帧优化收益要回到长时间 workload 复测。抓到的帧可能处于冷态、特殊相机视角或偶发资源上传阶段，不能代表整段游戏或动画。
