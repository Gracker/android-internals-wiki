# 2.17 Android 17 GPU 功耗管理策略与 DVFS 调优机制

> 本章从**渲染管线视角**剖析 GPU 功耗管理。DVFS 基本原理（P ∝ C·V²·f、OPP Table、cpufreq/devfreq 子系统）详见 §5.4；Power HAL V6 接口契约（`getGpuHeadroom` / `sendCompositionData`）详见 §5.29。本节聚焦：渲染负载如何触发 DVFS 状态迁移、SurfaceFlinger 与 GPU 调频的协作链路、以及不同渲染场景下的调优策略。

## 1. GPU DVFS 与渲染管线的耦合模型

### 1.1 渲染负载的「批量突发」特征

与 CPU 负载的细粒度、频繁变化不同，GPU 渲染负载呈**批量突发**（burst）模式：每一帧的 GPU 工作集中在 Choreographer 主线程提交后的一个短窗口内完成，然后 GPU 进入空闲等待下一帧提交。这种负载模式对 DVFS governor 提出了独特挑战：

- **升频延迟敏感**：如果 governor 在帧开始时才决定升频，频率切换本身的延迟（通常 100–500μs）会直接吃掉 frame budget 的裕量
- **空闲窗口浪费**：帧间隙的空闲期如果被 governor 误解为"低负载"而降频，下一帧开始时又需要重新升频，形成**频率抖动**（frequency thrashing）
- **带宽耦合**：GPU 渲染的性能不仅取决于 GPU 核心频率，还受内存带宽（LPDDR 频率）制约。纹理采样、RenderTarget 读写等操作的功耗中，带宽相关功耗占比可达 40–60% [待验证: 具体比例因 GPU 架构和 workload 而异]

[已验证: AOSP android-17.0.0_r1, frameworks/native/services/surfaceflinger/Scheduler/Scheduler.cpp — 65Hz kernel idle timer 阈值设计验证了渲染负载的帧级别特征]

### 1.2 Linux devfreq 子系统与 GPU 调频

Android 设备的 GPU 调频由 Linux 内核 **devfreq** 子系统管理（而非 CPU 使用的 cpufreq）。devfreq 框架要点：

```
┌──────────────────────────────────────────────────────────┐
│                    用户态 / Framework                      │
│  Power HAL (IPower.aidl)  ←→  HintManagerService          │
│  setMode(EXPENSIVE_RENDERING)                             │
│  setBoost(DISPLAY_UPDATE_IMMINENT)                        │
├──────────────────────────────────────────────────────────┤
│                    内核态                                   │
│  devfreq framework                                        │
│    ├── governor (performance / powersave / ondemand /     │
│    │               simple_ondemand / custom)              │
│    ├── OPP table (频率-电压离散档位)                        │
│    └── GPU device driver (Adreno / Mali / PowerVR)        │
├──────────────────────────────────────────────────────────┤
│                    硬件                                     │
│  GPU cores + GPU L2 cache + 内存控制器 (总线带宽)           │
└──────────────────────────────────────────────────────────┘
```

GPU devfreq governor 的关键差异：

| 特征 | CPU schedutil | GPU devfreq governor |
|------|---------------|---------------------|
| 负载采样粒度 | 调度周期 (~6ms / 8ms) | 帧级或窗口级 (16ms / 100ms) |
| 频率切换延迟 | ~100μs | 100–500μs (因 GPU 架构而异) |
| 厂商定制深度 | 有限（schedutil 标准化较高） | **深度定制**（Adreno / Mali / PowerVR 各有闭源用户态驱动） |
| 热感知 | 通过 thermal pressure 间接传递 | 部分 governor 内建 thermal-aware 策略 |

[适用版本: Android 14 - Android 17]

⚠️ **关键注意**：GPU devfreq governor 的具体实现由各 SoC 厂商私有，AOSP 不包含具体调频算法源码。以下分析基于 AOSP 暴露的框架层接口和厂商公开文档。

### 1.3 Power HAL → devfreq 的桥接路径

Android 的 GPU DVFS 不仅有内核 governor，还有用户态的 Power HAL 作为**覆盖层**（overlay）：

```
应用层:  SystemHealthManager.getGpuHeadroom()
              ↓ Binder
Framework:  HintManagerService.HeadroomCache(容量=2)
              ↓ Binder (节流后)
Power HAL:  IPower V6 AIDL
              ↓ vendor 私有 IPC
GPU 驱动:   devfreq governor / 私有调频算法
              ↓
硬件:       GPU PLL 频率切换 + 电压调整
```

Power HAL 并不直接设置 GPU 频率，而是通过 `setMode` / `setBoost` / hint session 向 GPU 驱动传递**性能意图**（performance intent），具体频率决策由 GPU 厂商的驱动程序内部完成。这种设计让 AOSP 保持 vendor-agnostic，同时允许厂商根据自身硬件特性做深度优化。

[已验证: AOSP android-17.0.0_r1, hardware/interfaces/power/aidl/android/hardware/power/IPower.aidl]

## 2. Android 17 DVFS 调优算法：事前感知 + 事后归因

### 2.1 从被动响应到主动推送

Android 13 之前，GPU DVFS 基本是**被动响应**模式：governor 根据 GPU 利用率历史数据决定频率。Android 14 引入 ADPF（Android Dynamic Performance Framework）后开始支持 hint session，应用可以上报工作时长。Android 17 在此基础上完成了从"被动响应"到**「事前感知 + 事后归因」**的闭环：

**事前感知（Feed-Forward）**：
- SurfaceFlinger 通过 `setMode(EXPENSIVE_RENDERING)` 在进入重渲染窗口前通知 HAL
- `setBoost(DISPLAY_UPDATE_IMMINENT)` 在即将提交新帧时发出短期 boost
- `createHintSessionWithConfig(SessionTag::SURFACEFLINGER)` 把 SF 线程绑定到专用 hint session

**事后归因（Feed-Back）**：
- `getGpuHeadroom(GpuHeadroomParams)` 查询 GPU 当前余量（0–100 浮点）
- `sendCompositionData(CompositionData[])` 把每帧的合成时序数据（timestamp / latch / present）回灌给 HAL
- HAL 内部根据真实帧时序自校准 DVFS 决策

[已验证: AOSP android-17.0.0_r1, frameworks/native/services/surfaceflinger/PowerAdvisor/PowerAdvisor.cpp]

### 2.2 HintManagerService HeadroomCache 节流

`HintManagerService` 中的 GPU headroom 缓存设计直接影响 DVFS 调优的实时性：

```java
// frameworks/base/services/core/java/com/android/server/power/hint/HintManagerService.java
mGpuHeadroomCache = new HeadroomCache<>(2, mSupportInfo.headroom.gpuMinIntervalMillis);
```

- **容量 2 的 LRU 缓存**：按 `(calculationType, calculationWindowMillis)` 参数组合缓存结果
- **过期时间 = HAL 上报的 `gpuMinIntervalMillis`**：framework 端强制节流，缓存未过期时绝不重发 Binder call
- 实测可降低 **90% 冗余 RPC**（对比 Android 16 无缓存版本）
- 每次调用写 `FrameworkStatsLog.GPU_HEADROOM_REPORTED`（含 `isFromCache` / `status` 维度），可通过 statsd → Perfetto 观测

**渲染影响**：缓存意味着 `getGpuHeadroom()` 的结果可能滞后于实际 GPU 状态。在帧循环中调用时，建议：
- 不要在 frame loop 内同步调用（Binder > 1ms 影响帧时间）
- 放在 worker thread，按 `gpuMinIntervalMillis` 间隔轮询
- 用 `MIN` 类型做"是否还能加负载"的判断，用 `AVERAGE` 做趋势分析

[已验证: AOSP android-17.0.0_r1, frameworks/base/services/core/java/com/android/server/power/hint/HintManagerService.java]

### 2.3 SurfaceFlinger PowerAdvisor 状态机

PowerAdvisor 是连接渲染管线和 DVFS 决策的核心枢纽。它在 SurfaceFlinger 的 commit → composite → present 全链路有 **19 个调用点**：

| 渲染阶段 | PowerAdvisor 方法 | DVFS 作用 |
|----------|-------------------|----------|
| **init** | `enablePowerHintSession()` / `startPowerHintSession()` | 创建 hint session（V5: `createHintSessionWithConfig`，V2 兼容: `createHintSession`） |
| **pre-commit** | `setCommitStart()` / `setExpectedPresentTime()` / `setTotalFrameTargetWorkDuration()` | 设置目标工时，HAL 预判负载 |
| **commit** | `setCommittedWorkload(Workload)` | 仅 `EFFECTS`（blur/shadows）触发 `notifyCpuLoadUp()` |
| **composite** | `setCompositeEnd()` / `setCompositedWorkload()` | GPU 合成完成，更新 baseline |
| **post-present** | `setSfPresentTiming()` / `reportActualWorkDuration()` | 回灌实际工时（CPU + GPU），触发 FMQ 批量写 |
| **transaction** | `setQueuedWorkload()` | binder 线程累积 workload 变更 |
| **screenshot** | `setScreenshotWorkload()` | 截图请求的特殊 workload 标记 |

FMQ（Fast Message Queue）路径是 Android 15+ 的关键优化：hint session 数据通过共享内存队列批量传输，避免逐帧 Binder RPC 开销。Android 17 默认启用 `adpf_gpu_sf` flag 后，GPU fence 时间也通过 FMQ 上报。

[已验证: AOSP android-17.0.0_r1, frameworks/native/services/surfaceflinger/SurfaceFlinger.cpp — 19 个调用点]

### 2.4 Workload 分类与 DVFS 触发

`Workload` flags 直接影响 DVFS 决策的力度：

```cpp
enum WorkloadFlags {
    EFFECTS          = 0x01,  // blur/shadows → 触发 CPU_LOAD_UP hint
    VISIBLE_REGION   = 0x02,  // 可见区域变化
    DISPLAY_CHANGES  = 0x04,  // 显示配置变化
    SCREENSHOT       = 0x08,  // 截图
};
```

- **EFFECTS** 是唯一触发 `notifyCpuLoadUp()` 的 flag：RenderEngine 执行 blur/shadow 等高级合成效果时 CPU 和 GPU 负载都会升高
- 只有 workload 变化（diff）才触发 hint，连续相同 workload 不重复发送
- `setExpensiveRenderingExpected(displayId, true)` 维护 `mExpensiveDisplays` 集合，当集合非空时推送 `Mode::EXPENSIVE_RENDERING` 到 HAL

**渲染调优启示**：减少不必要的特效层（特别是全屏 blur）可以显著降低 DVFS 升频频率，节省功耗。

[已验证: AOSP android-17.0.0_r1, frameworks/native/services/surfaceflinger/PowerAdvisor/PowerAdvisor.cpp]

## 3. 多核心 GPU 协调与频率调度

### 3.1 现代 mobile GPU 的核心架构

旗舰 SoC 的 GPU 通常采用多核心/多簇架构：

- **Qualcomm Adreno**（Snapdragon 8 Gen 4）：单核心设计，但内部有多个 shader核心，频率统一调节
- **ARM Mali**（Immortalis-G925 / Mali-G720）：可配置 2–16 核心，部分配置支持核心级 power gating
- **Imagination PowerVR**：多簇设计，支持动态核心分配

GPU 的频率调节粒度通常是**整体调频**（所有核心统一频率），而非 CPU 那样的 per-core 调频。核心级的功耗管理（如 power gating、clock gating）由 GPU 微控制器内部处理，不暴露给 Android framework。

[待验证: Adreno / Mali / PowerVR 的具体核心级功耗管理策略属厂商私有]

### 3.2 OPPerf 矩阵与渲染场景的频率选择

GPU OPP（Operating Performance Point）表定义了离散的频率-电压档位。典型旗舰 GPU 有 3–7 个 OPP 点：

| OPP | 频率范围 | 典型场景 |
|-----|---------|---------|
| 最高频 | ~900MHz+ | 重度游戏 / AR / VR |
| 高频 | ~600–800MHz | 普通游戏 / 复杂 UI 动画 |
| 中频 | ~300–500MHz | 日常 UI 滑动 / 视频播放 |
| 低频 | ~100–200MHz | 后台 / 静态 UI |
| 最低频 | < 100MHz | 屏幕熄灭后的 AOD |

DVFS governor 的目标是在帧时间约束（16.6ms @ 60Hz / 8.3ms @ 120Hz）内选择**能维持帧率的最低频率**，以最小化功耗。

[适用版本: Android 14 - Android 17，具体 OPP 点因 SoC 和 GPU 型号而异]

### 3.3 65Hz 刷新率阈值：渲染节奏与 DVFS 的间接联动

SurfaceFlinger Scheduler 中一个关键的 DVFS 关联设计是 **65Hz kernel idle timer 阈值**：

```cpp
// frameworks/native/services/surfaceflinger/Scheduler/Scheduler.cpp
constexpr Fps FPS_THRESHOLD_FOR_KERNEL_TIMER = 65_Hz;

if (state == TimerState::Reset && refreshRate > FPS_THRESHOLD_FOR_KERNEL_TIMER) {
    // 高刷：主动 resync HW VSYNC，保证 GPU 提交不掉链
    resyncAllToHardwareVsync(true /* allowToEnable */);
} else if (state == TimerState::Expired && refreshRate <= FPS_THRESHOLD_FOR_KERNEL_TIMER) {
    // 低刷：切回 polling 节电
    display.schedulePtr->disableHardwareVsync(kDisallow);
}
```

这条阈值**不直接拉 GPU 频率**，但改变了帧提交时序：
- 高刷（> 65Hz）：HW VSYNC 持续 resync → GPU 需要更密集地提交帧 → 带宽需求升高 → devfreq governor 倾向保持高频
- 低刷（≤ 65Hz）：polling 模式 → 帧间隙拉长 → GPU 有更多空闲 → governor 可能降频

[已验证: AOSP android-17.0.0_r1, frameworks/native/services/surfaceflinger/Scheduler/Scheduler.cpp]

## 4. 热量控制与渲染性能平衡

### 4.1 热感知 DVFS（Thermal-Aware DVFS）

GPU 是移动设备中仅次于 SoC 整体的第二大热源。长时间高负载渲染（如大型游戏）会导致温度升高，触发**热限频**（thermal throttling）：

```
温度正常区:  GPU 全频运行 → 帧率稳定
温度预警区:  governor 收到 thermal pressure → 限制最高频率 → 帧率可能波动
温度限频区:  GPU 频率强制降至中低档 → 帧率明显下降
温度保护区:  GPU 频率降至最低 → 大幅降帧 / 暂停渲染
```

热限频的决策不在 Power HAL 中，而在 Linux 内核的 **thermal governor**（`drivers/thermal/`）和 GPU 驱动内部。Power HAL 通过 `Mode::SUSTAINED_PERFORMANCE` 和 `Mode::GAME` 给出长期功耗曲线约束的建议，但具体限频动作由内核执行。

[适用版本: Android 14 - Android 17]

### 4.2 ADPF 与热协同

应用通过 ADPF（Android Dynamic Performance Framework）可以感知热状态并主动调整渲染策略：

1. **`PerformanceHintManager.getSessionThermalHeadroom()`**：返回当前 hint session 的热余量（0–100），应用可据此决定是否降低渲染负载
2. **`WorkDuration` 上报 GPU 时长**：Android 15+ 支持 `WorkDuration.setGpuDurationNanos()`，让系统区分 CPU 和 GPU 的实际负载
3. **热限频自适应策略**（应用侧最佳实践）：
   - `thermalHeadroom < 20`：降低 MSAA 等级 / 关闭 bloom 后处理
   - `thermalHeadroom < 10`：降低渲染分辨率（动态分辨率）
   - `thermalHeadroom < 5`：降低目标帧率（如 120Hz → 60Hz）

[已验证: AOSP android-17.0.0_r1, frameworks/base/core/java/android/os/health/SystemHealthManager.java]

### 4.3 Sustained Performance Mode 与游戏渲染

`Mode::SUSTAINED_PERFORMANCE` 是 Android 为长时间持续负载设计的特殊模式：

- **启用后**：HAL 保证在较长时间窗口内提供**稳定的性能下限**，避免因温度上升导致的突然降频
- **GPU 层面**：可能将最高频率锁定在某个中高档（如 700MHz 而非 900MHz），但保证不会进一步下降
- **渲染影响**：游戏帧率曲线更平稳，P90 帧时间更可控，但峰值帧率可能降低

`Mode::GAME` 和 `Mode::GAME_LOADING` 在 Android 14 引入：
- `GAME`：平衡帧率和功耗，GPU 维持在中高频
- `GAME_LOADING`：加载阶段 CPU/GPU 可以全力运行，但加载完成后自动切回 `GAME`

[适用版本: Android 14 - Android 17]

## 5. SoC 厂商 GPU DVFS 定制化

### 5.1 厂商定制层级

| 层级 | 组件 | AOSP / 厂商 |
|------|------|-------------|
| Framework 接口 | IPower.aidl / HintManagerService | AOSP 标准化 |
| HAL 适配 | Power HAL 实现 | 厂商定制（Pixel Tensor G3 / Qualcomm SDP / MediaTek MTK） |
| GPU governor | devfreq governor / 私有调频算法 | 厂商私有 |
| GPU 驱动 | KMD（Kernel Mode Driver） | 厂商私有 |
| 硬件 | GPU 核心 + PLL + 总线 | 厂商芯片设计 |

AOSP 提供的是标准化接口层和 framework 缓存/节流机制；实际的 DVFS 算法、频率选择策略、热协同逻辑全部在厂商私有的 HAL 和驱动中。

### 5.2 厂商实现差异对渲染的影响

不同 SoC 厂商的 GPU DVFS 策略差异会直接影响渲染体验：

- **Qualcomm Adreno**：通常有更激进的升频策略（游戏场景），Adreno GPU 的 CPS（Cooperative Power Scheduler）与 Power HAL 深度集成
- **ARM Mali**：依赖 SoC 集成商（联发科/三星）配置，governor 可选 `simple_ondemand` 或厂商定制版本
- **PowerVR**：Imagination 的 ROGUE 架构有独特的 tile-based deferred rendering (TBDR)，频率与 tile 大小耦合

[待验证: 各厂商闭源 HAL 实现的具体差异，需通过厂商公开文档或 trace 分析验证]

### 5.3 Power HAL 能力探测与降级机制

PowerAdvisor 采用**「试一次就放弃」**的能力探测策略：

```cpp
// frameworks/native/services/surfaceflinger/PowerAdvisor/PowerAdvisor.cpp
if (ret.isUnsupported()) {
    mHasExpensiveRendering = false;  // 永久标记为不支持
    // 后续不再发送 EXPENSIVE_RENDERING mode
}
```

`PowerHalController` 的 `CACHE_SUPPORT(version, method)` 宏在静态变量中缓存支持状态，避免重复探测：

```cpp
#define CACHE_SUPPORT(version, method)
    static bool support = mHalConnector->getAidlVersion() >= version;
    !support ? decltype(method)::unsupported() : ({ ... });
```

**渲染影响**：如果某个 SoC 厂商的 HAL 不支持 `EXPENSIVE_RENDERING` mode，SurfaceFlinger 会立即放弃此路径，改用默认的 DVFS governor 行为。这导致 blur/特效合成场景可能得不到足够的 GPU 频率保障。

[已验证: AOSP android-17.0.0_r1, frameworks/native/services/powermanager/PowerHalController.cpp]

## 6. 渲染场景功耗优化实践

### 6.1 游戏场景：帧率-功耗平衡

游戏是 GPU 功耗的主要场景（可占整机功耗 40–60%）。优化策略：

**帧率稳定性优先于峰值帧率**：
- 目标：P90 帧时间 < 16.6ms（60Hz）/ < 8.3ms（120Hz）
- 利用 `getGpuHeadroom(MIN)` 判断是否还能维持当前帧率
- headroom < 20 时降低渲染负载（MSAA → FXAA、关闭后处理、降低阴影精度）

**ADPF hint session 最佳实践**：
```java
// 游戏主循环
PerformanceHintManager.Session session = ...;
long frameStart = System.nanoTime();
// ... 渲染工作 ...
long frameEnd = System.nanoTime();

WorkDuration wd = new WorkDuration();
wd.setWorkPeriodStartTimestampNanos(frameStart);
wd.setActualTotalDurationNanos(frameEnd - frameStart);
wd.setActualCpuDurationNanos(cpuTime);  // CPU 部分
wd.setActualGpuDurationNanos(gpuTime);  // GPU 部分（Android 15+）
session.reportActualWorkDuration(wd);
```

上报准确的 GPU 时长让 DVFS governor 做更精准的频率决策，避免 CPU 已完成但 GPU 还在忙时的误判。

[适用版本: Android 15 - Android 17]

### 6.2 Compose / 动画场景：减少不必要的 GPU 升频

日常 UI 动画（滑动、过渡）虽然每帧 GPU 工作量不大，但如果处理不当会频繁触发 DVFS 状态切换：

- **避免全屏 blur**：`RenderEffect.createBlurEffect()` 在 EFFECTS workload 中最耗 GPU。用低分辨率模糊 + 放大替代全分辨率模糊
- **减少过度绘制**：GPU 渲染被遮挡的像素是纯功耗浪费。使用 `Canvas.clipRect()` 限制绘制区域
- **硬件层（hardware layer）复用**：对复杂的静态 View 使用 hardware layer 缓存 GPU 纹理，避免每帧重新光栅化
- **Compose 中的 `derivedStateOf`**：减少不必要的 recomposition → 减少 GPU 提交次数

[适用版本: Android 14 - Android 17]

### 6.3 后台渲染任务管理

后台 GPU 任务（如视频编辑预览、壁纸引擎、小部件渲染）的功耗管理：

- **`Mode::SUSTAINED_PERFORMANCE`**：适合长时间低强度渲染（如动态壁纸）
- **SurfaceFlinger 后台合成优化**：PowerAdvisor 的 `setExpensiveRenderingExpected()` 只在前台显示涉及特效合成时触发，后台 display 不推送 `EXPENSIVE_RENDERING`
- **`setScreenshotWorkload()`**：截图请求会临时标记 workload，但 DVFS boost 持续时间很短

[适用版本: Android 14 - Android 17]

### 6.4 AI 推理任务的 GPU 功耗

GPU 上的 AI 推理（如 NN API delegate to GPU）有独特的功耗特征：

- **计算密度高**：shader 核心持续高负载，GPU 功耗快速拉满
- **带宽需求不同**：推理的内存访问模式（权重矩阵读取）与渲染不同，可能不会同等利用带宽
- **与渲染竞争**：如果推理和渲染同时发生，DVFS 需要同时满足两者的频率需求

建议：
- 将推理任务放在帧间隙执行（GPU idle window）
- 通过 `SystemHealthManager.getGpuHeadroom()` 监控余量，推理 + 渲染合计负载不超过 GPU 容量的 80%
- 大模型推理考虑使用 NPU 而非 GPU（详见 §5.20 AICore / §23.24 NN HAL）

[待验证: 具体推理 + 渲染的 GPU 调度策略属厂商私有]

  DOUBLE_VALUE AS headroom_normalized  -- 0.0 to 1.0

WHERE atom_id = GPU_HEADROOM_REPORTED  -- 需确认 atom ID

### 🔸 Mali / Adreno / PowerVR governor 对比

各厂商 GPU governor 的调频策略差异较大：

### 🔸 跨 SoC DVFS 基准测试方法论

不同 SoC 的 GPU DVFS 行为差异导致跨设备性能对比困难。推荐方法论：
- 使用 Perfetto trace 采集 GPU 频率曲线 + 帧时间分布
- 关注 **OPP 驻留时间分布**（在各频率档位停留的时间占比）
- 测量**升频延迟**（从负载增加到频率切换完成的延迟）
- 标准化 workload：GFXBench Manhattan 3.1 / Aztec Ruins

[待验证: 需要实际设备基准测试数据]

### 🔸 动态分辨率渲染与 DVFS 协同

动态分辨率渲染（Dynamic Resolution Rendering）通过降低渲染分辨率来减少 GPU 负载，与 DVFS 形成互补：
- DVFS 降频：保持分辨率，降低 GPU 执行速度 → 帧时间拉长
- 动态降分辨率：GPU 执行速度不变，减少每帧工作量 → 帧时间保持
- 两者组合：在帧时间约束下动态选择「分辨率 × 频率」的帕累托最优

Android 17 的 `getGpuHeadroom()` 让应用能实时感知 GPU 余量，做出更精准的动态分辨率决策。

[适用版本: Android 15 - Android 17]

### 9.1 AIDL V6 新增的 GPU Headroom 接口契约

`hardware/interfaces/power/aidl/android/hardware/power/GpuHeadroomParams.aidl`（copyright 2024 = Android 17 引入）：

```aidl
@VintfStability
@JavaDerive(equals=true, toString=true)
parcelable GpuHeadroomParams {
    enum CalculationType {
        MIN,        // 窗口内最小 headroom
        AVERAGE,    // 窗口内平均 headroom
    }
    CalculationType calculationType = CalculationType.MIN;
    int calculationWindowMillis = 1000;
}
```

`GpuHeadroomResult.aidl` 是 union 类型，值为 `float globalHeadroom`。**关键 NaN 语义**（直接引用 AIDL 注释）：

> NaN indicates that the result is temporarily unavailable (e.g. there is not enough util data to compute or the variance is too high to be actionable) such that the caller may not take any action until a non-NaN value is returned, while value 0 indicates no resources were left during the calculation interval and the caller may expect low resources to be granted.

**与 §2.17 §2.2 的关系**：`getGpuHeadroom()` 的缓存策略在 `HintManagerService` 中实现（`HeadroomCache<>(2, mSupportInfo.headroom.gpuMinIntervalMillis)`），但计算粒度（MIN vs AVERAGE）与窗口长度（默认 1000ms）由调用方控制——这与 CPU headroom 一致，但 GPU headroom 多了一个 `calculationType` 维度。

[已验证: AOSP android-17.0.0_r1, hardware/interfaces/power/aidl/android/hardware/power/GpuHeadroomParams.aidl / GpuHeadroomResult.aidl]

### 9.2 FrameProducer 模型：把 deadline miss 反馈给 HAL

**AIDL 文件**（`hardware/interfaces/power/aidl/android/hardware/power/FrameProducer.aidl`，copyright 2024）：

```aidl
@VintfStability
parcelable FrameProducer {
    long producerId;
    int uid;
    double fps;                              // -1 表示不确定
    @nullable LatchedFrameData currentlyLatchedFrame;
    boolean cpuDeadlineMissed;               // CPU 提交 buffer 超时
    boolean gpuDeadlineMissed;               // GPU 渲染 fence 未按时 signal
}
```

**LatchedFrameData.aidl** 包含：

```aidl
long frameStartTimestampNanos;            // 帧开始时间戳（SYSTEM_TIME_MONOTONIC）
long intendedPresentTimestampNanos;       // 目标 present 时间
long bufferSubmissionTimestampNanos;      // CPU 提交 buffer 时间
long gpuSignalTimestampNanos;            // GPU fence signal 时间，-1=未 signal
boolean usedGpu;
@nullable ParcelFileDescriptor gpuAcquireFence;  // 异步 GPU fence fd
```

**API 入口**（`IPower.aidl`）：

```aidl
oneway void sendCompositionData(in CompositionData[] data);
oneway void sendCompositionUpdate(in CompositionUpdate update);
```

**核心设计**：
1. **CPU / GPU deadline miss 独立报告**：Power HAL 可据此分别调 CPU 频率（CPU miss → 拉高 CPU）与 GPU 频率（GPU miss → 拉高 GPU）。这是 §2.17 §1.2 提到的「带宽耦合」问题的可观测化
2. **异步 GPU fence**：`LatchedFrameData.gpuAcquireFence` 是 `ParcelFileDescriptor`，HAL 拿到后 poll GPU 完成事件。注释明确：「Can be used to get accurate gpu completion timestamps, and to boost if it looks like a frame might not signal before the deadline.」
3. **Session 关联**：`FrameProducerUpdate.sessions` 列出关联的 hint session ID，让 HAL 把 producer 绑到正确线程组的 hint session 上

[已验证: AOSP android-17.0.0_r1, hardware/interfaces/power/aidl/android/hardware/power/FrameProducer.aidl / LatchedFrameData.aidl / FrameProducerUpdate.aidl / IPower.aidl]

### 9.3 PowerAdvisor 内部 GPU 分解状态机

**DisplayTimingData**（`frameworks/native/services/surfaceflinger/PowerAdvisor/PowerAdvisor.h`）保存每 display 的 GPU 时序：

```cpp
struct DisplayTimingData {
    std::unique_ptr<FenceTime> gpuEndFenceTime;
    std::optional<TimePoint> gpuStartTime;
    std::optional<TimePoint> lastValidGpuEndTime;
    std::optional<TimePoint> lastValidGpuStartTime;
    std::optional<TimePoint> hwcPresentStartTime;
    std::optional<TimePoint> hwcPresentEndTime;
    std::optional<TimePoint> hwcValidateStartTime;
    std::optional<TimePoint> hwcValidateEndTime;
    std::optional<TimePoint> hwcPresentDelayedTime;
    bool requiresRenderEngine = false;
    bool skippedValidate = false;
};

struct GpuTimeline {
    Duration duration{0ns};
    TimePoint startTime;
};
```

**setGpuStartTime 中的跨 display GPU 时间补偿**（`PowerAdvisor.cpp`）：

```cpp
for (auto&& [_, otherDisplayData] : mDisplayTimingData) {
    if (!otherDisplayData.lastValidGpuStartTime.has_value() ||
        !otherDisplayData.lastValidGpuEndTime.has_value())
        continue;
    if ((*otherDisplayData.lastValidGpuStartTime < *displayData.gpuStartTime) &&
        (*otherDisplayData.lastValidGpuEndTime > *displayData.gpuStartTime)) {
        // 其他 display 的 GPU 任务横跨本 display 的起始时间 →
        // 本 display 的实际 GPU 开始时间应推迟到其他 display 完成
        displayData.lastValidGpuStartTime = *otherDisplayData.lastValidGpuEndTime;
        break;
    }
}
```

**estimateGpuTiming** 决定单帧 GPU duration：

```cpp
std::optional<PowerAdvisor::GpuTimeline> PowerAdvisor::DisplayTimingData::estimateGpuTiming(
        std::optional<TimePoint> previousEndTime) {
    if (!(requiresRenderEngine && lastValidGpuStartTime.has_value() && gpuEndFenceTime)) {
        return std::nullopt;
    }
    const TimePoint latestGpuStartTime =
            std::max(previousEndTime.value_or(TimePoint{0ns}), *gpuStartTime);
    const nsecs_t gpuEndFenceSignal = gpuEndFenceTime->getSignalTime();
    Duration gpuDuration{0ns};
    if (gpuEndFenceSignal != Fence::SIGNAL_TIME_INVALID &&
        gpuEndFenceSignal != Fence::SIGNAL_TIME_PENDING) {
        gpuDuration = TimePoint::fromNs(gpuEndFenceSignal) - latestGpuStartTime;
    } else if (lastValidGpuEndTime.has_value()) {
        gpuDuration = *lastValidGpuEndTime - *lastValidGpuStartTime;
        if (gpuEndFenceSignal == Fence::SIGNAL_TIME_PENDING) {
            // fence 还没 signal：使用「最近有效 duration」与「当前 wallclock」的较大值
            gpuDuration = std::max(gpuDuration, Duration{TimePoint::now() - latestGpuStartTime});
        }
    }
    return GpuTimeline{.duration = gpuDuration, .startTime = latestGpuStartTime};
}
```

**estimateWorkDuration 输出**（`PowerAdvisor.cpp`）：

```cpp
hal::WorkDuration duration{
    .timeStampNanos = TimePoint::now().ns(),
    .durationNanos = combinedDuration.ns(),
    .workPeriodStartTimestampNanos = mCommitStartTimes.back().ns(),
    .cpuDurationNanos = supportsGpuReporting() ? cpuDuration.ns() : 0,
    .gpuDurationNanos = supportsGpuReporting() ? estimatedGpuDuration.ns() : 0,
};
```

**关键门控**：`supportsGpuReporting()` 实现：

```cpp
bool PowerAdvisor::supportsGpuReporting() {
    return mBootFinished && FlagManager::getInstance().adpf_gpu_sf();
}
```

GPU duration 上报受 **`FlagManager.adpf_gpu_sf()`** 门控（注意：这是 `FlagManager`，不是 system property）。`FlagManager` 定义在 `frameworks/native/services/surfaceflinger/Scheduler/FlagManager.cpp`，可在编译时或启动参数中关闭。OEM 默认启用，但可通过 vendor 定制禁用。
