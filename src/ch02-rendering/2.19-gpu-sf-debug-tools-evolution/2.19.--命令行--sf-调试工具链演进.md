# Android 17 命令行 GPU/SF 调试工具链演进

<!-- outline-start -->
## 要点

### 🔹 GPU功耗管理基础
Android 17 引入了全新的 GPU 功耗管理策略，基于 DVFS（动态电压频率调节）机制的深度优化。

### 🔹 DVFS 调优算法
新算法结合了应用负载预测和系统资源监控，实现了更智能的频率和电压调节。

### 🔹 多核心协调机制
跨 GPU 核心的功耗分配协调，根据不同应用场景动态调整核心工作状态。

### 🔹 热量控制与性能平衡
在控制 GPU 发热的同时保持最佳的性能表现，引入了热量感知的调度策略。

### 🔹 SoC 厂商定制化
支持不同 SoC 厂商的定制化 DVFS 策略，充分发挥硬件性能潜力。

## 扩展

### 🔸 游戏场景优化
针对游戏场景的特殊功耗优化策略，平衡帧率和功耗的关系。

### 🔸 AI 推理任务
AI 推理任务在 GPU 上的功耗管理，考虑模型大小和推理频率的影响。

### 🔸 后台任务处理
后台 GPU 任务的功耗管理策略，避免不必要的资源占用。

## 工具分成三类

命令行输出的时间范围和责任对象不同：

| 类型 | 代表工具 | 能回答的问题 | 主要限制 |
|---|---|---|---|
| 当前快照 | `dumpsys SurfaceFlinger`、`dumpsys gpu` | 当前 Display、Layer、buffer、composition 与 GPU service 状态 | 不能还原几百毫秒前某帧的事件顺序 |
| 应用帧统计 | `dumpsys gfxinfo <package> framestats` | View 窗口的帧时间戳与 jank 分布 | 不覆盖所有 SurfaceView/游戏/视频主体工作 |
| 时间线 | Perfetto/APA、ftrace、厂商 GPU producer | App、RenderThread、GPU、SF、HWC、频率与 fence 的先后关系 | 数据源和计数器依赖设备与驱动 |

排查顺序通常是时间线定位问题帧，再用 dump 补当前对象映射。先抓 dump、过一段时间再抓 trace，Layer id、display mode、composition type 和 buffer 状态都可能已经改变。

## SurfaceFlinger 快照

下面的命令用于 Android 17 设备采集当前 SF 状态。

```bash
adb shell dumpsys SurfaceFlinger
adb shell dumpsys SurfaceFlinger --list
adb shell dumpsys SurfaceFlinger --display-id
```

输出 section 会随版本、build type 和厂商改动变化。分析时优先确认：

- 目标 Layer 名、owner、parent、layer stack 和 display；
- active buffer、尺寸、dataspace、transform 与可见区域；
- CLIENT/DEVICE 等 composition type；
- HWC/RenderEngine 路径、display mode 与刷新率；
- buffer 数量、pending 状态和 fence 摘要。

`--list` 只列当前 Layer 名。名称可能包含动态后缀，重建 Surface 后 layer id 也会变化；脚本不应把一次采集的完整字符串永久写死。

### `--latency` 不是统一帧真值

旧脚本常使用 `dumpsys SurfaceFlinger --latency <layer>` 与 `--latency-clear`。这组接口的可用性、目标 layer 选择和时间戳含义随版本与厂商实现变化，也不能覆盖应用 CPU、GPU command、HWC 与 display driver 的全部阶段。

Android 17 的帧归因应以 FrameTimeline、buffer transaction、GPU/fence、SF/HWC 与 present 证据为主。兼容旧自动化时，先在目标 build 上验证 `--latency` 输出，再标明它测量的边界。

## `gfxinfo framestats`

下面的命令用于采集某个应用的 View 窗口帧统计。

```bash
adb shell dumpsys gfxinfo com.example.app framestats
```

结果适合生成帧时长分布、定位慢帧时间戳并与 trace 对齐。它不等于 GPU profiler：

- 一个 package 可以有多个窗口或进程；
- SurfaceView、游戏 swapchain、视频 overlay 有独立 producer 路径；
- 长帧只能说明时间超出预算，不能判定 CPU、GPU、SF 或 HWC 责任；
- 刷新率改变后，固定 16.6 ms 阈值不再适用。

## GpuService 与 GPU 计数器

设备注册 `gpu` service 时，可先通过 `service list` 确认，再采集其 dump。

```bash
adb shell service list | grep -w gpu
adb shell dumpsys gpu
```

GpuService dump 可能包含 driver、stats 或 GPU memory 相关状态，内容取决于平台与 vendor 支持。它不提供跨厂商统一的 shader、cache、bandwidth 或 utilization 定义。

Perfetto 的 `gpu.counters`、`gpu.renderstages`、`gpu_mem_total` 与 `power/gpu_frequency` 也要按设备查询：

- data source 名可能带硬件后缀；
- counter ID、名称、单位和归一化方式由 producer 描述；
- ftrace event 是否存在取决于内核与厂商驱动；
- counter 在采集工具开启后可能改变 GPU 工作量或功耗。

报告应保留 producer descriptor、trace config、GPU/driver、采样周期和工具版本。

## `sfdo` 与 `flatland`

Android 17 AOSP 包含两个面向平台工程的辅助工具：

| 工具 | 用途 | 边界 |
|---|---|---|
| `sfdo` | 控制 debug flash、强制 client composition、frame-rate indicator、schedule commit/composite 等 SF 状态 | 目标 build 未必安装；需要相应 SF 权限 |
| `flatland` / `flatland64` | 运行 EGL/GLES 合成基准 | 合成 microbenchmark，不能代表真实 App 或游戏 |

下面的命令用于做 HWC 与 RenderEngine 的对照实验，前提是设备包含 `sfdo`。

```bash
adb shell sfdo force-client-composition enabled
# 复现场景并录制一轮 trace
adb shell sfdo force-client-composition disabled
```

实验结束必须恢复 disabled。强制 CLIENT 后问题变化只能证明合成路径改变；还要检查 composition type、RenderEngine、HWC、GPU 与 fence，才能定位哪段受影响。

`flatland` 测试应记录场景、分辨率、刷新率、温度和 build。它适合系统合成回归，不适合替代应用 workload。

## `cmd gpu`、sysfs 与 `service call` 的限制

部分 userdebug/eng 或厂商系统提供 `adb shell cmd gpu ...`，用于图形 driver 选择或调试。Android 17 user build 不保证存在相同子命令，使用前应查看该设备的 `cmd gpu help`。

GPU 频率、busy、温度与 reset 节点也没有跨厂商固定路径。`/sys/class/kgsl/` 属于 Qualcomm 路径，Mali、PowerVR 和其他实现不同；脚本需要按设备能力发现节点，并保存字段文档。

不要用硬编码 `service call SurfaceFlinger <number>` 作为长期工具。Binder transaction code 会随接口、版本和构建变化，参数错误还可能修改系统状态。优先使用 `dumpsys`、`sfdo`、稳定 AIDL/CLI 或明确版本的测试程序。

## fence 语义

命令行快照常显示 buffer/fence 状态，但三类 fence 要分开：

| fence | 所属对象 | 表达的完成边界 |
|---|---|---|
| acquire/producer completion | 一块提交给消费者的 buffer | producer 写入完成，消费者可以读取 |
| release | 被消费的 layer/buffer | 旧 buffer 可以回到 producer 复用 |
| present | 一个 display present | Android 显示栈的 present 完成边界 |

present fence 后仍有 panel scanout 与像素响应。只看 fence fd 是否存在也不够，要对齐 signal 时间与对应 buffer、layer、display。

## 一套可复查的命令行流程

1. 记录 build fingerprint、API、内核、GPU/driver、刷新率和 thermal 状态。
2. 用 Perfetto/APA 复现并固定慢帧时间窗。
3. 在同一场景采集 SF、GpuService 与应用 framestats 快照。
4. 建立 package → process/window → layer → display 映射。
5. 区分 App deadline、GPU completion、SF/HWC 与 present。
6. 只改变一项渲染或合成条件，复测 trace 与功耗。
7. 脚本保存原始输出，并检查命令 exit code、权限错误和空 section。

命令返回成功不表示目标数据源存在；脚本要把“命令可执行”“section 有数据”“字段语义已验证”分别记录。
