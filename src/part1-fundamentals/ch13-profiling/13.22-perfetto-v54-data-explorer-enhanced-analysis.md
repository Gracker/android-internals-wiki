## Trace Processor 引擎架构

### 三层架构：Probes → Traced → Trace Processor

Perfetto 的设计遵循生产者-代理消费者-消费者的三层模型 [来源: Perfetto 官方文档]:

```
┌─────────────────────────────────────────────────────┐
│                   数据生产者 (Probes)                 │
│  ┌─────────┐  ┌─────────┐  ┌──────────┐            │
│  │ ftrace   │  │ atrace   │  │ heapprofd │  ...      │
│  │(内核)    │  │(用户态)  │  │(Native)   │           │
│  └────┬────┘  └────┬────┘  └─────┬────┘            │
│       │            │              │                  │
│       ▼            ▼              ▼                  │
│  ┌─────────────────────────────────────────┐        │
│  │     Shared Memory Buffer (SMB)           │        │
│  │  Page → Chunk (lock-free 写入)           │        │
│  └─────────────────┬───────────────────────┘        │
└─────────────────────┼───────────────────────────────┘
                      │ IPC (Binder)
                      ▼
┌─────────────────────────────────────────────────────┐
│              traced (代理消费者)                      │
│  ┌─────────────────────────────────────────┐        │
│  │         Central Buffer                   │        │
│  │  Buffer 0 (ftrace)  Buffer 1 (其他)      │        │
│  │  fill_policy: RING_BUFFER / STOP_WHEN_FULL│       │
│  └─────────────────┬───────────────────────┘        │
└─────────────────────┼───────────────────────────────┘
                      │ 序列化 TracePacket 流
                      ▼
┌─────────────────────────────────────────────────────┐
│           Trace Processor (分析引擎)                   │
│  ┌──────────┐  ┌──────────┐  ┌──────────────┐      │
│  │ Proto     │  │ SQL      │  │ Metrics      │      │
│  │ Decoder   │→ │ Engine   │  │ Calculator   │      │
│  └──────────┘  └──────────┘  └──────────────┘      │
│  → 虚拟表 (slice, thread, sched, ...)               │
└─────────────────────────────────────────────────────┘
```

**数据流路径**：Probe 产生数据 → 通过 Shared Memory Buffer (SMB) 传递给 `traced` → 存入 Central Buffer → 最终由 Trace Processor 解析为结构化数据。

[已验证: 官方文档, perfetto.dev/docs/]

### Shared Memory Buffer 的 Chunk 状态机

SMB 是 Perfetto 数据传输的核心机制。它不是一整块内存，而是被划分为 **Page**（进程间共享的最小单元），每个 Page 内部再切分为 **Chunk** [来源: Cubox/Perfetto数据流架构故障分析]:

每个 Chunk 有三种状态，且任意时刻只能被一个实体访问：

| 状态 | 访问者 | 说明 |
|------|--------|------|
| **Free** | Producer | 空闲，生产者申请写入 |
| **BeingWritten** | Producer | 正在写入，消费者不会拷贝 |
| **BeingRead** | Consumer | 已写满，traced 正在拷贝 |

Chunk 的写入是 **lock-free** 的——每个 chunk 对应一个生产线程，无需同步锁。这是 Perfetto 实现低开销的关键设计之一。

**Chunk 大小的 trade-off**：
- Page/Chunk 越大 → IPC 信号频率越低 → 但 BeingWritten 的 chunk 积压风险增加
- Page/Chunk 越小 → 状态切换频繁 → 需要更多同步开销
- Perfetto 默认 SMB 为 128-512 KB，单个 Page 为 4KB-32KB [来源: Cubox/Perfetto数据流架构]

[已验证: Perfetto 源码, external/perfetto/src/ipc/]

### TracePacket：跨 Chunk 的原子数据单元

TracePacket 是 Perfetto Trace 中的最小数据单元。它采用 Protobuf 序列化（通过 Perfetto 自研的 ProtoZero 库优化性能），且可以跨越多个 Chunk 存储：

```
Chunk 0     | Chunk 1           | Chunk 2     | Chunk 3
┌──────────┐┌──────────────────┐┌────────────┐┌──────────┐
│ Packet 0 ││ Packet 1 (part1) ││ Packet 1   ││ Packet 2 │
│          ││                  ││ (part2)    ││          │
└──────────┘└──────────────────┘└────────────┘└──────────┘
                    └─── Chunk header 记录前后关联 ID ────^
```

TracePacket 的 size 字段采用**延迟回填**策略：编码时先预留 size 位，payload 写完后再回填实际长度。如果跨 Chunk 的 TracePacket 还在写入时，记录 size 的 chunk 已经被消费，Perfetto 会通过 `CommitDataRequest.ChunkToPatch` IPC 信号进行事后修复 [来源: Cubox/Perfetto数据流架构]。

### 增量编码（Interned Data）

Perfetto 采用类似视频帧间编码的策略来压缩数据：

- **关键帧（I-frame equivalent）**：完整记录 string → id 映射表，存储在独立的 TracePacket 中
- **增量帧（P-frame equivalent）**：后续 TracePacket 只记录 id，不重复记录 string

**风险**：如果关键帧丢失（在 RING BUFFER 模式下更常见），所有依赖该映射的增量帧都无法解析，Trace Processor 会跳过这些数据。

`clear_period_ms` 参数控制关键帧的刷新间隔——值越小，关键帧越频繁，数据越安全但开销越大。

[已验证: Perfetto 源码, external/perfetto/src/protozero/]

## 数据流可靠性与 Trace 丢失诊断

### Perfetto 不是 100% 可靠的 tracing 平台

这不是缺陷，而是 **设计上的 trade-off**：在观测开销、内存占用和数据完整性之间，Perfetto 选择优先保证低开销。理解这一点对于正确使用 Perfetto 至关重要 [来源: Cubox/Perfetto数据流架构]。

### 四个故障点

| 故障点 | 位置 | 原因 | 后果 |
|--------|------|------|------|
| **① ftrace buffer** | 内核 | ftrace 事件产生速度 > traced_probes 读取速度 | 内核事件丢失 |
| **② SMB 不足** | Producer→traced | Free chunk 耗尽，生产者拿不到可用 chunk | 用户态 trace 事件丢失 |
| **③ Central Buffer** | traced 内部 | RING BUFFER 模式下数据被覆写 | 时间窗口前端数据丢失 |
| **④ 文件写入** | traced→文件 | I/O 阻塞导致 Central Buffer 溢出 | 整体数据丢失 |

### stats 表：数据完整性检查

Trace Processor 将所有数据丢失事件记录在 `stats` 表中。每次拿到 trace 后，第一步应该执行：

```sql
-- 检查所有数据丢失记录
SELECT name, idx, severity, source, value, description
FROM stats
WHERE severity = 'data_loss' AND value > 0;

-- 常见关键字段解读：
-- ftrace_cpu_overrun_delta: 内核 ftrace buffer 溢出（按 CPU 分索引）
-- traced_buf_trace_writer_packet_loss: SMB 写入失败
-- traced_final_flush_failed: 结束时 flush 失败
-- misplaced_end_event: begin/end 不配对
```

如果查询返回空或 value 全为 0，说明 trace 数据完整。否则应根据 `description` 字段的提示调整配置。

[已验证: 官方文档, perfetto.dev/docs/reference/sql-tables/stats]

### 降低数据丢失的配置策略

**策略一：为高吞吐数据源分配独立的大 Buffer**

```protobuf
# ftrace 是最大的数据来源，分配最大的 buffer
buffers {
  size_kb: 262144          # 256 MB for ftrace
  fill_policy: RING_BUFFER
}
# 低频数据源使用小 buffer
buffers {
  size_kb: 2048            # 2 MB for metadata
  fill_policy: RING_BUFFER
}

data_sources {
  config {
    name: "linux.ftrace"
    target_buffer: 0       # → 256MB buffer
    # ...
  }
}
data_sources {
  config {
    name: "android.packages_list"
    target_buffer: 1       # → 2MB buffer
  }
}
```

**策略二：启用流式写入和定期 flush**

```protobuf
duration_ms: 60000
write_into_file: true          # STREAM 模式
file_write_period_ms: 2500     # 每 2.5s 读出一次
flush_period_ms: 30000         # 强制 flush 未满的 chunk
flush_timeout_ms: 30000
```

**策略三：调整增量编码刷新间隔**

```protobuf
incremental_state_config {
  clear_period_ms: 5000        # 每 5s 刷新关键帧（默认更久）
}
```

> ⚠️ 以上配置基于 8 核设备、60 秒系统 trace 的经验值。低端设备可能需要调整 buffer 大小。Google 无法为所有场景提供通用参数——这正是理解 Data Flow 架构的价值所在。[来源: Cubox/Perfetto数据流架构]

## Trace 配置与采集策略

### 按场景选择配置模板

不同的性能问题需要不同的 trace 配置。以下是四种常见场景的配置策略：

#### 场景一：UI 卡顿（Jank）分析

```protobuf
data_sources {
  config {
    name: "linux.ftrace"
    ftrace_config {
      ftrace_events: "sched/sched_switch"
      ftrace_events: "sched/sched_wakeup"
      ftrace_events: "sched/sched_waking"
      ftrace_events: "power/cpu_frequency"
      atrace_categories: "gfx"
      atrace_categories: "view"
      atrace_categories: "input"
      atrace_categories: "wm"
      atrace_categories: "am"
      atrace_categories: "binder_driver"
      atrace_categories: "dalvik"
      atrace_apps: "*"
    }
  }
}
data_sources {
  config { name: "android.surfaceflinger.frametimeline" }
}
buffers { size_kb: 131072  fill_policy: RING_BUFFER }
duration_ms: 10000
```

**关键点**：必须开启 `android.surfaceflinger.frametimeline` 数据源以获取 FrameTimeline 信息（含 expected/dropped 帧）。`gfx` 类别覆盖 RenderThread、HWUI 等图形管线事件。

#### 场景二：应用启动分析

```protobuf
data_sources {
  config {
    name: "linux.ftrace"
    ftrace_config {
      ftrace_events: "sched/sched_switch"
      ftrace_events: "sched/sched_wakeup"
      ftrace_events: "sched/sched_process_exit"
      ftrace_events: "task/task_newtask"
      ftrace_events: "task/task_rename"
      atrace_categories: "am"
      atrace_categories: "view"
      atrace_categories: "pm"
      atrace_categories: "binder_driver"
      atrace_categories: "dalvik"
      atrace_categories: "ss"
      atrace_apps: "<your.package.name>"
    }
  }
}
data_sources { config { name: "linux.process_stats" } }
data_sources { config { name: "linux.sys_stats" } }
buffers { size_kb: 131072  fill_policy: STOP_ON_FULL }
duration_ms: 30000
```

**关键点**：`STOP_ON_FULL` 确保启动过程不被截断。指定具体 `atrace_apps` 而非 `*` 可以减少无关进程的 trace 数据量。`pm`（package manager）类别记录安装/解析过程。

#### 场景三：功耗/后台耗电分析

```protobuf
data_sources {
  config {
    name: "linux.ftrace"
    ftrace_config {
      ftrace_events: "power/suspend_resume"
      ftrace_events: "power/cpu_frequency"
      ftrace_events: "power/cpu_idle"
      ftrace_events: "sched/sched_switch"
      atrace_categories: "power"
      atrace_categories: "wm"
      atrace_categories: "am"
    }
  }
}
data_sources { config { name: "linux.sys_stats" } }
buffers { size_kb: 65536  fill_policy: RING_BUFFER }
duration_ms: 300000       # 5 分钟长 trace
write_into_file: true
```

**关键点**：功耗分析通常需要长时间 trace（分钟级），必须使用 `write_into_file: true`（STREAM 模式）。`power` 类别记录 wakelock、电源状态变更。

#### 场景四：内存问题分析

```protobuf
data_sources {
  config {
    name: "linux.ftrace"
    ftrace_config {
      ftrace_events: "sched/sched_switch"
      atrace_categories: "am"
      atrace_categories: "dalvik"
      atrace_categories: "view"
    }
  }
}
data_sources { config { name: "linux.process_stats" 
  process_stats_config { scan_all_processes_on_start: true }
} }
buffers { size_kb: 131072  fill_policy: RING_BUFFER }
duration_ms: 60000
```

**关键点**：`linux.process_stats` 定期扫描进程的 RSS/PSS。如需更详细的 Native 堆分析，配合 `heapprofd` 数据源。

### 采集方式选择

| 方式 | 适用场景 | 优势 | 局限 |
|------|----------|------|------|
| **设备端系统跟踪 App** | 快速现场诊断 | UI 友好、无需电脑 | 配置选项有限 |
| **Perfetto Web UI 录制** | 连接 ADB 的开发环境 | 配置详细、实时预览 | 需要 USB 连接 |
| **adb shell perfetto** | 自动化测试 | 最灵活、支持复杂配置 | 需要手写配置文件 |
| **record_android_trace** | CI/CD 集成 | 脚本化、可复现 | 需要 Perfetto Python SDK |

[结构参考: Cubox/系统级性能分析与调优]

## 系统级性能诊断工作流

### UI Jank 诊断十步法

这是基于 Perfetto trace 分析 UI 卡顿的系统性方法 [结构参考: Cubox/系统级性能分析与调优]:

1. **抓取 trace**：开启 `sched`、`gfx`、`view`、`wm`、`am`、`binder_driver`、`freq`、`dalvik` 类别
2. **定位掉帧**：在 FrameTimeline 轨道中找到红色（dropped）或黄色（long）的帧
3. **选中问题帧的 doFrame**：在 UI 线程轨道上找到对应的 `Choreographer#doFrame` slice
4. **分析内部耗时**：
   - `measure` / `layout` 是否过长？→ 布局层级问题
   - `draw` / `Record` 是否过长？→ 绘制复杂度问题
   - `sync` 是否过长？→ Surface 同步问题
5. **检查线程状态**：在 doFrame 执行期间，UI 线程是什么状态？
   - **Running**（代码本身慢）→ 需要 CPU profile 定位热点方法
   - **Runnable**（CPU 被抢占）→ 查看哪个线程/进程占用了 CPU
   - **Sleeping**（等待资源）→ 查看等待什么：锁、Binder、I/O
6. **如果是 Runnable**：查看 CPU 轨道，确认抢占者是谁
7. **如果是 Sleeping**：查看 flow event 箭头，追踪等待依赖（锁持有者、Binder 对端）
8. **检查 RenderThread**：`DrawFrame` 是否也超时？（GPU 负载？同步等待？）
9. **检查 SurfaceFlinger**：是否按时收到 buffer 并合成？
10. **排查并发 GC**：dalvik 轨道是否有 GC 暂停与 doFrame 时间重叠？

### 应用启动性能分析方法

启动分析的关键是建立**时间基线**——从进程创建到首帧显示的分段耗时 [结构参考: Cubox/系统级性能分析与调优]:

```
进程创建 ──► bindApplication ──► Application.onCreate ──► 
Activity.onCreate ──► onResume ──► 首个 doFrame ──► 
首帧 DrawFrame ──► SurfaceFlinger 合成 ──► 显示
```

在 Perfetto 中的定位方法：

```sql
-- 查找应用进程的启动关键事件
SELECT
  ts,
  dur,
  name,
  thread.name AS thread_name
FROM slice
JOIN thread_track ON slice.track_id = thread_track.id
JOIN thread USING (utid)
JOIN process USING (upid)
WHERE process.name LIKE '%your.app.package%'
  AND name IN (
    'ActivityManager:bindApplication',
    'ActivityThreadMain',
    'activityStart',
    'Choreographer#doFrame'
  )
ORDER BY ts
LIMIT 20;
```

重点检查：
- **Application.onCreate**：同步 I/O？复杂初始化？锁等待？
- **Activity.onCreate/onResume**：布局加载？数据初始化？
- **CPU 状态**：启动初期系统繁忙，CPU 争抢导致大量 Runnable
- **磁盘 I/O**：`diskio` 轨道是否有大量读写阻塞？
- **Binder 调用**：是否依赖响应慢的系统服务？
- **GC 活动**：启动过程中是否频繁 GC？

### 功耗诊断方法

功耗分析的核心是找到 **"阻止 CPU 进入深度休眠的线程"** [结构参考: Cubox/系统级性能分析与调优]:

1. **Wakelock 分析**：在 wakelock 轨道检查长时间持有的 `PARTIAL_WAKE_LOCK`
2. **CPU Idle 分析**：查看 CPU 能否进入深度 idle 状态（`cpuidle`）
3. **CPU 频率分析**：CPU 是否长期运行在 高频（`cpufreq`）
4. **后台活动排查**：网络轮询（`net`）、磁盘读写（`diskio`）、后台同步（`sync`）
5. **关联电池数据**：将 batt 轨道的耗电峰值与上述活动关联

### 自定义 Trace 埋点最佳实践

在应用代码中添加自定义 trace 点是定位业务逻辑耗时的关键手段：

```kotlin
import android.os.Trace

// 同步埋点：包裹代码块（推荐在 finally 中 endSection）
Trace.beginSection("DataParsing")
try {
    parseData(rawData)  // 业务逻辑
} finally {
    Trace.endSection()   // 必须配对调用
}

// 异步埋点：跨线程/回调操作
val cookie = "ImageLoad:${System.nanoTime()}"
Trace.beginAsyncSection("LoadImage", cookie.hashCode())
scope.launch {
    val bitmap = loadImage(url)
    Trace.endAsyncSection("LoadImage", cookie.hashCode())
}
```

**实践建议**：
- Section 名称要有描述性、唯一性
- 在关键业务路径、核心算法、UI 准备阶段策略性添加
- 避免过度添加（干扰分析且增加开销）
- 使用 `finally` 确保配对，否则会触发 `misplaced_end_event`

[已验证: 官方文档, developer.android.com/reference/android/os/Trace]

## Trace Processor SQL 查询进阶

### 核心虚拟表速查

| 表名 | 内容 | 常用场景 |
|------|------|----------|
| `slice` | 所有 atrace/ftrace 切片事件 | 查找耗时操作 |
| `thread_state` | 线程状态（Running/Sleeping/Runnable） | 分析 CPU 占用 |
| `sched_slice` | CPU 调度切片 | 分析调度延迟 |
| `thread` / `process` | 线程/进程信息 | 关联查询 |
| `counter` | 计数器值（CPU 频率、内存等） | 趋势分析 |
| `frame_timeline` | 帧时间线（expected/dropped） | Jank 分析 |
| `binder_calls` | Binder 事务 | IPC 延迟分析 |
| `stats` | Trace 完整性统计 | 数据丢失检查 |

### 常用查询模板

**查找 UI 线程最耗时的 slice（Top 20）**：

```sql
SELECT
  s.name,
  s.dur / 1e6 AS dur_ms,
  t.name AS thread
FROM slice s
JOIN thread_track tt ON s.track_id = tt.id
JOIN thread t USING (utid)
WHERE t.is_main_thread = 1
  AND s.dur > 1e6       -- > 1ms
ORDER BY s.dur DESC
LIMIT 20;
```

**统计线程状态分布**：

```sql
SELECT
  t.name AS thread,
  ts.state,
  SUM(ts.dur) / 1e9 AS total_s,
  SUM(ts.dur) * 100.0 / (SELECT SUM(dur) FROM thread_state WHERE utid = ts.utid) AS pct
FROM thread_state ts
JOIN thread t USING (utid)
WHERE t.name = 'main'
GROUP BY ts.state, t.name
ORDER BY total_s DESC;
```

**查找 Binder 调用延迟 Top 10**：

```sql
SELECT
  server_thread.name AS server_thread,
  client_thread.name AS client_thread,
  b.server_tid,
  b.dur / 1e6 AS dur_ms
FROM binder_calls b
JOIN thread server_thread ON b.server_tid = server_thread.tid
JOIN thread client_thread ON b.client_tid = client_thread.tid
ORDER BY b.dur DESC
LIMIT 10;
```

### Trace Processor 命令行工具

除了 Perfetto UI，Trace Processor 也可以作为独立命令行工具使用：

```bash
# 启动交互式 SQL Shell
./trace_processor_shell trace.perfetto-trace

# 直接执行 SQL 查询
./trace_processor_shell --run-metrics android_startup \
  trace.perfetto-trace > startup_metrics.json

# 导出为 JSON
./trace_processor_shell --json trace.perfetto-trace \
  -q "SELECT name, dur FROM slice WHERE dur > 10000000 LIMIT 10"
```

这使其可以集成到 CI/CD 管线中进行自动化性能回归测试。

[已验证: 官方文档, perfetto.dev/docs/quickstart/trace-analysis]

## Perfetto 自身开销分析

性能分析工具本身也有性能开销——"观察者效应"无法完全消除。实测数据如下（前台随机启动应用 60 秒）[来源: Cubox/Perfetto数据流架构]:

| 进程 | PID | CPU 时间 (ms) | CPU 占比 |
|------|-----|---------------|----------|
| traced_probes | 2376 | 11013 | 2.29% |
| logd | 1034 | 6802 | 1.42% |
| logcat | 3756 | 4546 | 0.95% |
| traced | 2386 | 2064 | 0.43% |
| statsd | 1066 | 1125 | 0.23% |

**关键观察**：
- `traced_probes`（读取 ftrace buffer 的进程）是开销最大的组件，约 2.3%
- `traced`（Central Buffer 管理者）开销较低，约 0.4%
- 开销与 trace 配置的数据源数量和采样频率正相关
- 合理的配置可以将总开销控制在 **3-5%** 以内

**降低开销的策略**：
1. 精简 atrace_categories——只开启分析目标相关的类别
2. 使用 `atrace_apps: "<具体包名>"` 代替 `*`——减少无关应用的事件
3. 避免长时 trace + 大 buffer + 高频事件的组合
4. 对 ftrace 事件，可以通过 `ftrace_config.buffer_size_kb` 控制 per-CPU buffer 大小

## v54 新特性在诊断工作流中的应用

### Data Explorer 与传统 SQL 查询的关系

Data Explorer（详见 13.21）降低了 SQL 的使用门槛，但它并不能完全替代手写 SQL 查询。两者的定位不同 [已验证: 官方文档]:

| 维度 | Data Explorer | 手写 SQL |
|------|--------------|----------|
| **适用场景** | 探索性分析、快速验证假设 | 复杂聚合、自动化指标计算 |
| **灵活性** | 中等（受限于节点类型） | 高（任意 SQL） |
| **复用性** | 可保存管线配置 | 可保存 SQL 脚本 |
| **学习曲线** | 低（拖拽式） | 中高（需了解表结构） |
| **CI/CD 集成** | 不支持 | 支持（trace_processor_shell） |

### Collapsed Stack 与火焰图

v54 新增的 Collapsed Stack 格式支持，使得 Perfetto trace 可以直接导出为 Brendan Gregg FlameGraph 兼容格式：

```bash
# 通过 trace_processor_shell 导出 Collapsed Stack
./trace_processor_shell trace.perfetto-trace \
  --run-metrics cpu_flamegraph \
  --metrics-output=json > collapsed.txt

# 使用 FlameGraph 工具生成火焰图
./flamegraph.pl collapsed.txt > flamegraph.svg
```

这一功能对于 CPU profile 分析特别有用——可以快速识别 CPU 热点函数的调用栈深度和频率分布。

### Firefox Profiler 格式互操作

v54 支持将 trace 导出为 Firefox Profiler 的 preprocessed JSON 格式，使得开发者可以利用 Firefox Profiler 的火焰图、调用树、标记时间轴等功能来分析 Perfetto trace 数据。这为习惯了 Firefox Profiler 工作流的开发者提供了平滑过渡。

详见 13.21 中 "Trace Processor 增强功能" 小节的完整论述。

## 扩展

### 🔸 跨版本兼容性

Perfetto trace 文件格式具有良好的向后兼容性。v54 的 Trace Processor 可以解析旧版本（v30+）生成的 trace 文件。但反向不成立——旧版 Trace Processor 可能无法解析 v54 新增的数据源格式。

对于 Android 17 设备：
- 默认内置的 Perfetto 版本通常与系统版本匹配
- 可以通过 `adb shell perfetto --version` 确认
- 如需使用最新版 Trace Processor 分析功能，建议从 [perfetto.dev](https://perfetto.dev) 下载独立的 trace_processor_shell

### 🔸 自动化性能测试集成

Trace Processor 的命令行工具使其天然适合集成到自动化测试管线中：

```bash
#!/bin/bash
# CI/CD 性能回归检测脚本示例

TRACE_FILE="startup_trace.perfetto-trace"

# 1. 抓取 trace
adb shell perfetto -c trace_config.txt -o /data/local/tmp/$TRACE_FILE
adb pull /data/local/tmp/$TRACE_FILE

# 2. 检查数据完整性
./trace_processor_shell $TRACE_FILE -q "SELECT COUNT(*) FROM stats WHERE severity='data_loss' AND value > 0" \
  --json | jq '.[].count'

# 3. 计算启动指标
./trace_processor_shell $TRACE_FILE \
  --run-metrics android_startup \
  --metrics-output=json > startup_metrics.json

# 4. 对比基线（伪代码）
# python3 compare_with_baseline.py startup_metrics.json baseline.json --threshold 5%
```

这种模式可以在每次代码提交时自动检测性能回归，而不依赖人工分析 trace。

### 🔸 性能基准测试方法论

建立有意义的性能基准需要注意：

1. **环境一致性**：同一设备、相同温控状态、相同后台负载
2. **统计显著性**：至少 10 次采样，取 P50/P90 而非平均值
3. **控制变量**：每次只改变一个因素
4. **Warm-up**：前 2-3 次运行作为热身（JIT 编译、文件系统缓存），不纳入统计
5. **版本基线**：每个里程碑版本建立性能基线，后续版本对比

## 总结

Perfetto v54 提供了从数据采集到分析输出的完整工具链。要高效使用这一工具链，关键在于：

1. **理解数据流架构**——知道数据从哪来、怎么传输、可能在哪丢失
2. **按场景配置**——不同问题需要不同的数据源组合和 buffer 策略
3. **系统化分析**——遵循"定位 → 分解 → 归因"的工作流，而非漫无目的地浏览 trace
4. **自动化集成**——将 trace 采集和指标计算集成到 CI/CD 中，实现持续性能监控

Data Explorer（13.20/13.21）降低了使用门槛，而理解 Trace Processor 内部机制（本节）则决定了你能在多深的层次上使用 Perfetto。
