## 1. 本章解决什么问题

Data Explorer 把 PerfettoSQL 查询组织成一张可编辑的节点图。它适合在已经加载的 trace 上快速验证假设：选表、裁剪时间、关联字段、过滤、聚合，再把结果画成柱状图或直方图。它不会替代数据采集，也不会凭空补出 trace 中没有的 FrameTimeline、调度、heap graph 或 ANR 事件。

本章侧重操作路径和结果校验。[13.20 Perfetto v54 Data Explorer 与 Jank CUJ](./13.20-Perfetto-v54-Data-Explorer-与-Jank-CUJ.md) 侧重 v54 源码语义、CUJ marker 边界和指标实现。两章配合阅读时，可以把工作分成三层：

1. timeline 用来观察事件的时间关系；
2. Data Explorer 用来交互式筛选和聚合；
3. PerfettoSQL 文件或 metric 用来保存可重复执行的分析。

### 1.1 平台版本与主机工具要分开

“Android 17 支持 Perfetto v54”容易被误解为一项 Android SDK API。更准确的描述是：

- Android 17 设备负责记录 trace 数据，数据是否齐全由设备构建、trace config、权限和运行场景共同决定；
- Trace Processor 负责把 trace 转成表和 PerfettoSQL 标准库对象；
- Perfetto UI 的 Data Explorer 运行在主机浏览器中，节点种类和交互由 UI 版本决定；
- 同一个 Android 17 trace 可以交给不同版本的主机工具解析，但生产分析应固定工具版本，并记录查询文本。

本文不把 v54 的 UI 功能归为 API 37 行为，也不把较新的网页界面反推到 v54。

## 2. 先认识 v54 的节点图

v54 的 Explore Page 注册了四类源节点：

| 源节点 | 用途 | 注意点 |
| --- | --- | --- |
| Slices | 浏览 trace 中的 slice | 适合按名称和轨道探索，不等同于任意 SQL 表 |
| Table | 从已知 Trace Processor 表开始 | 能保留列类型和 `JOINID` 元数据 |
| Query | 手写一条 PerfettoSQL 查询 | 需要手动执行，适合引入标准库模块 |
| Time Range | 使用 timeline 当前选择区间 | 可保存静态区间，也可跟随选择变化 |

后续节点包括 Filter、Aggregation、Sort、Modify Columns、Add Columns、Limit and Offset、Counter to Intervals，以及 Join、Union、Filter During、Interval Intersect、Create Slices 等多输入操作。v54 的 Visualisation 注册表只有两种图：`bar` 和 `histogram`。折线图、散点图或其他后来出现的图表不能写成 v54 已有能力。

一条常见的交互分析路径可以简写为：

```text
Table / Query
  → Time Range + Filter During
  → Add Columns / Join
  → Filter
  → Aggregation
  → Sort
  → Visualisation
```

这条路径的含义是先缩小时间和行数，再关联维度，随后聚合与展示。执行结果异常时，按箭头反向查看每个节点的行数和生成 SQL，通常能较快找到误过滤或重复关联的位置。

### 2.1 Query 节点不是任意 SQL 控制台

v54 的 Query 源节点接受零条或多条 `INCLUDE PERFETTO MODULE`，随后必须只有一条以 `SELECT` 或 `WITH` 开头的查询。`CREATE`、`INSERT` 和多条独立 `SELECT` 会被校验器拒绝。连接其他节点后，可以在查询中引用 `$input_0`、`$input_1` 等输入。

下面的结构符合 Query 节点约束：

```sql
INCLUDE PERFETTO MODULE time.conversion;

WITH positive_slices AS (
  SELECT ts, dur, name
  FROM $input_0
  WHERE dur > 0
)
SELECT
  ts,
  time_to_ms(dur) AS dur_ms,
  name
FROM positive_slices;
```

这里仅有一条末尾查询，前面只有模块引入。Query 节点默认需要手动执行；修改 SQL 后应重新执行，再观察下游节点是否取得了新的列集合。

### 2.2 Table 源与 Query 源的取舍

Table 源读取 Trace Processor 的表定义，像 `utid JOINID(thread.id)` 这样的关系可帮助 Data Explorer 提供关联字段。自定义 Query 的返回列通常只保留查询结果类型，下游若要依赖时间列、时长列或 ID 语义，应检查列类型是否符合节点要求。

经验上：

- 已知表和简单筛选从 Table 源开始；
- 需要 `INCLUDE PERFETTO MODULE`、复杂 CTE 或精确控制关联条件时，从 Query 源开始；
- 图形探索完成后，把关键 SQL 放入独立文件并用固定版本的 Trace Processor 回归。

## 3. Perfetto 表的四条基本规则

### 3.1 时间单位默认是纳秒

`ts`、`dur` 以及多数时间差使用纳秒。不要把 `dur` 直接标成毫秒。展示时可引入 `time.conversion`，使用 `time_to_ms()`；参与区间关联时保留原始整数，避免过早转换造成精度损失。

### 3.2 `upid`、`utid` 才是 trace 内的唯一身份

操作系统的 PID/TID 可能在一次长 trace 中被复用。Trace Processor 用 `upid` 和 `utid` 表示 trace 内唯一进程、线程实例。按进程或线程关联时优先：

- `sched_slice.utid → thread.utid`
- `thread.upid → process.upid`
- `actual_frame_timeline_slice.upid → process.upid`

PID/TID 适合展示和与外部日志对照，不适合作为长时间窗口中的唯一连接键。

### 3.3 `dur = -1` 和 `NULL` 需要单独处理

某些未结束事件用负时长表示，某些标准库字段在数据缺失时返回 `NULL`。求和、分桶和区间关联前要明确排除或标注这类行。把 `NULL` 直接补成 0 会混淆“测得为零”和“没有采到”。

### 3.4 关联后先检查行数

帧、slice、track 和进程之间并非处处一对一。一次关联后行数突然放大，常见原因是：

- 同一帧在多个 layer 或 track 上有记录；
- 仅按名称关联，没有同时限制 `upid`、token 或时间；
- 区间条件允许一行匹配多个重叠事件；
- 使用 PID/TID 命中了复用后的另一个实例。

在计算总量前，先查看键的重复数，必要时按业务含义去重。

## 4. 实战一：分析线程 CPU 运行时间

目标是回答：“选定时间窗口内，目标进程的哪些线程获得了最多 CPU 运行时间？”

### 4.1 用节点搭出分析图

在 timeline 中选中待分析区间，然后按下面顺序创建节点：

1. 创建 `Table(sched_slice)`；
2. 创建 `Time Range`；
3. 用 `Filter During` 连接调度表与时间范围；
4. 从 `utid` 添加 `thread` 表的 `tid`、`name`、`upid`；
5. 从 `upid` 添加 `process` 表的 `pid`、`name`；
6. 过滤目标进程，并排除 `dur <= 0`；
7. 按线程名与 `utid` 聚合 `SUM(dur)`；
8. 按总时长降序排列；
9. 用柱状图展示前若干项。

这里选择 `sched_slice`，因为它记录线程在 CPU 上运行的区间；不存在一个可直接按 `cpu.duration` 求和的通用 `cpu` 表。`cpu` 是 `sched_slice` 的列，表示该运行区间所在的逻辑 CPU。

### 4.2 用 SQL 校验节点结果

下面的查询保留原始调度行，适合对照 Data Explorer 每一步的关联结果：

```sql
INCLUDE PERFETTO MODULE time.conversion;

SELECT
  s.ts,
  s.dur,
  s.cpu,
  s.utid,
  t.tid,
  t.name AS thread_name,
  p.upid,
  p.pid,
  p.name AS process_name,
  time_to_ms(s.dur) AS runtime_ms
FROM sched_slice AS s
JOIN thread AS t
  USING (utid)
LEFT JOIN process AS p
  ON p.upid = t.upid
WHERE
  s.dur > 0
  AND p.name = 'com.example.app';
```

查询结果一行仍对应一个调度区间。若节点聚合值和 SQL 不一致，应检查 Data Explorer 的时间范围是否与 SQL 查询范围一致，以及 Add Columns 是否引入了重复行。

若要在 SQL 中复现聚合，可按 `utid` 分组。不要只按线程名分组，因为多个线程可能同名。

```sql
INCLUDE PERFETTO MODULE time.conversion;

SELECT
  s.utid,
  t.tid,
  t.name AS thread_name,
  time_to_ms(sum(s.dur)) AS runtime_ms
FROM sched_slice AS s
JOIN thread AS t
  USING (utid)
JOIN process AS p
  ON p.upid = t.upid
WHERE
  s.dur > 0
  AND p.name = 'com.example.app'
GROUP BY
  s.utid,
  t.tid,
  t.name
ORDER BY
  runtime_ms DESC
LIMIT 30;
```

这份结果表示“获得 CPU 的累计运行时间”，不能直接解释为 wall time、CPU 利用率或卡顿根因。要计算利用率，还需要明确时间窗口长度和 CPU 数；要判断卡顿，还要回到对应帧区间检查 runnable 等待、锁、I/O、频率和渲染阶段。

## 5. 实战二：从 CUJ 找到问题帧

### 5.1 CUJ 数据从哪里来

`android.cujs.base` 识别名称形如 `J<...>` 的 CUJ slice，并结合 `FT#begin`、`FT#end`、`FT#cancel`、layer ID、UI thread 等 marker 计算 `android_jank_cuj`。其 `ts`、`ts_end` 和 `dur` 以首尾帧边界为准，不一定等于原始 CUJ slice 的区间。

`state` 的有效文本是：

- `completed`：观察到结束 marker；
- `canceled`：基础模块在输出前会过滤这类 CUJ；
- `NULL`：旧 trace 缺少状态 marker，模块会保留持续时间大于 4 ms 的记录。

这些 CUJ marker 主要来自 Android 平台的特定进程和插桩场景，普通三方应用的 trace 不保证进入 `android_jank_cuj`。v54 `android.cujs.base` 的 `_is_jank_slice` 只接受名称匹配 `J<*>` 且进程名匹配 `com.android.*` 或 `com.google.android*` 的 CUJ slice；第三方 App 即使写出同名 atrace marker，也需要自定义 SQL 扩展或直接分析 FrameTimeline。查询为空时，应检查 trace 是否录到了应用 atrace、FrameTimeline、目标 CUJ marker，以及目标进程是否被标准库过滤。

### 5.2 在 Query 节点取出 CUJ 与帧

下面的查询把已完成 CUJ 与同进程、时间上重叠的 app FrameTimeline 行关联起来：

```sql
INCLUDE PERFETTO MODULE android.cujs.base;
INCLUDE PERFETTO MODULE android.frames.jank_type;

SELECT
  c.cuj_id,
  c.cuj_name,
  c.process_name,
  c.state,
  f.name AS frame_id,
  f.track_id,
  f.ts,
  f.dur,
  f.jank_type,
  f.jank_severity_type,
  f.jank_score,
  android_is_app_jank_type(f.jank_type) AS app_missed,
  android_is_sf_jank_type(f.jank_type) AS sf_missed
FROM android_jank_cuj AS c
JOIN actual_frame_timeline_slice AS f
  ON f.upid = c.upid
  AND f.ts < c.ts_end
  AND c.ts < f.ts + f.dur
WHERE
  c.state = 'completed';
```

区间判断使用半开区间重叠条件，避免仅凭 frame 名称关联。`actual_frame_timeline_slice.name` 是帧 token 的文本表示；同一帧在不同 layer 或 track 上仍可能出现多行，所以聚合前要检查 `frame_id`、`track_id` 和 layer 关系。

在 Data Explorer 中，可在该 Query 后连接：

1. Filter：只保留 `app_missed = 1`、`sf_missed = 1` 或指定 `jank_type`；
2. Aggregation：按 `cuj_name` 统计帧数、missed frame 数或 `SUM(jank_score)`；
3. Sort：按 missed 数或分数降序；
4. Visualisation：柱状图比较不同 CUJ，直方图查看单帧 `dur` 或 `jank_score` 分布。

`jank_score` 在 v54 表定义中仍标为 experimental。它可用于同一工具版本、同一采集口径下的排序，不宜脱离版本作为长期稳定协议。

### 5.3 counter-based weighted jank 的边界

v54 还增加了 `android.cujs.cuj_frame_counters`。它从名称形如 `J<CUJ>#counterName` 的进程 counter track 中提取值，并且仍会通过 `android_jank_cuj` 限定同一 `upid` 与 CUJ 名；也就是说，默认标准库没有接纳的第三方进程 counter 不会自动进入这条管线。Android jank metric 会读取 `weightedAppJank` 和 `weightedSfJank`，先按 1000 缩放为加权 jank 速率，再结合 CUJ 动画时长换算为该次 CUJ 的加权 missed frame 总量。

这里有两个容易混淆的量：

- `actual_frame_timeline_slice.jank_score` 来自每帧参数 `Jank Severity Score (experimental)`；
- CUJ counter 的 weighted jank 来自被测端写入的 CUJ counter，默认还要求该 CUJ 已进入 `android_jank_cuj`。

两者的来源和缺失条件不同。没有对应 counter 时，不能用任意帧时长公式伪造 weighted jank；需要帧级解释时，应保留 `jank_type`、`jank_score` 与 FrameTimeline 证据。

## 6. 实战三：heap graph 与 DMA-BUF 只做相关性分析

v54 模块 `android.memory.heap_graph.heap_graph_stats` 公开表 `android_heap_graph_stats`。每一行对应一次 ART heap graph 快照，包含：

- Java heap 总大小、可达大小和对象数；
- `NativeAllocationRegistry` 登记的 native allocation 大小；
- 快照时刻的进程 uptime 与 `oom_score_adj`；
- 快照附近的 anon RSS + swap；
- 快照附近的进程 DMA-BUF RSS。

下面的查询把进程名和主要统计量放在一行，便于在 Data Explorer 中继续筛选：

```sql
INCLUDE PERFETTO MODULE android.memory.heap_graph.heap_graph_stats;
INCLUDE PERFETTO MODULE time.conversion;

SELECT
  h.upid,
  p.pid,
  p.name AS process_name,
  h.graph_sample_ts,
  time_to_ms(h.process_uptime) AS process_uptime_ms,
  h.total_heap_size,
  h.reachable_heap_size,
  h.total_native_alloc_registry_size,
  h.reachable_native_alloc_registry_size,
  h.total_obj_count,
  h.reachable_obj_count,
  h.oom_score_adj,
  h.anon_rss_and_swap_size,
  h.dmabuf_rss_size
FROM android_heap_graph_stats AS h
JOIN process AS p
  USING (upid)
ORDER BY
  h.graph_sample_ts;
```

如果结果为空，说明 trace 中没有可汇总的 `heap_graph_object` 数据，或相应数据源未成功采集。Data Explorer 不会主动触发 heap dump。

### 6.1 为什么 `dmabuf_rss_size` 不是泄漏结论

模块内部通过 `_closest_value` 关联内存区间：优先取覆盖 heap graph 时间点的值；若没有覆盖项，可以取快照之后 500 ms 内最近的值。找不到匹配项时结果为 `NULL`。所以 `dmabuf_rss_size` 是时间相关的进程视角样本，不是某个 Java 对象“拥有”DMA-BUF 的证明。

Camera、视频、图形合成场景常同时推动 Java 对象、native allocation 和 DMA-BUF 变化。合适的判断步骤是：

1. 比较多次快照的增长方向；
2. 在同一时间窗查看 camera、binder、BufferQueue/SurfaceFlinger 与内存事件；
3. 检查资源释放后数值是否回落；
4. 需要归因到 buffer 或分配方时，补充 DMA-BUF、图形和进程内诊断证据。

单个时间点的同步上涨只能说明相关，不能独立证明泄漏或所有权。

## 7. 实战四：用增强后的 `android_anrs`

v54 给 `android_anrs` 增加 `intent` 和 `component`。表中还包括 `process_name`、`pid`、`upid`、`error_id`、`ts`、`subject`、`timer_delay`、`anr_type`、`anr_dur_ms` 和 `default_anr_dur_ms`。

下面的查询适合用作 Data Explorer 的 ANR 源：

```sql
INCLUDE PERFETTO MODULE android.anrs;
INCLUDE PERFETTO MODULE time.conversion;

SELECT
  ts,
  process_name,
  pid,
  upid,
  error_id,
  anr_type,
  subject,
  intent,
  component,
  time_to_ms(timer_delay) AS timer_delay_ms,
  anr_dur_ms,
  default_anr_dur_ms
FROM android_anrs
ORDER BY
  ts;
```

`intent` 和 `component` 由 ANR 类型与 subject 文本解析，某些 ANR 没有这些概念，字段会是 `NULL`。`default_anr_dur_ms` 表示 AOSP/Pixel 默认值，源码明确提示 OEM 可能修改超时，因此不能拿它覆盖设备侧证据。

建议从三个方向使用 Data Explorer：

- 按 `anr_type`、`component` 聚合，观察问题是否集中在某类入口；
- 以 `ts` 为中心建立时间范围，回到 timeline 查看主线程状态、binder 等待、锁和 CPU 调度；
- 用 `error_id` 与 bugreport、dropbox 或其他日志核对同一事件。

`timer_delay_ms` 表示计时器到期事件与 ANR counter 事件之间的延迟。它不是应用主线程阻塞时长，也不能代替 ANR trace 的线程栈。

## 8. v54 的 DataGrid 与时间选择

### 8.1 Pivot table 应放在聚合语义之后

v54 的 DataGrid 支持可配置 pivot。透视只是重新组织查询结果，分组维度和聚合函数仍要有清楚的含义。例如分析 ANR 时可用 `anr_type` 作为行、`component` 作为列、`COUNT(*)` 作为值；分析 CUJ 时可用 `cuj_name` 与 `jank_type` 分组。

若原始数据在 Join 后发生一对多放大，pivot 只会把错误汇总得更整齐。创建 pivot 前应核对原始行数和去重键。

### 8.2 GLOB、contains 与正则表达式不同

v54 DataGrid 增加 glob、contains、not-contains 和 distinct value picker。PerfettoSQL 的 `GLOB` 使用 SQLite glob 语义，常用通配符是 `*`、`?` 和字符集合 `[...]`，并区分大小写。它不是正则表达式。

下面的过滤匹配以 `RenderThread` 开头的名称：

```sql
SELECT name
FROM thread
WHERE name GLOB 'RenderThread*';
```

如果要搜索任意位置的普通文本，DataGrid 的 contains 操作更直观；需要可审核的固定查询时，把规则写成明确的 SQL。

### 8.3 snap-to-boundaries 解决的是选区精度

拖动选择边界或创建 area selection 时，v54 UI 会吸附到附近 slice 边界；按住 Alt 可临时关闭吸附。它帮助精确选择区间，不会改变 trace 内事件的时间戳，也不会提高采集精度。

选定区间后创建 Time Range 节点，再与数据源连接到 Filter During，可让节点图和 timeline 使用同一个观察窗口。

## 9. 三种新增导入与去混淆能力

### 9.1 Collapsed Stack

v54 Trace Processor 能识别 Brendan Gregg FlameGraph 工具使用的 Collapsed Stack 文本，例如：

```text
main;foo;bar 100
main;foo;baz 40
```

分号分隔调用帧，末尾数字是样本计数。该能力让 Trace Processor 接收这种 profile 输入，不表示 Android 设备会自动生成这种文件，也不等同于把任意文本转换为系统 trace。

### 9.2 Firefox Profiler 预处理 JSON

v54 增加 Firefox Profiler preprocessed JSON 的导入支持。输入格式支持属于 Trace Processor 解析能力；导入后有哪些表和字段，应对样本文件运行查询确认，不能套用 Android FrameTimeline 或 CUJ 表的假设。

### 9.3 R8 retracing

v54 改进了部分受支持 profiling 类型的 R8 retracing。要得到可读 Java/Kotlin 符号，仍需要匹配构建产物的映射信息。版本不匹配或没有 mapping 时，工具无法可靠恢复原名称。

这三项扩展影响“Trace Processor 能读什么、能否改善符号”，与 Data Explorer 节点数量没有直接关系。

## 10. 性能与正确性：一张图不要吞掉整条 trace

调度和 slice 表可能有数百万行。节点图能执行不代表查询成本合理。建议按以下顺序压缩数据：

1. 尽早使用 Time Range 或明确的 `ts` 条件；
2. 在 Join 前过滤进程、线程、事件名和无效时长；
3. 探索阶段加 Limit and Offset，确认列与键后再放宽；
4. 聚合前检查 Join 的输入行数、输出行数和重复键；
5. 查看生成 SQL，确认过滤条件没有被放到会改变语义的位置；
6. 比较结果时固定 Trace Processor 版本、trace config 和 SQL。

对于区间表，过滤条件还要考虑跨越窗口边界的事件。只写 `ts BETWEEN start AND end` 会漏掉从窗口前开始、但在窗口内仍持续的事件。通用重叠条件是：

```sql
event.ts < window_end
AND window_start < event.ts + event.dur
```

这表示两个半开区间存在交集。遇到负时长或开放区间时，需要先按相应表的定义处理，不能直接套用。

## 11. 从 UI 交给命令行回归

Data Explorer 适合探索，稳定分析应保存 SQL。v54 的 `trace_processor_shell` 用 `-q` 或 `--query-file` 执行查询文件，命令格式如下：

```bash
./trace_processor_shell \
  --query-file analysis.sql \
  trace.perfetto-trace
```

命令会加载 trace 后执行 `analysis.sql`。在 CI 或批量分析中，还应固定 shell 二进制版本，并把工具版本写入结果元数据。

Data Explorer 也可以导入、导出节点图 JSON，但 v54 源码在导出界面明确警告：Explore Page 仍在开发，未来版本不保证兼容该 JSON。它适合作为同版本下的工作草稿，不能代替 SQL 作为长期接口。

## 12. 排错清单

当结果为空或不可信时，依次检查：

- Trace Processor 和 UI 是否为预期版本；
- trace config 是否采集了目标数据源；
- 目标进程是否有正确的 `upid`，线程是否有正确的 `utid`；
- 时间单位是否仍为纳秒；
- `dur <= 0` 与 `NULL` 是否被误当作正常数值；
- Query 节点是否已手动重新执行；
- CUJ 是否存在 `J<...>` 与状态 marker；
- FrameTimeline 是否存在，帧关联是否限制了 `upid` 和区间；
- heap graph 是否采集成功，DMA-BUF 关联值是否为 `NULL`；
- ANR 的 `intent`、`component` 是否适用于该 `anr_type`；
- Join 后行数是否异常增长；
- 网页端新功能是否被误写成 v54 能力。

分析报告至少保存：Android 构建标识、trace config、Perfetto/Trace Processor 版本、SQL、时间窗口和关键原始行。只有图表而没有这些上下文，很难复核结论。
