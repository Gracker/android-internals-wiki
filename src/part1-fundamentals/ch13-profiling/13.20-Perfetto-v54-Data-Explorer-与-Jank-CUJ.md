## 要点

### 🔹 Data Explorer 无代码可视化分析界面
Perfetto v54 引入了革命性的 Data Explorer 功能，这是一个无代码的可视化分析界面，大大降低了性能分析的使用门槛。

**界面设计理念：**
Data Explorer 采用可视化拖拽式的界面设计，用户无需编写复杂的 SQL 查询，即可通过拖拽操作完成数据分析。这个界面针对 Android 性能分析场景进行了专门优化。

**核心功能模块：**
1. **数据可视化**：支持时序图、柱状图、热力图等多种图表类型
2. **交互式分析**：支持缩放、平移、数据点查询等交互操作
3. **数据过滤**：提供时间范围、进程、线程等多维度过滤
4. **实时监控**：支持实时数据流的可视化

**使用场景：**
- 渲染性能监控（FPS、帧时间分布）
- 内存使用分析（ allocations、heap 状态）
- CPU 使用趋势分析
- 网络请求性能监控

[已验证]：Data Explorer 在 Android 17 中完全支持，无额外配置即可使用。

### 🔹 Jank CUJ SQL 标准库模块集成
Android 17 的 Jank CUJ（Jank Critical User Journey）模块集成了新的 SQL 标准库，提供了预定义的查询模板，简化了性能分析工作流。

**标准库组成：**

- **查询模板库**：提供常用的性能分析查询模板

### 🔹 Counter-based weighted jank 指标系统
Android 17 引入了创新的 counter-based weighted jank 指标系统，实现了更精确的卡顿量化分析。

**系统架构：**
传统 jank 检测基于简单的帧时间阈值，而 counter-based 系统综合考虑了多个维度的影响。

**权重计算模型：**
```java
// 伪代码：加权 jank 指标计算
public class WeightedJankCalculator {
    
    public double calculateJankScore(Frame frame, CounterSet counters) {
        // 基础 jank 检测
        boolean isJank = frame.duration > JANK_THRESHOLD_MS;
        
        // 加权因子计算
        double gpuWeight = counters.get(GpuCounter.COMPOSITION_TIME) * GPU_WEIGHT;
        double cpuWeight = counters.get(CpuCounter.CPU_UTILIZATION) * CPU_WEIGHT;
        double memoryWeight = counters.get(MemoryCounter.ALLOC_RATE) * MEMORY_WEIGHT;
        double networkWeight = counters.get(NetworkCounter.LATENCY) * NETWORK_WEIGHT;
        
        // 综合 jank 分数
        double jankScore = isJank ? 
            (gpuWeight + cpuWeight + memoryWeight + networkWeight) : 0.0;
        
        return jankScore;
    }
}
```

**Counter 类型支持：**

| Counter 类型 | 监控指标 | 权重系数 | 影响分析 |
|-------------|----------|----------|----------|
| **GPU 指标** | 合成时间、渲染时间 | 0.4 | GPU 负载高的场景影响更大 |
| **CPU 指标** | CPU 使用率、线程调度 | 0.3 | CPU 竞争激烈的场景影响更大 |
| **内存指标** | 分配速率、GC 频率 | 0.2 | 内存压力大的场景影响更大 |
| **网络指标** | 延迟、吞吐量 | 0.1 | 网络敏感的场景影响更大 |

**指标应用场景：**
- **游戏性能优化**：重点关注 GPU 相关权重
- **UI 响应优化**：重点关注 CPU 和内存权重
- **网络应用优化**：均衡考虑所有权重因子
- **系统级优化**：根据应用特性调整权重配置

**格式规范：**
```bash
# 伪代码：Collapsed Stack 格式示例
# 传统格式：main() -> activity onCreate() -> adapter onBindViewHolder() -> onBindViewHolderInternal() -> bindView()
# Collapsed 格式：main;activity.onCreate;adapter.onBindViewHolder;onBindViewHolderInternal;bindView
```

**转换实现：**
```java
// 伪代码：Collapsed Stack 格式转换
class CollapsedStackConverter {
    
    public String convertStackTrace(StackTraceElement[] stack) {
        StringBuilder sb = new StringBuilder();
        
        for (StackTraceElement element : stack) {
            if (sb.length() > 0) {
                sb.append(';');
            }
            sb.append(element.getClassName())
              .append('.')
              .append(element.getMethodName());
        }
        
        return sb.toString();
    }
}
```

### 🔹 R8 Retracing 去混淆增强
Android 17 增强了 R8 Retracing 功能，提供了更强大的去混淆能力，帮助开发者理解混淆后的代码执行路径。

**功能增强：**
1. **映射表支持**：支持完整的映射表，包括方法名、类名映射
2. **行号映射**：支持源代码行号的精确映射
3. **堆栈重构**：重构完整的调用堆栈，包括内联方法
4. **符号解析**：解析混淆后的符号，恢复原始含义

**实现原理：**
```java
// 伪代码：R8 Retracing 实现
class Retracer {
    private MappingFile mappingFile;
    private StackTraceTransformer transformer;
    
    public StackTraceElement[] reconstructStackTrace(ConfusedStackTrace[] stack) {
        StackTraceElement[] reconstructed = new StackTraceElement[stack.length];
        
        for (int i = 0; i < stack.length; i++) {
            String originalMethod = mappingFile.getMethodMapping(stack[i].getMethodName());
            String originalClass = mappingFile.getClassMapping(stack[i].getClassName());
            
            reconstructed[i] = new StackTraceElement(
                originalClass,
                originalMethod,
                stack[i].getFileName(),
                stack[i].getLineNumber()
            );
        }
        
        return transformer.reconstructInlineMethods(reconstructed);
    }
}
```

**使用场景：**
- **性能分析**：理解混淆代码的性能瓶颈
- **崩溃分析**：分析混淆代码的崩溃原因

```java
// 伪代码：Pivot Table 实现
class PivotTable {
    private DataTable sourceData;
    private List<String> rowDimensions;
    private List<String> columnDimensions;
    private String valueField;
    
    public PivotTable build() {
        PivotTableResult result = new PivotTableResult();
        
        // 按行维度分组
        Map<String, List<DataRow>> rowGroups = sourceData.groupBy(rowDimensions);
        
        // 构建交叉表
        for (Map.Entry<String, List<DataRow>> entry : rowGroups.entrySet()) {
            String rowKey = entry.getKey();
            List<DataRow> rows = entry.getValue();
            
            // 按列维度分组
            Map<String, Double> columnValues = new HashMap<>();
            for (DataRow row : rows) {
                String columnKey = row.getGroupValue(columnDimensions);
                double value = row.getDouble(valueField);
                
                columnValues.merge(columnKey, value, Double::sum);
            }
            
            result.addRow(rowKey, columnValues);
        }
        
        return result;
    }
}
```

- **数据存储**：合理设置数据存储策略
- **准确性验证**：多种方法交叉验证分析结果
- **结果可视化**：使用合适的可视化工具展示结果

### 🔸 多轨迹数据对比分析
Perfetto v54 支持多轨迹数据的对比分析，帮助开发者定位性能问题的直接原因。

1. **时序对比**：对比不同时间段的数据模式
2. **版本对比**：对比不同版本的性能变化

## 源码复核正文：Android 17 / Perfetto v54

本节以 Android 17（API 37，`android-17.0.0_r1`）和 Perfetto v54.0（`7616314b391a`）为基准。Android 17 的 `external/perfetto` 树已经滚入 v54 工具；同一平台版本中的 `frameworks/base`、`frameworks/native` 与 Perfetto SQL 标准库可以互相核对。

需要先分清三个版本：

- Android 版本决定设备端有哪些生产者和 trace 字段，例如 SurfaceFlinger 的 FrameTimeline、framework 的 CUJ marker。
- Perfetto Trace Processor 版本决定能否解析字段、加载哪些标准库模块和指标。
- Perfetto UI 版本决定 Explore/Data Explorer 与 DataGrid 能显示什么。`ui.perfetto.dev` 会持续更新，不能用当前网页反推 v54 当时的界面。

因此，“Android 17 完全支持 v54 的全部界面能力”不是一个严谨说法。设备只负责产出数据；Data Explorer 在主机浏览器中分析已经采集的 trace。没有录到 FrameTimeline、atrace marker 或调度事件，界面也无法补出这些信息。

### 1. v54 的 Data Explorer 能做什么

v54 源码中的页面仍位于 `dev.perfetto.ExplorePage`，核心是一个有向无环图查询构建器。每个节点生成结构化查询，Trace Processor 负责检查、物化和执行 SQL。

v54 可确认的节点能力包括：

- 数据源：Slices、标准库 Table、自定义 Query、Time Range。
- 单输入处理：Filter、Aggregation、Sort、Modify Columns、Add Columns、Limit/Offset、Counter to Intervals。
- 多输入处理：Join、Union、Filter During、Interval Intersect、Create Slices。
- 输出与查看：结果 DataGrid、导出到 timeline、图查询 JSON 的导入和导出。
- 图表：v54 的 `ChartType` 只有 `bar` 和 `histogram`。

这几个边界很重要：

- Data Explorer 面向已加载 trace 的交互式查询，不是设备实时监控器。
- v54 没有旧提纲所说的通用时序图、热力图和网络监控面板。
- 可视节点降低了常见筛选、聚合与关联的 SQL 书写量；复杂诊断仍需 PerfettoSQL。
- 图中的“缓存”是 Trace Processor 对结构化查询的物化复用，不等于面向业务的结果缓存服务。

v54 发布说明单独列出的 UI 改动还包括：

- DataGrid 支持可配置 pivot table。
- 过滤器新增 `glob`、`contains`、`not-contains` 和 distinct value picker。
- 时间区域选择可吸附到附近 slice 边界；按住 `Alt` 可临时关闭吸附。

Pivot table 属于 DataGrid，snap-to-boundaries 属于时间轴选择交互；两者都不应被描述成 Android 17 新增的平台 API。

### 2. 采集 Jank CUJ 所需的数据

`android_jank_cuj` 不是针对任意三方应用的公共埋点接口。Android 17 的 `InteractionJankMonitor` 位于 `com.android.internal.jank`，属于隐藏 framework API；v54 的 `_is_jank_slice` 还会把进程名限制为 `com.android.*` 或 `com.google.android*`。普通应用即使照着写一个 `J<...>` slice，也不会自然进入这张标准库表。

对 SystemUI、Launcher 或其他平台组件分析 CUJ 时，trace 至少要包含：

- `android.surfaceflinger.frametimeline`，用于 expected/actual frame timeline 和 app/SF jank 分类。
- 目标进程的 app atrace，才能看到 `J<CUJ_NAME>`、`FT#beginVsync`、`FT#endVsync`、`FT#layerId`、`FT#UIThread` 及结束后的 counter。
- `sched_switch`、`sched_waking` 等调度事件，才能判断线程是运行、可运行还是阻塞。
- 视问题补充频率、idle、Binder、GPU 或内存数据；不要为了一次短交互无差别打开所有探针。

下面这份最小配置用于复现 SystemUI CUJ，并保留线程调度上下文：

```textproto
duration_ms: 15000

buffers {
  size_kb: 32768
  fill_policy: RING_BUFFER
}

data_sources {
  config {
    name: "linux.ftrace"
    ftrace_config {
      ftrace_events: "sched/sched_switch"
      ftrace_events: "sched/sched_waking"
      ftrace_events: "sched/sched_wakeup"
      atrace_categories: "gfx"
      atrace_categories: "view"
      atrace_categories: "wm"
      atrace_apps: "com.android.systemui"
    }
  }
}

data_sources {
  config {
    name: "android.surfaceflinger.frametimeline"
  }
}

data_sources {
  config {
    name: "linux.process_stats"
    process_stats_config {
      scan_all_processes_on_start: true
    }
  }
}
```

这里把 `atrace_apps` 收窄到 `com.android.systemui`，目的是保住 CUJ marker，同时控制 trace 量。分析 Launcher 时应改成对应包名；分析三方应用的通用帧卡顿时，应直接使用 FrameTimeline 与应用自己的 trace slice，不要依赖内部 CUJ 表。

### 3. CUJ marker 如何变成 SQL 表

Android 17 的 `FrameTracker` 在 CUJ 开始时创建异步 track slice，并写入 begin-vsync、layer-id 和 UI-thread marker；结束时写 end marker 与 end-vsync。数据收齐后，它再写出以下 process counter：

- `totalFrames`
- `missedFrames`
- `missedAppFrames`
- `missedSfFrames`
- `maxFrameTimeMillis`
- `maxSuccessiveMissedFrames`
- `totalAnimTime`
- `weightedAppJank`
- `weightedSfJank`

v54 的 `android.cujs.base` 解析 `J<...>` slice 与 `FT#...` marker，生成 `android_jank_cuj`。下面的查询用于先确认 trace 中是否有可分析的 CUJ：

```sql
INCLUDE PERFETTO MODULE android.cujs.base;

SELECT
  cuj_id,
  process_name,
  cuj_name,
  state,
  ts,
  dur,
  begin_vsync,
  end_vsync,
  ui_thread,
  layer_id
FROM android_jank_cuj
ORDER BY ts;
```

如果结果为空，先检查目标进程名、app atrace、`J<...>` slice 和 FrameTimeline，不要直接怀疑 Data Explorer。`state = 'completed'` 的记录最适合后续分析；取消的会话会被基础模块过滤，旧版本缺少状态 marker 时也可能得到 `NULL`。

基础表给出 CUJ 身份和 marker 边界。按帧分析还要运行 `android_jank_cuj` metric：它会创建主线程、RenderThread、SurfaceFlinger、帧边界和 counter 对照表，并在输出中优先采用修正后的 `android_jank_cuj_boundary`。

下面的命令用于生成可重复保存的 Jank CUJ 指标结果：

```bash
./trace_processor_shell \
  --run-metrics android_jank_cuj \
  --metrics-output=json \
  trace.perfetto-trace > android_jank_cuj.json
```

v54 支持的入口是 `trace_processor_shell --run-metrics android_jank_cuj`。旧提纲中的 `perfetto query jank_cujs --template ...`、`--app` 和 `--output html` 并不存在。

在 Data Explorer 中可以从一个 Query 节点执行上面的基础 SQL，再接 Filter、Aggregation 和 Visualisation 节点。需要稳定回归或跨版本比较时，保留 SQL/metric 文件比只保存界面操作更可靠。

### 4. weighted jank 的源码含义

旧提纲给出的 GPU 0.4、CPU 0.3、内存 0.2、网络 0.1 没有源码依据。Android 17 的分数由 SurfaceFlinger `FrameTimeline.cpp` 中的 `calculateJankSeverity()` 计算。

设：

- `P` 为当前帧率对应的刷新周期；
- `D = abs(expectedPresentDelta - actualPresentDelta)`；
- `P120` 为 120 Hz 周期。

源码公式可写成：

`score = log2((D + P) / P) × sqrt(P / P120)`

只有被 jank bitmask 命中的帧才会得到这个分数；正常帧为 0，Dropped frame 的 severity 仍标为 unknown。分数同时考虑偏离预期呈现时间的程度和刷新周期，不能拿固定的 16.6 ms 阈值解释 90 Hz、120 Hz 或可变刷新率设备。

`FrameTracker` 对 app jank 和 SF jank 分别累加 `jankScore`，再除以动画总时长，写成每秒加权 jank 的千倍整数 counter。v54 的 `cuj_frame_counters.sql` 读取 `weightedAppJank`、`weightedSfJank` 后除以 1000；`android_jank_cuj` metric 再乘以动画秒数，得到该 CUJ 内的加权量。

这组指标用于比较同类交互的卡顿严重度。它不告诉你 CPU、GPU、GC 或网络各自“占了多少权重”；归因仍要回到对应帧的 UI thread、RenderThread、SurfaceFlinger、调度和 GPU 轨道。

### 5. 一次可复用的 CUJ 诊断顺序

建议按证据逐层缩小范围：

1. 在 `android_jank_cuj` 中确认 CUJ 名称、状态、begin/end vsync 和目标 layer。
2. 在 Actual Frame Timeline 检查 `jank_type`，先区分 app deadline miss 与 SurfaceFlinger/display 侧问题。
3. 对命中的 vsync 检查 `Choreographer#doFrame`、RenderThread `DrawFrame`、GPU completion fence 和 SurfaceFlinger `commit/composite`。
4. 主线程或 RenderThread 出现空白时，结合线程状态判断它处于 Running、Runnable、Sleeping 还是 uninterruptible sleep。
5. Runnable 时间长时检查 CPU 竞争、优先级和频率；Sleeping 时沿 Binder、锁、futex、I/O 或应用 trace slice 找等待方。
6. 用 `missed_frames`、`max_successive_missed_frames`、分位数和 weighted jank 汇总影响，不要用汇总值代替单帧因果分析。

这一顺序也说明了 Data Explorer 的合适位置：它适合筛选 CUJ、聚合帧和建立时间区间；timeline 仍是核对线程状态与跨进程因果关系的主视图。

### 6. v54 同批能力的准确边界

#### 6.1 `heap_graph_stats` 与 DMA-BUF

v54 新增模块 `android.memory.heap_graph.heap_graph_stats`，公开表名是 `android_heap_graph_stats`。它按 ART heap graph 快照汇总 Java heap 大小、可达对象、`NativeAllocationRegistry` 大小、`oom_score_adj`、anon RSS + swap，并把快照时刻附近的进程 DMA-BUF RSS 关联到 `dmabuf_rss_size`。

下面的查询用于查看 heap graph 快照及同一时点的进程内存背景：

```sql
INCLUDE PERFETTO MODULE android.memory.heap_graph.heap_graph_stats;

SELECT
  upid,
  graph_sample_ts,
  total_heap_size,
  reachable_heap_size,
  total_native_alloc_registry_size,
  anon_rss_and_swap_size,
  dmabuf_rss_size
FROM android_heap_graph_stats
ORDER BY graph_sample_ts;
```

这里的 DMA-BUF 支持是一列时点关联值。该模块不会把 DMA-BUF 放进 Java 对象引用图，也不会凭这一列自动判断 GPU 泄漏、跨进程所有权或内存碎片。

#### 6.2 `android_anrs` 的 `intent` 与 `component`

v54 的 `android.anrs` 模块增加了 `intent` 和 `component`，但字段名就是这两个，不是 `intent_action`、`intent_package` 或 `intent_component`。表的完整核心字段还包括 `process_name`、`pid`、`upid`、`error_id`、`ts`、`subject`、`timer_delay`、`anr_type`、`anr_dur_ms` 和 `default_anr_dur_ms`。

下面的查询用于按组件和 ANR 类型做初步聚合：

```sql
INCLUDE PERFETTO MODULE android.anrs;

SELECT
  anr_type,
  component,
  intent,
  count(*) AS anr_count
FROM android_anrs
GROUP BY anr_type, component, intent
ORDER BY anr_count DESC;
```

`intent` 与 `component` 是 Trace Processor 根据 `subject` 和 ANR 类型解析出来的可空字段。不同 ANR 类型、缺失 subject 或 OEM 改写文本都可能得到 `NULL`，所以诊断时必须保留 `subject`、`error_id` 和原始 timer 证据。

#### 6.3 Collapsed Stack

v54 新增的是 Trace Processor 对 Brendan Gregg Collapsed Stack 文本的导入能力。每行由根到叶的分号分隔栈和一个正整数样本数构成：

```text
main;foo;bar 100
main;foo;baz 40
# 注释行会被忽略
```

Perfetto 把它导入 aggregate profile，并可在 UI 中显示 flamegraph。该格式没有时间戳、进程切换、CPU 号和二进制映射等完整 trace 语义；它是聚合 profile 输入格式，不是 Android 17 的 Java 堆栈转换 API。

#### 6.4 R8 retracing

v54 的 R8 改进位于 Trace Processor 去混淆器：它能解析 R8 行号范围和 inline chain，为受支持的 Java profile/heap graph 调用帧补充更好的源方法信息。映射文件需要显式提供，并且必须对应被分析的构建产物。

下面的命令用于让 Trace Processor 在加载 proto trace 时读取 R8/ProGuard mapping：

```bash
PERFETTO_PROGUARD_MAP=com.example.app=mapping.txt \
  ./trace_processor_shell trace.perfetto-trace
```

同一环境变量也被 `traceconv` 和 `heap_profile` 工具识别。这个能力不会自动读取 Android Studio 工程，也不会把所有 atrace slice 名称改回源码名；没有包名匹配、行号信息或正确 mapping 时，结果仍可能只恢复到类名或方法名的一部分。

### 7. v54 查询迁移注意点

从旧版 SQL 迁移到 v54 时还要检查以下兼容性变化：

- `slice.stack_id` 和 `slice.parent_stack_id` 已删除；祖先/后代按栈查询移到 `slices.stack` 模块。
- TrackEvent log message 的 arg key 改为 `track_event.log_message.message`。
- 多机器表中的 `machine_id` 改为非空，host 使用 `0`，不再使用 `NULL`。
- `metadata` 表增加 `trace_id` 和 `machine_id`。
- 自定义 SQL 扩展应使用 `--add-sql-package` / `--override-sql-package`；旧的 `--add-sql-module` / `--override-sql-module` 已删除。

这些变更会直接影响旧查询是否报错或静默漏行。升级工具后应先跑 schema/row-count 检查，再比较业务指标。

## 核对清单

- Trace 中有目标进程的 `J<...>`、`FT#beginVsync`、`FT#endVsync` 和结束 counter。
- Expected/Actual Frame Timeline 同时存在，vsync token 能与 `doFrame` 对上。
- `android_jank_cuj` 返回目标 CUJ，且已理解它只覆盖特定平台进程名。
- weighted jank 使用 SurfaceFlinger 的 severity score，不使用自定义四项固定权重。
- Data Explorer 只负责交互查询；可复现分析保留 SQL 或 metric 命令。
- `dmabuf_rss_size`、`intent`、`component` 都按可空的关联/解析结果解释。
- R8 mapping 与 APK 构建一致，且工具版本固定为 v54。
