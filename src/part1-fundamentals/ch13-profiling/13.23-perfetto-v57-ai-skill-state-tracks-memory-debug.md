# 13.23 Perfetto v57 AI Skill 与 State Tracks 在内存调试中的应用

> 本章保留 Perfetto 工具的版本迭代，但平台边界仍锚定 Android 17 / API 37 / `android-17.0.0_r1`。该平台的 `external/perfetto` 已包含 v54.0，尚无 v57 的 `TRACE_STATE`、`StateTrack` 和 `state` SQL 表。v57.1 可以作为主机侧工具分析 Android 17 trace；这不等于 v57.1 已进入 Android 17 平台源码。

v54 的功能与数据完整性基线见 [13.20 Perfetto v54 Data Explorer 与 Jank CUJ](./13.20-Perfetto-v54-Data-Explorer-与-Jank-CUJ.md)、[13.21 Data Explorer 实操](./13.21-perfetto-v54-data-explorer-analysis.md) 和 [13.22 采集可靠性](./13.22-perfetto-v54-data-explorer-enhanced-analysis.md)。

---

## 1. 先把三个版本对象分开

Perfetto 同时存在设备 tracing service、应用/平台 SDK 和主机 Trace Processor/UI。说“使用 v57 分析 Android 17”时，必须指出是哪一个组件：

| 对象 | 本章基线 | 能力边界 |
| --- | --- | --- |
| Android 平台 | `android-17.0.0_r1`，内含 v54.0 系列源码 | 平台自带头文件没有 `TRACE_STATE`；设备负责采集 |
| 主机分析工具 | Perfetto v57.1 | 能解析 State Track，提供 `state` 表；可读取 Android 17 trace |
| AI skill | v57.1 发布时的 skill bundle | 给 coding agent 提供说明、SQL、脚本与 `trace_processor` wrapper |

主机工具比设备源码新是常见组合。protobuf tracing service 负责搬运 packet，字段语义主要由 producer 和 Trace Processor 决定。不过，若要在 Android 17 应用中产生 v57 State Track，需要显式集成 v57 或更新的 Perfetto C++ SDK，并在目标构建上做采集兼容性测试；仅使用 Android 17 平台自带 SDK 无法调用这组 API。

## 2. v57 的 AI Skill 是什么

Perfetto AI Skill 不是内置在 Trace Processor 中的模型，也不会在设备上自动诊断。它是一组符合 Agent Skills 规范的 Markdown 工作流、PerfettoSQL、Python 辅助脚本和 `trace_processor` wrapper。coding agent 读取这些文件，按指令执行本地查询，再结合代码仓库形成候选解释。

v57.0 发布说明把它描述为一个可安装的 skill；v57.1 修复了所有安装方式中 wrapper 未随 skill 一起发布的问题。wrapper 首次运行时按主机平台下载预编译 Trace Processor，并缓存到本机。分析能否离线完成，取决于预编译文件是否已下载以及 agent 自身的运行环境。

### 2.1 固定到 v57.1 的安装方式

官方文档给 Claude Code 和 Codex 提供指向 `ai-agents` 分支的插件命令。该分支会继续更新；需要复现实验时，可用 fallback installer 的 `--version` 固定 bundle。

下面的命令把 v57.1 安装到明确目录：

```bash
curl -fsSL https://get.perfetto.dev/agents-install \
  | python3 - --version v57.1 --target /absolute/path/to/perfetto-agent
```

安装脚本会通过自定义 git ref 命名空间（`refs/ai-agent-tag/<version>`）把 v57.1 解析为对应的 bundle commit，找不到时回退到 `ai-agents` 分支 tip。团队环境应审阅下载脚本、固定版本，并把目标目录设为项目允许的位置。不要在包含敏感 trace 的环境里直接执行未经审阅的移动分支脚本。

安装完成后，skill 要求设置 `SKILL_ROOT`，并把 bundle 中的 wrapper 加入 `PATH`：

```bash
export SKILL_ROOT="/absolute/path/to/perfetto-agent/skills/perfetto"
export PATH="$SKILL_ROOT/bin:$PATH"
trace_processor --version
```

版本输出应与预期 bundle 对应。若企业/OEM 环境已经提供固定 Trace Processor，应按团队约束使用，不要让 wrapper 静默换成另一个版本。

### 2.2 v57.1 的 Android 内存工作流

v57.1 标签下有五个顶层 Android 内存工作流：

1. `heap_dump.md`：单个或多快照 Java heap dump 的 dominator 路径排查；
2. `heap_dump_caching_optimizer.md`：重复对象和缓存机会；
3. `heap_dump_cluster.md`：批量 heap dump 的路径聚类；
4. `java_allocation_profile.md`：Java allocation profile；
5. `native_heap.md`：native heap / heapprofd 分析。

同一 bundle 还包含 GPU 工作流。注意，`index.json` 不在 Perfetto 源码树中，而是 `agents-install` 安装后在目标 skills 目录（`<target>/skills/index.json`）生成的清单，用于 OpenCode 等按 `skills/index.json` 发现技能的 agent。它的文件条目数只是打包清单，不是功能数量；不要用“共 N 个文件”推断有 N 个诊断能力。

## 3. Heap dump 的两阶段工作流

### 3.1 Phase 1 做了什么

`heap_dump.md` 要求 agent 在开放式查询前执行固定脚本：

```bash
trace_processor query \
  --query-file "$SKILL_ROOT/workflows/android_memory/scripts/triage_dominator_path.sql" \
  TRACE_FILE
```

脚本返回 `process_name`、`graph_sample_ts`、`path`、`class_name` 和 `self_size`。一条 trace 可以含多个进程或同一进程的多个 heap dump，工作流要求按每个 `(process_name, graph_sample_ts)` 分开报告。

脚本的核心不是“全 trace 只取一行”，而是对每个 `(upid, graph_sample_ts)` 的 dominator class tree 选取 `self_size` 最大的 class node：

```sql
CREATE OR REPLACE PERFETTO TABLE _top_class_nodes AS
SELECT id
FROM (
  SELECT
    id,
    ROW_NUMBER() OVER (
      PARTITION BY upid, graph_sample_ts
      ORDER BY self_size DESC
    ) AS rn
  FROM _heap_graph_dominator_class_tree
)
WHERE rn = 1;
```

后续 SQL 使用 graph/hierarchy 模块恢复该节点的祖先路径。这里的 `self_size` 来自按 dominator class path 聚合后的 class tree，不能当作某一个 Java 对象的 shallow size。

### 3.2 “最大路径”不是泄漏证明

Phase 1 的目标是稳定地产生第一批候选。它没有自动证明：

- 对象数量会随时间持续增长；
- 这些对象已经越过业务需要的生命周期；
- 路径中的每一层都对应可修复的所有者；
- 释放该 class 就会回收所有显示字节；
- 最大 class 一定是导致 OOM 的原因。

skill 的提示模板会使用“likely a memory leak”一类判断。工程报告应把它降级为待验证假设，并补充：

1. 多个 `graph_sample_ts` 的数量与大小趋势；
2. GC root 类型和 dominator/reference 路径；
3. 对应源码中的生命周期、注册与释放点；
4. 场景结束后对象是否仍被保留；
5. 与正常样本或修复后样本的对照。

一个大而稳定的缓存、资源池或预加载结构可能符合设计；一个单次只占几 MiB、却每次场景都增长的对象链更值得追踪。

### 3.3 Phase 2 为什么要由用户明确触发

开放式 deep dive 可能执行更多 SQL、读取源码并生成修改建议。工作流要求用户确认 Phase 1 不足后再进入 Phase 2，目的是控制查询范围和代码访问范围。

进入 Phase 2 后，仍需区分三组量：

- object/class 自身大小；
- dominator 下的 retained/dominated 大小；
- allocation profile 中的累计分配与尚未释放大小。

Heap dump 是某时刻的对象图；allocation profile 是时间序列。两种数据回答的问题不同，不能用同一列名替代。

## 4. Fleet 聚类：适合归并线索，不负责定案

### 4.1 脚本做了什么

`cluster_paths.py` 会：

1. 去掉路径中的实例计数，如 `[104]`；
2. 去掉 `[ROOT...]` 标签；
3. 把 `A -> B -> C` 转成文本；
4. 用 TF-IDF 向量化；
5. 对多个 K 运行 K-Means；
6. 用 silhouette score 选 K；
7. 把 `cluster_id` 写回 CSV。

下面是 v57.1 的路径预处理：

```python
def preprocess_path(path):
  if not isinstance(path, str):
    return ""
  path = re.sub(r"\[\d+\]", "", path)
  path = re.sub(r"\[ROOT.*?\]", "", path)
  classes = [c.strip() for c in path.split("->") if c.strip()]
  return " ".join(classes)
```

这会减少实例数和 GC root 标签造成的噪声。TF-IDF 默认采用词袋特征，无法完整保留 class path 的严格顺序与引用字段语义；K-Means 的相似簇应被理解为“值得一起看”的候选。

### 4.2 输入数据必须自行把关

工作流期望输入至少包含：

```text
trace_uuid,process_name,path,class_name,self_size
```

`triage_dominator_path.sql` 不输出 `trace_uuid`，批处理时要用文件名或稳定 ID 补齐。它会输出 `graph_sample_ts`，建议保留该列，避免同一 trace、同一进程的多次 dump 混在一起。

v57.1 的 `cluster_paths.py` 接收 `--process_name`，但脚本本身没有用该参数过滤 DataFrame。调用方应先把 CSV 限定为一个进程，并验证列名和空路径。`summarize_clusters.py` 用唯一 `trace_uuid` 数作为 trace 总数；若一个 trace 贡献多个 dump，直接用 cluster 行数除以 trace 数可能得到超过 100% 的“占比”。报告比例前应按想要的统计单位重算。

### 4.3 何时值得用聚类

适合：

- 同一进程的大量线上 heap dump；
- 希望发现重复出现的 dominator class path；
- 已有稳定 trace ID、场景标签和构建版本；
- 能回到代表样本与源码复核。

不适合：

- 只有两三个样本；
- 混入不同进程、版本或采集配置；
- 路径已经被符号缺失严重破坏；
- 想让聚类结果直接给出泄漏责任类。

## 5. State Track 的数据模型

### 5.1 它与 slice、counter 的区别

State Track 表示“某个系统或子系统在一段时间内处于哪个符号状态”：

- slice 表示有开始/结束边界的工作；
- counter 表示某时刻的数值；
- state 表示互斥的字符串状态，某个状态持续到下一次变化或显式清空。

v57.1 在 `TrackEvent.Type` 中增加 `TYPE_STATE = 5`，并在 `TrackDescriptor` 中增加 `StateDescriptor state = 18`。Trace Processor 将事件写入公开 `state` view。

公开表结构为：

| 列 | 含义 |
| --- | --- |
| `id` | state 行 ID |
| `ts` | 状态开始时间，纳秒 |
| `dur` | 持续时间，纳秒；未关闭时为 `-1` |
| `track_id` | 关联 `track.id` |
| `category` | Track Event category，可空 |
| `value` | 状态字符串 |
| `arg_set_id` | 附加参数 |

它不是内核调度 `thread_state` 表，也不是 Android 生命周期回调的自动镜像。只有 producer 发送 `TYPE_STATE`，或 parser 把特定系统事件映射为 State Track，`state` 表才有对应行。

### 5.2 Parser 路径已经完整实现

v57.1 的处理路径可以从源码逐步跟到：

1. `track_event_tokenizer.cc` 校验 state event 必须有 `track_uuid`，且 descriptor 是 state track；
2. `track_event_event_importer.h` 对 `TYPE_STATE` 调用 `ParseStateEvent()`；
3. event 的 name/name_iid 被解析成状态字符串；
4. `StateTracker::UpdateState()` 关闭旧状态并创建新行；
5. `prelude/after_eof/views.sql` 把 `__intrinsic_state` 暴露为 `state`。

原先“在 `track_event_parser.cc` 搜不到字面量，因此实现可能缺失”的判断不成立；v57.1 把逻辑放在 tokenizer 和 event importer 中。

### 5.3 状态更新语义

`StateTracker` 的行为很具体：

- 新值与当前值不同：旧行的 `dur = new_ts - old_ts`，随后创建新行；
- 新值与当前值相同：不创建新行，只把新参数合入当前行；
- 空字符串或 `nullptr`：关闭当前状态，不创建“空状态”行；
- trace 结束前没有变化或清空：当前行保留 `dur = -1`。

因此，重复上报 `"Playing"` 不能用来统计心跳次数。需要次数时应使用 instant event 或独立 counter。

## 6. 在 Android 17 应用中记录 State Track

### 6.1 C++ SDK 示例

下面示例使用 v57.1 C++ SDK，并让 `StateTrack` 默认挂在当前进程下：

```cpp
perfetto::StateTrack playback_state("Playback state");

TRACE_STATE("player", "Buffering", playback_state);
// 缓冲结束。
TRACE_STATE("player", "Playing", playback_state);
// 用户暂停。
TRACE_STATE("player", "Paused", playback_state);
// 生命周期结束，显式清空当前状态。
TRACE_STATE("player", nullptr, playback_state);
```

每次调用描述一次状态变化，不需要手工计算 duration。使用动态字符串时要考虑事件量、interning 和敏感信息；状态值宜采用稳定枚举文本，不要放 URL、账号或用户输入。

### 6.2 Android 17 的集成边界

在 `android-17.0.0_r1` 的 Perfetto 源码中搜索不到 `TYPE_STATE`、`StateTrack`、`TRACE_STATE` 和公开 `state` view。因此有三种组合：

| 组合 | 结果 |
| --- | --- |
| Android 17 平台 SDK + v54 主机工具 | 没有 v57 State Track API/表 |
| Android 17 trace + v57.1 主机 Trace Processor | 可用 v57.1 的解析和 AI skill；已有数据不会自动变成 state |
| Android 17 应用集成 v57.1 C++ SDK + v57.1 主机工具 | 可以尝试记录/解析 State Track，需在目标设备验证 system backend 与采集配置 |

State Track 不是 API 37 的 Android framework API。应用集成新版 Perfetto SDK 时，还要检查二进制体积、初始化方式、category 配置、release 构建策略和与平台 tracing service 的兼容性。

## 7. 查询 State Track

### 7.1 查看状态与所属进程

`StateTrack("Playback state")` 默认是进程子轨道。v57.1 的通用 `track` view 通过 dimension args 保存 `upid`，下面的查询取出轨道名、进程和状态：

```sql
SELECT
  s.ts,
  s.dur,
  s.category,
  s.value,
  t.name AS track_name,
  t.type AS track_type,
  p.upid,
  p.pid,
  p.name AS process_name
FROM state AS s
JOIN track AS t
  ON t.id = s.track_id
LEFT JOIN process AS p
  ON p.upid = extract_arg(t.dimension_arg_set_id, 'upid')
WHERE
  t.name = 'Playback state'
ORDER BY
  s.ts;
```

全局或线程作用域 State Track 的 dimension 不同，`upid` 可能为空或需要先从 `utid` 关联 `thread`。写通用分析脚本时，应先查看该 track 的 `type` 和 dimension args。

### 7.2 与 native heap allocation 做时间关联

State Track 可以给 `heap_profile_allocation` 提供业务状态窗口。下面查询统计每个播放状态下的正向分配量与净大小变化：

```sql
WITH playback_state AS (
  SELECT
    s.ts,
    s.dur,
    s.value,
    extract_arg(t.dimension_arg_set_id, 'upid') AS upid
  FROM state AS s
  JOIN track AS t
    ON t.id = s.track_id
  WHERE
    t.name = 'Playback state'
)
SELECT
  s.value,
  sum(CASE WHEN a.size > 0 THEN a.size ELSE 0 END) AS allocated_bytes,
  sum(a.size) AS net_bytes,
  sum(CASE WHEN a.count > 0 THEN a.count ELSE 0 END) AS allocation_count
FROM playback_state AS s
JOIN heap_profile_allocation AS a
  ON a.upid = s.upid
  AND a.ts >= s.ts
  AND (s.dur = -1 OR a.ts < s.ts + s.dur)
GROUP BY
  s.value
ORDER BY
  allocated_bytes DESC;
```

`heap_profile_allocation.size` 为正时表示分配，为负时表示释放。`allocated_bytes` 反映分配流量，`net_bytes` 反映该窗口内的净变化；两者都不是 heap dump 的 retained size。

`dur = -1` 被查询视为延续到 trace 结束。若 state 结尾缺失是由于丢包或未 flush，这个假设会放大窗口，所以还要检查 `stats` 和 State Track 是否显式清空。

### 7.3 “某状态分配很多”仍不是因果结论

时间重叠只说明 allocation 发生在该状态窗口。可能的解释包括：

- 该状态直接触发分配；
- 同进程其他线程同时工作；
- 前一状态提交的异步任务延迟执行；
- 采样或聚合把多个调用点合并；
- 状态边界过粗。

应继续解析 `callsite_id`、线程/进程上下文和源码，并与其他状态或正常样本对照。State Track 提供业务切片，不会自动生成因果链。

## 8. 如何审阅 AI Skill 的输出

把 agent 当作查询执行器和假设生成器，至少核对：

- 使用的 `trace_processor --version`；
- SQL 是否来自固定 bundle，是否被 agent 修改；
- 是否逐个处理所有 `(upid, graph_sample_ts)`；
- `self_size`、retained size、allocation size 是否混淆；
- 空结果是否被误写成“没有泄漏”；
- 进程、构建版本和场景是否一致；
- 代码引用是否对应当前构建；
- 聚类比例的分母是否正确；
- trace/code 是否被上传或写入不受控目录；
- 建议是否经过人工复核和修复后 trace 验证。

AI Skill 可以降低第一次写 SQL 的门槛，不能替代数据完整性检查、源码审阅和实验对照。

## 9. 版本演进

| 主机 Perfetto 版本 | 与本章相关的变化 | Android 17 使用方式 |
| --- | --- | --- |
| v54.0 | Data Explorer、heap graph stats、CUJ/ANR 增强 | Android 17 平台源码基线 |
| v55.0–v55.1 | 新 CLI 架构、Heap Dump Explorer 等 | 可作为更新主机工具，注意 CLI 迁移 |
| v56.0–v56.1 | heap dump bitmap/元数据与 UI 改进 | 可分析 Android 17 heap trace |
| v57.0 | State Track、`TRACE_STATE`、AI skill | 属于主机/SDK 后续迭代，不是 Android 17 平台自带能力 |
| v57.1 | 修复 skill bundle 缺失 wrapper | 本章固定的 AI skill 工具版本 |
| v57.2 | 修复嵌入 proto descriptor 的解析兼容问题 | 后续补丁；不改变本章 State Track 核心语义 |

Android 平台版本与 Perfetto 上游版本没有一一对应关系。更新主机工具可能修复 parser，也可能带来 SQL/CLI 变化；生产分析应固定版本并保存查询。
