# 2.29 Compose Pausable Composition 实战指南

Pausable Composition 对应用工程师的价值主要体现在 Lazy Layout 预取：Foundation 可以把即将进入视口的条目子组合分多次推进，剩余帧预算不足时请求暂停，后续再继续。业务代码通常不直接创建 `PausableComposition`，也没有公开的“时间片大小、并发组合数、优先级权重”配置。

应用实践集中在四个问题：

1. 怎样确认项目中的版本和默认行为；
2. 怎样编写有利于 Lazy 预取的列表；
3. 怎样用同一版本做可重复的开关对照；
4. 怎样从 Macrobenchmark 和 Perfetto 判断瓶颈在哪个阶段。

Runtime 对象模型、状态机、`RecordingApplier` 与 Android 调度器的源码细节见 2.28，这里聚焦应用侧的使用和测量。

## 1. 先确认三个版本轴

### 1.1 Compose 版本决定能力

Pausable Composition 属于 AndroidX Compose，不属于 Android 17 framework API：

| 版本阶段 | 行为 |
|---|---|
| Runtime 1.8.0-alpha02 | 首次加入 Pausable Composition |
| Runtime 1.8.0 | 公共 API 进入 1.8 稳定线 |
| Runtime 1.9.0 | 补充 `isApplied`、`isCancelled` 状态 |
| Foundation 1.10.0-alpha05 | Lazy 预取开关默认启用 |
| Foundation 1.10.6 | 因稳定性问题默认关闭 |
| Runtime/Foundation/UI 1.11.4 | 源码基线；Foundation 源码中开关为 `true` |

当前项目可能通过 Compose BOM、version catalog、直接依赖或第三方库约束版本。不能只看 Gradle 文件中声明的一个版本号，还要看最终解析结果。

下面的命令用于检查应用运行时 classpath 中解析出的 Compose 模块：

```bash
./gradlew :app:dependencyInsight \
  --dependency androidx.compose.runtime:runtime \
  --configuration releaseRuntimeClasspath

./gradlew :app:dependencyInsight \
  --dependency androidx.compose.foundation:foundation \
  --configuration releaseRuntimeClasspath

./gradlew :app:dependencyInsight \
  --dependency androidx.compose.ui:ui \
  --configuration releaseRuntimeClasspath
```

输出中应确认 Runtime、Foundation、UI 是否处于同一版本线，以及是否被其他依赖强制升级或降级。构建变体名称不同时，应把 `releaseRuntimeClasspath` 换成对应配置。

### 1.2 Android API 级别决定测试平台，不决定开关

1.11.4 的 Android AAR 声明 `minSdkVersion 23`。同一 Compose 版本可以运行在多个 Android 版本上，Pausable Composition 不需要 `Build.VERSION.SDK_INT >= 37` 判断。

Android 17 / API 37 是平台源码锚点。测试仍应覆盖业务最低版本和主流设备，因为 Choreographer、显示刷新率、CPU/GPU、厂商调度与内存条件都会影响测量结果。

### 1.3 默认开关随 Foundation 补丁版本变化

`ComposeFoundationFlags.isPausableCompositionInPrefetchEnabled` 是一个临时的 `@ExperimentalFoundationApi` 回退开关。1.11.4 源码默认值为 `true`，而 1.10.6 发布说明记录的默认值为关闭。

需要注意以下边界：

- 不能用“Compose 1.10+ 一定默认开启”概括所有补丁版本；
- 不能把该开关作为长期业务配置；
- 升级时同时检查 release notes、源码默认值和项目解析版本；
- 发现回归时可以短期关闭做定位，并向 AndroidX 报告可复现问题。

## 2. 应用侧能控制什么

### 2.1 使用稳定的 `key`

Lazy 条目的索引可能因插入、删除和排序而变化。稳定且唯一的 `key` 帮助 Compose 识别“同一个条目移到了新位置”，也让预取请求能判断索引对应的数据是否已经变化。

```kotlin
@Composable
fun MessageList(
    messages: List<Message>,
    modifier: Modifier = Modifier,
) {
    LazyColumn(modifier = modifier) {
        items(
            items = messages,
            key = { message -> message.id },
        ) { message ->
            MessageRow(message)
        }
    }
}
```

`key` 应来自持久 ID，不能使用会随位置变化的索引，也不应在每次组合时生成 UUID。`key` 变化会让已有预取请求失效，已准备的槽位也可能被取消或释放。

### 2.2 准确 `contentType`

Foundation 1.11.4 按 `contentType` 保存预取各阶段的平均耗时。异构列表若不区分类型，标题、文本卡片、视频卡片和广告位会共享一组估计，scheduler 更难判断剩余时间是否够用。

```kotlin
sealed interface FeedItem {
    val id: Long

    data class Header(
        override val id: Long,
        val title: String,
    ) : FeedItem

    data class Story(
        override val id: Long,
        val title: String,
        val imageUrl: String,
    ) : FeedItem
}

@Composable
fun Feed(items: List<FeedItem>) {
    LazyColumn {
        items(
            items = items,
            key = { it.id },
            contentType = {
                when (it) {
                    is FeedItem.Header -> "header"
                    is FeedItem.Story -> "story"
                }
            },
        ) { item ->
            when (item) {
                is FeedItem.Header -> FeedHeader(item)
                is FeedItem.Story -> StoryRow(item)
            }
        }
    }
}
```

类型数量应反映布局和组合成本的主要差异。把每个条目 ID 都作为 `contentType` 会失去聚合平均值的意义。

### 2.3 让条目的组合路径保持轻量

暂停是协作式的。`ShouldPauseCallback` 返回 `true` 后，Runtime 仍要到可暂停位置才能交还控制权。以下工作若直接出现在条目组合路径中，仍可能形成较长 slice：

- 同步文件或数据库 I/O；
- Bitmap 解码；
- 大集合排序、过滤或 JSON 解析；
- 在 Composable 函数体中反复创建复杂对象；
- 自定义 Layout 中耗时较长的测量；
- 不受 Compose 暂停点控制的阻塞调用。

可复用结果应在 ViewModel、repository 或明确的后台任务中准备；与组合输入相关的高成本纯计算可以在输入变化时缓存。Pausable Composition 不能修复条目内的同步阻塞。

### 2.4 控制无效重组

Pausable prefetch 处理“预取组合如何分段”，不会减少本来无需发生的重组。稳定参数、延后状态读取、`remember`、`derivedStateOf` 和正确的状态归属仍需独立处理。

例如，“是否显示回到顶部按钮”只在首个可见 item 是否为 0 时变化，可以用派生状态收窄重组：

```kotlin
val listState = rememberLazyListState()
val showScrollToTop by remember {
    derivedStateOf {
        listState.firstVisibleItemIndex > 0
    }
}

LazyColumn(state = listState) {
    // items(...)
}

AnimatedVisibility(visible = showScrollToTop) {
    ScrollToTopButton()
}
```

这段优化针对快速变化的 scroll state 读取，与暂停式预取解决的是不同问题。

## 3. `LazyLayoutCacheWindow` 怎样使用

`LazyLayoutCacheWindow` 决定前方预取和后方保留的距离。它是 `@ExperimentalFoundationApi`，需要显式 opt-in。

下面的示例把 cache window 配置到 `rememberLazyListState()`，再把状态交给 `LazyColumn`：

```kotlin
@OptIn(ExperimentalFoundationApi::class)
@Composable
fun CachedMessageList(
    messages: List<Message>,
    modifier: Modifier = Modifier,
) {
    val listState = rememberLazyListState(
        cacheWindow = LazyLayoutCacheWindow(
            aheadFraction = 1.0f,
            behindFraction = 0.5f,
        )
    )

    LazyColumn(
        state = listState,
        modifier = modifier,
    ) {
        items(
            items = messages,
            key = { it.id },
            contentType = { it.kind },
        ) { message ->
            MessageRow(message)
        }
    }
}
```

比例值表示视口比例。另一个重载接收 `ahead: Dp` 和 `behind: Dp`，Dp 会转换为滚动方向上的像素距离；两者都不表示条目数量。

示例中的 `1.0f` 和 `0.5f` 只用于展示 API。窗口越大，越可能提前准备更多条目，也会保留更多 Composition、LayoutNode、图片和其他资源。调参必须同时观察帧超时、预取命中和内存，不能只看滚动的主观感受。

### 3.1 先用默认策略建立基线

建议按以下顺序测试：

1. 默认 `rememberLazyListState()`；
2. 保持数据、手势和构建产物不变，采集多轮基线；
3. 再引入 cache window；
4. 分别改变 ahead 和 behind；
5. 比较 FrameTiming、trace 阶段与内存；
6. 只保留可重复收益。

一次手动滑动无法说明参数有效。快速 fling、慢速拖动、方向反转、列表更新、嵌套列表和图片缓存冷热都会改变结果。

## 4. 怎样做同版本开关对照

比较 Foundation 1.10.6 与 1.11.4，会同时引入许多其他修复，无法把差异全部归因于 pausable prefetch。解释力更强的方法，是在**同一 Foundation 版本、同一代码和同一设备**上构建两个 benchmark variant。

回退变体可以在 `Application` 的最早阶段关闭临时开关。下面代码只用于回归定位：

```kotlin
@OptIn(ExperimentalFoundationApi::class)
class BenchmarkLegacyPrefetchApp : Application() {
    override fun onCreate() {
        ComposeFoundationFlags
            .isPausableCompositionInPrefetchEnabled = false
        super.onCreate()
    }
}
```

另一个变体保持 1.11.4 的默认值 `true`。两者都应使用 release-like、non-debuggable、可 profile 的构建，并保持 R8、Baseline Profile、数据、图片缓存和网络状态一致。

源码明确警告：Compose 代码加载后再修改开关会产生未定义行为。不能在同一个进程运行到一半时动态切换；每个 variant 应冷启动独立进程。

这个开关是 AndroidX 用于风险功能回退的临时 API，后续可能被移除。生产环境长期关闭会失去后续修复路径，应优先升级到包含修复的补丁版本。

## 5. Macrobenchmark：先证明有无回归

Macrobenchmark 是官方推荐的 Compose 界面基准工具。列表滚动应使用独立的 `com.android.test` 模块，从进程外通过 UI Automator 操作 release-like app。

为了让 UI Automator 稳定找到 Compose 列表，可在测试构建中暴露资源 ID：

```kotlin
LazyColumn(
    state = listState,
    modifier = Modifier
        .semantics { testTagsAsResourceId = true }
        .testTag("message_list"),
) {
    // items(...)
}
```

`testTagsAsResourceId` 会让 `By.res("message_list")` 能找到该节点。不能让 benchmark 依赖屏幕坐标定位列表，否则窗口尺寸或系统栏变化会破坏脚本。

下面是最小滚动基准：

```kotlin
@LargeTest
@RunWith(AndroidJUnit4::class)
@OptIn(ExperimentalMetricApi::class)
class MessageListBenchmark {
    @get:Rule
    val benchmarkRule = MacrobenchmarkRule()

    @Test
    fun flingDown() = benchmarkRule.measureRepeated(
        packageName = "com.example.app",
        metrics = listOf(
            FrameTimingMetric(),
            TraceSectionMetric("compose:lazy:prefetch:compose"),
            TraceSectionMetric("compose:lazy:prefetch:apply"),
            TraceSectionMetric("compose:lazy:prefetch:measure"),
        ),
        iterations = 10,
        startupMode = StartupMode.WARM,
        setupBlock = {
            pressHome()
        },
    ) {
        startActivityAndWait()
        val list = device.findObject(By.res("message_list"))
        list.setGestureMargin(device.displayWidth / 5)
        list.fling(Direction.DOWN)
        device.waitForIdle()
    }
}
```

`TraceSectionMetric` 仍是实验性 API。若当前 Benchmark 版本不接受内部跟踪名称，就保留 `FrameTimingMetric()`，再打开每轮自动生成的 Perfetto 跟踪记录分析。

`FrameTimingMetric` 的主要输出是：

- `frameOverrunMs`：正值表示超过 deadline，负值表示仍有余量；API 31+ 可用；
- `frameDurationCpuMs`：UI thread 与 RenderThread 生产该帧的 CPU 时长。

应比较 p50、p90、p95、p99，不能只取一次平均 FPS。高刷新率设备的 deadline 短于 60 Hz，固定“16 ms 为慢帧”的规则不适用。

### 5.1 固定测试条件

对照至少记录：

- 设备型号、Android 构建版本与 Android 17 / API 37 标签的对应关系；
- Display 刷新率和分辨率；
- Foundation/Runtime/UI/Compiler/Benchmark 版本；
- build type、R8、Baseline Profile 和 compilation mode；
- 数据集内容与 `contentType` 分布；
- 图片、磁盘和网络缓存状态；
- 每轮起始位置、手势方向和速度；
- 温度、充电状态与后台负载。

官方不建议用模拟器产出面向用户的性能数字。CI 可用于发现相对回归，最终结论仍应在代表性物理设备上复核。

## 6. Perfetto：再解释为什么

Foundation 1.11.4 的 Lazy 预取路径包含以下 trace：

- `compose:lazy:schedule_prefetch:index`
- `compose:lazy:prefetch:available_time_nanos`
- `compose:lazy:prefetch:execute:item`
- `compose:lazy:prefetch:execute:urgent`
- `compose:lazy:prefetch:compose`
- `compose:lazy:prefetch:apply`
- `compose:lazy:prefetch:resolve-nested`
- `compose:lazy:prefetch:measure`
- `compose:lazy:prefetch:idle_frame`

Macrobenchmark 每轮都会生成 system trace。需要更完整的 Compose 组合跟踪时，可按 Benchmark 官方说明启用 `androidx.benchmark.fullTracing.enable` instrumentation argument；完整跟踪会增加开销，不宜把它和轻量指标采集结果直接混合比较。

### 6.1 正常的暂停式预取长什么样

同一个索引的工作可能分散到多次 scheduler 执行：

```text
调度索引
  -> compose / resume
  -> 预算不足，退出本轮
  -> 下一帧前再次组合 / resume
  -> measure
  -> 解析嵌套预取
  -> apply
```

看到多个较短的 `compose` slice 不等于发生了错误重组。应按索引、时间顺序和 `available_time_nanos` 判断它们是否属于同一个预取请求。

### 6.2 看不到 prefetch trace

依次检查：

1. 当前控件是否为支持该路径的 Lazy Layout；
2. 是否发生了足以触发预取的滚动；
3. Foundation 解析版本和开关值；
4. item 是否已经准备，或请求是否被快速取消；
5. View 是否可见、scheduler 是否活跃；
6. 当前帧是否一直没有剩余预算。

“没有 trace”不能直接写成“Pausable Composition 失效”。

### 6.3 单个 `compose` slice 仍然很长

常见原因是条目中存在长时间不可暂停的调用，或这段 Composable 没有到达可暂停位置。检查：

- 同步 I/O、解码和解析；
- 大集合计算；
- 自定义 Layout/measure；
- 复杂对象分配和 GC；
- Composition tracing 中对应的 Composable；
- UI thread 同期的 Binder、锁和调度延迟。

增大 cache window 只会更早、更多地调度这些工作，不能缩短单次阻塞。

### 6.4 `available_time_nanos` 经常为 0

Android 调度器的预算来自下一帧估算时间减去当前时间。若可见帧的界面、RenderThread 或其他主线程工作已经耗尽间隙，预取只能推迟。

此时应优先优化当前可见条目和同线程工作。盲目扩大 ahead window 会产生更多等待请求。

### 6.5 `apply` 或 `measure` 占比高

暂停机制只分段推进组合。录制操作完成后仍要 `apply()`，随后还要 premeasure。若瓶颈位于：

- `apply`：检查节点数量、modifier 更新、RememberObserver 与 SideEffect；
- `measure`：检查自定义 Layout、intrinsic measurement、嵌套约束和 placeable 数量；
- nested prefetch：检查嵌套 Lazy Layout 的层级和预取数量。

不能把整段预取成本都归给 `resume()`。

### 6.6 请求频繁取消

Foundation 会在索引越界、`key` 改变、列表状态失效或策略取消时清理预取。频繁的数据全量替换、不稳定的 `key`、快速方向反转都会降低命中率。

应先修正数据身份和更新方式，再讨论 cache window。取消不是内存泄漏证据；判断泄漏时，还要检查句柄是否释放、对象是否被引用以及堆增长。

## 7. 怎样解释内存变化

预组合会提前创建 Composition 状态、LayoutNode 和业务对象，图片组件还可能触发解码或缓存。暂停式预取的目标并不包括降低峰值内存。

内存对照应至少分开：

- Java/Kotlin heap；
- native heap；
- 图形/纹理内存；
- 图片缓存；
- 预组合槽位数量；
- GC 次数与 pause；
- cache window 前后保留范围。

若帧超时下降但内存明显增加，需要继续缩小 ahead/behind，或减少条目在组合时创建的重资源。没有采集对象数量和内存类别时，不能宣称“降低 30% 峰值内存”。

## 8. 升级与回退流程

### 8.1 升级前

1. 保存当前解析依赖树；
2. 建立固定数据和手势的 Macrobenchmark；
3. 保存基线 JSON 与 trace；
4. 记录当前开关默认值；
5. 覆盖快速 fling、慢拖、方向反转、列表刷新和嵌套列表。

### 8.2 升级后

1. 确认 Runtime、Foundation、UI 没有混用版本；
2. 重跑同一 benchmark；
3. 先看 FrameTiming 分位数，再看跟踪阶段；
4. 检查 release notes 中的 Pausable Composition、prefetch、cache window 修复；
5. 若出现回归，用同版本开关 A/B 对照缩小范围；
6. 保留最小复现、设备信息、trace 和依赖树，提交 AndroidX issue。

### 8.3 生产回退

只有证据指向 pausable prefetch 且短期无法升级修复时，才考虑在应用启动最早阶段关闭临时开关。回退后必须重新测量，因为旧的完整组合路径也可能造成更长的主线程占用。

flag 属于临时兼容设施。长期方案应是升级修复版本、修正条目代码或调整预取窗口。

## 9. 常见错误做法

### 9.1 按设备档次设置“8 ms / 16 ms / 32 ms 时间片”

公开 API 没有这组参数。Foundation 根据当前可用时间和历史平均耗时决定是否继续，Android 调度器也会按显示刷新率估算下一帧时间。

### 9.2 在业务 Composable 中调用 `pause()` / `resume()`

业务层没有 `rememberPausableCompositionScope()`、`PausableContent` 或“暂停后台组合”的标准 API。低层 `PausableComposition` 需要 `Applier` 和 `CompositionContext`，适合 Compose 基础设施。

### 9.3 用 API Level 判断是否支持

Compose 版本决定库能力。`Build.VERSION.SDK_INT >= 37` 分支会让 Android 17 以下设备错误走旧路径，也掩盖实际依赖版本。

### 9.4 把动画、网络加载和协程调度归入本机制

Pausable Composition 负责子组合。动画时钟、网络请求、`produceState` producer 协程和图片加载器有各自调度器，不会因暂停组合自动获得优先级。

### 9.5 只看平均 FPS

平均值会隐藏少量严重卡顿。结合 `frameOverrunMs` 的高分位、jank 帧跟踪和具体预取阶段，才能判断用户可感知的尾部问题。

## 10. 实战检查表

### 接入前

- [ ] Runtime、Foundation、UI 的解析版本已记录；
- [ ] 当前 Foundation 默认开关已从源码或发布说明确认；
- [ ] Lazy 条目有稳定的 `key`；
- [ ] 异构条目有合理的 `contentType`；
- [ ] item 组合路径没有同步 I/O、解码和大计算；
- [ ] 默认预取策略已有 Macrobenchmark 基线。

### 调参时

- [ ] cache window 的单位按 Dp 或 viewport fraction 理解；
- [ ] ahead 与 behind 分开调整；
- [ ] build、设备、刷新率、数据和手势固定；
- [ ] 同时观察 FrameTiming、trace 和内存；
- [ ] 快速 fling、方向反转、数据更新与嵌套列表均已覆盖。

### 回归时

- [ ] 已确认问题最早发生在组合、apply、measure 或其他线程阶段；
- [ ] 同版本开关 A/B 对照能稳定复现差异；
- [ ] flag 在进程最早阶段设置；
- [ ] 已尝试包含相关修复的补丁版本；
- [ ] issue 附带依赖树、最小复现、设备、benchmark 结果和 trace。

## 总结

应用使用 Pausable Composition 的主要方式，是让 Foundation 的 Lazy 预取在正确版本和列表结构上工作。稳定的 `key`、准确的 `contentType`、轻量条目与可测量的 cache window，决定了预取是否值得做、历史估计是否可信，以及准备结果能否命中。

评估顺序应保持稳定：先确认解析版本和默认开关，再用 Macrobenchmark 证明回归，最终用 Perfetto 区分组合、apply、nested 和测量。没有同版本对照和跟踪证据时，不应给出固定时间片、固定设备档位或固定性能百分比。
