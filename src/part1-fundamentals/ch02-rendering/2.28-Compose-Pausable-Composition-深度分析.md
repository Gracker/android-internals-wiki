# 2.28 Compose Pausable Composition 深度分析

<!-- outline-start -->
## 要点

### 🔹 锚点 1：PausableComposition 控制流机制

Pausable Composition 是 Compose 1.10+（BOM 2025.12.00）引入的核心运行时改进，允许组合工作在帧边界处暂停而非必须连续完成。在源码层面，`PausableComposition` 接口继承自 `CompositionImpl`（位于 `androidx.compose.runtime` 包），其核心是**带时间切片的组合控制流**。

**关键实现特点**：
- **控制流分块**：长组合工作被分割成多个时间可控的块
- **帧预算检查**：每个块执行完成后通过 `shouldPause` 回调检查帧截止时间
- **延迟提交**：所有组合完成后才通过 `apply()` 提交到 UI 树
- **原子性保证**：未完成的 UI 子树不会被渲染，避免中间状态

在源码中，`PausableComposition` 的实现位于 `androidx/compose/runtime/Composer.kt`，通过 `ComposeFeatureFlag.PausableComposition` 启用。该特性主要作用于 LazyColumn/LazyRow 的预取路径中，但也能在普通 Composable 中发挥作用。

[已验证: AOSP androidx-main compose/runtime/Composer.kt]
[适用版本: Android 13+ (Compose 1.10+) - Android 17 (API 37)]

### 🔹 锚点 2：setPausableContent() → PausedComposition 对象链路

Pausable Composition 的使用入口是 `setPausableContent()` 工厂函数，它创建 `PausedComposition` 对象，构成整个暂停-继续组合的核心数据结构：

```kotlin
// 内部控制流（简化）
// 1. setPausableContent() → PausedComposition 对象
val pausableContent = setPausableContent {
    // 用户定义的 Composable 内容
    Item {}
}

// 2. 对象链路结构
sealed interface PausedComposition {
    public val isComplete: Boolean     // 组合是否完成
    public val isApplied: Boolean      // 是否已提交到 UI 树
    public val isCancelled: Boolean    // 是否已取消
    
    public fun resume(shouldPause: ShouldPauseCallback): Boolean  // 继续执行
    public fun apply()                // 提交变更到 UI 树
    public fun cancel()              // 取消组合
}

// 3. typealias ShouldPauseCallback = () -> Boolean
// 回调用于检查是否应该暂停下一块组合
```

**对象生命周期**：
1. **创建阶段**：`setPausableContent` 初始化内部状态，准备记录组合工作
2. **执行阶段**：通过 `resume(shouldPause)` 执行分块组合
3. **暂停判定**：`shouldPause` 回调检查 `FrameData.deadlineNanos` 是否临近
4. **继续执行**：`resume` 循环直到所有组合完成或被取消
5. **提交阶段**：`apply()` 原子性地提交所有变更

### 🔹 锚点 3：resume() + shouldPause 回调判定逻辑

`resume()` 和 `shouldPause` 构成了 Pausable Composition 的时间切片核心，其判定逻辑基于帧预算约束：

**shouldPause 回调机制**：
```kotlin
// 帧数据来源：Choreographer.FrameData.deadlineNanos
private fun shouldPause(): Boolean {
    val currentTimeNanos = System.nanoTime()
    val frameDeadline = Choreographer.getInstance().frameDeadlineNanos
    return currentTimeNanos + TIME_BUDGET_THRESHOLD > frameDeadline
}
```

**resume() 执行流程**：
1. **执行组合块**：运行一部分组合工作（如 1-2 个 item）
2. **检查时间预算**：通过 `shouldPause` 检查是否即将超时
3. **暂停决策**：
   - `shouldPause() == false`：继续执行下一块
   - `shouldPause() == true`：暂停并返回当前状态
4. **完成检查**：如果 `isComplete == true`，执行 `apply()`

**性能优化特点**：
- **时间预算控制**：预留 `TIME_BUDGET_THRESHOLD`（通常 1-2ms）作为安全缓冲
- **优先级保证**：组合工作暂停后，主线程优先处理当前帧绘制
- **平滑继续**：下一帧通过 `resume()` 继续未完成工作

### 🔹 锚点 4：与 Choreographer FrameData deadline 协作

Pausable Composition 与 Android 渲染管线中的 `Choreographer` 紧密协作，确保组合工作不干扰流畅的帧渲染：

**FrameData 时序关系**：
```
┌─────────────────┐    ┌─────────────────┐    ┌─────────────────┐
│   帧 N-1        │    │   帧 N         │    │   帧 N+1        │
│  (已渲染)       │    │  (正在渲染)    │    │  (待渲染)       │
├─────────────────┤    ├─────────────────┤    ├─────────────────┤
│ 16.67ms 完整周期│    │ 16.67ms        │    │ 16.67ms        │
└─────────────────┘    └─────────────────┘    └─────────────────┘
     ↑                       ↑                       ↑
     └─ Choreographer 触发  └─ FrameData.deadline ──┘

Pausable Composition 在帧 N 执行部分组合工作
当接近 FrameData.deadline 时，暂停等待帧 N 完成渲染
在帧 N+1 继续未完成的组合工作
```

**系统集成细节**：
- **VSync 同步**：组合暂停点与 VSync 信号对齐，避免撕裂
- **帧优先级**：组合让位给绘制，保证 60fps 流畅度
- **内存友好**：暂停时减少不必要的对象分配，降低 GC 压力

**实际应用场景**：
- **首屏加载**：复杂界面的组合工作分到多帧，避免掉帧
- **列表滚动**：预取工作被切分，不会阻塞当前帧渲染
- **状态更新**：频繁状态变化导致的重组被平滑处理

[已验证: AOSP android-17.0.0_r1, frameworks/base/services/core/java/com/android/server/wm/Choreographer.java]

### 🔹 锚点 5：LazyList 预取系统集成机制

Pausable Composition 在 LazyList 中主要用于预取机制的优化，与 `LazyLayoutPrefetchState` 和 `LazyLayoutCacheWindow` 深度集成：

**预取与 Pausable Composition 的协作路径**：
```
LazyList 滚动事件
    ↓
LazyLayoutPrefetchState.schedulePrefetch()
    ↓
SubcomposeLayout.subcompose(slotId, content)
    ↓
PausableComposition.setPausableContent { }
    ↓
resume(shouldPause) 分块执行预取组合
    ↓
检查帧 deadline，必要时暂停
    ↓
预取结果缓存到 item pool
    ↓
滚动时直接从 pool 取，无需重组
```

**LazyLayoutCacheWindow API**（Compose 1.9+）：
```kotlin
// 方式 1: Dp 单位
@OptIn(ExperimentalFoundationApi::class)
val listState = rememberLazyListState(
    cacheWindow = LazyLayoutCacheWindow(
        ahead = 150.dp,        // 预取多少个 item（固定距离）
        behind = 50.dp         // 保留多少个 item（固定距离）
    )
)

// 方式 2: viewport fraction
@OptIn(ExperimentalFoundationApi::class)

        aheadFraction = 1f,     // 预取1个 viewport 的内容
        behindFraction = 0.5f   // 保留0.5个 viewport 的内容
    )
)
```

**性能平衡策略**：
- **简单列表项**：预取窗口可以较小（1-2 个 viewport）
- **复杂列表项**：适当增大预取窗口，但注意内存开销
- **动态调整**：基于滚动速度自动调整预取范围

### 🔹 锚点 6：apply() 提交与 applyChanges() 回放

`apply()` 是 Pausable Composition 的原子性提交阶段，确保 UI 树状态的一致性：

**apply() 核心机制**：
```kotlin
public fun apply() {
    if (!isComplete) {
        throw IllegalStateException("Cannot apply incomplete composition")
    }
    
    // 原子提交所有变更到 UI 树
    synchronized(uiLock) {
        composition.updateComposedValue()
        notifyListeners()
    }
    
    isApplied = true
}
```

**applyChanges() 回放机制**：
- **增量更新**：只提交实际发生变更的部分 UI 子树
- **状态回放**：按顺序执行暂停期间记录的所有状态变化
- **对象池复用**：复用已创建的对象，减少 GC 压力

**一致性保证**：
- **原子性**：要么全部成功，要么全部回滚
- **幂等性**：重复 `apply()` 不产生副作用
- **时序正确**：确保 UI 变更与状态变更的顺序一致

### 🔹 锚点 7：1.7 vs 1.10 行为对比与突破性改进

Compose 1.7 和 1.10 在组合行为上有根本性差异，Pausable Composition 是分水岭式的改进：

**版本对比**：
| 特性 | Compose 1.7 | Compose 1.10+ | 改进价值 |
|------|-------------|---------------|----------|
| 组合连续性 | 必须同步完成 | 支持分块暂停 | 避免帧阻塞 |
| 错误传播 | 任意错误中断 | 错误隔离到块内 | 提高稳定性 |
| 内存使用 | 一次性分配 | 按需分配 | 降低 GC 压力 |
| 调试能力 | 有限信息 | 详细的 trace 信息 | 便于诊断 |

**1.7 的局限性**：
```kotlin
// 1.7: 组合必须在一帧内完成
@Composable
fun LazyColumn1_7(items: List<Item>) {
    LazyColumn {
        items(items) { item ->
            ComplexItem(item)  // 如果复杂度太高，可能掉帧
        }
    }
}
```

**1.10 的突破性改进**：
```kotlin
// 1.10: 组合可以跨帧执行，不会掉帧
@Composable
fun LazyColumn1_10(items: List<Item>) {
    LazyColumn(
        cacheWindow = LazyLayoutCacheWindow(ahead = 3.dp, behind = 1.dp)
    ) {
        items(items) { item ->
            ComplexItem(item)  // Pausable Composition 自动分块执行
        }
    }
}
```

**1.10 的关键改进**：
1. **时间切片**：长组合工作被切分成 1-2ms 的块
2. **智能暂停**：自动检测帧截止时间，适时暂停
3. **并行优化**：与 LazyPrefetch 和 Strong Skipping 协同工作
4. **工具链支持**：Android Studio 2024.2.1+ 提供 Compose Profiler

## 扩展

### 🔸 扩展点 1：复杂 UI 树的 checkpoint 设计

检查点（Checkpoint）是 Pausable Composition 的高级应用，用于精确控制复杂 UI 树的组合进度：

**Checkpoint 设计原理**：
```kotlin
// 自定义 checkpoint 设计
@Composable
fun ComplexScreenWithCheckpoints() {
    val checkpointManager = remember { CheckpointManager() }
    
    Column {
        // 顶部标题区
        HeaderSection()
        
        // 第一个 checkpoint：确保标题渲染完成
        checkpointManager.checkpoint("header_rendered")
        
        // 列表内容
        LazyColumn {
            items(items) { item ->
                CheckpointItem(item, checkpointManager) {
                    // 子 item 内部也可以设置 checkpoint
                    checkpointManager.checkpoint("item_${item.id}_loaded")
                }
            }
        }
        
        // 第二个 checkpoint：确保列表渲染完成
        checkpointManager.checkpoint("list_rendered")
        
        // 底部操作区
        FooterSection()
    }
}

class CheckpointManager {
    private val checkpoints = mutableMapOf<String, Boolean>()
    
    fun checkpoint(name: String) {
        // 只有在完成前续 checkpoint 后，才继续当前部分
        if (checkpoints.values.all { it }) {
            checkpoints[name] = true
        }
    }
}
```

**应用场景**：
- **分步加载**：先显示关键内容，逐步加载次要内容
- **内存控制**：在特定阶段释放不再需要的资源
- **性能监控**：监控各阶段组合耗时，找出瓶颈

**设计挑战**：
- **状态同步**：多个 checkpoint 之间的依赖关系
- **错误处理**：某个 checkpoint 失败时的回滚策略
- **可视化支持**：调试工具中显示 checkpoint 执行情况

### 🔸 扩展点 2：shouldPause 回调的性能开销

`shouldPause` 回调虽然带来了时间切片的优势，但也引入了额外的性能开销，需要谨慎使用：

**性能开销来源**：
```kotlin
// 回调调用的直接开销
fun shouldPauseCallback(): Boolean {
    val currentTime = System.nanoTime()    // 1. 系统调用开销
    val deadline = getFrameDeadline()     // 2. 时间计算开销
    return currentTime + 1000000 > deadline  // 3. 条件判断开销
}
```

**实际性能影响**：
- **调用频率**：每组合块执行一次，可能每帧调用 10-100 次
- **内存分配**：回调 lambda 可能导致额外的对象分配
- **JIT 优化**：重复的调用可能被 JIT 优化，但仍有成本

**优化建议**：
```kotlin
// 优化方案 1：缓存帧截止时间
@Composable
fun OptimizedPausableContent() {
    var frameDeadline by remember { mutableLongStateOf(0L) }
    
    LaunchedEffect(Unit) {
        while (true) {
            frameDeadline = Choreographer.getInstance().frameDeadlineNanos
            delay(16) // 每帧更新一次
        }
    }
    
    setPausableContent {
        // 使用缓存的 frameDeadline
        val shouldPause = remember { System.nanoTime() + 1000000 > frameDeadline }
        // ...
    }
}

// 优化方案 2：动态调整检查频率
@Composable
fun AdaptivePauseCheck() {
    var checkFrequency by remember { mutableIntStateOf(100) } // 每 N 个检查一次
    
    setPausableContent {
        var sinceLastCheck = 0
        while (!isComplete) {
            // 减少回调调用频率
            if (sinceLastCheck >= checkFrequency) {
                val shouldPause = shouldPause()
                if (shouldPause) break
                sinceLastCheck = 0
            }
            // 继续组合工作...
            sinceLastCheck++
        }
    }
}
```

**阈值策略**：
- **简单列表**：使用默认回调频率，开销可忽略
- **复杂场景**：使用缓存或动态调整策略
- **低端设备**：降低回调频率，减少性能损耗

### 🔸 扩展点 3：Compose 1.9 CacheWindow API 优化

LazyLayoutCacheWindow 是 Compose 1.9 引入的预取窗口控制 API，与 Pausable Composition 协同优化滚动性能：

**API 演进**：
```kotlin
// Compose 1.9 之前的固定预取
```

- **滚动流畅度**：减少首次可见时的组合卡顿
