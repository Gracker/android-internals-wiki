# 2.28 Compose Pausable Composition 深度分析

Pausable Composition 是 Compose Runtime 提供的一种可暂停子组合机制。它允许调用方在主组合需要某棵子树之前，分多次推进这棵子树的组合工作；全部组合完成并调用 `apply()` 后，结果才可交给布局树使用。Lazy Layout 的预取是它在 Android 上最重要的使用者。

先把范围说清楚：

- 它处理的是**子组合的准备过程**，不会把应用内任意一次重组自动切成多个帧片段。
- 它仍在 Android 主线程上执行。暂停可以缩短一次预取连续占用主线程的时间，不等于把组合搬到后台线程。
- `ShouldPauseCallback` 只提出暂停请求。运行时只能在可暂停的位置响应，返回 `true` 不保证立刻停止。
- 组合完成与结果可用是两个时刻：`isComplete == true` 之后还必须及时调用 `apply()`。
- 当前实现用 `RecordingApplier` 暂存节点操作；`apply()` 是一次性回放，不提供事务式回滚。

本章以 AndroidX Compose Runtime、Foundation、UI 1.11.4 源码为主，Android 端以 Android 17 / API 37 为平台上限。Compose 是独立发布的 Jetpack 库，库版本和 Android API Level 必须分开看。

## 1. 版本与平台边界

Pausable Composition 的 API 出现在 Runtime 1.8 系列，晚于 API 的 Foundation 默认接入不能倒推成“Runtime 1.10 才引入”。

| 版本 | 与本机制有关的变化 | 阅读结论 |
|---|---|---|
| Runtime 1.7.x | 没有公开的 `PausableComposition` API | 不能使用本章对象模型 |
| Runtime 1.8.0-alpha02 | 首次加入 Pausable Composition API | API 起点 |
| Runtime 1.8.0 | 1.8 系列稳定版 | `PausableComposition`、`PausedComposition` 可用 |
| Runtime 1.9.0 | 暴露 `isApplied`、`isCancelled` 等状态信息，并持续修复暂停组合 | 状态检查能力更完整 |
| Foundation 1.10.0-alpha05 | Lazy Layout 的 pausable prefetch 开关默认启用 | Foundation 开始默认走暂停式预取 |
| Foundation 1.10.6 | 发布说明记录因稳定性问题默认关闭该路径；同版本 Runtime 也修复相关崩溃 | 不能只凭 API 版本判断默认行为 |
| Runtime/Foundation 1.11.4 | 本章审阅时的最新稳定版；Foundation 源码中 `isPausableCompositionInPrefetchEnabled = true` | 本章的当前实现基线 |

1.11.4 的 `runtime-android` 和 `foundation-android` AAR 清单声明 `minSdkVersion 23`。因此本章在 Android 端的验证范围写为 Android 6.0 / API 23 至 Android 17 / API 37。公共接口位于 `commonMain`，机制本身并非 Android 17 平台 API；Android 17 在这里承担系统版本锚点。

1.10.6 和 1.11.0-beta01 的发布说明都包含 Pausable Composition 崩溃修复。升级 Runtime、Foundation、UI 时应保持版本对齐，并对 Lazy 列表预取做回归测试。

## 2. 对象关系：谁创建，谁推进，谁接收结果

### 2.1 `PausableComposition`

源码声明为：

```kotlin
public sealed interface PausableComposition : ReusableComposition {
    public fun setPausableContent(
        content: @Composable () -> Unit
    ): PausedComposition

    public fun setPausableContentWithReuse(
        content: @Composable () -> Unit
    ): PausedComposition
}
```

这段接口说明三个边界。

第一，`PausableComposition` 继承 `ReusableComposition`，没有继承 `CompositionImpl`。工厂函数的返回类型是接口，当前工厂实现才返回 `CompositionImpl(parent, applier)`：

```kotlin
public fun PausableComposition(
    applier: Applier<*>,
    parent: CompositionContext,
): PausableComposition = CompositionImpl(parent, applier)
```

第二，暂停式内容必须通过 `setPausableContent()` 或 `setPausableContentWithReuse()` 创建。对同一对象调用普通的 `setContent()` 或 `setContentWithReuse()`，组合会按非暂停方式工作；存在尚未应用的暂停组合时，这样调用还会抛异常。

第三，这是面向 Compose 基础设施的低层接口。普通业务代码通常拿不到合适的 `Applier` 和父 `CompositionContext`，也无需自行驱动它。Foundation 和 `SubcomposeLayout` 已经封装了列表预取所需的对象管理。

### 2.2 `PausedComposition`

`setPausableContent*()` 返回一个初始处于暂停状态的 `PausedComposition`。创建对象时不会执行 `content`，第一次 `resume()` 才开始初始组合。

```kotlin
public sealed interface PausedComposition {
    public val isComplete: Boolean
    public val isApplied: Boolean
    public val isCancelled: Boolean

    public fun resume(
        shouldPause: ShouldPauseCallback
    ): Boolean

    public fun apply()
    public fun cancel()
}
```

调用方的职责可归纳为：

1. 重复调用 `resume()`，直到返回 `true` 或 `isComplete` 为 `true`。
2. 再检查一次 `isComplete`，确认其没有因 Snapshot 状态变化退回未完成。
3. 同步、及时地调用 `apply()`。
4. 若预取请求失效且整个 composition 将被废弃，调用 `cancel()` 并丢弃原 composition。

### 2.3 `SubcomposeLayoutState.PausedPrecomposition`

Compose UI 在 Runtime 接口外又包了一层适合布局系统的抽象：

```kotlin
val paused = subcomposeLayoutState.createPausedPrecomposition(
    slotId = key,
    content = itemContent
)
```

`PausedPrecomposition.resume()` 继续组合，`apply()` 返回 `PrecomposedSlotHandle`。后者可查询 slot 产生的 placeable 数量、提前测量每个 placeable、遍历嵌套预取节点，或在请求失效时释放预组合内容。

因此 Lazy Layout 使用的是由 `SubcomposeLayout` 管理的预组合 slot 和对应 handle，不能笼统理解为“item pool”。

## 3. 生命周期与内部状态机

Runtime 1.11.4 的 `PausedCompositionImpl` 使用以下内部状态：

```text
InitialPending
    │ 第一次 resume：composeInitialPaused()
    ▼
RecomposePending
    │ 仍有 invalidScopes
    ▼
Recomposing
    │ recomposePaused() 返回
    └──────────────► RecomposePending
                         │ invalidScopes 为空
                         ▼
                    ApplyPending
                         │ applyChanges()
                         ▼
                       Applied

任一 resume/apply 异常 ──► Invalid
放弃结果并 cancel() ─────► Cancelled
ApplyPending 期间读到的状态失效 ──► RecomposePending
```

第一次 `resume()` 调用 `composeInitialPaused()`。如果仍有需要处理的 `RecomposeScopeImpl`，对象停在 `RecomposePending`；后续 `resume()` 通过 `recomposePaused()` 继续。`invalidScopes` 为空时才进入 `ApplyPending`，此时 `isComplete` 为 `true`。

状态机也限制了错误用法：

- `resume()` 完成后再次调用会抛异常；
- 未完成时调用 `apply()` 会抛异常；
- `apply()` 成功后再次调用任何推进方法会抛异常；
- `cancel()` 后继续使用该对象会抛异常；
- `resume()` 或 `apply()` 内部抛出的异常会把对象标记为 `Invalid`。

这组限制表明 `apply()` 不是幂等 API。调用者应把 `PausedComposition` 当成一次性任务句柄。

## 4. `resume()` 如何响应暂停请求

`ShouldPauseCallback` 是一个无参数函数接口：

```kotlin
public fun interface ShouldPauseCallback {
    public fun shouldPause(): Boolean
}
```

官方接口文档强调两点：

- 回调会被频繁调用，计算必须足够简单；
- 返回 `true` 只是请求暂停，并非强制中断；并非所有 Composable 函数都可暂停。

这意味着“每组合一两个 item 检查一次”或“固定执行 1–2 ms 后暂停”都不是 Runtime 契约。暂停点由 Compose 编译器与 Runtime 的可暂停组合路径共同决定，业务 Composable 没有公开的 checkpoint API。

调用方也不能在回调内执行 I/O、分配大量对象或读写复杂状态。Foundation 的回调只更新耗时估计、扣减本轮剩余预算并返回一个布尔值。回调自身越重，留给组合的时间越少，预算估计也越容易失真。

## 5. 组合期间记录了什么

### 5.1 `RecordingApplier` 隔离未完成的节点操作

普通组合通过 `Applier` 对目标树执行 `down`、`up`、插入、移动、删除和属性更新。暂停组合把这些操作先写入 `RecordingApplier`：

```text
DOWN / UP
INSERT_TOP_DOWN / INSERT_BOTTOM_UP
REMOVE / MOVE / CLEAR
APPLY / REUSE
```

因此暂停时可能已经创建对象并产生 Compose 内部状态，但这些节点操作尚未回放到目标 `Applier`。官方契约要求在 `isComplete == true` 且 `apply()` 完成之前，不得把结果加入布局树或参与放置。

这项设计保证未完成子树不会作为可用预组合结果交给布局阶段。它没有承诺降低分配量，也没有承诺减少 GC；预组合会提前消耗 CPU 和内存，收益来自把未来可能阻塞可见帧的工作移到帧间空档。

### 5.2 `apply()` 的真实顺序

`PausedCompositionImpl.applyChanges()` 在 composition 的锁内执行：

1. `RecordingApplier.playTo(realApplier, rememberManager)`；
2. 分发 `RememberObserver` 回调；
3. 分发 `SideEffect`；
4. 在 `finally` 中处理 abandon 集合并通知 composition 暂停任务结束。

`playTo()` 以 `onBeginChanges()` 开始，按录制顺序调用真实 `Applier`，最后执行 `onEndChanges()`。成功后录制列表会清空。

这里不能套用数据库事务语义。若回放中途抛异常，前面已经执行的真实 `Applier` 操作没有通用回滚路径；Runtime 会包装异常，并将 `PausedComposition` 标记为 `Invalid`。所以旧有论述中的“失败全部回滚”和“重复 apply 无副作用”均不成立。

## 6. Snapshot 变化为何会让完成态退回

暂停组合可能读取 `State`。如果 `resume()` 返回完成之后、`apply()` 之前，被读取的状态发生变化，Runtime 会把内部状态从 `ApplyPending` 改回 `RecomposePending`。此时 `isComplete` 会重新变成 `false`。

安全的驱动方式是：

```kotlin
while (!paused.isComplete) {
    paused.resume(shouldPause)
}

// apply 前再读一次；若状态失效，继续 resume。
if (paused.isComplete) {
    paused.apply()
}
```

这段代码用于说明调用顺序，不是业务层直接创建 Pausable Composition 的建议。生产实现还要处理请求取消、宿主生命周期和异常。官方文档要求完成后同步且尽快 `apply()`，目的就是缩短状态再次失效的窗口。

`cancel()` 也有严格边界：取消后，用来创建该 `PausedComposition` 的 composition 处于不确定状态，必须丢弃。它不能作为“稍后继续”的暂停按钮。

## 7. Lazy Layout 预取的完整链路

在 Foundation 1.11.4 中，一次 Lazy item 预取可能跨越多次调度，按以下阶段推进：

```text
滚动策略选出 index
    │
    ▼
LazyLayoutPrefetchState 创建请求
    │
    ├─ 校验 index、key、contentType
    ├─ 读取该 contentType 的历史平均耗时
    │
    ▼
createPausedPrecomposition(key, content)
    │
    ├─ resume / 请求暂停 / 下次继续
    │
    ▼
PausedPrecomposition.apply()
    │
    ▼
PrecomposedSlotHandle
    │
    ├─ 发现并调度嵌套 LazyLayout 预取
    └─ premeasure(placeable, constraints)
```

### 7.1 时间估计按 `contentType` 区分

请求先通过 `itemProvider.getContentType(index)` 取得类型，再从 `PrefetchMetrics` 获取对应平均值。1.11.4 分别记录：

- 完整组合耗时；
- 一次 resume 耗时；
- 响应暂停所需耗时；
- apply 耗时；
- measure 耗时；
- 嵌套预取数量。

为异构列表提供稳定的 `contentType`，可以避免把标题、图片卡片、分隔项等成本差异很大的内容混入同一组估计。稳定 `key` 则用于识别 index 背后的数据是否已变化；key 不匹配时，旧请求会被清理。

### 7.2 暂停判断使用历史平均值

普通优先级请求只有在：

```text
availableTimeNanos > averageResumeTime + averagePauseTime
```

时才尝试继续暂停组合。进入 `resume()` 后，回调更新本次实际耗时和剩余预算，再决定是否请求暂停。

紧急请求把预计所需时间视为 0，只要当前仍有正的剩余时间就可开始工作。它提高了即将可见 item 的优先级，但不会在剩余时间已经为 0 时强行执行。

### 7.3 完成组合后仍有 apply 和 measure

`pausedPrecomposition.isComplete` 只说明组合阶段结束。请求还要在预算允许时执行 `performApply()`，得到 `PrecomposedSlotHandle`，之后解析嵌套预取并进行 premeasure。

所以 Perfetto 中看到 `compose` 阶段完成，不能据此判断整个预取请求已经完成。item 即将进入视口却尚未 measure 时，可见帧仍可能承担剩余工作。

### 7.4 请求失效时如何清理

以下情况会使预取结果失去价值：

- Lazy state 已不活跃；
- index 越界；
- 相同 index 对应的 key 已变化；
- 滚动方向改变或策略取消请求；
- slot 已无近期使用可能。

清理路径会取消尚未应用的 `PausedPrecomposition`，或释放已经得到的 `PrecomposedSlotHandle`。这也是业务层需要稳定 key 的另一个原因：不稳定 key 会制造更多无效预取和丢弃工作。

## 8. Android 端如何计算本轮预算

`PrefetchScheduler.android.kt` 的实现没有读取 `Choreographer.FrameData.deadlineNanos`。它使用 `View` 与 `Choreographer` 估算下一帧开始时间：

```kotlin
val viewDrawTimeNanos =
    TimeUnit.MILLISECONDS.toNanos(view.drawingTime)

nextFrameTimeNs =
    maxOf(frameStartTimeNanos, viewDrawTimeNanos) +
        frameIntervalNs

availableTimeNanos =
    max(0, nextFrameTimeNs - System.nanoTime())
```

各变量来自：

- `frameStartTimeNanos`：上一轮 `Choreographer.FrameCallback#doFrame()` 的时间；
- `view.drawingTime`：View 最近一次绘制时间，毫秒转纳秒；
- `frameIntervalNs`：进程内首次初始化 scheduler 时读取 `Display.refreshRate` 后换算，并缓存在 companion object；显示数据无效或低于 30 Hz 时按 60 Hz 处理。

如果本轮预算不足，scheduler 通过 `postFrameCallback()` 等到下一帧，在 `doFrame()` 中记录帧时间，再用 `view.post(this)` 把预取任务放回主线程队列。

若 View 已经超过两个帧间隔没有绘制，scheduler 把当前时段视为 idle，并让 `availableTimeNanos()` 返回 `Long.MAX_VALUE`。这允许空闲时尽快处理积压预取。窗口不可见、View 未附着或请求队列为空时则停止执行。

有三个工程结论：

1. Pausable prefetch 仍与绘制共享主线程，重型 Composable 仍可能造成卡顿。
2. 预算使用进程内首次初始化 scheduler 时取得的显示刷新率，不会在每次暂停时查询 FrameTimeline deadline，也不会在这段实现中重新读取刷新率。
3. 在 60 Hz、90 Hz、120 Hz 和 Android 17 可变刷新率设备上都应采集 trace；只在固定 60 Hz 模拟器上验证不够。

## 9. `LazyLayoutCacheWindow` 与暂停机制的分工

`LazyLayoutCacheWindow` 决定前方准备范围和后方保留范围。Pausable Composition 决定其中一次预组合怎样在预算内推进。前者是“准备多少”，后者是“怎样分段执行”，两者不能互相替代。

1.11.4 提供两种实验性构造方式：

```kotlin
LazyLayoutCacheWindow(
    ahead: Dp = 0.dp,
    behind: Dp = 0.dp,
)

LazyLayoutCacheWindow(
    aheadFraction: Float = 0f,
    behindFraction: Float = 0f,
)
```

`Dp` 表示滚动轴上的物理布局距离，经 `Density` 转成像素，不表示 item 数量。fraction 表示 viewport 尺寸的比例。

下面的代码展示了正确的 API 挂载位置：

```kotlin
@OptIn(ExperimentalFoundationApi::class)
@Composable
fun MessageList(messages: List<Message>) {
    val state = rememberLazyListState(
        cacheWindow = LazyLayoutCacheWindow(
            aheadFraction = 1.0f,
            behindFraction = 0.5f,
        )
    )

    LazyColumn(state = state) {
        items(
            items = messages,
            key = { it.id },
            contentType = { it.kind },
        ) { message ->
            MessageRow(message)
        }
    }
}
```

这里的 `1.0f` 和 `0.5f` 只用于说明单位。窗口增大通常会提前准备更多内容，也会占用更多 CPU、节点和图片等资源；窗口过小则可能来不及覆盖快速滚动。参数应通过目标设备上的滚动 trace、内存曲线和业务命中率确定，不宜按“简单列表几个 item、复杂列表几个 item”套固定值。

## 10. Perfetto 中怎样验证

Foundation 1.11.4 为预取路径写入了可直接检索的 trace 名称：

- `compose:lazy:schedule_prefetch:index`
- `compose:lazy:prefetch:available_time_nanos`
- `compose:lazy:prefetch:execute:item`
- `compose:lazy:prefetch:execute:urgent`
- `compose:lazy:prefetch:compose`
- `compose:lazy:prefetch:apply`
- `compose:lazy:prefetch:resolve-nested`
- `compose:lazy:prefetch:measure`
- `compose:lazy:prefetch:idle_frame`

建议把排查分成四步：

1. 先看预取工作是否落在 UI 主线程，以及它与 `Choreographer#doFrame`、measure/layout/draw 的相对位置。
2. 对照 `available_time_nanos`，确认请求因预算不足分段，还是一次 `resume()` 内已有不可暂停的长段。
3. 按 item index 和 `contentType` 区分偶发重型 item，检查 key 是否频繁变化。
4. 分别统计 compose、apply、nested、measure；不要把整段耗时都归因于 Runtime 的组合阶段。

如果 `compose:lazy:prefetch:compose` 单段已经跨过帧边界，优先检查 item 内同步 I/O、大图解码、复杂对象构造以及长时间不可暂停的 Composable 调用。Pausable Composition 只能在运行时允许的位置交还控制权，无法修复 Composable 内部的阻塞调用。

## 11. 常见误解

### 11.1 “开启后，普通页面的首次组合会自动跨帧”

公共机制只在调用方创建并驱动暂停子组合时生效。当前主要集成点是 Lazy Layout 预取。普通 `setContent` 和正常重组仍走各自路径。

### 11.2 “`shouldPause()` 返回 true 就会立即停”

它是协作式请求。运行时到达可暂停位置后才能返回，回调本身也应保持轻量。

### 11.3 “暂停靠 Choreographer 的精确 deadline”

Foundation 1.11.4 Android scheduler 使用最近绘制时间、`doFrame` 时间和显示刷新率估算下一帧时刻，没有调用 `FrameData.deadlineNanos`。

### 11.4 “`isComplete` 为 true 后可以稍后 apply”

等待期间 Snapshot 状态可能变化，使对象退回未完成。完成后应重新检查并及时 apply。

### 11.5 “apply 可重复调用，失败会回滚”

重复 apply 会抛异常；回放中途失败没有通用回滚保证，对象会进入 `Invalid`。

### 11.6 “取消后保留 composition，下次继续”

官方契约要求取消后丢弃创建它的 composition。需要继续时应重新创建预组合任务。

### 11.7 “CacheWindow 的 Dp 数值代表 item 数”

Dp 会转换为滚动方向上的像素距离。item 高度不同，同一窗口覆盖的 item 数也不同。

## 12. 面向应用工程的使用建议

大多数应用无需直接调用 `PausableComposition()`。更有效的控制点是：

- 为 Lazy item 提供稳定且唯一的 `key`；
- 用 `contentType` 区分成本差异明显的 item；
- 避免在 Composable 中执行同步 I/O、图片解码和大对象构造；
- 只在有测量数据时调整实验性的 `LazyLayoutCacheWindow`；
- Runtime、UI、Foundation 使用同一 Compose 版本线；
- 升级到包含暂停组合修复的补丁版本，并覆盖快速滚动、方向反转、数据刷新、嵌套 Lazy Layout、item 动画和宿主销毁等场景；
- 在 Android 17 的 60/90/120 Hz 与可变刷新率设备上对照 Perfetto 主线程轨迹。

Pausable Composition 的价值边界很具体：它让支持该能力的子组合可以在帧间预算内逐步准备，并在完成后一次性转交给布局系统。它不会替代稳定 key、轻量 item、正确的状态建模和基于 trace 的性能分析。
