# 2.51 Android 17 GPU Trace 数据源与 Trace Processor 证据链

Perfetto 里出现一条 GPU 轨道，并不表示 Android 平台掌握了 GPU 的全部执行细节。GPU 渲染阶段、硬件计数器、频率、内存、Vulkan 分配和 SurfaceFlinger FrameTimeline 分别来自不同的数据生产方；设备驱动没有提供某类数据时，Perfetto 只能留下空白。

这里梳理 GPU 数据从生产方进入 `TracePacket`，再由 Android 17 对应的 Trace Processor 解析成 SQL 表的过程。工具选择与完整排查顺序见 2.15，SurfaceFlinger 的 FrameTracer、TimeStats 与卡顿统计见 2.52。源码结论按 Android 17 / API 37 的 `android-17.0.0_r1`、对应的 Perfetto 版本及 `android17-6.18-2026-06_r6` 内核标签核对。

分析前应区分四组边界：

1. 数据源名、Trace Processor 表名和 UI 轨道名不是同一个概念；
2. `gpu.renderstages` 与 `gpu.counters` 需要 GPU 数据生产方支持，Android 17 版本号不能保证设备有数据；
3. GPU 频率、硬件计数器和渲染阶段回答不同问题，任何一项都不能单独证明瓶颈位于 GPU；
4. 用户可见帧还要经过生产方围栏、BufferQueue、SurfaceFlinger、HWC 与显示提交，GPU 任务结束不等于画面已经上屏。

## 1. GPU 跟踪数据的四层结构

Perfetto GPU 数据可分为四层：

```text
数据生产方
  ├─ 内核 / 厂商 GPU 驱动
  ├─ Android GpuService
  ├─ Vulkan 跟踪层
  └─ SurfaceFlinger / 应用插桩
        ↓
TracePacket 协议
  ├─ GpuRenderStageEvent
  ├─ GpuCounterEvent
  ├─ GpuMemTotalEvent
  ├─ VulkanMemoryEvent
  └─ FrameTimeline / GraphicsFrameEvent
        ↓
Trace Processor 解析器
        ↓
`slice` / `counter` / `track` + `gpu_slice` / `gpu_counter_track` / 标准库表
```

这张图区分数据来源与最终落表位置。Trace Processor 能解析某种 proto，只代表文件格式受支持；目标设备仍要注册相应的数据生产方并发出数据。

## 2. 采集前先查询设备能力

下面的命令用于查看当前设备向跟踪服务注册的数据源及其描述符：

```bash
adb shell perfetto --query --long
```

检查输出中是否存在 `gpu.counters`、`gpu.renderstages`、`android.gpu.memory`、`vulkan.memory_tracker` 等名字。`gpu.counters` 的描述符还应给出计数器编号、名称、单位、采样周期和计数器块约束。没有描述符时，不要从其他机型复制计数器编号。

内核 ftrace 事件也要在设备上确认。下面的命令用于核对 GPU 内存与频率事件：

```bash
adb shell 'cat /sys/kernel/tracing/available_events 2>/dev/null | grep -E "gpu_mem_total|gpu_frequency"'
```

量产设备可能限制读取跟踪文件系统。命令无输出可能源于事件不存在或权限不足，需要结合 `perfetto --query --long`、系统构建类型和采集日志判断。

### 2.1 Android 17 常见 GPU 数据入口

| 数据入口 | 主要内容 | 谁负责提供 | 关键限制 |
|---|---|---|---|
| `gpu.renderstages` | GPU 队列上的阶段切片 | GPU/驱动数据生产方 | 阶段名称和粒度由数据生产方定义 |
| `gpu.counters` | 设备硬件计数器 | GPU/驱动数据生产方 | 编号、单位、容量和采样方式因设备而异 |
| `power/gpu_frequency` | GPU DVFS 频率变化 | 内核/厂商跟踪点 | Android 通用内核不保证存在 |
| `android.gpu.memory` | 跟踪开始时的全局/进程 GPU 内存快照 | Android GpuService | 依赖 `gpu_mem_total` 与 eBPF 初始化 |
| `gpu_mem/gpu_mem_total` | GPU 可寻址内存总量更新 | GPU 驱动 + ftrace | 总量不是分配对象清单 |
| `vulkan.memory_tracker` | Vulkan 驱动、设备、缓冲区与图像的分配事件 | Vulkan 跟踪层 | 不覆盖 GLES 和全部厂商内部内存 |
| GPU 日志数据包 | 数据生产方上报的级别、标签和消息 | GPU 数据生产方 | 不是完整的内核或驱动日志 |
| FrameTimeline / FrameTracer | 截止时间、卡顿、图层缓冲区与围栏 | SurfaceFlinger | 不等于应用的 GPU 命令时间线 |

Android 17 对应的 Perfetto `DataSourceConfig` 已定义 `gpu.renderstages`、`gpu.counters` 与 Vulkan 内存配置。配置字段存在不代表设备实现了相应的数据生产方。

## 3. `gpu.renderstages`：GPU 执行阶段

### 3.1 一个阶段事件包含什么

Android 17 的 `GpuRenderStageEvent` 可携带：

- 事件编号与持续时间；
- GPU id；
- 硬件队列定义；
- 阶段定义；
- 图形上下文；
- 渲染目标与可选调试名称；
- 提交编号；
- Vulkan 渲染通道、渲染通道实例与子通道掩码；
- Vulkan 命令缓冲区句柄与可选调试名称；
- 数据生产方自定义的附加数据。

硬件队列和阶段名称来自数据生产方发出的定义。Trace Processor 不会自行推断“顶点”“片段”“分块”或“计算”等名称的硬件含义。

### 3.2 阶段事件不记录每个绘制调用

`GpuRenderStageEvent` 描述数据生产方选定的一段 GPU 工作。它可以覆盖整个工作负载，也可以按渲染通道、加载/存储、分块、渲染、计算等阶段拆分。粒度取决于 GPU 数据生产方、配置和驱动能力。

因此，一条 `gpu_slice` 不能自动给出：

- 绘制调用数量；
- 每条着色器指令的耗时；
- 过度绘制热力图；
- 缓存未命中的根因；
- 某个纹理或流水线状态的完整内容。

这些问题需要帧捕获、硬件计数器或厂商分析器。

### 3.3 Android 17 配置里的低开销模式

Android 17 对应的 `GpuRenderStagesConfig` 包含：

- `full_loadstore`：把颜色与深度/模板的加载和存储拆得更细；
- `low_overhead`：把多个渲染阶段合并成工作负载阶段；
- `trace_metrics`：请求数据生产方支持的逐阶段指标。

当 `low_overhead=true` 时，`full_loadstore` 不生效。下面的配置先采集粗粒度 GPU 工作负载，适合初步缩小时间窗口：

```textproto
data_sources {
  config {
    name: "gpu.renderstages"
    gpu_renderstages_config {
      low_overhead: true
    }
  }
}
```

设备没有注册该数据生产方时，配置仍可能成功完成，但跟踪结果中不会出现渲染阶段数据。详细模式会增加 GPU 或驱动侧的观测成本，应在固定复现场景后短时使用。

### 3.4 `submission_id` 的关联能力

proto 对 `submission_id` 的建议语义如下：

- OpenGL：对应一次 API 提交，例如 `glFlush`、`glFinish` 或 `eglSwapBuffers`；
- Vulkan：与一次 `vkQueueSubmit` 一一对应。

这个字段可选，并由数据生产方生成。它不是 FrameTimeline 令牌、BufferQueue 帧号或 SurfaceFlinger 图层序号。只有跟踪数据同时包含 CPU 提交事件和相同的提交编号，才能可靠关联 CPU 与 GPU；字段缺失时，只能借助上下文、进程、队列、时间窗口和应用标记收窄候选范围。

## 4. `gpu.counters`：硬件计数器

### 4.1 描述符决定计数器数值的含义

`GpuCounterDescriptor.GpuCounterSpec` 为每个计数器描述：

- `counter_id`；
- 名称与说明；
- 分子/分母单位；
- 可选峰值；
- 是否建议默认选择；
- 所属分组，例如顶点、片段、内存、计算、光线追踪。

同一个“GPU active”名称在不同厂商、不同 GPU 世代上的采样口径也可能不同。报告必须保留描述符、GPU/驱动版本和工具版本，不能套用跨设备固定阈值表。

### 4.2 计数器块限制同时启用的数量

描述符还可以声明 `GpuCounterBlock`：

- 块编号与名称；
- 块容量；
- 该块包含的计数器编号。

如果一个块的容量小于待采集计数器的数量，数据生产方可能拒绝配置、只启用子集或采用多路复用。一次请求大量计数器会增加开销，也可能降低采样可靠性。

### 4.3 采样周期与插桩采样

`GpuCounterConfig` 支持：

- `counter_period_ns`；
- 计数器编号列表；
- `instrumented_sampling`；
- `fix_gpu_clock`。

数据生产方的描述符可声明最小/最大采样周期，以及是否支持命令缓冲区插桩。采样越密，数据量与观测成本通常越高。`fix_gpu_clock` 会改变 DVFS 条件，只适合受控对照，所得结果不能代表量产默认性能。

### 4.4 Trace Processor 会处理“回看型”数值

Android 17 的 `GpuEventParser::PushGpuCounterValue()` 注释说明：GPU 计数器事件报告的是当前时间戳之前区间内生效的值，普通 Perfetto 计数器通常从当前时间戳向后生效。解析器会插入当前点，并把数值回填到前一条计数器记录。

据此分析时：

- 分析计数器时应按时间区间加权；
- 跟踪末尾的一个点没有后续样本封闭其区间；
- 直接对所有 `counter.value` 做平均容易得到错误结论；
- 优先使用区间模块，或自行用 `LEAD(ts)` 计算持续时间。

### 4.5 计数器不能代替 GPU 时间线

一个时间窗口内的内存带宽或片段计数器很高，只能说明该计数器在窗口内发生了相应变化。要把它归因给目标应用，还要同时满足：

- 目标 GPU 队列和阶段与应用上下文一致；
- CPU 提交与 GPU 阶段的时间对应；
- 该窗口覆盖目标帧，而非 SurfaceFlinger CLIENT 合成或其他进程；
- 单变量对照中，阶段持续时间与计数器同向变化。

## 5. GPU 频率：频率不等于利用率

Perfetto 官方 GPU 文档给出的频率入口是 ftrace 事件：

```text
power/gpu_frequency
```

Android 17 对应的通用内核 `android17-6.18-2026-06_r6` 没有定义这个跟踪点，通常由具体 GPU 或厂商内核补充。因此，同为 Android 17 的两台设备可能只有一台存在 `gpufreq` 轨道。

频率变化只能说明 DVFS 选择：

- 高频时 GPU 可能繁忙，也可能被策略提前拉升；
- 低频时 GPU 可能负载很轻，也可能受温度或功耗限制；
- 频率不变时，GPU 忙碌率、ALU、纹理和带宽压力仍可变化。

Android 17 对应的 Perfetto 标准库提供 `android.gpu.frequency` 模块。下面的 SQL 把名为 `gpufreq` 的计数器转换成带持续时间的频率区间：

```sql
INCLUDE PERFETTO MODULE android.gpu.frequency;

SELECT
  ts / 1e6 AS ts_ms,
  dur / 1e6 AS dur_ms,
  gpu_id,
  gpu_freq,
  prev_gpu_freq,
  next_gpu_freq
FROM android_gpu_frequency
ORDER BY ts;
```

模块没有返回数据时，先确认跟踪数据中是否存在名称为 `gpufreq` 的 `gpu_counter_track`，再检查设备事件和采集配置。

## 6. GPU 内存：区分总量、分配与物理驻留

### 6.1 `gpu_mem_total` 报告当前总量

内核 `gpu_mem_total` 跟踪点的契约是：GPU 驱动在 GPU 可寻址空间发生分配、释放、导入或取消导入时，上报：

- GPU id；
- pid，`0` 表示全局总量；
- 当前总大小，单位为字节。

这里的 `size` 是更新后的总量，不是本次分配的增量。它也不直接等于：

- 进程 Java/原生堆；
- 物理显存或系统内存的唯一驻留量；
- dma-buf 对象数量；
- 当前内存带宽；
- 可以定位到调用栈的泄漏对象。

### 6.2 AOSP GpuService 提供跟踪起点快照

Android 17 的 `GpuMem` 将 eBPF 程序附加到 `gpu_mem/gpu_mem_total`，维护全局和进程总量映射。`GpuMemTracer` 注册 `android.gpu.memory` 数据源；跟踪开始时遍历映射，发出一组 `GpuMemTotalEvent` 作为计数器初值。

后续变化仍来自驱动发出的 `gpu_mem_total` 事件。完整时间线同时依赖初始快照和后续 ftrace 更新。驱动不发事件、BPF 初始化失败或权限受限时，内存轨道会缺失或不完整。

下面的配置用于采集 AOSP GPU 内存初值和后续事件：

```textproto
data_sources {
  config {
    name: "android.gpu.memory"
  }
}

data_sources {
  config {
    name: "linux.ftrace"
    ftrace_config {
      ftrace_events: "gpu_mem/gpu_mem_total"
    }
  }
}
```

这段配置不包含调度、FrameTimeline 或 GPU 阶段。实际诊断还要按问题加入应用线程、SurfaceFlinger 和目标 GPU 数据生产方，避免只得到内存轨道。

### 6.3 Vulkan 内存跟踪器的覆盖范围

`VulkanMemoryEvent` 可以记录驱动分配范围、设备内存、缓冲区和图像的创建、销毁与绑定，以及内存类型、堆、句柄和注释。它适合解释 Vulkan 分配的生命周期。

它不覆盖：

- 原生 GLES 驱动的完整分配；
- ANGLE 或引擎之外的所有厂商私有池；
- HWC、Camera、Codec 与其他进程的全部 dma-buf；
- 内核回收、IOMMU 映射和物理页生命周期的完整细节。

内存结论应结合 `gpu_mem_total`、Vulkan 分配、dma-buf 统计、进程生命周期和厂商工具。

## 7. Trace Processor 表怎么读

### 7.1 `gpu_slice` 不只包含渲染阶段

Android 17 的 `gpu_slice` 是一个视图，它从通用 `slice` 表筛选三类轨道：

- `gpu_render_stage`；
- `vulkan_events`；
- `gpu_log`。

直接执行 `SELECT * FROM gpu_slice` 会混入 Vulkan 提交事件和 GPU 日志。下面的 SQL 只查看渲染阶段：

```sql
SELECT
  s.ts / 1e6 AS ts_ms,
  s.dur / 1e6 AS dur_ms,
  p.name AS process_name,
  t.name AS hardware_queue,
  s.name AS stage_name,
  s.submission_id,
  s.context_id,
  s.render_pass,
  s.command_buffer
FROM gpu_slice AS s
JOIN track AS t
  ON s.track_id = t.id
LEFT JOIN process AS p
  ON s.upid = p.upid
WHERE t.type = 'gpu_render_stage'
ORDER BY s.ts;
```

结果中的阶段名与队列名由数据生产方的定义决定。`submission_id`、渲染通道和命令缓冲区都可能为空，SQL 不能用空值构造不存在的关联。

### 7.2 `gpu_counter_track` 保存描述符语义

下面的 SQL 列出 GPU 计数器样本及其轨道元数据：

```sql
SELECT
  c.ts / 1e6 AS ts_ms,
  t.gpu_id,
  t.name AS counter_name,
  t.unit,
  c.value
FROM counter AS c
JOIN gpu_counter_track AS t
  ON c.track_id = t.id
ORDER BY c.ts, t.name;
```

这段查询用于核对原始样本。计算利用率、平均频率或带宽时，还要转换为带持续时间的区间，并处理跟踪边界。

### 7.3 用标准库查询进程 GPU 内存

下面的 SQL 读取带持续时间的进程 GPU 内存：

```sql
INCLUDE PERFETTO MODULE android.gpu.memory;

SELECT
  m.ts / 1e6 AS ts_ms,
  m.dur / 1e6 AS dur_ms,
  p.name AS process_name,
  m.gpu_memory
FROM android_gpu_memory_per_process AS m
JOIN process AS p
  USING (upid)
ORDER BY m.ts;
```

表为空时，应逐层检查 `android.gpu.memory` 初始快照、`gpu_mem_total` 事件和驱动上报契约。

## 8. 把 GPU 数据放回一帧的显示路径

### 8.1 原生图形与游戏应从自身的生产线程开始

原生图形应用和游戏的主体画面常由渲染/RHI 线程通过 EGL 或 Vulkan 提交到独立 Surface。普通 HWUI RenderThread 可能只绘制宿主外壳。

每帧至少要区分：

```text
input / game logic
  → render preparation
  → API submission
  → GPU queue execution
  → producer completion fence
  → queueBuffer / present
  → SurfaceFlinger latch
  → HWC or RenderEngine composition
  → display present
```

这条顺序用于判断相邻证据所属的阶段。`eglSwapBuffers()`、`vkAcquireNextImageKHR()` 或 `vkQueuePresentKHR()` 的长切片可能包含空闲槽位等待、释放围栏、交换间隔、驱动刷新或主动帧节奏控制，不能直接归因为 GPU 着色器缓慢。

### 8.2 区分应用 GPU 与 SurfaceFlinger GPU

一个游戏缓冲区可以先由应用 GPU 渲染，再由 HWC 以 DEVICE 合成方式直接扫描输出。此时 SurfaceFlinger 没有 CLIENT 合成，瓶颈仍可能位于应用的 GPU 工作。

另一种情况是应用缓冲区很早就已就绪，但 SurfaceFlinger 需要 RenderEngine 完成 CLIENT 合成。GPU 跟踪数据后半段的工作负载属于 SurfaceFlinger，不能全部计入应用。

判断时检查：

- 渲染阶段对应的进程和上下文；
- 应用提交与生产方围栏；
- SurfaceFlinger 合成类型；
- RenderEngine GPU 工作；
- HWC 提交与显示围栏。

### 8.3 FrameTimeline 只负责帧计划与分类

FrameTimeline 可判断应用与 SurfaceFlinger 的预期时间线和实际时间线是否偏离，并给出卡顿分类。它不提供着色器、渲染通道或硬件计数器信息。

独立 SurfaceView 或原生 Surface 还可能缺少完整的应用 FrameTimeline。此时要用目标图层、缓冲区帧号、FrameTracer、获取围栏、HWC 提交和显示围栏补齐证据。宿主 Activity 的令牌不能代替游戏交换链的帧编号。

## 9. 一套低扰动到高粒度的排查顺序

### 第一步：固定测试条件

记录设备、系统构建版本、GPU、驱动、刷新率、分辨率、画质、引擎、图形 API、帧节奏、温度、游戏模式和持续运行时间。

### 第二步：查询数据源

保存 `perfetto --query --long` 输出和可用的 ftrace 事件。确认设备能够提供的证据后，再编写 TraceConfig。

### 第三步：低扰动找到问题窗口

先采集调度信息、应用标记、FrameTimeline、FrameTracer、BufferQueue、频率、内存及低开销渲染阶段数据，定位具体进程、Surface 和连续异常帧。

### 第四步：重建逐帧顺序

对齐 CPU 提交、GPU 阶段、生产方围栏、入队、锁存和显示提交。GPU 阶段偏晚只是一项候选原因；如果 CPU 提交已经延迟，应先处理 CPU 依赖。

### 第五步：短时加入计数器或详细阶段

根据设备描述符选择少量计数器。每次只验证一个假设，例如：

- 降低渲染比例是否缩短 GPU 阶段；
- 关闭一个后处理通道是否降低带宽或片段指标；
- 预热流水线缓存是否消除同步编译造成的长帧；
- 限制在途帧数量是否降低输入到显示的延迟。

### 第六步：需要资源级证据时进行帧捕获

Perfetto 将问题定位到某个 GPU 窗口后，再用 AGI、RenderDoc、Sokatoa 或厂商分析器检查绘制调用、着色器、流水线、纹理和微架构计数器。帧捕获会改变时序，不能替代原始系统跟踪。

### 第七步：恢复量产配置并复测

关闭固定时钟、插桩、强制合成和调试层。使用量产配置重复多轮，比较帧耗时分布、GPU 窗口、输入延迟、温度和功耗。

## 10. 现象与证据门槛

| 现象 | 可以先怀疑 | 还需要的证据 |
|---|---|---|
| CPU 提交早，GPU 阶段跨过截止时间 | 应用 GPU 工作负载或驱动队列 | 上下文/进程、生产方围栏、单变量对照 |
| GPU 频率长时间高 | DVFS 选择高频 | 忙碌率/阶段/计数器、温度与策略 |
| GPU 频率低且阶段变长 | 温度/功耗限制或负载轻 | 温度、计数器、历史频率、同场景基线 |
| 内存总量持续增长 | 分配/导入未回落 | 生命周期、Vulkan 事件、dma-buf、进程销毁后状态 |
| `eglSwapBuffers()` 周期性变长 | 队列堆积或节奏控制 | 待处理缓冲区、释放围栏、显示间隔 |
| 应用缓冲区就绪，DisplayFrame 仍然延迟 | SF/HWC/显示链路 | 合成、HWC 验证/提交、显示围栏 |
| `gpu_slice` 有很长事件 | 某类 GPU/Vulkan/日志轨道很长 | 按 `track.type` 分类后再解释 |
| 跟踪数据没有 GPU 阶段 | 数据生产方、配置或权限缺失 | 数据源描述符与采集日志 |

## 11. Android 17 源码中的接口边界

以下说法与 Android 17 源码不符：

- `frameworks/native/services/surfaceflinger/Flinger.cpp` 不是 Android 17 源码路径，主文件是 `SurfaceFlinger.cpp`；
- `android-17.0.0_r1` 标签中没有 `SurfaceFlinger::setDebugProperties()`、`mGpuTracingEnabled`、`mGpuCounters` 这组统一控制实现；
- Android 公开 API 中没有 `Choreographer.getGpuPerfMetrics()`；
- Trace Processor 没有名为 `gpu_state` 的标准表；
- `GpuRenderStageEvent` 在 `android-12.0.0_r1` 已经存在，因此 Android 17 没有首次引入 GPU 渲染阶段跟踪；当前 `gpu_slice` 仍要按 Android 17 的表结构解读；
- AOSP 没有自动分析着色器、合并绘制调用、预测优化收益或上传云端进行跨设备对比的 GPU AI 服务；
- Android Studio、APA、AGI 和第三方工具有各自发布周期，不能把某个 IDE 功能写成 Android 17 平台 API。

Android 17 源码中存在 `RenderCommandBuffer`，路径在 `frameworks/native/libs/gui` 与 `libs/ipcrenderbuffer`。`SurfaceComposerClient` 注释将其标为开发中功能：客户端通过共享内存把绘制命令交给 SurfaceFlinger，作为缓冲区合成的替代路径。它不负责监控从 Choreographer 到 GPU 提交的完整链路，也不属于 Perfetto GPU 计数器框架。

## 12. 版本边界

| 版本 | GPU 跟踪的解释边界 |
|---|---|
| Android 12 / API 31 | FrameTimeline 成为现代帧计划/jank 基线；GPU proto、counter 和 memory tracing 的部分能力更早已经存在 |
| Android 13 / API 33 | AIDL HWC 与现代显示诊断主线延续；GPU 数据生产能力仍由设备决定 |
| Android 14 / API 34 | Perfetto GPU/FrameTimeline 继续演进；不能把工具版本变化写成统一平台 GPU API |
| Android 15 / API 35 | 16KB 页大小影响原生分析器和跟踪层的可运行性，不改变 GPU 跟踪协议的基本证据边界 |
| Android 16 / API 36 | GPU 跟踪数据模型继续演进；数据生产方、权限和设备支持仍需逐机查询 |
| Android 17 / API 37 | `GpuRenderStagesConfig`、GPU proto、解析器、`gpu_slice`、计数器及标准库表均按 `android-17.0.0_r1` 核对 |

“Android 17 标签中存在”不等于“Android 17 首次加入”。判断首次引入版本时，应比较历史标签或官方发布说明，不能根据文件版权年份推断正式发布版本。

## 总结

Android 17 的 GPU 跟踪数据并非由 SurfaceFlinger 统一采集。渲染阶段和硬件计数器依赖 GPU 数据生产方，频率依赖设备跟踪点，GPU 内存时间线由驱动事件、GpuService 初值与 Trace Processor 计数器共同组成；Vulkan 内存跟踪器只覆盖经过插桩的 Vulkan 分配。

分析时先查询描述符，再按目标 Surface 和生产线程找到 CPU 提交，用 `gpu_render_stage` 过滤后的切片定位 GPU 窗口，用带描述符的计数器解释资源压力，最终沿生产方围栏、SurfaceFlinger 与显示提交验证用户可见结果。数据缺失只说明证据不足，不能据此判断 GPU 空闲。
