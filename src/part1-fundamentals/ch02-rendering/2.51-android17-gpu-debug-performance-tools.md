# 2.51 Android 17 GPU 调试性能工具链

## 为什么需要专门的 GPU 调试工具链

在 §2.10 中，我们分析了 GPU 渲染管线的内部机制——Vertex Shader、Fragment Shader、Framebuffer。但理解原理只是第一步：在实际性能优化中，开发者面对的问题是"我的应用为什么掉帧"，而答案往往分散在 SurfaceFlinger 合成、GPU 渲染、Vulkan/ANGLE 翻译等多个层面。没有一套系统化的调试工具链，GPU 性能问题就像一个黑盒——你知道有问题，但无法定位到具体的帧、具体的 Layer、具体的渲染阶段。

Android 的 GPU 调试工具链分为两个层次：**系统内建层**（FrameTracer、FPSReporter、JankTracker、TimeStats）由 SurfaceFlinger 原生提供，无需额外安装即可在 Perfetto Trace 中看到结构化的帧级数据；**外部工具层**（AGI、Sokatoa、ARM Streamline 等）需要单独安装，提供更深层的 GPU 计数器分析和帧级 Replay 能力。两层配合使用，才能完成从"发现问题"到"定位根因"的完整工作流。

[已验证: AOSP android-17.0.0_r1, frameworks/native/services/surfaceflinger/]

## GPU 性能分层监控体系

### FrameTracer：SurfaceFlinger 的帧事件追踪基石

FrameTracer 是 SurfaceFlinger 内嵌的 Perfetto 数据源，自 Android 10 起引入，在 Android 17 中承担着将每一帧的完整生命周期写入 Perfetto Trace 的核心职责。它的工作原理直接决定了我们能在 Perfetto 中看到多少帧级细节。

从源码看，FrameTracer 基于 Perfetto 的 Custom DataSource 机制实现。SurfaceFlinger 启动时，FrameTracer 通过 `initialize()` 注册名为 `"android.graphics.FrameLatency"`的数据源：

```cpp
// AOSP android-17.0.0_r1
// frameworks/native/services/surfaceflinger/FrameTracer/FrameTracer.cpp

void FrameTracer::initialize() {
    std::call_once(mInitializationFlag, [this]() {
        perfetto::TracingInitArgs args;
        args.backends = perfetto::kSystemBackend;
        perfetto::Tracing::Initialize(args);
        registerDataSource();
    });
}

void FrameTracer::registerDataSource() {
    perfetto::DataSourceDescriptor dsd;
    dsd.set_name(kFrameTracerDataSource);  // "android.graphics.FrameLatency"
    FrameTracerDataSource::Register(dsd);
}
```

注册完成后，FrameTracer 为每个 Layer 创建追踪上下文（`traceNewLayer`），然后在帧生命周期的关键节点写入 Trace 事件（`traceTimestamp` / `traceFence`）。可追踪的事件类型定义在 `GraphicsFrameEvent.BufferEventType` 枚举中：

```protobuf
// AOSP android-17.0.0_r1
// external/perfetto/protos/perfetto/trace/android/graphics_frame_event.proto

enum BufferEventType {
    UNSPECIFIED          = 0;
    DEQUEUE              = 1;  // 从 BufferQueue 取出 buffer
    QUEUE                = 2;  // 生产者（App）提交绘制完成的 buffer
    POST                 = 3;  // buffer 进入 SurfaceFlinger 的 posted 队列
    ACQUIRE_FENCE        = 4;  // acquire fence signal（buffer 可被读取）
    LATCH                = 5;  // SurfaceFlinger 选定该 buffer 用于合成
    HWC_COMPOSITION_QUEUED = 6;  // 提交给 HWC（Hardware Composer）合成
    FALLBACK_COMPOSITION = 7;   // RenderEngine（GPU）合成路径
    PRESENT_FENCE        = 8;   // present fence signal（帧上屏）
    RELEASE_FENCE        = 9;   // release fence signal（buffer 可回收）
    MODIFY                = 10;
    DETACH                = 11;
    ATTACH                = 12;
    CANCEL                = 13;
}
```

此外，SurfaceFlinger 额外追踪 `GPU_COMPOSITION_DONE` 事件——当 RenderEngine 完成 GPU 合成时触发。这个事件类型不在 Perfetto proto 枚举中定义，而是由 SurfaceFlinger 内部的 FrameEvent 扩展使用：

```cpp
// AOSP android-17.0.0_r1
// frameworks/native/services/surfaceflinger/SurfaceFlinger.cpp
// 帧生命周期追踪的事件列表
static const std::vector<FrameEvent> kFrameEventList = {
    FrameEvent::REQUESTED_PRESENT,
    FrameEvent::ACQUIRE,
    FrameEvent::LATCH,
    FrameEvent::FIRST_REFRESH_START,
    FrameEvent::LAST_REFRESH_START,
    FrameEvent::GPU_COMPOSITION_DONE,
    FrameEvent::DEQUEUE_READY,
    FrameEvent::RELEASE,
};
```

在 Perfetto Trace 中，这些事件呈现为 SurfaceFlinger 轨道下每个 Layer 的帧时间线。一帧从 `DEQUEUE` 开始（App 取出空 buffer），经过 `QUEUE`（App 提交绘制结果）、`LATCH`（SurfaceFlinger 选定该帧）、最终到 `PRESENT_FENCE`（帧上屏显示）。任意两个相邻事件之间的异常间隔，就是需要关注的性能瓶颈所在。

> [已验证: AOSP android-17.0.0_r1, frameworks/native/services/surfaceflinger/FrameTracer/FrameTracer.cpp + SurfaceFlinger.cpp]

### FrameTracer 的 Fence 追踪机制

GPU 渲染的一个核心挑战是异步性：CPU 提交命令后，GPU 的执行是异步的，需要通过 Fence（同步屏障）来标记完成时间点。FrameTracer 的 `traceFence` 方法负责追踪这些 Fence 的触发时间：

```cpp
// AOSP android-17.0.0_r1
// frameworks/native/services/surfaceflinger/FrameTracer/FrameTracer.cpp

void FrameTracer::traceFence(int32_t layerId, uint64_t bufferID, uint64_t frameNumber,
                             const std::shared_ptr<FenceTime>& fence,
                             FrameEvent::BufferEventType type, nsecs_t startTime) {
    FrameTracerDataSource::Trace([this, layerId, bufferID, frameNumber, &fence, type,
                                  startTime](FrameTracerDataSource::TraceContext ctx) {
        std::lock_guard<std::mutex> lock(mTraceMutex);
        // ... 处理该 buffer 的 pending fences
        tracePendingFencesLocked(ctx, layerId, bufferID);

        if (fence->getSignalTime() == Fence::SIGNAL_TIME_PENDING) {
            // Fence 尚未触发：加入 pending 列表，等待下次 trace 调用时检查
            mPendingTraces[layerId][bufferID].push_back(
                {frameNumber, fence, type, startTime});
        } else {
            // Fence 已触发：立即写入 Trace
            traceLocked(ctx, layerId, bufferID, frameNumber,
                       fence->getSignalTime(), type, startTime);
        }
    });
}
```

这个设计意味着：如果 `ACQUIRE_FENCE` 到 `LATCH` 之间的时间很长，说明 buffer 从 GPU 渲染完成到被 SurfaceFlinger 选中合成的等待时间久——可能是渲染管线拥塞，也可能是合成调度延迟。在 Perfetto 中，FrameTracer 的数据通常与 `gpu_cont`（GPU 计数器）轨道、`traced_probes`（系统指标）轨道并列显示，形成完整的 GPU-CPU-SurfaceFlinger 三方时间线。

### FPSReporter：跨进程 FPS 监控

FPSReporter 是 SurfaceFlinger 中负责向系统组件报告 FPS 数据的模块。与开发者通过 Choreographer 自行计算的 FPS 不同，FPSReporter 提供的是 **SurfaceFlinger 侧** 的合成帧率——即最终上屏的帧率，而不是 App 渲染的帧率。两者的区别在于：App 可能以 120fps 渲染，但 SurfaceFlinger 最终只以 60fps 合成上屏。

```cpp
// AOSP android-17.0.0_r1
// frameworks/native/services/surfaceflinger/FpsReporter.cpp

void FpsReporter::dispatchLayerFps(const frontend::LayerHierarchy& layerHierarchy) {
    const auto now = mClock->now();
    if (now - mLastDispatch < kMinDispatchDuration) {
        return;  // 节流：避免过于频繁的报告
    }

    // 遍历 LayerHierarchy，匹配注册了监听的 Task
    layerHierarchy.traverse([&](const frontend::LayerHierarchy& hierarchy,
                                const frontend::LayerHierarchy::TraversalPath& traversalPath) {
        const auto& metadata = hierarchy.getLayer()->metadata;
        if (metadata.has(gui::METADATA_TASK_ID)) {
            int32_t taskId = metadata.getInt32(gui::METADATA_TASK_ID, 0);
            // 匹配到监听者的 taskId，收集该 task 下所有 layer 的 ID
            // 然后通过 FrameTimeline::computeFps() 计算 FPS
            listener.listener->onFpsReported(
                mFrameTimeline.computeFps(layerIds));
        }
        return true;
    });
}
```

FPSReporter 的核心设计要点：

1. **基于 FrameTimeline 计算**：FPS 不是简单数帧，而是通过 `FrameTimeline.computeFps(layerIds)` 基于帧时间线数据精确计算
2. **按 Task 维度聚合**：一个 App 可能有多个 Window/Layer，FPSReporter 按 Task ID 聚合所有相关 Layer 的帧数据
3. **监听器机制**：系统组件（如 Game Mode、Performance Manager）通过 `addListener` 注册监听，FPSReporter 定期推送 FPS 数据
4. **节流策略**：`kMinDispatchDuration` 控制最小分发间隔，避免频繁 IPC 的性能开销

> [已验证: AOSP android-17.0.0_r1, frameworks/native/services/surfaceflinger/FpsReporter.cpp]

### JankTracker：基于帧分类的卡顿检测

JankTracker（自 Android 15 引入，Android 17 进一步增强）是 SurfaceFlinger 中专门负责卡顿分类和通知的组件。与 Perfetto 的事后分析不同，JankTracker 提供 **运行时** 的卡顿检测——当帧被识别为 Jank 时，立即通知注册的监听者。

```cpp
// AOSP android-17.0.0_r1
// frameworks/native/services/surfaceflinger/Jank/JankTracker.h

class JankTracker {
public:
    // 按_layer 注册 jank 监听
    static void addJankListener(int32_t layerId, sp<IBinder> listener);
    // 刷新挂起的 jank 数据
    static void flushJankData(int32_t layerId);
    // 移除监听（可指定 afterVsync，只移除该 vsync 之后的）
    static void removeJankListener(int32_t layerId, sp<IBinder> listener, int64_t afterVsync);
    // 接收 SurfaceFlinger 传来的 jank 数据
    static void onJankData(int32_t layerId, gui::JankData data);
};
```

JankTracker 的核心设计模式：

1. **单例 + BackgroundExecutor**：所有方法都是 static，通过 `getInstance()` 访问单例。实际操作通过 `BackgroundExecutor::getLowPriorityInstance()` 在低优先级后台线程执行，避免阻塞合成管线
2. **批量处理**：jank 数据不是逐帧通知，而是批量积累到 `kJankDataBatchSize`（50 帧）后统一分发，减少 IPC 开销
3. **监听者计数优化**：`sListenerCount` 是一个 `std::atomic` 计数器，当没有监听者时（count=0），`onJankData` 直接 return，避免无监听者时的数据收集开销
4. **按 Layer 粒度追踪**：每个 Layer 独立注册和管理，支持精细化的卡顿监控

JankTracker 的 `gui::JankData` 包含帧的卡顿分类信息（如是否为 jank 帧以及具体原因分类）。这些分类由 FrameTimeline 的帧预期完成时间 vs 实际完成时间比较得出。

> [已验证: AOSP android-17.0.0_r1, frameworks/native/services/surfaceflinger/Jank/JankTracker.cpp + .h]

### TimeStats：帧时间统计与 statsd 上报

TimeStats 是 SurfaceFlinger 中最全面的统计数据收集器，它记录帧在各阶段的时间分布，并通过 statsd pull atom 机制上报给系统统计服务。

```cpp
// AOSP android-17.0.0_r1
// frameworks/native/services/surfaceflinger/TimeStats/TimeStats.h

class TimeStats {
public:
    virtual void incrementTotalFrames() = 0;          // 总帧数
    virtual void incrementMissedFrames() = 0;          // 丢帧数
    virtual void incrementRefreshRateSwitches() = 0;   // 刷新率切换次数

    // 帧各阶段耗时记录
    virtual void recordFrameDuration(nsecs_t startTime, nsecs_t endTime) = 0;
    virtual void recordRenderEngineDuration(nsecs_t startTime, nsecs_t endTime) = 0;
    virtual void recordRenderEngineDuration(nsecs_t startTime,
                                            const std::shared_ptr<FenceTime>& readyFence) = 0;

    // 每层每帧的时间戳记录
    virtual void setPostTime(int32_t layerId, uint64_t frameNumber, ...) = 0;
    virtual void setLatchTime(int32_t layerId, uint64_t frameNumber, nsecs_t latchTime) = 0;
    // ...更多阶段时间记录方法
};
```

TimeStats 通过 `dumpsys SurfaceFlinger --timestats` 命令可以导出详细的帧统计信息，开发者无需 Perfetto 也能快速获取帧时间数据。关键统计项包括：

- **总帧数 / 丢帧数**：全局帧率与丢帧率
- **Frame Duration**：SurfaceFlinger 从 invalidate 到提交 HWC 的耗时
- **RenderEngine Duration**：GPU 合成耗时（从 RenderEngine::drawLayers 开始到 fence signal）
- **Per-Layer 时间线**：每个 Layer 的 post → latch → present 全链路时间
- **刷新率切换次数**：评估 ARR（自适应刷新率）策略的有效性

在 Android 17 中，TimeStats 还集成了 LatchSkipReason 枚举，记录 buffer 被 skip latched 的原因（如 acquire fence 未触发、buffer 未变化等），这对于分析"帧已提交但未上屏"的问题非常有价值。

> [已验证: AOSP android-17.0.0_r1, frameworks/native/services/surfaceflinger/TimeStats/TimeStats.h]

## SurfaceFlinger GPU 调试系统

### GPU 后端与合成回压控制

SurfaceFlinger 在初始化时加载大量与 GPU 合成相关的调试属性。这些属性控制着 GPU 合成管线的核心行为，理解它们对于分析合成性能至关重要。

```cpp
// AOSP android-17.0.0_r1
// frameworks/native/services/surfaceflinger/SurfaceFlinger.cpp (init 阶段)

// GPU 合成回压控制
mBackpressureGpuComposition =
    base::GetBoolProperty("debug.sf.enable_gl_backpressure"s, true);
// 默认 true：当 GPU 合成已有 pending buffer 时，跳过新的合成请求
// 避免合成管线积压导致帧延迟持续增长

// 合成策略预测
property_get("debug.sf.predict_hwc_composition_strategy", value, "1");
mPredictCompositionStrategy = atoi(value);
// 默认 1：SurfaceFlinger 预测 HWC 是否能完成合成，
// 如果预测 HWC 可处理则跳过 GPU 合成准备阶段

// Layer 缓存
base::GetBoolProperty("debug.sf.enable_layer_caching"s, ...);
// 控制 Layer caching 优化是否启用

// 客户端合成缓存禁用
property_get("debug.sf.disable_client_composition_cache", value, "0");
// 默认 0：启用客户端合成缓存，减少重复 GPU 合成

// Luma Sampling
property_get("debug.sf.luma_sampling", value, "1");
// 默认 1：启用亮度采样（用于 HDR/SDR 混合合成的亮度计算）
```

回压机制是 Android 17 GPU 合成管线的关键优化。当 `mBackpressureGpuComposition = true` 时，SurfaceFlinger 在检测到 GPU 合成已有 pending buffer 时，会主动跳过新的合成请求：

```cpp
// AOSP android-17.0.0_r1, SurfaceFlinger.cpp
if (mBackpressureGpuComposition || pacesetterFrameTargetPtr->didMissHwcFrame()) {
    // GPU 合成回压：已有 pending buffer，跳过本次合成
}
```

这个机制防止了 GPU 合成任务的无限堆积。在 Perfetto Trace 中，如果看到 SurfaceFlinger 某些帧没有合成动作（没有 `FALLBACK_COMPOSITION` 事件），但前一帧有 `GPU_COMPOSITION_DONE` 且耗时较长，很可能就是回压在生效。

> [已验证: AOSP android-17.0.0_r1, frameworks/native/services/surfaceflinger/SurfaceFlinger.cpp]

### RenderEngine 后端选择与 Vulkan 化

Android 17 的 SurfaceFlinger RenderEngine 支持四种后端配置：

```cpp
// AOSP android-17.0.0_r1
// frameworks/native/services/surfaceflinger/SurfaceFlinger.cpp

void chooseRenderEngineType(renderengine::RenderEngineCreationArgs::Builder& builder) {
    char prop[PROPERTY_VALUE_MAX];
    property_get(PROPERTY_DEBUG_RENDERENGINE_BACKEND, prop, "");

    if (strcmp(prop, "skiagl") == 0) {
        // Skia + OpenGL ES，非线程化
        builder.setThreaded(Threaded::No).setGraphicsApi(GraphicsApi::GL);
    } else if (strcmp(prop, "skiaglthreaded") == 0) {
        // Skia + OpenGL ES，线程化
        builder.setThreaded(Threaded::Yes).setGraphicsApi(GraphicsApi::GL);
    } else if (strcmp(prop, "skiavk") == 0) {
        // Skia + Vulkan，非线程化
        builder.setThreaded(Threaded::No).setGraphicsApi(GraphicsApi::Vk);
    } else if (strcmp(prop, "skiavkthreaded") == 0) {
        // Skia + Vulkan，线程化
        builder.setThreaded(Threaded::Yes).setGraphicsApi(GraphicsApi::Vk);
    } else {
        // 默认路径：优先 Vulkan（含 Graphite），回退 OpenGL ES
        const auto kVulkan = RenderEngine::GraphicsApi::Vk;
        const bool useVulkan = FlagManager::getInstance().vulkan_renderengine()
                && RenderEngine::canSupport(kVulkan);
        // Android 17 默认走 Vulkan + threaded 路径
    }
}
```

Android 17 的默认 RenderEngine 后端是 **SkiaVk + Threaded（线程化 Vulkan）**，即 SurfaceFlinger 的 GPU 合成通过 Vulkan 完成，且在独立线程中执行。这意味着 SurfaceFlinger 的合成过程本身就走 Vulkan 管线，与 App 的渲染（也越来越多走 Vulkan/ANGLE→Vulkan）共享同一条 GPU 资源竞争链路。

> [已验证: AOSP android-17.0.0_r1, frameworks/native/services/surfaceflinger/SurfaceFlinger.cpp]

### GPU 合成 Offload

Android 17 引入了 GPU 合成 Offload 机制，允许 RenderEngine 在独立线程上运行，与主合成循环解耦：

```cpp
// AOSP android-17.0.0_r1, SurfaceFlinger.cpp
const bool canOffloadGpuComposition =
    FlagManager::getInstance().offload_gpu_composition()
    && mRenderEngine->isThreaded();
```

当 Offload 启用时，SurfaceFlinger 主线程将 GPU 合成任务派发给 RenderEngine 的工作线程，主线程可以继续处理 Transaction 和 Layer 管理工作。这减少了合成阶段对主线程的阻塞时间，在多显示器场景下尤其有效。

## Android 17 ANGLE 策略与调试影响

### 从 Allowlist 到 Denylist 的根本转变

Android 17 在 GPU 工具链层面最重要的变化是 ANGLE 部署策略从 allowlist 转为 denylist。这意味着：

- **Android 16 及之前**：ANGLE 默认不启用，仅 allowlist 中的应用通过 ANGLE 翻译
- **Android 17（新设备）**：所有 App 默认通过 ANGLE→Vulkan 路径，仅 denylist 中的 App 使用原生 GLES 驱动

这对 GPU 调试工具链产生了直接影响：

1. **Perfetto GPU 轨道变化**：ANGLE 路径下，GPU 命令经过翻译层，原生 GPU 驱动的 Perfetto 轨道会显示翻译后的 Vulkan 命令，而非原始 GLES 命令
2. **AGI 分析路径**：AGI 本身就是通过自定义 ANGLE build 将 GLES 命令翻译为 Vulkan 进行追踪。Android 17 强制 ANGLE 后，AGI 的追踪路径与系统运行路径一致，分析结果更贴近真实运行情况
3. **Shader 调试复杂化**：GLES Shader 经过 ANGLE→SPIR-V→Vulkan 翻译后，开发者看到的 GPU 指令与原始 GLSL 差异更大

> [来源: intake/research-feeds/2026-04-04-15-ch02-android17-mandatory-angle-vulkan14.md]

### AGI（Android GPU Inspector）

AGI 是 Google 官方维护的 Android GPU 分析工具，目前最新版本为 v3.3.3（2025-01）。它提供两种核心分析模式：

**System Profiler 模式**：基于 Perfetto 系统 Trace，增加 GPU 特有的计数器轨道（GPU 频率、GPU 利用率、内存带宽等）。适合定位整体性能瓶颈和 GPU-CPU 协同分析。

**Frame Profiler 模式**：捕获单帧的完整 GPU 命令流（Vulkan 或通过 ANGLE 翻译的 GLES），支持逐 draw call 检查、纹理/Shader 检查、Render Pass 分析。适合深度优化具体场景的渲染性能。

AGI 2026 路线图包含两个重要里程碑：

- **改进版 System Profiler（2026 H1）**：速度和可靠性大幅提升，支持超大 trace 文件、帧截图功能、side-by-side 多 trace 对比，计划开源
- **高级 Frame Profiler Alpha（2026 H2）**：基于 GFXReconstruct 构建，核心特性包括 frame looping（精确测量重复帧性能）、render pass graph（可视化 RenderPass 依赖关系）、帧/RenderPass 级计时和硬件计数器、导出到 RenderDoc

> [来源: intake/research-feeds/2026-04-05-11-agi-2026-roadmap-system-frame-profiler.md]

### Samsung Sokatoa：多帧 GPU Profiler

Sokatoa 是 Samsung 于 2026 年 3 月发布的开源 GPU 性能分析器，与 Google、LunarG 合作开发。与 AGI/RenderDoc 的单帧分析范式不同，Sokatoa 的核心创新是 **多帧分析能力**：

- 可同时分析多个连续帧的 GPU 行为
- 定位单帧工具难以发现的间歇性渲染异常（偶发卡顿、shader 编译尖刺）
- 基于 LunarG GFXReconstruct 的 API 调用捕获/回放引擎
- 兼容 Samsung Xclipse、Qualcomm Adreno、ARM Mali 多种 GPU

Sokatoa 与 AGI 形成互补：AGI 适合深度单帧分析，Sokatoa 适合广度多帧模式识别。对于"偶发掉帧但不知道是哪一帧"这类问题，Sokatoa 是更合适的入口工具。

> [来源: intake/research-feeds/2026-04-05-11-samsung-sokatoa-gpu-profiler.md]

## GPU 调试工具选型决策树

基于上述工具链分析，Android 17 平台上的 GPU 性能调试可以按照以下决策路径选择工具：

**第一层：Perfetto + FrameTracer（发现问题）**

所有 GPU 性能分析的起点都应该是 Perfetto Trace。通过配置 `graphics_frame_events` 数据源，可以获取 SurfaceFlinger 的完整帧生命周期数据。在 Perfetto 中关注：
- 帧从 `QUEUE` 到 `PRESENT_FENCE` 的总耗时——如果超过 Vsync 周期（16.6ms @ 60Hz），说明掉帧
- `FALLBACK_COMPOSITION` 到 `GPU_COMPOSITION_DONE` 的间隔——GPU 合成耗时
- `gpu_cont` 轨道中的 GPU 利用率——如果 GPU 利用率不高但帧耗时长，可能是 CPU 提交瓶颈或内存带宽瓶颈

**第二层：dumpsys SurfaceFlinger（快速诊断）**

不需要 Perfetto 时，通过 `adb shell dumpsys SurfaceFlinger --timestats` 可以快速获取帧统计信息。适合 CI/CD 管线中的自动化性能检测。

**第三层：AGI System Profiler（GPU 深度分析）**

当 Perfetto 发现 GPU 相关瓶颈但无法进一步定位时，使用 AGI System Profiler 获取详细的 GPU 计数器数据（ALU 利用率、纹理带宽、Shader 指令数等）。

**第四层：AGI Frame Profiler / Sokatoa（帧级 Replay）**

当需要分析具体 draw call 的性能时，使用 AGI Frame Profiler 捕获单帧进行逐命令分析。如果问题是偶发卡顿，使用 Sokatoa 的多帧分析模式。

## 生产环境 GPU 监控建议

在生产环境中部署 GPU 监控时，需要注意以下要点：

1. **JankTracker API**：通过 `SurfaceControl.addJankDataListener`（Android 15+）注册 jank 监听，获取运行时卡顿通知。注意设置合理的 batch size，避免 IPC 开销过大
2. **FPSReporter 监听**：通过 `WindowManager` 注册 FPS 监听，获取 SurfaceFlinger 侧的合成帧率。比 Choreographer 自行计算的 FPS 更准确（因为是最终上屏帧率）
3. **TimeStats statsd 上报**：TimeStats 通过 statsd pull atom 自动上报帧统计数据，可在后台通过 `statsd` 命令行工具或 `dumbsys stats` 获取聚合数据
4. **Perfetto 采样开销**：FrameTracer 的 Perfetto 数据源使用 system backend，在未启用 tracing 时几乎零开销（`sListenerCount == 0` 直接 return）。启用 tracing 后的开销主要取决于 Layer 数量和帧率

## 源码级深挖（2026-07-07 调研补丁）

本节作为对前文 §2.51 的源码级补充，基于 AOSP `android-17.0.0_r1` tag 实测了核心调用链与三个被低估的实现细节。

### 1. FrameTracer 的真实调用入口（Layer.cpp）

FrameTracer 的所有 `trace*` 调用都不是凭空发生的，它们来自 Layer 在 buffer 生命周期中的关键事件。`frameworks/native/services/surfaceflinger/Layer.cpp` 中的实际调用链：

```cpp
// AOSP android-17.0.0_r1, frameworks/native/services/surfaceflinger/Layer.cpp

// 入口 1：Buffer 首次进入 Layer 的 posted 队列
const uint64_t bufferId = mDrawingState.buffer->getId();
mFlinger->mFrameTracer->traceNewLayer(layerId, getName().c_str());
mFlinger->mFrameTracer->traceTimestamp(layerId, bufferId, bufferData.frameNumber,
                                       bufferData.dequeueTime,
                                       FrameTracer::FrameEvent::DEQUEUE);
mFlinger->mFrameTracer->traceTimestamp(layerId, bufferId, bufferData.frameNumber, postTime,
                                       FrameTracer::FrameEvent::QUEUE);

// 入口 2：合成前，acquire fence signal 时
mFlinger->mFrameTracer->traceFence(layerId, bufferId, frameNumber, acquireFence,
                                   FrameTracer::FrameEvent::ACQUIRE_FENCE);
mFlinger->mFrameTracer->traceTimestamp(layerId, bufferId, frameNumber, latchTime,
                                       FrameTracer::FrameEvent::LATCH);

// 入口 3：客户端合成完成（RenderEngine GPU 合成路径）
mFlinger->mFrameTracer->traceTimestamp(layerId, getLatchedBufferId(), mCurrentFrameNumber,
                                       clientCompositionTimestamp,
                                       FrameTracer::FrameEvent::FALLBACK_COMPOSITION);

// 入口 4：present fence signal
mFlinger->mFrameTracer->traceFence(layerId, getLatchedBufferId(), mCurrentFrameNumber,
                                   presentFence,
                                   FrameTracer::FrameEvent::PRESENT_FENCE);
```

**性能影响**：每个 Layer 的每次 buffer 操作都是一次 Perfetto trace 写入调用。在 120Hz 刷新率下，一个 8 Layer 的全屏应用每秒产生 8×120×6 ≈ 5760 次 trace 调用。FrameTracer 通过 `mTraceTracker.find(layerId) == mTraceTracker.end()` 提前 return，未注册 Layer 跳过全部开销。

### 2. JankTracker 的批量分派与零监听者短路

```cpp
// AOSP android-17.0.0_r1, frameworks/native/services/surfaceflinger/Jank/JankTracker.cpp

constexpr size_t kJankDataBatchSize = 50;
std::atomic<size_t> JankTracker::sListenerCount(0);

void JankTracker::onJankData(int32_t layerId, gui::JankData data) {
    if (sListenerCount == 0) {
        return;   // 零监听者：完全跳过
    }
    BackgroundExecutor::getLowPriorityInstance().sendCallbacks(
            {[layerId, data = std::move(data)]() {
                JankTracker& tracker = getInstance();
                ...
                tracker.mJankData.emplace(layerId, data);
                size_t count = tracker.mJankData.count(layerId);
                if (count >= kJankDataBatchSize && !sCollectAllJankDataForTesting) {
                    tracker.doFlushJankData(layerId);
                }
            }});
}
```

**三个关键设计点**：

1. **`sListenerCount` 原子快速路径**：`std::atomic<size_t>` 保证无监听者时第一行直接 return，整个 jank 数据收集管线不会进入——生产环境零开销
2. **BackgroundExecutor 低优先级线程**：合成主线程不被 jank 通知阻塞
3. **`kJankDataBatchSize=50`**：每积累 50 帧 jank 数据才触发一次 binder IPC，避免高频调用

> [已验证: AOSP android-17.0.0_r1, frameworks/native/services/surfaceflinger/Jank/JankTracker.cpp + .h]

### 3. TimeStats 的 statsd Pull Atom 双通道

TimeStats 是**独立的 statsd 通道**，与 FrameTracer 的 Perfetto 通道互补不重叠。两个 pull atom：

```cpp
// AOSP android-17.0.0_r1, TimeStats/TimeStats.cpp

bool TimeStats::onPullAtom(const int atomId, std::vector<uint8_t>* pulledData) {
    bool success = false;
    if (atomId == 10062) { // SURFACEFLINGER_STATS_GLOBAL_INFO
        success = populateGlobalAtom(pulledData);
    } else if (atomId == 10063) { // SURFACEFLINGER_STATS_LAYER_INFO
        success = populateLayerAtom(pulledData);
    }
    enable();   // 注意：第一次 pull 完成后才 enable timestats
    return success;
}
```

**全局 atom（10062）暴露的 Jank 7 维度分类**：

| 字段 | 含义 |
|------|------|
| `total_janky_frames_with_long_cpu` | SF 检测到 CPU 阶段过长的 jank |
| `total_janky_frames_with_long_gpu` | SF 检测到 GPU 阶段过长的 jank |
| `total_janky_frames_sf_unattributed` | SF 侧未归因的 jank |
| `total_janky_frames_app_unattributed` | App 侧未归因的 jank |
| `total_janky_frames_sf_scheduling` | SF 调度延迟导致的 jank |
| `total_jank_frames_sf_prediction_error` | SF 预测错误导致的 jank |
| `total_jank_frames_app_buffer_stuffing` | App buffer 填充不及时导致的 jank |

**Layer atom（10063）**额外提供 7 种 per-layer histogram：`present2present` / `present2presentDelta` / `post2present` / `acquire2present` / `latch2present` / `desired2present` / `post2acquire`。

**零开销保证**：所有 record 方法第一行 `if (!mEnabled.load()) return;`，`mEnabled` 默认 false，仅在 statsd 第一次 pull 完成后才 enable。

> [已验证: AOSP android-17.0.0_r1, frameworks/native/services/surfaceflinger/TimeStats/TimeStats.cpp]

### 4. GpuCounterEvent 双模式：跨设备 GPU 计数器标准化困境

`external/perfetto/protos/perfetto/trace/gpu/gpu_counter_event.proto` 的注释直接揭示了 GPU counter 的标准化困境：

```protobuf
// AOSP android-17.0.0_r1
// protos/perfetto/trace/gpu/gpu_counter_event.proto
//
// There are two "modes" to use these protos:
//   1) Using GpuCounterDescriptor. This is the simplest way ... but counter ids
//      are *global* so must only be emitted by a single producer ...
//      **must** be used by Android OEMs to be compliant with CDD/CTS tests.
//   2) Using InternedGpuCounterDescriptor. This is generally recommended for
//      more complex use-cases involving multiple producers, multiple GPUs etc.
message GpuCounterEvent {
  oneof desc {
    GpuCounterDescriptor counter_descriptor = 1;   // mode 1
    uint64 counter_descriptor_iid = 4;             // mode 2
  }
}
```

**这是 AGI / Sokatoa 跨设备分析的最大障碍**：

- **mode 1（OEM 路径，CDD/CTS 强制）**：`counter_id` 是全局 ID，不同 OEM 的 counter 集合不同——Adreno 的 `shader_core_active` 在 Mali 上不存在，Mali 的 `fragment_jobs` 在 Xclipse 上也没有对应物
- **mode 2（多 producer 路径）**：使用 `InternedData` 的 iid，需要 trace 消费方支持 iid 解析

**直接推论**：AGI 的 System Profiler 在不同 OEM 设备上看到的 GPU counter 轨道**不可直接比较**。要做跨设备基准测试，开发者必须先把 counter 标准化到应用层（如"GPU 占用率 = 任意 shader_core 类 counter / cycle count"），而不是依赖 Perfetto UI 的原始 counter 显示。Sokatoa 的多帧分析在这一层同样受限——它能做"同一设备上的多帧对比"，但**难以做"不同设备的 GPU 占用率横向对比"**。

### 5. tracePendingFencesLocked：Fence 异步触发的批处理

GPU 渲染的核心异步性体现在 fence 上。FrameTracer 的 `traceFence` 在 fence 未 signal 时不写入 trace，而是 push 到 `pendingFences` 列表：

```cpp
// AOSP android-17.0.0_r1, FrameTracer/FrameTracer.cpp

void FrameTracer::tracePendingFencesLocked(FrameTracerDataSource::TraceContext& ctx,
                                           int32_t layerId, uint64_t bufferID) {
    ...
    if (signalTime != Fence::SIGNAL_TIME_INVALID &&
        systemTime() - signalTime < kFenceSignallingDeadline) {
        traceSpanLocked(...);
    }
    pendingFences.erase(pendingFences.begin() + i);
    --i;
}
```

`kFenceSignallingDeadline` 是**stale 丢弃阈值**——超过该阈值的 fence signal 事件直接丢弃，避免污染 trace。

### 6. 生产环境选型决策（结合本次深挖修订）

基于本次源码级深挖，对前文决策树补充如下要点：

1. **跨设备基准**：不要依赖 Perfetto UI 的原始 GPU counter 显示，必须应用层标准化
2. **零开销保证**：JankTracker / TimeStats / FrameTracer 在各自短路路径上都做到零开销，可放心在生产环境启用监听
3. **statsd vs Perfetto 双通道**：TimeStats 的 statsd pull atom（10062/10063）适合后台长期聚合，FrameTracer 的 Perfetto 数据源适合事后 trace 分析，两者数据**不重叠**，建议同时启用
4. **多帧分析首选 Sokatoa**：因 GPU counter 标准化问题，同一设备多帧对比才有意义，跨设备分析需应用层归一化
