# 2.51 Android 17 GPU Trace 数据源与 Trace Processor 证据链

Perfetto 里出现一条 GPU 轨道，并不表示 Android 平台掌握了 GPU 的全部执行细节。GPU render stage、硬件计数器、频率、内存、Vulkan allocation、SurfaceFlinger FrameTimeline 分别来自不同 producer；设备驱动没有提供某类数据时，Perfetto 只能留下空白。

本章关注一件事：GPU 数据如何从 producer 进入 trace packet，再被 Android 17 对应的 Trace Processor 解析成 SQL 表。工具选择与完整排查顺序见 2.15；SurfaceFlinger 的 FrameTracer、TimeStats 与 jank 统计见 2.52；本章只负责把 GPU 证据的来源和解释边界讲清楚。

验证锚点固定为：

- Android 平台：Android 17 / API 37 / `android-17.0.0_r1`；
- Perfetto：平台对应的 `android-17.0.0_r1`；
- kernel：`android17-6.18-2026-06_r6`；
- 渲染拓扑参考：`Writer/rendering_pipelines/S08_native_graphics_type.md` 与 `S13_game_type.md`。

先记住四条规则：

1. 数据源名、Trace Processor 表名和 UI 轨道名不是同一个概念；
2. `gpu.renderstages` 与 `gpu.counters` 需要 GPU producer 支持，Android 17 版本号不能保证设备有数据；
3. GPU frequency、GPU counter 和 GPU render stage 回答不同问题，任何一项都不能单独证明 GPU bound；
4. 用户可见帧还要经过 producer fence、BufferQueue、SurfaceFlinger、HWC 与 display present，GPU job 结束不是上屏结束。

## 1. GPU trace 的四层结构

Perfetto GPU 数据可以按下面四层理解：

```text
data producer
  ├─ kernel / vendor GPU driver
  ├─ Android GpuService
  ├─ Vulkan tracing layer
  └─ SurfaceFlinger / App instrumentation
        ↓
TracePacket proto
  ├─ GpuRenderStageEvent
  ├─ GpuCounterEvent
  ├─ GpuMemTotalEvent
  ├─ VulkanMemoryEvent
  └─ FrameTimeline / GraphicsFrameEvent
        ↓
Trace Processor parser
        ↓
slice / counter / track + gpu_slice / gpu_counter_track / stdlib tables
```

这张图用于区分“谁产生数据”和“数据最后落在哪张表”。Trace Processor 能解析某种 proto，只代表文件格式受支持；目标设备仍要有 producer 注册并发出该数据。

## 2. 采集前先查询设备能力

下面的命令用于查看当前设备向 tracing service 注册的数据源及其 descriptor：

```bash
adb shell perfetto --query --long
```

检查输出中是否存在 `gpu.counters`、`gpu.renderstages`、`android.gpu.memory`、`vulkan.memory_tracker` 等名字。`gpu.counters` 的 descriptor 还应给出 counter id、名称、单位、采样周期和 counter block 约束。没有 descriptor 时，不要从其他机型复制 counter id。

kernel ftrace event 也要在设备上确认。下面的命令用于核对 GPU memory 与 frequency event：

```bash
adb shell 'cat /sys/kernel/tracing/available_events 2>/dev/null | grep -E "gpu_mem_total|gpu_frequency"'
```

量产设备可能限制读取 tracing filesystem。命令无输出可以是 event 不存在，也可以是权限不足；需要结合 `perfetto --query --long`、系统构建类型和采集日志判断。

### 2.1 Android 17 常见 GPU 数据入口

| 数据入口 | 主要内容 | 谁负责提供 | 关键限制 |
|---|---|---|---|
| `gpu.renderstages` | GPU queue 上的阶段 slice | GPU/驱动 producer | stage 名称和粒度由 producer 定义 |
| `gpu.counters` | 设备硬件计数器 | GPU/驱动 producer | id、单位、容量和采样方式因设备而异 |
| `power/gpu_frequency` | GPU DVFS 频率变化 | kernel/vendor tracepoint | Android common kernel 不保证存在 |
| `android.gpu.memory` | trace 开始时的 global/per-process GPU memory 快照 | Android GpuService | 依赖 `gpu_mem_total` 与 eBPF 初始化 |
| `gpu_mem/gpu_mem_total` | GPU addressable memory 总量更新 | GPU driver + ftrace | 总量不是 allocation 对象清单 |
| `vulkan.memory_tracker` | Vulkan driver/device/buffer/image allocation 事件 | Vulkan tracing layer | 不覆盖 GLES 和全部 vendor 内部内存 |
| GPU log packet | producer 上报的 severity/tag/message | GPU producer | 不是完整的 kernel/driver 日志 |
| FrameTimeline / FrameTracer | deadline、jank、layer buffer 与 fence | SurfaceFlinger | 不等于应用 GPU command 时间线 |

`gpu.renderstages`、`gpu.counters` 与 Vulkan memory 配置已经在 Android 17 对应的 Perfetto `DataSourceConfig` 中定义。配置字段存在不代表设备实现了对应 producer。

## 3. `gpu.renderstages`：GPU 执行阶段

### 3.1 一个 stage 事件包含什么

Android 17 的 `GpuRenderStageEvent` 可携带：

- event id 与 duration；
- GPU id；
- hardware queue specification；
- stage specification；
- graphics context；
- render target 与可选 debug name；
- submission id；
- Vulkan render pass、render-pass instance、subpass mask；
- Vulkan command buffer handle 与可选 debug name；
- producer 自定义的 extra data。

hardware queue 和 stage 名称来自 producer 发出的 specification。Trace Processor 不会自行推断 “vertex”“fragment”“tiler”“compute” 的硬件含义。

### 3.2 stage 不是逐 draw-call 记录

`GpuRenderStageEvent` 描述 producer 选择的一段 GPU 工作。它可以是一整个 workload，也可以按 render pass、load/store、binning、render、compute 等阶段拆分。粒度取决于 GPU producer、配置和驱动能力。

因此，一条 `gpu_slice` 不能自动给出：

- draw-call 数量；
- 每条 shader 指令的耗时；
- overdraw 热力图；
- cache miss 的根因；
- 某个纹理或 pipeline state 的完整内容。

这些问题需要 frame capture、硬件 counter 或厂商 profiler。

### 3.3 Android 17 配置里的低开销模式

Android 17 对应的 `GpuRenderStagesConfig` 包含：

- `full_loadstore`：把 color 与 depth/stencil load/store 拆得更细；
- `low_overhead`：把多个 render stage 合并成 workload stage；
- `trace_metrics`：请求 producer 支持的 per-stage metric。

当 `low_overhead=true` 时，`full_loadstore` 不生效。下面的配置用于先采集低粒度 GPU workload，适合第一轮缩小时间窗口：

```textproto
data_sources {
  config {
    name: "gpu.renderstages"
    gpu_renderstages_config {
      low_overhead: true
    }
  }
}
```

设备没有注册该 producer 时，配置仍可能成功完成，但 trace 中不会出现 render-stage 数据。详细模式会增加 GPU 或 driver 侧观测成本，应在已经固定复现场景后短时使用。

### 3.4 `submission_id` 的关联能力

proto 对 `submission_id` 的建议语义是：

- OpenGL：对应一次 API submission，例如 `glFlush`、`glFinish` 或 `eglSwapBuffers`；
- Vulkan：与一次 `vkQueueSubmit` 一一对应。

这个字段是 optional，并由 producer 生成。它不是 FrameTimeline token、BufferQueue frame number 或 SurfaceFlinger layer sequence。只有 trace 同时提供 CPU submission event 和相同 submission id 时，才能做可靠的 CPU→GPU 关联；缺少时只能借助 context、process、queue、时间窗口和应用 marker 收窄候选。

## 4. `gpu.counters`：硬件计数器

### 4.1 descriptor 比 counter 数值更重要

`GpuCounterDescriptor.GpuCounterSpec` 为每个 counter 描述：

- `counter_id`；
- name 与 description；
- numerator / denominator unit；
- 可选 peak value；
- 是否建议默认选择；
- 所属 group，例如 vertices、fragments、memory、compute、ray tracing。

同一个 “GPU active” 名字在不同厂商、不同 GPU 世代上，采样口径也可能不同。报告必须保留 descriptor、GPU/driver 版本和工具版本，不能维护一张跨设备固定阈值表。

### 4.2 counter block 限制同时启用数量

descriptor 还可以声明 `GpuCounterBlock`：

- block id 与名称；
- block capacity；
- 该 block 包含的 counter id。

如果一个 block 的容量小于想采集的 counter 数，producer 可能拒绝配置、只启用子集或采用 multiplexing。一次请求大量 counter 会增加开销，也可能改变采样可靠性。

### 4.3 采样周期与 instrumented sampling

`GpuCounterConfig` 支持：

- `counter_period_ns`；
- counter id 列表；
- `instrumented_sampling`；
- `fix_gpu_clock`。

producer descriptor 可声明最小/最大采样周期，以及是否支持 command-buffer instrumentation。采样越密，数据量与观测成本通常越高。`fix_gpu_clock` 会改变 DVFS 条件，只适合受控对照；它不能用于代表量产默认性能。

### 4.4 Trace Processor 会处理“回看型”数值

Android 17 的 `GpuEventParser::PushGpuCounterValue()` 注释明确写出：GPU counter event 报告的是当前 timestamp 之前区间生效的值，而普通 Perfetto counter 通常向后生效。parser 会插入当前点，并把数值回填到前一条 counter 记录。

这意味着：

- 分析 counter 应按时间区间加权；
- trace 末尾的最后一个点没有后续 sample 帮它封闭区间；
- 直接对所有 `counter.value` 做平均容易得到错误结论；
- 优先使用 interval/span 模块，或自行用 `LEAD(ts)` 计算 duration。

### 4.5 counter 不能代替 GPU timeline

一个时间窗口内 memory bandwidth 或 fragment counter 很高，只说明该计数器在该窗口变化。要把它归因给目标 App，还要同时满足：

- 目标 GPU queue/stage 与 App context 对得上；
- CPU submission 和 GPU stage 时间对得上；
- 该窗口覆盖目标帧，而不是 SurfaceFlinger client composition 或其他进程；
- 单变量对照能让 stage duration 与 counter 同向变化。

## 5. GPU frequency：频率不是利用率

Perfetto 官方 GPU 文档给出的频率入口是 ftrace event：

```text
power/gpu_frequency
```

Android 17 对应的 common kernel `android17-6.18-2026-06_r6` 并没有定义这个 tracepoint；它通常由具体 GPU/vendor kernel 补充。因此，同为 Android 17 的两台设备可以一台有 `gpufreq` 轨道，另一台没有。

频率变化只能说明 DVFS 选择：

- 高频时 GPU 可能繁忙，也可能被策略提前拉升；
- 低频时 GPU 可能负载很轻，也可能受 thermal/power 限制；
- 频率不变时 GPU 的 busy ratio、ALU、texture 和 bandwidth 压力仍可变化。

Android 17 对应的 Perfetto stdlib 提供 `android.gpu.frequency` 模块。下面的 SQL 用于把名为 `gpufreq` 的 counter 转成带 duration 的频率区间：

```sql
INCLUDE PERFETTO MODULE android.gpu.frequency;

SELECT
  ts / 1e6 AS ts_ms,
  dur / 1e6 AS dur_ms,
  gpu_id,
  gpu_freq,
  prev_gpu_freq,
  next_gpu_freq
FROM android_gpu_frequency
ORDER BY ts;
```

模块没有返回数据时，先确认 trace 中是否存在 name 为 `gpufreq` 的 `gpu_counter_track`，再检查设备 event 和采集配置。

## 6. GPU memory：总量、allocation 与物理驻留要分开

### 6.1 `gpu_mem_total` 报告累计总量

kernel `gpu_mem_total` tracepoint 的契约是：GPU driver 在 GPU addressable space 发生 allocate、free、import 或 unimport 时，上报：

- GPU id；
- pid，`0` 表示 global total；
- 当前总 size，单位 byte。

这里的 `size` 是更新后的总量，不是本次 allocation 的增量。它也不直接等于：

- 进程 Java/native heap；
- 物理显存或系统内存的唯一驻留量；
- dma-buf 对象数量；
- 当前内存带宽；
- 可以定位到调用栈的泄漏对象。

### 6.2 AOSP GpuService 提供 trace 起点快照

Android 17 的 `GpuMem` 把 eBPF program attach 到 `gpu_mem/gpu_mem_total`，维护 global/per-process 总量 map。`GpuMemTracer` 注册 `android.gpu.memory` data source；trace 开始时遍历 map，发出一组 `GpuMemTotalEvent` 作为初始 counter。

持续变化仍来自 driver 发出的 `gpu_mem_total` event。因此，要得到完整时间线，需要 initial snapshot 和后续 ftrace update 都可用。driver 不发 event、BPF 初始化失败或权限受限时，memory 轨道会缺失或不完整。

下面的配置用于采集 AOSP GPU memory 初值和后续 event：

```textproto
data_sources {
  config {
    name: "android.gpu.memory"
  }
}

data_sources {
  config {
    name: "linux.ftrace"
    ftrace_config {
      ftrace_events: "gpu_mem/gpu_mem_total"
    }
  }
}
```

这段配置不包含调度、FrameTimeline 或 GPU stage。实际诊断还要按问题加入应用线程、SurfaceFlinger 和目标 GPU producer，避免只得到内存轨道。

### 6.3 Vulkan memory tracker 的覆盖范围

`VulkanMemoryEvent` 可以记录 driver allocation scope、device memory、buffer、image 的 create/destroy/bind，以及 memory type、heap、handle 和 annotation。它适合解释 Vulkan allocation 生命周期。

它不覆盖：

- 原生 GLES driver 的完整 allocation；
- ANGLE 或引擎之外的所有 vendor 私有池；
- HWC、Camera、Codec 与其他进程的全部 dma-buf；
- kernel reclaim、IOMMU mapping 和物理页生命周期的完整细节。

内存结论应组合 `gpu_mem_total`、Vulkan allocation、dma-buf 统计、进程生命周期和厂商工具。

## 7. Trace Processor 表怎么读

### 7.1 `gpu_slice` 不是纯 render-stage 表

Android 17 的 `gpu_slice` 是一个 view，它从通用 `slice` 表筛选三类 track：

- `gpu_render_stage`；
- `vulkan_events`；
- `gpu_log`。

所以直接 `SELECT * FROM gpu_slice` 会把 Vulkan submission event 和 GPU log 也混进来。下面的 SQL 用于只查看 render stage：

```sql
SELECT
  s.ts / 1e6 AS ts_ms,
  s.dur / 1e6 AS dur_ms,
  p.name AS process_name,
  t.name AS hardware_queue,
  s.name AS stage_name,
  s.submission_id,
  s.context_id,
  s.render_pass,
  s.command_buffer
FROM gpu_slice AS s
JOIN track AS t
  ON s.track_id = t.id
LEFT JOIN process AS p
  ON s.upid = p.upid
WHERE t.type = 'gpu_render_stage'
ORDER BY s.ts;
```

结果里的 stage name 与 queue name 由 producer specification 决定。`submission_id`、render pass 和 command buffer 都可能为空，SQL 不能把空值补成不存在的关联。

### 7.2 `gpu_counter_track` 保存 descriptor 语义

下面的 SQL 用于列出 GPU counter 样本及其 track 元数据：

```sql
SELECT
  c.ts / 1e6 AS ts_ms,
  t.gpu_id,
  t.name AS counter_name,
  t.unit,
  c.value
FROM counter AS c
JOIN gpu_counter_track AS t
  ON c.track_id = t.id
ORDER BY c.ts, t.name;
```

这段查询用于核对原始样本。做利用率、平均频率或带宽统计时，还要转换为 duration interval，并处理 trace 边界。

### 7.3 per-process GPU memory 使用 stdlib

下面的 SQL 用于读取带 duration 的进程 GPU memory：

```sql
INCLUDE PERFETTO MODULE android.gpu.memory;

SELECT
  m.ts / 1e6 AS ts_ms,
  m.dur / 1e6 AS dur_ms,
  p.name AS process_name,
  m.gpu_memory
FROM android_gpu_memory_per_process AS m
JOIN process AS p
  USING (upid)
ORDER BY m.ts;
```

表为空时，回到 `android.gpu.memory` 初始快照、`gpu_mem_total` event 和 driver 上报契约逐层检查。

## 8. 把 GPU 数据放回一帧的显示路径

### 8.1 Native Graphics / Game 应从自有 producer 线程开始

Native Graphics 和游戏的主体画面常由 render/RHI 线程通过 EGL 或 Vulkan 提交到独立 Surface。普通 HWUI RenderThread 可能只绘制宿主壳。

每帧至少要区分：

```text
input / game logic
  → render preparation
  → API submission
  → GPU queue execution
  → producer completion fence
  → queueBuffer / present
  → SurfaceFlinger latch
  → HWC or RenderEngine composition
  → display present
```

这条顺序用于判断相邻证据属于哪个阶段。`eglSwapBuffers()`、`vkAcquireNextImageKHR()` 或 `vkQueuePresentKHR()` 的长 slice 可能包含 free slot、release fence、swap interval、driver flush 或主动 frame pacing，不能直接贴上 “GPU shader slow”。

### 8.2 App GPU 与 SurfaceFlinger GPU 要分开

一个游戏 buffer 可以先由 App GPU 渲染，再被 HWC 以 DEVICE composition 直接扫描输出；这时 SurfaceFlinger 没有 client composition，App 仍可能 GPU bound。

另一种情况是 App buffer ready 很早，但 SurfaceFlinger 需要 RenderEngine 做 CLIENT composition。GPU trace 里后半段 workload 属于 SurfaceFlinger，不能全部计入 App。

判断时检查：

- render-stage 对应的 process/context；
- 应用 submission 与 producer fence；
- SurfaceFlinger composition type；
- RenderEngine GPU 工作；
- HWC present 与 display fence。

### 8.3 FrameTimeline 只负责帧计划与分类

FrameTimeline 能告诉你 App/SF expected 和 actual 是否偏离，以及 jank 分类。它不会提供 shader、render pass 或硬件 counter。

独立 SurfaceView/native Surface 还可能缺少完整 App FrameTimeline。此时从目标 layer、buffer frame number、FrameTracer、acquire fence、HWC present 和 display fence 补齐。不要把宿主 Activity 的 token 当成游戏 swapchain frame id。

## 9. 一套低扰动到高粒度的排查顺序

### 第一步：固定测试条件

记录设备、系统 build、GPU、driver、刷新率、分辨率、画质、引擎、graphics API、frame pacing、温度、Game Mode 和持续运行时间。

### 第二步：查询数据源

保存 `perfetto --query --long` 输出和可用 ftrace event。先确认设备能提供哪些证据，再写 TraceConfig。

### 第三步：低扰动找到问题窗口

先采集 sched、应用 marker、FrameTimeline、FrameTracer、BufferQueue、frequency/memory，以及 low-overhead render stages。找到具体进程、Surface 和连续异常帧。

### 第四步：重建逐帧顺序

对齐 CPU submission、GPU stage、producer fence、queue、latch 和 present。GPU stage 晚只是候选原因；CPU submission 本来就晚时，先处理 CPU 依赖。

### 第五步：短时加入 counter 或详细 stage

根据设备 descriptor 选择少量 counter。一次验证一个假设，例如：

- 降低 render scale 是否缩短 GPU stage；
- 关闭一个 post-processing pass 是否降低 bandwidth/fragment 指标；
- 预热 pipeline cache 是否消除同步编译长帧；
- 限制 in-flight frame 是否降低输入到显示延迟。

### 第六步：需要资源级证据时做 frame capture

Perfetto 把问题定位到某个 GPU 窗口后，再用 AGI、RenderDoc、Sokatoa 或厂商 profiler 检查 draw、shader、pipeline、texture 和微架构 counter。frame capture 会改变时序，不能替代原始系统 trace。

### 第七步：恢复量产配置并复测

关闭 fixed clock、instrumentation、强制 composition 和调试 layer。使用量产配置重复多轮，比较 frame-time 分布、GPU window、输入延迟、温度和功耗。

## 10. 现象与证据门槛

| 现象 | 可以先怀疑 | 还需要的证据 |
|---|---|---|
| CPU submission 早，GPU stage 跨过 deadline | App GPU workload 或 driver queue | context/process、producer fence、单变量对照 |
| GPU frequency 长时间高 | DVFS 选择高频 | busy/stage/counter、thermal 与策略 |
| GPU frequency 低且 stage 变长 | thermal/power 限制或负载轻 | thermal、counter、历史频率、同场景基线 |
| memory 总量持续增长 | allocation/import 未回落 | 生命周期、Vulkan event、dma-buf、进程销毁后状态 |
| `eglSwapBuffers()` 周期性变长 | queue-stuffing 或 pacing | pending buffer、release fence、present interval |
| App buffer ready，DisplayFrame 仍 late | SF/HWC/display | composition、HWC validate/present、display fence |
| `gpu_slice` 有很长事件 | 某类 GPU/Vulkan/log track 很长 | 先按 `track.type` 分类，再解释 |
| trace 没有 GPU stage | producer/配置/权限缺失 | data-source descriptor 与采集日志 |

## 11. Android 17 exact tag 中不存在的“统一 GPU 调试框架”

现稿常见的几类说法需要明确删除：

- `frameworks/native/services/surfaceflinger/Flinger.cpp` 不是 Android 17 源码路径，主文件是 `SurfaceFlinger.cpp`；
- exact tag 中没有 `SurfaceFlinger::setDebugProperties()`、`mGpuTracingEnabled`、`mGpuCounters` 这组统一控制实现；
- Android 公开 API 中没有 `Choreographer.getGpuPerfMetrics()`；
- Trace Processor 没有名为 `gpu_state` 的标准表；
- `GpuRenderStageEvent` 在 `android-12.0.0_r1` 已经存在，不能写成 Android 17 全新引入 GPU render-stage tracing；当前 `gpu_slice` 仍要按 Android 17 schema 解读；
- AOSP 没有自动分析 shader、合并 draw call、预测优化收益或上传云端做跨设备对比的 GPU AI 服务；
- Android Studio、APA、AGI 和第三方工具有各自发布周期，不能把某个 IDE 功能写成 Android 17 平台 API。

Android 17 源码里确有 `RenderCommandBuffer`，路径在 `frameworks/native/libs/gui` 与 `libs/ipcrenderbuffer`。`SurfaceComposerClient` 注释把它标为 WIP：客户端通过共享内存把绘制命令交给 SurfaceFlinger，作为 buffer composition 的替代路径。它不是从 Choreographer 到 GPU submission 的通用监控器，也不是 Perfetto GPU counter 框架。

## 12. 版本边界

| 版本 | 与本章相关的解释边界 |
|---|---|
| Android 12 / API 31 | FrameTimeline 成为现代帧计划/jank 基线；GPU proto、counter 和 memory tracing 的部分能力更早已经存在 |
| Android 13 / API 33 | AIDL HWC 与现代显示诊断主线延续；GPU producer 能力仍由设备决定 |
| Android 14 / API 34 | Perfetto GPU/FrameTimeline 继续演进；不能把工具版本变化写成统一平台 GPU API |
| Android 15 / API 35 | 16KB page size 影响 native profiler/layer 可运行性，不改变 GPU trace proto 的基本证据边界 |
| Android 16 / API 36 | GPU trace 主数据模型继续演进；producer、权限和设备支持仍需逐机查询 |
| Android 17 / API 37 | 本章锚点；`GpuRenderStagesConfig`、GPU proto、parser、`gpu_slice`/counter/stdlib 表均按 `android-17.0.0_r1` 核对 |

“Android 17 tag 中存在”不等于“Android 17 首次加入”。涉及首引版本时，应比较历史 tag 或官方 release note，不能从文件 copyright 年份推断正式发布版本。

## 总结

Android 17 的 GPU trace 不是一个由 SurfaceFlinger 统一采集的总线。render stage 和硬件 counter 依赖 GPU producer，frequency 依赖设备 tracepoint，GPU memory 由 driver event、GpuService 初值与 Trace Processor counter 共同组成，Vulkan memory tracker 只覆盖被 instrumentation 的 Vulkan allocation。

分析时先查询 descriptor，再按目标 Surface 和 producer 线程找到 CPU submission，用 `gpu_render_stage` 过滤后的 slice 定位 GPU 窗口，用带 descriptor 的 counter 解释资源压力，最后沿 producer fence、SurfaceFlinger 与 display present 验证用户可见结果。数据缺失只能说明证据不足，不能说明 GPU 空闲。
