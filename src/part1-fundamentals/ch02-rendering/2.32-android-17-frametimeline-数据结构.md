# 2.32 Android 17 FrameTimeline 数据结构

## 概述

FrameTimeline 在 Android 12 引入后，经过六个版本的迭代，到 Android 17 已经成为 SurfaceFlinger 中最复杂的数据追踪子系统之一。它的数据结构横跨 Perfetto Proto 定义、SurfaceFlinger C++ 类层次、以及 App 侧 Java API 三个层面。

本节从 **源码数据结构视角** 解析 FrameTracer 与 FrameTimeline 的内部架构——包括 BufferEvent Proto 的 13 种类型定义、SurfaceFrame 的生命周期状态机、TokenManager 的预测 token 管理、以及 FrameTracer 的 pending fence 队列机制。

> **与其它章节的分工**：§2.23 七点五节从 VSync 调度视角介绍了 FrameTracer/FrameTimeline 的数据源配置和阈值；§2.30 从性能诊断视角讨论了 GPU/CPU 合成边界判定的应用方法。本节聚焦数据结构本身——Proto 字段定义、C++ 类层次、状态机转换——是理解前两节分析结论的底层基础。

## 一、FrameTracer：Buffer 级事件追踪器

### 1.1 数据源与 Proto 定义

FrameTracer 向 Perfetto 注册的数据源名为 `android.surfaceflinger.frame`（常量 `kFrameTracerDataSource`，定义于 `FrameTracer.h:90`）。其 Proto 格式为 `perfetto::protos::pbzero::GraphicsFrameEvent::BufferEvent`。

[已验证: AOSP android-17.0.0_r1, frameworks/native/services/surfaceflinger/FrameTracer/FrameTracer.h:90]

**BufferEvent Proto 核心字段**：

| 字段 | 类型 | 含义 |
|------|------|------|
| `buffer_id` | `uint32` | Buffer ID，由 BufferQueue 分配 |
| `frame_number` | `uint64` | 帧序号，Layer 级递增 |
| `layer_name` | `string` | Layer 名称（用于 Perfetto UI 显示） |
| `type` | `BufferEventType` (enum) | 事件类型，共 13 种 |
| `duration_ns` | `uint64` | 事件持续时间（用于 span 类型事件） |
| `timestamp` | `uint64` | 事件时间戳，时钟源 `BUILTIN_CLOCK_MONOTONIC` |

[已验证: AOSP android-17.0.0_r1, external/perfetto/protos/perfetto/trace/android/graphics_frame_event.proto]

### 1.2 13 种 BufferEventType 枚举

Proto 中定义了 13 种 Buffer 事件类型（`graphics_frame_event.proto`），但从 Android 12 到 Android 17（`android-17.0.0_r1`），该 proto 文件完全一致，未发生变更：

| 编号 | 事件类型 | AOSP 中的 emit 站点 | 语义 |
|------|---------|---------------------|------|
| 1 | `DEQUEUE` | `Layer.cpp:982-985` | App 侧 dequeueBuffer，buffer 从 FREE → DEQUEUED |
| 2 | `QUEUE` | `Layer.cpp:986-987` | App 侧 queueBuffer，buffer 从 DEQUEUED → QUEUED |
| 3 | `CANCEL` | — | 取消事件（proto 占位符，AOSP 无 emit） |
| 4 | `ACQUIRE_FENCE` | `Layer.cpp:1269-1270` | acquire fence signal，buffer 从 QUEUED → ACQUIRED |
| 5 | `LATCH` | `Layer.cpp:1271-1272` | SurfaceFlinger latch 该 buffer 进入合成 |
| 6 | `HWC_COMPOSITION_QUEUED` | **无 AOSP emit** | HWC 合成完成（OEM 自定义发射） |
| 7 | `FALLBACK_COMPOSITION` | `Layer.cpp:1453-1455` | GPU/RenderEngine 合成完成时间戳 |
| 8 | `PRESENT_FENCE` | `Layer.cpp:1476 / 1496-1498` | present fence signal 或反推时间戳 |
| 9 | `RELEASE_FENCE` | buffer release 路径 | buffer 释放同步信号 |
| 10 | `MODIFY` | — | buffer 属性修改（proto 占位符） |
| 11 | `ATTACH` | — | buffer attach 到 slot（proto 占位符） |
| 12 | `DETACH` | — | buffer detach 从 slot（proto 占位符） |
| 13 | `CANCEL` | — | 取消（重复定义） |

[已验证: AOSP android-17.0.0_r1, 逐文件确认 FrameTracer.cpp/Layer.cpp/SurfaceFlinger.cpp/HWComposer.cpp/AidlComposerHal.cpp/OutputLayer.cpp/HwcAsyncWorker.cpp 中 type=6 HWC_COMPOSITION_QUEUED 无任何 `traceTimestamp/traceFence` 调用]

**关键发现**：13 种类型中，**AOSP 真正 emit 的只有 6 种**（DEQUEUE、QUEUE、ACQUIRE_FENCE、LATCH、FALLBACK_COMPOSITION、PRESENT_FENCE）。`HWC_COMPOSITION_QUEUED`（type=6）在标准 AOSP 代码中没有任何发射点——它是 proto 中的占位枚举值，部分 OEM（如 Pixel/Samsung）在闭源 HWC HAL callback 中自行发射。

这意味着：如果在 Perfetto trace 中观测到 `HWC_COMPOSITION_QUEUED` 事件，说明该设备的 OEM HWC 实现了自定义 trace 发射；如果没有观测到，不能判定为"未走 HWC 合成"——需要通过 `FALLBACK_COMPOSITION` 的**缺席**来反推走了 HWC 路径。

### 1.3 FrameTracer 内部数据结构

FrameTracer 的 C++ 实现中，核心数据结构是 `TraceTracker`：

```
FrameTracer
├── mTraceTracker: unordered_map<int /* layerId */, TraceTracker>
│   ├── pendingFences: unordered_map<uint64_t /* bufferID */, FencePending>
│   │   └── FencePending { BufferEventType type, startTime, endTime, frameNumber }
│   └── lastTrace: unordered_map<uint64_t /* bufferID */, BufferEvent>
└── mInitializationFlag: std::once_flag
```

**Pending Fence 队列机制**（`FrameTracer.cpp:79-100`）：

Fence 类事件（`ACQUIRE_FENCE`、`RELEASE_FENCE`、`PRESENT_FENCE`）是异步的——emit 事件时 fence 可能尚未 signal。FrameTracer 通过 pending 队列处理这种情况：

1. 当 `traceFence()` 被调用但 fence 未 signal 时，事件进入 `pendingFences[bufferID]` 队列
2. 下次同一 buffer 的 trace 触发时，`tracePendingFencesLocked()` 消费已 signal 的 pending 事件
3. **硬超时保护**：`kFenceSignallingDeadline = 60'000'000'000` ns（60 秒），定义于 `FrameTracer.h:93`。超过 60s 未 signal 的 fence 事件被丢弃，防止 pending 队列无限增长导致 OOM

[已验证: AOSP android-17.0.0_r1, FrameTracer.cpp:79-100, FrameTracer.h:93]

**Span 与 Instant 语义**（`traceSpanLocked:172-181`）：
- fence 事件携带 `startTime` 时，生成 `[startTime, endTime]` 区间的 span 事件
- fence 事件不携带 `startTime` 时，只生成 `endTime` 时刻的 instant 事件

这个语义差异影响了 Perfetto UI 中的呈现方式：span 显示为持续区间 slice，instant 显示为单点标记。

### 1.4 FrameTracer 初始化与热路径

```
FrameTracer::initialize()
  └── std::call_once(mInitializationFlag)
      ├── perfetto::TracingInitArgs { backends = kSystemBackend }
      ├── perfetto::Tracing::Initialize(args)
      └── registerDataSource()  // 注册 DataSourceDescriptor "android.surfaceflinger.frame"
```

初始化使用 `std::call_once` 保证只执行一次。热路径（`traceTimestamp`/`traceFence`）在 trace 关闭时退化为空操作（Perfetto DataSource 的 `trace_checked` 机制），几乎零开销。

[已验证: AOSP android-17.0.0_r1, FrameTracer.cpp:40-55]

## 二、FrameTimeline：帧级时间线追踪器

### 2.1 SurfaceFrame 数据结构

FrameTimeline 的核心数据单元是 `SurfaceFrame`（定义于 `FrameTimeline.h`），它包装了一个 Layer 在一帧中的完整生命周期数据：

```
SurfaceFrame
├── TimelineItem expected  // 预期时间线
│   ├── startTime          // 预期开始渲染时刻
│   ├── endTime            // 预期完成渲染（latch）时刻
│   ├── presentTime        // 预期上屏时刻
│   └── desiredPresentTime // App 通过 setFrameTimeline 声明的目标
├── TimelineItem actual    // 实际时间线
│   ├── startTime          // 实际开始渲染时刻
│   ├── endTime            // 实际完成渲染（latch）时刻
│   └── presentTime        // 实际上屏时刻
├── JankClassificationThresholds thresholds
├── uint64_t frameToken    // 帧标识符（由 TokenManager 分配）
├── JankType jankType      // jank 类型 bitmask
├── JankSeverity severity  // jank 严重度
├── PredictionState predictionState  // 预测状态
└── bool gpuComposition    // 是否涉及 GPU 合成
```

[已验证: AOSP android-17.0.0_r1, frameworks/native/services/surfaceflinger/FrameTimeline/FrameTimeline.h:83-94]

### 2.2 JankClassificationThresholds 阈值结构

```
JankClassificationThresholds
├── presentThreshold  = 2ms   // actual present 偏离 expected 超过此值 → late/early
├── deadlineThreshold = 0ms   // actual endTime 晚于 deadline → late finish
└── startThreshold    = 2ms   // actual startTime 偏离 expected 超过此值 → late/early start
```

这三个阈值是 jank 分类的核心判定参数。SurfaceFlinger 在 `FrameTimeline::finalizeStats()` 中用这些阈值计算每帧的 jank 类型和严重度。

[已验证: AOSP android-17.0.0_r1, FrameTimeline.h:100-105]

### 2.3 Jank 类型 Bitmask 与严重度

FrameTimeline 定义了 13+ 种 jank 类型 bitmask（`jankTypeBitmaskToProto`，`FrameTimeline.cpp`）：

| Jank 类型 | 含义 | isSelfJanky |
|-----------|------|:-----------:|
| `DisplayHAL` | Display HAL 层延迟 | ✗ |
| `SurfaceFlingerCpuDeadlineMissed` | SF CPU 合成超时 | ✗ |
| `SurfaceFlingerGpuDeadlineMissed` | SF GPU 合成超时 | ✗ |
| `AppDeadlineMissed` | App 渲染超时 | ✓ |
| `AppResyncedJitter` | App 与 VSync 重同步抖动 | ✓ |
| `PredictionError` | VSyncPredictor 预测误差 | ✗ |
| `SurfaceFlingerScheduling` | SF 调度延迟 | ✗ |
| `BufferStuffing` | Buffer 积压 | ✗ |
| `SurfaceFlingerStuffing` | SF Buffer 积压 | ✗ |
| `Dropped` | 丢帧（覆写语义） | ✗ |
| `Unknown` | 未知原因 | ✓ |
| `NonAnimating` | 非动画场景的 jank | ✗ |
| `DisplayNotOn` | 显示器关闭状态 | ✗ |
| `DisplayModeChangeInProgress` | 显示模式切换中 | ✗ |
| `DisplayPowerModeChangeInProgress` | 显示电源模式切换中 | ✗ |

**`isSelfJanky()` 判定**（`FrameTimeline.cpp:562-573`）：只有 `AppDeadlineMissed | Unknown | AppResyncedJitter` 三种类型被视为"App 自己造成的 jank"。这意味着——把完整 jank bitmask 直接归因给 App 是误读，SF 调度、HWC、Dropped 等原因都不在 self-janky 集合中。

**严重度计算**（`calculateJankSeverity`）：使用 Google 内部的 `go/refined-jank-metric` 公式，输出 `JankSeverityType { None, Partial, Full, Unknown }` 四级以及 0~1 的连续分数。

[已验证: AOSP android-17.0.0_r1, FrameTimeline.cpp]

### 2.4 TokenManager 与预测 token 生命周期

TokenManager 是 FrameTimeline 中管理 VSync 预测 token 的组件：

```
TokenManager
├── mTokens: unordered_map<int64_t /* token */, nsecs_t /* predictedTime */>
├── kMaxTokenRetention = 120ms  // 默认 TTL
└── mNextTokenId: int64_t       // 递增 token ID 生成器
```

**Token 生命周期**：
1. `manager.generateToken()` → 分配新 token 并记录预测时间
2. App 通过 `Choreographer.FrameData` 拿到 token 对应的帧调度计划
3. App 在提交 buffer 时携带 token（`setFrameTimeline(token)`）
4. SurfaceFlinger 收到 buffer 后通过 token 查找预测时间
5. 如果 token 已过期（超过 120ms），`PredictionState` 标记为 `Expired`

**120ms TTL 的物理含义**：在 120Hz 刷新率下，120ms = 14.4 个 VSync 周期。超过此时间未提交的 buffer 被视为"预测已失效"，FrameTimeline 在 trace 中标注 `PredictionState::Expired`，避免把"丢失预测"误归类为 jank。

[已验证: AOSP android-17.0.0_r1, FrameTimeline.cpp TokenManager 实现]

## 三、FALLBACK_COMPOSITION 与 HWC_COMPOSITION_QUEUED 的真实语义

### 3.1 FALLBACK_COMPOSITION：GPU 合成的真实时间戳

`FALLBACK_COMPOSITION`（type=7）的 emit 站点在 `Layer::onCompositionPresented`（`Layer.cpp:1453-1455`）：

```cpp
// Layer.cpp:1453-1455 (android-17.0.0_r1 简化)
if (outputLayer->getState().clientCompositionTimestamp.has_value()) {
    mFlinger->mFrameTracer->traceTimestamp(layerID, bufferID, frameNumber,
        outputLayer->getState().clientCompositionTimestamp.value(),
        FrameTracer::FrameEvent::FALLBACK_COMPOSITION);
}
```

**关键语义**：`FALLBACK_COMPOSITION` 的时间戳来自 `clientCompositionTimestamp`——这是 **GPU/RenderEngine 实际完成合成的时间**，而不是决定走 GPU 合成的瞬间。因此：
- 它是 GPU 合成耗时的真实指标（GPU rendering completion timestamp）
- 它的出现意味着该帧确实走了 GPU 合成路径
- 它的缺席意味着该帧可能走了 HWC 路径（但不能 100% 确定——可能是 trace 配置缺失）

### 3.2 HWC_COMPOSITION_QUEUED：Proto 占位符

如前所述（§1.2），`HWC_COMPOSITION_QUEUED`（type=6）在 AOSP 标准代码中没有任何 emit 调用。验证方法：在 `android-17.0.0_r1` 的以下文件中搜索 `traceTimestamp` 和 `traceFence` 调用，均未发现使用 `HWC_COMPOSITION_QUEUED` 类型：

- `FrameTracer.cpp` — 无
- `Layer.cpp` — 无
- `SurfaceFlinger.cpp` — 无
- `HWComposer.cpp` — 无
- `AidlComposerHal.cpp` — 无
- `OutputLayer.cpp` — 无
- `HwcAsyncWorker.cpp` — 无

**结论**：`HWC_COMPOSITION_QUEUED` 是 proto 中的预留枚举值，等待 OEM 在 HWC HAL callback 中自行实现。标准 AOSP 不提供 HWC 合成的时间戳追踪——这限制了在不依赖 OEM 实现的情况下精确测量 HWC 合成延迟的能力。

[已验证: AOSP android-17.0.0_r1, 逐文件确认无 emit 调用]

### 3.3 GPU/HWC 合成边界的判定方法

由于 `HWC_COMPOSITION_QUEUED` 在标准 AOSP 中不发射，判定一帧是否走了 GPU 合成需要用**反向推理**：

| 观测结果 | 判定 |
|---------|------|
| `FALLBACK_COMPOSITION` 事件存在 | ✅ 该帧走了 GPU 合成（确认） |
| `FALLBACK_COMPOSITION` 事件缺席 | ⚠️ 该帧**可能**走了 HWC 合成（但需排除 trace 配置缺失） |
| FrameTimeline `gpu_composition = true` | ✅ 该帧走了 GPU 合成（FrameTimeline 层面确认） |
| FrameTimeline `gpu_composition = false` | ✅ 该帧走了 HWC 合成 |

**`requiresClientComposition()` 源码判定**（`OutputLayer.cpp:1137-1140`）：

```cpp
bool OutputLayer::requiresClientComposition() const {
    const auto& state = getState();
    return !state.hwc || state.hwc->hwcCompositionType == Composition::CLIENT;
}
```

边界条件：① `state.hwc == nullptr`（无 HWC 关联，走 GPU）；② `hwcCompositionType == Composition::CLIENT`（HWC 决策回退到 GPU）；其余 6 种合成类型（DEVICE / SOLID_COLOR / CURSOR / SIDEBAND / DISPLAY_DECORATION / REFRESH_RATE_INDICATOR）走 HWC 路径。

[已验证: AOSP android-17.0.0_r1, OutputLayer.cpp:1137-1140]

> 性能诊断中如何利用这些判定指标，详见 §2.30「Android 17 FrameTimeline GPU/CPU 合成边界判定机制」。

## 四、合成队列性能分析

### 4.1 FrameTracer 事件链与 Buffer 状态机映射

FrameTracer 的 6 种 AOSP emit 事件完整映射了 Buffer 的状态机转换：

```
FREE ──DEQUEUE──→ DEQUEUED ──QUEUE──→ QUEUED ──ACQUIRE_FENCE──→ ACQUIRED ──LATCH──→ [合成中] ──PRESENT_FENCE──→ [已上屏]
                                                                                      └──RELEASE_FENCE──→ FREE
```

| Buffer 状态转换 | FrameTracer 事件 | 时间戳来源 |
|----------------|-----------------|-----------|
| FREE → DEQUEUED | `DEQUEUE` (type=1) | `systemTime()` 即时 |
| DEQUEUED → QUEUED | `QUEUE` (type=2) | `systemTime()` 即时 |
| QUEUED → ACQUIRED | `ACQUIRE_FENCE` (type=4) | fence signal 时间戳（可能延迟） |
| ACQUIRED → 合成 | `LATCH` (type=5) | `systemTime()` 即时 |
| 合成完成 | `FALLBACK_COMPOSITION` (type=7) | `clientCompositionTimestamp`（仅 GPU 路径） |
| 上屏 | `PRESENT_FENCE` (type=8) | present fence signal 或反推时间戳 |
| 回收 | `RELEASE_FENCE` (type=9) | release fence signal |

**关键时间间隔**：
- `QUEUE → LATCH`：buffer 在 BufferQueue 中等待被 SurfaceFlinger 消费的时间。此间隔过长说明 SF latch 不及时（VSync-sf offset 问题或 SF 主线程阻塞）。
- `LATCH → PRESENT_FENCE`：从 latch 到上屏的总合成 + 显示延迟。此间隔包含 HWC 合成或 GPU 合成 + display 扫描输出时间。
- `LATCH → FALLBACK_COMPOSITION`：仅 GPU 路径，GPU 合成的实际耗时。

### 4.2 validateDisplay / presentOrValidate 状态机

SurfaceFlinger 向 HWC 提交合成请求时，存在快速路径和慢速路径（`HWComposer.cpp:537-628`）：

**快速路径**（`presentOrValidate`，state==Presented）：
- HWC 直接 present，跳过 `getChangedCompositionTypes`/`acceptChanges` 等 IPC
- 节省约 100-300μs 的 HWC IPC 开销
- 条件：`canSkipValidate` 返回 true（frameUsesClientComposition==false 且 earliestPresentTime 可用且未过期）

**慢速路径**（`validate` → `acceptChanges` → `present`）：
- 完整执行 5 个 IPC：`getChangedCompositionTypes`、`getRequests`、`clientTargetProperty`、`getRequestedLuts`、`acceptChanges`
- 当帧需要 GPU 合成时必须走此路径

[已验证: AOSP android-17.0.0_r1, HWComposer.cpp:537-628]

### 4.3 Perfetto SQL：GPU stall 识别

通过 FrameTracer 事件链的 SQL 查询，可以精确定位 GPU 合成瓶颈：

```sql
-- LATCH → FALLBACK_COMPOSITION 间隔 = GPU 实际渲染耗时
SELECT
  layer_name,
  frame_number,
  latch_ts / 1e9 as latch_s,
  fallback_ts / 1e9 as fallback_s,
  (fallback_ts - latch_ts) / 1e6 as gpu_render_ms
FROM (
  SELECT
    a.layer_name,
    a.frame_number,
    MAX(CASE WHEN a.type = 5 THEN a.timestamp END) AS latch_ts,
    MAX(CASE WHEN a.type = 7 THEN a.timestamp END) AS fallback_ts
  FROM android.surfaceflinger.frame a
  GROUP BY a.layer_name, a.frame_number
  HAVING latch_ts IS NOT NULL AND fallback_ts IS NOT NULL
)
ORDER BY gpu_render_ms DESC
LIMIT 20;
```

此查询过滤出同时包含 LATCH 和 FALLBACK_COMPOSITION 的帧，计算两者间隔即为 GPU 合成实际耗时。

> 更多 Perfetto SQL 分析模式详见 §13.17「Android 17 数据源」和 §2.30「FrameTimeline GPU/CPU 合成边界」。

## 五、合成事件时序精度

### 5.1 时间戳类型与精度

FrameTracer/FrameTimeline 中的时间戳分为三类，精度特征不同：

| 时间戳类型 | 时钟源 | 精度 | 获取方式 |
|-----------|--------|------|---------|
| 即时时间戳 | `CLOCK_MONOTONIC` | 纳秒级（~μs 抖动） | `systemTime()` 直接读取 |
| Fence 时间戳 | `CLOCK_MONOTONIC` | 纳秒级（fence signal 时刻） | fence signal 后通过 callback 获取 |
| 反推时间戳 | `CLOCK_MONOTONIC` | ~100μs 误差 | present fence signal 时刻 − 已知 display 延迟 |

**即时时间戳**（DEQUEUE、QUEUE、LATCH）：在 SurfaceFlinger 主线程中通过 `systemTime()` 获取，精度受 CPU 频率和系统负载影响，通常在微秒级。

**Fence 时间戳**（ACQUIRE_FENCE、RELEASE_FENCE、PRESENT_FENCE）：通过 Linux sync fence 的 callback 获取。Fence signal 的时刻由硬件（GPU/HWC/Display 驱动）决定，精度取决于驱动实现。FrameTracer 通过 pending 队列机制异步处理这些时间戳。

**反推时间戳**：当 present fence 无法直接获取时（部分虚拟显示或 OEM 实现不返回 present fence），SurfaceFlinger 使用 `expectedPresentTime + compositeOffset` 反推。`Layer.cpp:1496-1498` 中的逻辑：
- 如果 present fence 有效，使用 fence signal 时间
- 如果 present fence 无效，使用 `systemTime()` 作为 fallback
- 误差通常在 100μs 以内（取决于 VSync 预测精度）

[已验证: AOSP android-17.0.0_r1, Layer.cpp:1476-1498]

### 5.2 60s Fence 超时对数据完整性的影响

`kFenceSignallingDeadline = 60s` 意味着如果 fence 在 60 秒内未 signal，该 fence 事件被丢弃。这对数据完整性有直接影响：

- **正常场景**：fence 通常在 1-2 帧内（16-33ms @60Hz）signal，60s 超时不会触发
- **异常场景**：GPU hang、HWC crash、驱动超时等情况下 fence 可能永久不 signal。60s 超时确保 pending 队列不会无限增长
- **数据缺失**：被超时丢弃的事件在 Perfetto trace 中表现为"事件链断裂"——例如只有 LATCH 没有 PRESENT_FENCE 的帧

在分析 Perfetto trace 时，如果发现大量帧缺失 PRESENT_FENCE 事件，首先应该排查是否有 GPU/HWC 异常导致 fence 超时。

### 5.3 FrameTimeline 事件对齐机制

FrameTimeline 通过 `frameToken` 实现 App 侧和 SurfaceFlinger 侧的事件对齐：

1. **Token 分配**：VSyncPredictor 预测下一个 VSync 时刻，TokenManager 生成对应 token
2. **Token 传递**：Choreographer 通过 `VsyncEventData` 将 token 传递给 App
3. **Token 使用**：App 通过 `BLASTBufferQueue::setFrameTimeline(token)` 将 token 与 buffer 关联
4. **Token 消费**：SurfaceFlinger latch buffer 时读取 token，在 `FrameTimeline::addSFFramePrediction()` 中关联预测数据和实际数据

这种设计确保了即使 App 和 SF 运行在不同进程/不同时间线上，也能通过 token 精确关联每一帧的预期和实际数据。

## 扩展

### 🔸 双数据源融合算法

FrameTracer（`android.surfaceflinger.frame`）和 FrameTimeline（`android.surfaceflinger.frametimeline`）是两个独立的 Perfetto 数据源。将两者融合分析可以构建完整的帧诊断视图：

- **FrameTracer** 提供 buffer 级事件链（DEQUEUE → QUEUE → LATCH → COMPOSITION → PRESENT）
- **FrameTimeline** 提供帧级 jank 分类（Expected vs Actual 偏差 + jank bitmask + severity）
- **关联键**：`frame_number` + `layer_name` 联合键（两个数据源的 `buffer_id` 字段语义不同，不能直接 join）

融合后的诊断流程：
1. 在 FrameTimeline 中定位 jank 帧（红色/黄色 slice）
2. 通过 frame_token 找到对应的 FrameTracer 事件链
3. 分析事件链中哪个环节（QUEUE→LATCH 或 LATCH→PRESENT）耗时最长
4. 结合 `gpu_composition` 标志确定是 GPU 合成还是 HWC 路径

### 🔸 OEM 定制实现分析

不同 OEM 对 FrameTracer/FrameTimeline 的定制程度不同：

| OEM | HWC_COMPOSITION_QUEUED | FrameTimeline 完整度 | 已知差异 |
|-----|:----------------------:|:-------------------:|---------|
| Pixel (Google) | ✓（闭源 HWC） | 完整 | 参考实现 |
| Samsung | ✓（闭源 HWC） | 完整 | OneUI 可能调整 VSync offset |
| 小米 | 部分 | 完整 | MIUI HWC 可能添加自定义 trace 事件 |
| 华为 | ✗ | 部分 | HMS 不使用标准 AOSP FrameTimeline |

**建议**：在性能基准测试中标注设备型号，因为 OEM 定制可能导致 FrameTimeline 数据不完整或行为差异。

[待验证: 具体 OEM 设备的 FrameTimeline 数据完整性需要通过多设备实测来评估]

### 🔸 渲染性能诊断应用

基于本节描述的数据结构，可以设计更精确的渲染性能诊断流程：

1. **Buffer 生命周期分析**：通过 FrameTracer 的 6 种事件重建每帧 buffer 的完整状态机转换，定位阻塞点
2. **Jank 归因精确化**：不仅看 `isSelfJanky()`，还看完整 bitmask 中各 bit 的组合模式（例如 `SurfaceFlingerGpuDeadlineMissed | PredictionError` 表示 GPU 合成负载导致预测失效）
3. **Token 过期分析**：监控 `PredictionState::Expired` 的比例，如果持续偏高说明 VSyncPredictor 需要重新校准

> 实际性能诊断案例分析详见 §2.30 的三个案例（列表滑动卡顿、游戏画面撕裂、复杂半透明 UI 的 GPU 合成瓶颈）。
