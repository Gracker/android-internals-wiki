# 2.32 Android 17 FrameTimeline 数据结构

Android 图形 trace 中有两个名称相近、用途不同的数据源：

- `android.surfaceflinger.frame` 由 `FrameTracer` 产生，记录一块 buffer 从 dequeue、queue 到 latch、present 的阶段事件；
- `android.surfaceflinger.frametimeline` 由 `FrameTimeline` 产生，用预测时间线和完成时间线描述 App `SurfaceFrame` 与 SurfaceFlinger `DisplayFrame`，并给出 jank 分类。

混用两者会产生几类典型误判：把 data-source 名称当成 SQL 表名，把 BufferQueue frame number 当成 FrameTimeline token，把 client composition 的准备时间当成 GPU 完成时间，以及用某个枚举事件的缺席证明 HWC 路径。

以下讨论以 Android 17 / API 37 / `android-17.0.0_r1`、对应版本的 Perfetto 和内核 `android17-6.18-2026-06_r6` 为验证边界。

FrameTimeline 对标准 App Window 的覆盖最完整。Perfetto 官方文档仍明确写着 SurfaceView 不受完整支持；遇到 Camera、Video、SurfaceView、游戏或自研 renderer，还要补充 layer、BufferQueue、fence 与 producer 线程证据。

## 1. 两套数据模型各自回答什么

两套模型的边界如下：

| 维度 | FrameTracer | FrameTimeline |
|---|---|---|
| 数据源 | `android.surfaceflinger.frame` | `android.surfaceflinger.frametimeline` |
| 核心标识 | buffer id、frame number、layer name | surface frame token、display frame token、pid、layer name |
| 主要问题 | buffer 在 producer、fence、SF 与 display 阶段停了多久 | expected 与 actual 是否偏离，谁被分类为 jank |
| Trace Processor 入口 | `frame_slice` | `expected_frame_timeline_slice`、`actual_frame_timeline_slice` |
| 适合场景 | buffer 阶段拆分、queue/acquire/latch/present | 标准窗口帧、App/SF deadline、jank 类型 |

一条 FrameTimeline `SurfaceFrame` 不等于一块 GraphicBuffer。它也可以表示没有 buffer 的 SurfaceControl transaction；源码用 `is_buffer` 区分 buffer frame 与动画/状态 frame。

## 2. FrameTracer：buffer 事件数据结构

### 2.1 Proto 没有独立 timestamp 字段

`GraphicsFrameEvent::BufferEvent` 的 Android 17 定义只有五个字段：

| 字段 | Proto 类型 | 说明 |
|---|---|---|
| `frame_number` | `uint32` | 该 layer 的 buffer frame number |
| `type` | `BufferEventType` | 事件类型 |
| `layer_name` | `string` | SurfaceFlinger layer 名称 |
| `duration_ns` | `uint64` | 可选；大于 0 时形成 duration event |
| `buffer_id` | `uint32` | buffer 标识 |

事件时间放在外层 `TracePacket.timestamp`，`FrameTracer` 同时把 clock id 设为 `BUILTIN_CLOCK_MONOTONIC`。原始 C++ 调用接受 `uint64_t bufferID` 和 `uint64_t frameNumber`，写入 Proto 时都会收窄到 `uint32`；长时间运行或跨进程分析时，不能把这两个字段当成全局永久 ID。

### 2.2 13 个非零枚举值

Proto 中 0 是 `UNSPECIFIED`，1—13 是以下事件：

| 值 | 枚举 | Android 17 AOSP SurfaceFlinger 是否发射 |
|---:|---|:---:|
| 1 | `DEQUEUE` | 是 |
| 2 | `QUEUE` | 是 |
| 3 | `POST` | 否 |
| 4 | `ACQUIRE_FENCE` | 是 |
| 5 | `LATCH` | 是 |
| 6 | `HWC_COMPOSITION_QUEUED` | 否 |
| 7 | `FALLBACK_COMPOSITION` | 是 |
| 8 | `PRESENT_FENCE` | 是 |
| 9 | `RELEASE_FENCE` | 否 |
| 10 | `MODIFY` | 否 |
| 11 | `DETACH` | 否 |
| 12 | `ATTACH` | 否 |
| 13 | `CANCEL` | 否 |

“Proto 定义了事件”只表示 trace 格式可以容纳它。`android-17.0.0_r1` 的标准 SurfaceFlinger 生产代码只调用六种；测试代码引用其他枚举不能算作设备运行时发射点。

### 2.3 六种 AOSP 事件的精确来源

`Layer.cpp` 的调用点给出了这些事件的含义：

| 事件 | 时间来源 | 能证明什么 |
|---|---|---|
| `DEQUEUE` | transaction 中的 `BufferData.dequeueTime` | producer 开始持有本次 buffer 的时刻 |
| `QUEUE` | buffer transaction 的 `postTime` | producer 把 buffer update 交给 SF transaction 的时刻 |
| `ACQUIRE_FENCE` | acquire fence signal time | producer 的异步写入何时完成 |
| `LATCH` | SF 的 `latchTime` | SF 何时采纳该 buffer |
| `FALLBACK_COMPOSITION` | client composition layer 准备时的 `systemTime()` | 该 layer 被纳入 client/GPU composition 准备 |
| `PRESENT_FENCE` | present fence signal；无有效 fence 时使用 HWC present timestamp 估算 | 对应 display frame 的 present 时间锚点 |

`QUEUE` 发生不代表 GPU 已写完 buffer，后面的 acquire fence 才说明 producer 写入完成。Android 13 起允许在满足条件时先 latch 未 signal 的 buffer，所以 `LATCH` 与 `ACQUIRE_FENCE` 也不必保持固定先后。

### 2.4 `FALLBACK_COMPOSITION` 不是 GPU 完成时间

Android 17 `CompositionEngine::Output` 在 `prepareClientComposition()` 返回 layer settings 后写入：

```cpp
layer->editState().clientCompositionTimestamp = systemTime();
```

`Layer::onCompositionPresented()` 随后把这个值作为 `FALLBACK_COMPOSITION` 事件发给 FrameTracer，并为关联的 `SurfaceFrame` 调用 `setGpuComposition()`。

这枚时间戳确认 client composition layer 已经准备，不能替代 RenderEngine GPU fence。判断 GPU 工作何时完成时，应查看 FrameTimeline `DisplayFrame` 使用的 GPU fence、RenderEngine/GPU 轨道以及最终 present。

`HWC_COMPOSITION_QUEUED` 在 Android 17 AOSP SurfaceFlinger 中没有生产调用。它的缺席不能证明 frame 走了 client composition；`FALLBACK_COMPOSITION` 的缺席也不能单独证明完整的 device composition。

## 3. FrameTracer 的 pending fence

`FrameTracer` 用下面的结构保存尚未可写入 trace 的 fence：

```text
mTraceTracker
  └─ layerId → TraceRecord
       ├─ layerName
       └─ pendingFences
            └─ bufferId → vector<PendingFence>
                 └─ frameNumber、type、fence、startTime
```

`traceFence()` 先读取 `FenceTime::getSignalTime()`：

- 已 signal：立即写 instant 或 span；
- 仍 pending：把记录放入 `pendingFences[bufferId]`；
- invalid：本次不写记录。

待处理记录不会由计时器主动唤醒。下一次同一 layer、同一 buffer id 的 `traceTimestamp()` 或 `traceFence()` 才会调用 `tracePendingFencesLocked()` 再查 signal time。

`kFenceSignallingDeadline = 60s` 也不是“60 秒一到就删除 pending fence”的后台超时器。实现只在后续检查已经 signal 的记录时，丢弃 signal time 距当前超过 60 秒的旧事件。若一块 buffer 后续再无 trace，不能指望该常量定时清空记录。

### 3.1 instant 与 span

`traceSpanLocked()` 的规则很简单：

```text
startTime > 0 且 startTime < fenceSignalTime
  → timestamp = startTime
  → duration  = fenceSignalTime - startTime

其他情况
  → timestamp = fenceSignalTime
  → duration  = 0
```

因此，同一种 fence event 在 Perfetto 中可能显示为区间，也可能显示为单点。比较两台设备前要查看 `duration_ns` 是否存在，不能只按 slice 长度聚合。

## 4. Trace Processor 怎样解析 FrameTracer

`android.surfaceflinger.frame` 是采集配置中的 data-source 名称，不是 SQL 表。Perfetto 的 `GraphicsFrameEventParser` 把事件解析进 `slice`，预置视图 `frame_slice` 再提供这些列：

- `layer_name`
- `frame_number`
- `queue_to_acquire_time`
- `acquire_to_latch_time`
- `latch_to_present_time`

parser 同时构造四类 phase：

```text
APP:    DEQUEUE → QUEUE
GPU:     QUEUE → ACQUIRE_FENCE
SF:      LATCH → PRESENT_FENCE
Display: 本次 PRESENT_FENCE → 同一 layer 下一次 PRESENT_FENCE
```

这里的 `GPU` 是 Trace Processor 的 phase 命名。对 HWUI producer，queue 到 acquire fence 的区间通常对应 GPU 继续写 buffer 的时间；对其他 producer，完成 fence 可能来自不同硬件或软件路径。

下面的查询用于查看目标 layer 在 present 时已经积累出的三个阶段间隔：

```sql
SELECT
  ts,
  layer_name,
  frame_number,
  queue_to_acquire_time / 1e6 AS queue_to_acquire_ms,
  acquire_to_latch_time / 1e6 AS acquire_to_latch_ms,
  latch_to_present_time / 1e6 AS latch_to_present_ms
FROM frame_slice
WHERE name = 'PresentFenceSignaled'
  AND layer_name GLOB '*com.example.app*'
ORDER BY ts;
```

字段为 0 或负值时，应先检查事件是否缺失、trace 是否在一帧中途才开始。Android 13+ 的 unsignaled latch 还可能让 `acquire_to_latch_time` 为负，这时要继续检查 acquire fence 在 RenderEngine/HWC 读取前是否 signal。parser 对丢失 `QUEUE` 等情况有容错，容错后的 phase 不具备完整测量精度。

## 5. FrameTimeline 的对象关系

FrameTimeline 用 `DisplayFrame` 表示 SurfaceFlinger 组织并送显的一轮 display frame，用 `SurfaceFrame` 表示参与其中的某个 App/layer frame：

```text
DisplayFrame(display_frame_token)
  ├─ SurfaceFrame A(surface_frame_token, layer A)
  ├─ SurfaceFrame B(surface_frame_token, layer B)
  └─ SurfaceFrame C(surface_frame_token, layer C)
```

一枚 `display_frame_token` 可以关联多个进程、多个 layer 的 `SurfaceFrame`。同一个 App token 也可能被多个 layer 共享，例如同一帧更新多个 Surface。token 与 layer/pid 必须一起查看。

### 5.1 `TimelineItem`

预测与完成时间都用同一个四字段结构表示：

```cpp
struct TimelineItem {
    nsecs_t startTime;
    nsecs_t endTime;
    nsecs_t presentTime;
    nsecs_t desiredPresentTime;
};
```

字段在 `SurfaceFrame` 与 `DisplayFrame` 中的含义略有差异：

| 对象 | `startTime` | `endTime` | `presentTime` |
|---|---|---|---|
| SurfaceFrame predictions | App 预期开始 | App 预期完成并可供 SF 使用 | 预期上屏 |
| SurfaceFrame actuals | App / native Choreographer 本帧开始 | `max(queueTime, acquireFenceSignalTime)` | 所属 DisplayFrame 的 present |
| DisplayFrame predictions | SF 预期开始 | SF 预期完成 | 预期 present |
| DisplayFrame actuals | SF wake-up | SF 提交 present 的时间；分类时还会考虑 GPU fence | present fence signal |

`SurfaceFrame::setAcquireFenceTime()` 遇到 pending fence 时，先用 queue time 作为 end；fence 已有 signal time 时取 `max(acquireFenceTime, queueTime)`。因此，actual slice 的 App end 用于覆盖 CPU post 与异步 producer 工作，不能用 `queueBuffer()` 返回时刻代替。

### 5.2 `SurfaceFrame` 保存哪些状态

Android 17 的 `SurfaceFrame` 主要持有：

- `FrameTimelineInfo.vsyncId` 对应的 token；
- input event id、VSync resync jitter、dequeue duration；
- owner pid/uid、layer id/name、debug name；
- `PredictionState` 与 predictions；
- actual start、queue、acquire、drop、present；
- `PresentState::{Unknown, Presented, Dropped}`；
- `isBuffer`、render rate、GPU composition；
- legacy/experimental 两份 jank 分类结果；
- 前一帧弱引用，用于 BufferStuffing 与帧间节奏判断。

它不是 App 进程直接创建的公共 Java 对象。App/Choreographer 得到 VSync ID 和预测信息，提交 transaction/buffer 时把 `FrameTimelineInfo` 带到 SurfaceFlinger；SF 再创建内部 `SurfaceFrame`。

### 5.3 bufferless frame 也会出现

SurfaceControl transaction 可以只改位置、alpha、crop 等状态而不带 buffer。`Layer` 会为这类 transaction 创建 `isBuffer=false` 的 `SurfaceFrame`。若同一 token 后续又带来 buffer，源码可以把 bufferless frame 提升为 buffer frame。

看到同一 token 的多个 actual slice 时，要检查 `is_buffer` 与 `layer_name`。不能把每条 slice 都统计为一次 App buffer 生产。

## 6. TokenManager：容量保留，不是固定 TTL 定时器

接口注释说预测“保存 120ms”，Android 17 的具体实现则是固定容量环：

```text
kMaxTokens = 500
mPredictions =
    StaticVector<pair<int64_t, TimelineItem>, 500>
```

`generateTokenForPredictions()` 递增 `mCurrentToken`：

- 容量未满时追加；
- 容量满后以 `assignedToken % 500` 覆盖最旧项。

`getPredictionsForToken()` 从最新项向前查最多 500 条。找不到 token 时：

- token 无效：`PredictionState::None`；
- token 有效但记录已不在环中：`PredictionState::Expired`；
- 找到预测：`PredictionState::Valid`。

所以，`Expired` 表示预测记录已无法从当前 TokenManager 取回，不保证“刚好超过 120ms”。在高刷新率、多 Display 或异常调度下，500 枚 token 对应的墙钟时间并不固定。

Android 17 对 expired frame 的 legacy 处理也很明确：已 present 的 frame 记为 `AppDeadlineMissed`，未 present 的记为 `Dropped`，severity 为 `Unknown`。它表示调度延迟已经超出预测保留窗口，不等同于 VSyncPredictor 数学模型出错。

## 7. FrameTimeline Proto 怎样关联 start/end

`FrameTimelineEvent` 用五类消息构建 slice：

- `ExpectedDisplayFrameStart`
- `ActualDisplayFrameStart`
- `ExpectedSurfaceFrameStart`
- `ActualSurfaceFrameStart`
- `FrameEnd`

start 消息携带 metadata 和一个 cookie，end 消息只携带相同 cookie。Trace Processor 用 cookie 闭合 expected/actual slice，减少每个 end packet 重复发送 token、pid 和分类信息。

SurfaceFrame 消息包含：

- surface token；
- 对应 display token；
- App pid；
- layer name。

Actual 消息还包含 present type、on-time finish、GPU composition、jank bitmask、prediction type、`is_buffer`、severity、present delay 与 resync jitter。

DisplayFrame 消息没有 surface token；它的 token 直接写入 `display_frame_token`。这正是“一枚 display token 对应 N 枚 surface frame”的数据关系。

### 7.1 两套时钟由 Trace Processor 统一

FrameTracer packet 使用 `BUILTIN_CLOCK_MONOTONIC`。FrameTimeline 内部时间原本也来自 Android monotonic 时间线，但发送 packet 时换算到 `BUILTIN_CLOCK_BOOTTIME`。Perfetto 负责根据 clock snapshot 归一化。

使用 Trace Processor 的 `ts` 可以直接关联。若自行解析 raw proto，必须先做 clock-domain 转换，不能直接相减 packet 中的整数 timestamp。

## 8. JankType：15 个原因 bit

Android 17 `JankInfo.h` 定义 15 个非零原因 bit：

| 组别 | JankType | 说明 |
|---|---|---|
| App | `AppDeadlineMissed` | App/producer 完成晚 |
| App | `AppResyncedJitter` | App 修改 VSync 时间造成节奏偏差 |
| 系统 | `SurfaceFlingerCpuDeadlineMissed` | SF CPU 路径超期 |
| 系统 | `SurfaceFlingerGpuDeadlineMissed` | SF client composition 的 GPU 路径超期 |
| 系统 | `DisplayHAL` | SF 按时完成，但 display 侧晚 present |
| 系统 | `PredictionError` | 预测 present 与硬件节奏偏离 |
| 系统 | `SurfaceFlingerScheduling` | SF 的调度时点造成 early/late |
| 排队 | `BufferStuffing` | 当前 App buffer 因前一 buffer 占用目标 VSync 而后移 |
| 排队 | `SurfaceFlingerStuffing` | 前一 DisplayFrame 占用当前目标 VSync |
| 状态 | `Dropped` | frame 被更新 frame 替换 |
| 状态 | `NonAnimating` | 时间偏离但不属于可感知动画 |
| 状态 | `DisplayNotOn` | display 处于 off/doze |
| 状态 | `DisplayModeChangeInProgress` | 显示模式切换中 |
| 状态 | `DisplayPowerModeChangeInProgress` | 显示电源状态切换中 |
| 兜底 | `Unknown` | 当前证据不能分类 |

同一 frame 可以同时带多个 bit。`SurfaceFrame::isSelfJanky()` 只把 `AppDeadlineMissed | Unknown | AppResyncedJitter` 视为 App 自身 jank；SF、DisplayHAL 与 queue state 不在这个集合中。`Unknown` 被纳入 self-janky，是 Android 17 当前的着色/归类实现，不能解释成已经证明 App 代码有错。

### 8.1 C++ 与 Proto 的数值不能直接比较

`JankInfo.h` 中 `DisplayHAL` 是 `0x1`，而 `frame_timeline_event.proto` 把 `JANK_NONE` 放在 bit 0，`JANK_DISPLAY_HAL` 使用另一个 bit 位。SurfaceFlinger 的 `jankTypeBitmaskToProto()` 负责逐 bit 映射。

读取 trace 时使用 `jank_type` 的字符串或 Proto 枚举，读取 SurfaceFlinger 内存/日志时使用 C++ `JankType`。不能拿两侧十六进制数值直接做等值判断。

## 9. 分类阈值、legacy 与 experimental

`JankClassificationThresholds` 的 Android 17 默认值为：

```text
presentThreshold  = 2ms
deadlineThreshold = 0ms
startThreshold    = 2ms
```

这些阈值分别用于 present 偏差、完成 deadline 与 start 偏差。分类还会参考 refresh rate、render rate、前一 frame、display state、GPU fence 和 prediction state。单独用“actual end 是否晚于 expected end”可以计算 overrun，但不能完整重做 SurfaceFlinger 的 jank bitmask。

Android 17 的 `Experimental<T>` 同时保存 legacy 与 experimental 值，`use_experimental_jank_classification` flag 决定 `.value()` 选哪一份。FrameTimeline Proto 同时写入：

- `jank_type` / `present_type`：当前 flag 选中的值；
- `jank_type_experimental` / `present_type_experimental`：另一份对照值。

Proto 注释要求分析工具不能把实验字段作为正式卡顿结论。

### 9.1 severity

Proto 暴露四级严重程度：

- `Unknown`
- `None`
- `Partial`
- `Full`

Android 17 还计算连续的 `jank_severity_score`。下面的公式用于理解源码输入，不建议在业务 SQL 中复制一套分类器：

```text
ratio =
  (abs(expectedPresentDelta - actualPresentDelta) + framePeriod)
  / framePeriod

score =
  log2(ratio)
  × sqrt(framePeriod / periodAt120Hz)
```

代码把 `0 < score < 0.9` 归为 `Partial`，`score >= 0.9` 归为 `Full`；帧被丢弃或缺少有效期望差值时，严重程度为 `Unknown`。BufferStuffing、NonAnimating、DisplayNotOn 与显示切换状态属于非卡顿严重程度集合，不能看到任意非零位就强制算作 `Full`。

## 10. 怎样读取 GPU composition 字段

`SurfaceFrame.gpu_composition` 在 `Layer::onCompositionPresented()` 发现目标输出 layer `requiresClientComposition()` 时设为 `true`。`DisplayFrame.gpu_composition` 则依据是否存在 GPU fence。

可以采用以下证据强度：

| 证据 | 可得结论 |
|---|---|
| `actual_frame_timeline_slice.gpu_composition = 1` | 该 FrameTimeline 记录涉及 client/GPU composition |
| `FALLBACK_COMPOSITION` 出现 | 对应 layer 已准备为 client composition |
| GPU/RenderEngine fence 或 GPU slice | 可继续测量 GPU 完成时间与耗时 |
| `gpu_composition = 0` | 当前记录没有标为 GPU composition；还要确认 FrameTimeline 覆盖范围与目标显示设备 |
| 没有 `HWC_COMPOSITION_QUEUED` | 没有结论，AOSP 本来就不发这个事件 |

对于官方尚未完整支持的 SurfaceView，以及 Camera/Video 独立 layer，应回到 HWC composition type、layer snapshot、acquire/release/present fence 和 vendor Composer 证据。

## 11. 用正确的 SQL 表

### 11.1 列出目标 App 的 actual frame

下面的查询用于找出目标进程中非 `None` 的 frame，并保留 surface/display token：

```sql
SELECT
  a.ts,
  a.dur,
  a.surface_frame_token,
  a.display_frame_token,
  a.layer_name,
  a.present_type,
  a.on_time_finish,
  a.gpu_composition,
  a.jank_type,
  a.prediction_type,
  p.name AS process_name
FROM actual_frame_timeline_slice AS a
JOIN process AS p USING (upid)
WHERE p.name = 'com.example.app'
  AND a.surface_frame_token != 0
  AND a.jank_type != 'None'
ORDER BY a.ts;
```

`surface_frame_token = 0` 常用于 SurfaceFlinger DisplayFrame，App 查询应排除。一个 token 可能对应多个 layer，统计前还要按 `layer_name` 选定目标窗口。

### 11.2 expected 与 actual 按契约字段对齐

下面的查询用于计算同一 App、同一 token、同一 layer 的结束时间偏差：

```sql
WITH app_actual AS (
  SELECT
    a.*,
    p.name AS process_name
  FROM actual_frame_timeline_slice AS a
  JOIN process AS p USING (upid)
  WHERE p.name = 'com.example.app'
    AND a.surface_frame_token != 0
    AND a.layer_name GLOB '*com.example.app*'
),
app_expected AS (
  SELECT
    upid,
    surface_frame_token,
    layer_name,
    ts AS expected_ts,
    dur AS expected_dur
  FROM expected_frame_timeline_slice
  WHERE surface_frame_token != 0
)
SELECT
  a.surface_frame_token,
  a.display_frame_token,
  a.layer_name,
  a.ts AS actual_ts,
  a.dur AS actual_dur,
  e.expected_ts,
  e.expected_dur,
  (a.ts + a.dur)
    - (e.expected_ts + e.expected_dur) AS overrun_ns,
  a.jank_type,
  a.present_type,
  a.on_time_finish,
  a.gpu_composition,
  a.prediction_type
FROM app_actual AS a
LEFT JOIN app_expected AS e
  ON a.upid = e.upid
 AND a.surface_frame_token = e.surface_frame_token
 AND a.layer_name = e.layer_name
ORDER BY a.ts;
```

`overrun_ns > 0` 只表示 actual slice 的结束晚于 expected slice。它是定位入口，后续仍要看 `jank_type`、线程调度、`DrawFrame`、fence 和 display token。

### 11.3 App 与 DisplayFrame 用 display token 关联

FrameTimeline Proto 的正式关系是：

```text
SurfaceFrame.display_frame_token
  = DisplayFrame.display_frame_token
```

一枚 display token 可能匹配多个 SurfaceFrame。做 display 级统计时，应先选择 `surface_frame_token = 0` 的 SF 行，再以 `display_frame_token` 查找参与该次 present 的 App/layer，不能把 N 个 SurfaceFrame 当作 N 次独立 display present。

## 12. FrameTracer 与 FrameTimeline 怎样配合

两套 Proto 没有声明 `FrameTracer.frame_number = FrameTimeline.surface_frame_token`。下面这些 join 都不可靠：

- 只按数值相等连接 frame number 与 token；
- 只按 layer name 连接整段 trace；
- 把 buffer id 当作 surface token；
- 用相邻行号推定同一帧。

稳妥顺序是：

1. 在 `actual_frame_timeline_slice` 中用 process、layer、surface/display token 找出目标帧；
2. 用 Perfetto UI flow 观察该 SurfaceFrame 与 DisplayFrame 的正式关联；
3. 在它的时间窗口内查 App main、RenderThread、`BufferTX`、`frame_slice` 与 fence；
4. 用 layer name 和时间区间缩小 FrameTracer 候选；
5. 若必须自动匹配，把“时间窗口 + layer + producer frame metadata”标为启发式规则，并统计未匹配/多匹配率。

FrameTimeline 用于判断这帧相对计划是否异常；FrameTracer 用于拆分 buffer 阶段。二者互补，但没有一个公共万能 ID。

## 13. 采集配置与覆盖边界

下面的 TraceConfig 片段用于同时启用两个 SurfaceFlinger 数据源：

```protobuf
data_sources {
  config {
    name: "android.surfaceflinger.frametimeline"
  }
}

data_sources {
  config {
    name: "android.surfaceflinger.frame"
  }
}
```

采集后先确认两张 FrameTimeline 表和 `frame_slice` 都有目标进程/layer 数据。数据缺失可能来自：

- trace 开始得太晚，expected 或前序 buffer 事件不在文件中；
- SurfaceView/独立 Surface 的官方覆盖限制；
- producer 没有传递有效的 FrameTimelineInfo；
- layer 在采集期间创建、销毁或改名；
- fence 仍 pending，且同一 buffer 后续没有触发 FrameTracer 重查；
- display off、mode/power 切换或 present fence 不可用；
- vendor 图形管线未暴露足够事件。

缺少事件只能降低结论强度，不能自动归因给 App、SurfaceFlinger、HWC 或 driver。

## 14. Android 12—17 的解释边界

| 版本 | 相关边界 |
|---|---|
| Android 12 / API 31 | FrameTimeline 可用于标准 App Window，提供 App/SF expected 与 actual |
| Android 13 / API 33 | 默认的 unsignaled buffer latch 策略改变了 latch 与 acquire fence signal 的先后解释 |
| Android 14 / API 34 | 标准窗口的 token、SurfaceFrame、DisplayFrame 分析主线延续 |
| Android 15 / API 35 | HDR/headroom 等显示能力会改变 layer/display 条件，不改变两类 token 的关系 |
| Android 16 / API 36 | 主数据模型延续；跨版本分析仍要固定刷新率、设备固件与 Perfetto 版本 |
| Android 17 / API 37 | 源码锚点更新到 Android 17；15 个 JankType 原因 bit、500-token 实现、legacy/experimental 分类与当前 SQL parser 均按 `android-17.0.0_r1` 核对 |

“源码存在于 Android 17”不等于“Android 17 首次加入”。涉及版本首引时，应继续比较历史标签或公开 API 文档。

## 总结

FrameTracer 以 buffer id、frame number 和 layer name 描述从 producer 到 present 的阶段；FrameTimeline 以 surface/display token 描述计划、完成与 jank。前者进入 `frame_slice`，后者进入 `expected_frame_timeline_slice` 与 `actual_frame_timeline_slice`。

分析一帧时，先用 FrameTimeline 确认目标 App/layer、surface token、display token 和分类，再用 FrameTracer、线程 slice、BufferTX、fence 与 HWC 证据解释具体阶段。不能假设 frame number 等于 token，也不能用某个未发射枚举的缺席证明合成路径。
