# 2.32 Android 17 FrameTimeline 数据结构

Android 图形跟踪中有两个名称相近、用途不同的数据源：

- `android.surfaceflinger.frame` 由 `FrameTracer` 产生，记录一块缓冲区从出队、入队到锁存、展示的阶段事件；
- `android.surfaceflinger.frametimeline` 由 `FrameTimeline` 产生，用预测时间线和完成时间线描述应用 `SurfaceFrame` 与 SurfaceFlinger `DisplayFrame`，并给出卡顿分类。

混用两者会产生几类典型误判：把数据源名称当成 SQL 表名，把 BufferQueue 帧号当成 FrameTimeline 令牌，把客户端合成的准备时间当成 GPU 完成时间，以及用某个枚举事件的缺席证明 HWC 路径。

以下讨论以 Android 17 / API 37 / `android-17.0.0_r1`、对应版本的 Perfetto 和内核 `android17-6.18-2026-06_r6` 为验证边界。

FrameTimeline 对标准应用窗口的覆盖最完整。Perfetto 官方文档仍明确写着 SurfaceView 不受完整支持；遇到相机、视频、SurfaceView、游戏或自研渲染器，还要补充图层、BufferQueue、围栏与生产者线程证据。

## 1. 两套数据模型各自回答什么

两套模型的边界如下：

| 维度 | FrameTracer | FrameTimeline |
|---|---|---|
| 数据源 | `android.surfaceflinger.frame` | `android.surfaceflinger.frametimeline` |
| 核心标识 | 缓冲区 ID、帧号、图层名称 | Surface 帧令牌、显示帧令牌、pid、图层名称 |
| 主要问题 | 缓冲区在生产者、围栏、SurfaceFlinger 与显示阶段停了多久 | 期望时间与实际时间是否偏离，谁被分类为卡顿 |
| Trace Processor 入口 | `frame_slice` | `expected_frame_timeline_slice`、`actual_frame_timeline_slice` |
| 适合场景 | 缓冲区阶段拆分、入队/获取/锁存/展示 | 标准窗口帧、应用/SurfaceFlinger 截止时间、卡顿类型 |

一条 FrameTimeline `SurfaceFrame` 不等于一块 GraphicBuffer。它也可以表示没有缓冲区的 SurfaceControl 事务；源码用 `is_buffer` 区分缓冲区帧与动画/状态帧。

## 2. FrameTracer：缓冲区事件数据结构

### 2.1 Proto 没有独立时间戳字段

`GraphicsFrameEvent::BufferEvent` 的 Android 17 定义只有五个字段：

| 字段 | Proto 类型 | 说明 |
|---|---|---|
| `frame_number` | `uint32` | 该图层的缓冲区帧号 |
| `type` | `BufferEventType` | 事件类型 |
| `layer_name` | `string` | SurfaceFlinger 图层名称 |
| `duration_ns` | `uint64` | 可选；大于 0 时形成持续时间事件 |
| `buffer_id` | `uint32` | 缓冲区标识 |

事件时间放在外层 `TracePacket.timestamp`，`FrameTracer` 同时把时钟 ID 设为 `BUILTIN_CLOCK_MONOTONIC`。原始 C++ 调用接受 `uint64_t bufferID` 和 `uint64_t frameNumber`，写入 Proto 时都会收窄到 `uint32`；长时间运行或跨进程分析时，不能把这两个字段当成全局永久 ID。

### 2.2 13 个非零枚举值

Proto 中 0 是 `UNSPECIFIED`，1—13 是以下事件：

| 值 | 枚举 | Android 17 AOSP SurfaceFlinger 是否发射 |
|---:|---|:---:|
| 1 | `DEQUEUE` | 是 |
| 2 | `QUEUE` | 是 |
| 3 | `POST` | 否 |
| 4 | `ACQUIRE_FENCE` | 是 |
| 5 | `LATCH` | 是 |
| 6 | `HWC_COMPOSITION_QUEUED` | 否 |
| 7 | `FALLBACK_COMPOSITION` | 是 |
| 8 | `PRESENT_FENCE` | 是 |
| 9 | `RELEASE_FENCE` | 否 |
| 10 | `MODIFY` | 否 |
| 11 | `DETACH` | 否 |
| 12 | `ATTACH` | 否 |
| 13 | `CANCEL` | 否 |

“Proto 定义了事件”只表示跟踪格式可以容纳它。`android-17.0.0_r1` 的标准 SurfaceFlinger 生产代码只调用六种；测试代码引用其他枚举不能算作设备运行时发射点。

### 2.3 六种 AOSP 事件的精确来源

`Layer.cpp` 的调用点给出了这些事件的含义：

| 事件 | 时间来源 | 能证明什么 |
|---|---|---|
| `DEQUEUE` | 事务中的 `BufferData.dequeueTime` | 生产者开始持有本次缓冲区的时刻 |
| `QUEUE` | 缓冲区事务的 `postTime` | 生产者把缓冲区更新交给 SurfaceFlinger 事务的时刻 |
| `ACQUIRE_FENCE` | 获取围栏发出信号的时间 | 生产者的异步写入何时完成 |
| `LATCH` | SurfaceFlinger 的 `latchTime` | SurfaceFlinger 何时采纳该缓冲区 |
| `FALLBACK_COMPOSITION` | 客户端合成图层准备时的 `systemTime()` | 该图层被纳入客户端/GPU 合成准备 |
| `PRESENT_FENCE` | 展示围栏发出信号的时间；无有效围栏时使用 HWC 展示时间戳估算 | 对应显示帧的展示时间锚点 |

`QUEUE` 发生不代表 GPU 已写完缓冲区，后面的获取围栏才说明生产者写入完成。Android 13 起允许在满足条件时先锁存尚未发出信号的缓冲区，所以 `LATCH` 与 `ACQUIRE_FENCE` 也不必保持固定先后。

### 2.4 `FALLBACK_COMPOSITION` 不是 GPU 完成时间

Android 17 `CompositionEngine::Output` 在 `prepareClientComposition()` 返回图层设置后写入：

```cpp
layer->editState().clientCompositionTimestamp = systemTime();
```

`Layer::onCompositionPresented()` 随后把这个值作为 `FALLBACK_COMPOSITION` 事件发给 FrameTracer，并为关联的 `SurfaceFrame` 调用 `setGpuComposition()`。

这枚时间戳确认客户端合成图层已经准备，不能替代 RenderEngine GPU 围栏。判断 GPU 工作何时完成时，应查看 FrameTimeline `DisplayFrame` 使用的 GPU 围栏、RenderEngine/GPU 轨道以及最终展示记录。

`HWC_COMPOSITION_QUEUED` 在 Android 17 AOSP SurfaceFlinger 中没有生产调用。它的缺席不能证明帧走了客户端合成；`FALLBACK_COMPOSITION` 的缺席也不能单独证明完整的设备合成。

## 3. FrameTracer 的待定围栏

`FrameTracer` 用下面的结构保存尚未可写入跟踪记录的围栏：

```text
mTraceTracker
  └─ layerId → TraceRecord
       ├─ layerName
       └─ 待定围栏
            └─ 缓冲区 ID → vector<PendingFence>
                 └─ 帧号、类型、围栏、起始时间
```

`traceFence()` 先读取 `FenceTime::getSignalTime()`：

- 已发出信号：立即写入单点或区间；
- 仍处于待定状态：把记录放入 `pendingFences[bufferId]`；
- 无效：本次不写记录。

待处理记录不会由计时器主动唤醒。下一次同一图层、同一缓冲区 ID 的 `traceTimestamp()` 或 `traceFence()` 才会调用 `tracePendingFencesLocked()` 再查信号时间。

`kFenceSignallingDeadline = 60s` 也不是“60 秒一到就删除待定围栏”的后台超时器。实现只在后续检查已经发出信号的记录时，丢弃信号时间距当前超过 60 秒的旧事件。若一块缓冲区后续再无跟踪事件，不能指望该常量定时清空记录。

### 3.1 单点与区间

`traceSpanLocked()` 的规则很简单：

```text
startTime > 0 且 startTime < fenceSignalTime
  → timestamp = startTime
  → duration  = fenceSignalTime - startTime

其他情况
  → timestamp = fenceSignalTime
  → duration  = 0
```

因此，同一种围栏事件在 Perfetto 中可能显示为区间，也可能显示为单点。比较两台设备前要查看 `duration_ns` 是否存在，不能只按切片长度聚合。

## 4. Trace Processor 怎样解析 FrameTracer

`android.surfaceflinger.frame` 是采集配置中的数据源名称，不是 SQL 表。Perfetto 的 `GraphicsFrameEventParser` 把事件解析进 `slice`，预置视图 `frame_slice` 再提供这些列：

- `layer_name`
- `frame_number`
- `queue_to_acquire_time`
- `acquire_to_latch_time`
- `latch_to_present_time`

解析器同时构造四类阶段：

```text
应用:    DEQUEUE → QUEUE
GPU:     QUEUE → ACQUIRE_FENCE
SF:      LATCH → PRESENT_FENCE
显示:    本次 PRESENT_FENCE → 同一图层下一次 PRESENT_FENCE
```

这里的 `GPU` 是 Trace Processor 的阶段命名。对 HWUI 生产者，从入队到获取围栏的区间通常对应 GPU 继续写缓冲区的时间；对其他生产者，完成围栏可能来自不同硬件或软件路径。

下面的查询用于查看目标图层在展示时已经积累出的三个阶段间隔：

```sql
SELECT
  ts,
  layer_name,
  frame_number,
  queue_to_acquire_time / 1e6 AS queue_to_acquire_ms,
  acquire_to_latch_time / 1e6 AS acquire_to_latch_ms,
  latch_to_present_time / 1e6 AS latch_to_present_ms
FROM frame_slice
WHERE name = 'PresentFenceSignaled'
  AND layer_name GLOB '*com.example.app*'
ORDER BY ts;
```

字段为 0 或负值时，应先检查事件是否缺失、跟踪是否在一帧中途才开始。Android 13+ 的未发信号锁存还可能让 `acquire_to_latch_time` 为负，这时要继续检查获取围栏在 RenderEngine/HWC 读取前是否发出信号。解析器对丢失 `QUEUE` 等情况有容错，容错后的阶段不具备完整测量精度。

## 5. FrameTimeline 的对象关系

FrameTimeline 用 `DisplayFrame` 表示 SurfaceFlinger 组织并送显的一轮显示帧，用 `SurfaceFrame` 表示参与其中的某个应用/图层帧：

```text
DisplayFrame(display_frame_token)
  ├─ SurfaceFrame A(surface_frame_token, 图层 A)
  ├─ SurfaceFrame B(surface_frame_token, 图层 B)
  └─ SurfaceFrame C(surface_frame_token, 图层 C)
```

一枚 `display_frame_token` 可以关联多个进程、多个图层的 `SurfaceFrame`。同一个应用令牌也可能被多个图层共享，例如同一帧更新多个 Surface。令牌与图层/pid 必须一起查看。

### 5.1 `TimelineItem`

预测与完成时间都用同一个四字段结构表示：

```cpp
struct TimelineItem {
    nsecs_t startTime;
    nsecs_t endTime;
    nsecs_t presentTime;
    nsecs_t desiredPresentTime;
};
```

字段在 `SurfaceFrame` 与 `DisplayFrame` 中的含义略有差异：

| 对象 | `startTime` | `endTime` | `presentTime` |
|---|---|---|---|
| SurfaceFrame 预测值 | 应用预期开始 | 应用预期完成并可供 SurfaceFlinger 使用 | 预期上屏 |
| SurfaceFrame 实际值 | 应用 / 原生 Choreographer 本帧开始 | `max(queueTime, acquireFenceSignalTime)` | 所属 DisplayFrame 的展示时间 |
| DisplayFrame 预测值 | SurfaceFlinger 预期开始 | SurfaceFlinger 预期完成 | 预期展示 |
| DisplayFrame 实际值 | SurfaceFlinger 唤醒 | SurfaceFlinger 提交展示的时间；分类时还会考虑 GPU 围栏 | 展示围栏发出信号的时间 |

`SurfaceFrame::setAcquireFenceTime()` 遇到待定围栏时，先用入队时间作为结束时间；围栏已有信号时间时取 `max(acquireFenceTime, queueTime)`。因此，实际切片的应用结束时间用于覆盖 CPU 提交与异步生产者工作，不能用 `queueBuffer()` 返回时刻代替。

### 5.2 `SurfaceFrame` 保存哪些状态

Android 17 的 `SurfaceFrame` 主要持有：

- `FrameTimelineInfo.vsyncId` 对应的 token；
- 输入事件 ID、VSync 重同步抖动、出队时长；
- 所有者 pid/uid、图层 ID/名称、调试名称；
- `PredictionState` 与预测值；
- 实际开始、入队、获取、丢弃、展示时间；
- `PresentState::{Unknown, Presented, Dropped}`；
- `isBuffer`、渲染帧率、GPU 合成；
- 旧版/实验版两份卡顿分类结果；
- 前一帧弱引用，用于 BufferStuffing 与帧间节奏判断。

它不是应用进程直接创建的公共 Java 对象。应用/Choreographer 得到 VSync ID 和预测信息，提交事务/缓冲区时把 `FrameTimelineInfo` 带到 SurfaceFlinger；SurfaceFlinger 再创建内部 `SurfaceFrame`。

### 5.3 无缓冲区帧也会出现

SurfaceControl 事务可以只改位置、透明度、裁剪等状态而不带缓冲区。`Layer` 会为这类事务创建 `isBuffer=false` 的 `SurfaceFrame`。若同一令牌后续又带来缓冲区，源码可以把无缓冲区帧提升为缓冲区帧。

看到同一令牌的多个实际切片时，要检查 `is_buffer` 与 `layer_name`。不能把每条切片都统计为一次应用缓冲区生产。

## 6. TokenManager：容量保留，不是固定 TTL 定时器

接口注释说预测“保存 120ms”，Android 17 的具体实现则是固定容量环：

```text
kMaxTokens = 500
mPredictions =
    StaticVector<pair<int64_t, TimelineItem>, 500>
```

`generateTokenForPredictions()` 递增 `mCurrentToken`：

- 容量未满时追加；
- 容量满后以 `assignedToken % 500` 覆盖最旧项。

`getPredictionsForToken()` 从最新项向前查最多 500 条。找不到令牌时：

- 令牌无效：`PredictionState::None`；
- 令牌有效但记录已不在环中：`PredictionState::Expired`；
- 找到预测：`PredictionState::Valid`。

所以，`Expired` 表示预测记录已无法从当前 TokenManager 取回，不保证“刚好超过 120ms”。在高刷新率、多显示设备或异常调度下，500 枚令牌对应的墙钟时间并不固定。

Android 17 对预测过期帧的旧版处理也很明确：已展示的帧记为 `AppDeadlineMissed`，未展示的记为 `Dropped`，严重程度为 `Unknown`。它表示调度延迟已经超出预测保留窗口，不等同于 VSyncPredictor 数学模型出错。

## 7. FrameTimeline Proto 怎样关联开始与结束

`FrameTimelineEvent` 用五类消息构建切片：

- `ExpectedDisplayFrameStart`
- `ActualDisplayFrameStart`
- `ExpectedSurfaceFrameStart`
- `ActualSurfaceFrameStart`
- `FrameEnd`

开始消息携带元数据和一个 cookie，结束消息只携带相同 cookie。Trace Processor 用 cookie 闭合期望/实际切片，减少每个结束数据包重复发送令牌、pid 和分类信息。

SurfaceFrame 消息包含：

- Surface 令牌；
- 对应显示令牌；
- 应用 pid；
- 图层名称。

实际消息还包含展示类型、是否按时完成、GPU 合成、卡顿位掩码、预测类型、`is_buffer`、严重程度、展示延迟与重同步抖动。

DisplayFrame 消息没有 Surface 令牌；它的令牌直接写入 `display_frame_token`。这正是“一枚显示令牌对应 N 枚 Surface 帧”的数据关系。

### 7.1 两套时钟由 Trace Processor 统一

FrameTracer 数据包使用 `BUILTIN_CLOCK_MONOTONIC`。FrameTimeline 内部时间原本也来自 Android 单调时钟，但发送数据包时换算到 `BUILTIN_CLOCK_BOOTTIME`。Perfetto 负责根据时钟快照归一化。

使用 Trace Processor 的 `ts` 可以直接关联。若自行解析原始 Proto，必须先转换时钟域，不能直接相减数据包中的整数时间戳。

## 8. JankType：15 个原因位

Android 17 `JankInfo.h` 定义 15 个非零原因位：

| 组别 | JankType | 说明 |
|---|---|---|
| 应用 | `AppDeadlineMissed` | 应用/生产者完成晚 |
| 应用 | `AppResyncedJitter` | 应用修改 VSync 时间造成节奏偏差 |
| 系统 | `SurfaceFlingerCpuDeadlineMissed` | SF CPU 路径超期 |
| 系统 | `SurfaceFlingerGpuDeadlineMissed` | SurfaceFlinger 客户端合成的 GPU 路径超期 |
| 系统 | `DisplayHAL` | SurfaceFlinger 按时完成，但显示侧展示晚 |
| 系统 | `PredictionError` | 预测展示时间与硬件节奏偏离 |
| 系统 | `SurfaceFlingerScheduling` | SF 的调度时点造成 early/late |
| 排队 | `BufferStuffing` | 当前应用缓冲区因前一缓冲区占用目标 VSync 而后移 |
| 排队 | `SurfaceFlingerStuffing` | 前一 DisplayFrame 占用当前目标 VSync |
| 状态 | `Dropped` | 帧被更新的帧替换 |
| 状态 | `NonAnimating` | 时间偏离但不属于可感知动画 |
| 状态 | `DisplayNotOn` | 显示设备处于关闭/低功耗状态 |
| 状态 | `DisplayModeChangeInProgress` | 显示模式切换中 |
| 状态 | `DisplayPowerModeChangeInProgress` | 显示电源状态切换中 |
| 兜底 | `Unknown` | 当前证据不能分类 |

同一帧可以同时带多个原因位。`SurfaceFrame::isSelfJanky()` 只把 `AppDeadlineMissed | Unknown | AppResyncedJitter` 视为应用自身卡顿；SurfaceFlinger、DisplayHAL 与队列状态不在这个集合中。`Unknown` 被纳入自身卡顿，是 Android 17 当前的着色/归类实现，不能解释成已经证明应用代码有错。

### 8.1 C++ 与 Proto 的数值不能直接比较

`JankInfo.h` 中 `DisplayHAL` 是 `0x1`，而 `frame_timeline_event.proto` 把 `JANK_NONE` 放在第 0 位，`JANK_DISPLAY_HAL` 使用另一个位。SurfaceFlinger 的 `jankTypeBitmaskToProto()` 负责逐位映射。

读取跟踪数据时使用 `jank_type` 的字符串或 Proto 枚举，读取 SurfaceFlinger 内存/日志时使用 C++ `JankType`。不能拿两侧十六进制数值直接做等值判断。

## 9. 分类阈值、旧版与实验版

`JankClassificationThresholds` 的 Android 17 默认值为：

```text
presentThreshold  = 2ms
deadlineThreshold = 0ms
startThreshold    = 2ms
```

这些阈值分别用于展示偏差、完成截止时间与开始偏差。分类还会参考刷新率、渲染帧率、前一帧、显示状态、GPU 围栏和预测状态。单独用“实际结束时间是否晚于期望结束时间”可以计算超期，但不能完整重做 SurfaceFlinger 的卡顿位掩码。

Android 17 的 `Experimental<T>` 同时保存旧版与实验版值，`use_experimental_jank_classification` 开关决定 `.value()` 选哪一份。FrameTimeline Proto 同时写入：

- `jank_type` / `present_type`：当前开关选中的值；
- `jank_type_experimental` / `present_type_experimental`：另一份对照值。

Proto 注释要求分析工具不能把实验字段作为正式卡顿结论。

### 9.1 严重程度

Proto 暴露四级严重程度：

- `Unknown`
- `None`
- `Partial`
- `Full`

Android 17 还计算连续的 `jank_severity_score`。下面的公式用于理解源码输入，不建议在业务 SQL 中复制一套分类器：

```text
ratio =
  (abs(expectedPresentDelta - actualPresentDelta) + framePeriod)
  / framePeriod

score =
  log2(ratio)
  × sqrt(framePeriod / periodAt120Hz)
```

代码把 `0 < score < 0.9` 归为 `Partial`，`score >= 0.9` 归为 `Full`；帧被丢弃或缺少有效期望差值时，严重程度为 `Unknown`。BufferStuffing、NonAnimating、DisplayNotOn 与显示切换状态属于非卡顿严重程度集合，不能看到任意非零位就强制算作 `Full`。

## 10. 怎样读取 GPU 合成字段

`SurfaceFrame.gpu_composition` 在 `Layer::onCompositionPresented()` 发现目标输出图层 `requiresClientComposition()` 时设为 `true`。`DisplayFrame.gpu_composition` 则依据是否存在 GPU 围栏。

可以采用以下证据强度：

| 证据 | 可得结论 |
|---|---|
| `actual_frame_timeline_slice.gpu_composition = 1` | 该 FrameTimeline 记录涉及客户端/GPU 合成 |
| `FALLBACK_COMPOSITION` 出现 | 对应图层已准备为客户端合成 |
| GPU/RenderEngine 围栏或 GPU 切片 | 可继续测量 GPU 完成时间与耗时 |
| `gpu_composition = 0` | 当前记录没有标为 GPU 合成；还要确认 FrameTimeline 覆盖范围与目标显示设备 |
| 没有 `HWC_COMPOSITION_QUEUED` | 没有结论，AOSP 本来就不发这个事件 |

对于官方尚未完整支持的 SurfaceView，以及相机/视频独立图层，应回到 HWC 合成类型、图层快照、获取/释放/展示围栏和厂商 Composer 证据。

## 11. 用正确的 SQL 表

### 11.1 列出目标应用的实际帧

下面的查询用于找出目标进程中非 `None` 的帧，并保留 Surface/显示令牌：

```sql
SELECT
  a.ts,
  a.dur,
  a.surface_frame_token,
  a.display_frame_token,
  a.layer_name,
  a.present_type,
  a.on_time_finish,
  a.gpu_composition,
  a.jank_type,
  a.prediction_type,
  p.name AS process_name
FROM actual_frame_timeline_slice AS a
JOIN process AS p USING (upid)
WHERE p.name = 'com.example.app'
  AND a.surface_frame_token != 0
  AND a.jank_type != 'None'
ORDER BY a.ts;
```

`surface_frame_token = 0` 常用于 SurfaceFlinger DisplayFrame，应用查询应排除。一个令牌可能对应多个图层，统计前还要按 `layer_name` 选定目标窗口。

### 11.2 按契约字段对齐期望值与实际值

下面的查询用于计算同一应用、同一令牌、同一图层的结束时间偏差：

```sql
WITH app_actual AS (
  SELECT
    a.*,
    p.name AS process_name
  FROM actual_frame_timeline_slice AS a
  JOIN process AS p USING (upid)
  WHERE p.name = 'com.example.app'
    AND a.surface_frame_token != 0
    AND a.layer_name GLOB '*com.example.app*'
),
app_expected AS (
  SELECT
    upid,
    surface_frame_token,
    layer_name,
    ts AS expected_ts,
    dur AS expected_dur
  FROM expected_frame_timeline_slice
  WHERE surface_frame_token != 0
)
SELECT
  a.surface_frame_token,
  a.display_frame_token,
  a.layer_name,
  a.ts AS actual_ts,
  a.dur AS actual_dur,
  e.expected_ts,
  e.expected_dur,
  (a.ts + a.dur)
    - (e.expected_ts + e.expected_dur) AS overrun_ns,
  a.jank_type,
  a.present_type,
  a.on_time_finish,
  a.gpu_composition,
  a.prediction_type
FROM app_actual AS a
LEFT JOIN app_expected AS e
  ON a.upid = e.upid
 AND a.surface_frame_token = e.surface_frame_token
 AND a.layer_name = e.layer_name
ORDER BY a.ts;
```

`overrun_ns > 0` 只表示实际切片的结束晚于期望切片。它是定位入口，后续仍要看 `jank_type`、线程调度、`DrawFrame`、围栏和显示令牌。

### 11.3 应用与 DisplayFrame 用显示令牌关联

FrameTimeline Proto 的正式关系是：

```text
SurfaceFrame.display_frame_token
  = DisplayFrame.display_frame_token
```

一枚显示令牌可能匹配多个 SurfaceFrame。做显示级统计时，应先选择 `surface_frame_token = 0` 的 SurfaceFlinger 行，再以 `display_frame_token` 查找参与该次展示的应用/图层，不能把 N 个 SurfaceFrame 当作 N 次独立显示展示。

## 12. FrameTracer 与 FrameTimeline 怎样配合

两套 Proto 没有声明 `FrameTracer.frame_number = FrameTimeline.surface_frame_token`。下面这些关联方式都不可靠：

- 只按数值相等连接帧号与令牌；
- 只按图层名称连接整段跟踪数据；
- 把缓冲区 ID 当作 Surface 令牌；
- 用相邻行号推定同一帧。

稳妥顺序是：

1. 在 `actual_frame_timeline_slice` 中用进程、图层、Surface/显示令牌找出目标帧；
2. 用 Perfetto 界面流向观察该 SurfaceFrame 与 DisplayFrame 的正式关联；
3. 在它的时间窗口内查应用主线程、RenderThread、`BufferTX`、`frame_slice` 与围栏；
4. 用图层名称和时间区间缩小 FrameTracer 候选；
5. 若必须自动匹配，把“时间窗口 + 图层 + 生产者帧元数据”标为启发式规则，并统计未匹配/多匹配率。

FrameTimeline 用于判断这帧相对计划是否异常；FrameTracer 用于拆分缓冲区阶段。二者互补，但没有公共的万能 ID。

## 13. 采集配置与覆盖边界

下面的 TraceConfig 片段用于同时启用两个 SurfaceFlinger 数据源：

```protobuf
data_sources {
  config {
    name: "android.surfaceflinger.frametimeline"
  }
}

data_sources {
  config {
    name: "android.surfaceflinger.frame"
  }
}
```

采集后先确认两张 FrameTimeline 表和 `frame_slice` 都有目标进程/图层数据。数据缺失可能来自：

- 跟踪开始得太晚，期望事件或前序缓冲区事件不在文件中；
- SurfaceView/独立 Surface 的官方覆盖限制；
- 生产者没有传递有效的 FrameTimelineInfo；
- 图层在采集期间创建、销毁或改名；
- 围栏仍处于待定状态，且同一缓冲区后续没有触发 FrameTracer 重查；
- 显示关闭、模式/电源切换或展示围栏不可用；
- 厂商图形管线未暴露足够事件。

缺少事件只能降低结论强度，不能自动归因给应用、SurfaceFlinger、HWC 或驱动。

## 14. Android 12—17 的解释边界

| 版本 | 相关边界 |
|---|---|
| Android 12 / API 31 | FrameTimeline 可用于标准应用窗口，提供应用/SurfaceFlinger 期望值与实际值 |
| Android 13 / API 33 | 默认的未发信号缓冲区锁存策略改变了锁存与获取围栏发出信号的先后解释 |
| Android 14 / API 34 | 标准窗口的 token、SurfaceFrame、DisplayFrame 分析主线延续 |
| Android 15 / API 35 | HDR/余量等显示能力会改变图层/显示条件，不改变两类令牌的关系 |
| Android 16 / API 36 | 主数据模型延续；跨版本分析仍要固定刷新率、设备固件与 Perfetto 版本 |
| Android 17 / API 37 | 源码锚点更新到 Android 17；15 个 JankType 原因位、500 令牌实现、旧版/实验版分类与当前 SQL 解析器均按 `android-17.0.0_r1` 核对 |

“源码存在于 Android 17”不等于“Android 17 首次加入”。涉及版本首引时，应继续比较历史标签或公开 API 文档。

## 总结

FrameTracer 以缓冲区 ID、帧号和图层名称描述从生产者到展示的阶段；FrameTimeline 以 Surface/显示令牌描述计划、完成与卡顿。前者进入 `frame_slice`，后者进入 `expected_frame_timeline_slice` 与 `actual_frame_timeline_slice`。

分析一帧时，先用 FrameTimeline 确认目标应用/图层、Surface 令牌、显示令牌和分类，再用 FrameTracer、线程切片、BufferTX、围栏与 HWC 证据解释具体阶段。不能假设帧号等于令牌，也不能用某个未发射枚举的缺席证明合成路径。
