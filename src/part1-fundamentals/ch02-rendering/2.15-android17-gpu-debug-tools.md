# 2.15 Android 17 GPU 图形调试与性能优化工具链

## 要点

### 🔹 GPU 性能分析框架：渲染管线的可观测性分层

要理解 GPU 性能分析工具的架构定位，需要先看清 Android 渲染管线中**可观测性的三个层次**，以及每一层能"看到"什么、看不到什么。

**第一层：CPU 侧时间线（Perfetto 主场）**

应用主线程的 Measure → Layout → Draw → RenderThread 提交，以及 SurfaceFlinger 的合成调度——这些全部是 CPU 侧执行，Perfetto 能完整捕获。当帧时间超标，第一步永远是确认瓶颈在 CPU 侧还是 GPU 侧。如果 RenderThread 的 draw 调用很快返回、主线程没有阻塞，但帧仍然超时，GPU 就是嫌疑对象。

Perfetto 在 GPU 侧提供的是**系统级 metric**，不是帧级调试能力：

| 数据源 | 机制 | 能力 | 局限 |
|--------|------|------|------|
| GPU 频率 | `power/gpu_frequency` ftrace | DVFS 频率变化追踪 | Pixel 设备可靠；Adreno 需 `kgsl/gpu_frequency`，Mali 默认不暴露 [待验证: 厂商差异] |
| GPU 内存 | `gpu_mem/gpu_mem_total` ftrace | 全局/per-process GPU 内存 | Android 10+，通过 GpuService 上报 |
| GPU 计数器 | `gpu.counters` producer | 硬件性能计数器采样 | producer 在 GPU 驱动中实现，需厂商适配；直接用 Perfetto 配置难以可靠启用 |
| GPU Render Stages | `gpu.renderstages` producer | GPU 命令执行时间线 | 粒度取决于驱动实现，render pass 级别而非 Draw Call 级别 |
| GPU Work Period | `power/gpu_work_period` ftrace | GPU 活跃工作周期 | 仅 Pixel 6+，用于功耗估算 |
| FrameTimeline | `android.surfaceflinger.frametimeline` | 帧预期/实际时间线、jank 归因 | Android 12+；SurfaceView 不支持 |

[已验证: Perfetto 官方文档, perfetto.dev/docs/data-sources/gpu]

**第二层：GPU 内部行为（专用工具主场）**

Perfetto 能告诉我们"GPU 在忙"，但看不到 GPU 内部在忙什么——是显存带宽瓶颈、Shader 太复杂打满 ALU、还是 Draw Call 太多导致驱动开销。这些答案需要 GPU 专用分析工具：

- **AGI**（Android GPU Inspector）：Google 官方工具，双模架构（System Profiler + Frame Profiler）
- **Sokatoa**：三星 SARC + Google + LunarG 联合开发，2026 年 3 月发布，基于 GFXReconstruct 的跨厂商 Vulkan Profiler
- **RenderDoc**：开源跨厂商帧调试器，支持 Vulkan 和 OpenGL ES
- **厂商专用工具**：Arm Streamline/Frame Advisor（Mali）、Qualcomm Snapdragon Profiler（Adreno）、Imagination PVRTune（PowerVR）

**第三层：GPU 微架构级（厂商工具深度分析）**

需要分析特定 GPU 微架构的性能时，只有厂商工具能提供足够深度：ARM Mali 的约 80 个硬件计数器（Streamline）、Adreno 的 DSP/功耗/温控全维度分析（Snapdragon Profiler）。这些工具直接读取 GPU 寄存器，不经过 Android 框架层。

> 💡 三层之间的关系不是替代而是互补：先用 Perfetto 确认"问题在 GPU"，再用 GPU 工具定位"GPU 哪个环节慢"，最后用厂商工具深入"微架构为什么慢"。工具选型决策矩阵详见 §14.8。

### 🔹 Android 17 GPU 调试器架构：工具链分层与管线集成

Android 17 的 GPU 调试工具链在架构上呈现**命令行工具 + 系统级追踪 + 帧级分析**三个维度，每个维度通过不同的机制与渲染管线集成。

#### 命令行工具：flatland 与 sfdo 的双重定位

Android 源码树 `frameworks/native/cmds/` 下有两个与 GPU/合成器调试相关的工具，它们代表了"基准"与"调试"两条线在命令行层面的分流：

**flatland**（C++ cc_benchmark）：长期维护的 GPU 2D 合成基准工具，起源于 2012 年。使用 OpenGL ES 2.0 + gralloc + 显式同步框架，跑 5 类预定义场景（单静态窗口、App→Home 转场、SurfaceView→Home 转场、ColorBlend、Stacking），输出 frame time（ms）。定位是 SoC 选型阶段的 GPU 硬件性能评估，不是日常开发调试工具。

```python
# frameworks/native/cmds/flatland/Android.bp (android-17.0.0_r1)
cc_benchmark {
    name: "flatland",
    srcs: ["Composers.cpp", "GLHelper.cpp", "Renderers.cpp", "Main.cpp"],
    shared_libs: ["libEGL", "libGLESv2", "libcutils", "libgui", "libui", "libutils"],
    compile_multilib: "both",  # 同时产出 32/64 位
}
```

核心抽象包括 `Composer`（层叠加）和 `Renderer`（层内容生成）两个接口，通过 `LayerDesc` 数据驱动组装测试场景。依赖精简到 `libgui`（SurfaceControl + BufferQueue）+ `libui`（Fence）+ GLES 2.0，不依赖 GLES 3.x。

[已验证: AOSP android-17.0.0_r1, frameworks/native/cmds/flatland/Android.bp, Main.cpp, Flatland.h]

**sfdo**（Rust + AIDL）：2024 年新增的 SurfaceFlinger 命令行工具，用 Rust edition 2021 编写，通过 `clap` 解析参数 + `android_gui::ISurfaceComposer` AIDL bindgen 绑定到 SurfaceFlinger 服务。提供 5 个子命令：

| 子命令 | 功能 |
|--------|------|
| `debug-flash` | 调试闪烁（屏幕边缘闪烁用于刷新率验证） |
| `force-client-composition` | 强制 GPU 合成（绕过 HWC，排查 HWC bug） |
| `frame-rate-indicator` | 帧率指示器显示 |
| `schedule-composite` | 手动触发合成调度 |
| `schedule-commit` | 手动触发提交流程 |

[已验证: AOSP android-17.0.0_r1, frameworks/native/cmds/sfdo/]

这两个工具的演进趋势是：C++ 基准工具（flatland）保持稳定，Rust + AIDL 调试工具（sfdo）代表新方向——Google 在命令行层面逐步用 Rust 重写 SF 交互工具，利用 AIDL bindgen 保证类型安全。

#### AGI：双模架构与管线集成

AGI 的架构分两部分，各自以不同方式与渲染管线交互：

**System Profiler** 本质是面向 GPU 场景优化过的 Perfetto 封装。通过两种方式调用 Perfetto：调用设备上的 `perfetto` CLI，或通过 `/dev/socket/traced_consumer` 直连 traced 守护进程。其核心增值在于 GPU 硬件计数器的收集——通过 `agi_launch_producer` 工具在 trace 开始前预先启动位于 GPU 驱动内部的 Perfetto data producer，解决手动配置 Perfetto GPU counter producer 成功率不稳定的问题。

**Frame Profiler** 是完全独立于 Perfetto 的系统，基于 Graphics API 拦截-重放架构：
- **GAPII**（Graphics API Interceptor）：通过 Vulkan Layer 注入目标进程，拦截所有 Vulkan API 调用并序列化为 gfxtrace 文件。对 OpenGL ES 应用，安装定制 ANGLE 先将 GLES 转译为 Vulkan 再拦截
- **GAPIR**（Replayer）：在设备上重放捕获的帧，支持懒加载资源
- **GAPIS**（Server）：开发机上的 Go 服务，协调捕获/重放/分析，内嵌 Perfetto Trace Processor 解析系统 trace

[已验证: AGI 官方文档, developer.android.com/agi; DeepResearch: Android GPU 性能分析工具链现状]

#### Sokatoa：下一代跨厂商 GPU Profiler

2026 年 3 月，三星 Austin Research Center（SARC）联合 Google、LunarG 发布 Sokatoa。底层构建于 LunarG 的 GFXReconstruct 捕获-重放引擎，仅支持 Vulkan。核心差异化特性包括**多帧 GPU Profiling**（可同时分析多个连续帧的渲染行为，解决单帧捕获工具的结构性盲区）和**On-Device Shader 编辑重放**。

Google 选择与三星共建新工具而非继续投入 AGI——AGI 在 2025 年 1 月发布 v3.3.3 后 15 个月无新版本，设备兼容性列表仅约 16-17 款机型。Sokatoa 的出现标志着 Google GPU 工具战略的转向，但 AGI 文档仍在更新，未正式弃用。

[已验证: github.com/sarc-acl/sokatoa; GDC 2025 Android Developers Blog]

### 🔹 GPU 性能瓶颈定位：从管线事件到根因归因

当 Perfetto FrameTimeline 显示某帧超时，如何判定瓶颈在 GPU 侧的哪个环节？这涉及渲染管线中多个阶段的性能归因机制。

#### FrameTimeline 的 Jank 归因

SurfaceFlinger 的 FrameTimeline 子系统（详见 §2.52）对每帧进行预期/实际时间对比，并将 jank 归类。GPU 相关的 jank 类型包括：

- **GPU composition jank**：SurfaceFlinger 使用 RenderEngine（GLES/Vulkan）进行客户端合成，GPU 合成耗时超过 vsync deadline
- **HWC fallback jank**：Hardware Composer 无法处理某些 layer 组合，回退到 GPU 合成导致超时
- **App GPU rendering jank**：应用 RenderThread 的 GPU draw 调用耗时过长，导致 buffer 未在 deadline 前_queueBuffer_

FrameTimeline 通过 `FrameTracer` 的 Perfetto Custom DataSource 在 Layer buffer 生命周期的 6 个关键点（DEQUEUE / QUEUE / POST / ACQUIRE_FENCE / LATCH / PRESENT_FENCE）写入时间戳，使得每帧的 GPU 相关事件可以在 trace 中精确定位。

[已验证: AOSP android-17.0.0_r1, frameworks/native/services/surfaceflinger/Layer.cpp, FrameTracer/FrameTracer.cpp]

#### GPU 计数器与瓶颈类型

当确认瓶颈在 GPU 内部后，GPU 硬件计数器能进一步区分瓶颈类型。不同 GPU 厂商暴露的计数器名称和定义不同（这是跨设备标准化的核心难题，详见 §2.52 的 InternedGpuCounterDescriptor 机制），但常见类别包括：

| 瓶颈类型 | 相关计数器信号 | 管线含义 |
|----------|---------------|---------|
| ALU 瓶颈 | Shader cycles > 访存 cycles | Shader 太复杂，算术逻辑单元打满 |
| 带宽瓶颈 | 访存 cycles 占比高、L2 cache miss 高 | 显存带宽不足，纹理采样或 buffer 读写拥堵 |
| 光栅化瓶颈 | Primitive throughput 低 | 几何体过多或过小（overdraw 严重） |
| 驱动开销 | Draw Call count 高 + per-call GPU time 低 | 大量小 Draw Call，GPU 启动开销成瓶颈 |
| Tile 刷新 | Tile flush count 高（TBR 架构） | 频繁切换 render target 导致 tile reload |

> ⚠️ 不同 GPU 架构（ARM Mali 的 TBR、Adreno 的 FlexRender、PowerVR 的 TBDR）对同一工作负载的瓶颈表现差异巨大。TBR/TBDR 架构下，切换 render target 的代价远高于立即渲染架构（IMR），因为每次切换都需要 store/load tile buffer。这一点在 §2.10 GPU 渲染深入中有更详细的架构对比。

#### HWC 与 GPU 合成的性能边界

当 SurfaceFlinger 判断 layer 组合超出 HWC 能力时，回退到 GPU（RenderEngine）合成。这个回退路径的性能特征与 HWC 合成截然不同：

- HWC 合成在显示控制器硬件中完成，几乎不消耗 GPU 时间
- GPU 合成需要 SurfaceFlinger 调用 RenderEngine（基于 GLES 或 Vulkan），在 GPU 上执行渲染命令
- `sfdo force-client-composition` 命令可以强制 GPU 合成，用于排查"HWC 实际处理了但结果错误"的问题

FrameTimeline 中 `FALLBACK_COMPOSITION` 事件标记（对应 Layer.cpp 中 client composition timestamp 的 FrameTracer 调用）专门追踪这一回退路径。

[已验证: AOSP android-17.0.0_r1, frameworks/native/services/surfaceflinger/Layer.cpp]

### 🔹 实时性能监控：GPU 频率/热/功耗的管线感知

GPU 实时监控不是独立的子系统——它通过多个路径与渲染管线交互，影响帧调度和合成策略。

#### GPU 频率追踪与 DVFS

Android 的 GPU DVFS（Dynamic Voltage and Frequency Scaling）频率信息通过 ftrace 暴露：

```
# power/gpu_frequency tracepoint（标准）
# kgsl/gpu_frequency tracepoint（Adreno 特定）
```

Perfetto 通过 `power/gpu_frequency` ftrace 事件追踪 DVFS 频率变化。然而这个 tracepoint 在不同厂商设备上的可靠性差异显著：Pixel 设备（Tensor GPU）可靠工作，Adreno 设备需要 `kgsl/gpu_frequency`，Mali 设备的暴露情况取决于厂商驱动实现。

Perfetto v52.0（2025 年 9 月）新增了 Adreno 频率轮询支持，通过直接读取 sysfs 节点而非依赖 ftrace，改善了非 Pixel 设备的 GPU 频率追踪覆盖。

[已验证: Perfetto 官方文档; 待验证: v52.0 Adreno 轮询具体实现路径]

#### 热节流与 ADPF 集成

Android 的 ADPF（Android Dynamic Performance Framework）通过 Power HAL 向应用提供热状态信号。GPU 是热节流的主要触发源之一——重度 GPU 负载（游戏、复杂动画）会快速拉高 SoC 温度，触发降频。

ADPF 的 `PowerManager.getThermalHeadroom()` API 让应用查询未来一段时间内的热裕量，应用可据此主动降低 GPU 负载（如降低分辨率、简化 shader）以避免被动节流。这个信号走的是 Power HAL 通道而非 PSI（Pressure Stall Information），是 GPU 前瞻性性能管理的应用侧入口。

[适用版本: Android 12+ (API 31+)]

#### GPU Work Period

Pixel 6+ 设备暴露 `power/gpu_work_period` ftrace 事件，追踪 GPU 活跃工作周期。这个数据源主要用于功耗估算（如 Perfetto 的 Wattson 面板），不在标准 Android 兼容性要求中——其他厂商设备不一定暴露。

### 🔹 渲染异常分析：从管线异常到诊断

#### GPU 复位事件

GPU 复位（GPU reset）是严重的渲染异常——驱动检测到 GPU 挂起或超时后重置 GPU 硬件状态。在 Perfetto trace 中，GPU 复位通常表现为：

- RenderThread 的 GPU 命令突然全部返回错误
- FrameTimeline 中连续多帧的 GPU composition 显示为异常时长（极短=命令被丢弃，极长=等待复位完成）
- SurfaceFlinger 可能触发 HWC → GPU 合成切换或 layer 重建

[待验证: Android 17 是否有专用的 GPU reset tracepoint；当前依赖间接特征诊断]

#### HWC ↔ GPU 合成切换

SurfaceFlinger 的合成策略是动态的——每帧都可能根据 layer 变化重新决定使用 HWC 还是 GPU 合成。频繁的 HWC ↔ GPU 切换本身可能是性能问题的征兆：

- 应用频繁更新 layer 内容/属性 → HWC 需要重新评估合成策略
- 透明度/圆角/复杂变换导致 layer 超出 HWC 能力 → 回退 GPU
- HWC 能力不足（layer 数量上限、格式不支持）→ 部分 layer GPU 合成

通过 `dumpsys SurfaceFlinger` 可以查看最近帧的合成类型分布。Perfetto trace 中 `FALLBACK_COMPOSITION` 事件的密度是判断切换频率的直接指标。

#### 驱动层问题诊断

GPU 驱动 bug 的典型表现包括：随机崩溃（native crash 在 libGLESv2.so / vulkan.so 中）、渲染错误（画面撕裂/花屏/黑屏）、性能骤降（驱动内部 fallback 到软件渲染）。

诊断工具链：
1. Perfetto 确认崩溃发生的时间点和调用栈
2. `debug.sf.disable_backpressure` 等属性帮助隔离 SF 侧 vs GPU 侧问题
3. AGI/Sokatoa 帧捕获确认是否特定 Draw Call 触发驱动 bug
4. 厂商 GPU 工具查看驱动内部状态（需要 root 或厂商调试权限）

## 扩展

### 🔸 Vulkan 工具链集成：Layers 与捕获-重放架构

Android 的 Vulkan 调试基础设施核心是 **Vulkan Layers** 机制——可插拔的 layer 在 Vulkan 实例/设备创建时被加载，拦截所有 Vulkan API 调用。这是 AGI Frame Profiler、Sokatoa、RenderDoc 实现 GPU 调试的共同基础。

关键组件：

- **VK_LAYER_GOOGLE_gpu_timeline**：Google 维护的 Vulkan layer，将 GPU command buffer 执行时间线写入 Perfetto trace
- **VK_LAYER_GOOGLE_threading**：多线程 Vulkan 调用序列化，用于诊断线程安全问题
- **VK_LAYER_LUNARG_monitor**：LunarG 的监控 layer，显示 FPS 和 GPU 信息
- **GFXReconstruct**：LunarG 的捕获-重放引擎，是 Sokatoa 的底层基础。捕获 Vulkan API 调用序列为 `.gfxr` 文件，支持离线重放和分析
- **SPIR-V 工具链**：Validator（验证 SPIR-V 合规性）、Optimizer（优化 shader 字节码）、Cross（反编译为 GLSL/HLSL）

对于 OpenGL ES 应用，AGI 通过安装定制 ANGLE 实现（`org.chromium.angle.agi`）将 GLES 调用转译为 Vulkan，再通过 Vulkan Layer 拦截——这是一种"间接拦截"策略，可能引入与原生 GLES 驱动的行为差异。

[已验证: Vulkan LunarG 工具文档; AGI 官方文档]

ANGLE（Almost Native Graphics Layer Engine）本身在 Android 17 中也作为系统级 GLES 实现可选：当应用或调试工具指定使用 ANGLE 时，所有 GLES 调用走 ANGLE → Vulkan 路径而非厂商原生 GLES 驱动。SurfaceFlinger 的 `sfdo` 工具不直接操作 ANGLE，但开发者可通过 `dumpsys gfxinfo` 查看应用的 ANGLE 使用状态和统计信息。

### 🔸 游戏引擎与 GPU 管线协同

游戏是 GPU 负载最重的应用类型，Android 为游戏场景提供了专门的 GPU 管线协同机制：

**ADPF（Android Dynamic Performance Framework）** 让游戏引擎根据热状态动态调整 GPU 工作负载。游戏通过 `PerformanceHintManager` 获取 GPU 热裕量信号，主动降低 shader 复杂度或渲染分辨率。ADPF 还提供 `FrameRateManager` 让游戏声明目标帧率，SurfaceFlinger 据此优化帧调度和 GPU 频率。

**Game Mode API** 让用户选择性能/省电/标准模式，系统据此调整 GPU DVFS 策略。Performance Mode 下 GPU 更频繁地运行在最高频率，Battery Saver 下 GPU 频率被限制。

**Frame Pacing Library (Swappy)** 确保帧提交节奏与显示 vsync 对齐，避免 GPU 渲染过快（浪费功耗）或过慢（掉帧）。Swappy 通过 `eglPresentationTimeANDROID` 或 `vkQueuePresent` 的 present timestamp 精确控制 GPU 合成结果的提交时机。

这三者的协同关系：ADPF 管"GPU 能跑多快"、Game Mode 管"GPU 该跑多快"、Swappy 管"帧什么时候提交给 GPU 合成"。详见 §2.17 Frame Pacing Library 和 §19.1 游戏性能优化。

> 本节聚焦 GPU 调试工具链在渲染管线中的架构定位和数据流。具体工具的使用教程、操作步骤和截屏分析详见 §14.8「GPU 图形调试与分析工具」；SurfaceFlinger 内部 GPU 调试子系统（FrameTracer / TimeStats / JankTracker）的源码级分析详见 §2.52。
