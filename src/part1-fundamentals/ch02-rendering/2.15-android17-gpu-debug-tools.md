# 2.15 Android 17 GPU 图形调试与性能优化工具链

GPU 性能分析最容易犯的错误，是先打开一个 GPU 工具，再设法从图中找结论。更稳妥的顺序是先回答“哪一帧、哪个阶段、哪块 GPU 工作、哪项证据”，再选择能回答下一层问题的工具。

平台源码以 Android 17 / API 37 / `android-17.0.0_r1` 为锚点，分析范围从 FrameTimeline、Perfetto/Android Performance Analyzer（APA）延伸到 AGI、Sokatoa、RenderDoc 和厂商分析器。内核侧以 `android17-6.18-2026-06_r6` 为边界；量产设备的 GPU 驱动与计数器仍以厂商实现为准。

## 1. 工具回答的问题不同

一帧从应用提交到屏幕，需要经过应用 CPU、GPU、SurfaceFlinger、RenderEngine/HWC 和显示设备。没有任何单一工具能完整解释每个阶段。

| 问题 | 首选证据 | 适合的工具 |
|---|---|---|
| 哪些帧 late，责任更靠近 App 还是 SurfaceFlinger | expected/actual FrameTimeline、jank type | Perfetto、APA |
| CPU 在哪里阻塞或被抢占 | sched、线程 slice、Binder、锁、fence wait | Perfetto、APA |
| GPU 何时执行、队列是否繁忙 | GPU render stages、fence、GPU frequency | Perfetto、APA、AGI System Profile |
| GPU 为什么慢 | 硬件计数器、render pass、shader、带宽与利用率 | AGI、Sokatoa、厂商 profiler |
| 哪个 draw、pipeline 或资源造成错误 | API capture/replay、framebuffer、shader、state | AGI Frame Profiler、RenderDoc、Sokatoa |
| HWC 与 RenderEngine 路径是否影响结果 | composition type、FrameTracer、对照实验 | Perfetto、`sfdo`、设备 HWC trace |
| 驱动是否 hang/reset | fence、内核/驱动日志、crash dump、厂商事件 | Perfetto 加厂商内核工具 |

工具覆盖范围越深，对设备驱动、可调试构建和捕获时扰动的要求通常越高。一个生产问题往往需要两轮数据：先用低扰动的系统 Trace 找到目标窗口，再用 GPU 工具对该场景做短时捕获。

## 2. 一套可重复的分析顺序

### 2.1 固定场景和测试条件

在判断 GPU bound 前，先记录：

- 设备、系统 build、GPU 和驱动版本；
- 分辨率、显示刷新率、游戏画质和目标帧率；
- 应用是 debuggable、profileable 还是量产包；
- 温度、充电状态、持续运行时间；
- 是否开启固定性能模式，是否改变了调度或 DVFS 行为；
- 每轮测试从冷启动、热启动还是稳定态开始。

移动 GPU 的频率和热限制会随时间变化。只比较一次优化前后截图，无法区分代码变化与设备状态变化。

### 2.2 用 FrameTimeline 找到目标帧

Android 12 起，`android.surfaceflinger.frametimeline` 提供 App SurfaceFrame 和 SurfaceFlinger DisplayFrame 的 expected/actual 时间线。它适合先回答：

- App 是否错过 deadline；
- SurfaceFlinger 是否错过 deadline；
- 该帧是 early、on-time 还是 late present；
- 是否发生 buffer stuffing；
- SurfaceFlinger 是否使用 GPU/client composition；
- App 帧与最终 DisplayFrame 如何关联。

FrameTimeline 的 `AppDeadlineMissed` 使用应用帧的 post time 和 GPU 完成时间参与判断。它可以把排查方向指向应用帧，但不会指出 shader 中的慢指令。

官方 Perfetto 文档仍注明 SurfaceView 暂不支持完整的 App FrameTimeline。游戏、Camera、Video 常把主体内容放在独立 SurfaceView/Surface，因此不能只看宿主 Activity 的 App timeline。还需要追踪主体 Layer、BufferQueue、acquire fence、SurfaceFlinger DisplayFrame 和 present。

### 2.3 判断 CPU、GPU、合成还是显示

以一帧为单位检查：

1. `Choreographer#doFrame`、游戏线程和 RenderThread 是否按时开始；
2. CPU 是否被调度延迟、锁、Binder、GC 或资源加载拖慢；
3. 应用何时 queue buffer，acquire fence 何时 signal；
4. GPU render stage 是否延伸到 App deadline 之后；
5. SurfaceFlinger 是否做 client composition；
6. present fence 与 DisplayFrame 是否延迟；
7. 显示模式切换、HWC validate/present 或驱动事件是否与该帧重合。

只有第三、四项把延迟指向应用 GPU 工作时，才进入 shader、带宽、render pass 等微架构分析。若 buffer 本来就提交晚，GPU 利用率高可能只是同一场景的伴随现象。

### 2.4 做单变量对照

常用对照包括：

- 同一场景降低渲染分辨率；
- 关闭某个后处理 pass；
- 固定显示模式和目标帧率；
- 分别使用 HWC 与强制 client composition；
- 保持画面不变，只替换一个 shader 或纹理格式；
- 同一设备、相近温度下重复多轮。

若降低分辨率后 GPU render stage 明显缩短，应优先检查像素填充、带宽或后处理；这项变化仍不能单独区分 ALU 与带宽，需要硬件计数器或帧级分析。

## 3. Perfetto 与 APA：系统时间线

### 3.1 APA 与 Perfetto 的关系

截至 2026 年 7 月，Android Performance Analyzer 的 System Profiler 处于公开 beta，Android 官方将它作为新的系统 profiling 推荐入口。APA 可以采集 CPU、GPU、内存和功耗数据，也允许使用自定义 Perfetto `TraceConfig`。

Perfetto 仍是 Android 系统 Trace 的数据采集、Trace Processor 和 SQL 分析基础。工程团队可以根据工作方式选择入口：

- 需要开箱即用的录制和分析界面：APA；
- 需要精确 `TraceConfig`、自动化采集或 SQL 回归：Perfetto CLI/Trace Processor；
- 已有 AGI 工作流：AGI System Profile 仍可使用，但官方 quickstart 已提示系统 profiling 优先评估 APA。

### 3.2 Android GPU 数据源

Perfetto 官方定义了以下 GPU 数据源：

| 数据源 | 能回答什么 | 不能直接推出什么 |
|---|---|---|
| `power/gpu_frequency` | GPU 频率变化 | GPU 利用率、某个 shader 的耗时 |
| `gpu_mem/gpu_mem_total` | 全局或进程 GPU 内存总量事件 | 内存带宽、缓存命中率、泄漏对象 |
| `gpu.counters` | 设备 producer 暴露的硬件计数器 | 跨 GPU 通用的计数器名称和阈值 |
| `gpu.renderstages` | graphics/compute submission 的 GPU 时间线 | 每个 API draw 的完整状态与资源 |
| `vulkan.memory_tracker` | Vulkan 分配和绑定事件 | GLES 或厂商私有分配的完整视图 |
| `gpu.log` | producer 上报的 GPU 调试消息 | 所有驱动错误或 reset |

下面这段最小配置用来请求通用 GPU 频率与 render-stage 数据。它只说明数据源名称，不能据此假设所有设备都会返回数据：

```textproto
buffers {
  size_kb: 32768
  fill_policy: RING_BUFFER
}

data_sources {
  config {
    name: "linux.ftrace"
    ftrace_config {
      ftrace_events: "power/gpu_frequency"
      ftrace_events: "gpu_mem/gpu_mem_total"
    }
  }
}

data_sources {
  config {
    name: "gpu.renderstages"
  }
}
```

设备可能注册带硬件后缀的数据源，例如 `gpu.counters.adreno` 或 `gpu.renderstages.mali`。Perfetto 跟踪服务会精确匹配数据源名称。录制前应查询设备的 data-source descriptor，使用其中公布的名称、counter ID 或 counter name。

空轨道不等于 GPU 空闲。它也可能表示：

- 内核没有该 tracepoint；
- GPU producer 没有注册；
- 数据源名字或计数器 ID 不匹配；
- 应用的 Graphics API 不在该 producer 的覆盖范围；
- 权限、驱动或设备验证未满足。

### 3.3 如何读取频率和计数器

频率升高只表示 DVFS 选择发生变化。频率处于高位时，GPU 可能繁忙，也可能被策略提前拉升；频率处于低位时，GPU 可能受到热、功耗或策略限制，也可能负载很轻。

硬件计数器应按目标 GPU 的官方定义读取。不同架构对“繁忙”“带宽”“tile”“cache miss”“shader core active”等指标的命名和归一化方式不同。不能维护一张跨 Mali、Adreno、PowerVR 的通用阈值表。

合理的解释方式是：

1. 先找到目标 GPU render stage；
2. 取该时间窗口内的计数器；
3. 使用同一设备、同一场景的基线做比较；
4. 一次只改变一个渲染因素；
5. 用厂商文档解释计数器含义。

### 3.4 FrameTimeline 中的 GPU 标记

FrameTimeline 的 `GPU Composition` 表示该 DisplayFrame 是否由 GPU 客户端合成参与。它描述的是 SurfaceFlinger 的 RenderEngine 路径，不等同于应用内容是否由 GPU 渲染。

例如，游戏 buffer 由应用 GPU 生成，随后 HWC 可以把该 Layer 作为 `DEVICE` composition 直接扫描输出；这时应用仍可能受 GPU bound，而 DisplayFrame 的 client composition 标记为 `false`。反过来，一个 CPU 绘制的普通 buffer 也可能因整屏组合条件进入 RenderEngine client composition。

## 4. FrameTracer：Layer buffer 事件

Android 17 的 `FrameTracer` 注册 Perfetto data source：

```text
android.surfaceflinger.frame
```

`Layer.cpp` 在具体 Layer/buffer 上写入事件。`GraphicsFrameEvent::BufferEventType` 包括 `DEQUEUE`、`QUEUE`、`ACQUIRE_FENCE`、`LATCH`、`HWC_COMPOSITION_QUEUED`、`FALLBACK_COMPOSITION`、`PRESENT_FENCE` 等类型。

需要把它与 FrameTimeline 分开理解：

- FrameTimeline 围绕 expected/actual frame、token、deadline 和 jank type；
- FrameTracer 围绕 layer name、buffer ID、frame number、buffer 生命周期事件和 fence；
- 两者都来自 SurfaceFlinger，但 data source、数据结构和分析问题不同。

Android 17 的 `Layer.cpp` 在设置 buffer 时记录 dequeue/queue 时间，在 latch 时记录 acquire fence 和 latch，在合成后记录 RenderEngine fallback 或 HWC 路径及 present fence。它适合回答“哪一块 buffer 何时被 SurfaceFlinger 接收、锁存、合成和展示”。

`FALLBACK_COMPOSITION` 是 FrameTracer 的 buffer event，表示该 buffer 走 RenderEngine composition。它不是所有 Perfetto 配置都会默认出现的独立顶层 slice，也不能仅凭事件数量判断 GPU 是性能瓶颈。

## 5. APA、AGI、Sokatoa 与 RenderDoc 怎么选

### 5.1 Android Performance Analyzer

APA System Profiler 适合系统级 CPU/GPU/内存/功耗关联分析。它侧重时间线与跨子系统关系，不用于逐 draw 检查 shader、pipeline 和纹理。

适用问题：

- 一段 gameplay 的帧率和长帧分布；
- CPU 与 GPU 是否并行、是否存在空洞；
- GPU 频率、内存和设备提供的计数器；
- 应用与 SurfaceFlinger、HWC、调度、热状态的关系。

### 5.2 Android GPU Inspector

AGI 有两类能力：

- System profiling：系统时间线及 GPU 数据；
- Frame profiling：捕获单帧，检查 Vulkan 调用、framebuffer、draw、内存、pipeline、state、shader 和 texture。

AGI Frame Profiler 直接跟踪 Vulkan。OpenGL ES 应用通过 AGI 提供的定制 ANGLE 转成 Vulkan 后捕获，因此重放路径可能与设备原生 GLES 驱动不同。若问题只在原生 GLES 驱动出现，应保留原路径证据，并用厂商工具或其他捕获方式复核。

AGI 需要兼容的 GPU 驱动并会执行设备验证；模拟器不在官方支持范围内。设备未通过验证时，不应把缺失计数器解释为 GPU 没有工作。

### 5.3 Sokatoa

Sokatoa 面向 Android Vulkan 应用，提供 system 与 frame 视角的多帧捕获、Vulkan API/pipeline/shader 分析和设备端重放。项目当前资料要求 Android 13 或更高版本；捕获 GFXReconstruct 和 Sokatoa Vulkan layer 时，需要 debuggable APK 或已取得 root 权限的设备。

它适合单帧工具难以覆盖的跨帧问题，例如：

- 间歇出现的 pipeline/state 抖动；
- 连续帧资源生命周期；
- 某个 shader 修改对后续多帧的影响。

项目由 Samsung Austin Research Center 发起，并与 Google、LunarG 协作。这个事实不能延伸为 AGI 已停止维护或 Android 工具路线已经迁移；工具选型仍以目标 API、设备支持和问题类型为准。

### 5.4 RenderDoc 与厂商 profiler

RenderDoc 适合 Android Vulkan 的帧捕获、资源与渲染状态检查，通常要求应用可调试。它能定位 API/state/资源问题，但通用视角不一定包含目标 GPU 的全部微架构计数器。

需要解释 Mali、Adreno、PowerVR 或 Xclipse 的特定计数器时，应使用对应的厂商 profiler。厂商工具更接近驱动与硬件，但采集权限、设备列表和计数器定义随 GPU/驱动版本变化。报告中应记录工具版本与计数器文档版本。

## 6. AOSP 自带的两个辅助工具

### 6.1 `sfdo`：控制 SurfaceFlinger 的对照工具

Android 17 的 `frameworks/native/cmds/sfdo/sfdo.rs` 使用 Rust 2021、`clap` 和 `ISurfaceComposer` AIDL。源码包含 7 个子命令：

| 子命令 | 用途 |
|---|---|
| `debug-flash` | 设置 SurfaceFlinger debug flash |
| `force-client-composition` | 强制窗口走 GPU/client composition |
| `frame-rate-indicator` | 显示或隐藏刷新率覆盖层 |
| `schedule-composite` | 提前请求一次 composite |
| `schedule-commit` | 提前请求一次 commit |
| `force-pacesetter` | 强制指定多显示场景中的 pacesetter display |
| `reset-forced-pacesetter` | 清除强制 pacesetter |

下面的命令用于比较 HWC 与 RenderEngine 路径。执行前要确认测试设备包含 `sfdo`，调用方也要有 SurfaceFlinger access 权限：

```bash
adb shell sfdo force-client-composition enabled
# 复现场景并录制一轮 Trace
adb shell sfdo force-client-composition disabled
```

第二条命令必须执行，以恢复设备状态。若强制 client composition 后问题消失，说明差异与 HWC/device composition 路径相关；若问题加重，只能说明额外的 RenderEngine 工作改变了系统，仍需结合 composition type、fence 和 HWC 日志定位。

`sfdo` 不是 GPU profiler。它不会提供 shader、带宽或 GPU counter，也不应成为量产应用的功能依赖。

### 6.2 `flatland`：合成基准

Android 17 的 `flatland` 是 `cc_benchmark`，使用 EGL、OpenGL ES 2.0、`libgui`、`libui` 和 fence 运行合成场景，并分别构建 32 位 `flatland` 与 64 位 `flatland64`。

它适合平台工程中的可重复合成基准与回归比较。它不是线上帧诊断器，也不能代表真实应用的 shader、资源加载、游戏引擎或 HWC 行为。测试报告必须写明场景、分辨率、刷新率和设备状态。

## 7. 从症状走向证据

### 7.1 怀疑应用受 GPU bound

建议要求同时满足多项证据：

- App FrameTimeline late，CPU 提交没有同等幅度的延迟；
- 对应 GPU stage 或应用完成 fence 延伸到 deadline 之后；
- 降低分辨率、关闭 pass 或简化 shader 后，该 GPU 窗口随之缩短；
- 设备计数器或帧 profiler 能解释哪类 GPU 资源受限。

只有“GPU 频率很高”或“RenderThread 很短”不够。异步 API 调用返回快，不表示 GPU 已完成。

### 7.2 怀疑 SurfaceFlinger GPU composition

先查看 FrameTimeline 的 `GPU Composition`、FrameTracer 的 `FALLBACK_COMPOSITION`、RenderEngine slice 和 client target fence。再用 `sfdo force-client-composition` 做受控比较。

不能把 HWC fallback 写成永久状态。CompositionEngine 与 HWC 每帧协商 composition type；Layer 数量、格式、变换、颜色、保护属性、HDR/SDR 混合和硬件 plane 竞争都会影响结果。

### 7.3 怀疑 shader 或 pipeline

Perfetto 的 GPU stage 可以定位较慢的提交窗口，但通常不能还原每个 Vulkan/OpenGL ES draw 的完整 pipeline state。进入 AGI Frame Profiler、Sokatoa、RenderDoc 或厂商 profiler 后，重点检查：

- render pass 和 draw 的耗时分布；
- pipeline/state 切换；
- shader 指令、occupancy 与寄存器压力；
- 纹理格式、采样和带宽；
- attachment load/store 与 resolve；
- overdraw、geometry 和小 draw 数量；
- pipeline cache miss 与运行时 shader/pipeline 编译。

计数器结论要绑定具体 GPU 架构。不能从“ALU busy 高”直接给所有设备同一个优化处方。

### 7.4 怀疑 GPU 内存

`gpu_mem_total` 记录总量变化，不提供对象归属的完整语义，也不表示内存带宽。需要同时检查：

- Vulkan memory tracker 或 API capture 中的 allocation/bind；
- dma-buf heap、进程映射和 gralloc buffer；
- 资源生命周期与场景切换；
- 驱动私有内存统计；
- 内存压力、回收和 allocation failure。

GPU 内存上升可能来自缓存、buffer 数量、分辨率、纹理或驱动内部对象。先用场景与对象证据分解，不能仅凭总量曲线定性为泄漏。

### 7.5 怀疑热限制

ADPF 的 Thermal API 负责热状态与 thermal headroom；Performance Hint Session 负责向系统报告工作线程、目标时长和完成时长。这两类接口不等同于直接控制 GPU 频率。

分析时把温度、thermal headroom、CPU/GPU frequency、帧时间和画质档放在同一时间轴。固定性能模式适合在基准测试中隔离动态频率影响，不代表用户日常运行状态。

### 7.6 怀疑 GPU hang 或 reset

AOSP 与通用 Perfetto 没有覆盖所有 GPU 厂商的统一 reset tracepoint。较可靠的证据组合是：

- GPU fence 长时间不 signal；
- RenderThread、RenderEngine 或 HWC 等待链；
- 内核/驱动 error、hangcheck、fault 或 reset 日志；
- tombstone、Vulkan device-lost 或 GLES error；
- reset 前后的 GPU context、进程和 buffer 状态；
- 同一 API capture 是否能在目标驱动稳定复现。

日志字段和恢复策略属于厂商驱动实现。没有驱动证据时，只能写“疑似 GPU/驱动停滞”，不能从一段空白 GPU track 断言发生 reset。

## 8. 内核与厂商边界

`android17-6.18-2026-06_r6` 包含 Linux devfreq、DRM scheduler、dma-fence 以及开源 DRM GPU 驱动中的频率管理参考实现。这些代码可以解释通用概念：

- devfreq 如何表达设备频率与 governor；
- DRM scheduler 如何管理 GPU job；
- dma-fence 如何表达异步完成依赖；
- DRM GPU 驱动如何把频率和任务状态接到内核基础设施。

量产 Android 设备常使用厂商内核 GPU 驱动和专用用户态驱动。`power/gpu_frequency`、`kgsl/gpu_frequency`、GPU counter producer、hang/reset 事件是否存在，以及字段语义如何，都要在目标设备验证。主线 DRM 路径只能作为参考，不能替代产品内核源码。

## 9. 常见误区

### 误区一：RenderThread 很短，瓶颈一定在 GPU

RenderThread 可能只是异步提交，也可能在别处等待。需要 GPU stage、fence 和 FrameTimeline 共同证明。

### 误区二：GPU 频率高等于 GPU 利用率高

频率是 DVFS 状态。利用率和资源瓶颈需要 activity 或硬件计数器。

### 误区三：`gpu.counters` 在所有 Android 17 设备上都可用

数据源由 GPU producer 和驱动实现。Android 版本相同不代表 counter 名称、ID 和覆盖范围相同。

### 误区四：FrameTimeline 能看到 SurfaceView 主体帧的完整 App 时间线

Perfetto 官方文档仍标注 SurfaceView 不支持完整 App FrameTimeline。独立 Surface 要补 Layer、BufferQueue、fence 和显示侧证据。

### 误区五：`GPU Composition` 表示应用由 GPU 渲染

该字段描述 SurfaceFlinger 的 client composition。应用内容如何生成是另一条路径。

### 误区六：强制 client composition 能直接证明 HWC 有 bug

它只改变了一个关键变量。还需要 composition type、图像差异、fence、HAL/驱动日志和可重复实验。

### 误区七：通用 Perfetto 能解释任意 GPU reset

reset 事件依赖厂商驱动。通用 Trace 主要提供等待链和时间窗口，最终结论需要驱动证据。

## 10. 实战清单

1. 明确用户可见问题和可重复场景。
2. 记录 build、GPU/驱动、分辨率、刷新率、温度与画质。
3. 用 APA/Perfetto 捕获 FrameTimeline、sched、gfx、view、SurfaceFlinger、fence 和设备可用的 GPU 数据源。
4. 找到具体 SurfaceFrame/DisplayFrame，区分 App、SurfaceFlinger GPU、SurfaceFlinger CPU、DisplayHAL 和 buffer stuffing。
5. 对 SurfaceView/独立 Surface 补 Layer、BufferQueue 与 fence。
6. 确认 GPU producer、数据源名称和 counter descriptor，避免解释空轨道。
7. 用分辨率、pass、HWC/client composition 等单变量实验缩小方向。
8. 再选择 AGI、Sokatoa、RenderDoc 或厂商 profiler 做帧级/微架构分析。
9. 优化后在相近热状态重复多轮，并保留原始 Trace、配置和工具版本。
10. 将结论写成“证据 → 推断 → 对照结果”，把设备特有事实与 AOSP 通用机制分开。
