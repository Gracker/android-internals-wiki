# 2.29 Android 17 桌面模式窗口管理性能

Android 17 把桌面窗口扩展为按显示设备配置的系统能力。一台设备可以让内屏保持触控优先，让外接屏进入桌面优先；同一任务还可以在自由窗口、最大化、全屏、分屏以及不同桌面、显示设备之间切换。性能问题由多套状态共同决定，不能只盯应用 `DecorView` 或 SurfaceFlinger。

以下讨论以 Android `android-17.0.0_r1`、API 37 和内核 `android17-6.18-2026-06_r6` 为源码边界。判断窗口性能时，可以按下面的层次定位状态：

```text
显示设备
  └─ 桌面 / TaskDisplayArea
       └─ 任务（窗口模式、边界、Z 序）
            ├─ WM Shell 窗口装饰（标题栏、调整大小手柄、菜单）
            └─ 应用窗口（ViewRootImpl、HWUI、BLAST 缓冲区）

WindowContainerTransaction：任务 / WindowContainer 的高层状态
SurfaceControl.Transaction：控制节点 / 图层的位置、裁剪、层级和可见性
BLAST 缓冲区事务：应用新画面的缓冲区与获取围栏
```

三类事务可以在一次转场中协作，但职责不同。桌面窗口“位置已经动了”只证明某个控制节点或容器的几何更新，不能证明应用已经按新尺寸画出缓冲区；应用已经把缓冲区入队，也不能证明该缓冲区已被目标显示设备选中并展示。

## 1. Android 17 的桌面窗口边界

### 1.1 每个显示设备独立决定桌面状态

Android 17 的 AOSP 发布说明把按显示设备配置桌面窗口列为显示系统变化。官方实现区分两种行为状态：

- 桌面优先（desktop-first）：偏键盘、鼠标和触控板，默认更倾向自由窗口；
- 触控优先（touch-first）：偏触控，默认更倾向全屏。

它们是每个显示设备的状态，不是两套窗口管理系统。状态来源是该显示设备的 `TaskDisplayArea` 窗口模式，Shell 与 Launcher 可从 `DisplayAreaInfo` 或显示设备上下文的 `WindowConfiguration` 读取。

同一设备可能同时出现：

- 内屏触控优先、外接屏桌面优先；
- 内屏与外屏都可承载独立桌面；
- 外屏只镜像内屏，不承载独立任务；
- 不支持桌面窗口，但仍支持普通分屏或画中画。

因此，跟踪分析的第一列必须是 `displayId`。将外屏的 WindowManager 状态与内屏的展示围栏放在一条时间线上，会得到错误归因。

### 1.2 设备支持取决于产品配置

设备要启用桌面窗口，至少要满足多窗口、自由窗口、桌面顶层开关、显示设备资格和非低内存设备等条件。Android 17 常见配置包括：

- `config_supportsMultiWindow`；
- `config_freeformWindowManagement`；
- `config_isDesktopModeSupported`；
- `config_canInternalDisplayHostDesktops`；
- `config_enterDesktopByDefaultOnFreeformDisplay`；
- `config_maxDesktopWindowingActiveTasks`；
- `config_maxDesktopWindowingDesks`。

`config_isDesktopModeSupported` 是总开关。系统界面的桌面体验面向至少 600 dp 宽的显示设备；低内存设备不具备多窗口资格。任务上限或桌面上限为 `0` 时表示不限制，具体产品可以配置其他数值。

“运行 Android 17”不等于“所有设备都提供相同桌面窗口行为”。AOSP 给出框架和配置入口，OEM 仍需决定显示设备能力、任务数量、外接屏策略与 HWC 资源。

### 1.3 以 API 37 为目标版本对大屏应用的影响

应用以 Android 17 / API 37 为目标版本后，在 `sw >= 600dp` 的显示设备上，系统会忽略固定方向、不可调整和宽高比限制，包括：

- `screenOrientation` 的固定横竖屏值；
- `setRequestedOrientation()` 对应固定值；
- `resizeableActivity`；
- `minAspectRatio`；
- `maxAspectRatio`。

游戏、`sw < 600dp` 的屏幕，以及用户在宽高比设置中明确选择应用默认行为的情况属于例外。Android 17 移除了 Android 16 提供的临时开发者退出选项，没有另起一套 SurfaceFlinger 或 BLAST 管线。

这一变化会增加应用遇到边界、方向、Insets 和配置变化的频率。应用状态恢复、资源切换、相机预览变换和自定义动画更容易暴露问题。性能评审应分别评估“平台允许调整大小”和“应用能否低成本、正确地响应尺寸变化”。

## 2. 桌面窗口涉及哪些进程和线程

### 2.1 应用进程

每个顶层应用窗口通常拥有自己的：

- `ViewRootImpl`；
- `ThreadedRenderer` / `CanvasContext`；
- 应用窗口 Surface；
- BLAST / BufferQueue；
- FrameTimeline SurfaceFrame。

同一进程的多个顶层窗口若挂在同一界面 Looper，会共享线程局部的 `Choreographer`，遍历回调在该线程串行运行。它们仍有独立的 ViewRoot 和窗口缓冲区。

硬件加速窗口在同一进程内共享进程级 HWUI RenderThread。窗口 A 的 `DrawFrame`、出队或 GPU 提交拖长，窗口 B 即使自身布局很轻，也可能在 RenderThread 队列中晚启动。

### 2.2 system_server

WindowManager 在 system_server 中维护：

- `RootWindowContainer` / `DisplayContent`；
- `DisplayArea` / `TaskDisplayArea`；
- `Task` / `TaskFragment`；
- `ActivityRecord` / `WindowToken` / `WindowState`；
- 转场收集与 `BLASTSyncEngine` 同步。

这些对象组成窗口管理树。它和 SurfaceFlinger 图层树有映射关系，但节点数量、父子关系不必相同：转场控制节点、特效图层、快照和启动窗口都会改变 Surface 层级。

### 2.3 SystemUI 的 WM Shell

Android 17 的桌面控制器位于：

```text
frameworks/base/libs/WindowManager/Shell/src/com/android/wm/shell/
  desktopmode/
  windowdecor/
  transition/
```

`DesktopTasksController` 生成桌面任务相关 WCT，`DesksOrganizer` 管理任务与桌面的关系，`DesktopModeWindowDecoration` 管理标题栏、菜单、调整大小手柄和输入区域。`Transitions` 把 WCT 交给 WindowOrganizer，并把开始/结束事务、`TransitionInfo.Change` 与控制节点交给具体动画处理器。

这些工作主要运行在 Shell 主线程或其明确的执行器上。Android 17 的这些核心类没有实现动画期间动态扩容线程池的机制。

### 2.4 SurfaceFlinger、HWC 与内核

SurfaceFlinger FrontEnd 接收：

- Shell/WMS 的图层几何与层级事务；
- 各应用窗口的 BLAST 缓冲区事务；
- 系统栏、壁纸、IME、标题栏、变暗层、快照等图层更新。

CompositionEngine 按显示设备构造可见图层集合，HWC 再为整个显示设备选择 `DEVICE` 或 `CLIENT` 合成。窗口多不必然进入 `CLIENT`，单个具有复杂缩放、圆角、透明度、HDR 或受保护属性的窗口也可能改变 HWC 策略。

缓冲区的获取/释放同步最终依赖 dma-fence。固定内核标签中的 `drivers/dma-buf/dma-fence.c` 和 `sync_file.c` 定义通用围栏语义；某台设备的 DPU 平面、GPU、显示驱动与 HWC 能力仍属于厂商实现，不能由通用内核推出固定性能数字。

## 3. 应用 `DecorView` 与 Shell 窗口装饰

桌面标题栏、最大化按钮、菜单和调整大小手柄由 WM Shell 的窗口装饰子系统管理，不是应用 `PhoneWindow` 中的 `DecorView`。

`DesktopModeWindowDecorViewModel` 按任务创建、更新和销毁 `DesktopModeWindowDecoration`。后者在 `relayout()` 中根据：

- 任务边界与窗口模式；
- 显示设备 Insets；
- 焦点、锁屏、沉浸状态；
- 标题栏类型与可定制区域；
- 调整大小/拖动状态；
- 主题、语言区域与字体缩放比例

更新装饰布局、输入区域和装饰 Surface。

### 3.1 Android 17 确有 ViewHost 池

`PooledWindowDecorViewHostSupplier` 按 `displayId` 保存 `SynchronizedPool<WindowDecorViewHost>`，可在 Shell 初始化后预热 `ReusableWindowDecorViewHost`：

```text
acquire()
  有同一显示设备的空闲宿主 -> 复用
  没有 -> 新建 ReusableWindowDecorViewHost

release()
  重置宿主
  池未满 -> 放回同一显示设备的池
  池已满或显示设备已移除 -> 释放 Surface
```

这项优化减少窗口装饰 ViewHost 的重复创建成本。它没有缓存应用 `DecorView` 的测量结果，也没有让多个应用窗口共享 Surface。

可在 Perfetto 中查找 `PooledWindowDecorViewHostSupplier#acquire-newInstance`。频繁出现这个切片，说明池未命中或目标显示设备的池不可用；仍需结合池配置、窗口生命周期与显示设备增删判断。

### 3.2 重新布局如何避免装饰与应用内容撕裂

自由窗口标题栏重新布局时会设置 `applyStartTransactionOnDraw`。源码注释说明，任务裁剪事务要和装饰 View 的缓冲区事务同步显示；分开应用容易产生闪烁。

`DesktopModeWindowDecoration#relayout` 也限制谁能修改任务的可见性、位置和裁剪。一般转场期间由转场处理器控制任务控制节点，避免 `onTaskInfoChanged` 触发的重新布局提前覆盖动画状态；连续调整大小是例外，因为它有意不为每次拖动使用 Shell 转场。

更贴合源码的成本构成是：装饰重新布局、应用配置/遍历、新应用窗口缓冲区和任务控制节点几何可能分别发生，需要用事务流向和图层跟踪判断它们是否在同一显示帧生效。

## 4. 进入桌面与退出桌面

### 4.1 后台任务进入桌面

`DesktopTasksController.moveBackgroundTaskToDesktop()` 为后台任务创建启动 WCT。`ActivityOptions` 指定：

```text
launchWindowingMode = WINDOWING_MODE_FREEFORM
launchBounds = initialBounds
launchDisplayId = targetDisplayId
```

之后由进入桌面的转场处理器或远程转场启动动画。初始边界可能来自记忆位置，也可能由当前显示设备的稳定边界、标题栏 Insets、布局重力和窗口级联规则计算。

### 4.2 已运行任务进入桌面

运行中的任务通过 `addMoveToDeskTaskChanges()` 处理：

1. 计算或继承任务边界；
2. `wct.setBounds(task.token, bounds)`；
3. 由 `DesksOrganizer.moveTaskToDesk()` 更新任务与桌面的容器关系；
4. 产品启用桌面密度覆盖时，再写入任务密度。

若任务原本在分屏中，还要先准备退出分屏。进入桌面也可能伴随桌面激活、主屏/壁纸次序、任务上限导致的最小化和沉浸状态退出。因此，一次 WCT 可以包含多个容器变化，不能把它概括成单个 `setWindowingMode()`。

### 4.3 从桌面进入全屏

`addMoveToFullscreenChanges()` 会按目标 `TaskDisplayArea` 决定显式全屏或继承模式，并执行：

- `setWindowingMode()`；
- 以空 `Rect` 清除显式任务边界；
- 必要时清除应用边界；
- 恢复默认密度；
- 把任务重新挂到目标 `TaskDisplayArea`；
- 跨显示设备时重新排序任务及其父容器；
- 在退出仅剩的桌面任务时清理桌面、壁纸等状态。

进入全屏会改变 WindowContainer 归属和模式。它与桌面内“最大化自由窗口”是两种操作。

## 5. 最大化与还原：自由窗口任务仍可保持自由窗口

`toggleDesktopTaskSize()` 的源码注释把最大化描述为“由稳定边界表示的全屏状态”。这里的状态指视觉尺寸，不等于 `WINDOWING_MODE_FULLSCREEN`。

最大化时：

1. 保存当前自由窗口边界，供还原使用；
2. 计算显示设备稳定区域内的最大化边界；
3. 创建只含目标边界的 WCT；
4. 由 `ToggleResizeDesktopTaskTransitionHandler` 启动专用转场。

还原时优先取出最大化前保存的边界；没有记录才回到默认初始边界。

转场处理器从 `TransitionInfo.Change` 取得任务控制节点、起始边界和结束边界，用 `ValueAnimator<Rect>` 对控制节点逐帧写入：

```text
setPosition(leash, animated.left, animated.top)
setWindowCrop(leash, animated.width, animated.height)
show(leash)
setFrameTimeline(Choreographer.getInstance().getVsyncId())
```

动画开始和结束还会分别设置开始/结束事务。FrameTimeline 的 VSync ID 为事务提供本帧关联，不保证每帧都能命中显示期限。

应用何时收到新边界、何时完成重新布局、何时提交匹配尺寸的缓冲区，仍需结合转场同步与绘制记录判断。动画控制节点可以暂时缩放或裁剪旧内容，避免立即暴露未完成的新布局；应用调整大小的成本依然存在。

源码用 InteractionJankMonitor 记录：

- `CUJ_DESKTOP_MODE_MAXIMIZE_WINDOW`；
- `CUJ_DESKTOP_MODE_UNMAXIMIZE_WINDOW`；
- `CUJ_DESKTOP_MODE_SNAP_RESIZE`。

排查最大化时应以对应 CUJ 的帧为边界，再检查 Shell 动画、应用重新布局/绘制、SurfaceFlinger 合成和展示阶段。

## 6. 拖拽移动与调整大小

### 6.1 只移动位置

连续位置调整器在非缩放拖动中直接用 `SurfaceControl.Transaction` 更新任务 Surface 的位置。这样可以避免每次指针移动都进入 WMS 做边界/配置变更。

移动几何与应用窗口缓冲区分离后，应用可以继续显示原缓冲区，Shell 只改变控制节点/容器位置。若拖动期间出现掉帧，应先检查 Shell 主线程输入与事务、SurfaceFlinger/HWC，再判断是否与应用重新布局有关。

对应源码 CUJ 是 `CUJ_DESKTOP_MODE_DRAG_WINDOW`。

### 6.2 连续调整大小

`FluidResizeTaskPositioner` 在任务边界每次有效变化时：

1. 计算新的任务边界；
2. 第一次变化时通过 WCT 设置 `dragResizing=true`；
3. `wct.setBounds()`；
4. `ShellTaskOrganizer.applyTransaction(wct)`。

拖动结束后再设置 `dragResizing=false`，必要时写入最终边界，并用 `TRANSIT_CHANGE` 转场收尾。最终转场可能因边界已和末次移动相同而被中止，但完成回调仍用于清理状态和结束卡顿监控。

连续调整大小可让内容随窗口连续变化，代价是应用可能频繁收到边界/配置变化、执行遍历并提交新尺寸缓冲区。同一进程内多个窗口还会竞争界面 Looper 和 RenderThread。

### 6.3 遮罩调整大小

`VeiledTaskResizer` 在拖动期间计算边界，但只显示或更新缩放遮罩。结束时才创建：

```text
WindowContainerTransaction()
  .setBounds(task.token, finalBounds)
```

应用内容在拖动期间无需跟随每次指针移动重新布局，最终提交时才处理新尺寸。这通常会减少连续调整大小对应用和 WMS 的压力，但用户看到的是遮罩，不是实时内容。

Android 17 会根据桌面配置、按应用兼容性变更与功能开关选择遮罩或连续调整路径。分析设备跟踪数据前要确认当前任务使用的位置调整器；不能把两条路径的成本模型混用。

对应的调整大小 CUJ 是 `CUJ_DESKTOP_MODE_RESIZE_WINDOW`。源码把拖动/调整大小监控的超时时间设得比默认 CUJ 更长，用于覆盖长手势，与窗口帧预算无关。

## 7. 几何、缓冲区和同步

### 7.1 四种可见组合

调整大小或转场过程中，任务几何和应用窗口缓冲区可能以不同速度到达：

| 几何 | 缓冲区 | 可能的画面 |
|---|---|---|
| 旧 | 旧 | 转场尚未切换 |
| 新 | 旧 | 旧内容被控制节点缩放、裁剪或加黑边 |
| 旧 | 新 | 应用已按新配置画，几何尚未切换；若同步设计不允许，会形成错误帧 |
| 新 | 新 | 新边界与匹配内容一起显示 |

系统也可能使用快照、启动窗口或其他替代图层覆盖应用重绘间隙。允许哪种组合取决于转场处理器、WMS 同步参与者和本轮事务。

### 7.2 WMS 内部同步

`BLASTSyncEngine` 在 system_server 内等待一组 `WindowContainer` 产出 Surface 事务，再把合并结果交给转场或调用方。它只等待注册进同步集合的对象。

应用公开的 `SurfaceSyncGroup` 面向 `AttachedSurfaceControl`、`SurfacePackage` 等场景，和 WMS 内部同步引擎不是同一个 API。相机、编解码器或自研引擎的业务帧如果没有加入受控同步对象，窗口转场不会自动知道其内容时刻。

### 7.3 开始事务与结束事务

Shell `Transitions` 把两份事务交给处理器：

- 开始事务：动画开始前的初始 Surface 状态，处理器应按约定应用；
- 结束事务：动画结束后的最终状态，由转场基础设施在完成时处理。

处理器在动画过程中可以创建额外事务来更新控制节点。若窗口装饰重新布局同时修改同一任务的裁剪或位置，就可能出现抢写和闪烁。因此，Android 17 的装饰源码在非连续调整大小的场景中，把任务控制节点的控制权留给转场处理器。

## 8. Z-order、合成和 GPU

### 8.1 Z 序是容器状态，不等于全屏重绘

任务前置、桌面激活、最小化和跨显示设备移动会产生 WCT `reorder`、重新挂载或组织器操作。WMS/Shell 再把层级变化转成 SurfaceControl 层级事务。

SurfaceFlinger FrontEnd 更新 `RequestedLayerState` 与 `LayerSnapshot`，按目标显示设备构造可见层。Z 序变化不要求所有应用重新绘制；没有新缓冲区的窗口可以继续使用上一块已选缓冲区。

没有通用源码或官方指标支持“窗口数量使合成开销呈二次方增长”，Android 17 也没有所谓的“智能 Z 序缓存”。应检查目标设备上的可见图层集合、遮挡、几何与 HWC 策略。

### 8.2 何时可能增加合成成本

以下状态可能改变 `DEVICE`/`CLIENT` 选择或 RenderEngine 工作：

- 多个窗口的缩放、旋转、透明度、圆角与裁剪；
- 标题栏、变暗层、IME、任务栏、壁纸和转场控制节点；
- HDR/SDR 混合、数据空间与色彩变换；
- 受保护缓冲区与安全显示要求；
- 叠加平面、缩放器和带宽限制；
- 外接屏分辨率、刷新率与色彩模式。

重叠窗口也不必然增加应用过度绘制。每个应用窗口在自己的缓冲区中渲染，跨窗口遮挡由 SurfaceFlinger/HWC 处理；应用内过度绘制和显示合成层数是两个指标。

### 8.3 每个显示设备有自己的展示边界

SurfaceFlinger 为每个显示设备执行合成与展示，并得到对应的展示围栏。外接屏与内屏可以有不同：

- 模式和帧周期；
- HWC 能力；
- 客户端目标；
- 展示围栏；
- VSync 与 FrameTimeline；
- 受保护路径。

同一任务跨屏移动后，不能继续用原显示设备的截止时间或 HWC 结论解释新屏。

## 9. 内存与任务数量

每个独立硬件窗口通常有自己的应用窗口缓冲区周转。标题栏、缩放遮罩、快照、壁纸和转场控制节点也可能对应额外 Surface 或图层。共享进程级 RenderThread 不会合并这些窗口缓冲区。

内存占用取决于：

- 缓冲区宽高、格式和队列中的缓冲区数量；
- HDR、广色域或受保护用途；
- 多个可见/后台任务的 Surface 保留策略；
- 快照、启动窗口、缩放遮罩；
- 应用图片、纹理、RenderNode 和 GPU 资源缓存；
- 厂商 gralloc 压缩与对齐。

无法用“六个窗口固定占 120 MB”描述 Android 17。可以结合 `dumpsys`、SurfaceFlinger 图层/缓冲区信息、Perfetto 图形内存和进程 PSS/GPU 统计按对象计量。

产品可通过 `config_maxDesktopWindowingActiveTasks` 限制活动桌面任务数。它是产品策略，与缓冲区共享无关；设为 `0` 表示不限制任务数量。任务数达到上限时，Shell 可能最小化其他任务，单次启动转场因而会包含额外变化。

## 10. Perfetto 与 Winscope 排查方法

### 10.1 先建立对象表

每个异常窗口至少记录：

| 层级 | 必填信息 |
|---|---|
| 显示设备 | `displayId`、模式、刷新率、分辨率、桌面优先/触控优先 |
| 桌面 / 任务 | 桌面 ID、任务 ID、窗口模式、边界、焦点、Z 序 |
| 应用 | uid/pid、界面线程 tid、RenderThread tid、ViewRoot、目标 SDK |
| Shell | 转场 ID/类型、处理器、CUJ、窗口装饰、连续/遮罩调整大小 |
| SurfaceFlinger | 任务/容器/控制节点/缓冲区图层 ID、父节点、裁剪、透明度、可见性 |
| 缓冲区 | BLAST 名称、帧号、获取/释放围栏 |
| 时间线 | SurfaceFrame、DisplayFrame、展示类型、目标显示设备 |

如果表中缺少 `displayId`、任务控制节点的父节点或应用窗口缓冲区图层，不宜开始归因。

### 10.2 源码已有的跟踪入口

WM Shell 直接写入的区间包括：

- `DesktopModeWindowDecoration#relayout`；
- `DesktopModeWindowDecoration#relayout-startTransition`；
- `DesktopModeWindowDecoration#relayout-applyWCT`；
- `DesktopModeWindowDecoration#relayout-bindData`；
- `PooledWindowDecorViewHostSupplier#acquire-newInstance`；
- `playTransition: <transition type>` 及转场跟踪器。

InteractionJankMonitor 的源码常量带 `CUJ_` 前缀，`Cuj.getNameOfCuj()` 映射到跟踪/统计名称时会去掉该前缀。对应名称是：

- `DESKTOP_MODE_DRAG_WINDOW`；
- `DESKTOP_MODE_RESIZE_WINDOW`；
- `DESKTOP_MODE_MAXIMIZE_WINDOW`；
- `DESKTOP_MODE_UNMAXIMIZE_WINDOW`；
- `DESKTOP_MODE_SNAP_RESIZE`。

InteractionJankMonitor 能标出 CUJ 中发生卡顿的帧，但无法单独给出根因。还需要对齐 Shell、应用、system_server、SurfaceFlinger、GPU 和围栏。

### 10.3 按最早偏离点排查

1. 选择异常 CUJ 和目标 DisplayFrame；
2. 确认输入/指针事件何时到达 Shell；
3. 检查 WCT 创建、WindowOrganizer Binder 调用与转场就绪时刻；
4. 检查任务控制节点的开始/动画/结束事务；
5. 检查应用收到边界/配置变化的时刻；
6. 检查界面遍历、RenderThread 和 BLAST 缓冲区提交；
7. 对齐 SurfaceFlinger 几何与缓冲区各自在第几个 DisplayFrame 生效；
8. 检查 HWC 策略、客户端目标和展示围栏。

最早晚于目标时间的对象，才是当前证据支持的阻塞点。后续切片变长可能只是级联结果。

## 11. 典型问题与判断

### 11.1 调整大小时内容模糊

先确认当前采用连续调整还是遮罩调整。连续调整时，如果任务控制节点已按新边界变化，而应用的新尺寸缓冲区尚未到达，旧缓冲区可能被缩放。此时要检查应用配置/遍历、BLAST 帧尺寸和该帧控制节点的裁剪。

### 11.2 最大化时闪一下

对齐大小切换转场的开始/结束事务、窗口装饰重新布局与应用窗口缓冲区。重点检查是否有非转场路径过早修改任务可见性、位置或裁剪，以及装饰缓冲区是否与任务裁剪同步。

### 11.3 拖动窗口掉帧但应用没有 `doFrame`

位置拖动可以只更新任务 Surface，不要求应用每帧重画。此时应检查 Shell 主线程、输入、SurfaceControl 事务、SurfaceFlinger/HWC 和 GPU；应用没有新缓冲区可能符合设计。

### 11.4 多开窗口后整屏 GPU 升高

比较增加窗口前后的可见图层集合和 HWC 合成类型。标题栏、圆角、透明度、HDR/受保护属性或叠加资源不足，都可能使更多图层进入 `CLIENT` 合成。窗口数量本身不足以证明原因。

### 11.5 外接屏比内屏卡

分别检查两个显示设备的模式、输出图层、HWC 策略与展示围栏。还要确认跨屏后任务密度、边界、资源配置与应用缓冲区尺寸是否改变。

### 11.6 以 API 37 为目标版本后布局频繁重建

确认显示设备的最小宽度、游戏例外和用户宽高比设置，再检查应用是否依赖固定方向或 `resizeableActivity=false`。Android 17 大屏规则会让这些限制失效；问题通常出现在状态保存、资源选择和自定义 View/相机变换。

## 12. 评审清单

1. 设备的桌面总开关、内外屏资格、任务/桌面上限是什么？
2. 目标显示设备是桌面优先还是触控优先？
3. 操作是桌面内最大化，还是切到 `WINDOWING_MODE_FULLSCREEN`？
4. 调整大小使用连续路径还是遮罩位置调整器？
5. 任务的 WMS 父节点与 SurfaceFlinger 控制节点父节点是否都已记录？
6. WCT、SurfaceControl 事务和 BLAST 缓冲区事务分别何时生效？
7. 窗口装饰重新布局是否与转场处理器抢写任务几何？
8. 应用何时收到边界/配置变化，何时提交匹配尺寸的缓冲区？
9. 同进程多个窗口是否在界面 Looper 或 RenderThread 排队？
10. HWC 策略是否因标题栏、IME、HDR、受保护图层或外屏能力改变？
11. 获取、释放、展示围栏是否标明所属缓冲区与显示设备？
12. 目标 SDK、`sw`、游戏类别和用户宽高比设置是否确认？

## 总结

Android 17 桌面窗口性能要按显示设备、任务、Shell 窗口装饰、应用窗口与 SurfaceFlinger 图层分层分析。`DesktopTasksController` 用 WCT 改变边界、容器和窗口模式；转场处理器用控制节点事务实现移动、裁剪和动画；应用通过 ViewRoot/HWUI/BLAST 提交内容；SurfaceFlinger 与 HWC 按显示设备完成合成和展示。

Android 17 的源码优化包括窗口装饰 ViewHost 池、装饰缓冲区与裁剪同步、连续/遮罩调整大小策略，以及带 FrameTimeline 标记的边界动画。它们都有明确适用范围，没有提供固定百分比、固定毫秒目标、跨窗口 Surface 共享或窗口数到合成成本的通用公式。
