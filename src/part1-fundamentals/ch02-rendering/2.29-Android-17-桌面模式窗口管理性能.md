# 2.29 Android 17 桌面模式窗口管理性能

Android 17 把桌面窗口扩展为按 Display 配置的系统能力。一台设备可以让内屏保持 touch-first，让外接屏进入 desktop-first；同一 Task 还可以在 freeform、最大化、fullscreen、split screen 以及不同 desk、Display 之间切换。性能问题由多套状态共同决定，不能只盯 App `DecorView` 或 SurfaceFlinger。

以下讨论以 Android `android-17.0.0_r1`、API 37 和内核 `android17-6.18-2026-06_r6` 为源码边界。判断窗口性能时，可以按下面的层次定位状态：

```text
Display
  └─ Desk / TaskDisplayArea
       └─ Task（windowing mode、bounds、Z-order）
            ├─ WM Shell window decoration（caption、resize handle、menu）
            └─ App Window（ViewRootImpl、HWUI、BLAST buffer）

WindowContainerTransaction：Task / WindowContainer 的高层状态
SurfaceControl.Transaction：leash / layer 的位置、裁剪、层级和可见性
BLAST buffer transaction：应用新画面的 buffer 与 acquire fence
```

三类 transaction 可以在一次转场中协作，但职责不同。桌面窗口“位置已经动了”只证明某个 leash 或 container 的几何更新，不能证明应用已经按新尺寸画出 buffer；应用已经 queue buffer，也不能证明该 buffer 已被目标 Display 选中并 present。

## 1. Android 17 的桌面窗口边界

### 1.1 每个 Display 独立决定桌面状态

Android 17 的 AOSP 发布说明把 per-display desktop windowing 列为 Display 变化。官方实现区分两种行为状态：

- desktop-first：偏键盘、鼠标和触控板，默认更倾向 freeform；
- touch-first：偏触控，默认更倾向 fullscreen。

它们是每个 Display 的状态，不是两套窗口管理系统。状态来源是该 Display 的 `TaskDisplayArea` windowing mode，Shell 与 Launcher 可从 `DisplayAreaInfo` 或 Display context 的 `WindowConfiguration` 读取。

同一设备可能同时出现：

- 内屏 touch-first、外接屏 desktop-first；
- 内屏与外屏都可承载独立 desk；
- 外屏只镜像内屏，不承载独立任务；
- 不支持桌面窗口，但仍支持普通 split screen 或 PiP。

因此，trace 的第一列必须是 `displayId`。将外屏的 WindowManager 状态与内屏的 present fence 放在一条时间线上，会得到错误归因。

### 1.2 设备支持取决于产品配置

设备要启用桌面窗口，至少要满足多窗口、freeform、桌面顶层开关、Display 资格和非 low-RAM 等条件。Android 17 常见配置包括：

- `config_supportsMultiWindow`；
- `config_freeformWindowManagement`；
- `config_isDesktopModeSupported`；
- `config_canInternalDisplayHostDesktops`；
- `config_enterDesktopByDefaultOnFreeformDisplay`；
- `config_maxDesktopWindowingActiveTasks`；
- `config_maxDesktopWindowingDesks`。

`config_isDesktopModeSupported` 是总开关。System UI 的桌面体验面向至少 600 dp 宽的 Display；low-RAM 不具备多窗口资格。任务上限或桌面上限为 `0` 时表示不限制，具体产品可以配置其他数值。

“运行 Android 17”不等于“所有设备都提供相同桌面窗口行为”。AOSP 给出框架和配置入口，OEM 仍需决定 Display 能力、任务数量、外接屏策略与 HWC 资源。

### 1.3 target 37 对大屏应用的影响

应用 target Android 17 / API 37 后，在 `sw >= 600dp` 的 Display 上，系统会忽略固定方向、不可调整和宽高比限制，包括：

- `screenOrientation` 的固定横竖屏值；
- `setRequestedOrientation()` 对应固定值；
- `resizeableActivity`；
- `minAspectRatio`；
- `maxAspectRatio`。

游戏、`sw < 600dp` 的屏幕，以及用户在宽高比设置中明确选择应用默认行为的情况属于例外。Android 17 移除了 Android 16 提供的临时开发者 opt-out，没有另起一套 SurfaceFlinger 或 BLAST 管线。

这一变化会增加应用遇到 bounds、orientation、Insets 和 configuration 变化的频率。应用状态恢复、资源切换、Camera 预览变换和自定义动画更容易暴露问题。性能评审应分别评估“平台允许 resize”和“应用能否低成本、正确地响应 resize”。

## 2. 桌面窗口涉及哪些进程和线程

### 2.1 应用进程

每个顶层 App Window 通常拥有自己的：

- `ViewRootImpl`；
- `ThreadedRenderer` / `CanvasContext`；
- App Window Surface；
- BLAST / BufferQueue；
- FrameTimeline SurfaceFrame。

同一进程的多个顶层窗口若挂在同一 UI Looper，会共享 ThreadLocal `Choreographer`，traversal callback 在该线程串行运行。它们仍有独立的 ViewRoot 和 Window buffer。

硬件加速窗口在同一进程内共享进程级 HWUI RenderThread。Window A 的 `DrawFrame`、dequeue 或 GPU 提交拖长，Window B 即使自身布局很轻，也可能在 RenderThread 队列中晚启动。

### 2.2 system_server

WindowManager 在 system_server 中维护：

- `RootWindowContainer` / `DisplayContent`；
- `DisplayArea` / `TaskDisplayArea`；
- `Task` / `TaskFragment`；
- `ActivityRecord` / `WindowToken` / `WindowState`；
- transition collection 与 `BLASTSyncEngine` 同步。

这些对象组成窗口管理树。它和 SurfaceFlinger layer 树有映射关系，但节点数量、父子关系不必相同：transition leash、effect layer、snapshot 和 starting window 都会改变 Surface 层级。

### 2.3 SystemUI 的 WM Shell

Android 17 的桌面控制器位于：

```text
frameworks/base/libs/WindowManager/Shell/src/com/android/wm/shell/
  desktopmode/
  windowdecor/
  transition/
```

`DesktopTasksController` 生成桌面 Task 相关 WCT，`DesksOrganizer` 管理 Task 与 desk 的关系，`DesktopModeWindowDecoration` 管理 caption、menu、resize handle 和输入区域。`Transitions` 把 WCT 交给 WindowOrganizer，并把 start/finish transaction、`TransitionInfo.Change` 与 leash 交给具体 animation handler。

这些工作主要运行在 Shell 主线程或其明确的 executor 上。Android 17 的这些核心类没有实现动画期间动态扩容线程池的机制。

### 2.4 SurfaceFlinger、HWC 与 kernel

SurfaceFlinger FrontEnd 接收：

- Shell/WMS 的 layer geometry 与 hierarchy transaction；
- 各 App Window 的 BLAST buffer transaction；
- 系统栏、壁纸、IME、caption、dim、snapshot 等 layer 更新。

CompositionEngine 按 Display 构造可见 layer 集合，HWC 再为整个 Display 选择 `DEVICE` 或 `CLIENT` composition。窗口多不必然进入 `CLIENT`，单个具有复杂缩放、圆角、alpha、HDR 或 protected 属性的窗口也可能改变 HWC strategy。

buffer 的 acquire/release 同步最终依赖 dma-fence。固定 kernel tag 中的 `drivers/dma-buf/dma-fence.c` 和 `sync_file.c` 定义通用 fence 语义；某台设备的 DPU plane、GPU、显示驱动与 HWC 能力仍属于 vendor 实现，不能由 common kernel 推出固定性能数字。

## 3. 应用 `DecorView` 与 Shell 窗口装饰

桌面 caption、最大化按钮、菜单和 resize handle 由 WM Shell 的 window decoration 子系统管理，不是应用 `PhoneWindow` 中的 `DecorView`。

`DesktopModeWindowDecorViewModel` 按 Task 创建、更新和销毁 `DesktopModeWindowDecoration`。后者在 `relayout()` 中根据：

- Task bounds 与 windowing mode；
- Display Insets；
- focus、keyguard、immersive 状态；
- caption 类型与可定制区域；
- resize/drag 状态；
- theme、locale 与 font scale

更新装饰布局、输入区域和 decoration surface。

### 3.1 Android 17 确有 ViewHost 池

`PooledWindowDecorViewHostSupplier` 按 `displayId` 保存 `SynchronizedPool<WindowDecorViewHost>`，可在 Shell 初始化后预热 `ReusableWindowDecorViewHost`：

```text
acquire()
  有同一 Display 的空闲宿主 -> 复用
  没有 -> 新建 ReusableWindowDecorViewHost

release()
  重置宿主
  池未满 -> 放回同一 Display 的池
  池已满或 Display 已移除 -> 释放 Surface
```

这项优化减少窗口装饰 ViewHost 的重复创建成本。它没有缓存应用 `DecorView` 的测量结果，也没有让多个 App Window 共享 Surface。

可在 Perfetto 中查找 `PooledWindowDecorViewHostSupplier#acquire-newInstance`。频繁出现这个 slice，说明池未命中或目标 Display 的池不可用；仍需结合池配置、窗口生命周期与 Display 增删判断。

### 3.2 重新布局如何避免装饰与应用内容撕裂

freeform header 的 relayout 会设置 `applyStartTransactionOnDraw`。源码注释说明，task crop transaction 要和装饰 View 的 buffer transaction 同步显示；分开应用容易产生 flicker。

`DesktopModeWindowDecoration#relayout` 也限制谁能修改 task visibility、position 和 crop。一般 transition 期间由 transition handler 控制 task leash，避免 `onTaskInfoChanged` 触发的 relayout 提前覆盖动画状态；fluid resize 是例外，因为它有意不为每次拖动使用 Shell transition。

更贴合源码的成本构成是：装饰 relayout、应用 configuration/traversal、新 App Window buffer 和 task leash geometry 可能分别发生，需要用 transaction flow 和 layer trace 判断它们是否在同一显示帧生效。

## 4. 进入桌面与退出桌面

### 4.1 后台任务进入桌面

`DesktopTasksController.moveBackgroundTaskToDesktop()` 为后台任务创建启动 WCT。`ActivityOptions` 指定：

```text
launchWindowingMode = WINDOWING_MODE_FREEFORM
launchBounds = initialBounds
launchDisplayId = targetDisplayId
```

之后由 enter-desktop transition handler 或 remote transition 启动动画。初始 bounds 可能来自记忆位置，也可能由当前 Display stable bounds、caption Insets、layout gravity 和窗口级联规则计算。

### 4.2 已运行任务进入桌面

运行中的任务通过 `addMoveToDeskTaskChanges()` 处理：

1. 计算或继承 task bounds；
2. `wct.setBounds(task.token, bounds)`；
3. 由 `DesksOrganizer.moveTaskToDesk()` 更新 task 与 desk 的容器关系；
4. 产品启用 desktop density override 时，再写入 task density。

若任务原本在 split screen 中，还要先准备退出 split。进入桌面也可能伴随 desk 激活、home/wallpaper 次序、任务上限导致的最小化和 immersive 状态退出。因此，一次 WCT 可以包含多个容器变化，不能把它概括成单个 `setWindowingMode()`。

### 4.3 从桌面进入 fullscreen

`addMoveToFullscreenChanges()` 会按目标 `TaskDisplayArea` 决定显式 fullscreen 或继承模式，并执行：

- `setWindowingMode()`；
- 以空 `Rect` 清除显式 task bounds；
- 必要时清除 app bounds；
- 恢复默认 density；
- 把 task reparent 到目标 `TaskDisplayArea`；
- 跨 Display 时 reorder task 及其父容器；
- 在退出仅剩的桌面任务时清理桌面、壁纸等状态。

进入 fullscreen 会改变 WindowContainer 归属和模式。它与桌面内“最大化 freeform”是两种操作。

## 5. 最大化与还原：freeform 任务仍可保持 freeform

`toggleDesktopTaskSize()` 的源码注释把最大化描述为“由 stable bounds 表示的 fullscreen state”。这里的 state 指视觉尺寸，不等于 `WINDOWING_MODE_FULLSCREEN`。

最大化时：

1. 保存当前 freeform bounds，供还原使用；
2. 计算 Display stable bounds 内的 maximize bounds；
3. 创建只含目标 bounds 的 WCT；
4. 由 `ToggleResizeDesktopTaskTransitionHandler` 启动专用 transition。

还原时优先取出最大化前保存的 bounds；没有记录才回到默认初始 bounds。

transition handler 从 `TransitionInfo.Change` 取得 task leash、start bounds 和 end bounds，用 `ValueAnimator<Rect>` 对 leash 逐帧写入：

```text
setPosition(leash, animated.left, animated.top)
setWindowCrop(leash, animated.width, animated.height)
show(leash)
setFrameTimeline(Choreographer.getInstance().getVsyncId())
```

动画开始和结束还会分别设置 start/finish transaction。FrameTimeline VSync ID 为 transaction 提供本帧关联，不保证每帧都能命中显示期限。

应用何时收到新 bounds、何时完成 relayout、何时提交匹配尺寸的 buffer，仍需结合 transition sync 与绘制记录判断。动画 leash 可以暂时缩放或裁剪旧内容，避免立即暴露未完成的新布局；应用 resize 的成本依然存在。

源码用 InteractionJankMonitor 记录：

- `CUJ_DESKTOP_MODE_MAXIMIZE_WINDOW`；
- `CUJ_DESKTOP_MODE_UNMAXIMIZE_WINDOW`；
- `CUJ_DESKTOP_MODE_SNAP_RESIZE`。

排查最大化时应以对应 CUJ 的帧为边界，再检查 Shell animation、应用 relayout/draw、SurfaceFlinger composition 和 present。

## 6. 拖拽移动与 resize

### 6.1 只移动位置

fluid positioner 在非 resize 拖动中直接用 `SurfaceControl.Transaction` 更新 task surface 的位置。这样可以避免每次 pointer move 都进入 WMS 做 bounds/configuration 变更。

移动几何与 App Window buffer 分离后，应用可以继续显示原 buffer，Shell 只改变 leash/容器位置。若拖动期间出现掉帧，应先检查 Shell 主线程输入与 transaction、SurfaceFlinger/HWC，再判断是否与应用重新布局有关。

对应源码 CUJ 是 `CUJ_DESKTOP_MODE_DRAG_WINDOW`。

### 6.2 Fluid resize

`FluidResizeTaskPositioner` 在任务 bounds 每次有效变化时：

1. 计算新的任务 bounds；
2. 第一次变化时通过 WCT 设置 `dragResizing=true`；
3. `wct.setBounds()`；
4. `ShellTaskOrganizer.applyTransaction(wct)`。

拖动结束后再设置 `dragResizing=false`，必要时写入最终 bounds，并用 `TRANSIT_CHANGE` transition 收尾。最终 transition 可能因 bounds 已和末次 move 相同而被中止，但 completion callback 仍用于清理状态和结束 jank 监控。

fluid resize 可让内容随窗口连续变化，代价是应用可能频繁收到 bounds/配置变化、执行 traversal 并提交新尺寸 buffer。同一进程内多个窗口还会竞争界面 Looper 和 RenderThread。

### 6.3 Veiled resize

`VeiledTaskResizer` 在拖动期间计算 bounds，但只显示或更新 resize veil。结束时才创建：

```text
WindowContainerTransaction()
  .setBounds(task.token, finalBounds)
```

应用内容在拖动期间无需跟随每次 pointer move 重新布局，最终提交时才处理新尺寸。这通常会减少连续 resize 对应用和 WMS 的压力，但用户看到的是 veil，不是实时内容。

Android 17 会根据 desktop 配置、per-app compat change 与 feature flag 选择 veiled 或 fluid 路径。分析设备 trace 前要确认当前 task 使用的 positioner；不能把两条路径的成本模型混用。

对应的调整大小 CUJ 是 `CUJ_DESKTOP_MODE_RESIZE_WINDOW`。源码把拖动/调整大小监控的超时时间设得比默认 CUJ 更长，用于覆盖长手势，与窗口帧预算无关。

## 7. 几何、buffer 和同步

### 7.1 四种可见组合

调整大小或 transition 过程中，任务几何和 App Window buffer 可能以不同速度到达：

| 几何 | buffer | 可能的画面 |
|---|---|---|
| 旧 | 旧 | 转场尚未切换 |
| 新 | 旧 | 旧内容被 leash 缩放、裁剪或加黑边 |
| 旧 | 新 | 应用已按新配置画，几何尚未切换；若同步设计不允许，会形成错误帧 |
| 新 | 新 | 新 bounds 与匹配内容一起显示 |

系统也可能使用 snapshot、starting window 或其他替代 layer 覆盖应用重绘间隙。允许哪种组合取决于 transition 处理器、WMS 同步参与者和本轮 transaction。

### 7.2 WMS 内部 sync

`BLASTSyncEngine` 在 system_server 内等待一组 `WindowContainer` 产出 surface transaction，再把合并结果交给 transition 或调用方。它只等待注册进 sync set 的对象。

应用公开的 `SurfaceSyncGroup` 面向 `AttachedSurfaceControl`、`SurfacePackage` 等场景，和 WMS 内部 sync engine 不是同一个 API。Camera、codec 或自研引擎的业务帧如果没有加入受控同步对象，窗口 transition 不会自动知道其内容时刻。

### 7.3 start transaction 与 finish transaction

Shell `Transitions` 把两份事务交给 handler：

- start transaction：动画开始前的初始 surface 状态，handler 应按约定应用；
- finish transaction：动画结束后的最终状态，由 transition 基础设施在完成时处理。

handler 在动画过程中可以创建额外 transaction 来更新 leash。若 window decoration relayout 同时修改同一 task crop/position，就可能出现抢写和闪烁。因此，Android 17 的装饰源码在非 fluid resize 场景中，把 task leash 的控制权留给 transition handler。

## 8. Z-order、合成和 GPU

### 8.1 Z-order 是容器状态，不等于全屏重绘

task 前置、desk 激活、最小化和跨 Display 移动会产生 WCT `reorder`、reparent 或 organizer 操作。WMS/Shell 再把层级变化转成 SurfaceControl hierarchy transaction。

SurfaceFlinger FrontEnd 更新 `RequestedLayerState` 与 `LayerSnapshot`，按目标 Display 构造可见层。Z-order 变化不要求所有应用重新绘制；没有新 buffer 的窗口可以继续使用上一块已选 buffer。

没有通用源码或官方指标支持“窗口数量使合成开销呈二次方增长”，Android 17 也没有所谓的“智能 Z-order 缓存”。应检查目标设备上的可见 layer 集合、遮挡、几何与 HWC 策略。

### 8.2 何时可能增加合成成本

以下状态可能改变 DEVICE/CLIENT 选择或 RenderEngine 工作：

- 多个窗口的缩放、旋转、alpha、圆角与 crop；
- caption、dim、IME、taskbar、壁纸和 transition leash；
- HDR/SDR 混合、dataspace 与色彩变换；
- protected buffer 与安全 Display 要求；
- overlay plane、缩放器和带宽限制；
- 外接屏分辨率、刷新率与 color mode。

重叠窗口也不必然增加应用 overdraw。每个 App Window 在自己的 buffer 中渲染，跨窗口遮挡由 SurfaceFlinger/HWC 处理；应用内 overdraw 和 Display 合成层数是两个指标。

### 8.3 每个 Display 有自己的 present 边界

SurfaceFlinger 为每个 Display 执行 composition/present，并得到该 Display 的 present fence。外接屏与内屏可以有不同：

- mode 和帧周期；
- HWC 能力；
- client target；
- present fence；
- VSync 与 FrameTimeline；
- protected path。

同一任务跨屏移动后，不能继续用原 Display 的 deadline 或 HWC 结论解释新屏。

## 9. 内存与任务数量

每个独立硬件窗口通常有自己的 App Window buffer 周转。caption、缩放遮罩、snapshot、壁纸和 transition leash 也可能对应额外 Surface 或 layer。共享进程级 RenderThread 不会合并这些窗口 buffer。

内存占用取决于：

- buffer 宽高、格式和队列中的 buffer 数量；
- HDR、广色域或受保护用途；
- 多个可见/后台任务的 Surface 保留策略；
- snapshot、starting window、缩放遮罩；
- 应用图片、纹理、RenderNode 和 GPU 资源缓存；
- vendor gralloc 压缩与对齐。

无法用“六个窗口固定占 120 MB”描述 Android 17。可以结合 `dumpsys`、SurfaceFlinger layer/buffer 信息、Perfetto 图形内存和进程 PSS/GPU 统计按对象计量。

产品可通过 `config_maxDesktopWindowingActiveTasks` 限制活动桌面任务数。它是产品策略，与 buffer 共享无关；设为 `0` 表示不限制任务数量。任务数达到上限时，Shell 可能最小化其他任务，单次启动 transition 因而会包含额外变化。

## 10. Perfetto 与 Winscope 排查方法

### 10.1 先建立对象表

每个异常窗口至少记录：

| 层级 | 必填信息 |
|---|---|
| Display | `displayId`、mode、刷新率、分辨率、desktop-first/touch-first |
| Desk / Task | desk id、task id、windowing mode、bounds、focus、Z-order |
| App | uid/pid、UI tid、RenderThread tid、ViewRoot、target SDK |
| Shell | transition id/type、handler、CUJ、window decoration、fluid/veiled resize |
| SF | task/container/leash/buffer layer id、parent、crop、alpha、visibility |
| Buffer | BLAST 名称、frame number、acquire/release fence |
| Timeline | SurfaceFrame、DisplayFrame、present type、目标 Display |

如果表中缺少 `displayId`、task leash 的父节点或 App Window buffer layer，不宜开始归因。

### 10.2 源码已有的 trace 入口

WM Shell 直接写入的 section 包括：

- `DesktopModeWindowDecoration#relayout`；
- `DesktopModeWindowDecoration#relayout-startTransition`；
- `DesktopModeWindowDecoration#relayout-applyWCT`；
- `DesktopModeWindowDecoration#relayout-bindData`；
- `PooledWindowDecorViewHostSupplier#acquire-newInstance`；
- `playTransition: <transition type>` 及 transition tracer。

InteractionJankMonitor 的源码常量带 `CUJ_` 前缀，`Cuj.getNameOfCuj()` 映射到跟踪/统计名称时会去掉该前缀。对应名称是：

- `DESKTOP_MODE_DRAG_WINDOW`；
- `DESKTOP_MODE_RESIZE_WINDOW`；
- `DESKTOP_MODE_MAXIMIZE_WINDOW`；
- `DESKTOP_MODE_UNMAXIMIZE_WINDOW`；
- `DESKTOP_MODE_SNAP_RESIZE`。

InteractionJankMonitor 能标出 CUJ 中发生卡顿的帧，但无法单独给出根因。还需要对齐 Shell、应用、system_server、SurfaceFlinger、GPU 和 fence。

### 10.3 按最早偏离点排查

1. 选择异常 CUJ 和目标 DisplayFrame；
2. 确认输入/指针事件何时到达 Shell；
3. 检查 WCT 创建、WindowOrganizer Binder 调用与 transition ready；
4. 检查 task leash 的 start/animation/finish transaction；
5. 检查应用收到 bounds/配置变化的时刻；
6. 检查界面 traversal、RenderThread 和 BLAST buffer 提交；
7. 对齐 SurfaceFlinger 几何与 buffer 各自在第几个 DisplayFrame 生效；
8. 检查 HWC strategy、client target 和 present fence。

最早晚于目标时间的对象，才是当前证据支持的阻塞点。后续 slice 变长可能只是级联结果。

## 11. 典型问题与判断

### 11.1 调整大小时内容模糊

先确认当前采用 fluid 还是 veiled。fluid resize 时，如果 task leash 已按新 bounds 变化，而应用的新尺寸 buffer 尚未到达，旧 buffer 可能被缩放。此时要检查应用 configuration/traversal、BLAST frame size 和该帧 leash crop。

### 11.2 最大化时闪一下

对齐 toggle-resize transition 的 start/finish transaction、window decoration relayout 与 App Window buffer。重点检查是否有非 transition 路径过早修改 task visibility/position/crop，以及装饰 buffer 是否与 task crop 同步。

### 11.3 拖动窗口掉帧但应用没有 `doFrame`

位置拖动可以只更新任务 Surface，不要求应用每帧重画。此时应检查 Shell 主线程、输入、SurfaceControl transaction、SurfaceFlinger/HWC 和 GPU；应用没有新 buffer 可能符合设计。

### 11.4 多开窗口后整屏 GPU 升高

比较增加窗口前后的可见 layer 集合和 HWC composition type。caption、圆角、alpha、HDR/protected 属性或 overlay 资源不足，都可能使更多 layer 进入 CLIENT composition。窗口数量本身不足以证明原因。

### 11.5 外接屏比内屏卡

分别检查两个 Display 的 mode、Output layer、HWC strategy 与 present fence。还要确认跨屏后 task density、bounds、资源 configuration 与应用 buffer 尺寸是否改变。

### 11.6 以 API 37 为目标版本后布局频繁重建

确认 Display 的最小宽度、游戏例外和用户宽高比设置，再检查应用是否依赖固定方向或 `resizeableActivity=false`。Android 17 大屏规则会让这些限制失效；问题通常出现在状态保存、资源选择和自定义 View/相机变换。

## 12. 评审清单

1. 设备的桌面总开关、内外屏资格、任务/桌面上限是什么？
2. 目标 Display 是 desktop-first 还是 touch-first？
3. 操作是桌面内最大化，还是切到 `WINDOWING_MODE_FULLSCREEN`？
4. resize 使用 fluid 还是 veiled positioner？
5. task 的 WMS parent 与 SF leash parent 是否都已记录？
6. WCT、SurfaceControl transaction 和 BLAST buffer transaction 分别何时生效？
7. window decoration relayout 是否与 transition handler 抢写 task geometry？
8. 应用何时收到 bounds/配置变化，何时提交匹配尺寸的 buffer？
9. 同进程多个窗口是否在 UI Looper 或 RenderThread 排队？
10. HWC strategy 是否因 caption、IME、HDR、protected layer 或外屏能力改变？
11. acquire、release、present fence 是否标明所属 buffer 与 Display？
12. target SDK、`sw`、game category 和用户宽高比设置是否确认？

## 总结

Android 17 桌面窗口性能要按 Display、Task、Shell decoration、App Window 与 SF layer 分层分析。`DesktopTasksController` 用 WCT 改变 bounds、容器和 windowing mode；transition handler 用 leash transaction 实现移动、裁剪和动画；应用通过 ViewRoot/HWUI/BLAST 提交内容；SurfaceFlinger 与 HWC 按 Display 完成 composition 和 present。

Android 17 的源码优化包括窗口装饰 ViewHost 池、装饰 buffer 与 crop 同步、fluid/veiled resize 策略，以及带 FrameTimeline 标记的 bounds 动画。它们都有明确适用范围，没有提供固定百分比、固定毫秒目标、跨窗口 Surface 共享或窗口数到合成成本的通用公式。
