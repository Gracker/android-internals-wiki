# 2.31 Camera HAL3 Buffer 管理与 BufferQueue 协作的内存模型

Camera HAL3 不维护覆盖预览、录像、分析和拍照的公共 GraphicBuffer 池。Camera2 会配置若干输出 `Surface`，camera service 为每个输出建立流；每个流再通过自己的队列与 Surface 后面的 consumer 协作。HAL 在这条链路中负责生产图像，而 GraphicBuffer 的分配、缓存、跨进程传递和回收由框架、图形分配器、BufferQueue、HAL 与 consumer 共同完成。

以下讨论以 Android 17 / API 37 / `android-17.0.0_r1` 和内核 `android17-6.18-2026-06_r6` 为源码边界。分析缓冲区所有权时，应把握四条规则：

1. `HalStream.maxBuffers` 限制 HAL 同时持有的 in-flight buffer 数量，不是应用层的缓存配置；
2. `dequeueBuffer()` 返回的 fence 会作为 Camera HAL 的 acquire fence，HAL 返回的 release fence 又会成为下游 consumer 读取该 buffer 前要等待的 fence；
3. HAL buffer management 只把“提交 request”和“取得 output buffer”解耦，buffer 仍来自对应输出 Surface；
4. 预览正常不代表录像或 ImageReader 正常，多输出必须按 stream 分别检查。

## 1. 从 request-result 模型理解 buffer

### 1.1 一个 request 可以有多个输出

App 创建 `CameraCaptureSession` 时，把预览、录像、图像分析、JPEG、RAW 等 `Surface` 交给 Camera2。`Camera3Device::RequestThread` 把设置、frame number 和目标流送入 HAL。HAL 完成 sensor、ISP 与后处理后，通过 `processCaptureResult()` 异步返回 metadata 和 output buffer。

下面的结构图用于区分控制流、像素流和各路 consumer：

```text
Camera2 / CameraX
  └─ CameraCaptureSession
       └─ Camera3Device / RequestThread
            └─ Camera HAL3
                 ├─ preview stream  ─→ SurfaceView / SurfaceTexture
                 ├─ record stream   ─→ MediaCodec
                 ├─ analysis stream ─→ ImageReader
                 └─ still stream    ─→ JPEG / HEIC / RAW consumer
```

同一个帧号的 metadata 和各路 buffer 可以分批返回。预览 buffer 已经进入 BufferQueue，只能说明预览输出有了进展；它不能证明 analysis buffer 已被应用关闭，也不能证明录像 encoder 已消费同帧。

### 1.2 每个输出流都有自己的队列边界

`Camera3OutputStream` 持有目标 `Surface`，并以 `NATIVE_WINDOW_API_CAMERA` 连接 producer 端。Surface 后面的 consumer 决定 buffer 的用途：

| 输出目标 | Camera buffer 的直接 consumer | 是否直接形成可见图层 |
|---|---|---|
| `SurfaceView` | SurfaceFlinger 一侧的 Surface consumer | 通常是独立 child layer |
| `TextureView` | App 进程中的 `SurfaceTexture` | 否，宿主 HWUI 再画进 App Window |
| `ImageReader` | ImageReader / App | 否 |
| MediaCodec input Surface | encoder | 否 |
| 自研 GL / Vulkan 输入 | App GPU renderer | 输入本身不直接上屏，renderer 还要生产第二条可见输出 |

所以，“HAL 是 producer、SurfaceFlinger 是 consumer”只适用于部分预览拓扑。TextureView、ImageReader、encoder 与自研渲染器都有不同的直接 consumer。

## 2. `configureStreams()` 决定什么

Camera service 把宽高、格式、dataspace、旋转、consumer usage 等信息交给 HAL。Android 17 的 AIDL HAL 通过 `HalStream` 返回以下关键结果：

- `overrideFormat`：`IMPLEMENTATION_DEFINED` 输出可由 HAL 选择实际格式；
- `producerUsage`：output stream 上 HAL 所需的 gralloc usage；
- `consumerUsage`：input stream 上 HAL 所需的用途；
- `maxBuffers`：HAL 同时可能持有的最大 buffer 数量；
- `overrideDataSpace`：允许覆盖的 dataspace；
- `enableHalBufferManager`：在 session-configurable 模式下，决定该流是否由 HAL 按需请求 buffer。

framework 会把 producer 与 consumer 的用途合并后交给图形分配器。对于 `IMPLEMENTATION_DEFINED`，最终布局可能依赖相机写入端和显示、GPU、codec 等读取端的组合要求，不能只根据公开 pixel format 推断步幅、plane offset 或压缩方式。

### 2.1 `maxBuffers` 与队列总量

Android 17 的 `Camera3OutputStream::configureConsumerQueueLocked()` 会查询 consumer 要求保留的最小 undequeued buffer 数量，再计算：

```text
mTotalBufferCount =
    NATIVE_WINDOW_MIN_UNDEQUEUED_BUFFERS
    + camera_stream::max_buffers
```

这个值描述该输出 Surface 的基础队列容量。consumer 必须留有自己正在读取或显示的 buffer，HAL 也必须有空间推进 pipeline。`Camera3Stream::getBuffer()` 还会检查 HAL 已取走的 buffer 数量；达到 `max_buffers` 时，它会等待 buffer 返回，并记录 `wait on max_buffers` 延迟直方图。

不能直接增大 `maxBuffers` 来掩盖 consumer 慢。增加它可能让 pipeline 暂时不阻塞，也会增加该流可同时驻留的图像内存。这个字段由 HAL 根据 pipeline 需求声明，错误的数值还可能破坏框架与 HAL 的流控约定。

### 2.2 framework 内部 BufferManager 与 HAL buffer management 不同

源码里还能看到 `Camera3BufferManager`。它属于 camera service 内部，可让兼容流复用框架管理的 GraphicBuffer，并通过 `attachBuffer()` 接回具体 BufferQueue。启用后，`Camera3OutputStream` 会禁止对应 BufferQueue 自行分配。

HAL buffer-management API 则是 HAL 通过 `requestStreamBuffers()` 向 camera service 取 buffer。两套机制可以出现在同一条调用路径中，但调用者、接口边界和目标都不同：

| 名称 | 所在侧 | 主要作用 |
|---|---|---|
| `Camera3BufferManager` | camera service 内部 | 在框架管理的兼容流之间调度 GraphicBuffer |
| HAL buffer management | Camera HAL ↔ camera service | 把 capture request 提交与 output buffer 获取分开 |

排查日志或源码时要先确认说的是哪一个 BufferManager。

## 3. framework 管理 buffer 时的一帧生命周期

没有为某个输出启用 HAL 缓冲区管理时，`RequestThread` 会在调用 HAL 前为该请求取得 output buffer。

### 3.1 framework 从 Surface 取得可写 buffer

`Camera3OutputStream::getBufferLockedCommon()` 最终调用 `ANativeWindow::dequeueBuffer()`。成功后得到：

- 一个 `ANativeWindowBuffer`，其句柄指向 GraphicBuffer；
- 一个 fence fd，表示该 buffer 何时结束上一次 consumer 使用。

`Camera3OutputStream::getBufferLocked()` 把围栏填入 `camera_stream_buffer.acquire_fence`，再把 buffer 交给 HAL。源码注释明确写明，此后 fence fd 由 HAL 持有。

### 3.2 HAL 等待 acquire fence 后写图像

HAL 在读写 buffer 前必须等待 acquire fence。对 output stream 来说，这一步保护 HAL，避免它覆盖 GPU、SurfaceFlinger、encoder 或应用仍在读取的旧内容。

如果 acquire fence 为空，表示无需等待。若 HAL 因错误没有等待该围栏，AIDL `StreamBuffer` 约定要求 HAL 把原 acquire fence 作为 release fence 退回，让框架在复用前仍能等待正确的完成点。

### 3.3 HAL 用 release fence 归还写入结果

HAL 通过 `processCaptureResult()` 返回：

- stream 与 buffer 标识；
- `BufferStatus.OK` 或 `ERROR`；
- release fence，表示 HAL 何时停止访问该 buffer。

release fence 为空表示在调用 `processCaptureResult()` 时已经完成所有访问。若围栏有效，HAL 可以先返回结果，由下游异步等待。fence signal 之后，HAL 不得再次访问该 buffer。

### 3.4 CameraService 入队或取消

`Camera3OutputStream::returnBufferCheckedLocked()` 总会接收 HAL 的 release fence：

- buffer 正常且 timestamp 有效时，调用 `queueBuffer()` 交给 Surface consumer；
- buffer 为错误、stream 正在丢帧或 timestamp 为 0 时，调用 `cancelBuffer()`；
- 两条路径都会带上 HAL release fence，保证下游或队列在 HAL 停止访问后再处理该 buffer。

正常入队后，BufferQueue 中的围栏从 consumer 视角又叫 acquire fence：consumer 要等它 signal 才能读取新图像。这是同一个同步对象跨接口后的命名变化，并未额外生成相机围栏。

### 3.5 consumer 释放后才能再次出队

consumer 用完 buffer 后把 release fence 交回 BufferQueue。下一轮 producer `dequeueBuffer()` 取得该槽位时，会拿到描述 consumer 完成时间的围栏。CameraService 再把它放进 HAL 的 acquire fence 字段，生命周期由此进入下一轮。

完整顺序可以写成：

```text
消费者释放围栏
        ↓
BufferQueue dequeueBuffer()
        ↓
HAL acquire fence → HAL wait/write
        ↓
HAL release fence
        ↓
BufferQueue queueBuffer()
        ↓
consumer acquire/wait/read
```

判断围栏方向时，要同时写出“谁准备读或写”和“谁已经结束访问”。只记获取、`release` 两个名字，很容易在 HAL 接口与 BufferQueue 接口之间说反。

## 4. Android 17 的 HAL 缓冲区管理路径

Android 10 引入可选的 HAL3 buffer-management API。HAL 处理管线可以同时排队 N 个请求，却可能只在靠近输出的阶段需要少量 buffer。如果框架在 request 入 HAL 前就为所有输出取齐 buffer，会让暂时用不到的图像内存长期驻留。

Android 17 同时保留两类行为：

- 未启用的 stream：framework 仍随 request 提供真实 output buffer；
- 已启用的流：request 中只有流的占位信息，`buffer` 为空，HAL 稍后调用 `requestStreamBuffers()`。

在 `SESSION_CONFIGURABLE` 模式下，HAL 可以通过 `HalStream.enableHalBufferManager` 按流选择；在 AIDL 设备级模式下，framework 会把全部 output stream 视为 HAL 管理。

### 4.1 `requestStreamBuffers()` 取得的 buffer 不绑定特定帧

Android 17 的 `AidlCamera3OutputUtils.cpp` 明确说明：一次 `requestStreamBuffers()` 返回的 buffer 不与某个 `CaptureRequest` 预先绑定。HAL 可以：

1. 为多个流批量请求若干 buffer；
2. 选择其中一个用于某帧；
3. 把已使用的 buffer 随该帧的 `processCaptureResult()` 返回；
4. 把多取但未使用的 buffer 经 `returnStreamBuffers()` 退回。

CameraService 会逐个流检查：

- stream 是否存在且启用了 HAL buffer management；
- 是否重复请求同一个流 ID；
- Surface 是否已断开；
- `当前 outstanding + 本次请求数` 是否超过 `maxBuffers`；
- 当前是否正在 `configureStreams()`。

可能的结果包括 `STREAM_DISCONNECTED`、`NO_BUFFER_AVAILABLE`、`MAX_BUFFER_EXCEEDED` 与 `FAILED_CONFIGURING`。`requestStreamBuffers()` 是同步调用，AIDL 注释建议 HAL 使用专用线程，并避免在延迟敏感路径一次请求大量 buffer。

### 4.2 `bufferId` 与句柄缓存

跨 Binder 每帧重复传 native handle 会增加开销。Android 17 的 `StreamBuffer` 采用 `streamId + bufferId` 建立缓存约定：

- 某个 buffer 第一次交给 HAL 时，同时带 `bufferId` 和 native handle；
- HAL 记住两者的映射；
- 同一个 buffer 后续再次出现时，只传 `bufferId`，handle 为空；
- `CaptureResult` 返回时句柄也为空，framework 用帧、stream 和 buffer 记录找回原对象；
- `processCaptureRequest(..., cachesToRemove)` 要求 HAL 删除已经失效的缓存项。

stream 被移除、session 关闭或框架通知 cache removal 后，HAL 不能继续使用旧映射。把 `bufferId` 当作跨会话稳定句柄，会造成释放后使用、错配或设备错误。

### 4.3 `returnStreamBuffers()` 只归还未用于结果的 buffer

HAL 已把 buffer 用于某帧时，应随 `processCaptureResult()` 返回。多取、预取后未使用的 buffer 才走 `returnStreamBuffers()`。CameraService 找回对应 in-flight buffer 后，以错误状态和时间戳 0 交还输出流，最终走 `cancelBuffer()`，不会把它当成一帧有效图像送给 consumer。

### 4.4 `signalStreamFlush()` 与 `flush()` 的区别

两个接口都会促使 buffer 返回，但语义不同：

| 接口 | 目的 | pending request 的处理 |
|---|---|---|
| `signalStreamFlush()` | 为流重配置回收 HAL 手中的 buffer | HAL 应正常完成已有请求，并及时归还指定流的 buffer |
| `flush()` | 尽快清空整个 capture pipeline | 允许把未完成 buffer 标为 `ERROR`，返回时不得再有 outstanding request 或 buffer |

`signalStreamFlush()` 是异步提示，`streamConfigCounter` 用于识别它是否晚于对应的 `configureStreams()` 到达。HAL 不能只按 Binder 到达顺序判断配置代次。

## 5. 三组围栏不能混为一谈

Camera 预览上屏时，至少要区分下面三组同步：

| 同步边界 | 完成了什么 | 常见等待方 |
|---|---|---|
| framework → HAL acquire fence | 上一个 consumer 已停止使用 output buffer | Camera HAL / ISP |
| HAL → consumer release fence | sensor / ISP / HAL 已完成当前图像写入 | BufferQueue consumer、ImageReader、codec、App GPU |
| SurfaceFlinger / HWC 释放与 present fence | display 是否停止读取 layer buffer，以及 display frame 何时展示 | BufferQueue producer、显示性能分析工具 |

display present fence 不能证明 camera output 已完成；analysis 或 JPEG 缓冲区也可能从未进入显示系统。反过来，HAL 释放围栏已 signal 只能证明 camera producer 完成写入，不表示 SurfaceFlinger 已锁存，更不表示面板已经展示。

kernel `android17-6.18-2026-06_r6` 中，`dma_fence` 表示异步工作完成点，`sync_file` 负责把一个或多个围栏暴露成 fd。Camera AIDL 传递的是 native handle 中的围栏文件描述符；厂商 ISP、GPU、codec 和显示驱动怎样创建围栏并发出信号，要回到对应设备的驱动和 HAL 源码核对。

## 6. 多输出的内存与背压

### 6.1 每路输出单独计算，整组会话共同受限

粗略估算相机图像内存时，应按流求和：

```text
session GraphicBuffer 驻留量
  ≈ Σ（该流已分配 buffer 数 × allocator 返回的单 buffer 大小）
```

这只是排查起点。单 buffer 大小还受步幅、plane 对齐、压缩元数据、保护属性、tile 布局与 vendor allocator 影响；HAL、ISP firmware、GPU 和 codec 的内部工作 buffer 也不一定出现在 CameraService 的流统计中。

常见未压缩载荷可以用来检查数量级：

| 格式 | 可见像素载荷的粗略量级 | 注意事项 |
|---|---:|---|
| RGBA_8888 | `width × height × 4` | stride 与压缩会改变物理分配 |
| YUV 4:2:0 | `width × height × 1.5` | plane stride、slice height 不能省略 |
| RAW10 | `width × height × 1.25` | 行打包与对齐由实现决定 |
| RAW12 | `width × height × 1.5` | 同上 |
| RAW14 | `width × height × 1.75` | Android 17 能力仍要查设备特征 |

`IMPLEMENTATION_DEFINED` 不能套用固定的 bytes-per-pixel。BLOB stream 还要使用配置中的 `bufferSize` 边界，不能把 JPEG 文件大小当作 GraphicBuffer 的分配大小。

### 6.2 慢 consumer 怎样形成背压

每路输出有独立队列，但一次 capture request 可以同时要求多个输出。下面几种情况都会让 buffer 回收变慢：

- `ImageReader` 取得 `Image` 后没有及时 `close()`；
- CameraX `ImageProxy` 未关闭；
- encoder 输入拥塞；
- TextureView 所在应用长时间不绘制或不消费 `SurfaceTexture`；
- Surface 被销毁或弃用；
- 自研 GL / Vulkan 渲染器长时间持有输入 `AHardwareBuffer`；
- SurfaceFlinger 或 HWC 长时间占用预览 buffer。

framework 管理 buffer 时，只要某个目标流达到 HAL 可持有上限，RequestThread 就可能在取得该路 buffer 时等待。HAL 缓冲区管理模式把请求提交提前了，HAL 则必须自行控制 pipeline 深度，并处理 `requestStreamBuffers()` 暂时拿不到 buffer 的情况。

多路是否互相拖慢还取决于 vendor pipeline。设备可能共享 sensor readout、ISP stage、缩放器、带宽或内部 pool。看到 analysis 积压后预览也掉帧时，只能先把分析流列为候选原因；还要用帧号、各路结果时间与 buffer 归还记录证明因果关系。

### 6.3 App 侧最重要的归还动作

以下示例用于展示 ImageReader 消费者的最小资源边界：

```kotlin
imageReader.setOnImageAvailableListener({ reader ->
    val image = reader.acquireLatestImage() ?: return@setOnImageAvailableListener
    try {
        analyze(image)
    } finally {
        image.close()
    }
}, analysisHandler)
```

`acquireLatestImage()` 适合只关心新数据的分析任务，它可以丢弃较旧图像；`image.close()` 才把当前 buffer 归还队列。若业务要求逐帧处理，可改用 `acquireNextImage()`，但处理能力必须跟得上输入速率，并把 `maxImages` 视为并发持有上限。

## 7. 16KB 页面大小与 ION：纠正常见误解

### 7.1 16KB 页面大小并非 Android 17 首次引入

AOSP 从 Android 15 起支持 16KB page size。它主要改变内核页粒度、`mmap()` 取整、ELF 对齐以及依赖固定 `PAGE_SIZE` 的原生代码。Android 17 继续处在这条兼容线上。

Camera AIDL、`GraphicBuffer` 和 BufferQueue 没有规定：

- 每个 camera buffer 的逻辑宽高必须按 16KB 对齐；
- 图像载荷大小必须是 16KB 的整数倍；
- App 或 Camera HAL 应手工把 gralloc 分配结果补齐到 16KB。

物理页、IOMMU 映射、plane stride、heap 粒度和硬件块对齐属于不同层次。allocator 与驱动可以因 16KB 内核产生不同的物理占用，但不能由此推出统一的 Camera HAL 缓冲区对齐公式。排查时应读取 mapper 返回的布局、dma-buf 大小和设备堆配置。

### 7.2 Android 17 不再支持 ION

Android 17 AOSP 发布说明要求删除 vendor 中的 ION 调用。Android 12 的 GKI 2.0 已用 DMA-BUF 堆取代 ION；到 Android 17，所有支持 ION 的内核都已结束维护。

Android 17 Android 17 camera 路径涉及以下对象：

- gralloc / graphics allocator 决定 GraphicBuffer 的实现与布局；
- DMA-BUF 堆或 vendor allocator 提供可共享分配；
- dma-buf fd 让 HAL、GPU、codec、HWC 等设备共享同一分配；
- dma-fence / sync_file fd 传递访问完成关系。

`ashmem` 也不是 Android 17 camera GraphicBuffer 的可选“内存类型”。它解决普通共享内存问题，不提供 Camera HAL 图形流所需的 gralloc metadata、usage 协商和设备导入语义。

## 8. SurfaceView、TextureView 与自研预览的回收路径

### 8.1 SurfaceView

Camera HAL 完成 buffer 后，`Camera3OutputStream` 直接 queue 到 Surface。SurfaceFlinger 为预览维护独立图层，HWC 再决定 `CLIENT` 或 DEVICE composition。buffer 释放取决于 SurfaceFlinger/HWC 是否还在读取该图层。

这种路径省去宿主应用每帧采样 camera texture，但宿主窗口与预览图层的几何、crop、alpha、圆角和可见性仍需协同。预览 buffer 到得早，不代表 layer transaction 已在同一 display frame 生效。

### 8.2 TextureView

Camera buffer 先进入 `SurfaceTexture`。App 的 HWUI 在宿主窗口绘制时获取它，再把预览纹理采样进 App Window。这里至少有两条队列：

```text
Camera HAL → SurfaceTexture
App HWUI   → App Window → SurfaceFlinger
```

第一条队列有新相机帧后，还要等待应用主线程、RenderThread、GPU 和第二条队列。SurfaceFlinger 通常只看到宿主 App layer，不能只看 layer tree 判断 Camera HAL 是否迟到。

### 8.3 自研 GL / Vulkan

滤镜、AR、畸变矫正或分割场景中，App renderer 先消费 camera buffer，再生产一张新的可见 buffer。性能分析必须拆成：

1. Camera HAL 写入及其 release fence；
2. App GPU 等待、采样和算法通道；
3. renderer 输出 Surface 的入队；
4. SurfaceFlinger / HWC present。

只测最终 App Window 的帧时间，会把相机输入迟到和应用 GPU 处理慢混在一起。

## 9. 出错、重配置与关闭时的所有权

### 9.1 buffer error 也要保留围栏语义

HAL 填充失败时把状态设为 `ERROR`。如果它从未等待框架给出的 acquire fence，就把该围栏原样作为 release fence 返回；如果已经等待完成，可以返回空 release fence。错误不能成为跳过同步的理由。

CameraService 收到 error buffer 后走 `cancelBuffer()`。这会把槽位还给 BufferQueue，但仍要携带有效围栏，防止队列过早复用。

### 9.2 Surface 断开是流的局部错误

App 销毁 Surface、ImageReader 或 codec 后，`requestStreamBuffers()` 可能得到 `STREAM_DISCONNECTED`，普通 `dequeueBuffer()` 也可能返回 `NO_INIT`/`DEAD_OBJECT`。HAL 应针对涉及该流的请求报错，camera service 再决定是否重建会话；不能继续使用旧 buffer handle。

### 9.3 `flush()` 返回后不得残留 HAL buffer

AIDL `flush()` 约定返回时 HAL 中不能再有 outstanding request 或 buffer。随后框架才能安全地调用 `configureStreams()` 或提交新请求。close 与 stream removal 还会终止缓冲区 ID 缓存的有效期。

“相机已经关闭”应至少验证三件事：

- repeating request 已停止，in-flight frame 已完成或报错；
- 所有 output/input buffer 已返回；
- Surface、Image、codec 与自研 renderer 没有继续持有旧对象。

## 10. 用 Perfetto 和 dumpsys 建立证据

### 10.1 记录会话配置

采 trace 前记录：

- camera id，以及 logical / physical camera 关系；
- 每个流的 Surface 类型、format、size、dataspace、fps、dynamic range；
- CameraX 版本与 `PreviewView` 实际选用的 SurfaceView/TextureView；
- `maxImages`、encoder 配置和自研 renderer 的输入输出；
- 是否启用 HAL buffer management，按设备还是按流；
- vendor build、Camera HAL、ISP 固件与内核版本。

缺少这些信息时，同一段 `dequeueBuffer()` 等待可能被误判为 gralloc、消费者或 HAL 处理管线过慢。

### 10.2 按一帧的事件顺序检查

建议按下面顺序查一帧：

```text
capture request / frame number
  → sensor timestamp / shutter
  → HAL output buffer result
  → HAL release fence
  → preview queueBuffer
  → SurfaceTexture 获取或 SF latch
  → display present
```

analysis、record 和 still output 另建时间线，不能用其中一路回调代替 preview ready。HAL buffer-management 模式还要增加 `requestStreamBuffers()`、buffer id 与 `returnStreamBuffers()` 事件。

### 10.3 AOSP 能直接提供的线索

Android 17 CameraService 源码包含以下可核对点：

- `Camera3Device::RequestThread`：request 提交、按流取得 buffer；
- `Camera3OutputStream::getBufferLockedCommon()`：`dequeueBuffer()` 或框架 BufferManager 路径；
- `Camera3Stream::getBuffer()`：等待 `max_buffers` 的时长；
- `Camera3OutputStream::returnBufferCheckedLocked()`：`queueBuffer()`、`cancelBuffer()` 和 HAL release fence；
- `AidlCamera3OutputUtils.cpp` 中的 `requestStreamBuffers()`：HAL 缓冲区请求的逐流校验；
- stream dump 中的 `DequeueBuffer latency histogram` 与 `wait on max_buffers` 统计。

设备 trace 中是否出现完整的相机、ISP、V4L2、IOMMU 或带宽轨道由厂商决定。看不到 vendor event 时，只能把问题收敛到 framework/HAL 边界，不能据此断言某个 ISP 模块的耗时。

### 10.4 常见现象与下一步

| 现象 | 优先检查 | 不能直接下的结论 |
|---|---|---|
| `dequeueBuffer()` 长时间等待 | consumer 是否归还、Surface 是否断开、队列是否到上限 | gralloc 分配一定慢 |
| `requestStreamBuffers()` 返回 `NO_BUFFER_AVAILABLE` | outstanding 数量、`maxBuffers`、consumer 持有时间 | HAL 内存泄漏 |
| ImageReader 延迟持续增长 | acquire/close、`maxImages`、分析耗时 | sensor fps 不稳 |
| SurfaceView 已入队但没换帧 | HAL fence、SF latch、HWC 与展示 | Camera HAL 没产出 |
| TextureView 输入已到但屏幕晚 | SurfaceTexture acquire、App main/RT、GPU、host queue | SurfaceFlinger 丢帧 |
| dma-buf 总量增长 | 各流数量、分配大小、HAL/ISP/codec 内部 buffer | Java 堆泄漏 |

### 10.5 buffer 阻塞不自动等于 ANR

buffer 不足可以让 CameraService RequestThread、HAL 专用线程或应用的同步调用等待。Android ANR 仍要求应用主线程、广播、service、input 等路径超过相应超时。要证明两者有因果关系，必须找到主线程或关键 Binder 调用等待相机操作的调用栈，再对齐 buffer/fence 阻塞时间。

## 11. 评审清单

### HAL / vendor

- [ ] `maxBuffers` 与处理管线的并发持有量一致；
- [ ] 每次写 buffer 前等待 acquire fence；
- [ ] result 返回 release fence 后不再访问 buffer；
- [ ] HAL 缓冲区管理不超过每个流的上限；
- [ ] `bufferId` cache 能处理 `cachesToRemove`、reconfigure 与关闭；
- [ ] `signalStreamFlush()` 使用 `streamConfigCounter` 处理乱序；
- [ ] `flush()` 返回前已归还所有请求和 buffer；
- [ ] Android 17 厂商代码不再调用 ION；
- [ ] 4KB 与 16KB 内核上都没有硬编码 `PAGE_SIZE` 假设。

### framework / App

- [ ] 明确每个输出 Surface 的直接 consumer；
- [ ] Image / ImageProxy 在所有异常路径都能关闭；
- [ ] TextureView 与 SurfaceView 的性能证据分开采集；
- [ ] 自研 renderer 的相机输入与可见输出分开计时；
- [ ] 以内存分配大小和 buffer 数量计算驻留量，不用分辨率乘固定 bpp 代替；
- [ ] 诊断记录包含 frame number、stream id、buffer id、sensor timestamp 与 fence；
- [ ] ANR 结论有主线程或关键 Binder 等待栈支持。

## 12. Android 10—17 的版本边界

| 版本 | 相关变化 |
|---|---|
| Android 10 / API 29 | 引入可选 Camera HAL3 buffer-management API，HAL 可按需请求 output buffer |
| Android 12 / API 31 | GKI 2.0 以 DMA-BUF heaps 取代 ION，HAL3 request-result 与 Surface 队列主线不变 |
| Android 13 / API 33 | 新设备的 Camera HAL 接口开发转向 AIDL；HIDL 设备仍受兼容支持 |
| Android 15 / API 35 | AOSP 开始支持 16KB page size；它不是 Camera HAL3 独有能力 |
| Android 16 / API 36 | 继续完善 16KB 兼容检查，buffer 生命周期约定没有改变 |
| Android 17 / API 37 | 平台源码锚点更新到 Android 17；AIDL 流级 HAL buffer management、buffer cache、flush 约定按 `android-17.0.0_r1` 核对；ION 不再受支持 |

## 总结

Camera 缓冲区问题应从“哪个流、哪个 consumer、谁正在持有、等待哪一条围栏”开始。framework 管理模式在 request 入 HAL 前从 Surface 取 buffer；HAL buffer-management 模式把取 buffer 延后，但仍受同一 Surface 队列、`maxBuffers` 和 consumer 回收速度约束。

一帧预览的 HAL release fence、BufferQueue consumer acquire、SurfaceFlinger 锁存与 display present 分属不同阶段。再加上录像、analysis、still capture 各自的 buffer pool，单看某个回调或一条图层轨道无法解释整个 Camera session。把帧号、流 ID、stream id、buffer id、sensor timestamp、fence 与 consumer release 对齐，才能区分 HAL/ISP 过慢、buffer 不足、App 持有过久和显示链路迟到。
