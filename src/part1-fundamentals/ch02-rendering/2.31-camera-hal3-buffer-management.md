# 2.31 Camera HAL3 Buffer 管理与 BufferQueue 协作的内存模型

Camera HAL3 不维护覆盖预览、录像、分析和拍照的公共 GraphicBuffer 池。Camera2 会配置若干输出 `Surface`，相机服务为每个输出建立流；每个流再通过自己的队列与 Surface 后面的消费者协作。HAL 在这条链路中负责生产图像，而 GraphicBuffer 的分配、缓存、跨进程传递和回收由框架、图形分配器、BufferQueue、HAL 与消费者共同完成。

以下讨论以 Android 17 / API 37 / `android-17.0.0_r1` 和内核 `android17-6.18-2026-06_r6` 为源码边界。分析缓冲区所有权时，应把握四条规则：

1. `HalStream.maxBuffers` 限制 HAL 同时持有的在途缓冲区数量，不是应用层的缓存配置；
2. `dequeueBuffer()` 返回的围栏会作为 Camera HAL 的获取围栏，HAL 返回的释放围栏又会成为下游消费者读取该缓冲区前要等待的围栏；
3. HAL 缓冲区管理只把“提交请求”和“取得输出缓冲区”解耦，缓冲区仍来自对应输出 Surface；
4. 预览正常不代表录像或 ImageReader 正常，多输出必须按流分别检查。

## 1. 从请求—结果模型理解缓冲区

### 1.1 一个请求可以有多个输出

应用创建 `CameraCaptureSession` 时，把预览、录像、图像分析、JPEG、RAW 等 `Surface` 交给 Camera2。`Camera3Device::RequestThread` 把设置、帧号和目标流送入 HAL。HAL 完成传感器、ISP 与后处理后，通过 `processCaptureResult()` 异步返回元数据和输出缓冲区。

下面的结构图用于区分控制流、像素流和各路消费者：

```text
Camera2 / CameraX
  └─ CameraCaptureSession
       └─ Camera3Device / RequestThread
            └─ Camera HAL3
                 ├─ 预览流 ─→ SurfaceView / SurfaceTexture
                 ├─ 录像流 ─→ MediaCodec
                 ├─ 分析流 ─→ ImageReader
                 └─ 静态图像流 ─→ JPEG / HEIC / RAW 消费者
```

同一个帧号的元数据和各路缓冲区可以分批返回。预览缓冲区已经进入 BufferQueue，只能说明预览输出有了进展；它不能证明分析缓冲区已被应用关闭，也不能证明录像编码器已消费同帧。

### 1.2 每个输出流都有自己的队列边界

`Camera3OutputStream` 持有目标 `Surface`，并以 `NATIVE_WINDOW_API_CAMERA` 连接生产者端。Surface 后面的消费者决定缓冲区的用途：

| 输出目标 | 相机缓冲区的直接消费者 | 是否直接形成可见图层 |
|---|---|---|
| `SurfaceView` | SurfaceFlinger 一侧的 Surface 消费者 | 通常是独立子图层 |
| `TextureView` | 应用进程中的 `SurfaceTexture` | 否，宿主 HWUI 再画进应用窗口 |
| `ImageReader` | ImageReader / 应用 | 否 |
| MediaCodec 输入 Surface | 编码器 | 否 |
| 自研 GL / Vulkan 输入 | 应用 GPU 渲染器 | 输入本身不直接上屏，渲染器还要生产第二条可见输出 |

所以，“HAL 是生产者、SurfaceFlinger 是消费者”只适用于部分预览拓扑。TextureView、ImageReader、编码器与自研渲染器都有不同的直接消费者。

## 2. `configureStreams()` 决定什么

相机服务把宽高、格式、数据空间、旋转、消费者用途等信息交给 HAL。Android 17 的 AIDL HAL 通过 `HalStream` 返回以下关键结果：

- `overrideFormat`：`IMPLEMENTATION_DEFINED` 输出可由 HAL 选择实际格式；
- `producerUsage`：输出流上 HAL 所需的 gralloc 用途；
- `consumerUsage`：输入流上 HAL 所需的用途；
- `maxBuffers`：HAL 同时可能持有的最大缓冲区数量；
- `overrideDataSpace`：允许覆盖的数据空间；
- `enableHalBufferManager`：在会话可配置模式下，决定该流是否由 HAL 按需请求缓冲区。

框架会把生产者与消费者的用途合并后交给图形分配器。对于 `IMPLEMENTATION_DEFINED`，最终布局可能依赖相机写入端和显示、GPU、编解码器等读取端的组合要求，不能只根据公开像素格式推断步幅、平面偏移或压缩方式。

### 2.1 `maxBuffers` 与队列总量

Android 17 的 `Camera3OutputStream::configureConsumerQueueLocked()` 会查询消费者要求保留的最小未出队缓冲区数量，再计算：

```text
mTotalBufferCount =
    NATIVE_WINDOW_MIN_UNDEQUEUED_BUFFERS
    + camera_stream::max_buffers
```

这个值描述该输出 Surface 的基础队列容量。消费者必须留有自己正在读取或显示的缓冲区，HAL 也必须有空间推进处理管线。`Camera3Stream::getBuffer()` 还会检查 HAL 已取走的缓冲区数量；达到 `max_buffers` 时，它会等待缓冲区返回，并记录 `wait on max_buffers` 延迟直方图。

不能直接增大 `maxBuffers` 来掩盖消费者过慢。增加它可能让处理管线暂时不阻塞，也会增加该流可同时驻留的图像内存。这个字段由 HAL 根据处理管线需求声明，错误的数值还可能破坏框架与 HAL 的流控约定。

### 2.2 框架内部 BufferManager 与 HAL 缓冲区管理不同

源码里还能看到 `Camera3BufferManager`。它属于相机服务内部，可让兼容流复用框架管理的 GraphicBuffer，并通过 `attachBuffer()` 接回具体 BufferQueue。启用后，`Camera3OutputStream` 会禁止对应 BufferQueue 自行分配。

HAL 缓冲区管理 API 则是 HAL 通过 `requestStreamBuffers()` 向相机服务取得缓冲区。两套机制可以出现在同一条调用路径中，但调用者、接口边界和目标都不同：

| 名称 | 所在侧 | 主要作用 |
|---|---|---|
| `Camera3BufferManager` | 相机服务内部 | 在框架管理的兼容流之间调度 GraphicBuffer |
| HAL 缓冲区管理 | Camera HAL ↔ 相机服务 | 把捕获请求提交与输出缓冲区获取分开 |

排查日志或源码时要先确认说的是哪一个 BufferManager。

## 3. 框架管理缓冲区时的一帧生命周期

没有为某个输出启用 HAL 缓冲区管理时，`RequestThread` 会在调用 HAL 前为该请求取得输出缓冲区。

### 3.1 框架从 Surface 取得可写缓冲区

`Camera3OutputStream::getBufferLockedCommon()` 最终调用 `ANativeWindow::dequeueBuffer()`。成功后得到：

- 一个 `ANativeWindowBuffer`，其句柄指向 GraphicBuffer；
- 一个围栏文件描述符，表示该缓冲区何时结束上一次消费者使用。

`Camera3OutputStream::getBufferLocked()` 把围栏填入 `camera_stream_buffer.acquire_fence`，再把缓冲区交给 HAL。源码注释明确写明，此后围栏文件描述符由 HAL 持有。

### 3.2 HAL 等待获取围栏后写图像

HAL 在读写缓冲区前必须等待获取围栏。对输出流来说，这一步保护 HAL，避免它覆盖 GPU、SurfaceFlinger、编码器或应用仍在读取的旧内容。

如果获取围栏为空，表示无需等待。若 HAL 因错误没有等待该围栏，AIDL `StreamBuffer` 约定要求 HAL 把原获取围栏作为释放围栏退回，让框架在复用前仍能等待正确的完成点。

### 3.3 HAL 用释放围栏归还写入结果

HAL 通过 `processCaptureResult()` 返回：

- 流与缓冲区标识；
- `BufferStatus.OK` 或 `ERROR`；
- 释放围栏，表示 HAL 何时停止访问该缓冲区。

释放围栏为空表示在调用 `processCaptureResult()` 时已经完成所有访问。若围栏有效，HAL 可以先返回结果，由下游异步等待。围栏发出信号之后，HAL 不得再次访问该缓冲区。

### 3.4 CameraService 入队或取消

`Camera3OutputStream::returnBufferCheckedLocked()` 总会接收 HAL 的释放围栏：

- 缓冲区正常且时间戳有效时，调用 `queueBuffer()` 交给 Surface 消费者；
- 缓冲区状态为错误、流正在丢帧或时间戳为 0 时，调用 `cancelBuffer()`；
- 两条路径都会带上 HAL 释放围栏，保证下游或队列在 HAL 停止访问后再处理该缓冲区。

正常入队后，BufferQueue 中的围栏从消费者视角又叫获取围栏：消费者要等它发出信号才能读取新图像。这是同一个同步对象跨接口后的命名变化，并未额外生成相机围栏。

### 3.5 消费者释放后才能再次出队

消费者用完缓冲区后把释放围栏交回 BufferQueue。下一轮生产者通过 `dequeueBuffer()` 取得该槽位时，会拿到描述消费者完成时间的围栏。CameraService 再把它放进 HAL 的获取围栏字段，生命周期由此进入下一轮。

完整顺序可以写成：

```text
消费者释放围栏
        ↓
BufferQueue dequeueBuffer()
        ↓
HAL 获取围栏 → HAL 等待/写入
        ↓
HAL 释放围栏
        ↓
BufferQueue queueBuffer()
        ↓
消费者获取/等待/读取
```

判断围栏方向时，要同时写出“谁准备读或写”和“谁已经结束访问”。只记获取、释放两个名字，很容易在 HAL 接口与 BufferQueue 接口之间说反。

## 4. Android 17 的 HAL 缓冲区管理路径

Android 10 引入可选的 HAL3 缓冲区管理 API。HAL 处理管线可以同时排队 N 个请求，却可能只在靠近输出的阶段需要少量缓冲区。如果框架在请求进入 HAL 前就为所有输出取齐缓冲区，会让暂时用不到的图像内存长期驻留。

Android 17 同时保留两类行为：

- 未启用的流：框架仍随请求提供真实输出缓冲区；
- 已启用的流：请求中只有流的占位信息，`buffer` 为空，HAL 稍后调用 `requestStreamBuffers()`。

在 `SESSION_CONFIGURABLE` 模式下，HAL 可以通过 `HalStream.enableHalBufferManager` 按流选择；在 AIDL 设备级模式下，框架会把全部输出流视为 HAL 管理。

### 4.1 `requestStreamBuffers()` 取得的缓冲区不绑定特定帧

Android 17 的 `AidlCamera3OutputUtils.cpp` 明确说明：一次 `requestStreamBuffers()` 返回的缓冲区不与某个 `CaptureRequest` 预先绑定。HAL 可以：

1. 为多个流批量请求若干缓冲区；
2. 选择其中一个用于某帧；
3. 把已使用的缓冲区随该帧的 `processCaptureResult()` 返回；
4. 把多取但未使用的缓冲区经 `returnStreamBuffers()` 退回。

CameraService 会逐个流检查：

- 流是否存在且启用了 HAL 缓冲区管理；
- 是否重复请求同一个流 ID；
- Surface 是否已断开；
- `当前 outstanding + 本次请求数` 是否超过 `maxBuffers`；
- 当前是否正在 `configureStreams()`。

可能的结果包括 `STREAM_DISCONNECTED`、`NO_BUFFER_AVAILABLE`、`MAX_BUFFER_EXCEEDED` 与 `FAILED_CONFIGURING`。`requestStreamBuffers()` 是同步调用，AIDL 注释建议 HAL 使用专用线程，并避免在延迟敏感路径一次请求大量缓冲区。

### 4.2 `bufferId` 与句柄缓存

跨 Binder 每帧重复传原生句柄会增加开销。Android 17 的 `StreamBuffer` 采用 `streamId + bufferId` 建立缓存约定：

- 某个缓冲区第一次交给 HAL 时，同时带 `bufferId` 和原生句柄；
- HAL 记住两者的映射；
- 同一个缓冲区后续再次出现时，只传 `bufferId`，句柄为空；
- `CaptureResult` 返回时句柄也为空，框架用帧、流和缓冲区记录找回原对象；
- `processCaptureRequest(..., cachesToRemove)` 要求 HAL 删除已经失效的缓存项。

流被移除、会话关闭或框架通知删除缓存后，HAL 不能继续使用旧映射。把 `bufferId` 当作跨会话稳定句柄，会造成释放后使用、错配或设备错误。

### 4.3 `returnStreamBuffers()` 只归还未用于结果的缓冲区

HAL 已把缓冲区用于某帧时，应随 `processCaptureResult()` 返回。多取、预取后未使用的缓冲区才走 `returnStreamBuffers()`。CameraService 找回对应在途缓冲区后，以错误状态和时间戳 0 交还输出流，最终走 `cancelBuffer()`，不会把它当成一帧有效图像送给消费者。

### 4.4 `signalStreamFlush()` 与 `flush()` 的区别

两个接口都会促使缓冲区返回，但语义不同：

| 接口 | 目的 | 待定请求的处理 |
|---|---|---|
| `signalStreamFlush()` | 为流重配置回收 HAL 手中的缓冲区 | HAL 应正常完成已有请求，并及时归还指定流的缓冲区 |
| `flush()` | 尽快清空整个捕获管线 | 允许把未完成缓冲区标为 `ERROR`，返回时不得再有未完成请求或缓冲区 |

`signalStreamFlush()` 是异步提示，`streamConfigCounter` 用于识别它是否晚于对应的 `configureStreams()` 到达。HAL 不能只按 Binder 到达顺序判断配置代次。

## 5. 三组围栏不能混为一谈

Camera 预览上屏时，至少要区分下面三组同步：

| 同步边界 | 完成了什么 | 常见等待方 |
|---|---|---|
| 框架 → HAL 获取围栏 | 上一个消费者已停止使用输出缓冲区 | Camera HAL / ISP |
| HAL → 消费者释放围栏 | 传感器 / ISP / HAL 已完成当前图像写入 | BufferQueue 消费者、ImageReader、编解码器、应用 GPU |
| SurfaceFlinger / HWC 释放与展示围栏 | 显示设备是否停止读取图层缓冲区，以及显示帧何时展示 | BufferQueue 生产者、显示性能分析工具 |

显示展示围栏不能证明相机输出已完成；分析流或 JPEG 缓冲区也可能从未进入显示系统。反过来，HAL 释放围栏已经发出信号，只能证明相机生产者完成写入，不表示 SurfaceFlinger 已锁存，更不表示面板已经展示。

内核 `android17-6.18-2026-06_r6` 中，`dma_fence` 表示异步工作完成点，`sync_file` 负责把一个或多个围栏暴露成文件描述符。Camera AIDL 传递的是原生句柄中的围栏文件描述符；厂商 ISP、GPU、编解码器和显示驱动怎样创建围栏并发出信号，要回到对应设备的驱动和 HAL 源码核对。

## 6. 多输出的内存与背压

### 6.1 每路输出单独计算，整组会话共同受限

粗略估算相机图像内存时，应按流求和：

```text
会话 GraphicBuffer 驻留量
  ≈ Σ（该流已分配缓冲区数 × 分配器返回的单缓冲区大小）
```

这只是排查起点。单个缓冲区大小还受步幅、平面对齐、压缩元数据、保护属性、图块布局与厂商分配器影响；HAL、ISP 固件、GPU 和编解码器的内部工作缓冲区也不一定出现在 CameraService 的流统计中。

常见未压缩载荷可以用来检查数量级：

| 格式 | 可见像素载荷的粗略量级 | 注意事项 |
|---|---:|---|
| RGBA_8888 | `width × height × 4` | 步幅与压缩会改变物理分配 |
| YUV 4:2:0 | `width × height × 1.5` | 平面步幅、切片高度不能省略 |
| RAW10 | `width × height × 1.25` | 行打包与对齐由实现决定 |
| RAW12 | `width × height × 1.5` | 同上 |
| RAW14 | `width × height × 1.75` | Android 17 能力仍要查设备特征 |

`IMPLEMENTATION_DEFINED` 不能套用固定的每像素字节数。BLOB 流还要使用配置中的 `bufferSize` 边界，不能把 JPEG 文件大小当作 GraphicBuffer 的分配大小。

### 6.2 慢消费者怎样形成背压

每路输出有独立队列，但一次捕获请求可以同时要求多个输出。下面几种情况都会让缓冲区回收变慢：

- `ImageReader` 取得 `Image` 后没有及时 `close()`；
- CameraX `ImageProxy` 未关闭；
- 编码器输入拥塞；
- TextureView 所在应用长时间不绘制或不消费 `SurfaceTexture`；
- Surface 被销毁或弃用；
- 自研 GL / Vulkan 渲染器长时间持有输入 `AHardwareBuffer`；
- SurfaceFlinger 或 HWC 长时间占用预览缓冲区。

框架管理缓冲区时，只要某个目标流达到 HAL 可持有上限，RequestThread 就可能在取得该路缓冲区时等待。HAL 缓冲区管理模式把请求提交提前了，HAL 则必须自行控制处理管线深度，并处理 `requestStreamBuffers()` 暂时拿不到缓冲区的情况。

多路是否互相拖慢还取决于厂商处理管线。设备可能共享传感器读出、ISP 阶段、缩放器、带宽或内部缓冲池。看到分析流积压后预览也掉帧时，只能先把分析流列为候选原因；还要用帧号、各路结果时间与缓冲区归还记录证明因果关系。

### 6.3 应用侧最重要的归还动作

以下示例用于展示 ImageReader 消费者的最小资源边界：

```kotlin
imageReader.setOnImageAvailableListener({ reader ->
    val image = reader.acquireLatestImage() ?: return@setOnImageAvailableListener
    try {
        analyze(image)
    } finally {
        image.close()
    }
}, analysisHandler)
```

`acquireLatestImage()` 适合只关心新数据的分析任务，它可以丢弃较旧图像；`image.close()` 才把当前缓冲区归还队列。若业务要求逐帧处理，可改用 `acquireNextImage()`，但处理能力必须跟得上输入速率，并把 `maxImages` 视为并发持有上限。

## 7. 16KB 页面大小与 ION：纠正常见误解

### 7.1 16KB 页面大小并非 Android 17 首次引入

AOSP 从 Android 15 起支持 16KB 页面大小。它主要改变内核页粒度、`mmap()` 取整、ELF 对齐以及依赖固定 `PAGE_SIZE` 的原生代码。Android 17 继续处在这条兼容线上。

Camera AIDL、`GraphicBuffer` 和 BufferQueue 没有规定：

- 每个相机缓冲区的逻辑宽高必须按 16KB 对齐；
- 图像载荷大小必须是 16KB 的整数倍；
- 应用或 Camera HAL 应手工把 gralloc 分配结果补齐到 16KB。

物理页、IOMMU 映射、平面步幅、堆粒度和硬件块对齐属于不同层次。分配器与驱动可以因 16KB 内核产生不同的物理占用，但不能由此推出统一的 Camera HAL 缓冲区对齐公式。排查时应读取映射器返回的布局、dma-buf 大小和设备堆配置。

### 7.2 Android 17 不再支持 ION

Android 17 AOSP 发布说明要求删除厂商代码中的 ION 调用。Android 12 的 GKI 2.0 已用 DMA-BUF 堆取代 ION；到 Android 17，所有支持 ION 的内核都已结束维护。

Android 17 相机路径涉及以下对象：

- gralloc / 图形分配器决定 GraphicBuffer 的实现与布局；
- DMA-BUF 堆或厂商分配器提供可共享分配；
- dma-buf fd 让 HAL、GPU、codec、HWC 等设备共享同一分配；
- dma-fence / sync_file fd 传递访问完成关系。

`ashmem` 也不是 Android 17 相机 GraphicBuffer 的可选“内存类型”。它解决普通共享内存问题，不提供 Camera HAL 图形流所需的 gralloc 元数据、用途协商和设备导入语义。

## 8. SurfaceView、TextureView 与自研预览的回收路径

### 8.1 SurfaceView

Camera HAL 完成缓冲区写入后，`Camera3OutputStream` 直接将其入队到 Surface。SurfaceFlinger 为预览维护独立图层，HWC 再决定 `CLIENT` 或 `DEVICE` 合成。缓冲区何时释放取决于 SurfaceFlinger/HWC 是否还在读取该图层。

这种路径省去宿主应用每帧采样相机纹理的工作，但宿主窗口与预览图层的几何、裁剪、透明度、圆角和可见性仍需协同。预览缓冲区到得早，不代表图层事务已在同一显示帧生效。

### 8.2 TextureView

相机缓冲区先进入 `SurfaceTexture`。应用的 HWUI 在宿主窗口绘制时获取它，再把预览纹理采样进应用窗口。这里至少有两条队列：

```text
Camera HAL → SurfaceTexture
应用 HWUI → 应用窗口 → SurfaceFlinger
```

第一条队列有新相机帧后，还要等待应用主线程、RenderThread、GPU 和第二条队列。SurfaceFlinger 通常只看到宿主应用图层，不能只看图层树判断 Camera HAL 是否迟到。

### 8.3 自研 GL / Vulkan

滤镜、AR、畸变矫正或分割场景中，应用渲染器先消费相机缓冲区，再生产一张新的可见缓冲区。性能分析必须拆成：

1. Camera HAL 写入及其释放围栏；
2. 应用 GPU 等待、采样和算法通道；
3. 渲染器输出 Surface 的入队；
4. SurfaceFlinger / HWC 展示。

只测最终应用窗口的帧时间，会把相机输入迟到和应用 GPU 处理慢混在一起。

## 9. 出错、重配置与关闭时的所有权

### 9.1 缓冲区错误也要保留围栏语义

HAL 填充失败时把状态设为 `ERROR`。如果它从未等待框架给出的获取围栏，就把该围栏原样作为释放围栏返回；如果已经等待完成，可以返回空释放围栏。错误不能成为跳过同步的理由。

CameraService 收到错误缓冲区后走 `cancelBuffer()`。这会把槽位还给 BufferQueue，但仍要携带有效围栏，防止队列过早复用。

### 9.2 Surface 断开是流的局部错误

应用销毁 Surface、ImageReader 或编解码器后，`requestStreamBuffers()` 可能得到 `STREAM_DISCONNECTED`，普通 `dequeueBuffer()` 也可能返回 `NO_INIT`/`DEAD_OBJECT`。HAL 应针对涉及该流的请求报错，相机服务再决定是否重建会话；不能继续使用旧缓冲区句柄。

### 9.3 `flush()` 返回后不得残留 HAL 缓冲区

AIDL `flush()` 约定返回时 HAL 中不能再有未完成请求或缓冲区。随后框架才能安全地调用 `configureStreams()` 或提交新请求。关闭会话与移除流还会终止缓冲区 ID 缓存的有效期。

“相机已经关闭”应至少验证三件事：

- 重复请求已停止，在途帧已完成或报错；
- 所有输出/输入缓冲区已返回；
- Surface、Image、编解码器与自研渲染器没有继续持有旧对象。

## 10. 用 Perfetto 和 dumpsys 建立证据

### 10.1 记录会话配置

采集跟踪数据前记录：

- 相机 ID，以及逻辑/物理相机关系；
- 每个流的 Surface 类型、格式、尺寸、数据空间、帧率、动态范围；
- CameraX 版本与 `PreviewView` 实际选用的 SurfaceView/TextureView；
- `maxImages`、编码器配置和自研渲染器的输入输出；
- 是否启用 HAL 缓冲区管理，按设备还是按流；
- 厂商构建版本、Camera HAL、ISP 固件与内核版本。

缺少这些信息时，同一段 `dequeueBuffer()` 等待可能被误判为 gralloc、消费者或 HAL 处理管线过慢。

### 10.2 按一帧的事件顺序检查

建议按下面顺序查一帧：

```text
捕获请求 / 帧号
  → 传感器时间戳 / 快门
  → HAL 输出缓冲区结果
  → HAL 释放围栏
  → 预览 queueBuffer
  → SurfaceTexture 获取或 SurfaceFlinger 锁存
  → 显示展示
```

分析、录像和静态图像输出应另建时间线，不能用其中一路回调代替预览就绪。HAL 缓冲区管理模式还要增加 `requestStreamBuffers()`、缓冲区 ID 与 `returnStreamBuffers()` 事件。

### 10.3 AOSP 能直接提供的线索

Android 17 CameraService 源码包含以下可核对点：

- `Camera3Device::RequestThread`：请求提交、按流取得缓冲区；
- `Camera3OutputStream::getBufferLockedCommon()`：`dequeueBuffer()` 或框架 BufferManager 路径；
- `Camera3Stream::getBuffer()`：等待 `max_buffers` 的时长；
- `Camera3OutputStream::returnBufferCheckedLocked()`：`queueBuffer()`、`cancelBuffer()` 和 HAL 释放围栏；
- `AidlCamera3OutputUtils.cpp` 中的 `requestStreamBuffers()`：HAL 缓冲区请求的逐流校验；
- 流转储中的 `DequeueBuffer latency histogram` 与 `wait on max_buffers` 统计。

设备跟踪数据中是否出现完整的相机、ISP、V4L2、IOMMU 或带宽轨道由厂商决定。看不到厂商事件时，只能把问题收敛到框架/HAL 边界，不能据此断言某个 ISP 模块的耗时。

### 10.4 常见现象与下一步

| 现象 | 优先检查 | 不能直接下的结论 |
|---|---|---|
| `dequeueBuffer()` 长时间等待 | 消费者是否归还、Surface 是否断开、队列是否到上限 | gralloc 分配一定慢 |
| `requestStreamBuffers()` 返回 `NO_BUFFER_AVAILABLE` | 未完成数量、`maxBuffers`、消费者持有时间 | HAL 内存泄漏 |
| ImageReader 延迟持续增长 | 获取/关闭、`maxImages`、分析耗时 | 传感器帧率不稳 |
| SurfaceView 已入队但没换帧 | HAL 围栏、SurfaceFlinger 锁存、HWC 与展示 | Camera HAL 没产出 |
| TextureView 输入已到但屏幕晚 | SurfaceTexture 获取、应用主线程/RenderThread、GPU、宿主队列 | SurfaceFlinger 丢帧 |
| dma-buf 总量增长 | 各流数量、分配大小、HAL/ISP/编解码器内部缓冲区 | Java 堆泄漏 |

### 10.5 缓冲区阻塞不自动等于 ANR

缓冲区不足可以让 CameraService RequestThread、HAL 专用线程或应用的同步调用等待。Android ANR 仍要求应用主线程、广播、服务、输入等路径超过相应超时。要证明两者有因果关系，必须找到主线程或关键 Binder 调用等待相机操作的调用栈，再对齐缓冲区/围栏阻塞时间。

## 11. 评审清单

### HAL / 厂商实现

- [ ] `maxBuffers` 与处理管线的并发持有量一致；
- [ ] 每次写缓冲区前等待获取围栏；
- [ ] 结果返回释放围栏后不再访问缓冲区；
- [ ] HAL 缓冲区管理不超过每个流的上限；
- [ ] `bufferId` 缓存能处理 `cachesToRemove`、重配置与关闭；
- [ ] `signalStreamFlush()` 使用 `streamConfigCounter` 处理乱序；
- [ ] `flush()` 返回前已归还所有请求和缓冲区；
- [ ] Android 17 厂商代码不再调用 ION；
- [ ] 4KB 与 16KB 内核上都没有硬编码 `PAGE_SIZE` 假设。

### 框架 / 应用

- [ ] 明确每个输出 Surface 的直接消费者；
- [ ] Image / ImageProxy 在所有异常路径都能关闭；
- [ ] TextureView 与 SurfaceView 的性能证据分开采集；
- [ ] 自研渲染器的相机输入与可见输出分开计时；
- [ ] 以内存分配大小和缓冲区数量计算驻留量，不用分辨率乘固定的每像素字节数代替；
- [ ] 诊断记录包含帧号、流 ID、缓冲区 ID、传感器时间戳与围栏；
- [ ] ANR 结论有主线程或关键 Binder 等待栈支持。

## 12. Android 10—17 的版本边界

| 版本 | 相关变化 |
|---|---|
| Android 10 / API 29 | 引入可选 Camera HAL3 缓冲区管理 API，HAL 可按需请求输出缓冲区 |
| Android 12 / API 31 | GKI 2.0 以 DMA-BUF heaps 取代 ION，HAL3 request-result 与 Surface 队列主线不变 |
| Android 13 / API 33 | 新设备的 Camera HAL 接口开发转向 AIDL；HIDL 设备仍受兼容支持 |
| Android 15 / API 35 | AOSP 开始支持 16KB 页面大小；它不是 Camera HAL3 独有能力 |
| Android 16 / API 36 | 继续完善 16KB 兼容检查，缓冲区生命周期约定没有改变 |
| Android 17 / API 37 | 平台源码锚点更新到 Android 17；AIDL 流级 HAL 缓冲区管理、缓冲区缓存、刷新约定按 `android-17.0.0_r1` 核对；ION 不再受支持 |

## 总结

Camera 缓冲区问题应从“哪个流、哪个消费者、谁正在持有、等待哪一条围栏”开始。框架管理模式在请求进入 HAL 前从 Surface 取得缓冲区；HAL 缓冲区管理模式把取缓冲区的时机延后，但仍受同一 Surface 队列、`maxBuffers` 和消费者回收速度约束。

一帧预览的 HAL 释放围栏、BufferQueue 消费者获取、SurfaceFlinger 锁存与显示展示分属不同阶段。再加上录像、分析、静态捕获各自的缓冲池，单看某个回调或一条图层轨道无法解释整个 Camera 会话。把帧号、流 ID、缓冲区 ID、传感器时间戳、围栏与消费者释放事件对齐，才能区分 HAL/ISP 过慢、缓冲区不足、应用持有过久和显示链路迟到。
