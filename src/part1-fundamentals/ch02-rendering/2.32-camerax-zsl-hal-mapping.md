# 2.32 CameraX ZSL 与 HAL Reprocessing Request 的映射关系

CameraX 的零快门延迟（Zero Shutter Lag，ZSL）模式会持续保留近期拍摄的 `PRIVATE` 图像。用户按下快门时，如果缓存里存在满足条件的图像，CameraX 将该图像和与它同一时间戳的 `TotalCaptureResult` 送入 Camera2 可重处理会话，再请求设备输出 JPEG。相机不需要为这次请求重新曝光，所以照片内容可以来自按键之前。

“Zero”只描述快门动作到源图像时刻之间的目标。JPEG 编码、回调调度和文件写入仍然需要时间，ZSL 也不承诺每次拍照都使用历史帧。

以下讨论以 CameraX 稳定版 `1.6.1`、Android 17 / API 37 / `android-17.0.0_r1` 和内核 `android17-6.18-2026-06_r6` 为验证边界。映射 ZSL 路径时，需要把握四条规则：

1. CameraX ZSL 依赖 `PRIVATE_REPROCESSING`、合法的 input/output 配置和当前 UseCase 组合，不能只看 `CAPTURE_MODE_ZERO_SHUTTER_LAG`；
2. CameraX 1.6.1 的 ZSL 环形缓冲区固定保留 3 个合格的 `ImageProxy`，没有图像清晰度打分、运动补偿或可配置的 5—10 帧缓存；
3. CameraX 显式重处理与 `CONTROL_ENABLE_ZSL` 所代表的设备内部 ZSL 是两条不同路径；
4. 到达 Camera HAL AIDL 边界后，有效的 `CaptureRequest.inputBuffer` 才能证明该请求是 reprocess request。

## 1. ZSL 减少的是哪一段时间

一次普通 still capture 可以简化为：

```text
按下快门
  → 提交 still capture request
  → 等待 sensor 曝光
  → ISP / 厂商算法处理
  → JPEG 输出
  → CameraX 回调
  → 应用写文件
```

这张时序只用于划分时间段。普通拍照的源帧通常产生于按键之后，因此曝光和三自动状态收敛可能进入用户感知延迟。

CameraX ZSL 的成功路径是：

```text
持续 repeating request
  → PRIVATE output + TotalCaptureResult
  → 按 timestamp 匹配图像和 metadata
  → 过滤 AF / AE / AWB 状态
  → 3 帧 ring

按下快门
  → 取出一帧及其 TotalCaptureResult
  → ImageWriter.queueInputImage()
  → CameraDevice.createReprocessCaptureRequest()
  → JPEG output
  → CameraX 回调
  → 应用写文件
```

这里省去了“按键后再取得一张 sensor 图像”这一步。reprocess、JPEG、回调和存储仍在按键之后执行。源帧来自按键前也带来一个取舍：照片记录的时刻可能早于用户触摸事件，运动主体的位置未必等于按键瞬间。

## 2. 先区分两种都叫 ZSL 的机制

Android Camera2 同时暴露了设备内部 ZSL 和应用管理的 ZSL。名称相近，控制方式和证据不同。

| 机制 | 控制入口 | 历史帧由谁保留 | HAL 请求特征 | 是否保证使用历史帧 |
|---|---|---|---|---|
| 设备内部 ZSL | `CONTROL_ENABLE_ZSL=true`，且 capture intent 为 `STILL_CAPTURE` | Camera HAL / 厂商管线 | 可以仍是无 input buffer 的普通 capture request | 不保证 |
| 应用管理的 ZSL | 可重处理 session、缓存图像、`createReprocessCaptureRequest()` | CameraX / Camera2 client | request 带有效 input buffer | 缓存和提交成功时使用该 input buffer |

Android 17 的 `CaptureRequest.CONTROL_ENABLE_ZSL` 文档表达的是“may enable”。即使键值为 `true`，设备也可以不选历史帧；输出内容和 `SENSOR_TIMESTAMP` 还可能早于之前的普通 request。

`CameraDevice.TEMPLATE_ZERO_SHUTTER_LAG` 面向应用管理的 ZSL。CameraX 1.6.1 同时把这个模板类型作 capture 配置的意图标记：`CaptureConfigAdapter` 看到它后尝试从 ring 取出 input image。成功时，CameraPipe 调用 `createReprocessCaptureRequest(totalCaptureResult)`；ring 没有可用帧时，配置会改为普通 still capture template。

看到 `TEMPLATE_ZERO_SHUTTER_LAG` 只能说明上层想走 ZSL，看到 `CONTROL_ENABLE_ZSL=true` 只能说明设备获准尝试内部 ZSL。确认显式重处理时，还要检查 input stream 和 input buffer。

## 3. `isZslSupported()` 是设备能力预筛选

下面的示例用于在构建 `ImageCapture` 前选择 capture mode：

```kotlin
@OptIn(ExperimentalZeroShutterLag::class)
fun buildImageCapture(cameraInfo: CameraInfo): ImageCapture {
    val captureMode = if (cameraInfo.isZslSupported) {
        ImageCapture.CAPTURE_MODE_ZERO_SHUTTER_LAG
    } else {
        ImageCapture.CAPTURE_MODE_MINIMIZE_LATENCY
    }

    return ImageCapture.Builder()
        .setCaptureMode(captureMode)
        .setFlashMode(ImageCapture.FLASH_MODE_OFF)
        .build()
}
```

这段代码只做能力选择。最终能否建立 ZSL session，还要等 CameraX 合并所有 UseCase 配置并检查 stream 组合。

在 CameraX 1.6.1 的 Camera2 实现中，`CameraInfoAdapter.isZslSupported()` 主要检查两项：

- CameraCharacteristics 包含 `REQUEST_AVAILABLE_CAPABILITIES_PRIVATE_REPROCESSING`；
- 当前设备没有命中 `ZslDisablerQuirk`。

API 文档还规定最低系统版本为 Android 6.0 / API 23。这个返回值不覆盖当前闪光灯模式、VideoCapture、Camera Extension 和分辨率策略，也不验证本次 session 最终选中的所有 Surface 是否能同时配置。

可以把判定分成三层：

| 层次 | 典型检查 | 失败结果 |
|---|---|---|
| 设备能力 | API 23+、`PRIVATE_REPROCESSING`、无禁用 quirk | 不宣称支持 ZSL |
| session 配置 | `PRIVATE` input size、`PRIVATE → JPEG` 有效、UseCase 组合可配置 | 不建立 reprocess input |
| 单次拍照 | flash 为 `OFF`、ring 中存在带完整 metadata 的合格帧 | 改走普通 still capture |

### 3.1 CameraX 1.6.1 的禁用条件

以下情况会禁用或绕过 CameraX ZSL：

- 绑定 `VideoCapture`；
- 启用 Camera Extension；
- flash mode 为 `ON` 或 `AUTO`；
- 请求高分辨率优先模式，导致 `OPTION_ZSL_DISABLED` 被设置；
- 命中 `ZslDisablerQuirk` 设备特例；
- 设备没有 `PRIVATE_REPROCESSING`；
- `StreamConfigurationMap` 没有可用的 `PRIVATE` input size；
- `getValidOutputFormatsForInput(PRIVATE)` 不包含 JPEG；
- 拍照时 ring 为空，或其中没有可用的 metadata。

flash 的处理需要单独说明。CameraX 可以保留已经建立的 reprocessable session，只在 flash 为 `ON/AUTO` 时提交普通 still capture；用户切回 `OFF` 后，无需仅为这一变化重建整套会话。UseCase 配置、能力或 quirk 不允许 ZSL 时，`ZslControlImpl` 会跳过 input stream 的建立。

CameraX 1.6.1 的 quirk 列表包含若干 Samsung Fold4/S22/S24 型号和 Xiaomi Mi 8，原因是重处理图像可能出现颜色或变焦冻结。机型名单属于库版本实现细节，升级 CameraX 后应重新检查对应版本的 `ZslDisablerQuirk`。

## 4. 会话怎样完成配置

### 4.1 输入格式固定为 `PRIVATE`

`ZslControlImpl` 把 ZSL 格式固定为 `ImageFormat.PRIVATE`。它从：

```text
StreamConfigurationMap.getInputSizes(ImageFormat.PRIVATE)
```

选择面积最大的 input size，然后确认：

```text
getValidOutputFormatsForInput(ImageFormat.PRIVATE)
```

包含 `ImageFormat.JPEG`。

这些查询解决两个不同问题：

- input size 决定哪一种 `PRIVATE` 图像可以送回设备；
- input/output format map 决定这种 input 能否重处理成 JPEG。

`PRIVATE` 表示应用不读取图像像素布局。CameraX 持有的是 `Image`/GraphicBuffer 句柄和 metadata，设备端按 implementation-defined buffer 契约处理。不能用 `width × height × 固定 bpp` 精确计算这批 buffer 的物理内存。

### 4.2 同一个会话里同时存在 output 与 input

CameraX 创建一个 `MetadataImageReader`，把它的 Surface 加入 repeating request 的输出。这个 output 持续接收可作为候选的 `PRIVATE` 图像。

CameraX 还给 session 设置相同宽、高和格式的 `InputConfiguration`。Camera2 建立 reprocessable capture session 后，session 会暴露一个 input Surface。CameraPipe 在该 input Surface 上创建 `ImageWriter`，供拍照时把候选图像送回相机设备。

结构可以画成：

```text
regular repeating request
  ├─ preview output → PreviewView / Surface
  └─ ZSL PRIVATE output → MetadataImageReader → ZslRingBuffer

selected PRIVATE Image
  → ImageWriter → session input Surface
  → reprocess request
  → JPEG output Surface
```

上半部分仍是 sensor capture，下半部分以既有 buffer 为输入，不再触发一次新的 sensor 曝光。

## 5. RingBuffer 中保存了什么

### 5.1 图像必须先与 metadata 按时间戳匹配

`MetadataImageReader` 同时监听 `ImageReader` 和 `CameraCaptureCallback`。图像与 `CameraCaptureResult` 的到达顺序可以不同，它用 timestamp 把二者配成一个带 `ImageInfo` 的 `ImageProxy`。

只有匹配成功后，`ZslRingBuffer` 才能读取对应的 AF、AE、AWB 状态。图像和 result 长期无法匹配时，旧数据会被清理；不能把“ImageReader 回调到达”当成“ring 已有可重处理帧”。

### 5.2 CameraX 1.6.1 只接纳三自动状态合格的帧

`ZslRingBuffer.isValidZslFrame()` 的条件是：

- AF 为 `LOCKED_FOCUSED` 或 `PASSIVE_FOCUSED`；
- AE 为 `CONVERGED`；
- AWB 为 `CONVERGED`。

任一条件不满足，`ImageProxy` 会立即关闭，不进入 ring。这是离散 metadata 过滤，没有图像内容分析。弱光下 AE 长时间不收敛、连续对焦扫描、快速切换场景或 metadata 缺失，都可能让 ring 为空。

### 5.3 三个容易混淆的数量

CameraX 1.6.1 源码里出现了三个不同的 buffer 数量：

| 名称 | 数值 | 约束对象 |
|---|---:|---|
| `RING_BUFFER_CAPACITY` | 3 | 可供 ZSL 选择的合格 `ImageProxy` |
| `ZslControlImpl.MAX_IMAGES` | 9 | 传给 `MetadataImageReader` 的 image 上限，源码为 ring 容量的 3 倍 |
| CameraPipe input `maxImages` | 1 | session input Surface 上的 `ImageWriter` 并发 image 数 |

“ZSL 缓存 3 帧”不代表整条 camera pipeline 只分配 3 个 GraphicBuffer。Preview、JPEG、ZSL output、HAL in-flight、ImageReader 和 input stream 各有自己的队列约束，驻留量要按流分开统计。

### 5.4 当前实现没有“最佳帧评分器”

`ZslRingBuffer` 继承自 `ArrayRingBuffer`。新帧通过 `addFirst()` 加入，`dequeue()` 通过 `removeLast()` 取出；容量已满时，也会先移除并关闭队尾的最旧帧。

由此得到 CameraX 1.6.1 的准确行为：

1. listener 每次通过 `acquireLatestImage()` 取得当时最新的已匹配图像；
2. 图像先经过 AF/AE/AWB 过滤；
3. ring 最多持有 3 帧；
4. 拍照时取出当前队列里最早保留的合格帧。

`ImageCapture` API 注释把目标概述为交付时间戳接近快门的中间结果，但 1.6.1 的这段实现没有按触摸时间遍历候选，也没有清晰度评分或运动补偿。排查具体版本时，应以该版本源码和实测 `SENSOR_TIMESTAMP` 为准。

## 6. 从 CameraX 请求映射到 Camera2 reprocess request

CameraX 1.6.1 的 Camera2 后端已经迁移到 CameraPipe。较早资料中常见的 `androidx.camera.camera2.internal.*` 路径不能直接代表这个版本；对应的核心实现位于 `androidx.camera.camera2.adapter` 和 `androidx.camera.camera2.pipe.compat`。

### 6.1 `CaptureConfigAdapter` 生成 `InputRequest`

当 capture config 的模板为 `TEMPLATE_ZERO_SHUTTER_LAG`，且 UseCase 和 flash 没有禁用 ZSL 时，`CaptureConfigAdapter` 尝试从 ring 取出一帧。

取帧成功后，它完成三件事：

1. 从 `ImageProxy.imageInfo` 取回匹配的 `CameraCaptureResult`；
2. 把底层 `Image` 包装为 CameraPipe 的 image 对象；
3. 把 image 与对应 `FrameInfo` 组合成 `InputRequest`。

如果 ring 为空，`inputRequest` 保持为空，CameraX 把请求模板改为普通 `TEMPLATE_STILL_CAPTURE`。ring 中的帧已经经过 metadata 匹配；若内部 image/result 类型或非空约束被破坏，源码会在构造 `InputRequest` 时失败，不能把这种异常算作普通降级。

### 6.2 `ImageWriter` 把 buffer 送入 session input

CameraPipe 为 reprocessable session 的 input Surface 创建 `ImageWriter`。准备提交 request 时，`Camera2CaptureSequenceProcessor` 先调用：

```text
imageWriter.queueInputImage(selectedImage)
```

这一步把 CameraX 持有的 `PRIVATE` image 排入 Camera2 session input queue。它没有复制出一张可由应用访问的 bitmap，也没有把 JPEG 数据送回 HAL。

### 6.3 `TotalCaptureResult` 初始化 reprocess request

CameraPipe 从 `FrameInfo` 解包同一源帧的 `TotalCaptureResult`，再调用：

```text
cameraDevice.createReprocessCaptureRequest(totalCaptureResult)
```

设备需要原始 capture result 中的曝光、白平衡、镜头、裁剪和厂商 metadata，才能按源图像的拍摄条件进行重处理。Android Camera2 要求 input image 来自同一 camera device，并在同一 session 中直接或间接产生；随意组合其他相机、其他 session 的 image 与 result 不符合契约。

创建 builder 后，CameraPipe 添加本次 still capture 的目标 Surface，通常是 CameraX 图像管线的 JPEG output，并写入 JPEG orientation、quality 等请求参数。

### 6.4 生命周期必须覆盖成功、失败和取消

被选中的 `ImageProxy` 在排入 `ImageWriter` 后仍持有底层资源。CameraX 给请求安装 listener，在以下路径中用同一个原子引用关闭它：

- request complete；
- request failed；
- request aborted；
- total capture result 到达。

多个回调可能先后发生，原子引用保证只关闭一次。若自行实现 Camera2 ZSL，也要给提交失败、session close、abort 和异常路径补齐 input image 回收。

失败边界分为两种：如果拍照时没有候选帧，CameraX 会改用普通 still capture；如果已经构造 `InputRequest`，随后 `ImageWriter.queueInputImage()` 或 `createReprocessCaptureRequest()` 失败，CameraPipe 会让本次 capture sequence 构建失败。不能假定这一阶段仍会自动重试普通拍照。

## 7. Android 17 Framework 如何识别 reprocess

Camera2 请求进入 camera service 后，`Camera3Device` 根据 request metadata 中的 input stream id 找到 `mInputStream`。`RequestThread` 在提交 HAL 前从 `Camera3InputStream` 取得下一块 input buffer，并填入：

```text
camera_capture_request_t.input_buffer
camera_capture_request_t.input_width
camera_capture_request_t.input_height
```

如果 request 没有 input stream，`input_buffer` 为 `NULL`。这一分支决定了请求是新 sensor capture 还是重处理。

Camera service 的 AIDL 适配层再把 native request 转为 `android.hardware.camera.device.CaptureRequest`：

- `inputBuffer.streamId` 标识 input stream；
- `inputBuffer.bufferId` 标识该 stream 内的 buffer；
- 首次出现的 buffer 还会携带 handle，后续可以只用 `bufferId`；
- `inputBuffer.acquireFence` 约束 HAL 何时可以读取输入缓冲区；
- `inputWidth/inputHeight` 描述实际输入尺寸；
- `outputBuffers[]` 至少包含一个待写入的目标 buffer。

AIDL `CaptureRequest.aidl` 直接规定：

- 无有效 `inputBuffer`：从 imager 捕获新图像；
- 有有效 `inputBuffer`：重处理该图像；
- HAL 必须等待 input acquire fence 后再读取；
- HAL 必须在后续 `CaptureResult` 中归还 input buffer；
- output buffer 也有各自的 acquire/release fence 和所有权转换。

这就是 CameraX ZSL 到 Camera HAL3 的可靠映射：

```text
CameraX InputRequest
  → Camera2 reprocess CaptureRequest
  → Camera3Device::CaptureRequest.mInputStream
  → camera_capture_request_t.input_buffer
  → AIDL CaptureRequest.inputBuffer
  → HAL reprocessing
```

HAL 内部重新经过 ISP 的哪些模块、是否使用专用硬件、如何执行降噪或 JPEG 编码，属于设备实现。公共接口只约束输入 buffer、metadata、输出 buffer、fence、结果和错误行为，不能从接口名称推导厂商算法阶段。

## 8. Buffer、fence 与反压

### 8.1 ZSL output 也会占用 camera stream buffer

ring 保存的是尚未关闭的 `ImageProxy`。每保留一帧，就有一块 `PRIVATE` output buffer 不能回到其 producer 队列。ring 满后会关闭被淘汰帧，拍照完成或失败后关闭被选中帧，session reset 时清空全部帧。

如果 image 没有按预期关闭，可能出现：

- `MetadataImageReader` 达到 `maxImages`；
- ZSL output stream 无空闲 buffer；
- repeating request 被 output 反压拖慢；
- 预览、分析或其他共享 camera 资源出现连带延迟。

这类问题要按 [Camera HAL3 Buffer 管理](./2.31-camera-hal3-buffer-management.md) 的方法分 stream 检查。preview 正常不能证明 ZSL output 和 input queue 正常。

### 8.2 input buffer 的所有权跨过 HAL

调用 `ImageWriter.queueInputImage()` 后，input Surface 的 consumer 是 camera service / HAL 路径。HAL 读取前等待 acquire fence，完成访问后通过结果和 release fence 归还。release fence signal 前，client 不能安全复用该 buffer。

kernel 的 dma-fence 和 sync_file 只提供同步原语；CameraX 的三帧策略、AF/AE/AWB 过滤、降级条件和 reprocess metadata 都在用户空间。分析 ZSL 失败时，不应先把业务策略归因于内核。

### 8.3 reprocess request 不读取 sensor

Android 17 `CameraDevice` 文档明确规定 reprocess request 不捕获新的 image data。它从会话输入 Surface 取得下一块 buffer，再为本次请求的输出 Surface 生成结果。

这也解释了两个常见现象：

- 输出 JPEG 的 `SENSOR_TIMESTAMP` 可以早于按键时间；
- reprocess 仍可能等待 input queue、HAL pipeline、JPEG output buffer 或 fence，源帧已存在并不代表回调立即返回。

## 9. 如何验证设备上是否走了 ZSL

### 9.1 记录应用层条件

每次拍照至少记录：

- CameraX 版本；
- camera id；
- `CameraInfo.isZslSupported()`；
- capture mode；
- flash mode；
- 已绑定的 UseCase；
- extension 是否启用；
- 目标分辨率策略；
- `SENSOR_INFO_TIMESTAMP_SOURCE`；
- 按键的 `elapsedRealtimeNanos()`；
- 输出图像或 capture result 的 sensor timestamp；
- 成功、失败和错误码。

不能只记录一个 `zsl=true` 布尔值。它无法说明 session 是否建立 input stream，也无法说明本次是否取得环形缓冲区中的帧。

### 9.2 检查 CameraX 日志

CameraX 1.6.1 源码中可直接定位的诊断文本包括：

- `Private reprocessing isn't supported`；
- `Unable to find a supported size for ZSL`；
- `JPEG isn't valid output for ZSL format`；
- `Selected ZSL size`；
- `No such element`；
- `Queuing image ... for reprocessing to ImageWriter`；
- `Failed to create a ReprocessingCaptureRequest.Builder`。

第一组说明能力或会话配置，`No such element` 说明拍照时 ring 没有帧，末两项才接近单次 reprocess 提交。

### 9.3 用 `dumpsys media.camera` 查看 input stream

`Camera3Device::dump()` 会输出当前 stream configuration、input stream，以及最近一次请求的 input/output stream id。它适合回答：

- session 是否配置了 input stream；
- 最近请求是否引用 input stream；
- 输出 stream 是否仍在；
- 设备当前是否处于 active/error 等状态。

`dumpsys` 是当前状态快照。短请求已经完成或 session 已重建时，快照可能错过目标事件，因此要和带时间戳的应用日志、CameraService 日志或 Perfetto 同时使用。

### 9.4 HAL 侧以 `inputBuffer` 为准

厂商可在 `processCaptureRequest()` 入口记录：

- frame number；
- input stream id / buffer id；
- input acquire fence；
- output stream id / buffer id；
- request settings 是否来自 FMQ；
- 返回 input/output buffer 的 release fence 和 status。

有效 input buffer 说明这是 reprocess request。无 input buffer 但 `CONTROL_ENABLE_ZSL=true`，说明设备可以尝试内部 ZSL；两者不能相互替代。

### 9.5 延迟要拆成 source age 与完成时间

建议分别统计：

```text
source_age = shutter_event_time - sensor_timestamp
callback_latency = callback_time - shutter_event_time
save_latency = file_complete_time - callback_time
```

这三个量回答不同问题。`source_age > 0` 表示图像来自按键前；它不能证明回调快。`callback_latency` 包含 reprocess、JPEG 和调度；`save_latency` 主要属于应用编码后的 I/O 路径。

只有 `SENSOR_INFO_TIMESTAMP_SOURCE_REALTIME` 才能把 `SENSOR_TIMESTAMP` 直接与 `elapsedRealtimeNanos()` 比较。时间戳来源为 `UNKNOWN` 时，两者可能不在同一时钟域，必须先做设备侧校准，不能直接计算 `source_age`。

## 10. 常见误判

| 误判 | 源码对应的修正 |
|---|---|
| ZSL 一定走 HAL reprocessing | 条件满足且本次 ring 有可用帧时才构造 `InputRequest` |
| `isZslSupported()` 为 `true` 就一定生效 | 它没有覆盖 flash、VideoCapture、Extension、高分辨率偏好和本次流配置 |
| CameraX 会缓存 5—10 帧并动态调节 | 1.6.1 的 ring 容量常量为 3 |
| CameraX 从候选中做清晰度评分和运动补偿 | 1.6.1 只检查 AF/AE/AWB 枚举状态 |
| `CONTROL_ENABLE_ZSL=true` 就是 reprocess request | 设备内部 ZSL 可以没有 input buffer |
| `TEMPLATE_ZERO_SHUTTER_LAG` 能证明 HAL 收到 input image | template 是上层意图；HAL 侧要检查 `inputBuffer` |
| ZSL 能把整次拍照压到固定毫秒数 | 设备、场景、JPEG、线程调度和存储都会改变完成时间 |
| ring 只有 3 帧，所以内存就是 3 个 buffer | reader、input、preview、JPEG 和 HAL in-flight 都有独立 buffer |
| reprocess 会重新曝光一次 | Camera2 契约规定不捕获新的 image data |
| reprocess 失败总会自动重试普通拍照 | 取帧前可降级；排入输入后的失败不应假定有透明重试 |

## 11. 评审清单

### CameraX / App

- [ ] 依赖版本固定为 CameraX 1.6.1，源码路径按 CameraPipe 后端核对；
- [ ] 使用 `CameraInfo.isZslSupported()` 做设备能力预筛选；
- [ ] flash 保持 `OFF`；
- [ ] 未同时启用 VideoCapture 或 Camera Extension；
- [ ] 高分辨率策略没有禁用 ZSL；
- [ ] 拍照日志记录 capture mode、UseCase、flash 和 extension 状态；
- [ ] 统计 `SENSOR_TIMESTAMP` 与快门事件时间，不用回调时间代替拍摄时间；
- [ ] 对普通 capture fallback 和 reprocess submission failure 分开统计。

### Framework / HAL

- [ ] `PRIVATE_REPROCESSING` capability 与 stream configuration 一致；
- [ ] `PRIVATE` input size 有效；
- [ ] `PRIVATE → JPEG` 是合法重处理格式组合；
- [ ] session 配置了 input stream；
- [ ] input image 与 `TotalCaptureResult` 来自同一 camera device 和 session；
- [ ] reprocess request 带有效 input buffer 和至少一个 output buffer；
- [ ] HAL 等待 input/output acquire fence；
- [ ] HAL 在 result 中归还 input/output buffer 与 release fence；
- [ ] 失败、flush、reconfigure 和 close 路径不会遗留 input buffer；
- [ ] 以 frame number、stream id、buffer id、sensor timestamp 和 fence 串起证据。

## 12. 版本边界

| 版本 | 相关边界 |
|---|---|
| Android 6.0 / API 23 | Camera2 可重处理 session、`createReprocessCaptureRequest()` 和 `ImageWriter` 能力成为 CameraX ZSL 的系统基础 |
| CameraX 1.2.0 | `CAPTURE_MODE_ZERO_SHUTTER_LAG` 作为实验 API 引入 |
| Android 14 / API 34 | reprocess request 的 `CONTROL_CAPTURE_INTENT` 默认设为 `STILL_CAPTURE`；更早版本需要调用方自行留意 |
| CameraX 1.6.0 | Camera2 后端迁移到 CameraPipe，排障时应使用新的 adapter/pipe 实现路径 |
| CameraX 1.6.1 | 库侧锚点；固定 3 帧 ring、`PRIVATE` reprocessing、当前 quirk 和降级逻辑均按该版本源码核对 |
| Android 17 / API 37 | 平台源码锚点；Camera2 reprocess、Camera3 输入流与 AIDL `CaptureRequest.inputBuffer` 按 `android-17.0.0_r1` 核对 |

CameraX 是独立于 Android 系统发布的 Jetpack 库。同一台 Android 17 设备可以运行不同 CameraX 版本，分析报告必须同时写明系统 tag、vendor build 和 CameraX 版本。

## 总结

CameraX ZSL 是一条有条件的显式重处理路径。CameraX 1.6.1 持续接收 `PRIVATE` output，把图像与 capture result 按时间戳配对，只保留 AF 已对焦且 AE/AWB 收敛的帧，再从容量为 3 的 ring 取出一帧。拍照时，CameraPipe 通过 `ImageWriter` 把这帧送入 session input Surface，并用同帧的 `TotalCaptureResult` 创建 reprocess request。

在 Android 17 camera service 和 HAL AIDL 边界，是否存在有效 `inputBuffer` 决定 request 是重处理还是新 sensor capture。模板名、capture mode 和 `CONTROL_ENABLE_ZSL` 都不足以单独证明这件事。排障时，应分层记录能力、session 配置、单次取帧、input buffer、output buffer、timestamp 与围栏，才能解释某次拍照为何使用历史帧、为何降级，或为何在 reprocess 阶段失败。
