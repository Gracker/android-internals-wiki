## Android 17 没有统一的 Agent 内存沙箱

`android-17.0.0_r1` 中无法定位一个名为 “AI Agent Memory Sandbox” 的公共子系统，也没有跨应用自动共享模型、KV cache 或中间 tensor 的通用内存池。端侧智能功能仍要组合已有边界：

- Linux process/UID 隔离；
- SELinux domain 与 Binder service 权限；
- package/签名/role/permission 级调用资格；
- `SharedMemory`、`HardwareBuffer`、file/URI 等显式数据载体；
- service/session 生命周期与 fd 所有权；
- cgroup、MemoryLimiter、lmkd 与设备内存策略。

组件名称包含 agent、AI 或 inference，不会自动获得更高进程优先级、共享内存权限或 lmkd 豁免。

## 1. 进程隔离要先写威胁模型

同一 UID 的 `android:process=":inference"` 能隔离 crash 和部分内存峰值，但仍共享应用 UID 权限。isolated service 获得独立临时 UID，Binder service、文件和硬件节点访问都需要明确授权。Android 17 sepolicy 还区分普通 isolated app 与 isolated compute 场景，是否可用取决于服务声明和系统配置。

设计评审应记录：

- 每个 PID/UID/SELinux domain；
- 模型文件和输入数据的所有者；
- 谁能建立 Binder session；
- 调用方死亡、service 被杀或冻结时怎样取消；
- fd、mapping、fence 与 session 由谁关闭。

只写“沙箱进程”不能证明权限隔离或数据删除。

## 2. 数据复用要经过显式授权

跨进程复用大数据可以选择：

| 载体 | 适用内容 | 必查边界 |
|---|---|---|
| Binder Parcel | 小型控制参数、descriptor、状态 | transaction buffer、序列化、异常与超时 |
| `SharedMemory` | CPU 可访问的大块数据 | fd grant、size、mapping、只读保护、close/unmap |
| `HardwareBuffer` | 图形、Camera、codec 或加速器 buffer | format/usage、import、fence、producer/consumer 生命周期 |
| file/URI | 模型、文档、持久数据 | file mode、URI grant、撤销、at-rest policy |
| provider/service API | 有 schema 的跨应用数据 | caller validation、permission、rate limit、审计 |

共享 mapping 可以减少重复物理页或数据 copy，但发送方和接收方各自的 PSS/RSS 记账仍需按 mapping 与共享比例解释。接收方若解压、转码、repack 或复制到 delegate buffer，峰值可能继续增加。

App Functions 提供受系统管理的跨应用函数调用接口。它有 caller validation、request/response Parcelable 与 URI grant 机制；这些接口没有开放任意跨应用内存读取。

## 3. 内存归因按 PID、mapping 与 fd 展开

端侧推理常同时占用：

- model file mapping 与 page cache；
- runtime/native heap；
- tensor arena、KV cache 和临时 workspace；
- SharedMemory 或 dma-buf；
- GPU/NPU driver buffer；
- 调用方与服务端的序列化/转换副本。

Java heap dump只覆盖 managed object，native heap profile 也不覆盖全部 file mapping、dma-buf 或 driver allocation。测量时应对每个 PID 记录 RSS/PSS、anonymous/file/swap、fd/mapping、dma-buf 与 session 阶段。

多个进程的 RSS 不能直接相加当作系统占用；共享 page 会重复计数。PSS 按 mapping 数分摊共享页，也不能表示某个进程独占该页。

## 4. MemoryLimiter 与 lmkd 没有“AI 自动保护”

Android 17 的 MemoryLimiter 受 feature flag、vendor config、总内存和豁免列表控制。源码中的 default config 带有测试用途说明，不能直接当成所有设备生产值。只有配置指定的 sandboxed inference service 才可能进入豁免；第三方进程名包含 `inference` 不会自动匹配。

lmkd 仍依据 pressure、`oom_score_adj`、进程状态、内存占用与设备策略选择候选。推理占用增加会提高系统压力，不会为进程生成一个 Agent 专用保护等级。

## 5. Review 顺序

1. 画出 caller、broker、provider/inference service 与硬件进程；
2. 标记每个进程的 UID、SELinux domain、procstate 与 `oom_score_adj`；
3. 标记每块大数据的 owner、fd、mapping、读写权限和释放点；
4. 分阶段测量进程启动、模型映射、prefill/decode、session 释放和后台恢复；
5. 注入 caller death、service restart、fd 泄漏、权限撤销和低内存；
6. 用 smaps、heapprofd、Binder、scheduler、page fault、dma-buf 与 lmkd 证据验证。
