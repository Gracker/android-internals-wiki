## 审阅结论

Android 17 / API 37 的可核验变化是后台音频 hardening。它限制后台播放、音频焦点和音量/铃声 API，减少没有明确用户意图的播放与泄漏 session。这个机制可能间接避免无效耗电，但 AOSP 和官方行为说明没有承诺固定功耗收益，也没有把它定义成 LE Audio 的省电调度器。

LE Audio 的系统级支持从 Android 13 开始。到 Android 17，Classic Audio 与 LE Audio 仍会按设备能力和场景共存；LC3、ISO 调度、controller、Bluetooth Audio HAL、codec offload、射频条件和耳机端实现都会改变延迟与功耗。受保护提纲中的“智能管理”“动态频率调整”和跨设备统一能效结论没有源码与实验条件，不能作为平台保证。

本文件已被标记为重复稿，以下内容只负责划清 Android 17 边界。完整实现与应用适配分别由现有专题承载。

## 1. 后台音频 hardening 的规则

在 Android 17 上运行的 App，只要从后台进行受影响的音频交互，就必须满足以下基础条件之一：

- 存在对用户可见的 Activity；
- 运行一个类型不是 `shortService` 的 foreground service。

这条基础限制不以 target SDK 37 为前提。对于 target SDK 37 的 App，后台 foreground service 还要具备 while-in-use（WIU）能力。典型做法是在 Activity 可见或用户明确触发播放时启动 `MediaSessionService`/`mediaPlayback` FGS；仅仅让服务显示通知，不能证明它获得了 WIU。

精确闹钟是窄范围例外：App 具有 exact-alarm 能力，并且操作使用 `USAGE_ALARM` 的音频流时，可以豁免 WIU 要求。它不能用于普通媒体播放。

不满足条件时，各 API 的失败形态不同：

| 调用面 | Android 17 的表现 |
|---|---|
| playback track | 被静音；显式 write 路径在强制测试模式下可持续返回错误 |
| `requestAudioFocus()` | 返回 `AUDIOFOCUS_REQUEST_FAILED`，不改变其他 App 的焦点 |
| 音量与铃声 API | 调用被忽略，默认不会抛异常 |

应用自己的播放器状态仍可能显示 `PLAYING`。排障时需要同时检查系统音频日志、MediaSession、foreground service 和实际 Track 状态。

## 2. 源码中是两类判定

Android 17 的实现不能简化为单个 Java 开关：

| 路径 | 源码入口 | 控制对象 |
|---|---|---|
| AudioManager 控制 API | `HardeningEnforcer` | audio focus、音量和铃声操作 |
| playback track | AudioFlinger `Tracks.cpp::getHardeningDecision()` | 每条播放 Track 的 enforcement level 与静音 |

Java 路径会检查 `OP_TAKE_AUDIO_FOCUS`、`OP_CONTROL_AUDIO_PARTIAL`、`OP_CONTROL_AUDIO`，再结合 override、权限、usage、target SDK 和 exact-alarm 条件判定。native 路径为 Track 计算 `NONE`、`PARTIAL` 或 `FULL` enforcement，并监听对应 AppOps 状态。

两侧共享 `DEFAULT`、`ENABLE`、`DISABLE`、`THROW` override，但输入与结果不同。焦点申请通过，不等于随后创建的播放 Track 一定不会被限制；Track 有声音，也不表示 App 可以在后台修改系统音量。

`BLUETOOTH_CONNECT` 在焦点与 native playback 判定中最多带来 partial exemption。它用于蓝牙相关系统交互，不能推导出 LE Audio 播放无条件放行，更不能证明 controller 或 LC3 已进入最低功耗状态。

## 3. 调试命令存在文档与源码差异

Android 17 官方行为页当前写的是 `set-enable-hardening`，而 `android-17.0.0_r1` 的 `AudioManagerShellCommand.java` 暴露 `set-hardening` 和 `clear-hardening`。设备镜像可能来自不同阶段，执行测试前应先读取设备实际帮助。

下面这组命令用于确认当前镜像的命令名，并采集 hardening、焦点和 Track 证据。

```bash
adb shell cmd audio help
adb shell dumpsys audio
adb logcat -s AudioHardening AudioService AudioFlinger
```

如果 help 显示 `set-hardening`，可按镜像支持的 `enable`、`disable`、`throw` 模式做线下 A/B；测试完成后用 `clear-hardening` 回到默认政策。强制模式会改变 target SDK 与闹钟豁免条件，不能拿它代替默认行为的兼容性测试。

## 4. LE Audio 功耗必须实测

判断 LE Audio 是否省电，应固定手机、耳机固件、音量、Codec/QoS、声道、射频环境和播放内容，并至少区分：

- App/AudioTrack 与 AudioFlinger 的唤醒、buffer 和 underrun；
- Bluetooth stack 的 active group、路由与 CIS/BIS 状态；
- host codec 与 controller/DSP offload 的执行位置；
- controller 空口占用、重传与连接事件；
- 耳机端解码、后处理和功放成本；
- 手机整机 power rail 或可比较的电量计结果。

`dumpsys audio` 能说明路由、焦点和部分策略状态，HCI snoop 能还原 Bluetooth 控制过程，Perfetto 能观察 host 线程和调度；三者都不能单独给出耳机端功耗。没有目标硬件的 rail 数据时，不应填写“LC3 比 SBC 省电多少”或“续航提升多少”的固定百分比。

buffer、低延迟和功耗也不存在单向关系。缩小 buffer 可能增加唤醒和 underrun 风险；增大 buffer 可能提高稳定性，却增加交互延迟。FAST Mixer、AAudio MMAP 或 codec offload 是否可用，取决于 AudioPolicy、HAL、驱动和硬件能力。
