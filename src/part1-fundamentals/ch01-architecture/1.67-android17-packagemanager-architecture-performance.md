# 1.67 Android 17 PackageManager 架构与性能优化

> **版本边界**：本节基于 Android 17 (API 37) 源码验证，锚定 `android-17.0.0_r1`。涉及 Android 14-16 的历史对照时明确标注版本。
>
> **定位**：本节聚焦 PackageManager 的**系统服务架构**——服务初始化、包解析流水线、安装状态机、权限委托与查询缓存。安装编译（dexopt / SDM / Cloud Profile）的完整机制详见 §16.6 和 §16.9，此处仅引用结论。

---

## 要点

### 🔹 PackageManager 服务架构演进

#### 从单体到分模块：PMS 的职责拆分轨迹

`PackageManagerService`（PMS）长期是 `system_server` 中最重的服务之一。早期 Android 版本里，PMS 同时承担包解析、安装、卸载、权限管理、包查询、用户空间隔离和 dexopt 调度等全部职责。Android 12 之后，Google 逐步把职责拆出去：

| 拆出组件 | 大致版本 | 现位置 | PMS 保留的职责 |
|---|---|---|---|
| PermissionManagerService | Android 12 拆出框架，后续版本持续迁移 | `frameworks/base/services/core/java/com/android/server/pm/permission/PermissionManagerService.java` | 权限授予/撤销的 PMS 侧入口仍在，但判定逻辑委托给 PermissionManagerService |
| ART Service（dexopt 控制面） | Android 14 引入 | `art/libartservice/service/java/com/android/server/art/` | PMS 不再直接调用 `installd` 的 dexopt 命令，安装后通过 `ArtManagerLocal` 触发编译 [已验证: AOSP android-17.0.0_r1, art/libartservice/service/java/com/android/server/art/ArtManagerLocal.java] |
| InstallPackageHelper | Android 14 重构 | `frameworks/base/services/core/java/com/android/server/pm/InstallPackageHelper.java` | PMS 保留安装入口，安装流水线逻辑移至 Helper |

到 Android 17，PMS 的角色更像一个**协调门面**：外部调用 `PackageManager` API → PMS 做路由和基础校验 → 具体工作委托给子组件。这种分层对性能优化的意义在于：安装和编译的热路径不再全部挤在 PMS 的 `installPackageWithConfirmation` 锁里，减少了 main handler thread 的阻塞窗口。

[已验证: AOSP android-17.0.0_r1, frameworks/base/services/core/java/com/android/server/pm/PackageManagerService.java]

#### Binder 接口与线程模型

`PackageManager` 客户端接口通过 Binder IPC 与 PMS 通信。PMS 在 `system_server` 中注册为 `package` 服务，Binder 线程池处理进来的调用。高频调用（如 `getPackageInfo`、`getApplicationInfo`）走的是标准的 oneway/sync Binder 模型——Binder 缓冲池的约束详见 §1.44。

PMS 内部维护了一个 `mHandler`（`PackageHandler`），安装相关的异步消息（如 `POST_INSTALL`、`PACKAGE_VERIFIED`）在 handler thread 上串行处理。这是安装流程串行化的核心设计：同一时间只有一个安装事务在进行最终提交，避免了 `/data/app` 目录下文件操作的竞争。

> ⚠️ 安装事务的串行性意味着：如果某个应用的安装因为 dexopt 或验证流程卡住，排在后面的安装请求必须等待。Android 14+ 的 ART Service 分层在一定程度上缓解了这个问题——dexopt 通过 `artd` 异步执行，PMS 在提交安装结果后可以更快释放 handler thread。详见 §16.6。

### 🔹 APK 解析与验证机制

#### 解析流水线：从 APK 文件到 PackageInternal

Android 12 起，包解析逻辑迁移到了 `frameworks/base/core/java/android/content/pm/parsing/` 包下，核心入口是 `ParsingPackageUtils`。解析分两阶段：

**轻量解析（Lite Parsing）**：在安装前和包扫描时执行，只提取 manifest 的关键字段（包名、版本号、签名、split 列表），用于快速过滤和冲突检测。对应 `ApkLiteParseUtils`，产出 `ApkLite` 对象。

**完整解析（Full Parsing）**：在确认安装后执行，解析完整 manifest 的所有组件（Activity、Service、Receiver、Provider、权限声明、uses-feature 等），产出 `ParsingPackageImpl` 对象，后续转化为 `AndroidPackage`。

[已验证: AOSP android-17.0.0_r1, frameworks/base/core/java/android/content/pm/parsing/ParsingPackageUtils.java]

#### 签名验证：APK Signature Scheme v2/v3/v4

Android 7 引入 APK Signature Scheme v2（全文件签名），Android 9 引入 v3（支持密钥轮换），Android 11 引入 v4（增量安装）。到 Android 17，安装时签名验证的优先级链：

1. **v4 签名**：如果存在 `.idsig` 文件，使用 `incfs`（Incremental File System）挂载，支持流式安装
2. **v3 签名**：检查 APK 内的 v3 签名块，验证签名链和密钥轮换谱系
3. **v2 签名**：检查 APK 内的 v2 签名块
4. **v1 签名**（JAR 签名）：仅当上述均不存在时回退，已不推荐

签名验证的性能开销主要在 v2/v3 的全文件哈希计算——对大 APK（>100MB）可耗时数百毫秒。v4 + incfs 的流式安装把这部分开销摊到了下载阶段。

[已验证: 官方文档, source.android.com/docs/security/features/apksigning]

### 🔹 Staged Install 状态机

#### 安装事务的完整生命周期

一次标准的 APK 安装（通过 `PackageInstallerSession`）经历以下状态：

```
INIT → SEALING → SEALED → COMMITTING → COMMITTED → VERIFYING → VERIFIED → INSTALLING → INSTALLED
                                                                        ↘ FAILED
```

关键节点：

- **SEALING**：会话被锁定，不再接受新的 split 文件添加
- **SEALED**：所有文件已就位，开始计算哈希和签名验证
- **COMMITTING**：向 PMS 提交安装事务
- **VERIFYING**：调用 `PackageVerificationAgent`（如 Play Protect）进行安全验证
- **INSTALLING**：在 `InstallPackageHelper` 中执行实际的文件拷贝、UID 分配、dexopt 触发

[已验证: AOSP android-17.0.0_r1, frameworks/base/services/core/java/com/android/server/pm/PackageInstallerSession.java]

#### Staged Install 与 A/B 更新

Android 10+ 引入的 Staged Install 机制允许安装操作跨重启生效：安装提交后写入 B 槽（或 snapshot），下次启动时通过 `update_engine` 切换。这对系统级更新和主模块更新特别重要：

- `StagedInstallSession` 继承自 `PackageInstallerSession`，在 `commit()` 时标记为 staged
- PMS 在提交后通知 `PackageManagerService.sendStagedSessionChangedBroadcast()`
- 实际的 A/B 切换由 `update_engine`（`system/update_engine/`）处理，不属于 PMS

[已验证: AOSP android-17.0.0_r1, frameworks/base/services/core/java/com/android/server/pm/PackageInstallerSession.java]

### 🔹 权限管理与运行时检查

#### PermissionManagerService 的委托架构

Android 12 起，运行时权限的判定逻辑从 PMS 迁移到 `PermissionManagerService`（`PermissionManagerService.java`）。PMS 仍然保留 `checkPermission()` 的入口，但实际调用链：

```
PMS.checkPermission()
  → PermissionManagerService.checkPermission()
    → PermissionManagerService.Internal.checkPermission()
      → AppPermissionManager / PermissionGrantPolicy 判定
```

权限检查的性能优化点在于：`PermissionManagerService` 内部维护了权限授予状态的内存缓存（`mGrantedPermissions`），大部分 `checkPermission()` 调用不需要查数据库。PMS 的 `checkUidPermission()` 同理走委托路径。

[已验证: AOSP android-17.0.0_r1, frameworks/base/services/core/java/com/android/server/pm/permission/PermissionManagerService.java]

#### 安装时权限授予

安装完成后，PMS 在 `grantPermissions()` 中调用 `PermissionManagerService` 的接口为新安装的应用授予默认权限（如 INTERNET 等 normal permissions）。dangerous 权限不在安装时授予，需要运行时用户确认。

安装时权限授予的耗时通常很短（<10ms），但对大量预装包的系统首次启动（first-boot）阶段会累积——数百个预装包 × 5-10ms/包 = 数秒。这也是 §16.7 讨论的系统启动耗时的一个贡献项。

### 🔹 应用信息缓存机制

#### PackageInfoCache 与查询优化

PMS 面临最高频的调用是包信息查询：`getPackageInfo()`、`getApplicationInfo()`、`queryIntentActivities()` 等。这些查询如果每次都走完整的 Package 对象遍历，在数百个已安装应用上会非常慢。

Android 17 的查询路径利用了多层缓存：

1. **客户端缓存**：`PackageManager` 的客户端对象（`ApplicationPackageManager`）内部有 `mApplicationInfoCache`，对同一进程内的重复查询做 LRU 缓存
2. **PMS 侧缓存**：PMS 维护了 `mSettings.getTag()` 和 package map（`mPackages`），通过包名直接索引到 `AndroidPackage` 对象，不需要线性扫描
3. **PackageManagerInternal**：供系统服务使用的高速查询接口，绕过 Binder IPC（直接在 `system_server` 内调用）

[待验证: 客户端缓存的具体实现类名和 LRU 策略，AOSP android-17.0.0_r1]

对性能敏感的系统组件（如 `ActivityManagerService` 做进程调度时查询应用信息）应优先使用 `PackageManagerInternal`，避免 Binder 开销。这也是 §1.68 将讨论的 AMS 与 PMS 协作接口。

### 🔹 安装包来源验证

#### PackageVerificationAgent 与 Play Protect

安装来源验证分两层：

**第一层：安装来源约束（Install Source Restriction）**
Android 14+ 强化了安装来源追踪。每个安装会话记录 installer package name（如 `com.android.vending`、`com.google.android.packageinstaller`）。应用可以通过 `<manifest>` 中的 `android:installerPackageName` 声明偏好，但最终由系统决定。

**第二层：安全验证（Security Verification）**
PMS 在 `VERIFYING` 状态调用已注册的 `PackageVerificationAgent`。在带有 Google Play Services 的设备上，这会触发 Play Protect 扫描。验证超时默认为 10 秒（可配置），超时后根据 `verification_timeout` 策略决定是放行还是拒绝。

安全验证对安装耗时的影响是线性的：小 APK 通常 <1 秒，大 APK 或首次扫描（未在云端缓存验证结果）可达数秒。非 Play 渠道安装不会触发 Play Protect，但也缺少云端安全验证。

[已验证: 官方文档, source.android.com/docs/security/features]

### 🔹 应用更新策略优化

#### 增量更新与差分包

Google Play 使用差分包（delta/apk patch）减少更新下载量。设备端的差分合并由 Play Store app 完成，合并后的完整 APK 走标准安装流程。PMS 本身不感知"这是差分更新"——它只看到最终的完整 APK。

差分合并的 CPU 开销取决于差分算法（bsdiff / archive-patch）。在低端设备上，大 APK 的合并可耗时 5-15 秒，这部分时间不算在 PMS 安装耗时里，但用户感知为"更新很慢"。

#### App Standby Buckets 与更新优先级

Android 12+ 的 App Standby Buckets（`UsageStatsManager`）会影响应用的后台行为，但不直接影响安装优先级。PMS 的安装队列按 FIFO 顺序处理，不根据 bucket 做优先级排序。不过，后台 dexopt（`bg-dexopt-job`）的调度会参考 bucket——Active 应用更早获得 dexopt 机会，Rare 应用可能延迟数天。详见 §16.6。

### 🔹 MultiDex 处理优化

#### 从 MultiDex 到 ART 的原生 DEX 支持

Android 5 (Lollipop) 的 ART 运行时原生支持多 DEX 文件，`classes.dex`、`classes2.dex`...`classesN.dex` 在安装时统一被 dex2oat 处理。老的 MultiDex Support Library（`androidx.multidex`）只对 Dalvik 有意义——ART 设备上它只是一个空操作。

在 Android 17 的安装流程中，PMS 通过 `ParsingPackageUtils` 扫描 APK 内所有 `classes*.dex` 文件，将它们的偏移和大小记录到 `AndroidPackage` 对象中。dexopt 时，ART Service 的 `ArtFileManager` 会为每个 DEX 文件创建独立的 `.vdex`/`.odex` 产物。

[已验证: AOSP android-17.0.0_r1, art/libartservice/service/java/com/android/server/art/ArtFileManager.java]

#### 内存映射优化

Android 17 的 ART 运行时对 DEX 文件使用 `mmap` 而非 `read`，多个 DEX 文件的页可以共享 page cache。这意味着即使一个 APK 有 10+ 个 DEX 文件（常见于大型应用和 Flutter 应用），运行时的内存占用主要取决于实际访问的代码页，而非 DEX 文件总大小。

但安装时的 dex2oat 编译成本与 DEX 数量正相关：每个 DEX 文件需要独立的 class loader analysis 和 verification pass。对于 >5 个 DEX 文件的大型应用，安装时编译可能多耗时 3-8 秒。SDM（Staged Dalvik Compilation）在 Android 16 引入后可以把这部分成本前移到云端——详见 §16.9。

## 扩展

### 🔸 动态模块加载优化

Dynamic Feature Module（DFM）通过 Play Feature Delivery 按需下发 split APK。安装流程走 `PackageInstallerSession`，但只安装对应的 split 而非完整 APK。PMS 在 `INSTALLING` 阶段处理 split 合并：检查已有 base APK 的签名兼容性，为 split 分配资源 ID 空间。

Split 的安装耗远低于完整 APK——通常 1-3 秒（不含 dexopt），因为只需要拷贝一个较小的 APK 文件并更新 `PackageSetting`。但 split 的 dexopt 仍然需要走完整流程，除非该 split 有独立的 `.dm`/`.sdm` 产物。

详见 §25.8（App Bundle 与按需分发）。

### 🔸 应用沙箱性能边界

Android 的应用沙箱基于 Linux UID/GID 隔离。每个应用有独立的 UID（安装时由 PMS 分配），文件系统权限以 UID 为核心。PMS 在安装时调用 `installd`（`frameworks/native/cmds/installd/`）创建 `/data/data/<pkg>`、`/data/user/<user>/<pkg>` 等目录并设置 owner 和 SELinux context。

沙箱的运行时性能开销主要是 SELinux avc 检查和文件系统权限验证——这些在内核路径中，对 I/O 密集型应用有可感知的累积延迟。但这是安全隔离的基础，不可关闭。

[已验证: 官方文档, source.android.com/docs/security/app-sandbox]

### 🔸 包名冲突处理机制

PMS 在 `mPackages`（`ArrayMap<String, AndroidPackage>`）中以包名为键索引。同名包冲突（不同签名）会在安装时被拒绝，返回 `INSTALL_FAILED_UPDATE_INCOMPATIBLE` 或 `INSTALL_FAILED_ALREADY_EXISTS`。PMS 不做包名级别的"优雅降级"——要么替换（签名匹配），要么拒绝。

### 🔸 应用冻结/解冻优化

Android 15+ 增强了应用休眠（App Hibernation）能力。PMS 通过 `AppHibernManager`（`frameworks/base/services/core/java/com/android/server/apphibernation/`）管理休眠状态。休眠应用的通知通道被禁用、后台 FCM 被延迟，但 APK 本身不被移除。

解冻（unhibernate）的延迟主要来自 dexopt 检查——如果休眠期间应用的编译产物被清理，解冻后首次启动可能触发 dexopt。这个路径详见 §16.6 的 BackgroundDexOptService 调度。

[待验证: AppHibernManager 在 Android 17 的确切类名和方法签名]

### 🔸 预装包优化策略

系统首次启动（first-boot）需要扫描 `/system/app/`、`/system/priv-app/`、`/product/app/`、`/product/priv-app/` 等目录下的所有预装 APK。PMS 在 `PackageManagerService.` 的构造函数中执行初始扫描（通过 `PackageScanner`）。

预装扫描的耗时与 APK 数量和存储 I/O 速度线性相关。典型旗舰设备（~200 个预装包，UFS 3.1）的首次扫描耗时约 5-15 秒。这个时间不算在用户感知的"开机时间"里（因为它在 Zygote 启动前完成），但会影响 `system_server` 的就绪时间。

优化策略：
- 预编译 OAT/VDEX 产物预置在 `/system/app/<pkg>/oat/` 下，跳过首次启动 dexopt
- 使用 `dexopt` 的 `--compiler-filter=speed` 对系统应用做全量编译（不受空间限制时）
- 通过 `SystemConfig` 的 `fixed-performance` 标签标记关键系统应用，确保它们在首次启动后立即获得最高编译优先级

详见 §16.7（系统启动耗时优化）。
