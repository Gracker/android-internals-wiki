# 1.67 Android 17 PackageManager 架构与性能优化

版本范围是 Android 17（API 37）`android-17.0.0_r1`。签名方案等历史背景可以追溯到旧版本，类、线程、锁和调用关系均以 Android 17 为准。这里讨论包扫描、查询、安装、校验、权限委托和性能诊断；DEX 优化、云端配置文件、DM/SDM 的编译策略分别见 §16.6、§16.9 和 §21.11。

---

## 整体模型

应用进程拿到的 `PackageManager` 是客户端 API。大多数查询最终通过 `IPackageManager` Binder 接口进入 `system_server`，由 `PackageManagerService`（PMS）及其内部组件处理。Android 17 的 PMS 仍是包管理中心，但它已经把安装会话、权限、域名验证、ART 编译等工作交给专门组件。

`PackageManagerService.main()` 完成 PMS 构造后，向 `ServiceManager` 发布两个服务：

- `package`：Java Binder 接口 `IPackageManager`；
- `package_native`：面向原生调用者的 `PackageManagerNative`。

服务构造发生在 `SystemServer` 的 `StartPackageManagerService` 阶段。`system_server` 本身由 Zygote 派生，因此“PMS 扫描发生在 Zygote 启动前”是错误的。包扫描位于 `system_server` 启动关键路径中，扫描结束和 PMS 就绪之前，许多依赖包信息的系统服务还不能正常工作。

Android 17 包管理可以分成六层：

| 层次 | Android 17 代表组件 | 主要职责 |
| --- | --- | --- |
| 客户端 API | `PackageManager`、`ApplicationPackageManager` | 参数整理、Binder 调用、进程内查询缓存 |
| Binder 门面 | `PackageManagerService.IPackageManagerImpl` | 身份与跨用户检查、查询入口、服务路由 |
| 只读查询视图 | `Computer`、`ComputerEngine` | 在一致的包状态快照上执行查询 |
| 安装会话 | `PackageInstallerService`、`PackageInstallerSession` | 会话所有权、文件写入、seal/commit、用户确认、校验 |
| 安装事务 | `InstallingSession`、`InstallPackageHelper` | 复制、解析、scan、reconcile、dexopt、commit、安装后处理 |
| 专项服务 | Permission、ART、`apexd`、`installd`、Rollback 等 | 权限状态、编译、APEX 激活、应用数据、回滚 |

这个划分能解释两个常见现象：

1. `PackageManager` 查询慢，不一定卡在 Binder；服务端快照重建、包可见性过滤或客户端缓存失效都可能参与。
2. 安装进度停住，不一定是 PMS 处理线程在执行 APK 解析；验证器、原生库提取、dexopt、`apexd` 或用户确认都可能尚未完成。

## 线程模型：多个执行域协作

Android 17 没有一条包管理线程包办所有工作。源码中至少有这些明确的执行域：

| 执行域 | 创建位置 | 负责的工作 |
| --- | --- | --- |
| Binder 线程池 | `system_server` Binder 运行时 | 处理同步 IPC 入口 |
| PMS handler | `ServiceThread(TAG, THREAD_PRIORITY_DEFAULT, allowIo=true)` | `PackageHandler` 消息、安装阶段推进、安装后处理 |
| PMS background handler | `ServiceThread("PackageManagerBg", THREAD_PRIORITY_BACKGROUND, allowIo=true)` | 后台消息 |
| PackageInstaller handler | `HandlerThread(TAG)` | 会话回调、会话校验、staged session 管理等 |
| 启动解析线程池 | `ParallelPackageParser` | 最多 4 个前台优先级线程并行解析，结果队列容量 30 |
| 原生库提取线程 | `PackageInstallerSession` | 独立前台优先级线程，避免占用共享 `IoThread` |
| dexopt executor | `DexOptHelper` | 单线程 executor 调用 `ArtManagerLocal` |
| rebootless APEX 安装线程 | `InstallingSession` | 与 apexd 通信，完成后回到 PMS handler |

### 安装不按全局先进先出顺序执行

`InstallingSession.installStage()` 会把 `start()` 投递给 PMS 处理器，`processInstallRequests()` 也会回到这个处理器推进。与此同时：

- 会话的封存、校验与回调在 PackageInstaller 专用处理器上运行；
- 多包会话用多个 `CompletableFuture` 汇总结果；
- 原生库提取使用新线程；
- DEX 优化投递到单线程 executor，完成后再把后续动作投回 PMS handler；
- 某些版本开关下，更新应用的 freeze/stop-and-kill 可以在专用 executor 中并行；
- APEX 与外部服务的交互会离开 PMS handler。

后一个安装请求是否等待前一个请求，取决于它们到达了哪个阶段、是否争用相同包名、是否需要 `installd`、是否等待 dexopt，以及提交区间是否占用锁。源码用 `mInstallingPackages` 拒绝同一包名的并发安装，但这不等价于“设备一次只能处理一个安装任务”。

### Watchdog 的十分钟阈值

PMS 把 handler 注册给 Watchdog，并把超时设为十分钟。源码注释说明，大体积应用的 I/O 可能很长，所以这里比系统常见的一分钟更宽松。这个值只决定何时把线程判定为卡死，不能用作安装耗时预算。

## 三把关键锁

PMS 类注释直接给出了锁协议。这是阅读安装与查询源码时最重要的前置知识。

| 锁 | 保护内容 | 约束 |
| --- | --- | --- |
| `mLock` | 已解析包、Settings 等内存状态 | 高争用，只应短时间持有 |
| `mInstallLock` | 所有 `installd` 访问及相关磁盘重操作 | `installd` 单线程；持有 `mLock` 时禁止再获取它 |
| `mSnapshotLock` | `Computer` 快照引用与失效版本 | 只应在 `snapshotComputer()` 获取；获取顺序早于 `mLock` |

方法名也会表达调用者必须满足的条件：

- `fooLI()`：调用者持有 `mInstallLock`；
- `fooLIF()`：持有 `mInstallLock`，目标包还必须处于冻结状态；
- `fooLPr()`：持有 `mLock`，读内存状态；
- `fooLPw()`：持有 `mLock`，写内存状态。

允许在持有 `mInstallLock` 或 `mSnapshotLock` 时短暂获取 `mLock`，反向顺序会引入死锁风险。分析 traces 时，如果看到 `package` Binder 调用长期阻塞，应区分它是在等待 `mLock`、等待 `mInstallLock`，还是已经离开 PMS 等外部服务。

## 启动扫描：PMS 为什么影响开机

PMS 构造函数记录以下 boot event：

- `BOOT_PROGRESS_PMS_START`
- `BOOT_PROGRESS_PMS_SYSTEM_SCAN_START`
- `BOOT_PROGRESS_PMS_DATA_SCAN_START`
- `BOOT_PROGRESS_PMS_SCAN_END`
- `BOOT_PROGRESS_PMS_READY`

Android 17 由 `InitAppsHelper` 组织扫描：

1. 收集系统分区和活动 APEX 对应的扫描目录；
2. 先扫描 APEX，使 APEX 内 APK 的信息可供后续步骤使用；
3. 扫描 overlay、framework、各分区的 `priv-app` 与 `app`；
4. 初始化 overlay 配置并处理 system package 变化；
5. 扫描 `/data/app`，再修正被用户安装版本覆盖的系统包和 stub package；
6. 写入 Settings，发布就绪状态。

系统目录并不只包括 `/system/app`。`PackagePartitions` 提供的 `system`、`vendor`、`product`、`system_ext`、`odm` 等分区，以及 APEX 映射目录，都可能参与扫描。具体集合取决于设备构建。

### 解析并行，状态接入仍受控

`ParallelPackageParser` 的常量在 Android 17 中是：

- `MAX_THREADS = 4`
- `QUEUE_CAPACITY = 30`
- worker 优先级为 `THREAD_PRIORITY_FOREGROUND`

并行化的部分主要是 APK 解析。解析结果进入后续扫描、Settings 和 `mPackages` 时，仍要遵守 PMS 的锁和状态一致性约束。增加设备 CPU 核数不会让 PMS 自动创建更多解析线程。

### 解析缓存的作用

启动扫描使用带 `PackageCacher` 的 `PackageParser2`。缓存命中可以避免重复解析清单；分区指纹变化、升级、包文件变化或缓存未命中会增加扫描成本。`InitAppsHelper` 会记录：

- 系统/数据分区扫描总耗时；
- 包数量；
- 平均每包耗时；
- 缓存命中数量。

这些设备日志比“某档设备通常需要几秒”的固定经验值更可信。预装包数量、APK 体积、overlay 数量、存储性能、OTA 状态和缓存命中率都会改变结果。

### 首次启动优化的检查顺序

遇到 PMS 启动阶段变慢，可以按以下顺序定位：

1. 对齐 `PMS_SYSTEM_SCAN_START`、`PMS_DATA_SCAN_START`、`PMS_SCAN_END`；
2. 比较系统与 data 的包数量、平均耗时和 cache hit；
3. 在 Perfetto 中检查 `scanApexPackages`、`scanDir [...]`、`parallel parsePackage [...]`；
4. 找到耗时异常的具体 APK，再检查清单规模、split、签名读取、I/O 和 overlay；
5. 如果是 OTA/first boot，再单独分析启动阶段的 boot dexopt，避免把扫描和编译合并成一个数字。

预置 OAT/VDEX 能影响编译阶段，但不会跳过清单解析、签名与包状态接入。源码中也没有 `SystemConfig fixed-performance` 这一类用于保证某应用最高编译优先级的通用标签。

## 包解析：Lite 与 Full 各自解决什么问题

### Lite 解析

`ApkLiteParseUtils` 产出 `ApkLite` 或 `PackageLite`。它适合在会话校验和安装位置判断等阶段快速读取关键字段，包括：

- 包名、拆分包名；
- 版本号、修订号；
- 安装位置、目标 SDK；
- 基础包/拆分包关系与拆分类型；
- 按标志收集的签名信息。

对一个 APK cluster，`parseClusterPackageLite()` 会检查：

- 所有 APK 的包名一致；
- 版本号一致；
- 只有一个基础 APK；
- 拆分包名唯一；
- split 按确定顺序组合。

这一步的目标是尽早拒绝结构错误的安装输入。

### Full 解析

完整安装准备阶段通过 `PackageParser2.parsePackage()` 调用 `ParsingPackageUtils`，返回 `ParsedPackage`。这一步解析完整清单和组件模型，包括活动、Service、Receiver、Provider、权限、feature、进程及库依赖等。

安装流水线中的关键调用是：

```text
PackageParser2.parsePackage()
  -> ParsingPackageUtils.parsePackage()
  -> ParsingPackage.hideAsParsed()
  -> ParsedPackage
```

这段调用只描述完整解析的对象转换。扫描、签名兼容性、shared library 协调、UID 分配和系统状态写入发生在后续阶段。

### 启动扫描和新安装的差异

- 启动扫描：`PackageParser2` 可使用 `PackageCacher`，并由 `ParallelPackageParser` 并行调度；
- 新安装会话：先用 `ApkLiteParseUtils` 校验会话内容，进入 `InstallPackageHelper.preparePackage()` 后再用不带缓存的 preparing parser 做完整解析。

“Android 17 的包解析入口只有 `ParsingPackageUtils`”不够精确。它是完整解析实现的一部分；外层的轻量校验、`PackageParser2`、缓存和扫描调度同样决定行为与耗时。

## APK 签名：v4 不能脱离 v2/v3

Android 17 的 `ApkSignatureVerifier.verifySignaturesInternal()` 先尝试 v4；找不到 v4 时，再根据允许的最低方案检查 v3、v2 和 v1。这个顺序容易引出一个误解：v4 并非独立替代 v2/v3 的最高优先级签名。

源码对 v4 的定义很明确：v4 是附加签名，必须借助 v2 或 v3 校验其证书与摘要。验证器还会比较：

- v4 签名者与 APK 内 v2/v3 signer；
- v4 记录的 APK 摘要与 v2/v3 content digest；
- v3 的 proof-of-rotation 信息（存在时）。

各方案在 Android 17 安装路径中的角色可以概括为：

| 方案 | 主要能力 | Android 17 校验要点 |
| --- | --- | --- |
| v1 | JAR 条目签名 | 仅在目标包允许且更高方案不存在时回退 |
| v2 | APK 全文件内容签名 | 校验 signing block 和内容摘要 |
| v3/v3.1 | v2 能力加密钥轮换 | 保留当前与历史 signer 关系 |
| v4 | 为增量/流式安装提供独立 `.idsig` 数据 | 必须与 APK 内 v2/v3 证书和摘要对上 |

签名校验耗时受 APK 大小、存储吞吐、页缓存、签名方案和是否需要完整内容校验影响。源码没有给出适用于所有设备的固定耗时，应使用 `verifyV4`、`verifyV3`、`verifyV2`、`strictJarFileCtor` 等 trace slice 在目标设备测量。

## PackageInstallerSession：用字段表达状态

Android 17 的 `PackageInstallerSession` 没有一组 `INIT -> SEALING -> ...` 的单一枚举。它用多个字段表达不同维度：

- `mPrepared`
- `mSealed`
- `AtomicBoolean mCommitted`
- `mDestroyed`
- `mStageDirInUse`
- staged session 专用的 `mSessionReady`、`mSessionApplied`、`mSessionFailed`
- 失败码与失败消息
- 父/子会话关系

用阶段理解流程仍然有帮助，但排障时要映射到这些实际字段：

| 阶段 | 关键事实 |
| --- | --- |
| 创建并写入 | installer 拥有会话，可写 base/split/元数据 |
| seal | 禁止继续修改；多包父会 seal 所有 child |
| validate and commit | 校验 APK/APEX、`DataLoader`、文件一致性，再原子设置 `mCommitted` |
| 用户确认 | 需要时发送确认 Intent，收到允许后重新处理 `MSG_INSTALL` |
| verify | 开发者验证、包验证、rollback 验证、原生库提取等异步工作 |
| install | 非 staged session 进入 `InstallingSession` |
| 就绪/已应用/失败 | 阶段式会话的跨重启状态 |
| destroy/abandon | 阻止继续使用暂存文件并清理会话 |

### `commit()` 的处理步骤

`commit()` 的主要步骤是：

1. 校验 status receiver；新兼容规则要求可变 `PendingIntent`；
2. `markAsSealed()`，多包会话同时 seal children；
3. 投递 `MSG_ON_SESSION_SEALED`；
4. 阻塞写入封存状态，避免后续 hard link 被篡改；
5. `streamValidateAndCommit()` 校验输入并设置 `mCommitted`；
6. 投递 `MSG_INSTALL`；
7. 如需用户确认，等待结果后再次进入 `MSG_INSTALL`；
8. 解析 APK，执行可配置的开发者验证，再进入通用会话验证；
9. 非 staged 安装在验证完成后创建 `InstallingSession`。

这里的“committed”只表示会话输入已确认并进入安装流程，不表示包状态已经写入 PMS，也不表示应用已经可启动。

### 原生库提取为什么另开线程

非阶段式 APK 在通用验证前可能提取 native libraries。Android 17 源码明确创建名为 `extractNativeLibraries` 的前台优先级线程，因为提取可能是长时间 I/O，不能阻塞共享 `IoThread`。如果安装在验证阶段停留较久，应把 ABI、压缩方式、存储吞吐和可用空间纳入检查。

## 非阶段式 APK 安装：四阶段原子事务

完成会话验证后，`InstallingSession.installStage()` 把安装起点投递给 PMS handler。文件复制完成后，`InstallPackageHelper.installPackagesTraced()` 处理一个或多个包。

AOSP 注释把事务明确定义为四个阶段：

1. **准备（Prepare）**：分析现有安装状态、完整解析新包、完成初步校验；
2. **扫描（Scan）**：根据上下文生成候选 `PackageSetting`、ABI、appId 等扫描结果；
3. **协调（Reconcile）**：把所有候选包与当前系统状态一起校验，包括签名、shared library 和多包间冲突；
4. **提交（Commit）**：写入 `mPackages`、Settings 等系统状态。

任何阶段失败，当前请求中的所有包都会失败。`Commit` 是设计上唯一允许修改包系统状态的阶段，所以可预见错误应在此前被发现。源码仍留有警告：commit 中途抛出异常可能造成不一致，这个异常窗口还没有被完全消除。

### Android 17 的实际顺序

把中间的文件与编译步骤补上后，常见路径是：

```text
PackageInstallerSession
  -> 会话校验 / 用户确认 / 安全验证
  -> InstallingSession.installStage()
  -> 复制或复用暂存文件
  -> Prepare
  -> Scan
  -> Reconcile
  -> 重命名代码路径
  -> 准备应用数据
  -> 按需执行 DEX 优化
  -> 冻结包
  -> Commit
  -> 提交后处理应用数据、权限、广播与恢复
```

Android 17 先启动 `performDexoptIfNeededAsync()`，等待相关 future 后再回到 PMS 处理线程执行 commit。dexopt 在独立 executor 上运行，但当前安装的后续动作仍要等它完成。普通 DEX 优化失败会生成失败结果，源码明确要求不要因此让应用安装失败。

### 锁在四阶段中的位置

- `Prepare` 和 `Scan` 会短暂读取现有状态；
- `Reconcile` 先获取 `mInstallLock`，再短暂持有 `mLock`；
- code path rename 在 `mInstallLock` 下完成；
- app data 操作通过 `mInstallLock` 约束 `installd`；
- `Commit` 在 `mInstallLock` 与 `mLock` 保护下更新包状态；
- post-commit 再处理数据、权限、广播、备份恢复等动作。

`mInstallLock` 的主要目的在于串行保护 `installd`，不是把所有解析、验证与编译都包进同一临界区。

### 多包事务的边界

多包会话把 child sessions 聚合为一次请求，Prepare/Scan/Reconcile/Commit 以同一组包进行，任一 child 失败都会使整组失败。这里还有两个边界：

- 非阶段式多包安装不能混合 APK 与 APEX；
- rebootless APEX 由 `apexd` 先处理；PMS 与 `apexd` 之一发生异常时，原子性仍是源码列出的待改进项。

## dexopt：异步执行不等于安装无需等待

Android 17 的 `DexOptHelper` 通过 `ArtManagerLocal.dexoptPackage()` 请求 ART Service。调用被放到单线程 executor 中，避免直接占住 PMS handler。`InstallPackageHelper` 汇总 future，完成后把 `doPostDexopt()` 投回 PMS handler。

这几个结论需要同时成立：

- PMS 已把编译控制面交给 ART Service；
- 当前实现中，`ArtManagerLocal.dexoptPackage()` 仍可能在 DEX 优化执行器内同步等待；
- 安装事务通常等待对应 future 后再提交；
- instant app、APEX、debuggable 或 incremental 等路径可能跳过编译，或使用 `noop` compiler filter；
- ART 服务还会根据 compilation reason、filter、profile 和现有产物决定是否执行编译。

看到 PMS 处理线程空闲时，仍不能排除安装正在等待 DEX 优化。应同时观察 `dexopt` trace、ART 服务日志与会话状态。编译策略和 DM/SDM 文件校验见 §16.6、§16.9、§21.11。

## Staged Install：跨重启应用 APK/APEX

`isStaged=true` 的会话在当前启动周期完成重启前验证，标记为就绪，重启后再应用。它主要服务于需要跨重启保证一致性的 APK/APEX 更新。

### 提交前

`PackageSessionVerifier` 对 staged session 执行：

- 通用 APK 校验；
- APEX 更新权限与 container signature 校验；
- 多个 staged session、rollback 和包重叠冲突检查；
- 把 APEX 会话提交给 `apexd`；
- 设备支持时启用文件系统检查点；
- 检查通过后设置 `mSessionReady`，再通知 apexd session ready。

### 重启后

`StagingManager` 恢复会话：

1. 读取 checkpoint 状态；
2. 核对 `apexd` 是否已激活 APEX；
3. 处理 APK-in-APEX 的安装结果和回滚用户数据；
4. 安装会话中的普通 APK；
5. 标记会话已应用；
6. 启动完成后把成功状态通知 `apexd`。

失败时，系统可能：

- 标记会话失败；
- 中止文件系统检查点；
- 请求 apexd revert active sessions；
- 重启回到安全状态。

### 与 A/B OTA 的边界

staged install 不属于通用 A/B OTA 写槽流程。纯 APK 阶段式会话也可以跨重启应用，不需要 `update_engine` 切换槽位。含 APEX 的会话通过 `apexd` 激活模块，并可结合 filesystem checkpoint 与 `RollbackManager`。整机 OTA 的槽位管理属于另一套更新体系。

`PackageInstallerSession` 也没有 `StagedInstallSession` 子类；它创建一个实现 `StagingManager.StagedSession` 接口的适配对象，并使用 `mSessionReady/mSessionApplied/mSessionFailed` 保存状态。

## 两类安全校验不要混在一起

### APK 加密签名

v1/v2/v3/v4 验证回答的是：

- APK 内容有没有被改动；
- signer 是谁；
- 更新包与已安装包的签名或轮换关系是否兼容。

它不判断应用行为是否恶意。

### 安装验证器

`VerifyingSession` 可以向系统配置的必要验证器发送 `ACTION_PACKAGE_NEEDS_VERIFICATION`，也可匹配 APK 声明的 sufficient verifier。Android 17 还提供受 feature flag 和设备配置控制的 developer verification service，执行位置早于通用会话验证。

AOSP 没有把 required verifier 硬编码为 Play Protect。带 GMS 的产品可以由 Google 组件实现，AOSP 或 OEM 产品也可以配置其他系统验证器。非 Play 渠道同样可能触发系统验证；ADB 是否校验还受安装标志、全局设置和用户限制影响。

### 超时与默认决策

`VerificationUtils` 的 Android 17 默认下限是：

- 常规校验：10 秒；
- 满足条件的流式校验：3 秒。

`Settings.Global` 可以增大超时，源码用 `Math.max()` 阻止把它降到默认值以下。超时后允许还是拒绝，由 `PACKAGE_VERIFIER_DEFAULT_RESPONSE`、用户限制和安装场景共同决定。不能把“10 秒后自动放行”当成固定规则。

排障时应把等待分成三段：

1. 开发者验证服务；
2. `ACTION_PACKAGE_NEEDS_VERIFICATION` required/sufficient verifier；
3. 启用回滚与会话自身校验。

## 安装来源：由调用者与系统共同记录

`PackageInstallerService.createSessionInternal()` 会检查：

- 跨用户权限与用户安装限制；
- caller UID 与 installer package 的归属；
- `AppOpsManager.checkPackage()`；
- caller 是否具有 `INSTALL_PACKAGES` 等权限；
- installer 是否有权替另一个包设置安装者身份；
- APEX、staged、rollback、install reason 等专项权限。

会话随后构造 `InstallSource`，分别记录发起包、来源包、登记安装者和更新所有者：

- 谁发起了操作；
- 内容最初来自谁；
- 谁被记录为安装者；
- 后续更新由谁负责。

manifest 中没有供应用自行声明 `android:installerPackageName` 的合法机制。安装者身份来自 `PackageInstaller` 调用与系统校验，应用不能在自己的清单中指定可信安装来源。

## 权限服务：PMS 入口后的 `AccessCheckingService`

Android 17 不再以“PMS 内一张已授予权限表”描述权限调用关系。

`AccessCheckingService.onStart()` 创建 `PermissionService`，并把它注册为 `PermissionManagerServiceInterface`。随后 `PermissionManagerService` 作为 Binder 与 LocalServices 门面，把 `checkPermission()`、`checkUidPermission()` 委托给该实现。

常见调用可以概括为：

```text
PMS.checkPermission(package, permission, user)
  -> PermissionManagerService.checkPermission(
       package, permission, persistentDeviceId, user)
  -> PermissionService.checkPermission(...)
  -> filtered package snapshot + AccessState permission flags
```

这段调用里有两个容易漏掉的维度：

- **包可见性**：按包名检查权限时，`PermissionService` 通过带调用方 UID 与 userId 的 filtered `PackageManagerLocal` snapshot 查包；调用者看不到目标包时会得到 denied。
- **设备维度**：Android 17 的接口携带持久设备 ID，权限状态不再只能理解为 `(appId, userId, permission)` 三元组。

### 权限状态如何读写

`AccessCheckingService` 持有当前 `AccessState`。读取使用当前状态；写入时在 `stateLock` 下复制出可变状态，更新并持久化后替换引用。这里没有 `mGrantedPermissions` 查询缓存。

包安装完成时，PMS 调用权限服务的 package-installed hook，让权限策略根据声明、保护级别、目标 SDK、用户、角色、allowlist、既有授权和设备策略更新状态。normal permission 通常可在安装策略中授予；dangerous permission 不能简单归纳为“安装时一律不授予”，更新、恢复、预授权、角色与企业策略都可能影响结果。

任何权限性能结论都应基于目标设备测量。首次启动会处理大量包，但源码没有“每包固定 5–10 ms”的保证。

## 查询路径：快照、可见性与多级缓存

### 服务端 `Computer` 快照

PMS 的读查询大量使用 `snapshotComputer()`。它维护：

- 当前缓存的 `Computer`；
- 快照版本；
- 待处理的失效版本。

版本匹配时直接复用旧快照。版本失效时，只允许一个调用者在 `mSnapshotLock` 下重建；等待者再次检查版本，避免重复构造。若调用线程已经持有 `mLock`，默认 API 可返回实时 `Computer`，因为该线程可能刚修改状态、尚未发出 snapshot invalidation。

`Computer` 接口要求查询函数只读取快照数据，不能修改它。普通读路径因此可以在一致视图上工作，并减少长期占用 PMS 高争用锁的需要。

### 客户端缓存

Android 17 有这些可从源码确认的 `PropertyInvalidatedCache`：

| API | 缓存 | 最大条目数 | key |
| --- | --- | ---: | --- |
| `getApplicationInfo` | `PackageManager.sApplicationInfoCache` | 2048 | package + flags + user |
| `getPackageInfo` | `PackageManager.sPackageInfoCache` | 2048 | package + flags + user |
| `getPackagesForUid` | `ApplicationPackageManager.sGetPackagesForUidCache` | 1024 | uid |
| `queryIntentActivities` | `ApplicationPackageManager.sQueryIntentActivitiesCache` | 1024 | intent + type + flags + user |

前两项会缓存空值；`queryIntentActivities` 缓存受 feature flag 控制。它们不是某个 `ApplicationPackageManager` 实例中的通用 LRU 缓存。

包或权限状态改变时，系统通过共享 invalidation property 使其他进程的旧缓存失效。`AppsFilterImpl` 在包可见性变化时还会主动失效 package info、packages-for-uid、query-intent-activities 和 AppOps 包检查缓存。

### 包可见性属于查询语义

Android 11 之后的 package visibility 规则在 Android 17 继续生效。`ComputerEngine` 会用 `AppsFilter.shouldFilterApplication()` 过滤 package info、application info 和 Intent 查询结果。因此：

- 查不到包不一定表示系统未安装；
- 相同 API 在不同调用方 UID 下可以得到不同结果；
- userId、标志、即时应用、共享库和跨配置文件条件也会改变结果。

系统服务使用 `PackageManagerInternal` 或 `PackageManagerLocal` 可以省去 Binder，但调用者必须明确选择过滤或 unfiltered snapshot，并保留相应的用户、flags 和安全检查。不能仅为了速度把受过滤的公开查询换成未过滤的内部查询。

## Split APK 与动态特性模块

Play Feature Delivery 或其他分发端最终把基础/拆分 APK 写入标准 `PackageInstallerSession`。PMS 不负责在安装时“为 split 分配资源 ID”；资源 ID 和拆分元数据由构建产物决定。

会话校验会检查：

- 包名一致；
- 版本号一致；
- signer 完全一致；
- split name 不重复；
- 完整安装包含基础包；
- 必需 split type 已满足；
- 继承现有安装模式与已安装的基础包/拆分包相容；
- 被移除的 split 存在于当前安装；
- 包名、应用包名与会话参数一致。

之后的完整解析、scan、reconcile 和 DEX 优化仍按普通安装规则执行。安装耗时取决于新增 split 的体积、native libraries、DEX、签名、验证器和编译策略，不能给出跨设备通用的秒数。

ART 支持一个包包含多个 DEX code container。PMS 的清单解析不会把所有 `classes*.dex` 的偏移与大小写入 `AndroidPackage`，也不能保证每个 DEX 都对应一组独立 `.odex/.vdex` 文件。具体编译单元和产物位置由 ART Service、class loader context、ISA、compiler filter 及存储布局共同决定。

App Bundle 与按需交付的分发侧机制见 §25.8。

## UID、应用数据与沙箱

安装扫描阶段会为新包预先注册 appId；reconcile 和提交成功后，包状态获得稳定的 appId。多用户设备上的 Linux UID 由 `userId` 与 appId 组合。

应用数据操作由 PMS 的 `AppDataHelper` 经 `Installer` 调用 `installd`，包括创建或修正 DE/CE 数据目录、设置 owner、生成 seInfo 对应标签等。相关调用受 `mInstallLock` 约束。

安全边界来自多层共同作用：

- Linux UID/GID；
- SELinux 域与文件标签；
- 挂载/存储隔离；
- permission 与 AppOps；
- 包可见性；
- isolated process、SDK 沙箱等专项 UID 模型。

不能把应用沙箱的运行时开销归结为一个“SELinux 检查延迟”数字。文件系统、策略缓存、系统调用类型和工作负载都会影响结果，关闭其中任一安全机制也不属于应用可用的性能选项。

## 更新、冲突和应用冻结

### 包名相同不等于可以覆盖

更新会在 Prepare/Reconcile 阶段检查：

- 已安装包是否允许替换；
- 新旧签名者或签名轮换谱系是否兼容；
- 版本号与降级策略；
- 共享用户、共享库、静态 SDK 库约束；
- 系统应用、更新所有者、安装者权限；
- target SDK、ABI、数据模型及其他兼容规则。

签名不兼容常见为 `INSTALL_FAILED_UPDATE_INCOMPATIBLE`；重复包或会话内冲突也有各自错误码。不要只根据 `mPackages` 中是否已有包名判断更新可行性。

### freeze 的用途

更新进入 commit 前会冻结目标包，停止或杀死相关进程，避免进程继续使用即将替换的代码和资源。Android 17 在部分开关启用时，会在专用线程池并行停止和杀死多个包的进程，再回到 PMS handler commit。

安装耗时里出现数秒停顿时，还应检查目标进程或共享 UID 的同组进程是否退出。PMS 为普通包与共享 UID 路径设置了不同的等待策略，超时后会强制 kill。

### 应用休眠不是安装状态

Android 17 的服务类名是 `AppHibernationService`，PMS 只持有 `AppHibernationManagerInternal` 接口。休眠状态由该服务管理，不能描述成 PMS 的 `AppHibernManager`。休眠后的通知、任务、权限撤销、存储回收与首次启动行为由多个服务和产品策略共同决定，不能简化为安装队列规则。

## 性能诊断：从阶段和证据入手

### 先判断慢在哪个边界

| 现象 | 优先查看 |
| --- | --- |
| `PackageManager` API 偶发长尾 | Binder 等待、`mLock`、snapshot rebuild、visibility filter、cache invalidation |
| 开机 PMS 很慢 | 系统/数据分区扫描日志、cache hit、并行解析、APEX/overlay、OTA/first boot |
| 提交后长时间无结果 | 用户确认、开发者验证器、必要验证器、回滚、原生库提取 |
| `installStage` 后停住 | `copyApk`、存储空间、`installd`、同包并发、PMS handler |
| `reconcilePackages` 很慢 | 多包数量、shared library、签名、Settings 状态、锁竞争 |
| `dexopt` 很慢 | compiler filter、profile/DM/SDM、code size、ISA、ART 服务与 `artd` |
| 阶段式会话重启后失败 | `apexd` 状态、检查点、回滚、APEX 内 APK、会话的就绪/已应用/失败状态 |

- `copyApk`
- `installPackages`
- `preparePackage`

- `scanApexPackages`
- `parallel parsePackage [...]`

`installStage*` 和 `queueInstall` 使用 async trace，其 cookie 用于把跨 handler 的起止事件配对；其他名称多为当前调用栈上的普通片段。它们能把“安装慢”分成文件、解析、校验、编译、提交和安装后处理。定位阶段后，再检查该阶段的锁与外部调用，比只看 PackageInstaller 界面的百分比更有效。

### 基础命令

先用只读命令核对设备和包状态：

```bash
adb shell getprop ro.build.version.sdk
```

## 常见误区校正

| 误区 | Android 17 源码结论 |
| --- | --- |
| PMS 在 Zygote 前扫描预装包 | PMS 由 `SystemServer` 启动，`system_server` 是 Zygote 派生进程 |
| 所有安装严格按 PMS 处理线程先进先出串行执行 | 多个 handler、工作线程和 future 协作；锁与同包保护只约束相应阶段 |
| v4 可独立替代 v2/v3 | v4 是附加签名，必须与 v2/v3 证书和摘要对应 |
| session 有一条固定枚举状态机 | `PackageInstallerSession` 用多个布尔值、原子字段和 staged 状态表达 |
| staged install 就是写 B 槽 | staged APK/APEX 由 `StagingManager`、`apexd`、checkpoint 和 rollback 协作；整机 A/B OTA 另有体系 |
| verifier 就是 Play Protect | AOSP 使用配置的系统验证器；不同产品实现不同 |
| installer 可在 manifest 自报 | installer 身份由 PackageInstaller 调用、caller UID、AppOps 和权限校验确定 |
| 权限检查只读 `mGrantedPermissions` | Android 17 经 PermissionManagerService 委托到 PermissionService 和 AccessState |
| 客户端有通用 `mApplicationInfoCache` LRU | 具体实现是静态 `PropertyInvalidatedCache`，key 与失效规则按 API 定义 |
| PMS 给 split 分配资源 ID | 构建产物定义资源；PMS 校验 base/split 的一致性 |
| 预置 OAT/VDEX 可跳过包扫描 | 它影响编译，不会取消清单解析和包状态接入 |

## 小结

Android 17 的包管理性能来自明确的阶段分工：

- 启动时，4 线程解析池和 `PackageCacher` 缩短 APK 扫描，但 Settings 与包状态接入仍受锁约束；
- 查询时，`Computer` 快照减少高争用锁读取，客户端 `PropertyInvalidatedCache` 减少 Binder 往返；
- 安装时，session、验证器、PMS handler、原生库线程、ART executor、`installd` 和 `apexd` 分别负责不同工作；
- 一致性由 lite/full 解析、签名、Prepare/Scan/Reconcile/Commit、freeze 与三把锁共同维持；
- 阶段式安装通过重启前验证、`apexd`、检查点和回滚机制处理跨重启更新。

诊断 PackageManager 问题时，应先确定当前处于扫描、会话、验证、复制、四阶段事务、dexopt、提交或安装后处理中的哪一步，再检查对应线程、锁和外部服务。这样能把笼统的“PMS 慢”缩小到可验证的源码路径。
