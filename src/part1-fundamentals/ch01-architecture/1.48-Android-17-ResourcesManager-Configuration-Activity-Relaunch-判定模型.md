# 1.48 Android 17 ResourcesManager/Configuration 与 Activity Relaunch 判定模型

> **版本边界**：本节只讨论 Android 17 / API 37，源码基线固定为 `android-17.0.0_r1`。
>
> **审计说明**：2026-07-27 deep-review 已移除早期占位稿中的伪代码、未来源化性能数字，以及“Android 17 中 `shouldRelaunchLocked()` 不存在”的错误注入；保留下列可由 DeepResearch 一手源码摘录支撑的链路与策略。

## 要点

Android 17 的 Configuration 变更不是由应用侧 `ResourcesManager` 主动“发现后通知 ATMS”，而是由 ATMS / WindowManager 在全局或窗口容器配置变化时更新系统配置，再按进程与 Activity 分发。核心路径可以概括为：

1. **全局配置更新**：`ActivityTaskManagerService.updateConfigurationLocked()` 先 `deferWindowLayout()`，再进入 `updateGlobalConfigurationWithTransition()`；其中 `getGlobalConfiguration().diffPublicOnly(values)` 用于判断公开配置位是否变化，Shell Transitions 开启时创建 `TRANSIT_CHANGE` 并在各 `DisplayContent` 上记录 known config changes。
2. **进程级分发**：`updateGlobalConfigurationLocked()` 写入 `mTempConfig.seq = increaseConfigurationSeqLocked()`，同步调用 system_server 内 `mSystemThread.applyConfigurationToResources(mTempConfig)`，随后遍历 `mProcessMap`，对每个 `WindowProcessController` 触发 `onConfigurationChanged()` / `dispatchConfiguration()`。
3. **客户端资源应用**：非 cached 进程收到 `ConfigurationChangeItem`；`preExecute()` 更新 pending configuration，`execute()` 进入 `ActivityThread.handleConfigurationChanged()`，再由 `ConfigurationController.handleConfigurationChangedInner()` 调用 `ResourcesManager.applyConfigurationToResources()` 与 `ComponentCallbacks2`。
4. **Activity 级 relaunch 判定**：可见 Activity 走 `ActivityRecord.ensureActivityConfiguration()`；若配置变化不能被 mask 吃掉，则 `shouldRelaunchLocked(changes, changesConfig)` 返回 true，并进入 `relaunchActivityLocked()`。

```text
ATMS.updateConfigurationLocked
  └─ updateGlobalConfigurationWithTransition
       ├─ diffPublicOnly(values)
       ├─ TransitionController.createTransition(TRANSIT_CHANGE) [Shell transitions enabled]
       └─ updateGlobalConfigurationLocked
            ├─ mTempConfig.updateFrom(values)
            ├─ mTempConfig.seq = increaseConfigurationSeqLocked()
            ├─ mSystemThread.applyConfigurationToResources(mTempConfig)
            ├─ for each WindowProcessController: app.onConfigurationChanged(mTempConfig)
            │    └─ dispatchConfiguration(config)
            │         ├─ cached 进程短路
            │         └─ scheduleClientTransactionItem(ConfigurationChangeItem)
            └─ mRootWindowContainer.onConfigurationChanged(mTempConfig)
  └─ ensureConfigAndVisibilityAfterUpdate
       └─ ActivityRecord.ensureActivityConfiguration
            └─ shouldRelaunchLocked(changes, changesConfig)
                 └─ relaunchActivityLocked(...) [仅当仍有未豁免 changes]
```

## `shouldRelaunchLocked`：从 manifest mask 到 AppCompat 策略的 7 层判定

`ActivityRecord.shouldRelaunchLocked(int changes, Configuration changesConfig)` 在 `android-17.0.0_r1` 中存在，关键逻辑位于 `frameworks/base/services/core/java/com/android/server/wm/ActivityRecord.java` 约 8740-8798 行。判定不是“旧 diff 与新 diff 直接相减”，而是先构造 `skipRelaunchConfigMask`，再用 `changes & ~skipRelaunchConfigMask` 判断是否仍有需要重建的配置位。

```java
int skipRelaunchConfigMask = info.getRealConfigChanged();
if ((skipRelaunchConfigMask & CONFIG_RESOURCES_UNUSED) != 0) {
    return false;
}

// targetSdk<O + VR UI mode、Desk docking、PiP density、DisplayCompat、RRO 等继续叠加 mask。
if (getWindowingMode() == WINDOWING_MODE_PINNED) {
    skipRelaunchConfigMask |= CONFIG_DENSITY;
}

skipRelaunchConfigMask |= mAppCompatController.getDisplayCompatPolicy()
        .getDisplayCompatModeConfigMask();

if ((skipRelaunchConfigMask & CONFIG_ASSETS_PATHS) == 0
        && (changes & CONFIG_ASSETS_PATHS) != 0
        && !mAppCompatController.getResourceOverlayPolicy()
                .doResourceOverlayChangesAffectActivity()) {
    skipRelaunchConfigMask |= CONFIG_ASSETS_PATHS;
}

skipRelaunchConfigMask &= (~mAppCompatController.getRecreateOnConfigChangePolicy()
        .getRecreateConfigMask());
return (changes & (~skipRelaunchConfigMask)) != 0;
```

完整顺序如下：

| 层级 | 策略 | Android 17 语义 |
|---|---|---|
| 0 | `CONFIG_RESOURCES_UNUSED` | Activity 声明完全不依赖资源时直接 `return false`，后续 mask 不再参与。 |
| a | `info.getRealConfigChanged()` | manifest `android:configChanges` 是基础豁免集。 |
| b | targetSdk < O + VR UI mode | 仅 VR UI mode 切换时，为旧 target 兼容豁免 `CONFIG_UI_MODE`。 |
| c | Desk docking | Dock 模式且包内无 desk 资源时，豁免对应 `CONFIG_UI_MODE`。 |
| d | PiP density | `getWindowingMode() == WINDOWING_MODE_PINNED` 时无条件加入 `CONFIG_DENSITY`，避免 PiP 窗口 density 变化导致完整 relaunch。 |
| e | DisplayCompatPolicy | 游戏 display move 可豁免 `DENSITY|TOUCHSCREEN|COLOR_MODE`；computer-control 外接显示器路径可豁免 `TOUCHSCREEN|COLOR_MODE|NAVIGATION|KEYBOARD_HIDDEN|KEYBOARD`。普通 app 未命中这些状态时该层通常为 0。 |
| f | ResourceOverlayPolicy | RRO 资产路径变化若不影响当前 Activity，则把 `CONFIG_ASSETS_PATHS` 加入 skip mask。 |
| g | RecreateOnConfigChangePolicy | 反向剥离：`skipMask &= ~recreateMask`。如果包内存在对应备用资源，即使 manifest 声明了跳过，也可能被强制 recreate。 |

这个模型的关键结论是：**Android 17 更像是在“先尽量热更新，再把确实需要重建的 bit 挖出来”**。最终是否 relaunch 由 `changes` 中剩余未被豁免的 bit 决定，而不是由单一配置项或固定三段式策略决定。

## 性能相关但有边界的源码事实

下列优化点来自 DeepResearch 中的 `android-17.0.0_r1` 源码摘录；本节只给出机制收益，不再保留早期占位稿中的百分比性能表，因为那些数字没有对应 Perfetto / benchmark 证据。

| 优化点 | 源码位置 | 可支撑的结论 |
|---|---|---|
| cached 进程短路 | `WindowProcessController.dispatchConfiguration()` 约 1957-1964 行 | cached 进程只记录 `mHasCachedConfiguration`，不立即下发 `ConfigurationChangeItem`，屏幕旋转等配置变化不会唤醒所有 cached app。 |
| `seq` 单调递增 | WPC dispatch + `Configuration.isOtherSeqNewer` | 服务端递增 seq，客户端可丢弃乱序旧配置，避免 stale configuration 覆盖新状态。 |
| `diffPublicOnly` 等价优化 | `ConfigurationController` 约 201 行 | 公开配置未变时可避免回调应用 `ComponentCallbacks2`，减少内部字段变化对应用代码的打扰。 |
| resize-only 保留窗口 | `ActivityRecord.ensureActivityConfiguration()` 约 8675-8680 行 | `isAppResizeOnly` 可影响 `preserveWindow`，使纯尺寸变化尽量保留窗口、IME/动画/滚动状态。 |
| TextLayout cache 精准失效 | `ConfigurationController.freeTextLayoutCachesIfNeeded(configDiff)` | 只有 fontScale 等相关变化才清理文本布局缓存，避免无关配置变化扩大成本。 |
| Theme 按需 rebase | `ConfigurationController` 约 223-230 行 | 只有 theme 的 `getChangingConfigurations()` 命中 config diff 时才 rebase。 |
| drag-resize relaunch postpone | `relaunchActivityLocked()` 中 `Flags.improveFluidResizingPerformance` gate | 连续 resize 场景可合并 relaunch config flags 到最后一帧，减少中间帧反复 relaunch。 |

## AppCompat 三个策略的读法

### DisplayCompatPolicy：普通 app 多数时候不是“免费跳过 relaunch”

`AppCompatDisplayCompatPolicy.getDisplayCompatModeConfigMask()` 是双路径互斥：

- `mDisplayChangedWithoutRestart`：走静态 display compat mask，且 DeepResearch 确认为 `CATEGORY_GAME` 游戏场景服务，mask 为 `CONFIG_DENSITY | CONFIG_TOUCHSCREEN | CONFIG_COLOR_MODE`。
- `mDisplayChangedForComputerControlWithoutRestart`：走 computer-control 路径，mask 为 `CONFIG_TOUCHSCREEN | CONFIG_COLOR_MODE | CONFIG_NAVIGATION | CONFIG_KEYBOARD_HIDDEN | CONFIG_KEYBOARD`，不包含 `CONFIG_DENSITY`。

因此，不能把该策略泛化为“Android 17 对所有外接显示器迁移都跳过重建”。普通 app 未命中特定 compat 状态时，这一层返回 0。

### ResourceOverlayPolicy：RRO 变化要看是否影响当前 Activity

`AppCompatResourceOverlayPolicy.doResourceOverlayChangesAffectActivity()` 会比较 `applicationInfo.overlayPaths` 的新增/删除路径，并通过 `OverlayManagerInternal.getOverlayConstraints(path, userId)` 查询约束。只有约束匹配当前 Activity 时才认为 RRO 变化会影响该 Activity；否则调用方可把 `CONFIG_ASSETS_PATHS` 加入 skip mask。

这个设计的收益是：RRO 切换不再等价于所有 Activity 必然 relaunch；但它也带来一个同步查询成本，尤其是首次或 overlay 路径变化较多时。

### RecreateOnConfigChangePolicy：less-recreation 不是“永远少重建”

`AppCompatRecreateOnConfigChangePolicy.getRecreateConfigMask()` 的语义容易误读。它并不是单纯扩大 skip mask，而是在满足 feature flag 与 `ActivityInfo.SKIP_ACTIVITY_RECREATION_ON_CONFIG_CHANGE` opt-in 后，扫描 APK 资源配置并生成 `recreateMask`。调用方执行：

```java
skipRelaunchConfigMask &= ~recreateMask;
```

也就是说，如果 Activity 声明“我自己处理某类 configChanges”，但包内事实上存在该维度的备用资源，系统仍可能把该 bit 从 skip mask 中挖掉，强制 recreate 以加载正确资源。这是兼容性兜底，不是无条件的 View hierarchy 复用策略。

## 客户端 `ResourcesManager.applyConfigurationToResources` 的边界

客户端侧 `ResourcesManager.applyConfigurationToResources()` 大致流程是：先用 `mResConfiguration.isOtherSeqNewer(config)` 与 compat 变化做短路，再 `mResConfiguration.updateFrom(config)`；若 `CONFIG_ASSETS_PATHS` 变化则应用 pending app info updates；随后更新 system configuration 与 `ApplicationPackageManager.configurationChanged()`，并倒序遍历 `ResourcesImpl` 应用新配置。

这里的“倒序遍历”不是新的业务策略，而是资源实现集合的维护细节：已经被 GC 清掉的 weak ref 可以在循环中移除，避免无效对象长期滞留。
