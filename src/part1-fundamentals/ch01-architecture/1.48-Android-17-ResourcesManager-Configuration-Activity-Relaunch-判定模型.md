# 1.48 Android 17 ResourcesManager/Configuration 与 Activity 重建判定模型

一次旋转、窗口缩放、显示屏迁移或外设变化，可能更新已有 Activity，也可能触发完整重建。`ResourcesManager` 负责应用进程里的资源状态，重建判定发生在 system_server 的 `ActivityRecord`；应用侧不会先“发现变化”再通知 ATMS。

以下分析以 Android 17 / API 37 / AOSP `android-17.0.0_r1` 为锚点，聚焦 `ActivityRecord.ensureActivityConfiguration()` 与 `shouldRelaunchLocked()`。进程级 Configuration 派发和资源缓存见 [1.46 Android 17 ResourcesManager 与 Configuration 变更性能](1.46-resourcesmanager-configuration-performance.md)，应用适配与性能测试见 [1.24 ResourcesManager 与 Configuration 变更性能](24-resourcesmanager-configuration-performance.md)。

## 进程配置与 Activity 配置是两条路径

下图表达职责关系。客户端 Binder 执行与 system_server 容器更新可能交错。

```text
ActivityTaskManagerService.updateGlobalConfigurationLocked()
  ├─ WindowProcessController
  │    └─ ConfigurationChangeItem
  │         └─ ConfigurationController
  │              └─ ResourcesManager.applyConfigurationToResources()
  └─ RootWindowContainer / Display / Task
       └─ ActivityRecord 的合并 Configuration
            └─ ensureActivityConfiguration()
                 ├─ ActivityConfigurationChangeItem
                 └─ ActivityRelaunchItem
```

进程级 `ConfigurationChangeItem` 更新全局资源和非 Activity 组件。Activity 还会叠加窗口、显示屏与兼容模式产生的覆盖配置，所以服务端要按每个 `ActivityRecord` 单独判定。

## `changes` 怎样产生

`ensureActivityConfiguration()` 会先处理一些无需继续判断的状态：

- Activity 正在结束或已经销毁；
- Activity 不可见且调用方没有要求忽略可见性；
- Configuration 派发处于暂停状态；
- `displayId`、`ActivityWindowInfo` 和完整配置都未变化。

进入 `updateReportedConfigurationAndSend()` 后，服务端保留旧的合并配置，并用当前值计算 `changes`。计算过程还有两次过滤：

1. `SizeConfigurationBuckets.filterDiff()` 去掉没有跨过该 Activity 资源尺寸分桶的细小尺寸差异。
2. 从重建变化集中清除 `CONFIG_WINDOW_CONFIGURATION`，WindowConfiguration 自身不直接触发 Activity 重建。

随后服务端先更新 `mLastReportedConfiguration`，再根据 Activity 是否运行、是否初始化以及 `shouldRelaunchLocked()` 的结果选择热派发或重建。这个顺序让服务端记录的“已报告配置”覆盖本轮目标状态，避免同一变化反复发送。

## 最终判断只有一个位运算

`shouldRelaunchLocked()` 的结果可以概括为：

```java
return (changes & ~skipRelaunchConfigMask) != 0;
```

`changes` 中只要存在一个没有进入跳过重建掩码的位，就需要重建。`orientation` 常与 `screenSize`、`screenLayout` 等位一同变化，因而 Manifest 只声明 `orientation` 时仍可能重建。

## 跳过重建掩码的构造顺序

Android 17 按下表构造 `skipRelaunchConfigMask`：

| 顺序 | 源码分支 | 对结果的影响 |
|---|---|---|
| 1 | `info.getRealConfigChanged()` | 以 `ActivityInfo.configChanges` 为基础。旧目标 SDK 还会兼容加入尺寸相关位。 |
| 2 | `CONFIG_RESOURCES_UNUSED` | 命中后直接返回 `false`，不再检查后续策略。 |
| 3 | Android O 之前的 VR 界面模式 | 旧目标版本且进入或退出 VR 界面模式时加入 `CONFIG_UI_MODE`。 |
| 4 | 桌面模式 | 满足减少重建策略或设备资源开关、只变化桌面模式、包内又没有桌面模式资源时加入 `CONFIG_UI_MODE`。 |
| 5 | 画中画密度 | Activity 位于固定窗口模式时加入 `CONFIG_DENSITY`。 |
| 6 | 显示兼容 | 特定显示屏迁移兼容状态加入一组显示相关变化位。 |
| 7 | RRO 约束 | `CONFIG_ASSETS_PATHS` 不影响当前 Activity 时加入该位。 |
| 8 | 配置变化重建策略 | 从跳过重建掩码中移除包内确有对应限定符资源的位。 |

第 8 步的运算方向和前几步相反：

```java
skipRelaunchConfigMask &=
        ~mAppCompatController.getRecreateOnConfigChangePolicy()
                .getRecreateConfigMask();
```

它会缩小可热处理范围。需要区分 Manifest 解析器生成 `ActivityInfo.configChanges` 的过程，以及 WindowManager 根据包内资源再次修正掩码的过程。

## Android 17 默认减少哪几类重建

`ParsedActivityUtils` 定义的默认掩码包含：

- 长期存在的 `CONFIG_MCC`、`CONFIG_MNC`；
- Android 17 减少重建功能开关与兼容性变更开启时新增的 `CONFIG_KEYBOARD`、`CONFIG_KEYBOARD_HIDDEN`、`CONFIG_NAVIGATION`、`CONFIG_TOUCHSCREEN`、`CONFIG_COLOR_MODE`。

Manifest 解析阶段使用下面的等式：

```java
ActivityInfo.configChanges =
        manifestConfigChanges
        | (~manifestRecreateOnConfigChanges
                & RECREATE_ON_CONFIG_CHANGES_MASK);
```

没有写进 `recreateOnConfigChanges` 的默认跳过位会被加入 `ActivityInfo.configChanges`，系统会把它视为可热处理。应用在 `recreateOnConfigChanges` 中声明某一位，会阻止解析器自动加入该位；同一位也显式出现在 `configChanges` 时，左侧的按位或运算仍让 `configChanges` 生效。

`recreateOnConfigChanges` 在 Android 17 源码标签中支持 `mcc`、`mnc`、`touchscreen`、`keyboard`、`keyboardHidden`、`navigation`、`colorMode`。它不支持 `uiMode`、`orientation`、`screenSize`、`density`。桌面模式的默认减少重建策略由 `ActivityRecord.shouldSkipActivityRelaunchWhenDocking()` 单独处理。

需要恢复键盘等变化的重建行为时，可以写成：

```xml
<activity
    android:name=".InputActivity"
    android:recreateOnConfigChanges=
        "keyboard|keyboardHidden|navigation|touchscreen|colorMode" />
```

这段声明只覆盖列出的低频配置位。页面对语言区域、夜间模式、密度、窗口尺寸或方向的处理方式，仍由对应变化位、Manifest 和其他系统策略决定。

## 包内限定符资源会再次缩小掩码

`AppCompatRecreateOnConfigChangePolicy.getRecreateConfigMask()` 只在 `enableLessActivityRecreationOnConfigChange()` 与 `SKIP_ACTIVITY_RECREATION_ON_CONFIG_CHANGE` 兼容性变更开启时工作。它扫描包的 `Resources.getResourceConfigurations()`，关注键盘、键盘隐藏、导航、触摸屏和色彩模式五类限定符。

包内存在某类限定符资源时，该位进入 `mRecreateConfigMask`，随后被 `skipMask &= ~recreateMask` 清除。此时系统可以重建 Activity，重新选择资源。该策略读取的是解析后的 `ActivityInfo.configChanges`，没有保留某一位来自默认掩码还是显式 `configChanges` 的来源信息。

判断结果不能只看 Manifest 一行。还要检查 APK 是否含有对应限定符资源、功能开关、兼容性变更和本轮 `changes`。`attrs_manifest.xml` 对“同一位同时出现在两个属性”的描述只涉及 Manifest 解析关系；WindowManager 后续的资源限定符策略仍会参与最终判定。

## 显示兼容策略的适用范围

`AppCompatDisplayCompatPolicy` 只在 Activity 发生相关显示屏迁移且尚未重启时返回掩码，并按两条互斥路径处理：

- 普通显示兼容路径只面向 `ApplicationInfo.CATEGORY_GAME`，原始掩码是 `DENSITY | TOUCHSCREEN | COLOR_MODE`。
- 计算机控制路径要求对应功能开关，原始掩码是 `TOUCHSCREEN | COLOR_MODE | NAVIGATION | KEYBOARD_HIDDEN | KEYBOARD`。

两条路径都会再清除 Activity 已经支持的 `configChanges` 位。普通应用、内部显示屏之间的常规切换或没有进入对应状态的 Activity，不能依靠这套策略跳过重建。

## RRO 约束怎样影响 `CONFIG_ASSETS_PATHS`

`AppCompatResourceOverlayPolicy` 保存上次报告的覆盖层路径及约束，下一次变化时计算新增/删除集合：

- 删除的路径使用缓存的约束；
- 新增的路径通过 system_server 内的 `OverlayManagerInternal.getOverlayConstraints()` 读取；
- 约束为空时视为影响所有目标；
- `TYPE_DEVICE_ID` 或 `TYPE_DISPLAY_ID` 与当前 Activity 匹配时视为受影响；
- 找不到 `OverlayManagerInternal` 时采取保守策略，认为变化会影响 Activity。

该调用通过 `LocalServices` 取得 system_server 内部服务，不是应用进程到 OverlayManager 的 Binder RPC。只有 `changes` 包含 `CONFIG_ASSETS_PATHS`、Activity 尚未声明处理该位，而且约束判定为不影响当前 Activity 时，系统才把它加入跳过重建掩码。

## `preserveWindow` 只保留窗口

`shouldRelaunchLocked()` 返回 `true` 后，`ensureActivityConfiguration()` 还会计算 `isAppResizeOnly`。要求如下：

- `changes` 只含 `SCREEN_SIZE | SMALLEST_SCREEN_SIZE | ORIENTATION | SCREEN_LAYOUT`；
- 显示屏旋转与最大边界没有命中 `displayMayChange`。

命中后，`relaunchActivityLocked(preserveWindow = true, ...)` 可以让窗口重建过程复用旧窗口 Surface，降低视觉跳变。Activity 实例仍会重建，`preserveWindow` 也不会自动保留 View 树和滚动位置；状态保存、ViewModel 和应用恢复逻辑仍要正确。

### 拖拽调整大小只合并满足条件的后续重建

`improveFluidResizingPerformance` 开启时，还要同时满足拖拽调整大小、`preserveWindow`，并且已有待处理的重建或首个新窗口尚未绘制，系统才会把后续 `configChangeFlags` 放入 `mPostponedRelaunchConfigChangesFlags`。

首轮重建仍可能发生，积累的标志也不固定在“拖拽收尾帧”处理。拖拽调整大小状态结束时，`resetDragResizingChangeReported()` 会尝试 `resumePostponedRelaunch()`；其他满足条件的时机也可以继续该流程。

## 客户端收到热派发时做什么

服务端决定不重建后，会发送 `ActivityConfigurationChangeItem`。客户端预先计算资源是否需要更新以及 `shouldReportChange()` 的结果；继续处理时，先用 `ResourcesManager.updateResourcesForActivity()` 切换 Activity 的覆盖配置和显示屏资源，再按已算出的结果决定是否调用 `Activity.onConfigurationChanged()`。

进程级 `ConfigurationController` 还有另一组工作：

- 更新所有存活 `ResourcesImpl`；
- 对依赖变化位的系统主题执行 `rebase()`；
- 语言区域变化时调用 `Canvas.freeTextLayoutCaches()`；
- 公开配置有差异时回调 Application、Service 和 Provider 等非 Activity 组件。

`freeTextLayoutCachesIfNeeded()` 检查的是 `CONFIG_LOCALE`，没有检查 `CONFIG_FONT_SCALE`。Activity 专用事务负责派发 Activity 回调，不经过进程级 `collectComponentCallbacks(false)`。

## Perfetto 中验证哪条分支

Android 17 源码建立了以下相关切片：

| 切片 | 判断 |
|---|---|
| `configChanged` | 进程级 Configuration 更新 |
| `ResourcesManager#applyConfigurationToResources` | 全局 ResourcesImpl 更新 |
| `ResourcesManager#updateResourcesForActivity` | Activity 覆盖配置/显示屏资源切换 |
| `activityConfigChanged` | Activity 热派发 |
| `activityRestart` | Activity 重建 |

`activityRestart` 存在时，继续分析暂停/停止/销毁/创建、布局加载与新窗口首帧。只有 `activityConfigChanged` 时，把应用的 `onConfigurationChanged()`、布局和渲染更新加入自定义跟踪。PiP、RRO 与拖拽调整大小的成本没有平台固定值，应在目标设备、相同窗口状态和相同页面上测量。

## 排查顺序

1. 记录新旧合并配置和 `Configuration.configurationDiffToString(changes)`。
2. 检查 Manifest 的 `configChanges` 与 `recreateOnConfigChanges`，确认目标 SDK 和兼容性变更。
3. 查看本轮是否处于 PiP、显示屏迁移、桌面模式、RRO 或拖拽调整大小。
4. 检查 APK 中与键盘、导航、触摸屏、色彩模式相关的限定符资源。
5. 用 `activityConfigChanged` / `activityRestart` 选择热派发或重建分支。
6. 将框架层资源成本、应用回调、Activity 生命周期和首帧分开归因。
