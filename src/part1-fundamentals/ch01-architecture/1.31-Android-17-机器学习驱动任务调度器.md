# 1.31 Android 17 机器学习驱动任务调度器

这个标题来自早期研究素材。以 `android-17.0.0_r1` 和 `android17-6.18-2026-06_r6` 为锚点，Android 17 AOSP 没有一套名为 ML Scheduler 的通用任务调度器，也没有一条由模型分数统一控制 Job、进程优先级、CPU 频率、内存 cgroup 和内核 runnable task 的平台协议。

AOSP 中确有“预测的 App Standby bucket”输入通道。这个事实只能说明系统允许特权组件提交一个预测桶值；源码没有规定提交者必须运行机器学习模型。JobScheduler、ADPF、输入预测和内核 EEVDF 各自处理不同对象，不能合并成同一个 Android 17 特性。

更完整的同题核查见 [1.59 Android 17「ML 驱动任务调度器」事实核查](./1.59-android17-ml-task-scheduler-comprehensive.md)。

## 可核验结论

| 说法 | Android 17 源码结论 |
|---|---|
| `MLScheduler` 或 `PredictiveScheduler` 系统服务 | AOSP 中没有对应服务、AIDL 或公开命令 |
| App Standby 接收预测桶值 | 有，受 `CHANGE_APP_IDLE_STATE` 保护 |
| `REASON_MAIN_PREDICTED` 表示 ML 已运行 | 不能这样判断；它表示桶值来自符合条件的特权调用方 |
| `adaptivebat=<provider_pkg>` 暴露模型提供方 | 错误；源码中的 `adaptivebat` 是全局布尔设置的调试日志 |
| JobScheduler 有 Android 17“五维节流” | `QuotaController` 中没有该结构，也不管理 FGS type、`memory.high` 或 `cpu.weight` |
| ADPF 预测应用使用行为 | ADPF 接收应用显式提交的线程工作时长提示 |
| MotionPredictor 参与后台任务调度 | 它属于输入事件预测，作用域与 JobScheduler 无关 |
| 论文指标可当作 Android 17 性能数据 | 论文原型和 OEM 扩展不能证明 API 37 平台行为 |

## App Standby 的预测输入通道

### bucket 不止原稿列出的五项

`UsageStatsManager` 在 Android 17 中定义 `EXEMPTED`、`ACTIVE`、`WORKING_SET`、`FREQUENT`、`RARE`、`RESTRICTED` 和内部 `NEVER`。面向应用的限制通常沿 `ACTIVE` 到 `RESTRICTED` 逐级增加；`EXEMPTED` 和 `NEVER` 还带有 system API 边界。

原稿把 `EXEMPTED` 放入“五桶模型”，同时漏掉 `RESTRICTED`，会让 JobScheduler 的 bucket index、受限任务规则和网络限制解释失真。

### `PREDICTED` 是来源标记

`UsageStatsManager.setAppStandbyBucket(s)` 是 `@SystemApi`，要求 `CHANGE_APP_IDLE_STATE`。Android 17 的权限定义为 `signature|privileged`，普通应用不能为其他包写 bucket。

Binder 请求到达 `AppStandbyController.setAppStandbyBuckets()` 后，controller 依据调用 UID 和 PID 选择 reason：

- shell 或特定 system UID 调用记为 `REASON_MAIN_FORCED_BY_USER`；
- core UID 调用记为 `REASON_MAIN_FORCED_BY_SYSTEM`；
- 其余通过权限校验的调用记为 `REASON_MAIN_PREDICTED`。

这段分支没有读取模型名称、置信度、特征或 provider 包名。`reason=p` 能证明一次 bucket 写入被归为 predicted，不能证明设备使用了 LSTM、Usage Ranker 或某个品牌的私有模型。

### 预测值会过期

`DEFAULT_PREDICTION_TIMEOUT` 在常规构建中是 12 小时，测试压缩时间时为 10 分钟；`DeviceConfig` 的 `app_standby/prediction_timeout` 可以覆盖它。

`AppIdleHistory` 保存 `lastPredictedTime` 和 `lastPredictedBucket`。预测超时后，`AppStandbyController` 会回到基于使用事件、屏幕时间、经过时间、最小 bucket 和临时提升期限的计算。预测也不能覆盖用户或系统强制设置的状态。

“有 12 小时 prediction timeout”因此是 AOSP 事实；“AOSP 自带每 12 小时运行一次的 ML 模型”没有源码依据。

### `adaptivebat` 不能用来找 provider

`AppStandbyController.ConstantsObserver.updateSettings()` 在 `DEBUG` 条件下用 `Slog.d()` 输出：

`adaptivebat=<Settings.Global.ADAPTIVE_BATTERY_MANAGEMENT_ENABLED>`

右侧是启用状态，通常按 0/1 理解。它不来自 `dump()`，也不包含 provider 包名。原稿示例中的 `adaptivebat=com.google.android.as` 与 Android 17 这段实现不符，不能用 `dumpsys usagestats | grep adaptivebat` 判断模型来源。

## JobScheduler 怎样消费 bucket

`JobSchedulerService.standbyBucketForPackage()` 从 `UsageStatsManagerInternal` 读取当前 bucket，再映射成 JobScheduler 内部 index。`QuotaController` 根据 effective standby bucket 选择执行时长、执行窗口、job/session 次数和 expedited job 限额，并处理充电、前台状态、临时 allowlist 等豁免条件。

bucket 还会影响任务批处理和 `RESTRICTED` 任务的额外约束。`UsageStatsManager` 的公开说明也指出，较低 bucket 的应用可能受到后台网络限制。不过，网络访问策略属于更广的 App Standby 与网络策略体系，不能全部归到 `QuotaController`。

原稿列出的 FGS type、`memory.high`、`cpu.weight` 和电量阈值分别属于前台服务校验、进程资源策略、内核 cgroup 或其他 JobScheduler controller。Android 17 的 `QuotaController.java` 没有“五维节流”对象，也没有把这些输入组合成 ML 评分。

JobScheduler 的源码边界与排查方法见 [Android 17 JobScheduler 系统级节流](../ch05-cpu-power/23-android17-jobscheduler-system-throttling.md)。

## ADPF、MotionPredictor 与 EEVDF 分别做什么

### ADPF

`PerformanceHintManager` 让应用为一组线程创建 hint session，设置目标工作时长，并上报已完成工作的实测时长。`HintManagerService` 和设备侧实现消费这些提示。公开契约不承诺某个 CPU 频点、核编号或 NPU 配额，也不预测用户下一次启动哪个应用。

ADPF 适合周期性负载的性能与能效协作，具体边界见 [ADPF 自适应性能框架](../ch05-cpu-power/09-adpf.md) 和 [Android 17 PerformanceHintManager](../ch08-startup/8.37-android17-performance-hint-manager.md)。

### MotionPredictor

`android.view.MotionPredictor` 预测后续输入事件，帮助应用缩短手写笔等场景的感知延迟。即使底层实现加载预测模型，它也不会写 App Standby bucket，不会提交 Job，也不会改变 EEVDF 的候选任务选择。

### Linux EEVDF

`android17-6.18-2026-06_r6` 的 fair scheduler 根据权重、virtual runtime、lag、eligibility 和 virtual deadline 选择 runnable entity。Framework 可以通过 nice、task profile、cpuset、cgroup weight 和 uclamp 改变约束，但 Android 17 没有向 EEVDF 传递通用 ML priority score 的接口。调度细节见 [Android 17 EEVDF 调度器](../ch05-cpu-power/31-android17-eevdf-scheduler.md)。

## 设备上怎样核查

下面的命令只读取现有状态，不预设设备带有预测模型：

```bash
adb shell am get-standby-bucket com.example.app
adb shell dumpsys usagestats com.example.app
adb shell dumpsys jobscheduler
adb shell dumpsys performance_hint
```

`dumpsys usagestats` 的包记录会显示 `bucket=<value>`、`reason=<code>` 和 `lastPred=<duration>`。`reason=p` 对应 `REASON_MAIN_PREDICTED`，`reason=t` 对应时间阈值回退；这仍只是状态来源。`dumpsys jobscheduler` 用于核对 effective bucket、约束、quota 和停止原因，`performance_hint` 则属于另一套 hint session。

要证明某台设备使用 ML 预测 bucket，还需取得产品级证据：

1. 找到拥有 `CHANGE_APP_IDLE_STATE` 的实际调用包；
2. 确认它何时调用 `setAppStandbyBucket(s)`；
3. 定位模型文件、推理库、服务接口或厂商技术文档；
4. 用固定版本设备记录 bucket 写入前后的 reason、JobScheduler 状态和后台执行结果；
5. 设置无预测对照组，控制温度、电量、充电状态、网络与用户操作。

只看到 `reason=p`、一个厂商进程名或一组性能数字，证据仍不足以把行为写成 Android 17 平台能力。

## 删除的无依据结论

本次审阅移除了以下内容：

- Pixel、Samsung、小米、OPPO 具体 provider 名称与模型实现，因为原稿没有厂商一手资料或设备证据；
- “启动降低 30%”“内存降低 25%”以及论文中的量化结果，因为它们没有 Android 17 AOSP 对照实验；
- Zygote 按使用模式延迟预加载、AICore 经 ADPF 调度 NPU、SystemServer 为预测启动提供基础设施等推断；
- 对未来 LLM 意图调度、动态 FGS 优先级和 DMA 带宽分配的设想。

保留下来的窄结论是：Android 17 AOSP 支持特权组件写入带 `PREDICTED` reason 的 App Standby bucket，JobScheduler 会消费 bucket；AOSP 没有规定预测算法，也没有把这条输入通道升级为通用 ML Scheduler。
