# 1.31 Android 17 机器学习驱动任务调度器

Android 系统中"机器学习驱动调度"并非一个独立的单一服务。它是一组分散在 JobScheduler、AppStandbyController、ADPF 和 OEM 私有预测器中的机制集合：ML 模型产生预测信号（应用使用频率、启动概率、资源需求），框架消费这些信号决定后台任务配额、CPU 频率提示和进程优先级。理解这套链路需要沿着"预测 → 桶值 → 配额 → 执行"这条数据流走一遍，而非寻找一个名为 "MLScheduler" 的类。

[已验证: AOSP android-17.0.0_r1, frameworks/base/apex/jobscheduler/service/java/com/android/server/usage/AppStandbyController.java]

## 预测信号的生产者：Usage Ranker 与 AppStandbyController

### 桶值预测链路

Android 的后台调度核心是 App Standby Bucket 五桶模型（ACTIVE / WORKING_SET / FREQUENT / RARE / EXEMPTED）。桶值由两条路径写入：

1. **时间阈值回退路径**：`AppStandbyController.getBucketForLocked()` 根据应用最后一次使用时间，纯算法计算桶值，不依赖任何 ML 模型。这条路径是默认保底。
2. **ML 预测路径**：OEM 或 GMS Core 提供的 Usage Ranker 通过 `UsageStatsManagerInternal` 接口调用 `AppStandbyController.setAppStandbyBuckets()`，以 `REASON_MAIN_PREDICTED` reason 写入预测桶值。

预测桶值有 **12 小时保质期**（`DEFAULT_PREDICTION_TIMEOUT`）：

```java
// AppStandbyController.java
private static final long DEFAULT_PREDICTION_TIMEOUT =
        COMPRESS_TIME ? 10 * ONE_MINUTE : 12 * ONE_HOUR;
```

超时后桶值回退到时间阈值路径。这意味着 ML 预测需要持续刷新——如果预测服务崩溃或 OEM 未实现，系统自动降级到纯时间算法，不会导致调度瘫痪。

[已验证: AOSP android-17.0.0_r1, AppStandbyController.java DEFAULT_PREDICTION_TIMEOUT]

### AOSP 主线不包含完整 ML 模型

关键事实：**AOSP 主线不包含完整的 Usage Ranker ML 模型实现**。`frameworks/base/services/people/java/com/android/server/people/` 提供了 Provider 接口框架，但实际的预测模型（基于使用频率、时间窗口、场景上下文等特征的分类器）由 OEM 私有实现。Pixel 设备通过 GMS Core 的私有 provider 提供预测，其他厂商各自实现。

`AppStandbyController.dump()` 输出中的 `adaptivebat=<provider_pkg>` 字段可用于确认设备是否启用了真实 ML provider：

```
$ adb shell dumpsys usagestats | grep adaptivebat
adaptivebat=com.google.android.as
```

如果该字段为空或显示 `null`，说明设备运行在纯时间阈值模式，ML 预测未生效。

[已验证: AOSP android-17.0.0_r1, AppStandbyController.java dump 实现]

## 预测信号的消费者：JobScheduler 配额矩阵

JobScheduler 是 ML 预测信号的最大消费者。`JobSchedulerService` 读取 App Standby Bucket 决定每个应用的：

- **后台任务执行配额**（每小时可执行 Job 的时长和次数）
- **Job 执行间隔**（ACTIVE 应用可频繁调度，RARE 应用被严格限制）
- **网络访问权限**（RARE 桶的应用可能被限制后台网络）

### 配额控制器：QuotaController

`QuotaController`（`frameworks/base/apex/jobscheduler/service/java/com/android/server/job/controllers/QuotaController.java`）维护每应用每时间窗口的执行配额。Android 17 的配额架构引入了五维节流（详见 §5.23）：

| 节流维度 | 机制 | 影响 |
|----------|------|------|
| App Standby Bucket | 按桶分配配额 | RARE 桶配额最低 |
| FGS Type | 前台服务类型限制 | 错误声明 FGS type 导致启动失败 |
| MemoryLimiter | cgroup memory.high 约束 | 后台进程内存受限 |
| CPU Quota | cgroup cpu.weight | 低优先级进程 CPU 时间减少 |
| Battery | 电量阈值触发降级 | 低电量时配额进一步收缩 |

[已验证: AOSP android-17.0.0_r1, QuotaController.java]
[待验证: Android 17 具体配额数值，需实机 dumpsys jobscheduler 确认]

### Android 17 JobScheduler 系统级节流

Android 17 对 JobScheduler 进行了系统级五维节流架构升级（详见 §5.23）。这一变更不直接依赖 ML 预测，但 ML 预测通过桶值间接影响每个应用的节流强度。当 ML 预测将某个应用判定为 RARE 时，五维节流中的多个维度同时收紧，产生复合限制效果。

详见 §5.23 "Android 17 JobScheduler 系统级五维节流架构"。

## ADPF：端侧 AI 推理的调度通道

ADPF（Adaptive Performance Framework）为应用提供了主动管理 CPU/NPU 资源的 API。虽然 ADPF 本身不使用 ML 驱动调度，但端侧 AI 应用（LLM 推理、图像处理）通过 ADPF 与系统调度器交互。

### PerformanceHintManager 会话

应用通过 `PerformanceHintManager.createHintSession()` 创建会话，系统据此优化线程的 CPU 频率和调度策略。Android 17 扩展了 ADPF 的能力：

- `reportActualWorkDuration()` 上报推理耗时，系统据此调整频率
- GPU 负载上报（Android 16+），支持 GPU 推理任务的性能调优
- 会话可绑定多个 TID，支持多线程推理场景

ADPF 详见 §5.19 "端侧 AI 调度与 ADPF 智能优化"和 §5.9 "ADPF 自适应性能框架"。

[已验证: AOSP android-17.0.0_r1, frameworks/base/core/java/android/os/PerformanceHintManager.java]

## MotionPredictor：输入子系统的 ML 预测

Android 输入子系统包含一个独立的 ML 预测组件——`MotionPredictor`。它使用 TensorFlow Lite 模型预测未来触摸事件位置，减少感知输入延迟。

- **Framework API**：`android.view.MotionPredictor`（API 34+），面向应用开发者
- **Native 实现**：`frameworks/native/libs/input/` 中的 `TfLiteMotionPredictorModel`
- **模型加载**：从 system 或 vendor 目录加载 `.tflite` 模型
- **预测窗口**：约 30ms（面向 stylus 场景验证）

MotionPredictor 是 AOSP 中少数可见的"ML 模型直接影响系统行为"的组件。但它的作用域限于输入预测，不参与任务调度。详见 §3.4 "输入延迟与预测输入技术"。

[已验证: AOSP android-17.0.0_r1, frameworks/native/libs/input/ MotionPredictor 实现]
[已验证: 官方文档, developer.android.com/reference/android/view/MotionPredictor]

## AppFlow：基于预测的冷启动调度（前沿研究）

AppFlow（MobiCom '26, arXiv:2503.15148）是一个跨 Framework 和 Linux 内核的预测式调度系统，展示了 ML 驱动调度在应用启动场景的潜力：

| 指标 | 改进幅度 |
|------|----------|
| GB 级应用冷启动延迟 | 降低 66.5%（2s → 690ms） |
| I/O 吞吐量 | 提升 2.35 倍 |
| 内存压力 | 降低 67.9% |

AppFlow 的三大组件：
1. **Selective File Preloader**：基于启动历史预测哪些文件需要预加载
2. **Adaptive Memory Reclaimer**：在内存压力下优先保留文件页
3. **Context-Aware Process Killer**：选择性 Kill 长期后台应用

⚠️ AppFlow 是学术研究成果，**未进入 Android 17 (android-17.0.0_r1) AOSP 主线**。但其设计思路——预测驱动的预加载与选择性 Kill——与 Android 现有的 Zygote 预加载和 LMKD 机制存在直接对应关系。

[引用: arxiv.org/abs/2503.15148, AppFlow, MobiCom '26]

## 与传统调度器的关系

"ML 驱动调度"在 Android 中不是替换传统调度器，而是在其上叠加预测层：

```
传统调度栈（不受 ML 影响）：
  Linux CFS/EEVDF → CPU 频率（DVFS）→ 进程优先级（nice/oom_score_adj）

ML 预测叠加层：
  Usage Ranker → AppStandby Bucket → JobScheduler 配额 → 资源限制
                                      ↓
  MotionPredictor → 输入事件预测 → 渲染提前启动
                                      ↓
  ADPF Session → 推理负载上报 → CPU 频率 hint
```

ML 预测层和传统调度层的关系是**覆盖而非替代**：预测层调整的是"允许做什么"（配额、频率提示、优先级提示），传统调度层负责"具体怎么做"（时间片分配、上下文切换、内存回收）。

## 系统启动中的调度优化

Android 17 在系统启动阶段有一些与预测调度相关的设计：

- **Zygote 延迟预加载**：不再在启动时全量预加载资源类，而是根据使用模式延迟加载（详见 §16.7）
- **bootanalyze 工具链**：Android 17 提供了启动分析工具，帮助 OEM 识别启动瓶颈
- **SystemServer 初始化流水线化**：`SystemServerInitThreadPool` 并行化各服务初始化

这些优化不直接依赖 ML 预测，但为未来"基于设备使用模式自适应调整启动流程"提供了基础设施。

详见 §16.7 "Android 系统启动耗时优化与 bootanalyze"。

## 可观测性：如何确认 ML 调度是否生效

开发者可以通过以下命令检查 ML 预测和调度状态：

```bash
# 查看应用当前桶值和 reason
adb shell dumpsys usagestats | grep -A5 "<package_name>"

# 检查是否有 ML provider
adb shell dumpsys usagestats | grep adaptivebat

# 查看 JobScheduler 配额状态
adb shell dumpsys jobscheduler | grep -A10 "<package_name>"

# 查看 ADPF 会话
adb shell dumpsys performance_hint

# 强制设置桶值（测试用）
adb shell am set-standby-bucket <package_name> active
```

桶值的 `bucketingReason` 字段是关键诊断信息：
- `REASON_MAIN_PREDICTED` → ML 预测写入（正常状态）
- `REASON_MAIN_DEFAULT` → 系统默认值（ML 未生效或超时回退）
- `REASON_MAIN_FORCED_BY_USER` → adb 或 Settings 手动设置
- `REASON_MAIN_TIMEOUT` → 预测超时后回退到时间阈值

[已验证: AOSP android-17.0.0_r1, AppStandbyController.java reason 常量定义]

## 扩展

### 🔸 OEM 实现差异

OEM 的 ML 预测实现差异巨大。Samsung 通过 Custom Performance Provider、小米通过 MiuiBatteryProvider、OPPO 通过 ColorOS BatteryProvider 各自实现预测算法。这些实现的预测精度、更新频率、特征工程完全不公开，导致同一应用在不同设备上的后台行为差异显著。

排查 OEM 差异的第一步是 `dumpsys usagestats | grep adaptivebat` 确认 provider 包名。

### 🔸 与 Google Intelligence API 的关系

Google Intelligence API（通过 AICore 分发）是端侧 AI 推理基础设施，但它运行在应用进程中，不直接参与系统调度。AICore 消耗的 CPU/NPU 资源通过 ADPF 与系统调度器交互。详见 §5.20 "GenAI 应用集成性能边界"。

### 🔸 未来方向：Predictive Resource Allocation

Android 17 的基础设施（App Hibernation 状态机、MemoryLimiter cgroup 配额、ADPF Power Efficiency Mode）为更激进的预测式资源分配铺路。可能的演进方向包括：
- 基于使用模式预测的 Zygote 预加载（类似 AppFlow 的 Selective File Preloader）
- 基于 LLM 意图理解的动态前台服务优先级
- 基于场景识别的 CPU/DMA 带宽动态分配

[待补充: 这些方向均为推测，当前 AOSP 中无对应实现]
