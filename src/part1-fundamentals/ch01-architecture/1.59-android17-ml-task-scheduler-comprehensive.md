# 1.59 Android 17「ML 驱动任务调度器」事实核查

> 本页保留用于消除重复内容和错误引用。它不再描述一个名为 ML Scheduler 的 Android 17 平台组件。

核查锚点：

- 平台源码：Android 17 / API 37 / `android-17.0.0_r1`
- 内核源码：`android17-6.18-2026-06_r6`
- 官方发布说明：[Android 17 is here](https://android-developers.googleblog.com/2026/06/Android-17.html)
- ADPF 文档：[Performance Hint API](https://source.android.com/docs/core/perf/performance-hint-api)

## 核查结果

Android 17 的公开 AOSP 源码和官方发布说明中，没有一套面向 Activity、Service、Worker、Binder 与 CPU runnable task 的通用“ML 驱动任务调度器”。以下名称、字段和命令均未出现在对应源码中：

- `MLScheduler`、`MLModel`、`ScheduleEngine`、`BehaviorPredictor`；
- `priority score ∈ [0, 100]`、`prefetchHint ∈ {NONE, WARM, HOT}`；
- `am proc-list --ml-priority`；
- `dumpsys activity scheduler --ml-stats`；
- 位于 `frameworks/base/services/core/java/com/android/server/pm/` 的闭源模型接口。

原稿给出的 LSTM、CNN、GNN 结构是伪代码，不能标成 AOSP 路径。冷启动提升 28%–45%、内存下降 25%、调度延迟从 50 ms 降至 15 ms 等数字也没有公开实验环境、样本或官方来源，全部删除。

官方 Android 17 发布文章介绍了内存限制、ART 分代 GC、动态代码加载限制和其他平台变化，没有发布上述 ML Scheduler。搜索不到某个公开类，单独看还不足以证明设备内部绝无私有策略；结合 AOSP 全树、公开命令、API 和发布文档，可以确定它不是 Android 17 / API 37 的平台契约。

## Android 17 中实际存在的几套机制

“系统安排工作何时运行”横跨多个层次。每层处理的对象不同，没有一个 framework 预测分数可以替代它们。

| 层次 | 调度对象 | Android 17 入口 | 决策依据 |
| --- | --- | --- | --- |
| Activity/Service 进程管理 | 组件生命周期、进程状态 | ATMS、AMS、OomAdjuster | 生命周期、可见性、绑定关系、前台服务等 |
| 后台工作 | `JobInfo` | JobScheduler controllers | 网络、充电、idle、quota、standby bucket、deadline 等 |
| 应用性能提示 | 一组线程的周期性工作 | ADPF、`PerformanceHintManager` | target/actual work duration、能效模式、设备策略 |
| CPU 调度 | runnable task | Linux fair scheduler / EEVDF | 权重、virtual lag、eligibility、virtual deadline |
| CPU 选核与频率 | utilization 与性能约束 | EAS、PELT、uclamp、schedutil、Power HAL | 利用率、容量、能耗模型、温控和厂商策略 |

### OomAdjuster 管进程重要性，不生成 ML task score

Android 17 的 OomAdjuster 位于 `frameworks/base/services/core/java/com/android/server/am/psc/`。它根据 Activity、Service、Provider、Broadcast、绑定关系和进程状态计算 `oom_score_adj` 与 process state，并推动进程组等状态更新。

这些值会影响内存回收优先级、后台限制、cpuset/cgroup 归属和部分调度属性。OomAdjuster 不负责在 EEVDF runqueue 中挑选下一条 runnable task，也没有读取统一 ML 预测分数的代码。进程优先级链见 [1.34 Android 17 进程优先级模型](34-oomadjuster-process-priority-performance.md)。

### JobScheduler 的 prefetch 会使用“预计启动时间”

Android 17 的 `JobInfo.Builder.setPrefetch(true)` 表示该 job 用于准备用户可能需要的内容。`PrefetchController` 会向 `UsageStatsManagerInternal` 查询应用的预计启动时间，并在接近该时间的窗口里调整 prefetch constraint。

这项能力容易被误写成“ML 预测启动并预热应用”。AOSP 默认估计逻辑在：

```text
frameworks/base/services/usage/java/com/android/server/usage/UsageStatsService.java
```

`calculateNextLaunchTime()` 使用清晰的时间规则：

- 使用历史超过 24 小时时，把已知启动事件向后推一周；
- 历史不足 24 小时时，把启动事件向后推一天。
- 最近一周没有可用的 `ACTIVITY_RESUMED` 事件时，`calculateEstimatedPackageLaunchTime()` 返回当前时间加 365 天，表示暂时未知。

这些分支都没有加载模型，也没有生成 0–100 的应用优先级。`PrefetchController` 只约束应用主动提交且标记为 prefetch 的 Job；它不会预启动任意 Activity，也不会给目标进程预留固定 CPU 或内存。

系统还提供受 `CHANGE_APP_LAUNCH_TIME_ESTIMATE` 保护的写入接口。拥有该权限的系统组件可以提供其他估计值，OEM 也可能在产品中接入私有预测逻辑。这样的实现属于设备扩展，应以具体产品源码、服务清单和 trace 为证据，不能写成 AOSP Android 17 的统一机制。

JobScheduler 的约束、quota 与后台限制见 5.23 节。

### ADPF 传递工作时长提示

`PerformanceHintManager` 让应用为一组线程创建 hint session，提交目标工作时长并报告实际工作时长。`HintManagerService`、Power HAL 和厂商实现据此调整 CPU 性能或能效策略。

ADPF 的输入来自应用明确上报，不负责预测用户下一次会打开哪个应用，也不决定 Activity、Service 或 Job 的提交顺序。设备策略可以把 hint 映射到频率、核型、uclamp 或其他控制项；公开 API 不允许应用直接指定 CPU 编号、频点或 EEVDF deadline。

ADPF 基础见 5.9 节，`PerformanceHintManager` 的 Java/NDK 使用边界见 8.37 节。

### EEVDF 选择 CPU 上的 runnable task

`android17-6.18-2026-06_r6` 的 `kernel/sched/fair.c` 使用 EEVDF：

1. `entity_eligible()` 判断调度实体是否满足 eligibility；
2. `pick_eevdf()` 在 eligible 候选中选择 virtual deadline 更早的实体；
3. 权重、virtual runtime、virtual lag 和 slice 共同影响结果。

framework 可以经 nice、task profile、cpuset、cgroup weight、uclamp 等机制改变内核看到的约束，但它不会向 EEVDF 传递原稿所写的 `predictedPriority`。EEVDF 细节见 5.31 节。

## “ML 调度”材料应怎样验真

遇到 OEM 文档、论文摘要或 RSS 把某项功能称为 ML scheduling，可以按四层证据判断适用范围：

1. **平台 API**：`developer.android.com/reference` 是否有公开或 `@SystemApi` 接口，API level 和权限是什么。
2. **AOSP 组件**：类、AIDL、native service、APEX 或 HAL 是否能在准确 tag 中定位，调用方和输出字段是否一致。
3. **设备扩展**：`service list`、`dumpsys -l`、`/system_ext`、`/product`、`/vendor` 与厂商 APEX 中是否存在额外服务或库。
4. **运行证据**：Perfetto 是否能观察到任务提交、进程组变化、频率/idle 变化和 CPU 调度结果；对照组是否固定缓存、温度、功耗模式与输入负载。

设备上出现一个预测服务，只能说明该产品带有扩展。若服务不在 AOSP、接口不属于 SDK、行为依赖厂商模型，就要写明设备、版本、权限和回退路径。

下面的命令用于枚举现有服务与 JobScheduler 状态，不假设一个不存在的 `--ml-priority` 参数：

```bash
adb shell service list
adb shell dumpsys -l
adb shell dumpsys jobscheduler
adb shell dumpsys usagestats
```

结果中若出现厂商服务名，再结合进程映射、包路径和 Perfetto 继续追踪。命令本身不能证明该服务使用机器学习；模型文件、推理调用或厂商文档至少要有一项可核验的证据。

## 与 1.41、1.43 的关系

1.41、1.43 和本页来自同一组“Android 17 ML Scheduler”材料，重复了相似的伪类、调试命令与性能数字。三页之间的互相引用不能充当独立证据；阅读时应回到本页列出的 AOSP tag、内核 tag 和官方发布说明核对。

## 保留结论

Android 17 有 JobScheduler prefetch、UsageStats 启动时间估计、OomAdjuster、ADPF、EAS/PELT/uclamp 和内核 EEVDF。它们可以共同影响后台工作时机、进程资源资格、线程性能与 CPU 运行顺序，但公开 AOSP 没有把这些组件合成一套通用 ML Scheduler。

若厂商在产品中加入预测模型，应把它描述为 OEM 扩展，并单独验证输入、输出、权限、失败回退和与 AOSP 各层的连接位置。
