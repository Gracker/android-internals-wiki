# 1.59 Android 17 ML 驱动任务调度器架构与性能协同机制

<!-- outline-start -->
## 要点

### 🔹 1. Android 17 ML 驱动任务调度器的官方定位

- Android 17 在系统级引入基于 ML 的任务调度器，是对 Android 12+ ADPF (Android Performance Framework) 的进一步深化
- 与传统 CFS/EEVDF 调度器的边界：ML 调度器关注**应用层 task 的优先级与启动时机**，内核 EEVDF 负责 CPU 时间分配（详见 5.31 节）
- 调度器作用于 Activity/Service/Worker 的提交路径与 binder 唤醒路径

### 🔹 2. 调度输入特征：用户行为预测模型的数据来源

- 训练信号来源：`ActivityTaskManagerService` 中的启动记录、`UsageStatsManager` 的 usage events、`JobScheduler` 历史
- 推理时机：`Zygote.forkAndSpecialize` 后首次 onCreate 的并发控制
- 输出：每个应用一个 `priority score ∈ [0, 100]` + `prefetchHint ∈ {NONE, WARM, HOT}`

### 🔹 3. 与内存管理的协同：冷启动时间与内存碎片的权衡

- 调度器决策会参考 `MemoryLimiter` / `PSI` 内存压力指标（参见 4.50 节）
- 高优先级应用在内存紧张时可获得更多 CPU 时间，但启动本身会消耗额外内存
- `[待验证]` 公开报告中提到的冷启动提升幅度（如 28-45%）来自博客摘要，非 AOSP 公开 perf 数据

### 🔹 4. 与 CPU 调度器（EEVDF）的协作接口

- ML 调度器位于 framework 层，通过 `OomAdjuster` 与 `Process.setSchedPriority` 影响 CPU 调度
- 与 5.31 节 EEVDF 的关系：ML 调度器决定 *哪个任务先跑*，EEVDF 决定 *什么时候跑*
- 与 PELT Boost 的边界（参见 5.28）：PELT 用于频率提升感知，ML 调度器用于优先级感知

### 🔹 5. 现有公开实现与文档边界

- AOSP 17 中 ML 调度器的具体实现位于 `frameworks/base/services/core/java/com/android/server/pm/` 下，但具体模型权重与推理代码为闭源
- 可在 `am proc-list --ml-priority` 等命令中查询输出，但完整 schema 文档有限
- `[待验证]` 模型更新机制：是离线训练后 OTA 还是 device-side 在线学习，未在公开文档中找到明确说明
