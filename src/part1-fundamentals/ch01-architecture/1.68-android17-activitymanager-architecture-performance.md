# 1.68 Android 17 ActivityManager 架构与性能优化

正文基于 Android 17（API 37）`android-17.0.0_r1`，内核部分基于 `android17-6.18-2026-06_r6`。Android 10 以来的变化只用于解释职责迁移。覆盖范围包括 AMS、ATMS、组件调度器、进程状态控制器与 LMKD 的边界，以及组件启动、进程创建、优先级更新和进程死亡清理。

---

## 职责边界

Android 17 已拆分相关职责，主要边界如下。

| 模块 | Android 17 的核心职责 | 不应归给它的职责 |
| --- | --- | --- |
| `ActivityManagerService`（AMS） | 进程生命周期、Service、Broadcast、Provider、UID 状态、错误处理，以及各子控制器的协调 | Task/Activity/窗口层级的主存储 |
| `ActivityTaskManagerService`（ATMS） | Activity 启动策略、Task、Display、`ActivityRecord` 与生命周期状态 | 应用进程的完整创建和死亡清理 |
| `ProcessStateController` | 进程重要性输入的单写入口，触发单进程、待处理或全量 OOM 更新 | 内存压力监测和最终选杀 |
| `OomAdjusterImpl` | 计算进程状态、`oom_adj`、调度组和 capability，处理 Service/Provider 依赖图 | 直接读取 PSI 并选择牺牲进程 |
| `ProcessList` | 进程记录索引、LRU、启动 Zygote、与 `lmkd` 通信 | Task 排布和广播策略 |
| `BroadcastQueueImpl` | 按目标进程排队、延迟、并发与冷启动控制 | 完全脱离 AMS 锁运行 |
| `ActiveServices` | Service 的解析、启动、绑定、前台服务约束、重启和超时 | JobScheduler 的任务调度 |
| `ContentProviderHelper` | Provider 解析、进程拉起、发布、引用与死亡处理 | Provider 业务调用的执行 |
| `lmkd` | 监测内存压力，依据进程分数与内存信息选择并杀死进程 | 计算 Activity/Service 语义上的重要性 |
| Linux 内核 | 提供 PSI、cgroup/freezer、进程信号和内核 OOM 兜底 | 理解 Android 组件状态 |

可以把整条控制关系概括为：

```text
Activity / Service / Receiver / Provider 的状态变化
                         │
                         ▼
             AMS / ATMS 维护组件事实
                         │
                         ▼
              ProcessStateController
                         │
                         ▼
      OomAdjusterImpl 计算 procstate / adj / sched group
                         │
                         ▼
        ProcessList 通过 lmkd socket 同步进程分数
                         │
          ┌──────────────┴──────────────┐
          ▼                             ▼
 lmkd 消费内核 PSI 并选杀       内核 OOM killer 作为末级保护
```

`procstate` 与 `oom_adj` 是两套指标。前者面向框架层的进程可见性和能力判断，后者面向内存回收优先级，二者没有固定的一一映射。框架层给出进程重要性，`lmkd` 再结合当时的压力和内存占用决定回收时机与目标；内核 OOM 机制仍是一条独立的末级保护路径。

## AMS 如何进入 `system_server`

### 初始化顺序

`SystemServer.startBootstrapServices()` 先启动 ATMS，再通过 `ActivityManagerService.Lifecycle.startService()` 创建 AMS。AMS 构造完成后，`Lifecycle.onStart()` 调用 `start()`；稍后的 `setSystemProcess()` 才把 `activity`、`procstats`、`meminfo` 等 Binder 服务发布到 `ServiceManager`。

- AMS 构造期间已经需要 `ActivityTaskManagerInternal`，所以 ATMS 先建立。
- `start()` 会发布 BatteryStats、AppOps、ProcessStats 等协作服务，并注册 `ActivityManagerInternal`、`ActivityManagerLocal` 等进程内接口。
- 同在 `system_server` 的服务优先使用 `LocalServices`/本地接口，跨进程客户端才经过 `IActivityManager` Binder。

不要把“对象已构造”“系统服务已发布”“第三方进程允许启动”当成同一个时刻。启动早期若 `mProcessesReady` 尚未置位，普通应用可能先进入 `mProcessesOnHold`，待系统就绪后再启动。

### Android 17 的线程模型

AMS 的生产构造函数明确创建两条前台优先级 `ServiceThread`：

```java
// AMS 主处理线程与进程启动线程。
mHandlerThread = new ServiceThread(TAG, THREAD_PRIORITY_FOREGROUND, false);
mHandler = new MainHandler(mHandlerThread.getLooper());

mProcStartHandlerThread =
        new ServiceThread(TAG + ":procStart", THREAD_PRIORITY_FOREGROUND, false);
mProcStartHandler = new ProcStartHandler(this, mProcStartHandlerThread.getLooper());
```

这里的 `mHandler` 不依附 `system_server` 主线程。`mUiHandler` 使用 `UiThread`；`AppProfiler` 使用 `BackgroundThread`；缓存应用压缩与冻结也有专用执行线程。线程拆分降低了相互阻塞的机会，但共享状态仍受锁约束，不能据此推断所有工作都能并行。

默认启用异步启动时，`ProcessList` 把可能阻塞的 Zygote 调用投递给 `mProcStartHandler`。Zygote 返回后，结果再在 AMS 锁内核验并写回，从而避免持有 AMS 全局锁等待 fork。

### 三类常见锁

| 锁 | Android 17 中的用途 | 阅读源码时的规则 |
| --- | --- | --- |
| `mGlobalLock` / `synchronized (mService)` | `mGlobalLock` 指向 AMS 自身；Service、Provider、Broadcast 等大量状态由它保护 | 看到 `Locked` 方法先确认调用方是否已持锁 |
| `mProcLock` | 保护高频进程状态；锁顺序低于 AMS 全局锁 | 不得先持 `mProcLock` 再获取全局锁 |
| `mPidsSelfLocked` | 单独保护 PID 到 `ProcessRecord` 的映射 | 它不是 AMS 全局锁的别名 |

Android 17 的 `ProcessRecord` 上大量字段使用 `@CompositeRWLock({"mService", "mProcLock"})`。这表示读写条件由注解逐字段说明，不能用“所有 ProcessRecord 字段都只受一把锁保护”来简化。

性能分析中，锁等待和 Handler 排队要分开看：

- Binder 线程可能在获取 AMS 锁前等待。
- `mHandler` 可能没有锁竞争，却因前序消息耗时而延迟。
- 一个方法离开全局锁后执行 I/O，不代表整个功能已经去掉全局锁。

## Activity 启动：ATMS 主导，AMS 负责进程

Android 10 把 Activity/Task 主路径拆到 ATMS。Android 17 的冷启动主干如下：

```text
Context.startActivity()
  → Instrumentation.execStartActivity()
  → ActivityTaskManager.getService().startActivity(...)   [Binder]
  → ActivityTaskManagerService
  → ActivityStarter.execute()
  → Task / TaskFragment / ActivityRecord 选择与状态更新
  → ActivityTaskSupervisor.startSpecificActivity()
      ├─ 目标进程存活：realStartActivityLocked()
      └─ 目标进程不存在：ATMS.startProcessAsync()
                            → ActivityManagerInternal
                            → ProcessList / Zygote
```

进程就绪后，`ActivityTaskSupervisor.realStartActivityLocked()` 构造 `LaunchActivityItem`，再配一个目标生命周期项：

- 需要立即前台显示时使用 `ResumeActivityItem`；
- 可见但暂不恢复时使用 `PauseActivityItem`；
- 不可见启动时使用 `StopActivityItem`。

随后 `ClientLifecycleManager.scheduleTransactionItems()` 把这些项目发给应用的 `IApplicationThread`。冷启动要求立即发送，以便服务端及时发现失效的 Binder 并重启进程；其他生命周期事务可以等待表面放置阶段批量发送。

`ActivityClientController` 是 `ActivityClient` 调用 `system_server` 的服务端 Binder 入口，用于 Activity 向 ATMS 报告状态或请求操作。`system_server` 向应用下发生命周期使用的是 `ClientLifecycleManager` 和 `IApplicationThread`。

### 冷启动中各层负责什么

| 阶段 | 主要负责者 | 常见耗时来源 |
| --- | --- | --- |
| Intent 解析与启动权限 | ATMS、PMS | 包可见性、权限、目标解析 |
| Task 与 `ActivityRecord` 决策 | ATMS/WMS | launchMode、Task 复用、配置与转场 |
| 进程创建 | AMS、`ProcessList`、Zygote | fork/specialize、进程组、存储目录准备 |
| `bindApplication` | AMS → `IApplicationThread` | 应用信息和运行时配置的 Binder 数据 |
| Provider 与 Application 初始化 | `ActivityThread` 主线程 | 类加载、Provider `onCreate()`、`Application.onCreate()` |
| Activity 生命周期 | ATMS → `ClientLifecycleManager` | `onCreate()`、布局、资源加载 |
| Surface、同步事务与首帧 | WMS、SurfaceFlinger、应用渲染管线 | 窗口提交、measure/layout/draw、GPU 工作 |

Zygote fork 没有跨设备通用的固定耗时。文章、监控或告警若写死 “30–80 ms”，会掩盖 ABI、映射页、存储、调试器、OEM 初始化和负载差异。应以设备上的 `ApplicationStartInfo` 时间戳、Perfetto 和应用首帧数据为准。

AMS 也不负责“提前准备好 Surface 和 InputChannel”。这些属于 ATMS/WMS 与输入系统的协作范围。AMS 在 Activity 冷启动中的任务是提供可用进程，并及时更新其重要性。

## ProcessRecord：进程事实被拆成多个子记录

Android 17 的 `ProcessRecord` 继承 `psc.ProcessRecordInternal`。它保存身份、PID、`IApplicationThread`、启动参数等进程事实，同时把不同领域拆到专门记录中。

| 子记录/控制器 | 内容 |
| --- | --- |
| `ProcessRecordInternal` | OOM 计算需要的内部状态与访问接口 |
| `ProcessProfileRecord` | PSS、CPU、profiling 等统计 |
| `ProcessServiceRecord` | 进程托管和执行的 Service、连接 |
| `ProcessProviderRecord` | 已发布和正在使用的 Provider |
| `ProcessReceiverRecord` | 进程中的 Receiver 执行状态 |
| `ProcessErrorStateRecord` | crash、ANR、bad process 等错误状态 |
| `ProcessCachedOptimizerRecord` | 压缩、冻结相关状态 |
| `WindowProcessController` | ATMS/WMS 侧看到的进程、Activity 和 Task 关系 |

旧资料中的 `app.curAdj`、`app.curProcState` 或 `app.crashing`，在 Android 17 中需要到子记录和 `ProcessRecordInternal` 查找实际所有者。照搬旧字段会误读锁范围，也容易在版本迁移时引用不存在的字段。

### 进程启动决策

`ProcessList.startProcessLocked()` 的关键判断可以按以下顺序理解：

1. 根据进程名和 UID 查找现有记录；已在运行或已经有 PID 等待 attach 时复用。
2. 后台来源若命中 bad-process 规则，可拒绝启动；显式用户启动会清理相应崩溃状态。
3. 需要时创建新的 `ProcessRecord`，记录 `HostingRecord`、ABI、隔离进程信息等。
4. 系统尚未允许普通进程启动时，把记录加入 `mProcessesOnHold`。
5. 标记 pending start 和 start sequence。
6. 默认在 `mProcStartHandler` 上调用 Zygote；WebView Zygote、App Zygote 和普通 Zygote 分支各自处理。
7. Zygote 返回 PID 后再次验证 start sequence 和记录有效性，防止过期结果覆盖新进程。

源码没有“内存压力高就按当前 `oom_adj` 拒绝任何低优先级进程启动”这一条通用规则。内存不足主要由缓存上限、OOM 计算、`lmkd`、进程启动限制和具体组件策略共同处理。

### attach 与 `bindApplication`

新进程从 `ActivityThread.main()` 启动后调用 `attachApplication()`。AMS 会：

- 校验 PID、UID、start sequence 和进程记录；
- 给 `IApplicationThread` 注册 `DeathRecipient`；
- 发送 `bindApplication()`；
- 安排待启动的 Provider、Service、Broadcast 或 Activity；
- 更新进程状态与 OOM 分数；
- 设置启动、bind 和 Provider 发布等超时。

`IApplicationThread.aidl` 是 `oneway interface`，所以 `system_server` 发起 `bindApplication()` 时不会同步等待应用执行完 `Application.onCreate()`。这只能缩短服务端 Binder 等待；应用主线程仍会串行执行 Provider 初始化、Application 初始化和后续组件回调。

### 进程死亡清理

应用线程 Binder 死亡后，`AppDeathRecipient.binderDied()` 在 AMS 全局锁内进入 `appDiedLocked()`。清理过程覆盖：

- 校验死亡通知是否仍对应当前 PID，忽略旧实例的迟到通知；
- 更新 BatteryStats、进程退出信息和 killed 状态；
- 清理进程的冻结/压缩状态；
- 让 BroadcastQueue 移除该应用的执行记录；
- 断开或按策略重启 Service；
- 处理 Provider 及其客户端引用；
- 通知 ATMS 清理 `WindowProcessController` 对应的 Activity/Task 状态；
- 从 LRU、PID 和进程名映射移除记录；
- 对 persistent 或仍有托管组件需求的进程安排重启；
- 重新计算受依赖关系影响的进程重要性。

TOP 进程死亡属于进程退出，不会自动转成 ANR。ANR 表示进程仍在但未在期限内响应，两者的取证路径不同。死亡清理耗时也取决于该进程拥有的组件和依赖关系，不宜用固定 “10–20 ms” 描述。

## ProcessStateController 与 OomAdjuster

### 四个结果维度

Android 17 的 OOM 更新会共同维护：

1. **process state**：framework 对进程可见性和活跃度的抽象；
2. **oom adj**：传给 `lmkd`/内核的相对保护级别，数值越大越容易被回收；
3. **scheduler group**：影响线程调度与 cpuset/cgroup 归属；
4. **process capability**：服务于 while-in-use 权限等按前后台状态判断的能力。

同一个进程可能因 Activity 可见、执行 Receiver、托管前台服务、被 TOP 客户端绑定或被 Provider 客户端引用而改变多个维度。服务绑定 flags 也会改变重要性传播方式，因此“绑定次数越多，`oom_adj` 越低”并不成立。

### Android 17 的单写入口

`ProcessStateController` 的类注释规定：凡是会影响 OomAdjuster 计算的状态，都应只通过该控制器写入。它提供三类同步更新：

| 更新方式 | 使用场景 |
| --- | --- |
| `runUpdate(proc, reason)` | 目标进程及其可达依赖图发生变化 |
| `runPendingUpdate(reason)` | 合并此前入队的多个目标 |
| `runFullUpdate(reason)` | 全局条件变化，需要重新评估全部进程 |

批处理会把多次状态变化合到一个 `SyncBatchSession`，会话结束后再执行待处理或全量更新。`FOLLOW_UP_UPDATE_MSG` 和 Service Binder 调用状态可以在控制器所用线程上异步排队，但核心计算仍在 AMS 全局锁 `mLock` 保护下执行。

### 依赖图算法

Service 绑定和 Provider 引用形成进程依赖图。Android 17 使用现代 `OomAdjusterImpl`：

1. 先忽略外部客户端，计算每个进程自身的 Activity、Receiver、Service、Provider 等基础状态。
2. 按重要性把进程放入优先级 bucket。
3. 从高重要性 bucket 开始广度优先遍历 Service/Provider 边。
4. 绑定规则允许提升被依赖进程时，把它移动到更高 bucket。
5. 局部更新只处理目标和可达图；全量更新处理整个进程集。
6. 应用最终状态，并批量向 `lmkd` 发送变化的 `oom_adj`。

AOSP 的 `OomAdjuster.md` 给出的复杂度边界是：

- 旧递归算法约为 `O((1 + retries) × processes × bindings)`，环会触发重试；
- 现代 bucket/BFS 算法约为 `O(processes × bindings)`。

这里的复杂度是算法上界，不等于每次更新都扫描所有进程。目标更新、待处理队列和批量会话正是为了减少无关计算。

### 如何读 `oom_adj`

下表列出 Android 17 `psc/Constants.java` 中有代表性的分值。它用于识别区间，不能替代完整决策逻辑。

| 类别 | `oom_adj` |
| --- | ---: |
| native | -1000 |
| system | -900 |
| persistent process | -800 |
| persistent service | -700 |
| foreground app | 0 |
| visible | 100 |
| perceptible | 200 |
| backup | 300 |
| heavy-weight | 400 |
| service A | 500 |
| home | 600 |
| previous | 700 |
| service B | 800 |
| cached | 900–999 |

还要留意三点：

- visible、previous 和 cached 区间内可以继续分层；
- 最近前台、前台服务、绑定 flags、外部 Provider 句柄等会改变最终结果；
- 进程从一种状态切到另一种状态时，可能存在 grace period，避免短暂退后台后立即失去保护。

排查时应同时看 `setAdj/curAdj`、`setProcState/curProcState`、调度组、capability 和 adj reason。只截取一个调整值，通常无法解释它为什么出现。

## AMS、lmkd 与内核的边界

### 分数如何到达 lmkd

`ProcessList.setOomAdj()` 不直接写 `/proc/<pid>/oom_score_adj`。它构造 `LMK_PROCPRIO` 消息，把 PID、UID、adj 和进程类型写入 lmkd socket。批量路径使用 `LMK_PROCS_PRIO`，Android 17 每个消息包最多携带三个进程条目。

```text
OomAdjusterImpl.apply...
  → ProcessList.setOomAdj() / batchSetOomAdj()
  → LmkdConnection
  → /dev/socket/lmkd
  → lmkd 处理 LMK_PROCPRIO
  → 写 /proc/<pid>/oom_score_adj
```

这条链路说明两类问题要分开查：

- 框架层分数错误：检查组件状态、依赖边和 OomAdjuster reason；
- 分数正确但回收行为异常：检查 `lmkd` 配置、PSI、meminfo、swap、thrashing、进程 RSS 和厂商策略。

### PSI 与选杀

`android17-6.18-2026-06_r6` 的 `kernel/sched/psi.c` 维护 CPU、内存和 I/O stall 统计，并提供 trigger 接口。Android 17 的 `lmkd` 初始化内存 PSI monitor，读取 memory SOME/FULL 统计，在压力事件后结合：

- 可用内存和 file cache；
- 交换空间用量和剩余量；
- reclaim/thrashing 情况；
- 进程 `oom_score_adj`；
- 进程 RSS、swap 等内存数据；
- `lmkd` 属性和厂商事件；

选择候选进程。PSI 是压力信号，`oom_adj` 是保护等级，两者用于不同的判断阶段。

内核的 `mm/oom_kill.c` 还有 `oom_badness()` 和 OOM victim 选择。它同样参考 `oom_score_adj`，并结合 RSS、swap、页表等信息。内核 OOM 发生时，系统已进入比 `lmkd` 日常回收更严峻的分配失败阶段；分析日志时不要把 `lowmemorykiller` 事件与 kernel OOM trace 混为一类。

### 缓存进程、压缩与冻结

Android 17 的缓存进程上限来自 `ActivityManagerConstants`。AOSP 的 `DEFAULT_MAX_CACHED_PROCESSES` 为 1024，`MAX_CACHED_PROCESSES` 以它初始化；设备执行策略使用的 `CUR_MAX_CACHED_PROCESSES` 则从可 overlay 的 `config_customizedMaxCachedProcesses` 初始化，还可被 DeviceConfig 或运行时 override 改写。分析单机行为时应读取有效值，不能只看源码常量。这个上限由 framework 管理，`lmkd` 可能在达到它之前就因内存压力杀掉缓存进程。

因此，“系统只保留 32 个缓存进程”已经不适合作为 Android 17 基线。进程占用也没有统一的 “10–50 MB” 区间，WebView、游戏、相机、64 位运行时和共享页都会让 PSS/RSS 差异很大。

`CachedAppOptimizer` 为符合条件的缓存进程提供两项能力：

- **compaction**：在后台线程上请求压缩，策略会参考 swap 等条件；
- **freezer**：经过 debounce 和豁免检查后冻结 Binder 与进程，进程重新需要工作时解冻。

freezer 是缓存进程节能机制，不是名为 `BG_FROZEN` 的公开进程状态，也不会在设备空闲时替应用预先 fork 一个可直接使用的进程。冻结前还要处理 Binder 事务和可冻结性，不能把它描述为零成本保活。

## 四大组件调度器

### Activity：Task 状态留在 ATMS/WMS

Android 17 中不存在仍负责维护任务栈的 `ActivityStack` 类。常见层级是：

```text
RootWindowContainer
  → DisplayContent
    → TaskDisplayArea
      → Task
        → TaskFragment
          → ActivityRecord
```

Task 切换、Z-order、分屏/自由窗、转场和窗口可见性由 ATMS/WMS 维护。AMS 通过 `WindowProcessController` 接收 Activity 可见性等进程级信息，再参与 OOM 更新。

任务切换快慢通常分三种情况：

1. 进程和 Activity 都在：主要成本在生命周期、布局、绘制与转场；
2. 进程在但 Activity 要重建：省去 fork/Application 初始化，仍要创建 Activity 和窗口；
3. 进程已死亡：进入完整冷启动，并可能恢复 saved state。

`onSaveInstanceState()` 的调用条件没有在 Android 10 改成“只在配置变化或系统准备杀进程时”。它与 Activity stop、目标版本和具体生命周期路径有关，也不能把它当作系统杀进程前一定执行的持久化通知。

### Service：`ActiveServices` 管理 start、bind 与重启

`ActiveServices` 按用户维护 `ServiceMap`。其中包括：

- `mServicesByInstanceName`：按实例组件名索引 `ServiceRecord`；
- `mServicesByIntent`：按 Intent 过滤结果索引；
- `mStartingBackground` 与 `mDelayedStartList`：控制后台 Service 并发启动；
- 全局的 pending、restarting、destroying Service 集合和连接记录。

一次冷 Service 启动可概括为：

```text
Context.startService() / bindService()
  → AMS Binder 入口
  → ActiveServices.startServiceLocked() / bindServiceLocked()
  → 解析目标、权限和后台启动条件
  → bringUpServiceLocked()
      ├─ 进程存在：IApplicationThread.scheduleCreateService(...)
      └─ 进程不存在：加入 pending → ProcessList 启动进程
  → attachApplication 后处理 pending Service
```

Service 执行状态也会成为 OOM 计算输入。绑定客户端的重要性可能经连接传播到服务进程，但结果受 `BIND_WAIVE_PRIORITY`、`BIND_IMPORTANT`、`BIND_NOT_FOREGROUND`、`BIND_ALLOW_OOM_MANAGEMENT` 等 flags 约束。

#### 前台服务的几个超时不要混用

Android 17 源码中至少要区分：

- `mFgsStartForegroundTimeoutMs`：`startForegroundService()` 后调用 `startForeground()` 的默认期限为 10 秒，可由配置改变；
- `SERVICE_TIMEOUT`：`shouldExecServicesFg()` 判定为前台执行时，Service 回调的默认超时为 `20 秒 × HW_TIMEOUT_MULTIPLIER`；
- `SERVICE_BACKGROUND_TIMEOUT`：后台进程的默认值是前者的 10 倍；
- short service 和受时限约束的 FGS 类型还有各自的超时、警告与 ANR 消息。

统一的“5 秒规则”在 Android 17 上不准确。前台服务能否从后台启动、是否需要对应 type 与权限、while-in-use 权限能否在后台取得，都要按调用者状态、目标 SDK、豁免和服务类型分别判断。

`bindIsolatedService(..., instanceName, ...)` 可以让同一声明对应具名隔离实例；`system_server` 侧 Binder 方法名是 `bindServiceInstance()`。它不等于 Android 15 新增一个 `bindServiceInstances()` 公共 API，也不意味着多个连接会线性叠加进程保护等级。

### Broadcast：Android 17 只有一套主实现

Android 17 的工厂直接创建 `BroadcastQueueImpl`，源码中没有 `BroadcastQueueModernImpl.java`。这里的 `BroadcastQueue` 是抽象基类，`BroadcastQueueImpl` 是当前实现，`BroadcastProcessQueue` 表示目标进程的队列。

当前设计为每个潜在目标进程维护一条队列：

- 每条进程队列根据 urgent、delayed、cached、instrumented、ordered 等条件计算 `runnableAt`；
- 可运行队列按时间排序，优先处理等待更久的目标；
- 一个进程同一时刻只分发一个广播，保持该进程看到的顺序；
- 多个进程可以并行处于 running 状态；
- 同一时刻最多只安排一个广播冷启动，避免多个 Zygote fork 争抢系统资源；
- 连续给同一进程分发可以摊薄 OOM 更新成本；
- urgent 与普通广播分队列，积压过大时会绕过部分延迟策略；
- 有序或带优先级的广播仍提供相应的跨接收器顺序语义。

`BroadcastQueue.md` 还说明，系统可根据 CPU 延迟扩展 soft ANR timeout，避免目标进程已获调度但因系统竞争拿不到 CPU 时过早判超时。

这套实现仍有大量字段和方法标注 `@GuardedBy("mService")`，Handler 回调也会重新进入 `synchronized (mService)`。它优化的是每进程排队、并行上限、冷启动串行化和饥饿控制，不能概括成“广播分发已经移出 AMS 全局锁”或“改成细粒度分段锁”。

#### BroadcastOptions 的准确用法

下面的代码用于把同一业务键的多次广播折叠为最近一次，并让缓存进程等到活跃后接收；调用方需要拥有相应 API 可见性与权限：

```java
// 目的：同一业务键只保留最近一次广播，并允许缓存进程延迟接收。
BroadcastOptions options = BroadcastOptions.makeBasic()
        .setDeliveryGroupPolicy(
                BroadcastOptions.DELIVERY_GROUP_POLICY_MOST_RECENT)
        .setDeliveryGroupMatchingKey("sync", accountId)
        .setDeferralPolicy(
                BroadcastOptions.DEFERRAL_POLICY_UNTIL_ACTIVE);
```

`UNTIL_ACTIVE` 只针对运行时注册的接收器，并且不适用于 ordered、alarm、interactive 或 manifest broadcast；接收可以被无限期延后。`DEFAULT` 表示未表达偏好，由系统采用默认策略，不等于“一定延迟到设备空闲”。投产前还应确认这些 API 对普通第三方应用是否公开、调用方权限以及接收语义是否允许丢弃或合并。

### Provider：进程启动时通常早于 `Application.onCreate()`

应用进程首次执行 `bindApplication` 时，`ActivityThread.handleBindApplication()` 先创建 `Application`，再按 `data.providers` 安装 Provider，然后调用 `Application.onCreate()`。Provider 的 `onCreate()` 因而是常见的冷启动前置成本。

```text
ActivityThread.handleBindApplication()
  → makeApplicationInner()
  → installContentProviders(app, data.providers)
      → installProvider()
      → ContentProvider.onCreate()
      → publishContentProviders()          [Binder → AMS]
  → callApplicationOnCreate(app)
```

manifest 中的 `android:enabled` 控制组件是否启用，不是 Android 11 起自动延迟 Provider 创建的开关。`initOrder` 控制同一进程中 Provider 的初始化顺序，也不会自动把它们推迟到首次 query。

跨进程首次获取尚未运行的 Provider 时，`ContentProviderHelper` 会启动宿主进程并登记 launching provider。Android 17 需要区分两个时间：

- Provider 已随进程 attach 后，发布超时默认是 `10 秒 × HW_TIMEOUT_MULTIPLIER`；
- 调用方等待 Provider ready 的超时默认是发布超时再加 `10 秒 × HW_TIMEOUT_MULTIPLIER`，合计为 `20 秒 × HW_TIMEOUT_MULTIPLIER`。

应用内的 `ActivityThread.acquireProvider()` 会等待 ready，收到 `ContentProviderHolder` 后安装并缓存 Binder 代理；后续调用通常直接通过该代理到 Provider 进程。Provider 业务方法本身没有一条统一的“`call()` 默认 10 秒超时”。ANR 是否发生取决于调用线程、Binder 阻塞和相应 ANR 检测条件。

Provider 冷启动优化应从其 `onCreate()` 的同步工作入手：只保留轻量对象创建与必要注册，把数据库大扫描、网络、复杂依赖初始化移到可控时机。若组件必须在首个 query 前完成准备，还要明确并发和失败语义，不能只把同步代码丢到后台线程。

## 性能诊断：先定位层，再谈优化

### 1. 确认等待所在的线程

先回答以下问题：

- 调用者在 Binder reply、Java monitor、native futex 还是 I/O 上等待？
- `system_server` 对应 Binder 线程是否在等 AMS/ATMS 锁？
- AMS `mHandler` 或 `:procStart` 队列是否积压？
- 应用主线程是否卡在 Provider、Application、Service/Receiver 回调或 Activity 生命周期？

一段 `startActivity` 慢调用跟踪，可能落在 Intent 解析、Zygote、Provider、应用初始化、窗口同步或首帧。划分阶段后，才能决定检查 AMS、ATMS、PMS、WMS、ART 还是应用代码。

### 2. 同时读取状态与原因

常用入口包括：

```bash
adb shell dumpsys activity processes
adb shell dumpsys activity oom
adb shell dumpsys activity services
adb shell dumpsys activity broadcasts
adb shell dumpsys activity providers
adb shell dumpsys activity activities
adb shell dumpsys meminfo <package-or-pid>
adb shell cat /proc/pressure/memory
adb shell cat /proc/<pid>/oom_score_adj
```

这些命令用于交叉验证：

- `ProcessRecord` 认为进程是什么状态；
- OomAdjuster 给出的 adj 和 reason；
- `lmkd`/内核看到的 `oom_score_adj` 是否一致；
- 进程托管哪些组件、被谁绑定或引用；
- 当前是否有广播、Service 或 Provider 等待；
- 内存压力是否与进程状态变化同时发生。

`dumpsys activity` 的子命令和输出字段属于调试接口，不应被生产解析器当成稳定 API。自动化采集要按具体 Android 版本做兼容和抽样验证。

### 3. 用 Perfetto 验证时序

建议至少同时采集：

- `am`/`wm` 相关 atrace 或对应 Perfetto 数据源；
- Binder transaction 与 Binder lock contention；
- sched/sched_wakeup；
- process stats、LMK 和内存计数；
- 应用主线程、RenderThread 与首帧相关 slice。

关注因果顺序，而非只盯总耗时：

```text
请求进入 system_server
  → 获取全局锁
  → 解析/状态决策
  → 是否请求进程启动
  → Zygote 返回
  → attachApplication / bindApplication
  → Provider / Application
  → 组件 lifecycle
  → 窗口事务和首帧
```

这条时间线应来自同一份 Perfetto 采集。服务端进程启动事件、应用侧 `bindApplication` slice、目标 PID、进程名和启动序列需要能够相互对应；应用自定义首帧点也应使用同一单调时钟域。若只有来自不同进程的墙上时钟日志，不能直接相减得到 Zygote、Binder 或 Provider 的阶段耗时。

若 Zygote 很快而 Provider 区间很长，调整 AMS 锁或缓存进程上限不会解决问题。若 `system_server` Binder 线程长期等待全局锁，继续拆分应用初始化也不会缩短服务端排队。

### 4. 修改系统策略时守住边界

系统厂商或平台开发者常调整 cached 上限、OOM bucket、广播并发、Service 超时或 freezer 参数。每次修改都要同时评估：

- 用户可见切换和冷启动；
- 内存水位、swap、thrashing OOM；
- 后台工作完成率和功耗；
- Binder 队列、锁持有时间和 ANR；
- 多用户、工作资料、isolated/sandbox 进程；
- CTS/GTS 语义与 DeviceConfig 回滚。

提高缓存上限可能减少冷启动，也可能加重 reclaim 和 swap；延长超时可能减少误报，也可能让卡死状态维持更久；提高广播并发可能缩短队列，也可能制造 CPU 与 fork 峰值。参数变化必须用目标设备的压力场景、长稳数据和失败样本验证。

## 常见误区速查

| 说法 | Android 17 的源码结论 |
| --- | --- |
| AMS `mHandler` 就是 `system_server` 主线程 | 生产构造函数创建独立前台优先级 `ServiceThread` |
| Activity 启动由 AMS 完整管理 | Task/Activity 主路径在 ATMS；AMS 提供进程与进程级状态 |
| `ActivityClientController` 向应用下发生命周期 | 它接收 Activity 客户端到 ATMS 的调用；下发使用 `ClientLifecycleManager` |
| `ProcessRecord` 直接拥有全部 adj、Service、Provider 和错误字段 | Android 17 已拆到 `ProcessRecordInternal` 和多个子记录 |
| OOM 更新固定为 `O(N²)` | 现代 bucket/BFS 上界约为 `O(processes × bindings)`，并支持局部更新 |
| AMS 直接写 `oom_score_adj`，再通知 `lmkd` | `ProcessList` 发消息给 `lmkd`，由 `lmkd` 写入 proc 节点 |
| `lmkd` 与 kernel OOM 是同一个杀进程路径 | `lmkd` 做 Android 用户态压力回收，kernel OOM 是独立兜底 |
| Android 17 默认只保留 32 个缓存进程 | AOSP 的默认常量与资源值为 1024；设备有效值可配置，压力下 `lmkd` 也可更早回收 |
| freezer 会预创建常用应用进程 | freezer 冻结符合条件的现有缓存进程 |
| Android 17 默认用 `BroadcastQueueModernImpl` | 源码工厂创建 `BroadcastQueueImpl`，没有该 ModernImpl 文件 |
| 新广播队列不再需要 AMS 全局锁 | 大量状态仍由 `mService` 锁保护 |
| manifest Provider 默认延迟加载 | `bindApplication` 时通常先安装 Provider，再调用 `Application.onCreate()` |
| Provider 调用统一有 10 秒超时 | 发布、ready 等待和业务 Binder 调用是不同机制 |
