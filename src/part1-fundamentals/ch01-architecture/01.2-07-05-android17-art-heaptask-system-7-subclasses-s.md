## 源码核查

`HeapTask` 是 ART runtime 的内部延时任务抽象。Java `HeapTaskDaemon` 通过隐藏的 `VMRuntime` 方法进入 native `TaskProcessor::RunAllTasks()`；`TaskProcessor` 使用按 `target_run_time_` 排序的 `std::multiset` 等待和取出到期任务。单个 `HeapTaskDaemon` 依次执行取出的任务，因此不能把它描述成七类任务并发运行的线程池。

“7 个子类”也不是 `android-17.0.0_r1` 的完整统计。按 ART runtime 生产 C++ 源码搜索可找到 10 个 `HeapTask` 派生类，其中 6 个位于 `runtime/gc/heap.cc`。`ClearedReferenceTask` 虽然继承 `HeapTask`，但该 tag 默认配置下通常由 GC 调用方处理，不进入 `TaskProcessor`。统计时必须同时说明搜索范围和当前路径是否入队。

HeapTask 承载的工作包括并发 GC 请求、收集器切换、heap trim、按时间检查 GC 阈值、post-fork GC 与目标 footprint 调整、启动完成清理、trace 停止和 JIT boot-image 方法映射。它不是只为 GC 服务，也没有面向普通应用的队列、优先级或“GC 抑制”控制 API。

Android 17 源码只能证明这些类和路径在当前 tag 中存在。若要声明某个任务由 Android 17 新增，必须对比早期 release tag 或找到对应提交；单看 r1 类名不能确定首次引入版本。

应用排查时可在 Perfetto 中定位 `HeapTaskDaemon`，再结合 GC cause、collector、暂停时间、allocation 和 heap trim 证据判断具体工作。反射隐藏 `VMRuntime`、修改 ART 私有字段或 patch C++ vtable 会破坏内部 ABI 与任务所有权，也可能连带阻塞 GC 之外的 runtime 任务。
