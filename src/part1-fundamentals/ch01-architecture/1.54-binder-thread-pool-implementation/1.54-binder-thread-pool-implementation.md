# 1.54 Android 17 Binder 线程池实现机制与调优参数

Binder 服务端没有预先填满的固定线程数组。Native libbinder 主动启动一条池线程，Binder 驱动在工作到达且没有空闲线程时再请求 worker。线程上限、等待线程选择、命令执行计数和业务耗时分属不同层次，排查时要分别取证。

平台源码锚点是 `android-17.0.0_r1`，内核锚点是 `android17-6.18-2026-06_r6`。讨论对象是内核 Binder 驱动与 C++ libbinder；Java Binder、NDK Binder 和 RPC Binder 的入口及配置不能直接套用同一组数字。饥饿案例和 Perfetto 查询见 [1.38 Binder 线程池管理与 IPC 线程饥饿性能边界](../38-binder-thread-pool-starvation-performance.md)，事务优先级见 [1.44 Binder IPC 优先级继承](../1.44-binder-ipc-priority-inheritance.md)。

## 一、默认 15 表示什么

`ProcessState` 打开 Binder 设备时会向驱动设置默认 lazy worker 上限，并为接收事务映射虚拟地址空间。下面两行是 Android 17 的原始常量：

```cpp
#define BINDER_VM_SIZE ((1 * 1024 * 1024) - sysconf(_SC_PAGE_SIZE) * 2)
#define DEFAULT_MAX_BINDER_THREADS 15
```

`BINDER_VM_SIZE` 是 1 MiB 减去两个系统页，页面大小由目标设备决定。该映射用于接收事务数据；驱动仍要从发送进程复制数据，因此不能称为“零拷贝”。

`DEFAULT_MAX_BINDER_THREADS = 15` 配置的是驱动最多按需请求多少条 lazy worker。它不包括 `startThreadPool()` 主动创建的 main pool thread，也不限制进程显式调用 `joinThreadPool()` 或采用轮询接口加入的线程。常见原生配置可达到“1 条主动池线程 + 最多 15 条驱动请求线程”，但并非所有进程都固定拥有 16 条 Binder 线程。

### `ProcessState` 中几个计数不能互换

| 字段 | Android 17 类型 | 统计范围 |
|---|---|---|
| `mMaxThreads` | `std::atomic_size_t` | 驱动可请求的 lazy worker 上限 |
| `mCurrentThreads` | `std::atomic_size_t` | 当前已进入 pool 或 polling 路径的线程 |
| `mKernelStartedThreads` | `std::atomic_size_t` | 由 `ProcessState::spawnPooledThread()` 创建的池线程 |
| `mExecutingThreadsCount` | `std::atomic_size_t` | 正在执行一个顶层驱动返回命令的线程 |
| `mThreadPoolStarted` | `std::atomic_bool` | `startThreadPool()` 是否已执行 |

`mExecutingThreadsCount` 包围的是 `executeCommand(cmd)`。这个命令可能是 `BR_TRANSACTION`，也可能是引用计数、完成通知或其他返回命令，所以它不是精确的“正在运行 AIDL 方法数”。`mCurrentThreads` 会在 `joinThreadPool()` 进入和退出时增减，也不是累计创建总数。

## 二、线程如何进入池

### main pool thread 由用户态主动创建

`ProcessState::startThreadPool()` 在锁内把 `mThreadPoolStarted` 设为 `true`，然后调用 `spawnPooledThread(true)`。新线程进入 `IPCThreadState::joinThreadPool(true)`，向驱动发送 `BC_ENTER_LOOPER`。

这里的 main 表示 Binder pool 内的角色，与 Android 应用的 UI 主线程无关。重复调用 `startThreadPool()` 不会再创建一条 main pool thread。

### lazy worker 由驱动请求

驱动在 `binder_thread_read()` 返回前判断是否需要扩容。下面摘录标准分支的条件，同时保留 Android common kernel 的 vendor hook：

```c
if (force_spawn || (proc->requested_threads == 0 &&
    list_empty(&thread->proc->waiting_threads) &&
    proc->requested_threads_started < proc->max_threads &&
    (thread->looper & (BINDER_LOOPER_STATE_REGISTERED |
     BINDER_LOOPER_STATE_ENTERED)))) {
    proc->requested_threads++;
    /* return BR_SPAWN_LOOPER */
}
```

在 `force_spawn` 没有被 vendor hook 改写时，四项条件分别表示：没有尚未兑现的请求、没有普通等待 worker、已注册的请求线程仍低于上限、当前读线程是合法的 Binder looper。`requested_threads` 在发出请求时增加，lazy worker 随后用 `BC_REGISTER_LOOPER` 消耗请求并增加 `requested_threads_started`。

libbinder 在 `IPCThreadState::executeCommand()` 收到 `BR_SPAWN_LOOPER` 后调用 `spawnPooledThread(false)`。创建和注册线程仍要经过用户态调度，一次创建请求发出时还没有可用 worker；线程创建失败或进程退出都会中断这段时序。

### 两种注册命令的记账不同

| 命令 | 常见来源 | 驱动记账 |
|---|---|---|
| `BC_ENTER_LOOPER` | main pool thread、主动 join 或 polling setup | 标记线程已主动进入，不增加 `requested_threads_started` |
| `BC_REGISTER_LOOPER` | `BR_SPAWN_LOOPER` 创建的 lazy worker | 减少 `requested_threads`，增加 `requested_threads_started` |
| `BC_EXIT_LOOPER` | `joinThreadPool()` 返回前 | 标记 looper 已退出 |

如果线程先发过 `BC_ENTER_LOOPER` 又发 `BC_REGISTER_LOOPER`，或没有内核请求却直接 register，驱动会加上 `BINDER_LOOPER_STATE_INVALID` 并记录 user error。`max_threads` 约束的是 register 路径，主动 enter 的线程要单独计数。

## 三、驱动怎样选择等待线程

普通 Binder 工作线程没有事务时会进入 `binder_wait_for_work()`。驱动使用 `list_add()` 把它插到 `waiting_threads` 链表头；事务到达后，`binder_select_thread_ilocked()` 又从链表头取线程。这两个操作组合后的顺序接近后进先出（LIFO）：较晚进入等待的线程较早被选中。

该链表不按 nice、RT priority、历史执行时长或 CPU 负载排序。线程被选中后，Binder 的事务优先级规则还会计算它本次处理的调度策略；获得 CPU 的时间则继续受调度器、cpuset、uclamp 和系统负载影响。

通过 `setupPolling()` 接入 epoll 的线程使用 `BINDER_LOOPER_STATE_POLL`，不一定出现在 `waiting_threads`。找不到普通等待线程时，驱动会扫描可接收进程工作且正在轮询的线程并唤醒它们。观察线程分发时，要先确认服务采用传统 pool 还是 polling。

## 四、worker 会不会因空闲自动缩容

`joinThreadPool(false)` 保留了收到 `BR_FINISHED` 后以 `TIMED_OUT` 退出的兼容分支，退出前会发送并刷新 `BC_EXIT_LOOPER`。`PoolThread::threadLoop()` 在 `joinThreadPool()` 返回后返回 `false`，表示该 `Thread` 对象不再重复运行。

在 `android17-6.18-2026-06_r6` 的 Binder 驱动中，`BR_FINISHED` 仍有 UAPI 命令定义和调试字符串，但常规 `binder_thread_read()` 路径不发送它。因此 lazy worker 不会按可配置的 idle timeout 周期性退出，再由驱动补回。Android 17 AOSP 也没有 `idle_timeout` 线程池参数。

进程退出、Binder fd 失效或其他错误仍可让 `joinThreadPool()` 结束。这里讨论的是空闲状态下的正常行为，不能扩展成线程永远不会退出。

## 五、100 ms 饥饿日志如何解释

`IPCThreadState::getAndExecuteCommand()` 在执行一个顶层返回命令前增加 `mExecutingThreadsCount`。计数达到 `mMaxThreads` 时记录时间；计数回落到阈值以下后计算持续时间，超过 100 ms 才输出类似日志：

```text
binder thread pool (15 threads) starved for 234 ms
```

这条日志证明 libbinder 的命令执行计数曾持续达到配置阈值。它没有直接读取驱动 todo 队列，也不能证明所有线程都在执行服务方法。嵌套同步调用、锁等待、引用计数命令、调度延迟和慢 I/O 仍要结合调用链核对。

100 ms 是 `IPCThreadState.cpp` 中的字面量，没有公开的运行时开关。相同的饥饿记账在 Android 14 tag 中已经存在；Android 16 起把旧 mutex/condition 与整数时间戳实现调整为 C++ 原子计数、`std::condition_variable` 和 `steady_clock`。它不是 Android 17 新增机制。

### `blockUntilThreadAvailable()` 不在标准 `transact()` 路径自动执行

这个公开方法会显式等待 `mExecutingThreadsCount < mMaxThreads`。Android 17 的实现用 `mOnThreadAvailableCondVar` 休眠；命令执行结束且存在等待者时调用 `notify_all()`。

标准 `IPCThreadState::transact()`、`talkWithDriver()` 和 `getAndExecuteCommand()` 没有自动调用 `blockUntilThreadAvailable()`。因此线程池达到阈值不会让进程内每一笔新出站 Binder 调用都先经过这个条件变量，也不能把它视为驱动队列的背压实现。只有明确调用该 API 的上层代码才会受它约束。

## 六、线程上限怎样设置

Native libbinder 的配置入口是 `ProcessState::setThreadPoolMaxThreadCount()`。下面的源码片段展示线程池启动后的收缩保护：

```cpp
LOG_ALWAYS_FATAL_IF(mThreadPoolStarted && maxThreads < mMaxThreads,
        "Binder threadpool cannot be shrunk after starting");
ioctl(mDriverFD, BINDER_SET_MAX_THREADS, &maxThreads);
```

线程池启动后传入更小的值会终止进程；传入更大的值可以更新驱动和 `mMaxThreads`。驱动处理 `BINDER_SET_MAX_THREADS` 时只写 `proc->max_threads`，不会立即创建线程，也不会验证某个业务负载是否适合这个数值。

配置最好在 `startThreadPool()` 前完成。把上限设为 0 是特殊用法，调用 `startThreadPool()` 仍会额外创建 main pool thread 并输出配置警告；采用 polling 或自行 join 的服务还要按自己的启动模型计算。

Android 17 的 `system_server` 在启动阶段通过 `BinderInternal.setMaxThreads(31)` 把 lazy worker 上限设为 31。这个调用不会一次创建 31 条线程，main pool thread 和其他主动加入者也不包含在 31 内。普通应用、native daemon、HAL 以及厂商进程可能使用不同 Binder 设备和初始化入口，诊断时应读取目标产品源码与运行时线程。

Android 17 AOSP 的 Binder 线程池没有 `priority_threshold`、`queue_threshold`、`starvation_threshold` 和 `idle_timeout` 这些配置参数。线程优先级由事务、目标节点和调度限制计算，不是池上限的附属阈值。

## 七、何时调大线程池

线程池耗尽常由服务方法长期持锁、阻塞 I/O、慢数据库访问、嵌套同步 IPC 或下游资源不足引起。提高上限只增加并发进入服务的机会，不会增加数据库连接、设备队列或共享锁的容量。

| 观测结果 | 可能方向 | 处理方式 |
|---|---|---|
| worker 多数等待同一把锁 | 锁竞争 | 缩短临界区，避免持锁跨进程调用 |
| worker 多数等待磁盘、设备或下游 IPC | 阻塞依赖 | 设置超时，减少同步工作，修复下游容量 |
| worker 长时间 runnable 但未获 CPU | 调度或 CPU 饱和 | 检查 CPU、cpuset、uclamp 与高优先级负载 |
| 驱动/Perfetto 显示事务排队，工作线程任务彼此独立 | 并发不足 | 在目标设备上试验提高上限 |
| 高频 oneway 在单一 node 排队 | async 串行与生产过快 | 限频、合并状态、设计有界队列 |

调大上限前，应验证请求之间可以安全并行，服务内部锁与下游资源仍有余量，并用相同 workload 比较排队时间、CPU、内存和尾延迟。若所有请求都卡在同一依赖上，增加 worker 只会增加等待者。

## 八、Android 17 诊断步骤

下面这组命令用于快速确认目标进程的线程、libbinder 饥饿日志和方法级统计：

```bash
adb shell ps -T -p "$(adb shell pidof -s com.example.app)"
adb logcat -b all -s libbinder.IPCThreadState:E
adb shell dumpsys binder_calls_stats
```

线程列表只能说明当时有哪些线程；饥饿日志是用户态阈值信号；`binder_calls_stats` 更适合找高频或高服务端耗时的方法。三者都不能单独给出驱动排队时间。

完整分析应在同一时间轴上对齐：

1. 同步调用方从 transaction 到 reply 的 wall time；
2. 服务端 Binder transaction 何时开始与结束；
3. 目标进程各 worker 的 Running、Runnable、锁等待和 I/O 状态；
4. `BR_SPAWN_LOOPER`、线程注册与目标进程 todo 的变化；
5. 下游 Binder、数据库、文件系统或设备队列。

Perfetto 的 `android.binder` 与 `android.binder_breakdown` 模块可以关联 client/server slice 和调度状态。`client_dur - server_dur` 还会混入传输、调度和其他边界开销，不能直接命名为“驱动队列耗时”。binderfs/debugfs 状态节点是否可读取取决于构建类型、挂载和 SELinux，工具脚本应允许节点缺失。
