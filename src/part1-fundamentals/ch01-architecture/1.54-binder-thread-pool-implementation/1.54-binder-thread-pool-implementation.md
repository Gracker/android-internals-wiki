# 1.54 Android 17 Binder 线程池实现机制与调优参数

> 本节从**源码级**剖析 Binder 线程池的用户态/内核态协同机制、精确的参数语义与约束。线程饥饿场景诊断、ANR 关联分析、Perfetto 工作流详见 §1.38。

## 要点

### 🔹 ProcessState 单例与核心状态量

Android 每个进程在首次使用 Binder 时，`ProcessState::self()` 完成单例初始化。`ProcessState` 持有 **5 个核心原子状态量**控制线程池生命周期：

| 状态量 | 类型 | 语义 |
|--------|------|------|
| `mMaxThreads` | `size_t` | 线程池上限，默认 `DEFAULT_MAX_BINDER_THREADS = 15` |
| `mExecutingThreadsCount` | `atomic` | 正在执行 `executeCommand()` 的线程数 |
| `mCurrentThreads` | `atomic` | 已 `joinThreadPool` 的线程总数（含已退出的累计递减） |
| `mKernelStartedThreads` | `atomic` | 已 spawn 给内核的线程数（只增不减） |
| `mThreadPoolStarted` | `bool` | 池启动标志，`true` 后 `startThreadPool()` 变为 no-op |

[已验证: AOSP android-17.0.0_r1, frameworks/native/libs/binder/ProcessState.cpp:605-620, 构造函数初始化列表]

**构造函数关键常量**：

```cpp
// ProcessState.cpp line 48-49
#define BINDER_VM_SIZE ((1 * 1024 * 1024) - sysconf(_SC_PAGE_SIZE) * 2)
#define DEFAULT_MAX_BINDER_THREADS 15
```

`BINDER_VM_SIZE` 约 1MB 减去 2 个保护页（4K 体系下约 1032KB），是每个进程通过 `mmap` 一次性映射的 Binder 事务共享内存大小。这段内存由内核驱动管理，用于 zero-copy 传递 transaction 数据。

[已验证: AOSP android-17.0.0_r1, frameworks/native/libs/binder/ProcessState.cpp:48-49]

**fork 安全机制**：`ProcessState::init()` 使用 `[[clang::no_destroy]]` 标注 `static std::once_flag`，保证全局静态不在动态库卸载时被析构。同时通过 `pthread_atfork` 注册三阶段钩子（`onFork` / `parentPostFork` / `childPostFork`）：子进程 fork 后关闭 `mDriverFD` 并标记 `mForked = true`，防止子进程误用父进程的 binder 连接。

```cpp
// ProcessState::init() — 简化
sp<ProcessState> ProcessState::init(const char* driver, bool requireDefault) {
    [[clang::no_destroy]] static std::once_flag gProcessOnce;
    std::call_once(gProcessOnce, [&](){
        gProcess = sp<ProcessState>::make(driver);
    });
    return gProcess;
}
```

### 🔹 内核侧 BR_SPAWN_LOOPER 四条件守门

Binder 线程的按需创建由**内核驱动**决定，不是用户态主动判断。内核在 `binder_thread_read()` 的 `done` 段中评估是否需要请求用户态创建新线程：

```c
// drivers/android/binder.c — BR_SPAWN_LOOPER 触发条件
if (force_spawn ||
    (proc->requested_threads == 0 &&
     list_empty(&thread->proc->waiting_threads) &&
     proc->requested_threads_started < proc->max_threads &&
     (thread->looper & (BINDER_LOOPER_STATE_REGISTERED |
      BINDER_LOOPER_STATE_ENTERED)))) {
    proc->requested_threads++;
    binder_inner_proc_unlock(proc);
    if (put_user(BR_SPAWN_LOOPER, (uint32_t __user *)buffer))
        return -EFAULT;
    binder_stat_br(proc, thread, BR_SPAWN_LOOPER);
} else {
    binder_inner_proc_unlock(proc);
}
```

[已验证: AOSP, drivers/android/binder.c:5397-5411, kernel android16-6.12]

四个守门条件**全部为真**才会发送 `BR_SPAWN_LOOPER`：

| # | 条件 | 语义 | 设计意图 |
|---|------|------|----------|
| 1 | `requested_threads == 0` | 没有"已请求但未注册"的待办 | 防止重复 spawn：内核每发 1 个 `BR_SPAWN_LOOPER` 就 `requested_threads++`，用户态每收到 1 个就 spawn 1 个线程并回 `BC_REGISTER_LOOPER`（`requested_threads--`） |
| 2 | `list_empty(&waiting_threads)` | 进程级等待线程链表为空 | 防止"有可复用线程但被搁置"时浪费资源新建 |
| 3 | `requested_threads_started < max_threads` | 累计已注册线程数 < 用户态设置的上限 | 总量控制：`max_threads` 由 `BINDER_SET_MAX_THREADS` ioctl 写入 |
| 4 | 当前线程处于 REGISTERED 或 ENTERED 状态 | 是真实的 binder 工作线程在接收 BR | 防止非 binder 线程误触发 spawn |

**关键不变量**：`proc->requested_threads_started` 永远不超过 `proc->max_threads`，内核的 1 次 spawn 请求严格对应 1 次 `BC_REGISTER_LOOPER` 偿还。

### 🔹 BC_REGISTER_LOOPER 与 BC_ENTER_LOOPER 的计数语义

两种线程注册方式在内核侧的计数行为截然不同：

```c
// binder.c — BC_REGISTER_LOOPER 处理
case BC_REGISTER_LOOPER:
    binder_inner_proc_lock(proc);
    if (thread->looper & BINDER_LOOPER_STATE_ENTERED) {
        thread->looper |= BINDER_LOOPER_STATE_INVALID;  // 错误：先 ENTER 再 REGISTER
    } else if (proc->requested_threads == 0) {
        thread->looper |= BINDER_LOOPER_STATE_INVALID;  // 错误：未经内核请求
    } else {
        proc->requested_threads--;            // 偿还 spawn 请求
        proc->requested_threads_started++;    // 累计已注册数
    }
    thread->looper |= BINDER_LOOPER_STATE_REGISTERED;
    break;

case BC_ENTER_LOOPER:
    // main 线程专用，不修改 requested_threads 计数
    thread->looper |= BINDER_LOOPER_STATE_ENTERED;
    break;
```

[已验证: AOSP, drivers/android/binder.c:4574-4596, kernel android16-6.12]

| 注册命令 | 使用者 | requested_threads 影响 | max_threads 计数 |
|---------|--------|----------------------|-----------------|
| `BC_ENTER_LOOPER` | 主线程 / 主动 join 的线程 | 无影响（不参与 spawn 计数） | 不受约束 |
| `BC_REGISTER_LOOPER` | `BR_SPAWN_LOOPER` 触发创建的 worker | `-1`（偿还请求） | `requested_threads_started +1`，受 `max_threads` 约束 |

**设计含义**：主线程通过 `BC_ENTER_LOOPER` 注册时不计入 `max_threads` 上限。这意味着一个 `mMaxThreads = 15` 的进程实际上可以有 16 个 binder 线程（15 个 worker + 1 个 main）。内核选择等待线程时使用 FIFO 链表 `waiting_threads`，不区分 main/worker——所有已注册线程平等竞争事务分发。

[已验证: AOSP, drivers/android/binder.c:614-625, `binder_select_thread_ilocked` 使用 `list_first_entry_or_null` 纯 FIFO]

### 🔹 用户态 joinThreadPool 主循环与线程退出语义

`IPCThreadState::joinThreadPool(bool isMain)` 是每个 binder 线程的入口函数，核心循环：

```cpp
void IPCThreadState::joinThreadPool(bool isMain) {
    mProcess->mCurrentThreads++;
    mOut.writeInt32(isMain ? BC_ENTER_LOOPER : BC_REGISTER_LOOPER);
    mIsLooper = true;
    status_t result;
    do {
        processPendingDerefs();
        result = getAndExecuteCommand();
        if (result == TIMED_OUT && !isMain) {
            break;  // 非 main 线程超时后主动退出
        }
    } while (result != -ECONNREFUSED && result != -EBADF);

    mOut.writeInt32(BC_EXIT_LOOPER);
    size_t oldCount = mProcess->mCurrentThreads.fetch_sub(1);
    LOG_ALWAYS_FATAL_IF(oldCount == 0,
        "Threadpool thread count underflowed...");
}
```

[已验证: AOSP android-17.0.0_r1, frameworks/native/libs/binder/IPCThreadState.cpp:868-905]

**关键设计**：

1. **非 main 线程空闲超时退出**：`TIMED_OUT && !isMain` 触发 `break`，发送 `BC_EXIT_LOOPER` 后线程结束。这意味着 binder 池在空闲时不会无限制保留 worker 线程——它们会自然退出，下次需要时由内核通过 `BR_SPAWN_LOOPER` 重新创建。

2. **`mCurrentThreads` 下溢保护**：退出时 `fetch_sub(1)`，若减到 0 则 `LOG_ALWAYS_FATAL` 直接 abort。这要求进程在主线程退出前必须保持池中至少一个存活线程。

3. **`PoolThread::threadLoop()` 返回 `false`**：Thread 框架不再重复调用，线程彻底结束。

```cpp
class PoolThread : public Thread {
public:
    explicit PoolThread(bool isMain) : mIsMain(isMain) {}
protected:
    virtual bool threadLoop() {
        IPCThreadState::self()->joinThreadPool(mIsMain);
        return false;  // 一次性，不循环
    }
};
```

[已验证: AOSP android-17.0.0_r1, frameworks/native/libs/binder/ProcessState.cpp:86-99]

### 🔹 blockUntilThreadAvailable 条件变量等待机制

当 `talkWithDriver()` 拿到进站 transaction 但发现本进程 binder 线程全部在忙时（`mExecutingThreadsCount >= mMaxThreads`），调用 `blockUntilThreadAvailable()` 阻塞等待：

```cpp
void IPCThreadState::blockUntilThreadAvailable() {
    std::unique_lock lock_guard_(mProcess->mOnThreadAvailableLock);
    mProcess->mOnThreadAvailableWaiting++;
    mProcess->mOnThreadAvailableCondVar.wait(lock_guard_, [&] {
        size_t max = mProcess->mMaxThreads;
        size_t cur = mProcess->mExecutingThreadsCount;
        if (cur < max) return true;
        ALOGW("Waiting for thread to be free. mExecutingThreadsCount=%zu "
              "mMaxThreads=%zu\n", cur, max);
        return false;
    });
    mProcess->mOnThreadAvailableWaiting--;
}
```

[已验证: AOSP android-17.0.0_r1, frameworks/native/libs/binder/IPCThreadState.cpp:740-755]

**注意**：此等待是**进程内**的——限制的是本进程新发起 binder 调用的线程，而非进站事务处理。等待期间不主动 spawn 新线程（避免无脑扩容到 `mMaxThreads`），而是通过条件变量等待某个 worker 完成当前事务后释放容量。

**线程唤醒通知路径**：worker 线程在 `getAndExecuteCommand()` 结束时 `mExecutingThreadsCount.fetch_sub(1)`，随后 `notify_one()` 唤醒等待者。这条路径是 binder 线程池背压的用户态核心机制。

### 🔹 setThreadPoolMaxThreadCount 单向调升约束

唯一的运行时调优入口是 `ProcessState::setThreadPoolMaxThreadCount(size_t maxThreads)`：

```cpp
status_t ProcessState::setThreadPoolMaxThreadCount(size_t maxThreads) {
    LOG_ALWAYS_FATAL_IF(mThreadPoolStarted && maxThreads < mMaxThreads,
           "Binder threadpool cannot be shrunk after starting");
    status_t result = NO_ERROR;
    if (ioctl(mDriverFD, BINDER_SET_MAX_THREADS, &maxThreads) != -1) {
        mMaxThreads = maxThreads;
    } else {
        result = -errno;
        ALOGE("Binder ioctl to set max threads failed: %s", strerror(-result));
    }
    return result;
}
```

[已验证: AOSP android-17.0.0_r1, frameworks/native/libs/binder/ProcessState.cpp:451-462]

**核心约束**：

1. **只能调高，不能调低**：如果 `mThreadPoolStarted` 已为 `true`，传入比当前 `mMaxThreads` 小的值会触发 `LOG_ALWAYS_FATAL` 直接 abort 进程。
2. **双写**：先通过 `BINDER_SET_MAX_THREADS` ioctl 写入内核 `proc->max_threads`，再更新用户态 `mMaxThreads`。
3. **时序要求**：SystemServer 和 vendor 进程通常在启动早期（`startThreadPool()` 之前）调用一次设置上限。运行时再调很危险。

内核侧 `BINDER_SET_MAX_THREADS` 处理极简，仅写字段无校验：

```c
case BINDER_SET_MAX_THREADS: {
    u32 max_threads;
    if (copy_from_user(&max_threads, ubuf, sizeof(max_threads))) {
        ret = -EINVAL; goto err;
    }
    binder_inner_proc_lock(proc);
    proc->max_threads = max_threads;
    binder_inner_proc_unlock(proc);
    break;
}
```

[已验证: AOSP, drivers/android/binder.c:6046-6057, kernel android16-6.12]

### 🔹 100ms 饥饿检测：用户态增强（非内核功能）

> §1.38 已详述此机制的诊断视角，此处补充源码级实现。

`mStarvationStartTime` 是 `ProcessState` 的 `atomic<steady_clock::time_point>` 成员。`getAndExecuteCommand()` 在线程计数达到上限时记录起始时间戳，回落时计算持续时间：

```cpp
status_t IPCThreadState::getAndExecuteCommand() {
    status_t result;
    result = talkWithDriver();
    if (result >= NO_ERROR) {
        size_t newThreadsCount =
            mProcess->mExecutingThreadsCount.fetch_add(1) + 1;
        // 线程池满载 → 开始计时
        if (newThreadsCount >= mProcess->mMaxThreads) {
            auto expected = ProcessState::never();
            mProcess->mStarvationStartTime.compare_exchange_strong(
                expected, std::chrono::steady_clock::now());
        }
        result = executeCommand(cmd);
        // 线程释放 → 检查饥饿时长
        size_t maxThreads = mProcess->mMaxThreads;
        newThreadsCount =
            mProcess->mExecutingThreadsCount.fetch_sub(1) - 1;
        if (newThreadsCount < maxThreads) {
            auto starvationStartTime =
                mProcess->mStarvationStartTime.exchange(ProcessState::never());
            if (starvationStartTime != ProcessState::never()) {
                auto starvationTime =
                    std::chrono::steady_clock::now() - starvationStartTime;
                if (starvationTime > 100ms) {
                    ALOGE("binder thread pool (%zu threads) starved for %"
                          PRId64 " ms", maxThreads, to_ms(starvationTime));
                }
            }
        }
    }
    return result;
}
```

[已验证: AOSP android-17.0.0_r1, frameworks/native/libs/binder/IPCThreadState.cpp:760-820]

**关键实现细节**：

1. `compare_exchange_strong` 保证只有第一个检测到满载的线程写入时间戳，避免多线程竞争。
2. 100ms 阈值是**硬编码**的 `100ms` 字面量（C++14 用户定义字面量），不是可配置参数。
3. 这是 **Android 14+ 引入的 libbinder 用户态增强**，内核 API 不涉及。Android 12 无此机制。

### 🔹 线程优先级与 FLAT_BINDER_FLAG 标志位

Binder 驱动支持通过 `flat_binder_object.flags` 在 transaction 传递时临时修改目标线程的调度优先级：

| Flag | 语义 | 设置方式 |
|------|------|----------|
| `FLAT_BINDER_FLAG_PRIORITY_MASK` | 优先级数值（0-99） | `flags & 0xFF` |
| `FLAT_BINDER_FLAG_SCHED_POLICY_MASK` | 调度策略（SCHED_NORMAL/FIFO/RR） | `(flags >> 8) & 0x3` |
| `FLAT_BINDER_FLAG_INHERIT_RT` | 继承调用方 RT 优先级 | `(flags >> 9) & 0x1` |

内核在 `binder_transaction_priority()` 中通过 `scheduler_setattr()` 临时提升目标线程优先级，transaction 完成后 `binder_restore_priority()` 恢复。这是 binder 避免"高优先级调用者被低优先级服务卡住"的核心机制。

> 优先级继承机制的完整分析详见 §1.48。

### 🔸 不同进程类型的配置差异

| 进程类型 | 典型 `mMaxThreads` | 设置方式 | 说明 |
|---------|-------------------|----------|------|
| 普通应用进程 | 15（默认） | 不修改 | 绝大多数 App 不需要调高 |
| `system_server` | 31 | `SystemServer.java` 启动时设置 | 承载 AMS/PMS/WMS 等数十个核心服务 |
| `surfaceflinger` | 视厂商而定 | `init.rc` 或代码 | 渲染合成高频 IPC |

| 轻量 AIDL 服务 | 4-8 | `setThreadPoolMaxThreadCount()` | 自定义 Service 调低以减少开销 |
