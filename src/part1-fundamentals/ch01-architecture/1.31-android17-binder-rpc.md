# 1.31 Android 17 Binder RPC 事务上限优化与性能影响

当前实现锚点为 Android 17 / API 37 / `android-17.0.0_r1`。源码中确有 600 KiB 的 RPC Binder 限制，但它在 `android-16.0.0_r1` 已经存在。Android 17 保留该数值，并补强发送端和回复端的完整 wire packet 校验。

600 KiB 只约束 libbinder RPC transport。普通 `/dev/binder` 调用仍由内核 Binder 的目标进程映射区和驱动分配器约束。把两套容量相加、互相套用，都会得到错误结论。

Binder 基础路径见 [Binder IPC 机制与性能影响](./04-binder.md)。

## 版本差分

| 标签 | RPC 接收分配保护 | 发送与回复校验 | 大事务日志阈值 |
|---|---|---|---|
| `android-15.0.0_r1` | `CommandData` 使用局部常量 `100 * 1000` 字节 | 发送前没有 Android 17 这两处完整 packet 校验 | 300 KiB，以 `BpBinder.cpp` / `Binder.cpp` 内部宏表示 |
| `android-16.0.0_r1` | 改用 `kRpcTransactionLimitBytes = 600 * 1024` | 接收分配受 600 KiB 保护，尚无 Android 17 的 request/reply 主动校验 | 移入 `Constants.h`，数值仍为 300 KiB |
| `android-17.0.0_r1` | 保持 600 KiB | 请求发送前检查完整正文；回复超限时清空载荷并返回失败状态 | 保持 300 KiB，并增加服务端入站日志 |

100,000 字节到 614,400 字节的扩大属于 Android 15 到 Android 16 的变化。Android 17 改善了边界执行和 transport 错误处理，没有再次扩大上限。

## 两个常量分别管什么

下面是 Android 16 与 Android 17 完全相同的常量定义：

```cpp
namespace android::binder {

constexpr size_t kLogTransactionsOverBytes = 300 * 1024;
constexpr size_t kRpcTransactionLimitBytes = 600 * 1024;

} // namespace android::binder
```

`kLogTransactionsOverBytes` 是日志阈值。代码使用 `>` 比较，所以恰好 300 KiB 不触发这条警告；超过阈值也不会仅因这条检查而失败。

`kRpcTransactionLimitBytes` 是 RPC 线协议数据包的保护上界。它不是“应用可以写满的 600 KiB Parcel”，因为 packet 中还有 `RpcWireHeader`、`RpcWireTransaction` 或 `RpcWireReply`、对象位置表等开销。

`Constants.h` 的注释说明，这个数值服务于一个特定 use case，并提到 Baklava 时期 RPC Binder 缺少 shared memory 支持。该注释同时要求尽量避免这类大事务。它不能推导出“所有 RPC 传输层都不能传文件描述符”：`RpcSession` 还定义了 `NONE`、`UNIX` 和 `TRUSTY` 三种 FD transport mode，能力取决于会话与底层 transport。

## Android 17 怎样执行上限

### 请求发送

`RpcState::transactAddress()` 先计算 request body：

`sizeof(RpcWireTransaction) + Parcel dataSize + object table byteSize`

下面的源码分支在发送前拒绝过大的完整 packet：

```cpp
if (bodySize >= binder::kRpcTransactionLimitBytes - sizeof(RpcWireHeader)) {
    ALOGE("Transaction for function %s, too large: %" PRIu32 " body size bytes.",
          functionNameLog(maybeBinder, code).c_str(), bodySize);
    return FAILED_TRANSACTION;
}
```

比较符号是 `>=`。因此标头加正文必须严格小于 614,400 字节，可用的 Parcel 空间还会随对象数量和 wire protocol 结构变化。把 614,400 当成 `Parcel.dataSize()` 的安全值会越界。

### 接收分配

`CommandData(size)` 在 `size > kRpcTransactionLimitBytes` 时拒绝分配，并在 `size > kLogTransactionsOverBytes` 时写 warning。这里保护的是接收端根据对方标头申请动态内存的动作。它不代表一次事务的全部内存峰值，也不提供业务级流控。

### 回复发送

服务端构造回复时也会计算：

`RpcWireReply size + reply dataSize + object table byteSize`

若标头与正文无法保持在限制内，Android 17 清空 reply data 和 object table，把 `replyStatus` 改为 `FAILED_TRANSACTION`，再向调用方发送失败回复。这个动作避免对端按超大标头申请内存。

### 传输层系统调用分块

Android 17 的 `RpcTransportUtils.h` 把单次读写尝试的初始 `chunkSize` 设为 600 KiB；遇到 vhost-vsock `ENOMEM` 时可以降低到页大小并重试。这里切分的是 `sendmsg()` / `recvmsg()` 处理的 iovec 字节，不会把一个 RPC 调用变成多个可独立重放的业务事务，也不会绕过 wire packet 上限。

## 与内核 Binder 的边界

`BpBinder::transact()` 先检查 `isRpcBinder()`：

- `true`：调用 `RpcSession::transact()`，进入上述 RPC 数据包限制；
- `false`：调用 `IPCThreadState::transact()`，进入内核 Binder 驱动。

Android 17 的 `ProcessState.cpp` 仍把内核 Binder 映射大小定义为：

`1 MiB - 2 × sysconf(_SC_PAGE_SIZE)`

这是每个目标进程的入站 Binder 映射区，多笔尚未释放的事务共享。驱动分配失败为 `-ENOSPC` 或 `-ENOMEM` 时走 `BR_FAILED_REPLY`；`BR_DEAD_REPLY` 对应目标已死亡、VMA 已清理等死亡路径。缓冲区不足不会自动阻塞等待，也不能统一归为 `BR_DEAD_REPLY`。

RPC Binder 不从这段目标进程内核 Binder 映射区分配载荷。一笔接近 600 KiB 的 RPC 数据包不会占用 `BINDER_VM_SIZE` 的“约 60%”。反方向也一样：kernel Binder 的并发映射压力不能用于计算 RPC 数据包还能剩多少空间。

普通应用通过 `ContentResolver` 访问 ContentProvider 时，常见路径是内核 Binder。只有实际取得的 `BpBinder` 由 `RpcSession` 创建、`isRpcBinder()` 为 `true`，600 KiB 限制才适用。不能因为接口形式像 RPC，就把 ContentProvider、AIDL 或 ServiceManager 调用默认算成 RPC Binder。

## 共享内存与 FD

kernel Binder 可以在 Parcel 中传递文件描述符，但“大 Parcel 自动回退成 ashmem”并不存在。调用双方需要显式约定 `ParcelFileDescriptor`、memfd、共享内存或文件协议；CursorWindow 也是专门设计的共享窗口协议。

RPC Binder 是否能传 FD 由 `RpcSession::FileDescriptorTransportMode` 决定。Unix 域套接字可以用 ancillary data 传 FD，Trusty 可以传 IPC handle，其他会话可以设为 `NONE`。即使 FD 能传递，也不代表框架会把超过阈值的 byte array 自动移入共享内存。

大对象协议应把 metadata 与 bulk data 分开：RPC 事务只传长度、版本、校验值和句柄，数据放在 transport 支持的共享区域或流式通道。若 transport 无法传 FD，则使用显式分片、流或上层文件传输协议，并设计顺序、重试、取消和完整性校验。

## 300 KiB 日志怎样理解

Android 17 的三条常见警告是：

| 位置 | log tag | 消息前缀 | 适用范围 |
|---|---|---|---|
| `BpBinder.cpp` | `libbinder.BpBinder` | `Large outgoing transaction` | 选择传输层之后记录，kernel 与 RPC Binder 都可能出现 |
| `Binder.cpp` 入站 | `libbinder.Binder` | `Large data transaction` | 本地 BBinder 接收请求 |
| `Binder.cpp` 回复 | `libbinder.Binder` | `Large reply transaction` | 本地 BBinder 生成回复 |

`RpcState::CommandData` 还可能用 `libbinder.RpcState` 输出 `Transaction too large: inefficient and in danger of breaking`。300 KiB 是排查起点，不是推荐批大小，也不是事务成功保证。

下面的命令只筛选相关 log tag，便于区分警告与 hard failure：

```bash
adb logcat -v threadtime \
  -s libbinder.BpBinder libbinder.Binder libbinder.RpcState
```

看到警告后，应记录接口 descriptor、transaction code/function、flags、Parcel data size、对象表大小、transport 类型和并发量。`Transaction for function ... too large` 或 `Reply transaction ... too large` 才直接对应 Android 17 的 RPC 线协议上限检查。

## 错误怎样到达调用方

Native RPC Binder 的主动上限检查返回 `FAILED_TRANSACTION`。Java Binder JNI 对这个状态仍使用启发式映射：

- 方法允许抛 `RemoteException` 且请求 Parcel 大于 200 KiB 时，倾向抛 `TransactionTooLargeException`；
- 其他情况可能映射为 `DeadObjectException` 或运行时异常；
- `FAILED_TRANSACTION` 还可能来自格式错误、关闭的 FD 等原因。

因此，异常类本身不能证明失败发生在请求还是回复，也不能证明命中了 RPC 600 KiB 检查。Android 17 的 `TransactionTooLargeException` 文档也要求调用方按“可能部分执行”处理，避免盲目重试有副作用的操作。

## 性能与兼容性

600 KiB 允许 Android 16/17 的 RPC Binder 接收比 Android 15 更大的 packet，但“能发送”不等于“适合发送”。实际成本受 Parcel 对象、FD、socket 或 vsock、线程排队、内存分配和复制次数影响，源码不能推出固定的 1.2 MiB 峰值、1.8 MiB 拷贝量或 ART GC 次数。

业务协议可以采用以下约束：

1. 为请求和回复分别设置远低于 transport hard limit 的业务上限；
2. 对数组、字符串和嵌套 Parcelable 限制元素数与总字节数；
3. 大数据使用流、FD 或共享内存，并保留分片方案；
4. 在 Android 15～17 混合端点中按能力协商，不能只看本地 `SDK_INT`；
5. 对超限失败记录原始 native status 与 transport，Java 异常只作为一条线索。

`Build.VERSION.SDK_INT >= 37` 无法可靠判断对端 libbinder 版本、RpcSession 传输类型或协议能力。原有分片协议也不应仅因本地系统升级就删除。

## Perfetto 观测边界

kernel Binder driver 的 `binder_transaction` trace event 只覆盖 `/dev/binder` 路径。RPC Binder 通过 socket、vsock 或 Trusty transport 传输，不能把一条 kernel Binder slice 当作 RPC packet 证据。

分析 RPC Binder 时，组合以下证据更可靠：

- libbinder 大事务与 hard-failure 日志；
- 应用或 native service 自己标记的接口跟踪；
- RPC 工作线程的调度与阻塞状态；
- socket/vsock 的 syscall、吞吐和 `ENOMEM`；
- 同一请求的 Parcel data size、object count 与端到端耗时。

若 trace 中只有 kernel Binder transaction，应回到 `BpBinder::isRpcBinder()` 与服务建立方式核对 transport。
