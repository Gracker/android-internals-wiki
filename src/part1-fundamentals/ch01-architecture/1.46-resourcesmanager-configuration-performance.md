# 1.46 Android 17 ResourcesManager 与 Configuration 变更性能

> **版本边界**：本节基于 Android 17 (API 37) 源码验证，版本基线 `android-17.0.0_r1`。Android 14 以下的部分机制（WeakReference 缓存化、seq 比对）作为背景知识引用。
>
> **定位**：1.24 节从**实战角度**覆盖了 ResourcesManager 与 Configuration 变更的性能问题（卡顿排查、configChanges 声明、避免 recreate 策略）。1.48 节从**判定模型角度**分析了 `shouldRelaunchLocked()` 的位掩码逻辑。本节从**源码内部机制角度**切入，覆盖 Configuration 派发流水线的进程间通信、ResourcesManager 的锁与缓存、以及 Android 17 新增的系统级优化。三者互补，不重复展开。

## 要点

### 锚点 1：Configuration 派发的 8 段式流水线

Configuration 变更从系统服务到 App 进程的完整传递路径，是理解性能开销的起点。

[已验证: AOSP android-17.0.0_r1, 完整调用链 ATMS → WPC → ConfigurationChangeItem → ActivityThread → ConfigurationController → ResourcesManager → ActivityRecord.ensureActivityConfiguration]

```
(1) ATMS.updateConfigurationLocked()
  → (2) updateGlobalConfigurationWithTransition()
    → diffPublicOnly() 计算 changes
    → Shell Transitions 收集
  → (3) updateGlobalConfigurationLocked()
    → mResConfiguration 更新
    → mSystemThread.applyConfigurationToResources()
    → 遍历 pidMap: WPC.onConfigurationChanged()
  → (4) WPC.dispatchConfiguration(config)
    → config.seq = increaseConfigurationSeqLocked()  // 单调递增
    → CACHED 进程短路检查
    → scheduleClientTransactionItem(ConfigurationChangeItem)
  → (5) ConfigurationChangeItem.preExecute()
    → updatePendingConfiguration()
  → ConfigurationChangeItem.execute()
    → (6) ActivityThread.handleConfigurationChanged()
      → (7) ConfigurationController.handleConfigurationChangedInner()
        → ResourcesManager.applyConfigurationToResources()
        → ComponentCallbacks2 回调
      → (8) RootWindowContainer.onConfigurationChanged()
        → ActivityRecord.ensureActivityConfiguration()
        → shouldRelaunchLocked() 判定
        → relaunchActivityLocked() 或 scheduleConfigurationChanged()
```

关键性能特征：

- **diffPublicOnly 早返回**：`Configuration.diffPublicOnly()` 在全局 Configuration 对比中只计算 App 可见的字段变化。如果 `diffPublicOnly == 0`，`ConfigurationController` 不会回调任何 `ComponentCallbacks2`——纯内部字段（如 `appBounds`、`mLastReportedDisplayId`）变化不打扰应用代码。

[已验证: AOSP android-17.0.0_r1, frameworks/base/core/java/android/content/res/Configuration.java:1920-1960 — diffPublicOnly()]

- **seq 单调递增保障**：服务端在 `WPC.dispatchConfiguration()` 中执行 `config.seq = mAtm.increaseConfigurationSeqLocked()`，确保每次下发的 seq 单调递增。客户端的 `ResourcesManager.applyConfigurationToResources()` 通过 `mResConfiguration.isOtherSeqNewer(config)` 检测——如果收到的 config seq 不比当前新，直接 return false 跳过整轮刷新。这是防止乱序 IPC 导致 stale config 覆盖的关键机制。

[已验证: AOSP android-17.0.0_r1, frameworks/base/core/java/android/app/ResourcesManager.java:1561 — isOtherSeqNewer() early-out]

### 锚点 2：Cached 进程短路优化

Android 17 对 cached 进程的 Configuration 派发做了显著优化——屏幕旋转或语言切换不会唤醒所有后台缓存的应用。

`WindowProcessController.dispatchConfiguration()` 中的关键短路逻辑：

```java
// frameworks/base/services/core/java/com/android/server/wm/WindowProcessController.java:1960
if (mRepProcState >= CACHED_CONFIG_PROC_STATE) {
    mHasCachedConfiguration = true;
    if (...) return;  // 不下发 ClientTransactionItem
}
```

当进程的 `mRepProcState >= CACHED_CONFIG_PROC_STATE`（通常对应 `PROCESS_STATE_CACHED_EMPTY` 或更空），Configuration 只被记录到 `mHasCachedConfiguration`，不发送 `ConfigurationChangeItem`。下次该进程从 cached 恢复到 active 时（如 `setReportedProcState`），缓存的 Configuration 会合并到 `LaunchActivityItem` 中一起下发。

**性能影响**：在典型手机上有 20-40 个 cached 进程。一次屏幕旋转如果全部下发 Configuration IPC，会产生 20-40 次 binder transaction。短路优化将这个数字降到 0——cached 进程在被唤醒启动 Activity 时自然拿到最新 Configuration。

[已验证: AOSP android-17.0.0_r1, WindowProcessController.java:1947-1990 — dispatchConfiguration()]

此外，`WPC.onConfigurationChanged()` 在入口处还有一层快速比较：

```java
// WPC.java:1854
if (mLastReportedConfiguration.equals(getConfiguration())
        && topActivityDeviceId == mLastTopActivityDeviceId) {
    return;  // Configuration 和 deviceId 都没变，直接 return
}
```

这层比较保证即使 `ATMS.updateGlobalConfigurationLocked()` 遍历所有 pidMap 进程，真正走到 `dispatchConfiguration()` 的只是 Configuration 确实发生了变化的进程。

### 锚点 3：ResourcesManager 的锁与缓存架构

ResourcesManager 是进程内单例（`@UnsupportedAppUsage`，由 `ActivityThread` 持有）。它的所有公开方法都在 `synchronized (mLock)` 块内执行——这意味着 Resources 的创建、查找、Configuration 更新是全局串行化的。

```java
// frameworks/base/core/java/android/app/ResourcesManager.java
public Resources getResources(...) {
    synchronized (mLock) {
        // 查找或创建 Resources / ResourcesImpl
    }
}

public boolean applyConfigurationToResources(Configuration config, CompatibilityInfo compat) {
    synchronized (mLock) {
        // 更新所有 ResourcesImpl 的 Configuration
    }
}
```

**竞争场景**：`mLock` 的竞争主要来自：
1. `ActivityThread.handleConfigurationChanged()` — 主线程收到 Configuration 变更
2. `ActivityThread.handleBindApplication()` — Application 初始化时创建 Resources
3. `ActivityThread.performLaunchActivity()` — Activity 启动时 `getResources()`
4. 其他线程通过 `Context.createConfigurationContext()` 创建子 Context

实际上 (1)(2)(3) 都在主线程执行，只有 (4) 可能来自子线程。因此 `mLock` 的竞争在正常 App 中很少成为瓶颈。但如果 App 在 `Application.onCreate()` 中于子线程大量创建 ConfigurationContext（如某些多语言 SDK），可能遇到阻塞。

[已验证: AOSP android-17.0.0_r1, ResourcesManager.java — 所有公开方法均 synchronized(mLock)]

### ResourcesImpl 的 WeakReference 缓存

Android 14 起，`mResourceImpls` 从 `ArrayMap<ResourcesKey, ResourcesImpl>` 改为 `ArrayMap<ResourcesKey, WeakReference<ResourcesImpl>>`：

```java
// ResourcesManager.java
@GuardedBy("mLock")
private final ArrayMap<ResourcesKey, WeakReference<ResourcesImpl>> mResourceImpls = new ArrayMap<>();
```

**设计意图**：当 App 不再持有某个 ResourcesImpl 的强引用时（如 Activity 销毁后），GC 可以自动回收该 ResourcesImpl，避免缓存膨胀。查找时如果 WeakReference.get() 返回 null，该条目在下次遍历时被移除。

**Configuration 更新时的 GC 协同**：`applyConfigurationToResources()` 倒序遍历 `mResourceImpls`，对每个 entry 检查 `WeakReference.get()`。如果返回 null，直接 `mResourceImpls.removeAt(i)`。这意味着一次 Configuration 变更顺便完成了缓存清理——避免在 App 运行期间因 ResourcesImpl 积累导致的内存增长。

[已验证: AOSP android-17.0.0_r1, ResourcesManager.java:1554-1620 — applyConfigurationToResources() 倒序遍历 + weakRef 清理]

详见 1.24 节"锚点 7: Resources 缓存与内存占用"对 `dumpsys activity resources` 的诊断方法。

### 锚点 4：applyConfigurationToResources() 的执行细节

这是 ResourcesManager 处理 Configuration 变更的核心方法。完整执行步骤：

```java
// ResourcesManager.java:1554
public boolean applyConfigurationToResources(@NonNull Configuration config,
        @Nullable CompatibilityInfo compat) {
    synchronized (mLock) {
        // 步骤 1: seq 快速跳过
        if (!mResConfiguration.isOtherSeqNewer(config) && compat == null) {
            return false;
        }

        // 步骤 2: 计算变化
        int changes = mResConfiguration.updateFrom(config);

        // 步骤 3: CONFIG_ASSETS_PATHS 变化时更新 AppInfo
        if ((changes & ActivityInfo.CONFIG_ASSETS_PATHS) != 0) {
            applyAllPendingAppInfoUpdates();
        }

        // 步骤 4: 更新全局 Resources 系统配置
        final DisplayMetrics displayMetrics = getDisplayMetrics(config);
        Resources.updateSystemConfiguration(config, displayMetrics, compat);
        ApplicationPackageManager.configurationChanged();

        // 步骤 5: 倒序遍历所有 ResourcesImpl，逐个更新
        for (int i = mResourceImpls.size() - 1; i >= 0; i--) {
            WeakReference<ResourcesImpl> weakImpl = mResourceImpls.valueAt(i);
            ResourcesImpl resourcesImpl = weakImpl != null ? weakImpl.get() : null;
            if (resourcesImpl == null) {
                mResourceImpls.removeAt(i);  // GC 已回收
                continue;
            }

            ResourcesKey key = mResourceImpls.keyAt(i);
            // 合并 override configuration
            if (key.hasOverrideConfiguration()) {
                tmpConfig.setTo(config);
                tmpConfig.updateFrom(key.mOverrideConfiguration);
            } else {
                tmpConfig.setTo(config);
            }

            // 应用 DisplayAdjustments
            DisplayAdjustments daj = resourcesImpl.getDisplayAdjustments();
            daj.setCompatibilityInfo(compat);
            daj.setConfiguration(tmpConfig);

            resourcesImpl.updateConfiguration(tmpConfig, getDisplayMetrics(tmpConfig), compat);
        }
        return changes != 0;
    }
}
```

**关键细节**：

1. **seq 跳过是第一道闸门**：如果 `config.seq` 不比当前新且无 compat 变化，整个方法直接返回 false。在正常使用中，绝大多数"无效"的 Configuration 派发都被这里拦截。

2. **倒序遍历不是偶然**：从最新的 ResourcesImpl 到最旧的。原因：新创建的 ResourcesImpl 通常属于当前可见的 Activity，优先更新可以让可见 Activity 尽快拿到正确资源。同时 GC 回收的旧 WeakReference 在遍历中被清理。

3. **Override Configuration 合并**：每个 Activity 可能有独立的 override Configuration（如多窗口模式下的窗口尺寸）。全局 Configuration 先 `setTo(config)`，再 `updateFrom(key.mOverrideConfiguration)` 叠加 override——保证 Activity 的 ResourcesImpl 拿到的是合并后的最终 Configuration。

4. **DisplayAdjustments 独立于 Configuration**：`DisplayAdjustments` 持有 CompatibilityInfo 和 Configuration，但它在 ResourcesImpl 层面管理，不是 ResourcesKey 的一部分。`daj.setConfiguration(tmpConfig)` 确保 DisplayAdjustments 和 ResourcesImpl 内部的 Configuration 保持同步。

[已验证: AOSP android-17.0.0_r1, ResourcesManager.java:1554-1640]

### 锚点 5：ConfigurationController 的回调分发

`ConfigurationController.handleConfigurationChangedInner()` 是进程内 Configuration 派发的中枢。它在调用 `ResourcesManager.applyConfigurationToResources()` 后，还负责：

1. **Theme.rebase()**：当 `(theme.getChangingConfigurations() & configDiff) != 0` 时，系统 Theme 缓存需要 rebase。`getChangingConfigurations()` 返回 Theme 所依赖的 Configuration 位掩码——只有相关位变化才触发 rebase，纯旋转不需要重新加载字体缓存。

2. **freeTextLayoutCachesIfNeeded(configDiff)**：**仅在 `fontScale` 变化时**清空 TextLayout 缓存。`BoringLayout`、`StaticLayout` 等文字测量结果在 fontScale 不变时可以安全复用——旋转屏幕不触发文字缓存清空。

3. **ComponentCallbacks2 回调**：对 Application 和所有非 Activity 的 `ComponentCallbacks2`（Service、ContentProvider）回调 `onConfigurationChanged()`。**如果 `equivalent == true`（`diffPublicOnly == 0`），跳过回调**。

```java
// ConfigurationController.java:165-238 (简化)
private void handleConfigurationChangedInner(@Nullable Configuration config,
        @Nullable CompatibilityInfo compat) {
    synchronized (mResourcesManager) {
        equivalent = mConfiguration != null
                && (0 == mConfiguration.diffPublicOnly(config));
        mResourcesManager.applyConfigurationToResources(config, compat);
        configDiff = mConfiguration.updateFrom(config);
        config = applyCompatConfiguration();

        if ((systemTheme.getChangingConfigurations() & configDiff) != 0) {
            systemTheme.rebase();
        }
    }
    freeTextLayoutCachesIfNeeded(configDiff);

    final ArrayList<ComponentCallbacks2> callbacks =
            mActivityThread.collectComponentCallbacks(false);
    if (callbacks != null) {
        for (int i = 0; i < size; i++) {
            if (!equivalent) {
                performConfigurationChanged(callbacks.get(i), config);
            }
        }
    }
}
```

**注意**：Activity 的 `onConfigurationChanged()` 不通过这条路径——Activity 的 Configuration 更新由 `ActivityRecord.ensureActivityConfiguration()` 通过独立的 `ClientTransaction` 派发（`ActivityConfigurationChangeItem` 或 `ActivityRelaunchItem`）。这种 split 设计保证了 Activity 的 Configuration 更新是事务性的、可回滚的，而 Application/Service 的更新是 fire-and-forget。

[已验证: AOSP android-17.0.0_r1, ConfigurationController.java:165-238 — handleConfigurationChangedInner()]

### 锚点 6：Android 17 drag-resize relaunch 延迟机制

Android 17 引入了 `Flags.improveFluidResizingPerformance()` flag，在分屏拖拽过程中延迟 Activity relaunch，显著减少了连续 recreate 导致的闪烁和卡顿。

`ActivityRecord.relaunchActivityLocked()` 中的延迟判定：

```java
// ActivityRecord.java:8912-8930
if (Flags.improveFluidResizingPerformance()
        && isDragResizing()
        && preserveWindow
        && (mPendingRelaunchCount > 0 || mRelaunchStartTime > 0)) {
    // 正在 drag-resize 且已有 pending relaunch → 合并到 postponed flags
    mPostponedRelaunchConfigChangesFlags |= changes;
    return;  // 不发送 ActivityRelaunchItem
}
```

**工作机制**：
- 用户在分屏模式下拖拽分隔线时，`screenWidthDp` / `screenHeightDp` 连续变化
- 每次 `shouldRelaunchLocked()` 返回 true → 进入 `relaunchActivityLocked()`
- 如果已经在 relaunch 过程中（`mPendingRelaunchCount > 0`），后续的 configChangeFlags 被缓存到 `mPostponedRelaunchConfigChangesFlags`
- 拖拽结束后，缓存的 flags 合并到下一次 relaunch 中一次性处理

**效果**：分屏拖拽过程中不再连续触发 Activity destroy + create，避免 UI 闪烁和主线程阻塞。拖拽结束后的单次 relaunch 带上了所有累积的 config 变更，保证最终状态正确。

**前置条件**：`preserveWindow == true` 要求 `isAppResizeOnly == true`——即变化只涉及 `CONFIG_SCREEN_SIZE | CONFIG_SMALLEST_SCREEN_SIZE | CONFIG_ORIENTATION | CONFIG_SCREEN_LAYOUT`，不涉及 locale、density 等需要完整 recreate 的字段。

[已验证: AOSP android-17.0.0_r1, ActivityRecord.java:8912-8930 — relaunchActivityLocked() with improveFluidResizingPerformance]

### 锚点 7：WindowProcessController 的 UI/非 UI 进程区分派发

`WPC.scheduleClientTransactionItem()` 根据进程是否有 Window Session 区分派发路径：

```java
// WindowProcessController.java
void scheduleClientTransactionItem(IApplicationThread thread, ClientTransactionItem item) {
    if (mWindowSession != null && mWindowSession.hasWindow()) {
        // UI 进程：走 lifecycleManager.scheduleTransactionItem，延迟到下一帧
        mAtm.getLifecycleManager().scheduleTransactionItem(thread, item);
    } else {
        // 非 UI 进程：立即入队
        scheduleTransactionItemNow(thread, item);
    }
}
```

**设计原因**：UI 进程的 Configuration 更新最好和下一帧的渲染对齐——`scheduleTransactionItem` 会延迟到 `ClientTransaction` 的批处理时机，与 `activityTransitionState` 协调。非 UI 进程（如仅含 Service 的进程）没有渲染需求，立即派发反而能减少延迟。

**与 cached 进程短路的配合**：cached 进程通常 `mWindowSession.hasWindow() == false`（Activity 已销毁），即使没被 `CACHED_CONFIG_PROC_STATE` 短路，也会走 `scheduleTransactionItemNow` 路径。但 `CACHED_CONFIG_PROC_STATE` 短路在更前面生效，通常不会走到这里。

[已验证: AOSP android-17.0.0_r1, WindowProcessController.java — scheduleClientTransactionItem()]

### 锚点 8：ResourcesManager 性能诊断实战

### dumpsys activity resources

```bash
adb shell dumpsys activity resources
```

输出中的关键区域：

```
ResourcesManager:
  # of ResourcesImpl: 3
  # of Resources: 5
  
  ResourcesImpl[key=wcp=android.os.BinderProxy@xxx config=...
  ResourcesImpl[key=wcp=android.os.BinderProxy@yyy config=...
  ...
```

**诊断思路**：
- `# of ResourcesImpl` 异常高（>10）通常意味着多组 Configuration 并存——可能是多窗口、多 display、或 override Configuration 泄漏
- 如果同一个 Activity token 出现多个 ResourcesImpl，检查 `createConfigurationContext()` 的调用是否有必要
- 结合 `dumpsys meminfo <package>` 的 `Native Heap` 增长，判断 `resources.arsc` mmap 的内存影响

详见 1.24 节"锚点 7"的完整诊断流程。

### Perfetto 中的 Configuration 派发 trace

在 Perfetto 中搜索以下 slice 名定位 Configuration 派发开销：

| Slice 名 | 含义 | 预期耗时 |
|----------|------|----------|
| `handleConfigurationChanged` | 进程级 Configuration 处理入口 | 1-10ms（不含 relaunch） |
| `applyConfigurationToResources` | ResourcesManager 资源更新 | <2ms（seq 跳过时 <0.1ms） |
| `ensureActivityConfiguration` | Activity 级 relaunch 判定 | <1ms |
| `handleRelaunchActivity` | Activity 完整重建 | 50-200ms（取决于 View 树复杂度） |

如果 `applyConfigurationToResources` 耗时异常高（>10ms），检查：
- `mResourceImpls` size 是否过大（WeakReference 清理不及时）
- 是否有 `CONFIG_ASSETS_PATHS` 变化触发了 `applyAllPendingAppInfoUpdates()`（涉及 PackageManager 查询）

## 扩展

### 🔸 ResourcesKey 的构造与缓存命中条件

ResourcesKey 由以下字段构成：
- `apkPaths`（List<String>，split APK 路径列表）
- `overlayPaths`（String[]，Runtime Resource Overlay 路径）
- `libDirs`（String[]，native library 目录）
- `mOverrideConfiguration`（Configuration，Activity 级 override）

两个 ResourcesKey 相等（`equals()` + `hashCode()`）要求所有字段完全一致。这意味着：
- 同一个 Activity 在多窗口模式下拖拽 resize 会产生新的 ResourcesKey（`screenWidthDp` 不同）
- 旋转屏幕时如果 `configChanges` 声明了 `orientation`，Activity 不 recreate 但新的 override Configuration 会产生新 ResourcesImpl（旧的被 GC 回收）

在 `getResources()` 查找时，先检查 `mResourceImpls` 是否已有匹配 key 的缓存。如果命中，直接返回已有的 ResourcesImpl；如果未命中，创建新的 AssetManager + ResourcesImpl 并缓存。

[已验证: AOSP android-17.0.0_r1, ResourcesManager.java — findOrCreateResourcesImplForKeyLocked()]

### 🔸 split APK 与 dynamic feature module 的 Resources 管理

使用 dynamic feature module（DFM）时，每个已安装的 split APK 路径都会被添加到 ResourcesKey 的 `apkPaths` 中。这意味着：

- 安装新 DFM 后 `CONFIG_ASSETS_PATHS` 变化 → `applyAllPendingAppInfoUpdates()` 更新 AppInfo → 新 ResourcesImpl 被创建
- 旧 ResourcesImpl 在 WeakReference 中等待 GC 回收
- 在过渡期间，App 可能同时持有新旧两组 ResourcesImpl——内存峰值短暂上升

如果 App 频繁安装/卸载 DFM（如按需功能模块），注意监控 `mResourceImpls` size 和 Native Heap 增长。

[待验证: DFM 安装后 ResourcesImpl 的过渡期内存峰值量级，需要实际测试数据]

### 🔸 Configuration seq 的并发安全性

`Configuration.seq` 是 `int` 类型，在 `increaseConfigurationSeqLocked()` 中递增（ATMS 持锁）。客户端收到的 seq 通过 `isOtherSeqNewer()` 比较——如果新 config 的 seq 小于等于当前 seq，判定为过时数据。

在多窗口/分屏场景下，不同 Display 的 Configuration 变更可能产生不同的 seq。但全局 Configuration 的 seq 是统一递增的——`increaseConfigurationSeqLocked()` 不区分 Display。这意味着 Display A 的 density 变化和 Display B 的 orientation 变化不会产生相同的 seq，不会发生 seq 冲突。

[待验证: 分屏下两个 Display 同时 Configuration 变更的极端场景]
