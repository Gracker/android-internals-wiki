# 1.46 Android 17 ResourcesManager 与 Configuration 变更性能

一次 Configuration 变化会同时触达 system_server 的窗口层级、应用进程的全局资源和具体 Activity。三部分互相关联，却不构成一条等待上一步执行完毕才继续的同步调用栈。把它们画成单线流程，很容易误判 Binder 次数、Activity 重建时机和性能归因。

本文以 Android 17 / API 37 / AOSP `android-17.0.0_r1` 为源码锚点，集中解释进程级派发、cached 进程抑制、`ResourcesManager` 缓存和连续窗口缩放。`configChanges` 的使用方式、状态恢复与完整性能排查见 [1.24 ResourcesManager 与 Configuration 变更性能](24-resourcesmanager-configuration-performance.md)。

## 三条相关路径

下面的结构图用于区分全局配置、进程配置和 Activity merged Configuration。

```text
system_server
  ActivityTaskManagerService.updateGlobalConfigurationLocked()
    ├─ system_server 自身 Resources
    ├─ 每个 WindowProcessController
    │    └─ ConfigurationChangeItem
    │         └─ 应用进程的 ConfigurationController
    │              ├─ ResourcesManager.applyConfigurationToResources()
    │              └─ Application / Service / Provider 等组件回调
    └─ RootWindowContainer.onConfigurationChanged()
         └─ ActivityRecord 的 merged Configuration
              └─ ensureActivityConfiguration()
                   ├─ ActivityConfigurationChangeItem
                   └─ ActivityRelaunchItem
```

源码在 `updateGlobalConfigurationLocked()` 中先遍历进程，再调用 `RootWindowContainer.onConfigurationChanged()`。这只是 system_server 内的调度顺序。带窗口的进程可能把 `ClientTransactionItem` 暂存在 `ClientLifecycleManager`，Binder 客户端也会异步执行，因此不能从这段顺序推导“进程资源已经更新完成，服务端才判定 Activity”。

进程级 `ConfigurationChangeItem` 更新全局资源和非 Activity 组件。Activity 自身还需要 merged override Configuration，服务端会单独选择热派发或 relaunch。两个事务进入同一客户端事务体系，`preExecute()` 和 pending Configuration 用于避免新 Activity 在旧的进程配置上创建。

## system_server 如何产生和派发全局配置

`updateGlobalConfigurationWithTransition()` 用 `diffPublicOnly()` 计算应用可见的变化位。结果为零时，不启动这轮全局更新；存在变化时，方法收集 Shell Transition，并进入 `updateGlobalConfigurationLocked()`。

该方法的工作顺序包括：

1. 把新值合入 `mTempConfig`，设置新的 `seq`。
2. 更新 system_server 自身 Resources。
3. 遍历 `mProcessMap.getPidMap()`，调用每个 `WindowProcessController.onConfigurationChanged()`。
4. 调用 `RootWindowContainer.onConfigurationChanged()`，让 display、task 和 Activity 的 ConfigurationContainer 层级重新计算。

`WindowProcessController.onConfigurationChanged()` 会比较当前进程 Configuration 和 `mLastReportedConfiguration`，也会比较顶部 Activity 的 deviceId。二者都未变化时直接返回。派发前又为该进程副本设置新的 `seq`，并保存到 `mLastReportedConfiguration`。

### `seq` 是乱序保护，不是内容版本号

客户端的快速判断位于 `ResourcesManager.applyConfigurationToResources()`：

```java
if (!mResConfiguration.isOtherSeqNewer(config) && compat == null) {
    return false;
}
```

该判断在 compatibility 信息没有单独变化时，阻止旧 Configuration 覆盖新状态。`Configuration.isOtherSeqNewer()` 还处理两类边界：`seq == 0` 表示无法比较，需要接受；差值跨度很大时按 `int` 回绕处理。因而“数值小于等于当前值就丢弃”并不覆盖完整语义。

`seq` 只表达派发新旧关系。两个 Configuration 的内容是否等价，仍由 `equals()`、`diff()` 或 `diffPublicOnly()` 判断。

## cached 进程为何可以暂缓通知

Android 17 的阈值是：

```java
private static final int CACHED_CONFIG_PROC_STATE =
        PROCESS_STATE_CACHED_ACTIVITY;
```

该常量表明 `PROCESS_STATE_CACHED_ACTIVITY` 及更低优先级的 cached 状态都进入抑制范围，并不限于 `PROCESS_STATE_CACHED_EMPTY`。

`dispatchConfiguration()` 仍会先更新 `mLastReportedConfiguration`，随后检查进程状态：

```java
if (mRepProcState >= CACHED_CONFIG_PROC_STATE) {
    mHasCachedConfiguration = true;
    if (mRepProcState >= CACHED_CONFIG_PROC_STATE) {
        return;
    }
}
```

第二次读取用于处理 `mRepProcState` 与 `mHasCachedConfiguration` 两个 volatile 字段之间的竞态。进程仍处于 cached 状态时，本轮不发送 `ConfigurationChangeItem`，从而避免只为配置通知唤醒没有运行中组件的进程。

缓存状态有两条恢复路径：

- 进程从 cached 进入更活跃状态时，`setReportedProcState()` 立即用 `scheduleTransactionItemNow()` 补发最新 `ConfigurationChangeItem`。Receiver 的 `onReceive()`、Service 的 `onCreate()` 等生命周期回调由此看到新配置。
- Activity 启动时，`prepareConfigurationForLaunchingActivity()` 为 `LaunchActivityItem` 提供最新进程 Configuration，并清除 `mHasCachedConfiguration`。

不能用固定的“每次旋转节省 20–40 个 Binder 事务”描述收益。saved/cached 进程数量、OEM 进程管理和当前组件状态都会改变实际结果，应从目标设备 trace 计数。

## 带窗口与无窗口进程的调度差异

`WindowProcessController` 根据 Window Session 选择客户端事务入口：

```java
if (mWindowSession != null && mWindowSession.hasWindow()) {
    mAtm.getLifecycleManager().scheduleTransactionItem(thread, item);
} else {
    mAtm.getLifecycleManager().scheduleTransactionItemNow(thread, item);
}
```

无窗口进程直接发出事务。带窗口进程交给 `ClientLifecycleManager`，它可以把同一客户端的多个 item 合入一个 `ClientTransaction`。当 WindowManager 没有推迟布局、没有已请求的 traversal、也不在 layout 中时，该事务仍可能立即发出；只有相关窗口工作尚未完成时，才等待 `performSurfacePlacementNoTrace()` 或 `onLayoutContinued()` 派发。

所以这里的延迟边界是 WindowManager 布局状态，不对应固定的“下一帧”，也没有固定等待时长。

## 客户端怎样接收最新 Configuration

`ConfigurationChangeItem.preExecute()` 先调用 `updatePendingConfiguration()`，`execute()` 再调用 `ActivityThread.handleConfigurationChanged()`。`ConfigurationController` 处理 pending 值时会保留更新的一份，随后按以下顺序工作：

1. 调用 `ResourcesManager.applyConfigurationToResources()` 更新进程资源基线和所有存活的 `ResourcesImpl`。
2. 更新进程保存的 `mConfiguration`，得到 `configDiff`。
3. 仅对依赖变化位的 system theme 与 system UI theme 执行 `rebase()`。
4. locale 变化时调用 `Canvas.freeTextLayoutCaches()`。
5. 收集不含 UI Context 的 `ComponentCallbacks2`，公开配置有差异时派发回调。

`freeTextLayoutCachesIfNeeded()` 在 Android 17 检查的是 `ActivityInfo.CONFIG_LOCALE`，没有检查 `CONFIG_FONT_SCALE`。字体缩放会沿资源更新和 View 重布局路径生效，不能据此推断文字布局缓存由这个 helper 清除。

`diffPublicOnly() == 0` 会把进程级非 Activity 组件回调判为等价。Activity 不在 `collectComponentCallbacks(false)` 的这组回调里；它的资源 override 和生命周期由 `ActivityConfigurationChangeItem` 或 `ActivityRelaunchItem` 处理。该分工没有提供通用回滚能力，也不应描述为一种“事务可回滚”保证。

## `ResourcesManager` 的锁与缓存

`ResourcesManager` 是应用进程单例。`mResourceImpls`、Activity 资源映射、全局配置和相关缓存的关键读写受私有 `mLock` 保护。创建或查找资源、切换 Activity override、应用全局 Configuration 都会进入该锁。

“所有公开方法都持有 `mLock`”并不准确；源码中还有只访问其他状态或采用其他同步方式的方法。性能分析应盯住发生资源创建、查找和更新的具体临界区。

常见 UI 生命周期工作多在主线程执行，锁竞争仍可能来自后台线程创建 Configuration Context、注册动态资源路径，或框架同时处理全局配置。遇到长 slice 时，需要用线程状态和锁等待证据判断，不能仅凭 `synchronized` 推定瓶颈。

### `ResourcesKey` 决定能否复用实现

Android 17 的 `ResourcesKey` 包含以下字段：

| 字段 | 作用 |
|---|---|
| `mResDir`、`mSplitResDirs` | base APK 与 split 资源路径 |
| `mOverlayPaths`、`mLibDirs` | overlay 与共享库路径 |
| `mDisplayId` | override display |
| `mOverrideConfiguration` | 相对全局配置的覆盖值 |
| `mCompatInfo` | 兼容模式信息 |
| `mLoaders` | 动态 `ResourcesLoader` 数组 |

`equals()` 会比较全部字段。全局 Configuration 改变时，`ResourcesManager` 通常更新现有 impl；Activity override、display、资源路径、compat 或 loader 组合改变时，新的 key 才可能需要另一份 `ResourcesImpl`。一次旋转或一次 resize 不等于必然创建新 impl。

### WeakReference 解决存活性，不证明没有泄漏

Android 17 的映射类型如下：

```java
private final ArrayMap<ResourcesKey, WeakReference<ResourcesImpl>>
        mResourceImpls = new ArrayMap<>();
```

该 WeakReference 设计早于 Android 14，不能列为 Android 14 新增机制。应用不再强引用某个 `ResourcesImpl` 后，GC 可以回收它；全局配置更新的倒序遍历会删除已经失效的条目。倒序的直接用途是允许 `removeAt(i)` 时安全遍历，源码没有“按新旧顺序优先更新可见 Activity”的约定。

Android 17 还受 `resourcesManagerCacheLeakCleanup()` flag 控制：开启时使用 `ReferenceQueue` 及时移除死亡 key，关闭时由后续遍历等机会清理。WeakReference 只说明缓存 map 不会单独保活 impl。旧 Activity、Context、Theme 或插件框架仍有强引用时，资源对象照样无法回收。

## `applyConfigurationToResources()` 做了哪些工作

下面的伪代码只保留 Android 17 中影响判断和成本的分支。

```java
synchronized (mLock) {
    if (!mResConfiguration.isOtherSeqNewer(config) && compat == null) {
        return false;
    }

    int changes = mResConfiguration.updateFrom(config);
    if ((changes & ActivityInfo.CONFIG_ASSETS_PATHS) != 0) {
        applyAllPendingAppInfoUpdates();
    }

    Resources.updateSystemConfiguration(config, getDisplayMetrics(config), compat);
    ApplicationPackageManager.configurationChanged();

    for (int i = mResourceImpls.size() - 1; i >= 0; i--) {
        ResourcesImpl impl = dereference(mResourceImpls.valueAt(i));
        if (impl == null) {
            mResourceImpls.removeAt(i);
            continue;
        }
        applyConfigurationToResourcesLocked(
                config, compat, tmpConfig, mResourceImpls.keyAt(i), impl);
    }
    return changes != 0;
}
```

每个存活 impl 都会以全局 `config` 为基准，再叠加 key 中的 `mOverrideConfiguration`。框架依据 key 的 displayId 和 `DisplayAdjustments` 计算 `DisplayMetrics`，然后调用 `ResourcesImpl.updateConfiguration()`。

compat 改变时，源码复制当前 `DisplayAdjustments` 再写入新的 `CompatibilityInfo`，不会无条件改写 impl 原对象。`CONFIG_ASSETS_PATHS` 分支只说明待处理的 `ApplicationInfo` 更新要在资源刷新前应用；它本身不能证明某次 dynamic feature 安装必定新建 impl，也不能推出固定内存峰值。

## Activity relaunch 与连续 resize

`ActivityRecord.ensureActivityConfiguration()` 在 system_server 内比较上次报告的 merged Configuration 与当前值。方法会经过可见性、运行状态、displayId、ActivityWindowInfo 和 size bucket 等检查，再决定：

- 变化位可由 Activity 或系统策略处理：发送 `ActivityConfigurationChangeItem`。
- 仍有未处理变化位：发送 `ActivityRelaunchItem`。
- Activity 未运行或处于部分不可处理状态：保存新配置，等后续生命周期使用。

进程级 `ConfigurationChangeItem` 和 Activity 级判定可能来自同一轮全局变化，却负责不同职责。客户端更新了全局 Resources，不能替代 Activity override 的热派发或重建。

### Android 17 的拖拽重建合并

`Flags.improveFluidResizingPerformance()` 开启时，`relaunchActivityLocked()` 有一个窄条件：

```java
if (isDragResizing() && preserveWindow
        && (mPendingRelaunchCount > 0 || mRelaunchStartTime > 0)) {
    mPostponedRelaunchConfigChangesFlags |= configChangeFlags;
    return;
}
```

它只在拖拽 resize、允许保留窗口，并且 Activity 已有 pending relaunch 或首个新窗口尚未绘制时合并后续变化。首轮 relaunch 仍可能发生，因此“拖拽期间完全不重建”过度扩大了行为范围。

`preserveWindow` 来自 `isAppResizeOnly`。变化位只能落在 `screenSize`、`smallestScreenSize`、`orientation`、`screenLayout` 内，同时 display rotation 与 max bounds 的特定变化不能命中该条件。拖拽状态结束时，`resetDragResizingChangeReported()` 会调用 `resumePostponedRelaunch()`；积累的 flags 合入后续 relaunch。

这一优化减少连续重建的机会，效果仍取决于 Activity 声明、变化位和窗口状态。是否改善帧率要用目标页面的 FrameTimeline 验证。

## 可依赖的 trace 与诊断方法

Android 17 源码明确建立的相关 slice 有：

| Slice | 源码位置 | 用途 |
|---|---|---|
| `configChanged` | `ConfigurationController` | 进程级 Configuration 处理 |
| `ResourcesManager#applyConfigurationToResources` | `ResourcesManager` | 全局 Resources 更新 |
| `ResourcesManager#updateResourcesForActivity` | `ResourcesManager` | Activity override/display 资源切换 |
| `activityConfigChanged` | `ActivityConfigurationChangeItem` | Activity 热派发 |
| `activityRestart` | `ActivityRelaunchItem` | Activity relaunch |

`handleConfigurationChanged`、`applyConfigurationToResources`、`ensureActivityConfiguration` 和 `handleRelaunchActivity` 这些方法名不能直接当成稳定 slice 名。耗时也没有 `<2 ms`、`50–200 ms` 一类平台保证；设备、资源数量、页面初始化和窗口状态都会改变结果。

排查时可按下面的证据顺序推进：

1. `configChanged` 较长：展开其中的 Resources 更新和组件回调，判断时间属于 framework 还是应用代码。
2. `ResourcesManager#applyConfigurationToResources` 较长：检查存活 impl 数、资源路径变化、overlay/shared library 和锁等待。
3. 出现 `activityRestart`：继续分析 Activity 生命周期、inflate、View/Compose 首帧与状态恢复。
4. 只有 `activityConfigChanged`：检查应用回调、布局和自定义渲染更新。
5. slice 很短但仍有卡顿：回到 FrameTimeline、主线程调度、RenderThread、GPU 与 Surface transition。

Android 17 没有稳定、公开的 `adb shell dumpsys activity resources` 子命令，也不能依靠一份固定输出格式读取 `ResourcesKey` 列表。通用内存检查可以从以下命令开始。

```bash
adb shell dumpsys meminfo <package-name>
adb shell am dumpheap <process-name> /data/local/tmp/app.hprof
```

`am dumpheap` 受 debuggable、权限和设备策略限制。Java heap 用于寻找仍存活的 Activity、Context、Resources 和 impl 的强引用；AssetManager 与资源表的 native 成本需要 Perfetto native heap profiler。只有死亡 weak-reference key 增加、GC 后内存稳定时，不能定性为资源泄漏。

## 阅读源码时容易混淆的边界

- `diffPublicOnly()` 用于排除公开语义等价的差异，例如 `appBounds`；它和 `ResourcesImpl.updateConfiguration()` 的工作范围不同。
- 全局 `seq` 由 ATMS 生成，WPC 派发还会更新进程副本的 `seq`。它们使用同一递增入口，不按 display 分配独立序列。
- `ResourcesKey.mOverrideConfiguration` 保存相对全局配置的覆盖值。全局 `locale` 或 `orientation` 变化不必改 key。
- cached 抑制避免无组件进程被单纯配置通知唤醒；进程恢复活跃后仍会收到最新配置。
- UI 进程的事务可参与窗口事务合并，但是否排队由当前 layout/traversal 状态决定。
- drag-resize 优化只合并满足条件的后续 relaunch，不能替代应用正确处理连续窗口变化。
