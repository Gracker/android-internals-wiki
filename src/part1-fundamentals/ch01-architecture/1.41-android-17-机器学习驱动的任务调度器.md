# 1.41 Android 17 机器学习驱动的任务调度器


## Android 17 源码结论

平台锚点为 Android 17 / API 37 / `android-17.0.0_r1`，内核锚点为 `android17-6.18-2026-06_r6`。AOSP 没有 `MLScheduler`，也没有用 LSTM、CNN 和 GNN 统一安排应用启动、后台任务、内存回收与 CPU 可运行任务的框架层组件。

`frameworks/base/services/core/java/com/android/server/am/` 在该标签下有 140 个直接目录项，没有 Kotlin 文件。下列 `.kt` 文件均不存在：

- `MLScheduler.kt`、`MLModel.kt`、`ScheduleEngine.kt`；
- `BehaviorPredictor.kt`、`PreloadManager.kt`、`ResourceManager.kt`；
- `BackgroundOptimizer.kt`、`MemoryOptimizer.kt`、`BatteryAwareScheduler.kt`；
- `AdaptiveLearner.kt`、`AppSchedulerAPI.kt`、`DebugTools.kt`。

相关代码块还引用了没有定义的 `Task`、`ResourceRequirements`、`NeuralNetworkModel` 等类型，属于演示性质的伪代码。文件路径注释和 `@RequiresApi(35)` 不会把伪代码变成 Android API。

## Android 17 中对应职责由谁负责

| 关注对象 | AOSP 机制 | 能决定的范围 |
|---|---|---|
| 应用后台工作 | JobScheduler 控制器、配额、App Standby 分桶 | Job 是否满足约束、是否在配额内、何时进入可执行集合 |
| 进程重要性 | AMS、OomAdjuster、进程状态、任务配置 | `oom_score_adj`、进程状态、回收与资源分组依据 |
| 周期性线程负载 | ADPF、`PerformanceHintManager`、Power HAL | 应用提交目标/实际时长后，设备策略怎样响应 |
| CPU 可运行实体 | Linux 公平调度器 / EEVDF | 根据权重、滞后量、可运行资格与虚拟期限选择任务 |
| 产品私有策略 | OEM 服务、厂商钩子、私有模型 | 只对已验证的设备、版本和实现成立 |

这些机制可以先后影响同一个应用，但源码中没有统一的 `SchedulePrediction`、置信度排序或 `ResourceReservation` 对象。

### JobScheduler 与 App Standby

JobScheduler 根据网络、充电、空闲、截止时间、配额、App Standby 分桶等约束管理应用提交的 Job。`QuotaController` 按有效待机分桶维护执行时长与次数等额度，源码中没有预测模型训练或反向传播。

Android 17 的 App Standby 允许拥有 `CHANGE_APP_IDLE_STATE` 的特权组件提交分桶，部分调用会标记为 `REASON_MAIN_PREDICTED`。这个原因只记录来源类别，不证明调用方使用机器学习。12 小时预测超时、权限和观测字段见 [5.7 后台执行限制与优化](../ch05-cpu-power/07-background-execution.md)。

### OomAdjuster

OomAdjuster 根据 Activity、Service、Provider、Broadcast、绑定关系和进程状态计算进程重要性。它会推动 `oom_score_adj`、进程状态和进程组更新，但不预加载预测应用，也不在内核运行队列中挑选下一条线程。

源码中没有 `MemoryOptimizer.compactMemoryFragments()` 这个 AOSP API。Android 的进程压缩、LMKD 和内核内存回收有各自触发条件，不能改写成一个机器学习调度器的方法。

### ADPF

`PerformanceHintManager` 接收应用显式报告的目标工作时长与实测工作时长。它不收集用户满意度，也不公开 CPU、NPU 或内存预留接口。设备策略怎样响应提示取决于 Power HAL 和产品实现。

ADPF 的 API 与线程约束见 [ADPF 自适应性能框架](../ch05-cpu-power/09-adpf.md)。

### EEVDF

`android17-6.18-2026-06_r6` 的公平调度器使用 EEVDF 选择可运行实体。框架层可以通过 nice、cpuset、cgroup 权重、uclamp 和任务配置改变约束，内核接口中没有 `predictedPriority`、模型置信度或用户行为特征。

CPU 调度细节见 [5.1 Linux 进程调度基础](../ch05-cpu-power/01-linux-scheduling.md)。

## 开发者 API 核查

Android 17 SDK 和对应 AOSP 包中没有 `AppSchedulerAPI.requestScheduleOptimization()` 与 `BehaviorEventListener`，也没有与之匹配的系统服务、AIDL 或权限。

API 35 对应 Android 15，API 36 对应 Android 16，API 37 对应 Android 17。伪代码中的 `@RequiresApi(35)` 不能作为 Android 17 能力证据。

应用能够使用的调度入口仍是职责明确的公开 API，例如 JobScheduler、WorkManager、AlarmManager 与 `PerformanceHintManager`。每个入口都有自己的权限、约束和失败语义，不接受提纲中的通用模型配置。

## 性能数据核查

冷启动 2.1 秒降到 1.4 秒、应用切换 120 毫秒降到 45 毫秒、续航 8.5 小时增到 10.2 小时等数字没有设备型号、构建版本、工作负载、样本量、温度、功耗模式、统计分布或跟踪数据。对应 `BenchmarkTest.kt` 也不存在。

这组数字不能标成 Android 17 测试结果。若产品确有预测式扩展，至少应给出：

1. 系统服务、包名、模型或推理库；
2. 模型输出进入 JobScheduler、task profile、uclamp 或其他执行机制的调用路径；
3. 固定 build fingerprint 与设备状态；
4. 冷热缓存、温度、电量和输入序列一致的对照组；
5. 原始 Perfetto、功耗与内存数据，以及 P50/P90/P99 或置信区间。

没有这些材料时，只能记录为待验证的 OEM 假设。
