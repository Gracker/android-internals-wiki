# 1.41 Android 17 机器学习驱动的任务调度器


## Android 17 源码核查

平台锚点为 Android 17 / API 37 / `android-17.0.0_r1`，内核锚点为 `android17-6.18-2026-06_r6`。核查结果与历史提纲末尾的“源码级验证”声明相反：AOSP 没有 `MLScheduler`，也没有用 LSTM、CNN 和 GNN 统一安排应用启动、后台任务、内存回收与 CPU runnable task 的 framework 组件。

`frameworks/base/services/core/java/com/android/server/am/` 在该标签下有 140 个直接目录项，没有 Kotlin 文件。提纲声称位于这里的 19 个 `.kt` 文件均不存在，包括：

- `MLScheduler.kt`、`MLModel.kt`、`ScheduleEngine.kt`；
- `BehaviorPredictor.kt`、`PreloadManager.kt`、`ResourceManager.kt`；
- `BackgroundOptimizer.kt`、`MemoryOptimizer.kt`、`BatteryAwareScheduler.kt`；
- `AdaptiveLearner.kt`、`AppSchedulerAPI.kt`、`DebugTools.kt`。

这些代码块还引用了没有定义的 `Task`、`ResourceRequirements`、`NeuralNetworkModel` 等类型，属于演示性质的伪代码。文件路径注释和 `@RequiresApi(35)` 不会把伪代码变成 Android API。

## Android 17 中对应职责由谁负责

| 关注对象 | AOSP 机制 | 能决定的范围 |
|---|---|---|
| 应用后台工作 | JobScheduler controllers、quota、App Standby bucket | Job 是否满足约束、是否在 quota 内、何时进入可执行集合 |
| 进程重要性 | AMS、OomAdjuster、process state、task profile | `oom_score_adj`、进程状态、回收与资源分组依据 |
| 周期性线程负载 | ADPF、`PerformanceHintManager`、Power HAL | 应用提交 target/actual duration 后，设备策略怎样响应 |
| CPU runnable entity | Linux fair scheduler / EEVDF | 根据权重、lag、eligibility 与 virtual deadline 选择任务 |
| 产品私有策略 | OEM service、vendor hook、私有模型 | 只对已验证的设备、版本和实现成立 |

这些机制可以先后影响同一个应用，但没有提纲所写的统一 `SchedulePrediction`、置信度排序或 `ResourceReservation` 对象。

### JobScheduler 与 App Standby

JobScheduler 根据网络、充电、idle、deadline、quota、App Standby bucket 等约束管理应用提交的 Job。`QuotaController` 按 effective standby bucket 维护执行时长与次数等额度，源码中没有预测模型训练或反向传播。

Android 17 的 App Standby 允许拥有 `CHANGE_APP_IDLE_STATE` 的特权组件提交 bucket，部分调用会标记为 `REASON_MAIN_PREDICTED`。这个 reason 只记录来源类别，不证明调用方使用机器学习。12 小时 prediction timeout、权限和观测字段见 [1.31 App Standby 预测与 ML 调度边界](./1.31-Android-17-机器学习驱动任务调度器.md)。

### OomAdjuster

OomAdjuster 根据 Activity、Service、Provider、Broadcast、绑定关系和进程状态计算进程重要性。它会推动 `oom_score_adj`、process state 和进程组更新，但不预加载预测应用，也不在内核 runqueue 中挑选下一条线程。

提纲中的 `MemoryOptimizer.compactMemoryFragments()` 不是 AOSP API。Android 的进程 compaction、LMKD 和内核内存回收有各自触发条件，不能改写成一个 ML scheduler 的方法。

### ADPF

`PerformanceHintManager` 接收应用显式报告的目标工作时长与实测工作时长。它没有收集提纲中的用户满意度，也不公开 CPU、NPU 或内存预留接口。设备策略怎样响应 hint 取决于 Power HAL 和产品实现。

ADPF 的 API 与线程约束见 [ADPF 自适应性能框架](../ch05-cpu-power/09-adpf.md)。

### EEVDF

`android17-6.18-2026-06_r6` 的 fair scheduler 使用 EEVDF 选择可运行实体。Framework 可以通过 nice、cpuset、cgroup weight、uclamp 和 task profile 改变约束，内核接口中没有 `predictedPriority`、模型置信度或用户行为特征。

CPU 调度细节见 [Android 17 EEVDF 调度器](../ch05-cpu-power/31-android17-eevdf-scheduler.md)。

## 开发者 API 核查

历史提纲宣称第三方应用可以调用 `AppSchedulerAPI.requestScheduleOptimization()` 并注册 `BehaviorEventListener`。Android 17 SDK 和对应 AOSP 包中没有这些类与方法，也没有与之匹配的 system service、AIDL 或权限。

版本号也被写错：API 35 对应 Android 15，API 36 对应 Android 16，API 37 对应 Android 17。伪代码中的 `@RequiresApi(35)` 不能作为 Android 17 能力证据。

应用能够使用的调度入口仍是职责明确的公开 API，例如 JobScheduler、WorkManager、AlarmManager 与 `PerformanceHintManager`。每个入口都有自己的权限、约束和失败语义，不接受提纲中的通用模型配置。

## 性能数据核查

冷启动 2.1 秒降到 1.4 秒、应用切换 120 毫秒降到 45 毫秒、续航 8.5 小时增到 10.2 小时等数字没有设备型号、构建版本、工作负载、样本量、温度、功耗模式、统计分布或 trace。对应 `BenchmarkTest.kt` 也不存在。

这组数字不能标成 Android 17 测试结果。若产品确有预测式扩展，至少应给出：

1. 系统服务、包名、模型或推理库；
2. 模型输出进入 JobScheduler、task profile、uclamp 或其他执行机制的调用路径；
3. 固定 build fingerprint 与设备状态；
4. 冷热缓存、温度、电量和输入序列一致的对照组；
5. 原始 Perfetto、功耗与内存数据，以及 P50/P90/P99 或置信区间。

没有这些材料时，只能记录为待验证的 OEM 假设。
