# 1.11 Android 17 ContentProvider 实际变更分析（源码验证版）

`ContentProviderClient` 在 Android 16 到 Android 17 之间的变化以固定源码标签为准。几组容易混淆的容量与引用概念也需要分别核对。ContentProvider 的启动、查询、超时和诊断主线见 [ContentProvider 性能与优化](./10-content-provider.md)。

源码基线为 AOSP `android-17.0.0_r1`。对比标签使用 `android-15.0.0_r1` 和 `android-16.0.0_r1`，不把主干代码或尚未进入该标签的提交算入 Android 17。

## 源码结论

| 主张 | Android 17 源码结论 | 工程边界 |
|---|---|---|
| 新增普通应用公开 API | `ContentProviderClient` 没有新增供普通应用调用的对应公开方法 | 不能靠 `SDK_INT >= 37` 绕过 SDK 可见性和权限 |
| 新增取消后无响应监测 | 新增 `setDetectNotRespondingOnCancel(long, long)` | `@SystemApi`、`@hide`、`@FlaggedApi`，并要求 `REMOVE_TASKS` |
| 新增 `setCallNotCancelledTimeout(long)` | 源码中存在 | `@hide`、`@VisibleForTesting`，属于测试调节入口 |
| 新增 `setSticky()` | Android 15、16、17 的该类中均未找到 | 不存在所谓 `setSticky()` 性能收益 |
| Binder transaction buffer 扩到 2 MiB | `BINDER_VM_SIZE` 仍为 `1 MiB - 2 × page size` | 这是进程共享的 Binder 映射区，不能当作单笔事务额度 |
| CursorWindow 为 2 MiB | base 配置值为 2048 KiB | 产品可以覆盖默认值，公开构造函数也可指定窗口容量 |

这里的“没有新增公开 API”只针对核查到的 `ContentProviderClient` 变化，不能外推成 Android 17 的整个 ContentProvider 子系统没有其他提交。

## Android 17 的取消后无响应监测

### 两个新增方法的可见性不同

下面的摘录省略方法体，只保留决定调用边界的注解和参数：

```java
/** @hide */
@SystemApi
@FlaggedApi(FLAG_ENABLE_CONTENT_PROVIDER_CLIENT_ANR_ON_CANCEL)
@RequiresPermission(android.Manifest.permission.REMOVE_TASKS)
public void setDetectNotRespondingOnCancel(
        @DurationMillisLong long timeoutFixedMillis,
        @DurationMillisLong long timeoutOnCancelMillis);

/** @hide */
@VisibleForTesting
public void setCallNotCancelledTimeout(
        @DurationMillisLong long timeoutMillis);
```

第一个方法有两个时长参数，没有第三个 `flags` 参数。它面向受支持的系统调用方，还受 aconfig 开关 `enable_content_provider_client_anr_on_cancel` 控制。`REMOVE_TASKS` 在 Android 17 中是 `signature|recents|role` 权限，普通三方应用不能获得。

第二个方法只调整“调用长期没有收到取消”这一测试监测窗口。默认常量是 6 小时，超时后的 `CallNotCancelledRunnable` 调用 `Log.wtf()`；它不会直接把 Provider 判为 ANR，也不属于应用侧请求超时 API。

### 两个时长从不同起点计时

`setDetectNotRespondingOnCancel(fixed, onCancel)` 把调用分成两类：

- 不支持 `CancellationSignal` 的调用，以及 `onCancel == 0` 时的可取消调用，从远程调用开始按 `fixed` 计时；
- 可取消调用且 `onCancel > 0` 时，调用开始阶段不启用 `fixed` 计时。调用者触发 `CancellationSignal.cancel()` 后，client 才按 `onCancel` 安排 `NotRespondingRunnable`。

`NotRespondingRunnable` 会进入 `ContentResolver.appNotRespondingViaProvider()`，通知系统处理已连接但无响应的 Provider。它是系统侧故障治理能力，不是给普通应用返回 `TimeoutException` 的计时器。

Android 17 还让原有 `setDetectNotResponding(fixed)` 在功能开关启用时委托给新方法，并把 `onCancel` 传为 0。这样保留原先“从调用开始使用固定时长”的行为。

### `CancellationSignal` 仍是协作式取消

普通应用可以向支持取消的公开 API 传入 `CancellationSignal`，并在自己的业务截止时间到达时调用 `cancel()`。下面的示例应运行在工作线程；5 秒是业务策略，不是系统常量：

```kotlin
val signal = CancellationSignal()
val cancellation = scheduler.schedule(
    { signal.cancel() },
    5,
    TimeUnit.SECONDS,
)

try {
    resolver.query(uri, projection, queryArgs, signal)?.use { cursor ->
        consume(cursor)
    }
} catch (_: OperationCanceledException) {
    recordQueryCancellation(uri)
} finally {
    cancellation.cancel(false)
}
```

这段代码把超时转换成取消请求，并及时关闭 Cursor。Provider 及其数据库执行路径仍要响应取消信号；调用 `cancel()` 不等于强制终止远程线程。业务层还应丢弃截止时间之后返回的结果。

## Stable 与 unstable 引用的准确语义

`acquireContentProviderClient()` 通过 `acquireProvider()` 建立 stable 引用，`acquireUnstableContentProviderClient()` 通过 `acquireUnstableProvider()` 建立 unstable 引用。两者在 `ContentProviderClient` 中分别记录为 `mStable = true` 和 `false`。

stable 引用表达调用进程对 Provider 的稳定依赖。它会参与 ActivityManager 的 Provider 引用与进程依赖管理，但不保证 Provider 永不死亡，也不代表 client 可以长期不关闭。`close()` 会按引用类型调用 `releaseProvider()` 或 `releaseUnstableProvider()`。

unstable 引用允许平台在 Provider 进程消失时采用不同的依赖清理语义。`ContentProviderClient.execute*()` 捕获 `DeadObjectException` 后，仅对 unstable client 调用 `unstableProviderDied()`；当前 client 随即失效，调用方应关闭它，并按业务策略重新 acquire。

因此，unstable 不等同于“临时查询”，也不会缩短查询耗时或自动增加超时。选择依据是 Provider 进程死亡时，调用方是否接受失败并自行恢复。

## 三类容量不能混算

### Binder 映射区

Android 15、16、17 的 `ProcessState.cpp` 都使用：

`BINDER_VM_SIZE = 1 MiB - 2 × sysconf(_SC_PAGE_SIZE)`

4 KiB 页设备对应 1,040,384 字节，即 1016 KiB；16 KiB 页设备对应 1,015,808 字节，即 992 KiB。页大小决定数值，进程是 32 位还是 64 位不能直接推出结果。

这段空间由一个目标进程中多笔尚未释放的入站 Binder 事务共享。Parcel 数据、对象 offsets、对齐、并发占用和碎片都会影响分配，所以它也不是单笔 Parcel 的稳定上限。

### `IPCThreadState` 的命令 Parcel

Android 17 的 `IPCThreadState` 构造函数把 `mIn` 和 `mOut` 的初始容量设为 256 字节。它们承载用户态与驱动交互的 Binder 命令流，必要时可以增长；这个初始容量既不代表内核 transaction buffer，也不限制 ContentProvider 查询结果。

### CursorWindow

`frameworks/base/core/res/res/values/config.xml` 的 base 值是 `config_cursorWindowSize = 2048`，单位为 KiB。`CursorWindow.getCursorWindowSize()` 读取系统资源后乘以 1024，因此默认构造路径在未被产品资源覆盖时得到 2 MiB。

CursorWindow 保存查询结果的一段行数据。跨进程传递时，窗口的共享内存文件描述符和控制信息经过 Binder；窗口中的全部行字节不会复制进 Binder transaction buffer。公开的 `CursorWindow(String, long)` 还允许指定容量，因此“所有 CursorWindow 固定 2 MiB”也不成立。

## 对性能排查的影响

出现 `TransactionTooLargeException` 时，优先核对 URI、`projection`、query args、`Bundle`、`ContentValues`、批量操作数组及同进程并发事务。不要因为 CursorWindow 的基础配置是 2 MiB，就把异常归因于“2 MiB Binder 缓冲区”。

查询长时间不返回时，可以按以下顺序拆分：

1. 调用是否发生在主线程；
2. Provider 进程是否正在冷启动或等待发布；
3. 提供方 Binder 线程是否排队；
4. 数据库是否受锁、I/O 或低效查询计划影响；
5. `CancellationSignal` 是否已传递，Provider 路径是否检查取消；
6. stable 或 unstable client 在进程死亡后是否按预期释放和重建。

Android 17 新增的 system API 只改变受权限调用方的无响应监测策略，没有减少一次 query 的 Binder 往返、数据库工作量或 CursorWindow 填充成本。

## 版本差分

| 标签 | `setDetectNotResponding()` | `setDetectNotRespondingOnCancel()` | `setCallNotCancelledTimeout()` | `setSticky()` |
|---|---|---|---|---|
| `android-15.0.0_r1` | 有 | 无 | 无 | 无 |
| `android-16.0.0_r1` | 有 | 无 | 无 | 无 |
| `android-17.0.0_r1` | 有 | 有，System API | 有，测试入口 | 无 |

这张表只陈述三个固定标签中该类的符号差异。方法是否可用于某个产品，还要同时检查 SDK surface、权限、feature flag 和设备配置。
