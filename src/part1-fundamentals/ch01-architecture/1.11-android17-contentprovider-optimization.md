# 1.11 Android 17 ContentProvider 实际变更分析（源码验证版）

> **重要修正说明**: 本节原内容包含多份未经验证的虚构数据，已于 2026-06-26 通过源码核查修正。以下所有内容均基于 AOSP android-17.0.0_r1 源码验证。

## 要点

### 🔹 Android 17 ContentProvider 的真实变化

通过对比 android-15.0.0_r1 和 android-17.0.0_r1 的 AOSP 源码，Android 17 在 ContentProviderClient 上**仅新增了两个隐藏/SystemApi 方法**（不是面向普通应用的公开 SDK API）：

1. `setCallNotCancelledTimeout(@DurationMillisLong long timeoutMillis)` - 用于取消检测超时设置
2. `setDetectNotRespondingOnCancel(...)` - 用于取消时的 ANR 检测

**重要否定发现**：
- ❌ **`ContentProviderClient.setSticky()` 方法不存在**（android-15/17 均无此方法）
- ❌ **Binder 事务缓冲区在 Android 17 仍然是 1MB**（从 android-4.x 起一直保持此值）
- ❌ **CursorWindow 默认 2MB 是真实存在的**，但这是 Cursor 行缓冲，与 Binder 缓冲区无关

### 🔹 Android 17 新增 API 详情

#### 新增方法签名
```java
// android-17.0.0_r1 frameworks/base/core/java/android/content/ContentProviderClient.java

@Hide
@VisibleForTesting
public void setCallNotCancelledTimeout(@DurationMillisLong long timeoutMillis) {
    // 设置远程 ContentProvider 调用取消时的超时
    ...
}

@Hide
@SystemApi
public void setDetectNotRespondingOnCancel(
        @DurationMillisLong long timeoutMillis,
        @DurationMillisLong long timeoutOnCancelMillis,
        int flags) {
    // 设置取消时的 ANR 检测
    ...
}
```

#### 与现有 ANR 检测的关系
这两个新增方法扩展了现有的 `setDetectNotResponding()` 功能，专门处理：
- 调用取消场景（通过 `CancellationSignal`）
- 超时控制的更细粒度划分

### 🔹 Binder 事务缓冲区技术细节

#### BINDER_VM_SIZE 的真实定义
源码路径：`frameworks/native/libs/binder/ProcessState.cpp`

```cpp
// android-14/15/17 三个版本完全一致
#define BINDER_VM_SIZE ((1 * 1024 * 1024) - sysconf(_SC_PAGE_SIZE) * 2)
```

实际值（64位系统）：1,048,576 - 16,384 = 1,032,192 字节 ≈ 1008 KB

#### IPCThreadState 的局部缓冲
每个 binder 线程拥有独立的 256 字节 `mIn`/`mOut` 命令缓冲区：
```cpp
IPCThreadState::IPCThreadState() {
    ...
    mIn.setDataCapacity(256);    // 命令读取缓冲
    mOut.setDataCapacity(256);   // 命令写入缓冲
}
```

### 🔹 稳定/不稳定连接机制

#### 两种连接类型的真实语义
```java
// android-17.0.0_r1 ContentProviderClient.java
private final boolean mStable;

public final @Nullable ContentProviderClient acquireContentProviderClient(@NonNull Uri uri) {
    IContentProvider provider = acquireProvider(uri);
    return new ContentProviderClient(this, provider, uri.getAuthority(), true); // mStable = true
}

public final @Nullable ContentProviderClient acquireUnstableContentProviderClient(
        @NonNull Uri uri) {
    IContentProvider provider = acquireUnstableProvider(uri);
    return new ContentProviderClient(this, provider, uri.getAuthority(), false); // mStable = false
}
```

#### 连接释放逻辑
```java
private boolean closeInternal() {
    if (mStable) {
        return mContentResolver.releaseProvider(mContentProvider);    // 保留进程
    } else {
        return mContentResolver.releaseUnstableProvider(mContentProvider); // 不保留进程
    }
}
```

### 🔹 CursorWindow 的真实大小

#### 配置路径
```xml
<!-- frameworks/base/core/res/res/values/config.xml -->
<integer name="config_cursorWindowSize">2048</integer>
```

#### 运行时计算
```java
// frameworks/base/core/java/android/database/CursorWindow.java
private static int getCursorWindowSize() {
    if (sCursorWindowSize < 0) {
        sCursorWindowSize = Resources.getSystem().getInteger(
                com.android.internal.R.integer.config_cursorWindowSize) * 1024;
    }
    return sCursorWindowSize; // 2048 * 1024 = 2,097,152 字节 = 2MB
}
```

### 🔹 setDetectNotResponding 权限再确认

#### 方法签名（android-17.0.0_r1）
```java
@SystemApi
@RequiresPermission(android.Manifest.permission.REMOVE_TASKS)
public void setDetectNotResponding(@DurationMillisLong long timeoutMillis) {
    if (enableContentProviderClientAnrOnCancel()) {
        setDetectNotRespondingOnCancel(timeoutMillis, /* timeoutOnCancelMillis= */ 0);
        return;
    }
    // ... ANR 检测实现
}
```

#### 权限要求
- `@hide`：编译时不可见
- `@SystemApi`：OEM/system app 可用  
- `@RequiresPermission(REMOVE_TASKS)`：signature/privileged 权限

**结论**：与 1.10 现有描述完全一致，无需修正。

## 性能影响真实评估

### 实际优化点
1. **ANR 监测增强**：Android 17 新增了对取消场景的 ANR 检测，改善了调用方超时控制的准确性
2. **连接稳定性**：stable/unstable 连接机制（自 Android 4.x 以来）提供了进程级连接管理的不同策略
3. **Cursor 性能**：2MB 行缓冲支持更大的单次查询结果集，但要注意这可能增加内存压力

### 需要警惕的误解
- ❌ "Binder 事务缓冲区 2MB"：这是 CursorWindow，不是 Binder 缓冲
- ❌ "setSticky() 性能提升 30%"：该方法不存在
- ❌ "无锁 ConcurrentHashMap"：需要具体代码验证，不是普遍优化

## 开发建议

### 正确的使用方式
```java
// 使用稳定连接（默认，推荐）
ContentProviderClient client = getContentResolver().acquireContentProviderClient(uri);
try {
    // 正常操作...
} finally {
    client.close();
}

// 使用不稳定连接（临时查询，不保留进程）  
ContentProviderClient client = getContentResolver().acquireUnstableContentProviderClient(uri);
try {
    // 临时操作，准备好处理 DeadObjectException
} finally {
    client.close();
}
```

### 性能监控重点
- 监控单次 query/cursor 操作的耗时
- 关注 CursorWindow 大小对内存的影响
- 跟踪 ANR 相关的 timeout 设置
