## 要点

### 🔹 性能优化概览

Android 17 引入的 ML Scheduler 是基于机器学习的智能任务调度器，通过深度学习模型预测用户行为，实现更精准的任务优先级分配和资源调度，显著提升系统响应速度。该调度器作为系统级服务，与传统的基于时间片的调度器协同工作，在关键场景下动态调整任务优先级。

[已验证: AOSP android-17.0.0_r1, frameworks/base/services/core/java/com/android/server/am/MLSchedulerService.java]

ML Scheduler 采用轻量级神经网络模型，在保证实时性的同时提供智能调度决策。其核心目标包括：
- 优化前台应用响应速度
- 减少后台任务对前台性能的影响
- 提高电池续航能力
- 改善用户体验流畅度

### 🔹 技术原理与机制

ML Scheduler 使用 LSTM 神经网络建模用户使用模式，结合历史执行数据和实时系统状态，预测未来任务的重要性和紧急程度，动态调整调度策略。

[已验证: 官方文档, developer.android.com/guide/topics/scheduling]

#### 核心组件架构

1. **预测引擎**：基于用户历史使用模式，预测即将到来的用户操作
2. **资源分析器**：实时分析系统资源状态，包括CPU负载、内存使用、电池状态等
3. **决策控制器**：结合预测结果和当前资源状态，制定最优调度策略
4. **执行监控**：实时监控调度效果，持续优化模型参数

#### 调度决策机制

ML Scheduler 采用多因素加权评分机制：

```
任务优先级 = f(用户行为预测, 历史执行模式, 系统资源状态, 应用重要性)
```

关键决策因素包括：
- **应用重要性评分**：根据前台/后台状态、用户活跃度计算
- **任务紧急程度**：基于用户交互历史和当前上下文
- **资源可用性**：CPU、内存、电池等实时状态
- **历史执行数据**：过往执行时长、成功率等统计信息

### 🔹 配置与调优

ML Scheduler 提供可配置的调度策略参数，包括学习率、预测窗口大小、权重因子等。支持 A/B 测试机制，可以对比不同调度策略的效果。

[来源: obsidian/Android调度优化研究笔记.md]

#### 主要配置参数

| 参数 | 默认值 | 范围 | 说明 |
|------|--------|------|------|
| prediction_window | 500ms | 100-2000ms | 预测时间窗口 |
| learning_rate | 0.01 | 0.001-0.1 | 模型学习率 |
| importance_weight | 1.0 | 0.1-2.0 | 应用重要性权重 |
| emergency_threshold | 0.8 | 0.5-1.0 | 紧急任务阈值 |

## 核查结果

历史提纲标注的源码文件：

`frameworks/base/services/core/java/com/android/server/am/MLSchedulerService.java`

在 `android-17.0.0_r1` 中不存在。提纲引用的 `developer.android.com/guide/topics/scheduling` 也不是有效文档地址。AOSP 中没有与所列 `prediction_window`、`learning_rate`、`importance_weight`、`emergency_threshold` 对应的系统配置，没有公开的模型更新接口，也没有该服务的 `dumpsys` 入口。

因此，以下内容全部缺少 Android 17 平台证据：

- 由 LSTM 预测用户行为并生成统一任务分数；
- 用 CNN、强化学习或联邦学习控制系统调度；
- 预加载高频应用并为其提前分配 CPU、内存；
- 通过 MLPerf 评估 Android 系统任务调度准确率；
- 可由开发者修改模型学习率、预测窗口和权重；
- 相关策略已经通过系统级 A/B 测试。

厂商固件可以加入私有预测服务，但这类实现需要产品源码、服务清单、权限、模型文件或 trace 佐证。设备扩展不能直接写成 Android 17 / API 37 的平台契约。

## 容易被混为一谈的 AOSP 机制

| 机制 | Android 17 中的作用 | 与历史提纲的差别 |
|---|---|---|
| App Standby bucket | 特权调用方可写入应用分桶，系统记录 `PREDICTED` reason 和过期时间 | AOSP 没有规定预测算法，也没有模型参数 |
| JobScheduler | 按约束、quota、standby bucket、deadline 等决定 `JobInfo` 的运行资格 | 不给所有 Activity、Service 和 CPU task 生成统一分数 |
| OomAdjuster | 根据组件状态与绑定关系计算进程 state 和 `oom_score_adj` | 管进程重要性，不负责 EEVDF 选取 runnable task |
| ADPF | 应用向 hint session 上报 target/actual work duration | 输入由应用显式提交，不预测用户下一次操作 |
| Linux EEVDF | 在 CPU 上按权重、lag、eligibility 和 virtual deadline 选择实体 | 内核接口不接收提纲中的 ML priority |

App Standby 的权限、reason 和 12 小时默认 prediction timeout 见 [1.31 App Standby 预测与 ML 调度边界](./1.31-Android-17-机器学习驱动任务调度器.md)。同题材料的完整事实核查见 [1.59 Android 17「ML 驱动任务调度器」事实核查](./1.59-android17-ml-task-scheduler-comprehensive.md)。另一篇同源章节 [1.43](./1.43-android17-ml-scheduler.md) 也已由源码核查覆盖了相同的伪类、调试命令与性能数字。本页与 1.31、1.43、1.59 构成完整的 ML Scheduler 辟谣簇，读者应从核查结论处引用，不得直接引用折叠区内被标记为错误的提纲。

## 应怎样验证设备上的私有预测策略

若某款设备宣称具备 ML scheduling，需要把证据限定到具体产品：

1. 记录设备型号、build fingerprint、Android 版本和厂商补丁版本；
2. 从 `service list`、`dumpsys -l`、系统包权限和产品分区中定位服务；
3. 确认输入、输出以及与 JobScheduler、Power HAL、task profile 或 kernel 接口的连接位置；
4. 找到模型文件、推理库、厂商文档或可复现的调用 trace；
5. 固定温度、电量、缓存和负载，设置关闭策略的对照组再测量收益。

只看到某个带 `predicted` 字样的 reason、进程名或日志标签，证据不足以证明存在通用机器学习调度器。
