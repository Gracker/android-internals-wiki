# 1.50 Android 17 ResourcesManager/Configuration 与 Activity Relaunch 判定模型

<!-- outline-start -->
## 要点

### 🔹 配置变更判定模型
Android 17 中 ActivityRecord#shouldRelaunchLocked() 已被重构为基于配置差分和 Shell Transitions 的新判定模型。配置变更不再立即触发全局 relaunch，而是通过 TransitionController 创建 TRANSIT_CHANGE 过渡动画实现原子性配置更新。

### 🔹 精确触发条件
新增 RELAUNCH_REASON_WINDOWING_MODE_RESIZE 和 RELAUNCH_REASON_FREE_RESIZE 两种精确触发条件，使用 deferWindowLayout/continueWindowLayout 嵌套锁避免冗余布局计算。

### 🔹 6层掩码策略
skipRelaunchConfigMask 实现7层叠加：CONFIG_RESOURCES_UNUSED 直接 return false 后，(a)~(g) 六层叠加。DisplayCompatPolicy 是双路径策略，PiP skip CONFIG_DENSITY 是显式无条件豁免。

## 扩展

### 🔸 跨应用配置同步
配置变更在多应用场景下的同步机制与性能影响分析。

### 🔸 低内存条件下的配置优化
在内存受限情况下，配置变更的处理策略和性能调优。

### Shell Transition 不替代 relaunch 判定

全局配置更新从 `ActivityTaskManagerService.updateConfigurationLocked()` 进入。它在 `deferWindowLayout()` 和 `continueWindowLayout()` 包围的区间内调用 `updateGlobalConfigurationWithTransition()`；启用 Shell Transitions 时，后者可以创建 `TRANSIT_CHANGE`，收集各 display 的变化。

这层 transition 负责组织窗口变化的收集与呈现。每个 Activity 是否重建，仍由 `ActivityRecord.ensureActivityConfiguration()` 计算 `changes`，再调用 `shouldRelaunchLocked()`。不能从存在 `TRANSIT_CHANGE` 推导出 Activity 获得了“原子配置更新”，也不能把 transition 当成跳过 relaunch 的条件。

### relaunch reason 是结果标签

`RELAUNCH_REASON_WINDOWING_MODE_RESIZE` 和 `RELAUNCH_REASON_FREE_RESIZE` 在 `shouldRelaunchLocked()` 返回 true 之后赋值。前者表示包含 resize 变化，后者还要求 task 正在 drag resizing；没有 resize 变化时使用 `RELAUNCH_REASON_NONE`。

这些常量记录这次重建的原因，供崩溃恢复和统计等后续路径读取。它们没有参与 skip mask 的计算，也没有构成两种独立的“精确触发条件”。判断时应从 `changes`、Activity 可处理的位及系统兼容策略出发。

### layout defer 是调度边界

`deferWindowLayout()` 把窗口布局置于 deferred 状态；`continueWindowLayout()` 恢复布局，并通知 `ClientLifecycleManager` 继续发送 defer 期间排队的 client transactions。源码允许 defer 嵌套，但这里描述的是布局和事务调度边界，不是互斥锁，也不负责判断某次 relaunch 是否冗余。

连续拖拽中的重建合并位于 `ActivityRecord.relaunchActivityLocked()` 一侧。它还受 `improveFluidResizingPerformance`、drag-resizing、`preserveWindow`、pending relaunch 或新窗口绘制状态约束，不能由一对 layout defer 调用概括。

### skip mask 不能按固定“六层”理解

Android 17 以 `ActivityInfo.getRealConfigChanged()` 初始化 `skipRelaunchConfigMask`。命中 `CONFIG_RESOURCES_UNUSED` 时直接跳过重建；其后还会依次考虑旧 target 的 VR UI mode、desk mode、PiP density、display-move 兼容、RRO constraints，以及包内限定符资源对应的 recreate mask。最终表达式是 `(changes & ~skipRelaunchConfigMask) != 0`。

PiP 中加入 `CONFIG_DENSITY` 只说明 density 位可以被当前分支忽略。若同一轮还含有未被 mask 覆盖的变化位，Activity 依旧需要 relaunch。固定写成“六层”或“七层”容易遗漏早返回、加 mask 与清 mask 三种不同方向的操作。

## 本页不承载的两个议题

“跨应用配置同步”和“低内存条件下的配置优化”没有在本页 outline 中给出可验证的源码入口。进程间的全局配置派发应沿 `WindowProcessController`、`ClientTransaction` 和 `ConfigurationController` 分析；内存回收则要区分 cached 进程的配置延迟、`ResourcesImpl` 弱引用回收和 `releaseSomeActivities("low-mem")`。这些机制不能合并成一个笼统的优化策略。
