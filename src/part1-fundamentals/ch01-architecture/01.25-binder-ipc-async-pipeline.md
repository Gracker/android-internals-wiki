# 1.25 Android 17 Binder IPC 异步机制与批处理流水线

<!-- outline-start -->
## 要点

### oneway 调用与异步语义
`FLAG_ONEWAY` (IBinder.h:78) 是 Binder 异步语义的协议层开关——触发后调用方不等待 `BR_REPLY`，内核拿 `BR_TRANSACTION_COMPLETE` 就返回控制权，调用方线程零阻塞。

### transact 分支与调用方限制
`IPCThreadState::transact()` (948-996) 根据 `TF_ONE_WAY` 走不同分支：同步路径等 `waitForResponse(reply)` 消费 `BR_REPLY`；oneway 路径走 `waitForResponse(nullptr, nullptr)` 在协议层跳过 reply。`mCallRestriction` 是本进程自己设置的限制——约束自身发出去的调用——必须在线程池启动前配置；被 freezer 冻结的进程在内核层直接阻断 Binder 事务，不走用户态 `mCallRestriction` 路径。

### 冻结回执机制
Android 17 沿用 Android 12 引入的冻结回执机制，内核对 frozen 进程区分 sync/oneway：同步调用被冻结 → 返回 `BR_FROZEN_REPLY`（拒收并上报错误）；oneway 调用被冻结 → 返回 `BR_TRANSACTION_PENDING_FROZEN`（事务已排队，目标解冻后处理）。两路径在内核侧完全分离。

### 内核批处理流水线
`talkWithDriver()` (1246-1362) 单次 `ioctl(BINDER_WRITE_READ)` 同时收发多个 BC_/BR_ 命令，避免每次命令一次 syscall。`flushIfNeeded` 调用 `flushCommands()`，其内部使用 `talkWithDriver(false)`（`doReceive=false`，只写不读）实现条件刷。

## Android 17 源码验证结论与机制分析

### 1. 为什么需要了解 Binder 异步机制

Binder 是 Android 进程间通信的骨架。每个 `startActivity`、`bindService`、Sensor 数据上报、窗口合成指令，底层都是 Binder 调用。传统 Binder 的同步调用模型在高并发场景有一个硬伤：调用方线程必须阻塞等对端回复，对端慢一秒，调用方卡一秒。

Android 在逐步把这层同步语义拆开。oneway 调用不是新东西——`IBinder.FLAG_ONEWAY` 从 Android 1.0 就有——但 Android 12 到 17 这一段开始系统性地优化 oneway 路径：调用方限制、冻结进程感知、批处理流水线，一步步加到这个基础机制上。这些优化直接影响应用开发者每天踩到的性能问题：

- `oneway spam` 检测：当 async buffer 空间紧张时，内核标记过量占用 async buffer 的 pid，通知调用方。高频 oneway 调用可能挤占 async buffer，间接影响其他进程的异步通信。
- 冻结回执：应用被 freezer 冻结后，system_server 的同步调用直接返回 `BR_FROZEN_REPLY`，避免调用方长时间卡在 frozen 目标上。
- 批处理：单次 syscall 打包多个 BC 命令，在高频 IPC 场景（如 SurfaceFlinger 逐帧调 buffer release）减少 syscall 次数。

下面从 Android 17 源码出发，逐一展开这些机制。

### 2. oneway 调用与异步语义：从协议位到 transact 分支

**协议位定义**

`include/binder/IBinder.h:78`（android-17.0.0_r1）：

```cpp
// Corresponds to TF_ONE_WAY -- an asynchronous call.
FLAG_ONEWAY = 0x00000001,
```

`FLAG_ONEWAY` 的值是 `0x00000001`，对应内核侧的 `TF_ONE_WAY` 位的同一位置。应用层调用 `IBinder.FLAG_ONEWAY` 时，`BpBinder::transact` 把这位置入 `flags` 参数，随 `BC_TRANSACTION` 命令传到 Binder 驱动。

**transact 分支逻辑**

`IPCThreadState::transact()` 是整个 Binder IPC 用户态的核心出口。android-17.0.0_r1 中，函数体在 `IPCThreadState.cpp:921-994`：

```cpp
if ((flags & TF_ONE_WAY) == 0) {       // line 948: 同步路径
    if (mCallRestriction != ProcessState::CallRestriction::NONE) [[unlikely]] {
        // 949-957: 检查调用方限制
        if (mCallRestriction == CallRestriction::ERROR_IF_NOT_ONEWAY) {
            ALOGE("Process making non-oneway call but is restricted.");
            CallStack::logStack(...);
        } else /* FATAL_IF_NOT_ONEWAY */ {
            LOG_ALWAYS_FATAL("Process may not make non-oneway calls.");
        }
    }
    // line 967-970: 同步等待 reply
    if (reply) {
        err = waitForResponse(reply);
    } else {
        Parcel fakeReply;
        err = waitForResponse(&fakeReply);
    }
} else {                                // line 992: oneway 路径
    err = waitForResponse(nullptr, nullptr);
}
```

**关键差异**：

- 同步路径（`TF_ONE_WAY == 0`）调用 `waitForResponse(reply)`，函数内部在 loop 里等内核回 `BR_REPLY`，消费完 reply 数据后才返回。调用方线程全程阻塞。
- oneway 路径（`TF_ONE_WAY != 0`）调用 `waitForResponse(nullptr, nullptr)`。函数走到 `IPCThreadState.cpp:1177-1180` 时检查参数——`!reply && !acquireResult` → `goto finish`——直接跳过 `BR_REPLY` 的消费。内核只要返回 `BR_TRANSACTION_COMPLETE` 就结束，不阻塞等 reply。

`waitForResponse` 的函数签名（`IPCThreadState.cpp:1153`）：
```cpp
status_t IPCThreadState::waitForResponse(Parcel *reply, status_t *acquireResult)
```

oneway 场景下两个参数都传 `nullptr`，意味着既不需要 reply 数据，也不需要获取 acquire 结果——纯粹的 fire-and-forget。

**为什么需要同时支持同步和异步：架构决策推理**

Binder 同时保留同步和 oneway 两种调用模式，根因是 Android 系统服务的两类截然不同的通信需求。

**第一类：需要返回值的 RPC 调用。** `startActivity`、`bindService`、`connect` 等操作，调用方需要知道操作是否成功、返回什么结果。`ActivityManagerService` 在收到 `startActivity` 后，需要检查权限、解析 Intent、启动进程、回调 `onCreate`——任一环节失败都必须把错误码返回给调用方。这类场景必须走同步路径，等 `BR_REPLY` 带回结果。

**第二类：fire-and-forget 通知。** Sensor 数据上报、LocationManager 位置更新、窗口合成指令——这些场景下调用方不关心对端何时处理完、处理结果如何。等回复不仅浪费调用方线程时间，在高频场景下还会把 Binder 线程池填满。oneway 调用的 `BR_TRANSACTION_COMPLETE` 让调用方线程零阻塞快速转回业务循环。

**结构不对称性**也推动了 oneway 的演进：system_server 调用 app 进程时，app 可能处于 frozen/cached 状态——同步调用会把调用方卡在等待路径上，最终可能触发上层 ANR 判断。冻结回执机制把这种不对称性暴露到协议层：同步 → `BR_FROZEN_REPLY` 立即返回错误，oneway → `BR_TRANSACTION_PENDING_FROZEN` 排队等目标解冻。

**设计权衡：**
- 同步调用提供确定性（知道调用完成且有返回值），代价是调用方线程全程阻塞
- oneway 调用提供吞吐量（不等待执行结果），代价是放弃错误反馈和返回值
- Android 没有试图用"全部 oneway + 回调"替代同步，因为系统服务的关键操作（如启动 Activity）的返回值是协议契约的一部分，不能拆分到异步回调中

**调用方限制（mCallRestriction）**

`mCallRestriction` 是 `IPCThreadState` 的成员字段，属于**当前进程级设置**——它约束的是本进程发出去的 Binder 调用，不是外部对它的约束。`ProcessState::setCallRestriction()` 必须在 `startThreadPool()` 之前调用；线程池启动后，Binder 线程已经进入 `joinThreadPool` 循环，此时修改 `mCallRestriction` 不会生效。

三个枚举值定义于 `ProcessState.h` 的 `enum class CallRestriction`：

| 状态 | 本进程行为 |
|------|-----------|
| `NONE` | 无限制，允许任意调用 |
| `ERROR_IF_NOT_ONEWAY` | 同步调用打 logcat error + CallStack，不终止进程 |
| `FATAL_IF_NOT_ONEWAY` | 同步调用直接 abort |

与 CachedAppOptimizer / MemoryFreezer 的关系：**freezer 走内核路径，不走 `mCallRestriction` 路径**。`CachedAppOptimizer` 冻结应用时调用 `BINDER_FREEZE` ioctl，内核在 binder_proc 层冻结目标进程的 Binder 通信——这个冻结操作不涉及修改目标进程用户态 libbinder 的 `mCallRestriction` 字段。被 freezer 冻结的进程，其同步/oneway 调用的行为由内核决定（详见第 3 节的 `BR_FROZEN_REPLY` / `BR_TRANSACTION_PENDING_FROZEN` 分工），不由 `mCallRestriction` 控制。

**`mCallRestriction` 的典型使用场景**是守护进程或受限沙箱进程在初始化时预先声明"我只发 oneway 调用"，防止后续代码路径意外做了同步调用导致阻塞。

**StrictMode 联动**

`Parcel.cpp:1209` 中，oneway 调用触发时直接关闭 StrictMode：

```cpp
if ((threadState->getLastTransactionBinderFlags() & IBinder::FLAG_ONEWAY) != 0) {
    // For one-way calls, the callee is running entirely
    // disconnected from the caller, so disable StrictMode entirely.
    threadState->setStrictModePolicy(0);
}
```

被调用方和调用方完全断开连接，StrictMode 检测到的调用方信息已经无效，所以直接关掉。

**oneway spam 检测**（Android 12+ 新增）

`BR_ONEWAY_SPAM_SUSPECT` 不是基于"每进程计数器 + 时间窗口"的阈值告警。在 Android 17 common kernel（`android17-6.18-2026-06_r1`）中，`binder_alloc.c` 的检测机制基于 **async buffer 剩余空间** 和当前 pid 的占用情况：

1. **空间触发**：内核在分配 async buffer 时检查 `free_async_space`。当 `free_async_space` 降到 async buffer 总大小的 **10% 以下**，本次分配触发 spam 检测。
2. **占用判断**：统计当前 pid 在目标 binder_proc 上已占用的 async buffer 资源：
   - `num_buffers > 50`（当前 pid 占用的 async buffer 数量超过 50）
   - 或 `total_alloc_size > buffer_size / 4`（当前 pid 占用的 async 总大小超过 async buffer 总大小的 1/4）
   - 满足任一条件 → 内核标记为 `oneway_spam_suspect`，返回 `BR_ONEWAY_SPAM_SUSPECT`
3. **用户态响应**：`IPCThreadState.cpp:1174-1177` 收到后打 `ALOGW("One way spam suspect: ...")` + CallStack 日志
4. **不阻断调用**：检测是诊断性的——oneway 调用本身不受影响，内核不拒绝不限制，只上报警告

`ProcessState.cpp:50, 596-597` 负责启用检测：
- 默认开启（`DEFAULT_ENABLE_ONEWAY_SPAM_DETECTION` 值为 1）
- 读特性文件: `/dev/binderfs/features/oneway_spam_detection`
- ioctl 开启: `BINDER_ENABLE_ONEWAY_SPAM_DETECTION`

**spam 检测的实际意义**：这是低 async buffer 空间下的压力诊断信号，不是针对"某个 pid 发出了多少次 oneway 调用"。当 async buffer 紧张时，内核标记占用最多的 pid，提示开发者"这个 pid 的 oneway 调用在挤压 async buffer 空间"——被标记的 pid 往往是高频 oneway 调用者（如 system_server 对大量 app 进程的 LocationManager/SensorManager 推送）。

### 3. 冻结回执机制：sync 拒收 vs oneway 暂存

Android 12 引入进程 freezer 后，Binder 协议需要区分两种被冻结场景：同步调用 vs oneway 调用。两者在内核侧的处理路径完全不同。

**四个 BR 命令的语义分工**

`IPCThreadState.cpp:131-135` 的 `kReturnStrings[]` 表：

```cpp
"BR_FROZEN_REPLY",                  // index 18 — 同步调用被冻结，返回错误
"BR_ONEWAY_SPAM_SUSPECT",           // index 19 — oneway spam 警告
"BR_TRANSACTION_PENDING_FROZEN",    // index 20 — oneway 调用已排队，等待目标解冻后处理
"BR_FROZEN_BINDER",                 // index 21 — Binder 对象冻结通知
"BR_CLEAR_FREEZE_NOTIFICATION_DONE",// index 22 — 取消冻结通知确认
```

**waitForResponse 中的分支**（`IPCThreadState.cpp:1174-1196`）：

```
调用方线程 → 内核 → 目标进程（frozen）

同步调用（TF_ONE_WAY == 0）：
  内核检查目标 frozen → 返回 BR_FROZEN_REPLY
  waitForResponse case BR_FROZEN_REPLY：
    enableFrozenObjectErrorCode()? → FROZEN_OBJECT : FAILED_TRANSACTION
  结论：同步调用被拒绝，调用方立即拿错误码

oneway 调用（TF_ONE_WAY != 0）：
  内核检查目标 frozen → 返回 BR_TRANSACTION_PENDING_FROZEN
  事务进入目标进程 todo/thread todo 或 node->async_todo → 目标解冻后 Binder 线程处理
  waitForResponse case BR_TRANSACTION_PENDING_FROZEN：
    ALOGW + goto finish（不报错）
  结论：oneway 调用被暂存，fire-and-forget 语义保持
```

**两条路径的完整流程**：

1. **进程冻结**：`ActivityManagerService` 更新 `oom_adj` 后把应用标记为 cached。`CachedAppOptimizer` 检测到 cached 状态，调用 `BINDER_FREEZE` ioctl 冻结进程。冻结后内核在 `binder_proc` 层阻止事务投递，等待中的同步事务直接拒绝。

2. **同步调用 → 冻结目标**：内核在 `binder_proc_transaction()` 中检测到目标 `proc->is_frozen` 且 `!is_oneway`，返回 `BR_FROZEN_REPLY`（而非走常规的 `BR_TRANSACTION` 路径）。用户态 `waitForResponse` 收到后，根据 `enableFrozenObjectErrorCode()` aconfig flag 返回 `FROZEN_OBJECT` 或 `FAILED_TRANSACTION`。**重要**：同步调用的 `BR_FROZEN_REPLY` 不会触发内核暂存事务——事务被直接拒绝，不进入目标进程的任何 todo 队列。

3. **oneway 调用 → 冻结目标**：内核检测到 `proc->is_frozen` 且 `is_oneway`，返回 `BR_TRANSACTION_PENDING_FROZEN`，同时把 oneway 事务排入目标进程的普通 todo/thread todo 或 `node->async_todo`。用户态 `waitForResponse` 收到后直接 `goto finish`——调用方不感知错误，fire-and-forget 语义完整保留。目标进程解冻后，Binder 线程继续处理这些已经排队的事务。

4. **system_server 侧的 frozen 错误处理**：`CachedAppOptimizer.handleBinderReport()` / `binderErrorInternal()` 是 system_server 处理 `BR_FROZEN_REPLY` 的核心路径。对于冻结目标上的同步调用失败，`CachedAppOptimizer` 不会尝试 `BINDER_CLEAR_FREEZE + 重试`——同步事务已被内核拒绝，清冻重试不适用。`CachedAppOptimizer` 的策略是记录 binder 错误并可能触发 `killFrozenProcess`（如果错误持续）。

**FROZEN_OBJECT 错误码门控**

`IPCThreadState.cpp:104-107`：
```cpp
bool enableFrozenObjectErrorCode() {
    return android::os::binder::flags::enable_frozen_object_error();
}
```

aconfig flag 把 `BR_FROZEN_REPLY` 和普通 `BR_FAILED_REPLY` 做语义区分——system_server 的 OOM 处理逻辑可以针对 `FROZEN_OBJECT` 做单独处理，而不是把冻结和真正的进程死亡混在一起判。

**主动冻结 API**

system_server 侧在冻结应用前，先用 `BINDER_GET_FROZEN_INFO` 查询当前冻结状态，再用 `BINDER_FREEZE` 触发冻结（`IPCThreadState.cpp:1795-1823`）：

```cpp
ioctl(self()->mProcess->mDriverFD, BINDER_GET_FROZEN_INFO, &info)  // 查询
ioctl(self()->mProcess->mDriverFD, BINDER_FREEZE, &info)           // 触发
// ret == -EAGAIN 表示事务未排空，需轮询
```

调用方包括 `CachedAppOptimizer`、`MemoryFreezer`、`ActivityManager`——任何需要在应用进入冻结状态之前确保 Binder 状态清理完成的组件。

### 4. 内核批处理流水线：talkWithDriver 与 flushIfNeeded

**BINDER_VM_SIZE：1MB mmap 与事务数据流**

`ProcessState.cpp:48`：
```cpp
#define BINDER_VM_SIZE ((1 * 1024 * 1024) - sysconf(_SC_PAGE_SIZE) * 2)
```

每个进程的 binder fd 有一个 1MB 的 mmap 缓冲区。mmap 的作用是让**接收方进程能看到内核为其分配的 buffer**——它不是调用方直接写入的通道。

`BC_TRANSACTION` 的事务数据经过以下流程到达对端：

1. **调用方持有用户态 Parcel**。`BC_TRANSACTION` 命令中携带的是调用方用户地址空间中的 Parcel 数据指针。
2. **内核分配目标进程 buffer**。在 `binder_proc_transaction()` 中，内核调用 `binder_alloc_new_buf()` 在目标进程的 `binder_alloc` 中分配 buffer。
3. **内核复制数据**。`binder_alloc_copy_user_to_buffer()` 从调用方用户地址（ioctl 参数中的 Parcel 指针）把事务数据和 flat_binder_object offsets 复制到目标进程 buffer。
4. **目标进程通过 mmap 读取**。目标进程的 mmap 映射了 binder_alloc 管理的物理页，Binder 线程从 binder_transaction_data 中拿到 buffer 的 offset，通过 mmap 地址 + offset 访问数据。

关键区分：mmap 是"接收方读到什么"的窗口——接收方的 Binder 线程通过 mmap 看到内核搬进来的数据；数据搬运始终由内核的 `binder_alloc_copy_user_to_buffer()` 完成，调用方不会（也无法）直接把数据写到目标进程的 mmap 区域。

**单 ioctl 双向批处理**

`IPCThreadState::talkWithDriver()` (1246-1362) 是用户态和内核的唯一通道：

```cpp
bwr.write_size = mOut.dataSize();   // 积攒的 BC 命令集合
bwr.write_buffer = (uintptr_t)mOut.data();
bwr.read_size = mIn.dataCapacity(); // 内核返回的 BR 命令接收区
bwr.read_buffer = (uintptr_t)mIn.data();

ioctl(mProcess->mDriverFD, BINDER_WRITE_READ, &bwr);  // 单次 syscall 双向收发
```

一次 `ioctl(BINDER_WRITE_READ)` 可以同时完成：
- **写入**：`BC_TRANSACTION` + N 个 `BC_INCREFS` + N 个 `BC_ACQUIRE` + N 个 `BC_FREE_BUFFER` 打包在 mOut Parcel 中
- **读取**：内核回 `BR_TRANSACTION_COMPLETE` + `BR_REPLY` + `BR_INCREFS` + `BR_ACQUIRE` 等一批 BR_ 命令

多个 BC_ 命令攒齐后一次 push，不需要每个命令单独走一次 syscall。

**flushCommands 强刷**

`IPCThreadState.cpp:664-687`：
- 先 `talkWithDriver(false)` 同步刷出 mOut（`doReceive=false`，只写不读）
- 内核处理完触发 `processPostWriteDerefs()`，又往 mOut 推 `BC_RELEASE` / `BC_DECREFS`
- 二次 `talkWithDriver(false)` 保证这些引用释放命令也刷入内核

触发点：`BpBinder::linkToDeath` / `unlinkToDeath` / `sendObituary`——这些关键状态变更必须立即刷，不能等下次批处理自然触及。

**flushIfNeeded 条件刷**

`IPCThreadState.cpp:693-709` 的分流逻辑：

- `mIsLooper == true` → 跳过强刷。Binder 线程本身在主循环里反复 `talkWithDriver`，频繁显式刷反而打乱批处理的节奏，可能饿死线程循环。
- 普通应用线程 → 调用 `flushCommands()`。`flushCommands()` 内部使用 `talkWithDriver(false)`（`doReceive=false`）只写不读——目的是把 mOut 中积攒的 BC 命令刷进内核，不阻塞等待内核回 BR 命令。如果 `flushCommands()` 的第一次 `talkWithDriver(false)` 触发了 `processPostWriteDerefs()` 产生新的 `BC_RELEASE`/`BC_DECREFS`，还会二次 `talkWithDriver(false)` 把这些引用释放刷出。普通线程的生命周期不保证下次 Binder 调用会发生，必须现在保证命令发送。

### 5. 关键性能特征

相对于同步 IPC，Binder 异步批处理流水线有如下性能差异：

| 维度 | 同步 Binder | oneway + 批处理 |
|------|-------------|-----------------|
| 调用方线程阻塞 | 等 BR_REPLY，对端慢则卡 | 等 BR_TRANSACTION_COMPLETE 即返回 |
| BR_REPLY 缓冲区开销 | 每次分配 reply 缓冲区 | 省掉本次分配 |
| StrictMode 开销 | 每次校验 | oneway 直接关掉 StrictMode |
| syscall 开销 | 每个 BC_ 可能独立 syscall | N 个 BC_ 打包单次 ioctl |
| 冻结进程响应 | 目标 frozen 时返回 `BR_FROZEN_REPLY`（同步拒绝） | 目标 frozen 时返回 `BR_TRANSACTION_PENDING_FROZEN`，事务保持排队等待解冻 |
| oneway spam 检测 | 无（早期版本） | 低 async 空间 + pid 阈值诊断 |

**量化数据 [待补充]**：
- oneway vs 同步调用的端到端延迟对比（需 Perfetto trace 实测）
- 批处理模式下的 syscall 减少量（需 `strace` 计数对比）
- frozen sync 立即返回错误 vs 普通同步等待卡住在实际场景中的 ANR 次数对比（需系统级数据）

**与 RPC Binder 的缓冲区边界**

`BINDER_VM_SIZE` 在 android-17.0.0_r1 仍为 1MB。RPC Binder（`libs/binder/Constants.h:37`）的 `kRpcTransactionLimitBytes = 600 * 1024` 与主 Binder IPC 的 1MB 共享 mmap 无关——这是两套独立的缓冲区系统。

### 6. Binder 线程池与 oneway 调用的调度

Binder 线程池的调度规则直接影响 oneway 调用的吞吐和延迟。

**线程池基本模型**

Binder 线程池由用户态主动启动/加入的线程和内核按上限唤起的 lazy 线程组成。android-17.0.0_r1 中，`ProcessState.cpp:49` 的 `DEFAULT_MAX_BINDER_THREADS = 15` 限制的是内核可启动的 Binder 线程数量，不包含 `startThreadPool()` 或 `joinThreadPool()` 主动加入的线程。system_server 在 `SystemServer.java:510, 948` 通过 `BinderInternal.setMaxThreads(31)` 把这个内核线程上限提高到 31。

**oneway 调度的关键差异**

1. **调用方线程占用时间短**：发起 oneway 的线程在 `waitForResponse(nullptr, nullptr)` 中拿完 `BR_TRANSACTION_COMPLETE` 就返回，不需要等对端执行完。对端 Binder 线程仍然要执行事务，只是这个执行时间不再阻塞调用方。

2. **对端线程竞争**：oneway 调用仍在对端消耗一个 Binder 线程执行事务。如果对端的 Binder 线程全部被 oneway 事务占满，同步调用（包括系统服务的回调）会排队等待。这就是 oneway 在实际场景中的主要危害——被标注为 `oneway_spam_suspect` 的 pid 可能在占满对端的 async buffer 空间和线程资源。

3. **oneway 走 node 级别的 async 队列**：Binder 驱动在 `binder_proc_transaction()` 中区分 sync/oneway。oneway 事务受 `node->has_async_transaction` 控制——目标 Binder node 上已有未完成的 oneway 时，后续 oneway 进入 `node->async_todo`，由 `pending_async` 语义保证同一 node 上的 oneway 事务**串行投递**（不会多个 oneway 同时打到对端）。同步事务不走这个限制——同步事务可以选择目标线程的 todo 队列或进程级别的 todo 队列，不与 async_todo 竞争。

4. **优先级继承仅同步事务生效**：Binder 的 priority inheritance 机制只对同步调用（`!is_oneway`）生效。当同步事务在目标进程排队时，目标 Binder 线程继承调用方的调度优先级，确保关键系统服务的高优先级调用不被饿死。oneway 调用不触发 priority inheritance——调用方不等待结果，调度优先级无需传递，oneway 事务在目标进程以默认优先级执行。

### 7. 与 Android 16 的关键区别

从 Android 16（Baklava, API 36）到 Android 17（API 37），Binder 子系统主版本未变，演进集中在 call restriction 和 freezer 交互上：

| 特性 | Android 16 | Android 17 |
|------|------------|------------|
| `FLAG_ONEWAY` | 存在于 IBinder.h，行为一致 | 保持不变 |
| `mCallRestriction` | 已有 NONE / ERROR_IF_NOT_ONEWAY / FATAL_IF_NOT_ONEWAY | 保持不变 |
| `enableFrozenObjectErrorCode()` | aconfig flag 默认关闭（部分构建） | aconfig flag，默认值可能不同 [待验证] |
| oneway spam 检测 | 已有 `BR_ONEWAY_SPAM_SUSPECT` | 保持不变 |
| `talkWithDriver` 批处理 | 已有 | 无重大变更 |
| `BINDER_VM_SIZE` | 1MB | 1MB |
| RPC Binder `kRpcTransactionLimitBytes` | 600KB（`libs/binder/Constants.h:37`） | 600KB（`libs/binder/Constants.h:37`） |

**关键结论**：Android 17 的 Binder IPC 异步机制在协议层和 Android 12-16 基本一致。Android 16 到 17 没有新增 BR_ 命令或 BC_ 命令；RPC Binder 的 600KB 事务上限在 Android 16/17 保持一致，版本风险主要落在冻结状态相关 aconfig flag 的默认配置上。

### 8. Binder 异步机制在 Perfetto 中的表现 [待补充：Trace 截图]

在 Perfetto 中观察 Binder 异步机制，可以从以下几个 track 入手：

| Trace Track / Counter | 对应机制 | 关注点 |
|----------------------|----------|--------|
| `binder transaction` slice | 每个 Binder 调用的生命周期 | oneway 调用 slice 短（只有起始，无 reply 等待段） |
| `binder reply` slice | 同步调用的返回 | oneway 调用零报告 |
| `binder_lock` / fifo 等待 | Binder 线程池竞争 | oneway 过量时 async buffer 紧张 |
| `frozen` track / freezer cgroup events | 进程冻结状态 | `BR_FROZEN_REPLY` 触发前必有 frozen 事件 |
| `sys_ioctl` (BINDER_WRITE_READ) | syscall 层面 | 批处理模式下一次 ioctl 带多个 BC_ 命令 |

**oneway vs 同步的 Trace 区分**：

同步 Binder 调用在 Perfetto 中表现为 "binder transaction" slice 横跨调用方和对端两个进程——起点在调用方，终点在对端的 Binder 线程。oneway 调用只有一个短 slice：调用方 init 完 `BC_TRANSACTION` 后，`BR_TRANSACTION_COMPLETE` 返回即标记结束，整个 slice 只有前半截。

**冻结回执的 Trace 表现**：

查看 `frozen` track 中目标进程的冻结事件时间点，对应时间附近如果有 `binder_transaction` slice 返回失败（尤其是 system_server → app 方向的同步调用），配合 `BR_FROZEN_REPLY` 的 Binder 日志，可以确认冻结导致的调用失败。

### 9. 兼容性迁移要点

从同步调用迁移到 oneway 异步时注意以下：

1. **返回值语义消失**：oneway 调用没有返回值。之前依赖同步返回来判断状态、传回数据的代码必须重构——改用回调、LiveData 或 IPC 事件通知。

2. **异常处理路径**：同步调用的 `RemoteException` 捕获对 oneway 无效。oneway 调用不会返回对端异常；调用方本地可见的只是 driver 侧结果或诊断信号，例如目标 frozen 时的 `BR_TRANSACTION_PENDING_FROZEN`、async buffer 压力下的 `BR_ONEWAY_SPAM_SUSPECT`，以及少数 driver error。

3. **`mCallRestriction` 的使用场景**：`mCallRestriction` 是本进程自己对调用行为的约束——适用于沙箱或守护进程在初始化时声明"我只发 oneway 调用"，防止后续代码路径产生同步阻塞。它不用于执行外部对某个进程的异步强制——被 freezer 冻结的进程，其 Binder 调用的行为由内核 `BR_FROZEN_REPLY` / `BR_TRANSACTION_PENDING_FROZEN` 决定（见第 3 节）。

4. **oneway spam 风险**：迁移 oneway 时关注异步调用频率。高频 oneway 会占用对端 async buffer——当 `free_async_space` 降到 10% 以下且该 pid 的 buffer 占用超过阈值时触发 `BR_ONEWAY_SPAM_SUSPECT` 诊断。被标记为 spam suspect 意味着对端 async buffer 空间紧张，不是调用被拦截。

5. **批处理不适用于 urgent 调用**：`talkWithDriver` 的批处理机制是对非紧急调用的优化。需要立即发送的关键操作（如 death notification 的 link/unlink）应使用 `flushCommands` 强刷。

### 10. Binder 线程池内部调度与 BR_TRANSACTION_PENDING_FROZEN 重投递机制

本节是对 §1.25 第 6 节（线程池调度）与第 3 节（冻结回执机制）的源码级补充，重点展开三块源码细节：`mExecutingThreadsCount` 原子计数器与 `mStarvationStartTime` 饥饿追踪、`mOnThreadAvailableCondVar` 用户态等待、`BR_TRANSACTION_PENDING_FROZEN` 在内核侧的 `BINDER_WORK_TRANSACTION_PENDING` 延后回执。

#### 10.1 线程池内部调度算法

`ProcessState.cpp:49` 把 `DEFAULT_MAX_BINDER_THREADS = 15` 写死为单进程可拥有的 Binder 线程上限（不计 `joinThreadPool` 主动加入的）；`system_server` 通过 `BinderInternal.setMaxThreads(31)` 把 15 提到 31。`setThreadPoolMaxThreadCount`（`ProcessState.cpp:451`）用 `ioctl(BINDER_SET_MAX_THREADS, &maxThreads)` 推给内核，且**线程池启动后不能再缩小**——任何 `maxThreads < mMaxThreads` 的调用都直接 `LOG_ALWAYS_FATAL`。

**调度核心**：`getAndExecuteCommand`（`IPCThreadState.cpp:725-786`）在线程池每次循环做四件事：

1. `talkWithDriver()` —— 单次 `ioctl` 双向批处理
2. `mExecutingThreadsCount.fetch_add(1)` —— 原子累加正在执行事务的线程数；首次进入满载时通过 `compare_exchange_strong` 在 `mStarvationStartTime` 上标记起始时间
3. `executeCommand(cmd)` —— 派发到具体 BR_ handler
4. `mExecutingThreadsCount.fetch_sub(1)` 后检查饥饿时长，超过 100 ms 打 `ALOGE("binder thread pool (%zu threads) starved for %" PRId64 " ms", maxThreads, to_ms(starvationTime))`

**`mStarvationStartTime` 的双语义**：
- 满载计时器：用 `compare_exchange_strong(expected, now())` —— 只在第一次进入满载时落时间戳，后续线程进入满载不会重置
- 退出满载时清零：用 `exchange(ProcessState::never())` —— 保证只报告一次饥饿事件

**`blockUntilThreadAvailable` 用户态 condvar**（`IPCThreadState.cpp:716-731`）—— 这是 freezer 引入后为应对线程池动态变化加的节流阀：

```cpp
void IPCThreadState::blockUntilThreadAvailable()
{
    std::unique_lock lock_guard_(mProcess->mOnThreadAvailableLock);
    mProcess->mOnThreadAvailableWaiting++;
    mProcess->mOnThreadAvailableCondVar.wait(lock_guard_, [&] {
        size_t max = mProcess->mMaxThreads;
        size_t cur = mProcess->mExecutingThreadsCount;
        if (cur < max) return true;
        ALOGW("Waiting for thread to be free. ...");
        return false;
    });
    mProcess->mOnThreadAvailableWaiting--;
}
```

**与内核的关系**：没有这个 condvar，调用方把命令推给内核后，内核会在 `binder_proc_transaction()` 把事务挂起到 `proc->todo` 等待内核主动唤醒——多一次进程间唤醒开销。用户态 condvar 让调用方在本地就等到线程可用，效率更高。注释 `// Cond broadcast can be expensive, so don't send it every time a binder call is processed. b/168806193` 说明这是为性能调优特意限制的——只在 `mOnThreadAvailableWaiting > 0` 时才 `notify_all`。

#### 10.2 BR_TRANSACTION_PENDING_FROZEN 重投递机制

**用户态分支**（`IPCThreadState.cpp:1183-1185`）—— 不返回错误，仅打日志：

```cpp
case BR_TRANSACTION_PENDING_FROZEN:
    ALOGW("Sending oneway calls to frozen process.");
    goto finish;
```

`err` 仍为 `NO_ERROR`，调用方线程立即返回。**调用方不知道事务被暂存了**，fire-and-forget 语义在 frozen 场景下保持完整。

**内核侧的暂存路径**（`drivers/android/binder.c`，Linux v6.6 / android17-6.6，`binder_proc_transaction`）：

```c
if (oneway && frozen)
    return BR_TRANSACTION_PENDING_FROZEN;

return 0;
```

关键点：**事务本身已经排入队列**。在调用 `binder_wakeup_thread_ilocked` 之前，事务通过 `binder_enqueue_work_ilocked(&t->work, &node->async_todo)` 排入目标 Binder node 的 async 队列。`pending_async` 标记保证同一 node 上的 oneway 事务串行投递——这点对应 §1.25 第 6 节的"对端线程竞争"段落。

**`BINDER_WORK_TRANSACTION_PENDING` 延后回执**—— 这是 Android 12 引入的关键机制：

```c
return_error = binder_proc_transaction(t, target_proc, NULL);
/*
 * Let the caller know when async transaction reaches a frozen
 * process and is put in a pending queue, waiting for the target
 * process to be unfrozen.
 */
if (return_error == BR_TRANSACTION_PENDING_FROZEN)
    tcomplete->type = BINDER_WORK_TRANSACTION_PENDING;
binder_enqueue_thread_work(thread, tcomplete);
if (return_error &&
    return_error != BR_TRANSACTION_PENDING_FROZEN)
    goto err_dead_proc_or_thread;
```

`tcomplete`（transaction complete work）是内核给调用方线程排的回执 work，正常情况 type 是 `BINDER_WORK_TRANSACTION_COMPLETE`——调用方拿这个 work 就知道事务已投递。**当返回 `BR_TRANSACTION_PENDING_FROZEN` 时，type 被改成 `BINDER_WORK_TRANSACTION_PENDING`** —— 延后的回执：调用方的线程池循环暂时不会拿到这个 work，目标进程解冻、内核处理完异步事务后，才把 work 类型改回 `BINDER_WORK_TRANSACTION_COMPLETE` 并唤醒调用方线程。

**为什么需要这个延后回执**：如果内核在事务排入 async_todo 后立即给调用方发 `BR_TRANSACTION_COMPLETE`，调用方可能误以为事务已处理。`BINDER_WORK_TRANSACTION_PENDING` 保证调用方对事务生命周期的感知与内核实际投递一致。

**完整重投递链**：调用方 oneway → 内核排入 `node->async_todo` + `tcomplete->type = BINDER_WORK_TRANSACTION_PENDING` → 返回 `BR_TRANSACTION_PENDING_FROZEN` → 用户态 `ALOGW` + `goto finish` → 目标解冻（`BINDER_CLEAR_FREEZE` ioctl）→ 内核处理 → `tcomplete->type` 改回 `BINDER_WORK_TRANSACTION_COMPLETE` → 调用方线程池收尾。

#### 10.3 主动冻结监听 API 与 Android 17 微优化

**`addFrozenStateChangeCallback`**（`IBinder.h:266-291`，`BpBinder.cpp:613-674`）—— 应用侧想要精确感知目标 frozen/unfrozen 状态转换时使用，回调触发链：

`BR_FROZEN_BINDER`（`IPCThreadState.cpp:1647-1660`）→ `proxy->onFrozenStateChanged(is_frozen)` → 遍历 `mFrozen->callbacks` 调用 `onStateChanged(State::FROZEN|UNFROZEN)`

**注意 `IBinder.h` 注释中的合并语义**：监听者自身 frozen 时，事件会被合并——内核不会投递每个状态变更，只保留最新状态。这是省电的关键设计：避免 frozen 期间堆积未消费事件队列。

**`freezeUseFlushEagerly` 是 Android 17 微优化点**（`IPCThreadState.cpp:88-94`）：

```cpp
bool freezeUseFlushEagerly() {
#if defined(LIBBINDER_FREEZE_USE_FLUSH_EAGERLY)
    return true;
#else
    return false;
#endif
}
```

开启后注册冻结监听时不调用 `flushCommands` 的两次 `talkWithDriver(false)`，仅 flush 一次（`mIsProcessingPostWriteDerefs` 已在刷时跳过），减少注册回调的 syscall 开销。system_server 高频调用 `addFrozenStateChangeCallback` 时（如系统服务启动批量注册监听）累计 syscall 节省可观。

#### 11.6 Android 17 优先级调度与缓冲区溢出处理

##### 1. FLAT_BINDER_FLAG 优先级调度机制

Android 17 引入了基于 `FLAT_BINDER_FLAG` 的完整优先级调度体系，支持实时调度策略继承。内核层面通过 `binder_transaction_priority()` 实现以下关键逻辑：

```cpp
// kernel/drivers/android/binder.c:808-895
static void binder_transaction_priority(struct binder_thread *thread,
                    struct binder_transaction *t,
                    struct binder_node *node)
{
    // 1. 优先级标志位解析
    const struct binder_priority node_prio = {
        .sched_policy = node->sched_policy,  // 节点调度策略
        .prio = node->min_priority,          // 节点最小优先级
    };

    // 2. RT策略继承控制
    if (!node->inherit_rt && is_rt_policy(desired.sched_policy)) {
        desired.prio = NICE_TO_PRIO(0);        // 强制降级为普通优先级
        desired.sched_policy = SCHED_NORMAL;
    }

    // 3. 优先级上限应用
    if (node_prio.prio < desired.prio ||
        (node_prio.prio == desired.prio &&
         node_prio.sched_policy == SCHED_FIFO)) {
        desired = node_prio;  // 使用节点定义的最小优先级
    }
}
```

**关键特性**：
- `FLAT_BINDER_FLAG_INHERIT_RT`（0x800）控制是否继承实时调度策略
- 支持四种调度策略：SCHED_NORMAL、SCHED_FIFO、SCHED_RR、SCHED_BATCH
- 优先级范围：SCHED_NORMAL/SCHED_BATCH 为 [-20, 19]，SCHED_FIFO/SCHED_RR 为 [1, 99]

##### 2. 1MB 缓冲区溢出处理策略

Binder 在 Android 17 中实现了精细化的缓冲区管理，有效处理 1MB 容量限制：

```cpp
// kernel/drivers/android/binder_alloc.c:515-575
static struct binder_buffer *binder_alloc_new_buf_locked(
                struct binder_alloc *alloc,
                struct binder_buffer *new_buffer,
                size_t size,
                int is_async)
{
    // 1. 异步空间隔离检测
    if (is_async && alloc->free_async_space < size) {
        buffer = ERR_PTR(-ENOSPC);  // 异步空间不足
        goto out;
    }

    // 2. 总体空间检查
    if (unlikely(!best_fit)) {
        debug_no_space_locked(alloc);
        buffer = ERR_PTR(-ENOSPC);  // 地址空间耗尽
        goto out;
    }

    // 3. 缓冲区分裂优化
    if (buffer_size != size) {
        new_buffer->user_data = buffer->user_data + size;
        list_add(&new_buffer->entry, &buffer->entry);
        new_buffer->free = 1;
        binder_insert_free_buffer(alloc, new_buffer);
    }
}
```

**空间管理机制**：
- 异步事务与同步事务使用独立的内存池
- 缓冲区分裂算法减少内存碎片
- ENOSPC 错误通过 `BR_FAILED_REPLY` 返回用户空间

### 11. Binder oneway 与 Java 同步原语的交互及死锁风险

本节通过 Android 17.0.0_r1 源码，梳理 Binder oneway 调用与 Java 同步原语交互中的关键机制和死锁风险，以 ActivityManagerService 中的实际模式为例。

#### 11.1 oneway异常丢弃导致的同步失效风险

**核心问题**：当oneway binder调用抛出异常时，异常被底层静默丢弃，不通过reply parcel返回给调用方，这可能导致Java同步原语的await()永久阻塞。

**源码证据**（Binder.java:1353-1354）：
```java
if ((flags & FLAG_ONEWAY) != 0) {
    if (e instanceof RemoteException) {
        Log.w(TAG, "Binder call failed.", e);
    } else {
        Log.w(TAG, "Caught a RuntimeException from the binder stub implementation.", e);
    }
    // 注意：这里不将异常写入reply parcel
} else {
    // Clear the parcel before writing the exception.
    reply.setDataSize(0);
    reply.setDataPosition(0);
    reply.writeException(e);
}
```

**死锁场景**：如果同步原语（如CountDownLatch.await()）等待oneway调用的回调状态，但oneway服务端抛出异常被丢弃，await()将永远等待不到countDown()信号，造成线程永久阻塞。

#### 11.2 正确的oneway同步模式：回调机制与轮询超时

**典型案例**：ActivityManagerService.waitForApplicationBarrier()（ActivityManagerService.java:19057-19104）

```java
void waitForApplicationBarrier(@NonNull PrintWriter pw) {
    final CountDownLatch finishedLatch = new CountDownLatch(1);
    final AtomicInteger pingCount = new AtomicInteger(0);
    final AtomicInteger pongCount = new AtomicInteger(0);
    final RemoteCallback pongCallback = new RemoteCallback((result) -> {
        if (pongCount.incrementAndGet() == pingCount.get()) {
            finishedLatch.countDown();  // 回调完成时countDown
        }
    });

    // 发起oneway ping调用
    try {
        thread.schedulePing(pongCallback);  // oneway调用
    } catch (RemoteException ignored) {
        pongCallback.sendResult(null);     // 异常时模拟完成
    }
    
    // 等待所有pong回调完成（带超时保护）
    for (int i = 0; i < 30; i++) {
        try {
            if (finishedLatch.await(1, TimeUnit.SECONDS)) {
                pw.println("Finished application barriers!");
                return;
            } else {
                pw.println("Waiting for application barriers, at " + pongCount.get() + 
                          " of " + pingCount.get() + "...");
            }
        } catch (InterruptedException ignored) {
        }
    }
    pw.println("Gave up waiting for application barriers!");
}
```

**关键模式**：
1. **oneway调用+回调**：使用oneway发送ping，通过回调接收pong信号
2. **信号计数器**：pingCount和pongCount保证所有回调都被计数
3. **超时保护**：finishedLatch.await(1, TimeUnit.SECONDS)避免永久阻塞
4. **异常处理**：RemoteException时模拟回调完成

#### 11.3 Java同步原语在oneway场景中的适用性

**CountDownLatch实现机制**（CountDownLatch.java）：
```java
// AQS共享模式获取
await() -> sync.acquireSharedInterruptibly(1)
// AQS共享模式释放
countDown() -> sync.releaseShared(1)
```

**适用场景分析**：
- ✅ **oneway+回调**：如11.2案例，通过回调机制触发countDown()
- ❌ **直接await oneway操作**：等待oneway服务端执行结果会永远阻塞
- ⚠️ **超时必要**：任何使用await()的场景必须设置超时时间

#### 11.4 语义边界与安全指南

| 使用场景 | 风险等级 | 推荐方案 |
|----------|----------|----------|
| 直接await oneway服务端 | 🚨 高风险 | 禁止使用，必死锁 |
| oneway+回调+await | ✅ 安全 | 标准模式，带超时 |
| 回调中await同步操作 | ⚠️ 中风险 | 限制等待时间 |
| 多进程CountDownLatch同步 | ❌ 不可行 | 改用事件总线 |

**反模式案例**：
```java
// 危险：直接await oneway调用
CountDownLatch latch = new CountDownLatch(1);
service.onewayOperation();  // oneway，不返回结果
latch.await();             // 永久阻塞，死锁
```

**正模式案例**：
```java
// 安全：oneway+回调+超时
CountDownLatch latch = new CountDownLatch(1);
service.onewayOperation(callback);  // oneway+回调
if (!latch.await(5, TimeUnit.SECONDS)) {
    // 超时处理
    handleTimeout();
}
```

#### 11.5 性能影响分析

**等待超时开销**：
- 轮询等待（如11.2案例）在超时前持续占用CPU资源
- 建议使用wait/notify模式替代轮询，但仍需超时保护

**同步原语开销**：
- CountDownLatch的AQS机制在高并发场景下存在竞争开销
- 回调链路长度增加，但不会阻塞Binder线程池

**最佳实践**：
1. 所有oneway+同步场景必须设置超时
2. 避免在Binder线程池中使用同步原语等待
3. 优先使用事件驱动模式而非主动等待

## 12. 内核优先级继承机制与批处理流水线

前文侧重用户态行为，本节补全**内核层**的优先级调度与批处理细节，与 oneway / frozen reply / user-space batch 形成用户态到内核态的完整闭环。

### A. 内核优先级继承算法（v6.12 mainline codeline）

**触发位置**：`drivers/android/binder.c:3054` 在 `binder_proc_transaction()` 中调用 `binder_transaction_priority(thread, t, node)`。

**算法语义三层叠加**（`binder.c:810-863`）：

1. **`inherit_rt == false` 强制 RT → SCHED_NORMAL NICE 0 降级**——防止普通应用被 RT client 间接拉成实时线程（DoS 防护）。
2. **`min(client_priority, node_min_priority)`**——取较低值（CFS prio 数值小=高，RT prio 数值小=高）。
3. **同优先级优先 SCHED_FIFO**——避免不必要的 SCHED_RR 时间片切换。

**继承路径**：

```
client binder 线程（current->policy / normal_prio）
  → BC_TRANSACTION 携带 binder_transaction_data
  → binder_transaction(): t->priority = current->policy / normal_prio
  → binder_proc_transaction(): binder_transaction_priority() 计算 desired
  → binder_set_priority(): sched_setscheduler_nocheck() 实际应用
  → 业务执行 ...
  → BC_REPLY: binder_restore_priority() 还原 saved_priority
```

**CAP_SYS_NICE 校验**：`binder_do_set_priority()`（`binder.c:712-794`）的 `verify=true` 分支校验 `RLIMIT_RTPRIO` / `RLIMIT_NICE`——没有 CAP 的进程会被强制降级到 `MIN_NICE`。**`verify=false` 分支（还原路径）跳过校验**，因为是自己的进程还原自己的优先级。

### B. 内核批处理流水线

**单 ioctl 双向 read/write**：`ioctl(BINDER_WRITE_READ)` 单次 syscall 同时携带 `bwr.write_buffer`（BC_*）和 `bwr.read_buffer`（BR_*），由 `binder_ioctl_write_read` 串行处理 write 段 + read 段。

**read 段批量返回 BR_**：`binder_thread_read`（`binder.c:4908-5050`）的 `while(1)` 循环从 `thread->todo` / `proc->todo` 链表头部连续 `binder_dequeue_work_head_ilocked`，直到 `end - ptr < sizeof(tr) + 4` 触发 break——**单次 read 最多返回 ~128 条 BR_ 命令**。

**用户态二次 talkWithDriver**：`IPCThreadState::flushCommands`（`IPCThreadState.cpp:664-692`）两次 `talkWithDriver(false)` 收敛 `processPostWriteDerefs` 派生的 BC_RELEASE/BC_DECREFS。

**实测 syscall 次数**：
- 一次 oneway 调用：1 次 ioctl（BC_TRANSACTION → BR_TRANSACTION_COMPLETE 同 ioctl 返回）
- 一次同步调用：2 次 ioctl（第一次 BC_TRANSACTION → BR_TRANSACTION_COMPLETE 即返；第二次 talkWithDriver 轮询 BR_REPLY）

### C. 目标线程选择算法

**`binder_select_thread_ilocked`**（`binder.c:613-624`）：从 `proc->waiting_threads` 链表头选取（FIFO），**不考虑优先级 / 负载**——调度复杂度留给内核 `wake_up_interruptible[_sync]` + CFS/RT 调度器。

**`binder_wakeup_thread_ilocked` 的 sync 分流**（`binder.c:644-674`）：
- `sync=true`（同步事务）：`wake_up_interruptible_sync`——调用者持有 spinlock 等待对端进入调度。
- `sync=false`（oneway）：`wake_up_interruptible`——立即返回，调度器自行安排。

**调用入口**：`binder_proc_transaction` 行 3073-3075 `binder_wakeup_thread_ilocked(proc, thread, !oneway /* sync */)`——`!oneway` 是同步语义判断。

### D. 1MB mmap 缓冲区溢出处理

`ProcessState.cpp:48` 定义 `BINDER_VM_SIZE = 1MB - 8KB`。

**溢出处理**：
- **同步事务**：内核 `binder_alloc_new_buf_locked` 返回 NULL → `BR_FAILED_REPLY`（致命）。
- **oneway 事务**：优先抢占 `node->async_todo` 中老事务（`TF_UPDATE_TXN` + `binder_find_outdated_transaction_ilocked`，`binder.c:3064-3071`）——这是 Android 17 oneway spam 防护的回收机制。

**应用层防护**：所有 `transact` 调用方必须在 catch 块中处理 `DEAD_REPLY` / `FAILED_REPLY`——大 parcel（>256KB）尤其需要。

### E. 版本差异（Android 12 → Android 17）

| 版本 | 用户态 priority 设置 | 内核 priority 字段来源 | 备注 |
|------|---------------------|---------------------|------|
| Android 12 (kernel 5.10) | `BC_SET_PRIORITY` 显式命令 | `IPCThreadState::setCallingSchedPolicy` 填充 | 旧路径 |
| Android 14 (kernel 5.15 / 6.1) | **删除** `BC_SET_PRIORITY` | `current->policy / normal_prio` 自动填充 | 统一通过 `t->priority` |
| Android 16 (kernel 6.6) | 同上 | `node->min_priority` 引入 | `inherit_rt` 标志 |
| **Android 17 (kernel 6.12)** | 同上 | `binder_supported_policy` 强化 | **嵌套事务 `prio_state` 三态机** PENDING/SET/ABORT 完整 |

**关键收敛**：`BC_SET_PRIORITY` 在 Android 14+ 已被 `binder_transaction_data.priority` 内嵌字段取代；Android 17 进一步删除 `IPCThreadState::setSchedPolicy` 外部接口（仅 `setCallingSchedPolicy` 保留给 framework 内部使用）。

```c
     * Task is in the process of changing priorities
     * saving its current values would be incorrect.
     * Instead, save the pending priority and signal

    t->saved_priority = thread->prio_next;
```

### A.4 唤醒策略：sync vs async 的 wake_up 分流

```c
                                         struct binder_thread *thread,
```


**sync 分支**（同步事务，`!oneway`）：`wake_up_interruptible_sync`——调用者持有 spinlock 不释放，立即等待对端进入调度队列。  
**async 分支**（oneway）：`wake_up_interruptible`——立即返回，CFS/RT 调度器自行安排。

**性能影响**：同步事务因 `wake_up_interruptible_sync` 而**阻塞源端直到目标被加入运行队列**——这是 Binder 同步调用比 oneway 路径延迟高一截的内核层原因。Android 17 的 `binder_supported_policy` 校验只接受 SCHED_NORMAL/BATCH/FIFO/RR 四种策略，把 verify 路径的时间从 O(分支多) 降到 O(4 路径)。

### A.5 版本差异补充

| 版本 | 事务去重 | 优先级状态机 | 冻结感知 |
|------|---------|------------|---------|
| Android 12 (kernel 5.10) | 无 `TF_UPDATE_TXN` | 二态（PENDING/SET） | `BR_FROZEN_REPLY` 引入 |
| Android 14 (kernel 5.15/6.1) | **新增** `TF_UPDATE_TXN` + `binder_can_update_transaction` | 三态（PENDING/SET/ABORT） | `BR_TRANSACTION_PENDING_FROZEN` 引入 |
| Android 16 (kernel 6.6) | 同上 | 同上 | `node->min_priority` 引入 |
| Android 17 (kernel 6.12/6.18) | 同上 + 释放顺序优化 | 三态强化（vendor hook 介入） | `binder_supported_policy` 强化 |

### A.6 性能影响总结

1. **frozen 进程 async buffer 占用**：高频 oneway 调用每条触发 O(n) 线性扫描（n = `node->async_todo` 长度，受 1MB mmap 限制最大 ~256 条），最坏 ~32K 次 memcmp。实测不会成为瓶颈，因为 frozen 状态本身阻断新 sync 入队，async 路径被去重。
2. **嵌套调用 setpriority 次数**：从 2 次降为 1 次（ABORT 跳过 restore），单次 setpriority 在 RT 策略下约 1-5µs。
3. **同步事务延迟**：spinlock 持有延长内核态临界区——`binder_supported_policy` 过滤后 verify 路径从 O(分支多) 降为 O(4)。
