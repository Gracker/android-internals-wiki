# 1.32 Android 17 Binder IPC 观测：Perfetto、内核快照与 Parcel 证据

Binder 性能分析要先回答具体问题：调用发生在哪两个线程之间，时间花在服务端执行还是服务端开始前的等待，事务有多大，目标进程是否缺少可接单的 Binder 线程。不同观测面只能回答其中一部分，没有一个接口能同时给出完整答案。

以下分析以 `android-17.0.0_r1` 和 `android17-6.18-2026-06_r6` 为准。Binder 缓冲区分配见 [1.30](30-binder-transaction-buffer-performance.md)，事务录制的专门机制见 [1.31](31-binder-performance-recording-trace.md)，线程池饥饿见 [1.38](38-binder-thread-pool-starvation-performance.md)。

## 一、先选择能回答问题的观测面

| 观测面 | 能看到什么 | 看不到什么 | 常见权限 |
| --- | --- | --- | --- |
| 应用或服务自行计时 | 接口、业务参数摘要、调用结果、调用方感知耗时 | 内核排队、服务端调度分量 | 普通应用可用 |
| Perfetto Binder + sched | client/server 线程、同步或 oneway、事务时序、线程调度状态 | Parcel 内容；未启用 AIDL trace 时通常没有方法名 | 开发者或平台调试 |
| Binder 内核 tracepoint | transaction id、目标进程/线程、code、flags、分配大小 | 业务接口语义、Parcel 内容 | 系统 trace 配置 |
| debugfs Binder 快照 | 线程、ready thread、free async space、待处理工作和最近失败 | 连续时间轴、端到端耗时 | 通常需要 userdebug/eng、root 或额外 SELinux 权限 |
| libbinder 日志与 Java 异常 | 大事务警告、扩展错误、失败的 Java 映射 | 成功事务的完整分布 | 查看对应进程日志 |
| `RecordedTransaction` | 受控测试中的请求和回复 Parcel | 通用线上监控能力 | 编译期开关开启且调用者为 root |

排查时先用 Perfetto 找到慢事务，再用调度数据解释等待；怀疑大事务时加入 buffer 分配事件；怀疑队列或 oneway 积压时读取 debugfs 快照。只有协议内容本身无法从时间和大小定位时，才在隔离测试环境考虑事务录制。

## 二、用 Perfetto 建立 Binder 时间轴

### 1. Android 17 内核中有哪些关键事件

`binder_trace.h` 在 r6 内核中定义了以下常用 tracepoint：

- `binder_transaction`：事务进入驱动，包含 transaction id、目标进程/线程、reply、code 和 flags；
- `binder_transaction_received`：目标线程从驱动取得该事务；
- `binder_transaction_alloc_buf`：目标进程分配事务缓冲区，包含 `data_size`、`offsets_size` 和 `extra_buffers_size`；
- `binder_txn_latency_free`：事务对象释放时记录两端 pid/tid、code 和 flags，适合与 transaction id 关联对象生命周期；
- `binder_wait_for_work`：Binder 线程进入等待时的工作状态；
- `binder_command` / `binder_return`：用户态与驱动交换 BC/BR 命令；
- 一组 `binder_alloc_*`、`binder_free_*` 和 `binder_update_page_range` 事件：用于分析缓冲区页分配与回收。

r6 内核没有名为 `binder_reply` 或 `binder_freeze` 的 tracepoint。回复通过 `binder_transaction` 的 `reply` 字段表达，冻结相关状态也不能用虚构事件名加入 Perfetto 配置。

### 2. 一份可复用的录制配置

下面的配置用于分析事务时序、缓冲区大小和线程调度。问题只涉及时延时，可以删去 `binder_transaction_alloc_buf`；需要更深的分配分析时，再加入其他 `binder_alloc_*` 事件。

```textproto
duration_ms: 15000

buffers {
  size_kb: 65536
  fill_policy: RING_BUFFER
}

data_sources {
  config {
    name: "linux.ftrace"
    target_buffer: 0
    ftrace_config {
      ftrace_events: "binder/binder_transaction"
      ftrace_events: "binder/binder_transaction_received"
      ftrace_events: "binder/binder_transaction_alloc_buf"
      ftrace_events: "sched/sched_switch"
      ftrace_events: "sched/sched_waking"

      atrace_categories: "aidl"
      atrace_apps: "*"
    }
  }
}

data_sources {
  config {
    name: "linux.process_stats"
    target_buffer: 0
    process_stats_config {
      scan_all_processes_on_start: true
    }
  }
}
```

`aidl` category 用于给受支持的 AIDL 调用增加接口和方法切片。未采到 AIDL 切片时，Binder 事务仍可通过线程、进程、transaction code 和时序分析，只是 `aidl_name`、`interface`、`method_name` 可能为空。用户版本对应用级 atrace 有额外限制，`atrace_apps` 最好换成待测的可调试包名。

将配置保存为 `binder.pbtxt` 后，可以用下面的命令录制。输出路径是 Android 为 Perfetto 预留的目录。

```bash
adb shell perfetto --txt -c - \
  -o /data/misc/perfetto-traces/binder.perfetto-trace \
  < binder.pbtxt

adb pull /data/misc/perfetto-traces/binder.perfetto-trace
```

也可以使用 Perfetto 官方的 `record_android_trace` 脚本或 UI。轻量模式中的 `binder_driver` 是方便的 atrace 类别；需要精确控制事件与 buffer 时，pbtxt 配置更便于复现。

### 3. `android_binder_txns` 的字段怎样解释

导入 `android.binder` 标准库后，`android_binder_txns` 会把 client slice、flow 和 server slice 关联起来。Android 17 tag 中的常用字段包括：

- `client_ts` / `client_dur`：调用方 Binder slice 的时间与墙钟时长；
- `server_ts` / `server_dur`：服务端 Binder slice 的时间与墙钟时长；
- `client_process`、`client_thread`、`server_process`、`server_thread`；
- `is_main_thread`、`is_sync`；
- `aidl_name`、`interface`、`method_name`；
- `client_monotonic_dur` / `server_monotonic_dur`：排除系统 suspend 后的时长；
- `binder_txn_id` / `binder_reply_id`：回到原始 slice 和其他标准库表的关联键。

这个表没有 `dispatch_dur` 列。`server_ts - client_ts` 可以作为“事务进入追踪点后，到服务端 slice 开始”的间隔，但它同时受目标线程可用性、CPU 调度和跟踪点定义影响。不要只凭这个差值断言线程池已经饱和。

下面的查询列出最慢的主线程同步事务，并显式计算服务端开始前的间隔。

```sql
INCLUDE PERFETTO MODULE android.binder;

SELECT
  COALESCE(interface, '<unknown-interface>') AS interface,
  COALESCE(method_name, '<unknown-method>') AS method,
  client_process,
  client_thread,
  server_process,
  server_thread,
  (server_ts - client_ts) / 1e6 AS server_start_delay_ms,
  server_dur / 1e6 AS server_ms,
  client_dur / 1e6 AS client_ms,
  binder_txn_id
FROM android_binder_txns
WHERE is_sync = 1
  AND is_main_thread = 1
  AND client_dur >= 5e6
ORDER BY client_dur DESC
LIMIT 50;
```

这里的 `5e6` 只是查询筛选值，不是平台健康阈值。动画、启动、后台批处理和系统服务有不同预算，应按具体场景设定。

### 4. 聚合分位数要使用聚合函数

按 AIDL 方法统计 P50/P90/P99 时，必须对每组调用使用 `PERCENTILE()`。直接在 `GROUP BY` 查询中选择未聚合的 `client_dur`，得到的是组内某一行，不能代表分位数。

```sql
INCLUDE PERFETTO MODULE android.binder;

SELECT
  COALESCE(interface, '<unknown-interface>') AS interface,
  COALESCE(method_name, '<unknown-method>') AS method,
  COUNT(*) AS calls,
  PERCENTILE(client_dur, 50) / 1e6 AS client_p50_ms,
  PERCENTILE(client_dur, 90) / 1e6 AS client_p90_ms,
  PERCENTILE(client_dur, 99) / 1e6 AS client_p99_ms,
  PERCENTILE(server_dur, 90) / 1e6 AS server_p90_ms
FROM android_binder_txns
WHERE is_sync = 1
GROUP BY interface, method_name
ORDER BY client_p99_ms DESC;
```

方法名为空时，先按 client/server 进程聚合，再结合原始 slice、transaction code 和服务源码缩小范围。缺少 AIDL trace 时强行按 `aidl_name` 分组，只会把大量不同调用合在 `<unknown>` 中。

### 5. 结合线程状态解释慢在哪里

`android.binder` 还提供 `android_sync_binder_thread_state_by_txn`。它按 transaction id 汇总 client 和 server 在事务区间内的线程状态，可用于区分运行、可运行但未获 CPU、可中断睡眠和不可中断等待。

找到一个 `binder_txn_id` 后，可以用下面的查询查看两端状态。示例中的 `12345` 要替换为上一条查询返回的 id。

```sql
INCLUDE PERFETTO MODULE android.binder;

SELECT
  b.client_process,
  b.server_process,
  s.thread_state_type,
  s.thread_state,
  s.thread_state_dur / 1e6 AS state_ms,
  s.thread_state_count
FROM android_binder_txns b
JOIN android_sync_binder_thread_state_by_txn s
  USING (binder_txn_id)
WHERE b.binder_txn_id = 12345
ORDER BY state_ms DESC;
```

按以下顺序解释：

1. `server_dur` 长，服务端线程大部分时间处于 Running：优先检查服务代码、序列化和计算；
2. 服务端线程长时间 Sleeping 或 Uninterruptible Sleep：检查锁、文件、驱动或下游同步 Binder 调用；
3. `server_start_delay_ms` 长且服务端缺少及时运行的线程：再结合 debugfs 的 ready thread、pending work 和目标线程 sched 轨迹判断；
4. `client_dur` 明显长于服务端区间：检查回复后的调用方唤醒、CPU 调度以及 client 区间中的其他嵌套调用。

`client_dur - server_dur` 不是纯排队时间。同步 Binder 的 client slice 覆盖调用方等待回复的墙钟区间，里面可能混入 client/server 调度、嵌套 Binder、锁等待和系统 suspend。

### 6. oneway 要看频率、开始延迟和消费速度

oneway 调用在提交给驱动后不等待服务端完成。诊断 oneway 风暴时，应同时观察单位时间调用数、`server_ts - client_ts` 的增长和服务端 `server_dur`，而不是只看一次调用的 client 时长。

```sql
INCLUDE PERFETTO MODULE android.binder;

SELECT
  client_process,
  server_process,
  COALESCE(interface, '<unknown-interface>') AS interface,
  COALESCE(method_name, '<unknown-method>') AS method,
  COUNT(*) AS calls,
  PERCENTILE(server_ts - client_ts, 90) / 1e6 AS start_delay_p90_ms,
  PERCENTILE(server_dur, 90) / 1e6 AS server_p90_ms
FROM android_binder_txns
WHERE is_sync = 0
GROUP BY client_process, server_process, interface, method_name
ORDER BY calls DESC;
```

调用数必须结合 trace 时长换算为频率。固定写成“超过 50 次就是风暴”没有跨设备和跨业务的依据。

## 三、debugfs 是快照，不是时序数据库

### 1. r6 内核暴露的文件

Android 17 的 r6 内核在 Binder debugfs 根目录创建：

| 文件 | r6 内核中的内容 |
| --- | --- |
| `state` / `state_hashed` | 进程、线程、node、ref、buffer、事务栈和待处理工作；hashed 版本隐藏部分指针值 |
| `stats` | 全局及逐进程 BC/BR 命令计数、对象计数、线程数、ready thread、free async space、pending transaction 快照 |
| `transactions` / `transactions_hashed` | 当前进程和事务状态的精简输出 |
| `transaction_log` | 最近 32 条事务日志的环形快照 |
| `failed_transaction_log` | 最近 32 条失败事务日志的环形快照 |
| `proc/<pid>` | 指定 Binder 进程的详细状态 |

标准路径是 `/sys/kernel/debug/binder/`。不存在通用的 `/proc/<pid>/binder/stats` 接口。设备没有挂载 debugfs、SELinux 不允许 shell 读取或采用厂商裁剪内核时，这些文件可能不可用。

在允许 `adb root` 的调试版本上，可以先读取目标进程文件和全局统计。下面用示例 pid `12345`，执行时要替换为目标 pid。

```bash
adb root
adb shell cat /sys/kernel/debug/binder/proc/12345
adb shell cat /sys/kernel/debug/binder/stats
adb shell cat /sys/kernel/debug/binder/failed_transaction_log
```

不要把 `stats` 当作带时间窗口的监控指标。大部分计数从驱动初始化后累积，没有每秒速率；若要比较前后变化，应在明确的复现窗口读取两次并计算差值。

### 2. 如何解释逐进程统计

`print_binder_proc_stats()` 在 r6 内核中输出：

- `threads`：该 `binder_proc` 当前登记的线程数；
- `requested threads: requested+started/max`；
- `ready threads`：位于 `waiting_threads` 列表中的线程数；
- `free async space`：该进程异步事务可用空间；
- node、ref、buffer 和页面统计；
- `pending transactions`：当时位于 `proc->todo` 且类型为 transaction 的数量；
- 该进程累计的 BC/BR 与对象计数。

这些字段都有边界。`threads` 不等于“业务正在工作的线程数”；进入过 Binder 驱动的线程也会出现在进程结构中。`pending transactions` 只统计 `proc->todo` 中的事务，不能代表 `thread->todo`、每个 node 的 `async_todo` 等所有队列之和。

线程池饥饿需要组合证据：复现期间 `ready threads` 持续为 0，`proc->todo` 有待处理事务，Perfetto 中服务端开始延迟升高，并且现有 Binder 线程被锁、I/O 或下游同步调用占用。任意一个单点快照都不足以下结论。

### 3. binderfs features 只表示能力

Android 17 的 `ProcessState` 从 `/dev/binderfs/features/` 探测驱动能力。r6 内核创建 `oneway_spam_detection`、`extended_error`、`freeze_notification` 和 `transaction_report` 文件，每个文件返回 0 或 1。

这些文件不是开销、事务数或队列长度。它们只能说明驱动是否支持对应协议。binderfs 的实际挂载点可能因设备而异；AOSP libbinder 使用的是 `/dev/binderfs/features/`。

## 四、大事务与缓冲区压力要看哪些证据

### 1. `binder_transaction_alloc_buf` 提供事务大小

r6 内核的 `binder_transaction_alloc_buf` 事件包含三个大小：

- `data_size`：Parcel 普通数据区；
- `offsets_size`：Binder object 偏移数组；
- `extra_buffers_size`：scatter-gather 附加缓冲区；

它们通过同一个 transaction id 与 `binder_transaction` 关联。Perfetto UI 可以查看事件参数；批量分析时也可以从原始 ftrace event 和 args 表提取。不要用 `client_dur` 反推 payload 大小，两者没有稳定换算关系。

### 2. Android 17 的日志阈值不是驱动上限

`frameworks/native/libs/binder/Constants.h` 在 Android 17 中把 `kLogTransactionsOverBytes` 设为 `300 * 1024`。`BpBinder` 会为超过该值的发出事务记录 `Large outgoing transaction`，`BBinder` 也会记录接收到的大事务。

300 KiB 是主动告警线，不是单次事务的硬上限。Binder 映射空间由进程内所有在途事务共享；同步回复、并发调用、oneway 缓冲区和对象偏移都会占用空间，因此“低于 1 MiB 就安全”同样错误。

### 3. `TransactionTooLargeException` 是 Java 层启发式映射

Android 17 的 JNI 在收到 `FAILED_TRANSACTION` 时记录 Parcel 大小。只有允许抛出 `RemoteException` 且请求 Parcel 大于 200 KiB 时，它才把失败映射为 `TransactionTooLargeException`；较小 Parcel 的相同驱动返回会映射为 `DeadObjectException`，因为失败也可能来自远端死亡、无效对象或 buffer 空间耗尽。

这层异常映射有三条边界：

- `TransactionTooLargeException` 不等于驱动报告了一个精确的“超过 N 字节”原因；
- 失败可能发生在请求或回复，调用方不一定能区分；
- 全局 `UncaughtExceptionHandler` 不能恢复当时的 Binder 队列，更不能从 `MessageQueue` 取得 Parcel 大小。

对于自有 AIDL，应该在调用边界记录请求的可控大小、接口和结果，并捕获对应调用的 `RemoteException`。平台工程师还可以结合 `BINDER_GET_EXTENDED_ERROR`：Android 17 的 `IPCThreadState.logExtendedError()` 在驱动支持 `extended_error` 时读取扩展错误，其中 `ENOSPC` 会明确记录 Binder buffer 已满。

### 4. oneway 压力看 free async space 和驱动告警

`stats` 中的 `free async space` 是目标进程当前可用的异步事务空间。它应结合复现前后差值、pending work、oneway 调用频率和 `BR_ONEWAY_SPAM_SUSPECT` 日志分析。

这个值没有通用的 50% 或 80% 健康线。不同进程的并发模式不同，短暂下降也可能是正常突发；持续下降且消费速度跟不上，才说明需要限制生产速率、合并语义事件或减少 payload。

## 五、Parcel 序列化：以 Android 17 实现为准

### 1. Java Parcel 有对象池，但不会保留无限对象

Android 17 的 `Parcel.java` 维护 owned pool 和 holder pool，每个池的 `POOL_SIZE` 都是 32。`recycle()` 会先调用 `freeBuffer()`，再把 Java 包装对象放回相应池；它不会承诺为下一次调用保留任意大小的 native 数据区。

生成的 AIDL proxy/stub 已管理其创建的 Parcel。应用只应回收自己通过 `Parcel.obtain()` 获得的对象，不能在 `onTransact()` 或 Binder 回调中擅自回收框架传入的 Parcel。Android 17 还提供 `Parcel.obtain(IBinder)`，让 Parcel 与目标 Binder 的线格式关联，手写 Binder 代码应优先采用它。

没有源码或基准数据时，不应给对象池命中率写固定百分比。

### 2. Typed Parcelable 不通过反射写每个对象

`writeTypedObject()` 写入存在标记后，直接调用对象的 `writeToParcel()`。`writeParcelable()` 会额外写类名，再调用同一个方法；读取通用 Parcelable 时需要通过 class loader 查找 `CREATOR`。因此 typed API 的主要优势是省去类名和通用类型解析，不能概括为“每个元素都反射序列化”。

`Bundle` 适合可扩展的键值数据，但它携带 key、类型信息和逐项分派。高频、结构稳定的 AIDL 接口更适合字段明确的 structured Parcelable。具体收益必须用目标设备、真实字段分布和相同构建类型测量。

### 3. Native Parcel 按 1.5 倍扩容，最小容量为 128 字节

Android 17 的 `Parcel::growData()` 计算 `(mDataSize + len) * 3 / 2`，随后调用 `continueWrite()`，并保证新容量至少为 128 字节。它不是固定从 4 KiB 开始，也不是每次按 2 倍扩容。

Native 调用方已知大小时可以使用 `setDataCapacity()` 减少扩容。Java 公共 API 没有等价的容量设置接口；`appendFrom()` 会复制指定数据区，并非通用的预分配手段。

### 4. 大数据不会因使用 byte[] 自动转成共享内存

`Parcel.cpp` 的显式 `writeBlob()` 路径以 16 KiB 为 `BLOB_INPLACE_LIMIT`。FD 被允许且 blob 更大时，该函数使用 ashmem；普通 `writeByteArray()` 和 AIDL `byte[]` 不会因为超过 16 KiB 自动切换到这个路径。

反复传输大块数据时，应设计基于 `ParcelFileDescriptor`、`SharedMemory` 或专用共享缓冲区的协议，并通过 Binder 传递描述符、offset、length 和所有权信息。共享内存减少大块数据重复进入 Binder buffer，但仍有映射、缓存一致性、生命周期和同步成本，不能笼统称为“零拷贝”。

Scatter-gather Binder 事务从 Android 8 就已存在。Android 17 继续使用 `BC_TRANSACTION_SG` / `binder_transaction_data_sg`，它不是 Android 17 新增的应用层优化开关。

## 六、线程池健康度没有一张固定阈值表

libbinder 的默认最大线程数是 15，也可以在启动线程池前通过 `setThreadPoolMaxThreadCount()` 调整。进程可能使用 Java Binder、Native Binder、自建线程或不同厂商配置，`ps -T` 看到的线程数不能直接与 15 作危险等级比较。

判断线程池问题时，应检查：

1. 服务端开始延迟是否在问题窗口上升；
2. 是否有 ready Binder thread；
3. `proc->todo` 是否有待处理事务；
4. 现有 Binder 线程在运行、等锁、做 I/O，还是同步调用下游；
5. oneway 是否在同一 Binder node 上串行消费；
6. 增加并发是否会引入新的锁竞争和重入问题。

嵌套同步 Binder 调用会延长当前服务线程被占用的时间，但 Binder 也支持把嵌套回调路由回原调用线程。不能用“每嵌套一次必然多占一个线程”的模型推导线程数。

## 七、应用侧监控能做什么

普通应用无法读取全系统 Binder 事务，也不能从公开 API 取得驱动排队时间。对自有 AIDL，应在 client 边界记录单调时钟耗时，在 server 端为业务阶段增加 trace slice，并将两者用请求 id 关联。

下面的示例只测量调用方感知的同步耗时。它不能把排队、服务执行和回复调度自动分开。

```kotlin
inline fun <T> measuredBinderCall(
    interfaceName: String,
    methodName: String,
    call: () -> T,
): T {
    val startNs = SystemClock.elapsedRealtimeNanos()
    return try {
        call()
    } finally {
        val durationNs = SystemClock.elapsedRealtimeNanos() - startNs
        BinderMetrics.record(
            interfaceName = interfaceName,
            methodName = methodName,
            durationNs = durationNs,
        )
    }
}
```

线上采集需要控制基数和隐私：接口名、方法名、同步/oneway、结果类型和分桶后的时长通常足够；不要上报 Parcel 原文、账号、URI、文件描述符或用户内容。高频接口应采样，并在开启监控前后比较 CPU、分配量和丢事件情况。

固定的纳秒或微秒开销数字无法跨内核配置、trace buffer、CPU 和事件频率成立。Perfetto 的成本应在目标设备上以相同工作负载做有/无 trace 对照。

## 八、RecordedTransaction 的适用边界

`BBinder::startRecordingTransactions()` 只有在 libbinder 以 `BINDER_ENABLE_RECORDING` 构建时可用，并且 Android 17 源码要求调用方 UID 为 root。开启后，`BBinder` 会把接口名、transaction code、flags、状态、请求 Parcel 和回复 Parcel 写入文件描述符。

`RecordedTransaction.cpp` 明确标注文件格式仍在开发中。它还可能记录敏感业务数据，因此适合受控测试和协议复现，不适合作为常驻性能监控，也不能简单归纳为“userdebug 上默认可用”。是否编入目标产品必须检查构建配置。

## 九、推荐的排查流程

1. **定义问题窗口**：记录调用方、接口、同步或 oneway、卡顿或失败时间；
2. **录制最小 trace**：Binder transaction/received、sched；怀疑大小时加入 alloc buffer；
3. **定位 transaction**：先按 client/server、主线程和 `client_dur` 找到样本；
4. **解释两端时间**：比较 server start delay、server duration，并查询 client/server 线程状态；
5. **检查 payload**：关联 `binder_transaction_alloc_buf`，查看 300 KiB libbinder 警告和 Java 失败映射；
6. **检查目标进程快照**：ready thread、pending `proc->todo`、free async space 和失败日志；
7. **回到接口设计**：减少同步主线程调用，限制批量大小，为大数据改用共享缓冲区或 FD，给 oneway 增加背压；
8. **同负载复测**：报告分位数、调用频率、payload 分布和 trace 配置，不使用脱离样本的固定优化百分比。
