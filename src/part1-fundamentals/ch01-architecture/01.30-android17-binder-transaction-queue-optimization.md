# 1.30 Android 17 Binder 事务排队机制与高频 IPC 优化

## 1.30.1 源码中的三类待办队列

Binder 驱动把一次事务封装成 `binder_work`，再把它挂到不同的链表。理解这些链表，比笼统地说“Binder 有一个事务队列”更准确。

| 队列 | 归属 | 典型内容 | 谁消费 |
|---|---|---|---|
| `thread->todo` | 指定 Binder 线程 | 定向事务、reply、transaction complete、错误通知 | 指定线程 |
| `proc->todo` | 目标进程 | 尚未绑定到具体线程的进程级 work | 下一个可用 Binder 线程 |
| `node->async_todo` | Binder node | 同一 node 上等待前序事务完成的 oneway | 前一笔异步 buffer 释放后转入 `proc->todo` |

`binder.c` 顶部的 locking overview 明确写出：`proc->inner_lock` 保护 `proc->todo`、`thread->todo`、`node->async_todo`、线程列表和 transaction stack；`node->lock` 保护 node 的多数状态；`proc->outer_lock` 保护 Binder 引用。入队函数最终使用 `list_add_tail()`。

当前实现通过缩短临界区、遵守固定锁顺序，把工作交给合适线程。驱动 spinlock 的持有时间通常很短；应用看到的长 Binder 延迟更常来自目标线程忙、服务端业务执行、调度等待、嵌套调用或 buffer 压力。

## 1.30.2 一次同步事务怎样排队

Native libbinder 的发送路径可以简化为：

```text
BpBinder::transact()
  → IPCThreadState::transact()
  → writeTransactionData(BC_TRANSACTION)
  → talkWithDriver(BINDER_WRITE_READ)
  → binder_transaction()
  → binder_proc_transaction()
```

客户端把事务命令和 `binder_transaction_data` 写进 `IPCThreadState.mOut`。`talkWithDriver()` 组装 `binder_write_read`，通过 ioctl 把写缓冲交给驱动，并用 `mIn` 接收驱动返回命令。

驱动完成权限检查、对象转换和目标进程 buffer 分配后，选择接收位置：

1. 嵌套同步调用可能沿 transaction stack 回到正在等待的原调用线程，这能维持同步调用链并减少死锁风险。
2. 没有指定线程时，`binder_select_thread_ilocked()` 从 `proc->waiting_threads` 取第一个等待线程。
3. 当前没有等待线程时，事务挂到 `proc->todo`，由稍后进入驱动的线程领取；驱动也可能请求用户空间扩充 Binder 线程池。

线程选择函数的核心只有下面几行，用于核对它没有“按优先级或最近事务时间打分”：

```c
thread = list_first_entry_or_null(&proc->waiting_threads,
                                  struct binder_thread,
                                  waiting_thread_node);
if (thread)
    list_del_init(&thread->waiting_thread_node);
```

同步事务在服务端返回 `BC_REPLY` 前会阻塞客户端。驱动对受支持的调度策略执行同步优先级继承，并结合 Binder node 的最低优先级约束选择服务端执行优先级。等待时间仍包含服务端排队、调度和业务代码，不能只归因于驱动。

## 1.30.3 oneway：调用方早返回，服务端并不自动并行

AIDL 方法使用 `oneway` 后，远程调用不等待服务端 reply。若调用发生在同一进程，本地 Binder 直接调用仍是同步的，因此单进程测试无法验证远程 oneway 的异步行为。

对于远程 oneway，驱动在 node 上维护 `has_async_transaction`：

```c
if (oneway) {
    if (node->has_async_transaction)
        pending_async = true;
    else
        node->has_async_transaction = true;
}
```

第一笔 oneway 可以投给目标线程或 `proc->todo`。同一 node 后续到达的 oneway 被标为 `pending_async`，进入 `node->async_todo`，不会再唤醒另一线程并行执行。接收方处理完前一笔事务并释放 Binder buffer 时，`binder_free_buf()` 才把下一笔移到 `proc->todo` 并唤醒进程。

这个规则提供了单 node 的异步顺序，但也会形成队头阻塞：某个耗时 oneway 会拖住同一 Binder 对象后续的所有 oneway。增加发送线程或服务端线程都不能打破该 node 的串行约束。

调用方收到 `BR_TRANSACTION_COMPLETE`，表示驱动已经接收并排队该事务，不表示目标方法执行完成。oneway 无 reply，目标进程也可能在执行前死亡或冻结。需要可靠完成语义时，应设计显式回调、状态查询或使用同步方法，不能把“提交成功”当成“业务完成”。

## 1.30.4 oneway buffer 配额与 spam 检测

Binder buffer 属于接收进程，并由该进程所有在途事务共享。Android 17 libbinder 仍请求约 1 MiB、扣除两个页面的映射；r6 内核会把单进程映射上限限制在 4 MiB。对标准 libbinder 进程来说，用户空间请求值更小，因此有效容量仍接近 1 MiB。

`binder_alloc_mmap_handler()` 初始化时把一半容量记为 `free_async_space`。oneway buffer 会扣减这部分配额，释放时再归还。当前 kernel tag 的 spam 检测逻辑是：

- 剩余 async 空间低于总 buffer 的 10% 后，开始寻找主要发送者。
- 同一发送进程占有超过 50 个 async buffer，或占用超过总 buffer 的 25%，会被标记为疑似 oneway spam。
- libbinder 默认启用驱动的 oneway spam detection，收到 `BR_ONEWAY_SPAM_SUSPECT` 时记录调用栈。

这些阈值是 `android17-6.18-2026-06_r6` 的诊断实现，不是应用可依赖的流控协议。大量小型 oneway 事务仍会耗尽共享 buffer，使后来无关的事务失败。发送端需要自己做合并、去重、限频或背压。

## 1.30.5 `BINDER_WRITE_READ` 的“批量”边界

`IPCThreadState` 的 `mOut` 与 `mIn` 初始容量都是 256 字节。`writeTransactionData()` 会向 `mOut` 追加一条事务命令，缓冲中还可能带有待提交的引用计数或释放 buffer 命令；一次 `BINDER_WRITE_READ` 通过 `write_size/write_buffer` 提交当前内容，同一次 ioctl 也能从驱动读取多个 BR 命令。

这属于 Binder 协议命令缓冲，可减少 ioctl 次数。它没有改变每笔事务的 Parcel、目标 node、权限检查和完成语义，也不会在接收端执行下面这类操作：

- 自动把多笔 AIDL 调用合并成一笔。
- 创建固定 `batch_size` 后用 OpenMP 并行执行。
- 让同一 node 的 oneway 绕过顺序保证。
- 向 Java/Kotlin 应用暴露 `BinderTransactionBatch`。

业务需要批量时，应把批量定义进 AIDL 接口。例如，把一组独立小更新表达成一次有边界的请求：

```aidl
parcelable Update;

interface IUpdateService {
    void applyUpdates(in List<Update> updates);
    oneway void notifyInvalidation(in List<String> keys);
}
```

`applyUpdates()` 保留同步错误语义；`notifyInvalidation()` 只适合允许异步处理、允许单 node 顺序执行的通知。服务端仍要限制列表长度和单项大小，避免一次超大 Parcel 把“调用次数问题”变成 buffer 压力。

## 1.30.6 Binder 线程池怎样参与并发

目标进程可以用多个 Binder 线程并行处理不同 node 或同步事务。AIDL 服务实现必须线程安全，也要考虑同步回调引起的重入。

Android 17 `ProcessState.cpp` 中：

- `DEFAULT_MAX_BINDER_THREADS` 为 15。
- `startThreadPool()` 先启动主池线程。
- 驱动按需请求更多线程，直到配置上限。
- Native 服务可在启动线程池前调用 `setThreadPoolMaxThreadCount()`；线程池启动后不能缩小上限。

默认值不等于每个服务都应该使用 15 条活跃线程。增加上限只在“线程池饱和且服务端代码可安全并行”时可能有用，还会增加内存、调度竞争和共享锁压力。Java 应用进程的 Binder 池由平台管理，业务代码不应依赖私有接口调整它。

服务端方法执行较长任务时，可以把任务交给受控 executor，再尽快返回。但要先确定调用语义：

- 同步方法直接返回，意味着客户端认为工作已经完成；需要异步完成时应增加 callback、job ID 或状态查询。
- oneway 转交到无界线程池，只是把 Binder 队列换成应用队列，过载仍会积压。
- 多个 Binder 线程同时进入同一服务对象时，共享数据必须正确同步，不能依赖调用顺序。

## 1.30.7 高频 IPC 的有效优化顺序

### 先减少跨进程次数

把 getter 风格的逐字段查询改成一次快照，把逐项更新改成有上限的列表请求。批量边界应来自业务原子性和大小预算，不要使用固定“10–50 条”经验值。测量序列化后 Parcel 大小、服务端执行时间和失败率，再决定上限。

### 再选择同步或 oneway

需要结果、错误或自然背压时使用同步调用，并避免从主线程执行慢 IPC。通知类、幂等更新类请求才考虑 oneway；同时准备合并重复状态与限制发送速率。同一对象上的 oneway 串行，不能用于提高服务端并行度。

### 大数据传句柄，不传整块字节

图像、模型、长音频和大文件优先使用 `SharedMemory`、`ParcelFileDescriptor`、`AHardwareBuffer` 或领域已有的共享缓冲机制。Binder 适合传控制信息、元数据和句柄。接收进程约 1 MiB 的映射被所有在途事务共享，不能把它理解为“每个事务可稳定发送 1 MiB”。

### 缩短 Binder 线程占用

服务端在 Binder 线程上做权限检查、轻量参数验证和必要的短操作；阻塞 I/O、长计算与外部网络应使用有界工作队列。同步接口仍要在正确时机回复，异步接口要提供取消和过载策略。

### 避免嵌套同步调用链

A → B → C → A 这类同步 Binder 链会放大线程池占用和重入复杂度。能返回数据就一次返回，能通过状态快照解决就少做回调。遇到线程池 starvation 时，先找嵌套调用和服务端锁，再考虑线程数。

## 1.30.8 用 Perfetto 区分客户端等待与服务端执行

采集包含 Binder/AIDL 轨道的系统 trace 后，可使用 Perfetto 标准库 `android.binder`。下面的查询聚合主线程发起的同步事务：

```sql
INCLUDE PERFETTO MODULE android.binder;

SELECT client_process,
       server_process,
       COALESCE(aidl_name, method_name, interface, 'unknown') AS call_name,
       COUNT(*) AS call_count,
       SUM(client_dur) / 1000000.0 AS client_total_ms,
       AVG(client_dur) / 1000000.0 AS client_avg_ms,
       MAX(client_dur) / 1000000.0 AS client_max_ms,
       SUM(server_dur) / 1000000.0 AS server_total_ms
FROM android_binder_txns
WHERE is_sync = 1
  AND is_main_thread = 1
  AND client_dur > 0
GROUP BY client_process, server_process, call_name
ORDER BY client_total_ms DESC;
```

`client_dur` 是客户端墙钟等待区间，`server_dur` 是服务端 Binder 处理区间。两者差距大时，继续看目标线程何时被调度、是否先在 `proc->todo` 等待，以及客户端是否被其他工作延迟；服务端区间本身很长时，再展开 AIDL 方法内部的锁、I/O 和下游 Binder 调用。

oneway 的客户端 slice 主要反映提交，不代表服务端完成时间。分析异步积压时，应沿 Binder flow 找服务端接收 slice，观察同一接口的到达速率、执行时长和间隔；必要时结合 `binder_calls_stats`、服务端队列指标或 userdebug 设备上的 Binder 状态文件。不能拿 oneway 客户端耗时直接证明服务端吞吐提高。

## 1.30.9 根据 trace 特征定位

| 现象 | 更可能的原因 | 下一步 |
|---|---|---|
| 主线程同步 Binder slice 很长，服务端 slice 也长 | 服务端方法或下游调用慢 | 展开服务端 AIDL、锁、I/O 和嵌套 Binder |
| 客户端等待很长，服务端开始得晚 | 目标线程池忙或调度延迟 | 看目标 Binder 线程状态、`proc->todo` 迹象和 CPU runnable 延迟 |
| 同一 oneway 接口服务端严格排队 | 同一 Binder node 的异步串行 | 合并状态、缩短处理、拆分有独立顺序语义的对象 |
| `BR_ONEWAY_SPAM_SUSPECT` 或 transaction failure | async buffer 压力或共享 buffer 不足 | 限频、合并、减小 Parcel；大数据改传共享内存/FD |
| 增加线程后仍无吞吐提升 | 单 node oneway 串行、全局锁或硬件瓶颈 | 检查排队位置和临界区，不再盲目加线程 |
| Binder 调用很短但调用次数巨大 | 接口过碎，固定开销累积 | 用调用统计找高频方法，重新设计批量/快照接口 |

没有官方证据支持“Android 17 所有 Binder IPC 固定提升 45–50%”。Binder 性能取决于调用形状、目标进程负载、数据量、设备内核与调度状态。对比 Android 16/17 时，应在同一硬件、同一服务实现、同一频率与热状态下测量调用次数、分位数、CPU 时间和失败率。
