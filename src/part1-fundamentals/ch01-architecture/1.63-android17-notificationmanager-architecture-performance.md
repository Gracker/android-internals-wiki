# 1.63 Android 17 NotificationManager 架构与性能优化

NotificationManager 是 Android 通知体系的 SDK 入口。应用通过它发布、更新和取消通知；系统通过它执行权限校验、速率限制、排序和分发。本节聚焦 NotificationManager 的**架构边界与内部机制**，性能优化实战与 ANR 诊断详见 §8.14（推送通知管线延迟）和 §9.6（Notification 性能与 ANR）。

## NotificationManager 在系统架构中的位置

### SDK 客户端代理

`NotificationManager` 本身是一个运行在 App 进程中的轻量客户端。它不持有通知状态，所有操作都通过 Binder IPC 委托给 `system_server` 中的 `NotificationManagerService`（NMS）。

```
┌──────────────────────────────────────────────────────────┐
│  App Process                                               │
│  ┌──────────────────────────┐                             │
│  │  NotificationManager      │  ← SDK API                  │
│  │  NotificationChannel      │                             │
│  │  Notification.Builder     │                             │
│  └───────────┬──────────────┘                             │
│              │ Binder IPC (INotificationManager.aidl)      │
└──────────────┼─────────────────────────────────────────────┘
               │
               ▼
┌──────────────────────────────────────────────────────────┐
│  system_server                                             │
│  ┌──────────────────────────┐                             │
│  │  NotificationManager      │                             │
│  │       Service (NMS)       │                             │
│  │  ┌────────────────────┐  │                             │
│  │  │ NotificationRanker │  │  ← 排序与过滤                │
│  │  └────────────────────┘  │                             │
│  │  ┌────────────────────┐  │                             │
│  │  │ UsageStats         │  │  ← 包级速率统计              │
│  │  └────────────────────┘  │                             │
│  └───────────┬──────────────┘                             │
│              │ oneway Binder (INotificationListener)       │
└──────────────┼─────────────────────────────────────────────┘
               │
       ┌───────┴───────┐
       ▼               ▼
  SystemUI        其他 NLS 监听器
  (渲染通知)      (穿戴/助手/自动化)
```

[已验证: AOSP android-17.0.0_r1, frameworks/base/core/java/android/app/NotificationManager.java — 通过 `INotificationManager` AIDL 接口委托]

### 与其他系统服务的协作

NMS 不是孤立运行的。它需要与多个 `system_server` 内的兄弟服务交互：

| 协作服务 | 交互内容 |
|---------|---------|
| `ActivityManagerService` | 前台/后台状态判断、进程优先级、FGS 启动校验 |
| `PackageManagerService` | 通知渠道权限检查、包可见性过滤 |
| `UsageStatsManager` | 包级通知发布频率统计 (`getAppEnqueueRate`) |
| `AppOpsManager` | `OP_POST_NOTIFICATION` 权限校验 |
| `UiModeManager` | 驾驶模式通知过滤 |

NMS 的入口校验路径中，上述每一个协作点都可能引入 Binder 等待或锁竞争。排查通知发布延迟时，需要区分是 NMS 自身处理慢，还是被协作服务拖住。

## NotificationManagerService 架构剖析

### Binder 入口与任务派发

App 调用 `NotificationManager.notify()` 后，经过 `NotificationManager.notifyAsUser()` 进入 `INotificationManager.enqueueNotificationWithTag()`。这是**同步 Binder 调用**：调用线程会等待 NMS 入口返回，但不会等到通知渲染完成。

NMS 入口的核心设计是**快速入队、异步处理**：

```java
// frameworks/base/services/core/java/com/android/server/notification/
// NotificationManagerService.java (android-17.0.0_r1)
// 简化展示核心路径，非完整源码

public void enqueueNotificationWithTag(String pkg, String opPkg,
        String tag, int id, Notification notification, int userId) {
    // 1. 权限校验（PackageManager + AppOps）
    checkCallerIsSystemOrSameApp(pkg);
    // 2. Notification 对象校验
    fixNotification(notification);
    // 3. 创建 NotificationRecord
    NotificationRecord r = new NotificationRecord(getContext(), sbn, notification);
    // 4. post 到工作 Handler 异步处理
    mHandler.post(new EnqueueNotificationRunnable(userId, r, ...));
}
```

`EnqueueNotificationRunnable` 在 NMS 的工作线程上执行排序、限流检查、listener 分发等工作。这种设计确保 App 的调用线程不会因为 listener fan-out 或 SystemUI 渲染而阻塞。

[已验证: AOSP android-17.0.0_r1, frameworks/base/services/core/java/com/android/server/notification/NotificationManagerService.java — `mHandler.post(new EnqueueNotificationRunnable(...))` 模式]

### Handler 线程模型

NMS 使用一个专用的 `ServiceThread`（标记为 `NotificationManager`）作为工作线程。所有排序、分发、限流决策都在这个线程上串行执行。这意味着：

- 通知排序和 listener 分发是**串行的**——一条通知处理完才处理下一条
- 如果某条通知的 `rankerSort` 或 listener fan-out 耗时长，后续通知会排队
- 高频通知场景下，工作线程的队列深度是潜在瓶颈

在 Perfetto trace 中，NMS 工作线程表现为一段连续的 `EnqueueNotificationRunnable` / `rankerSort` slice。如果队列深度增加，可以看到 slice 之间的间隔缩短（背压）。

## 通知队列与排序机制

### NotificationRecord 数据模型

每条进入 NMS 的通知都会被包装成 `NotificationRecord`，它携带：

- `StatusBarNotification`（通知快照，包含包名、ID、tag、user）
- `Notification` 对象（完整内容、样式、Intent）
- `Importance` 级别（由渠道重要性和系统调整共同决定）
- 排序信号（isUpdate、isAutogroup、hasCompletedProgress 等）

`NotificationRecord` 是 NMS 内部的**唯一数据源**——所有后续判断（排序、限流、分发过滤）都基于这个对象。

### NotificationRankerService 排序管线

Android 17 的通知排序由 `NotificationRankerService` 负责。排序管线的核心步骤：

1. **拦截校验**（`checkDisqualifyingFeatures`）：速率限制、重复通知检测、包状态检查
2. **重要性评估**（`getImportance`）：根据渠道级别、用户调整、应用前台状态计算最终重要性
3. **排序信号提取**：提取排序关键字（重要性、时间戳、是否用户互动过）
4. **排名计算**（`rankerSort`）：对全局通知列表执行排序算法

排序完成后，NMS 生成 `RankingMap` 并分发给所有注册的 `NotificationListenerService`。

[已验证: AOSP android-17.0.0_r1, frameworks/base/services/core/java/com/android/server/notification/NotificationManagerService.java — `checkDisqualifyingFeatures` 包含速率限制逻辑]

### 包级速率限制

NMS 的速率限制是**包级别**的，不是渠道级。核心判断逻辑：

```java
// android-17.0.0_r1 简化展示
boolean isUpdate = isNotificationRecordExists(key);
if (isUpdate && !hasCompletedProgress() && !isAutogroup) {
    float rate = mUsageStats.getAppEnqueueRate(pkg);
    if (rate > mMaxPackageEnqueueRate) {
        return false;  // 丢弃该通知更新
    }
}
```

关键边界：
- **首次发布**（非 update）不受速率限制
- **已完成的进度更新**（`hasCompletedProgress()`）不受限制
- **自动分组摘要**（`isAutogroup`）不受限制
- 阈值 `DEFAULT_MAX_NOTIFICATION_ENQUEUE_RATE` 默认值为 `5f`（每秒 5 条 update）
- 被丢弃的通知**不抛异常、不回调通知 App**——静默 shed

[已验证: AOSP android-17.0.0_r1, NotificationManagerService.java — 速率限制条件判断路径]

## NotificationChannel 机制

### 渠道生命周期

`NotificationChannel` 是 Android 8.0 (API 26) 引入的通知分类机制，在 Android 17 中仍然是通知系统的核心组织单元。

渠道的生命周期状态机：

```
创建 → 活跃 → [用户修改重要性] → 活跃（已调整）
             → [用户删除渠道] → 已删除（不可重建）
```

关键设计约束：
- **渠道 ID 由 App 定义**，一旦创建即持久化在系统中
- **用户可以降低渠道重要性，但不能提升**（`IMPORTANCE_*` 不可向上覆盖）
- **删除渠道后重建同名渠道会恢复原设置**（系统保留已删除渠道的配置快照）
- **渠道路由是 NMS 入口校验的一部分**——发布通知时如果渠道不存在，NMS 会拒绝并降级为默认渠道

### 渠道与性能的交叉点

从架构角度看，渠道机制对通知发布性能有两层影响：

**第一层：渠道查询开销。** `createNotificationChannel()` 和首次 `notify()` 都涉及跨进程查询渠道是否存在。NMS 内部通过 `mNotificationChannelGroups` 缓存渠道信息，缓存命中时开销可忽略。但在应用冷启动时连续创建多个渠道，每次都是一次 Binder round-trip。

**第二层：渠道重要性影响系统调度。** 渠道的 `importance` 级别直接影响：
- 是否触发 heads-up 通知（`IMPORTANCE_HIGH`）
- 是否在锁屏可见
- 是否触发声音/振动
- NMS 的全局排序权重

`IMPORTANCE_HIGH` 触发的 heads-up 通知会额外占用 SystemUI 的 WindowManager 资源（窗口创建、动画、RenderThread），性能成本显著高于普通状态栏通知。

## 通知渲染管线：NMS → SystemUI

### 分发边界

NMS 处理完排序后，通过 `INotificationListener.onNotificationPosted()` 将通知变更异步分发给所有注册的监听器。SystemUI 是其中最重要的监听器。

关键架构边界：
- `INotificationListener` 是 **`oneway` interface**——NMS 调用后不等待监听器返回
- 监听器可以有多 个（SystemUI、穿戴设备服务、自动化工具），NMS 对所有监听器做 fan-out
- 监听器的处理速度**不影响**调用方 `notify()` 的同步返回时间

[已验证: AOSP android-17.0.0_r1, INotificationListener.aidl — `oneway interface`]

### SystemUI 侧的渲染链路

SystemUI 收到通知后，渲染链路为：

1. `NotificationEntryManager` 接收 `onNotificationPosted` 回调
2. `NotificationContentInflater` 执行 RemoteViews inflate 或 reapply
3. `ExpandableNotificationRow` 创建/更新视图
4. `NotificationStackScrollLayout` 执行 measure/layout
5. RenderThread 执行 `drawDisplayList`

inflate 和 reapply 的选择逻辑：
- 如果新旧通知的 `package` 和 `layoutId` 相同 → 走 `reapply`（跳过 inflate，只重新执行 action）
- 否则 → 走完整 `inflate`

通知渲染的详细性能分析与优化策略详见 **§8.14** 和 **§9.6**。

## RemoteViews 跨进程机制

RemoteViews 是通知 UI 内容的传输载体。它不传输 View 树实例，而是传输**一组序列化的 View 操作指令**（`ArrayList<Action> mActions`），由 SystemUI 在自己的进程中 inflate 并 apply。

```
App 进程                         SystemUI 进程
─────────                        ─────────────
Notification.Builder
  → 设置 contentView
    = RemoteViews(layoutId, actions)
      → Parcel 序列化              → Parcel 反序列化
                                  → inflateView(layoutId)
                                  → performApply(actions → view)
```

RemoteViews 的架构约束：
- 只能调用 `RemoteViews` 白名单 API（如 `setText`, `setImageViewBitmap`）
- 不支持自定义 View 的公开方法（安全限制——SystemUI 加载的是 App 的布局资源，但不执行 App 的代码）
- `Bitmap` 通过 `Bitmap.asShared()` 走共享内存传递（详见 §9.6 图片通知开销分析）

## PendingIntent 与通知点击响应

### PendingIntent 的创建开销

通知点击通过 `PendingIntent` 实现。`PendingIntent` 的本质是一个由系统持有的 `Intent` 触发凭证。

```java
PendingIntent contentIntent = PendingIntent.getActivity(
    context, requestCode, intent,
    PendingIntent.FLAG_IMMUTABLE | PendingIntent.FLAG_UPDATE_CURRENT);
```

性能要点：
- `PendingIntent.getActivity()` 是一次 Binder 调用到 `ActivityManagerService`
- `FLAG_IMMUTABLE`（Android 12+ 强制要求之一）比 `FLAG_MUTABLE` 更轻量——系统不需要创建可修改的 PendingIntent 代理
- 在通知更新场景中，`FLAG_UPDATE_CURRENT` 复用已有 PendingIntent slot，避免重复创建

### 点击响应延迟链路

用户点击通知后的响应链路：

1. SystemUI 收到点击事件 → 通过 `PendingIntent.send()` 触发
2. AMS 收到 Intent → 检查目标 Activity 的进程状态
3. 如果目标进程不存在 → 冷启动（延迟 1-5 秒）
4. 如果目标进程存在但冻结 → 解冻（延迟 100-500ms，详见 §4.11）
5. 目标 Activity 进入 `onCreate()` / `onNewIntent()`

从用户感知角度，通知点击到 Activity 可见的延迟主要取决于进程状态。优化策略与启动优化（§8.1-§8.5）一致。

## 通知分组（Group）机制

### 手动分组与自动分组

Android 支持两种通知分组方式：

**手动分组**：App 使用 `Notification.Builder.setGroup(key)` 和 `setGroupSummary(true)` 主动创建分组摘要通知。

**自动分组（Autogroup）**：当 App 发布多条通知但没有设置 group 时，NMS 自动将它们归为一组，生成摘要通知。Autogroup 摘要在 NMS 内部生成，不走 App 的发布路径，因此**不受速率限制**（`isAutogroup` 为 true 时跳过 rate check）。

### 分组的性能收益

分组对系统性能的收益在通知密集场景下最明显：

- 减少 SystemUI 同时渲染的 `ExpandableNotificationRow` 数量
- 折叠状态下只渲染摘要通知，子通知延迟到展开时才 inflate
- NMS 可以批量处理同组通知的 ranking 更新

消息类 App 在群聊消息爆发场景下，不使用分组会导致通知栏瞬间出现几十条通知，SystemUI 的 inflate + measure + layout 开销急剧上升。推荐使用 `MessagingStyle` + `setGroup()` 的组合。

## 通知权限管理

### POST_NOTIFICATIONS 运行时权限

Android 13 (API 33) 起，`POST_NOTIFICATIONS` 成为运行时权限。NMS 在入口校验阶段通过 `AppOpsManager.checkOpNoThrow(OP_POST_NOTIFICATION)` 检查权限状态。

权限被拒绝时的行为：
- `notify()` **不抛异常**，静默返回
- 通知不会进入 NMS 处理管线
- App 可以通过 `NotificationManager.areNotificationsEnabled()` 提前检查权限状态

[已验证: 官方文档, developer.android.com/about/versions/13/changes/notification-permission]

### 渠道级可见性控制

除了运行时权限，用户可以在系统设置中：
- 关闭整个 App 的通知
- 关闭特定渠道的通知
- 降低渠道重要性

这些调整持久化在 NMS 的渠道配置存储中。App 通过 `NotificationManager.getNotificationChannel(channelId)` 可以查询当前渠道状态（包括用户是否修改了重要性），但无法覆盖用户的下调。

## 通知计数与 Badge 更新

### StatusBarIconController

通知发布后，SystemUI 的 `StatusBarIconController` 负责更新状态栏的通知图标。在 Android 17 中，状态栏图标显示策略有以下约束：

- 每个包在状态栏最多显示一个图标（同包多条通知折叠为一个图标）
- `IMPORTANCE_LOW` 和 `IMPORTANCE_MIN` 的通知不显示状态栏图标
- 通知图标使用 `Notification.smallIcon`，不是 `largeIcon`

状态栏图标更新的开销很小（一次 `ImageView.setImageDrawable()` + `invalidate()`），但高频通知更新场景下会触发频繁的 `onNotificationPosted` 回调，间接增加 SystemUI 主线程负载。

### Launcher Badge（通知圆点）

Launcher 的通知圆点（notification dot / badge）通过 `NotificationListenerService` 实现。Launcher 进程注册为通知监听器，接收通知变化后更新图标角标。

这意味着每次通知变化，NMS 都会额外通知 Launcher 进程。在通知密集场景下，Launcher 进程的 NLS 回调也可能成为性能瓶颈（参见 §9.6 中 NLS 回调线程模型的讨论）。

## Perfetto 观测要点

### NMS 工作线程监控

NMS 的排序和分发工作在 `NotificationManager` 服务线程上执行。Perfetto 中关注以下信号：

| 观测对象 | Track | 关键信号 |
|---------|-------|---------|
| App 调用线程 | App 主线程 | `notify` trace section, Binder wait |
| NMS 入口 | system_server | `enqueueNotificationWithTag`, Binder dispatch |
| NMS 工作线程 | NotificationManager 线程 | `EnqueueNotificationRunnable`, `rankerSort` |
| SystemUI 渲染 | SystemUI 主线程 + RenderThread | `inflate`, `onMeasure`, `onLayout`, `drawDisplayList` |

### 关键 Perfetto SQL 查询

定位通知从发布到渲染的端到端延迟：

```sql
-- 通知发布到 SystemUI 渲染的延迟分解
WITH notify_call AS (
  SELECT slice.ts AS start_ts, slice.ts + slice.dur AS end_ts
  FROM slice
  JOIN thread_track ON slice.track_id = thread_track.id
  JOIN thread ON thread_track.utid = thread.utid
  JOIN process ON thread.upid = process.upid
  WHERE slice.name = 'notif.notify'  -- App 侧自定义 trace section
    AND process.name = 'your.package'
  ORDER BY slice.ts DESC LIMIT 1
)
SELECT
  'NMS enqueue to render' AS stage,
  (render.ts - notify.end_ts) / 1e6 AS latency_ms
FROM notify_call, slice AS render
JOIN thread_track ON render.track_id = thread_track.id
JOIN thread ON thread_track.utid = thread.utid
WHERE thread.name LIKE '%systemui%'
  AND render.name LIKE 'inflate%'
  AND render.ts > notify.end_ts
ORDER BY render.ts LIMIT 1;
```

通知 ANR 和性能问题的深度 Perfetto 诊断方法详见 **§9.6**（包含 thread_state 分析、Binder 等待定位、dumpsys notification 辅助诊断）。

## Android 17 通知架构变更

### Notification.MetricStyle

Android 17 (API 37) 新增 `Notification.MetricStyle` 通知模板，面向健康/健身、计时器、出行等场景。允许在 AOD（Always-On Display）、锁屏、状态栏同时展示最多三个数据指标。

相关类：
- `Notification.MetricStyle` — 样式定义
- `Notification.Metric` — 指标容器
- `Notification.Metric.MetricValue` — 单个指标值（名称、单位、数值）

从架构角度，`MetricStyle` 与 Android 16 的 `ProgressStyle` 一样走**系统模板渲染路径**，减少自定义 RemoteViews 的需求。App 只提供数据，渲染由系统模板负责。

### Live Update 与 Semantic Coloring API

Android 17 的 Live Update 扩展支持 `MetricStyle`（Android 16 仅支持 `ProgressStyle`）。新增 **Semantic Coloring API**，用语义化颜色（绿/红/蓝）标记积极/消极/中性内容。

Semantic Coloring 的架构意义：
- 系统根据语义自动选择展示颜色，App 不需要自定义 RemoteViews 仅为了改颜色
- 颜色映射由 SystemUI 的通知模板引擎负责，不走 App 的 Resource 加载路径
- 与 AOD/锁屏的颜色策略联动（如 AOD 模式下降低色彩饱和度）

[已验证: 官方文档, developer.android.com/about/versions/17 — MetricStyle 与 Live Update 扩展]

### 版本演进汇总

| 版本 | 架构变更 | 性能影响 |
|------|---------|---------|
| Android 13 (API 33) | `POST_NOTIFICATIONS` 运行时权限 | NMS 入口增加 AppOps 检查；权限被拒的通知不入队 |
| Android 14 (API 34) | FGS 类型声明强制化 | FCM 回调中启动 FGS 需声明类型 |
| Android 15 (API 35) | FGS 超时机制 | 由通知触发的 FGS 受配额限制 |
| Android 16 (API 36) | `Notification.ProgressStyle`；promoted ongoing / Live Update | 进度通知走系统模板；减少自定义 RemoteViews |
| Android 17 (API 37) | `Notification.MetricStyle`；Semantic Coloring API | 指标通知走系统模板；语义颜色减少自定义渲染 |

## 与其他系统服务的关系

- **§1.44 Binder IPC 优先级继承**：通知发布的所有跨进程调用都走 Binder，NMS 的 Binder 线程模型与优先级继承机制影响通知入口延迟
- **§1.64 BiometricService**：与 NotificationManager 类似，都是 `system_server` 内的核心系统服务，共享 Binder 线程池资源
- **§8.14 推送通知管线性能**：FCM 投递延迟与 NMS 入队处理的端到端性能分析
- **§9.6 Notification 性能与 ANR**：NMS 内部机制、RemoteViews 开销、NLS 回调性能、通知 ANR 诊断
- **§4.11 Cached App Freezer**：缓存冻结影响 FCM 消息投递和 PendingIntent 触发延迟
- **§1.68 ActivityManagerService**：NMS 的前台/后台状态判断依赖 AMS
