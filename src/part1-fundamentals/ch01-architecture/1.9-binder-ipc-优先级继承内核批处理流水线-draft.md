## 一、Binder 路径由哪些组件组成

一笔 AIDL 调用通常经过四层：

1. 生成的 Proxy/Stub 负责接口 code、参数编码和方法分发；
2. libbinder 的 `Parcel` 与 `IPCThreadState` 组织用户态命令；
3. Binder 驱动完成对象引用转换、目标 buffer 分配、排队、线程唤醒和回复匹配；
4. 目标进程的 Binder worker 执行 Stub 与服务实现。

`servicemanager` 负责服务注册与查询。它不是替所有进程执行事务的“Binder 守护进程”。`system_server` 也只有自己的 Binder 线程池；应用、native daemon 和 HAL 各自在所属进程处理到达的事务。

Native libbinder 的默认 `mMaxThreads` 是 15，表示驱动可按需请求的 lazy worker 上限；`startThreadPool()` 还会主动创建 main pool thread。显式 join、polling、`system_server` 的 31 上限和厂商配置都会改变可见线程数，不能把全平台概括成固定 16 条线程。线程创建细节见 [1.54 Binder 线程池实现机制](1.54-binder-thread-pool-implementation/1.54-binder-thread-pool-implementation.md)。

## 二、`BINDER_WRITE_READ` 怎样传递命令

每个 native Binder 线程持有 `mOut` 和 `mIn` 两个 Parcel。`mOut` 写入 `BC_TRANSACTION`、`BC_REPLY`、引用计数和 looper 命令；`mIn` 接收 `BR_TRANSACTION`、`BR_REPLY`、完成通知与错误。两个 Parcel 的初始容量都是 256 字节，容量可以增长。

下面的内核代码展示同一次 ioctl 的处理顺序：

```c
if (bwr.write_size > 0) {
    ret = binder_thread_write(proc, thread, bwr.write_buffer,
                              bwr.write_size, &bwr.write_consumed);
}
if (bwr.read_size > 0) {
    ret = binder_thread_read(proc, thread, bwr.read_buffer,
                             bwr.read_size, &bwr.read_consumed,
                             filp->f_flags & O_NONBLOCK);
}
```

驱动先消费 write buffer，再填充 read buffer。每个 buffer 可容纳多条变长命令，已消费字节数通过 `write_consumed` 和 `read_consumed` 返回。命令聚合减少的是 ioctl 边界，不会把多笔 transaction 变成一个共享成败结果。

### ioctl 次数没有固定答案

同步调用由 `waitForResponse()` 循环驱动，直到收到 `BR_REPLY`、`BR_DEAD_REPLY`、`BR_FAILED_REPLY` 或其他终止结果。循环中也可能处理 `BR_TRANSACTION_COMPLETE`、引用计数命令和嵌套 transaction。

服务端执行时间、信号中断、输入缓冲区剩余命令、嵌套调用与回复到达时机都会改变 ioctl 次数。`flushCommands()` 最多主动调用两次 `talkWithDriver(false)`，第二次只用于冲刷第一次 post-write 引用计数处理产生的 `BC_RELEASE`/`BC_DECREFS`；这不是每笔业务调用固定“两次 syscall”的规则。

## 三、不存在固定的 Binder batch 阈值

Android 17 AOSP 没有下面这些通用参数：

| 旧说法 | 源码结论 |
|---|---|
| transaction 小于 4 KiB 才能 batch | 命令是否同处 `mOut` 由用户态调用时序决定，没有 4 KiB 门槛 |
| 连续三笔、间隔小于 16 ms 触发 | 驱动没有对应计数器或时间窗口 |
| 一批最多 16 笔、总计 64 KiB | read/write 按字节容量与命令种类推进，没有这两个常量 |
| `mBatchQueue`、`flushBatch()` | `ProcessState`/`IPCThreadState` 没有这些成员和方法 |
| 内核为 batch 改成一把新自旋锁 | Binder 已长期按不同对象使用多把锁，不能由虚构 batch 推出锁替换 |

read buffer 能返回多少条 `BR_*` 命令，取决于容量、命令长度、todo 内容以及是否需要等待。简单命令只有命令字，transaction 还包含 `binder_transaction_data`；把 256 字节直接除成“约 128 条”没有意义。

## 四、命令 Parcel 与 transaction buffer 是两类内存

`mIn`、`mOut` 保存用户态驱动命令。目标进程的 transaction buffer 由 `binder_alloc` 管理，存放请求/回复数据、对象偏移和 scatter-gather 额外区。两者的容量不能互换。

Android 17 libbinder 请求映射 `1 MiB - 2 × page size`，内核把任何进程的映射上限限制为 4 MiB。常规 libbinder 进程因用户态请求较小，生效容量接近前一个值。该空间由目标进程所有未释放 transaction 共享，还会受到碎片影响；异步 transaction 另有初始为映射一半的预算。

因此，没有适用于所有进程的“单笔控制在 0.5 MiB 就安全”规则。一笔较小请求也可能在目标空间接近耗尽或碎片严重时失败。native `waitForResponse()` 把 `BR_FAILED_REPLY` 映射为 `FAILED_TRANSACTION`；Java 层看到的 `TransactionTooLargeException` 也不能告诉你一定是请求、回复还是其他并发 transaction 占满空间。

大数据应通过 `SharedMemory`、文件描述符或面向媒体/硬件的专用共享缓冲协议传递。Binder 不会自动把 Parcel 数据放进 BufferPool；Zygote 预加载也不会减少某个接口的 Binder 调用次数。

## 五、同步与 oneway 的排队差异

同步 transaction 需要服务端 reply，调用线程在 `waitForResponse()` 中等待。等待线程可能是 UI 线程、普通业务线程或正在处理另一笔请求的 Binder worker；只有第三种会继续占用调用方进程的 Binder 服务能力。

oneway 让发送方在驱动接收 transaction 后返回，不等待业务执行或 reply。服务端仍要用 Binder worker 执行方法，而且同一个 Binder node 的 async transaction 会串行：一个 active transaction 处理期间，后续请求进入该 node 的 `async_todo`。不同 node 才有机会并行。

把同步接口改成 oneway 只能改变等待语义。生产速度持续高于消费速度时，队列、async buffer 和服务端 CPU 压力仍会增长。限频、状态合并、有界队列及丢弃策略见 [1.25 Binder 异步流水线](01.25-binder-ipc-async-pipeline.md)。

## 六、同步事务怎样继承优先级

驱动创建 transaction 时，使用下面的分支选择初始候选值：

```c
if (!(t->flags & TF_ONE_WAY) &&
    binder_supported_policy(current->policy)) {
    t->priority.sched_policy = current->policy;
    t->priority.prio = current->prio;
} else {
    t->priority = target_proc->default_priority;
}
```

受支持 policy 的同步调用以发送线程为候选；oneway 或不受支持的 policy 使用目标进程默认值。这个值随后还要与目标 Binder node 的配置合并。

`binder_transaction_priority()` 按以下边界收敛：

- node 未设置 `FLAT_BINDER_FLAG_INHERIT_RT` 时，RT 候选降为 `SCHED_NORMAL`、nice 0；
- node 的 `min_priority` 表示最低保障，数值更小、调度优先级更高时采用 node 值；
- 缺少 `CAP_SYS_NICE` 时，RT 与 nice 调整仍受 `RLIMIT_RTPRIO`、`RLIMIT_NICE` 限制；
- 已经具有相同 policy/prio 时，统一设置函数可直接返回，不必调用 scheduler 设置路径。

`set_priority_called` 属于单个 `binder_transaction`，只防止该对象重复应用优先级。嵌套同步调用会创建新的 transaction，各自保存 `saved_priority`。

### 三态机处理恢复竞态

接收线程的 `prio_state` 使用 `BINDER_PRIO_SET`、`BINDER_PRIO_PENDING` 和 `BINDER_PRIO_ABORT`。回复路径准备恢复旧值时进入 PENDING；若新 transaction 在恢复完成前选中同一线程，新事务保存待恢复值并改成 ABORT，旧恢复便不会覆盖新优先级。

这组状态没有 `IDLE`，也不是业务调用状态机。更完整的竞态时序见 [1.44 Binder IPC 优先级继承](1.44-binder-ipc-priority-inheritance.md)。

## 七、等待线程选择接近 LIFO

空闲 worker 在 `binder_wait_for_work()` 中通过 `list_add()` 插入 `waiting_threads` 链表头；`binder_select_thread_ilocked()` 用 `list_first_entry_or_null()` 从头取出。两步组合后，较晚进入等待的线程较早被选择。

选择过程不按 nice、RT priority、CPU 使用或历史服务时长排序。事务交给线程后，优先级继承决定本次期望 policy/prio；线程何时运行继续由调度器、cpuset、uclamp 与系统负载决定。

## 八、`TF_UPDATE_TXN` 的窄边界

`TF_UPDATE_TXN` 只在目标进程 frozen、同一 Binder node 已有 pending async transaction 时尝试替换旧请求。新旧事务都要带 `TF_ONE_WAY | TF_UPDATE_TXN`，并匹配目标进程、code、完整 flags、发送进程以及目标 node 的 ptr/cookie。

替换发生在新 transaction 已完成 buffer 分配之后。它不会为同步 transaction 合并请求，也不负责从 buffer 分配失败中恢复。这个机制适合可覆盖的状态更新，调用方仍要保证丢弃旧值不会破坏业务语义。

## 九、Perfetto 中怎样读延迟

Android 17 Perfetto stdlib 的 `android_binder_txns` 同时覆盖 sync 与 async transaction。下面的查询用于列出某个服务最慢的同步调用：

```sql
INCLUDE PERFETTO MODULE android.binder;

SELECT
  client_process,
  client_thread,
  server_process,
  server_thread,
  aidl_name,
  client_dur / 1e6 AS client_ms,
  server_dur / 1e6 AS server_ms
FROM android_binder_txns
WHERE is_sync = 1
  AND server_process = 'system_server'
ORDER BY client_dur DESC
LIMIT 50;
```

`client_dur` 是调用方 transaction slice 的 wall duration，`server_dur` 是服务端 reply slice 的 wall duration。两者之差混有驱动排队、线程唤醒、调度和 trace 边界开销，不能直接命名为 `dispatch_dur`。`android_binder_txns` 也没有原文使用的标准 `dispatch_dur` 列。

拿到慢调用后，再对齐 server thread 的 Running/Runnable/锁等待/I/O 区间、同进程其他 Binder worker、下游 transaction 和 CPU 负载。客户端停在 `ioctl(BINDER_WRITE_READ)` 只说明它正在与驱动交互或等待结果，不能单独证明目标线程池已经耗尽。

## 十、调优顺序

可以先用下面的只读命令收集目标进程线程和 Binder 方法统计：

```bash
adb shell ps -T -p "$(adb shell pidof -s com.example.app)"
adb shell dumpsys binder_calls_stats
adb logcat -b all -s libbinder.IPCThreadState:E
```

线程快照、方法统计和 100 ms libbinder 饥饿日志提供不同证据。它们都需要与 Perfetto 时间窗对齐。

修复时按调用链处理：

1. 缩短服务端持锁、I/O、数据库和下游同步 IPC；
2. 禁止持锁跨进程调用，检查嵌套回调重入；
3. 让大数据离开 Parcel，控制 outstanding transaction 数量；
4. 对 oneway 生产端限频并合并可覆盖状态；
5. 只有工作彼此独立、下游资源有余量且 trace 证明缺少 worker 时，再试验提高线程上限；
6. 用同一 workload 比较 client/server duration、CPU、内存、page fault 和 P95/P99。

线程池从 4 调到 32 不是通用配置模板。更多 worker 可能增加锁竞争、调度开销和内存，也可能让更多调用同时堵在同一数据库或设备队列。
