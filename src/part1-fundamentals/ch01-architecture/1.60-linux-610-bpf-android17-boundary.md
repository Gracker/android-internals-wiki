# 1.60 Linux 6.10 BPF 集成对 Android 17 内核可观测性的影响边界

## 概述

Linux 6.10 内核在 BPF 子系统上引入了多项重要增强——struct_ops 扩展、kfunc 多版本机制、BPF Arena、以及 BPF iterators 的改进。然而，Android 17（`android-17.0.0_r1`）的 GKI（General Kernel Image）内核主线基于 Linux 5.15 / 6.1 / 6.6，最新的 ACK（Android Common Kernel）分支延伸到 6.12。这意味着 Linux 6.10 mainline 的 BPF feature 中，只有被 ACK backport 的子集才能在 Android 17 设备上实际使用。

本节的定位是**影响边界分析**：厘清 Linux 6.10 BPF 增强中哪些已进入 Android 17 GKI、哪些仅存在于 mainline 而未进入产品设备，以及这些新增能力与 AIW 已有 eBPF 章节（§2.6、§14.25）的关系。

[适用版本: Android 17 (API 37), GKI 内核 5.15/6.1/6.6/6.12]

---

## 🔹 1. Android 17 内核版本基线与 BPF 子系统现状

### GKI 内核版本矩阵

Android 17 设备的 GKI 内核遵循 ACK（Android Common Kernel）分支策略：

| GKI 版本 | 对应 Mainline | Android 版本范围 | BPF 状态 |
|-----------|--------------|-----------------|----------|
| 5.15-lts | Linux 5.15 | Android 13-17 | 基础 eBPF（tracepoint + kprobe + map） |
| 6.1-lts | Linux 6.1 | Android 14-17 | sched_ext 实验性、BPF iterators 增强 |
| 6.6-lts | Linux 6.6 | Android 15-17 | struct_ops 初步、kfunc 扩展 |
| 6.12-lts | Linux 6.12 | Android 17（新设备） | 最接近 mainline 6.10+ 的 BPF 能力 |

> Android 17 新设备的 GKI 推荐版本为 **6.6-lts 或 6.12-lts**。5.15 和 6.1 仅用于旧设备升级。 [来源: source.android.com GKI 文档]

### Android 17 中已确认的 BPF 程序

在 `android-17.0.0_r1` 的 `system/bpf/progs/` 目录下，已固化以下 eBPF 程序（详见 §2.6 的深度分析）：

- **cyclePerUid** — 按 UID 统计 CPU 物理周期（sched_switch tracepoint）
- **dmabufIter** — DMA-BUF 显存生命周期追踪（BPF Iterator）
- **kernelWakelockDuration** — 内核唤醒锁累计持续时间（raw tracepoints）
- **locks** — 内核锁竞争延迟分析（contention_begin/end tracepoints）

这四个程序是 Android 17 eBPF 可观测性的**已落地基线**。Linux 6.10 mainline 的 BPF 增强属于**上游能力扩展**，其中部分 feature 可能通过 ACK backport 进入 6.12-lts GKI。

[已验证: AOSP android-17.0.0_r1, system/bpf/progs/ — 程序列表与 §2.6 一致]

### Linux 6.10 BPF 子系统的主要增强

以下是 Linux 6.10 mainline 中与 Android 可观测性相关的 BPF 增强概览：

1. **BPF Arena**：一种新的 map 类型，支持用户态与 BPF 程序之间的 zero-copy 共享内存区域，使用户态可以直接读取 BPF 程序写入的复杂数据结构，无需 `bpf_map_lookup_elem` 系统调用
2. **kfunc 多版本支持**：允许同一 kfunc 有多个版本，BPF 程序在加载时选择兼容版本，改善跨内核版本的可移植性
3. **struct_ops 扩展**：BPF 程序可以通过 struct_ops 机制注册为内核子系统（如 TCP拥塞控制、调度器）的实现，扩展了 BPF 从"观测"走向"控制"的能力边界
4. **BPF iterators 增强**：支持更灵活的内核数据结构遍历，减少用户态消费器的复杂度

> 这些 feature 在 Android 17 GKI 中的可用性**因内核版本而异**。6.12-lts GKI 可能包含部分 backport，但绝非全部。6.6-lts 及以下大概率不包含 6.10 的 BPF 增强。

[来源: Linux 6.10 changelog / BPF 子系统邮件列表 — mainline 特性，未逐一验证 ACK backport 状态]

## 🔹 3. 内存管理观测点（与 §4.50 LMKD v2 + PSI 呼应）

### 现有内存观测的 BPF 基线

Android 17 已落地的内存相关 BPF 观测能力：

- **dmabufIter**（§2.6）：DMA-BUF 显存生命周期追踪，BPF Iterator 单次 read 获取全量统计
- **Perfetto system_probes**：通过 ftrace/poll 读取 `/proc/pressure/memory`（PSI）数据
- **ion/system heap 监控**：通过 `/proc/ion_heaps` 等接口（非 BPF 路径）

### Linux 6.10 的内存管理 BPF 增强方向

Linux 6.10 mainline 中，BPF 在内存管理子系统的增强主要体现在以下方向：

**方向 1：cgroup 级内存事件观测**

mainline 6.10 引入了更丰富的 cgroup memory event hook，允许 BPF 程序在 per-cgroup 的内存压力路径上插入低开销探针。这与 Android 17 LMKD v2（§4.50）的 PSI 分层压力治理形成互补：

- LMKD v2 基于 PSI 接口（`/proc/pressure/memory`）做**反应式**杀进程决策
- BPF cgroup memory probes 可以做**前摄式**的压力趋势观测——在 PSI 触发 stall 之前，BPF 就能捕获到 alloc/reclaim 路径上的异常模式

> 注意：这种"前摄式观测"在 Android 17 GKI 上的可用性 **[待验证]**。ACK 是否 backport 了 6.10 的 cgroup memory BPF hooks 尚无公开确认。

**方向 2：BPF Arena 与 zero-copy 内存数据共享**

BPF Arena（Linux 6.10 新增）允许 BPF 程序将复杂数据结构直接映射到用户态地址空间。在内存观测场景中：

- 传统方式：BPF 程序写 Map → 用户态 `bpf_map_lookup_elem` 逐条读取 → 序列化/反序列化开销
- Arena 方式：BPF 程序直接写入 Arena 共享区域 → 用户态指针直接访问，零拷贝

对于高频内存事件（如 page fault 统计、slab 分配追踪），Arena 可以显著降低用户态消费器的 CPU 开销。

> BPF Arena 在 Android 17 GKI 6.12-lts 上的可用性 **[待验证]**。Arena 依赖内核 mm 子系统的地址空间管理改动，backport 难度较高。

**方向 3：memory cgroup 遍历 BPF iterator**

mainline 中讨论了 `bpf_memcg_foreach` 类接口，允许 BPF 程序遍历指定 cgroup 子树的所有内存统计。在 Android 场景中，每个应用进程通常有独立的 cgroup，这种遍历能力可以实现：

- 一次性获取整个应用组的内存占用快照
- 对比 fork 前后的 cgroup 内存变化（与 §1.59 ML 调度器的进程创建决策协同）

> 此接口在 mainline 中仍在讨论阶段，Android 17 中 **[待验证]** 不可用。

### 对 "内存占用减少 40%" 数据点的审慎评估

daily-info 2026-07-16 RSS 摘要中提到"Linux 6.10 的 BPF 深度集成实现……内存占用减少 40%"。

**[待验证]** 该数据点未给出测量条件、基线对照、测试设备信息。审慎评估如下：

- "减少 40%" 可能指特定 workload（如服务器场景的 cgroup 内存配额优化）下的峰值占用降低，而非通用场景
- Android 设备的内存管理与服务器场景差异巨大（LMKD 主动杀进程、zRAM 压缩、App Lifecycle 管理），同一 BPF feature 的实际收益不可直接套用
- AIW 主线结论必须基于 `android-17.0.0_r1` 的实际代码和文档，该数据点仅作为"上游方向参考"标注

## 🔹 4. 调度观测点（与 §5.32 BPF DVFS + EEVDF 呼应）

### 现有调度观测的 BPF 基线

Android 17 已落地的调度相关 BPF 观测：

- **cyclePerUid**（§2.6）：通过 sched_switch tracepoint 按 UID 统计 CPU 物理周期，间接反映调度结果
- **Perfetto sched slice**：通过 ftrace 的 sched_switch 事件生成调度时间片轨迹
- **lock contention**（§2.6 locks 程序）：mmap_lock 等动态锁的竞争延迟可间接影响调度延迟

### Linux 6.10 的调度 BPF 增强方向

**方向 1：runqueue 观测 hook**

mainline 中讨论的 `bpf_runqueue_hook` 系列接口，允许 BPF 程序在调度器 runqueue 的关键路径（enqueue/dequeue/task_migration）上插入观测探针。与 Android 17 的调度子系统关系：

- **与 PELT（§5.28）的关系**：BPF runqueue hook 可观测 PELT 信号的实际衰减过程和 load_avg 计算，但**不修改**PELT 算法本身
- **与 EEVDF（§5.31）的关系**：BPF 可观测 EEVDF 的 deadline 计算和 vruntime 排序，但调度决策仍由内核 EEVDF 逻辑决定
- **与 ML 调度器（§1.59）的关系**：ML 调度器影响进程优先级（`oom_score_adj`、`sched_priority`），BPF 可观测优先级变化对 runqueue 排序的影响

> 这些 runqueue hook 在 Android 17 GKI 上的可用性 **[待验证]**。sched_ext（BPF 可编程调度器）在 Linux 6.18 中默认启用，但在 Android 17 中仍处于实验阶段。

**方向 2：BPF 与 sched_ext 的关系**

sched_ext 是 Linux 内核中允许通过 BPF 程序实现自定义调度器类（scheduling class）的机制。其与可观测性的关系：

- sched_ext 本身是**控制面**能力（用 BPF 写调度策略），不只是**观测面**
- 在 Android 17 中，sched_ext **不是默认启用的调度器**——设备仍使用 EEVDF（CFS 的演进）
- sched_ext 的存在使得"用 BPF 做调度实验"成为可能，但产品设备上的调度行为以内核内置调度器为准

> 对 sched_ext 的深入分析参见 §17.4（如已覆盖）。本节仅涉及 sched_ext 与可观测性的边界。

**方向 3：cpufreq/schedutil 观测**

§5.32 节覆盖了 BPF 在 DVFS/schedutil 调频闭环中的应用边界。本节补充可观测性视角：

- mainline 中讨论的 `bpf_cpufreq_hook` 可以在 cpufreq driver 的频率切换路径上插入探针
- 这允许观测 schedutil governor 发出频率请求 → driver 实际执行频率切换 → 硬件响应的完整延迟链
- 在 Android 17 上，此类 hook 的可用性取决于 SoC 厂商的 cpufreq driver 是否暴露了对应的 tracepoint

> **[待验证]** 厂商 cpufreq driver（高通 `qcom-cpufreq-hw`、联发科 `mtk-cpufreq-hw`）是否提供了 BPF 可挂载的 tracepoint。

### 对 "关键任务响应时间改善 35%" 数据点的审慎评估

daily-info 摘要中提到"关键任务响应时间改善 35%"。

**[待验证]** 与"内存占用减少 40%"类似，该数据点缺乏可复现的 benchmark 描述。审慎评估：

- "关键任务"的定义不明确——是 UI 线程的帧延迟？还是后台任务的完成时间？
- "改善 35%" 的基线不明——是与 Linux 6.6 对比？还是与不开 BPF 对比？
- 在 Android 17 产品设备上，调度性能改善主要来自 EEVDF（§5.31）和 ML 调度器（§1.59），BPF 观测 hook 本身不直接改善调度性能
- 此数据点仅作为"上游趋势参考"，AIW 正文不做结论性引用

## 🔸 扩展点 1：BPF Arena 与大模型推理

Linux 6.10 引入的 BPF Arena（zero-copy 共享内存）与 §5.27 OnDevice LLM 推理能效存在潜在协同：

- LLM 推理过程中，GPU/NPU 与 CPU 之间的数据交换是性能瓶颈
- 如果 BPF 能通过 Arena 直接观测 GPU buffer 的生命周期（与 dmabufIter 互补），可以为推理过程的显存管理提供细粒度数据
- 但这需要 GPU 驱动层暴露相应的 hook，目前在 Android 17 中**[待补充]** 未见公开实现

> 此方向属于前沿研究，不作为正文结论。

## 🔸 扩展点 2：BPF for storage / I/O

mainline 中 BPF 在 I/O 栈的增强：

- `bpf_iter_io_lat`：块设备 I/O 延迟分布 BPF iterator（mainline 5.20+ 引入，Android 17 GKI 可能已包含）
- 可观测 per-device、per-process 的 I/O 延迟分布，与 §6.x 存储性能章节呼应
- Android 17 中已有 `iowait` 统计（通过 `/proc/pid/stat`），但 BPF 版本可以做到 per-IO-request 级别

> [待补充] Android 17 GKI 6.12-lts 中 io_lat BPF iterator 的具体可用性。

## 🔸 扩展点 3：BPF for SELinux / 安全

BPF LSM（Linux Security Module）是 BPF 子系统中一个独立于可观测性的方向：

- 允许通过 BPF 程序实现自定义安全策略（而非仅观测）
- Android 的 SELinux 与 BPF LSM 属于不同的安全框架，二者在 Android 17 中的交互关系**[待补充]** 尚未见公开分析
- 不属于本节的可观测性范围，但值得关注其演进

## 小结

Linux 6.10 的 BPF 增强代表了上游内核在可观测性和可编程性方面的持续演进。对于 Android 17 设备而言：

1. **已确认可用**的是 `android-17.0.0_r1` 中固化的四个 BPF 程序（cyclePerUid、dmabufIter、kernelWakelockDuration、locks），这些已在 §2.6 深度分析
2. **可能可用**的是通过 ACK 6.12-lts backport 的部分 6.10 BPF feature，具体子集需逐 feature 验证
3. **明确不可用**的是仅存在于 mainline 6.10+ 且未被 ACK backport 的 feature
4. daily-info 中的性能数据（"40% / 35%"）**不可作为 AIW 正文结论**，仅作上游趋势参考

BPF 在 Android 上的核心价值仍然是**低开销的内核态数据采集与预处理**——这个定位在 Android 17 中没有变化。Linux 6.10 mainline 的增强更多是扩展了"BPF 能做什么"的边界，而非改变了"BPF 在 Android 中做什么"的基本面。
