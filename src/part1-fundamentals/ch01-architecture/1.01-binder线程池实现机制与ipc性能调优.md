## Android 17 线程池边界

当前源码锚点为平台 `android-17.0.0_r1` 与内核 `android17-6.18-2026-06_r6`。Native Binder 线程池由 libbinder 和驱动共同管理：

1. `ProcessState::setThreadPoolMaxThreadCount()` 通过 `BINDER_SET_MAX_THREADS` 把内核可请求的 worker 上限写给驱动。
2. `ProcessState::startThreadPool()` 主动创建池内的 main thread。这里的 main 指 Binder pool 角色，不是 Java UI 主线程。
3. 驱动发现没有待注册请求、没有 ready thread、已启动的请求线程仍低于上限且当前线程符合 looper 条件时，返回 `BR_SPAWN_LOOPER`。
4. libbinder 收到命令后调用 `spawnPooledThread(false)`，新 worker 以 `BC_REGISTER_LOOPER` 注册。主动加入池的线程使用 `BC_ENTER_LOOPER`，计数语义不同。
5. 事务到达后，驱动从目标进程的等待线程链表选择线程；无可用线程时，工作留在进程或节点待办链表。同步调用方会继续等待服务端执行与回复。

`DEFAULT_MAX_BINDER_THREADS = 15` 表示 Native libbinder 默认配置给驱动的按需请求上限。`startThreadPool()` 创建的 main pool thread、显式 `joinThreadPool()` 的线程以及服务自行设置的上限都会改变进程中可见的 Binder 线程数量，因此“每个进程固定 15 个 Binder 线程”是错误结论。

## 调优原则

线程池饥饿通常由长时间持锁、阻塞 I/O、慢数据库操作、嵌套同步 IPC 或服务端过载引起。直接提高线程上限可能增加锁竞争、内存占用和 CPU 抢占，也可能让更多调用同时卡在同一资源上。调优时按以下顺序收集证据：

- 用 Perfetto 对齐 client 同步等待、server Binder transaction、线程调度状态、锁与 I/O 区间。
- 查看服务线程是否全在执行业务，还是有线程处于 runnable 却拿不到 CPU。
- 检查 `oneway` 是否在同一 Binder 节点的 `async_todo` 上积压。异步调用不会替服务端提供无限吞吐。
- 区分线程池饥饿日志与 ANR 根因。饥饿可以造成 ANR，也可能只是其他锁竞争或 I/O 问题的结果。
- 只有在服务端任务彼此独立、锁与 I/O 已缩短且负载确有并发收益时，再评估提高上限，并用同一 workload 比较排队时间、CPU、内存和尾延迟。

Java Binder、NDK Binder、AIDL HAL 与 RPC Binder 的线程池入口和默认配置不完全相同。任何固定数值都要回到目标进程所用 Binder 栈、启动方式与产品源码核对。
