# 1.65 Android 17 LocationManager 架构与性能优化

`LocationManager` 是 Android 平台位置 API 的客户端入口。应用选定提供者，描述更新间隔、质量、批处理延迟等需求，再通过 Binder 把请求交给 `system_server`。服务端负责权限检查、前后台限制、请求合并、提供者调度、结果裁剪和回调投递。

范围限定在 Android 平台 API 与 AOSP 服务端。Google Play 服务的 `FusedLocationProviderClient`、`LocationCallback` 和地理围栏 API 是另一套客户端 API；它们可能使用系统的 `fused` 提供者，也可能在自己的服务中增加策略，但不能用来解释 `LocationManager` 的公开调用链。

平台基线是 Android 17 / API 37 / `android-17.0.0_r1`，GNSS HAL 接口以同一平台标签下的 `hardware/interfaces` 为准。Linux 内核实现不在讨论范围内，厂商 GNSS 驱动行为不能推断为 `LocationManagerService` 的固定语义。

## 1. 系统边界：应用提出需求，提供者生产位置

Android 17 的主链路如下：

```text
应用进程
  LocationManager
    ├─ getLastKnownLocation(provider)
    ├─ getCurrentLocation(provider, ..., Consumer<Location>)
    └─ requestLocationUpdates(provider, ..., LocationListener/PendingIntent)
                     │
                     │ ILocationManager
                     ▼
system_server
  LocationManagerService
    └─ LocationProviderManager（每个提供者一个实例）
         ├─ passive → PassiveLocationProvider
         ├─ gps     → GnssLocationProvider（默认）或配置的代理提供者
         │              └─ GnssNative → JNI GnssHal → 厂商 GNSS HAL
         ├─ network → ProxyLocationProvider → 外部系统提供者服务
         └─ fused   → ProxyLocationProvider → 外部系统提供者服务
```

`LocationManagerService` 在 `SystemServer` 中启动。它先发布 `location` Binder 服务并创建 `passive` 提供者；到 `PHASE_THIRD_PARTY_APPS_CAN_START`，再初始化 network、fused、GNSS 以及相关代理服务。GNSS 放在这些提供者之后初始化，避免早期 GNSS 回调依赖尚未就绪的系统组件。

### 1.1 四个常见提供者的含义

| 提供者 | Android 17 框架层实现 | 请求是否主动驱动数据源 | 需要注意的边界 |
| --- | --- | ---: | --- |
| `gps` | 默认是 `GnssLocationProvider`，可由配置的代理提供者覆盖 | 是 | 默认路径进入 JNI 和厂商 GNSS HAL；能力、功耗和射频表现取决于设备 |
| `network` | `ProxyLocationProvider` | 是 | 算法位于受配置约束的系统提供者服务中，AOSP 不规定其一定由 GMS 实现 |
| `fused` | `ProxyLocationProvider` | 是 | 系统要求存在可直接启动的系统实现；它不等同于 Play services 客户端类 |
| `passive` | `PassiveLocationProvider` | 否 | 只接收其他提供者已产生的位置，不独立启动定位硬件 |

在纯 AOSP、GMS 设备和 OEM 设备上，network/fused 背后的包可能不同。框架层能验证的是绑定条件、Binder 协议和提供者输出，无法据此断言外部服务采用 Wi-Fi 指纹、卡尔曼滤波或某个私有数据库。设备若配置 GNSS 提供者替换，`gps` 会绑定代理实现，进程内 HAL 路径则可注册为受 `LOCATION_HARDWARE` 权限保护的 `gps_hardware` 提供者。

### 1.2 `FUSED_PROVIDER` 与 Play 服务 API

这两个名称容易产生误解：

- `LocationManager.FUSED_PROVIDER` 是平台定义的提供者名称。调用者仍通过 `LocationManager`、`LocationListener` 或 `PendingIntent` 使用它。
- `FusedLocationProviderClient` 是 Google Play 服务的客户端 API，回调类型是 `LocationCallback`。
- 平台 `LocationManager` 没有接收 `LocationCallback` 的 `requestLocationUpdates` 重载。

排查问题时，应先看应用链接的是 `android.location.*` 还是 `com.google.android.gms.location.*`。API 入口不同，进程、日志和版本依赖也会不同。

[源码依据：`SystemServer.java`、`LocationManagerService.Lifecycle`、`ProxyLocationProvider.java`，`android-17.0.0_r1`]

## 2. 提供者由调用者选择，质量字段不负责自动选源

平台 API 的规则是：**提供者决定请求交给谁，`LocationRequest.quality` 只是给该提供者的质量提示。**

例如，调用：

```java
locationManager.requestLocationUpdates(
        LocationManager.GPS_PROVIDER,
        request,
        executor,
        listener);
```

服务端会查找名为 `gps` 的 `LocationProviderManager`。它不会因为 `request` 使用 `QUALITY_LOW_POWER` 就把请求迁移到 `network`；同理，向 `network` 提供者提交 `QUALITY_HIGH_ACCURACY` 也不会自动启动 GNSS。提供者对质量字段的解释由具体实现决定。

旧的 `Criteria` API 可以让框架层从现有提供者中挑选一个名称，但那是调用前的提供者选择，不是一次请求同时驱动多个提供者。

### 2.1 `LocationRequest` 中值得区分的字段

| 字段 | 服务端用途 |
| --- | --- |
| `intervalMillis` | 期望更新周期，也是同一提供者合并请求时的主要调度输入 |
| `quality` | 质量/功耗提示；数值越小表示要求越高，`100` 比 `104` 更强 |
| `minUpdateIntervalMillis` | 对单个注册的投递限速 |
| `minUpdateDistanceMeters` | 对单个注册按位移过滤 |
| `maxUpdateDelayMillis` | 允许批量延迟；达到条件时提供者才可能批处理 |
| `durationMillis` | 注册有效时间 |
| `maxUpdates` | 成功投递达到次数后移除注册 |
| `lowPower` | 传给提供者的低功耗提示，是否支持由实现决定 |
| `WorkSource` | 供有权限的调用者指定能耗归因；普通应用不能随意伪造 |

公开的 Builder 形式自 API 31 起可用。`maxUpdates` 和 `durationMillis` 也不是 Android 14 才出现的字段。

下面的示例用于明确指定平台 `gps` 提供者，并允许最多 10 秒的批量延迟：

```java
LocationRequest request = new LocationRequest.Builder(5_000L)
        .setQuality(LocationRequest.QUALITY_HIGH_ACCURACY)
        .setMinUpdateIntervalMillis(2_000L)
        .setMaxUpdateDelayMillis(10_000L)
        .build();

LocationListener listener = location -> {
    // 把重计算转交给工作线程；这里保持回调短小。
};

locationManager.requestLocationUpdates(
        LocationManager.GPS_PROVIDER,
        request,
        context.getMainExecutor(),
        listener);
```

`LocationRequest.Builder(long)` 的参数是间隔，不是优先级。示例中的 `10_000 / 2 >= 5_000` 满足框架层接受批处理参数的基本比例，但设备还要具备批处理扩展，提供者也要接受该请求；因此这段代码不构成硬件批处理保证。

[源码依据：`LocationManager.java`、`LocationRequest.java`、`LocationManagerService.validateLocationRequest()`，`android-17.0.0_r1`]

## 3. 三类位置读取的成本不同

### 3.1 最近位置：只读缓存

`getLastKnownLocation(provider)` 通过 `ILocationManager.getLastLocation()` 读取指定提供者的服务端缓存。它不会为了这次调用启动提供者，返回值可以为 `null`，也可能已经过时。业务必须结合 `Location.getElapsedRealtimeAgeMillis()`、精度和数据完整性判断能否使用。

墙上时钟可能被修改，不能用 `System.currentTimeMillis() - location.getTime()` 作为唯一新鲜度依据。比较位置年龄应优先使用单调时钟对应的经过时间。

### 3.2 单次位置：先尝试缓存，再等待新结果

`getCurrentLocation()` 的 Android 17 服务端行为包含两个明确上限：

1. 注册激活时，指定提供者若有不超过 30 秒的合格缓存，可以立即返回；
2. 请求 duration 超过 30 秒时，`LocationProviderManager` 会把它截到 30 秒。

权限、位置开关、提供者状态或 AppOps 导致注册不活跃时，回调可能很快收到 `null`。超时也返回 `null`。调用者应保留并在业务结束时触发 `CancellationSignal`，不要把“等待单次结果”写成无期限状态。

### 3.3 连续更新：注册会参与提供者合并

`requestLocationUpdates()` 会建立长期注册。监听器适合进程存活且生命周期清晰的页面或服务；`PendingIntent` 适合需要跨组件交付的场景，但仍受后台位置权限、前台服务和系统节流规则约束。

使用监听器时，应保存同一个实例，并在生命周期结束时取消：

```java
private final LocationListener listener = this::onLocationChanged;

@Override
protected void onStart() {
    super.onStart();
    locationManager.requestLocationUpdates(
            LocationManager.GPS_PROVIDER,
            request,
            getMainExecutor(),
            listener);
}

@Override
protected void onStop() {
    locationManager.removeUpdates(listener);
    super.onStop();
}
```

`removeUpdates()` 需要原先的监听器对象。及时取消既能断开 Activity/Fragment 与回调对象的引用，也能把该注册从服务端合并请求中移除，避免页面不可见后仍维持高频提供者请求。若产品需要后台定位，应把注册放到有明确停止条件且满足权限要求的组件，不应依赖页面对象继续存活。

## 4. Binder 入口之后发生了什么

以连续监听器注册为例，Android 17 的主要路径是：

```text
LocationManager.requestLocationUpdates()
  → ILocationManager.registerLocationListener()
    → LocationManagerService.registerLocationListener()
      → CallerIdentity + permission level
      → validateLocationRequest()
      → getLocationProviderManager(provider)
      → LocationProviderManager.registerLocationRequest()
        → Registration 参与活跃性判断与请求合并
```

### 4.1 身份、权限和请求清洗

`LocationManagerService` 从 Binder 调用构造 `CallerIdentity`，读取精确/粗略权限级别，并检查提供者是否存在。`validateLocationRequest()` 会处理：

- 普通调用者无权指定的 `WorkSource`；
- `lowPower`、忽略位置设置、ADAS GNSS bypass 等受限字段；
- 包名、归因标签与调用 UID 的一致性；
- 对特权绕过的权限及允许列表限制。

所以，客户端对象中的隐藏字段不等于服务端会照单执行。调试系统应用时，要同时打印“客户端构造的请求”和 `dumpsys location` 中“服务端接受后的请求”。

### 4.2 注册能否生效，由动态状态共同决定

`LocationProviderManager` 会持续重算注册是否处于活动状态，条件包括：

- 调用者是否仍有相应位置权限；
- 用户是否可见、提供者对该用户是否启用；
- 包是否命中位置黑名单；
- 前后台状态及后台节流；
- Battery Saver 的位置模式、屏幕状态；
- AppOps 是否允许本次使用；
- 特权绕过是否仍满足策略。

Binder 注册成功不代表提供者马上运行，也不代表每个位置都能交付。权限、前后台和省电状态可以在注册存续期间改变，服务端会随之更新活动状态。

### 4.3 粗略位置权限会改请求，也会改结果

Android 12 起，用户可以在应用同时请求精确和粗略位置时选择大致位置。Android 17 服务端对只有粗略位置权限的注册至少做两层处理：

1. `LocationProviderManager` 把质量改为 `QUALITY_LOW_POWER`，并把间隔与最小间隔提高到内部的 10 分钟下限；
2. 位置结果经过 `LocationFudger`，通过随时间变化的偏移和网格化生成粗略位置。

“10 分钟”是 `android-17.0.0_r1` 的框架层内部调度下限，不是公开 API 对所有设备、所有版本的回调承诺。粗略位置也不是简单地截断经纬度小数位。应用不应依赖固定的模糊半径或固定小数位数。

后台还有另一层动态间隔调整。Android 官方文档将普通后台应用描述为每小时只能收到少量位置更新；具体节流值由系统配置、设备版本、进程状态和豁免条件共同决定。

[源码依据：`LocationProviderManager.Registration.calculateProviderLocationRequest()`、`LocationFudger.java`，`android-17.0.0_r1`]

## 5. 同一提供者的请求如何合并

每个提供者有自己的 `LocationProviderManager`，只合并发往该提供者且当前处于活动状态的注册。合并过程不是“全系统挑一个最佳位置源”。

### 5.1 `ProviderRequest` 的合并规则

Android 17 的 `mergeRegistrations()` 对非 passive 请求执行：

- 间隔取最小值；
- 质量取数值最小值，也就是更强的质量要求；
- 最大更新延迟取最小值；
- ADAS 绕过与忽略设置标志做 OR；
- `lowPower` 做 AND；
- WorkSource 收集接近最短间隔、会影响底层工作量的注册。

如果 `maxUpdateDelay / 2 < interval`，框架层把合并后的批处理延迟置为 0。这样可以避免一个不具备批处理意义的延迟字段反复触发提供者重配。公开 `LocationRequest` 文档也把“最大延迟至少为间隔的两倍”列为可能批处理的条件。

例如，同一 `gps` 提供者有两个活动请求：

```text
A: interval=5s,  quality=HIGH, maxDelay=20s, lowPower=false
B: interval=30s, quality=LOW,  maxDelay=60s, lowPower=true

合并给 gps 提供者：
interval=5s
quality=HIGH
maxDelay=20s
lowPower=false
```

这个结果只配置一次 `gps` 提供者。A、B 各自是否收到某个位置，仍要经过各自注册的最小间隔、最小距离、权限、AppOps、持续时间和最大更新次数过滤。B 不会因为底层以 5 秒工作就必然每 5 秒收到回调。

### 5.2 一条高频请求会抬高该提供者的公共成本

同一提供者的活动请求共享底层工作。一条 1 秒 GPS 请求可能使 GNSS 持续工作；其他低频 GPS 注册虽然被单独限速，底层成本已经由最激进的请求决定。优化时应找出参与合并的最短间隔和最强质量，而不能只看某个业务模块自己的配置。

`dumpsys location` 会列出提供者请求和注册，是定位“谁把 GPS 拉到高频”的首选证据。WorkSource/BatteryStats 用于能耗归因，但合并后的归因集合不能表示各应用的实际能耗占比。

## 6. 位置上报与回调投递

提供者上报 `LocationResult` 后，`LocationProviderManager` 会先更新缓存，再对注册逐一处理。连续更新的主要过滤点包括：

- 经纬度是否合法；
- 最小更新间隔，包含框架层允许的小幅时序抖动；
- 最小更新距离；
- 持续时间与最大更新次数；
- 精确/粗略位置结果选择；
- AppOps 是否允许本次交付。

回调路径可简化为：

```text
提供者上报位置
  → LocationProviderManager
    → Registration.acceptLocationChange()
      → ILocationListener.onLocationChanged()（单向 Binder）
        → 应用的 LocationListenerTransport
          → 指定 Executor
            → LocationListener.onLocationChanged()
              → IRemoteCallback 通知 system_server 本次处理完成
```

### 6.1 执行器堵塞为什么也会带来系统成本

对非 passive 的连续更新，服务端在交付前获取一个部分唤醒锁，超时为 30 秒。应用侧 `LocationListenerTransport` 在指定执行器上完成回调后，通过 `IRemoteCallback` 通知服务端释放它。

这带来三点工程约束：

1. 单向 Binder 只表示发送方不等待同步返回，不表示应用回调没有背压；
2. 执行器队列长时间拥塞，会延后完成回调，服务端唤醒锁只能等回调或 30 秒超时；
3. 回调中如果需要比这更长的后台工作，应用应自行采用符合系统约束的执行与保活机制，不能把框架层的交付唤醒锁当作业务唤醒锁。

不要假设 Perfetto 中存在稳定的 `LocationManagerService` 或 `GnssLocationProvider` 自定义轨道。`android-17.0.0_r1` 的这些 Java 路径没有提供可依赖的统一时间片名称。可用 Binder、线程调度、CPU 频率/空闲状态、唤醒锁和应用自定义跟踪点组合还原延迟。

[源码依据：`ILocationListener.aidl`、`LocationManager.LocationListenerTransport`、`LocationProviderManager.Registration.acceptLocationChange()`，`android-17.0.0_r1`]

## 7. GNSS 从框架层到 HAL

Android 17 的 GNSS 主路径是：

```text
LocationProviderManager[gps]
  → GnssLocationProvider
    → GnssNative（Java）
      → JNI
        → services/core/jni/gnss/Gnss.cpp
          → AIDL IGnss 或旧版 HIDL IGnss
            → 厂商 GNSS 服务 / 芯片组
```

`GnssLocationProvider` 运行在 `system_server`，主要任务是把合并后的 `ProviderRequest` 转换成 GNSS 引擎配置，管理启动、停止、框架层调度、批处理、辅助数据和指标。`GnssNative` 汇集 Java/JNI 回调。射频跟踪、基带算法和大部分硬件电源状态位于厂商实现。

### 7.1 Android 17 仍保留 AIDL/HIDL 兼容路径

JNI `GnssHal` 先等待 VINTF 声明的 AIDL 服务。AIDL 接口版本大于等于 2 时，构造过程直接结束；否则还会依次探测 HIDL 2.1、2.0、1.1、1.0。Android 17 仍带着多版本兼容代码，不能预设设备只走 AIDL。分析单机问题时，要从 `dumpsys` 和 `GnssJni` 日志确认连接到的接口版本。

AIDL `IGnss` 的主生命周期接口是：

- `setCallback()`；
- `start()` / `stop()`；
- `close()`；
- `setPositionMode()`；
- 时间、位置和辅助数据注入；
- 获取测量、PSDS、批处理、地理围栏、功耗指示等扩展。

`IGnss` 没有 `open()`。各扩展通常使用自己的 `setCallback()` 或 `init()` 建立回调。

### 7.2 能力位是“设备支持什么”，不是性能数字

HAL 会上报调度、测量、地理围栏、低功耗模式等能力。框架层据此启用对应路径。例如，没有调度能力时，`GnssLocationProvider` 可以通过闹钟在低频请求之间休眠和唤醒；具备调度能力时，可把周期直接交给 HAL。

能力位不能推导出固定精度、TTFF 或电流值。天线、天空可视度、频段、热状态、厂商固件、辅助数据、移动速度和测量环境都会改变结果。通用章节不应给出“GPS 恒定 3–10 米”或“批处理恒定 1–5 mA”一类设备无关结论。

## 8. GNSS 调度、批处理与全程跟踪

### 8.1 普通定位请求如何驱动 GNSS

`GnssLocationProvider.updateRequirements()` 从合并请求读取间隔、最大更新延迟、低功耗提示和 WorkSource：

- 满足批处理条件时，停止普通导航并启动硬件批处理；
- 已启动且 HAL 支持调度时，更新 `setPositionMode()`；
- 尚未启动时，设置 position mode 后调用 `start()`；
- HAL 不支持调度时，框架层用闹钟辅助长间隔轮询；
- 提供者请求变为非活动状态时，停止导航和批处理。

这里没有“间隔大于 10 秒就必定批处理”的规则。

### 8.2 硬件批处理的必要条件

Android 17 框架层至少检查：

1. `initBatching()` 成功；
2. HAL 报告的批处理容量大于 1；
3. `batchLength = min(maxUpdateDelay, 框架层上限)`；
4. `batchLength / 2 >= max(interval, 框架层最小批处理间隔)`。

满足这些条件后，`GnssNative.startBatch()` 才会进入 `IGnssBatching.start()`。如果请求的批处理长度小于硬件缓冲区容量对应的时长，框架层还会设置精确闹钟，按批处理长度调用 `flushBatch()`。

批处理的收益来自减少 AP 唤醒和 Binder/Java 交付次数，但 GNSS 接收机仍可能按设定周期采样。它不能自动把射频跟踪成本降为零。评估收益要同时比较 AP 空闲时间、唤醒次数、GNSS 功耗统计和厂商电源轨数据。

### 8.3 GNSS 测量的全程跟踪是另一条请求

`GnssMeasurementRequest.Builder.setFullTracking(true)` 自 API 31 起用于原始 GNSS 测量。它要求关闭占空比循环，以连续跟踪更多 GNSS 信号，通常会增加功耗。多个测量监听器合并时，只要任一活动请求要求全程跟踪，合并结果就启用全程跟踪；最短测量间隔也会胜出。

API 34 增加了 `GnssMeasurementsEvent.isFullTracking()`，调用者可以在 HAL 支持相应信息时判断事件是否处于全程跟踪模式。

普通 `LocationRequest` 的 `QUALITY_HIGH_ACCURACY + 短间隔` 不等价于显式 `GnssMeasurementRequest.setFullTracking(true)`。`IGnssPowerIndication` 也不是全程跟踪开关：它只提供 `setCallback()` 和 `requestGnssPowerStats()`，用途是报告 GNSS 功耗能力和统计。

[源码依据：`GnssLocationProvider.updateRequirements()`、`GnssMeasurementsProvider.mergeRegistrations()`、`IGnssBatching.aidl`、`IGnssPowerIndication.aidl`，`android-17.0.0_r1`]

## 9. PSDS 与 TTFF：把测量事实和经验值分开

### 9.1 PSDS 数据路径

HAL 通过 PSDS 回调请求框架层下载数据。Android 17 的路径是：

```text
厂商 GNSS HAL
  → IGnssPsdsCallback.downloadRequest(type)
    → GnssLocationProvider
      → GnssPsdsDownloader
        → 下载配置的厂商 URL
          → GnssNative.injectPsdsData(type, opaque bytes)
            → IGnssPsds.injectPsdsData()
```

框架层把 PSDS 内容视为不透明字节，不解析成“星历表字段”。`GnssPsdsDownloader` 对单次内容设置 1 MB 上限，连接超时 30 秒、读取超时 60 秒；服务器地址来自设备配置。下载失败会按框架层策略重试，但设备是否支持某类 PSDS、数据含义及有效期由 HAL/服务配置决定。

PSDS 有助于缩短部分启动场景的捕获时间，却不是 TTFF 的唯一变量。时间/位置注入、SUPL、网络状态、辅助数据、天线、天空遮挡、干扰、频段和厂商算法都可能影响首次定位。

### 9.2 框架层如何记录 TTFF

`startNavigating()` 成功调用 HAL `start()` 后记录 `mFixRequestTime`。收到第一份含经纬度的有效 GNSS location 时：

```text
TTFF = 首个有效定位的经过时间 - mFixRequestTime
```

结果写入 `GnssMetrics`，`GnssStatus.Callback.onFirstFix(ttffMillis)` 也向有权限的监听者暴露相应事件。这个定义可以用于同设备、同场景的前后对比；“冷启动必为 30–60 秒”或“A-GPS 必为 1–5 秒”没有跨设备保证。

做可重复测试时，至少记录：

- 设备、构建指纹、GNSS HAL 接口版本；
- 是否删除辅助数据，是否重启 GNSS；
- 网络、SUPL/PSDS 状态；
- 室外天空条件、静止/运动状态；
- 请求开始的经过时间与首个有效定位；
- 多轮分布，而非只报一次最小值。

## 10. 地理围栏：公开邻近提醒与硬件围栏是两条路径

### 10.1 `LocationManager.addProximityAlert()` 的框架层路径

平台遗留 API 的调用链是：

```text
LocationManager.addProximityAlert()
  → ILocationManager.requestGeofence()
    → LocationManagerService
      → GeofenceManager
        → 使用 FUSED_PROVIDER 请求位置
          → system_server 中计算进入/离开
            → PendingIntent
```

`GeofenceManager` 要求精确位置权限。它为所有活动围栏合并一个位置请求，根据“当前位置到最近围栏边界的距离 / 假定最大速度”估算下次更新间隔，并受后台邻近提醒节流值约束，最长不超过 2 小时。缓存位置超过 5 分钟就不用于这个估算。

收到位置后，它计算中心距离，并用：

```text
effectiveRadius = max(geofenceRadius, locationAccuracy)
inside = distanceToCenter <= effectiveRadius
```

从 `UNKNOWN`/`OUTSIDE` 进入 `INSIDE` 时发送进入提醒；只有先处于 `INSIDE`，之后转为 `OUTSIDE`，才发送离开提醒。该实现没有网格空间索引、驻留延迟或通用迟滞边界。

### 10.2 硬件 GNSS 地理围栏路径

Android 17 还存在独立的硬件围栏基础设施：

```text
配置的地理围栏提供者
  ↔ GeofenceProxy
  ↔ GeofenceHardwareService
  ↔ GnssGeofenceProxy
  ↔ GnssNative
  ↔ IGnssGeofence
```

`GnssGeofenceProxy` 支持 add/remove/pause/resume，并缓存已接受的条目，以便 HAL 重启后恢复。`GeofenceProxy` 是否创建取决于设备 overlay 与可解析的系统服务。

不能由此得出 `addProximityAlert()` 会自动把同一个围栏切换到 GNSS 硬件。前者在 `GeofenceManager` 中以位置更新做软件判断；后者服务于配置的硬件地理围栏提供者。Google Play 服务的地理围栏 API 也不属于这条公开平台调用链。

[源码依据：`GeofenceManager.java`、`GeofenceProxy.java`、`GnssGeofenceProxy.java`、`IGnssGeofence.aidl`，`android-17.0.0_r1`]

## 11. 性能问题的证据链

位置问题常同时跨越应用、`system_server`、提供者服务和厂商 HAL。只看一条回调耗时，很难区分请求未激活、提供者没有定位、结果被过滤或执行器堵塞。

### 11.1 先用 `dumpsys location` 建立状态快照

以下命令分别查看常规状态、详细状态和 GNSS metrics：

```bash
adb shell dumpsys location
adb shell dumpsys location -a
adb shell dumpsys location --gnssmetrics
```

应重点核对：

- 提供者是否存在、是否启用；
- 每个提供者的活动请求与注册调用者；
- 间隔、质量、最大延迟是否已被服务端改写；
- 最近位置的年龄；
- GNSS 启动/批处理/能力与 TTFF 指标；
- 框架层邻近提醒和硬件地理围栏状态。

命令输出会随构建类型和厂商扩展变化。调试用户版本时，部分身份或 HAL 细节可能被裁剪。

### 11.2 分清应用打点与系统观测点

普通应用只能稳定记录自己的请求和回调，不能直接给 `system_server` 的注册激活或提供者上报打点。应用侧应使用单调时钟，例如 `SystemClock.elapsedRealtimeNanos()`，记录这三个事件：

```text
A_request   调用 LocationManager API
A_callback  指定执行器开始执行回调
A_done      应用完成轻量回调处理
```

这组数据能直接计算应用看到的端到端等待时间 `A_callback - A_request`，以及回调工作时间 `A_done - A_callback`。前者包含服务端策略、提供者产出、Binder 投递和执行器排队，不能仅凭应用日志继续归因。

要继续分段，需要在 userdebug/eng 构建、定制框架层/提供者或设备已经提供对应 Perfetto 数据源时，增加系统侧观测点：

| 观测点 | 所在层 | 可用于解释的阶段 |
| --- | --- | --- |
| `S_active` | `system_server` 注册变为活动状态，合并后的 `ProviderRequest` 更新 | 请求是否通过权限、位置开关、前后台和省电策略 |
| `P_report` | 提供者向框架层上报 `LocationResult` | 提供者或 GNSS/HAL 等待时间 |
| `S_deliver` | `system_server` 决定向目标注册投递 | 单注册过滤与服务端投递时间 |

当这些事件来自同一次受控请求，并且都使用可换算到同一单调时钟域的时间戳时，才可以计算：

- `S_active - A_request`：Binder 入口、校验与激活；
- `P_report - S_active`：提供者等待，GNSS 场景还要结合 TTFF；
- `S_deliver - P_report`：缓存更新、单注册过滤与投递准备；
- `A_callback - S_deliver`：Binder、进程调度和执行器排队。

并发请求下，不能用“时间上最近的一条位置记录”猜测跨进程事件属于同一个注册。应使用定制关联 ID，或把实验限制为单应用、单提供者、单注册，再结合调用者身份、请求参数和 `Location.getElapsedRealtimeNanos()` 交叉核对。

Perfetto 可组合 `sched`、`binder_driver`、CPU 频率/空闲状态、唤醒锁/功耗、网络，以及设备提供的厂商 GNSS 数据源。没有明确的框架层/HAL 事件或自定义时间戳时，不能凭模糊的 “Gnss” 字符串把某段时间片当成 TTFF。

### 11.3 常见症状与核查点

| 症状 | 第一批证据 | 高概率方向 |
| --- | --- | --- |
| 注册成功但无回调 | 活动状态、提供者是否启用、AppOps | 权限/后台/省电限制，或提供者没有结果 |
| 回调频率低于请求 | 服务端改写后的间隔、单注册过滤 | 粗略位置/后台节流、最小间隔、最小距离、批处理 |
| GPS 长时间保持活动 | `gps` 的合并请求和调用者 | 另一条更短间隔请求、未取消注册 |
| TTFF 变长 | 多轮 TTFF、PSDS/SUPL/网络、天空条件 | 辅助数据、射频环境、HAL/固件变化 |
| 回调后系统仍持有唤醒锁 | 应用执行器与完成时间 | 执行器拥塞或回调耗时 |
| 围栏漏报 | 使用的平台/GMS API、位置精度、软件/硬件路径 | 路径判断错误、权限/后台限制、位置本身不稳定 |

## 12. 设计与审查清单

应用侧：

- 明确写出使用的平台 API 还是 Play 服务 API；
- 明确选哪个提供者，不把质量字段当作自动选源器；
- 最近位置要检查年龄与精度；
- 单次请求处理 `null`、取消与 30 秒服务端上限；
- 连续请求绑定清晰生命周期，停止时用同一监听器或 PendingIntent 取消；
- 回调只做轻量工作，避免堵塞指定执行器；
- 需要大致位置时按能力降级，不假设固定模糊半径；
- 后台定位同时检查后台位置权限、前台服务类型和系统节流。

系统与厂商侧：

- 以 `dumpsys location` 中的服务端请求为准，不只看客户端对象；
- 分提供者检查最短间隔、最高质量要求和最短允许批处理延迟；
- 确认 GNSS 使用 AIDL 还是 HIDL，以及能力是否匹配预期；
- 对批处理同时验证 HAL 支持、批处理容量、请求比例和实际刷新；
- 把测量全程跟踪与普通 LocationRequest、功耗指示分开；
- TTFF、精度和电流只报告指定设备与测试条件下的统计分布；
- 区分 `GeofenceManager` 软件邻近提醒与硬件地理围栏提供者。
