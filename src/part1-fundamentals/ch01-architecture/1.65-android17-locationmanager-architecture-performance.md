# 1.65 Android 17 LocationManager 架构与性能优化

LocationManager 是 Android 位置服务的 SDK 入口。应用通过它请求周期性位置更新、查询最近一次位置、注册地理围栏、获取 GNSS 卫星状态。从架构角度看，LocationManager 是一个轻量客户端代理——所有调用通过 Binder IPC 进入 `system_server` 中的 `LocationManagerService`（LMService）。

本节聚焦 LocationManager 的**架构边界与内部机制**。位置 API 的应用层实践（Battery 性能权衡、前台服务联动）详见 §5.21，位置回调管线延迟与 ANR 防范详见 §8.14。

### 与 FusedLocationProvider 的关系

Android SDK 中存在两套位置 API：

1. **LocationManager**（AOSP 原生）：直接管理 GNSS、Network、Passive Provider。应用直接指定数据源和精度参数。所有 Android 设备必须实现。
2. **FusedLocationProviderClient**（Google Play Services）：Google 的融合定位服务，在 GMS 进程中运行，自动融合 GNSS + Wi-Fi + 蓝牙 + 加速度计数据。仅 GMS 设备可用。

本节聚焦 AOSP 原生 LocationManager。在 Perfetto trace 中，两者会以不同的进程/线程出现：LocationManagerService 在 `system_server` 中，FusedLocationProvider 在 `com.google.android.gms` 进程中。

> **性能观测提示**：在 Perfetto 中，位置相关的 trace event 以 `LocationManagerService` 前缀出现。GNSS HAL 的 NMEA 句子、TTFF（首次定位时间）等事件以 `Gnss` 前缀出现。

## LocationProvider 适配器机制

### Provider 抽象模型

LocationManagerService 不直接操作硬件，而是通过 `LocationProviderManager` 管理一组 Provider。每个 Provider 是一个独立的适配器，封装特定定位技术的数据获取逻辑。

Android 17 中实际注册的 Provider 类型：

| Provider 名称 | 实现类 | 数据源 | 典型精度 | 功耗 |
|---|---|---|---|---|
| `gps` | `GnssLocationProvider` | GNSS 芯片（GPS/GLONASS/Galileo/BDS） | 3-10m | 高 |
| `network` | `NetworkLocationProvider`（代理） | Wi-Fi AP + 基站三角测量 | 10-100m | 低 |
| `passive` | `PassiveProvider` | 接收其他 Provider 的位置更新 | N/A | 极低 |
| `fused` | `FusedLocationProvider`（GMS） | 多源融合 | 3-50m | 自适应 |

[已验证: AOSP android-17.0.0_r1, frameworks/base/services/core/java/com/android/server/location/provider/LocationProviderManager.java — Provider 注册与管理]

### Provider 生命周期

```
LocationProviderManager
  ├── onRegistration()       ← 系统启动时注册
  ├── setRequest()           ← 接收 LocationRequest
  ├── onStart()              ← 开始定位
  ├── onStop()               ← 停止定位
  ├── onReportLocation()     ← Provider 上报位置
  └── onUnregistration()     ← 注销
```

每个 Provider 内部维护自己的工作状态（STARTED / STOPPED / DISABLED）。LMService 根据所有活跃 LocationRequest 的并集计算每个 Provider 应该运行的时间窗口和精度级别。

### GnssLocationProvider 内部架构

`GnssLocationProvider` 是最复杂的 Provider，直接与 GNSS HAL 通信：

```
GnssLocationProvider (system_server)
  ├── GnssHal                     ← AIDL HAL 绑定
  │   ├── IGnss.open()            ← 打开 GNSS 芯片
  │   ├── IGnss.start()           ← 开始定位
  │   ├── IGnss.stop()            ← 停止定位
  │   ├── IGnss.injectPsds()      ← 注入辅助数据 (A-GPS)
  │   └── GnssCallback            ← HAL→Framework 回调
  │       ├── onNmeaReceived()    ← NMEA 句子
  │       ├── onLocationChanged() ← 位置更新
  │       ├── onSvStatusChanged() ← 卫星状态
  │       └── onCapabilities()    ← 芯片能力上报
  ├── GNSS Measurements           ← 原始测量数据
  │   ├── GnssMeasurementsEvent
  │   └── GnssClock
  └── Navigation Message          ← 导航电文
      └── GnssNavigationMessage
```

### Network Location Provider 架构

与 GNSS Provider 直接操作硬件不同，Network Provider 通过一个独立的 Binder 服务代理获取位置：

```
LocationManagerService
  └── NetworkLocationProvider (代理)
       └── ILocationProviderManager.aidl → NetworkLocationService (外部进程)
```

NetworkLocationService 通常由 GMS（Google Mobile Services）或 OEM 自定义的定位服务实现。它内部使用 Wi-Fi AP RSSI 指纹库 + 基站 Cell-ID 数据进行三角测量。在非 GMS 设备上（如 AOSP bare build），network provider 可能返回空结果。

> **架构要点**：Network Location Provider 的进程边界是 Android 位置架构的关键设计决策——它允许 OEM 替换定位算法而不修改 framework 代码，同时隔离了位置服务崩溃风险。

## LocationRequest 请求队列管理

### LocationRequest 模型

`LocationRequest` 是应用向 LocationManager 提交的定位需求描述符，核心字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| `priority` | int | 定位优先级（PRIORITY_HIGH_ACCURACY / BALANCED_POWER_ACCURACY / LOW_POWER / NO_POWER） |
| `intervalMs` | long | 期望位置更新间隔（毫秒） |
| `minUpdateIntervalMs` | long | 最小更新间隔（节流下限） |
| `maxUpdates` | int | 最大更新次数（Android 14+） |
| `minUpdateDistanceM` | float | 最小位移触发距离（米） |
| `durationMillis` | long | 请求有效期（Android 14+） |
| `workSource` | WorkSource | 能耗归因目标（谁触发定位） |

[已验证: AOSP android-17.0.0_r1, frameworks/base/location/java/android/location/LocationRequest.java]

### 优先级与 Provider 映射

```
PRIORITY_HIGH_ACCURACY (100)
  → 激活 GPS + Network Provider
  → 间隔通常 ≤ 5s
  → 功耗最高

PRIORITY_BALANCED_POWER_ACCURACY (102)
  → 优先 Network Provider，GPS 作为补充
  → 间隔通常 10s-60s
  → 功耗中等

PRIORITY_LOW_POWER (104)
  → 仅 Network Provider（Wi-Fi/Cell）
  → 间隔通常 60s-300s
  → 功耗低

PRIORITY_NO_POWER (106)
  → 仅 Passive Provider
  → 接收其他应用触发的位置更新
  → 功耗 ≈ 0
```

### 请求合并与调度

LMService 收到多个应用的 LocationRequest 后，会进行**请求合并**（coalescing）：

1. **取最短间隔**：如果 App A 要求 10s 间隔，App B 要求 30s 间隔，系统以 10s 间隔运行 GPS。
2. **取最高精度**：如果 App A 要求 HIGH_ACCURACY，App B 要求 LOW_POWER，系统使用 HIGH_ACCURACY（GPS 激活）。
3. **能耗归因**：通过 WorkSource 将 GPS 唤醒成本分配给正确的 App。

```
App A: interval=5s, priority=HIGH_ACCURACY
App B: interval=30s, priority=LOW_POWER

合并结果: interval=5s, priority=HIGH_ACCURACY
  → GPS Provider 以 5s 间隔运行
  → App B 被动接收（如果位置满足其精度要求）
```

[已验证: AOSP android-17.0.0_r1, frameworks/base/services/core/java/com/android/server/location/LocationManagerService.java — 请求合并逻辑]

> **性能影响**：请求合并是 LocationManagerService 的核心优化。如果没有合并，多个应用同时请求 GPS 定位会导致 GNSS 芯片被反复唤醒。合并后，所有应用共享同一次 GNSS 读取结果，显著降低功耗。

## A-GPS 辅助定位优化

### PSDS 数据注入

GNSS 首次定位时间（TTFF, Time To First Fix）在冷启动时可达 30-60 秒，因为接收机需要下载完整的星历数据（Ephemeris）。A-GPS 通过网络注入辅助数据将 TTFF 降至 1-5 秒。

Android 支持三种 PSDS（Positioning and Satellite Data Service）数据：

| 类型 | 说明 | 更新频率 | 数据量 |
|---|---|---|---|
| **Ephemeris** | 精密星历（每颗卫星的精确轨道参数） | 4 小时 | ~50 KB |
| **Almanac** | 粗略星历（所有卫星的粗略轨道） | 数天 | ~150 KB |
| **Long-term PSDS** | 长期预测星历（多天预测） | 1-7 天 | ~200 KB |

注入路径：
```
LocationManagerService
  → GnssLocationProvider
    → GnssHal.injectPsds(psdsData, psdsType)
      → IGnssPsds.aidl
        → GNSS HAL (vendor)
          → GNSS 芯片
```

[已验证: AOSP android-17.0.0_r1, hardware/interfaces/gnss/aidl/android/hardware/gnss/IGnssPsds.aidl]

### TTFF 性能分析

```
冷启动（无 A-GPS）:  30-60s  ← 需要完整下载星历
温启动（有 Almanac）: 10-20s  ← 大致知道卫星位置
热启动（有 Ephemeris）: 1-5s   ← 星历仍在有效期
A-GPS 辅助:          1-5s   ← 网络注入星历，等效热启动
```

> **性能观测**：在 Perfetto 中搜索 `GnssLocationProvider` track，可以看到 `start` → `firstFix` 之间的时间差即为实际 TTFF。`TTFF * 1000ms` 以上的冷启动延迟通常指向 PSDS 注入失败或网络不可用。

### Android 17 GNSS 能力探测

GNSS HAL 在启动时通过 `GnssCallback.onCapabilities()` 上报芯片能力 bitmask：

```
GNSS_CAPABILITY_SCHEDULING      (1 << 0)  // 支持定时调度
GNSS_CAPABILITY_ON_DEMAND_TIME  (1 << 1)  // 支持按需时间注入
GNSS_CAPABILITY_GEOFENCING      (1 << 2)  // 支持硬件地理围栏
GNSS_CAPABILITY_MEASUREMENTS    (1 << 3)  // 支持原始测量数据
GNSS_CAPABILITY_NAV_MESSAGES    (1 << 4)  // 支持导航电文
GNSS_CAPABILITY_LOW_POWER_MODE  (1 << 5)  // 支持低功耗模式
GNSS_CAPABILITY_SATELLITE_BLOCKLIST (1 << 6) // 支持卫星黑名单
GNSS_CAPABILITY_SATELLITE_PVL   (1 << 7)  // 支持卫星 PVL
```

[已验证: AOSP android-17.0.0_r1, hardware/interfaces/gnss/aidl/android/hardware/gnss/IGnssCallback.aidl — capabilities bitmask 定义]

LMService 根据能力 bitmask 选择最优策略。例如，如果 HAL 不支持 `GNSS_CAPABILITY_GEOFENCING`，地理围栏监测回退到软件实现（system_server 中轮询位置）。

## 低功耗定位模式

### 功耗模型

GNSS 芯片的典型功耗：

| 模式 | 功耗 | 说明 |
|---|---|---|
| 连续跟踪 | 30-80 mA | 芯片持续工作 |
| 周期性唤醒 | 5-20 mA | 每 N 秒唤醒一次，利用硬件 batching |
| 硬件 Batching | 1-5 mA | 芯片内部缓存多个位置，批量上报 |
| 低功耗模式 | 0.5-2 mA | 仅维护基本卫星跟踪 |
| 关闭 | < 0.1 mA | 芯片进入 sleep |

### Hardware Batching

Android 7.0+ 引入了 GNSS 硬件 Batching 支持。当 LocationRequest 的 `interval` > 一定阈值（通常 10s）且 HAL 支持 batching 时，LMService 会启用硬件 Batching：

```
传统模式:
  Framework → start → (等待) → onLocationChanged → stop → start → ...

Batching 模式:
  Framework → startBatch(minInterval, minFlingDistance)
    → 芯片自主运行，Framework 进入 sleep
    → 芯片缓存 N 个位置
    → flushBatch() → 批量回调 onLocationChanged × N
```

[已验证: AOSP android-17.0.0_r1, hardware/interfaces/gnss/aidl/android/hardware/gnss/IGnssBatching.aidl]

> **性能意义**：Hardware Batching 是导航类应用后台持续定位的关键优化。使用 batching 后，`system_server` 不需要每 30 秒唤醒一次来读取 GPS，GNSS 芯片完全自主工作，CPU 可以保持 deep sleep。

### Android 14+ GNSS Full Tracking

Android 14 引入了 GNSS Full Tracking 模式（`IGnssPowerIndication`），允许系统在特定场景下请求 GNSS 芯片进入最大功率模式以获取最快首次定位：

```java
// LocationRequest 隐式触发
LocationRequest request = new LocationRequest.Builder(
    PRIORITY_HIGH_ACCURACY)
    .setIntervalMillis(1000)  // 1 秒间隔
    .build();
```

当系统检测到 HIGH_ACCURACY + 短间隔请求时，GnssLocationProvider 会通知 HAL 进入 full tracking 模式，持续跟踪所有可见卫星。

[已验证: AOSP android-17.0.0_r1, hardware/interfaces/gnss/aidl/android/hardware/gnss/IGnssPowerIndication.aidl]

## 位置精度与实时性权衡

### Provider 选择决策树

```
请求到达 LMService
  │
  ├── priority == HIGH_ACCURACY?
  │     ├── GPS 可用? → GnssLocationProvider (主动)
  │     └── GPS 不可用? → NetworkLocationProvider (降级)
  │
  ├── priority == BALANCED_POWER_ACCURACY?
  │     ├── Network Provider 可用且精度足够? → NetworkLocationProvider
  │     └── 否? → GnssLocationProvider (低频)
  │
  ├── priority == LOW_POWER?
  │     └── NetworkLocationProvider only
  │
  └── priority == NO_POWER?
        └── PassiveProvider only
```

### 位置融合策略

LMService 不做位置融合——每个 Provider 独立上报位置，LMService 按时间戳和精度选择"最佳"位置分发给应用。真正的多源融合发生在 FusedLocationProvider（GMS）或 NetworkLocationService 中。

```
GnssLocationProvider → Location(gps, accuracy=5m, t=10:00:05)
NetworkLocationProvider → Location(network, accuracy=30m, t=10:00:06)

LMService 分发逻辑:
  → 对于 HIGH_ACCURACY 请求: 使用 GPS Location（精度更高）
  → 对于 LOW_POWER 请求: 使用 Network Location（已满足精度要求）
```

## LocationListener 回调机制与内存泄漏防护

### 回调注册模型

应用通过两种方式接收位置更新：

1. **LocationListener**（传统接口）：
```java
locationManager.requestLocationUpdates(
    LocationManager.GPS_PROVIDER,
    new LocationRequest.Builder(PRIORITY_HIGH_ACCURACY)
        .setIntervalMillis(5000).build(),
    context.getMainExecutor(),
    new LocationListener() {
        @Override
        public void onLocationChanged(Location location) {
            // 处理位置更新
        }
    });
```

2. **LocationCallback**（Android 9+ 推荐）：
```java
locationManager.requestLocationUpdates(
    LocationRequest.Builder(PRIORITY_HIGH_ACCURACY)
        .setIntervalMillis(5000).build(),
    context.getMainExecutor(),
    new LocationCallback() {
        @Override
        public void onLocationResult(LocationResult locationResult) {
            // 处理位置更新
        }
    });
```

### 回调投递路径

```
Provider.onReportLocation()
  → LocationProviderManager.onReportLocation()
    → LMService.handleLocationChanged()
      → 遍历匹配的 Registration
        → ILocationListener.aidl (Binder 调用)
          → App 进程 (通过 Executor 执行回调)
```

每次位置更新触发一次 Binder oneway 调用。如果 App 进程的 Executor 队列拥塞（如主线程被阻塞），oneway 调用会积压在 Binder 驱动的 buffer 中。

[已验证: AOSP android-17.0.0_r1, frameworks/base/services/core/java/com/android/server/location/LocationManagerService.java — 回调投递]

### 常见内存泄漏场景

1. **未调用 removeUpdates()**：
```java
// 错误：Activity 销毁时未取消注册
locationManager.requestLocationUpdates(..., listener);
// Activity onDestroy 未调用 locationManager.removeUpdates(listener)
```
LMService 持有 listener 的 Binder 代理，导致 Activity 无法被 GC 回收。

2. **匿名内部类隐式引用**：
```java
// 错误：匿名 LocationListener 隐式持有外部 Activity 引用
locationManager.requestLocationUpdates(...,
    new LocationListener() {
        @Override
        public void onLocationChanged(Location location) {
            updateUI(location); // 隐式持有 Activity.this
        }
    });
```

3. **正确实践**：
```java
// 使用 WeakReference 或在生命周期中显式取消
private LocationListener locationListener;

@Override
protected void onResume() {
    super.onResume();
    locationListener = new LocationListener() { ... };
    locationManager.requestLocationUpdates(request, executor, locationListener);
}

@Override
protected void onPause() {
    super.onPause();
    if (locationListener != null) {
        locationManager.removeUpdates(locationListener);
        locationListener = null;
    }
}
```

> **性能观测**：在 Perfetto 的 `Heap Profile` 中，如果看到 `LocationManager$ListenerTransport` 对象持续增长，说明存在 listener 泄漏。每个 `ListenerTransport` 对应一个未取消的注册。

## 地理围栏 (Geofence) 优化

### GeofenceManager 架构

地理围栏允许应用注册"当设备进入/离开特定圆形区域时接收通知"。Android 17 中地理围栏的架构：

```
App: LocationManager.requestLocationUpdates(geofence)
  → LMService
    → GeofenceManager (system_server)
      ├── 软件围栏: 定期位置 + 距离计算
      └── 硬件围栏: GeofenceProxy
            → IGnssGeofence.aidl (HAL)
              → GNSS 芯片硬件围栏引擎
```

[已验证: AOSP android-17.0.0_r1, frameworks/base/services/core/java/com/android/server/location/geofence/GeofenceManager.java]
[已验证: AOSP android-17.0.0_r1, hardware/interfaces/gnss/aidl/android/hardware/gnss/IGnssGeofence.aidl]

### 硬件围栏 vs 软件围栏

| 特性 | 硬件围栏 (HAL) | 软件围栏 (Framework) |
|---|---|---|
| 运行位置 | GNSS 芯片 | system_server |
| CPU 唤醒 | 仅触发时唤醒 CPU | 需要周期性唤醒 CPU 读取位置 |
| 功耗 | 极低（~0.5 mA） | 中等（依赖位置更新频率） |
| 围栏数量 | 受芯片限制（通常 ≤ 100） | 无硬性限制 |
| 精度 | 芯片级判断 | Framework 级计算 |
| 回退 | 不支持时降级为软件围栏 | 总是可用 |

### Geofence 触发算法

软件围栏的核心算法基于**空间索引 + 距离比较**：

```
for each registered geofence:
    distance = greatCircleDistance(currentLocation, geofence.center)
    
    if distance < geofence.radius - geofence.loiteringDelay:
        → ENTER transition
    elif distance > geofence.radius + hysteresisMargin:
        → EXIT transition
    else:
        → 待定区域 (loitering zone)
```

LMService 为减少不必要的计算，首先用**粗粒度空间过滤**（网格索引）排除明显不在范围的围栏，再对候选围栏做精确距离计算。

> **性能优化建议**：避免注册过多小半径围栏（< 50m）。小围栏需要更高频率的位置更新才能可靠触发，显著增加 GPS 唤醒频率。

## 扩展

### 🔸 多源定位融合算法

AOSP 的 LocationManager 本身不做多源融合——每个 Provider 独立上报。真正的融合发生在两个层面：

1. **FusedLocationProvider（GMS）**：使用 Kalman Filter 或加权平均融合 GNSS + Wi-Fi + Sensor 数据
2. **NetworkLocationService**：使用 Wi-Fi 指纹匹配 + 基站三角测量，内部融合算法由实现方（通常为 Google）决定

[待补充: FusedLocationProvider 的 Kalman Filter 参数调优细节属于 GMS 私有实现，AOSP 中无公开源码]

### 🔸 室内定位技术支持

Android SDK 不直接提供室内定位 API，但通过以下机制支持：

- `WifiManager.getScanResults()` → 获取 Wi-Fi AP RSSI，用于指纹定位
- `BluetoothAdapter.startLeScan()` / `BluetoothLeScanner` → BLE Beacon 测距
- `SensorManager` → 加速度计/陀螺仪/磁力计数据，用于 DR（Dead Reckoning）

这些数据源的融合完全由应用层实现。Android 17 没有在 framework 层引入统一的室内定位框架。

[待验证: Android 17 是否在 `packages/modules/` 下新增了室内定位相关模块]

### 🔸 轨迹平滑算法优化

位置轨迹平滑（去除 GPS 抖动）通常在应用层实现，常见算法：

- **Kalman Filter**：状态空间模型，预测 + 校正
- **Moving Average**：简单滑动窗口平均
- **Ramer-Douglas-Peucker**：轨迹抽稀（减少点数）

Android SDK 不提供内置轨迹平滑 API。

### 🔸 隐私保护定位模式

Android 12+ 引入了**粗略位置权限**（`ACCESS_COARSE_LOCATION`），允许应用获取模糊化位置：

```
精确位置 (ACCESS_FINE_LOCATION):
  → 精度 ~5m (GPS)
  → 适用于导航类应用

粗略位置 (ACCESS_COARSE_LOCATION):
  → 精度 ~3km (降采样后)
  → 适用于天气/新闻类应用
```

Android 14+ 进一步要求：同时请求 `FINE` 和 `COARSE` 时，用户可以独立授予或拒绝每个权限。应用必须处理"仅有 COARSE 权限"的场景。

[已验证: 官方文档, developer.android.com/about/versions/12/behavior-changes-12#approximate-location]
[已验证: 官方文档, developer.android.com/about/versions/14/changes/granular-media-permissions]
