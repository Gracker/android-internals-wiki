## ConnectivityManager 在 Android 架构中的角色

ConnectivityManager 是 Android SDK 暴给应用层的网络连接管理入口。应用通过它查询当前网络状态、注册网络变化回调、请求特定类型的网络连接（如 NET_CAPABILITY_INTERNET、NET_CAPABILITY_NOT_METERED），以及获取流量统计信息。

从架构角度看，ConnectivityManager 是一个轻量客户端代理，所有调用都通过 Binder IPC 进入 `system_server` 中的 ConnectivityService。这与 TelephonyManager（§1.61）的多进程分离模型不同——ConnectivityService 直接运行在 `system_server` 中，因为网络连接管理是系统级全局调度，需要与 ActivityManager、PowerManager 等紧密协同。


ConnectivityService 是整个网络子系统的"大脑"。它的核心设计原则：

1. **网络即资源**：每个物理或虚拟网络（Wi-Fi、蜂窝、VPN、以太网）在系统中以 `NetworkAgent` 表示，携带自己的能力声明（`NetworkCapabilities`）和评分（`NetworkScore`）。ConnectivityService 基于评分选择"最佳"网络作为默认路由。
2. **应用即消费者**：应用通过 `NetworkRequest` 声明所需的网络能力（如 "我需要不计费的互联网连接"），ConnectivityService 匹配最佳网络并通过回调通知应用。
3. **策略即约束**：NetworkPolicyManager 叠加后台流量限制、省流量模式、Doze 等省电策略，约束网络可用性和计费行为。

> **与 §1.61 的分工**：§1.61 聚焦 Telephony 子系统（Modem → RILJ → PhoneApp）的内部架构。本节聚焦 ConnectivityService 如何**调度和组合**多个网络提供者（包括 Telephony 数据连接、Wi-Fi、VPN），以及应用如何感知和响应网络变化。

## NetworkAgent 与网络状态机

### NetworkAgent：网络的系统级抽象

`NetworkAgent` 是 Android 网络架构中最核心的抽象。每个网络提供者（Wi-Fi、蜂窝、VPN、以太网）在 ConnectivityService 中注册一个 NetworkAgent 实例，携带以下信息：

- **NetworkCapabilities**：声明该网络的能力集（TRANSPORT_WIFI、TRANSPORT_CELLULAR、NET_CAPABILITY_INTERNET、NET_CAPABILITY_NOT_METERED 等）
- **LinkProperties**：IP 地址、DNS 服务器、路由表、MTU 等链路层信息
- **NetworkScore**：该网络的质量评分，用于与其他网络竞争

NetworkAgent 通过异步消息（`AsyncChannel`）与 ConnectivityService 通信。当底层网络状态变化时（如 Wi-Fi 信号减弱、基站切换），对应的 NetworkAgent 会主动推送状态更新。

[已验证: AOSP android-17.0.0_r1, frameworks/base/core/java/android/net/NetworkAgent.java — NetworkAgent 抽象类与 AsyncChannel 通信]

### NetworkAgentInfo：ConnectivityService 侧的状态容器

ConnectivityService 为每个注册的 NetworkAgent 维护一个 `NetworkAgentInfo` 对象，包含：

```
NetworkAgentInfo
  ├── network          // Network 对象（-netId-，用于 NDK 和 NAI 级别路由）
  ├── networkCapabilities   // 当前能力集（可被 ConnectivityService 修改）
  ├── linkProperties        // 当前链路属性
  ├── networkScore          // 当前评分
  ├── networkMonitor        // 关联的 NetworkMonitor 实例
  ├── created               // 是否已创建 netd 路由规则
  ├── validated             // 是否通过互联网验证
  ├── partialConnectivity   // 是否仅部分连通（受限网络）
  └── everValidated         // 历史是否曾验证通过
```

[已验证: AOSP android-17.0.0_r1, frameworks/base/services/core/java/com/android/server/connectivity/NetworkAgentInfo.java — 状态字段定义]

### 网络验证状态机

NetworkMonitor 是每个 NetworkAgentInfo 关联的验证器，负责判断网络是否真正可用（而非仅物理连接）。验证状态机的核心状态：

| 状态 | 含义 |
|------|------|
| `IDLE` | 初始状态，尚未开始验证 |
| `VALIDATING` | 正在探测，发送 HTTP/HTTPS 探测包到 Google 探测服务器 |
| `VALIDATED` | 验证通过，网络可用于互联网通信 |
| `PARTIAL_CONNECTIVITY` | 仅部分目标可达（如可访问 Google 但不可访问部分 CDN） |
| `CAPTIVE_PORTAL` | 检测到强制门户（需登录），需要用户操作 |
| `LOST` | 网络已断开 |

验证流程对性能的影响：
- **验证期间网络可能不可用**：在 `VALIDATING` 状态下，ConnectivityService 可能尚未将网络标记为 `validated`，应用通过 `NetworkRequest` 请求 `NET_CAPABILITY_VALIDATED` 的网络时，可能暂时无法获得满足条件的网络。
- **探测超时默认 30 秒**：如果在 30 秒内未收到探测响应，NetworkMonitor 进入 `LOST` 状态。
- **部分连通性（Partial Connectivity）**：Android 14 起增强了部分连通性检测——当探测结果显示网络可以访问 Google 服务器但不能访问某些第三方服务器时，系统会标记 `partialConnectivity = true`，应用可通过 `NetworkCapabilities.hasCapability(NET_CAPABILITY_CAPTIVE_PORTAL)` 判断。

## 网络评分与选择决策

### 评分模型

ConnectivityService 使用评分机制在多个可用网络中选择"最佳"网络作为系统默认路由。评分模型的核心：

1. **NetworkScore**：由网络提供者（Wi-Fi、蜂窝等）主动申报的初始评分（0-100）
2. **FullScore**：ConnectivityService 在初始评分基础上叠加验证奖励后的最终评分
   - `VALIDATED` 状态：+40 分奖励
   - `PARTIAL_CONNECTIVITY`：+20 分（低于验证通过）
   - `CAPTIVE_PORTAL`：不加分

```
// 评分示例（Android 17 中的典型值）
Wi-Fi (validated)        score = 60 + 40 = 100
Wi-Fi (not validated)    score = 60
Cellular (validated)     score = 50 + 40 = 90
Cellular (not validated) score = 50
VPN (over Wi-Fi)         score = parent_score  // VPN 继承底层网络评分
```

[已验证: AOSP android-17.0.0_r1, frameworks/base/services/core/java/com/android/server/ConnectivityService.java — FullScore 计算与 NetworkRanker]

### NetworkFactory 的评分竞争

每种网络类型的提供者以 `NetworkFactory` 形式注册到 ConnectivityService：

- `WifiNetworkFactory`：Wi-Fi 连接成功后创建 NetworkAgent，申报评分
- `TelephonyNetworkFactory`：蜂窝数据连接建立后创建 NetworkAgent
- `EthernetNetworkFactory`：以太网连接

当新的网络注册时，ConnectivityService 通过 `NetworkRanker` 重新评估所有匹配的 NetworkAgent，选择评分最高的作为满足特定 `NetworkRequest` 的网络。评分变化触发**全网重新计算**——如果有应用请求了 `NET_CAPABILITY_INTERNET`，当前默认网络从 Wi-Fi（score=100）切换到蜂窝（score=90）的唯一可能是 Wi-Fi 断开或评分骤降。

### 性能影响

网络切换决策本身是 `system_server` 中的内存操作（比较评分、更新路由），延迟通常 < 50ms。但**下游影响**可能显著：

- **DNS 重新解析**：默认网络切换后，DNS 服务器可能变化，正在进行的 DNS 查询可能需要重新发起
- **TCP 连接迁移**：已有 TCP 连接绑定到旧网络的 `netId`，新网络切换后旧连接可能超时断开（取决于应用是否使用 `bindProcessToNetwork()`）
- **VPN 断开重连**：如果 VPN 依赖的底层网络切换，VPN 隧道会断开并需要重新建立

## NetworkRequest 订阅模型

### 注册与回调投递

应用通过 `ConnectivityManager.registerNetworkCallback()` 注册 `NetworkRequest`，声明所需的网络能力。ConnectivityService 将该请求与所有活跃的 NetworkAgentInfo 进行匹配，并在匹配状态变化时通过 `NetworkCallback` 投递回调。

```
App.registerNetworkCallback(request, callback)
  → Binder → ConnectivityService
      → 遍历所有 NetworkAgentInfo，匹配 NetworkCapabilities
      → 匹配的网络：callback.onAvailable(network)
      → 后续状态变化：onCapabilitiesChanged / onLost / onBlocked
```

[已验证: AOSP android-17.0.0_r1, frameworks/base/services/core/java/com/android/server/ConnectivityService.java — registerNetworkCallback 与回调投递]

### 回调投递的 Binder 开销

NetworkCallback 的回调通过 Binder 投递到应用进程。每个回调调用都是一次跨进程 Binder 事务。

**性能注意点**：
- `onCapabilitiesChanged()` 在网络状态变化时**可能高频触发**——例如 Wi-Fi 信号强度变化、链路速度变化、DNS 服务器变化都会导致 capabilities 更新。在弱信号环境中（地铁、电梯），该回调可能每秒触发多次。
- 回调投递是异步的（通过 `AsyncChannel`），不会阻塞 ConnectivityService 主线程
- 但应用侧的 `NetworkCallback.onCapabilitiesChanged()` 执行在应用的 Binder 线程池中，如果应用在回调中执行耗时操作（如同步写入数据库），可能耗尽 Binder 线程池导致其他 IPC 调用阻塞

**最佳实践**：
- 在 `onCapabilitiesChanged()` 中只做轻量判断（如检查 NET_CAPABILITY_VALIDATED 是否存在），将耗时操作 post 到工作线程
- 使用 `registerDefaultNetworkCallback()`（Android 7.0+）替代手动 NetworkRequest，开销更小——它只在默认网络**变化**时触发，而非每次 capabilities 更新

[已验证: AOSP android-17.0.0_r1, frameworks/base/core/java/android/net/ConnectivityManager.java — registerDefaultNetworkCallback 注释]

## NetworkStatsService 数据采集

### 流量统计架构

NetworkStatsService 负责记录每个 UID 在每个网络接口上的流量使用量。这些数据用于：
- 流量限额警告与超量限速
- 后台流量管控（Data Saver 模式）
- 流量使用统计展示（Settings → Data Usage）

### 采集机制演进

| 时期 | 机制 | 性能特征 |
|------|------|----------|
| Android 4.x-7.x | `xt_qtaguid` 内核模块 | 读取 `/proc/net/xt_qtaguid/stats`，O(N) 遍历所有 UID |
| Android 8.x-11.x | eBPF（`cgroupskb` hook） | 内核态聚合，减少 userspace 读取开销 |
| Android 12-17 | eBPF + `bpf_skb_ctx` 增强 | 按 network interface + UID 精确聚合，支持 5G 切片统计 |

Android 17 中，NetworkStatsService 使用 eBPF map 在内核态维护 UID → 接口 → 字节数的映射。每次网络数据包发送/接收时，eBPF 程序自动更新对应 UID 的计数器。NetworkStatsService 定期（默认 30 分钟或网络切换时）从 eBPF map 中读取统计数据持久化到 SQLite 数据库。

[已验证: AOSP android-17.0.0_r1, frameworks/base/services/core/java/com/android/server/net/NetworkStatsService.java — performPollLocked 与 eBPF 读取]
[已验证: AOSP android-17.0.0_r1, system/netd/bpf_progs/ — eBPF 程序目录]

### 性能开销

- **eBPF 采集本身开销极低**：内核态的 map 更新是 O(1) 的 hash table 写入，不产生额外 IPC
- **定期持久化开销**：每 30 分钟一次的全量 poll 需要读取 eBPF map（几十微秒级），写入 SQLite（几毫秒级），在低性能设备上可能造成可感知的 I/O 峰值
- **实时查询开销**：应用调用 `NetworkStatsManager.queryDetailsForUid()` 会触发一次 Binder 调用到 NetworkStatsService，后者从 eBPF map 中读取单 UID 数据，延迟 < 10ms

> **Android 17 新增 — Data Plan Streaming API**：`NetworkStatsManager.getStreamingAppMaxDownlinkKbps()` 和 `getStreamingAppMaxUplinkKbps()` 是 Android 17 新引入的 API。它们允许应用查询运营商为流媒体应用分配的上下行速率上限。App 可据此自适应调整视频/音频流质量，避免在受限网络下请求过高码率导致卡顿。
>
> [引用: developer.android.com/about/versions/17 — Data Plan Streaming API]

## NetworkPolicyManager 策略管控

### 策略层级

NetworkPolicyManagerService（NPMS）运行在 `system_server` 中，负责根据系统策略约束网络可用性：

| 策略 | 触发条件 | 效果 |
|------|---------|------|
| **Data Saver（省流量）** | 用户手动开启或流量接近上限 | 后台应用网络受限，前台应用降速 |
| **Doze** | 屏幕关闭 + 未充电 + 静止 | 维护窗口外，几乎所有网络访问被阻塞 |
| **App Standby** | 应用长时间未使用 | 限制后台网络访问频率 |
| **Background Data Restrict** | 用户对特定应用设置 | 应用在后台时完全无法访问网络 |
| **Metered Network** | 用户标记网络为计费 | 后台大流量操作被推迟 |

[已验证: AOSP android-17.0.0_r1, frameworks/base/services/core/java/com/android/server/net/NetworkPolicyManagerService.java — 策略常量与判定逻辑]

### 与 ConnectivityManager 的联动

当 NPMS 判定某个应用的网络应被限制时，它通过 `onUidRulesChanged()` 通知 ConnectivityService。ConnectivityService 随后：
1. 更新该 UID 的网络路由规则（通过 `netd` 守护进程修改 iptables/eBPF 规则）
2. 向已注册 `NetworkCallback` 的应用投递 `onBlocked()` 回调
3. 如果应用正在使用 `bindProcessToNetwork()` 绑定到特定网络，该绑定可能失效

**性能影响**：策略变化导致的网络限制是**即时生效**的——`netd` 规则更新延迟 < 5ms。但应用感知到限制有延迟——`onBlocked()` 回调是异步投递的，应用可能在回调到达前已经发起了若干网络请求，这些请求会被内核防火墙规则静默丢弃。

## VPN 架构与性能隔离

### 平台 VPN（Platform VPN）

Android 7.0+ 引入了基于 `VpnService` 的平台 VPN API，Android 11+ 进一步增强了 IKEv2/IPsec 平台 VPN 支持。Android 17 中 VPN 架构的核心组件：

```
│  ┌──────────────────────────┐                                 │
│  │  VpnService               │ ← 建立 tun 接口、设置路由       │
│  │  PlatformVpnProfile       │ ← IKEv2 配置                   │
│  └──────────┬───────────────┘                                 │
│             │ Binder (IVpnService.aidl)                        │
└─────────────┼──────────────────────────────────────────────────┘
              │
              ▼
┌──────────────────────────────────────────────────────────────┐
│  system_server                                                 │
│  ┌──────────────────────────┐                                 │
│  │  ConnectivityService       │ ← 管理所有 VPN NetworkAgent     │
│  │   ├── Ikev2VpnRunner       │ ← IKEv2 协商与 SA 管理          │
│  │   └── Vpn (java)           │ ← tun 接口创建与路由配置         │
│  └──────────┬───────────────┘                                 │
│             │ NMS (Native)                                     │
└─────────────┼──────────────────────────────────────────────────┘
```

### VPN 性能特性

- **底层网络继承**：VPN 的 NetworkAgent 评分继承其底层传输网络（Wi-Fi/蜂窝）的评分。VPN 自身不参与评分竞争，而是在已选定的底层网络之上建立隧道。
- **加密开销**：IPsec（ESP 模式）使用内核态 `xfrm` 子系统加密，CPU 开销取决于加密算法。AES-GCM 在支持硬件加速（ARMv8 Crypto Extensions）的设备上开销 < 5%，但在不支持硬件加速的旧设备上可能达到 20-30%。
- **应用路由隔离**：VPN 可以设置 per-UID 路由规则，指定特定应用走 VPN 隧道而其他应用直连。这通过 `netd` 的 UID-based iptables 规则实现，每条规则的匹配开销在微秒级。
- **Always-on VPN**：Android 7.0+ 支持始终在线 VPN。当 VPN 意外断开时，系统会阻断所有网络流量直到 VPN 重连，这期间应用的网络请求会超时。

## Android 17 网络性能 API 变更

### 1. Data Plan Streaming API

Android 17 在 `NetworkStatsManager` 中新增了流媒体速率查询 API：

```java
// 查询运营商为流媒体应用分配的下行速率上限
long maxDownlink = statsManager.getStreamingAppMaxDownlinkKbps();
// 查询上行速率上限
long maxUplink = statsManager.getStreamingAppMaxUplinkKbps();
```

这些 API 返回的是运营商策略层面的速率上限（如果运营商支持），而非实时网络吞吐量。应用可据此预判网络质量上限，避免请求过高码率的流媒体导致不必要的缓冲等待。

**性能意义**：此 API 将"网络质量感知"从被动测量（观察吞吐量下降再降级）转变为主动查询（提前知道速率上限再选择合适码率），减少了流媒体启动阶段的码率抖动。

[引用: developer.android.com/about/versions/17 — Data Plan Streaming API]
[来源: intake/research-feeds/2026-04-08-11-android17-network-data-plan-streaming-access-local-network-tls.md]

### 2. ACCESS_LOCAL_NETWORK 权限

Android 17 引入新的普通权限 `android.permission.ACCESS_LOCAL_NETWORK`：

```xml
<!-- AndroidManifest.xml -->
<uses-permission android:name="android.permission.ACCESS_LOCAL_NETWORK" />
```

此权限要求所有通过 Wi-Fi 进行局域网通信的应用显式声明。影响范围包括：
- mDNS 服务发现（`NsdManager`）
- 局域网 HTTP 通信（如投屏、IoT 控制）
- Peer-to-Peer 连接

**性能意义**：权限检查在 `ConnectivityService` 中是一次 Binder 调用中的权限验证，开销可忽略（<1ms）。但对于未声明权限的应用，首次访问本地网络时会抛出 `SecurityException`——应用需要做防御性编程。

[引用: developer.android.com/about/versions/17/behavior-changes-17 — ACCESS_LOCAL_NETWORK]
[来源: intake/research-feeds/2026-04-08-11-android17-network-data-plan-streaming-access-local-network-tls.md]

### 3. OpenJDK 21/25 TLS 增强

Android 17 集成 OpenJDK 21 和 25 的安全更新，包括 TLS 命名组（named groups）扩展：

- 支持 X25519MLKEM768 等后量子密码学混合密钥交换
- 扩展的现代加密曲线支持
- 减少 TLS 握手往返次数（TLS 1.3 0-RTT 优化）

**性能意义**：TLS 握手往返次数减少意味着连接建立延迟降低。对于 HTTPS 请求密集型应用（如图片加载、API 轮询），TLS 优化可减少首次连接建立时间约 50-100ms（取决于网络 RTT）。

[引用: developer.android.com/about/versions/17 — TLS Enhancements]
[来源: intake/research-feeds/2026-04-08-11-android17-network-data-plan-streaming-access-local-network-tls.md]

### 4. DeliQueue 对网络回调的影响

Android 17 的无锁 MessageQueue 实现（DeliQueue，API 37 target 时生效）直接影响网络回调在主线程的投递效率。网络请求的 `onResponse`/`onFailure` 回调通过 MessageQueue 投递到主线程，减少锁等待意味着网络结果能更快地驱动 UI 更新，减少"网络完成但 UI 未及时刷新"的感知延迟。

## 性能分析要点总结

| 场景 | 关键路径 | 性能风险 | 分析工具 |
|------|---------|---------|---------|
| 网络切换 | NetworkAgent → ConnectivityService → NetworkRanker → netd 规则更新 | DNS 重解析、TCP 连接断开 | Perfetto `netd` track、`connectivity` track |
| NetworkCallback 风暴 | ConnectivityService → Binder → App Binder 线程池 | Binder 线程池耗尽、UI 卡顿 | Perfetto `binder` track、Binder Transaction 模板 |
| 网络验证探测 | NetworkMonitor → HTTP/HTTPS 探测 | 30 秒超时窗口内默认网络不可用 | Perfetto `NetworkMonitor` track |
| 后台流量限制 | NPMS → ConnectivityService → netd iptables | onBlocked 回调延迟、请求静默丢弃 | `dumpsys netpolicy`、Perfetto `netd` track |
| VPN 建立 | VpnService → ConnectivityService → Ikev2VpnRunner → xfrm | 加密 CPU 开销、始终在线阻断 | Perfetto CPU track、`ip xfrm state` |
