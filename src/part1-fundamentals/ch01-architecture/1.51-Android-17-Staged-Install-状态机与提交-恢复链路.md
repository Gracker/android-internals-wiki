# 1.51 Android 17 Staged Install 状态机与提交/恢复链路

## 要点

### 🔹 配置变更判定模型
Android 17 中 ActivityRecord#shouldRelaunchLocked() 已被重构为基于配置差分和 Shell Transitions 的新判定模型。配置变更不再立即触发全局 relaunch，而是通过 TransitionController 创建 TRANSIT_CHANGE 过渡动画实现原子性配置更新。

### 🔹 精确触发条件
新增 RELAUNCH_REASON_WINDOWING_MODE_RESIZE 和 RELAUNCH_REASON_FREE_RESIZE 两种精确触发条件，使用 deferWindowLayout/continueWindowLayout 嵌套锁避免冗余布局计算。

### 🔹 6层掩码策略
skipRelaunchConfigMask 实现7层叠加：CONFIG_RESOURCES_UNUSED 直接 return false 后，(a)~(g) 六层叠加。DisplayCompatPolicy 是双路径策略，PiP skip CONFIG_DENSITY 是显式无条件豁免。

## 状态字段表达什么

`PackageInstallerSession` 用 `mSessionReady`、`mSessionApplied` 和 `mSessionFailed` 表达 staged 结果。三个字段初始都为 false：

- ready 表示重启前验证已经通过，可以等待重启应用；
- applied 表示重启后的安装收尾成功；
- failed 表示 session 已失败。

`mDestroyed` 描述 session 生命周期和资源清理。applied、failed 或 abandon 都可能伴随 destroyed，因此它不能充当第四个 staged outcome。`isInTerminalState()` 也只检查 applied 或 failed。

## commit 到 ready 的调用顺序

installer 调用 `commit()` 后，session 还要经历 seal、通用 package verification 和 staged 专用验证。有效主线是 `PackageInstallerSession` 驱动 `PackageSessionVerifier.verifyStaged()`；`endVerification()` 在支持 filesystem checkpoint 时调用 `startCheckpoint(2)`，再设置 framework session ready，含 APEX 时随后通知 apexd ready。

`StagingManager.commitSession()` 负责登记 session 和 staged APEX observer，不执行包安装，也不负责把 APEX 激活。ready 表示 pre-reboot verification 已完成，不能解释成“安装正在进行”。

## 持久化与开机恢复是两段流程

session 变化经 `PackageInstallerService.onSessionChanged()` 和 `RequestThrottle` 异步写入 `/data/system/install_sessions.xml`，底层使用 `AtomicFile` 防止单个 XML 文件留下半写结果。这种文件替换保护没有覆盖 apexd 或 filesystem checkpoint，不能推导跨服务原子事务。

开机时，`PackageInstallerService.restoreAndApplyStagedSessionIfNeeded()` 只挑选 committed、非终态、没有 parent 的顶层 staged session。`StagingManager.restoreSessions()` 再核对 build fingerprint、checkpoint 状态和 apexd session：

- ready session 在 boot completed 前进入恢复和安装收尾；
- 尚未 ready 的 session 等到 boot completed 后重新发起 verification；
- 不支持 checkpoint 的设备不能同时恢复多个非终态顶层 staged session。

session 的 applied 状态由 `PackageInstallerSession.install()` 完成回调写入。它与 apexd activation、apexd successful 是不同阶段。

## APEX successful 与回滚边界

checkpoint 设备上，含 APEX 的 session 成功后先记录 id；到 boot completed，`markStagedSessionsAsSuccessful()` 遍历这些 id，并逐个调用 `markStagedSessionSuccessful()`。这是启动完成后的成功确认，不是批量激活，也不是一次合并 RPC。

失败处理取决于设备能力和 session 内容。checkpoint 路径可以调用 StorageManager 的 `abortChanges()`；非 checkpoint 的 APK-only session 与含 APEX session 处理不同，后者还可能请求 apexd revert 并重启。不能把所有 staged failure 归入同一条 reboot 或 rollback 路径。
