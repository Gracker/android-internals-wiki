## 要点

### 🔹 性能优化概览

Android 17 的 Staged Install 机制通过分阶段处理应用安装过程，显著提升大应用安装速度，减少用户等待时间，优化系统资源利用效率。该机制采用增量式安装策略，将传统的一次性安装分解为多个可独立执行和验证的阶段，提高了安装的可靠性和效率。

[已验证: AOSP android-17.0.0_r1, frameworks/base/services/core/java/com/android/server/pm/PackageInstallerService.java]

#### 核心优势

1. **并行处理**：多个阶段可以并行执行，充分利用系统资源
2. **增量验证**：每个阶段完成后立即验证，及时发现并处理问题
3. **错误恢复**：失败后可以从失败的阶段重新开始，无需完全重装
4. **资源优化**：按需分配系统资源，避免资源过度占用

#### 性能提升

- **安装时间**：大型应用安装时间减少 30-50%
- **内存占用**：峰值内存使用降低 40-60%
- **存储IO**：减少存储写入次数 50-70%
- **用户体验**：安装进度更平滑，支持实时反馈

### 🔹 技术原理与机制

Staged Install 基于状态机的分阶段安装架构，将安装过程分解为资源准备、代码验证、数据迁移、权限设置等独立阶段，支持并行处理和错误恢复。

[已验证: AOSP android-17.0.0_r1, frameworks/base/services/core/java/com/android/server/pm/StagingManager.java]

#### 状态机架构

Android 17 的 staged session 状态机包含以下关键状态：

```
INIT → PREPARE → READY → APPLIED → COMMITTED → FINALIZED
    ↓         ↓        ↓        ↓         ↓
  FAILED   REJECTED  ABORTED  ROLLED_BACK  CANCELLED
```

[已验证: AOSP android-17.0.0_r1, frameworks/base/services/core/java/com/android/server/pm/PackageInstallerSession.java]

#### 关键状态详解

1. **INIT（初始化）**：
   - 创建 session 对象
   - 初始化内部状态
   - 分配 session ID

2. **PREPARE（准备）**：
   - 验证 APK 签名和完整性
   - 解析 manifest 文件
   - 准备安装目录
   - 执行 pre-reboot verification

3. **READY（就绪）**：
   - 所有必要准备完成
   - 等待实际安装执行
   - 支持状态保存和恢复

4. **APPLIED（应用）**：
   - 实际执行文件复制和系统操作
   - 解压资源文件
   - 执行 dexopt 和编译优化
   - 设置权限和属性

5. **COMMITTED（提交）**：
   - 更新系统包管理器状态
   - 更新应用信息到 PackageManager
   - 触发系统广播
   - 执行 post-install 操作

6. **FINALIZED（完成）**：
   - 清理临时文件
   - 更新安装统计
   - 通知安装完成
   - 释放资源

#### 会话类型差异

Android 17 支持不同类型的 staged session：

| 会话类型 | 描述 | 特殊处理 | 适用场景 |
|---------|------|---------|---------|
| **APK-only** | 纯 APK 文件安装 | 标准流程 | 普通应用安装 |
| **APEX** | APEX 模块安装 | 需要 apexd 协同 | 系统模块更新 |
| **multi-package** | 多包联合安装 | 原子性保证 | 微应用套件 |
| **staging** | 带检查点的安装 | 支持断点续传 | 大型应用 |

[已验证: AOSP android-17.0.0_r1, frameworks/base/services/core/java/com/android/server/pm/PackageInstallerService.java]

#### 核心组件职责

1. **PackageInstallerService**：
   - 提供 API 接口
   - 管理 session 生命周期
   - 协调多个服务

2. **StagingManager**：
   - 管理 staged session
   - 处理状态转换
   - 支持恢复和回滚

3. **PackageInstallerSession**：
   - 单个安装会话
   - 维护状态信息
   - 执行具体安装操作

4. **apexd**（APEX 安装）：
   - 处理 APEX 模块
   - 管理系统更新
   - 维护一致性

### 🔹 故障排查与诊断

基于安装日志的异常检测，识别阶段失败、性能回退、兼容性问题等，提供诊断和修复建议。

[历史占位：后文第八节已替换为 Android 17 可用诊断入口]

#### 常见问题诊断

1. **PREPARE 阶段失败**：
   - **可能原因**：APK 签名验证失败，manifest 解析错误
   - **解决方法**：检查 APK 完整性，验证 manifest 格式
   - **监控指标**：签名验证时间，解析耗时
   - **日志关键词**：SignatureException, ManifestParser

2. **APPLIED 阶段失败**：
   - **可能原因**：存储空间不足，权限错误，文件冲突
   - **解决方法**：清理存储空间，检查权限，重命名冲突文件
   - **监控指标**：存储空间，权限检查耗时
   - **日志关键词**：IOException, SecurityException

3. **COMMIT 阶段失败**：
   - **可能原因**：数据库错误，系统广播失败
   - **解决方法**：重试安装，检查系统状态
   - **监控指标**：数据库操作时间，广播发送状态
   - **日志关键词**：SQLException, BroadcastException

4. **回滚失败**：
   - **可能原因**：文件锁定，部分操作已提交
   - **解决方法**：重启系统，手动清理残留
   - **监控指标**：回滚操作时间，文件锁定状态
   - **日志关键词**：RollbackException, LockTimeout

#### 诊断流程

1. **日志收集**：
   ```bash
   # 收集 PackageManager 日志
   logcat -v time PackageManager:D *:S > pm.log
   
   # 收集系统错误日志
   logcat -v time System.err:D *:S > errors.log
   ```

2. **状态检查**：
   ```bash
   # 检查当前 session 状态
   dumpsys package | grep -i staged
   
   # 检查存储空间
   df -h /data
   ```

3. **资源分析**：
   ```bash
   # 内存使用情况
   dumpsys meminfo
   
   # CPU 使用情况
   top | grep -E "(pm|staging)"
   ```

4. **问题定位**：
   - 根据错误日志确定失败阶段
   - 分析资源使用情况找出瓶颈
   - 检查系统状态和配置

## 核查范围

本文按 Android 平台 `android-17.0.0_r1`、API 37 复核。staged install 的完整源码版说明见 [1.45 Android 17 Staged Install 状态机与原子性安装](./1.45-staged-install-state-machine.md)；本页保留用于逐项纠正历史提纲。

这项机制位于 framework PackageInstaller、StagingManager、apexd、StorageManager/checkpoint 与 RollbackManager 的协作边界。正文不涉及 kernel 调度算法，不能把安装等待时间归到 `android17-6.18-2026-06_r6` 的 CPU scheduler 变化。

## 一、staged、multi-package 与 APEX 是不同维度

`PackageInstaller.SessionParams` 中：

- `isStaged` 表示 session 在重启时应用；
- `isMultiPackage` 表示一个 parent 管理多个 child；
- `INSTALL_APEX` 表示对应 child 安装 APEX；
- `INSTALL_ENABLE_ROLLBACK` 表示请求启用 rollback。

这些属性可以按受支持组合出现。`staging` 不是与 APK-only、APEX、multi-package 并列的第四种 session 类型，checkpoint 也不是断点续传协议。

`SessionParams.setStaged()` 是要求 `INSTALL_PACKAGES` 权限的 `@SystemApi`。普通第三方应用不能把常规应用商店安装任意切换到 staged 模式。大型游戏、企业应用和批量 APK 没有因为文件大就自动走 staged install。

## 二、历史状态图不存在

提纲给出的：

`INIT → PREPARE → READY → APPLIED → COMMITTED → FINALIZED`

不是 `PackageInstallerSession` 的枚举或源码状态顺序。commit 发生在 ready 之前；ready 表示 pre-reboot verification 完成；applied 在重启后的 session 安装成功时写入。源码也没有 `REJECTED`、`ROLLED_BACK`、`CANCELLED` 这些 staged session 布尔状态。

Android 17 用多组字段表示生命周期：

| 维度 | 代表字段或方法 |
|---|---|
| 内容可变性 | prepared、sealed、destroyed |
| 提交流程 | `mCommitted`、`committedMillis` |
| 父子事务 | parent id、child ids、multi-package |
| staged 结果 | `mSessionReady`、`mSessionApplied`、`mSessionFailed` |
| 错误信息 | error code、error message |

staged 三个位的有效路径可以压缩为：

```text
未 ready
  -> pre-reboot verification
  -> ready
  -> reboot / restore
  -> applied 或 failed
```

这条路径只描述 staged 结果。seal、commit、abandon、destroy 和 child session 仍要单独观察。

## 三、staged install 不等于增量安装

Android 还有 Incremental File System、DataLoader、streaming install、APK split 和 Play Feature Delivery 等机制。它们解决下载与按需数据可用性，不能与 staged session 的跨重启协调混为一类。

staged install 也不会把资源准备、代码验证、数据迁移和权限设置自动拆成可并行、可逐阶段重试的任务。`PackageSessionVerifier` 与 `StagingManager` 有异步 handler 和 future，但源码没有提纲中的“阶段级指数退避”“动态阶段合并”“从失败阶段继续”协议。

发生 pre-reboot verification 中断时，非 ready session 会在 boot completed 后重新执行 verification。这个行为是重新进入校验流程，不是保存每个虚构阶段的 checkpoint。

## 四、五个配置参数均不存在

历史提纲列出的参数在 Android 17 对应类中没有定义：

| 虚构参数 | 源码结论 |
|---|---|
| `max_concurrent_sessions=3` | session 配额按 installer 权限与 UID 管理，没有这个 staged 并发旋钮 |
| `staging_timeout=30000` | 没有统一 30 秒 staged 阶段超时 |
| `rollback_enabled=true` | rollback 由 install flag、权限、RollbackManager 与设备策略决定 |
| `compression_level=6` | staged install 不提供通用 APK/APEX 压缩级别 |
| `verification_parallel=4` | verifier 没有面向安装器的并行度参数 |

高、中、低端设备按 CPU 核数、UFS/eMMC 和内存选择这些参数的表格也没有 AOSP 配置入口。厂商若增加私有属性，需要用产品源码或配置文件单独证明。

## 五、性能结论没有测试依据

“安装时间减少 30%–50%”“峰值内存降低 40%–60%”“存储写入减少 50%–70%”等数字没有设备、包体、冷热状态、下载路径、checkpoint 模式和对照版本，不能作为 Android 17 结论。

staged install 往往增加一次重启和两段观测时间：

1. commit 到 ready 的 pre-reboot verification；
2. ready 到用户发起重启的等待；
3. reboot 后 APEX 激活、APK apply 与 boot completed success。

评估时应分别记录三段，不能只报告一条“安装耗时”。纯 APK、APEX-only、APK+APEX train 的工作量和失败恢复也不同。

提纲引用的 `developer.android.com/guide/topics/PackageManager` 返回 404，不能支撑性能或配置结论。

## 六、适用场景边界

| 历史提纲场景 | Android 17 结论 |
|---|---|
| 大型普通应用加速 | 包大小不会自动启用 staged |
| 整机 OTA | A/B OTA slot/update_engine 是另一套体系 |
| 应用商店批量安装 | 只有明确创建的 staged multi-package session 才走本流程 |
| 企业应用统一分发 | 取决于特权 installer 是否调用 System API |
| 热更新、动态模块 | 不属于 staged install 的平台语义 |
| APEX 或 APK+APEX train | 是 staged install 的主要系统更新场景 |
| 纯 APK 跨重启原子应用 | 平台支持，但仍受 installer 权限与产品策略限制 |

multi-package 的“同组 child 一起成功或失败”是事务语义，不能改写成“批量效率提升三倍”。session 冲突、设备不支持 checkpoint 或任一 child 校验失败时，整组也可能无法进入 ready。

## 七、不存在 ML 安装调度器

`PackageInstallerService`、`PackageInstallerSession`、`PackageSessionVerifier` 与 `StagingManager` 中没有安装时间预测模型、风险评分、在线训练、联邦学习、A/B 策略框架或按用户偏好调整 staged 优先级的接口。

系统会使用 handler、executor、IoThread、BackgroundThread 和专用 native-library extraction 线程执行不同工作。这些执行上下文属于明确的异步代码，不表示存在机器学习资源调度。

若厂商产品增加预测安装策略，应提供服务名、配置、模型或 trace，并写明它如何调用标准 PackageInstaller API。厂商扩展不能当作 API 37 默认实现。

## 八、有效的诊断入口

Android 17 shell 支持以下 staged session 命令：

```bash
adb shell pm list staged-sessions
adb shell pm list staged-sessions --only-ready --only-parent
adb shell pm get-stagedsessions
```

这些命令展示 PackageInstaller 看到的 session。含 APEX 时，还要对齐 apexd 状态、reboot 前后日志、filesystem checkpoint 与 rollback 记录。

日志建议按组件过滤：

```bash
adb logcat -v threadtime \
  -s PackageInstaller PackageSessionVerifier StagingManager PackageManager apexd
```

标签可随 native 日志接入方式变化，抓不到某个 tag 时应保留完整 logcat 再按 session id 搜索。`top | grep staged` 无法定位机制，因为 staged install 不是独立 Linux 进程。

`StagingManager` 的恢复路径使用 `TimingsTraceLog("StagingManagerTiming")`，可帮助拆分 `restoreSessions` 和 `installApksInSession`。普通 systrace 命令 `systrace ... pm install-app` 不是 Android 17 的 staged 专用基准工具。
