# 1.55 Android 17 VNDK 隔离与原生库加载性能影响


## 一、Android 17 的 VNDK 边界

VNDK 从 Android 15 开始弃用。`vendor` 或 `product` 分区面向 Android 15 及以上版本构建时，原 VNDK 库与其他可用库一样安装到对应分区，不再生成当前版本的 VNDK APEX，`ro.vndk.version` 与 `ro.product.vndk.version` 也被移除。

两类兼容边界仍要保留：

- VNDK 版本 14 及以下的 APEX 继续用于支持旧 `vendor` 镜像；
- LL-NDK 不属于 VNDK，稳定 ABI 仍用于 `system`/`vendor` 边界。

因此，Android 17 新设备的库隔离不能继续描述为“当前 VNDK APEX 执行五级检查”。VNDK 的历史版本兼容、Soong 的 `vendor` 变体规则、动态链接器命名空间和 SELinux 是相邻机制，生命周期不同。

### “自包含 HAL”不是新的链接器模式

旧 VNDK 文档要求 VNDK-SP 及 SP-HAL 依赖集合满足自包含约束，避免框架进程加载 `vendor` HAL 时跨越不允许的库边界。Android 17 的 bionic 中没有名为“自包含 HAL”的新命名空间类型、`dlopen()` 标志或预加载调度器。

把 HAL 及依赖放在 `vendor`/`product` 侧，是构建与部署约束。静态链接多少库、是否采用 AIDL HAL、哪些库由 LL-NDK 提供，要由模块定义、稳定接口要求和升级边界决定。它不会自动减少动态库数量，也没有平台承诺的启动收益。

## 二、链接器命名空间仍是运行时隔离基础

Android 11 起，`linkerconfig` 根据分区、已安装 APEX、公开库和运行时环境生成 `/linkerconfig/ld.config.txt` 及相关配置。动态链接器读取配置后，为进程建立默认、APEX、`vendor`、SP-HAL 等所需命名空间，并用命名空间链接声明可跨边界访问的 soname。

一个进程可以有多个命名空间。每个命名空间保存自己的搜索路径、许可路径、允许库名和到其他命名空间的链接。跨命名空间的库查找只会沿配置好的链接继续，且通常受共享库 soname 集合限制。

应用的类加载器命名空间还会经 `libnativeloader` 创建。系统原生进程、应用 JNI、APEX 进程和 `vendor` 守护进程的命名空间图不同，不能从一个进程的 `LD_LIBRARY_PATH` 推断整台设备的库可见性。

## 三、`is_accessible()` 的准确语义

`android_namespace_t::is_accessible(path)` 是通用的隔离命名空间检查，不是 VNDK 专用算法。下面的代码省略日志和局部变量，只保留 Android 17 的判断方向：

```cpp
if (!is_isolated_) {
    return true;
}
if (!allowed_libs_.empty()) {
    const char* name = basename(file.c_str());
    if (std::find(allowed_libs_.begin(), allowed_libs_.end(), name)
            == allowed_libs_.end()) {
        return false;
    }
}
for (const auto& dir : ld_library_paths_) {
    if (file_is_in_dir(file, dir)) return true;
}
for (const auto& dir : default_library_paths_) {
    if (file_is_in_dir(file, dir)) return true;
}
for (const auto& dir : permitted_paths_) {
    if (file_is_under_dir(file, dir)) return true;
}
return false;
```

这段摘录展示了早返回、库名限制与三组路径检查的先后关系。`ld_library_paths_` 与 `default_library_paths_` 使用 `file_is_in_dir()`，只接受目录的直接子项；`permitted_paths_` 使用 `file_is_under_dir()`，允许更深层路径。

`allowed_libs_` 的实现类型是 `std::vector<std::string>`，检查使用 `std::find()`。“哈希表平均 O(1)”与源码不符。它也不是独立的动态允许列表服务；配置在命名空间建立时写入对象。

正常按路径加载时，链接器先解析候选文件并取得真实路径，再执行命名空间可访问性检查。文件 DAC 权限、挂载选项和 SELinux 仍由各自层次处理；`permitted_paths_` 不会递归验证每级父目录权限，也不能替代 SELinux。

### 搜索路径和许可路径回答不同问题

`ld_library_paths_` 与 `default_library_paths_` 参与按 soname 搜索。`permitted_paths_` 允许隔离命名空间通过绝对路径访问额外目录，但不会自动把目录加入 soname 搜索顺序。把路径加入许可列表，不等于 `dlopen("libfoo.so")` 会从那里找到库。

`LD_LIBRARY_PATH` 只在非安全执行环境读取，并作用于默认命名空间的对应搜索路径。Android 17 bionic 没有名为 `LOADER_PATH` 的同类环境变量。系统进程和应用还受启动环境、命名空间配置与公开库规则限制。

## 四、符号可见性怎样限制

库文件能够装入某个命名空间，只完成了路径层检查。重定位与 `dlsym()` 还受下面几组范围影响：

- 本命名空间的全局组与局部依赖组；
- 共享/次级命名空间成员关系；
- 命名空间链接是否允许该 soname；
- ELF 可见性、版本脚本、`RTLD_LOCAL`、`RTLD_GLOBAL` 与 `DF_1_GLOBAL`；
- 目标库的 `DT_NEEDED` 依赖能否继续解析。

同名库可以分别存在于不同命名空间，减少框架层/`vendor` 或 APEX 之间的符号串扰。命名空间也允许显式导出少量稳定库。`dlopen()` 和 `dlsym()` 仍是 bionic API，没有额外的“安全包装器”自动解决 ABI 不兼容或对象跨版本传递问题。

## 五、`dlopen()` 时间花在哪里

一次冷 `dlopen()` 可能包含：

1. soname 与命名空间链接搜索；
2. 路径解析、`open()`、ELF 程序头校验；
3. 段映射与按需缺页；
4. `DT_NEEDED` 依赖图遍历；
5. GNU/SysV 哈希符号查找与重定位；
6. RELRO、TLS、MTE 等装载属性处理；
7. C/C++ 构造函数。

命名空间的允许列表和路径检查只是其中一段。库大小、依赖数量、重定位数量、存储冷热状态、页大小、构造函数工作和设备 I/O 都会改变总耗时。AOSP 没有“VNDK 检查固定增加 15–25%”的结论，未给出工作负载与测量方法的百分比不能写进容量预算。

已经装入且可复用的库，后续 `dlopen()` 可能命中已有 `soinfo`；冷启动、首次缺页和构造函数成本不会按相同比例重复。跨命名空间需要装入另一份库时，映射、重定位和私有脏页可能增加。是否共享物理文件页还取决于加载的是同一 inode 还是不同分区中的不同副本。

Android 17 链接器是原生 C++ 实现，没有 JIT 编译访问检查，也没有基于 AI 的库访问预测。平台同样没有通用异步 `dlopen()` API；业务可以把允许后台执行的加载放到工作线程，但构造函数、JNI 注册和调用方线程约束仍要自行验证。

## 六、如何测量加载性能

bionic 为 `dlopen()`、加载/链接、构造函数、`dlsym()` 和 `dlclose()` 建立跟踪区间。Perfetto 中应把这些区间与文件系统 I/O、缺页、CPU 调度和应用启动阶段对齐，避免把整个加载窗口都归因于命名空间。

链接器日志支持 `dlopen`、`dlsym` 和 `dlerror` 三类选项。下面的命令只适合可调试进程，并应在复现结束后清除属性：

```bash
adb shell setprop debug.ld.app.com.example.app dlopen,dlsym,dlerror
adb logcat -s linker:D
adb shell setprop debug.ld.app.com.example.app ''
```

属性名使用进程基本名，带冒号的服务进程会截断冒号及其后缀。不可转储的进程不会启用这组日志；用户版本、权限与产品策略也可能限制设置属性。

设备上的命名空间图应直接查看生成结果：

```bash
adb shell cat /linkerconfig/ld.config.txt
adb shell find /linkerconfig -maxdepth 3 -name ld.config.txt -print
```

这些文件反映设备当前分区与 APEX 组合，比套用历史 `ld.config.vndk_lite.txt` 模板可靠。读取权限和路径会随构建类型变化，脚本需要处理文件不可访问的情况。

性能实验至少区分冷/热文件页、首次/重复加载、相同/不同命名空间，并记录库及依赖的构建 ID。报告中应给出 P50/P95、CPU 时间、经过时间、主要/次要缺页、重定位与构造函数区间；只报告一次 `dlopen()` 经过时间无法说明隔离开销。

## 七、Android 17 排障顺序

遇到 `dlopen failed` 时，可按错误信息依次确认：

1. 请求从哪个命名空间发起，调用方属于哪个类加载器/APEX/`vendor` 进程；
2. soname 是否在当前命名空间的搜索路径或已链接命名空间的允许列表中；
3. 绝对路径是否通过允许库与许可路径检查；
4. `DT_NEEDED` 中是否存在跨分区私有依赖；
5. ELF 类别、ABI、页大小对齐、符号版本和重定位是否兼容；
6. 文件权限、SELinux 拒绝记录、分区挂载和 APEX 激活状态；
7. 库是否带有耗时或有线程约束的构造函数。

错误信息中的 “not accessible for the namespace” 属于链接器命名空间边界；“library not found” 也可能来自依赖库；“cannot locate symbol” 已进入符号解析阶段。三者需要不同修复，扩宽 `permitted_paths_` 不会修复缺失符号或 ABI 不兼容。

## 九、版本范围

版本边界固定为 Android 17/API 37 与 `android-17.0.0_r1`。Android 17 的链接器命名空间、VNDK 弃用说明和 Perfetto/链接器日志行为不能外推为后续平台能力。
