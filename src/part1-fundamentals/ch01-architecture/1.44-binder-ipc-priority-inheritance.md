# 1.44 Android 17 Binder IPC 优先级继承与内核批处理流水线

本文以 Android 平台 `android-17.0.0_r1`、API 37 和 Android common kernel `android17-6.18-2026-06_r6` 为准，解释三条容易互相干扰的路径：

- `IPCThreadState` 怎样把 BC 命令送进驱动并读取 BR 命令；
- 驱动选中目标线程后，怎样计算、设置和恢复调度优先级；
- 目标进程冻结时，`TF_UPDATE_TXN` 怎样替换尚未执行的 oneway。

这里的“批处理”指用户态命令 Parcel 与驱动 read buffer 可以各自携带多个命令。它不提供跨 write/read 的数据库式原子提交，也不保证一次业务调用固定只产生一到两次 ioctl。

## 一、一次 `BINDER_WRITE_READ` 做了什么

### 1. 用户态准备两个命令缓冲区

每个 native Binder 线程都有自己的 `IPCThreadState`。`mOut` 保存待发送的 `BC_*` 命令，`mIn` 保存驱动返回的 `BR_*` 命令。构造函数只把两者的初始容量设为 256 字节；Parcel 可以增长，因此 256 不是命令数上限，更不是 transaction buffer 大小。

`talkWithDriver()` 根据当前状态填写 `binder_write_read`：

- `write_size` / `write_buffer` 指向 `mOut`；
- `read_size` / `read_buffer` 在需要读取时指向 `mIn`；
- `write_consumed` / `read_consumed` 由驱动回填。

对应的 ioctl 调用可以概括为：

```cpp
binder_write_read bwr = prepareFrom(mOut, mIn);
ioctl(driverFd, BINDER_WRITE_READ, &bwr);
consumeWrittenCommands(bwr.write_consumed);
publishReadCommands(bwr.read_consumed);
```

上面是调用关系的简化表示，不是可直接编译的 libbinder 代码。Android 17 的实现还会在 `EINTR` 时重试，并在写入未被完整消费时触发致命检查。

### 2. 驱动先处理 write，再处理 read

`binder_ioctl_write_read()` 在 `write_size > 0` 时调用 `binder_thread_write()`，成功后才在 `read_size > 0` 时调用 `binder_thread_read()`。这个顺序让一次 ioctl 可以同时提交命令并等待返回数据。

write 和 read 没有被一个覆盖整段调用的 `proc->inner_lock` 包住。两段内部按各自对象与队列获取锁，read 还可能等待工作。其他线程和其他进程可以在其间运行，所以“同一 ioctl”不能解释为“所有 BC 命令与 BR 结果不可被并发观察”。

错误发生在 write 阶段时，驱动把 `read_consumed` 设为 0 并退出；read 阶段错误也会经 `binder_write_read` 返回。用户态必须按 consumed 字段和返回值处理，不能假设两个方向同时成功。

### 3. BR 命令批量受字节容量限制

`binder_thread_read()` 会从目标线程或进程的 todo 队列取工作，并把一个或多个 BR 命令写入调用方提供的 read buffer。不同命令长度不同：简单 completion 只有命令字，transaction 还带 `binder_transaction_data`。

驱动每次写入前都检查剩余字节数。源码没有“最多 128 条”的固定常量；可返回数量取决于 read buffer 容量、命令种类、是否需要等待以及当前 todo 内容。初始 256 字节也不能直接除出业务调用数，因为同一 `mIn` 中还可能出现引用计数、死亡通知和 looper 管理命令。

### 4. 同步调用的 ioctl 次数不固定

`waitForResponse()` 循环调用 `talkWithDriver()`，直到看到 `BR_REPLY`、`BR_DEAD_REPLY`、`BR_FAILED_REPLY` 等终止条件。循环中还会处理 `BR_TRANSACTION_COMPLETE`、引用计数命令，以及当前线程收到的嵌套事务。

同步调用可能在一个 ioctl 中完成写入并读到回复，也可能经历多个阻塞与返回。服务端执行时间、信号中断、嵌套调用和 read buffer 内容都会改变次数。

`flushCommands()` 最多直接调用两次 `talkWithDriver(false)`：第一次写命令后，post-write 引用计数处理可能又生成 `BC_RELEASE` 或 `BC_DECREFS`，此时再写一次。它只描述显式 flush 的收尾逻辑，不能用来证明每笔 Binder 业务固定产生两次 syscall。

## 二、事务优先级的输入来自哪里

### 1. 同步调用才可能继承发送线程

创建 `binder_transaction` 时，driver 按下面的规则选择初始值：

| 事务条件 | `t->priority` 来源 |
|---|---|
| 同步，发送线程 policy 受 Binder 支持 | 发送线程的 `current->policy` 与 `current->prio` |
| oneway | 目标进程 `default_priority` |
| 同步，但发送线程 policy 不受支持 | 目标进程 `default_priority` |

Binder 支持 `SCHED_NORMAL`、`SCHED_BATCH`、`SCHED_FIFO` 和 `SCHED_RR`。`SCHED_IDLE`、`SCHED_DEADLINE` 等策略不会沿事务传递。目标进程打开 Binder 设备时，如果自身 policy 也不受支持，默认值回退为 `SCHED_NORMAL`、nice 0。

oneway 不继承调用线程优先级，但目标 Binder node 的最低调度策略仍会参与后续计算。把“oneway 不继承 caller”写成“oneway 永远按 nice 0 执行”同样不准确。

### 2. node 可以声明最低策略与 RT 继承

native `BBinder` 提供 `setMinSchedulerPolicy()`、`setInheritRt()` 和进程级 `setGlobalInheritRt()`。这些值必须在 Binder object 发送到其他进程前配置，随后通过 flat Binder object flags 进入内核 node：

- `sched_policy` 与 `min_priority` 给出该 node 的最低处理优先级；
- `inherit_rt` 决定调用方的 `SCHED_FIFO` / `SCHED_RR` 是否允许传入。

Android 17 native libbinder 的全局 RT 继承默认值是 `false`，单个 BBinder 或进程可以在 parcel 之前改写。因而“所有 node 永远禁止 RT”与“RT 会自动继承”都不成立，判断时要看具体 Binder object 的 flags。

## 三、目标线程的期望优先级怎样计算

`binder_transaction_priority()` 从事务候选值开始，按两步收敛：

1. 候选值是 RT policy 且 `node->inherit_rt == false` 时，改为 `SCHED_NORMAL`、nice 0；
2. node 的 `min_priority` 数值更小、调度优先级更高时，选择 node 值；数值相同且 node 使用 `SCHED_FIFO` 时也选择 node 值。

这里的 `min_priority` 是最低保障。kernel priority 数值越小，调度优先级越高，所以分支选择的是更高的有效优先级，不是“更保守、更低的优先级”。

随后，`binder_set_priority()` 以 `verify=true` 调用统一设置函数。没有 `CAP_SYS_NICE` 时：

- RT policy 受 `RLIMIT_RTPRIO` 限制；
- 无 RT 额度时先回退到 `SCHED_NORMAL`；
- fair policy 的 nice 值还要继续受 `RLIMIT_NICE` 限制。

源码中的回退临时写入 `MIN_NICE`，后续 fair-policy 校验仍可能把它夹到调用线程允许的 nice 范围。不能把中间变量写成“最终一定得到 nice -20”。

线程已经处于相同 policy/prio 时，`binder_do_set_priority()` 只更新 `prio_state` 后返回。一次 Binder 优先级处理不等于一次 `sched_setscheduler_nocheck()`；固定的系统调用次数和纳秒收益都需要 trace，不能从分支数量推算。

## 四、`set_priority_called` 的边界

`set_priority_called` 位于 `struct binder_transaction`，入口守卫是：

```c
if (t->set_priority_called)
    return;
t->set_priority_called = true;
```

它防止同一个 transaction 对象重复执行 `binder_transaction_priority()`。每次嵌套同步调用都会创建新的 transaction，分别保存目标 node、候选优先级和 `saved_priority`。

因此，该字段不会把多层 Binder 调用压缩成一次优先级设置，也不保证四层调用只获取一次 `prio_lock`。嵌套深度、目标线程是否已经处于期望值、policy 是否变化，都会影响设置与恢复路径。

## 五、三态机保护的是恢复竞态

### 1. 状态只有 `SET`、`PENDING`、`ABORT`

Android 17 kernel r6 的枚举没有 `IDLE`：

- `BINDER_PRIO_SET`：优先级设置路径已经稳定；
- `BINDER_PRIO_PENDING`：嵌套事务回复前，线程准备恢复到 `prio_next`；
- `BINDER_PRIO_ABORT`：新事务在恢复窗口进入，旧恢复必须退出。

`prio_lock` 保护 `prio_state` 与 `prio_next`。每笔事务的 `saved_priority` 则保存该事务结束时要恢复的 policy/prio。

### 2. 普通设置和恢复

目标线程接受事务时，`binder_transaction_priority()` 在非 `PENDING` 状态下保存线程当前的 `task->policy` 与 `task->normal_prio`，随后应用事务期望值。

事务回复或失败时，驱动把 `saved_priority` 传给 `binder_restore_priority()`。恢复调用使用 `verify=false`：旧值来自驱动先前保存的线程状态，无需重新按 caller rlimit 限制；同时，这个标志启用 `ABORT` 检查。

### 3. 嵌套回复与新事务竞态

嵌套同步事务回复时，驱动执行以下时序：

1. 把目标 Binder 线程的 `prio_state` 设为 `PENDING`；
2. 把当前事务的 `saved_priority` 写入 `prio_next`；
3. 唤醒等待回复的线程；
4. 调用 `binder_restore_priority()`。

如果新的 incoming transaction 在第 1 步与第 4 步之间选中同一线程，新事务的优先级入口会看到 `PENDING`。它把自己的 `saved_priority` 设为 `prio_next`，再把线程状态改为 `ABORT`。

旧恢复随后发现 `verify == false && prio_state == BINDER_PRIO_ABORT`，便放弃写回旧值。新事务继续设置自己的期望优先级，并在结束时恢复到刚才继承的 `prio_next`。这样可避免已经过期的 restore 覆盖新事务。

`ABORT` 保留的是新事务处理资格；它不表示“内层结束后永久保留外层优先级”。事务栈继续用各自的 `saved_priority` 维持后续恢复顺序。

## 六、等待线程选择是 LIFO，不是 FIFO

Binder 线程准备等待进程级工作时，kernel r6 调用 `list_add()` 把 `waiting_thread_node` 插到 `proc->waiting_threads` 表头。选择函数再从表头取第一个元素：

```c
list_add(&thread->waiting_thread_node, &proc->waiting_threads);
thread = list_first_entry_or_null(&proc->waiting_threads,
        struct binder_thread, waiting_thread_node);
```

这组操作优先取得最近加入等待链表的线程，行为接近 LIFO。它没有按 nice、RT priority、历史服务时长或 CPU 负载排序。

若找到等待线程，`binder_proc_transaction()` 会先为它处理事务优先级，再把 work 放入该线程 todo，之后调用 wakeup。找不到普通 waiter 时，事务进入进程 todo；使用 poll 接口且可处理进程工作线程可能被统一唤醒。

`wake_up_interruptible_sync()` 中的 `sync` 是 scheduler wakeup hint。它不让发送线程自旋等到服务线程进入运行态，也不保证服务线程立即抢占当前 CPU。同步 Binder 的业务等待发生在调用方等待 reply 的路径上，不能从 wake 函数名推导出一个额外握手。

## 七、`TF_UPDATE_TXN` 不负责缓冲区溢出恢复

### 1. 新事务先完成 buffer 分配

`binder_transaction()` 在进入 `binder_proc_transaction()` 前，已经为新事务在目标 `binder_alloc` 中分配并填充 buffer。若这一步因为连续空间、async 预算或页面安装失败而退出，后面的 update 逻辑没有执行机会。

所以，`TF_UPDATE_TXN` 不能在新事务 `-ENOSPC` 后删除旧事务再重试，也不是同步/异步“完全不同的溢出恢复策略”。容量与 oneway spam 机制见 [Binder 4 MiB 映射上限、异步预算与优先级状态](./1.44-android17-binder-sz4m-kernel-buffer-pool.md)。

### 2. 替换需要同时满足多项条件

替换分支只在以下条件同时满足时执行：

- 新事务带 `TF_ONE_WAY | TF_UPDATE_TXN`；
- 目标进程处于 frozen 状态；
- 同一 node 已有正在执行的 oneway，故新事务准备进入 `node->async_todo`；
- 待替换事务与新事务的目标进程、transaction code、完整 flags、发送 PID、node ptr/cookie 一致。

驱动在 `node->async_todo` 找到第一个匹配项后把它移出队列，先入队新事务，再在释放锁后释放旧 transaction 与 buffer。这是冻结期间丢弃可覆盖旧状态的队列语义，不保证替换“最老的任意 oneway”，也不适用于正常运行目标上的所有异步消息。

业务接口只有在“同一发送方、同一方法的新值可以完整覆盖旧值”时才适合 update 语义。事件流、增量命令、计数变化和必须逐条交付的操作不能随意启用，否则旧事务被替换后无法从 Binder 自动恢复。

## 八、失败码要按语言层解释

目标 buffer 分配等内核事务错误通常沿 `BR_FAILED_REPLY` 返回。Android 17 native `IPCThreadState::waitForResponse()` 将其映射为 `FAILED_TRANSACTION`；`BR_DEAD_REPLY` 则映射为 `DEAD_OBJECT`。

Java 层还会经过 JNI 的异常映射，可能得到 `DeadObjectException`、`TransactionTooLargeException` 或其他 `RemoteException` 语义。`TransactionTooLargeException` 的判断带有启发式，不能反向证明 Parcel 超过某个固定字节值。

接口调用方应按所用语言和生成代码处理错误。对于状态修改，还要决定失败后能否重试、怎样保证幂等；对于查询，要限制回复集合大小并避免与并发事务共同耗尽目标地址空间。

## 九、用 trace 验证调度与等待

下面的 PerfettoSQL 用于找出耗时较长的同步事务：

```sql
INCLUDE PERFETTO MODULE android.binder;

SELECT
  client_process,
  client_thread,
  server_process,
  server_thread,
  interface,
  method_name,
  (server_ts - client_ts) / 1e6 AS server_start_delay_ms,
  server_dur / 1e6 AS server_ms,
  client_dur / 1e6 AS client_ms,
  binder_txn_id
FROM android_binder_txns
WHERE is_sync = 1
ORDER BY client_dur DESC
LIMIT 50;
```

`server_ts - client_ts` 同时包含驱动交付、目标线程可用性和 CPU 调度影响，不能单凭这一列判定线程池已满。还应关联 `sched_switch`、线程 Running/Runnable/Sleeping 区间、Binder transaction flow 和服务端 AIDL slice。

下面的命令用于确认设备提供哪些 Binder 调试与 trace 节点：

```bash
adb shell ls /dev/binderfs/binder_logs
adb shell ls /sys/kernel/tracing/events/binder
adb shell ps -AT -o PID,TID,CLS,PRI,NI,NAME
```

节点是否可读取决于 binderfs 挂载、内核配置、build type 与 SELinux。`persist.binder.debug.priority_cap` 不是 Android 17 AOSP 中启用 driver priority 日志的标准属性，不能作为通用排障命令。

观测优先级继承至少需要对齐：

- `binder_transaction`、`binder_transaction_received` 与目标 transaction id；
- `binder_set_priority` tracepoint；
- 目标线程 policy、nice/RT priority；
- `sched_switch` 和 runnable 等待；
- BBinder 的最低策略与 `inherit_rt` 配置。

没有这些证据时，5–15 μs ioctl、200 ns ABORT 或固定 P99 等数字只能代表未说明环境的估算，不能作为 Android 17 平台指标。

## 十、源码阅读结论

`BINDER_WRITE_READ` 可以减少用户态命令往返，但 write/read 之间没有整体原子事务；命令批量按字节容量和 todo 状态决定，也没有固定 128 条或固定 syscall 次数。

同步事务优先级由 caller、目标 node、RT 继承门禁与 rlimit 共同决定。`set_priority_called` 约束单个 transaction，三态机则保护目标线程上的 restore 竞态。

等待线程链表在 kernel r6 中采用表头插入与表头取出，表现为 LIFO。`TF_UPDATE_TXN` 只替换冻结目标 node 上符合严格条件的 pending oneway；它发生在新 buffer 成功分配之后，不能修复 buffer 溢出。
