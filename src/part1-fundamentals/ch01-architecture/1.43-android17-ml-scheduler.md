## 要点

### 🔹 核心概念与架构原理
Android 17 引入了革命性的机器学习驱动任务调度器（ML Scheduler），这是对传统基于规则调度的重要革新，显著提升了系统性能和用户体验。

**核心设计理念：**
ML Scheduler 采用深度学习模型预测用户行为模式和系统资源需求，实现前瞻性的任务调度。与传统的静态优先级调度相比，ML Scheduler 能够根据历史数据学习用户的使用习惯，动态调整任务执行策略。

**学习目标：**
- 用户行为模式预测（应用启动时间、使用频率）
- 系统资源需求预测（CPU、内存、电池消耗）
- 应用间依赖关系识别
- 用户注意力状态感知

**预测模型架构：**
```java
// 伪代码：ML 调度器的核心模型架构
class MLScheduler {
    private LSTM userBehaviorModel;      // 用户行为 LSTM 模型
    private CNN resourceDemandModel;     // 资源需求 CNN 模型
    private GNN dependencyGraphModel;     // 依赖关系图神经网络
    
    public ScheduledTask predictOptimalSchedule(List<Task> tasks) {
        UserContext context = getUserContext();
        ResourceState state = getResourceState();
        
        // 多模型联合预测
        double userPriority = userBehaviorModel.predict(tasks, context);
        double resourceDemand = resourceDemandModel.predict(tasks, state);
        double dependencyScore = dependencyGraphModel.predict(tasks);
        
        // 综合调度决策
        return optimizeSchedule(userPriority, resourceDemand, dependencyScore);
    }
}
```

**技术优势：**
1. **智能预加载**：在用户即将使用前预启动相关应用
2. **资源优化**：预测资源需求高峰，提前分配资源
3. **性能提升**：应用启动时间减少 30%（低端设备提升更显著）
4. **电池优化**：后台应用内存占用优化 25%

## 源码核查后的结论

以 Android 17 平台标签 `android-17.0.0_r1` 和内核标签 `android17-6.18-2026-06_r6` 为基准，AOSP 没有提供一套由 LSTM、CNN 或 GNN 统一决定应用启动、Job 执行、进程优先级、CPU 分配和内存回收的调度器。历史提纲中的 `MLScheduler` 是示意伪代码，不能映射到某个 framework service、AIDL、HAL 或内核子系统。

这类材料容易把几个独立机制放在同一个名称下。阅读源码时应按调度对象拆开：

| 机制 | 处理对象 | 可核验输入与输出 |
|---|---|---|
| App Standby | 应用的后台活跃分桶 | 特权调用方可以写入 bucket；系统记录 bucket、reason 与预测过期时间 |
| JobScheduler | 应用提交的 `JobInfo` | controllers 综合网络、充电、idle、quota、standby bucket、deadline 等约束 |
| OomAdjuster | 应用进程 | 根据组件生命周期、绑定关系与可见性计算 process state 和 `oom_score_adj` |
| ADPF | hint session 中的一组线程 | 应用提交 target/actual work duration，设备策略选择性能或能效响应 |
| Linux EEVDF | CPU 上的 runnable entity | 依据权重、virtual runtime、lag、eligibility 与 virtual deadline 选择任务 |

这些机制可以在一次应用启动或后台工作中同时出现，但它们没有共享历史提纲所写的统一 ML priority score。

## App Standby 中的“预测”边界

Android 17 的 `UsageStatsManager.setAppStandbyBucket(s)` 是受 `CHANGE_APP_IDLE_STATE` 保护的 `@SystemApi`。`AppStandbyController.setAppStandbyBuckets()` 会给符合条件的特权调用写入分配 `REASON_MAIN_PREDICTED`；这个 reason 记录值的来源类别，没有携带模型名称、特征、置信度或推理结果。

`AppIdleHistory` 保存 `lastPredictedTime` 与 `lastPredictedBucket`。常规构建中的默认预测有效期为 12 小时，也可由 `DeviceConfig` 的 `app_standby/prediction_timeout` 调整。预测超时后，controller 会继续依据使用事件、屏幕时间、经过时间和其他状态更新 bucket。

因此，设备上看到 `reason=p` 只能证明一次 bucket 写入被归到 predicted 来源。若要断言某款产品使用机器学习，还要找到实际调用包、模型或推理库、厂商接口文档，以及可重复的设备 trace。AOSP 没有限定预测值必须由机器学习生成。

这条路径及权限、reason 和超时逻辑的逐段分析见 [1.31 App Standby 预测与 ML 调度边界](./1.31-Android-17-机器学习驱动任务调度器.md)；同题材料的完整事实核查见 [1.59 Android 17「ML 驱动任务调度器」事实核查](./1.59-android17-ml-task-scheduler-comprehensive.md)。

## JobScheduler、ADPF 与 EEVDF 各自负责什么

JobScheduler 会读取应用的 standby bucket，并由 `QuotaController` 等 controller 计算执行时长、执行窗口、job/session 次数与 expedited job 限额。prefetch job 还能消费 UsageStats 提供的预计启动时间，但 AOSP 默认估计逻辑基于时间规则，不能据此推导出一套通用深度学习调度器。约束传播和排查入口见 [Android 17 JobScheduler 系统级节流](../ch05-cpu-power/23-android17-jobscheduler-system-throttling.md)。

ADPF 的 `PerformanceHintManager` 接收应用明确上报的目标工作时长和已完成工作的实测时长。它帮助设备在性能与能效之间选择响应策略，不预测用户将打开哪个应用，也不提交 Job。接口边界见 [ADPF 自适应性能框架](../ch05-cpu-power/09-adpf.md)。

`android17-6.18-2026-06_r6` 的 fair scheduler 使用 EEVDF 选择 runnable entity。framework 可以通过 nice、task profile、cpuset、cgroup weight 和 uclamp 改变内核可见约束；源码没有接收历史提纲中 `predictedPriority` 的接口。调度算法见 [Android 17 EEVDF 调度器](../ch05-cpu-power/31-android17-eevdf-scheduler.md)。

## 调试命令核对

历史提纲给出的三个命令：

- `adb shell dumpsys activity scheduler --ml-stats`
- `adb shell dumpsys activity scheduler --ml-debug`
- `adb shell dumpsys activity scheduler --ml-reset`

没有对应的 Android 17 ActivityManager shell 子命令，也没有可接收这些参数的 ML Scheduler 服务。运行它们得到的错误不能用于判断设备是否启用了预测策略。

排查 AOSP 中现有机制时，可分别查看 `dumpsys usagestats`、`dumpsys jobscheduler` 和 `dumpsys performance_hint`。其中 `usagestats` 的 `reason=p` 表示 predicted 来源；`jobscheduler` 展示 effective bucket、约束、quota 与停止原因；`performance_hint` 展示 hint session 状态。三组输出不能互相替代。
