# 1.26 DeliQueue 无锁队列源码解析（AOSP android-17.0.0_r1）

## 1.26.1 旧队列为什么会卡住主线程

Android 17 仍保留 legacy 实现，用于未启用新行为的进程。它用 `synchronized (this)` 保护按 `when` 排序的单链表：

- 生产者插入消息时持有对象锁；尾部有快速路径，其余位置最坏需要 O(N) 扫描。
- Looper 取消息、处理同步屏障和判断空闲时也要拿同一把锁。
- 多个 Binder 线程同时向主线程投递消息时，入队操作会在 monitor 上排队。

共享链表必须在锁内维护，所以问题不只是“头尾能否并行”。生产者可能扫描并改写链表中间位置，消费者会移除队首，屏障还会改变异步消息的选择规则。单锁实现简单，却把生产者、消费者和队列维护都放进了同一个互斥区。

更棘手的是调度优先级。Android Developers Blog 给出的 Launcher 案例中，低优先级 `BackgroundExecutor` 持有 MessageQueue monitor；中优先级相机工作线程抢占 CPU 后，等待该 monitor 的 Launcher 主线程阻塞了约 18 ms，错过 60 Hz 帧期限。Java monitor 不提供优先级继承，主线程的高优先级不会自动传给持锁线程。

DeliQueue 的目标是移除这把核心共享锁，同时保留 `Handler`、`Looper`、同步屏障、定时消息和取消消息的既有语义。

## 1.26.2 Android 17 源码地图

以下源码路径以 `android-17.0.0_r1` 为准：

| 文件 | 职责 |
|---|---|
| `core/java/android/os/CombinedDeliMessageQueue/MessageQueue.java` | 新旧实现分派、等待/唤醒、屏障、IdleHandler、FD 监听与退出 |
| `core/java/android/os/MessageStack.java` | Treiber stack、tombstone、freelist、同步/异步堆的入口 |
| `core/java/android/os/MessageHeap.java` | Looper 线程使用的数组最小堆 |
| `core/java/android/os/Message.java` | `removed` 状态、堆下标、前后向链和排序比较器 |
| `core/java/android/os/Looper.java` | 从队列取消息、派发回调与 `mq` Perfetto 事件 |

`MessageQueue.java` 把字段明确分成 legacy 与 DeliQueue 两组。DeliQueue 组包含以下关键字段：

- `MessageStack mStack`：生产者与 Looper 之间的共享入口。
- `mNextInsertSeqValue` / `mNextFrontInsertSeqValue`：相同 `when` 下的稳定次序。
- `mWaitState`：Looper 当前处于运行计数态还是等待截止时间态，并记录同步屏障状态。
- `mMptrRefCountValue`：保护跨线程 `nativeWake(mPtr)` 与退出时的 native 对象销毁。
- `mIdleHandlersLock` / `mFileDescriptorRecordsLock`：两类非核心队列数据的专用锁。

因此，“Android 17 的 MessageQueue 完全没有锁”并不准确。更严谨的说法是：核心消息数据结构和等待状态不再依赖全局对象锁，少量附属状态改用范围更小的专用锁。

## 1.26.3 生产者：CAS 入栈，不在调用线程排序

`MessageStack.pushMessage()` 的核心循环如下，用来说明发布时的内存顺序：

```java
do {
    current = mTopValue;
    if (isQuittingMessage(current)) return false;
    m.next = current;
} while (!sTop.weakCompareAndSetRelease(this, current, m));
```

生产者先把新消息的 `next` 指向旧栈顶，再用 release CAS 发布新栈顶。CAS 失败说明其他线程抢先发布了消息，当前线程读取新栈顶后重试。它不会因为另一线程被挂起而一直等待某把锁，但单个生产者仍可能在竞争中多次失败，所以 DeliQueue 是 lock-free，不是 wait-free。

`enqueueMessageUnchecked()` 在入栈前完成三件事：

1. 普通定时消息从递增序列取号；`sendMessageAtFrontOfQueue()` 使用递减的负序列。
2. 写入 `when`、`insertSeq`，并把消息标为 in-use。
3. 更新消息计数后调用 `mStack.pushMessage(msg)`。

入栈成功后，生产者还要更新 `mWaitState`。Looper 已醒时只递增计数；新消息不早于当前唤醒截止时间时无需唤醒；更早到期的消息则结合“是否异步、是否被同步屏障挡住”决定是否调用 `concurrentWake()`。这段 CAS 协议避免两类错误：该醒时漏唤醒，以及每次 post 都触发无意义的 `nativeWake()`。

从复杂度看，发布到 Treiber stack 的结构操作是 O(1)，但 CAS 重试次数没有固定上限。排序成本被移到 Looper 线程，而不是凭空消失。

## 1.26.4 消费者：增量迁移到两个最小堆

Looper 进入 `nextMessage()` 后，先把 `mWaitState` 从截止时间态转换为计数态，然后执行：

```java
mStack.heapSweep();
mStack.drainFreelist();
Message msg = mStack.peek(false);
Message asyncMsg = mStack.peek(true);
```

`heapSweep()` 用 acquire 语义读取栈顶，并以 `mLooperProcessed` 作为上一轮边界。它只遍历两轮之间新增的 k 条消息：未删除的同步消息进入 `mSyncHeap`，异步消息进入 `mAsyncHeap`；同时补上仅由 Looper 维护的 `prev` 反向链接。

两个堆分开的原因是同步屏障。选择规则可概括为：

- 同步堆顶是屏障时，只考虑已经到期的异步堆顶。
- 没有屏障时，在同步、异步两个堆顶中选择排序更靠前的一条。
- 候选消息尚未到期时，根据它的 `when` 计算下一次 `nativePollOnce()` 的超时。
- 消息准备交付时，先 CAS 标记 removed，再从堆和栈的链接中移除。

`MessageHeap` 是从 16 个元素起步的 `Message[]` 数组。插入执行 sift-up，删除堆顶执行 sift-down，任意位置删除利用 `Message.heapIndex` 定位。堆只由 Looper 线程维护，不需要并发容器。

若本轮迁入 k 条消息、堆中共有 N 条消息，迁移成本上界可写为 O(k log N)。按每条消息摊销，生产者 O(1) 发布，Looper 负责 O(log N) 排序。不能据此预设 k 的常见值，也不能在没有 trace 或插桩证据时宣称某次 `heapSweep()` 会耗时多少毫秒。

## 1.26.5 排序：`when` 优先，`insertSeq` 解决同刻次序

Android 17 使用下面的无分支比较器确定堆顺序：

```java
final int whenSign = Long.signum(m1.when - m2.when);
final int insertSeqSign = Long.signum(m1.insertSeq - m2.insertSeq);
return whenSign * 2 + insertSeqSign;
```

`when` 是主键，`insertSeq` 仅在时间相同时参与比较。普通消息的序列递增，所以同一 `when` 下保持先入先出；队首消息使用递减的负序列，所以连续调用 `sendMessageAtFrontOfQueue()` 呈后入先出，这与该 API 的历史语义一致。

Google 在开发过程中用 simpleperf 发现最小堆比较会产生较多分支预测失败，于是把条件分支改为算术组合。官方博客报告，这项比较器优化在部分基准中达到 5 倍提升。它是局部热点的结果，不能写成 MessageQueue 或应用端到端性能提升 5 倍。

## 1.26.6 删除：先做逻辑删除，再由 Looper 改结构

`removeCallbacks()` 与 `removeMessages()` 需要从任意线程扫描全部候选消息。生产者不能一边让 Looper 维护最小堆，一边直接改堆数组，因此 DeliQueue 使用 tombstone：

1. 扫描线程从栈顶做一次 acquire 读取，随后沿 `next` 遍历。
2. 匹配消息通过 CAS 设置 removed 标记，并清理 callback、obj 等引用字段。
3. 被标记的消息通过另一个 CAS 链加入 freelist。
4. Looper 下次运行 `drainFreelist()` 时，从堆和双向链中物理移除这些消息。

`heapSweep()` 也会跳过已经 marked-removed 的新消息。若删除与交付同时竞争，`markRemoved()` 只会有一方成功，从而决定该消息是交付还是取消。

遍历中的普通 `next` 读取构成经过刻意约束的数据竞争。Looper 摘除节点时不会清空该节点原有的 `next`；扫描线程即使看到旧链接，也能沿已摘除节点回到仍存活的链。官方团队为这组不变量运行了压力测试和 Java ThreadSanitizer。它依赖具体字段生命周期与单消费者规则，不适合作为普通应用并发代码的模板。

## 1.26.7 等待、唤醒与退出安全

DeliQueue 还维护两组原子状态。

第一组是 `WaitState`。它在两种表示之间切换：Looper 工作时保存入队计数；Looper 准备休眠时保存下一截止时间和同步屏障标记。生产者通过 CAS 更新该值，只有可能让 Looper 更早工作时才唤醒 native looper。

第二组是 `mPtr` 的 tagged refcount。最高位表示 teardown，低 63 位是正在使用原生 looper 指针的线程数。跨线程唤醒先增加引用计数，退出线程先设置 teardown 位，再等待已有引用归零后释放 native 对象。与此同时，`MessageStack` 顶部的 quitting sentinel 会拒绝后续入栈。这两层分别保护 Java 消息发布和 native 指针生命周期。

退出路径允许 Looper 等待其他使用者释放引用，因此“无锁”也不表示整个生命周期永不等待；该等待只发生在销毁阶段，不在正常消息发布热路径。

## 1.26.8 启用条件：先看进程启动，再看 `computeUseDeliQueue()`

源码中的 change ID 是：

```java
@EnabledAfter(targetSdkVersion = Build.VERSION_CODES.BAKLAVA)
public static final long USE_NEW_MESSAGEQUEUE = 421623328L;
```

`BAKLAVA` 是 API 36；`EnabledAfter` 表示目标版本高于 36，所以默认边界是 targetSdk 37。Android 17 官方行为变更文档给出相同结论。

`computeUseDeliQueue()` 只负责启动流程中的一段判断；compat change、aconfig flag 和启动参数并不是三个可以互相覆盖的末级开关。完整启动流程如下：

1. system_server 的 `PlatformCompat.getUseDeliQueue(app.info)` 先计算应用是否启用 `USE_NEW_MESSAGEQUEUE`。
2. `ProcessList` 把该布尔值传给 Zygote，最终追加为 `--use-deliqueue=true|false`。
3. `ActivityThread.main()` 在创建主 Looper 前调用 `MessageQueue.setUseDeliQueue(useDeliQueue)`。
4. `setUseDeliQueue(false)` 直接选择 legacy；只有参数为 `true` 时才调用 `computeUseDeliQueue(true)`。
5. 结果写入进程级静态字段，第一次初始化后不再改变。

`computeUseDeliQueue(true)` 的当前实现如下，它用于说明第 4 步内部的优先级：

```java
if (CompatChanges.isChangeEnabled(USE_NEW_MESSAGEQUEUE)
        || Flags.useConcurrentMessageQueueInApps()) return true;
if (Process.myProcessName() == null) return false;
return enable;
```

因此，普通应用的可观察规则应按下面理解：

| 场景 | 进程启动结果 |
|---|---|
| targetSdk 37+，未覆盖 compat change | 默认使用 DeliQueue |
| targetSdk 37+，显式 disable 该 change | 使用 legacy 实现 |
| targetSdk ≤ 36，未覆盖 compat change | 默认使用 legacy 实现 |
| targetSdk ≤ 36，显式 enable 该 change | 可提前测试 DeliQueue |
| system_server | 启动前显式请求 DeliQueue |

aconfig flag 位于 `computeUseDeliQueue()`，但它不能推翻一次已经以 `setUseDeliQueue(false)` 完成的初始化。把它描述为应用进程中的独立第二层总开关，会掩盖 system_server 预计算与“首次调用生效”这两个关键事实。

可调试应用可以用官方命令提前启用或暂时关闭：

```bash
adb am compat enable USE_NEW_MESSAGEQUEUE <package-name>
adb am compat disable USE_NEW_MESSAGEQUEUE <package-name>
```

修改后应重启目标进程，让进程级选择重新初始化。compat override 适合验证行为差异，不应成为长期依赖的发布配置。

## 1.26.9 Perfetto：分别看 monitor 锁竞争与消息派发

### 查找 MessageQueue monitor contention

官方博客给出的模块可以聚合“主线程阻塞在 MessageQueue 方法”这一类事件：

```sql
INCLUDE PERFETTO MODULE android.monitor_contention;

SELECT process_name,
       SUM(dur) / 1000000.0 AS blocked_ms,
       COUNT(*) AS blocked_count
FROM android_monitor_contention
WHERE is_blocked_thread_main
  AND short_blocked_method LIKE '%MessageQueue%'
GROUP BY process_name
ORDER BY SUM(dur) DESC;
```

该结果没有通用的“超过多少毫秒就异常”阈值，应与帧时间线、启动区间和业务操作对齐。DeliQueue 启用后，legacy 的 `enqueueMessage()`/`next()` 共享锁竞争应消失；查询仍可能命中 `IdleHandler`、FD 记录的专用锁，或名称中包含 MessageQueue 的其他 monitor。定位时要继续查看阻塞方法、持锁方法和对应线程，不能把结果非零直接判成回退到 legacy。

### 采集 `mq` 类别

要记录消息从 post 到 receive 的 flow 与元数据，在 Perfetto 配置中启用 `mq` 类别：

```protobuf
data_sources {
  config {
    name: "track_event"
    track_event_config { enabled_categories: "mq" }
  }
}
```

`Looper.loopOnce()` 在 `mQueue.next()` 返回后开始 `message_queue_receive`，在消息派发和 Looper 的收尾检查之后结束。因此该 slice 不包含 `nativePollOnce()`、`heapSweep()` 或堆选择；它主要反映消息派发区间，不能用来测量 DeliQueue 取队列成本。

这些 slice 位于线程轨道。下面的查询按进程、线程统计派发区间：

```sql
SELECT p.name AS process_name,
       t.name AS thread_name,
       COUNT(*) AS dispatch_count,
       AVG(s.dur) / 1000000.0 AS avg_ms,
       MAX(s.dur) / 1000000.0 AS max_ms
FROM slice s
JOIN thread_track tt ON s.track_id = tt.id
JOIN thread t ON tt.utid = t.utid
LEFT JOIN process p ON t.upid = p.upid
WHERE s.category = 'mq'
  AND s.name = 'message_queue_receive'
  AND s.dur > 0
GROUP BY p.name, t.name
ORDER BY max_ms DESC;
```

长 `message_queue_receive` 通常要继续展开内部 `Handler` 回调和 CPU 调度；消息间隔很长且线程位于 `nativePollOnce()` 则通常表示队列空闲。公开事件没有单独包住 `heapSweep()`，要研究迁移成本，需要 platform 插桩、CPU 采样或与入队 flow、消息积压量联合分析。

## 1.26.10 性能结果与适用边界

Android Developers Blog 在 2026 年 2 月公布了以下结果：

- ARMv8.1 LSE 可让 ART 为原子操作生成无需 LL/SC 重试循环的指令；高竞争 CAS 基准相对 LL/SC 版本约快 3 倍。
- 繁忙队列上的多线程插入合成基准，最高比 legacy MessageQueue 快 5000 倍。
- 内部 beta 用户 trace 中，应用主线程花在锁竞争上的时间减少 15%。
- 同一批测试设备上，应用 missed frames 减少 4%，System UI 与 Launcher 交互 missed frames 减少 7.7%。
- 应用启动到首帧的 P95 时间减少 9.1%。

这些数字的测量对象不同：3 倍是原子指令实现，5000 倍是高竞争队列插入，15% 是锁竞争时间，后三项才是用户可见指标。把它们放在一条线性因果链上相乘没有意义。

DeliQueue 也有成本：

- 竞争激烈时，Treiber stack 的 CAS 会重试。
- Looper 每轮要把新增消息迁入最小堆，并维护堆下标和前后向链接。
- 同步、异步两个堆的数组会随队列容量增长和收缩。
- 取消消息需要逻辑删除、freelist 与延迟物理清理。

收益最大的位置是多生产者同时向繁忙 Looper 投递消息，以及 legacy 链表较长的尾延迟场景。低消息量应用是否有可测差异，应由同设备、同负载的 trace 或基准回答。

## 1.26.11 兼容性与测试迁移

Android 17 为二进制兼容保留了私有字段 `mMessages`，但在 DeliQueue 模式下它始终为 `null`，不能表示待处理消息。反射该字段或私有方法的应用、测试框架和 APM 插件都需要检查。

官方迁移建议是：

- 避免通过反射查看 `MessageQueue` 内部结构。
- Espresso 升级到 3.7.0 或更高版本；该版本使用 `TestLooperManager` 与 Android 16 新增的测试接口。
- Robolectric 升级到 4.17 或更高版本，并从 `@LooperMode(LEGACY)` 迁移到 `@LooperMode(PAUSED)`。
- 应用自己的空闲协调优先使用公开测试能力或业务层 IdlingResource，不要把 `mMessages == null` 当作空闲条件。

这次改动不改变 `Handler` 回调 API，也不重写 ANR 判定策略。减少主线程等待 MessageQueue monitor 的时间，可能降低某些卡顿和超时发生的概率；它不能修复耗时回调、同步 Binder、I/O、死锁或过载的消息生产者。

## 1.26.12 Android 16 原型与 Android 17 当前实现

Android 16 原型与 Android 17 当前实现存在以下差异：

| 版本 | 实现 | 范围与结构 |
|---|---|---|
| Android 16 / `android-16.0.0_r1` | `CombinedMessageQueue`、`ConcurrentMessageQueue`、`LegacyMessageQueue` | 默认限制在 core UID 与 SystemUI；并发实现使用 `ConcurrentSkipListSet` 和带 ACTIVE/PARKED/TIMEDPARK 状态节点的 Treiber stack |
| Android 17 / `android-17.0.0_r1` | `CombinedDeliMessageQueue` | 应用按 targetSdk 37 compat change 启用；使用 `MessageStack`、同步/异步 `MessageHeap` 和独立 `WaitState` |

Android 16 原型有助于理解设计取舍，但不能拿它的类名、状态节点或跳表路径解释 Android 17 线上行为。排查 Android 17 时，应从 `CombinedDeliMessageQueue/MessageQueue.java` 开始，沿 `MessageStack`、`MessageHeap` 和 `Looper` 阅读。
