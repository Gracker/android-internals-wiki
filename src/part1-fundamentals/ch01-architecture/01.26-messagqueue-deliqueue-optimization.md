# 1.26 DeliQueue 无锁队列源码解析（AOSP android-17.0.0_r1）

<!-- outline-start -->
## 要点

### 🔹 传统 MessageQueue 的性能瓶颈
锁竞争是传统 MessageQueue 在高并发场景下的核心瓶颈。单锁保护 `mMessages` 链表，生产者（Binder 线程池）与消费者（主线程 Looper）抢同一把锁，多 Binder 线程并发 enqueueMessage 时排队等锁，拖慢消息分发。

### 🔹 DeliQueue 无锁队列设计
AOSP android-17.0.0_r1 正式引入了 DeliQueue（CombinedDeliMessageQueue），采用 CAS + volatile 可见性 + MessageStack 无锁栈 + MessageHeap min-heap 实现线程安全，消除锁竞争开销。生产者通过 `MessageStack.pushMessage()`（VarHandle.weakCompareAndSetRelease）无锁入队；Looper 线程独占访问 `MessageHeap`（`Message[]` min-heap）做 O(log n) 优先级排序。

### 🔹 两阶段发布路线
Android 16 AOSP 提供了 System-only 的 `ConcurrentMessageQueue` 原型（基于 ConcurrentSkipListSet + Treiber Stack 4 态节点）；Android 17 正式发布 `CombinedDeliMessageQueue`，通过 `USE_NEW_MESSAGEQUEUE` changeId（`@EnabledAfter(targetSdkVersion = BAKLAVA)`）面向 targetSdk 37+ 应用默认启用。§1.13 有更完整的版本路线与行为变更说明。

### 🔹 源码级数据结构
本章提供 android-17.0.0_r1 源码级验证：MessageStack CAS 入队与 heapSweep 迁移、MessageHeap min-heap 排序机制、USE_NEW_MESSAGEQUEUE changeId 与 CompatChanges 判定链、Looper dispatch 调用链。

## 扩展

### 🔸 无锁队列性能数据
CAS 在 ARM v8.1+（LSE 扩展）上硬件加速，~3x 快于 LL/SC 循环。Google 官方 benchmark 报告高竞争插入最高 5000x 改善，应用 missed frames 下降 4%，Launcher 交互 missed frames 下降 7.7%，冷启动首帧 P95 下降 9.1%。代价包括每消息额外内存开销、heapSweep 批量迁移成本。

### 🔸 与 §1.13 的分工
§1.13 注重 MessageQueue 全景机制与 Android 17 行为变更；本节专注 android-17.0.0_r1 源码级数据结构与并发细节。

### 🔸 Android 16 历史对照
android-16.0.0_r1 提供 System-only 的 `ConcurrentMessageQueue`（ConcurrentSkipListSet<MessageNode> + 4 态 Treiber Stack），作为 DeliQueue 的方向验证原型。本节正文以 android-17.0.0_r1 `CombinedDeliMessageQueue` 为主线，Android 16 原型仅在要点中提及作为历史参照。

## 1.26.1 为什么需要无锁 MessageQueue

传统 MessageQueue 以 `synchronized` 保护内部 `mMessages` 链表：

- MessageQueue.enqueueMessage() 获取对象锁 → 链表插入 → 释放锁
- MessageQueue.next() 获取对象锁 → 链表取头 → 可能 wait() → 释放锁

这个设计在高并发场景下暴露三个问题：

**锁竞争热点**：多 Binder 线程同时向主线程发消息时，所有线程串行化排队拿锁——先拿到锁的线程插入消息，后面的阻塞等待。线程数越多，等锁时间越长。

**生产者-消费者互斥**：主线程 Looper 取消息（next）和 Binder 线程投消息（enqueueMessage）共享同一把锁。即使入队和出队操作不冲突（一个在链表头，一个在链表尾），也必须串行执行。

**优先级倒置风险**：低延迟消息（如触摸事件）被高延迟消息（如后台 work）的锁持有时间阻塞。

DeliQueue 的方案：用 CAS 原子操作替代锁，把生产者和消费者的数据结构分离——生产者写入无锁栈（MessageStack），消费者（Looper 线程）独占 min-heap（MessageHeap），消除所有锁等待。

## 1.26.2 目录结构拆分

android-17.0.0_r1 的 DeliQueue 由以下文件组成，位于 `frameworks/base/core/java/android/os/`：

- **CombinedDeliMessageQueue/MessageQueue.java** — DeliQueue 主入口，集成入队/出队/等待/唤醒全流程。包含 `computeUseDeliQueue()` 判定逻辑与 USE_NEW_MESSAGEQUEUE changeId gating。
- **MessageStack.java** — 无锁栈，通过 `VarHandle.weakCompareAndSetRelease` CAS 实现多生产者安全 push。暴露 `pushMessage()`、`heapSweep()`（将栈上消息批量迁移到 MessageHeap）、`removeMessages()`（tombstone 逻辑删除）。
- **MessageHeap.java** — min-heap，基于 `Message[] mHeap` 数组维护按 `when + insertSeq` 排序的消息。仅 Looper 线程访问，无需同步。
- **Message.java** — 消息对象，排序键为 `Message.compareMessages()` 的 `when`（主键）和 `insertSeq`（副键）。

> **源码锚点**：`android-17.0.0_r1:frameworks/base/core/java/android/os/{CombinedDeliMessageQueue/MessageQueue.java, MessageStack.java, MessageHeap.java, Message.java}`
> **已验证**：DeepReview 2026-06-28 确认上述 4 个文件均存在于 android-17.0.0_r1 tag。

> **历史对照**：Android 16 仅有 System-only 原型——`CombinedMessageQueue/`（分派器）、`ConcurrentMessageQueue/`（基于 ConcurrentSkipListSet<MessageNode> + 4 态 Treiber Stack）、`LegacyMessageQueue/`（传统单锁）三个实现并列。Android 17 删除 `ConcurrentMessageQueue/` 和 `LegacyMessageQueue/`，统一为 `CombinedDeliMessageQueue/`。

## 1.26.3 优先级队列数据结构

CombinedDeliMessageQueue 使用 `MessageHeap`（`Message[]` array-based min-heap）实现优先级排序，O(log n) 插入和删除：

```java
// MessageHeap.java
// A min-heap of Message objects. Used by MessageQueue.
// Only Looper thread accesses this heap, so no synchronization needed.
final Message[] mHeap;
```

**排序规则**：由 `Message.compareMessages()` 决定：

```java
// Message.java — 排序比较器
int compareMessages(long when, int sequenceNumber) {
    if (mWhen != when) {
        return Long.compare(mWhen, when);
    }
    return Integer.compare(mSequenceNumber, sequenceNumber);
}
```

- 主键：`mWhen`（触发时间，绝对值），小值优先
- 副键：`mSequenceNumber`（插入序号，AtomicLong 递增），同时间保持 FIFO

> **注意**：android-16 原型使用 `ConcurrentSkipListSet<MessageNode>`（跳表），android-17 已替换为 `MessageHeap`（array min-heap）。min-heap 的优势：更紧凑的内存布局（连续数组 vs 跳表节点链），且 Looper 独占访问无需并发安全，因此跳表的多线程安全能力在此场景下是多余开销。

## 1.26.4 无锁入队与消息迁移

DeliQueue 的入队不直接操作 min-heap，而是先通过 CAS 写入 `MessageStack`（无锁栈），再由 Looper 线程批量迁移到 `MessageHeap`：

**入队（任意线程）**：`MessageStack.pushMessage()` 使用 `VarHandle.weakCompareAndSetRelease` 执行 CAS 循环：

```java
// MessageStack.java（示意，基于源码结构）
public void pushMessage(Message msg) {
    // CAS loop: set msg.next = current head, attempt to set head = msg
    // Uses VarHandle.weakCompareAndSetRelease for release semantics
    do {
        msg.next = (Message) HEAD.get(this);
    } while (!HEAD.weakCompareAndSetRelease(this, msg.next, msg));
}
```

**消息迁移（仅 Looper 线程）**：Looper 线程调用 `heapSweep()` 遍历栈上未处理的消息，批量插入 `MessageHeap`：

```java
// MessageStack.java（示意）
void heapSweep(MessageHeap heap) {
    // 1. Atomically drain the stack into a local list
    Message drained = drainStack();
    // 2. Insert each message into the heap
    while (drained != null) {
        heap.insert(drained);
        drained = drained.next;
    }
}
```

**设计要点**：
- 生产者只做 CAS push（O(1)），不访问 heap
- 消费者批量 drain + insert（摊销 O(n × log n)），无锁冲突
- `VarHandle.weakCompareAndSetRelease` 的 release 语义确保入队消息对其他线程立即可见

> **历史对照**：android-16 原型使用 Treiber Stack 4 种节点类型（STACK_NODE_MESSAGE/ACTIVE/PARKED/TIMEDPARK）和 `drainStack()` 批量迁移到 `ConcurrentSkipListSet`。android-17 简化了状态模型：栈只包含 Message 节点，等待/唤醒信号不再走栈（由系统调用 epoll 管理）。

## 1.26.5 入队流程

```java
// CombinedDeliMessageQueue/MessageQueue.java（示意）
boolean enqueueMessage(Message msg, long when) {
    if (msg.isInUse()) {
        throw new IllegalStateException("Message already in use");
    }
    msg.markInUse();
    msg.when = when;
    // 写入无锁栈
    mStack.pushMessage(msg);
    // 如果需要唤醒 Looper（消息到期时间早于当前等待时间）
    if (needWake) {
        nativeWake(mPtr);
    }
    return true;
}
```

入队始终走无锁路径。不存在慢速路径：CAS 竞争时 `weakCompareAndSetRelease` 自动重试直到成功，无需显式 backoff——ARM v8.1+ LSE 原子指令使 CAS 竞争开销远低于锁阻塞。

**出队（仅 Looper**：`MessageQueue.next()` 的实现：

1. 调用 `mStack.heapSweep(mHeap)` 将新消息从栈迁移到 heap
2. 从 `mHeap.poll()` 获取最早到期的消息
3. 若消息尚未到达 `when` 时间，进入 timed wait（epoll_wait）
4. 若有 idle handler 注册，到期时回调

## 1.26.6 Gating 条件与生效范围

DeliQueue 的启用由两层判定链控制：

**第一层：changeId**。`USE_NEW_MESSAGEQUEUE` 定义为：
```java
@EnabledAfter(targetSdkVersion = Build.VERSION_CODES.BAKLAVA)
public static final long USE_NEW_MESSAGEQUEUE = 326383834L;
```
- targetSdk ≥ 37（BAKLAVA）的应用默认启用
- targetSdk < 37 的应用走传统 MessageQueue
- 开发者可通过 `adb am compat disable USE_NEW_MESSAGEQUEUE <package>` 关闭

**第二层：运行时判定**。`CombinedDeliMessageQueue/MessageQueue.java` 中的 `computeUseDeliQueue()`：
```java
// CombinedDeliMessageQueue/MessageQueue.java（示意）
static boolean computeUseDeliQueue() {
    return CompatChanges.isChangeEnabled(USE_NEW_MESSAGEQUEUE)
            && Flags.useConcurrentMessageQueueInApps();
}
```
- `CompatChanges.isChangeEnabled(USE_NEW_MESSAGEQUEUE)` — 基于 targetSdk + adb compat 状态
- `Flags.useConcurrentMessageQueueInApps()` — aconfig flag，允许系统级关闭

**两阶段历史路线**：

| 阶段 | 版本 | 实现 | 生效范围 |
|------|------|------|----------|
| 阶段 0（方向验证） | Android 16 AOSP | ConcurrentMessageQueue（ConcurrentSkipListSet + Treiber Stack 4 态节点） | System 进程 only（`UserHandle.isCore()` + `com.android.systemui`） |
| 阶段 1（正式发布） | Android 17 | CombinedDeliMessageQueue（MessageStack + MessageHeap） | targetSdk 37+ 的所有应用，通过 USE_NEW_MESSAGEQUEUE changeId 控制 |

阶段 0 的 ConcurrentMessageQueue 在 android-17.0.0_r1 中已被移除，不被视为 DeliQueue 的当前实现。

## 1.26.7 Looper 调用链与 Perfetto 集成

```java
// Looper.java:194-280
private static boolean loopOnce(final Looper me, ...) {
    Message msg = me.mQueue.next(); // CombinedDeliMessageQueue 走 MessageStack.heapSweep + MessageHeap.poll
    if (msg == null) return false;
    msg.target.dispatchMessage(msg);
}
```

CombinedDeliMessageQueue 中 `next()` 的完整路径：

1. `heapSweep()` — CAS drain 栈上消息 → 批量插入 `MessageHeap`
2. `mHeap.poll()` — 从 min-heap 弹出最早到期的消息
3. 若消息未到 `when` 时间 → `nativePollOnce(timeout)` 进入 epoll wait
4. 到期或有新消息唤醒 → 返回消息
5. Looper 派发 → `msg.target.dispatchMessage(msg)`

**Perfetto 集成**：消息派发前后输出 `message_queue_receive` trace slice，可在 Perfetto 中与 `Choreographer#doFrame` 的 VSYNC-app slice 对齐，分析消息处理延迟。

## 1.26.8 性能特征

**收益**（基于 Google Android Developers Blog 2026-02-17 公布的 benchmark）：

- CAS 在 ARM v8.1+（LSE 扩展）上硬件加速，~3x 快于 LL/SC 循环
- 高竞争插入操作最高 5000x 改善（合成 benchmark，大量并发 Binder 线程入队）
- 应用整体 missed frames 下降 4%；Launcher 交互 missed frames 下降 7.7%
- 冷启动首帧 P95 下降 9.1%

**代价**：

- heapSweep 为摊销 O(n × log n) 批量迁移（n = 自上次迁移以来入队消息数）
- min-heap 的 Message[] 数组需要额外内存（但 ConcurrentSkipListSet 节点指针开销更高）
- 低消息量场景（每个 Looper cycle 仅 1-2 条消息）heapSweep 开销几乎为零，传统 MessageQueue 的链表操作同样简单——此场景下两者差异不大

**实战要点**：

- DeliQueue 消除的是队列入口的锁等待，不会让 `onBindViewHolder()` 等回调变快
- 锁消除后，布局/bind/measure 等 CPU 瓶颈会更直接暴露在 trace 中
- 依赖反射读取 `MessageQueue.mMessages` 的测试框架（Espresso、Robolectric）需适配——新实现中 `mMessages` 不再使用
