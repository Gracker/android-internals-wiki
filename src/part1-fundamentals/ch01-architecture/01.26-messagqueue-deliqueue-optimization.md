# 1.26 DeliQueue 无锁队列源码解析（AOSP android-17.0.0_r1）

<!-- outline-start -->
## 要点

### 🔹 传统 MessageQueue 的性能瓶颈
锁竞争是传统 MessageQueue 在高并发场景下的核心瓶颈。单锁保护 `mMessages` 链表，生产者（Binder 线程池）与消费者（主线程 Looper）抢同一把锁，多 Binder 线程并发 enqueueMessage 时排队等锁，拖慢消息分发。

### 🔹 DeliQueue 无锁队列设计
AOSP android-17.0.0_r1 正式引入了 DeliQueue（CombinedDeliMessageQueue），采用 CAS + volatile 可见性 + MessageStack 无锁栈 + 同步/异步两个 MessageHeap min-heap 实现线程安全，消除锁竞争开销。生产者通过 `MessageStack.pushMessage()`（VarHandle.weakCompareAndSetRelease）无锁入队；Looper 线程独占访问 `mSyncHeap` / `mAsyncHeap` 做 O(log n) 优先级排序。

### 🔹 两阶段发布路线
Android 16 AOSP 提供了 System-only 的 `ConcurrentMessageQueue` 原型（基于 ConcurrentSkipListSet + Treiber Stack 4 态节点）；Android 17 正式发布 `CombinedDeliMessageQueue`，通过 `USE_NEW_MESSAGEQUEUE` changeId（`@EnabledAfter(targetSdkVersion = BAKLAVA)`）面向 targetSdk 37+ 应用默认启用。§1.13 有更完整的版本路线与行为变更说明。

### 🔹 源码级数据结构
本章提供 android-17.0.0_r1 源码级验证：MessageStack CAS 入队与 heapSweep 迁移、MessageHeap min-heap 排序机制、USE_NEW_MESSAGEQUEUE changeId 与 CompatChanges 判定链、Looper dispatch 调用链。

## 扩展

### 🔸 无锁队列性能数据
CAS 在 ARM v8.1+（LSE 扩展）上硬件加速，~3x 快于 LL/SC 循环。Google 官方 benchmark 报告高竞争插入最高 5000x 改善，应用 missed frames 下降 4%，Launcher 交互 missed frames 下降 7.7%，冷启动首帧 P95 下降 9.1%。代价包括每消息额外内存开销、heapSweep 批量迁移成本。

### 🔸 与 §1.13 的分工
§1.13 注重 MessageQueue 全景机制与 Android 17 行为变更；本节专注 android-17.0.0_r1 源码级数据结构与并发细节。

### 🔸 Android 16 历史对照
android-16.0.0_r1 提供 System-only 的 `ConcurrentMessageQueue`（ConcurrentSkipListSet<MessageNode> + 4 态 Treiber Stack），作为 DeliQueue 的方向验证原型。本节正文以 android-17.0.0_r1 `CombinedDeliMessageQueue` 为主线，Android 16 原型仅在要点中提及作为历史参照。

## 1.26.1 为什么需要无锁 MessageQueue

传统 MessageQueue 用 `synchronized` 锁保护 `mMessages` 链表：

- MessageQueue.enqueueMessage() 获取对象锁 → 链表插入 → 释放锁
- MessageQueue.next() 获取对象锁 → 链表取头 → 可能 wait() → 释放锁

这个设计在高并发场景下暴露三个问题：

**锁竞争热点**：多 Binder 线程同时向主线程发消息时，所有线程串行化排队拿锁——先拿到锁的线程插入消息，后面的阻塞等待。线程数越多，等锁时间越长。

**生产者-消费者互斥**：主线程 Looper 取消息（next）和 Binder 线程投消息（enqueueMessage）共享同一把锁。即使入队和出队操作不冲突（一个在链表头，一个在链表尾），也必须串行执行。

**优先级倒置风险**：低延迟消息（如触摸事件）被高延迟消息（如后台 work）的锁持有时间阻塞。

DeliQueue 的方案：用 CAS 原子操作替代锁，把生产者和消费者的数据结构分离——生产者写入无锁栈（MessageStack），消费者（Looper 线程）独占 min-heap（MessageHeap），消除所有锁等待。

## 1.26.2 目录结构拆分

android-17.0.0_r1 的 DeliQueue 由以下文件组成，位于 `frameworks/base/core/java/android/os/`：

- **CombinedDeliMessageQueue/MessageQueue.java** — DeliQueue 主入口，集成入队/出队/等待/唤醒全流程。包含 `computeUseDeliQueue()` 判定逻辑与 USE_NEW_MESSAGEQUEUE changeId gating。
- **MessageStack.java** — 无锁栈，通过 `VarHandle.weakCompareAndSetRelease` CAS 实现多生产者安全 push。内部维护 `mSyncHeap` / `mAsyncHeap` 两个 `MessageHeap`，`heapSweep()` 将新增消息按同步/异步分流到对应堆，`remove()` 配合 `markRemoved()` 清理已删除节点。
- **MessageHeap.java** — min-heap，基于 `Message[] mHeap` 数组维护按 `when + insertSeq` 排序的消息。仅 Looper 线程访问，无需同步。
- **Message.java** — 消息对象，排序键为 `Message.compareMessages(Message m1, Message m2)` 的 `when`（主键）和 `insertSeq`（副键）。

> **源码锚点**：`android-17.0.0_r1:frameworks/base/core/java/android/os/{CombinedDeliMessageQueue/MessageQueue.java, MessageStack.java, MessageHeap.java, Message.java}`
> **已验证**：DeepReview 2026-06-28 确认上述 4 个文件均存在于 android-17.0.0_r1 tag。

> **历史对照**：Android 16 仅有 System-only 原型——`CombinedMessageQueue/`（分派器）、`ConcurrentMessageQueue/`（基于 ConcurrentSkipListSet<MessageNode> + 4 态 Treiber Stack）、`LegacyMessageQueue/`（传统单锁）三个实现并列。Android 17 删除 `ConcurrentMessageQueue/` 和 `LegacyMessageQueue/`，统一为 `CombinedDeliMessageQueue/`。

**Tombstone 删除机制**

`Handler.removeCallbacks()` / `removeMessages()` 不直接修改无锁栈或 heap——生产者线程和 Looper 线程同时在读这些结构。DeliQueue 用两阶段 tombstone 标记解决这一问题：

1. **标记阶段（任意线程）**：调用 `Message.markRemoved()`，通过 CAS 设置消息内部的 `FLAG_REMOVED` 状态位，标识该消息已废弃。这一步不修改栈指针、不调整 heap 数组，纯逻辑标记。

2. **清理阶段（仅 Looper 线程）**：Looper 执行 `heapSweep()` 扫描栈时，对每个消息调用 `isRemoved()` 检查标记位：
   - 未被标记的消息 → 加入同步/异步 heap
   - 已被标记的消息 → 跳过，不进入 heap

```java
// MessageStack.java — heapSweep 中的 tombstone 过滤（示意）
public void heapSweep() {
    Message current = (Message) sTop.getAcquire(this);
    Message prevLooperProcessed = mLooperProcessed;
    mLooperProcessed = current;

    while (current != null && current != prevLooperProcessed) {
        if (current.next != null) {
            current.next.prev = current;
        }
        // tombstone: 跳过已标记删除的消息
        if (!current.isRemoved()) {
            getHeap(current).add(current);
        }
        current = current.next;
    }
}
```

**为什么不在匹配扫描阶段物理删除**：Treiber Stack 是无锁栈，生产者线程 push 新节点只修改栈顶指针，删除中间节点会破坏其他线程正在遍历的链表。DeliQueue 先用 `markRemoved()` 标记，再把待删消息挂到 freelist；Looper 线程在 `heapSweep()` 中建立 backlink 并过滤 removed message，随后通过 `drainFreelist()` 或取出消息后的 `mStack.remove()` 从 heap 和 stack 里摘除节点。

已标记的消息从 stack / heap 摘除并清掉引用后由 JVM 回收；DeliQueue 维护的 freelist 只用于延迟 unlink，不复用 `Message` 对象。

## 1.26.3 优先级队列数据结构

CombinedDeliMessageQueue 通过 `MessageStack` 内部的 `mSyncHeap` / `mAsyncHeap` 两个 `MessageHeap` 实现优先级排序，单个 heap 的插入和删除为 O(log n)：

```java
// MessageHeap.java
// A min-heap of Message objects. Used by MessageQueue.
// Only Looper thread accesses this heap, so no synchronization needed.
Message[] mHeap = new Message[INITIAL_SIZE];
```

**排序规则**：由 `Message.compareMessages()` 决定：

```java
// Message.java — 排序比较器
static int compareMessages(@NonNull Message m1, @NonNull Message m2) {
    final long when1 = m1.when;
    final long when2 = m2.when;
    final long insertSeq1 = m1.insertSeq;
    final long insertSeq2 = m2.insertSeq;
    final int whenSign = Long.signum(when1 - when2);
    final int insertSeqSign = Long.signum(insertSeq1 - insertSeq2);
    return whenSign * 2 + insertSeqSign;
}
```

- 主键：`when`（触发时间，绝对值），小值优先
- 副键：`insertSeq`（插入序号，普通消息递增，`sendMessageAtFrontOfQueue()` 递减），同时间按序号稳定排序

**add() — sift-up 上浮**：插入时新元素放在堆末尾，沿父节点方向逐层 compareMessages 交换，直到堆性质恢复：

```java
// MessageHeap.java — add 示意（基于源码结构）
void add(Message msg) {
    int i = size++;
    while (i > 0) {
        int parent = (i - 1) / 2;
        if (compareMessages(mHeap[parent], msg) < 0) break;
        mHeap[i] = mHeap[parent];
        i = parent;
    }
    mHeap[i] = msg;
}
```

Looper 线程独占访问 heap，整个过程无锁。最坏 O(log n) 次比较和交换。

**poll() — sift-down 下沉**：取出堆顶后，将末尾元素提到根位置，沿子节点方向逐层下沉：

```java
// MessageHeap.java — poll 示意（基于源码结构）
Message poll() {
    Message result = mHeap[0];
    Message last = mHeap[--size];
    mHeap[size] = null;
    if (size > 0) siftDown(0, last);
    return result;
}

void siftDown(int i, Message key) {
    int half = size / 2;
    while (i < half) {
        int child = i * 2 + 1;
        if (child + 1 < size && compareMessages(mHeap[child + 1], mHeap[child]) < 0) child++;
        if (compareMessages(key, mHeap[child]) <= 0) break;
        mHeap[i] = mHeap[child];
        i = child;
    }
    mHeap[i] = key;
}
```

**设计要点**：
- sift-up / sift-down 两种内部操作覆盖所有插入和删除场景
- `compareMessages` 的唯一调用点在 heap 内部，排序逻辑单一入口
- MessageHeap 不维护额外线程安全结构——Looper 线程通过 epoll wait 序列化所有 heap 访问

> **注意**：android-16 原型使用 `ConcurrentSkipListSet<MessageNode>`（跳表），android-17 已替换为 `MessageHeap`（array min-heap）。min-heap 的优势：更紧凑的内存布局（连续数组 vs 跳表节点链），且 Looper 独占访问无需并发安全，因此跳表的多线程安全能力在此场景下是多余开销。

## 1.26.4 无锁入队与消息迁移

DeliQueue 的入队不直接操作 min-heap，而是先通过 CAS 写入 `MessageStack`（无锁栈），再由 Looper 线程批量迁移到 `MessageHeap`：

**入队（任意线程）**：`MessageStack.pushMessage()` 使用 `VarHandle.weakCompareAndSetRelease` 执行 CAS 循环：

```java
// MessageStack.java（示意，基于源码结构）
public void pushMessage(Message msg) {
    // CAS loop: set msg.next = current head, attempt to set head = msg
    // Uses VarHandle.weakCompareAndSetRelease for release semantics
    do {
        msg.next = (Message) HEAD.get(this);
    } while (!HEAD.weakCompareAndSetRelease(this, msg.next, msg));
}
```

**消息迁移（仅 Looper 线程）**：Looper 线程调用 `heapSweep()`，用 acquire 读到当前栈顶，再从栈顶扫描到上一轮记录的 `mLooperProcessed` 边界，把新增消息加入同步或异步 heap：

```java
// MessageStack.java（android-17.0.0_r1 节选）
public void heapSweep() {
    Message current = (Message) sTop.getAcquire(this);
    Message prevLooperProcessed = mLooperProcessed;
    mLooperProcessed = current;

    while (current != null && current != prevLooperProcessed) {
        if (current.next != null) {
            current.next.prev = current;
        }
        if (!current.isRemoved()) {
            getHeap(current).add(current);
        }
        current = current.next;
    }
}
```

**设计要点**：
- 生产者只做 CAS push（O(1)），不访问 heap
- 消费者用 `mLooperProcessed` 做增量扫描边界，按 `Message.isAsynchronous()` 写入 `mSyncHeap` 或 `mAsyncHeap`
- `weakCompareAndSetRelease` 与 `getAcquire` 配合，保证生产者写入的 `Message` 字段在 Looper 迁移时可见

> **历史对照**：android-16 原型使用 Treiber Stack 4 种节点类型（STACK_NODE_MESSAGE/ACTIVE/PARKED/TIMEDPARK）并迁移到 `ConcurrentSkipListSet`。android-17 简化了状态模型：栈只包含 Message 节点，等待/唤醒信号改由 `WaitState`、`nativePollOnce()` 与 `nativeWake()` 配合管理。

## 1.26.5 入队流程

```java
// CombinedDeliMessageQueue/MessageQueue.java（示意）
boolean enqueueMessage(Message msg, long when) {
    if (msg.isInUse()) {
        throw new IllegalStateException("Message already in use");
    }
    msg.markInUse();
    msg.when = when;
    // 写入无锁栈
    mStack.pushMessage(msg);
    // 如果需要唤醒 Looper（消息到期时间早于当前等待时间）
    if (needWake) {
        nativeWake(mPtr);
    }
    return true;
}
```

在 DeliQueue 启用且队列未退出时，入队不走 `synchronized` 链表插入。`pushMessage()` 的 `weakCompareAndSetRelease` 失败会重试，队列已进入 quitting 状态时返回 false；随后唤醒状态还要通过 `mWaitState` CAS 循环决定是否 `nativeWake()`。ARM v8.1+ LSE 原子指令使 CAS 竞争开销低于锁阻塞，但这不是“无失败路径”。

**出队（仅 Looper 线程）**：`MessageQueue.next()` 的实现：

1. 调用 `mStack.heapSweep()` 将新消息从栈迁移到同步/异步两个 heap
2. 通过 `mStack.peek(false)` / `mStack.peek(true)` 分别查看同步消息和异步消息堆顶
3. 若同步屏障存在，优先选择可绕过屏障的异步消息；否则在两个堆顶中选择最早到期的消息
4. 若消息尚未到达 `when` 时间，设置 `mNextPollTimeoutMillis` 后进入 `nativePollOnce()` 等待
5. 取出消息前通过 `found.markRemoved()` 与 `mStack.remove(found)` 从 stack/heap 结构中摘除

## 1.26.6 Gating 条件与生效范围

DeliQueue 的启用由 compat change、aconfig flag 和进程启动参数共同决定：

**第一层：changeId**。`USE_NEW_MESSAGEQUEUE` 定义为：
```java
@EnabledAfter(targetSdkVersion = Build.VERSION_CODES.BAKLAVA)
public static final long USE_NEW_MESSAGEQUEUE = 421623328L;
```
- `@EnabledAfter(targetSdkVersion = BAKLAVA)` 表示 targetSdk 高于 Baklava（API 36），即 API 37+ 默认启用
- targetSdk ≤ 36 默认不因该 compat change 启用，但仍可能受 aconfig flag 或进程启动参数影响
- 开发者可通过 `adb am compat disable USE_NEW_MESSAGEQUEUE <package>` 关闭

**第二层：运行时判定**。`CombinedDeliMessageQueue/MessageQueue.java` 中的 `computeUseDeliQueue()`：
```java
// CombinedDeliMessageQueue/MessageQueue.java（示意）
static boolean computeUseDeliQueue(boolean enable) {
    if (CompatChanges.isChangeEnabled(USE_NEW_MESSAGEQUEUE)
            || Flags.useConcurrentMessageQueueInApps()) {
        return true;
    }
    final String processName = Process.myProcessName();
    if (processName == null) {
        return false;
    }
    return enable;
}
```
- `CompatChanges.isChangeEnabled(USE_NEW_MESSAGEQUEUE)` — 基于 targetSdk + adb compat 状态；命中后直接启用
- `Flags.useConcurrentMessageQueueInApps()` — aconfig flag；为 true 时可绕过 compat 判定启用
- `enable` — 进程启动阶段通过 `--use-deliqueue=` 传入的兜底开关

**两阶段历史路线**：

| 阶段 | 版本 | 实现 | 生效范围 |
|------|------|------|----------|
| 阶段 0（方向验证） | Android 16 AOSP | ConcurrentMessageQueue（ConcurrentSkipListSet + Treiber Stack 4 态节点） | System 进程 only（`UserHandle.isCore()` + `com.android.systemui`） |
| 阶段 1（正式发布） | Android 17 | CombinedDeliMessageQueue（MessageStack + 同步/异步 MessageHeap） | targetSdk API 37+ 默认由 USE_NEW_MESSAGEQUEUE changeId 启用，flag 与启动参数仍参与最终判定 |

阶段 0 的 ConcurrentMessageQueue 在 android-17.0.0_r1 中已被移除，不被视为 DeliQueue 的当前实现。

## 1.26.7 Looper 调用链与 Perfetto 集成

```java
// Looper.java:194-280
private static boolean loopOnce(final Looper me, ...) {
    Message msg = me.mQueue.next(); // CombinedDeliMessageQueue 走 MessageStack.heapSweep + MessageHeap.poll
    if (msg == null) return false;
    msg.target.dispatchMessage(msg);
}
```

CombinedDeliMessageQueue 中 `next()` 的完整路径：

1. `heapSweep()` — acquire 读取栈顶，扫描到 `mLooperProcessed` 边界，将新增消息加入同步/异步两个 heap
2. `mStack.peek(false)` / `mStack.peek(true)` — 查看同步和异步 heap 堆顶，结合同步屏障选择候选消息
3. 若候选消息未到 `when` 时间 → `nativePollOnce(timeout)` 进入 epoll wait
4. 到期或有新消息唤醒 → 返回消息
5. Looper 派发 → `msg.target.dispatchMessage(msg)`

**Perfetto 集成**：`Looper.loopOnce()` 在 `mQueue.next()` 返回后，通过 `PerfettoTrace.begin(PerfettoCategories.MQ_CATEGORY, "message_queue_receive")` emit 消息队列事件，并写入发送线程、接收线程、message code、message delay 等字段。这个 slice 包住的是后续 `dispatchMessage()`，不是 `heapSweep()` / `nativePollOnce()` 的取队列过程；它适合标记哪条消息被派发，不能直接用来量化 DeliQueue 的迁移成本。

**监控遗留 MessageQueue 锁竞争**（用于对比新旧实现）：

```sql
INCLUDE PERFETTO MODULE android.monitor_contention;

SELECT
  process_name,
  SUM(dur) / 1000000.0 AS blocked_ms,
  COUNT(*) AS blocked_count
FROM android_monitor_contention
WHERE is_blocked_thread_main
  AND short_blocked_method LIKE '%MessageQueue%'
GROUP BY process_name
ORDER BY blocked_ms DESC;
```

如果 `short_blocked_method` 包含 `MessageQueue.enqueueMessage` 或 `MessageQueue.next`，且 `blocked_ms` 总时长超过 10ms/帧窗口，说明传统锁竞争正在拖慢主线程。DeliQueue 启用后，这个查询的结果应该归零——入队不再走 synchronized 块。

**Message dispatch slice 分析（不等同于取队列耗时）**：

```sql
SELECT
  process.name AS process,
  slice.name AS trace_name,
  COUNT(*) AS count,
  CAST(AVG(dur) / 1000000.0 AS REAL) AS avg_ms,
  CAST(MAX(dur) / 1000000.0 AS REAL) AS max_ms
FROM slice
JOIN process_track ON slice.track_id = process_track.id
JOIN process ON process_track.upid = process.id
WHERE slice.name GLOB '*message_queue*' OR slice.name GLOB '*MessageQueue*'
GROUP BY process.name, slice.name
ORDER BY avg_ms DESC;
```

这组查询看到的是 `message_queue_receive` slice 的派发范围。`dur` 变长通常表示 `Handler.dispatchMessage()` 之后的回调执行时间变长，不等同于 `MessageStack.heapSweep()` 或 `mStack.peek()` 变慢。

**正常 vs 异常 trace 特征**：

| 状态 | trace 图样 | 含义 |
|------|-----------|------|
| 正常派发 | `message_queue_receive` slice 短，随后进入 `Choreographer#doFrame` 或业务回调 | Looper 已取到消息，回调执行成本低 |
| 回调耗时 | `message_queue_receive` slice 长，内部 CPU 时间落在目标 `Handler` / callback | 问题在消息处理函数，不在队列结构 |
| heapSweep 积压 | public Perfetto slice 不能直接看到 `heapSweep()` 子阶段；只能结合 message delay 字段、队列长度监控或临时插桩判断 | 两轮 Looper dispatch 之间积压了大量入队消息时，迁移成本可能集中到下一次 `next()` |
| nativePollOnce 长休眠 | `message_queue_receive` 间隔长，但线程处于 poll / idle | 空闲——没有消息需要处理，不是问题 |
| 锁竞争（已消除） | `monitor contention` slice 与 `MessageQueue` 关联 | DeliQueue 启用后不应出现；如仍存在，说明 gating 未命中（compat change 被禁用、flag 未开或 processName 判定） |

## 1.26.8 性能特征

**收益**（基于 Google Android Developers Blog 2026-02-17 公布的 benchmark）：

- CAS 在 ARM v8.1+（LSE 扩展）上硬件加速，~3x 快于 LL/SC 循环
- 高竞争插入操作最高 5000x 改善（合成 benchmark，大量并发 Binder 线程入队）
- 应用整体 missed frames 下降 4%；Launcher 交互 missed frames 下降 7.7%
- 冷启动首帧 P95 下降 9.1%

**代价**：

- heapSweep 为摊销 O(n × log n) 批量迁移（n = 自上次迁移以来入队消息数）
- min-heap 的 Message[] 数组需要额外内存（但 ConcurrentSkipListSet 节点指针开销更高）
- 低消息量场景（每个 Looper cycle 仅 1-2 条消息）heapSweep 开销几乎为零，传统 MessageQueue 的链表操作同样简单——此场景下两者差异不大

**实战要点**：

- DeliQueue 消除的是队列入口的锁等待，不会让 `onBindViewHolder()` 等回调变快
- 锁消除后，布局/bind/measure 等 CPU 瓶颈会更直接暴露在 trace 中
- 依赖反射读取 `MessageQueue.mMessages` 的测试框架（Espresso、Robolectric）需适配——新实现中 `mMessages` 不再使用

## 1.26.9 常见问题与误区

**Q1：CAS 无锁队列在所有场景都比传统锁快？**

不在低竞争场景。每个 Looper cycle 仅有 1-2 条消息入队时，传统 `synchronized` 的偏向锁/轻量锁开销几乎为零——JIT 编译后锁 acquire/release 只有几条 CPU 指令，而 CAS 需要完整的 load-link/store-conditional（无 LSE 时）或原子指令序列。DeliQueue 的收益集中在高并发场景：多个 Binder 线程同时向主线程 post 消息时的锁排队被消除。低竞争场景两者差异可忽略，但 DeliQueue 的摊销 heapSweep 开销（虽极小）仍然存在。

**Q2：heapSweep 的每消息迁移成本是恒定的？**

不是。heapSweep 有两层成本：

1. 栈遍历：从栈顶扫描到 `mLooperProcessed` 边界，O(k) 正比于本轮新入队的消息数 k。正常场景 k ≤ 5，几乎无开销。
2. heap 插入：每消息一次 min-heap add，O(log n)，n 为 heap 中当前消息总数。

总成本为摊销 O(k × log n)，不是每消息固定常数。当 Looper dispatch 频率远低于入队频率时（如主线程在做大量同步 Binder 调用导致 next() 迟迟不被调用），k 变大，单次 heapSweep 可能超过 5ms。在 Perfetto 中将 `message_queue_receive` slice 放大，查看 `heapSweep()` 子 slice。

**Q3：targetSdk 37+ 等于 DeliQueue 一定启用？**

不一定。gating 链为 `CompatChanges.isChangeEnabled(USE_NEW_MESSAGEQUEUE)` → `Flags.useConcurrentMessageQueueInApps()` → 进程启动参数 `--use-deliqueue=`。以下情况可能导致 DeliQueue 不启用：

- 通过 `adb am compat disable USE_NEW_MESSAGEQUEUE <package>` 手动关闭
- aconfig flag `useConcurrentMessageQueueInApps` 在设备端被覆盖为 false
- 进程启动时显式传入 `--use-deliqueue=false`

反过来，targetSdk ≤ 36 的应用也可能通过 flag 或启动参数启用 DeliQueue。设备 Android 版本（API 37+）是必要条件但不是充分条件。

**Q4：DeliQueue 启用后依赖反射读取 MessageQueue.mMessages 的测试框架会怎样？**

`mMessages` 字段仍保留在 `CombinedDeliMessageQueue/MessageQueue.java` 中，用于 legacy implementation 和兼容旧测试；但 DeliQueue 模式下真实待派发消息在 `MessageStack` / `MessageHeap`，`mMessages` 不是权威数据源。Espresso、Robolectric 等框架的 IdlingResource 若通过反射访问 `MessageQueue.mMessages` 判断主线程空闲，可能读到 null 或 legacy-only 状态，不能代表 DeliQueue 的 pending 消息。适配方向：

- Espresso：等待官方更新 IdlingResource 实现
- Robolectric：使用 `Looper.getMainLooper().getQueue().isIdle()` 替代反射
- 自定义测试：检查 `MessageQueue.isIdle()` 结合 Perfetto trace 确认无 pending 消息

**Q5：DeliQueue 会影响 ANR 行为吗？**

不会改变 ANR 判定逻辑。ANR 由 InputDispatcher 的超时机制和 `AMS.appNotResponding()` 触发，基于 input 事件未在 5 秒内派发，与 MessageQueue 的内部实现无关。DeliQueue 消除锁竞争可能减少因主线程等锁而累积 input 事件的情况，间接降低特定场景的 ANR 概率，但这不是 DeliQueue 的设计目标。
