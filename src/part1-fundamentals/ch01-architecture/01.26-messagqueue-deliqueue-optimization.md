# 1.26 DeliQueue 无锁队列源码解析（AOSP android-16.0.0_r1）

<!-- outline-start -->
## 要点

### 🔹 传统 MessageQueue 的性能瓶颈
锁竞争是传统 MessageQueue 在高并发场景下的核心瓶颈。单锁保护 `mMessages` 链表，生产者（Binder 线程池）与消费者（主线程 Looper）抢同一把锁，多 Binder 线程并发 enqueueMessage 时排队等锁，拖慢消息分发。

### 🔹 DeliQueue 无锁队列设计
AOSP android-16.0.0_r1 引入了 DeliQueue（ConcurrentMessageQueue），采用 CAS（compareAndSwap）+ volatile 可见性 + Treiber Stack 状态机实现线程安全，消除锁竞争开销。队列底层使用 ConcurrentSkipListSet<MessageNode>（跳表）实现 O(log n) 优先级排序。

### 🔹 两阶段发布路线
Android 16 AOSP 源码树中 DeliQueue 已存在但仅限 system 进程使用；Android 17（官方 blog 2026-02-17）宣布面向 targetSdk 37 应用默认启用。§1.13 有更完整的版本路线与行为变更说明。

### 🔹 源码级数据结构与状态机
本章提供 android-16.0.0_r1 的源码级验证：跳表优先级队列结构、Treiber Stack 4 种节点类型、入队 CAS 快速路径与重试慢速路径、drainStack O(n) 迁移机制。

## 扩展

### 🔸 无锁队列性能数据
CAS vs LL/SC 硬件层面 ~3x 快；长 parking 场景写入无锁避免阻塞；代价包括每消息额外分配 MessageNode 对象、drainStack O(n) 迁移开销。

### 🔸 与 §1.13 的分工
§1.13 注重 MessageQueue 全景机制与 Android 17 行为变更；本节专注 android-16.0.0_r1 源码级数据结构与并发细节。

## 1.26.1 为什么需要无锁 MessageQueue

传统 MessageQueue 以 `synchronized` 保护内部 `mMessages` 链表：

- MessageQueue.enqueueMessage() 获取对象锁 → 链表插入 → 释放锁
- MessageQueue.next() 获取对象锁 → 链表取头 → 可能 wait() → 释放锁

这个设计在高并发场景下暴露三个问题：

**锁竞争热点**：多 Binder 线程同时向主线程发消息时，所有线程串行化排队拿锁——先拿到锁的线程插入消息，后面的阻塞等待。线程数越多，等锁时间越长。

**生产者-消费者互斥**：主线程 Looper 取消息（next）和 Binder 线程投消息（enqueueMessage）共享同一把锁。即使入队和出队操作不冲突（一个在链表头，一个在链表尾），也必须串行执行。

**优先级倒置风险**：低延迟消息（如触摸事件）被高延迟消息（如后台 work）的锁持有时间阻塞。

DeliQueue 的方案：用 CAS 原子操作替代锁，让入队线程不需要等待 Looper 释放锁就能投递消息。

## 1.26.2 目录结构拆分

android-16.0.0_r1 将 MessageQueue 拆分为三个并列实现，位于 `frameworks/base/core/java/android/os/`：

- **CombinedMessageQueue/MessageQueue.java** (2951 行) — 对外入口，根据 aconfig flag 和调用者 UID 动态分派到 Concurrent/Legacy
- **ConcurrentMessageQueue/MessageQueue.java** (1789 行) — 无锁实现（即 DeliQueue）
- **LegacyMessageQueue/MessageQueue.java** (1357 行) — 传统单锁实现，行为与旧版 MessageQueue 一致

> **源码锚点**：`android-16.0.0_r1:frameworks/base/core/java/android/os/{Combined,Concurrent,Legacy}MessageQueue/MessageQueue.java`
> **已验证**：DeepResearch 2026-06-17 确认上述三个文件均存在，类名均为 MessageQueue（无 DeliQueue 类名）。

## 1.26.3 优先级队列数据结构

ConcurrentMessageQueue 使用 `ConcurrentSkipListSet<MessageNode>`（跳表 / 红黑树变体，O(log n)）实现优先级排序：

```java
// ConcurrentMessageQueue/MessageQueue.java:200-202
private final ConcurrentSkipListSet<MessageNode> mPriorityQueue =
        new ConcurrentSkipListSet<MessageNode>();
private final ConcurrentSkipListSet<MessageNode> mAsyncPriorityQueue =
        new ConcurrentSkipListSet<MessageNode>();
```

> **注意**：此前有资料描述为"基于数组的优先级队列"，不准确。

**排序规则**：
- 主键：`mMessage.when`（触发时间，绝对值）
- 副键：`mInsertSeq`（插入序号，`AtomicLong` 递增，同时间保持 FIFO）
- LIFO 例外：`sendMessageAtFrontOfQueue` 使用 Long.MIN_VALUE 序号实现 LIFO

每个 `MessageNode` 包装原始 `Message` 对象并附加排序键，额外内存开销约为每消息 40 字节（对象头 + 两个 long 字段 + 引用）。

## 1.26.4 Treiber Stack 状态机

DeliQueue 的入队不直接写跳表，而是先通过 CAS 写入 Treiber Stack（无锁栈），再由 Looper 线程批量迁移：

**4 种节点类型**：
```java
// ConcurrentMessageQueue/MessageQueue.java:75-95
private static final int STACK_NODE_MESSAGE = 0;   // 消息节点
private static final int STACK_NODE_ACTIVE = 1;     // Looper 处理中
private static final int STACK_NODE_PARKED = 2;     // Looper 睡眠
private static final int STACK_NODE_TIMEDPARK = 3;  // Looper 限时睡眠（带超时）
```

**状态迁移路径**：
1. 写入：任意线程通过 CAS 将新 `StackNode` 推入 `mStackTop`（volatile）
2. 读取：Looper 线程调用 `swapAndSetStackStateActive()` → CAS 将栈顶替换为 STACK_NODE_ACTIVE → 返回旧栈
3. 迁移：`drainStack()` 遍历栈上所有 MESSAGE 节点 → 批量插入 `mPriorityQueue`（跳表）

Thread 等待/唤醒信号（PARKED / TIMEDPARK）也走同一栈，避免了传统 wait/notify 的锁开销。

## 1.26.5 入队快速路径与慢速路径

```java
// ConcurrentMessageQueue/MessageQueue.java（伪代码示意）
boolean enqueueMessage(Message msg, long when) {
    // 快速路径：CAS 推入 Treiber Stack
    if (tryFastEnqueue(msg, when)) {
        return true;
    }
    // 慢速路径：栈满或 CAS 竞争失败时重试
    return enqueueWithRetry(msg, when);
}
```

- **tryFastEnqueue**：单次 CAS，适用低竞争场景（多数情况）
- **enqueueWithRetry**：退避 + 重试循环，CAS 失败超过阈值后走 backoff

## 1.26.6 Gating 条件与生效范围

DeliQueue 的启用分两个阶段，与源码版本对应：

| 阶段 | 版本 | 生效范围 | 控制方式 |
|------|------|----------|----------|
| 阶段 1 | Android 16 AOSP | System 进程（`UserHandle.isCore()` + `com.android.systemui`） | aconfig flag `message_queue_force_legacy` / `force_concurrent_message_queue` |
| 阶段 2 | Android 17（官方 blog 2026-02-17） | targetSdk 37+ 的所有应用 | 官方 blog 声明，具体 aconfig 策略需参考 android-17.0.0_r1 |

> **版本边界说明**：本节源码全部来自 android-16.0.0_r1。阶段 2 的 Android 17 面向应用默认启用来自官方 blog 与 §1.13 的引用；android-17.0.0_r1 的源码级验证尚未执行，正文结论以 Android 16 实现为准。

**aconfig flag**（android-16.0.0_r1）：
- `message_queue_force_legacy` — holdback 模式，强制降级到 LegacyMessageQueue
- `force_concurrent_message_queue` — 强制开启 ConcurrentMessageQueue（优先级低于 holdback）

## 1.26.7 Looper 调用链与 Perfetto 集成

```java
// Looper.java:194-280
private static boolean loopOnce(final Looper me, ...) {
    Message msg = me.mQueue.next(); // 可能 block（ConcurrentMessageQueue 走 drainStack + poll）
    if (msg == null) return false;
    msg.target.dispatchMessage(msg);
}
```

ConcurrentMessageQueue 中 `next()` 的实现：
1. 调用 `swapAndSetStackStateActive()` 获取栈快照
2. 调用 `drainStack()` 将栈上消息迁移到跳表
3. 从跳表 `poll()` 获取最早到期消息
4. 若有 idle handler 注册，到期时回调

**Perfetto 集成**：消息派发前后输出 `message_queue_receive` trace slice，可在 Perfetto 中与 `Choreographer#doFrame` 的 VSYNC-app slice 对齐，分析消息处理延迟。

## 1.26.8 性能特征（基于 android-16.0.0_r1 结构分析）

**收益**：
- CAS 在 ARM v8.1+（LSE 扩展）上硬件加速，~3x 快于 LL/SC 循环
- 长 parking 期（消息队列空）写入无锁，不阻塞新消息入队
- Binder 线程并发入队完全无锁，消除多线程串行化瓶颈

**代价**：
- 每消息额外分配 MessageNode 包装对象（约 40 字节额外内存）
- drainStack 为 O(n) 全量迁移（n = 自上次迁移以来入队消息数）
- 低消息量场景（< 5 条/帧）的迁移开销可能抵消 CAS 收益

> **适用性判断**：高并发场景（多个 Binder 线程频繁 post 消息）收益最明显；低消息量场景 LegacyMessageQueue 可能更优。
