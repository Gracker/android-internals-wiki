## TelephonyManager 在 Android 架构中的角色

TelephonyManager 是 Android SDK 暴露给应用层的电话服务入口。应用通过它查询信号强度、网络注册状态、通话状态、SIM 信息、数据连接类型等蜂窝能力。从架构角度看，TelephonyManager 只是一个轻量的客户端代理——它不持有任何业务逻辑，所有调用都通过 Binder IPC 进入独立的系统进程。

与 AMS/PMS 这类运行在 `system_server` 中的系统服务不同，Telephony 子系统采用了**多进程分离**架构：

```
┌─────────────────────────────────────────────────────────┐
│  App Process                                             │
│  ┌──────────────────────┐                               │
│  │  TelephonyManager     │  ← SDK API (sdk.jar)         │
│  │  SubscriptionManager  │                              │
│  └──────────┬───────────┘                               │
│             │ Binder IPC (ITelephony.aidl)              │
└─────────────┼───────────────────────────────────────────┘
              │
              ├──→ system_server (TelephonyRegistry)
              │      状态注册中心：回调分发、权限校验
              │
              └──→ com.android.phone (PhoneApp 进程)
                     ┌────────────────────────┐
                     │  PhoneInterfaceManager   │ ← Binder 服务端
                     │  CallManager             │ ← 通话状态管理
                     │  RILJ (RIL Java)         │ ← Radio 接口层
                     │  SMSDispatcher           │ ← 短信分发
                     │  SubscriptionController  │ ← 多卡管理
                     └───────────┬────────────┘
                          │ Socket (RIL 协议)
                          ▼
                     ┌────────────────────┐
                     │  RILD (rild)        │ ← C/C++ 守护进程
                     │  /vendor/bin/rild   │
                     │  Vendor RIL .so     │ ← 厂商实现
                     └───────────┬────────┘
                          │ AT 命令 / 共享内存
                          ▼
                     ┌────────────────────┐
                     │  Baseband Modem     │ ← 基带芯片
                     └────────────────────┘
```

[已验证: AOSP android-17.0.0_r1, frameworks/base/telephony/java/android/telephony/TelephonyManager.java — 客户端代理类]
[已验证: AOSP android-17.0.0_r1, packages/services/Telephony/src/com/android/phone/PhoneApp.java — PhoneApp 进程入口]

这种多进程分离是 Android Telephony 架构的核心设计决策。原因有三：

1. **稳定性隔离**：Modem 交互（AT 命令、RIL 协议）可能因厂商实现缺陷导致崩溃。把 RILJ 和 PhoneApp 放在独立进程，使得 Telephony 崩溃不会拖垮 `system_server`。
2. **权限隔离**：Telephony 涉及 SIM 卡、IMEI、通话记录等敏感信息，独立进程便于实施细粒度的 SELinux 策略和权限控制。
3. **厂商定制隔离**：Vendor RIL 作为 `.so` 动态库加载到 RILD 中，厂商的 Modem 交互逻辑与框架代码完全解耦。

> **与 §8.8 的分工**：本节聚焦 Telephony 子系统的**架构全景、进程模型和 IPC 边界**——帮助你在 Perfetto 中理解 telephony 相关 track 和事件的来源。具体的 API 调用性能优化、ANR 防范和回调优化实践，详见 §8.8 TelephonyManager 性能优化实战。

## Telephony 子系统的三条 IPC 路径

应用进程与 Telephony 子系统的交互可以归纳为三条不同的 IPC 路径，它们的阻塞特征和性能边界完全不同。

### 路径一：App → TelephonyRegistry（system_server）—— 状态订阅

```
App.registerTelephonyCallback()
  → Binder → TelephonyRegistry (system_server)
      → 记录注册者到 mRemoveList system_server 中
```

TelephonyRegistry 运行在 `system_server` 中，是 Telephony 状态的**注册中心和广播站**。所有通过 `listen()` / `registerTelephonyCallback()` 注册的监听者都由它管理。

Modem 上报的信号变化经由 PhoneApp → RILJ → TelephonyRegistry.notifyXXX()，TelephonyRegistry 再遍历全部注册者分发回调。这意味着：

- **注册操作本身是轻量的**（一次 Binder 调用写入列表），延迟通常 < 10ms。
- **回调分发是 O(N) 的**——N 是系统中所有 TelephonyCallback 注册者数量，不限于你的 App。高频信号变化（如地铁中基站频繁切换）会导致分发风暴。

[已验证: AOSP android-17.0.0_r1, frameworks/base/services/core/java/com/android/server/TelephonyRegistry.java — 注册者列表与 notify 系列方法]

### 路径二：App → PhoneApp 进程 —— 查询类 API

```
App.getNetworkType() / getCellLocation() / getServiceState()
  → Binder (ITelephony.aidl) → PhoneInterfaceManager (com.android.phone)
      → 可能触发 RILJ → RILD → Modem 同步查询
```

查询类 API（如 `getNetworkType()`、`getCellLocation()`、`getAllCellInfo()`）通过 Binder 进入 PhoneApp 进程。部分 API 从 TelephonyRegistry 的缓存中直接返回（低延迟），部分则需要 RILJ 向 RILD/Modem 发起同步查询（高延迟）。

**关键阻塞风险**：RILJ 到 RILD 是 Socket 通信，RILD 到 Modem 可能涉及 AT 命令同步等待。如果 Modem 响应缓慢（如正在进行小区切换、弱信号场景），调用方线程会被阻塞。RIL 请求的超时默认值通常为 5-10 秒，超时后返回错误但**不会主动解除调用方的阻塞**——调用方只能等到 Binder 超时或 ANR 触发。

> 详细的 API 分级（高风险/低风险）和具体延迟数据见 §8.8。

### 路径三：PhoneApp → system_server / 其他系统服务 —— 内部协调

PhoneApp 进程内部在处理通话、数据连接等业务时，会反向调用 system_server 中的服务：

- **ConnectivityService**：数据连接的建立/断开需要通知 ConnectivityService 更新 `NetworkAgent` 和 `NetworkCapabilities`。
- **NotificationManagerService**：来电/短信通知。
- **AudioService**：通话音频路由（Audio Focus、模式切换）。
- **ActivityManagerService**：前台 Service 管理（PHONE 类型前台服务）、进程优先级调整。

这些调用对应用开发者不直接可见，但在 Perfetto 中分析 Telephony 相关性能问题时（如数据连接建立延迟、通话音频路由卡顿），需要关注 PhoneApp 进程与 system_server 之间的 Binder 交互。

## RIL（Radio Interface Layer）架构

RIL 是 Telephony 子系统中最核心的抽象层，负责将 Android 框架的电话/数据指令翻译为 Modem 可理解的命令，并将 Modem 的上行状态报告回传给框架。

### RILJ（Java 侧）

RILJ 位于 `frameworks/opt/telephony/src/java/com/android/internal/telephony/RIL.java`，运行在 PhoneApp 进程中。它的核心职责：

- **Request/Response 模型**：`RIL.sendRILRequest()` 发送请求到 RILD，维护 `mRequestList`（token → 请求映射），RILD 响应时通过 token 匹配并完成对应的异步回调。
- **Solicited/Unsolicited 消息**：
  - Solicited（请求-响应）：如 `RIL_REQUEST_GET_SIGNAL_STRENGTH`，RILJ 发送请求，等待 RILD 回复。
  - Unsolicited（主动上报）：如 `RIL_UNSOL_SIGNAL_STRENGTH`，RILD 主动通知 Modem 状态变化，RILJ 通过 `processResponse` 分发到对应的 `Handler`。
- **Socket 通信**：RILJ 通过 `RILReceiver` / `RILSender` 线程与 RILD 维持 Unix Socket 连接。Socket 断开后会自动重连。

[已验证: AOSP android-17.0.0_r1, frameworks/opt/telephony/src/java/com/android/internal/telephony/RIL.java — mRequestList、RILReceiver、processResponse]

### RILD（C/C++ 侧）

RILD 是 `/vendor/bin/rild` 守护进程，加载厂商提供的 Vendor RIL 动态库（`.so`）。它的职责：

- 接收 RILJ 的 RIL 协议请求，调用 Vendor RIL 的函数指针转化为 AT 命令或厂商私有协议。
- 管理 Modem 的 AT 命令通道（串口/共享内存/USB）。
- 将 Modem 的 URC（Unsolicited Result Code）转化为 RIL_UNSOL_* 消息发送给 RILJ。

### IRadio HAL（AIDL）

Android 17 中，IRadio HAL 已全面迁移到 AIDL（从早期的 HIDL 1.0-1.6 迁移完成）。IRadio 定义在 `hardware/interfaces/radio/` 下，按功能域拆分为多个接口：

| AIDL 接口 | 功能域 |
|-----------|--------|
| `IRadioMessaging` | SMS、MMS |
| `IRadioVoice` | 通话、来电 |
| `IRadioData` | 数据连接、APN |
| `IRadioNetwork` | 网络注册、信号、小区信息 |
| `IRadioSim` | SIM 卡管理 |
| `IRadioModem` | Modem 状态、重启 |
| `IRadioVoice` | 语音通话 |

[已验证: AOSP android-17.0.0_r1, hardware/interfaces/radio/ — AIDL 接口定义目录结构]

这种按功能域拆分的设计从 Android 13 起逐步引入，相比早期单一的 `IRadio` 接口，它允许 Modem HAL 只实现必要的功能域，也便于按需降级（如某个功能域 crash 不影响其他域）。

## TelephonyRegistry：状态注册中心

TelephonyRegistry 是 system_server 中管理 Telephony 状态分发的核心组件。理解它的内部模型对于分析信号变化导致的性能问题至关重要。

### 注册者管理

TelephonyRegistry 维护多个注册者列表，按事件类型分组：

- **CallState 注册者**：通话状态变化（IDLE/RINGING/OFFHOOK）
- **ServiceState 注册者**：服务状态变化（注册/去注册、漫游状态、制式切换）
- **SignalStrength 注册者**：信号强度变化
- **DataConnectionState 注册者**：数据连接状态（CONNECTED/DISCONNECTED/SUSPENDED）
- **CellInfo 注册者**：小区信息变化

每个注册者记录包含：调用方 UID/PID、回调接口（`ITelephonyCallback`）、Executor、监听的事件掩码。

### 回调分发路径

当 PhoneApp 中的电话框架检测到状态变化时：

```
PhoneApp (RILJ 接收 Modem 上报)
  → TelephonyRegistry.notifySignalStrength() / notifyCallState() / ...
    → Binder (system_server 内部)
      → 遍历对应事件的注册者列表
        → 对每个注册者：callback.onSignalStrengthsChanged(...)
          → Binder onTransact → App 进程 → Executor 分发
```

**性能边界**：

- TelephonyRegistry 对 SignalStrength 有内置去重——只有 level（0-4 级）变化时才分发。但对于通过 `SignalStrengthsListener` 注册的回调，每次 Modem 上报的完整 `SignalStrength` 对象都会分发（包含各制式 RSRP/RSRQ/SNR 细节）。
- 分发是顺序遍历，不并行。如果某个注册者的回调处理耗时（如 `onTransact` 被阻塞），后续注册者的分发都会被延迟。
- `notePhoneState` 和 `notifySignalStrength` 这些通知方法在 system_server 的 `phone` 线程上执行，不是在主线程上。

[已验证: AOSP android-17.0.0_r1, frameworks/base/services/core/java/com/android/server/TelephonyRegistry.java — notify 系列方法、注册者遍历]

> 回调分发的具体性能陷阱（注册者风暴、Executor 选择、重操作阻塞）和优化建议详见 §8.8。

## 电话状态机与通话模型

Android 的电话状态机在 PhoneApp 进程中维护，对外暴露为三个简单的 CALL_STATE 常量：

| 状态 | 含义 | 触发条件 |
|------|------|----------|
| `CALL_STATE_IDLE` | 无通话 | 挂断后恢复 |
| `CALL_STATE_RINGING` | 来电响铃 | 收到来电 INVITE/RING |
| `CALL_STATE_OFFHOOK` | 通话中 | 接听或主动拨号 |

应用通过 `TelephonyManager.getCallState()` 查询（Android 12+ 推荐使用 `TelephonyCallback.CallStateListener`）。在架构层面，这三个状态背后是更复杂的 Phone 状态机：

- **GsmCdmaCallTracker**：跟踪 CS（Circuit Switched）域通话状态，管理 AT 命令交互（ATH 挂断、ATA 接听等）。
- **ImsPhoneCallTracker**：跟踪 IMS（IP Multimedia Subsystem）域通话状态，VoLTE/VoWiFi/VoNR 通话走此路径。
- **CallManager**：统一管理 CS 和 IMS 两个域的通话状态，向 TelephonyRegistry 上报合并后的 CALL_STATE。

通话的双轨架构（CS 域 + IMS 域）意味着，在 VoLTE/VoWiFi 覆盖区域，通话实际上由 IMS 栈处理而非传统 CS 栈。对于性能分析，IMS 通话的建立延迟模型与 CS 通话完全不同——IMS 通话依赖 SIP 信令 over IP，延迟受网络质量影响更大。

## 短信发送管线架构

Android 的短信子系统采用三层架构：

```
App (SmsManager)
  → Binder → IccSmsInterfaceManager (PhoneApp 进程)
    → SMSDispatcher (GsmSMSDispatcher / CdmaSMSDispatcher / ImsSmsDispatcher)
      → RILJ.sendSMS() → RILD → Modem
```

### 发送路径

1. **SmsManager.sendTextMessage()**：应用层入口，参数包含目标地址、内容、PendingIntent（用于发送结果回调）。
2. **IccSmsInterfaceManager**：PhoneApp 中的 Binder 服务端，负责权限校验（SEND_SMS 权限、AppOps 检查、carrier permission）和短信分段（长短信拆分）。
3. **SMSDispatcher**：按制式分发到 `GsmSMSDispatcher`（GSM/UMTS/LTE/NR）、`CdmaSMSDispatcher`（CDMA）或 `ImsSmsDispatcher`（IMS 域，VoLTE 场景下短信走 IP）。
4. **RILJ.sendSMS()**：通过 RIL 协议将短信 PDU 发送给 RILD。

### 接收路径

1. Modem 收到短信 → RILD 通过 `RIL_UNSOL_RESPONSE_NEW_SMS` 上报。
2. RILJ 通过 `processResponse` 将 PDU 分发给对应的 `SMSDispatcher`。
3. SMSDispatcher 解析 PDU，通过 `Intent` 广播 `SMS_RECEIVED_ACTION`。
4. Android 17 中，`SMS_RECEIVED_ACTION` 广播的发送走 `BroadcastQueueModernImpl` 的有序广播调度。

**性能边界**：

- 短信发送本身是异步的——应用传入 `PendingIntent` 作为发送结果回调，不会阻塞调用线程。但 `SmsManager.sendTextMessage()` 内部的权限校验和分段处理是同步的，通常耗时 5-30ms。
- 短信接收走有序广播，如果多个接收者依次处理（特别是有的接收者做磁盘 I/O），从 Modem 上报到最终用户通知的延迟可达数百毫秒。
- Android 17 引入了 SMS/MMS 在卫星连接下的支持（见 §24.11 卫星与低带宽网络适配），IMS 域短信在弱信号下的延迟模型与地面网络差异显著。

[已验证: AOSP android-17.0.0_r1, frameworks/base/telephony/java/android/telephony/SmsManager.java]
[已验证: AOSP android-17.0.0_r1, frameworks/opt/telephony/src/java/com/android/internal/telephony/SMSDispatcher.java]

## SubscriptionManager 与多卡架构

Android 从 5.0（API 21）起原生支持多 SIM。SubscriptionManager 是多卡管理的架构核心。

### SubInfoRecord 数据模型

每张 SIM 卡对应一个 `SubscriptionInfo`，包含：

- `subscriptionId`：唯一标识（系统分配的整数值）
- `iccId`：SIM 卡的 ICCID（集成电路卡标识符）
- `displayName`：用户可编辑的 SIM 名称
- `carrierName`：运营商名称
- `mcc` / `mnc`：移动国家码/网络码
- `simSlotIndex`：所在卡槽位（0 或 1）
- `dataRoaming`：数据漫游开关状态

`SubscriptionManager.getActiveSubscriptionInfoList()` 返回当前激活的 SIM 列表。该方法是 IPC 调用（进入 PhoneApp 进程），应避免在主线程频繁调用——Android 17 建议通过 `ContentObserver` 监听 `Telephony.SimInfo` 内容 URI 的变化代替轮询。

[已验证: AOSP android-17.0.0_r1, frameworks/base/telephony/java/android/telephony/SubscriptionManager.java]
[已验证: AOSP android-17.0.0_r1, frameworks/base/telephony/java/android/telephony/SubscriptionInfo.java]

### DSDS vs DSDA 架构差异

| 模式 | 全称 | Radio 架构 | 通话/数据 |
|------|------|-----------|----------|
| DSDS | Dual SIM Dual Standby | 共享一个 Radio 收发器 | SIM 1 通话/数据时，SIM 2 信号监听中断 |
| DSDA | Dual SIM Dual Active | 独立 Radio 收发器（部分高端设备） | 两张 SIM 可同时通话/数据 |

DSDS 是主流方案。当 SIM 1 进行数据传输或通话时，SIM 2 的信号监听会出现 "tuning gap"——Modem 在 SIM 1 的空闲时隙中短暂切到 SIM 2 的信道做寻呼监听。这会导致 SIM 2 上注册的 `TelephonyCallback` 经历周期性的信号丢失上报，在 Perfetto 中表现为规律性的 `notifySignalStrength` 间隔异常。

Android 17 中，`SubscriptionController` 负责管理默认数据 SIM、默认语音 SIM、默认 SMS SIM 的选择逻辑。切换默认数据 SIM（`setDefaultDataSubId()`）会触发数据连接的断开-重连，在 Perfetto 中表现为 `DATA_DISCONNECTED → DATA_CONNECTING → DATA_CONNECTED` 状态序列。

## ConnectivityManager 集成

TelephonyManager 与 ConnectivityManager 的架构关系是理解数据连接性能的关键：

```
Telephony 子系统                    Connectivity 子系统
┌──────────────────┐               ┌──────────────────────┐
│ PhoneApp          │               │ ConnectivityService    │
│  └─ DataNetwork   │───→ 通信 ───→ │  └─ NetworkAgentInfo   │
│     (数据连接)     │               │     (网络评分、路由)   │
└──────────────────┘               └──────────────────────┘
```

当 Telephony 建立或断开数据连接时，PhoneApp 中的 `DataNetwork` / `PhoneSwitcher` 会通过 `NetworkAgent` 向 ConnectivityService 注册/注销网络。ConnectivityService 据此更新 `NetworkCapabilities`（包含传输类型 `TRANSPORT_CELLULAR`、能力 `NET_CAPABILITY_INTERNET` 等），并通知所有注册了 `NetworkCallback` 的应用。

**架构关键点**：

- Telephony 负责数据连接的**建立和维护**（APN 配置、PDN 拨号、QoS）。
- Connectivity 负责网络的**选择和路由**（Wi-Fi vs 蜂窝评分、多网络优先级）。
- 应用通过 `ConnectivityManager` 感知网络变化，通过 `TelephonyManager` 感知蜂窝信号变化——两者信息来源不同，可能暂时不一致（如数据连接已断开但信号强度仍显示正常）。

> ConnectivityManager 的详细架构和性能分析见 §1.62。

## 在 Perfetto 中定位 Telephony 相关事件

分析 Telephony 相关的性能问题时，在 Perfetto 中关注以下信号：

**PhoneApp 进程（`com.android.phone`）**：
- Binder 线程池中的 `binder:phone` 线程——ITelephony Binder 调用的服务端
- `RILReceiver` / `RILSender` 线程——Socket 通信
- `Phone` 线程——电话状态机 Handler

**system_server 进程**：
- `phone` 线程——TelephonyRegistry 的通知处理
- Binder 事务中搜索 `com.android.phone` 相关调用

**App 进程**：
- 主线程上的 `TelephonyCallback.onSignalStrengthsChanged` 等 Binder 回调
- 主线程上的 `TelephonyManager.getXxx()` Binder 调用

```sql
-- 查找 TelephonyManager IPC 调用（App → PhoneApp）
SELECT slice.name, slice.ts, slice.dur, thread.name as thread_name
FROM slice
JOIN thread_track ON slice.track_id = thread_track.id
JOIN thread ON thread_track.utid = thread.id
JOIN process USING (upid)
WHERE process.name = 'com.android.phone'
  AND slice.name LIKE 'binder%'
ORDER BY slice.dur DESC
LIMIT 50;
```

> 更多 Perfetto SQL 技巧见 §13.22 Perfetto SQL 查询手册。
