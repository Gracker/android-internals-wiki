# 1.49 Android 17 分阶段安装状态机与提交/恢复链路


## 状态模型

源码基线为 Android 17 / API 37 / AOSP `android-17.0.0_r1`。完整机制见 [1.45 Android 17 分阶段安装状态机](1.45-staged-install-state-machine.md)。状态持久化与启动恢复由下述路径衔接。

`PackageInstallerSession` 用三个分阶段结果字段描述状态：

| 字段组合 | 含义 |
|---|---|
| `ready=false, applied=false, failed=false` | 尚未完成重启前验证 |
| `ready=true, applied=false, failed=false` | 重启前验证已通过，可等待重启应用 |
| `ready=false, applied=true, failed=false` | 重启后 APK/APEX 收尾成功 |
| `ready=false, applied=false, failed=true` | 验证、激活或安装失败 |

`mDestroyed` 表示会话生命周期和资源清理状态，不是第四个分阶段结果。`setSessionApplied()` 与 `setSessionFailed()` 会调用 `destroy()`，放弃会话等路径也可能进入销毁状态，因此不能只用 `mDestroyed` 推导 `applied` 或 `failed`。

`ready` 不表示“安装进行中”。它表示重启前验证已经完成，并且会话已按正确顺序与 apexd 对齐，设备可以在后续重启时应用分阶段内容。

## 从提交到 `ready`

下面的顺序图保留影响一致性的节点，省略普通 APK 验证器的内部消息跳转。

```text
PackageInstallerSession.commit()
  → 密封会话；多包会话同时密封子会话
  → 流式校验 / 安装处理器
  → 分阶段会话进入验证
       → StagingManager.commitSession()
            → 记录会话，处理观察者
       → StagedSession.verifySession()
            → PackageSessionVerifier.verifyStaged()
                 → checkActiveSessions()
                 → checkRollbacks()
                 → checkOverlaps()
                 → verifyApex() / submitStagedSession()
                 → endVerification()
                      → 支持检查点时 startCheckpoint(2)
                      → session.setSessionReady()
                      → 含 APEX 时 markStagedSessionReady()
```

`StagingManager.commitSession()` 只把会话纳入 StagingManager 并处理观察者；它不负责 apexd 激活，也不把会话直接推进到 `ready`。

`endVerification()` 先写入框架层会话的 `ready` 状态，再调用 apexd 的 `markStagedSessionReady()`。源码注释明确说明，这个顺序用于避免“apexd 已进入 `ready`，但 PackageInstaller 会话尚未进入 `ready`”的跨重启不一致。

重启前验证包含活动会话、回滚、包重叠、APEX 提交与签名等检查。重启后的恢复侧重核对 apexd 激活状态、检查点状态和 APK 安装收尾；它不是一套统一的“重启后重新验证签名、权限、依赖和应用数据”流程。

## 状态怎样持久化

三个状态写方法都在更新字段后调用 `mCallback.onSessionChanged(this)`。`PackageInstallerService` 的回调会：

1. `session.markUpdated()`；
2. 通过 `RequestThrottle` 调度 `writeSessions()`；
3. 由 `AtomicFile` 写入 `/data/system/install_sessions.xml`。

这条路径也负责保存 `isSessionReady`、`isSessionApplied`、`isSessionFailed`、错误码与错误信息。`dispatchSessionFinished()` 面向状态接收方和回调，不是会话 XML 持久化的唯一触发点。

## 开机恢复筛选

`PackageInstallerService.restoreAndApplyStagedSessionIfNeeded()` 从已经恢复到内存的会话中筛选分阶段会话：

- 子会话的父会话丢失时标记失败；
- 只把已提交、非终态、没有父会话的顶层会话交给 `StagingManager.restoreSessions()`；
- 调用恢复方法时不持有 `mSessions` 锁，因为 APK 原子安装还会查询会话。

`restoreSessions()` 接着处理：

1. `sys.boot_completed` 已为 `true` 时不再恢复。
2. 校验输入都是已提交、非终态的父会话。
3. 设备正在升级时，因验证前提可能变化，全部标记失败。
4. 查询 `supportsCheckpoint()` 与 `needsCheckpoint()`。
5. 不支持检查点却出现多个顶层分阶段会话时抛出异常。
6. 收集 apexd 或框架层无法识别的悬空会话。
7. 已销毁会话执行放弃操作；尚未进入 `ready` 的会话在 `mBootCompleted` 的异步结果完成后重新验证，并从本轮恢复集合移除。
8. 核对 apexd 会话处于 `activated`、`failed`、`staged` 还是非法状态。
9. 对可继续的会话调用 `resumeSession()`。

尚未进入 `ready` 的会话延迟到系统启动完成后重新验证，以等待验证依赖的系统组件可用。本轮启动恢复不会把它当作 `ready` 会话安装。

## `resumeSession()` 与 `applied`

检查点设备只有在 `needsCheckpoint == true` 时继续恢复；支持检查点但当前不在检查点模式时，会话会被标记失败。

含 APEX 的会话要先确认：

- APK-in-APEX 安装结果；
- APK 与 APK-in-APEX 没有重复包名；
- 回滚用户数据的快照/恢复已处理。

之后 `installApksInSession()` 阻塞等待 `session.installSession().get()`。它最终进入 `PackageInstallerSession.install()`；所有 APK/子会话异步结果成功时，由 `setSessionApplied()` 写入 `applied`，任一异步结果失败则由 `setSessionFailed()` 写入 `failed`。

`applied` 来自会话安装完成回调，不由 `resumeSession()` 直接置位。多包父会话聚合子会话异步结果和警告，但父子会话的校验、`packageName` 与结果回调仍有各自边界。

## APEX `success` 与系统启动完成

检查点设备上的 APEX 会话在 APK 收尾成功后，会话 ID 先加入 `mSuccessfulStagedSessionIds`。到 `PHASE_BOOT_COMPLETED`，`markStagedSessionsAsSuccessful()` 遍历列表，并对每个 ID 分别调用 `mApexManager.markStagedSessionSuccessful()`。

这是延迟确认，不会把多个 ID 合成一次 apexd RPC。不支持检查点的设备会在 `resumeSession()` 中立即确认对应 ID 成功。

APEX 激活已在重启过程中由 apexd 完成；系统启动完成阶段的 `markStagedSessionSuccessful()` 只负责成功确认，不能称作“启动完成后批量激活 APEX”。

## 检查点与失败恢复

`onInstallationFailure()` 先把会话标记为 `failed`，再调用 `abortCheckpoint()`。该辅助方法只在 `supportsCheckpoint && needsCheckpoint` 时执行以下操作：

- 写 `/metadata/staged-install/failure_reason.txt`；
- 请求 apexd 回退活动会话；
- 调用 StorageManager `abortChanges()`。

该辅助方法发生异常时，兜底路径会再次请求 apexd 回退，并调用 `PowerManager.reboot()`。

不支持检查点的设备还要根据会话内容处理。纯 APK 安装失败会在标记 `failed` 后返回；含 APEX 的安装失败会尝试 `revertActiveSessions()`，成功后重启以恢复旧 APEX。并非所有分阶段安装失败都会中止检查点或触发重启。

## 可观测状态

下面两个 shell 入口来自 Android 17 `PackageManagerShellCommand`：

```bash
adb shell pm list staged-sessions
adb shell pm get-stagedsessions
```

命令用于查看分阶段会话与状态，不提供每个验证子步骤的耗时。时序分析可以采集包管理器的 atrace，并搜索 `StagingManagerTiming`、`restoreSessions`、`installApksInSession`，同时对照 `install_sessions.xml`、logcat、apexd 会话状态和检查点状态。

排障时优先确认：

- 会话是未验证、`ready`、`applied`、`failed` 还是单独进入销毁状态；
- 框架层与 apexd 是否识别同一个顶层会话 ID；
- 是否处于检查点模式；
- 会话是纯 APK、纯 APEX 还是多包会话；
- 失败发生在重启前验证、APEX 激活、APK 安装还是成功确认阶段。
