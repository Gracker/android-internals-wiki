### 🔹 锚点 1：Staged Install 状态机架构
Staged Install 状态机实现了原子性应用安装流程，通过布尔状态位机制确保安装过程的可靠性和一致性（Staged Install 自 Android 10 / API 29 引入，Android 17 在此基础上保持语义稳定）。

> ⚠️ 此处原始 Kotlin 伪代码（虚构的 `enum State { IDLE, PENDING, ABORT, COMMITTED, DESTROYED }` 和 `transition()` 方法）已移除——AOSP 中 `PackageInstallerSession` 并无此枚举或状态转换函数。真实实现为四个独立布尔位 `mSessionReady / mSessionApplied / mSessionFailed / mDestroyed` + 三个 setter 推进，详见[源码级补充](#真实状态字段定义packageinstallersessionjava-line-670-685)。

### 🔹 锚点 2：Pre-reboot Verification 机制
Android 17 的重启前验证机制确保系统重启后应用的完整性：

1. **签名验证**：重启后验证 APK 签名有效性
2. **权限检查**：重新验证应用权限
3. **依赖关系检查**：验证系统组件依赖
4. **数据完整性检查**：确保应用数据未被损坏

> ⚠️ 此处原始 Kotlin 伪代码（虚构的 `PackageManagerService.verifyPreReboot()` 方法）已移除——AOSP 中并无此方法。真实的验证路径为 `commit()` → handler 6 跳 → `onVerificationComplete()` → `mStagingManager.commitSession()`，详见[增量勘误：commit → handler 派发链](#一client-端-commit--handler-派发完整链)。

### 🔹 锚点 3：Boot-time Restore 机制
启动时恢复机制确保应用在系统重启后能够正确恢复到安装完成状态：

1. **状态恢复**：从持久化存储中恢复安装状态
2. **数据迁移**：必要的数据迁移操作
3. **权限恢复**：重新应用权限设置
4. **组件注册**：重新注册系统组件

> ⚠️ 此处原始 Kotlin 伪代码（虚构的 `PackageManagerService.restoreBootTimeInstallations()` 方法）已移除——AOSP 中并无此方法。真实的恢复路径为 `PMS.systemReady()` → `restoreAndApplyStagedSessionIfNeeded()` → `StagingManager.restoreSessions()`，详见[增量勘误：restore 链路完整调用链](#三restore-链路完整调用链)。

### 🔹 锚点 4：PackageInstallerSession 链路优化
Android 17 对 PackageInstallerSession 进行了多项优化：

1. **批量操作支持**（Multi-package session）：
   - 支持 parent + child session 批量安装
   - parent 仅做调度，child 各自 validate
   - APK child 与 APEX child 分别走不同安装路径

2. **并行处理优化**：
   - `CompletableFuture.allOf()` 并发控制
   - APEX 延迟激活（boot 完成后批量标记）
   - `extractNativeLibraries` 改用专用线程

3. **内存管理改进**：
   - `appMetadataFile` 大小校验防 DoS
   - 流式 native lib 提取避免共享 IoThread 阻塞
   - 终态自动 `destroy()` 清理

> ⚠️ 此处原始 Kotlin 伪代码（虚构的 `PackageInstallerService.installMultiplePackages()` 使用 `parallelStream()`）已移除——AOSP 中并无此方法。Multi-package 通过 `PackageInstallerSession` 的 `commit()` + child session seal 实现，详见[APK-only vs Multi-package 差异表](#四apk-only-vs-multi-package-session-状态机差异核心增量表)。

## 扩展

### 🔸 扩展点 1：与 APEX 的协同
Staged Install 与 APEX (Android Pony EXpress，AOSP 模块化系统) 的深度协同：

1. **系统组件集成**：
   - APEX session 通过 `mApexManager.markStagedSessionReady()` 在 verify 链中激活
   - `markStagedSessionsAsSuccessful()` 在 `PHASE_BOOT_COMPLETED` 批量通知 apexd
   - APEX + APK 同包冲突检测（`checkDuplicateApkInApex`）

2. **版本管理**：
   - APEX 版本兼容性检查
   - `snapshotAndRestoreForApexSession` rollback 调用
   - 升级路径优化

3. **跨重启一致性**：
   - `failure_reason.txt` 持久化失败原因
   - `InstallLocationUtils.getStorageManager().abortChanges()` 文件系统回滚
   - APEX `revertActiveSessions()` 与 checkpoint 协同

### 🔸 扩展点 2：企业级部署优化
企业级场景下的深度优化：

1. **大规模部署**：
   - Multi-package session 批量部署（需 checkpoint 支持）
   - 非 checkpoint 设备 fail-fast 限制单 staged session
   - `maybeFinishChildSessions` 同步通知所有 child

2. **安全要求**：
   - `THROW_EXCEPTION_COMMIT_WITH_IMMUTABLE_PENDING_INTENT` 强制 mutable PendingIntent
   - 签名验证在 verify 链中执行
   - `appMetadataFile` 大小校验防 DoS

3. **管理工具**：
   - `PackageInstallerService` session 状态查询
   - `SessionInfo` 序列化（XML 持久化 `isSessionReady/isSessionApplied/isSessionFailed`）
   - Perfetto `StagingManagerTiming` trace 分析

### 🔸 扩展点 3：故障排查与恢复机制
完善的故障排查和恢复机制：

1. **故障检测**：
   - `setSessionFailed(errorCode, errorMessage)` 精确错误码
   - `mSessionErrorMessage` 持久化到 XML
   - `failure_reason.txt` 跨重启错误传递

2. **恢复策略**：
   - Checkpoint 设备：`abortChanges()` 回滚到上次 checkpoint
   - 非 checkpoint 设备：`revertActiveSessions()` + reboot
   - `handleNonReadyAndDestroyedSessions` 区分 destroyed / unverified / active

3. **调试工具**：
   - `StagingManagerTiming` Perfetto trace track
   - `TimingsTraceLog` 开机恢复耗时分段
   - `adb shell pm get-stagedsessions` 查看状态

```java
void setSessionReady() {                          // 仅置位，不销毁（中间态）
    synchronized (mLock) {
        if (mDestroyed || mSessionFailed) return; // 终态守卫
        mSessionReady = true;
        mSessionApplied = false;
        mSessionFailed = false;
        // ...
    }
    mCallback.onSessionChanged(this);
}

void setSessionApplied() {                        // 成功终态
    synchronized (mLock) {
        if (mDestroyed || mSessionFailed) return;
        mSessionReady = false;
        mSessionApplied = true;
        mSessionFailed = false;
        // ...
    }
    destroy(null);                                // 进入 DESTROYED
    mCallback.onSessionChanged(this);
}

void setSessionFailed(int errorCode, String errorMessage) {  // 失败终态
    synchronized (mLock) {
        if (mDestroyed || mSessionFailed) return;
        mSessionReady = false;
        mSessionApplied = false;
        mSessionFailed = true;
        mSessionErrorCode = errorCode;
        mSessionErrorMessage = errorMessage;
    }
    destroy("Session marked as failed: " + errorMessage);  // 进入 DESTROYED
    mCallback.onSessionChanged(this);
}
```

```java
void restoreSessions(@NonNull List<StagedSession> sessions, boolean isDeviceUpgrading) {
    TimingsTraceLog t = new TimingsTraceLog("StagingManagerTiming", Trace.TRACE_TAG_PACKAGE_MANAGER);
    t.traceBegin("restoreSessions");

    if (SystemProperties.getBoolean("sys.boot_completed", false)) return;

    // ... 多 session 限制：仅 checkpoint 设备允许多 staged
    if (sessions.size() > 1 && !supportsCheckpoint) {
        throw new IllegalStateException("Detected multiple staged sessions on a device without"
                + " fs-checkpoint support");
    }

    handleNonReadyAndDestroyedSessions(sessions); // !isSessionReady → mBootCompleted.thenRun → verifySession

    // ... APEX session 状态校验 ...
    for (StagedSession session : sessions) {
        try {
            resumeSession(session, supportsCheckpoint, needsCheckpoint);
        } catch (PackageManagerException e) {
            onInstallationFailure(session, e, supportsCheckpoint, needsCheckpoint);
        }
    }
    t.traceEnd();
```

### 失败回滚实路径（`StagingManager.abortCheckpoint()` line 105）

```java
private void abortCheckpoint(String failureReason, boolean supportsCheckpoint,
        boolean needsCheckpoint) {
    Slog.e(TAG, failureReason);
    try {
        if (supportsCheckpoint && needsCheckpoint) {
            // 写入失败原因到 /metadata/staged-install/failure_reason.txt
            try (BufferedWriter writer = new BufferedWriter(
                    new FileWriter(mFailureReasonFile))) {
                writer.write(failureReason);
            }
            if (mApexManager.isApexSupported()) {
                mApexManager.revertActiveSessions();
            }
            InstallLocationUtils.getStorageManager().abortChanges(
                    "abort-staged-install", false /*retry*/);
        }
    } catch (Exception e) {
        // 兜底：即使 abortChanges 异常，也要 revert APEX + reboot
        if (mApexManager.isApexSupported()) mApexManager.revertActiveSessions();
        mPowerManager.reboot(null);
    }
}
```

### 状态机修正版全景图（基于源码）

```
client create ─►  [IDLE: mSealed=false]
client write  ─►  [WRITTEN: mSealed=true]
commit()    ───►  [STAGED: 已提交给 StagingManager]  ← commitSession() 记录 session
                       │
resumeSession() ──►  [installApksInSession() → PackageInstallerSession.install()]
                       │
                       ├─ 成功 → setSessionApplied()   (mSessionApplied=true, destroy)
                       └─ 失败 → setSessionFailed()    (mSessionFailed=true, destroy)
```

**状态机最终公式**：
- `mSessionReady ∧ ¬mSessionApplied ∧ ¬mSessionFailed ∧ ¬mDestroyed` ＝ pre-reboot verification 已通过，等待重启/后续应用
- `mSessionApplied ∧ mDestroyed` ＝ 成功终态
- `mSessionFailed ∧ mDestroyed` ＝ 失败终态
- `mDestroyed ∧ ¬mSessionApplied ∧ ¬mSessionFailed` ＝ 仅销毁（可能为 abandoned）

### 性能调优点（实测可观测）

1. **APEX 成功延迟标记**：`markStagedSessionsAsSuccessful()`（line 425）在 `PHASE_BOOT_COMPLETED` 遍历 `mSuccessfulStagedSessionIds`，逐 id 调用 `markStagedSessionSuccessful()` 做成功确认。这是延迟确认而非合成单次 RPC，APEX activation 本身已在重启过程由 apexd 完成。
2. **verifySession 延后到 boot 完成**：`mBootCompleted.thenRun(() -> session.verifySession())`，避免开机关键路径 PM 重负载。
3. **Checkpoint 设备才允许多 staged**：`sessions.size() > 1 && !supportsCheckpoint` 时直接抛 `IllegalStateException`——非 checkpoint 设备 fail-fast。

## 增量勘误（2026-07-02）：commit → restore 完整调用链 + APK-only vs Multi-package 差异

基于 AOSP `android-17.0.0_r1` 源码（`PackageInstallerSession.java:2392-2440`、`StagingManager.java:497-737`、`PackageSessionVerifier.java:341-410`、`PackageManagerService.java:4656-4657`）的二次验证，对前述章节进行以下补充。

### 一、client 端 commit() → handler 派发完整链

`commit()` 实际只是入口，从 `markAsSealed()` 到调 `mStagingManager.commitSession(mStagedSession)`，中间经 6 跳 handler 消息：

```
commit(statusReceiver, forTransfer)         [PackageInstallerSession.java:2392]

  ├─ [multi-package] 递归 seal 所有 children [2404-2418]
  ├─ appMetadataFile.length() > sizeLimit 检查 [2428-2434]
  └─ dispatchSessionSealed() → MSG_ON_SESSION_SEALED
       └─ handleSessionSealed() [2499-2511]
            ├─ mCallback.onSessionSealedBlocking(this)
            └─ dispatchStreamValidateAndCommit() → MSG_STREAM_VALIDATE_AND_COMMIT
                 └─ handleStreamValidateAndCommit() [2513-2530]
                      ├─ 遍历 child.streamValidateAndCommit()
                      └─ streamValidateAndCommit()  [2697-2745]
                           └─ dispatchStreamValidateAndCommit → MSG_INSTALL
                                └─ handleInstall() → install() → verify()
                                     └─ runExtractNativeLibraries() [3445-3479, 专用线程]
                                          └─ handleOnNativeLibsExtracted() → verifyNonStaged() / resumeVerify()
                                               └─ onVerificationComplete() [4234-4249]

```

注意 `commitSession()` 在 StagingManager 里的实际职责只是 `createSession()` + `notifyStagedApexObservers()`（StagingManager.java:497-507），**实际的 apexd activation 由 `PackageSessionVerifier#endVerification()` 里的 `markStagedSessionReady()` 完成**。

### 二、PackageSessionVerifier#endVerification() 的关键调用顺序

源码注释（line 351-360）直陈设计动机：

> "Proactively mark session as ready before calling apexd. Although this call order looks counter-intuitive, this is the easiest way to ensure that session won't end up in the inconsistent state."

```java
session.setSessionReady();   // ① PMS 内部状态置为 ready
if (hasApex) mApexManager.markStagedSessionReady(sessionId);  // ② apexd 进入 ready 状态
```

**先 setSessionReady() 再 markStagedSessionReady()**——若顺序颠倒，重启时序异常下会出现「apex 已激活但 session 未标记 ready」的不一致状态。

### 三、restore 链路完整调用链

```

                      ├─ [multi-session]  !supportsCheckpoint → IllegalStateException [633-635]
                      ├─ handleNonReadyAndDestroyedSessions [599-622]（destroyed/abandon + 未 ready 重 verify）
                      ├─ APEX 状态一致性检查（apexd vs PMS）[677-721]
```

### 四、APK-only vs Multi-package Session 状态机差异（核心增量表）

| 维度 | APK-only 单 session | Multi-package session |
|---|---|---|
| `streamValidateAndCommit` | 自己执行 `prepareDataLoaderLocked()` + validate | parent **完全跳过 validate**（line 2710 提前 return）；只让 child 各自 validate |
| `commit()` 中 seal 顺序 | 仅自己 | parent + 所有 child 都 seal；child 用 `markAsSealed(null, forTransfer)` |
| `markStagedSessionReady` | 直接调 | `submitSessionToApexService` 仅把 apex child id 塞进 `ApexSessionParams.childSessionIds` |
| `restoreSessions` 校验 | 无 multi-session 限制 | `sessions.size() > 1 && !supportsCheckpoint` → fail-fast |
| `abandon` parent | 仅自己 | `maybeFinishChildSessions()` 把所有 child 标同样 status |
| `installApksInSession` | session.installSession().get() | 同上；child 各自有 `install()`，并发受 `CompletableFuture` 控制 |

## 源码复核后的状态模型

本文以 Android 17 / API 37 / AOSP `android-17.0.0_r1` 为准。完整机制见 [1.45 Android 17 Staged Install 状态机](1.45-staged-install-state-machine.md)；本节集中纠正历史审计里仍会影响排障的状态和恢复边界。

`PackageInstallerSession` 用三个 staged outcome 字段描述结果：

| 字段组合 | 含义 |
|---|---|
| `ready=false, applied=false, failed=false` | 尚未完成 pre-reboot verification |
| `ready=true, applied=false, failed=false` | pre-reboot verification 已通过，可等待重启应用 |
| `ready=false, applied=true, failed=false` | 重启后 APK/APEX 收尾成功 |
| `ready=false, applied=false, failed=true` | verification、activation 或安装失败 |

`mDestroyed` 是 session 生命周期/资源清理状态，不是第四个 staged outcome。`setSessionApplied()` 与 `setSessionFailed()` 会调用 `destroy()`，abandon 等路径也可能产生 destroyed；所以不能只用 `mDestroyed` 推导 applied 或 failed。

`ready` 也不表示“安装进行中”。它表示重启前验证已经完成，并且 session 已按正确顺序与 apexd 对齐，设备可以通过后续重启应用 staged 内容。

## 从 commit 到 ready

下面的顺序图保留影响一致性的节点，省略普通 APK 验证器的内部消息跳转。

```text
PackageInstallerSession.commit()
  → seal session；multi-package 同时 seal children
  → stream validate / install handler
  → staged session 进入 verify
       → StagingManager.commitSession()
            → 记录 session，处理 observer
       → StagedSession.verifySession()
            → PackageSessionVerifier.verifyStaged()
                 → checkActiveSessions()
                 → checkRollbacks()
                 → checkOverlaps()
                 → verifyApex() / submitStagedSession()
                 → endVerification()
                      → 支持 checkpoint 时 startCheckpoint(2)
                      → session.setSessionReady()
                      → 含 APEX 时 markStagedSessionReady()
```

`StagingManager.commitSession()` 只把 session 纳入 StagingManager 并处理 observer；它不负责 apexd activation，也不把 session 直接推进到 ready。

`endVerification()` 先写 framework session ready，再调用 apexd `markStagedSessionReady()`。源码注释明确说明这个顺序用于避免“apexd 已 ready，但 PackageInstaller session 尚未 ready”的跨重启不一致。

Pre-reboot verification 发生在重启前，包含 active session、rollback、package overlap、APEX 提交与签名等检查。重启后的 restore 侧重核对 apexd activation 状态、checkpoint 状态和 APK 安装收尾；不能把它描述成一套统一的“重启后重新验证签名、权限、依赖和应用数据”流程。

## 状态怎样持久化

三个 setter 都在更新字段后调用 `mCallback.onSessionChanged(this)`。`PackageInstallerService` 的 callback 会：

1. `session.markUpdated()`；
2. 通过 `RequestThrottle` 调度 `writeSessions()`；
3. 由 `AtomicFile` 写入 `/data/system/install_sessions.xml`。

这条路径也负责保存 `isSessionReady`、`isSessionApplied`、`isSessionFailed`、错误码与错误信息。`dispatchSessionFinished()` 面向状态接收方和回调，不是 session XML 持久化的唯一触发点。

## 开机恢复筛选

`PackageInstallerService.restoreAndApplyStagedSessionIfNeeded()` 从已经恢复到内存的 sessions 中筛选 staged session：

- child 的 parent 丢失时标记失败；
- 只把 committed、非终态、没有 parent 的顶层 session 交给 `StagingManager.restoreSessions()`；
- 调用 restore 时不持有 `mSessions` 锁，因为 APK atomic install 还会查询 session。

`restoreSessions()` 接着处理：

1. `sys.boot_completed` 已为 true 时不再恢复。
2. 校验输入都是 committed、非终态的 parent。
3. 设备正在升级时，因验证前提可能变化，全部标记失败。
4. 查询 `supportsCheckpoint()` 与 `needsCheckpoint()`。
5. 没有 checkpoint 支持却出现多个顶层 staged session 时抛出异常。
6. 收集 apexd 不认识或 framework 不认识的 dangling session。
7. destroyed session 执行 abandon；尚未 ready 的 session 在 `mBootCompleted` future 完成后重新 verification，并从本轮 resume 集合移除。
8. 核对 apexd session 是 activated、failed、staged 还是非法状态。
9. 对可继续的 session 调用 `resumeSession()`。

非 ready session 延迟到 boot completed 后重新验证，是为了等待验证依赖的系统组件可用。它没有在本轮 boot restore 中被当作 ready session 安装。

## `resumeSession()` 与 applied

checkpoint 设备只有在 `needsCheckpoint == true` 时继续 resume；支持 checkpoint 但当前不在 checkpoint 模式时，session 会被标记失败。

含 APEX 的 session 要先确认：

- apk-in-apex 安装结果；
- APK 与 APK-in-APEX 没有重复包名；
- rollback user data snapshot/restore 已处理。

之后 `installApksInSession()` 阻塞等待 `session.installSession().get()`。它最终进入 `PackageInstallerSession.install()`；所有 APK/child future 成功时由 `setSessionApplied()` 写 applied，任一 future 失败则由 `setSessionFailed()` 写 failed。

所以 applied 的来源是 session install completion，不是 `resumeSession()` 直接置位。multi-package parent 聚合 child future 和 warnings，但 parent/child 的 validate、packageName 与结果回调仍有各自边界。

## APEX success 与 boot completed

checkpoint 设备上的 APEX session 在 APK 收尾成功后，session id 先加入 `mSuccessfulStagedSessionIds`。到 `PHASE_BOOT_COMPLETED`，`markStagedSessionsAsSuccessful()` 遍历列表，并对每个 id 分别调用 `mApexManager.markStagedSessionSuccessful()`。

这是一处延迟确认，不是把多个 id 合成一次 apexd RPC。非 checkpoint 设备会在 `resumeSession()` 中立即对该 id 调用 successful。

APEX activation 已在重启过程由 apexd 完成；boot completed 阶段的 `markStagedSessionSuccessful()` 是成功确认，不能称作“boot 完成后批量激活 APEX”。

## checkpoint 与失败恢复

`onInstallationFailure()` 先把 session 标记 failed，再调用 `abortCheckpoint()`。该 helper 只有在 `supportsCheckpoint && needsCheckpoint` 时：

- 写 `/metadata/staged-install/failure_reason.txt`；
- 请求 apexd revert active sessions；
- 调用 StorageManager `abortChanges()`。

上述 helper 自身发生异常时，兜底路径再次请求 apexd revert，并调用 `PowerManager.reboot()`。

非 checkpoint 设备还要看 session 内容。APK-only 失败在标记 failed 后返回；含 APEX 的失败会尝试 `revertActiveSessions()`，成功后 reboot 以恢复旧 APEX。因而“所有 staged failure 都 abort checkpoint”与“所有失败都 reboot”都不准确。

## 可观测状态

下面两个 shell 入口来自 Android 17 `PackageManagerShellCommand`：

```bash
adb shell pm list staged-sessions
adb shell pm get-stagedsessions
```

命令用于查看 staged session 与状态，不提供每个 verification 子步骤的耗时。时序分析可以采集 package manager atrace，并搜索 `StagingManagerTiming`、`restoreSessions`、`installApksInSession`，同时对照 `install_sessions.xml`、logcat、apexd session 状态和 checkpoint 状态。

排障时优先确认：

- session 是未验证、ready、applied、failed 还是单独 destroyed；
- framework 与 apexd 是否认识同一个顶层 session id；
- 是否处于 checkpoint 模式；
- session 是 APK-only、APEX-only 还是 multi-package；
- failure 是否发生在 pre-reboot verification、APEX activation、APK install 或成功确认。
