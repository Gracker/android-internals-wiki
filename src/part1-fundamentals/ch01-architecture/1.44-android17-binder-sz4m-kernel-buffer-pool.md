# 1.44 Android 17 Binder 4 MiB 映射上限、异步预算与优先级状态

源码锚点如下：

- Android 平台：`android-17.0.0_r1`，API 37；
- Android common kernel：`android17-6.18-2026-06_r6`。

kernel r6 把单个 `binder_alloc` 接受的 mmap 长度限制在 4 MiB；Android 17 的 AOSP libbinder 仍只请求 `1 MiB - 2 × page_size`。标准进程不会自动获得 4 MiB，也不存在所有进程共同使用的一块固定 4 MiB 池。

这三个问题需要分开：

1. 接收进程的 Binder 地址窗口有多大，物理页何时安装；
2. 同步事务与 oneway 如何共享地址空间，`free_async_space` 怎样限制 oneway；
3. `set_priority_called`、`saved_priority` 与 `BINDER_PRIO_*` 状态怎样避免优先级恢复竞态。

事务排队和 node 级 oneway 串行流程见 [Binder IPC 异步批处理流水线](./01.25-binder-ipc-async-pipeline.md)，更完整的容量分析见 [Binder 事务缓冲区性能](./30-binder-transaction-buffer-performance.md)。

## 一、约 1 MiB 与 4 MiB 描述的是两层限制

### 1. libbinder 请求的映射长度

Android 17 `ProcessState.cpp` 用下面的常量调用 Binder 设备的 `mmap()`：

```cpp
#define BINDER_VM_SIZE \
    ((1 * 1024 * 1024) - sysconf(_SC_PAGE_SIZE) * 2)
```

4 KiB 页设备请求 1016 KiB，16 KiB 页设备请求 992 KiB。这里扣除的是两个系统页大小，不能把结果写成精确 1 MiB。

### 2. 驱动只接受不超过 4 MiB

kernel r6 的 `binder_alloc_mmap_handler()` 用下面的表达式确定 `binder_alloc` 的地址窗口：

```c
alloc->buffer_size = min_t(unsigned long,
        vma->vm_end - vma->vm_start, SZ_4M);
```

标准 libbinder 的请求小于驱动上限，所以有效 `buffer_size` 仍是 1016 KiB 或 992 KiB。其他用户态 Binder 实现可以请求更大的 VMA，但驱动只管理前 4 MiB；是否修改产品侧 libbinder 属于设备实现选择，不能写成 Android 17 默认行为。

### 3. mmap 长度不等于常驻物理内存

`binder_alloc_mmap_handler()` 建立地址范围、页面指针数组和初始 free buffer。事务分配成功后，`binder_install_buffer_pages()` 才为覆盖该 buffer 的范围安装页面。扩大 VMA 会增加可寻址容量和最大内存压力，不会在 mmap 成功时立刻提交同等大小的全部物理页。

Binder buffer 归接收进程所有。发送线程把 Parcel 交给驱动后，驱动在目标进程的 `binder_alloc` 中分配 buffer，并把数据复制到目标可见的映射页。两个进程没有直接共享同一个 `binder_alloc`。

## 二、分配器怎样处理大小、碎片与页面

### 1. 驱动分配的大小包含三部分

`sanitized_size()` 对 `data_size`、`offsets_size` 与 `extra_buffers_size` 分别按指针宽度对齐后求和。零长度事务也会得到一个指针宽度的大小，以保持 buffer 地址唯一。

- `data_size`：Parcel 的普通数据；
- `offsets_size`：Binder object、FD 等对象的偏移数组；
- `extra_buffers_size`：scatter-gather 事务的附加 buffer。

因此，`Parcel.dataSize()` 只反映应用可见数据的一部分，不能直接当作驱动最终占用。

### 2. free-buffer 红黑树执行最佳适配

`binder_alloc_new_buf_locked()` 从按大小组织的 free-buffer 红黑树中寻找能容纳请求的最小空闲块。块大于请求时，驱动把它切分；释放时再与地址相邻的空闲块合并。

最佳适配减少了一部分外部碎片，却无法保证“总空闲字节够用”就一定成功。若空闲空间被分成多个小块，没有一段可以容纳当前请求，函数返回 `-ENOSPC`。异步预算不足也返回 `-ENOSPC`。

分配地址成功后还要安装页面。页面分配失败可在 `binder_install_buffer_pages()` 路径返回内存错误，驱动随后释放刚取得的 buffer。地址空间不足与物理页分配失败是两类不同故障。

### 3. buffer 的释放晚于发送完成

调用方收到 `BR_TRANSACTION_COMPLETE`，只表示驱动已经接收本次提交。目标进程中的请求 buffer 通常要等接收方 Parcel 释放并发送 `BC_FREE_BUFFER` 后才回到 free tree。

同步请求会等待回复；同一 node 上的后续 oneway 事务还可能停留在 `async_todo`。高频 oneway 事务的生产速度超过服务端消费速度时，多个已提交 buffer 会同时占用目标进程的地址窗口。

## 三、async 预算保留同步事务余量

### 1. 一半容量是记账额度

映射初始化时，驱动设置：

```c
alloc->free_async_space = alloc->buffer_size / 2;
```

这行代码没有切出一块独立的 oneway 内存。同步和异步事务都从同一棵 free-buffer 树分配；异步事务还要通过 `free_async_space` 检查。同步事务不扣 async 额度，但仍受总空闲空间、连续块大小和页面分配结果约束。

异步分配成功后，驱动按对齐后的事务大小扣减 `free_async_space`；buffer 释放时归还相应大小。初始值等于总地址窗口的一半，目的是阻止 oneway 事务把整个窗口占满，为同步请求和回复留下空间。

### 2. 没有固定的“安全单笔大小”

一笔事务能否成功取决于目标进程当前状态：

- 地址窗口的连续空闲块；
- 并发请求、回复和待处理 oneway 事务的占用；
- data、offsets 与 extra buffers 的总大小；
- oneway 事务剩余预算；
- 页面分配、目标冻结和进程存活状态。

因此，400 KiB、512 KiB 或其他固定值都不能保证成功。大图、文件、长列表和媒体数据应优先留在文件、共享内存或专用数据通道中，Binder 只传递有界的控制信息与描述符。拆分事务时还要设计序列号、部分失败处理和版本一致性，不能只把一个大 Parcel 切成若干小 Parcel。

## 四、oneway spam 检测的准确门槛

### 1. 检测在 async 预算接近耗尽后启动

`debug_low_async_space_locked()` 仅在以下条件成立时扫描已分配的异步 buffer：

`free_async_space < buffer_size / 10`

初始 async 预算是 `buffer_size / 2`。因此，这个门槛表示：

- 剩余 async 预算小于总窗口的 10%；
- 等价于剩余量小于初始 async 预算的 20%；
- 已消耗 async 预算大于总窗口的 40%。

把这个门槛换算成“总 buffer 的 5%”会少算一倍。

### 2. 统计对象是当前发送进程

进入低空间区间后，驱动扫描目标 `binder_alloc` 中仍未释放的 async buffer，只累计 `buffer->pid == current->tgid` 的项目。这里的 PID 属于当前发送进程，buffer 则占在目标进程的地址窗口里。

满足任一严格大于条件时，当前 buffer 可被标为 suspect：

- 该发送进程占用的 async buffer 数量 `> 50`；
- 这些 buffer 的总大小 `> buffer_size / 4`。

它统计的是尚未释放的 buffer 数量和容量，没有时间窗口，也不计算每秒调用次数。“高频滥用”只能作为现象描述，不能从这段代码得出固定 QPS。

### 3. suspect 是诊断信号，不会拒绝当前事务

检测发生在地址分配成功并扣除 async 预算之后。达到门槛的当前事务已经取得 buffer；驱动用 `oneway_spam_suspect` 标记它，并在调用进程启用检测时返回 `BR_ONEWAY_SPAM_SUSPECT`。

`alloc->oneway_spam_detected` 会抑制同一低空间阶段的重复报告。只有 `free_async_space` 恢复到 `buffer_size / 10` 或更高时，这个标志才清零。一轮持续压力通常只报告从未触发到已触发的那次转换，不能拿警告条数估算事务总数。

libbinder 把这个返回码当作带诊断信息的 transaction completion 处理。它不会自动限速、丢弃后续业务事件或扩大缓冲区；合并可覆盖状态、限制队列长度、采样和背压仍由接口设计负责。

## 五、优先级继承按事务处理

### 1. 同步与 oneway 的输入不同

创建事务时，驱动只让采用受支持策略的同步调用继承发送线程优先级。对应判断可以概括为：

```c
if (!oneway && binder_supported_policy(current->policy))
    t->priority = current_priority;
else
    t->priority = target_proc->default_priority;
```

`binder_supported_policy()` 接受 `SCHED_NORMAL`、`SCHED_BATCH`、`SCHED_FIFO` 与 `SCHED_RR`。oneway 和使用 `SCHED_IDLE`、`SCHED_DEADLINE` 等不受支持策略的同步调用都会从目标进程默认优先级起步；目标 node 的最低优先级配置仍可继续影响结果。

### 2. RT 继承需要 node 明确允许

`binder_transaction_priority()` 先读取事务优先级。若它是 `SCHED_FIFO` 或 `SCHED_RR`，而目标 node 没有 `FLAT_BINDER_FLAG_INHERIT_RT`，驱动把候选值降为 `SCHED_NORMAL`、nice 0。

随后，驱动比较候选值与 node 的 `min_priority`，选择数值更小、调度优先级更高的一方；数值相同且 node 使用 `SCHED_FIFO` 时选择 node 配置。普通 Binder node 因而不会被调用方的 RT 策略自动提升为实时线程。

能力与资源限制仍会生效。设置路径以 `verify=true` 调用 `binder_do_set_priority()`；缺少 `CAP_SYS_NICE` 时，实时优先级受 `RLIMIT_RTPRIO` 限制，fair policy 的 nice 值受 `RLIMIT_NICE` 限制。

### 3. `set_priority_called` 只约束同一事务

`set_priority_called` 是 `struct binder_transaction` 上的字段。入口守卫如下：

```c
if (t->set_priority_called)
    return;
t->set_priority_called = true;
```

它保证同一个 transaction 对象最多执行一次 `binder_transaction_priority()`。嵌套 Binder 调用会创建新的 transaction，每笔都有自己的标志、目标 node、期望优先级和 `saved_priority`。因此，它不会把四层嵌套调用压缩成一次优先级设置，也不能据此推算 `sched_setscheduler_nocheck()` 次数下降 50%。

`binder_do_set_priority()` 还会先比较线程当前 policy/prio 与期望值；数值相同时直接更新状态并返回。一次优先级处理也不等于必然执行一次 scheduler 设置。

## 六、`PENDING` 与 `ABORT` 解决恢复竞态

`BINDER_PRIO_PENDING`、`BINDER_PRIO_ABORT` 和 `BINDER_PRIO_SET` 描述的是目标 Binder 线程上的优先级状态。它们处理“旧事务正在恢复优先级时，新嵌套事务又到达同一线程”的竞态。

时序可以分成四步：

1. 线程准备回复一个嵌套同步事务时，把 `prio_state` 设为 `PENDING`，并把待恢复值写入 `prio_next`；
2. 回复路径调用 `binder_restore_priority()`，它以 `verify=false` 进入统一设置函数；
3. 若新事务在恢复完成前进入，`binder_transaction_priority()` 发现 `PENDING`，把新事务的 `saved_priority` 设为 `prio_next`，再把线程状态改为 `ABORT`；
4. 旧恢复路径看到 `!verify && prio_state == BINDER_PRIO_ABORT` 后退出，避免旧值覆盖新事务即将设置的优先级。

`verify=true` 属于设置继承优先级的路径，并负责权限与 rlimit 校验；`verify=false` 属于恢复路径，并负责识别 `ABORT`。两者的方向不能互换。

恢复竞态与 `set_priority_called` 处于不同层次：前者保护线程状态，后者限制单个 transaction 重复应用优先级。把两者合成“N 层调用只设置一次”，会误判嵌套事务的保存与恢复次数。

## 七、调试时怎样收集证据

下面的命令用于检查驱动统计、事务日志和进程线程调度状态：

```bash
adb shell cat /dev/binderfs/binder_logs/stats
adb shell cat /dev/binderfs/binder_logs/transactions
adb shell ps -AT -o PID,TID,CLS,PRI,NI,NAME
```

具体节点取决于设备是否挂载 binderfs、内核调试配置和 SELinux 权限。量产 user build 可能无法读取全部日志，因此命令失败不能反推出 Binder 没有压力。

分析缓冲问题时，应同时记录目标进程、发送 PID、事务方向、data/offsets/extra 大小、async 剩余量和 buffer 生命周期。只看到 `FAILED_TRANSACTION`，无法区分连续地址不足、async 预算耗尽、页面分配失败、目标死亡或其他事务错误。

分析优先级时，应把 Binder transaction trace 与 `sched_switch`、线程 policy/nice、目标 node 配置放在同一时间轴。优先级变化可能影响运行资格，但 `schedutil` 依据利用率等信号调频；源码没有“Binder 继承发生后 CPU 必然升频”的契约。

## 八、结论

Android 17 标准 libbinder 进程仍使用约 1 MiB 的接收地址窗口，kernel r6 的 4 MiB 只是 mmap 接受上限。同步与 oneway 共享这段地址空间，oneway 事务另受初始为一半容量的 async 预算限制。

oneway spam 检测在 async 剩余量低于总窗口 10% 后启动，并按当前发送进程统计未释放 buffer。它发出诊断信号，不负责拒绝、限速或业务背压。

Binder 优先级继承以 transaction 为单位。`set_priority_called` 不跨嵌套事务去重；`PENDING`/`ABORT` 防止旧恢复覆盖新事务优先级。性能分析应从目标 buffer 生命周期和线程调度 trace 取证，不能从 4 MiB 常量或一个布尔标志推导容量与调用次数收益。
