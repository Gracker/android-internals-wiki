# 1.44 Android 17 Binder 4M 内核缓冲池与优先级去重

> **版本边界**：本节基于 Android 17 (API 37) 源码验证，内核锚定 `android17-6.18-2026-06_r1` [已验证: AOSP android-17.0.0_r1]

## 要点

### 🔹 Binder IPC 缓冲架构演进

#### 内核侧 mmap 上限：从 1MB 封顶到 4MB 扩展

Android 17 内核 `binder_alloc.c` 的 `binder_alloc_mmap_handler()` 引入了 `SZ_4M` 上限收敛，这是一个重要的架构演化节点：

```c
// drivers/android/binder_alloc.c:894-915 简化
int binder_alloc_mmap_handler(struct binder_alloc *alloc,
                              struct vm_area_struct *vma)
{
    ...
    alloc->buffer_size = min_t(unsigned long, vma->vm_end - vma->vm_start,
                               SZ_4M);   // ←── 内核侧 4MB 封顶
    ...
}
```

[已验证: AOSP android17-6.18-2026-06_r1, drivers/android/binder_alloc.c:894-915]

**收敛逻辑的三层含义**：

| 层级 | 代码位置 | 大小 | 说明 |
|------|----------|------|------|
| 用户态请求 | `ProcessState.cpp:48` `BINDER_VM_SIZE = (1*1024*1024) - sysconf(_SC_PAGE_SIZE)*2` | ≈ 0.99 MB (4KB page) / ≈ 0.95 MB (16KB page) | 编译期常量，当前版本未上调 |
| 内核态封顶 | `binder_alloc.c:908` `min_t(unsigned long, vma_size, SZ_4M)` | 4 MB | 从 Android 14 的 `SZ_1M` 扩展到 `SZ_4M` |
| 实际生效值 | `min(用户态请求, 内核态封顶)` | ≈ 0.99 MB | 当前等于用户态请求值 |

[已验证: AOSP android-17.0.0_r1, frameworks/native/libs/binder/ProcessState.cpp:48]

**演化的工程意义**：

1. **内核侧已为未来扩容铺路**：用户态 `BINDER_VM_SIZE` 一旦从 1MB 上调到 2-3MB，无需修改内核驱动代码
2. **当前用户态仍保守**：`BINDER_VM_SIZE` 在 Android 14-17 期间保持不变，说明 Google 对"每进程 Binder 缓冲占用"仍采取谨慎策略
3. **大事务判定边界未变**：虽然内核允许 4MB，但用户态仍按 ~1MB 请求，超过 ~0.5MB 的 async 配额即触发 oneway 限制

> ⚠️ **注意**：§1.25、§1.30、§1.44(existing) 中"Binder mmap 为 1MB"的表述是**用户态请求值**，非内核上限。本节补充这一精度差异。

#### 50% Async 配额初始化

缓冲池初始化时，内核将 50% 容量预留给 oneway/async 事务：

```c
// drivers/android/binder_alloc.c:939
alloc->free_async_space = alloc->buffer_size / 2;
```

[已验证: AOSP android17-6.18, drivers/android/binder_alloc.c:939]

这意味着：
- **同步事务**理论可用全部 `buffer_size`（~1MB），不受 async 配额限制
- **异步事务**最多使用 `buffer_size / 2`（~0.5MB），通过 `free_async_space` 追踪剩余配额
- 每次 async buffer 分配时 `free_async_space -= size`，释放时 `free_async_space += buffer_size`

#### 缓冲池碎片管理：best-fit 分配器

`binder_alloc_new_buf_locked()` 采用 best-fit 策略管理缓冲池空闲空间：

```c
// drivers/android/binder_alloc.c:515-616 简化
static struct binder_buffer *binder_alloc_new_buf_locked(
        struct binder_alloc *alloc, size_t size, int is_async)
{
    // 1. async 配额检查
    if (is_async && alloc->free_async_space < size) {
        return ERR_PTR(-ENOSPC);   // async 配额不足
    }

    // 2. best-fit 搜索空闲 buffer 链表
    best_fit = list_first_entry_or_null(&alloc->free_buffers,
                                        struct binder_buffer, entry);
    // ... 遍历找最合适的空闲块 ...

    // 3. 如果找到的块比请求大很多，执行拆分
    if (buffer_size > size + sizeof(struct binder_buffer)) {
        // 拆分出新的空闲 buffer
    }

    return best_fit;
}
```

[已验证: AOSP android17-6.18, drivers/android/binder_alloc.c:515-616]

碎片化场景下，即使 `free_async_space` 足够，连续空间不足也会导致 `-ENOSPC`。这是 §1.44(existing) "同步事务溢出：致命失败" 中 `BR_FAILED_REPLY` 的底层根因之一。

### 🔹 优先级设置与调用去重

#### `set_priority_called` 单飞标志

`binder_transaction_priority()` 入口的单飞去重机制是 Android 17 Binder 优先级系统的关键优化：

```c
// drivers/android/binder.c:821-824
if (t->set_priority_called)
    return;
t->set_priority_called = true;
```

[已验证: AOSP android17-6.18, drivers/android/binder.c:821-824]

**设计意图**：同一个 `binder_transaction` 在嵌套调用链上最多被升级一次线程优先级。考虑以下场景：

```
Process A (SCHED_FIFO prio=10)
  └→ sync transaction → Process B (SCHED_NORMAL nice=0)
       └→ sync transaction → Process C (SCHED_NORMAL nice=5)
            └→ binder_transaction_priority() 被调用
```

如果没有单飞标志，`binder_transaction_priority()` 可能被多次调用（每次嵌套进入），导致冗余的 `sched_setscheduler_nocheck()` 系统调用。`set_priority_called` 确保：

1. **第一次调用执行优先级升级**：设置线程优先级 + 保存 `saved_priority`
2. **后续嵌套调用直接 return**：跳过冗余的 `sched_setscheduler` 调用

#### 与 `BINDER_PRIO_ABORT` 状态机的协同

单飞标志与 §1.44(existing) 详述的 `prio_state` 三态机协同工作：

```
外层事务进入 → set_priority_called=true, prio_state=SET
  └→ 嵌套事务进入 → set_priority_called 已 true → return（跳过升级）
      └→ 嵌套事务结束 → restore_priority(verify=true)
  └→ 外层事务结束 → restore_priority(verify=false)
```

**精度补强**（§1.44 existing 已覆盖 ABORT 状态，此处补充与单飞标志的协同）：

当 `set_priority_called` 阻止了嵌套事务的优先级升级后，`binder_restore_priority()` 的 `verify` 参数行为如下：

- `verify=true`（嵌套事务结束）：检查 `prio_state`，如果为 ABORT 则不还原
- `verify=false`（外层事务结束）：无条件还原到 `saved_priority`

这种设计使得单飞 + ABORT 共同把嵌套事务的 `sched_setscheduler` 调用次数从理论 2N 次降为 N+1 次。

[已验证: AOSP android17-6.18, binder.c:810-872, 与 §1.44(existing) prio_state 分析交叉验证]

#### DoS 防护：RT 客户端 → 非 RT 服务降级

`binder_transaction_priority()` 的 DoS 防护层（line 826-830）：

```c
if (!node->inherit_rt && is_rt_policy(desired.sched_policy)) {
    desired.prio = NICE_TO_PRIO(0);       // 强制降级到 NICE 0
    desired.sched_policy = SCHED_NORMAL;  // 强制使用 CFS
}
```

**触发条件**（两者同时满足）：
1. 目标 Binder 节点未设置 `FLAT_BINDER_FLAG_INHERIT_RT`
2. 客户端 caller 持有 SCHED_FIFO/SCHED_RR 策略

**效果**：RT 客户端无法强制把普通应用 Binder 服务拉成 RT，防止恶意应用通过 RT 策略抢占系统资源。

[已验证: AOSP android17-6.18, binder.c:826-830]

### 🔹 内核级实现细节

#### Oneway Spam 检测：精确阈值

`debug_low_async_space_locked()` 实现了三级阈值检测：

```c
// drivers/android/binder_alloc.c:462-513 简化
static bool debug_low_async_space_locked(struct binder_alloc *alloc, int pid)
{
    // 第一级：系统级 async 紧张度检查
    if (alloc->free_async_space >= alloc->buffer_size / 10) {
        alloc->oneway_spam_detected = false;
        return false;   // 剩余 > 10%（总 buffer 的 5%）→ 不检测
    }

    // 第二级：逐 pid 统计
    size_t total_alloc_size = 0;
    size_t num_buffers = 0;
    for_each_allocated_buffer(buffer) {
        if (buffer->pid != pid || !buffer->async_transaction)
            continue;
        total_alloc_size += buffer_size(buffer);
        num_buffers++;
    }

    // 第三级：spam 判定
    if (num_buffers > 50 || total_alloc_size > alloc->buffer_size / 4) {
        // 频率型 spam（>50 个 oneway）或容量型 spam（> 总 buffer 25%）
        alloc->oneway_spam_detected = true;
        return true;
    }
    return false;
}
```

[已验证: AOSP android17-6.18, drivers/android/binder_alloc.c:462-513]

**精确阈值含义**（基于 `free_async_space = buffer_size / 2`）：

| 检测条件 | 阈值 | 物理含义 |
|----------|------|----------|
| 触发检测门槛 | `free_async_space < buffer_size / 10` | async 配额剩余 < 10%（**总 buffer 的 5%**） |
| 频率型 spam | 单 pid oneway buffer 数 > 50 | 大量小 oneway 频繁发送 |
| 容量型 spam | 单 pid oneway 占用 > `buffer_size / 4` | 单一 pid 占总 buffer 25%（async 配额的 50%）|

**关键特性**：
1. **滞后诊断**：检测在 async 配额接近耗尽时才触发，不预防
2. **粘性标志**：`oneway_spam_detected` 触发后保持 true，直到 `free_async_space` 回到 10% 以上才清零
3. **逐 pid 隔离**：统计限定到具体 pid，避免误报

用户态响应路径（§1.25 已详述）：`BR_ONEWAY_SPAM_SUSPECT` → `IPCThreadState` 执行 `oneway_spam_suspect = true` → 上报到 `BpBinder::logIfNotInRuntime()` → 最终打印 warning 日志。

#### `min(client, node)` 优先级收敛算法

```c
// drivers/android/binder.c:832-843
if (node_prio.prio < desired.prio ||
    (node_prio.prio == desired.prio &&
     node_prio.sched_policy == SCHED_FIFO)) {
    desired = node_prio;
}
```

**收敛规则**：
1. 取 `min(client_priority, node_min_priority)`（数值小 = 优先级高）
2. 同优先级时优先 `SCHED_FIFO`（可无界运行），因为 `SCHED_RR` 有时间片限制
3. 仅支持四种调度策略：`SCHED_NORMAL`、`SCHED_BATCH`、`SCHED_FIFO`、`SCHED_RR`

[已验证: AOSP android17-6.18, binder.c:832-843]

#### `binder_supported_policy()` 策略过滤

```c
// drivers/android/binder.c:3612-3620
static bool binder_supported_policy(int policy)
{
    if (policy == SCHED_NORMAL || policy == SCHED_BATCH ||
        policy == SCHED_FIFO  || policy == SCHED_RR)
        return true;
    return false;   // SCHED_IDLE / SCHED_DEADLINE 不被 Binder 支持
}
```

`binder_open()` 的 `default_priority` 在遇到不支持的策略时强制降级到 `SCHED_NORMAL NICE 0`，确保内核调度器永远不会收到 Binder 传递的 DEADLINE 策略请求。

[已验证: AOSP android17-6.18, binder.c:3612-3620]

### 🔹 性能提升效果

#### SZ_4M 封顶的实际影响

虽然当前用户态仍请求 ~1MB，但内核侧 SZ_4M 封顶在以下场景产生实际影响：

1. **自定义 Binder 服务**：OEM 或系统服务可通过修改 `BINDER_VM_SIZE` 单独请求更大缓冲区（如 SurfaceFlinger 的大事务），内核侧已无需额外适配
2. **16KB page size 兼容**：Android 15+ 支持 16KB page，`BINDER_VM_SIZE = 1MB - 2*16KB = 0.97MB`，与 4KB page 的 0.99MB 差异微小但内核侧已预留余量
3. **大 payload Parcel 传输**：接近 1MB 的同步事务（如 `Bitmap` 传递）在 SZ_4M 时代可以安全扩容

#### `set_priority_called` 的量化收益

以典型的 4 层 Binder 调用链为例（UI → SystemServer → ServiceA → ServiceB）：

| 场景 | 无单飞标志 | 有单飞标志 |
|------|-----------|-----------|
| `sched_setscheduler` 调用次数 | 4 次（每层 1 次） | 2 次（首层 1 次 + 外层 restore 1 次） |
| `prio_lock` 获取次数 | 4 次 | 2 次 |
| 嵌套抢占风险 | 中（可能 ABORT 多次） | 低（ABORT 最多 1 次） |

[来源: DeepResearch/2026-07-05 分析推算，非实测数据，仅供参考]

#### Oneway Spam 检测的实际触发频率

基于 `buffer_size ≈ 1MB` 和 `free_async_space ≈ 0.5MB` 的前提：

- **频率型 spam**（>50 buffers）：平均每个 oneway buffer ≤ 10KB，属于高频小消息场景（如日志埋点上报）
- **容量型 spam**（>256KB 总占用）：平均每个 oneway buffer > 5KB，属于大 payload 异步传输场景（如 `Bitmap` oneway 传递）

两种阈值覆盖了不同 spam 模式，实际系统中以频率型更为常见。

## 扩展

### 🔸 缓冲池调优策略

#### 用户态 BINDER_VM_SIZE 上调路径

当前 `ProcessState.cpp:48` 的 `BINDER_VM_SIZE` 是编译期常量：

```cpp
// frameworks/native/libs/binder/ProcessState.cpp:48
#define BINDER_VM_SIZE ((1 * 1024 * 1024) - sysconf(_SC_PAGE_SIZE) * 2)
```

如果未来 Google 将此值上调到 2MB 或 3MB，内核侧 `SZ_4M` 封顶已就绪。但需要注意：

1. **每进程内存开销增加**：Binder mmap 是 per-process 的，1MB → 4MB 意味着系统级内存开销线性增长
2. **async 配额翻倍**：`free_async_space = buffer_size / 2` 会自动跟进，oneway 配额从 0.5MB → 1.5MB
3. **spam 阈值联动**：`buffer_size / 4` 和 `buffer_size / 10` 阈值同步放大，spam 检测敏感度降低

[待验证: 目前无迹象表明 Google 在 Android 17 时间 frame 内会上调 BINDER_VM_SIZE]

#### Parcel 大小监控与防御性设计

应用层应监控 outgoing Parcel 大小，避免触发 `-ENOSPC`：

### 🔸 多级优化协同

#### 与 schedutil 调频协同

Binder 优先级继承 → 线程获得更高 CFS/RT 优先级 → 触发 `schedutil` CPU 调频更快响应。这种"IPC 优先级 → 调度器优先级 → CPU 频率"的三级联动是 Android 系统性能的关键保障。

详见 §5.x（CPU 调频子系统）和 §15.1（PowerManagerService × cpuidle × schedutil）的交叉分析。

#### 与 lmkd 内存压力协同

当系统内存紧张时，lmkd 会杀进程释放内存。Binder 缓冲池中的待处理事务会被丢弃（`binder_proc` 的 `binder_thread` 全部清理），客户端收到 `DEAD_REPLY`。`free_async_space` 配额在进程死亡后自然回收。

这种"lmkd 杀进程 → Binder 事务失败 → 客户端 error handling"的链路是系统级内存治理的一部分，详见 §4.x（lmkd 内存管理）。
