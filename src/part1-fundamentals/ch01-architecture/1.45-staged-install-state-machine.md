## 要点

### 🔹 状态机机制

Android 17 Staged Install 采用三态状态机模型，由 `PackageInstallerSession` 中的三个独立布尔字段控制：

```java
private boolean mSessionReady;
private boolean mSessionApplied;
private boolean mSessionFailed;
```

每个状态都有明确的状态转换规则和语义：

**状态定义与转换**：
- **Ready 状态**：表示通过 pre-reboot verification，可以安全执行安装的预备状态
- **Applied 状态**：表示安装成功完成的终态
- **Failed 状态**：表示安装失败或验证失败的终态

**状态转换函数**：
- `setSessionReady()`：将状态置为 ready，同时清除 applied 和 failed 标记
- `setSessionApplied()`：将状态置为 applied，终态，会触发 `destroy()` 并写入成功记录
- `setSessionFailed()`：将状态置为 failed，终态，会触发 `destroy()` 并记录错误信息

**状态持久化**：状态变更通过 `dispatchSessionFinished()` 写入 `mSessionsFile`（`AtomicFile` 实现），重启后通过 `readSessionSettingsLocked()` 恢复状态。

**守卫机制**：所有状态转换都有共同的守卫逻辑，确保 destroyed 和 failed 状态不可逆：
```java
if (mDestroyed || mSessionFailed) return;
```

[已验证: AOSP android-17.0.0_r1, frameworks/base/services/core/java/com/android/server/pm/PackageInstallerSession.java:676-678]

### 🔹 原子性保证

Android 17 Staged Install 通过严格的五阶段 pre-reboot verification 流水线确保安装的原子性和一致性：

**五阶段 verification 流程**：
1. **checkActiveSessions**：验证多 session 场景下是否支持 checkpoint，防止冲突
2. **checkRollbacks**：处理 rollback session 抢占逻辑，确保回滚操作的互斥性
3. **checkOverlaps**：按 `getCommittedMillis()` 比较时间戳，防止重叠安装
4. **verifyApex**：向 apexd 提交 APEX session，执行签名验证和完整性检查
5. **endVerification**：启动 checkpoint 服务并标记 session 为 ready

**原子性保证机制**：
- **时序控制**：`endVerification()` 中先 `setSessionReady()` 再 `markStagedSessionReady()`，防止 "APEX 已激活但 session 未标记" 的不一致状态
- **失败传播**：任一阶段失败都会立即终止后续流程，并设置相应错误状态
- **幂等性**：verification 过程支持幂重试，`mBootCompleted.thenRun(() -> session.verifySession())` 处理重启后的重验证

**Checkpoint 协议**：通过 `InstallLocationUtils.getStorageManager().startCheckpoint(2)` 建立事务性检查点，确保要么全部成功，要么全部回滚。

[已验证: AOSP android-17.0.0_r1, frameworks/base/services/core/java/com/android/server/pm/PackageSessionVerifier.java:547-397]

### 🔹 恢复机制

Android 17 实现了完整的 boot-time restore 链路，确保系统重启后能正确恢复 staged session：

**恢复触发条件**：
- 无 parent 且 committed 且未终态的 session
- 非 device upgrading 场景（build fingerprint 未变化）
- 非 boot completed 后触发

**恢复流程**：
1. **孤儿 session 处理**：parent 缺失的 session 立即标记为 failed
2. **APEX 一致性检查**：对比 apexd 和 PMS 的 session 状态，处理不一致
3. **状态校验**：检查 applied + failed 共存的冲突情况
4. **逐 session 恢复**：通过 `resumeSession()` 执行实际安装

**失败恢复策略**：
- **单个失败**：将所有其他 session 标记为 failed，保持一致性
- **APEX 失败**：调用 `abortCheckpoint()` 触发文件系统回滚
- **系统级失败**：通过 `mPowerManager.reboot(null)` 重启使 apexd revert 生效

**状态持久化恢复**：重启后 `readSessionSettingsLocked()` 从 `mSessionsFile` 读取状态，重建 session 对象。

### 🔹 性能优化

Android 17 在 Staged Install 中引入多项性能优化：

**批处理优化**：
- **内核批处理**：Binder IPC 支持单次 ioctl 返回 ~128 条 BR_* 命令，减少系统调用次数
- **用户态批处理**：`flushCommands()` 实现双收敛模式，合并多次提交

**异步执行优化**：
- **Boot 完成异步重试**：中断的 verification 在 boot 完成后异步执行，不阻塞启动流程
- **APEX 延迟标记**：APEX session 的成功标记延迟到 boot completed，减少启动时的同步等待

**检查点优化**：
- **条件检查点**：`supportsCheckpoint()` 和 `needsCheckpoint()` 根据存储条件动态启用/禁用
- **失败快速回退**：`abortCheckpoint()` 写入失败原因文件，避免重复失败时的冗长检查

**内存管理优化**：
- **Session 对象复用**：通过状态持久化和重建减少重复创建对象
- **错误信息缓存**：失败原因写入文件系统，避免内存中保存大量错误信息

## 一、staged install 解决什么问题

普通 APK session 通常在当前启动周期完成安装。`isStaged=true` 的 session 会在当前周期完成校验并进入 ready，待重启后再应用，适合需要跨重启协调的 APK、APEX 或多包更新。

staged install 与整机 A/B OTA 是两套流程。纯 APK 也可以使用 staged session；包含 APEX 时由 apexd 负责早期启动阶段的激活。这里没有 `update_engine` slot 切换，也没有 kernel 6.18 专属状态机。

“原子性”要按范围解释：

- multi-package session 用父子关系表达一组包的提交边界；
- pre-reboot verification 尽量在重启前排除签名、包重叠、rollback 冲突和 APEX 提交错误；
- filesystem checkpoint 可在受支持设备上恢复用户数据变化；
- apexd 管 APEX session 的 staged、activated、success、revert 等状态；
- PackageInstaller 保存 framework session 状态，并在重启后继续安装 APK。

这些机制共同减少 APK/APEX 混合更新的部分成功窗口，但不能概括成“任何失败都会自动恢复全部系统状态”。设备是否支持 checkpoint、session 是否含 APEX、失败发生在何时，都会改变处理路径。

## 二、三个布尔字段不是完整状态机

`PackageInstallerSession` 保存 staged session 的三个专用字段：

```java
private boolean mSessionApplied;
private boolean mSessionReady;
private boolean mSessionFailed;
```

这段代码只表示 staged 结果维度。一个 session 还同时拥有 sealed、committed、destroyed、active、parent/child、错误码和更新时间等状态，因此不能只用 Ready、Applied、Failed 三个节点描述完整生命周期。

### 1. 可观察组合

| 组合 | 含义 |
|---|---|
| ready=false, applied=false, failed=false | 尚未完成 pre-reboot verification，或刚从 XML 恢复等待处理 |
| ready=true | 重启前校验完成；含 APEX 时 apexd 也应已接收 ready 标记 |
| applied=true | 重启后 APK 阶段完成，session 进入成功终态 |
| failed=true | 校验、激活或恢复失败，session 进入失败终态 |

`isInTerminalState()` 只检查 `mSessionApplied || mSessionFailed`。ready 不是终态，设备仍需重启并完成恢复流程。

### 2. 三个写方法的守卫

`setSessionReady()`、`setSessionFailed()` 和 `setSessionApplied()` 都在 `mLock` 下检查 `mDestroyed || mSessionFailed`。ready 会清除 applied/failed 和错误；failed/applied 会清除 ready，并在更新字段后调用 `destroy()`。

applied 之后 `mDestroyed=true`，后续写状态会被守卫拦截；failed 自身也被守卫直接拦截。方法级不变量保证三个位由正常写路径保持互斥。

这里的 `destroy()` 负责关闭 session、清理 staging 内容和阻止继续操作，不等于立刻从 `PackageInstallerService.mSessions` 删除记录。staged terminal session 可以按保留策略继续出现在历史或持久化信息中。

## 三、状态怎样写入磁盘

旧提纲把状态写入归给 `dispatchSessionFinished()`，调用链不对。三个 `setSession*()` 方法在字段更新后调用 `mCallback.onSessionChanged(this)`；`PackageInstallerService.InternalCallback` 再执行：

1. 更新 session 的修改时间；
2. 通过 `RequestThrottle` 调度 settings 写入；
3. 条件满足时向安装器发送 staged session 更新广播。

settings 写入会快照当前 `mSessions`，再用 `AtomicFile` 更新：

`/data/system/install_sessions.xml`

`AtomicFile` 用于避免 XML 替换过程中留下半写文件。它不把 framework XML、apexd 状态和 filesystem checkpoint 合成一笔跨服务磁盘事务。

状态变化后的 `schedule()` 也是异步写请求。`PackageSessionVerifier.endVerification()` 调用 `setSessionReady()` 后再调用 apexd 的 `markStagedSessionReady()`；源码明确选择这个调用顺序来降低 APEX 已准备而 framework 仍未 ready 的风险，但 `setSessionReady()` 本身没有同步等待 XML 刷盘完成。

系统启动时，`PackageInstallerService.readSessionsLocked()` 从 `install_sessions.xml` 调用 `PackageInstallerSession.readFromXml()` 重建对象。源码中没有名为 `readSessionSettingsLocked()` 的 staged 恢复入口。

## 四、提交与 pre-reboot verification

### 1. `commit()` 不会直接应用包

installer 提交后，session 先完成 seal、内容校验、用户确认和通用 package verification。Android 17 的 `PackageSessionVerifier.verify()` 会检查 APEX 更新权限、rebootless/staged 组合、APEX 容器签名，再通过 `VerifyingSession` 执行 APK 侧校验。

staged session 在通用校验成功后进入 `verifyStaged()`。成功回调返回 `PackageInstallerSession.onVerificationComplete()`，该方法才调用 `StagingManager.commitSession()`。此时 ready 已由 `endVerification()` 设置，所以 `StagingManager.commitSession()` 的职责主要是登记 session，并在 ready 且含 APEX 时通知 staged APEX observer。

### 2. staged 专用校验顺序

`verifyStaged()` 依次完成：

1. `checkActiveSessions()`：设备不支持 filesystem checkpoint 时，只允许一个非终态 active staged session；
2. `checkRollbacks()`：rollback session 可使现有非 rollback session 失败，现有 rollback 也会阻止新的普通 staged session；
3. `checkOverlaps()`：多个 session 包含同一 package 时，按 `getCommittedMillis()` 保留更早提交者；
4. `verifyApex()`：按需通知 RollbackManager，并把含 APEX 的 session 提交给 apexd，执行相关 APEX 校验；
5. `endVerification()`：支持 checkpoint 时调用 `startCheckpoint(2)`，设置 framework ready，并按需通知 apexd ready。

前两组 APEX 权限与签名检查发生在 `verifyStaged()` 之前，因此“五阶段”只能表示 staged 专用片段，不能覆盖完整提交校验链。

任一步抛出 `PackageManagerException` 时，verifier 会尝试终止 active APEX session，随后把 framework session 标为 failed 并返回失败回调。rollback enable 失败是一个例外：源码记录错误后允许安装继续，不能把它写成所有失败都立即终止。

## 五、为什么 ready 要先于 apexd ready

`endVerification()` 的调用顺序是：

```text
startCheckpoint(2)                 // 仅在设备支持时
session.setSessionReady()          // framework 内存状态，调度 XML 写入
mApexManager.markStagedSessionReady(sessionId)  // 仅含 APEX 时
```

如果设备在 framework ready 后、apexd ready 前重启，apexd 不会激活该 APEX，恢复阶段会把不一致 session 判为失败。反向顺序可能让 apexd 激活 APEX，而 framework 没有对应 ready 状态，混合 APK/APEX 更新的另一部分就无法按预期继续。

这段顺序只处理特定重启窗口。掉电时 XML 是否已经持久化、checkpoint 是否进入所需阶段，仍要由启动恢复逻辑核对，不能从三行调用推导绝对无部分失败。

## 六、重启后怎样恢复

### 1. PackageInstallerService 先筛 session

`restoreAndApplyStagedSessionIfNeeded()` 遍历所有 session：

- 非 staged 直接跳过；
- 非终态 child 找不到 parent 时标记为 orphan failed；
- 只把“无 parent、已 committed、未终态”的顶层 staged session交给 `StagingManager.restoreSessions()`。

调用期间不会持有 `mSessions` 锁，因为后续 APK 原子安装还会查询 session。

### 2. restore 的入口守卫

`restoreSessions()` 要求运行时 `sys.boot_completed=false`。若 build fingerprint 已变化，传入的 `isDeviceUpgrading=true`，所有候选 session 会被标为 `INSTALL_ACTIVATION_FAILED`，本轮不再恢复。

随后读取 StorageManager 的 `supportsCheckpoint()` 与 `needsCheckpoint()`。持久化数据出现多个 staged session、设备却不支持 checkpoint 时，源码抛出 `IllegalStateException`；正常提交阶段本应已阻止这种组合。

### 3. non-ready 与 destroyed 的分流

destroyed session 会执行 abandon 并从本轮候选中移除。尚未 ready 的 session 也会移出立即恢复列表，但不会直接失败；代码通过 `mBootCompleted.thenRun(() -> session.verifySession())` 在 boot completed 信号到达后重启 verification。

所以，ready session 在 boot completed 前继续 apply；中断在 pre-reboot verification 的 session 等系统启动完成后再验证。旧提纲写成统一的 boot-time resume 会漏掉这条分支。

### 4. 对齐 apexd 状态

含 APEX 的 ready session 必须与 apexd 报告一致：

- apexd 不认识 session、报告 activation failed/reverted/revert failed 等状态时，framework 标记失败；
- apexd 仍停在 staged、没有 activated 或 failed 时，framework也主动标记失败；
- apexd 已 activated 或 success 时，session 才能继续 APK 阶段；
- apexd 中没有 framework 对应项的 dangling session 会被收集并终止。

同一轮恢复同时出现已应用和失败的 APEX session 时，`abortCheckpoint()` 处理 checkpoint 回退。出现任一 failed APEX 时，其余候选 session也会被标为 failed，保持这一批 staged 更新的结果一致。

## 七、APK 安装、applied 与 APEX success

`resumeSession()` 对含 APEX 的 session 先检查 APK-in-APEX 安装结果、重复包和 rollback user-data snapshot，再调用 `installApksInSession()`。该方法阻塞等待 `session.installSession().get()`。

`PackageInstallerSession.install()` 的 futures 全部成功后调用 `setSessionApplied()`。所以 applied 由统一 APK/session 安装完成链写入，不是 `StagingManager.resumeSession()` 末尾手工设置。

APEX 的 successful 状态还有单独时机：

- 支持 checkpoint：先把 session id 放入 `mSuccessfulStagedSessionIds`，到 `PHASE_BOOT_COMPLETED` 批量调用 `markStagedSessionSuccessful()`；
- 不支持 checkpoint：APK 阶段成功后立即通知 apexd successful。

framework applied 与 apexd successful 属于两个服务的状态，不能合并成一个布尔位。

## 八、失败与 checkpoint 回退

`abortCheckpoint()` 只有在 `supportsCheckpoint && needsCheckpoint` 时才写：

`/metadata/staged-install/failure_reason.txt`

随后按设备能力请求 apexd revert，并调用 StorageManager：

`abortChanges("abort-staged-install", false)`

若 checkpoint 调用抛异常，catch 路径再次请求 apexd revert，并显式调用 `PowerManager.reboot(null)`。因此，“abortCheckpoint 每次都会显式 reboot”不符合源码。

非 checkpoint 设备发生安装失败时，纯 APK session 标记失败后返回；含 APEX 时还会调用 `revertActiveSessions()`，成功后显式重启以让 apexd revert 生效。失败类型决定回退范围。

## 九、诊断路径

下面的命令由 Android 17 `PackageManagerShellCommand` 提供，可列出 staged session：

```bash
adb shell pm list staged-sessions
adb shell pm list staged-sessions --only-ready --only-parent
adb shell pm get-stagedsessions
```

`get-stagedsessions` 是独立命令入口，`pm list staged-sessions` 还支持只看 ready、session id 或 parent。输出来自 PackageInstaller session 信息，含 APEX 时还要结合 apexd 日志判断激活状态。

排障时按时间顺序收集：

1. commit 返回的 session id、installer 和 parent/child 关系；
2. `PackageSessionVerifier` 的 active/rollback/overlap/APEX 错误；
3. reboot 前 ready/failed 与错误码；
4. reboot 后 apexd session 状态、checkpoint 状态和 `StagingManagerTiming` trace；
5. APK-in-APEX、普通 APK 安装结果与 applied；
6. boot completed 后 apexd successful 或 revert 记录。

`/data/system/install_sessions.xml` 和 `/metadata/staged-install/failure_reason.txt` 通常需要 root/debug 权限。`/data/app-staging/` 只保存 staging 内容，不能替代 session XML、apexd 与 checkpoint 状态。

旧提纲中的 Binder “约 128 条 BR 命令”、session 对象复用、错误信息减少内存等内容与 staged install 状态机没有直接源码关系，也没有基准数据支持，不能列为 Android 17 性能优化。
