# 1.45 Android 17 Staged Install 状态机与原子性安装

<!-- outline-start -->
## 要点

### 🔹 状态机机制

Android 17 Staged Install 采用三态状态机模型，由 `PackageInstallerSession` 中的三个独立布尔字段控制：

```java
private boolean mSessionReady;
private boolean mSessionApplied;
private boolean mSessionFailed;
```

每个状态都有明确的状态转换规则和语义：

**状态定义与转换**：
- **Ready 状态**：表示通过 pre-reboot verification，可以安全执行安装的预备状态
- **Applied 状态**：表示安装成功完成的终态
- **Failed 状态**：表示安装失败或验证失败的终态

**状态转换函数**：
- `setSessionReady()`：将状态置为 ready，同时清除 applied 和 failed 标记
- `setSessionApplied()`：将状态置为 applied，终态，会触发 `destroy()` 并写入成功记录
- `setSessionFailed()`：将状态置为 failed，终态，会触发 `destroy()` 并记录错误信息

**状态持久化**：状态变更通过 `dispatchSessionFinished()` 写入 `mSessionsFile`（`AtomicFile` 实现），重启后通过 `readSessionSettingsLocked()` 恢复状态。

**守卫机制**：所有状态转换都有共同的守卫逻辑，确保 destroyed 和 failed 状态不可逆：
```java
if (mDestroyed || mSessionFailed) return;
```

### 🔹 原子性保证

Android 17 Staged Install 通过严格的五阶段 pre-reboot verification 流水线确保安装的原子性和一致性：

**五阶段 verification 流程**：
1. **checkActiveSessions**：验证多 session 场景下是否支持 checkpoint，防止冲突
2. **checkRollbacks**：处理 rollback session 抢占逻辑，确保回滚操作的互斥性
3. **checkOverlaps**：按 `getCommittedMillis()` 比较时间戳，防止重叠安装
4. **verifyApex**：向 apexd 提交 APEX session，执行签名验证和完整性检查
5. **endVerification**：启动 checkpoint 服务并标记 session 为 ready

**原子性保证机制**：
- **时序控制**：`endVerification()` 中先 `setSessionReady()` 再 `markStagedSessionReady()`，防止 "APEX 已激活但 session 未标记" 的不一致状态
- **失败传播**：任一阶段失败都会立即终止后续流程，并设置相应错误状态
- **幂等性**：verification 过程支持幂重试，`mBootCompleted.thenRun(() -> session.verifySession())` 处理重启后的重验证

**Checkpoint 协议**：通过 `InstallLocationUtils.getStorageManager().startCheckpoint(2)` 建立事务性检查点，确保要么全部成功，要么全部回滚。

### 🔹 恢复机制

Android 17 实现了完整的 boot-time restore 链路，确保系统重启后能正确恢复 staged session：

**恢复触发条件**：
- 无 parent 且 committed 且未终态的 session
- 非 device upgrading 场景（build fingerprint 未变化）
- 非 boot completed 后触发

**恢复流程**：
1. **孤儿 session 处理**：parent 缺失的 session 立即标记为 failed
2. **APEX 一致性检查**：对比 apexd 和 PMS 的 session 状态，处理不一致
3. **状态校验**：检查 applied + failed 共存的冲突情况
4. **逐 session 恢复**：通过 `resumeSession()` 执行实际安装

**失败恢复策略**：
- **单个失败**：将所有其他 session 标记为 failed，保持一致性
- **APEX 失败**：调用 `abortCheckpoint()` 触发文件系统回滚
- **系统级失败**：通过 `mPowerManager.reboot(null)` 重启使 apexd revert 生效

**状态持久化恢复**：重启后 `readSessionSettingsLocked()` 从 `mSessionsFile` 读取状态，重建 session 对象。

### 🔹 性能优化

Android 17 在 Staged Install 中引入多项性能优化：

**批处理优化**：
- **内核批处理**：Binder IPC 支持单次 ioctl 返回 ~128 条 BR_* 命令，减少系统调用次数
- **用户态批处理**：`flushCommands()` 实现双收敛模式，合并多次提交

**异步执行优化**：
- **Boot 完成异步重试**：中断的 verification 在 boot 完成后异步执行，不阻塞启动流程
- **APEX 延迟标记**：APEX session 的成功标记延迟到 boot completed，减少启动时的同步等待

**检查点优化**：
- **条件检查点**：`supportsCheckpoint()` 和 `needsCheckpoint()` 根据存储条件动态启用/禁用
- **失败快速回退**：`abortCheckpoint()` 写入失败原因文件，避免重复失败时的冗长检查

**内存管理优化**：
- **Session 对象复用**：通过状态持久化和重建减少重复创建对象
- **错误信息缓存**：失败原因写入文件系统，避免内存中保存大量错误信息

### 🔹 源码验证

基于 Android 17.0.0_r1 源码，我们验证了以下关键实现细节：

**关键类和方法**：
- `PackageInstallerSession`：状态机核心实现
- `StagingManager`：session 管理和恢复逻辑
- `PackageSessionVerifier`：五阶段 verification 流水线
- `PackageInstallerService`：恢复入口和协调
- `ApexManager`：APEX 特有的激活和回滚逻辑

**核心方法调用链**：
1. **提交链路**：`onVerificationComplete()` → `commitSession()` → `verifyStaged()`
2. **恢复链路**：`restoreAndApplyStagedSessionIfNeeded()` → `restoreSessions()` → `resumeSession()`
3. **安装链路**：`resumeSession()` → `installApksInSession()` → `installSession().get()`

**状态持久化路径**：
- 写入：`setSessionXXX()` → `dispatchSessionFinished()` → `mSessionsFile.writeAtomic()`
- 读取：`readSessionSettingsLocked()` → `mSessionsFile.readAtomic()` → 重建 session 对象

**失败恢复路径**：
- 会话级：`setSessionFailed()` → `destroy()` → 错误记录
- 系统级：`abortCheckpoint()` → `abortChanges()` → `reboot()`

## 扩展

### 🔸 兼容性分析

**与 APEX 的兼容性**：
- APEX session 走专门的 apexd 激活流程，支持 `markStagedSessionReady()` 和 `markStagedSessionSuccessful()`
- APK-in-APEX 需要额外的完整性检查：`checkInstallationOfApkInApexSuccessful()`

**多 package session 支持**：
- 通过 `isMultiPackage()` 判断，需要子 session 循环处理
- 父子 session 依赖关系通过 `getParentSessionId()` 管理

**存储兼容性**：
-checkpoint 依赖 vold 的 StorageManager 接口
- 非 checkpoint 模式下走传统的 fs-rollback 路径

### 🔸 故障排查

**常见失败场景**：
1. **Session 冲突**：多 session 同时存在且不支持 checkpoint
2. **APEX 不一致**：apexd 和 PMS 状态不同步
3. **回滚失败**：checkpoint 回滚过程中断
4. **孤儿 session**：parent session 被意外删除

**诊断工具**：
- `dumpsys package`：查看所有 session 状态
- `logcat | grep PackageInstaller`：跟踪状态转换日志
- `/data/app-staging/`：检查 session 文件持久化
- `/metadata/staged-install/failure_reason.txt`：读取失败原因
