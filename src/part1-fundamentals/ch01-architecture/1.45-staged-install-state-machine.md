# 1.45 Android 17 分阶段安装状态机与原子性

## 一、分阶段安装解决什么问题

普通 APK 会话通常在当前启动周期完成安装。`isStaged=true` 的会话会在当前周期完成校验并进入 `ready`，待重启后再应用，适合需要跨重启协调的 APK、APEX 或多包更新。

staged install 与整机 A/B OTA 是两套流程。纯 APK 也可以使用 staged session；包含 APEX 时由 apexd 负责早期启动阶段的激活。这里没有 `update_engine` slot 切换，也没有内核 6.18 专属状态机。

“原子性”要按范围解释：

- multi-package session 用父子关系表达一组包的提交边界；
- 重启前验证尽量排除签名、包重叠、rollback 冲突和 APEX 提交错误；
- filesystem checkpoint 可在受支持设备上恢复用户数据变化；
- apexd 管理 APEX 会话的 `staged`、`activated`、`success`、`revert` 等状态；
- PackageInstaller 保存 framework session 状态，并在重启后继续安装 APK。

这些机制共同减少 APK/APEX 混合更新的部分成功窗口，但不能概括成“任何失败都会自动恢复全部系统状态”。设备是否支持 checkpoint、session 是否含 APEX、失败发生在何时，都会改变处理路径。

## 二、三个布尔字段只表示结果维度

`PackageInstallerSession` 保存 staged session 的三个专用字段：

```java
private boolean mSessionApplied;
private boolean mSessionReady;
private boolean mSessionFailed;
```

这段代码只表示 staged 结果维度。一个会话还同时拥有 `sealed`、`committed`、`destroyed`、`active`、parent/child、错误码和更新时间等状态，因此不能只用 `ready`、`applied`、`failed` 三个节点描述完整生命周期。

### 1. 可观察组合

| 组合 | 含义 |
|---|---|
| `ready=false, applied=false, failed=false` | 尚未完成 pre-reboot verification，或刚从 XML 恢复等待处理 |
| `ready=true` | 重启前校验完成；含 APEX 时 apexd 也应已接收 `ready` 标记 |
| `applied=true` | 重启后 APK 阶段完成，session 进入成功终态 |
| `failed=true` | 校验、激活或恢复失败，session 进入失败终态 |

`isInTerminalState()` 只检查 `mSessionApplied || mSessionFailed`。`ready` 不是终态，设备仍需重启并完成恢复流程。

### 2. 三个写方法的守卫

`setSessionReady()`、`setSessionFailed()` 和 `setSessionApplied()` 都在 `mLock` 下检查 `mDestroyed || mSessionFailed`。`ready` 会清除 `applied`/`failed` 和错误；`failed`/`applied` 会清除 `ready`，并在更新字段后调用 `destroy()`。

applied `applied` 后 `mDestroyed=true`，后续写状态会被守卫拦截；`failed` 自身也被守卫直接拦截。方法级不变量保证三个位由正常写路径保持互斥。

这里的 `destroy()` 负责关闭会话、清理暂存内容和阻止继续操作，不等于立刻从 `PackageInstallerService.mSessions` 删除记录。staged terminal session 可以按保留策略继续出现在历史或持久化信息中。

## 三、状态怎样写入磁盘

状态写入不经过 `dispatchSessionFinished()`。三个 `setSession*()` 方法在字段更新后调用 `mCallback.onSessionChanged(this)`；`PackageInstallerService.InternalCallback` 再执行：

1. 更新会话的修改时间；
2. 通过 `RequestThrottle` 调度设置写入；
3. 条件满足时向安装器发送 staged session 更新广播。

settings 写入会快照当前 `mSessions`，再用 `AtomicFile` 更新：

`/data/system/install_sessions.xml`

`AtomicFile` 用于避免 XML 替换过程中留下半写文件。它不把框架层 XML、apexd 状态和 filesystem checkpoint 合成一笔跨服务磁盘事务。

状态变化后的 `schedule()` 也是异步写请求。`PackageSessionVerifier.endVerification()` 调用 `setSessionReady()` 后再调用 apexd 的 `markStagedSessionReady()`；源码明确选择这个调用顺序来降低 APEX 已准备而 framework 仍未进入 `ready` 的风险，但 `setSessionReady()` 本身没有同步等待 XML 刷盘完成。

系统启动时，`PackageInstallerService.readSessionsLocked()` 从 `install_sessions.xml` 调用 `PackageInstallerSession.readFromXml()` 重建对象。源码中没有名为 `readSessionSettingsLocked()` 的 staged 恢复入口。

## 四、提交与重启前验证

### 1. `commit()` 不会直接应用包

installer 提交后，session 先完成密封、内容校验、用户确认和通用 package verification。Android 17 的 `PackageSessionVerifier.verify()` 会检查 APEX 更新权限、rebootless/staged 组合、APEX 容器签名，再通过 `VerifyingSession` 执行 APK 侧校验。

staged session 在通用校验成功后进入 `verifyStaged()`。成功回调返回 `PackageInstallerSession.onVerificationComplete()`，该方法才调用 `StagingManager.commitSession()`。此时 `ready` 已由 `endVerification()` 设置，所以 `StagingManager.commitSession()` 的职责主要是登记 session，并在 `ready` 且含 APEX 时通知 staged APEX observer。

### 2. staged 专用校验顺序

`verifyStaged()` 依次完成：

1. `checkActiveSessions()`：设备不支持 filesystem checkpoint 时，只允许一个非终态 active staged session；
2. `checkRollbacks()`：rollback session 可使现有非 rollback session 失败，现有回滚也会阻止新的普通 staged session；
3. `checkOverlaps()`：多个会话包含同一包时，按 `getCommittedMillis()` 保留更早提交者；
4. `verifyApex()`：按需通知 RollbackManager，并把含 APEX 的会话提交给 apexd，执行相关 APEX 校验；
5. `endVerification()`：支持 checkpoint 时调用 `startCheckpoint(2)`，设置框架层的 framework ready，并按需通知 apexd `ready`。

前两组 APEX 权限与签名检查发生在 `verifyStaged()` 之前，因此“五阶段”只能表示 staged 专用片段，不能覆盖完整提交校验链。

任一步抛出 `PackageManagerException` 时，verifier 会尝试终止活动 active APEX session，随后把 framework session 标为 `failed` 并返回失败回调。rollback enable 失败是一个例外：源码记录错误后允许安装继续，不能把它写成所有失败都立即终止。

## 五、为什么框架层的 `ready` 要先于 apexd `ready`

`endVerification()` 的调用顺序是：

```text
startCheckpoint(2)                 // 仅在设备支持时
session.setSessionReady()          // framework 内存状态，调度 XML 写入
mApexManager.markStagedSessionReady(sessionId)  // 仅含 APEX 时
```

如果设备在框架层进入 `ready` 后、apexd ready 前重启，apexd 不会激活该 APEX，恢复阶段会把不一致会话判为失败。反向顺序可能让 apexd 激活 APEX，而 framework 没有对应的 `ready` 状态，混合 APK/APEX 更新的另一部分就无法按预期继续。

这段顺序只处理特定重启窗口。掉电时 XML 是否已经持久化、checkpoint 是否进入所需阶段，仍要由启动恢复逻辑核对，不能从三行调用推导绝对无部分失败。

## 六、重启后怎样恢复

### 1. PackageInstallerService 先筛 session

`restoreAndApplyStagedSessionIfNeeded()` 遍历所有会话：

- 非 staged 直接跳过；
- 非终态子会话找不到父会话时标记为孤儿失败；
- 只把“无 parent、已提交、未终态”的顶层 staged session交给 `StagingManager.restoreSessions()`。

调用期间不会持有 `mSessions` 锁，因为后续 APK 原子安装还会查询会话。

### 2. 恢复入口的守卫

`restoreSessions()` 要求运行时 `sys.boot_completed=false`。若 build fingerprint 已变化，传入的 `isDeviceUpgrading=true`，所有候选会话会被标为 `INSTALL_ACTIVATION_FAILED`，本轮不再恢复。

随后读取 StorageManager 的 `supportsCheckpoint()` 与 `needsCheckpoint()`。持久化数据出现多个 staged session、设备却不支持 checkpoint 时，源码抛出 `IllegalStateException`；正常提交阶段本应已阻止这种组合。

### 3. non-ready 与 destroyed 的分流

destroyed session 会执行 abandon 并从本轮候选中移除。尚未进入 `ready` 的会话也会移出立即恢复列表，但不会直接失败；代码通过 `mBootCompleted.thenRun(() -> session.verifySession())` 在 boot completed 信号到达后重新验证。

`ready` 会话在系统启动完成前继续应用；中断在重启前验证阶段的会话，等系统启动完成后再验证。这两类会话走不同分支。

### 4. 对齐 apexd 状态

含 APEX 的 `ready` 会话必须与 apexd 报告一致：

- apexd 不认识会话、报告 `activation failed`、`reverted`、`revert failed` 等状态时，framework 标记失败；
- apexd 仍停在 `staged`、没有 `activated` 或 `failed` 时，framework也主动标记失败；
- apexd 已进入 `activated` 或 `success` 时，session 才能继续 APK 阶段；
- apexd 中没有 framework 对应项的 dangling session 会被收集并终止。

同一轮恢复同时出现已应用和失败的 APEX 会话时，`abortCheckpoint()` 处理 checkpoint 回退。出现任一 `failed` APEX 时，其余候选会话也会被标为 `failed`，保持这一批 staged 更新的结果一致。

## 七、APK 安装、`applied` 与 APEX `success`

`resumeSession()` 对含 APEX 的会话先检查 APK-in-APEX 安装结果、重复包和 rollback user-data snapshot，再调用 `installApksInSession()`。该方法阻塞等待 `session.installSession().get()`。

`PackageInstallerSession.install()` 的所有异步结果都成功后调用 `setSessionApplied()`。`applied` 由统一的 APK/session 安装完成调用链写入，不是 `StagingManager.resumeSession()` 末尾手工设置。

APEX 的 `success` 状态还有单独时机：

- 支持 checkpoint：先把会话 ID 放入 `mSuccessfulStagedSessionIds`，到 `PHASE_BOOT_COMPLETED` 批量调用 `markStagedSessionSuccessful()`；
- 不支持 checkpoint：APK 阶段成功后立即通知 apexd `success`。

framework applied 与 apexd successful 属于两个服务的状态，不能合并成一个布尔位。

## 八、失败与 checkpoint 回退

`abortCheckpoint()` 只有在 `supportsCheckpoint && needsCheckpoint` 时才写：

`/metadata/staged-install/failure_reason.txt`

随后按设备能力请求 apexd revert，并调用 StorageManager：

`abortChanges("abort-staged-install", false)`

若 checkpoint 调用抛异常，catch 路径再次请求 apexd revert，并显式调用 `PowerManager.reboot(null)`。因此，“abortCheckpoint 每次都会显式重启”不符合源码。

不支持检查点的设备发生安装失败时，纯 APK 会话标记失败后返回；含 APEX 时还会调用 `revertActiveSessions()`，成功后显式重启以让 apexd 回退生效。失败类型决定回退范围。

## 九、诊断路径

下面的命令由 Android 17 `PackageManagerShellCommand` 提供，可列出 staged session：

```bash
adb shell pm list staged-sessions
adb shell pm list staged-sessions --only-ready --only-parent
adb shell pm get-stagedsessions
```

`get-stagedsessions` 是独立命令入口，`pm list staged-sessions` 还支持只看 `ready`、session id 或 parent。输出来自 PackageInstaller 会话信息，含 APEX 时还要结合 apexd 日志判断激活状态。

排障时按时间顺序收集：

1. commit 返回的 session id、installer 和 parent/child 关系；
2. `PackageSessionVerifier` 的 active/rollback/overlap/APEX 错误；
3. reboot `ready`/`failed` 与错误码；
4. reboot apexd apexd session 状态、checkpoint 状态和 `StagingManagerTiming` trace；
5. APK-in-APEX、普通 APK 安装结果与 `applied`；
6. boot completed apexd `success` 或回退记录。

`/data/system/install_sessions.xml` 和 `/metadata/staged-install/failure_reason.txt` 通常需要 root 或调试权限。`/data/app-staging/` 只保存暂存内容，不能替代会话 XML、apexd 与检查点状态。
