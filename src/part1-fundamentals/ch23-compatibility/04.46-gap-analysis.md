## 1. HeapTask 是单线程延时队列

Java `Daemons.HeapTaskDaemon` 调用隐藏的 `VMRuntime.startHeapTaskProcessor()` 和 `runHeapTasks()`，native 层进入 `gc::TaskProcessor::RunAllTasks()`。`TaskProcessor` 用以下容器保存任务：

```cpp
std::multiset<HeapTask*, CompareByTargetRunTime> tasks_;
```

比较器按 `HeapTask::target_run_time_` 排序，`GetTask()` 只取最早到期项。队首尚未到期时，处理线程在条件变量上定时等待；新任务加入后发送信号，让线程重新检查队首。

同一进程通常只有一个 Java `HeapTaskDaemon` 执行这些任务。GC 请求、heap trim、收集器切换和启动清理可以异步提交，但到期任务仍由这条线程依次运行。“HeapTask 并发”描述的是提交方与守护线程、GC 内部阶段之间可能并行，不能解释成 HeapTask 线程池并行执行多个任务。

任务从队列取出后会执行 `Run()`，随后执行 `Finalize()`。`HeapTask` 继承 `SelfDeletingTask`，默认 `Finalize()` 释放任务对象。已经交给处理器的任务不能由提交方再次释放。

## 2. `target_run_time_` 只决定先后时间

目标时间不代表 deadline、优先级或执行时长。两个任务目标时间相同时，比较器还要用对象地址形成稳定的严格弱序；源码没有定义面向业务的重要性等级。

修改已入队任务的目标时间必须经过 `TaskProcessor::UpdateTargetRunTime()`。该方法在锁内找到并移除旧元素，修改时间后重新插入。直接改 `target_run_time_` 会破坏 `multiset` 的排序不变量。

处理器停止时也不会简单丢弃队列。`Stop()` 把运行标记清零并唤醒等待线程，`GetTask()` 随后会忽略未来目标时间，提前取出剩余任务，直到队列为空。这项行为说明“停止 HeapTaskDaemon 以取消 GC”既不成立，也可能让延时任务集中执行。

## 3. GC 请求怎样避免重复

`Heap::RequestConcurrentGC()` 使用 `max_gc_requested_` 与已完成 GC 序号合并请求。只有成功推进最大请求序号的调用方会创建 `ConcurrentGCTask`。任务运行时再次检查目标 GC 是否已经由其他路径完成，已满足的请求成为空操作。

其他任务采用不同的 pending 规则：

| 任务 | 合并方式 |
|---|---|
| `ConcurrentGCTask` | 按 GC 序号合并重复请求 |
| `CollectorTransitionTask` | 只保留一个 pending 对象，新请求可改期 |
| `HeapTrimTask` | 已有 pending 请求时直接返回，不改原目标时间 |
| `TimeBasedGcThresholdCheckTask` | 根据分配进度重新估算检查时间 |
| `TriggerPostForkCCGcTask` | 运行时核对 GC 序号，期间已有 GC 就不再请求 |
| `ReduceTargetFootprintTask` | 运行时核对 GC 序号与 collector 状态，再决定是否收紧目标 |

因此不存在一组通用的“三条护栏”。每个任务按自己的状态与目标处理重复或过期工作。

## 4. 启动期减少 GC 干扰的源码机制

Android 17 的 `Heap::PostForkChildAction()` 会暂时把 `target_footprint_` 提高到 `growth_limit_`，并使过早的 GC 请求序号失效。随后按 heap 配置安排一到两次 `ReduceTargetFootprintTask`，逐步把目标堆大小收紧。

`target_footprint_` 用来决定堆增长和 GC 触发时机，`growth_limit_` 才是 ART heap 的增长边界。提高前者不会扩大应用清单决定的 heap class，也不会修改 lmkd 的 `oom_score_adj`、PSI 或 memcg。

启动后长时间没有 GC 时，`TriggerPostForkCCGcTask` 可以请求一次后台 Concurrent Copying GC。任务运行前仍会比较 GC 序号，启动期间已经发生过收集时不重复执行。

这是一套 ART 自己维护的短期启动策略。普通应用没有受支持的 API 可以设置“抑制时长”、跳过特定 GC 或直接改 HeapTask 队列。

## 5. 为什么不能使用 mSponge 或 vtable Hook

所谓 mSponge 方案修改 `num_bytes_allocated_` 等 ART 私有记账，或通过符号偏移、vtable patch 跳过某个任务的 `Run()`。这些字段、符号、对象布局和虚表都不是 Android 应用 ABI。

这种修改会让分配统计、GC 阈值、OOM 判断和 telemetry 看到互相矛盾的状态。即使跳过 `ConcurrentGCTask`，分配失败路径仍可触发同步 GC；其他 collector、显式 GC、post-fork 任务和 native 内存压力也不会被同一个 Hook 覆盖。

阻断 `HeapTaskDaemon` 的影响还超出 GC：

- heap trim 无法按期执行；
- 收集器切换与 time-based 检查被延后；
- 启动缓存和 startup linear alloc 清理受影响；
- 低开销方法追踪的停止任务可能逾期；
- JIT boot-image method mapping 任务可能延后；
- runtime 停止时可能集中排空任务。

应用侧应从分配速率、对象存活时间、缓存上限和启动工作拆分入手。系统产品若要改变 ART 策略，应在固定 tag 上修改源码，并运行 ART GC、OOM、启动、进程冻结/解冻和 runtime shutdown 测试。

## 6. Perfetto 中怎样核对

`TaskProcessor::RunAllTasks()` 没有为每个 C++ 子类自动创建同名 slice。排查时可以：

1. 在线程列表定位 `HeapTaskDaemon`。
2. 查看相邻 ART GC slice 的 cause、collector、暂停时间和释放字节数。
3. 识别 `TimeBasedGcThresholdCheck`、`PureTimeGcTrigger`、heap trim 与启动清理的源码 trace 名称。
4. 把进程 fork、首帧、进后台、冻结与解冻时间放到同一时间轴。
5. 对照 GC 序号守卫，判断 post-fork 任务到期后是否做了有效工作。

只有 `HeapTaskDaemon` 忙碌这一条信号，无法判断它正在 GC、trim、启动清理、追踪停止还是 JIT 工作。
