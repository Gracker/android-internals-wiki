## 1. “模块”在 Android 中有多种含义

原题把交付单元、进程、系统服务和应用初始化写成了一套架构。这些对象的启动入口、依赖表达和故障范围不同：

| 对象 | Android 17 入口 | 依赖怎样表达 | 故障范围 |
|---|---|---|---|
| native service | init `.rc` 的 `service` 与 action | trigger、属性、action 命令顺序、显式 `start` | 通常是独立进程，由 init 按声明监管 |
| Java system service | `SystemServer`、`SystemServiceManager` | Java 调用顺序、boot phase、显式 Future/等待 | 多数共享 system_server 进程 |
| APEX/Mainline | apexd、模块 manifest、system_server jar 或模块进程 | 解决交付与类加载；运行时入口仍要声明 | 取决于服务运行在哪个进程 |
| Binder service | ServiceManager 注册名与接口 | 客户端按服务名取得 handle，协议自行处理就绪与死亡 | 服务进程或 system_server |
| 应用组件 | manifest、Zygote fork、AMS/ATMS | Activity/Service/Provider 生命周期和 Binder IPC | 每个应用进程独立 |
| AndroidX App Startup | `Initializer` 与依赖列表 | 当前应用进程内的同步依赖遍历 | 当前进程初始化 |

“APEX 可更新”“服务运行在独立进程”“存在 Binder 接口”都不等于网页后端所说的微服务。Android 没有为这些对象统一提供 sidecar、服务网格、透明负载均衡、自动重试或分布式事务。

## 2. init 启动 native service

Android 17 的 [init README](https://android.googlesource.com/platform/system/core/+/refs/tags/android-17.0.0_r1/init/README.md) 定义 rc 语言。`on <trigger>` 选择 action，action 内命令按加入顺序执行；`service` 段声明进程、class、用户、group、capability、重启与失败策略。

init 不扫描所有 rc 服务后生成全局 DAG。几个语义容易混淆：

- `start <service>` 发起进程启动，不等待服务完成业务初始化；
- `disabled` 让服务等待显式启动，不等于按首个 API 调用自动加载；
- `oneshot` 影响进程退出后的重启；
- `class_start` 启动某一 class 中符合条件的服务；
- 属性 trigger 可以把后续 action 接到明确状态变化。

多个 native service 进程可以并行运行，但调用方需要自行处理服务尚未注册、socket 尚未监听或依赖属性尚未就绪。若启动协议需要“等服务可用”，应使用明确的属性、socket、Binder 注册或其他 readiness 信号。

## 3. Zygote 和应用进程不是系统服务调度器

init 启动 Zygote。Zygote 预加载公共类与资源，fork SystemServer，随后接收应用进程创建请求。fork 通过 Copy-on-Write 复用未修改页，应用开始写堆、加载类和初始化 native runtime 后会产生私有页。

Zygote 不解析 SystemService 依赖，也不根据应用模块图排序组件。它提供进程模板和创建通道。应用冷启动的 Provider、`Application.onCreate()`、Activity、首帧等顺序由 framework 生命周期和应用代码共同决定。

一个应用通过 `android:process` 把组件放到其他进程后，每个进程会拥有独立的 ART、`Application`、静态字段、主 Looper、Binder 线程池、heap 和缓存。跨进程边界需要明确 IPC、超时、死亡通知、重连和数据版本。

新增进程有固定成本：fork/绑定应用、类加载、PSS、线程栈和 Binder 调用。只有当故障隔离、权限边界或生命周期收益覆盖这些成本时，多进程才合理；它不会自动让启动更快。

## 4. SystemServer 使用显式顺序和 boot phase

Android 17 的 [`SystemServer.java`](https://android.googlesource.com/platform/frameworks/base/+/refs/tags/android-17.0.0_r1/services/java/com/android/server/SystemServer.java) 在准备 Looper、system context 和 `SystemServiceManager` 后，按源码顺序进入四组服务：

1. `startBootstrapServices()`；
2. `startCoreServices()`；
3. `startOtherServices()`；
4. `startApexServices()`。

[`SystemServiceManager.startService()`](https://android.googlesource.com/platform/frameworks/base/+/refs/tags/android-17.0.0_r1/services/core/java/com/android/server/SystemServiceManager.java) 反射或直接构造服务，把实例加入已启动列表，再调用 `onStart()`。服务可以发布 Binder 接口或 `LocalServices` 接口。

这条主路径没有自动拓扑排序。服务顺序由 `SystemServer.java` 的显式调用、注释、boot phase 与等待点表达。`SystemService` 虽有 dependency 相关接口，Android 17 注释把它用于 Ravenwood 测试环境理解传递依赖，不能把它解释成量产启动 DAG。

### boot phase 的有限并行

`startBootPhase()` 要求 phase 单调递增，并向已经启动的服务分发 `onBootPhase()`。Android 17 还有受 `Flags.parallelizeOnbootphase()` 控制的并行路径：

- 指定为 serial 的服务仍顺序执行；
- 其他服务的同一 phase 回调可以提交给 `SystemServerInitThreadPool`；
- 管理器等待该批任务完成后再结束 phase；
- 回调异常仍会造成启动失败。

它只覆盖 boot-phase 回调，不会自动发现 `onStart()` 依赖，也不证明目标产品打开了 flag。并行化前要核对共享锁、线程安全、隐含初始化顺序和失败传播。

## 5. APEX 解决交付边界

APEX 允许部分系统组件独立更新。`SystemServer.startApexServices()` 可启动由激活 APEX 提供的 system_server service；`startServiceFromJar()` 使用独立 class loader 加载相应 jar。

服务代码来自 APEX，也可能继续运行在 system_server 中，共享同一个 heap、线程资源和进程崩溃范围。另一些 Mainline 模块有自己的进程。应根据模块 manifest、进程和服务注册点判断，不能用“Apex 一个包”推导“一个独立微服务”。

APEX 激活、OTA 与回滚也不等于运行中 Java service 可以任意热替换。版本切换时点、重启要求和回滚条件由 apexd 与模块规则决定。

## 6. Binder 提供 IPC，不提供服务网格

Android 17 的 [`ServiceManager.cpp`](https://android.googlesource.com/platform/frameworks/native/+/refs/tags/android-17.0.0_r1/cmds/servicemanager/ServiceManager.cpp) 保存 Binder 服务名到 handle 的注册关系，并执行访问控制、通知和客户端计数等逻辑。

ServiceManager 解决“按名字找到 Binder 服务”。以下能力仍由服务协议和调用方实现：

- 服务何时完成业务初始化；
- 请求超时和取消；
- Binder death 后是否重连；
- 多实例如何选择；
- 请求是否幂等；
- 数据一致性与版本协商。

`waitForService()` 可以等待注册发生，但注册完成不一定代表所有后端资源就绪。让客户端无限等待会把服务启动慢转化为调用方卡住；启动关键路径应设置清晰的 ready 语义与超时策略。

## 7. AndroidX App Startup 只管理当前应用进程

AndroidX App Startup 允许 `Initializer.dependencies()` 声明进程内依赖，由 `InitializationProvider` 发现并初始化。它是 Jetpack 库，不是 Android 17 新增的 SystemServer 框架。

默认 Provider 通常只在默认进程运行。次进程需要初始化同一库时，要为该进程配置入口或由代码显式触发。各进程拥有各自的初始化图，不存在跨进程自动完成屏障。

把不需要首帧前完成的 initializer 移出自动发现，可以缩短应用关键路径；但它必须在首个消费者之前完成。延迟动作没有消失，只是移动了时间位置，应同时测量首帧、首次功能使用和总资源占用。

## 8. 启动优化必须先选执行层

| 调查目标 | 主要证据 |
|---|---|
| native boot | init action/service 日志、bootchart、内核与 Perfetto trace |
| Zygote | preload timing、fork SystemServer、应用 specialization |
| SystemServer | `SystemServerTiming`、`StartService <class>`、`OnBootPhase_*`、线程和锁 |
| APEX service | 模块激活状态、class loader、服务注册与目标进程 |
| App 冷启动 | `ApplicationStartInfo`、Macrobenchmark、Provider、`Application.onCreate()`、首帧 |
| App 多进程 | 每个 PID 的创建/初始化、Binder 延迟、PSS 与死亡恢复 |

对同一设备和构建重复采样，报告启动类型、起止里程碑和分位值。一次开机总时长无法说明优化属于 bootloader、kernel、init、Zygote、SystemServer 还是 Launcher。

并行化也要看关键路径。把两个任务放进线程池，若它们争用同一锁、存储或 Binder 服务，墙上时间可能没有下降，CPU 峰值和时序风险反而增加。trace 要同时显示任务起止、Runnable 等待、I/O、锁和主线程阻塞。
