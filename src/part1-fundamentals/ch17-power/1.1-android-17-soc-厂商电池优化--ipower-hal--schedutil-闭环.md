## 1. 本文解决什么问题

本文以 Android 平台 `android-17.0.0_r1`、Android Common Kernel
`android17-6.18-2026-06_r6` 为源码锚点，讨论设备厂商怎样把 Android 电源场景
翻译成 SoC 可执行的约束，以及怎样证明这些约束既省电又没有破坏性能。

它和 [15.1 PowerManagerService、cpuidle 与 schedutil 的协作边界](../ch15-power-management/15.1-android17-pms-cpuidle-schedutil.md)
的分工如下：

- 15.1 解释 Framework、Power HAL、`schedutil`、`cpuidle` 各自负责什么；
- 本文站在设备实现者角度，重点解释 AIDL Power HAL 的实现、策略仲裁、内核映射、
  验证和 SoC 差异。

一个需要提前说明的限制是：Qualcomm、MediaTek 等商品平台的 Power HAL 配置、固件
协议和部分内核模块通常不在同一份 Android 公共源码中。没有对应产品、build 和
公开实现时，不能把某个节点名、boost 时长或 DVFS 延迟写成该厂商的通用行为。本文
只给出 AOSP/GKI 能证实的公共接口，以及可在目标设备上验证的工程方法。

## 2. Android 17 的 IPower HAL 契约

### 2.1 服务身份与版本

`hardware/interfaces/power/aidl/Android.bp` 在 `android-17.0.0_r1` 中把
`android.hardware.power` 冻结在 V7。AOSP 示例 manifest 这样声明默认实例：

```xml
<hal format="aidl">
    <name>android.hardware.power</name>
    <version>7</version>
    <fqname>IPower/default</fqname>
</hal>
```

这段声明告诉 VINTF 和客户端：设备提供 AIDL v7 的
`android.hardware.power.IPower/default`。厂商可以替换可执行文件和实现类，但
服务名、接口版本、SELinux 权限、init 启动与 VINTF 声明必须互相匹配。

AOSP 示例 `main.cpp` 通过 `AServiceManager_addService()` 注册
`Power::descriptor + "/default"`，然后进入 Binder 线程池。示例服务用于验证接口
骨架，不能代表商品设备的调频策略。

### 2.2 Mode、Boost 与 Hint Session 的语义不同

下面的接口片段用于确认 `Mode`、`Boost` 的调用形式和能力查询方式：

```aidl
oneway void setMode(in Mode type, in boolean enabled);
boolean isModeSupported(in Mode type);

oneway void setBoost(in Boost type, in int durationMs);
boolean isBoostSupported(in Boost type);
```

`oneway` 表示调用者不等待服务端执行结果。Binder 事务成功，只能说明请求成功排队，
不能说明 sysfs、固件或硬件频点已经变化。

三类输入应采用不同的状态模型：

| 输入 | 生命周期 | 厂商实现应维护的状态 |
| --- | --- | --- |
| `Mode` | `enabled=true` 到对应的 `false` | 持久 vote；重复 enable/disable 应保持幂等 |
| `Boost` | 正时长、默认时长或显式取消 | 带过期时间的临时 vote；新请求需定义覆盖或延长规则 |
| Hint Session | session 创建到 close | 线程集合、目标时长、实际工作时长和 session hint/mode |

`Boost.durationMs` 的 AIDL 语义也不能忽略：

- 正数表示调用方给出的预期持续时间；
- `0` 表示持续时间未知，平台可选择自己的超时；
- 负数表示取消此前的 boost。

把 `Boost` 当成永久 mode 会留下性能约束；把 `Mode` 当成一次脉冲则可能在场景尚未
结束时提前撤销。

### 2.3 能力声明必须与行为一致

Android 17 同时保留 `isModeSupported()`、`isBoostSupported()`，并在 V6 及后续
接口提供聚合的 `SupportInfo`。`SupportInfo` 中的 mode、boost、session hint、
session mode 和 session tag 使用位图表示；headroom 与 composition data 有各自
的支持字段。

厂商实现应遵循两条规则：

1. 声明不支持的能力必须安全地拒绝或忽略，不能造成服务崩溃；
2. 声明支持的能力必须有可观察效果，并在 VTS 和产品测试中覆盖启用、撤销与异常
   恢复。

AOSP `power/aidl/default/Power.cpp` 是一个有意保持简单的反例：它把 mode/boost
位图设为支持，但 `setMode()`、`setBoost()` 只记录日志；CPU/GPU headroom 则返回
`EX_UNSUPPORTED_OPERATION`。这说明 default 目录适合跑通接口，不适合作为产品
实现，也不能据此评估功耗收益。

## 3. 厂商 Power HAL 的内部结构

### 3.1 把接口、策略与执行器分开

一套便于维护的实现通常分为四部分：

| 部分 | 责任 | 不应负责的责任 |
| --- | --- | --- |
| Binder 接口层 | 校验枚举、记录调用、维护死亡通知 | 直接堆叠大量 sysfs 写操作 |
| 状态与仲裁层 | 合并 mode、boost、session、thermal 等 vote | 假定每个请求都能独占硬件 |
| 执行层 | 原子地应用一组节点、ioctl 或固件命令 | 决定业务场景 |
| 观测层 | trace、dump、失败计数、当前 vote | 静默吞掉写入失败 |

这种拆分让同一套场景语义可以适配不同 SoC，也让节点迁移不会改动 Binder 处理逻辑。
若直接在 `setMode()` 的 switch 中写十几个节点，mode 叠加、进程重启和超时取消很
快会产生难以复现的残留状态。

### 3.2 每个资源要有明确的所有者

一个 cpufreq policy 的 min/max 可能同时受这些来源影响：

- Power HAL 的启动或交互 vote；
- 电池节省模式；
- ADPF session；
- thermal cooling 与固件保护；
- 用户空间 power policy；
- 内核或驱动本身的上下界。

若多个服务直接写同一节点，后写者会覆盖前一个约束，撤销时还可能恢复到过期值。
更稳妥的做法是让一个资源管理器持有所有 vote：

- 有效最小值取各 min vote 的较大值；
- 有效最大值取各 max vote 的较小值；
- 若 min 大于 max，应由安全/thermal 上限获胜，同时记录冲突；
- vote 必须携带来源、创建时间、过期时间和撤销路径。

这里的优先级是产品安全规则，不是 IPower AIDL 自动提供的功能。厂商需要在设计文档
和测试用例中明确它。

### 3.3 配置驱动不等于“任意写节点”

把 mode/boost 到 action 的映射放进 vendor 配置，能缩短调参周期，但配置仍需满足：

- 每个 action 有明确的 reset 值或可逆操作；
- 节点缺失、格式错误、写入失败时有日志和计数；
- 一组 action 应尽量原子切换，避免只写成功一半；
- 启动时读取当前硬件状态，不能假定所有节点处于默认值；
- Power HAL 崩溃重启后能重建仍有效的持久 mode，临时 boost 不应无限续存；
- user build 不暴露可被普通应用修改的 vendor 配置。

AOSP 的 task profile 也能提供一部分标准化执行能力。
`system/core/libprocessgroup/profiles/task_profiles.json` 在 Android 17 中定义了
`UClampMin`、`UClampMax`、`UClampLatencySensitive` 属性，以及
`HighPerformance`、`MaxPerformance` 等 profile。`TaskProfiles::SetTaskProfiles()`
最终逐项执行对应 action。

这些 profile 证明 Android 已有 cgroup/uclamp 的统一描述机制，但没有规定 Power
HAL 必须使用它们。厂商若自行写 cgroup 节点，要确认 v1/v2 路径、进程迁移和
Framework task profile 不会互相覆盖。

## 4. 怎样把电源提示映射到 schedutil

### 4.1 schedutil 的输入是利用率与约束

Power HAL 不需要、也不应调用 `sugov_update_single_freq()` 之类内核内部函数。
常见做法是修改 schedutil 能看到的输入或边界：

- 给关键线程或 task group 设置 uclamp min/max；
- 调整 cpufreq policy min/max；
- 改变任务所在 cpuset 或调度分组；
- 通过设备驱动或固件设置性能等级；
- 使用 vendor hook 影响 util 到频率的映射。

在 `android17-6.18-2026-06_r6` 中，`sugov_get_util()` 会处理
`scx_cpuperf_target()`、CFS boost、`effective_cpu_util()`、uclamp、I/O wait 等
输入；`get_next_freq()` 再通过 `trace_android_vh_map_util_freq` vendor hook、
`map_util_freq()` 和 `cpufreq_driver_resolve_freq()` 得到合法频点。

这意味着 uclamp min 更适合表达“该线程至少需要多少 CPU capacity”，cpufreq min
更像整个 policy 的频率下限。把短交互一律映射成很高的 policy min，可能让同一
cluster 上无关任务也长期运行在高频。

### 4.2 不要把 `rate_limit_us` 当成功耗旋钮

Android Common Kernel 6.18 通过
`cpufreq_policy_transition_delay_us(policy)` 初始化 `rate_limit_us`：

- 驱动提供 `transition_delay_us` 时使用驱动值；
- 否则从 `transition_latency` 计算并增加 50% 间隔；
- 都不可用时才回退到 1 ms。

减小 `rate_limit_us` 只会让 schedutil 更频繁地考虑更新，不保证频率更快生效，也
不保证更省电。它可能增加 irq work、锁竞争和固件请求。调整前应测量 util 变化到
频点生效的时间，并统计请求次数、命中率和能耗。

### 4.3 fast switch、`adjust_perf` 与固件 DVFS

Android Common Kernel 的单 CPU policy 有三种相关路径：

- fast switch 已启用且驱动支持 `adjust_perf`：直接提交 performance level；
- fast switch 已启用：调用 `cpufreq_driver_fast_switch()`；
- 不支持 fast switch：通过 irq work 和 governor kthread 延后更新。

shared policy 会聚合 policy 内各 CPU 的需求。即便两个 SoC 都显示
`scaling_governor=schedutil`，它们也可能采用不同的 policy 拓扑、驱动回调和固件
控制方式，所以频率响应、能耗与 thermal 行为不能只按 governor 名称比较。

## 5. 与 cpuidle、thermal 的交互

### 5.1 性能 vote 会改变空闲机会

提高 uclamp 或频率下限可能缩短任务执行时间，增加连续 idle 窗口；也可能提高动态
功耗和温度，导致后续 thermal 限频。降低频率可能减少瞬时功率，却让任务运行更久，
推迟 CPU 进入空闲。

这就是 race-to-idle 需要实测的原因。没有哪一种策略能脱离工作负载、漏电、频点
能效和 idle state 切换成本，单靠“频率更低”证明省电。

### 5.2 latency QoS 会限制 idle 深度

交互、音频或相机等低延迟场景可以通过 PM QoS 限制允许的 idle exit latency。
cpuidle governor 会在约束内选择状态；约束越紧，可选的深状态越少。

这类 vote 必须有清晰的撤销路径。音频停止后若 latency constraint 残留，CPU 可能
长期只能进入浅 idle，即使 schedutil 已经降到最低频。排查时要把 cpufreq residency
和 cpuidle residency 分开看。

### 5.3 thermal 必须独立于性能提示

Power HAL 可以把温度或 headroom 纳入策略，但 thermal safety 不应依赖应用是否
正确关闭 session。thermal 上限应能压过 LAUNCH、GAME、ADPF 等性能 vote。

性能退化也不能只归因于 schedutil：当 thermal cooling 限制加强 policy max 时，
schedutil 即使请求更高频率，也会被 `cpufreq_driver_resolve_freq()` 限制在当前
上界内。

## 6. 常见 mode/boost 的实现检查

| 输入 | 合理目标 | 需要警惕的问题 |
| --- | --- | --- |
| `LOW_POWER` | 降低非关键资源上限、减少后台能耗 | 与 thermal 重复限频；退出后未恢复 |
| `INTERACTIVE` | 区分可交互与非交互设备状态 | 误当成每次触摸 boost |
| `DEVICE_IDLE` | 配合整机空闲减少非必要活动 | 误认为它会直接选择 cpuidle state |
| `DISPLAY_INACTIVE` | 优化显示关闭或低功耗显示场景 | 与 HWC、刷新率状态不同步 |
| `LAUNCH` | 给应用启动提供短期资源 | 电池节省策略可能在 PMS 中拦截 enable |
| `INTERACTION` | 覆盖 governor 尚未感知负载的短窗口 | 固定超长时限、连续事件无限续期 |
| `DISPLAY_UPDATE_IMMINENT` | 提前准备显示处理路径 | 每帧都设置高 policy min |
| `SUSTAINED_PERFORMANCE` | 提供可持续、稳定的性能范围 | 当成峰值性能模式 |
| `FIXED_PERFORMANCE` | 降低基准测试中的频率波动 | 用于普通用户场景；忽略 thermal |
| Hint Session | 按线程工作时长调节性能 | TID 生命周期错误、session 泄漏、报告过频 |

Android 17 的 `Mode` 和 `Boost` 枚举只定义场景语义，不给出表中的具体参数。表内
“合理目标”是实现检查方向，参数仍要由产品数据决定。

## 7. 不同 SoC 应怎样比较

缺少同版本公开源码时，可以按以下维度做设备实测，而不是按品牌给结论：

| 维度 | 需要记录的证据 |
| --- | --- |
| Power HAL | AIDL 版本、支持位图、dump、场景 trace、配置版本 |
| CPU topology | cpufreq policy 覆盖哪些 CPU、capacity、OPP 表 |
| schedutil | `rate_limit_us`、fast switch、`adjust_perf`、vendor hook |
| 调度约束 | cpuset、uclamp、task profile、sched_ext 是否启用 |
| CPU idle | driver、governor、state latency/residency、vendor hook |
| 其他资源 | GPU、DDR/interconnect、cache、DSP/NPU 是否跟随场景 |
| thermal | cooling device、温度阈值、skin/SoC sensor、持续功耗 |
| 固件 | DVFS 是否由 firmware 仲裁、请求到生效的 trace 差值 |

比较报告应至少写明设备型号、SoC、Android build fingerprint、kernel tag/commit、
Power HAL 服务版本、环境温度、电池电量和测试次数。只写“某厂商 fast switch 更快”
无法复现，也无法排除 thermal、频点表或 workload 差异。

## 8. 验证：从接口到能耗分四步

### 8.1 验证服务与契约

下面的命令用于确认服务注册、VINTF 声明和 AIDL VTS：

```bash
adb shell service list | grep android.hardware.power
adb shell dumpsys android.hardware.power.IPower/default
adb root
adb shell grep -R -A6 android.hardware.power /vendor/etc/vintf /odm/etc/vintf
atest VtsHalPowerTargetTest
```

`VtsHalPowerTargetTest.cpp` 在 Android 17 源码中覆盖 mode、boost、支持查询、
Hint Session、FMQ channel、headroom 和 composition data 等接口。VTS 通过只证明
契约行为符合要求，不证明场景参数带来净能耗收益。`adb root` 只适用于可调试
build；量产 user build 应通过构建产物或设备厂商提供的诊断接口核对 VINTF fragment。

### 8.2 验证触发与撤销

每个 mode/boost/session 都应留下可查询记录：

- 收到请求的时间、参数和调用来源；
- 是否支持、是否进入仲裁；
- 生效 action、失败 action 和最终 vote；
- boost 过期时间；
- disable/close 后撤销了哪些约束；
- HAL 重启后恢复了哪些持久状态。

下面的命令用于在测试前后保存 Power HAL 与关键内核节点：

```bash
adb shell dumpsys android.hardware.power.IPower/default > power-before.txt
adb shell 'for p in /sys/devices/system/cpu/cpufreq/policy*; do
  echo "$p"
  cat "$p/scaling_min_freq" "$p/scaling_max_freq" "$p/scaling_cur_freq"
  cat "$p/schedutil/rate_limit_us" 2>/dev/null
done' > cpufreq-before.txt
```

触发场景后重复采集并比较。`scaling_cur_freq` 是采样值，不能替代 trace；节点也可能
因 user build 权限无法读取，需要在 userdebug/eng build 上完成底层验证。

### 8.3 验证内核响应

建议用同一条 Perfetto trace 对齐以下信号：

- Power HAL mode/boost/session 的 atrace；
- `sched_switch`、`sched_wakeup` 和可用的 uclamp trace；
- `cpu_frequency`、cpufreq policy limit；
- `cpu_idle`；
- thermal temperature 与 cooling state；
- 目标业务的 frame、launch 或 work-duration 指标。

判断因果时按“请求 → vote → 内核约束 → 调度/频率/idle → 业务结果”逐段取证。若只
看到 boost 与频率同时上升，还不能区分是 Power HAL 提高了约束，还是任务利用率本身
触发 schedutil。

### 8.4 验证净收益与恢复

一次合格的 A/B 测试至少同时报告：

- 业务：启动分位数、帧 deadline miss、音频 underrun、相机时延等；
- 功耗：电池电流或 rail energy，不能只用 CPU frequency 代替；
- thermal：初始温度、峰值、稳态温度和 throttling 时间；
- 内核：频率分布、idle residency、调度迁移和唤醒次数；
- 稳定性：HAL 重启、调用方死亡、boost 超时、session close 后是否恢复。

测试应固定亮度、网络、温度区间、电量区间、应用数据和操作脚本，随机化 A/B 顺序并
重复多轮。优化若只降低平均功率，却使任务时间明显拉长，需要比较整段任务能量，而
不是截取相同的几秒。

## 9. 版本演进应怎样写

Android 的 Power HAL 早期使用 HIDL 1.0～1.3，主要承载 interactive 与传统 power
hint。AIDL 接口加入稳定版本管理，并逐步扩展 Hint Session、FMQ、支持信息、
composition data 与 headroom。

在 `android-17.0.0_r1` 中：

- `android.hardware.power` 已冻结到 V7；
- `PowerHalController` 优先连接 AIDL，源码仍保留 HIDL 1.0～1.3 fallback；
- AIDL V7 有 18 个 mode、6 个 boost；
- VTS 会按实现声明的能力测试 Hint Session、FMQ、headroom 等路径；
- kernel 侧统一以 `android17-6.18-2026-06_r6` 的 schedutil、cpuidle 和 vendor
  hook 为准。

版本演进可以保留历史 HIDL 行为，但分析 Android 17 商品实现时，应以设备实际注册
的 AIDL/HIDL 服务为准，不能因为 Framework 有 fallback 就推断设备仍使用 HIDL。

## 10. 实现评审清单

- [ ] VINTF、init、SELinux 与 `IPower/default` 服务名一致。
- [ ] `isModeSupported()`、`isBoostSupported()`、`SupportInfo` 与行为一致。
- [ ] `Mode` 幂等，`Boost` 有过期和取消，Hint Session 能处理调用方死亡。
- [ ] 每个资源只有一个仲裁所有者，min/max 冲突有确定规则。
- [ ] action 可逆；部分写入失败、HAL 重启后不会残留高性能约束。
- [ ] thermal/safety 上限可覆盖所有性能请求。
- [ ] 没有把商品设备私有节点写成 Android 公共接口。
- [ ] schedutil 参数修改有 trace 数据，不使用固定延迟传闻。
- [ ] 同时评估业务、功耗、thermal、cpufreq 与 cpuidle。
- [ ] 结论包含设备、build、kernel、HAL 配置和实验条件。
