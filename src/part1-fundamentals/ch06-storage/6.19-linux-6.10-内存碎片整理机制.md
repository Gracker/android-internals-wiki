# 6.19 Android 17 / Linux 6.18 内存规整机制

> 内核源码锚点为 `android17-6.18-2026-06_r6`。Proactive compaction 早于 Linux 6.10 已存在，不能把它列为 6.10 新特性。

## 1. 物理内存规整解决什么问题

应用看到的是连续虚拟地址，页表可以把它映射到分散的物理页；多数普通 order-0 分配不要求物理连续。问题出现在内核需要高阶连续页时，例如：

- Transparent Huge Page（THP）分配；
- CMA 或部分 DMA 连续内存需求；
- SLUB、高阶内核页和其他明确请求 `order > 0` 的分配。

系统可能还有很多空闲页，但这些页散落在不同 pageblock 中，无法组成所需阶数的 buddy block。这是外部碎片。

Memory compaction 会从一端隔离可迁移页，从另一端隔离空闲页，把仍在使用的 movable page 迁移到目标页，腾出较大的连续空闲块。它不会凭空增加空闲内存总量。回收（reclaim）负责释放或换出页，规整（compaction）负责重新排列物理页，两者目标不同。

## 2. Android 17 内核中的四种触发路径

`android17-6.18-2026-06_r6` 的 `mm/compaction.c` 保留四类触发：

| 路径 | 触发者 | 目标 | 可能影响前台延迟吗 |
|---|---|---|---|
| direct compaction | 高阶分配调用线程 | 尽快满足当前 order | 会，调用线程可能同步扫描和迁移 |
| allocation-driven `kcompactd` | page allocator 唤醒每个 node 的线程 | 在后台准备指定 order | 间接影响 CPU、内存带宽和锁竞争 |
| proactive compaction | `kcompactd` 周期检查碎片分数 | 在请求到来前降低高阶碎片 | 会产生系统级后台成本 |
| 手工触发 | `compact_memory` 或可用的 node sysfs | 规整全部 node 或指定 node | 容易形成明显的扫描和迁移峰值 |

`vm.compaction_proactiveness=0` 只关闭 proactive compaction。高阶分配仍可进入 direct compaction，也仍可按分配需求唤醒 `kcompactd`。

## 3. Proactive compaction 的评分算法

Proactive compaction 不是 Linux 6.10 新增功能。Linux 5.19 文档已经记录 `compaction_proactiveness`；这里只讨论 Android 17 的 6.18 锚点中它怎样工作。

下面的源码片段用于说明 zone 分数和 node 权重，来自当前基线的 `mm/compaction.c`：

```c
static unsigned int fragmentation_score_zone(struct zone *zone)
{
    return extfrag_for_order(zone, COMPACTION_HPAGE_ORDER);
}

static unsigned int fragmentation_score_zone_weighted(struct zone *zone)
{
    unsigned long score;

    score = zone->present_pages * fragmentation_score_zone(zone);
    return div64_ul(score, zone->zone_pgdat->node_present_pages + 1);
}
```

`extfrag_for_order()` 计算相对于 `COMPACTION_HPAGE_ORDER` 的外部碎片比例，范围是 0—100。zone 分数再按该 zone 占整个 node 的页数加权，所以较大的 `ZONE_NORMAL` 通常比小型专用 zone 更影响 node 总分。源码没有按“数据库”“游戏”或“车机”给不同 zone 写死策略。

阈值由 `compaction_proactiveness` 推导：

```text
low  = 100 - compaction_proactiveness
high = min(low + min(10, low / 2), 100)
```

默认值 20 对应 low=80、high=90。node 分数高于 high 时，`should_proactive_compact_node()` 允许启动；规整持续到各 zone 分数落到 low 附近，或遇到锁竞争、无进展等退避条件。`kswapd` 正在运行时，proactive 路径会跳过，避免两种后台内存工作同时争用资源。

如果本轮规整后 node 分数没有下降，`kcompactd` 会放大下一次检查的等待时间。这是避免反复做无效扫描的退避，不是按负载趋势预测未来碎片。

## 4. 参数含义不能互换

### `vm.compaction_proactiveness`

- 范围 0—100，内核默认值为 20；
- 0 关闭 proactive compaction；
- 写入任何非零值会立即唤醒各在线 node 的 `kcompactd`；
- 大于 80 会让触发更敏感、单次目标区间更窄；
- 内核文档明确警告，接近 100 可能造成过量后台规整。

因此，执行 `echo 20 > ...` 也会立即触发一次 proactive 检查。测试参数变化时，应把写入瞬间与稳态观测分开。

### `vm.extfrag_threshold`

范围 0—1000，默认值 500。它使用 debugfs `extfrag_index` 的 fragmentation index，帮助高阶分配在 compaction 和 reclaim 之间做选择。接近 0 表示失败更像是内存不足，接近 1000 表示失败更像是外部碎片，`-1` 表示水位满足时分配可以成功。

该参数不等于 proactive compaction 的 0—100 score，也不能用来直接指定 `kcompactd` 的积极程度。

### `vm.compact_unevictable_allowed`

它控制 compaction 是否检查 unevictable LRU 上的页。普通内核默认 1，PREEMPT_RT 默认 0。迁移 mlocked page 可能让后续 minor fault 等待页迁移完成，低延迟产品需要结合内核配置和实测评估。

### `vm.compact_memory`

写入 1 会对所有 node 的 zone 执行手工规整。它适合受控诊断或实验，不是日常“清理内存”按钮。频繁调用可能把扫描、迁移和内存带宽成本集中到前台敏感窗口。

`/sys/devices/system/node/node*/compact` 只在相应 `CONFIG_SYSFS`、`CONFIG_NUMA` 等条件成立时注册。量产 Android 设备未必暴露该节点，不能把它列为所有设备通用接口。

## 5. Android 平台中的“app compaction”是另一件事

Android 17 的 `CachedAppOptimizer` 也使用 compaction 这个词，但当前源码主要做进程内存回收：

- native 路径通过 `process_madvise()` 对目标进程 VMA 发送 `MADV_COLD` 或 `MADV_PAGEOUT`；
- memcg 路径可以写 cgroup v2 的 `memory.reclaim`；
- 目标是降低 cached process 的 RSS 或把匿名页换出到 zram。

这些操作释放或降温进程页，不负责在 buddy allocator 中把空闲页拼成高阶连续块。它们可能间接改变内存压力和可迁移页分布，但不能与 `mm/compaction.c` 的 physical compaction 画等号。

LMKD 同样没有调用 `fragmentation_score_node()` 的直接协调协议。LMKD 依据压力和进程优先级选择杀进程；进程退出后释放页面可能改善后续分配条件，这只是间接关系。

## 6. Android 17 产品边界

源码锚点为 `android17-6.18-2026-06_r6`。该源码中：

- `CONFIG_COMPACTION` 默认启用，并由 THP 等配置选择；
- arm64 GKI defconfig 启用 `CONFIG_TRANSPARENT_HUGEPAGE=y` 和 `CONFIG_TRANSPARENT_HUGEPAGE_MADVISE=y`；
- GKI defconfig 启用 CMA；
- `mm/compaction.c` 还包含 Android vendor hook，厂商可对可规整 zone 和部分决策做定制。

这些事实证明 common kernel 具备实现，不代表所有 Android 17 设备运行 6.18，也不代表最终产品保留所有 debugfs、tracepoint 或 sysctl 写权限。设备分析必须记录：

- `uname -r` 与 kernel build；
- 最终 `.config` 或 `/proc/config.gz`；
- page size、THP/CMA 配置；
- OEM init、SELinux 和 sysctl 初始值；
- vendor module 与 hook 行为。

## 7. 正确读取指标

### 7.1 `/proc/vmstat`

下面的命令用于读取 Android 17 内核中与规整相关的累计计数：

```bash
adb shell 'grep -E "^(compact_|compact_daemon_)" /proc/vmstat'
```

当前源码导出的关键名字包括：

- `compact_stall`：分配路径进入 direct compaction 的次数；
- `compact_success` / `compact_fail`：direct compaction 对目标分配的结果计数；
- `compact_migrate_scanned` / `compact_free_scanned`：扫描规模；
- `compact_isolated`：隔离页计数；
- `compact_daemon_wake`：`kcompactd` 被分配需求唤醒的次数；
- `compact_daemon_migrate_scanned` / `compact_daemon_free_scanned`：daemon 扫描规模。

它们是开机以来的累计值，先后两次采样做 delta 才能对应一次场景。`compact_fail` 增加不等于应用崩溃；它只表示一次 direct compaction 没有为目标分配形成所需连续块。

### 7.2 buddy 与外部碎片

下面的命令用于同时查看各 order 空闲块和按 migratetype 划分的 pageblock：

```bash
adb shell cat /proc/buddyinfo
adb shell su 0 cat /proc/pagetypeinfo
adb shell su 0 cat /sys/kernel/debug/extfrag/extfrag_index
```

`/proc/buddyinfo` 能看到高阶空闲块是否稀缺，但不能区分“总内存太少”和“空闲页太碎”。`extfrag_index` 帮助区分这两类原因；`pagetypeinfo` 的 mixed pageblock 信息依赖 `CONFIG_PAGE_OWNER`，而且收集成本较高，不适合高频轮询。debugfs 路径也只在产品启用对应配置并挂载 debugfs 时存在。

### 7.3 tracepoint

Android 17 基线在 `include/trace/events/compaction.h` 定义了以下可用事件：

- `mm_compaction_begin` / `mm_compaction_end`；
- `mm_compaction_migratepages`；
- `mm_compaction_try_to_compact_pages`；
- `mm_compaction_kcompactd_sleep`；
- `mm_compaction_wakeup_kcompactd` / `mm_compaction_kcompactd_wake`。

采集前先从 tracefs `available_events` 枚举产品内核保留的事件。Perfetto 中把 compaction 区间与应用 runnable latency、CPU 频率、page fault、reclaim、PSI 和 block I/O 对齐，才能判断规整是否处在卡顿窗口。

## 8. 怎样判断是否需要调参

不要从设备 RAM 容量直接推出一个固定 `compaction_proactiveness`。同样是 8GB 设备，相机连续 buffer、游戏资源加载、16KB page size、THP 使用率和厂商驱动高阶分配需求都可能不同。

建议按以下顺序实验：

1. 记录默认 sysctl、内核配置和 30 分钟以上的代表性负载；
2. 计算 vmstat delta，观察 direct compaction stall、成功率和 daemon 扫描量；
3. 用 trace 确认前台长尾是否与 compaction 重叠；
4. 检查目标高阶分配来自 THP、CMA、驱动还是内核对象；
5. 每次只改一个参数，用小步变化做 A/B，并预设回滚值；
6. 同时评估功耗、CPU 时间、应用 P95/P99、分配失败和 OOM/LMKD 指标。

以下信号组合比单个计数更有意义：

| 现象 | 可能解释 | 下一步 |
|---|---|---|
| `compact_stall` 高、success 比例低、extfrag index 接近 0 | 更像内存不足 | 同查 reclaim、PSI、LMKD 和工作集 |
| `compact_stall` 高、extfrag index 接近 1000 | 高阶外部碎片明显 | 找到目标 order 和分配者，再评估后台准备 |
| daemon 扫描量大、node score 降不下来 | 页不可迁移、锁竞争或分布不利 | 查看 pagetypeinfo、migrate failure 与 vendor hook |
| 前台卡顿与 proactive 区间重叠 | 后台规整争用 CPU/带宽/锁 | 小步降低积极度并复测分配失败 |
| 高阶分配稳定、proactive CPU 明显 | 可能规整过度 | 评估较低值，不能直接关闭所有 compaction |

## 9. 常见误区

- Proactive compaction 早于 Linux 6.10，不能写成 6.10 的“创新分层策略”；
- 当前 Android 17 内核锚点是 `android17-6.18-2026-06_r6`，不是 `android17-6.12`；
- 源码不支持“碎片率降低 60%”或“崩溃减少 45%”的通用结论；
- 没有按数据库、游戏、低内存设备规定 35、10、15 等固定参数；
- score 是当前高阶外部碎片度量，不是趋势预测器；
- `extfrag_threshold` 与 `compaction_proactiveness` 使用不同刻度、服务不同决策；
- `/proc/meminfo` 没有通用的 `Compacted` 统计，正确累计计数位于 `/proc/vmstat`；
- debugfs 路径是 `/sys/kernel/debug/extfrag/extfrag_index`，不是 `/sys/kernel/debug/mm/extfrag`；
- `dmesg | grep kcompactd` 没有稳定的周期统计语义，应优先使用 vmstat 和 tracepoint；
- CachedAppOptimizer 的进程 “compaction” 属于 reclaim/pageout 路径，不是 physical compaction。

## 10. 小结

Linux memory compaction 的任务是移动可迁移页，形成高阶连续空闲块；它不增加空闲内存总量。Android 17 的 6.18 锚点同时包含 direct compaction、allocation-driven `kcompactd`、proactive compaction 和手工触发路径。

`compaction_proactiveness` 只控制 proactive 路径，默认值 20 也不是所有产品的最优值。调参前先确认高阶分配需求、外部碎片程度、direct stall 与前台长尾之间的关系，再用小步 A/B 验证。否则，降低规整可能把成本推回前台 direct compaction，提高规整又可能制造后台 CPU、内存带宽和锁竞争。
