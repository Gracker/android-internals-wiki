# 6.03 Android 17 SharedPreferencesImpl ANR机制

> **版本边界**：本节锚定 AOSP `android-17.0.0_r1` / Android 17 (API 37)。调研材料指出，`SharedPreferencesImpl` 相比 Android 16 的运行时写入/加载路径没有行为变化，Android 17 的重点信号是 `SharedPreferences.java` javadoc 更明确地劝退 SharedPreferences 并推荐迁移到 DataStore。

## 要点

### 锚点 1：SharedPreferencesImpl 的真实架构边界

Android 17 中，`SharedPreferencesImpl` 仍是 `SharedPreferences` 的核心平台实现。它的性能风险来自“内存先行、磁盘异步或同步落盘”的设计，而不是 Android 17 新增了一套特殊 ANR 机制：

- **内存状态**：解析后的键值对保存在 `mMap`，编辑器通过 `commitToMemory()` 先合并到内存，再决定是否写盘。
- **文件状态**：主文件 `mFile` 与备份文件 `mBackupFile` 组成简单的崩溃恢复协议；写入前可能把旧 `.xml` rename 为 `.bak`，成功写入后删除 `.bak`，失败时保留备份供下次 `loadFromDisk()` 恢复。
- **锁边界**：源码中不是通用“读写锁分离”模型，而是多个 monitor 分工：`mLock` 保护加载/内存状态，`mWritingToDiskLock` 串行化磁盘写入，`EditorImpl` 还使用 `mEditorLock` 保护本次编辑的修改集。
- **加载线程**：构造 `SharedPreferencesImpl` 后通过 `startLoadFromDisk()` 把解析任务投递到静态 `sLoadExecutor`；调研材料记录该 executor 为 0-1 核心的串行线程池，空闲约 10 秒后回收线程。

### 锚点 2：读路径 ANR 风险：awaitLoadedLocked 是隐式主线程等待

首次访问 SharedPreferences 时，真实 XML 解析虽然在后台加载线程上执行，但调用方读值仍可能在主线程等待加载完成：

```text
ContextImpl.getSharedPreferences()
  -> new SharedPreferencesImpl(...)
  -> startLoadFromDisk()

UI thread: getString()/getInt()/edit()
  -> synchronized (mLock)
  -> awaitLoadedLocked()
  -> while (!mLoaded) mLock.wait()

sLoadExecutor:
  -> loadFromDisk()
  -> XmlUtils.readMapXml(...)
  -> synchronized (mLock) { mLoaded = true; mLock.notifyAll(); }
```

两个容易误判的点：

1. `awaitLoadedLocked()` 在等待前会调用 `BlockGuard.getThreadPolicy().onReadFromDisk()`。这是为了让 StrictMode 能把“主线程等待读盘结果”识别为读盘违规，即使实际文件读取发生在后台线程。
2. ANR 的门槛不是 SharedPreferences 自己定义的固定 5 或 10 秒；真正是否 ANR 取决于调用场景所处的系统超时窗口。SharedPreferences 在这里提供的是“让主线程等待”的条件。

### 锚点 3：写路径风险：commit 同步 fsync，apply 异步但会被生命周期收口

`commit()` 与 `apply()` 的区别主要体现在写盘线程和结果返回语义：

- **`commit()`**：调用 `commitToMemory()` 后同步等待磁盘写入完成，并返回写盘成功/失败结果。源码调研材料指出，当 `mDiskWritesInFlight == 1` 时，`enqueueDiskWrite()` 会直接在调用线程执行 `writeToFile()`，因此主线程调用 `commit()` 可能直接卡在 `FileUtils.sync()` / `FileDescriptor.sync()`。
- **`apply()`**：先把变更合并到内存并立即返回，不暴露写盘失败信号；写盘任务通过 `QueuedWork.queue()` 放到 `queued-work-looper` 后台线程串行执行。
- **关键风险**：`apply()` 不是“永不阻塞主线程”。它会向 `QueuedWork` 注册 finisher，系统在特定生命周期收口点调用 `QueuedWork.waitToFinish()`，把未完成的 apply 写盘同步等完。

典型卡顿链路：

```text
Activity A: editor.apply()
  -> queued-work-looper 正在 fsync
用户切到 Activity B / Activity A stop
  -> ActivityThread.handleStopActivity()
  -> QueuedWork.waitToFinish()
  -> 主线程等待 finisher / 写盘完成
慢存储或队列堆积
  -> 主线程长时间无响应，可能演化为 ANR
```

### 锚点 4：QueuedWork.waitToFinish 的 Android 17 调用点

调研材料在 `ActivityThread.java`（`android-17.0.0_r1`）中定位到 4 个 `QueuedWork.waitToFinish()` 主线程调用点：

| 场景 | 调用点含义 | 风险说明 |
|---|---|---|
| `Service.handleStartCommand` 后 | Service 启动命令处理完毕后收口 | Service 内 apply 队列可能反压主线程 |
| `Service.handleStopService` 后 | Service 销毁清理前收口 | 停止服务时等待未完成写盘 |
| `handlePauseActivity` | legacy / pre-Honeycomb Activity 路径 | 旧兼容路径，不是现代 Activity 的主要触发点 |
| `handleStopActivity` | Activity 停止时收口 | 常见：页面跳转、退后台、配置变化后等待 apply 写盘 |

`QueuedWork` 内部维护等待耗时 histogram，并使用 `MAX_WAIT_TIME_MILLIS = 512ms` 作为慢等待告警阈值。需要注意：512ms 是 waitToFinish 的慢等待记录/告警阈值，不是 EditorImpl 的操作超时，也不是“512ms 后自动取消写盘”。

### 锚点 5：fsync 监控：histogram 是观测，不是 ANR 触发器

`SharedPreferencesImpl.writeToFile()` 在 XML 内容写入后调用 `FileUtils.sync(FileOutputStream)`，后者包装 `stream.getFD().sync()`。源码调研材料记录写盘结束后会把 fsync 耗时写入 `mSyncTimes`：

```java
long fsyncDuration = fsyncTime - writeTime;
mSyncTimes.add((int) fsyncDuration);
mNumSync++;
if (DEBUG || mNumSync % 1024 == 0 || fsyncDuration > MAX_FSYNC_DURATION_MILLIS) {
    mSyncTimes.log(TAG, "Time required to fsync " + mFile + ": ");
}
```

- `MAX_FSYNC_DURATION_MILLIS = 256ms`：单次 fsync 超过 256ms 会触发日志输出。
- `ExponentiallyBucketedHistogram(16)`：用于记录 fsync 耗时分布。
- **审计修正**：histogram 只在 fsync 完成后观测耗时，不会主动阻塞业务，也不是 ANR 触发器；它也不直接暴露 `QueuedWork` 队列长度。

## 工程建议

### 1. 主线程读路径：避免首次访问即等待 XML 解析

- 不要在启动首帧、`ContentProvider.onCreate()`、首个 `Activity.onCreate()` 的关键路径上首次读取大 SharedPreferences 文件。
- 若仍需使用 SharedPreferences，可在可控时机提前触发小文件加载；但这只是把等待移动到更安全的窗口，不改变底层 XML 解析成本。
- 对大对象、列表、频繁变化的配置，不要继续塞进单个 SharedPreferences XML。

### 2. 写路径：减少生命周期收口时的 apply 堆积

- UI 生命周期回调（尤其 `onPause()` / `onStop()`）中避免批量 `apply()` 多个文件。
- 把高频计数、埋点缓存、会话状态与低频配置拆开，避免每次页面切换都触发同一 SharedPreferences 文件重写。
- 对必须知道持久化结果的关键配置，不能简单把 `commit()` 机械替换为 `apply()`；应在后台线程执行同步写入并显式处理失败。

### 3. 迁移策略：DataStore 是新实现优先项

Android 17 的 `SharedPreferences.java` javadoc 已更明确列出 SharedPreferences 的缺陷：UI 阻塞、`apply()` 可能触发生命周期等待、缺少错误信号、内存状态可能领先磁盘状态。新代码优先考虑 Jetpack DataStore；老代码迁移时建议：

1. 先识别启动关键路径和生命周期回调中的 SharedPreferences 读写。
2. 对低风险配置做 DataStore 旁路迁移或双读校验。
3. 对登录态、实验开关等关键配置保留回滚方案，避免迁移过程引入一致性问题。

### 4. 诊断抓手

- **StrictMode**：用于暴露主线程首次读取 SharedPreferences 的风险；`awaitLoadedLocked()` 已主动标记 read-from-disk。
- **日志与源码 histogram**：关注 `Time required to fsync ...` 相关日志，尤其是超过 256ms 的 fsync。
- **ANR trace / Perfetto**：从主线程栈中确认是否卡在 `QueuedWork.waitToFinish()`、`CountDownLatch.await()` 或 SharedPreferences 加载等待；Perfetto 侧应使用通用调度、block I/O、binder/lifecycle 等信号交叉判断。不要假设存在 `sharedpreferences_read` / `sharedpreferences_write` 这类 AOSP ftrace 事件。

## 待验证与边界

- 本节不推导 Android 18/API 38+ 主线行为；所有源码结论限制在 `android-17.0.0_r1`。
- `@RavenwoodKeepWholeClass` 的测试框架语义未在本节展开；当前材料只支持“对 SharedPreferencesImpl 运行时行为无新增优化结论”。
- 设备端 fsync 延迟高度依赖闪存、文件系统、压力与厂商内核策略；文中不使用未实测的固定耗时作为普遍结论。
- Perfetto 可辅助定位调度和 I/O 等待，但本节不声明 Android 17 平台提供专属 SharedPreferences ftrace 事件。
