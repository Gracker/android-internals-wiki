# 6.2 Android 17 SharedPreferencesImpl ANR 深度机制

> **版本边界**：本节基于 `android-17.0.0_r1` 源码逐行验证，diff `android-16.0.0_r3` 在 SharedPreferencesImpl.java 上仅有 `@RavenwoodKeepWholeClass` 注解的新增，无运行时行为变更。[已验证: AOSP android-17.0.0_r1]
>
> 与 6.5 节的关系：6.5 覆盖 SharedPreferences/DataStore 的全景优化策略，本节聚焦 SharedPreferencesImpl **内部状态机与 ANR 触发链的源码级拆解**，为 6.5 的优化建议提供机制底座。

## 1. SharedPreferencesImpl 的双轨架构

SharedPreferencesImpl（以下简称 SPI）采用「内存缓存 + 文件持久化」双轨设计。理解 ANR 的第一步是理清两条轨道的状态如何同步。

### 1.1 内存轨道的关键字段

```java
// frameworks/base/core/java/android/app/SharedPreferencesImpl.java @ android-17.0.0_r1

@GuardedBy("mLock")
private Map<String, Object> mMap;              // 当前生效的键值对

@GuardedBy("mLock")
private int mDiskWritesInFlight = 0;           // 已提交到内存但尚未完成落盘的写入数

@GuardedBy("mLock")
private boolean mLoaded = false;               // 初始 XML 是否已解析完毕

@GuardedBy("this")
private long mCurrentMemoryStateGeneration;    // 内存状态代际号（单调递增）

@GuardedBy("mWritingToDiskLock")
private long mDiskStateGeneration;             // 最后一次成功落盘的代际号
```

`mCurrentMemoryStateGeneration` 与 `mDiskStateGeneration` 的差值代表「内存已变更但磁盘尚未同步」的代数。`writeToFile()` 在成功写入后会执行 `mDiskStateGeneration = mcr.memoryStateGeneration`，将两者对齐。

### 1.2 文件轨道的关键字段

```java
private final File mFile;          // 正式文件：/data/data/<pkg>/shared_prefs/<name>.xml
private final File mBackupFile;    // 备份文件：mFile.getPath() + ".bak"
```

每次写入前，SPI 会将 `mFile` 重命名为 `mBackupFile`，然后创建新的 `mFile`。如果写入过程中崩溃，下次启动时 `loadFromDisk()` 发现 `mBackupFile` 存在，就会删除残缺的 `mFile`、将 `mBackupFile` 恢复为 `mFile`。这就是 SPI 的崩溃恢复原子性协议。

### 1.3 锁层次

源码注释中明确声明了锁获取顺序：

```
// Lock ordering rules:
//  - acquire SharedPreferencesImpl.mLock before EditorImpl.mLock
//  - acquire mWritingToDiskLock before EditorImpl.mLock
```

三把锁的职责：
- **`mLock`**：保护内存状态（mMap、mLoaded、mDiskWritesInFlight 等）
- **`mEditorLock`**（EditorImpl 内部）：保护 Editor 的修改缓冲区 `mModified`
- **`mWritingToDiskLock`**：保护磁盘写入的串行化

锁顺序违反会导致死锁。`commitToMemory()` 先获取 `mLock` 再获取 `mEditorLock`，`writeToFile()` 获取 `mWritingToDiskLock`，严格遵守上述层次。

[已验证: AOSP android-17.0.0_r1, frameworks/base/core/java/android/app/SharedPreferencesImpl.java]

## 2. ANR 触发链 1：首次加载阻塞（awaitLoadedLocked）

### 2.1 加载流程

SPI 构造函数调用 `startLoadFromDisk()`，将 `loadFromDisk()` 投递到静态线程池：

```java
private static final ThreadPoolExecutor sLoadExecutor = new ThreadPoolExecutor(
    0, 1,                          // core=0, max=1：单线程，空闲 10s 后回收
    10L, TimeUnit.SECONDS,
    new LinkedBlockingQueue<Runnable>(),
    new SharedPreferencesThreadFactory());  // 线程名: "SharedPreferences"
```

⚠️ **Android 17 变化注意**：旧文档中常提到的固定线程名 `"SharedPreferencesImpl-load"` 已不适用。android-17.0.0_r1 中线程名仅返回 `"SharedPreferences"`（通过 `SharedPreferencesThreadFactory`）。在 Perfetto / systrace 中搜索旧线程名会导致漏检。

`loadFromDisk()` 的核心步骤：
1. 检查 `mBackupFile.exists()` → 若存在，删除 `mFile`，将 `mBackupFile` 重命名为 `mFile`（崩溃恢复）
2. `Os.stat(mFile.getPath())` 获取文件元数据
3. `XmlUtils.readMapXml(new BufferedInputStream(new FileInputStream(mFile), 16*1024))` 解析 XML
4. 在 `mLock` 下更新 mMap、mStatTimestamp、mStatSize，设置 `mLoaded = true`
5. `mLock.notifyAll()` 唤醒所有等待线程

### 2.2 阻塞点

任何对 SP 的读写操作（`getString()`、`edit()`、`contains()` 等）都会先调用 `awaitLoadedLocked()`：

```java
@GuardedBy("mLock")
private void awaitLoadedLocked() {
    if (!mLoaded) {
        BlockGuard.getThreadPolicy().onReadFromDisk();
    }
    while (!mLoaded) {
        try {
            mLock.wait();
        } catch (InterruptedException unused) {
        }
    }
    if (mThrowable != null) {
        throw new IllegalStateException(mThrowable);
    }
}
```

主线程在 `mLock.wait()` 上阻塞，直到后台线程完成 XML 解析。阻塞时长取决于：
- **XML 文件大小**：几十 KB 的 SP 文件在低端设备上解析可超过 1 秒
- **I/O 竞争**：若设备正处于 I/O 压力下（如多个应用同时启动），`FileInputStream` 读取延迟放大
- **XML 解析效率**：`XmlUtils.readMapXml` 使用 `XmlPullParser`，对大 Map 的解析是 CPU 密集型操作

[已验证: AOSP android-17.0.0_r1, SharedPreferencesImpl.java#awaitLoadedLocked]

### 2.3 ANR 触发条件

主线程在 `awaitLoadedLocked()` 中阻塞时间过长 → InputDispatcher 无响应 → ANR。典型场景：
- 应用启动时在 `Application.onCreate()` 或首个 Activity 中同步读取大型 SP 文件
- SP 文件因长期累积，超过 100 KB 甚至更大
- 设备 I/O 繁忙（多应用并发启动、后台同步等）

## 3. ANR 触发链 2：commit() 同步落盘

### 3.1 commit() 的完整调用链

```java
// EditorImpl.commit()
public boolean commit() {
    MemoryCommitResult mcr = commitToMemory();           // 1. 更新内存
    SharedPreferencesImpl.this.enqueueDiskWrite(
        mcr, null /* sync write on this thread okay */); // 2. 当前线程执行磁盘写入
    try {
        mcr.writtenToDiskLatch.await();                  // 3. 等待写入完成
    } catch (InterruptedException e) {
        return false;
    }
    notifyListeners(mcr);
    return mcr.writeToDiskResult;
}
```

`enqueueDiskWrite()` 对 commit() 有特殊处理 — 当 `postWriteRunnable == null` 时，标记为同步写入：

```java
private void enqueueDiskWrite(final MemoryCommitResult mcr,
                              final Runnable postWriteRunnable) {
    final boolean isFromSyncCommit = (postWriteRunnable == null);
    // ...
    if (isFromSyncCommit) {
        boolean wasEmpty = false;
        synchronized (mLock) {
            wasEmpty = mDiskWritesInFlight == 1;
        }
        if (wasEmpty) {
            writeToDiskRunnable.run();  // 直接在调用线程执行！
            return;
        }
    }
    QueuedWork.queue(writeToDiskRunnable, !isFromSyncCommit);
}
```

当 `mDiskWritesInFlight == 1`（当前 commit 是唯一在途写入）时，`writeToDiskRunnable.run()` **直接在调用线程（通常是主线程）执行**。这意味着 `writeToFile()` 的全部 I/O 操作（包括 fsync）都在主线程完成。

如果 `mDiskWritesInFlight > 1`（前面有 apply() 的异步写入未完成），commit() 会被排入 QueuedWork 队列，等待异步线程处理后再执行，此时主线程阻塞在 `mcr.writtenToDiskLatch.await()`。

[已验证: AOSP android-17.0.0_r1, SharedPreferencesImpl.java#enqueueDiskWrite]

### 3.2 commit() 在主线程的 I/O 成本

主线程直接执行 `writeToFile()` 意味着以下操作同步发生：
1. `mFile.renameTo(mBackupFile)` — 文件系统元数据操作
2. `new FileOutputStream(mFile)` — 创建新文件
3. `XmlUtils.writeMapXml(mcr.mapToWriteToDisk, str)` — 序列化整个 Map 为 XML
4. **`FileUtils.sync(str)`** — **fsync**，强制刷盘，这是最耗时的操作
5. `Os.stat(mFile.getPath())` — 获取新文件元数据
6. `mBackupFile.delete()` — 删除备份文件

其中 fsync 的耗时取决于磁盘负载和硬件。SPI 内置了告警阈值：

```java
private static final long MAX_FSYNC_DURATION_MILLIS = 256;
// ...
long fsyncDuration = fsyncTime - writeTime;
mSyncTimes.add((int) fsyncDuration);
mNumSync++;
if (DEBUG || mNumSync % 1024 == 0 || fsyncDuration > MAX_FSYNC_DURATION_MILLIS) {
    mSyncTimes.log(TAG, "Time required to fsync " + mFile + ": ");
}
```

超过 256ms 的 fsync 会触发 logcat 警告。在生产环境中，I/O 繁忙时单次 fsync 可达数百毫秒甚至数秒，直接导致 ANR。

[已验证: AOSP android-17.0.0_r1, SharedPreferencesImpl.java#writeToFile]

## 4. ANR 触发链 3：apply() + QueuedWork.waitToFinish()

### 4.1 apply() 的「假异步」

`apply()` 的设计意图是异步写入，但实际存在隐式同步点：

```java
// EditorImpl.apply()
public void apply() {
    final MemoryCommitResult mcr = commitToMemory();

    final Runnable awaitCommit = new Runnable() {
        @Override
        public void run() {
            try {
                mcr.writtenToDiskLatch.await();  // 等待磁盘写入完成
            } catch (InterruptedException ignored) {
            }
        }
    };

    QueuedWork.addFinisher(awaitCommit);          // 注册到全局 finisher 队列

    Runnable postWriteRunnable = new Runnable() {
        @Override
        public void run() {
            awaitCommit.run();
            QueuedWork.removeFinisher(awaitCommit);  // 写入完成后移除
        }
    };

    SharedPreferencesImpl.this.enqueueDiskWrite(mcr, postWriteRunnable);
    notifyListeners(mcr);
}
```

`apply()` 本身立即返回，但 `awaitCommit` 被添加到 `QueuedWork.sFinishers`。这个 Runnable 的作用就是等待磁盘写入完成（`writtenToDiskLatch.await()`）。

### 4.2 QueuedWork.waitToFinish() 的强制同步

系统在组件生命周期切换时会调用 `QueuedWork.waitToFinish()`：

```java
// frameworks/base/core/java/android/app/QueuedWork.java @ android-17.0.0_r1

/** If a waitToFinish() takes more than 512 ms, warn */
private static final long MAX_WAIT_TIME_MILLIS = 512;

public static void waitToFinish() {
    long startTime = System.currentTimeMillis();
    boolean hadMessages = false;

    synchronized (sLock) {
        // 取消延迟消息
        handlerRemoveMessages(QueuedWorkHandler.MSG_RUN);
        // 禁止延迟新工作
        sCanDelay = false;
    }

    StrictMode.ThreadPolicy oldPolicy = StrictMode.allowThreadDiskWrites();
    try {
        processPendingWork();   // 先处理所有 pending 的磁盘写入
    } finally {
        StrictMode.setThreadPolicy(oldPolicy);
    }

    try {
        while (true) {
            Runnable finisher;
            synchronized (sLock) {
                finisher = sFinishers.poll();
            }
            if (finisher == null) break;
            finisher.run();     // 逐个执行 finisher（即 awaitCommit）
        }
    } finally {
        sCanDelay = true;
    }

    // 超过 512ms 输出告警
    synchronized (sLock) {
        long waitTime = System.currentTimeMillis() - startTime;
        if (waitTime > 0 || hadMessages) {
            mWaitTimes.add(Long.valueOf(waitTime).intValue());
            mNumWaits++;
            if (DEBUG || mNumWaits % 1024 == 0 || waitTime > MAX_WAIT_TIME_MILLIS) {
                mWaitTimes.log(LOG_TAG, "waited: ");
            }
        }
    }
}
```

关键流程：先 `processPendingWork()` 在当前线程（主线程）上执行所有排队的磁盘写入 Runnable，然后 drain `sFinishers` 列表（每个 finisher 内部等待写入 latch）。

调用 `waitToFinish()` 的时机（android-17.0.0_r1）：
- **ActivityThread.handleStopActivity()**：`if (!r.isPreHoneycomb()) QueuedWork.waitToFinish()`
- **ActivityThread.handlePauseActivity()**：`if (r.isPreHoneycomb()) QueuedWork.waitToFinish()`（仅 pre-Honeycomb）
- **ActivityThread.handleServiceArgs()**：Service 的 onStartCommand 返回后
- **ActivityThread.handleStopService()**：Service onDestroy 后
- **BroadcastReceiver**：`PendingResult.finish()` 时，若 `QueuedWork.hasPendingWork()` 为真，将 sendFinished 追加到队尾

### 4.3 apply() ANR 的典型场景

```
主线程：Activity.onPause() / onStop()
  └→ QueuedWork.waitToFinish()
       ├→ processPendingWork()
       │    └→ writeToDiskRunnable.run()  ← 主线程执行磁盘写入
       │         └→ writeToFile()
       │              └→ FileUtils.sync(str)  ← fsync，可能阻塞数百 ms
       └→ finisher.run()
            └→ writtenToDiskLatch.await()    ← 通常此时已写入完成，快速返回
```

ANR 触发条件：
1. `apply()` 被频繁调用，QueuedWork 队列积压多个写入任务
2. 每个写入任务的 fsync 耗时较长（I/O 繁忙、文件较大）
3. 组件生命周期切换时 `waitToFinish()` 需要串行处理所有积压任务
4. 总耗时超过 ANR 阈值（前台 5s，后台 200s in Android 17）

⚠️ **关键细节**：即使 `apply()` 的异步线程已经开始处理写入，`waitToFinish()` 的 `processPendingWork()` 也会在调用线程（主线程）上**重新执行**未完成的写入 Runnable。这是因为 `processPendingWork()` 会从 `sWork` 队列中 poll 出所有任务并在当前线程执行。

[已验证: AOSP android-17.0.0_r1, QueuedWork.java#waitToFinish, ActivityThread.java]

## 5. writeToFile() 的原子性协议与失败恢复

### 5.1 正常写入流程

```java
@GuardedBy("mWritingToDiskLock")
private void writeToFile(MemoryCommitResult mcr, boolean isFromSyncCommit) {
    // 1. 检查是否需要写入（代际号比较）
    if (mDiskStateGeneration < mcr.memoryStateGeneration) {
        if (isFromSyncCommit) {
            needsWrite = true;
        } else {
            // 异步写入：只保留最新代际
            if (mCurrentMemoryStateGeneration == mcr.memoryStateGeneration) {
                needsWrite = true;
            }
        }
    }
    if (!needsWrite) { mcr.setDiskWriteResult(false, true); return; }

    // 2. 将当前文件重命名为备份
    if (!backupFileExists) {
        mFile.renameTo(mBackupFile);
    } else {
        mFile.delete();  // 上次有残留备份，直接删原文件
    }

    // 3. 写入新文件
    FileOutputStream str = createFileOutputStream(mFile);
    XmlUtils.writeMapXml(mcr.mapToWriteToDisk, str);
    FileUtils.sync(str);     // fsync — 最耗时的单步操作
    str.close();
    ContextImpl.setFilePermissionsFromMode(mFile.getPath(), mMode, 0);

    // 4. 更新文件元数据缓存
    StructStat stat = Os.stat(mFile.getPath());
    mStatTimestamp = stat.st_mtim;
    mStatSize = stat.st_size;

    // 5. 删除备份文件，写入成功
    mBackupFile.delete();
    mDiskStateGeneration = mcr.memoryStateGeneration;
    mcr.setDiskWriteResult(true, true);
}
```

### 5.2 异步写入的代际优化

对 `apply()` 触发的异步写入，有一个关键优化：

```java
// 只在 mCurrentMemoryStateGeneration == mcr.memoryStateGeneration 时才写入
if (mCurrentMemoryStateGeneration == mcr.memoryStateGeneration) {
    needsWrite = true;
}
```

这意味着如果在异步写入队列中排了多个 `apply()`，只有最后一个代际号等于当前内存代际号的写入会被实际执行，中间的写入被跳过（`setDiskWriteResult(false, true)` 直接返回成功）。这是 SPI 的「合并写入」优化。

### 5.3 失败恢复

如果 `writeToFile()` 在任何步骤抛出异常（`XmlPullParserException`、`IOException`）：
1. 删除可能已部分写入的 `mFile`
2. `mcr.setDiskWriteResult(false, false)` — 标记写入失败
3. 下次启动时 `loadFromDisk()` 发现 `mBackupFile` 存在 → 恢复备份

这个协议保证了「要么完全写入新数据，要么保留旧数据」，但**不保证写入不丢失** — 如果 `apply()` 返回后进程崩溃，未完成落盘的修改会丢失。

[已验证: AOSP android-17.0.0_r1, SharedPreferencesImpl.java#writeToFile]

## 6. commitToMemory() 的 Clone-on-Write 机制

`commitToMemory()` 是连接 Editor 和 SPI 内存状态的核心方法：

```java
private MemoryCommitResult commitToMemory() {
    synchronized (SharedPreferencesImpl.this.mLock) {
        // 如果有在途写入，克隆 mMap（Copy-on-Write）
        if (mDiskWritesInFlight > 0) {
            mMap = new HashMap<String, Object>(mMap);  // 浅拷贝
        }
        mapToWriteToDisk = mMap;
        mDiskWritesInFlight++;

        synchronized (mEditorLock) {
            // 将 Editor.mModified 中的变更应用到 mapToWriteToDisk
            if (mClear) {
                mapToWriteToDisk.clear();
            }
            for (Map.Entry<String, Object> e : mModified.entrySet()) {
                String k = e.getKey();
                Object v = e.getValue();
                if (v == this || v == null) {
                    mapToWriteToDisk.remove(k);  // remove 操作
                } else {
                    mapToWriteToDisk.put(k, v);  // put 操作
                }
            }
            mModified.clear();

            if (changesMade) {
                mCurrentMemoryStateGeneration++;
            }
            memoryStateGeneration = mCurrentMemoryStateGeneration;
        }
    }
    return new MemoryCommitResult(..., mapToWriteToDisk);
}
```

关键点：
- **`mDiskWritesInFlight > 0` 时执行浅拷贝**：如果上次写入尚未完成，当前 mMap 正在被写入线程使用，必须克隆一份再修改，避免并发修改异常
- **`mDiskWritesInFlight++` 在释放 `mEditorLock` 前递增**：确保 enqueueDiskWrite 能正确判断是否有多个写入在途
- **`mCurrentMemoryStateGeneration++` 仅在实际变更时递增**：如果 Editor 中的值与现有值相同（`existingValue.equals(v)`），不会递增，避免无意义的磁盘写入

[已验证: AOSP android-17.0.0_r1, SharedPreferencesImpl.java#commitToMemory]

## 7. Android 17 中的监控指标埋点

### 7.1 fsync 耗时直方图

SPI 内置了 fsync 耗时的指数桶直方图：

```java
@GuardedBy("mWritingToDiskLock")
private final ExponentiallyBucketedHistogram mSyncTimes =
    new ExponentiallyBucketedHistogram(16);
private int mNumSync = 0;
```

每 1024 次写入或超过 256ms 时输出日志：
```
SharedPreferencesImpl: Time required to fsync /data/.../shared_prefs/config.xml: { ... }
```

### 7.2 QueuedWork 等待耗时直方图

```java
@GuardedBy("sLock")
private final static ExponentiallyBucketedHistogram mWaitTimes =
    new ExponentiallyBucketedHistogram(16);
private static int mNumWaits = 0;
```

每 1024 次或超过 512ms 时输出：
```
QueuedWork: waited: { ... }
```

这些日志是生产环境中定位 SP ANR 的一手信号。在 logcat 中搜索 `SharedPreferencesImpl` + `fsync` 或 `QueuedWork` + `waited` 可以快速锁定问题。

### 7.3 Perfetto 中的 SP ANR 确认方法

在 Perfetto trace 中确认 SP ANR 的关键步骤：

1. **搜索主线程栈**：查找 `SharedPreferencesImpl.writeToFile` 或 `QueuedWork.waitToFinish` 帧
2. **检查 "SharedPreferences" 线程**：`sLoadExecutor` 的线程名为 `"SharedPreferences"`（注意不是 `"SharedPreferencesImpl-load"`）
3. **观察 fsync ftrace 事件**：`file_sync` / `ext4_sync_file` / `f2fs_sync_file` 的持续时间
4. **检查 "queued-work-looper" 线程**：QueuedWork 的 HandlerThread 名称
5. **关联组件生命周期**：在 `handleStopActivity` / `handleStopService` 附近寻找 `waitToFinish` 调用

⚠️ 旧版文档中 `SharedPreferencesImpl-load` 线程名在 android-17.0.0_r1 中已不存在。搜索旧线程名会漏检。

| 触发链 | API | 阻塞位置 | 典型耗时 | ANR 阈值 |
|--------|-----|----------|----------|----------|
| 首次加载 | getString/edit | `mLock.wait()` (awaitLoadedLocked) | 50ms-2s (取决于文件大小) | 前台 5s |
| commit() | commit() | 主线程 writeToFile + fsync | 10ms-500ms+ | 前台 5s |
| apply() 生命周期 | apply() | waitToFinish → processPendingWork | 100ms-数秒 (取决于积压量) | 前台 5s / 后台 200s |
| BroadcastReceiver | apply() | PendingResult.finish 等待 QueuedWork | 变化大 | 前台 10s (broadcast) |

### 各触发链的规避策略

**首次加载阻塞**：
- 避免在主线程首次访问大型 SP 文件
- 预加载：在子线程提前调用 `getSharedPreferences()` 触发异步加载
- 拆分大型 SP 文件为多个小文件
- 迁移到 DataStore（异步读取 API 设计从源头避免此问题）

**commit() 同步落盘**：
- 主线程绝对禁止 `commit()`，全部替换为 `apply()`
- 使用 StrictMode 检测 `commit()` 调用：`detectCustomSlowCalls()` 或 `detectDiskWrites()`

**apply() + 生命周期 ANR**：
- 控制 `apply()` 的调用频率，避免短时间内大量写入
- 关注 SP 文件大小，XML 序列化和 fsync 的成本与文件大小正相关
- 在 `onPause()` / `onStop()` 前确保已有足够时间完成异步写入
- 高频写入场景迁移到 DataStore 或 MMKV

**BroadcastReceiver**：
- `onReceive()` 中避免 `apply()`
- 如必须写入，使用 `goAsync()` 并在子线程完成写入后再 `finish()`

> 详见 6.5 节 for SharedPreferences/DataStore 的完整优化策略和 DataStore 迁移路径。
