# 6.1 Android 17 上的 DataStore 1.2.1 多进程一致性机制

> 平台边界为 Android 17 / API 37 / `android-17.0.0_r1`；Jetpack 源码边界为稳定版 AndroidX DataStore 1.2.1。DataStore 随应用依赖发布，多进程实现不属于 Android 17 framework 新增功能。官方文档说明多进程支持从 DataStore 1.1.0 开始。

## 要点

### 🔹 锚点 1：DataStore 机制架构
#### 基础架构演进
Android DataStore 作为 SharedPreferences 的现代化替代方案，在 Android 17 中实现了更高效的多进程 IPC 机制。其核心架构基于以下组件：

- **ProtoDataStore**：基于 Protocol Buffers 的类型安全实现
- **PreferenceDataStore**：传统键值对的现代化封装
- **MultiProcessDataStoreFactory**：多进程环境下的工厂模式实现
- **FileChannel-based IPC**：通过 FileChannel 实现跨进程数据同步

#### 与 SharedPreferences 的本质区别
与传统 SharedPreferences 不同，DataStore 在 Android 17 中采用了：
- 异步操作模型（suspend 函数）
- 流式数据观察（Flow<Data<T>>）
- 事务性写入保证
- 自动版本迁移机制

### 🔹 锚点 2：Multi-process 作用原理
#### 多进程同步机制
DataStore 在多进程环境下的同步基于以下机制：

1. **文件锁（FileLock）**：使用 `FileChannel.lock()` 实现进程间的读写锁
2. **观察者模式**：通过 `Flow` 实现跨进程数据变更通知
3. **原子性写入**：使用临时文件 + 原子重命名保证数据一致性
4. **缓存策略**：进程内缓存减少重复文件读取

#### 进程间通信路径
```
Process A (Writer) → FileChannel.lock() → Temporary File → Atomic Rename → Process B (Reader)
                                      ↓
                               Flow<Data<T>> Notification
```

### 🔹 锚点 3：IPC 触发条件
#### 触发时机分析
DataStore 的 IPC 机制在以下条件下触发：

1. **首次访问**：进程首次创建 DataStore 实例时
2. **数据变更**：调用 `edit()` 或 `updateData()` 时
3. **观察订阅**：首个 `collect()` 调用时建立监听
4. **进程竞争**：多进程同时尝试修改数据时

#### 性能优化策略
Android 17 中引入的优化包括：
- **延迟初始化**：DataStore 实例延迟创建以减少启动开销
- **批量操作**：支持批量数据更新减少 IPC 调用次数
- **智能缓存**：基于使用模式的智能缓存失效策略

### 🔹 锚点 4：FileChannel 源码实现
#### 核心实现细节
基于 Android 17 源码分析，DataStore 的 FileChannel 实现包含：

```kotlin
// 伪代码展示核心实现逻辑
class ProtoDataStore<T> {
    private val fileChannel = RandomAccessAccessFile(file, "rw").channel
    
    suspend fun edit(update: suspend (T) -> T): T {
        val lock = fileChannel.lock() // 获取文件锁
        try {
            val current = readData()
            val updated = update(current)
            writeData(updated) // 原子写入
            return updated
        } finally {
            lock.release() // 释放锁
        }
    }
}
```

#### 错误处理机制
- **锁超时**：设置合理的锁等待超时避免死锁
- **异常恢复**：写入失败时回滚到上一个一致状态
- **进程崩溃**：通过文件校验和检测损坏数据

### 🔹 锚点 5：性能影响分析

|---------|-----------------|----------|----------|

## 源码审阅结论

DataStore 1.2.1 的 Android 多进程实现不使用 Binder，也没有一个常驻的“DataStore 服务进程”。同一应用的各进程各自持有 DataStore 实例，通过同一组文件完成协调：

| 文件或机制 | 用途 | 不能替代的能力 |
|---|---|---|
| 数据文件 | 保存序列化后的完整 `T` | 不负责互斥与变更通知 |
| `<data>.lock` | `FileChannel` 跨进程读写协调 | 不传输数据内容 |
| `<data>.version` | 4 字节共享原子计数器，判断进程内缓存是否过期 | 不保存业务数据 |
| `<data>.tmp` | 写入、`fd.sync()` 后替换正式文件 | 不提供历史版本回滚 |
| `FileObserver(MOVED_TO)` | 正式文件被替换后通知其他进程重新检查 | 不是事务日志，也不保证每个中间状态都被观察 |
| 进程内 `Mutex` 与 write actor | 串行化本进程操作 | 不能独自协调其他进程 |

因此，把多进程实现概括成“FileChannel 文件锁”只说对了一部分。文件锁负责互斥，共享计数器负责低成本版本判断，FileObserver 负责唤醒活跃订阅者，临时文件与替换操作负责内容更新。

## 1. 先满足四条使用约束

官方文档和 `MultiProcessDataStoreFactory` 源码给出了四条必须遵守的约束：

1. 同一进程内，同一个 canonical file 只能有一个活跃 DataStore 实例；
2. 所有访问同一文件的进程都要使用 `MultiProcessDataStoreFactory`，不能混用 single-process 与 multi-process DataStore；
3. `produceFile` 每次必须返回同一路径，而且各进程必须指向同一文件；
4. `DataStore<T>` 的 `T` 必须保持不可变。transform 返回之后再修改同一对象，会破坏缓存 hash 与一致性检查。

“每个进程一个实例”不等于创建多个文件。Android 的进程各有独立堆，单例只在本进程生效；各进程中的单例要指向同一个应用私有文件。

下面的例子用于展示 factory 的正确边界：依赖注入容器应在每个进程只创建一次 `SettingsStore`。

```kotlin
class SettingsStore(
    context: Context,
    scope: CoroutineScope,
) {
    val dataStore: DataStore<Settings> =
        MultiProcessDataStoreFactory.create(
            serializer = SettingsSerializer,
            scope = scope,
            produceFile = {
                File(context.applicationContext.filesDir, "settings.pb")
            },
        )
}
```

这里的 `scope` 应由进程级组件管理，通常包含 `SupervisorJob` 与 `Dispatchers.IO`，并在不再使用 DataStore 时取消。不要在每次读取时重新创建 scope 和 factory 实例。

DataStore 1.2.1 的 typed artifact 是 `androidx.datastore:datastore:1.2.1`；Preferences 版本使用 `androidx.datastore:datastore-preferences:1.2.1`。Android 平台 API 37 不会自动替应用升级 Jetpack 依赖，最终运行版本以 APK/AAB 中打包的依赖为准。

## 2. `.lock`：写独占，读尝试共享锁

`MultiProcessCoordinator.lock()` 先取得进程内 `Mutex`，再用 `FileOutputStream(<data>.lock).channel.lock(..., shared=false)` 获取跨进程独占锁。以下操作会使用这条路径：

- `updateData()` 的读—改—写事务；
- 需要串行完成的 migration；
- corruption handler 确认文件仍损坏并替换内容；
- 收到跨进程通知后要求稳定快照的重新读取。

Android 某些文件系统/内核组合可能让 `FileChannel.lock()` 抛出 “Resource deadlock would occur”。1.2.1 源码对此以 10ms 起步做指数退避，退避值最多增长到 60 秒，随后再次调用阻塞式 `lock()`。这不是“60 秒自动取消操作”，也不是面向业务的可配置超时。

读路径使用 `tryLock(..., shared=true)`。如果进程内 mutex 或共享文件锁暂时拿不到，block 仍会执行，并收到 `locked=false`。`DataStoreImpl` 可以读取当前正式文件，但不会用这次无锁结果更新稳定的进程内缓存；之后由版本与通知机制再次校准。

官方对多进程 DataStore 的公开语义是：

- 读取只返回已持久化的数据；
- 保证 read-after-write consistency；
- 写操作串行；
- 读不被写操作阻塞。

最终一条依赖“读可以在拿不到共享锁时读取正式文件”的设计。通知驱动的缓存刷新可以等待写锁结束，但普通读没有必要为了正在生成的 `.tmp` 文件停住。

## 3. `.version`：共享计数器只回答“缓存是否过期”

`MultiProcessCoordinator` 为数据文件创建 `<data>.version`。`SharedCounter.android.kt` 通过 JNI 加载 `libdatastore_shared_counter.so`，把文件映射成一个跨进程共享计数器。

下面的 C++ 结构用于说明这个计数器的内存语义，代码要点来自 DataStore 的 `shared_counter.cc`：

```cpp
constexpr int NUM_BYTES = 4;
static_assert(sizeof(std::atomic<uint32_t>) == NUM_BYTES);
static_assert(std::atomic<uint32_t>::is_always_lock_free);

void* address = mmap(
        nullptr,
        NUM_BYTES,
        PROT_READ | PROT_WRITE,
        MAP_SHARED | MAP_POPULATE,
        fd,
        0);
```

文件先被截断为 4 字节，再以 `MAP_SHARED` 映射；各进程对同一映射文件执行原子 load 或 `fetch_add(1)`。DataStore 1.2.1 的 Android AAR 已为 arm64-v8a、armeabi-v7a、x86 和 x86_64 打包该 native library，应用不需要自行编译 JNI。

每次准备读取时，`DataStoreImpl` 比较进程内缓存版本和共享计数器：

- 版本相同，直接复用缓存；
- 版本不同，读取正式文件，并在取得合适锁时更新缓存；
- 写事务在写文件前递增版本，避免进程在“文件已替换、版本尚未递增”的崩溃窗口里永久误认为旧缓存有效。

计数器提前递增意味着崩溃时版本可能领先数据文件。这个状态是安全侧的额外重读信号，不代表内容已经提交。业务数据始终来自数据文件，不能把 `.version` 当作提交记录或恢复日志。

在 Robolectric 等非 Dalvik 主机环境，源码使用进程内 `AtomicInteger` 作为 shadow 实现。这只能支持主机测试运行，不能验证真实跨进程一致性。多进程测试应在 Android 设备或模拟器上执行。

## 4. `.tmp`：完整序列化、sync、替换

DataStore 不支持局部更新。`updateData()` 得到完整不可变对象，serializer 把完整对象写入 `<data>.tmp`，随后调用 `FileDescriptor.sync()`，最终用同目录 move 替换正式数据文件。

下面的时序用于解释一次成功写入涉及哪些成本：

```text
write actor
  -> coordinator.lock()                 // <data>.lock 独占锁
  -> 读取正式文件并反序列化
  -> 在调用方 coroutine context 执行 transform
  -> 检查旧对象 hash 未被外部修改
  -> SharedCounter.incrementAndGet()    // <data>.version
  -> serializer.writeTo(<data>.tmp)
  -> fd.sync()
  -> move(<data>.tmp, data file)
  -> 释放独占锁
```

transform 在跨进程独占锁范围内执行。它应保持短小、确定且无副作用；不要在 transform 中访问网络、等待另一把业务锁或执行长时间计算，否则其他进程的写事务都会排队。

“事务性更新”指 transform 看到一个稳定旧值，多个 writer 的读—改—写由独占锁串行化，正式文件通过替换切换到新内容。它不等于数据库事务：DataStore 没有多文件原子提交、查询、部分字段写入、外键或历史版本。需要这些能力时应使用 Room。

还有一条持久性边界需要保留：1.2.1 的 `FileWriteScope` 对临时文件执行 `fd.sync()`，源码同时留有目录 fsync 的 TODO。极端掉电或文件系统故障下，不应把 DataStore 描述为拥有数据库级 WAL 恢复或“永不回退到旧状态”。

## 5. `FileObserver`：通知活跃 collector 重新读取

`MulticastFileObserver` 监听数据文件父目录的 `MOVED_TO`，并只在事件文件名等于目标数据文件时发送 `Unit`。这与 `.tmp` 替换正式文件的写入方式配套。

同一进程中，多个 DataStore 观察需求共享一个按 canonical parent path 注册的 FileObserver，规避 Android 上重复注册 observer 的已知问题。末尾一个 delegate 移除后，observer 才停止。

`DataStoreImpl` 只在 `data` Flow 至少有一个下游 collector 时启动 `updateNotifications` 收集任务；collector 数量回到零后取消该 job。收到通知后，它获取 coordinator lock，读取稳定数据并刷新缓存。

可以把跨进程传播理解为：

```text
Process A: updateData()
  -> .tmp sync + move
  -> parent directory emits MOVED_TO

Process B: active data Flow collector
  -> FileObserver emits Unit
  -> compare shared version
  -> acquire coordinator lock
  -> read data file
  -> update in-process Flow/cache
```

这段时序说明，Flow 是进程内响应式 API，跨进程唤醒来自 FileObserver。没有 Binder callback，也没有把 `Flow` 对象跨进程传递。通知可以被 `conflate()` 合并；collector 应关心最新完整状态，不应把每次发射当成不可丢失的事件日志。

## 6. `updateData()` 的返回语义与失败边界

`updateData()` 把请求交给进程内 write actor，并等待 `CompletableDeferred`。只有对应更新处理结束后，调用才返回；serializer、文件锁、sync 或 move 抛出的异常会向调用方传播。

这比 `SharedPreferences.apply()` 更容易处理错误，但“suspend API”不等于没有延迟：

- 调用方协程仍会挂起到写事务完成；
- 文件锁竞争、完整对象序列化和 fsync 都可能形成长尾；
- `runBlocking`、错误的同步桥接或在主线程等待 Future，仍能把异步 API 变成 UI 阻塞；
- 默认 factory scope 使用 `Dispatchers.IO + SupervisorJob()`，传入自定义 scope 后，调度责任由应用负责。

`ReplaceFileCorruptionHandler` 只处理 serializer 抛出的 `CorruptionException`。它会在独占锁内重新确认文件仍损坏，再用 handler 提供的新值替换；普通 `IOException`、权限问题、空间不足和任意业务异常不会被自动改成默认值。

## 7. 性能结论必须来自具体负载

DataStore 1.2.1 源码没有提供“Android 17 比 Android 16 快 30%”之类的平台保证，也没有通用的 SharedPreferences 对比数字。两者的成本模型不同：

| 维度 | SharedPreferences | Multi-process DataStore |
|---|---|---|
| 首次读取 | 后台解析，但同步 getter 可能等待 | 首次 collect/currentData 挂起读取 |
| 写入格式 | 整个 XML map | 整个 `T` |
| 并发更新 | 进程内锁；不支持多进程一致性 | write actor + 跨进程文件锁 |
| 持久化 | `commit()` 或 `apply()` + `QueuedWork` | 临时文件、sync、替换 |
| 跨进程失效 | 无可靠支持 | shared counter + FileObserver |
| 错误返回 | `apply()` 无结果；`commit()` 只有 boolean | 异常通过 suspend 调用传播 |

Multi-process DataStore 为一致性增加了文件锁、版本文件、mmap 和 observer 成本。它适合少量配置或小型状态，不适合高频事件流、大列表、分片查询或大对象局部更新。一次 transform 修改一个字段，文件层仍要重写完整对象。

评测时至少记录：

- DataStore 版本、Android build、设备和文件系统；
- 数据文件大小、serializer 类型、字段数量；
- 单进程或多进程、writer 数量、更新频率；
- 冷启动首次读取、稳定缓存读取、无竞争写、锁竞争写；
- 平均值以外的 P95/P99、失败率和 fsync 长尾。

没有这些条件，固定毫秒值和百分比没有迁移决策价值。

## 8. 排查多进程问题

### 8.1 先确认实例与路径

在每个进程打印以下信息：

- `Application.getProcessName()`；
- `produceFile().canonicalPath`；
- DataStore factory 类型与库版本；
- 实例创建次数和 scope 生命周期。

同一进程同一路径出现两个活跃 `FileStorage` connection 时，源码会抛出 `IllegalStateException`。不同进程路径不一致则不会报这个错误，但它们读写的是两个数据源，看起来会像“通知丢失”。

### 8.2 查看协调文件，不要手工修改

下面的命令用于在 debuggable 应用中确认数据、锁和版本文件是否位于预期目录：

```bash
adb shell run-as com.example.app \
  ls -la files/settings.pb files/settings.pb.lock files/settings.pb.version
```

`.tmp` 通常只在写入窗口存在。不要删除、truncate 或替换 `.lock`、`.version` 和数据文件来“解除锁”；这会破坏正在运行的 DataStore 实例。需要做故障注入时，应使用隔离测试包和可恢复的测试数据。

### 8.3 用通用系统信号定位

AOSP 没有 `datastore_read`、`datastore_write`、`file_lock_acquire` 这些专属 ftrace 事件。可用的证据包括：

- Perfetto 的线程调度、应用自定义 trace、文件系统和 block I/O；
- userdebug/root 环境中的 `strace`，观察 `fcntl`、`mmap`、`fsync`、`rename/move` 和 inotify 相关 syscall；
- coroutine dump 或应用日志，确认请求停在 transform、serializer、文件锁还是 sync；
- 多进程 instrumentation test，显式覆盖并发 increment、进程死亡和 collector 切换。

设备内核提供哪些文件系统 tracepoint，应先从 tracefs 的 `available_events` 枚举。不要把另一个设备上存在的事件名写死成通用 Perfetto 配置。

## 9. 对历史大纲中错误说法的逐项修正

- **“Android 17 引入 DataStore 多进程优化”**：错误。DataStore 是独立发布的 Jetpack 库，多进程 API 从 1.1.0 提供；本章验证版本是 1.2.1。
- **“只靠 FileChannel.lock() 完成同步”**：不完整。还依赖共享版本计数器、FileObserver、临时文件替换和进程内状态机。
- **“锁有业务超时，超时自动回滚”**：错误。源码只对特定 deadlock errno 退避后重试；业务取消、失败处理和重试策略需要调用方设计。
- **“校验和自动修复任意损坏”**：错误。serializer 必须抛出 `CorruptionException`，并且应用要配置 corruption handler；普通 I/O 错误不会自动修复。
- **“DataStore 与 MemoryLimiter/ZRAM 集成并自动压缩”**：没有 1.2.1 源码或官方 API 支持。
- **“支持分片、增量字段写入、版本回滚和租户配额”**：没有。DataStore 保存完整对象，不提供这些数据库能力。
- **“Binder 事务上限影响 DataStore 批量写入”**：无关。多进程协调不经 Binder 传输业务对象。
- **“存在专属 DataStore ftrace 事件”**：没有对应 AOSP/AndroidX 实现。
- **固定性能提升与内存数字**：无可复现设备、版本、数据规模和测试脚本，全部删除出可引用结论。

## 10. 小结

DataStore 1.2.1 的多进程一致性由四条路径配合完成：

1. `.lock` 文件串行化写事务；
2. `.version` 的 4 字节 `MAP_SHARED` 原子计数器判断缓存新旧；
3. `.tmp` 写入、sync 与替换更新完整数据文件；
4. `FileObserver(MOVED_TO)` 通知其他进程的活跃 Flow collector 重新读取。

它提供跨进程串行写、read-after-write consistency 和响应式读取，但不具备数据库的局部更新、关系约束、事件日志或多文件事务。性能排查应围绕锁持有时间、完整序列化、fsync、文件替换和通知刷新分别取证，不能用“异步”两个字替代测量。
