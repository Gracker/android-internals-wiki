# 6.20 Linux 6.10 内存碎片整理优化实践

> **版本边界**：本节基于 `android-17.0.0_r1` / GKI `android17-6.18`（Linux 6.18 LTS），涵盖 Linux 6.10 引入的 proactive compaction 与 mTHP compaction 在 Android 设备上的实践调优。Linux 6.10 引入的所有内存管理改进均已包含在 Android 17 内核中 [已验证: AOSP kernel/common android17-6.18]。涉及 `mseal(2)`、Android 17 MemoryLimiter 等已在 §6.18 详述的特性，此处仅做交叉引用。

## 这一节补哪块缺口

§6.18 讲了 Linux 6.10 内存碎片整理的技术原理（mTHP compaction、folio 体系、mseal），§6.19 从源码级分析了 proactive compaction 的评分算法和调度机制，§4.10 讲了 compaction 与 direct reclaim、ZRAM 的性能边界。本节聚焦"怎么用"：在真实 Android 设备上如何调参、度量、排查碎片整理相关的性能问题。

## 1. Proactive Compaction 调优实践

### 1.1 核心参数：compaction_proactiveness

`/proc/sys/vm/compaction_proactiveness` 是 proactive compaction 的主控开关，取值 0-100，默认 20。

[已验证: AOSP android17-6.18, kernel/common mm/compaction.c `sysctl_compaction_proactiveness`]

| 取值范围 | 行为 | 适用场景 |
|----------|------|---------|
| 0 | 完全禁用 proactive compaction | 对延迟极度敏感的实时场景 |
| 1-19 | 低积极性，间隔较长 | 普通手机日常使用 |
| 20 (默认) | 平衡模式 | 大多数 Android 设备 |
| 21-49 | 较积极，整理频率提升 | 长期运行、大内存设备 |
| 50-100 | 高积极性，持续整理 | 服务器/数据库（Android 上极少使用） |

**调优原理**：proactive compaction 的后台守护线程 `kcompactd` 会定期检查每个 NUMA 节点的碎片评分（`fragmentation_score_node()`），当评分超过 `sysctl_compaction_proactiveness` 时触发整理。值越高，触发阈值越低，整理越频繁。

[已验证: §6.19 源码分析 — `should_proactive_compact_node()` 比较评分与 proactiveness 值]

**Android 设备推荐配置**：

```bash
# 查看当前值
cat /proc/sys/vm/compaction_proactiveness
# 默认输出: 20

# 低内存设备（≤4GB RAM）— 降低积极性，减少 CPU 开销
echo 15 > /proc/sys/vm/compaction_proactiveness

# 标准设备（6-12GB RAM）— 保持默认
# 无需修改

# 高内存设备 + 长期运行场景（如车机）
echo 30 > /proc/sys/vm/compaction_proactiveness
```

> ⚠️ Android 用户空间无法直接修改此参数（需 root 或 vendor init 脚本）。OEM 通常在 `init.*.rc` 中设定，开发者可通过 `adb shell` 在 eng/userdebug build 上调试。

### 1.2 与 Watermark 参数的协同

Compaction 不是孤立运作的——它和 watermark、min_free_kbytes 共同决定内存回收节奏：

```
# 相关参数链
/proc/sys/vm/min_free_kbytes        → 最小空闲页阈值
/proc/sys/vm/watermark_scale_factor  → watermark 缩放因子（默认 10）
/proc/sys/vm/compaction_proactiveness → proactive compaction 积极性
```

当空闲内存降到 watermark 以下时，kswapd 被唤醒做页面回收；当高阶页分配仍然失败时，触发 direct compaction。proactive compaction 的作用是在这些同步路径之前，提前整理好碎片，减少 direct compaction 的触发频率。

[交叉引用: §4.10 详解 watermark → kswapd → direct reclaim → direct compaction 的完整路径]

**协同调优建议**：

- 提高 `min_free_kbytes` 可让 kswapd 更早启动，间接减少 direct compaction 概率，但会减少可用内存
- 降低 `watermark_scale_factor` 会缩窄 kswapd 活跃区间，可能增加突发回收压力
- Android 17 的 LMKD v2 已整合 PSI（Pressure Stall Information）触发，与 compaction 形成三层防线

[已验证: AOSP system/memory/lmkd, lmkd.cpp PSI 集成]

## 2. mTHP 与 Compaction 协同优化

### 2.1 mTHP 对 Compaction 效率的影响

Linux 6.10 的关键改进是让 compaction 直接支持 mTHP（multi-size Transparent Huge Pages）。在 6.10 之前，高阶页分配失败后的 compaction 只产出 order-0 页面，需要多次 compaction pass 才能组装出目标阶数。6.10 允许 compaction 在页面释放路径中直接捕获该页面用于满足 mTHP 分配请求。

[交叉引用: §6.18 锚点 2 详解 mTHP compaction 直接捕获释放页面机制]

**对 Android 的实际影响**：
- Android 应用的匿名页（如 ART 堆、Native 堆）大量以 mTHP 形式映射
- mTHP compaction 效率直接影响应用启动和切换延迟
- 在 Android 17 的 GKI 内核中，mTHP 默认启用 order-0 到 order-4（4KB-64KB）

### 2.2 mTHP 配置与调试

```bash
# 查看 mTHP 配置
cat /sys/kernel/mm/transparent_hugepage/enabled
# 输出示例: [always] madvise never

# 查看各阶 mTHP 的启用状态（Linux 6.10+）
for order in 0 1 2 3 4; do
    echo "order-$order ($(echo "4 * 2^$order" | bc)KB): $(cat /sys/kernel/mm/transparent_hugepage/hugepages-${order}kB/enabled 2>/dev/null || echo 'N/A')"
done

# 推荐：匿名页 mTHP 使用 madvise 模式，让应用自主选择
echo madvise > /sys/kernel/mm/transparent_hugepage/enabled
```

**调试 mTHP compaction 效果**：

```bash
# 查看 THP 分配统计
cat /sys/kernel/mm/transparent_hugepage/khugepaged/full_scans
grep -E "thp_fault_alloc|thp_collapse_alloc|thp_file_alloc" /proc/vmstat
```

[已验证: kernel.org admin-guide/mm/transhuge]

### 2.3 mTHP order 选择策略

不同 workload 适合不同 mTHP order：

| 场景 | 推荐 mTHP order | 理由 |
|------|----------------|------|
| 普通应用匿名页 | order-2 (16KB) | 平衡 TLB 效率与 compaction 开销 |
| 数据库/大缓冲区 | order-4 (64KB) | 减少页表项数量，提升访问效率 |
| 游戏纹理/图形缓冲 | order-0 (4KB) | 避免大页 compaction 影响帧率 |
| 系统服务长期映射 | order-3 (32KB) | 减少 page fault 频率 |

> ⚠️ 以上推荐基于内核文档和社区经验 [已验证: kernel.org admin-guide/mm/transhuge]。实际最佳值取决于设备内存大小、CPU L1 TLB 容量和 workload 特征，应在目标设备上实测验证。

## 3. Android CachedAppOptimizer 的进程级 Compaction

### 3.1 进程级 Compaction 机制

Android 10+ 引入了 CachedAppOptimizer，对进入 cached 状态的后台进程执行进程级内存压缩（process compaction）。这与内核的 page-level compaction 不同——CachedAppOptimizer 通过 `/proc/<pid>/reclaim` 或 `process_madvise()` 将进程的文件页和匿名页分别压缩/回写。

[已验证: frameworks/base/services/core/java/com/android/server/am/CachedAppOptimizer.java]

```java
// CachedAppOptimizer.java 核心逻辑（简化）
@VisibleForTesting static final boolean DEFAULT_USE_COMPACTION = true;

// 压缩策略枚举
enum CompactProfile {
    NONE, SOME, ANON, FULL
}

// Android 17 新增：use_memcg_for_compaction flag
// 改用 memcg 路径进行 compaction 决策，更精确地控制单进程压缩范围
```

[交叉引用: §4.20 Android 17 Compaction + Freezer 对性能监控的影响]

### 3.2 进程级 Compaction 的性能影响

当应用进入 cached 状态时，CachedAppOptimizer 会：

1. **短延迟后触发 compaction**（默认延迟约 10 分钟，可配置 `ActivityManagerConstants.COMPACT_ACTION_DELAY`）
2. **分两步执行**：先 `COMPACT_ACTION_SOME`（轻量），再 `COMPACT_ACTION_FULL`（完整）
3. **冻结进程**（cgroup freezer），停止 CPU 调度

**可观测的性能特征**：
- RSS 下降：压缩后进程 RSS 显著降低（anon 页被 zRAM 压缩，file 页被回写丢弃）
- Perfetto 中可见 `rss_stat` 事件和 `mm_event` 计数器变化
- 恢复时延迟：应用从 cached 返回前台时，需要重新解压/重新加载，产生额外冷启动延迟

[已验证: §4.20 源码分析]

### 3.3 调优建议

```bash
# 查看 compaction 相关系统属性
getprop | grep compaction
# 典型输出:
# [ro.compact_action_1]: [1]  # COMPACT_ACTION_SOME
# [ro.compact_action_2]: [4]  # COMPACT_ACTION_FULL
# [ro.compact_throttled_duration]: [300]  # 节流时间（秒）

# 查看进程的 compaction 状态
dumpsys activity processes | grep -E "compacted|frozen|cached"
```

**禁用 compaction（仅调试）**：
```bash
# 在 userdebug build 上临时禁用进程级 compaction
setprop persist.sys.use_compaction false
# 需要 reboot 生效
```

> ⚠️ 禁用 CachedAppOptimizer compaction 会增加后台内存压力，可能导致 LMKD 更激进地杀进程。仅在 A/B 对比测试时临时使用。

## 4. 碎片度量与性能分析

### 4.1 核心度量指标

**（1）/proc/pagetypeinfo — 页块类型分布**

```bash
cat /proc/pagetypeinfo
# 输出示例（简化）：
# Page block order: 9
# Pages per block:  512
#
#  Node 0, zone  Normal, type  Unmovable  # Blocks of 512 pages
#  Node 0, zone  Normal, type  Movable
#  Node 0, zone  Normal, type  Reclaimable
#  ...
#  Free block types:
#  Node 0, zone  Normal, type   Unmovable   0B  ...  2MB
```

这个文件显示每个 zone 中不同迁移类型的页块分布。如果 Movable 页块大量分散在 Unmovable 区域之间，说明碎片化严重。

[已验证: kernel.org admin-guide/mm/concepts — "The buddy allocator works with page blocks"]

**（2）外部碎片指数：extfrag_index**

```bash
# 查看 fragmentation index（需要 debugfs）
cat /sys/kernel/debug/extfrag/extfrag_index 2>/dev/null || \
  cat /proc/sys/vm/extra_free_kbytes  # 间接指标
```

碎片指数范围 0-1000（0.000-1.000），值越高表示外部碎片越严重。extfrag_index > 0.5 意味着分配失败更多由碎片化而非内存不足导致。

[已验证: AOSP android-mainline, mm/compaction.c `extfrag_for_order()`; §6.19 锚点 1]

**（3）/proc/vmstat compaction 统计**

```bash
grep -E "compact|compact_stall|compact_fail|compact_success" /proc/vmstat
# 关键指标：
# compact_stall          — direct compaction 被触发的次数（同步路径）
# compact_fail           — compaction 未能产生所需阶数页的次数
# compact_success        — compaction 成功的次数
# compact_migrated       — 迁移的页面总数
# compact_isolated       — 隔离的页面总数
```

**解读方法**：
- `compact_stall` 持续增长 → 系统频繁在分配路径上同步等待 compaction
- `compact_fail / compact_stall` 比值高 → 碎片化已经严重影响分配成功率
- `compact_migrated / compact_isolated` 比值低 → compaction 效率差，很多被隔离的页无法迁移

[已验证: kernel.org Documentation/admin-guide/mm/ — compaction statistics]

### 4.2 使用 Perfetto 分析 Compaction

**（1）ftrace tracepoints**

Perfetto 可以捕获内核 compaction tracepoints：

```
# Perfetto config 相关 tracepoints
linux.ftrace {
  ftrace_events: "mm_compaction_begin"
  ftrace_events: "mm_compaction_end"
  ftrace_events: "mm_compaction_try_to_compact_pages"
  ftrace_events: "mm_compaction_suitable"
  ftrace_events: "mm_compaction_deferred"
  ftrace_events: "mm_compaction_migratepages"
}
```

[已验证: §4.10 详述 Perfetto 中 kswapd/kcompactd/mm_events 的联合分析方法]

**（2）分析策略**

在 Perfetto UI 中，按时间窗口对齐以下信号：

| 信号 | 轨道 | 含义 |
|------|------|------|
| `mm_compaction_begin/end` | linux.ftrace | compaction 执行区间 |
| `kcompactd0` 线程状态 | linux.sched | 后台 compaction 线程活跃时间 |
| `mm_vmscan_*` | linux.ftrace | 页面回收事件 |
| `rss_stat` | linux.system_stats | 进程 RSS 变化 |
| `psi.memory` | linux.system_stats | 内存压力停顿 |
| App 线程 D 状态 | linux.sched | 线程在内核态等待 |

**典型 compaction stall 场景在 Perfetto 中的表现**：
1. App 主线程进入 `D` (uninterruptible sleep) 状态
2. 同时间窗出现 `mm_compaction_begin` → `mm_compaction_end`
3. `compact_fail` 计数增加
4. 后续可能触发 `lmkd` 杀进程

[交叉引用: §4.10 "Perfetto / bugreport 中如何识别规整和回收"; §13.22 Perfetto v54 Data Explorer 分析]

### 4.3 使用 drop_caches 的注意事项

```bash
# 谨慎使用！仅限调试
echo 3 > /proc/sys/vm/drop_caches  # 释放 pagecache + slab
```

`drop_caches` 不会直接做 compaction，但它释放大量文件页后，可移动页的比例提升，后续 compaction 效果会变好。**生产环境严禁使用**，因为它会导致大量 cache miss 和 I/O 峰值。

[已验证: kernel.org admin-guide/sysctl/vm.txt — drop_caches 说明]

## 5. 场景化优化策略

### 5.1 低内存设备（≤4GB RAM）

低内存设备上，compaction 面临两难：内存碎片影响应用切换性能，但 compaction 本身消耗 CPU 和内存带宽。

**推荐策略**：
- `compaction_proactiveness`: 10-15（降低后台 compaction 频率）
- 依赖 LMKD 及时回收后台进程，而非过度 compaction
- zRAM 压缩比例适当调高（如 lz4 → zstd），减少匿名页占用的物理页
- mTHP 保持 order-2（16KB），避免高阶 compaction 开销

```bash
# 低内存设备推荐配置
echo 15 > /proc/sys/vm/compaction_proactiveness
echo madvise > /sys/kernel/mm/transparent_hugepage/enabled
```

### 5.2 游戏与高帧率场景

游戏前台运行时，每帧 8.3ms（120fps）的预算不允许 compaction 造成额外延迟。

**推荐策略**：
- 游戏前台时：降低 `compaction_proactiveness` 到 5-10
- 游戏切换到后台后：恢复默认值 20，利用空闲时段整理碎片
- OEM 可通过 `ActivityManager.setProcessState` 监听切换，动态调整

```bash
# 游戏前台时（临时调低）
echo 5 > /proc/sys/vm/compaction_proactiveness

# 游戏退出后恢复
echo 20 > /proc/sys/vm/compaction_proactiveness
```

> ⚠️ 动态调整 compaction_proactiveness 需要系统级权限。应用层开发者应通过 `WindowManager` 的 `onWindowFocusChanged` 回调间接感知前后台切换，无法直接控制内核参数。

### 5.3 车机与长期运行设备

车机设备运行时间长（可能数周不重启），内存碎片会逐步累积。

**推荐策略**：
- `compaction_proactiveness`: 25-35（更积极地整理）
- 配合 `ScheduledExecutor` 在车辆熄火/充电时段做深度整理
- 监控 `/proc/vmstat` 中 `compact_stall` 的增长率，作为碎片化趋势指标

### 5.4 相机启动场景

相机启动需要分配大量连续物理页（DMA 缓冲、图像处理 buffer），是 compaction 敏感的典型场景。

**关键排查点**：
- 相机启动时 `compact_stall` 是否急剧增加
- CMA 区域是否充足（`/proc/meminfo | grep Cma`）
- 是否有 `compact_fail` 表明碎片化已影响 DMA 分配

```bash
# 相机启动前后对比 compaction 统计
cat /proc/vmstat | grep compact > /tmp/before.txt
# 启动相机...
cat /proc/vmstat | grep compact > /tmp/after.txt
diff /tmp/before.txt /tmp/after.txt
```

[已验证: §4.10 "相机启动、游戏切场景"作为高阶页分配敏感场景]

## 6. 典型问题排查

### 6.1 Compaction Storm（整理风暴）

**症状**：`compact_stall` 在短时间内急剧增长，系统整体响应变慢，`top` 中 `kcompactd0` 占用大量 CPU。

**排查步骤**：
1. 确认是否有大量进程同时进入 cached 状态（触发批量 CachedAppOptimizer compaction）
2. 检查 `compaction_proactiveness` 是否被误设为高值
3. 检查是否有大量 mTHP 分配失败导致 fallback 到 order-0 + 后续 compaction
4. 使用 Perfetto 确认 compaction 是否与某个应用启动/退出时间重合

**缓解措施**：
```bash
# 临时降低 compaction 积极性
echo 10 > /proc/sys/vm/compaction_proactiveness

# 如果是 CachedAppOptimizer 导致的批量压缩
setprop persist.sys.use_compaction false  # 临时禁用，需 reboot
```

### 6.2 THP/mTHP 分配失败率过高

**症状**：`thp_fault_alloc` 增长缓慢，`compact_fail` 持续增长，应用启动延迟高于预期。

**排查步骤**：
```bash
# 查看 THP 分配统计
grep -E "thp_fault_alloc|thp_fault_fallback|thp_collapse_alloc|thp_collapse_alloc_failed" /proc/vmstat

# 如果 thp_fault_fallback / thp_fault_alloc 比值 > 0.3，说明 THP 分配成功率低
```

**缓解措施**：
- 确认 mTHP enabled 模式是否正确（`madvise` 或 `always`）
- 检查应用是否大量使用 `madvise(MADV_HUGEPAGE)` 但实际访问模式不适合大页
- 考虑降低目标 mTHP order（如 order-4 → order-2）

### 6.3 Direct Compaction 导致应用卡顿

**症状**：应用主线程偶发卡顿，Perfetto 显示线程 `D` 状态与 `mm_compaction_begin/end` 重叠。

**排查步骤**：
1. 在 Perfetto 中确认卡顿时间窗内是否有 `mm_compaction_begin` 事件
2. 检查同一时间窗是否有 `kswapd` 活跃、PSI memory stall
3. 确认应用是否在高阶页分配（如大 Bitmap、GPU buffer 映射）

**缓解措施**：
- 应用层：将大块内存分配移出主线程（后台线程预分配）
- 系统层：适当提高 `min_free_kbytes`，让 kswapd 更早启动，减少 direct compaction 概率
- 评估是否可用 `madvise(MADV_HUGEPAGE)` 预留大页，避免运行时 compaction

[交叉引用: §4.10 "App 侧能做什么，不能做什么"; §4.14 ART GC Region 碎片化策略]

## 7. 监控体系建议

### 7.1 持续监控指标

| 指标 | 数据源 | 告警阈值（建议） |
|------|--------|-----------------|
| compact_stall 增长率 | `/proc/vmstat` | >100/分钟 |
| compact_fail 比率 | `compact_fail / compact_stall` | >30% |
| extfrag_index（高阶） | `/sys/kernel/debug/extfrag/` | >0.7 |
| THP fallback 率 | `thp_fault_fallback / (thp_fault_alloc + thp_fault_fallback)` | >30% |
| PSI memory pressure | `/proc/pressure/memory` avg10 | >5% |
| kcompactd CPU 占比 | `/proc/<pid>/stat` (kcompactd0) | >3% |

### 7.2 定期检查清单

```
□ 检查 compact_stall 增长趋势（对比基线）
```

## 扩展

### 🔸 compaction 与 16KB Page Size 的交互

Android 15+ 支持 16KB page size。页变大后，order-0 就是 16KB，mTHP 的最小粒度也相应变大。这对 compaction 的影响包括：TLB miss 减少、但单次页面迁移开销增大、内部碎片率上升。具体量化影响需在目标设备上实测。

[交叉引用: §6.18 锚点 4 "对 Android 的实际意义"]

### 🔸 memcg-based compaction（Android 17 新特性）

Android 17 引入 `use_memcg_for_compaction` flag，将 compaction 决策从全局 zone 级别改为 memcg（cgroup）级别。这意味着 CachedAppOptimizer 可以更精确地对单个进程做 compaction，而不影响其他进程的内存布局。

```java
// frameworks/base/services/core/java/com/android/server/am/flags.aconfig
flag_value {
    name: "use_memcg_for_compaction"
    state: ENABLED
    permission: READ_ONLY
}
```

[交叉引用: §4.20 "Android 17 内存管理政策"; §16.07 系统启动优化中的 flag 分析]

### 🔸 folio 体系对 Compaction 的长期影响

Linux 内核正在从 page-based 管理全面迁移到 folio-based 管理。folio 是连续物理页的集合，本身就是一个"整理好"的单位。随着 folio 体系成熟，传统意义上的"碎片整理"需求可能会逐步降低——因为 folio 分配天然就是连续的。但这个演进仍在进行中，Android 17 的内核仍同时支持 page 和 folio 两种路径。

[待验证: folio 体系对 Android workload 的长期影响需要更多实测数据]

---

> **总结**：内存碎片整理优化是一个系统工程问题。内核参数（compaction_proactiveness、watermark）是基础调节手段，mTHP 配置影响碎片产生的速率，CachedAppOptimizer 控制进程级别的内存压缩。在 Android 17 上，这三层机制已形成完整的协同体系。实际调优时，应先通过 `/proc/vmstat` 和 Perfetto 定位瓶颈，再针对性调整参数，避免盲目调参引入新的性能问题。
