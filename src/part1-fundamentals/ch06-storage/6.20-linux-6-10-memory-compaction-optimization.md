# 6.20 Android 17 / Linux 6.18 内存规整调优与排障

> **源码锚点**
>
> - Android 平台：`android-17.0.0_r1`
> - Android common kernel：`android17-6.18-2026-06_r6`
>
> 本知识库统一采用上述版本核对源码，不表示所有 Android 17 设备都运行 Linux 6.18。量产设备的内核版本、最终配置、厂商补丁和权限策略仍以目标机为准。

6.19 解释 physical compaction 的机制，本章处理工程问题：怎样确认卡顿是否来自内存规整，怎样判断参数是否值得调整，以及怎样设计一次能被复核的实验。Proactive compaction 早于 Linux 6.10 已存在，不能把它写成 Linux 6.10 新增特性。

## 1. 先给问题起对名字

Linux 内存文档和 Android 源码都使用过 `compaction`，但它们指向的工作并不相同。

| 现象或组件 | 主要任务 | 能否直接产生高阶连续空闲块 |
|---|---|---|
| reclaim、kswapd、direct reclaim | 回收文件页，或把匿名页换出 | 不能保证 |
| `mm/compaction.c` | 迁移可移动页，重新排列物理页 | 可以，这是 physical compaction 的目标 |
| `CachedAppOptimizer` | 对 cached process 执行 `MADV_COLD`、`MADV_PAGEOUT` 或 memcg reclaim | 不能保证 |
| zram | 压缩换出的匿名页 | 不能 |
| LMKD | 在内存压力下选择并杀死进程 | 不能直接保证 |

高阶分配失败至少有两类原因：

1. 空闲页总量不足，回收后仍可能满足分配；
2. 空闲页数量看似足够，却无法组成目标 order 的连续块，属于外部碎片。

规整只改变物理页的排列，不会凭空增加空闲内存。诊断时如果把 reclaim、swap 和 physical compaction 统称为“内存压缩”，后面的指标和调参方向很容易出错。

## 2. 调参前记录设备边界

同一个 Android 17 平台版本可以搭配不同内核。GKI defconfig 也只是构建起点，产品的最终 `.config`、启动参数和厂商模块才决定设备暴露哪些能力。

下面这组命令用于记录实验设备的内核、基础页大小、关键配置和当前参数：

```bash
adb shell uname -a
adb shell getconf PAGESIZE
adb shell 'zcat /proc/config.gz 2>/dev/null | grep -E "CONFIG_(COMPACTION|MIGRATION|TRANSPARENT_HUGEPAGE|CMA|NUMA)="'
adb shell 'for f in compaction_proactiveness extfrag_threshold compact_unevictable_allowed min_free_kbytes watermark_scale_factor; do printf "%s=" "$f"; cat "/proc/sys/vm/$f" 2>/dev/null || echo unavailable; done'
adb shell cat /proc/cmdline
```

`/proc/config.gz`、部分 sysctl 和启动参数可能被 user build 隐藏。缺失表示“当前接口不可读”，不能据此断言对应功能没有编入内核。无法读取最终配置时，应从 OEM 构建产物补齐证据。

还要记录测试条件：可用 RAM、zram 配置、屏幕状态、温度、充电状态、前后台应用集合，以及触发高阶分配的工作负载。没有这些条件，两个版本的计数差异无法可靠比较。

## 3. 建立一次可重复的基线

### 3.1 `/proc/vmstat` 要看增量

Android 17 的 6.18 内核从 `mm/vmstat.c` 导出以下规整计数：

- `compact_stall`：分配线程进入 direct compaction 的次数；
- `compact_success`、`compact_fail`：direct compaction 返回成功或失败的次数；
- `compact_migrate_scanned`、`compact_free_scanned`：direct 路径扫描的页数；
- `compact_isolated`：隔离的页数；
- `compact_daemon_wake`：分配需求唤醒 `kcompactd` 的次数；
- `compact_daemon_migrate_scanned`、`compact_daemon_free_scanned`：daemon 路径扫描的页数。

下面的命令用于采集测试前后的累计值：

```bash
adb shell 'grep -E "^(compact_|compact_daemon_)" /proc/vmstat' > vmstat.before.txt
# 执行一次定义清楚的测试场景
adb shell 'grep -E "^(compact_|compact_daemon_)" /proc/vmstat' > vmstat.after.txt
```

文件保存在执行 `adb` 的主机上。分析时计算同名字段的 after-before；不要把开机以来的累计值直接归因给刚运行的应用。

`compact_fail / compact_stall` 也不是通用“碎片失败率”。一次 direct compaction 的返回结果受目标 order、watermark、迁移模式和分配上下文影响，必须与目标分配和 trace 同看。旧稿中的 `compact_migrated` 不是该内核导出的字段。

### 3.2 buddy、migratetype 和 fragmentation index

下面的接口从不同角度描述空闲页：

- `/proc/buddyinfo`：每个 zone、每个 order 的空闲块数量；
- `/proc/pagetypeinfo`：按 migratetype 划分的空闲块和 pageblock 信息；
- debugfs `extfrag_index`：按 zone、order 区分“内存不足”和“外部碎片”；
- debugfs `unusable_index`：某个 order 不能用于分配的空闲内存比例。

下面的命令用于在支持并授权这些接口的设备上采样：

```bash
adb shell cat /proc/buddyinfo
adb shell su 0 cat /proc/pagetypeinfo
adb shell su 0 cat /sys/kernel/debug/extfrag/extfrag_index
adb shell su 0 cat /sys/kernel/debug/extfrag/unusable_index
```

debugfs 通常需要 userdebug/eng 构建、root 权限和已挂载的 debugfs。`buddyinfo` 中高阶块少，只能说明当前快照下高阶余量有限；它无法单独证明外部碎片是分配失败的主因。

`extfrag_index` 接近 0，表示失败更偏向空闲内存不足；接近 1000，表示更偏向外部碎片；`-1` 表示只要 watermark 允许，当前分配可以成功。这里的 0—1000 与 proactive compaction 使用的 0—100 score 不是同一个量。

### 3.3 用 trace 确认时间关系

计数器能说明发生过多少工作，却不能回答某次主线程卡顿是否等待了 direct compaction。先从产品内核枚举事件，避免把 common kernel 中存在、产品中未开放的 tracepoint 写进配置。

下面的命令用于查找当前设备可用的规整事件：

```bash
adb shell su 0 sh -c 'cat /sys/kernel/tracing/available_events 2>/dev/null | grep "^compaction:"'
adb shell su 0 sh -c 'cat /sys/kernel/debug/tracing/available_events 2>/dev/null | grep "^compaction:"'
```

两个路径通常只有一个可用。`android17-6.18-2026-06_r6` 的 `include/trace/events/compaction.h` 定义了 `mm_compaction_begin`、`mm_compaction_end`、`mm_compaction_migratepages`、`mm_compaction_try_to_compact_pages` 和多组 `kcompactd` 事件。

下面的 Perfetto 文本配置用于采集规整事件和调度切换；应删掉设备未列出的事件：

```textproto
buffers: { size_kb: 32768 fill_policy: RING_BUFFER }
duration_ms: 15000
data_sources: {
  config {
    name: "linux.ftrace"
    ftrace_config {
      ftrace_events: "compaction/mm_compaction_begin"
      ftrace_events: "compaction/mm_compaction_end"
      ftrace_events: "compaction/mm_compaction_migratepages"
      ftrace_events: "compaction/mm_compaction_try_to_compact_pages"
      ftrace_events: "compaction/mm_compaction_wakeup_kcompactd"
      ftrace_events: "compaction/mm_compaction_kcompactd_wake"
      ftrace_events: "sched/sched_switch"
      ftrace_events: "sched/sched_wakeup"
    }
  }
}
```

在时间轴上同时查看调用线程、`kcompactd`、CPU 频率、reclaim、PSI、page fault 和 I/O。两个区间重叠只能建立相关性；还需要调用线程处于何种状态、事件参数和对照实验，才能判断规整是不是延迟来源。

## 4. 读懂三个可调参数

### 4.1 `vm.compaction_proactiveness`

`android17-6.18-2026-06_r6` 的默认值为 20，合法范围为 0—100。源码不是直接比较“score > proactiveness”，而是先计算两个 watermark：

- `low = 100 - proactiveness`
- `high = min(low + min(10, low / 2), 100)`

默认值 20 对应 low=80、high=90。node 的加权碎片分数高于 high 时，proactive 路径可以启动；规整会尝试让 zone 分数回到 low 附近。`kswapd` 正在运行时，`should_proactive_compact_node()` 会拒绝启动 proactive work。

写入任何非零值都会立即唤醒在线 node 的 `kcompactd`。因此，即便把 20 再写成 20，写入后的短窗口也不代表稳态行为。值为 0 只关闭 proactive compaction，direct compaction 和 allocation-driven `kcompactd` 仍然存在。

内核文档只给出语义和极值警告，没有按 4GB、8GB、游戏或车机给出推荐值。接近 100 可能产生过量后台扫描和迁移；固定写成 5、15 或 35 同样缺少跨设备依据。

### 4.2 `vm.extfrag_threshold`

该值范围为 0—1000，默认 500。高阶分配路径用它判断更应该尝试 compaction 还是 direct reclaim。`extfrag_index <= extfrag_threshold` 时，zone 不会因这一判断进入 compaction。

调低该值可能让更多高阶分配尝试规整，调高则可能更偏向回收。它与 proactive score 的计算和触发用途都不同，不能配成一组看起来相同的数字。

### 4.3 `vm.compact_unevictable_allowed`

值为 1 时，compaction 可以检查 unevictable LRU 上的页；普通内核默认 1，PREEMPT_RT 默认 0。迁移 mlocked page 可能使访问线程在 minor fault 上等待迁移完成。低延迟产品需要同时评估连续页收益和访问停顿，不能只看规整成功次数。

`min_free_kbytes`、`watermark_scale_factor` 会改变回收时机和空闲余量，但它们不是 compaction 的附属旋钮。修改这类全局参数还会影响内存可用量、kswapd 活动和 OOM 行为，应另设实验。

## 5. 一次合格的 A/B 调参

建议按以下顺序进行：

1. 明确目标：例如相机冷启动 P99、游戏资源加载的最大帧耗时，或持续运行 72 小时后的高阶分配长尾；
2. 固定设备、构建、温度和工作负载，至少重复多轮；
3. 采集默认配置下的 latency、vmstat delta、buddy/extfrag 快照和 trace；
4. 找到目标 order 与分配者，区分 THP、CMA、驱动、SLUB 或其他内核分配；
5. 每次只改一个参数，变化幅度从小开始；
6. 同时检查前台 P95/P99、CPU 时间、功耗、规整扫描量、分配失败、PSI、LMKD 和 OOM；
7. 恢复默认值并复测，排除温度、缓存和运行顺序造成的偏差。

下面的命令只用于 userdebug/eng 设备上的临时实验，并在修改前保存原值：

```bash
adb shell su 0 sh -c 'old=$(cat /proc/sys/vm/compaction_proactiveness); echo "old=$old"; echo 15 > /proc/sys/vm/compaction_proactiveness'
# 完成测试后，把上一步打印的 old 值明确写回
adb shell su 0 sh -c 'echo 20 > /proc/sys/vm/compaction_proactiveness'
```

示例中的 15 和 20 只是演示写法，不是产品建议。第二条命令必须替换为该设备先前记录的值；写回非零值本身也会触发一次 proactive 检查。

手工向 `/proc/sys/vm/compact_memory` 写 1 会规整所有 node。它适合受控诊断，例如比较规整前后目标 order 的可用块和一次分配延迟，不适合按分钟执行，也不应作为量产设备的定期“清理”任务。

## 6. THP 与 mTHP：按设备暴露的 size 分析

现代内核支持 multi-size THP（mTHP）：匿名内存可以使用大于 base page、小于传统 PMD-sized THP 的 2 的幂倍页面。mTHP 仍由 PTE 映射，可以减少 page fault 和 TLB 压力，同时把单次清零和分配成本控制在比 PMD THP 更小的范围。

Android 17 common kernel 的 arm64 GKI defconfig 启用了 `CONFIG_TRANSPARENT_HUGEPAGE=y` 和 `CONFIG_TRANSPARENT_HUGEPAGE_MADVISE=y`，但这不等于所有 mTHP size 在产品上默认启用。sysfs 目录按字节大小命名，例如 `hugepages-16kB`，不是按 order 命名。

下面的命令用于读取设备支持的 size、策略和逐 size 统计：

```bash
adb shell 'cat /sys/kernel/mm/transparent_hugepage/enabled 2>/dev/null; cat /sys/kernel/mm/transparent_hugepage/defrag 2>/dev/null'
adb shell 'for d in /sys/kernel/mm/transparent_hugepage/hugepages-*kB; do [ -d "$d" ] || continue; echo "[$d]"; cat "$d/enabled" 2>/dev/null; grep -H . "$d"/stats/* 2>/dev/null; done'
adb shell 'grep -E "^thp_" /proc/vmstat'
```

输出中的方括号表示当前策略。不同内核配置导出的统计项可能不同，应先枚举，再选择适用于该 size 的 `anon_fault_alloc`、fallback 等计数。不要假定 order-0 到 order-4 都存在。

在 4KB base page 设备上，order-2 是 16KB；在 16KB base page 设备上，order-2 是 64KB。分析文档应写实际 size，并同时记录 base page，避免只写 order 后被误用。

`madvise(MADV_HUGEPAGE)` 表示应用希望内核优先在该区域使用 THP。它不会预留物理大页，也不能保证未来分配避开 direct compaction。选择 `always`、`madvise`、`defer` 等策略前，应测量目标映射的访问密度、内存占用、fault latency、fallback 和规整成本。

Folio 是内核表示一组页的类型和接口，不会自动让离散物理页连续。引入 large folio 后，高阶分配和迁移策略可以更清楚地表达，但物理连续性仍由 buddy allocator、reclaim 和 compaction 等机制共同决定。

## 7. CachedAppOptimizer 不是物理内存规整

`android-17.0.0_r1` 的 `CachedAppOptimizer` 保留 `SOME`、`ANON`、`FULL` 等 `CompactProfile` 名称，这是 Android 历史命名。当前实现的目标是回收或降温 cached process 的页：

- JNI 路径通过 `process_madvise()` 对私有文件映射使用 `MADV_COLD`，对合适的私有匿名映射使用 `MADV_PAGEOUT`；
- memcg 路径可以向 cgroup v2 的 `memory.reclaim` 发起回收；
- Java 层还会根据进程状态、RSS、swap 余量、节流配置和请求来源决定执行、降级或跳过。

这些操作可能减少 RSS、增加 zram 使用或释放页，却不调用 `fragmentation_score_node()`，也不负责把 buddy 空闲页整理为指定 order。`use_memcg_for_compaction` 改变的是进程回收接口，不是把 physical compaction 从 zone 级改成 memcg 级。

下面的命令用于查看 ActivityManager 当前导出的 cached-app 优化状态；不同构建的字段会有差异：

```bash
adb shell dumpsys activity settings | sed -n '/Compaction settings/,+40p'
adb shell dumpsys activity processes | grep -i -A8 -B3 compact
```

如果系统没有输出对应段落，应结合 `CachedAppOptimizer.dumpCompact()` 的调用位置和当前构建的 dumpsys 入口查找，不能退回到旧版本的 `ro.compact_action_*` 属性。Perfetto 中 `CachedAppOptimizer` 的 ATrace 区间和内核 `compaction:*` 事件也要分开统计。

## 8. 四类常见现场怎样判断

### 8.1 direct compaction 多、成功少

先看 `extfrag_index`：

- 接近 0：优先检查内存不足、reclaim、PSI、zram 和工作集；
- 接近 1000：继续确认目标 order、migratetype、不可移动页和分配者；
- 没有 debugfs：用 buddy、pagetypeinfo、trace 参数和复现实验补证。

`compact_fail` 增加不代表应用一定失败。allocator 还可能降低 order、回退到其他 migratetype、重试或返回错误，结论取决于调用者。

### 8.2 `kcompactd` CPU 高、前台同时变慢

区分 proactive work 与分配需求唤醒的 daemon work。查看 trace 中 `kcompactd` 唤醒原因、扫描范围、CPU 运行时间，以及 node score 是否随工作下降。

如果调低 `compaction_proactiveness` 后前台长尾下降，但 direct compaction 或高阶分配失败明显增加，说明成本只是从后台移到了请求路径。判断标准应覆盖两侧，而不是只看 `kcompactd` CPU。

### 8.3 相机启动需要连续内存

相机、显示和多媒体 buffer 可能来自 DMA-BUF heap、CMA、ION 兼容路径或厂商驱动自己的 allocator。`compact_stall` 只能证明内核发生了 direct compaction，不能证明某次 DMA 分配就是原因。

需要同时确认：

- `/proc/meminfo` 中设备是否导出 `CmaTotal`、`CmaFree`；
- DMA-BUF heap、CMA 或驱动 tracepoint；
- 失败日志中的目标 size、order 和 allocator；
- 相机启动窗口与 compaction/CMA 迁移区间是否一致。

只有证据指向普通 zone 的外部碎片时，才进入 proactiveness 或 migratetype 调整。CMA 区过小、长期 pin 页或驱动生命周期错误需要在各自路径修复。

### 8.4 游戏或 UI 帧卡顿

应用层不能也不应根据窗口焦点修改全局 sysctl。全局 proactiveness 会影响整台设备，前台降低后可能让相机、媒体或其他高阶分配在稍后承担 direct compaction。

先把超时帧与 `mm_compaction_*`、reclaim、major fault、CPU 调度、频率和 I/O 对齐。如果卡顿发生在资源首次触页或 shader 编译阶段，规整计数同时增长也可能只是共同受内存压力驱动。

## 9. 不要用 `drop_caches` 制造“好看”的结果

向 `drop_caches` 写 1 或 3 会丢弃可回收 page cache 和 slab。它不执行 physical compaction，也不模拟用户的正常稳态。后续测试会遭遇额外 cache miss 和 I/O，前后样本不再等价。

只有在研究缓存冷启动本身时，才应把它作为明确的实验变量，并让所有对照组执行相同操作。排查碎片时，更合适的办法是重复固定工作负载、记录计数增量，并用手工 `compact_memory` 做单独的因果验证。

## 10. 建立产品自己的阈值

`compact_stall > 100/分钟`、`fail > 30%`、`extfrag > 0.7` 这类数字没有跨设备通用性。目标 order、页大小、RAM、负载和厂商分配器不同，绝对阈值会产生大量误报。

产品监控可以保留以下原始量：

- 分场景的 `compact_*` 与 `compact_daemon_*` delta；
- 目标 order 的 buddy 与 extfrag 分布；
- direct compaction 持续时间及调用线程；
- `kcompactd` CPU 时间和扫描效率；
- THP/mTHP 按 size 的分配、fallback、split 计数；
- CMA、DMA-BUF、PSI、reclaim、zram、LMKD 和 OOM 指标；
- 用户可感知的启动、帧耗时、相机首帧和功耗。

阈值应来自同一产品、同一版本、同一场景的健康样本分布，再结合故障样本验证召回率。版本升级后重新建立基线，避免把内核计数语义变化误判为性能回退。

## 11. 排障结论模板

一次可复核的结论至少回答以下问题：

1. 设备运行的内核、page size、最终配置和 sysctl 是什么；
2. 哪个调用者申请了多大 size、哪个 order、哪种 migratetype；
3. 分配失败更接近内存不足还是外部碎片；
4. direct、daemon、proactive 或手工规整中的哪一条路径在工作；
5. 规整区间与用户可感知延迟有什么时间关系；
6. 修改单一变量后，收益、CPU/功耗代价和高阶分配失败怎样变化；
7. 恢复默认值后，结果是否可重复。

如果其中第 2—4 项还没有证据，就不宜写“compaction 导致卡顿”。更准确的表述是“卡顿窗口与规整活动重叠，尚未确认触发者和等待关系”，并列出下一步采证方法。

## 12. 小结

Android 17 的内存规整调优从区分概念开始：reclaim 负责腾出页，physical compaction 负责重新排列页，CachedAppOptimizer 面向 cached process 做降温或换出。名称相近，源码路径和指标不同。

`compaction_proactiveness` 只控制 proactive 路径；`extfrag_threshold` 影响高阶分配在规整和回收之间的判断；`compact_unevictable_allowed` 决定是否检查 unevictable LRU。三个参数没有按设备 RAM 划分的固定答案。

工程上可靠的顺序是：记录产品边界，采集 vmstat delta、buddy/extfrag 和 trace，找到目标 order 与分配者，再做单变量、可回滚的 A/B。只要无法说明是哪一种规整、由谁触发、对哪个延迟指标产生了什么变化，就还没有到修改量产参数的时候。
