## 审阅结论

Android 17 / API 37 / `android-17.0.0_r1` 没有一个名为“模块化启动框架”的统一平台组件。受保护提纲把 init 服务、SystemServer、APEX、应用进程初始化和运维策略放进了同一套生命周期，无法据此推导源码行为。

原稿给出的[掘金链接](https://juejin.cn/post/7617108607432736778)当前页面标题是“Android Room 3.0 来了”，内容与系统启动无关；“结构参考”又来自电量优化章节，两者都不能支撑提纲中的 Android 17 新机制。本页保留为历史核查入口，不把缺失的组件名、接口和实验数据补成推测。

## 1. “模块”先分层

Android 中至少有四类启动对象。它们可以分别优化，但没有共享的依赖图、状态机或动态参数中心。

| 层次 | Android 17 的真实入口 | 启动关系 | 故障边界 |
|---|---|---|---|
| native service | init `.rc` 的 `service`、`on`、property trigger | 配置中的 action 顺序与显式 `start`/`class_start` | 单独进程，可由 init 按声明策略监管 |
| Java 系统服务 | `SystemServer`、`SystemServiceManager` | Java 源码顺序、boot phase、显式等待 | 多数位于 system_server，共享进程故障域 |
| 可更新系统模块 | APEX/Mainline、system_server jar | 解决交付与类加载边界；服务仍由明确入口启动 | 取决于模块进程与服务位置 |
| App 初始化器 | 平台组件生命周期、AndroidX App Startup | 当前应用进程内的同步依赖遍历 | 每个 App 进程拥有独立状态 |

讨论“解耦”“延迟启动”或“并行”之前，应先确定对象属于哪一层。跨层使用同一组结论，常见后果是把 APEX 更新能力解释成运行时热替换，或把 App Startup 依赖图解释成系统服务调度器。

## 2. Android 17 的系统启动没有自动依赖图

`SystemServer.run()` 仍然按源码顺序调用：

1. `startBootstrapServices()`；
2. `startCoreServices()`；
3. `startOtherServices()`；
4. `startApexServices()`。

`SystemServiceManager.startService()` 构造服务、加入已启动列表，然后调用 `SystemService.onStart()`。系统服务的主要先后关系来自 `SystemServer.java` 中的显式调用、boot phase 和 Future 等待，不会扫描所有服务后自动拓扑排序。

Android 17 的 `startBootPhase()` 包含受 `Flags.parallelizeOnbootphase()` 控制的并行路径。服务通过 `setBootPhaseSerial(phase)` 标记必须串行的阶段，管理器用 `getBootPhaseSerial(phase)` 读取标记；其余回调提交给 `SystemServerInitThreadPool`，管理器等待这一批任务全部结束。这个实现只覆盖 boot-phase 回调，不能外推为所有服务的智能并行启动。

init 也不计算全局 DAG。`.rc` action 由事件或属性触发，action 中的 command 按加入顺序执行；`start` 发起服务启动后，不表示依赖服务已经完成业务初始化。跨进程就绪关系仍需由属性、socket、Binder 服务注册或明确协议表达。

## 3. 提纲中的优化项应怎样解释

### 3.1 按需加载与预加载

- init 的 `disabled` 服务等待显式 `start`，`oneshot` 控制退出后的重启行为；这些是服务策略，不是通用懒加载 API。
- SystemServer 可以把服务放在较晚的调用位置或 boot phase，但移动前要核对调用方、Binder 注册时间和用户解锁阶段。
- AndroidX App Startup 可以移除某个 `Initializer` 的自动发现，在首个消费者之前手动初始化；调用仍然同步执行。
- Zygote preload 用进程启动前的共享页和固定启动成本换取后续进程收益。只看设备内存大小就增加预加载项，可能同时拉长开机并增加常驻页。

关键路径上的工作能否延后，要由“首个消费者何时需要结果”决定。没有调用点和 trace 证据时，不应把预加载或延迟初始化作为默认答案。

### 3.2 生命周期与失败处理

四层对象的失败语义差异很大：

- init service 是否重启由 `oneshot`、`critical`、`reboot_on_failure` 等声明和实现共同决定；
- SystemService 的 `onStart()` 或 boot-phase 回调抛出未处理异常，可能中止 system_server 启动；
- APEX 更新、激活与回滚由 apexd 和系统更新流程管理，不能等同于正在运行服务的任意热替换；
- App Startup 的 `Initializer.create()` 发生异常会经 `StartupException` 传播，默认 Provider 启动失败可能直接导致应用进程创建失败。

因此，所谓“统一模块状态机”需要先定义具体对象。把失败一律重试，可能造成 crash loop、重复副作用或更长的启动阻塞。

### 3.3 配置与设备适配

设备差异通常通过 product/board `.rc`、资源 overlay、DeviceConfig/feature flag、系统属性或模块自身配置表达。配置入口是否能在运行时修改、修改后何时生效、是否需要重启，都由具体组件决定。

高端机与低端机的策略也不能只按 RAM 分组。CPU 核型、存储随机读、热状态、ZRAM、首屏依赖和厂商服务数量都会改变关键路径。可靠做法是在同一构建和同一启动类型下比较 trace 分位值，再决定是否拆分设备策略。

## 4. 可观测性要对应执行层

| 调查对象 | 首选证据 |
|---|---|
| init/native boot | init action/service 时序、bootchart、内核与 Perfetto trace |
| SystemServer | `SystemServerTiming`、`StartService <class>`、`OnBootPhase_<phase>_<class>`、线程状态与锁等待 |
| App 冷启动 | `ApplicationStartInfo`、Macrobenchmark `StartupTimingMetric`、Perfetto 的 process start、bindApplication、Provider 与首帧 |
| App 初始化依赖 | 每个 `Initializer.create()` 的 trace section、Merged Manifest、依赖声明与首个消费者 |

“自动诊断报告”只能汇总这些证据，不能替代执行层判断。报告至少要保留设备、构建指纹、启动类型、样本数、trace 时间边界和回归基线。
