## 审阅结论

截至 Android 17 正式版资料，以 Android 17 / API 37 / `android-17.0.0_r1` 为基线，没有找到官方博客声称“全新 ML 任务调度器把应用启动时间减少 30%”。原文件也没有保存博客 URL、文章标题、作者、发布日期或实验条件，不能把提纲中的数字当成平台结论。

[Android 17 is Here](https://developer.android.com/blog/posts/android-17-is-here) 的性能部分公开讨论了应用内存限制、ART 分代 GC 改进、lock-free `MessageQueue` 和 static final 字段限制。与启动直接相关的队列变化是：target SDK 37 及以上应用使用新的 lock-free `MessageQueue` 实现。博客没有把它描述为用户行为预测器，也没有给出“启动时间减少 30%”的固定结果。

## “30%”可能来自哪里

[应用启动优化最佳实践](https://developer.android.com/topic/performance/appstartup/best-practices) 提到 Baseline Profiles 可以让代码从首次启动开始获得最高约 30% 的执行速度改善。这个数字描述的是 profile 引导编译对代码执行速度的潜在影响，页面同时要求结合应用结构和实际测量理解收益。

它不能改写成以下任何说法：

- Android 17 平台新增一个 ML 调度器；
- 所有应用的冷启动时间都会缩短 30%；
- 系统根据用户行为自动延迟或预启动应用；
- 不生成 profile、不更新应用也能得到相同收益。

启动耗时还包括进程创建、类加载、Provider、`Application.onCreate()`、Activity、资源加载、布局和首帧提交。某段代码执行加速 30%，不代表端到端 TTID 或 TTFD 同样缩短 30%。

## Android 17 中真实的 JobScheduler 更新

[Android 17 功能与 API 页面](https://developer.android.com/about/versions/17/features) 列出的 JobScheduler 相关变化是 `JobDebugInfo` API 扩展。`getPendingJobReasonStats()` 等接口帮助开发者了解 job 为什么处于 pending 状态，以及各原因累计持续多久。

这是诊断能力，不是新的调度决策模型。JobScheduler 仍用于满足约束和系统策略后的后台 job，不负责 Activity 冷启动中的初始化顺序，也不向应用公开用户行为预测模型。

同一页面还列出了 `ProfilingManager` 的冷启动和异常触发器。这些触发器用于收集 trace、stack sample 或 heap dump，属于性能资料采集能力，不能证明系统存在提纲所述的 ML 启动调度。

## 可以验证的 Android 17 启动改进

| 方向 | 可验证机制 | 适用边界 |
|---|---|---|
| 主线程队列 | lock-free `MessageQueue` | target SDK 37 及以上；需关注反射私有字段的兼容性 |
| 代码编译 | Baseline Profiles | 随应用交付热点路径，收益因应用和设备而异 |
| DEX 布局 | Startup Profiles | 构建期优化启动类的 DEX 排列 |
| 初始化依赖 | AndroidX App Startup | 当前应用进程内合并 Provider 并声明初始化器依赖 |
| 延后非关键工作 | 应用按首个消费者设计 | 需要处理线程安全、失败和首次使用延迟 |
| 启动诊断 | Perfetto、Macrobenchmark、ProfilingManager | 分析和测量，不替应用自动修改启动路径 |

## 如何验证收益数字

如果后续资料再次声称“减少 30%”，至少应记录：

1. 冷启动、温启动还是热启动；
2. TTID、TTFD、某段代码耗时还是 CPU time；
3. 设备型号、系统构建、应用构建和编译模式；
4. 是否安装 Baseline Profile / Startup Profile；
5. 样本量、预热与清理方式、P50/P90/P95 等统计量；
6. 对照组与实验组之间唯一改变的变量。

只有端到端 Macrobenchmark 与 Perfetto trace 同时支持时，才能把局部优化归因到应用启动指标。
