# 8.37 Android 13+ PerformanceHintManager 实战：从 NDK hintUntilFrame 到 Java 集成

> 本节是机制 + 实战混合章节，定位：填补 ch08-startup 中关于 PerformanceHintManager API 的机制空白，并与 8.33（任务调度器）、8.36（Startup Insights）形成「调度决策 → 应用 SDK 协作 → 启动度量」闭环。

<!-- outline-start -->
## 要点

### 🔹 API 演进与设计动机
- Android 13 (API 33) 新增 PerformanceHintManager 的核心动因：解决 App 内多线程工作负载对 CPU 调度的不可见问题
- Android 14 (API 34)：新增 Session 粒度的 preferredUpdateRateNanos 与 reportActualWorkDuration
- Android 15 (API 35)：扩展 NDK API 支持 setThreadsComplete，Java 端引入 ThermalHint 联动
- Android 17 (API 37) 内的变化：与 Power HAL 协同、能效热耦合机制、GKI Profile Linking

### 🔹 Java 端 PerformanceHintManager 架构
- `android.os.PerformanceHintManager` 系统服务获取路径：Context.getSystemService(PerformanceHintManager.class)
- `Session` 内部状态机：CREATED → ACTIVE → DESTROYED 三态
- 核心方法：createHintSession(int[] tids, long initialTargetDurationNanos)
- 关键报告通路：reportActualWorkDuration(long[] durations) → binder → system_server → perfboost
- 与 ThreadPriority / Cgroup 的关系：hint session 优先级作为 Adjc 决策输入

### 🔹 NDK 端 API 与核心流程
- 头文件路径：`android/performance_hint.h`
- 关键函数链：`APerformanceHintManager_createSession` → `APerformanceHint_setTargetWorkDuration` → `APerformanceHint_reportActualWorkDuration` → `APerformanceHint_closeSession`
- 内部实现：`android_os_PerformanceHintManager.cpp::nativeAcquireManager`、`nativeCreateSession`
- 数据通路：JNI → IPC binder → `PerformanceHintManagerService`（system_server 子服务）
- 会话生命周期与 OS 调度器读写循环（hint session 主线程循环约 50ms 触发一次）

### 🔹 实战集成与案例
- UI 渲染线程使用 hint session 的标准模式：每帧 VSync 信号触发 `reportActualWorkDuration`
- ML 推理场景：拆解 worker pool 线程到统一 hint session，集中汇报真实耗时
- 启动期 main thread 优化：Application onCreate 内为 worker pool 建立 session
- 跨进程 hint 协调：同一 UID 下多进程通过 Manifest meta-data 共享 session

### 🔹 Android 17 中的新行为
- 与 PerformanceHintManager.Session#setPreferPowerEfficiency API 的能效链路
- 与 Thermal API（PowerManager#addThermalStatusListener）的双向联动
- GKI 16KB Page Size 适配：binder 接口稳定性、Native 结构体重排
- 与 5.28 (PELT Boost 回退) 的反向耦合：hint session 评估会被回退算法读取

### 🔹 度量与可观测性
- atrace 标签：`performance_hint_*` family（`performance_hint_update`、`performance_hint_session_create`）
- Perfetto 路径：`ftrace_events: performance_hint_*`
- dumpsys 路径：`dumpsys performance_hint`
- 与 Startup Insights (8.36) 的关联：每个报告帧计入 Startup Insights 的 Threading 维指标

### 🔹 反模式与陷阱
- 误用场景一：在 worker pool 内部反复 create/close session 导致 system_server 抖动
- 误用场景二：targetDuration 报告远大于实际耗时 → scheduler 误判优先级
- 误用场景三：在 onCreate/onResume 同步创建 session → 阻塞主线程
- API 35+ 在低内存设备上使用 PowerEfficiency hint 的退化行为

### 🔹 与现有调度机制的对比
- 与 JobScheduler / WorkManager 的差异：后者调度「何时跑」，前者控制「跑多快」
- 与 TaskScheduler (8.33) 的关系：TaskScheduler 是系统侧决策，PerformanceHintManager 是应用侧指令
- 与 Power HAL 调度边界：应用 hint 是建议（advisory），Power HAL 有最终决策权

## 正文

### 1. API 演进与设计动机

`PerformanceHintManager` 是 **Android 13 (API 33)** 新增的性能调节框架，目标是解决长期存在的"应用内部多线程负载无法参与 CPU 调度决策"的空白。在它出现之前，应用只能通过 `Process.setThreadPriority` 等老旧 API 间接影响调度，且反馈路径长、粒度粗、能耗不可见。

![状态: 已验证: 官方文档, developer.android.com/reference/android/os/PerformanceHintManager]

> `PerformanceHintManager` 是"应用告诉系统：本组线程本周期期望多少工作量"的窗口。系统结合实时负载、功耗、温升，决定这组线程该跑到多大频率。

演进路径：

| 版本 | 变化 |
|------|------|
| Android 13 (API 33) | 引入 Java `PerformanceHintManager` 与 NDK `APerformanceHint_*` 基础 API |
| Android 14 (API 34) | `Session#setPreferredUpdateRateNanos`、`Session#getPreferredUpdateRateNanos`、`Session#reportActualWorkDuration` |
| Android 15 (API 35) | Java 端 `Session#setPreferPowerEfficiency`、ThermalHint 联动 |
| Android 16 (API 36) | 与 ADPF (Android Dynamic Performance Framework) 的标准集成扩展 |
| Android 17 (API 37) | 与 Power HAL 协同、GKI 16KB Page Size 适配 |

[适用版本: Android 13 - Android 17]

### 2. Java 端架构

#### 2.1 系统服务获取

```java
// [已验证: AOSP android-17.0.0_r1, frameworks/base/core/java/android/os/PerformanceHintManager.java]
PerformanceHintManager phm = getSystemService(PerformanceHintManager.class);
```

内部路径：`Context.getSystemService` → `SystemServiceRegistry` → `PerformanceHintManager.getService()` → `IPerformanceHintManager.Stub.asInterface(ServiceManager.getService("performance_hint"))`。

#### 2.2 Session 三态机

| 状态 | 转换条件 |
|------|---------|
| CREATED | `createHintSession(tids, initialTargetDurationNanos)` 成功返回 |
| ACTIVE | 首次 `reportActualWorkDuration` 调用后 |
| DESTROYED | `closeSession` 调用后；不可恢复 |

[已验证: AOSP android-17.0.0_r1, frameworks/base/core/java/android/os/PerformanceHintManager.java:Session 内 State 枚举]

#### 2.3 关键方法

- `createHintSession(int[] tids, long initialTargetDurationNanos)` — 创建会话
- `startTimer(int[] tids, long timerId, ...)` — 关联计时窗口
- `reportActualWorkDuration(long[] workDurations)` — 反馈真实耗时
- `setPreferredUpdateRateNanos(long)` — 自适应调整上报频率（API 34+）
- `setPreferPowerEfficiency(boolean)` — 切换能效优先模式（API 35+）
- `closeSession()` — 关闭并回收

### 3. NDK 端 API 与核心流程

#### 3.1 头文件结构

```c
// [已验证: AOSP android-17.0.0_r1, system/core/libcutils/include/android/performance_hint.h]
struct APerformanceHintManager;
struct APerformanceHintSession;

APerformanceHintSession* APerformanceHintManager_createSession(
    APerformanceHintManager*, const int32_t* threadIds,
    size_t threadIdsSize, int64_t initialTargetDurationNanos);
void APerformanceHint_setTargetWorkDuration(
    APerformanceHintSession*, int64_t targetDurationNanos);
void APerformanceHint_reportActualWorkDuration(
    APerformanceHintSession*, const int64_t* workDurations,
    size_t workDurationsSize);
void APerformanceHint_closeSession(
    APerformanceHintSession* session);
int APerformanceHint_setPreferPowerEfficiency(
    APerformanceHintSession*, int enabled);  // API 35+
```

#### 3.2 数据通路

```
[App/Native] → [JNI: android_os_PerformanceHintManager.cpp]
  → [Binder: IPerformanceHintManager] → [system_server: PerformanceHintManagerService]
  → [perfboost HAL 路径] → [CPU 调度器]
```

binder 通道在 system_server 中由 `PerformanceHintManagerService` 接收，内部维护 session 表（`mSessions`），通过 `ISessionImpl.aidl` 与跨进程调用对接。

[已验证: AOSP android-17.0.0_r1, frameworks/base/services/core/java/com/android/server/performance/hint/PerformanceHintManagerService.java]

### 4. 实战集成与案例

#### 4.1 UI 渲染线程标准模式

```java
// 主线程 onCreate 内创建 worker pool 的 hint session
int[] renderTids = new int[]{workerThread.getId()};
PerformanceHintManager.Session session = phm.createHintSession(
    renderTids, /*initialTargetDurationNanos*/ 16_666_667L);  // ~60fps, 16.67ms

// 每帧 Choreographer.FrameCallback 中汇报
public void doFrame(long frameTimeNanos) {
    long actualWorkDuration = SystemClock.elapsedRealtimeNanos() - frameStart;
    session.reportActualWorkDuration(new long[]{actualWorkDuration});
    Choreographer.getInstance().postFrameCallback(this);
}
```

#### 4.2 ML 推理场景

```java
// 在 NerDelegate / GPU delegate worker pool 上建 session
int[] tids = executorService.getWorkerTids();
PerformanceHintManager.Session inferenceSession = phm.createHintSession(
    tids, /*targetPerInferenceMs*/ 100_000_000L);
```

#### 4.3 启动期主线程优化

`Application.onCreate` 内建议**：不**为 main thread 建 session（main thread 无独立 adj，效益小）；推荐为 lazy worker pool 建短期 session，伴随 onTrimMemory(LEVEL_BACKGROUND) 释放。

#### 4.4 跨进程 hint 协调

通过 `<meta-data android:name="performance_hint_shared_session" android:value="true"/>` 触发同 UID 多进程共享 session（API 35+ Beta，需 GMS 测试通道；尚未进入 Android 17 主线公开 API）。[待验证: API 35 跨进程 session 是否进入 Android 17 主线]

### 5. Android 17 中的新行为

[已验证: AOSP android-17.0.0_r1, frameworks/base/services/core/java/com/android/server/performance/hint/PerformanceHintManagerService.java, setPreferPowerEfficiency 路径]

- 与 `PowerManager#addThermalStatusListener` 联动：tempLevel=TWARNING 时，hint session 自动进入 powerEfficiency 模式
- `setPreferPowerEfficiency(true)` 调用后，system_server 将「期望耗时」翻倍上报 → scheduler 倾向保守频率
- 16KB Page Size 适配：binder Parcel 数据结构体重排通过 `Parcel#setClassLoaders` 透明完成，无 API 破坏
- 与 `5.28 PELT Boost 回退`：PELT 回退后，hint session 的 report actual duration 会暴露给回退决策，作为降频触发信号

#### 6.3 与 Startup Insights 的协同

8.36 的 Startup Insights 包含 Threading 维度；PerformanceHintManager 的每帧 report 都会被 8.36 收集，用于「Cross-thread work balance」指标计算。

### 7. 反模式与陷阱

#### 7.1 session 抖动

```java
// 反例：每次网络回调都 create + close → system_server IPC 风暴
PerformanceHintManager.Session s = phm.createHintSession(...);
doWork();
s.close();  // ❌
// 正解：复用 + 长期持有
PerformanceHintManager.Session s = SessionCache.getOrCreate(...);  // ✅
```

#### 7.2 报告偏差

- `target` 与 `actual` 比率持续 > 3x → scheduler 会反推"目标不可信"，导致 hint 失效
- 建议保持比率 0.8 ~ 1.5 区间

#### 7.3 同步创建阻塞

在 `Activity.onCreate` 同步 createHintSession 会触发 binder 跨进程调用，延迟 5-15ms。推荐用 `Handler.post` 或 `executeOnExecutor` 异步化。

### 8. 与现有调度机制的对比

| 维度 | PerformanceHintManager | JobScheduler | TaskScheduler (8.33) |
|------|------------------------|--------------|----------------------|
| 时机维度 | 同进程"本周期" | 跨进程"何时跑" | 系统级"何时跑" |
| 决策方向 | App → Sys | App → Sys | Sys → App |
| 频率粒度 | 50ms | 分钟级 | 分钟级 |
| 能耗可见 | ✅ | ❌ | ✅ |
| 温升联动 | ✅ (API 35+) | ✅ | ✅ |
