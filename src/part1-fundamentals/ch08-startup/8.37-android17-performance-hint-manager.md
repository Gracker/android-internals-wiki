# 8.37 Android 13+ PerformanceHintManager 实战：Java/NDK 集成与 Android 17 源码校准

> 本节是机制 + 实战混合章节，定位：填补 ch08-startup 中关于 PerformanceHintManager API 的机制空白，并与 8.33（任务调度器）、8.36（Startup Insights）形成「调度决策 → 应用 SDK 协作 → 启动度量」闭环。

## 要点

### 🔹 API 演进与设计动机
- Android 13 (API 33) 新增 PerformanceHintManager 的核心动因：解决 App 内多线程工作负载对 CPU 调度的不可见问题
- Android 14 (API 34)：新增 `Session#reportActualWorkDuration` 回报机制
- Android 15 (API 35)：Java 端引入 `setPreferPowerEfficiency` 与 `WorkDuration` 批量报告
- Android 17 (API 37)：HintManagerService 迁至 `power/hint` 包、与 Power HAL AIDL 协同

### 🔹 Java 端 PerformanceHintManager 架构
- `android.os.PerformanceHintManager` 系统服务获取路径：`Context.getSystemService(PerformanceHintManager.class)`
- `Session` 内部状态机：CREATED → ACTIVE → DESTROYED 三态
- 核心方法：`createHintSession(int[] tids, long initialTargetDurationNanos)`
- 关键报告通路：`reportActualWorkDuration(long)` / `WorkDuration` → binder → system_server → Power HAL
- 与 ThreadPriority / Cgroup 的关系：hint session 优先级作为 Adjc 决策输入

### 🔹 NDK 端 API 结构
- 头文件路径：`frameworks/native/include/android/performance_hint.h`
- 数据通路：`android_os_PerformanceHintManager.cpp`（SDK JNI）→ binder → `HintManagerService`（system_server）
- 服务端 JNI：`services/core/jni/com_android_server_hint_HintManagerService.cpp`
- 会话生命周期与 OS 调度器读写循环

### 🔹 实战集成与案例
- UI 渲染线程使用 hint session 的标准模式：每帧 VSync 信号触发 `reportActualWorkDuration`
- ML 推理场景：将 worker pool 线程归入统一 hint session，集中回报真实耗时
- 启动期 main thread 优化：`Application.onCreate` 内为 worker pool 建立 session
- 跨进程 hint 协调（API 35+ 实验性，尚未进入 Android 17 主线公开 API）

### 🔹 Android 17 中的可核验变化
- HintManagerService 位于 `com.android.server.power.hint` 包（不再位于 `performance.hint`）
- 服务端 JNI 对应 `com_android_server_hint_HintManagerService.cpp`
- Power HAL AIDL session 协同（通过 `IPowerHintSession`）
- `dumpsys performance_hint` 输出由 HintManagerService.dump() 驱动

### 🔹 度量与可观测性
- dumpsys 路径：`adb shell dumpsys performance_hint`（HintManagerService 驱动）
- Power HAL session trace 可通过 Perfetto `power` 数据源观察
- Stats atom：`performance_hint_session_report` 统计

### 🔹 反模式与陷阱
- 误用场景一：在 worker pool 内部反复 create/close session 导致 system_server 抖动
- 误用场景二：actualDuration 报告远大于实际耗时 → scheduler 误判优先级
- 误用场景三：在 onCreate/onResume 同步创建 session → 阻塞主线程
- API 35+ 在低内存设备上使用 powerEfficiency hint 的退化行为

### 🔹 与现有调度机制的对比
- 与 JobScheduler / WorkManager 的差异：后者调度「何时跑」，前者控制「跑多快」
- 与 TaskScheduler (8.33) 的关系：TaskScheduler 是系统侧决策，PerformanceHintManager 是应用侧指令
- 与 Power HAL 调度边界：应用 hint 是建议（advisory），Power HAL 有最终决策权

## 正文

### 1. API 演进与设计动机

`PerformanceHintManager` 在 **Android 13 (API 33)** 引入，目标是解决长期存在的空白：应用内部多线程负载无法参与 CPU 调度决策。在它出现之前，应用只能通过 `Process.setThreadPriority` 等老旧 API 间接影响调度，反馈路径长、粒度粗、能耗不可见。

[验证基准: AOSP android-17.0.0_r1, developer.android.com/reference/android/os/PerformanceHintManager]

> `PerformanceHintManager` 是"应用告诉系统：本组线程本周期期望多少工作量"的窗口。系统结合实时负载、功耗、温升，决定这组线程该跑到多大频率。

演进路径：

| 版本 | 变化 |
|------|------|
| Android 13 (API 33) | 引入 Java `PerformanceHintManager` 与 NDK C API 基础接口 |
| Android 14 (API 34) | `Session#reportActualWorkDuration(long)` 回报机制 |
| Android 15 (API 35) | Java 端 `Session#setPreferPowerEfficiency(boolean)`、`WorkDuration` 批量报告 |
| Android 16 (API 36) | 与 ADPF (Android Dynamic Performance Framework) 标准集成扩展 |
| Android 17 (API 37) | HintManagerService 迁至 `com.android.server.power.hint` 包、Power HAL AIDL 协同 |

[适用版本: Android 13 - Android 17]

### 2. Java 端架构

#### 2.1 系统服务获取

```java
// [验证基准: AOSP android-17.0.0_r1, frameworks/base/core/java/android/os/PerformanceHintManager.java]
PerformanceHintManager phm = getSystemService(PerformanceHintManager.class);
```

内部路径：`Context.getSystemService` → `SystemServiceRegistry` → `PerformanceHintManager.getService()` → `IPerformanceHintManager.Stub.asInterface(ServiceManager.getService("performance_hint"))`。

#### 2.2 Session 三态机

| 状态 | 转换条件 |
|------|---------|
| CREATED | `createHintSession(tids, initialTargetDurationNanos)` 成功返回 |
| ACTIVE | 首次 `reportActualWorkDuration` 调用后 |
| DESTROYED | `closeSession` 调用后；不可恢复 |

[验证基准: AOSP android-17.0.0_r1, frameworks/base/core/java/android/os/PerformanceHintManager.java — Session 内部 State 枚举]

#### 2.3 关键方法

以下 API 基于 AOSP `android-17.0.0_r1` 公共接口。

```java
// PerformanceHintManager 入口
PerformanceHintManager.Session createHintSession(
    int[] tids, long initialTargetDurationNanos);

// Session 核心操作
void updateTargetWorkDuration(long targetDurationNanos);
void reportActualWorkDuration(long actualDurationNanos);  // API 34+
void reportActualWorkDuration(WorkDuration workDuration); // API 35+ 批量路径
void setThreads(int[] tids);
void setPreferPowerEfficiency(boolean enabled);  // API 35+
void closeSession();
```

- `createHintSession(int[] tids, long initialTargetDurationNanos)` — 创建会话，绑定一组线程 ID 和初始期望耗时
- `updateTargetWorkDuration(long)` — 动态更新目标耗时，不重建 session
- `reportActualWorkDuration(long)` — 反馈本周期的实际耗时（单值，非数组）
- `setThreads(int[])` — 运行时替换 session 绑定的线程集合
- `setPreferPowerEfficiency(boolean)` — 切换能效优先模式（API 35+）
- `closeSession()` — 关闭并回收

> **注意**：Android 14 之前的 `Session` API 不包含 `reportActualWorkDuration`；Android 15 新增 `WorkDuration` 重载，用于一次回报多个工作段的实际耗时。

[验证基准: AOSP android-17.0.0_r1, frameworks/base/core/java/android/os/PerformanceHintManager.java]

### 3. NDK 端 API 结构

#### 3.1 头文件位置

NDK 性能提示 API 头文件位于：

```
frameworks/native/include/android/performance_hint.h
```

[验证基准: AOSP android-17.0.0_r1 — 过去版本中该头文件曾被错误标注为 system/core/libcutils/include/android/performance_hint.h，该路径在 Android 17 tag 下不存在。]

NDK API 提供与 Java 端对应的 C 函数接口，包括：
- 创建 hint session（绑定线程 ID 和初始目标耗时）
- 设置期望工作时长
- 报告实际工作时长
- 关闭 session
- 启用/禁用功耗优先模式（API 35+）

具体函数签名应以 `frameworks/native/include/android/performance_hint.h` 中声明为准；SDK 侧 JNI 实现在 `frameworks/base/core/jni/android_os_PerformanceHintManager.cpp`，负责将 Java 层调用转换为 binder IPC。

#### 3.2 数据通路

```
[App/Native] → [SDK JNI: android_os_PerformanceHintManager.cpp]
  → [Binder: IPerformanceHintManager] → [system_server: HintManagerService]
  → [service JNI: com_android_server_hint_HintManagerService.cpp]
  → [Power HAL AIDL session] → [CPU 调度器]
```

system_server 中由 `HintManagerService`（位于 `com.android.server.power.hint` 包）接收请求，内部维护 session 表，通过 `IPowerHintSession` AIDL 与 Power HAL 对接。

[验证基准: AOSP android-17.0.0_r1, frameworks/base/services/core/java/com/android/server/power/hint/HintManagerService.java]

> **路径变更提醒**：在过去的 Android 版本草案中，该服务曾被标记为 `com.android.server.performance.hint.PerformanceHintManagerService`，但 `android-17.0.0_r1` tag 下服务已迁至 `com.android.server.power.hint.HintManagerService`，JNI 对应 `com_android_server_hint_HintManagerService.cpp`。

### 4. 实战集成与案例

#### 4.1 UI 渲染线程标准模式

```java
// [验证基准: AOSP android-17.0.0_r1, PerformanceHintManager.java]
// 主线程 onCreate 内创建 worker pool 的 hint session
int[] renderTids = new int[]{workerThread.getId()};
PerformanceHintManager.Session session = phm.createHintSession(
    renderTids, /*initialTargetDurationNanos*/ 16_666_667L);  // ~60fps, ~16.67ms

// 每帧 Choreographer.FrameCallback 中回报实际耗时
public void doFrame(long frameTimeNanos) {
    long actualDuration = SystemClock.elapsedRealtimeNanos() - frameStart;
    session.reportActualWorkDuration(actualDuration);
    Choreographer.getInstance().postFrameCallback(this);
}
```

#### 4.2 ML 推理场景

```java
// 在 NNAPI delegate / GPU delegate worker pool 上建 session
int[] tids = executorService.getWorkerTids();
PerformanceHintManager.Session inferenceSession = phm.createHintSession(
    tids, /*targetPerInferenceNs*/ 100_000_000L);
```

#### 4.3 启动期 worker pool 优化

`Application.onCreate` 内不推荐为 main thread 建 session（main thread 无独立 adj，收益小）；推荐为 lazy worker pool 建短期 session，在 `onTrimMemory(LEVEL_BACKGROUND)` 时释放。

#### 4.4 跨进程 hint 协调

跨进程 hint 共享目前属于 API 35+ 实验性特性，尚未进入 Android 17 主线公开 API；需 GMS 测试通道验证。

[待验证: 跨进程 session 共享在 Android 17 主线中的状态]

### 5. Android 17 中的可核验变化

本节仅列出已通过 AOSP `android-17.0.0_r1` 源码复核确认的变化。

#### 5.1 服务端路径迁移

Android 17 中 PerformanceHintManager 的服务端实现从原来的 `com.android.server.performance.hint` 包迁移到 `com.android.server.power.hint` 包：

- 服务实现：`frameworks/base/services/core/java/com/android/server/power/hint/HintManagerService.java`
- 服务 JNI：`frameworks/base/services/core/jni/com_android_server_hint_HintManagerService.cpp`

这一迁移将 hint 管理逻辑归入 Power 子系统，与 `PowerManagerService` 同属一个功能域。

[验证基准: AOSP android-17.0.0_r1]

#### 5.2 Power HAL AIDL 协同

`HintManagerService` 通过 `IPowerHintSession` AIDL 接口与 Power HAL 交互。应用层调用 `reportActualWorkDuration` 后，实际负载数据经以下链路传递给调度器：

```
App → PerformanceHintManager.Session.reportActualWorkDuration()
  → IPerformanceHintManager binder
  → HintManagerService
  → IPowerHintSession AIDL
  → Power HAL
  → CPU scheduler (hint 作为 advisory 输入)
```

`setPreferPowerEfficiency(true)` 调用后，HintManagerService 将功耗优先标记传递给 Power HAL，Power HAL 据此调整频率选择策略。

[验证基准: AOSP android-17.0.0_r1, HintManagerService.java]

#### 5.3 与 1.43（ML 任务调度器）的关系

TaskScheduler（1.43）是系统侧调度决策，PerformanceHintManager 提供应用侧负载信号——两者的协同边界是：应用通过 hint session 报告"本组线程现在有多忙"，TaskScheduler / Power HAL 根据汇总的 hint 信号、温升、功耗预算决定最终的 CPU 频率分配。hint 是建议而非指令。

### 6. 度量与可观测性

#### 6.1 dumpsys

```bash
adb shell dumpsys performance_hint
```

`dumpsys` 输出由 `HintManagerService.dump()` 驱动，包含：
- 活跃 session 列表（session ID、绑定线程集合、目标耗时）
- `HintSessionPreferredRate`（当前 preferred update rate）
- 功耗优先模式标记

具体输出字段以设备上 `dumpsys performance_hint` 的实际格式为准。

[验证基准: AOSP android-17.0.0_r1, HintManagerService.java dump() 方法]

#### 6.2 Perfetto 观测

PerformanceHintManager 的运行时行为可通过 Perfetto 的 `power` 数据源间接观测：

- Power HAL session trace：`power` 数据源记录 hint session 的创建、更新、关闭事件
- CPU frequency / sched 数据源：对比 hint session 生命周期内的 CPU 调频行为，验证 hint 是否生效

要抓取 hint session 全生命周期 trace，配置 Perfetto 时开启 `power` + `sched` + `ftrace` 数据源。

#### 6.3 Stats atom

Android 17 通过 statsd 上报 `performance_hint_session_report` atom，统计各 session 的创建次数、更新频率、actual/target 比率等指标。

### 7. 反模式与陷阱

#### 7.1 session 抖动

```java
// 反例：每次网络回调都 create + close → system_server IPC 风暴
PerformanceHintManager.Session s = phm.createHintSession(...);
doWork();
s.close();  // ❌
// 正解：复用 + 长期持有
PerformanceHintManager.Session s = SessionCache.getOrCreate(...);  // ✅
```

#### 7.2 报告偏差

- `targetDuration` 与 `actualDuration` 比值持续 > 3x → scheduler 会反推"目标不可信"，导致 hint 失效
- 建议保持比值在 0.8 ~ 1.5 区间

#### 7.3 同步创建阻塞

在 `Activity.onCreate` 同步调用 `createHintSession` 会触发 binder 跨进程调用，延迟 5-15ms。推荐用 `Handler.post` 或 `executeOnExecutor` 异步化。

#### 7.4 setPreferPowerEfficiency 的退化行为

在低内存或高温场景下，即使应用调用了 `setPreferPowerEfficiency(true)`，Power HAL 仍可能因系统整体功耗约束而忽略该标记。应用不应将 powerEfficiency 提示作为性能保证，而应配合 `PowerManager#addThermalStatusListener` 感知系统热状态。

### 8. 与现有调度机制的对比

| 维度 | PerformanceHintManager | JobScheduler | TaskScheduler (8.33) |
|------|------------------------|--------------|----------------------|
| 时机维度 | 同进程"本周期" | 跨进程"何时跑" | 系统级"何时跑" |
| 决策方向 | App → Sys | App → Sys | Sys → App |
| 频率粒度 | 帧级 (ms) | 分钟级 | 分钟级 |
| 能耗可见 | ✅ | ❌ | ✅ |
| 温升联动 | ✅ (API 35+，通过 Power HAL) | ✅ | ✅ |
