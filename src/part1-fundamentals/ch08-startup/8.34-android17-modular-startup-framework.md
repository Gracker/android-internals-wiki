## 审阅结论

Android 17 / API 37 / `android-17.0.0_r1` 没有向应用开发者提供名为“模块化启动框架”或“多进程微服务架构”的新平台 API。提纲也没有提供 AOSP 路径、官方说明或实验数据，无法支撑“动态依赖图”“服务网格”“智能排序”和“自动负载均衡”等描述。

这些词混合了四个边界清晰的层次：

| 层次 | Android 中的真实机制 | 依赖与通信边界 |
|---|---|---|
| native 系统进程 | [`init`](https://android.googlesource.com/platform/system/core/+/refs/tags/android-17.0.0_r1/init/README.md) 解析 `.rc`，启动和监管 native service | 属性、socket、Binder/HAL 等；不属于应用启动框架 |
| system_server | `SystemServer` 与 `SystemServiceManager` 启动 Java 系统服务 | 显式源码顺序、boot phase、Binder/LocalServices |
| Mainline / APEX | 交付可更新模块，也可携带 system_server jar | 解决模块交付和类加载，不自动生成运行时服务依赖图 |
| 应用进程 | manifest 组件、`Application`、Provider、Service、AndroidX App Startup | 每个进程独立初始化；跨进程通信由 Binder 等 IPC 协议负责 |

理解“模块化”之前，必须先确定讨论的是交付单元、进程、系统服务，还是应用内部代码模块。这几类对象不能共用一套生命周期和故障恢复结论。

## Android 17 的 SystemService 启动模型

`SystemServer.run()` 创建系统上下文和 `SystemServiceManager` 后，按源码顺序调用：

1. `startBootstrapServices()`；
2. `startCoreServices()`；
3. `startOtherServices()`；
4. `startApexServices()`。

`SystemServiceManager.startService()` 会构造服务、加入已启动列表，再直接调用 `SystemService.onStart()`。`SystemService` 的契约说明这些生命周期回调通常位于 system_server 主 Looper；服务可在 `onStart()` 发布 Binder 接口或 `LocalServices` 接口。

这条主路径不是通用 DAG 调度器。系统服务之间的先后关系主要由 `SystemServer.java` 中的调用顺序、注释、boot phase 和显式等待表达。某项服务如果在 `onStart()` 阻塞，就可能直接延长 system_server 的关键启动路径。

`SystemService` 在 Android 17 源码中虽然有 `dependencies` 构造参数和 `getDependencies()`，注释明确说明它当前用于 Ravenwood 无设备测试环境理解测试所需的传递依赖，不能据此声称量产启动会自动解析依赖图。

## boot phase 的并行边界

`SystemServiceManager.startBootPhase()` 只允许 phase 单调递增，并对已经启动的服务分发 `onBootPhase(phase)`。

Android 17 源码包含受 `Flags.parallelizeOnbootphase()` 控制的并行路径：

- 调用 `setBootPhaseSerial(phase)` 的服务仍按串行列表先执行；
- 其余服务可提交到 `SystemServerInitThreadPool`；
- 管理器会等待该批 Future 全部完成，再结束当前 phase；
- 任一回调抛出异常都会转成启动失败。

这是一条有条件的 boot phase 并行实现，不等于自动识别系统服务依赖，也不能推导出所有设备默认开启。是否启用、哪些服务强制串行以及并行后的共享状态安全，都需要在目标构建上核查 flag 和 trace。

`SystemService` 的类注释仍称所有生命周期方法都在 system_server 主 Looper 调用，但 Android 17 上述并行分支会在 `SystemServerInitThreadPool` 执行非串行服务的 `onBootPhase()`。flag 开启时应以 `startBootPhase()` 的执行路径为准；服务实现不能仅凭类注释假定该回调始终位于主线程。

## APEX 模块不等于微服务

`SystemServiceManager.startServiceFromJar()` 可以为独立 jar 创建 `PathClassLoader`，`SystemServer.startApexServices()` 也负责启动由 APEX 提供的 system_server 组件。这让部分服务可以随模块交付，但服务仍可能运行在同一个 system_server 进程中，共享进程故障域、堆和线程资源。

因此，APEX 边界不能直接解释为“每个模块一个微服务”。Android 17 也没有为这些服务提供网页服务体系中的 sidecar、服务网格、自动服务发现或透明负载均衡语义。

## 应用多进程的准确边界

应用在 manifest 中为 Activity、Service、Receiver 或 Provider 声明 `android:process` 后，系统可以为该组件创建独立进程。每个进程都有自己的：

- ART 虚拟机和静态字段；
- `Application` 实例；
- 主线程与 Looper；
- Binder 线程池；
- Java 堆和进程级缓存。

这会增加进程创建、内存、类加载和 IPC 成本。跨进程依赖必须设计明确协议、超时、死亡通知、重连和数据一致性；平台不会依据模块 import 关系自动建立启动顺序。

AndroidX App Startup 1.2.0 的默认 `InitializationProvider` 只在默认进程运行。需要在次进程主动初始化时，应为目标进程配置独立的 `InitializationProvider` 子类、authority 和 metadata。各进程仍各自执行自己的初始化器依赖图，没有跨进程完成屏障。

## 启动性能与可观测性

SystemServer 启动分析应从 `SystemServerTiming` trace、`StartService <class>`、`OnBootPhase_<phase>_<class>` 和显式 Future 等待入手。应用多进程则应分别观察进程创建、Provider、`Application.onCreate()`、Binder 调用和首帧。

评审时至少确认：

1. 优化目标属于 native boot、system_server 还是应用启动；
2. 关键路径是显式顺序、boot phase 还是 IPC 等待；
3. 并行任务是否存在共享锁、隐含依赖和失败传播；
4. 新进程节省的主进程工作是否大于额外的 PSS、类加载和 IPC 成本；
5. trace 中的收益能否在同一设备、构建和启动类型下复现。
