## 1. 版本与职责

本章的平台测试基线是 Android 17 / API 37 / `android-17.0.0_r1`，工具基线是 AndroidX Benchmark 1.4.1。

Startup Insights 在 AndroidX Benchmark 1.4.0 中进入稳定发布版，1.4.1 是当前稳定版本。用于开启它的 `ExperimentalConfig` 和 `StartupInsightsConfig` 仍标有 `@ExperimentalBenchmarkConfigApi`，升级 AndroidX Benchmark 时需要回归编译与输出格式。

它的职责可以概括为：

1. Macrobenchmark 在每次应用启动测量时捕获 Perfetto trace。
2. TraceProcessor 执行 Perfetto 的 `android_startup` metric。
3. `StartupInsights` 读取目标包的 `slow_start_reason_with_details`。
4. 工具把同类问题按迭代汇总，展示期望阈值、观测值和对应 trace 链接。

这是一套基于 trace metric 与阈值的诊断提示，不是 Android 17 system_server 服务，也没有训练用户行为模型。它不会修改应用代码、改变任务优先级或自动修复启动问题。

## 2. 与几个相近名称的区别

| 名称 | 所在层次 | 数据来源 | 适合回答的问题 |
|---|---|---|---|
| AndroidX Startup Insights | 测试工具 | Macrobenchmark 捕获的 Perfetto trace | 某组可重复启动实验中出现了哪些常见慢启动信号 |
| `ApplicationStartInfo` | Android 平台 API | 系统记录的进程启动信息与时间戳 | 进程为何启动、启动类型和关键时间点是什么 |
| `ProfilingTrigger.TRIGGER_TYPE_COLD_START` | Android 17 平台 API | 系统触发的 trace 与 stack sample | 如何在真实冷启动时采集诊断资料 |
| Android vitals 启动指标 | Google Play 质量数据 | 线上设备聚合数据 | 用户群体中的 TTID 分布是否异常 |

`ApplicationStartInfo` 从 API 35 起可用，不应写成 Android 17 才出现。Android 17 / API 37 新增的冷启动 profiling trigger 会在 `START_TYPE_COLD` 时尽早开始采集，并持续到 `reportFullyDrawn()` 或默认超时；它与本地 Macrobenchmark 的 Startup Insights 可以互补，但不是同一个 API。

## 3. 接入 AndroidX Benchmark 1.4.1

Startup Insights 应放在独立的 Macrobenchmark 测试模块中，目标应用使用接近发布环境的构建。下面的依赖用于为该模块加入 1.4.1 的 JUnit4 Macrobenchmark API：

```kotlin
dependencies {
    androidTestImplementation(
        "androidx.benchmark:benchmark-macro-junit4:1.4.1"
    )
}
```

这段配置只添加测试依赖，不应放进目标应用的运行时依赖。还需要按照 Macrobenchmark 要求配置测试模块、instrumentation runner、目标项目和 `profileable` 发布构建。

下面的测试用于测量 Android 17 设备上的冷启动，并让工具对每次捕获的 trace 生成 Startup Insights：

```kotlin
@OptIn(ExperimentalBenchmarkConfigApi::class)
@RunWith(AndroidJUnit4::class)
class StartupBenchmark {

    @get:Rule
    val benchmarkRule = MacrobenchmarkRule()

    @Test
    fun coldStart() {
        benchmarkRule.measureRepeated(
            packageName = "com.example.app",
            metrics = listOf(StartupTimingMetric()),
            iterations = 10,
            experimentalConfig = ExperimentalConfig(
                startupInsightsConfig = StartupInsightsConfig(isEnabled = true)
            ),
            compilationMode = CompilationMode.Partial(),
            startupMode = StartupMode.COLD
        ) {
            pressHome()
            startActivityAndWait()
        }
    }
}
```

这段测试把启动类型固定为冷启动，并以安装 Baseline Profile 后的 partial compilation 状态测量。若应用没有可安装的 Baseline Profile，`CompilationMode.Partial()` 的默认 `BaselineProfileMode.Require` 会使测试失败；此时应根据实验目的显式选择编译模式，不能为了让测试通过就混用结果。

代码还需要导入 `ExperimentalConfig`、`StartupInsightsConfig`、`ExperimentalBenchmarkConfigApi`、Macrobenchmark 的 metric、mode 和 rule。API 带实验标记，所以示例用 `@OptIn` 把接受风险的范围限制在测试类。

## 4. 输出是怎样生成的

AndroidX Benchmark 1.4.1 的 `StartupInsights.queryInsights()` 会：

- 对 trace 执行 `android_startup` metric；
- 用目标 package name 选择对应 startup；
- 展开 `slow_start_reason_with_details`；
- 把 reason、期望阈值、观测值转换成 `Insight`；
- 为 Perfetto UI 附上包名与 slow-start reason 参数；
- 跨迭代合并相同的 `Insight.Category`。

结果通常和 TTID/TTFD 指标一起出现在 Android Studio Benchmark 面板或测试输出中。一个类别只在某些迭代出现时，输出会列出命中的迭代及其 trace 链接。这有助于区分稳定瓶颈和偶发噪声。

1.4.1 所使用的 Perfetto slow-start reason 包含下列类别：

- 没有 Baseline Profile 或 Cloud Profile；
- 从 APK 直接运行代码、JIT 活动或 JIT 编译方法过多；
- 应用以 debuggable 模式运行；
- GC、dex2oat 或 installd 与启动重叠；
- 主线程 runnable、interruptible sleep、blocking I/O；
- `bindApplication`、View inflation、资源获取、类校验耗时；
- 与其他进程发生潜在 CPU 竞争；
- 主线程锁竞争、monitor 竞争或阻塞 Binder transaction；
- 启动期间收到过多 broadcast，或其他 startup 同时运行。

这些类别和阈值来自当前 Perfetto `android_startup` metric。升级 Benchmark 或设备上的 Perfetto 组件后，reason 与阈值可能变化；不要在 CI 脚本中依赖展示文字长期不变。

## 5. 如何读一条 Insight

以 “Main Thread - Binder transactions blocked” 为例，它表示 metric 在启动窗口观察到主线程 Binder transaction 阻塞信号。下一步应打开对应迭代的 trace，继续确认：

1. Binder slice 的调用方、目标进程和持续时间；
2. 主线程是在同步等待返回，还是只与其他耗时区间重叠；
3. 调用发生在 Provider、`Application.onCreate()`、Activity 生命周期还是首帧之后；
4. 多次迭代是否落在同一调用链；
5. 移动或缓存调用后，TTID/TTFD 与业务正确性是否同时改善。

Insight 是调查入口，不是根因判决。比如 “Potential CPU contention with another process” 只能说明 trace 中存在竞争迹象；温控、后台进程、频率、核心类型和测试噪声仍需结合调度轨迹判断。

## 6. 实验设计比开关更重要

为了让结果可以比较，应固定以下条件：

- 使用 release 或接近 release 的 profileable 构建，避免 debuggable 自身成为问题；
- 固定设备、Android 17 构建、电量、温度和后台负载；
- 分开记录 `StartupMode.COLD`、`WARM` 和 `HOT`；
- 固定 `CompilationMode`，不要混合 None、Partial 和 Full；
- 保持相同启动入口、账号状态、数据量和网络条件；
- 使用足够迭代并关注 P50/P90/P95，而不只看最小值；
- 修改前后保留原始 trace，检查指标变化是否来自同一关键路径。

Startup Insights 只分析已经捕获到的数据。如果 trace 丢事件、包名不匹配、启动窗口没有形成或目标进程启动失败，缺少 Insight 不代表启动没有问题。

## 7. 从提示到修复

建议按下面的顺序处理：

1. 先确认 TTID 或 TTFD 是否存在可重复回归。
2. 找出多个慢迭代共有的 Insight，不优先追逐单次异常。
3. 从 Insight 链接进入 Perfetto，定位主线程、RenderThread、Binder 和 CPU 调度证据。
4. 回到源码识别对应 Provider、初始化器、布局、类加载或 IPC。
5. 一次只改一个假设，再运行相同 benchmark。
6. 检查首次交互、错误处理和线程安全，避免把启动延迟移动到用户操作。
7. 在不同性能档位的 Android 17 设备上复测。

常见修复方向包括：删除不必要的启动初始化、延后与首屏无关的库、生成并验证 Baseline/Startup Profile、减少首屏 View inflation、消除主线程 I/O、缓存稳定的 Binder 结果，以及缩短锁的持有范围。是否采用仍要以 trace 和对照实验为依据。

## 8. 常见误区

| 误区 | 正确理解 |
|---|---|
| Startup Insights 是 Android 17 新系统服务 | 它属于独立发布的 AndroidX Benchmark |
| 开启后会自动优化应用 | 它只输出 trace 诊断提示和链接 |
| “智能识别”意味着使用 AI | 1.4.1 源码读取 Perfetto metric 的 slow-start reason 与阈值 |
| 每条 Insight 都是根因 | 它是需要回到 trace 验证的候选信号 |
| 没有 Insight 就代表启动健康 | trace 完整性、启动识别和规则覆盖都有边界 |
| 只要 TTID 下降就完成优化 | 还应检查 TTFD、首次交互、稳定性和业务结果 |
| 可以跨版本硬编码提示文字 | Perfetto metric 和实验 API 都可能演进 |

## 9. Android 17 联合诊断建议

在 Android 17 上，本地回归与线上诊断可以分工：

- Macrobenchmark + Startup Insights 用于稳定复现、比较代码改动和快速定位常见信号；
- `ApplicationStartInfo` 用于记录启动原因、启动类型和平台时间戳；
- `TRIGGER_TYPE_COLD_START` 用于在受支持的真实冷启动中采集 system trace 与 stack sample；
- Android vitals 用于判断问题覆盖多少用户和设备；
- 手工 Perfetto 分析用于确认每个候选根因的调用链与调度细节。

这些数据的时间基准、采样环境和覆盖人群不同，不能把本地十次 benchmark 的比例直接当成线上用户分布。
