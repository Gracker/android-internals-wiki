# 8.39 Android 17 heapprofd 生产环境部署

`heapprofd` 是 Perfetto 的抽样堆分析器，用调用栈解释一段时间内的分配与释放。它适合回答“哪些调用路径制造了 native heap 增长或分配 churn”，不适合作为常驻内存监控器，也不能直接代表进程 RSS。

heapprofd 从 Android 10 起可用；本章以 Android 17 / API 37 的 `android-17.0.0_r1` Perfetto 源码为当前实现锚点。这里的“生产环境”分两类：在 retail user build 上对 profileable 应用做受控诊断，以及通过 API 35+ `ProfilingManager` 采集真实用户样本。任意 App 远程启动系统级 Perfetto 会话、持续抓取其他进程，不属于公开 SDK 能力。

## 1. 先选对内存工具

Android 的“堆分析”至少有四种含义。混用它们会让诊断目标从一开始就偏掉。

| 工具/数据源 | 记录对象 | 主要输出 | 适合的问题 |
|---|---|---|---|
| `android.heapprofd` 默认 heap | native `malloc/free`、C++ `new/delete` | 抽样分配调用栈、分配与释放计数 | native 分配热点、churn、未释放分配 |
| `android.heapprofd` + `heaps: "com.android.art"` | Java/Kotlin 对象分配，Android 12+ | 抽样分配调用栈；不跟踪对象何时被 GC | Java 分配 churn 和创建路径 |
| `android.java_hprof` | ART 对象引用图，Android 11+ | 某个时刻的 live object、引用和 retained graph | Java 泄漏、重复对象、retainer |
| `linux.process_stats` / `dumpsys meminfo` | 进程 RSS/PSS、映射和匿名页等 | 进程级内存快照或时间序列 | 总体内存趋势、系统回收压力 |

native heap flamegraph 中的“unreleased malloc size”只统计 profiling 开始后被采样且尚未匹配到 free 的分配。allocator thread cache、碎片、页粒度、profiling 前的内存和一部分 Zygote 早期分配不会完整出现在这里。RSS 高于 heapprofd 结果并不自动表示 profiler 丢数据；两者测量对象不同。

## 2. Android 17 的 daemon 与数据路径

### 2.1 一个进程注册两个不同的数据源

`external/perfetto/heapprofd.rc` 把 `/system/bin/heapprofd` 声明为 `class late_start`、`disabled` 服务。`disabled` 表示 init 不会因为启动 `late_start` class 就自动拉起它。两组属性能启动服务：

- `persist.heapprofd.enable=1`：人工保持 daemon 运行，适合平台调试。
- `traced.lazy.heapprofd=1`：traced 按需启动 daemon；相关会话结束后可清理属性并停止服务。

`StartCentralHeapprofd()` 在同一个进程里创建 `HeapprofdProducer` 与 `JavaHprofProducer`，两者各自连接 traced。native heap profiler 使用 `__SIGRTMIN + 4` 唤醒已运行目标；`android.java_hprof` 使用 `__SIGRTMIN + 6` 请求 ART heap dump。这两个 signal 和 producer 不能被解释成“native/Java 分配都走同一种采样协议”：

- native 分配以及可选的 `com.android.art` Java allocation sampling 由 `android.heapprofd` 处理；
- Java live-object 引用图由 `android.java_hprof` 处理。

daemon 以 `nobody` 用户、`nobody readproc` 组运行，init socket 名为 `heapprofd`。它声明 `KILL` 和 `DAC_READ_SEARCH` capability；源码注释明确写着，SELinux 在 user build 上拒绝后一个 capability，因为相关权限只在 userdebug/eng 放行。user build 仍可分析合格的 App，目标资格由 manifest、会话发起者与 SELinux 共同限制。

### 2.2 从启动接入与运行中接入是两条路径

按进程名配置 session 后，heapprofd 会为后续启动的目标设置启动属性。Android App 从 Zygote fork 后，在 specialization 阶段启用 `libheapprofd_client`，安装分配 hook，再通过共享内存把抽样调用栈交给 daemon 远程 unwind。trace 中对应 `ProcessHeapSamples.from_startup = true`。

这条路径能覆盖 specialization 后到 profiling 结束之间的大部分分配，但 Perfetto 文档明确保留一个边界：specialization 早期已有少量分配发生在 hook 安装之前。heapprofd 不能声称覆盖“从 Zygote fork 第一条指令开始”的所有 native 分配。

按 PID 或进程名连接一个已运行进程时，producer 会发送 signal。目标在后续分配点装载 client，连接可能延后数百毫秒；空闲后突然发生的一小段 allocation burst 可能赶在 profiling 建立之前。启动分析应先建立 session，再启动目标进程。

## 3. user build 上的权限边界

### 3.1 shell 诊断与 trusted system 会话

`producer_support.cc::CanProfileAndroid()` 在 user build 上按 UID 和 session initiator 分流：

- shell/普通 Perfetto 会话的 initiator 为 `UNSPECIFIED`，普通 App 需要 `profileable_from_shell` 或 `debuggable`。
- `TRUSTED_SYSTEM` 会话可以分析标记为 `profileable` 或 `debuggable` 的普通 App。
- platform UID 只能由 trusted system 发起者分析。
- SDK sandbox UID 会映射回所属 App UID；isolated UID 无法可靠反查所属包，源码采用更保守的全包检查。
- `target_installed_by` 只有在配置显式填写时才参与过滤，可用特殊值包括 `@system`、`@product` 和 `@null`。

非 user build 在这层代码中直接放行，但 userdebug 仍有 `never_profile_heap` SELinux 目标限制。是否能抓到 profile，应同时检查 build type、目标 manifest、会话发起者和 SELinux；不能只看 heapprofd 进程是否存在。

下面的 manifest 片段用于允许 adb shell/Perfetto 对 release-like App 做受控 profiling。这个开关会增加可诊断面，应由安全和发布策略共同决定。

```xml
<manifest xmlns:android="http://schemas.android.com/apk/res/android">
    <application>
        <profileable android:shell="true" />
    </application>
</manifest>
```

`android:shell="true"` 不等于 `android:debuggable="true"`，也不会赋予 App 自身抓取其他进程的权限。启用后应在 retail build 上做一次空 profile 验证；空结果最常见的原因就是目标不满足 profileable/debuggable 条件。

### 3.2 面向真实用户的采集入口

API 35+ 的 `ProfilingManager.PROFILING_TYPE_HEAP_PROFILE` 是 App 面向真实用户设备请求 heap profile 的公开入口。系统负责限流，结果写入 App 私有目录并通过 `ProfilingResult` 返回文件路径；请求可能被延迟或拒绝，不能作为每次启动必采的硬依赖。

直接执行 `adb shell perfetto` 或 `tools/heap_profile` 适合实验室、CI、dogfood 和现场连接设备。规模化真实用户采集应使用 `ProfilingManager`/AndroidX 封装，遵守系统 rate limit、redaction、文件保留和用户数据政策。traced 不负责把 trace 自动上传到企业服务器；App 取得结果后才决定是否上传和何时删除。

## 4. 冷启动抓取：trace 要先于目标进程

### 4.1 一份最小且有效的 textproto

下面的 Perfetto textproto 只抓指定主进程的 startup native allocations。16 KiB 采样间隔用于降低诊断对启动的扰动，8 MiB 是 Android 17 源码中的默认 client/daemon shared-memory 大小；它们是起始配置，不是跨设备最佳值。

```protobuf
buffers {
  size_kb: 65536
  fill_policy: RING_BUFFER
}

data_sources {
  config {
    name: "android.heapprofd"
    target_buffer: 0
    heapprofd_config {
      process_cmdline: "com.example.app"
      sampling_interval_bytes: 16384
      shmem_size_bytes: 8388608
      no_running: true
      block_client: false
      continuous_dump_config {
        dump_phase_ms: 5000
        dump_interval_ms: 5000
      }
    }
  }
}

duration_ms: 30000
```

`no_running: true` 排除启动 trace 前已经存在的进程，只匹配会话建立后启动的目标。`process_cmdline` 可以出现多次；多进程 App 应明确写出 `com.example.app`、`com.example.app:remote` 等目标，避免用 `all: true` 扩大范围。

`all: true` 在未修改的 userdebug build 上可能让 Zygote 带着意外的 heapprofd socket fork，proto 注释直接警告会造成系统崩溃。生产和日常调试都应使用进程名/PID allowlist。

### 4.2 推荐使用 `tools/heap_profile`

Perfetto 官方文档把 `tools/heap_profile` 作为推荐入口，因为它负责生成配置、运行会话、拉取 raw trace、转换 profile，并可接入本地符号。下面的命令用于准备一次只接入新进程的 30 秒采集；命令会保持运行，等待另一个终端启动 App。

```bash
adb shell am force-stop com.example.app

tools/heap_profile android \
  -n com.example.app \
  -d 30000 \
  -i 16384 \
  -c 5000 \
  --no-running \
  --no-block-client
```

脚本的 duration 单位是 ms，interval 单位是 bytes，continuous dump 单位也是 ms。这里显式使用 `--no-block-client`：buffer 满时 profile 提前结束，目标 App 不会为了等待 profiler 空间而阻塞。脚本默认会启用 block-client；那种模式更重视采集完整性，会显著拖慢被测进程，不适合拿同一次运行判断启动耗时。

当第一个终端已经建立 profiling session 后，在第二个终端启动目标 Activity。下面的命令只负责制造一次可重复的冷启动入口，组件名应替换为被测 App 的真实 launcher Activity。

```bash
adb shell am start -W \
  -n com.example.app/.MainActivity
```

第一个终端结束后，输出目录中的 `raw-trace` 可直接在 Perfetto UI 打开。若 profile 为空，依次检查 App 是否 profileable、进程名是否匹配、是否已有并发 heapprofd session，以及 target 是否在 session 建立后启动。

### 4.3 heapprofd 运行不能兼任性能基线

heapprofd 会在目标进程安装 allocator hook、执行抽样、复制寄存器/栈数据并通过 shared memory 发送；daemon 还要远程 unwind 和写 trace。sampling interval、buffer 策略、符号信息和 workload 都会改变额外成本。

启动优化要分两轮验证：

1. 无 heapprofd 的 Macrobenchmark/Perfetto run 用于计算 TTID、TTFD、帧 deadline 和 CPU 调度基线。
2. heapprofd run 用于解释分配调用栈、未释放 native allocation 和 churn。

把 profiling run 的启动时长直接与普通 run 比较，会把观测开销算进业务回归。

## 5. 采样、buffer 与 guardrail

### 5.1 sampling interval

Android 17 的 `tools/heap_profile` 默认 interval 是 4096 bytes。heapprofd 使用与分配大小相关的随机抽样，并按概率放大样本权重；interval 越小，样本越密、统计误差通常越小，目标和 daemon 的 CPU/内存成本也越高。interval 为 1 接近逐次记录，开销很大。

出现 buffer overrun 时有两条修复路线：

- allocation spike 很短，可增大 `shmem_size_bytes`；
- 持续分配速率超过 daemon 处理能力，可把 interval 提高到 16 KiB 或更大，接受较低精度。

shared-memory 默认 8 MiB，配置值至少 8192 bytes，同时必须是 4096 的整数倍和 2 的幂；超过 500 MiB 会被截断。字段名是 `shmem_size_bytes`，不是 `shared_memory_buffer_size_kb`。

### 5.2 block-client

`block_client: true` 在 buffer 满时等待空间，可以保住更多数据，却会直接拖慢发生分配的线程。`block_client: false` 让会话在 overrun 时结束，保留 App 行为的可解释性。两种模式解决的目标不同：

- 分配正确性实验可以接受有限阻塞，但结果不能用于 latency KPI。
- 启动/帧时间相关调查优先不阻塞，并通过增大 interval、缩短窗口或扩大 buffer 降低 overrun。

### 5.3 daemon guardrail

`max_heapprofd_memory_kb` 和 `max_heapprofd_cpu_secs` 限制的是 heapprofd data source 自身。Android 17 实现分别读取 daemon 的 `RssAnon + VmSwap`，以及从 data source 开始后的 `utime + stime`；超过限制后停止 profiling。检查任务以 30 秒周期运行，所以很短的启动会话不能把 guardrail 当作精确的实时熔断器。

阈值应从目标设备的空载、启动 workload、采样 interval 和并发数据源测试中得出。固定写成 256 MiB、CPU 若干秒或分配增长 15%，都缺少跨设备依据。

### 5.4 continuous dump

continuous dump 会在时间轴上生成多个 diamond。每个快照是从 profiling 开始到该时间点的累计结果，适合比较“首帧前、首帧后、进入稳定页后”的变化。dump 间隔越短，trace 和处理成本越高；启动阶段通常只需要少量边界快照。

也可以在 userdebug 实验中向 heapprofd 发送 `SIGUSR1` 生成一次额外 dump。retail user build 和真实用户采集不要依赖这个 shell 操作。

## 6. 正确读取 flamegraph 和 SQL

Perfetto UI 对 native heap profile 提供四个常用视图：

- Unreleased malloc size：从 profiling 开始到快照时仍未 free 的抽样字节。
- Total malloc size：期间所有抽样分配字节，包括后来已经 free 的部分。
- Unreleased malloc count：快照时仍未 free 的抽样分配数量。
- Total malloc count：期间所有抽样分配次数。

看泄漏倾向时优先比较同一进程、同一业务状态下的 unreleased size/count；看 churn 时比较 total size/count。一次冷启动结束后进程随即退出，所有进程内分配都会消失，不能把两个不同 PID 的 total allocation 差值直接称为“泄漏”。

`heap_profile_allocation` 中正 `size/count` 表示分配，负值表示对应 free。它的 `ts` 是 dump profiling window 的结束时间，同一批 allocation/free 会共用这个时间戳，不是每次 `malloc()` 的发生时间。原稿用 `a.ts < MIN(ts) + 10s` 截取“启动前 10 秒”的 SQL 口径不成立。要划分启动阶段，应在目标边界生成 dump，或把 heap snapshot 与同一 trace 中的启动 marker 对齐。

下面的 PerfettoSQL 用 Android 17 已内置的 standard library 递归展开 callsite，输出未释放与总分配两组累计值。它适合单目标 profile；该 summary table 会把 trace 中所有进程合并，多目标 trace 应改用带 `upid` 的原始表。

```sql
INCLUDE PERFETTO MODULE android.memory.heap_profile.summary_tree;

SELECT
  name,
  mapping_name,
  self_size,
  cumulative_size,
  self_alloc_size,
  cumulative_alloc_size
FROM android_heap_profile_summary_tree
ORDER BY ABS(cumulative_alloc_size) DESC
LIMIT 30;
```

`cumulative_size` 表示该 frame 出现在调用栈任意位置时对应的未释放抽样字节，`cumulative_alloc_size` 包含后来已经释放的总分配。二者同时偏高时既有 retained growth 也有 churn；只有 total 很高而 unreleased 较低时，更像短命分配密集。

## 7. 符号、混合栈与误判

### 7.1 符号必须按 Build ID 匹配

release so 常被 strip。`tools/heap_profile`、`traceconv` 和 Trace Processor 可以通过 `PERFETTO_BINARY_PATH` 查找带符号 ELF，并按 Build ID 匹配。文件名相同但 Build ID 不同的符号会给出错误或缺失结果；CI 应保存每个 versionCode/ABI 对应的 native symbols。

Java/Kotlin allocation sampling 若遇到混淆，可用 `PERFETTO_PROGUARD_MAP` 提供包名到 mapping 文件的映射。包含 `[DEDUPED]` 的 Java frame 以及启用 ICF 后别名相同的 native 函数都可能让函数名与源码直觉不一致，判断时要回到 mapping、Build ID、相邻 frame 和构建配置。

### 7.2 heapprofd、malloc_info 与 RSS 不会相等

heapprofd 聚合的是 profiling 窗口内的 sampled allocations/frees；`malloc_info` 还可能看到 allocator 保留的 thread cache；RSS/PSS 还包含页粒度、fragmentation、文件映射和其他内存类别。排障时可以用三者回答不同问题：

- heapprofd 高：找调用栈和对象生命周期。
- malloc_info 明显高于 heapprofd：检查 profiling 前分配、thread cache 和 hook 覆盖。
- RSS/PSS 明显高于 allocator 数据：检查映射、图形内存、ashmem/memfd、页表、fragmentation 与 swap。

## 8. 生产采集的安全与运维边界

heap profile 包含函数名、so/apk/jar mapping、Build ID、调用栈、线程和进程信息。它通常不包含业务 payload，但足以暴露代码结构、第三方 SDK 和版本细节。真实用户采集至少要具备：

- 明确的采样触发条件和低频 rate limit，失败时不影响启动主路径；
- 使用 `ProfilingManager` 生成的 redacted result，避免自行扩大 system trace 范围；
- trace 文件只写 App 私有目录，上传使用鉴权和传输加密；
- 服务端按版本、ABI、Build ID 保存受控符号，原始 trace 设定短保留期；
- 上传成功、过期或用户撤回同意后删除本地文件；
- 指标报告按设备档位、构建版本和场景分组，公开采样数与置信区间。

heapprofd 不提供 MDM 配置分发、服务器上传、告警阈值或数据脱敏方案。那些属于 App/企业诊断系统的职责，需要单独设计权限、同意、网络和删除策略。

## 9. 一套可执行的启动调查顺序

1. 用无 profiler 的 Macrobenchmark 建立冷启动分位值和 trace 基线。
2. 判断问题是否与 native heap、Java allocation churn、Java retention 或 RSS 相关，选对数据源。
3. retail build 先核对 profileable 和会话入口；实验室 run force-stop 目标 App。
4. 先启动按进程名匹配、`no_running` 的 heapprofd session，再启动 App。
5. 从 16 KiB 或更稀疏 interval 起步；无 overrun 且信号不足时再降低 interval。
6. Perfetto UI 先比较 total 与 unreleased，再用 summary tree 找完整调用栈。
7. 用正确 Build ID 的符号回填函数名，检查 DEDUPED/ICF 造成的别名。
8. 修复后分别重复无 profiler 的性能 run 和有 profiler 的分配 run。
9. 真实用户样本只通过 `ProfilingManager` 受控采集，处理 rate limit、redaction、上传和删除。
