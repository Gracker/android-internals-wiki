# 8.39 Android 17 heapprofd 生产环境部署

> 本章聚焦 **启动阶段** heapprofd 部署的特定挑战与方案。heapprofd 通用架构与权限模型的完整论述详见 §14.1，本节仅引用结论并补充启动场景的差异。

## 要点

### 🔹 heapprofd 架构演进与启动场景定位

heapprofd 是 Perfetto 框架下的用户态堆分析守护进程，在 Android 12 引入后持续演进。Android 17（API 37，`android-17.0.0_r1`）中 heapprofd 采用 **双 Producer 并行架构**：

- **Native Producer**：占用信号 `__SIGRTMIN + 4`，通过 `android.heapprofd` 数据源处理 native 堆抓取
- **Java Producer**：占用信号 `__SIGRTMIN + 6`，通过 `android.java_hprof` 数据源处理 Java 堆抓取

两个 Producer 共享同一进程空间（`/system/bin/heapprofd`），但通过独立信号通道区分职责，避免相互干扰。

[已验证: AOSP android-17.0.0_r1, `external/perfetto/src/profiling/memory/heapprofd.cc:89`]

**启动场景的特殊性**：heapprofd 默认以 `disabled` 状态注册为 `late_start` 服务，需通过属性触发才启动。这意味着在系统启动（boot）阶段 heapprofd 并不运行，只有在 `persist.heapprofd.enable=1` 或应用通过 Perfetto 配置主动请求时才激活。对于 **应用启动优化** 场景，这种延迟激活机制带来一个核心矛盾：

- heapprofd 激活前分配的内存不会被记录 → 启动初期的关键分配可能丢失
- 在 zygote fork 前激活 heapprofd 可能导致系统崩溃（详见 §扩展）

`heapprofd.rc` 关键配置：

```ini
service heapprofd /system/bin/heapprofd
    class late_start
    disabled
    user nobody
    group nobody readproc
    capabilities KILL DAC_READ_SEARCH
    onrestart exec_background - nobody shell -- /system/bin/heapprofd --cleanup-after-crash
```

- **`class late_start`**：在主启动流程之后才触发，不影响系统启动速度
- **`disabled`**：默认不启动，需属性触发
- **`capabilities DAC_READ_SEARCH`**：仅 userdebug/eng 构建可用，user 构建无此权限
- **`--cleanup-after-crash`**：crash 后自动清理残留 socket 文件

[已验证: AOSP android-17.0.0_r1, `external/perfetto/heapprofd.rc`]

> ⚠️ heapprofd 的通用架构、双 Producer 通信机制、信号处理链路的完整分析详见 §14.1。本节后续聚焦启动部署的差异部分。

### 🔹 生产部署配置（启动优化视角）

#### 白名单模式：启动场景的唯一安全选项

`all=true` 配置在未修改的 userdebug 构建上会触发 **zygote 启动崩溃**——每个新进程 fork 后遇到意外的 heapprofd socket，导致系统无法正常启动。Perfetto 配置 proto 注释明确警告：

```protobuf
// WARNING: Using `all=true` on an unmodified userdebug build will cause the system
// to crash during zygote startup (a new process encounters an unexpected heapprofd socket).
// Only use `all=true` in production if you have modified the zygote to handle this.
```

[已验证: AOSP android-17.0.0_r1, `external/perfetto/protos/perfetto/config/profiling/heapprofd_config.proto`]

**启动阶段的正确配置**是使用 `process_cmdline` 白名单模式，精确指定目标应用包名：

```protobuf
data_sources {
  data_source: "android.heapprofd"
  target_buffer: 0
  config {
    heapprofd_config {
      process_cmdline: "com.example.app"
      sampling_interval_bytes: 4096     # 4KB 采样间隔
      shared_memory_buffer_size_kb: 8192 # 8MB 共享内存
      idle_allocations: true             # 记录空闲分配
    }
  }
}
```

启动场景采样策略建议：
| 场景 | `sampling_interval_bytes` | 理由 |
|------|--------------------------|------|
| 冷启动内存画像 | 4096 (4KB) | 启动阶段分配量大，4KB 粒度足够识别热点 |
| Native 泄漏排查 | 1024 (1KB) | 小泄漏通常在低频分配路径，需更细粒度 |
| 长期运行监控 | 65536 (64KB) | 降低运行时开销，仅捕获大额分配 |

#### 连接退避机制

heapprofd 客户端连接失败时采用 **指数退避策略**，避免在系统高负载（如启动阶段）下雪崩：

- 初始延迟：`kInitialConnectionBackoffMs = 100ms`
- 最大延迟：`kMaxConnectionBackbackMs = 30000ms`（30 秒）
- 倍增策略：每次失败后等待时间翻倍

[已验证: AOSP android-17.0.0_r1, `external/perfetto/src/profiling/memory/java_hprof_producer.cc`]

#### 连续 Dump 与 PID 重扫

Android 13+（含 Android 17）默认行为变更：`scan_pids_only_on_start = false`，即每次 dump 都重新扫描 `/proc` 目录发现新进程。对于启动场景意义重大——新 fork 的子进程（如启动时创建的渲染进程、GPU 进程）能在下一次 dump 周期自动纳入监控，无需重启 trace 会话。

```cpp
void JavaHprofProducer::DoContinuousDump(DataSourceInstanceID id, uint32_t dump_interval) {
  DataSource& ds = data_sources_[id];
  if (!ds.config().continuous_dump_config().scan_pids_only_on_start()) {
    ds.CollectPids();  // Android 13+ 默认：每次 dump 重扫 /proc
  }
  ds.SendSignal();
  task_runner_->PostDelayedTask([...]{ DoContinuousDump(id, dump_interval); }, dump_interval);
}
```

[已验证: AOSP android-17.0.0_r1, `external/perfetto/src/profiling/memory/java_hprof_producer.cc:DoContinuousDump()`]

版本差异速查：
| Android 版本 | `scan_pids_only_on_start` 默认 | `process_cmdline` 通配符 | `target_installed_by` |
|---|---|---|---|
| 11 (API 30) - | true | 精确匹配 | 不支持 |
| 12 (API 31) | true | 精确匹配 | 支持 |
| 13 (API 33) + | **false** | 支持 `*` 通配 | 支持 |
| 14-17 (API 34-37) | false | 通配行为扩展 | 支持 |

### 🔹 性能监控指标（启动阶段关键指标）

#### 启动期内存分配热点识别

heapprofd 采样数据通过 Perfetto trace 导出后，可用 SQL 查询启动阶段 Top-N 分配调用栈：

```sql
-- 启动阶段（前 10 秒）Top-20 内存分配调用栈
SELECT
  f.name AS function,
  m.mapping_name AS library,
  SUM(a.size) AS total_allocated,
  COUNT(*) AS alloc_count
FROM heap_profile_allocation a
JOIN stack_profile_frame f ON a.callstack_id IN (
  SELECT id FROM stack_profile_callstack cs
  WHERE cs.depth > 0
)
JOIN stack_profile_mapping m ON f.mapping_id = m.id
WHERE a.ts < (
  SELECT MIN(ts) + 10000000000  -- 10 秒（纳秒）
  FROM heap_profile_allocation
)
GROUP BY function, library
ORDER BY total_allocated DESC
LIMIT 20;
```

启动阶段常见热点：
1. **资源加载**：`LayoutInflater.inflate()` 链路中的 Bitmap 分配
2. **类初始化**：`Class.forName()` 触发的 static 字段分配
3. **第三方 SDK**：广告/统计 SDK init 中的 native so 加载与内部分配
4. **ART runtime**：GC 卡表、IC（Inline Cache）分配

#### 内存泄漏检测：启动 → 退出循环

利用 heapprofd 的 `continuous_dump` 机制，在应用完整生命周期（冷启动 → 使用 → 退出 → 再次冷启动）中持续采样，对比两次启动间的 native 堆增长：

```sql
-- 第二次启动比第一次启动多出的分配（潜在泄漏）
WITH first_run AS (
  SELECT callsite_id, SUM(size) AS size1
  FROM heap_profile_allocation
  WHERE ts < 30000000000  -- 前 30s
  GROUP BY callsite_id
),
second_run AS (
  SELECT callsite_id, SUM(size) AS size2
  FROM heap_profile_allocation
  WHERE ts >= 30000000000  -- 30s 后
  GROUP BY callsite_id
)
SELECT s.callsite_id, s.size2 - COALESCE(f.size1, 0) AS growth
FROM second_run s
LEFT JOIN first_run f ON s.callsite_id = f.callsite_id
WHERE s.size2 - COALESCE(f.size1, 0) > 102400  -- 增长 >100KB
ORDER BY growth DESC;
```

#### 内存使用模式分析

Perfetto UI 的 `heap_profile.flamegraph` 视图提供三种分析维度：
- **Bytes**：按分配字节数聚合，识别内存大户
- **Allocs**：按分配次数聚合，识别 churn（频繁分配/释放）
- **RSS contribution**：按实际物理内存占用聚合，识别碎片化问题

[结构参考: Clippings/Android 性能优化 - 原理：掌握 App 运行时的内存模型]

### 🔹 权限与安全

#### 三层权限模型

Android 17 heapprofd 采用三层权限校验，`ProducerSupport::CanProfile()` 按顺序检查：

1. **UID 范围限制**：仅允许 `AID_APP`（10000）至 `AID_ISOLATED`（99999）范围的 UID
2. **安装者过滤**：校验 `installed_by` 字段，仅允许 `@system`、`@product`、`@null`
3. **TRUSTED_SYSTEM 绕过**：`SESSION_INITIATOR_TRUSTED_SYSTEM` 类型的会话发起者直接通过

[已验证: AOSP android-17.0.0_r1, `external/perfetto/src/profiling/common/producer_support.cc:CanProfile()`]

#### packages.list 安全校验

heapprofd 通过解析 `/data/system/packages.list` 获取应用的安全属性：

```
# packages.list 字段格式（tab 分隔）
# 0:name  1:uid  2:debuggable  6:profileable_from_shell  8:profileable  9:installed_by
com.example.app  10042  0  ...  0  ...  1  ...  @system
```

关键字段与 `ApplicationInfo` 的对应：
- `profileable_from_shell` → `PRIVATE_FLAG_PROFILEABLE_BY_SHELL = 1 << 23`
- `profileable` → `PRIVATE_FLAG_EXT_PROFILEABLE = 1 << 0`

[已验证: AOSP android-17.0.0_r1, `external/perfetto/src/traced/probes/packages_list/packages_list_parser.cc:ReadPackagesListLine()`]

#### SELinux 策略要点

- **userdebug/eng 构建**：heapprofd 具有 `DAC_READ_SEARCH` capability，可读取 `/proc/<pid>/maps` 和 `/proc/<pid>/mem`
- **user 构建**：heapprofd 受限，仅可通过 `profileable` manifest flag 的应用使用
- 生产环境部署需确保 SELinux 策略不阻止 heapprofd 访问 `/proc` 文件系统

> heapprofd 完整权限模型分析详见 §14.1 和 §26.24。

## 扩展

### 🔸 资源守护机制（Guardrails）

heapprofd 内置内存和 CPU 守护机制，防止 profiling 自身耗尽系统资源：

```cpp
// 内存检查：读取 /proc/self/status 的 RssAnon + Swap
void ProfilerGuardrails::CheckMemoryLimit() {
  uint64_t rss_anon_kb = ParseStatusFile("/proc/self/status", "RssAnon");
  uint64_t swap_kb = ParseStatusFile("/proc/self/status", "VmSwap");
  if (rss_anon_kb + swap_kb > max_memory_limit_kb_) {
    return false;  // 超限，停止 profiling
  }
  return true;
}

// CPU 检查：读取 /proc/self/stat 的 utime + stime
void ProfilerGuardrails::CheckCpuLimit() {
  uint64_t total_time_ns = (utime + stime) * user_hz_;
  if (total_time_ns > max_cpu_limit_ns_) {
    return false;
  }
  return true;
}
```

[已验证: AOSP android-17.0.0_r1, `external/perfetto/src/profiling/common/profiler_guardrails.cc`]

可通过 Perfetto 配置设置限制：
- `max_heapprofd_memory_kb`：heapprofd 进程最大内存使用
- `max_heapprofd_cpu_secs`：heapprofd 进程最大 CPU 时间

启动场景建议保守设置（如 `max_heapprofd_memory_kb: 262144` 即 256MB），避免在启动高负载时 heapprofd 自身竞争资源。

### 🔸 大规模部署与容器化

企业级多设备部署的架构要点：

1. **配置下发**：通过 MDM/EMM 系统推送 Perfetto 配置到目标设备
2. **数据回收**：trace 文件通过 `traced` 的 IPC 上报到集中服务器
3. **数据聚合**：使用 TraceProcessor 批量解析，提取启动内存分配指标
4. **隐私脱敏**：heapprofd 采样数据包含调用栈地址，需脱敏处理后上传

[待补充: 具体企业部署 MDM 集成方案细节]

### 🔸 内存使用模式优化建议

基于 heapprofd 启动分析数据的优化路径：

1. **延迟初始化**：将非关键路径的 native 分配推迟到启动完成后
2. **池化复用**：对高频分配/释放的对象使用内存池（详见 §23.6 Native 内存优化实战）
3. **so 优化**：识别启动阶段加载但不使用的 so 库，延迟 dlopen
4. **Bitmap 归一化**：启动阶段多个 Bitmap 合并为 atlas，减少单个分配次数

[结构参考: Clippings/Android 性能优化 - Native 内存优化（上）：so 库申请的内存优化]
