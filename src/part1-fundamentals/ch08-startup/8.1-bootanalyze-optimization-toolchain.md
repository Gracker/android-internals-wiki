# 8.1 Android 17 系统启动优化与 bootanalyze 工具链

> **版本边界**：本节基于 Android 17 (API 37) 源码验证 [已验证: AOSP android-17.0.0_r1]

## 1. bootanalyze 工具链架构

bootanalyze 是 AOSP 内置的启动性能分析工具，位于 `system/extras/boottime_tools/bootanalyze/`，核心是一个 1382 行的 Python 3 脚本，配合 bash 包装脚本 `bootanalyze.sh` 和 YAML 配置文件使用。

[已验证: AOSP android-17.0.0_r1, system/extras/boottime_tools/bootanalyze/bootanalyze.py]

### 1.1 工具链组成

| 文件 | 行数 | 功能 |
|------|------|------|
| `bootanalyze.py` | 1382 | 主脚本，负责事件采集、正则匹配、时间校正、报告生成 |
| `bootanalyze.sh` | — | bash 包装，设置 Python 环境并调用主脚本 |
| `config.yaml` | — | 事件正则定义、时间校正键配置 |
| `README.md` | — | 使用文档（⚠️ 存在文档漂移，仍写 Python 2.7 依赖，实际已迁移到 Python 3） |

> ⚠️ **文档漂移**：bootanalyze.py 第 1 行 shebang 为 `#!/usr/bin/python3`，但 README.md 仍声称"Only works on Linux with Python 2.7"。这是 AOSP 文档与代码不一致的典型案例。

[已验证: AOSP android-17.0.0_r1, bootanalyze.py line 1 vs README.md]

### 1.2 三类事件模型

bootanalyze 从 `config.yaml` 加载三类事件规则，通过 `re.compile()` 编译为正则匹配器：

```python
# bootanalyze.py line 117-127
search_events_pattern = {
    key: re.compile(pattern)
    for key, pattern in cfg['events'].items()
}
timing_events_pattern = {
    key: re.compile(pattern)
    for key, pattern in cfg['timings'].items()
}
shutdown_events_pattern = {
    key: re.compile(pattern)
    for key, pattern in cfg['shutdown_events'].items()
}
```

- **events（单点事件）**：布尔匹配，记录事件发生的时间戳。如 `apexd_ready`、`zygote_preload_end`
- **timings（阶段耗时）**：使用 `(?P<name>...)` 命名捕获组抽取子阶段名。如 `SystemServerTiming: PhaseX took to complete: 123ms`
- **shutdown_events（关机事件）**：在 reboot 触发后捕获前一次启动的关机事件

[已验证: AOSP android-17.0.0_r1, bootanalyze.py line 117-127]

### 1.3 config.yaml 的关键事件定义

```yaml
# Zygote preload 4 阶段事件
events:
  zygote_preload_start: Zygote\s*:\s*begin preload
  zygote_preload_classes_start: Zygote\s*:\s*Preloading classes...
  zygote_preload_res_start: Zygote\s*:\s*Preloading resources...
  zygote_preload_end: Zygote\s*:\s*end preload

  # APEX 启动 3 阶段事件
  apexd_activated: apexd.*Marking APEXd as activated
  apexd_bootstrapping_done: apexd.*Bootstrapping done
  apexd_ready: apexd.*Marking APEXd as ready
```

**关键发现**：
- ZygoteInit.java 中 `"begin preload"` 和 `"end preload"` 日志是 bootanalyze 的**采集契约**，修改这些日志字符串会破坏启动分析
- APEX 有三个独立追踪事件，覆盖从 bootstrap 到 ready 的完整生命周期
- **没有 lazy preload 对应的事件名**——lazy preload 在 fork 前完成，日志与正常 preload 共用

[已验证: AOSP android-17.0.0_r1, config.yaml + ZygoteInit.java line 129/173]

### 1.4 停止事件链表

bootanalyze 定义了多场景停止事件（line 425-432），默认使用 `BootComplete`：

```python
_LOGCAT_BOOT_COMPLETE = "BootComplete"  # 默认
# 可选追加：
# FsStat、_CARWATCHDOG_BOOT_COMPLETE（车机）、_LOGIN_END、_LAUNCHER_SHOWN
```

这意味着 bootanalyze **不只关注 boot complete**，原生支持车机 CarWatchdog、登录场景、Launcher 显示三类扩展场景。

[已验证: AOSP android-17.0.0_r1, bootanalyze.py line 41-43, 425-432]

## 2. 双源时间校正算法

启动早期内核时钟可能未校准，同一事件在 logcat 和 dmesg 中的时间戳不一致。bootanalyze 通过双源校正机制解决这个问题。

### 2.1 校正逻辑

```python
# bootanalyze.py line 444-498 核心逻辑
# 同一事件若在 logcat 与 dmesg 都有 → 以 dmesg 时间为准
# 其他事件 → 以 time_correction_delta 补偿时钟漂移
```

校正流程：
1. 识别同时在 logcat 和 dmesg 中出现的事件作为**锚点**
2. 计算两个源之间的时间差 `time_correction_delta`
3. 对只在单源出现的事件，用 delta 补偿到统一时间轴

### 2.2 Perfetto Login Trace 支持

bootanalyze 原生支持 Perfetto login trace 采集（line 56-58）：

```python
_PERFETTO_LOGIN_CONFIG = "/data/misc/perfetto-configs/perfetto-login.textproto"
_PERFETTO_LOGIN_TRACE = "/data/misc/perfetto-traces/perfetto-login.perfetto-trace"
```

这与 boot time 文档中的"systrace/ftrace"路线互补——Perfetto trace 提供函数级粒度，bootanalyze 提供事件级粒度。

[已验证: AOSP android-17.0.0_r1, bootanalyze.py line 56-58]

## 3. bootstat 事件体系

bootstat 是 bootanalyze 的底层数据源，位于 `system/core/bootstat/bootstat.cpp`（1648 行），提供 25+ 个 boot event 的记录和聚合能力。

### 3.1 事件分类

| 类型 | 数量 | 示例 |
|------|------|------|
| **ELAPSED_TIME** | 10+ | `boot_complete`, `boot_complete_no_encryption`, `ota_boot_complete`, `ro.boottime.event.zygote-start` |
| **DURATION** | 10 | `absolute_boot_time`, `boottime.bootloader.1BLE/1BLL/KL/2BLE/2BLL/SW/splash/total`, `boottime.init.cold_boot_wait` |
| **UTC_TIME** | 1 | `last_boot_time_utc` |
| **ERROR_CODE** | 若干 | factory reset / ota 异常码 |

[已验证: AOSP android-17.0.0_r1, bootstat.cpp line 95-175]

### 3.2 init rc 阶段自动记录

`RecordInitBootTimeProp()` 在启动过程中被调用 11 次（bootstat.cpp line 1412-1423），自动记录 14 个 init rc 阶段：

```
init.first_stage, init.selinux, init.cold_boot_wait,
event.early-init, event.init, event.late-init,
event.early-fs, event.fs, event.post-fs, event.late-fs,
event.post-fs-data, event.zygote-start, event.early-boot, event.boot
```

### 3.3 Bootloader 时间契约

`boottime.bootloader.*` 共 8 个细分阶段，通过 `GetBootLoaderTimings()` 从 `ro.boot.bootloader` 属性解析：

| 字段 | 含义 |
|------|------|
| 1BLE | First Stage Exec |
| 1BLL | First Stage Load |
| KL | Kernel Load |
| 2BLE | Second Stage Exec |
| 2BLL | Second Stage Load |
| SW | UI Wait |
| splash | Splash Screen |
| total | 总计 |

这是 Pixel 等 OEM bootloader **必须填充的契约**——不写入这些属性值，bootstat 就无法采集 bootloader 阶段耗时。

[已验证: AOSP android-17.0.0_r1, bootstat.cpp line 1200+]

### 3.4 事件时间基准

boot event 使用 **uptime 而非 wall clock** 记录（bootstat.cpp line 1301-1310 注释），原因：
- 设备早期时间未校准（NTP 尚未同步）
- uptime 不受时区/用户修改影响
- 跨设备聚合必须带 build fingerprint + 启动原因 + userdebug 标志

## 4. init 动作队列执行模型

### 4.1 单线程串行执行

Android 17 的 init 进程采用**单线程动作队列模型**，没有并行执行机制。

```cpp
// init.cpp line 1295-1347
while (true) {
    if (!(prop_waiter_state.MightBeWaiting() || Service::is_exec_service_running())) {
        am.ExecuteOneCommand();  // 每次只执行一个命令
        if (am.HasMoreCommands()) {
            next_action_time = boot_clock::now();
        }
    }
}
```

`ExecuteOneCommand()` 确保每次只执行一个命令，整个启动路径严格串行。

[已验证: AOSP android-17.0.0_r1, init/init.cpp line 1295-1347]

### 4.2 Service Class 启动顺序

```cpp
// builtins.cpp line 167
static Result<void> do_class_start(const BuiltinArguments& args) {
    if (android::base::GetBoolProperty(
            "persist.init.dont_start_class." + args[1], false))
        return {};
    for (const auto& service : ServiceList::GetInstance()) {
        if (service->classnames().count(args[1])) {
            service->StartIfNotDisabled();
        }
    }
    return {};
}
```

启动顺序按 class name 分组：
1. **class main** — 核心服务（zygote, servicemanager 等）
2. **class core** — 基础系统服务
3. **class early_hal** — 早期 HAL
4. **class late_hal** — 晚期 HAL

> `persist.init.dont_start_class.<name>` 属性可在运行时禁用特定 class，用于调试和测试。

[已验证: AOSP android-17.0.0_r1, init/builtins.cpp line 167]

### 4.3 init.rc 执行阶段

```
early-init → init → early-fs → fs → post-fs → late-fs
→ post-fs-data → zygote-start → early-boot → boot
```

Android 17 较 Android 16 的变化：
- **移除**：`TestPerfEventSelinuxAction`、`SetKptrRestrictAction`
- **新增**：`ConnectEarlyStageSnapuserdAction`、`SetCopyRollbackLogsAction`
- **核心执行机制不变**：单线程动作队列

[已验证: AOSP android-17.0.0_r1, system/core/rootdir/init.rc]
[来源: DeepResearch/2026-07-02-android-17-boot-execution-model.md]

## 5. Zygote 延迟预加载机制

### 5.1 --enable-lazy-preload 参数

Android 17 在 ZygoteInit.java 中引入 `--enable-lazy-preload` 命令行参数（line 854-898）：

```java
boolean enableLazyPreload = false;
for (int i = 1; i < argv.length; i++) {
    if ("start-system-server".equals(argv[i])) {
        startSystemServer = true;
    } else if ("--enable-lazy-preload".equals(argv[i])) {
        enableLazyPreload = true;
    }
    // ...
}

if (!enableLazyPreload) {
    bootTimingsTraceLog.traceBegin("ZygotePreload");
    EventLog.writeEvent(LOG_BOOT_PROGRESS_PRELOAD_START, SystemClock.uptimeMillis());
    preload(bootTimingsTraceLog);
    EventLog.writeEvent(LOG_BOOT_PROGRESS_PRELOAD_END, SystemClock.uptimeMillis());
    bootTimingsTraceLog.traceEnd();
}
```

由 init.rc 启动 Zygote 时传入，是 AOSP 主线支持，非厂商私有。

[已验证: AOSP android-17.0.0_r1, ZygoteInit.java line 854-898]

### 5.2 lazyPreload() 实现

```java
// ZygoteInit.java line 178-183
static void lazyPreload() {
    Preconditions.checkState(!sPreloadComplete);
    Log.i(TAG, "Lazily preloading resources.");
    preload(new TimingsTraceLog("ZygoteInitTiming_lazy", Trace.TRACE_TAG_DALVIK));
}
```

**关键设计**：lazy preload 是"延后而非拆分"——`lazyPreload()` 仍然调用完整的 9 步 `preload()`，只是执行时机从 Zygote 启动期推到首次 fork 前。使用独立的 trace tag `ZygoteInitTiming_lazy`，便于在 Perfetto 中区分。

### 5.3 preload() 9 步链路

```java
// ZygoteInit.java line 128-176
static void preload(TimingsTraceLog bootTimingsTraceLog) {
    Log.d(TAG, "begin preload");                    // bootanalyze 契约: zygote_preload_start
    bootTimingsTraceLog.traceBegin("BeginPreload");
    beginPreload();
    bootTimingsTraceLog.traceEnd();

    bootTimingsTraceLog.traceBegin("PreloadClasses");
    preloadClasses();                                // 预加载 classes.txt
    bootTimingsTraceLog.traceEnd();

    bootTimingsTraceLog.traceBegin("CacheNonBootClasspathClassLoaders");
    cacheNonBootClasspathClassLoaders();
    bootTimingsTraceLog.traceEnd();

    bootTimingsTraceLog.traceBegin("PreloadResources");
    Resources.preloadResources();
    bootTimingsTraceLog.traceEnd();

    Trace.traceBegin(Trace.TRACE_TAG_DALVIK, "PreloadAppProcessHALs");
    nativePreloadAppProcessHALs();
    Trace.traceEnd(Trace.TRACE_TAG_DALVIK);

    Trace.traceBegin(Trace.TRACE_TAG_DALVIK, "PreloadGraphicsDriver");
    maybePreloadGraphicsDriver();
    Trace.traceEnd(Trace.TRACE_TAG_DALVIK);

    preloadSharedLibraries();
    preloadTextResources();
    preloadCompatConfig();

    // Android 17 新增：HttpEngine.preload() (25Q2 flag, b/206676167)
    if (preloadHttpengineInZygote()) {
        try { HttpEngine.preload(); } catch (NoSuchMethodError e) { /* ... */ }
    }

    WebViewFactory.prepareWebViewInZygote();
    endPreload();
    warmUpJcaProviders();
    Log.d(TAG, "end preload");                       // bootanalyze 契约: zygote_preload_end
    sPreloadComplete = true;
}
```

[已验证: AOSP android-17.0.0_r1, ZygoteInit.java line 128-176]

### 5.4 工程取舍

| 维度 | 收益 | 代价 |
|------|------|------|
| 启动时间 | Zygote 启动期峰值内存降低，缩短 `sys.boot_completed` | — |
| 首次应用冷启动 | — | 增加 5-10ms（需先完成完整 preload） |
| 可观测性 | `ZygoteInitTiming_lazy` trace tag 独立识别 | — |
| 适用场景 | 车机（启动时间敏感）、低端设备（内存受限） | 桌面/高性能设备（首次冷启动延迟更敏感） |

> lazy preload **不是免费午餐**——它把开销从启动期转移到首次 fork 前。需要根据产品场景选择是否启用。

[来源: DeepResearch/2026-06-28-android17-bootanalyze-zsygotelazy-sourcepath-correction.md]

## 6. SystemServer 启动优化

### 6.1 4MB Perfetto Buffer

Android 17 SystemServer 显式初始化 4MB Perfetto 共享内存缓冲区：

```java
// SystemServer.java line 862-863
// Explicitly initialize a 4 MB shmem buffer for Perfetto producers (b/382369925)
android.tracing.perfetto.Producer.init(new InitArguments(
        InitArguments.PERFETTO_BACKEND_SYSTEM, 4 * 1024));
```

- **4 \* 1024 = 4096 KB = 4 MiB**，使用 system backend
- b/382369925 是 Google 内部 bug——system_server 启动早期缺乏足够 Perfetto buffer，导致 trace 数据丢失
- 该缓冲区独立于应用层 Perfetto 配置，确保 SystemServer 启动全程可追踪

[已验证: AOSP android-17.0.0_r1, SystemServer.java line 862-863]

### 6.2 7 阶段 BootPhase

SystemServer 启动过程通过 7 个 BootPhase 检查点推进：

```
PHASE_WAIT_FOR_DEFAULT_DISPLAY
→ PHASE_WAIT_FOR_SENSOR_SERVICE
→ PHASE_LOCK_SETTINGS_READY
→ PHASE_SYSTEM_SERVICES_READY
→ PHASE_DEVICE_SPECIFIC_SERVICES_READY
→ PHASE_ACTIVITY_MANAGER_READY
→ PHASE_THIRD_PARTY_APPS_CAN_START
```

每个 phase 由 `mSystemServiceManager.startBootPhase()` 触发，所有系统服务按依赖关系在这些 phase 间注册。

[已验证: AOSP android-17.0.0_r1, SystemServer.java line 1355-3535]

### 6.3 APEX 服务启动阶段

Android 17 新增 `startApexServices()` 独立阶段（SystemServer.java line 3685-3711）：

```java
private void startApexServices(@NonNull TimingsTraceAndSlog t) {
    t.traceBegin("startApexServices");
    List<ApexSystemServiceInfo> services =
        ApexManager.getInstance().getApexSystemServices();
    for (ApexSystemServiceInfo info : services) {
        if (TextUtils.isEmpty(info.getJarPath())) {
            mSystemServiceManager.startService(info.getName());
        } else {
            mSystemServiceManager.startServiceFromJar(
                info.getName(), info.getJarPath());
        }
    }
    mSystemServiceManager.sealStartedServices();  // 硬约束：此后禁止注册
    t.traceEnd();
}
```

**关键约束**：`sealStartedServices()` 在 android-17 才完整生效——所有非 APEX 服务必须在 APEX 阶段前注册完成，APEX 模块提供的 service 自动归入此阶段。

[已验证: AOSP android-17.0.0_r1, SystemServer.java line 3685-3711]

## 7. Android 17 启动新特性

### 7.1 PSI 监控延后

启动阶段 lmkd 不开启 PSI 监控（`PSI_MONITOR_PERIOD_MS=0`），直到 boot 完成后才由 AMS 显式触发：

```java
// ActivityManagerService.java line 5991-5995 (finishBooting 内)
SystemProperties.set("sys.boot_completed", "1");
SystemProperties.set("dev.bootcomplete", "1");
ProcessList.startPsiMonitoringAfterBoot();  // 显式触发 PSI 监控
```

```java
// ProcessList.java line 1657-1660
public static void startPsiMonitoringAfterBoot() {
    ByteBuffer buf = ByteBuffer.allocate(4);
    buf.putInt(LMK_START_MONITORING);
    writeLmkd(buf, null);
}
```

**设计意图**：冷启动阶段 CPU/内存资源紧张，PSI 采样的 memcg 开销会加剧启动延迟。延后到 boot 完成后开启，是"启动性能 vs 运行期内存压力感知"的工程取舍。

[已验证: AOSP android-17.0.0_r1, AMS.java line 5991-5995, ProcessList.java line 1657-1660]

### 7.2 BOOT_TIME_EVENT_ELAPSED_TIME_REPORTED 基准事件

Android 17 在三个层共埋 6 个 StatsLog 启动基准事件：

| 事件 | 埋点位置 |
|------|----------|
| `ZYGOTE_INIT_START` | ZygoteInit.java:872-879 |
| `SECONDARY_ZYGOTE_INIT_START` | ZygoteInit.java:880-883 |
| `SYSTEM_SERVER_INIT_START` | SystemServer.java:910-914 |
| `SYSTEM_SERVER_READY` | SystemServer.java:1067-1069 |
| `PACKAGE_MANAGER_INIT_START` | SystemServer.java:1360-1362 |
| `PACKAGE_MANAGER_INIT_READY` | SystemServer.java:1394-1396 |

与 bootstat 的 event-log 形式不同，StatsLog 事件**跨重启持久化**，可在 metrics 平台中查询聚合。

```java
// SystemServer.java line 1067-1075
if (!mRuntimeRestart && !isFirstBootOrUpgrade()) {
    final long uptimeMillis = SystemClock.elapsedRealtime();
    FrameworkStatsLog.write(FrameworkStatsLog.BOOT_TIME_EVENT_ELAPSED_TIME_REPORTED,
            FrameworkStatsLog.BOOT_TIME_EVENT_ELAPSED_TIME__EVENT__SYSTEM_SERVER_READY,
            uptimeMillis);
    final long maxUptimeMillis = 60 * 1000;
    if (uptimeMillis > maxUptimeMillis) {
        // 超过 60s 告警
    }
}
```

[已验证: AOSP android-17.0.0_r1, SystemServer.java line 1063-1075]

### 7.3 finishBooting 收尾序列

`AMS.finishBooting()` 包含 13 步有序流程：

1. ART runtime 完成通知
2. 服务阶段通知（各 BootPhase 回调）
3. 用户解锁状态设置
4. `sys.boot_completed=1` / `dev.bootcomplete=1`
5. PSI 监控开启（`startPsiMonitoringAfterBoot`）
6. 全量 PSS 推迟 60s
7. ...（后续步骤）

全量 PSS 推迟 60s 是为了避免 boot 完成瞬间所有进程同时上报 PSS 造成 CPU 尖峰。

[已验证: AOSP android-17.0.0_r1, AMS.java finishBooting()]
[来源: DeepResearch/2026-07-01-android17-boot-optimization-apex-psi-statslog.md]

## 扩展

### 🔸 Perfetto + bootanalyze 协同工作流

生产环境的启动性能分析推荐工作流：

1. **Perfetto 抓 trace**：`perfetto -o /data/misc/perfetto-traces/boot.trace -c /data/misc/perfetto-configs/boot.cfg`
2. **bootanalyze 抓事件**：`bootanalyze.py --iterate 1` 采集 logcat/dmesg + 时间校正
3. **交叉分析**：在 Perfetto UI 中导入 bootanalyze 输出的事件时间线，与 trace 数据对齐
4. **bootstat 聚合**：`bootstat --list` 查看历史启动事件，`bootstat --print_boot_complete` 查看最近一次

### 🔸 bootanalyze 性能开销

- **多轮 boot 采集**（`--iterate N`）：默认 N=1；超过 1 时强制 `--reboot`，单次循环约几十秒到几分钟
- **双线程采集**（line 409-418）：`threading.Thread` 并行采集 dmesg 和 logcat，主线程解析正则
- 对目标设备性能影响可忽略（adb 旁路采集）
