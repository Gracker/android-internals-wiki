# 8.1 Android 17 系统启动优化与 bootanalyze 工具链

> **源码锚点**
>
> - Android 平台：`android-17.0.0_r1`
> - bootanalyze：`system/extras/boottime_tools/bootanalyze/`
> - bootstat 与 init：`system/core/`
>
> `system/core/bootstat/bootanalyze.cpp` 在该标签中不存在。bootanalyze 是运行在主机上的 Python 工具，不是 Android 设备里的启动守护进程。

这篇文章解决三个问题：

1. bootanalyze、bootstat 和 Perfetto 各自提供什么证据；
2. Android 17 的 init、Zygote 和 SystemServer 启动点该怎样解释；
3. 怎样把“某阶段变慢”推进到“哪段执行造成变慢”。

## 1. 三类工具不要混用

| 工具或数据 | 主要输入 | 适合回答 | 不能单独回答 |
|---|---|---|---|
| bootanalyze | 实时 logcat、dmesg、`ro.boottime.*`、`ro.boot.boottime` | 关键事件发生时间、多轮均值与离散程度 | 线程为何等待、CPU/I/O 因果 |
| bootstat | 持久化 boot event、init 属性、bootloader timing | 本机记录的启动里程碑和 boot reason | 一段代码内部耗时 |
| Perfetto/ftrace | sched、binder、I/O、page fault、ATRACE 等 | 哪个线程在何处运行或等待 | 没有业务里程碑时，指标属于哪个产品阶段 |
| bootchart | 进程、CPU、I/O 的粗粒度启动视图 | 进程何时出现、系统负载怎样变化 | Java/SystemServer 的细粒度调用 |

bootanalyze 适合做“事件记分板”，Perfetto 适合解释时间花在何处，bootstat 适合保存和汇报少量里程碑。把三者的时间基准、启动定义和测试条件对齐，证据才可比较。

## 2. bootanalyze 在 Android 17 中怎样工作

### 2.1 代码组成与运行条件

`android-17.0.0_r1` 中的目录包含：

- `bootanalyze.py`：Python 3 主程序；
- `config.yaml`：事件与 timing 正则；
- `bootanalyze.sh`：多轮采集包装脚本；
- `bugreport_anayze.py`、`stressfs/` 和 README。

`bootanalyze.py` 的 shebang 是 `#!/usr/bin/python3`，README 却仍写 Python 2.7。这是文档漂移；以当前脚本和实际依赖为准。工具要通过 `su root` 读取 dmesg、调整设备设置并触发重启，通常需要 userdebug/eng 设备。普通 user build 不满足完整采集条件。

下面的命令用于按 AOSP 包装脚本进行多轮测试：

```bash
ANDROID_BUILD_TOP="$PWD" \
CONFIG_YMAL="$PWD/system/extras/boottime_tools/bootanalyze/config.yaml" \
LOOPS=5 \
RESULTS_DIR="$PWD/bootAnalyzeResults" \
"$PWD/system/extras/boottime_tools/bootanalyze/bootanalyze.sh" -s DEVICE_SERIAL
```

`CONFIG_YMAL` 的拼写来自脚本本身，不是本文笔误。包装脚本会逐轮调用 `bootanalyze.py`，把文本报告放进对应结果目录；开始前应确认当前目录是完整 AOSP checkout，并记录设备序列号、构建和启动类型。

### 2.2 配置文件是日志解析契约

主程序把 `config.yaml` 的三组配置编译为正则：

- `events`：单点里程碑；
- `timings`：必须能捕获命名组 `name` 和 `time` 的耗时日志；
- `shutdown_events`：重启前一轮关机过程的事件。

下面的片段用于说明配置语义：

```yaml
time_correction_key: correction
timings:
  system_server: 'SystemServerTiming(Async)?\s*:\s*(?P<name>\S+) took to complete:\s(?P<time>[0-9]+)ms'
events:
  correction: 'Updating system time diff=([0-9]+\.?[0-9]*), cuttime=([0-9]+)'
  zygote_preload_start: 'Zygote\s*:\s*begin preload'
  zygote_preload_end: 'Zygote\s*:\s*end preload'
  apexd_ready: 'apexd.*Marking APEXd as ready'
```

这类规则依赖日志文本。修改 tag、标点或 message 后，工具可能静默缺少事件；因此升级平台时要把 `config.yaml` 与目标版本日志一起审阅。日志命中也只表示字符串出现，不能自动证明对应模块占用了前后两个事件之间的全部时间。

### 2.3 停止条件不是只有 `BOOT_COMPLETED`

当前代码为 logcat 默认加入 `BootComplete` 和 `LauncherStart` 两个停止事件；启用选项后还可以等待 `FsStat`、CarWatchdog、登录完成或 Launcher shown。dmesg 侧等待内核 boot complete 或 init second-stage 等事件。

“boot complete”“Launcher 首次启动”“首帧可交互”“用户解锁”是不同指标。实验报告要写出使用了哪个停止条件，不能把它们都称为“开机时间”。

### 2.4 时间校正的准确含义

bootanalyze 同时读取：

- `adb ... logcat -b all -v epoch`；
- `adb ... shell su root dmesg -w`；
- `adb ... shell su root getprop`。

校正分两步：

1. 如果日志命中 `time_correction_key`，脚本会根据 `Updating system time diff=...` 修正该切换点之前的 logcat epoch；
2. 脚本再用 BootAnimation end、boot complete，或 init second stage 在 logcat/dmesg 中的对应事件计算偏差，把只存在于 logcat 的事件换算到内核时间附近；同名事件若也在 dmesg 中，会采用 dmesg 时间。

这是一种面向启动日志的近似对齐，不是通用的时钟同步算法。配置缺少锚点、日志丢失或厂商修改 message 时，本轮样本可能无法解析。

### 2.5 `ro.boottime.*` 当前来自 getprop

`fetch_boottime_property()` 直接解析 `ro.boottime.*` 和 `ro.boot.boottime`。源码还保留了“未来改用 bootstat”的 TODO，所以 bootstat 不是当前 bootanalyze 的底层数据源。

脚本按字段选择单位：

- `ro.boottime.init.*` 按毫秒转成秒；
- 其他 `ro.boottime.*` 按纳秒转成秒；
- `ro.boot.boottime` 的 bootloader 子项按毫秒处理。

工具计算 bootloader 合计时会忽略 `SW` 与 `splash`，因为它们可能与其他阶段重叠。设备没有填充 `ro.boot.boottime` 时，不会生成 bootloader 合计；这不是采集失败。

### 2.6 输出适合比较，不负责归因

多轮结果包含均值、标准差和有效样本数，也可以列出 SystemServer、PackageManager、init command、ueventd 与 Zygote timing。工具还支持 bootchart、已有 kernel trace 的 systrace 抓取、登录场景 Perfetto 和产品扩展事件。

“某个 timing 最大”只说明它值得继续分析。timing 日志本身可能包住异步工作、等待或多个子模块；需要 Perfetto、线程栈和源码边界继续拆解。

## 3. bootstat 是另一套记录机制

`system/core/bootstat` 的职责是记录命名 boot event、保存相对时间，并把部分事件写入 statsd atom 或日志系统。`BootEventRecordStore` 保存本机事件；`bootstat.cpp` 在 boot complete 时还会读取 init 与 bootloader 属性。

下面的命令用于查看设备已经保存的 bootstat 记录：

```bash
adb shell bootstat -p
adb shell getprop | grep -E '^\[ro\.(boot\.)?boottime'
adb shell getprop ro.boot.bootreason
```

`bootstat -p` 输出的是记录存储中的事件，`getprop` 展示当前启动暴露的属性，两者不保证字段完全相同。部分命令和属性在 user build 上可能受权限限制。

### 3.1 init 里程碑的单位

`RecordBootComplete()` 读取以下属性：

- `ro.boottime.init`；
- `ro.boottime.init.first_stage`、`init.selinux`、`init.cold_boot_wait`；
- `ro.boottime.event.early-init` 到 `event.boot` 的一组 trigger 时间。

`ro.boottime.init` 和 `ro.boottime.event.*` 原值按纳秒转换成毫秒；其他 `ro.boottime.init.*` 已是毫秒。分析原始属性时如果统一除以同一个系数，会得到错误时间。

### 3.2 bootloader timing 是可选输入

`GetBootLoaderTimings()` 解析 `ro.boot.boottime` 的 `stage:milliseconds` 列表。源码明确说明该属性并非所有设备都会提供。`1BLE`、`1BLL`、`KL`、`2BLE`、`2BLL`、`SW` 和 `splash` 是 bootstat 能识别并映射到 atom 的常见字段，不是 Android 对所有 OEM 的强制完整清单。

`absolute_boot_time` 是 bootstat 根据 Android uptime 与部分 bootloader timing 估算出的值。bootloader 没上报、字段语义与产品不同或阶段重叠时，要在报告中注明缺口。

### 3.3 statsd atom 不等于永久历史库

Android 17 源码会为多组启动里程碑写 `BOOT_TIME_EVENT_*` atom。atom 是否被收集、保留多久、能否导出，受 statsd 配置和产品权限影响。不能只因为存在 `FrameworkStatsLog.write()` 就声称事件一定跨重启永久保存或可由应用查询。

## 4. init：command 串行，服务可以并行

第二阶段 init 的主循环调用 `ActionManager::ExecuteOneCommand()`，每次执行 action queue 中的一条 command。以下情况会使 action command 停住或等待：

- `wait_for_prop` 等待属性；
- `exec` / `exec_start` 等同步服务尚未结束；
- `mount_all`、文件系统检查、restorecon 等命令本身耗时。

但 `start` 或 `class_start` 成功 fork/exec 服务后，init 可以继续执行后续 command，被启动的多个服务进程也可以并行运行。把整个启动过程描述为“严格单线程串行”会漏掉大量并发和资源竞争。

### 4.1 trigger 顺序与产品 action

AOSP root `init.rc` 的 `late-init` 依次触发：

`early-fs → fs → post-fs → late-fs → post-fs-data → load-bpf-programs → zygote-start → firmware_mounts_complete → early-boot → boot`

同一 trigger 可以在 system、vendor、odm 等多个 rc 文件中注册 action。解析顺序、属性条件和每条 command 的阻塞语义都会影响实际时间。优化时应从目标产品的合并 rc 和日志出发，不能只看 root `init.rc`。

### 4.2 service class 不是固定性能层级

`class_start NAME` 遍历当前 `ServiceList`，启动带有该 class 且未显式 disabled 的服务。AOSP root rc 在不同 trigger 中使用 `early_hal`、`hal`、`core`、`main`、`late_start` 等 class；设备 rc 还可以定义自己的 class。

class 表示批量启动分组，不表示这些进程按 class 内顺序完成初始化。`persist.init.dont_start_class.<name>` 是源码支持的调试开关，但禁用整组服务可能破坏依赖，不能当成通用的启动提速办法。

### 4.3 怎样找 init 长尾

bootanalyze 的 config 已能解析 `init: Command ... took ...ms` 与同步 exec service 的等待耗时。发现长 command 后，再按类型处理：

- `mount_all` / fsck：检查文件系统、块 I/O、加密与 checkpoint；
- `restorecon_recursive`：检查扫描范围、标签变化和文件数量；
- `wait_for_prop`：找属性生产者以及它为何没有及时运行；
- `exec`：分析子进程 CPU、I/O 和依赖；
- `class_start` 后变慢：转向被启动服务的并行竞争，不能把整段都算给 class_start 本身。

## 5. Zygote preload：当前实现与版本历史

`ZygoteInit` 接受 `--enable-lazy-preload`。未启用时，Zygote 在进入 socket select loop 前调用 `preload()`；启用时，预加载被推迟到首次需要 fork 之前。

下面的简化控制流用于说明 eager 与 lazy 的区别：

```text
Zygote main
  ├─ 未传 --enable-lazy-preload
  │    └─ preload() → 进入 select loop
  └─ 传入 --enable-lazy-preload
       └─ 进入 select loop → 首次 fork 请求前 lazyPreload() → preload()
```

两条路径最终调用同一个 `preload()`，lazy 模式改变的是时间位置，不是缩减预加载内容。`ZygoteInitTiming_lazy` 为 trace 提供单独名称。

这个参数至少在 Android 8 的 AOSP 源码中已经存在，不是 Android 17 新增。`android-17.0.0_r1` 的 `init.zygote64_32.rc` 给 secondary 32-bit Zygote 传入该参数，primary 64-bit Zygote仍做 eager preload。其他 ABI 组合和产品 rc 需要单独查看。

旧稿给出的“首次冷启动增加 5—10ms”没有设备、样本和工作负载，不能保留。lazy preload 的成本接近该设备一次完整 preload，可能远高于固定个位数毫秒；收益与代价应分别在 boot 指标和首次触发 secondary Zygote 的应用启动中测量。

`preload()` 当前包含 class、resource、classloader、graphics driver、shared library、text resource、compat config、WebView/JCA 等工作，并在 flag 开启时尝试 `HttpEngine.preload()`。这些步骤会随平台演进，不宜固化为“9 步不变”。

## 6. SystemServer：看当前事实，不猜新增版本

### 6.1 Perfetto producer buffer

`SystemServer.run()` 在启动服务前调用 `Producer.init(..., 4 * 1024)`，注释把它定义为 4 MB shmem buffer。它为 SystemServer 的 Perfetto producer 准备共享内存，不会自动开始系统启动 trace，也不能保证任何采集配置下都不丢数据。

判断 trace 是否完整仍要检查：

- Perfetto data source 和 buffer 配置；
- trace 是否在目标阶段前开始；
- ftrace/ATRACE category 是否启用；
- buffer wrap、producer drop 和 flush 状态。

### 6.2 BootPhase 是回调里程碑

Android 17 当前可见的主要 SystemServer phase 包括：

- `PHASE_WAIT_FOR_DEFAULT_DISPLAY`；
- `PHASE_WAIT_FOR_SENSOR_SERVICE`；
- `PHASE_LOCK_SETTINGS_READY`；
- `PHASE_SYSTEM_SERVICES_READY`；
- `PHASE_DEVICE_SPECIFIC_SERVICES_READY`；
- `PHASE_ACTIVITY_MANAGER_READY`；
- `PHASE_THIRD_PARTY_APPS_CAN_START`。

`SystemServiceManager.startBootPhase()` 按已启动 service 列表调用 `onBootPhase()`。这些 phase 用于声明系统状态已经推进到某个里程碑，不是自动求解依赖的调度器；服务的构造、`onStart()` 和其他异步工作仍可能发生在 phase 之外。

### 6.3 APEX system service 的封口点

`SystemServer` 按 `startBootstrapServices()`、`startCoreServices()`、`startOtherServices()`、`startApexServices()` 的顺序启动服务。最后一个方法从 `ApexManager` 取得 APEX system service，按 class name 或 jar path 启动，并调用 `sealStartedServices()`。

源码注释要求 APEX services 成为最后一类启动的 system service，避免 platform 对可独立更新 APEX 建立反向依赖。本文只确认 Android 17 当前行为，不把 `startApexServices()` 或 `sealStartedServices()` 标成 Android 17 首次引入。

### 6.4 启动 atom 与 60 秒告警

Zygote、SystemServer 和 PackageManager 当前会写多组 `BOOT_TIME_EVENT_ELAPSED_TIME_REPORTED`。`SYSTEM_SERVER_READY` 只在非 runtime restart、非首次启动/升级条件下写入；同一分支中，uptime 超过 60 秒会 `Slog.wtf`。

60 秒是源码中的异常检查值，不是产品启动 KPI，也不是达到 60 秒才算性能问题。产品仍应根据用户可感知目标和健康样本建立自己的门槛。

## 7. `finishBooting()` 中两个容易误读的点

### 7.1 PSI monitoring 命令是“如果之前跳过”

AMS 设置 `sys.boot_completed=1` 和 `dev.bootcomplete=1` 后，调用 `ProcessList.startPsiMonitoringAfterBoot()` 向 lmkd 发送 `LMK_START_MONITORING`。源码注释写的是“如果之前跳过，则开始 PSI monitoring”。

这段 Java 代码不能证明所有设备在整个 boot 期间都关闭 PSI，也不能证明关闭的目的或开销大小。lmkd 是否延迟监控还受其配置和启动状态影响，分析时应核对当前 lmkd 源码、属性和日志。

### 7.2 全量 PSS 默认延后约 20 分钟

用户控制器回报 boot complete 后，AMS 通过 `FULL_PSS_MIN_INTERVAL` 延后一次全量 PSS 请求。Android 17 的 `ActivityManagerConstants` 默认值为 `20 * 60 * 1000` 毫秒，并可由 settings 常量更新。

旧稿写成固定 60 秒不符合当前源码。这里的延后时间还可能被产品配置修改，设备上应读取 `dumpsys activity settings` 的实际值。

## 8. 一套可复核的启动分析流程

### 8.1 定义样本

先固定以下条件：

- cold boot、warm reboot、OTA 后首启或 system_server restart；
- 是否完成用户解锁、是否等待 Launcher shown；
- bootloader 是否计入；
- 文件系统检查、checkpoint、dexopt、APEX activation 是否发生；
- 电池、温度、存储余量、网络和外设状态；
- user/userdebug 构建与 trace 开销。

OTA 后首启、首次解锁和常规重启不能放进同一组求均值。

### 8.2 用事件缩小范围

先用 bootanalyze 比较多轮里程碑和 timing：

1. bootloader、kernel、init first/second stage；
2. fs、post-fs-data、APEX、Zygote；
3. SystemServer、PackageManager、boot complete；
4. Launcher start/shown 或产品自己的可交互事件。

如果总时间回退 300ms，而所有已知事件只解释了 80ms，说明配置还缺关键里程碑，不能把余量随意归给最大的现有阶段。

### 8.3 用 Perfetto解释阶段内部

针对回退区间采集：

- `sched_switch`、`sched_wakeup` 与 CPU frequency/idle；
- binder transaction；
- block I/O、writeback、page fault、reclaim；
- init、Zygote、SystemServer 和产品 service 的 ATrace；
- 锁等待、线程池和异步任务。

结论应写成可检验的执行关系，例如：“SystemServer 主线程在 `StartPackageManagerService` 区间等待某 future 240ms；worker 同期执行 dex scan，并在 userdata 上产生读 I/O。”只有“PackageManager 变慢 240ms”还不足以指导修改。

### 8.4 单变量复测

每次只修改一个 rc command、service 初始化点、预加载项或 I/O 策略。至少同时观察：

- 目标启动 KPI 的 P50、P95/P99；
- 首次应用启动和解锁时间是否退化；
- CPU time、I/O、功耗与峰值内存；
- 后续稳定性、服务可用性和 CTS/VTS；
- 恢复原配置后结果能否复现。

把任务异步化不等于消除成本。工作如果仍阻塞 Launcher、首个 Binder 请求或用户解锁，只是换了等待位置。

## 9. 常见误区

- 把 `sys.boot_completed` 当作“屏幕已经可交互”；
- 把 bootanalyze 与 bootstat 写成调用关系；
- 把 init action command 串行解释为整个系统启动串行；
- 把 `--enable-lazy-preload` 写成 Android 17 新功能；
- 用固定毫秒数描述 lazy preload 成本；
- 把 SystemServer 的 Perfetto producer buffer 当成自动启动 trace；
- 把 `FrameworkStatsLog.write()` 当成永久保存保证；
- 把 lmkd 的启动后命令解释为所有产品启动期都禁用 PSI；
- 把 `FULL_PSS_MIN_INTERVAL` 写成固定 60 秒；
- 只跑一轮重启就下优化结论。

## 10. 小结

bootanalyze 的价值是把 Android 启动日志整理成可比较的事件时间轴。它在主机上读取 logcat、dmesg 和 boot properties，通过配置中的正则与时间锚点校正事件；它当前没有以 bootstat 作为数据源。

bootstat 保存少量 boot event，Perfetto解释线程和资源消耗，三者需要配合。分析 init 时要区分串行 command 与并发 service，分析 Zygote 时要区分 eager/lazy 的成本转移，分析 SystemServer 时要把 BootPhase、APEX service 和异步工作放回源码调用点。

可靠的优化结论应包含样本定义、事件差值、执行证据、单变量改动和副作用。缺少其中任何一项，都不宜把某个日志阶段直接认定为启动瓶颈。
