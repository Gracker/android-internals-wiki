## 审阅结论

原始占位稿把“任务调度器”当成一个单独的平台组件，还给出了 `https://android-developers.googleblog.com/2026/06/android-17-performance-optimization`。Android Developers Blog 没有与该 URL 和标题对应的文章，`android-17.0.0_r1` 也没有名为 `TaskScheduler`、负责用 ML 统一优化应用启动的 framework service。这个来源和“新增 ML 驱动任务调度器”结论不能继续引用。

Android 17 与“任务怎么运行”相关的变化分散在不同层，每层解决的问题不同：

| 层次 | Android 17 可核验变化 | 能优化什么 | 不能替代什么 |
|---|---|---|---|
| App `Looper` / `MessageQueue` | target SDK 37 应用默认启用 DeliQueue；生产者用 CAS 发布消息，Looper 用最小堆维护执行顺序 | 降低多线程向同一队列投递时的 monitor contention | 不会缩短消息回调内部的业务耗时，也不负责后台 Job |
| `JobScheduler` | API 37 新增 `getPendingJobReasonStats(jobId)`，返回 pending reason 到累计 `Duration` 的映射 | 判断 Job 长时间未运行主要受哪类约束影响 | 只提供诊断，不会改变配额、Doze、standby bucket 或约束 |
| ADPF / `PerformanceHintManager` | Android 17 延续 API 31—36 已有能力，当前源码加入 FMQ、ATrace 与更多 session 模式实现 | 向系统报告周期性工作的 target/actual duration | 不决定一次性启动任务的依赖顺序，也不保证升频 |
| Linux scheduler | 内核锚点为 `android17-6.18-2026-06_r6`，调度器分配 runnable thread 的 CPU 时间 | 处理线程公平性、唤醒和 CPU 放置等内核决策 | 普通应用不能直接配置 CPU 亲和性或厂商调频策略 |
| App 初始化框架 | AndroidX App Startup 1.2.0 用 `Initializer.dependencies()` 描述进程内依赖 | 删除重复 provider、延迟非必要初始化、保证依赖先后顺序 | 不负责 JobScheduler 配额，也不干预 Linux 调度 |

## Android 17 中可直接采用的优化路径

### 1. 主线程排队：先区分等待时间与执行时间

DeliQueue 改的是 `MessageQueue` 内部的并发数据结构。`android-17.0.0_r1` 中，system_server 通过 `PlatformCompat.getUseDeliQueue(app.info)` 计算进程是否启用，再把 `--use-deliqueue=` 传给 `ActivityThread.main()`；后者在创建主 Looper 前调用 `MessageQueue.setUseDeliQueue()`。`USE_NEW_MESSAGEQUEUE` 标注为 `@EnabledAfter(targetSdkVersion = BAKLAVA)`，因此 target SDK 37 应用默认进入新实现。

这项变化减少生产者线程与 Looper 围绕旧单链表对象锁竞争的机会。消息回调执行 40 ms、主线程同步 I/O、锁等待或 Binder 阻塞仍要按原调用栈修复。Perfetto 中应把以下两段分开：

- dispatch 前的 runnable/blocked 区间，用于判断线程有没有及时拿到 CPU、是否等待锁或 Binder；
- `Looper.dispatchMessage()` 覆盖的回调区间，用于定位消息自身执行了什么。

DeliQueue 的数据结构、启用参数和 Perfetto 轨道已经在 [1.26 DeliQueue 无锁队列源码解析](../ch01-architecture/01.26-messagqueue-deliqueue-optimization.md) 展开，本页不复制同一套源码。

### 2. 后台任务没运行：读取 pending reason，不猜“系统不调度”

Job 已提交但迟迟没有进入 `JobService` 时，API 37 的 `getPendingJobReasonStats(jobId)` 可以查看每类等待原因累计了多长时间。多个原因能同时存在，所以各项 `Duration` 相加可能大于 Job 的总等待时间；设备重启后统计不保留，Job 成功完成或取消后也会清空。

这个 API 适合 dogfood 和灰度诊断。看到 `CONSTRAINT_CHARGING`、`QUOTA`、`APP_STANDBY` 或 `BACKGROUND_RESTRICTION` 后，再分别检查约束是否过严、是否有重试风暴、应用 standby bucket 以及用户的后台限制。它不应进入高频热路径，也不应被写成任务准点运行的保证。

完整版本边界、reason 映射与 `dumpsys jobscheduler` 方法见 [25.14 JobScheduler 调试：Pending Reasons 与 JobDebugInfo](../../part5-app/ch25-power-size/14-jobdebuginfo-jobscheduler-diagnostics.md)。

### 3. 启动任务：先修依赖和主线程工作

应用冷启动中的类加载、ContentProvider 初始化、`Application.onCreate()` 和首屏构建通常是一次性工作。优化顺序是：

1. 用 Macrobenchmark 固定启动模式和测试数据，记录多轮 startup timing。
2. 在 Perfetto 中找主线程长 slice、Binder 等待、I/O、锁竞争和晚到的渲染工作。
3. 删除重复初始化，把首屏不需要的工作移出关键路径。
4. 使用 AndroidX App Startup 时显式声明 `Initializer` 依赖，手动初始化的组件要给出可验证的完成条件。
5. 只有启动后持续运行的周期负载，才评估 `PerformanceHintManager`。

依赖建模见 [8.33 Android 17 模块化启动框架](./8.33-android17-modular-startup-framework-dependency-graph.md)，启动度量见 [8.36 AndroidX Benchmark 1.4.1 Startup Insights](./8.36-android17-startup-insights.md)，周期性性能提示见 [8.37 PerformanceHintManager](./8.37-android17-performance-hint-manager.md)。

### 4. 线程优先级与 CPU 亲和性：应用层不要越过权限边界

普通应用可以通过线程池大小、任务拆分、队列顺序和有限的线程优先级 API 管理自己的并发。把线程绑到指定 CPU、直接写调度器 sysctl、控制频点或替 Power HAL 选择策略都不属于通用 SDK 能力。厂商系统组件即使拥有这些权限，也必须用目标设备的功耗、温度和尾延迟数据验证，不能把单一 SoC 的参数复制成跨设备建议。

应用侧常见的有效动作更朴素：

- CPU 密集任务限制并发，避免与主线程、RenderThread 同时争抢所有大核；
- I/O 等待任务不占用 CPU 线程池的全部 worker；
- 用户可见工作和后台维护工作分开排队，避免后台长任务挡住交互路径；
- 对任务记录 enqueue、start、finish/stop 三个时间点，先确认延迟发生在排队、系统等待还是执行阶段；
- 用 P50/P90/P99 和 deadline miss 比较修改前后结果，同时记录温度与设备电源状态。
