## 1. 先建立准确的分层模型

本文以 Android 平台源码 `android-17.0.0_r1`、Android Common Kernel
`android17-6.18-2026-06_r6` 为准。这里讨论的三个组件没有共用一套状态机，也没有
一条由 `PowerManagerService` 直接写到 `cpuidle`、`schedutil` 的固定调用链。

它们各自回答不同的问题：

| 组件 | 所在位置 | 负责回答的问题 | 直接输入 |
| --- | --- | --- | --- |
| `PowerManagerService`（PMS） | `system_server` | 设备是否应保持唤醒、显示组应处于什么状态、能否释放 suspend blocker | wake lock、用户活动、供电状态、显示状态、Doze 等 |
| Power HAL | Framework 与厂商实现之间 | 某个场景提示是否需要调整平台性能或功耗参数 | `Mode`、`Boost`、ADPF Hint Session 等 |
| `cpuidle` | 内核 | 当前 CPU 已经无任务可运行时，应进入哪个 idle state | 预计空闲时长、退出延迟约束、历史唤醒结果 |
| `schedutil` | 内核 | CPU 仍在执行任务时，cpufreq policy 应请求多高的性能 | 调度器利用率、uclamp、I/O wait、deadline bandwidth、sched_ext 目标等 |

因此，阅读这条路径时应区分两种关系：

- **明确的接口调用**：PMS 可以经 JNI 和 `PowerHalController` 向 Power HAL 发送
  `INTERACTIVE`、`DEVICE_IDLE` 等 mode。
- **间接的系统效应**：屏幕熄灭、后台限制和定时器减少后，可运行任务变少；
  `schedutil` 看到的利用率随之下降，CPU 更容易进入空闲，`cpuidle` 才有机会选择
  更深的状态。

Power HAL 的厂商实现可以增加一层设备相关策略，但 AOSP 接口没有规定它必须修改
哪一个 sysfs 节点，也没有规定必须改 `schedutil` 或 `cpuidle`。把某个厂商实现
观察到的写节点行为画成 Android 的通用调用链，会掩盖移植和排障时最关键的边界。

> **对受保护提纲的说明**：这套分层并非 Android 17 才新增。Android 17 在既有
> 电源管理架构上继续演进 AIDL Power HAL、ADPF、CPU/GPU headroom 和 composition
> data 等能力。提纲中的“实时同步”“自动调整”应理解为可能的厂商策略目标，不能
> 当作 AOSP 已提供的统一反馈协议。

## 2. Framework：PMS 管设备状态，不替内核选择频率

### 2.1 `DIRTY_*` 是增量重算条件

Android 17 的 `PowerManagerService.java` 定义了 **16 个具名 `DIRTY_*` 常量**：
位 0～12、14、16、17；位 13 和 15 没有对应常量。位编号的最大值是 17，不等于
存在 18 个标志。

`updatePowerStateLocked()` 是 PMS 的中心重算入口。它在持有 `mLock` 时按八个
阶段处理状态：

1. 更新供电、Stay On 和亮度临时增强等基础状态；
2. 在循环中重算 wake lock 摘要、用户活动、注意力状态和 wakefulness，直到
   wakefulness 稳定；
3. 处理已超时的 profile；
4. 更新各 `PowerGroup` 的显示电源请求；
5. 更新 Dream；
6. 完成 wakefulness 变更通知；
7. 通知屏幕超时策略变化；
8. 更新 suspend blocker。

下面的源码片段用于说明 `mDirty` 为什么会在循环内清零，而不是把整个方法简化成
一次线性执行：

```java
for (;;) {
    int dirtyPhase1 = mDirty;
    dirtyPhase2 |= dirtyPhase1;
    mDirty = 0;

    updateWakeLockSummaryLocked(dirtyPhase1);
    updateUserActivitySummaryLocked(now, dirtyPhase1);
    updateAttentiveStateLocked(now, dirtyPhase1);
    if (!updateWakefulnessLocked(dirtyPhase1)) {
        break;
    }
}
```

`updateWakefulnessLocked()` 可能产生新的 dirty bit，所以 Phase 1 必须重复。后面的
显示、Dream 与 suspend blocker 更新依赖前面已经稳定的结果。这是 PMS 内部的状态
收敛过程，与 `schedutil` 的频率更新周期无关。

### 2.2 PMS 向 Power HAL 发送哪些信号

几条对本文有用的 Android 17 路径如下：

- `setHalInteractiveModeLocked()` 调用
  `nativeSetPowerMode(Mode.INTERACTIVE, enable)`。
- `setDeviceIdleModeInternal()` 和 `setLightDeviceIdleModeInternal()` 合并深度、
  轻度 idle 状态，再发送 `Mode.DEVICE_IDLE`。
- `onDisplayStateChange()` 发送 `Mode.DISPLAY_INACTIVE`，并按配置处理 HAL
  interactive mode 与 autosuspend。
- `BatterySaverController.handleBatterySaverStateChanged()` 通过
  `PowerManagerInternal.setPowerMode(Mode.LOW_POWER, isEnabled())` 发送低功耗模式。

`setPowerModeInternal()` 还有一个容易被误读的特例。下面的片段用于确认 LAUNCH
mode 在进入 HAL 之前可能被电池节省策略拦截：

```java
private boolean setPowerModeInternal(int mode, boolean enabled) {
    if (mode == Mode.LAUNCH && enabled && mBatterySaverStateMachine != null
            && mBatterySaverStateMachine.getBatterySaverController()
                    .isLaunchBoostDisabled()) {
        return false;
    }
    return mNativeWrapper.nativeSetPowerMode(mode, enabled);
}
```

这里拦截的是 `Mode.LAUNCH` 的启用请求，不是名为 “LAUNCH Boost” 的 boost；AIDL
枚举中也没有这个 boost。未被拦截的调用进入 JNI：
`nativeSetPowerMode()` → `PowerHalController::setMode()` → Power HAL。

JNI 中的 20 ms 判断也要按源码语义阅读。它只在 `Mode::INTERACTIVE` 调用耗时超过
20 ms 时打印 “Excessive delay” 日志。它不是 `setMode()` 的延迟保证，更不能用来
推出一般 Binder 调用都小于 20 ms。

### 2.3 suspend、Doze 与 CPU idle 不是同一个状态

这三个术语常被混在一起：

- **Device Idle / Doze** 是 Android 的应用与系统策略状态。它会限制任务、网络、
  alarm 和部分 wake lock，并向 Power HAL 发送 `DEVICE_IDLE` mode。
- **System suspend** 是整机级低功耗状态。PMS 在各项状态更新完成后维护 suspend
  blocker，SystemSuspend 服务再与内核 suspend 机制交互。
- **CPU idle** 是单 CPU 在没有 runnable task 时进入的局部空闲状态。其他 CPU、
  外设乃至整机仍可工作。

设备进入 Doze 不代表每个 CPU 立刻进入最深 idle state；CPU 进入深 idle 也不代表
整机已经 suspend。排查“灭屏耗电”时，必须分别检查 Framework 状态、suspend
阻塞原因、唤醒源和各 CPU 的 idle residency。

## 3. Power HAL：它传递提示，不规定厂商动作

### 3.1 Android 17 使用冻结的 AIDL v7 接口

`hardware/interfaces/power/aidl/Android.bp` 在 `android-17.0.0_r1` 中把
`android.hardware.power` 固定到 V7。该版本包含：

- 19 个 `Mode`，包括 `LOW_POWER`、`LAUNCH`、`INTERACTIVE`、
  `DEVICE_IDLE`、`DISPLAY_INACTIVE`、`GAME`、`DISPLAY_CHANGE`、
  `AUTOMOTIVE_PROJECTION` 等；
- 6 个 `Boost`：`INTERACTION`、`DISPLAY_UPDATE_IMMINENT`、`ML_ACC`、
  `AUDIO_LAUNCH`、`CAMERA_LAUNCH`、`CAMERA_SHOT`；
- Hint Session、进程级 FMQ session channel；
- `SupportInfo`、CPU/GPU headroom；
- composition data 与 composition update。

接口注释明确允许平台忽略某个 mode 或 boost。`IPower.aidl` 只说明实现“可能”
调整 cpufreq governor 或其他设备参数，也允许 boost 阻止 CPU 进入深睡状态；
它没有指定操作对象和参数值。

AOSP 的 `power/aidl/default/Power.cpp` 更能说明这条边界：

- `setMode()`、`setBoost()` 只记日志并返回成功；
- `getCpuHeadroom()`、`getGpuHeadroom()` 返回
  `EX_UNSUPPORTED_OPERATION`；
- 示例 `getSupportInfo()` 把 mode/boost 位图置为支持，但 `setMode()` 与
  `setBoost()` 并未执行硬件调节。

这个 default 目录是接口示例，不是 Pixel 或任意商品设备的性能策略。判断一台设备
的行为，应查看它注册的 Power HAL 服务、VINTF manifest 和对应厂商实现，不能从
AOSP 示例反推。

### 3.2 厂商实现可能影响哪些量

厂商 Power HAL 常见的可选动作包括：

- 调整 CPU/GPU/内存互连的最低或最高性能约束；
- 更新任务分组、cpuset、uclamp 或设备专用调度参数；
- 通过 PM QoS 限制 idle exit latency，暂时避免过深的 CPU idle；
- 给 cpufreq 驱动、GPU DVFS 或固件发送场景提示；
- 为 ADPF Hint Session 维护每组线程的性能目标。

这些是实现选择，不是 AIDL 契约。比如，`LOW_POWER` 可以设置频率上限，也可以只改
内存或显示相关参数；`INTERACTION` 可以提高 uclamp，也可以由固件处理。文章、测试
脚本和性能结论都应写明具体设备、build、Power HAL 版本及改动节点。

### 3.3 ADPF 与 IPowerStats 不属于 PMS 状态机

ADPF Hint Session 以一组长期存活的线程、目标工作时长和周期性实际工作时长为输入。
它是面向工作负载的反馈接口，和 PMS 根据 wakefulness、显示状态维护整机策略是两条
不同路径。Android 17 的 FMQ channel 能减少高频 session message 的传输开销，但
源码没有给出“比 Binder 快 60%”这类跨设备结论。

`IPowerStats` AIDL v2 提供 power entity、state residency、energy consumer 和
energy meter 数据。它主要用于观测与统计；AOSP 没有把这些读数自动送入 PMS、
`cpuidle` 或 `schedutil` 的通用控制器。某个厂商若基于这些数据调整策略，也应作为
设备实现单独说明。

## 4. Kernel：`cpuidle` 只在 CPU 已经空闲时工作

### 4.1 driver 描述硬件状态，governor 负责选择

在 `android17-6.18-2026-06_r6` 的 `include/linux/cpuidle.h` 中，
`struct cpuidle_state` 的关键字段包括：

- `exit_latency_ns`：从该状态恢复的退出延迟；
- `target_residency_ns`：进入该状态值得付出切换成本的参考驻留时间；
- `flags`：例如本地 timer 是否停止、是否为 polling state；
- `enter()` / `enter_s2idle()`：驱动进入状态的回调。

`struct cpuidle_driver` 提供按功耗递减排序的状态表；`struct cpuidle_governor` 的
`select()` 根据预测空闲时间、延迟约束和历史结果选择索引。通用路径很短：

```c
int cpuidle_select(struct cpuidle_driver *drv, struct cpuidle_device *dev,
                   bool *stop_tick)
{
    return cpuidle_curr_governor->select(drv, dev, stop_tick);
}

int cpuidle_enter(struct cpuidle_driver *drv, struct cpuidle_device *dev,
                  int index)
{
    int ret = 0;

    WRITE_ONCE(dev->next_hrtimer, tick_nohz_get_next_hrtimer());

    if (cpuidle_state_is_coupled(drv, index))
        ret = cpuidle_enter_state_coupled(dev, drv, index);
    else
        ret = cpuidle_enter_state(dev, drv, index);

    WRITE_ONCE(dev->next_hrtimer, 0);
    return ret;
}
```

governor 选状态，driver 执行状态。`cpuidle_enter_state()` 还会处理 broadcast timer、
tracepoint、驻留时间和次数统计。Android Common Kernel 在进入、退出处提供
`android_vh_cpu_idle_enter/exit` vendor hook，厂商模块可以修正选择或采集信息；
这也意味着设备行为可能偏离纯上游算法。

### 4.2 menu 与 TEO 都可能存在，运行时只能有当前 governor

Android 17 的 GKI arm64 defconfig 同时启用 `CONFIG_CPU_IDLE_GOV_MENU=y` 和
`CONFIG_CPU_IDLE_GOV_TEO=y`。这只表示两个 governor 被编进内核，不表示所有设备
都在用 TEO，也不表示两者同时决策。当前选择可从
`/sys/devices/system/cpu/cpuidle/current_governor_ro` 或
`current_governor` 查看，具体节点取决于内核配置。

以 TEO 为例，它会综合：

- 各状态以往的 hit 与 intercept；
- 当前 CPU 的延迟约束；
- 下一次 timer 到期时间；
- `target_residency_ns`；
- 是否停止 scheduler tick。

频繁唤醒会让历史结果偏向较浅状态；较紧的 latency QoS 也会限制可选深度。这里没有
“Android 用户场景”这个直接输入。场景只有通过 runnable task、timer、IRQ、QoS
约束或厂商 hook 改变内核可见条件后，才会影响选择。

### 4.3 “进不了深 idle”应分成两类问题

- **没有足够长的空闲窗口**：短周期 timer、IRQ、内核线程或应用唤醒不断打断 CPU。
  governor 选浅状态通常是合理结果。
- **空闲窗口存在但状态受限**：idle state 被禁用、退出延迟约束过紧、driver/固件
  没有暴露深状态，或厂商 hook 改写了索引。

只调 `target_residency` 或只看 CPU 平均利用率，无法区分这两类问题。应同时观察
唤醒事件、预计空闲时长、所选 state 和实际 residency。

## 5. Kernel：`schedutil` 把调度器需求映射到性能请求

### 5.1 更新节流不是固定 1 ms

`sugov_should_update_freq()` 比较本次更新时间和
`sg_policy->last_freq_update_time`。只有间隔达到
`freq_update_delay_ns`，或 policy limit / deadline bandwidth 等条件要求立即
更新时，才继续计算。

`sugov_init()` 这样初始化 tunable：

```c
tunables->rate_limit_us = cpufreq_policy_transition_delay_us(policy);
```

`cpufreq_policy_transition_delay_us()` 的规则是：

1. 驱动若提供 `policy->transition_delay_us`，直接使用；
2. 否则根据 `transition_latency` 计算，并留出 50% 间隔；
3. 两者都不可用时，返回 1 ms。

所以 1 ms 是兜底值，不是所有 Android 17 设备的 schedutil 默认值。用户空间还可能
通过 policy 的 `schedutil/rate_limit_us` 修改它。过低的值会增加频率切换请求和
调度开销，过高则可能错过短任务的性能窗口。

### 5.2 利用率不只来自 CFS

Android Common Kernel 6.18 的 `sugov_get_util()` 从
`scx_cpuperf_target(cpu)` 开始；当 sched_ext 没有切换全部调度类时，它还会加上
`cpu_util_cfs_boost(cpu)`。随后：

- `effective_cpu_util()` 合并调度类需求和 uclamp 等约束，得到 `min`、`max`；
- I/O wait boost 可抬高本次 util；
- `sugov_effective_cpu_perf()` 加 DVFS headroom，并在 min/max 范围内得到性能需求。

这不是“sched_ext 永远覆盖 CFS 利用率”。是否由 sched_ext 提供主要目标，取决于
`scx_switched_all()` 和调度器当前状态；混合运行时仍会计入 CFS。

### 5.3 从 util 到驱动请求

`get_next_freq()` 的注释给出核心关系：

`next_freq = C × reference_freq × util / capacity`

其中 `C = 1.25` 用于让频率在 `util / capacity = 0.8` 左右达到参考频率，这是
DVFS headroom，不是算法失效点。Android Common Kernel 还先调用
`trace_android_vh_map_util_freq`，允许 vendor hook 给出映射结果；未给出时才使用
`map_util_freq()`。`cpufreq_driver_resolve_freq()` 再把原始请求约束到 policy
min/max 和驱动支持的频点。

执行路径也不只有“快速/慢速”两个固定延迟档：

- 单 CPU policy 同时启用 fast switch 且驱动支持 `adjust_perf` 时，可直接提交
  性能级别；
- 启用 fast switch 时调用 `cpufreq_driver_fast_switch()`；
- 不支持 fast switch 时，经 irq work 和 governor kthread 延后执行；
- shared policy 会聚合 policy 内各 CPU 的需求，取其中较高值。

延迟取决于 SoC 驱动、固件、总线和当前系统负载。源码没有承诺 fast switch 小于
10 μs，也没有承诺 deferred path 位于某个固定区间；这些数值只能来自指定设备上的
trace 或硬件测量。

## 6. 三者如何在常见场景中相互影响

### 6.1 灭屏并进入 Device Idle

可以把事件顺序理解为：

1. PMS 根据用户活动、wake lock 和显示状态更新 wakefulness、PowerGroup 与
   suspend blocker。
2. PMS 向 Power HAL 发送 `DISPLAY_INACTIVE`、`INTERACTIVE=false`；进入轻度或
   深度 Device Idle 时再发送 `DEVICE_IDLE=true`。
3. 厂商 Power HAL 可以调整设备约束，也可以忽略部分提示。
4. Framework 的后台限制、alarm 批处理和网络策略使 runnable task 与唤醒减少。
5. schedutil 根据新的调度器需求降低或提高性能请求。
6. 某个 CPU 的 runqueue 为空后，cpuidle governor 才选择 idle state。
7. 所有 suspend 条件满足并释放 blocker 后，系统才可能进入整机 suspend。

第 4～7 步受工作负载、IRQ、timer、内核驱动和固件共同影响。某一步没有发生，不能
直接归因于 PMS “没有通知 schedutil”。

### 6.2 启动和交互

应用启动时，Framework 可以发送 `Mode.LAUNCH`；电池节省策略可拦截其启用请求。
输入和即将显示新帧还可能触发 `INTERACTION` 或
`DISPLAY_UPDATE_IMMINENT` boost。厂商实现若提高 uclamp 或硬件性能下限，
schedutil 会在新的约束内计算；任务本身带来的利用率也会直接抬高请求。

CPU 忙时不会进入 cpuidle。负载出现短间隙时，下一 timer、latency QoS 和历史
intercept 可能使 governor 选择浅状态。这种结果通常是在响应延迟和省电之间取舍，
不代表 cpuidle 被 PMS 关闭。

### 6.3 ADPF 稳态渲染

ADPF Hint Session 通过目标时长与实际工作时长表达某组线程的性能需求。Power HAL
可据此修改线程或设备约束，调度器与 schedutil 再消费内核可见的约束和利用率。
PMS 不参与每一帧的 Hint Session 更新；它仍维护整机交互、显示和 suspend 状态。

## 7. 设备上的核查步骤

### 7.1 核对 Framework 状态

下面的命令用于同时检查 PMS 与 Device Idle，而不是只根据“屏幕已黑”判断设备状态：

```bash
adb shell dumpsys power
adb shell dumpsys deviceidle
adb shell dumpsys battery
adb shell dumpsys suspend_control_internal
```

关注 wakefulness、wake lock summary、suspend blockers、Device Idle 状态和
wakeup reason。不同版本或产品可能不公开
`suspend_control_internal` dumpsys 服务；节点缺失不表示 suspend 功能缺失。

### 7.2 核对 Power HAL

下面的命令用于确认注册的是哪个 AIDL 服务以及 Framework 是否报告 Power HAL
能力：

```bash
adb shell service list | grep -E 'power|Power'
adb shell dumpsys android.hardware.power.IPower/default
adb shell lshal | grep -i power
```

Android 17 新设备通常使用 AIDL Power HAL，源码中的 `PowerHalController` 仍保留
HIDL 1.0～1.3 连接路径以兼容旧实现。`dumpsys` 是否有内容取决于厂商服务是否实现
dump；`lshal` 主要用于核对 HIDL 服务，不能单独证明 AIDL 服务不存在。

### 7.3 核对 cpuidle

下面的命令用于查看当前 governor、driver 以及 CPU0 暴露的 idle states：

```bash
adb shell 'cat /sys/devices/system/cpu/cpuidle/current_governor_ro 2>/dev/null \
  || cat /sys/devices/system/cpu/cpuidle/current_governor'
adb shell 'cat /sys/devices/system/cpu/cpuidle/current_driver'
adb shell 'for s in /sys/devices/system/cpu/cpu0/cpuidle/state*; do
  echo "$s"
  cat "$s/name" "$s/desc" "$s/latency" "$s/residency" "$s/usage" "$s/time"
done'
```

`latency`、`residency` 的公开 sysfs 单位通常为微秒，`time` 是累计驻留时间。具体
state 名称和数量由平台 driver/固件决定。量产 user build 可能因权限或 SELinux
限制无法读取全部节点，可在 userdebug build 上复现。

### 7.4 核对 schedutil

下面的命令用于逐个 cpufreq policy 查看当前 governor、频率边界和更新间隔：

```bash
adb shell 'for p in /sys/devices/system/cpu/cpufreq/policy*; do
  echo "$p"
  cat "$p/scaling_governor" "$p/scaling_min_freq" "$p/scaling_max_freq"
  cat "$p/schedutil/rate_limit_us" 2>/dev/null
done'
```

如果 governor 不是 `schedutil`，本文的 sugov 路径就不是该 policy 的运行路径。
即便 governor 是 `schedutil`，policy min/max、thermal cooling、firmware 和
driver 仍可能改变最终频点。

### 7.5 用 Perfetto 建立时间相关性

下面的配置用于同时采集 idle、频率与调度事件，避免只看累计计数：

```protobuf
buffers {
  size_kb: 32768
  fill_policy: RING_BUFFER
}
data_sources {
  config {
    name: "linux.ftrace"
    ftrace_config {
      ftrace_events: "power/cpu_idle"
      ftrace_events: "power/cpu_frequency"
      ftrace_events: "sched/sched_switch"
      ftrace_events: "sched/sched_wakeup"
      atrace_categories: "power"
    }
  }
}
duration_ms: 15000
```

环形缓冲区可限制长时间采集的内存占用；这里选取的四组 ftrace event 用来观察
idle 进出、频率变化、任务切换和唤醒来源，`power` atrace 类别补充 Framework 事件。

将配置保存为 `power.cfg` 后，下面的命令在设备端生成 trace：

```bash
adb shell perfetto --txt -c - -o /data/misc/perfetto-traces/power.perfetto-trace \
  < power.cfg
adb pull /data/misc/perfetto-traces/power.perfetto-trace
```

分析时按时间对齐 PMS 的 `updatePowerState`/mode 事件、runnable task、CPU frequency
和 CPU idle state。看到 mode 事件后频率变化，只能证明二者相关；还要结合
schedutil util、policy limit 与厂商 Power HAL trace，才能判断是场景约束还是负载
变化造成的。

## 8. 常见误判与检查方法

| 现象 | 容易得出的错误结论 | 更可靠的检查 |
| --- | --- | --- |
| `INTERACTIVE=false` 后频率仍高 | PMS 没有控制 schedutil | 查 runnable task、uclamp、thermal/firmware constraint 和 policy min |
| 灭屏后没有深 idle | cpuidle 没收到 Device Idle | 查 timer/IRQ、latency QoS、state disable、driver 与 vendor hook |
| `setMode()` 返回成功 | 厂商已经执行调频 | 核对 HAL 实现和实际约束变化；AOSP 示例本身是日志空操作 |
| `rate_limit_us=1000` | Android 17 固定为 1 ms | 查驱动 transition delay、启动脚本与运行期写入 |
| fast switch 已启用 | DVFS 延迟一定小于 10 μs | 用 trace 测请求到生效时间，并标注设备与频率驱动 |
| Doze 已启用 | 设备已经 system suspend | 查 suspend blocker、wakeup source 和 suspend residency |
| CPU 平均利用率低 | 应当长期驻留最深 state | 检查短周期唤醒与每次 idle duration 分布 |

## 9. 面向开发与移植的结论

1. PMS 的职责边界止于 Android 电源状态、suspend blocker 和 Power HAL 提示。AOSP
   没有让 PMS 直接选择 cpuidle state 或 schedutil 频率。
2. Power HAL 是可选策略接口。Mode/Boost 的语义稳定，具体写什么节点由设备实现
   决定，且平台可以声明不支持或忽略提示。
3. schedutil 在 CPU 有任务运行时依据调度器需求请求性能；`rate_limit_us` 不是固定
   1 ms，最终频率仍受 policy、driver、thermal 和 firmware 限制。
4. cpuidle 在 CPU 无任务可运行后选择状态；深度取决于空闲窗口、退出延迟、timer、
   历史唤醒和设备 driver。
5. 评估功耗优化时，要以同一条 trace 对齐 Framework 状态、HAL 约束、调度器负载、
   cpufreq 与 cpuidle。缺少其中一层，只能得到相关性，不能确认因果关系。
