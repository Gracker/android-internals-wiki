# 5.34 Android 17 任务调度器优化

<!-- outline-start -->
## 要点

### 🔹 本节当前结论
Android 17 AOSP 中可以复核到的是一组分层任务执行与资源约束机制：JobScheduler、DeviceIdleController、ActivityManager/ProcessList、TaskProfiles/cgroup、内核调度器以及 Perfetto/statsd/dumpsys 观测面；这些结论锚定到本文 frontmatter 的 `android-17.0.0_r1` 与 `android17-6.18-2026-06_r6` 来源清单。[已验证: 本文 sources 中的 JobSchedulerService.java、JobStatus.java、DeviceIdleController.java、ProcessList.java、task_profiles.json 与 android17-6.18 kernel 路径]

本次时效性巡检将章节范围重新收敛到 Android 17 / API 37：正文不再使用具体后续平台版本号作为对比对象，也不把厂商预测调度、研究型 ML scheduler 或未来版本接口写成 Android 17 AOSP 主线事实。[来源: src/part1-fundamentals/ch05-cpu-power/5.34-android17-task-scheduler-optimization.md]

### 🔹 应用层：JobScheduler 是后台任务入口
Android 17 的 JobScheduler 服务源码位于 `frameworks/base/apex/jobscheduler/service/java/com/android/server/job/`。它负责把应用提交的 job 与网络、电量、idle、充电、deadline 等约束关联起来；调优重点不是“预测一个固定延迟”，而是减少不必要 job、合并可延迟任务、给出正确约束，并用 `dumpsys jobscheduler` 与 statsd 观察实际调度状态。[已验证: frameworks/base/apex/jobscheduler/service/java/com/android/server/job/JobSchedulerService.java; frameworks/base/apex/jobscheduler/service/java/com/android/server/job/controllers/JobStatus.java]

### 🔹 系统与电源层：状态约束影响任务何时能跑
Device idle、进程优先级、后台执行限制与低内存策略会共同影响任务执行窗口。`DeviceIdleController.java`、`ProcessList.java`、`task_profiles.json` 等路径可以作为 Android 17 口径的边界锚点；它们不能直接推出“后台固定 5–20% CPU”或“夜间自动延迟 5–15 秒”这类全局数值。[已验证: frameworks/base/apex/jobscheduler/service/java/com/android/server/DeviceIdleController.java; frameworks/base/services/core/java/com/android/server/am/ProcessList.java; system/core/libprocessgroup/profiles/task_profiles.json]

### 🔹 内核与观测层：用 trace 解释调度延迟
Kernel 固定到 android17-6.18-2026-06_r6 时，任务最终仍进入 Linux 调度、cpuset、uclamp/schedutil 等路径。Perfetto 中的 `sched_switch`、`sched_wakeup`、CPU frequency、power/thermal 与 JobScheduler/statsd 事件可以把“job 何时满足约束”和“线程何时获得 CPU”拆开分析。[已验证: kernel/sched/core.c; kernel/sched/fair.c; kernel/cgroup/cpuset.c; kernel/sched/cpufreq_schedutil.c]

## 扩展

### 🔸 推荐调优顺序
先确认任务是否应该存在，再确认约束是否正确，最终用 trace 区分等待约束、等待唤醒、等待 CPU、等待锁/I/O 或被热/电源策略压制。

### 🔸 版本边界
本文只讨论 Android 17 / API 37 的 `android-17.0.0_r1` 与 android17-6.18 kernel；不把后续平台版本、厂商预测调度或研究型 ML scheduler 当成 Android 17 AOSP 主线事实。[来源: src/part1-fundamentals/ch05-cpu-power/5.34-android17-task-scheduler-optimization.md]

## 1. “任务调度”要先区分五层

Android 17 没有一个平台组件同时决定后台任务准入、进程存活、线程资源组、CPU 选核和频率。各层回答的问题如下：

| 层次 | 主要组件 | 决策 |
|---|---|---|
| 后台工作准入 | JobScheduler、WorkManager | 工作何时满足执行条件 |
| 设备与应用政策 | Device Idle、App Standby、配额和后台限制 | 当前应用是否允许消耗后台资源 |
| 进程生命周期 | AMS、ProcessList、OOM adjuster、lmkd | 进程是否存在、何时被回收 |
| 线程资源属性 | TaskProfiles、cgroup、cpuset、uclamp | 线程在哪些 CPU 上竞争、使用哪些调度约束 |
| 内核运行 | EEVDF、EAS、schedutil、cpufreq | 选 CPU、选线程和请求频率 |

一项 job 仍处于 pending，Linux scheduler 还没有可调度的 worker 线程。worker 已经 runnable 后，JobScheduler 也不会替内核挑选下一位运行者。把两段等待合成一个“任务调度耗时”，会把业务约束问题误判为 CPU 调度问题。

## 2. JobScheduler 管可延期后台工作

Android 17 的 [`JobSchedulerService`](https://android.googlesource.com/platform/frameworks/base/+/refs/tags/android-17.0.0_r1/apex/jobscheduler/service/java/com/android/server/job/JobSchedulerService.java) 位于 jobscheduler APEX。应用提交的 `JobInfo` 转换为内部 `JobStatus`，由不同 controller 持续更新约束状态；具备执行资格后，服务再经过 pending queue、配额和并发管理选择可运行 job。

[`JobStatus`](https://android.googlesource.com/platform/frameworks/base/+/refs/tags/android-17.0.0_r1/apex/jobscheduler/service/java/com/android/server/job/controllers/JobStatus.java) 保存 job 身份、约束、时间和运行状态。网络、电量、充电、idle、存储、content trigger 与 quota 等条件由对应 controller 提供，不能用一个固定延迟公式预测。

WorkManager 是 Jetpack 的持久工作抽象。现代 Android 上，满足持久调度条件的工作通常通过 SystemJobScheduler 接入 JobScheduler；进程存活时也可能由库内 scheduler 直接推动已具备条件的工作。应用仍要按 WorkManager 版本和当前配置确认，不能把它描述成 Android 17 framework 的另一个系统服务。

适合 JobScheduler/WorkManager 的工作包括同步、上传、缓存维护和可重试批处理。用户点击后必须立刻给反馈的交互任务、精确闹钟和持续媒体播放有各自的 API 与生命周期，不能为了“后台可靠”全部塞进 job。

### Android 17 的调试能力

Android 17 的 [`JobScheduler`](https://android.googlesource.com/platform/frameworks/base/+/refs/tags/android-17.0.0_r1/apex/jobscheduler/framework/java/android/app/job/JobScheduler.java) 提供 `getPendingJobReasons()`、`getPendingJobReasonsHistory()` 和 `getPendingJobReasonStats()` 等调试入口，可以按 job 查看当前原因、有限历史及累计等待时间。统计接口受 feature flag 控制，使用前还要按目标构建确认可用性。这些 API 改善了可观测性，没有改变 controller、quota 和并发管理的基本职责。

`schedule()` 成功只表示系统接受 job，不承诺立刻执行。分析延迟时应记录：

- job id、触发来源和期望时限；
- 声明的约束；
- pending reason 与状态持续时间；
- 执行开始、停止原因、重试和退避；
- 业务线程的运行与 I/O 时间。

## 3. Device Idle 与配额决定执行窗口

Android 17 的 [`DeviceIdleController`](https://android.googlesource.com/platform/frameworks/base/+/refs/tags/android-17.0.0_r1/apex/jobscheduler/service/java/com/android/server/DeviceIdleController.java) 管理 light/deep idle、白名单和临时豁免等状态。JobScheduler controller、AlarmManager 和其他系统服务读取或响应这些状态，各自执行相应政策。

Doze 是系统后台政策，不是 Linux CPU idle state。设备进入 Doze 后，CPU 仍可能为获准工作、维护窗口、中断或前台活动运行；设备不在 Doze 时，单颗 CPU 也可以频繁进入 cpuidle state。

App Standby bucket、job quota、expedited work、user-initiated data transfer 和 foreground service 也有各自资格与限制。提高业务“优先级”不能绕过权限、配额或后台启动政策。对用户不可见的周期轮询应减少频率或合并，不应伪装成长驻前台任务。

## 4. AMS 影响进程生命周期，不分配固定 CPU 百分比

[`ProcessList`](https://android.googlesource.com/platform/frameworks/base/+/refs/tags/android-17.0.0_r1/services/core/java/com/android/server/am/ProcessList.java) 参与进程创建和状态管理。OOM adjuster 根据 Activity、Service、Provider、绑定关系和可感知性计算进程状态与 `oom_score_adj`，lmkd 再结合内存压力选择回收对象。

`oom_score_adj` 是内存回收输入，不是 CPU 调度优先级，也不是进程 CPU quota。进程因内存压力被杀、被冻结或重新创建时，job 可能中断和重试；这属于生命周期影响。

CPU 竞争要继续查看线程的 nice、调度策略、cgroup weight、cpuset、uclamp、affinity 和运行队列状态。进程处于 foreground/cached 档位可以触发一组系统政策，但没有“前台固定 80%、后台固定 20%”的平台保证。

## 5. TaskProfiles 把 Android 政策映射到内核接口

Android 17 的 [`task_profiles.json`](https://android.googlesource.com/platform/system/core/+/refs/tags/android-17.0.0_r1/libprocessgroup/profiles/task_profiles.json) 定义一批命名 profile 和 action。系统组件可通过 libprocessgroup 应用 profile，把线程或进程放入 cgroup、设置 timer slack、uclamp 或其他已配置属性。

这个 JSON 是平台基线。量产设备可以通过 vendor 配置、内核能力和启动脚本改变有效层级与数值。分析目标设备时，应把三件事对应起来：

1. 调用方申请了哪个 profile；
2. 设备上的 profile 最终包含哪些 action；
3. 目标线程当前落在哪个 cgroup/cpuset，属性值是多少。

只看到 profile 名称不能证明 action 已成功应用；只看到某个 cgroup 节点也不能知道是谁、在何时设置。

## 6. 内核分别完成选核、选人和调频

内核锚点固定为 `android17-6.18-2026-06_r6`。

### EAS 处理唤醒选核

公平任务唤醒时，[`fair.c`](https://android.googlesource.com/kernel/common/+/refs/tags/android17-6.18-2026-06_r6/kernel/sched/fair.c) 的 `select_task_rq_fair()` 处理目标 CPU 选择。EAS 条件满足时，`find_energy_efficient_cpu()` 使用任务利用率、CPU capacity 与 Energy Model 评估候选。root domain overutilized 等情况会绕开 EAS 能耗比较。

### EEVDF 处理公平实体选人

线程进入目标 CPU 的公平运行队列后，EEVDF 先判断实体是否 eligible，再比较虚拟 deadline。它不识别 JobScheduler job id、应用包名或 WorkManager tag。JobScheduler 的优先级也不会直接写入 `sched_entity.deadline`。

### schedutil 处理频率请求

[`cpufreq_schedutil.c`](https://android.googlesource.com/kernel/common/+/refs/tags/android17-6.18-2026-06_r6/kernel/sched/cpufreq_schedutil.c) 根据调度器利用率、capacity、uclamp、I/O wait 等信号更新 cpufreq policy 请求。driver、共享 policy、thermal 限制和固件决定可到达的性能状态。

三项决策可能在相近时间发生，但含义不同：

- 线程放到哪颗 CPU；
- 本 CPU 运行哪个线程；
- policy 请求多高频率。

## 7. 用状态机和 trace 定位等待发生在哪里

下面的命令用于采集调度前的系统状态：

```bash
adb shell dumpsys jobscheduler
adb shell dumpsys deviceidle
adb shell dumpsys activity processes
adb shell dumpsys batterystats
```

这些 dump 是时点或累计状态，不能替代时间线。保存输出时要同时记录复现时刻、包名、job id 和设备状态。

Perfetto 至少应包含 sched wakeup/switch、CPU frequency/idle、Binder、应用自定义 trace，以及目标构建可提供的 JobScheduler、power 和 thermal 事件。对照以下现象：

| 现象 | 下一步证据 |
|---|---|
| job 长时间 pending | pending reason、controller 状态、quota、Device Idle |
| job 已获准但进程迟迟未出现 | 进程启动、Service bind、Zygote 与 AMS |
| worker 已创建但在线程池排队 | executor queue、协程 dispatcher、WorkManager 内部状态 |
| worker runnable 但运行片段稀疏 | sched delay、CPU 竞争、cpuset、uclamp、thermal |
| worker 持续 Running 仍耗时高 | simpleperf、锁、算法、GC、数据库或序列化 |
| worker 多次阻塞 | Binder、futex、文件 I/O、网络和 wakeup |
| 周期工作频繁唤醒设备 | job/alarm 周期、maintenance window、wakeup source |

只有业务触发点、系统准入、进程启动、线程状态和工作结束同时对齐，才能把总延迟分配到各层。

## 8. 应用调优顺序

一项后台工作可以依次回答：

1. 这项工作是否必须存在，能否由服务端推送或用户操作触发；
2. 多项小工作能否合并，周期是否可以放宽；
3. 网络、充电、电量和 idle 约束是否与业务一致；
4. 唯一工作、重试、退避和取消是否正确；
5. 执行体是否受线程池排队、锁、I/O、GC 或算法拖慢；
6. 设备是否因热、低功耗模式或后台政策改变执行条件；
7. 优化后是否同时改善完成时延、唤醒次数、成功率和能量。

不要用更短的周期制造“更及时”的假象。重复唤醒、争用网络和失败重试可能让系统合并空间变小，也会增加电量与服务端负载。

## 9. 来源边界

在 `android-17.0.0_r1` 与指定内核标签中，没有独立的 ML TaskScheduler、跨应用预测启动模型或平台固定资源百分比。厂商可以叠加预测、boost、资源预取和调度 hook；这类实现必须以 vendor 源码、产品文档和设备 trace 为证据。[已验证: 本文 sources 的 AOSP 与 kernel 锚点；来源: src/part1-fundamentals/ch05-cpu-power/5.34-android17-task-scheduler-optimization.md]

未来平台接口、研究型 BPF/ML scheduler 和其他操作系统的后台调度模型也不能回填为 Android 17 行为。版本演进可以保留，但每项结论要写清首次出现版本和当前锚点实现。[来源: src/part1-fundamentals/ch05-cpu-power/5.34-android17-task-scheduler-optimization.md]
