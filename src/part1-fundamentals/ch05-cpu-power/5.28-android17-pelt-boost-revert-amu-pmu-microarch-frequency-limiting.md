# 5.28 PELT Boost 回退与 AMU/PMU 微架构感知调频

> **一句话总结**：Linux 调度器 `cpu_util()` 中基于 `runnable_avg` 的 boost 机制，曾为改善 Android UI 流畅度而设计，但在现代 ARMv9 SoC + 多层性能 hint 叠加的环境下，反而导致最高约 20% 的 SoC 功耗浪费。传音工程师通过 git bisect 定位根因、提交 LKML revert patch，并在 OSPM 2026 提出基于 AMU/PMU 的微架构感知频率限制方案，量产验证功耗下降达 10%。

---

## 要点

### 🔹 Linux 调度器 cpu_util() Boost 机制的起源与设计意图

#### PELT 双信号体系

PELT（Per-Entity Load Tracking）从 Linux 3.8 开始引入，为每个调度实体（任务、任务组、CPU runqueue）维护两个独立的负载追踪信号：

- **`util_avg`**：任务**实际获得 CPU 执行时间**的指数加权移动平均（EWMA）。窗口约 32ms，归一化到 0\~1024。它反映的是"CPU 实际给了多少算力"。
- **`runnable_avg`**：任务处于 **runnable 状态的总时间**（包括正在执行 + 排队等待 CPU）的 EWMA。它反映的是"任务想跑多少"。

在无 CPU 竞争时，两者几乎相等。但在 CPU contention 场景下差异显著——例如 4 个任务争抢一个 CPU，每个任务只能获得 25% 的执行时间，`util_avg` 会偏低（因为实际只跑了 25%），但 `runnable_avg` 接近满载（因为任务一直想跑）。

[已验证: 官方文档, Documentation/scheduler/sched-utilization.rst — PELT signals: util_avg vs runnable_avg]

> 详见 §5.1 Linux 进程调度基础 和 §5.2 EAS 能量感知调度 中对 PELT 的基础解析。

#### Boost 的设计初衷

Linux 调度器在 `cpu_util()` 函数中实现了一个 boost 逻辑：当 `runnable_avg` 明显高于 `util_avg` 时，将 boost 后的值（取 `runnable_avg` 和 `util_avg` 的某种组合）作为 CPU utilization 返回给 schedutil governor。

推理链路如下：

```
runnable_avg >> util_avg
  → 说明有大量任务在排队
  → 可能 CPU 频率不够，导致任务执行慢
  → schedutil 更积极地提频
  → CPU 频率提升，任务更快完成，排队减少
```

这个设计在早期 Android（Android 7\~10 时代）有其实际价值：

1. **PELT 响应慢**：`util_avg` 使用 EWMA 平滑，新任务唤醒后需要约 32ms 才能爬升到真实负载水平。而 Android UI 线程 / RenderThread 的工作模式是"短而急"——任务执行时间可能只有几毫秒，PELT 还没反应过来任务就结束了。
2. **schedutil 提频慢**：如果只看 `util_avg`，CPU 频率在任务到来时来不及拉升，导致 UI 线程在低频下执行，错过帧预算（\~16.6ms for 60Hz, \~8.3ms for 120Hz）。
3. **Android 图形管线的延迟敏感性**：Choreographer → RenderThread → GPU → SurfaceFlinger 的管线中，任何一环因 CPU 频率不足而延迟，都会导致掉帧。

因此，引入 `runnable_avg` boost 的目的是：**在 PELT 还没反应过来时，用排队信号提前补一脚油门**。JankBench 等流畅度测试工具正是在这种背景下被用于验证 UI 流畅度提升。

[来源: Cubox/一个 Linux 调度器优化，让 Android 多耗 20% 的电 — 2026-06-04]

#### schedutil 调频链路

Android 手机的 CPU 调频路径可以简化为：

```
任务运行 / 唤醒 / 迁移
  → 调度器更新 PELT 信号
  → schedutil 读取 cpu_util()
  → 计算目标频率
  → cpufreq 驱动切换到对应 OPP (Operating Performance Point)
```

关键代码路径（Linux mainline `kernel/sched/cpufreq_schedutil.c`）：

```c
// schedutil governor 的频率更新回调
static void sugov_update_single(struct update_util_data *hook, u64 time, unsigned int flags)
{
    // ...
    util = sugov_get_util(sg_cpu);  // 内部调用 cpu_util_cfs_boost()
    // ...
    sg_cpu->util = sugov_effective_cpu_perf(sg_cpu->cpu, util, ...);
    // → 最终触发 cpufreq 频率切换
}
```

其中 `cpu_util_cfs_boost()` 会返回包含 runnable_avg boost 的 utilization 值。一旦该值偏高，CPU 就更容易被推到高频。**在 Android 上，这不是一个无关紧要的小数值差异——它直接决定了 CPU 在每个调度 tick 后被设在什么频率**。

[已验证: AOSP android-17.0.0_r1, kernel/sched/cpufreq_schedutil.c — schedutil 由调度器事件驱动，每次负载更新都会评估频率]

### 🔹 Boost 机制在现代 Android 设备上的功耗回退

#### 问题发现

传音控股（Transsion）内核工程师 Hongyan Xia（夏弘彦）在升级 Linux 内核版本后，发现多款 Android 手机的 SoC 功耗出现明显上升。测试覆盖以下场景：

| 场景 | 类型 | 功耗异常 |
|------|------|----------|
| YouTube 1080p60 | 视频播放 | SoC 功耗偏高 |
| 无尽对决 (Mobile Legends) | 重载游戏 | SoC 功耗偏高 |
| 原神 (Genshin Impact) | 重载游戏 | SoC 功耗偏高，最高约 **20%** |
| 多种真实手机工作负载 | 综合 | CPU 更常维持高频 |

**关键观察**：CPU 频率确实更高了，但性能没有明显提升——功耗却显著增加。这种"光耗电、不干活"的现象表明频率提升未能转化为性能收益。

[来源: Cubox/一个 Linux 调度器优化，让 Android 多耗 20% 的电 — 2026-06-04]

#### 根因分析：Boost 的假设在现代设备上失效

Boost 机制的隐含假设是：

```
runnable_avg 高 → CPU contention → CPU 频率不够 → 提频能改善体验
```

但在现代 Android 设备上，这个推理链的多个环节不成立：

**1. 任务排队 ≠ CPU 频率不够**

`runnable_avg` 高只能说明"有任务在排队"，但排队的原因可能是：

- **GPU 瓶颈**：游戏主线程在等待 GPU fence，提高 CPU 频率无济于事
- **内存带宽压力**：数据搬运成为瓶颈，CPU 提频不改变带宽限制
- **锁竞争**：任务等待 mutex/spinlock，不是 CPU 算力问题
- **Binder 调度延迟**：跨进程通信的唤醒延迟导致任务堆积
- **Thermal 限制**：温控策略已经限制了 SoC 性能输出
- **线程模型不合理**：应用自身创建了过多线程竞争同一资源

在这些场景下，提高 CPU 频率并不能减少排队——瓶颈不在 CPU。

**2. 现代 Android 已有更精准的性能 hint 机制**

Android 12+ 引入了 ADPF（Android Dynamic Performance Framework），允许游戏和性能敏感应用直接向系统传递性能需求：

```java
// ADPF 示例：性能敏感时段请求高频
PerformanceManager pm = getSystemService(PerformanceManager.class);
try (PerformanceHintSession session = pm.createHintSession(
        Thread.currentThread(), /* targetDurationNanos */ 16_000_000)) {
    session.reportActualWorkDuration(/* actualDurationNanos */ 12_000_000);
    session.updateTargetWorkDuration(/* newTargetNanos */ 16_000_000);
}
```

ADPF 比调度器靠 `runnable_avg` 盲猜更精准——应用知道自己需要多少算力。在 ADPF 已经提供明确 hint 的情况下，调度器再叠加一层 boost 就变成了"多层策略叠加 → 过度提频"。

**3. SoC 厂商已有自己的提频策略**

SoC 厂商（Qualcomm RPMh/PDC、MediaTek MTLP/dvfsrc、Samsung ASV）和系统厂商都有自己的 Power HAL hint、thermal governor、GPU governor。如果厂商已经对前台 App、SurfaceFlinger、RenderThread 做了 boost，Linux 调度器再根据 `runnable_avg` 加一层 boost，就形成了：

```
厂商 Power HAL boost
  + ADPF hint boost
  + schedtune boost (legacy)
  + cpu_util() runnable_avg boost  ← 这层多余了
  = 过度提频 → 功耗飙升
```

[来源: Cubox/一个 Linux 调度器优化，让 Android 多耗 20% 的电 — 2026-06-04]

> 详见 §5.4 DVFS 与功耗管理 和 §17.21 Android 17 SoC 厂商 Power HAL 与 schedutil 闭环。

#### 排查链路

传音工程师的排查过程是一个教科书级的 Linux 内核性能问题定位案例：

```
1. 发现功耗异常（升级内核版本后）
   ↓
2. 确认问题可复现（多款设备、多个场景）
   ↓
3. git bisect 二分定位
   - 在新旧内核版本之间二分
   - 每个中间 commit 跑功耗测试
   - 最终锁定到 cpu_util() boost 相关 patch
   ↓
4. 分析根因（见上一节）
   ↓
5. 编写 revert patch 并提交 LKML
```

#### LKML Patch

传音工程师 Hongyan Xia 在 LKML 提交了：

> **[PATCH] sched/fair: Revert boost in cpu_util()**
> 提交时间：2026-05-18
> 邮件归档：https://lore.kernel.org/lkml/20260518024039.932-1-hongyan.xia@transsion.com/

Patch 的核心内容是将 `cpu_util()` 中基于 `runnable_avg` 的 boost 逻辑移除，使 schedutil 回归仅依赖 `util_avg` 做频率决策。

技术论证要点：
1. 在多个真实工作负载（YouTube、游戏、AI 推理）上，revert 后 SoC 功耗显著下降
2. 用户可感知的流畅度没有退化（JankBench / 帧率无明显变化）
3. Boost 机制解决的问题（PELT 响应慢、schedutil 提频慢）已被 ADPF 和厂商策略覆盖

[来源: LKML patch by Hongyan Xia, 传音 — 2026-05-18]

#### 调试方法论启示

这个案例展示了一个重要的工程问题定位模式：**"一段代码之前是好的，但经过多年迭代后，虽然没动过，可能就变成了问题"**。根因不是代码本身有 bug，而是**运行环境和生态系统发生了变化**——PELT 变快了、ADPF 出现了、厂商策略更多了、SoC 架构更复杂了。旧时代的优化在新时代可能变成负债。

### 🔹 AMU/PMU 微架构感知频率限制方案（OSPM 2026）

#### OSPM 峰会简介

OSPM（Power Management and Scheduling in the Linux Kernel）是 Linux 内核电源管理与调度子系统的全球最高技术会议，始于 2017 年，每年一届。会议规模严格限制在 50 人以内，参会者包括 Linux 内核 Power Management 和 Scheduler 子系统的核心 Maintainer，以及来自 Arm、Google、Red Hat、Meta 等顶级企业的技术专家。

历届 OSPM 讨论的议题往往直接决定后续 Linux 内核主线代码的演进方向。

[已验证: 官方文档, https://lwn.net/Articles/1078696/ — OSPM 2026 议程与资料]

#### ARM AMU 与 PMU 能力

- **AMU（Activity Monitors Extension）**：ARMv8.6-A 引入的架构级活动监视器，提供 CPU 周期级计数器：
  - `CPU_CYCLES`：CPU 周期总数
  - `CONST_CYCLES`：常数周期（执行有效指令的周期）
  - `STALL_MEM`：因等待内存而停顿的周期
  - 其他架构定义的 Stall 原因计数器

- **PMU（Performance Monitor Unit）**：ARMv8-A 的性能监视单元，提供更丰富的微架构事件：
  - L1/L2/L3 cache miss / hit
  - Branch prediction miss
  - Pipeline stall 原因（前端 / 后端 / 内存层次）
  - 各级 TLB miss

AMU 是架构标准化的，所有 ARMv8.6+ 实现都必须提供；PMU 是实现定义的，不同 SoC 厂商可能提供不同的事件集。

[已验证: 官方文档, ARM Architecture Reference Manual — AMU v1.1 (ARMv9.2-A), PMU v3 (ARMv8-A)]

#### 核心思想：区分"有效繁忙"与"无效繁忙"

传音方案的核心创新是利用 AMU/PMU 计数器在微架构层面区分两种 CPU 繁忙状态：

| 状态 | 表现 | AMU/PMU 特征 | 决策 |
|------|------|-------------|------|
| **有效繁忙** | CPU 全速执行有用指令 | `CPU_CYCLES` ≈ `CONST_CYCLES`，stall 占比低 | 维持 / 提升频率 |
| **无效繁忙** | CPU 高频但大部分时间在等待 | stall 占比高（如等内存、等 GPU） | **限制频率** |

数据驱动的频率限制流程：

```
1. 采样 AMU/PMU 计数器
   → 获取 stall 占比、cache miss 率等微架构指标

2. 评估"频率有效性"
   → 如果频率提升后，stall 占比反而上升（更多等待）
   → 说明当前处于"频率提升但性能停滞"的无效区间

3. 频率限制干预
   → 识别到无效功耗区间时
   → 主动抑制 schedutil 的频率拉升请求
   → 将 CPU 维持在"够用且高效"的甜点频率
```

这个方案的关键优势是**数据驱动而非启发式规则**——不是猜测"runnable 高可能需要提频"，而是用实际微架构计数器数据判断"提频是否有用"。

#### 方案通用性

该方案适配所有支持 AMU/PMU 接口的 ARMv9+ 架构芯片，不依赖特定 SoC 厂商的私有接口。这一点对 Linux 内核社区合入至关重要——mainline 内核只接受通用方案，不接受厂商特异实现。

### 🔹 对 Android 应用性能优化的启示

#### CPU 频率 ≠ 应用性能

这是本节最重要的认知纠正。应用开发者（尤其是游戏和 AI 应用）需要理解：

- **SoC 级资源瓶颈是多元的**：CPU、GPU、NPU、内存带宽、散热——任何一个成为瓶颈都会限制整体性能
- **盲目请求高频反而有害**：过高的 CPU 频率 → 更快耗电 → 更快触发热限制 → SoC 降频 → 性能反而下降
- **正确的做法**：通过 ADPF 精确告知系统你的性能需求，让系统做全局最优决策

#### ADPF 与 schedutil 的协作边界

```
应用层 (ADPF)
  → "我需要这帧在 16ms 内完成"
  → 系统根据当前资源状况决定最优频率组合（CPU + GPU + 内存带宽）

内核层 (schedutil + AMU/PMU)
  → 监测频率有效性
  → 在"无效功耗区间"主动限制频率
  → 将省下的功耗预算留给真正需要的场景
```

应用层和内核层各司其职：应用知道自己需要什么（延迟目标），内核知道硬件能做到什么（微架构状态）。`runnable_avg` boost 的错误在于让内核去猜应用的意图，而 AMU/PMU 方案的正确在于让内核专注于硬件效率监测。

#### OEM 厂商的差异化功耗优化路径

传音在 OSPM 2026 的实践表明，OEM 厂商可以通过以下路径在 Linux 内核社区框架内做差异化：

1. **发现通用机制的问题**：在真实设备上暴露 Linux mainline 代码的适用性缺陷
2. **提交根因修复**：如 revert patch，直接修复 mainline 代码
3. **贡献创新方案**：如 AMU/PMU 微架构感知方案，推动 mainline 演进
4. **获得社区认可**：OSPM 峰会宣讲 → Maintainer 讨论上游合入 → 进入 mainline

这条路径对所有中国手机厂商（小米、OPPO、vivo 等）都有借鉴意义。

### 🔸 PELT 信号在 Android 性能分析中的观测方法

#### Perfetto 中观察 PELT 信号

在 Perfetto trace 中，可以通过以下 track 观察 PELT 相关数据：

1. **CPU Scheduling track**：查看任务的 `util_avg` 变化（通过 `sched/cpu_util` 数据源）
2. **CPU Frequency track**：查看 schedutil 设置的实际频率
3. **`ftrace/raw` track**：过滤 `sched_util_*` 事件，观察 `cpu_util()` 返回值和 schedutil 的频率决策

#### 判断"无效功耗区间"的方法

1. 在 Perfetto 中同时显示 CPU 频率和任务 runnable 时间
2. 如果频率持续在高区间，但任务的 `util_avg` 并不高且帧率稳定——可能处于无效功耗区间
3. 结合 GPU frequency track 和 thermal track 判断瓶颈是否在其他硬件单元
4. 使用 simpleperf 或 Perfetto 的 PMU counter 数据源获取微架构级 stall 信息

### 🔸 与 sched_ext / BPF 可编程调度器的关系

`sched_ext`（sched_ext / extsched）是 Linux 6.12+ 引入的可编程调度器框架，允许通过 BPF 程序自定义调度策略。在 `sched_ext` 框架下：

- OEM 厂商可以实现类似 AMU/PMU 频率限制的自定义调度策略，无需修改 mainline CFS 代码
- 这降低了 OEM 差异化优化的门槛——从"修改 mainline → 提交 LKML → 等待合入"简化为"编写 BPF 程序 → 部署到自己的设备"
- 但 `sched_ext` 的 CPU governor 交互接口仍在演进中，Android 对 `sched_ext` 的支持状态也需跟进

### 🔸 传音内核技术团队的系统性优化方向

根据 OSPM 2026 演讲中展示的未来规划，传音内核团队的三大方向：

1. **软硬一体化调频**：基于 AMU/PMU 的微架构感知扩展到 GPU/NPU 频率协同
2. **精细化内存管理**：内核内存子系统的细粒度调优，针对不同工作负载的内存策略
3. **智能精准调度**：结合 ML 模型的任务调度优化

这三大方向对中国手机厂商的内核团队建设和技术路线规划有参考价值。
