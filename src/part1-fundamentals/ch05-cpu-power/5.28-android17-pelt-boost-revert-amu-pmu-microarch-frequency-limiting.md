# 5.28 PELT Boost 回退与 AMU/PMU 微架构感知调频

<!-- outline-start -->
## 要点

### 🔹 Linux 调度器 cpu_util() Boost 机制的起源与设计意图
- PELT（Per-Entity Load Tracking）双信号：util_avg（实际执行时间）与 runnable_avg（排队等待时间）
- Boost 机制初衷：在 CPU contention 场景下，仅看 util_avg 会低估 CPU 需求，引入 runnable_avg 使 schedutil 更积极提频
- Android 图形管线（Choreographer → RenderThread → GPU）对调度器响应延迟的敏感性

### 🔹 Boost 机制在现代 Android 设备上的功耗回退
- 传音工程师在升级 Linux 内核版本后发现多款 Android 手机 SoC 功耗明显上升（最高约 20%）
- 根因：runnable_avg boost 在 CPU 受其他硬件资源瓶颈（GPU/NPU/内存带宽）限制时，盲目拉升 CPU 频率
- "光耗电、不干活"现象：频率提升但性能停滞，形成无效功耗区间
- 测试场景：YouTube 1080p60、无尽对决、原神等重载游戏

### 🔹 Git Bisect 定位流程与调试方法论
- 从功耗异常到内核 patch 定位的完整排查链路
- LKML patch：[PATCH] sched/fair: Revert boost in cpu_util()
- 传音在 LKML 提交的 revert patch 及其技术论证

### 🔹 AMU/PMU 微架构感知频率限制方案（OSPM 2026）
- ARM AMU（Activity Monitors Extension）与 PMU（Performance Monitor Unit）在 ARMv9 架构中的能力
- 核心思想：通过 AMU/PMU 计数器精确区分"有效繁忙"与"无效繁忙"
- 微架构感知的频率限制机制：数据驱动识别"频率提升但性能停滞"的无效区间
- 方案通用性：适配所有支持 AMU/PMU 接口的 ARMv9+ 架构芯片

### 🔹 量产验证结果与收益数据
- 重载游戏（原神）：功耗下降 10%
- 端侧大模型推理：功耗降低 1W
- 用户体验无损：不牺牲可感知的流畅度与响应速度
- 验证平台：天玑 8400 等主流 SoC

### 🔹 对 Android 应用性能优化的启示
- CPU 频率 ≠ 应用性能：理解 SoC 级资源瓶颈（CPU/GPU/NPU/内存带宽/散热）
- 应用层 ADPF 与内核层 schedutil 的协作边界
- OEM 厂商如何利用内核社区机制做差异化功耗优化
