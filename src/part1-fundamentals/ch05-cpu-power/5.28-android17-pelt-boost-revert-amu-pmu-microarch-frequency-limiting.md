# 5.28 Android 17 runnable boosting、修复提案与 AMU/PMU 调频研究

> **结论边界**
>
> - 在内核锚点 `android17-6.18-2026-06_r6` 中，`cpu_util()` 的 runnable boosting 仍然存在，schedutil 仍会调用 `cpu_util_cfs_boost()`。
> - 2026 年 5 月发布的 `Revert boost in cpu_util()` 是邮件列表提案，不能写成 Android 17 已采用的行为。
> - 2026 年 6 月进入 `tip:sched/core` 的补丁只修正迁移预测时混用 `runnable_avg` 与 `util_avg` 的算术；它保留 boosting，而且尚未出现在上述 Android 17 内核标签中。
> - OSPM 2026 的 AMU/PMU 工作展示了用硬件计数器和回归模型限制无收益提频的研究方向。公开资料不足以证明它已成为 Android 17、Linux 主线或某类 Arm SoC 的通用机制。

这四条边界需要同时成立。只写“回退节省约 20% 功耗”，会把单个平台的补丁实验、上游讨论和 Android 设备现状混在一起。

## 1. 先区分 PELT 的几个信号

PELT（Per-Entity Load Tracking）用指数衰减平均值跟踪调度实体和 CPU 运行队列。内核文档给出的参数是：每个周期为 1024µs，并令 `y^32 = 0.5`。因此最近约 32ms 的样本贡献一半权重。32ms 是**半衰期**，不是只保留 32ms 数据的固定窗口。

与该机制直接相关的信号如下：

| 信号 | 近似含义 | 不能直接推出什么 |
| --- | --- | --- |
| `util_avg` | 实体获得 CPU 执行时间形成的平均利用率，并按 CPU 容量与频率做尺度处理 | 不能单独说明任务是否受内存、锁或其他设备限制 |
| `runnable_avg` | 实体处于 runnable 状态的平均值；对运行队列聚合后可反映 CPU 上的可运行竞争 | 不能判断提高 CPU 频率后吞吐是否会上升 |
| `util_est` | 对周期性任务的利用率做快速估计，缓解任务睡眠后 PELT 衰减带来的调频爬升 | 不是 `runnable_avg` 的别名 |
| `uclamp` | 给任务或运行队列施加有效利用率上下界 | 不等同于直接指定某个 CPU 频点 |

当单个 CPU 上只有一个持续运行的任务时，running 与 runnable 两类信号通常接近。多个任务同时可运行时，运行时间要在任务间分配，而 runnable 时间会反映排队竞争，二者可能拉开。

这里还要排除一个常见误读：等待 mutex、futex、Binder 回复或 GPU fence 的线程通常处于睡眠状态，等待期间不会继续贡献 runnable 时间。`runnable_avg` 偏高说明 CPU 运行队列存在可运行竞争，但它无法分辨这些线程是相互独立的计算任务，还是吞吐受生产者、消费者、缓存或内存系统限制的任务集合。

## 2. Android 17 内核锚点中 boosting 仍在工作

下面的源码节选用于确认 `android17-6.18-2026-06_r6` 的默认回退路径。代码省略了 `util_est` 和容量封顶部分，只保留相关分支。

```c
static unsigned long
cpu_util(int cpu, struct task_struct *p, int dst_cpu, int boost)
{
    struct cfs_rq *cfs_rq = &cpu_rq(cpu)->cfs;
    unsigned long util = READ_ONCE(cfs_rq->avg.util_avg);
    unsigned long runnable;

    if (boost) {
        runnable = READ_ONCE(cfs_rq->avg.runnable_avg);
        util = max(util, runnable);
    }

    if (p && task_cpu(p) == cpu && dst_cpu != cpu)
        lsub_positive(&util, task_util(p));
    else if (p && task_cpu(p) != cpu && dst_cpu == cpu)
        util += task_util(p);

    /* 后续还会与 util_est 比较，并按 CPU capacity 封顶 */
}

unsigned long cpu_util_cfs_boost(int cpu)
{
    unsigned long util = INT_MAX;

    trace_android_rvh_cpu_util_cfs_boost(cpu, &util);
    if (util != INT_MAX)
        return util;

    return cpu_util(cpu, NULL, -1, 1);
}
```

`boost == 1` 时，初始利用率取 `max(util_avg, runnable_avg)`。Android common kernel 还在 `cpu_util_cfs_boost()` 前放置了 restricted vendor hook：厂商模块可以返回自定义值；没有模块接管时，才执行下方的通用 boosting。因而“源码标签的默认行为”和“一台商品机的运行时行为”仍需分别验证。

schedutil 在同一标签中的取值路径如下。这个片段用于确认 CPUFreq 侧传给 `cpu_util()` 的 `p` 为 `NULL`。

```c
static void sugov_get_util(struct sugov_cpu *sg_cpu, unsigned long boost)
{
    unsigned long min, max;
    unsigned long util = scx_cpuperf_target(sg_cpu->cpu);

    if (!scx_switched_all())
        util += cpu_util_cfs_boost(sg_cpu->cpu);

    util = effective_cpu_util(sg_cpu->cpu, util, &min, &max);
    util = max(util, boost);
    sg_cpu->util = sugov_effective_cpu_perf(
            sg_cpu->cpu, util, min, max);
}
```

这里至少有四种输入需要分开理解：CFS 利用率、sched_ext 的 CPU performance target、RT/DL/IRQ 与 uclamp 形成的有效边界，以及 schedutil 自身的 I/O-wait boost。`runnable_avg` boosting 只是其中一项，删除它不代表 schedutil 从此只读取裸 `util_avg`。

### 2.1 谁会读取 boosted utilization

| 使用者 | r6 中的入口 | 作用 |
| --- | --- | --- |
| schedutil | `cpu_util_cfs_boost(cpu)` | 为 CPUFreq 计算利用率输入；`p == NULL` |
| EAS | `cpu_util(cpu, p, dst_cpu, 1)` | 预测任务迁移到候选 CPU 后的最大利用率和能耗状态 |
| 负载均衡 | `cpu_util_cfs_boost(cpu)` | `migrate_util` 路径评估运行队列 |
| Android 厂商扩展 | `android_rvh_cpu_util_cfs_boost` | 可在默认实现之前替换返回值 |

所以，这个机制同时影响调频与部分放置/均衡判断。分析功耗回归时，不能只盯着 `scaling_cur_freq`；CPU 迁移、簇选择和频率驻留时间也要一起看。

## 3. 2026 年补丁的准确时间线

| 时间 | 事件 | 截至 2026-07-25 的边界 |
| --- | --- | --- |
| 2023 年 | `7d0583cf9ec7` 引入 runnable boosting，定义 boosted utilization 为 `max(CPU runnable, CPU utilization)` | 设计目标是利用 runnable 信号感知 CFS 竞争；原始提交没有把它描述为 Android UI 或 JankBench 专用优化 |
| 2026-05-18 | Hongyan Xia 发布 v1 `Revert boost in cpu_util()` | 提案 |
| 2026-05-28 | v2 补充 YouTube、Mobile Legends、Genshin Impact 数据，并继续建议完整删除 boost | 提案；讨论中维护者要求继续寻找比直接删除更合适的竞争度量方式 |
| 2026-06-05 | v2 `Fix cpu_util runnable_avg arithmetic` 发布 | 把可独立确认的算术错误拆成小补丁 |
| 2026-06-09 | 补丁以 `29922fdfc2a4` 进入 `tip:sched/core` | 保留 boosting，只修正迁移时的信号运算 |
| Android 17 r6 标签 | `fair.c` 仍是修复前写法，schedutil 仍调用 `cpu_util_cfs_boost()` | 当前采用的内核现状 |

“完整回退”“已进入调度器开发分支的修复”和 Android 17 r6 分属三种状态。

### 3.1 完整回退提案报告了什么

v2 邮件给出了下面三组结果：

| 场景 | 有 boost | 无 boost | 邮件报告的差异 |
| --- | --- | --- | --- |
| YouTube 1080p60 | 59.94 FPS，SoC 913.6mW | 59.93 FPS，SoC 720.4mW | SoC 功耗 -21.15% |
| Mobile Legends | 120.16 FPS，标准差 0.47，总功耗 3294.10mW | 120.07 FPS，标准差 0.56，总功耗 2996.09mW | 总功耗 -9.05% |
| Genshin Impact，中画质 | 60.05 FPS，标准差 0.34，总功耗 6215.84mW | 60.03 FPS，标准差 0.35，总功耗 5695.46mW | 总功耗 -8.37% |

这些数字是补丁作者在其测试平台上的报告，可以证明“当前算法在某些移动工作负载上可能造成显著能耗回归”，但不能外推为：

- 所有 Android 设备都多耗 20%；
- 原神场景节省 20%；
- 回退对所有延迟、尾帧、触控响应和热稳态都没有影响；
- 完整回退已获上游接受。

公开邮件没有给出足够完整的硬件型号、构建配置、环境温度、重复次数、置信区间和功耗轨道定义。复现实验必须补齐这些条件。

### 3.2 算术错误在哪里

r6 先执行：

`util = max(rq->util_avg, rq->runnable_avg)`

随后在模拟任务迁移时，却对这个结果加减 `task_util(p)`。如果前一步选中的是 `runnable_avg`，后一步就把 task utilization 加到或减自 runqueue runnable，量纲对应的信号不一致。

进入 `tip:sched/core` 的修复分别维护两条路径：

1. `util_avg` 只加减 `task_util(p)`；
2. `runnable_avg` 只加减 `p->se.avg.runnable_avg`；
3. 两条迁移预测都完成后，再计算 `max(util, runnable)`。

这会改进 EAS 的迁移后利用率预测。它不会改变 schedutil 的 boosting，因为 schedutil 调用 `cpu_util(cpu, NULL, -1, 1)`，没有待迁移任务，也就不会执行上述加减运算。补丁讨论中，作者也明确指出 CPUFreq 一侧的频率问题仍在。

### 3.3 为什么不能用 ADPF 为完整回退背书

Android 17 的 `PerformanceHintManager.Session` 允许周期性工作负载报告目标工期和本轮实际工期。Power HAL AIDL 则把 hint session 交给设备实现，并明确允许平台自行决定如何响应。

这条路径与内核 PELT/schedutil 处于不同层次：

```text
应用或系统组件
  └─ PerformanceHintManager：目标工期、实际工期、线程集合
       └─ Power HAL hint session：设备厂商解释并执行策略

内核调度器
  └─ PELT / util_est / uclamp / runnable boosting
       └─ schedutil / cpufreq：请求 CPU 性能状态
```

该图用于划清接口边界。ADPF 可以影响厂商的 CPU、GPU 或内存策略，但接口契约没有规定它必须关闭 `cpu_util_cfs_boost()`。不支持 hint session、没有建立 session、厂商忽略 hint，或者工作负载未按周期正确上报时，内核调度路径仍按设备配置运行。因此，不能把“设备存在 ADPF”当作删除 boosting 的充分条件。

## 4. AMU、PMU 与“提频是否有收益”

### 4.1 Android 17 内核已经怎样使用 AMU

Armv8.4-A 引入 Activity Monitors Extension。AMU v1 的架构固定 Group 0 计数器包括：

| 计数器 | 含义 |
| --- | --- |
| `AMEVCNTR0_CORE_EL0` | core cycles |
| `AMEVCNTR0_CONST_EL0` | constant/reference cycles |
| `AMEVCNTR0_INST_RET_EL0` | instructions retired |
| `AMEVCNTR0_MEM_STALL` | memory stall cycles |

支持情况还受 CPU 实现、固件是否启用、内核配置和勘误处理影响，不能只看“Armv8.6”或“Armv9”标签就断定所有计数器都可用。

`android17-6.18-2026-06_r6` 的 `arch/arm64/kernel/topology.c` 使用 core/constant 两个计数器计算频率不变性比例，核心关系如下：

```text
frequency scale
  ≈ Δcore_cycles / Δconstant_cycles
    × platform maximum-frequency scale
```

这段关系用于说明 Linux 当前 AMU 用法。它估计 CPU 在采样期交付的相对频率，让 PELT 在不同 DVFS 状态下具有可比性；它并不回答这些周期完成了多少有用工作。判断 IPC 或内存停顿，还需要 retired-instruction、memory-stall 或适当的 PMU 事件。

### 4.2 PMU 的能力与限制

PMU（Performance Monitoring Unit）可以统计 CPU cycles、instructions、cache refill、branch miss 等事件，但只有一部分事件是架构定义的，更多事件由具体微架构实现。可编程计数器数量、事件编号、是否允许 EL0 访问、是否被 perf 子系统或其他调试工具占用，也会随设备变化。

因此，下列写法都过于绝对：

- “所有 Armv9 芯片都能读取同一组 L1/L2/L3 stall 事件”；
- “`CORE_CYCLES` 接近 `CONST_CYCLES` 就代表有效计算”；
- “一个通用阈值可以覆盖所有 SoC 和工作负载”。

在同一个 workload 上，IPC 下降、memory-stall 占比上升、频率增加后吞吐几乎不变，才构成“当前提频收益较低”的一组证据。单个计数器很容易受乱序执行、预取、共享缓存、内存控制器和其他 CPU 干扰。

### 4.3 OSPM 2026 工作做到哪一步

LWN 对 OSPM 2026 的报告给出了有限但清楚的范围：

- 研究动机是 CPU 可交付性能并不总与频率线性增长，缓存和 DRAM 竞争会削弱提频收益；
- 方案从 Arm64 AMU/PMU 中选择有帮助的计数器；
- 使用线性回归模型判断何时限制 CPU 频率；
- 展示结果为性能接近、能效改善。

公开报告没有给出完整补丁、模型参数、训练集、硬件覆盖范围或通用上游接口。现有证据只能支持“已公开演示的研究/工程方案”这一定位，不能写成 Linux 主线 governor、Android 17 标准能力，也不能补写“所有 Armv9 SoC 通用”“已在天玑 8400 多机型量产”“游戏固定节省 10%”“大模型固定节省 1W”等结论。

### 4.4 它与 schedutil 的关系

schedutil 文档开头就标明：利用率与工作容量近似按频率线性变化，这个假设并不完美，但便于实现。AMU/PMU 研究针对的正是线性近似失效的场景。

可以把候选控制逻辑理解成：

1. schedutil 根据调度器利用率计算需求；
2. 微架构模型估计继续提频能否增加吞吐；
3. 当模型有足够置信度认为收益很低时，对请求频率施加上限；
4. uclamp、thermal、CPUFreq policy、Power HAL 等已有约束仍要保留优先级关系；
5. 性能反馈用于防止模型在突发延迟敏感负载上误限频。

这是设计分析，不是 r6 源码描述。r6 的 arm64 AMU 代码只为频率不变性读取 core/constant counters，没有上述线性回归限频器。

## 5. 在 Android 设备上怎样验证

### 5.1 先确认设备采用哪条调频路径

下面的命令用于 userdebug/eng 或已取得相应权限的设备，先确认 governor、CPUFreq policy 和内核可导出的事件。量产 user build 可能拒绝访问 tracefs。

```bash
adb shell 'for f in /sys/devices/system/cpu/cpufreq/policy*/scaling_governor; do
  printf "%s: " "$f"
  cat "$f"
done'

adb shell 'cat /sys/kernel/tracing/available_events' \
  | grep -E '(^sched:sched_(switch|wakeup|migrate_task)$|^power:cpu_(frequency|idle)$|pelt|sugov)'
```

第一段确认设备是否使用 schedutil；第二段只列出**该内核构建实际导出的**事件。r6 源码里的 `pelt_*` 内部 tracepoint 明确标注为不导出到 tracefs，所以不要预设 Perfetto 一定存在 `sched/cpu_util` 或某个 PELT track。厂商若增加了 tracepoint，名称也应以 `available_events` 为准。

### 5.2 用 Perfetto 对齐调度、频率和业务指标

最低限度应同时采集：

- `sched_switch`、`sched_wakeup`、`sched_migrate_task`；
- `power/cpu_frequency`、`power/cpu_idle`；
- thermal、CPUFreq residency 或设备提供的功耗轨；
- SurfaceFlinger/FrameTimeline，或业务自己的帧率、延迟与吞吐指标；
- 设备可用时的 Android vendor scheduler tracepoint。

`cpu_frequency` 只能说明报告频率发生了变化。它不能独自证明电压、实际交付频率或整机功耗按相同比例变化。频率驻留、温度、任务运行位置和电源轨数据需要放在同一时间轴上。

### 5.3 用 simpleperf 检查 PMU 可用性

下面的命令用于枚举当前设备允许使用的事件，再对目标进程做短时统计。先枚举，避免照搬另一颗 SoC 的 raw event 编号。

```bash
adb shell simpleperf list hw
adb shell simpleperf list hw-cache
adb shell simpleperf stat \
  -e cpu-cycles,instructions,cache-misses \
  -p <PID> --duration 10
```

`cpu-cycles` 和 `instructions` 通常比厂商私有 stall 事件更容易跨设备，但仍可能因权限、虚拟化、计数器占用或 multiplexing 而不可用。看到 `not supported`、`0` 或极低运行占比时，应先处理采样有效性，不能直接计算 IPC。

### 5.4 A/B 实验的最低要求

1. 只改变一个变量，例如启用/禁用 vendor hook，或应用单个候选内核补丁。
2. 固定屏幕刷新率、亮度、网络条件、视频码率或游戏画质。
3. 先预热到可比较的温度区间，再记录稳态；冷启动结果和热稳态结果分开报告。
4. 同时报均值和尾部指标。视频至少看 dropped frames；游戏看帧时间分位数；推理看 token latency 或端到端延迟。
5. 区分 SoC、CPU rail 与整机输入功耗。三者不能混用。
6. 重复多轮并随机化 A/B 顺序，给出离散程度。
7. 检查 CPU 迁移和簇驻留，防止把 EAS 放置变化误判为纯调频收益。

只有在性能约束等价时，功耗差异才有解释价值。

## 6. 常见误判

### 误判一：`runnable_avg > util_avg` 等于 CPU 频率不足

这个差值表明可运行竞争增加。任务依赖、CPU affinity、短线程数量和内存系统限制都可能让“更高 runnable”无法换来同等吞吐增量。是否提频有收益还要测量。

### 误判二：完整回退已进入 Android 17

r6 源码直接否定了这一点。完整回退仍是提案；进入 `tip:sched/core` 的是迁移算术修复。

### 误判三：算术修复解决了 schedutil 功耗问题

schedutil 传入 `p == NULL`，不会执行任务迁移加减。补丁改善 EAS 计算，却保留 `max(util_avg, runnable_avg)` 对 CPUFreq 的影响。

### 误判四：ADPF 已取代内核 boost

ADPF 是可选的应用到 Power HAL 的性能提示路径，具体策略由设备实现。它与内核 runnable boosting 可以同时存在。

### 误判五：AMU 天然提供“有效工作比例”

core/constant counters 主要用于交付频率估算。instructions retired、memory stall 和 PMU 事件才可能帮助构造效率特征，而且模型仍需按硬件与负载验证。

### 误判六：看到高频且 FPS 不变，就能判定浪费

FPS 上限可能被刷新率锁住，平均 FPS 也会掩盖尾帧。需要同时比较帧时间、响应延迟、吞吐、温度与功耗。

- [ ] 把 Android 17 r6、完整回退提案、`tip:sched/core` 算术修复分开记录。
- [ ] 不把 runnable contention 直接解释成“提高 CPU 频率会增加吞吐”。
