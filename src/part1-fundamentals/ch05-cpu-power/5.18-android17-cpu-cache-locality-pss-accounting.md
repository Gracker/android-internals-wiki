# 5.18 Android 17 CPU 缓存局部性与 PSS 内存核算源码机制

“cache 优化后 PSS 会下降”是一个很容易写进性能报告、也很容易误判的结论。CPU cache 描述处理器最近使用的数据；PSS 描述进程映射的物理页如何在多个进程之间分摊。两者处在不同的抽象层，采集方法也完全不同。

本章以 Android 17 / API 37 / `android-17.0.0_r1` 和 Android common kernel `android17-6.18-2026-06_r6` 为基线，回答四个问题：

- RSS、PSS、USS 与 SwapPss 各自统计什么；
- `/proc/<pid>/smaps`、`smaps_rollup` 和 `status` 在 Android 17 中怎样被选择；
- `Debug`、`ActivityManagerService` 与 `AppProfiler` 返回或记录的值有什么差别；
- 优化数据布局后，怎样判断收益来自 CPU cache，还是来自进程驻留页变化。

CPU cache 的层级、false sharing、AoS/SoA、Startup Profile 与 Simpleperf PMU 分析见本卷另一篇 5.18《CPU Cache 友好代码与数据布局优化》。本章只保留理解 PSS 所需的 cache 边界，避免重复两套优化规则。

## 先把 CPU cache 与内存页核算分开

| 观察对象 | 常见粒度 | 回答的问题 | 主要工具 |
|---|---:|---|---|
| L1/L2/SLC | cache line，当前 arm64 kernel 基线的 L1 line 为 64 B | 数据到达执行核心的成本有多高 | Simpleperf、Arm SPE、厂商 PMU |
| TLB / 页表 | 页，设备可采用 4 KiB 或 16 KiB 等基页 | 虚拟地址翻译和页表遍历成本有多高 | PMU、Perfetto、内核 trace |
| RSS/PSS | 物理页及其映射关系 | 进程当前驻留了多少页，这些页该怎样归因 | `smaps`、`smaps_rollup`、`dumpsys meminfo` |
| Java/native heap | 对象、allocation、space/arena | 哪类分配形成了 live set | heap dump、heapprofd、allocation profiler |

一张物理页可以已经驻留在 RAM 中，同时它的某些 cache line 不在当前 CPU 的 L1/L2。此时访问会产生 cache miss，RSS/PSS 不会因为这次 miss 改变。反过来，一段代码可能通过 tiling 或 SoA 降低 L1D refill，却保持相同的映射页与 resident page 数，PSS 曲线也就基本不变。

数据布局仍可能间接改变 PSS。例如，去掉装箱对象、缩小结构体、减少 allocator 碎片，可能让进程少提交或少触碰一些页；对象池若长期保留对象，也可能抬高 live set 和驻留页。报告里应分别记录 cache 事件、CPU 时间和 PSS/RSS，不能用其中一个替代另一个。

这里还要区分 CPU cache 与 Linux page cache。文件映射页进入进程页表且驻留后，会出现在 RSS/PSS 的 file-backed 统计中；没有映射到该进程的 page-cache 页面，不会凭借“属于同一个 APK 文件”就计入该进程 PSS。

## RSS、PSS、USS 和 SwapPss 怎样计算

### RSS：每个进程都按整页计数

RSS（Resident Set Size）统计进程页表当前映射的 resident pages。某个共享页同时映射到四个进程时，每个进程的 RSS 都会按整页计入。因此，多进程 RSS 不能直接相加；直接求和会重复计算共享页。

`/proc/<pid>/status` 的 `VmRSS` 是一条便宜的汇总值。Android 17 `libmeminfo` 对它的注释很谨慎：这个值读取便宜，但不够精确；需要更可靠估计时应读取 maps/smaps。这里的“不够精确”还意味着它不提供 PSS、USS、SwapPss 和按 VMA 分类，不能把 `VmRSS` 当成低成本 PSS。

### PSS：共享页按映射数分摊

PSS（Proportional Set Size）把私有 resident page 全额归给进程，把共享页按映射数分摊。简化模型如下：

```text
PSS(process) =
    Σ private_resident_page_size
  + Σ shared_resident_page_size / page_mapcount
```

这段公式用于解释 PSS 的归因方式。Android common kernel 6.18 的 `fs/proc/task_mmu.c` 会累计 resident size；需要处理共享映射时，按 page/folio 的 mapcount 计算 PSS 份额。源码也指出，未持有 folio lock 时读到的 mapcount 是一个快照，映射并发变化时可能有轻微误差。

PSS 适合比较一个进程对系统 RAM 的相对负担，也可以在同一采样口径下汇总多个进程。它仍是观测时刻的统计结果：进程可能在读取期间继续 mmap、munmap、fault 或换页，GPU/设备内存还可能依赖 memtrack 补充。

### USS：Android 在用户态合成私有页

USS（Unique Set Size）可理解为只归当前进程使用的 resident memory。Android 17 的 `SmapsOrRollupFromFile()` 没有读取名为 `Uss:` 的字段，而是把 `Private_Clean + Private_Dirty` 累加到 `stats->uss`。

USS 适合回答“进程退出后，哪些 resident pages 更可能直接释放”。它不等于 Java heap，也不包含共享页对该进程的使用价值。

### SwapPss：交换空间也要按共享关系分摊

`Swap` 按完整换出量统计，`SwapPss` 按共享计数分摊换出页。Android 的若干总量 API 会把 SwapPss 加入返回值：

- `Debug.getPss()` 的 JNI 实现把 `stats.pss`、`stats.swap_pss` 和额外的 memtrack 归因相加；
- `Debug.MemoryInfo.getTotalPss()` 返回三个 heap 类别的 PSS，再加 `getTotalSwappedOutPss()`。

所以日志中的 “total PSS” 需要注明来自哪个 API。直接读取 `smaps_rollup` 的 `Pss:`，与 `Debug.getPss()` 的数值口径并不完全相同。

## kernel 输出：`smaps` 与 `smaps_rollup` 精度相近，信息量不同

### `smaps` 保留每个 VMA

`/proc/<pid>/smaps` 在每个 VMA 后输出 `Rss`、`Pss`、private/shared clean/dirty、SwapPss 等字段。它能回答：

- 哪个 `.so`、DEX/OAT/ART 文件或匿名映射占用内存；
- Java、native、stack、graphics 等类别如何归因；
- 某个映射是否出现大页、锁页或异常增长。

代价来自内核遍历页表、生成大量文本，以及用户态逐 VMA 解析。VMA 很多时，输出量与解析成本会明显增加。

### `smaps_rollup` 仍会遍历内存映射

`/proc/<pid>/smaps_rollup` 把全进程统计聚合成一个记录。它减少了输出和用户态解析，不保留每个 VMA 的路径与分类。

“rollup”不表示读取成本变成常数。Android common kernel 的 `show_smaps_rollup()` 仍遍历 VMA 并执行 page walk，随后由 `__show_smap()` 输出汇总字段。它通常比读取整份 `smaps` 更适合周期性总量采样，但加速倍数会随 VMA 数量、驻留页、page-table 状态、内核和硬件变化。没有目标设备测量时，不应写固定的 1–5 ms 或 50–100 倍。

### 两条路径不是精度逐级下降

对于 `Pss`、`Rss`、private clean/dirty 和 `SwapPss` 这些汇总字段，`smaps` 与 `smaps_rollup` 都来自内核 smaps 页表统计。主要差别是输出粒度和用户态开销，不应把 rollup 称为“低精度 PSS”。

`/proc/<pid>/status` 的 `VmRSS` 则是另一项指标。它缺少共享页比例信息，不能组成 `smaps → smaps_rollup → status` 的三层 PSS 降级模型。

## Android 17 `libmeminfo` 的选择逻辑

`ProcMemInfo::SmapsOrRollup()` 的核心逻辑很短：

```cpp
std::string path = StringPrintf(
        "/proc/%d/%s", pid_,
        IsSmapsRollupSupported() ? "smaps_rollup" : "smaps");
return SmapsOrRollupFromFile(path, stats);
```

这段代码说明周期性总量采样优先选择 `smaps_rollup`；设备不支持时才选择 `smaps`。选定文件后，parser 只累计 `Pss`、`Rss`、`Private_Clean`、`Private_Dirty` 和 `SwapPss`，并用两项 private 值合成 USS。它没有在 `smaps_rollup` 打开失败后再读 `status`。

### 支持探测是进程级缓存

`IsSmapsRollupSupported()` 首次检查 `/proc/self/smaps_rollup` 是否存在且可读，然后把 `SUPPORTED` 或 `UNSUPPORTED` 存入全局 atomic。后续调用复用结果。

源码使用 relaxed load/store，没有 compare-and-swap 或 `call_once`。多个线程同时进行首次调用时，可能各自执行一次 `access()`；它保证的是状态读写无 data race 和结果可缓存，不应解释成“全进程严格只探测一次”。检查 self 也只代表内核提供该文件且调用进程可读 self，读取目标 PID 仍受 procfs 与权限限制。

### `StatusVmRSS()` 是并列接口

`ProcMemInfo::StatusVmRSS()` 直接打开 `/proc/<pid>/status`，找到唯一的 `VmRSS:` 行后返回。调用方必须主动选择它。Android 17 中选择 RSS 的主要系统调用方是 AppProfiler 的后台采样路径，而非 `SmapsOrRollup()` 内部降级。

## Framework 的三个入口不能混用

### `Debug.getMemoryInfo()`：为分类读取完整 `smaps`

`Debug.getMemoryInfo(MemoryInfo)` 最终进入 `android_os_Debug_getDirtyPagesPid()`。它调用 `ExtractAndroidHeapStats()`，而 Android 17 `androidprocheaps.cpp` 明确打开 `/proc/<pid>/smaps`，逐 VMA 分类到 Dalvik、native、stack、code、graphics 等 bucket。

这里不能换成只有一条汇总记录的 `smaps_rollup`，因为分类需要 VMA 名称、地址范围和各自的统计字段。JNI 还会通过 memtrack 补上未计入 procfs smaps 的 graphics、GL 和 other device memory；HAL 不可用时，这部分可能缺失。

### `Debug.getPss()`：总量快照，包含 SwapPss 与 memtrack

`Debug.getPss()` 使用 `ProcMemInfo::SmapsOrRollup()`。Android 17 的 JNI 先尝试取得 memtrack graphics/GL/other，再累加：

```text
return value =
    procfs Pss
  + procfs SwapPss
  + memtrack graphics/gl/other
```

这个入口适合取得当前进程的单一总量，不提供完整 VMA 分类。返回单位为 KiB。把它与 `smaps_rollup` 的 `Pss:` 对比时，要单独查看 SwapPss 和 memtrack，否则差值会被误判成采样误差。

### `Debug.getRss()`：API 35 起的低成本当前进程入口

官方 API 文档把 `Debug.getRss()` 标为 API 35 新增。Android 17 源码仍带 `FLAG_REMOVE_APP_PROFILER_PSS_COLLECTION`，JNI 调用 `StatusVmRSS()`，并尝试加入未被 procfs 统计的 memtrack graphics/GL/other。

因此，`Debug.getRss()` 返回值也可能高于直接读取 `/proc/self/status` 的 `VmRSS`。memtrack HAL 不可用时，函数不会为避免 log flooding 而持续告警，返回值只剩 `VmRSS` 部分。线上趋势图若跨设备比较，应记录机型、版本与采集口径，不要假定所有设备都补齐了相同的 graphics memory。

## Android 17 AppProfiler：默认后台 RSS，不代表 PSS 已被移除

Android 17 的 `AppProfiler.BgHandler` 在收到采样消息后调用：

- `isProfilingPss()` 为 true：`collectPssInBackground()`；
- 否则：`collectRssInBackground()`。

`isProfilingPss()` 读取 `ActivityManagerConstants.mForceEnablePssProfiling`。该字段默认 false，可由 `Settings.Global.FORCE_ENABLE_PSS_PROFILING` 强制打开。因此，AOSP Android 17 的常规后台 profiling 使用 RSS，降低周期性 smaps 采样成本；需要诊断时仍可强制使用 PSS。

PSS 并没有从 framework 消失。源码仍在以下场景读取它：

- 显式的 `Debug.getPss()`；
- `Debug.getMemoryInfo()` 和 `ActivityManager.getProcessMemoryInfo()`；
- 完整内存 dump 与 native process 汇总；
- heap-watch 阈值检查；
- 强制启用的 AppProfiler PSS 模式。

这种改动应描述成“后台周期采样默认从 PSS 切换到 RSS”。写成“Android 17 要求应用迁移到 RSS-only”会超出源码和 API 文档能支持的范围。

## `getProcessMemoryInfo()` 的五分钟缓存要准确理解

Android 17 `ActivityManagerService.getProcessMemoryInfo()` 的默认 throttle window 为五分钟，配置键是 `memory_info_throttle_time`。对于 system_server 已知的目标进程，若 `ProcessProfileRecord` 中的上次 `Debug.MemoryInfo` 仍在窗口内，调用方会收到缓存副本。

有三条边界常被漏写：

1. Android Q 起，普通应用只能看到与调用方 UID 相同的进程；其他 UID 的结果为空。
2. 该 API 面向调试或用户可见的进程管理界面，不适合作为秒级遥测接口。
3. throttle 例外只在“调用进程正由 shell/root 来源的 instrumentation 驱动”时成立。普通 `adb shell dumpsys meminfo` 走系统 dump 诊断路径，不能用它证明任意 shell 调用都会命中这里的 bypass 条件。

采样完成后，AMS 会把结果保存回 `ProcessProfileRecord`，并以 `ADD_PSS_EXTERNAL_SLOW` 记录稳定进程的样本。当前方法中没有直接写 `FrameworkStatsLog.PROCESS_MEMORY_STAT_REPORTED`；也不能据此宣称 Battery Historian 会自动消费每次应用查询。

## 如何选择采集入口

| 目标 | 建议入口 | 得到什么 | 主要限制 |
|---|---|---|---|
| 应用内低频 RSS 趋势 | `Debug.getRss()`，API 35+ | `VmRSS` 加可用的 memtrack 补充 | 无 PSS/USS/SwapPss 与 VMA 分类 |
| 应用内一次性 PSS 快照 | `Debug.getPss()` | PSS + SwapPss + 可用 memtrack | 读取 smaps/rollup 有成本 |
| 应用内详细分类 | `Debug.getMemoryInfo()` | Dalvik/native/code/stack/graphics 等 | 需要完整 `smaps`，成本更高 |
| 多进程调试 UI | `ActivityManager.getProcessMemoryInfo()` | 每 PID 的 `MemoryInfo` | UID 限制与默认五分钟缓存 |
| 开发机诊断 | `adb shell dumpsys meminfo -d <package-or-pid>` | 系统权限下的详细快照 | 输出是瞬时值，采样本身有成本 |

如果同一监控系统要同时覆盖 API 34 与 API 35+，不要把旧系统的 `getPss()` 与新系统的 `getRss()` 拼成一条未标注的曲线。至少存储 `metric_kind`、单位、Android 版本、设备型号与采样原因，分别设置基线。

下面的命令用于开发阶段核对“总量”和“分类”是否一致：

```bash
adb shell dumpsys meminfo -d com.example.app
adb shell cat /proc/$(adb shell pidof -s com.example.app)/smaps_rollup
```

第二条命令能否读取目标 procfs 文件取决于设备构建、SELinux 与调用权限。`dumpsys meminfo` 还可能加入 memtrack 等系统可见数据，所以两份结果无需逐字相等。应对齐采样时间，并分别比较 Pss、SwapPss、RSS 和 graphics。

## Cache 优化与 PSS 变化怎样联合验证

### 情况一：CPU 变快，PSS 基本不变

这通常符合局部性优化的预期。例如，保持相同数组容量，只把遍历顺序改成线性；工作集页数不变，L1D refill 与 CPU cycles 下降。验收应看端到端耗时、cycles、cache/TLB 事件和能耗，PSS 只作为回归保护。

### 情况二：CPU 与 PSS 同时下降

可能原因包括去装箱、紧凑数据结构、减少临时 allocation、缩短对象生命周期。需要用 heap dump 或 allocation profile 证明对象数/live set 下降，再用 RSS/PSS 证明 resident pages 变化。单看 PSS 无法指出是哪种数据结构起作用。

### 情况三：CPU 变快，PSS 上升

padding、预计算表、对象池、SoA 多份 buffer 或过度 `reserve()` 都可能用空间换时间。是否接受取决于业务延迟、设备内存档位和长时压力测试，不能只凭 cache miss 下降作决定。

### 情况四：PSS 抖动，cache 指标没有同步变化

先排查 GC、页面回收、文件映射、共享库、GPU allocation、进程状态和采样口径。PSS 是进程级快照；把整进程 PSS 的小幅变化归因到一个函数的 L1 行为，证据通常不够。

建议用同一套 workload 做 A/B：

1. 固定输入、进程生命周期、设备温度与前后台状态；
2. 记录业务延迟和 CPU time；
3. 用 Simpleperf 记录目标设备支持的 cache/TLB events；
4. 在相同阶段采集 RSS/PSS，注明所用 API；
5. 重复多轮，比较分布并检查热降频；
6. 若 PSS 变化，再用 heap/VMA 分类定位来源。

## ART 相关的三个纠偏

### TLAB 提供虚拟地址区间，不保证物理连续

线程局部分配可以在 TLAB 中通过指针 bump 快速获得一段堆地址。连续分配的对象往往具有较好的虚拟地址空间局部性，但 Linux 仍以页为单位建立物理映射；连续虚拟页不保证连续物理页。线程迁移、page fault 和 cache coherence 也不会由 TLAB 自动消失。

TLAB 大小和启用条件属于 ART collector、space、对象大小与运行时策略的一部分。Android 17 源码不能支持“所有线程默认固定 8 KiB，恰好适配 L1”这样的通用结论。

### CardTable 粒度是 1 KiB heap，不是 512 B

Android 17 ART `card_table.h` 定义 `kCardShift = 10`，一个 card-table byte 对应 1 KiB heap。CardTable 让 GC 用脏卡缩小引用扫描范围，其 byte array 也便于顺序处理。

这项设计不能推导出应用 PSS 或 L1 命中率。CardTable 自身占用进程内存，dirty-card 数描述 GC 记忆集状态；它没有记录 CPU cache line 当前在哪个核心。

### cpuset 不承诺“大核簇本地内存”

cpuset/cgroup 可以约束线程允许运行的 CPU 和部分内存策略，但 Android 平台没有承诺“前台 Java heap 优先分配到大核簇本地内存控制器”。多数手机 SoC 对 CPU 集群呈现共享内存系统，也不能把 big.LITTLE 直接等同于传统多插槽 NUMA。

若某个产品暴露 NUMA topology，需要核对该设备的 device tree、kernel config、memory policy 和 vendor allocator，再写产品级结论。AOSP Region/CC collector 本身不足以证明 cluster-local physical allocation。

## 常见误判

### “PSS 下降，所以 L1 命中率提高”

PSS 下降只能说明按当前口径归因的 resident/swap/device memory 变少。L1 命中率需要 PMU 或等价硬件证据。

### “RSS 更快，所以可以替代所有 PSS”

RSS 适合低成本趋势采样，无法合理分摊共享页。多进程 WebView、共享库、zygote 页等场景尤其需要 PSS 解释进程 RAM 权重。

### “rollup 只读几行，所以内核无需遍历页表”

少量文本降低的是输出与解析成本。kernel 仍需遍历 VMA/page table 才能得到这些字段。

### “`getProcessMemoryInfo()` 每次都是实时数据”

普通调用可能拿到五分钟窗口内的缓存值。诊断报告必须记录入口和时间，不能把缓存样本解释成刚刚发生的内存变化。

### “memtrack 失败固定低估 5%–15%”

低估幅度取决于 GPU/显示栈、HAL、workload 和厂商实现，源码没有给出固定比例。可确认的结论只有：memtrack 失败后，对应的 graphics/GL/other 补充不会进入返回值。

## 结论

Android 17 的内存核算可以归纳为三条并列路径：

- 需要 VMA 分类时读取完整 `smaps`；
- 需要 PSS/RSS/USS/SwapPss 总量时，`libmeminfo` 优先读取 `smaps_rollup`，不支持时读取 `smaps`；
- 需要低成本后台趋势时，显式读取 `status:VmRSS`，AppProfiler 默认采用这条 RSS 路径。

CPU cache 局部性属于另一组指标。布局优化可能间接改变 resident pages，也可能只改变 cache miss、CPU 时间和能耗。把“处理器数据搬运效率”和“进程物理页归因”分开测量，才能解释一次优化为什么有效，以及它付出了多少内存代价。
