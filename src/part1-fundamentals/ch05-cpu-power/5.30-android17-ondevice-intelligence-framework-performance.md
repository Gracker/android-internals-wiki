# 5.30 Android 17 OnDeviceIntelligence 框架性能：FoundationModelManager 推理调度与资源隔离

Android 15（API 35）引入了 `OnDeviceIntelligenceManager`（ODI），这是 Android 系统原生的端侧 AI 推理调度框架。与 AICore（Google Play services 组件，面向 Gemini Nano 等具体模型，详见 §5.20）不同，ODI 是一个**平台级推理调度基础设施**——它不绑定具体模型，而是定义了「Feature → 模型加载 → 推理执行 → 功耗归因」的完整管线，让 OEM 通过标准接口接入自家的推理后端。

截至 Android 17（API 37），ODI 仍以 `@SystemApi` + `@FlaggedApi(FLAG_ENABLE_ON_DEVICE_INTELLIGENCE)` 形式存在，并非面向第三方 App 的公共 SDK API。它的服务端实现由设备厂商通过 `config_defaultOnDeviceIntelligenceService` 配置项指定。这意味着该框架的性能特征主要体现在**系统进程间通信开销、沙箱化进程模型的资源隔离、以及推理调度的 QoS 策略**上。

[已验证: AOSP android-17.0.0_r1, frameworks/base/core/java/android/app/ondeviceintelligence/OnDeviceIntelligenceManager.java — `@SystemApi @SystemService(Context.ON_DEVICE_INTELLIGENCE_SERVICE)`]

## OnDeviceIntelligence 三层架构与 Mainline 独立性

### 包结构与 API 分层

ODI 的源码分布在 `frameworks/base` 的三个子包中，各自承担不同角色：

| 层 | 包路径 | 角色 | 进程 |
|----|--------|------|------|
| 客户端 API | `android.app.ondeviceintelligence` | 开发者调用的 Manager 和数据类 | App 进程 |
| 服务端 API | `android.service.ondeviceintelligence` | OEM 实现的抽象 Service 类 | 推理服务进程 |
| 系统调度 | `com.android.server.ondeviceintelligence` | system_server 内的中介服务 | system_server |

客户端 API 文件清单（`core/java/android/app/ondeviceintelligence/`）：

- `OnDeviceIntelligenceManager.java` — 主入口
- `Feature.java` / `FeatureDetails.java` — Feature 元数据（id、name、modelName、type、variant、featureParams）
- `InferenceInfo.java` — 功耗归因数据（uid、startTimeMs、endTimeMs、suspendedTimeMs）
- `OnDeviceIntelligenceException.java` — 14 种错误码
- `ProcessingCallback.java` / `StreamingProcessingCallback.java` — 推理回调
- `DownloadCallback.java` — 模型下载回调
- `ProcessingSignal.java` — 双向处理信号
- `TokenInfo.java` — token 级元信息

[已验证: AOSP android-17.0.0_r1, frameworks/base/core/java/android/app/ondeviceintelligence/ 目录结构]

### 非 Mainline 模块，而是 framework 原生服务

ODI 不是 Project Mainline 模块（APEX）。它的代码直接编译进 `framework.jar`，随系统 OTA 更新。与 AICore（通过 Mainline 独立更新）的关键区别：

- **AICore**：Google Play services 组件，`com.google.android.aicore` 独立进程，通过 ML Kit GenAI API 调用，模型管理由 PCS（Private Compute Services）完成
- **OnDeviceIntelligence**：framework 原生系统服务，`@SystemService`，由 OEM 配置实现，运行在系统级沙箱进程中

[已验证: AOSP android-17.0.0_r1, `@SystemService(Context.ON_DEVICE_INTELLIGENCE_SERVICE)` — 非Mainline APEX 模块，编译进 framework]

### 三进程 IPC 拓扑

ODI 的完整调用链涉及**三个进程间的 Binder IPC**：

```
App 进程                    system_server              沙箱推理进程 (isolatedProcess=true)
│                           │                         │
├─ OnDeviceIntelligenceManager                        │
│   └─ Binder ────────────→ OnDeviceIntelligenceManagerService
│                           │  权限检查 + 参数消毒      │
│                           │  ServiceConnector        │
│                           │  └─ Binder ────────────→ OnDeviceSandboxedInferenceService
│                           │                         │  模型推理执行
│                           │  ←───────────── Binder ─┤  结果回调
│  ←────────────── Binder ─┤                         │
├─ ProcessingCallback                                 │
```

每次推理请求至少经历 4 次 Binder 事务（App→system_server, system_server→sandbox, sandbox→system_server, system_server→App）。流式推理会在中间产生多次 `onPartialResult` 回调，每个 partial result 又增加 2 次 Binder 事务。

Binder 事务本身的开销在亚毫秒级，但 system_server 作为中介引入了额外的线程调度和 `ServiceConnector` 排队延迟。`OnDeviceIntelligenceManagerService` 使用 `Executors.newCachedThreadPool()` 处理回调和资源清理，在高并发推理场景下可能产生线程池争抢。

[已验证: AOSP android-17.0.0_r1, OnDeviceIntelligenceManagerService.java — `callbackExecutor = Executors.newCachedThreadPool()`, `resourceClosingExecutor = Executors.newCachedThreadPool()`]

### 权限模型

三个权限定义在 `frameworks/base/core/res/AndroidManifest.xml` 中：

| 权限 | protectionLevel | 用途 |
|------|----------------|------|
| `USE_ON_DEVICE_INTELLIGENCE` | `signature\|privileged` | App 调用 ODI API |
| `BIND_ON_DEVICE_INTELLIGENCE_SERVICE` | `signature\|privileged` | 系统绑定 OEM 的 IntelligenceService |
| `BIND_ON_DEVICE_SANDBOXED_INFERENCE_SERVICE` | `signature` | 系统绑定沙箱推理服务（仅系统签名） |

注意推理服务的 binding 权限是纯 `signature` 级别（不含 `privileged`），比管理服务的 `signature|privileged` 更严格。这意味着只有平台签名的应用才能实现推理服务。

[已验证: AOSP android-17.0.0_r1, AndroidManifest.xml — 三个权限的 protectionLevel 定义]

## Feature 模型与推理 API 生命周期

### Feature 是推理任务的抽象单元

ODI 不直接暴露「模型」概念，而是用 `Feature` 作为推理任务的抽象。每个 Feature 包含：

- `id`（int）：唯一标识符
- `name`（String）：人类可读名称
- `modelName`（String）：底层模型名称
- `type`（int）：类型标识
- `variant`（int）：变体标识
- `featureParams`（PersistableBundle）：自由参数

调用方通过 `listFeatures()` 发现设备支持的 Feature 列表，再按需 `requestFeatureDownload()` 下载所需模型。这种设计把模型管理与推理调用解耦——同一个 Feature 的模型可以被多个 App 共享。

[已验证: AOSP android-17.0.0_r1, Feature.java — `@SystemApi` Parcelable，字段如上所述]

### 推理调用的两条路径

ODI 提供同步推理和流式推理两种模式：

**同步推理** — `processRequest(Feature, Bundle, RequestType, CancellationSignal, ProcessingSignal, ProcessingCallback)`：

```
App → processRequest(feature, requestBundle, REQUEST_TYPE_INFERENCE, ...)
       → system_server: 权限检查 + sanitizeInferenceParams(request)
         → sandbox: processRequest(callerUid, feature, request, requestType, ...)
           → 执行推理
         ← onResult(responseBundle) 或 onError(exception)
       ← system_server: wrapWithValidation + tryCloseResource
     ← App: ProcessingCallback.onResult(result)
```

**流式推理** — `processRequestStreaming(Feature, Bundle, RequestType, ...)`：

与同步路径相同，但使用 `IStreamingResponseCallback`，推理过程中可以多次调用 `onPartialResult(Bundle)` 推送中间结果。最终调用 `onResult(Bundle)` 表示完成，可选附带聚合的完整响应。

流式推理的性能优势在于：调用方可以在首个 partial result 到达时就开始 UI 渲染，无需等待完整推理结束。对于 token-by-token 的生成式推理（如文本摘要），这意味着首 token 延迟（TTFT）变为用户感知延迟的关键指标，而非总推理时间。

[已验证: AOSP android-17.0.0_r1, OnDeviceIntelligenceManager.java — `processRequest()` 和 `processRequestStreaming()` 方法签名与实现]

### RequestType 三种类型

- `REQUEST_TYPE_INFERENCE` (0)：标准推理请求
- `REQUEST_TYPE_PREPARE` (1)：预热环境（加载推理运行时、预编译计算图等），不产生最终结果
- `REQUEST_TYPE_EMBEDDINGS` (2)：请求向量嵌入

`REQUEST_TYPE_PREPARE` 是重要的性能优化手段：App 可以在用户还未触发推理时先调用 prepare，将模型加载和运行时初始化提前完成，使后续实际推理的首 token 延迟大幅降低。这与 §5.20 中 AICore 的冷启动问题对应——ODI 提供了框架级的预热解决方案。

[已验证: AOSP android-17.0.0_r1, OnDeviceIntelligenceManager.java — `REQUEST_TYPE_PREPARE = 1`]

### 数据传输的 Bundle 约束

ODI 对推理请求的 Bundle 数据施加了严格约束，定义了三种注解类型：

- `@StateParams`：最严格，仅允许 PersistableBundle + 原始类型 + 只读 ParcelFileDescriptor
- `@InferenceParams`：在 StateParams 基础上，额外允许 immutable Bitmap、CursorWindow、PROT_READ 的 SharedMemory
- `@ResponseParams`：允许写入 Bitmap

`SharedMemory`（`PROT_READ`）是传递大输入数据（如高分辨率图片）的推荐方式，避免了 Binder 事务的 1MB 大小限制。系统服务在转发前会调用 `BundleUtil.sanitizeInferenceParams()` 验证所有 ParcelFileDescriptor 确实是只读模式。

推理完成后，系统服务通过 `BundleUtil.tryCloseResource(request)` 在 `resourceClosingExecutor` 上异步关闭资源，防止文件描述符泄漏。

[已验证: AOSP android-17.0.0_r1, OnDeviceIntelligenceManager.java — `@InferenceParams` 注解定义 + OnDeviceIntelligenceManagerService.java — `sanitizeInferenceParams(request)` 调用]

### Data Augment 回调模式

`ProcessingCallback` 除了 `onResult` 和 `onError`，还有一个特殊回调 `onDataAugmentRequest(Bundle processedContent, Consumer<Bundle> contentConsumer)`。

这个机制允许推理服务在处理过程中**向调用方请求额外数据**。典型场景：推理服务收到用户查询后，根据部分处理结果判断需要更多上下文（如用户最近的聊天记录、位置信息），通过 `onDataAugmentRequest` 向 App 请求增强数据。App 提供 augmentation data 后，推理服务将其融入后续推理。

这个模式把 RAG（Retrieval-Augmented Generation）的 retrieval 步骤放到了系统推理框架内部。对性能的影响是：整个推理过程的墙钟时间取决于 App 响应 `onDataAugmentRequest` 的速度。如果 App 在回调中执行数据库查询或网络请求，会直接拉长推理延迟。

[已验证: AOSP android-17.0.0_r1, ProcessingCallback.java — `onDataAugmentRequest()` default 方法，默认接受 `Bundle.EMPTY`]

## 推理调度与系统资源协同

### 沙箱化进程模型

推理在 `OnDeviceSandboxedInferenceService` 中执行，该服务声明为 `android:isolatedProcess="true"`：

```xml
<service android:name=".SampleSandboxedInferenceService"
         android:permission="android.permission.BIND_ONDEVICE_SANDBOXED_INFERENCE_SERVICE"
         android:isolatedProcess="true">
</service>
```

`isolatedProcess="true"` 意味着该服务运行在**没有任何权限的沙箱进程**中——不能访问网络、不能读写文件系统、不能调用大部分系统 API。模型文件和输入数据的传递完全依赖 IPC：

- 模型文件：通过 `IRemoteStorageService`（由非沙箱的 `OnDeviceIntelligenceService` 注册）以只读 ParcelFileDescriptor 方式传入
- 输入数据：通过 `@InferenceParams Bundle` 以 `SharedMemory`（PROT_READ）或只读 ParcelFileDescriptor 方式传入
- 输出数据：通过 `@ResponseParams Bundle` 原路返回

这种设计的安全性极高，但代价是**所有数据传输都需要跨进程**。对于大模型推理（模型权重动辄 GB 级别），权重文件通过 `mmap` 方式共享（`ParcelFileDescriptor` + `SharedMemory`），避免了数据拷贝。但每次推理请求的输入/输出数据仍需序列化和跨进程传输。

[已验证: AOSP android-17.0.0_r1, OnDeviceSandboxedInferenceService.java — manifest 声明示例 + `isolatedProcess="true"` + `IRemoteStorageService` 注册接口]

### 连接管理与超时策略

`RemoteOnDeviceSandboxedInferenceService` 使用 `ServiceConnector.Impl` 管理与沙箱进程的连接：

- **绑定标志**：`BIND_FOREGROUND_SERVICE | BIND_INCLUDE_CAPABILITIES` — 推理服务被当作前台服务绑定，获取更高的调度优先级
- **请求超时**：`LONG_TIMEOUT = 1 小时`（单个推理请求的最大执行时间）
- **自动断开**：默认 30 秒无活动后解绑，可通过 `Settings.Secure.ON_DEVICE_INFERENCE_UNBIND_TIMEOUT_MS` 配置

非沙箱的 `RemoteOnDeviceIntelligenceService` 使用更长的超时：

- **请求超时**：`LONG_TIMEOUT = 4 小时`（管理操作如模型下载可能耗时更长）
- **自动断开**：同样 30 秒，可通过 `Settings.Secure.ON_DEVICE_INTELLIGENCE_UNBIND_TIMEOUT_MS` 配置

系统服务的 `getIdleTimeoutMs()` 默认 1 小时，通过 `Settings.Secure.ON_DEVICE_INTELLIGENCE_IDLE_TIMEOUT_MS` 配置。每个 API 调用都用 `future.orTimeout(getIdleTimeoutMs(), TimeUnit.MILLISECONDS)` 包装，超时后抛出 `TimeoutException`。

[已验证: AOSP android-17.0.0_r1, RemoteOnDeviceSandboxedInferenceService.java + RemoteOnDeviceIntelligenceService.java — 超时常量和 Settings.Secure 配置项]

### 推理并发与 QoS 排队

ODI 的错误码体系揭示了其 QoS 设计：

- `PROCESSING_ERROR_BUSY` (9)：服务忙，调用方应使用指数退避重试
- `PROCESSING_ERROR_SUSPENDED` (13)：推理被挂起，以便更高优先级的推理可以运行

`SUSPENDED` 错误码的注释明确写道：**"Inference suspended so that higher-priority inference can run"**。这说明 ODI 内部维护了优先级队列，当 NPU 资源紧张时，低优先级推理会被挂起。`InferenceInfo` 数据结构中也有 `suspendedTimeMs` 字段，用于记录推理被挂起的总时长。

这种 QoS 机制与 §5.19 中讨论的 ADPF（Android Dynamic Performance Framework）形成互补：
- ADPF 通过 `PerformanceHintManager.Session` 向调度器提供 workload hint，影响 CPU/GPU 频率选择
- ODI 通过自身的优先级队列管理推理任务的调度顺序

两者的协同点在于：推理服务进程可以同时使用 ADPF hint（影响硬件频率）和 ODI 内部 QoS（管理推理排队）。但截至 Android 17，ODI 的公开 API 中没有暴露优先级设置接口——优先级判断逻辑完全由 OEM 实现的 `OnDeviceSandboxedInferenceService` 决定。

[已验证: AOSP android-17.0.0_r1, OnDeviceIntelligenceException.java — `PROCESSING_ERROR_SUSPENDED = 13` + `PROCESSING_ERROR_BUSY = 9` + InferenceInfo.java — `suspendedTimeMs` 字段]

### 单实例约束

OnDeviceIntelligenceManagerService 的注释明确指出：

> "Both the remote services run under the SYSTEM user, as we cannot have separate instance of the Inference service for each user, due to possible high memory footprint."

推理服务在整个设备上只有**一个实例**（SYSTEM 用户下），所有用户、所有 App 的推理请求共享同一个推理进程。这意味着：

- 多用户设备上，用户 A 的推理请求可能与用户 B 的请求竞争同一个 NPU 资源
- 一个 App 的大量推理请求可能阻塞其他 App 的推理（由 `BUSY` / `SUSPENDED` 错误码反映）
- 推理服务的内存占用需要 OEM 实现仔细管理，因为单个实例服务全局

[已验证: AOSP android-17.0.0_r1, OnDeviceIntelligenceManagerService.java — 类注释中关于 SYSTEM user 和单实例的说明]

## 功耗核算与 PowerStats 归因

### InferenceInfo 功耗归因机制

ODI 提供了框架级的推理功耗归因能力——这是它与 AICore（功耗归因不透明，详见 §5.20）的关键区别。

`OnDeviceIntelligenceManager.getLatestInferenceInfo(long startTimeEpochMillis)` 返回 `InferenceInfo` 列表，每条记录包含：

- `uid`：发起推理的调用方 UID
- `startTimeMs` / `endTimeMs`：推理起止时间
- `suspendedTimeMs`：推理被挂起的总时间

这个方法的权限是 `Manifest.permission.DUMP`（system-only），面向系统诊断工具而非普通 App。`InferenceInfoStore` 在系统服务内部维护一个 3 小时窗口（`MAX_AGE_MS = TimeUnit.HOURS.toMillis(3)`）的推理记录。

功耗归因路径：

```
推理执行 → InferenceInfoStore 记录 {uid, startTime, endTime, suspendedTime}
    → BatteryStats 可以将推理期间的 NPU/GPU rail 功耗归因到对应 uid
    → getLatestInferenceInfo() 查询历史归因数据
```

与 BatteryStats 的协作：ODI 系统服务通过 `OnDeviceIntelligenceManagerInternal`（`LocalServices` 内部接口）暴露推理服务的 UID，BatteryStats 模块可以据此将推理进程的功耗按发起方 UID 分摊。这是 §5.20 中「AICore 推理内存不归 App 管」问题在 ODI 框架下的对应解法——ODI 至少提供了框架级的功耗归属数据。

[已验证: AOSP android-17.0.0_r1, OnDeviceIntelligenceManager.java — `getLatestInferenceInfo()` + InferenceInfoStore — `MAX_AGE_MS = 3h`]

### NPU rail 统计的挑战

`InferenceInfo` 只记录时间维度（起止时间 + 挂起时间），不直接包含功耗数值。实际的 NPU 功耗需要通过 Power Stats HAL 读取 NPU rail 的累积功耗计数器，再与 `InferenceInfo` 的时间窗口对齐计算。

NPU rail 统计的复杂性在于：
- 不同 SoC 厂商的 NPU rail 划分方式不同（有的与 GPU 共享 rail，有的独立）
- NPU 低功耗状态（power collapse）期间的功耗统计精度降低
- 多个推理并发时，单个 NPU rail 的总功耗需要按推理时间比例分摊

详见 §25.18 关于 Power Stats HAL 架构与 OEM 实现差异的分析。

[待验证: NPU rail 功耗归因的具体实现取决于 OEM，公开 AOSP 代码未包含厂商私有逻辑]

## OnDeviceIntelligence vs AICore vs NeuralNetworks API 的分工边界

Android 17 上端侧 AI 推理存在三个并行框架，各自定位不同：

| 维度 | OnDeviceIntelligenceManager | AICore | NeuralNetworks API (NNAPI) |
|------|---------------------------|--------|---------------------------|
| 引入版本 | Android 15 (API 35) | Android 14 (API 34) | Android 8.1 (API 27) |
| API 级别 | `@SystemApi` | 公共 SDK（ML Kit GenAI） | 公共 SDK |
| 模型管理 | OEM 配置的 OnDeviceIntelligenceService | Google Play services 内部管理 | 开发者自行管理 |
| 推理执行 | 沙箱化隔离进程 | AICore 独立进程 | App 进程内或 HAL delegate |
| 功耗归因 | `InferenceInfo` 框架级支持 | 不透明 | 无框架级归因 |
| 适用场景 | OEM 定义的 Feature 推理（如系统级智能摘要、通知分类） | Gemini Nano 等 Google 模型推理 | 自定义模型直接部署 |
| 状态 | Android 17 仍为 flag-gated，未成为公共 API | 通过 ML Kit 稳定可用 | API 15 起 deprecated |
| 更新机制 | 系统 OTA | Mainline / Play services | 系统 OTA |

三者的选择逻辑：
- 需要 Gemini Nano → AICore（§5.20）
- 需要自定义 TFLite 模型 → LiteRT + NNAPI/NPU delegate（§5.11, §5.14）
- OEM 想提供系统级 AI Feature（如智能回复、内容摘要）→ OnDeviceIntelligence

ODI 的定位更接近「OEM 的 AI Feature 基础设施」，而非「App 开发者的推理 SDK」。它的 API 约束（`@SystemApi`、`signature|privileged` 权限）决定了只有系统应用和特权应用才能使用。

[已验证: AOSP android-17.0.0_r1 + §5.20 AICore 分析 + §5.14 NNAPI deprecated 状态]

## 推理预热与首帧延迟优化策略

ODI 的 `REQUEST_TYPE_PREPARE` 提供了框架级的预热方案。典型的预热流程：

1. App 启动时或用户即将触发 AI 功能前（如打开输入法、进入聊天页），调用 `processRequest(feature, emptyBundle, REQUEST_TYPE_PREPARE, ...)` 预热推理运行时
2. 预热请求触发沙箱进程加载模型、初始化推理引擎、预编译计算图
3. 用户实际触发推理时，调用 `processRequest(feature, inputBundle, REQUEST_TYPE_INFERENCE, ...)`，模型已在内存中就绪

预热效果的关键影响因素：

- **模型加载时间**：取决于模型大小和存储 I/O 速度。GB 级模型从 flash 加载到内存需要数百毫秒到数秒
- **计算图编译时间**：NPU delegate 首次执行时需要将模型编译为硬件指令，这个过程可能耗时数秒
- **沙箱进程启动时间**：如果 `autoDisconnectTimeoutMs`（默认 30 秒）已到期，沙箱进程已被解绑，下次调用需要重新绑定和启动进程

性能建议：
- 在非 UI 关键路径调用 prepare（如页面加载的 `onCreate` 中异步调用）
- 监听 `PROCESSING_ERROR_BUSY` 并退避重试，避免 prepare 请求挤占正在进行的推理
- 如果设备支持，配置较长的 `ON_DEVICE_INFERENCE_UNBIND_TIMEOUT_MS`（默认 30 秒可能太短），保持沙箱进程常驻

[已验证: AOSP android-17.0.0_r1, OnDeviceIntelligenceManager.java — `REQUEST_TYPE_PREPARE = 1` + RemoteOnDeviceSandboxedInferenceService.java — `getAutoDisconnectTimeoutMs()` 默认 30 秒]

## OEM 自定义推理后端的扩展点

### OnDeviceIntelligenceService 的实现框架

OEM 通过实现两个抽象 Service 来接入 ODI：

**`OnDeviceIntelligenceService`**（非沙箱，模型管理）：
- 权限：`BIND_ON_DEVICE_INTELLIGENCE_SERVICE`
- 职责：Feature 注册、模型下载/管理、文件访问代理（`IRemoteStorageService`）
- 默认实现配置：`config_defaultOnDeviceIntelligenceService`（`frameworks/base/core/res/res/values/config.xml`）

**`OnDeviceSandboxedInferenceService`**（沙箱，推理执行）：
- 权限：`BIND_ONDEVICE_SANDBOXED_INFERENCE_SERVICE`（纯 signature）
- 声明：`android:isolatedProcess="true"`
- 职责：执行实际推理（processRequest / processRequestStreaming / requestTokenInfo）
- 数据来源：通过 `IRemoteStorageService` 从非沙箱 Service 获取只读文件描述符

OEM 需要在沙箱环境中实现自己的推理管线——ODI 框架本身不包含任何推理引擎。OEM 可以选择在沙箱进程中集成 TFLite/LiteRT 运行时、厂商自研 NPU SDK（如 QNN、NeuroPilot）、或任何其他推理框架。

[已验证: AOSP android-17.0.0_r1, OnDeviceIntelligenceService.java + OnDeviceSandboxedInferenceService.java — 抽象方法定义]

### 性能基线对比方法论

评估不同 OEM 的 ODI 实现性能时，建议关注以下指标：

| 指标 | 测量方法 | 预期范围 |
|------|---------|---------|
| Feature 列举延迟 | `listFeatures()` 从调用到回调的墙钟时间 | < 100ms |
| 模型下载时间 | `requestFeatureDownload()` 从开始到完成的墙钟时间 | 取决于模型大小和 I/O |
| 预热延迟 | `REQUEST_TYPE_PREPARE` 的执行时间 | 500ms - 5s |
| 首 token 延迟（TTFT） | 流式推理从 `processRequestStreaming()` 到首个 `onPartialResult` 的时间 | 200ms - 2s |
| 稳态 token rate | 流式推理中连续 `onPartialResult` 之间的间隔倒数 | 10 - 100 tokens/s |
| 推理并发容量 | 同时发起多个推理请求，观察 `BUSY` / `SUSPENDED` 频率 | 1 - 4 并发 |
| 沙箱进程内存占用 | `adb shell dumpsys meminfo <sandboxed_process>` | 500MB - 4GB |
| 推理期间 NPU frequency | Perfetto trace 中 NPU frequency counter | 取决于 SoC |

[待验证: 以上预期范围来自端侧 AI 推理的通用经验值，具体性能取决于 OEM 实现和设备硬件]

## Perfetto 观测要点

| 观测目标 | Track / 方法 | 说明 |
|---------|-------------|------|
| 推理服务进程活跃度 | Process track + CPU scheduling | 沙箱进程名取决于 OEM 实现，需先通过 `dumpsys activity service` 确认包名 |
| Binder IPC 延迟 | Binder track | 观察 App→system_server 和 system_server→sandbox 的事务耗时 |
| NPU/GPU 频率 | System counters | 推理期间频率抬升，thermal throttling 时下降 |
| 内存压力 | `oom_score_adj` + RSS | 沙箱进程 RSS 增长可能触发系统级 LMK |
| 推理墙钟延迟 | App 侧 `Trace.beginSection("odi_process_request")` | 测量从请求到回调的完整时间 |

ODI 框架本身不输出 Perfetto trace slice。要在 trace 中看到推理阶段细节，需要 OEM 实现在 `OnDeviceSandboxedInferenceService` 中添加 `Trace.beginSection()` 调用。

[已验证: AOSP android-17.0.0_r1 — ODI 框架代码中无 Perfetto trace 埋点]

## 扩展

### 🔸 DeviceConfig 热更新

ODI 通过 `DeviceConfig` namespace `ondeviceintelligence` 管理运行时配置。`OnDeviceIntelligenceManagerService` 注册了 `OnPropertiesChangedListener`，当 `service_enabled` 配置变化时热更新服务状态。此外还支持临时服务名（`mTemporaryServiceNames`）和临时广播 key，用于测试环境覆盖默认实现，3 小时后自动重置（`MAX_AGE_MS`）。

[已验证: AOSP android-17.0.0_r1, OnDeviceIntelligenceManagerService.java — `NAMESPACE_ON_DEVICE_INTELLIGENCE` + `DeviceConfig.OnPropertiesChangedListener`]

### 🔸 ProcessingSignal 双向信号通道

`ProcessingSignal` 是 ODI 独特的设计——除了标准的 `CancellationSignal`（取消请求），还提供了双向处理信号通道。调用方可以通过 `ProcessingSignal` 在推理进行中发送自定义信号（如「用户已离开页面，降低推理优先级」），推理服务据此调整执行策略。这个通道通过 `IProcessingSignal` AIDL 接口实现，使用 `AndroidFuture` 桥接到远端。

[已验证: AOSP android-17.0.0_r1, OnDeviceIntelligenceManager.java — `configureRemoteProcessingSignalFuture()` 方法]

[适用版本: Android 15 (API 35) - Android 17 (API 37) — android-17.0.0_r1]
