# 5.19 端侧 AI 调度与 ADPF 智能优化

端侧 AI 的一次响应可能经过输入解码、张量转换、模型编译、CPU/GPU/NPU 执行、同步等待、后处理和 UI 更新。ADPF 只覆盖其中一部分：应用把一组长期存活线程的周期性工作时长告诉系统，系统再尝试调整这些线程的 CPU core placement 和频率。它没有场景分类器，也不会替应用选择模型、delegate、NPU 队列或推理优先级。

“智能”在这里来自反馈：应用持续上报 target 与 actual，系统结合设备拓扑、电源和热状态做决策。应用仍要负责模型选择、质量降级、并发控制和端到端验收。

本章以 Android 17 / API 37 / `android-17.0.0_r1` 为平台基线，以 Android common kernel `android17-6.18-2026-06_r6` 为内核基线，重点说明 ADPF 怎样服务端侧 AI 的 CPU 关键线程，以及它与 LiteRT、NNAPI 和 Android 17 NPU scheduling HAL 的边界。ADPF 基础与 Thermal/Headroom API 见 5.9，异构执行和功耗归因见 5.16，Android 17 NPU 平台接口见 5.14。

## 先分清三套控制面

端侧推理没有一套能同时管理 CPU、GPU 和 NPU 的应用 API。Android 17 上至少要区分三层：

```text
应用业务
  ├─ 模型 / runtime / delegate 选择
  │    └─ CPU、GPU、NPU、部分委派与 fallback
  │
  ├─ PerformanceHintManager / ADPF
  │    └─ 描述应用进程内一组长期线程的周期工作
  │         → performance_hint service
  │         → Power HAL 与设备策略
  │         → CPU 放置 / CPUFreq 等可能响应
  │
  └─ Android 17 NPU scheduling control plane
       └─ system 按 UID 配置优先级、直接访问与归因权限
            → vendor NPU scheduling HAL
```

这张图用于说明职责。Power HAL 怎样把 hint 映射到 Linux scheduler、CPUFreq 或厂商控制器，属于设备实现；Android common kernel 的 EAS、schedutil 也不会接受应用传入的“NPU 优先级”。

### 应用运行时选择执行后端

LiteRT `CompiledModel`、delegate 或厂商 runtime 负责加载模型、编译、选择硬件、创建 buffer 和执行。部分算子不受目标加速器支持时，runtime 还可能拆分子图或 fallback。ADPF 不参与算子覆盖判断。

NNAPI 在 Android 15（API 35）已标记 deprecated。Android 17 平台仍保留相关 API/HAL 以支持兼容性，不适合据此继续设计新的通用推理架构。新项目应按所选 runtime 的官方迁移路径与版本说明决定 CPU/GPU/NPU 接入，不能把旧 Neural Networks HAL 方法拼成应用代码。

### ADPF 描述线程工作，不授予硬件控制权

`PerformanceHintManager.Session` 从 API 31 起公开。创建时传入应用线程的 Linux TID 和 target work duration；每个周期完成后上报 actual work duration。Android 17 `PerformanceHintManager.java` 的公开契约写明：系统会尝试调整 session 线程的 core placement 和/或所在 core 的频率，使 actual 接近 target。

公开 API 没有以下能力：

- 指定 big/little core 或调用 `sched_setaffinity`；
- 设置最小/最大 CPU、GPU、NPU 频率；
- 申请独占 NPU；
- 设置 `HINT_PRIORITY_HIGH`、`FLAG_PRIORITY_LOW_LATENCY` 等推理优先级；
- 注册 deadline 或 priority callback；
- 让系统自动识别人脸解锁、语音、LLM 或后台批处理场景。

创建 HintSession 不要求 `WAKE_LOCK` 权限。会话也不提供后台执行豁免；前台服务、JobScheduler、后台启动限制和电量策略仍按各自规则生效。

### NPU scheduling HAL 是系统与 vendor 的接口

Android 17 新增的 `android.hardware.npu.IScheduling` 接收 `SchedulingConfig[]`。每个配置包含：

- `uid`；
- `priority`，范围 0–1000，数值越小优先级越高；
- `hasDirectAccess`；
- `canAttributeOtherUid`。

接口注释要求 NPU 尽力遵循 UID priority，具体行为由硬件能力决定。这是 system/vendor 的 VINTF AIDL，不是普通应用可调用的 SDK。应用也不能从 ADPF target duration 推导出自己的 NPU UID priority。

API 37 的 `PackageManager.FEATURE_NEURAL_PROCESSING_UNIT` 值为 `android.hardware.npu`，表示设备具备 NPU 或类似 AI accelerator。面向 Android 17 且需要直接访问 NPU 的应用要把它作为 manifest feature 声明；运行时仍只能把它用于能力判断。它不承诺算子覆盖、内存容量、执行延迟、并发数量或 LiteRT delegate 可用。

## 哪些 AI 工作适合 HintSession

HintSession 面向长期线程上的周期性 workload。对端侧 AI，较合适的候选包括：

- 相机每帧或每 N 帧执行一次预处理、提交与后处理；
- 音频流按固定 chunk 做特征提取和识别；
- 实时字幕按稳定窗口做 CPU 前后处理；
- LLM decode 的重复 CPU orchestration、sampling 和 detokenization；
- 与渲染周期相邻的 AI 特效 CPU stage。

以下工作通常不适合作为一个长期反馈 session：

- 应用启动时只发生一次的模型下载、解压或校验；
- 首次模型编译和 cache 建立；
- 完全阻塞等待远端服务或磁盘的任务；
- 主要时间都在 NPU 执行、应用线程长时间 sleeping 的一次性推理；
- 大量短命线程或每次请求都会重建的线程池。

判断标准是：线程是否长期存活，工作是否重复，target 是否有业务含义，系统调整 CPU 资源后是否有机会缩短该阶段。

## 先拆推理周期，再选 session 边界

以一帧视觉推理为例：

| 阶段 | 常见执行方 | 是否适合放入 ADPF session | 原因 |
|---|---|---|---|
| 图像裁剪、颜色转换、归一化 | CPU/GPU | CPU 线程通常适合 | 周期稳定，可受 CPU 资源影响 |
| delegate 编译 | runtime/vendor compiler | 通常不适合周期 session | 一次性或低频，耗时分布与稳态不同 |
| 命令准备与提交 | CPU/driver | 可能适合 | CPU 延迟可能影响整体 deadline |
| NPU kernel 执行 | NPU | 无法直接表达 | `WorkDuration` 没有 NPU duration 字段 |
| fence / callback 等待 | sleeping CPU thread | 谨慎 | 增加 CPU 频率未必能缩短等待 |
| 解码、NMS、sampling、detokenization | CPU | 通常适合 | 重复且可能位于用户可见关键路径 |
| UI 合成 | RenderThread/GPU | 应按渲染 session 设计 | 不应随意并入模型 worker session |

把整个 `model.run()` 的 wall time 原样报给只包含一个 CPU 提交线程的 session，可能让系统把 NPU 排队或 fence 等待误判成 CPU 算力不足。更稳的做法是：

1. 用 trace 拆出 CPU active、accelerator execution 和 wait；
2. HintSession 覆盖可受 CPU 调度影响的长期线程；
3. NPU latency、queueing 和 delegate 信息单独记录；
4. 通过同机 A/B 判断 session 是否改善端到端指标。

如果一条流水线同时有可准确测量的 CPU 与 GPU 工作，可使用 `WorkDuration`；NPU 时间不能填进 GPU 字段。

## Java 公共 API 的正确接法

### 固定 worker 比跟随协程迁移更稳

HintSession 绑定 Linux TID。`Process.myTid()` 要在目标 worker 上调用；Java `Thread.getId()`、Kotlin coroutine ID 和任务 ID 都不能代替 TID。

下面的骨架用于展示一个长期 AI CPU worker 的 session 生命周期。`runCpuCriticalStage()` 应只包含经 profile 确认、能受 CPU 调度影响的周期工作。

```java
PerformanceHintManager hintManager =
        context.getSystemService(PerformanceHintManager.class);

aiExecutor.execute(() -> {
    int workerTid = Process.myTid();
    long targetNanos = 4_000_000L;
    PerformanceHintManager.Session session =
            hintManager.createHintSession(new int[] {workerTid}, targetNanos);

    try {
        while (hasNextRequest()) {
            long start = SystemClock.uptimeNanos();
            runCpuCriticalStage(nextRequest());
            long actual = SystemClock.uptimeNanos() - start;

            if (session != null) {
                session.reportActualWorkDuration(actual);
            }
        }
    } finally {
        if (session != null) {
            session.close();
        }
    }
});
```

`createHintSession()` 可能返回 `null`，表示设备不支持或 TID 校验失败，业务必须继续运行。`Session` 的调用会修改内部状态，跨线程访问时要由应用自行同步。会话应显式关闭，不能依赖 finalizer。

Kotlin coroutine 在 `Dispatchers.Default` 或 `Dispatchers.IO` 上可能迁移。常见选择是给关键周期使用受控的固定 executor/dispatcher。API 34 起可用 `setThreads(int[])` 替换 TID 列表，但它是同步操作，可能因线程不属于应用、列表为空或 session 不在前台而失败；不应在每次 continuation 恢复时调用。

### target 是 session 工作预算

target duration 属于 session 中线程完成一个周期工作的预算，不等于整个推理 SLA。假设用户要求一帧在 33 ms 内完成，而 CPU 预处理只分到 5 ms，HintSession target 应围绕这 5 ms 设计。

target 的确定可以按以下顺序：

1. 从用户可见 deadline 拆出各阶段预算；
2. 在代表性设备上确认 CPU stage 的 p50/p90/p99；
3. 选择可达到、又能暴露退化的 target；
4. 场景、模型、帧率或质量档变化时调用 `updateTargetWorkDuration()`；
5. 不要为了“请求更多性能”故意填一个无法达到的极小值。

ADPF 是反馈控制，actual 通常在周期结束后影响后续周期。它无法挽回已经超时的当前请求。

### `WorkDuration` 只能拆 CPU 和 GPU

API 35 的 `WorkDuration` 使用 `SystemClock.uptimeNanos()` 时间基准。开始时间与 total duration 必须大于 0；CPU/GPU duration 不能小于 0，而且两者至少有一项大于 0。

下面的代码只负责构造已测得的数据。`cpuWallNanos` 和 `gpuWallNanos` 必须来自可靠测量，不能按 total duration 猜比例。

```java
WorkDuration duration = new WorkDuration();
duration.setWorkPeriodStartTimestampNanos(periodStartNanos);
duration.setActualTotalDurationNanos(totalWallNanos);
duration.setActualCpuDurationNanos(cpuWallNanos);
duration.setActualGpuDurationNanos(gpuWallNanos);
session.reportActualWorkDuration(duration);
```

CPU 与 GPU 可以重叠，所以 total 不要求等于两项简单相加。端侧 AI 若没有准确的 GPU 时间，CPU-only session 继续使用 `reportActualWorkDuration(long)` 更清楚；NPU 时间没有公开字段。

### 能效模式不是低优先级模式

API 35 的 `setPreferPowerEfficiency(true)` 表示这些线程允许系统偏向节能调度，即使工作可能完成得慢一些。它适合 deadline 宽松的 CPU 后处理、离线索引或批量 embedding，但仍需以完成时间和能耗验证。

该方法不会：

- 修改 Linux nice；
- 把任务变成 JobScheduler 工作；
- 选择 little core；
- 把 NPU 频率设为低档；
- 赋予后台运行权限。

交互式首帧、首 token 或相机实时预览是否启用能效模式，要由产品预算和持续性能实验决定。

## Android 16 NDK workload hint 的准确边界

Android 16 / API 36 的 NDK `performance_hint.h` 公开：

- `APerformanceHint_notifyWorkloadIncrease()`；
- `APerformanceHint_notifyWorkloadReset()`；
- `APerformanceHint_notifyWorkloadSpike()`。

它们可以标记 CPU、GPU 或两者即将发生的显著变化，并带一个用于区分 hint 的 UTF-8 identifier。hint 应在变化前或周期早期发送；持续高负载仍靠 actual duration 反馈。framework 有 per-app rate limiter，被限流时返回 `EBUSY`，不支持的 hint 可以被静默忽略。

这组函数没有 NPU 参数。Java `Session.sendHint()` 以及 `CPU_LOAD_*`、`GPU_LOAD_*` 在 Android 17 源码中仍是 `@TestApi` / hidden，普通应用不能作为稳定 SDK 使用。

对 LLM 可以这样映射：

- prefill 切到 decode：更新 target；NDK 客户端可发送 workload reset；
- context 或 batch 显著增大：NDK 客户端可发送 workload increase；
- 偶发的长 context 或一次性 expensive token：证据充分时使用 workload spike；
- 每个 token 都重复发送 increase：会被限流，也破坏 hint 的语义。

## LLM 场景：不要用一套固定 target 覆盖全部阶段

LLM 的 prefill 与 decode 在计算形态上差异很大：

- prefill 通常一次处理较长 prompt，吞吐和首 token latency 更重要；
- decode 逐 token 迭代，inter-token latency、tokens/s 与稳定性更重要；
- sequence 增长会改变 KV-cache 访问和每 token 成本；
- sampling、tokenizer、detokenizer 和 UI streaming 常在 CPU；
- 模型主体可能在 CPU、GPU、NPU 或多后端之间拆分。

因此，可以为同一长期线程保留 session，但在阶段切换时更新 target；也可以把具有不同线程集合的 prefill/decode CPU stage 分开管理。选择依据是线程拓扑和业务预算，不是“聊天优先级”枚举。

一次端侧 LLM 实验至少记录：

- model、量化、context length、输出长度和 sampling 参数；
- runtime/delegate 版本与后端；
- cold load、compile/cache、prefill、首 token、decode；
- p50/p90/p99 inter-token latency 与 tokens/s；
- CPU/GPU/NPU fallback 和 buffer copy；
- 峰值 RSS/PSS、温度、功耗与持续运行时间。

固定写“预分配 512 MB NPU 内存”或“每 token 20–50 ms”没有跨设备意义。内存、精度和时延要绑定模型与设备测量。

## Runtime、ADPF 与应用策略怎样配合

### 后端选择由测量结果驱动

对每个目标设备或能力组，至少保留 CPU 基线，并比较 GPU/NPU：

| 维度 | 需要分开记录的内容 |
|---|---|
| 初始化 | runtime load、delegate load、model compile、cache hit/miss |
| 执行 | accelerator time、CPU fallback、同步等待、端到端 latency |
| 数据 | 输入转换、layout、量化/反量化、buffer copy |
| 稳态 | p50/p90/p99、吞吐、温控后的性能 |
| 资源 | CPU/GPU/NPU 占用、memory、energy |
| 正确性 | 输出误差、质量指标、失败与 fallback 比例 |

模型成功运行只证明某条路径可用。NPU 子图覆盖率、delegate 编译和转换成本共同决定端到端收益。

### 质量策略由应用实现

ADPF 没有 `AIPredictor` 或 `ContextAwareScheduler`。应用需要根据产品语义建立有限档位，例如：

- 降低相机采样频率或输入分辨率；
- 选择更小模型、较短 context 或较低输出上限；
- 调整 batch/concurrency，优先保护交互请求尾延迟；
- 暂停可选的后台 embedding、索引或预热；
- 在已验证条件下切换 CPU/GPU/NPU fallback。

档位切换要有滞回和最短保持时间，避免温度或 headroom 在阈值附近波动时频繁重建模型。

### Thermal 与 Headroom 提供约束信号

Performance Hint 告诉系统“线程希望按什么预算完成工作”；Thermal API 告诉应用设备是否接近热限制；Android 16 的 CPU/GPU Headroom 表示当前还有多少对应计算容量。三类信号不能互换。

对持续相机 AI 或 LLM，建议在非关键 worker 上低频读取 thermal/headroom，并用它选择质量档。不要根据一次电量百分比直接设所谓 `ULTRA_PERFORMANCE`，Android 公共 Session 没有这类模式。

## 不要用 affinity、busy loop 或 `MAP_HUGETLB` 代替调度设计

官方 Performance Hint 文档明确建议应用不要自行选择 CPU core affinity。移动 SoC 的 core topology、thermal 能力和厂商策略差异很大；绑到“大核”还可能压缩持续运行时间，或被设备忽略。

Android common kernel 6.18 中，EAS 决定 CPU placement，schedutil/CPUFreq 决定 policy frequency。ADPF 通过 framework 与 Power HAL 提供额外信号，公共契约没有“固定到 performance core”这一步。

同样，普通应用不能把 `MAP_HUGETLB | 2 MB` 当作可移植的模型内存方案。设备可能使用 16 KiB 基页，hugetlb pool 也未必配置或允许应用访问。模型 buffer 应按 runtime 和 accelerator 的公开 allocator/interop 要求创建，并分别测量 copy、TLB、RSS 与初始化成本。

## Perfetto 与运行时日志怎样配合

Android 没有保证每台设备都出现固定名为 `android.performance_hint` 的 Perfetto track。可移植的观测起点是：

- 应用自定义 slice：`ai/preprocess`、`ai/submit`、`ai/wait`、`ai/postprocess`；
- `sched_switch` / `sched_wakeup`：确认 session TID 是否及时运行；
- CPU frequency：观察 CPU 状态，但不把相关性写成 HintSession 的直接因果；
- GPU frequency/counter：设备与权限允许时采集；
- FrameTimeline：相机预览、AI 特效或结果 UI 是否影响帧；
- thermal status/headroom：记录热约束；
- runtime/delegate 日志：编译、划分、fallback 与错误；
- vendor NPU trace：有工程机或厂商工具时确认 NPU 执行和排队。

为每个 ADPF 周期加一个自定义 slice，可以把 target、actual 和阶段切换与 sched/frequency 对齐。slice 只能证明应用何时调用了 API；Power HAL 是否采取动作，仍需要系统日志、厂商 trace 或同机 A/B 支撑。

普通发布设备上，NPU queue、frequency 和能耗 rail 经常不可见。此时应把结论收窄到可观测层：端到端 latency、CPU scheduling、温度、总能耗与 delegate 确认。不要由 CPU frequency 单项推导 NPU 已提频。

## 一套可复现的接入顺序

### 1. 建立无 ADPF 基线

固定设备、build、模型、runtime、输入、温度区间和电源状态，记录 cold/warm 与持续运行结果。

### 2. 拆出 CPU 可控阶段

用自定义 trace 和线程 CPU time 区分 active work、accelerator execution、fence wait、I/O 和 UI。先确认 session 调整 CPU 资源有改善空间。

### 3. 固定线程所有权

为关键周期使用长期 worker，记录 Linux TID。避免每次请求创建线程、session 或模型。

### 4. 定义 target 并持续上报

target 来自阶段预算；每个周期上报 actual。质量档、模型或阶段改变后更新 target。NDK 客户端只在显著变化时使用 workload hint。

### 5. 接入热与质量策略

为分辨率、模型、context、batch、采样频率等建立少量已测档位，用滞回控制切换。ADPF 失败或 session 为 null 时，策略仍可运行。

### 6. 做同机 A/B

至少比较：

- end-to-end p50/p90/p99；
- first result / first token / inter-token latency；
- CPU time、run-queue delay 和频率分布；
- accelerator compile/execute/fallback；
- energy、thermal 与稳定运行时长；
- UI frame 与其他前台 workload 的回归。

### 7. 覆盖失败与生命周期

测试前后台切换、线程重建、delegate 初始化失败、NPU 不可用、模型 cache 失效、thermal severe 和取消请求。显式关闭 session、model 和 buffer。

## Android 17 公共 API 速查

| 能力 | 首次公开版本 | Android 17 边界 |
|---|---:|---|
| Java `PerformanceHintManager` / Session | API 31 | 创建 session、更新 target、上报 actual、关闭 session |
| NDK Performance Hint | API 33 | 与 Java 对应的 native session，不扩展到 NPU 控制 |
| Java/NDK `setThreads()` | API 34 | 替换 TID 集合；Java 调用同步 |
| `WorkDuration` + `reportActualWorkDuration(WorkDuration)` | API 35 | 只拆 CPU/GPU，无 NPU 字段 |
| `setPreferPowerEfficiency()` | API 35 | 能效偏好，不是 priority |
| NDK workload increase/reset/spike | API 36 | CPU/GPU 标记，per-app 限流 |
| `FEATURE_NEURAL_PROCESSING_UNIT` | API 37 | 能力声明，无性能保证 |
| `android.hardware.npu.IScheduling` | Android 17 vendor interface | system 按 UID 配置，非应用 SDK |

Android 17 的公开 Java Session 仍只有 `close()`、两种 `reportActualWorkDuration()`、`setPreferPowerEfficiency()`、`setThreads()` 和 `updateTargetWorkDuration()`。原稿中的 Session priority、migration policy、performance mode、frequency setter 和 callback 都不在 API 37 `core/api/current.txt`。

## 常见误区

### ADPF 会自动把推理放到 NPU

后端选择属于 LiteRT/delegate/vendor runtime。HintSession 只描述关联线程及其周期工作。

### actual 超过 target 时应切到 CPU

超时原因可能是 CPU 调度、NPU 排队、fallback、buffer copy、温控或 I/O。切到 CPU 只是一个需要 A/B 的候选，不能由一个比值自动决定。

### 前台任务都应提高优先级

公开 Session 没有应用可写的 priority API。前台状态、Linux scheduler、Power HAL 和 NPU UID policy 分属不同机制。

### 多线程越多，吞吐越高

增加 preprocessing worker、并发 inference 或 batch 可能造成 CPU、内存带宽、GPU/NPU queue 与 thermal 争用。交互业务通常先保护 p90/p99，再评估 throughput。

### 预热总能降低首帧

预热会提前消耗 CPU/NPU、内存与电量，还可能与启动或 UI 抢资源。需要区分 runtime load、model compile、buffer allocation 和 dummy inference，并在合适生命周期触发。

## 结论

ADPF 对端侧 AI 的价值集中在“可预测、周期性的 CPU/GPU 相关线程工作”：

- 给长期线程设置合理 target；
- 每周期报告可测的 actual；
- 在线程拓扑或业务阶段变化时更新 session；
- 用能效、thermal 和 headroom 信号选择应用质量档；
- 用端到端与持续性能验证系统是否受益。

模型由谁执行、NPU 怎样排队、哪些算子 fallback、内存怎样共享，仍由 runtime、vendor driver 和 Android 17 NPU control plane 分别负责。把这些层拆开，才能避免用一组不存在的“AI priority API”解释复杂的异构性能问题。
