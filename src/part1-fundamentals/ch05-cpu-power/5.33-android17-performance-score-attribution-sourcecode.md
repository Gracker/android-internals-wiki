# 5.33 Android 17 App Performance Score 归因链与低端机样本池建设

本节把“App Performance Score”限定为工程侧的性能评分归因模型，而不是 Android 17 公开提供的单一系统类或单一系统分数。材料首先纠正了一个容易误导后续实现的入口：在 android-17.0.0_r1 的 `frameworks/base` 源码中，`PerformanceMetricsManager.java` 不存在；可落地的 AOSP 性能提示基础设施应从 `PerformanceHintManager.java`、`IHintManager.aidl`、`IHintSession.aidl` 与 HAL 侧 `PowerHintSessionWrapper.cpp` 建模。[来源: 2026-07-16-android17-performance-score-attribution-sourcecode.md]

## 5.33.1 先纠错：不要把 PerformanceMetricsManager 当作 Android 17 入口

材料通过 `git ls-tree` 与目录检查确认，android-17.0.0_r1 的 `frameworks/base/core/java/android/app/` 下不存在 `PerformanceMetricsManager.java`，因此任何以该类作为 Android 17 性能评分主入口的链路都应回退重查。[来源: 2026-07-16-android17-performance-score-attribution-sourcecode.md]

正确的基础入口是 `core/java/android/os/PerformanceHintManager.java`。该类以 `@SystemService(Context.PERFORMANCE_HINT_SERVICE)` 暴露性能提示服务，并提供 `createHintSession(int[] tids, long initialTargetWorkDurationNanos)` 创建 hint session；会话侧可调用 `updateTargetWorkDuration(long targetDurationNanos)` 更新目标工作时长，也可通过 `reportActualWorkDuration(long actualDurationNanos)` 反馈实际工作时长。[来源: 2026-07-16-android17-performance-score-attribution-sourcecode.md]

材料还记录了一个 Android 17 相关的增强点：`PerformanceHintManager.Session` 存在带 `WorkDuration` 参数的 `reportActualWorkDuration(@NonNull WorkDuration workDuration)` 变体，并由 `@FlaggedApi(Flags.FLAG_ADPF_GPU_REPORT_ACTUAL_WORK_DURATION)` 标记，用于支持分离 CPU/GPU 工作时长的反馈路径。[来源: 2026-07-16-android17-performance-score-attribution-sourcecode.md]

## 5.33.2 归因链：从应用工作时长到 HAL 与调度器

基于材料中的调用链，Android 17 上可以把性能归因链拆成七段：App Layer 调用 `PerformanceHintManager.createHintSession()`；随后 `PerformanceHintManager.Session.reportActualWorkDuration()` 反馈实际耗时；Java 层通过 `nativeReportActualWorkDuration` 进入 JNI bridge；AIDL 层落到 `IHintSession.reportActualWorkDuration()`；native power manager 侧由 `PowerHintSessionWrapper` 转发；HAL 层进入 `IPowerHintSession`；最终反馈给 Kernel Scheduler 相关实现。[来源: 2026-07-16-android17-performance-score-attribution-sourcecode.md]

这条链路的工程含义是：应用先声明目标工作时长，再报告实际工作时长；系统侧结合 CPU/GPU headroom 结果与 hint session 状态，把“目标—实际—硬件余量”的差异转化为可观测的样本数据。[来源: 2026-07-16-android17-performance-score-attribution-sourcecode.md]

因此，若要在应用或厂商平台侧构建 App Performance Score，分数本身应作为业务层/平台层模型产物，而底层证据可来自三类 AOSP 信号：目标工作时长、实际工作时长、CPU/GPU 负载头寸。材料没有验证 AOSP 存在一个名为 App Performance Score 的统一系统 API，所以本节不把它写成 Android 17 的官方单点接口。[来源: 2026-07-16-android17-performance-score-attribution-sourcecode.md]

## 5.33.3 Android 17 CPU/GPU Headroom API

材料确认 Android 17 新增了 CPU/GPU 负载头寸计算相关接口：`IHintManager.getCpuHeadroom()` 与 `IHintManager.getGpuHeadroom()`，并配套最小查询间隔方法 `getCpuHeadroomMinIntervalMillis()`、`getGpuHeadroomMinIntervalMillis()`。[来源: 2026-07-16-android17-performance-score-attribution-sourcecode.md]

CPU 侧参数类为 `CpuHeadroomParams`，材料摘录的关键字段包括 `calculationType`、`calculationWindowMillis` 与 `tids`；其中 `calculationType` 可表达 MIN/AVERAGE 这类计算类型，`tids` 用于限定目标线程集合。[来源: 2026-07-16-android17-performance-score-attribution-sourcecode.md]

GPU 侧参数类为 `GpuHeadroomParams`，材料摘录的关键字段包括 `calculationType` 与 `calculationWindowMillis`；材料标注 `calculationWindowMillis` 的范围为 50-10000ms。[来源: 2026-07-16-android17-performance-score-attribution-sourcecode.md]

内部 AIDL 参数 `CpuHeadroomParamsInternal` 还包含 `usesDeviceHeadroom`、`tids`、默认 1000ms 的 `calculationWindowMillis`，以及默认为 `CpuHeadroomParams.CalculationType.MIN` 的 `calculationType`。[来源: 2026-07-16-android17-performance-score-attribution-sourcecode.md]

这些 API 在材料中被标记为 `@FlaggedApi(Flags.FLAG_CPU_GPU_HEADROOMS)`，因此在书稿表达上应把它们视作 Android 17 源码中可见的受 flag 管控能力，而不是无条件、全设备稳定开放的应用契约。[来源: 2026-07-16-android17-performance-score-attribution-sourcecode.md]

## 5.33.4 AIDL 与 HAL 版本边界

材料中的 `IHintManager.aidl` 片段显示，除 CPU/GPU headroom 查询外，Android 17 相关接口还包括 `setHintSessionThreads(in IHintSession hintSession, in int[] tids)` 与 `associateToLayers(in IBinder[] layerTokens)`；后者用于把 session 与图形层 token 关联。[来源: 2026-07-16-android17-performance-score-attribution-sourcecode.md]

材料中的 `IHintSession.aidl` 片段显示，会话侧存在 `reportActualWorkDuration2(in WorkDuration[] workDurations)` 批量工作时长报告、`setMode(int mode, boolean enabled)` 会话模式切换，以及 `associateToLayers(in IBinder[] layerTokens)` 图形层关联能力。[来源: 2026-07-16-android17-performance-score-attribution-sourcecode.md]

HAL 包装层由 `frameworks/native/services/powermanager/PowerHintSessionWrapper.cpp` 封装。材料记录的版本映射是：HAL v2 覆盖 `updateTargetWorkDuration` 与 `reportActualWorkDuration`；HAL v4 增加 `sendHint`；HAL v5 增加 `setMode`。[来源: 2026-07-16-android17-performance-score-attribution-sourcecode.md]

因为 `PowerHintSessionWrapper` 同时承担版本检测、故障回退与统一错误处理，所以跨设备实现时不能只看 Java API 是否存在，还要检查目标设备 Power HAL 对相应版本方法的支持情况。[来源: 2026-07-16-android17-performance-score-attribution-sourcecode.md]

## 5.33.5 低端机样本池：用 headroom 与 work duration 建基线

材料给出的低端机适配价值主要有四点：通过 headroom API 量化硬件负载，通过样本池收集不同硬件配置下的性能基线，通过实际工作时长反馈动态调整线程调度策略，并在目标设备的 hint session 模式与 Power HAL 版本支持时承载偏省电取向的调度策略。[来源: 2026-07-16-android17-performance-score-attribution-sourcecode.md]

在样本池设计上，材料支持的最小可落地字段应包括：设备/SoC 分组、目标线程 `tids`、目标工作时长、实际工作时长、CPU headroom、GPU headroom、计算窗口大小、hint session 模式状态，以及采样时间戳。[来源: 2026-07-16-android17-performance-score-attribution-sourcecode.md]

对国内厂商或非 Play 渠道场景，材料明确提出可以通过 `CpuHeadroomParams` 做参数定制；低端机可在遵守 headroom 最小查询间隔与窗口范围的前提下尝试较小的 `calculationWindowMillis`，模式切换能力则可作为自定义调度策略的系统侧承载点。[来源: 2026-07-16-android17-performance-score-attribution-sourcecode.md]

需要保守处理的是：材料没有验证真实硬件 headroom 算法、国内厂商私有扩展接口、以及端到端样本聚合方法；这些内容依赖芯片厂商 HAL、非 AOSP 仓库或系统分析工具。因此本节不写入“某厂商必然如此实现”或“某固定样本量/阈值必然有效”的结论。[来源: 2026-07-16-android17-performance-score-attribution-sourcecode.md]

## 5.33.6 建议的评分归因模型边界

基于材料，本书建议把 App Performance Score 归因拆成三层：第一层是 AOSP 可验证信号，包括 `PerformanceHintManager` 会话、实际工作时长反馈、CPU/GPU headroom 与 AIDL/HAL 版本能力；第二层是设备样本池，用相同窗口与相同线程集合对不同硬件分组形成基线；第三层才是业务评分模型，把目标耗时偏差、实际耗时、headroom 与设备分组输入到业务侧评分器。[来源: 2026-07-16-android17-performance-score-attribution-sourcecode.md]

这种分层能避免两个常见错误：一是把不存在的 `PerformanceMetricsManager.java` 当作源码入口；二是把业务侧的 Performance Score 误写成 Android 17 源码已经提供的统一官方得分。[来源: 2026-07-16-android17-performance-score-attribution-sourcecode.md]

## 5.33.7 待验证清单

- JNI bridge 的 `android_os_PerformanceHintManager.cpp` 实现尚未在材料中验证，因为材料说明浅克隆无法获取对应源码。[来源: 2026-07-16-android17-performance-score-attribution-sourcecode.md]
- system_server 层 `PerformanceHintManagerService` 实现尚未在材料中验证，需要独立仓库或更完整源码树继续核查。[来源: 2026-07-16-android17-performance-score-attribution-sourcecode.md]
- 真实硬件的 headroom 计算算法依赖芯片厂商 HAL，材料未验证具体算法。[来源: 2026-07-16-android17-performance-score-attribution-sourcecode.md]
- 国内厂商定制化扩展接口不属于材料已验证范围，需要非 AOSP 仓库或厂商文档继续调研。[来源: 2026-07-16-android17-performance-score-attribution-sourcecode.md]
- 低端机样本池的数据聚合和统计方法仍需系统分析工具验证，本节只给出基于 AOSP 信号的字段边界。[来源: 2026-07-16-android17-performance-score-attribution-sourcecode.md]
