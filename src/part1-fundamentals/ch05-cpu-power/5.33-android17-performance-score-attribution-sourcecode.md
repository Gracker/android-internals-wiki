# 5.33 Android 17 App Performance Score 归因链与低端机样本池建设

“App Performance Score”在本章中指团队自建的评价指标。Android 17 没有同名系统分数，也没有 `PerformanceMetricsManager` 这个公开类。AOSP 能提供的是多组含义不同的信号：ADPF hint session 接收应用的工作周期反馈，CPU/GPU Headroom 给出近期可用容量估计，帧时序、温度、功耗和业务结果则要从各自的数据源采集。评分器只能在这些原始数据之上建设，不能冒充系统能力。

这项区分很重要。ADPF 报告一次工作耗时，并不等于 Android 已经替应用完成性能归因；Headroom 返回一个百分比，也不能单独证明掉帧由 CPU 或 GPU 引起。先弄清每个信号的生产者、时间语义和设备边界，评分才有解释价值。

## 5.33.1 先校正 API 与版本边界

Android 17 / API 37 的平台源码锚点为 `android-17.0.0_r1`。从这个 tag 检查 `frameworks/base`，可以确认以下事实：

- `PerformanceHintManager` 位于 `core/java/android/os/PerformanceHintManager.java`，通过 `Context.PERFORMANCE_HINT_SERVICE` 获取。该公开能力从 Android 12 / API 31 开始提供，并非 Android 17 新增。
- `PerformanceHintManager.Session.reportActualWorkDuration(WorkDuration)` 和 `setPreferPowerEfficiency()` 从 API 35 开始提供。`WorkDuration` 可以分别携带总耗时、CPU 耗时、GPU 耗时和工作周期开始时间。
- CPU/GPU Headroom 的应用入口位于 `android.os.health.SystemHealthManager`，从 Android 16 / API 36 开始提供。Android 17 延续并完善了对应的 framework、system_server 与 Power HAL 支持。
- `PerformanceMetricsManager.java` 不存在。遇到以该类为起点的调用链、示例代码或架构图，应先检查资料是否把自建类名误写成了 Android API。

公开 API 的版本号只回答“应用能否编译调用”。设备是否支持，还取决于 `HintManagerService` 从 Power HAL 获得的 `SupportInfo`。因此，应用仍要处理 `createHintSession()` 返回 `null`、Headroom 抛出 `UnsupportedOperationException`，以及 Headroom 暂时返回 `Float.NaN` 等情况。

## 5.33.2 ADPF 是控制反馈通道

ADPF hint session 面向具有稳定周期和明确截止时间的工作，例如游戏每帧的仿真、渲染准备或音频处理。应用创建 session 时提交一组长期存活、共同完成同一工作负载的 Linux TID，并给出每个周期的目标时长；之后逐周期报告实际时长。系统和厂商实现可以据此调整线程调度与性能状态。

这里的关键词是“控制反馈”。`targetDurationNanos` 表示应用希望完成工作的截止预算，`actualDurationNanos` 表示上一周期的观测值。Power HAL 根据连续反馈决定资源策略。AOSP 没有把这些报告存成面向应用的性能分数，也没有承诺某次报告一定触发升频、迁核或某个内核调度接口。

### Java 调用走过哪些层

以 `reportActualWorkDuration()` 为例，Android 17 的完整路径需要分成客户端和服务端两部分：

1. `PerformanceHintManager.Session` 调用 `core/jni/android_os_PerformanceHintManager.cpp`。
2. 该 JNI 文件动态加载 `libandroid.so`，解析 `APerformanceHint_*` 与 `AWorkDuration_*` NDK 符号。
3. `frameworks/base/native/android/performance_hint.cpp` 中的客户端创建 `IHintManager` 代理，通过 `createHintSessionWithConfig()` 在 `system_server` 创建会话。
4. 对高频的实际时长、目标时长、hint 和 mode 报告，客户端会优先尝试 FMQ。FMQ 未启用、缺少 session config、空间不足或队列损坏时，回退到 `IHintSession` 的 one-way Binder 调用。
5. `HintManagerService.AppHintSession` 检查会话状态和参数，经 `services/core/jni/com_android_server_hint_HintManagerService.cpp` 调用 `PowerHalController`。
6. `frameworks/native/services/powermanager/PowerHintSessionWrapper.cpp` 把请求转给 Power HAL 的 `IPowerHintSession`。
7. Power HAL 如何解释报告，由设备实现决定。它可能调节 CPU/GPU 性能、线程放置或其他电源策略；AOSP 这条调用链没有规定请求最终必须落到某个 Kernel Scheduler hook。

FMQ 优化的是高频消息传输成本。它没有改变信号含义，也不会自动生成额外的性能指标。分析 trace 时还要注意：FMQ 正常工作时，不一定能在每个周期看到对应的 app 到 `system_server` Binder 事务。

### 前后台状态会改变会话行为

`HintManagerService` 通过 UID 进程状态限制应用 session。UID 离开允许的前台状态后，`AppHintSession.updateHintAllowedByProcState()` 会暂停 HAL session；回到前台后再恢复。会话被暂停时，`updateTargetWorkDuration()` 和实际时长报告会被服务端忽略。线程全部失效等情况还可能触发强制暂停。

因此，样本记录至少要带上应用可见性、生命周期阶段和 session 是否有效。把后台阶段的“没有调节效果”解释为 ADPF 算法失效，会得到错误结论。

## 5.33.3 正确理解 WorkDuration

`reportActualWorkDuration(long)` 适合只报告总周期耗时的常规 CPU 工作。Android 17 的 native 客户端会把它转换为一条 `WorkDuration`：总耗时和 CPU 耗时都等于传入值，GPU 耗时为 0，工作周期开始时间为 0，以兼容旧接口。

`reportActualWorkDuration(WorkDuration)` 可以表达更完整的异构工作周期：

- `actualTotalDurationNanos` 是工作周期的墙上时间，必须大于 0。
- `workPeriodStartTimestampNanos` 使用与 `SystemClock.uptimeNanos()` 一致的时基，公开对象要求大于 0。
- `actualCpuDurationNanos` 与 `actualGpuDurationNanos` 均不得小于 0，且不能同时为 0。
- CPU 和 GPU 工作可能重叠。总耗时不要求等于 CPU 耗时与 GPU 耗时之和，也不应由两者直接相加推导。

客户端会暂存一小批 duration，并根据 HAL preferred update rate 控制报告频率；随后通过 FMQ 或 `IHintSession.reportActualWorkDuration2()` 批量提交。由此带来两个采集要求：应用侧评分必须保存自己测得的逐周期原始值，不能期望从 system_server 反查完整分布；分析时间线时也不能把一次 IPC 当成一个工作周期。

目标时长变更时调用 `updateTargetWorkDuration()`。目标 FPS、场景预算没有变化时，无需每帧重复更新。实际时长则应按完成的工作周期持续报告，不能只挑慢帧上报，否则反馈会偏向最差样本。

## 5.33.4 Headroom 是独立的容量估计

CPU/GPU Headroom 由 `SystemHealthManager` 暴露，经 `IHintManager.getCpuHeadroom()` 或 `getGpuHeadroom()` 到 `HintManagerService`，再查询 Power HAL。它与某个 `PerformanceHintManager.Session` 没有绑定关系。AOSP 也没有把 Headroom 和 session 的目标/实际耗时合并。

有效返回值位于 `[0, 100]`：

- `0` 表示按设备当前算法，已经没有更多相应资源可授予。
- 较大的值表示近期观测下还有更多容量。
- `Float.NaN` 表示暂时无法给出结果，例如服务端错误或 CPU 用户态工作量不足。

Headroom 描述近期历史窗口中的容量估计，不是利用率、频率占比、未来性能保证或固定的硬件上限。查询完成到应用采取动作之间存在 TOCTOU 窗口；温控、电源限制、其他进程负载和 DVFS 都可能让容量迅速变化。

CPU Headroom 与 GPU Headroom 还来自两个设备实现。即便都使用 0 到 100 的范围，二者也不能相加、相减，或按数值大小直接判定“CPU 比 GPU 忙”。更可靠的用法是在同一设备、同一场景、相同参数下观察各自的变化，并结合 CPU/GPU 工作耗时、帧时序和温控状态判断瓶颈。

### 参数与调用成本

CPU 和 GPU 参数都支持 `MIN` 与 `AVERAGE` 两种计算类型：

- `MIN` 关注窗口内最小 Headroom，适合观察一段时间内最紧张的容量点，但更容易受短时波动影响。
- `AVERAGE` 反映窗口平均水平，读数更平稳，也可能掩盖短促尖峰。

`calculationWindowMillis` 必须落在设备通过 `SupportInfo` 报告的范围内。`GpuHeadroomParams` 源码中虽定义了 50 ms 与 10000 ms 常量，调用端仍应以 `getGpuHeadroomCalculationWindowRange()` 返回值为准；CPU 也应先查询自己的窗口范围。较小窗口只会提高时间敏感度和波动，不等于更适合低端机。

CPU 参数还能指定 TID。普通应用提交的 TID 必须属于调用进程；多 TID 查询还可能检查各线程的 CPU affinity 是否一致，并受设备报告的最大数量约束。TID 未设置时，以调用进程为范围。GPU Headroom 没有对应的 TID 过滤。

每次合法的公开 Headroom 调用至少包含一次同步 Binder 事务，文档提示耗时可能超过 1 ms，首次使用非默认参数还可能更慢。不要在渲染关键线程或每帧路径中等待结果。调用频率高于 `getCpuHeadroomMinIntervalMillis()` / `getGpuHeadroomMinIntervalMillis()` 时，`HintManagerService` 可以返回缓存值；采集端应把查询时间、计算窗口和最小轮询间隔一起保存。

Android 17 的 Headroom 支持信息来自 Power HAL v6 的 `getSupportInfo()`。设备未报告 CPU 或 GPU Headroom 支持时，framework 会拒绝相应调用。不能仅凭系统版本推断某台设备一定有有效读数。

## 5.33.5 AIDL 与 Power HAL 的版本界线

`android-17.0.0_r1` 中，`IHintManager` 负责管理器级操作，包括创建 session、设置和获取线程、建立/关闭 FMQ channel、查询 Headroom、注册客户端与取得支持信息。图形层关联不在该接口中。

`IHintSession` 是 one-way 会话接口，包含目标时长更新、两种实际时长报告、`sendHint()`、`setMode()` 和 `associateToLayers()`。后者接收 layer token，只能在已有 session 上调用。把 `associateToLayers()` 写成 `IHintManager` 方法，会导致源码导航和版本判断同时出错。

`PowerHintSessionWrapper.cpp` 的最低 HAL 版本映射如下：

| Power HAL 版本 | wrapper 放行的方法 |
|---|---|
| v2 | `updateTargetWorkDuration`、`reportActualWorkDuration`、`pause`、`resume`、`close` |
| v4 | `sendHint`、`setThreads` |
| v5 | `setMode`、`getSessionConfig` |

wrapper 会先看接口版本，并缓存某个方法返回 unsupported 的结果，避免后续反复调用。表中的“放行”只表示接口版本满足最低要求；某项 session hint、mode 或 tag 是否受支持，还要看 Android 17 的 `SupportInfo` 位图。Headroom 则要求 Power HAL v6 才能通过 `getSupportInfo()` 声明能力、窗口范围和最小轮询间隔。

## 5.33.6 AOSP 自带的统计能回答什么

`HintManagerService` 注册了多组 statsd atom，但这些 atom 不能替代应用样本池：

- `ADPF_SYSTEM_COMPONENT_INFO` 记录 SurfaceFlinger/HWUI 相关开关和 FMQ 使用状态。
- `ADPF_SUPPORT_INFO` 记录 Power HAL 版本、vendor API level、session/hint/mode/tag 支持位图，以及 Headroom 支持、窗口和轮询间隔。
- `ADPF_SESSION_SNAPSHOT` 按 UID 和 session tag 记录最大并发 session 数、最大线程数、偏省电 session 数、若干目标时长、图形管线 session 数等摘要。
- `CPU_HEADROOM_REPORTED` 与 `GPU_HEADROOM_REPORTED` 记录调用参数、缓存命中、状态和归一化后的返回值等系统统计。

`ADPF_SESSION_SNAPSHOT` 不含应用逐周期上报的 actual duration 分布，也没有“App Performance Score”字段。statsd atom 还是系统内部遥测接口，普通应用不能把它当成稳定的业务数据 API。要复现评分、解释回归，应用或测试平台必须保存自己的原始观测。

## 5.33.7 低端机样本池怎么建

“低端机”不宜只按发布价格或品牌划分。对性能分析更有用的分组条件包括 CPU 拓扑和 ABI、GPU 型号与驱动、内存容量、屏幕分辨率与刷新率、存储类型、Android build、Power HAL 能力，以及长期运行后的温控表现。最终分组应由目标场景的实测分布校正。

### 场景必须先固定

不同场景的数据混在一起，分数很快会失去含义。每条样本需要标出：

- 场景 ID 与场景版本，例如“战斗场景 A / 60 FPS / 1080p / 特效等级 2”。
- 冷启动、热启动或稳定运行阶段，以及预热时长。
- 前后台、充电、电池电量、热状态、环境温度可用性。
- 应用版本、资源版本、Android build、设备和 SoC 分组。
- 是否启用 ADPF、session tag、目标时长、Power HAL 版本及相关 capability。

渲染分辨率、目标 FPS 或内容复杂度变化后，应产生新的场景版本。旧基线仍可用于版本对比，但不能与新配置混算成同一总体。

### 保存可重放的原始维度

一次工作周期建议至少记录：

- `work_period_start_ns`、`target_ns`、`actual_total_ns`。
- 可可靠测得时的 `actual_cpu_ns`、`actual_gpu_ns`，并注明测量口径。
- 帧开始、提交、present 或业务完成时间，以及 jank / deadline miss 结果。
- 最近一次 CPU/GPU Headroom 的值、查询时间、计算类型、窗口和是否为 `NaN`。
- thermal status、thermal headroom、充电状态、电量和当前显示模式。
- session 是否创建成功、是否在前台、报告错误和 capability 缺失原因。

原始 Linux TID 只在进程生命周期内有意义，跨启动会复用。样本池可保存“渲染线程”“工作线程组”这类逻辑角色和线程数量，排障日志再按需保存短期 TID；不要把 TID 当成长期设备标识。

### Headroom 采样不要阻塞工作线程

Headroom 查询放在非关键线程，频率不高于设备报告的最小轮询间隔。读数必须带时间戳，再与附近的工作周期关联。CPU 与 GPU 可以有不同的最小间隔和计算窗口，分析时要保留这种差异。

一个常见误区是只在慢帧发生后查询 Headroom，再把读数当作慢帧发生前的资源状态。Headroom 本来就回看一段历史，查询本身又晚于事件；这种样本最多支持相关性分析。需要精确归因时，应同时使用 Perfetto 的调度、频率、GPU、FrameTimeline 和 thermal 轨迹。

### 用设备内基线，再做跨设备比较

建议先在每个“设备分组 × 场景版本”中计算：

- deadline 命中率；
- `actual_total_ns / target_ns` 的 p50、p90、p95 与 p99；
- jank 比例和连续 jank 长度；
- CPU/GPU Headroom 各自的分位数与 `NaN` 比例；
- 不同 thermal status 下的性能衰减；
- 样本数、设备数和置信区间。

这些维度比单一平均值更容易发现问题。低端机的长尾经常决定体验，平均耗时可能仍在目标以内。

若产品必须输出 0 到 100 的单一分数，可以在同一设备分组和场景版本内，用 `actual_total_ns / target_ns` 的经验分位、deadline miss 与 jank 共同映射，再单独展示 thermal 和 Headroom 诊断项。映射规则、基线版本和样本量必须随结果发布。不要把 CPU Headroom 与 GPU Headroom 直接加权成总分，也不要用跨 SoC 的固定 Headroom 阈值定义优劣。

## 5.33.8 如何从相关走向归因

评分用于发现回归，归因需要额外证据。可以按以下顺序缩小范围：

1. 先确认业务结果：哪一类场景、哪个版本、哪个设备分组的 deadline 或 jank 退化。
2. 检查数据质量：目标时长是否一致、session 是否有效、Headroom 是否过期或为 `NaN`。
3. 比较同设备同场景的 CPU/GPU 工作耗时和各自 Headroom 趋势，只提出“更像 CPU 受限”或“更像 GPU 受限”的假设。
4. 用 Perfetto 验证线程 runnable、CPU 频率与迁核、GPU queue、FrameTimeline、thermal throttling 等事件。
5. 通过控制变量实验确认原因，例如降低 CPU 工作量、降低 GPU 分辨率、关闭某项特效或固定内容输入。

只有 Headroom 下降与耗时上升的相关性时，不足以断言因果。其他进程竞争、温控降频、驱动排队和内容变化都可能同时影响两者。

## 5.33.9 源码锚点与核查结论

本章以 Android 平台 `android-17.0.0_r1` 为准，关键源码位置如下：

- `frameworks/base/core/java/android/os/PerformanceHintManager.java`
- `frameworks/base/core/java/android/os/WorkDuration.java`
- `frameworks/base/core/java/android/os/CpuHeadroomParams.java`
- `frameworks/base/core/java/android/os/GpuHeadroomParams.java`
- `frameworks/base/core/java/android/os/health/SystemHealthManager.java`
- `frameworks/base/core/java/android/os/IHintManager.aidl`
- `frameworks/base/core/java/android/os/IHintSession.aidl`
- `frameworks/base/core/jni/android_os_PerformanceHintManager.cpp`
- `frameworks/base/native/android/performance_hint.cpp`
- `frameworks/base/services/core/java/com/android/server/power/hint/HintManagerService.java`
- `frameworks/base/services/core/jni/com_android_server_hint_HintManagerService.cpp`
- `frameworks/native/services/powermanager/PowerHintSessionWrapper.cpp`

已通过上述源码确认 Java/JNI/native client、FMQ/Binder 回退、system_server、JNI 到 Power HAL 的路径。仍不能从 AOSP 得出统一的厂商 Headroom 算法、Power HAL 资源决策或私有扩展接口；这些结论需要目标设备的 vendor 源码、HAL 调试信息和实机 trace。Kernel 侧也没有一条由本章 API 保证抵达的固定调用链，因此无需为本章虚构 `android17-6.18-2026-06_r6` 下的调度器终点。
