# 5.23 Android 17 后台音频 Hardening 与 LE Audio 功耗边界

<!-- outline-start -->
## 要点

### 🔹 控制 API 与 playback hardening 分层
Android 17 的 Java `HardeningEnforcer` 处理音量/铃声/focus 控制入口，AudioFlinger `Tracks.cpp` 处理 playback track 静音政策；两者共享 override，但不能合并成“同一事件双判定”。

### 🔹 硬化决策矩阵设计
音量与焦点方法的精细化控制矩阵，包括权限豁免、targetSdk 版本判断、蓝牙连接权限特殊处理等。

### 🔹 音频焦点状态机
`MediaFocusControl` 在 hardening 放行后才进行焦点仲裁，同时还受 external policy、multi-focus、delayed focus 与 isolation 等路径影响。

### 🔹 LE Audio 功耗治理边界
蓝牙 LE Audio 在 system suspend 入口会停止当前 background scan；active device 与 HFP handover 是连接/通话兼容流程，不是 hardening 的后续调用链。

### 🔹 LC3 codec offload capability 匹配
`IsLc3ConfigMatched()` 只匹配 ADSP capability 的 LC3 维度；HOST 路径仍是系统侧 codec pipeline，不等于应用进程解码。

## 扩展

### 🔸 硬化事件 metrics 上报
`maybeLogPlaybackHardening()` 机制及 `mPlaybackHardeningLogged` 守门设计防止重复上报。

### 🔸 Shell 接口与系统交互
`cmd audio set-hardening` 命令实现及四种模式（DEFAULT/ENABLE/DISABLE/THROW）的行为差异。
<!-- outline-end -->

> [!NOTE]
> 本文已按 `android-17.0.0_r1` 的 Framework、AudioFlinger 与 Bluetooth module 源码复核：控制 API hardening、playback hardening、audio focus 与 LE Audio/offload 是相邻但不同的机制，功耗或静音问题要先分清触发路径。本文没有使用 Android 18/API 38+ 主线行为外推，也不把 LE Audio offload 的设备相关收益写成 AOSP 保证。

## 先把三类机制分开

这篇文章涉及的代码都与音频有关，但它们解决的问题不同：

| 机制 | 所在进程/模块 | 处理对象 | 主要结果 |
|---|---|---|---|
| 控制 API hardening | `system_server` / `HardeningEnforcer` | 音量、铃声模式、audio focus 请求 | 允许、忽略、返回 focus failed，测试模式下也可能抛异常 |
| Playback hardening | `audioserver` / AudioFlinger | playback track | 根据 enforcement level 与 AppOps 状态决定是否静音 |
| LE Audio 连接与 codec offload | Bluetooth module | 扫描、active group、CIS/SCO handover、codec 配置 | 管理蓝牙连接与选择 host/ADSP codec 路径 |

`HardeningEnforcer` 不负责 LE Audio 扫描，`LeAudioService` 也不参与音频 hardening 的 AppOps 判定。功耗分析时可以在同一用例中观察这些机制，却不能把它们画成一条固定调用路径。

## Hardening 的共同基础：AppOps、兼容规则与 override

Android 17 使用两级控制 AppOps：

- `OP_CONTROL_AUDIO_PARTIAL`
- `OP_CONTROL_AUDIO`

代码中的 `PARTIAL` 和 `FULL` 表示应检查哪一级 AppOp，不是“限制 50%”或“完全没有声音”的通用比例。最终动作还取决于调用面：控制 API 可能被忽略，focus 请求可能返回失败，playback track 则可能被 AudioFlinger 静音。

系统还保存一个 hardening override。`AudioService.setHardeningOverride()` 先更新 Java 侧的 `AtomicInteger`，再调用 `mAudioPolicy.setHardeningOverride()` 把同一个 override 交给 audioserver。四个值为：

| Override | 语义 |
|---|---|
| `DEFAULT` | 按 flags、权限、target SDK 与 usage 等规则判断 |
| `DISABLE` | 调试时关闭 hardening enforcement |
| `ENABLE` | 调试时按 FULL 级别处理 |
| `THROW` | Java 控制 API 遇到受限操作时抛出 `IllegalStateException`；native playback 路径把它按 FULL 处理 |

共享 override 不代表 Java 与 C++ 会对“同一个 `AudioAttributes`”重复作出相同结论。两条路径的对象、输入和输出均不同。

## Java 路径：在 API 入口挡住音量与焦点操作

### 音量与铃声模式

`AudioService` 在 `adjustStreamVolume()`、`setStreamVolumeWithAttribution()`、`adjustVolume()`、`adjustSuggestedStreamVolume()` 和 `setRingerModeExternal()` 等入口调用 `blockVolumeMethod()`。该方法先 note 两级 AppOp；两级均允许时直接放行，只有 AppOp 已受限时才继续计算兼容政策。

默认 override 下，Android 17 的非 Automotive 路径按以下顺序处理：

1. 具有特权音频权限的 UID 放行；
2. 具有 `USE_EXACT_ALARM` 或 schedule-exact-alarm 能力的 UID，最多应用 PARTIAL 级别；
3. `hardeningPartialVolume()` 关闭时放行；
4. `targetSdk < 37` 时，最多应用 PARTIAL 级别；
5. 其余情况采用 FULL 级别。

音量 API 没有 `AudioAttributes` 参数，因此这里的 exact-alarm 兼容分支不检查 `USAGE_ALARM`。Automotive 另有 `autoPublicVolumeApiHardening()` 分支，不能套用手机路径的规则表。

### Audio focus 请求

`AudioService.requestAudioFocus()` 先做调用参数、权限等检查，随后调用 `blockFocusMethod()`。hardening 判定返回 blocked 时，方法返回 `AUDIOFOCUS_REQUEST_FAILED`，请求不会进入 `MediaFocusControl`。

下面的缩减代码用于说明 DEFAULT 模式的兼容顺序；它省略了 metrics 常量，但没有改变判断关系：

```java
if (isPrivileged) {
    enforcedLevel = ALLOWED;
} else if (usage == USAGE_ALARM && canScheduleExactAlarm) {
    enforcedLevel = DENIED_IF_PARTIAL;
} else if (!hardeningPartial() && targetSdk < VANILLA_ICE_CREAM) {
    enforcedLevel = ALLOWED;
} else if (holdsPermission(BLUETOOTH_CONNECT, uid)) {
    enforcedLevel = DENIED_IF_PARTIAL;
} else if (targetSdk < CINNAMON_BUN) {
    enforcedLevel = DENIED_IF_PARTIAL;
} else if (!hardeningStrict()) {
    enforcedLevel = DENIED_IF_PARTIAL;
} else {
    enforcedLevel = DENIED_IF_FULL;
}
```

这段顺序说明 `BLUETOOTH_CONNECT` 只把 enforcement level 降到 PARTIAL；它不是无条件放行权限。闹钟分支同时要求 `USAGE_ALARM` 和精确闹钟能力。`VANILLA_ICE_CREAM` 是 API 35，`CINNAMON_BUN` 是 API 37；这些常量说明 Android 17 当前代码的兼容分支，不能单独证明旧版本当时启用了哪些 flags。

- [`HardeningEnforcer.java`](https://cs.android.com/android/platform/superproject/+/android-17.0.0_r1:frameworks/base/services/core/java/com/android/server/audio/HardeningEnforcer.java)
- [`AudioService.requestAudioFocus()`](https://cs.android.com/android/platform/superproject/+/android-17.0.0_r1:frameworks/base/services/core/java/com/android/server/audio/AudioService.java)

## AudioFlinger 路径：在 playback track 上执行静音政策

`AfPlaybackCommon` 由普通 playback track 与 MMAP track 共用。构造时，`getHardeningDecision()` 根据 override、usage、权限、flags 和 UID 的最高 target SDK 选择 `NONE`、`PARTIAL` 或 `FULL`。随后为需要 hardening 的非可信 UID 建立两个 `AppOpsSession`，持续接收两级 AppOp 的状态。

下面的源码节选用于确认 enforcement level 怎样变成 playback restriction：

```cpp
bool isPlaybackRestrictedControl() const {
    switch (mEnforcementLevel) {
        case EnforcementLevel::NONE:
            return false;
        case EnforcementLevel::PARTIAL:
            return !hasOpControlPartial();
        case EnforcementLevel::FULL:
            return !hasOpControlFull();
    }
}
```

该函数只回答 track 是否因 control AppOp 受限。`PlaybackTrack::isPlaybackRestricted()` 还会合并 `OP_PLAY_AUDIO` 的结果，因此排查静音时不能只看 hardening level。

### Native 判定与 Java 判定为何不能叫“双判同一事件”

AudioFlinger 处理的是 playback track，Java `HardeningEnforcer` 处理的是控制方法。两者有相似的兼容项，但 native 路径还包含：

- `AUDIO_USAGE_VIRTUAL_SOURCE` 与 system usage 豁免；
- playback usage 相关的 alarm/accessibility 分支；
- `MODIFY_AUDIO_ROUTING`、`MODIFY_PHONE_STATE` 等 native permission provider 查询；
- `shouldPlaybackHarden`、可信 UID 过滤以及 AppOps session 生命周期。

反过来，Java 音量路径知道具体调用的是 set/adjust/ringer API，却没有 playback track 的 usage。把两条路径合并成同一套规则会丢失这些差异。

### 40 ms 是 Offload/MMAP callback 的延迟，不是 Track 创建耗时

`Tracks.cpp` 中的 `kBroadcastDelay = 40ms` 只用于 Offload 或 MMAP track：当 partial/full permission callback 到达后，通过 `asyncBroadcast()` 唤醒线程，并给两种 callback 留出汇合时间。它不是构造 `AudioTrack` 的固定开销，也不表示每个 track 都会被额外阻塞 40 ms。

### Metrics 每个 track 最多上报一次

`maybeLogPlaybackHardening()` 仅在发现 partial 或 full AppOp 不允许时尝试上报。`mPlaybackHardeningLogged.exchange(true, std::memory_order_acq_rel)` 让同一个 track 只发送一次 playback hardening 事件。

事件经 `IAudioManagerNative` 的 oneway 方法回到 `AudioService`。Java 侧先确认调用 UID 是 `AUDIOSERVER_UID`，再更新 counter、hardening event log 和 `AUDIO_HARDENING_REPORTED` atom。因此“每次创建 track 都同步写 metrics”并不符合调用条件。

源码锚点：

- [`Tracks.cpp`](https://cs.android.com/android/platform/superproject/+/android-17.0.0_r1:frameworks/av/services/audioflinger/Tracks.cpp)
- [`IAfTrack.h`](https://cs.android.com/android/platform/superproject/+/android-17.0.0_r1:frameworks/av/services/audioflinger/IAfTrack.h)

## Audio focus：hardening 在前，焦点仲裁在后

hardening 允许请求后，`MediaFocusControl.requestAudioFocus()` 才处理焦点所有者。普通模式中，`mFocusStack` 的尾部是当前栈顶；新请求会向现有 requester 传播相应 loss，再把新 requester 压栈。栈顶退出时，系统可通知下一项重新获得 `AUDIOFOCUS_GAIN`。

这还不是 Android 17 焦点模型的全部。当前实现同时支持：

- external focus policy；
- multi-audio-focus list；
- delayed focus；
- locked focus owner；
- focus isolation；
- client Binder death 与最大栈深限制。

`sendFocusLossAndUpdate()` 的注释说明它服务于 `AudioPolicy.sendFocusLossAndUpdate()`：当外部 policy 指定的 loser 位于栈顶时，移除它并恢复下一项。源码没有把这个方法限定为“蓝牙设备切换恢复”。设备路由与 audio focus 可能在同一用户操作中变化，但两套状态需要分别验证。

源码锚点：[`MediaFocusControl.java`](https://cs.android.com/android/platform/superproject/+/android-17.0.0_r1:frameworks/base/services/core/java/com/android/server/audio/MediaFocusControl.java)。

## Hardening 的 shell 调试

下面的命令用于在测试设备上切换 override，并查看 AudioService 保存的 hardening 事件：

```sh
adb shell cmd audio set-hardening enable
adb shell cmd audio set-hardening disable
adb shell cmd audio set-hardening throw
adb shell cmd audio clear-hardening

adb shell dumpsys audio | sed -n '/Hardening enforcement/,+30p'
```

`set-hardening default` 也被 parser 接受，`clear-hardening` 会恢复 `HARDENING_DEFAULT`。这些命令改变设备全局音频行为，`throw` 还可能让受限的 Java 控制 API 抛异常；只应在测试设备或隔离用例中使用，并在结束后执行 `clear-hardening`。

`THROW` 需要额外说明：Java 的音量/focus hardening 在遇到受限 AppOp 后会抛 `IllegalStateException`；AudioFlinger 的 `getHardeningDecision()` 则把 `THROW` 与 `ENABLE` 一并映射到 `FULL`。当前 native 代码不会让 `AudioTrack.write()` 因这个 override 自动抛出同一种异常。

源码锚点：[`AudioManagerShellCommand.java`](https://cs.android.com/android/platform/superproject/+/android-17.0.0_r1:frameworks/base/services/core/java/com/android/server/audio/AudioManagerShellCommand.java)。

## LE Audio：suspend 时管理 background scan

`LeAudioService` 的 background scan 用 CAP targeted-announcement service data 过滤器，scan mode 为 `SCAN_MODE_BALANCED`，PHY 为 LE 1M。注册、启动、停止都交给 `ScanController` 的 scan thread。

下面的代码用于确认 suspend/resume 对 scanner 的直接动作：

```java
public void setSystemSuspended(boolean suspended) {
    mSystemSuspended = suspended;
    if (suspended) {
        mScanCallback.stopBackgroundScan();
    } else if (isScannerNeeded()) {
        mScanCallback.startBackgroundScan();
    }
}
```

进入 suspend 时，服务把停止并注销当前 scanner 的工作投递到 scan thread；恢复时只有 `isScannerNeeded()` 为 true 才重启。`stopBackgroundScan()` 本身不是同步等待硬件扫描停止完成的屏障，因此不应描述成调用返回前硬件扫描已经同步停止。

`isScannerNeeded()` 还检查：

- 是否已有 device descriptor，Bluetooth 是否启用；
- 是否存在禁用 auto-active mode 的 group；
- LE Audio 设备是否已全部连接；
- `mSystemSuspended`。

代码先处理 auto-active mode 的特殊分支，再检查 suspend。因而更准确的结论是“suspend 入口主动停止当前 background scan”，而非“任何 suspended 状态下所有路径都不可能请求 scanner”。

停止扫描可以减少这一路扫描工作，但节省多少能量取决于 controller offload、scan 参数、广告密度、固件和 suspend residency。AOSP Java 代码无法给出固定百分比，也不能单独证明停止前每次扫描都会唤醒 AP。

源码锚点：[`LeAudioService.setSystemSuspended()`](https://cs.android.com/android/platform/superproject/+/android-17.0.0_r1:packages/modules/Bluetooth/android/app/src/com/android/bluetooth/le_audio/LeAudioService.java)。

## Active device 与 HFP handover

`setActiveDevice(device)` 先要求设备处于 `STATE_CONNECTED`。启用 dual-mode audio 时，还要求该设备支持的 classic audio profiles 已处于 active，最后才调用 `setActiveGroupWithDevice()`。

HFP handover 是一个范围更窄的兼容流程，用于无法同时维持 SCO 和 CIS 的 controller：

1. `setInactiveForHfpHandover()` 记录 HFP device 和当前暴露的 LE Audio device，再移除 active LE group 以拆除 CIS；
2. group idle 后，`handleGroupIdleDuringCall()` 激活 HFP device 或连接 SCO；
3. 通话 handover 结束后，`setActiveAfterHfpHandover()` 尝试恢复之前记录的 LE Audio device。

这不是所有路由失败都会触发的“通用 HFP fallback”。恢复仍调用 `setActiveDevice()`，因此之前记录的设备必须继续满足连接与 dual-mode 条件。

## LC3 与 ADSP：匹配的是 offload capability

CodecManager 默认 `CodecLocation::HOST`。只有以下条件满足时，构造函数才把位置设为 `ADSP`：

1. `ro.bluetooth.leaudio_offload.supported=true`；
2. `persist.bluetooth.leaudio_offload.disabled` 未禁用；
3. Bluetooth Audio HAL 通过 `SupportsLeAudioHardwareOffload()` 报告支持。

随后 `UpdateOffloadCapability()` 读取 HAL 的 offload capabilities，并将系统侧软件配置、offload preference 与 ADSP 配置逐项匹配。下面把 `IsLc3ConfigMatched()` 中的四个相等条件等价缩减，用于确认 LC3 的匹配维度：

```cpp
return adsp_lc3_config.sampling_frequency == target_lc3_config.sampling_frequency
        && adsp_lc3_config.frame_duration == target_lc3_config.frame_duration
        && adsp_config.GetChannelCountPerIsoStream()
                == target_config.GetChannelCountPerIsoStream()
        && adsp_lc3_config.octets_per_codec_frame
                == target_lc3_config.octets_per_codec_frame;
```

采样率、帧时长、每条 ISO stream 的通道数以及每个 codec frame 的字节数都相等，才认为这组 LC3 配置可由已声明的 ADSP capability 支持。外层还会检查 ASE 数量、方向和 codec preference，因此 `IsLc3ConfigMatched()` 不是单独决定 codec location 的开关。

HOST 路径表示 codec 工作留在 host-side Bluetooth/audio pipeline，不等于交给应用进程解码。ADSP 模式下，当前 `GetLocalCodecConfigurations()` 还有一条明确 TODO：缺少 offload 配置时，需要一种切换到 software session 的机制。因此不能写成“任意字段不匹配就自动回退应用态解码”。

源码锚点：[`codec_manager.cc`](https://cs.android.com/android/platform/superproject/+/android-17.0.0_r1:packages/modules/Bluetooth/system/bta/le_audio/codec_manager.cc)。

## 如何验证功耗与时序

阅读属性和 dumpsys 只能确认配置。下面的命令用于收集 hardening、LE Audio offload 与服务状态的起点信息：

```sh
adb shell getprop ro.bluetooth.leaudio_offload.supported
adb shell getprop persist.bluetooth.leaudio_offload.disabled
adb shell dumpsys audio
adb shell dumpsys bluetooth_manager
```

这些输出可以确认 override、hardening log、焦点状态以及 Bluetooth 服务配置，但不能直接给出能量收益。评估 background scan 或 LC3 offload 时，还要固定设备、耳机、codec 配置、音量、射频环境、屏幕状态和温度，并对照以下事件：

- `LeAudioService` 的 scan start/stop 与 system suspend/resume；
- controller/HCI 活动和 AP wakeup；
- CPU time、suspend residency 与电池电流；
- Audio HAL/CodecManager 报告的 HOST 或 ADSP 路径；
- 路由切换期间的 SCO、CIS、focus 和 active device 状态。

至少比较多轮相同 workload 的 host/offload 或 scan-on/scan-off 样本，才能给出延迟、CPU 占用和能耗结论。AOSP 中的 40 ms callback delay 不能拿来代替端到端音频性能测量。

## 常见误区

| 说法 | Android 17 源码给出的边界 |
|---|---|
| Java 和 C++ 对同一个音频事件重复判定 | Java 管控制 API，AudioFlinger 管 playback track；只共享 override 和部分政策输入 |
| FULL 表示系统把音量设为 0 | FULL 表示使用 full control AppOp 作为 enforcement 门槛；具体动作取决于调用面 |
| hardening 通过后一定进入 `mFocusStack` | 还可能交给 external policy、multi-focus、delayed focus 或 isolation |
| `sendFocusLossAndUpdate()` 专供蓝牙设备切换 | 它是 AudioPolicy 可调用的焦点栈更新接口，源码没有限定蓝牙场景 |
| suspend 后 LE scanner 永远不可能再被请求 | suspend 入口会停止当前 scanner；`isScannerNeeded()` 仍有顺序更靠前的 auto-active 特殊分支 |
| `IsLc3ConfigMatched()` 成功就一定启用硬件 offload | 属性、HAL capability、preference、ASE 和整组配置都要满足 |
| LC3 不匹配就由应用进程解码 | HOST 是系统侧 host codec 路径；当前 ADSP 路径甚至标有 software-session fallback TODO |
| 40 ms 是 AudioTrack 创建固定开销 | 它是 Offload/MMAP permission callback 的延迟广播参数 |

## Android 17 锚点小结

Android 17 的 audio hardening 将“控制 API 是否允许”和“playback track 是否静音”放在各自合适的执行位置，并用 AppOps、兼容规则与共享 override 保持政策方向一致。LE Audio 的扫描、active group、HFP/CIS handover 和 codec offload 则由 Bluetooth module 管理。

排查“后台音频没声音”时，先看 hardening/AppOps 与 focus；排查“LE Audio 功耗高”时，再看 scan、host/ADSP codec location、controller activity 和 suspend residency。先确认是哪套机制在起作用，后续 trace 才有可解释性。
