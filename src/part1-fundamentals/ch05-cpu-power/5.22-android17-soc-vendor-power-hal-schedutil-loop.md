# 5.22 Android 17 IPower HAL、schedutil、cpuidle 与 Energy Model 的边界

<!-- outline-start -->
## 要点

### 🔹 IPower AIDL 接口架构
Android 17 的 5 层协作关系为：Framework → PowerManagerService → IPower AIDL → vendor native 实现 → 内核 schedutil。AOSP 只强制稳定接口，不强制厂商内部采用同一种控制算法。

### 🔹 Mode 与 Boost 枚举设计
16 种长生命周期 Mode 与 6 种高频短脉冲 Boost 的精细化控制机制，包括跨厂商兼容性设计。

### 🔹 Schedutil Governor 内核守门
`sugov_should_update_freq()` 与 `rate_limit_us` 守门机制，防止高频 Hint 导致底层 DVFS 抖动。

### 🔹 跨厂商实现差异
Qualcomm RPMh/PDC、MediaTek mtlp/dvfsrc、Samsung ASV/TMU 的不同实现路径与性能影响。

### 🔹 性能影响与延迟分析
可量化指标包括 `setMode` 端到端延迟、`rate_limit_us` 的限频效果和 Energy Model 注册开销。

## 扩展

### 🔸 Energy Model 注册与反查
Android 17 新增 `getCpuHeadroom()` / `getGpuHeadroom()` API，基于 PD 模型的反查机制实现。

### 🔸 Menu cpuidle Governor
12 个时长分桶与标准差检测窗口的深度 C-state 控制机制，跨厂商 target_residency 差异。

## 先建立正确的控制关系

Android 17 没有定义一条从 `IPower` 直达 `schedutil` 的通用反馈通路。平台上同时存在几套职责不同的机制：

- `Mode` 和 `Boost` 向 Power HAL 表达场景或短时资源需求。厂商可以调整 CPU、GPU、内存、idle 等策略，也可以忽略某个 hint。
- ADPF Hint Session 报告一组线程的目标时长和实际工作时长，让 Power HAL 根据设备实现调整资源。
- `schedutil` 根据调度器利用率、capacity、uclamp 等输入选择 cpufreq 目标频率。
- EAS 在任务放置时使用 Energy Model 估算候选 CPU 的能耗。
- cpuidle governor 从 cpuidle driver 提供的 idle states 中选择本次空闲状态。
- CPU/GPU headroom 是 Power HAL 对历史负载所做的可用余量估计；AIDL 没有规定它必须由 Energy Model 计算。

下面这幅关系图用于区分“标准接口”和“厂商可以采用的实现动作”：

```text
Framework / native clients
  ├─ Mode、Boost ───────────────┐
  ├─ ADPF Hint Session / FMQ ───┼─> PowerHalController ─> Power HAL
  └─ CompositionData ───────────┘                         │
                                                         ├─> 厂商策略，可调整
                                                         │   uclamp / cpufreq / devfreq /
                                                         │   cpuidle 约束 / 内存带宽等
                                                         └─> Headroom 查询结果

scheduler utilization ─> schedutil ─> cpufreq driver ─> CPU DVFS
task placement ─────────> EAS + Energy Model
CPU idle entry ─────────> cpuidle governor ─> cpuidle driver state
```

图中只有实线文字所示的接口关系可以从 AOSP 合同或实现直接确认。Power HAL 右侧采用哪种控制手段，由设备实现决定；不能从 `IPower.aidl` 推导出某款 SoC 的固件消息、sysfs 写入或固定延迟。

## Framework 到 Power HAL：调用没有 200 ms 聚合

`PowerManagerService` 中的 Mode/Boost 路径很短。下面的源码节选用于确认调用是否经过 `mDirty` 或定时聚合：

```java
private void setPowerBoostInternal(int boost, int durationMs) {
    // Maybe filter the event.
    mNativeWrapper.nativeSetPowerBoost(boost, durationMs);
}

private boolean setPowerModeInternal(int mode, boolean enabled) {
    // Maybe filter the event.
    if (mode == Mode.LAUNCH && enabled && mBatterySaverStateMachine != null
            && mBatterySaverStateMachine.getBatterySaverController()
                    .isLaunchBoostDisabled()) {
        return false;
    }
    return mNativeWrapper.nativeSetPowerMode(mode, enabled);
}
```

这两段代码直接进入 native wrapper。`LAUNCH` 有省电状态过滤，其余行为由后续 Power HAL 路径处理。源码中没有 `DIRTY_BOOST`、`DIRTY_MODE` 或 `POLL_DELAY_DEFAULT=200ms` 的这套聚合设计。

JNI 持有一个 `PowerHalController`。Controller 先尝试 AIDL；AIDL 不可用时，当前 Framework 实现仍依次尝试 HIDL 1.3、1.2、1.1 和 1.0 wrapper。因此：

1. Android 17 的冻结 Power AIDL 是 V7，设备开发应以该稳定接口为当前基准。
2. 仅凭 Framework 代码不能写成“所有设备运行时只可能走 AIDL”，因为兼容回退仍在。
3. `setMode()` 和 `setBoost()` 到达 vendor HAL 后如何影响硬件，不属于 AIDL 规定的固定调用序列。

## Mode 与 Boost：合同表达意图，不保证硬件动作

Android 17 的 `Mode.aidl` 有 19 个枚举值，`Boost.aidl` 有 6 个枚举值。这是 `android-17.0.0_r1` 的当前快照，不应据此反推各枚举在哪个 Android 版本首次出现。

### Mode 是可独立启停的场景状态

`setMode(type, enabled)` 表示启用或停用某种 mode。AIDL 没有“同一时刻最多一个 Mode”的限制；例如交互状态、低功耗状态和具体业务场景在合同层是不同维度。平台是否支持某个值，要先看 `isModeSupported(type)` 或 V7 的 `SupportInfo.modes` 位图。

当前 19 个值按用途可分为：

| 类别 | Mode |
|---|---|
| 系统状态 | `INTERACTIVE`、`DEVICE_IDLE`、`DISPLAY_INACTIVE`、`LOW_POWER` |
| 性能与调试 | `SUSTAINED_PERFORMANCE`、`FIXED_PERFORMANCE`、`LAUNCH`、`EXPENSIVE_RENDERING` |
| 显示与交互形态 | `DOUBLE_TAP_TO_WAKE`、`VR`、`DISPLAY_CHANGE`、`AUTOMOTIVE_PROJECTION` |
| 音视频与相机 | `AUDIO_STREAMING_LOW_LATENCY`、四种 `CAMERA_STREAMING_*` |
| 游戏 | `GAME`、`GAME_LOADING` |

`FIXED_PERFORMANCE` 的目标是给 profiling 提供可重复的性能区间，仍可能受到 thermal throttling。`SUSTAINED_PERFORMANCE` 更偏向长时间稳定性。两者不等同于“锁最高频”。

### Boost 是带时长提示的短时需求

当前 6 个值是 `INTERACTION`、`DISPLAY_UPDATE_IMMINENT`、`ML_ACC`、`AUDIO_LAUNCH`、`CAMERA_LAUNCH` 和 `CAMERA_SHOT`。AIDL 对 `durationMs` 的解释为：

- 正数：调用方已知的预计持续时间；
- `0`：预计时间未知，由平台选择合适时长；
- 负数：取消之前的同类 boost。

`ML_ACC` 以及三个音频/相机 boost 在枚举注释中标明当前 Framework 不发送，OEM 可以自行使用。即使收到 boost，平台也可以忽略。诸如“触摸必然同时拉高 CPU 和 GPU”“拍照必然拉满 ISP 电源域”都超出了接口保证。

### V7 的能力查询

`getSupportInfo()` 返回一个 `SupportInfo` parcelable，而非一个枚举。它一次给出：

- 是否使用 Hint Session；
- Boost、Mode、SessionHint、SessionMode、SessionTag 的支持位图；
- composition data 的支持状态与 batching 配置；
- CPU/GPU headroom 的支持状态、最小查询间隔、计算窗口边界和 CPU TID 数上限。

单个 `isModeSupported()`、`isBoostSupported()` 仍然存在。调用方不应因为枚举出现在 AIDL 中，就假定当前设备实现了对应优化。

## ADPF、composition data 与 headroom 各自解决什么问题

这三组 API 都位于 Power AIDL，却不能合并理解成同一个控制器。

### Hint Session

Hint Session 关联一组具有周期性、相互关联工作的线程。调用方提供目标工作时长，并持续报告实际工作时长。`createHintSessionWithConfig()` 还能返回 session 配置；`getSessionChannel()` 可为进程建立 FMQ 通道，减少高频报告的 Binder 成本。

FMQ 负责传输 Hint Session 消息。它不会直接调用 `sugov_should_update_freq()`，也不会把 Power HAL 的 preferred update rate 改写成 schedutil 的 `rate_limit_us`。厂商 HAL 如何把 session 信息转换为 uclamp、频率、带宽或其他请求，属于设备实现。

### Composition data

`sendCompositionData()` 向 Power HAL 提供已关联 surface 的 FPS 与 frame timing 数据，用于补充和校验 Hint Session 的实际时长报告。`sendCompositionUpdate()` 传递 display 或 FrameProducer 生命周期、帧率变化等重要更新。接口注释没有把它们定义成 headroom 的反向查询输入。

### CPU/GPU headroom

`getCpuHeadroom()` 和 `getGpuHeadroom()` 返回基于历史信息估算的可用余量。Android 17 的结果结构很小：

```aidl
union CpuHeadroomResult {
    float globalHeadroom;
}

union GpuHeadroomResult {
    float globalHeadroom;
}
```

结果为 `NaN` 或 `[0, 100]`。`NaN` 表示当前数据不足或方差过大，调用方此时不应据此调参；`0` 表示计算区间内没有剩余资源。结构中没有 `criticalityLevel`、`thermalHeadroom` 或 `powerBudgetRemaining` 字段。

查询频率也不是 Framework 固定的 100 ms。`SupportInfo.HeadroomSupportInfo` 由设备报告 CPU/GPU 各自的最小查询间隔。合同给出的默认计算窗口下界是 50 ms、上界是 10000 ms，并要求实现上报可支持边界。AOSP [reference `Power.cpp`](https://cs.android.com/android/platform/superproject/+/android-17.0.0_r1:hardware/interfaces/power/aidl/default/Power.cpp) 对两种 headroom 查询都返回 `EX_UNSUPPORTED_OPERATION`，说明接口存在不代表 reference HAL 已提供算法。

AIDL 没有要求 headroom 必须读取内核 Energy Model、Power Domain 或某个厂商电源控制器。若文档需要说明具体计算方法，必须引用目标设备 HAL 的公开实现或实测证据。

## schedutil：根据调度器利用率选频

`schedutil` 是一个 cpufreq governor。设备是否使用它取决于内核配置、cpufreq policy 和运行时 governor 选择，不能写成 Android 17 所有 SoC 唯一允许的 governor。

### 更新频率的条件

下面的缩减代码用于说明 `sugov_should_update_freq()` 的检查顺序：

```c
if (!cpufreq_this_cpu_can_update(policy))
    return false;

if (sg_policy->limits_changed) {
    sg_policy->limits_changed = false;
    sg_policy->need_freq_update = true;
    return true;
}

if (sg_policy->need_freq_update)
    return true;

return time - sg_policy->last_freq_update_time
        >= sg_policy->freq_update_delay_ns;
```

它先判断当前 CPU 能否更新该 policy，再处理 policy limits 改变和强制更新，最终应用更新间隔。这个间隔只限制 schedutil 提交新频率的节奏，不能充当所有 Power HAL hint 的统一节流器。

Android 17 的锚点内核没有 `DEF_RATE_LIMIT_US 10000`。policy 初始化时使用：

```c
tunables->rate_limit_us = cpufreq_policy_transition_delay_us(policy);
```

因此默认值来自 cpufreq policy 的 transition delay；用户空间还可以通过 schedutil tunable 修改它。固定写成 10 ms 会掩盖不同 cpufreq driver 和设备配置的差异。

### 利用率、参考频率与提交路径

schedutil 从 scheduler 的 update-util 路径取得利用率，经过 `effective_cpu_util()`、uclamp 与 capacity 等处理后映射目标频率。`get_capacity_ref_freq()` 会读取 `arch_scale_freq_ref(policy->cpu)`；若架构没有提供，再按 frequency-invariance 状态采用 max 或当前频率的回退值。

这里没有读取 `struct em_perf_domain`。Energy Model 与 schedutil 都会接触“capacity”概念，但用途不同：

- schedutil 用 utilization/capacity 比例决定 cpufreq 请求；
- EAS 用 Energy Model 比较任务放到不同 CPU 后的估算能耗。

目标频率算出后，支持 fast switch 的 driver 走 `cpufreq_driver_fast_switch()`；否则通过 irq work 与 governor kthread 延后执行。频率何时生效还受 driver、firmware、policy limits、thermal 和硬件 DVFS 机制影响。

源码锚点：[`kernel/sched/cpufreq_schedutil.c`](https://android.googlesource.com/kernel/common/+/refs/tags/android17-6.18-2026-06_r6/kernel/sched/cpufreq_schedutil.c)。

## Energy Model：服务于能耗估算与任务放置

Android 17 的锚点内核仍提供 `em_dev_register_perf_domain()`。驱动或平台代码通过 callback 注册 performance domain；每个 `em_perf_state` 包含 `performance`、`frequency`、`power`、`cost` 和 flags。运行期也支持通过 `em_dev_update_perf_domain()` 更新表。

EAS 的 `find_energy_efficient_cpu()` 会为候选 CPU 计算任务放置前后的 energy delta。它最终在 `compute_energy()` 中调用：

```c
energy = em_cpu_energy(pd->em_pd, max_util, busy_time, eenv->cpu_cap);
```

这段调用说明 Energy Model 直接参与的是调度器候选 CPU 的能耗比较。schedutil 在 governor 初始化和退出时调用 `em_rebuild_sched_domains()`，让调度域与 governor 状态保持一致；这也不等于 schedutil 每次选频都会反查 EM 表。

当前源码中没有 `em_adapt_cpu`，也没有“Android 17 从 `em_register` 改为 `em_adapt_cpu`”的迁移。EM 注册时间、单次计算耗时以及 CPU 占比都依赖设备、表规模和负载，缺少同一设备上的 trace 或 benchmark 时不应填写固定区间。

## cpuidle 与 cpufreq 是两条控制轴

cpufreq 决定 CPU 运行时采用的性能档位，cpuidle 决定 CPU 无可运行任务时进入哪个 idle state。Power HAL 可以在厂商实现中影响两者的约束，但 schedutil 不负责挑选 C-state。

### menu 的预测输入

下面的常量用于校正原文的分桶数量和时间单位：

```c
#define BUCKETS 6
#define INTERVAL_SHIFT 3
#define INTERVALS (1UL << INTERVAL_SHIFT)
#define RESOLUTION 1024
#define DECAY 8
#define MAX_INTERESTING (50000 * NSEC_PER_USEC)
```

`BUCKETS` 是 6，保存六组按预计 idle 时长数量级索引的 correction factor；`INTERVALS` 是 8，重复间隔检测器记录最近八次 idle 时长。`50000 * NSEC_PER_USEC` 等于 50,000 µs，也就是 50 ms。

`menu.c` 顶部注释只列出两个独立决策因素：

1. energy break-even point，由 cpuidle driver 的 `target_residency` 表达；
2. latency tolerance，来自 PM QoS。

menu 结合下一定时器、历史 correction factor 和重复间隔检测预测 idle 时长，再在 latency 约束内选择 state。exit latency、target residency 和实际低功耗动作来自 cpuidle driver/firmware，不由 menu 为某个 SoC 固定。

### 不要把 menu 写成所有设备的固定选择

锚点内核同时包含 `menu`、`teo`、`ladder`、`haltpoll` 等 governor。当前源码中 menu 的 rating 是 20，TEO 是 19；可用项仍受内核配置影响，运行时还可能显式选择 governor。分析设备功耗前，应先读取该机实际配置。

源码锚点：

- [`drivers/cpuidle/governors/menu.c`](https://android.googlesource.com/kernel/common/+/refs/tags/android17-6.18-2026-06_r6/drivers/cpuidle/governors/menu.c)
- [`drivers/cpuidle/governors/teo.c`](https://android.googlesource.com/kernel/common/+/refs/tags/android17-6.18-2026-06_r6/drivers/cpuidle/governors/teo.c)

## 厂商差异该怎样写才严谨

Qualcomm、MediaTek、Samsung 的量产设备可能使用不同的电源控制器、固件协议、cpufreq/devfreq driver、idle state 和 thermal 策略。但 `IPower.aidl` 只能证明厂商 HAL 接收了哪些标准化意图，不能证明某个枚举一定映射到 RPMh、DVFSRC、ASV/TMU 或特定电源域。

对具体设备下结论，至少需要以下一类证据：

- 对应 BSP 内核或公开 vendor HAL 源码；
- 设备树、driver binding、sysfs/debugfs 节点与 trace event；
- Perfetto/ftrace 中 hint、scheduler、frequency、idle、thermal 的时间关系；
- 同一 build、温度和 workload 下的可重复测量。

若只有 AOSP 接口，合适的表述是“厂商可以调整 CPU/GPU/内存频率或 idle 约束”。库名、固件函数名、OPP 数量以及几十微秒级延迟需要设备证据，不应写成品牌通用结论。

## 在设备上验证

第一组命令用于确认当前 governor、schedutil 参数和 cpuidle state。不同内核可能裁剪节点，所以命令逐项判断文件是否存在：

```sh
adb shell '
for policy in /sys/devices/system/cpu/cpufreq/policy*; do
  echo "== $policy =="
  cat "$policy/scaling_governor" 2>/dev/null
  cat "$policy/scaling_available_governors" 2>/dev/null
  cat "$policy/schedutil/rate_limit_us" 2>/dev/null
done

for node in \
  /sys/devices/system/cpu/cpuidle/current_governor_ro \
  /sys/devices/system/cpu/cpuidle/current_governor \
  /sys/devices/system/cpu/cpuidle/available_governors; do
  [ -r "$node" ] && { echo "== $node =="; cat "$node"; }
done

for state in /sys/devices/system/cpu/cpu0/cpuidle/state*; do
  echo "== $state =="
  for field in name latency target_residency usage time; do
    [ -r "$state/$field" ] && printf "%s=" "$field" && cat "$state/$field"
  done
done
'
```

输出先回答三个基础问题：设备是否运行 schedutil、它的实际 `rate_limit_us` 是多少、CPU0 暴露了哪些 idle states。无法读取某个节点时，应检查权限、内核配置和厂商是否改名，不能用另一款设备的默认值补齐。

第二组命令用于盘点当前内核能提供哪些 trace 证据：

```sh
adb shell '
tracefs=/sys/kernel/tracing
[ -r "$tracefs/available_events" ] || tracefs=/sys/kernel/debug/tracing
grep -E "sugov|cpu_frequency|cpu_idle|thermal" \
  "$tracefs/available_events" 2>/dev/null
'
```

根据输出选择 Perfetto/ftrace 事件，再将 `setMode`/`setBoost`、scheduler utilization、CPU frequency、CPU idle 和 thermal 放在同一时间轴观察。延迟要从发起点、HAL 接收点、kernel request 和硬件状态变化分别量取；只看一次 sysfs 快照无法证明因果关系。

## 常见误区

| 说法 | Android 17 源码给出的边界 |
|---|---|
| Power HAL hint 会直接调用 schedutil | 标准接口没有这条固定路径；vendor HAL 决定采用何种控制手段 |
| Mode 同时只能启用一个 | AIDL 按 `type + enabled` 独立启停，没有互斥合同 |
| schedutil 的默认限速固定为 10 ms | 默认值来自 `cpufreq_policy_transition_delay_us(policy)` |
| schedutil 从 Energy Model 读取参考频率 | 它优先读取 `arch_scale_freq_ref()`；EAS 才直接用 EM 做能耗比较 |
| FMQ 报告速率就是 schedutil 更新速率 | 两者属于不同组件，没有共享 tunable 的标准定义 |
| headroom 一定由 EM/PD 反查得到 | AIDL 只规定结果、参数与支持信息，没有规定算法 |
| menu 有 12 个 correction buckets | 当前源码是 6 个 buckets、8 个历史 intervals |
| menu 适用于所有 Android SoC | 实际 governor 受内核配置和运行时选择影响 |

## Android 17 锚点小结

`android-17.0.0_r1` 中 Power AIDL 已冻结到 V7，提供 19 个 Mode、6 个 Boost、Hint Session/FMQ、`SupportInfo`、CPU/GPU headroom 以及 composition data 接口。`android17-6.18-2026-06_r6` 中，schedutil、Energy Model 和 cpuidle governor 各自保有清楚的职责边界。

分析 SoC 级电池优化时，先确认请求属于场景提示、任务放置、运行频率、空闲状态还是观测接口，再追到目标设备的 vendor HAL、driver 和 firmware。这样才能把 AOSP 合同、内核机制与厂商策略分开验证。
