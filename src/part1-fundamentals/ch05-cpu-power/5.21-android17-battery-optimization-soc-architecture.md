Android 17 没有新增一套通用的“SoC 厂商电池优化框架”。这一版本沿用并扩展稳定 AIDL Power HAL，平台当前冻结版本为 V7；Framework 仍保留对旧 HIDL Power HAL 的兼容加载。这里的 V7 是 HAL 接口版本，不能与 Android API 37 混为一谈。

设备上的功耗策略也不一定由芯片厂商独立完成。SoC 厂商、整机厂、Power HAL 供应方和内核维护方可能属于不同团队。AOSP 只定义接口和 Framework 行为，不规定某一家应当怎样实现 CPU、GPU、内存、总线或低功耗状态的控制。

本章以 Android 17 / API 37 / `android-17.0.0_r1` 为平台基线，以 Android common kernel `android17-6.18-2026-06_r6` 为内核基线，回答三个问题：

- Framework 通过 `IPower` 向设备表达了什么；
- `IPowerStats` 能观测什么，以及它为何不等于控制策略；
- Linux schedutil 怎样根据调度负载选频，厂商策略又可以在哪里介入。

## 先拆开四个职责

下面的示意图用于标出各层的输入和责任：

```text
Framework 策略与系统状态
  ├─ Mode / Boost ──> PowerManagerService
  │                     └─ JNI -> PowerHalController -> IPower/default
  ├─ ADPF session ──> performance_hint service ────────┘
  └─ Battery Saver / Device Idle / display state / thermal policy

设备 Power HAL 实现
  └─ 将提示映射为设备可用的 scheduler、CPUFreq、GPU、内存、总线或 idle 控制

Linux kernel
  └─ scheduler + schedutil + cpufreq driver + thermal/cooling + idle

IPowerStats
  └─ 报告能量计数和状态驻留数据，供统计与归因使用
```

图中的箭头只表示接口调用关系。AIDL 没有规定 `Mode.LAUNCH` 必须写哪个 sysfs 节点，也没有要求 `IPowerStats` 的读数自动改变 schedutil 参数。设备可以在自己的 Power HAL 和内核中建立控制策略，但那属于具体产品实现。

| 层次 | AOSP 定义的内容 | 不能仅凭 AOSP 推断的内容 |
|---|---|---|
| Framework | 何时发送部分 Mode、Boost 和 ADPF 信息 | 一次提示能带来多少性能或节省多少电 |
| `IPower` | 提示类型、查询能力、HintSession 和 headroom 契约 | 提示到 CPU/GPU/DDR 参数的固定映射 |
| `IPowerStats` | 能量、能耗归因、状态驻留的数据格式 | 设备一定具备哪些 rail、精度和采样频率 |
| kernel | 调度、选频、频率约束和低功耗机制 | 某款量产机采用哪些私有策略 |

## Framework 到 Power HAL 的调用路径

`PowerManagerService` 的 `setPowerModeInternal()` 很短，但它说明了一个重要边界。下面的源码用于观察 `Mode.LAUNCH` 送往 HAL 前的 Framework 筛选：

```java
private boolean setPowerModeInternal(int mode, boolean enabled) {
    if (mode == Mode.LAUNCH && enabled && mBatterySaverStateMachine != null
            && mBatterySaverStateMachine.getBatterySaverController().isLaunchBoostDisabled()) {
        return false;
    }
    return mNativeWrapper.nativeSetPowerMode(mode, enabled);
}
```

当 Battery Saver 策略报告 launch boost 已禁用时，Framework 不会把“启用 `Mode.LAUNCH`”送进 HAL，并返回 `false`。这段代码没有给出 0–50 ms 的固定加速窗口，也没有承诺省电模式始终拦截所有性能提示。历史命名中虽有 “launch boost”，AIDL 类型仍是有启停状态的 `Mode.LAUNCH`。

后续路径可以在源码中逐段确认：

1. JNI 的 `nativeSetPowerMode()` 和 `nativeSetPowerBoost()` 调用 `PowerHalController`；
2. `PowerHalLoader` 先查找已在 VINTF 声明的 `android.hardware.power.IPower/default`；
3. AIDL 服务不存在时，加载器仍会尝试 HIDL 1.0–1.3；
4. `PowerHalController` 负责连接、能力缓存、失败后重连，不负责制定设备调频策略；
5. 量产设备的 HAL 收到调用后，才按产品实现处理提示。

普通应用不能把 Binder 当作公开性能接口直接调用。`PowerManagerService` 暴露的相关系统入口受 `DEVICE_POWER` 等权限约束。应用侧持续性能反馈应使用 `PerformanceHintManager` / ADPF，详见 5.9 和 5.19。

## Mode、Boost 与 HintSession

这三类输入的生命周期不同，排查时要先确认调用类型。

### Mode：带启停状态的场景

`setMode(type, enabled)` 表示某种状态进入或退出。Android 17 的 `Mode.aidl` 包含 `LOW_POWER`、`SUSTAINED_PERFORMANCE`、`LAUNCH`、`INTERACTIVE`、`DEVICE_IDLE`、`GAME`、`DISPLAY_CHANGE` 等枚举。

接口注释允许平台忽略某个 Mode。调用方应先通过 `isModeSupported()` 或 V6 起的 `getSupportInfo()` 理解设备声明的能力；即使设备返回支持，也只能说明 HAL 接受该语义，不能推导频率值。

### Boost：有时长的短期提示

`setBoost(type, durationMs)` 用于负载即将上升、内核 governor 可能尚未响应的阶段。Android 17 的 `Boost.aidl` 包含 `INTERACTION`、`DISPLAY_UPDATE_IMMINENT`、`ML_ACC`、`AUDIO_LAUNCH`、`CAMERA_LAUNCH` 和 `CAMERA_SHOT`，没有 `LAUNCH` 这一项。

`durationMs` 的契约是：

- 正数：调用方知道的预期时长；
- `0`：预期时长未知，由平台选择合适的时限；
- 负数：取消此前的同类 Boost。

它仍是提示。设备可以忽略，也可以依据热状态、当前频率和资源余量缩短响应。把 `durationMs` 当作 CPU 必须锁定高频的时间，会让诊断方向偏离接口契约。

### HintSession：周期工作反馈

HintSession 面向一组长期存活、彼此相关的线程。调用方提供 target work duration，并持续报告 actual work duration。Android 17 的接口还包括：

- `createHintSessionWithConfig()`；
- 每进程的 HintSession FMQ channel；
- `getSupportInfo()`；
- CPU/GPU headroom 查询；
- SurfaceFlinger 发来的 composition data 与 update。

这里的 FMQ 服务于 HintSession 高频消息。`IPowerStats.readEnergyMeter()` 是普通 AIDL 方法，与该 FMQ channel 无关。

## 参考 Power HAL 只能说明接口形状

AOSP `power/aidl/default/Power.cpp` 的命名空间是 `impl::example`。它适合演示服务接线和接口兼容，不能代表量产设备策略。

在 Android 17 的参考实现中：

- `setMode()` 与 `setBoost()` 只记日志并返回成功；
- `isModeSupported()` 与 `isBoostSupported()` 对合法枚举返回 `true`；
- `getCpuHeadroom()` 与 `getGpuHeadroom()` 返回 `EX_UNSUPPORTED_OPERATION`；
- `getSupportInfo()` 报告 headroom 和 composition data 不受支持；
- HintSession 使用示例对象和 stub FMQ，没有面向真实硬件的调节逻辑。

因此，“AOSP example 对某个枚举返回支持”不能作为设备产生频率变化的证据。验证量产机时要观察该产品的 VINTF 声明、HAL dump、trace 与内核状态。

## `IPowerStats` 是观测接口

`android.hardware.power.stats.IPowerStats` 与 `android.hardware.power.IPower` 是两个独立的 VINTF AIDL 接口。前者报告统计数据，后者接收性能与功耗提示。

Android 17 的 `IPowerStats` 有三组数据：

| 方法 | 对象 | 关键字段与时间含义 |
|---|---|---|
| `getEnergyConsumed()` | `EnergyConsumer` | `energyUWs`：自开机累计能量；`timestampMs`：`CLOCK_BOOTTIME` |
| `readEnergyMeter()` | `Channel` | `energyUWs`：测量窗口累计能量；另有 `durationMs` 和 `timestampMs` |
| `getStateResidency()` | `PowerEntity` | 各状态的累计驻留时间、进入次数和最近进入时间 |

`energyUWs` 的单位是微瓦秒（μWs），数值上等于微焦耳（μJ），不是微库仑（μC）。从能量换算电荷还需要电压信息，AIDL 结果中没有提供通用电压字段。

`getEnergyConsumed()` 与 `readEnergyMeter()` 返回数组。调用为空 ID 列表时，请求所有可用对象；接口也提醒客户端，某次请求不保证每一个对象都有结果。它们返回累计量，不是瞬时功率。对同一 ID 取两次有效样本时，平均功率可按 `ΔenergyUWs / ΔtimeMs` 计算，结果单位为 mW。

`vendor_available: true` 表示生成的接口库可以被 vendor 模块使用；它不强制每台设备注册这个服务，也不保证每个 rail 都可见。AOSP 的 `FakeEnergyMeter`、`FakeEnergyConsumer` 和 `FakeStateResidencyDataProvider` 属于示例服务组件。产品是否采用、替换或不提供这些能力，要看设备清单与实现。

## schedutil 根据利用率选频

Android common kernel 的 schedutil 是 CPUFreq governor。它从 scheduler 的 utilization、带宽约束和有效性能上下限计算目标频率，再交给 cpufreq driver。代码中没有“读取电池百分比后直接调频”的通用路径。

### 更新限流不是固定 1 ms

在 `android17-6.18-2026-06_r6` 中，`sugov_init()` 这样设置初始值：

```c
tunables->rate_limit_us = cpufreq_policy_transition_delay_us(policy);
```

初始 `rate_limit_us` 取决于当前 cpufreq policy 和 driver 的 transition delay。用户空间还可通过 governor sysfs 属性修改它。某台设备读到 `1000` 只能证明该设备当时的配置，不能写成 Android 17 默认值。

`sugov_should_update_freq()` 通常比较本次时间与 `last_freq_update_time`，达到 `freq_update_delay_ns` 才允许再次选频；policy limits 改变或特定 deadline utilization 情况可以要求立即更新。

### reference frequency 不是电池预测

`get_capacity_ref_freq()` 先调用 `arch_scale_freq_ref(policy->cpu)`，用于取得“频率与 CPU capacity 对应关系所采用的参考频率”。架构代码没有给出该值时，schedutil 会按 frequency invariance 和当前 policy 选择后备值。

这项能力让架构代码表达 CPU capacity 标度，不能据此推导一个 SoC 已实现电池状态预测。

### I/O-wait boost 有严格触发条件

`IOWAIT_BOOST_MIN` 的确等于 `SCHED_CAPACITY_SCALE / 8`。它只在 update flags 带 `SCHED_CPUFREQ_IOWAIT`，也就是任务从 I/O wait 唤醒时启动。连续请求时 boost 逐次翻倍，长时间没有新请求时会衰减或重置。

这套机制处理 I/O 唤醒后的响应速度。它不是 Framework `Boost` 枚举，也不会因电量降低自动变小。

### fast switch 由 driver 能力决定

schedutil 初始化时请求启用 fast switch。policy 支持时可在调度路径调用 `cpufreq_driver_fast_switch()`；不支持时由 irq work 和 `sugov` kthread 延后执行。设备树、cpufreq driver、OPP、thermal/cooling 和 policy min/max 都可能限制最后可用的频率。

## 厂商可以修改哪里

Power HAL 接口允许设备自由选择响应方式。常见实现可能调整：

- scheduler 的 uclamp、任务组或其他厂商扩展；
- CPUFreq policy、CPU/GPU/DDR devfreq 约束；
- interconnect bandwidth、idle latency 和低功耗状态；
- 面向相机、游戏、音频或显示的专用资源控制器；
- HintSession 的线程放置、频率建议和设备级反馈策略。

“可能”很重要。AIDL 没有规定 `Mode.GAME` 必须设置 uclamp，也没有规定 `Boost.INTERACTION` 必须提高哪一个 cluster。设备还要同时服从热约束、功率预算、当前负载和产品配置。

Qualcomm、MediaTek、Samsung 等平台的驱动名或守护进程名，会随 SoC 世代、内核版本和整机配置变化。只依据 AOSP example 无法证明某家量产方案的内部算法，所以本章不列固定的厂商对照表。分析特定设备时，应以该设备公开内核、vendor 源码、VINTF、运行时 trace 和实测为准。

## Battery Saver、thermal 与 schedutil 的关系

这三套机制会在最终频率上相遇，但输入不同：

- Battery Saver 在 Framework 侧修改系统策略，也可以阻止部分 Power HAL 提示；
- Power HAL 接收场景或工作反馈，再按设备能力施加约束；
- schedutil 依据 scheduler utilization 计算请求频率；
- thermal/cooling 与 cpufreq policy limits 可以压低可用上限；
- cpufreq driver 将合法请求转换为硬件支持的 OPP。

所以一次 `Mode.LAUNCH` 没带来频率上升，至少有几种解释：Framework 没有发送、HAL 不支持、HAL 选择忽略、CPU 已在足够高的 OPP、频率被上限限制，或者瓶颈在 CPU 之外。只看一次 Binder 调用无法确定原因。

电池百分比、温度、电压、电流和健康度也要分开。AOSP schedutil 不直接读取电池百分比；设备可能在 vendor policy 中依据电池或电源状态改变约束，但这需要产品源码或运行证据。

## 在目标设备上验证

### 第一步：确认服务与 governor

下面的命令用于建立设备能力快照；不同构建的权限和可见节点可能不同：

```bash
adb shell service list | grep -E 'android.hardware.power|android.hardware.power.stats'
adb shell dumpsys power
adb shell 'for p in /sys/devices/system/cpu/cpufreq/policy*; do
  echo "$p"
  cat "$p/scaling_governor" "$p/scaling_min_freq" "$p/scaling_max_freq" 2>/dev/null
  cat "$p/schedutil/rate_limit_us" 2>/dev/null
done'
```

第一条用于查看已注册的 AIDL 服务，第二条用于保存 Framework 电源状态，最后一组读取各 CPUFreq policy。节点缺失或权限拒绝也属于结果：它说明不能把另一台设备的 governor 配置直接套用。

如果设备走旧 HIDL Power HAL，可再用 `adb shell lshal` 检查服务；Android 17 Framework 中保留 fallback 不代表新设备应继续选择 HIDL。

### 第二步：同时记录请求、约束与结果

一次实验至少记录：

1. build fingerprint、内核 tag、Power HAL AIDL 版本；
2. battery saver、充电、屏幕、thermal status 与环境温度；
3. 相关 Mode、Boost 或 HintSession 的进入、退出与持续时间；
4. `sched_switch`、CPU frequency、CPU idle、thermal 和应用自定义 trace；
5. 任务的 p50/p90/p99 延迟、掉帧、吞吐与能量差值。

频率上升不等于体验改善，频率不变也不等于提示无效。任务可能被迁移到容量不同的 CPU，或者设备调整了 GPU、内存、总线和 idle 状态。结论应同时覆盖业务指标和功耗指标。

### 第三步：用可重复的 A/B 回答因果问题

有效的 A/B 只改变一个待验证因素。例如比较 Battery Saver 开关时，要固定工作负载、亮度、网络、温度起点、充电状态和采样窗口。每组多次运行并报告分位数，避免用单次冷启动解释设备策略。

读取 PowerStats 前后样本时，还要检查：

- ID、名称和测量对象一致；
- 计数器来自同一次开机；
- 时间戳递增且能量差非负；
- 测量窗口覆盖相同业务阶段；
- 设备无法提供某个结果时，不用零值代替缺失。

要比较 SoC 或整机的总能耗，外部电源仪通常比若干内部 rail 相加更可靠；PowerStats 更适合设备内归因和趋势判断。

## 常见误判

| 说法 | Android 17 下的判断 |
|---|---|
| Android 17 新增 SoC 电池优化框架 | 不准确。Android 17 延续稳定 AIDL Power HAL，并在现有接口上演进 |
| `Mode.LAUNCH` 是 0–50 ms 的 Boost | 不准确。它是可启停的 Mode，接口未规定固定时长 |
| `readEnergyMeter()` 通过 FMQ 返回即时功率 | 不准确。它是普通 AIDL 调用，返回累计能量测量 |
| `energyUWs` 是微库仑 | 不准确。单位是微瓦秒，等于微焦耳 |
| `vendor_available` 强制厂商提供 PowerStats | 不准确。它描述构建可见性，不是设备实现要求 |
| schedutil 默认 `rate_limit_us=1000` | 不准确。初始值来自 cpufreq policy transition delay |
| `arch_scale_freq_ref()` 是电池预测接口 | 不准确。它提供 capacity 计算所用的参考频率 |
| I/O-wait boost 会根据低电量自动收缩 | AOSP 源码没有这条路径；它由 I/O wait 唤醒标志驱动 |
| PowerStats 会自动反馈给 schedutil | AOSP 接口没有规定这样的连接 |
| AOSP example 支持 Mode，量产机就一定会提频 | 不成立。example 的 Mode/Boost 处理没有硬件动作 |

## 阅读源码时的顺序

遇到“某个提示为何没有效果”，按以下顺序排查更省时间：

1. Framework 是否在当前状态下发送了调用；
2. 调用属于 Mode、Boost 还是 HintSession；
3. 设备是否声明并报告支持；
4. Power HAL 对该类型采取了什么动作；
5. kernel policy、thermal 和 driver 是否限制结果；
6. 频率、线程放置、其他硬件资源和业务指标是否变化；
7. 能量结果是否来自同一对象、同一时间基准和可比窗口。

这套顺序把接口契约、产品策略和观测结果分开，避免由一个日志点推断整台设备的功耗架构。
