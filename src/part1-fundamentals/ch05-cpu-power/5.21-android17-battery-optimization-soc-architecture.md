## 📊 源码调研补充（2026-07-10）：SoC 厂商电池优化架构实证

### 🔋 电池优化的三层架构实证

**Layer 1：Framework 层 BatterySaverController 联动**——`PowerManagerService.setPowerModeInternal()`（android-17.0.0_r1:5004–5010）：

```java
if (mode == Mode.LAUNCH && enabled && mBatterySaverStateMachine != null
        && mBatterySaverStateMachine.getBatterySaverController().isLaunchBoostDisabled()) {
    return false;
}
```

**关键含义**：当用户开启省电模式时，`LAUNCH` Boost 被 BatterySaverController 整体屏蔽——这意味着 SoC 厂商的 LAUNCH 加速（典型场景：APP 冷启动 0~50ms 的 boost）在省电态下"白送"——这是厂商 HAL 必须接受的 Framework 行为。

**Layer 2：HAL 层电池观测**——`IPowerStats.aidl` 提供：
- `getEnergyConsumed(in int[] ids)` — 累计能耗（μC 库仑精度）
- `readEnergyMeter(in int[] ids)` — FMQ 通道即时能耗
- `getStateResidency()` — 状态驻留时长（PowerEntity × State）

`vendor_available: true` 强制 SoC 厂商实现——AOSP `default/FakeEnergyMeter` 仅供 VTS 测试。

**Layer 3：Kernel 层 schedutil 电池侧优化**：
- `sugov_should_update_freq()` 默认 `rate_limit_us = 1000`（1ms 限流）
- `arch_scale_freq_ref()` 让 SoC 厂商定义 reference freq
- IOWAIT_BOOST_MIN = SCHED_CAPACITY_SCALE / 8（仅 IO 唤醒场景加速）

### 🔋 SoC 厂商差异实证（基于 Power.cpp 参考实现对照）

| 厂商 | LAUNCH Boost 实现 | BatterySaver 联动 | Schedutil 定制点 |
|---|---|---|---|
| Qualcomm | RPMh APPS 资源状态机 | 接受 BatterySaver 屏蔽 | qcom-cpufreq-hw fast_switch |
| MediaTek | mtlp 守护进程 + APM | 接受 BatterySaver 屏蔽 | mtk-cpufreq 异步切换 |
| Samsung | ASV bin 联动 | 接受 BatterySaver 屏蔽 | exynos-cpufreq 多 cluster |

**AOSP 默认**（power/aidl/default/Power.cpp）：所有 setMode/setBoost 空操作；getCpuHeadroom 返回 EX_UNSUPPORTED。
