# 5.29 Android 17 GPU DVFS Headroom 与 SurfaceFlinger PowerAdvisor 链路


## 两条路径共享 Power HAL，但没有直接调用关系

以 `android-17.0.0_r1` 为锚点，需要先澄清以下版本和实现边界：

| 容易混淆的说法 | Android 17 源码结论 |
| --- | --- |
| GPU headroom 是 Android 17 首次公开 | Java/NDK 公共 API 从 Android 16 / API 36 加入；Android 17 继续提供 |
| Android 17 使用 Power HAL V6 | GPU headroom、composition data 等方法最早出现在冻结的 AIDL V6；Android 17 标签的 `Android.bp` 构建目标是 `android.hardware.power-V7` |
| `HeadroomCache` 固定两槽并采用 LRU | 构造参数 `2` 只用于 `ArrayMap` 初始容量；源码没有容量淘汰，命中时也不移动节点 |
| 缓存命中不发生 Binder 调用 | 应用到 system_server 的 `IHintManager` 同步 Binder 仍会发生；缓存省掉的是 system_server 到 Power HAL 的调用 |
| SurfaceFlinger 已持续调用 `sendCompositionData()` | AIDL、wrapper 和测试已存在，但 `frameworks/native` 的 Android 17 标签中没有生产调用点 |
| 65Hz 以下切回 polling | 65Hz 判断控制 kernel idle timer 到 HW VSYNC 的 resync/disable 行为；源码没有把该分支描述成 GPU DVFS 或 polling 策略 |
| FMQ、缓存带来固定百分比或微秒收益 | 源码能证明减少部分 Binder 往返，不能证明特定设备上的固定时延或节省比例 |

先把两条主路径画开，后面再分别展开：

```text
应用读取 GPU 余量
  SystemHealthManager.getGpuHeadroom()
    → IHintManager
      → HintManagerService cache
        → IPower.getGpuHeadroom()

SurfaceFlinger 提供合成负载提示
  帧目标 + HWC/RenderEngine/GPU fence 时间
    → PowerAdvisor
      → Power Hint Session（FMQ 优先，Binder 回退）
      → IPower.setMode() / IPower.setBoost()
```

这张图说明调用方向。`PowerAdvisor` 没有读取 `getGpuHeadroom()`；应用的 headroom 查询也不会经过 SurfaceFlinger。二者都连接 Power HAL，厂商实现可以在 HAL 内部综合这些输入，但 AOSP 没有规定具体 GPU governor、频点或电压动作。

## 1. GPU headroom 的接口边界

### 1.1 API 版本与 HAL 版本要分开

Android 公共 API 文档把 `SystemHealthManager.getGpuHeadroom()`、窗口范围和最小轮询间隔标为 **API 36**。所以它是 Android 16 已公开、Android 17 继续保留的接口。

Power HAL 的版本号属于另一套版本体系：

- 冻结的 `android.hardware.power-V6` 首次包含 `getGpuHeadroom()`、`getSupportInfo()`、`sendCompositionData()` 和 `sendCompositionUpdate()`；
- `android-17.0.0_r1` 的 `power/aidl/Android.bp` 将 `power_version` 设为 `android.hardware.power-V7`；
- AIDL V6 不能直接换算成 Android API 36 或 API 37。

版本判断应回答两个问题：应用编译时能否看到 API，以及当前设备的 Power HAL 是否声明支持。只看 Android 系统版本仍不够。

### 1.2 返回值是什么

`GpuHeadroomResult.globalHeadroom` 的有效范围是 `[0, 100]`：

- `0` 表示计算窗口内没有可继续分配的 GPU 容量余量；
- 较大值表示 HAL 估计的可用容量更多；
- `Float.NaN` 表示结果暂时不可用，例如数据不足或波动过大；
- 该值是 Power HAL 基于历史窗口给出的估计，不等于 GPU utilization、当前频率或 thermal headroom。

请求参数只有两个核心维度：

| 参数 | 含义 |
| --- | --- |
| `MIN` | 返回窗口内的最小余量，适合关注最差片段 |
| `AVERAGE` | 返回窗口内的平均余量，波动更平滑 |
| `calculationWindowMillis` | 历史计算窗口；合法范围由设备的 `SupportInfo` 决定 |

AIDL 默认值是 `MIN + 1000ms`。不要把 50—10000ms 当成每台设备都相同的固定范围；应用应调用 `getGpuHeadroomCalculationWindowRange()` 读取当前设备的范围。

### 1.3 三层守门

一次有效调用至少经过三层守门：

1. 公共 API 以 `@FlaggedApi(FLAG_CPU_GPU_HEADROOMS)` 声明；进入方法后，`SystemHealthManager` 检查注册时缓存的 `isGpuSupported` 以及窗口范围；
2. `HintManagerService` 再校验 calculation type 和 HAL 上报的窗口范围；
3. Power HAL 根据设备数据返回 `globalHeadroom`、`NaN` 或错误。

设备不支持时，公共 API 抛出 `UnsupportedOperationException`。参数越界时抛出 `IllegalArgumentException`。HAL 返回空结果或 system_server 捕获到远端错误时，framework 最终向应用返回 `Float.NaN`。

### 1.4 应用侧安全调用

下面的示例用于展示调用顺序。它应在工作线程或调度器中运行，不能放进 UI、RenderThread 或游戏逐帧热路径。

```java
@RequiresApi(36)
static float readGpuHeadroom(Context context) {
    SystemHealthManager manager =
            context.getSystemService(SystemHealthManager.class);

    try {
        Pair<Integer, Integer> range =
                manager.getGpuHeadroomCalculationWindowRange();
        int windowMillis = Math.max(
                range.first, Math.min(1000, range.second));

        GpuHeadroomParams params = new GpuHeadroomParams.Builder()
                .setCalculationType(
                        GpuHeadroomParams.GPU_HEADROOM_CALCULATION_TYPE_MIN)
                .setCalculationWindowMillis(windowMillis)
                .build();
        return manager.getGpuHeadroom(params);
    } catch (UnsupportedOperationException e) {
        return Float.NaN;
    }
}
```

示例先用设备范围约束窗口，再处理不支持状态。调用方还要读取 `getGpuHeadroomMinIntervalMillis()` 并限制调度频率；拿到 `NaN` 时保持当前策略，不应把它按 `0` 处理。

`SystemHealthManager` 的源码注释明确提醒：合法调用至少进行一次同步 Binder 事务，可能超过 1ms，首次调用或更换参数后还可能触发 HAL 的延迟初始化。即使 system_server 命中缓存，应用侧 Binder 也没有消失。

## 2. `HintManagerService` 缓存到底做了什么

### 2.1 缓存键与过期时间

system_server 把 framework 参数转换成 HAL 的 `GpuHeadroomParams`，以完整参数对象为键。对 GPU 来说，键由 calculation type 和 calculation window 构成。

缓存项的过期时间是：

```text
插入时的 System.currentTimeMillis()
  + SupportInfo.headroom.gpuMinIntervalMillis
```

该公式用于解释缓存有效期。相同参数在有效期内再次查询时，`HintManagerService` 返回缓存结果，不再调用 `IPower.getGpuHeadroom()`；过期后下一次查询会重新访问 HAL。

### 2.2 `2` 不是容量上限

下面的源码节选用于解释容易被误读的构造参数：

```java
HeadroomCache(int size, long expDurationMillis) {
    mItemList = new LinkedList<>();
    mKeyItemMap = new ArrayMap<>(size);
    mItemExpDurationMillis = expDurationMillis;
}
```

`size` 只传给 `ArrayMap` 作为初始容量。`add()` 没有在条目达到 2 时淘汰旧键，`get()` 命中后也没有把条目移到队尾。因此这里是带过期时间的参数缓存，不能称为“两槽 LRU”。

实现会在查询时从列表头清理已过期项。相同键重新写入时，旧项先从列表移除，再把新项追加到队尾。测试覆盖了两个参数键和按最小间隔过期的行为，但没有证明固定容量或 LRU 淘汰。

### 2.3 statsd 记录什么

每次 `getGpuHeadroom()` 服务调用都会写 `GPU_HEADROOM_REPORTED`，包括：

- calculation window；
- calculation type；
- `isFromCache`；
- success/HAL error 状态；
- 归一化到 `[0, 1]` 的结果值。

这是 statsd atom，不会自动成为 Perfetto 中名为 `GPU_HEADROOM_REPORTED` 的时间轨。需要 statsd 配置或设备已有的数据采集规则才能读取；调试单次调用时，应用自己的时间戳日志通常更直接。

## 3. SurfaceFlinger `PowerAdvisor` 的真实职责

### 3.1 显式 Mode 与 Boost

`setExpensiveRenderingExpected(displayId, expected)` 用 `mExpensiveDisplays` 聚合多个显示设备的状态。集合从空变为非空时发送：

`Mode::EXPENSIVE_RENDERING = true`

集合重新变空时发送 `false`。Power HAL 可以据此调整 CPU、GPU、内存或其他设备策略，也可以忽略该 mode；AIDL 契约没有规定固定动作。

`notifyDisplayUpdateImminentAndCpuReset()` 在系统启动完成后处理两类提示：

- 向 hint session 发送 `SessionHint::CPU_LOAD_RESET`；
- 调用 `setBoost(Boost::DISPLAY_UPDATE_IMMINENT, 0)`。

`mScreenUpdateTimer` 控制这组 reset/boost 是否可以再次发送。定时器存在时，连续屏幕更新不会逐帧重复发这组提示；超时回调把 `mSendUpdateImminent` 重新设为 true。设备未配置该定时器时，源码允许下一次调用继续发送。

### 3.2 “不支持”和“调用失败”走不同分支

PowerAdvisor 对 `EXPENSIVE_RENDERING` 和 `DISPLAY_UPDATE_IMMINENT` 采用探测式缓存：

- HAL 返回 `isUnsupported()` 后，对应布尔值设为 false，后续跳过；
- 普通调用失败不会把能力永久标为不支持。

`PowerHalController::processHalResult()` 遇到 failed result 时会丢弃当前 HAL handle，并让后续调用重新连接。`CACHE_SUPPORT(version, method)` 则按方法静态缓存 `isUnsupported()`。写成“任何失败后永久放弃”会混淆这两种状态。

### 3.3 SurfaceFlinger 的 ADPF hint session

SurfaceFlinger 在 boot finished 阶段根据 flag 和 HAL 能力创建 hint session，线程集合至少包含 SurfaceFlinger 主线程，并在可用时加入 RenderEngine 线程。每帧附近会更新或采集：

- commit start、expected present time、frame delay 和 target duration；
- HWC validate/present 起止时间；
- 是否使用 RenderEngine；
- GPU command submit 附近的起点和 GPU fence；
- present 结束与 post-composition 时间。

`PowerAdvisor::estimateWorkDuration()` 用这些时间计算 `WorkDuration`。`adpf_gpu_sf` flag 启用时，报告中会填充 `cpuDurationNanos` 和 `gpuDurationNanos`；否则相应字段为 0，并保留兼容计算路径。

这组数据是**工作量提示**。Power HAL 怎样把它映射到 GPU DVFS、CPUFreq、内存带宽或其他控制器，由设备实现决定。看到 `reportActualWorkDuration()` 不能直接断言 GPU 已升频。

### 3.4 FMQ 优先，Binder 回退

`createHintSessionWithConfig()` 成功后，PowerAdvisor 尝试通过 `getSessionChannel()` 建立 FMQ。当前代码要求：

- message queue descriptor 有效；
- write flag bitmask 大于 0；
- `eventFlagDescriptor` 存在且 flag queue 有效。

缺少 event flag 时，FMQ message queue 被置空。后续的 target、hint 或 work duration 写入会回退到 `IPowerHintSession` Binder 方法。FMQ 空间不足、begin/commit write 失败时也会回退。

这能说明 FMQ 用于减少高频 Binder 事务，不能从源码推出“每帧固定节省 200µs”。`mHintSessionQueue` 在正常成功发送后立即清空，也不能描述成固定跨多帧批量；发生失败并保留待重试数据时，队列才可能包含多项。

## 4. `sendCompositionData()` 尚不能写成 Android 17 活跃主路径

Power HAL V6 起声明了两类 composition 接口：

| 接口 | AIDL 定义的用途 |
| --- | --- |
| `sendCompositionData(CompositionData[])` | 发送与帧绑定的 scheduled present、latch、producer 和 output 信息，可批量 |
| `sendCompositionUpdate(CompositionUpdate)` | 发送 producer 生命周期、display/output 断开等非逐帧更新 |

`SupportInfo.CompositionDataSupportInfo` 还定义了 `isSupported`、是否禁用 GPU fence、最大批大小和 always-batch 策略。

Android 17 的 `PowerHalController` 已封装这两个调用，AIDL wrapper 测试也覆盖了参数转发。不过，对 `frameworks/native` 的 `android-17.0.0_r1` 全仓调用点检索只找到：

- controller/wrapper 的方法定义；
- empty wrapper；
- 单元测试和 mock；
- 没有 SurfaceFlinger 生产代码发起调用。

同一标签中的 `SessionManager` 和 `SessionLayerMap` 已能维护 hint session 与 layer 的关联，但还没有把关联数据组装成 `CompositionData` 并发送给 Power HAL。因此当前状态是“稳定 AIDL 与 framework scaffolding 已存在”，尚未进入帧处理主路径。

SurfaceFlinger 当前可确认的反馈路径仍是 `PowerAdvisor::reportActualWorkDuration()` 及显式 mode/boost，它们与 `sendCompositionData()` 是不同接口。

## 5. 65Hz kernel idle timer 是显示同步策略

`Scheduler::kernelIdleTimerCallback()` 读取活动模式的 peak FPS，并使用 `65_Hz` 阈值：

- timer reset 且 peak FPS 大于 65Hz 时，调用 `resyncAllToHardwareVsync(true)`；
- timer expired 且 peak FPS 小于等于 65Hz 时，对显示禁用 HW VSYNC；
- 最终通知 `kernelTimerChanged()`。

源码注释把它放在 DPU power collapse、performance mode 与 VSyncController 模型的上下文中。该判断会影响显示同步和唤醒行为，也可能通过帧节奏间接改变系统负载，但它没有读取 GPU headroom，也没有直接设置 GPU 频率。把它命名为“GPU DVFS 65Hz 阈值”会夸大关联。

## 6. 应用怎样使用 headroom 做画质调节

应用控制器需要联合判断 headroom、frame time 和 thermal 状态。

| 证据 | 能说明什么 | 单独使用的风险 |
| --- | --- | --- |
| GPU headroom | HAL 估计的历史窗口余量 | 设备模型不同，短时结果可能为 NaN |
| GPU frame time / fence | 当前渲染工作耗时 | 可能受 frame pacing、排队和 present 节拍影响 |
| CPU frame time | 游戏逻辑或提交端是否赶得上 | 不能代表 GPU 压力 |
| thermal status/headroom | 热预算是否逼近限制 | 响应尺度与 GPU 负载尺度不同 |
| 实际 present interval | 用户看到的帧节奏 | 受刷新率上限和 BufferQueue 背压影响 |

一个稳健的控制器通常按以下顺序工作：

1. 在 worker thread 按设备最小间隔采样 GPU headroom；
2. 对 NaN 和短时尖峰做保护，保留最近一次可信状态；
3. 用连续多次样本确认压力方向；
4. 结合 GPU frame time 和 thermal 状态选择分辨率、阴影、后处理、LOD 或目标 FPS；
5. 对升档和降档使用不同阈值，并设置最短保持时间；
6. 每次改档后等待管线稳定，再评价效果。

阈值需要按游戏内容、SoC 和画质档校准。把 `headroom < 20` 写成所有设备通用规则，或每帧在两个画质档之间切换，都会引入新的资源重建和 frame-time 抖动。

## 7. 调试与验证

### 7.1 查看设备支持信息

下面的命令用于读取 `HintManagerService.dump()` 暴露的 HAL 版本、GPU headroom 支持、最小间隔、窗口范围和一次默认查询结果：

```bash
adb shell dumpsys performance_hint
```

输出中的 `GPU headroom: N/A` 可能表示不支持、暂时不可用或查询失败，需要结合前面的 support、interval 和系统日志判断。商品机可能限制部分 dump 信息。

### 7.2 对齐 SurfaceFlinger 提示与设备响应

验证 PowerAdvisor 是否产生效果，需要三组时间相关证据：

1. SurfaceFlinger trace 中的 `ExpensiveRendering`、`Session hint`、`Target Work Duration`、`Reported Work Duration`、`Reported cpu duration`、`Reported gpu duration`；
2. Power HAL 或厂商 trace 中接收到的 mode、boost、hint session 数据；
3. 随后的 GPU devfreq、CPUFreq、memory/thermal 状态与帧时间变化。

只看到第一组，最多证明 framework 发出了提示；只看到频率变化，也无法归因到某个提示。厂商 GPU tracepoint 和 sysfs 节点没有统一名称，应先检查该设备的 `tracefs/available_events` 与 devfreq 目录。

### 7.3 复现实验的对照项

- 固定刷新率、分辨率、亮度、画质、场景脚本和温度起点；
- 分别记录 HWC composition 与 client/GPU composition 比例；
- 同时报平均帧率、frame-time 分位数、GPU frequency residency 和功耗轨；
- 区分首次调用、参数切换后的冷状态与稳定状态；
- 记录 headroom 查询参数、采样间隔、NaN 比例和画质状态机转移；
- 不用单次 headroom 数值证明 HAL 的计算公式。
