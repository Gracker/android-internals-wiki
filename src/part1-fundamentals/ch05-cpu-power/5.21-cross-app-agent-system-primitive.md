# 5.21 跨应用 AI Agent 系统原语：AccessibilityService / VoiceInteractionService / AppFunctionService 三条技术路径对比

§5.20 讲了 Agent 怎么调模型（AICore / ML Kit GenAI / LiteRT-LM）。本节补完另一面——Agent 怎么跨 App。Android 17 提供三条并存的系统原语，对应不同的语义层与 OEM 控制深度：

| 维度 | AccessibilityService | VoiceInteractionService | AppFunctionService (Android 17 新) |
|------|---------------------|------------------------|-----------------------------------|
| 引入 API | 4 (2011) | 23 (2015) | 37 (Android 17, 2026) |
| 适用场景 | 任意第三方 AI Agent | 系统级 Assistant | 跨 App Agent 标准化协议 |
| 谁能成为该 Service | 任意第三方（manifest + 用户授权） | 仅 OEM 预装（signature 权限） | 仅 target App 自己（manifest 声明） |
| 权限级别 | `BIND_ACCESSIBILITY_SERVICE` (signature) | `BIND_VOICE_INTERACTION` (signature) | `BIND_APP_FUNCTION_SERVICE` (signature) + 调用方 `EXECUTE_APP_FUNCTIONS` (normal, 设备白名单 + 用户授权) |
| 跨 App UI 控制 | 完全（看屏幕 + 模拟手势） | 间接（拿 AssistStructure） | 无（target 自己执行函数） |
| Target App 感知 | 否 | 否 | 是 |
| 生态适配成本 | 低 | 低 | 高（target 需主动适配） |

## AccessibilityService — 第三方 AI Agent 的现实路径

权限定义（`frameworks/base/core/res/AndroidManifest.xml` line 6342）：

```xml
<permission android:name="android.permission.BIND_ACCESSIBILITY_SERVICE"
    android:protectionLevel="signature" />
```

> signature 级——只有 Android 系统镜像签名者能让系统绑它的 AccessibilityService。第三方的 `<service>` 必须要求这个权限才能被系统识别为合法 AccessibilityService。

关键 API（`core/java/android/accessibilityservice/AccessibilityService.java`）：

- `dispatchGesture(GestureDescription, ...)` — 注入手势
- `performGlobalAction(int action)` — 21 个 GLOBAL_ACTION 常量（BACK/HOME/RECENTS/LOCK_SCREEN/TAKE_SCREENSHOT 等）
- `getRootInActiveWindow(...)` — 读屏基础
- `onServiceConnected()` — 系统绑定后回调

权限路径的「双层网关」：

1. Manifest 层：开发者必须写 `<service android:permission="android.permission.BIND_ACCESSIBILITY_SERVICE">`
2. 用户层：用户必须在 Settings → Accessibility 里主动开启（`AccessibilityManagerService.onServiceInfoChangedLocked`）
3. RestrictedSetting 拦截层：`AccessibilityManagerService.sendRestrictedDialogIntent`（line 5610）— 非预安装包弹出受限设置警告（Android 13 引入）

> **「豆包模式」的 UX 缺陷由此而来**：豆包得抢焦点、模拟手势、解析目标 UI；当用户输入密码或验证码时，系统对 `EditText` 标记 `isAccessibilityDataSensitive` 时屏蔽内容，Agent 无法完成支付/验证码场景。这是**安全设计的有意限制**。

## VoiceInteractionService — 系统级 Assistant 的官方路径

权限定义（`AndroidManifest.xml` line 6493 + line 8484）：

```xml
<permission android:name="android.permission.BIND_VOICE_INTERACTION"
    android:protectionLevel="signature" />

<permission android:name="android.permission.ACCESS_VOICE_INTERACTION_SERVICE" ... />
```

用户授权通过 `RoleManager.ASSISTANT`（系统默认角色）：

```java
// VoiceInteractionManagerServiceImpl.java line 309
public void grantImplicitAccessLocked(int grantRecipientUid, @Nullable Intent intent) {
    final int grantRecipientAppId = UserHandle.getAppId(grantRecipientUid);
    final int grantRecipientUserId = UserHandle.getUserId(grantRecipientUid);
    final int voiceInteractionUid = mInfo.getServiceInfo().getUid();
    mPackageManagerInternal.grantImplicitAccess(
            grantRecipientUserId, intent,
            grantRecipientAppId, voiceInteractionUid,
            /* direct= */ true);
}
```

`AssistContent` 跨进程传输（`core/java/android/app/assist/AssistContent.java`）：
- `setIntent(Intent)` / `getIntent()` — 当前 Activity 的 Intent 上下文
- `setStructuredData(String)` — App 主动声明的结构化数据
- `setClipData(ClipData)` — 选中文本/拖拽数据
- `setUri(Uri)` — 当前主要 Uri
- `setSessionTransferUri(Uri)` — Android 17 新增，让 Agent session 跨进程恢复

**Android 17 新增的安全约束**（`VoiceInteractionManagerServiceStub.enforceSessionFlags` line 1230）：

```java
// For services targeting CINNAMON_BUN or higher:
// SHOW_WITH_ASSIST          removed if !usesAssistData
// SHOW_WITH_SCREENSHOT      removed if !usesAssistScreenshots
// SHOW_WITH_ASSIST_STRUCTURE_SCREEN_CONTENT
//                           removed if !usesAssistStructureScreenContent

// Self-trigger restrictions:
// If the session is initiated by the voice interaction service itself from
// the background without a valid user signal...all flags related to accessing
// screen content are removed.
```

> 这是 Android 17（API 37，CINNAMON_BUN）**强制收紧**的边界条件：Assistant 服务必须在 manifest 里**显式声明**它要用 assistData/assistScreenshots/assistStructureScreenContent 三类能力；后台自触发时所有 screen 相关 flag 强制清除。

## AppFunctionService — Android 17 为 AI Agent 准备的官方协议

权限定义（`AndroidManifest.xml` line 9481-9515）：

```xml
<!-- BIND_APP_FUNCTION_SERVICE: target side -->
<permission android:name="android.permission.BIND_APP_FUNCTION_SERVICE"
    android:featureFlag="android.app.appfunctions.flags.enable_app_function_manager"
    android:protectionLevel="signature" />

<!-- EXECUTE_APP_FUNCTIONS: agent side -->
<permission android:name="android.permission.EXECUTE_APP_FUNCTIONS"
    android:protectionLevel="normal" />
    <p>... the application must be on a device allowlist, and its ability to execute
       functions is subject to user approval or disapproval. -->

<!-- EXECUTE_APP_FUNCTIONS_SYSTEM: system agents only -->
<permission android:name="android.permission.EXECUTE_APP_FUNCTIONS_SYSTEM"
    android:protectionLevel="internal|recents|role" />
```

> `DISCOVER_APP_FUNCTIONS`（`AndroidManifest.xml` line 9442）只给 `SYSTEM_UI_INTELLIGENCE` 与 `SYSTEM_VENDOR_INTELLIGENCE` 两个角色。第三方 AI App 拿到 `EXECUTE_APP_FUNCTIONS` 后能执行，但**不能发现** target App 的所有函数清单——避免「全 App 列表枚举攻击」。

Manifest 声明模板（`AppFunctionService.java` line 50-65）：

```xml
<service
    android:name=".YourAppFunctionService"
    android:permission="android.permission.BIND_APP_FUNCTION_SERVICE">
  <property
      android:name="android.app.appfunctions"
      android:value="your_app_functions.xml" />
  <intent-filter>
    <action android:name="android.app.appfunctions.AppFunctionService" />
  </intent-filter>
</service>
```

Agent 端调用（`AppFunctionManager.java` line 378-405）：


> 与 AccessibilityService 路径的关键差异：AppFunctionService 调用是**显式 API 调用**，target App 知道自己被调用、能控制暴露什么；AccessibilityService 是**「读屏 + 模拟输入」**，target App 完全无感知。「豆包模式」用前者还是后者，决定了 target App 是否愿意适配。

## 豆包模式的工程实质

1. **前台 App 没声明 AppFunctionService** → 豆包无法走 AppFunction 路径（除非 target 主动适配）
2. **豆包没拿到 `Role.ASSISTANT`** → 豆包无法走 VoiceInteractionService 路径（除非 OEM 给）
3. **现实选择**：用 AccessibilityService 读屏 + 手势 + 剪贴板 + 全局动作。代价：
   - 用户必须在设置里主动开启
   - 支付/密码/验证码场景被系统主动屏蔽
   - 性能开销：每次模拟手势 = 一次完整 Binder + InputDispatcher 路径

## 性能数据

- **AccessibilityService 路径**：每次手势 = 一次 Binder 事务 + InputManager.injectInputEvent + InputDispatcher 链路。实测 ~30-80ms。跨 App「点外卖」流程（10+ 步）总耗时 1-3s——豆包类 App 用户感知「AI 操作有延迟」的根因。
- **VoiceInteractionService 路径**：AssistStructure 序列化在 Bundle 里可达 100KB-1MB，binder 延迟 + 序列化 ~50-150ms。
- **AppFunctionService 路径**：仅一次 Binder 事务 + target 冷启动（如未启动）。冷启 200-500ms，热路径 20-80ms——三条路径里**性能可控**的，前提是 target 已适配。

## 版本差异

- **Android 14 (API 34)**：首次收紧 Restricted Settings 对 AccessibilityService 的限制，非预装 App 必须弹警告。
- **Android 15 (API 35)**：`migrateSystemUserToDefault` 强制主用户必须是 default user，影响多用户下 Assistant 可见性。
- **Android 16 (API 36)**：`FLAG_VISUAL_QUERY_ACCESS` + `MANAGE_HOTWORD_DETECTION` 必须 preinstalled。
- **Android 17 (API 37)**：
  1. 新增 AppFunctionService / AppFunctionManager 完整协议栈（`FLAG_ENABLE_APP_FUNCTION_MANAGER`）
  2. 新增 `EXECUTE_APP_FUNCTIONS_SYSTEM`（internal|recents|role）
  3. `ENABLE_RESTRICT_ASSIST_STRUCTURE` 兼容变更（CINNAMON_BUN 后）— VoiceInteractionService 必须显式声明三 assist flag，否则强制裁剪
  4. 新增 `AssistContent.EXTRA_APP_FUNCTION_DATA` + `mSessionTransferUri`，Agent session 跨进程状态可序列化
  5. `DISCOVER_APP_FUNCTIONS` 对调用方不可见
