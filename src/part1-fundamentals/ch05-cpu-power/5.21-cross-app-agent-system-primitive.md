# 5.21 跨应用 AI Agent 系统原语：AccessibilityService / VoiceInteractionService / AppFunctionService 三条技术路径对比

端侧模型解决“怎样理解用户意图”，跨应用执行还需要 Android 组件、安全边界和目标应用配合。`AccessibilityService`、`VoiceInteractionService` 与 App Functions 都能参与跨应用流程，但三者表达的含义差别很大：

- `AccessibilityService` 面向无障碍辅助，通过 UI 语义树、节点动作、全局动作和手势与当前界面交互；
- `VoiceInteractionService` 是每用户选中的语音交互服务，配套 `VoiceInteractionSession` 获取受控的 assist 上下文，并可调用目标 Activity 提供的 `DirectAction`；
- App Functions 让目标应用显式声明可执行函数，由 system_server 校验调用方后绑定目标 `AppFunctionService`，或调用 Android 17 的运行时函数实现。

它们不是 Android 上全部的跨应用机制。Intent、deep link、ContentProvider、MediaSession、RemoteViews 和各类领域 API 往往更合适。本章只比较 AI Agent 容易混用的三套系统原语。

本章以 Android 17 / API 37 / `android-17.0.0_r1` 为平台基线。结论来自 Framework 与 system_server 源码；商店政策、OEM 默认 Assistant 选择和产品 allowlist 需要按发行渠道与具体设备另行确认。

## 先看选择结论

| 维度 | `AccessibilityService` | `VoiceInteractionService` / Session | App Functions |
|---|---|---|---|
| 首次公开 | API 4 | API 21 | API 36 |
| 主要语义 | 辅助用户操作 UI | 当前 Assistant 的会话与上下文 | 目标应用显式发布函数 |
| 提供方 | 声明组件并由用户启用的应用 | 每用户选中的 active voice interaction service | 声明函数的目标应用 |
| 调用方控制 | 用户开启服务；系统和设备策略继续约束 | Assistant 选择、session flags、用户信号与设备策略 | 权限、设备 allowlist、用户授权、包可见性与企业策略 |
| 目标应用配合 | 无需专门适配，但 UI 必须暴露可用语义或可交互坐标 | 可通过 assist callbacks、`AssistContent`、`DirectAction` 配合 | 必须声明 metadata，并提供 Service 或运行时实现 |
| 跨应用动作 | 节点 action、全局 action、注入手势 | `DirectAction`、voice activity、assistant activity 等受控入口 | 函数请求、参数、响应、取消与错误 |
| 主要弱点 | UI 变化、节点陈旧、敏感视图、坐标和动画使流程脆弱 | 只有 active service；assist 内容受多重裁剪；不是通用 UI 自动化 | 功能仍受 feature flag 与访问策略影响；目标应用要适配 |

工程上优先采用目标应用认可的语义接口：App Functions、`DirectAction` 或领域 API。UI 自动化适合用户明确授权、界面可见且能够容忍失败的辅助流程，不能替代支付、授权和数据访问的业务协议。

## 先纠正 `BIND_*` 权限的方向

三类 Service 都会在 manifest 的 `<service android:permission="...">` 上声明 signature 权限。这里的含义是：绑定该 Service 的调用者必须持有权限。system_server 持有平台 signature 权限，因此可以绑定；提供 Service 的 APK 不需要因这项声明而使用平台签名。

例如，普通应用可以声明 `AccessibilityService`。系统解析组件时会检查 Service 是否要求 `BIND_ACCESSIBILITY_SERVICE`，然后等待用户在设置中启用。`BIND_VOICE_INTERACTION` 和 `BIND_APP_FUNCTION_SERVICE` 采用相同的“只允许系统绑定”模式。

这与 `EXECUTE_APP_FUNCTIONS` 的方向相反。后者是 Agent 调用其他应用函数时需要的执行权限，随后还会经过 allowlist 和用户访问状态校验。

## AccessibilityService：基于界面语义的辅助操作

### 声明组件不等于获得能力

下面的 manifest 用于说明系统识别一个 AccessibilityService 所需的最小结构：

```xml
<service
    android:name=".AgentAccessibilityService"
    android:permission="android.permission.BIND_ACCESSIBILITY_SERVICE"
    android:exported="true">
    <intent-filter>
        <action android:name="android.accessibilityservice.AccessibilityService" />
    </intent-filter>
    <meta-data
        android:name="android.accessibilityservice"
        android:resource="@xml/agent_accessibility_service" />
</service>
```

`android:permission` 保护绑定入口，`intent-filter` 让系统识别组件，`meta-data` 描述事件、包、反馈类型和能力。安装应用后，服务仍是关闭状态，必须由用户启用；设备策略、Enhanced Confirmation 或 Restricted Setting 还可能阻止或增加确认步骤。

XML 配置决定服务能否读取窗口和注入手势：

- `canRetrieveWindowContent` 控制窗口节点检索能力；
- `canPerformGestures` 控制 `dispatchGesture()`；
- `packageNames` 和 `eventTypes` 可以缩小事件范围；
- `notificationTimeout` 会合并高频事件；
- `isAccessibilityTool` 表示服务是否用于帮助残障用户，Android 17 的敏感视图过滤会使用这个属性。

`getRootInActiveWindow()` 只返回当下 active window 的节点快照。窗口可能在查询后立即变化，节点可能陈旧，服务也可能因配置、包过滤、`importantForAccessibility` 或自绘 UI 而看不到业务需要的元素。

### 操作优先级：语义 action 在前，坐标手势在后

一个较稳的 UI 辅助流程通常按以下顺序尝试：

1. 用 view ID、文本、内容描述、role 或层级定位节点；
2. 调用节点的 `ACTION_CLICK`、`ACTION_SET_TEXT`、`ACTION_SCROLL_*`；
3. 等待与动作相关的 window/content 事件，并重新获取节点；
4. 节点未提供有效 action 时，再考虑 `dispatchGesture()` 的坐标 fallback；
5. 每一步检查前台包、窗口 ID、节点状态与超时，不盲目执行下一步。

`dispatchGesture()` 在客户端生成 gesture steps，经 `IAccessibilityServiceConnection` 进入 system_server。`AccessibilityServiceConnection` 校验 `canPerformGestures` 后，把事件交给 `MotionEventInjector`。因此它不只是“一次 Binder + InputDispatcher”，还包含采样、权限检查、注入、目标窗口分发、动画和目标应用处理。

坐标方案在字体缩放、横竖屏、折叠屏、分屏、IME、弹窗、广告位和无障碍放大下都可能偏移。对关键操作，应要求用户确认目标与最终结果。

### 敏感内容不是一个简单的“全部不可见”

Android 17 的 `View.accessibilityDataSensitive` 会限制非 accessibility-tool 服务：

- 敏感 View 及其后代可以不进入这类服务的节点查询；
- 敏感事件只发给符合条件的 accessibility tool；
- 来自非 accessibility-tool 服务的注入触摸会在敏感 View 上被过滤。

密码字段还有 `AccessibilityNodeInfo.isPassword()`、文本变换和应用自身保护。`FLAG_SECURE`、自绘控件、Web 内容以及应用的业务确认也会改变可见性和可操作性。

因此不能写成“验证码和支付必然无法完成”，也不能假设打开无障碍后便能读取所有内容。可靠结论必须针对具体 View 类型、服务的 `isAccessibilityTool`、设备构建和目标应用验证。即使技术上可以触发动作，涉及转账、授权、删除和隐私披露时也应保留用户确认。

### 它没有目标应用认可的函数契约

目标应用会生成 accessibility 节点和事件，系统也能标记输入来自 AccessibilityService；但调用没有“函数 ID、参数 schema、调用方身份、响应类型”这类业务契约。页面改版或文案变化就可能破坏流程。

这也是 AccessibilityService 与 App Functions 的主要差异：前者操作用户界面，后者让目标应用执行自己声明的业务函数。

## VoiceInteractionService：每用户选中的 Assistant

### `BIND_VOICE_INTERACTION` 不等于“仅 OEM 预装”

`VoiceInteractionServiceInfo` 检查组件是否要求 `BIND_VOICE_INTERACTION`，目的是只让系统绑定。`VoiceInteractionService` 的公开契约写明，当前服务由用户选择，系统会让它保持运行。源码没有用该权限要求 Service APK 必须是平台签名。

某个应用能否成为设备上的 Assistant，还取决于 role 配置、Service metadata、系统设置和 OEM 选择。HotwordDetectionService、VisualQueryDetectionService 及其麦克风能力有额外的系统权限和预装限制，不能反推所有 VoiceInteractionService 都只能预装。

`VoiceInteractionService` 本身应保持轻量。显示 UI 和处理会话的重工作应放在单独进程中的 `VoiceInteractionSessionService` / `VoiceInteractionSession`。

### assist 上下文由目标应用与系统共同提供

当 session 请求 assist 数据时，前台 Activity 可以通过 `onProvideAssistData()` 和 `onProvideAssistContent()` 补充内容。`VoiceInteractionSession.onHandleAssist()` 收到：

- Activity 提供的 `Bundle`；
- `AssistStructure` 窗口结构；
- `AssistContent` 中的 Intent、ClipData、JSON-LD structured data、web URI 和 extras；
- Android 17 源码中的 `EXTRA_APP_FUNCTION_DATA`；
- feature flag 开启时的 session transfer URI。

目标应用并非完全无感知：它可以参与 assist callback，窗口设为 secure 时结构会成为空 stub，自动填充的内容与 screenshot 也会受限制。用户设置、设备策略和 session flags 还能让各字段为 `null`。

`AssistContent.setSessionTransferUri()` 服务于应用到 Web 的 session transfer 场景，源码还明确提醒不要在 URI 中编码认证凭据。它不能被概括成任意 Agent 的跨进程状态恢复通道。

### Android 17 对 screen content 改为显式申请

对 targetSdk 37 且启用 `ENABLE_RESTRICT_ASSIST_STRUCTURE` 兼容变更的 Assistant，`enforceSessionFlags()` 会按 manifest 声明裁剪：

- 未声明 `usesAssistData`：清除 `SHOW_WITH_ASSIST`；
- 未声明 `usesAssistScreenshots`：清除 `SHOW_WITH_SCREENSHOT`；
- 未声明 `usesAssistStructureScreenContent`：清除 `SHOW_WITH_ASSIST_STRUCTURE_SCREEN_CONTENT`。

结构化 screen content 还要满足 `READ_ASSIST_STRUCTURE_SCREEN_CONTENT` 权限和对应 show flag。旧 target SDK 的隐式默认值用于兼容，不能作为新 Assistant 的设计依据。

Android 17 还可启用 self-trigger 限制。当前 VoiceInteractionService 从后台自行拉起 session 时，若没有近期 hotword、前台状态、media projection 等允许条件，系统会清除三类 screen-content flag。源码中的近期 hotword 窗口为 30 秒，但这只是“是否允许携带 assist flag”的判断，不是 session 的通用超时。

### `DirectAction` 比 UI 点击更接近业务语义

`VoiceInteractionSession.requestDirectActions()` 会向指定 Activity 请求它通过 `Activity.onGetDirectActions()` 发布的动作；`performDirectAction()` 再请求该 Activity 执行。目标应用决定动作 ID、参数处理和返回 Bundle。

这条路径需要 Activity 主动适配，并且动作与 Activity 实例关联。它比坐标点击稳定，但没有 App Functions 的全局 metadata、按包搜索和独立 Service 唤醒模型。

VoiceInteractionService 也没有自动获得任意 App 的 UI 控制权。没有 DirectAction 时，assist 数据主要用于理解上下文；后续动作仍要通过公开 Intent、目标 API 或用户可见交互完成。

## App Functions：目标应用发布可调用能力

### Android 17 是扩展版本，起点是 API 36

`AppFunctionManager` 与 `AppFunctionService` 在 API 36 加入。Android 17 / API 37 的源码继续增加：

- `searchAppFunctions()` 与 `observeAppFunctions()`；
- `getAppFunctionStates()` 和 activity state 查询；
- `registerAppFunction()` / `registerAppFunctions()` 运行时实现；
- activity scope 与 `AppFunctionActivityId`；
- 面向 agent-target 的访问状态和授权 UI；
- permission V2、allowlist 与更细的 package visibility 规则。

Android 17 的 package 文档仍将 App Functions 标为 beta/experimental preview，相关 API 带 `@FlaggedApi`。开发时要同时检查 SDK API level、设备 feature flag、system service 是否发布，以及目标应用是否声明函数。

### 目标应用怎样提供函数

下面的 manifest 用于展示 Service 形式的函数提供方：

```xml
<service
    android:name=".NoteAppFunctionService"
    android:permission="android.permission.BIND_APP_FUNCTION_SERVICE"
    android:exported="true">
    <property
        android:name="android.app.appfunctions"
        android:value="note_app_functions.xml" />
    <intent-filter>
        <action android:name="android.app.appfunctions.AppFunctionService" />
    </intent-filter>
</service>
```

系统只允许一个 `AppFunctionService` 在应用内处于 active 状态。XML asset 声明函数 ID、参数、返回类型、默认启用状态和 schema 等 metadata；一个 Service 可以按 `request.getFunctionIdentifier()` 分发多个函数。

`onExecuteFunction()` 在主线程回调。文件访问、数据库、网络或模型推理必须切到 worker，并在所有路径调用 callback。`CancellationSignal` 是协作式取消，目标实现需要主动检查或向下游传播。

Android 17 还允许应用在运行时注册 global 或 activity-scoped 实现。metadata 仍要预先在 application 级 XML 中声明；进程被冻结、注册 Context 销毁或显式 unregister 后，运行时实现不可用。

### Agent 的执行权限有两套 feature-flag 分支

Android 17 的 `AndroidManifest.xml` 对 `EXECUTE_APP_FUNCTIONS` 有条件定义：

- `app_function_access_api_enabled` 开启时，它是 normal 权限，但跨应用执行还要求设备 allowlist、agent-target 用户授权、目标包可见、目标 Service 存在；
- 该 flag 关闭时，旧定义为 `internal|privileged`；
- `EXECUTE_APP_FUNCTIONS_SYSTEM` 是 `internal|recents|role`，供受信任的系统入口使用，并可绕过普通 Agent 的 allowlist 校验。

normal 权限不表示安装后可以调用任意应用。`CallerValidatorImpl` 会核对 Binder UID 与包名、目标用户、执行权限、allowlist、用户访问状态和 enterprise policy。Permission V2 还拒绝跨用户及 secondary profile 交互。

普通 Agent 可以用 `getAccessRequestState(targetPackage)` 区分：

- `GRANTED`：当前 agent-target 已获访问；
- `DENIED`：用户未批准或已拒绝；
- `UNREQUESTABLE`：权限、allowlist、包可见性、安装状态或目标 Service 不满足。

需要用户授权时，API 37 可通过 `createRequestAccessIntent()` 打开系统管理界面。Agent 不应自建一个外观相同的授权页，也不应把 target App 的登录态当作 App Functions 访问授权。

### discovery 与 execution 不是一条“全部可见”权限

API 37 的 `searchAppFunctions()` 允许调用方搜索：

- 自己包内的函数，无需跨应用权限；
- 持有 `EXECUTE_APP_FUNCTIONS`、`DISCOVER_APP_FUNCTIONS` 或 `EXECUTE_APP_FUNCTIONS_SYSTEM` 时，搜索 `PackageManager.canPackageQuery()` 允许查询的其他包。

所以“持有普通执行权限后完全不能发现函数”并不成立。`DISCOVER_APP_FUNCTIONS` 是 `internal|role`，授予 system intelligence 角色，用于更广的受信任发现；普通 Agent 的结果仍受包可见性和访问策略过滤。

执行时，system_server 校验调用方、查询 metadata 和 enabled state，解析目标 Service，再以 `BIND_AUTO_CREATE` 绑定。跨应用且通过权限校验的调用还会使用 `BIND_FOREGROUND_SERVICE` 提升目标处理期间的进程状态。系统随后把请求、取消通道和一次性 callback 交给目标 Service。

这条路径至少包含“Agent 到 system_server”和“system_server 到 target Service”两段 Binder，以及可能的 AppSearch 查询和进程启动。不能描述为一次 Binder 事务。

### Android 17 不再向目标函数暴露 Agent 身份

`AppFunctionService.onExecuteFunction()` 仍保留 `callingPackage` 与 `callingPackageSigningInfo` 参数，但源码契约规定，从 `CINNAMON_BUN` 起前者始终为空字符串，后者始终是 unknown signing info。目标应用不应按调用方包名改变函数行为。

目标应用仍然知道“自己的函数正在被系统调用”，也掌握函数实现、用户登录、数据校验、业务权限和最终返回。需要用户确认的业务动作，应由函数实现显式触发确认，不应依赖调用方身份猜测风险。

### App Functions 不是 MCP

App Functions 定义 Android 本地的 metadata、请求、响应、权限和 Service 生命周期。MCP 定义另一套工具/资源协议和传输方式。二者可以通过适配器连接，但 App Functions 源码没有实现 MCP transport，也没有把 function metadata 声明为 MCP tool schema。

把 App Functions 叫作“on-device MCP”会混淆协议、权限和兼容性。更准确的称呼是 Android 的跨应用函数调用框架。

## 三条路径的耗时应怎样测

原稿给出的 20–500 ms 固定区间没有设备、构建、样本和 trace 依据。跨应用操作的主要延迟来自不同阶段，应该分段采集。

| 路径 | 至少要拆出的阶段 |
|---|---|
| Accessibility | 事件到达、节点查询、决策、gesture step 生成、Binder、注入、目标首个响应、动画稳定 |
| Voice interaction | session 拉起、Activity assist callback、结构采集/传输、screenshot、`onHandleAssist()`、DirectAction |
| App Functions | caller API、system_server 校验、metadata 查询、Service bind/进程启动、主线程回调、业务 worker、callback |

冷启动、应用网络请求、页面动画和模型推理不能算成 Binder 固有耗时。Binder 也可能不止一跳。

下面的命令用于确认目标设备是否启用了三套服务，并保存系统侧状态：

```bash
adb shell dumpsys accessibility
adb shell dumpsys voiceinteraction
adb shell service check app_function
adb shell dumpsys app_function
```

`app_function` 未发布时，后两条会显示 service 不存在或无 dump；这比只检查 API level 更能反映设备构建。`dumpsys accessibility` 中可能包含敏感的组件信息，报告对外分享前应脱敏。

一次可比较的 Perfetto / app trace 至少应记录：

1. Agent 收到意图、开始查节点或发 request 的时间；
2. system_server 入口与返回；
3. 目标进程是否已存在、何时启动；
4. 目标主线程何时收到回调；
5. 业务工作线程的开始、结束与取消；
6. UI 首个可见结果与最终结果；
7. 成功、拒绝、超时、节点陈旧、函数禁用等失败类型。

对十步 UI 流程，报告每一步和端到端的 p50/p90/p99，并区分冷/热、设备、动画倍率、网络与 target 版本。一个总耗时无法告诉你应该修节点定位、减少 bind、预热进程还是优化目标业务。

## 设计跨应用 Agent 时的检查表

### 先选最低权限的语义入口

1. 目标应用已有 Intent、deep link、MediaSession 或领域 API：先用这些接口；
2. 目标应用提供 App Functions：使用声明的函数和系统授权；
3. 当前 Assistant 与 Activity 有 DirectAction：使用 DirectAction；
4. 只有用户可见 UI，且任务允许人工确认与失败恢复：再评估 AccessibilityService。

### 再补安全与失败处理

- 每次关键动作前后校验包名、窗口、对象和结果；
- 支付、授权、删除、发送和隐私数据读取要求用户确认；
- 对 `CancellationSignal`、进程死亡、Service bind 失败和 callback 超时做幂等处理；
- App Function 目标同时检查登录态、业务权限、参数 schema 和资源归属；
- 不记录 AssistStructure、节点文本、函数参数中的凭据和个人数据；
- 不把 accessibility tool 声明当作绕过业务安全的手段。

### 最终验证版本与产品差异

- API 36：AppFunctionManager / Service、静态 metadata、执行与 enabled state；
- API 37：动态函数、activity scope、搜索/观察、访问管理以及 permission V2；
- targetSdk 37：VoiceInteractionService 的 assist manifest opt-in 与结构化 screen-content 约束；
- Android 17 feature flags：App Functions、permission V2、access UI、Voice self-trigger 限制可能分别控制；
- OEM / 企业：Assistant 候选、allowlist、工作资料与 device policy 可以继续缩小能力。

## 常见误判

| 说法 | Android 17 源码结论 |
|---|---|
| `BIND_ACCESSIBILITY_SERVICE` 是第三方 App 无法持有的门槛 | 方向错误。Service 要求该权限，是为了只让系统绑定 |
| VoiceInteractionService 只能由 OEM 预装 | 核心 Service 源码没有这个限制；active service 由用户与设备配置选择，hotword 等子能力另有约束 |
| Voice Assistant 只能读 AssistStructure，不能调用目标语义动作 | 不完整。适配后的 Activity 可以提供并执行 `DirectAction` |
| App Functions 是 Android 17 才加入 | 不准确。Manager / Service 从 API 36 加入，API 37 做了大幅扩展 |
| `EXECUTE_APP_FUNCTIONS` 是 normal，所以所有 App 都能互调 | 不准确。feature flag、allowlist、用户授权、包可见性、企业策略和目标 Service 都会参与校验 |
| 普通 Agent 有执行权限但完全不能搜索函数 | 不准确。API 37 的 search 允许执行权限参与，结果仍受可查询包与访问策略限制 |
| AppFunction 调用只有一次 Binder | 不准确。至少有 Agent→system_server 和 system_server→target 两段，还可能启动进程与查询 metadata |
| Accessibility 能读到所有密码、验证码与支付信息 | 不成立。密码、敏感 View、accessibility-tool 过滤、secure window 和应用实现都会限制 |
| `setSessionTransferUri()` 是 Agent 通用状态迁移 | 不准确。它面向 app-to-web session transfer，并带有凭据安全限制 |
| App Functions 就是 Android 版 MCP | 不准确。两者协议、传输、权限和生命周期不同 |
