# 3.14 Input 系统参考文献

这份索引收录 Android 输入系统的固定源码入口与章节对应关系。

当前复核锚点为：

- platform：Android 17 / API 37 / `android-17.0.0_r1`；
- kernel：`android17-6.18-2026-06_r6`；
- 历史章节可保留 Android 8—17 的演进，当前对象名和调用关系以 Android 17 固定 tag 为准。

## 1. Android 17 输入事件主线

触摸屏、鼠标、键盘等 Linux input 设备通过 evdev 暴露事件。Android native 输入主线可概括为：

`evdev → EventHub → InputReader → InputListener stages → InputDispatcher → InputChannel/InputTransport → InputEventReceiver → ViewRootImpl`

Android 17 的 [`InputManager.cpp`](https://android.googlesource.com/platform/frameworks/native/+/android-17.0.0_r1/services/inputflinger/InputManager.cpp) 直接给出当前 `InputListener` 顺序：

1. `InputReader`
2. `UnwantedInteractionBlocker`
3. `InputFilter`
4. `PointerChoreographer`
5. `InputProcessor`
6. 可选的 `InputDeviceMetricsCollector`
7. 可选的 `InteractionReporter`
8. `InputDispatcher`

旧资料常见的 `classifier/InputClassifier.cpp` 路径在 `android-17.0.0_r1` 中不存在。当前 motion classification 相关实现位于 `InputProcessor.cpp`，手掌与触控笔冲突处理还要查看 `UnwantedInteractionBlocker.cpp`。`InputProcessor` 只对满足来源和配置条件的 motion event 执行分类，不能把所有输入事件都写成“经过机器学习分类”。

`InputDispatcher` 之后，事件通过 socket-based `InputChannel` 送到目标进程。应用侧的 native `InputConsumer` 位于 `InputTransport.cpp`，Java 入口由 `InputEventReceiver` 承接。触摸批处理可在接近 VSync 时由 `ViewRootImpl` 消费；普通输入消息、应用业务处理、HWUI 出图和 display present 仍属于后续时间区间。

## 2. Kernel 输入边界

以下链接固定到 `android17-6.18-2026-06_r6`：

- [`drivers/input/input.c`](https://android.googlesource.com/kernel/common/+/refs/tags/android17-6.18-2026-06_r6/drivers/input/input.c)：Linux input core 的设备、handler 与 event 分发基础；
- [`include/uapi/linux/input-event-codes.h`](https://android.googlesource.com/kernel/common/+/refs/tags/android17-6.18-2026-06_r6/include/uapi/linux/input-event-codes.h)：`EV_*`、`KEY_*`、`ABS_*` 等 UAPI event code；
- [`Documentation/input/event-codes.rst`](https://android.googlesource.com/kernel/common/+/refs/tags/android17-6.18-2026-06_r6/Documentation/input/event-codes.rst)：事件类型、同步报告和 multi-touch 语义。

kernel 时间戳只能说明事件在 input/evdev 边界的时序。目标窗口选择、焦点、触摸区域、手势策略和 ANR 归责发生在 Android framework/native 层，不能从 evdev 事件单独推导。

## 3. Native InputFlinger 源码

### 3.1 设备发现与事件读取

- [`EventHub.cpp`](https://android.googlesource.com/platform/frameworks/native/+/android-17.0.0_r1/services/inputflinger/reader/EventHub.cpp)：打开 `/dev/input/event*`、读取 epoll 事件、设备增删与 raw event；
- [`InputReader.cpp`](https://android.googlesource.com/platform/frameworks/native/+/android-17.0.0_r1/services/inputflinger/reader/InputReader.cpp)：消费 EventHub 事件、维护设备与 mapper、向 listener chain 发出 `Notify*Args`；
- [reader mapper 目录](https://android.googlesource.com/platform/frameworks/native/+/android-17.0.0_r1/services/inputflinger/reader/mapper/)：触摸、键盘、鼠标、旋钮等设备类型的协议映射。

阅读 `InputReader` 时应把硬件采样率、kernel event time、reader loop 和 mapper 输出分开。应用收到的 `MotionEvent` 可能经过 batching、resampling 或 prediction，原始采样点与显示反馈也不会共享同一个完成时间。

### 3.2 过滤、指针管理与分类

- [`UnwantedInteractionBlocker.cpp`](https://android.googlesource.com/platform/frameworks/native/+/android-17.0.0_r1/services/inputflinger/UnwantedInteractionBlocker.cpp)：手掌拒绝、stylus/touch 冲突与相关 feature flag；
- [`InputFilter.cpp`](https://android.googlesource.com/platform/frameworks/native/+/android-17.0.0_r1/services/inputflinger/InputFilter.cpp)：C++ wrapper、Rust input filter、bounce/slow/sticky keys 配置；
- [`rust/`](https://android.googlesource.com/platform/frameworks/native/+/android-17.0.0_r1/services/inputflinger/rust/)：Android 17 的 Rust filter 实现；
- [`PointerChoreographer.cpp`](https://android.googlesource.com/platform/frameworks/native/+/android-17.0.0_r1/services/inputflinger/PointerChoreographer.cpp)：pointer display、cursor controller 与相关设备状态；
- [`InputProcessor.cpp`](https://android.googlesource.com/platform/frameworks/native/+/android-17.0.0_r1/services/inputflinger/InputProcessor.cpp)：motion classification service 连接、事件队列与 classification 更新。

Rust 组件位于 filter 分支，没有替换 `EventHub`、`InputReader` 或 `InputDispatcher`。描述“InputFlinger Rust 化”时，应写明具体 module 和受影响的 event 类型。

### 3.3 目标选择、分发与超时

- [`InputDispatcher.cpp`](https://android.googlesource.com/platform/frameworks/native/+/android-17.0.0_r1/services/inputflinger/dispatcher/InputDispatcher.cpp)：焦点与 touched window 目标、inbound queue、connection wait queue、dispatch cycle、stale event 与 ANR；
- [`InputTransport.cpp`](https://android.googlesource.com/platform/frameworks/native/+/android-17.0.0_r1/libs/input/InputTransport.cpp)：`InputPublisher`、`InputConsumer`、消息序列号和 finish signal；
- [`InputThread.cpp`](https://android.googlesource.com/platform/frameworks/native/+/android-17.0.0_r1/services/inputflinger/InputThread.cpp)：native 输入线程循环与调度属性。

分析 InputDispatcher 时要区分：

- 事件尚在 inbound queue；
- 已找到目标，等待 connection 可写或应用确认；
- 焦点窗口不存在或尚未就绪；
- 事件因 stale、policy、drop reason 或安全约束被丢弃；
- 目标应用未在 timeout 内完成输入处理。

“InputDispatcher 慢”无法描述上述状态差异。trace、dumpsys 与日志应指向具体 queue、connection、target 和 drop/timeout reason。

## 4. Framework 与应用进程入口

- [`InputManagerService.java`](https://android.googlesource.com/platform/frameworks/base/+/android-17.0.0_r1/services/core/java/com/android/server/input/InputManagerService.java)：system_server 输入策略、native service 连接、monitor/filter 与设备管理；
- [`InputEventReceiver.java`](https://android.googlesource.com/platform/frameworks/base/+/android-17.0.0_r1/core/java/android/view/InputEventReceiver.java)：应用或系统组件接收 InputChannel 事件的 Java 抽象；
- [`ViewRootImpl.java`](https://android.googlesource.com/platform/frameworks/base/+/android-17.0.0_r1/core/java/android/view/ViewRootImpl.java)：窗口输入 stage、batched input consumption、pointer event 与 traversal 协作；
- [`Choreographer.java`](https://android.googlesource.com/platform/frameworks/base/+/android-17.0.0_r1/core/java/android/view/Choreographer.java)：VSync callback 与 `CALLBACK_INPUT` 调度。

`Choreographer.CALLBACK_INPUT` 不等于 native InputReader/InputDispatcher 的全部执行时间。它用于应用帧内的输入 callback 阶段；事件从 kernel 到应用进程的前半段应从 InputFlinger 和 InputTransport 取证。

## 5. 系统手势、返回与 IME

- [`OnBackInvokedDispatcher.java`](https://android.googlesource.com/platform/frameworks/base/+/android-17.0.0_r1/core/java/android/window/OnBackInvokedDispatcher.java)：应用侧 back callback 注册与优先级接口；
- [`BackNavigationController.java`](https://android.googlesource.com/platform/frameworks/base/+/android-17.0.0_r1/services/core/java/com/android/server/wm/BackNavigationController.java)：WindowManager 中的 back navigation、动画目标和 transaction 协作；
- [`InputMethodManager.java`](https://android.googlesource.com/platform/frameworks/base/+/android-17.0.0_r1/core/java/android/view/inputmethod/InputMethodManager.java)：应用侧输入法会话、focus 与 show/hide 请求；
- [`InputMethodManagerService.java`](https://android.googlesource.com/platform/frameworks/base/+/android-17.0.0_r1/services/core/java/com/android/server/inputmethod/InputMethodManagerService.java)：system_server 的 IME client/session、target window 与显示策略。

Predictive Back 和 IME 问题都跨越输入、窗口、动画与渲染。回调到达、SurfaceControl transaction 提交和动画 present 是不同证据点。

## 7. 使用这些资料时的证据顺序

一条输入延迟结论应按时间顺序回答：

1. 哪个 input device 产生了哪类 kernel event，event time 是什么；
2. EventHub 和 InputReader 何时读取并转换事件；
3. listener chain 是否过滤、修改、分类或丢弃了事件；
4. InputDispatcher 选中了哪个 window/connection，是否发生 queue wait；
5. 目标进程何时收到并 finish 事件；
6. 应用何时改变 UI 状态并提交新 buffer；
7. SurfaceFlinger 何时 latch，display 何时 present。

前五项属于输入投递，后两项属于视觉反馈。只测 `MotionEvent.eventTime` 到业务 callback 的间隔，只能覆盖输入到应用；把它称为“触摸到显示延迟”会遗漏渲染与显示时间。
