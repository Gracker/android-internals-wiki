## 📊 源码调研补充（2026-07-10）

基于 `android-17.0.0_r1` 源码拉取 + Linux v6.12 内核核对，本节"三层协作闭环"的具体源码锚点如下：

### 🔧 Framework 层：PowerManagerService DIRTY 位图状态机

**源码位置**：`frameworks/base/services/core/java/com/android/server/power/PowerManagerService.java`（android-17.0.0_r1，行号 210–2791）

- 18 个 DIRTY_* 标志位（`1 << 0` 到 `1 << 17`，注意 `1 << 13` 与 `1 << 15` 是历史预留位，Android 12 后废弃）
- `updatePowerStateLocked()` 三阶段增量更新：`updateIsPoweredLocked → updateStayOnLocked → updateScreenBrightnessBoostLocked` 串行 phase1，`mDirty = 0` 重置后 phase2/phase3
- **`setPowerModeInternal()` 闸门**（PowerManagerService.java:5004–5010）：

```java
private boolean setPowerModeInternal(int mode, boolean enabled) {
    if (mode == Mode.LAUNCH && enabled && mBatterySaverStateMachine != null
            && mBatterySaverStateMachine.getBatterySaverController().isLaunchBoostDisabled()) {
        return false;
    }
    return mNativeWrapper.nativeSetPowerMode(mode, enabled);
}
```

**关键发现**：`Mode.LAUNCH` Boost 在 BatterySaver 启用时被 `BatterySaverController.isLaunchBoostDisabled()` 屏蔽——这是 §15.1 闭环的"策略层否决权"，厂商 HAL 无权修改此过滤。

### 🔧 HAL 层：IPower AIDL v7 + IPowerStats AIDL v2 双通道

**IPower AIDL v7**（`hardware/interfaces/power/aidl/android/hardware/power/IPower.aidl`，android-17.0.0_r1）：
- **18 种 Mode**：DOUBLE_TAP_TO_WAKE / LOW_POWER / SUSTAINED_PERFORMANCE / FIXED_PERFORMANCE / VR / LAUNCH / EXPENSIVE_RENDERING / INTERACTIVE / DEVICE_IDLE / DISPLAY_INACTIVE / AUDIO_STREAMING_LOW_LATENCY / CAMERA_STREAMING_SECURE-LOW-MID-HIGH / GAME / GAME_LOADING / DISPLAY_CHANGE / AUTOMOTIVE_PROJECTION
- **6 种 Boost**：INTERACTION / DISPLAY_UPDATE_IMMINENT / ML_ACC / AUDIO_LAUNCH / CAMERA_LAUNCH / CAMERA_SHOT
- 关键扩展：**HintSession 通道**（`createHintSessionWithConfig()` + `getSessionChannel()` FMQ + `getHintSessionPreferredRate()` 默认 1ms）+ **CPU/GPU Headroom**（`getCpuHeadroom(CpuHeadroomParams)` / `getGpuHeadroom(GpuHeadroomParams)`）

**IPowerStats AIDL v2**（`hardware/interfaces/power/stats/aidl/Android.bp`，android-17.0.0_r1，`frozen: true`）：
- `getPowerEntityInfo()` — SoC 电源域清单（GPU/CODEC/Modem/Display）
- `getStateResidency()` — 状态驻留累计时长
- `getEnergyConsumed()` — 能耗累计（μC 库仑）
- `readEnergyMeter()` — 即时能耗读数（FMQ 通道）
- `vendor_available: true`——厂商必须实现，无 fallback

**SupportInfo 位图协商**（`SupportInfo.aidl`）：
- `HeadroomSupportInfo.cpuMinCalculationWindowMillis = 50` / `cpuMaxCalculationWindowMillis = 10000`
- `cpuMaxTidCount = 5`——单次最多跟踪 5 个 TID
- `CpuHeadroomResult.union { float globalHeadroom }`——NaN 表示不可用，[0,100] 表示余量百分比

**AOSP 参考实现**（`hardware/interfaces/power/aidl/default/Power.cpp`）：
- `setMode/setBoost` 默认空操作（仅 `LOG(VERBOSE)`）
- `getCpuHeadroom/getGpuHeadroom` 默认 `EX_UNSUPPORTED_OPERATION`
- `getSupportInfo` 用 `bitsForEnum<Mode/Boost>()` 生成全 1 位图（声明"全能力"，但实际未实现）

### 🔧 Kernel 层：cpufreq_schedutil 三函数决策链

**源码位置**：`kernel/sched/cpufreq_schedutil.c`（Linux v6.12）

1. **守门 `sugov_should_update_freq()`**：`rate_limit_us` 默认 1000μs（1ms），防 DVFS 抖动
2. **计算 `get_next_freq()`**：公式 `next_freq = C × max_freq × util / max`，`C = 1.25` 在 `util/max = 0.8` 处翻车
3. **执行 `cpufreq_driver_fast_switch()` vs `sugov_deferred_update()`**：硬件直写路径（< 10μs）vs kthread 异步路径（100μs~1ms）

**v6.12 新增 sched-ext 兼容**（`sugov_get_util()`）：
```c
static unsigned long sugov_get_util(struct sugov_cpu *sg_cpu, unsigned long boost) {
    unsigned long min, max, util = scx_cpuperf_target(sg_cpu->cpu);  // 优先取 BPF 调度器目标
    util = max(util, boost);
    sg_cpu->bw_min = min;
    sg_cpu->util = sugov_effective_cpu_perf(sg_cpu->cpu, util, min, max);
}
```

`scx_cpuperf_target()` 优先于 CFS 利用率计算——这是 sched-ext 接管后 schedutil 仍能正常工作的关键兼容路径，详见 §17.4（sched-ext/OEM BPF）。

### 🔁 三层闭环调用链（自上而下）

```
PowerManager.setPowerMode(MODE_LOW_POWER, true)           [SystemApi]
  ↓
PowerManagerService.setPowerModeInternal(LOW_POWER, true)  [Framework 闸门]
  ↓
PowerManagerService.nativeSetPowerMode(LOW_POWER, true)    [JNI]
  ↓
HalController::setMode() → binder → vendor IPower::setMode()
  ↓ (SoC 厂商实现差异)
vendor impl  → /dev/cpuctl/<tgid>/cpu.shares + schedutil rate_limit_us
  ↓
enqueue_task_fair() → cpufreq_update_util() → sugov_update_single_freq()
  ↓
sugov_should_update_freq() 守门 → get_next_freq() 计算 → cpufreq_driver_fast_switch()
```

### ⚡ 性能数据（基于 §17.21 中 2026-07-09 调研）

- setMode/setBoost binder 延迟 < 20ms
- HintSession FMQ 通道延迟比 binder IPC 低约 60%
- DVFS fast_switch 路径延迟 < 10μs（高通 Cpufreq-HW / MTK MT_CPUDVFS）
- schedutil rate_limit 默认 1ms（即 DVFS 下发最快频率）
