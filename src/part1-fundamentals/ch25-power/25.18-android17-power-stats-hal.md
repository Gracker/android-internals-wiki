## 1. Power Stats HAL 的职责

`android.hardware.power.stats.IPowerStats` 是只读统计 HAL。它报告自开机累计的能量和状态驻留数据，不接收 boost、performance mode、thermal policy 或频率请求。

Android 17 中需要区分两个 VINTF AIDL HAL：

| 接口 | 方向 | 主要用途 |
|---|---|---|
| `android.hardware.power.IPower` | Framework 向 vendor 发送 hint/session 请求 | 控制性能与能效策略 |
| `android.hardware.power.stats.IPowerStats` | Framework 从 vendor 读取累计统计 | 观测策略结果与做功耗归因 |

`IPowerStats` 的数据可以帮助验证 Power HAL、scheduler、cpuidle 或固件策略产生了什么结果，但它不会自行修改这些策略。完整的控制与观测分层见 [5.21 Android 17 电池优化与 SoC 架构](../ch05-cpu-power/5.21-android17-battery-optimization-soc-architecture.md)。

## 2. 版本边界

Power Stats HAL 从 Android 10 起成为独立接口族。Android 10、11 常见 HIDL 1.0；后续平台加入稳定 AIDL 接口。Android 17 的 `aidl_api/android.hardware.power.stats/` 保留版本 1、版本 2 与 current，Framework 把当前 AIDL 路径称为 PowerStats HAL 2.0。

因此，Android 17 的事实是“继续使用冻结的 AIDL v2 合约”，没有新增一套 ML 功耗预测 HAL。Framework 的 `PowerStatsHALWrapper` 会优先连接：

```text
android.hardware.power.stats.IPowerStats/default
```

连接不到 AIDL v2 时，Android 17 Framework 仍有 HIDL 1.0 JNI wrapper 作为兼容路径。产品是否声明服务，要看 VINTF manifest；`vendor_available: true` 也不强制每台设备提供该 HAL。

## 3. 六个 AIDL 方法

Android 17 的 [`IPowerStats.aidl`](https://android.googlesource.com/platform/hardware/interfaces/+/refs/tags/android-17.0.0_r1/power/stats/aidl/android/hardware/power/stats/IPowerStats.aidl) 定义六个方法：

```aidl
PowerEntity[] getPowerEntityInfo();
StateResidencyResult[] getStateResidency(in int[] powerEntityIds);

EnergyConsumer[] getEnergyConsumerInfo();
EnergyConsumerResult[] getEnergyConsumed(in int[] energyConsumerIds);

Channel[] getEnergyMeterInfo();
EnergyMeasurement[] readEnergyMeter(in int[] channelIds);
```

三组 API 都采用“先取元信息，再按 ID 读累计值”的模式。读数方法传入空 ID 数组时请求所有可用对象；传入非法 ID 应返回 `EX_ILLEGAL_ARGUMENT`。接口文档还允许某个有效对象的结果暂时缺失，客户端不能假设返回数组与请求数组永远等长。

### 3.1 `PowerEntity`：状态驻留

`PowerEntity` 表示平台子系统、外设或 power domain。它包含设备定义的 `name` 和一组 `State`。`getStateResidency()` 返回每个状态：

- `totalTimeInStateMs`：自开机累计驻留毫秒数；
- `totalStateEntryCount`：自开机累计进入次数；
- `lastEntryTimestampMs`：该状态最近一次进入时的 `CLOCK_BOOTTIME` 毫秒时间。

状态驻留描述“在各状态待了多久”，没有直接给出这些状态消耗多少能量。把 residency 乘以实验室 power profile 可以建立软件模型，但模型、校准和误差处理位于 HAL 合约之外。

### 3.2 `EnergyConsumer`：逻辑能耗对象

`EnergyConsumer` 是 Framework 可识别的逻辑对象。它包含 `id`、`ordinal`、`type` 和 vendor-specific `name`。同一 type 有多个实例时，ordinal 必须从 0 开始连续编号。

Android 17 的 [`EnergyConsumerType`](https://android.googlesource.com/platform/hardware/interfaces/+/refs/tags/android-17.0.0_r1/power/stats/aidl/android/hardware/power/stats/EnergyConsumerType.aidl) 有八种值：

- `OTHER`
- `BLUETOOTH`
- `CPU_CLUSTER`
- `DISPLAY`
- `GNSS`
- `MOBILE_RADIO`
- `WIFI`
- `CAMERA`

标准枚举没有 GPU 或 NPU。厂商可以用 `OTHER` 加设备私有名称表示相关对象，也可能把 GPU、内存和总线放在共享 rail 或组合模型中。这样的结果不能按名称直接跨机型对齐。

`EnergyConsumerResult` 返回：

- `timestampMs`：采集时的 `CLOCK_BOOTTIME` 毫秒时间；
- `energyUWs`：自开机累计能量，单位微瓦秒；
- 可选 `attribution[]`：按 Android ID/Linux UID 分配的累计能量。

所有 attribution 能量之和必须小于或等于 consumer 总量。字段存在不代表设备一定填充 UID attribution，也不代表共享 rail 已有准确的软件分摊。

### 3.3 `Channel`：硬件计量通道

`Channel` 更接近 ODPM 的 bus、sense resistor 或 power rail。它包含 `id`、vendor-specific `name` 和 `subsystem`。`readEnergyMeter()` 返回 `EnergyMeasurement`：

- `timestampMs`：采集时刻；
- `durationMs`：这份能量读数的累计窗口；
- `energyUWs`：累计能量。

EnergyConsumer 可以来自一个或多个 Channel，也可以来自软件模型；Channel 也可能覆盖多个逻辑组件。两张表没有标准的一一映射关系。

## 4. 累计能量怎样换算平均功率

`energyUWs` 是累计能量，不是瞬时功率。对同一 ID 取得两个有效样本后，可以计算时间窗口内的平均功率。

```text
deltaEnergyUWs = energyUWs(t2) - energyUWs(t1)
deltaTimeMs    = timestampMs(t2) - timestampMs(t1)

averagePowerMw = deltaEnergyUWs / deltaTimeMs
```

单位换算成立是因为 `µW·s / ms = mW`。计算前要检查 ID 相同、时间递增、能量没有回退、两个样本来自同一次开机，并处理 `ENERGY_UNAVAILABLE`、结果缺失和计数器重置。

平均值会掩盖窗口内的峰值。若 HAL 或 Framework 的缓存周期较长，一次很短的相机启动、GPU burst 或 modem tail 会被摊进整个窗口。毫秒级瞬态分析仍要结合 trace marker、硬件计数器或外接功耗仪。

## 5. Framework 怎样消费 HAL

Android 17 的 [`PowerStatsHALWrapper.java`](https://android.googlesource.com/platform/frameworks/base/+/refs/tags/android-17.0.0_r1/services/core/java/com/android/server/powerstats/PowerStatsHALWrapper.java) 把 AIDL v2 与 HIDL 1.0 包成统一内部接口。AIDL 连接使用 `waitForDeclaredService()`，binder death 后会清理缓存并重新连接。

[`PowerStatsService.java`](https://android.googlesource.com/platform/frameworks/base/+/refs/tags/android-17.0.0_r1/services/core/java/com/android/server/powerstats/PowerStatsService.java) 发布 `powerstats` Binder 服务；HAL 可用时还发布 `PowerStatsInternal`，供 system_server 内部异步读取：

- `getEnergyConsumedAsync()`；
- `getStateResidencyAsync()`；
- `readEnergyMeterAsync()`。

Framework 客户端包括：

- BatteryStats/PowerStats collectors，用 measured energy 改善组件与 UID 归因；
- statsd pull atoms；
- PowerStatsLogger 的周期或电池事件记录；
- Perfetto 的 `android.power` 数据源；
- API 35 起的 `SystemHealthManager` PowerMonitor API。

这些客户端有各自的调度、缓存和失败策略。HAL 本身没有“动态采样频率”RPC，也没有向 vendor 下发采样周期。

## 6. 普通应用看到的 PowerMonitor

API 35 起，[`SystemHealthManager`](https://developer.android.com/reference/android/os/health/SystemHealthManager) 可以异步列出 `PowerMonitor` 并读取累计能量。Monitor 包括 modeled EnergyConsumer 和 raw ODPM measurement；设备不支持时列表可以为空。

Android 17 的服务实现有两档 freshness：

| 调用方 | 最大缓存年龄 | 返回处理 |
|---|---:|---|
| 普通调用方 | 20 秒 | 在相邻累计值区间内加入按 UID 稳定的随机化，降低细粒度侧信道 |
| 持有 `ACCESS_FINE_POWER_MONITORS` | 250 毫秒 | 返回 fine granularity |

`ACCESS_FINE_POWER_MONITORS` 是 `signature|privileged|development` 权限，普通第三方应用不能依赖。公开 API 返回的累计能量同时包括电池供电和插电期间，不能直接等同于电池放电量。

`PowerMonitor` 的 index 不保证跨重启稳定，不应持久化。调用方应在每次进程或设备启动后重新枚举，并把 monitor name、type、设备型号、build fingerprint 和采样窗口写进实验记录。

## 7. OEM 差异来自哪里

AIDL 统一了结构、单位、异常和稳定性边界，无法统一硬件电源树。OEM 差异主要来自：

1. PMIC/SoC 是否有 ODPM 或等价能量累加器；
2. firmware 是否能低成本提供 subsystem residency；
3. vendor kernel、sysfs、mailbox 或共享内存如何暴露计数；
4. rail 怎样覆盖 CPU cluster、GPU、DDR、modem、Wi-Fi 等电源域；
5. EnergyConsumer 使用硬件累计、软件模型还是混合结果；
6. 是否提供 UID attribution；
7. 计数器的位宽、分辨率、更新时机和 suspend 行为；
8. 服务是否在 VINTF manifest 中声明并通过 VTS。

AOSP `power/stats/aidl/default/` 提供 `FakeEnergyMeter`、`FakeEnergyConsumer` 和 `FakeStateResidencyDataProvider` 示例。它们用于接口开发和测试，不能代表 Pixel 或其他量产设备的 rail。

厂商若复用 AOSP `PowerStats` helper，可以通过 `setEnergyMeter()`、`addEnergyConsumer()` 和 `addStateResidencyDataProvider()` 组装实现；也可以自行实现 `BnPowerStats`。这些 C++ helper 是参考实现入口，不是每家 OEM 必须采用的内部架构。

## 8. 精度与一致性检查

一份可用的 Power Stats 实现至少要验证：

- 同一 ID 的 `timestampMs` 单调递增；
- 自开机累计 `energyUWs` 不应无解释回退；
- state 总驻留时间与设备 uptime/suspend 语义相符；
- `lastEntryTimestampMs` 不晚于当前 `CLOCK_BOOTTIME`；
- 同类型 consumer 的 ordinal 连续；
- attribution 总和不超过 consumer 总能量；
- 空 ID 请求、单 ID 请求、非法 ID 和暂时缺数都符合契约；
- suspend/resume、HAL 重启和计数器 wrap 后没有巨大伪增量；
- 读取本身不会频繁唤醒休眠子系统；
- 4 KB/16 KB kernel、不同 SoC SKU 和不同电源配置分别验证。

不同 rail 的硬件采样时刻可能不完全同步。要做多 rail 求和或差分时，应比较各自 `timestampMs`/`durationMs`，不能仅按 Binder 返回时间假定同一快照。

## 9. 设备核查步骤

下面的命令用于确认 Framework 服务、VINTF HAL 和可见数据。

```bash
adb shell service list | grep -i powerstats
adb shell dumpsys powerstats
adb shell 'getprop ro.vendor.api_level'
adb shell 'cat /vendor/etc/vintf/manifest.xml 2>/dev/null | grep -A8 -B2 power.stats'
```

`dumpsys powerstats` 的可见内容和权限随 build 类型变化。VINTF manifest 还可能拆在多个 fragment 中，只检查单一 XML 不能覆盖所有设备。

Perfetto 的 `android.power` 数据源可以请求 power rails：

```text
data_sources {
  config {
    name: "android.power"
    android_power_config {
      battery_poll_ms: 250
      collect_power_rails: true
    }
  }
}
```

这里的 250 ms 是 Perfetto 请求的轮询间隔，不是 HAL 对硬件采样率的承诺。官方 [Power data sources](https://perfetto.dev/docs/data-sources/battery-counters) 文档也说明 ODPM 需要专用硬件，rail 的存在与分辨率由设备厂商决定。

## 10. 报告中应保留哪些信息

跨版本或跨 OEM 比较时，至少记录：

- Android build fingerprint 与 `android-17.0.0_r1` 的偏离；
- Power Stats AIDL/HIDL 路径和接口版本；
- EnergyConsumer、Channel、PowerEntity 的完整元信息；
- page/kernel/vendor build 与 firmware 版本；
- 电池/USB 状态、屏幕亮度、网络、温度和测试场景；
- 原始累计读数、时间戳、缺失样本与计算脚本；
- PowerMonitor 是否为 coarse/fine granularity；
- 外接功耗仪或电池 fuel gauge 的交叉验证。

同名 rail 在两台设备上可能覆盖不同电源域；不同名 rail 也可能测量相同物理路径。跨设备汇总前要有电源树或 vendor 文档证据，不能只按字符串归类。
