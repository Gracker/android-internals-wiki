## 1. 先把“沙箱”和“复用”拆开

端侧 Agent 可以运行在应用进程、同 UID 的独立进程、isolated service、系统服务或厂商推理服务中。每种部署方式的身份、权限、内存归属和生命周期不同。“运行 AI”本身不会创建一种新的 Linux 内存域。

跨应用复用还包含三个独立问题：

1. 调用方是否获准访问数据；
2. 两个进程是否映射同一批物理页或同一个 buffer；
3. 推理 runtime 或加速器驱动是否又生成私有副本。

Binder 权限检查或 URI grant 只能回答第一项。两个进程映射同一个 fd 可以减少 CPU 侧副本，仍不能证明 NPU/GPU 导入时没有重排、量化、解压或设备私有分配。

## 2. Android 17 的隔离边界

| 部署方式 | 身份与地址空间 | 适用边界 |
|---|---|---|
| 应用主进程内推理 | 应用 UID、主进程地址空间 | 调用简单；模型、KV cache 与 UI 共享进程内存上限和故障域 |
| `android:process=":inference"` | 通常仍是应用 UID，单独 PID | 隔离地址空间和 native crash；不形成跨 UID 安全边界 |
| isolated service | 独立 isolated UID 与 PID | 权限和文件访问收窄，所需 fd 与能力要经受控 IPC 传入 |
| SDK Runtime / 其他专用沙箱 | 由对应平台组件定义身份和服务范围 | 不能用普通 isolated service 的规则替代其合同 |
| 系统或 vendor 推理服务 | 服务自己的 UID、SELinux domain 和进程 | 能力、缓存、优先级和硬件访问由系统映像与 vendor 策略决定 |

Android 17 仍使用进程地址空间、UID、SELinux domain、Binder 身份、cgroup、AMS 进程状态与 lmkd 作为通用隔离和回收基础。AOSP 没有一个“Agent 身份”让进程自动得到固定 quota、oom adj 或更高存活优先级。

同 UID 的独立进程适合故障隔离和整进程回收，但同一应用身份仍能访问应用获准的资源。isolated service 的限制更强，宿主应只传入完成一次请求所需的句柄和元数据。

## 3. 跨进程数据怎样传

### Binder 负责控制面

Binder 适合请求参数、状态、句柄与结果元数据。大模型权重、图像、音频块或 tensor 不应直接塞进 transaction buffer。Android 17 的 [`Parcel.cpp`](https://android.googlesource.com/platform/frameworks/native/+/refs/tags/android-17.0.0_r1/libs/binder/Parcel.cpp) 支持随 Binder 传递文件描述符，接收端再映射或导入目标对象。

服务协议要验证调用 UID、对象类型、offset、length、格式、版本和访问模式。文件描述符已经送达，也不代表接收端可以忽略内容校验；恶意长度和竞态仍可能导致越界、资源耗尽或解析漏洞。

### `SharedMemory` 共享匿名页

[`SharedMemory`](https://android.googlesource.com/platform/frameworks/base/+/refs/tags/android-17.0.0_r1/core/java/android/os/SharedMemory.java) 封装 ashmem/memfd 风格的共享区域，可通过 `ParcelFileDescriptor` 跨进程传递。生产者写完后可以降低 protection，再把只读 fd 交给消费者。

共享区需要明确所有权和关闭顺序：

- 谁创建并保持 backing fd；
- 写入完成后何时切换为只读；
- 每个进程何时 `unmap()` 和 `close()`；
- 请求取消、Binder death 或超时时谁释放引用；
- 数据版本变化时怎样避免消费者读到半成品。

`SharedMemory` 适合 CPU 可寻址的普通页。它没有自带对象序列化、版本管理、租户 quota 或缓存淘汰策略。

### `HardwareBuffer` 服务图形与硬件共享

[`HardwareBuffer`](https://android.googlesource.com/platform/frameworks/base/+/refs/tags/android-17.0.0_r1/core/java/android/hardware/HardwareBuffer.java) 可跨进程传递由 gralloc 分配的 buffer，并被 CPU、GPU、camera、codec 或其他硬件路径使用。格式、usage、stride、同步 fence 与驱动导入能力都需要由协议约束。

共享同一个 `HardwareBuffer` 可以避免一部分像素复制，但它不适合作为任意模型对象容器。某些加速器仍会为 tensor 建立私有布局或内存，收益要用目标 runtime 和 driver 测量。

### ContentProvider、URI 与 App Functions

跨应用持久数据通常使用 ContentProvider 与临时 URI grant；平台级应用能力调用可以使用 Android 17 的 App Functions 合同。[`AppFunctionManager`](https://android.googlesource.com/platform/frameworks/base/+/refs/tags/android-17.0.0_r1/core/java/android/app/appfunctions/AppFunctionManager.java) 负责发现和执行应用声明的 function，不提供任意内存互访，也不会自动共享调用双方的模型缓存。

选择接口时，应先确定数据是否持久、是否需要流式读取、谁负责授权和撤销、是否跨 user/profile，再决定传 fd、URI 或结构化参数。

## 4. 共享页怎样记账

RSS 会在每个映射进程中完整计入共享驻留页，直接相加会重复。PSS 按映射者数量分摊共享页，更适合估算多个进程对物理内存的合计压力。USS 则更接近某进程独占页。

模型服务还可能同时占用：

- Java/Kotlin heap；
- native heap；
- file-backed model mapping；
- anonymous activation 与 KV cache；
- dma-buf、GPU/NPU driver memory；
- zram/swap 中的匿名页；
- runtime 编译或权重重排缓存。

因此，“模型文件只映射一次”不足以证明总内存只保留一份。评估复用时应比较所有相关进程的 PSS 总和、page fault、复制字节、dma-buf/driver 计数、加载时延和峰值工作集。

## 5. 回收与进程优先级

Android 17 的 [`MemoryLimiter`](https://android.googlesource.com/platform/frameworks/base/+/refs/tags/android-17.0.0_r1/services/core/java/com/android/server/am/MemoryLimiter.java) 与 lmkd 面向进程状态、设备配置和内存压力工作，不根据通用“AI Agent”标签分配资源。

服务进程的 oom adj 会随组件状态、绑定关系和调用方重要性变化。某个 vendor 推理服务是否常驻、是否被 freezer 处理、是否在内存限制白名单中，都应从目标产品配置和运行状态确认。产品实现不能外推成 Android 17 平台保证。

## 6. 安全和性能应一起验证

一条跨应用推理通路至少需要检查：

- Binder 调用方身份、导出属性、权限与 SELinux allow 规则；
- fd/URI 的访问模式、长度、格式、生命周期和撤销；
- 多 user、work profile 与锁屏状态下的数据边界；
- Binder death、取消、超时和服务重启后的资源释放；
- 映射前后 PSS、缺页、复制量、推理时延和驱动内存；
- 敏感输入是否被日志、缓存、core dump 或持久文件保留。

共享内存优化能减少复制，但会增加所有权、同步与撤销复杂度。数据量小或生命周期短时，普通 Binder/URI 流程可能更容易验证；数据量大且调用频繁时，再评估 fd-backed 共享。
