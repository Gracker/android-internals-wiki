## 1. Hardening 管访问资格，LE Audio 管传输路径

Android 17 的后台音频 hardening 限制 playback、audio focus、音量和铃声模式等交互。它关注应用是否处在用户可感知、具备合格前台服务或得到特定例外的生命周期中。

LE Audio 处理的是 Bluetooth 音频设备、group、Codec、ISO stream、软件或硬件 offload。它会影响延迟、AP 唤醒和射频活动，但不参与 hardening 的 AppOps 判定。

| 问题 | 主要组件 | 结果 |
|---|---|---|
| 后台应用能否播放 | AudioFlinger playback hardening | track 可被静音或写入失败 |
| 后台应用能否请求 focus | `AudioService` / `HardeningEnforcer` | 请求可返回 `AUDIOFOCUS_REQUEST_FAILED` |
| 后台应用能否改音量 | `AudioService` / `HardeningEnforcer` | 调用可被忽略 |
| 音频走 Classic 还是 LE Audio | Audio Policy、Bluetooth profile 与设备能力 | 选择输出设备和 Profile |
| LC3 在 host 还是硬件执行 | Bluetooth Audio HAL、CodecManager、vendor 实现 | HOST 或 ADSP/offload 路径 |
| LE Audio 消耗多少能量 | AP/DSP、Controller、射频、耳机端共同决定 | 需要设备级测量 |

Hardening 可以阻止一次播放；通过 hardening 后也不代表系统一定选择 LE Audio。反过来，耳机已经建立 CIS 也不能绕过应用的后台音频资格。

## 2. Android 17 后台音频规则

Android 17 的[后台音频 hardening 文档](https://developer.android.com/about/versions/17/changes/bg-audio)给出应用可见性和前台服务边界：

- 所有运行在 Android 17 上的应用，后台音频交互需要可见 Activity，或运行一个类型不是 `SHORT_SERVICE` 的 foreground service；
- target API 37 的应用在后台还需要具有 while-in-use 能力的 foreground service；
- 持有精确闹钟能力并操作 `USAGE_ALARM` 音频时，可以进入对应例外；
- playback 与音量修改通常静默受限，audio focus 返回明确的失败码。

while-in-use 能力与“进程里存在一个 foreground service”不是同义词。服务从可见界面、用户操作、媒体按键或系统委托等入口启动时，资格可能不同。应用应让媒体会话和前台服务跟随用户发起的播放生命周期，不能在 `BOOT_COMPLETED` 后偷偷建立长期播放来规避限制。

### Java 控制 API 路径

Android 17 的 [`HardeningEnforcer.java`](https://android.googlesource.com/platform/frameworks/base/+/refs/tags/android-17.0.0_r1/services/core/java/com/android/server/audio/HardeningEnforcer.java) 在 `AudioService` 入口处理 focus、volume 和 ringer mode。它结合两级 control-audio AppOp、调用 UID、特权权限、target SDK、usage、foreground service 状态和兼容 flag 得出允许、partial 或 full enforcement。

partial/full 表示检查哪一级 AppOp，不是“音量减少一部分”与“音量归零”的比例。不同 API 的失败形式也不同：focus 返回失败，volume/ringer 调用可能没有效果，测试 override 可以让部分 Java 路径抛异常。

### Native playback 路径

[`Tracks.cpp`](https://android.googlesource.com/platform/frameworks/av/+/refs/tags/android-17.0.0_r1/services/audioflinger/Tracks.cpp) 在 audioserver 中对 playback track 做 hardening。普通 playback 和 MMAP 路径共享 `AfPlaybackCommon` 的判定，并持续观察相关 AppOp。

Java enforcer 与 AudioFlinger 没有对同一个事件做重复投票：

- Java 路径在控制 API 入口拦 focus 与音量操作；
- native 路径在音频 track 上执行 playback restriction；
- 两边共享 hardening override 和部分政策输入，但对象与失败形式不同。

AudioFlinger 中的 40 ms broadcast delay 只服务 Offload/MMAP permission callback 汇合，不是每个 `AudioTrack` 的创建开销。

## 3. LE Audio 的控制面和数据面

Android 17 的 Bluetooth module 同时管理单播、广播、active group、profile 切换与 codec capability。[`LeAudioService.java`](https://android.googlesource.com/platform/packages/modules/Bluetooth/+/refs/tags/android-17.0.0_r1/android/app/src/com/android/bluetooth/le_audio/LeAudioService.java) 位于 Java service 层，native BTA LE Audio 代码继续处理 ASE、CIG/CIS、Codec 与 HAL 协商。

一条播放路径可以分为：

1. 应用与 AudioFlinger 生成媒体数据；
2. Audio Policy 选择 BLE 输出设备；
3. Bluetooth Audio Provider 建立 software 或 offload session；
4. Bluetooth stack 配置 LC3 与 CIS/BIS；
5. Controller 按 ISO 计划发送；
6. 耳机端缓冲、解码、DSP 后处理并输出。

7.5 ms 或 10 ms 是常见 LC3 frame duration，不能直接当成端到端延迟。AudioTrack/AudioFlinger 缓冲、组帧、ISO schedule、Presentation Delay 和耳机渲染都会增加时间。

## 4. HOST 与 ADSP/offload

Android 17 的 [`codec_manager.cc`](https://android.googlesource.com/platform/packages/modules/Bluetooth/+/refs/tags/android-17.0.0_r1/system/bta/le_audio/codec_manager.cc) 默认使用 `CodecLocation::HOST`。进入 ADSP 路径需要同时满足设备属性、未被持久属性禁用，以及 Bluetooth Audio HAL 报告硬件 offload 能力。

LC3 capability 匹配还会比较 sampling frequency、frame duration、每条 ISO stream 的通道数和每个 codec frame 的字节数。外层继续检查方向、ASE 数量和 preference。

HOST 表示 codec 留在系统 host-side Bluetooth/audio pipeline，不表示由应用进程解码。ADSP 也不承诺零 AP 唤醒；控制、缓冲、路由变化和状态事件仍可能经过 AP。

offload 对功耗的收益取决于：

- host 与 DSP 的 codec 实现效率；
- 每批音频数据的大小和唤醒周期；
- 内存搬运与共享 buffer；
- CIS/BIS 数量、上下行方向与 QoS；
- Controller 和耳机端的射频/DSP 工作；
- thermal、Wi-Fi 共存和信号质量。

AOSP 能证明能力协商路径，不能提供跨设备固定省电比例。

## 5. Suspend 与 background scan

`LeAudioService.setSystemSuspended(true)` 会停止当前 background scan；恢复时只有 `isScannerNeeded()` 满足才重启。start/stop 工作由 scan thread 异步处理，方法返回不代表 Controller 已经同步完成硬件动作。

停止扫描可能减少 AP 或 Controller 工作，但收益还受 scan offload、广告密度、固件和 suspend residency 影响。活跃 LE Audio stream、连接维护与 background scan 也不是同一个活动；停止 scanner 不等于断开正在播放的 CIS。

## 6. 应用迁移

音乐、播客和有声内容应把用户发起的播放交给 Media3 `MediaSessionService` 或等价的 `mediaPlayback` foreground service，并在播放永久结束时停止服务和 session。短暂 buffering 或 `AUDIOFOCUS_LOSS_TRANSIENT` 可以保持会话，永久 focus loss、播放完成或不可恢复错误后应结束。

通信应用应使用 Telecom/音频通信设备 API 管理路由。`BluetoothLeAudio` 的许多 active-device、连接和 codec 控制接口仍受 `@SystemApi`、`@Hide` 或 `BLUETOOTH_PRIVILEGED` 限制，普通应用不能假定自己可以指定 CIS、LC3 参数或 offload location。

应用还应监听设备变化，而不是根据系统版本认定 LE Audio 一定可用。手机能力、耳机能力、Profile 状态、用户选择和产品配置都可能让系统保留 A2DP/HFP 或扬声器路径。

## 7. 怎样诊断

判断“后台没有声音”时，按以下顺序检查：

1. Activity 是否可见，foreground service 是否存在且类型正确；
2. target API 37 时，服务是否获得 while-in-use 能力；
3. `dumpsys audio` 与 logcat 是否出现 `AudioHardening`；
4. focus 请求是否返回失败，playback track 是否被 hardening 静音；
5. hardening 通过后，异常是否落在路由、Codec 或蓝牙连接阶段。

下面的命令按 `android-17.0.0_r1` 的 shell parser 切换测试 override：

```bash
adb shell cmd audio set-hardening enable
adb shell cmd audio set-hardening disable
adb shell cmd audio set-hardening throw
adb shell cmd audio clear-hardening
```

`throw` 会扩大失败影响，只应在隔离测试设备使用。测试结束要执行 `clear-hardening`，恢复默认政策。Android 开发者网页仍可能出现预览期命令名；固定标签中的 `AudioManagerShellCommand.java` 以 `set-hardening` 和 `clear-hardening` 为准。

评估“LE Audio 功耗高”时，要固定手机 build、耳机固件、音量、codec/QoS、上下行方向、屏幕、Wi-Fi、射频环境和温度。至少同时记录：

- HOST/ADSP/offload location；
- scan start/stop 与 suspend/resume；
- HCI/Controller 活动、CIS/BIS 和丢包；
- AudioFlinger/codec CPU time 与 AP idle residency；
- 手机电源轨或外部电源，必要时再测耳机侧电流。

单看 CPU frequency、`batterystats` 百分比或 LC3 frame duration，都不能独立给出 LE Audio 的增量能量。
