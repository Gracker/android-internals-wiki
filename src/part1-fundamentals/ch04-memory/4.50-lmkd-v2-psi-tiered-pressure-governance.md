# 4.50 Android 17 LMKD v2 用户态迁移 + PSI 分层内存压力治理

## 要点

- `LMKD v2` 不是 `android-17.0.0_r1` 中的正式版本名。源码区分 userspace lmkd 与旧 in-kernel LMK，也区分 PSI 的 new strategy 与 memcg v1 的 old strategy。
- Android 17 lmkd 的 PSI trigger 打开全局 `/proc/pressure/memory`，不监听每个 App 的 `memory.pressure`。
- PSI 只负责唤醒。是否 kill 还要结合 zone watermark、有效 free swap、file-cache refault、reclaim 状态和候选进程的 `oom_score_adj`。
- lmkd 不负责向应用发送 `onTrimMemory()`，也没有 `MemoryPressureMonitor`、AppFlow 或 ML 调度器接口。
- `per_app_memcg`、Reaper 的 cgroup kill 与 per-cgroup PSI 是三个不同概念。

## 1. “用户态迁移”和“v2”应怎样理解

AOSP lmkd README 对历史边界的表述很直接：早期 Android 由内核 lowmemorykiller driver 监控压力并选择进程；upstream Linux 4.12 移除该 driver 后，这些职责转到 userspace lmkd。这个迁移早于 Android 17，不能写成 Android 16 或 Android 17 新增能力。

Android 17 启动时仍保留兼容判断：

```text
存在可写的 /sys/module/lowmemorykiller/parameters/minfree
  → 使用旧 in-kernel LMK 接口

否则
  → 初始化 userspace lmkd 的 PSI monitors
```

Android 17 common kernel 锚点 `android17-6.18-2026-06_r6` 不包含旧 lowmemorykiller driver。设备若走旧分支，应继续检查厂商内核源码，不能把该行为归到 common kernel。

`lmkd.cpp` 里也没有 `v1`、`v2` 版本对象。接近这个说法的代码是 `use_new_strategy`：

- new strategy 使用 zone watermark、free swap、thrashing 和 reclaim 状态；
- old strategy 由 `mp_event_common()` 实现，并依赖 memcg v1；
- `use_minfree_levels` 默认 `false`，因此常规 AOSP 配置会选择 new strategy；
- 请求 old strategy 但系统不是 memcg v1 时，初始化会直接失败。

因此，标题中的 “LMKD v2” 只能作为检索旧资料的关键词。分析 Android 17 时，应落到具体函数、属性和数据源。

## 2. PSI 提供什么信息

### 2.1 `some`、`full` 与时间窗口

kernel 6.18 的 `/proc/pressure/memory` 形如：

```text
some avg10=0.12 avg60=0.05 avg300=0.01 total=12345678
full avg10=0.03 avg60=0.01 avg300=0.00 total=3456789
```

- `some` 表示统计区间内至少有一部分任务因内存资源发生停顿；
- `full` 表示所有 non-idle 任务同时停顿，CPU 没有执行有效工作；
- `avg10`、`avg60`、`avg300` 是最近 10、60、300 秒的停顿时间比例；
- `total` 是累计停顿时间，单位为微秒。

`full` 不能简写成“所有进程都在等待分配”。内核定义以 non-idle tasks 为统计对象，内存回收、换页等路径造成的停顿也在范围内。

### 2.2 trigger 与 avg10 是两种观测

用户空间可以向 PSI 文件写入 trigger：

```text
<some|full> <threshold_us> <window_us>
```

例如 `some 70000 1000000` 表示任意 1 秒跟踪窗口内累计 70ms `some` stall 后通知。lmkd 用 trigger fd 加入 epoll；`avg10` 等平均值则在事件处理时重新读取，用于日志或附加判断。

Android 17 new strategy 最终注册两个 trigger：

| 压力档 | 类型 | 普通设备默认值 | low-RAM 默认值 |
| --- | --- | ---: | ---: |
| low | `PSI_SOME` | 关闭 | 关闭 |
| medium | `PSI_SOME` | 70ms / 1s | 200ms / 1s |
| critical | `PSI_FULL` | 700ms / 1s | 700ms / 1s |

critical 50ms 与源码不符。`psi_window_size_ms` 默认 1000；调整窗口时，partial 与 complete stall 也要按测试目标一起评估。

## 3. lmkd 监听的是全局 PSI

`libpsi` 把三个资源固定映射为：

```cpp
static const char* psi_resource_file[] = {
    "/proc/pressure/memory",
    "/proc/pressure/io",
    "/proc/pressure/cpu",
};
```

lmkd 的压力 trigger 选择 `PSI_MEMORY`，因此打开的是全局 `/proc/pressure/memory`。Android 17 这份实现没有遍历 App cgroup，也没有为 UID 或进程注册 `memory.pressure` fd。

cgroup v2 本身支持 `memory.pressure`，这不代表 lmkd 使用了它。两者之间还差一层明确的 userspace 注册、epoll handler 和选择策略；当前源码没有这层代码。

### 3.1 `per_app_memcg` 不是 per-app PSI

`ro.config.per_app_memcg` 控制的是旧 memcg 使用与统计路径。注册 App 时，旧代码可写 soft limit；记录 kill 统计时，`stats_read_memory_stat()` 也会参考该开关。它没有把 per-App PSI 接入 `__mp_event_psi()`。

### 3.2 Reaper 的 cgroup kill 也不是 per-cgroup 压力决策

lmkd 先按全局条件和 `oom_score_adj` 选中一个 `proc`。Reaper 收到目标后优先向该进程对应的 `cgroup.kill` 写 `1`，5.10 兼容路径遍历 `cgroup.procs`；无法使用 cgroup 时回退到 `pidfd_send_signal(SIGKILL)`。

这里使用 cgroup 的目的是把目标进程组清理干净。受害者仍由全局候选表选择，不能写成“哪个 cgroup 的 PSI 最高就优先杀哪个 cgroup”。

## 4. 一次 Android 17 压力决策怎样发生

把 framework、lmkd 与 kernel 放在同一条时间线上，数据流如下：

```text
system_server 计算进程 adj
  → LMK_PROCPRIO / LMK_PROCS_PRIO packet
  → lmkd 按 oom_score_adj 保存候选

kernel PSI trigger
  → libpsi fd 上报 EPOLLPRI
  → mp_event_psi()
  → __mp_event_psi()
  → 读取 meminfo / vmstat / zoneinfo / PSI
  → 结合 swap、thrashing 与 reclaim 状态选择 kill reason
  → find_and_kill_process()
  → Reaper kill + process_mrelease()
```

PSI 事件是判断入口，不是 kill 命令。`__mp_event_psi()` 还会检查：

- free pages 落在 `min`、`low`、`high` 哪个 zone watermark 区间；
- ZRAM-aware 的有效 free swap；
- `workingset_refault_file` 相对于 file-backed page cache 的增长；
- direct reclaim 与 kswapd 是否活跃；
- 上一次 kill 是否仍在等待进程死亡；
- 当前条件允许搜索到的最低 `oom_score_adj`。

PSI trigger 每个窗口最多通知一次。首次事件之后，lmkd 在同一 `psi_window_size_ms` 内按 10ms 或 100ms 间隔复查状态，避免只看单个时间点。等待 pidfd 死亡通知时，复查会暂停。

各 kill reason 的完整判断顺序、thrashing 衰减和 critical stall 边界分别见 [4.15 PSI/LowMemDetector 与 lmkd](15-psi-lowmemdetector-lmkd-architecture.md) 与 [4.36 LMK_PROCS_PRIO 批量命令](4.36-android17-lmkd-procs-prio-batch.md)。

## 5. lmkd 不执行哪些工作

### 5.1 不做通用 proactive reclaim

Android 17 的默认 lmkd 压力路径读取 reclaim 状态并选择牺牲进程。它不会因 medium PSI 事件主动调用 `reclaim` 文件或替 kswapd 回收 page cache。

`lmkd_free_memory_before_kill_hook()` 是明确的 hook；返回正值时 lmkd 可以因为其他位置已经释放内存而跳过 kill。不能据此把默认实现描述成一套通用 proactive reclaim 模式。

kswapd 由内核水位与分配路径驱动。lmkd 观察 kswapd/direct reclaim 状态并参与用户空间 kill，因果方向不能写反。

### 5.2 不发送应用 trim 回调

`onTrimMemory()` 由 framework 的 `AppProfiler`、`CachedAppOptimizer` 等路径经 `IApplicationThread` 发送。lmkd 通过控制 socket 接收进程优先级，选中目标后执行 kill；它没有反向调用 `ApplicationThread.scheduleTrimMemory()`。

因此不存在稳定的三级时间线：

```text
onTrimMemory → cgroup reclaim → lmkd kill
```

应用可能因 UI 隐藏或即将 freeze 收到 trim，也可能在没有新 trim 的情况下被 LMKD 终止。准确的回调边界见 [4.49 trimMemory API 演进](4.49-android17-trim-memory-api-evolution.md)。

### 5.3 不使用 `MemoryPressureMonitor`、AppFlow 或 ML 调度器

`android-17.0.0_r1` 中没有公开的 `MemoryPressureMonitor`、AppFlow、`AppStateException`，也没有“ML 调度器读取 oom_score_adj 分布后决定 fork”的架构。把这些名称放进 lmkd 时序图会制造不存在的依赖。

Android 17 `MemoryLimiter` 是 `system_server` 内独立的进程内存限制策略，使用 cgroup `memory.high`、`memory.swap.high` 和周期检查。它不读取 lmkd 的 PSI trigger，也不向应用提供连续压力回调。

## 6. ZRAM、swap 与 thrashing 的准确关系

lmkd 不控制 ZRAM 压缩算法，也不会从“ZRAM 越满压缩比越差”推导固定 kill 规则。它主要使用三组量：

1. `SwapFree` 与 `SwapTotal`；
2. `swap_free_low_percentage`；
3. 通过 `swap_compression_ratio / swap_compression_ratio_div` 估算的物理内存约束。

有效 free swap 取逻辑 free swap 与下面估算值的较小者：

```text
easy_available_pages × swap_compression_ratio
                     ÷ swap_compression_ratio_div
```

默认 ratio/div 为 1/1。这是配置估算，不是 lmkd 实时读取 ZRAM 压缩率。`swap_util_max` 的 AOSP 默认值是 100，而不是 80。

thrashing 使用 file-backed page cache 的 refault 增长率。它不表示匿名页换入率，也不等于 PSI `full`。PSI 提供停顿，refault 提供工作集反复丢失的证据，两者在 kill 决策中分别判断。

## 7. Android 17 关键属性

下面只列 `android-17.0.0_r1` 源码中可直接定位的默认值：

| 属性后缀 | AOSP 默认值 | 作用 |
| --- | ---: | --- |
| `use_minfree_levels` | `false` | 是否采用旧 minfree 风格 |
| `use_new_strategy` | `low_ram_device || !use_minfree_levels` | 选择 PSI handler 的决策策略 |
| `psi_window_size_ms` | 1000 | trigger 窗口与事件后复查时长 |
| `psi_partial_stall_ms` | 70 / low-RAM 200 | medium `some` trigger |
| `psi_complete_stall_ms` | 700 | critical `full` trigger |
| `swap_free_low_percentage` | 10 | low-swap 判定 |
| `thrashing_limit` | 100 / low-RAM 30 | file refault 基准阈值 |
| `thrashing_limit_decay` | 10 / low-RAM 50 | 成功 kill 后的阈值降幅 |
| `thrashing_limit_critical` | 300 | 是否取消额外的 perceptible 保护 |
| `swap_util_max` | 100 | swap utilization 阈值 |
| `direct_reclaim_threshold_ms` | 0 | 默认关闭 stuck direct reclaim 判断 |
| `lowmem_min_oom_score` | 701 | low-memory fallback 的候选下限 |
| `kill_timeout_ms` | 100 | kill 后的等待/节流配置 |

读取顺序是先看 `persist.device_config.lmkd_native.<name>`，没有值时再看 `ro.lmk.<name>`。只有在 `lmkd.rc` 注册了属性变化 trigger 的项，DeviceConfig 改动才会自动触发 reinit；不能把所有属性都当作即时热更新。

`cached_kill_limit`、`file_inkb`、`dma_inkb` 不是这版 `update_props()` 中的对应属性。设备调优文档应保留 `getprop` 实测值、构建指纹和 workload，避免把厂商值写成 AOSP 默认。

## 8. Watchdog 的紧急路径

Android 17 lmkd 为每次事件 handler 启动 2 秒 watchdog。handler 正常返回后停止 timer；超时则在独立线程执行 `watchdog_callback()`。

回调从 `oom_score_adj=1000` 向 0 搜索有效候选，使用 Reaper 同步 kill 一个进程，写入 `killinfo`，随后使该进程记录失效。它没有重新执行完整的 PSI/watermark/reason 决策，因此应理解为 lmkd 主事件处理超时后的紧急释放路径。

Watchdog 不生成 `reclaim_start/reclaim_end` trace，也不能证明某次普通 kill 的原因来自 PSI。诊断时应单独搜索 `lmkd watchdog timed out!` 日志。

## 9. 可观测性与排查步骤

### 9.1 先确认配置

```bash
adb shell getprop ro.config.low_ram
adb shell getprop ro.lmk.use_minfree_levels
adb shell getprop ro.lmk.use_new_strategy
adb shell getprop ro.lmk.psi_window_size_ms
adb shell getprop ro.lmk.psi_partial_stall_ms
adb shell getprop ro.lmk.psi_complete_stall_ms
adb shell getprop ro.lmk.thrashing_limit
adb shell getprop ro.lmk.swap_free_low_percentage
```

空值表示使用源码默认或其他覆盖来源，不能直接读成 0。

### 9.2 读取同一时段的系统状态

```bash
adb shell cat /proc/pressure/memory
adb shell cat /proc/meminfo
adb shell cat /proc/vmstat
adb shell cat /proc/zoneinfo
```

PSI avg10 适合描述一段时间内的停顿，不存在可通用于所有设备的 1%、5%、15% 用户体验分界。线上阈值需要按机型、RAM/ZRAM 配置和交互场景标定。

### 9.3 关联 kill 证据

lmkd 发出 kill 时使用一个 `ATRACE_INSTANT_FOR_TRACK`，名称格式是：

```text
lmk,<pid>,<kill_reason>,<oom_score_adj>,<min_score_adj>,<max_thrashing>
```

它没有固定输出 `kill_start`、`kill_end`、`pressure_event`、`reclaim_start` 或 `reclaim_end` 这些名称。event log 的 `killinfo` 包含更完整的内存、PSI、thrashing 与 reason 字段；Perfetto 的 `android.memory.lmk` SQL module 可把兼容格式整理为 `android_lmk_events`。

排查时至少回答四个问题：

1. 哪个 PSI trigger 唤醒了 lmkd？
2. 哪个 kill reason 分支命中？
3. 当时允许搜索到的最低 adj 是多少？
4. victim 的 adj、RSS/anon/swap 与进程状态是否匹配预期？

只看到 PSI 升高或某个 App 被杀，都不足以证明该 App 制造了压力。PSI 和 refault 是系统级证据，触发压力的进程与牺牲进程可以不同。
