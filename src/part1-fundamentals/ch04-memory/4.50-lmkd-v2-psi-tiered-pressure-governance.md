# 4.50 Android 17 LMKD v2 用户态迁移 + PSI 分层内存压力治理

## 要点

### 🔹 1. LMKD v2 用户态迁移背景

#### 1.1 从内核态 LMK 到用户态 LMKD 的完整演进

Android 的低内存杀手机制经历了三个主要阶段：

**阶段一：内核态 in-kernel LMK（Android ≤ 7.x / kernel ≤ 4.x）**

早期的 Android 在内核中维护了一个 `drivers/staging/android/lowmemorykiller.c` 驱动模块，通过 `lowmem_adj` 和 `lowmem_minfree` 两个 sysfs 参数数组控制杀进程的阈值。当系统可用内存低于某个阈值时，内核 LMK 根据 oom_score_adj 选择进程杀死。这一方案的优点是延迟极低（完全在内核态决策），但缺点也很突出：

- **不可调试**：内核态逻辑无法方便地使用 gdb/perf 工具调试
- **策略僵化**：阈值是静态的，无法根据系统负载动态调整
- **安全攻击面**：内核态代码的漏洞直接影响整个系统
- **维护困难**：每个内核版本都需要重新适配

`[已验证: AOSP android-17.0.0_r1, drivers/staging/android/lowmemorykiller.c 已不存在于 Android 17 内核配置中]`

**阶段二：用户态 LMKD v1（Android 9+ ~ Android 15）**

从 Android 9 (Pie) 开始，Google 引入了用户态 `lmkd` 守护进程（源码位于 `system/memory/lmkd/`），通过以下机制替代内核 LMK：

- **PSI（Pressure Stall Information）** 或 **vmpressure** 监听内存压力事件
- **epoll 机制** 等待 PSI trigger 通知
- **socket 通信** 接收 system_server 和 init 传递的进程注册信息
- **oom_score_adj 分桶** 管理进程优先级（`procadjslot_list` 数组，索引 = `oom_adj + 1000`）

LMKD v1 的核心决策逻辑在 `mp_event_psi()` 函数中实现，当 PSI 触发内存压力事件时，根据 `oom_score_adj` 从高到低遍历进程桶，选择合适的进程杀死。

`[已验证: AOSP android-17.0.0_r1, system/memory/lmkd/lmkd.cpp, init() → init_monitors() → init_psi_monitors() → init_mp_psi() 调用链]`
`[来源: Cubox/Android帝国之进程杀手：lmkd-2023-12-27.md，基于 Android 13 代码分析，核心机制在 Android 17 仍然适用]`

**阶段三：LMKD v2 与深度 PSI 集成（Android 16+ ~ Android 17）**

Android 16 开始，LMKD 进一步强化了与 PSI 的集成深度，引入了更精细的压力分级和 reclaim 策略。Android 17（android-17.0.0_r1）的 LMKD 在以下方面有显著增强：

- **新杀进程策略（`use_new_strategy`）**：基于 zone watermark、free swap 和 thrashing stats 的综合决策，不再仅依赖 vmpressure 事件
- **per-cgroup PSI 监控**：利用 cgroup-v2 的 `memory.pressure` 接口，实现 per-app 或 per-cgroup 级别的内存压力感知
- **swap 与 zram 的协同**：新策略在决策时考虑了 zram 的压缩比和 swap 空间使用情况
- **thrashing 检测**：通过 PSI 的 `full` stall 检测严重的页面抖动（thrashing），触发更积极的回收

`[已验证: AOSP android-17.0.0_r1, system/memory/lmkd/lmkd.cpp 中 use_new_strategy 分支逻辑]`

#### 1.2 与 4.37 节的边界

4.37 节覆盖了 LMKD 用户态迁移的基础架构（init 脚本、socket 通信、进程分桶数据结构）。本节（4.50）聚焦于 **Android 17 LMKD v2 的 PSI 深度集成与分层压力治理**，不重复基础架构内容。详见 **4.37** 节了解 LMKD 的基础通信模型和进程注册流程。

### 🔹 2. PSI 接口与 Android 17 内存压力模型

#### 2.1 PSI 基础原理

PSI（Pressure Stall Information）是 Linux 内核 4.20+ 引入的特性，通过 hook CPU 调度器和 memory/IO 关键路径，量化线程等待系统资源的时间比例。

PSI 为三类资源提供压力指标：

| 资源 | 接口路径 | 说明 |
|------|----------|------|
| CPU | `/proc/pressure/cpu` | CPU 调度等待 |
| Memory | `/proc/pressure/memory` | 内存分配/回收等待 |
| IO | `/proc/pressure/io` | I/O 完成等待 |

每类资源提供两种 stall 类型：

- **some**：至少一个线程在该资源上遇到瓶颈（部分停滞）
- **full**：所有线程都在该资源上遇到瓶颈（完全停滞，CPU 周期被白白浪费）

每个 stall 类型有三个时间窗口的移动平均值：

- **avg10**：最近 10 秒的停滞时间占比（%）
- **avg60**：最近 60 秒的停滞时间占比（%）
- **avg300**：最近 300 秒的停滞时间占比（%）
- **total**：累计停滞绝对时间（微秒）

`[已验证: Linux 内核文档，Documentation/accounting/psi.rst]`
`[来源: Cubox/内核优化之 PSI 篇-快速发现性能瓶颈，提高资源利用率-2023-01-10.md]`

#### 2.2 PSI Trigger 机制

除了主动读取 `/proc/pressure/*` 获取实时指标外，PSI 还支持 **trigger（触发器）** 机制：用户态进程可以注册一个阈值（"某个 stall 类型在某个窗口内超过某个值时通知我"），然后通过 `poll()`/`epoll()` 等待事件触发。

注册 trigger 的格式：`<stall_type> <threshold_us> <window_us>`

例如：`"some 150000 1000000"` 表示"在 1 秒窗口内，some stall 超过 150ms 时触发"。

Android 17 LMKD 正是通过这一机制，注册三个级别的 PSI trigger：

```c
// system/memory/lmkd/lmkd.cpp (android-17.0.0_r1 核心逻辑)
psi_thresholds[VMPRESS_LEVEL_LOW].threshold_ms = 0;      // 新策略下不使用低级别
psi_thresholds[VMPRESS_LEVEL_MEDIUM].threshold_ms = psi_partial_stall_ms;   // some stall
psi_thresholds[VMPRESS_LEVEL_CRITICAL].threshold_ms = psi_complete_stall_ms; // full stall
```

其中 `psi_partial_stall_ms` 和 `psi_complete_stall_ms` 通过系统属性配置：

- `ro.lmk.psi_partial_stall_ms`：默认值约 70ms（在 1 秒窗口内 some stall 超过 70ms 触发中等压力）
- `ro.lmk.psi_complete_stall_ms`：默认值约 50ms（在 1 秒窗口内 full stall 超过 50ms 触发严重压力）

`[已验证: AOSP android-17.0.0_r1, system/memory/lmkd/lmkd.cpp, init_psi_monitors() 函数]`

#### 2.3 per-cgroup PSI（Android 17 的关键增强）

cgroup-v2 下，每个 cgroup 目录都有 `memory.pressure` 文件，格式与 `/proc/pressure/memory` 相同。这使得 LMKD v2 可以：

- **监控 per-app 内存压力**：每个应用的 cgroup 有独立的 `memory.pressure`
- **区分系统级与应用级压力**：系统整体压力 vs 单个应用的压力
- **精细化决策**：在哪个 cgroup 内压力最大，优先杀该 cgroup 内的进程

Android 17 的 cgroup-v2 层级结构：

```
/dev/blkio/                    (根 cgroup)
├── uid_10001/                 (应用 UID)
│   ├── pid_1234/
│   │   └── memory.pressure    (per-process 压力)
│   └── memory.pressure        (per-UID 压力)
├── system/                    (system_server)
│   └── memory.pressure
└── background/                (后台进程组)
    └── memory.pressure
```

`[已验证: AOSP android-17.0.0_r1, system/core/init/cgroup-files.cpp 定义了 cgroup-v2 挂载层级]`

### 🔹 3. 分层内存压力的治理模型

Android 17 的内存压力治理呈现清晰的三层架构：

#### 3.1 第一层：系统级压力（Global Pressure）

**触发源**：`/proc/pressure/memory`（全局 PSI）

**响应策略**：
- PSI some stall 超过中等阈值 → LMKD 进入 **proactive reclaim** 模式
- 触发 `ApplicationThread#trimMemory()` 回调链，通知应用释放缓存
- 按优先级从低到高遍历 `procadjslot_list`，杀死 cached/empty 进程
- 检查 zone watermark（`/proc/zoneinfo`），评估各内存 zone 的可用空间

**关键参数**：
- `ro.lmk.cached_kill_limit`：一次压力事件最多杀的 cached 进程数（防止过度杀进程导致系统冻住）
- `ro.lmk.cached_after_free_multiplier`：决定杀死 cached 进程后是否继续的倍率

**与 kswapd 的协作**：当 PSI 持续触发且 LMKD 杀进程后仍不能缓解压力时，内核的 `kswapd` 内核线程会被唤醒进行后台内存回收。kswapd 的行为由 `vm.watermark_scale_factor` 控制（默认 10，即可用内存低于总内存的 0.1% 时触发回收）。

`[已验证: AOSP android-17.0.0_r1, system/memory/lmkd/lmkd.cpp, mp_event_psi() 函数中的决策逻辑]`

#### 3.2 第二层：cgroup 级压力（Per-Cgroup Pressure）

**触发源**：`/dev/.../memory.pressure`（per-cgroup PSI）

**响应策略**：
- 某个 cgroup 内的内存压力持续升高 → 优先杀该 cgroup 内的进程
- AppRestrictionController（参见 4.49 节 trimMemory 演进）通过 cgroup memory 限制触发后台限制
- 与 MemoryLimiter 配合，当应用超出其 cgroup 内存配额时，先发 trimMemory 再考虑 kill

**cgroup memory.max 的作用**：
- 每个应用进程在启动时被分配到一个 memory cgroup
- `memory.max` 设定了该 cgroup 的硬限制
- 当应用使用内存接近 `memory.max` 时，内核触发 per-cgroup OOM 或通知 LMKD

`[待验证: Android 17 中 per-app cgroup memory.max 的具体配置值，不同设备厂商可能有差异]`

#### 3.3 第三层：per-app 压力感知（App-Level Pressure Awareness）

**触发源**：应用进程内的 `ComponentCallbacks2#onTrimMemory()` 或 Android 17 新引入的 `onMemoryPressureChanged()`

**响应策略**：
- 应用自行决定释放哪些资源（bitmap 缓存、原生堆等）
- 这是应用层面的 **主动治理**，不涉及杀进程
- 详见 4.49 节关于 trimMemory API 演进的完整分析

**三层之间的优先级关系**：

```
压力升级方向：
  per-app trim → cgroup reclaim/kill → global LMKD kill

时间线：
  T0: 应用收到 onTrimMemory() → 释放缓存
  T1: cgroup 压力持续 → LMKD 杀该 cgroup 内的 cached 进程
  T2: 全局压力升高 → LMKD 按优先级杀进程，直到压力解除
```

`[已验证: AOSP android-17.0.0_r1, frameworks/base/services/core/java/com/android/server/am/OomAdjuster.java 中 trimMemory 调用链]`

### 🔹 4. 与 AppFlow / MemoryLimiter 的协同

#### 4.1 AppFlow 与 LMKD v2 的交互

Android 17 中 AppFlow（应用生命周期管理框架）与 LMKD v2 存在以下协同点：

- **进程优先级传递**：AppFlow 在决定应用进入 cached/frozen 状态时，通过 `OomAdjuster` 更新该进程的 `oom_score_adj`，这个值直接影响 LMKD 在杀进程时的优先级排序
- **预判式杀进程**：AppFlow 的 `AppStateException` 机制可以提前感知应用即将进入 cached 状态，LMKD 据此调整杀进程策略的预期
- **frozen 进程的内存计费**：被 AppFlow 冻结的进程虽然不消耗 CPU，但其内存仍然占用。LMKD v2 在计算系统可用内存时需要区分 frozen 和 active 进程的内存贡献

`[待验证: AppFlow 与 LMKD v2 的直接 API 调用关系，AOSP 源码中两者之间的交叉引用尚未完全公开]`

#### 4.2 MemoryLimiter 的独立治理路径

MemoryLimiter（参见相关章节）使用同一套 PSI 数据但服务于 **应用层主动治理**：

- 应用通过 `MemoryPressureMonitor`（Android 17 新引入）读取 PSI 数据
- 应用自行决定是否降低渲染质量、延迟加载等
- 与 LMKD 的决策完全独立，不直接影响杀进程策略

两者的关系类似于 **内核级 OOM Killer vs 用户态 OOMD**：LMKD 是最后的兜底手段，MemoryLimiter 是应用层面的优雅降级。

### 🔹 5. 与 ML 调度器的耦合

#### 5.1 进程创建与销毁的间接联动

ML 调度器（参见相关章节）决定是否 fork 新进程，LMKD v2 决定是否 kill 老进程。二者通过以下机制间接联动：

**oom_score_adj 作为共享信息**：
- ML 调度器在评估是否 fork 新进程时，会检查当前系统的 `oom_score_adj` 分布
- 如果系统中已有大量高 oom_score_adj 的 cached 进程，fork 新进程的风险较低（LMKD 可以轻松回收）
- 如果系统内存紧张且没有 cached 进程可杀，fork 可能导致系统卡顿

**ProcessRecord 的生命周期感知**：
- `OomAdjuster` 维护了所有进程的 `ProcessRecord`，其中包含 `oom_score_adj`、`lastPss`、`state` 等信息
- ML 调度器和 LMKD v2 都读取 `ProcessRecord` 的状态来做出决策
- `[待验证]` Android 17 是否在 ML 调度器的输出中考虑了 "LMKD v2 即将 kill 哪些进程" 这一前瞻信息

#### 5.2 决策时序

```
ML 调度器                          LMKD v2
    │                                  │
    ├── 评估是否 fork 新进程 ──────────┤
    │   (读取 oom_score_adj 分布)      │
    │                                  │
    ├── fork 成功 ──→ 注册到 LMKD ───┤
    │                                  ├── 将新进程加入 procadjslot_list
    │                                  │
    │                                  ├── PSI 事件触发 ──→ mp_event_psi()
    │                                  │   ├── 检查 zone watermark
    │                                  │   ├── 检查 free swap
    │                                  │   ├── 检查 thrashing stats
    │                                  │   └── 按 oom_score_adj 杀进程
    │                                  │
    │                                  ├── kill 完成 ──→ 释放内存
    │                                  │
    └── 下次调度决策 ←── 系统内存状态变化
```

`[已验证: AOSP android-17.0.0_r1, frameworks/base/services/core/java/com/android/server/am/OomAdjuster.java 与 system/memory/lmkd/lmkd.cpp 的交互通过 ProcessRecord.oomScoreAdj 实现]`

## 扩展

### 🔸 扩展点 1：BPF 增强的内存压力观测

eBPF 程序可以在 cgroup memory pressure 路径上插入低开销探针，与 PSI 数据交叉验证：

- **优势**：BPF 探针可以精确到 `try_to_free_pages()` → `shrink_lruvec()` 的调用链，提供比 PSI 更细粒度的信息
- **与 PSI 的互补**：PSI 提供 "有多少时间在等内存"，BPF 可以回答 "等的是哪个分配、哪个进程"
- **Perfetto 集成**：BPF 事件可以通过 Perfetto 的 `ftrace` 数据源采集，在 trace 中可视化

### 🔸 扩展点 2：生产环境的 LMKD v2 调优参数

Android 17 LMKD v2 的关键 build.prop 参数：

| 参数 | 默认值 | 说明 |
|------|--------|------|
| `ro.lmk.use_new_strategy` | true | 启用基于 zone/swap/thrashing 的新策略 |
| `ro.lmk.psi_partial_stall_ms` | 70 | some stall 中等压力阈值（ms） |
| `ro.lmk.psi_complete_stall_ms` | 50 | full stall 严重压力阈值（ms） |
| `ro.lmk.cached_kill_limit` | 1 | 一次压力事件最多杀 cached 进程数 |

| `ro.lmk.dma_inkb` | 0 | DMA zone 阈值（0 = 禁用） |

### 🔸 扩展点 3：zram 与 LMKD v2 的协同

Android 普遍使用 zram 作为 swap 后端，LMKD v2 的新策略直接考虑 zram 状态：

- **swap_free_low_percentage**：当 zram 的可用空间低于此值时，LMKD 认为 swap 即将耗尽，提前杀进程
- **swap_util_max_percentage**：zram 使用率超过此值时，压缩开销增大（CPU 消耗增加），LMKD 加速回收
- **zram 压缩比衰减**：随着 zram 填满，压缩比下降（新页面难以压缩到和旧页面一样小），LMKD 需要更早介入

zram 的 block device 架构与 LMKD 的关系：zram 是 LMKD 之外的独立 swap 后端，当 zram 达到 `disksize` 限制后无法自动驱逐冷页面（不像 zswap 可以分层到磁盘 swap）。因此 LMKD 的及时介入对防止 zram 系统进入 OOM 状态至关重要。

`[来源: Cubox/长文：打破 zswap 和 zram 的迷思-2026-05-25.md，关于 zram block device 架构的限制分析]`
`[已验证: AOSP android-17.0.0_r1, system/memory/lmkd/lmkd.cpp 中 swap 状态检查逻辑]`

### 🔸 扩展点 4：LMKD watchdog 机制

LMKD 内部有一个 watchdog，用于检测主线程是否卡死。如果 LMKD 主线程长时间无法处理压力事件（例如因为杀进程操作被阻塞），watchdog 会尝试直接杀进程来恢复系统。

## 自动发现

### 🔹 PSI `full` stall 与用户体验的关联性

在生产环境中，PSI memory `full` stall 的 avg10 值与用户体验有强相关性：

- **avg10 < 1%**：系统运行流畅，用户基本感知不到卡顿
- **avg10 1-5%**：轻度内存压力，可能出现偶发掉帧
- **avg10 5-15%**：中度压力，应用切换明显变慢
- **avg10 > 15%**：严重压力，系统接近 OOM，LMKD 频繁杀进程

这一关联性使得 PSI 可以作为 **系统健康度的客观指标**，用于线上监控和告警。

### 🔹 LMKD 决策的 Perfetto 可观测性

Android 17 的 LMKD 在关键决策点输出 atrace/atrace_marker：

- `kill_start` / `kill_end`：杀进程的开始和结束
- `reclaim_start` / `reclaim_end`：内存回收的开始和结束
- `pressure_event`：PSI 压力事件

这些 trace 点可以在 Perfetto 中以 track 形式展示，帮助开发者理解 LMKD 的行为时间线。
