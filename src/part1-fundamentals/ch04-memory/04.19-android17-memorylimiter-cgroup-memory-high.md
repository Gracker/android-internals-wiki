## 要点

### 🔹 MemoryLimiter 架构与设计原理
Android 17 的 MemoryLimiter 是实现精准内存管理的核心组件，采用了全新的 cgroup memory.high 机制，实现了对后台任务内存使用的精细控制。

**整体架构设计：**
MemoryLimiter 采用分层架构，包含了五大子系统：ProcState 限制矩阵、inotify→polling 回退机制、AnonSwapState 四态机、memcg v2 memory.high 语义、statsd 令牌桶限流。

**限制矩阵体系：**
```java
// 伪代码：完整的 23 个 ProcState→Limits 映射矩阵
class ProcStateMemoryMatrix {
    private Map<ProcState, MemoryLimits> matrix;
    
    public MemoryLimits getLimits(ProcState state, BatteryLevel level, MemoryState memState) {
        // 基础限制
        MemoryLimits baseLimits = matrix.get(state);
        
        // 电池状态影响因子
        double batteryFactor = getBatteryFactor(level);
        
        // 内存状态影响因子
        double memoryFactor = getMemoryFactor(memState);
        
        return baseLimits.multiply(batteryFactor).multiply(memoryFactor);
    }
}
```

**ProcState 限制矩阵细节：**

| ProcState | 基础配额 | 压缩因子 | 适用场景 | 优先级 |
|-----------|----------|----------|----------|--------|
| **TOP** | 1024MB | 1.0 | 前台应用 | 最高 |
| **FOREGROUND** | 768MB | 0.8 | 前台服务 | 高 |
| **VISIBLE** | 512MB | 0.6 | 可见应用 | 中高 |
| **PERCEPTIBLE** | 256MB | 0.5 | 可感知应用 | 中 |
| **HEAVY_WEIGHT** | 128MB | 0.4 | 重量级应用 | 中低 |
| **CACHED** | 64MB | 0.3 | 缓存应用 | 低 |

**inotify→polling 回退机制：**
1. **inotify 模式**：实时监控内存文件变化，响应延迟 < 1s
2. **red zone 阶段**：内存接近限制时（距离限制 30s 内），启用增强监控
3. **polling 模式**：常规状态下采用 5 分钟间隔的轮询机制
4. **回退条件**：当 inotify 监控失败或性能瓶颈时自动切换到 polling

### 🔹 cgroup memory.high 机制深度解析
Android 17 基于 Linux 内核的 cgroup v2 memory.high 机制，实现了创新的内存管理策略。

**memory.high 工作原理：**
memory.high 是 cgroup v2 中的一个软限制，当内存使用超过这个阈值时，内核会尝试回收内存，但不会强制杀死进程。

**Android 定制化扩展：**
```c
// 伪代码：Android 定制的 memory.high 实现
static int android_memory_high_write(struct cgroup_subsys_state *css,
                                   struct cftype *cft, const char *buf)
{
    struct mem_cgroup *memcg = mem_cgroup_from_css(css);
    unsigned long val;
    
    // 解析用户设置的值
    if (kstrtoul(buf, 0, &val))
        return -EINVAL;
    
    // Android 特定：添加内存保护阈值
    memcg->android_high_watermark = val * 0.8;
    memcg->android_soft_limit = val;
    
    // 设置 cgroup 原始限制
    memcg->high = val;
    
    return 0;
}
```

**throttle + reclaim 语义：**
1. **throttle 阶段**：内存使用接近 high 阈值时，触发内存回收
2. **reclaim 阶段**：持续超过 high 阈值时，强制回收内存
3. **优雅降级**：允许应用在短时间内超过 high 阈值
4. **信号传递**：通过 oom_score_adj 通知系统内存压力

**memory.high 与 memory.max 的关系：**
- **memory.high**：软限制，触发回收但不强制终止
- **memory.max**：硬限制，超过强制终止进程
- **协同策略**：high 作为早期预警，max 作为最终保障

**内存压力信号传递：**

### 🔹 MemoryLimiter 与 lmkd 的协同工作
MemoryLimiter 与 Low Memory Killer Daemon (lmkd) 形成了双重的内存管理体系，实现了从配额管理到进程回收的完整闭环。

**调度协同机制：**
MemoryLimiter 负责配额管理和早期预警，lmkd 负责实际的进程回收决策。

**内存压力场景下的任务淘汰顺序：**
```java
// 伪代码：协同淘汰算法
class MemoryElectionManager {
    
    public List<Process> selectVictims(MemoryPressureEvent event) {
        List<Process> candidates = getCandidateProcesses(event);
        
        // MemoryLimiter 优先级评估
        for (Process process : candidates) {
            process.setMemoryPriority(calculateMemoryPriority(process));
        }
        
        // lmkd 最终决策
        return lmkd.makeFinalDecision(candidates, event);
    }
}
```

**配额超限时的优雅降级策略：**
1. **第一阶段**：通知应用减少内存使用
2. **第二阶段**：冻结非关键内存分配
3. **第三阶段**：压缩缓存数据
4. **第四阶段**：准备进程回收

**内存回收的优先级调度算法：**

| 优先级类别 | 评估因素 | 回收策略 | 适用场景 |
|------------|----------|----------|----------|
| **最高** | 前台应用、用户正在交互 | 保护性回收 | 保持用户体验 |
| **高** | 重要服务、系统核心 | 选择性回收 | 系统稳定性 |
| **中** | 后台服务、次要功能 | 主动回收 | 资源优化 |
| **低** | 缓存数据、可重建对象 | 强制回收 | 内存压力缓解 |

**协作流程：**
1. **MemoryLimiter** 检测到内存压力
2. **发送信号** → lmkd
3. **lmkd** 评估进程优先级
4. **制定回收计划** → MemoryLimiter
5. **MemoryLimiter** 执行配额调整
6. **反馈结果** → lmkd
