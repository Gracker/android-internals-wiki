# 4.35 Android 17 CPU 缓存局部性与 PSS 内存核算源码机制

CPU 缓存局部性和 PSS 经常同时出现在性能报告中，但它们描述的是两个层级的问题：

- 缓存局部性关注 CPU 访问数据时，能否在较近的缓存层命中。它受数据布局、访问顺序、工作集大小、线程迁移和 SoC 缓存拓扑影响。
- PSS（Proportional Set Size）关注进程应分摊多少物理页。它由页表、物理页的映射关系以及交换页共享关系计算。

二者会在一次诊断中互相影响。例如，读取 `smaps` 要遍历 VMA 和页表，会消耗 CPU 时间并扰动缓存；扩大热数据集也可能同时增加 cache miss 和驻留页。可是，cache line 不参与 PSS 分摊公式，PSS 数值也不能反推出某段数据是否还在 L1、L2 或 LLC 中。

平台源码以 `android-17.0.0_r1` 为基准，内核以 `android17-6.18-2026-06_r6` 为基准。

## 1. 先区分 cache line、page 与 ART card

这三个粒度都和内存有关，职责却不同：

| 粒度 | 所属层级 | 主要用途 | Android 17 中如何确定 |
|---|---|---|---|
| cache line | CPU 微架构 | 数据传输、缓存一致性 | 由处理器报告；不能统一写死为 64 B |
| page | Linux 虚拟内存 | 映射、权限、回收、PSS/RSS 记账 | 运行时页大小或内核配置 |
| ART card | ART GC | 标记一段堆内存是否可能含跨代引用 | `1 << 10`，即每个 card 覆盖 1 KiB 堆 |

常见 ARM64 Android 设备采用 64 B 数据缓存行，但 AArch64 架构允许软件从 `CTR_EL0` 获取最小缓存行信息。Android 17 的 bionic 没有把 64 写成平台常量。`libc/bionic/sysconf.cpp` 读取 `CTR_EL0`，按下面的规则计算 L1 指令和数据缓存行大小。

这段源码用于说明“运行时查询”对应的计算方式：

```cpp
uint64_t ctr_el0;
__asm__ __volatile__("mrs %0, ctr_el0" : "=r"(ctr_el0));
info.l1_i.linesize = 4 << (ctr_el0 & 0xf);
info.l1_d.linesize = 4 << ((ctr_el0 >> 16) & 0xf);
```

bionic 随后通过 `_SC_LEVEL1_ICACHE_LINESIZE` 和 `_SC_LEVEL1_DCACHE_LINESIZE` 返回结果。该实现还明确注明：ARM64 只能由这里推导 L1 cache line 大小，不能同时得到 L1 容量、相联度以及所有下级缓存参数。因此，文章或工具不应把某一款 SoC 的 L1/L2/L3 容量和访问周期写成 Android 17 的统一规格。

工程上可以遵循两条规则：

1. 需要精确对齐时，在目标设备上查询，不要把 64 B 当成 API 契约。
2. 页大小、分配对齐和 cache line 大小分别处理。16 KiB page 不代表 16 KiB allocator chunk，也不会改变 cache line 的一致性粒度。

## 2. CPU 位置由调度器选择，schedutil 负责频率

“选哪个 CPU 运行”和“这个 CPU 运行在什么频率”是两项不同工作。

在 Android 17 的 6.18 内核中：

- `kernel/sched/fair.c` 的 `select_task_rq_fair()` 为 CFS/EEVDF 公平调度类选择目标 runqueue。
- 唤醒快速路径可能经过 `wake_affine()` 和 `select_idle_sibling()`。
- `wake_affine_idle()`、previous CPU 和 recent-used CPU 的候选判断会调用 `cpus_share_cache()`。缓存共享关系是选核约束之一，还要同时考虑空闲状态、CPU capacity、任务 affinity、负载均衡、SMT/cluster 拓扑等条件。
- `kernel/sched/cpufreq_schedutil.c` 文件头把 schedutil 定义为“基于调度器提供的 CPU utilization 数据的 CPUFreq governor”。它计算和提交频率，不负责 `select_task_rq_fair()` 的选核职责。

所以，“schedutil 优先选择 L2 命中率高的 CPU”这个说法混合了两个模块。更准确的表述是：公平调度器的部分唤醒路径会考虑 CPU 间是否共享缓存；任务落到某个 CPU 后，schedutil 可根据利用率驱动 cpufreq policy 调频。

Energy Model 也不存放 L2 容量或所谓 `idle_cost`。`include/linux/energy_model.h` 中的 `em_perf_state` 包含 `performance`、`frequency`、`power`、`cost` 和 `flags`，其中 `cost` 的定义是 `10 * power * max_frequency / frequency`。缓存拓扑、CPU capacity 与能耗估算会共同影响调度决策，但不能把它们压缩成“L2 越大，EM idle_cost 越高”。

### 2.1 局部性优化应从可测量对象入手

对应用和系统组件更有用的检查项是：

- 热路径是否顺序访问连续内存，还是频繁追逐指针。
- 高频读写字段是否与低频冷字段混排，导致更多 cache line 被带入。
- 多线程高频写字段是否落在同一 cache line，触发 false sharing。
- 工作集是否超过某级缓存容量。
- 线程是否在不共享私有缓存的 CPU 间频繁迁移。

迁移后，旧 CPU 的私有 L1 通常不能直接供新 CPU 使用；L2、LLC 是否共享取决于具体 SoC。不能把一次迁移等价为“L1/L2 全失效”，也不能预设固定的毫秒级预热时间。

## 3. Linux 如何计算 PSS

PSS 的基本思想是按映射关系分摊物理页。对一个驻留页，可用下面的概念式理解：

`该进程的页贡献 ≈ PAGE_SIZE / 当前映射计数`

进程总 PSS 是各页贡献之和。private/shared、clean/dirty 是 `smaps` 的其他统计维度，并非 PSS 公式的四个输入项。把 PSS 写成 `private_clean + private_dirty + shared_clean / N + shared_dirty / N` 可以帮助入门理解，但内核执行时以 folio/page 的映射计数为依据。

### 3.1 Android 17 内核的定点数记账

`fs/proc/task_mmu.c` 使用 `PSS_SHIFT = 12` 保存分数页精度。`smaps_account()` 先判断 folio 是否只映射一次；存在共享时，根据配置和页类型读取精确或平均 page mapcount，再对 `PAGE_SIZE << PSS_SHIFT` 做除法。

以 4 KiB page 为例：

- 只映射一次：该进程获得约 4 KiB PSS。
- 同一页当前存在 4 个映射：每个映射获得约 1 KiB PSS；按进程汇总时，同一进程内的多次映射会一起累加。
- 某个进程写入共享页并触发 COW：新私有页通常完整计入该进程，原共享页的分母也会变化。

内核源码还说明，未持有 folio lock 时读取到的 mapcount 是一个快照，极端并发下可能存在小偏差。因此，即使应用没有调用 `malloc`，进程创建、退出、映射和 COW 也能让共享页 PSS 变化。

### 3.2 SwapPss、RSS 与 USS 的口径

交换页没有驻留在 DRAM 中。内核对 SwapPss 使用 `swp_swapcount()` 分摊：共享交换项按 swap mapcount 计算，独占交换项记完整页。

Android 17 中几个常见口径如下：

| 指标 | Android 17 采集含义 |
|---|---|
| RSS | 当前驻留物理内存；共享页在每个映射进程中都计完整大小 |
| PSS | 驻留页按 mapcount 分摊 |
| USS | libmeminfo 按 `Private_Clean + Private_Dirty` 累加 |
| SwapPss | 交换页按 swap mapcount 分摊 |

`Debug.MemoryInfo.getTotalPss()` 返回 `dalvikPss + nativePss + otherPss + getTotalSwappedOutPss()`。这里的 “Total PSS” 包含 SwapPss，而 `getTotalRss()` 只表示驻留页。因此，Android API 的 total PSS 在某些状态下可以大于 total RSS；简单套用“PSS 必然小于等于 RSS”会忽略交换页口径。

## 4. Android 17 的三种进程内存采集路径

Android 17 的 `frameworks/base/core/jni/android_os_Debug.cpp` 提供详细分桶、总 PSS 和总 RSS 三种采集方式。它们不是同一次采集的三个阶段。

| Java/JNI 入口 | Linux 数据源 | 能否按 VMA 名称分类 | 主要结果 |
|---|---|---|---|
| `Debug.getMemoryInfo(..., MemoryInfo)` | 完整 `/proc/<pid>/smaps` + memtrack | 能 | Dalvik、Native、Other 及细分类 |
| `Debug.getPss(pid, ...)` | `smaps_rollup`，不支持时回退 `smaps`；另加 memtrack | 不能 | PSS、USS、SwapPss、RSS 总量 |
| `Debug.getRss(pid, ...)` | `/proc/<pid>/status` 的 `VmRSS`；另加 memtrack | 不能 | RSS 总量 |

### 4.1 详细 `MemoryInfo` 为什么必须读取完整 smaps

`android_os_Debug_getDirtyPagesPid()` 先调用 libmeminfo 的 `ExtractAndroidHeapStats()`。后者明确打开 `/proc/<pid>/smaps`，逐个 VMA 读取名称和统计值，再进行分类。例如：

- `[heap]`、`[anon:libc_malloc]`、`[anon:scudo:*]` 归入 Native Heap。
- ART/Java 堆相关匿名映射归入 Dalvik 及其细分类。
- `.so`、`.apk`、`.dex`、`.oat`、`.art`、stack 和设备映射分别进入对应的 Other 子项。

解析完成后，JNI 把核心结果写入 `otherPss`、`dalvikPss`、`nativePss` 等字段。这三个字段是一次完整 smaps 扫描后的输出桶，不是三个后端，也没有各自的采样频率。

`smaps_rollup` 只提供进程汇总值，缺少 VMA 名称。它可以减少用户态读取和解析大量逐 VMA 文本的开销，却不能替代详细分桶。内核仍要遍历相关 VMA 和页表，不能把 rollup 理解为常数时间缓存查询。

### 4.2 `getPss()` 与 `getRss()` 的快速总量路径

`Debug.getPss(pid, ...)` 通过 `ProcMemInfo::SmapsOrRollup()` 采集汇总。libmeminfo 首次检查 `/proc/self/smaps_rollup` 是否受支持和可读：检查通过时选择目标进程的 `smaps_rollup`，否则选择完整 `smaps`。目标文件本次打开失败会直接返回失败，并不会在同一次调用中再次尝试另一个文件。libmeminfo 从成功打开的结果中累计：

- `Pss`
- `Private_Clean + Private_Dirty`，作为 USS
- `Rss`
- `SwapPss`

JNI 将 `SwapPss` 加到返回的 PSS 中，源码注释给出的理由是：这些页若仍驻留，本来会参与 PSS 计算。

`Debug.getRss(pid, ...)` 走更轻的路径，通过 `ProcMemInfo::StatusVmRSS()` 读取 `/proc/<pid>/status` 中的 `VmRSS`。它没有 VMA 级分类，也不计算 PSS。

`mallinfo()` 与上述 PSS 采集无关。`android_os_Debug.cpp` 只在 `getNativeHeapSize()`、`getNativeHeapAllocatedSize()` 和 `getNativeHeapFreeSize()` 中使用它。allocator 维护的 native heap 数值和内核看到的驻留/共享页数具有不同口径，不能互相替代。

### 4.3 memtrack 为什么要单独相加

JNI 中 `read_memtrack_memory()` 的注释限定得很清楚：它获取的是 `/proc/<pid>/smaps` 尚未核算的 graphics memory。返回值分为 graphics、GL 和 other，详细 `MemoryInfo` 路径分别写入 `HEAP_GRAPHICS`、`HEAP_GL` 与 `HEAP_OTHER_MEMTRACK`。

这带来几个边界：

1. 不能假定同一 DMA-BUF 在 App 和 SurfaceFlinger 之间固定按 50% 分摊。映射者、驱动统计方式和 memtrack HAL 实现都可能不同。
2. memtrack 的结果可能由设备 HAL 和驱动提供，源码也承认 graphics 数值存在误报可能。
3. CMA 是系统级连续内存池统计，不能直接归因到 camera、GPU 或某个进程。
4. 某段 graphics memory 已经出现在 smaps 时，memtrack 应报告尚未包含的部分；诊断时要防止手工重复相加。

## 5. 系统 `/proc/meminfo` 与进程 `MemoryInfo` 是两套接口

`Debug.getMemInfo(long[])` 读取系统范围的 `/proc/meminfo`。Android 17 的 `Debug.java` 定义 `MEMINFO_COUNT = 29`，后半部分包括：

| 索引 | 常量 | 系统含义 |
|---:|---|---|
| 15 | `MEMINFO_KRECLAIMABLE` | 内核可回收内存，包含 `SReclaimable` |
| 24 | `MEMINFO_CMA_TOTAL` | CMA 总量 |
| 25 | `MEMINFO_CMA_FREE` | CMA 空闲量 |
| 26 | `MEMINFO_SWAP_CACHED` | 仍保留在 swap cache 中的内存 |
| 27 | `MEMINFO_SEC_PAGE_TABLES` | secondary page tables；内核文档列举 KVM MMU 与 IOMMU 分配 |
| 28 | `MEMINFO_PERCPU` | per-CPU 内核分配 |

JNI 从 `SysMemInfo::kDefaultSysMemInfoTags` 构造标签列表，在 ZRAM 对应位置插入 `Zram:`，然后读取系统 meminfo。这些常量不属于进程 `Debug.MemoryInfo` 的 Dalvik/Native/Other 分类，也不会给进程 smaps 增加五个解析字段。

以下字段布局对应 `android-17.0.0_r1`。若要说明某个字段在哪一版加入，需要逐版核对 AOSP 历史；不能仅凭 Android 17 当前有 29 项，就推断它们都在 Android 17 新增。

## 6. ART CardTable：GC 粒度和硬件缓存粒度不要混用

ART 的 CardTable 用一个字节描述一段 Java heap 是否可能含有需要 GC 关注的引用。Android 17 源码定义：

- `kCardShift = 10`
- `kCardSize = 1 << 10`，每个 card 覆盖 1 KiB heap
- `kCardDirty = 0x70`
- `kCardAged = 0x6f`
- `kCardAged2 = 0x6e`

`CardTable::Create()` 按 `heap_capacity / 1024 + 256` 申请卡表空间。额外的 256 B 用于调整 biased base，使其地址低 8 bit 等于 `0x70`。源码注释说明，这样 JIT 在生成写屏障时可以避免另行构造或加载 `kCardDirty`。

地址换算关系可以概括为：

`card_address = biased_base + (heap_address >> 10)`

`biased_base` 可能落在 mmap 起点之前的数值地址上，但加上合法 heap address 的高位后，结果会落入实际卡表映射。具体机器指令由编译器后端和目标 ISA 决定，不能凭 biased-base 设计臆造一条带立即数字节存储的 AArch64 指令。

1 KiB card 是 GC 记账范围。若目标 CPU 的 cache line 恰好是 64 B，一个 card 在数值上覆盖 16 条 cache line，也不能推导出硬件预取器会一次取满 16 条，或 GC 扫描一定命中某级缓存。CardTable 的价值在于减少写屏障指令与定位成本；硬件缓存效果仍要在目标 SoC 上测量。

## 7. Scudo、页大小与 false sharing

Android 17 的 Scudo Linux 适配在没有编译期固定 `SCUDO_PAGE_SIZE` 时，通过 `sysconf(_SC_PAGESIZE)` 获取运行时页大小。这个值用于页级操作，不能据此推导每个 chunk 或 pool 都按 16 KiB 分配。

分析 native 分配器时，应分别观察：

- allocator 对齐保证；
- size class 与 chunk 大小；
- page size；
- cache line 大小；
- 线程本地缓存或 TSD 的配置。

16 B 对齐不能保证任意结构体都不跨 cache line。false sharing 的判定条件是多个 CPU 对同一 cache line 中的不同数据执行冲突写入；两个对象位于同一 16 KiB page，但不在同一 cache line，并不会仅因共享 page 就产生 false sharing。

## 8. 如何联合测量 PSS 与缓存局部性

先明确要回答的问题：

- 内存归因问题：谁占用了物理页，变化来自私有页、共享分母、COW、swap 还是设备内存？
- CPU 访存问题：热点函数的 miss 是否升高，变化来自工作集、数据布局、false sharing 还是迁移？

### 8.1 建立可比较的内存快照

系统权限允许时，可用下面的命令分别取得汇总和 VMA 细节：

```bash
adb shell dumpsys meminfo <package-or-pid>
adb shell cat /proc/<pid>/smaps_rollup
adb shell cat /proc/<pid>/smaps
```

第一项适合观察 Android 分类和 memtrack 汇总；第二项适合较低文本解析开销的进程总量；第三项用于追查 VMA。`/proc` 可见性受 Android 版本、SELinux、UID 和调试权限限制，普通应用不能假定这些文件都可读。

采样时同时记录进程状态、GC、页面回收、前后台切换和测试输入。PSS 是共享状态的快照，只比较两个孤立数字很容易把其他进程退出引起的分母变化误判为本进程泄漏。

### 8.2 在目标设备确认 PMU 事件

先查看设备对 Simpleperf 暴露的硬件事件：

```bash
adb shell simpleperf list hw
```

列表决定后续能否使用 `cache-references`、`cache-misses` 或 SoC 特定 raw event。事件支持、访问权限和计数精度取决于 PMU、内核配置与设备策略；`raw-l1-dcache-refill` 之类的文本名称不能视为跨 SoC 标准。

设备支持通用事件时，可以对同一段稳定负载采集：

```bash
adb shell simpleperf stat \
  -e cpu-cycles,instructions,cache-references,cache-misses \
  -p <pid> --duration 10
```

结果应结合 instructions、cycles 和业务吞吐量解读。单看 cache-miss 总数会受运行时长影响；比较 miss rate 或每单位工作量的 miss 更有意义。采集时长和频率需通过目标设备上的 overhead 测试决定，不应套用统一周期。

### 8.3 用 Perfetto解释调度上下文

Perfetto 的 scheduling 数据可用于查看线程在哪个 CPU 上运行、何时阻塞以及是否迁移。它不会因为启用了 `sched` 就自动生成 cache-miss 计数；PMU 数据需要对应的数据源、权限和配置。推荐把 Perfetto 的时间区间与 Simpleperf、GC 事件及内存快照对齐，再判断迁移是否与 miss 上升同时发生。

`/proc/<pid>/pagemap` 描述虚拟页的 present、swapped、PFN 等信息，并受严格权限限制。它不记录 cache residence 或 cache affinity，不能用来证明某页位于 L1/L2。

## 9. 常见现象的判读

| 观测 | 优先检查 | 不宜直接下的结论 |
|---|---|---|
| PSS 上升，allocator 指标近似不变 | 共享页 mapcount、COW、文件映射、memtrack、SwapPss | “一定是 native 泄漏” |
| cache miss 上升，PSS 近似不变 | 访问顺序、工作集、false sharing、线程迁移 | “内存占用变大” |
| PSS 与 cache miss 同时上升 | 新增热数据、触页范围扩大、分配布局变化 | “PSS 采样导致业务长期退化” |
| PSS 下降但 major fault 增加 | reclaim、swap、文件页重新读取 | “内存优化没有副作用” |
| `dumpsys meminfo` graphics 与 smaps 对不上 | memtrack HAL、驱动口径、重复计数 | “App 与 SurfaceFlinger 必须各占一半” |

### 9.1 一个最小归因方法

1. 固定业务输入、设备温度、前后台状态和运行时长。
2. 记录 `dumpsys meminfo`，必要时保存 rollup 和完整 smaps。
3. 记录 allocator/GC 指标，区分逻辑分配量与物理驻留量。
4. 运行 Simpleperf，使用目标设备确认支持的事件。
5. 用 Perfetto 对齐线程迁移、GC、page fault 和业务阶段。
6. 只改一个变量，再重复相同工作量。

若优化数据布局后 cache miss 降低、吞吐提高而 PSS 不变，这是合理结果；若减少分配后 PSS 暂时不降，也应继续检查对象是否仍可达、allocator 是否保留 page、内核是否已回收以及共享页分母是否变化。

## 10. 检查清单

- [ ] 是否把 cache line 写成了设备统一固定值？
- [ ] 是否混淆 CPU 选核与 schedutil 调频？
- [ ] 是否把 Energy Model 描述成包含 L2 大小或 idle-state cost？
- [ ] 是否把 `mallinfo()` 当作 native PSS 数据源？
- [ ] 是否误称详细 `MemoryInfo` 只读 `smaps_rollup`？
- [ ] 是否明确 Android `getTotalPss()` 包含 SwapPss？
- [ ] 是否把系统 `Debug.getMemInfo()` 字段混入进程 PSS 分类？
- [ ] 是否把 ART 1 KiB card、page size 和硬件 cache line 当成同一粒度？
- [ ] 是否给 DMA-BUF 写了固定分摊比例？
- [ ] 是否先在设备上确认 PMU 事件，再解释 cache miss？
- [ ] 是否把 `/proc/pagemap` 误作 cache residence 证据？
