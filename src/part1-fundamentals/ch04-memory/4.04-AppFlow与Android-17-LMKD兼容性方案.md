## 要点

### 🔹 锚点 1：AppFlow 冷启动内存调度机制
AppFlow 是 Android 17 中针对冷启动场景的内存调度优化方案，通过智能化的内存管理提升应用启动速度：

- **内存预分配策略**：应用启动前预先分配所需内存，减少运行时分配开销
- **页面预加载机制**：根据历史使用模式预加载高频页面到内存
- **内存压缩优化**：采用先进的内存压缩算法，减少物理内存占用
- **启动资源优先级**：为启动资源设置最高优先级，确保快速可用

### 🔹 锚点 2：LMKD 优先级继承机制
Low Memory Killer Daemon (LMKD) 在 Android 17 中实现了更精细的进程管理：

- **多级优先级架构**：支持 8 级进程优先级，精确控制内存回收
- **智能预测算法**：基于应用使用模式预测内存需求
- **批量回收策略**：减少频繁的小规模内存回收操作
- **实时反馈机制**：根据系统负载动态调整回收策略

### 🔹 锭点 3：兼容性技术架构
AppFlow 与 LMKD 的兼容性架构设计：

```kotlin
// frameworks/base/services/core/java/com/android/server/am/AppFlowManager.java
class AppFlowManager {
    private final LmkdService mLmkdService;
    private final MemoryTracker mMemoryTracker;
    
    // 兼容性协调机制
    public boolean coordinateColdLaunch(String packageName) {
        // 1. 通知 LMKD 提高进程优先级
        mLmkdService.setProcessPriority(packageName, Process.PRIORITY_FOREGROUND);
        
        // 2. AppFlow 预分配内存
        MemoryAllocation allocation = mMemoryTracker.preAllocate(packageName);
        
        // 3. 启动完成后回调 LMKD 恢复优先级
        return launchWithMemoryAllocation(packageName, allocation);
    }
}
```

### 🔹 锚点 4：协同优化机制
AppFlow 与 LMKD 的协同优化机制：

1. **时序协调**：
   - 冷启动开始：LMKD 提高进程优先级
   - 内存分配阶段：AppFlow 执行预分配
   - 启动执行阶段：保持高优先级
   - 启动完成：恢复正常优先级

2. **资源协调**：
   - 内存池共享：两个系统共享内存资源池
   - CPU 调度协调：避免资源竞争
   - I/O 优化：顺序化 I/O 操作

3. **故障恢复**：
   - 优先级回退机制：异常时自动恢复
   - 内存分配回滚：失败时清理预分配内存
   - 状态监控与告警

## 源码边界

Android 17 冷启动时，AMS/ATMS 根据 Activity、Service、Provider 等状态计算进程 proc state 与 `oom_score_adj`，再由 framework 的 lmkd 控制客户端发送 `LMK_PROCPRIO` 或 `LMK_PROCS_PRIO` packet。lmkd 记录这个候选优先级；发生全局内存压力时，它结合 PSI、zone watermark、swap、thrashing 与 reclaim 状态选择受害进程。

这条关系是单向状态传递：

```text
framework 计算进程重要性
  → 把 oom_score_adj 发送给 lmkd
  → lmkd 在压力发生时按候选优先级决策
```

lmkd 不为冷启动进程预分配 Java/native 内存，不预加载页面，也不会调用 framework API 临时“提升启动优先级”。冷启动阶段的 CPU、I/O、编译和页面缓存优化需要分别从启动流程、ART、文件系统与具体产品策略取证。

MemoryLimiter 也不是 AppFlow 的配额服务。它是 `system_server` 内独立的进程内存限制机制，以进程状态映射 `memory.high` / `memory.swap.high`，并按自己的检查与 kill 路径工作；lmkd 不与它共享所谓内存池或回滚协议。

protected outline 中的 1200ms→850ms、80ms→25ms 等数字没有设备、build、样本量、测试命令或原始数据，全部作废。若要评估冷启动与内存压力的关系，应至少同时采集：

- 启动阶段的 Perfetto `android_startup` 与调度/I/O 信息；
- 进程 adj 变化和 lmkd `lmk,...` instant event；
- kill reason、PSI、PSS/RSS、swap 与 ZRAM 配置；
- 冷启动、温启动、热启动的分组结果。

Android 17 lmkd 的已核验实现见 [4.50 LMKD PSI 分层内存压力治理](4.50-lmkd-v2-psi-tiered-pressure-governance.md)，批量 adj packet 见 [4.36 LMK_PROCS_PRIO 批量命令](4.36-android17-lmkd-procs-prio-batch.md)，MemoryLimiter 见 [4.17 Android 17 MemoryLimiter 与内存监控影响](17-android17-MemoryLimiter-与内存监控影响.md)。本页不再扩写 AppFlow 兼容方案。
