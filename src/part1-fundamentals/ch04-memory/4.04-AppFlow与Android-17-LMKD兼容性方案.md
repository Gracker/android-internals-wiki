# 4.04 AppFlow与Android 17 LMKD兼容性方案

> **⚠️ 源码边界**
>
> `android-17.0.0_r1` 中不存在 `AppFlowManager`、`LmkdService`、`MemoryTracker.preAllocate()` 或 AppFlow/LMKD 共享内存池，因此不能把 AppFlow 视为 Android 17 的冷启动内存调度机制。
>
> AOSP `android-17.0.0_r1` 中，冷启动进程优先级通过 `oom_score_adj` 传递给 lmkd；源码中没有对应的 AppFlow 兼容方案。
>
> Android 17 lmkd 的相关实现见 [4.50](4.50-lmkd-v2-psi-tiered-pressure-governance.md)、[4.36](4.36-android17-lmkd-procs-prio-batch.md) 和 [4.17](17-android17-MemoryLimiter-与内存监控影响.md)。

---

## 要点

### 🔹 锚点 1：AppFlow 在 AOSP android-17.0.0_r1 中不存在

"AppFlow" 作为 Android 17 冷启动内存调度方案的说法没有任何 AOSP 源码证据。在 `android-17.0.0_r1` 的 `frameworks/base/services/core/java/com/android/server/am/` 目录树中：

- 不存在 `AppFlowManager.java` 或任何名为 `AppFlow*` 的类。
- 不存在 `LmkdService` 类——framework 与 lmkd 的交互通过 `ProcessList`（`OomAdjuster` / `LmkdConnection` 线程）完成，而非一个独立的 "LmkdService"。
- 不存在 `MemoryTracker.preAllocate()` 方法，也不存在冷启动前的 Java/native 内存预分配路径。
- 不存在 AppFlow 与 lmkd 共享的内存资源池、回滚协议或优先级继承机制。

> `AppFlowManager` Kotlin 代码、`MemoryAllocation` 返回值和 `setProcessPriority` 调用均没有 AOSP 源码依据。LMKD 的优先级更新路径不接受 framework 临时“提升启动优先级”的 API 调用，只接收 `oom_score_adj` 值并将其记录为候选优先级。

### 🔹 锚点 2：冷启动与 lmkd 的真实关系——单向状态传递

冷启动时，Android framework 的行为链路如下：

```text
AMS / ATMS 计算进程重要性
  → OomAdjuster 根据 Activity、Service、Provider 状态
    计算 proc state 与 oom_score_adj
  → ProcessList 通过 socket 向 lmkd 发送
    LMK_PROCPRIO（单进程）或 LMK_PROCS_PRIO（批量）packet
  → lmkd 记录候选优先级
  → 发生全局内存压力时，lmkd 按 PSI、zone watermark、
    swap、thrashing、reclaim 状态选择受害进程
```

**行为边界：**

- **单向通知**：framework → lmkd 是单向状态传递。lmkd 不会回调 framework，也不会临时 "提升" 启动进程的优先级。
- **无预分配**：lmkd 不为冷启动进程预分配 Java/native 内存，不预加载页面，不管理 ART 堆。
- **候选优先级语义**：`LMK_PROCPRIO` / `LMK_PROCS_PRIO` 携带的 adj 值是 "当内存压力发生时谁先被杀" 的排序依据，不是 "谁获得更多内存" 的分配指令。
- **批量路径**：Android 17 引入 `LMK_PROCS_PRIO` 批量命令，减少 per-process socket 往返。详见 [4.36 LMK_PROCS_PRIO 批量命令](4.36-android17-lmkd-procs-prio-batch.md)。

### 🔹 锚点 3：MemoryLimiter 是独立机制，不是 AppFlow 的配额服务

MemoryLimiter 不是“AppFlow 的配额服务”，两者也不共享内存池。

在 `android-17.0.0_r1` 中，MemoryLimiter 的定位如下：

- 它是 `system_server` 内**独立的**进程内存限制机制。
- 按进程状态映射 cgroup v2 的 `memory.high` / `memory.swap.high`。
- 拥有自己的检查路径和 kill 路径，不依赖 AppFlow（因为 AppFlow 不存在）。
- lmkd **不**与 MemoryLimiter 共享内存池或回滚协议。

MemoryLimiter 的实现见 [4.17 Android 17 MemoryLimiter 与内存监控影响](17-android17-MemoryLimiter-与内存监控影响.md)。

### 🔹 锚点 4：冷启动内存性能的取证方法

“1200ms→850ms 冷启动”“80ms→25ms 内存分配开销”等数据没有设备、build、样本量、测试命令或原始数据，不能作为性能结论。

评估冷启动与内存压力的关系时，应至少同时采集以下数据：

| 数据维度 | 工具 / 事件 |
|---------|------------|
| 启动阶段时间线 | Perfetto `android_startup` slice |
| 调度与 I/O | Perfetto sched / `f2fs` / block I/O |
| 进程 adj 变化 | Perfetto `oom_adjustment` 或 `dumpsys meminfo` |
| lmkd kill 决策 | Perfetto `lmk,...` instant event |
| kill reason / PSI | `lmkd` 日志、PSI 事件 |
| 内存占用 | PSS / RSS（`dumpsys meminfo`、Perfetto `perfetto track_event`） |
| swap / ZRAM | `/proc/swaps`、`/sys/block/zram0` |
| 启动类型分组 | 冷启动、温启动、热启动分开统计 |

没有上述证据的任何 "AppFlow 提升 X%" 性能结论均不可信。

## 源码边界

Android 17 冷启动时，AMS/ATMS 根据 Activity、Service、Provider 等状态计算进程 proc state 与 `oom_score_adj`，再由 framework 的 lmkd 控制客户端发送 `LMK_PROCPRIO` 或 `LMK_PROCS_PRIO` packet。lmkd 记录这个候选优先级；发生全局内存压力时，它结合 PSI、zone watermark、swap、thrashing 与 reclaim 状态选择受害进程。

这条关系是单向状态传递：

```text
framework 计算进程重要性
  → 把 oom_score_adj 发送给 lmkd
  → lmkd 在压力发生时按候选优先级决策
```

lmkd 不为冷启动进程预分配 Java/native 内存，不预加载页面，也不会调用 framework API 临时"提升启动优先级"。冷启动阶段的 CPU、I/O、编译和页面缓存优化需要分别从启动流程、ART、文件系统与具体产品策略取证。

MemoryLimiter 也不是 AppFlow 的配额服务。它是 `system_server` 内独立的进程内存限制机制，以进程状态映射 `memory.high` / `memory.swap.high`，并按自己的检查与 kill 路径工作；lmkd 不与它共享所谓内存池或回滚协议。
