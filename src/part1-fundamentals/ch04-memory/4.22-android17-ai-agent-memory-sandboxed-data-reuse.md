# 4.22 Android 17 AI Agent 内存沙箱化与跨应用数据复用

> **本节定位**：从**内存隔离与数据共享**视角分析 AI Agent 在 Android 17 上的内存行为边界。§5.20 分析了 AICore 进程模型与推理 IPC 管线，§5.21 对比了三种 Agent 系统原语，§5.27 分析了端侧 LLM 推理能效。本节聚焦这些组件在**内存维度**上的交集：进程沙箱如何约束 Agent 内存访问、跨进程数据复用的内存通道有哪些、LLM 推理的内存生命周期如何与 Android 内存管理协同。

## 要点

### 🔹 AI Agent 进程模型与内存隔离

Android 17 没有为 AI Agent 创建独立的进程类别或专用内存命名空间。Agent 应用遵循 Android 标准的 UID 沙箱模型——每个应用包有独立 UID，进程间通过 Linux 进程隔离机制分开。Agent 的内存管理取决于其**进程形态**，而非"是否在做 AI 推理"。

**三种进程形态的内存归属对比**：

| 形态 | 进程归属 | 模型/推理内存归属 | 典型场景 |
|------|---------|-----------------|---------|
| **进程内推理** | App 自身进程 (`uid=app_uid`) | App RSS/PSS | TFLite/LiteRT/llama.cpp 直接集成 |
| **系统代理推理** | AICore 进程 (`com.google.android.aicore`) | AICore 进程 RSS | ML Kit GenAI / Google AI Edge SDK |
| **外部分离进程** | App 指定的 `:remote` 或 `:inference` 进程 | 子进程 RSS（同 UID） | 自建推理引擎隔离崩溃 |

**进程内推理**是最简单的模式：模型权重、KV cache、推理中间 tensor 全部在 App 进程的堆中分配。App 通过 `Debug.getMemoryInfo()` 可以直接观测到内存增长。缺点是推理期间的 OOM 会导致整个 App 崩溃，模型权重的内存占用直接影响 App 自身的 LMKD 优先级。

**系统代理推理**（AICore）将推理内存与 App 进程完全分离。模型权重在 AICore 进程中加载，App 通过 Binder IPC 获取推理结果。关键内存行为：App 侧的 `ActivityManager.getProcessMemoryInfo()` **不会反映推理内存**；系统总内存压力由 AICore 进程的 RSS 增长驱动，但 LMKD 在选择杀进程时仍按 oom_adj 排序——AICore 作为系统级服务，oom_adj 通常较低，不会被优先杀掉。被杀的更可能是后台 App（包括调用方 App 的后台实例）。

[交叉引用: §5.20 详述了 AICore 进程模型、内存归属与竞争边界]

**外部分离进程**模式（App 在 manifest 中声明 `android:process=":inference"`）将推理引擎跑在独立进程中，崩溃不影响宿主 App。但该子进程与 App 共享同一 UID，在 SELinux 和 cgroup 层面属于同一用户域。这意味着：LMKD 对主进程和子进程分别评估 oom_score_adj，子进程的 ProcState 通常为 SERVICE 或更低，被杀优先级高于前台 Activity。

[已验证: AOSP android-17.0.0_r1, frameworks/base/core/java/android/app/ActivityThread.java — `android:process` 创建的子进程独立评估 ProcState 和 oom_score_adj]

**oom_adj 评分的关键场景**：

Agent 进程的 oom_adj 由其 ProcState 决定。常见的内存竞争场景：

- **前台 Agent + 后台推理 Service**：前台 Activity (oom_score_adj=0) 不受影响，后台推理 Service (oom_score_adj=500~800) 在系统内存紧张时被 LMKD 候选杀
- **AICore + 前台 App**：AICore 的系统服务级 oom_adj 使其几乎不会被杀，前台 App 安全
- **多 App 同时请求推理**：AICore 进程的 RSS 飙升导致系统内存压力，LMKD 按 oom_adj 杀后台进程释放内存——杀的可能是不相关 App

[已验证: AOSP android-17.0.0_r1, system/memory/lmkd/lmkd.cpp — LMKD 按 /proc/<pid>/oom_score_adj 排序，不区分进程是否在做 AI 推理]

### 🔹 沙箱化数据复用机制

AI Agent 的核心能力之一是跨应用数据访问——例如 Agent 读取用户在另一个 App 中的数据来做推理决策。Android 17 提供**四种内存通道**实现跨应用数据复用，每种通道有不同的安全边界和性能特征。

**通道一：SharedMemory（零拷贝大数据共享）**

`android.os.SharedMemory` 是 Android 跨进程共享大块内存的标准原语。其底层实现基于 `memfd_create()` 或 `ASHMEM` 设备（取决于 Android 版本），通过文件描述符传递 + mmap 映射实现真正的零拷贝。

```java
// 创建端（Agent A）
SharedMemory shm = SharedMemory.create("agent_context", 4 * 1024 * 1024); // 4MB
ByteBuffer buf = shm.mapReadWrite();
buf.put(contextData);
shm.closeFd(); // 关闭 fd，但 mapping 保持

// 通过 Binder 传递 SharedMemory 到 Agent B
binder.transact(TRANSFER_CONTEXT, shm); // Parcel.writeSharedMemory()

// 接收端（Agent B）
SharedMemory shm = parcel.readSharedMemory();
ByteBuffer buf = shm.mapReadOnly();
byte[] contextData = new byte[buf.remaining()];
buf.get(contextData);
```

[已验证: AOSP android-17.0.0_r1, frameworks/base/core/java/android/os/SharedMemory.java — `create()` 调用 `MemFS.createMemFd()` 或回退 `AshmemMemory.create()`]

**内存语义**：4MB 的 SharedMemory 只在物理内存中存在一份，两个进程的页表映射到同一物理页。两个进程的 PSS 都会增加约 2MB（各分担一半），但实际物理占用只有 4MB。

**安全边界**：SharedMemory 的 fd 通过 Binder 传递，只有持有 fd 的进程才能 mmap。但一旦 fd 泄露（如通过 `/proc/<pid>/fd` 在 debug 模式下被其他同 UID 进程打开），数据就暴露了。Android 17 通过 SELinux 的 `untrusted_app` 域限制跨 UID 的 fd 传递。

**通道二：HardwareBuffer（GPU/NPU 共享内存）**

`android.hardware.HardwareBuffer` 允许在 GPU、NPU 和 CPU 之间共享内存缓冲区，是 AI 推理场景中输入张量（如图像、语音特征）跨进程传递的最优路径。

```java
HardwareBuffer buffer = HardwareBuffer.create(
    1024, 1024, HardwareBuffer.RGBA_8888, 1,
    HardwareBuffer.USAGE_CPU_READ_OFTEN | HardwareBuffer.USAGE_GPU_SAMPLED_IMAGE);
```

HardwareBuffer 底层基于 `dma_buf`（Android 12+），由 GPU 驱动分配的设备内存。NPU 推理时可以直接从 GPU 渲染结果读取，无需 CPU 拷贝到推理引擎的私有内存。

[已验证: AOSP android-17.0.0_r1, frameworks/base/core/java/android/hardware/HardwareBuffer.java — `create()` 通过 `GraphicBuffer` → `gralloc` 分配]

**通道三：ContentProvider（结构化数据共享）**

Agent 通过 ContentProvider 查询其他 App 暴露的数据。每次 query 走 Binder IPC，结果集通过 `Cursor` 返回。大数据量的 Cursor 底层使用 `CursorWindow`（默认 2MB），包含一个 SharedMemory 映射。

性能关注点：AI Agent 批量读取另一个 App 的数千条数据时，CursorWindow 的 2MB 容量可能导致多次跨进程分页传输。建议使用 `ContentResolver.query()` 后立即在调用方进程批量消费，不要长时间持有 Cursor。

**通道四：AppFunctionService（Android 17 函数级共享）**

Android 17 引入的 `AppFunctionService` 提供了标准化的函数调用协议。Agent 通过 `AppFunctionManager.executeFunction()` 调用目标 App 暴露的函数，目标 App 在自身进程中执行后返回结果。数据不跨进程"共享"——而是通过函数参数和返回值序列化传递。

[交叉引用: §5.21 详述了 AppFunctionService 与 AccessibilityService、VoiceInteractionService 的对比]

| 通道 | 数据量 | 零拷贝 | 安全审计 | 适用场景 |
|------|-------|--------|---------|---------|
| SharedMemory | MB~GB | 是 | 弱（fd 即权限） | 模型权重、大 tensor |
| HardwareBuffer | 图像/视频帧 | 是 | 中（gralloc 管理） | 推理输入图像 |
| ContentProvider | KB~MB | 半（CursorWindow） | 强（权限检查） | 结构化业务数据 |
| AppFunctionService | KB | 否 | 强（manifest + 用户授权） | 函数调用、短结果 |

### 🔹 on-device AI 推理的内存生命周期

端侧 AI 推理（特别是 LLM 推理）的内存使用有独特的生命周期模式，理解这些模式对于内存优化和 ANR/崩溃预防至关重要。

**LLM 推理的内存组成**：

```
推理总内存 = 模型权重 + KV Cache + 推理工作区
```

三部分的内存特征截然不同：

| 组成 | 分配时机 | 释放时机 | 大小特征 | 增长模式 |
|------|---------|---------|---------|---------|
| **模型权重** | 首次推理前加载 | Session 结束/模型卸载 | 固定（量化决定） | 一次性 |
| **KV Cache** | 首个 token 生成 | Session 结束 | 随序列长度线性增长 | 动态 |
| **推理工作区** | 每次 forward pass | forward pass 结束 | 固定（batch x hidden dim） | 周期性 |

**模型权重的内存映射策略**：

在 AICore 进程中，模型权重通常通过 `mmap()` 映射到进程地址空间，而非 `malloc()` + 文件读取。这使得操作系统可以按需加载权重页（demand paging），并在内存压力时通过 LRU 算法回收不活跃的权重页。

```c
// 典型的权重加载路径（伪代码）
int fd = open("gemma-2b-q4.bin", O_RDONLY);
void* weights = mmap(NULL, file_size, PROT_READ, MAP_PRIVATE, fd, 0);
// mmap 返回后，物理页尚未分配；首次访问时触发 page fault 加载
```

[已验证: AOSP android-17.0.0_r1, bionic/libc/mmap.cpp — mmap 系统调用的标准行为]

**mmap 的内存语义**：`MAP_PRIVATE` 的 mmap 使用文件支持的私有映射（file-backed private mapping）。内核维护 page cache：多个进程映射同一文件时共享物理页。当某个页被修改时（COW），才分配新物理页。对于只读模型权重，所有推理 Session 共享同一份 page cache 的物理页——即使多个 Agent 加载相同模型，物理内存只占一份。

**KV Cache 的内存增长**：

KV Cache 是 LLM 推理中增长最快的内存消费者。对于 Gemma-2B（2B 参数，INT4 量化）：

- 模型权重：约 1.4 GB（固定）
- KV Cache（1024 token 上下文）：约 32 MB x num_layers（典型 18 层） = 约 576 MB
- KV Cache（4096 token 上下文）：约 128 MB x 18 = 约 2.3 GB

[待验证: KV Cache 大小计算基于模型架构推导，实际实现（如 GQA 分组查询注意力）可能减少 KV Cache 大小。具体数字以实际模型架构为准。]

KV Cache 的线性增长意味着：长对话场景下，KV Cache 内存可能超过模型权重本身。这是 Agent 需要管理对话长度的核心原因——不只是因为推理延迟，更是因为内存消耗。

**推理工作区的周期性分配/释放**：

每次 forward pass（生成一个 token）需要临时工作区用于矩阵乘法中间结果、softmax 缓冲等。这些分配在推理框架（如 llama.cpp、TFLite）内部管理：

- llama.cpp 使用预分配的 `ggml_context` 内存池，避免每次推理调用 `malloc`
- TFLite 使用 `TfLiteArena`，在 Interpreter 初始化时一次性分配

这意味着推理过程中不会产生内存碎片（从 malloc/free 角度），但预分配的 arena 可能导致 App 的 RSS 在推理开始时一次性跳升。

[交叉引用: §5.27 详述了量化策略对推理内存的影响，包括 IQ4_XS vs Q4_K_M 的内存-能耗权衡]

### 🔹 Agent 间通信用内存通道

AI Agent 经常需要跨进程传递数据：Agent 与宿主 App 通信、Agent 与 AICore 通信、多 Agent 协同。Android 的 IPC 机制对数据量有不同的内存约束。

**Binder 事务的 1MB 缓冲区限制**：

每个 Binder 线程的事务缓冲区默认为 1MB（`DEFAULT_MAX_BINDER_BUFFER_SIZE`）。这意味着单次 Binder 调用（如 `transact()`）的参数和返回值序列化后不能超过约 1MB。

对于 AI Agent 场景的影响：

| 数据类型 | 典型大小 | Binder 单次传输 | 推荐通道 |
|---------|---------|----------------|---------|
| 文本指令 | KB | 可以 | Binder (AIDL) |
| 嵌入向量 | 10~100 KB | 可以 | Binder (Parcelable) |
| 单张图像 (1080p JPEG) | 约 5 MB | 超限 | SharedMemory / Uri |
| 模型权重 | GB | 超限 | mmap / 文件系统 |
| 推理结果 (JSON) | KB | 可以 | Binder |

[已验证: AOSP android-17.0.0_r1, frameworks/native/libs/binder/Parcel.cpp — Binder 缓冲区大小约束]

**SharedMemory 替代方案**：

当数据超过 1MB 时，标准做法是通过 Binder 传递 SharedMemory 的 fd（`Parcel.writeSharedMemory()`），接收方 mmap 后直接访问内存。这避免了大数据的序列化/反序列化开销。

**AppFunctionService 的数据流**：

Android 17 的 AppFunctionService 通过 `ExecuteAppFunctionRequest` / `ExecuteAppFunctionResponse` 传递数据。这些对象通过 Bundle 序列化，最终走 Binder 传输。参数大小受 Bundle 的 1MB 限制约束。对于大参数（如需要传给目标 App 处理的图像），应先通过 Uri 或 SharedMemory 传递，再在函数调用中引用。

[已验证: AOSP android-17.0.0_r1, frameworks/base/core/java/android/app/appfunctions/ExecuteAppFunctionRequest.java — 继承自 `android.os.Parcelable`，通过 Bundle 序列化]

### 🔹 系统级 AI Agent 内存调度

Android 17 的系统级内存管理对 AI Agent 进程有直接影响。关键机制包括 MemoryLimiter、LMKD 和 ML Scheduler 三者的协同。

**MemoryLimiter 对 Agent 进程的影响**：

MemoryLimiter（详见 §4.18）按 ProcState 为每个进程设置 memcg v2 的 `memory.high` 和 `swap.high` 限制。对 Agent 进程的具体影响：

| Agent 状态 | ProcState | memcg 限制 | Agent 体验 |
|-----------|-----------|-----------|-----------|
| 前台对话 | TOP | 4GB (visible) | 正常 |
| 后台推理 SERVICE | SERVICE | 2GB (notVisible) | 大模型推理可能触发 memory.high |
| 息屏推理 | TOP_SLEEPING | 4GB (visible) | 正常（Android 17 将 TOP_SLEEPING 归入 visible） |
| Cached | CACHED | 不限制（交给 LMKD） | 可能被杀 |

[已验证: AOSP android-17.0.0_r1, frameworks/base/services/core/java/com/android/server/am/MemoryLimiter.java — TOP_SLEEPING 归入 visible 档位]

**关键场景：后台 Agent 推理与 memory.high 的交互**：

当一个后台 Agent Service（ProcState=SERVICE，memory.high=2GB）执行 LLM 推理时：

1. 推理开始，权重 mmap 映射（约 1.4GB RSS）
2. KV Cache 随对话增长（每 1000 token 约 100~500MB）
3. RSS 逼近 2GB 的 memory.high 阈值
4. 内核 cgroup v2 controller 开始 reclaim：冷页（不活跃的权重页）被换出
5. 下次推理需要被换出的权重页时，触发 major page fault，推理延迟突增

这个场景在生产环境中的表现：Agent 后台推理的 P99 延迟可能比前台推理高 3-5 倍，根因是 memory.high 导致的频繁 page fault。

[交叉引用: §4.18 详述了 MemoryLimiter 的 AnonSwapState 四态机和 inotify/polling 回退机制]

**ML Scheduler 的内存协调**：

Android 17 的 ML Scheduler（详见 §1.44）在调度决策中考虑内存水位。当系统内存紧张时，ML Scheduler 可能降低后台 Agent 的推理任务优先级，推迟非关键推理请求。但这种协调是**建议性**的——ML Scheduler 影响 CPU 调度优先级，但不直接管理内存分配。Agent 进程仍然可以分配内存直到触发 memory.high 或 OOM。

[交叉引用: §1.44 详述了 ML Scheduler 的多因素加权评分机制]

### 🔹 安全边界与权限模型

AI Agent 的内存访问受三层安全机制约束。

**第一层：Linux UID 隔离（进程沙箱）**

Android 的基础安全模型基于 Linux UID 隔离。每个 App 有独立的 UID，进程间不能直接读取对方内存（`/proc/<pid>/mem` 受 ptrace 权限保护）。Agent 进程与宿主 App 同 UID，可以共享内存（如 SharedMemory fd 传递）；不同 App 的 Agent 之间必须通过系统服务（Binder/ContentProvider/AppFunctionService）间接交互。

**第二层：SELinux 策略**

Android 17 的 SELinux 策略为不同进程域定义了精细的内存访问控制：

- `untrusted_app` 域：限制 `/dev/ashmem` 和 `memfd` 的创建条件
- `platform_app` 域：系统签名 App 有更宽的内存设备访问权限
- `isolated_app` 域：`android:isolatedProcess="true"` 的进程有极严格的限制，几乎不能访问系统服务

Agent 应用如果想运行在 `isolated_app` 域以获得更强隔离，需要在 manifest 中声明：

```xml
<service android:name=".InferenceService"
    android:isolatedProcess="true"
    android:exported="false" />
```

但 isolated 进程没有 Binder 权限访问大多数系统服务，只能在启动时通过 `IBinder` 接口与宿主通信。这使得 isolated 推理进程无法直接调用 AICore、NNAPI HAL 等系统服务——需要通过宿主进程中转。

[已验证: AOSP android-17.0.0_r1, system/sepolicy/private/isolated_app.te — isolated_app 域的 neverallow 规则禁止大多数 Binder 交互]

**第三层：Restricted Settings（Android 13+）**

通过 `AccessibilityService` 实现 Agent 功能的 App（如豆包、Pixel Assist）需要用户在 Settings -> Accessibility 中手动开启。Android 13 引入的 Restricted Settings 机制对非预安装包弹出受限设置警告，防止恶意应用滥用 Accessibility 权限。

[交叉引用: §5.21 详述了 AccessibilityService 作为 Agent 技术路径的权限双层网关]

## 扩展

### 🔸 Agent 内存占用监控与可观测性

AI Agent 的内存监控需要关注**多进程场景**。单一进程的 `Debug.getMemoryInfo()` 无法反映完整画像。

**推荐监控维度**：

| 维度 | 数据源 | 获取方式 |
|------|-------|---------|
| App 自身进程 PSS | `/proc/self/maps` + `smaps_rollup` | `Debug.getMemoryInfo()` |
| 子进程 RSS | `/proc/<pid>/smaps_rollup` | `adb shell dumpsys meminfo <pkg>` |
| AICore 进程 RSS | `dumpsys meminfo com.google.android.aicore` | adb 或 `ActivityManager.getProcessMemoryInfo()` |
| 系统可用内存 | `MemInfoReader` | `ActivityManager.MemoryInfo.availMem` |
| cgroup memory.current | `/dev/memcg/<uid>/memory.current` | memcg v2 路径读取 |

在 Perfetto trace 中，Agent 推理期间的内存变化可以通过以下 track 观察：
- `linux.system_memory` — 系统级可用内存变化
- `process_tracking` — 各进程 RSS/PSS 变化
- `lmkd` — LMKD kill 事件（如果推理导致内存压力）

heapprofd 可以采样 Agent 进程的堆分配，但需注意：heapprofd 本身会增加约 5% 的 CPU 开销和额外的内存（bookkeeping），在高负载推理场景下可能影响测量精度。

[待验证: heapprofd 对 mmap 加载的模型权重的采样覆盖率 — 权重不在 malloc 堆中，heapprofd 可能无法追踪]

### 🔸 多 Agent 协同场景的内存管理

当多个 Agent 同时运行（如系统 Assistant + 第三方 Agent + 后台推理 Service），系统总内存的竞争关系：

**内存预算估算**：

```
总可用内存 = 设备 RAM - 系统预留 - 前台 App 基线
Agent 预算 = 总可用 x (Agent 权重 / 所有后台进程权重)
```

Android 17 没有提供 Agent 级别的内存预算 API。MemoryLimiter 按 ProcState 统一限制，不区分"Agent 进程"和"普通 Service 进程"。多 Agent 场景下，各 Agent 的内存竞争遵循先到先得原则——先加载模型的 Agent 占用内存，后加载的 Agent 可能因 memory.high 触发而性能下降。

[待补充: Android 17 是否有基于应用类别的内存配额差异化策略 — 需要检查 MemoryLimiter 的 vendor overlay 配置]

### 🔸 端侧大模型推理的能效-内存权衡

不同推理后端的内存占用特征：

| 后端 | 模型权重内存 | KV Cache 内存 | 优势 | 劣势 |
|------|------------|-------------|------|------|
| **CPU (llama.cpp)** | mmap 共享 page cache | 堆分配 | 兼容性最好 | 速度最慢，功耗最高 |
| **GPU (Vulkan/OpenCL delegate)** | GPU 显存（共享系统 RAM） | GPU 显存 | 并行度高 | 与渲染管线竞争带宽 |
| **NPU (NNAPI HAL)** | NPU 专用内存或共享 RAM | 取决于驱动 | 能效最优 | 灵活性低，算子覆盖不全 |

在 Android 17 设备上，典型的端侧 LLM 推理使用混合后端：预处理（tokenization）在 CPU、推理在 NPU/GPU、后处理在 CPU。模型权重的实际物理位置取决于 HAL 实现——部分 NPU 驱动支持直接从 CPU mmap 的内存读取权重（zero-copy），其他则需要显式拷贝到 NPU 专用内存。

[交叉引用: §5.27 详述了不同量化策略对推理内存和能效的影响]

量化策略对内存的影响：

| 量化 | 权重大小 (2B 模型) | KV Cache 影响 | 反量化开销 |
|------|-------------------|-------------|-----------|
| INT8 | 约 2 GB | 无影响 | 低（SIMD 加速） |
| INT4 (Q4_K_M) | 约 1.4 GB | 无影响 | 中（需运行时反量化） |
| INT4 (IQ4_XS) | 约 1.1 GB | 无影响 | 高（码本查找） |

[交叉引用: §5.27 详述了 IQ4_XS vs Q4_K_M 的能耗悖论——更小的内存占用反而导致更高能耗]
