# 4.18 Android 17 onTrimMemory 链路源码解析与公平内存适配实战

`onTrimMemory()` 是 App 与系统内存管理之间最核心的契约接口。从 Android 14（API 34）起，这套接口经历了显著的收敛：七档 trim 等级被砍掉五档，调度时机被推迟到帧绘制完成后，而 Android 17 引入的 MemoryLimiter 又在 trim 路径之外开辟了一条全新的进程级内存配额链路。本节基于 `android-17.0.0_r1` 一手源码，完整拆解 onTrimMemory 从系统压力到 App 回调的全链路，并分析其对监控体系和适配策略的影响。

> **与 §4.4 的关系**：§4.4 从 lmkd 视角覆盖了 onTrimMemory 的基本链路（扩展六/七）。本节是独立的 onTrimMemory 专题，聚焦链路完整拆解、Android 17 新机制交互、以及监控/测试体系，不重复 lmkd 内部机制。

## 要点

### 🔹 onTrimMemory 机制演进与 Android 17 变更

[已验证: AOSP android-17.0.0_r1, frameworks/base/core/java/android/content/ComponentCallbacks2.java, line 99–161]

`ComponentCallbacks2` 定义了七档 trim 等级。从 API 34（Android 14）开始，其中五档被标记 `@Deprecated`，AOSP 不再向 App 派发：

| 等级常量 | 数值 | API 26-33 | API 34+ | Android 17 |
|---------|------|-----------|---------|------------|
| `TRIM_MEMORY_RUNNING_MODERATE` | 5 | 系统内存开始紧张时派发 | `@Deprecated`，不再派发 | 不再派发 |
| `TRIM_MEMORY_RUNNING_LOW` | 10 | 系统内存较低时派发 | `@Deprecated`，不再派发 | 不再派发 |
| `TRIM_MEMORY_RUNNING_CRITICAL` | 15 | 系统内存极度紧张时派发 | `@Deprecated`，不再派发 | 不再派发 |
| `TRIM_MEMORY_UI_HIDDEN` | 20 | Activity#onStop 后同步派发 | **仍派发** | **仍派发** |
| `TRIM_MEMORY_BACKGROUND` | 40 | 进程进入 LRU 背景区时派发 | **仍派发** | **仍派发** |
| `TRIM_MEMORY_MODERATE` | 60 | 后台进程内存压力中等时派发 | `@Deprecated`，不再派发 | 不再派发 |
| `TRIM_MEMORY_COMPLETE` | 80 | 后台进程内存极度紧张时派发 | `@Deprecated`，不再派发 | 不再派发 |

**收敛的设计意图**：旧版五档 `RUNNING_*` / `MODERATE` / `COMPLETE` 的实际触发时机在不同 OEM ROM 上高度不一致——同一设备同一内存条件下，有的 ROM 派发 `RUNNING_LOW`，有的只派发 `BACKGROUND`。Google 的收敛策略是：**只保留生命周期对齐的 `UI_HIDDEN(20)` 和进程状态对齐的 `BACKGROUND(40)`**，把"内存压力程度"的判断权收回到系统侧（lmkd PSI + MemoryLimiter cgroup），不再暴露给 App。

Android 17 对 onTrimMemory 本身没有新增 API 等级，但通过两个系统性变更间接影响了 trim 的触发环境和回调窗口：

1. **MemoryLimiter 成为第三道防线**：与 lmkd（系统级）和 CachedAppOptimizer（进程状态级）并行，MemoryLimiter 面向**正在运行的 notVisible 进程**施加 cgroup `memory.high` 软限制。MemoryLimiter 触发的 kill 不走 trim 路径——App 不会收到 `onTrimMemory()` 回调。详见 §4.17。
2. **cgroup freeze 的窗口压缩**：Android 14+ 的 CachedAppOptimizer 在 freeze 前只给一次 `TRIM_MEMORY_BACKGROUND`，App 回调完成后系统会立即执行 freeze。从 trim 回调到进程冻结的窗口进一步被压缩。

### 🔹 onTrimMemory 源码链路完整拆解

[已验证: AOSP android-17.0.0_r1, 多文件交叉验证]

onTrimMemory 的完整触发链路有两条独立路径，最终汇合到 `ActivityThread.handleTrimMemory()`：

**路径 A：生命周期驱动（TRIM_MEMORY_UI_HIDDEN）**

```
Activity.onStart → ActivityThread.handleStartActivity
  → ActivityThread.performStart
  → 之前的 Activity#onStop（如果存在）
    → ActivityThread.handleStopActivity
      → scheduleTrimMemory(TRIM_MEMORY_UI_HIDDEN = 20)
```

这条路径在 Activity 变为不可见时触发，与 App 前后台切换直接关联。`UI_HIDDEN(20)` 是最稳定的 trim 信号——它在每个 Activity 的 onStop 后同步发出。

**路径 B：进程状态驱动（TRIM_MEMORY_BACKGROUND）**

```
lmkd (kernel PSI / lowmemdetector)
  → ActivityManager.updateOomAdjLocked()
    → OomAdjuster.computeOomAdjLSP()
      → ProcessRecord.setProcState(newState)
    → CachedAppOptimizer.freezeAppAsyncLSP()
      → [冻结前检查] app.getSetAdj() >= CACHED_APP_MIN_ADJ?
        → IApplicationThread.scheduleTrimMemory(TRIM_MEMORY_BACKGROUND = 40)
          → [Binder IPC → App 进程]
            → ActivityThread.ApplicationThread.scheduleTrimMemory(40)
              → Choreographer.postCallback(CALLBACK_COMMIT, trimRunnable)
                → [下一帧 COMMIT 阶段]
                  → handleTrimMemory(40)
                    → collectComponentCallbacks(true)
                      → Application.onTrimMemory(40)
                      → Activity.onTrimMemory(40)
                      → Service.onTrimMemory(40)
                      → ContextWrapper.onTrimMemory(40)
                    → WindowManagerGlobal.trimMemory(40)
```

[已验证: AOSP android-17.0.0_r1, frameworks/base/services/core/java/com/android/server/am/CachedAppOptimizer.java:1409-1420]

**路径 B 的调度细节**：`scheduleTrimMemory()` 不是直接执行，而是通过 `Choreographer.CALLBACK_COMMIT` 延迟到帧绘制完成后：

```java
// frameworks/base/core/java/android/app/ActivityThread.java:2289-2304
@Override
public void scheduleTrimMemory(int level) {
    final Runnable r = PooledLambda.obtainRunnable(ActivityThread::handleTrimMemory,
            ActivityThread.this, level).recycleOnUse();
    // Schedule trimming memory after drawing the frame to minimize jank-risk.
    Choreographer choreographer = Choreographer.getMainThreadInstance();
    if (choreographer != null) {
        choreographer.postCallback(Choreographer.CALLBACK_COMMIT, r, null);
    } else {
        mH.post(r);
    }
}
```

Choreographer 的 callback 执行顺序为 `INPUT → ANIMATION → LAYOUT → COMMIT`。trim 被排到 COMMIT 阶段意味着发生在帧绘制完成之后、下一帧遍历之前。这个设计的工程目标是**避免 onTrimMemory 内的缓存清理操作（如 `Bitmap.recycle()` / `LruCache.evictAll()`）打断正在进行的 GPU 渲染管线导致 jank**。

`PooledLambda.obtainRunnable(...).recycleOnUse()` 是另一层优化：高频 trim 调用时复用 Runnable 对象，避免分配新对象造成额外 GC 压力。这与 Android 17 的 DeliQueue 无锁优化方向一致（详见 §1.28）。

**handleTrimMemory 的前台保护**：

```java
// frameworks/base/core/java/android/app/ActivityThread.java:7868-7894
private void handleTrimMemory(int level) {
    Trace.traceBegin(Trace.TRACE_TAG_ACTIVITY_MANAGER, "trimMemory: " + level);
    try {
        if (skipBgMemTrimOnFgApp()
                && mLastProcessState <= ActivityManager.PROCESS_STATE_IMPORTANT_FOREGROUND
                && level >= ComponentCallbacks2.TRIM_MEMORY_BACKGROUND) {
            return;  // 前台进程跳过 background trim
        }
        final ArrayList<ComponentCallbacks2> callbacks =
                collectComponentCallbacks(true /* includeUiContexts */);
        for (int i = 0; i < N; i++) {
            callbacks.get(i).onTrimMemory(level);
        }
    } finally {
        Trace.traceEnd(Trace.TRACE_TAG_ACTIVITY_MANAGER);
    }
    WindowManagerGlobal.getInstance().trimMemory(level);
}
```

`skipBgMemTrimOnFgApp()` 的含义：**前台进程收到 `TRIM_MEMORY_BACKGROUND` 或更高档位时直接 return**。这是 Android 14+ 引入的体验优化——避免前台 App 因为系统短暂回收内存的信号而产生不必要的缓存清理（导致回到前台时重新加载）。

最后的 `WindowManagerGlobal.getInstance().trimMemory(level)` 让 WindowManager 释放 SurfaceFlinger 端的图形缓存（如 BufferQueue 中的空闲 buffer），这是系统层面减少图形内存占用的辅助手段。

**回调分发顺序**：`collectComponentCallbacks(true)` 收集的顺序是 Application → ContentProvider → Activity → Service（具体顺序取决于注册时间）。开发者需要注意：**Application 的 `onTrimMemory()` 最先被调用**，适合做全局资源管理；Activity 的回调在后面，适合做页面级资源释放。

### 🔹 Android 17 公平运行内存适配机制

Android 17 的"公平运行内存"概念涉及三个独立子系统的协作：

| 子系统 | 触发条件 | 目标进程 | trim 回调 | kill 机制 | 详见 |
|--------|---------|---------|----------|----------|------|
| lmkd | 系统级 PSI 内存压力 | cached 进程 | freeze 前下发 `BACKGROUND(40)` | SIGKILL | §4.4 |
| CachedAppOptimizer | 进程进入 cached 状态 | cached 进程 | freeze 前下发 `BACKGROUND(40)` | cgroup freeze（非 kill） | §4.11 |
| MemoryLimiter | 进程级内存超限 | notVisible 运行中进程 | **不走 trim 路径** | 30s 后 SIGKILL | §4.17 |

**关键区分**：`onTrimMemory()` 是 lmkd / CachedAppOptimizer 路径的产物，**MemoryLimiter 路径不触发 trim 回调**。MemoryLimiter 的 kill 走 `ApplicationExitInfo.REASON_OTHER` + `description = "MemoryLimiter:AnonSwap"`，而不是 `REASON_LOW_MEMORY`。

这意味着 App 在 Android 17 上面临两套并行的内存治理：

1. **trim 路径**（lmkd + CachedAppOptimizer）：通过 `onTrimMemory(40)` 给 App 一次释放机会，然后 freeze 或 kill
2. **quota 路径**（MemoryLimiter）：直接 cgroup `memory.high` throttle，30s 后 kill，不通知 App

App 需要在 `onTrimMemory(40)` 中尽可能释放资源，因为**对于 cached 进程，这是 freeze 前最后一次机会**；但对于 notVisible 运行中进程（如后台 Service），MemoryLimiter 可能随时触发 kill，App 无法通过 `onTrimMemory()` 感知。

**ProcessRecord 中的 MemoryLimiter 集成**：

[已验证: AOSP android-17.0.0_r1, frameworks/base/services/core/java/com/android/server/am/ProcessRecord.java:1625]

```java
// ProcessRecord.setProcState() 中的 MemoryLimiter 更新
mMemoryLimiter.onProcStateUpdated(newState);
```

每当 OomAdjuster 重新计算进程优先级时，`ProcessRecord.setProcState()` 会同时通知 MemoryLimiter 更新该进程的 cgroup 限制。proc state → limit 的完整映射矩阵详见 §4.17 和 §4.19。

**OomAdjuster 与 trim 的协同**：

[已验证: AOSP android-17.0.0_r1, frameworks/base/services/core/java/com/android/server/am/OomAdjuster.java]

`OomAdjuster.computeOomAdjLSP()` 在重新计算 oom_adj 时，会设置 `app.pendingTrimMinLevel` 并在后续的 `applyOomAdjLSP()` 中触发 trim。关键的 trim 触发决策在 `ProcessList.makeActive()` / `ProcessList.makeInactive()` 中：

- 进程从 foreground 降到 background → 触发 `TRIM_MEMORY_UI_HIDDEN(20)` + 可能的 `TRIM_MEMORY_BACKGROUND(40)`
- 进程保持在 cached → 被 CachedAppOptimizer 接管，freeze 前下发 `TRIM_MEMORY_BACKGROUND(40)`

### 🔹 Binder IPC 对 onTrimMemory 的影响

onTrimMemory 的系统侧 → App 侧通信通过 **Binder IPC** 完成：

```
system_server: CachedAppOptimizer
  → IApplicationThread.scheduleTrimMemory(level)  [Binder oneway transact]
    → [内核 Binder 驱动：binder_thread_write → binder_transaction]
      → App 进程: ApplicationThread.scheduleTrimMemory(level)  [Binder oneway receive]
        → ActivityThread.scheduleTrimMemory(level)  [Handler post]
```

[已验证: AOSP android-17.0.0_r1, frameworks/base/core/java/android/app/ActivityThread.java]

`scheduleTrimMemory` 使用 `@Override` 标记但没有 `oneway` 注解——实际上 `IApplicationThread` 的 AIDL 定义中大部分生命周期方法（包括 `scheduleTrimMemory`）都是 `oneway` 的，这意味着：

1. **系统侧不阻塞等待 App 响应**：CachedAppOptimizer 发出 `scheduleTrimMemory` 后立即继续执行 freeze 逻辑，不等 App 完成 trim
2. **Binder 事务缓冲区不受限**：oneway 调用不占用同步事务缓冲区，即使 App 的 Binder 线程池全部忙碌，oneway 消息仍能入队

**内存压力下的 Binder 行为风险**：

在极端内存压力下，Binder 驱动本身也可能受到影响：

- **Binder 线程饥饿**：当进程被 cgroup throttle（MemoryLimiter 的 `memory.high` 触发后），CPU 时间片被压缩，Binder 线程可能无法及时处理 oneway 消息。这导致 `scheduleTrimMemory` 的实际执行被延迟——系统发出了 trim 通知，但 App 的 `handleTrimMemory()` 要等 Binder 线程调度到 CPU 后才执行。
- **事务排队与 freeze 的竞态**：CachedAppOptimizer 发出 `scheduleTrimMemory(40)` 后立即安排 freeze。如果 App 的 Binder 线程在 freeze 生效前还没处理完这条消息，trim 回调就会丢失——进程已经被冻结，排队的 Binder 消息不会执行。
- **跨进程内存共享边界**：App 通过 Binder 传递的 `Bundle` / `ParcelFileDescriptor` 共享内存不受 `onTrimMemory` 管理。MemoryLimiter 的 cgroup 限制只统计被限制进程自身的 `memory.current`，但通过 `ashmem` / `dmabuf` 共享的内存可能被多个 cgroup 重复计数。

**对监控的实操意义**：APM SDK 不能假设 `onTrimMemory(40)` 一定会被调用。在 MemoryLimiter throttle 场景下，进程可能在收到任何 trim 回调之前就被 30s 后 kill。监控方案需要结合 `Debug.MemoryInfo` 主动轮询和 `ApplicationExitInfo` 事后归因，不能仅依赖 `onTrimMemory` 作为唯一的内存压力信号。

### 🔹 实战场景适配策略

> App 侧的详细适配清单（Glide/Coil/OkHttp/LruCache 协同、代码示例）详见 §23.13。本节聚焦系统层面的场景差异。

**多进程应用的 trim 分发差异**：

Android 的 `onTrimMemory` 是**进程级**回调——每个进程独立收到自己的 trim 通知。多进程 App 需要注意：

- 主进程的 `TRIM_MEMORY_UI_HIDDEN(20)` 不会自动传递到子进程
- 子进程（如 `:push` / `:remote`）的 trim 时机取决于各自的 proc state
- 如果子进程是 `PROCESS_STATE_SERVICE`，它会在自己的 proc state 降级时收到 `TRIM_MEMORY_BACKGROUND(40)`
- 子进程需要自行注册 `ComponentCallbacks2` 或通过 `Application.registerComponentCallbacks()` 挂载回调

**游戏场景的内存预留与自适应调整**：

游戏是内存消耗大户。在 Android 17 的 MemoryLimiter 架构下：

- 游戏前台运行时 proc state 为 `PROCESS_STATE_TOP`，memHigh 配额默认 4 GB（`mConfiguration.memVisible`），通常不会触发 MemoryLimiter
- 但游戏切到后台时 proc state 可能降为 `PROCESS_STATE_HEAVY_WEIGHT` 或 `PROCESS_STATE_LAST_ACTIVITY`，memHigh 配额立即降到 2 GB（`memNotVisible`）
- 如果游戏后台占用超过 2 GB → MemoryLimiter throttle → 30s 后 kill（不走 trim 路径）
- **适配策略**：游戏应在 `onStop()` 中主动释放纹理缓存和音频缓冲，不要等 `onTrimMemory(40)`——因为 `TRIM_MEMORY_BACKGROUND` 可能在 freeze 前才到来，窗口太短

**视频播放器的内存缓存管理**：

视频播放器通常维护预解码缓冲队列。在 Android 17 上：

- 前台播放时不受 MemoryLimiter 限制（`PROCESS_STATE_TOP`）
- 后台音频播放（`PROCESS_STATE_FOREGROUND_SERVICE` 带媒体类型）的 memHigh 配额是 2 GB
- 如果播放器维护了大量预解码帧（如 AV1 1080p 预解码缓冲可能达到 500 MB+），需要监控总 PSS
- **适配策略**：在 `onTrimMemory(20)` 时缩减预解码缓冲到最小值（保留 2-3 帧），在 `onTrimMemory(40)` 时释放所有非必要缓冲

### 🔹 兼容性边界与版本适配

**API 26-33 vs API 34+ 的统一处理方案**：

```kotlin
override fun onTrimMemory(level: Int) {
    when {
        level == ComponentCallbacks2.TRIM_MEMORY_UI_HIDDEN -> {
            // 所有版本可靠触发
            // 释放 UI 相关资源：图片缓存、Surface、布局缓存
            releaseUiResources()
        }
        level == ComponentCallbacks2.TRIM_MEMORY_BACKGROUND -> {
            // 所有版本可靠触发
            // 释放非必要 Java 堆、Bitmap、LruCache
            releaseNonCriticalCache()
        }
        level >= ComponentCallbacks2.TRIM_MEMORY_RUNNING_LOW -> {
            // API 26-33 可靠触发，API 34+ 不会收到
            // 但保留处理逻辑以兼容旧设备
            if (Build.VERSION.SDK_INT < 34) {
                aggressiveMemoryRelease()
            }
        }
        // API 34+ 不会进入 TRIM_MEMORY_MODERATE/COMPLETE 分支
    }
}
```

**关键兼容性原则**：
- 只依赖 `UI_HIDDEN(20)` 和 `BACKGROUND(40)` 作为可靠的 trim 信号
- 对 API 33 及以下，可以额外处理 `RUNNING_LOW(10)` / `RUNNING_CRITICAL(15)` / `MODERATE(60)` / `COMPLETE(80)`，但不能把这些等级作为必需的触发条件
- 官方文档明确写：「不要比较 exact value，只比较大于等于」——这覆盖了中间档位被取消的兼容场景

**OEM 定制的额外信号**：

主流 OEM ROM 在 AOSP trim 链路之上可能有额外扩展：

| OEM | 扩展机制 | 兼容性 |
|-----|---------|--------|
| 小米 HyperOS | 公平运行内存：基于 AOSP `CachedAppOptimizer` 钩子，额外要求 App 在规定时间内响应 trim | App 正确实现 `onTrimMemory()` 即可兼容 |
| 华为 EMUI/HarmonyOS | 独有的后台内存管理策略，可能提前 kill 高内存后台进程 | 依赖 `ApplicationExitInfo` 归因 |
| OPPO ColorOS | 内存优化策略，可能对后台进程做额外压缩 | 不影响 trim 回调，但可能影响 PSS 采集精度 |
| 三星 OneUI | 类似 AOSP 行为，额外限制后台 Service 数量 | 不影响 trim 链路 |

**32 位 vs 64 位应用的适配差异**：

64 位进程的虚拟地址空间（48-bit）远大于 32 位进程，内存分配策略差异显著：

- 32 位进程的虚拟地址空间上限约 3-4 GB（用户态），更容易触发地址空间耗竭而非物理内存耗竭
- 64 位进程几乎不会遇到地址空间问题，但物理内存超限会直接触发 MemoryLimiter（Android 17）
- `Debug.MemoryInfo.totalPss` 在 32 位和 64 位进程中的统计口径一致，但 `nativeHeap` 占比差异大

## 扩展

### 🔸 内存碎片化分析与 Compaction 策略

`onTrimMemory(40)` 回调后，App 大量释放 Java 堆对象和 Bitmap，会产生内存碎片。这涉及两个独立的 compaction 机制：

**ART 堆 Compaction**：Android 14+ 的 Generational GC（详见 §4.8）在 `onTrimMemory` 触发后可能执行 Major GC + Compaction，将存活对象移动到连续区域。这个过程中应用线程被暂停（GC pause），通常持续 5-50ms。

**Linux Kernel Direct Reclaim**：当系统级物理内存紧张时，内核的 `kswapd` 内核线程会对页缓存做回收。`onTrimMemory` 释放的 Java 对象对应的 anon 页如果没有被 swap-out，会回到 buddy allocator，减少外部碎片。

两者的交互：ART Compaction 减少内部碎片（Java 堆内的空闲块），Kernel Direct Reclaim 减少外部碎片（物理页框的空闲块）。`onTrimMemory` 是这两个机制的触发点之一——大量释放后两者可能同时工作，造成短暂的 I/O wait 增加。

在 Android 17 上，MemoryLimiter 的 `memory.high` throttle 会加剧 Direct Reclaim 的频率。进程在 red zone 时，每 30s 轮询周期内都可能经历一次完整的 reclaim → allocate → reclaim 循环。

### 🔸 端侧 AI 模型的内存适配边界

端侧大模型（LLM）推理是 Android 17 内存生态的新挑战：

- 一个 4B 参数的量化模型（INT4）占用约 2 GB 内存，恰好等于 MemoryLimiter 的 `memNotVisible` 默认配额
- 模型推理期间的工作集（KV cache + activation）可能额外占用 500MB-1GB
- 如果推理在后台 Service 中执行，极有可能触发 MemoryLimiter 的 `memory.high` 限制

**适配策略**：
- 推理任务应在前台 `PROCESS_STATE_TOP` 时执行，享受 4GB 的宽松配额
- 后台推理应使用 `WorkManager` + 前台 Service，确保 proc state 不低于 `PROCESS_STATE_FOREGROUND_SERVICE`
- `onTrimMemory(40)` 时应暂停推理，保存中间状态（KV cache dump），等待内存压力缓解后恢复
- 模型加载应分页进行（mmap 模型文件而非一次性 read 到内存），让内核按需加载页面

### 🔸 性能优化案例与最佳实践

**案例 1：Glide 内存缓存的 trim 响应**

Glide 的 `MemorySizeCalculator` 根据设备 RAM 和屏幕大小计算内存缓存上限。收到 `onTrimMemory` 时：

- `TRIM_MEMORY_UI_HIDDEN(20)`：不清理内存缓存（UI 不可见但可能很快回来）
- `TRIM_MEMORY_BACKGROUND(40)`：清空内存缓存（`memoryCache.clearMemory()`）
- 高于 40 的等级（API 33-）：同时清空 BitmapPool（`bitmapPool.clearMemory()`）

Glide 的 `trimMemory()` 实现在主线程同步执行，清理 200-500 条 Bitmap 引用通常耗时 5-15ms（取决于缓存大小），基本不会引发 jank。

**案例 2：新闻 App 的分层缓存策略**

某新闻 App 在 `onTrimMemory` 中的分层响应：

| trim level | 释放内容 | PSS 释放量 | 恢复成本 |
|-----------|---------|----------|---------|
| `UI_HIDDEN(20)` | 文章列表缩略图缓存 | 50-100 MB | 低（网络重新加载） |
| `BACKGROUND(40)` | 首页 Feed 数据 + 用户头像缓存 + 预加载视频 | 150-300 MB | 中（需重新请求 API） |
| MemoryLimiter 触发 | 保留当前正在阅读的文章数据，其余全部释放 | 300-500 MB | 高（需要完整重新加载） |

该 App 在实施分层策略后，后台 freeze 后的冷启动恢复时间从 1.8s 降到 0.9s（因为 onTrimMemory(40) 已提前释放了大部分资源，freeze 时工作集更小）。
