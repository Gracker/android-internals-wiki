# 4.20 Android 17 LMKD v2 内存回收优先级机制详解

<!-- outline-start -->
## 要点

### 🔹 LMKD v2 核心改进
Android 17 引入了 LMKD v2，在传统低内存杀手机制基础上增加了优先级回收策略，实现了更精细的内存管理。

### 🔹 Memory Reclaim Priority
新增的内存回收优先级机制允许系统根据应用的优先级和状态，智能选择回收对象，优先保护重要应用。

### 🔹 Adaptive Background Activity Manager
Android 17 引入了自适应背景活动管理器，与 LMKD v2 协同工作，实现更智能的后台进程管理。

### 🔹 三段式内存回收策略
采用前端回收、中间回收和后端回收的三段式策略，确保在不同压力条件下都能高效回收内存。

### 🔹 CGroup 内存限制增强
LMKD v2 与 CGroup 深度集成，提供了更精确的内存统计和限制机制。

### 🔹 AppFlow 兼容性
新机制与 AppFlow 大型应用冷启动内存联合调度机制兼容，形成完整的内存管理生态系统。

## 扩展

### 🔸 与 Android 16 LMK 对比
Android 16 的 LMK 主要基于简单的 oom_score_adj 阈值机制，而 Android 17 的 LMKD v2 实现了多维度、智能化的优先级评估。

### 🔸 性能优化收益
通过更精细的内存管理，LMKD v2 减少了不必要的进程终止，提高了系统响应速度和用户体验。

## LMKD v2 架构设计

### 核心组件关系

Android 17 的内存管理机制由以下几个核心组件协同工作：

#### 1. LMKD (Low Memory Killer Daemon) v2
- **职责**：内核内存管理守护进程，负责监控系统内存使用和决定回收策略
- **新特性**：支持优先级回收、多级阈值、动态调整
- **位置**：`system/lowmemorykiller/lmkd` 

#### 2. Memory Reclaim Priority Service
- **职责**：管理应用的内存回收优先级
- **新特性**：基于应用重要性、用户活跃度、系统状态的综合评估
- **位置**：`frameworks/base/services/core/java/com/android/server/am/MemoryReclaimPriorityService.java`

#### 3. Adaptive Background Activity Manager
- **职责**：智能管理后台活动，优化内存使用
- **新特性**：预测用户行为，动态调整后台策略
- **位置**：`frameworks/base/services/core/java/com/android/server/am/AdaptiveBackgroundActivityManager.java`

#### 4. CGroup Memory Controller
- **职责**：精确控制每个进程的内存使用
- **新特性**：增强的统计功能和限制机制
- **位置**：`system/core/cgroup/cgroup_memory.c`

### 三段式内存回收策略

LMKD v2 引入了智能的三段式回收策略：

#### 前端回收（Front-end Reclaim）
**触发条件**：
- 系统内存使用 > 70%
- 用户连续操作超过 30 秒
- 应用内存增长超过阈值

**回收策略**：
- 优先回收非活跃进程的缓存页面
- 回收被标记为 "可回收" 的匿名内存
- 保留活跃应用的活跃页面

**实现代码**：
```cpp
// frameworks/native/services/lmkd/lmkd.cpp
void LMKD::frontEndReclaim() {
    for (const auto& process : m_processes) {
        if (process->state == ProcessState::INACTIVE && 
            process->memory_usage > FRONTEND_THRESHOLD) {
            reclaimMemory(process, RECLAIM_CACHE_ONLY);
        }
    }
}
```

#### 中间回收（Mid-end Reclaim）
**触发条件**：
- 系统内存使用 > 85%
- 前端回收效果不显著
- 系统开始出现内存压力

**回收策略**：
- 回收低优先级进程的非关键内存
- 终止长时间未使用的后台服务
- 强制回收应用的部分共享内存

**实现代码**：
```cpp
// frameworks/native/services/lmkd/lmkd.cpp
void LMKD::midEndReclaim() {
    std::vector<Process*> sorted_processes = sortProcessesByPriority();
    for (size_t i = sorted_processes.size() - 1; i > 0; --i) {
        if (sorted_processes[i]->memory_usage > MIDEND_THRESHOLD) {
            reclaimMemory(sorted_processes[i], RECLAIM_ACTIVE_AND_CACHE);
        }
    }
}
```

#### 后端回收（Back-end Reclaim）
**触发条件**：
- 系统内存使用 > 95%
- 中间回收效果不显著
- 系统面临严重内存不足

**回收策略**：
- 终止最低优先级进程
- 强制杀死所有可回收进程
- 触发系统级内存压缩

**实现代码**：
```cpp
// frameworks/native/services/lmkd/lmkd.cpp
void LMKD::backEndReclaim() {
    auto processes_to_kill = getProcessesToKill(OOM_KILL_THRESHOLD);
    for (const auto& process : processes_to_kill) {
        terminateProcess(process);
    }
    system("echo 1 > /proc/sys/vm/compact_memory");
}
```

## Memory Reclaim Priority 机制详解

### 优先级评估算法

Android 17 的内存回收优先级基于多维度评估：

#### 1. 应用重要性评分
```java
// frameworks/base/services/core/java/com/android/server/am/MemoryReclaimPriorityService.java
public int calculateAppImportance(ProcessRecord app) {
    int score = 0;
    
    // 前台应用 +100
    if (app.isForeground()) {
        score += 100;
    }
    
    // 用户活跃度 +30-70
    score += calculateUserActivityScore(app);
    
    // 系统应用 +50
    if (app.isSystemApp()) {
        score += 50;
    }
    
    // Service 绑定状态 +20-40
    score += calculateServiceBindScore(app);
    
    // 内存使用量 -10~-50
    score -= calculateMemoryUsagePenalty(app);
    
    return score;
}
```

#### 2. 用户活跃度评估
基于用户历史行为数据计算活跃度：

```java
public int calculateUserActivityScore(ProcessRecord app) {
    UserActivityHistory history = mActivityHistoryDao.get(app.uid);
    if (history == null) return 0;
    
    int recentUsage = history.getRecentUsageMinutes(24); // 24小时内
    int frequency = history.getLaunchCount(7); // 7天内启动次数
    int recency = history.getLastLaunchMinutes(); // 最后启动时间
    
    // 综合计算活跃度分数
    return (recentUsage * 2) + (frequency * 5) + Math.max(0, 30 - recency / 60);
}
```

#### 3. 系统状态适应性
根据系统状态动态调整优先级：

```java
public int getSystemAdaptiveScore(ProcessRecord app) {
    SystemState state = getSystemState();
    
    // 低电量时，优先保护核心应用
    if (state.batteryLevel < 20) {
        return app.isCoreApp() ? 20 : -10;
    }
    
    // 游戏模式下，优先保护游戏进程
    if (state.gamingMode) {
        return app.isGame() ? 30 : -5;
    }
    
    // 多任务模式下，平衡各应用优先级
    if (state.multiTaskMode) {
        return calculateBalancedScore(app);
    }
    
    return 0;
}
```

### 优先级管理策略

#### 动态优先级调整

    for (ProcessRecord app : mRunningApps) {

    switch (app.memoryPriority) {
        case PRIORITY_CRITICAL: return CRITICAL_THRESHOLD;
        case PRIORITY_HIGH: return HIGH_THRESHOLD;
        case PRIORITY_NORMAL: return NORMAL_THRESHOLD;
        case PRIORITY_LOW: return LOW_THRESHOLD;
        case PRIORITY_MIN: return MIN_THRESHOLD;

    }
}

int update_memory_limit(const char* cgroup_path, uint64_t limit) {
    char limit_path[PATH_MAX];
    snprintf(limit_path, sizeof(limit_path), "%s/memory.limit_in_bytes", cgroup_path);
    
    FILE* fp = fopen(limit_path, "w");
    if (!fp) return -ENOENT;
    
    fprintf(fp, "%lu\n", limit);
    fclose(fp);
    
    // 设置软限制
    snprintf(limit_path, sizeof(limit_path), "%s/memory.soft_limit_in_bytes", cgroup_path);
    fp = fopen(limit_path, "w");
    if (fp) {
        fprintf(fp, "%lu\n", limit * 120 / 100); // 软限制 = 硬限制 * 1.2
        fclose(fp);
    }
    
    return 0;
}

## 故障排查与优化

### 常见问题诊断

#### 1. 优先级评估异常
**症状**：应用被意外终止或内存管理不生效
**诊断命令**：
```bash
# 检查进程优先级
adb shell dumpsys meminfo <package_name>

# 检查 LMKD 决策日志
adb logcat -s "LMKD:D" -v threadtime | grep -E "decision|priority"
```

**解决方案**：
- 检查用户活跃度数据是否正确
- 验证系统状态传感器数据
- 调整权重参数配置

#### 2. CGroup 内存限制问题
**症状**：应用内存使用异常或限制不生效
**诊断命令**：
```bash
# 查看 CGroup 配置
adb shell cat /sys/fs/cgroup/memory/app_<uid>/cgroup.procs
adb shell cat /sys/fs/cgroup/memory/app_<uid>/memory.limit_in_bytes

# 检查内存统计
adb shell cat /sys/fs/cgroup/memory/app_<uid>/cgroup.memory.stat
```

**解决方案**：
- 重新设置内存限制
- 清理 CGroup 缓存
- 重启 lmkd 服务

#### 3. ABA 预测不准确
**症状**：后台活动预测与实际用户行为不符
**诊断命令**：
```bash
# 查看预测日志
adb logcat -s "AdaptiveBackgroundActivityManager:D" -v threadtime

# 分析用户行为数据
adb shell dumpsys activity user_activity
```

**解决方案**：
- 收集更多用户行为数据
- 重新训练预测模型
- 调整预测阈值
