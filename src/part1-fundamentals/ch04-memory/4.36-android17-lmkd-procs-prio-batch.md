# 4.36 Android 17 LMK_PROCS_PRIO 批量命令与 thrashing 衰减机制

lmkd 中有两个相互独立的机制：

- `LMK_PROCS_PRIO` 位于控制面，让 framework 用较少的 socket packet 更新多个进程的 `oom_score_adj`。
- thrashing 检测位于杀进程决策面，根据 file-backed page cache 的 refault、watermark、swap 和 reclaim 状态决定是否需要释放内存。

批量命令不会改变 OOM 调整算法，thrashing 也不决定 framework 如何计算某个进程的 adj。两者只在 lmkd 选择牺牲进程时相遇：控制面注册的 adj 决定候选优先级，压力决策给出本轮允许搜索到的最低 adj。

平台源码以 `android-17.0.0_r1` 为基准，相关内核统计以 `android17-6.18-2026-06_r6` 为基准。

## 1. lmkd 控制 socket 与命令编号

`lmkd.rc` 将 `/dev/socket/lmkd` 定义为 `seqpacket+passcred`，权限为 `0660 system system`。`passcred` 让 daemon 能获取发送者的 PID、UID 和 GID；lmkd 还会记录某个进程条目由哪个客户端 PID 注册，阻止其他客户端随意修改该记录。

Android 17 的 `include/lmkd.h` 中，命令从 0 依次排列：

| 值 | 命令 | 用途 |
|---:|---|---|
| 0 | `LMK_TARGET` | 更新 minfree/adj target |
| 1 | `LMK_PROCPRIO` | 更新单个进程 |
| 2 | `LMK_PROCREMOVE` | 移除进程记录 |
| 3 | `LMK_PROCPURGE` | 清空注册记录 |
| 4～10 | 查询、订阅、属性更新与 boot 通知 | 其他控制功能 |
| 11 | `LMK_PROCS_PRIO` | 批量更新进程 |

因此，`LMK_PROCS_PRIO` 的 Android 17 枚举值是 11。把它写成 10 会与 `LMK_BOOT_COMPLETED` 冲突。

所有整数字段按 network byte order 放入 packet。批量 payload 中的每条记录占 5 个 `int`：

| 字段 | 含义 |
|---|---|
| `pid` | 目标 thread-group leader PID |
| `uid` | 目标 UID |
| `oomadj` | `oom_score_adj`，有效范围 -1000～1000 |
| `ptype` | `PROC_TYPE_APP` 或 `PROC_TYPE_SERVICE` |
| `for_lmkd_only` | 是否只改 lmkd 内部记录 |

结构体中的 `for_lmkd_only` 是 `bool`，协议仍按一个 32-bit integer 编解码。源码用 `LMK_PROCPRIO_SIZE = 5 * sizeof(int)` 计算 wire size，不能用 C++ 结构体的 `sizeof` 猜测 packet 布局。

## 2. 为什么每个 packet 最多放 3 个进程

lmkd 控制包要容纳两种最大候选：

- `LMK_TARGET`：最多 6 对 `minfree/adj` 加一个 command，共 13 个 `int`。
- `LMK_PROCS_PRIO`：3 条记录，每条 5 个 `int`，再加一个 command，共 16 个 `int`。

所以 `CTRL_PACKET_MAX_SIZE` 在 Android 17 为 64 B。`PROCS_PRIO_MAX_RECORD_COUNT` 按 `64 / 20` 做整数除法，结果是 3。

这个上限是当前协议缓冲和 wire format 的结果，不是 lmkd 一次只能处理三个进程。framework 可以连续发送多个 packet；lmkd 每收到一个 packet，就逐条调用 `apply_proc_prio()`。

### 2.1 Framework 如何组包

`ProcessList.batchSetOomAdj()` 的流程如下：

1. 分配 64 B `ByteBuffer`，先写入 `LMK_PROCS_PRIO`。
2. 跳过 PID 无效或 adj 为 `UNKNOWN_ADJ` 的记录。
3. 每个有效进程写入 PID、UID、当前 adj、`PROC_TYPE_APP` 和 `for_lmkd_only=false`。
4. 累积 3 条后调用 `writeLmkd()`，清空 buffer 并写入下一包的 command。
5. 循环结束后发送最末包。

`OomAdjuster` 在完成一轮 adj 计算和应用后，把待批量更新的进程交给该方法。若有 N 个有效进程，控制 packet 数量从单条模式的 N 个降为 `ceil(N / 3)` 个。

这里减少的是 socket write 和 daemon 收包次数。`LMK_PROCPRIO`/`LMK_PROCS_PRIO` 更新通常不要求每条都返回 reply，称为“往返次数降低”并不准确。批量包也不是事务：

- lmkd 仍按记录顺序逐条应用；
- 某个 PID 已退出时，该条可以失败，前面的记录不会回滚；
- `oom_score_adj` 文件写入和内部索引更新仍分别发生。

### 2.2 lmkd 如何校验和应用

`lmkd_pack_get_procs_prio()` 要求 payload 字段数至少为 5，且能被 5 整除。socket read 又被 `CTRL_PACKET_MAX_SIZE` 限制，所以合法 packet 最多解出 3 条记录。

每条记录进入 `apply_proc_prio()` 后依次检查：

1. `oomadj` 是否落在 -1000～1000。
2. `ptype` 是否在已知枚举范围。
3. `/proc/<pid>/status` 中的 `Tgid` 是否等于 PID，避免把普通线程注册为进程。
4. `for_lmkd_only=false` 时，写 `/proc/<pid>/oom_score_adj`。
5. 使用 userspace lmkd 进程表时，将 PID、UID、adj、pidfd/cgroup fd 和注册者凭据写入内部索引。

旧 in-kernel lowmemorykiller 接口仍启用时，普通更新写完内核 adj 后会保存统计所需名称并返回，不进入 userspace 候选索引。理解 `apply_proc_prio()` 时要先确认设备使用哪种 lmk 实现。

### 2.3 `for_lmkd_only` 的准确边界

该字段为 `true` 时，`apply_proc_prio()` 跳过 `/proc/<pid>/oom_score_adj` 写入，只更新 lmkd 自己维护的候选 adj。它允许 lmkd 候选视图与内核 OOM killer 视图不同。

Android 17 的 `batchSetOomAdj()` 固定发送 false，所以 framework 的批量常规更新会同时尝试写内核 adj。源码没有把这个字段描述成 “speculative ranking”；不应给它添加未经验证的业务语义。

## 3. Thrashing 在 lmkd 中表示什么

lmkd 关注 file-backed page cache 的 workingset refault。页面刚被回收又很快重新访问，会增加 `workingset_refault_file`；持续 refault 意味着回收没有形成稳定空闲空间，还给任务带来 I/O 或 fault 成本。

Android 17 兼容旧字段名：优先读取 legacy `workingset_refault` 的非零值，否则使用 `workingset_refault_file`。kernel 6.18 对应后一个字段。

在一个观察窗口内，lmkd 的基本计算是：

`thrashing = (当前 refault - 窗口起点 refault) * 100 / (窗口起点 file LRU pages + 1)`

其中 file LRU pages 是 `nr_inactive_file + nr_active_file`。`+1` 用于避免分母为零。

这个百分比表示“相对于窗口起点 file LRU 规模，窗口内发生了多少 refault”。它不是 CPU 利用率、I/O wait 百分比，也不是被回收页中有多少页已经再次驻留的精确集合比例。

## 4. 一秒窗口和历史量衰减

`THRASHING_RESET_INTERVAL_MS` 为 1000 ms，但代码运行在 PSI 事件后的状态检查与 polling 中，没有独立的每秒 timer。因此，它是事件驱动的观察窗口，不是严格每秒采样的滚动窗口。

第一次进入或一次成功 kill 后，lmkd 重置：

- `base_file_lru`
- `init_ws_refault`
- `thrashing_reset_tm`
- `prev_thrash_growth`

当本次检查距离窗口起点超过 1 秒时，lmkd 先计算刚跨过窗口的 `prev_thrash_growth`，再得到跨过的窗口数 `windows_passed`。

### 4.1 为什么有时保留上一窗口的 thrashing

源码注释描述了一种情况：上一窗口已经超过阈值，但当时找不到可杀的合格进程。lmkd 希望在新的候选进程出现后继续尝试，所以：

- 只跨过 1 个窗口且 `prev_thrash_growth >= 当前 thrashing_limit` 时，保留该值。
- 跨过多个窗口，或上一窗口低于阈值时，执行 `prev_thrash_growth >>= windows_passed`。
- shift 位数达到 64 时直接清零，避免 C++ 中越界 shift 的未定义行为。

本轮 `thrashing` 最终还会加上这个保留或衰减后的历史量。它提供短期记忆，同时让长时间没有持续 refault 的历史逐渐失去影响。

窗口跨越后，动态 `thrashing_limit` 会恢复为配置基准 `thrashing_limit_pct`。这决定了 kill 后降低阈值的有效期。

## 5. 哪些条件会因 thrashing 触发 kill

Android 17 的 PSI 路径会结合 watermark、swap 和 reclaim 选择 kill reason。以下是与 thrashing 直接有关的分支：

| 条件 | kill reason | 候选 adj 下限 | 是否降低动态阈值 |
|---|---|---:|---|
| swap 低且 thrashing 超过基准阈值 | `LOW_SWAP_AND_THRASHING` | 通常保护 adj ≤ 200；低于 min watermark 或达到 critical thrashing 时放宽 | 否 |
| watermark 低于 high，thrashing 超过动态阈值 | `LOW_MEM_AND_THRASHING` | thrashing 未达 critical 时从 201 开始 | kill 返回正的估算释放页数后降低 |
| direct reclaim 且 thrashing 超过动态阈值 | `DIRECT_RECL_AND_THRASHING` | thrashing 未达 critical 时从 201 开始 | kill 返回正的估算释放页数后降低 |

“候选 adj 下限为 201”表示 `find_and_kill_process()` 从 1000 向下搜索到 201，优先保护 foreground、visible 和 perceptible 一类较重要进程。达到 critical thrashing 后，该保护钳位不再设置，默认下限 0 生效。

这仍不等于“任何优先级都可杀”。搜索范围是 `oom_score_adj >= 0`，负 adj 的 persistent/system 进程不在这一轮候选中。具体进程当前 adj 还取决于 AMS 状态计算和 OEM 修改。

## 6. Kill 后如何降低 thrashing_limit

`LOW_MEM_AND_THRASHING` 或 `DIRECT_RECL_AND_THRASHING` 分支会设置 `cut_thrashing_limit=true`。只有 `find_and_kill_process()` 发出 kill，并返回估算值 `pages_freed > 0` 时，lmkd 才执行：

`new_limit = current_limit * (100 - decay_pct) / 100`

以普通设备源码默认值 `limit=100`、`decay=10` 为例，连续满足条件且每次 kill 都返回正的估算释放页数时，整数计算会得到 90、81、72……。这只是公式示例，设备属性可以覆盖默认值。

阈值在成功发出 kill 后立即降低，不需要先证明目标进程已经退出或回收完成。后续检查若继续满足条件，会更容易进入同一 kill 分支；一旦跨过下一个观察窗口，`thrashing_limit` 恢复为配置基准。成功发出 kill 后，refault 和 file LRU 基线也会在下一轮重置。

所以该机制的准确描述是“在当前短窗口内逐次提高敏感度”。它不是一个读取 kill 前后同一指标并计算控制误差的完整反馈控制器。

## 7. critical thrashing 与 critical stall 是两个条件

### 7.1 `thrashing_limit_critical`

`thrashing_critical_pct` 的 AOSP 默认值为 300。它决定是否取消对 adj ≤ 200 进程的额外保护。达到该阈值后，候选下限通常从 201 放宽到 0。

### 7.2 `critical_stall`

`critical_stall` 来自另一套数据。lmkd 解析 `/proc/pressure/memory`，检查：

`psi_data.mem_stats[PSI_FULL].avg10 > stall_limit_critical`

若本轮已经有 kill reason，并且该条件成立，lmkd 在调用 `find_and_kill_process()` 前把 `min_score_adj` 设为 0。它与 `direct_reclaim_threshold_ms`、`thrashing_limit_critical` 都是独立判断。

AOSP 的 `stall_limit_critical` 默认值是 100；PSI avg10 是百分比，默认比较通常不会成立。设备若通过只读属性或重初始化后的覆盖值降低阈值，critical stall 才可能放宽候选范围。

### 7.3 `direct_reclaim_threshold_ms`

该属性控制 `DIRECT_RECL_STUCK` 分支，源码默认 0，表示关闭。启用时还要求内核 memevent listener 能提供 direct reclaim 起止；缺少支持时 lmkd 会把配置归零并告警。

因此，旧文“thrashing 超过 300 且 direct reclaim 超时后可杀任意进程”的描述把三个不同开关合成了一个条件。

## 8. Android 17 AOSP 默认值

| 属性后缀 | 普通设备默认 | Low-RAM 默认 | 说明 |
|---|---:|---:|---|
| `thrashing_limit` | 100 | 30 | 基准 refault 阈值 |
| `thrashing_limit_decay` | 10 | 50 | 成功 kill 后的动态阈值降幅 |
| `thrashing_limit_critical` | 300 | 300 | 取消 perceptible 保护的 thrashing 阈值 |
| `swap_free_low_percentage` | 10 | 10 | free swap 低水位百分比 |
| `swap_util_max` | 100 | 100 | 高 swap utilization 分支上限；100 默认使该分支不触发 |
| `filecache_min_kb` | 0 | 0 | thrashing 后继续保护 file cache 的下限 |
| `direct_reclaim_threshold_ms` | 0 | 0 | 0 表示关闭 stuck direct reclaim 判断 |
| `stall_limit_critical` | 100 | 100 | PSI memory.full avg10 比较阈值 |

默认值来自 `lmkd.cpp`，产品可以用 `ro.lmk.*` 覆盖。`ro.config.low_ram=true` 只影响源码明确选择 low-RAM 默认的属性，不能推导所有 lmkd 参数都会更激进。

## 9. DeviceConfig 覆盖与 reinit

`GET_LMK_PROPERTY` 先读取 `persist.device_config.lmkd_native.<name>`，没有覆盖值时再读取 `ro.lmk.<name>` 和源码默认值。

`lmkd.rc` 为一组允许实验调整的属性注册 trigger。以 thrashing 为例：

- `persist.device_config.lmkd_native.thrashing_limit`
- `persist.device_config.lmkd_native.thrashing_limit_decay`
- `persist.device_config.lmkd_native.thrashing_limit_critical`

属性改变后，rc 将 `lmkd.reinit` 设为 boot 完成状态。值为 1 时执行 `/system/bin/lmkd --reinit`；该辅助进程连接运行中的 lmkd，发送 `LMK_UPDATE_PROPS` 并读取 reply。boot 尚未完成时，rc 先保留 reinit 标记，boot 完成后再触发。

这套属性是系统和实验基础设施，不是 App SDK。调试前可先只读检查目标设备：

```bash
adb shell getprop ro.config.low_ram
adb shell getprop ro.lmk.thrashing_limit
adb shell getprop persist.device_config.lmkd_native.thrashing_limit
adb shell getprop persist.device_config.lmkd_native.thrashing_limit_decay
```

第一项决定 low-RAM 默认分支；后面三项用于区分只读产品配置与实验覆盖。修改 persistent DeviceConfig 属性会改变系统杀进程策略，应只在可恢复的测试设备上由平台工程师执行，并记录原值。

## 10. 如何观测一次 thrashing kill

lmkd 在成功发出 kill 时写两类证据：

1. `ATRACE_INSTANT_FOR_TRACK`，名称格式为 `lmk,<pid>,<kill_reason>,<oom_score_adj>,<min_score_adj>,<max_thrashing>`。
2. event log 的 `killinfo`（tag `10195355`），字段包含 PID、UID、adj、kill reason、meminfo、Thrashing、MaxThrashing、PSI avg10 和 DMA-BUF PSS/RSS。

Perfetto 没有名为 `lmkd` 的专用 data source。采集 atrace/ftrace 后，Trace Processor 的 `android.memory.lmk` SQL module 会兼容当前 instant event、旧 slice event 和更早的 counter 表示，并暴露 `android_lmk_events`。该表给出 kill 时间、进程、adj 与 reason；详细 thrashing 数值还应结合 `killinfo` event log。

一次完整分析至少对齐：

- kill 前后的 PSI memory some/full；
- `workingset_refault_file`、active/inactive file；
- free swap、watermark 与 reclaim；
- 被杀进程的 `oom_score_adj`、RSS、swap 和 DMA-BUF；
- kill 后 PSI/refault 是否下降，前台卡顿是否恢复。

只看到 `LOW_MEM_AND_THRASHING` reason 还不能证明某个 App 自身制造了 page-cache thrashing。refault 是系统级统计，触发者和牺牲进程可以是不同进程。

## 11. 检查清单

- [ ] `LMK_PROCS_PRIO` 是否按 Android 17 的枚举值 11 解释？
- [ ] 是否区分 packet 数减少与 request/reply 往返？
- [ ] 是否说明一个批量 packet 仍逐条应用、允许部分失败？
- [ ] `for_lmkd_only` 是否只按源码语义描述？
- [ ] thrashing 分母是否使用窗口起点 file LRU pages？
- [ ] 1 秒窗口是否被误写成独立定时器或严格滚动采样？
- [ ] 阈值是否只在成功释放内存后衰减？
- [ ] 是否区分 critical thrashing、PSI critical stall 和 direct reclaim timeout？
- [ ] 候选下限 0 是否被误解为能杀负 adj 进程？
- [ ] 是否将当前 `android17-6.18-2026-06_r6` 作为内核统计锚点？
- [ ] 观测方案是否同时保存系统压力与被杀进程信息？

`LMK_PROCS_PRIO` 优化的是控制面的 packet 数量；thrashing 逻辑保护的是系统在反复 refault 时的可响应性。把控制面 adj、系统级压力和单进程内存证据分开，才能解释一次 kill 为什么发生。
