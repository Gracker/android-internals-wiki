# 4.36 Android 17 LMK_PROCS_PRIO 批量命令与 thrashing 衰减机制

4.4 节介绍了 lmkd 的整体架构与杀进程策略，4.15 节深入了 PSI 内存压力检测链路。本节聚焦 Android 17 上 lmkd 协议的两个工程级改进：**LMK_PROCS_PRIO 批量优先级注册**和 **thrashing 衰减闭环**。前者减少 OOM 调整时的 socket I/O 往返次数，后者通过动态下调 thrashing 阈值避免系统在内存抖动中陷入"杀了但没恢复"的循环。

## LMKD 批量命令机制

### LMK_PROCPRIO → LMK_PROCS_PRIO 的演进

lmkd 通过 `/dev/socket/lmkd` 接收 framework 侧的命令。传统 OOM 优先级更新使用 `LMK_PROCPRIO`（命令枚举值 1），一次只注册一个进程：

```c
// include/lmkd.h (android-17.0.0_r1)
enum lmk_cmd {
    LMK_TARGET = 0,
    LMK_PROCPRIO,           // 单进程优先级注册
    LMK_PROCREMOVE,
    LMK_PROCPURGE,
    LMK_GETKILLCNT,
    LMK_SUBSCRIBE,
    LMK_PROCKILL,
    LMK_UPDATE_PROPS,
    LMK_STAT_KILL_OCCURRED,
    LMK_START_MONITORING,
    LMK_BOOT_COMPLETED,
    LMK_PROCS_PRIO,         // 批量优先级注册 (枚举值 10)
};
```

[已验证: AOSP android-17.0.0_r1, system/memory/lmkd/include/lmkd.h]

`LMK_PROCS_PRIO` 是 `LMK_PROCPRIO` 的批量版本，允许 framework 在一次 socket 写入中注册**最多 3 个进程**的 oom_score_adj。这个上限由宏 `MAX_PROCS_PRIO_RECORD_COUNT` 控制：

```c
#define MAX_PROCS_PRIO_RECORD_COUNT 3
#define LMK_PROCPRIO_FIELD_COUNT 5
#define MAX_CTRL_PACKET_SIZE (LMK_PROCPRIO_FIELD_COUNT * MAX_PROCS_PRIO_RECORD_COUNT + 1)
```

[已验证: AOSP android-17.0.0_r1, system/memory/lmkd/include/lmkd.h]

每个 `lmk_procprio` 包含 5 个字段（`LMK_PROCPRIO_FIELD_COUNT`），因此批量命令的数据包大小为 `(5 × 3 + 1) × sizeof(int) = 64 字节`（含 1 个命令字）。这也成为 `CTRL_PACKET_MAX_SIZE` 的约束之一——lmkd 控制包的最大尺寸必须能容纳一个完整的 `LMK_TARGET`（13 ints）或 `LMK_PROCS_PRIO`（16 ints）。

### 数据结构：lmk_procprio 与 lmk_procs_prio

```c
// 单个进程的优先级记录
struct lmk_procprio {
    pid_t pid;
    uid_t uid;
    int oomadj;
    enum proc_type ptype;       // PROC_TYPE_APP 或 PROC_TYPE_SERVICE
    bool for_lmkd_only;         // true = 仅注册到 lmkd 内部，不写入 /proc/<pid>/oom_score_adj
};

// 批量记录容器
struct lmk_procs_prio {
    struct lmk_procprio procs[PROCS_PRIO_MAX_RECORD_COUNT];
};
```

`for_lmkd_only` 字段值得特别关注。当设为 `true` 时，lmkd 只更新内部数据结构（`proc` 节点的 oomadj），不写 `/proc/<pid>/oom_score_adj`。这用于 framework 和 lmkd 对同一进程持有不同 oomadj 视图的场景——framework 可能因为 speculative ranking 先行调整，但暂不希望影响内核 OOM killer 的判断。

[已验证: AOSP android-17.0.0_r1, system/memory/lmkd/include/lmkd.h, lmkd.cpp:1250-1302]

### lmkd 侧处理：cmd_procs_prio

lmkd 收到 `LMK_PROCS_PRIO` 后调用 `cmd_procs_prio()`：

```c
// lmkd.cpp:1512 (android-17.0.0_r1)
static void cmd_procs_prio(LMKD_CTRL_PACKET packet,
                           const int field_count, struct ucred* cred) {
    struct lmk_procs_prio params;
    const int procs_count = lmkd_pack_get_procs_prio(packet, &params, field_count);
    if (procs_count < 0) {
        ALOGE("LMK_PROCS_PRIO received invalid packet format");
        return;
    }
    for (int i = 0; i < procs_count; i++) {
        apply_proc_prio(params.procs[i], cred);
    }
}
```

`lmkd_pack_get_procs_prio()` 解包时做了字段数校验：`field_count` 必须是 `LMK_PROCPRIO_FIELD_COUNT`（5）的整数倍且 ≥ 5，否则返回 -1。解包后循环调用 `apply_proc_prio()`，该函数是 `LMK_PROCPRIO` 和 `LMK_PROCS_PRIO` 的共用入口：校验 oomadj 范围、验证 pid 是 thread group leader、根据 `for_lmkd_only` 决定是否写入 `/proc/<pid>/oom_score_adj`，最后调用 `register_oom_adj_proc()` 注册到 lmkd 的内部哈希表。

[已验证: AOSP android-17.0.0_r1, system/memory/lmkd/lmkd.cpp:1512-1525, 1250-1302]

### Framework 侧调用：batchSetOomAdj

在 framework 侧，`ProcessList.java` 提供了 `batchSetOomAdj()` 方法：

```java
// ProcessList.java:1557 (android-17.0.0_r1)
public static void batchSetOomAdj(ArrayList<ProcessRecordInternal> apps) {
    final int totalApps = apps.size();
    if (totalApps == 0) return;

    ByteBuffer buf = ByteBuffer.allocate(MAX_OOM_ADJ_BATCH_LENGTH);
    int total_procs_in_buf = 0;
    buf.putInt(LMK_PROCS_PRIO);
    for (int i = 0; i < totalApps; i++) {
        final int pid = apps.get(i).getPid();
        final int amt = apps.get(i).getCurAdj();
        final int uid = apps.get(i).uid;
        if (pid <= 0 || amt == UNKNOWN_ADJ) continue;
        if (total_procs_in_buf >= MAX_PROCS_PRIO_PACKET_SIZE) {
            writeLmkd(buf, null);    // 发送当前批次
            buf.clear();
            total_procs_in_buf = 0;
            buf.allocate(MAX_OOM_ADJ_BATCH_LENGTH);
            buf.putInt(LMK_PROCS_PRIO);  // 开始新批次
        }
        buf.putInt(pid);
        buf.putInt(uid);
        buf.putInt(amt);
        buf.putInt(0);  // PROC_TYPE_APP
        buf.putInt(0);  // for_lmkd_only = false（批量更新不支持）
        total_procs_in_buf++;
    }
    writeLmkd(buf, null);  // 发送最后一批
}
```

关键设计点：

- **MAX_PROCS_PRIO_PACKET_SIZE = 3**：每批发送最多 3 个进程，与 lmkd 的 `MAX_PROCS_PRIO_RECORD_COUNT` 对齐
- **分批发送**：如果 apps 列表超过 3 个，会分多次写入 socket，每次重新构造包头
- **for_lmkd_only 不支持**：批量更新中该字段始终为 0（false），因为批量场景主要用于常规 OOM 调整
- **MAX_OOM_ADJ_BATCH_LENGTH** = `(4 × 5 × 3) + 4 = 64 字节`，恰好对应一个 LMKD 控制包最大尺寸

[已验证: AOSP android-17.0.0_r1, frameworks/base/services/core/java/com/android/server/am/ProcessList.java:1544-1583]

### 批量 vs 单条的性能意义

当系统同时调整大量进程优先级时（如 `OomAdjuster` 更新所有可见/后台进程的 oom_score_adj），传统 `LMK_PROCPRIO` 需要 N 次 socket 写入。批量命令将往返次数降低到 ⌈N/3⌉ 次：

| 进程数 | LMK_PROCPRIO 写入次数 | LMK_PROCS_PRIO 写入次数 | 减少 |
|--------|----------------------|------------------------|------|
| 10     | 10                   | 4                      | 60%  |
| 30     | 30                   | 10                     | 67%  |
| 50     | 50                   | 17                     | 66%  |

`LMK_PROCS_PRIO` 最初在 Android 12 引入，在 Android 17 上保持稳定。它在 `OomAdjuster` 批量更新场景（如屏幕旋转、应用切换）中减少了 lmkd socket 的上下文切换开销。

## Thrashing 衰减策略

### 什么是内存 thrashing

当系统频繁在 page cache 中换入换出页面（workingset refault 飙升），但实际可用内存没有增加时，称为 **thrashing**。此时 CPU 大量时间花在 I/O 等待上，用户体验急剧下降，但传统的 free-memory 阈值可能并未触发 kill——因为 page cache 占用的内存被"回收"后立刻又被换入，free 内存看起来是够的。

lmkd 从 Android 11 起引入 thrashing 检测，通过监控 `workingset_refault_file`（vmstat 中文件支持页面的 workingset refault 计数）来判断是否进入 thrashing 状态。

### Thrashing 计算公式

lmkd 在每次内存压力事件 (`__mp_event_psi`) 中计算 thrashing 比率：

```c
// lmkd.cpp:2949 (android-17.0.0_r1)
/* Calculate what % of the file-backed pagecache refaulted so far */
thrashing = (workingset_refault_file - init_ws_refault) * 100
            / (base_file_lru + 1);
```

- `workingset_refault_file`：当前从 `/proc/vmstat` 读取的累积值
- `init_ws_refault`：上一个 `THRASHING_RESET_INTERVAL_MS` 窗口开始时的基准值
- `base_file_lru`：上一个窗口开始时的文件支持 LRU 页面总数（`nr_inactive_file + nr_active_file`）
- `+1` 防除零

结果是"文件支持页面 cache 的 refault 百分比"。超过 `thrashing_limit` 阈值即判定为 thrashing。

### 衰减窗口：THRASHING_RESET_INTERVAL_MS

thrashing 检测基于一个 **1 秒滚动窗口**：

```c
#define THRASHING_RESET_INTERVAL_MS 1000
```

每隔 1 秒，lmkd 重新计算 `prev_thrash_growth` 并重置基准：

```c
// lmkd.cpp:2944-2970 (android-17.0.0_r1)
since_thrashing_reset_ms = get_time_diff_ms(&thrashing_reset_tm, &curr_tm);
if (since_thrashing_reset_ms > THRASHING_RESET_INTERVAL_MS) {
    long windows_passed;
    /* 重新计算上一窗口的 thrashing 增长 */
    prev_thrash_growth = (workingset_refault_file - init_ws_refault) * 100
                         / (base_file_lru + 1);
    windows_passed = (since_thrashing_reset_ms / THRASHING_RESET_INTERVAL_MS);

    /*
     * 衰减 prev_thrashing，除非上一窗口的 thrashing 超过阈值。
     * 超阈值时保留计数器，确保一旦有新的可杀进程出现就立即 kill。
     */
    if (windows_passed > 1 || prev_thrash_growth < thrashing_limit) {
        if (static_cast<size_t>(windows_passed) < 8 * sizeof(prev_thrash_growth)) {
            prev_thrash_growth >>= windows_passed;  // 按窗口数右移衰减
        } else {
            prev_thrash_growth = 0;  // 窗口数过大则直接归零
        }
    }

    /* 更新基准 */
    base_file_lru = vs.field.nr_inactive_file + vs.field.nr_active_file;
    init_ws_refault = workingset_refault_file;
    thrashing_reset_tm = curr_tm;
    thrashing_limit = thrashing_limit_pct;  // 重置回初始阈值
} else {
    thrashing = (workingset_refault_file - init_ws_refault) * 100
                / (base_file_lru + 1);
}
/* 累加上一窗口的衰减残余 */
thrashing += prev_thrash_growth;
```

衰减的核心机制是 **按窗口数右移**（`>>= windows_passed`）。如果 3 秒没有压力事件，`prev_thrash_growth` 会右移 3 位（除以 8），逐渐"遗忘"历史 thrashing。这是一个指数衰减过程。

[已验证: AOSP android-17.0.0_r1, system/memory/lmkd/lmkd.cpp:2787-2977]

### Kill 后的阈值下调（cut_thrashing_limit）

当 lmkd 因为 thrashing 超限而 kill 了进程，但系统仍未恢复时，lmkd 会**动态下调** thrashing_limit：

```c
// lmkd.cpp:3075-3091 (android-17.0.0_r1)
} else if (wmark < WMARK_HIGH && thrashing > thrashing_limit) {
    // ...
    cut_thrashing_limit = true;
} else if (reclaim == DIRECT_RECLAIM && thrashing > thrashing_limit) {
    // ...
    cut_thrashing_limit = true;
}

// Kill 之后执行下调 (lmkd.cpp:3153-3158)
if (pages_freed > 0) {
    killing = true;
    max_thrashing = 0;
    if (cut_thrashing_limit) {
        /*
         * Cut thrashing limit by thrashing_limit_decay_pct percentage
         * of the current thrashing limit until the system stops thrashing.
         */
        thrashing_limit = (thrashing_limit * (100 - thrashing_limit_decay_pct)) / 100;
    }
}
```

这是一个**负反馈循环**：

1. thrashing 超过 `thrashing_limit` → kill 一个进程
2. 如果 kill 后 thrashing 仍然超标 → 下次 kill 时将 `thrashing_limit` 下调 `thrashing_limit_decay_pct%`
3. 更低的阈值 → 更容易触发 kill → 更积极地释放内存
4. 直到 thrashing 低于（已下调的）阈值 → 系统恢复
5. 下一个 `THRASHING_RESET_INTERVAL_MS` 窗口开始时 → `thrashing_limit` 重置为初始值

举例：默认 `thrashing_limit = 100`、`thrashing_limit_decay_pct = 10`，如果连续触发 cut：

| 轮次 | thrashing_limit | 触发 thrashing 阈值 |
|------|-----------------|---------------------|
| 1    | 100             | thrashing > 100     |
| 2    | 90              | thrashing > 90      |
| 3    | 81              | thrashing > 81      |
| 4    | 72              | thrashing > 72      |

[已验证: AOSP android-17.0.0_r1, system/memory/lmkd/lmkd.cpp:3075-3158]

### Critical stall 检测

除了常规 thrashing，lmkd 还有 **critical stall** 机制，由 `thrashing_limit_critical` 控制（默认 300）：

```c
#define DEF_THRASHING_CRITICAL 300
```

当 thrashing 超过 critical 阈值且伴随 direct reclaim 停顿时（`direct_reclaim_duration_ms > direct_reclaim_threshold_ms`），lmkd 会将 `min_score_adj` 设为 0，允许 kill **任何优先级的进程**（包括 perceptible app），以防止系统彻底卡死。

[已验证: AOSP android-17.0.0_r1, system/memory/lmkd/lmkd.cpp:218-220, 4123-4129]

## 调优属性一览

以下是 Android 17 上 lmkd 的 thrashing 相关 tunable properties：

| 属性 | 高内存设备默认 | 低内存设备默认 | 含义 |
|------|---------------|---------------|------|
| `ro.lmk.thrashing_limit` | 100 | 30 | workingset refault 百分比阈值 |
| `ro.lmk.thrashing_limit_decay` | 10 | 50 | kill 后阈值下调百分比 |
| `ro.lmk.thrashing_limit_critical` | 300 | 300 | critical stall 触发阈值 |
| `ro.lmk.swap_util_max` | 100 | 100 | swap 使用率上限，超过后额外触发 thrashing 检测 |
| `ro.lmk.direct_reclaim_threshold_ms` | — | — | direct reclaim 时长阈值，超过判定为 stall |
| `ro.lmk.filecache_min_kb` | 0 | 0 | 最小文件 cache 要求，低于此值时更激进 kill |

运行时可通过 `persist.device_config.lmkd_native.*` 前缀动态调整（无需重启，lmkd 会 reinit）：

```
adb shell setprop persist.device_config.lmkd_native.thrashing_limit 80
adb shell setprop persist.device_config.lmkd_native.thrashing_limit_decay 15
```

lmkd.rc 中注册了对应的 property trigger，设值后自动触发 `lmkd --reinit`。

## 扩展

### 🔸 低内存设备的差异化策略

低内存设备（`ro.config.low_ram=true`）的 thrashing 阈值显著更严格：`thrashing_limit = 30`（vs 100），`thrashing_limit_decay = 50`（vs 10）。这意味着低内存设备在 thrashing 时更激进地 kill 并更快地下调阈值，因为低内存设备没有余裕让 page cache 抖动。

### 🔸 Perfetto 观察 lmkd thrashing 行为

lmkd 在 kill 时会通过 `android_log_write_int32()` 记录 `thrashing` 和 `max_thrashing` 值（lmkd.cpp:2242-2243）。可以通过 Perfetto 的 `lmkd` 数据源捕获这些事件，观察 thrashing 阈值在 kill 前后的动态变化。详见 4.15 节关于 Perfetto lmkd trace 的说明。

### 🔸 PROCS_PRIO_MAX_RECORD_COUNT 的约束

批量上限为 3 是受 `CTRL_PACKET_MAX_SIZE` 约束——这个大小同时要容纳 `LMK_TARGET`（最多 6 对 minfree/adj = 13 ints）和 `LMK_PROCS_PRIO`（3 × 5 + 1 = 16 ints）。如果要增大批量上限，需要扩大控制包尺寸，这会影响所有 lmkd 命令的内存占用。
