# 4.36 Android 17 高级内存优化与治理

Android 内存诊断需要分别回答四个问题，不能把若干工具简单拼成“高级优化开关”：

1. 系统是否处在内存压力中？
2. 哪个进程分摊了多少物理页？
3. 进程内部由哪些对象、分配调用栈或设备缓冲占用？
4. GC、allocator、内核回收和 lmkd 在什么时刻采取了动作？

四个问题对应不同统计口径。只看 Java heap 无法解释 graphics、file mapping 和 native RSS；只看 PSS 也无法定位对象引用。通常应先缩小层级，再启用更重的 profiler。

平台源码以 `android-17.0.0_r1` 为基准，内核以 `android17-6.18-2026-06_r6` 为基准。内核 tag 用于核对相关 Linux 行为，不表示每台 Android 17 设备必须运行同一个内核版本。

## 4.36.1 从现象选择观测层级

| 现象 | 第一组证据 | 第二组证据 | 相关章节 |
|---|---|---|---|
| App 被 lmkd 杀死或频繁重启 | PSI、系统 meminfo、进程状态、lmkd 记录 | 事发前 PSS/RSS 与工作负载 | §4.15、§4.18 |
| PSS 持续增长 | `dumpsys meminfo`、`smaps_rollup`、完整 `smaps` | Java heap graph 或 native heap profile | §4.35、§14.1 |
| Java heap 增长且 GC 后不降 | ART heap/GC 计数 | Java HPROF 的 dominator 与引用关系 | §4.8、§14 |
| native RSS 或 Native Heap 增长 | `Debug.MemoryInfo`、allocator 指标 | `android.heapprofd` 调用栈 | §8.39、§26.24 |
| graphics/GL 增长 | `dumpsys meminfo`、memtrack、DMA-BUF 统计 | Surface、ImageReader、codec 生命周期 | §4.35 |
| 启动内存峰值 | 启动阶段 Perfetto trace、GC、RSS/PSS | 对峰值时段做定向 heap profiling | §4.21、§8.39 |
| native 越界或 UAF | tombstone、MTE/HWASan 报告 | 同场景复现与分配栈 | §4.9 |
| 推理任务占用过大 | 按 PID/UID 拆分 PSS、mapping、dma-buf | runtime 的权重、KV cache、workspace 记录 | §4.22 |
| Android 17 进程因内存异常退出 | `ApplicationExitInfo`、MemoryLimiter/lmkd 日志、PSI | anon、shmem、swap、PSS/RSS 的事发前时间线 | [§4.17](17-android17-MemoryLimiter-与内存监控影响.md) |

“内存高”本身不是根因。它可能表示存活对象过多、allocator 保留 page、共享页分母变化、文件页驻留、zRAM 交换、驱动缓冲，或某个进程进入了更高负载阶段。

### Android 17 MemoryLimiter 不是 PSS 阈值

Android 17 的 [App memory limits](https://developer.android.com/about/versions/17/behavior-changes-all#app-memory-limits) 只在部分设备启用，阈值由设备配置决定。AOSP [`MemoryLimiter.java`](https://android.googlesource.com/platform/frameworks/base/+/refs/tags/android-17.0.0_r1/services/core/java/com/android/server/am/MemoryLimiter.java) 根据进程状态选择配置，JNI [`MemoryLimiter.cpp`](https://android.googlesource.com/platform/frameworks/base/+/refs/tags/android-17.0.0_r1/services/core/jni/com_android_server_am_MemoryLimiter.cpp) 写入 cgroup v2 `memory.high` 与 `memory.swap.max`，并读取 `memory.stat` 和 `memory.swap.current`。

联合超限判断使用 `anon + shmem + swap.current`，与配置的 memory limit 加 swap limit 比较。它不读取 PSS：PSS 会按共享映射者分摊驻留页，统计口径和 memcg 联合指标不同。`memory.high` 事件也不等于进程已经被终止；MemoryLimiter 会进入自己的检查、可选 profiling 和延迟 kill 流程。

应用没有 MemoryLimiter 专属回调。下次启动可读取 `ApplicationExitInfo`：Android 17 把这类退出报告为 `REASON_OTHER`，description 包含 `MemoryLimiter:AnonSwap`。这条路径还要与 lmkd 分开：MemoryLimiter 检查单进程的设备配置阈值，lmkd 在系统压力下结合进程重要性选择目标。现场只看到 PSS 上升或进程消失时，不能省略退出原因、PSI 和系统日志。

## 4.36.2 Perfetto 中与内存有关的四个数据源

Android 17 源码中可确认的核心数据源如下：

| 数据源名 | Producer / 探针 | 采集内容 | 关键限制 |
|---|---|---|---|
| `linux.process_stats` | `traced_probes` | `/proc/<pid>/status`、`oom_score_adj`；可选 `smaps_rollup` | 周期采集下限 100 ms；rollup 受 ptrace/procfs 权限限制 |
| `linux.sys_stats` | `traced_probes` | `/proc/meminfo`、`vmstat`、PSI、buddyinfo 等可选计数器 | 各 poll period 要满足配置约束；项目需显式开启 |
| `android.heapprofd` | `HeapprofdProducer` | native heap 的采样分配、释放和调用栈 | 采样会增加 CPU、内存和分配路径成本 |
| `android.java_hprof` | `JavaHprofProducer` + ART | managed heap graph 快照 | dump 较重，需要目标进程满足 profile 权限 |

不存在名为 `linux.system_memory` 或 `android.memory` 的同类采集数据源。Perfetto UI 中的 Process Memory、Heap Profile 等轨道，以及 Trace Processor 中 `android.memory.*` SQL module，是对 trace packet 的显示或派生分析，不能把显示名称抄回数据源配置。

### `linux.process_stats` 默认没有完整 PSS

`ProcessStatsConfig` 的注释和实现说明：

- `proc_stats_poll_ms` 大于 0 时，周期读取 `/proc/<pid>/status` 和 `oom_score_adj`。
- 小于 100 ms 的值会被提高到 100 ms。
- 只有显式打开 `scan_smaps_rollup`，才把 `/proc/<pid>/smaps_rollup` 内容并入解析。
- Android 上读取其他进程的 rollup 需要通过 ptrace 检查，还可能受 `hidepid` 和 SELinux 限制。配置文件明确提示，系统 daemon 场景默认不能依赖该选项。

所以，看到 Perfetto 中有 RSS 曲线，不表示 trace 同时采到了 PSS、USS 和 Android heap 分类。录制前应先确认配置和权限。

### `linux.sys_stats` 负责系统压力背景

`SysStatsConfig` 可以分别轮询：

- `/proc/meminfo`
- `/proc/vmstat`
- `/proc/stat`
- `/proc/buddyinfo`
- `/proc/pressure/*`
- CPU/GPU/devfreq、thermal 和 cpuidle 等平台计数器

这些数据用于解释“进程增长发生在怎样的系统环境中”。例如，PSS 增长与 PSI memory stall 同时出现，说明工作负载可能进入回收竞争；只有 PSS 增长而 PSI 平稳，则应优先检查对象生命周期、mapping 和共享关系。

采样不是越密越好。`SysStatsConfig` 对大多数相关周期要求大于 10 ms，`process_stats` 要求至少 100 ms，这些只是源码守门值，不是推荐的生产配置。周期还要按设备规模、trace 时长和可接受 overhead 评估。

## 4.36.3 heapprofd 与 Java HPROF：同一 daemon 中的两个 Producer

Android 17 的 `external/perfetto/src/profiling/memory/heapprofd.cc` 在 central daemon 中创建两个对象：

- `HeapprofdProducer` 注册 `android.heapprofd`；
- `JavaHprofProducer` 注册 `android.java_hprof`。

它们共用 `/system/bin/heapprofd` 进程和 task runner，但分别连接 tracing service，数据模型也不同。源码中的 TODO 仍写着后续可合并 producer 管理，说明当前实现不能当成一个统一 Producer。

对已经运行的目标进程，native heap profiling 使用 `__SIGRTMIN + 4`，Java heap dump 使用 `__SIGRTMIN + 6`。信号只负责通知目标进入相应 profiling 协议；native 分配采样和 managed heap graph 仍由不同的客户端代码完成。

### 4.36.3.1 `android.heapprofd` 回答分配调用栈问题

`HeapprofdConfig` 的核心字段是 `sampling_interval_bytes`：值为 1 时追求逐次分配精度，其他正值表示平均每分配若干字节取样。该字段必须为非零值，除非所有目标 heap 都通过 `heap_sampling_intervals` 给出非零配置。

目标可按 `process_cmdline`、PID 和安装来源筛选，还可以选择命名 heap。配置中的 `all` 表示尝试 profile 系统中所有符合资格的进程；proto 警告它可能让未修改的 userdebug 系统因 zygote 持有意外 socket 而崩溃，也可能压垮 heapprofd。生产诊断不应把 `all=true` 当作“完整性优先”的普通选项。

heapprofd 适合回答：

- 哪些 native 调用栈贡献了当前 sampled heap；
- 分配和释放在采样窗口内如何变化；
- 某个改动是否减少了特定调用栈的存活分配；
- 自定义注册 heap 是否贡献了异常增长。

它不能直接解释所有 native RSS。allocator 元数据、未注册分配器、线程栈、JIT/code mapping、文件映射、共享内存和设备缓冲可能不在 `libc.malloc` 的采样结果里。

### 4.36.3.2 `android.java_hprof` 回答对象可达性问题

`JavaHprofConfig` 可以按 cmdline 或 PID 选择目标，支持单次或连续 dump，并可忽略指定类型。Producer 在发 `__SIGRTMIN + 6` 前读取目标 `/proc/<pid>/status`，通过 `CanProfile()` 检查 UID 与 profiling 资格。

Java heap graph 适合分析：

- 某类对象实例数和 retained size；
- dominator；
- 从 GC root 到对象的引用关系；
- dump 之间仍存活的对象集合。

它是重量级快照，不是每次 Java 分配的实时事件流。连续 dump 会多次暂停和遍历 managed heap，必须先在测试设备上评估对停顿、trace 大小和目标进程内存的影响。

### 4.36.3.3 daemon 如何启动

`heapprofd.rc` 把主服务定义为 `class late_start`、`disabled`，并提供名为 `heapprofd` 的 Unix socket。两个属性触发服务启动：

- `persist.heapprofd.enable=1`
- `traced.lazy.heapprofd=1`

第二个属性用于 tracing service 的按需启动。普通应用不能把设置系统属性当作公开 API；实际可用范围还受 build type、profileable/debuggable、SELinux 和目标安装来源影响。

## 4.36.4 profiler guardrail 只在配置后生效

旧文给 heapprofd 写了固定的 `max_samples`、local cache 数量和 5 秒 client timeout，这些不是 Android 17 `HeapprofdConfig` 的三层默认守门值。

当前源码可直接配置的保护项包括：

| 配置 | 作用 |
|---|---|
| `max_heapprofd_memory_kb` | daemon 超过指定匿名 RSS + swap 后停止该数据源 |
| `max_heapprofd_cpu_secs` | daemon 为该数据源累计 CPU time 超过上限后停止 |
| `adaptive_sampling_shmem_threshold` | 共享缓冲剩余空间不足时提高采样间隔 |
| `adaptive_sampling_max_sampling_interval_bytes` | 限制自适应采样能增大到的间隔 |
| `shmem_size_bytes` | 设置目标进程与 heapprofd 之间共享缓冲大小 |
| `block_client` / `block_client_timeout_us` | 缓冲满时阻塞客户端以及可选超时 |

CPU 和 memory guardrail 的 0 值表示不启用对应限制。`block_client` 会直接拖慢目标进程，只适合明确接受停顿风险的诊断。采样 interval 越小，调用栈 unwind、传输和聚合开销通常越高，但不能给所有设备套用固定的 CPU 百分比。

一组可复现的 heapprofd 对比至少要保存：

- Perfetto config 原文；
- App 构建、设备 build type 与 profileable 状态；
- 目标 cmdline/PID；
- 采样间隔和命名 heap；
- trace 时长、业务工作量与 profiler 是否丢数据；
- profiler 开启前后的 CPU time、长尾延迟和内存。

## 4.36.5 PSS、allocator 与 heap profile 的关系

这三类数据回答不同问题：

| 数据 | 统计主体 | 适合回答 |
|---|---|---|
| `Debug.MemoryInfo` / smaps | 物理页及映射 | 进程分摊了多少驻留页、swap 和设备内存 |
| allocator 指标 | 分配器管理的地址范围/chunk | native heap 已分配、空闲和保留多少 |
| heap profile / heap graph | sampled allocation 或 managed object | 哪些调用栈/对象仍占用 |

Android 17 的详细 `Debug.MemoryInfo` 读取完整 `/proc/<pid>/smaps`，按 VMA 名称分类为 Dalvik、Native 和 Other，再加入 smaps 尚未核算的 memtrack 结果。`Debug.getPss(pid, ...)` 才使用 libmeminfo 的 rollup/完整 smaps 汇总选择。`mallinfo()` 只服务于 native heap size/allocated/free API，不是 Native PSS 后端。

`MemoryInfo.getTotalPss()` 把 Dalvik、Native、Other 的 PSS 与 SwapPss 相加；`getTotalUss()` 是三类 `Private_Clean + Private_Dirty` 之和。PSS 由内核依据 page/folio mapcount 分摊，不是 `Shared_Clean` 乘某个 Android 侧缓存比例。

下面几种看似矛盾的结果都可能成立：

- native allocated bytes 下降，RSS 不降：allocator 仍保留 page，或空闲范围还不能归还。
- heap profile 的存活采样稳定，PSS 上升：变化来自 file mapping、stack、graphics、共享分母或 swap。
- Java heap committed 大，PSS 较小：部分虚拟范围尚未触页，或 page 已被回收。
- 杀死一个共享库映射者后，其他进程 PSS 上升：共享页分母变小。

## 4.36.6 ART 启动期策略：阈值调整与定时维护任务

Android 17 的 ART 使用 `gc::TaskProcessor` 执行到期的 `HeapTask`。`task_processor.h` 中的队列是按 `target_run_time` 排序的 `std::multiset`；`GetTask()` 等待最早任务到期，`RunAllTasks()` 调用任务的 `Run()` 和 `Finalize()`。

### post-fork 期间做了什么

`Heap::PostForkChildAction()` 先把 `target_footprint_` 提高到 `growth_limit_`，并重设 concurrent GC 起点，以减少应用启动早期触发 GC 的机会。随后：

1. 安排一个或两个 `ReduceTargetFootprintTask`，逐步降低 target footprint。
2. 安排 `TriggerPostForkCCGcTask`。
3. 两类任务都记录 post-fork 时的 GC 编号；如果期间已经发生 GC，任务会成为 no-op 或不再重复请求。

这是一段临时的 GC 阈值策略，不是“启动阶段禁止 GC”。应用仍可能因达到 growth limit、显式请求、进程状态变化或其他条件触发 GC。两个 Reduce 任务也只在 `initial_heap_size_ < growth_limit_` 等条件成立时入队，不能固定称为每个 App 都有“两次收缩”。

### `StartupCompletedTask` 不调用 `Heap::Trim()`

应用调用 `VMRuntime.notifyStartupCompleted()` 时，会把 `StartupCompletedTask` 以当前时间加入队列；若应用没有通知，zygote child 初始化还安排一个 5 秒后的兜底任务。

任务运行时可以：

- 通知 runtime 启动完成；
- 在满足条件时生成临时 runtime app image；
- 解除 startup dex cache；
- 释放 startup linear alloc 和 app image metadata；
- 删除用于 app image loading 的 thread pool。

这段 `Run()` 没有调用 `Heap::Trim()`。Heap trim 由 `HeapTrimTask` 和 `RequestTrim()` 等其他路径处理。`VMRuntime.runHeapTasks()` 进入 TaskProcessor 主循环，也不能当作 App 启动时可随意调用的“排空 pending 任务”优化 API。

开发者能控制的重点仍是启动期工作量：延迟非首屏需要的初始化，减少短命大对象和重复解码，避免把 `System.gc()` 当作启动优化手段，并用 trace 验证 GC 是否落在关键区间。

## 4.36.7 kernel 6.18 侧：压力、回收与碎片要分开看

相关内核行为以 `android17-6.18-2026-06_r6` 为源码锚点。不能用“Android 17 基于 Linux 6.1，同时统一 backport 6.10 特性”概括所有设备。

三个常被混在一起的状态如下：

| 状态 | 典型证据 | 含义 |
|---|---|---|
| 内存压力 | PSI memory、reclaim、refault、swap、lmkd | 任务因回收或内存争用发生 stall |
| 物理碎片 | buddyinfo、compaction trace、order allocation failure | 空闲总量可能足够，但目标 order 难以满足 |
| 虚拟地址碎片/allocator 碎片 | VMA、allocator statistics、heap profile | 进程地址空间或分配器内部难以复用 |

proactive compaction 不是 Android 17 或 Linux 6.10 才出现的通用新能力。它能在后台整理 pageblock，也会消耗 CPU 和内存带宽；是否启用、阈值和收益由内核配置与设备工作负载决定。App 的普通 `mmap()` 只要求连续虚拟地址，不等价于请求高阶连续物理页。GPU/camera buffer 是否需要连续物理内存，要看 dma-buf heap、IOMMU 和驱动约束。

因此，遇到“大块 mmap 很慢”时不能直接归因于 compaction。至少要区分 page fault、文件 I/O、zero-fill、allocator 锁、驱动 ioctl 和高阶页分配。

## 4.36.8 MTE 是内存安全能力，不是 PSS 优化项

MTE 为每个 16 B allocation granule 关联 4-bit allocation tag，并在指针中携带 logical tag。16:1 描述的是 tag 检查粒度，不能直接得出“进程内存固定增加 6.25%”：allocation tag 的物理存储由硬件和平台实现，普通进程的 RSS/PSS 也不把它当作每 16 B 额外映射 1 B。

MTE 的价值是发现 native heap、stack 或 globals 上满足标记条件的越界和 use-after-free。开启范围由 CPU、内核、mapping、编译插桩、bionic/Scudo 和 manifest 配置共同决定。`android:memtagMode` 不是只在 userdebug 生效的关闭开关，具体可用模式和系统覆盖规则见 §4.9。

性能评估应比较同一设备、同一 build 和同一工作量下的 off、ASYNC/设备实际首选模式与 SYNC，同时记录 CPU time、长尾延迟、RSS/PSS 和 MTE 报告可归因性。

## 4.36.9 一套逐级加深的诊断步骤

### 第一步：确认用户可见问题和时间区间

记录场景、输入、设备温度、前后台状态、进程重启、耗时和失败点。没有稳定复现窗口，后续工具很难对齐。

### 第二步：先采轻量系统与进程计数

使用 `linux.sys_stats`、`linux.process_stats`、调度/fault/reclaim 事件，以及必要的 `dumpsys meminfo` 快照。先判断是系统压力、单进程增长、交换，还是设备内存变化。

### 第三步：按归因方向启用 profiler

- managed heap 异常：Java HPROF。
- native heap 异常：heapprofd。
- graphics/dma-buf：memtrack、服务生命周期和设备接口。
- 碎片或回收延迟：buddyinfo、vmstat、PSI、compaction/reclaim 事件。
- native 内存错误：MTE 或 HWASan。

一次只增加必要的数据源。这样容易量化 profiler 对目标进程和系统的扰动。

### 第四步：用同一工作量验证

优化前后保持 Perfetto config、采样 interval、设备状态和业务输入一致。比较单位工作量指标，例如每次操作后的 retained objects、每分钟存活 native allocation、稳定态 PSS、峰值 RSS、PSI stall 和长尾耗时。

### 第五步：把“释放”拆成四个状态

1. 业务不再引用对象。
2. GC 或 allocator 已把对象/chunk 标为空闲。
3. allocator/runtime 已把 page 交还内核或允许回收。
4. 内核已回收，RSS/PSS 快照反映下降。

四个状态可能相隔多个时刻。对象不可达后 PSS 没有立即下降，不足以证明泄漏；PSS 暂时下降也不能证明引用关系已经修复。

## 4.36.10 检查清单

- [ ] Perfetto 配置使用的是源码存在的数据源名。
- [ ] `linux.process_stats` 是否显式启用 `scan_smaps_rollup`，权限是否满足。
- [ ] heapprofd 与 Java HPROF 是否按采样分配和对象图分别解释。
- [ ] 是否记录 sampling interval、目标进程和 guardrail。
- [ ] 是否避免 `all=true` 以及无约束的逐分配采样。
- [ ] PSS、RSS、USS、SwapPss 和 allocator 指标是否保持各自口径。
- [ ] ART post-fork 策略是否被误写为绝对 GC 禁止。
- [ ] `StartupCompletedTask` 是否被误写成自动调用 `Heap::Trim()`。
- [ ] 内核结论是否锚定 `android17-6.18-2026-06_r6`，同时注明设备差异。
- [ ] MTE 的 16 B granule 是否被误算成固定 PSS 开销。
- [ ] MemoryLimiter 的 anon + shmem + swap 是否与 PSS 分开解释，并与 lmkd 分开归因。
- [ ] 所有固定百分比和耗时是否有目标设备 benchmark 支撑。

- [Perfetto `ProcessStatsConfig`](https://android.googlesource.com/platform/external/perfetto/+/refs/tags/android-17.0.0_r1/protos/perfetto/config/process_stats/process_stats_config.proto) 与 [`SysStatsConfig`](https://android.googlesource.com/platform/external/perfetto/+/refs/tags/android-17.0.0_r1/protos/perfetto/config/sys_stats/sys_stats_config.proto)：进程和系统轮询字段。

- [ART `task_processor.cc`](https://android.googlesource.com/platform/art/+/refs/tags/android-17.0.0_r1/runtime/gc/task_processor.cc) 与 [`heap.cc`](https://android.googlesource.com/platform/art/+/refs/tags/android-17.0.0_r1/runtime/gc/heap.cc)：HeapTask 队列、post-fork 与 startup-completed 行为。

高级内存诊断应让每一份数据回答一个边界清楚的问题，再用统一时间轴验证它们之间的先后关系。一次打开过多数据源只会增加扰动和归因难度。
