## MTE 硬件架构演进：从 FEAT_MTE 到 FEAT_MTE4

ARM Memory Tagging Extension（MTE）是 ARMv8.5 架构引入的硬件级内存安全检测技术，通过在指针和内存块上分别打上 4-bit 标签（Tag），由 CPU 硬件在 load/store 指令执行时自动比对二者是否匹配，实现接近零开销的内存越界检测。

MTE 的架构演进经历了四个版本：

| MTE 版本 | 架构版本 | 年份 | 核心增量 |
|----------|---------|------|---------|
| FEAT_MTE | Armv8.5 | 2018 | 确立指令规范（IRG/STG 等） |
| FEAT_MTE2 | Armv8.5 | 2018 | 完全体：Tag 物理存储 + 硬件检测 + Sync/Async 双模式 |
| FEAT_MTE3 | Armv8.7 | 2020 | 引入 Asymmetric 检测模式 |
| FEAT_MTE4 | Armv8.9 | 2022 | Enhanced MTE：Canonical Check 等安全增强 |

[已验证: ARM 架构手册, developer.arm.com]

**FEAT_MTE** 确立了指令接口规范，引入了 `IRG`（Insert Random Tag）、`STG`（Store Tag）等专用指令，确保了软件生态的向前兼容性。

**FEAT_MTE2** 是真正意义上的完全体，打通了 Tag 的生成、物理存储和硬件检测链路，并定义了 Synchronous（同步）和 Asynchronous（异步）两种基础检测模式。

**FEAT_MTE3** 引入了 Asymmetric（非对称）检测模式：读操作采用同步检测（精确报错），写操作采用异步检测（低开销）。这一模式在性能与安全之间提供了优雅的平衡点。

**FEAT_MTE4**（也称 Enhanced MTE）通过 Canonical Check 等特性修补了未标记内存访问的安全漏洞。苹果在 iPhone 17（2025 年 9 月）中以"MIE（Memory Integrity Enforcement）"的名义落地了基于 FEAT_MTE4 的完整内存安全方案。

[来源: Cubox/四年之后，重新审视 MTE：从硬件架构到工程落地-2025-12-18.md]

### Tag 存储模型

MTE 的 Tag 存储采用物理地址线性映射方式：

```
Tag_PA = Base + (Data_PA >> 5)
```

每 32 字节的内存块对应 1 字节的 Tag 存储（实际仅使用 4 bit）。这意味着对于 32GB 的物理内存，需要预留约 1GB（1/32）的物理空间存储 Tag。这段内存在 Bootloader 阶段被 Carve-out，操作系统完全不可见。

ARM 曾提出 **vMTE**（Virtual Memory Tagging Extension）架构展望，将 Tag 存储从物理地址映射改为页表映射，实现按需分配。这将从根本上消除 Tag 存储的静态内存开销。

[已验证: ARM 官方博客, developer.arm.com/community/blogs]

## Tag 生成与硬件检测机制

### Tag 生成

MTE 使用 4-bit Tag，取值范围 0-15。Tag 通过以下机制工作：

1. **指针 Tag**：利用 AArch64 的 TBI（Top Bytes Ignore）特性，地址的高 4 位（bit 56-59）存储 Tag 值。MMU 在地址翻译时忽略这些位。
2. **内存 Tag**：存储在专用的 Tag 空间中，通过 `STG` 指令写入。每个 32 字节对齐的内存块对应一个 Tag。
3. **随机 Tag 生成**：`IRG`（Insert Random Tag）指令从 `GCR_EL1` 寄存器指定的允许集合中随机选取一个 Tag 值。

在 Android 中，系统通过 `GCR_EL1` 排除 Tag 0，只允许生成 1-15 的 Tag。Tag 0 被保留给 Scudo 内存分配器的 Chunk Header——这样任何溢出踩踏到头部元数据的行为都会因 Tag 不匹配而被立即检测到。

[已验证: AOSP android-17.0.0_r1, bionic/libc/platform/bionic/mte.h]

### CPU 检测流程

当 CPU 在用户态执行一条带 Tag 的 load/store 指令时，检测按以下顺序进行：

1. **TCO 检查**：首先检查 `PSTATE.TCO` 寄存器。若 TCO=1，当前线程处于免检状态（Tag Checking Off），直接跳过所有 Tag 检查。Scudo 在内存初始化等特殊时刻通过 `msr tco, #1` 指令临时开启免检。

2. **TLB 属性检查**：CPU 检查访问地址在 TLB 中的 MTE 属性位。只有页表项（PTE）标记了 `PROT_MTE` 的内存页才会触发硬件 Tag 比对。

3. **Tag 比对**：硬件比较器将指针 Tag（高 4 位）与内存 Tag（从 Tag 存储读取）进行比对。匹配则正常执行；不匹配则根据 `SCTLR_EL1.TCF0` 字段决定处理方式。

[已验证: ARM Architecture Reference Manual]

## 三种检测模式的 CPU 流水线级分析

MTE 的核心设计权衡在于检测精度与性能开销的平衡。三种检测模式的差异本质上体现在 CPU 流水线的不同处理时机上。

### SYNC（同步模式）

- **行为**：Tag 不匹配时，CPU 立即产生同步异常，内核捕获后发送 `SIGSEGV(MTESERR)` 信号
- **异常精确性**：精确指向出错指令，调试价值最高
- **性能开销**：变化范围大（3%-30%，取决于 workload），主要来源是 store 操作的流水线阻塞

对于 store 指令（`str x0, [x1, #0x8]`），同步模式要求 Tag 检测必须在指令退休（retire）前完成。由于 Tag 读取涉及 Cache 访问（高延迟），这条 store 指令在 ROB（Reorder Buffer）中长时间驻留，一旦到达 ROB 头部就会阻塞后续已完成指令的提交，最终导致整个流水线停顿。

### ASYNC（异步模式）

- **行为**：Tag 不匹配时记录异常但不中断执行，延迟到下一次内核进入（如系统调用）时结算，发送 `SIGSEGV(MTEAERR)` 信号
- **异常精确性**：无法精确指向出错指令，仅知道进入内核时存在不匹配
- **性能开销**：约 1%-2%（ARM 官方 Benchmark 数据）

异步模式下，store 指令只要数据和地址进入 Store Buffer（SB），ROB 即认为该指令逻辑完成。Tag 读取和检测完全推迟到指令退休之后——此时数据真正写入 Cache 时才执行 Tag 检查。后续指令可通过 Store-to-Load Forwarding 直接从 SB 获取数据，完全绕过 Cache。从流水线吞吐率角度看，异步模式的 Tag 检测实现了真正的"无感"。

### ASYMM（非对称模式）

- **行为**：读操作采用同步检测（精确报错），写操作采用异步检测（低开销）
- **异常精确性**：读操作可精确定位，写操作延迟报告
- **性能开销**：与 ASYNC 基本一致（约 1%-2%），因为 ldr 的同步检测几乎不增加开销

关键洞察：对于 load 指令，同步和异步的性能差异可忽略不计。因为 ldr 的 Tag 检测是一个简单的比较逻辑，与数据读取并行进行，在 ldr 整体执行时间（主体是与 Cache 交互的时间）中几乎可以忽略。ASYMM 正是基于这一洞察，在不增加可感知性能开销的前提下，显著提升了读操作的安全精度。

[来源: Cubox/四年之后，重新审视 MTE：从硬件架构到工程落地-2025-12-18.md]
[已验证: ARM 官方博客与用户手册]

### 性能开销汇总

| 模式 | CPU 开销 | 内存开销 | 适用场景 |
|------|---------|---------|---------|
| ASYNC | ~1-2% | ~3%（Tag 存储） | 生产环境 |
| ASYMM | ~1-2% | ~3% | 生产环境（安全性更优） |
| SYNC | 3-30% | ~3% + 调用栈记录 | 测试 / 调试 |

ASYNC 额外开销的三个来源：
1. Tag 数据需要加载到 Cache，Cache Miss 时产生额外总线传输
2. Tag 占用 Cache 空间，导致 Cache Miss 率上升
3. `IRG`/`STG` 等管理指令本身的执行开销

## 内核 MTE 管理与 prctl 接口

### PROT_MTE：单向开关

Linux 内核为 MTE 提供了 `PROT_MTE` 内存保护标志。通过 `mmap` 或 `mprotect` 可以将内存页标记为 MTE 保护区域，内核会在对应 PTE 中打上标记，最终被加载进 TLB 生效。

**关键约束**：`PROT_MTE` 一旦设置便无法通过 `mprotect` 清除。这是基于两点考虑：

1. **生态兼容**：历史上大量代码（如 JIT 内存区域的 `mprotect` 权限切换）不会考虑保留 `PROT_MTE` 标志，允许清除将导致 MTE 被意外失效
2. **语义安全**：如果允许 `PROT_MTE` 被清除后重新开启，内存的 Tag 将被清零，而仍持有带 Tag 指针的代码将引发大面积误报

[已验证: Linux kernel 文档, docs.kernel.org/arch/arm64/memory-tagging-extension.html]

### 线程级与 CPU 级控制

MTE 检测策略在两个层级进行控制：

**线程级（per-thread `mte_ctrl`）**：每个线程的 `mte_ctrl` 决定其 MTE 检测模式和 Tag 范围。线程切换时，内核负责同步 `SCTLR_EL1` 和 `GCR_EL1` 寄存器。因此 MTE 策略本质上是线程绑定的，而非 CPU 绑定的。

**CPU 级（per-CPU `mte_tcf_preferred`）**：每个 CPU 核心有自己的 `mte_tcf_preferred` 变量，提供"升舱"机制。例如线程请求 ASYNC，但当前 CPU 的 `mte_tcf_preferred` 为 ASYMM，则实际运行模式升级为 ASYMM。这一升级发生在内核/硬件层，应用层完全无感知。

```
/sys/devices/system/cpu/cpu<N>/mte_tcf_preferred
```

OEM 厂商可在设备启动时向该 sysfs 节点写入 `asymm`，使得所有请求 ASYNC 的进程自动升级为 ASYMM 运行。

[已验证: AOSP android-17.0.0_r1, kernel arch/arm64/kernel/mte.c]

### heap_tagging_level 的单向性

类似地，`heap_tagging_level` 也具有单向性：从 `M_HEAP_TAGGING_LEVEL_NONE` 切换到任何检测模式是不允许的。因为关闭期间 Scudo 不再管理 Tag，释放的内存被复用后 Pointer Tag（为 0）与 Memory Tag（残留）不匹配。虽然关闭期间不检测不会出问题，但一旦重新开启，将导致大面积崩溃。

[已验证: AOSP android-17.0.0_r1, bionic/libc/bionic/malloc_common.cpp]

## Bionic/Scudo MTE 集成链路

### 进程启动时的 MTE 配置链路

Android 进程启动分为两条路径，MTE 的初始化方式也不同：

**路径一：Native 可执行文件（Dynamic Loader 主导）**

Linker 在加载依赖库之前，按以下优先级决定 MTE 策略：

1. 环境变量 `MEMTAG_OPTIONS`（最高优先级）
2. 系统属性 `arm64.memtag.process.{basename}`
3. 常驻属性 `persist.arm64.memtag.default`
4. 云端属性 `persist.device_config.memory_safety_native.mode_override.process.{basename}`
5. ELF Dynamic Section 中的 `DT_AARCH64_MEMTAG_MODE`（最低优先级）

**路径二：Java 进程（Zygote 主导）**

Java 进程 fork 自 Zygote，跳过了 Dynamic Loader 环节。AMS 按以下优先级获知 MTE 策略，在 Zygote Specialize 阶段通过 `mallopt` 写入子进程：

1. `persist.arm64.memtag.app.{PackageName}`（最高优先级）
2. Manifest `<process>` 标签的 `android:memtagMode`
3. Manifest `<application>` 标签的 `android:memtagMode`
4. 开发者选项兼容性配置（`am compat enable/disable NATIVE_MEMTAG_*`）
5. `persist.arm64.memtag.app_default`（最低优先级）

特殊升舱规则：当上述配置解析为 ASYNC 时，若设备为 USERDEBUG/ENG 版本且 `persist.arm64.memtag.default` 为 SYNC，则自动升舱为 SYNC。

[已验证: AOSP android-17.0.0_r1, frameworks/base/core/java/com/android/internal/os/Zygote.java]

### Bionic __libc_init_mte() 初始化

Bionic 的 `__libc_init_mte()` 是连接上层策略与底层实现的核心函数，在进程启动早期被调用：

```cpp
// bionic/libc/bionic/libc_init_common.cpp
// 简化伪代码
void __libc_init_mte() {
    // 1. 尝试 SYNC 模式（若策略要求）
    if (prctl(PR_SET_TAGGED_ADDR_CTRL, prctl_arg | PR_MTE_TCF_SYNC, ...) == 0 ||
        // 2. 回退到请求的模式
        prctl(PR_SET_TAGGED_ADDR_CTRL, prctl_arg, ...) == 0) {
        // 3. 配置 Scudo 的 heap tagging level
        __libc_shared_globals()->initial_heap_tagging_level = level;
        __libc_shared_globals()->initial_memtag_stack = memtag_stack;
        // 4. 为栈设置 PROT_MTE
    }
}
```

`heap_tagging_level` 作为 Bionic 的全局静态变量，通过 `mallopt(M_BIONIC_SET_HEAP_TAGGING_LEVEL)` 可动态调控，控制三件事：
- Scudo 分配的内存页是否标记 `PROT_MTE`
- 内存分配时是否生成随机 Tag 并通过 `STG` 写入
- `malloc`/`free` 时是否记录调用栈（用于可调试性）

[已验证: AOSP android-17.0.0_r1, bionic/libc/bionic/libc_init_common.cpp]

### 应用层不暴露 ASYMM

Android 框架层（`ApplicationInfo.java` 和 `Zygote.java`）仅定义了四种 memtagMode 枚举：

```java
// frameworks/base/core/java/android/content/pm/ApplicationInfo.java
public static final int MEMTAG_OFF = 0;
public static final int MEMTAG_DEFAULT = 1;
public static final int MEMTAG_ASYNC = 2;
public static final int MEMTAG_SYNC = 3;
```

**没有 `MEMTAG_ASYMM`**。ASYMM 是纯设备侧机制，不能通过 manifest 配置。当设备 `mte_tcf_preferred` 写入 `asymm` 时，请求 ASYNC 的进程在该 CPU 上会被内核静默升级。应用层对此完全无感知，`prctl` 返回仍报告 ASYNC 成功。

[已验证: AOSP android-17.0.0_r1, ApplicationInfo.java + Zygote.java]
[来源: DeepResearch/2026-05-26-android-mte-asymm-auto-enablement-mechanism.md]

## Android 17 MTE 增进：栈与全局变量检测

### Stack Tagging

Android 对 MTE Stack Tagging 的支持经历了漫长的成熟过程：

- Android 14 QPR3（2024 年中）：初次宣布支持
- Android 16（2025 年）：比较完整的代码支持
- Android 17（2026 年）：成熟可用阶段

Stack MTE 的核心逻辑发生在 LLVM 编译阶段。使用 `-fsanitize=memtag-stack` 编译时，LLVM 在函数入口（Prologue）处对当前 SP 执行 `IRG` 指令生成带随机 Tag 的基地址，为每个局部变量分配递增 Tag。函数返回（Epilogue）前擦除/重置 Tag。这使得只有在函数生命周期内的局部变量访问才是合法的，越界访问和使用后返回（Use-After-Return）均可被检测。

启用 Stack MTE 需要三步配合：
1. 将线程栈 remap/mprotect 为 `PROT_MTE`
2. 通过 `prctl(PR_SET_TAGGED_ADDR_CTRL, ...)` 设置检测模式
3. 分配 stack history buffer（每线程一个 ring buffer，挂在 TLS 上）

当栈上对象触发错误时，`debuggerd` 将 stack history 写入 tombstone。开发者需要借助 `development/scripts/stack` 脚本和 symbols 文件，从 DWARF 调试信息恢复栈帧局部变量布局，根据 fault 地址和 Tag 值判断是 overflow/underflow 还是 use-after-return。

### Globals Tagging

Android 对 MTE Globals Tagging 的支持发生在 2024 年底，Android 16 才有可用功能。

使用 `-fsanitize=memtag-globals` 编译时，LLD 会在 ELF 的 Dynamic Section 中写入 `DT_AARCH64_MEMTAG_GLOBALS` 和 `DT_AARCH64_MEMTAG_GLOBALSSZ`。汇编指令层面不做插桩——真正的工作由 Dynamic Loader（Android Linker）完成：

1. 为全局变量地址范围开启 `PROT_MTE`（由于内核限制，共享库的 `.data` 段需要先转换为匿名映射并拷贝初始内容）
2. 解析 `DT_AARCH64_MEMTAG_GLOBALS` 指向的 description stream（ULEB128 编码），为每个全局变量打上合适的 Tag
3. 为使用这些全局变量的指针（GOT 表等重定位目标）也打上对应 Tag

### Android 17 bionic ifunc 优化

Android 17 在 arm64 `ifuncs.cpp` 中新增了 `wcslen` 和 `wmemchr` 的 ifunc（Indirect Function）实现。在支持 MTE 的芯片上，这两个宽字符函数会自动选择 MTE 优化版本，在 Tag 检测路径上进行针对性优化。

[已验证: AOSP android-17.0.0_r1, bionic/libc/arch-arm64/ifuncs.cpp]
[来源: 技术文章/Android/Android-17系统层面新特性/09-arm64-MTE-wcslen-wmemchr-ifunc.md]

## Tag 存储的内存开销与 vMTE 展望

MTE 的 Tag 存储采用静态预留方式，物理内存的 1/32（约 3%）被硬性划给 Tag 空间。即使只为小部分内存开启 MTE，剩余 Tag 空间也无法被操作系统复用。

2023-2024 年间，ARM 工程师 Alexandru Elisei 向 Linux 内核提交了三个版本的 dynamic tag storage reuse 补丁集（37 → 27 → 35 个 patch），尝试将闲置 Tag 内存归还给系统。但社区最终未采纳，核心原因如 core-mm maintainer David Hildenbrand 所述：不应为单一架构特性对 core-mm 做过多侵入性修改。

ARM 的长期解决方案是 **vMTE**（Virtual Memory Tagging Extension），将 Tag 存储关系从物理地址映射改为页表映射，实现按需分配。这种从静态预留到动态映射的架构转变，将从根本上消除 MTE 的内存开销。

## MTE 安全攻击面与缓解

随着 MTE 逐渐成为内存安全的标配，它也成为顶级安全研究员的攻击目标。

2024 年，首尔大学和三星的研究人员联合发表了 **TIKTAG** 攻击论文，揭示了通过操纵分支预测（Branch Prediction）和推测执行（Speculative Execution），观察 Cache 状态变化（通过读取时间判断 Cache 命中），可以在不触发 MTE 异常的情况下"偷看"到正确的 Tag 值。这种侧信道攻击打破了 MTE 的 Tag 保密性假设。

FEAT_MTE4（Enhanced MTE）通过 Canonical Check 等特性部分缓解了这类攻击，但推测执行侧信道的封堵仍然是 ongoing 研究课题。苹果在 iPhone 17 的 MIE 方案中据信采用了更激进的微架构级缓解措施。
