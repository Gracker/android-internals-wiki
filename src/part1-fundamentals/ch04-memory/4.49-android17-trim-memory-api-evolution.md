# 4.49 Android 17 trimMemory 回调 API 演进与 ART Heap Trim 链路

## 1. API 34 之后的投递边界

`ComponentCallbacks2.onTrimMemory(int)` 本身仍然存在，也没有被整体废弃。发生变化的是系统常规投递的 level。

Android 17 的 `ComponentCallbacks2.java` 保留七个常量，其中五个带有 `@Deprecated`，注释明确写着应用从 API 34 起不再收到这些级别：

| level | 数值 | Android 17 常规投递 | 处理建议 |
| --- | ---: | --- | --- |
| `TRIM_MEMORY_RUNNING_MODERATE` | 5 | 不再投递 | 只为旧系统或厂商差异保留兼容代码 |
| `TRIM_MEMORY_RUNNING_LOW` | 10 | 不再投递 | 同上 |
| `TRIM_MEMORY_RUNNING_CRITICAL` | 15 | 不再投递 | 同上 |
| `TRIM_MEMORY_UI_HIDDEN` | 20 | 仍会投递 | 释放只服务于可见 UI 的资源 |
| `TRIM_MEMORY_BACKGROUND` | 40 | 仍会投递 | 缩减可快速重建的进程级缓存 |
| `TRIM_MEMORY_MODERATE` | 60 | 不再投递 | 不要依赖它预告进程终止 |
| `TRIM_MEMORY_COMPLETE` | 80 | 不再投递 | 不要依赖它预告进程终止 |

这里有三个容易混淆的点：

1. “不再常规投递”不等于常量从 SDK 中删除。常量继续存在，旧二进制和测试命令仍可引用。
2. `UI_HIDDEN` 描述 UI 可见性变化，不表示系统还剩多少内存。
3. `BACKGROUND` 描述进程已经进入可终止的后台范围，也不承诺进程随后一定被杀。

Android 17 AOSP 中找不到公开的 `onMemoryPressureChanged()`，也没有向普通应用提供 0～100 压力值的 `MemoryPressureMonitor`。`AppProfiler` 内部有一个名为 `MEMORY_PRESSURE_CHANGED` 的 Handler 消息，但它在 `system_server` 内更新内存因子相关状态，不会变成应用回调。

## 2. 两条仍然有效的系统侧发送路径

### 2.1 `TRIM_MEMORY_UI_HIDDEN`

`AppProfiler.updateLowMemStateLSP()` 检查进程状态与 `pendingUiClean`。进程已经进入后台、此前又显示过 UI 时，系统通过 `IApplicationThread.scheduleTrimMemory(20)` 通知目标进程。

源码路径可以概括为：

```text
AppProfiler.updateLowMemStateLSP()
  └─ IApplicationThread.scheduleTrimMemory(TRIM_MEMORY_UI_HIDDEN)
       └─ ActivityThread.ApplicationThread.scheduleTrimMemory()
```

这条链路表达“UI 资源现在可以缩减”。它适合清理全尺寸 Bitmap、只为当前页面服务的预加载对象、不可见动画和播放器画面缓存。音乐播放、下载、定位等仍服务于用户的后台工作不能仅因 UI 隐藏而被停止。

### 2.2 `TRIM_MEMORY_BACKGROUND`

`CachedAppOptimizer.freezeAppAsyncInternalLSP()` 准备冻结 cached 进程时，如果目标进程的 adj 已进入 cached 范围，会先发送 `TRIM_MEMORY_BACKGROUND`，再投递延迟冻结消息：

```text
CachedAppOptimizer.freezeAppAsyncInternalLSP()
  ├─ IApplicationThread.scheduleTrimMemory(TRIM_MEMORY_BACKGROUND)
  └─ mFreezeHandler.sendMessageDelayed(SET_FROZEN_PROCESS_MSG, ...)
```

这是单向 Binder 通知。系统没有等待应用回调完成的确认协议，应用也拿不到“距离冻结还有多少毫秒”的稳定窗口。主线程繁忙、Binder 排队或设备策略变化都可能压缩可执行时间。

LMKD 的 kill 路径更直接：选中牺牲进程后发送终止信号，不保证此前先投递 trim。重要状态应在正常生命周期和业务事务完成时持久化，不能押在 `onTrimMemory()` 上。

## 3. 应用进程如何分发回调

`ActivityThread.ApplicationThread.scheduleTrimMemory()` 收到 Binder 调用后，不会立刻在 Binder 线程执行应用代码。它创建一个 `Runnable`，优先投递到主线程 Choreographer 的 `CALLBACK_COMMIT` 阶段；主线程还没有 Choreographer 时才退回到 `Handler.post()`。

下面摘出调度结构，用于确认线程与执行时机：

```java
public void scheduleTrimMemory(int level) {
    final Runnable r = PooledLambda.obtainRunnable(
            ActivityThread::handleTrimMemory, ActivityThread.this, level)
            .recycleOnUse();
    Choreographer choreographer = Choreographer.getMainThreadInstance();
    if (choreographer != null) {
        choreographer.postCallback(Choreographer.CALLBACK_COMMIT, r, null);
    } else {
        mH.post(r);
    }
}
```

这段调度让清理工作尽量避开当前帧的关键阶段，但回调仍在主线程执行。回调里做大量对象遍历、同步 I/O 或复杂压缩，依然会阻塞后续消息和帧。

`handleTrimMemory()` 的处理顺序如下：

1. 建立 `trimMemory: <level>` trace slice。
2. 当 `skip_bg_mem_trim_on_fg_app` 开启、进程仍属重要前台且 level 至少为 40 时，直接跳过。
3. 收集当前进程中的 `Application`、未结束的 `Activity`、`Service` 和本地 `ContentProvider`。
4. 依次调用每个组件的 `onTrimMemory(level)`。
5. 调用 `WindowManagerGlobal.trimMemory(level)`，让窗口与渲染相关资源处理同一提示。

回调是进程级通知。多进程应用中的主进程、远程 Service 进程和 isolated 进程拥有各自的 `ActivityThread`，一个进程收到 level 20 不会自动转发给其他进程。

## 4. AConfig 在这里控制什么

Android 17 的 `activity_manager.aconfig` 中，与这条应用分发路径直接相关的是固定只读 flag：

```text
skip_bg_mem_trim_on_fg_app
```

它用于阻止前台重要进程处理 level 40 及以上的后台 trim，避免错误状态下清掉前台资源。源码没有为普通应用提供以下能力：

- 配置系统 trim 阈值；
- 为单个应用订阅连续压力值；
- 热更新 ART 回收策略；
- 设置基于模型预测的资源配额。

AConfig 是平台功能开关设施。发现某个内存相关 flag，只能说明对应代码路径受开关控制，不能推导出一套应用可配置的内存管理 API。

## 5. `onTrimMemory()` 与 ART Heap Trim 是两条独立链路

Android 17 源码中，`onTrimMemory()` 不会经 `VMRuntime` 触发 GC 和压缩。

应用回调链的终点是组件回调和 `WindowManagerGlobal.trimMemory()`：

```text
IApplicationThread.scheduleTrimMemory(level)
  → ActivityThread.handleTrimMemory(level)
  → ComponentCallbacks2.onTrimMemory(level)
  → WindowManagerGlobal.trimMemory(level)
```

`handleTrimMemory()` 没有调用 `VMRuntime.requestConcurrentGC()`、`requestHeapTrim()` 或 `trimHeap()`。应用在回调中释放强引用后，对象只是变成可回收；何时 GC 仍由 ART 的分配压力、目标 footprint、进程状态和 collector 策略决定。

ART 的 heap trim 路径从 GC 完成处出发。`Heap::CollectGarbageInternal()` 完成 collector 工作后调用 `RequestTrim()`。该方法会合并重复请求，并以 `kHeapTrimWait`（Android 17 源码为 5 秒）安排 `HeapTrimTask`：

```text
Heap::CollectGarbageInternal()
  → Heap::RequestTrim()
  → HeapTrimTask
  → Heap::Trim()
  → TrimIndirectReferenceTables() / TrimSpaces() / ArenaPool::TrimMaps()
```

`Heap::Trim()` 的重点是把分配器中可归还的页和部分运行时表、arena 占用交还给内核。它不等同于一次“Major GC + compaction”，也没有按年轻代、老年代解析 trim level。

进程前后台变化可以间接影响 ART。`ActivityThread.updateProcessState()` 调用隐藏的 `VMRuntime.updateProcessState()`；ART 在进入不可感知卡顿的后台状态时可请求后台 collector transition 或 full compaction，回到前台时则切回前台策略并调整 heap footprint。这个信号与组件收到的 `onTrimMemory(20/40)` 时间上可能接近，但接口和调度状态各自独立。

另外，`ActivityThread.handleLowMemory()` 是另一条旧的严重低内存路径。它会调用组件的 `onLowMemory()`、释放 SQLite/Canvas 缓存，并通过 `BinderInternal.forceGc("mem")` 请求 GC。不要把这段代码套到 `handleTrimMemory()` 上。

## 6. 应用侧应该怎样实现

下面的示例只做两级、低成本、可重建资源清理。判断顺序从较高 level 开始，可以兼容旧系统或测试注入的更高数值：

```kotlin
override fun onTrimMemory(level: Int) {
    super.onTrimMemory(level)

    when {
        level >= ComponentCallbacks2.TRIM_MEMORY_BACKGROUND -> {
            imageMemoryCache.trimToFraction(0.25f)
            decodedDocumentCache.clear()
        }
        level >= ComponentCallbacks2.TRIM_MEMORY_UI_HIDDEN -> {
            visibleScreenPreloader.cancel()
            fullResolutionPreviewCache.clear()
        }
    }
}
```

这段代码假设缓存具备清晰的所有权，并且释放操作不会做磁盘访问。项目中还应遵守以下边界：

- 回调只清理可重建数据；用户编辑内容、事务状态和任务进度按业务时机持久化。
- 不在回调中主动调用 `System.gc()`。平台文档与 `ComponentCallbacks2` 源码都说明 runtime 会结合进程状态自行安排 GC。
- 不在回调中同步写数据库、压缩大文件或等待锁。
- 缓存必须有常态预算。没有收到回调时，应用的 PSS/RSS 也应受控。
- `UI_HIDDEN` 只清 UI 资源；后台仍在为用户工作的 Service 要保留完成任务所需的最小工作集。

## 7. 验证时看什么

### 7.1 手动注入

Android 17 的 shell 命令仍可向指定进程注入 level：

```bash
adb shell am send-trim-memory com.example.app HIDDEN
adb shell am send-trim-memory com.example.app BACKGROUND
```

`HIDDEN` 映射到 20，`BACKGROUND` 映射到 40。shell 解析器也接受旧 level 和原始整数，所以手工触发 `COMPLETE` 不能证明 Android 17 的正常系统策略仍会发送 80。

### 7.2 Trace 与应用指标

包含 Activity Manager atrace 事件的 Perfetto trace 会显示 `trimMemory: 20` 或 `trimMemory: 40`。这个 slice 只证明调用进入 `ActivityThread.handleTrimMemory()`；若前台过滤 flag 命中，trace 仍可能出现，而组件回调已经被跳过。要确认应用代码执行，应增加轻量业务计数或 trace，并记录释放的缓存条目与字节数。

一次有效测试至少比较：

- 回调前后缓存持有量；
- 回调前后 PSS、RSS 与 Java/native heap；
- 回到前台后的重建耗时和掉帧；
- 多轮前后台切换后的稳定值；
- 被冻结、解冻或杀进程时的数据完整性。

PSS 会受共享页和其他进程影响，单次下降值不能直接归因于某个缓存。固定设备状态、重复多轮并结合堆分类，结论才有可比性。

`dumpsys activity processes` 中的 `trimMemoryLevel` 可辅助查看 `system_server` 记录的最近 level；应用也可以用 `ActivityManager.getMyMemoryState()` 读取 `lastTrimLevel`。它们记录最近状态，不提供连续压力百分比。

## 8. 检查清单

- [ ] 是否只把 level 20 和 40 当作 Android 17 的常规应用回调？
- [ ] 是否避免依赖 `COMPLETE` 作为“即将被杀”通知？
- [ ] 是否区分 UI 隐藏、cached/freeze、LMKD kill 与 ART GC？
- [ ] 是否说明回调在主线程执行，并限制清理成本？
- [ ] 是否把用户数据持久化放在正常业务与生命周期路径？
- [ ] 是否用应用计数、Perfetto 和内存分类共同验证收益？
