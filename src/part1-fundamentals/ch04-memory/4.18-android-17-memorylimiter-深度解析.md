# 4.18 Android 17 MemoryLimiter 深度解析

> **本节定位**：§4.17 从**应用监控影响**视角分析 MemoryLimiter，本节从**系统架构设计**视角进行深度解析。两节互补：§4.17 回答"MemoryLimiter 对我的 APM SDK 有什么影响"，本节回答"MemoryLimiter 为什么这样设计、内部如何运转、与同类机制如何对比"。

## 要点

### 🔹 MemoryLimiter 五大子系统架构

[已验证: AOSP android-17.0.0_r1, MemoryLimiter.java + com_android_server_am_MemoryLimiter.cpp]

MemoryLimiter 不是一个单一的"限制器"，而是由五个松耦合子系统组成的**进程级内存配额管理框架**。从系统设计视角，五子系统的职责划分遵循了"关注点分离"原则：

| 子系统 | 层级 | 职责 | 核心数据结构 |
|--------|------|------|-------------|
| **① ProcState 限制矩阵** | Java | 进程状态 → 配额映射 | `mStateLimit[]` 数组（22 个 case 分支） |
| **② AnonSwapState 状态机** | JNI | 进程内存热度状态判定 | `kCold / kOkay / kHot / kTriggered` 四态枚举 |
| **③ 事件监听回退机制** | JNI | inotify ↔ polling 双模式切换 | `MemWatcher` + 三档轮询周期 |
| **④ memcg 契约管理** | JNI + Kernel | cgroup v2 文件写入/读取 | `CgroupFile` 枚举（5 个文件） |
| **⑤ statsd 事件限流** | Java | 上报频率控制 | 令牌桶（4 token/h，上限 4） |

**五子系统的协作关系（事件生命周期）**：

```
                    ┌─────────────────────────────────────────────┐
                    │           ActivityManagerService             │
                    │  onProcStateUpdated() → 子系统①查表          │
                    └──────────────────────┬──────────────────────┘
                                           │ 新的 memHigh/swapHigh
                                           ▼
                    ┌─────────────────────────────────────────────┐
                    │        子系统④ memcg 契约管理                  │
                    │  writeLimit() → memory.high / swap.high      │
                    │  子系统③ inotify 监听 memory.events           │
                    └──────────────────────┬──────────────────────┘
                                           │ memory.events 触发
                                           ▼
                    ┌─────────────────────────────────────────────┐
                    │        子系统② AnonSwapState 状态机            │
                    │  testAnonSwap() → kCold/kOkay/kHot/kTriggered│
                    │  kHot → 子系统③ 切换 30s 轮询                 │
                    │  kTriggered → 释放限制 + 30s kill 倒计时      │
                    └──────────────────────┬──────────────────────┘
                                           │ onLimitExceeded()
                                           ▼
                    ┌─────────────────────────────────────────────┐
                    │        子系统⑤ statsd 令牌桶限流               │
                    │  shouldLogAtom() → 4 token/h，≤28 events/day │
                    └─────────────────────────────────────────────┘
```

**设计哲学**：

1. **为什么不用单一子系统？** 如果把限制判定、事件监听、cgroup 文件写入全部放在 Java 层，AMS 主线程会因 cgroup 文件 I/O 而阻塞。JNI 层独立处理 cgroup I/O，Java 层只处理策略决策和 kill 调度。这种分层是 Android system_server 中标准的"Java 策略 + Native 执行"模式（参见 Binder、AudioFlinger 等子系统的同类设计）。

2. **为什么有独立的 AnonSwapState？** 如果在每次 cgroup 事件触发时都 kill 进程，系统会被误杀淹没。AnonSwapState 四态机在"触发"与"kill"之间插入了 `kHot` 缓冲态——给内核 reclaim 机制一个机会在 30s 内把进程内存降下来。这与 lmkd 的 PSI 多级压力（some/full）设计异曲同工。

3. **为什么 statsd 限流独立成子系统？** statsd 是系统级共享的上报管道（电池、网络、内存等所有模块都走 statsd），如果不限流，MemoryLimiter 事件可能挤占其他模块的上报配额。令牌桶的设计保证了 MemoryLimiter 每天最多贡献约 24-28 条事件，对 statsd 总吞吐量的影响 < 0.1%。

> 详细的子系统间数据流转和 AMS 挂载点分析，参见 §4.17「MemoryLimiter 对监控体系的定位」。

### 🔹 ProcState → Limits 映射矩阵（22 个 case 分支）

[已验证: AOSP android-17.0.0_r1, MemoryLimiter.java:initializeMemoryLimits()]

> **数量校正**：本节原始大纲写作"23 个 ProcState→Limits 映射矩阵"，经源码核实为 **22 个 switch case 分支**，覆盖 `MIN_PROCESS_STATE`(0) 到 `MAX_PROCESS_STATE`(22) 共 23 个枚举值（含 UNKNOWN 和 NONEXISTENT 两个边界值）。22 个 case 中，UNKNOWN 和 NONEXISTENT 映射到 `ignored`（不写入 cgroup），实际写入 cgroup 限制的是 20 个有效状态。§4.17 已做过同样的校正。

`initializeMemoryLimits()` 的 switch 表达式按进程可见性将 22 个状态分为**四档**：

| 档位 | memHigh 策略 | swapHigh 策略 | 涉及的 ProcState | 设计理由 |
|------|-------------|---------------|-----------------|----------|
| **unlimited** | `LIMIT_IS_DISABLED`(-1) | `LIMIT_IS_DISABLED`(-1) | PERSISTENT, PERSISTENT_UI | 系统服务不可被 throttle，否则 system_server 自身可能卡死 |
| **visible** | `memVisible`(默认 4GB) | `swapVisible`(默认 2GB) | TOP, BOUND_TOP, IMPORTANT_FOREGROUND, **TOP_SLEEPING** | 屏幕关但不影响前台体验的进程给宽松配额 |
| **notVisible** | `memNotVisible`(默认 2GB) | `swapNotVisible`(默认 2GB) | FGS, SERVICE, RECEIVER, BACKUP, BOUND_FGS, IMPORTANT_BG, TRANSIENT_BG, HEAVY_WEIGHT, **HOME**, LAST_ACTIVITY | 运行中但用户不可见的后台进程，是**主要受控群体** |
| **cached** | `LIMIT_IS_IGNORED`(-2) | `LIMIT_IS_DISABLED`(-1) | CACHED_ACTIVITY, CACHED_ACTIVITY_CLIENT, CACHED_RECENT, CACHED_EMPTY | 完全交给 lmkd/CachedAppOptimizer，避免双重管理 |

**映射矩阵中的设计决策分析**：

**决策一：TOP_SLEEPING 归入 visible**

`TOP_SLEEPING` 表示设备息屏但前台进程仍在运行。将它归入 `visible`（4GB 配额）而非 `notVisible`（2GB）的理由：息屏场景下用户可能正在听音乐、导航、下载——这些场景对内存的需求与亮屏时几乎相同。如果降级到 `notVisible`，息屏瞬间的 proc state 降级会触发 cgroup 限制收紧，导致前台 Service 被意外 throttle。

**决策二：HOME 归入 notVisible**

`HOME` 表示 Launcher 进程。虽然 Launcher 始终"可见"（用户随时可能回到桌面），但 Android 的设计判断是 Launcher 退到后台时不需要保持大量 anon 内存——UI 可以重建。这与 iOS 的 SpringBoard 常驻内存策略不同，是 Android 多任务模型的选择。

**决策三：cached 完全豁免**

Cached 进程使用 `LIMIT_IS_IGNORED`（memHigh）和 `LIMIT_IS_DISABLED`（swapHigh）。这是因为 Cached 进程已有两道防线（lmkd 按 oom_score_adj kill + CachedAppOptimizer freeze/compact），再加 MemoryLimiter 会造成三重管理的混乱。MemoryLimiter 的设计边界明确：**只管"运行中但不可见"的进程**。

**动态重计算机制**：

[已验证: AOSP android-17.0.0_r1, ProcessRecord.java:1625]

```
ProcessRecord.setProcState(newState)
    → mLim.onProcStateUpdated(newState)    // MemoryLimiter.java
        → mStateLimit[newState]            // 查表
        → setLimit(pid, uid, limit)        // Handler MESSAGE_CONFIG
            → JNI setLimit_native()
                → writeLimit(memory.high)  // cgroup 文件写入
                → writeLimit(swap.high)    // cgroup 文件写入
```

每次 proc state 变化都会触发一次 cgroup 写入。高频 proc state 变化（如应用在 FGS ↔ Service 之间快速切换）会产生频繁的 cgroup I/O，但 JNI 层的 Handler 队列会合并连续的 setLimit 调用（只执行最后一次）。

> 完整的 ProcState → Limits 配额矩阵表和监控关注点，参见 §4.17「swap 指标在内存限制下的行为变化」。

### 🔹 inotify → polling 回退机制

[已验证: AOSP android-17.0.0_r1, com_android_server_am_MemoryLimiter.cpp:43-52, 506-528]

MemoryLimiter 的事件监听采用**双模式自适应切换**设计，这是 Native 层最精巧的部分。

**模式一：inotify 事件驱动（常态）**

JNI 通过 `inotify_add_watch(memory.events, IN_MODIFY)` 监听 cgroup 的 `memory.events` 文件。当内核 reclaim 或 throttle 发生时，`memory.events` 文件被更新，触发 inotify 事件。优势：零 CPU 开销，事件驱动。

**模式二：polling 定时轮询（red zone）**

当进程内存使用超过 `memory.high` 但未超过 `memory.swap.high`（即 AnonSwapState = kHot），cgroup 事件流停止 fire（内核在 hot 状态下不再写入 `memory.events`）。此时 inotify 失效，必须切换为定时轮询。

**三档轮询周期**：

| 常量 | 值 | 使用场景 | 设计考量 |
|------|-----|---------|---------|
| `PID_POLL_PERIOD_MS` | 5 分钟 | 常态清扫 | 5 分钟足够发现缓慢泄漏，又不会产生过多 cgroup I/O |
| `RED_POLL_PERIOD_MS` | 30 秒 | Red zone 高频监控 | 30 秒在内核 reclaim 的典型时间尺度（秒级）和 kill 窗口（30s）之间取得平衡 |
| `TEST_POLL_PERIOD_MS` | 1 秒 | 测试模式 | 仅供 CTS/VTS 测试用，生产环境不启用 |

**切换条件**（`Process::isRed()`）：

```cpp
bool isRed() const {
    return mMemWatcher.mTriggered && !mAnonSwapTriggered;
}
```

即 `memory.high` 已触发但 `memory.swap.high` 还没触发。一旦 `swap.high` 也触发，`mAnonSwapTriggered = true`，进程离开 red zone 进入 kill 流程。

**恢复条件**：进程的 `(anon + shmem)` 必须下降到 `memHigh - mMemHighHysteresis`（10MB 滞回带）以下，才能从 polling 恢复到 inotify 模式。10MB 滞回带防止在边界值附近频繁切换监听模式。

> inotify/polling 对应用 PSS 监控的影响和补偿方案，参见 §4.17「cgroup memory.high 限制机制与监控边界」。

### 🔹 AnonSwapState 四态机

[已验证: AOSP android-17.0.0_r1, com_android_server_am_MemoryLimiter.cpp:78-83, 103-111, 512-528]

AnonSwapState 是 MemoryLimiter 的核心决策引擎，将进程的内存热度划分为四个精确状态：

```
    ┌─────────┐    (anon+shmem)    ┌─────────┐   超过 anonSwapLimit   ┌─────────┐
    │  kCold  │ ──────────────→   │  kOkay  │ ──────────────────→  │  kHot   │
    │ inotify │    超过阈值         │ polling │                       │ polling │
    └─────────┘                   └─────────┘                       └────┬────┘
        ▲                             ▲                                  │
        │ anon+shmem <                │ anon+shmem 下降到                 │ swap.high 也触发
        │ memHigh - 10MB              │ memHigh - 10MB 以下                │
        │                             └──────────────────────────────────┘
        │                                                                │
        │                                                                ▼
        │                                                        ┌──────────────┐
    ┌───┴───────┐                                                │  kTriggered  │
    │ (正常恢复) │                                                │ 限制释放      │
    └───────────┘                                                │ 30s kill     │
                                                                 └──────────────┘
```

**状态判定函数**（`testAnonSwap()`）：

```cpp
AnonSwapState testAnonSwap() const {
    if (mAnonSwapTriggered) return AnonSwapState::kTriggered;
    int64_t metric = getMetric(MonitoredLimit::kAnonSwap);
    if (mAnonSwapLimit < 0) return AnonSwapState::kOkay;
    else if (metric > mAnonSwapLimit) return AnonSwapState::kHot;
    else if (metric < (mMemoryHighLimit - mMemHighHysteresis)) return AnonSwapState::kCold;
    else return AnonSwapState::kOkay;
}
```

**状态转换的设计要点**：

1. **kCold → kOkay → kHot 是单向递进的**（在内存上升时）。没有"直接从 kCold 跳到 kHot"的快捷路径——必须经过 kOkay 中间态。这确保了状态转换的可观测性和可回溯性。

2. **kTriggered 是终态**。一旦进入 kTriggered，cgroup 限制被立即释放（`LIMIT_IS_DISABLED`），进程在 30 秒内被 kill。没有从 kTriggered 回退的路径——设计上 kTriggered 不可逆。

3. **滞回带（10MB）只在 kOkay ↔ kCold 之间生效**。kOkay → kHot 的转换没有滞回保护——一旦 anon+shmem 超过 anonSwapLimit，立即进入 kHot。这反映了"宁可多轮询也不可漏检超限"的保守策略。

4. **`mAnonSwapLimit < 0` 时返回 kOkay**：如果 OEM 未配置 swap 限制（config 中 swapHigh 为 0 或未设置），进程直接进入 kOkay 永不升级——相当于 swap 限制功能关闭但 memory.high 限制仍然生效。

> AnonSwapState 四态机对应用监控的影响（PSS 抖动模式）和滑动窗口过滤建议，参见 §4.17「PSS 抖动与 30s kill 窗口影响分析」。

### 🔹 内核 memcg v2 memory.high 语义

[已验证: kernel.org Documentation/admin-guide/cgroup-v2.rst]

MemoryLimiter 选择 memcg v2 的 `memory.high` 而非 `memory.max` 作为限制机制，是一个关键的架构决策。

**memory.high vs memory.max**：

| 属性 | memory.high | memory.max |
|------|-------------|------------|
| 超限行为 | throttle + 主动 reclaim | OOM kill |
| 进程影响 | 被减速但存活 | 被杀死 |
| 内核行为 | 分配被阻塞，触发回收 | `oom_kill()` 直接杀进程 |
| 适用场景 | 软限制、性能隔离 | 硬限制、资源保护 |
| MemoryLimiter 使用 | ✅ 主限制 | ❌ 不使用 |

**为什么不用 memory.max？**

使用 `memory.max` 意味着进程超限时内核直接 OOM kill——没有缓冲期、没有 profiling 机会、没有 `onTrimMemory` 回调时间。MemoryLimiter 的设计目标是**"限制而非杀死"**：通过 `memory.high` 的 throttle 语义给进程"自救"的机会（通过 onTrimMemory 回调释放内存），只有当进程在 30 秒内**同时**超过 memory.high 和 swap.high（ANON_SWAP 联合超限）时才 kill。

**100MB margin 的条件性写入**：

[已验证: AOSP android-17.0.0_r1, com_android_server_am_MemoryLimiter.cpp:472-483]

```cpp
case MonitoredLimit::kMemoryHigh:
    mMemoryHighLimit = limit;
    if (mMemWatcher.mTriggered) {
        // Add some margin to memHigh so that the CPU can run
        // and perhaps shed anon memory before hitting the limit.
        limit = incrLimit(limit, mMemWatcher.mMargin);  // +100MB
    }
    writeLimit(cgroupPath(CgroupFile::kMemoryHigh), limit);
```

- **常态**：cgroup 收到原始 `memHigh` 配置值
- **触发后**：cgroup 收到 `memHigh + 100MB`

margin 的用途是给被 throttle 的进程留出 CPU 运行空间——如果 memory.high 设置过紧，进程的 GC 和内存释放代码本身都无法执行（因为分配内存时直接被 throttle）。100MB 余量让进程能完成 anon 回收操作。

**swap.high 的 ZRAM 交互**：

Android 设备的 swap 通常通过 ZRAM（压缩内存）实现。`memory.swap.high` 触发时：
- ZRAM 压缩比已达上限，内核开始限制新的 swap 写入
- 进程被迫保留更多 anon 页在物理内存中
- PSS 可能反而**上升**（原本可以换出到 swap 的页现在必须驻留 anon）

这使得 swap.high 触发后，进程的 memory.high 更容易也被触发——形成"swap 限制连锁触发 memory 限制"的级联效应。

> memory.high 的监控影响（PSS 不含 swap 的盲区、DMA-BUF 不计入 PSS 等），参见 §4.17「Debug.MemoryInfo 指标缺失与补偿方案」。

### 🔹 statsd 令牌桶限流

[已验证: AOSP android-17.0.0_r1, MemoryLimiter.java:onLimitExceeded() + shouldLogAtom()]

MemoryLimiter 向 statsd 上报事件使用令牌桶限流算法。这不是可配置的优化项，而是**硬编码的系统设计约束**。

**令牌桶参数**：

```java
static final int MAX_TOKENS = 4;                                       // 容量上限
static final long TOKEN_PERIOD_MS = Duration.ofHours(1).toMillis();    // 补充周期：1 token / 小时
```

**算法流程**（`shouldLogAtom()`）：

1. 计算距上次更新的小时数 `accumulated = (now - mLastBucketUpdate) / TOKEN_PERIOD_MS`
2. 补充 token：`mAvailableTokens = min(mAvailableTokens + accumulated, MAX_TOKENS)`
3. 如果有 token（`mAvailableTokens > 0`）：消耗 1 个，返回 true（允许上报）
4. 如果无 token：返回 false（丢弃事件）

**稳态行为**：满桶（4 个 token）时，前 4 小时每小时消耗 1 个；之后每小时补充 1 个再消耗 1 个。24 小时内最多 4（初始）+ 20（补充）= 24 条，极端情况下可达 28 条。

**设计理由**：

statsd 是 Android 系统级的遥测管道（参见 §4.15 的 statsd 架构），所有系统模块共享带宽。如果 MemoryLimiter 不限流，一个频繁触发限制的后台 Service 可能每秒产生数十条事件，挤占电池、网络等模块的上报配额。4 token/h 的限流确保 MemoryLimiter 的事件量在 statsd 总流量中占比极低。

> statsd 限流对 APM SDK 的影响和 Java 层反射 hook 方案，参见 §4.17「多层级内存保护策略协同机制」。

## 扩展

### 🔸 限制矩阵配置详解：vendor overlay 机制

[已验证: AOSP android-17.0.0_r1, MemoryLimiter.java:920-986]

MemoryLimiter 的配额不是硬编码的——OEM 通过 `/vendor/etc/memory-limiter-config.xml` 自定义。这是 Android 系统模块的标准 overlay 机制（与 RRO、framework overlay 类似）。

**配置文件格式**：

```xml
<!-- /vendor/etc/memory-limiter-config.xml 示例 -->
<config version="1">
    <limit-set minMemTotal="4096">  <!-- 4GB RAM 设备 -->
        <limits
            memVisible="3072"
            swapVisible="1536"
            memNotVisible="1536"
            swapNotVisible="1536" />
    </limit-set>
    <limit-set minMemTotal="8192">  <!-- 8GB RAM 设备 -->
        <limits
            memVisible="4096"
            swapVisible="2048"
            memNotVisible="2048"
            swapNotVisible="2048" />
    </limit-set>
</config>
```

**"最大匹配"选择算法**：

`initializeMemoryLimits()` 在加载配置时，遍历所有 `<limit-set>`，选择 `minMemTotal <= 实际设备 RAM` 中最大的那一组。例如设备 RAM = 6GB，配置中有 4GB 和 8GB 两组，则选择 4GB 组（因为 6 < 8，不满足 8GB 组的 minMemTotal 要求）。

**配置约束**：

- `version` 必须 == 1（未来版本可能变更格式）
- 至少 1 个 `<limit-set>`（否则抛 `IllegalArgumentException`）
- 解析失败或文件不存在 → MemoryLimiter **静默禁用**，不阻止 system_server 启动
- 默认值 `Configuration(4GB, 2GB, 2GB, 2GB)` 仅用于测试环境

**启用条件（三重门控）**：

```
MemoryLimiter 启用 = Flags.memoryLimiterEnable()  // DeviceConfig flag
                   ∧ /vendor/etc/memory-limiter-config.xml 存在且合法
                   ∧ 设备支持 cgroup v2 memory controller
```

Android 17 GA 设备中，只有 OEM 主动提供配置文件的设备才启用 MemoryLimiter。没有 vendor config 文件的设备上 MemoryLimiter 代码路径完全不执行——不会产生任何 cgroup I/O 或内存开销。

### 🔸 轮询回退优化策略

[已验证: AOSP android-17.0.0_r1, com_android_server_am_MemoryLimiter.cpp]

**潜在优化方向**（分析源码中的设计冗余，非官方推荐）：

1. **自适应轮询周期**：当前 `RED_POLL_PERIOD_MS = 30s` 是固定值。如果进程在 red zone 内内存下降速度快（如 5s 内下降 200MB），理论上可以缩短轮询周期到 10s 以更快检测到退出条件。源码中无此优化——可能是为了保持逻辑简单和可预测性。

2. **批量轮询合并**：当多个进程同时处于 red zone 时，每个进程独立的 30s 定时器会产生 N 个独立的 cgroup I/O 操作。如果按 uid 批量读取 `memory.stat`，可以减少 I/O 次数。源码中每个进程独立轮询，未做批量合并。

3. **梯度轮询**：进入 red zone 的前 10s 使用 5s 高频轮询（捕捉快速恢复），之后降为 30s 常态轮询。这种梯度策略在测试环境（`TEST_POLL_PERIOD_MS = 1s`）和生产环境之间增加了一档中间频率。源码中使用单一 30s 周期。

以上均为源码分析推导，非 Android 官方推荐方向。当前固定 30s 周期的设计在正确性和复杂度之间取得了合理平衡。

### 🔸 与传统 Low Memory Killer 对比

[已验证: AOSP android-17.0.0_r1, 对比 lmkd + MemoryLimiter 源码]

MemoryLimiter 与 lmkd 是**互补而非替代**关系。下表从系统设计维度全面对比：

| 维度 | lmkd (Low Memory Killer Daemon) | MemoryLimiter (Android 16+) |
|------|--------------------------------|----------------------------|
| **触发信号** | PSI memory pressure（system级） | cgroup memory.high/swap.high（进程级） |
| **作用范围** | 全系统所有进程 | 非cached、非persistent进程 |
| **响应动作** | SIGKILL（立即杀死） | throttle → 30s kill（仅ANON_SWAP） |
| **缓冲机制** | PSI some/full 两级（短暂的some可恢复） | kCold→kOkay→kHot→kTriggered 四态机 |
| **配置来源** | `/system/etc/lmkd.conf`（minfree + adj） | `/vendor/etc/memory-limiter-config.xml` |
| **配置粒度** | oom_score_adj 级别（系统级优先级） | ProcState 级别（进程状态级别） |
| **是否区分前后台** | 是（通过 adj score） | 是（通过 ProcState 可见性） |
| **kill 策略** | 按 adj 从高到低批量 kill | 单进程独立 kill（不波及其他进程） |
| **profiling 支持** | 无 | ProfilingServiceHelper（三重门控，默认关闭） |
| **事件上报** | 无 statsd 上报 | statsd 令牌桶限流（4 token/h） |
| **进程自查机会** | 无（SIGKILL 不可拦截） | 有（30s 窗口 + onTrimMemory 回调） |
| **内核依赖** | PSI（memory pressure） | memcg v2（memory.high/swap.high） |
| **Android 版本** | Android 12+（PSI模式），更早有 legacy LMK | Android 16+（内部引入），17 增强 |
| **详见** | §4.4 / §4.15 | 本节 + §4.17 |

**协同工作的关键场景**：

1. **系统内存紧张 + 单进程超限同时发生**：lmkd 按 adj 顺序杀 cached 进程，MemoryLimiter 可能在某个后台 Service 上启动 30s kill 倒计时。如果 lmkd 先杀了该进程，MemoryLimiter 的 `MESSAGE_KILL` 到期时发现进程已不存在（`kill` 返回 `-ESRCH`），无害退出。两者不冲突。

2. **MemoryLimiter kill 的归因问题**：MemoryLimiter kill 进程时使用 `REASON_OTHER`，而非 `REASON_LOW_MEMORY`。APM SDK 的崩溃归因如果只按 `REASON_LOW_MEMORY` 分类，会遗漏 MemoryLimiter kill 的事件。建议同时检查 `ApplicationExitInfo.getDescription()` 是否包含 `"MemoryLimiter:AnonSwap"`。

3. **cached 进程的双重豁免**：cached 进程在 MemoryLimiter 中为 `LIMIT_IS_IGNORED`，完全由 lmkd 管理。这避免了"cached 进程同时被 lmkd 和 MemoryLimiter 管理"的混乱场景。

> §4.4 详细介绍了 lmkd 的 PSI 架构和 oom_score_adj 优先级设计，§4.15 分析了 Android 17 中 PSI/LowMemDetector 的演进。

## 版本差异

| 版本 | MemoryLimiter 状态 | 备注 |
|------|-------------------|------|
| Android 15 (API 35) | **不存在** | `MemoryLimiter.java` 在 android-15.0.0_r1 中不存在 |
| Android 16 (API 36) | **引入** | Copyright 2025，`Flags.memoryLimiterEnable()` 默认关闭 |
| **Android 17 (API 37)** | **架构稳定** | Java 1291 行 + JNI 1276 行，可作为生产参考 |

MemoryLimiter 是 Android 16 引入、Android 17 架构稳定的子系统。任何 Android 15 及以下设备的内存监控兼容性测试结果**不能直接外推到 Android 16/17**。

> **版本边界**：本节所有源码引用均锚定 `android-17.0.0_r1`。Android 18 / API 38 及更高版本不在研究范围内。
