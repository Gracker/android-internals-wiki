# 4.20 Android 17 内存管理政策（Compaction + Freezer）对性能监控的影响

§4.10 讲了 Linux 内核级的 memory compaction 与 direct reclaim，§4.11 讲了 Cached App Freezer 与 GC 的触发边界，§4.14 讲了 ART 堆内 Region 级碎片化与 compaction 策略，§4.18 拆解了 onTrimMemory 全链路，§4.19 解析了 MemoryLimiter 的 cgroup memory.high 机制。这一节聚焦它们交汇处的一个实战问题：**当 Android 17 的 compaction + freezer 政策同时作用时，性能监控数据会出现哪些盲区、失真和调优需求**。

读完这一节，应该能回答四个问题：App 被冻结期间性能指标如何采集才不失真；compaction 发生时 Perfetto trace 中能看到什么、看不到什么；Android 17 新引入的 `use_memcg_for_compaction` 和 `defer_service_restart_when_frozen` 两个 flag 对监控策略有什么影响；以及在做线上性能监控体系时，如何处理 freezer 导致的"数据黑洞"。

## 要点

### 🔹 App 级 Compaction 机制：madvise 驱动的页面驱逐

[已验证: AOSP android-17.0.0_r1, frameworks/base/services/core/jni/com_android_server_am_CachedAppOptimizer.cpp]

Android 的"App 级 compaction"和 §4.10 讲的"Linux kernel compaction"是两件不同的事。kernel compaction 做的是物理页框的外部碎片整理（迁移 migrate type，腾出连续高阶页）；App 级 compaction 做的是**通过 `madvise(2)` 系统调用主动驱逐进程的内存页**，让内核把这些页标记为 cold 或直接回收到 swap。

`CachedAppOptimizer` 定义了三种 compaction 级别：

| Compaction Action | madvise 策略 | 作用对象 | 效果 |
|---|---|---|---|
| `COMPACT_PROCESS_SOME` | `MADV_COLD` | 文件 backed 页面 | 页面移入 inactive LRU，优先被回收 |
| `COMPACT_PROCESS_FULL` | `MADV_PAGEOUT` | 匿名页 + 文件页 | 页面直接换出到 swap/ZRAM，立即释放物理内存 |
| `COMPACT_PROCESS_PERSISTENT` | `MADV_PAGEOUT` + 重试 | 全部非锁定页 | 针对长期 cached 且内存压力高的进程 |

[已验证: AOSP android-17.0.0_r1, frameworks/base/services/core/jni/com_android_server_am_CachedAppOptimizer.cpp — process_madvise syscall 调用]

底层实现使用 `process_madvise(2)` syscall（Linux 5.6+，Android common kernel 从 5.10 开始支持），而不是逐 VMA 调用 `madvise`。这保证了 compaction 可以一次性处理整个进程的地址空间，避免多次 syscall 的开销：

```cpp
// com_android_server_am_CachedAppOptimizer.cpp (简化)
int64_t bytesProcessed = process_madvise(pidfd, batch.vmas, batch.totalVmas, madviseType, 0);
```

`VmaBatchCreator` 把进程的 `/proc/<pid>/maps` 解析成 VMA 批次，每批最多 `UIO_MAXIOV`（1024）个 VMA，避免单次 `process_madvise` 参数溢出。处理完成后，内核根据 madvise hint 回收或降级对应页面。

**与 §4.10 kernel compaction 的区别**：
- Kernel compaction 在**分配高阶页失败时**同步触发，做的是**物理页框搬迁**
- App compaction 在**进程进入 cached 状态后**异步触发，做的是**页面驱逐/降级**
- 两者可以同时发生：App compaction 驱逐页面 → 系统内存压力下降 → kernel compaction 不再被触发

**与 §4.14 ART Region compaction 的区别**：
- ART compaction 做**Java 堆内**存活对象搬迁（Region 间移动）
- App compaction 做**进程地址空间**层面的页面驱逐（不关心 Java/Native 归属）
- ART compaction 在 GC pause 中同步执行；App compaction 在 `CachedAppOptimizer` 线程异步执行

### 🔹 Freezer 对性能监控的核心影响：指标采集的"数据黑洞"

[已验证: AOSP android-17.0.0_r1, frameworks/base/services/core/java/com/android/server/am/CachedAppOptimizer.java]

这是本节要回答的核心实战问题。当一个 cached 进程被 cgroup freezer 冻结后，它对性能监控体系产生五层影响：

**第一层：CPU 采样完全消失。**

进程被冻结后，所有线程进入 `FROZEN` 状态，内核调度器不再给它们分配时间片。在 Perfetto trace 中，目标进程的所有线程轨道在冻结窗口内**完全空白**——没有 Running 切片，没有 sched wakeup 事件，什么都没有。这和进程被 LMK 杀死的表现不同：被杀进程的轨道会直接消失（后续不再有事件），被冻结进程的轨道仍然存在但内容为空白。

| 状态 | 轨道存在 | 轨道内容 | 后续恢复 | ApplicationExitInfo |
|---|---|---|---|---|
| 被 LMK 杀死 | 消失 | N/A | 冷启动重新创建 | `REASON_LOW_MEMORY` |
| 被冻结 | 持续存在 | 空白（无 Running） | 解冻后继续运行 | 无退出记录 |
| 正常运行 | 持续存在 | 有 CPU 切片 | N/A | N/A |

**第二层：FPS/渲染数据断流。**

冻结进程的 Surface 不再收到 Vsync 信号，Choreographer 不再回调，RenderThread 不再执行渲染管线。如果监控 SDK 在进程内部采集 FPS（通过 FrameCallback 或 FrameMetrics），冻结期间会返回 0 FPS 或 NaN，需要特殊处理：

```java
// 性能监控 SDK 需要处理 frozen 状态
@Override
public void onFrameStart(long frameTimeNanos) {
    if (lastFrameTime > 0) {
        long delta = frameTimeNanos - lastFrameTime;
        if (delta > FROZEN_THRESHOLD_NS) {
            // 帧间隔超过阈值（如 1s），标记为 frozen gap
            metricsReporter.reportFrozenGap(delta);
        }
    }
    lastFrameTime = frameTimeNanos;
}
```

[适用版本: Android 14 - Android 17]

**第三层：Binder 调用超时归因错误。**

进程冻结期间，同步 Binder 调用会收到 `DEAD_OBJECT`（如果内核杀死目标进程）或等到解冻后才返回。如果 A 端设了 Binder 超时（如 `ServiceConnection` 的 `getService` 有 ANR 风险），这个超时会错误归因到 B 端的"响应慢"，而实际原因是 B 端被冻结了。

在 Android 16+ 上，`IBinder.addFrozenStateChangeCallback()`（API 36）允许系统服务在远端进程冻结/解冻时收到回调。性能监控 SDK 应该利用这个 API 做正确的 Binder 延迟归因：

```java
// API 36+ 使用 FrozenStateChangeCallback
binder.addFrozenStateChangeCallback(executor, (who, state) -> {
    if (state == FrozenStateChangeCallback.STATE_FROZEN) {
        // 标记后续 Binder 调用可能因 frozen 延迟
        binderLatencyTracker.markRemoteFrozen(who);
    } else {
        binderLatencyTracker.markRemoteUnfrozen(who);
    }
});
```

[已验证: AOSP android-17.0.0_r1, frameworks/base/core/java/android/os/IBinder.java — FrozenStateChangeCallback, API 36+]

**第四层：内存指标在解冻后突变。**

进程冻结期间，`CachedAppOptimizer` 可能同时触发 compaction（`MADV_PAGEOUT`），把进程的匿名页换出到 ZRAM。解冻后，进程访问这些页面会触发 major page fault，内核从 ZRAM 解压页面回填。在内存监控指标上表现为：

- **PSS（Proportional Set Size）**：compaction 后立即下降（页面被驱逐），解冻后逐步回升（按需换入）
- **RSS**：下降更明显，因为不计入共享库的按比例分摊
- **swap/zram-usage**：compaction 后上升（匿名页被压缩到 ZRAM）
- **major fault**：解冻后短期突增（从 ZRAM 换入页面）

如果内存监控 SDK 以固定间隔采样 PSS，冻结期间的采样值会误导排查方向：看起来进程"内存泄漏缓解了"，实际上只是页面被暂时驱逐。

**第五层：ANR 计时偏差。**

Android 14+ 的 `DEFAULT_FREEZER_DEBOUNCE_TIMEOUT` 从 10 分钟降到 10 秒，意味着进程进入 cached 状态后很快就会被冻结。如果 App 的 ANR 计时依赖于 `System.currentTimeMillis()` 或 `SystemClock.elapsedRealtime()`，冻结期间这些时钟仍在走（wall clock 不会停），但 App 的 MessageQueue 被暂停了。解冻后，ANR 监控可能误判一个"正常的解冻恢复时间"为"消息处理超时"。

### 🔹 Compaction 与 GC 的协同时机

[已验证: AOSP android-17.0.0_r1, frameworks/base/services/core/java/com/android/server/am/CachedAppOptimizer.java]

`CachedAppOptimizer` 在冻结流程中会和 GC 做两步协同：

```
1. 冻结前：scheduleGcIfNeeded() → ART 执行一次 GC（清理短生命周期对象）
2. 冻结后：compactProcess() → process_madvise(MADV_PAGEOUT) 驱逐页面
```

先 GC 再 compaction 的设计逻辑：GC 回收 Java 堆中的垃圾对象后，这些对象对应的物理页变成可回收状态。随后 compaction 的 `MADV_PAGEOUT` 才能高效地把这些页换出。如果不先 GC，大量已死但未被回收的对象仍占用物理页，compaction 换出的只是"死数据的尸体"。

**对监控的影响**：

在 Perfetto trace 中，一次完整的 freeze + compact 流程会产生以下事件序列（在 `system_server` 的 `Freezer` track 上）：

```
[GC Request]  →  [Freeze Binder]  →  [Freeze Process]  →  [Compaction SOME/FULL]
```

`system_server` 侧的 `Trace` 方法会在 `TRACE_TAG_ACTIVITY_MANAGER` 下写入：
- `Freeze <processName>:<pid> <reason>` — 冻结事件
- `Unfreeze <processName>:<pid> <reason>` — 解冻事件
- `Reschedule freeze <processName>:<pid> timeout=..., reason=...` — 冻结延后重排
- `Compact <processName>:<pid> <action>` — 压缩事件

[已验证: AOSP android-17.0.0_r1, frameworks/base/services/core/java/com/android/server/am/CachedAppOptimizer.java — traceAppFreeze/traceAppUnfreeze/traceAppCompaction]

同时，EventLog 写入 `AM_FREEZE`（事件码 `30031`）和 `AM_UNFREEZE`（事件码 `30032`），可通过 `adb logcat -b events | grep -E 'am_freeze|am_unfreeze'` 确认。

### 🔹 Perfetto 中的内存事件追踪与 SQL 分析

以下 SQL 从 Perfetto trace 中提取 freezer + compaction 事件，并与目标进程的 CPU 活动、内存变化做时间轴对齐：

```sql
INCLUDE PERFETTO MODULE slices.with_context;

-- 1. 提取 Freeze/Unfreeze/Compact 事件
SELECT
  ts,
  dur,
  process_name,
  track_name,
  name AS event_name
FROM process_slice
WHERE process_name = 'system_server'
  AND track_name = 'Freezer'
ORDER BY ts;

-- 2. 检查冻结后目标进程是否有 CPU 活动（异常信号）
WITH freeze_events AS (
  SELECT ts, dur, SUBSTR(name, INSTR(name, ':') + 2) AS proc_pid
  FROM process_slice
  WHERE process_name = 'system_server'
    AND track_name = 'Freezer'
    AND name LIKE 'Freeze %'
)
SELECT
  f.ts AS freeze_ts,
  f.dur AS freeze_dur,
  COUNT(s.ts) AS sched_slices_during_freeze
FROM freeze_events f
LEFT JOIN sched s
  ON s.ts >= f.ts AND s.ts < f.ts + f.dur
  -- 匹配被冻结进程的 PID
  AND s.utid IN (
    SELECT utid FROM thread
    WHERE upid IN (
      SELECT upid FROM process
      WHERE REPLACE(name, ':', ' ') LIKE '%' || f.proc_pid || '%'
    )
  )
GROUP BY f.ts, f.dur, f.proc_pid
HAVING sched_slices_during_freeze > 0;
-- 如果有结果：说明进程在"冻结"期间仍有 CPU 活动，可能存在反复解冻问题
```

```sql
-- 3. 对齐 compaction 前后的内存 counter 变化
WITH compact_ts AS (
  SELECT ts
  FROM process_slice
  WHERE process_name = 'system_server'
    AND name LIKE 'Compact %'
  ORDER BY ts
  LIMIT 1
)
SELECT
  ts,
  value,
  CASE
    WHEN ts < (SELECT ts FROM compact_ts) THEN 'before_compaction'
    ELSE 'after_compaction'
  END AS phase
FROM counter c
JOIN counter_track t ON c.track_id = t.id
WHERE t.name = 'mem.rss'
  AND ABS(ts - (SELECT ts FROM compact_ts)) < 30 * 1e9  -- ±30s 窗口
ORDER BY ts;
```

[结构参考: Perfetto SQL 标准模块 slices.with_context / counter / sched]

### 🔹 Android 17 新增 Flag 对监控策略的影响

[已验证: AOSP android-17.0.0_r1, frameworks/base/services/core/java/com/android/server/am/flags.aconfig + performance_flags.aconfig]

Android 17 引入了两个与 compaction/freezer 直接相关的 aconfig flag：

**`use_memcg_for_compaction`**（namespace: `system_performance`）：

这个 flag 改变了 compaction 的决策依据。在 Android 16 及之前，compaction 的触发条件主要基于进程的 oom_adj 和全局内存压力（PSI）。开启后，compaction 改用 **memory cgroup（memcg）级别的内存压力**作为决策依据，即只看目标进程自身的 cgroup 内存使用是否达到阈值，而不是全局内存水位。

对监控的影响：
- compaction 可能更频繁地针对**单个高内存进程**触发，而不是等全局内存紧张才批量触发
- 监控时不能只看全局 PSI 指标判断"是否会有 compaction"，还要看进程级 memcg 压力
- 如果线上监控发现某个进程频繁被 compaction，应检查其 memcg `memory.pressure` 和 `memory.events`

**`defer_service_restart_when_frozen`**（namespace: `backstage_power`，bug 478967958）：

这个 flag 是 Android 17 首创。当某个 Service 的所有 binding client 都被冻结时，系统**延迟该 Service 的重启时机**，而不是在 Service crash 后立即重启。

对监控的影响：
- Service 重启延迟不再能简单归因为"系统繁忙"或"AMS 调度慢"
- 监控 SDK 如果依赖 Service 的 `onCreate` 时间戳来判断冷启动，冻结期间的 Service 重启会产出异常大的 `onCreate` latency
- 排查时需要先确认 Service 的 binding client 是否处于 frozen 状态

```bash
# 检查设备是否启用了这些 flag
adb shell device_config get system_performance use_memcg_for_compaction
adb shell device_config get backstage_power defer_service_restart_when_frozen
```

### 🔹 内存压力场景下的 Compaction 节流策略

`CachedAppOptimizer` 内置了一套 compaction 节流机制，防止在内存压力持续时过于频繁地触发 compaction（因为 compaction 本身会消耗 CPU 和 I/O）：

| DeviceConfig 参数 | 默认值 | 含义 |
|---|---|---|
| `compact_throttle_b_fg` | 5 分钟 | 前台进程 compaction 最小间隔 |
| `compact_throttle_b_fg_persistent` | 10 分钟 | 持久化 compaction 最小间隔 |
| `compact_throttle_b_some` | 10 分钟 | SOME 级别 compaction 最小间隔 |
| `compact_throttle_b_full` | 30 分钟 | FULL 级别 compaction 最小间隔 |
| `compact_throttle_h_some` | 20 分钟 | 重度压力下 SOME 最小间隔 |
| `compact_throttle_h_full` | 30 分钟 | 重度压力下 FULL 最小间隔 |

[已验证: AOSP android-17.0.0_r1, frameworks/base/services/core/java/com/android/server/am/CachedAppOptimizer.java — DeviceConfig defaults]

这些 throttle 意味着：**即使内存压力持续，单个进程最快每 5-30 分钟才会被 compaction 一次**。在做线上内存监控时，如果看到某个进程的 PSS 在短时间内反复"下降→回升→下降"，不太可能是 compaction 导致的（throttle 不允许），更可能是 App 自身的内存波动（如页面加载/卸载、Bitmap 分配/回收）。

### 🔹 兼容性与边界问题

**32 位应用的 compaction 限制**：在 16KB page size 设备上，32 位应用的地址空间更紧张（通常 3GB），compaction 换出大量页面后，解冻时的 major page fault 风暴可能导致短期性能急剧下降。这是因为 32 位进程的 TLB 容量更小，大量页面换入更容易触发 TLB miss 风暴。

[待验证: 16KB page + 32-bit process 在 compaction 后的 page fault latency 实测数据]

**厂商定制的内存管理信号**：国内主流 ROM 通常在 AOSP freezer 基础上叠加自研后台管控（如墓碑机制、智能冻结、省电白名单）。这些策略可能：
- 提前冻结（debounce < 10s）
- 叠加额外的 compaction（使用厂商自研的内存压缩策略）
- 对特定白名单应用豁免冻结
- 在 AOSP freezer 之外使用 vendor freezer（走不同 cgroup 层级）

判断设备上实际生效的是 AOSP freezer 还是厂商策略：
```bash
# AOSP freezer 的 cgroup 路径
adb shell cat /sys/fs/cgroup/apps/uid_*/pid_*/cgroup.freeze 2>/dev/null

# 厂商可能的额外 freezer cgroup
adb shell find /sys/fs/cgroup -name "cgroup.freeze" -path "*/vendor/*" 2>/dev/null

# EventLog 是最可靠的 AOSP freezer 信号
adb logcat -b events | grep -E 'am_freeze|am_unfreeze'
```

**不同设备类型的差异**：
- 低 RAM 设备（≤4GB）：compaction 更激进，throttle 更短，可能导致频繁的 page fault 风暴
- 大内存设备（≥8GB）：compaction 频率低，但单次 compaction 处理的页面量大
- 折叠屏/多窗口设备：多窗口场景下进程更难进入 cached 状态（可见性判定更复杂），freezer 触发频率低于普通手机

## 扩展

### 🔸 内存规整的预测性优化

线上性能监控可以引入预测模型来预判 compaction 触发时机。核心思路：

1. 监控进程的 oom_adj 变化（通过 `OnOomAdjustChangeListener` 或轮询 `dumpsys activity processes`）
2. 当 adj 从 FOREGROUND 降到 CACHED 时，启动预测计时器
3. 倒计时 `DEFAULT_FREEZER_DEBOUNCE_TIMEOUT`（10s）后，预判即将 freeze + compact
4. 在 compaction 预测窗口内主动释放可回收内存（如 ImageCache、预加载资源）

这套策略的关键是区分"主动释放"和"被系统 compaction"：主动释放可以按优先级逐步进行，避免一次性 page fault 风暴；被系统 compaction 则是一次性驱逐所有页面。

[待验证: 主动释放 vs 系统强制 compaction 在 PSS 恢复曲线上的差异]

### 🔸 游戏场景的特殊处理

游戏应用的内存特征（大纹理常驻、GPU buffer 频繁分配）使其在 compaction 场景下有特殊表现：

- **纹理资源**：GLES/Vulkan 纹理通常通过 `gralloc` 分配 DMA-BUF，不受 `madvise` 影响。compaction 主要驱逐的是 CPU 侧的匿名页（如 Java 堆、Native 堆），GPU 内存的回收依赖驱动层
- **音频 buffer**：AAudio 的 MMAP buffer 如果被锁定（`mlock`），不受 compaction 影响
- **解冻恢复**：游戏从后台恢复时，CPU 侧页面需要从 ZRAM 换入，但 GPU 纹理如果未被销毁（Surface 未 detach），可以快速恢复渲染

监控游戏应用的 compaction 影响，应额外关注：
- `gfxinfo` 的帧时间在解冻后 1-3 秒内的分布（page fault 期间丢帧）
- `/proc/<pid>/stat` 的 major fault 计数在解冻前后的增量
- Perfetto 中 `mm_page_fault` tracepoint 的密度变化

### 🔸 厂商 freezer 差异的监控适配

面对不同厂商的 freezer 实现差异，线上监控 SDK 应采用多层探测策略：

| 层次 | 探测方法 | 可靠性 | 适用范围 |
|---|---|---|---|
| L1: EventLog | `am_freeze` / `am_unfreeze` | 高（AOSP 保证） | 仅 AOSP freezer |
| L2: cgroup | `cgroup.freeze` 文件读取 | 中（路径依赖设备配置） | AOSP + 部分厂商 |
| L3: 进程状态 | `/proc/<pid>/status` 的 `State` 字段 | 中（frozen 表现为 `D` 状态） | 通用，但无法区分 frozen vs I/O wait |
| L4: 间接信号 | CPU 活动 + Binder 响应延迟 | 低（需要时间窗分析） | 最后手段，适用于所有设备 |

实践中推荐 L1 + L3 组合：EventLog 确认 AOSP 行为，`/proc/<pid>/status` 做通用检测。如果两者信号矛盾（EventLog 没有记录但进程表现为冻结），大概率是厂商 freezer 生效。
