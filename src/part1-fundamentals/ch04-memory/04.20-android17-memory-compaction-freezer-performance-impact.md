# 4.20 Android 17 缓存进程页面回收与冻结对性能监控的影响

AOSP 以 `android-17.0.0_r1` 为锚点，内核以 `android17-6.18-2026-06_r6` 为锚点。§4.10 讨论为高阶页分配进行的物理页迁移，§4.11 讨论 Cached App Freezer 与 GC 边界，§4.14 讨论 ART 堆内对象整理。这里分析 `CachedAppOptimizer` 的进程页面回收、cgroup freezer，以及两者给性能数据带来的偏差。

## 三个名字相近、处理对象不同的机制

| 机制 | 处理对象 | 典型入口 | 目标 |
|---|---|---|---|
| Linux memory compaction | 物理页框 | page allocator / `kcompactd` | 形成连续的高阶空闲页 |
| ART compaction | Java 堆中的存活对象 | ART GC | 减少堆内碎片，移动对象 |
| Cached app compaction | 目标进程的文件页和匿名页 | `CachedAppOptimizer` | 将文件页变冷或主动回收匿名页，降低驻留内存 |

`CachedAppOptimizer` 沿用了 compaction 这个名称，但 JNI 的旧后端执行 `MADV_COLD` / `MADV_PAGEOUT`，Android 17 的新后端写 `memory.reclaim`。两条路径都在回收页面，不会整理物理页框，也不会移动 Java 对象。

## Android 17 的冻结与回收顺序

Android 17 的 OOM 调整器根据进程是否还具有 `CPU_TIME` 能力计算 freeze policy。符合条件后，AMS 进入以下流程：

```text
freeze policy = true
    │
    ├─ [cached adj] scheduleTrimMemory(TRIM_MEMORY_BACKGROUND)
    │
    ├─ 等待 freezer debounce
    │
    ├─ freezeBinder(pid, true, 0)
    │
    ├─ setProcessFrozen(pid, uid, true)
    │      └─ task profile "Frozen" 写 cgroup.freeze = 1
    │
    ├─ 记录 AM_FREEZE / Perfetto freeze instant
    │
    └─ onProcessFrozen()
           └─ cached adj 满足条件时，异步申请 FULL compaction
```

目标进程处于 cached adj 时，冻结前会收到一次 `TRIM_MEMORY_BACKGROUND` 通知；其他可冻结场景没有这项保证。源码没有在这里调用“强制 GC”。应用可能在回调中释放对象，ART 也可能按自己的策略触发 GC，不能把它写成固定的 `GC → freeze → compact` 系统序列。

完整页面回收在进程已经冻结后由 `onProcessFrozen()` 申请。申请还要经过 OOM adj、时间、进程状态、RSS 和 RSS 变化量等节流检查，ART 也可能被降级或取消。

Android 17 的默认手机资源 `config_defaultFreezerDebounceTimeout` 为 10 秒。该值可被资源覆盖，也可由 `activity_manager_native_boot/freeze_debounce_timeout` 调整，因此不能把 10 秒当作所有设备的固定值。

## App compaction 的两个执行后端

### `CompactProfile` 只描述回收范围

`CachedAppOptimizer.CompactProfile` 有四个值：

| Profile | 含义 | 逐 VMA 后端 |
|---|---|---|
| `NONE` | 不执行 | 无 |
| `SOME` | 文件页 | 私有 file-backed VMA 使用 `MADV_COLD` |
| `ANON` | 匿名页 | 可读或可写、非 executable、非 shared VMA 使用 `MADV_PAGEOUT` |
| `FULL` | 文件页和匿名页 | 私有匿名 VMA 使用 `MADV_PAGEOUT`，其余可处理 VMA 使用 `MADV_COLD` |

源码中没有 `COMPACT_PROCESS_PERSISTENT` 这个 profile。persistent 是节流或调用场景中的概念，不能扩写成一种带重试的 madvise 策略。

还有一个容易漏掉的编译期行为：`ENABLE_SHARED_AND_CODE_COMPACT` 在 `android-17.0.0_r1` 为 `false`。`resolveCompactionProfile()` 会将 `FULL` 收窄为 `ANON`，将 `SOME` 变为 `NONE`。当空闲 swap 低于 20% 时，`FULL` 会先降为 `SOME`，随后又可能因文件页 compaction 关闭而变成 `NONE`。

EventLog 和 trace 应记录 resolved profile；只看最初请求的 `FULL` 会高估本次回收范围。

### 旧后端：`process_madvise()`

JNI 先读取 `/proc/<pid>/maps`，按 VMA 类型选择 `MADV_COLD` 或 `MADV_PAGEOUT`。它通过 `pidfd_open()` 获得目标进程 pidfd，再把 VMA 分批传给 `process_madvise()`。单批最多 `UIO_MAXIOV` 个 iovec；一个地址空间通常需要多次 syscall，不能描述成“一次 syscall 处理整个进程”。

两种 advice 的效果也要分开：

- `MADV_COLD` 是降温提示，文件页随后更容易被回收，调用完成不保证 RSS 立即按同等字节数下降；
- `MADV_PAGEOUT` 尝试回收给定页，匿名页通常会进入 swap/ZRAM，但仍受页状态、锁页、共享关系和内核回收结果影响。

### Android 17 后端：memcg `memory.reclaim`

`use_memcg_for_compaction` 的 aconfig 描述是“使用 memcg reclaim 执行 compaction”。开启后，Java 在目标 profile 得到内核支持时调用：

```text
SetProcessProfiles(uid, pid, ["CompactFull" | "CompactAnon" | "CompactFile"])
```

`system/core/libprocessgroup` 的 task profile 再读取目标进程 memcg 的 `memory.current`，把该值写入 `memory.reclaim`：

| task profile | 写入参数 |
|---|---|
| `CompactFull` | 当前 `memory.current` |
| `CompactAnon` | 当前值加 `swappiness=200` |
| `CompactFile` | 当前值加 `swappiness=0` |

内核文档说明，`memory.reclaim` 是主动回收接口，内核可以多回收或少回收；少于请求量时可返回 `EAGAIN`。libprocessgroup 对回收整个 memcg 常见的 `EAGAIN` 做了容忍。

这个 flag 改变的是执行后端，没有把 compaction 触发条件改成“监控进程级 memcg 压力”。OOM adj、冻结完成、节流和 RSS 检查仍在 Java 层。若 memcg profile 不可用，代码会退回逐 VMA 后端。

## Freezer 同时处理 Binder 与 CPU 执行

### 先冻结 Binder

`freezeProcess()` 先调用 `Freezer.freezeBinder(pid, true, 0)`。Binder 文档给出的语义如下：

- 同步事务发往 frozen 远端时返回错误；
- 异步事务可以缓冲，待解冻后投递；
- 冻结时若有未处理事务，操作可能失败，系统会缩短重试间隔；持续制造 Binder 流量还可能使 cached 进程被杀。

所以“同步调用一直等到对端解冻”并非 Android 17 的通用 Binder 语义。监控端应把同步错误、异步积压和进程死亡分开归因。

`IBinder.FrozenStateChangeCallback` 可以监听远端 Binder 所在进程的冻结状态，但它受 feature flag 和驱动能力约束，只对 remote binder 有意义。回调允许合并连续状态变化，不能用于统计精确的冻结次数。它也不是查询本进程全局冻结状态的接口。

### 再写 cgroup freezer

Binder 冻结成功后，`Process.setProcessFrozen()` 应用 `Frozen` task profile。Android 17 `task_profiles.json` 将它映射为：

```text
FreezerState -> cgroup.freeze
Frozen       -> 写 "1"
Unfrozen     -> 写 "0"
```

Linux cgroup v2 文档指出，写 `1` 后冻结可能需要一段时间。所有成员进程都停止运行以后，`cgroup.events` 中的 `frozen` 才变为 1。冻结状态不会把 `/proc/<pid>/status` 的 `State` 可靠地改成某个专用字母，更不能用 `D` 状态代表 freezer；`D` 表示不可中断睡眠，常见于 I/O 等待。

需要判定内核侧状态时，应读取目标 cgroup 的：

```text
cgroup.freeze
cgroup.events        # frozen 0/1
cgroup.stat.local    # frozen_usec，内核 6.18 提供
```

其中 `cgroup.events:frozen=1` 表示冻结已经完成。路径由设备的 cgroup 配置和目标 UID/PID 决定，不要在采集脚本中固定成某个目录模板。

## 性能监控会看到什么

### CPU 与 Perfetto

进程达到内核 frozen 状态后，其线程不会获得 CPU 时间。启用了 `sched_switch` 的 Perfetto trace 在该窗口内不应出现目标线程的 Running slice。进程与线程元数据仍可保留，因此界面上可能还有线程轨道，只是没有运行片段。

Freezer 的 atrace 记录是 instant event：

```text
track: Freezer
name:  Freeze <processName>:<pid> -1
name:  Unfreeze <processName>:<pid> <reason>
```

instant 的 `dur` 不能当作冻结时长。应按同一 PID 配对 Freeze 与下一条 Unfreeze，再结合 `cgroup.events:frozen` 判断内核何时完成冻结。进程在配对窗口内被终止或 trace 截止时，可能没有对应的 Unfreeze。

Android 17 还可在 Perfetto SDK v3 flag 启用时发出结构化 `freeze` / `unfreeze` 事件，携带 UID、PID 和冻结前后持续时间字段。分析脚本应兼容 atrace 与 SDK 两种来源，避免重复计数。

### 帧率与卡顿

被冻结进程没有机会执行 Choreographer、RenderThread 或进程内监控 SDK。后台 cached 进程本来就不应贡献可见帧率，因此冻结区间应从前台 jank 分母中排除。

解冻后的第一次回调会出现很大的 wall-clock 或 elapsed-realtime 间隔。把这段间隔算成一帧会制造“数秒甚至数分钟的超长帧”。监控端可按以下方式处理：

1. 同时记录 Activity/Window 可见性和进程重要性；
2. 发现长采样空洞时，查找系统侧 freeze/unfreeze 证据；
3. 将冻结空洞标为 `not-observable/background-frozen`，不填成 0 FPS；
4. 从解冻后的第一帧重新建立帧间隔基线。

仅靠进程内 SDK 无法在自己冻结期间写日志。需要精确识别冻结区间时，采集器必须位于未被冻结的系统进程、测试进程或离线 trace 分析端。

### Binder 延迟

远端冻结后，同步 Binder 更可能表现为错误，异步 Binder 则可能积压并在解冻后集中处理。两种情况对指标的影响不同：

- 同步错误要与 `DEAD_OBJECT`、服务进程退出和普通业务错误区分；
- 异步积压会让解冻后的工作突增，可能形成 CPU 峰值；
- frozen-state callback 可辅助归因，但事件可能合并，且注册本身也可能因驱动不支持而抛出异常。

对一次 Binder 调用设置“冻结超时”并不能改变驱动语义。应避免向已知 frozen 的远端发送非必要事务，并为必须发送的同步调用保留清晰的错误处理。

### RSS、PSS、swap 与缺页

full/anon compaction 后常见的方向是 anon RSS 下降、RSS swap 上升；file-only 的 `MADV_COLD` 只表示页面更容易被回收，短时间内未必看到明显下降。`AM_COMPACT` 本身会记录 compaction 前 RSS、各分项 delta、耗时、resolved action、oom_adj、proc state 和 ZRAM 变化，优先使用这些系统侧证据。

解冻后访问已换出的匿名页会产生 swap-in 和缺页处理成本。ZRAM 是内存中的压缩块设备，不能仅凭 `/proc/<pid>/stat` 的 `majflt` 增长判断所有 ZRAM 换入；major fault 通常表示需要 I/O。分析恢复成本时可联合观察：

- 解冻后的 CPU 和调度延迟；
- `memory.stat`、`memory.swap.current` 或对应进程 RSS swap；
- ZRAM 读写统计；
- 已在 trace 配置中启用的 page-fault、vmscan 与 block I/O 事件；
- 第一帧、首个 Binder 响应或业务恢复点的耗时。

进程内部的固定周期 PSS 采样在冻结期间同样停止。两次采样之间的下降可能来自 compaction，也可能来自系统或应用的其他回收动作；没有 freeze/compact 时间戳时，不应直接归因。

### 应用自建 watchdog

`elapsedRealtime()` 在进程冻结期间继续前进，MessageQueue 和采样线程没有执行机会。解冻后，自建 watchdog 可能观察到一次很大的调度间隔。

这类间隔是否属于应用卡死，要结合当时是否可见、是否处于 cached 状态以及系统 freezer 事件判断。平台 ANR、应用自建 watchdog 和线上 jank 指标的超时定义不同，不能用一条固定阈值同时解释。

## 页面回收没有“每 5～30 分钟一次”的固定节流

Android 17 默认的四个 APP 来源组合节流值是：

| 上一次 → 本次 | 默认最小间隔 |
|---|---:|
| SOME → SOME | 5 秒 |
| FULL → SOME | 10 秒 |
| SOME → FULL | 500 毫秒 |
| FULL → FULL | 10 秒 |

这些值可由 DeviceConfig 改写。除此之外还有多道检查：

- 进程重新变得 perceptible 时跳过，并可取消正在进行的 compaction；
- 默认只接受 cached adj 范围内的进程；
- `PROCESS_STATE_RECEIVER` 默认在 proc-state throttle 列表中；
- full 请求的 anon RSS 默认低于 12,000 KiB 时跳过；
- 与上次 compaction 后的 file/anon/swap RSS 绝对变化总和不超过 8,000 KiB 时跳过；
- 空闲 swap 低于 20% 时降级 full 请求。

短时间内出现多次 RSS 下降并不能排除 compaction。收到一次 `FULL` 请求也不能证明 Native 已执行 `MADV_PAGEOUT` 或 `memory.reclaim`；应以 resolved profile、`AM_COMPACT` 和 trace 为准。

## `defer_service_restart_when_frozen` 的证据边界

`services/core/java/com/android/server/am/flags.aconfig` 在 Android 17 定义了 `defer_service_restart_when_frozen`，描述为“当 Service 的所有绑定客户端都被冻结时延迟重启”。

在 `android-17.0.0_r1` 的 `services` Java 调用点中，没有该 flag 对应的 `Flags.deferServiceRestartWhenFrozen()` 使用链。仅凭 aconfig 定义，无法证明 release tag 已执行这项策略，也无法推导具体延迟多久。排查某台设备的 Service restart 时，应继续核对该设备分支的 `ActiveServices`、生成 flag 值和厂商补丁。

aconfig 定义说明设计意图，调用点和分支控制才说明运行行为。

## Perfetto 与 EventLog 查询

以下 SQL 找出 system_server 中与冻结和回收相关的 slice，不假设 Freeze instant 自带时长：

```sql
SELECT
  s.ts,
  s.dur,
  t.name AS track_name,
  s.name
FROM slice AS s
JOIN track AS t ON t.id = s.track_id
WHERE t.name IN ('Freezer', 'Compaction')
   OR s.name GLOB 'Freeze *'
   OR s.name GLOB 'Unfreeze *'
   OR s.name GLOB 'Compact *'
   OR s.name = 'compactSystem'
ORDER BY s.ts;
```

结果中的 Freeze/Unfreeze 需要按名称里的 PID 配对；`Compact ...` 的 `dur` 才是 `Trace.traceBegin()` 到 `traceEnd()` 的处理时长。若 trace 开启了结构化 freezer category，还要检查对应的 TrackEvent 表达，避免与 atrace instant 重复。

EventLog tag 在 Android 17 为：

| Tag | ID | 关键字段 |
|---|---:|---|
| `am_compact` | 30063 | PID、进程名、action、前后 RSS delta、耗时、adj、proc state、ZRAM delta |
| `am_freeze` | 30068 | PID、进程名 |
| `am_unfreeze` | 30069 | tag schema 声明 PID、进程名；`reportUnfreeze()` 的写调用还传入第三个 reason |

用于现场观察的命令如下：

```bash
adb logcat -b events -v threadtime \
  | grep -E 'am_(compact|freeze|unfreeze)'
```

EventLog 能确认 framework 已记录动作；若要确认 cgroup 已完成冻结，仍要读取 `cgroup.events:frozen`。

## 监控实现检查清单

- 冻结空洞与“0 FPS”“CPU 使用率为 0”分开编码，避免把缺失数据当有效零值。
- 帧率和 watchdog 在解冻后重置时间基线，不把整个冻结期计入一帧或一次主线程卡顿。
- Binder 指标区分同步错误、异步积压和目标死亡；可用时再用 frozen-state callback 辅助标记。
- 内存分析同时保留 anon RSS、file RSS、RSS swap、ZRAM 变化和 resolved compaction profile。
- Perfetto 中按 PID 配对 Freeze/Unfreeze instant；不要读取 instant 的 `dur` 作为冻结时长。
- 用 `cgroup.events:frozen` 验证内核状态，不以 `/proc/<pid>/status:State=D` 代替。
- 设备侧检查资源 overlay、DeviceConfig、aconfig 与 task profile；AOSP 默认值不能代替厂商配置。

## Android 17 版本边界

平台行为以 `android-17.0.0_r1` 为边界，cgroup v2 语义以内核 `android17-6.18-2026-06_r6` 为边界。冻结防抖、Binder freezer、memcg compaction 与 Perfetto SDK 事件都可能受 release flag、资源 overlay 和设备内核能力影响。

跨版本核对时至少检查：

- `CachedAppOptimizer.resolveCompactionProfile()` 与 `onProcessFrozen()`；
- `Freezer.freezeBinder()` / `Process.setProcessFrozen()`；
- `flags.aconfig` 的定义与 Java 调用点；
- `task_profiles.json` 的 `Frozen`、`Unfrozen`、`Compact*` profile；
- 内核 `cgroup.freeze`、`cgroup.events` 与 `memory.reclaim` 文档。
