# 4.1 Android 17 MemoryLimiter 的 30 秒 Kill 窗口真相与 ProfilingServiceHelper 触发条件

[已验证: AOSP android-17.0.0_r1, frameworks/base/services/core/java/com/android/server/am/MemoryLimiter.java:813-836]
[已验证: AOSP android-17.0.0_r1, frameworks/base/services/core/jni/com_android_server_am_MemoryLimiter.cpp:472-483]
[已验证: AOSP android-17.0.0_r1, frameworks/base/services/core/java/com/android/server/am/MemoryLimiter.java:920-986]

**版本边界**：本节内容基于 Android 17 (API 37) 源码验证，MemoryLimiter 是 Android 16 引入、17 增强的子系统 [已验证: AOSP android-15.0.0_r1 中不存在该文件]

## 要点

### 🔹 锚点 1：MemoryLimiter 机制架构

MemoryLimiter 是 Android 16 引入、17 增强的全新内存管理子系统，其核心架构围绕 cgroup v2 的 `memory.high` 和 `memory.swap.high` 限制展开。[已验证: AOSP android-17.0.0_r1]

#### 关键组件

1. **配置层**：`/vendor/etc/memory-limiter-config.xml` 采用"最大匹配"算法，从多组 LimitSet 中选择最适合当前设备 RAM 的一组（`minimumRequiredMemTotal ≤ memTotal` 中最大者）
   
2. **状态机层**：通过 22 个 ProcessState 完整映射矩阵，为不同进程状态分配不同的内存配额：
   - `TOP/TOP_SLEEPING/IMPORTANT_FOREGROUND`：使用 `memVisible`（可见性配额）
   - `FOREGROUND_SERVICE/SERVICE/BACKUP`：使用 `memNotVisible`（不可见配额）
   - `CACHED_*` 状态完全交给 lmkd 处理，MemoryLimiter 不干预

3. **事件驱动层**：`AnonSwapState` 四态机（`kCold` → `kOkay` → `kHot` → `kTriggered`）监控 anon+swap 组合指标，配合 30s kill 倒计时实现软着陆

#### 常量绑定

Java 端与 Native 端通过 `LINT.IfChange/ThenChange` 严格同步枚举值和特殊哨兵值：
```java
// MemoryLimiter.java
static final int LIMIT_TYPE_UNKNOWN = 0;
static final int LIMIT_TYPE_MEMORY = 1;
static final int LIMIT_TYPE_SWAP = 2;
static final int LIMIT_TYPE_ANON_SWAP = 3;
private static final Long LIMIT_IS_DISABLED = -1L;
private static final Long LIMIT_IS_IGNORED = -2L;
```

### 🔹 锚点 2：30s Kill 作用原理

**核心真相：30秒延迟实为等待 ProfilingServiceHelper 完成 heap dump**

[已验证: AOSP android-17.0.0_r1, MemoryLimiter.java:828-836]

```java
// Request that the target be killed.  The delay allows the profiler, if
// configured to complete.
// TODO: eliminate this when the ProfilingServiceHelper API accepts a "kill when"
// finsished" flag.  // [注释 typo: finsished → finished]
Message msg = mQueue.obtainMessage(MESSAGE_KILL, pid, uid,
        "MemoryLimiter:AnonSwap");
mQueue.sendMessageDelayed(msg, KILL_DELAY_MS);  // KILL_DELAY_MS = 30 * 1000
```

#### 三重作用理解

1. **临时性设计**：源码 TODO 注释明确表示 30s 是等待 ProfilingServiceHelper API 完善的临时方案，未来可能改为"profile 完成即杀"
2. **双重职责**：默认情况下作为软着陆期；若 ProfilingServiceHelper 触发，则承担 heap dump 完成的等待任务
3. **演进方向**：存在明确的 API 演进路径，目标是消除固定延迟

#### PSS 变化阶段

30s kill 窗口期间，进程 PSS 经历两个阶段：

| 阶段 | 时间 | PSS 行为 | 原因 |
|------|------|----------|------|
| **释放阶段** | 0-1s | 解除 cgroup 限制，PSS 可能反弹 | `configureLimit(LIMIT_IS_DISABLED, LIMIT_IS_DISABLED)` 立即生效 |
| **处理阶段** | 1-30s | 若触发 profiling 则 COW 下降；否则业务逻辑驱动 | ProfilingServiceHelper fork 子进程或正常业务执行 |

### 🔹 锚点 3：ProfilingServiceHelper 触发条件

**三重门控缺一不可**（默认情况下全关闭）：

[已验证: AOSP android-17.0.0_r1, MemoryLimiter.java:815-826]

| 条件 | 含义 | 默认状态 | 影响 |
|------|------|----------|------|
| `systemTriggeredProfilingNew()` | SystemTriggeredProfiling 新版 flag | **关闭** | Android 17 默认关闭 |
| `anomalyDetectorCoreC()` | anomalyDetector 模块 core-c 标志 | **关闭** | 依赖编译配置 |
| `pkg != null` | 进程必须能解析 package name | 多数应用满足 | 基础条件 |

```java
if (android.os.profiling.Flags.systemTriggeredProfilingNew()
        && android.os.profiling.anomaly.flags.Flags.anomalyDetectorCoreC()
        && pkg != null) {
    
    ProfilingServiceHelper helper = ProfilingServiceHelper.getInstance();
    helper.onProfilingTriggerOccurred(uid, pkg,
            ProfilingTrigger.TRIGGER_TYPE_ANOMALY);
}
```

#### 默认场景分析

**Android 17 GA 设备上，ProfilingServiceHelper 不会触发**：
- 三个条件中 `systemTriggeredProfilingNew()` 和 `anomalyDetectorCoreC()` 均为关闭
- 30s 窗口纯作为软着陆期，不包含 heap dump 事件
- 与早期内部文档"MemoryLimiter 自带 profiling"描述不符

#### 异常处理机制

```java
try {
    ProfilingServiceHelper.getInstance().onProfilingTriggerOccurred(uid, pkg, 
            ProfilingTrigger.TRIGGER_TYPE_ANOMALY);
} catch (IllegalStateException e) {
    Slog.w(TAG, "Profiling trigger failed", e);  // 失败不影响 kill 流程
}
```

- Profiling 生成失败**不影响 kill 流程**
- 30s 倒计时独立运行，ProfilingServiceHelper 异常时仍正常杀死进程

### 🔹 锚点 4：memcg v2 源码实现

#### 100MB Margin 的条件性激活

[已验证: AOSP android-17.0.0_r1, com_android_server_am_MemoryLimiter.cpp:472-483]

```cpp
void setLimit(MonitoredLimit type, int64_t limit) {
    if (limit <= LIMIT_IS_IGNORED) return;

    switch (type) {
        case MonitoredLimit::kMemoryHigh:
            mMemoryHighLimit = limit;
            if (mMemWatcher.mTriggered) {  // 关键条件：已触发过
                // Add some margin to memHigh so that the CPU can run and perhaps shed anon
                // memory before hitting the limit.
                limit = incrLimit(limit, mMemWatcher.mMargin);  // +100MB
            }
            writeLimit(cgroupPath(CgroupFile::kMemoryHigh), limit);
            break;
    }
}
```

#### Margin 机制详解

- **常态下**：cgroup 文件收到原始 memHigh（无 margin）
- **触发后**（`mMemWatcher.mTriggered = true`）：cgroup 文件收到 memHigh + 100MB
- **用途**：避免被 throttle 的进程没有 CPU 时间回收 anon 内存

#### 配置匹配算法

```java
private static Configuration getConfiguration(List<LimitSet> sets, long memTotal) {
    long minRequiredMem = 0;
    Configuration result = null;
    for (int i = 0; i < sets.size(); i++) {
        LimitSet cfg = sets.get(i);
        long minMemTotal = cfg.getMinimumRequiredMemTotal().longValue() * MB;
        if (minMemTotal > memTotal || minMemTotal < minRequiredMem) {
            continue;
        }
        minRequiredMem = minMemTotal;  // 保留最大满足条件的 minMemTotal
        result = new Configuration(...);
    }
    return result;
}
```

### 🔹 锚点 5：性能影响分析

#### 30s 窗口的 PSS 影响

**ProfilingServiceHelper 触发场景**：
1. fork 子进程读取 heap dump
2. 触发 COW (Copy-On-Write)，原始进程 anon 内存减少
3. PSS 出现异常下降**不应被误读为业务释放**

**ProfilingServiceHelper 未触发场景**：
1. 30s 窗口内进程 PSS 受业务逻辑影响
2. 这段时间实际上是"无限制"窗口
3. APM SDK 需要用 `ApplicationExitInfo.getDescription()` 精确归因

#### 对 APM 监控的建议

1. **归因分析**：使用 `ApplicationExitInfo.getDescription().contains("MemoryLimiter:AnonSwap")` 精确识别 MemoryLimiter 触杀
2. **PSS 变化解读**：30s 内 PSS 变化需考虑是否触发 ProfilingServiceHelper
3. **进程消失标记**：30s 结束后进程死亡，应标记为"突然消失 + 30s 前 ANON_SWAP 告警"

## 扩展

### 🔸 扩展点 1：与其他内存管理机制的协同

MemoryLimiter 在 Android 内存管理体系中处于中间层，与多层机制协同工作：

1. **与 lmkd 的边界**：`CACHED_*` 状态完全交给 lmkd 处理，MemoryLimiter 只干预非缓存状态
2. **与 CachedAppOptimizer 的关系**：CachedAppOptimizer 处理缓存进程，MemoryLimiter 处理活跃进程配额
3. **与 OOM killer 的协作**：MemoryLimiter 是 soft limit，OOM killer 是 hard limit 的最终兜底

### 🔸 扩展点 2：企业级应用场景优化

**内存适配策略**：
1. **配置文件定制**：OEM 可定制 `/vendor/etc/memory-limiter-config.xml` 实现设备差异化配额
2. **进程状态优化**：应用可通过前台服务、绑定服务等机制提升到 `memVisible` 配额
3. **监控降级方案**：APM SDK 需实现 MemoryLimiter 触杀后的数据补全策略

**性能指标调整**：
- 100MB margin 与 10MB hysteresis 的比例关系可能需要根据实际负载调整
- OEM 可考虑动态调整 margin 大小以适应不同内存压力场景

### 🔸 扩展点 3：故障排查与调优方法

**常见问题诊断**：

1. **MemoryLimiter 未生效**：
   - 检查 `/vendor/etc/memory-limiter-config.xml` 是否存在
   - 验证是否有匹配的 LimitSet（`getConfiguration()` 返回非 null）
   - 确认版本号为 1

2. **30s 窗口异常长**：
   - 检查是否意外触发 ProfilingServiceHelper
   - 验证 `systemTriggeredProfilingNew` 和 `anomalyDetectorCoreC` flag 状态
   - 查看 kernel log 是否有异常 fork 行为

3. **PSS 测量异常**：
   - 区分内存释放和 COW 效应
   - 使用 `adb shell dumpsys meminfo` 验证 PSS 数据准确性
   - 监控 `memory.events` 和 `memory.swap.events` 文件变化

**调优建议**：
- 通过 `adb shell cat /sys/fs/cgroup/memory/app/<pid>/memory.high` 实时观察 limit 设置
- 监控 `inotify` 事件与轮询模式的切换
- 使用 `perfetto` 追踪 MemoryLimiter 相关的 kernel 事件
