# 6.18 Linux 6.10 内存碎片整理机制

Linux 6.10 对多尺寸透明大页（multi-size THP，mTHP）的 compaction、swap、NUMA balancing、`MADV_FREE` 和统计接口做了多项补强。Android 17 的内核审阅锚点 `android17-6.18-2026-06_r6` 保留了这些代码，但“代码存在”“GKI 编译启用”“某款设备运行时开启”是三种不同证据。

新闻素材中的“碎片率下降 60%”和“系统崩溃减少 45%”没有可复核的测试环境、指标定义或原始数据，本文不采用这两个数字。Linux 6.10 对 `compaction_capture()` 的提交给出过特定 1 MB mTHP 测试数据，测量对象是 compaction 扫描量与扫描效率，不能改写成 Android 的碎片率或崩溃率。

本文保留 Linux 6.10 作为机制演进节点，当前实现统一核到 `android17-6.18-2026-06_r6`。

## 1. 外部碎片是什么

伙伴分配器按 order 管理物理连续页块。若基础页为 `PAGE_SIZE`，order 为 `n` 的块大小是：

```text
blockSize = PAGE_SIZE × 2^n
```

这条公式说明 order 与字节数必须结合内核基础页大小解读。在 4 KB 内核中，order-2 是 16 KB；在 16 KB 内核中，order-2 是 64 KB。Android 17 支持 16 KB page size，因此不能把固定的 order 表直接套到所有设备。

外部碎片描述“空闲页总量尚可，但缺少满足目标 order 的连续空闲块”。它与以下问题不同：

- 内存不足：可回收与空闲页总量已经不够；
- 内部碎片：分配到的块大于有效数据，占用了未使用空间；
- Java/Kotlin heap 碎片：由 ART 与应用分配器管理；
- 虚拟地址碎片：连续虚拟区间不足，和物理页连续性是不同维度。

Compaction 通过隔离可迁移页、寻找空闲页并迁移内容，尝试在物理页框中聚合高 order 空闲块。迁移会消耗 CPU、内存带宽和锁，也可能引入延迟尖峰。

## 2. Compaction 的三条执行路径

内核会按分配上下文选择不同路径：

| 路径 | 触发者 | 对请求线程的影响 | 常见目标 |
|---|---|---|---|
| direct compaction | 高 order 分配慢路径 | 请求线程同步等待 | 尽快满足当前分配 |
| `kcompactd` | 页分配器或后台策略唤醒 | 工作由每个 NUMA node 的内核线程执行 | 为后续高 order 分配准备空间 |
| proactive compaction | `kcompactd` 按 fragmentation score 判断 | 后台执行，仍会争用 CPU 与带宽 | 把碎片分数维持在阈值区间 |

`android17-6.18-2026-06_r6/mm/compaction.c` 中，`compaction_proactiveness` 默认值为 20，`extfrag_threshold` 默认值为 500。产品可以通过 sysctl 改写它们，内核默认值不能代表量产设备的运行值。

核心流程可以用下面的顺序理解。

```text
高 order 分配未命中
    → 判断 zone watermark 与 fragmentation index
    → 隔离 migrate scanner 找到的可迁移页
    → free scanner 寻找目标空闲页
    → migrate_pages()
    → 伙伴系统合并空闲块
    → 重试目标 order 分配
```

这条流程不会保证成功。被 pin、不可迁移、位于特殊 migratetype 或受 watermark 限制的页，都可能阻止形成目标连续块。

## 3. Linux 6.10 的 `compaction_capture()` 改动

`compaction_capture()` 早于 Linux 6.10 已经存在。它允许正在执行 direct compaction 的任务在页释放并合并到目标 order 时，直接取得该空闲块，省去重新扫描和从 freelist 再分配的步骤。

Linux 6.9 的条件会拒绝所有“小于 pageblock order 且 migratetype 为 `MIGRATE_MOVABLE`”的捕获。Linux 6.10 的提交 [`231f8c7127e3`](https://github.com/torvalds/linux/commit/231f8c7127e3) 收窄了拒绝条件：compaction 自己也在请求 `MIGRATE_MOVABLE` 时，允许这种 lower-order 捕获。mTHP 常请求小于传统 PMD THP 的 order，因此能受益。

Android 17 锚点中的判断仍保留这一结构：

```c
if (order < pageblock_order &&
    migratetype == MIGRATE_MOVABLE &&
    capc->cc->migratetype != MIGRATE_MOVABLE)
    return false;

capc->page = page;
return true;
```

这段代码还受其他条件约束：释放块的 order 必须等于当前 compaction 目标 order，CMA 与 isolate migratetype 不会被捕获，`capture_control` 也只属于当前 direct compaction 上下文。它没有在系统范围内截获任意释放页，也不能据此推断 `kcompactd` 唤醒次数必然下降。

原提交的 1 MB mTHP 工作负载报告了 free scanned 和 migrate scanned 等计数变化。该结果证明这次条件调整可以减少特定测试中的重复扫描，测试没有给出 Android 应用启动、系统崩溃率或长期碎片率结论。

## 4. Linux 6.10 的 mTHP 配套变化

mTHP 的匿名页基础支持在 Linux 6.8 已经出现。Linux 6.10 继续补齐周边路径，相关改动应分开理解。

### 4.1 Swap-out 尽量保留 large folio

6.10 的回收路径可以尝试把 mTHP 作为 large folio 加入 swap cache 并写出，减少预先拆成 order-0 页的工作。连续 swap slot 不可用或其他条件不满足时仍会走 fallback。Android 常用 zram 作为 swap block device；这不等同于默认启用 zswap。

当前锚点在 `mm/vmscan.c` 中继续维护 `swpout` 与 `swpout_fallback` 统计。看到 fallback 不表示数据丢失，它表示该次 large-folio swap-out 没有按目标粒度完成。

### 4.2 NUMA balancing 支持 mTHP

6.10 为 mTHP 增加 NUMA balancing 支持，迁移粒度和失败处理不再只围绕 order-0 与 PMD THP。多数手机是单 NUMA node，这项能力对手机应用的收益不能从服务器或虚拟化测试外推。具体设备要先检查 `/sys/devices/system/node/possible` 和内存拓扑。

### 4.3 `MADV_FREE` 处理 large folio

`madvise(MADV_FREE)` 将匿名页标记为可延迟回收。6.10 改善了 mTHP 范围的处理，减少不必要的逐页操作或拆分。它改变 lazy-free 路径的处理效率，不会主动把离散空闲页整理成连续块。

### 4.4 按尺寸统计

6.10 加入 per-order mTHP allocation 与 swap-out 统计。到 Android 17 锚点时，接口已经扩展为每个支持尺寸目录下的 `stats/`：

```text
/sys/kernel/mm/transparent_hugepage/
  hugepages-<size>kB/
    enabled
    stats/
      anon_fault_alloc
      anon_fault_fallback
      anon_fault_fallback_charge
      nr_anon
      nr_anon_partially_mapped
      swpout
      swpout_fallback
      split
      split_failed
```

这份列表来自当前 `mm/huge_memory.c`，设备只会创建架构支持的 size 目录，配置也可能影响部分文件。旧文所列的 `nr_allocated`、`nr_swpout`、`nr_alloc_failed` 不是当前接口名。

## 5. Android 17 的能力与默认值

[`arch/arm64/configs/gki_defconfig`](https://android.googlesource.com/kernel/common/+/refs/tags/android17-6.18-2026-06_r6/arch/arm64/configs/gki_defconfig) 可以确认：

- `CONFIG_TRANSPARENT_HUGEPAGE=y`；
- `CONFIG_TRANSPARENT_HUGEPAGE_MADVISE=y`；
- `CONFIG_CMA=y`；
- `CONFIG_DAMON=y`；
- `CONFIG_MEM_ALLOC_PROFILING=y`，但没有默认开启 allocation profiling。

GKI 能编译这些机制，不表示各尺寸 mTHP 都处于 `always`。当前 [`mm/huge_memory.c`](https://android.googlesource.com/kernel/common/+/refs/tags/android17-6.18-2026-06_r6/mm/huge_memory.c) 的无启动参数默认策略是：

- PMD-sized THP 的 per-size 策略为 `inherit`；
- 其他匿名 THP size 的策略为 `never`；
- 顶层 THP 策略受 Kconfig、`transparent_hugepage=` 与运行时 sysfs 控制；
- `thp_anon=` 可以按尺寸覆盖启动策略。

所以“Android 17 默认启用 order-0 到 order-4 mTHP”没有源码依据。order-0 是基础页，也不属于 mTHP。量产设备还会叠加 vendor config、bootconfig、kernel command line 和 init 写 sysfs 的动作。

Android 17 具备 4 KB 与 16 KB page-size 产品形态。相同的 `hugepages-64kB` 在两类内核上对应不同 order，分析报告应同时记录 `getconf PAGE_SIZE`、内核 release、THP size 目录和每个 `enabled` 的方括号当前值。

`mseal()`、memory allocation profiling、DAMON、vmalloc 优化属于同一内核版本中的其他内存能力。它们可用于保护或观测，但不应计入 compaction 的碎片改善数字。

## 6. 设备上怎样核对

需要 root 或 userdebug 权限的节点应在报告中标明，不能把权限错误当成内核不支持。

下面这组命令用于记录内核、基础页大小、THP 策略和内存拓扑。

```bash
adb shell uname -a
adb shell getconf PAGE_SIZE
adb shell 'cat /proc/cmdline 2>/dev/null'
adb shell 'cat /sys/kernel/mm/transparent_hugepage/enabled'
adb shell 'cat /sys/kernel/mm/transparent_hugepage/defrag'
adb shell 'for f in /sys/kernel/mm/transparent_hugepage/hugepages-*kB/enabled; do echo \"$f: $(cat \"$f\")\"; done'
adb shell 'cat /sys/devices/system/node/possible'
```

方括号包围的 token 是当前策略。`/proc/cmdline` 可能不展示 bootconfig 的全部来源，产品审计还要检查 `/proc/bootconfig`、init rc 和 vendor 配置。

下面这组命令用于采集 compaction、伙伴系统和 per-size mTHP 计数。

```bash
adb shell 'grep -E \"^(compact|kcompactd|thp_|pgmigrate)\" /proc/vmstat'
adb shell 'cat /proc/buddyinfo'
adb shell 'cat /proc/pagetypeinfo'
adb shell 'for f in /sys/kernel/mm/transparent_hugepage/hugepages-*kB/stats/*; do echo \"$f: $(cat \"$f\")\"; done'
```

`/proc/pagetypeinfo` 和部分 sysfs 文件在 user build 上可能不可读。`/proc/buddyinfo` 展示每个 zone 各 order 的空闲块数量；它是一张瞬时快照，不能单独证明长期碎片趋势。

## 7. 用哪些计数判断 compaction

`/proc/vmstat` 中与当前锚点直接对应的计数包括：

- `compact_stall`：请求线程进入 direct compaction 的次数；
- `compact_success`、`compact_fail`：direct compaction 的结果；
- `compact_migrate_scanned`、`compact_free_scanned`：direct compaction 扫描量；
- `compact_isolated`：隔离页量；
- `kcompactd_wake`；
- `kcompactd_migrate_scanned`、`kcompactd_free_scanned`；
- `pgmigrate_success`、`pgmigrate_fail`；
- `thp_swpout`、`thp_swpout_fallback`。

分析要比较同一工作负载前后的增量。只看累计值会混入开机以来的安装、dexopt、相机、游戏和后台任务。

建议至少同时观察四组信号：

1. 目标 order 的空闲块是否在压力后持续耗尽；
2. `compact_stall` 是否伴随主线程或 Binder 关键线程延迟；
3. 扫描页数增长后，`compact_success` 是否同步增加；
4. mTHP fault allocation、fallback、split 与 swap-out 是否符合产品策略。

内核 tracepoint 位于 [`include/trace/events/compaction.h`](https://android.googlesource.com/kernel/common/+/refs/tags/android17-6.18-2026-06_r6/include/trace/events/compaction.h)，可关注：

- `mm_compaction_begin`、`mm_compaction_end`；
- `mm_compaction_isolate_migratepages`、`mm_compaction_isolate_freepages`；
- `mm_compaction_migratepages`；
- `mm_compaction_wakeup_kcompactd`、`mm_compaction_kcompactd_wake`。

Perfetto 采集时应把这些 ftrace 事件与 `sched_switch`、`sched_wakeup`、应用启动或滚动时间线对齐。这样才能判断 direct compaction 是否落在用户可感知路径，以及后台整理是否和前台线程争用 CPU。

## 8. 调优边界

`compaction_proactiveness` 越高，后台整理触发越积极。它可能改善高 order 空闲块供应，也可能增加页迁移、CPU 和内存带宽占用。内核文档明确提醒高值可能造成延迟尖峰。

调参前应回答：

- 谁在请求高 order 页，申请的 order 和 migratetype 是什么？
- 失败来自低内存，还是外部碎片？
- 产品是否启用了对应 mTHP size？
- 迁移失败是否由 long-term pin、不可移动页或 CMA 边界造成？
- 增加后台整理后，前台延迟和功耗是否恶化？

不要在通用应用代码中写 sysctl 或 THP 全局策略。它们属于系统镜像和内核产品策略，必须在目标 SoC、vendor kernel、内存容量、zram 配置和业务负载上验证。

## 9. 结论

Linux 6.10 在 mTHP 周边补上了一批缺口，其中 `compaction_capture()` 的改动很具体：允许 lower-order movable compaction 直接取得刚形成的 movable 空闲块，从而减少特定场景的重复扫描。它是 compaction 的局部效率改进，不能推导出通用的碎片下降比例。

Android 17 的 `android17-6.18-2026-06_r6` 提供相关代码和 GKI 编译能力。设备是否启用某个 mTHP size、采用哪种 defrag 策略，以及这些策略是否改善应用延迟，都要用该设备的启动配置、sysfs、vmstat、buddyinfo 与 trace 共同确认。
