# 6.18 Linux 6.10 内存碎片整理机制

> **版本边界**：Linux 6.10 于 2024-07-14 发布 [已验证: kernelnewbies.org]。Android 17 使用 GKI 内核 `android17-6.18`（基于 Linux 6.18 LTS），因此 Linux 6.10 引入的所有内存管理改进均已包含在 Android 17 内核中 [已验证: AOSP kernel/common android17-6.18]。本节描述的机制在 Android 15 (kernel 6.6 部分回移) 到 Android 17 (kernel 6.18 完整包含) 中均可观察到。

---

## 要点

### 🔹 锚点 1：分层内存管理策略架构

Linux 6.10 在内存管理上引入了**分层策略**，核心思想是将传统的"单一页面尺寸"管理演化为多粒度协同的 folio 体系：

| 层级 | 粒度 | 对应内核对象 | 适用场景 |
|------|------|-------------|---------|
| order-0 | 4 KB | `page` / order-0 folio | 小对象、元数据 |
| mTHP (小) | 16 KB - 64 KB (order 2-4) | mTHP folio | 常规应用匿名页 |
| mTHP (大) | 128 KB - 1 MB (order 5-8) | mTHP folio | 数据库、大缓冲区 |
| 传统 THP | 2 MB (order 9) | huge folio | 大型应用、虚拟化 |

在 Linux 6.10 之前，匿名页分配已支持 mTHP（multi-size Transparent Huge Pages），但 NUMA balancing 和 compaction 仍禁止 mTHP 迁移。6.10 的关键改进是**打通了 mTHP 与 compaction/swap/NUMA balancing 的全链路**：

- `page_alloc: allowing mTHP compaction to capture the freed page directly`：当页面被释放时，compaction 可以直接将其捕获为 mTHP 分配，而非仅 order-0 [已验证: kernelnewbies.org, Linux 6.10 Memory management section]
- `Multi-size THP numa balancing`：NUMA 平衡算法对 mTHP 采用与 THP 相同的基础策略 [已验证: kernelnewbies.org, Prominent features #5]
- `Swap-out mTHP without splitting`：mTHP 可以作为整体 swap-out，无需先拆分为 order-0 [已验证: kernelnewbies.org, Linux 6.10 Memory management section]

这套分层策略构成了 RSS 报道中提到的"分层内存管理"架构基础 [来源: intake/daily-info/2026-06-29.md]。

### 🔹 锚点 2：内存碎片率 60% 下降机制

> ⚠️ "碎片率下降 60%" 数据来源于 Phoronix 报道 [来源: phoronix.com/news/Linux-6.10-Memory-Fragmentation]，原始文章无法访问验证。以下分析基于 Linux 6.10 实际合入的 commit，描述碎片减少的技术机制。

Linux 6.10 中减少内存碎片的核心机制包括：

**（1）mTHP compaction 直接捕获释放页面**

在 6.10 之前，当高阶页面（mTHP）需要分配时，compaction 必须从已释放的 order-0 页面重新组装。6.10 的改进允许 compaction 在页面释放路径中**直接捕获**该页面用于满足 mTHP 分配请求，减少了 compaction 的扫描开销和中间状态的碎片化。

```
// Linux 6.10 page_alloc.c 关键改动概念
// compaction readiness check 在 free 路径直接完成
// 而非依赖后续的独立 compaction pass
```

[已验证: kernelnewbies.org, "page_alloc: allowing mTHP compaction to capture the freed page directly"]

**（2）filemap folio 优化**

`filemap: optimize folio adding and splitting` 系列改进优化了文件映射页面的 folio 添加和拆分逻辑，减少了 pagecache 操作引入的碎片 [已验证: kernelnewbies.org]。

**（3）madvise 增强释放**

`madvise: enhance lazyfreeing with mTHP in madvise_free`：应用调用 `madvise(MADV_FREE)` 时，mTHP 页面可以被整体标记为 lazyfree，而非逐页处理。这意味着应用释放大块内存时，内核可以更高效地回收连续物理页面 [已验证: kernelnewbies.org]。

**（4）对 Android 的实际意义**

Android 应用的内存特征（大量匿名页映射、频繁的 Activity 切换导致内存分配/释放）正是 mTHP compaction 的理想场景。在 Android 17 的 `android17-6.18` GKI 内核中，mTHP 默认启用 order-0 到 order-4（4KB-64KB），compaction 的效率直接影响应用启动和切换的延迟 [待验证: 需在 Android 17 设备上实测 /sys/kernel/mm/transparent_hugepage/ 确认默认配置]。

### 🔹 锚点 3：系统崩溃 45% 减少效果验证

> ⚠️ "系统崩溃减少 45%" 数据来源于 Phoronix 报道 [来源: phoronix.com/news/Linux-6.10-Memory-Fragmentation]，原始文章无法访问验证。以下分析可能相关的稳定性增强机制。

Linux 6.10 中与内存稳定性相关的改进：

**（1）mseal(2) 系统调用**

mseal(2) 是 Linux 6.10 的旗舰特性之一，用于保护虚拟内存区域免受意外修改：
- 防止攻击者修改内存权限（如将只读页改为可写）
- 阻止 `mmap`/`mprotect`/`mremap` 对已密封区域的修改
- 对 Android 系统服务（如 system_server 的关键数据结构）提供额外保护层

[已验证: kernelnewbies.org, Prominent features #1, "mseal(2) to protect memory from unwanted modifications"]

**（2）内存分配分析（memprofiling）**

新增的低开销内核内存分配分析器，可用于：
- 检测内存泄漏（Android 系统服务长时间运行时的慢速泄漏）
- 识别内存回归（OTA 后的内存消耗变化）
- 非仅限 debug 内核，开销足够低可用于生产环境

[已验证: kernelnewbies.org, Prominent features #2, "Memory allocation profiling"]

> 注意：mseal 和 memprofiling 是稳定性增强工具，但"45% 崩溃减少"这一具体数据 `[待验证: 原始 Phoronix 文章无法访问]`。该数据可能来自特定工作负载的基准测试，不代表 Android 设备的实际改善。

### 🔹 锚点 4：高负载场景下的性能表现

Linux 6.10 中针对高负载场景的关键优化：

**（1）vmalloc 锁竞争减半**

`vmalloc: eliminated the lock contention from twice to once`：vmalloc 区域的页表映射操作从需要两次锁竞争减少为一次。这对高负载场景（大量并发 `vmalloc` 调用）有显著意义：
- Android 的 GPU 驱动（如 Mali/Adreno）大量使用 vmalloc 分配 GPU 命令缓冲区
- 内核模块加载/卸载时的 vmalloc 密集调用
- ftrace/perf 等追踪工具的 ring buffer 分配

[已验证: kernelnewbies.org, Linux 6.10 Memory management section]

**（2）anon_vma 可扩展性改进**

`Improve anon_vma scalability for anon VMAs`：匿名 VMA 的反向映射（reverse mapping）数据结构可扩展性提升。在进程拥有大量 VMA（Android 应用进程典型有数百个 VMA）时，`rmap` 遍历性能显著改善 [已验证: kernelnewbies.org]。

**（3）SLUB 极端场景内存优化**

`slub: Reduce memory consumption in extreme scenarios`：SLUB 分配器在内存压力极端场景下的元数据开销减少。Android 设备在 low-memory 状态下（lmkd 触发前后）的 slab 占用更稳定 [已验证: kernelnewbies.org]。

**（4）DAMON 页面粒度访问检查**

`damon: add a DAMOS filter type for page granularity access recheck`：DAMON（Data Access MONitor）新增页面粒度的访问模式检查过滤器，使得内存回收策略可以更精确地识别冷热页面 [已验证: kernelnewbies.org]。

### 🔹 锚点 5：数据库/虚拟化应用场景优化

Linux 6.10 的内存改进对以下工作负载特别有益：

**数据库（如 Android 的 SQLite/WAL 场景）**

- mTHP 整体 swap-out：数据库的大缓冲区在内存压力下可以高效 swap-out，无需拆分
- `filemap: optimize folio adding and splitting`：文件映射页面的 folio 管理更高效，直接受益于 SQLite 的 page cache 操作
- mTHP compaction 捕获：数据库频繁的分配/释放后，物理内存连续性更好

**虚拟化（Android Virtualization Framework）**

- `Multi-size THP numa balancing`：虚拟机的内存可以在 NUMA 节点间以 mTHP 粒度迁移，减少迁移开销
- 传统 THP（2MB）仍然为虚拟机的 EPT/NPT 页表提供最优粒度
- `page_table_check: support userfault wr-protect entries`：支持 userfault 的写保护，为虚拟化框架的 Live Migration 提供基础 [已验证: kernelnewbies.org]

**Android 特有场景**

- ZRAM recompression 改进：`zram: add max_pages param to recompression`，允许对 ZRAM 中的大压缩流进行更细粒度的管理 [已验证: kernelnewbies.org]
- `Reduce memory consumption by memcg stats`：cgroup 内存统计的开销减少，对 Android 的 `memcg` 隔离（每个应用进程一个 cgroup）直接受益

### 🔹 锚点 6：内存碎片整理与并发安全

**（1）vmalloc 锁优化**

Linux 6.10 将 vmalloc 的页表建立过程中的锁竞争从两次减少到一次。具体路径：

```
// 简化的 vmalloc 路径
vmalloc(size)
  → __vmalloc_node_range()
    → vmap_pages_range()        // 建立页表映射
      → vmap_pages_range_noflush()
        // 6.10 之前: 需要在 pgd/p4d/pud/pmd 各级都获取锁
        // 6.10 之后: 优化为单次锁覆盖更大范围
```

[已验证: kernelnewbies.org, "vmalloc: eliminated the lock contention from twice to once"]

**（2）batch mm counter 更新**

`batch mm counter updating in filemap_map_pages()`：文件映射页面的 mm counter（如 `_file_rss`）更新改为批量模式，减少了 per-page 的原子操作开销 [已验证: kernelnewbies.org]。

**（3）large folio mapcount 清理**

`mapcount for large folios + page_mapcount() cleanups`：大 folio 的引用计数管理从 per-page 演进为 per-folio，简化了并发逻辑。这减少了 THP/mTHP 在 fork() 后 COW（Copy-on-Write）场景的锁竞争 [已验证: kernelnewbies.org]。

**（4）page_table_check 增强**

`page_table_check: support userfault wr-protect entries`：page table check 机制扩展支持 userfault 的写保护条目，增强了内存保护的并发安全性 [已验证: kernelnewbies.org]。

### 🔹 锚点 7：碎片检测算法与阈值策略

**（1）mTHP compaction 的触发逻辑**

Linux 6.10 中 mTHP 的 compaction 触发遵循已有的 watermark + compact_priority 机制，但新增了**直接捕获释放页面**的能力：

- 当 alloc 页面释放时，内核检查该释放是否可以满足待处理的 mTHP compaction 请求
- 如果可以，直接将释放的页面交给 compaction，跳过独立的 compaction pass
- 这减少了 `kcompactd` 的唤醒频率和扫描成本

[已验证: kernelnewbies.org, "page_alloc: allowing mTHP compaction to capture the freed page directly"]

**（2）per-order mTHP 统计**

`Add per-order mTHP alloc and swpout counters`：为每个 order 的 mTHP 添加独立的分配和 swap-out 计数器。在 Android 17 上可通过以下节点观察：

```
/sys/kernel/mm/transparent_hugepage/hugepages-<size>kB/
  ├── nr_allocated      # 当前分配的 mTHP 数量
  ├── nr_swpout         # swap-out 的 mTHP 数量
  └── nr_alloc_failed   # 分配失败的 mTHP 数量
```

[已验证: kernelnewbies.org, "Add per-order mTHP alloc and swpout counters"]  
[待验证: 具体节点路径需在 Android 17 设备上确认]

**（3）DAMON 访问模式检测**

DAMON 在 6.10 中新增了 DAMOS filter type for page granularity access recheck，允许在 DAMON 的访问模式采样后，对候选区域进行页面粒度的二次检查。这提高了内存回收决策的精确度，减少了错误回收热页的概率 [已验证: kernelnewbies.org]。

**（4）zswap 改进**

`zswap: replace RB tree with xarray`：zswap 的存储结构从红黑树替换为 xarray，查找/插入/删除操作从 O(log n) 改善为 O(1)。对 Android 的 ZRAM + zswap 链路（如果启用）有延迟改善 [已验证: kernelnewbies.org]。

## 扩展

### 🔸 扩展点 1：vmalloc/ioremap/vmap 基建提速（Linux 7.3+）

小米 Wen Jiang 等开发者在 mm-new 分支推进了一个 6-patch 系列，对 vmalloc/ioremap/vmap 进行基建提速：

**核心创新 1：避免页表反复 rewalk**

页表映射需要遍历 pgd → p4d → pud → pmd → pte 层级。如果多个页面落在同一 pmd 范围内，可以直接在 pmd 级别批量映射，跳过 pgd/p4d/pud 的遍历。核心改动在于支持 order-0 以外 `page_shift` 的内存映射免 rewalk。

**核心创新 2：batch mapping 扩展**

vmap 原先不支持大块映射，此 patchset 扩展了 vmap 的 batch 能力。在 ARM64 上，不再限于 order-4（CONT-PTE），order-5/order-6 及以上也可以直接映射为 CONT-PTE。

**收益**

- 映射操作本身的加速（减少页表遍历）
- 映射后内存访问加速（TLB refill 开销大幅减少，ARM Leo Yan 验证）

> ⚠️ 此 patchset 最早预期在 Linux 7.3 中面世，**不属于 Linux 6.10**。Android 17 (kernel 6.18) 不包含此改进 [来源: Cubox/一次vmalloc, ioremap, vmap的基建提速-2026-06-28.md]  
> [待验证: patchset 实际合入版本和 Android ACK 是否回移]

### 🔸 扩展点 2：碎片整理的性能开销分析

Linux 6.10 的 mTHP compaction 改进通过**直接捕获释放页面**减少了独立 compaction pass 的需求，但 compaction 本身的开销并未消除：

- **直接 compaction**：在页面分配失败时同步触发，延迟可能达到毫秒级
- **后台 compaction**（kcompactd）：异步执行，对前台影响小但可能无法及时满足分配请求
- **6.10 改进**：释放路径的直接捕获机制减少了对两者的依赖，是介于"零开销"和"完整 compaction"之间的折中

Android 设备上的典型表现：
- 应用启动时的大块匿名页分配 → mTHP compaction 命中率提升
- Activity 切换时的内存抖动 → kcompactd 唤醒频率降低
- `[待验证: 需在 Android 17 设备上用 Perfetto trace 验证 compaction 延迟]`

### 🔸 扩展点 3：不同工作负载的碎片整理策略

不同 Android 工作负载对内存碎片整理的需求不同：

| 工作负载 | mTHP 需求 | compaction 敏感度 | 推荐策略 |
|---------|----------|------------------|---------|
| 应用启动 | order-2/3 (16-32KB) | 高（影响冷启动延迟） | 启用 direct compaction |
| UI 渲染 | order-0/2 | 中（buffer 分配） | 后台 compaction 即可 |
| 数据库 I/O | order-4+ (64KB+) | 高（page cache） | 启用 mTHP + khugepaged |
| 后台任务 | order-0 | 低（不敏感） | 禁用 mTHP 以节省内存 |
| ZRAM 压缩 | order-0 | 低（流式压缩） | 依赖 swap-out mTHP |

> `[待验证: 上述策略建议基于 Linux 内核机制推导，未在 Android 17 设备上实测验证]`

## 与 Android 17 的版本映射

| Linux 版本 | Android GKI 分支 | 状态 |
|-----------|-----------------|------|
| Linux 6.10 | (上游 mainline) | 原始引入版本 |
| Linux 6.12 | android16-6.12 | Android 16 GKI 基线 |
| Linux 6.18 | android17-6.18 | Android 17 GKI 基线 ✅ |
