## 校核结论

“应用启动调度”不是 Android 源码中的单一模块名。一次冷启动横跨 Activity 启动、进程创建、包与组件解析、ART 代码加载、文件 I/O、CPU 选核、线程调度、调频以及厂商性能策略。把这些路径合称为“Android 17 机器学习调度器”，会让排查对象和测量口径同时失真。

Android 17 的[功能与 API 列表](https://developer.android.com/about/versions/17/features)记录了 JobScheduler 调试 API、ProfilingManager 触发器等变化，没有声明大纲所述的启动预测组件。源码校核也没有得到以下公开契约：

- 按用户行为预测下一次启动应用的 framework API；
- 由 AOSP 统一训练、部署和更新的启动预测模型；
- 把预测结果直接写入 EEVDF 虚拟 deadline 的接口；
- 面向所有 Android 17 设备的预加载命中率、启动提速或内存降幅承诺。

因此，旧稿中的“全新的任务调度器”“内核级机器学习实现”“应用依赖关系智能解析”以及三组百分比均撤销。设备厂商可以在 AOSP 之外加入应用预热、I/O 预取、CPU boost 或行为预测策略，这类能力需要按具体设备和 vendor 实现验证。

## 一次应用启动经过哪些调度层

下表把容易混淆的职责拆开。各层可能交换状态或提示，但没有一个公共 AOSP 类包办整条路径。

| 层次 | Android 17 中可验证的职责 | 不应从中推导的结论 |
|---|---|---|
| ATMS / WMS | `ActivityStarter` 解析启动请求、选择任务与 Activity，并推进启动事务 | 它不负责 Linux 线程选人，也不包含通用用户行为模型 |
| AMS 进程管理 | `ProcessList` 参与应用进程创建；进程状态和 OOM adj 影响回收优先级 | OOM adj 不是 CPU 调度优先级，也不等同于启动预测分数 |
| Zygote / ART | fork 应用进程、装载运行时；profile、dexopt 与 app image 影响代码加载成本 | profile-guided compilation 不会预测用户下一次点击哪个应用 |
| Linux 公平调度 | EEVDF 在单个 CPU 的公平调度实体中按 eligibility 和虚拟 deadline 选人 | EEVDF 不识别应用包名、Activity 或“高频应用” |
| EAS | 在满足启用条件时，根据容量与 Energy Model 评估唤醒任务放到哪个 CPU | EAS 处理 CPU placement，不解析应用依赖 |
| schedutil / cpufreq | 根据调度器利用率等信号提出频率请求，驱动和固件决定可用频点 | 频率请求不承诺某次启动的完成时间 |
| Power HAL / ADPF | 接收平台 power hint 或应用 Hint Session 的工作时长反馈 | 公共 AIDL 没有规定厂商必须使用机器学习 |
| JobScheduler / WorkManager | 安排可延期、受约束的后台工作 | 它们不调度用户点击后的交互式 Activity 冷启动 |

### Framework：启动请求与进程创建

Android 17 的 [`ActivityStarter`](https://android.googlesource.com/platform/frameworks/base/+/refs/tags/android-17.0.0_r1/services/core/java/com/android/server/wm/ActivityStarter.java) 位于 WindowManager/ActivityTaskManager 服务侧。它负责检查调用方、解析 Intent 与 ActivityInfo、选择或创建 task，并把启动推进到后续生命周期路径。

目标应用没有存活进程时，系统还要经过 AMS 的进程启动路径。Android 17 标签中的 [`ProcessList`](https://android.googlesource.com/platform/frameworks/base/+/refs/tags/android-17.0.0_r1/services/core/java/com/android/server/am/ProcessList.java) 包含向 Zygote 发起进程创建等逻辑。冷启动由此增加 fork、绑定应用、类加载和首帧构建等成本；热启动可能复用进程与已有运行时状态。

进程状态与 OOM adj 服务于内存回收排序。前台进程通常更难被杀，但不能据此断言它的每个线程都具有更高的 Linux 调度优先级。Android 17 标签提供的 [`OomAdjuster.md`](https://android.googlesource.com/platform/frameworks/base/+/refs/tags/android-17.0.0_r1/services/core/java/com/android/server/am/OomAdjuster.md) 还说明了新旧 OOM adjuster 的组织方式；分析该版本时应沿文档与当前文件布局查找，不能套用旧标签的类路径。

### ART：已经发生过的执行行为

ART profile 记录已观测到的方法和类使用情况，dexopt 可据此选择编译策略。应用 image、共享运行时页、类预加载与编译产物都会影响启动阶段的缺页、解释执行和 JIT 压力。这类优化依据历史执行数据改善代码装载与执行成本，但“使用 profile”不足以证明系统存在跨应用的用户行为预测模型。

评估 ART 对启动的影响时，应区分：

- 首次安装或更新后的启动；
- dexopt 完成前后的启动；
- 冷文件缓存、暖文件缓存与进程仍存活的启动；
- baseline profile 是否随 APK 提供，设备侧 profile 是否已合并；
- 受测构建是否相同，应用数据与账号状态是否一致。

只写“冷启动下降 30%”会丢失这些条件，其他设备无法复现实验。

### Kernel：选核、选人和调频是三项决策

`android17-6.18-2026-06_r6` 的 [`fair.c`](https://android.googlesource.com/kernel/common/+/refs/tags/android17-6.18-2026-06_r6/kernel/sched/fair.c) 实现公平调度类。EEVDF 使用 lag 判断调度实体是否 eligible，再在候选中比较虚拟 deadline。它从 Linux 6.6 起进入上游调度器演进，不是 Android 17 单独引入的应用启动功能。算法细节见同一标签的 [`sched-eevdf.rst`](https://android.googlesource.com/kernel/common/+/refs/tags/android17-6.18-2026-06_r6/Documentation/scheduler/sched-eevdf.rst)。

任务唤醒时，EAS 在可用条件满足后评估 CPU placement。它使用调度器利用率、CPU capacity 与 Energy Model 估算候选放置方案，边界见 [`sched-energy.rst`](https://android.googlesource.com/kernel/common/+/refs/tags/android17-6.18-2026-06_r6/Documentation/scheduler/sched-energy.rst)。当 root domain 被标记为 overutilized 等条件出现时，公平调度代码不会沿 EAS 能耗比较路径选核。

任务进入目标 CPU 的运行队列后，EEVDF 决定公平调度实体的运行顺序。随后，[`cpufreq_schedutil.c`](https://android.googlesource.com/kernel/common/+/refs/tags/android17-6.18-2026-06_r6/kernel/sched/cpufreq_schedutil.c) 根据有效利用率等信号更新频率请求。三个问题应分开回答：

1. 线程被放到哪颗 CPU；
2. 该 CPU 当前运行哪个线程；
3. cpufreq policy 请求哪个性能状态。

启动线程可能受到 top-app cgroup、cpuset、uclamp、nice、CPU affinity 和 vendor hook 影响。上述机制能改变放置、竞争份额或性能请求，但公共内核代码没有“大纲预测到用户将启动某包后，把它设为最高优先级”的规则。

### Power HAL 与 ADPF：提示通道不规定厂商算法

Android 17 的 [`IPower.aidl`](https://android.googlesource.com/platform/hardware/interfaces/+/refs/tags/android-17.0.0_r1/power/aidl/android/hardware/power/IPower.aidl) 提供 power mode、boost 与 hint session 等接口。AIDL 定义调用契约，设备 Power HAL 决定怎样把提示映射到 CPU、GPU、内存带宽或其他资源。AOSP 接口没有要求实现行为预测模型，也没有统一的“启动资源预分配”算法。

应用侧 [`PerformanceHintManager`](https://android.googlesource.com/platform/frameworks/base/+/refs/tags/android-17.0.0_r1/core/java/android/os/PerformanceHintManager.java) 允许一组线程声明目标工作时长并上报实际工作时长。Hint Session 适合周期性、可测量的工作，例如渲染循环。它的 target duration 是墙上时间目标；EEVDF deadline 是公平调度器内部的虚拟服务期限，两者不能互换。

厂商实现可能依据应用切前台、启动阶段或历史行为发出 boost，也可能进行文件预取。这些实现可以通过设备 trace、vendor 源码或厂商文档确认。仅凭 `IPower` 接口存在，无法推出某台设备采用何种策略，更无法把 OEM 数据写成 Android 17 的通用收益。

### JobScheduler：延迟后台工作与交互式启动的边界

Android 17 的 [`JobSchedulerService`](https://android.googlesource.com/platform/frameworks/base/+/refs/tags/android-17.0.0_r1/apex/jobscheduler/service/java/com/android/server/job/JobSchedulerService.java) 管理应用提交的持久化后台 job。网络、电量、充电、空闲、存储、配额和时间等 controller 共同决定 job 何时具备运行条件。

“延迟启动机制”若指 JobScheduler，它延迟的是可延期后台工作，不是用户已经请求的 Activity 启动。WorkManager 通常把满足条件的工作委托给 JobScheduler，同时提供依赖、重试和持久化语义。应用不应使用它们预订一次交互式冷启动的 CPU 执行顺序。

Android 17 新增的 `JobDebugInfo` 能帮助应用观察 job 的等待原因与累计时长。该变化属于后台任务可观测性增强，也不能作为“新应用启动调度器”的证据。

## 如何判断设备是否有预测式启动优化

面对 OEM 宣称的“智能启动”或“AI 调度”，验证工作应落到可观测事件：

1. 固定系统构建、设备温度、电量、刷新率、网络与应用数据。
2. 分开测量冷进程启动、暖进程启动和从后台恢复。
3. 用 Macrobenchmark 或等价方案记录 `timeToInitialDisplay`；需要完整可交互状态时，再记录 `reportFullyDrawn()` 对应指标。
4. 采集 Perfetto，检查 ActivityManager、应用主线程、RenderThread、CPU scheduling、frequency、I/O、binder 与 frame timeline。
5. 对照 `sched`、cpufreq、Power HAL 和 vendor trace 事件，确认 boost 或预取发生的时点。
6. 关闭对应 OEM 功能或切换同构实验组，重复足够轮次并报告分布，避免只选最好的一次。
7. 同时记录 PSS/RSS、缺页、CPU time、能耗和热状态，防止启动变快来自更高常驻内存或更激进功耗。

“平均减少 30%”至少要附带样本应用、统计量、轮次、基线版本、设备型号、存储状态和置信区间。“低端设备提升 40%”还要定义低端设备。后台内存下降比例也必须说明测量对象、时间窗口和进程存活策略。在这些条件缺失时，百分比只能视为未证实素材。
