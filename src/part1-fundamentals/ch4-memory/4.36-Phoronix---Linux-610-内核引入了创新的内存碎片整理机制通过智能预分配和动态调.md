## 这条素材混合了哪些概念

Linux 6.10 的内存管理合并窗口包含多项 mTHP（multi-size Transparent Huge Pages）改动，例如 NUMA balancing、large-folio swap-out、按尺寸统计和 `MADV_FREE` 支持。它们分别修改不同路径，不能概括成一套名为“智能内存碎片整理”的内核组件。

旧稿还把物理页规整、页面回收和系统稳定性写成了直接因果链。三个对象应分别观察：

| 对象 | 内核要解决的问题 | 适合使用的证据 |
|---|---|---|
| memory compaction | 空闲页总量可能足够，但缺少目标 order 的连续物理页 | `/proc/buddyinfo`、compaction vmstat、`mm_compaction_*` tracepoint |
| page reclaim | 可分配页数量不足，需要回收文件页或换出匿名页 | reclaim vmstat、PSI、`mm_vmscan_*` tracepoint |
| mTHP | 以小于 PMD THP 的多种 large-folio 尺寸服务匿名内存 | 每个 `hugepages-<size>kB/` 的策略和统计 |

Android framework 中的 cached app compaction 又是另一种操作。它通过 `MADV_COLD`、`MADV_PAGEOUT` 或 memcg reclaim 降低缓存进程驻留内存，不等于 `mm/compaction.c` 对 buddy 空闲块做物理页规整。

## Linux 6.10 中可定位的 compaction 改动

与 mTHP 和 compaction 直接相关的一项上游修改是 commit [`231f8c7127e3`](https://github.com/torvalds/linux/commit/231f8c7127e3)。`compaction_capture()` 早已存在；该提交调整了它捕获小于 pageblock order 的 `MIGRATE_MOVABLE` 空闲块时所用的条件。

修改后，当前 direct compaction 本身请求 `MIGRATE_MOVABLE` 时，可以捕获刚刚形成、order 与目标相符的 movable 空闲块。这对 1 MB mTHP 等小于传统 PMD THP 的请求有帮助，因为请求线程少做一轮扫描和 freelist 再分配。

这项修改有严格的执行边界：

- 只服务当前 direct compaction 上下文；
- 捕获块的 order 必须匹配目标 order；
- CMA 和 isolate migratetype 等情况仍受排除条件限制；
- 它没有预测未来的内存热点；
- 它没有建立按应用或区域分层的通用“智能预分配器”。

上游提交中提到的测试指标是特定 mTHP 工作负载下的 free scanned、migrate scanned 与扫描效率。它没有给出 Android 设备的长期碎片率或系统崩溃率。把扫描页数变化改写成“碎片率下降 60%”，指标含义已经发生改变。

## Android 17 内核怎样继承这段历史

本知识库的内核锚点是 `android17-6.18-2026-06_r6`。该标签的 [`mm/compaction.c`](https://android.googlesource.com/kernel/common/+/refs/tags/android17-6.18-2026-06_r6/mm/compaction.c) 保留了上述捕获条件，同时也包含 Linux 6.10 之后持续演进的 compaction 代码。因此，分析 Android 17 时应以 6.18 标签中的完整调用路径为准；Linux 6.10 只用于说明某项改动从哪个历史节点进入。

该标签的 GKI arm64 配置编译了 THP，但编译能力不能代表每种 mTHP 尺寸都在设备上开启。[`mm/huge_memory.c`](https://android.googlesource.com/kernel/common/+/refs/tags/android17-6.18-2026-06_r6/mm/huge_memory.c) 给出的默认策略包括：

- PMD-sized THP 的单尺寸策略继承顶层设置；
- 其他匿名 THP 尺寸在没有额外参数时采用 `never`；
- `transparent_hugepage=`、`thp_anon=`、运行时 sysfs 和厂商启动配置可以覆盖策略。

Android 17 还支持 4 KB 与 16 KB base page 产品形态。相同 order 对应的字节数会随 `PAGE_SIZE` 改变；报告 mTHP 或高阶分配时，必须同时记录基础页大小、目标尺寸、内核标签和生效策略。

## “动态调整”在内核里应怎样描述

Linux compaction 包含多项运行时决策，但这些决策有具体名称和输入，不需要用“智能”替代源码语义：

- direct compaction 由高阶分配慢路径触发，请求线程可能同步等待；
- `kcompactd` 在后台为后续高阶分配准备连续空闲块；
- proactive compaction 根据 fragmentation score 与 `compaction_proactiveness` 决定后台工作强度；
- migrate scanner 与 free scanner 从 zone 的不同方向寻找可迁移页和目标空闲页；
- watermark、目标 order、migratetype、页的可迁移性和重试策略共同限制结果。

Android 17 标签的 [VM sysctl 文档](https://android.googlesource.com/kernel/common/+/refs/tags/android17-6.18-2026-06_r6/Documentation/admin-guide/sysctl/vm.rst) 明确提醒，高 `compaction_proactiveness` 可能带来延迟尖峰。更积极的后台规整有机会增加高阶空闲块，也会消耗 CPU 和内存带宽，不能直接视为稳定性收益。

## 怎样验证设备上的收益

一次可复核实验至少应固定系统构建、设备、基础页大小、THP 策略、温度、内存压力和工作负载。采集时比较同一时间窗口内的增量：

1. 从 `/proc/buddyinfo` 观察目标 zone 与 order 的空闲块变化；
2. 从 `/proc/vmstat` 记录 `compact_stall`、`compact_success`、`compact_fail` 以及扫描计数；
3. 从各尺寸 THP `stats/` 记录 allocation、fallback、split 与 swap-out；
4. 用 `mm_compaction_*` tracepoint 对齐请求线程、`kcompactd` 和用户可感知事件；
5. 同时记录 CPU time、内存带宽、功耗与延迟分布。

“碎片率”必须给出计算方式，例如基于哪个 zone、哪个 order、哪种 fragmentation index，以及统计窗口多长。“系统崩溃减少”还要定义崩溃类型和归因证据。缺少这些信息时，60% 与 45% 均属于不可复核数字。
