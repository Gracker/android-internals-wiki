## 源码级补充（基于 deep-research/2026-07-08-android17-debuggerd-signal-handler-architecture.md）

### ⚠️ 数据边界提示

公开 AOSP 镜像 (`aosp-mirror/platform_bionic`、`platform_system_core`) 截至 2026-07-08 仍未发布 `android-17.0.0_r1` tag，以下片段引用 `main` 分支，**标记"未进入 Android 17"**——它们反映 Linux 6.12 / bionic linker 当前主线状态，不构成 Android 17 正文定论。所有"Android 17 是否改动"必须在官方 tag 公开后复核。

### 链路骨架（main 分支，未进入 Android 17）

```
内核投递 → bionic libc sigaction 表（SA_ONSTACK 命中 altstack）
        → debuggerd_signal_handler() [debuggerd/handler/debuggerd_handler.cpp]
        → 切栈到 pseudothread_stack
        → 异步安全 log 输出（不分配）
        → clone(CLONE_FILES) x 2 → crash_dump64 独占子进程
        → crash_dump ptrace 双端抓寄存器/内存/elf 符号
        → tombstone 写入 /data/tombstones/
        → notify_gdb_of_libraries（linker 侧注册的 post-dump 钩子）
```

要点：

1. **handler 在崩溃线程上就地执行**，没有专用"信号分发线程"——线程亲和性由内核投递规则决定，不是被刻意绑定。
2. **altstack 是 libc 启动期就绪的**，不是崩溃时再分配。
3. **crash_dump 是一次性进程**，不常驻，与 zygote 等长生命周期进程无关。

### altstack 与动态尺寸（main 分支）

`debuggerd_init()` 约第 825–855 行：

```cpp
size_t thread_stack_pages = 8;
void* thread_stack_allocation = mmap(nullptr, getpagesize() * (thread_stack_pages + 2), PROT_NONE,
                                     MAP_ANONYMOUS | MAP_PRIVATE, -1, 0);
...
char* stack = static_cast<char*>(thread_stack_allocation) + getpagesize();
if (mprotect(stack, getpagesize() * thread_stack_pages, PROT_READ | PROT_WRITE) != 0) { ... }

stack = (stack + thread_stack_pages * getpagesize() - 1);
stack -= 15;
pseudothread_stack = stack;

struct sigaction action;
memset(&action, 0, sizeof(action));
sigfillset(&action.sa_mask);
action.sa_sigaction = debuggerd_signal_handler;
action.sa_flags = SA_RESTART | SA_SIGINFO;
action.sa_flags |= SA_ONSTACK;   // Use the alternate signal stack if available so we can catch stack overflows.
action.sa_flags |= SA_EXPOSE_TAGBITS;  // Request that the kernel set tag bits in the fault address. ...
debuggerd_register_handlers(&action);
```

四个关键设计点：

1. **页粒度自适应 altstack**：以 `getpagesize()` 为基础。4K page → 32 KiB altstack；16K page → 128 KiB altstack。这是 Android 13 起引入的"page-size aware"模式。
2. **守护页（guard page）**：mmap 多出 `+2` 页，前后各 1 页 PROT_NONE 把 altstack 框住。栈溢出 → PROT_NONE SEGV，不会递归打自己。
3. **`thread_stack_pages = 8` 是动态上限密度**：handler 进入时不可重入，整个调用链必须塞在 8 页内。Android 17 是否调整，待 tag 公开后复核。
4. **sigaction flags 组合**：`SA_RESTART | SA_SIGINFO | SA_ONSTACK | SA_EXPOSE_TAGBITS`。
   - `SA_ONSTACK` 强制使用 altstack；
   - `SA_SIGINFO` 让 handler 拿到 `(siginfo_t*, ucontext_t*)`；
   - `SA_EXPOSE_TAGBITS` 是 Android 14+ 引入，让 fault address 的高 8 位 MTE 标签可读。

### 信号线程亲和性的实际语义

`bionic/linker/linker_main.cpp` 仅在主进程启动时调用一次：

```cpp
// linker_main.cpp（第 298 行附近）
linker_debuggerd_init();
```

`linker/linker_debuggerd_android.cpp`（全文 75 行）：

```cpp
void linker_debuggerd_init() {
  debuggerd_callbacks_t callbacks = {
#if defined(__ANDROID_APEX__)
    .get_process_info = get_process_info,
    .get_gwp_asan_callbacks = get_gwp_asan_callbacks,
#endif
    .post_dump = notify_gdb_of_libraries,
  };
  debuggerd_init(&callbacks);
}
```

结论：

- **`debuggerd_init` 全进程只调用一次**，不是每线程一份 handler。
- **崩溃信号自然归属"出事线程"**：内核直接写 `task->thread->pending` 到当前 task_struct，所以不存在"专门崩溃分发线程"——AOSP 公开资料未见主动切换线程的机制。**Android 17 待验证**。
- **崩溃线程被冻结**：信号处理函数是阻塞式同步流程，崩溃线程在 altstack 上跑完 handler + 触发 crash_dump 之前，无法回到原始 stack/PC。
- **APEX 两阶段初始化**：bootstrap linker 不信任 libc 全局，只传 `post_dump = notify_gdb_of_libraries`；`get_process_info` / `get_gwp_asan_callbacks` 留给 runtime APEX 重新注入。

### 双克隆 vm-process

`create_vm_process()`（main 分支）：

```cpp
static void create_vm_process() {
  pid_t first = clone(nullptr, nullptr, CLONE_FILES, nullptr);
  if (first == -1) {
    fatal_errno("failed to clone vm process");
  } else if (first == 0) {
    drop_capabilities();
    if (clone(nullptr, nullptr, CLONE_FILES, nullptr) == -1) {
      _exit(errno);
    }
    // crash_dump is ptracing both sides of the fork; it'll let the parent exit,
    // but keep the orphan stopped to peek at its memory.
    // ... (SIGHUP workaround ... continuing)
  }
  ...
}
```

- 第一次 `clone(CLONE_FILES)` 共享 fd 表，让 `kcmp` 校验一致；
- 第二次 `clone(CLONE_FILES)` 让原始崩溃进程继续 SIGSEGV 终止，crash_dump 独占"孤儿子进程"；
- crash_dump64 是 `/apex/com.android.runtime/bin/crash_dump64`，独立二进制。

### MTE / GWP-ASan 钩子（main 分支）

```cpp
bool debuggerd_handle_signal(int signal_number, siginfo_t* info, void* context) {
  if (signal_number != SIGSEGV) return false;
  if (info->si_code == SEGV_MTEAERR || info->si_code == SEGV_MTESERR) {
    if (!is_permissive_mte()) return false;
    debuggerd_signal_handler(signal_number, info, context);
    return true;
  }
  if (!signal_has_si_addr(info)) return false;
  return debuggerd_handle_gwp_asan_signal(signal_number, info, context);
}
```

- `SEGV_MTEAERR`/`SEGV_MTESERR`（MTE 异步/同步 tag-fault）：在 `is_permissive_mte()` 开启时，handler 走"报告 + 业务继续"路径；
- `is_permissive_mte()` 来自 `persist.sys.mte.permissive` / `persist.device_config.memory_safety_native.permissive.*` sysprop；
- 关闭时进程直接被原信号杀死。
- GWP-ASan 救援通过 `debuggerd_handle_gwp_asan_signal()` 复用主 handler 路径，配合 `debuggerd_needs_gwp_asan_recovery` 决定是否"报告 + 恢复"。

### 关键结论（Android 17 普遍推断，待 tag 复核）

1. **崩溃处理 = 业务线程同步执行**：没有专用信号分发线程。Native Crash SDK 必须在任何线程上都可能崩溃的假设下设计；不能依赖单例线程变量。
2. **altstack = 32–128 KiB**（页大小决定）：sigaltstack 深度栈会触发 PROT_NONE 二次 SEGV，让 handler 自杀。
3. **MTE 救援会"抑制死亡"**：SDK 监听到时进程仍存活，要按 GWP-ASan 主路径生成堆元数据 dump。
4. **crash_dump 迁移路径由 kcmp 约束**：SDK 不要自己 fork 抓现场；必须经由现有信号流触发 crash_dump。
5. **sigaction 在全进程注册一次**：sigchain（libart 侧）总是首跳，Java 进程总在 `debuggerd_signal_handler` 之前经过 libart 的可恢复 GWP-ASan / permissive MTE 判定。
