## 审阅结论

`debuggerd` 的 dump、unwind、tombstone 编码与 `tombstoned` 仍位于 `system/core/debuggerd/`。Bionic linker 负责在进程早期调用 `debuggerd_init()`，并提供 libc allocator、abort message、fdsan、GWP-ASan、Scudo 等诊断状态。Android 17 没有把 debuggerd 整体搬进 linker。

## 1. 进程启动时怎样接入 debuggerd

Android 17 的 `linker_main()` 在普通共享库构造函数和应用入口之前调用 `linker_debuggerd_init()`。Android 版本的适配层组装 `debuggerd_callbacks_t`，再调用 `debuggerd_init()`。

这条接线让进程很早就具备 fatal signal handler，也让 tombstone 能读取 linker/libc 已知的诊断信息。复杂的 ptrace、unwind、maps 读取和文件输出仍由 `crash_dump32/64` 与 `tombstoned` 完成。

Android 17 新增的 `RELEASE_DEPRECATE_RUNTIME_APEX` 条件会影响 `crash_dump` 位于 `/system/bin` 还是 Runtime APEX。它属于产品构建布局兼容，不改变各组件的职责。

## 2. 信号由哪个线程处理

同步硬件 fault 通常送到产生 fault 的线程，例如非法访问、总线错误或非法指令。handler 起初就在该线程的 signal frame 上运行，`ucontext_t` 保存该线程收到信号时的寄存器。

进程定向的异步信号可以由任一未屏蔽该信号的合格线程接收。signal disposition 是进程级状态，signal mask 和 alternate signal stack 是线程级状态。

Android 17 debuggerd 没有调用 `sched_setaffinity()` 或 `pthread_setaffinity_np()` 把 handler 绑定到某个 CPU。寄存器现场已经由内核写入 signal frame，CPU affinity 与现场准确性没有直接关系。

## 3. `SA_ONSTACK` 与 pseudothread stack 是两块栈

fatal action 使用 `SA_RESTART | SA_SIGINFO | SA_ONSTACK | SA_EXPOSE_TAGBITS`。`SA_ONSTACK` 只在目标线程已经通过 `sigaltstack()` 配置备用栈时生效。`debuggerd_init()` 不会为进程中每条线程统一创建 altstack。

`debuggerd_init()` 自己预留的是 pseudothread stack。它映射 10 个运行时 page：中间 8 页可读写，两侧各 1 页保持 `PROT_NONE` 作为 guard。

下面的换算用于区分 page 数与字节数。

```text
usable pseudothread stack = 8 × getpagesize()
whole mapping             = 10 × getpagesize()

4 KiB page  -> 32 KiB usable, 40 KiB mapping
16 KiB page -> 128 KiB usable, 160 KiB mapping
```

这块映射供 crash 之后 clone 出来的辅助执行单元使用，没有通过 `sigaltstack()` 安装到崩溃线程。旧文把它称为“动态 altstack”，会把两个生命周期和用途不同的对象混为一谈。

## 4. fatal signal 到 tombstone 的职责链

Android 17 的主路径可以按以下阶段理解。

```text
faulting thread
  -> debuggerd_signal_handler
  -> clone dispatch pseudothread
       shares VM/thread/signal-handler state
       keeps a separate FD table
  -> pseudothread fork/exec crash_dump32|64
  -> crash_dump ptrace threads and read CrashInfo/maps/registers
  -> VM snapshot assists unwind
  -> tombstoned writes text/protobuf tombstone
  -> native crash notification reaches system_server
```

这条链路仍然使用 ptrace。dispatch pseudothread 创建时刻意不共享 FD table，使其能在原进程接近 fd exhaustion 时关闭自己的描述符并建立 pipe。后续 VM snapshot 中的 clone 细节不能反推 pseudothread 使用 `CLONE_FILES`。

handler 会临时调整 `PR_SET_DUMPABLE`，并在受支持的内核上处理 ptracer 约束，流程结束后恢复原值。第三方 SDK 不应在 fatal handler 中重复改这些进程安全属性。

## 5. ART sigchain 位于 debuggerd handler 前方时

linker 先安装 debuggerd action。ART 启动后，`libsigchain` claim `SIGSEGV` 等运行时相关信号，把原 action 保存为用户链的一部分，再让 `SignalChain::Handler` 成为内核看到的 action。

已 claim 信号的顺序可概括为：

1. ART 或 native bridge 的 special handler；
2. `android_handle_signal()`，用于平台定义的 recoverable GWP-ASan 或 permissive MTE；
3. 当前用户 action；没有 Crash SDK 时通常继续到先前保存的 debuggerd action。

应用通过标准 `sigaction()` 安装 handler 仍然有效，但必须保存旧 action 并按原语义转交。直接覆盖后 `_exit()` 会丢失系统 tombstone、allocator 证据或 system_server 的 native crash 记录。

`AddSpecialSignalHandlerFn()`、Bionic 保留实时信号与 debuggerd client 都是平台私有接口，不属于 NDK 兼容承诺。Crash SDK 不应通过 `dlsym()` 争抢 ART 的内部 special-handler 槽位。

## 6. MTE 与 GWP-ASan 的恢复边界

`SA_EXPOSE_TAGBITS` 让支持该标志的内核在 fault `siginfo_t.si_addr` 中保留架构定义的 tag bits，便于 MTE 诊断。它不承诺所有寄存器和返回地址都保留 tag。

Recoverable GWP-ASan 与 permissive MTE 是平台受控模式：

- fault 必须符合 allocator 或 MTE 的判定条件；
- debuggerd 先生成报告；
- 平台回调调整 allocator protection 或线程 MTE 模式；
- ART signal chain 在恢复成功时停止向用户 handler 继续分发。

“Recoverable”不表示进程状态仍然可靠。内存越界或 use-after-free 已经发生，进程后续仍可能崩溃。SDK handler 若收到普通 `SIGSEGV`，不能只看 `si_code` 就吞掉信号并继续执行。

同步 MTE fault 的 `SEGV_MTESERR` 能更接近触发访问；异步 fault 的 `SEGV_MTEAERR` 可能延迟上报，也可能没有精确 fault address。两类报告应分开归因。

## 7. Crash SDK 的兼容边界

第三方 fatal handler 应保持很小：

- 复制固定大小的 `siginfo_t` 与 `ucontext_t`；
- 写入预分配缓冲或预打开、非阻塞的 fd；
- 处理 partial write、`EINTR` 和重入；
- 不调用 Java/JNI、`malloc()`、`dlopen()`、`dladdr()`、普通日志或网络；
- 按保存的旧 `sigaction` 继续分发；
- 保留原 signal 和 fault address。

`write()` 属于 async-signal-safe，并不保证写入阻塞 fd 时及时返回。SDK 仍需设计截断与超时路径。

量产应用获取自身历史 native tombstone 可使用 API 31 起的 `ApplicationExitInfo.getTraceInputStream()`。主动发送 `BIONIC_SIGNAL_DEBUGGER`、构造 debuggerd wire protocol 或读取其他进程 tombstone，都不属于普通应用的稳定能力。

## 8. 调试时怎样逐段定位

Tombstone 缺失时，按职责链检查：

1. `logcat -b crash` 是否出现 signal、`si_code`、fault address 与 abort message；
2. 系统是否生成文本或 protobuf tombstone；
3. build ID、ABI、APEX/APK 版本与 unstripped symbols 是否匹配；
4. `crash_dump` 是否受 ptrace、SELinux、fd exhaustion 或进程属性影响；
5. allocator 是否给出 GWP-ASan、Scudo、fdsan 或 MTE 证据；
6. 多个 Crash/APM SDK 是否正确保存并转交各自的旧 action。

ANR 的 SIGQUIT/trace、Java 未捕获异常、主动 debuggerd backtrace 和 native fatal tombstone 是不同采集路径，不能用同一份“崩溃恢复”结论解释。
