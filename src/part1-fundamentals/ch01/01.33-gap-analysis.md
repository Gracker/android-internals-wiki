## 源码复核结论

本文件与[1.54 Binder 线程池实现机制](../ch01-architecture/1.54-binder-thread-pool-implementation/1.54-binder-thread-pool-implementation.md)重复。旧路径仍由 `SUMMARY.md` 引用，因此保留本页作为兼容入口；实现细节和后续修订以 1.54 为准。线程池耗尽诊断可继续阅读[1.38 Binder 线程池饥饿](../ch01-architecture/38-binder-thread-pool-starvation-performance.md)，Binder 总览见[1.4 Binder IPC](../ch01-architecture/04-binder.md)。

原正文有以下源码错误，不能继续用于 Android 17：

- `ProcessState`/`IPCThreadState` 中没有 `mStarvationStartTimeMs`、100 ms 饥饿检测后自动提权的实现；
- libbinder 没有“10 ms 快速响应、100 ms 普通响应”的 Binder 双间隔调度器；
- lazy worker 不会在任务完成后自动退出，Android 17 常规 driver 路径也不靠 `BR_FINISHED` 周期性回收 worker；
- 线程池上限不能按“高并发应用 20–25、低内存设备 10–12”这类经验表统一配置；
- “单线程大于 1000 TPS”“平均小于 5 ms”没有 workload、事务大小、CPU、锁与服务实现，不能作为性能基线；
- `BINDER_VM_SIZE` 使用 `1 MiB - 2 × page_size`，在 16KB page 设备上不能写成固定的 `1 MiB - 8 KiB`；
- Binder 事务不是“整包零拷贝”。驱动在发送方与接收方之间仍要复制 transaction data，Binder buffer 的 mmap 设计避免的是额外用户态中转。

## Android 17 的线程池模型

本文讨论 C++ libbinder 与 kernel Binder driver。Java Binder、NDK Binder、RPC Binder、polling mode 和显式加入线程池的线程有各自入口，不能共享一组固定数字。

### `ProcessState` 管理进程级资源

`ProcessState` 持有 Binder driver fd、进程级 mmap、线程池启动状态、最大 lazy worker 数与线程命名计数。native libbinder 的默认值是：

- `DEFAULT_MAX_BINDER_THREADS = 15`；
- `BINDER_VM_SIZE = 1 MiB - 2 × page_size`。

15 表示 driver 可按需请求的 lazy worker 上限。`startThreadPool()` 还会主动创建一条 main pool thread；显式调用 `joinThreadPool()` 的线程、polling 模式、Java Binder 运行时和进程自己的配置都会改变实际可见线程数。把任意进程概括成“固定 15 条”或“固定 16 条”都会误导现场判断。

### `IPCThreadState` 管理线程级协议状态

每条参与 Binder 的线程有自己的 `IPCThreadState`，负责：

- 组装 `BC_TRANSACTION`/`BC_REPLY` 等写命令；
- 执行 `talkWithDriver()` 的 `BINDER_WRITE_READ` ioctl；
- 解析 `BR_TRANSACTION`、`BR_REPLY`、`BR_SPAWN_LOOPER` 等返回命令；
- 在 `joinThreadPool()` 中进入 driver read/dispatch loop；
- 保存 calling pid/uid、work source、strict mode 与 transaction 相关线程局部状态。

线程池内部的 main pool thread 与 Android 应用 UI 主线程无关。main/worker 的差异落在 `BC_ENTER_LOOPER`、`BC_REGISTER_LOOPER` 和线程创建来源上。

### Driver 只在条件满足时请求 worker

当进程没有可用 waiting thread、当前请求数允许增加、已启动 lazy worker 少于 `max_threads`，且当前 looper state 满足要求时，driver 可以向用户空间返回 `BR_SPAWN_LOOPER`。`IPCThreadState::executeCommand()` 收到后调用 `ProcessState::spawnPooledThread(false)`，新线程进入 `joinThreadPool(false)` 并用 `BC_REGISTER_LOOPER` 注册。

worker 创建是 driver 与 libbinder 协作的结果。一次事务没有直接“创建线程”的保证；等待线程存在、线程上限、looper state 和进程是否启动 thread pool 都会改变结果。

## 上限配置的安全边界

`ProcessState::setThreadPoolMaxThreadCount()` 通过 `BINDER_SET_MAX_THREADS` 告诉 driver lazy worker 上限。线程池启动后，libbinder 不允许把上限降低到当前值以下，因为已经存在的 worker 无法据此安全撤销。普通 SDK 应用也没有一个公开 API，可以随意修改 framework Java Binder pool。

提高上限可能缓解服务端 worker 长时间被占用造成的排队，也会增加：

- native stack 与 thread metadata；
- CPU runnable 竞争和 context switch；
- 服务内部锁竞争；
- 并发进入原本未按高并发设计的状态；
- 下游 Binder、I/O、数据库或硬件服务的压力。

因此，上限调整要针对具体服务完成 load test。更常见的修复是缩短 Binder 方法的同步工作，把长 I/O/计算交给有界执行器，并避免 worker 持锁等待仍需同一线程池处理的回调。

## 优先级与“饥饿”要分开

Binder transaction 的调度策略来自调用线程、目标 node 设置、driver 的 priority 计算和权限限制。优先级继承不等同于线程池饥饿恢复，也不存在一个通用 100 ms 阈值把所有 worker 自动升到高优先级。

线程池饥饿描述目标进程暂时没有可用 Binder worker。常见成因包括：

- worker 在服务代码中执行慢 I/O 或计算；
- worker 持锁或等待主线程；
- 同步嵌套 IPC 形成长等待链；
- oneway transaction 在同一 node 上积压；
- 下游服务或硬件返回慢。

单条 starvation 日志或线程总数不足以确定原因。还要检查每条 worker 的状态、服务端开始执行时间、调用方等待区间和目标进程待办事务。

## Perfetto 取证顺序

1. 用 Binder transaction id 或调用栈找到一次慢调用；
2. 对齐调用方发起、driver 传输、服务端开始和 reply；
3. 列出目标进程所有 Binder worker 的 running/runnable/blocking 状态；
4. 对 blocking worker 继续展开 lock、futex、Binder、I/O 或主线程依赖；
5. 检查 oneway/sync、目标 node、调用频率和事务大小；
6. 在修改上限前，用压力测试确认排队时间、CPU、内存和锁竞争的变化。

`binder transaction` slice 很长，可能包含调用方等待服务端和 reply 的时间，不能整体归到 driver CPU。服务端 worker 长时间运行，也可能来自业务代码，不表示 Binder driver 本身耗时高。

- [kernel `binder.c`](https://android.googlesource.com/kernel/common/+/refs/tags/android17-6.18-2026-06_r6/drivers/android/binder.c)：waiting thread、spawn 条件、transaction 派发与 priority；
- [kernel `binder_alloc.c`](https://android.googlesource.com/kernel/common/+/refs/tags/android17-6.18-2026-06_r6/drivers/android/binder_alloc.c)：进程 Binder buffer 映射与分配；
