## 1. 电源管理没有一条固定的端到端调用链

Android 17 的电池续航来自多层策略共同作用。AOSP 定义 framework 状态机、HAL 合同和 Android Common Kernel 机制，SoC 厂商再接入 cpufreq、devfreq、电源域、固件与传感器。平台源码能确认接口与默认实现，不能从中推导每款设备的频点、功耗或续航收益。

| 层次 | 主要职责 | 不能直接推出的结论 |
|---|---|---|
| `PowerManagerService` | wakefulness、wake lock、用户活动、显示电源请求、suspend blocker | PMS 不替内核选择 CPU 频率或 idle state |
| Device Idle / App Standby / JobScheduler | 限制和批处理可延期后台活动 | Doze 不等同于 CPU idle，也不保证某个进程立即停止 |
| Power HAL / ADPF | 接收 mode、boost、Hint Session、composition data；提供 headroom 能力 | AIDL 不规定厂商必须写哪个 sysfs 或固件接口 |
| Linux scheduler / EAS | 管理 runnable task、公平选人和选核 | EAS 不是调频 governor |
| schedutil / cpufreq | 根据调度器利用率等信号请求 CPU 频率 | 频率请求还受 driver、thermal 和固件限制 |
| cpuidle | CPU 无任务可运行时选择可进入的 idle state | cpuidle 不负责应用后台权限 |
| thermal / 电流限制 | 限制可持续功率和部分功能 | 降频不一定由 framework thermal status 触发 |
| Power Stats / Batterystats | 记录状态驻留、能量或软件归因 | 观测接口不会主动调节硬件 |

这张表是排查顺序，不是一个同步状态机。屏幕熄灭后，可运行任务可能减少，schedutil 利用率随之降低，CPU 也更容易进入深 idle；这属于多层行为的间接结果。AOSP 没有一条 `PowerManagerService → schedutil → cpuidle` 的标准直调用。

## 2. Framework 管理设备状态

Android 17 的 [`PowerManagerService`](https://android.googlesource.com/platform/frameworks/base/+/refs/tags/android-17.0.0_r1/services/core/java/com/android/server/power/PowerManagerService.java) 在 `system_server` 中维护电源状态。它处理 wake lock、用户活动超时、wakefulness、各 display group 的请求、Dream 和 suspend blocker。

`DIRTY_*` 位用于标记哪些 framework 状态需要重新计算。`updatePowerStateLocked()` 会在 wakefulness 尚未稳定时重复一部分计算，再更新显示、Dream 和 suspend blocker。这是 PMS 内部的状态收敛过程，与 cpufreq governor 的更新周期无关。

PMS 可以向 Power HAL 发送 `INTERACTIVE`、`DEVICE_IDLE`、`DISPLAY_INACTIVE`、`LOW_POWER` 或 `LAUNCH` 等 mode。电池节省策略还能过滤 `LAUNCH` mode。信号抵达 HAL 后怎样映射到 CPU、GPU、内存带宽或 idle 约束，由设备实现决定。

Device Idle 是 Android 的后台策略状态；system suspend 是整机暂停；CPU idle 是单颗 CPU 在没有 runnable task 时进入空闲状态。三个术语要分开：

- Device Idle 约束网络、job、alarm 和部分 wake lock；
- system suspend 要求系统释放相应 suspend blocker；
- cpuidle 在系统仍运行时也会频繁进入和退出浅层或深层 state。

## 3. Power HAL 表达意图

Android 17 的 [`IPower.aidl`](https://android.googlesource.com/platform/hardware/interfaces/+/refs/tags/android-17.0.0_r1/power/aidl/android/hardware/power/IPower.aidl) 定义 mode、boost、Hint Session、CPU/GPU headroom 与 composition data 等合同。合同描述参数、能力查询和错误边界，没有规定设备的控制算法。

这里有三组常被混写的接口：

- `setMode()` 表达持续到显式关闭的场景状态；
- `setBoost()` 表达带时长的短时需求；
- ADPF Hint Session 让一组线程报告 target duration 与 actual duration，设备可据此调整后续资源。

枚举值存在不代表设备支持。调用方应通过 `isModeSupported()`、`isBoostSupported()` 或 `getSupportInfo()` 查询能力。AOSP reference Power HAL 对部分高级查询会返回 unsupported，量产支持由 vendor HAL 决定。

Hint Session 的墙上时间目标也不是 EEVDF 的虚拟 deadline。厂商可以把 ADPF 信息映射到 uclamp、频率、GPU 或带宽请求，但这种映射不属于公共 AIDL 语义。

## 4. 内核分开处理选核、选人、调频和空闲

Android 17 的内核锚点固定为 `android17-6.18-2026-06_r6`。

### EEVDF 与 EAS

普通公平调度实体由 EEVDF 按 eligibility 与虚拟 deadline 选取。任务唤醒时，满足条件的 EAS 路径使用 CPU capacity 和 Energy Model 比较候选 CPU。两项机制都位于 [`kernel/sched/fair.c`](https://android.googlesource.com/kernel/common/+/refs/tags/android17-6.18-2026-06_r6/kernel/sched/fair.c)，但回答不同问题：EEVDF 选择本 CPU 下一位运行者，EAS 选择任务放在哪颗 CPU。

### schedutil

[`cpufreq_schedutil.c`](https://android.googlesource.com/kernel/common/+/refs/tags/android17-6.18-2026-06_r6/kernel/sched/cpufreq_schedutil.c) 把调度器利用率、capacity、uclamp、I/O wait 等信号转换为 cpufreq policy 请求。`rate_limit_us` 等机制限制更新节奏。

schedutil 给出的是频率请求。cpufreq driver、共享 policy、OPP、thermal QoS、硬件电流限制和固件会继续约束结果。设备也可能选择其他 governor，Android 17 平台版本不强制所有 SoC 使用 schedutil。

### cpuidle

cpuidle driver 公布硬件支持的 idle states，包括退出延迟与 target residency。governor 根据预计空闲时长和 latency constraint 选择 state。Android 17 内核包含 [`menu`](https://android.googlesource.com/kernel/common/+/refs/tags/android17-6.18-2026-06_r6/drivers/cpuidle/governors/menu.c) 与 [`TEO`](https://android.googlesource.com/kernel/common/+/refs/tags/android17-6.18-2026-06_r6/drivers/cpuidle/governors/teo.c) 等实现，运行时使用哪一个由内核配置和设备决定。

更深 state 往往有更低静态功耗和更高退出延迟。频繁 timer、IPI、IRQ 或 runnable work 会缩短 residency，使深 state 难以摊平进出成本。排查“待机耗电”时，唤醒来源和 residency 比单看 CPU 平均频率更有解释力。

## 5. Thermal 是并行约束

Android 17 的 [`IThermal.aidl`](https://android.googlesource.com/platform/hardware/interfaces/+/refs/tags/android-17.0.0_r1/thermal/aidl/android/hardware/thermal/IThermal.aidl) 向 framework 报告温度、阈值、cooling device 和 throttling severity。降载控制可以发生在硬件、固件、Linux thermal core 或 vendor daemon 中，不必等待 framework 回调。

PowerManager 公开的 thermal status 适合应用调整分辨率、特效、帧率或并发度，不能换算成固定 CPU/GPU 频率上限。相同 severity 在不同设备上可能对应不同动作。持续性能测试必须记录温度曲线和 throttling 状态，否则冷机峰值与稳态吞吐会被混在一起。

## 6. 控制面与观测面要配对

调优需要同时观察“发出了什么策略信号”和“硬件结果怎样变化”：

| 观察对象 | 常用证据 |
|---|---|
| PMS 与 wake lock | `dumpsys power`、Perfetto power/wakelock 轨道 |
| 后台任务与 alarm | `dumpsys jobscheduler`、`dumpsys alarm`、应用 standby bucket |
| CPU 调度和频率 | Perfetto sched、cpufreq、idle 与 uclamp 信息 |
| thermal | PowerManager 状态、Thermal HAL/内核事件、设备温度 |
| suspend 与唤醒 | suspend/resume trace、wakeup source、irq/timer |
| 能量和状态驻留 | Power Stats HAL、Batterystats、设备 rail 或实验室电源 |

Power Stats HAL 是只读统计接口。它可报告 power entity residency、energy consumer 和 energy meter 的自开机累计值；它与接收性能提示的 Power HAL 不是同一接口。Batterystats 还包含 framework 侧的 UID 与组件归因，模型值和硬件测量值也不能混作同一口径。

一次实验应固定系统 build、设备、亮度、网络、刷新率、温度、充电状态和工作负载。报告平均功耗时还要给出采样窗口、稳态区间、循环次数与方差；只比较电量百分比变化容易受到电池计量粒度和后台噪声影响。

## 7. 应用与系统工程师各自能做什么

应用侧可以减少不必要的 wake lock、精确 alarm、后台网络、轮询和高频小任务；可延期工作交给 JobScheduler/WorkManager；周期性高负载可使用 ADPF 并响应 thermal status。应用无权假定量产设备允许写 cpufreq、cpuidle 或 thermal sysfs。

系统侧要从目标设备的 VINTF、Power/Thermal HAL、kernel config、bootconfig、governor、OPP、firmware 和 vendor trace 还原策略。修改一个 governor 参数可能同时影响延迟、能耗和热平衡，必须在交互、后台、持续负载与 suspend 场景分别复测。
