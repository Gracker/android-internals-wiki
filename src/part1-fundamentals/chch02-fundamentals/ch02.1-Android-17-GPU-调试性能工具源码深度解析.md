# ch02.1 Android 17 SurfaceFlinger 帧观测组件源码解析

这组代码观测的是 layer、buffer、present 与 jank 分类，不能统称为“GPU 性能监控子系统”。SurfaceFlinger 能知道某个 GPU completion fence 何时 signal，也能判断 client composition 是否错过 deadline；它通常不知道 shader 指令、纹理带宽、GPU cache miss 或每个 draw call 的成本。

本文固定到 Android 17 / API 37 / `android-17.0.0_r1`，只解释五个源码对象：

- `FrameTimeline` 生成 expected/actual 时间线并做 jank 分类；
- `FpsReporter` 从 `FrameTimeline` 的 present 时间计算 task 对应 layer tree 的 FPS；
- `JankTracker` 批量投递已经生成的 `JankData`；
- `FrameTracer` 把 buffer 生命周期事件写入 Perfetto；
- `TimeStats` 把帧结果聚合成统计与直方图。

GPU render stage、硬件 counter、频率和 Vulkan frame capture 属于其他数据源。工具选择见 [2.15 Android 17 GPU 图形调试与性能优化工具链](../ch02-rendering/2.15-android17-gpu-debug-tools.md)，GPU trace packet 与 SQL 表见 [2.51 Android 17 GPU Trace 数据源与 Trace Processor 证据链](../ch02-rendering/2.51-android17-gpu-debug-performance-tools.md)。

## 1. 五个对象的职责边界

| 组件 | 输入 | 输出 | 适合回答的问题 |
|---|---|---|---|
| `FrameTimeline` | 调度预测、SurfaceFrame、DisplayFrame、present fence | jank 分类、Perfetto frame timeline、FPS 计算所需历史 | 哪一帧偏离预算，异常靠近 App 还是显示侧 |
| `FpsReporter` | task metadata、layer hierarchy、present history | `IFpsListener::onFpsReported(float)` | 某个 task 对应 layer tree 的近期呈现速率 |
| `JankTracker` | `FrameTimeline` 生成的 `JankData` | `IJankListener::onJankData()` | 已分类帧怎样批量送到 layer listener |
| `FrameTracer` | buffer id、frame number、timestamp、fence | `android.surfaceflinger.frame` Perfetto packets | buffer 在 dequeue、queue、acquire、latch、present 哪段停留 |
| `TimeStats` | 帧时长、present、refresh/render rate、jank payload | dumpsys、statsd pull atoms | 一段时间内的帧与 jank 分布 |

这些输出互相补充。FPS 下降只能说明呈现节奏变慢；jank type 给出分类方向；FrameTracer 复原 buffer 节点；GPU counter 或 frame capture 才能继续解释 GPU 微架构成本。

## 2. `FpsReporter`：从 task 找 layer，再按 present 计算 FPS

Android 17 的 [`FpsReporter.h`](https://android.googlesource.com/platform/frameworks/native/+/refs/tags/android-17.0.0_r1/services/surfaceflinger/FpsReporter.h) 把 listener 与 `taskId` 放在 `TrackedListener` 中，固定最小派发间隔为 500 ms。这个间隔限制回调频率，不代表 FPS 使用固定 500 ms 滑动窗口。

[`dispatchLayerFps()`](https://android.googlesource.com/platform/frameworks/native/+/refs/tags/android-17.0.0_r1/services/surfaceflinger/FpsReporter.cpp) 按以下顺序工作：

1. 距上次派发不足 500 ms 时返回；
2. 在 `mMutex` 内复制 listener 列表；
3. 遍历当前 `LayerHierarchy`，按 `METADATA_TASK_ID` 找到每个 task 的根；
4. 遍历该根的子树，收集所有 layer id；
5. 调用 `FrameTimeline::computeFps(layerIds)`；
6. 通过 oneway `IFpsListener` 回调结果。

`computeFps()` 会筛选至少包含一个目标 layer 且已经 present 的 DisplayFrame。若 present 时间少于两个，结果为 0；否则用相邻 present 间隔总和计算平均 FPS。它测量的是呈现节奏，不是应用提交率、显示刷新率或 GPU 利用率。

锁的边界也要讲清楚。listener map 的锁在 Binder 回调前已经释放，但 `FpsReporter.h` 要求调用者持有 SurfaceFlinger 的 `mStateLock`，因为层级遍历需要稳定状态。`IFpsListener` 是 oneway 接口，可以避免等待接收端处理完成，发送 Binder transaction 与遍历层级仍有成本。

注册入口是隐藏的 `ISurfaceComposer.addFpsListener()`，AIDL 注释要求 `READ_FRAME_BUFFER`。Android 17 的 [`ISurfaceComposer.aidl`](https://android.googlesource.com/platform/frameworks/native/+/refs/tags/android-17.0.0_r1/libs/gui/aidl/android/gui/ISurfaceComposer.aidl) 和服务实现都执行这一权限边界，普通第三方应用不能把它当成通用 FPS SDK。

## 3. `JankTracker`：分类后的异步投递

jank 分类发生在 [`FrameTimeline.cpp`](https://android.googlesource.com/platform/frameworks/native/+/refs/tags/android-17.0.0_r1/services/surfaceflinger/Scheduler/FrameTimeline.cpp)。`SurfaceFrame` 形成 `JankData` 后调用 `JankTracker::onJankData(layerId, data)`。因此，`JankTracker` 不负责决定 `AppDeadlineMissed`、`SurfaceFlingerGpuDeadlineMissed` 等类型；它管理积压数据和 listener。

Android 17 的 [`JankTracker.cpp`](https://android.googlesource.com/platform/frameworks/native/+/refs/tags/android-17.0.0_r1/services/surfaceflinger/Jank/JankTracker.cpp) 有四个值得保留的实现点：

- `sListenerCount == 0` 时，`onJankData()` 在调用线程上直接返回；
- 注册、移除、入队和 flush 工作交给低优先级 `BackgroundExecutor`；
- 每个 layer 的积压达到 50 条时自动 flush；
- 调用方也能显式 flush，移除还可以指定 `afterVsync`，让目标帧之后的数据保持完整。

“批量大小 50”描述自动派发阈值，不表示每次 callback 一定含 50 条。显式 flush、listener 移除和已有积压都可能产生更小批次。数据先按 layer id 放进 `unordered_multimap`，listener 回调在内部锁释放后执行。

Android 17 framework 提供带 feature flag 的 `AttachedSurfaceControl.registerOnJankDataListener()`。直接的 `SurfaceControl.addOnJankDataListener()` 仍是隐藏接口。应用侧入口与 `JankData` 字段见 [`AttachedSurfaceControl.java`](https://android.googlesource.com/platform/frameworks/base/+/refs/tags/android-17.0.0_r1/core/java/android/view/AttachedSurfaceControl.java) 和 [`SurfaceControl.java`](https://android.googlesource.com/platform/frameworks/base/+/refs/tags/android-17.0.0_r1/core/java/android/view/SurfaceControl.java)。使用前还要核对目标 SDK 暴露、feature flag 和设备构建，不能只看服务端类存在。

## 4. `FrameTracer`：buffer 生命周期事件

[`FrameTracer`](https://android.googlesource.com/platform/frameworks/native/+/refs/tags/android-17.0.0_r1/services/surfaceflinger/FrameTracer/FrameTracer.cpp) 注册名为 `android.surfaceflinger.frame` 的 Perfetto data source。`initialize()` 用 `std::call_once` 初始化 system backend 并注册数据源。`OnSetup()`、`OnStart()` 和 `OnStop()` 没有额外业务逻辑，启停与 trace gating 仍由 Perfetto `DataSource::Trace()` 负责。

`Layer.cpp` 在相应节点调用：

- `traceTimestamp()` 记录 dequeue、queue、latch 和 fallback composition 等已知时间；
- `traceFence()` 在 acquire 或 present fence 已 signal 时写入时间；尚未 signal 的 fence 先进入 pending 列表；
- 后续同一 buffer 的 trace 调用会检查 pending fence；
- 距 signal 已超过 60 秒的陈旧 fence 不再生成事件；
- layer 销毁或断开时，`onDestroy()` 删除该 layer 的追踪状态。

FrameTracer packet 带 layer name、buffer id、frame number、event type、timestamp 与可选 duration。这些字段有助于复原 buffer 流动，仍不能直接给出 GPU command queue 内的 render pass 或 shader 时间。

“DataSource 回调为空”也不能推导出零开销。trace 关闭时，Perfetto gating 会避开大部分 lambda 内工作；trace 开启后仍有互斥锁、layer map、pending fence 与 packet 写入。开销大小要按设备、layer 数和采集配置测量。

## 5. `TimeStats`：长期聚合与 pull 语义

Android 17 的 [`TimeStats.cpp`](https://android.googlesource.com/platform/frameworks/native/+/refs/tags/android-17.0.0_r1/services/surfaceflinger/TimeStats/TimeStats.cpp) 维护 global 与 per-layer 统计。内容包括总帧数、janky frame 分类、refresh/render rate bucket、present-to-present 等时间差、RenderEngine timing 和 composition strategy 状态。

`histogramToProto()` 先按出现次数降序排列 bucket，再截取最多 `mMaxPulledHistogramBuckets` 个；默认上限是 6。这个 protobuf 顺序用于控制 pull atom 大小，不能按数组位置理解为帧时长从小到大。

statsd 使用两个 pull atom：

- `SURFACEFLINGER_STATS_GLOBAL_INFO`：atom id 10062；
- `SURFACEFLINGER_STATS_LAYER_INFO`：atom id 10063。

旧稿中的 51017 不对应 Android 17 这两个 atom。`onPullAtom()` 在处理后启用 TimeStats；global 或 layer pull 都会清除自己已经取出的聚合数据，因此连续两次 pull 不是同一累计窗口。

下面的命令用于在有 shell/dumpsys 权限的设备上显式控制 TimeStats：

```bash
adb shell dumpsys SurfaceFlinger --timestats -clear
adb shell dumpsys SurfaceFlinger --timestats -enable
# 复现目标场景
adb shell dumpsys SurfaceFlinger --timestats -dump
adb shell dumpsys SurfaceFlinger --timestats -disable
```

`-clear` 清空旧数据，`-enable` 开始统计，`-dump` 输出当前窗口，`-disable` 停止继续积累。量产设备可能限制 dumpsys 内容；统计窗口也应写进测试记录。

## 6. SurfaceFlinger 调试属性不属于观测组件

[`SurfaceFlinger.cpp`](https://android.googlesource.com/platform/frameworks/native/+/refs/tags/android-17.0.0_r1/services/surfaceflinger/SurfaceFlinger.cpp) 在构造阶段读取 `debug.sf.enable_gl_backpressure`、`debug.sf.luma_sampling`、`debug.sf.disable_client_composition_cache` 和 `debug.sf.predict_hwc_composition_strategy`。它们会改变合成或采样行为，不是用于开启前述四种统计的统一属性系统。

以 `debug.sf.enable_gl_backpressure` 为例，字段参与 HWC backpressure 和 scheduler feature 选择。修改它可能改变被测路径本身。性能采集时应记录属性值，不能为了“打开监控”随意切换。

旧稿还列出通用的 `persist.sf.*` 前缀，但没有给出 Android 17 中对应的具体读取点。属性是否存在、何时读取、是否只在 userdebug 生效，都应逐个沿 `GetProperty()`、`property_get()` 或生成的 SurfaceFlinger config 查证。

## 7. gralloc usage 转换为何不在这条观测链

[`GrallocUsageConversion.cpp`](https://android.googlesource.com/platform/system/core/+/refs/tags/android-17.0.0_r1/libgrallocusage/GrallocUsageConversion.cpp) 转换旧版 gralloc producer/consumer usage bit。它参与 buffer 分配语义兼容，没有采集 FPS、jank、frame timeline 或 GPU counter。

usage bit 有助于判断 buffer 准备用于 GPU texture、render target、HWC、camera 或 video 等用途，但标记描述允许的使用方式，不代表该帧已经沿某条硬件路径执行。把该文件列为“第五个 GPU 监控子系统”会混淆资源契约与观测数据。

## 8. 怎样组合这些证据

一次帧问题可以按以下顺序收敛：

1. 用 FrameTimeline 找到 late frame，并区分 App、SurfaceFlinger、DisplayHAL 与 prediction 等分类。
2. 用 FrameTracer 对齐目标 layer 的 queue、acquire、latch 和 present，确认 buffer 停留区间。
3. 用 CPU scheduling、Binder、锁和 GC 轨道解释应用或 SurfaceFlinger 的 CPU 延迟。
4. 出现 GPU completion 偏晚时，再加入设备支持的 GPU render stage、frequency 和 counter。
5. 用 TimeStats 判断单帧异常是否形成持续分布，用 FPSReporter 或应用帧指标观察呈现速率。

完整的四组件数据关系和 jank 类型见 [2.52 Android 17 帧诊断](../ch02-rendering/2.52-android17-gpu-debug-performance-tools.md)。分析结论应写明数据源、设备 GPU/驱动、Surface/layer、合成类型与采集窗口；仅凭一条 FPS 或 `SurfaceFlingerGpuDeadlineMissed` 不能断言 shader 是瓶颈。
