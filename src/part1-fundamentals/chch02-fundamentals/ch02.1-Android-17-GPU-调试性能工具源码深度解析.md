# ch02.1 Android 17 SurfaceFlinger GPU 性能监控子系统源码解析

## 概述

Android 17 的 SurfaceFlinger 内部集成了完整的 GPU 性能监控基础设施，由四大子系统构成：**FPSReporter**（分层 FPS 监控）、**JankTracker**（卡顿分类检测）、**FrameTracer**（Perfetto 跨进程帧追踪）和 **TimeStats**（帧时间直方图统计）。这些子系统在 `frameworks/native/services/surfaceflinger/` 下实现，通过系统属性开关控制，为应用开发者、系统开发者和性能分析工具提供实时性能数据。

与 §14.8 讨论的外部 GPU 调试工具（AGI、Perfetto GPU 计数器等）不同，本节聚焦于 SurfaceFlinger **进程内部**的性能监控基础设施——它们如何被架构、如何在源码层面工作、以及各自的开销特征。

> **版本边界**：所有源码引用基于 `android-17.0.0_r1`，适用于 Android 12 (API 31) 及以上版本，部分特性（如 FrameTracer Perfetto DataSource）在 Android 14+ 才完整集成。

## 要点

### 🔹 SurfaceFlinger GPU 调试属性系统

SurfaceFlinger 在初始化阶段通过系统属性加载大量 GPU 调试开关。这些属性决定了 GPU 合成、回压、预测等关键行为的运行时表现。

**核心调试属性**（`android-17.0.0_r1`）：

```cpp
// frameworks/native/services/surfaceflinger/SurfaceFlinger.cpp:541
mBackpressureGpuComposition = base::GetBoolProperty("debug.sf.enable_gl_backpressure", true);
ALOGI_IF(mBackpressureGpuComposition, "Enabling backpressure for GPU composition");

// SurfaceFlinger.cpp:549
property_get("debug.sf.luma_sampling", value, "1");
property_get("debug.sf.disable_client_composition_cache", value, "0");
property_get("debug.sf.predict_hwc_composition_strategy", value, "1");
```

**GPU 回压控制**（`debug.sf.enable_gl_backpressure`）是默认开启的关键开关。当启用时，SurfaceFlinger 会在 GPU 合成管线积压时主动施加回压，避免帧队列无限增长导致延迟累积。这一机制直接影响用户感知的输入延迟和帧一致性。

**调试属性的分层设计**：

| 属性前缀 | 控制范围 | 典型场景 |
|----------|---------|---------|
| `debug.sf.*` | SurfaceFlinger 合成行为 | GPU 回压、HWC 预测、luma 采样 |
| `ro.surface_flinger.*` | 只读构建时配置 | 虚拟显示器、广色域支持 |
| `persist.sf.*` | 持久化调试开关 | 帧调试 overlay、Systrace 级别 |

### 🔹 FPSReporter 分层 FPS 监控架构

FPSReporter 是 SurfaceFlinger 中负责向系统服务（如 WindowManager）和应用提供实时 FPS 数据的组件。

**类架构**（`android-17.0.0_r1`）：

```cpp
// frameworks/native/services/surfaceflinger/FpsReporter.h:28-36
class FpsReporter : public IBinder::DeathRecipient {
    struct TrackedListener {
        sp<gui::IFpsListener> listener;
        int32_t taskId;
    };

    void dispatchLayerFps(const frontend::LayerHierarchy& layerHierarchy);
    void addListener(const sp<gui::IFpsListener>& listener, int32_t taskId);
    void removeListener(const sp<gui::IFpsListener>& listener);
};
```

**分层调度机制**：

```cpp
// FpsReporter.cpp:40-56
void FpsReporter::dispatchLayerFps(const frontend::LayerHierarchy& layerHierarchy) {
    const auto now = mClock->now();
    if (now - mLastDispatch < kMinDispatchDuration) {
        return;  // 节流：两次调度间至少间隔 kMinDispatchDuration
    }

    std::vector<TrackedListener> localListeners;
    {
        std::scoped_lock lock(mMutex);
        if (mListeners.empty()) {
            return;
        }
        std::transform(mListeners.begin(), mListeners.end(),
                       std::back_inserter(localListeners),
                       [](const auto& entry) { return entry.second; });
    }
    // ... dispatch to listeners
}
```

**设计要点**：
- **按 taskId 而非 Layer 分组**：FPSReporter 以 Task（窗口/活动）为粒度聚合 FPS，而非按单个 Surface Layer，避免多 Layer 窗口的数据碎片化
- **DeathRecipient 机制**：监听器进程死亡时自动清理，防止悬挂引用
- **调度节流**（`kMinDispatchDuration`）：避免高频 FPS 回调淹没消费端，默认间隔约 500ms
- **读写分离**：先在锁内拷贝 listener 列表，再在锁外执行回调，避免持锁阻塞 SurfaceFlinger 主线程

### 🔹 JankTracker 异步卡顿检测系统

JankTracker 是 Android 12+ 引入的卡顿检测系统，在 Android 17 中进一步完善。它采用**批量异步处理**架构，将卡顿检测开销从渲染关键路径上移除。

**架构设计**（`android-17.0.0_r1`）：

```cpp
// frameworks/native/services/surfaceflinger/Jank/JankTracker.h:25-38
class JankTracker {
public:
    static void addJankListener(int32_t layerId, sp<IBinder> listener);
    static void flushJankData(int32_t layerId);
    static void removeJankListener(int32_t layerId, sp<IBinder> listener, int64_t afterVsync);
    static void onJankData(int32_t layerId, gui::JankData data);

private:
    static constexpr size_t kJankDataBatchSize = 50;
    static std::atomic<size_t> sListenerCount;
    static std::atomic<bool> sCollectAllJankDataForTesting;
};
```

**异步批处理流程**：

```cpp
// JankTracker.cpp:30-40
void JankTracker::addJankListener(int32_t layerId, sp<IBinder> listener) {
    sListenerCount++;

    BackgroundExecutor::getLowPriorityInstance().sendCallbacks(
            {[layerId, listener = std::move(listener)]() {
                JankTracker& tracker = getInstance();
                const std::lock_guard<std::mutex> _l(tracker.mLock);
                tracker.addJankListenerLocked(layerId, listener);
            }});
}
```

**关键设计决策**：
- **低优先级后台线程**：所有 listener 注册/注销操作通过 `BackgroundExecutor::getLowPriorityInstance()` 在低优先级线程执行，不阻塞合成主线程
- **批量大小 50**（`kJankDataBatchSize`）：卡顿数据按 50 条一批累积后统一 flush，平衡了延迟与开销
- **原子计数器追踪状态**：`sListenerCount` 使用 atomic 确保线程安全，允许快速判断是否有活跃监听器
- **按 LayerId 隔离**：每个 Surface Layer 维护独立的卡顿数据队列，支持细粒度的问题定位

### 🔹 FrameTracer Perfetto 集成

FrameTracer 是 SurfaceFlinger 与 Perfetto 追踪系统的直接集成点。它通过 Perfetto 的 DataSource 机制实现跨进程帧追踪。

**Perfetto DataSource 架构**（`android-17.0.0_r1`）：

```cpp
// frameworks/native/services/surfaceflinger/FrameTracer/FrameTracer.h:27-41
class FrameTracer {
public:
    class FrameTracerDataSource : public perfetto::DataSource<FrameTracerDataSource> {
        virtual void OnSetup(const SetupArgs&) override {};
        virtual void OnStart(const StartArgs&) override {};
        virtual void OnStop(const StopArgs&) override {};
    };

    void initialize();
    void registerDataSource();
    void traceNewLayer(int32_t layerId, const std::string& layerName);
};
```

**一次性初始化**：

```cpp
// FrameTracer.cpp:15-26
void FrameTracer::initialize() {
    std::call_once(mInitializationFlag, [this]() {
        perfetto::TracingInitArgs args;
        args.backends = perfetto::kSystemBackend;
        perfetto::Tracing::Initialize(args);
        registerDataSource();
    });
}
```

**设计要点**：
- **`std::call_once` 保证**：FrameTracer 初始化只执行一次，即使多个线程同时调用 `initialize()` 也安全
- **仅系统后端**：`kSystemBackend` 意味着仅响应系统级 Perfetto 追踪会话，应用进程无法直接触发
- **DataSource 空壳设计**：`OnSetup/OnStart/OnStop` 均为空实现——FrameTracer 不依赖 Perfetto 的生命周期回调，而是主动通过 `traceLayerCreation()` / `traceEndFrame()` 等方法写入追踪事件
- **层名称映射**：`traceNewLayer` 将 Layer ID 与人类可读名称关联，使得 Perfetto UI 中可以直接看到窗口名称而非数字 ID

与 §13.22 中讨论的 Perfetto Trace Processor 架构互补：FrameTracer 是**数据生产端**，Trace Processor 是**数据消费端**。

### 🔹 TimeStats 帧时间直方图统计

TimeStats 提供 SurfaceFlinger 层面的帧时间统计，包括帧渲染时间分布直方图，可通过 `dumpsys SurfaceFlinger` 或 stats pull 服务获取。

**帧时间直方图生成**（`android-17.0.0_r1`）：

```cpp
// frameworks/native/services/surfaceflinger/TimeStats/TimeStats.cpp:36-50
FrameTimingHistogram histogramToProto(
        const std::unordered_map<int32_t, int32_t>& histogram,
        size_t maxPulledHistogramBuckets) {
    auto buckets = std::vector<std::pair<int32_t, int32_t>>(histogram.begin(),
                                                             histogram.end());
    std::sort(buckets.begin(), buckets.end(),
              [](const auto& left, const auto& right) {
                  return left.second > right.second;  // 按出现频次降序
              });

    FrameTimingHistogram histogramProto;
    int histogramSize = 0;
    for (const auto& bucket : buckets) {
        if (histogramSize >= maxPulledHistogramBuckets) break;
        histogramProto.add_bucket(bucket.first);   // 帧时间 (ms)
        histogramProto.add_count(bucket.second);    // 出现次数
        histogramSize++;
    }
    return histogramProto;
}
```

**设计要点**：
- **频次排序**：直方图按出现频次降序排列（非按时间排序），使最常见帧时间一眼可见
- **桶数上限**：`maxPulledHistogramBuckets` 限制 protobuf 消息大小，避免 statsd 拉取时内存暴涨
- **两字段编码**：每个桶用 `bucket`（帧时间 ms）和 `count`（出现次数）两个字段表示，紧凑高效

**获取方式**：
```bash
# 通过 dumpsys 获取
adb shell dumpsys SurfaceFlinger --timestats

# 通过 statsd 拉取（原子指标）
adb shell cmd stats pull_atom 51017  # SurfaceFlingerTimeStats atom
```

### 🔹 GPU 资源使用转换：gralloc usage 系统

SurfaceFlinger 与 GPU 驱动之间的资源描述通过 gralloc usage 标志传递。Android 17 的 `libgrallocusage` 提供了从旧版 Gralloc 0 到 Gralloc 1 的使用标志转换。

**转换机制**（`android-17.0.0_r1`）：

```cpp
// system/core/libgrallocusage/GrallocUsageConversion.cpp:11-30
void android_convertGralloc0To1Usage(int32_t usage,
                                     uint64_t* producerUsage,
                                     uint64_t* consumerUsage) {
    constexpr uint64_t PRODUCER_MASK =
        GRALLOC1_PRODUCER_USAGE_CPU_READ |
        GRALLOC1_PRODUCER_USAGE_CPU_WRITE |
        GRALLOC1_PRODUCER_USAGE_GPU_RENDER_TARGET |
        GRALLOC1_PRODUCER_USAGE_PROTECTED |
        GRALLOC1_PRODUCER_USAGE_CAMERA |
        GRALLOC1_PRODUCER_USAGE_VIDEO_DECODER |
        GRALLOC1_PRODUCER_USAGE_SENSOR_DIRECT_DATA;

    constexpr uint64_t CONSUMER_MASK =
        GRALLOC1_CONSUMER_USAGE_CPU_READ |
        GRALLOC1_CONSUMER_USAGE_GPU_TEXTURE |
        GRALLOC1_CONSUMER_USAGE_HWCOMPOSER |
        GRALLOC1_CONSUMER_USAGE_CLIENT_TARGET |
        GRALLOC1_CONSUMER_USAGE_CURSOR |
        GRALLOC1_CONSUMER_USAGE_VIDEO_ENCODER |
        GRALLOC1_CONSUMER_USAGE_CAMERA |
        GRALLOC1_CONSUMER_USAGE_RENDERSCRIPT |
        GRALLOC1_CONSUMER_USAGE_GPU_DATA_BUFFER;
}
```

**设计要点**：
- **生产者/消费者分离**：Gralloc 1.x 将使用标志分为 producer（写入端：GPU 渲染目标、相机、视频解码器）和 consumer（读取端：GPU 纹理、HWC、视频编码器），比 Gralloc 0 的统一标志更精确
- **位掩码转换**：使用 constexpr 位掩码进行高效转换，运行时零开销
- **调试相关性**：理解 gralloc usage 转换对于诊断 GPU 内存共享问题（如 SurfaceTexture 延迟、BufferQueue 拥塞）至关重要

### 🔹 四子系统性能开销分析

| 子系统 | CPU 开销 | 内存开销 | 触发频率 | 适用场景 |
|--------|---------|---------|---------|---------|
| **FPSReporter** | 低（500ms 调度间隔） | 监听器列表 + 层级遍历栈 | 每秒 ≤2 次 | 系统级 FPS 监控、WindowManager 调度 |
| **JankTracker** | 极低（后台低优先级线程） | 50 条批量队列 × N layers | 每帧收集、批量 flush | 应用卡顿诊断、Janky frames 统计 |
| **FrameTracer** | 低（Perfetto DataSource 空壳） | 层名称映射表 | 仅追踪会话激活时 | Perfetto 跨进程帧追踪 |
| **TimeStats** | 中（直方图排序 + protobuf 编码） | 帧时间直方图哈希表 | 每次 stats pull 或 dumpsys | 长期帧时间分布分析 |

**整体设计原则**：
1. **异步优先**：所有子系统使用后台线程或延迟处理，不在 SurfaceFlinger 主合成线程上执行重计算
2. **节流机制**：通过调度间隔（FPSReporter）或批量大小（JankTracker）控制回调频率
3. **零开销关闭**：FrameTracer 的 DataSource 空壳设计确保无追踪会话时几乎零开销
4. **可组合**：四子系统可独立启用/禁用，也可同时工作而不互相干扰
