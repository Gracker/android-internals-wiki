# 4.19 Android 17 MemoryLimiter 内存限制器与 ProcState 机制

<!-- outline-start -->
## 要点

### 🔹 MemoryLimiter 基本架构
Android 17 MemoryLimiter 是 Android 平台引入的内存管理系统，旨在通过 cgroup v2 的 `memory.high` 软限制机制实现后台应用的精细化管理。该系统在 Android 16 中作为可选项引入（默认关闭），在 Android 17 中成为默认启用的核心内存防线。

MemoryLimiter 的核心设计理念是**内存软限制**而非传统的硬限制（OOM kill）。它通过以下五个核心组件协同工作：

1. **Java 层控制器**：负责进程状态监控、限制matrix配置和事件分发
2. **JNI 层监控**：实现内存状态的实时监控和状态机管理
3. **内核层 memcg v2**：提供 `memory.high` 的 throttle + reclaim 语义
4. **statsd 事件系统**：实现内存超限事件的频控上报
5. **AnonSwapState 状态机**：管理进程在内存压力下的四种状态转换

**关键优势**：相比传统的 lmkd（Low Memory Killer Daemon），MemoryLimiter 能够更精准地控制后台内存使用，减少不必要的进程杀掉，提升系统整体性能和用户体验。

### 🔹 ProcState 限制matrix机制
MemoryLimiter 通过完整的 23 个 ProcState→Limits 映射matrix实现不同进程状态下的差异化内存管理。该matrix在 systemReady 阶段通过 `ControllerEnabled.initializeMemoryLimits()` 初始化，是限制生效的"静态配置表"。

**限制matrix分类表**：

| ProcState 分类 | memHigh | swapHigh | 监控关注点 | 业务影响 |
|---|---|---|---|---|
| `PROCESS_STATE_PERSISTENT` / `PROCESS_STATE_PERSISTENT_UI` | `LIMIT_IS_DISABLED`（"max"） | `LIMIT_IS_DISABLED` | 永不触发 | 系统服务/系统 UI 不受限 |
| `PROCESS_STATE_TOP` / `PROCESS_STATE_BOUND_TOP` / `PROCESS_STATE_IMPORTANT_FOREGROUND` / `PROCESS_STATE_TOP_SLEEPING` | `memVisible`（默认 4 GB） | `swapVisible`（默认 2 GB） | 配额宽松 | 前台可见应用几乎不会触发 |
| `PROCESS_STATE_IMPORTANT_BACKGROUND` / `PROCESS_STATE_TRANSIENT_BACKGROUND` / `PROCESS_STATE_BACKUP` / `PROCESS_STATE_SERVICE` / `PROCESS_STATE_RECEIVER` / `PROCESS_STATE_FOREGROUND_SERVICE` / `PROCESS_STATE_BOUND_FOREGROUND_SERVICE` / `PROCESS_STATE_HEAVY_WEIGHT` / `PROCESS_STATE_HOME` / `PROCESS_STATE_LAST_ACTIVITY` | `memNotVisible`（默认 2 GB） | `swapNotVisible`（默认 2 GB） | **主要受影响群体** | 后台 Service/FGS 监控必须在此处降级 |
| `PROCESS_STATE_CACHED_ACTIVITY` / `PROCESS_STATE_CACHED_ACTIVITY_CLIENT` / `PROCESS_STATE_CACHED_RECENT` / `PROCESS_STATE_CACHED_EMPTY` | `LIMIT_IS_IGNORED`（不写入） | `LIMIT_IS_DISABLED`（"max"） | 不受 MemoryLimiter 控制 | 完全交给 lmkd / CachedAppOptimizer |
| `PROCESS_STATE_UNKNOWN` / `PROCESS_STATE_NONEXISTENT` | `LIMIT_IS_IGNORED` | `LIMIT_IS_IGNORED` | 监控无意义 | 不会被 setLimit 调用 |

**关键调用链**：
```
Activity.setProcessState() → ProcessRecord.setProcState() → 
mMemoryLimiter.onProcStateUpdated(newState) → 
Controller.getStateLimit(newState) → mStateLimit[] 数组查询 → 
setLimit(pid, uid, limit) → Handler MESSAGE_CONFIG → JNI setLimit()
```

**对监控的实操意义**：APM SDK 在标记 `ProcessLifecycleOwner` 阶段时，**必须主动记录 proc state 变化事件**并与 PSS 数据关联。后台 Service 在 2 GB memNotVisible 配额下，1.5 GB 触顶即可触发 `memory.high`，PSS 抖动 30+ 秒——这段抖动期是 APM 上报的"高噪声时段"。

### 🔹 inotify→polling 回退机制
MemoryLimiter 监控机制的核心是 **inotify 与 polling 的智能切换**，通过 red zone 概念实现不同压力级别下的最优监控策略。

**三档轮询周期常量**（JNI 层定义）：
```cpp
// com_android_server_am_MemoryLimiter.cpp:43-52
const int PID_POLL_PERIOD_MS = 5 * 60 * 1000;    // 常态 5 分钟轮询
const int RED_POLL_PERIOD_MS = 30 * 1000;         // red zone 30 秒轮询
const int TEST_POLL_PERIOD_MS = 1000;             // 测试模式 1 秒轮询
```

**双模式切换触发条件**：
```cpp
bool isRed() const {
    return mMemWatcher.mTriggered && !mAnonSwapTriggered;
}
```
当 `memory.high` 触发但 `memory.swap.high` 还没触发时进入 red zone，inotify 监听失效，必须切换到 30s 轮询。

**轮询的判定逻辑**：
```cpp
AnonSwapState testAnonSwap() const {
    if (mAnonSwapTriggered) return AnonSwapState::kTriggered;
    int64_t metric = getMetric(MonitoredLimit::kAnonSwap);
    if (mAnonSwapLimit < 0) {
        return AnonSwapState::kOkay;             // 限制未配置
    } else if (metric > mAnonSwapLimit) {
        return AnonSwapState::kHot;              // 超限 → red zone
    } else if (metric < (mMemoryHighLimit - mMemHighHysteresis)) {
        return AnonSwapState::kCold;             // 低于 (memHigh-10MB) → 回到 inotify
    } else {
        return AnonSwapState::kOkay;             // 中间地带，需轮询
    }
}
```

**滞回带机制**：`mMemHighHysteresis = 10 * (1024 * 1024)`（10MB滞回带）避免边界值反复触发内存回收事件，防止"惊群"效应。

**对监控的影响**：30s 轮询窗口期内，PSS 数据会因为内核主动 reclaim anon 而出现**锯齿状抖动**——单次轮询周期可能同时包含"内存回收"和"内存重新分配"两个事件。

[已验证: AOSP android-17.0.0_r1, com_android_server_am_MemoryLimiter.cpp:506-528]

### 🔹 AnonSwapState 四态机
Native 端定义了 `AnonSwapState` 四态枚举，对应进程在 cgroup 内存视图中的状态，实现精细化的内存状态管理。

**四态机定义表**：

| 状态 | 判定条件 | 监听方式 | 业务影响 |
|---|---|---|---|
| `kCold` | `(anon + shmem) < (memHigh - 10MB)` | inotify 零开销 | 监控数据稳定 |
| `kOkay` | `(memHigh - 10MB) ≤ metric ≤ anonSwapLimit` | 30s 轮询 | PSS 数据有噪声但不影响进程 |
| `kHot` | `metric > anonSwapLimit` 但 `!mAnonSwapTriggered` | 30s 轮询 | 内核 throttle，进程被节流，PSS 锯齿抖动 |
| `kTriggered` | `mAnonSwapTriggered = true`（已发生过 ANON_SWAP） | 限制已释放，倒计时 kill | 进程进入 30s 死亡窗口 |

**状态转换逻辑**：
- `kCold → kOkay`：进程内存增长到 `(memHigh - 10MB)` 以上
- `kOkay → kHot`：内存超过 anonSwapLimit 但 swap.high 未触发
- `kHot → kTriggered`：swap.high 触发，Memitmiter 开始 30s 倒计时
- `kTriggered → kCold`：进程被 kill 后重新启动，内存重置

**状态持久化**：AnonSwapState 状态通过 `mAnonSwapTriggered` 标志位持久化，确保进程状态在系统重启后能正确恢复。

**对监控的实操建议**：监控 SDK 应在本地维护一个 30s 滑动窗口的 PSS 变化率指标，当变化率 > 5 MB/s 持续超过 10s 时标记为"MemoryLimiter 抖动期"，这段时间的 PSS 数据应降级为"低置信度"。

### 🔹 memcg v2 内存契约机制
Android 17 MemoryLimiter 依赖于内核 memcg v2 的 `memory.high` 软限制机制，这是 MemoryLimiter 能够实现精细内存管理的技术基础。

**`memory.high` 与 `memory.max` 的关键区别**：
- `memory.high`：软限制（throttle），永不触发 OOM
- `memory.max`：硬限制（OOM kill），达到阈值直接杀死进程

**`memory.high` 的官方语义**（kernel.org Documentation）：
> Memory usage throttle limit. If a cgroup's usage goes over the high boundary, the processes of the cgroup are throttled and put under heavy reclaim pressure.
> 
> **Going over the high limit never invokes the OOM killer** and is handled gracefully by the kernel.

**MemoryLimiter 的具体实现**：
```cpp
// android-17.0.0_r1 中没有设置 O_NONBLOCK
android::base::WriteStringToFile(path, value, 0666);  // 触发同步 reclaim
```

**内存回收策略**：
- **同步 reclaim**：每次写入新限制值时触发，给被 throttle 的进程留出 100MB 的 anon 余量
- **异步 reclaim**：内核在后台主动回收匿名内存
- **ZRAM 特殊处理**：`memory.swap.high` 触发时，ZRAM 压缩比已达上限，内核开始 throttle swap in/out 操作

**内存契约关系**：
```
MemoryLimiter ←→ kernel memcg v2
   ↓              ↓
设定 memory.high ←→ 执行 throttle + reclaim
   ↓              ↓
观察 memory.events ←→ 控制进程行为
```

**`O_NONBLOCK` 的使用场景**：如果 MemoryLimiter 设置 `O_NONBLOCK`，writeLimit 立即返回，但内核不强制 reclaim，进程 anon 继续增长——这对 MemoryLimiter 没用，因为它需要立刻观察 `memory.events.high` 的变化。

[已验证: kernel.org Documentation/admin-guide/cgroup-v2.rst, "memory.high" 章节]

### 🔹 statsd 令牌桶限流
MemoryLimiter 通过 statsd 实现内存超限事件的频控上报，避免系统被过多内存事件淹没。该机制采用严格的令牌桶算法进行限流。

**令牌桶常量配置**：
```java
// MemoryLimiter.java: 常量定义
static final int MAX_TOKENS = 4;                          // 上限 4 个 token
static final long TOKEN_PERIOD_MS = Duration.ofHours(1).toMillis();  // 每小时补 1 个
static final long KILL_DELAY_MS = 30 * 1000;             // 30s 后 kill
```

**令牌桶算法实现**：
```java
final boolean shouldLogAtom(long now) {
    synchronized (mBucketLock) {
        // 计算当前可用 token 数
        now = (now / TOKEN_PERIOD_MS) * TOKEN_PERIOD_MS;   // 对齐到整小时
        long accumulated = (now - mLastBucketUpdate) / TOKEN_PERIOD_MS;
        mLastBucketUpdate = now;
        accumulated = Math.max(0, accumulated);
        mAvailableTokens += accumulated;
        mAvailableTokens = Math.min(mAvailableTokens, MAX_TOKENS);
        if (mAvailableTokens > 0) {
            mAvailableTokens--;
            return true;
        } else {
            return false;
        }
    }
}
```

**限流效果计算**：
- 每小时补 1 个 token，上限 4 个 token
- 满桶状态时每小时最多 4 条 statsd event
- 24 小时内最多 4 × 24 = 96 条，但实际稳态下每天约 24-28 条

**对监控的硬性约束**：APM SDK **不能依赖 statsd 通路做高频告警**。即使被 MemoryLimiter 触发 100 次，statsd 也只会记录 4-28 条。**必须在 Java 层自行 hook** `MemoryLimiter$ControllerEnabled.onLimitExceeded()` 才能获取完整事件流。

**事件上报时机**：
```java
// 仅在 shouldLogAtom() 返回 true 时上报
if (shouldLogAtom(now)) {
    FrameworkStatsLog.write(MEMORY_LIMITER_OVER_LIMIT_EVENT, ...);
}
```

### 🔹 实际应用与配置
MemoryLimiter 的实际应用涉及开发者配置接口、参数调优和监控方法，需要深入理解其工作原理才能正确配置和使用。

**开发者配置接口**：
- `ActivityManager.getMemoryClass()`：获取标准内存类别
- `ActivityManager.getLargeMemoryClass()`：获取大内存类别
- `ApplicationInfo.memoryClass`：在 AndroidManifest.xml 中配置

**参数调优策略**：
1. **内存敏感应用**：降低 `memNotVisible` 配额（如从 2GB 调整到 1.5GB）
2. **内存密集型应用**：适当增加 `memVisible` 配额，避免频繁 throttle
3. **后台服务**：重点关注 `PROCESS_STATE_SERVICE` 和 `PROCESS_STATE_FOREGROUND_SERVICE` 的限制

**监控调试方法**：
1. **实时监控**：`adb shell dumpsys meminfo <pid>` 查看 PSS 和 swap 使用情况
2. **事件追踪**：`adb shell logcat | grep MemoryLimiter` 监控内存事件
3. **状态检查**：`adb shell cat /sys/fs/cgroup/memory/<pid>/memory.high` 查看当前限制
4. **性能分析**：使用 Perfetto 监控内存回收事件

**最佳实践**：
- **避免内存泄漏**：严格控制后台内存使用，接近限制时主动释放
- **优化内存访问模式**：减少匿名内存分配，增加共享内存使用
- **合理设置缓冲区**：根据 ProcState 配置不同大小的内存缓冲区
- **监控 PSS 抖动**：识别 MemoryLimiter 引起的锯齿状内存变化

**常见问题排查**：
1. **应用被意外杀死**：检查是否达到 `memNotVisible` 限制
2. **性能下降**：监控是否进入 red zone 30s 轮询期
3. **内存事件丢失**：确认是否被 statsd 令牌桶限流
4. **监控数据异常**：检查是否在 PSS 抖动期采集数据

## 1. MemoryLimiter 是条件启用的 system_server 机制

Android 17 的 [`MemoryLimiter.java`](https://android.googlesource.com/platform/frameworks/base/+/refs/tags/android-17.0.0_r1/services/core/java/com/android/server/am/MemoryLimiter.java) 位于 AMS 进程内。它根据应用进程的 proc state 选择一组限制，再由 [`com_android_server_am_MemoryLimiter.cpp`](https://android.googlesource.com/platform/frameworks/base/+/refs/tags/android-17.0.0_r1/services/core/jni/com_android_server_am_MemoryLimiter.cpp) 写入进程 cgroup v2 节点、监听事件并执行后续检查。

默认 controller 进入 enabled 状态需要同时满足：

1. `Flags.memoryLimiterEnable()` 为真；
2. 当前进程使用 system UID；
3. `/vendor/etc/memory-limiter-config.xml` 存在；
4. XML 中至少一组 `minimumRequiredMemTotal` 不大于本机 `MemTotal`。

缺少配置或没有匹配项时，系统使用无操作的 `ControllerDisabled`。所以源码中存在这个类，不能推导出每台 Android 17 设备都启用了限制。

enabled controller 还受三类开关影响：

| 开关 | 作用 |
|---|---|
| `memoryLimiterTrigger()` | 是否建立 Native inotify/epoll 监控线程 |
| `memoryLimiterSwap()` | 是否配置 swap 上限 |
| `memory_limiter_disable_limits` | 让后续 proc-state 更新返回 unlimited 限制 |
| `memory_limiter_disable_kill` | 保留检测与记录，跳过延迟 kill |

运行时关闭 limits 不会立即遍历所有进程。受控进程要等下一次 proc-state 更新，才会收到 `max/max`。

## 2. 配额来自 vendor XML

[`memory-limiter-config.xsd`](https://android.googlesource.com/platform/frameworks/base/+/refs/tags/android-17.0.0_r1/services/core/xsd/memory-limiter-config/memory-limiter-config.xsd) 定义了：

- `minimumRequiredMemTotal`；
- `memVisible`；
- `memNotVisible`；
- `swapVisible`；
- `swapNotVisible`。

XML 中的容量单位是 MiB。`getConfiguration()` 在所有满足 `minimumRequiredMemTotal <= MemTotal` 的条目中，选择门槛最高的一组，再换算成字节。

Java 源码里的 4 GiB / 2 GiB / 2 GiB / 2 GiB `sDefaultConfig` 带有 `@VisibleForTesting`，注释明确提示生产环境需要重新评审。这组数值不是 Android 17 的平台默认配置，也不能用来推导“后台进程达到 1.5 GiB 就会触发”的通用结论。

`ActivityManager.getMemoryClass()`、`getLargeMemoryClass()` 和 manifest `largeHeap` 管理的是应用受管堆等级。它们不能修改 MemoryLimiter vendor 配额。

## 3. ProcState 映射的准确语义

`initializeMemoryLimits()` 将状态归为五组：

| 组别 | proc state | `memory.high` 参数 | swap 参数 |
|---|---|---|---|
| ignored | `UNKNOWN`、`NONEXISTENT` | 不写 | 不写 |
| unlimited | `PERSISTENT`、`PERSISTENT_UI` | `max` | `max` |
| visible | `TOP`、`BOUND_TOP`、`IMPORTANT_FOREGROUND`、`TOP_SLEEPING` | `memVisible` | `swapVisible` |
| not-visible | `FOREGROUND_SERVICE`、`BOUND_FOREGROUND_SERVICE`、`IMPORTANT_BACKGROUND`、`TRANSIENT_BACKGROUND`、`BACKUP`、`SERVICE`、`RECEIVER`、`HEAVY_WEIGHT`、`HOME`、`LAST_ACTIVITY` | `memNotVisible` | `swapNotVisible` |
| cached | 四个 `CACHED_*` 状态 | 不改当前值 | `max` |

Native 识别两个特殊值：

- `LIMIT_IS_DISABLED = -1`：向 cgroup 文件写 `max`；
- `LIMIT_IS_IGNORED = -2`：跳过本次写入。

cached 组对 `memory.high` 使用 ignored，对 swap 使用 disabled。进程由 not-visible 转为 cached 后，旧的 `memory.high` 可能继续留在 cgroup 文件中，swap 上限则被取消。只看当前 proc state，不能推断两个节点都已经恢复为 `max`。

前台服务处于 not-visible 配额组。这里的 visible 是 MemoryLimiter 自身的分类名，不能直接等同于应用生命周期库的 `STARTED`/`RESUMED` 状态。

## 4. Android 17 写入 `memory.high` 和 `memory.swap.max`

Java 字段名使用 `swapHigh`，一些注释也提到 `memory.swap.high`。执行代码中的 `CgroupFile` 映射却很明确：

```text
kMemoryStat   -> memory.stat
kMemoryEvent  -> memory.events
kMemoryHigh   -> memory.high
kSwapCurrent  -> memory.swap.current
kSwapMax      -> memory.swap.max
```

这段映射说明 Android 17 实现写入的是 `memory.swap.max`。源码命名和注释不能覆盖 Native 端打开的文件。

指定内核 tag 的 [`cgroup-v2.rst`](https://android.googlesource.com/kernel/common/+/refs/tags/android17-6.18-2026-06_r6/Documentation/admin-guide/cgroup-v2.rst) 对两个节点给出不同语义：

- `memory.high` 是回收压力与节流边界。越界本身不会调用 memcg OOM killer，使用量在极端情况下仍可暂时超过它；
- `memory.swap.max` 是 cgroup 的 swap 使用硬上限。到达上限后，该 cgroup 的匿名页不能继续换出。

Native 使用普通 `WriteStringToFile()` 写入限制，没有以 `O_NONBLOCK` 打开 `memory.high`。下调 `memory.high` 时，内核触发的回收可能同步占用 MemoryLimiter 的后台 Handler/Native 调用路径；AMS 锁内的进程状态更新者已经通过消息队列与这项文件写入分离。

## 5. 事件监听与 red-zone 轮询

### 正常阶段只监听 `memory.events`

Native 通过 `CgroupGetAttributePathForProcess("MemEvents", uid, pid, ...)` 找到进程 cgroup，再对 `memory.events` 添加 `IN_MODIFY` watch。开始监听时记录 `high` 计数基线。收到文件修改通知后还要重读计数；只有 `high` 发生变化才算 MemoryLimiter 需要处理的事件。

Android 17 没有为 `memory.swap.events` 建立第二个 watch。`LIMIT_TYPE_SWAP` 和 `kSwapMax` 虽然保留在枚举中，现行 `watch()`、`getLimitType()` 与 `getEventCount()` 不会生成独立 swap 回调。

### `memory.high` 事件后进入 red zone

确认 `high` 增长后，Native 会：

1. 移除该进程的 `memory.events` watch；
2. 置位 `mMemWatcher.mTriggered`；
3. 把 `memory.high` 重新写成原配额加 100 MiB；
4. 回调 Java 的 `LIMIT_TYPE_MEMORY`；
5. 将监控线程切换到 red-zone 轮询。

100 MiB margin 只改变写入 cgroup 的 `memory.high`，Java 保存的原始 `memHigh` 与联合阈值不变。它让进程在高回收压力下保留一定运行空间，不代表系统向应用承诺了固定的额外可用内存。

### 轮询检查匿名内存、shmem 与 swap

监控线程只有一个 `epoll_wait()` 循环：

- 没有 red-zone 进程时，生产环境超时是 5 分钟，用于清理退出 PID；
- 有 red-zone 进程时，超时缩短为 30 秒；
- 测试模式与启动后的初始超时是 1 秒。

每轮 red-zone 检查计算：

```text
metric = memory.stat:anon
       + memory.stat:shmem
       + memory.swap.current

limit  = configured memHigh
       + configured swapMax
```

这段公式中的 `memHigh` 使用原始配置，不包含 100 MiB margin。它也不等于单个 PID 的 PSS；指标属于进程 cgroup，可能覆盖该 cgroup 的后代。

## 6. `AnonSwapState` 是轮询结果，不是持久状态机

`testAnonSwap()` 的四个返回值如下：

| 返回值 | 判断 | 动作 |
|---|---|---|
| `kCold` | metric 小于 `memHigh - 10 MiB` | 重新安装 `memory.events` watch |
| `kOkay` | 尚未超过联合阈值，也没有降到恢复边界 | 保持轮询 |
| `kHot` | metric 大于联合阈值 | 生成 `LIMIT_TYPE_ANON_SWAP` |
| `kTriggered` | 联合事件已经置位 | 避免重复触发 |

这些值不要求按固定次序迁移。一个进程在第一次 30 秒检查时就可能返回 `kHot`；返回 `kCold` 时也可以在进程仍存活的情况下恢复 inotify。

10 MiB 是从轮询返回事件监听的滞回量。它没有直接触发内核回收，也不能证明 30 秒采样窗口内一定出现锯齿形 PSS。要把 PSS 变化归因给 MemoryLimiter，还需同时看到 proc-state 更新、cgroup 值和 `memory.events:high`。

`mAnonSwapTriggered` 是 Native `Process` 对象中的内存字段。它不跨进程重启或系统重启持久化。

## 7. 联合越界后的处理顺序

Native 发现 `kHot` 后回调 `LIMIT_TYPE_ANON_SWAP`。Java 侧依次执行：

1. 记录日志，并在令牌桶允许时写 statsd atom；
2. 向 `memory.high` 与 `memory.swap.max` 写 `max`，解除该进程限制；
3. 在两个 profiling flag 都打开且包名可解析时，请求系统触发式 profiling；
4. 向 BackgroundThread 投递延迟 30 秒的 kill 消息；
5. 到期后若 kill 未被 DeviceConfig 关闭，通过 AMS `killPids()` 终止目标 PID。

30 秒的源码注释指向 profiler 完成时间。MemoryLimiter 没有向目标应用派发专属 `onTrimMemory()`，也没有在内存下降后自动取消已经排队的 kill。

单次 `memory.high` 事件只会进入 red-zone 检查，不会直接安排 kill。只有匿名内存、shmem 与 swap 的联合指标超过阈值，才会进入上述终止路径。

## 8. statsd 令牌桶怎样计算

桶容量是 4，每经过一小时补 1 个 token，最多恢复到 4。每次成功写 atom 消耗 1 个 token。

“4”表示空闲一段时间后可连续写四条，不表示每小时固定允许四条。空桶后的持续速率是每小时一条；源码注释把上限概括为每天 28 条，而非 96 条。

限流只影响 `MEMORY_LIMITER_OVER_LIMIT_EVENT` atom。日志、解除限制、profiling 与 kill 仍会继续。

普通应用不应反射 hook `MemoryLimiter$ControllerEnabled`。它是 system_server 的隐藏实现，受进程隔离、hidden API 和 SELinux/权限边界约束，也没有稳定兼容承诺。

## 9. 应用怎样识别和处理

普通应用没有公开的 MemoryLimiter 越界回调，也通常无权读取目标进程的 memcg 文件。应用侧可以：

- 分开记录 PSS、RSS、SwapPss/VmSwap，不混成一个不明口径的总数；
- 记录 UI 可见性、Service/FGS 状态、GC、大分配和关键业务阶段；
- 下次启动时查询 `ApplicationExitInfo`；
- 保存 reason、subreason、timestamp、importance、status 与 description 原文；
- 在服务端按设备 build 和平台版本做归因。

MemoryLimiter 的 kill reason 是 `"MemoryLimiter:AnonSwap"`，AMS 退出记录使用 `REASON_OTHER` 与 `SUBREASON_KILL_PID`。description 是人类可读字段，格式不属于长期稳定协议，不能只依赖一个字符串分支。

减少后台匿名内存和及时释放可重建缓存仍有价值，但“改用共享内存”不是普遍解法。共享内存、DMA-BUF、文件映射和匿名内存具有不同 charge、生命周期与安全成本，必须按数据访问方式选择。

## 10. 平台现场检查

下面的命令用于确认 controller 状态并观察目标进程的公开内存统计：

```bash
adb shell am memory-limiter status
adb shell dumpsys meminfo <package-or-pid>
adb shell logcat -d -b all -s MemoryLimiter ActivityManager lowmemorykiller
```

`am memory-limiter status` 会显示 enabled、monitoring、killing、visible/not-visible 配额与 Native 统计。该命令可用性仍取决于 build 和 shell 权限。

不要把 cgroup 路径写死成 `/sys/fs/cgroup/memory/<pid>/`。Android 17 Native 通过 libprocessgroup 的 `MemEvents` attribute 查找实际位置。平台工程师应先解析目标进程所在 cgroup，再读取：

```text
memory.high
memory.events
memory.stat
memory.swap.current
memory.swap.max
```

连续采样时至少保留三个时间点：

1. proc state 改变及新限制下发；
2. `memory.events:high` 增长；
3. 联合指标越界及 kill 消息排队。

这三个时点可以区分下调 `memory.high` 时的同步回收、high 越界后的持续压力，以及联合超限后的终止。

`am memory-limiter manual` 和 `ignore` 是测试接口。Android 17 shell help 把 manual 参数写成 percentage，执行代码却把整数传入 `setManualLimit()` 并按 MiB 换算。自动化脚本使用前必须按目标 build 核对，不能只照 help 文本执行。

## 11. 与 lmkd 和 CachedAppOptimizer 分开

| 机制 | 主要输入 | 动作 |
|---|---|---|
| MemoryLimiter | 单进程 proc state、vendor 配额、memcg high 与联合指标 | 配置 cgroup、记录、可选 profiling、联合超限后定点 kill |
| lmkd | 系统 PSI、可用内存、swap、进程优先级等 | 在系统压力下选择 victim |
| CachedAppOptimizer | cached 状态、压缩与冻结策略 | 压缩或冻结 cached 进程 |

三套机制可以影响同一个进程，没有固定执行顺序。lmkd 可能在 MemoryLimiter 的 30 秒等待期间先终止进程；cached 状态也可能触发 freezer 或 compaction。PSS 下降和进程消失都要结合日志、cgroup 事件、PSI 与退出记录判断。

## 12. 版本与来源边界

`android-15.0.0_r1` 与 `android-16.0.0_r1` 中没有这组 Java/JNI 文件，`android-17.0.0_r1` 可以找到完整实现。正文不把开发分支的版权年份或 feature flag 名称当成交付版本证据。
