# Android 17 启动观测：ApplicationStartInfo 与 AppStartInfoTracker

## 要点

### 🔹 GPU功耗管理基础
Android 17 引入了全新的 GPU 功耗管理策略，基于 DVFS（动态电压频率调节）机制的深度优化。

### 🔹 DVFS 调优算法
新算法结合了应用负载预测和系统资源监控，实现了更智能的频率和电压调节。

### 🔹 多核心协调机制
跨 GPU 核心的功耗分配协调，根据不同应用场景动态调整核心工作状态。

### 🔹 热量控制与性能平衡
在控制 GPU 发热的同时保持最佳的性能表现，引入了热量感知的调度策略。

支持不同 SoC 厂商的定制化 DVFS 策略，充分发挥硬件性能潜力。

## 1. 它是启动记录，不是任务编排器

`ApplicationStartInfo` 从 Android 15 / API 35 开始提供。Android 17 / API 37 保留这套能力，并在本文以 `android-17.0.0_r1` 重新核对。它记录系统观察到的启动身份、原因、类型、状态与时间点；它不会分析依赖图、排序初始化任务、创建线程或自动并行执行模块。

Android 平台中也没有名为 `StartupInsights` 的公开 Framework 类。几个相近对象的职责如下：

| 对象 | 所在位置 | 作用 |
| --- | --- | --- |
| `ApplicationStartInfo` | 公开 Framework API | 承载一条进程启动记录 |
| `ActivityManager` 配套 API | 应用进程 | 查询历史、注册首帧完成监听、添加开发者时间戳 |
| `AppStartInfoTracker` | system_server | 建立、补全、保存和返回近期启动记录 |
| AndroidX Startup Insights | Macrobenchmark 工具 | 从 Perfetto startup metric 汇总慢启动线索 |
| Jetpack App Startup | AndroidX 库 | 让应用的 `Initializer` 声明依赖 |

若项目需要“启动任务编排”，应在应用架构层显式设计依赖、线程、超时、失败和生命周期。`ApplicationStartInfo` 可以衡量改造前后的启动区间，不能充当执行框架。

## 2. Android 15、16、17 的版本边界

| 能力 | API 35 | API 36 | API 37 |
| --- | --- | --- | --- |
| `ApplicationStartInfo` 与历史查询 | 加入 | 保留 | 保留 |
| 首帧完成监听 | 加入 | 保留 | 保留 |
| 系统时间戳 0–7 | 加入 | 保留 | 保留 |
| 开发者时间戳 key 21–30 | 加入 | 保留 | 保留 |
| `getStartComponent()` | 无 | 加入 | 保留 |

Android 17 不是这套 API 的起始版本。API 37 的 `android.app` 公共 API 差异中没有新增 `ApplicationStartInfo` 成员。分析历史数据时还要注意：官方源码注释指出，Service 拉起的 `START_TIMESTAMP_LAUNCH` 在 Android 16 及更早版本可能不准确。

## 3. 一条记录包含什么

`ApplicationStartInfo` 可提供 PID、real/package/defining UID、process name、启动原因、cold/warm/hot 类型、launch mode、启动组件、force-stop 状态和去除 extras 的启动 `Intent`。字段能否使用取决于 API 版本和记录状态，采集代码要容忍缺失值。

启动类型常量是：

- `START_TYPE_COLD`：本次启动需要创建进程；
- `START_TYPE_WARM`：进程已存在，但 Activity 等界面状态需要重建；
- `START_TYPE_HOT`：进程和可复用界面状态已经存在。

这组枚举名为 `START_TYPE_*`，不是旧稿中的 `TEMPERATURE_*`。它描述系统对本次启动的分类，不足以解释启动为何变慢。

### 3.1 三种记录状态

| 状态 | 含义 | 时间戳保证 |
| --- | --- | --- |
| `STARTUP_STATE_STARTED` | 启动仍在进行 | `LAUNCH` |
| `STARTUP_STATE_ERROR` | 启动失败 | 除已写入节点外，不保证新增节点 |
| `STARTUP_STATE_FIRST_FRAME_DRAWN` | Activity 已到首帧 | 还保证 `BIND_APPLICATION`、`APPLICATION_ONCREATE`、`FIRST_FRAME` |

`FULLY_DRAWN` 不是第四种状态。它是应用调用 `Activity.reportFullyDrawn()` 后才可能出现的可选时间戳。

### 3.2 八个系统时间戳

`getStartupTimestamps()` 返回 key 到单调时钟纳秒值的 Map。Android 17 定义八个系统 key：

| key | 含义 | 解读边界 |
| --- | --- | --- |
| `START_TIMESTAMP_LAUNCH` | 系统记录的本次组件启动起点 | 不一定等于用户点击时间 |
| `START_TIMESTAMP_FORK` | 进程 fork 节点 | 可缺失；不表示进程初始化完成 |
| `START_TIMESTAMP_BIND_APPLICATION` | 系统调用 `bindApplication` 的节点 | 不表示绑定工作完成 |
| `START_TIMESTAMP_APPLICATION_ONCREATE` | 调用 `Application.onCreate()` 的节点 | 不等于 onCreate 已执行完 |
| `START_TIMESTAMP_FIRST_FRAME` | 首帧绘制节点 | 不单独证明画面已经呈现或可交互 |
| `START_TIMESTAMP_FULLY_DRAWN` | 应用调用 `reportFullyDrawn()` | 可缺失，条件由应用定义 |
| `START_TIMESTAMP_INITIAL_RENDERTHREAD_FRAME` | 初始 RenderThread frame | 可缺失 |
| `START_TIMESTAMP_SURFACEFLINGER_COMPOSITION_COMPLETE` | SurfaceFlinger 合成完成 | 可缺失，不等于业务内容已就绪 |

常量编号不表示调用顺序。例如 `APPLICATION_ONCREATE` 的 key 值小于 `BIND_APPLICATION`，运行路径仍是 bind 在前。计算耗时时，应按语义选择起止节点，并先确认两个 key 都存在。

应用可用 `ActivityManager.addStartInfoTimestamp()` 写入 21–30 的开发者 key。传入值必须处于相同的单调时钟域；相同 key 会覆盖旧值，`reportFullyDrawn()` 之后写入会被丢弃。团队还要维护 key 注册表，防止多个 SDK 使用同一编号。

## 4. AppStartInfoTracker 怎样维护记录

`AppStartInfoTracker` 位于 system_server。它按 package/UID 保存 `AppStartInfoContainer`，系统不同路径会逐步写入 launch、fork、bind、首帧和呈现时间点。

Android 17 源码中的存储行为包括：

- 历史查询返回环形记录中的近期结果，可能包含仍在进行的启动；
- 普通持久化任务使用 30 分钟间隔；
- 持久化历史按 14 天时间窗清理；
- 历史条数由资源配置决定，不应在应用侧写死；
- isolated process 不按 isolated UID 保存；
- 首帧状态触发 completion callback，错误状态不会走这条完成回调。

`addApplicationStartInfoCompletionListener()` 的“complete”指首帧已绘制。它不会等待 `reportFullyDrawn()`，回调至多触发一次并自动移除。需要 fully drawn 数据时，应在应用上报后再次调用历史查询。

只由 Service、Broadcast 或 ContentProvider 拉起且没有 Activity 首帧的进程，可能等不到首帧完成监听。监控 SDK 应同时使用历史查询处理进行中、错误和非 Activity 记录，不能把“监听未回调”直接记为启动失败。

## 5. 时间区间怎样用于排查

以下区间适合缩小调查范围：

- `LAUNCH → FIRST_FRAME`：系统启动起点到首帧；
- `FORK → BIND_APPLICATION`：进程创建后到系统发起应用绑定；
- `BIND_APPLICATION → APPLICATION_ONCREATE`：应用绑定入口到 Application onCreate 调用；
- `APPLICATION_ONCREATE → FIRST_FRAME`：应用初始化与首帧准备区间；
- `LAUNCH → FULLY_DRAWN`：应用定义的内容就绪区间。

长区间只能指向调查范围。`APPLICATION_ONCREATE → FIRST_FRAME` 增长可能来自 Provider、类加载、同步 I/O、Binder、锁、GC、布局、Compose 首次组合或调度延迟。需要 Perfetto、应用阶段事件、调用栈和相同场景对照才能确定原因。

`ApplicationStartInfo` 本身不采集 PSI、CPU、PSS、I/O 或方法调用。旧稿把 `startPsiMonitoringAfterBoot()` 写进同一机制，混合了 system_server 的其他监控职责。资源竞争应通过 Perfetto、Simpleperf、内存工具或目标设备 trace 补证。

## 6. 接入检查

一套稳健的启动采集应做到：

1. 先按 API 版本检查字段与方法；
2. 保存 startup state、start type、reason、component、process 和 build；
3. 只计算同时存在且时钟域一致的时间戳；
4. 用开发者 key 标记少量稳定业务阶段；
5. 把 TTID 与 `reportFullyDrawn()` 的 TTFD 条件分别定义；
6. 对 cold/warm/hot、前台/后台和组件类型分组；
7. 控制 Intent、组件名和业务标识的上传范围；
8. 用 Perfetto 解释异常区间，用修复后相同场景验证收益。
