# Android 17 启动洞察分析与缺口研究

<!-- outline-start -->
## 要点

### 🔹 GPU功耗管理基础
Android 17 引入了全新的 GPU 功耗管理策略，基于 DVFS（动态电压频率调节）机制的深度优化。

### 🔹 DVFS 调优算法
新算法结合了应用负载预测和系统资源监控，实现了更智能的频率和电压调节。

### 🔹 多核心协调机制
跨 GPU 核心的功耗分配协调，根据不同应用场景动态调整核心工作状态。

### 🔹 热量控制与性能平衡
在控制 GPU 发热的同时保持最佳的性能表现，引入了热量感知的调度策略。

### 🔹 SoC 厂商定制化
支持不同 SoC 厂商的定制化 DVFS 策略，充分发挥硬件性能潜力。

## 扩展

### 🔸 游戏场景优化
针对游戏场景的特殊功耗优化策略，平衡帧率和功耗的关系。

### 🔸 AI 推理任务
AI 推理任务在 GPU 上的功耗管理，考虑模型大小和推理频率的影响。

### 🔸 后台任务处理
后台 GPU 任务的功耗管理策略，避免不必要的资源占用。

## 1. “启动洞察”不是单一 Android 服务

本文的平台锚点为 Android 17 / API 37 / `android-17.0.0_r1`。启动调查会同时用到几套名称接近、数据范围不同的能力：

| 能力 | 版本来源 | 数据 | 适合回答的问题 |
| --- | --- | --- | --- |
| AndroidX Benchmark Startup Insights | AndroidX Benchmark；本库工具主章固定 1.4.1 | Macrobenchmark 捕获的 Perfetto trace 与 `android_startup` metric | 可重复实验中命中了哪些慢启动候选信号 |
| `ApplicationStartInfo` | Android 15 / API 35 起 | system_server 保存的启动原因、类型、状态和时间戳 | 进程为何拉起、属于哪类启动、哪些平台节点可用 |
| `ProfilingTrigger.COLD_START` | Android 17 / API 37 | 系统触发的 trace 与 stack sampling | 难以本地复现的真实冷启动怎样获得诊断资料 |
| Android vitals | Google Play 线上聚合 | 用户设备上的 TTID/TTFD 分布 | 某版本或设备群体的启动体验是否退化 |

AOSP 中没有把这些能力合并起来的 `StartupInsightsService`，也没有一份由 `SystemHealthManager` 自动收集 CPU、内存、I/O、网络并给出修复方案的启动记录。工具可以互补，版本、样本和时间窗必须分别保存。

## 2. AndroidX Startup Insights 能提供什么

AndroidX Benchmark 的 Startup Insights 会对 Macrobenchmark 生成的 trace 运行 Perfetto `android_startup` metric，再读取 `slow_start_reason_with_details`。候选类别可涉及：

- 缺少 Baseline Profile 或 Cloud Profile；
- debuggable 构建、JIT、dex2oat 或 installd 活动；
- 主线程 runnable、blocking I/O、锁或 Binder 等待；
- GC、类校验、资源获取、View inflation；
- 与其他进程的 CPU 竞争；
- 同时发生的 broadcast 或其他 startup。

这些 reason 由 metric 与阈值产生，适合导航到对应迭代的 trace。它们不会自动证明因果。以“主线程 Binder 阻塞”为例，还要确认调用位置、对端进程、阻塞区间、重复性及修改后的 TTID/TTFD。

工具版本与平台版本要分开：

- Android 17 是测试设备的平台基线；
- Startup Insights 行为来自测试工程采用的 AndroidX Benchmark；
- slow-start reason 和阈值来自对应版本的 Perfetto metric；
- 升级任一工具后，都要重新核对 API、输出文本、SQL 与 CI 解析规则。

CI 不宜依赖展示文案长期不变。更稳妥的做法是保存原始 trace、Benchmark 版本、metric 输出和结构化类别，再由团队自己的规则生成告警。

## 3. ApplicationStartInfo 留下哪些缺口

`ApplicationStartInfo` 提供八个系统时间戳，以及 API 35 起可写的开发者 key 21–30。它能缩小慢启动区间，却不包含以下信息：

- 函数级 CPU time 与调用栈；
- 主线程 runnable 时在等待哪个 CPU；
- Binder 对端及服务端工作；
- 锁所有者和等待链；
- I/O 文件、page fault 与 page-cache 状态；
- GC pause、allocation 来源和 live set；
- RenderThread、GPU、SurfaceFlinger 的完整帧管线；
- 网络请求、业务依赖和内容可用条件。

因此，`APPLICATION_ONCREATE → FIRST_FRAME` 变长只能说明调查窗口扩大。原因需要 Perfetto、Simpleperf、应用阶段事件或 heap 工具补证。

历史查询还可能返回进行中的记录；首帧完成监听不等待 `reportFullyDrawn()`；Service、Broadcast 或 Provider 拉起的无界面进程可能没有首帧回调。采集端要把缺失字段当作正常状态，而非自动写成错误。

## 4. Android 17 冷启动 trigger 的位置

`ProfilingTrigger.TRIGGER_TYPE_COLD_START` 是 API 37 能力。应用预先注册 trigger 与全局结果 listener；系统遇到符合条件的真实冷启动时，尽早开始采集 system trace 和 stack sampling，并在 `reportFullyDrawn()` 或默认超时处结束。

它解决的是“问题发生时没有提前手工开 trace”。它不会把产物写回 `ApplicationStartInfo`，也不会运行 AndroidX Startup Insights。接入时仍要处理：

- trigger 注册、平台版本和系统限流；
- `registerForAllProfilingResults()` 的异步结果；
- 文件路径、trigger type、失败码与过期文件；
- trace 中可能包含的组件、线程名和业务标识；
- 上传同意、采样率、保留期限与访问权限。

完整的 trigger 类型、结果格式和停止条件见 [ProfilingManager 系统触发式性能追踪](../../part2-performance/ch08-responsiveness/08-system-triggered-profiling.md)。

## 5. 线上与实验室样本不能直接互换

Macrobenchmark 适合固定变量并重复测量；Android vitals 反映真实用户分布；触发式 profiling 只覆盖命中条件且成功产出文件的样本；`ApplicationStartInfo` 则是有限历史记录。四者的样本人群不同。

一份可复核的启动实验至少记录：

1. build、ABI、设备、Android 版本、刷新率和温度；
2. cold/warm/hot 定义与进程清理方式；
3. compilation mode、Baseline Profile 状态和测试工具版本；
4. 启动入口、账号状态、网络与首次安装数据；
5. TTID、TTFD 和业务内容 ready 的定义；
6. 迭代数、预热、异常样本规则与统计区间；
7. 对应 trace、`ApplicationStartInfo` 字段和代码版本。

本地十次冷启动的 Insight 命中比例不能当作线上用户比例。线上 P95 变差也不能直接归因到某条本地 trace。两边应通过相同版本、启动入口、设备 cohort 和阶段定义建立可检验的联系。

## 6. 缺口审阅表

| 结论 | 单独使用时缺少什么 | 补充证据 |
| --- | --- | --- |
| `LAUNCH → FIRST_FRAME` 变长 | 区间内部活动 | Perfetto 与应用阶段事件 |
| Insight 报告 blocking I/O | 文件、调用点与重复性 | trace slice、stack、源码与多轮实验 |
| CPU contention reason 命中 | 核心类型、频率、竞争进程与热状态 | scheduler trace、CPUFreq、thermal |
| TTFD 改善 | 内容正确性与交互可用性 | 业务 ready 条件、首交互测试 |
| vitals P95 退化 | 受影响 cohort 与代码路径 | 版本/设备/入口分组、触发 trace |
| cold-start trigger 有产物 | 样本选择偏差与结果完整性 | 注册率、命中率、失败率、trace stats |

“洞察”应被写成证据导航，而非诊断结论。每条优化建议都要回到对应 trace 或源码，再用相同条件的修复后实验验证。
