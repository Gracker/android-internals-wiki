# 19.10 APM 工具基准测试与兼容性验证

<!-- outline-start -->
## 要点

### 🔹 版本边界与来源口径
- 本节只使用 `Tencent/matrix`、`KwaiAppTeam/KOOM`、`Kyson/AndroidGodEye` 与 BlockCanary 的已读源码路径；原选题中的 `Tencent/Collie`、`bytedance/Rabbit` 已标为不存在仓库，不能继续作为论据。
- Android 版本边界固定到 Android 17 / API 37；所有 API 37 结论均保持“源码机制推断 + 团队接入前真机回归”的口径，不写成已量产验证。
- 本节不再发布源码估算开销数字；没有团队一手 benchmark 的位置保留为空值或准入测试要求。

### 🔹 三类 APM 机制对比
- Matrix：`Looper.setMessageLogging(Printer)` 与 `UIThreadMonitor` 反射路径，适合完整卡顿 / ANR / 启动监控，但需关注 hidden API 风险。
- KOOM：OOM tracker 周期检测 + ART 内部符号 + fork 子进程 dump，适合 OOM 监控，但 Android 大版本升级必须回归 `libart.so` 符号。
- AndroidGodEye：公开 `Choreographer.FrameCallback` + `/proc/stat` 采样，版本风险最低，但生产规模证据弱于 Matrix / KOOM。

### 🔹 本轮复核结论
- 旧“开销表”中的百分比、MB 级估算已经删除，正文只保留成对 benchmark 方法与空结果模板。
- 厂商 ROM 兼容性只作为测试维度呈现，不写无设备日志支撑的确定性适配结论。
- API 37 结论统一限定为源码边界与准入流程，明确不能误读为第三方二进制已完成真机认证。

## 扩展

### 🔸 接入前实测材料
- 真实设备 benchmark：冷启动、长稳、后台采样、弱网缓存、功耗与 hprof 写盘峰值。
- Android 17 真机/模拟器端到端验证：Matrix Choreographer 反射、KOOM fork dump、AndroidGodEye `/proc` 兜底路径。
- 厂商 ROM 回归matrix：MIUI/HyperOS、ColorOS/OriginOS、EMUI/HarmonyOS 的 SELinux 与 hidden API 表现。

## 19.10.1 先固定比较对象

兼容性评审必须绑定 commit。只写“master 支持”会让结论随着仓库变化，也无法确认测试使用了哪一份源码。截至 2026-07-25，本节固定以下 HEAD：

| 项目 | 固定源码 | 发布与构建状态 | Android 17 初判 |
|---|---|---|---|
| Tencent Matrix | [`3b8293bd`](https://github.com/Tencent/matrix/tree/3b8293bd65d47eeea7caf1f32a3a5d4d5eab60e7) | 正式版 2.1.0；Gradle 插件仍依赖旧 Transform API | 需维护 fork；不能把官方产物直接认定为兼容 |
| Kwai KOOM | [`df3b8c33`](https://github.com/KwaiAppTeam/KOOM/tree/df3b8c33f63ab1f23e814c19792314efb653deaf) | 正式版 2.2.2；master 版本号 2.2.3，未发布 | Java fast-dump 主动拒绝 API 37 |
| AndroidGodEye | [`459f5cb5`](https://github.com/Kyson/AndroidGodEye/tree/459f5cb5a2a4d176ff63f27322644a8191df2af9) | JitPack 3.4.3；AGP 3.2.1，`compileSdk`/`targetSdk` 29 | 适合阅读设计，不宜作为新项目二进制基线 |
| BlockCanary | [`ed688391`](https://github.com/markzhai/AndroidPerformanceMonitor/tree/ed688391cdf95742892ce61494736667cf5baf08) | 正式版 1.5.0；代码停在 2017 年 | 保留原理，不能原样用于 API 37 |

### 关于 Collie 与 Rabbit 的命名勘误

`Tencent/Collie` 和 `bytedance/Rabbit` 这两个精确的 GitHub org/repo 组合不存在，但不能由此推导出“Collie、Rabbit 项目不存在”。本知识库另有两份可核对的公开源码：

- [`happylishang/Collie@bfdc6782`](https://github.com/happylishang/Collie/tree/bfdc6782d568bfcefef01e846e81ccfd5a7e3470)
- [`SusionSuc/rabbit-client@d29f293a`](https://github.com/SusionSuc/rabbit-client/tree/d29f293a373167b03fc946e763d57e72157ab0e5)

它们的源码审阅位于“其他开源 APM 库”一节。本节只比较 Matrix、KOOM、AndroidGodEye 和 BlockCanary，不再用错误的仓库归属支撑结论。

## 19.10.2 “兼容”至少包含六层

一个库能够被 Gradle 解析，只证明依赖坐标存在。Android 17 的准入结论至少覆盖下面六层：

1. **构建**：当前 JDK、Gradle、AGP、Kotlin、R8 和 targetSdk 37 能完成 clean/release 构建。
2. **打包**：manifest 合并、资源冲突、consumer rules、ABI 和 16 KB page-size 检查通过。
3. **启动**：4 KB 与 16 KB 设备均能安装、冷启动和初始化，未触发链接或 hidden API 异常。
4. **采集**：每个启用模块都能生成语义正确的测试事件，不能只看“初始化返回成功”。
5. **失败降级**：反射、私有符号、权限、磁盘或子进程失败时，不应崩溃、不进入死循环、不阻塞主线程。
6. **停止与隐私**：关闭模块后恢复 Hook/Printer/线程状态；报告不携带未经授权的 Hprof、网络正文或设备标识符。

“minSdk 很低”只说明声明的安装下限，无法证明 targetSdk 37、ART 私有符号、16 KB native 产物或 Android 17 行为已经验证。

## 19.10.3 Matrix：公开 Looper 入口与私有 Choreographer 实现并存

### `LooperMonitor` 不能按一两个 Java 操作估算成本

固定 commit 的 `LooperMonitor.resetPrinter()` 反射读取 `Looper.mLogging`，保留原 Printer，再调用公开的 `Looper.setMessageLogging(Printer)` 安装包装器。Android 17 `android-17.0.0_r1` 中：

- `Looper.setMessageLogging()` 仍是公开 API。
- `Looper` 仍只有一个 `mLogging` 槽位。
- logger 非空时，平台在每次 dispatch 前后构造 `>>>>> Dispatching` 与 `<<<<< Finished` 字符串并回调 Printer。

因此开销不只是 Matrix `println()` 里的 `charAt()` 和 listener 循环。平台字符串构造、原 Printer、同步、所有 listener 以及启用 tracer 的处理都在路径上。监听器数量与业务 Message 密度不同，成本也不同，无法从源码常数项可靠换算成 `<0.1%`。

还要测试 Printer 冲突。后安装的 SDK 可以覆盖 Matrix；Matrix 也会包装当时读到的 Printer。反射读取失败时，它无法安全取得旧值。停止、重复初始化、另一个 SDK 重装 Printer 和多 ClassLoader 都要有用例。

### `UIThreadMonitor` 在 API 37 源码里“字段仍在”，但没有 SDK 保证

`UIThreadMonitor.init()` 会反射读取 `Choreographer.mFrameIntervalNanos`、`mLock`、`mCallbackQueues`、`mDisplayEventReceiver` 和内部 callback 方法。Android 17 AOSP 源码仍能找到这些成员，这只能证明平台实现当前存在对应字段。

应用通过反射访问 `@hide` 实现还受 hidden API 策略、targetSdk、厂商修改与异常回退影响。准入测试必须验证：

- 每个成员是否取得，失败后对应 tracer 是否明确降级。
- 60/90/120 Hz 与动态刷新率下，frame interval 和掉帧计算是否随显示模式变化。
- 主线程很忙、RenderThread/GPU 很忙、无绘制长消息三类场景能否区分。
- 应用前后台、窗口切换和多进程初始化后，observer 是否重复注册。

### Android 17 的两个构建阻塞项

Matrix 2.1.0 Trace Gradle 插件仍使用 `AppExtension`、`registerTransform()` 和已经由 AGP 8.0 删除的 Transform API。现代 AGP 工程需要移植到 Android Components Instrumentation/Artifacts API，或者采用经过审计的维护分支。只启用 task injection 也没有绕开这些旧类型。

Matrix 多个模块包含 native `.so`。官方 2.1.0 产物早于当前 16 KB 工具链，应逐库检查 ELF LOAD segment 与 APK ZIP 对齐，并在 Android 17 的 16 KB 严格模式执行安装、启动、Hook、停止 Hook 和异常回调。

结论：Matrix 的模块设计和专项能力仍有价值，但 API 37 准入单位应是“某个固定 fork 的某个 artifact”，不能用项目名一次性放行全部模块。

## 19.10.4 KOOM：API 37 当前有明确版本门

KOOM 不是通用卡顿 APM，它面向 Java heap、native heap 与 pthread 生命周期问题。固定 commit 中最重要的 Android 17 结论来自源码条件，而不是推测：

- `DefaultInitTask` 与 `ForkJvmHeapDumper.dump()` 把 Java fast-dump 支持范围限制为 API 21～36，API 37 会被拒绝。
- `ThreadMonitor` 只接受 API 28～34 且要求 arm64，API 37 同样不在支持范围。
- Native `LeakMonitor` 只检查 API 24+ 和 arm64，没有上限；“没有上限判断”不表示上游验证了 API 37。

### fork dump 降低长时间主进程阻塞，也会制造峰值

KOOM fast-dump 通过 `libart.so` 私有 C++ 符号进入 ART 临界区，暂停 Java 线程、fork，再恢复父进程，由子进程写 Hprof。这个设计把大部分写盘时间移到子进程，但下面的成本仍然存在：

- `SuspendAll` 带来的主进程停顿。
- fork 后 copy-on-write 页面造成的额外物理内存。
- 子进程 CPU、I/O、磁盘空间和进程调度。
- 低内存时父进程、子进程或分析进程被杀的风险。
- Hprof 含业务对象、字符串和图片字节带来的隐私风险。

`android-17.0.0_r1` 的 ART 源码中存在相近类和能力，不等于这些 mangled symbol 对普通 App 提供稳定 ABI。上游把公共版本门停在 API 36，所以 API 37 适配不能只删除 `SDK_INT` 判断；每个私有符号、锁、dump、恢复与失败分支都要重新移植和验证。

### KOOM 要分两组测

周期 tracker 与 dump 事件的成本相差很大，不能汇总成一个“KOOM CPU 平均值”：

- **常驻组**：只启用周期检测，测空闲唤醒、CPU、PSS/RSS、线程、FD 和电量变化。
- **事件组**：在受控 heap 中触发一次 dump，测主线程最长停顿、峰值 RSS、子进程存活、Hprof 大小、写盘耗时、失败恢复和剩余磁盘。

API 37 上若源码按设计拒绝 fast-dump，这一轮应记录为 `unsupported_by_version_gate`，不能删除门槛后把一次成功 dump 当成上游兼容证据。

## 19.10.5 AndroidGodEye：回调次数不是呈现帧数

AndroidGodEye 的结构适合学习：Core 负责采集，Debug Monitor 提供浏览器看板，Toolbox 组合调试能力。但固定 commit 仍使用 AGP 3.2.1、`compileSdk`/`targetSdk` 29 和旧发布流程，没有 Android 17 的构建与运行证明。

### `FpsMonitor` 测到什么

`FpsMonitor` 实现 `Choreographer.FrameCallback`。每次 `doFrame()` 增加计数并再次调用 `postFrameCallback(this)`，`FpsEngine` 定期读取并清零计数。这条路径使用公开 API，版本破坏风险低于私有反射，但指标语义更窄：

- 计数表示主线程收到的 Choreographer 回调。
- 回调发生不保证 App 提交了新 buffer。
- 它看不到 buffer 是否被 SurfaceFlinger 按时呈现，也看不到 GPU deadline miss。
- 静止页面上持续自注册 callback 还会让主线程保持逐 VSYNC 唤醒。

因此不能把这个值命名成“用户看到的 FPS”，也不能据此推荐 AndroidGodEye 作为 API 37 帧率基线。现代项目应优先使用 JankStats/FrameMetrics 记录应用帧，再用 Perfetto FrameTimeline 排查系统呈现问题。

### CPU 采样的边界

`CpuUsage` 读取 `/proc/stat` 与 `/proc/<pid>/stat` 做 jiffies 差分；不可读时执行 `top -n 1`。这条路径需要验证：

- Android 17 与目标厂商 ROM 上两个 proc 文件是否可读、字段解析是否正确。
- 多核归一化口径与团队报告是否一致。
- `top` fallback 的命令启动成本、输出格式和超时。
- 前后台切换、进程重启与采样间隔变化后，差分基线是否重置。

“两次 readLine 和若干次 parse”不能推导出低开销；文件 I/O、进程创建、调度、Rx interval 和导出链路都要进入测量。

结论：AndroidGodEye 更适合保留为调试 UI 与模块边界的设计样本。把它接入 Android 17 新项目之前，需要现代化构建链并逐模块重写或回归；多数团队直接采用当前官方 API 的维护成本更低。

## 19.10.6 BlockCanary：正常路径也有成本

BlockCanary 1.5.0 使用公开的 `Looper.setMessageLogging()` 识别主线程 dispatch 起止，并在 dispatch 接近阈值时由后台线程采样主线程 Java 栈。它适合解释“长 Message + 栈采样”模型，但原发布物存在多项 API 37 阻塞：

- 构建基线仍是 AGP 2.2.2、compileSdk 23、targetSdk 22、minSdk 9。
- manifest、通知、`PendingIntent`、外部存储和设备标识符代码不符合现代平台与隐私要求。
- 上游代码提交停在 2017 年，未给出 targetSdk 37、16 KB 或 Android 17 验证。

旧开销表把它写成“只在 block 触发时有成本”，这不准确。只要 Printer 已安装，Android 17 Looper 每次 dispatch 都会构造两条字符串并回调；接近阈值后还会调用 `Thread.getStackTrace()`、拼接字符串并缓存样本。评测应同时覆盖：

- 高频短 Message，测正常路径开销。
- 低频长 Message，测事件采样和报告开销。
- Printer 被另一个 SDK 覆盖，以及 stop 时清空其他 Printer 的冲突。

新项目若需要帧级卡顿数据，应使用 JankStats/FrameMetrics；若需要单次长 dispatch 预警，可按 BlockCanary 原理重写一个有单调时钟、限频、隐私 schema 和 Printer 协调策略的最小实现。

## 19.10.7 Android 17 兼容性对照表

这里的“未通过”表示现有证据不足或源码明确阻止，不表示每次运行都会崩溃。

| 工具/模块 | 构建门槛 | API 37 运行门槛 | 16 KB | 当前建议 |
|---|---|---|---|---|
| Matrix Trace 插件 | Transform API 已从 AGP 8 删除 | Looper 公开入口仍在；Choreographer 私有反射需回归 | Trace 之外的 native artifacts 逐库检查 | 使用维护 fork，按 artifact 准入 |
| Matrix Java runtime | 可绕开部分构建插件，但仍要查依赖 | Printer 冲突、反射降级与动态刷新率未获上游保证 | 纯 Java artifact 无 ELF 问题 | 只启用能证明兼容的模块 |
| Matrix native 模块 | 需要现代 NDK/AGP 重编或验证旧产物 | Hook 与私有实现逐模块验证 | 必测 | 未测不进 Release |
| KOOM Java fast-dump | upstream 工程可构建不代表 App 可用 | 源码上限 API 36，API 37 拒绝 | master 有新改动，正式 2.2.2 不能继承其结论 | API 37 默认不采用 |
| KOOM thread leak | arm64，API 28～34 | API 37 拒绝 | native，必测 | API 37 默认不采用 |
| KOOM native leak | arm64、私有 `libmemunreachable` | 没有上限门，但没有 API 37 保证 | native，必测 | 仅维护 fork 专项验证 |
| AndroidGodEye | AGP 3.2.1、target 29 | 公开 API 与 procfs 模块仍需逐项验证 | 依赖集合按最终 APK 检查 | 借鉴设计，不作新项目基线 |
| BlockCanary 1.5.0 | 旧构建、manifest 与权限问题 | Looper 入口存在，外围实现不满足现代要求 | 自身无 native `.so` | 不直接依赖旧 AAR |

厂商 ROM 结论只能来自“工具版本 × 设备构建号 × 安全补丁”的测试记录。没有设备日志时，不写“某 ROM 一定允许 Looper Hook”或“某 ROM 一定拦截 fork”；把这些情况列为测试维度即可。

## 19.10.8 一套可复现的开销 benchmark

### 先做成对变体

同一 commit 至少构建这些 release 变体：

| 变体 | 内容 | 用途 |
|---|---|---|
| `baseline` | 不含被测 SDK | 设备与业务基线 |
| `linked-off` | 依赖 SDK，但全部模块关闭 | 观察打包、类加载与初始化前影响 |
| `module-on` | 一次只开一个模块 | 给成本归属到具体模块 |
| `production-set` | 生产计划中的模块、采样率与上报配置 | 验证组合效应 |
| `event-trigger` | 受控制造 block、dump 或 leak 事件 | 测峰值与失败恢复 |

所有变体必须使用相同源码、R8、签名、ABI、资源压缩和业务配置。禁止用 debug baseline 对比 release SDK，也不要同时改变日志、网络环境或混淆规则。

### 设备与系统

平台主锚点是 Android 17 / API 37 / `android-17.0.0_r1`。最低设备集合建议包含：

- Android 17、4 KB page size 的 arm64 设备或模拟器。
- Android 17、16 KB page size 且关闭兼容模式的 arm64 设备或模拟器。
- 一台团队主要厂商 ROM 的 Android 17 设备。
- 为验证兼容区间保留 Android 14、15、16 各一台代表设备。

测试记录包含构建号、安全补丁、page size、SoC、RAM、刷新率、性能模式、起止温度和电量。内核调度或 ftrace 证据统一参照 `android17-6.18-2026-06_r6`；量产设备的 vendor kernel 可能不同，报告还要保存设备 `uname` 与 trace 元数据。

### 场景与轮次

| 场景 | 建议轮次 | 主要观测 |
|---|---:|---|
| 冷启动 | 5 次预热后 20 次测量 | TTID、TTFD、主线程 CPU、初始化 trace |
| 前台空闲 | 3 × 30 分钟 | 周期唤醒、CPU time、wakeups、PSS/RSS |
| 固定滑动 | 5 × 10 分钟 | FrameTimeline、FTime、主线程 CPU、温度 |
| 高频 Message | 5 × 5 分钟 | Printer 正常路径、锁竞争、分配 |
| 后台静置 | 3 × 30 分钟 | 后台任务、进程存活、网络与电量 |
| 受控事件 | 每种事件至少 5 次 | block 栈采样、KOOM dump、失败恢复与峰值 |

轮次顺序采用 baseline/variant 交替或随机排列，每轮开始温度落入同一区间。设备断连、脚本失败、必填 trace 缺失等判废条件在测试前写好；性能差但流程完整的轮次不能删。

### 采什么数据

- **CPU**：Perfetto 中进程/线程 running time、主线程调度、进程 CPU time；不要只截一秒 `top`。
- **帧**：FrameTimeline、JankStats 或 FrameMetrics；固定同一 UI state 和刷新率。
- **内存**：PSS、RSS、Java/native heap、峰值与稳定段；KOOM 事件组另记父子进程总峰值。
- **启动**：Macrobenchmark 控制启动模式，应用用 `reportFullyDrawn()` 给出 TTFD 终点。
- **电量**：同设备同场景做相对比较；需要精确功耗时使用外置仪器。
- **I/O 与网络**：写入字节、文件数量、请求数量、缓存队列和失败重试；关闭上传的变体要单独测。
- **可靠性**：初始化失败、反射/符号解析失败、丢事件、重复事件、关闭后残留线程和崩溃。

报告同时给绝对差值和相对差值。例如 CPU time 从 10 ms 变成 12 ms，绝对增加 2 ms、相对增加 20%；只写 20% 会放大很小的基线。统计至少给中位数、P95、最差有效轮和样本数。

### 产物与 16 KB 检查

下面的命令用于检查最终 APK 中 native 库的 page-size 对齐；路径应替换为当前 NDK 与交付产物。

```bash
llvm-objdump -p path/to/libapm.so | grep LOAD
zipalign -c -P 16 -v 4 app-release.apk
adb shell getconf PAGE_SIZE
```

ELF LOAD segment、APK ZIP 对齐和设备 page size 是三个不同证据。AAB 需要用交付时的 bundletool 生成目标 APK 后再检查，不能只检查构建目录里的中间 `.so`。

### 不再填写“源码估算开销”

本节删除了旧表中的 `<0.1%`、`0.1% × tracer`、`3–10 MB` 等数字。原因很直接：

- 源码能列出路径，不能给出目标设备上的调度、缓存、JIT、GC、I/O 和温控成本。
- 不同模块配置的工作量差异很大，KOOM 周期检查和一次 Hprof dump 尤其不能共用平均数。
- 空闲 CPU 百分比容易受采样窗口取整影响，微小值应以 CPU time、wakeups 和置信区间补充。
- 工具自己的采样会影响被测 App，必须由成对变体量化。

## 19.10.9 API 37 接入前准入清单

下面清单用于团队把某个固定 artifact 接入真实 App 前逐项验收；它不是本章正文的未完成待办，也不能被当作上游已经通过的认证结果。

- 准入项：固定仓库、commit、依赖坐标、AGP、NDK、R8 和 targetSdk 37。
- 准入项：clean build、增量 build、configuration cache 与各 variant 均通过。
- 准入项：manifest、权限、Provider、Service、通知、`PendingIntent` 和文件路径完成现代化审查。
- 准入项：最终 APK/AAB 的全部 native 依赖通过 16 KB 检查，并在严格模式运行。
- 准入项：每个模块都有“正常事件、边界事件、失败事件、关闭模块”四类测试。
- 准入项：Matrix 验证 Printer 冲突、Choreographer 反射结果、动态刷新率和多进程。
- 准入项：KOOM 尊重 API 37 版本门；自有移植另行验证所有 ART 符号、fork、恢复、磁盘和隐私。
- 准入项：AndroidGodEye 验证 FrameCallback 口径、procfs、`top` fallback 和后台唤醒。
- 准入项：BlockCanary 不直接复用旧 AAR；自研实现验证正常 Message 与 block 事件两条路径。
- 准入项：SDK 初始化或采集失败会产生诊断事件，不能把“没有报告”解释成“没有问题”。
- 准入项：停用后恢复 Printer/Hook、退出线程、停止任务并清理有限缓存。
- 准入项：上传 schema 完成脱敏、大小限制、过期清理、重试上限和用户授权审查。
- 准入项：benchmark 保存原始 trace、脚本 commit、测试顺序、判废原因和汇总脚本。

只有上述清单和团队阈值全部通过，某个固定 artifact 才能标记为 Android 17 verified。仓库 README、低 minSdk、AOSP 中存在相似实现或一次启动成功，都达不到这个证据等级。

## 19.10.10 选型建议

1. 新项目的帧、启动、退出与系统 profiling 基线，优先采用 JankStats、FrameMetrics、Macrobenchmark、`ApplicationStartInfo`、`ApplicationExitInfo`、ProfilingManager 与 Perfetto。
2. 已有 Matrix 项目按 artifact 保留有价值的专项模块，并维护现代 AGP、16 KB 与 API 37 分支；不要一次性开启全部 Canary。
3. KOOM 在 API 37 上默认视为不支持 Java fast-dump 和 thread monitor。团队愿意长期维护 ART 私有实现时，才启动独立移植项目。
4. AndroidGodEye、Collie、Rabbit 与 BlockCanary 更适合学习模块划分、调试 UI 和早期监控思路。现代 Release 采集器应重写，并用本节 benchmark 验证。
5. 商业 APM 也要接受同一套成对测试。厂商声明“支持 Android 17”只能作为输入，不能替代应用自己的设备、配置和隐私验收。
