## 19.10.1 三大开源 APM 的真实代码地图（基于源码）

> **勘误**：daily-topics 中提到的 `Tencent/Collie` 与 `bytedance/Rabbit` 在 GitHub 上不存在（API 404）。本节基于**真实仓库**的源码（截至 2026-06-25 master 分支）：
> - **Tencent/matrix**（微信 APM）
> - **KwaiAppTeam/KOOM**（快手 OOM 监控，注意是 Kwai/Kuaishou 而非 Bytedance）
> - **Kyson/AndroidGodEye**

### 🔹 Tencent/matrix：`LooperMonitor` 主线程 hook

**源码**：`matrix/matrix-android/matrix-trace-canary/src/main/java/com/tencent/matrix/trace/core/LooperMonitor.java`

矩阵主线程性能采样的入口是 `Looper.setMessageLogging(Printer)`，在构造时通过 `resetPrinter()` 反射读取 `Looper.mLogging` 字段，把自己的 `LooperPrinter` 包装器装回去。`LooperPrinter.println(String x)` 是 AOSP `MessageQueue.next()` 在每条 Message 处理前后回调的入口（`"> ..."` / `"< ..."`）：

```java
@Override
public void println(String x) {
    if (null != origin) { origin.println(x); ... }
    if (!isHasChecked) {
        isValid = x.charAt(0) == '>' || x.charAt(0) == '<';
        isHasChecked = true;
        ...
    }
    if (isValid) { dispatch(x.charAt(0) == '>', x); }
}
```

**开销特性**：
- **每条 message 1 次 charAt + 1 次 dispatch 转发**，基线 O(1)；
- `dispatch()` 内 `synchronized(listeners)` 后遍历所有 `ILooperListener`；同时启用 5 个 tracer（FPS/ANR/Startup/IdleHandlerLag/TouchEventLag）时**每条 message 走 5 次循环**，这是为什么 TraceConfig 建议只开需要的 tracer；
- 注册为 `MessageQueue.IdleHandler`，每 60s 检查一次 printer 是否被其他 classloader 替换（多 module 防御），频率低可忽略。

**Android 17 风险点**：`UIThreadMonitor.init()` 用 `ReflectUtils.reflectObject` 读 `Choreographer.mFrameIntervalNanos` / `mCallbackQueues` / `mDisplayEventReceiver` / `mLock` —— 这些是 AOSP `@hide` 字段，**未经一手验证** API 37 是否调整字段名或访问权限。

### 🔹 KwaiAppTeam/KOOM：Fork-and-dump hprof 低停顿实现

**源码**：`koom-java-leak/src/main/java/com/kwai/koom/javaoom/monitor/OOMMonitor.kt` + `koom-fast-dump/src/main/cpp/hprof_dump_v_impl.cpp`

KOOM 的 OOM 监控是「5 个 tracker + 周期循环 + fork 子进程 dump」三件套：

1. `OOMMonitor` 是 `LoopMonitor`，以 `monitorConfig.loopInterval`（默认 5s）周期 `call()`；
2. `trackOOM()` 遍历 5 个 `OOMTracker`：`HeapOOMTracker` / `ThreadOOMTracker` / `FdOOMTracker` / `PhysicalMemoryOOMTracker` / `FastHugeMemoryOOMTracker`；
3. 任一 tracker 返回 true 即触发 `dumpAndAnalysis()` → `ForkJvmHeapDumper.dump(path)`；
4. Java → JNI `Java_com_kwai_koom_fastdump_ForkJvmHeapDumper_forkDump` → `HprofDump::GetInstance().SuspendAndFork()`。

**HeapOOMTracker 判定**（`tracker/HeapOOMTracker.kt`）：
```kotlin
override fun track(): Boolean {
    val heapRatio = SystemInfo.javaHeap.rate
    if (heapRatio > monitorConfig.heapThreshold
        && heapRatio >= mLastHeapRatio - HEAP_RATIO_THRESHOLD_GAP) {
        mOverThresholdCount++
    } else { reset() }
    mLastHeapRatio = heapRatio
    return mOverThresholdCount >= monitorConfig.maxOverThresholdCount
}
```
**关键参数**：`heapThreshold`（默认 0.85）、`maxOverThresholdCount`（默认 5）、`HEAP_RATIO_THRESHOLD_GAP=0.05f`（小幅回落不算下降，避免抖动）。

**Fork-and-dump 核心**（`hprof_dump_v_impl.cpp` 的 `Suspend`）：
```cpp
bool HprofDumpVImpl::Suspend() {
    void *self = __get_tls()[TLS_SLOT_ART_THREAD_SELF];
    sgc_instance_ = std::make_unique<ScopedGCCriticalSection>(self, kGcCauseHprof, kCollectorTypeHprof);
    ssa_instance_  = std::make_unique<ScopedSuspendAll>(LOG_TAG, true);
    return true;
}
```
**机制**：
1. 通过 `kwai_linker::dlsym_elf("libart.so", "_ZN3art16ScopedSuspendAllC1EPKcb")` 解析 ART 内部符号（**Android 11+ 必须**，因为 ART 不再导出 `hprof_constructor_fnc_`），构造栈对象 → **暂停所有 Java 线程**；
2. 在此临界区调用 `fork()`，子进程继承挂起状态后 dump heap、写盘、`FastExit(0)`；
3. 父进程 `Resume()` 恢复挂起、`waitpid()` 等待子进程。

**主进程开销**：在 `Suspend` 与 `Resume` 之间仅持有 ART thread list lock 一小段时间（源码机制上应远短于完整 hprof dump；具体耗时需以设备 benchmark 为准），dump 几秒到十几秒都跑在子进程，**对 UI 的主要影响是一次短暂停顿级 STW，而不是全程阻塞 dump**。这正是 `hprof_constructor_fnc_` 在 Android 14 被移除后，KOOM 与 Perfetto 都不再使用旧路径的原因。

**Android 17 风险**：`HprofDumpImpl` 工厂方法按 API level 派发（`android_api < R / < V / else`），`HprofDumpVImpl` 是 Android 11+ 路径。**未经一手验证** API 37 下 `ScopedSuspendAll` / `ScopedGCCriticalSection` / `Mutex::ExclusiveLock` 的 mangled 符号是否仍存在，**必须做一次 dump 端到端回归**。

### 🔹 Kyson/AndroidGodEye：FpsMonitor + CpuUsage 轻量实现

**源码**：`android-godeye/src/main/java/cn/hikyson/godeye/core/internal/modules/fps/FpsMonitor.java` + `internal/modules/cpu/CpuUsage.java`

**FPS 测量**（`FpsMonitor`，**直接实现 `Choreographer.FrameCallback` 而不 hook 内部队列**）：
```java
@Override
public void doFrame(long frameTimeNanos) {
    mCurrentFrameCount++;
    if (mStartFrameTimeNanos == 0) { mStartFrameTimeNanos = frameTimeNanos; }
    mCurrentFrameTimeNanos = frameTimeNanos;
    mChoreographer.postFrameCallback(this);
}
```
每帧 1 次回调、O(1)；`FpsEngine` 用 `Observable.interval(mIntervalMillis)`（默认 2000ms）在 computation 线程上定时 `exportThenReset()` 计算帧率。

**CPU 采样**（`CpuUsage.getCpuInfo()`）：直接读 `/proc/stat`（整机）与 `/proc/{pid}/stat`（当前进程），按 jiffies 差分计算使用率。每次采样 2 次 `BufferedReader.readLine` + 2 次 split + 7 个 `Long.parseLong` + 5 次减法，**单次 sub-ms**。`cpuFileUsability()` 启动时检查文件可读性，不可读时降级到 `top` 命令。

**Android 17 兼容性观察**：
- `/proc/stat` 与 `/proc/{pid}/stat` 字段在 Android 17 仍存在（kernel 5.15+ / 5.10 通用），启动检查已兜底，**理论上不 break**；
- `Choreographer.postFrameCallback` 是公开 API，**无版本风险**。

## 19.10.2 开源 APM 工具性能开销表（基于源码机制推断）

> **诚实标注**：下表数字基于代码路径常数项估算，**未经一手 benchmark**。生产数据应参考各工具官方公开报告与团队自行压测。

| 工具 | 空闲 CPU | 主动采样 CPU | 内存 baseline | 关键开销来源 |
|---|---|---|---|---|
| Tencent/matrix | < 0.1% | 启用 tracer 数量 × 0.1% | ~3-5 MB | `AppMethodBeat` 维护 100k long 缓冲 (~800 KB) |
| KwaiAppTeam/KOOM | < 0.1% | 5s 周期循环 < 0.05% | ~4-6 MB | fork-dump 瞬时峰值（子进程 + hprof 写盘） |
| Kyson/AndroidGodEye | < 0.1% | 2s 周期 + 1 回调/帧 | ~6-10 MB | LeakCanary 嵌入 + dashboard 启动 |
| markzhai/AndroidPerformanceMonitor (BlockCanary) | < 0.1% | 仅在 block 触发时栈采集 | ~2 MB | 5 年未 release |

## 19.10.3 厂商定制 ROM 适配经验（基于历史 issue 模式）

- **MIUI / HyperOS**：`Looper.setMessageLogging` hook 长期工作（BlockCanary 历史有大量 issue 报告与 workaround 文档）；fork 路径偶有 SELinux 拦截（需把 `koom-fast-dump.so` 加入白名单）。
- **ColorOS / OriginOS**：fork 路径在部分 Android 15 设备上有 SELinux 拦截。
- **EMUI / HarmonyOS**：`Looper` hook 路径稳定。
- **Android 17 (API 37) 兼容性现状**：四个工具的 `minSdk` 普遍 16-19，**没有任何一个工具的 master 明确声明已验证 Android 17 (API 37) 目标设备**。考虑到 ART 内部符号在 Android 15 后又有过调整，**厂商 ROM 上的 fork-dump 兼容性需逐设备验证**。

## 19.10.4 工具选型的源码级建议

1. **只需要卡顿 / 帧率监控**：选 `Kyson/AndroidGodEye` 的 FPS + CPU 模块（`Choreographer` + `/proc/stat` 纯公开 API，**最小版本风险**）。
2. **需要完整 APM（FPS / 卡顿 / 启动 / ANR）且接受 hook 风险**：选 `Tencent/matrix`（生产验证最完整，源码质量最高）。
3. **核心诉求是 OOM 监控**且能接受 fork-dump 的 ART 符号不确定性：选 `KwaiAppTeam/KOOM`。
4. **轻量 UI 卡顿监控（仅 debug 启用）**：`markzhai/AndroidPerformanceMonitor`（BlockCanary）已 5 年未 release，不建议线上使用。

## 19.10.5 待验证项

1. AOSP `frameworks/native/libs/trace_collection` 路径在 android-17.0.0_r1 与 android-14 tag 上均 NOT_FOUND；**该模块尚未公开进入 AOSP**。
2. `Tencent/Collie` 与 `bytedance/Rabbit` 仓库在 GitHub 上不存在（API 404）。
3. Android 17 上 ART 内部符号稳定性需真机 dump 验证。
4. `Looper.mLogging` / `Choreographer.mFrameIntervalNanos` 在 Android 15+ `hiddenapi` 行为对反射的影响未验证。
