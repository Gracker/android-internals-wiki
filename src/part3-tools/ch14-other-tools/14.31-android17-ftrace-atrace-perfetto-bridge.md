# 14.31 FTrace：内核 tracefs + atrace 桥 + Perfetto probe

<!-- outline-start -->
## 要点

### Linux tracefs

- tracepoint、function/function_graph tracer、kprobe 是三种不同机制，不能混用结论。
- `trace` 适合停止采集后的文本快照；`trace_pipe` 和 `per_cpu/cpu*/trace_pipe_raw` 是消费式读取入口。
- `buffer_size_kb` 是每 CPU ring buffer 大小；`buffer_percent` 是阻塞读取的唤醒水位。
- 本章内核锚点为 `android17-6.18-2026-06_r6`。

### Android atrace

- Android 17 的 `k_categories[]` 有 45 个内建 category；category 可以同时控制用户态 tag 和一组 tracefs event。
- `debug.atrace.tags.enableflags` 控制传统 ATrace tag，`-a` 通过进程名选择应用。
- atrace 优先使用 `/sys/kernel/tracing/`，缺失时回退 `/sys/kernel/debug/tracing/`。
- `/vendor/etc/atrace/atrace_categories.txt` 存在时优先使用该文件；否则尝试 `android.hardware.atrace@1.0` HIDL HAL。

### Perfetto `linux.ftrace`

- `FtraceConfigMuxer` 合并多个 session 的内核 event 集合，并为每个 data source 保留独立过滤配置。
- `compact_sched` 在格式校验成功且采集 `sched_switch` 时默认启用。
- `drain_buffer_percent` 在 Linux 6.9 以下无效；Android 17 的 6.18 锚点满足版本条件，运行时仍要检查 tracefs 权限。
- `buffer_size_lower_bound`、`atrace_userspace_only` 和 `kprobe_events` 都已存在于 Android 17 AOSP 的 `FtraceConfig`。

### 两条用户态事件路径

- ATrace：`ATRACE_NAME` / `ATrace_beginSection` / 传统模式下的 `android.os.Trace` → `trace_marker` → `ftrace/print` → Perfetto ftrace probe。
- Perfetto Track Event SDK：进程内 SDK data source → Perfetto producer buffer → tracing service；它不写 `trace_marker`。

<!-- outline-end -->

## 14.31.1 先区分四个名词

排查 Android trace 时，`ftrace` 常被用来泛指全部内核追踪能力。源码里至少要分开下面四类：

| 名词 | 插入位置 | 启用入口 | 典型事件 | 风险边界 |
|---|---|---|---|---|
| tracepoint | 内核源码预先声明的静态事件点 | `events/<group>/<event>/enable` | `sched_switch`、`binder_transaction`、`gpu_mem_total` | 事件字段随内核实现确定，工具可读取 `format` 做运行时解析 |
| function / function_graph tracer | 编译器插桩点与 dynamic ftrace patching | `current_tracer`、`set_ftrace_filter`、`set_graph_function` | 函数进入、退出与调用图 | 覆盖范围过大时开销很高，且 user build 权限通常受限 |
| kprobe / kretprobe | 运行时挂到内核函数入口或返回点 | `kprobe_events`，或 Perfetto `kprobe_events` 配置 | 目标函数命中、进入/退出区间 | 依赖内核配置、符号可见性、tracefs 写权限和安全策略 |
| 用户态 marker | 用户进程写入 tracefs | `trace_marker` | ATrace 的 `B/E/S/F/C/I/N/G/H` 文本协议 | 需要 tag/app 选择正确，事件最终表现为 `ftrace/print` |

tracepoint 的 event 开关不会自动选择 `function` tracer；`current_tracer=nop` 时仍然可以采集 tracepoint。反过来，切换为 `function_graph` 也不会自动启用 `sched_switch` 等 event。看到空 trace 时，应分别检查 `current_tracer`、`events/.../enable`、`tracing_on` 和访问权限。

## 14.31.2 Android 17 的端到端路径

下面的图用于区分 ATrace marker、内核事件和 Track Event SDK 的数据路径。

```text
传统 ATrace 路径
android.os.Trace（传统模式）/ ATrace_* / ATRACE_NAME
        │  libcutils 写 trace_marker
        ▼
tracefs: ftrace/print ───────────────┐
                                    │
内核事件路径                         │ per-CPU raw ring buffer
sched/*, binder/*, power/* ─────────┤
                                    ▼
                      traced_probes / linux.ftrace
                      FtraceController + CpuReader
                                    │ FtraceEventBundle
                                    ▼
                           Perfetto tracing service
                                    │
                                    ▼
                              .perfetto-trace

Track Event SDK 路径
应用内 Perfetto SDK ── producer shared memory ──► tracing service
```

两条用户态路径可以写入同一个 Perfetto trace 文件，但采集配置不同。ATrace marker 依赖 `linux.ftrace`、`ftrace/print`、category tag 和 app 选择；Track Event 依赖 `track_event` data source 及 SDK category 配置。把 Track Event 归到 `trace_marker` 会导致错误的缺失事件判断。

Android 17 的 ftrace probe 读取 `per_cpu/cpu*/trace_pipe_raw`。内核数据进入 per-CPU ring buffer 后，`CpuReader` 按 event format 解析，再由每个 data source 的过滤配置决定是否序列化到对应 session。

## 14.31.3 tracefs 控制文件怎样配合

本章使用 Android 17 GKI 6.18 的标准挂载点 `/sys/kernel/tracing`。`atrace.cpp::findTraceFiles()` 和 libcutils 的 `trace-dev.cpp` 都保留 `/sys/kernel/debug/tracing` 回退路径，用于兼容旧设备或不同挂载方式。

| 文件 | 语义 | 常见误用 |
|---|---|---|
| `tracing_on` | 控制 ring buffer 是否继续接收记录 | 写 0 只停止记录；已启用的 event/tracer 仍可能产生检查开销 |
| `trace` | 人类可读的当前 buffer 内容 | 适合停止采集后读取，不适合作为 Perfetto 的持续输入 |
| `trace_pipe` | 人类可读、消费式、可阻塞的流 | 读取会移除数据，多个消费者会互相影响 |
| `per_cpu/cpu*/trace_pipe_raw` | 每 CPU 二进制消费式流 | 需要解析 event `format`，Perfetto 从这里读取 |
| `buffer_size_kb` | 每 CPU buffer 大小 | 总内存约为单 CPU 大小乘可用 CPU 数量，并有页和管理数据误差 |
| `buffer_percent` | `trace_pipe_raw` 阻塞读取的唤醒水位 | 它不限制最大占用，也不等于 Perfetto 用户态 buffer 大小 |
| `events/<group>/<event>/format` | event 字段布局和 ID | 解析器不能只依赖开发机上的固定结构 |
| `available_tracers` | 当前内核编译并开放的 tracer | 输出内容由配置和设备策略决定，不能预设一定含 `function_graph` |
| `tracing_max_latency` | latency tracer 保存的最大延迟 | 与普通 tracepoint ring buffer 容量无关 |

Linux 文档对 `buffer_percent` 的定义是：阻塞读取 per-CPU `trace_pipe_raw` 时，buffer 达到指定水位才唤醒 waiter。Perfetto 的 `drain_buffer_percent` 借用这个机制。Android 17 AOSP 的 `FtraceController` 还会检查内核版本、`buffer_percent` 可写性和 `trace_pipe_raw` 的 poll 行为；任一检查失败都会回到周期读取。

## 14.31.4 atrace category 不只是 event 别名

Android 17 的 `frameworks/native/cmds/atrace/atrace.cpp` 在 `k_categories[]` 中定义了 45 个内建 category。这里的数量来自 `android-17.0.0_r1` 数组逐项计数，厂商文件和 HAL 动态返回的 category 不包含在这 45 个之内。

下面截取 `gfx` 与 `sched`，用于说明同一数据结构怎样表示用户态 tag 和内核 event。

```cpp
static const TracingCategory k_categories[] = {
    { "gfx", "Graphics", ATRACE_TAG_GRAPHICS, {
        { OPT, "events/gpu_mem/gpu_mem_total/enable" },
    } },
    // ...
    { "sched", "CPU Scheduling", 0, {
        { REQ, "events/sched/sched_switch/enable" },
        { REQ, "events/sched/sched_wakeup/enable" },
        { OPT, "events/sched/sched_waking/enable" },
        // ...
    } },
};
```

`gfx` 会设置 `ATRACE_TAG_GRAPHICS`，并尝试启用可选的 `gpu_mem_total`；`sched` 没有用户态 tag，主要是一组内核 event。`REQ` 路径不可写时该 category 不可用，`OPT` 路径缺失时允许继续。可用 category 应在目标设备上通过 `atrace --list_categories` 查询，不能用源码数组代替设备结果。

### 用户态 tag 和 app 选择

atrace 将已选 category 的 `ATRACE_TAG_*` 合并后写入 `debug.atrace.tags.enableflags`。`-a` 处理进程 cmdline：应用标记没有出现时，需要核对包名、多进程后缀、进程是否在采集开始前已读取新属性，以及目标调用使用的 tag 是否已启用。

传统 C++ 标记最终进入 libcutils。下面的片段说明 `ATRACE_NAME` 和 marker fd 的关系。

```cpp
// system/core/libutils/include/utils/Trace.h
#define ATRACE_NAME(name) \
    ::android::ScopedTrace PASTE(___tracer, __LINE__)(ATRACE_TAG, name)

// system/core/libcutils/trace-dev.cpp
atrace_marker_fd =
    open("/sys/kernel/tracing/trace_marker", O_WRONLY | O_CLOEXEC);

void atrace_begin_body(const char* name) {
    WRITE_MSG("B|%d|", "%s", "", name, "");
}
```

`ScopedTrace` 构造时调用 begin，析构时调用 end；`trace-dev.cpp` 把文本协议写入 `trace_marker`。Perfetto 采集 ATrace 时会加入 `ftrace/print`，再把 marker 还原为 slice、counter 或 instant event。

### 厂商 category：文件优先，HIDL 回退

Android 14 起，厂商可以提供 `/vendor/etc/atrace/atrace_categories.txt`。Android 17 的 atrace 初始化逻辑为：

1. 文件存在：解析文件，不连接 atrace HAL；
2. 文件不存在：调用 `android.hardware.atrace@1.0::IAtraceDevice::getService()`；
3. 两者都没有：只使用 AOSP 内建 category。

Android 17 的 AOSP 源码仍是 HIDL 1.0。Perfetto 的 `atrace_hal_wrapper.cc` 虽然通过动态库包装调用，但 `src/android_internal/atrace_hal.cc` 引用的同样是 `android::hardware::atrace::V1_0::IAtraceDevice`。据此不能写成 AIDL 接口，也不能把动态加载等同于接口版本迁移。

## 14.31.5 Perfetto 怎样复用一份内核状态

同一个 tracefs instance 的 event、clock、per-CPU buffer 和 `tracing_on` 是共享状态。`FtraceConfigMuxer` 为多个 Perfetto data source 做以下处理：

- 每个配置生成自己的 `EventFilter`；
- 内核侧启用所有存活配置需要的 event 并集；
- 移除配置时，只关闭已不被任何配置使用的 event；
- ATrace app/category 也按存活配置求并集；
- 每个 data source 只输出自己过滤器允许的 event；
- 所有活动配置的 `drain_buffer_percent` 取最小非零值。

这提供了事件输出隔离，但没有为每个 session 创建独立的 primary tracefs ring buffer。首个配置设置 clock 和 buffer；后续并发配置不能为满足自己的 `buffer_size_kb` 随意重设内核 buffer，因为重设会暂停记录并清空内容。包含 `tids_to_trace`、`tracefs_options` 或 `tracing_cpumask` 的配置属于单租户特性，已有 session 时会被拒绝。

### 两层 buffer 要分别计算

Perfetto 配置里的两个大小属于不同层：

| 配置位置 | 对象 | 单位与范围 |
|---|---|---|
| `TraceConfig.buffers.size_kb` | Perfetto tracing service 的用户态共享内存 buffer | 每个 Perfetto buffer |
| `FtraceConfig.buffer_size_kb` | tracefs 内核 ring buffer | 每 CPU |

Android 17 AOSP 在未设置 `FtraceConfig.buffer_size_kb` 时，以 7 GiB 物理内存为分界选择 2 MiB/CPU 或 8 MiB/CPU。`buffer_size_lower_bound: true` 表示请求值是下限，允许实现选用更大的默认值。内核按页分配并带管理开销，所以读取到的实际值可能与请求值略有差异。

### compact sched 的启用条件

Android 17 AOSP 的行为可以从 `CreateCompactSchedConfig()` 直接确定：

- 请求了 `sched_switch`；
- `sched_switch` 与 `sched_waking` 的运行时 event format 通过校验；
- 配置没有显式写 `compact_sched.enabled: false`。

三个条件满足时使用紧凑编码。格式校验失败会退回逐事件编码并记录错误；源码没有承诺固定的单事件字节数或固定压缩率。评估收益应对同一设备、同一负载和同一事件集合比较 trace 文件大小，同时检查丢事件统计。

### watermark 读取

`drain_buffer_percent: 50` 表示任一 per-CPU buffer 大约达到一半时可唤醒读取。Android 17 的 `FtraceController` 将 6.9 作为通用内核版本门槛，并对部分较老 GKI 修订做回补识别。`android17-6.18-2026-06_r6` 高于该门槛；设备若不允许写 `buffer_percent`，仍会回退到定时读取。

## 14.31.6 Android 14 到 Android 17 的边界

Android 平台版本、Perfetto 版本和 Linux 内核版本是三条不同坐标。不能用“Android 版本升级”替代具体能力检查。

| 范围 | 可由源码或官方注释确认的变化 |
|---|---|
| Android 14-17 | atrace 与 Perfetto 支持 `/vendor/etc/atrace/atrace_categories.txt`；Android 17 源码仍保留 HIDL 1.0 HAL 回退 |
| Perfetto v42+ | `compact_sched.enabled` 未设置时默认开启，但仍受 event format 校验约束 |
| Perfetto v43+ | `buffer_size_lower_bound` 可把 `buffer_size_kb` 解释为下限 |
| Perfetto v48+ | `drain_buffer_percent` 可配置；Linux 6.9 以下不生效 |
| Perfetto v52+ | `atrace_userspace_only` 可阻止 category 自动附带预定义及厂商 ftrace event |
| Android 17 锚点 | AOSP tag 为 `android-17.0.0_r1`；内核 tag 为 `android17-6.18-2026-06_r6`，以上 Perfetto 字段与实现路径均存在 |

`atrace_userspace_only` 只跳过 category 附带的内核 event。它不会关闭用户态 ATrace，也不会把传统 marker 自动改造成 Track Event。需要 SDK 路径时，应配置 `track_event` data source，并结合 `atrace_categories_prefer_sdk` 或 `atrace --prefer_sdk` 的适用范围验证进程行为。

## 14.31.7 开销怎样评估

没有统一的“ftrace 开销百分比”。开销由事件频率、字段处理、CPU 数量、buffer 大小、读取周期、过滤范围和设备内核实现共同决定。

| 选择 | 主要成本 | 观测方法 |
|---|---|---|
| 少量低频 tracepoint | event 判断、写 ring buffer、用户态读取 | 对照相同 workload 的耗时与 CPU time |
| `sched_switch` / `sched_waking` | 高频事件写入和解析 | 检查 ftrace overrun、Perfetto stats 与 trace data rate |
| 大 per-CPU buffer | 内核常驻内存 | 读取 `buffer_size_kb`、`buffer_total_size_kb` |
| 很低的 drain 水位 | 唤醒和读取次数增加 | 比较 `traced_probes` CPU time 与丢事件 |
| 大范围 function/function_graph | 动态插桩和大量函数事件 | 只在专用测试机上逐步扩大 filter |
| kallsyms / kprobe | 符号读取、动态探针与安全限制 | 查看数据源错误、kprobe hits/misses 与内核日志 |

测量时应保存未开启 tracing 的基线，并固定场景、持续时间、温度、频率策略和事件集合。若 trace 已经出现 overrun，文件变小可能来自数据丢失，不能作为编码效率提升的证据。

## 14.31.8 可直接执行的采集流程

### 设备能力探测

下面的命令用于确认目标设备实际开放的 category、event 和 tracer。

```bash
adb shell atrace --list_categories
adb shell 'test -d /sys/kernel/tracing && echo tracefs-mounted'
adb shell 'cat /sys/kernel/tracing/trace_clock'
adb shell 'cat /sys/kernel/tracing/available_tracers'
adb shell 'test -r /sys/kernel/tracing/events/sched/sched_switch/format &&
  sed -n "1,80p" /sys/kernel/tracing/events/sched/sched_switch/format'
```

category 列表会合并 AOSP、厂商文件或 HAL 能力；`available_tracers` 只说明已暴露的 tracer，不表示 shell 有写权限。`format` 可读时，应把 event ID 和字段布局作为目标设备的解析依据。

### atrace 快速采集

这条命令把设备输出重定向到主机文件，避免把主机重定向误写成设备路径。

```bash
adb shell "atrace -a 'com.example.game' -t 10 \
  sched freq idle am wm gfx view binder_driver" > trace.atrace
```

`com.example.game` 要替换为目标进程 cmdline；多进程应用可传逗号分隔列表。输出是 atrace/ftrace 文本流，不应仅因文件后缀写成 `.html` 就当作 HTML。需要长期、多数据源或可查询的 trace 时，使用 Perfetto 原生格式。

### Perfetto 文本配置

下面的配置同时采集 scheduler、频率、idle 和目标应用的 ATrace 标记。文件在主机创建，再推送到设备。

```bash
cat > ftrace.pbtx <<'EOF'
buffers {
  size_kb: 32768
  fill_policy: RING_BUFFER
}
data_sources {
  config {
    name: "linux.ftrace"
    target_buffer: 0
    ftrace_config {
      ftrace_events: "sched/sched_switch"
      ftrace_events: "sched/sched_waking"
      ftrace_events: "power/cpu_frequency"
      ftrace_events: "power/cpu_idle"
      atrace_categories: "gfx"
      atrace_categories: "view"
      atrace_categories: "wm"
      atrace_apps: "com.example.game"
      compact_sched { enabled: true }
      drain_buffer_percent: 50
    }
  }
}
duration_ms: 10000
EOF

adb push ftrace.pbtx /data/local/tmp/ftrace.pbtx
adb shell perfetto --txt \
  -c /data/local/tmp/ftrace.pbtx \
  -o /data/local/tmp/ftrace.perfetto-trace
adb pull /data/local/tmp/ftrace.perfetto-trace
```

`--txt` 明确告诉 Perfetto 输入是 textproto。外层 32 MiB 是 Perfetto 用户态 buffer；内核 per-CPU buffer 保持实现默认值。采集后应在 trace stats 中检查未知 event、data source 错误和数据丢失。

### 直接操作 tracefs

直接写 tracefs 会影响系统范围的 tracing 状态，只适合没有其他采集任务的 userdebug/eng 测试机。下面的流程限定为一个 scheduler event，并在退出前关闭它。

```bash
adb root
adb wait-for-device
adb shell '
set -eu
trace_dir=/sys/kernel/tracing
echo 0 > "$trace_dir/tracing_on"
: > "$trace_dir/trace"
echo 1 > "$trace_dir/events/sched/sched_switch/enable"
echo 1 > "$trace_dir/tracing_on"
sleep 5
echo 0 > "$trace_dir/tracing_on"
cat "$trace_dir/trace" > /data/local/tmp/sched.trace
echo 0 > "$trace_dir/events/sched/sched_switch/enable"
'
adb pull /data/local/tmp/sched.trace
```

该流程会清空当前 primary trace buffer，也没有恢复别的工具预先设置的 clock、buffer 和 event。实验前后都要确认没有 Perfetto、atrace 或厂商诊断程序并发使用 tracefs。

### function_graph 的受控验证

不要从“追踪所有函数”开始。下面的示例先验证 `binder_transaction` 与 `function_graph` 是否存在，只对一个函数采集，并使用 trap 恢复状态。

```bash
adb root
adb wait-for-device
adb shell '
set -eu
trace_dir=/sys/kernel/tracing
target_fn=binder_transaction
grep -qw function_graph "$trace_dir/available_tracers"
grep -qw "$target_fn" "$trace_dir/available_filter_functions"

cleanup_trace() {
  echo 0 > "$trace_dir/tracing_on"
  echo nop > "$trace_dir/current_tracer"
  : > "$trace_dir/set_graph_function"
}
trap cleanup_trace EXIT

echo 0 > "$trace_dir/tracing_on"
: > "$trace_dir/trace"
echo "$target_fn" > "$trace_dir/set_graph_function"
echo function_graph > "$trace_dir/current_tracer"
echo 1 > "$trace_dir/tracing_on"
sleep 5
echo 0 > "$trace_dir/tracing_on"
cat "$trace_dir/trace" > /data/local/tmp/function-graph.trace
'
adb pull /data/local/tmp/function-graph.trace
```

可执行性由目标设备决定：内核配置、`available_filter_functions`、文件权限和 SELinux 任一项都可能阻止采集。Android 17 GKI 源码具备相关机制，不代表所有量产设备向 adb shell 开放控制节点。

## 14.31.9 常见失败怎样定位

### `atrace --list_categories` 有 category，trace 里没有应用 slice

依次检查：

- `-a` 参数是否匹配进程 cmdline，而非只看 APK 包名；
- 进程是否在采集开始后刷新了 `debug.atrace.tags.enableflags`；
- 调用使用的 `ATRACE_TAG_*` 是否属于已选 category；
- Perfetto 配置是否包含 `atrace_apps` 和对应 `atrace_categories`；
- `ftrace/print` 是否被 data source 启用且没有被 `print_filter` 丢弃；
- 应用是否改走 Track Event SDK，配置却只有 `linux.ftrace`。

### 配置了 `drain_buffer_percent`，读取节奏没有变化

检查内核版本、`/sys/kernel/tracing/buffer_percent` 是否可写、per-CPU `trace_pipe_raw` 是否支持 poll，以及是否有并发 session 请求了更低水位。Perfetto 对活动配置取最小非零值。

### Perfetto 报 event unknown

先在设备上读取 `available_events` 与目标 event 的 `format`。同名 event 可能不存在于该设备内核，厂商 event 也不会因写进 textproto 就自动出现。Android 17 平台锚点只能证明 AOSP/GKI 参考实现，不能证明厂商内核启用了每个可选 event。

### function_graph 为空或启动失败

检查 `current_tracer` 是否已经被其他工具占用、目标函数是否在 `available_filter_functions`、函数是否被内联或裁剪，以及控制节点是否可写。Perfetto 发现非 `nop` tracer 被外部占用时会拒绝接管，避免破坏已有采集。

### 多 session 的 buffer 配置没有按预期生效

内核 buffer 不能在活动采集中无损调整。首个 ftrace data source 建立共享状态后，后续 session 的 `buffer_size_kb` 和 drain 周期不保证独立生效。需要严格控制这些参数时，应排除其他 trace session，并记录实际 tracefs 值。

## 14.31.10 与其他章节的证据组合

- §1.48 Binder IPC ThreadState：把 `binder/binder_*` 与 `sched_switch`、`sched_waking` 对齐，区分 IPC 等待和 CPU 调度等待。
- §14.10、§14.21、§14.25 eBPF：tracepoint 可同时作为 ftrace 与 BPF attach 点，但 map、ringbuf 和 Perfetto 的消费语义不同。
- §14.24 Simpleperf：PMU counter 提供采样或计数，ftrace 提供离散状态事件；时间轴联合分析比互相替代更合适。
- §14.29 AGI：GPU frame profile 属于图形工具链；需要系统调度、Binder 或电源上下文时再补 Perfetto/ftrace。
- §14.30 GpuService：`gpu_mem/gpu_mem_total` 既可更新 GpuMem BPF map，也可由 Perfetto ftrace 持续采集，二者核算和输出方式不同。
- §2.6 Perfetto：本章解释 `linux.ftrace` 数据源的内核入口，Perfetto 章节负责 trace 配置、SQL 与 UI 分析。

## 14.31.11 可由 Android 17 锚点支持的结论

- Android 17 atrace 有 45 个内建 category，并允许厂商文件或 HIDL HAL 扩展；
- atrace 和 libcutils 都优先访问 `/sys/kernel/tracing`；
- ATrace marker 经 `trace_marker` 进入 `ftrace/print`，Track Event SDK 走独立 producer 路径；
- Perfetto 为并发 ftrace data source 合并内核 event，并按 data source 过滤输出；
- 内核 `buffer_size_kb` 按 CPU 计，Perfetto `TraceConfig.buffers` 是另一层用户态 buffer；
- compact sched 默认行为受请求事件和运行时 event format 共同约束；
- Android 17 的 Perfetto 仍通过 `android.hardware.atrace@1.0` HIDL 访问 vendor atrace HAL；
- 6.18 锚点满足 `drain_buffer_percent` 的通用内核版本门槛；
- function tracer 和 kprobe 的真机可用性仍取决于内核配置、权限、SELinux 与厂商策略。
