# 14.30 GpuService GPU 内存可观测性架构

本章聚焦 Android 17（`android-17.0.0_r1`）中 `frameworks/native/services/gpuservice/` 的 GPU 内存可观测路径。结论先行：AOSP 用户态的 GpuService 不负责分配显存，也不做用户态显存池碎片整理；它的职责是把 GPU 驱动已经维护好的内存与驱动加载状态，以 **dumpsys 快照、Perfetto trace 快照、statsd 归因统计** 三种方式暴露出来。真正的 buffer 分配、复用和碎片整理仍落在 gralloc / GPU HAL / 厂商驱动侧。

> 版本边界：本章所有源码结论锚定 `android-17.0.0_r1`。涉及 Android 12-16 的描述只作为能力演进背景；未经本章源码核验的 Android 18 / API 38+ 改动不纳入结论。

## 14.30.1 三层观测栈：同一类 GPU 事实，不同消费通道

GpuService 里与 GPU 内存和驱动归因相关的主体可以拆成三层：

| 层级 | 组件 | 输入 | 输出 / 消费方 | 适合回答的问题 |
|---|---|---|---|---|
| 底层快照 | `GpuMem` + `gpuMem.c` BPF 程序 | GPU 驱动发出的 `gpu_mem/gpu_mem_total` tracepoint | `dumpsys gpuservice --gpumem`、`traverseGpuMemTotals()` | 现在每个 `(gpu_id, pid)` 占了多少 GPU 内存？ |
| Trace 桥接 | `GpuMemTracer` | `GpuMem` 遍历同一份 BPF map | Perfetto data source `android.gpu.memory`，写入 `gpu_mem_total_event` | trace session 启动时各进程 GPU 内存快照是多少？ |
| 统计归因 | `GpuStats` | GL / Vulkan / ANGLE 驱动加载上报 | statsd pull atom、`dumpsys gpuservice --gpustats` | 哪类驱动加载了几次、耗时多少、失败多少？ |

这三层不是三套独立真相源。`GpuMem` 与 `GpuMemTracer` 共享 BPF map；`GpuStats` 则不直接统计显存字节，而是统计图形驱动加载路径。因此排查 GPU 内存泄漏时，应把 `GpuMem` / Perfetto 当作显存占用观测面，把 `GpuStats` 当作驱动选择与失败模式的归因补充。

## 14.30.2 GpuService 启动与初始化边界

`GpuService.cpp` 的构造函数同步创建核心对象，然后把可能阻塞的 BPF 初始化放到独立线程里：

```cpp
GpuService::GpuService()
    : mGpuMem(std::make_shared<GpuMem>()),
      mGpuWork(std::make_shared<gpuwork::GpuWork>()),
      mGpuStats(std::make_unique<GpuStats>()),
      mGpuMemTracer(std::make_unique<GpuMemTracer>()),
      mFeatureOverrideParser(kConfigFilePath) {
    mGpuMemAsyncInitThread = std::make_unique<std::thread>([this] {
        mGpuMem->initialize();
        mGpuMemTracer->initialize(mGpuMem);
    });
    mGpuWorkAsyncInitThread = std::make_unique<std::thread>([this] {
        mGpuWork->initialize();
    });
}
```

关键点有三条：

1. **GpuMem → GpuMemTracer 是串行依赖**：`GpuMemTracer::initialize()` 要求传入的 `GpuMem` 已经初始化成功，否则不能从 BPF map 读取初始 counter。
2. **GpuWork 独立并行**：GPU work period 的 BPF 聚合与 GPU memory total 的 BPF 聚合是两条互补链路，本章只把 GpuWork 作为旁路观测面引用。
3. **主服务启动不被 BPF attach 拖住**：`mGpuMem->initialize()` 可能等待 bpfloader 和 GPU tracepoint 就绪，放在 `mGpuMemAsyncInitThread` 中可避免阻塞 GpuService 构造返回。

析构期则反过来收束：`mGpuMem->stop()` 置停止标志，`~GpuMem()` 负责 `bpf_detach_tracepoint()`，GpuService 主线程再 `join()` 初始化线程，避免服务退出时留下未解绑的 tracepoint 句柄。

## 14.30.3 GpuMem：基于 eBPF 的进程级 GPU 内存快照

`GpuMem.h` 定义了本章最核心的一组常量：

```cpp
static constexpr char kGpuMemTraceGroup[]      = "gpu_mem";
static constexpr char kGpuMemTotalTracepoint[] = "gpu_mem_total";
static constexpr char kGpuMemTotalProgPath[]   =
    "/sys/fs/bpf/prog_gpuMem_tracepoint_gpu_mem_gpu_mem_total";
static constexpr char kGpuMemTotalMapPath[]    =
    "/sys/fs/bpf/map_gpuMem_gpu_mem_total_map";
static constexpr int  kGpuWaitTimeout          = 30;  // seconds
```

`GpuMem::initialize()` 的工作顺序是：

1. 调 `bpf::waitForProgsLoaded()` 等待系统 BPF 程序加载完成；
2. 从 `/sys/fs/bpf/prog_gpuMem_tracepoint_gpu_mem_gpu_mem_total` 取出 pinned BPF program fd；
3. 调 `bpf_attach_tracepoint(fd, "gpu_mem", "gpu_mem_total")` 绑定 GPU 驱动 tracepoint；
4. 如果 attach 失败，每秒重试，最多 30 秒，用来覆盖 GPU 驱动晚于 gpuservice 启动的窗口；
5. 打开只读 map 包装 `bpf::BpfMapRO<uint64_t, uint64_t>(kGpuMemTotalMapPath)`，最后把 `mInitialized` 置为 true。

用户态 map 选择 `BpfMapRO` 是重要安全边界：GpuService 只读，BPF 程序写，普通上层代码不能伪造 GPU 内存统计。

### BPF key 编码与 map 更新语义

`frameworks/native/services/gpuservice/bpfprogs/gpuMem.c` 给出了归因粒度上限：

```c
#define GPU_MEM_TOTAL_MAP_SIZE 1024

DEFINE_BPF_MAP_GRO(gpu_mem_total_map, HASH, uint64_t, uint64_t,
                   GPU_MEM_TOTAL_MAP_SIZE, AID_GRAPHICS);

struct gpu_mem_total_args {
    uint64_t ignore;
    uint32_t gpu_id;
    uint32_t pid;
    uint64_t size;
};

DEFINE_BPF_PROG("tracepoint/gpu_mem/gpu_mem_total", AID_ROOT, AID_GRAPHICS,
                tracepoint_gpu_mem_gpu_mem_total)
(struct gpu_mem_total_args* args) {
    uint64_t key = ((uint64_t)args->gpu_id << 32) | args->pid;
    uint64_t cur_val = args->size;
    /* cur_val == 0 时删除 key；否则 update / insert size */
}
```

这里的 key 是 `uint64_t = (gpu_id << 32) | pid`：高 32 位放 `gpu_id`，低 32 位放 `pid`。value 是该 GPU / 进程组合的当前总占用字节数。`cur_val == 0` 时 BPF 程序删除 map entry，因此“条目消失”可视为进程级 GPU 内存归零信号。

这也解释了 GpuMem 的边界：tracepoint payload 只有 `gpu_id`、`pid`、`size`，没有 dmabuf fd，也没有 buffer handle；`GPU_MEM_TOTAL_MAP_SIZE = 1024` 也明显面向“活跃 GPU 进程数”而不是“活跃 buffer 数”。所以 GpuMem 能回答“哪个进程占了多少 GPU 内存”，不能回答“哪一块 dmabuf / 哪个 BufferQueue slot 占得最多”。

## 14.30.4 dumpsys gpuservice：即时查询入口

`GpuService.cpp::doDump()` 对 shell / dump 权限调用方开放，调用方需要满足 `uid == AID_SHELL` 或持有 `android.permission.DUMP`。常用命令族如下：

| 命令 | 触发模块 | 用途 |
|---|---|---|
| `dumpsys gpuservice` | dumpAll=true，全部模块输出 | 一次性查看 GameDriverInfo、GpuMem、GpuStats、GpuWork |
| `dumpsys gpuservice --gpumem` | `mGpuMem->dump()` | 只看 `(gpu_id, pid)` GPU 内存快照 |
| `dumpsys gpuservice --gpustats` | `mGpuStats->dump()` | 只看 GL / Vulkan / ANGLE 驱动加载统计 |
| `dumpsys gpuservice --gpudriverinfo` | GameDriverInfo | 查看 `ro.gfx.driver.*` 相关驱动信息 |
| `dumpsys gpuservice --gpuwork` | `mGpuWork->dump()` | 查看 GPU work period 相关统计 |

`GpuMem::dump()` 中的两个边界输出很适合排查启动问题：

- `Failed to initialize GPU memory eBPF`：`mInitialized` 为 false 或 BPF map 无效，通常意味着 BPF 程序、tracepoint attach 或初始化时序未完成；
- `GPU memory total usage map is empty`：GpuMem 已初始化，但 GPU 驱动尚未上报非零条目，或当前没有活跃 GPU 内存占用。

排查建议：不要用单次 dumpsys 判断泄漏。`--gpumem` 是瞬时快照，应在场景前、中、后多次采样，关注同一 pid 的 `size` 是否随场景退出归零或回落。

## 14.30.5 GpuMemTracer：Perfetto 的启动期 GPU 内存快照

`GpuMemTracer` 把同一份 `GpuMem` map 以 Perfetto data source 暴露出去。`GpuMemTracer.h` 在 `android-17.0.0_r1` 中定义的数据源名是：

```cpp
static constexpr char kGpuMemDataSource[] = "android.gpu.memory";
```

初始化后，`GpuMemTracer` 启动一个分离线程：

```cpp
std::thread tracerThread(&GpuMemTracer::threadLoop, this, true);
pthread_setname_np(tracerThread.native_handle(), "GpuMemTracerThread");
tracerThread.detach();
```

线程通过静态 `sTraceMutex` / `sCondition` / `sTraceStarted` 等待 Perfetto session Start。每次 Start 只触发一次 `traceInitialCounters()`，后者遍历 `mGpuMem->traverseGpuMemTotals()` 并写出 `gpu_mem_total_event`：

```cpp
auto* event = packet->set_gpu_mem_total_event();
event->set_gpu_id(gpuId);
event->set_pid(pid);
event->set_size(size);
packet->set_timestamp_clock_id(
    perfetto::protos::pbzero::BUILTIN_CLOCK_MONOTONIC);
packet->set_timestamp(ts);
```

因此，Perfetto 里的 GPU memory 事件应理解为 **trace session 启动瞬间的全量快照**，不是持续 polling 形成的采样曲线。若要观察趋势，需要在合适时间点启动多次 trace，或结合其他连续 counter / SurfaceFlinger / meminfo 数据源进行对账。

## 14.30.6 GpuStats：statsd 驱动加载归因，不是显存字节统计

`GpuStats` 的重点不是“占了多少 GPU 内存”，而是“图形驱动加载路径发生了什么”。`GpuStats.h` 中有明确的容量约束：

```cpp
static const size_t MAX_NUM_LOADING_TIMES = 16;
static const size_t MAX_NUM_APP_RECORDS   = 100;
static const size_t APP_RECORD_HEADROOM   = 10;
```

源码注释说明这组配比让 GpuStats 内存占用保持在约 10KB 以内；当 app record 超限时，`purgeOldDriverStats()` 按 `lastAccessTime` LRU 淘汰最旧记录。

Android 17 里 ANGLE 被作为独立驱动分支统计：

```cpp
case GpuStatsInfo::Driver::ANGLE:
    outGlobalInfo->angleLoadingCount++;
    if (!isDriverLoaded) outGlobalInfo->angleLoadingFailureCount++;
    break;
```

应用维度还会用双重条件识别 ANGLE：

```cpp
appInfo.angleInUse =
    driver == GpuStatsInfo::Driver::ANGLE || driverPackageName == "angle";
```

这对兼容性排查很重要：ANGLE-on-Vulkan 引入了额外翻译层，失败可能发生在 ANGLE 自身、Vulkan 驱动或 feature override 配置之间。`angleLoadingCount` / `angleLoadingFailureCount` 不是 GPU 内存泄漏证据，但可以解释“为什么某个 app 的 GPU 路径与普通 GL / Vulkan app 不同”。

`toggleAngleAsSystemDriver(enabled)` 也体现了权限边界：只有 `AID_SYSTEM` 且持有 `android.permission.ACCESS_GPU_SERVICE` 的调用方可切换，开启时写入 `persist.graphics.egl=angle`。配套的 `/system/etc/angle/feature_config_vk.binarypb` 由 `mFeatureOverrideParser` 加载，形成“配置文件 → 系统属性 → 运行时统计”的闭环。

## 14.30.7 dmabuf 归因：GpuMem 只能给总账，buffer 级定位要换通路

GpuMem 的进程级 map 不包含 dmabuf 句柄，因此 dmabuf 归因必须做多源对账：

| 数据源 | 视角 | 适合回答 |
|---|---|---|
| `dumpsys gpuservice --gpumem` | GPU 驱动侧 `(gpu_id, pid)` 总账 | 哪个进程当前 GPU 内存总量异常？ |
| `dumpsys meminfo` / memtrack HAL | `MemtrackType::GL`、`MemtrackType::GRAPHICS`、PSS 拆分 | GPU private 与 graphics / dmabuf 映射如何分布？ |
| `dumpsys SurfaceFlinger --bufferstats` | BufferQueue / layer / buffer 实例 | 哪些可见或缓存 buffer 仍被持有？ |

`IMemtrack.aidl` 的文档给出了关键语义：`MemtrackType::GRAPHICS` 覆盖 CPU-mapped 与 GPU-mapped DMA-BUF 的 PSS 并去重；`MemtrackType::GL` 覆盖指定 PID 下未计入 `/proc/<pid>/smaps` 的 GPU private allocation；PID 0 的 GL 查询用于全局 GPU-private memory。也就是说，GpuMem 更像 GPU 驱动侧“总账”，memtrack 更像进程内存核算口径，SurfaceFlinger 则提供 buffer 生命周期线索。

一个安全的排查流程是：

1. 用 `dumpsys gpuservice --gpumem` 找出异常 pid 与 gpu_id；
2. 用 `dumpsys meminfo <pid>` 查看 GL / Graphics 行是否同步偏高；
3. 用 `dumpsys SurfaceFlinger --bufferstats` 观察对应进程 / layer 是否有异常缓存 buffer；
4. 若 Perfetto trace 已开启，把 `gpu_mem_total_event.pid` 与 frame timeline、process memory counter、SurfaceFlinger 事件放在同一时间线上解释。

需要注意：实际数值是否严格可对账，取决于厂商 GPU 驱动和 memtrack HAL 的实现质量。本章只根据 AOSP 接口与 GpuService 源码给出排查路径，不把未实测的厂商行为写成确定结论。

## 14.30.8 与 SurfaceFlinger / gfxinfo / memtrack 的职责边界

- **GpuService / GpuMem**：按 `(gpu_id, pid)` 暴露 GPU 驱动上报的总占用。它是系统级 GPU 内存总账入口。
- **GpuMemTracer / Perfetto**：把 GpuMem 快照带入 trace session，方便与调度、帧时间线、进程内存等信号同图分析。
- **GpuStats / statsd**：统计驱动加载路径和失败率，解释 GL / Vulkan / ANGLE 路径差异。
- **memtrack HAL / `dumpsys meminfo`**：从进程内存核算角度拆分 GL、Graphics、dmabuf 映射口径。
- **SurfaceFlinger / `--bufferstats`**：从 layer / BufferQueue 角度定位 buffer 生命周期与持有者。
- **gfxinfo / GraphicsStats**：偏向帧耗时、jank、渲染阶段统计，不等同于 GPU 内存总账。

因此，本章应与 §10.8、§14.8、§14.25 互补阅读：§10.8 偏应用 / 图形内存症状，§14.8 偏 GPU 调试工具链，§14.25 偏 eBPF 可观测性矩阵，本节则把 GpuService 这条 GPU 内存与驱动归因通路单独拆清。

## 14.30.9 待验证项与审稿关注点

以下内容仍需在后续 review / 实机审稿中确认，不能作为最终发布结论：

- **厂商驱动 tracepoint 支持差异**：Adreno、Mali、PowerVR 对 `gpu_mem/gpu_mem_total` 的上报完整度需要真机或对应内核源码确认。
- **Pixel Android 17 实测输出**：`dumpsys gpuservice --gpumem` 的实际字段、空 map 场景、权限失败提示仍需设备验证。
- **Perfetto UI 呈现路径**：源码确认数据源名与 `gpu_mem_total_event` 写入，但 UI 中如何落到 track / SQL 表需用 trace processor 或 Perfetto UI 实测。
- **dmabuf 数值对账精度**：GpuMem、memtrack、SurfaceFlinger 三者的对账路径成立，但具体数值一致性依赖厂商 HAL，不应脱离设备实测下结论。
- **ANGLE feature override schema**：本章只确认 GpuService 加载 `/system/etc/angle/feature_config_vk.binarypb` 与 GpuStats 的 ANGLE 分支；protobuf schema 与 denylist 细节留给 ANGLE 专章。
