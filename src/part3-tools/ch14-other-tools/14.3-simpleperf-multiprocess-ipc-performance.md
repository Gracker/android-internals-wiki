# 14.3 Simpleperf 多进程性能监控架构深度解析

本文解析 Android 17 Simpleperf 多进程性能监控的复杂 IPC 架构。Simpleperf 作为 Android 系统级性能分析工具，在多进程场景下需要同时处理采集效率、跨进程数据同步、内存占用三大矛盾。本文从底层 IPC 机制出发，深入解析其设计原理与性能边界。

## 1. 三层 IPC 生产者-消费者架构

Simpleperf 多进程监控采用「三层生产者-消费者 + 一条主控通路 + 一条跨文件合并」的复合架构。这一设计解决了监控高频率（4kHz×N核×N进程）与用户态处理性能之间的矛盾。

### 1.1 第一层：RecordReadThread 无锁环形缓冲区

**问题**：kernel perf event 的 mmap() 环形 buffer 在高采样率下会产生大量 POLLIN 事件，主线程既要采样又要处理其他事务会被压垮。

**方案**：RecordReadThread 用一条独立线程从所有 event_fd 拉数据，与主线程通过 4 个 IPC 资源通信：

| 资源 | 方向 | 用途 | 同步方式 |
|------|------|------|----------|
| `record_buffer_` | 读→主 | 无锁环形 buffer，存 perf_event_record 字节 | `std::atomic<size_t>` write_head/read_head |
| `cmd_pipe` | 主→读 | 发送命令（添加/移除 event fd、同步、停止） | `pipe2(O_CLOEXEC)` + 1 字节通知 |
| `data_pipe` | 读→主 | 主线程 epoll 通知："buffer 有新数据" | `pipe2(O_CLOEXEC)`，1 字节 edge-trigger |
| `kernel mmap buffer` | 内核→读 | perf event 自身环形 buffer，按 CPU 划分 | 内核 vs 用户态共享页 |

**关键代码**：
```cpp
bool RecordReadThread::RegisterDataCallback(IOEventLoop& loop,
                                           const std::function<bool()>& data_callback) {
  int cmd_fd[2], data_fd[2];
  if (pipe2(cmd_fd, O_CLOEXEC) != 0 || pipe2(data_fd, O_CLOEXEC) != 0) {
    return false;
  }
  // 建立双向管道，注册读线程
  read_cmd_fd_.reset(cmd_fd[0]);
  write_cmd_fd_.reset(cmd_fd[1]);
  read_data_fd_.reset(data_fd[0]);
  write_data_fd_.reset(data_fd[1]);
  // 注册数据回调
  return loop.AddReadEvent(read_data_fd_, data_callback);
}
```

**性能设计**：
- **阈值分层**：10MB 触发 backpressure，5MB 触发 hard pause
- **内存序优化**：`write_head_.store(release)` / `read_head_.load(acquire)` 配对
- **线程优先级**：设置 nice=-20（最高实时优先级）

### 1.2 第二层：MapRecordThread 并行 mmap 扫描

**问题**：system-wide 模式监控所有进程，每个进程的 mmap 列表都含数千个 VMA；ETM aux tracing 需要扫描所有进程。

**方案**：MapRecordThread 在后台持续写临时文件，录制结束后再读回主线程：

```cpp
class MapRecordThread {
 public:
  MapRecordThread(const MapRecordReader& map_record_reader);
  bool Join();  // 等待后台线程完成
  bool ReadMapRecordData(const std::function<bool(const char*, size_t)>& callback);
 private:
  bool RunThread();
  std::unique_ptr<TemporaryFile> tmpfile_;  // 临时文件
  std::unique_ptr<FILE, decltype(&fclose)> fp_;
  std::thread thread_;
  std::atomic<bool> early_stop_ = false;
};
```

**生命周期**：
1. **T0（录制开始）**：启动后台线程，持续写 mmap record
2. **T0~T_end**：与 RecordReadThread 并发执行
3. **T_end**：`Join()` 等待完成
4. **T_end（join 后）**：回灌到 `RecordFileWriter`

### 1.3 第三层：ProfileSession app 内嵌子进程

**问题**：Android 高 API 限制 app 直接 perf_event_open，需要把 simpleperf 以子进程形式运行。

**方案**：通过 `vfork` + `pipe` 在 app 进程内嵌 simpleperf：

```cpp
bool ProfileSessionImpl::CreateSimpleperfProcess() {
  // 1. 建立两条 pipe：control 和 reply
  int control_fd[2], reply_fd[2];
  pipe(control_fd);
  pipe(reply_fd);
  
  // 2. vfork 子进程
  int pid = vfork();
  if (pid == 0) {
    // child: 把 pipe 接到 stdin/stdout
    dup2(control_fd[0], 0);
    dup2(reply_fd[1], 1);
    execvp(simpleperf_path, argv);
  }
  
  // parent
  control_fd_ = control_fd[1];  // 保留写端
  reply_fd_ = reply_fd[0];      // 保留读端
  simpleperf_pid_ = pid;
}
```

**控制协议**：
- `pause` / `resume`：暂停/恢复录制
- `ok` / `started`：命令响应状态
- SIGINT：停止录制

## 2. 多进程数据整合分析流程

### 2.1 cmd_merge 跨文件合并协议

多进程录制生成多份 perf.data，需要合并成单文件供 Android Studio 消费。

**9 项一致性检查**：
```cpp
bool IsMergeable() {
  return CheckFeatureSection() && CheckAttrSection();
}
```

| 检查项 | 字段 | 不一致的处理 |
|--------|------|---------------|
| 1. arch | `FEAT_ARCH` | 直接拒绝 |
| 2. kernel version | `FEAT_OSRELEASE` | 直接拒绝 |
| 3. simpleperf version | meta info | 直接拒绝 |
| 4. trace_offcpu | meta info | 直接拒绝 |
| 5. event_types | meta info | 直接拒绝 |
| 6. android_device | meta info | 直接拒绝 |
| 7. android_version | meta info | 直接拒绝 |
| 8. app_package_name | meta info | 直接拒绝 |
| 9. clockid | meta info | 直接拒绝 |

**event_id 重映射**：
```cpp
// 合并新文件时重映射 event_id
const std::unordered_map<uint64_t, size_t>& cur_map = readers_[prev_reader_id]->EventIdMap();
const EventAttrIds& attrs = readers_[next_reader_id]->AttrSection();
for (size_t attr_id = 0; attr_id < attrs.size(); attr_id++) {
  for (uint64_t event_id : attrs[attr_id].ids) {
    if (auto it = cur_map.find(event_id); it == cur_map.end()) {
      EventIdRecord record(attr_id, event_id);  // 记录重映射关系
      ProcessRecord(&record);
    }
  }
}
```

### 2.2 RecordFileWriter zstd 流式压缩

**问题**：多进程 perf.data 通常 50-500MB，host 端传输慢；linux-tools-perf 限制单条 record ≤ 65535 字节。

**方案**：zstd 压缩 + 二级分包：

```cpp
bool RecordFileWriter::WriteRecord(const Record& record) {
  // 第一层：未压缩前分包（> 65535 时拆分）
  if (record.size() <= 65535) {
    return WriteData(record.Binary(), record.size());
  } else {
    // 拆分为 SIMPLE_PERF_RECORD_SPLIT ×N + _END
    const char* p = record.Binary();
    uint32_t left_bytes = static_cast<uint32_t>(record.size());
    while (left_bytes > 0) {
      uint32_t bytes_to_write = std::min(65535 - Record::header_size(), left_bytes);
      WriteSplitRecord(p, bytes_to_write);
      p += bytes_to_write;
      left_bytes -= bytes_to_write;
    }
    WriteSplitEndRecord();
  }
  
  // 第二层：zstd 输出分包（压缩后 > 65535 时再拆分）
  if (compressor_) {
    const char* p = output.data();
    size_t left_size = output.size();
    while (left_size >= 65535) {
      WriteCompressRecord(p, 65535, data_section);
      p += 65535;
      left_size -= 65535;
    }
    if (left_size > 0) {
      WriteCompressRecord(p, left_size, data_section);
    }
  }
}
```

### 2.3 ThreadTree::Update 跨进程 record 折叠

**核心机制**：
```cpp
void ThreadTree::Update(const Record& record) {
  if (record.type() == PERF_RECORD_MMAP) {
    const MmapRecord& r = *static_cast<const MmapRecord*>(&record);
    if (r.InKernel()) {
      AddKernelMap(r.data->addr, r.data->len, r.data->pgoff, r.filename);
    } else {
      AddThreadMap(r.data->pid, r.data->tid, r.data->addr, r.data->len, r.data->pgoff, r.filename);
    }
  } else if (record.type() == PERF_RECORD_FORK) {
    const ForkRecord& r = *static_cast<const ForkRecord*>(&record);
    ForkThread(r.data->pid, r.data->tid, r.data->ppid, r.data->ptid);
  }
}
```

**MapSet 共享优化**：
```cpp
ThreadEntry* ThreadTree::CreateThread(int pid, int tid) {
  const char* comm;
  std::shared_ptr<MapSet> maps;
  if (pid == tid) {  // 主线程
    comm = "unknown";
    maps.reset(new MapSet);
  } else {  // 同进程的其他线程：共享主线程的 MapSet
    ThreadEntry* process = FindThreadOrNew(pid, pid);
    comm = process->comm;
    maps = process->maps;  // 零拷贝共享
  }
  // ...
}
```

**ForkThread 机制**：
```cpp
bool ThreadTree::ForkThread(int pid, int tid, int ppid, int ptid) {
  ThreadEntry* parent = FindThreadOrNew(ppid, ptid);
  ThreadEntry* child = FindThreadOrNew(pid, tid);
  child->comm = parent->comm;
  if (pid != ppid) {  // 子进程：拷贝 MapSet
    if (child->maps->maps.empty()) {
      *child->maps = *parent->maps;  // 首次 fork 全量拷贝
    } else {
      // 后续 fork 增量合并
      for (auto& pair : parent->maps->maps) {
        InsertMap(*child->maps, *pair.second);
      }
    }
  }
  return true;
}
```

## 3. 端侧 AI 应用的多进程可观测性要点

### 3.1 NPU delegate 进程监控

**特点**：
- ML Kit / TFLite / MediaPipe 都会派生 NPU 专属进程
- 必须使用 `--app <pkg>` 模式才能捕获
- NPU 进程在主进程推理时显示 CPU idle

**关键设置**：
```bash
# 监控包含 NPU 进程的应用
simpleperf record --app com.example.mlapp -g
```

### 3.2 mmap record 占比问题

**现象**：NPU delegate 进程会 mmap 大量权重文件，一个 1GB 模型 ≈ 250k 个 mmap record 项。

**影响**：
- 未压缩时 mmap record 占 perf.data 头部 30-50%
- `adb pull` 瓶颈在 IO 而非 CPU

### 3.3 线程覆盖机制

**inherit=1** 特性：simpleperf 默认会自动监控子线程和派生线程。

```cpp
// event_selection_set.cpp
if (!event_selection_.inherit) {
  // 仅监控指定线程
} else {
  // 递归监控所有派生线程
}
```

这一机制确保能捕获到推理 worker 线程的热点。

### 3.4 跨进程数据合并限制

**规则**：cmd_merge 直接拒绝跨 app 合并。

```cpp
if (readers_[0]->GetAppPackageName() != readers_[i]->GetAppPackageName()) {
  LOG(ERROR) << "Cannot merge files from different packages";
  return false;
}
```

但同一 app 的主进程和 NPU 进程可以合并，因为它们的 `app_package_name` 相同。

## 4. 性能影响与优化建议

### 4.1 性能开销分析

| 场景 | IPC 开销 | 优化点 |
|------|----------|--------|
| 8 核 system-wide 4kHz 采样 | RecordReadThread ≤ 5% CPU | `ShareMappedBuffer` 减少 mmap |
| 5 进程 × 1000 线程 fork | `PERF_RECORD_FORK` 处理 ~10k/秒 | `std::shared_ptr<MapSet>` 共享 |
| app 内嵌 simpleperf | vfork + pipe < 8ms | pipe 直接走 fd 0/1 |
| 多文件 merge | 流式处理，内存峰值=单条 record | EventIdRecord 重映射 |
| ETM aux tracing 5 分钟 | perf.data ≈ 200-500MB | 独立压缩流处理 |

### 4.2 优化建议

#### 4.2.1 针对 AI 应用的建议

1. **监控策略选择**：
   - 短时间推理分析：`--app <pkg> -f 1000`（聚焦 NPU 进程）
   - 长期线上监控：`--system -f 100`（监控全局，降低开销）

2. **数据压缩**：
   ```bash
   # 启用 zstd 压缩
   simpleperf record --compress zstd -f 1000
   ```

3. **内存管理**：
   ```cpp
   // 对于大规模 mmap record，建议:
   // 1. 使用 --max-size 限制文件大小
   // 2. 定期触发 merge 避免内存累积
   simpleperf record --max-size 100M --compress zstd
   ```

#### 4.2.2 系统级优化

1. **Buffer 阈值调优**：
   ```cpp
   // 根据设备内存调整
   constexpr size_t kDefaultLowBufferLevel = 10 * 1024 * 1024;  // 10MB
   constexpr size_t kDefaultCriticalBufferLevel = 5 * 1024 * 1024;  // 5MB
   ```

2. **线程优先级**：
   ```cpp
   // RecordReadThread 优先级提升
   if (setpriority(PRIO_PROCESS, gettid(), -20) == 0) {
     // 成功设置为最高实时优先级
   }
   ```

## 5. 实战案例分析

### 5.1 TFLite 推理性能监控

**场景**：监控 TFLite 模型在 NPU 上的推理性能

**命令**：
```bash
# 启动监控
simpleperf record --app com.example.tfliteapp -g -f 4000 --trace-offcpu --post-unwind

# 分析 NPU 线程热点
simpleperf report --sort comm,tid,sym -g
```

**关键观察点**：
1. **推理主线程**：`tf-lite` tid 的 CPU 使用率
2. **NPU 通信线程**：与 vendor driver 交互的线程
3. **内存分配模式**：mmap 记录中的模型文件映射

### 5.2 多进程协作监控

**场景**：监控主进程与 NPU delegate 进程的交互

**方案**：
```bash
# 主进程监控
simpleperf record --app com.example.mlapp -f 2000 -g -o main.perf

# NPU 进程监控（单独记录）
adb shell "run-as com.example.mlapp /data/local/tmp/simpleperf record -f 3000 -g -o npu.perf"

# 合并分析
simpleperf merge main.perf npu.perf -o merged.perf
simpleperf report -g --sym cpuinfo
```

### 5.3 线程折叠分析

**工具**：使用 ThreadTree 分析跨进程关系

**代码**：
```cpp
// 分析进程间 fork 关系

  for (const auto& [pid, thread] : tree.GetRootThreads()) {
    if (thread->HasChildThreads()) {

    }
  }
}
```

## 6. 边界与限制

### 6.1 版本兼容性

| Android 版本 | 关键 IPC 变化 |
|-------------|---------------|
| API 24 (Android 7) | 引入 `PERF_RECORD_MMAP2` |
| API 28 (Android P) | simpleperf 二进制化 |
| API 31 (Android 12) | `MapRecordThread` 并行 mmap 扫描 |
| API 33 (Android 13) | ProfileSession 持久化授权 |
| API 36 (Android 16) | cmd_merge 9 项一致性检查 |
| API 37 (Android 17) | 无可见改动 |

### 6.2 技术限制

1. **ETM aux tracing 合并限制**：包含 auxtrace 的文件不能跨文件合并
2. **符号表冲突**：不同编译版本的同名函数会被识别为不同符号
3. **时间戳对齐**：跨进程录制的时间戳在不同 process space 中难以对齐

### 6.3 性能边界

1. **内存占用**：大规模监控时，RecordReadThread 的环形 buffer 可能达到 10MB+
2. **CPU 开销**：高频率采样（>4kHz）可能导致目标应用性能下降
3. **磁盘 I/O**：多进程录制生成大量小文件，影响存储性能

## 7. 总结

Simpleperf 的多进程 IPC 架构体现了 Android 系统性能分析工具的工程权衡：

1. **三层设计平衡了监控粒度与性能**：RecordReadThread 负责热路径性能，MapRecordThread 处理系统级信息，ProfileSession 支持应用集成

2. **无锁机制处理高并发**：环形缓冲区、原子操作、优先级提升确保在高采样率下保持响应

3. **数据合并协议确保兼容性**：9 项一致性检查和 EventIdRecord 重映射使得多进程数据能被标准工具消费

4. **内存共享优化减少开销**：MapSet 共享机制大幅降低跨进程 fork 时的内存拷贝成本

这种架构设计使得 Simpleperf 能够在 Android 多进程环境中提供细粒度的性能监控能力，同时保持对目标应用的最小干扰。对于端侧 AI 应用，理解这些底层机制有助于更准确地定位性能瓶颈和优化监控策略。
