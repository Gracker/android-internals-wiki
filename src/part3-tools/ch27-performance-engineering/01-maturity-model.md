# 性能工程成熟度模型

<!-- outline-start -->
## 本节要点大纲

### 锚点（必须覆盖）

- 性能工程成熟度用于判断团队能否稳定发现、评估、修复和预防性能退化。
- 模型应按性能域拆分自评，不应把组织简单贴成一个等级。
- Android 语境下的成熟度要映射到启动、流畅性、内存、功耗、包体积和线上可观测性。
- ThoughtWorks 模型中的 DevPerfOps、性能建模、性能观测、看护定界、知识库和自助工具链，需要落到研发流程。
- 成熟度提升应从一个高影响性能域切入，再复制预算、CI、看板和复盘能力。

<!-- outline-end -->

性能工程成熟度模型用于回答一个管理层和技术团队都会反复遇到的问题：团队现在靠什么保证性能，下一步该补哪块能力。Android 团队常把性能理解为专项优化，但专项只能解决某个版本、某个页面、某类机型的问题；成熟度模型关注的是团队能否稳定发现、评估、修复和预防性能退化。

这里采用 L0 到 L4 五级模型，借鉴性能工程成熟度模型的分层思想，并按 Android 产品交付方式重新解释。它更像自评地图，不承担认证或排名功能。一个团队可能在启动治理上达到 L3，在内存治理上仍停在 L1；成熟度要按性能域、业务线和平台能力分别看。

ThoughtWorks 的性能工程成熟度模型强调的是一套完整能力链：通过 DevPerfOps 反馈系统，把性能建模、性能测试、观测看护、问题定界、分析优化和知识积累连起来。Android 团队应用时，可以把这套体系翻译成四类资产：可执行的场景模型、可复现的 benchmark、可追踪的线上指标、可复用的诊断 playbook。没有这些资产，成熟度很容易停留在口号上。

## L0 Initial：初始级

L0 团队的典型特征是反应式救火。线上用户反馈“卡”“慢”“耗电”，版本群里临时拉人看日志，性能工程师临时抓 Perfetto、Android Studio Profiler 或 Matrix 数据定位。问题解决后，经验停留在当事人的聊天记录和脑子里，下个版本还会以相似方式复发。

Android 团队里的常见模式包括：启动慢靠删除几个初始化任务，滑动卡顿靠临时减少图片尺寸，OOM 靠调大缓存或降低列表预加载数量，功耗问题靠关掉某个后台轮询。这些动作可能有效，但没有稳定基线，也缺少复现脚本，后续无法判断修复是否被新代码抵消。

L0 的关键实践是把“能复现、能度量、能归档”补起来，而不是急着引入一堆工具。每个性能事故至少记录设备、系统版本、App 版本、入口路径、指标变化、trace 文件位置和修复 PR。最小可行的升级动作是建立性能问题模板，并把启动、首页滑动、核心交易路径做成固定测试脚本。

## L1 Managed：管理级

L1 团队已经有基础测试和监控，但流程仍偏被动。测试同学可能在版本末期跑一次 Monkey、PerfDog 或自研脚本，客户端接入了 Android Vitals、Firebase Performance、Matrix、KOOM 或商业 APM，线上能看到 crash、ANR、启动和页面耗时。问题在于这些数据主要用于发布后观察，很少进入需求、设计和代码评审。

这一层的 Android 团队通常会有“重点机型测试清单”和“版本性能报告”。报告能指出某版本启动 P95 上涨、某页面 jank rate 变差、某 ROM 上 OOM 增多，但责任边界不清：是业务代码、图片资源、后端接口、实验配置，还是系统兼容性导致？没有 owner 时，性能问题会在版本压力下被推迟。

从 L1 升级到 L2，要把测试活动变成标准流程。每个重要页面需要定义进入路径、准备数据、度量指标和通过条件；每个版本需要固定比较上一个稳定版本；每个性能问题需要绑定 owner、截止时间和验收方式。15.10 中的性能治理可以从这里开始：预算、基线和发布门禁先覆盖少量核心路径，再逐步扩展。

## L2 Defined：规范级

L2 团队有统一流程，性能开始左移。需求评审会讨论“这个页面是否需要分页”“图片是否允许首屏加载原图”“动画是否会占用主线程”；技术设计会评估缓存、数据库查询、导航层级和后台任务；代码评审会检查主线程 I/O、同步 Binder 调用、Bitmap 分配、Compose recomposition 和 RecyclerView diff 策略。

这一层的标志是性能预算被写进工程规则。启动预算可能定义为冷启动 P50 小于 1200 ms、P95 小于 2500 ms；帧预算可能定义为核心列表 frozen frame 占比低于 0.1%，slow frame 占比低于 3%；内存预算可能按页面规定 Java heap、native heap 和图片缓存上限。预算的重点是可执行：CI、测试报告和代码评审都能引用同一套阈值。

L2 的风险是流程存在但执行质量不稳定。模板很多，数据很多，但团队仍可能在版本末期才发现回归。升级方向是把人工检查转成自动检查，把“是否变差”的判断转成趋势分析。15.9 的观测体系在这一层会开始成形：线下基准、灰度指标、线上报警和缺陷系统之间要能互相引用。

## L3 Quantitatively Managed：量化管理级

L3 团队用 SLO 和自动化回归检测管理性能。性能判断开始依赖用户群体、设备分层和版本趋势，单次测试结果只作为证据之一。启动、流畅性、内存、网络、功耗、包体积都有固定仪表盘；每个指标知道采样口径、统计窗口、告警阈值和 owner。

Android 侧的典型能力包括：Macrobenchmark 在 nightly 或合入前运行，启动和关键交互有稳定设备池；APK Analyzer 或 bundletool 检查每个模块的包体积增长；LeakCanary、KOOM 或自研内存巡检能在预发环境发现泄漏；Android Vitals、ApplicationExitInfo、FrameMetrics、JankStats 和自研埋点进入同一套分析视图。26.1 的可观测性架构在这里承担数据层职责。

L3 的工程判断更依赖统计。一次 benchmark 失败不直接阻断发布，需要看重复次数、设备温度、方差、历史趋势和变更范围；线上 P95 上涨也不直接指向客户端，需要按机型、国家、网络、实验桶、后端版本拆分。量化管理级的升级重点是减少误报和漏报，让性能报警能自动关联版本、commit、实验和 trace。

## L4 Optimizing：持续优化级

L4 团队把性能做成产品研发文化的一部分。性能指标进入产品目标，设计、后端、客户端、QA 和数据团队都知道自己的影响面；性能工程师从救火角色转向平台、规则、工具和训练机制建设。团队能从线上信号自动生成候选问题，自动拉取诊断数据，自动创建 issue，甚至在部分场景中通过远程配置降级风险能力。

Android 场景里的 L4 不等于所有指标都完美，而是团队具备持续改进能力。比如发现某类低端机冷启动受广告 SDK 初始化影响，系统会自动定位到启动阶段 trace、实验配置、SDK 版本和设备段；短期通过远程开关延后初始化，中期给 SDK 接入方设预算，长期把启动任务编排接入平台能力。

L4 的难点在组织层。性能文化要避免变成“性能团队检查所有人”。更有效的方式是让每个业务团队有 performance champion，平台团队提供 benchmark-as-code、预算校验、仪表盘和培训材料，管理层看 SLO 与用户指标，研发团队在日常评审里使用同一套语言。

## 自评矩阵

| 维度 | L0 | L1 | L2 | L3 | L4 |
|---|---|---|---|---|---|
| 指标 | 主要靠用户反馈 | 有基础监控 | 指标口径统一 | SLO 分层管理 | 指标驱动持续改进 |
| 测试 | 临时复现 | 版本末期测试 | 固定场景和基线 | 自动回归检测 | benchmark-as-code 平台化 |
| 流程 | 救火为主 | 有报告无门禁 | 预算进入评审 | 发布门禁稳定执行 | 需求到运营全流程使用 |
| 工具 | 个人工具箱 | APM 和测试工具接入 | 工具标准化 | 数据自动关联 | 自愈、降级和自动派单 |
| 组织 | 依赖少数高手 | 有兼职 owner | 明确责任边界 | 指标 owner 固定 | performance champion 网络 |

自评时可以用下面这组问题快速定位：

- 团队能否在 30 分钟内找到上个稳定版本的启动、帧率、内存和包体积基线？
- 每个核心页面是否有明确性能预算，预算是否会影响合入或发布决策？
- 线上性能回归是否能关联到版本、实验、设备段和疑似 commit？
- 性能问题修复后，是否有自动化用例防止同类问题回归？
- 业务团队是否能独立解释自己模块对启动、内存、网络和功耗的影响？

成熟度提升通常不按整级跳跃。比较稳的路径是：先选一个用户影响最大的性能域，例如冷启动或首页流畅性；把它做到 L2 或 L3；再把预算、CI、看板和复盘模板复制到其他性能域。模型的价值不在“评到几级”，而在让团队清楚下一项能力该建在哪里。
