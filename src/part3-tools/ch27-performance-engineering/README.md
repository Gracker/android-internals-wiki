# 第 27 章：性能工程体系

<!-- outline-start -->
## 本章要点

### 为什么需要性能工程

- 🔹 单兵作战的性能优化无法规模化——从"高手经验"到"工程体系"
- 🔹 性能不是上线后的事——它应该贯穿需求、设计、开发、测试、发布的全生命周期
- 🔹 成熟度模型帮助团队定位当前位置，明确演进路径

### 章节概览

- **27.1 性能工程成熟度模型**：从反应式救火到持续优化的五个等级，帮助团队自评和制定演进路线
- **27.2 性能策略制定与路线图**：如何定义性能愿景、拆解目标、排布季度路线图
- **27.3 性能预算体系**：从帧预算、内存预算到启动预算，建立可度量的性能约束
- **27.4 左移性能工程**：将性能关注点前移到设计评审、代码审查和日常开发中
- **27.5 持续性能验证与 CI/CD**：自动化性能回归检测、基线对比与发布门禁
- **27.6 性能文化构建与团队演进**：从组织结构、考核机制到知识传承的性能文化建设
<!-- outline-end -->

## 导读

前面各章已经详细介绍了 Android 性能的各个技术维度——流畅性、响应速度、内存、功耗、渲染、I/O、可观测性等。第 15 章讨论了性能方法论，第 19 章覆盖了 APM 工具生态。但一个现实问题是：**知道怎么做优化，和能在组织中持续做好优化，是两回事**。

本章关注的是"性能工程"（Performance Engineering）这个工程学科——不是某个具体的优化技巧，而是**如何将性能系统性嵌入软件开发的整个生命周期**。

传统的性能工作往往停留在"出问题了再修"的 reactive 模式。而性能工程强调：

1. **前置**：在需求和设计阶段就考虑性能影响
2. **量化**：用可度量的指标和预算代替"感觉快了"
3. **自动化**：通过 CI/CD 集成让性能回归无处遁形
4. **持续**：建立反馈闭环，每个迭代都在改进

本章借鉴性能工程成熟度模型的分层思想，并结合 Android 生态的实践经验，提供一个从 Level 0 到 Level 4 的改编框架。它不是对某个外部模型的逐条翻译，而是面向 Android 团队的自评和演进地图：无论团队当前处于哪个阶段，都可以找到明确的下一步行动。
