# 13.21 Perfetto 版本演进与 Android 9-17 新特性验证

## Perfetto 版本可用性时间线

Perfetto 从 Android 9（API 28）首次引入至今，经历了从基础 ftrace 采集到完整多数据源平台的演进。基于 AOSP `android-17.0.0_r1` 源码验证，版本时间线如下：

**Android 9 (API 28)**：基础服务首次引入
- Perfetto 首次进入 AOSP（`external/perfetto/Android.bp`），`src/traced/`、`src/perfetto_cmd/`、`src/probes/` 三类核心组件入树
- 提供基础的 ftrace 数据采集能力
- **默认禁用**，需要系统属性手动启用

**Android 10 (API 29)**：完整功能可用 + 默认启用
- Perfetto 服务与命令行工具首次默认启用
- 新增 `android.power` 数据源（`probes_producer.cc` include 列表）
- 提供稳定的 Java API 接口供应用层使用

**Android 11 (API 30)**：服务化完善
- Perfetto 成为系统级标准服务
- 稳定性提升：修复早期版本的内存泄漏和性能问题
- 保持与 Systrace 的向后兼容

**Android 12 (API 31)**：冻结进程 ftrace 与 per-UID CPU 统计
- 引入 `linux.ftrace_frozen`（冻结进程 ftrace）和 `android.cpu_per_uid`（per-UID CPU 统计）数据源
- release 构建 profiling 入口继续受 `<profileable>` / `profileable_from_shell` 等权限门控影响

**Android 13 (API 33)**：场景感知数据源
- 新增 `android.aflags`（features.xml 开关状态）和 `android.game_intervention_list`（Game Mode 干预策略）两个"场景感知"数据源
- FrameTimeline 跟踪能力进入 SurfaceFlinger/Scheduler，Android 17 基线实现位于 `Scheduler/FrameTimeline.{h,cpp}`

**Android 14-16 (API 34-36)**：持续增强
- 大数据文件处理性能优化
- per-display FrameTimeline 完善：每个 Display 独立 FrameTimeline 实例，VSync 偏移经由 `Scheduler/MessageQueue.cpp` 分派
- 与单显示器场景的区别：跨显示器帧匹配需通过 `Scheduler` 统一调度

**Android 17 (API 37)**：主线完整状态
- 19 个 ProbesProducer 数据源全部就绪（详见下文数据源清单）
- `Scheduler/FrameTimeline.cpp` 与 `FrameTracer/FrameTracer.cpp` 分别注册 FrameTimeline 与 SurfaceFlinger frame 数据源（详见 2.30 章对 FrameTimeline GPU/CPU 合成边界的分析）

**源码验证**：
```cpp
// external/perfetto/src/perfetto_cmd/main.cc — android-17.0.0_r1
int main(int argc, char** argv) {
    // Android 17 中的 Perfetto 命令行入口
    // 服务端（traced/traced_probes）由 init 拉起，perfetto 命令用于配置和控制
}
```

> 注：`debug.perfetto.enabled` 在 Android 17 中已部分被 DeviceConfig 机制替代（`perfetto_guardrail_config`），命令行动态启用依赖系统属性命名空间而非单一开关。

## 数据源演进历程

Perfetto 的数据源架构随 Android 版本迭代逐步扩展。经 `android-17.0.0_r1` 源码验证，**Android 17 Android build 实际注册 19 个 ProbesProducer 数据源**，覆盖内核/系统、用户态桥接、平台定制与自描述 metatrace。

**ProbesProducer 数据源完整清单**（`external/perfetto/src/traced/probes/probes_producer.cc` + 子目录扫描）：

| 类别 | 数据源名 | 用途 |
|------|----------|------|
| 内核/系统 | `linux.ftrace` | 内核函数追踪（atrace 类别枚举驱动） |
| 内核/系统 | `linux.ftrace_frozen` | 冻结进程的 ftrace 事件（Android 12+） |
| 内核/系统 | `android.process_stats` | 进程级 CPU/内存统计 |
| 内核/系统 | `android.sys_stats` | 系统级 CPU / I/O 统计 |
| 内核/系统 | `android.power` | Android 电源状态（BatteryStats） |
| 内核/系统 | `linux.power` | Linux 内核电源事件 |
| 内核/系统 | `android.system_info` | 系统版本/构建信息 |
| 内核/系统 | `android.system_property` | 系统属性快照 |
| 用户态桥接 | `android.statsd` | Statsd 指标桥接 |
| 用户态桥接 | `android.log` | logcat 桥接 |
| 用户态桥接 | `android.packages_list` | 已安装应用列表 |
| 用户态桥接 | `android.kernel_wakelocks` | 内核 wakelock 事件 |
| 用户态桥接 | `android.user_list` | 多用户列表 |
| 用户态桥接 | `android.initial_display_state` | 初始显示状态 |

| 平台定制 | `android.aflags` | features.xml 开关状态（Android 13+） |

**各版本新增数据源对照**（基于 `android-17.0.0_r1` 源码 + `git log --diff-filter=A` 追溯）：

| Android 版本 (API) | 新增数据源 | 新增数 | 累计 |
|---|---|---|---|
| 9 (28) | linux.ftrace, process_stats, sys_stats | 3+ | ~5 |
| 10 (29) | android.power | +1 | ~6+ |
| 12 (31) | linux.ftrace_frozen, android.cpu_per_uid | +2 | ~10+ |
| 13 (33) | android.aflags, android.game_intervention_list | +2 | ~14+ |
| 17 (37) | 补全至完整 19 个 ProbesProducer 数据源 | — | 19 |

> 注：API 32（12L）与 API 34/35/36 的中间版本差异未经逐 tag `git log --diff-filter=A` 验证，上表仅标注已验证 tag 的确定性数据。完整逐版本追溯建议在下一轮 DeepResearch 中补齐。

## ftrace 与 atrace 的集成机制

Perfetto 没有重写 atrace 的用户态标签系统（`ATRACE_BEGIN` 宏仍由 `libcutils` / 原生 `atrace` 维护）。两者的协作方式如下（`ftrace_data_source.cc:55-77`）：

```cpp
base::Subprocess p({"/system/bin/atrace", "--list_categories"});
// 解析 "name - description" 行，写入 FtraceDescriptor.atrace_categories
```

Perfetto 在注册时**枚举** atrace 类别，记录时**借用** atrace 启动/停止 ftrace events 的副作用。这解释了为什么 `systrace.py` 与 `perfetto` 命令在类别语义上部分兼容——内核事件集与用户态标签都来自同一份 atrace 清单。

## heapprofd 深度分析

在 Android 17 基线中，heapprofd 是独立的二进制程序（不由 `traced_probes` 管理，由 Android `init` 拉起），内部集成**双 producer 模型**（`src/profiling/memory/heapprofd.cc:65-95`）。历史 tag 对照显示，Native heapprofd 路径至少可追溯到 Android 10，`JavaHprofProducer` 至少可追溯到 Android 11，因此不能把 heapprofd 起点写成 Android 12：

| Producer | 信号 | 数据源名 | 用途 |
|---|---|---|---|
| `HeapprofdProducer` | `__SIGRTMIN + 4` | `android.heapprofd` | Native 调用栈采样 |
| `JavaHprofProducer` | `__SIGRTMIN + 6` | `android.java_hprof` | Java HPROF 周期 dump |

**关键参数**（`heapprofd_producer.cc:55-61`）：

```cpp
constexpr size_t kUnwinderThreads = 5;
constexpr uint64_t kDefaultShmemSize = 8 * 1048576;   // 8 MB
constexpr uint64_t kMaxShmemSize = 500 * 1048576;     // 500 MB
```

- **共享内存**：默认 8 MB，最大 500 MB（可配置）
- **Unwinder 线程池**：5 个线程并行 unwind，保证采样吞吐
- **信号通信**：`__SIGRTMIN+4` 用于 Native 采样控制，`__SIGRTMIN+6` 用于 Java HPROF dump

**JavaHprof 周期 dump 调度**（`java_hprof_producer.cc:38-56`）：

```cpp
ds.SendSignal();  // sigqueue(pid, __SIGRTMIN+6, {session_id})
task_runner_->PostDelayedTask(
    [weak_producer, id, dump_interval] {
      weak_producer->DoContinuousDump(id, dump_interval);
    },
    dump_interval);
```

`dump_interval_ms` 与 `dump_phase_ms` 双参数使多 session 错峰触发，避免信号风暴。

**与传统 HPROF 的对比**：

| 特性 | HPROF | heapprofd |
|---|---|---|
| **分析方式** | 静态快照（触发一次 dump） | 实时追踪（连续采样） |
| **内存开销** | dump 时内存峰值可达应用内存的 2-3 倍 | 运行时固定 8 MB 共享内存 + unwinder 线程栈 |
| **分析粒度** | 对象级（所有可达对象） | 分配点级（调用栈 + 分配大小） |
| **时间维度** | 单次快照 | 时间序列分析 |
| **过滤能力** | 无（dump 全部堆） | 按包名/对象类型/profiling 间隔过滤 |
| **兼容性** | Android 1.0+ | Native heapprofd Android 10+；Java HPROF Android 11+ |

**使用示例**：

```bash
# 启动 heapprofd 追踪（指定 pid + 过滤包名）
perfetto -c - <<EOF
buffers: { size_kb: 65536 }
data_sources: {
  config {
    name: "android.heapprofd"
    heapprofd_config {
      process_cmdline: "com.example.app"
      sampling_interval_bytes: 4096
      shmem_size_bytes: 8388608
    }
  }
}
duration_ms: 30000
EOF
```

**限制条件**：
- Native heapprofd 需 Android 10+；Java HPROF producer 需 Android 11+；本节参数按 Android 17 验证
- 需要 system 或 debug 权限
- 长时间追踪可能产生 GB 级文件（需控制采样间隔和持续时间）

**优化建议**：
- 使用过滤条件（`process_cmdline`）仅追踪目标进程
- 控制 `sampling_interval_bytes`：值越大采样越稀疏，开销越低
- 使用增量模式减少重复分析

## FrameTimeline 集成

FrameTimeline 是 Android 13+ 中的核心渲染追踪功能，通过 Perfetto 实现渲染管线的端到端追踪。

**追踪范围**：
- **UI 线程**：布局、绘制、动画执行
- **渲染线程**：Layer 处理、缓冲区管理
- **GPU 线程**：GPU 渲染管线执行
- **SurfaceFlinger**：图层合成与显示输出

**与 SurfaceFlinger 的协同工作**：

```
应用层请求绘制 → SurfaceFlinger 图层管理 → Perfetto 事件记录
     ↓                    ↓                       ↓
  VSync 信号         缓冲区分配/释放          FrameTimeline 事件
```

**关键协同点**：
- **VSync 信号**：SurfaceFlinger 发送的 VSync 事件是帧时间线的基准
- **图层状态**：图层创建、更新、销毁事件
- **缓冲区管理**：缓冲区分配、获取、释放事件
- **栅栏同步**：Fence 事件的创建与等待

Android 17 中，FrameTimeline 的 SurfaceFlinger 侧实现位于 `frameworks/native/services/surfaceflinger/Scheduler/FrameTimeline.{h,cpp}`，`FrameTimeline::registerDataSource()` 注册 `android.surfaceflinger.frametimeline`；`FrameTracer/FrameTracer.{h,cpp}` 注册 `android.surfaceflinger.frame`。多显示器场景的分析应以 trace 中的 DisplayFrame / SurfaceFrame 事件和显示器分组为准，跨显示器帧匹配需回到 `Scheduler/FrameTimeline.cpp` 的 token 与时间戳逻辑核对（详见 2.30 章对 FrameTimeline GPU/CPU 合成边界的分析）。

**SurfaceFlinger 集成源码锚点**：
```cpp
// frameworks/native/services/surfaceflinger/Scheduler/FrameTimeline.cpp — android-17.0.0_r1
void FrameTimeline::registerDataSource() {
    perfetto::DataSourceDescriptor dsd;
    dsd.set_name(kFrameTimelineDataSource); // android.surfaceflinger.frametimeline
    FrameTimelineDataSource::Register(dsd);
}
```

**FrameTimeline trace 观察入口**：
- Perfetto UI 中，FrameTimeline 呈现为 SurfaceFlinger track 下按 Display 分组的帧轨道，超 deadline 的帧以红色标记
- trace_processor 中通过 `actual_frame_timeline_slice` 表查询帧的实际呈现时间戳与预期 deadline 的偏差
- 多显示器场景下每个 Display 的帧轨道独立排列，可在 UI 中直接对比各 Display 的 jank 分布

## 性能优化与最佳实践

Perfetto 的大文件处理和实时分析需要针对性的配置策略。

**大型追踪文件的处理**：

| 优化维度 | 策略 | 说明 |
|----------|------|------|
| 缓冲区 | config 内 `buffers { size_kb: N }` | 根据追踪时长和目标事件密度调整 |
| 压缩 | trace 文件默认 deflate 压缩 | 无需手动指定，写入时自动压缩 |
| 分段 | 分次采集 | 避免单文件过大（建议单文件 < 1 GB） |
| 增量 | 增量模式 | 仅采集变化部分 |

```bash
# 通过 config 文件设置缓冲区（KB）和时长（ms），CLI 无 --buffer-size flag
perfetto -c trace_config.txt -o trace.perfetto
# trace_config.txt 内：buffers { size_kb: 262144 }  duration_ms: 30000
```

**实时追踪配置**：

```bash
# 限时追踪：-t 指定秒数，缓冲区在 config 中配置
perfetto -c real_time_config.txt -t 300 -o real_time_trace.perfetto
```

**追踪数据的存储与导出**：
- **本地存储**：设备本地用于实时分析
- **云端存储**：上传到云端进行长期分析
- **导出格式**：Perfetto 原生格式（完整功能）、Systrace 兼容格式（HTML）、JSON/CSV（程序化处理）

**最佳实践**：
- 控制单次追踪时长：推荐 ≤ 5 分钟
- 按数据敏感级别控制访问权限

## 与 Systrace 的对比

Perfetto 与 Systrace 各有适用场景，以下对比基于实际功能差异：

| 维度 | Perfetto | Systrace |
|------|----------|----------|
| **数据源** | 多数据源架构（19 个 ProbesProducer + traced + heapprofd 等独立二进制） | ftrace + atrace 类别 |
| **兼容性** | Android 9（API 28）+ | Android 1.0+ |
| **大文件处理** | 支持 1 GB+，SQL 查询引擎 | 受限于 HTML 渲染，建议 < 100 MB |
| **分析方式** | SQL 查询 + Web UI | 可视化时间线 |
| **扩展性** | protobuf 定义可扩展数据源 | 固定的 ftrace/atrace 类别 |
| **部署** | 服务端/设备端分离架构 | 一体化 Python 脚本 |

**从 Systrace 到 Perfetto 的迁移**：

```bash
# Systrace（-b 单位为 KB，8192 = 8 MB）
systrace -b 8192 -o trace.html -t 30 sched freq gfx view wm

# 等效 Perfetto（size_kb 单位同为 KB）
perfetto -c - <<EOF
buffers: { size_kb: 8192 }
data_sources: { config { name: "linux.ftrace" ftrace_config { atrace_categories: "sched" atrace_categories: "freq" atrace_categories: "gfx" atrace_categories: "view" atrace_categories: "wm" } } }
duration_ms: 30000
EOF
```

**迁移建议**：
- 短期：Systrace 和 Perfetto 并存，旧项目继续用 Systrace
- 长期：逐步迁移到 Perfetto（SQL 查询能力是主要优势）
- CI/CD：Perfetto 更易于脚本化集成

## 扩展

### 🔸 企业级部署考量

企业环境下的 Perfetto 部署需关注配置管理和合规要求。

**配置管理**：
- 通过 MDM 或配置服务器集中下发 perfetto 配置
- 配置文件版本控制（开发/测试/生产环境差异化）
- 按应用类型设定不同监控策略（游戏 vs 工具类应用）

**安全与隐私**：
- 传输和存储加密
- 基于角色的访问控制（RBAC）
- 敏感数据脱敏处理
- 遵循最小权限原则

**部署架构**：
- **边缘采集**：设备本地采集，仅上传分析结果
- **集中上报**：trace 数据统一上报到分析服务
- **混合模式**：实时分析在边缘、历史分析在云端
- 监控指标：设备覆盖率、数据完整性、端到端延迟

## 总结

从 Android 9 的基础 ftrace 采集起步，到 Android 17，Perfetto 已发展为覆盖 19 个 ProbesProducer 数据源、heapprofd 双 producer 堆分析、FrameTimeline 渲染管线追踪的完整性能分析平台。其架构特点在于：数据源以 protobuf 定义、SQL 查询引擎支持任意维度分析、生产者和消费者分离使定制数据源容易集成。

对开发者而言，Perfetto 的核心价值不在于数据源数量，而在于 SQL 分析能力和可扩展架构——理解数据源覆盖什么、SQL 能回答什么问题，远比记住数据源总数重要。





## heapprofd 生产环境部署模式

基线版本：`android-17.0.0_r1`，`external/perfetto` commit `201a16e409911aa016522a95143af2e5d52a3662`。报告：`DeepResearch/2026-07-03-android17-heapprofd-production-deployment.md`。

### 默认部署：init 阶段完全不拉起

`external/perfetto/heapprofd.rc` 是 Android 主线的 heapprofd 服务段，关键事实：

- **`disabled`**：init.rc 中未触发自动 start；不会被 class `late_start` 隐式拉起。
- **`user nobody`**：运行身份是 nobody，不在 `/data/local/tmp` 之外的任何位置写文件；HPROF/原生 dump 文件必须由 traced 端落盘。
- **`capabilities KILL DAC_READ_SEARCH`**：`DAC_READ_SEARCH` 在 user 构建上被 SELinux 强制 `userdebug_or_eng` 拒绝，因此 user 构建上 heapprofd 不能 `open(/proc/<pid>/mem)` 也就不能 unwind 任意进程——只能通过 `CanProfileAndroid` 过滤后的目标。
- **`onrestart --cleanup-after-crash`**：崩溃时调 `heapprofd.cc:107-114` 的 `SystemProperties::ResetHeapprofdProperties()`，清空被该 daemon 写入的 system property 避免污染下次启动。

### 启动路径：两条 sysprop 触发线

`external/perfetto/src/traced/service/builtin_producer.cc:39-90, 140-160`：

```
perfetto CLI / SDK
  → traced (TracingService)
    → BuiltinProducer::SetupDataSource(name="android.heapprofd")
      → SetAndroidProperty("traced.lazy.heapprofd", "1")
        → init property service
          → heapprofd.rc on property 触发 → service start heapprofd
            → HeapprofdMain → StartCentralHeapprofd
              → HeapprofdProducer::ConnectWithRetries(GetProducerSocket())
                → traced 注册 android.heapprofd 数据源
```

session 结束时反向：`MaybeInitiateLazyStop` 在 `lazy_heapprofd_.instance_ids` 清空后**延迟** `stop_delay_ms`（默认 5 秒，由 `traced --lazy-stop-daemon-delay-ms` 控制）清空 property，避免短间隔连续 trace 频繁启停 daemon。

### Java HPROF 信号机制

`java_hprof_producer.cc:35-58`：

```cpp
constexpr int kJavaHeapprofdSignal = __SIGRTMIN + 6;
constexpr const char* kJavaHprofDataSource = "android.java_hprof";

void JavaHprofProducer::DataSource::SendSignal() const {
  for (pid_t pid : pids_) {
    auto opt_status = ReadStatus(pid);
    auto uids = GetUids(*opt_status);
    if (!CanProfile(ds_config_, uids->effective, config_.target_installed_by())) {
      PERFETTO_ELOG("%d (UID %" PRIu64 ") not profileable.", pid, uids->effective);
      continue;
    }
    union sigval signal_value;
    signal_value.sival_int = static_cast<int32_t>(
        ds_config_.tracing_session_id() % std::numeric_limits<int32_t>::max());
    sigqueue(pid, kJavaHeapprofdSignal, signal_value);
  }
}
```

`session_id` 通过 `sival_int` 传入是为让目标进程（ART signal_chained_handler）识别本次 dump 属于哪个 session，避免多 session 并发混淆。与 `__SIGRTMIN + 4`（`HeapprofdProducer`，fork 模式走 unwinder 线程池）不同。

### 权限决策表（user 构建）

`producer_support.cc:96-187` 的 `CanProfileAndroid`：

| 目标 UID | session_initiator | 是否允许 | 所需标志 |
|---|---|---|---|
| 平台进程（UID<10000） | UNSPECIFIED | ❌ | — |
| 平台进程（UID<10000） | TRUSTED_SYSTEM | ✅ | — |
| 普通 app（10000-19999） | UNSPECIFIED | ⚠️ | `<profileable android:shell="true"/>` 或 `debuggable` |
| 普通 app | TRUSTED_SYSTEM | ⚠️ | `<profileable>` 或 `debuggable` |
| SDK Sandbox（20000-29999） | 任意 | ⚠️ | 同 app 检查 |
| Isolated（90000-99999） | TRUSTED_SYSTEM | ⚠️ | **所有 packages 必须 profileable** |
| 其他 UID | 任意 | ❌ | — |

`profileable`（Android 11/API 30）与 `profileable_from_shell`（Android 12/API 31）由 ART 启动时读 `<profileable>` 标签写入 `/data/system/packages.list`，heapprofd 通过 readproc group 读该文件判断。**生产结论**：API 30+ 才能在 release 构建上做 heapprofd profiling；API 30 之前仅 debuggable 可被 profile。

### OOM 自动抓取：`android.java_hprof.oom`

`builtin_producer.cc:53-58, 157-162`：

```cpp
constexpr char kJavaHprofOomDataSourceName[] = "android.java_hprof.oom";
constexpr char kJavaHprofOomActivePropertyName[] = "traced.oome_heap_session.count";

if (ds_config.name() == kJavaHprofOomDataSourceName) {
  java_hprof_oome_instances_.emplace(ds_id);
  SetAndroidProperty(kJavaHprofOomActivePropertyName,
                     std::to_string(java_hprof_oome_instances_.size()));
  return;
}
```

AMS / LMKD 通过订阅 `traced.oome_heap_session.count` 即可知道当前是否有 OOM 抓取在进行——这是与 `android.java_hprof` 分离的独立 data source，**不触发 heapprofd daemon 拉起**，走 ART 自带的进程内 dump 路径。

### 与 Systrace 协同的硬性约束

同一进程 **不能** 同时跑 Systrace HPROF（`am dumpheap`）与 perfetto `android.java_hprof` session——ART `Hprof::Dump` 是单线程 mutex，会导致 java_hprof 周期 dump 阻塞直到 Systrace 完成。生产 trace config 建议要么纯 Systrace、要么纯 Perfetto，避免混淆。

### 设备差异

- **手机/平板**：单 user 模型，UID 偏移 = `kAidUserOffset = 100000`。
- **TV/Auto**：多 user，UID 偏移累加；CanProfileAndroid 模运算后落到同一区间。
- **可折叠**：`linux.ftrace_frozen` 与 heapprofd 联动在 fold/unfold 时存在 race——`kFrozenProcess` 上的 `PostSocketDisconnected` 会清空 `signaled_pids`，unfold 后需重新 signal。
- **Wear OS/Embedded**：heapprofd.rc 是否被 sync 进 build 由 device 端 `init.<board>.rc` 决定，AOSP 默认 Wear OS 不包含；走 `system/extras/profcollectd` 替代。
