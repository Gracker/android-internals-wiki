# 13.21 Perfetto 版本演进与 Android 9-17 新特性验证

<!-- outline-start -->
## 要点

### 🔹 Perfetto 版本可用性时间线

Perfetto 从 Android 9（API 28）首次引入至今，经历了从基础 ftrace 采集到完整多数据源平台的演进。基于 AOSP `android-17.0.0_r1` 源码验证的版本时间线如下：

**Android 9 (API 28)**：基础服务首次引入
- Perfetto 首次进入 AOSP（`external/perfetto/Android.bp`），包含 `src/traced/`、`src/perfetto_cmd/`、`src/probes/` 三类核心组件
- 提供基础的 ftrace 数据采集能力
- **默认禁用**，需要系统属性手动启用

**Android 10 (API 29)**：完整功能可用 + 默认启用
- Perfetto 服务和命令行工具首次默认启用
- 新增 `android.power` 数据源（`probes_producer.cc` include 列表）
- 提供稳定的 Java API 接口供应用层使用

**Android 11 (API 30)**：服务化完善
- Perfetto 成为系统级标准服务
- 稳定性提升：修复早期版本的内存泄漏和性能问题
- 保持与 Systrace 的向后兼容

**Android 12 (API 31)**：heapprofd 与 GPU 数据源
- 引入 `linux.ftrace_frozen`（冻结进程 ftrace）和 `android.cpu_per_uid`（per-UID CPU 统计）数据源
- heapprofd 堆分析功能独立二进制发布（`src/profiling/memory/heapprofd.cc`）
- GPU 数据源开始集成

**Android 13 (API 33)**：场景感知数据源
- 新增 `android.aflags`（features.xml 开关状态）和 `android.game_intervention_list`（Game Mode 干预策略）两个"场景感知"数据源
- per-display FrameTimeline 实例化引入（`DisplayFrameTracker`，API 36+ 完善）

**Android 14-16 (API 34-36)**：持续增强
- 大数据文件处理性能优化
- per-display FrameTimeline 完善：每个 Display 独立 FrameTimeline 实例，VSync 偏移经由 `Scheduler/MessageQueue.cpp` 分派
- 与单显示器场景的区别：跨显示器帧匹配需通过 `Scheduler` 统一调度

**Android 17 (API 37)**：主线完整状态
- 18 个 ProbesProducer 数据源全部就绪（详见下文数据源清单）
- `DisplayFrameTracker` 与 `FrameTracer` 配合实现多显示器帧级追踪覆盖（详见 2.30 章对 FrameTimeline GPU/CPU 合成边界的分析）

**关键源码验证**：
```cpp
// external/perfetto/src/perfetto_cmd/main.cc — android-17.0.0_r1
int main(int argc, char** argv) {
    // Android 17 中的 Perfetto 命令行入口
    // 服务端（traced/traced_probes）由 init 拉起，perfetto 命令用于配置和控制
}
```

> 注：`debug.perfetto.enabled` 在 Android 17 中已部分被 DeviceConfig 机制替代（`perfetto_guardrail_config`），命令行动态启用依赖系统属性命名空间而非单一开关。

### 🔹 数据源演进历程

Perfetto 的数据源架构随 Android 版本迭代逐步扩展。经 `android-17.0.0_r1` 源码验证，**Android 17 实际注册 18 个 ProbesProducer 数据源**，覆盖内核/系统、用户态桥接和平台定制三类。

**ProbesProducer 数据源完整清单**（`external/perfetto/src/traced/probes/probes_producer.cc` + 子目录扫描）：

| 内核/系统 | `android.process_stats` | 进程级 CPU/内存统计 |
| 内核/系统 | `android.sys_stats` | 系统级 CPU / I/O 统计 |

| 内核/系统 | `linux.power` | Linux 内核电源事件 |
| 内核/系统 | `android.system_info` | 系统版本/构建信息 |
| 内核/系统 | `android.system_property` | 系统属性快照 |
| 用户态桥接 | `android.statsd` | Statsd 指标桥接 |
| 用户态桥接 | `android.log` | logcat 桥接 |

### 🔹 ftrace 与 atrace 的集成机制

Perfetto 没有重写 atrace 的用户态标签系统（`ATRACE_BEGIN` 宏仍由 `libcutils` / 原生 `atrace` 维护）。两者的协作方式如下（`ftrace_data_source.cc:55-77`）：

```cpp
base::Subprocess p({"/system/bin/atrace", "--list_categories"});
// 解析 "name - description" 行，写入 FtraceDescriptor.atrace_categories
```

Perfetto 在注册时**枚举** atrace 类别，记录时**借用** atrace 启动/停止 ftrace events 的副作用。这解释了为什么 `systrace.py` 与 `perfetto` 命令在类别语义上部分兼容——内核事件集与用户态标签都来自同一份 atrace 清单。

### 🔹 heapprofd 深度分析

Android 12（API 31）引入的 heapprofd 是独立的二进制程序（不由 `traced_probes` 管理，由 Android `init` 拉起），内部集成**双 producer 模型**（`src/profiling/memory/heapprofd.cc:65-95`）：

| Producer | 信号 | 数据源名 | 用途 |
|---|---|---|---|
| `HeapprofdProducer` | `__SIGRTMIN + 4` | `android.heapprofd` | Native 调用栈采样 |
| `JavaHprofProducer` | `__SIGRTMIN + 6` | `android.java_hprof` | Java HPROF 周期 dump |

**关键参数**（`heapprofd_producer.cc:55-61`）：

```cpp
constexpr size_t kUnwinderThreads = 5;
constexpr uint64_t kDefaultShmemSize = 8 * 1048576;   // 8 MB
constexpr uint64_t kMaxShmemSize = 500 * 1048576;     // 500 MB
```

- **共享内存**：默认 8 MB，最大 500 MB（可配置）
- **Unwinder 线程池**：5 个线程并行 unwind，保证采样吞吐
- **信号通信**：`__SIGRTMIN+4` 用于 Native 采样控制，`__SIGRTMIN+6` 用于 Java HPROF dump

**JavaHprof 周期 dump 调度**（`java_hprof_producer.cc:38-56`）：

```cpp
ds.SendSignal();  // sigqueue(pid, __SIGRTMIN+6, {session_id})
task_runner_->PostDelayedTask(
    [weak_producer, id, dump_interval] {
      weak_producer->DoContinuousDump(id, dump_interval);
    },
    dump_interval);
```

`dump_interval_ms` 与 `dump_phase_ms` 双参数使多 session 错峰触发，避免信号风暴。

**与传统 HPROF 的对比**：

| 特性 | HPROF | heapprofd |
|---|---|---|
| **分析方式** | 静态快照（触发一次 dump） | 实时追踪（连续采样） |
| **内存开销** | dump 时内存峰值可达应用内存的 2-3 倍 | 运行时固定 8 MB 共享内存 + unwinder 线程栈 |
| **分析粒度** | 对象级（所有可达对象） | 分配点级（调用栈 + 分配大小） |
| **时间维度** | 单次快照 | 时间序列分析 |
| **过滤能力** | 无（dump 全部堆） | 按包名/对象类型/profiling 间隔过滤 |
| **兼容性** | Android 1.0+ | Android 12（API 31）+ |

**使用示例**：

```bash
# 启动 heapprofd 追踪（指定 pid + 过滤包名）
perfetto -c - <<EOF
buffers: { size_kb: 65536 }
data_sources: {
  config {
    name: "android.heapprofd"
    heapprofd_config {
      process_cmdline: "com.example.app"
      sampling_interval_bytes: 4096
      shmem_size_bytes: 8388608
    }
  }
}
duration_ms: 30000
EOF
```

**限制条件**：
- 需要 Android 12（API 31）+ 
- 需要 system 或 debug 权限
- 长时间追踪可能产生 GB 级文件（需控制采样间隔和持续时间）

**优化建议**：
- 使用过滤条件（`process_cmdline`）仅追踪目标进程
- 控制 `sampling_interval_bytes`：值越大采样越稀疏，开销越低
- 使用增量模式减少重复分析
- 定期清理旧 trace 文件

### 🔹 FrameTimeline 集成

FrameTimeline 是 Android 13+ 中的核心渲染追踪功能，通过 Perfetto 实现渲染管线的端到端追踪。

**追踪范围**：
- **UI 线程**：布局、绘制、动画执行
- **渲染线程**：Layer 处理、缓冲区管理
- **GPU 线程**：GPU 渲染管线执行
- **SurfaceFlinger**：图层合成与显示输出

**与 SurfaceFlinger 的协同工作**：

```
应用层请求绘制 → SurfaceFlinger 图层管理 → Perfetto 事件记录
     ↓                    ↓                       ↓
  VSync 信号         缓冲区分配/释放          FrameTimeline 事件
```

**关键协同点**：
- **VSync 信号**：SurfaceFlinger 发送的 VSync 事件是帧时间线的基准
- **图层状态**：图层创建、更新、销毁事件
- **缓冲区管理**：缓冲区分配、获取、释放事件
- **栅栏同步**：Fence 事件的创建与等待

Android 17 多显示器场景中，`DisplayFrameTracker`（`frameworks/native/services/surfaceflinger/DisplayFrameTracker`）按显示器独立跟踪帧时间线，VSync 偏移经由 `Scheduler/MessageQueue.cpp` 分派。与单显示器场景的区别：每个 Display 拥有独立的 FrameTimeline 实例，跨显示器帧匹配需通过 `Scheduler` 统一调度（详见 2.30 章对 FrameTimeline GPU/CPU 合成边界的分析）。

**SurfaceFlinger 集成源码锚点**：
```cpp
// external/perfetto/src/tracing/surface_flinger_integration.cc — android-17.0.0_r1
void SurfaceFlingerDataSource::OnFramePresented(int64_t timestamp) {
    // SurfaceFlinger 帧显示事件的 Perfetto 记录
}
```

**UI 线程性能瓶颈典型场景**：
- **过度绘制**：同一像素区域被多次绘制
- **过度布局**：频繁的 layout 计算
- **阻塞操作**：I/O、网络等同步操作在 UI 线程执行
- **动画卡顿**：动画插值计算耗时过长

**分析方法**：
- **时间线分析**：识别 UI 线程的阻塞时间窗口
- **资源使用分析**：CPU、内存、GPU 使用情况
- **依赖关系分析**：UI 线程与其他线程的交互
- **热路径识别**：频繁执行的关键代码路径

### 🔸 性能优化与最佳实践

Perfetto 的大文件处理和实时分析需要针对性的配置策略。

**大型追踪文件的处理**：

| 优化维度 | 策略 | 说明 |
|----------|------|------|
| 缓冲区 | `--buffer-size=256M` | 根据追踪时长和目标事件密度调整 |
| 压缩 | `--compression=zstd` | zstd 压缩减少存储（压缩比约 3-5x） |
| 分段 | 分次采集 | 避免单文件过大（建议单文件 < 1 GB） |
| 增量 | 增量模式 | 仅采集变化部分 |

```bash
# 内存优化的 perfetto 配置示例
perfetto --buffer-size=256M \
  --compression=zstd \
  -c trace_config.txt \
  -o trace.perfetto
```

**实时追踪配置**：

```bash
# 限时实时追踪
perfetto --buffer-size=128M \
  --duration-seconds=300 \
  -c real_time_config.txt \
  -o real_time_trace.perfetto
```

**追踪数据的存储与导出**：
- **本地存储**：设备本地用于实时分析
- **云端存储**：上传到云端进行长期分析
- **导出格式**：Perfetto 原生格式（完整功能）、Systrace 兼容格式（HTML）、JSON/CSV（程序化处理）

**最佳实践**：
- 控制单次追踪时长（推荐 ≤ 5 分钟）
- 重要追踪数据定期备份
- 敏感数据注意权限控制

### 🔸 与 Systrace 的对比

Perfetto 与 Systrace 各有适用场景，以下对比基于实际功能差异：

| 维度 | Perfetto | Systrace |
|------|----------|----------|
| **数据源** | 多数据源架构（18 个 ProbesProducer + traced + heapprofd 等独立二进制） | ftrace + atrace 类别 |
| **兼容性** | Android 9（API 28）+ | Android 1.0+ |
| **大文件处理** | 支持 1 GB+，SQL 查询引擎 | 受限于 HTML 渲染，建议 < 100 MB |
| **分析方式** | SQL 查询 + Web UI | 可视化时间线 |
| **扩展性** | protobuf 定义可扩展数据源 | 固定的 ftrace/atrace 类别 |
| **部署** | 服务端/设备端分离架构 | 一体化 Python 脚本 |

**从 Systrace 到 Perfetto 的迁移**：

```bash
# Systrace
systrace -b 128 -o trace.html -t 30 sched freq gfx view wm

# 等效 Perfetto
perfetto -c - <<EOF
buffers: { size_kb: 131072 }
data_sources: { config { name: "linux.ftrace" ftrace_config { atrace_categories: "sched" atrace_categories: "freq" atrace_categories: "gfx" atrace_categories: "view" atrace_categories: "wm" } } }
duration_ms: 30000
EOF
```

**迁移建议**：
- 短期：Systrace 和 Perfetto 并存，旧项目继续用 Systrace
- 长期：逐步迁移到 Perfetto（SQL 查询能力是主要优势）
- CI/CD：Perfetto 更易于脚本化集成

## 扩展

### 🔸 企业级部署考量

企业环境下的 Perfetto 部署需关注配置管理和合规要求。

**配置管理**：
- 通过 MDM 或配置服务器集中下发 perfetto 配置
- 配置文件版本控制（开发/测试/生产环境差异化）
- 按应用类型设定不同监控策略（游戏 vs 工具类应用）

**安全与隐私**：
- 传输和存储加密
- 基于角色的访问控制（RBAC）
- 敏感数据脱敏处理
- 遵循最小权限原则

**大规模部署架构**：
- **边缘模式**：设备端本地采集，仅上传分析结果
- **集中模式**：所有 trace 数据上报到中央分析服务
- **混合模式**：实时分析在边缘，历史分析在云端
- 监控指标包括设备覆盖率、数据完整性、端到端延迟

## 总结

Perfetto 从 Android 9 的基础 ftrace 采集起步，到 Android 17 发展为包含 18 个 ProbesProducer 数据源、heapprofd 双 producer 堆分析、FrameTimeline 渲染管线追踪的完整性能分析平台。其架构特点在于：数据源以 protobuf 定义、SQL 查询引擎支持任意维度分析、生产者和消费者分离使定制数据源容易集成。

对开发者而言，Perfetto 的核心价值不在于数据源数量，而在于 SQL 分析能力和可扩展架构——理解数据源覆盖什么、SQL 能回答什么问题，远比记住数据源总数重要。

**基线版本**：`android-17.0.0_r1`，`external/perfetto` commit `201a16e409911aa016522a95143af2e5d52a3662`。

### ProbesProducer 数据源清单（18 个）

通过对 `external/perfetto/src/traced/probes/probes_producer.cc` include 列表与 `src/traced/probes/*` 子目录的源码扫描，**Android 17 主线（API 37）已注册 18 个数据源**：

- 内核/系统：`linux.ftrace`、`linux.ftrace_frozen`、`android.process_stats`、`android.sys_stats`、`android.power`、`linux.power`、`android.system_info`、`android.system_property`
- 用户态桥接：`android.statsd`、`android.log`、`android.packages_list`、`android.kernel_wakelocks`、`android.user_list`、`android.initial_display_state`、`android.inode_file_map`
- 平台定制：`android.aflags`（Android 13+）、`android.cpu_per_uid`（Android 12+）、`android.game_intervention_list`（Android 13+）
- 自描述：`metatrace`

> `android.aflags` 与 `android.game_intervention_list` 是 Android 13 后新增的「场景感知」数据源，前者抓取 features.xml 开关状态，后者记录 Game Mode 干预策略；当前章节未覆盖，可在 13.20/13.22 增补。

### `linux.ftrace` 与 atrace 的集成机制

`ftrace_data_source.cc:55-77` 关键调用：

```cpp
base::Subprocess p({"/system/bin/atrace", "--list_categories"});
// 解析 "name - description" 行写入 FtraceDescriptor.atrace_categories
```

**结论**：Perfetto 没有重写 atrace 的用户态标签系统（`ATRACE_BEGIN` 宏仍由 libcutils/原生 atrace 维护），而是在**注册时枚举**这些类别，**记录时**借用 atrace 启动/停止 ftrace events 的副作用。这是为什么 `systrace.py` 与 `perfetto` 命令在类别语义上**部分兼容**——内核事件集与用户态标签都来自同一份 atrace 清单。

### heapprofd 双 producer 模型

`src/profiling/memory/heapprofd.cc:65-95` 揭示 heapprofd 是**独立二进制**（不挂载到 traced_probes），由 Android init 拉起，内部集成两个 producer：

| Producer | 信号 | 数据源名 | 用途 |
|---|---|---|---|
| `HeapprofdProducer` | `__SIGRTMIN + 4` | `android.heapprofd` | Native 调用栈采样（unwinding 线程池 5 个） |
| `JavaHprofProducer` | `__SIGRTMIN + 6` | `android.java_hprof` | Java HPROF 周期 dump |

**关键参数**（`heapprofd_producer.cc:55-61`）：

```cpp
constexpr size_t kUnwinderThreads = 5;
constexpr uint64_t kDefaultShmemSize = 8 * 1048576;   // 8 MB
constexpr uint64_t kMaxShmemSize = 500 * 1048576;     // 500 MB
```

**JavaHprof 周期 dump 调度**（`java_hprof_producer.cc:38-56`）：

```cpp
ds.SendSignal();  // sigqueue(pid, __SIGRTMIN+6, {session_id})
task_runner_->PostDelayedTask(
    [weak_producer, id, dump_interval] {
      weak_producer->DoContinuousDump(id, dump_interval);
    },
    dump_interval);
```

`dump_interval_ms` 与 `dump_phase_ms` 双参数使多 session 错峰触发，避免信号风暴。
