# 13.25 源码调研：PerfDog 的 Android 平台 GPU/性能采集底层数据源

移动端性能分析绕不开 GPU。PerfDog 是腾讯出品的商业闭源移动端性能测试工具，提供帧率、CPU、GPU、内存等维度的实时监控。这里梳理 Android 平台 GPU 性能数据的采集通道：sysfs 节点、系统服务导出接口、ftrace/Perfetto 事件，以及引擎层 API。这些是 GPU 性能工具在 Android 上常用的数据源。

### 🔹 PerfDog 架构与 GPU 采集原理

PerfDog 的 Android 端采集逻辑运行在两个层面：设备端 daemon 通过 ADB 通道接收采集指令并执行数据抓取，PC/Mac 端客户端负责数据聚合与可视化。

GPU 性能数据的采集路径有三层。第一层是 sysfs——内核暴露的设备属性节点。以高通 Adreno GPU 为例，`/sys/class/kgsl/kgsl-3d0/gpubusy` 返回 GPU 繁忙百分比，`/sys/class/kgsl/kgsl-3d0/gpuclk` 返回当前时钟频率。ARM Mali GPU 的对应路径在 `/sys/class/misc/mali*/device/` 下，包含 `utilization`、`core_mask` 等信息。PerfDog 以固定采样周期（一般为 1s）读取这些文件，构建 GPU 频率和利用率的时序曲线。

第二层是 Android 系统服务。`SurfaceFlinger` 通过 `dumpsys` 命令暴露帧合成统计，`GraphicsStatsService`（`IGraphicsStats` AIDL 接口，位于 `frameworks/native/services/graphicsstats/`）提供应用的 GPU 渲染耗时直方图。`dumpsys gfxinfo <package>` 输出中包含每一帧的 GPU 命令提交时间和 GPU 完成时间，PerfDog 解析这些输出来计算帧级 GPU 耗时。

第三层是 Perfetto/atrace 事件。内核中的 GPU 驱动注册了 ftrace 事件——高通 kgsl 驱动提供 `kgsl_register_wakeup`、`kgsl_gpubusy` 等追踪点，ARM Mali 驱动提供 `mali_xxx` 系列事件。Perfetto 通过 ftrace 数据源采集这些事件，PerfDog 在启动 trace 时配置 Perfetto 的 GPU 相关数据源（`linux.ftrace` 的 `gpu_mem` 类别和 GPU frequency 的 `power.rails` 类别）。

三层数据靠 `elapsedRealtimeNanos` 对齐到同一时间轴。sysfs 采样后打 ELAPSED_REALTIME 时间戳，dumpsys 输出的帧时间戳也在同一时钟域——这样 PerfDog 面板上的 GPU 频率曲线和帧耗时柱状图才能精确对位。


### 🔹 SurfaceFlinger GPU 性能数据通路

SurfaceFlinger 是系统中帧数据的汇聚点，也是 GPU 性能数据最丰富的观察窗口。PerfDog 从 SurfaceFlinger 拿 GPU 数据主要靠三种机制。

`dumpsys SurfaceFlinger --latency <layer>` 输出指定图层的帧时间戳序列——每帧三列：预期 VSync 时间（`vsync`）、GPU 完成渲染时间（`gpu_composition_done`）、帧上屏时间（`present`）。这三个时间戳的差值直接给出 GPU 渲染耗时（`gpu_composition_done − vsync`）和合成延迟（`present − gpu_composition_done`）。该命令的底层实现在 `SurfaceFlinger::dumpFrameEventsLocked()`，它遍历 `mFrameEvents` 队列中每一帧的时间戳，通过 `String8::appendFormat()` 按帧输出。

`dumpsys gfxinfo <package> framestats` 提供以纳秒为精度的帧级耗时细分。输出中的 `GPU_COMPLETED` 时间戳标记 GPU 渲染完成的时刻，`TOTAL_GPU_COMMAND_ISSUED` 标记 GPU 命令提交的时刻。这两个值的差值反映 GPU 的执行耗时。对于识别 GPU 渲染瓶颈，可以关注 `GPU_COMPLETED − VSYNC_INTENDED` ——这个值持续超过 20 ms（以 60 FPS 为基准）说明 GPU 侧的渲染耗时是帧超时的主因。

HWComposer（HWC）的 retire fence 是判断硬件合成耗时的重要信号。HWC 在提交一帧到显示硬件时创建一个 fence，硬件合成完成后 signal 该 fence。在 Perfetto trace 中，`HW_VSYNC_ON` 和 `RELEASE_FENCE` 事件之间的时间间隔就是硬件合成耗时。PerfDog 通过解析 `dumpsys SurfaceFlinger` 输出中的 HWC present 时间戳和 fence 信号时间来判断硬合路径的性能。

在 Android 17 中，FrameTimeline 机制为帧生命周期的每个阶段创建了明确的 Perfetto slice：`APP_QUEUE`、`APP_GPU_COMPLETION`、`SF_COMPOSITION`、`HWC_COMPOSITION_QUEUED`、`DISPLAY_PRESENT`。PerfDog 可以在 Perfetto trace 中定位这些 slice，把帧在各个阶段的耗时分解为 GPU 渲染、SurfaceFlinger 合成和硬件扫描的时间比例——三者比例约 70:20:10 是典型的 GPU 渲染密集型场景，三者约 30:50:20 则是合成瓶颈。


### 🔹 GraphicBuffer 分配与 GPU 内存生命周期

帧性能数据可以定位慢帧；分析内存增长还要检查 GraphicBuffer 的分配和释放。

GraphicBuffer 通过 gralloc HAL 的 `allocate()` 分配 GPU 可见的连续物理内存。gralloc HAL 实现因厂商而异：高通使用 `msm_kgsl` 驱动的 ION 分配器，ARM Mali 使用 `dma-buf` heaps。`frameworks/native/libs/ui/GraphicBuffer.cpp` 中的 `GraphicBuffer::initSize()` 封装了 `GraphicBufferAllocator::alloc()` 调用，后者通过 HIDL/AIDL 与 gralloc HAL 服务通信。

BufferQueue 管理 GraphicBuffer 的流转。上限由 `BufferQueue::setMaxAcquiredBufferCount()` 设置，默认值通常为 2（双缓冲）或 3（三缓冲）。当 acquire 的 buffer 数量达到上限时，生产者调用 `dequeueBuffer()` 会阻塞，直到消费者 release buffer。PerfDog 的 GPU 内存曲线中出现台阶式增长后不再回落，通常说明应用持有的 GraphicBuffer 数量超过预期——可能是 SurfaceView 创建后未 release、或者 GLSurfaceView 的 EGL surface 未正确销毁。

在 Perfetto trace 中，`graphic_buffer_allocation` 事件（来自 `frameworks/native/libs/gui` 中的 ATrace 插桩）记录了每次 GraphicBuffer 分配的大小和用途（`usage` flags）。GraphicBuffer 的 usage flags（`GRALLOC_USAGE_HW_RENDER`、`GRALLOC_USAGE_HW_TEXTURE`、`GRALLOC_USAGE_HW_COMPOSER` 等）决定了 buffer 的内存属性和缓存策略——带 `HW_TEXTURE` 的 buffer 分配在 GPU 纹理内存中，带 `HW_COMPOSER` 的分配在显示专用的 overlay 内存中。

PerfDog 的 GPU 内存统计在 `dumpsys meminfo` 的 `Gfx dev` 列中汇总了 gralloc 分配的总量。Android 17 中 `dumpsys gfxinfo <package>` 输出增加了 `Total GPU memory usage` 行，直接给出当前 app 在所有 GPU 内存池（纹理、渲染目标、buffer 对象）中的合计占用。


### 🔹 Vulkan 驱动层的可观测性节点

Vulkan 作为 Android 推荐的低开销图形 API，其驱动层暴露了比 OpenGL ES 更丰富的性能计数器。

GPU 时间戳通过 `VK_EXT_calibrated_timestamps` 扩展获取。该扩展允许应用查询 GPU 的时间戳域并转换为 `VK_TIME_DOMAIN_DEVICE_EXT` 的单调时间。`vkGetCalibratedTimestampsEXT()` 同时返回 GPU 时间戳和设备单调时间（`CLOCK_MONOTONIC`），通过两个值的对应关系建立 GPU 时间到系统时间的映射。Perfetto GPU trace 事件的时间戳就是通过这条路径从 GPU 时钟转换到系统 unified trace clock 的。

GPU 利用率与频率的采集走另一条路径——sysfs 和 devfreq。GPU 驱动通过 Linux devfreq 框架上报负载状态。高通的 kgsl 驱动在每次 GPU 提交周期结束时更新 `gpubusy` 计数器，ARM Mali 驱动通过 `mali_metrics` 接口暴露 core 级别的活跃周期占比。PerfDog 读取这些节点计算 GPU 利用率，Perfetto 的 `linux.ftrace` 数据源中的 `gpu_mem_total` 和 `gpu_frequency` counter 也来自同一数据源。

Vulkan 命令缓冲区提交流程是 GPU 性能分析的关键观察点。`vkQueueSubmit()` 将命令缓冲区加入 GPU 队列，`vkQueuePresentKHR()` 请求将渲染结果提交到显示。如果两次 `vkQueuePresentKHR` 的 GPU 时间戳间隔超过 VSync 周期，说明 GPU 那一帧的渲染花了比帧预算更长的时间。

PerfDog 的 GPU 渲染耗时统计主要依据 `dumpsys gfxinfo framestats` 的 `GPU_COMPLETED` 时间戳，而非直接插桩 Vulkan 调用。Vulkan 层面的调试插桩通过 Android GPU Inspector (AGI) 工具链进行——AGI 在 Vulkan 驱动中添加了 `VK_LAYER_GOOGLE_frame_capture` 和 `VK_LAYER_GOOGLE_gpu_timing` 两个 layer，记录每一个 draw call 的 GPU 执行时间。PerfDog 不直接使用 AGI layer，但 Perfetto 的 GPU counter track 中包含了来自同一底层驱动的频率和利用率数据。


### 🔹 OpenGL ES 的 ANGLE 翻译层开销

对于还在用 OpenGL ES 的应用，ANGLE 翻译层是理解 GPU 耗时不可跳过的一环。Android 自 API 30 起引入 ANGLE 作为 OpenGL ES 到 Vulkan 的可选翻译层，到 Android 17 启用范围进一步扩大。

ANGLE 的翻译发生在两个层面。同步层面，每个 `glDrawArrays()` / `glDrawElements()` 调用被翻译为一次或多次 `vkCmdDraw()`——单次 draw 的翻译开销通常在 1-5 μs 级别，主要消耗在状态差异比较和 Vulkan pipeline 创建上。异步层面，ANGLE 维护了一个内部 shader 缓存——`glCompileShader()` 的首次调用会触发 GLSL 到 SPIR-V 的编译，耗时可能达到数百 ms，但第二次调用同一个 shader 时直接从磁盘缓存加载（位于 `/data/data/<package>/cache/angle_shader_cache/`），耗时降至毫秒级。

PerfDog 的 GPU 耗时统计中，ANGLE 翻译开销被包含在 `GPU_COMPLETED` 时间戳内——因为这个时间戳来自 GPU fence signal，无论 GPU 执行的是原生 Vulkan 命令还是 ANGLE 翻译后的命令，fence signal 的时刻都是 GPU 完成所有提交命令的时刻。对于 OpenGL ES 应用，PerfDog 面板上的 GPU 耗时如果明显高于同场景下的 Vulkan 应用，差异的主要来源就是 ANGLE 翻译开销和额外的 shader 编译延迟。

ANGLE 的 shader 编译缓存行为对性能的影响可以通过 Perfetto trace 观察。在首次运行的 trace 中，`glCompileShader` 触发的 SPIR-V 编译会产生一个持续时间明显的 slice（在 ANGLE 内部 trace 事件中显示为 `CompileShader`）。在第二次运行的 trace 中，同一个 shader 的 `CompileShader` slice 缩短到亚毫秒级——这就是缓存命中的效果。PerfDog 的冷启动和热启动性能对比中包含了对这个缓存行为的间接测量。

关于 Vulkan 版本：ANGLE 在 Android 17 的 AOSP build 中的 Vulkan 后端基于 Vulkan 1.3 API 功能集。Vulkan 1.4 规范发布于 2024 年底，截止 android-17.0.0_r1 尚未被 AOSP ANGLE 作为默认目标。如果厂商更新的 GPU 驱动支持 Vulkan 1.4，ANGLE 可以利用部分 Vulkan 1.4 特性，但这不是 AOSP 基准行为。


### 🔹 游戏引擎的 GPU 性能数据接入

游戏引擎自己也有 GPU 性能计数器，而且比系统层面的 dumpsys 粒度更细。Unity 和 Unreal 都提供了公开 API，PerfDog 可以直接对接。

Unity 通过 `UnityEngine.FrameStats` 类（自 Unity 2021 LTS 起）暴露 GPU 相关的性能指标：`gpuFrameTime`（GPU 帧耗时，ms）、`gpuRenderThreadTime`（渲染线程耗时）、`drawCallCount`（draw call 次数）、`setPassCallCount`（SetPass 调用次数）。这些数据通过 Unity 的 `PlayerLoop` 机制在每个渲染帧结束后更新，PerfDog 可以在 Java/Kotlin 层通过 `AndroidJavaObject` 调用 `UnityPlayer.UnitySendMessage()` 获取。

Unreal Engine 通过 CSV Profiler（`GAutomationCSVProfiler`）和 `stat gpu` 命令暴露 GPU 性能数据。CSV Profiler 记录每帧的 `GPUTime`、`RenderThreadTime`、`RHIThreadTime` 到 CSV 文件。PerfDog 可以配置 Unreal 项目在特定帧率下触发 CSV Profiler 输出，然后解析 CSV 中的 GPU 统计列。对于 Vulkan RHI 路径，Unreal 的 `RHIStats`（`FRHIStats` 结构体）记录了每个 RHI 命令的 GPU 执行时间——`DrawIndexedPrimitive`、`Dispatch`、`CopyTexture` 等。

Android Frame Pacing API（`android.gamedeviceperformance` 包，Android 17 中引入）在游戏引擎和 SurfaceFlinger 之间建立同步通道。`GameDevicePerformanceManager.setFrameRate()` 设置目标帧率后，SurfaceFlinger 在 VSync 调度时优先匹配游戏引擎的帧提交节奏。PerfDog 的帧率波动分析利用这个 API 的信息来区分"引擎主动降帧"（GameDevicePerformanceManager 触发）和"GPU 能力不足导致的被动丢帧"（帧时间超过预算）。

Draw call 数量和 GPU 耗时不是线性关系。10 个 draw call 和 1000 个 draw call，GPU 耗时可能只差不到 20%。瓶颈通常在 shader 复杂度、纹理带宽和 overdraw，而非 draw call 数量本身。PerfDog 的 GPU 利用率数据需要和 draw call 数量交叉解读：如果 GPU 利用率持续 > 90% 且 draw call 数量适中（< 500），瓶颈在 shader/纹理带宽；如果 draw call 数量巨大（> 2000）且 GPU 利用率不高，瓶颈在 CPU 侧的 draw call 提交。


### 🔹 Perfetto 中的 GPU 性能事件映射

PerfDog 和 Perfetto 的 GPU 数据可以交叉验证：PerfDog 用于识别异常指标，Perfetto 用于检查对应时间段的 GPU 命令耗时。

GPU 频率的 counter track 在 Perfetto 中通常命名为 `gpu_frequency` 或 `power.rails.gpu`，数据来源是内核 devfreq 框架或 GPU 驱动的周期性上报。查询当前 trace 中所有 GPU 相关 counter 的 SQL：

```sql
SELECT id, name, unit FROM counter_track WHERE name GLOB '*gpu*'
```

GPU 渲染阶段在 Perfetto 中以 gpu render stage slice 形式出现。这些 slice 来自 GPU 驱动的 ftrace 事件——高通 kgsl 驱动的 `kgsl_gpu_freq` 事件、Mali 驱动的 `mali_pm_status` 事件——Perfetto 将这些内核事件封装为 `gpu_render_stages` track 上的 slice。每个 slice 的 `dur` 表示 GPU 在该渲染阶段的实际执行时间。

GPU 内存的 counter track（`gpu_mem_total` 或 `gpu_mem`）反映 GPU 全局内存占用。该 counter 的值来自 GPU 驱动的 `meminfo` 报告——内核中 GPU 驱动通过 `/sys/kernel/debug/kgsl/kgsl-3d0/meminfo`（高通）或对应 Mali debugfs 节点采集。

帧级 GPU 耗时的 Perfetto 实现：在 trace 中启用 `gfx` 和 `frametimeline` 数据源后，每帧的 GPU 完成时间在 `Expected Timeline` track 上显示为 `APP_GPU_COMPLETION` slice。通过计算 `APP_GPU_COMPLETION` 与上一帧 `APP_QUEUE` 的偏移，可以得到帧级 GPU 耗时。这种方式精度受限于 trace 的时间戳粒度（通常 125 μs 级别，由 ftrace 的实现决定），比 PerfDog 的面板值（基于 `dumpsys gfxinfo` 的 ns 级时间戳）精度低但覆盖的系统范围更广。


### 🔹 GPU 性能问题定位实战

GPU 性能问题通常表现为帧率下降（FPS 低于目标值）或帧时间抖动（Jank）。PerfDog 的数据可以帮助区分三种典型瓶颈。

**渲染过载**：GPU 利用率持续 > 95%，频率跑在最高档。帧时间集中在 25-35 ms（60 FPS 目标下）。Perfetto trace 里 `APP_GPU_COMPLETION` slice 占整帧 70% 以上。PerfDog 面板上 GPU 利用率和频率双高就是这个模式的典型特征。解决方向：降 shader 复杂度、减 overdraw、用纹理压缩、降渲染分辨率。

**频率限制**：GPU 利用率 > 80%，但频率比最高档低 30-50%。帧时间波动大（20-60 ms），和 GPU 频率曲线高度相关。Perfetto 的 `gpu_frequency` 在帧超时前 1-2s 已经开始下降，可能是 thermal throttle 或功耗预算限制了频率。PerfDog 面板上频率台阶式下降、利用率随之上升，是这个模式的标志。解决方向：改善散热、降低整机功耗、CPU 侧减负以降总热负载。

**内存带宽瓶颈**：GPU 利用率中等（60-80%），但大量处理纹理操作或 framebuffer 格式转换。`dumpsys gfxinfo` 输出的 `TOTAL_GPU_COMMAND_ISSUED` 增加但 GPU 频率处于中等档位。Android GPU Inspector (AGI) 的 `Memory Bandwidth` counter 可以更直接地确认这个场景。解决方向：减少纹理尺寸、使用压缩纹理格式（ETC2/ASTC）、减少 render target 切换、避免每帧的纹理上传。

排查时要把 GPU 频率和利用率放在一起看：频率最高、利用率 > 95%，需要检查 GPU 算力；频率中等但帧超时，则检查 GPU idle bubble（GPU 等待 CPU 提交命令）或内存带宽瓶颈。PerfDog 用于确定异常指标，Perfetto trace 用于定位耗时最长的 GPU 命令区间。
