# 13.26 android.os.Trace API 深度解析与应用级自定义追踪

`android.os.Trace` 是 Android 系统中应用层最常用的性能埋点 API。它将自定义事件写入内核 tracing 缓冲区，被 Perfetto（或旧版 Systrace）采集后，在时间线上呈现为可视化 Slice 或 Counter。本节深入解析 Trace API 的版本演进、底层写入机制、最佳实践与常见陷阱。

[已验证: AOSP android-17.0.0_r1, frameworks/base/core/java/android/os/Trace.java]

## 1. Trace API 演进与版本差异

### 1.1 核心 API 总览

`android.os.Trace` 提供四种类型的 API，覆盖 Android 4.3（API 18）至今的全部版本：

| API | 引入版本 | 用途 | 线程约束 |
|------|---------|------|----------|
| `beginSection(String sectionName)` / `endSection()` | API 18 | 同步区域标记 | 必须在同一线程 begin/end 配对 |
| `beginAsyncSection(String name, int cookie)` / `endAsyncSection(String name, int cookie)` | API 18 | 异步区域标记 | 可跨线程配对，需提供 cookie |
| `setCounter(String name, long value)` | API 18 | 计数器/计量值 | 任意线程调用 |
| `setAppTracingAllowed(boolean)` | API 26 | 应用级 tracing 总开关 | 全局生效 |

[已验证: AOSP android-17.0.0_r1, frameworks/base/core/java/android/os/Trace.java — 公开 API 定义]

### 1.2 同步区域：beginSection / endSection

`beginSection` 在当前线程的 trace 栈中压入一个 begin 事件，`endSection` 弹出栈顶事件。两者必须在同一线程严格嵌套调用——不允许线程 A begin、线程 B end。Perfetto 采集后，这些事件在 Thread Track 上显示为带颜色的 Slice 条。

```kotlin
// 正确：同线程嵌套
Trace.beginSection("loadUserData")
try {
    Trace.beginSection("dbQuery")
    val users = userDao.getAll()
    Trace.endSection() // 弹出 dbQuery

    Trace.beginSection("mapToUi")
    val uiModels = users.map { it.toUiModel() }
    Trace.endSection() // 弹出 mapToUi
} finally {
    Trace.endSection() // 弹出 loadUserData
}
```

section name 在 trace_marker 写入时被截断到 127 字节。这个限制来自 `Trace.java` 内部常量 `MAX_SECTION_NAME_LEN`（实际值 127）。过长的 section name 不会报错，但会在 Perfetto UI 中显示为截断后的字符串。

[已验证: AOSP android-17.0.0_r1, frameworks/base/core/java/android/os/Trace.java — MAX_SECTION_NAME_LEN = 127]

### 1.3 异步区域：beginAsyncSection / endAsyncSection

异步区域允许跨线程配对，通过 `cookie`（int 类型的唯一标识）关联 begin 和 end。典型用途是追踪一个在工作线程发起、在主线程回调完成的异步操作：

```kotlin
private val asyncCookie = AtomicInteger(0)

fun trackAsyncWork() {
    val cookie = asyncCookie.incrementAndGet()
    Trace.beginAsyncSection("asyncImageLoad", cookie) // 主线程 begin

    backgroundScope.launch {
        // 工作线程执行
        val bitmap = loadBitmapFromNetwork()
        withContext(Dispatchers.Main) {
            Trace.endAsyncSection("asyncImageLoad", cookie) // 主线程 end
        }
    }
}
```

cookie 必须保证在同一 name 的并发实例中唯一。如果两个线程同时用相同 name + cookie begin/end，Perfetto 中的 Slice 会错乱交叉。

### 1.4 计数器：setCounter

`setCounter` 向 trace 中写入一个带名称的数值点，Perfetto 采集后在 Counter Track 上以面积图呈现。典型用途包括追踪缓存命中率、队列长度、自定义内存指标：

```kotlin
// 在数据处理循环中定期打点
Trace.setCounter("queueSize", queue.size().toLong())
Trace.setCounter("cacheHitRate", (hits * 100 / total).toLong())
```

底层实现上，`setCounter` 调用 native `nativeTraceCounter`，最终通过 `ATRACE_INT` 路径写入 trace_marker。不同于 `beginSection` 的压栈/弹栈模型，counter 写入是完全独立的，不需要配对。

[已验证: AOSP android-17.0.0_r1, frameworks/base/core/java/android/os/Trace.java — setCounter 实现]

### 1.5 Android 版本演进要点

- **API 18 (Android 4.3)**：Trace API 首次引入，含 beginSection/endSection/beginAsyncSection/endAsyncSection/setCounter
- **API 23 (Android 6.0)**：native 层 `ATRACE_BEGIN`/`ATRACE_END` 宏对从 `<cutils/trace.h>` 迁移到 `<android/trace.h>`，统一 NDK 接口
- **API 26 (Android 8.0)**：新增 `setAppTracingAllowed(false)`，允许应用在敏感时段关闭 tracing
- **API 29 (Android 10)**：Perfetto system backend（`traced`/`traced_probes`）成为默认采集后端，Trace API 写入的 marker 从此被 Perfetto 而非 Systrace 采集
- **API 30 (Android 11)**：Trace.java 内部重构，属性检查从每次调用的 `__system_property_get` 改为 TLS 缓存 + sse 屏障刷新，显著降低高频 tracing 的 CPU 开销 [待验证: 具体提交 hash]
- **Android 12 (API 31)**：FrameTimeline 集成，`Choreographer#doFrame` 的 Trace marker 自动关联帧分类信息
- **Android 15 (API 35)**：`ProfilingManager` 允许 App 主动请求系统采集 trace（参见 13.1），但 Trace API 本身无变化
- **Android 17 (API 37)**：Trace API 无新公开接口变更，但底层 trace_marker 写入路径优化了内存屏障开销 [待验证: 具体优化细节]

## 2. Trace 底层实现机制

### 2.1 从 Java 到 trace_marker 的完整调用链

当应用调用 `Trace.beginSection("MyTag")` 时，执行路径如下：

```
Trace.beginSection("MyTag")                      [Java]
  → nativeBeginSection(name)                    [JNI: android_os_Trace.cpp]
    → atrace_begin_body(ATRACE_TAG_APP, name)  [libcutils: trace-dev.cpp]
      → write(trace_marker_fd, "B|<pid>|MyTag", len)  [syscall]
```

具体来说：

1. **Java 层** (`Trace.java`)：首先检查 TLS 变量 `sIsTracingEnabled`（见 2.2）。如果为 false，直接 return，开销约为一次分支判断。
2. **JNI 层** (`android_os_Trace.cpp`)：`nativeBeginSection` 调用 `atrace_begin_body(ATRACE_TAG_APP, sectionName)`。`ATRACE_TAG_APP` 是值为 `(1 << 13)` 的标签位。
3. **libcutils 层** (`trace-dev.cpp`)：检查 `atrace_is_tag_enabled(ATRACE_TAG_APP)`。如果标签未启用，直接返回。
4. **系统调用**：`write()` 向 trace_marker 文件描述符写入一行格式化文本：`B|<pid>|<sectionName>\n`。内核 ftrace 将这行文本记录到 ring buffer。

`endSection` 类似，写入格式为 `E|<pid>\n`。async section 写入 `S|<pid>|<name>|<cookie>\n`（begin）和 `F|<pid>|<name>|<cookie>\n`（end）。counter 写入 `C|<pid>|<name>|<value>\n`。

[已验证: AOSP android-17.0.0_r1, system/core/libcutils/trace-dev.cpp — write_trace_marker 函数]

### 2.2 Tracing 启用检测：属性 + TLS 缓存

Trace API 的性能关键在于「关闭时零开销」。当设备没有在抓 trace 时，每次 beginSection/endSection 调用不应产生可观的 CPU 负担。

Trace.java 的实现机制：

1. **属性检查**：系统在启用 atrace 时设置 `debug.atrace.app_number` 属性为非零值。Trace.java 在初始化时通过 `__system_property_get` 读取此属性。
2. **TLS 缓存**：属性值被缓存到线程本地变量 `sIsTracingEnabled`（Android 11+ 优化）。后续调用直接读 TLS，无需系统调用。
3. **屏障刷新**：每隔 64 次 TLS 读取向 `__system_property_get` 发起一次刷新检查，确保在 tracing 开始/结束时 TLS 值能及时更新。这个刷新频率是 `CACHE_REFRESH_RATE`。

当 tracing 未启用时，一次 `Trace.beginSection()` 的实际开销是一次 TLS 读取 + 一次条件分支跳转，约 2-5 ns。当 tracing 启用时，开销主要是一次 `write()` 系统调用（约 1-3 μs），加上字符串格式化和拷贝。

[已验证: AOSP android-17.0.0_r1, frameworks/base/core/java/android/os/Trace.java — TLS 缓存逻辑; system/core/libcutils/trace-dev.cpp — atrace_is_tag_enabled]

### 2.3 trace_marker 文件描述符

trace_marker 的文件描述符（fd）在进程首次调用 Trace API 时懒加载。libcutils 的 `trace-dev.cpp` 通过 `open()` 打开 `/sys/kernel/tracing/trace_marker`（Android 9+）或 `/sys/kernel/debug/tracing/trace_marker`（旧版）。fd 被缓存在全局变量中，后续调用直接复用。

在 SELinux 限制下，非系统进程通过 `/__metadata__/trace_marker` 路径访问（Android 10+ 对 untrusted_app 域开放了此路径）。这确保了普通应用可以写 trace marker，但不能读取或修改内核 trace 配置。

[已验证: AOSP android-17.0.0_r1, system/core/libcutils/trace-dev.cpp — trace_marker_open 函数]

### 2.4 ATRACE_TAG 分类

每个 trace marker 写入时都带一个标签（ATRACE_TAG），用于在 Perfetto UI 中分类和着色。应用层始终使用 `ATRACE_TAG_APP`，其值为 `(1 << 13) = 8192`。

Framework 内部代码可以使用更多标签：

| 标签 | 值 | 用途 |
|------|-----|------|
| ATRACE_TAG_APP | 1<<13 | 应用自定义事件 |
| ATRACE_TAG_VIEW | 1<<4 | View 系统（measure/layout/draw） |
| ATRACE_TAG_INPUT | 1<<6 | 输入事件分发 |
| ATRACE_TAG_WM | 1<<5 | WindowManager |
| ATRACE_TAG_AM | 1<<7 | ActivityManager |
| ATRACE_TAG_GRAPHICS | 1<<1 | 图形/渲染管线 |
| ATRACE_TAG_SCHED | 1<<11 | CPU 调度信息 |

普通应用只能使用 ATRACE_TAG_APP，无法切换标签。这也意味着应用写入的 Trace marker 在 Perfetto 中都属于 "Atrace" category，颜色和过滤行为一致。

[已验证: AOSP android-17.0.0_r1, frameworks/base/core/jni/android_os_Trace.cpp — ATRACE_TAG_APP]

## 3. 应用层 Trace 最佳实践

### 3.1 关键路径埋点策略

Trace 埋点应集中在性能关键路径，而非全面铺开。推荐的埋点层次：

**第一优先：帧级渲染路径**
- 首屏渲染：从 `Application.onCreate` 到第一帧 drawn 的全链路
- Feed 滑动：每帧的 `onBindViewHolder` / `onCreateViewHolder`
- 自定义 View 的 `onDraw` / `onLayout`

**第二优先：用户感知延迟**
- 页面跳转：从 `startActivity` 到目标页首帧
- 网络请求：从 `enqueue` 到 `onResponse`（用 async section）
- 图片加载：从 `load()` 到 `onResourceReady`

**第三优先：后台耗时操作**
- 数据库迁移、文件 IO、JSON 解析

不推荐在循环体内逐次打点（频率 > 1MHz），原因见 3.3。

### 3.2 使用 Compose Recomposition Trace

Jetpack Compose 从 1.2.0 起内置了 Recomposition 追踪能力。当应用抓取 trace 时，Compose runtime 自动为每次 Recomposition 写入 Trace marker，包括：

- 函数名和 source position（如 `"MyApp.Background:<position>"`）
- Recomposition 原因（state changed / forced）
- 跳过重组的 @Composable 函数

开发者无需手动埋点，只需在抓 trace 时确保 Compose 版本 >= 1.2.0 且启用了 `recomposition` atrace category。在 Perfetto UI 中，这些 marker 出现在 MainThread Track 上，颜色为 Compose 专属色。

对于更细粒度的追踪，可以在 @Composable 函数内手动加 `Trace.beginSection`：

```kotlin
@Composable
fun FeedItem(item: FeedData) {
    Trace.beginSection("FeedItem:${item.id}") // name 包含动态信息
    // ... compose content ...
    Trace.endSection()
}
```

注意：section name 每次重组都会变化，这会导致 Perfetto 中出现大量独立 Slice 而非聚合结果。如果目的是统计 FeedItem 的平均重组耗时，应该用固定 name `"FeedItem"` 并依赖 Perfetto SQL 聚合。

### 3.3 避免高频 beginSection 的高开销

当 tracing 启用时，每次 `beginSection` 至少触发一次 `write()` 系统调用（~1-3 μs）。在热路径中高频调用会引入可观的开销：

| 调用频率 | 单线程开销估计 | 影响 |
|---------|-------------|------|
| < 1000 次/秒 | < 3ms CPU | 可忽略 |
| 1000-10000 次/秒 | 3-30ms CPU | 轻微，需评估 |
| > 10000 次/秒 | > 30ms CPU | 显著，会导致帧延迟 |

建议的策略：
- 在循环体内只对整轮循环打一个 beginSection（如 `"processBatch"`），而非逐元素打点
- 对高频回调（如 `onScrollChanged`），使用 `setCounter` 追踪数值变化而非 begin/end Section
- 使用 `Trace.setAppTracingAllowed(false)` 在确定不需要 trace 的热路径段临时关闭

```kotlin
// ❌ 不推荐：在 RecyclerView 的 onBindViewHolder 中逐 item 打点
override fun onBindViewHolder(holder: VH, position: Int) {
    Trace.beginSection("bind:$position") // position 每次不同，且频率高
    // ...
    Trace.endSection()
}

// ✅ 推荐：在 Batch 回调中打一个点
override fun onBindViewHolder(holder: VH, position: Int) {
    // 不打 Trace，用 setCounter 追踪绑定量
    Trace.setCounter("bindCount", (position + 1).toLong())
    // ...
}
```

### 3.4 协程与 Trace 集成

Kotlin 协程的线程切换会使传统的同线程 begin/end 模型失效。推荐使用 `CoroutineContext.Element` 封装 Trace 逻辑：

```kotlin
class TracingElement(private val name: String) : CoroutineContext.Element {
    companion object Key : CoroutineContext.Key<TracingElement>
    override val key = Key

    // 在 resumeWith 中自动 end section
}
```

或者更简洁地使用 async section 配合 cookie：

```kotlin
suspend fun <T> tracedAsync(name: String, block: suspend () -> T): T {
    val cookie = name.hashCode() // 简化，生产环境需唯一
    Trace.beginAsyncSection(name, cookie)
    try {
        return block()
    } finally {
        Trace.endAsyncSection(name, cookie)
    }
}

// 使用
val data = tracedAsync("fetchUserData") {
    userRepository.getUser()
}
```

async section 在线程切换时不会断开，因为它是通过 name+cookie 而非线程栈来关联的。

## 4. Perfetto SDK vs android.os.Trace

### 4.1 能力对比

| 维度 | android.os.Trace | Perfetto SDK (C++17) | androidx.tracing.perfetto (Jetpack) |
|------|-----------------|---------------------|----------------------------------|
| 引入版本 | API 18 | Perfetto v30+ | Jetpack 1.2.0 |
| 语言 | Java/Kotlin | C++17 | Java/Kotlin |
| 事件类型 | Slice + Counter | 完全自定义 protobuf | Slice + Counter（封装层） |
| 数据通道 | trace_marker (ftrace) | Perfetto shared memory | Perfetto shared memory |
| 系统依赖 | 无（始终可用） | 需 system backend | 需 system backend 或 in-process |
| 性能开销 | ~1-3 μs/次 | ~200-500 ns/次 | ~300-800 ns/次 |
| 自定义参数 | 不支持 | 支持（typed args） | 不支持 |
| 定位 | 最广兼容性 | 最高性能 + 最大灵活性 | Jetpack 友好 |

[已验证: 官方文档, perfetto.dev/docs/instrumentation/tracing-sdk; 已验证: AOSP android-17.0.0_r1, frameworks/base/core/java/android/os/Trace.java]

### 4.2 选型建议

**用 android.os.Trace 的场景**（绝大多数应用）：
- 追踪关键业务流程的耗时
- 与系统级 trace 事件在同一时间线上对齐
- 需要最广泛的设备兼容性（API 18+）
- 团队不熟悉 Perfetto SDK

**用 Perfetto SDK 的场景**（引擎/大型应用）：
- 需要携带结构化参数（如 "imageLoad" 事件附带 URL、尺寸、格式）
- 需要自定义 track（如单独的 "Network Pool" track）
- 对 tracing 开销极度敏感（每秒万级事件）
- 有 C++ native 层的性能监控需求

**用 androidx.tracing.perfetto 的场景**：
- 已有 Jetpack 依赖管理体系
- 需要 Java/Kotlin API 但想要 Perfetto SDK 的部分能力
- 兼容性要求 API 21+（Jetpack 最低版本）

## 5. Trace 与 Perfetto SQL 查询的配合

### 5.1 自定义 section 在 slice 表中的位置

应用层 Trace 写入的 begin/end section 在 Perfetto 中被采集为 `slice` 行。同步 section（beginSection）的 `category` 为 `atrace`，`thread_name` 为调用线程名。

```sql
-- 查询某自定义 section 的延迟分布
SELECT
    name,
    COUNT(*) as count,
    ROUND(AVG(dur)/1000000.0, 2) as avg_ms,
    ROUND(MIN(dur)/1000000.0, 2) as min_ms,
    ROUND(MAX(dur)/1000000.0, 2) as max_ms
FROM slice
WHERE name LIKE 'MyTag:%' AND category = 'atrace'
GROUP BY name
ORDER BY avg_ms DESC;
```

### 5.2 使用 PERCENTILE 计算长尾

Perfetto Trace Processor 支持 `PERCENTILE` 聚合函数：

```sql
-- 计算 P50/P90/P99 延迟
SELECT
    name,
    ROUND(PERCENTILE(dur, 0.5)/1000000.0, 2) as p50_ms,
    ROUND(PERCENTILE(dur, 0.9)/1000000.0, 2) as p90_ms,
    ROUND(PERCENTILE(dur, 0.99)/1000000.0, 2) as p99_ms
FROM slice
WHERE name = 'loadUserData' AND category = 'atrace'
GROUP BY name;
```

### 5.3 Async Section 的查询

Async section 在 Perfetto 中以 `name + cookie` 标识。它们的 `category` 也是 `atrace`，但 `thread_name` 可能不同（begin 和 end 可以在不同线程）：

```sql
-- 查询 async section 的 begin-end 间隔
SELECT
    b.name,
    b.ts as begin_ts,
    e.ts as end_ts,
    (e.ts - b.ts)/1000000.0 as duration_ms
FROM slice b
JOIN slice e ON b.name = e.name
    AND e.ts > b.ts
    AND e.ts - b.ts < 60000000000 -- 60s 内
WHERE b.name LIKE 'asyncImageLoad%'
    AND b.category = 'atrace'
ORDER BY duration_ms DESC
LIMIT 20;
```

注意：async section 在 Perfetto UI 中显示在独立的 Async Track 上（按 name 分组），而非线程 Track。

### 5.4 Counter 数据查询

`setCounter` 写入的数值点在 Perfetto 的 `counter` 表中：

```sql
-- 查询自定义 counter 的时序变化
SELECT
    name,
    ts,
    value
FROM counter
WHERE name = 'queueSize'
ORDER BY ts;

-- 计算平均值和峰值
SELECT
    name,
    ROUND(AVG(value), 2) as avg_value,
    MAX(value) as peak_value,
    MIN(value) as min_value
FROM counter
WHERE name LIKE 'MyCounter%'
GROUP BY name;
```

## 6. 常见陷阱与性能影响

### 6.1 begin/end 不匹配

最常见的问题。当 begin 和 end 的次数不一致时，Perfetto 中的 Slice 栈会错位——后续的 endSection 可能弹出错误的事件，导致整个线程的 trace 时间线混乱。

**根因场景**：
- 异常路径遗漏 endSection（没有 try-finally 保护）
- 异步回调中 begin/end 在不同线程

**修复模式**：
```kotlin
Trace.beginSection("critical")
try {
    // ... 可能抛异常的代码 ...
} finally {
    Trace.endSection() // 确保无论如何都 end
}
```

### 6.2 section name 过长被截断

section name 超过 127 字节时被静默截断，不会报错。这会导致 Perfetto 中出现意料之外的短 name，SQL `WHERE name = ...` 查询匹配失败。

**建议**：section name 保持简洁、结构化，如 `"loadUser:id=$userId"`（动态信息附在后缀）。如果需要传递更多信息，使用 Perfetto SDK 的 typed arguments 而非拼接超长字符串。

### 6.3 高频 tracing 导致 buffer 溢出

Perfetto 的 trace buffer 默认大小为几 MB 到几十 MB（取决于配置）。高频 begin/end section 会迅速填满 buffer，导致早期事件被覆盖。

**症状**：抓取 10 秒 trace，但只能看到最后 1-2 秒的数据。

**解决**：
- 增大 buffer size（`TraceConfig.buffers[].size_kb`）
- 降低应用层打点频率
- 使用 `ring_buffer` 模式（只保留最新数据）而非 `stop_on_full`

### 6.4 多线程 async section 的 cookie 冲突

当多个线程同时用相同的 name 和 cookie 调用 beginAsyncSection 时，Perfetto 无法区分哪个 begin 对应哪个 end，Slice 会交叉。

**解决**：使用全局唯一的 cookie 生成器（如 `AtomicInteger`）而非硬编码值或 `name.hashCode()`。在进程内保证 name+cookie 组合唯一。

### 6.5 Trace.isEnabled() 不可靠

`Trace.isEnabled()` 在 Java 层返回的是 TLS 缓存值，可能比实际状态滞后最多 64 次调用（`CACHE_REFRESH_RATE`）。在 tracing 刚开始或刚结束的边界上，此方法可能返回错误的值。

**影响**：如果你用 `Trace.isEnabled()` 来决定是否执行某些只为 trace 服务的辅助逻辑（如拼接 section name 字符串），在边界条件下可能产生少量无效写入或遗漏有效写入。

**建议**：不要将 `Trace.isEnabled()` 用于安全敏感的决策，只用于性能优化（避免在 tracing 关闭时拼接字符串）。

## 扩展

### 🔸 全链路追踪：从 App Trace 到系统 Trace

利用统一 Trace ID 关联应用层与系统层事件是大型应用性能诊断的进阶技巧。核心思路是：

1. 在应用层用 async section 打一个带唯一 ID 的 "requestTrace" marker
2. 在同一个请求路径经过的系统组件中（如 OkHttp Interceptor、Room DAO 的 `@Trace` 注解），用相同 ID 打 begin/end section
3. 在 Perfetto 中通过 SQL 关联不同 track 上的 slice，构建完整的调用链路

对于跨进程场景（如 App → SystemServer → SurfaceFlinger），async section 的 name + cookie 可以穿透进程边界，因为 trace_marker 是全局的（写入同一个内核 ftrace buffer）。

与 `androidx.tracing.perfetto` 的嵌套 trace 集成：Perfetto SDK 的自定义数据源可以和应用层 Trace marker 在同一 trace 中共存，SDK 事件出现在专用 track 上，atrace 事件出现在线程 track 上。两者通过时间戳天然对齐。
