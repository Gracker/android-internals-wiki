## Theme 1: Android 16 ARR API 生态 + SurfaceFlinger 动态帧率（Score: 19）

**目标章节：** §2.2 帧率与刷新率、§2.6 SurfaceFlinger 与合成、§2.9 渲染机制的版本演进

**核心发现：**

Android 16（API 36）为 Adaptive Refresh Rate 引入三个新 API，将帧率决策从"App 硬编码"升级为"系统智能协商"：

- `Display.hasArrSupport()`：查询设备是否支持 ARR（15-QPR1 引入的 HAL 接口）
- `Display.getSuggestedFrameRate(int)`：根据当前设备状态（刷新率、功耗策略、内容类型）返回系统建议的目标帧率
- `Display.getSupportedRefreshRates()`：恢复 API，返回面板所有物理刷新率列表

**SurfaceFlinger 端变化：**

ARR 启用面板上，SurfaceFlinger 将显示 VSync 频率与实际刷新率解耦。SurfaceFlinger 分析活跃 Layer 的内容更新节奏，通过离散 VSync 步进动态调整刷新率，而非传统的模式切换（mode switch）。这意味着：
- 不再出现 60Hz↔120Hz 切换时的掉帧间隙
- SurfaceFlinger 的 Layer 帧率请求（`setFrameRate()`）成为"投票"，系统综合所有活跃 Layer 的投票 + 功耗策略决定最终刷新率
- Choreographer 回调时序会随刷新率动态变化

**与现有章节的衔接点：**
- §2.2 已讨论帧率与刷新率的基本关系，ARR 是这一关系的 Android 15/16 具体实现
- §2.6 SurfaceFlinger 合成流程中，ARR 改变了 VSYNC-sf offset 的计算逻辑（不再是固定 offset）
- §2.9 版本演进表可新增 Android 15→16 的 ARR 时间线

**验证状态：** L2（Android 官方开发者文档 + AOSP 源码路径 `frameworks/base/core/java/android/view/Display.java`）

## Theme 2: RecyclerView 1.4 ARR 集成 + View 帧率投票机制（Score: 18）

**目标章节：** §7.4 典型场景分析（RecyclerView 滑动）、§7.5 优化策略、§2.2 帧率与刷新率

**核心发现：**

RecyclerView 1.4 内部集成了 ARR，在 fling 和 smooth scroll 期间自动调节刷新率。实现机制：

1. **`setFrameContentVelocity()`**：RecyclerView 在 OverScroller 驱动的滚动过程中，每帧调用此 API 向系统传递内容速度
2. **动态升降频**：fling 起手阶段，系统将刷新率提升至高帧率（90/120Hz）；减速阶段逐步降频，节省功耗
3. **Touch Boost 协调**：手指触摸期间已有 Touch Boost 机制维持高帧率，ARR 主要在手指离开后的 fling 减速阶段生效

**View.setRequestedFrameRate() 投票机制（API 35）：**

每个 View 可通过 `setRequestedFrameRate()` 表达帧率偏好：
- 可设置具体帧率（30/60/120）或类别（`CATEGORY_NORMAL` / `CATEGORY_HIGH`）
- 系统汇总所有可见 View 的投票，取最高帧率（若互为倍数）或按 >60Hz="High" / ≤60Hz="Normal" 分类
- `ViewGroup.setRequestedFrameRate()` 不向下传播
- 投票仅在 View 被 invalidate 时有效

**与现有章节的衔接点：**
- §7.4 典型场景分析中 RecyclerView 滑动优化策略可直接引用此机制
- §7.5 优化策略中"帧率优化"段落可补充 `setFrameContentVelocity()` 作为自定义可滚动组件的最佳实践
- §2.2 可在"刷新率适配"小节补充投票机制的完整链路描述

**验证状态：** L2（Android 官方文档 + Medium 技术文章引用 AOSP 源码）
