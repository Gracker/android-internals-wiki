### P1 问题

[P1][源码错误] L90-L170 OkHttp EventListener 示例 — NetworkMetricEventListener 在实例字段里保存 callId、attempts、callStartNs，但正文没有要求通过 OkHttpClient.Builder.eventListenerFactory(...) 为每个 Call 创建实例。若读者用 eventListener(...) 注册单例，多个并发请求会共享 attempts 列表，阶段耗时串线。 建议：示例改成 EventListener.Factory：override fun create(call: Call) = NetworkMetricEventListener(...); 同时说明 eventListener(...) 只适合无 per-call mutable state 的监听器。
  2. [P1][源码错误] L269-L272 PLT Hook 符号职责 — send/recv 被写成“明文传输字节数”，SSL_write/SSL_read 被写成“TLS 封装后的读写”。HTTPS 路径下正好相反：SSL_write 输入应用明文并由 TLS 层加密；SSL_read 向应用返回解密后的明文；send/recv 位于 TLS 下方，通常看到的是 TLS record/密文字节。 建议：改为：SSL_write/read 用于应用明文长度与错误观察；send/recv 用于 socket 层加密后字节、errno、重传/断连辅助归因；明文 HTTP 例外单独说明。
  3. [P1][原理断裂] L189-L203 字节码插桩目标 vs L403 插桩范围 — 章节目标包含“三方 SDK 内部封装的网络请求”，但工程建议写“插桩范围优先 PROJECT”。AGP InstrumentationScope.PROJECT 只处理当前模块类，无法覆盖 AAR/JAR 依赖中的 URL.openConnection 调用。 建议：补充 PROJECT 与 ALL 的边界：一方代码先用 PROJECT；要覆盖三方 SDK 必须用 InstrumentationScope.ALL，并通过 isInstrumentable 包名白名单、依赖排除和缓存策略控制构建开销。

### P1 问题
  1. [P1][版本差异] L187-L190 Android 11+ ApplicationExitInfo — 正文只写 getTraceInputStream() 在 ANR 场景下通常返回 traces，遗漏 Android 12/API 31+ 对 REASON_CRASH_NATIVE 的支持。API 31+ 可通过同一接口取 Native tombstone，内容是 protobuf 序列化的 tombstone。 建议：补一段版本矩阵：API 30 主要用于 ANR trace；API 31+ 可用于 native crash tombstone protobuf。说明需要用 tombstone.proto 解析，且读取要放后台线程并做去重。
  2. [P1][原理断裂] L133-L147 signal handler 链式处理 — 正文建议链到前一个 handler，但没有说明 sigaction 的 SA_SIGINFO 分支。旧 handler 若设置 SA_SIGINFO，应调用 sa_sigaction(signum, siginfo, ucontext)；否则调用 sa_handler(signum)。不区分会造成参数约定错误或二次崩溃。 建议：补一个最小伪代码：检查 old_action.sa_flags & SA_SIGINFO，再分别调用 sa_sigaction/sa_handler；同时处理 SIG_DFL/SIG_IGN 和 re-raise。
  3. [P1][原理断裂] L168-L185 SIGQUIT / Signal Catcher Hook — 正文说 Native 层 hook SIGQUIT，但没有解释 ART SignalCatcher 使用 sigwait 等待 SIGQUIT 的机制。被 sigwait 消费的信号不会再按普通 sigaction handler 分发，因此“注册 SIGQUIT handler”并不等价于能稳定截获 ANR。external-review 已命中该盲区。 建议：补充 ART signal_catcher.cc 的机制：SIGQUIT 通常由 SignalCatcher 线程同步等待；APM 所谓 Hook 往往是侵入 SignalCatcher/信号掩码/系统 dump 流程，普通 App 量产要谨慎评估。

### P2 问题
  1. [P2][知识盲区] L232 VMA 耗尽 — VMA/VmSize 被与 FD、线程并列为通用监控项，但未区分 32 位与 64 位。32 位进程地址空间紧张，VMA/映射碎片更容易变成真实故障；64 位进程地址空间大，监控重点更多是映射数量、RSS/PSS 与异常 mmap 泄漏。 建议：补充 32/64 位差异：32 位强调地址空间上限和碎片，64 位强调极端映射泄漏、maps 行数、RSS/PSS 与图形/ashmem 资源。
