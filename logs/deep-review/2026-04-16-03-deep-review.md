## 审查结果

### 维度 1：源码引用准确性
- 评分：3/5
- 问题数：4
- 具体问题：
  1. [P0] Frame Timeline SQL 查询中 `expected` 别名未定义。查询写的是 `WHERE actual.dur > expected.dur`，但 FROM 子句中没有 JOIN `expected_frame_timeline_slice` 表。该 SQL 会直接报错。应先与 expected 表按 frame_number 关联，再比较 dur。
  2. [P1] 冷启动查询中 `ZygoteInit.xxx` 是占位符，不是实际 slice 名称。AOSP 中实际的 slice 名称为 `ZygoteInit.main`（Java 进程）或 `ZygoteInit.native`（WebView zygote）。章节标注 `[已验证]` 但实际未验证。
  3. [P1] 加载了 `INCLUDE PERFETTO MODULE android.monitor;` 但后续 SQL 未使用该模块提供的视图（如 `android_monitor_contention`），而是用 `slice.name GLOB '*monitor*'` 查底层 slice 表。模块加载和实际查询不一致——要么用模块视图，要么去掉 INCLUDE 语句。
  4. [P2] `sched.end_state` 值描述不精确。章节称 Running、Runnable(R+)、Sleeping(S)、Uninterruptible(D) 为 end_state 值，但 `Running` 不是 end_state——它表示线程仍在 CPU 上（此时没有 sched 表记录）。end_state 的实际值是 'R'、'R+'、'S'、'D'、'T'、'X'、'Z' 等单字母或带+号的形式。章节将调度状态和 end_state 混在一起描述。

### 维度 2：原理链完整性
- 评分：2.5/5
- 问题数：5
- 具体问题：
  1. [P1] Binder 分析节声称"关键指标有三个维度：client_dur、server_dur、dispatch_dur"，但后续所有 SQL 查询都只查 `slice.name GLOB '*binder*'` 并按 `slice.dur` 排序。SQL 实际上无法区分这三个维度——它只看到 slice 的总持续时间。如果 Perfetto 的 raw 表中确实有这些 tracepoint，应展示如何从 ftrace 事件中提取这三个时间维度；如果做不到，就不应该声称可以。
  2. [P1] "调度延迟：Runnable → Running 的时间"——标题描述正确，但 SQL 查询完全没测量调度延迟。它只是列出主线程的 sched 条目并按时间排序。真正测量调度延迟需要：找到线程从 end_state='R' 或 'R+' 离开 CPU 的时刻，到下一次同一 utid 出现在 sched 表中的时间差。当前 SQL 和标题完全不匹配。
  3. [P1] CPU 利用率计算的分母错误。查询用 `MAX(ts + dur) - MIN(ts)` 作为分母，这是该线程第一次到最后一次被调度的跨度。如果主线程只在 Trace 开头和结尾各运行一次，中间有大量空闲时间，这个"利用率"会严重偏高。正确分母应该是整个 Trace 的时间跨度，可用 `(SELECT end_ts - start_ts FROM trace_bounds)` 或类似方式获取。
  4. [P2] 主线程阻塞原因分类查询使用 LEFT JOIN + 时间重叠条件关联 sched 和 slice，这在逻辑上是多对多匹配——一条 sched 记录可能与多条 slice 重叠，导致结果膨胀。作为"实战手册"级别的 SQL，应该给出更精确的写法或提醒这个限制。
  5. [P2] "锁竞争与帧时间关联"查询的 JOIN 条件 `lock.ts >= frame.ts AND lock.ts + lock.dur <= frame.ts + frame.dur` 要求锁等待完全落在帧内部。但实际的锁等待可能跨越帧边界（例如在 doFrame 之前就开始等锁，到 doFrame 期间才获取到）。这个严格包含条件会漏掉跨帧的锁等待。

### 维度 3：版本差异覆盖
- 评分：2/5
- 问题数：4
- 具体问题：
  1. [P1] 章节声明 applicable_versions 为 Android 10-17，但完全没有版本差异说明。例如：Frame Timeline（Android 12 引入）、`android.frames` 模块（Perfetto v38+ 可用）、`android.monitor` 模块（具体引入版本未标注）。一个声称覆盖 Android 10-17 的"实战手册"，不告诉读者哪些查询在哪个版本上能用，是不完整的。
  2. [P1] `counter_track.name` 中 Java Heap 的名称因 Android 版本而异（旧版本用 `mem.java_heap` 或 `_MEM_STATS.Java_Heap`，新版本可能不同）。章节虽标注了 `[待验证]`，但作为手册应该给出一个更鲁棒的写法（如 GLOB '*Java*Heap*' 或提供多个备选名称）。
  3. [P2] Choreographer#doFrame 的 slice 名称在不同 Android 版本中可能不同（例如某些 OEM 定制 ROM 可能修改了 trace tag），章节未提及这一现实问题。
  4. [P2] sched 表的可用性和详细程度取决于 trace 配置中是否启用了 `linux.ftrace` 的 `sched/sched_switch` 事件。虽然章节末尾简要提到，但各个 SQL 查询没有标注自己的依赖条件。

### 维度 4：知识盲区
- 评分：2/5
- 盲区数：5
- 具体盲区：
  1. [P1 高] 完全未提及 PerfettoSQL 的核心扩展操作符 `SPAN_JOIN` / `LEFT_JOIN_SPAN` / `PARTITIONED_JOIN`。这些是 Perfetto 特有的时间区间 JOIN 操作符，正是实现"帧期间的 Binder 调用""帧期间的 GC 暂停"这类交叉分析的正确工具。实战手册不介绍它们，等于给了读者错误的工具。
  2. [P1 高] 未提及窗口函数（LEAD/LAG/FIRST_VALUE）用于帧节奏分析。帧时间序列的前后帧对比是 cadence jank 分析的基础，缺少这部分使得帧时间分析只有统计没有时序。
  3. [P1 中] 未提及 `dur = -1`（slice 未结束）和 `dur = 0`（即时事件）的处理。在实战中，不做过滤会导致 AVG/SUM 计算出错。这是新手最常踩的坑。
  4. [P1 中] 未提及 `PERCENTILE` 或 `QUANTILES` 函数用于帧时间 P50/P90/P99 分布。业界标准做法是看百分位而非平均值，实战手册缺少这部分意味着读者无法产出符合行业标准的帧时间报告。
  5. [P2 低] 未提及 `trace_bounds` 表用于获取 Trace 的起止时间。这在多个查询中都有用（CPU 利用率的分母、时间窗口计算等）。

### 维度 5：数据与案例支撑
- 评分：1.5/5
- 问题数：5
- 具体问题：
  1. [P2] 所有 SQL 查询都缺少示例输出。作为"实战手册"，读者无法判断查询结果的格式和含义。至少每个主要查询应附带 2-3 行示例输出。
  2. [P2] "如果 jank 和 big jank 桶里的帧数超过总帧数的 5%，就需要关注了"——5% 阈值无来源。Google 的 Android Vitals 建议的是"慢帧 > 0.5%"，不是 5%。
  3. [P2] "Application.onCreate 应该控制在 200ms 以内，Activity.onCreate 在 100ms 以内"——无来源。这些阈值因应用复杂度和设备性能差异很大，应标注来源或改为"在 mid-range 设备上的参考值"。
  4. [P2] "GC 暂停超过 3-5ms 需要关注，超过 16ms 就会导致掉帧"——前者无来源，后者虽逻辑正确（16ms = 60fps 一帧预算）但表述应更精确。
  5. [P2] "锁等待超过 0.5ms"（500000ns）的过滤阈值——无来源。主线程锁等待 0.5ms 是否值得关注取决于场景，不应一刀切。
