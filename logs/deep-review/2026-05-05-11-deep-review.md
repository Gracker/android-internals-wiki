## Queue issue 详情

### 2.10 GPU 渲染深入
1. [P1] [版本差异/系统策略边界] L226、L464-L476（Android 16 Vulkan / ANGLE 默认路径）
   - 问题：正文仍保留“Android 16 将 Vulkan 定为默认图形 API”“大量 GLES 应用的答案是 ANGLE”等强结论，后文又说 ANGLE 取决于 launch policy 和厂商配置，前后口径不一致。AOSP android-16.0.0_r1 的 GraphicsEnvironment.setupAngle()/queryAngleChoice() 显示 ANGLE 启用受 ro.hardware.egl、全局/单应用 settings、平台 allowlist、ANGLE APK/system library 等条件控制；Vulkan 1.4/VPA16 能力基线不能推出所有 GLES 应用默认经 ANGLE-on-Vulkan。
   - 建议：把 Android 16 图形栈拆成 Vulkan 能力/launch requirement、HWUI/Skia 后端、GLES→ANGLE 策略三层；删除“Vulkan 已成为默认图形 API”“答案是 ANGLE”这类平台级结论，统一为“在配置了 ANGLE 的设备/应用上”。
2. [P1] [原理断裂/TBR 成本模型] L385（overdraw 与 tile buffer 写回次数）
   - 问题：正文写“减少 overdraw 会同时减少重复计算和 tile buffer 写回次数”。在移动 TBR 架构中，单个 render pass 内同一 tile 通常在片上 tile buffer 中完成多次 fragment/blend，最后按 tile/attachment store 写回；overdraw 主要增加 fragment work、texture fetch、blend 和片上带宽，不会按像素 overdraw 次数线性增加最终 tile resolve/writeback 次数。
   - 建议：改为分层成本模型：overdraw 增加片上 fragment/blend/texture 工作；外部内存写回主要受 render pass/store、render target 切换、MSAA/resolve 和是否读取/保留附件影响。
3. [P1] [原理边界/TBR clear 语义] L389（“部分清除是免费的”）
   - 问题：正文标题称“部分清除是免费的”，但示例实际对应 Vulkan render pass 开始时的 VK_ATTACHMENT_LOAD_OP_CLEAR 或全附件 clear。TBR 上便宜的是可由 tile 初始化替代 LOAD 的整附件/整 renderArea clear；scissor/partial clear、pass 中途 clear 或需要保留旧内容的场景可能仍需要 load、store 或额外 draw/fast-clear metadata 处理，不能统一写成免费。
   - 建议：将标题和正文改为“整附件 clear / LOAD_OP_CLEAR 可避免 LOAD 旧内容”；单列 partial/scissored clear 的条件和驱动差异，避免把 full clear 优化误用到局部清除。
4. [P1] [待验证事实/源码证据不足] L447-L451（Gralloc AIDL V2 sub-allocation）
   - 问题：正文主句仍写“Gralloc AIDL V2 在设计方向上引入内部子分配”。复核 android-16.0.0_r1 的 hardware/interfaces/graphics/allocator/aidl 后，公开 IAllocator 仅暴露 allocate/allocate2/isSupported 等接口，未看到 sub-allocation 方法签名；章节也承认缺少 VTS/CTS 或 vendor 实现证据。当前主句会被读作已验证平台事实。
   - 建议：将该段降级为“16KB 页可能促使部分 vendor 在 Gralloc 内部做小 buffer 池化/子分配，[待验证]”；在补齐 VTS、vendor mapper/allocator 或 source.android 证据前，不把它写成 Android 16/Gralloc AIDL V2 的确定设计。

### 7.3 卡顿分析方法论
1. [P1] [原理断裂/诊断归因过强] L633-L635（Binder dispatch 延迟判断树）
   - 问题：正文把 (server_ts - client_ts) 持续 >5ms 直接归因为 Binder 线程池饱和。Perfetto android_binder_txns 的 server_ts-client_ts 只能说明从客户端发起到服务端 slice 开始之间存在等待，原因可能是服务端 Binder 线程池满、服务端线程 Runnable 调度延迟、CPU 竞争、优先级/冻后台、驱动队列或 oneway 排队；单靠这个差值不能直接定性“所有 worker thread busy”。
   - 建议：把判断树改成“dispatch/queue 候选”。确认线程池饱和需同时检查服务端 Binder:* 线程数量、thread_state/Runnable、server_dur 分布、进程 CPU 负载、是否存在 oneway spam；>5ms 只能作为报警阈值，不作为单因结论。
