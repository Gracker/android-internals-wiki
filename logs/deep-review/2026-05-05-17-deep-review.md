#### 具体问题
1. [P0] [源码错误/版本差异] L69-L71 版本边界：FrameTimeline jank type 与 Android 8-11 gfx/view trace tag
   - 问题：文中把 TRACE_TAG_GRAPHICS 写成 1L << 4、TRACE_TAG_VIEW 写成 1L << 5，并给出组合值 0x30。AOSP Trace.java 中 GRAPHICS=1L<<1、VIEW=1L<<3，0x30 实际对应 WEBVIEW + WINDOW_MANAGER；同段的 SurfaceFlingerDeadlined 也不是 Perfetto FrameTimeline 文档中的 jank type。
   - 建议：旧版 setprop bitmask 不要再写 0x30；优先改为 Perfetto/atrace category：gfx、view、sched、input、wm。如果保留 bitmask，只能写 gfx+view=0x0A，并把 SurfaceFlinger jank type 改为 SurfaceFlingerCpuDeadlineMissed / SurfaceFlingerGpuDeadlineMissed 等文档枚举。
   - 依据：AOSP frameworks/base/core/java/android/os/Trace.java；Perfetto FrameTimeline docs
2. [P0] [工具 SQL 错误] L472-L473 场景化 Perfetto SQL 快速筛选
   - 问题：actual_frame_timeline_slice 的非 jank 行在 Perfetto 示例中 jank_type='None'，不是 NULL；`jank_type IS NOT NULL` 会把非 jank 帧也捞出来。BufferStuffing 的 SQL 枚举值示例为 `Buffer Stuffing`（带空格），`LIKE '%BufferStuffing%'` 查不到典型行。
   - 建议：掉帧初筛改为 `WHERE jank_type IS NOT NULL AND jank_type != 'None'`（或按实际 Trace Processor 版本兼容空值）；BufferStuffing 改为 `LIKE '%Buffer Stuffing%'`，并标注仅适用于 Android 12+ FrameTimeline trace。
   - 依据：Perfetto FrameTimeline docs: actual_frame_timeline_slice SQL 示例
3. [P1] [原理断裂/观察点错误] L395 耗电快或发热伴随卡顿：thermal 状态轨道
   - 问题：文中写 `power.thermal_*` ftrace 事件，容易让读者按 power 事件组配置 trace。Linux thermal tracepoint 位于 thermal 事件组，例如 thermal_temperature、cdev_update、thermal_zone_trip；Android 设备上 thermal 轨道还经常依赖厂商 HAL/Stats/日志，不能写成稳定的 `power.thermal_*`。
   - 建议：改为：优先看 CPU/GPU freq、thermal HAL/Stats/厂商温控日志；如抓 ftrace，使用 `thermal/thermal_temperature`、`thermal/cdev_update`、`thermal/thermal_zone_trip` 等可用事件，并说明设备内核可能裁剪。
   - 依据：Linux kernel drivers/thermal/thermal_trace.h
4. [P3] [数据支撑] L479 “10GB trace 用 SQL 效率高一个数量级”可保留为经验判断，但发布前最好补一条内部实测或收窄为“通常更快”。

#### 具体问题
1. [P0] [源码错误] L775-L776 PowerMonitor API 常量表
   - 问题：文中把 POWER_MONITOR_TYPE_MEASUREMENT 写成 0、POWER_MONITOR_TYPE_CONSUMER 写成 1。AOSP PowerMonitor.java 中 CONSUMER=0，MEASUREMENT=1；当前表格把两者完全反了。
   - 建议：改为 `POWER_MONITOR_TYPE_CONSUMER = 0`、`POWER_MONITOR_TYPE_MEASUREMENT = 1`，并保留 API 35/flag 边界。
   - 依据：AOSP frameworks/base/core/java/android/os/PowerMonitor.java
2. [P0] [源码错误/工具配置错误] L545-L546、L796-L818 Perfetto power rails 配置与数据源名
   - 问题：Perfetto 配置片段使用 `battery_polls_ms`，但 AndroidPowerConfig proto 字段是 `battery_poll_ms`；后文仍写 `android.power_rails` 数据源和 `power_rails: true`，而 Perfetto 数据源 descriptor 是 `android.power`，字段是 `collect_power_rails`。当前示例不能作为可运行配置。
   - 建议：统一为 `data_sources { config { name: "android.power" android_power_config { battery_poll_ms: 1000 collect_power_rails: true } } }`；正文保留 SQL 表 `android_power_rails_counters` 时，明确它是 trace processor 表，不是数据源名。
   - 依据：Perfetto android_power_config.proto；AndroidPowerDataSource descriptor
3. [P1] [原理断裂/版本差异] L758-L766 PerformanceHintManager 与 Power Efficiency Mode
   - 问题：小节声称 Android 15 Power Efficiency Mode 是重点，但核心 API 列表只列 createHintSession/reportActualWorkDuration/updateTargetWorkDuration，缺少真正打开节能偏好的 `PerformanceHintManager.Session#setPreferPowerEfficiency(boolean)`；读者无法区分 API 31 的普通 ADPF 会话与 API 35/flag 的 Power Efficiency 扩展。
   - 建议：补 `setPreferPowerEfficiency(boolean)`，标注 `FLAG_ADPF_PREFER_POWER_EFFICIENCY` / API 35 边界，并把 create/report/update 表述为会话基础 API，不要把它们写成 Android 15 新增能力。
   - 依据：AOSP frameworks/base/core/java/android/os/PerformanceHintManager.java
4. [P3] [数据支撑] L101 “整机功耗可以降到 1mA 以下”缺少设备/屏幕/基带/电池计量条件，建议发布前收窄为“可降到 mA 级”。
