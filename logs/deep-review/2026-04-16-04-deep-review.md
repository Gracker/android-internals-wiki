### 维度 1：源码引用准确性
- 评分：3/5
- 问题数：3
- 具体问题：
  1. [P0] ViewRootImpl.relayoutWindow() 代码片段中 `mTmpFrames.mPendingBackInsets` 参数不存在。AOSP ViewRootImpl 的 mTmpFrames（WindowFrames 类型）包含 mPendingContentInsets、mPendingVisibleInsets、mPendingStableInsets、mPendingOutsets，但从未有 mPendingBackInsets 字段。整个参数列表是旧版本和新版本的混合体，不具有参考价值。标注的源码路径正确但代码内容不匹配。
  2. [P1] SurfaceControl.Transaction 伪代码中 `t.setSize(surfaceControl, width, height)` 方法不存在。Transaction API 中没有 setSize()——Surface 尺寸通过 SurfaceControl.Builder.setSize() 在创建时设置，运行时尺寸变更使用 setCrop() 或 setMatrix()。虽然标注为"伪代码"，但作为技术书籍，伪代码应使用真实的 API 名称或明确标注哪些是简化。建议改为 `t.setCrop(surfaceControl, new Rect(0, 0, width, height))` 或改为使用 setMatrix()。

### 维度 2：原理链完整性
- 评分：3/5
- 问题数：4
- 具体问题：
  1. [P1] 缺少 DisplayContent/DisplayArea/WindowToken 层级结构的说明。现代 Android（10+）WMS 的窗口组织是 DisplayContent → DisplayArea.Group → DisplayArea（Task/WindowContainer）→ WindowToken → WindowState 的树形结构。当前章节对 WMS 内部数据结构的描述停留在 WindowState 一层，读者无法理解 performLayout() 如何遍历窗口树、Z-order 如何确定。这是理解 WMS 性能行为的基础骨架。
  2. [P1] StartingWindow 创建流程（步骤 3）"WMS 立即创建 StartingWindow"过于简化。实际流程涉及：WMS 通过 StartingData/SplashScreenStartingData 创建 StartingWindow → PhoneWindow + DecorView 构建视图 → 从 App 主题提取 windowBackground 或 SplashScreen 配置 → SurfaceControl 提前分配。当前描述跳过了关键的中间对象（StartingData、StartingSurfaceDrawer），导致读者对"为什么 StartingWindow 不需要 App 进程参与"缺少机制层面的理解。
  3. [P1] Window 动画节缺少动画值计算原理。章节说"WindowAnimator 计算所有参与动画的 Window 的 transform"，但没有解释动画值从哪来——是 SpringAnimation？是 Choreographer#FRAME_CALLBACKS？还是 WindowAnimator 自己维护的 Animation 对象？读者看完后知道"每帧提交 Transaction"，但不知道"每帧的 transform 值怎么算"。
  4. [P2] relayoutWindow 内部流程中 `mGlobalLock`（WindowManagerGlobalLock）的讨论只在 FAQ 中一笔带过。这把锁是 WMS 性能分析的核心——relayoutWindow、performLayout、动画更新等操作都需要持有它。缺少"哪些操作持有 mGlobalLock"的系统性说明。

### 维度 3：版本差异覆盖
- 评分：3.5/5
- 问题数：2
- 具体问题：
  1. [P1] 版本表中 Android 12 "SurfaceControl.Transaction 成为标准 API"描述不够精确。SurfaceControl 作为公开 API 从 Android 9（API 28）开始暴露，Transaction API 在 Android 10（API 29）正式可用。Android 12 的变化是 Transaction API 的进一步完善（如 addToTransaction()、mergeTransaction() 等），不是"成为标准"的起点。建议修正为更精确的描述。
  2. [P2] 缺少 BLASTBufferQueue 引入（Android 12）对 Surface 创建流程的影响。章节描述的 Surface 创建链路（步骤 7"WMS 将 SurfaceControl 包装成 Surface 通过 Binder 返回给 App"）在 Android 12+ 中发生了变化——BLASTBufferQueue 替代了 BufferQueue 作为 App 端的 buffer 管理，Surface 的传递方式也相应变化。对标注 applicable_versions 为 12-17 的章节，这个差异应该被覆盖。

### 维度 4：知识盲区
- 评分：3/5
- 盲区数：3
- 具体问题：
  1. [P1-高] Traversal vs Relayout 的触发条件区分。App 侧的 requestLayout() 触发的是 in-app traversal（measure/layout/draw），不需要 Binder 调用 WMS；但 Window 大小变化、visibility 变化等会触发 relayoutWindow（Binder 调用）。读者不清楚"什么情况下 App 自己处理就行，什么情况下必须走 WMS"，这是实际性能分析中最常见的困惑。
  2. [P2-中] InputWindowInfo 的构建和更新机制。章节提到"WMS 维护 Window Z-order 和区域信息给 InputDispatcher 做 hit-test"，但没有解释 InputWindowInfo 对象的构建时机、更新频率、以及跨进程传递方式（shared memory? binder?）。
  3. [P2-中] RelayoutWindow 的典型耗时分布。章节说超过 16ms 可能有问题，但没给出正常情况下的典型范围（1-5ms? 5-10ms?），也没有区分"Surface 创建型 relayout"和"纯属性更新型 relayout"的耗时差异。
