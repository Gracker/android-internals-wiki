- 统计：P0 1 / P1 2 / P2 2 / P3 0

具体问题：
  1. [P0] L173-L176 Large Object Space 实现选择 — 正文把 FreeListSpace 写成“arm64 设备”、LargeObjectMapSpace 写成“非 arm64 设备”。AOSP android-15/16 的默认选择在 Heap::kDefaultLargeObjectSpaceType 中由 USE_ART_LOW_4G_ALLOCATOR 决定：true→kFreeList，false→kMap；不是简单 arm64/非 arm64 二分。 建议：改为按 USE_ART_LOW_4G_ALLOCATOR / kDefaultLargeObjectSpaceType 说明；如要解释常见设备落点，另补构建宏与 ABI/产品配置的对应证据。
  2. [P1] L151-L159、L260-L268 Android 15+ CMC/BumpPointerSpace — 正文多处暗示 Android 15+ 已切到 CMC + BumpPointerSpace，但 AOSP Runtime::Init 仍按 gUseUserfaultfd、sysprop、kernel userfaultfd/MREMAP_DONTUNMAP 能力和命令行 GC 类型决定；不满足条件时仍可能走 CC/RegionSpace。 建议：把“Android 15+ 使用 CMC”改为“Android 15 AOSP 具备更完整 CMC/BumpPointerSpace 路径，启用取决于 gUseUserfaultfd/系统属性/内核能力/构建配置”；补 mark_compact.cc::ShouldUseUserfaultfd、runtime.cc 选择 background_gc 的源码锚点。
  3. [P1] L296-L299 Generational CMC 配置 — `gUseUserfaultfd` 不是 runtime.cc Init 阶段的局部开关，而是 mark_compact.cc 中由 ShouldUseUserfaultfd() 静态初始化的全局常量；`use_generational_cmc` 也不是系统属性名。AOSP android-16 中 Runtime::Init 使用变量 `use_generational_gc`，ShouldUseGenerationalGC() 先看 ART flag `use_generational_cmc()`，再读 `persist.device_config.runtime_native_boot.use_generational_gc`。 建议：按实际符号重写：mark_compact.cc::ShouldUseUserfaultfd / KernelSupportsUffd / ShouldUseGenerationalGC，runtime.cc 中 `use_generational_gc = (kUseBakerReadBarrier || gUseUserfaultfd) && xgc_option.generational_gc && ShouldUseGenerationalGC()`。
  4. [P1] L451-L458 JIT Code Cache — 正文写“默认大小约 4-16MB”。AOSP android-16 `runtime/jit/jit_code_cache.h` 中 `JitCodeCache::GetInitialCapacity()` release 默认约 64KB（至少 2*page size），`kMaxCapacity = 64 * MB`，runtime options 默认使用 initial/max 两个值。4-16MB 缺源码或设备配置来源。 建议：改为“初始容量很小，运行中按需增长，上限默认 64MB（可由 -Xjitcodecachesize / runtime option 调整）”；如保留 4-16MB，必须补设备属性或实测 dumpsys/trace 证据。
  5. [P2] L309-L324、L527-L545 GC baseline — Young GC 1-3ms、Pause 1-5ms、GC 吞吐量 >98%/95%、Young GC 每 2-5 秒一次等基线缺设备、应用类型、刷新率、collector、采样窗口。 建议：补一组 Perfetto/GC log 样例，明确 Android 版本、collector、heap 上限、刷新率、场景；或降级为“示例阈值，需按业务基线调整”。
