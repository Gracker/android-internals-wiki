   - 建议：核 `MessageQueue.java` ChangeId 常量名后再保留命令；不确定则标 [待验证]。

### 具体问题
1. [P1][源码行为] Glide 的 BitmapPool 实现 → onTrimMemory 顺序
   - 问题：`Glide.trimMemory()` 确实会先遍历 `RequestManager.onTrimMemory(level)` 再清 MemoryCache/BitmapPool/ArrayPool，但正文括号写“暂停未完成请求”过度泛化。Glide 4.16 `RequestManager.onTrimMemory()` 只有在 `level == TRIM_MEMORY_MODERATE && pauseAllRequestsOnTrimMemoryModerate` 时才 `pauseAllRequestsRecursive()`；默认不等于收到 trim 就暂停请求。
   - 建议：保留“通知 RequestManager”顺序，删除“暂停未完成请求”或改成条件性描述；把请求暂停主路径放到 lifecycle `onStop()`。
2. [P2][数据缺失] Hardware Bitmap / 首帧纹理上传
   - 问题：“1080p RGBA upload 4-8ms”缺 GPU/设备/负载来源，且两处未标 [待验证]。
   - 建议：补测量条件或标 [待验证]。
3. [P2][原理边界] inBitmap 工作原理
   - 问题：正文只讲 API 19+ 规则，未提示 API 11-18 的 inBitmap 限制。
   - 建议：补 pre-API 19 仅同尺寸/同配置、历史上 JPEG 等限制，避免低 minSdk 项目踩坑。
4. [P2][原理边界] BitmapPool 为什么需要复用
   - 问题：“GC 本身不耗时（通常 <1ms）”过度简化；ART 并发阶段仍占 CPU，Full/compact pause 可显著超过 1ms。
   - 建议：改成区分 Concurrent GC pause、并发阶段 CPU 占用、Full GC 边界。
