#### 具体问题

1. [P0] [工具 SQL 错误] L227-L238、L375-L384 Perfetto 核心迁移 SQL
   - 问题：两处 SQL 都从 `thread_state` 读取 `cpu` 字段并用 `state = 'Running'` 统计运行核心；Perfetto 官方调度运行片段应使用 `sched`/`sched_slice` 表，关键列是 `cpu, utid, ts, dur, end_state`。按现有写法在常见 Trace Processor schema 下不可运行或统计口径错误。
   - 建议：改用 `sched` 表，例如 `SELECT s.cpu, COUNT(*) slices, SUM(s.dur)/1e6 total_ms FROM sched s JOIN thread t USING(utid) WHERE t.tid=<target_tid> GROUP BY s.cpu ORDER BY s.cpu;`；全局 CPU 分布同样从 `sched` 聚合。

2. [P1] [原理断裂/源码准确性] L257-L258 schedutil 线性映射公式
   - 问题：正文写 `target_freq = max_freq * util / capacity`，并举 60% util → 60% max_freq。Linux schedutil 实际会经过 `map_util_perf()`/`sugov_effective_cpu_perf()` 等路径加入性能裕量、uclamp、RT/DL 带宽下限、rate limit 和 driver 约束；经典文档口径也包含约 1.25 的 headroom。当前公式会让读者低估 schedutil 的升频策略。
   - 建议：把该公式改成“教学近似”，紧接说明现代内核会加入 headroom/uclamp/bw_min 等修正；若给公式，写成近似 `next_freq ≈ 1.25 * max_freq * util / capacity`，并标注会受 policy/driver/thermal 限制。
