## 审查结果

### 维度 1：源码引用准确性
- 评分：3/5
- 问题数：4
- 具体问题：
  1. [P0] 参考资料列出的 `frameworks/base/services/core/java/com/android/server/input/InputDispatcher.java` 不存在。InputDispatcher 是 C++ 类，实际路径为 `frameworks/native/services/inputflinger/dispatcher/InputDispatcher.cpp`。Java 侧的入口是 `InputManagerService.java`。
  2. [P0] ViewPager2 的 `offscreenPageLimit` 默认值错误。章节称「默认值为 1（左右各保留 1 页）」，实际 `OFFSCREEN_PAGE_LIMIT_DEFAULT = -1`，意味着使用 RecyclerView 自身的缓存策略，不显式保留任何页面。设为 1 才是「左右各保留 1 页」，但那不是默认行为。
  3. [P1] 验证标记声称「AOSP android-16.0.0_r1, frameworks/base/fragment/java/androidx/fragment/app/FragmentManager.java」——AndroidX Fragment 不在 `frameworks/base` 树中，它在独立的 AndroidX 仓库（`androidx/fragment/fragment/src/main/java/androidx/fragment/app/FragmentManager.java`）。
  4. [P1] Activity 启动路径描述使用 `ActivityTaskManager.getService().startActivity()`，但 `ActivityTaskManager` 从 Android 10（API 29）引入。Android 8-9 使用的是 `ActivityManagerNative.getDefault().startActivity()`。章节声明 `applicable_versions: 8.0-16`，但启动路径描述只适用于 10+。

### 维度 2：原理链完整性
- 评分：3.5/5
- 问题数：3
- 具体问题：
  1. [P1] FragmentFactory 代码示例有逻辑缺陷。`PreloadFragmentFactory.instantiate()` 中调用 `fetchPreloadData()` 获取预加载数据——但这是在主线程上执行的同步调用。如果「预加载数据」需要 IO（网络/数据库），反而会拖慢 Fragment 创建。代码示例没有说明 `fetchPreloadData()` 必须是非阻塞的，容易误导读者在 Factory 中做同步数据获取。
  2. [P1] `setReorderingAllowed(true)` 的描述不准确。章节称「让系统并行处理多个 Fragment 操作，减少事务串行化带来的等待」，但 `setReorderingAllowed(true)` 的实际作用是允许 FragmentManager 重排操作顺序（如将 remove(A)+add(B) 优化为 replace(A,B)），减少不必要的生命周期回调。这不是并行执行，是操作合并优化。
  3. [P2] `commitNow()` 的限制条件描述不精确。章节说「在 onResume() 之后调用可能产生冲突导致 IllegalStateException」，但实际约束是 `commitNow()` 不能在 `onSaveInstanceState()` 之后调用（因为会影响已保存的状态）。`onResume()` 和 `onSaveInstanceState()` 之间没有必然的时序矛盾。

### 维度 3：版本差异覆盖
- 评分：2.5/5
- 问题数：3
- 具体问题：
  1. [P1] 版本演进中「Android 9.0（API 28）：引入 ViewPager2（通过 AndroidX 发布）」——ViewPager2 是 AndroidX 库，首个 alpha 于 2019 年 2 月发布，稳定版 1.0.0 于 2019 年 11 月发布。它不与任何 Android OS 版本绑定，归入「Android 9.0」条目是误导。应单独列出 AndroidX 库的版本。
  2. [P1] 版本演进中「Android X Fragment 1.2.0：引入 setMaxLifecycle()」——`setMaxLifecycle()` 实际在 Fragment 1.1.0 引入（1.1.0-alpha05 首次出现），不是 1.2.0。
  3. [P2] 章节声明 applicable_versions 8.0-16，但缺失以下版本差异：Android 10 的 ActivityTaskManager 迁移、Android 12 SplashScreen 对 Activity 跳转感知的影响、Android 12+ async layout inflation、Compose Navigation 的性能特性。

### 维度 4：知识盲区
- 评分：2.5/5
- 盲区数：4
- 具体盲区：
  1. [P1 高] Jetpack Navigation Component 完全未提及。Navigation 是现代 Android 页面导航的标准方案（NavGraph、deep link、transition animation），其性能特征（NavGraph inflate 开销、Fragment swap 优化）与本章高度相关。
  2. [P1 中] Compose Navigation 未提及。如果 applicable_versions 到 Android 16，Compose 的页面切换性能是不可忽略的话题（Compose relocate 节点复用 vs 传统 inflate）。
  3. [P2 低] DeepLink 响应速度在 outline 中列为扩展话题但正文完全未涉及。DeepLink 比普通 startActivity 多一步 Intent Filter 解析，延迟差异值得分析。
  4. [P2 低] ActivityOptions 和转场动画（Activity Transition API）对 Activity 跳转感知延迟的影响未讨论。合理的转场动画可以掩盖真实的加载时间。

### 维度 5：数据与案例支撑
- 评分：2/5
- 问题数：5
- 具体问题：
  1. [P2] Binder IPC「每次约 1-5ms」——无测量来源或方法论。实际值受负载、payload 大小、Binder 线程池状态影响较大。
  2. [P2] Activity 对象创建「5-15ms」——无来源。应标注在什么设备、什么 Android 版本上的测量结果。
  3. [P2] 「理想情况下的点击响应延迟大约是 30-60ms」——这个数字是各阶段估计值简单相加的结果，无实测验证。
  4. [P2] Ripple「16ms 内就开始扩散」——无来源。Ripple 的启动时间取决于 Choreographer 的 VSync 同步时机。
  5. [P2] 四个场景的 Perfetto Trace 截图全部为 [待补充] 占位符，无任何实际 Trace 分析案例支撑。对于一本以 Perfetto 为核心分析工具的书，这是较大的缺失。

### 维度 6：交叉引用一致性
- 评分：4/5
- 问题数：1
- 具体问题：
  1. [P2] 章节引用 RAIL 模型并链接到 `developer.android.com/topic/performance/vitals`，但 RAIL 是 Chrome 团队的 Web 性能模型（web.dev/rail），Android Vitals 是独立的 Android 性能监控方案。两者不应混为一谈。建议区分引用：RAIL 模型引用 web.dev，Android 响应时间阈值引用 Android Vitals 文档。
