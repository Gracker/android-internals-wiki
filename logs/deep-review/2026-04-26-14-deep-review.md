## 问题清单
P0-1. [P0] 9.1 “ANR 机制的核心流程 / 第一阶段：注册超时” — 文中把 BroadcastReceiver 超时写成固定“前台 10 秒、后台 60 秒”。该表述只适合 Android 13 及以下的排查口径；Android 14+ 官方口径是前台 10-20 秒、后台 60-120 秒。AOSP android-14.0.0_r1 的 BroadcastQueueModernImpl 会先发 soft timeout，再按 app.getCpuDelayTime() 追加不超过 soft timeout 的 hard timeout。
   - 建议：把 9.1 的固定值改成“旧版典型值”，并补充 Android 14+ soft/hard timeout 与 CPU starvation / cold start 计入窗口的说明，或显式跳转到 9.2。
   - 证据：AOSP android-14.0.0_r1: BroadcastQueueModernImpl.java dispatchReceivers() 记录 lastCpuDelayTime 并发送 MSG_DELIVERY_TIMEOUT_SOFT；deliveryTimeoutSoftLocked() 用 getCpuDelayTime() 计算 hard timeout。外部 review 已命中同一问题。
P0-2. [P0] 9.1 “AMS 中 ANR 的核心代码路径 / InputConnection ANR” — 文中写“InputMethodManagerService#onInputEvent timeout”，但 AOSP android-14.0.0_r1 的 InputMethodManagerService 中没有该 timeout 判定点。InputConnection 相关无响应更应落到 InputDispatcher 的 dispatching timeout / waitQueue 机制，IME/IMMS 是输入法交互路径的一部分，不是该 5s ANR 的直接判定者。
   - 建议：删除 `InputMethodManagerService#onInputEvent timeout` 说法，改为说明 IME/InputConnection 场景最终仍需回到 InputDispatcher 的 input dispatch timeout，并补 AOSP 路径 `frameworks/native/services/inputflinger/dispatcher/InputDispatcher.cpp`。
   - 证据：AOSP android-14.0.0_r1: InputDispatcher.cpp 定义 DEFAULT_INPUT_DISPATCHING_TIMEOUT 并对 waitQueue/AnrTracker 处理超时；InputMethodManagerService.java 未检索到 onInputEvent timeout。
P1-1. [P1] 9.2 “JobService callback ANR 与 job 超时的边界” — 章节把 JobService callback ANR 写成“几秒级”，但 sources 未列 AOSP JobScheduler 路径，也未给出 Android 14/15 的实际等待常量。
   - 建议：补充 `frameworks/base/apex/jobscheduler/service/java/com/android/server/job/JobServiceContext.java`：`OP_TIMEOUT_MILLIS = 8 * 1000 * Build.HW_TIMEOUT_MULTIPLIER`；`handleOpTimeoutLocked()` 对 STARTING/STOPPING 生成 `No response to onStartJob/onStopJob` 并调用 `ActivityManagerInternal.appNotResponding()`。
   - 证据：AOSP android-14.0.0_r1 / android-15.0.0_r1: JobServiceContext.java。
P1-2. [P1] 9.3 版本演进：Android 14 “Perfetto 中新增 android.anr track” — “android.anr track” 缺少可复核证据。AOSP android-15 SDK 可见的是 `AnrLatencyTracker` 写入 Trace slice/counter（如 `anrRecordPlacedOnQueue`、`anrProcessing`、`dumpStackTraces()`）和 statsd `ANR_LATENCY_REPORTED`，未能确认存在名为 `android.anr` 的 Perfetto track / SQL 表。
   - 建议：不要直接写 `android.anr track`。改为可验证表述：Android 13/14+ 增加 ANR latency trace/statsd 观测点；如保留 track 名，需补 Perfetto trace 示例或 SQL schema 证据。
   - 证据：AOSP android-35 SDK source: com/android/internal/os/anr/AnrLatencyTracker.java；FrameworkStatsLog 中 ANRLatencyReported atom。
P1-3. [P1] 9.3 frontmatter applicable_versions — frontmatter 写 `Android 17 (API 36)`，但正文版本演进又把 Android 16 标为 API 36；9.1/9.2 也写 Android 17 (API 37)。同一主题簇版本声明不一致。
   - 建议：统一 9.1/9.2/9.3 的适用版本。若 Android 17 API level 尚未发布，写到 `Android 17 [待确认]`；若按当前书内约定，9.3 应改为 Android 17 (API 37)。
   - 证据：9.3 frontmatter 与同文件版本演进段、9.1/9.2 frontmatter 互相矛盾。
P2-1. [P2] 9.1 “ANR 信息的产出 / traces.txt” — Android 10+ trace 文件命名与 Android 12/13 的按进程命名改进被合并成一句，版本线不够清楚。
   - 建议：拆成 Android 10 从单一 traces.txt 转为 /data/anr/anr_*，Android 12/13 再补按进程/时间命名与可靠性改进。
   - 证据：见正文与源码复核
P2-2. [P2] 9.1 “ANR 信息的产出” — 只列 traces/event log/dropbox，未提 Android 11+ ApplicationExitInfo 和 Android 16+ system-triggered profiling 作为线上回捞入口。
   - 建议：在概览节补一段“现代线上采集入口”，详细方法跳转到 9.3。
   - 证据：见正文与源码复核
P2-3. [P2] 9.2 “Service Timeout” — `Build.HW_TIMEOUT_MULTIPLIER` 出现但未解释默认值和适用边界。
   - 建议：补充默认值通常为 1，主要用于特殊硬件/测试环境放大 timeout，避免读者误解 20s/200s 不是默认值。
   - 证据：见正文与源码复核
