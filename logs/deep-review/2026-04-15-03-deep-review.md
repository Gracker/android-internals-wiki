## 审查结果

### 维度 1：源码引用准确性
- 评分：3/5
- 问题数：5
- 具体问题：
  1. [P1] "BLASTBufferQueue::onFirstRef() 会把 setMaxDequeuedBufferCount(2) 设成安全默认值" — 实际上在 AOSP android-11.0.0_r48 中，setMaxDequeuedBufferCount(2) 是在 BLASTBufferQueue 构造函数体中直接调用的，不是在 onFirstRef() 回调里。构造函数签名是 BLASTBufferQueue(const std::string& name, const sp<SurfaceControl>& sc, int width, int height, int32_t format)，在其函数体内依次调用 createBufferQueue()、setMaxAcquiredBufferCount(1)、setMaxDequeuedBufferCount(2)。写错位置会误导读者去 onFirstRef() 里找这行代码。
  2. [P1] BLAST 代码片段中的 Transaction::setBuffer() 调用传了 7 个参数 (mSurfaceControl, buffer, fence, bufferItem.mFrameNumber, mProducerId, releaseBufferCallback, dequeueTime)，这是 Android 12+ 的签名。Android 11 的 setBuffer() 只有 5 个参数（没有 mProducerId 和 dequeueTime）。代码片段标注了来自 AOSP main，但同节又说 BLAST 从 Android 11 开始存在，读者无法判断这个签名适用于哪个版本。建议明确标注版本或拆分为 Android 11 vs Android 12+ 两版签名。
  3. [P2] BufferSlot::BufferState 代码片段使用 uint32_t 计数器（mDequeueCount、mQueueCount、mAcquireCount），但 AOSP 部分版本实际使用的是 bool 标志（mDequeued、queuedByProducer、acquired）。计数器方案确实在某些版本中存在（用于支持 shared buffer mode 的计数叠加），但不一定是所有版本的标准实现。[待验证] 具体哪个 AOSP tag 使用了计数器方案。
  4. [P2] dequeueBuffer() 签名展示的是 Android 10-11 时期的版本（有 outBufferAge 和 FrameEventHistoryDelta 参数）。Android 13+ 的签名增加了 outMaxBufferCount 等参数。代码块标注路径为 AOSP main 但签名已过时。建议标注具体 AOSP tag 或标注为简化签名。
  5. [P2] "AOSP 注释给出的状态表很清楚" — 但文中没有给出这个状态表的链接或引用。对于想自行验证的读者，缺少足够的定位信息。

### 维度 2：原理链完整性
- 评分：3/5
- 问题数：4
- 具体问题：
  1. [P1] Consumer 路径严重不对称。全文详述了 producer 侧 dequeueBuffer -> requestBuffer -> queueBuffer 三步，但 consumer 侧的 acquireBuffer -> 消费 -> releaseBuffer 只在 fence 小节中提到一次 releaseBuffer。acquireBuffer 仅在 Perfetto 节提及"如果 trace 里没有直接露出 acquireBuffer 这种 slice 名字"。读者看完只能理解"生产者怎么填 buffer"，对"消费者怎么取 buffer、怎么归还"几乎没有建立心智模型。建议增加一个与 producer 三步对称的 consumer 三步说明。
  2. [P1] BufferQueue 四组件架构完全未提及。createBufferQueue(&mProducer, &mConsumer) 内部创建了 BufferQueueCore，然后分别包装为 BufferQueueProducer（实现 IGraphicBufferProducer）和 BufferQueueConsumer（实现 IGraphicBufferConsumer）。这四个类的关系是 BufferQueue 架构的骨架，不理解它就无法理解为什么 producer/consumer 操作的是同一个 slot 集合。sources 列表引用了 BufferQueueCore.cpp 但正文从未解释它。
  3. [P2] GraphicBuffer 的跨进程共享机制是黑盒。文中说"跨进程传的主要是 slot、fence 和元数据"，但没解释 GraphicBuffer 句柄本身是怎么跨进程映射的（Gralloc 分配 -> handle 传递 -> mmap）。这个机制决定了为什么 BufferQueue 能零拷贝。不解释这一步，"不复制像素"的论断缺少因果支撑。
  4. [P2] maxBufferCount / maxAcquiredBufferCount / maxDequeuedBufferCount 三者关系未展开。三缓冲的成因（maxDequeued=2 + consumer acquired 1 = 3 total）只提了一句，但没有解释为什么修改这些参数会影响 dequeueBuffer() 的阻塞行为。这是实际调优中最常碰到的问题。

### 维度 3：版本差异覆盖
- 评分：2/5
- 问题数：3
- 具体问题：
  1. [P1] 版本表只有 2 行（Android 4.1 和 11），但 applicable_versions 声称覆盖到 Android 17。Android 12（BLAST 取代旧 BufferQueue 成为窗口唯一路径）、Android 13（帧率覆盖 frame rate override）、Android 14+（预测性返回手势影响 BufferQueue 行为）都没有覆盖。特别是 Android 12 强制 BLAST 是一个关键里程碑：从此旧 BufferQueue 在窗口路径上被完全移除，理解这个分水岭对读者区分"兼容旧路径"和"只走 BLAST"至关重要。
  2. [P2] 文末提到 frame rate override、maxBufferCount 等说法"必须分别拿源码落点来支撑"——这个自我约束是好的，但结果是什么都没写。对于一本技术书籍，在 applicable_versions 覆盖 4.1-17 的情况下，至少应该列出 Android 12-17 的关键变化方向（即使标注为 [待验证]）。
  3. [P2] Android 8 Treble 对 Gralloc HAL 的重构（从直接 so 调用变为 HIDL 接口）未提及。这影响 GraphicBuffer 的分配路径，与 BufferQueue 紧密相关。

### 维度 4：知识盲区
- 评分：3/5
- 盲区数：4
- 具体问题：
  1. [高] BufferQueue 的阻塞与唤醒机制：当所有 slot 都被占用时，dequeueBuffer() 会阻塞 producer 线程。AOSP 使用 mDequeueCondition（一个 ConditionVariable）来实现等待/唤醒。消费者 releaseBuffer() 后通过 mDequeueCondition.notify_all() 唤醒等待的 producer。这个机制直接关联 RenderThread 卡在 dequeueBuffer() 的根因分析，当前完全缺失。
  2. [高] 不同 Surface 类型的 BufferQueue 配置差异。普通窗口、SurfaceView、视频播放器使用不同的 BufferQueue 配置（async mode、buffer count、消费者类型），导致阻塞行为差异很大。当前只讲了"普通窗口路径"，但读者在实际分析中碰到 SurfaceView 或媒体路径时会发现行为完全不同。
  3. [中] attachBuffer() / detachBuffer() 路径。这是 BufferQueue 的另一组 API，允许把已有的 GraphicBuffer 绑定到某个 slot 或从 slot 解绑。外部视频解码器常用这条路径。完全未提及。
  4. [中] shared buffer mode 的具体使用场景。文中多次提到 shared buffer mode，但没有解释谁在用、为什么用、什么场景下 mShared=true。当前读者只知道"它存在"，不知道"什么时候碰到它"。

## 核心发现

### 做得好的地方
1. 核心论点准确：BufferQueue 的本质是 slot 共享而非像素传递，这个定位精准且有力
2. BLAST 的核心价值解释到位：buffer 与 geometry transaction 按 frameNumber 绑定，不是简单的"少一次 Binder hop"
3. 对 shared buffer mode 和 counter-based state 的说明超越了多数公开资料
4. 版本验证采用 AOSP tag 实际检查，不猜测
5. "不编造假截图"的占位策略符合 writing-guide

### 主要技术风险
1. 源码位置标注有误（onFirstRef vs 构造函数）会直接误导想看源码的读者
2. Consumer 路径几乎空白——只理解 producer 半边，无法独立排查"queueBuffer 之后为什么很久没被消费"这类问题
3. 版本覆盖严重不足——声称覆盖 4.1-17，实际只讲了 4.1 和 11 两个版本
