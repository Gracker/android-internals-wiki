### 3.2 触摸响应的性能分析
- 文件：src/part1-fundamentals/ch03-input/02-touch-performance.md
- 结果：needs-rework
- 技术评分：源码 4/5 · 原理 3/5 · 版本 3/5 · 盲区 4/5 · 数据 3/5 · 交叉引用 5/5
- P0/P1/P2/P3：0/2/1/0

  1. [P1] [原理断裂] L279-L286 / L318-L323 Batching 的 Perfetto 观测 — 正文把 WaitQueue（wq）写成可直接观察 batching 的 Slice，并把一个 VSync 内多个 MOVE 等待解释为 App 在消费 batch。AOSP InputDispatcher 的 iq/oq/wq 更准确是 ATRACE_INT 队列长度计数；wq 表示已派发但等待 App finish/ACK 的事件，堆积能证明 App 侧处理慢或未 ACK，不能直接等同于 ViewRootImpl/InputConsumer 的 batched MotionEvent 消费。 建议：把 Perfetto 观测口径拆开：InputDispatcher 侧看 iq/oq/wq counter 判断派发/ACK 背压；App 侧看 consumeBatchedInputEvents、deliverInputEvent/InputResponse 与 MotionEvent history 判断 batching。不要把 WaitQueue 多个 MOVE 写成 batching 的直接证据。
  2. [P1] [版本差异/API边界] L255 / L526-L529 PointerCoords.isResampled — 正文面向 Android 10-16，但直接写应用可通过 MotionEvent.PointerCoords.isResampled() 识别重采样坐标。公开 API 口径需要按 Android 15/API 35 以后说明；Android 10-14 不能把这个方法写成通用可用能力。 建议：补版本边界：API 35+ 可用 PointerCoords.isResampled()；低版本只能依赖系统行为、trace/源码判断或避免在正文给出公共 API 调用建议。
  3. [P2] [数据缺失] L80 / L193-L196 延迟预算表 — 30-80ms 总触摸延迟、InputReader <1ms、InputDispatcher 1-3ms 等数字缺少设备、刷新率、trace 场景、采样次数和统计口径。 建议：补一组 Perfetto 样例：设备型号、刷新率、触摸采样率、场景、p50/p95；没有样本时把数字改成经验范围并标注需按目标设备实测。
### 14.9 Android Camera 性能与 Perfetto 分析
- 文件：src/part3-tools/ch14-other-tools/09-camera-performance-analysis.md
- 结果：needs-rework
- 技术评分：源码 2/5 · 原理 4/5 · 版本 4/5 · 盲区 4/5 · 数据 3/5 · 交叉引用 4/5
- P0/P1/P2/P3：2/0/1/0

  1. [P0] [源码错误/SQL错误] L295-L303 cam2_frame Counter SQL — Perfetto Trace Processor 的 counter 表不带 name 字段，counter 名称在 counter_track/process_counter_track 等 track 表上。当前 SQL 使用 counter.name LIKE "%cam2_frame%" 会直接查询失败或无法按 track 名过滤。 建议：改为从 counter JOIN process_counter_track pct ON counter.track_id=pct.id，再使用 pct.name LIKE "%cam2_frame%"；如目标 trace 使用通用 counter_track，也应先查 track 表确认具体 schema。
  2. [P0] [工具能力事实错误] L518 GFXReconstruct 辅助检查花屏和 YUV 帧问题 — 正文写 GFXReconstruct 可在 Vulkan / OpenGL 导入 AHardwareBuffer 的路径上抓取图形 API 调用。GFXReconstruct 主要支持 Vulkan（以及部分平台的 D3D12）捕获/回放，不是 OpenGL 抓帧工具；把 OpenGL 写进去会误导排查路径。 建议：改为“Vulkan 导入 AHardwareBuffer 的路径”；OpenGL/EGL 场景另行标注需要 AGI、厂商 GPU 工具或应用内 dump，不能归到 GFXReconstruct。
  3. [P2] [数据缺失] L490 CameraX 冷启动额外 80-150ms — “CameraX 首帧前常见额外 80-150ms 初始化开销”缺少测试条件、版本、设备和样本范围。CameraX 不同 use case、extension、device quirk 与预热策略差异很大。 建议：补 benchmark 条件，至少写清 CameraX/Camera2 版本、use case、设备、冷/热启动定义、p50/p95；没有一手数据时改成“可能引入额外初始化阶段，需按首帧 trace 实测”。
### 19.23 网络 APM 底层捕获原理
- 文件：src/part3-tools/ch19-apm/23-network-apm-internals.md
- 结果：needs-rework
- 技术评分：源码 3/5 · 原理 3/5 · 版本 4/5 · 盲区 4/5 · 数据 4/5 · 交叉引用 4/5
- P0/P1/P2/P3：1/0/1/0

  1. [P0] [代码错误/原理断裂] L151-L156 connectStart 懒创建 attempt — 代码注释说“当前 attempt 已有 failure 就创建新 attempt”，但条件写成 failure != null && connectStartNs == null。一次 connectFailed 后当前 attempt 通常已有 connectStartNs，下一次 connectStart 不会新建 attempt，反而覆盖同一 attempt 的 connectStartNs，导致弱网重试被合并，attempt_count、retry_overhead_ms、失败原因都会失真。dnsStart 也没有处理前一 attempt 已 failure 的场景。 建议：在进入新 DNS/connect 阶段前判断当前 attempt 是否已结束或已有 failure；条件应类似 if (currentAttempt().failure != null || currentAttempt().connectEndNs != null) attempts += Attempt()，并在 dnsStart/connectStart 都统一调用 ensureActiveAttemptForNewRoute()。
  2. [P2] [原理口径] L93 Interceptor 与 DNS/TCP 阶段 — 正文说“拦截器看到请求链条，DNS 查询和 Socket 建连已经由 OkHttp 内部完成或复用了连接”。这对 network interceptor 更接近，但 application interceptor 的 chain.proceed() 会包住后续 ConnectInterceptor，能量到包含 DNS/建连的总耗时，只是拿不到阶段回调。 建议：拆成两句：application interceptor 可量到一次 proceed 的总耗时但不能拆 DNS/TCP/TLS；network interceptor 运行时通常已经有 connection，因此更不能提供 dnsStart/connectStart 阶段口径。
