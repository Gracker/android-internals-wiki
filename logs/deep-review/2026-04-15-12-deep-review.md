## 审查结果

### 维度 1：源码引用准确性
- 评分：4/5
- 问题数：2
- 具体问题：
  1. [P1] SQL 查询 — 文中两段 SQL 直接引用 `cpu_frequency_slices` 表名。Perfetto trace processor 没有这个内置表；CPU 频率数据存储在 `counter` + `cpu_counter_track` 中，需通过 LEAD 窗口函数计算 duration。当前 SQL 无法直接运行。
  2. [P2] AOSP 源码路径 `cpufreq_schedutil.c` — 正文 frontmatter 和参考资料写的路径是 `kernel/sched/cpufreq_schedutil.c`，在 android16-6.6 内核树中该文件确实存在，路径准确。但 Linux mainline 6.6+ 已将 schedutil 合并到 `kernel/sched/cpufreq_schedutil.c`，仍保留该路径。

### 维度 2：原理链完整性
- 评分：4/5
- 问题数：1
- 具体问题：
  1. [P2] 调频延迟链路 — 正文把升频延迟归因链写得很好（PELT→schedutil→cpufreq driver→clock framework→regulator→voltage settle），但 PELT 响应时间只写了 "EWMA 的惯性" 而没有给出 PELT 的半衰期窗口（约 32ms）和具体收敛行为。对于理解 "为什么可能需要 200ms" 这个关键问题，缺了关键一环。

### 维度 3：版本差异覆盖
- 评分：4/5
- 问题数：2
- 具体问题：
  1. [P2] schedutil rate_limit_us — 正文写 "默认值通常在 0.5ms 到 2ms 之间"。实际上 Linux 内核 schedutil 有 `up_rate_limit_us` 和 `down_rate_limit_us` 两个独立参数，升频方向默认约 0.5-1ms，降频方向默认可达 20ms。正文没有区分两个方向。
  2. [P2] ADPF 演进 — 正文只在代码注释里提到 "Android 12 引入"。ADPF 在 Android 13/14/15/16 有显著 API 扩展（如 Game Mode API 集成、thermal status callback、fixed-performance mode），正文没有给出版本演进说明。

### 维度 4：知识盲区
- 评分：3/5
- 盲区数：3
- 具体问题：
  1. [P1] 缺少 cpuidle 与 DVFS 的联动说明 — 正文提到 CPU Idle State track 但没有解释 cpuidle governor 与 cpufreq governor 的交互。在移动设备上，cpuidle 的 target residency 和 exit latency 会影响整体 DVFS 决策延迟。
  2. [P2] 缺少 EAS + schedutil 的联合决策路径 — §5.2 讲 EAS，本节讲 schedutil，但两者在内核中的交互点（overutilized threshold、energy model feedback）没有串联。
  3. [P2] 缺少 devfreq / GPU DVFS 的观测方法 — GPU DVFS 章节只写了 "如果设备支持"，没有给出在 Perfetto 中具体看哪个 track 或需要什么数据源配置。
