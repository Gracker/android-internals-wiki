## Queue issue 详情
1. [P0] [源码错误] L101-L109 Canvas.drawRect 源码片段
   - 问题：正文标注 AOSP android-16.0.0_r1 的 Canvas.drawRect 直接调用 native_drawRect。实际 android-16.0.0_r1 中 Canvas.drawRect(float...) 调用 super.drawRect(...)；BaseCanvas.drawRect(...) 才执行 throwIfHasHwFeaturesInSwMode(paint) 并调用 nDrawRect(...)。native_drawRect 这个方法名与展示路径不符。
   - 建议：改为展示 Canvas -> BaseCanvas -> nDrawRect 的真实调用链；若只想说明最终 native 路径，代码块需明确标成“示意性伪代码”，不要写成 AOSP 原文片段。
2. [P0] [源码错误] L393-L408 GraphicBuffer.java 简化类定义
   - 问题：正文写 GraphicBuffer 的“唯一字段”是 mNativeObject，并把 getWidth/getHeight/getFormat/getUsage 写成 native 方法。实际 android-16.0.0_r1 GraphicBuffer.java 还有 mWidth、mHeight、mFormat、mUsage 等 Java 字段；这些 getter 是普通 Java getter，直接返回字段，不是 native 方法。
   - 建议：按实际源码改成 mWidth/mHeight/mFormat/mUsage + mNativeObject 的包装结构；删除“唯一字段”和 native getter 说法。
3. [P0] [源码错误] L686-L697 BufferQueueProducer::waitForFreeSlotThenRelock 片段
   - 问题：正文代码块给出 status_t waitForFreeSlotThenRelock(int* foundSlot) 并直接 return slot。实际 android-16.0.0_r1 签名是 waitForFreeSlotThenRelock(FreeSlotCaller, std::unique_lock<std::mutex>&, int*) const，返回 NO_ERROR/WOULD_BLOCK/TIMED_OUT 等 status，并通过 *found 返回 slot；内部还检查 mActiveBuffers、mMaxDequeuedBufferCount、shared buffer、tooManyBuffers 和条件变量等待。当前片段会误导 BufferQueue 空闲槽选择与阻塞语义。
   - 建议：替换为真实函数骨架：统计 dequeued/acquired -> 检查 maxDequeued -> getFreeBuffer/getFreeSlot -> 无可用 slot 时按阻塞/超时等待；或明确标注为“极简伪代码”并不要使用实际源码签名。
4. [P1] [版本差异/系统策略边界] L216、L224、L287、L449-L455 Android 16 Vulkan / ANGLE 默认路径
   - 问题：正文仍多处写 Android 16 将 Vulkan 定为默认图形 API、GLES App 通常/自动通过 ANGLE-on-Vulkan。android-16.0.0_r1 的 GraphicsEnvironment.setupAngle() 显示 ANGLE 选择取决于 ro.hardware.egl 是否为 angle、全局/单应用 settings、平台 allowlist、ANGLE APK/system library 等条件；VPA16/VP_ANDROID_16_minimums 能证明新设备 Vulkan 能力基线，不能推出所有 GLES App 自动走 ANGLE。
   - 建议：拆成三条线：Vulkan API/AVP16 能力基线、HWUI/Skia 后端选择、GLES -> ANGLE 的设备/应用策略。正文避免“自动”“通常”这类平台级结论，补 GraphicsEnvironment.setupAngle/queryAngleChoice 作为源码锚点。
5. [P1] [源码/API 行为] L323-L327 GPU Headroom 调用开销
   - 问题：正文写 getGpuHeadroom() 是一次 Binder 同步且“开销在亚毫秒级”。android-16.0.0_r1 SystemHealthManager#getGpuHeadroom 注释明确写每次有效调用至少一次同步 Binder transaction，可能超过 1ms；首次调用或非默认 params 还可能因按需初始化更慢。
   - 建议：改为官方口径：可能超过 1ms，不建议在 critical/render 线程调用或等待；示例只保留异步采样与 minInterval/cached result 边界。
6. [P1] [知识盲区/待验证事实] L432-L436 16KB 页环境下 Gralloc AIDL V2 sub-allocation
