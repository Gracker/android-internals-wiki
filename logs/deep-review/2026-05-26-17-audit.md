- Android Developers Frame Pacing：Swappy 使用 Choreographer、presentation timestamp、sync fences，支持多刷新率与 Frame stats；OpenGL/Vulkan 接入文档仍要求 `SwappyGL_setWindow()` / `SwappyVk_setWindow()` 补齐 `ANativeWindow` 路径。
- AOSP `frameworks/opt/gamesdk` main：`ChoreographerThread.cpp` 的回退链、`SwappyDisplayManager.cpp` 的 API 28-30 / API 31+ 边界、`SwappyCommon.cpp` 的 `calculateSwapInterval()` 与 `ANativeWindow_setFrameRate()` vote 路径、`swappyVk.h` 的 Vulkan 函数签名均与正文主线一致。
- Perfetto FrameTimeline 文档和 SQL：FrameTimeline 仍要求 Android 12(S)+；`SurfaceViews are currently not supported` 仍成立；`actual_frame_timeline_slice` / `expected_frame_timeline_slice` 与 `jank_type` / `present_type` / `on_time_finish` 字段可用。
- Android 17 MessageQueue 官方文档与 Android Developers Blog：target SDK 37+ 启用新的 lock-free `MessageQueue`；DeliQueue 使用 Treiber stack + Looper 线程 min-heap；影响边界是 Java `MessageQueue`，未发现官方资料证明 NDK `AChoreographer` / `ALooper` 同步改成同一套 DeliQueue。
- Khronos Vulkan registry：`VK_KHR_present_wait` 的 extension dependency 包含 `VK_KHR_present_id`；`VK_KHR_present_id` 只提供 present operation identifier，本身不等同于 display timing timestamp。

### 维度 1：源码引用准确性
- 评分：4/5
- 问题数：1（P2）

[P2][源码表述精度] L400 — 正文写“主线程的 `MessageQueue.nativePollOnce()` 和其他线程的同步操作共用一把 `mLock`”。旧 `MessageQueue.next()` 的真实结构是先调用 `nativePollOnce()`，随后进入 `synchronized (this)` 读写 `mMessages`；官方 DeliQueue 博文也把问题描述为 UI 线程读取 queue 时被后台线程持有的 `MessageQueue` monitor lock 阻塞。建议后续精修改成“主线程从 `MessageQueue` 取下一条消息时，可能在进入队列临界区后被后台线程持有的 monitor lock 阻塞”，避免把 native poll 本身写成持锁等待。
- 复核通过项：
  1. `SwappyGL::swapInternal()` 的 `insertSyncFence()` → `onPreSwap()` → `setPresentationTime()` → `swapBuffers()` → `onPostSwap()` 主链与当前 AOSP main 一致；正文标成伪代码，未把 synthetic snippet 写成真实函数体。
