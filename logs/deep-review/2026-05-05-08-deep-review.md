### 具体问题
1. [P0][源码错误] 版本边界：FrameTimeline Android 12+ / Android 8-11 fallback 的 gfx/view trace tag
   - 问题：`adb shell setprop debug.atrace.tags.enableflags 0x200` 被写成开启 gfx + view，但 AOSP `Trace.java` 中 `TRACE_TAG_VIDEO = 1L << 9`，0x200 对应 video；`TRACE_TAG_GRAPHICS = 1L << 1`，`TRACE_TAG_VIEW = 1L << 3`。当前命令会让 Android 8-11 fallback 抓错 trace 类别。
   - 建议：不要用错误 bitmask。改为 Perfetto/atrace category 方式明确启用 `gfx,view,sched,input,wm`；如果必须写 bitmask，只能把 gfx+view 解释为 0xA，并说明还需单独启用 sched/input/wm。
   - 证据：AOSP android-15.0.0_r1 frameworks/base/core/java/android/os/Trace.java
2. [P0][源码错误] 场景化 Perfetto SQL 快速筛选：jank / BufferStuffing 查询
   - 问题：文中使用 `frame_timeline_event` 表和 `jank_type = 'BufferStuffing'`。Perfetto FrameTimeline 文档的 SQL 表是 `expected_frame_timeline_slice` / `actual_frame_timeline_slice`，示例中的 jank_type 是 `Buffer Stuffing`（带空格）。当前 SQL 在常见 Perfetto Trace Processor 中不可执行或查不到结果。
   - 建议：改为查询 `actual_frame_timeline_slice`，并用文档枚举值 `Buffer Stuffing`；同时标注该 SQL 仅适用于 Android 12+ FrameTimeline trace。
   - 证据：Perfetto docs: Android Jank detection with FrameTimeline
3. [P1][版本差异] BufferStuffing 识别：Android 8-11 间接识别
   - 问题：该段把 Actual Present / Expected Present 用作 Android 8-11 fallback 观察点，但这两个字段属于 FrameTimeline 语义。Android 8-11 没有 FrameTimeline 表，不能要求读者用 Actual/Expected Present 判断固定 N 个周期延迟。
   - 建议：Android 8-11 分支应改成 `Choreographer#doFrame` 间隔、RenderThread dequeueBuffer/queueBuffer 阻塞、SurfaceFlinger layer/BufferQueue dump、input 到下一次 UI 更新的相对时差等可获得信号。
   - 证据：Perfetto FrameTimeline docs + Android 12 引入边界
4. [P1][知识盲区] 用户投诉映射表之后 / 八类现场清单
   - 问题：大纲承诺覆盖功耗入口，但正文仍只有 `[需补充素材]` 占位，没有耗电/发热场景的第一观察点、trace 配置和优先排查路径。

### 具体问题
1. [P0][源码错误] 在 Perfetto 中观察全大核迁移行为：migration SQL
   - 问题：SQL 使用 `prev_cpu != cpu`，但 Perfetto `sched` 表没有 `prev_cpu` 字段，CPU 维度在当前文档中是 `ucpu`；`prev_cpu` 需要用窗口函数从上一条 sched slice 推导。当前 SQL 直接执行会报列不存在，无法作为作战手册级查询。
   - 建议：改成 `lag(ucpu) over (partition by utid order by ts)` 推导 `prev_ucpu`，再统计 `prev_ucpu != ucpu`；或改用 Perfetto metrics / thread_state 派生表。
   - 证据：Perfetto SQL tables: SchedSliceTable["sched"] -> ucpu; no prev_cpu
2. [P1][原理断裂] 全大核迁移行为：迁移代价与 DSU/L2 解释
   - 问题：文中用“Armv8.5+ 的 DSU 缓存一致性协议让跨核 L2 命中延迟可接受”解释全大核迁移代价低。这个因果链不准确：DSU/DynamIQ 负责一致性和共享系统缓存/DSU 侧缓存，典型 Cortex 核心的 L1/L2 仍是私有层级；任务跨核迁移仍可能损失 L1/私有 L2 locality。不能用“跨核 L2 命中”作为低迁移成本依据。
   - 建议：改成更保守的说法：全大核核心性能差距缩小会改变负载均衡策略，但迁移成本必须结合 cache miss、task wakeup、uclamp、cluster policy 和实机 trace 观察判断；如要讨论 DSU，明确它提供 coherency/shared cache，不等于跨核复用私有 L2。
   - 证据：ARM DynamIQ/DSU 架构语义 + Android Perfetto sched/PMU 观察边界
3. [P2][数据缺失] 核心拓扑：Oryon / 全大核在 Perfetto 中的表现
   - 问题：“Oryon 架构线程迁移次数明显少于多集群设计”“高通 Oryon 双集群只有两个频率档位”缺少实机 trace/频率策略证据；后一句还把 cluster/policy 数量和具体 frequency value 混在一起。
   - 建议：把“两个频率档位”改为“两组 cpufreq policy/cluster 轨道（每组仍有多个频点）”；补一张 8 Elite 与 Dimensity 9400 的同场景 Perfetto 对比，或降级为待验证。
   - 证据：章节 last_verified_against 仅为公开资料；无 trace 数据
