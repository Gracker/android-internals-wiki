## 审计结论

### 维度 1：源码引用准确性
- 评分：4.5/5
- P0/P1：0
- P2：0
- 结论：未发现源码锚点错误。`View.updateDisplayListIfDirty()` 在 `LAYER_TYPE_SOFTWARE` 分支仍调用 `buildDrawingCache(true)`、`getDrawingCache(true)` 并 `drawBitmap(cache, 0, 0, mLayerPaint)`；`RenderProperties.h` 仍说明 Software layer 由 Java 侧管理，不能直接构建 RenderLayer。章节前序 P0 的修复在 Android 17 源码下仍成立。
- `Surface::lock()` 仍是 `dequeueBuffer()` → dirty/copyback 处理 → `GraphicBuffer::lockAsync()`；`unlockAndPost()` 仍是 `unlockAsync()` 后把 fence 交给 `queueBuffer()`。Android 17 把 `queueBuffer` 入口改成 `sp<Fence>` 形态，但不改变章节对 acquire/release fence 和 BufferQueue 等待点的结论。
- `ViewRootImpl` 仍按 `FLAG_HARDWARE_ACCELERATED` 创建 `ThreadedRenderer`，draw 分支仍是 `isHardwareEnabled()` 走硬件 renderer，否则走 `drawSoftware()`，整窗口软件渲染与单 View software layer 的区分成立。
