### 2.17 Frame Pacing Library 与帧节奏控制
- 技术评分：源码准确性 2/5 · 原理完整性 2/5 · 版本覆盖 2/5 · 知识盲区 3/5 · 数据支撑 2/5 · 交叉引用 4/5
- [P0][源码错误] L422-L434 Vulkan 1.4 present_id / Swappy Vulkan 路径 — 正文断言 Android 16 Vulkan 1.4 使 VK_KHR_present_id 默认启用，且 SwappyVk_queuePresent 会检查该扩展并用 present_id 确认真实上屏。复核 AOSP frameworks/opt/gamesdk main：include/swappy/swappyVk.h、games-frame-pacing/vulkan/SwappyVk.cpp、SwappyVkBase.cpp 均未出现 VK_KHR_present_id / present_id，Vulkan 路径仍围绕 VK_GOOGLE_display_timing、fence、Choreographer 与 SwappyStats。VK_KHR_present_id 也只是给 present 操作打递增 ID，不等同于 display driver 返回完成时间戳。 建议：删除“Swappy 已接入 present_id 硬件确认”的定论；如保留，只能作为待验证方向，并补 Vulkan spec、Android VPA/CDD、Swappy 对应 commit 与可运行验证。
- [P1][数据缺失/版本差异] L426-L432 present_id 抖动数据与版本表 — “Jitter 降低约 30%”以及 ±2-4ms / ±1-2ms / ±0.5-1ms 的抖动范围没有设备、驱动、刷新率、样本数、测量方法和原始 trace/log；“Android 16+（Vulkan 1.4 强制）”也把平台 Vulkan profile 要求、扩展可用性和 Swappy 是否使用扩展混在一起。 建议：没有一手 benchmark 时移除该表；若补表，至少给出设备、Android build、GPU/driver、swapchain present mode、是否启用 VK_GOOGLE_display_timing / present_wait / present_id，以及 trace 或日志样本。
- [P1][原理断裂/知识盲区] L438-L444 Android 17 DeliQueue 与 AChoreographer — 正文把 DeliQueue 对 AChoreographer 回调路径的收益写成已验证事实，并称 DeliQueue 是“单生产者-单消费者无锁队列”、使 AChoreographer 回调抖动减少约 15%。现有 research-gaps 已记录“确认 DeliQueue 是否仅优化 Java MessageQueue，还是影响 NDK AChoreographer/ALooper”。当前证据不能把 Java MessageQueue 的 lock-free producer path 直接推导到 Swappy native 回调抖动。 建议：拆成 Java Choreographer/MessageQueue 已知变化与 NDK AChoreographer/ALooper 待验证影响；无法定位 exact AOSP branch/commit 和性能数据前，改为 [待验证]，并交叉引用 §1.13 与 research-gaps。

### 5.3 大小核架构
- 技术评分：源码准确性 2/5 · 原理完整性 3/5 · 版本覆盖 3/5 · 知识盲区 3/5 · 数据支撑 3/5 · 交叉引用 4/5
- [P0][源码错误] L261-L287 schedutil sugov_get_util() 代码片段 — 正文标注 “Linux 6.6 实际签名” 且注释 @ android16-6.12（GKI），但片段与两个版本都没有完全对齐。Linux v6.6 的 sugov_get_util(struct sugov_cpu *sg_cpu) 没有 boost 参数；android16-6.12 的 sugov_get_util(struct sugov_cpu *sg_cpu, unsigned long boost) 使用 scx_cpuperf_target、effective_cpu_util(cpu, util, &min, &max)、bw_min 与 sugov_effective_cpu_perf()，没有 sg_cpu->max / bw_dl，也没有 FREQUENCY_UTIL 参数。 建议：拆成 Linux v6.6 与 android16-6.12 两个源码锚点，或只保留一个真实版本；不要把混合片段标为实际源码。
- [P1][原理断裂/源码锚点缺失] L176-L184 Wake-up Placement / EAS 选核 — 章节只用概念描述 EAS 会评估 util、capacity 和能量模型，但没有落到真实源码流转。上一轮 external-review 已要求补源码追踪；本轮复核后应把锚点修正为 kernel/sched/fair.c 的 select_task_rq_fair()、find_energy_efficient_cpu()、util_fits_cpu()/compute_energy() 等，而不是泛写“调度器会”。 建议：补一段 wake-up 选核源码链：try_to_wake_up()/select_task_rq_fair() 进入 fair class，EAS 在 find_energy_efficient_cpu() 里结合 task util、CPU capacity、energy model 与 uclamp/task profile 决策；版本上区分 mainline/GKI/vendor hook。
- [P2][原理口径] L180 PELT 时间尺度 — 正文把 PELT 32ms 写成“时间常数约 32ms（1024us × 32）”。Linux PELT 通常以 32ms half-life/半衰期描述，1024us 是采样周期量级；写成时间常数会误导读者理解衰减曲线。 建议：改为“PELT 的历史贡献约每 32ms 衰减一半”，不要写成时间常数。
- [P2][原理口径] L427-L430 线程优先级与大核选核 — 正文说 Process.setThreadPriority() 会让调度器更积极地把高优先级线程放到大核。nice/priority 主要改变 CFS 权重和抢占机会，不是稳定的大核选择接口；现代 Android 更直接的输入是 task profile、cpuset、uclamp、Power HAL hint 和厂商调度策略。 建议：把 setThreadPriority 降级为“影响调度权重/延迟”的间接因素；大核倾向改写为 cpuset/uclamp/Power HAL/vendor policy 的结果。
