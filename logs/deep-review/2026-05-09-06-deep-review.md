### 1. 16.5 Android 17 (API 37) 性能行为变更与适配方法

#### P0 级问题（源码准确性/原理链重大错误）

**[P0-1] DeliQueue 源码结构理解错误**  
原文："Android Developers Blog 的概念模型：使用 Treiber Stack（一种无锁栈），通过 CAS（Compare-And-Swap）操作实现多线程并发入队，不需要任何锁"
- **问题**：AOSP `frameworks/base/core/java/android/os/ConcurrentMessageQueue/MessageQueue.java` 实际使用 `ConcurrentSkipListSet<MessageNode>` 而非字面意义的 Treiber Stack
- **原理**：`ConcurrentSkipListSet` 是并发有序集合，不是传统的 CAS 栈结构。核心是通过无锁的 CAS 入队 + drain 批量搬运机制
- **建议**：将描述改为"概念上采用无锁并发入队算法，AOSP 实现为 `ConcurrentSkipListSet<MessageNode>` 结构，通过 CAS 操作实现线程安全"

**[P0-2] 分代 CMC 启用条件配置方法错误**  
原文："实际启用需要满足多个条件：`gUseUserfaultfd` 系统属性开启、`use_generational_cmc` flag 启用、`persist.device_config.runtime_native_boot.use_generational_gc` 设备配置支持"
- **问题**：根据 AOSP `android-16.0.0_r1/art/runtime/gc/collector/young_mark_compact.cc`，实际 gating 条件更复杂
- **正确条件**：
  1. `gUseUserfaultfd` 为 true
  2. `!gUseGenerationalGC || useGenerationalCMC()` 函数返回 true  
  3. `gHasYoungGen` 全局变量为 true
  4. Device config `persist.device_config.runtime_native_boot.use_generational_gc` 启用
- **建议**：修正为"需要满足 `gUseUserfaultfd` AND `useGenerationalCMC()` AND `gHasYoungGen` AND 设备配置支持"

#### P1 级问题（数据支撑/版本差异不准确）

**[P1-1] 性能收益数据缺少验证边界**  
原文："Synthetic benchmark 最多可比 legacy MessageQueue 快 5,000x"
- **问题**：未说明测试条件，容易误导读者认为所有场景都能获得此收益
- **数据约束**：5,000x 仅出现在特定高竞争场景（如 32 线程 busy queue bench），正常业务场景远低于此值
- **建议**：补充说明"5,000x 收益来自 32 线程高压力场景，业务中通常为 10x-100x 范围"

**[P1-2] 分代 GC 诊断建议不准确**  
原文："建议通过 Perfetto GC tracks 或 device_config 验证当前设备的具体配置"

- **正确方法**：应使用 `adb shell dumpsys meminfo | grep "Generational"` 或 `adb shell device_config get runtime_native_boot use_generational_gc`
- **建议**：提供可执行的诊断命令
