#### 具体问题
1. [P1][版本差异] §3 Alarm 与后台任务：setExactAndAllowWhileIdle / setAlarmClock — 正文只讨论 Doze 下高频唤醒，但没有交代 Android 12+ exact alarm 特殊权限与版本差异：SCHEDULE_EXACT_ALARM、canScheduleExactAlarms()、ACTION_REQUEST_SCHEDULE_EXACT_ALARM，以及 Android 13/14 后 USE_EXACT_ALARM / 默认授权策略变化。对 APM 来说，这会影响“业务设置了闹钟”和“系统是否允许精确触发”的归因判断。
   - 建议：补一张 Android 12/13/14+ exact alarm 权限与触发能力表；端侧样本增加 permission/app-op 状态、canScheduleExactAlarms() 结果、alarm type、allowWhileIdle/exact 标记、未获授权时的降级路径。
2. [P1][原理断裂] §5 Thermal API 示例：只注册 addThermalStatusListener — 示例只记录 thermal status change callback，没有在注册时读取 getCurrentThermalStatus()。应用如果在设备已经处于 SEVERE/CRITICAL 时启动，监听器可能要等下一次状态变化才回调，APM 会漏掉初始热状态，降级策略也可能延迟执行。
   - 建议：注册 listener 后立即读取 PowerManager.getCurrentThermalStatus() 并走同一条 record/applyThermalPolicy 路径；日志中区分 initial_snapshot 与 status_changed。

#### 具体问题
1. [P1][版本差异] §3 WebViewRenderProcessClient — 章节 frontmatter 写 Android 8/API 26 起适用，正文把 onRenderProcessGone() 与 WebViewRenderProcessClient 放在同一能力层描述。onRenderProcessGone() 是 API 26；WebViewRenderProcessClient / onRenderProcessUnresponsive / setWebViewRenderProcessClient 属于 API 29+。API 26-28 设备不能直接接入 unresponsive/responsive 回调。
   - 建议：拆成两级版本边界：API 26+ 处理 onRenderProcessGone()；API 29+ 再接 WebViewRenderProcessClient，并给 API 26-28 的降级信号（页面 ready 超时、JSBridge 心跳、PixelCopy/DOM 白屏采样）。
2. [P1][版本差异] §1 JS PerformanceObserver 示例：FCP / LCP — 示例直接 observe paint 和 largest-contentful-paint，但 WebView 的前端性能 API 能力取决于 Android System WebView / Chromium 版本，不只取决于 Android API level。LCP 在旧 WebView 中不可用；没有 supportedEntryTypes/try-catch 时，注入脚本可能异常退出，导致 FCP/LCP 都不上报。
   - 建议：在示例中加入 PerformanceObserver.supportedEntryTypes 特性检测和 try/catch；样本字段增加 webviewProviderPackage / Chromium major version；对不支持 LCP 的 WebView 回退到 FCP、业务 ready、DOM/像素采样。
3. [P2][数据缺失] §2 PixelCopy 白屏采样示例 — 示例每次 createBitmap，未说明 bitmap 复用、降采样尺寸、PixelCopy error code 记录和采样成本上限。线上白屏采样如果在弱机上集中触发，监控本身会制造内存抖动。
   - 建议：补充固定尺寸 bitmap pool / 采样矩形缩放 / result code 上报 / 采样频率上限，并建议在灰度中记录单次采样耗时和 bitmap 分配量。
4. [P2][原理链完整性] §5 Flutter FrameTiming 映射为 Android Jank — 正文提到 buildDuration/rasterDuration 超过刷新率预算可能丢帧，但没有说明 addTimingsCallback 是批量回调，也没有区分 build/raster/totalSpan 与 Android 宿主帧的关系。
   - 建议：补充“Flutter 自有帧预算”与“Android 宿主 Choreographer”分层：按当前刷新率计算预算，分别聚合 UI/Raster/totalSpan，不把单个字段直接等同于 Android FrameMetrics/JankStats 的 jank。
