## 维度 1：源码引用准确性
- 评分：4.5/5
- P0/P1：0
- 结论：Perfetto CPU Frequency 官方文档仍确认两条采集来源：`power/cpu_frequency` ftrace 事件与 `linux.sys_stats.cpufreq_period_ms` 轮询；`linux.system_info` 记录 `scaling_available_frequencies`；频率和 idle state 在 SQL 层通过 `counter` + `cpu_counter_track` 查询，`cpuidle=0xffffffff` 表示回到非 idle。正文采集入口、误判清单与 SQL 快查口径仍成立。
- 结论：Perfetto SQL tables 当前仍列出 `cpu.id`、`cpu.cpu`、`cpu.cluster_id`、`cpu.capacity` 与 `cpu_freq.ucpu -> cpu.id`，正文关于 cluster/capacity/cpu_freq 的识别顺序成立。
- 结论：Android 17 `packages/modules/Profiling` 的 `android.os.ProfilingManager` 仍包含 `requestProfiling()`、`PROFILING_TYPE_SYSTEM_TRACE`、`PROFILING_TYPE_JAVA_HEAP_DUMP`、`PROFILING_TYPE_HEAP_PROFILE`、`PROFILING_TYPE_STACK_SAMPLING`；正文“Android 15 起 ProfilingManager / AndroidX Profiling 可请求 system trace、heap dump、heap profile、stack sampling”的版本边界成立。
- 低风险观察（P2，仅日志）：上一轮指出的 `SPAN_JOIN` 示例中 `sched.ucpu` 与 `cpu_counter_track.cpu` 分区口径在普通单机 Android trace 中通常可用，但多 machine / 非连续 CPU id 场景仍可能歧义。正文已提示保留 `cpu` 与 `utid`，本轮不升级为 P0/P1。
