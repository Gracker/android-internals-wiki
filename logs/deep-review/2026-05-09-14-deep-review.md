### 章节 2.3: VSync 机制 - 技术审计结果

#### P0 严重问题

**[P0][版本差异][渲染架构进化]** - 缺失 Android 16/17 的 VSync 新特性
- **问题描述**: 当前内容停留在 Android 15 ARR（自适应刷新率）架构，未反映 Android 16 的核心演进
- **技术事实**: Android 16 引入了基于 VSync Reactor 的动态预测模型，新增 `VSyncPredictor::addVsyncTimestamp()` 的 AOT 预学习机制，同时支持多屏幕场景下的 Pacesetter Display 模式
- **影响范围**: 无法解释 2026 年新设备的渲染架构特性
- **修复建议**: 补充 Android 16 VSync Reactor 架构原理，增加 `VSyncPredictor::validate()` 版本差异对比

#### P1 重要问题

**[P1][原理链完整性][DispSync 模型演变]** - 软件锁相环机理描述不够透彻
- **问题描述**: 对 DispSync 从 Android 13 到 16 的重构过程缺乏解释
- **技术事实**: Android 16 将 `VSyncPredictor`、`VSyncReactor`、`VSyncDispatchTimerQueue` 职责拆分，引入 `VSyncConfiguration` 配置体系，`VsyncSchedule` 类统一调度
- **证据位置**: `services/surfaceflinger/Scheduler/` 目录重构历程
- **修复建议**: 添加架构演进时间线，解释各组件职责边界

**[P1][源码缺失][Phase Offset 计算]** - 缺少具体的源码调用锚点
- **问题描述**: WorkDuration 到 Phase Offset 的计算缺乏源码支撑
- **技术事实**: Android 16 使用 `VsyncConfiguration::calculateOffsets()` 和 `vsyncDurationToOffset()`、`appDurationToOffset()` 实现动态计算
- **源码位置**: `frameworks/native/services/surfaceflinger/Scheduler/VsyncConfiguration.cpp`
- **修复建议**: 补充具体计算函数的源码片段

**[P1][知识盲区][多屏幕同步]** - 未覆盖多显示器场景的 VSync 架构
- **问题描述**: 仅描述单屏 VSync 机制，缺失多屏同步的技术细节
- **技术事实**: Android 16 引入 `FrameTargeter` 独立同步架构，每个物理屏幕有自己的 VSync ID 计算和截止时间管理
- **证据位置**: `SF/DisplayManager.cpp` 中 Display 级别 VSync 管理
- **修复建议**: 增加多屏场景下的 VSync 时序分析

**[P1][交叉引用][RenderThread 协作]** - 与 RenderThread 协作机制描述不够深入
- **问题描述**: MainThread 与 RenderThread 的 VSync 同步机制过于简略
- **技术事实**: Android 17 的 DeliQueue 无锁消息队列消除了 UI 线程对 RT 获取任务的锁阻塞，掉帧率下降约 4%-7.7%
- **修复建议**: 补充 Android 17 DeliQueue 对 RenderThread 获取 VSync 任务的优化效果

### 章节 1.4: Binder IPC机制与性能影响 - 技术审计结果

#### P0 严重问题

**[P0][版本差异][Binder 内存管理]** - 缺失 16KB Page Size 对 Binder 的影响
- **问题描述**: 内容未反映 Android 16KB Page Size 强制推行对 Binder IPC 的影响
- **技术事实**: Android 16KB Page Size 强制要求 native 库的 ELF LOAD segment p_align 对齐，Binder mmap 缓冲区的物理页数量减少为原来的四分之一
- **影响范围**: 缺少对现代 Android 设备 Binder 性能特性的解释
- **修复建议**: 补充 16KB Page Size 下 Binder TLB 优化和页表遍历开销降低的量化分析

#### P1 重要问题

**[P1][源码准确性][Async Buffer 语义]** - oneway async buffer 语义描述存在偏差
- **问题描述**: async buffer 语义和边界条件描述不够准确
- **技术事实**: Android 12+ 引入 oneway spam detection (`BINDER_ENABLE_ONEWAY_SPAM_DETECTION`)，当同一 pid 占用过多 async buffer 时标记 `oneway_spam_suspect`
- **源码位置**: `frameworks/native/libs/binder/BinderAlloc.cpp` 中 `binder_alloc_new_buf()` 实现
- **修复建议**: 明确 async buffer 的空间限制和 overflow 时的错误处理机制

**[P1][原理链完整性][线程池管理]** - 线程池动态管理机制描述不够深入
- **问题描述**: 缺少线程池创建和销毁的详细流程
- **技术事实**: 线程池采用 `ProcessState::mMaxThreads` 控制，有 `binder::ProcessState::startThreadPool()` 和 `joinThreadPool()` 生命周期管理
- **源码位置**: `frameworks/native/libs/binder/ProcessState.cpp`
- **修复建议**: 补充线程池完整生命周期和线程状态转换逻辑

**[P1][数据支撑][冷启动 Binder 次数]** - 缺少具体的冷启动 Binder 调用量化数据
- **问题描述**: 声称"冷启动流程里，主线程可能发起 30-50 次同步 Binder 调用"但无数据支撑
- **证据缺失**: 需要实际测试数据或 AOSP 源码统计
- **修复建议**: 提供 adb shell dumpsys binder transactions 统计示例或实际测试数据

**[P1][交叉引用][Perfetto 字段]** - Perfetto Binder 字段口径与 Android 16 标准库不一致
- **问题描述**: PerfettoBinder 轨道字段描述需要更新
- **技术事实**: Android 16 Perfetto 标准库（`android/binder.sql`）完善了 interface 和 method_name 的拆分逻辑
- **修复建议**: 更新 Perfetto 字段描述，确保与最新标准库一致

### 章节 5.2: EAS能量感知调度 - 技术审计结果

#### P0 严重问题

**[P0][版本差异][Android 16 GKI 6.12 overutilized 行为]** - 缺失 Android 16 内核版本差异的准确描述
- **问题描述**: 描述 Linux 6.6 及更早和 Linux 6.12 / GKI 6.12 的 overutilized 行为差异存在偏差
- **技术事实**: Android 16 (GKI 6.12) 中 `find_energy_efficient_cpu()` 入口不再用 `rd->overutilized` 短路，但 overutilized 标志仍然存在，主要影响负载均衡和迁移策略
- **源码位置**: `kernel/sched/fair.c` 中 find_energy_efficient_cpu 和 load_balance 路径差异
- **影响范围**: 影响对 Android 16/17 设备 EAS 行为的准确分析
- **修复建议**: 明确区分 Linux 6.6 和 GKI 6.12 的 overutilized 处理差异，避免行为混同

#### P1 重要问题

**[P1][原理链完整性][PELT 与 WALT 关系]** - PELT 与 WALT 的描述存在混淆
- **问题描述**: 将 WALT 混为 Android 统一回归 PELT 的演进结果，实则为厂商定制扩展
- **技术事实**: WALT 是高通等厂商在部分 Android common kernel 上使用的负载跟踪扩展，主线 EAS 仍然基于 PELT
- **证据位置**: 不同厂商内核的 load tracking 实现
- **修复建议**: 明确区分主线内核 PELT、厂商内核 WALT 和 AOSP 用户态调度提示链

**[P1][版本差异][UClamp 聚合策略]** - UClamp 聚合方式演进描述不准确
- **问题描述**: 声称 sum 聚合为社区探索方向，但 Android 16 仍采用 max/bucket 策略
- **技术事实**: 截至 android16-6.12(GKI 6.12)，公开源码中 `uclamp_rq_util_with()` 仍走 max 路径，sum 聚合尚未合入主线
- **源码位置**: `kernel/sched/core.c` 中的 clamp bucket 逻辑
- **修复建议**: 明确说明当前仍采用 max 聚合策略，sum 聚合未进入主线

**[P1][交叉引用][SchedTune 与 UClamp 关系]** - 过于简化版本演进路径
- **问题描述**: 描述 Android 10-12 版本演进时不够细致
- **技术事实**: 
  - Android 10: task profile 已操作 `cpu.util.min/max`，但默认性能档位仍大量依赖 `schedtune`
  - Android 11: 接口名切到 `cpu.uclamp.min/max`，默认 profile 仍保留 `schedtune` 分组
  - Android 12+: 默认档位直接进入 `cpu/{background,foreground,top-app}`
- **修复建议**: 细化版本演进，明确过渡期的混合使用情况
