## 审查结果

### 维度 1：源码引用准确性
- 评分：3/5
- 问题数：4
- 具体问题：
  1. [P1] startSystemServer() 方法位置 — 正文引用 `ZygoteInit.java` 中的 `startSystemServer()` 方法。实际上，在 AOSP 当前版本（android-16.0.0_r1）中，`startSystemServer()` 方法定义在 `Zygote.java` 中（frameworks/base/core/java/com/android/internal/os/Zygote.java），ZygoteInit.java 仅包含入口逻辑 `startSystemServer()` 的调用。这两处容易混淆，但必须区分。
  2. [P1] preloadClasses()/preloadResources() 方法位置 — 正文说"定义在 ZygoteInit.java 中"，实际上这些预加载方法实现位于 `Zygote.java` 的 `preload()` 方法中，ZygoteInit 只是调用方（`ZygoteInit.main()` → `Zygote.preload()` → `preloadClasses()/preloadResources()`）。正文引用路径与实际方法定义位置不一致。
  3. [P2] init.rc action 顺序 — 正文列出 `early-init → init → late-init → ... boot → late-boot`，需要确认 `early-init` 与 `init` 的前后顺序是否准确。在 AOSP init.cpp 中，action 顺序有正确定义，常见顺序为：`early-init` 先于 `init`。
  4. [P2] preloaded-classes 文件路径 — 正文说"定义在 `/apex/com.android.art/etc/preloaded-classes` 文件中（Android 10+）"，但实际上 preloaded-classes 位于 `/apex/com.android.art/javalib/` 或在 build 时由 `frameworks/base/config/preloaded-classes` 复制到 APEX 中。准确路径应为 `apex/com.android.art/etc/preloaded-classes`（无 javalib 前缀），建议核实。

### 维度 2：原理链完整性
- 评分：4/5
- 问题数：2
- 具体问题：
  1. [P1] Zygote 预加载到 SystemServer 的交接节点 — 正文从"Zygote 进入等待状态"直接跳到"fork SystemServer"，缺少一个关键环节的说明：是谁（哪个组件）触发了 SystemServer fork？答案：是 ZygoteInit 的 main() 方法在预加载完成后，主动调用 `startSystemServer()`（在 Zygote.java 中），这不依赖任何外部信号——它是 Zygote 初始化流程的一部分。没有解释清楚触发机制，可能让读者误以为 SystemServer fork 是被动的。
  2. [P2] SELinux 加载时机缺失 — init 进程阶段有一个非常重要的安全初始化步骤：SELinux 策略加载（`restorecon` / `restorecon_recursive`），这直接影响 init 阶段耗时。但正文完全没有提及 SELinux，对 Android 安全启动链而言是个空白。

### 维度 3：版本差异覆盖
- 评分：3/5
- 问题数：3
- 具体问题：
  1. [P1] Android 16 启动优化数据未验证 — applicable_versions 声称覆盖到 API 36（Android 16），正文引用了 Android 16 的两项启动优化（并行内核模块加载减少 30%/25%、AutoFDO 减少 2.1%），但这两处数据都标注了 `[待验证: 仅基于 Pixel 设备数据]`。将未经验证的数据写入 ready-to-publish 章节有较高风险，建议核实后补充具体来源（AOSP Gerrit commit link）。
  2. [P2] APEX 模块化演进未系统覆盖 — applicable_versions 是 8-36，但正文对 Android 8 引入 APEX（Android 10 正式模块化）、Android 12 的 APEX 模块拆分重组、Android 14 的 APEX 服务化 等关键节点没有系统性梳理。startApexServices 章节的 `[待验证]` 标注本身就说明版本引入时间有争议。
  3. [P2] startApexServices 版本引入时间 — 正文标注 `[待验证: startApexServices 从 Android 10 引入，此处作为 TimingsTraceAndSlog 追踪阶段列出，确认为 Android 16 新增追踪还是此前已有]`。startApexServices 作为追踪阶段标签，在 Android 10+ APEX 引入后就存在，但作为显式追踪阶段可能是在较新版本才添加的。建议核实 AOSP TimingsTraceAndSlog.java 中 startApexServices 阶段的添加版本。

### 维度 4：知识盲区
- 评分：3/5
- 盲区数：4
- 具体问题：
  1. [P1] Zygote fork SystemServer 触发机制未说明 — 如维度 2 所述，缺少对"ZygoteInit.main() 主动触发 vs 被动通知"的说明，这是理解 Android 启动顺序的关键节点。
  2. [P2] SELinux 安全启动链缺失 — 对 init 阶段的安全性初始化（SELinux 策略加载、restorecon）完全缺失，是安全与性能交叉的重要知识盲区。
  3. [P2] Direct Boot 机制未覆盖 — `ACTION_LOCKED_BOOT_COMPLETED` 广播提了一下，但 Direct Boot（设备锁屏状态下特定组件可启动）机制没有解释。这是 Android 7.0 引入的重要特性，与锁屏状态下的通知、闹钟等功能直接相关。
  4. [P3] APEX 模块内部结构未展开 — 提到 APEX 是 Android 模块化的产物，但 APEX 内部结构（manifest.json、javalib、nativelib、etc）没有说明，无法让读者理解 APEX 相比传统 JAR/AAR 的本质差异。
