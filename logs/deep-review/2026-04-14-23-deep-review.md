### 维度 1：源码引用准确性
- 评分：3/5
- 问题数：5
- 具体问题：
  1. [P1] L170-188 — ViewRootImpl.relayoutWindow 代码块中的 mWindowSession.relayout() 方法签名使用了大量独立参数（mTmpFrames.mPendingContentInsets、mPendingMergedConfiguration 等），这是 Android 11 及更早的接口形态。Android 12 引入 BLAST BufferQueue 后，IWindowSession.relayout() 的参数结构发生了变化，多个 inset 参数被合并为 InsetsFlags 或通过其他结构传递。当前代码块标注为伪代码，但放在已验证章节中，容易误导读者以为这是 android-17 的真实签名。
  2. [P1] L224-229 — Perfetto SQL 查询使用 slice.name LIKE '%relayout%' 匹配 Slice 名称。文中表格列出 wm.relayout_window、wm.set_visibility、wm.pause_timeout 三个 Slice 名称，但这些名称未经实际 Perfetto Trace 验证。AOSP 中 WMS 的 atrace tag 可能使用不同命名（如 WM_RELAYOUT 或 relayoutWindow），直接用 %relayout% 模糊匹配可能导致误匹配或漏匹配。
  3. [P2] L91 — 验证标注写"relayoutWindow() 方法签名包含 Session、IWindow client、LayoutParams attrs 等参数"，这个描述过于概括，无法支撑后续代码示例的准确性。应标注具体验证的是哪个版本的签名。
  4. [P2] L126 — SurfaceControl.Transaction 代码示例标注为"伪代码"，但被放在"已验证"上下文的环境中。应明确标注这是示意代码还是实际 API。
  5. [P2] L240 — Slice 名称表格中 SurfaceControl.Transaction.apply 和 reportDrawFinished 的实际 Perfetto track/slice 命名缺少验证。reportDrawFinished 在 AOSP 中实际对应 ViewRootImpl.reportDrawFinish 或类似 trace event，不是直接的 Slice 名。

### 维度 2：原理链完整性
- 评分：3/5
- 问题数：4
- 具体问题：
  1. [P1] 全文 — WindowContainer 层级结构（DisplayContent -> DisplayArea -> Task -> WindowToken -> WindowState）完全未提及。这是 WMS 组织窗口的核心数据结构，不理解这个树形结构就无法理解 performLayout() 如何遍历窗口、relayout 如何影响多层级窗口、以及 WMS 的锁粒度。读者只知道 Window 对应 WindowState，不知道这些 WindowState 如何被组织和管理。
  2. [P1] L56 + L259 — mGlobalLock 在误区 1 中被提到是"WMS 需要的锁"，但正文从未解释这个锁的作用范围、持有时机、以及它与 system_server 主线程和 Binder 线程的关系。这是 WMS 性能分析中最关键的锁竞争源——AMS pause Activity 时持有 mGlobalLock 会阻塞 WMS 的 relayoutWindow——但读者从正文中无法建立这个因果链。
  3. [P2] L199 — performLayout() 被多次提到是性能瓶颈，但从未解释它具体做什么。它与 App 端 View 的 measure/layout 是完全不同的东西——WMS 的 performLayout 计算的是 Window 级别的 frame（parentFrame、displayFrame、contentFrame 等），不是 View 级别的布局。缺少这个区分会导致读者混淆。
  4. [P2] L83-89 — Surface 创建流程的第 2 步写"App 进程创建 ViewRootImpl，调用 WindowSession.relayout()"。实际上 ViewRootImpl 的创建发生在 WindowManager.addView() -> WindowManagerGlobal.addView() -> new ViewRootImpl() 链路中，而 relayout 是在后续的 ViewRootImpl.setView() 中触发的。将两个步骤合并跳过了 setView 这个关键环节。

### 维度 3：版本差异覆盖
- 评分：4/5
- 问题数：2
- 具体问题：
  1. [P1] L310-314 — "Android 16 (API 36) Desktop Windowing GA" 未区分大屏设备和手机端的可用性。Desktop Windowing GA 在 Android 16 首先面向大屏设备（外接显示器场景），手机端的 Desktop Windowing 在部分 Pixel 设备上通过 feature flag 开启。当前写法让读者以为所有 Android 16 设备都能用 Desktop Mode。
  2. [P2] 版本演进表 — 缺少 Android 10/11 的 WMS 内部架构重构（引入 DisplayArea、TaskFragment 等），这些重构直接影响了 performLayout() 的遍历方式和多窗口的实现路径。

### 维度 4：知识盲区
- 评分：3/5
- 盲区数：3
- 具体问题：
  1. [P1] 全文 — 缺少 BLAST BufferQueue 模型下 WMS 的角色变化。Android 12 引入 BLAST 后，Surface 的 dequeueBuffer/queueBuffer 不再由 SurfaceFlinger 管理，而是由 App 端直接管理。WMS 的 relayoutWindow 在创建/更新 Surface 时如何与 BLAST 交互，这是连接本章与 2.13 BufferQueue 的关键桥梁。
  2. [P2] 全文 — 缺少 TaskOrganizer / TaskFragment 的介绍。Android 12+ 的多窗口实现依赖 TaskOrganizer 来管理分屏边界和窗口模式切换，这是理解多窗口 relayout 性能开销的关键组件。
  3. [P2] L240 — 缺少 WMS 相关的 Perfetto trace category 配置说明。要看到 wm.* 相关的 Slice，需要在抓取 Trace 时启用 wm trace category。不提这个前提，读者按文中的 SQL 去查可能什么都查不到。
