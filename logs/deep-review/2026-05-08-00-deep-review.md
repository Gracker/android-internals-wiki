- [P1] L271-L274 dumpsys meminfo Activities / Views — [P1] 正文把 `Activities` 数量大于当前可见 Activity（通常 1）直接作为泄漏信号。`dumpsys meminfo` 的 Activities 会包含进程内仍处于 back stack、stopped、multi-window/多 Activity 场景中的合法实例；只和“当前屏幕可见数”比较会产生大量误报。 建议：改成受控复现口径：完成目标页面关闭/finish 后，等待一次 GC 与主线程空闲，再观察 Activities/Views 是否随重复进出单调增长；需要结合 LeakCanary 或 Heap Dump 的 GC Root path 才能确认泄漏。
- [P2] L331 ProfilingManager 线上采集 — 正文把 Android 15+ `ProfilingManager.requestProfiling()` 描述成“系统级零侵入触发能力”，但缺少 API 35 边界、rate limit、不保证一定执行、结果只落在应用数据目录/会被 redaction 的约束。 建议：补充 `PROFILING_TYPE_JAVA_HEAP_DUMP`、`PROFILING_TYPE_HEAP_PROFILE`、`PROFILING_TYPE_SYSTEM_TRACE` 的类型边界，并写明请求有系统限流与失败路径，线上只能作为按条件采样/诊断入口，不能替代常驻泄漏监控。

#### Top 问题
- [P1] L218-L241 Flutter FrameTiming 示例；L245-L260 Session Timeline — [P1] Flutter 段只上报 `buildDuration` / `rasterDuration` / `totalSpan`，但 Session Timeline 要求事件落到 `elapsed_realtime_ms`。`FrameTiming.timestampInMicroseconds(FramePhase)` 返回的是 Flutter 内部同一 epoch 下的 raw timestamp，官方说明不保证等于 `DateTime` epoch；正文没有给 Flutter 时间戳到 Native `elapsedRealtime` 的校准方法，无法把 UI/Raster jank 与 Native ANR、网络、WebView 事件放到同一时间轴。 建议：补充 Flutter 帧时间戳字段（frameNumber、vsyncStart/buildStart/rasterStart/rasterFinish 的 raw timestamp）和一次 Dart/Native 校准事件；如果只用 MethodChannel 接收时刻近似，要标注批量回调延迟与误差范围。
- [P2] L149-L178 PixelCopy 白屏采样示例 — 示例每次创建全宽、最高 480px 的 ARGB_8888 bitmap，没有检查 WebView 宽高/attach/window 状态，也没有复用或回收 bitmap；线上低频采样仍可能带来 Native heap 抖动或在宽高为 0 时抛异常。 建议：补充 `width/height > 0`、`isAttachedToWindow`、window token/可见性检查；使用下采样区域或 bitmap pool，分析后 `recycle()`/复用，并记录 PixelCopy result code 以区分采样失败和“非白屏”。
- [P2] L143 postVisualStateCallback 可见性说明 — `postVisualStateCallback` 只保证当前 WebView visual state 已准备好在后续 draw 中呈现，不保证已经显示到屏幕；WebView 被遮挡、未 attach、窗口不可见时也可能触发回调。正文用于白屏采样锚点时缺少这层边界。 建议：补一句：它只能作为渲染管线就绪信号，最终屏幕可见性仍要结合 View attach/visibility/window focus 和 PixelCopy/DOM/业务 ready 交叉判断。
