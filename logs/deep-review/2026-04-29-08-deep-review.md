### 5.3 大小核架构
#### 维度：源码引用准确性
- 评分：2/5
- 问题数：3
  - [P0] L101-L105 Perfetto SQL — 正文使用 `cpu_frequency_limits(max_freq)` 查询核心最大频率。Perfetto stdlib 文档未提供 `cpu_frequency_limits` 表；标准频率驻留表是 `linux.cpu.frequency` 模块的 `cpu_frequency_counters(cpu,freq,dur,...)`。该 SQL 直接不可执行。 建议：改为 `INCLUDE PERFETTO MODULE linux.cpu.frequency; SELECT cpu, max(freq)/1000.0 AS observed_max_freq_mhz FROM cpu_frequency_counters GROUP BY cpu;`，并说明它是 trace 期间观测到的最大频率，不等同于 sysfs `cpuinfo_max_freq`。
  - [P0] L254-L274 schedutil 代码片段 — 正文标注“Linux 6.6 实际签名”，但片段中 `cpu_util_cfs(rq)` 参数错误，且写入 `sg_cpu->max` 不是 Linux 6.6 `sugov_get_util()` 的实际结构。Linux 6.6 使用 `cpu_util_cfs_boost(sg_cpu->cpu)`、`cpu_bw_dl(rq)`、`effective_cpu_util(...)`；android16-6.12 又变为 `sugov_get_util(struct sugov_cpu *sg_cpu, unsigned long boost)` 并加入 `scx_cpuperf_target()`。 建议：按 Linux 6.6 与 GKI 6.12 分别给源码片段，避免把混合代码写成真实源码。
  - [P0] L90-L93 DSU-120 / 16KB 页 — 正文称 DSU-120 通过硬件寄存器开启 16KB 页模式、修正 Snoop Filter 哈希索引，并标“ARM 官方已验证”。公开 ARM/DSU-120 资料能确认 DSU/SCU/snoop filter 与 L3 cache slice，但未确认“16KB page mode + Snoop Filter 哈希寄存器”这一具体机制；snoop filter 通常按 cache line/coherency 状态工作，不应直接写成 OS page-size 优化。 建议：删除该段或改为待验证研究线索；如果要写，必须补 ARM TRM/whitepaper 页码或寄存器名。
