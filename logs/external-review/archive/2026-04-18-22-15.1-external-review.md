## 二、回炉问题摘要（P0 / P1）

### 1. [P0][源码准确性][第 145 行] ProfilingManager 版本严重错误

- **原文问题**：「Android 8 引入 ProfilingManager 并开始支持更多动态 trace point。」
- **核验结论**：ProfilingManager (`android.os.ProfilingManager`) 是 **Android 15 (API 35)** 引入的 API，不是 Android 8。该 API 允许应用在生产环境请求 profiling 数据（system traces、heap dumps、heap profiles、stack traces）。
- **源码 / 一手资料锚点**：
  - AOSP: `frameworks/base/core/java/android/os/ProfilingManager.java` (API 35+)
  - 官方文档: `developer.android.com/reference/android/os/ProfilingManager` (标注 Added in API level 35)
- **为什么错**：将 Android 15 的新 API 错误归属到 Android 8，版本差了 7 个大版本。Android 8 时期的 trace 相关变化主要是 atrace 的分类扩展和部分 ftrace 事件的增加，而非 ProfilingManager。
- **建议修正方向**：删除 Android 8 关于 ProfilingManager 的描述；如果要提 Android 8 的变化，应聚焦于 atrace 类别扩展或 systrace 改进。ProfilingManager 应该放在 Android 15 的描述中。

### 2. [P0][源码准确性][第 145 行] FrameMetrics API 版本错误

- **原文问题**：「Android 11-13 引入了 BlastBufferQueue 替代 BufferQueue、FrameMetrics API 暴露逐帧渲染耗时、以及 Baseline Profiles 等新机制」
- **核验结论**：FrameMetrics API (`android.view.FrameMetrics`) 是 **Android 7.0 (API 24)** 引入的，不是 Android 11-13。
- **源码 / 一手资料锚点**：
  - AOSP: `frameworks/base/core/java/android/view/FrameMetrics.java` (API 24+)
  - 官方文档: `developer.android.com/reference/android/view/FrameMetrics` (标注 Added in API level 24)
  - API 31 新增了 `DEADLINE` 指标
- **为什么错**：FrameMetrics 是 Android 7.0 就有的 API，而非 11-13。文章自身在 15.3 节（03-metrics.md 第 95 行）正确地写了「FrameMetrics API（Android 7.0+, API 24）」，与此处自相矛盾。
- **建议修正方向**：从 Android 11-13 的列表中移除 FrameMetrics。Android 11-13 的真正新增应聚焦于 BlastBufferQueue（Android 11-12）、FrameTimeline（Android 12）、`DEADLINE` 指标（API 31）等。

### 3. [P1][版本差异][第 144-145 行] BlastBufferQueue 版本和性质描述不准确

- **原文问题**：
  - 第 144 行：「Android 12 引入了 BlastBufferQueue 替代 BufferQueue」
  - 第 145 行：「Android 11-13 引入了 BlastBufferQueue 替代 BufferQueue」
  - 两处自相矛盾（12 vs 11-13），且"替代"一词不准确
- **核验结论**：
  - BLASTBufferQueue 在 **Android 11 (API 30)** 开始引入，**Android 12 (API 31)** 成为默认路径
  - BLASTBufferQueue **不是 BufferQueue 的替代品**，而是 BufferQueue 的上层封装/适配器。底层 BufferQueue 机制仍然存在，BLASTBufferQueue 改变的是 buffer 提交给 SurfaceFlinger 的方式（将 buffer 与 SurfaceControl transaction 打包同步提交）
- **一手资料锚点**：
  - AOSP: `frameworks/native/libs/gui/BLASTBufferQueue.cpp`
  - BLASTBufferQueue 内部仍然使用 BufferQueue 管理 buffer handle
- **建议修正方向**：
  1. 统一版本描述为「Android 11 引入、Android 12 成为默认路径」
  2. 将「替代 BufferQueue」改为「改变了 buffer 提交方式」或「在 BufferQueue 之上增加了同步提交机制」

### 4. [P1][版本差异][第 312 行] Baseline Profiles 适用版本描述有误

- **原文问题**：「Baseline Profiles（2022，随 Jetpack 从 Android 13 起分发）」
- **核验结论**：Baseline Profiles 通过 Jetpack `androidx.profileinstaller` 库工作，支持 **Android 7.0+ (API 24+)**，不是「从 Android 13 起」。Android 12 引入了云端 profile 分发（Cloud Profiles），Android 13 加速了云端分发的时效性，但这与 Baseline Profiles 本身的适用范围不同。
- **一手资料锚点**：
  - 官方文档: `developer.android.com/topic/performance/baselineprofiles`
  - Google Android Developers Blog, 2022-01-28: "Improving App Performance with Baseline Profiles"
- **为什么这是重要缺失**：读者可能误以为 Baseline Profiles 只在 Android 13+ 设备上有效，错过了在 API 24-32 设备上的优化机会
- **建议修正方向**：改为「Baseline Profiles（2022，通过 Jetpack ProfileInstaller 支持 Android 7.0+）」

### 5. [P1][数据/案例支撑][第 99 行] Google 搜索流量数据引用不够精确

- **原文问题**：「Google 的研究则表明，搜索结果页生成时间每增加 0.5 秒，流量会下降 20%」
- **核验结论**：这不是一个「每增加 0.5 秒就下降 20%」的线性规律。实际情况是 Marissa Mayer 在 2006 年 Web 2.0 会议上分享的一个**特定 A/B 测试**结果：Google 将搜索结果从 10 条增加到 30 条，页面生成时间从 0.4 秒增加到 0.9 秒（增加了 0.5 秒），流量下降了 20%。这是一次性实验结果，不是通用规律。
- **一手资料锚点**：
  - Greg Linden blog: glinden.blogspot.com/2006/11/marissa-mayer-at-web-20.html
  - Marissa Mayer, Web 2.0 Summit, 2006
- **建议修正方向**：改为「Google 在一次 A/B 测试中发现，搜索结果页从 10 条扩展到 30 条后，页面生成时间增加了约 0.5 秒，流量下降了 20%」

### 2. 源码锚点

### 3. 版本差异摘要
- **Android 7 (API 24)**：FrameMetrics API 引入
- **Android 8 (API 26)**：atrace 扩展、StrictMode 增强
- **Android 9 (API 28)**：Perfetto 初步引入
- **Android 10 (API 29)**：Perfetto 成为标准 trace 工具
- **Android 11 (API 30)**：BLASTBufferQueue 引入
- **Android 12 (API 31)**：BLASTBufferQueue 成为默认、FrameTimeline 引入、FrameMetrics 新增 DEADLINE 指标
- **Android 15 (API 35)**：ProfilingManager API 引入
- **Android 16 (API 36)**：System-triggered profiling 增强

### 5. 可直接复用的技术结论
- BLASTBufferQueue 不是 BufferQueue 的"替代品"，而是上层封装，底层 BufferQueue 机制仍在
- Baseline Profiles 通过 Jetpack ProfileInstaller 支持 API 24+，不限于 Android 13
- Google 搜索 20% 流量下降是特定 A/B 测试结果，不是通用线性规律
