## 五、P1 问题（重要缺失）
- [P1][源码准确性][Java 泄漏：重点是 dump 成本]

  - 源码 / 一手资料锚点：`dalvik/system/VMDebug.java` (`dumpHprofData()`)。
  - 缺失内容：原生的 `VMDebug.dumpHprofData()` 在 ART 中执行时会触发 Stop-The-World (STW)，挂起所有线程，这正是线上直接 dump 会引发 ANR 的根源所在。并且，KOOM 在使用 fork 时，必须处理子进程中复杂的锁状态与死锁风险。
  - 为什么这是重要缺失：这是 KOOM 解决的最大痛点。不交代 `dumpHprofData()` 带来的 STW，就无法凸显 fork dump 的必要性；不交代多线程环境下的 fork 风险，技术细节便显得漂浮。

- [P1][源码准确性][Native leak 检测的成本点]
  - 原文问题：文中提到“记录分配元数据，再扫描进程内存中可达指针”，但未交代记录的手段。
  - 缺失内容：KOOM 监控 Native 内存分配强依赖于 PLT Hook 技术（主要使用了 bhook 或 xhook 等优秀的开源 Hook 框架）来拦截 `malloc`、`free` 等底层 C 函数。
  - 为什么这是重要缺失：拦截 libc 内存分配是 Native 监控工具的基础。如果不说明使用 PLT Hook 及具体的库引擎（如 bhook），读者无法建立可落地的工程实践认知。
  - 建议补充方向：补充基于 PLT Hook（bhook/xhook）技术拦截 libc 函数的原理说明。

- [P1][版本差异覆盖][和 Android 系统内存信号配合]

### 9.4 可复用知识资产（高价值新增知识）
- **章节**：`03-koom.md`
- **一手资料链接或来源类型**：AOSP (`dalvik/system/VMDebug.java`) / KOOM GitHub
- **关键源码路径**：`dalvik/system/VMDebug.java` -> `dumpHprofData()`
- **关键调用链 / 代码逻辑摘要**：原生的 `dumpHprofData()` 操作在底层会引发虚拟机的 SuspendAll（STW），严重阻塞包括主线程在内的所有线程。KOOM 为了规避该痛点，采用了 Linux 的 Copy-on-Write 机制，通过 `fork()` 创建子进程在后台执行 Hprof 写入操作，使父进程可以瞬间恢复执行。同时配合诸如 bhook 等 PLT Hook 工具，将底层的内存释放分配以及线程状态尽收眼底。
- **Trace / Perfetto 观察点**：在 Perfetto Trace 中，若是使用原生的 `Debug.dumpHprofData()`，可以在主线程看到长达数秒甚至十几秒以上的超长 block 状态；如果应用了 KOOM 方案，则主进程的 block 耗时呈数量级下降，具体的耗时 IO 与文件生成被承接到派生的子进程轨道中。
- **为什么这条知识值得保留**：它是现代端侧 OOM 治理实现“无感”监测方案的根基，也是区别于传统本地开发依赖 LeakCanary 的最大工程亮点。
