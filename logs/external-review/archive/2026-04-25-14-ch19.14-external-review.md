## 五、P1 问题（重要缺失）
- [P1][原理链完整性/知识盲区][Microbenchmark 测小代码段]
  - 原文问题：完全遗漏了防御死代码消除（DCE）的机制，且未按照大纲要求覆盖 `Blackhole` 和 `BenchmarkState`。
  - 源码 / 一手资料锚点：`androidx.benchmark.Blackhole` 及其 `consume()` 方法，`androidx.benchmark.BenchmarkState`。
  - 缺失内容：Microbenchmark 执行的代码段往往因为返回值未被使用，在 AOT 编译阶段被编译器直接优化掉（Dead Code Elimination），导致耗时测出来为 0 或极小。
  - 运行原理说明：必须使用 `Blackhole.consume(result)` 来强制消费变量，欺骗编译器保留被测代码逻辑。
  - 为什么这是重要缺失：这是写 Microbenchmark 时最容易踩坑、最常导致“测了假数据”的致命点，大纲已要求却未覆盖。
  - 建议补充方向：在“避免测错对象”部分增加一个由于未处理返回值导致 DCE 的反面示例，并展示如何使用 `Blackhole.consume()` 修复。

- [P1][原理链完整性/实战落地][和 Baseline Profiles 的配合 & 工程形态]
  - 原文问题：未提及 `androidx.profileinstaller:profileinstaller` 依赖，以及 `BaselineProfileRule` 的使用。
  - 源码 / 一手资料锚点：`androidx.benchmark.macro.junit4.BaselineProfileRule` 及 `androidx.profileinstaller.ProfileInstaller`。
  - 缺失内容：要在本地或 CI 的 Android 7.0+ (API 24+) 设备上使得 `CompilationMode.Partial` 生效，**被测 App** 必须包含 `profileinstaller` 依赖。否则 Macrobenchmark 库无法将 Profile 写入被测 App 并触发编译。
  - 运行原理说明：Macrobenchmark 依赖 ProfileInstaller 将基线配置文件写入应用的私有目录，并发送广播要求 `bg-dexopt` 守护进程进行预编译。如果没有该依赖，`Partial` 模式将退化或失败。另外，生成 Baseline Profile 用的是 `BaselineProfileRule`，而不是 `MacrobenchmarkRule`。
  - 为什么这是重要缺失：缺乏 `profileinstaller` 会导致读者照着书写完示例后，跑出来的并不是 Partial 预编译效果；且混淆了两类 Rule 的职责。
  - 建议补充方向：明确指出目标 App 需要引入 `profileinstaller`；在“和 Baseline Profiles 的配合”小节明确指出生成 Profile 需使用 `BaselineProfileRule`。
