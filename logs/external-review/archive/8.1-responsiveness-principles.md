## 五、P1 问题（重要缺失）
- [P1][源码准确性][系统级响应路径：从触摸到像素 - 第一步：Input 事件的捕获与分发]
- 原文问题：“App 进程的 InputConsumer（在主线程的 NativeMessageQueue 中监听）接收到事件后，将其封装为 Java 层的 MotionEvent，投递到主线程的消息队列中。”
- 源码 / 一手资料锚点：`frameworks/base/core/jni/android_view_InputEventReceiver.cpp` (`NativeInputEventReceiver::handleEvent`) 与 `frameworks/base/core/java/android/view/InputEventReceiver.java`。
- 关键代码逻辑：Input 事件到达 App 进程是通过 `InputChannel` (基于 unix domain socket)。主线程的 native `Looper` 使用 `epoll_wait` 监听这个 socket fd。当有数据到达时，`Looper` 会唤醒，并直接在底层触发 `handleEvent` 回调，进而调用 Java 层的 `dispatchInputEvent`。
- 为什么错：这会让读者误以为 Input 事件被封装成了 Java 层的 `android.os.Message` 并“投递到主线程的消息队列中”排队（类似 `Handler.sendMessage`）。实际上，它是作为 fd 的回调事件在 `Looper` 本次轮询醒来时被同步且优先处理的。
- 建议修正方向：明确 Input 事件是通过 socket 触发 native Looper 的 epoll 唤醒，随后直接在回调中执行 Java 层的输入分发逻辑，而不是作为普通 Message 在 Java 队列中排队。
