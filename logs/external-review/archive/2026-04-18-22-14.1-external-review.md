## 四、P0 问题（事实错误）
- [P0][源码准确性][使用 Profiler API 在代码中触发 profiling]
- 原文问题：“Android 提供了 `ProfilingManager` API（Android 16，API 36 新增）... 触发器包括：`TRIGGER_TYPE_COLD_START`...”

- 关键代码逻辑：公开的 API 使用的是 `PROFILING_TYPE_SYSTEM_TRACE`, `PROFILING_TYPE_JAVA_HEAP_DUMP` 等常量，通过 `requestProfiling` 方法调用。
- 运行原理说明：`ProfilingManager` 主要是为了允许 App **主动**在生产环境中进行性能剖析（App-driven profiling），收集数据（Trace/Heap Dump）后再通过回调处理。
- 版本差异：`ProfilingManager` 实际上是在 **Android 15 (API 35)** 引入的，并非 Android 16 (API 36)。
- 核验结论：引入版本错误（API 35 误写为 36）。常量名称错误（不存在公开的 `TRIGGER_TYPE_COLD_START` 等常量，这是臆想或内部机制的混淆）。
- 为什么错：误导读者使用不存在的常量，并且把引入版本搞错了，导致开发者在错误的目标版本下查阅文档。
- 建议修正方向：修正版本号为 Android 15 (API 35)。删除虚假的 `TRIGGER_TYPE_*` 常量，改用官方的 `PROFILING_TYPE_SYSTEM_TRACE` 等真实类型来举例，并正确介绍 `requestProfiling` API。

## 五、P1 问题（重要缺失）
- [P1][知识盲区][使用 Profiler API 在代码中触发 profiling]
- 原文问题：文章描述 `ProfilingManager` 完全侧重于“系统级自动触发”（注册触发器等）。
- 源码 / 一手资料锚点：`ProfilingManager.requestProfiling()`
- 缺失内容：遗漏了 `ProfilingManager` 最核心的也是最推荐的使用场景：**App 驱动的性能分析 (App-driven profiling)**。
- 运行原理说明：在生产环境中，App 可以自己判断何时遇到性能瓶颈（例如帧率突然掉底），然后主动调用 `ProfilingManager.requestProfiling()` 触发一段 System Trace，这才是该 API 赋能开发者的最大价值。
- 为什么这是重要缺失：只讲系统触发会让读者认为这完全是一个被动工具，忽略了它在主动监控（APM 建设）中的核心战略意义。
- 建议补充方向：补充 `requestProfiling` 的主动调用场景，说明 App 如何通过代码主动请求 Trace/Heap Dump 并在回调中上传到服务端。
