## 四、P0 问题（事实错误）
- [P0][源码准确性][4.1 Buffer Management & 7.2 常见错误]
- **原文问题**：原文断言 "Android 10-15 没有 NDK 级 release callback 时... OnComplete 只能说明事务完成，不直接等价于 buffer 已释放"，要求开发者自己靠记账或保守延迟来维护。
- **源码 / 一手资料锚点**：`cs.android.com` `frameworks/native/include/android/surface_control.h` 中的 `ASurfaceTransactionStats_getPreviousReleaseFenceFd` (API 29)。
- **关键代码逻辑**：`ASurfaceTransaction_setOnComplete` 的回调中提供的 `ASurfaceTransactionStats*` 对象。
- **运行原理说明**：在 API 36 引入 `setBufferWithRelease` 之前，系统释放前一个 Buffer 的标准途径就是触发 `OnComplete`，开发者在回调内通过 `ASurfaceTransactionStats_getPreviousReleaseFenceFd(stats, surface_control)` 获取刚刚被替换下来的 Buffer 的 Release Fence fd。当该 fd signal 后，或者返回 -1 时，即可安全回收该 Buffer 供下一次渲染复用。
- **版本差异**：API 29 引入 `OnComplete` 及对应的 fd 获取；API 36 为了逻辑更加解耦和聚焦 buffer 池回收，引入了专用的 `setBufferWithRelease`。
- **核验结论**：AOSP 源码中对 `OnComplete` 明确支持获取 previous release fence，且是 API 29 以来的官方回收路径。
- **为什么错**：如果应用不使用这个机制而像文中说的一样“靠自己记账”，极易导致屏幕撕裂或大量 buffer 堆积，给读者传达了完全错误的最佳实践。
- **建议修正方向**：明确说明在 Android 10-15 期间，必须在 `OnComplete` 配合 `getPreviousReleaseFenceFd` 进行回收；然后指出 API 36 是其简化升级版。

## 五、P1 问题（重要缺失）

- **原文问题**：提到 "或从 ANativeWindow 创建"，但没说 `ANativeWindow` 是怎么来的。
- **源码 / 一手资料锚点**：NDK `<android/native_window_jni.h>` 的 `ANativeWindow_fromSurface`。
- **缺失内容**：从 Java 层的 `SurfaceView` 到 NDK `ASurfaceControl` 树挂接的初始链路。
- **运行原理说明**：由于 NDK 无法直接接触 Android View 树，实际工程中通常是在 Java 层使用 `SurfaceView` 占位，获取其 `Surface` 并通过 JNI 传递到 C++ 层。C++ 层通过 `ANativeWindow_fromSurface(env, jSurface)` 拿到 `ANativeWindow`，再调用 `ASurfaceControl_createFromWindow`。这就是 NDK 侧的根节点来源。
- **为什么这是重要缺失**：如果不解释这一环，读者知道怎么操作 NDK Layer 树，却不知道怎么把这棵树挂到 App 的屏幕上。
- **建议补充方向**：用简短的代码片段补充 `Surface` -> `ANativeWindow` -> `ASurfaceControl` 的桥接过程。

2. 
- [P1][知识盲区][4.2 Hierarchy Management / 8.2 画中画]
- **原文问题**：讲解了 reparent 和 画中画（PiP），但遗漏了跨进程 Layer 共享的关键点：如何将一个进程创建的 `SurfaceControl` 挂载到另一个进程？
- **源码 / 一手资料锚点**：Java 层 `android.view.SurfaceControl` 的 `Parcelable` 实现。
- **缺失内容**：`ASurfaceControl` 本身在 NDK 中缺乏显式的跨进程 Binder 传递机制。
- **运行原理说明**：PiP 或多窗口重组如果涉及跨进程挂载，往往必须依赖 Java 层的 `SurfaceControl` 作为 Parcelable 在进程间穿梭。NDK 目前无法直接用一个裸指针或 fd 来实现 `reparent` 到别家进程。
- **为什么这是重要缺失**：高级实战中（如浏览器多进程渲染），开发者很可能面临跨进程组织图层树的问题，这里存在明显的认知黑盒。
- **建议补充方向**：明确指出 NDK 侧 `ASurfaceControl` 目前的跨进程局限性，说明在 IPC 场景通常需要回到 Java 层封装处理。
