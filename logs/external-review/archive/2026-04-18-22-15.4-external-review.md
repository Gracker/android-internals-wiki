## 三、回炉问题摘要（P0 / P1）

### 1. [P1][源码准确性][第 115 行] TotalTime 的测量端点描述不精确

- **原文问题**：「它的原理很简单：通过 Activity Manager 发送一个启动 Intent，然后等待目标 Activity 完成 `onResume()` 回调后返回计时结果。」
- **核验结论**：**TotalTime 的终点不是 `onResume()` 回调**，而是**第一帧绘制完成**（first frame drawn）。具体来说，系统通过 `ViewRootImpl` 监控 `doTraversal()`（包含 measure → layout → draw）的完成，Choreographer 确认第一帧绘制完成后才报告 TotalTime。`onResume()` 之后还有布局膨胀和首帧渲染的过程，这部分时间包含在 TotalTime 中。
- **源码锚点**：
  - AOSP: `frameworks/base/services/core/java/com/android/server/wm/ActivityRecord.java` — 启动计时逻辑
  - AOSP: `frameworks/base/core/java/android/view/ViewRootImpl.java` — `doTraversal()` 完成标志
  - logcat 中 `ActivityTaskManager: Displayed` 标记的就是 TotalTime 对应的 TTID
- **为什么这是重要缺失**：如果读者以为 TotalTime 在 `onResume()` 时就结束了，可能会误解为什么将复杂布局的 inflate 从 `onCreate` 移到 `onResume` 后面不能改善 TotalTime——因为 TotalTime 实际包含了 `onResume()` 之后的整个首帧绘制过程。
- **建议修正方向**：改为「通过 Activity Manager 发送一个启动 Intent，然后等待目标 Activity 的第一帧绘制完成后返回计时结果。TotalTime 对应的是 TTID（Time to Initial Display），从进程创建到首帧绘制完成的全部耗时。」

## 五、一般建议摘要（P2）

### 1. [P2][数据/案例支撑][第 274 行] FrameMetrics TOTAL_DURATION 起点描述不够精确
- **位置**：第 274 行
- **问题描述**：文中说「FrameMetrics 的 `TOTAL_DURATION` 从 `performTraversals()` 开始到帧提交到 BufferQueue 结束」。严格来说，TOTAL_DURATION 覆盖的是从 `VSYNC` 信号（帧开始时间点）到 `SWAP_BUFFERS` + `COMMAND_ISSUE` 结束（GPU 命令提交完成），包含了 VSYNC 到 performTraversals 之间的 input handling 和 animation 时间。
- **建议**：改为「`TOTAL_DURATION` 覆盖从 VSync 信号到 GPU 命令提交完成的全过程」

### 2. [P2][数据/案例支撑][第 280 行] APK 体积转化率数据需标注来源和时效性
- **位置**：第 280 行
- **问题描述**：「APK 体积每增加 10MB，安装转化率下降约 1.5%」——Google 确实公布过类似数据，但具体数字因年份、市场和 App 类型而异。建议标注数据来源和年份。
- **建议**：加注「来源: Google I/O 2019, "Size matters: Reduce your app size and increase installs"；该数据为全球平均，新兴市场的影响更大」

### 3. [P2][原理链完整性][第 92 行] 动画缩放建议值存在取舍问题
- **位置**：第 92 行
- **问题描述**：文中建议「将动画缩放设为 0.5x 或关闭」。但设为 0x（关闭动画）会导致某些 App 的启动动画被跳过，可能改变启动流程的时序（如某些 Activity 依赖过渡动画完成才触发后续逻辑）。而设为 0.5x 则动画仍然存在但更短。建议更明确地说明选择的取舍。
- **建议**：修改为「设为 0.5x（保留动画但缩短时长）或 1x（保持默认，如果要对比真实用户体验）。不建议完全关闭（0x），因为某些 App 的启动流程可能依赖动画完成回调。」

## 六、可复用知识资产

### 1. 一手资料索引
- **AOSP / cs.android.com**：
  - `frameworks/base/services/core/java/com/android/server/wm/ActivityRecord.java` — 启动计时逻辑
  - `frameworks/base/core/java/android/view/ViewRootImpl.java` — doTraversal() 和首帧绘制完成标志
- **developer.android.com**：
  - `developer.android.com/topic/performance/launch-time` — TotalTime = TTID 定义
  - `developer.android.com/studio/build/apk-analyzer` — APK Analyzer
  - `developer.android.com/topic/performance/benchmarking/macrobenchmark-overview` — Macrobenchmark

### 2. 源码锚点
- **文件路径**：`frameworks/base/services/core/java/com/android/server/wm/ActivityRecord.java`
- **关键方法**：与 `Displayed` 日志对应的计时逻辑
- **为什么重要**：TotalTime 的终点是首帧绘制完成，不是 onResume()

### 3. 版本差异摘要
- **Android 12 (API 31)**：SplashScreen API 引入，影响 TotalTime 包含的内容
- **Android 12+**：`cmd package compile -m speed` 可强制全量编译

### 4. Trace / Perfetto 观察点
- **观察点 1**：竞品流畅性对比时，帧耗时的 P50/P90/P99 分布比平均 FPS 更有分析价值
- **观察点 2**：对比滑动 Trace 时需使用 `input swipe` 自动化操作，避免手工操作引入噪声
- **观察点 3**：Trace 采样时长建议 ≥10 秒以获得统计意义

### 5. 可直接复用的技术结论
- `am start -W` 的 TotalTime 对应 TTID（首帧绘制完成），不是 onResume() 回调
- `am kill-all` 只杀 safe-to-kill 后台进程，不影响前台 app
- 竞品启动对比建议至少 20-30 次采样，取中位数而非均值
- 编译状态（JIT vs AOT）可导致 20%+ 的启动时间差异
