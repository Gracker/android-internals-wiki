## 五、P1 问题（重要缺失）
- [P1][原理链完整性/知识盲区][核心架构/在 Perfetto 中识别]
  - **原文问题**：文章提到“Perfetto 里通常还能看到 app 进程的 RenderThread 和对应 GPU 工作”，但没有进一步说明 HBR 对 `RenderThread` 的抢占效应。
  - **关键机制**：`HardwareBufferRenderer` 并没有创建独立的 OpenGL/Vulkan 上下文或专属线程，它**与当前 App 进程的 UI 绘制（ViewRootImpl）共享同一个全局的 `RenderThread`**。
  - **为什么这是重要缺失**：如果开发者误以为 HBR 是“完全离屏且不影响 UI”，而在主进程的 HBR 中绘制极度复杂的 PDF 或位图，会直接阻塞 `RenderThread`，导致主 UI 的 `syncAndDrawFrame` 无法执行，从而引发严重的主界面掉帧（Jank）。这是实战中最容易踩坑的性能误区。
  - **建议补充方向**：在“核心架构”或“性能对比”中补充“共享 `RenderThread` 竞争”的警告；在“在 Perfetto 中识别”中，增加观察 `RenderThread` 被 HBR 任务长时间占据导致 UI Thread `DrawFrame` 迟延的 Trace 模式。

- [P1][版本差异覆盖][NDK API]
  - **原文问题**：NDK API 部分提到 `ASurfaceTransaction_setBufferWithRelease` 从 API 36 开始引入，并说明 Android 10-15 只有 `ASurfaceTransaction_setBuffer()`，需自己维护计数。这没错，但遗漏了 Java API 和 NDK API 在此处的断层对比。
  - **版本差异**：Java 层的 `setBuffer(..., fence, releaseCallback)` 在 API 33 (Android 13) 就已经公开。而 `HardwareBufferRenderer` 是 API 34 引入。因此 Java 侧完全可以在 API 34 直接用 callback 处理回收。但 NDK 侧 API 34、35（Android 14/15）不仅没有 `HardwareBufferRenderer` 的官方 NDK 封装，连安全回调 `setBufferWithRelease` 也没有（API 36 才补齐），只能退而求其次用 `ASurfaceTransaction_setOnComplete`。
  - **为什么这是重要缺失**：会导致跨端开发者在 Android 14/15 平台上用 NDK 仿写 Java HBR 逻辑时，找不到释放 Buffer 的对应方法。
  - **建议补充方向**：在 NDK 降级与版本差异部分，明确强调 Android 14/15 (API 34-35) 期间 Java 层与 NDK 层在 Release Callback 能力上的断层。
