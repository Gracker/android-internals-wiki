## 四、P0 问题（事实错误）
- [P0][源码准确性][软件事件：cpu-clock 和 task-clock]
- 原文问题：“`task-clock`：与 cpu-clock 类似，但还包括线程等待 CPU 调度的时间。”
- 源码 / 一手资料锚点：Linux 内核 `perf_event` 机制文档 (`man perf_event_open`) / Brendan Gregg 的 Linux 性能分析指南
- 关键代码逻辑：`task-clock` 绑定在具体的 task (线程/进程) 上，**只有当该 task 在 CPU 上实际运行 (Running 状态) 时，该时钟才会走动**。当 task 被调度器切出（如等待 I/O、Sleep 或在就绪队列中等待 CPU）时，`task-clock` 是停止的。
- 运行原理说明：如果 `task-clock` 包含了等待时间，它就变成了一个 Wall-Clock (现实时间) 采集器，这完全违背了 CPU Profiling 的初衷（找占用 CPU 的热点）。分析等待时间必须使用 `sched` 事件（或 off-CPU profiling）。
- 核验结论：原文描述完全反转了该事件的真实机制。
- 为什么错：不仅是概念错误，还会严重误导排查方向——如果开发者认为 `task-clock` 包含等待时间，看到某函数占比高，可能会误以为是它在“等”某样东西，而实际是它把 CPU“吃”满了。
- 建议修正方向：明确 `task-clock` 是纯粹的 CPU 执行时间（不包含任何挂起/等待时间），它与 `cpu-clock` 在分析单进程时基本等效，只是一个是 task 粒度，一个是 CPU 粒度。
