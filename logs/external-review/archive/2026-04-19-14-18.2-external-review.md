## 四、P0 问题（事实错误）
- [P0][源码准确性][18.2.4 Trace 视角]
- **原文问题**：将 `syncFrameState` Slice 列在了 "UI Thread 关键 Slice" 表格中。
- **源码 / 一手资料锚点**：AOSP `frameworks/base/libs/hwui/renderthread/DrawFrameTask.cpp` 的 `DrawFrameTask::run()` 方法。
- **关键代码逻辑**：UI 线程在 `ThreadedRenderer::syncAndDrawFrame` 中组装好 `DrawFrameTask` 后，将其 post 给 RenderThread 执行，然后 UI 线程调用 `wait()` 阻塞自己。RenderThread 在执行 `DrawFrameTask::run()` 时，首先调用 `syncFrameState()` 方法进行数据树同步。
- **运行原理说明**：`syncFrameState` 的实际执行者以及在 Perfetto 中打出 ATRACE 标记的，都是 **RenderThread**。UI 线程在此期间的 Slice 通常名为 `DrawFrame`（或表现为持续 1-2ms 的阻塞等待状态），而不是 `syncFrameState`。
- **核验结论**：Trace 中的 `syncFrameState` 属于 RenderThread，原文归类错误，会直接误导读者通过 Perfetto 定位主线程/渲染线程耗时瓶颈时的判断。
- **建议修正方向**：将 `syncFrameState` 移入 "RenderThread 关键 Slice" 表格，并说明 UI 线程在此阶段是通过等待 RenderThread 通知而阻塞。

## 五、P1 问题（重要缺失）
- [P1][原理链完整性][18.2.2 BLAST Buffer 生命周期]
- **原文问题**：对于 `releaseBuffer` 操作，仅简述为 "SF（通过回调） ACQUIRED → FREE"，没有说明 BLAST 的核心解耦设计，原理链断裂。
- **源码 / 一手资料锚点**：AOSP `frameworks/native/libs/gui/BLASTBufferQueue.cpp` 中的 `transactionCallback`。
- **关键代码逻辑**：在 BLAST 架构下，SurfaceFlinger 不再直接作为 Consumer 调用 release。当 SF 完成渲染且 Buffer 被替换后，SF 通过 `ITransactionCompletedListener` 发起 `onTransactionCompleted` Binder 回调，将 `ReleaseCallbackId` 和 `releaseFence` 发送回 App 进程。App 进程中的 BLASTBufferQueue 收到回调后，再调用内部 `BLASTBufferItemConsumer::releaseBuffer`。
- **缺失内容**：遗漏了 BLAST 模式下，Consumer 实际上位于 App 进程，通过跨进程的 Transaction 回调来实现释放的这一核心闭环。
- **运行原理说明**：旧版 BufferQueue 中 SF 是 Consumer；BLAST 中 App 进程的 BBQ 是 Consumer。这解释了为什么 App 的 dequeue 会受 SF 回调延迟的影响。
- **为什么这是重要缺失**：这是理解 "为什么 App 侧的 dequeueBuffer 会卡住" 以及 "BLAST 为什么能彻底解耦" 的核心源码机制，实战中极具排查价值。
- **建议补充方向**：补充基于 `TransactionCompletedCallback` 的异步释放机制，明确 Consumer 处于 App 进程。

- [P1][源码准确性][18.2.5 FrameTimeline 与 Jank 检测]
- **原文问题**："RenderThread 在 queueBuffer 时将 VSyncId 传递给 SurfaceFlinger" 这一表述在 BLAST 模式下机制不准确。
- **源码 / 一手资料锚点**：AOSP `frameworks/native/libs/gui/BLASTBufferQueue.cpp` 中的 `setFrameTimelineInfo`。
- **关键代码逻辑**：在 BLAST 模式中，RenderThread 将 VsyncId 传给 BBQ，BBQ 会将其打包进 `SurfaceControl.Transaction` 对象，调用 `Transaction::setFrameTimelineInfo`，最终通过 `apply()` 跨进程发给 SF，而非通过 `IGraphicBufferProducer::queueBuffer` 传递。
- **为什么这是重要缺失**：未体现 FrameTimeline 数据在 BLAST 模式下是搭乘 Transaction 顺风车这一关键架构特性。
- **建议补充方向**：明确 VSyncId 的跨进程传递载体是 `SurfaceControl.Transaction` 的 `setFrameTimelineInfo`。
