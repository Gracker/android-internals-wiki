## 五、P1 问题（重要缺失/不准）
- [P1][源码准确性][红黑树：O(log N) 的调度队列]
- **原文问题**：提到“最左边的节点就是 vruntime 最小的进程，也就是下一次应该被调度执行的进程”。
- **源码 / 一手资料锚点**：`kernel/sched/fair.c`, `pick_eevdf()` (Linux 6.6+)
- **关键代码逻辑**：EEVDF 选人时，先判定 `entity_eligible()` (lag >= 0)，然后在合格实体中寻找 `deadline` 最小的任务。
- **运行原理说明**：在 EEVDF 中，`vruntime` 最小的任务（红黑树最左侧）如果不符合 `eligible` 条件，或者有其他 `eligible` 任务的 `deadline` 更早，最左侧任务就不会被选中。
- **为什么构成 P1**：这打破了 CFS 时代长达十几年的“取最左节点”常识。如果读者沿用旧思维分析 6.6+ 内核的 Trace，会产生困惑。
- **建议修正方向**：明确指出在 EEVDF 模式下，红黑树虽仍以 `vruntime` 排序，但调度器执行的是基于 `deadline` 的树搜索（利用 `min_deadline` 属性），不再是简单的取最左指针。

- [P1][版本差异覆盖][Android 中绑核和 CPU 可用范围的几条路径]
- **原文问题**：提到 `sched_setattr` 的可用性。
- **源码 / 一手资料锚点**：Bionic `libc/include/sched.h`, `__INTRODUCED_IN(37)`。
- **关键代码逻辑**：Bionic 在 API 37 才正式提供了 `sched_setattr` 和 `sched_getattr` 的封装函数。在此之前（如 API 35/36），开发者必须使用 `syscall(SYS_sched_setattr, ...)`。
- **为什么构成 P1**：文中提到 EEVDF 调优涉及 `sched_setattr`，如果不说明 API 37 这一界限，开发者在 Android 15/16 上直接调用会报 Link error。
- **建议修正方向**：明确区分“系统调用可用性（Linux 3.14+）”、“EEVDF 功能支持（Linux 6.6+ / Android 15+）”与“Bionic 包装函数引入（API 37）”。
