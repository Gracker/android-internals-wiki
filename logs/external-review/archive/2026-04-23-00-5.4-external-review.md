## 四、P0 问题（事实错误）
- **[P0][源码准确性][schedutil 频率计算公式]**
- **原文位置**：`## cpufreq 子系统与 Governor 机制` -> `#### schedutil 的频率计算`
- **原文问题**：公式描述为 `f_target = 1.25 × f_max × util / max_capacity`，这在现代 Android 内核中是误导性的。
- **源码 / 一手资料锚点**：`kernel/sched/cpufreq_schedutil.c` -> `sugov_get_util()` (Android 16-6.6)
- **关键代码逻辑**：
  ```c
  static unsigned long sugov_get_util(struct sugov_cpu *sg_cpu) {
      util = cpu_util_cfs(sg_cpu->cpu); // 基础利用率
      util = uclamp_rq_util_with(rq, util, NULL); // 应用 uclamp 钳位
      return sugov_apply_iowait_boost(sg_cpu, util); // 应用 iowait boost
  }
  ```
- **运行原理说明**：最终参与频率计算的 `util` 是经过 `uclamp`（性能钳位）和 `iowait boost` 修正后的。
- **核验结论**：即使 CPU 利用率（PELT）很低，如果 `uclamp_min` 很大（例如 top-app 被赋予了高 boost 值），频率也会被强行拉高。
- **建议修正方向**：明确“有效利用率（Effective Utilization）”概念，说明它是由 `PELT`、`uclamp` 和 `iowait boost` 三者竞争产生。

## 五、P1 问题（重要缺失）
- **[P1][版本差异覆盖][ADPF Android 15/16 演进]**
- **原文位置**：`### ADPF：让应用参与调频决策`
- **原文问题**：仅覆盖了 Android 12 的 CPU 时长报告。
- **一手资料锚点**：`developer.android.com` -> "What's new in ADPF for Android 15/16"
- **缺失内容**：
  1. **GPU 工作时长报告**：Android 15 引入 `WorkDuration` 类，支持报告 GPU 耗时，从而驱动 GPU DVFS。
  2. **GpuHeadroom API**：Android 16 引入了 GPU 余量查询。
- **建议补充方向**：说明 ADPF 已演进为 CPU/GPU 协同调优框架，不应只提 CPU。

- **[P1][原理链完整性][SCMI + CPPC 现代架构]**
- **原文位置**：`## OPP Table：频率与电压的档位表`
- **缺失内容**：现代 SoC（如 ARMv8.4+）使用 SCMI (System Control and Management Interface) 和 CPPC (Collaborative Processor Performance Control)。
- **运行原理说明**：OS 不再直接请求特定频率（MHz），而是请求一个抽象的“性能等级（Performance Level）”。具体的电压/频率映射逻辑被剥离到固件（SCP处理器）中。
- **为什么这是重要缺失**：这解释了为什么“硬件切换延迟”在减少，因为固件可以使用 Fastchannels（内存映射）实现极低延迟的切换。
- **建议补充方向**：增加“抽象性能等级”的概念，说明 OPP Table 正在从 OS 层级下沉到固件层级。

## 六、P2 问题（建议改进）
- **[P2][知识盲区][调频延迟的构成]**
- **原文位置**：`### DVFS 的升频延迟`
- **问题描述**：原文提到升频可能需要 200ms。
- **建议**：应明确拆解这 200ms 的构成。硬件物理切换（SCMI/PLL）只需微秒级，主要的延迟来自 PELT 的指数衰减惯性（~32ms-64ms 达到稳定）以及系统的采样间隔。这样读者在分析 Trace 时就不会误以为是硬件“响应慢”。
