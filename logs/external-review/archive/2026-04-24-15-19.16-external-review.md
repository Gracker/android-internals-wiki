## 五、P1 问题（重要缺失）
- [P1][原理链完整性][调用形态与结果生命周期]
  - 原文问题：“结果文件的生命周期”图中只写了“记录 metadata 和文件引用”，未说明实际的文件物理限制。
  - 缺失内容：大纲明确要求“说明文件生成、可访问时间、复制……和 error code 的调用流程”。
  - 建议补充方向：必须补充说明 `ProfilingResult` 返回的往往是系统缓存目录下的一个临时路径或 FD。应用只有极短的**可访问时间**（通常在 callback 返回前或进程存活时），因此必须在回调中立即将数据**复制**到 App 自己的沙盒中才能丢给后台线程去慢慢压缩和上传。同时，还要补充 `ERROR_FAILED_RATE_LIMIT_EXCEEDED` 等系统限流错误码的捕获策略。

- [P1][数据/案例支撑][工具关系]
  - 原文问题：只对比了 Perfetto 和抽象的 APM SDK。
  - 缺失内容：大纲要求“和 Android Studio Profiler、JankStats、FrameMetrics 的使用顺序做说明”。
  - 建议补充方向：必须明确排查漏斗顺序。例如：线上通过 `JankStats` 发现高频慢帧 -> 通过 `FrameMetrics` 确认慢在 `DRAW_DURATION` -> 通过下发远端指令触发 `ProfilingManager` 抓取单次用户的 `System trace` -> 开发者将 trace 拉至本地用 `Android Studio Profiler / Perfetto UI` 找到具体耗时的 Draw 方法。

- [P1][版本差异覆盖][类型]
  - 原文问题：类型表格中未指明具体的输出文件格式。
  - 缺失内容：大纲要求“列出支持的 profiling 类型、输出文件……”。
  - 建议补充方向：在表格中补充说明：`JAVA_HEAP_DUMP` 输出的是 `.hprof` 格式，而 `SYSTEM_TRACE` 等通常输出的是 `.perfetto-trace` 格式。这是服务端决定用 Shark 还是 TraceProcessor 去解析文件的前提。
