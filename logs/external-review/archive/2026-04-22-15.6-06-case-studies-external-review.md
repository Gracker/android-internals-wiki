## 五、P1 问题（重要缺失/偏差）
- [P1][源码准确性/原理链完整性][案例四：RenderThread sync 阻塞主线程]
  - **原文问题**：“动态表情的每一帧都在变化，导致 Bitmap 频繁重新上传 GPU... RenderThread 承担了大量的绘制和 GPU 栅格化工作。RenderThread 处理变慢后，主线程在 syncFrameState() 阶段等待时间从正常的 <1ms 增加到 8-15ms”
  - **源码 / 一手资料锚点**：AOSP `AnimatedVectorDrawable.java`，`RenderNode.cpp`。
  - **运行原理说明**：其实 `AnimatedVectorDrawable` (AVD) 自 API 25 起就已经支持在 **RenderThread** 异步执行。这意味着正常的 AVD 动画*不会*唤醒 UI 线程，UI 线程的 `doFrame` 根本不需要执行。
  - **为什么错 / 偏差**：如果遇到了 UI 线程的 `syncFrameState` 被阻塞，往往是因为 AVD 的某些属性（例如 Path morphing 或者依赖不支持的 Canvas 操作）导致它**无法在 RenderThread 运行，退化（fallback）到了 UI 线程**。一旦退化到 UI 线程，UI 线程就必须每帧去计算动画、调用 `invalidate`，然后每帧重构 DisplayList 并进行 `syncAndDrawFrame`。此时如果包含大量复杂 Path，RenderThread 处理 DisplayList 会非常慢，从而阻塞 UI 线程的下一次 sync。原文将其混为一谈，没有点出“退化（fallback）到 UI 线程”这一根本前提。
  - **建议修正方向**：明确解释 AVD 默认在 RT 运行，但特定复杂动画会 fallback 到 UI 线程。UI 线程每帧重构 DisplayList 才是导致大量耗时和 sync 阻塞的直接原因。

## 六、P2 问题（建议改进）
- [P2][源码准确性][案例三：内存压力下 GC 频繁暂停主线程]
  - **原文问题**：修复方案中给出代码 `(Runtime.getRuntime().maxMemory() / 1024 / 8).toInt()`。
  - **问题描述**：`Runtime.getRuntime().maxMemory()` 在配置了 `android:largeHeap="true"` 的应用中会返回非常大的值（如 512MB 甚至更高），按照 1/8 划分可能会导致缓存占用过大，在低内存设备上反而加速 LMK 杀进程。
  - **建议**：建议补充说明优先使用 `ActivityManager.getMemoryClass()` 来获取标准内存指标，或者在代码示例中加入对 `largeHeap` 风险的提示。
