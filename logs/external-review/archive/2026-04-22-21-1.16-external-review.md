## 四、P0 问题（事实错误）
- **[P0][源码准确性][Android 17 音频性能变更 -> AudioTrack 新增精确 Flush 控制]**
- **原文问题**：称 `flushWrittenFramesFromPosition` “只适用于 offloaded AudioTrack”。
- **核验结论**：**完全相反**。根据 Android 15/17 API 文档，该方法明确**不支持** Offload 模式。
- **原因**：Offload 模式下音频在 DSP 中缓冲，系统无法控制硬件缓冲区内的精确帧位置。该 API 是为 PCM 轨道设计的。
- **建议修正方向**：明确指出其适用于 PCM 轨道，且在 Offload/Direct 模式下不可用；补充开发者需使用 `getFlushWrittenFramesFromPositionSupport` 进行探测。

- **[P0][源码准确性][Android 17 音频性能变更 -> 编解码器来源查询]**
- **原文问题**：称 `getCodecProvenance()` 返回的是“创建 AudioTrack 时配置的 codec media type string”。
- **核验结论**：不准确。该方法返回的是编解码器的**溯源/出处（Provenance）**，如 `c2.android.aac.decoder`（系统软解）或特定的硬件解码器名称。
- **建议修正方向**：修正为“返回编解码器的原始实现名称或出处”，用于区分软硬解和分析性能。

## 五、P1 问题（重要缺失）
- **[P1][原理链完整性][FAST Mixer -> 进入 FAST Mixer 的条件]**
- **缺失内容**：未提及 FAST Mixer 的**槽位限制（Slots Limit）**。
- **原理说明**：AOSP `AudioFlinger` 中 FAST Mixer 固定只有 8 个槽位（通常为 7 个 Client + 1 个内部线程使用的 PatchTrack）。如果设备上已有多个低延迟流（如按键音、通知音、游戏），新流即使满足采样率等条件也会因槽位满而降级。
- **源码锚点**：`frameworks/av/services/audioflinger/Threads.cpp` 中的 `mFastTrackAvailMask`。

- **[P1][原理链完整性][AAudio 与 MMAP -> MMAP 模式]**
- **缺失内容**：未提及 MMAP EXCLUSIVE 模式下的**时钟同步模型（Timing Model）**。
- **原理说明**：在独占模式下，虽然 `audioserver` 不搬运数据，但它必须通过原子消息队列定期向 App 传递硬件时间戳（Timestamp），否则 App 无法预测硬件读写位置，会导致严重的 XRun（Underrun/Overrun）。
- **源码锚点**：`frameworks/av/media/libaaudio/service/AAudioServiceEndpoint.cpp`。
