## 五、P1 问题（重要缺失/误导）

### 1. [P1][源码准确性][schedutil 工作流程]
- **原文位置**：`schedutil 的工作流程` -> 源码片段引用。
- **原文问题**：引用的 `effective_cpu_util` 签名与声称验证的 Linux 6.6 不符。
- **源码锚点**：`kernel/sched/fair.c` (Upstream Linux 6.6.89+ 或 Android 15 GKI)。
- **关键代码逻辑**：Linux 6.6 后期为了支持更精细的 uclamp 控制，将 `effective_cpu_util` 的 `type` 和 `p` 参数移除，替换为 `unsigned long *min, unsigned long *max`。
- **核验结论**：原文使用的是 Linux 6.1 (Android 14) 的旧签名。
- **建议修正方向**：说明内核版本演进导致的签名变化，或者至少将代码更新为 6.6 最新的形态，以符合前文声明。

### 2. [P1][原理链完整性][RTG (Related Thread Group) 驱动的集群偏好]
- **原文位置**：`核心迁移的触发条件` -> `3. RTG（Related Thread Group）`。
- **原文问题**：将 RTG 描述为“Android 内核中一个重要的客制化机制”，容易让读者误以为是 AOSP 通用机制。
- **核验结论**：RTG 是高通 (Qualcomm) WALT 调度器的私有实现。在 Pixel (Tensor) 或其他使用 PELT 的设备上，类似功能通过 `uclamp` 或 `schedtune` 组实现。
- **建议修正方向**：明确标注 RTG 为“以高通平台为代表的厂商定制机制”，并简述其在 GKI 时代通过 Vendor Hook 存在的形式。

## 六、P2 问题（建议改进）

### 1. [P2][原理链完整性][PELT 机制描述]
- **原文问题**：将 32ms 描述为“1024us × 32”，逻辑不严谨。
- **证据依据**：PELT 的负载计算公式是几何级数。32ms 是负荷衰减到一半的周期（Half-life），而 1024us 是其步进周期。
- **建议**：修正为“半衰期约为 32ms，负载每 1024us 更新一次”。

### 2. [P2][知识盲区][schedutil 调频裕量]
- **原文问题**：公式 `target_freq = max_freq * util / capacity` 过于理想化。
- **证据依据**：内核实际实现中，`schedutil` 默认会乘以 1.25 的 `SCHED_CAPACITY_SCALE` 裕量，以应对瞬时负载波动。
- **建议**：在公式中体现“性能裕量（Margin）”的概念。
