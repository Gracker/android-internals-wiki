## 五、P1 问题（重要缺失）

### 1. [P1][原理链完整性][Case 4] RenderThread 同步机制遗漏“提前唤醒”逻辑
- **原文问题**：Case 4 描述 RenderThread sync 阻塞主线程时，仅提到主线程等待 RenderThread。
- **源码 / 一手资料锚点**：`frameworks/base/libs/hwui/renderthread/DrawFrameTask.cpp` 中的 `DrawFrameTask::run()` 和 `unblockUiThread()`。
- **关键代码逻辑**：`DrawFrameTask` 在执行 `syncFrameState`（即 `prepareTree`）后，如果不需要进行耗时的位图上传，会**立即调用 `unblockUiThread()`**。这意味着 UI 线程并不一定要等到渲染完成。
- **运行原理说明**：只有当 `syncFrameState` 本身耗时（如大纹理上传）或 RenderThread 积压导致 `DrawFrameTask` 迟迟无法开始执行时，主线程才会感知到明显的 sync 阻塞。原文未区分“同步等待”和“渲染等待”，容易误导读者。
- **建议修正方向**：明确说明 `syncFrameState` 的“提前唤醒”机制，区分哪些操作（如位图上传、RenderNode 树过大）会导致 UI 线程被迫延长阻塞。

### 2. [P1][版本差异覆盖][Case 5] Android 14 内存回调变更背景缺失
- **原文问题**：提到 Android 14 不再收到部分回调，但未说明原因和后果。
- **一手资料锚点**：Android 14 Release Notes & "Cached App Freezer" 机制。
- **缺失内容**：必须提及 **“缓存应用冻结”** 机制。在 Android 14+，应用进入后台即被冻结，无法响应 `onTrimMemory`。
- **运行原理说明**：系统倾向于直接杀死缓存进程（LRU 策略）而非通知应用。此外，`onLowMemory()` 同样在 API 34+ 失效。
- **为什么这是重要缺失**：如果不解释原因，开发者会认为这是一个 Bug 或简单的 API 调整，而忽略了整体内存治理策略应向“降低常驻内存”转型的趋势。
- **建议补充方向**：补充缓存应用冻结的背景，强调 `TRIM_MEMORY_UI_HIDDEN` 是目前唯一的可靠“告别信”。

### 3. [P1][知识盲区][Case 5] 内核级优化 MGLRU 缺失
- **原文问题**：低内存场景修复建议仅停留在应用层和传统的 lmkd 调整。
- **一手资料锚点**：Android 13+ 内核特性 `CONFIG_LRU_GEN` (Multi-Generational LRU)。
- **缺失内容**：MGLRU 对 `pgdat->lru_lock` 竞争的解决效果。
- **为什么这是重要缺失**：在 Android 13 及更高版本的设备上，`kswapd` 导致的锁竞争已通过 MGLRU 得到极大缓解（CPU 占用降低 ~40%）。如果读者在高性能设备上仍然按旧思路分析，会南辕北辙。
- **建议补充方向**：在案例五的“修复方案（系统开发者视角）”中，将 MGLRU 作为首选推荐方案。

## 六、P2 问题（建议改进）

### 1. [P2][原理链完整性][Case 1] 嵌套布局导致 measure 多次的数学解释
- **建议**：原文提到层级嵌套导致 3-4 次 measure。建议补充说明：`RelativeLayout` 总是 2 次，`LinearLayout` 带 `weight` 总是 2 次，它们嵌套时是**指数级增长（乘法关系）**而非累加关系。这能更直观地解释为什么 6 层嵌套会产生几十次内部调用。

### 2. [P2][知识盲区][Case 2] Binder 调用的“冷启动”与“热调用”差异
- **建议**：在 `onBindViewHolder` 的 Binder 调用中，补充提到：第一次调用系统服务（如 `PackageManager`）往往伴随一次完整的 Binder 事务和系统端权限校验，耗时远高于后续缓存调用。
