## 五、P1 问题（重要缺失/偏差）

- [P1][知识盲区][自定义 trace 的命名规则]
- **原文问题**：声称 Trace 名称“最大长度 32 个字符”。
- **源码 / 一手资料锚点**：[Firebase Custom Traces Docs](https://firebase.google.com/docs/perf-mon/custom-code-traces?platform=android#add-custom-attributes)
- **关键代码逻辑**：SDK 内部常量 `MAX_TRACE_NAME_LENGTH` 在近几个版本中已上调。
- **运行原理说明**：Trace 和 Metric 名称上限为 **100** 字符。真正的 32 字符限制存在于 **Attribute Key**（部分文档标记为 32 或 40）。
- **核验结论**：原文将 Attribute 的限制套用到了 Trace 名称上，严重限制了用户命名的灵活性。
- **为什么是重要缺失**：误导用户进行过度缩写，降低了看板的可读性。
- **建议修正方向**：区分 Trace/Metric 名（100 字符）和 Attribute 名（32/40 字符）的限制。

- [P1][版本差异覆盖][自动采集能力与版本边界]
- **原文问题**：声称屏幕渲染“只有 screen 级聚合，没有页面上下文”。
- **源码 / 一手资料锚点**：Firebase Android SDK v20.1.0+ release notes.
- **关键代码逻辑**：`FragmentManager.FragmentLifecycleCallbacks` 被用于自动采集 Fragment 级的渲染数据。
- **缺失内容**：Firebase 现在已支持 **Fragment 的自动屏幕追踪**。
- **运行原理说明**：不再局限于 Activity，可以自动识别 `HomeFragment` 等页面，解决了单 Activity 架构下的监控痛点。
- **为什么这是重要缺失**：这是现代 Android 开发（Navigation Component）的基础，缺失此点会让读者认为 FPM 对单 Activity 架构无能为力。
- **建议补充方向**：在“自动采集能力”表格中明确补充对 Fragment 的支持及其 SDK 版本要求（20.1.0+）。

- [P1][原理链完整性][自动采集能力与版本边界 - App Start]
- **原文问题**：对应用启动的起点描述较模糊。
- **源码 / 一手资料锚点**：`Process.getStartUptimeMillis()` (API 24+)。
- **关键代码逻辑**：Firebase 优先使用系统 API 获取进程 fork 时间，而非仅依靠 ContentProvider。
- **运行原理说明**：区分了“绝对冷启动”（系统级起点）和“SDK 起点”。
- **核验结论**：原文仅提到“跟随当前 SDK 接入”，缺乏对 API 24+ 关键实现（`Process.getStartUptimeMillis()`）的提及。
- **建议补充方向**：说明 API 24+ 会使用系统级进程启动时间，以及 60 秒过滤规则（防止后台启动干扰）。

## 六、P2 问题（建议改进）

- [P2][知识盲区][网络请求聚合和 URL pattern]
- **原文问题**：提及了 Cronet，但未说明其采集特殊性。
- **问题描述**：FPM 的 Gradle 插件无法自动对 Cronet 这种 native 网络栈进行字节码插桩。
- **建议**：明确指出使用 Cronet 时需要手动使用 `FirebasePerfUrlConnection` 包装或添加拦截器，否则会自动“漏掉”。

- [P2][数据/案例支撑][数据模型：trace、metric、attribute]
- **原文问题**：描述 Metric 时使用“低基数”。
- **问题描述**：Metric 是数值（Long），属性（Attribute）才是用来做分类聚合的（涉及基数问题）。
- **建议**：修改表述，强调 Metric 用于计算（累加、平均），Attribute 用于过滤和分组（高基数 Attribute 会导致控制台聚合失败）。
