## 三、回炉问题摘要（P0 / P1）

### 1. [P0][源码准确性][第 107 行] Choreographer.FrameCallback 线程行为描述完全错误

- **原文问题**：「在 API 23 及以下版本中，`doFrame()` 回调在主线程执行；API 24 及以上版本会在独立线程执行。所以如果你的回调里有耗时操作（比如写文件），在旧版本上会直接阻塞主线程，反而制造额外的掉帧。」
- **核验结论**：**完全错误。** `Choreographer.FrameCallback.doFrame()` **始终在它所属的 Choreographer 实例的 Looper 线程上执行**。通过 `Choreographer.getInstance()` 获取的是主线程的 Choreographer，所以 `doFrame()` **在所有 API 版本上都在主线程执行**。API 24 并没有改变这个行为。
- **可能的混淆来源**：作者很可能将 `Choreographer.FrameCallback`（始终在主线程）与 `Window.OnFrameMetricsAvailableListener`（回调在开发者提供的 Handler 线程执行，通常是非主线程）混淆了。第 152 行对 FrameMetrics 回调的描述（"这个回调在独立线程执行（API 24+）"）才是正确的——但这描述的是 FrameMetrics，不是 FrameCallback。
- **源码锚点**：
  - AOSP: `frameworks/base/core/java/android/view/Choreographer.java`
  - `Choreographer.getInstance()` 返回与当前 Looper 绑定的实例
  - `postFrameCallback()` 的回调在 Choreographer 所在的 Looper 线程执行
  - 官方文档: `developer.android.com/reference/android/view/Choreographer.FrameCallback` — 无任何关于 API 24 线程变化的说明
- **为什么这是 P0**：如果读者相信 API 24+ 的 `doFrame()` 在独立线程执行，他们可能会在 `doFrame()` 中执行耗时操作（如磁盘 I/O、网络请求），认为"不会阻塞主线程"——实际上会直接阻塞主线程并导致掉帧。这个错误信息会导致读者在线上监控 SDK 中引入性能 bug。
- **建议修正方向**：删除关于 API 23/24 线程差异的描述。改为「`doFrame()` 回调始终在主线程执行（因为 `Choreographer.getInstance()` 获取的是主线程的 Choreographer 实例）。所以回调中不要有任何耗时操作，否则会直接阻塞主线程、制造额外掉帧。帧数据采集应尽量轻量，将上报逻辑放到后台线程异步执行。」

### 2. [P1][源码准确性][第 169 行] JankStats 默认掉帧判定策略描述不够准确

- **原文问题**：「JankStats 默认将超过刷新率 2 倍的帧判定为"jank"」
- **核验结论**：JankStats 的默认判定策略并非简单的"2 倍刷新率"。在 API 31+ 上，JankStats 使用 `FrameMetrics.DEADLINE` 与 `TOTAL_DURATION` 的比较来判定 jank（即 totalDuration > deadline 就是 jank）。在低版本上，才使用基于刷新率的启发式判定。"超过刷新率 2 倍"这个描述过于简化。
- **一手资料锚点**：
  - JankStats 源码: `androidx.metrics:metrics-performance` → `JankStatsApi31Impl.java` / `JankStatsApi26Impl.java`
  - 官方文档: `developer.android.com/jetpack/androidx/releases/metrics`
- **建议修正方向**：改为「JankStats 在 API 31+ 上直接使用 FrameMetrics.DEADLINE 判定掉帧（totalDuration > deadline），在低版本上使用基于刷新率的启发式算法」

## 五、一般建议摘要（P2）

### 1. [P2][原理链完整性] FrameCallback 代码示例中硬编码 16ms
- **位置**：第 89 行
- **问题描述**：代码中 `if (intervalMs > 16)` 硬编码了 16ms 作为掉帧阈值。在 120Hz 设备上，帧预算是 8.33ms，这个判定会漏掉大量 8.33-16ms 范围的掉帧。
- **建议**：在代码注释中补充说明这是 60Hz 设备的阈值，120Hz 设备应使用 8ms。或者参考后文 DEADLINE 指标动态获取帧预算。

### 2. [P2][原理链完整性] FrameMetrics 各指标的单位未明确标注
- **位置**：第 115-127 行的表格
- **问题描述**：FrameMetrics 各指标的单位是纳秒（nanoseconds），但表格中未标注。第 88 行的 FrameCallback 代码中做了 `/ 1_000_000` 的转换（纳秒→毫秒），但表格中没有提示读者这些值是纳秒级的。
- **建议**：在表格标题或脚注中加注「以下指标单位均为纳秒（ns）」

### 3. [P2][交叉引用一致性] JankStats 版本状态未更新
- **位置**：第 156 行
- **问题描述**：文中说「2022 年 Google 发布了 `JankStats` 库」，但未提及 JankStats 已于 2025 年 10 月发布 1.0.0 稳定版。对于线上监控来说，使用稳定版 vs alpha 版有重大区别。
- **建议**：补充「JankStats 1.0.0 已于 2025 年 10 月发布稳定版」

## 六、可复用知识资产

### 1. 一手资料索引
- **AOSP / cs.android.com**：
  - `frameworks/base/core/java/android/view/Choreographer.java` — FrameCallback 线程模型
  - `frameworks/base/core/java/android/view/FrameMetrics.java` — FrameMetrics 指标定义（含 DEADLINE）
- **developer.android.com**：
  - `developer.android.com/reference/android/view/Choreographer.FrameCallback`
  - `developer.android.com/reference/android/view/FrameMetrics`
  - `developer.android.com/jetpack/androidx/releases/metrics` — JankStats
  - `developer.android.com/reference/android/app/ApplicationExitInfo` — API 30+

### 2. 源码锚点
- **文件路径**：`frameworks/base/core/java/android/view/Choreographer.java`
- **关键方法**：`postFrameCallback()`, `doFrame()`
- **关键行为**：回调始终在 Choreographer 所在 Looper 线程执行，通过 `getInstance()` 获取的是主线程实例
- **为什么重要**：文中错误地声称 API 24+ 在独立线程执行

### 3. 版本差异摘要
- **Android 7.0 (API 24)**：FrameMetrics API 引入
- **Android 11 (API 30)**：ApplicationExitInfo API 引入
- **Android 12 (API 31)**：FrameMetrics.DEADLINE 指标引入
- **Android 15 (API 35)**：ProfilingManager 引入（线上 profiling 能力）
- **2025-10**：JankStats 1.0.0 stable 发布

### 4. Trace / Perfetto 观察点
- **观察点 1**：FrameMetrics 的 UNKNOWN_DELAY 过大说明主线程消息队列有延迟（可能有长消息阻塞）
- **观察点 2**：SYNC 耗时过长说明 DisplayList 同步到 RenderThread 的过程有问题（可能是过大的 Bitmap 上传）
- **观察点 3**：COMMAND_ISSUE 耗时过长说明 GPU 负载重或存在 GPU 频率限制

### 5. 可直接复用的技术结论
- `Choreographer.FrameCallback.doFrame()` 在所有 API 版本上都在主线程执行
- `Window.OnFrameMetricsAvailableListener` 回调在开发者提供的 Handler 线程执行（通常非主线程）
- JankStats 在 API 31+ 使用 DEADLINE 判定掉帧，低版本使用启发式算法
- ApplicationExitInfo 的 `getTraceInputStream()` 可以获取 ANR 时的线程 dump
- JankStats 1.0.0 已于 2025-10 发布稳定版
