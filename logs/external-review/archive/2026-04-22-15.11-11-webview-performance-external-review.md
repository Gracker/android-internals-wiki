## 五、P1 问题（重要缺失）
- **[P1][知识盲区][未调用 destroy()]**
  - 原文问题：提到“WebView 必须在不需要时调用 `destroy()` 释放 native 资源。而且 destroy() 之前要先从 View 树中移除。” 但未指出 `destroy()` 的线程限制。
  - 源码 / 一手资料锚点：`frameworks/base/core/java/android/webkit/WebView.java` 中的 `checkThread()` 机制。
  - 缺失内容：`WebView` 的绝大多数生命周期方法，包括 `destroy()`，都必须且只能在 UI 线程（MainThread）调用。如果开发者在后台线程异步清理，会直接抛出 `RuntimeException` 导致 Crash。
  - 运行原理说明：WebView 对象内部维持了与底层 Chromium browser 线程的强关联绑定，Android Framework 层面通过 `checkThread()` 强制约束所有对 View 树和主要资源的操作必须同步在 MainThread 执行。
  - 为什么这是重要缺失：这是 WebView 开发中最容易踩坑导致直接崩溃的点，作为实战优化指南必须提醒。
  - 建议补充方向：在代码示例中强调或添加主线程调用的检查/注解。

- **[P1][知识盲区][内存泄漏的常见原因]**
  - 原文问题：虽然列举了 Context 泄漏、未销毁、JS 回调和 Chromium bug 四类，但漏掉了 `CookieManager`、`CookieSyncManager` 和 `WebStorage` 导致的全局单例泄漏。
  - 源码 / 一手资料锚点：`android.webkit.CookieManager`。
  - 缺失内容：如果应用在使用 CookieManager 时注册了回调，或者因为底层网络栈缓存的原因，全局的 Cookie / Cache 模块可能会保持对相关回调或请求上下文的引用。
  - 为什么这是重要缺失：很多时候 App 处理了 `destroy()`，但由于使用了全局 WebView 服务缓存未能清理而依然泄漏。
  - 建议补充方向：补充 `CookieManager.getInstance().removeAllCookies(null)` 及相关的全局状态清理策略，作为防止 WebView 泄漏的兜底方案之一。

## 六、P2 问题（建议改进）
- [P2][原理链完整性][JS Bridge 与主线程阻塞]
- 原文问题：解释了 evaluateJavascript 同步阻塞引发 ANR。
- 证据或观察依据：在某些复杂 JS Bridge 交互中，大量短时间内的高频 JS-Java 调用也会瞬间填满 JS 引擎的消息队列，导致随后的 IPC 响应巨慢。
- 建议：补充一条建议：JS Bridge 不适合高频度（如 `onScroll` 中的每一帧）传递大量数据，大量数据应采用序列化或 ArrayBuffer，避免高频 IPC 卡顿。
