## 五、P1 问题（重要缺失）
- [P1][原理链完整性][定位]
  - 原文问题：仅说明了 APM 不替代 Perfetto 等，但缺失了“从发现到定位的例子”。
  - 缺失内容：大纲明确要求“补一个线上慢帧或 OOM 样本从发现到定位的例子”。
  - 建议补充方向：补充一个完整的推导路径：例如某版本 OOM 率飙升（指标异常） -> 通过 APM 后台捞取泄漏类 Top 1 排行榜并下载 Hprof 摘要（样本） -> 结合 trace 或本地抓取完整 Hprof（现场复核） -> 修复的完整故事。

- [P1][原理链完整性][数据模型]
  - 原文问题：正文标题为“指标、样本、trace 是三种不同证据”，遗漏了“上下文”，且没有写误用场景。
  - 缺失内容：大纲要求“展开指标、样本、trace、上下文四类证据；每类至少写 3 个字段例子和一个误用场景”。
  - 建议补充方向：补齐“上下文”这一层。列出每类的误用场景，例如“把 trace 当指标去算平均耗时导致性能预警失真”。

- [P1][知识盲区][工具边界]
  - 原文问题：没有给出“什么时候只用 APM 不够”的具体判断表。
  - 缺失内容：大纲要求包括 CPU 争抢、Binder 卡住、I/O 等待、GPU 阻塞、Java / native 内存泄漏的具体边界判定。
  - 建议补充方向：新增一张对照表，说明当怀疑 CPU 争抢时 APM 只能看到主线程耗时拉长，必须借助 system trace 看调度；怀疑 Binder 卡住时 APM 只能看到 blocked state，必须抓互斥锁或对端进程状态。

- [P1][知识盲区][线上策略]
  - 原文问题：完全遗漏了“线上策略”的说明。
  - 缺失内容：灰度开关、采样率、磁盘缓存、上传失败重试、端侧降级和服务端聚合对结论可信度的影响。
  - 建议补充方向：补充专门段落或表格。解释为何采样率设为 1% 时，低频长尾问题会被淹没；为何不带端侧降级可能导致 APM 自身引起 OOM。

- [P1][数据/案例支撑][数据合同]
  - 原文问题：虽然提及了数据合同的字段，但没有给出“保留周期、trace id / session id 关系”的深入解释，也没有“最小字段模板”。
  - 缺失内容：缺乏结构化的 JSON/代码块模板展示。
  - 建议补充方向：用 JSON 提供一个最小字段上报结构示例，体现 `session_id` 如何串联各个 event。
