## 五、P1 问题（重要缺失）
- [P1][知识盲区][锚点 2：Monitor Lock 的性能特征]
- **原文问题**：仅提到 `kLongWaitMs = 100ms`。
- **源码锚点**：`art/runtime/monitor.cc`
- **关键代码逻辑**：`static constexpr uint64_t kLongWaitMs = 100 * kDebugThresholdFudgeFactor;` 其中 `kDebugThresholdFudgeFactor` 在 Debug 版为 10。
- **运行原理说明**：在 Debug 构建中，阈值会被放大到 **1000ms**。
- **版本差异**：Android 14+ 引入。
- **核验结论**：原文结论在 Debug 环境下会误导开发者认为“没有长锁竞争”，实则是阈值变高了。
- **建议修正方向**：明确区分 Release (100ms) 和 Debug (1000ms) 的日志触发阈值。

- [P1][知识盲区][锚点 8：版本演进中的锁优化]
- **原文问题**：未提及 DeliQueue 的破坏性变更。
- **源码 / 一手资料锚点**：Android Developers Blog (2026-03) + `MessageQueue.java` (API 37)
- **运行原理说明**：DeliQueue 弃用了 `mMessages` 链表结构，改为无锁栈+最小堆。
- **核验结论**：反射访问 `MessageQueue.mMessages` 将始终返回 `null`。这会导致旧版 Espresso ( < 3.7.0 ) 和自定义空闲检测逻辑失效。
- **建议修正方向**：在“读者诊断清单”或“版本演进”中强制提醒：Android 17+ 严禁反射 `MessageQueue` 私有字段。

- [P1][版本差异覆盖][锚点 3：Futex 与 Linux 同步原语]
- **原文问题**：未提及 PI-Mutex 在 32 位 Android 系统上的特殊限制。
- **源码锚点**：`bionic/libc/bionic/pthread_mutex.cpp`
- **运行原理说明**：32 位系统 `pthread_mutex_t` 空间不足，需通过全局 ID 映射表管理 PI 状态。
- **核验结论**：该映射表上限为 **65536** 个。
- **为什么这是重要缺失**：虽然普通 App 很难达到此上限，但在高性能、大规模并发的系统级服务开发中，这是一个硬瓶颈。
- **建议补充方向**：补充 32 位系统的 ID 映射限制（65536）。
