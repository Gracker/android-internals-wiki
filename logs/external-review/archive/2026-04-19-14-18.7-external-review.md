## 四、P0 问题（事实错误）
- [P0][源码准确性][第二阶段：App RenderThread & 常见性能问题2 & Trace视角]
- **原文问题**：“`updateTexImage` 耗时增大，瓶颈在 `updateTexImage`。原因：Producer 的 acquireFence 未 signal（GPU 还在渲染上一帧），`updateTexImage` 等待 fence。”
- **源码 / 一手资料锚点**：`frameworks/native/libs/gui/GLConsumer.cpp`（对应 `doGLFenceWaitLocked` 及 `updateTexImage` 的 EGL 交互）。
- **关键代码逻辑**：`SurfaceTexture` (C++ 层为 `GLConsumer`) 在 `updateTexImage` 时，调用 `BufferQueue::acquireBuffer` 获取 GraphicBuffer 和对应的 `acquireFence`。在将 Buffer 绑定到 EGLImage 后，它并不是让 RenderThread CPU 睡眠死等这个 fence 释放。而是通过 `doGLFenceWaitLocked()`，在支持 `EGL_KHR_wait_sync` 的设备上，将该 fence 转化为 EGLSyncKHR 对象，并调用 `glWaitSyncKHR`。
- **运行原理说明**：`glWaitSyncKHR` 是一个 **Server-side wait（服务端等待）**指令。它会立即返回（CPU 不阻塞），仅仅是向 GPU 对应的 Command Buffer 插入一条“同步等待”指令，要求 GPU 在执行后续采样该 OES 纹理的操作前，必须等待此 fence signal。
- **核验结论**：因此，RenderThread（CPU）端记录的 `updateTexImage` 耗时通常极短（微秒级，仅为 EGL/GL API 调用的开销），真正的卡点和等待发生在 GPU Pipeline 执行阶段。
- **为什么错**：原文的表述会导致读者在 Perfetto/Systrace 的 CPU Track 中死盯着 `updateTexImage` 找大长条（实际上极少出现），而忽略了去 GPU Track 观察实际渲染延迟。这是经典的 Trace 诊断误区。
- **建议修正方向**：重写该部分。明确说明 `updateTexImage` 通过 `glWaitSyncKHR` 实现 Server-side wait。CPU 不阻塞，而是 GPU 阻塞。Trace 视角中应引导读者观察 GPU 等待而非 CPU 的 `updateTexImage` 耗时。

## 五、P1 问题（重要缺失）
- [P1][源码准确性][Trace 视角/与 SurfaceView 的 Trace 差异]
- **原文问题**：在对比表中提到 Composition Type，“SurfaceView 可能是 DEVICE(Overlay) | TextureView 总是 CLIENT”。
- **源码 / 一手资料锚点**：`frameworks/native/services/surfaceflinger/CompositionEngine`
- **关键代码逻辑**：SurfaceFlinger 进行合成时，针对的是 WindowManager 提供过来的各个 Layer。
- **缺失内容与运行原理**：TextureView 是被 App `RenderThread` 绘制到了**App 主窗口**的 GraphicBuffer 中。提交给 SurfaceFlinger 的是“App 主窗口”这个 Layer。由于 TextureView 不产生独立的 Layer，SurfaceFlinger 看到的只是 App 的主界面。这个主界面 Layer 完全可以被 HWC 设为 DEVICE 模式（硬件 Overlay 合成）。
- **为什么这是重要缺失**：虽然 TextureView 内部是由 App 的 GPU (RenderThread) 完成了采样合成（带有 CLIENT 渲染的性质），但反映在 `dumpsys SurfaceFlinger` 或 SysTrace 中的 Layer Composition Type，主窗口仍然可以是 DEVICE。原文将其描述为“总是 CLIENT”是对 SF Layer 架构的严重误导。
- **建议补充方向**：澄清 SF Composition Type 针对的是 Layer。TextureView 内部合成属于 App 进程内的 GPU 工作；而提交到 SF 的 App 主窗口 Layer，依然有机会走 DEVICE 合成。

- [P1][知识盲区][TextureView 特性与底层依赖]
- **原文问题**：整篇未提及 TextureView 对“硬件加速”的强制依赖。
- **源码 / 一手资料锚点**：`frameworks/base/core/java/android/view/TextureView.java` (`getHardwareLayer()` 相关逻辑和 `draw(Canvas)` 的 fallback 行为)。
- **知识盲区**：如果 App 或单独的 Activity / Window 被关闭了硬件加速（软件渲染模式，即 CPU 绘制），`TextureView.draw()` 将无法通过 RenderThread 生成 `HardwareLayer` 和调用 `updateTexImage`，会导致屏幕对应区域显示黑块或无法更新。
- **为什么这是重要缺失**：在实际业务兼容性问题排查中，“TextureView 黑屏”的极高频原因就是上层代码或者系统兼容模式关掉了硬件加速。与 SurfaceView 支持软件渲染的 fallback 形成鲜明对比，这是重要的实战知识。
- **建议研究方向**：在与 SurfaceView 的对比或问题排查段落，增加一条“硬件加速强依赖”的说明。

- **来源类型**：AOSP `frameworks/native/libs/gui/GLConsumer.cpp`
- **关键类 / 方法**：`GLConsumer::updateTexImage()` -> `doGLFenceWaitLocked()` -> `glWaitSyncKHR()`
- **可直接复用的技术结论**：SurfaceTexture 的纹理更新（`updateTexImage`）在 CPU 层面通常是极快的非阻塞操作。它将 Producer 带来的 `acquireFence` 通过 `glWaitSyncKHR` 转化为 Server-side wait，将真正的阻塞转移到了 GPU 侧。因此，排查 TextureView 卡顿时，CPU 上的 `updateTexImage` 耗时变长往往是 EGL 调用本身的系统问题，而真正的生产者-消费者速度不匹配导致的问题，必须去 GPU Track（或者对应的 Fence Track）排查。
