## 五、P1 问题（重要缺失）
- [P1][知识盲区][App 侧可以用的 ARR API]
- **原文问题**：未提及 `View` 层的 `REQUESTED_FRAME_RATE_CATEGORY_DEFAULT` 常量。
- **源码 / 一手资料锚点**：AOSP `frameworks/base/core/java/android/view/View.java`
- **关键代码逻辑**：`REQUESTED_FRAME_RATE_CATEGORY_DEFAULT` (值为 0) 用于清除之前的显式请求，让系统回归默认自动决策逻辑。
- **缺失内容**：在列举 `View.java` 可用类别时，只列出了 `NO_PREFERENCE`, `LOW`, `NORMAL`, `HIGH`。
- **为什么这是重要缺失**：开发者需要知道如何撤销之前的帧率请求，否则可能导致页面在不必要时持续处于高刷或低刷状态。
- **建议补充方向**：在 View API 章节补充该常量及其语义（重置投票）。

- [P1][原理链完整性][Display 查询 API]
- **原文问题**：未指出 `Display` 常量与 `View` 常量的数值与语义不一致性。
- **核验结论**：`Display.FRAME_RATE_CATEGORY_NORMAL` (0), `HIGH` (1)；而 `View.REQUESTED_FRAME_RATE_CATEGORY_NORMAL` (3), `HIGH` (4)。
- **为什么这是重要缺失**：虽然两套 API 逻辑相似，但常量不可通用。开发者如果把 `Display` 获取的建议类别直接传给 `View` 或反之，会产生非预期的行为。
- **建议修正方向**：增加“开发者注意”小贴士，强调 `Display.getSuggestedFrameRate` 返回的是 Hz 值，其入参类别常量与 `View` 层投票常量是相互独立的。
