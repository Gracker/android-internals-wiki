## 四、P0 问题（事实错误）
- [P0][版本差异][VRR 分析标准]
- **原文问题**：在 SQL 查询和 Checklist 中多次提到“以 16.6ms 为阈值判断掉帧”。
- **技术背景**：Android 15+ 广泛引入 ARR（Adaptive Refresh Rate）。系统会根据内容动态调整 `VsyncPeriod`（例如从 8.3ms 跳变到 24ms）。
- **核验结论**：在 VRR 开启时，一帧耗时 20ms 可能完全不掉帧（因为系统预期就是 24ms）。
- **建议修正方向**：强制要求使用 `Expected Timeline` 作为基准。修正 SQL 示例，演示如何关联 `Expected` 轨道的 `dur` 来计算真实的掉帧偏差。

## 五、P1 问题（重要缺失）
- [P1][工具链][Perfetto SDK]
- **原文问题**：未提及 `androidx.tracing:tracing-perfetto`。
- **技术背景**：该 SDK 允许在非 root 设备上通过应用代码动态开启/关闭 Perfetto 追踪，且能与线上 FrameMetrics 联动，实现在 Jank 发生时自动保存 Trace 段。
- **为什么这是重要缺失**：它是解决“偶发性卡顿”无法线下抓取 Trace 的终极武器。
- **建议补充方向**：在“抓取 Trace”章节增加“线上动态 Trace 方案”子节。

- [P1][自动化][SQL 性能优化]
- **原文问题**：未提及超大型 Trace（>500MB）下 SQL 查询的崩溃风险。
- **建议修正方向**：
    - 推荐使用 `perfetto --query` 命令行离线分析。
    - 推荐使用 `CREATE TEMP TABLE` 缓存主线程/SF 等高频过滤结果，避免在全量 `slice` 表上进行多重 JOIN。
