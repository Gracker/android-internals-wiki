## 四、P0 问题（事实错误/原理严重断裂）

- [P0][原理链完整性][Freeform Resize 竞态条件/BLAST Sync 如何缓解 Resize 错拍]
  - **原文问题**：只提到了 `BLASTBufferQueue.cpp` 里的 `syncNextTransaction()`，将解决 Resize 错位完全归功于 App 侧和 BLAST，没有说明是谁在跨进程协调这件事。
  - **源码 / 一手资料锚点**：`frameworks/base/services/core/java/com/android/server/wm/BLASTSyncEngine.java`
  - **运行原理说明**：单靠 App 端的 `BLASTBufferQueue` 无法完成跨进程同步。真正的流程是：WMS 在发起 Resize 几何变化时，会通过 `BLASTSyncEngine` 创建一个 `SyncGroup`，**拦截并挂起**当前的窗口几何 `SurfaceControl.Transaction`。WMS 会等待 App 完成 measure/layout/draw，App 通过 BLAST 将带有新尺寸 Buffer 的 Transaction 传回给 WMS (`WindowContainer#onSyncTransactionReady`)。WMS 收集齐后，才会将几何变化与新 Buffer 合并为同一个 Transaction 提交给 SF，从而实现原子性。
  - **为什么错/属于断层**：原文把这一过程描述成了“BLAST 负责把它们并进同一帧”，读者看完依然是一个黑盒。实际上 WMS 的“拦截-等待-合并”才是保证不出现黑边的核心。
  - **建议修正方向**：必须引入 `BLASTSyncEngine` 的概念，明确说明 WMS 侧是如何阻塞提交并等待 App 的新 Buffer Transaction 的。

## 五、P1 问题（重要缺失）

- [P1][知识盲区][在 Perfetto 中识别多窗口问题]
  - **原文问题**：讲了看 App 主线程和 RenderThread，但缺失了最关键的 WMS 同步超时判定。
  - **源码 / 一手资料锚点**：`BLASTSyncEngine.java` 中的 timeout 机制。
  - **缺失内容**：如果 App 画得太慢（如 onConfigurationChanged 做了大量耗时操作），WMS 的 `BLASTSyncEngine` 等待时间（通常是 5 秒左右）超时后，会强行提交已有的几何 Transaction，不等新 Buffer 了。这会直接导致画面出现巨大的黑边/拉伸。
  - **运行原理说明**：在 Perfetto 中寻找 `wmSync` 或者 `SyncGroup` 相关的 Trace 块，如果看到等待时间极长甚至触发 timeout 强行 finish 的逻辑，可以直接断定是 App 端耗时过长破坏了同步机制。
  - **建议补充方向**：在 Trace 定位中，明确加入 WMS 侧 `wmSync` 等待/超时的排查思路。

- [P1][源码准确性][Shell 控制面与渲染边界]
  - **原文问题**：PiP 场景主要引用了 `PipTaskOrganizer.java`。
  - **源码 / 一手资料锚点**：`frameworks/base/libs/WindowManager/Shell/src/com/android/wm/shell/pip/PipTransition.java`
  - **缺失内容**：在 Android 12+ (尤其是 13/14) 全面引入 Shell Transitions 后，PiP 的过渡动画和 Transaction 提交大量转移到了 `PipTransition.java` 进行控制，`PipTaskOrganizer` 的职责有所收缩或被协同。
  - **建议补充方向**：建议同时提及 `PipTransition.java` 以体现最新的 AOSP 架构。

### 9.4 可复用知识资产（高价值新增知识）
- **章节**：18-pip-freeform.md
- **来源**：`cs.android.com` (`BLASTSyncEngine.java`)
- **关键类/方法**：`com.android.server.wm.BLASTSyncEngine`
- **可直接复用的技术结论**：在 Android 12 之后，解决多窗口调整大小产生黑边/拉伸的核心机制不仅是 `BLASTBufferQueue`，更关键的是 WMS 的 `BLASTSyncEngine`。它通过 `SyncGroup` 拦截当前窗口几何变化的 Transaction，强行阻塞提交，直到目标 App 进程绘制完新尺寸内容并通过 BLAST 返回 Transaction，WMS 才将其合并并**一次性（原子化）提交**给 SurfaceFlinger。
