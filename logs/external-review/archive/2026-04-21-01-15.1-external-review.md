## 四、P0 问题（事实错误）
- [P0][版本差异覆盖][性能优化之「道」 -> 持续优化]
- **原文问题**：“Android 8 引入 ProfilingManager 并开始支持更多动态 trace point。”
- **源码 / 一手资料锚点**：[Android 官方文档 - ProfilingManager](https://developer.android.com/reference/android/os/ProfilingManager)
- **关键代码逻辑**：`android.os.ProfilingManager`。
- **运行原理说明**：`ProfilingManager` 是允许应用在生产环境中请求系统收集性能数据（如 Heap Dump, System Trace）的服务。
- **版本差异**：`ProfilingManager` 是在 **Android 15 (API 35)** 引入的，并不是 Android 8。Android 8 并没有这个公开 API。
- **核验结论**：原文把 Android 15 的新特性写成了 Android 8 的特性，严重误导。
- **为什么错**：事实错误。
- **建议修正方向**：删除 Android 8 引入 ProfilingManager 的描述。可以将 Android 8 的演进改为 Android 8.0 引入了 SystemTracing API (如 `Trace.beginAsyncSection`) 或者 Atrace 的增强，并将 ProfilingManager 移至 Android 15 的演进描述中。

- [P0][版本差异覆盖][性能优化之「道」 -> 持续优化]
- **原文问题**：“Android 11-13 引入了 BlastBufferQueue 替代 BufferQueue、FrameMetrics API 暴露逐帧渲染耗时、以及 Baseline Profiles 等新机制”

- **关键代码逻辑**：`android.view.Window.OnFrameMetricsAvailableListener`
- **版本差异**：`FrameMetrics` API 是在 **Android 7.0 (API 24)** 引入的，绝不是 Android 11-13。
- **核验结论**：API 引入版本严重错误。
- **为什么错**：事实错误。
- **建议修正方向**：将 `FrameMetrics` 归类到 Android 7.0 的工具演进中。对于 Android 11-13，可保留 Baseline Profiles (通过 Jetpack 引入)。关于 BlastBufferQueue，不要用“替代”一词，BlastBufferQueue 底层依然使用 BufferQueue 进行跨进程内存传递。

## 五、P1 问题（重要缺失）
- [P1][知识盲区][测量本身会影响被测系统]
- **原文问题**：“Macrobenchmark 连续跑几十次冷启动，设备可能因发热触发降频，导致后几轮数据偏低。这些影响在单次测量中往往可以忽略... 或者用 `adb shell settings put global always_finish_activities 1` 配合固定屏幕亮度减少变量。”
- **源码 / 一手资料锚点**：[Macrobenchmark 官方文档](https://developer.android.com/topic/performance/benchmarking/macrobenchmark-overview)
- **关键代码逻辑**：`CompilationMode` 配置。
- **缺失内容**：在使用 Macrobenchmark 测量冷启动时，最大的变量实际上是**应用的编译状态（Compilation State）**（如 JIT 预热、AOT 编译、Baseline Profile）。
- **运行原理说明**：Macrobenchmark 框架自身会在每次迭代前自动调用 `killProcess()` 杀掉应用以确保冷启动，**完全不需要（也不推荐）手动设置 `always_finish_activities 1`**，后者是早期人工测试的 Hack 手段。同时，Macrobenchmark 的核心能力是控制 `CompilationMode`（如 `CompilationMode.None()`, `CompilationMode.Partial()`）来对齐基线，这是减少变量的最重要手段，但原文未提及。
- **为什么这是重要缺失**：给出了过时的 Hack 手段，却遗漏了现代 Benchmark 框架控制变量的最核心机制。
- **建议补充方向**：删除 `always_finish_activities` 的建议。补充 Macrobenchmark 通过控制 `CompilationMode` 和锁定 CPU 频率（如果在 Root 设备上）来减少变量的现代实践。

## 六、P2 问题（建议改进）
- [P2][交叉引用一致性][性能优化之「道」 -> 持续优化]
- **原文问题**：“Android 12 引入了 BlastBufferQueue 替代 BufferQueue”
- **问题描述**：BlastBufferQueue 并不是“替代” BufferQueue。BlastBufferQueue 的引入改变了 SurfaceFlinger 的合成提交方式，Producer 端通过 BLAST 提交事务，但底层跨进程的内存流转仍然建立在 BufferQueue 之上。
- **建议**：改为“Android 12 引入了 BlastBufferQueue，改变了 BufferQueue 的事务提交模式（将 Buffer 的提交合并到 WindowManager 的 SurfaceControl 事务中）”。
