## 四、P1 问题（重要缺失）

- **[P1][原理链完整性/知识盲区][Perfetto SDK 一节]**
- **原文位置**：`## 自定义 Trace Point 的最佳实践` -> `### 方法二：Perfetto SDK TRACE_EVENT`
- **原文问题**：只介绍了 `TRACE_EVENT`（TrackEvent），未提及 `Custom Data Source`。
- **源码 / 一手资料锚点**：`perfetto.dev/docs/instrumentation/tracing-sdk#custom-data-sources`
- **运行原理说明**：`TrackEvent` 只是 SDK 提供的顶层封装（用于写 Slice）。真正的高级用法是继承 `perfetto::DataSource`，重写 `OnSetup/OnStart/OnStop`，并利用 `NewTracePacket` 写入自定义的 Proto 数据。这是系统级开发者扩展 Perfetto 采集能力的关键。
- **缺失内容**：建议补充自定义数据源的类结构示意和注册流程。

- **[P1][知识盲区/数据分析][CI/CD 与批量分析一节]**
- **原文位置**：`## Trace Processor Python API 的高级用法` -> `### BatchTraceProcessor`
- **原文问题**：提到了 `BatchTraceProcessor`，但未提及 `Bigtrace`。
- **源码 / 一手资料锚点**：`perfetto.dev/docs/analysis/bigtrace`
- **缺失内容**：`BatchTraceProcessor` 适合单机批量处理（数十个 Trace）。当面对千万级 Trace 或需要云端 K8s 分布式查询时，必须使用 `Bigtrace`。它是 Perfetto 官方应对大规模性能回归测试的终极方案。
- **建议补充方向**：简要说明 Bigtrace 的 Orchestrator/Worker 架构及其在 GCS/S3 云存储上的应用场景。

- **[P1][原理链完整性][Metrics v2 一节]**
- **原文位置**：`## 自定义 Perfetto Metric` -> `### 旧版 Metric vs Trace Summarization`
- **原文问题**：提到了 `trace_summary`，但没讲清它与 **Perfetto Standard Library** 的关系。
- **运行原理说明**：Metrics v2 的核心不再是手写 SQL，而是调用 Standard Library 中已经封装好的 Module（如 `android.startup`）。用户通过 `spec` 指定 dimensions 和 values，底层自动调用标准库函数。
- **建议补充方向**：明确指出 v2 提倡“基于标准库”而不是“基于原始表”进行聚合。
