## 五、P1 问题（重要缺失）
- [P1][知识盲区][EAS 适用范围]
- **原文问题**：未明确指出 EAS 仅作用于 CFS（Completely Fair Scheduler）调度类任务。
- **源码 / 一手资料锚点**：`kernel/sched/fair.c` 中的 `find_energy_efficient_cpu` 仅在 `select_task_rq_fair` 中被调用。
- **关键代码逻辑**：RT（Real-Time）和 DL（Deadline）任务在唤醒时走的是 `kernel/sched/rt.c` 或 `kernel/sched/deadline.c` 的逻辑，它们优先保证延迟或硬时限，完全不考虑能量消耗。
- **运行原理说明**：由于 RT 任务具有更高的优先级，它们会直接抢占 CFS 任务，并强制 CPU 频率上升（通常触发调频器的极速响应）。如果不交代这一点，读者在 Perfetto 中看到 RT 任务“乱跳”或强占大核时会无法理解。
- **为什么这是重要缺失**：实战中，很多音频卡顿或系统响应慢是因为 RT 线程不合理的绑核或强占资源，这超出了 EAS 的管辖范围。
- **建议补充方向**：在“EAS 的前提条件”或“常见问题”部分补充说明：EAS 是为“公平”任务设计的，高优先级的 RT/DL 任务不受此节能逻辑约束，且它们的运行会干扰 EAS 的能效预测（因为它们“偷走”了 CPU 的计算容量）。

## 六、P2 问题（建议改进）
- [P2][源码准确性][能量模型函数名]
- **原文问题**：引用了 `em_pd_energy()`。
- **证据或观察依据**：在 Linux v5.10 之后，由于 EM 框架开始支持 GPU 等非 CPU 设备，该函数已重命名为 `em_cpu_energy()`。
- **问题描述**：对于使用较新内核（如 Android 13/14 设备，通常使用 5.10/5.15/6.1 内核）的开发者，搜不到 `em_pd_energy`。
- **建议**：标注该函数在 v5.10+ 版本中更名为 `em_cpu_energy()`。

- [P2][版本差异][Cgroup V2 状态]
- **原文问题**：提到“freezer 迁到 cgroup v2”，但未明确说明 CPU 控制器（cpuctl）的状态。
- **证据或观察依据**：根据 AOSP 文档和内核实现，Android 12 虽然引入了混合模式，但 CPU 控制器由于需要支持实时线程（RT）和线程级控制，仍保留在 Cgroup V1（`/dev/cpuctl`）。
- **问题描述**：如果不说明这一点，开发者可能会去 `/sys/fs/cgroup/cpu` 寻找 UClamp 设置而扑空（取决于具体内核实现，很多 Android 12 仍通过 V1 接口或 Task Profile 映射）。
- **建议**：在“Android 中的 uclamp 使用”部分补充说明：尽管 Freezer 已迁移，但 Android 12 的 CPU 控制器（用于管理 top-app/background 等）在主流设备上仍保留在 Cgroup V1 架构中，这是为了兼容 RT 线程调度。
