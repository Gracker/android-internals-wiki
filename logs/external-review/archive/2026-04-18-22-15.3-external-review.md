## 三、回炉问题摘要（P0 / P1）

### 1. [P0][源码准确性][第 222 行] LMK 杀进程依据描述错误

- **原文问题**：「Android 的 LMK 在决定杀哪个进程时，主要参考的就是进程的 PSS 值——PSS 越大的进程被杀的优先级越高。」
- **核验结论**：**完全错误**。Android 的 lmkd（Low Memory Killer daemon）决定杀哪个进程时，主要依据是 **`oom_score_adj`**（进程重要性等级），**不是 PSS**。`oom_score_adj` 越高的进程越容易被杀（如后台 cached app 的 oom_score_adj 为 900+，前台 app 为 0）。PSS 只在同等 `oom_score_adj` 等级的进程之间作为辅助参考——杀掉一个 PSS 更大的进程能释放更多内存。
- **源码锚点**：
  - AOSP: `system/memory/lmkd/lmkd.cpp` — `find_and_kill_process()` 函数
  - AOSP: `frameworks/base/services/core/java/com/android/server/am/ProcessList.java` — oom_score_adj 分级定义
  - 官方文档: `source.android.com/docs/core/perf/lmkd`
- **为什么这是 P0**：PSS 不是 LMK 的主要决策依据，这个错误会误导读者对 Android 内存管理机制的理解。一个 PSS 很大但 oom_score_adj 很低（如前台 app）的进程，不会被 LMK 优先杀掉。
- **建议修正方向**：改为「Android 的 lmkd 在决定杀哪个进程时，主要依据 `oom_score_adj`（进程重要性等级），`oom_score_adj` 越高的进程越先被回收。在同等重要性等级的进程之间，PSS 较大的进程可能被优先回收以释放更多内存。」

### 2. [P1][源码准确性][第 95 行] FrameMetricsAggregator 版本标注不准确

- **原文问题**：「线上则推荐使用 `FrameMetrics` API（Android 7.0+, API 24）或 `FrameMetricsAggregator`（Android 9.0+, API 28）」
- **核验结论**：`FrameMetricsAggregator` 不是 Android 9.0 (API 28) 引入的平台 API。它是 **Jetpack `androidx.core.app` 库**中的工具类，底层依赖 API 24 的 `FrameMetrics` API。它在 API 24+ 设备上均可使用，不需要 API 28。标注「API 28」是错误的。
- **一手资料锚点**：
  - 源码: `androidx.core:core` 库中的 `FrameMetricsAggregator.java`
  - 官方文档: `developer.android.com/reference/androidx/core/app/FrameMetricsAggregator`
- **建议修正方向**：改为「`FrameMetricsAggregator`（Jetpack `androidx.core` 库，需 API 24+）」

### 3. [P1][数据/案例支撑][第 116 行] 慢帧不良行为阈值描述与官方定义不匹配

- **原文问题**：「如果超过 50% 的用户会话中出现严重慢帧，Google Play 会认为你的 App 存在"不良行为"（Bad Behavior），这会直接影响 Play Store 中的曝光和推荐。」
- **核验结论**：
  1. **Slow Rendering（慢帧渲染）目前不是 Core Vitals**，属于 "Other Vitals"，不会直接触发不良行为标签或降权。Core Vitals 只包括 ANR 率、Crash 率、过度 WakeLock。
  2. **游戏的 Slow Sessions** 用 50ms 阈值（20 FPS），定义是"会话中超过 25% 的帧是慢帧"算一个 Slow Session，不是 "50% 的用户会话"。
  3. 文中的 "50%"、">50ms 严重慢帧" 与官方定义均不匹配。
- **一手资料锚点**：
  - 官方文档: `developer.android.com/topic/performance/vitals/render` — Slow Rendering 定义
  - 官方文档: `developer.android.com/games/playtime/slow-sessions` — 游戏 Slow Sessions 定义
- **建议修正方向**：
  1. 删除"不良行为"（Bad Behavior）的说法，改为"会影响 Google Play 的用户体验评估"
  2. 明确区分一般应用的 Slow Rendering（>16ms 帧比例）和游戏的 Slow Sessions（50ms/34ms 阈值，25% 帧比例）
  3. 如果要提不良行为阈值，应限定在 Core Vitals 范围内（ANR、Crash、WakeLock）

## 四、知识盲区摘要

### 1. JankStats 1.0 Stable 未被提及
- **重要程度**：中
- **描述**：JankStats 库已于 2025 年 10 月发布 1.0.0 稳定版（`androidx.metrics:metrics-performance:1.0.0`），是 Google 官方推荐的替代 `FrameMetricsAggregator` 的现代帧性能监控方案。文章仅提到了 FrameMetrics 和 FrameMetricsAggregator，未提及 JankStats。
- **建议研究方向**：在 Frame Time 或 Janky Frame Rate 段落补充 JankStats 的介绍，说明其相比 FrameMetricsAggregator 的优势（自动关联 UI 状态、支持回调过滤）
- **关联章节**：15.5（线上性能监控）

### 2. Android 15 ARR（Adaptive Refresh Rate）的影响
- **重要程度**：低
- **描述**：文中提到 120Hz 帧预算是 8.33ms，但 Android 15 引入了 ARR（Adaptive Refresh Rate），通过 View 系统的投票机制动态调整刷新率。这意味着帧预算不再是固定的 8.33ms 或 16.67ms，而可能动态变化。
- **建议研究方向**：补充 ARR 对帧预算和流畅性度量的影响
- **关联章节**：§4.2（VSync 与刷新率）

- **source.android.com**：
  - `source.android.com/docs/core/perf/lmkd` — lmkd 架构文档

### 2. 源码锚点
- **文件路径**：`system/memory/lmkd/lmkd.cpp`
- **关键方法**：`find_and_kill_process()`
- **关键字段**：`oom_score_adj`（不是 `oom_adj_score`，也不是 PSS）
- **为什么重要**：文中将 PSS 作为 LMK 的主要杀进程依据，实际上 `oom_score_adj` 才是首要依据

### 3. 版本差异摘要
- **Android 7.0 (API 24)**：FrameMetrics API 引入，FrameMetricsAggregator (Jetpack) 底层依赖
- **Android 10 (API 29)**：lmkd 引入 PSI 监控，替代固定内存阈值触发
- **Android 12 (API 31)**：SplashScreen API 引入，影响 TTID 用户感知
- **Android 16 (API 36)**：system-triggered profiling（已在文中正确提及）
- **2025-10**：JankStats 1.0.0 stable 发布
- **2026-03**：Excessive Partial Wake Lock 成为 Core Vital（已在文中正确提及）

### 4. Trace / Perfetto 观察点
- **观察点 1**：Power Rails track 中 VDD_CPU/VDD_GPU/VDD_DDR 的电流数据
- **观察点 2**：Energy Consumer track（Android 12+）按子系统拆分能量消耗
- **观察点 3**：Memory track 中 Java Heap 使用曲线与 GC 事件的关联

### 5. 可直接复用的技术结论
- lmkd 杀进程的首要依据是 `oom_score_adj`，PSS 只是同等优先级下的辅助参考
- FrameMetricsAggregator 是 Jetpack 库组件（androidx.core），不是 API 28 平台 API
- Slow Rendering 目前不是 Core Vitals，不会直接触发 Play Store 不良行为标签
- Android Vitals Core Vitals（2026）：ANR 率、Crash 率、过度 WakeLock——三项达标即为合格
- TTID 不良行为阈值：冷启动 5s / 温启动 2s / 热启动 1.5s
