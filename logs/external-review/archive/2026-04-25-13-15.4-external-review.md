## 五、P1 问题（重要缺失）
- [P1][源码准确性][am start -W 计时入口]
  - 原文问题：参考资料中将 `am start -W` 的计时入口指向 `ActivityManagerService.java`。
  - 源码 / 一手资料锚点：`frameworks/base/services/core/java/com/android/server/wm/ActivityMetricsLogger.java`。
  - 关键代码逻辑：自 Android 10 起，AM 与 WM 核心逻辑合并。启动计时的核心逻辑（包括 `TotalTime` 的计算）已迁移至 `ActivityMetricsLogger`。它负责记录从进程启动到 Activity 窗口首次绘制完成（Window Drawn）的时间。
  - 建议修正方向：更新源码参考路径，并简述 `ActivityMetricsLogger` 如何通过监听窗口状态变更来结束计时。

- [P1][知识盲区][编译模式的一致性（Stable State）]
  - 原文问题：提到编译模式有影响，但未说明如何将竞品强制拉齐到“稳定状态”。
  - 缺失内容：竞品通常已在用户手机上运行多日，处于 `speed-profile` 状态，而新安装的测试机处于 `quicken` 或 `verify`。这种“不公平”会导致 20% 以上的误差。
  - 建议补充方向：补充强制编译指令：`adb shell cmd package compile -m speed-profile -f <package_name>`。并解释为什么在竞品分析中应优先使用 `speed-profile` 而非全量 `speed`（以模拟真实用户体感）。

- [P1][原理链完整性][SplashScreen 对 TTID 的干扰]
  - 原文问题：提到了 SplashScreen 的影响，但未说明其在 Android 12+ 之后如何改变了 `TotalTime` 的物理含义。
  - 缺失内容：在 API 31+ 中，`TotalTime` 实际上包含了 SplashScreen 显示的时间。如果 App 使用了 `KeepOnScreenCondition`，`am start -W` 会等到该条件为 false 且首页第一帧画完才返回。
  - 建议补充方向：增加一个“避坑指南”，说明如何通过 Perfetto 的 `ActivityManager` track 区分“进程启动到 SplashScreen 显示”和“SplashScreen 到首页显示”的两段耗时。

## 六、P2 问题（建议改进）
