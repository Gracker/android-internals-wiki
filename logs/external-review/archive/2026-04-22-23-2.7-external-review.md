## 五、P1 问题（重要缺失）

- [P1][原理链完整性][Perfetto 识别部分]
- **原文问题**：提到“Hardware Layer 的 `buildLayer` 操作发生在 RenderThread”，容易误导读者只去 RenderThread 找。
- **源码 / 一手资料锚点**：`View.buildLayer()` 及其调用的 `updateDisplayListIfDirty()` 发生在 UI Thread。
- **关键代码逻辑**：`View.buildLayer` 在 UI 线程触发录制，RenderThread 接收 DisplayList 后执行具体的 GPU 命令分发。
- **运行原理说明**：`buildLayer` slice 在 UI 线程代表“录制指令”耗时，在 RenderThread 代表“GPU 渲染到纹理”耗时。
- **为什么这是重要缺失**：如果 View 树极其复杂，录制指令过程本身就会阻塞主线程，产生 Jank。
- **建议补充方向**：明确 `buildLayer` 在双线程的分布及其不同的性能含义。

- [P1][知识盲区][与 RenderEffect 的关系]
- **原文问题**：提到了二者是同一套机制，但未点透“FBO 共享”。
- **核验结论**：Android 12+ 底层 HWUI 会在 `LAYER_TYPE_HARDWARE` 已存在时，直接复用该 FBO 给 `RenderEffect` 使用。
- **为什么这是重要缺失**：这解释了为什么“硬件层 + RenderEffect”在静态内容上是显存和计算性能的最佳平衡点。
- **建议补充方向**：在“与 RenderEffect 的关系”中增加“FBO 共享机制”这一技术亮点。

### 9.4 可复用知识资产

- **源码锚点**：`frameworks/base/core/java/android/view/View.java` -> `buildLayer()`。明确了硬件层依赖 `mThreadedRenderer` 分发至渲染线程。
- **源码锚点**：`frameworks/base/graphics/java/android/graphics/RenderNode.java` -> `setUseCompositingLayer()`。API 29 起可用，是 View 层级以下最直接的建层控制手段。
- **技术结论**：`CompositingStrategy.ModulateAlpha` 在无重叠内容时是极致的性能选择，因为它物理上消除了 Render Target 切换。
- **Android 12+ 优化**：`RenderEffect` 与 `LAYER_TYPE_HARDWARE` 共享同一个 GPU 纹理/FBO，这使得在复杂动效中同时开启二者具有正向收益。
- **Trace 特征**：UI 线程的 `buildLayer` 反映“录制”成本，RenderThread 的 `buildLayer` 反映“渲染到纹理”成本。
