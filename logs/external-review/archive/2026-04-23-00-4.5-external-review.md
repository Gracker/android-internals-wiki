## 四、P1 问题（重要缺失）

- **[P1][知识盲区][Hardware Bitmap 统计口径]**
  - **原文问题**：文中称硬件 Bitmap "不计入 App 的 PSS"，这在宏观上可能导致误导。
  - **核查结论**：Hardware Bitmap 确实不计入 `Java Heap` 或普通的 `Native Heap`，但在 `dumpsys meminfo` 中，它会出现在 **"Gfx dev"** 或 **"EGL mtrack"** 栏目中。这部分内存依然属于进程的 PSS 总量。
  - **建议修正方向**：明确指出 Hardware Bitmap 在 `meminfo` 中的归属栏目，并说明它仍然会消耗系统的图形内存资源。

- **[P1][版本差异][heapprofd --java 支持版本]**
  - **原文问题**：文中提到 `heapprofd --java` 需要 Android 12+。
  - **源码/一手资料锚点**：根据 Perfetto 官方文档和 AOSP 提交记录，`heapprofd` 对 Java 堆采样的支持始于 **Android 11**。
  - **建议补充方向**：将版本要求修正为 Android 11+，以覆盖更多存量设备。

- **[P1][知识盲区][16KB Page Size 验证工具]**
  - **原文问题**：提到了适配建议，但缺少底层开发者常用的核验手段。
  - **源码/一手资料锚点**：开发者可以通过 `readelf -l <so_file> | grep ALIGN` 来确认 ELF 段是否已对齐到 `0x4000` (16KB)。
  - **建议补充方向**：在 16KB 迁移小节补充 `readelf` 命令作为核心验证资产。

- **[P1][原理链完整性][主动获取内存状态]**
  - **原文问题**：重点讲了 `onTrimMemory` 回调，但缺失了 App 如何"主动"查询当前内存压力的机制。
  - **源码/一手资料锚点**：`ActivityManager.getMyMemoryState(RunningAppProcessInfo outState)`。
  - **运行原理说明**：该 API 允许 App 在非回调时机主动获取当前的 `trimLevel`。
  - **建议补充方向**：在 `onTrimMemory` 小节增加对 `getMyMemoryState` 的提及，作为主动防御手段。
