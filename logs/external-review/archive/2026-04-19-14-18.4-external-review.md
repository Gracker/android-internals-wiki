## 四、P0 问题（事实错误）

- **[P0][源码准确性][打洞与合成 - 挖洞]**
  - **原文问题**：“具体机制不应简单固化为某个 clipOut() 调用... 可能是 WMS 侧的 Z-Order 配置让 SurfaceView Layer 自动穿透显示... SurfaceFlinger 侧通过 Layer 叠加策略处理”
  - **源码 / 一手资料锚点**：`frameworks/base/core/java/android/view/SurfaceView.java` 的 `draw(Canvas canvas)` 和 `dispatchDraw(Canvas canvas)` 方法。
  - **关键代码逻辑**：`SurfaceView` 的本质是在 Z-Order 位于主窗口之下（默认 `Z=-2`）。因此，如果主窗口本身有背景或者不透明，SurfaceView 就会被遮挡。为了让它显示出来，`SurfaceView.java` 在被硬件加速渲染时，会通过 `canvas.drawColor(0, PorterDuff.Mode.CLEAR)` 或相关机制，在主窗口的 Buffer 中将自己所占的矩形区域的像素强制擦除（即 alpha 变为 0，变为全透明），这就是所谓的“挖洞”。
  - **运行原理说明**：SF 和 WMS 从不“自动穿透”主窗口去打洞，它们只负责 Z-order 的叠加。透明度的打洞必须由宿主窗口（ViewRootImpl/RenderThread）显式在自己的 Buffer 里绘制透明色来实现。如果宿主不打洞，SF 叠加时主窗口的非透明像素就会挡住下面的 SurfaceView。
  - **核验结论**：原文对“自动穿透”的描述完全错误，扭曲了 Android 框架内 SurfaceView 的基础工作原理。
  - **建议修正方向**：明确指出“打洞”是由 SurfaceView 在宿主的 UI 树绘制过程中，通过 `PorterDuff.Mode.CLEAR` 将宿主对应区域像素透明化来实现的。

- **[P0][源码准确性][性能特征与陷阱 - 视频“飘移”]**
  - **原文问题**：“但这是一种‘减竞态’机制，不是对逐帧完美同步的绝对保证。”
  - **源码 / 一手资料锚点**：`frameworks/base/core/java/android/view/SurfaceControl.Transaction` 以及 Android 11+ 的 `BLASTSyncEngine.java` / Android 14+ 的 `SurfaceSyncGroup.java`。
  - **关键代码逻辑**：BLAST（Buffer Queue Layer And Surface Transaction）和 `SurfaceSyncEngine` 的引入核心目的**就是**为了提供绝对的、原子级的几何与 Buffer 同步保证。当 ViewRootImpl 发生大小/位置变化时，它会请求一个 Sync。在 Sync 期间，SurfaceView 的位置/尺寸更新 Transaction 不会立即 apply，而是会 merge 到 RenderThread 绘制主窗口 Buffer 结束时产生的那个 Transaction 中。
  - **运行原理说明**：SurfaceFlinger 只有在 latch 主窗口的新 Buffer 时，才会同时应用这个 Transaction 中包含的 SurfaceView 的位置和尺寸修改。这两个操作被打包在同一个 Transaction 中原子执行，因此对用户来说，主窗口的挖洞位置和 SurfaceView 的实际位置在同一帧发生绝对的同步，**彻底解决了飘移和撕裂问题**，而不仅是“减竞态”。
  - **核验结论**：原文将绝对同步的机制描述为“减竞态机制，不保证逐帧完美”，这是根本性的理解错误。
  - **建议修正方向**：修正为“这是一种原子级的强同步机制，能够保证主窗口 Buffer 与 SurfaceView 几何属性的逐帧完美同步”。

## 五、P1 问题（重要缺失）

- **[P1][版本差异覆盖][性能特征与陷阱 - 视频“飘移”]**
  - **原文问题**：只提到了 Android 12+ 上的 BLAST / Transaction 模型同步。
  - **源码 / 一手资料锚点**：`frameworks/base/core/java/android/window/SurfaceSyncGroup.java` (API 34+)。
  - **缺失内容**：未提及 Android 14 (API 34) 引入了更加完善的 `SurfaceSyncGroup` 来替代/增强原有的 `BLASTSyncEngine`。
  - **运行原理说明**：`SurfaceSyncGroup` 支持跨进程、跨窗口、多 Surface 的完美同步。对于多 SurfaceView 嵌套、或者 SurfaceView 与主 UI 之间的复杂动画（如背部手势返回、PIP 等），`SurfaceSyncGroup` 提供了一套标准化的机制来收集所有相关的 `SurfaceControl.Transaction` 并一次性 apply。
  - **为什么这是重要缺失**：因为文章声明适用版本到 Android 16，而 Android 14+ 中 `SurfaceSyncGroup` 是混合渲染同步的核心基础设施。
  - **建议补充方向**：补充 Android 11 引入 BLASTBufferQueue，Android 12/13 完善 BLASTSyncEngine，Android 14+ 全面采用 `SurfaceSyncGroup` 的版本演进线。
