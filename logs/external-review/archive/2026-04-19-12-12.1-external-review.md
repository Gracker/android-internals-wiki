## 五、P1 问题（重要缺失）
- [P1][知识盲区][第 442 行]
- 原文问题：描述 Baseline Profile 对体积影响时，仅说“对 APK 体积几乎无影响”。
- 源码 / 一手资料锚点：[ART Runtime: Profile-guided optimization](https://source.android.com/docs/core/runtime/jit-compiler#profile-guided-optimization)
- 运行原理说明：Baseline Profile 决定了哪些方法被 AOT 编译。AOT 产生的机器码存储在 `.odex` / `.vdex` 文件中。
- 缺失内容：Baseline Profile 会显著增加**磁盘占用（Disk Footprint）**。虽然下载的 APK 体积不变，但安装后生成的机器码体积通常比 DEX 字节码大 10%-30%。
- 为什么这是重要缺失：性能优化工程师需要平衡“启动速度”与“磁盘占用”，如果不提副作用，读者会盲目添加过大的 Profile。
- 建议补充方向：区分“下载体积”与“运行/磁盘体积”，明确 Baseline Profile 是以空间换时间的权衡。

- [P1][源码准确性][第 102 行]
- 原文问题：对 `resources.arsc` 的描述仅停留在“资源索引表”。
- 源码 / 一手资料锚点：AOSP `libs/androidfw/include/androidfw/ResourceTypes.h` 中的 `ResTable_header` 和 `ResStringPool_header`。
- 运行原理说明：`resources.arsc` 包含全局字符串池（Global String Pool）和包级别的类型/名称池。资源混淆工具（如 AndResGuard）的核心原理是修改 `ResTable_package` 下的 `Type String Pool` 和 `Key String Pool` 索引，而非仅仅重命名文件。
- 缺失内容：缺乏对字符串池引用的深入解释，这直接关系到为什么混淆后加载速度也能提升（池子变小，内存映射更快）。
- 建议补充方向：简述 `resources.arsc` 的三层池结构，解释混淆是如何减少 `resources.arsc` 内存加载开销的。
