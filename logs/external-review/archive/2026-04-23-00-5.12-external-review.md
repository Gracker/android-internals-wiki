## 六、P2 问题（建议改进）

### [P2][原理链完整性][ADPF Headroom]
- **原文位置**：`ADPF 带来的范式变化` -> `getCpuHeadroom()` 描述段落。
- **问题描述**：原文提到 `getCpuHeadroom` 返回 `[0, 100]` 的浮点数。
- **核验结论**：根据 Android 16 API 36 预览版文档，`getCpuHeadroom` 确实返回 `0.0` 到 `100.0` 之间的值（百分比），但建议明确强调这是一个“容量余量 (Capacity Headroom)”，它受当前频率限制（Throttling）的影响。如果 CPU 已经被限频，即使 Utilization 不高，Headroom 也会因为理论最大能力的缩减而迅速减小。
- **建议**：补充说明 Headroom 的计算公式：`Headroom = (Current_Max_Capacity - Current_Usage) / Total_Max_Capacity * 100`。

### [P2][知识盲区][Perfetto SQL]
- **原文位置**：`在 Perfetto 中分析 Thermal 问题`。
- **问题描述**：SQL 查询主要关注了 `counter` 轨道的 `value`。
- **核验结论**：在部分 OEM 平台上，`thermal_zone` 和 `cooling_device` 的 `track_id` 可能因为 Trace 启动时传感器的离线而发生偏移。
- **建议**：在 SQL 示例前，建议先通过 `SELECT id, name FROM counter_track WHERE name LIKE '%thermal%'` 确认轨道 ID。此外，针对 Android 12+，建议增加对 `android_thermal` 标准表（如有）的查询说明，该表在 System Trace 中提供更聚合的数据。

### [P2][数据/案例支撑][MAGT]
- **原文位置**：`MediaTek MAGT：vendor case study`。
- **问题描述**：对性能收益的百分比描述较为谨慎（这是好事），但缺少了一个核心的“观测点”。
- **核验结论**：MAGT 的核心优势在于“帧同步后的热余量共享”。
- **建议**：补充一个技术细节：MAGT 允许游戏通过 `ADPF` 的 vendor 扩展直接读取 SoC 的热压力曲线（不仅仅是 Headroom 一个数值），这在 Dimensity 9300+ 之后的平台是关键差异点。
