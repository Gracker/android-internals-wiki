## 四、P0 问题（事实错误）

- **[P0][原理链完整性/源码准确性][独立 Surface 与挖洞机制]**
  - **原文问题**：“Android 10+（BLAST）：通过 SurfaceControl.Transaction 原子性地管理挖洞区域和 Buffer 更新，减少了尺寸不同步导致的闪烁” （暗示 BLAST 替代了物理的绘制“透明洞”行为）
  - **源码 / 一手资料锚点**：`cs.android.com` 中 `frameworks/base/core/java/android/view/SurfaceView.java` 的 `dispatchDraw(Canvas canvas)` 方法。
  - **关键代码逻辑**：`SurfaceView` 的 `dispatchDraw` 依然并且一直会调用 `canvas.drawColor(0, PorterDuff.Mode.CLEAR)`（或者利用 `BlendMode.CLEAR`）在宿主 Window 的 Buffer 上画一个透明的矩形区域。
  - **运行原理说明**：“挖洞”的物理动作——即在 App 的主窗口缓冲区中让出对应区域的像素，是**始终存在**的。BLAST BufferQueue（主要在 Android 11+ 引入，并非 10）解决的是**时序同步**问题：它让 App 主窗口的这笔绘制（包含透明洞）的 Transaction，和 SurfaceView 自身 Buffer 尺寸变化的 Transaction 绑定在一起，交给 SurfaceFlinger 原子提交。
  - **核验结论**：原文把“同步机制的升级”错误理解成了“挖洞手段的替换”。
  - **建议修正方向**：明确指出“挖洞”本质上依然是在 View 树渲染时用 `CLEAR` 模式画透明色，而 BLAST 是为了保证这个“透明洞”的几何变化与 SurfaceView 自身内容的更新实现帧级别的原子同步，从而消除旧版本中的黑边/拉伸闪烁。同时修正 BLAST 大规模引入的实际版本（Android 11/12）。

## 五、P1 问题（重要缺失与偏差）

- **[P1][源码准确性][Z-Order 与图层结构]**
  - **原文问题**：“SurfaceView 的独立 Layer 通常位于 App 主窗口下方（Z=-1）”
  - **源码 / 一手资料锚点**：`frameworks/base/core/java/android/view/SurfaceView.java` 的 `mSubLayer` 字段及 `setZOrderMediaOverlay` 方法。
  - **关键代码逻辑**：默认情况下 `mSubLayer = -2`。当调用 `setZOrderMediaOverlay(true)` 时，`mSubLayer = -1`。当调用 `setZOrderOnTop(true)` 时，`mSubLayer = 1`。
  - **运行原理说明**：SurfaceFlinger 处理相对于宿主窗口的 Z-Order 时，默认预留了 -1 层给 MediaOverlay（例如视频播放器上层的独立字幕 SurfaceView），而本体 SurfaceView 默认是 -2。
  - **为什么这是重要缺失**：Z=-1 的说法在 AOSP 源码层面不准确，会误导开发者在处理多 SurfaceView 叠加（如画中画或视频+字幕）时的层级预期。
  - **建议补充方向**：修正默认值为 Z=-2，并顺带提及 `setZOrderMediaOverlay(Z=-1)` 和 `setZOrderOnTop(Z=1)` 的实战用途。

- **[P1][源码准确性][第三阶段：SurfaceFlinger 合成]**
  - **原文问题**：“Wait acquireFence：确保 GPU 完成绘制... 未 signal 时 SF 会等待”
  - **源码 / 一手资料锚点**：`cs.android.com` 中 `frameworks/native/services/surfaceflinger/BufferStateLayer.cpp` 的 `latchBuffer` 及 `SurfaceFlinger::handleMessageInvalidate` 逻辑。
  - **关键代码逻辑**：SurfaceFlinger 在收到 VSync-SF 后，遍历所有 Layer 准备合成。当检查到某 Layer 的 Buffer 对应的 `acquireFence` 尚未 signaled 时，SF **不会阻塞主线程等待**。
  - **运行原理说明**：如果 Fence 没 ready，SF 会选择**跳过**该 Layer 本帧的 `latchBuffer`（即维持上一帧的旧 Buffer 继续展示），并利用 `mPreviousBuffer` 继续走合成，同时触发下一次重绘请求。SF 的主线程是绝对不能被单个 Layer 的慢速 Producer 阻塞的。
  - **为什么这是重要缺失**：描述 SF 会“等待”传递了一个严重的错误性能模型，掩盖了 SF 必须在极短的时间窗口内完成遍历的核心设计。
  - **建议补充方向**：修正为“检查 acquireFence”。如果未 signal，SF 会跳过该 Layer 本帧更新（丢帧），而不是阻塞等待。

- **[P1][原理链完整性][SurfaceView vs TextureView 内存]**
  - **原文问题**：详细对比表中指出内存占用为 “1x Buffer” vs “1x Producer + 1x App Buffer”。
  - **缺失内容**：对 BufferQueue 实际深度的忽视。
  - **运行原理说明**：SurfaceView 不仅仅是一个单独的 Buffer，它拥有一个完整的 `BufferQueue`（默认深度通常为 2 或 3，即 Double/Triple Buffering）。TextureView 则是 Producer 端有一个独立的 `BufferQueue`（绑定到 SurfaceTexture），然后 RenderThread 消费它后再绘制到 App 窗口的 `BufferQueue` 中。所以实际上是 “1 个完整 BufferQueue” 对比 “2 个完整 BufferQueue”。
  - **为什么这是重要缺失**：写“1x Buffer”会让读者误以为 SurfaceView 内存极小。实际上一个 4K 的 SurfaceView Triple Buffering 会直接占用巨大的连续内存。
  - **建议补充方向**：修正为“1 个独立 BufferQueue (通常 2-3 个 Slot)” vs “2 个 BufferQueue (Producer 侧 + App 窗口侧)”。
