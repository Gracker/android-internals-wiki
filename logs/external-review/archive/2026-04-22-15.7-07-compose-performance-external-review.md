## 五、P1 问题（重要缺失/偏差）
- [P1][原理链完整性][Compose 动画性能]
  - **原文问题**：“`animate*AsState` ...内部通过 State 变化驱动重组，意味着每一帧动画都会触发重组。”
  - **源码 / 一手资料锚点**：官方文档《Jetpack Compose Performance - Defer reads as long as possible》。
  - **运行原理说明**：Compose 的 State 系统会在状态被**读取**的阶段记录依赖。如果 `animate*AsState` 返回的 State 仅仅是在 `Modifier.drawBehind { drawRect(color = color.value) }` 等 Draw 阶段被读取，那么动画期间**完全不会发生 Composition（重组）和 Layout**，只会触发 Draw 阶段的更新。
  - **为什么错 / 偏差**：原文断言 `animate*AsState` “意味着每一帧动画都会触发重组”，这是将 API 和状态读取阶段混为一谈了。关键不在于使用了哪个 API，而在于**State 在哪个阶段被解包（调用 `.value`）**。
  - **建议修正方向**：明确强调 State 读取阶段的重要性：如果将动画 State 直接传给 Composable 参数，会导致重组；如果延迟到 DrawScope 内读取，则完全跳过重组。

- [P1][原理链完整性][derivedStateOf：只在结果真正变化时才触发重组]
  - **原文问题**：讲解了 `derivedStateOf` 的用法，但没说其反面陷阱。
  - **缺失内容**：未说明何时**不要**使用 `derivedStateOf`。
  - **运行原理说明**：`derivedStateOf` 内部维护了一套监听机制，会有少量的性能开销。如果派生状态的输出变化频率和输入状态完全一样（比如 `derivedStateOf { scrollState.value * 2 }`），它并不能减少任何重组，反而白白增加了对象创建和计算开销。
  - **为什么这是重要缺失**：初学者最容易犯的错就是“为了性能把所有 State 都套上一层 `derivedStateOf`”。
  - **建议补充方向**：明确一条铁律——仅当“输入状态高频变化，而派生结果低频变化（如连续的 offset 映射为 true/false 的 boolean）”时，才使用 `derivedStateOf`。
