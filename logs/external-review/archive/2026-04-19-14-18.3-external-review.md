## 四、P0 问题（事实错误）

- [P0][源码准确性][18.3.1 软件渲染的触发条件]
- **原文问题**：将 `View.setLayerType(LAYER_TYPE_SOFTWARE, null)` 作为触发当前章节描述的“软件渲染全链路”的条件之一，并在下文断言软件渲染“全链路执行流程... 核心特征是没有 RenderThread 参与。所有操作都在 UI Thread 上完成”。
- **源码 / 一手资料锚点**：`frameworks/base/core/java/android/view/View.java` 的 `setLayerType`，`RenderNode.java`
- **关键代码逻辑**：当一个 Window 开启硬件加速时，设置某个 View 的 LayerType 为 Software，仅仅意味着在 `updateDisplayListIfDirty` 阶段，该 View 树会被绘制到一个由 CPU 支撑的 `Bitmap` 上（此时会用 Skia CPU Backend，在 UI Thread 发生）。但这块 Bitmap 最终仍会被包装为一个硬件纹理节点（Layer），交由 **RenderThread** 的 GPU 绘制管线进行合成上屏。
- **运行原理说明**：View 级 Software Layer 和 Window 级软件回退是两回事。Window 级软件渲染才会绕过 RenderThread 直接通过 `ViewRootImpl.drawSoftware` -> `Surface.lockCanvas` 锁定整个屏幕的 GraphicBuffer。
- **为什么错**：如果读者在代码中看到了 `setLayerType(LAYER_TYPE_SOFTWARE)`，然后在 Trace 里寻找本文描述的“无 RenderThread，只有 UI Thread 的 lockCanvas”，他们会完全迷失，因为 RenderThread 依然非常活跃，且依然有 `SyncFrameState`。
- **建议修正方向**：从“软件渲染的触发条件”中移除 `setLayerType(LAYER_TYPE_SOFTWARE)` 作为**全局链路**触发条件的表述。或者在文中明确区分“Window 级全局软件渲染（无 RenderThread）”和“View 级局部软件渲染（生成 Bitmap，仍有 RenderThread）”，并说明本章主干讲的是前者。

## 五、P1 问题（重要缺失）

- [P1][版本差异覆盖][18.3.1 软件渲染的触发条件]
- **原文问题**：提到“直接使用 `Surface.lockCanvas()` ... 走的是纯 CPU 路径”时，没有提示现代 Android 的对应替代方案。
- **源码 / 一手资料锚点**：`frameworks/base/core/java/android/view/Surface.java` 的 `lockHardwareCanvas()` (API 23+)
- **缺失内容**：从 Android 6 开始，直接对 Surface 绘图已经不再必须走纯 CPU 路径，系统提供了 `lockHardwareCanvas()` 返回一个由 RenderNode 支持的硬件加速 Canvas。
- **运行原理说明**：很多时候开发者以为脱离了 View 树直接画 Surface 就必然没有硬件加速，这是典型的旧时代误区。
- **为什么这是重要缺失**：AIW 的目标是指导性能优化。如果是为了优化性能而脱离 View 树直接操作 Surface，读者必须知道应该优先使用 `lockHardwareCanvas` 才能利用 GPU 算力。
- **建议补充方向**：在提到 `lockCanvas()` 的地方，补充对比 `lockHardwareCanvas()`，指出 API 23+ 后的正确高性能画板做法。

- [P1][原理链完整性][18.3.5 性能特征与适用场景]
- **原文问题**：解释 CPU 密集原因时，只提到了“浮点运算和内存读写（如读写 8MB 数据）”。
- **源码 / 一手资料锚点**：`frameworks/native/libs/gui/Surface.cpp` 中 `GraphicBuffer::lock` 使用的 `GRALLOC_USAGE_SW_WRITE_OFTEN` 及其在底层 Gralloc/ION 中的行为。
- **缺失内容**：GraphicBuffer 通常是在 DMA-BUF 分配的，它的内存属性通常是 uncached 或者 write-combined。CPU 读写这种内存的性能惩罚远高于读写普通的 JVM Heap 或 Native Heap 里的 RAM。
- **运行原理说明**：特别是 Dirty Rect 的 `copyBlt` 阶段（从 `mPostedBuffer` 拷回数据），如果 Gralloc 没有分配带 Cache 的内存，CPU 去执行大量内存 `Read` 时，将遭受灾难性的性能拖累。这也是为什么软件渲染在某些机器上卡顿极其夸张的根本原因（不仅是算得慢，更是访存极慢）。
- **为什么这是重要缺失**：只说“8MB 读写”不足以解释它为什么比普通的 Bitmap 读写慢得多。必须点破 GraphicBuffer DMA 内存与 CPU Cache 的关系。
- **建议补充方向**：在“内存带宽瓶颈”小节补充说明 GraphicBuffer 内存的 Gralloc 映射特性（uncached/write-combined）导致的 CPU 访存惩罚。

## 六、P2 问题（建议改进）

- [P2][数据/案例支撑][18.3.4 Trace 视角]
- **原文问题**：“几乎看不到 DrawFrame、dequeueBuffer、queueBuffer 等 RenderThread 的 slice。”
- **证据或观察依据**：`dequeueBuffer` 和 `queueBuffer` 只是不在 RenderThread 里了，但由于 `lockCanvas` 和 `unlockAndPost` 内部调用了 `Surface.cpp` 的机制，它们依然会在 Systrace 的 UI Thread 中被记录。
- **建议**：修正说法为“RenderThread 处于闲置状态，`dequeueBuffer` 和 `queueBuffer` 等底层 BufferQueue 操作会直接出现在 UI Thread 的 `lockCanvas` 和 `unlockCanvasAndPost` 调用栈内”。

- **建议**：在场景与特性部分，补充一句由于 Skia CPU Backend 的限制，部分硬件 API 在软件渲染下会被忽略或表现异常。
