## 四、P0 问题（事实错误）
- [P0][版本差异覆盖][模式三：SurfaceControl / 独立 child layer]
- **原文问题**：将 SurfaceControl 路径描述为“跨版本差异很大……证据不完整时，这里应标成 `[待验证]`”，将其视为一种神秘的“候选路径”。
- **源码 / 一手资料锚点**：
  - AOSP: `frameworks/base/core/java/android/webkit/WebView.java` 并非关键。关键在 Chromium 源码 `android_webview/browser/gfx/hardware_renderer.cc` 与 `browser_view_renderer.cc`，以及 AOSP 侧提供的 API `android.graphics.HardwareRenderer` / `ASurfaceControl` (API 29)。
- **关键代码逻辑**：
  - 从 Android 10 (Q) 开始，平台引入了 `ASurfaceControl` API。Chromium WebView 实现了 `WebViewSurfaceControl` feature。
  - 当启用时，WebView 的 HardwareRenderer 不再仅仅是给 RenderThread 提供 Functor 回调，而是直接创建一个挂载在 App Window `SurfaceControl` 下的 Child `SurfaceControl`。
  - 网页的 Viz 线程独立向这个 Child Surface 提交 Buffer（通过 Vulkan 或 GL），完全绕过宿主的 `RenderThread` 主绘制流。
- **运行原理说明**：SurfaceControl 不是“候选路径”，而是 Google 针对 WebView 滚动不掉帧、视频独立合成等痛点给出的现代标准解法（在 Android 13+ 和较新内核中逐渐默认开启）。它实现了真正的合成器解耦。
- **版本差异**：Android 10 引入底层支持，后续 Chromium 逐步灰度，现代版本已规模化启用。
- **核验结论**：原文对现代 WebView 最核心的性能提升机制（SurfaceControl）认知停留在“无法确认”的阶段，属于对重要系统演进的事实性判断失误。
- **建议修正方向**：明确指出 Android 10+ 引入的 `WebViewSurfaceControl` 机制，解释其如何通过 Child Surface 实现 Viz 线程独立提交，绕过宿主 RenderThread 同步开销。

## 五、P1 问题（重要缺失）
1.
- [P1][原理链完整性][进程模型概述 & 模式一]
- **原文问题**：进程模型图中写 `Main -> Commit -> Comp -> Tile`，并说 `Comp -> SurfaceControl/SurfaceTexture -> Services`，未讲清与 GL Functor 的结合原理。
- **源码 / 一手资料锚点**：Chromium `components/viz/` 和 `android_webview/browser/gfx/`
- **缺失内容**：缺失 Viz Display Compositor 在 App 进程的角色说明。
- **运行原理说明**：在 WebView 中，Renderer 进程（Sandboxed）的 Compositor 会生成 `CompositorFrame`，跨进程发送给宿主 App 进程中的 Viz Display Compositor。在 GL Functor 模式下，宿主 `RenderThread` 执行 Functor 时，实际上是触发了运行在宿主进程的 Viz Display Compositor 执行 DrawGL/DrawFn，将 `CompositorFrame` 渲染到宿主的 Canvas 上。原文对这一交互过程描述为黑盒（`WP->>WP: Execute WebView Draw Path`），导致读者无法理解跨进程后到底怎么画的。
- **为什么这是重要缺失**：不懂 Viz 在 App 进程的代理角色，看 Perfetto 时就无法理解 `CrGpuMain` 或 `Viz` 线程为什么和 App RenderThread 产生强烈的锁竞争和时序依赖。
- **建议补充方向**：明确 Viz Display Compositor 运行在宿主进程，以及 Functor 本质上是触发 Viz 把收到（来自 Renderer）的帧画到宿主 FBO 上。

2.
- [P1][原理链完整性][模式二：SurfaceView Wrapper]
- **原文问题**：“网页请求全屏内容时……这个 view 经常承载全屏视频……可能是 SurfaceView、TextureView，也可能是外层包装容器。”
- **缺失内容**：未明确指出该模式的触发**唯一先决条件**。
- **运行原理说明**：`WebChromeClient.onShowCustomView` 并不是 WebView 内部根据内容大小自动决定的（比如网页元素撑满屏幕不会触发），它 **只在** 网页 JS 显式调用 HTML5 Fullscreen API（如 `video.requestFullscreen()`）时才会被 Chromium 触发。
- **为什么这是重要缺失**：容易误导开发者以为“全屏尺寸的 WebView 播放视频就会走这个路径”。如果不调用 Fullscreen API，视频依旧是在 GL Functor 中渲染，占用 RenderThread 的时长。
- **建议补充方向**：强调 `onShowCustomView` 的触发前提是 HTML5 Fullscreen API。

### 9.4 可复用知识资产（高价值新增知识）
- **章节**：13-webview-rendering.md
- **一手资料链接或来源类型**：Chromium / AOSP Source (WebViewFunctor)
- **关键源码路径**：AOSP `frameworks/base/libs/hwui/pipeline/skia/GLFunctorDrawable.cpp`, Chromium `android_webview/browser/gfx/`
- **关键类 / 方法 / 字段**：`WebViewSurfaceControl`, `ASurfaceControl`, `DrawFn`
- **关键调用链 / 代码逻辑摘要**：在 SurfaceControl 模式下，WebView 获取宿主 ViewRootImpl 的 `SurfaceControl` 作为 parent，创建独立的 child `SurfaceControl`。Viz 线程通过 Vulkan/GL 将渲染好的网页帧 buffer 直接 queue 给这个 child surface，从而由 SurfaceFlinger 统一合成，避免阻塞宿主 RenderThread。
- **版本差异摘要**：Android 5-9 为老一代 GL Functor；Android 10 引入 Hardware Draw Functor (支持 Vulkan) 以及 ASurfaceControl；后续版本 Chromium 逐步默认开启 `WebViewSurfaceControl` 避免动画掉帧。
- **Trace / Perfetto 观察点**：开启 SurfaceControl 时，Perfetto 中的 SurfaceFlinger 区域会多出一个独立的 Layer 属于 WebView，且宿主 RenderThread 里的 `DrawFunctor` 耗时会大幅度下降甚至消失（只在几何形变时通信）。
- **为什么这条知识值得保留**：这是解决 WebView 滑动掉帧与宿主 UI 掉帧相互影响的终极解法，对深度性能优化极为关键。
