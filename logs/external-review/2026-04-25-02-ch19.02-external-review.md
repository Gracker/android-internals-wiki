## 五、P1 问题（重要缺失）

- **[P1][版本差异/原理链完整性][Trace Canary 的工程边界]**
  - **原文问题**：“AGP 8.x 之后 `android.registerTransform` 已不再是可用入口。新项目接入时要先确认所用版本...适配当前 AGP。”
  - **缺失内容**：没有给出 AGP 8.x 时代 Matrix 的真正生存现状和适配方案。
  - **运行原理说明**：Matrix 官方仓库主分支（截至 2.1.0）尚未正式兼容 AGP 8。核心的 Trace 插桩强依赖已废弃的 Transform API。目前社区和实际工程中的标准解法是迁移至 AGP 8 推荐的 Instrumentation API (`AsmClassVisitorFactory`)。
  - **为什么这是重要缺失**：如今新项目几乎默认使用 AGP 8+，只抛出“确认适配”的建议属于黑盒化描述，读者读完仍然不知道怎么解决编译报错（`API 'android.registerTransform' is removed`）。
  - **建议补充方向**：明确指出 Matrix 官方版本对 AGP 8.x 的兼容现状，补充必须通过 `variant.instrumentation.transformClassesWith(AsmClassVisitorFactory::class.java)` 替代旧 Transform 的技术演进方向。

- **[P1][数据/案例支撑][全局/大纲要求]**
  - **原文问题**：大纲明确要求“补一个 Trace Canary 启动慢或慢函数案例，要求有报告字段... 补一个 IO Canary 案例”，但在正文中缺失。
  - **缺失内容**：具体的 Matrix Issue 报告示例（至少包含关键字段）。
  - **为什么这是重要缺失**：脱离了具体的 Report 字段（如 `stackKey`, `cost`, `method id`），读者无法建立对“Matrix 报上来的数据长什么样”的直观认知，纸上谈兵。
  - **建议补充方向**：构造或引用一个真实的 Trace Canary 慢函数/卡顿 Issue 数据结构片段，演示从 `stack` 字段拿到 `method id` 的过程。

## 六、P2 问题（建议改进）

- **[P2][原理链完整性][Trace Canary 的工程边界]**
  - **原文问题**：“混淆后需要稳定的 mapping / method map 关系，否则线上报告难以阅读。”
  - **问题描述**：并未解释 `method map` 是怎么来的。
  - **建议**：补充说明 Matrix 在编译期字节码插桩时，会给每个方法分配一个整数 ID 并生成 `methodMapping.txt`，线上的 payload 只包含方法 ID，必须依赖服务端结合该 txt 文件进行反解。这是 Trace 模块“数据怎么读”的核心知识。

- **[P2][知识盲区][模块怎么分 / 接入建议]**
  - **原文问题**：提到了 Battery Canary、MemGuard、Pthread Hook，但大纲要求“给 Battery Canary、MemGuard、pthread hook 的使用前提和风险边界”，正文并未点出具体的风险。
  - **问题描述**：Battery Canary 依赖大量的系统 API Hook（如 AMS、PMS、AlarmManager 等系统服务），在不同定制 ROM 上极易触发兼容性 Crash 或行为异常。Pthread Hook 依赖底层 PLT Hook，也容易因系统库更新或架构变更引发稳定性问题。
  - **建议**：在接入建议中，明确提出这三个深水区模块的“高崩溃/兼容风险”，强调它们不应作为默认开启的选项，必须配合云端下发配置和极低采样率灰度。
